# 一致性哈希在数据库

<div class="epigraph">
<p>节点与键放在环上，加节点只搬邻居区间。虚拟节点把负载摊匀。数据库用它当分片函数，仍要处理范围查询与事务。</p>
<footer>—— 据 Karger et al. consistent hashing；计算机栏一致性哈希课接到分片；Cassandra</footer>
</div>

[上一课](/cs/distributed-deadlock)处理跨节点等待。本课不 probe。缺口是再平衡搬家量：模 $N$ 哈希在 $N{+}1$ 时几乎全搬。一致性哈希（consistent hashing）让加删节点只影响环上相邻键。计算机课已有 [一致性哈希](/cs/consistent-hashing)；数据库进阶接到副本、虚节点、与范围分片对照。

## 问题

环：节点哈希到圆，键顺时针找后继。虚拟节点：每物理机多个点，改善均匀。缺口是 **SQL 范围**：环打散键则 `BETWEEN` 打全体节点，与范围分片相反。事务：跨相邻虚节点仍可能跨物理机。副本：后继 $R$ 个节点存副本，故障沿环走——与 Paxos 组划分不同。

<span class="marginnote">把哈希空间想成钟面：每台机器、每个键都被针扎在某个时刻位置上；一个键顺时针走，碰到的第一台机器就是它的主人。加一台新机器只是插进某个时刻点，它只接管顺时针到下一台机器之间那一小段键。</span>

再平衡：新节点从后继偷走一段，拷贝时双路由，同再平衡课。

<span class="marginnote">Karger et al. 一致性哈希（DHT 谱系）。Cassandra 令牌环是数据库著名实现。本课不重推哈希函数。</span>

## 方法

选：写均匀、节点频繁进出 → 环。范围扫描、时间局部 → 范围分片。混合：先租户范围再租户内哈希。查询路由：协调器算令牌。二级索引仍头痛。

与缓冲：无关直接。与 LSM：各节点本地 LSM，环只定键归属。

```mermaid
flowchart TD
  K["键哈希上环"] --> N["后继节点"]
  ADD["加节点"] --> MV["只搬邻接弧"]
  RNG["范围查询"] --> ALL["可能 scatter 全环"]
```

## 机制

虚拟节点数少则不均匀，多则元数据大。一致性哈希不给外部一致，只给键放置。读己之写仍要会话。倾斜：热键仍打一点，要打散后缀或单独拆。

从 4 台扩到 5 台，两种分片各搬多少：

```mermaid
flowchart TD
  Q["从 4 台扩到 5 台"] --> MOD["模 N 分片：key mod N 全变"]
  MOD --> M1["约五分之四的键重新映射"]
  M1 --> M2["几乎全量搬家与拷贝"]
  Q --> RING["环分片：只有新节点的弧易主"]
  RING --> R1["约五分之一的键搬家"]
  R1 --> R2["其余键原地不动"]
```

<span class="marginnote">虚节点的数字感受：100 台物理机、每台放 100 个虚节点，环上就是 1 万个点，负载波动被摊到约 1% 的粒度；若每台只有 1 个点，运气差的机器可能比平均值多扛三成——虚节点是用更多元数据换均匀。</span>

死锁：环不解决锁序。分片键课的热点病在环上变成单虚节点热。

## 边界

本课不比共享磁盘。也不把 DHT 动态成员当 Spanner 目录。RocksDB 是节点内引擎，后课。

后课默认：均匀写可用令牌环；范围查询慎用。无共享对共享存储：机器是否共用盘阵。

搬家量 $O(1/N)$ 是环的卖点，不是查询卖点。

<span class="marginnote">初学者容易把「一致性哈希」的「一致」读成分布式一致性（共识）。两者无关：这里的 consistent 只指加删节点时键的归属大体保持不变，与 Paxos 那套 consensus 是两个英文词、两码事——环上照样可能写入后立刻读到旧值。</span>

## 小结

- 一致性哈希减加节点搬家；范围查询与事务不自动变好。
- 虚节点摊负载；热键仍要另拆。
- 无共享对共享存储下一课。
- 出处：Karger et al.；Cassandra；分片课。
