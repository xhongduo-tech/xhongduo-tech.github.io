# 星型模式

<div class="epigraph">
<p>事实表存度量与外键，维表存描述属性：分析查询沿键连维，是受控反规范化，不是忘了 3NF。</p>
<footer>—— 据 Kimball 维建模；Inmon 对照；5NF 反规范化课的分析落地</footer>
</div>

[上一课](/cs/sqlite-architecture)收束嵌入式 OLTP。本课打开分析与流：数仓经典星型（star schema）。缺口是查询形状：`SUM` 按多个描述属性切。规范化 OLTP 要许多跳连接；星型把维退化成键，事实极窄、极长。雪花是维再规范化。OLAP 立方下一课预聚合。

## 问题

度量（销售额）在事实；谁、何时、何地在维。缺口是**键**：代理键、退化维、缓慢变化维（SCD）类型——维上属性改了历史事实如何指。与 3NF：维常不满足 BCNF，这是读路径合同，写走 ETL 受控。

位图索引、列存在事实与低 NDV 维上极合适。分区按时间在事实表。

<span class="marginnote">Kimball 维建模。Inmon 3NF 企业数仓是另一派，本课点名不站队。事实粒度量错会让所有合计不可加。</span>

## 方法

声明粒度（一行订单行）。ETL 灌代理键。查询：事实 join 维，聚合。优化器：星型变换（先维过滤再探事实）是特殊改写，broadcast 维表。与 shuffle 课对接。

物化：常用汇总事实表，刷新合同即 MV 课。

<span class="marginnote">术语翻译：粒度（granularity）就是「事实表里一行代表什么」——一行代表一张订单，还是代表一个订单里的一个商品行项？粒度越细，同一笔生意在事实表里行数越多；一旦把两个粒度的行混进一张表，所有 SUM 都会把同一件事算两遍。</span>

```mermaid
flowchart TD
  F["事实: 键 + 度量"] --> D1["维"]
  F --> D2["维"]
  FILT["维属性过滤"] --> BIT["位图 / 下推"]
  BIT --> F
```

## 机制

计划：维小可广播。无事实表分区裁剪则扫全部历史。HTAP：OLTP 3NF 与星型副本 CDC。文档反规范订单是另一种星（嵌套维）。

一条典型的「按地区看 2025 年销售额」查询在星型上的走法，正是星型变换优化器改写的对象。

```mermaid
flowchart LR
  Q["查询: 按地区按季度 SUM 销售额"] --> DF["先过滤维表: 地区 = 华东 年 = 2025"]
  DF --> PK["取命中维的代理键集合"]
  PK --> PF["用键集合探测事实表"]
  PF --> AG["对命中事实行做 SUM"]
  AG --> ANS["按维属性分组输出"]
```

校准：列存扫事实。学习优化器对星型连接顺序有偏见搜索。

<span class="marginnote">数字实例：一张 10 亿行的事实表，若「地区」维只有 32 个值、年份只有 10 个值，先用维表把范围缩到 1/320 再探事实，就比全表扫 10 亿行少扫约 99.7% 的行——这就是星型变换「先维后事实」的全部含义。</span>

## 边界

本课不讲 cube 操作符。也不把星型当事务模式。湖仓可用星型逻辑、Parquet 物理。

后课默认：分析模型先定粒度再星型。OLAP 立方：预先 rollup 的格，查询切块。

粒度错了，再快的列存也加错数。

## 小结

- 星型：窄事实+宽维，受控反规范服务聚合查询。
- 星型变换与广播维表是计划特化。
