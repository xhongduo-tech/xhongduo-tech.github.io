# 指针认证 PAC

<div class="epigraph">
<p>ARMv8.3 把短 MAC 塞进指针闲置位：改地址而不重签，使用时校验失败。密钥在内核/EL 管理，用户态任意写不再能静默改返回地址或函数指针。</p>

</div>

上一课[CET](/cs/shadow-stack-cet)是 x86 侧的硬件 CFI：影子栈钉住控制流转移的边。本课补 ARM 一侧的缺口——**指针签名**（PAC，ARMv8.3 起）：改地址而不重签，使用时校验失败。本课讲两件事：签什么、密钥放在哪；不给伪造 PAC 的步骤。

后课默认已经读完本课钉下的合同，只补差，不从该领域第一性原理重开。

## 问题

64 位虚拟地址用不满高位，指针里留有闲置位。PAC 用掉它们：对「地址 + 上下文（如 SP）」用密钥算一个短标签，替换进闲置位；写入时签名，取用前认证。返回地址、函数指针这类一旦被改就能劫持控制流的数据都可签。攻击者若改了地址而不重签，认证时标签对不上，跳转即失败。缺口有二：密钥若泄漏，签名形同虚设；标签位宽有限，有碰撞可能。本课只陈述余量有限，PAC 须与其他缓解配合，不当唯一防线。

### 不是加密内存

常见误读是「PAC 加密了内存」：并没有。数据载荷仍是明文，PAC 只管**指针值本身**的完整性——没签过的指针照常用，签过但被改的指针报错。保密性归加密与特权隔离管。

<span class="marginnote">ARM Pointer Authentication。Linux 以 `HWCAP_PACA` 报告支持。PAC 密钥（APIA、APDB 等）由 EL1/EL2 写入系统寄存器，用户态读不到。本课禁止绕过教程。</span>

## 方法

方法是与 CET 对照着读：CET 的影子栈管**边**（返回必须落回影子栈记录的地址），PAC 管**指针值**（指针被改则认证失败），保护对象不同，可以叠加。密钥按特权分离：内核与用户态各用各的密钥寄存器，用户态的任意写构造不出内核的签名。下一课：从硬件缓解走到语言迁移。

```mermaid
flowchart TD
  P["指针"] --> SIGN["PAC 签名"]
  SIGN --> USE["认证后使用"]
  TAMPER["改地址"] --> FAIL["校验失败"]
```

## 机制

机制要点是认证时机：签名与认证成对出现在函数序言与尾声（或编译器插入的位置），任何未经认证的写都无法把改过的指针送进间接跳转；短 MAC 的安全性在于「改地址必须重签，重签需要密钥」。控制数据的完整性由此有了指令级标签，但这是缓解不是根治——内存破坏仍在，只是被转化为可观测的失败；根治仍是少写 C。下一课内存安全语言迁移：类型与所有权进编译器。

## 边界

本课不分析 PAC 碰撞的构造，也不给绕过案例。内存安全语言下一课。

## 小结

- CET 钉控制流的边；PAC 钉指针值本身。
- 短 MAC 藏在指针闲置位；密钥由更高特权持有。
- 位宽有限、密钥可泄漏，须与其他缓解叠加。
