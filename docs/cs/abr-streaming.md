# ABR 自适应码率

<div class="epigraph">
<p>播放器根据吞吐估计与缓冲水位在阶梯码率间切换，逼近瞬时可用带宽，避免卡顿或无谓的 4K。</p>
<footer>—— 据 Huang et al. 缓冲基 ABR；DASH/HLS 实践；Kurose 多媒体节整理</footer>
</div>

[DASH/HLS](/cs/dash-hls) 提供阶梯。[速率自适应](/cs/mimo-rate-adaptation) 在 Wi‑Fi PHY。[上一课](/cs/dash-hls) 留下选哪一档。缺口是 **ABR 控制**：吞吐估计、缓冲、振荡。本课不把 CDN 层次写完。

## 问题

可用带宽随 Wi‑Fi、蜂窝、同屋流变化。固定高码率则再缓冲；固定低则浪费 $C$。ABR：测最近分片吞吐，看缓冲秒数，选下一表示。过敏则码率振荡（视觉差），过钝则卡。与 TCP CC 叠：ABR 在应用，CUBIC 在运输，双环。BBR 下估计更稳或仍抖，取决于实现。

不要把 ABR 写成 5G 切片保证。

<span class="marginnote">缓冲基（BBA）等算法。本课不点名商业播放器。</span>

<span class="marginnote">数字实例：阶梯码率常见如 240p 约 0.4 Mbps、720p 约 3 Mbps、1080p 约 6 Mbps。网络实际只有 4 Mbps 却锁 1080p，每秒就欠 2 Mbps，缓冲几十秒后耗尽必然卡顿；自动降到 720p 反而能一秒不断。</span>

<span class="marginnote">直觉类比：TCP 拥塞控制在运输层「探路有多宽」，ABR 在应用层「看路况决定开多快」——两个环叠着转。若 ABR 对吞吐的每次抖动都立刻反应，就会像新手司机一样忽快忽慢（码率振荡），所以估计必须滤波。</span>

### 应用层跟踪可用带宽

与 TCP/BBR 双环，要滤波防振荡。令牌桶边缘限速会表现为「网慢」。清单缺中间档则跳变。

## 方法

对照：基于吞吐 / 基于缓冲 / 混合。画：下片 → 估 BW → 选档。与令牌桶：边缘限速会让 ABR 降档，表现为「网很慢」。

```mermaid
flowchart TD
  THR["分片吞吐"] --> DEC["选码率"]
  BUF["缓冲水位"] --> DEC
  DEC --> NEXT["下一分片 GET"]
```

## 机制

CDN 不同 POP 吞吐不同，切换 POP 像路径变。ECN 膨胀影响估计。QUIC 迁移换路要重新估计。无线 TCP 误码让吞吐锯齿，ABR 应滤波。与 WFQ：隔离后估计更干净。

安全：恶意慢片可诱骗降档，点名。

第一张图画的是选档吃哪两路输入；这张图回答第二个问题：同样的输入下，缓冲水位落在哪个区间，决策就完全不同——这就是缓冲基算法的核心逻辑。

```mermaid
flowchart TD
  BUF["当前缓冲秒数"] --> LOW{"逼近危险线？"}
  LOW -->|"是，快没片了"| DOWN["降档：先保不卡"]
  LOW -->|"否"| MID{"水位充裕？"}
  MID -->|"一般"| HOLD["维持当前档"]
  MID -->|"是"| UP["升档：试更高码率"]
  DOWN --> NEXT["请求下一分片"]
  HOLD --> NEXT
  UP --> NEXT
```

<span class="marginnote">常见误区：初学者容易以为 ABR 的目标是「尽量播最高清」。实际目标是卡顿与画质的折中——一次三秒的转圈缓冲，比全程 720p 难受得多。若阶梯清单里缺了中间档位，控制算法再好也只能在 0.4 和 6 Mbps 之间大幅跳变。</span>

## 小结

- 吞吐与缓冲驱动选档。
- 与 TCP/BBR 形成双环，要滤波。
- 目标是卡顿与质量折中，不是峰值码率。
