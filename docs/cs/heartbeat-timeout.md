# 心跳与超时

<div class="epigraph">
<p>空闲连接与半开要用主动心跳在应用层刷新；超时值要大于 RTT 与短暂拥塞，小于用户可忍受的失败检测。</p>
<footer>—— 据 RFC 1122 对照；gRPC keepalive；WebSocket ping 整理</footer>
</div>

[TCP keepalive](/cs/keepalive-half-open) 太慢。[成帧](/cs/message-framing) 已能发小消息。[上一课](/cs/message-framing) 留下存活检测。缺口是**应用心跳**：间隔、超时、与 RTO 叠。本课不把重试写完。

## 问题

反向代理、NAT、Maglev 都可能静默丢空闲。应用 ping/pong：间隔 15–60 s 常见，远短于 TCP keepalive。超时：连续未应答则拆，触发发现换后端。与 NTP 无关。无线调度抖动要给余量，否则假死。SSE 用注释行当心跳。QUIC PING 帧。过频心跳在万连接上成 C10K 负载。

不要把心跳当业务数据。

<span class="marginnote">直觉类比：半开连接像「对方早挂了电话，你这边通话图标还亮着」——中间设备悄悄掐线，两端都不知情。心跳就是每半分钟互相喊一声「还在吗」，喊了没应答再挂断，才知道通话真的断了。</span>

<span class="marginnote">间隔无唯一 RFC。本课钉原则。</span>

### 值在 RTT 与 NAT 之间

太短杀卫星会话，太长留半开。心跳也是 C10K 负载。三层心跳要错开防同步。不是业务数据。

<span class="marginnote">数字实例：跨洋 RTT 约 150 毫秒，卫星链路 600 毫秒还常抖到 1 秒；家用 NAT 的 UDP 表项常 30–60 秒无流量就删。于是「间隔 15–30 秒、连续 2 次未应答才判死」是从这些数字之间夹出来的常见取法。</span>

## 方法

对照：传输 keepalive / 应用心跳 / LB 健康检查。画：定时发 → 等 pong → 失败则关。与 ICE 刷新一致。

```mermaid
flowchart TD
  TMR["定时"] --> PING["心跳帧"]
  PING --> PONG["应答"]
  FAIL["超时"] --> CLOSE["拆连接并发现"]
```

## 机制

超时 $\lt$ 2×RTT 会在卫星上误杀。超时 >> NAT 会话则半开。与 ABR 无关。服务发现心跳是控制面，连接心跳是数据面会话。

超时值的下界与上界各由谁决定：

```mermaid
flowchart TD
  T["选超时值 T"] --> LO["下界: 盖住 RTT+抖动余量"]
  LO --> E1["低于它: 慢链路被误杀"]
  T --> HI["上界: 压住 NAT 空闲与用户耐心"]
  HI --> E2["高于它: 半开堆积, 故障发现慢"]
  LO --> WIN["T 落在窗口内"]
  HI --> WIN
```

<span class="marginnote">常见误区：初学者以为心跳「只是保活，没有安全面」。无认证的心跳等于送分——攻击者开一万条连接只回 pong 不做业务，就把你的连接表与心跳算力占满。心跳帧要与会话认证绑定，陌生人答了也不算数。</span>

安全：无认证的心跳可被用来保活攻击连接表，要绑会话。

- 应用心跳补 NAT 与代理空闲策略。
- 超时在 RTT 与用户等待之间。
- 规模上心跳也是负载。
