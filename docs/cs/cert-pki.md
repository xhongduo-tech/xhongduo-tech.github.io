# 证书与 PKI

<div class="epigraph">
<p>证书把公钥绑到名字，并用另一把私钥签名；信任是对签发者的，不是对那串比特本身的神秘属性。</p>
<footer>—— 据 RFC 5280（X.509）；Anderson 对 PKI 失败模式的整理</footer>
</div>

[上一课](/cs/mac-signature)给出可公开验证的签名。本课不重写验签算法。缺口是：对方递来的公钥为什么是「银行」而不是中间人。[TLS 入口](/cs/mac-signature)已经假定证书存在；这里把 PKI 收成：根锚、链、撤销，以及信任锚本身是配置不是协议推出来的。

## 问题

信封和签名都要 $pk$。若 $pk$ 来自刚连上的对端，威胁模型里的主动者可以换钥匙。缺口不是新的公钥算法，而是**绑定**：证书 = 名字 + 公钥 + 元数据，由 CA 的私钥签名。<span class="marginnote">证书可以类比成公证处盖章的介绍信：写明「持钥者叫这个名字、钥匙长这个样（公钥）、有效期到哪天」，公证处（CA）用它的私钥盖章。你不认识持钥人没关系，只要信任公证处不会乱盖章——信任的落点从「千百个对端」缩到「少数几个 CA」。</span>验证者预置根证书，沿链验到叶子。名字还要与用户意图（主机名）一致，否则链再真也绑错对象。

<span class="marginnote">浏览器根程序决定锚。CA 被骗或被强制签发，链仍然密码学合法——PKI 的完整性依赖 CA 与撤销，不单依赖签名方案。</span>

## 方法

X.509 链：叶子由中间签，中间由根签。验证：路径、有效期、密钥用法、主机名（SAN）。撤销：CRL 或 OCSP，失败策略决定可用性与安全的挤法。本课不把 CT 日志的全部生态写完，只承认：仅验链不够应对误签，透明日志是补丁。

```mermaid
flowchart TD
  ROOT["预置根锚"] --> CHAIN["验证书链"]
  CHAIN --> NAME["名字匹配"]
  NAME --> SESS["后课会话 / 口令"]
  CHAIN --> PWD["后课: 口令与加盐"]
```

## 机制

PKI 把「谁的公钥」从每次人工比对指纹，变成对少数锚的信任。这服务 TLS 握手里的服务器认证；客户端证书较少见，机制相同。与[两阶段提交](/cs/two-pc)对照：2PC 假设参与者身份已定；PKI 要在开放网络上建立身份。锚泄露或算法过时，要轮换根——那是运维，不是握手能单独修的。

主机名检查发生在链验证之后：链真而名字错，仍是中间人几何。

```mermaid
flowchart TD
  LEAF["服务器递来叶子证书"] --> V1{"每个签名能验到预置根锚？"}
  V1 -->|"否"| F1["拒绝：链断，公钥无出处"]
  V1 -->|"是"| V2{"整条链都在有效期内？"}
  V2 -->|"否"| F2["拒绝：过期或未生效"]
  V2 -->|"是"| V3{"密钥用法与主机名匹配？"}
  V3 -->|"否"| F3["拒绝：链真但绑错对象"]
  V3 -->|"是"| OK["信任建立，握手继续"]
```

<span class="marginnote">这张图回答「验证一个证书到底查几道、各挡什么攻击」：第一道挡「假钥匙」（没出处），第二道挡「旧钥匙」，第三道挡「真钥匙绑错名」。初学者最容易省略第三道——攻击者拿一张自己域名的合法证书，链完全真，就能顶替银行；名字对不上必须拒。</span>

## 边界

不要把 DANE/DNSSEC 与 Web PKI 混成一课。也不把「自签证书」当成 PKI 失败：它只是把锚放到对端自己，适合已有带外信任。<span class="marginnote">自签证书类比「自己给自己写介绍信」：对外没人认，但在你已经认识对方的小圈子里（公司内网、自己的设备），把信任锚直接设成对方本人反而省去公证处一环——这是合法用法，不是体系故障。判断标准是「锚怎么进到验证者手里」有没有带外保证。</span>本课不讲区块链替代 CA。

叶子密钥轮换要发新证书；锚轮换要更新每个验证者的预置，周期长得多。后课默认：开放网上的公钥来自证书链与名字检查；人的口令是另一条身份路径，要单独存储与盐。

时间错误会让有效证书被拒、过期证书被收。可用与完整在时钟上相遇，本课只要求验证包含有效期。

## 小结
- 链上的每一个签名都要验；跳过中间用途检查等于换锚。
- 后课口令是人的秘密路径，与机器证书并列，不互相替代。

- 签名可验；本课把公钥绑到名字，信任落在根锚与 CA。
- 链合法 ≠ 名字对、≠ CA 没被骗。
- 人记得的秘密如何存，是口令课缺口。
- 出处：RFC 5280；Anderson, *Security Engineering*；对照 RFC 8446 对证书的使用。
