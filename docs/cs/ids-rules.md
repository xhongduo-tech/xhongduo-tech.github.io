# Snort / Suricata 规则

<div class="epigraph">
<p>规则把协议字段、内容匹配与流状态写成可部署的谓词。写得好能抓住已知形态；写得太宽则误杀。规则是知识压缩，不是应用规格。</p>
<footer>—— 据 Snort Users Manual 对规则语言；Suricata 对规则兼容的陈述</footer>
</div>

上一课[IDS/IPS](/cs/ids-ips)给了盒子。缺口是**规则怎么写才算合同**：协议、端口、内容、流。本课讲形态与维护，不提供针对特定 CVE 的利用匹配教程。

后课默认已经读完本课钉下的合同，只补差，不从该领域第一性原理重开。

## 问题

特征规则对已知利用有效，对加密与变形弱。缺口是：版本管理、测试流量、禁用噪声规则。Emerging Threats 一类社区集要审查后启用。

<span class="marginnote">「特征规则」翻译成大白话：一条 if 语句——「如果是从这个端口来的 TCP、载荷里出现这几串字节，就报警」。它的上限就是「见过并写下来的样子」，所以本课说规则是知识压缩：规则集是已知攻击的压缩档案，不是对应用的完整理解。</span>

### 内容匹配的限度

多态与编码让字节特征老化。协议状态比裸字符串稳。

<span class="marginnote">Snort 规则语法公开。课程禁止用规则开发当攻击演练。蜜罐下一课提供另一类观测。</span>

## 方法

读一条规则的头与选项（概念：msg、flow、content）。对照 Suricata 多线程。下一课蜜罐。

<span class="marginnote">读规则的顺序感：头（动作 协议 源地址 源端口 → 目的地址 目的端口）回答「在哪看」，选项（msg、flow、content、sid）回答「看什么、看见了说什么」。缺了 `flow:established` 这类状态约束的字节特征最容易误伤无关流量——误报多半源于头写得太宽。</span>

```mermaid
flowchart TD
  HDR["协议与地址"] --> OPT["内容与流选项"]
  OPT --> ALERT["告警或丢弃"]
  OPT --> TUNE["测试减少误报"]
```

## 机制

签名是过时的知识。要与威胁情报和下下一课 ATT&CK 映射，否则规则集膨胀。蜜罐提供低误报的触点。

```mermaid
flowchart TD
  W["编写签名规则"] --> T["回放测试流量验证"]
  T -->|"误报过多"| T2["收窄：补协议与流约束"]
  T2 --> T
  T -->|"可部署"| E["启用并接入威胁情报"]
  E --> AGE["变形与加密让特征老化"]
  AGE --> RET["审查后替换或下线"]
```

<span class="marginnote">规则集膨胀为什么危险：几万条规则逐包匹配会拖垮检测吞吐，一条过时规则还会对着每次扫描反复误报。与威胁情报对齐、定期审查下线，维护的其实是「信噪比」——不是规则越多越安全。</span>

## 边界

不写针对生产的攻击规则。蜜罐下一课。

## 小结

- IDS 要规则才认识形态。
- 协议状态优于裸字符串；要测试误报。
- 加密与变形让特征老化。
