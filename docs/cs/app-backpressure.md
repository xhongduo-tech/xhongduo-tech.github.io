# 应用层背压

<div class="epigraph">
<p>慢消费者必须让生产者少发：窗口、阻塞写、队列上限或显式信号。否则内存当无限缓冲，延迟与 OOM 替代了丢包。</p>
<footer>—— 据 TCP 窗口对照；Reactive Streams 背压；RFC 9113 流控整理</footer>
</div>

[TCP 窗口](/cs/tcp-window) 与 [PFC](/cs/pause-pfc) 已给下层反压。[C10K](/cs/c10k-concurrency) 的事件循环若盲目 `read` 会堆内存。[上一课](/cs/retry-idempotency) 的重试会加重生产者。缺口是**应用背压**：把反压接到业务。本课结束计算机网络进阶；下一课进入数据库，先命名[关系模型](/cs/relational-model)。

## 问题

运输窗口满则 `write` 阻塞或 EAGAIN，这是 TCP 背压。应用若在用户态无限队列「先收着」，等于把膨胀搬进进程，心跳仍绿、业务已死。H2/QUIC 每流窗口是应用可见的运输背压。Reactive 流 `request(n)` 显式拉。令牌桶在入口限速是策略背压。SSE 若生产快于浏览器，要停生成器。

不要把杀进程当背压。

<span class="marginnote">背压可以想象成水管下游堵了，水压顺着管子顶回上游，逼着水龙头关小。程序里同理：消费者处理不过来时，用某种信号让生产者少发或慢发。没有这根「回水管」，生产者只管发，多出来的数据就全靠内存替它兜着，兜到爆为止。</span>

<span class="marginnote">HTTP/2 流控。Reactive Streams 规范。本课钉原则。</span>

### 有界缓冲才是反压

无限用户态队列取消 rwnd 的意义。可与 PFC、H2 窗口叠三层。重试在满载时要停。「先打进队列」只是改名膨胀。

## 方法

对照：无限队列 / 有界队列阻塞 / 窗口 / 丢弃策略。画：快生产 → 信号 → 减速。与 DCTCP 浅队列同构，一层应用。

```mermaid
flowchart TD
  PROD["生产者"] --> Q["有界队列"]
  Q --> CONS["消费者"]
  FULL["满"] --> BP["阻塞或窗口减"]
```

<span class="marginnote">rwnd（接收窗口）是接收方每次告诉发送方「我还能再收多少字节」的额度：额度大发得快，缩到 0 就必须停。它就是 TCP 自带的背压信号——本课做的事情，本质上是把这个「按接收方消化能力发货」的思想搬进应用代码。</span>

## 机制

gRPC 流控、TCP rwnd、PFC 可叠三层；只开一层会在其它层爆。重试在背压时要停。负载均衡把溢出转到它机是横向背压。测量：队列深度与 p99，不是只看 iperf。

```mermaid
flowchart TD
  CONS["慢消费者：处理跟不上"] -->|"队列满，暂停拉取"| APP["应用层：有界队列 / request(n)"]
  APP -->|"缓冲堆积，接收窗口收缩"| TCP["传输层：TCP rwnd"]
  TCP -->|"网卡缓冲吃紧，发 PAUSE"| L2["链路层：PFC"]
  L2 --> SLOW["上游源头减速，内存不再膨胀"]
```

<span class="marginnote">初学者容易以为服务「没挂」就没问题：心跳和存活探针只看进程活着，不看队列堆积。无限队列把崩溃推迟成延迟爆炸——p99 从 10 毫秒涨到 10 秒，用户早已流失，监控面板却还是绿的。所以要盯队列深度和 p99，而不是只看存活探针。</span>

与端到端：最终仍要消费者处理完，背压只是保护途中内存。

## 小结

- 无限用户态队列取消了运输窗口的意义。
- 用窗口、有界阻塞或显式 request。
- 与 PFC/rwnd 分层叠，不要只信一层。
- 后课只引用本课钉死的对象，不从该领域总问题重开。
