# seccomp 过滤

<div class="epigraph">
<p>seccomp 在系统调用入口按过滤器决定允许、拒绝或杀死；过滤器看到的是调用号与参数的受限视图，不是攻击脚本。</p>
<footer>—— 据 Linux seccomp(2)；内核文档对 BPF 过滤器的整理</footer>
</div>

[上一课](/cs/container-os)仍把完整系统调用表暴露给容器内进程。[系统调用路径](/cs/syscall-path) 在陷入后按号分发。缺口是**调用号过滤器**：在分发前截住，缩小内核攻击面。本课只讲机制与允许/拒绝结果，不讨论如何绕过过滤器。

## 问题

容器切了 pid 与根，`mount`、`ptrace`、稀有 ioctl 仍可能到达同一内核。若用户态策略是「只许 read/write/exit」，需要内核强制。seccomp-BPF：进程安装过滤器，此后每次系统调用跑该程序，返回允许、ERRNO、KILL 等。strict 模式更粗（只许极少调用）。缺口不是罗列调用号清单，而是：过滤器是只读的、可继承的、安装后通常不可再放宽。<span class="marginnote">「seccomp-BPF」翻译成大白话：一段只读小程序，在每次系统调用的门口值班，只准看调用号和有限的参数字段，看完必须给出一个裁决——放行、报错或杀死进程，没有任何「商量」的余地。</span>

<span class="marginnote">过滤器不能当通用沙箱替代：仍共享内核。参数检查能力有限，不能替代 IOMMU 或用户命名空间。本课不给示例去探测内核。</span>

## 方法

进程（或运行时在 exec 前）安装过滤器。陷入：硬件路径同前，内核在进入具体 syscall 实现前求值。允许则照常 copy 参数、执行；拒绝则不进入实现。与 ptrace 的对照：ptrace 可拦截但重、且用途是调试；seccomp 是声明式子集。容器运行时常用「默认拒绝 + 白名单」。

```mermaid
flowchart TD
  TRAP["系统调用陷入"] --> FILT["seccomp 过滤器"]
  FILT --> OK["允许: 原路径"]
  FILT --> NO["拒绝/杀死: 不进入实现"]
```

## 机制

seccomp 把「谁可以请内核做什么」从「有 fd 和 uid」再收一层到「有哪些 syscall」。它发生在 [syscall-path](/cs/syscall-path) 的门口，不改页表。与 setuid 不同：不提升身份，只减操作面。不能替代虚拟机：敏感特权指令若在用户态乱执行，仍是非法指令，不是 seccomp 的对象——下一课才把「客内核执行特权指令」当问题。

「默认拒绝 + 白名单」落到过滤器程序内部，就是一次对调用号的集合判断，两个出口各自对应容器里看到的不同现象：

```mermaid
flowchart TD
  A["过滤器读入调用号 nr"] --> B{"nr 在白名单集合内?"}
  B -- "在" --> C["return ALLOW"]
  C --> F["内核照常执行该调用"]
  B -- "不在" --> D["return ERRNO / EPERM"]
  D --> E["用户态调用返回 -1"]
  E --> G["errno = EPERM, 进程未死"]
```

与 setuid 的差别还可以这样记：<span class="marginnote">常见误区：初学者容易以为「装了 seccomp 就是沙箱、内核漏洞就挡住了」——实际上进程仍在同一个内核里执行，只是能按的门铃变少了；内核自身的漏洞利用如果恰好用白名单内的调用，过滤器一个字节也拦不住。</span>

## 边界

本课不引入每条 BPF 指令的编写教程当攻击工具。不讨论如何使过滤器失效。下一课真正的虚拟化：客机认为自己在环 0，宿主要在敏感指令上陷入并模拟。

后课默认：本机进程的 syscall 面可裁。客内核的特权指令如何交给宿主，下一课陷阱与模拟。<span class="marginnote">「可继承」可以想象成闸机过闸：子进程从 fork 出来的那一刻起就带着和父进程相同的过滤器规则，且只能更严不能放松——所以容器运行时总是抢在 exec 目标程序之前装好过滤器，装晚了就再没有机会收紧了。</span>

## 小结

- seccomp 在 syscall 入口按过滤器允许或拒绝。
- 减面，不提供第二内核；本课无利用内容。
- 客机特权指令是 trap-and-emulate 的缺口。
- 出处：Linux `seccomp(2)`；内核 seccomp 文档。
