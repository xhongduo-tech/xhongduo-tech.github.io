# 密钥管理与 HSM

<div class="epigraph">
<p>算法正确只覆盖「运算」；密钥的生成、存放、使用、轮换、销毁才覆盖生命周期。HSM 把私钥关进盒子，让「算而不出」成为策略，而不是再加长 AES。</p>
<footer>—— 据 NIST SP 800-57；Anderson 对密钥生命周期；对照 PKCS #11 的角色分工</footer>
</div>

上一课[HKDF](/cs/hkdf)会派生多把键。缺口是**这些比特住在哪**。原语课序在 HKDF 结束；本课序从生命周期起。不重写 PRF 定义。

后课默认已经读完本课钉下的合同，只补差，不从该领域第一性原理重开。

## 问题

软件密钥在进程内存、交换分区、日志、快照里复制。威胁模型若含内存读取，AEAD 帮不上。HSM/TEE 提供：键不导出、使用要授权、审计。缺口是管理平面，不是又一种分组密码。

### HSM 不是魔法

盒子固件、管理卡、备份密钥、提权路径仍是 TCB。Anderson：多数事故是流程，不是因式分解。

<span class="marginnote">SP 800-57 分密钥类型与周期。PKCS #11 是常见 API 形状。后课 seL4 从微内核验证谈 TCB；本课只把 HSM 当密钥的引用监视器。</span>

## 方法

列出状态机：生成/注入、激活、轮换、吊销、销毁。对照软件 KMS 与硬件。签名与解密在盒内完成，主机只见明文业务数据或密文。备份用拆分或封装钥。

```mermaid
flowchart TD
  GEN["生成"] --> USE["盒内使用"]
  USE --> ROT["轮换"]
  ROT --> DEST["销毁"]
  USE --> POL["授权与审计"]
```

## 机制

最小特权落到键：谁能调用 Sign。前向保密下一课问会话键是否短命——HSM 管长期根，不自动让会话遗忘。二者要一起设计。

第一张图讲键的一生；这张回答具体问题：**「算而不出」在机器层面是什么样**——主机递进去的从来不是密钥请求，而是待处理的数据。

```mermaid
flowchart TD
  APP["主机应用"] -->|"送入待签哈希"| HSM["HSM 内部"]
  POL{"策略：这把键<br>允许该应用/操作吗？"} -->|"拒绝"| NO["返回错误并记审计"]
  POL -->|"允许"| SIG["盒内用私钥运算"]
  SIG -->|"只送出签名"| APP
  KEY["私钥"] --> SIG
  KEY -->|"永不导出"| BOXOUT["仅销毁或备份封装，不出盒"]
```

<span class="marginnote">直觉类比：HSM 像银行柜台的点钞机——钞票（待签数据）递进去、结果（签名）递出来，而点验的规则和现金的存放都在柜台内部；你能决定「办不办这笔业务」，却永远摸不到保险库本身。</span>

<span class="marginnote">数字实例：常见实践里，直接加密业务数据的密钥数月一换，而保护它们的根密钥数年一换、深藏 HSM；层次化的关键好处是轮换下层键时根密钥纹丝不动——换的不是保险库，只是保险库里的一只抽屉。</span>

<span class="marginnote">常见误区：初学者容易以为「把 AES 换成更长的密钥」就能补上管理缺漏。密钥泄漏发生在内存、交换分区、日志、快照这些**存放环节**，算法再强也照泄不误；HSM 缩小的正是这个暴露面，而不是数学强度。</span>

## 边界

本课不写某厂商的管理口令默认值清单当利用手册。下一课前向保密：长期根泄漏后历史会话是否仍保密。

## 小结

- HKDF 产出键；本课管键的住处与谁能用。
- HSM 让私钥不可导出成为策略。
- 生命周期失败比算法过时更常见。
