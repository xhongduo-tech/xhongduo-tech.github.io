# SDL

<div class="epigraph">
<p>安全开发生命周期把威胁建模、设计审查、工具门禁、事件响应写进版本列车。它是过程控制，不是一次扫描。微软 SDL 是公开的工程模板之一。</p>

上一课[TCB](/cs/tcb-minimization)要求信任基可审；缺口是**组织如何持续生产较小的 TCB**——答案是写进发布过程：门禁。本课 SDL。

后课默认已经读完本课钉下的合同，只补差，不从该领域第一性原理重开。

## 问题

没有安全活动的发布火车会持续回归：每批新功能把旧缺口重开一遍。缺口是在四个位置插入活动——需求阶段做威胁模型，把「信任谁、防谁」写成设计约束；编译与测试挂 sanitizer 和静态分析当门禁；依赖进 SBOM 审查；发布前过就绪检查，事件响应留轮值。

### 度量

度量要接住风险：漏洞密度与平均修复时间是过程健康指标；一旦直接当 KPI 考核，就会被「少报漏洞、关单求快」优化掉，变成虚荣指标。

<span class="marginnote">Howard–Lipner。seL4 下一课是另一极端：形式验证微内核。</span>

## 方法

方法是把课程已讲的活动按阶段插上火车：fuzz 挂测试，代码审查挂合并，SBOM 挂依赖准入，事件响应挂运维轮值。SDL 的主张是过程控制——门禁随每次构建自动执行，不是发布前的一次性扫描。下一课 seL4 封课程。

```mermaid
flowchart TD
  REQ["需求威胁模型"] --> DES["设计审查"]
  DES --> IMP["工具门禁"]
  IMP --> REL["就绪与响应"]
```

## 机制

SDL 的机制是把课程钉下的合同物化成列车上的门：威胁模型变成设计审查清单，sanitizer 变成合并门禁，SBOM 变成依赖准入。每道门把一类错误挡在发布之前；过程输出可审计，组织知识不随人员流动丢失。它不证明代码正确，只保证错误必须过门。形式验证下一课把微内核收到可机检证明。

## 边界

不把 SDL 写成官僚表格：每道检查项都要能说出它挡住的失效模式，说不出的一项就是纯开销。seL4 形式验证下一课。

## 小结

- TCB 要过程才能保持小。
- 威胁模型到门禁到响应是闭环。
- 工具是门，不是一次性扫描。
- 下一课 seL4 形式验证。
