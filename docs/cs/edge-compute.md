# 边缘计算

<div class="epigraph">
<p>把函数或小服务放到 POP，减 RTT 与回源；状态与一致性比缓存对象难，失败域跟着边缘走。</p>
<footer>—— 据 CDN 边缘函数实践；RFC 9110 对照；主干任播课整理</footer>
</div>

[上一课](/cs/cdn-cache-hierarchy) 缓存的是表示。缺口是**在边缘跑逻辑**：A/B、鉴权、改写、小 API。本课不把 L4/L7 LB 写完。

## 问题

缓存解决 GET 不变对象。个性化、Bot 校验、聚合要计算。边缘函数：请求到达 POP 即执行，近用户，冷启动与隔离是代价。状态：会话若在中心 DB，边缘仍要回源，延迟优势缩水。与 5G 边缘 MEC 同类动机，一层 Web，一层 RAN。不是把数据中心 Clos 搬到每座城。

<span class="marginnote">数字实例：用户到同城 POP 往返约 5 ms，到跨海源站约 200 ms。一次鉴权判断若在边缘完成，每个请求省约 195 ms；一个页面拉 20 个这样的小请求，累计差距就是秒级——这就是「把逻辑搬到 POP」的全部账本。</span>

不要把边缘写成「无限小云」。

<span class="marginnote">常见误区：把边缘当成「缩小的云」随便搬。边缘单点资源少、失败域是一个 POP、发布要滚全网，强一致账本搬上去就变成分布式事务难题。它适合「短平快、可降级」的逻辑，不是一切中心服务的替代品。</span>

<span class="marginnote">各家 Workers 是实现。本课钉位置与状态边界。</span>

### 算得近仍怕状态

无状态函数最赚 RTT。会话在中心 DB 则优势缩水。失败域随 POP。不是每城一座 Clos。

## 方法

对照：纯缓存 / 边缘函数 / 中心源。画：DNS → POP 计算 → 可选源。与 PTP：边缘时间仍靠 NTP 够用。

```mermaid
flowchart TD
  REQ["请求"] --> POP["边缘执行"]
  POP --> CACHE["本地缓存"]
  POP --> ORIGIN["仍可能回源状态"]
```

## 机制

GeoDNS/任播决定哪个 POP。Cookie 会话粘到 POP 或用全局存储。QUIC CID 要在任播集群可路由。gRPC 在边缘要终止 H2。失败：某 POP 代码坏只伤一区域，但版本发布要全网。

<span class="marginnote">术语翻译：任播（anycast）是让多台机器对外宣告同一个 IP，由路由协议把用户送到「网络距离最近」的一台；GeoDNS 则在域名解析阶段按用户位置挑 POP。两者共同决定请求落在哪台边缘机，也因此决定了你撞上哪个失败域。</span>

安全：多租隔离，不写逃逸。

状态放在哪，决定边缘的延迟优势还剩多少？

```mermaid
flowchart TD
  REQ["用户请求到附近 POP"] --> ST{"函数需要状态吗?"}
  ST -->|"无状态或读本地缓存"| L1["本地完成计算"]
  L1 --> R1["一次短往返内返回"]
  ST -->|"会话在中心 DB"| L2["仍要回源取状态"]
  L2 --> R2["每请求多一跳广域往返"]
  R2 --> R3["边缘只剩改写类小活的优势"]
```


## 边界

本课不引入 wasm 运行时的全部。L4/L7 负载均衡是下一课。后课默认：边缘计算换 RTT，状态仍是难题。

把强一致账本放边缘会变成分布式事务课，不在本课展开。

## 小结

- 计算随请求到 POP，减 RTT。
- 无状态最赚；有状态易回源。
- 与缓存层次互补。
- 后课只引用本课钉死的对象，不从该领域总问题重开。
