# 覆盖索引扫描

<div class="epigraph">
<p>若查询需要的列都在索引键（或包含列）里，扫描可以停在索引页，不必回表取堆行。</p>
<footer>—— 据 Ramakrishnan and Gehrke 对索引只扫描；Date 对物理独立性对照</footer>
</div>

[上一课](/cs/views-materialize)把宽接口收成视图或物化。本课不重做维护。缺口是物理访问：B+ 即将在后课展开，但优化器已经需要「覆盖」这一概念——二级索引通常只存键与 rid，回表随机 I/O 很贵。覆盖则叶子上已有投影所需列。页与槽下一课才讲记录布局。

## 问题

视图课留下逻辑宽表。执行仍要选访问路径。二级索引查找后用 rid 回堆，等于随机读。若 `SELECT` 的列是索引键的子集（或引擎支持 INCLUDE 列），索引叶子已是覆盖投影，范围扫描顺序 I/O。缺口是**何时可以不做堆取**，不是 B+ 分裂算法。

<span class="marginnote">覆盖是物理设计：多一列进索引，更新变重、叶子变宽。与物化视图不同，它仍是一种索引，不是另一张用户表。</span>

<span class="marginnote">术语翻译：rid（record id）是索引叶子上记的「行住哪儿」的地址条。普通二级索引查完后要拿这个地址跳回堆页把整行取出来——一次一次的随机 I/O；覆盖扫描意味着要读的列就写在索引叶上，连这条「回程路」都省了。</span>

## 方法

计划里出现 Index-Only Scan：过滤与投影都在索引结构上完成。过滤条件最好对准键前缀，否则退化成索引全扫。堆聚簇（主键顺序存行）是另一种「覆盖」亲戚：主键扫描即数据。本课不把每家 DBMS 的 INCLUDE 语法当标准。

```mermaid
flowchart TD
  Q["投影列集合"] --> KEY["是否包含于索引"]
  KEY --> ONLY["只扫索引叶"]
  KEY --> HEAP["rid 回表"]
```

## 机制

覆盖把[选择投影](/cs/algebra-reorder) 的投影推进存储结构，是谓词下推的列方向版本。语义不变：结果关系相同。代价模型应计入叶子页数而不是堆页数。后课页槽解释 rid 指向什么。

```mermaid
flowchart TD
  SCAN["索引范围扫描 顺序 I/O"] --> HIT["所需列都在叶子上?"]
  HIT -- "是 覆盖" --> ONLY["Index-Only 完成 不回表"]
  HIT -- "否" --> BACK["按 rid 逐行回堆 随机 I/O"]
  ONLY --> RES["同一结果关系"]
  BACK --> RES
```

<span class="marginnote">这张图回答「回表贵在哪」：索引叶子按键值有序相邻存放，顺序读很快；回表则是按 rid 跳到堆上乱序的页，一页一行地随机读。磁盘时代一次随机读顶几百次顺序读，这就是覆盖扫描能快几个量级的原因。</span>

<span class="marginnote">常见误区：以为给查询用到的每列都建一个单列索引就能覆盖。优化器通常一次只用一个索引，各索引各自给出 rid 再求交集反而更贵；真要覆盖，应建一个把所需列都收进键（或 INCLUDE）的复合索引。</span>

## 边界

## 小结

- 覆盖索引避免回表，服务投影子集。
- 用空间与更新成本换 I/O。
