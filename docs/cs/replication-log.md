# 复制与日志传送

<div class="epigraph">
<p>把 WAL 运到备库重放，备库得到同一串已提交历史；同步还是异步决定故障时丢多少提交。</p>
<footer>—— 据 Gray and Reuter 对复制；ARIES 日志作为运输对象；Bernstein 对照</footer>
</div>

[上一课](/cs/two-pc)让多个资源管理器一起提交。本课不重做投票。缺口是同一数据库的**副本**：不是两个独立 RM 的原子，而是一份历史的拷贝。日志传送（物理重放）与逻辑复制（重放 SQL）是两条路。分片下一课切的是键空间，不是同一键的副本。

## 问题

2PC 留下「跨 RM」。高可用常常是：一个主库接受写，备库应用主库日志。同步复制：提交等备库落日志，持久更强、延迟更大；异步：提交先返回，主挂可能丢尾部。缺口是**用 WAL 当复制管道**，复用 ARIES 的 REDO 解释器。

<span class="marginnote">副本不是快照隔离的读者集合自动扩展：只读备库的可见性仍要定义。脑裂（两个主）是故障切换的规格问题，本课只点名。</span>

## 方法

主库刷提交记录后（或同时）发送给备。备库 REDO 到同一 LSN，不开独立 UNDO 来自用户（备库通常不接受写）。逻辑复制解析日志为行变更，便于异构版本。冲突在多主时出现，本课默认单主。

<span class="marginnote">术语翻译：日志传送就是「把主的记账流水原样寄给分店照抄」。物理复制抄的是字节级流水（连页号都一样），两台机器须同版本同架构；逻辑复制先把流水翻译成「某表某行改成某某」再寄，跨版本跨产品都能对账，代价是翻译本身有开销与失真。</span>

<span class="marginnote">数字实例：异步复制下，主库崩溃瞬间可能有 200 ms 的提交还在网络里。若该库每秒 1000 笔交易，丢失窗口就是约 200 笔已返回「成功」的交易——业务上它们已被承诺，存储上却不存在了。同步复制把这个窗口压到 0，代价是每笔提交多等一个往返。</span>

```mermaid
  PRI["主库 WAL"] --> SHIP["传送记录"]
  SHIP --> STBY["备库 REDO"]
  SYNC["同步"] --> DUR["提交含备库持久"]

```

## 机制

复制把 D（持久）从「一块盘」扩展到「另一台机器的日志」。它不自动给跨分片事务；那要 2PC 或放弃原子。读扩展：只读可以打备库，但滞后是隔离规格的一部分。安全课的 CIA 里，副本也是泄密面。

```mermaid
flowchart TD
  F["主库故障"] --> H{"复制模式?"}
  H -- "同步" --> P1["备库已含全部已提交历史"]
  H -- "异步" --> P2["备库可能缺尾部提交"]
  P1 --> S1["提升备库, 零丢失"]
  P2 --> S2["提升备库, 丢丢失窗口内的提交"]
  P2 -.补救.-> S3["人工核对/接受丢失"]
```

这张图回答的问题是「主库挂掉那一刻，切到备库会得到什么」：同步复制切库只是换个入口，历史完整；异步复制切库等于默认接受一段已确认提交的蒸发——丢失窗口的大小就是切换时刻在途日志的长度。

<span class="marginnote">常见误区：初学者容易把「数据有副本」当成「不丢数据」。副本只能防磁盘与整机故障；异步复制下主库整机崩溃时，副本恰恰是唯一可能缺一段已确认提交的地方。防丢的合同是同步级别，不是副本数量。</span>

## 小结

- 日志传送让备库重放主库历史。
- 同步与异步换的是延迟与丢失窗口。
