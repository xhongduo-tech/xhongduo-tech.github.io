## 当物体成千上万，「查邻居」不能靠扫

前面讲过的 kd 树、范围树、区域树都是空间索引的成员，但它们各有侧重。**空间索引（spatial indexing）**这个更大的话题，回答的是一个数据库式的问题：**在大量几何对象中，快速找出「与给定区域相交」或「包含给定点」的那些**。从地图服务（「这个点附近有什么 POI」）、GIS（「哪些地块与这条河相交」）到游戏场景管理（「这个子弹会撞到谁」），空间索引是地理数据库的支柱。<span class="marginnote">空间索引与普通数据库索引（B 树）的最大区别：数据是<strong>多维且连续的</strong>，无法简单排序成一维。于是出现两条路线：<strong>网格</strong>（把空间切成规则格子，用哈希找）与<strong>树</strong>（递归细分空间，用层次剪枝）。工业上 R 树系（及其变体）统治地理数据库，四叉树统治游戏与图形学，各有地盘。</span>

## 1 均匀网格

**均匀网格（uniform grid）**：把平面切成 $m \times m$ 个等大方格，物体注册进「覆盖到的格子」的桶里。

查询「某区域内的物体」：遍历区域覆盖的格子，合并桶，去重。
查询复杂度：$O(\text{覆盖格子数} + \text{桶内物体数})$。
优点：实现极简、插入删除 $O(1)$、天然支持哈希。
缺点：**格子大小难选**。格子太大，桶内物体多、退化回扫描；格子太小，物体跨多格、桶重复存储。<span class="marginnote">网格的格子大小与「每格平均物体数」存在一个权衡：物体分布均匀时，取「每格约 1 个物体」最优（格子边长 ≈ 平均物体尺寸）。但真实分布往往是簇状的（城市中心物体密、郊区稀），均匀网格就吃亏了——这就是自适应结构（四叉树）出现的动机：<strong>让格子跟着数据密度走</strong>。</span>

## 2 四叉树

**四叉树（quadtree）**：递归把正方形区域四等分，直到每格内物体数低于阈值（或深度上限）。

自适应：密的地方切得深，稀的地方保持大格。
查询：从根按「查询区域与孩子格子相交」剪枝下潜，只访问相关子树。
复杂度：查询 $O(\text{深度} + k)$ 级别，对簇状数据远优于均匀网格。
空间：$O(n \times \text{深度})$，最坏深度可深（退化点簇），但实际良好。

四叉树在**游戏场景管理**里是默认选择：把动态物体按位置塞进四叉树，每帧查询「视锥 / 碰撞球附近的物体」，比全场景扫描快一个数量级。它的 3 维推广是**八叉树（octree）**。

## 3 R 树：磁盘上的数据库标配

**R 树（R-tree）**（Guttman, 1984）是地理数据库（PostGIS、Oracle Spatial、SQLite Spatialite）的支柱。它不像 kd 树/四叉树那样切割空间，而是**用轴对齐包围盒（MBR）层层包裹物体**：

叶子：物体及其 MBR。
内部节点：孩子 MBR 的**最小外接盒**，作为「这棵子树的所有物体都在这盒里」的近似。
树是**平衡的**（类似 B 树），每个节点容纳 $[m, M]$ 个子节点——针对磁盘页大小设计，一次 IO 读一整页。
查询「与矩形相交」：从根开始，凡是「查询矩形与节点 MBR 相交」就下潜，否则整棵剪枝。**利用 MBR 的层次包含关系剪枝，是 R 树的全部力量**。<span class="marginnote">R 树是 B 树向多维的推广：B 树把一维键排序分段，R 树把二维物体用 MBR 嵌套分组。设计难点在<strong>插入时的分裂策略</strong>——把一个满节点分成两个，怎么分让 MBR 总周长/重叠最小？Guttman 用启发式（最小扩张、最小重叠），后来的 R\* 树改进删除重插与分裂准则，是工程上更常用的增强版。</span>

**R 树查询不是最坏最优**（可能退化），但**对磁盘数据极友好**：节点即页、平衡、bulk-load 可顺序写盘。这正是数据库选择它的原因——空间换「IO 次数少」。

## 4 公式解析：MBR 剪枝判据

R 树（以及四叉树、kd 树）的查询都靠同一个剪枝判据——**「查询区域与子树包围盒是否相交」**：

$$
\text{intersects}(Q, \text{MBR}(v)) = \bigwedge_{\text{dim } d} \left( Q_d^{\min} \leq B_d^{\max} \wedge Q_d^{\max} \geq B_d^{\min} \right)
$$

拆解四步：

- **第一步，MBR 是一维区间的积**：轴对齐包围盒 $B$ 是各维闭区间的直积 $[B_x^{\min}, B_x^{\max}] \times [B_y^{\min}, B_y^{\max}]$。查询区域 $Q$ 同理。
- **第二步，相交的条件**：两个轴对齐盒相交，当且仅当**每一维**的区间都重叠。一维区间 $[a_1,a_2]$、$[b_1,b_2]$ 重叠 ⟺ $a_1 \leq b_2$ 且 $b_1 \leq a_2$。
- **第三步，逐维检查**：对每个维度做一次「区间重叠」判断，全部通过才可能相交。一维不重叠则整棵子树剪掉。
- **第四步，为什么可靠**：MBR 是子树物体集合的**外包络**——物体必在盒内。盒与查询区域不相交 ⇒ 盒内物体必不与查询区域相交 ⇒ 整棵子树无需细查。这是「外包络剪枝」的通用判据，kd 树、四叉树、R 树共用同一个公式。

**剪枝判据永远只问「可能吗」而不是「确定吗」**——外包络相交只说明「可能」，还需下潜到叶子确认。但它已经排除绝大多数无关子树。

## 5 三种索引对比

| 维度 | 均匀网格 | 四叉树 | R 树 |
| --- | --- | --- | --- |
| 结构 | 固定格 + 哈希 | 递归四等分 | MBR 层次包含 |
| 自适应性 | 无 | 有 | 有 |
| 平衡性 | 天然 | 不保证 | 平衡（B 树式） |
| 磁盘友好 | 否 | 否 | 是（节点=页） |
| 实现复杂度 | 极低 | 低 | 中 |
| 典型场景 | 粒子、小规模 | 游戏场景、图形 | 地理数据库 |
| 最坏查询 | $O(n)$ | $O(n)$ | $O(n)$ |

**没有全能冠军**：网格赢在简单，四叉树赢在自适应，R 树赢在磁盘与平衡。工程选择取决于数据规模、动态性、存储介质。

## 6 现代扩展

- **R\* 树 / R+ 树**：改进插入分裂与删除重插，PostGIS 默认。
- **Bulk-load（STR 打包）**：静态批量数据用排序打包建树，写盘顺序友好，建树快。
- **空间填充曲线**：用 Hilbert / Z 序曲线把二维映射成一维，让「空间邻近 → 一维邻近」，然后用普通 B 树索引——Google S2、PostGIS 空间分片都用它。
- **HNSW / 向量索引**：非空间结构，但「最近邻」查询在高维向量数据库（Milvus 等）里同样叫「空间索引」。

### 辨析：网格格子大小怎么选

**辨析｜易错点：** 均匀网格唯一要调的参数是格子边长 $g$，选错会让「索引」退化回「扫描」。经验法则：**格子边长取「物体平均尺寸」附近**，让每个格子平均容纳约 1 个物体。

| 格子偏大 | 格子偏小 |
| --- | --- |
| 每格物体多，桶内扫描退化 | 物体跨多格，重复存储浪费 |
| 查询区域覆盖格数少 | 查询区域覆盖格数多 |
| 适合物体稀疏 | 适合物体密集 |

**为什么簇状数据对网格不友好**：城市中心物体密、郊区稀，均匀网格在密区桶爆炸、在稀区格子浪费。这时自适应结构（四叉树、R 树）更优——它们让格子跟着密度走。

**插入 / 删除的注意**：物体运动时要从旧格子的桶里删除、注册进新格子；大物体可能同时覆盖多个格子，桶里要存「物体引用」而非复制本体，否则空间会膨胀。

<span class="marginnote"><strong>工程技巧</strong>：网格用「哈希表把格子坐标 $(gx, gy)$ 映射到桶」实现，查询「矩形区域内的物体」只需枚举覆盖的格子坐标，查哈希即可——比数组网格省内存，也更容易处理稀疏世界。</span>

**网格 vs 树的一个判断标准**：物体数量级 $n$ 与查询频率——网格插入 $O(1)$、适合动态；树查询更稳、适合静态与磁盘。游戏里「动态刚体」常用网格，「静态地形查询」常用四叉树/R 树，各取所长。

**一句话选型**：动态物体多、更新频繁选网格；数据静态但查询多选树；落盘大数据选 R 树。没有全能冠军，只有「适合场景」的结构。

## 7 小结

- 空间索引回答「谁在我的区域/邻域」，是地图、GIS、游戏场景管理的支柱。
- **均匀网格**：固定格 + 哈希，简单但格子大小难选、簇状数据退化。
- **四叉树**：递归四等分、自适应密度，游戏与图形学默认。
- **R 树**：MBR 层层包裹、平衡、磁盘页友好，地理数据库标配；R\* 树是增强版。
- 通用剪枝判据：**查询区域与 MBR 逐维区间重叠**，一维不重叠即剪枝。
- 现代方向：空间填充曲线（Hilbert / Z 序）把二维压成一维用 B 树，S2 / PostGIS 采用。
- 空间索引与范围树 / kd 树 / 区域树同族，是「用结构换查询」哲学的集大成。
