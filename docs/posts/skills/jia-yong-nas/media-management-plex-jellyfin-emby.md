## 为什么从影音服务器开始

影音是家庭 NAS 里「使用频率最高、幸福感最强」的应用——但「把视频堆进文件夹」和「拥有一个影音库」是两回事。**影音服务器**（Plex / Jellyfin / Emby）把零散的视频文件组织成带封面、简介、演员表的媒体库，让手机、电视、平板随时随地流畅播放。<span class="marginnote">影音服务器的核心三件事：<strong>刮削（抓取元数据）、转码（适配设备）、多端播放</strong>。理解这三件事，就理解了为什么影音服务器「不是文件管理器 + 播放器那么简单」。</span>

本篇讲清影音服务器做什么，三强怎么选，以及媒体库怎么组织。

## 1 影音服务器做什么：三件核心事

**影音服务器（Media Server）**：管理媒体文件并对外提供播放服务的软件。它做三件事：

**刮削（Scraper / Metadata）**：根据文件名自动匹配在线数据库（The Movie Database、TVDB 等），抓取海报、简介、评分、演员、集数信息，把「电影文件夹」变成「漂亮的媒体库」。<span class="marginnote">刮削的成败高度依赖<strong>命名规范</strong>：`片名 (年份).mkv`、`剧名/第1季/剧名 S01E01.mkv` 这类规范命名，刮削器才能准确识别。命名不规范，刮削就会「张冠李戴」——这是影音库整理最常见、也最见效的一步。</span>

**转码（Transcoding）**：把源视频转换成客户端能播放的格式。设备不支持原编码、或网络带宽不足时，服务器实时转码成低码率/兼容格式。转码是 CPU 重负载——再次呼应第 2 篇「选带 Intel 核显的 CPU」的建议。

**多端播放**：手机 App、电视客户端、浏览器通过 HTTP 访问媒体库，支持续播、多语言字幕、多用户（大人/儿童账号）。

**数值算例：远程播放的带宽账**。影音库的体验上限，还取决于「从 NAS 到播放设备」这条链路的带宽。一部 4K HDR 原盘（Remux）码率常在 60–100 Mbps，而家庭宽带的上传带宽通常只有 20–50 Mbps——远程播放 4K 原片会直接卡死。所以远程场景下「转码」不只是格式兼容，更是**降码率**：把 4K 原片实时转成 1080p、10–15 Mbps 的流，才能在家中上传带宽内顺畅播放。局域网内则带宽充足，设备支持直接播放原片，转码只在需要时触发——这也是「硬件加速转码」在远程场景价值最大的原因。

## 2 Plex / Jellyfin / Emby 三强对比

**Plex**：商业影音服务器，体验最「苹果化」。

优点：客户端覆盖最广（电视/手机/游戏机）、界面精致、家庭共享体验好。
代价：核心功能免费，但硬件转码、部分高级功能需 **Plex Pass** 订阅；元数据刮削走 Plex 自有服务器，依赖其服务。

**Jellyfin**：开源免费，功能几乎对标 Plex 全家桶。

优点：完全免费、无订阅、数据自持（元数据存本地）、开发活跃，支持硬件转码（需正确配置核显）。
- 代价：客户端生态略逊，部分设备需装第三方播放器；配置门槛略高。

**Emby**：商业软件，可视为 Plex 与 Jellyfin 之间的中间派。

- 优点：功能完整、有服务器端转码控制、插件生态好。
- 代价：免费版限制部分功能，高级功能需 Emby Premiere 订阅。

**辨析｜易错点：三者的「媒体库」不能直接迁移。** 换了影音服务器，元数据（海报、观看进度）通常不随媒体库走——但**视频文件本身不受影响**。所以「换软件不换文件」，损失的只是整理好的元数据，可以重新刮削。这也再次印证「备份数据、不备份应用」的原则。<span class="marginnote">Plex 与 Jellyfin 的哲学分野：Plex 用「厂商服务器 + 订阅」换「零配置好体验」，Jellyfin 用「自己动手」换「免费与数据主权」。对看重隐私与不付费的玩家，Jellyfin 是主流答案；对图省事的家庭，Plex 更顺滑。</span>

**媒体库与 NAS 目录的权限要点**：影音服务器进程要以「能读影音目录」的用户身份运行——部署时把容器/服务进程的用户，指向一个有影音目录读取权限的 NAS 用户即可。常见翻车是「库里显示 0 个媒体」：不是没扫到，而是进程没权限读目录。这也是为什么「挂载目录 + 配权限」在部署步骤里总被放在一起强调。

## 3 部署与媒体库组织

以 Jellyfin 部署为例（复用 Docker 篇的容器知识）：

1. **拉镜像**：`jellyfin/jellyfin` 稳定版。
2. **挂载目录**：把 NAS 的影音文件夹挂进容器（如 `/media/电影`、`/media/剧集` 分开挂）。
3. **配转码**：若 NAS 有 Intel 核显，配置「启用硬件加速」，转码性能大幅提升。
4. **映射端口**：`8096:8096`，浏览器访问 `NAS地址:8096` 进向导。
5. **建媒体库**：按类型建「电影」「剧集」「音乐」库，指向对应目录，触发刮削。

**媒体库目录规范**（直接影响刮削与体验）：

```
/media
├── 电影
│   └── 星际穿越 (2014).mkv
└── 剧集
    └── 三体
        ├── 第1季
        │   └── 三体 S01E01.mkv
```

**命名即一切**：电影用「片名 (年份)」，剧集用「剧名 SXXEYY」——遵循这个规范，刮削成功率接近 100%。

**数值算例：转码到底需要多强的 CPU**。影音库配不配硬件加速，看一个关键场景——远程播放时，家里的上传带宽不够支撑 4K 原片，服务器要现场转码成 1080p 低码率流。纯 CPU 软转一部 4K H.265 片，需要接近 8 核的算力，入门 NAS 的四核 CPU 会卡成幻灯片；而启用 Intel 核显（Quick Sync）后，同一部片子的转码只占不到一核，还能同时服务好几台设备。**结论：只要影音库要跨设备远程播放，选带 Intel 核显的 CPU 并打开硬件加速，是性价比最高的决定**——这正是第 2 篇「核心硬件」把核显列入选购要点，而本篇在应用层兑现它的地方。

**辨析｜易错点：刮削失败，先怪命名与网络，别怪软件。** 建库后常见两种翻车：一是刮削「张冠李戴」，八成是文件名不规范（缺年份、剧集没标 SXXEYY），改命名重新刮削即可；二是刮削不出任何信息，多半是**网络问题**——刮削器要访问 The Movie Database、TVDB 等站点，网络受限时抓取会超时。前者改命名，后者需要给 NAS 配上能访问这些站点的网络环境，或更换可用的刮削数据源。

**硬件转码的验证，别只看开关**：配好硬件加速后，进播放界面放一部 4K 片，打开转码状态看是否显示「硬件转码」而非「软件转码」——不少机型的核显驱动没装好，开关打了勾，实际仍是软转。这一步实机验证，是影音服务器部署里最容易被跳过、也最能暴露问题的一环。

## 4 核心对比表：Plex / Jellyfin / Emby

本篇的核心对比表如下（纯概念主题，以表格替代公式解析）：

| 维度 | Plex | Jellyfin | Emby |
| --- | --- | --- | --- |
| 价格 | 免费 + Plex Pass | 完全免费 | 免费 + Premiere |
| 客户端生态 | 最广 | 中 | 中 |
| 硬件转码 | Plex Pass 专享 | 免费支持 | Premiere 专享 |
| 数据自持 | 元数据依赖 Plex 服务 | 全本地 | 全本地 |
| 上手难度 | 最低 | 中 | 中 |
| 适合人群 | 家庭省心 | 免费/开源党 | 折中主义者 |

从表里能读出选择逻辑：**预算敏感或重视数据主权选 Jellyfin，图省心与生态选 Plex，介于两者选 Emby**——家用主流答案在 Jellyfin 与 Plex 之间。

## 6 术语速查

- **刮削（Scraper / Metadata）**：按文件名匹配在线数据库，抓取海报、简介、演员等元数据。
- **转码（Transcoding）**：把源视频实时转换成客户端兼容的格式与码率，CPU/核显负载高。
- **硬件加速（Hardware Transcoding）**：用 GPU/核显做转码，性能数倍于纯 CPU，需正确驱动配置。
- **媒体库（Library）**：按类型（电影/剧集/音乐）组织的媒体集合，每个库指向一个目录。
- **Plex Pass / Emby Premiere**：两家商业软件的高级订阅，硬件转码等能力需付费解锁。
- **多语言字幕**：从在线字幕源匹配并加载字幕，随播放自动选择，支持多轨切换。
- **硬件解码/编码**：用核显或独显承担视频解码与编码，需在系统层面正确配置驱动才生效。
- **媒体库扫描（Scan）**：新增视频后触发刮削的机制，可手动刷新或按计划自动扫描。

## 7 小结

- 影音服务器做三件事：**刮削（元数据）、转码（适配）、多端播放**。
- 刮削成败取决于**命名规范**：`片名 (年份)` 与 `剧名 SXXEYY`。
- **Plex** 体验最顺（需订阅）、**Jellyfin** 免费开源、**Emby** 折中。
- 部署即 Docker 三件套：拉镜像、挂目录、配转码。
- 换软件不换文件——元数据可重刮，视频文件才是真正的数据。
