## 为什么「本地通信」是高级方案的灵魂

同样是「米家灯接入 HA」，云集成（走小米云）和本地集成（走局域网）体验天差地别：本地方案响应毫秒级、断网照常、不依赖厂商服务器；云方案一条指令要在家里和云端之间绕一圈，厂商服务器一抽风全屋失灵。跨品牌集成的高手与新手的分水岭，就在**能不能把设备拉到局域网本地通信**。这一篇讲局域网通信的原理与跨品牌集成的四条路径。

## 1 局域网通信原理

**mDNS 与自动发现**：设备在局域网里「自我介绍」——通过 mDNS（多播 DNS）广播自己的服务与地址，HA 等平台在同一子网内自动发现它。这就是为什么 HA 常能「无配置」找到 HomeKit 设备。**前提：设备与 HA 必须在同一个局域网（同一子网）**，隔离网络（如访客网络）里互相看不见。<span class="marginnote">「明明连同一个 Wi-Fi 却找不到设备」的头号原因：<strong>路由器开了「AP 隔离/客户端隔离」，设备间互相不可见</strong>。这也是第 4 篇提过的坑——跨品牌集成的第一步，永远是确认网络没有互相隔离。</span>

**IP 与端口**：每台设备有局域网 IP（如 `192.168.1.50`），服务跑在特定端口上（如摄像头的 RTSP 流在 `554` 端口，HA 的 Web 在 `8123` 端口）。配置本地集成时，填设备 IP、端口与账号密码即可直连。

**本地协议**：设备与平台之间说「什么话」，决定集成方式。常见本地协议：HomeKit（苹果本地控制协议）、Onvif/RTSP（摄像头）、Modbus（工业设备）、ESPHome（自建设备）、Tasmota/TP-Link 等私有本地 API。

## 2 本地接入的四种典型

**① 支持本地 API 的厂商设备**：部分品牌（如 Yeelight 灯的局域网模式、TP-Link 部分插座、Sonoff）开放本地控制接口，HA 可直接通过 IP 控制，**无需厂商云**。配置方式：在 HA 集成里填设备 IP 与局域网密钥。

**② Onvif/RTSP 摄像头**：几乎所有专业摄像头支持 ONVIF（标准协议）与 RTSP（视频流协议）。HA 通过 ONVIF 集成接入摄像头，可看流、云台控制、触发事件——**本地、不依赖厂商云**，是摄像头跨品牌接入的标准姿势。

**③ ESPHome**：给 ESP32/8266 这类单片机刷 ESPHome 固件，自建传感器、开关、灯带，HA 直接本地接入。适合 DIY 玩家，能做厂商不做的「定制设备」——比如用门窗磁改一个「衣柜灯」触发器。<span class="marginnote">ESPHome 是「万物皆可 DIY 接入」的利器：<strong>一个 20 元的 ESP32 + 一个继电器，就能把普通电器变成可本地控制的智能设备</strong>。它写给 HA 的是原生本地协议，断网可用、无云依赖。</span>

**④ Modbus/串口设备**：中央空调、新风、地暖等大系统常走 Modbus 总线。HA 通过 Modbus 网关（TCP/串口）接入，实现「HA 控制中央空调」——这是**全屋集成单的增值点**，也是跨品牌集成的「深水区」，需要懂一点工业协议。

## 3 MQTT：设备间的「通用语言」

跨品牌集成绕不开的一个词是 **MQTT（Message Queuing Telemetry Transport）**，一种轻量级消息协议。它的角色是「局域网内的公共信箱」：

一个 **MQTT Broker（服务器，如 Mosquitto）** 常驻家中，设备往特定**主题（Topic）**发布消息，其他设备订阅该主题。
例如：传感器向主题 `home/bedroom/temp` 发布 `25.3`，HA 订阅后就能读到温度；HA 再向 `home/livingroom/light` 发布 `on`，对应灯就亮。

**为什么重要**：MQTT 是**厂商无关**的协议——只要设备支持 MQTT（很多开源/专业设备支持），就能绕过品牌私有协议直接通信。zigbee2mqtt（第 14 篇）就是把 Zigbee 数据「翻译」成 MQTT 消息，再交给 HA。<span class="marginnote">MQTT 是跨品牌集成的「公共语言」：<strong>品牌私有协议是方言，MQTT 是普通话</strong>。接入大量第三方设备的方案里，Broker 常在；排查 MQTT 故障，先看 Broker 进程是否在跑、主题是否发布正常。</span>

**MQTT 调试要点**：Broker 装在 HA（Mosquitto Add-on）或 NAS；用 MQTT 客户端（如 MQTT Explorer）订阅 `#` 主题观察消息流，能直观看到「设备有没有在说话」。

## 4 跨品牌集成四条路径

把散落的设备拉到一起，按「介入深度」有四条路，从轻到重：

**① 平台集中**：设备各自进自己的 App，HA 只做「统一界面与自动化」。最轻，但每台设备仍依赖各自云，HA 拿到的状态有延迟。

**② 云集成**：设备进厂商云，HA 通过厂商云 API（如米家 MIoT）拉取与控制。省事、覆盖面广，但**断网即断**，且厂商可随时改接口。

**③ 本地网关/桥接**：把设备的本地协议（Zigbee/Thread/私有 API）通过网关或桥接进 HA（第 13、15 篇）。**本地、稳定、断网可用**，是专业方案的主流。

**④ 替换固件/自建**：用开源固件（ESPHome、Tasmota）替换设备原固件，彻底「去云化」。最强、最可控，但有设备损坏风险，只适合玩家级项目。<span class="marginnote">给客户定集成深度的原则：<strong>安全与核心体验类设备（门锁、安防、灯光）尽量走本地（③④）；锦上添花类（空气净化器、吸尘器）走云集成（②）足够</strong>——把「命脉设备」的云依赖降到最低。</span>

## 5 核心对比表：本地集成 vs 云集成

纯技能主题，用对比表替代公式解析：

| 对比维度 | 本地集成 | 云集成 |
| --- | --- | --- |
| 控制路径 | 局域网直连 | 家庭 → 厂商云 → 家庭 |
| 响应速度 | 毫秒级 | 百毫秒～秒级 |
| 断网可用 | 可用 | 失灵 |
| 依赖厂商服务器 | 不依赖 | 依赖 |
| 隐私 | 数据不出家门 | 数据过厂商云 |
| 配置难度 | 较高 | 低 |
| 适合设备 | 命脉设备（灯/锁/安防） | 非核心设备（净化器/吸尘器） |

## 6 术语速查表

局域网通信与跨品牌集成的专业词，一次归档：

| 术语 | 含义 |
| --- | --- |
| mDNS | 局域网内的自动发现协议，设备广播自己的服务 |
| 子网 | 同一网段的设备集合，跨子网默认互不可见 |
| ONVIF | 摄像头标准协议，跨品牌接入的基础 |
| RTSP | 视频流传输协议，看监控流的通道 |
| ESPHome | 给 ESP 单片机刷的开源固件，HA 本地接入 |
| Tasmota | 给智能设备刷的开源固件，去云化方案 |
| Modbus | 工业设备常用的总线协议，中央空调等大系统走它 |
| MQTT | 轻量消息协议，设备间通信的公共语言 |
| Broker | MQTT 服务器，消息的中转站 |
| 主题（Topic） | MQTT 消息的分类名，如 `home/bedroom/temp` |

## 7 跨品牌集成深度选择

集成深度的选择直接影响稳定性与隐私，按设备重要性分层：

| 设备类别 | 推荐集成方式 | 原因 |
| --- | --- | --- |
| 门锁、安防 | 本地集成 | 命脉设备，断网必须可用 |
| 灯光 | 本地/桥接 | 高频操作，本地响应快 |
| 窗帘电机 | 本地/桥接 | 体验依赖稳定控制 |
| 净化器、吸尘器 | 云集成 | 非核心，云集成足够 |
| 自建设备 | ESPHome 本地 | 完全可控，去云化 |
| 摄像头 | ONVIF/RTSP 本地 | 断网可看流，不依赖厂商云 |
| 中央空调 | Modbus 本地 | 大系统走总线，本地控制 |
| 传感器 | Zigbee/Thread 本地 | 低功耗走网关，稳定省电 |
| 音箱 | 云集成 | 语音服务天然依赖云 |
| 门锁 | 本地+云冗余 | 本地保命脉，云端收通知 |
| 窗帘电机 | 本地/桥接 | 高频操作需稳定响应 |
| 扫地机 | 云集成 | 非核心，云集成足够 |

## 8 小结

- 本地通信基础：**mDNS 自动发现、IP+端口直连、本地协议**；先确认没开 AP 隔离。
- 四种本地接入：**厂商本地 API、Onvif/RTSP 摄像头、ESPHome 自建、Modbus 大系统**。
- **MQTT** 是厂商无关的「通用语言」，跨品牌设备靠 Broker 互通。
- 跨品牌四路径：**平台集中 → 云集成 → 本地桥接 → 固件替换**，介入越深越本地越稳。
- 集成深度原则：**命脉设备走本地，非核心设备可走云**。
