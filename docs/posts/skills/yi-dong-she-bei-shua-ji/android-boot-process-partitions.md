## 为什么从启动流程与分区结构开始

刷机（flashing）的本质，是**改写存储介质上存放系统的那些分区**。如果不知道系统被放在哪里、以什么顺序被加载、哪个分区坏了会变砖，那么解锁、刷 Recovery、刷 ROM 全都只是「照着教程敲命令」——一旦出错，连错误信息都读不懂。这一篇先把最底层的两张地图画出来：**启动流程**（软件如何一步步被加载）与**分区结构**（系统在存储里的物理布局）。理解了它们，后面每一篇刷机操作都能对号入座。

同时，这两张地图也是 Android 安全模型的地基：现代刷机遇到的大部分「锁」「校验」「熔断」，都是在启动链的某个环节上做文章。<span class="marginnote">把启动链想成一条安检流水线：<strong>每一级只信任上一级验过货的东西</strong>。Boot ROM 验 Bootloader，Bootloader 验 boot 镜像，Linux 内核再验 system——整条链上有任何一环要求「验签」，后面的东西就必须被签名。刷机破解的很多努力，就是在给这条链的某一环「走后门」。</span>

## 1 从按下电源键说起：Android 的启动链

一台 Android 手机的启动，是一条严格分级的链条，每一级负责加载并验证下一级：

**第一级，Boot ROM（固化只读存储器）**。它焊死在 SoC 里，出厂时写好、不可改写。上电后 CPU 从固定地址执行 Boot ROM 里的代码，它的首要任务是找到并验证 Bootloader，然后跳转过去。因为不可改，它成了整条链的「信任根」。<span class="marginnote">信任根（Root of Trust）是安全启动的起点：<strong>整条链的可信性最终锚定在一个出厂后不可篡改的元件上</strong>。对刷机用户来说，Boot ROM 无法直接改写，所以厂商的解锁策略往往从 Bootloader 这一层开始做文章。</span>

**第二级，Bootloader**。它分成多段，通常包括基带加载（modem）、可信执行环境（TEE）、主引导程序等。它的职责是初始化硬件、加载并验证 Linux 内核镜像，然后进入系统或恢复模式。**Bootloader 也是「锁」所在的位置**——设备锁、OEM 锁都由它强制执行。

**第三级，Linux 内核**。Bootloader 把 boot 分区里的内核与 ramdisk 读入内存，解压后交给内核。内核初始化驱动、挂载根文件系统，然后启动 **init** 进程。

**第四级，init 与 Zygote**。init 是用户空间的第一个进程（PID 1），它解析 init.rc 脚本，挂载各种分区，启动关键服务。其中最关键的是 **Zygote**——Android 的「进程孵化器」。所有应用进程都由 Zygote fork 出来，因为它预先加载好了共享库与框架，应用启动就快。

**第五级，System Server**。System Server 是系统框架的核心进程，它启动 Activity Manager、Package Manager、Window Manager 等几十个系统服务，最后才点亮桌面（Launcher）。**看到开机动画不等于系统启动完成**——System Server 里的服务一个个起来，直到桌面出现，才算走完全程。

这五级链条，就是刷机者眼里的「开机」。任何一级出了问题，手机的表现各不相同：Boot ROM 阶段出问题叫「深度变砖」（9008 深刷的原因），Bootloader 阶段出问题可能反复重启，内核崩了停在开机动画，System Server 崩了则卡在桌面之前。

## 2 分区结构：一张盘上的「角色分工」

手机里的存储（eMMC / UFS）不是一个大仓库，而是被切成了**几十个功能不同的分区**。刷机就是往这些分区里写对应内容。常见分区如下：

| 分区 | 名称含义 | 存放内容 | 刷机者视角 |
| --- | --- | --- | --- |
| `boot` | 引导分区 | 内核 + ramdisk | 内核与开机相关改动刷这里 |
| `recovery` | 恢复分区 | 独立的小系统 | 官方 Recovery、TWRP 刷这里 |
| `system` | 系统分区 | Android 系统主体 | 刷 ROM 的核心对象 |
| `vendor` | 厂商分区 | 厂商专有库与 HAL | 与 system 分工，勿乱动 |
| `data` | 用户数据分区 | 应用、用户数据 | **刷 data 会清空资料** |
| `cache` | 缓存分区 | 系统缓存、OTA 缓存 | 常见清 cache 操作 |
| `misc` | 杂项分区 | 启动指令、OTA 标记 | 控制「进系统还是进 Recovery」 |
| `bootloader` | 引导程序分区 | Bootloader 各段 | 解锁、回锁相关 |
| `modem` | 基带分区 | 通信基带固件 | 信号、网络问题刷这里 |
| `persist` | 持久分区 | 校准数据、传感器数据 | 别乱刷，丢了难恢复 |
| `EFS` | 基带配置分区 | IMEI、基带校准 | **备份 EFS = 备份「手机身份证」** |

**理解分区结构是刷机安全的头号功课**：绝大多数「刷机清空资料」的事故，都是因为把 `data` 分区当作可随意覆盖的对象。而 `EFS`、`persist` 这类分区一旦写坏，IMEI 丢失、传感器失效，往往比系统崩溃更难恢复。<span class="marginnote">分区之间的角色分工决定了刷机风险：<strong>boot/recovery/system 是「软件」，刷坏了重刷即可；EFS/persist 是「硬件校准与身份数据」，丢了不是重刷能救的</strong>。所以刷机社区的第一条铁律是「先备份 EFS」。后面《完整备份与分区级恢复》一篇会专门展开。</span>

## 3 A/B 无缝更新与 super 动态分区

现代手机还有两套分区设计，彻底改变了刷机玩法：

**A/B 分区（无缝更新）**：系统关键分区存两份——`system_a` 与 `system_b`、`boot_a` 与 `boot_b`。当前运行在 A 槽，升级时把新系统写入 B 槽，重启切换槽位；若新槽起不来，自动回滚到旧槽。<span class="marginnote">A/B 设计把「升级失败」从「变砖」降级为「自动回滚」：<strong>写坏的槽不会影响当前槽</strong>。但它也让「当前分区」变成了「当前槽位」，刷机命令要带 `_a` 或 `_b` 后缀，忘了选槽是新手常犯的错。</span>

**super 动态分区**：Android 10 起，`system`、`vendor`、`product` 等逻辑分区被装进一个大的 `super` 物理分区里，大小按需动态分配。刷机工具通过 `fastboot` 的 `dynamic partition` 命令或专用工具来操作，直接对 `super` 里的逻辑分区改名、调整大小都成了可能。

这两套设计让传统「单分区镜像刷写」的思路需要升级：**A/B 要管槽位，super 要管动态逻辑分区**。这也是为什么老教程里的命令在新机上常常失效——它们面对的分区模型已经不同了。

## 4 公式解析：启动验证链的哈希依赖

刷机社区资料里反复出现 dm-verity、vbmeta、哈希树这些词，背后其实是一条可以用「哈希」串起来的验证链。以镜像校验为例：

$$
\text{vbmeta} \xrightarrow{\text{公钥验签}} \text{boot / system} \xrightarrow{\text{哈希}} \text{启动时逐块比对}
$$

逐步拆解：

- **vbmeta**：存放每个被保护分区镜像的哈希值与签名。Bootloader 启动时读它，用**公钥验签**，确认 vbmeta 本身未被篡改。
- **公钥验签**：只有厂商私钥签过的 vbmeta 才通过。第三方镜像过不了这关——除非解锁设备、关闭验证，这就是「解锁」在验证链上的作用。
- **哈希比对**：启动后内核里的 dm-verity 机制对 `system` 分区逐块计算哈希，与 vbmeta 里存的期望值比对，不一致就拒绝读取。**改一个字节，哈希就变**，所以「改了 system 还想通过校验」在未解锁设备上是不可能的。

这条链解释了刷机社区里一个反复出现的现象：**为什么刷第三方系统必须先解锁**——不是厂商小气，而是解锁会关闭验证链上的「验签」环节，让未签名的镜像得以加载。理解了这条链，你就能看懂「解锁警告」「校验失败」「熔断」这些词的真正含义。

## 5 核心要点：分区与刷机风险对照表

| 分区 | 刷错后果 | 可恢复性 | 建议 |
| --- | --- | --- | --- |
| `boot` / `recovery` | 无法开机/无法进恢复 | 高，重刷即可 | 放心刷 |
| `system` | 系统损坏、卡动画 | 高，重刷即可 | 刷 ROM 主战场 |
| `data` | 用户资料清空 | 中，提前备份 | 刷前必备份 |
| `modem` | 无信号、无网络 | 高，重刷基带 | 备份原厂基带 |
| `EFS` | IMEI 丢失、无基带 | **低** | **最先备份** |
| `persist` | 传感器失效、校准丢失 | **低** | 别乱动 |
| `bootloader` | 变砖（解锁相关操作中断） | 视机型 | 断电前确认 |

| 术语 | 含义 | 刷机要点 |
| --- | --- | --- |
| Boot ROM | 出厂固化的信任根 | 不可改写 |
| Bootloader | 第二级引导程序 | 锁的所在位置 |
| Zygote | 应用进程孵化器 | 应用启动关键 |
| System Server | 系统服务核心 | 桌面出现的标志 |

| super 分区 | 动态逻辑分区容器 | 现代刷机对象 |

## 7 快速自查清单

刷任何东西之前，先回答这份清单：

- 是否知道这次刷写涉及**哪个分区**、它的角色是什么？
- 目标分区是否属于**可恢复类型**（boot/system/recovery）还是**不可逆类型**（EFS/persist/bootloader）？
- 设备是否支持 **A/B 槽**？当前槽位是哪个？
- 设备是否用 **super 动态分区**？刷写方式是否需要相应调整？
- 是否已**备份 EFS 与关键数据**？
- 是否理解这次操作**在启动验证链的哪个环节**（要不要解锁、关不关验证）？

## 8 小结

- Android 启动是**五级链条**：Boot ROM → Bootloader → 内核 → init/Zygote → System Server，每一级验证下一级。
- 分区是**角色分工**：boot/recovery/system 可重刷，EFS/persist 不可逆，`data` 存用户资料。
- 现代手机新增 **A/B 槽位**与 **super 动态分区**，改变了刷机命令与流程。
- 启动验证链由 **vbmeta + 公钥验签 + dm-verity 哈希**构成，这是「解锁」存在的原因。

在下一节，我们将把「刷机」从概念落到工具：解锁、Root、ROM 这些词到底指什么，完整工具链由哪些部分组成——这就是**刷机与系统定制的基本概念与完整工具链**。
