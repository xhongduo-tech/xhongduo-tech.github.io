## 为什么从文件系统损坏开始

分区表修好了，分区也认出来了，但分区里的文件系统却坏了——目录打不开、文件变成乱码、卷提示「无法访问」。文件系统损坏（corruption）是逻辑层恢复里最需要「临场判断」的场景：它不像误删那样有清晰的删除痕迹，而是**元数据处于半损坏状态**。这一节讲清文件系统损坏的几种形态，以及对应的提取策略：能修的修、不能修的绕、绕不过的挖。

<span class="marginnote">一条主线贯穿本节：<strong>元数据损坏程度决定策略</strong>。轻度损坏 → 修复元数据；中度损坏 → 用残留索引提取；重度损坏 → 放弃索引，按文件签名在原始数据里挖。永远先评估「哪部分元数据还活着」。</span>

## 1 文件系统损坏的四种形态

**目录结构损坏**：文件系统还在，但目录索引（FAT 目录项 / NTFS B+ 树 / EXT inode 目录）损坏。症状：能看到分区、容量正常，但某些目录打不开、文件「消失」。此时文件数据往往完好，只是「从哪找」的索引断了。

**索引结构损坏**：FAT 表项损坏、NTFS $MFT 部分记录损坏、EXT 超级块损坏。症状：整个卷的「文件分布地图」残缺，文件系统可能拒绝挂载或只读挂载。

**引导扇区/BPB 损坏**：卷的关键参数（簇大小、FAT 表位置、$MFT 位置）丢失或错误。症状：系统提示「未格式化」，无法识别文件系统类型。<span class="marginnote">BPB 损坏有个「幸运」之处：<strong>同一文件系统类型的 BPB 结构相同，参数可以从备份或同型号卷推断</strong>。很多情况下修复 BPB 就能让整个卷复活，这是「成本最低、收益最高」的修复动作之一。</span>

**元数据与数据错位**：文件系统正常，但数据块被覆盖或移动（如 SSD 的 FTL 异常、碎片严重）。症状：文件存在但内容错乱、读出的内容与文件名对不上。

## 2 提取策略一：修复元数据

当损坏是**局部**的，优先修复而不是提取。

**修复 BPB/引导扇区**：用卷备份或同参数卷的 BPB 覆盖损坏的引导扇区。FAT 卷可参考第二份 FAT 表与备份引导扇区；NTFS 可参考 $Boot 文件的备份。

**用副本修复主索引**：FAT 卷用第二份 FAT 表覆盖第一份；NTFS 用 $MFTMirr 修复 $MFT 开头记录；EXT 用备份超级块修复主超级块。<span class="marginnote">FAT 的双表、NTFS 的 $MFTMirr、EXT 的备份超级块——这些「冗余副本」都是为容灾设计的。修复时<strong>先把副本读到镜像</strong>，再决定用哪个副本覆盖哪个主区，避免把「好的副本」也写坏。</span>

**运行一致性检查**：修复后用文件系统自带的检查工具（`chkdsk`、`fsck`）扫描一致性。注意：一致性检查可能「修掉」一些恢复软件还能捞回的残留，所以**先镜像、后检查**。

## 3 提取策略二：用残留索引提取

当损坏**面积较大**但仍有部分索引残留时，绕过损坏区、只提取可用部分：

**FAT**：扫描仍有效的 FAT 表区段与目录项，提取对应的簇链。
**NTFS**：扫描 $MFT 中仍有效的记录，按 $DATA runlist 提取；损坏记录跳过，不中断整体提取。
**EXT**：扫描各块组的 inode 表，提取仍有效的 inode。

提取的关键是**容错**：一个文件读不出来，不能拖垮整个提取过程。工具应该记录「哪些文件成功、哪些失败」，最后给出报告。

## 4 提取策略三：按签名挖原始数据

当**元数据几乎全损**（格式化、$MFT 大面积损坏、重建文件系统），就走「签名扫描」路线：

**识别文件签名**：每种常见文件类型在开头有固定字节，如表：

| 文件类型 | 常见签名（十六进制） | 说明 |
| --- | --- | --- |
| JPEG | `FF D8 FF` | 图像 |
| PNG | `89 50 4E 47` | 图像 |
| PDF | `25 50 44 46` | `%PDF` |
| ZIP/DOCX | `50 4B 03 04` | `PK`，压缩包与 Office |
| GIF | `47 49 46 38` | `GIF89a` |

**扫描过程**：逐簇/逐扇区搜索签名，命中后按该类型的**文件结构**确定文件结束位置（JPEG 以 `FF D9` 结束，PNG 按块长度推算），把整段挖出。<span class="marginnote">签名扫描是最「暴力」也最「可靠」的兜底：它完全不依赖文件系统。代价是<strong>丢失文件名、目录结构、时间戳</strong>，且对「无固定签名」或「碎片化」的文件无能为力。所以它定位为「最后手段」，而不是首选。</span>

**碎片问题**：文件若被分成不连续的多个簇，签名扫描只能挖出「从开头到第一处断裂」的部分。这引出下一节的主题——**碎片重组**。

## 5 核心要点：损坏形态 × 策略对照表

| 损坏形态 | 残留元数据 | 首选策略 | 兜底策略 |
| --- | --- | --- | --- |
| 目录索引损坏 | 数据簇完好 | 修复/重建目录索引 | 签名扫描 |
| BPB/引导扇区损坏 | 数据簇完好 | 恢复 BPB | 参数推断重建 |
| FAT 表损坏 | 第二份表可能完好 | 用副本覆盖 | 扫描重建簇链 |
| $MFT 部分损坏 | 部分记录有效 | 提取有效记录 | 签名扫描 |
| 超级块损坏 | 块组备份在 | 用备份超级块 | 扫描 inode |
| 元数据全损 | 无 | 签名扫描 | 碎片重组 |

## 6 术语速查表

| 术语 | 含义 | 提取意义 |
| --- | --- | --- |
| 文件系统损坏 | 元数据无法正常解释 | 数据簇可能完好 |
| 目录损坏 | 目录索引失效 | 文件数据常完好 |
| BPB | 卷的关键参数块 | 损坏 → 显示未格式化 |
| 残留索引 | 损坏后仍有效的元数据 | 提取的锚点 |
| 签名扫描 | 按文件特征字节挖数据 | 元数据全损的兜底 |
| `chkdsk` | Windows 一致性检查 | 修复后运行 |
| `fsck` | Linux 一致性检查 | 修复后运行 |
| 元数据错位 | 数据块被移动/覆盖 | 文件内容错乱 |
| 容错提取 | 坏文件不中断整体提取 | 记录失败清单 |
| 兜底策略 | 最后手段的恢复方案 | 先修复后兜底 |

## 7 快速自查清单

面对一块「文件系统损坏」的盘，按这份清单定策略：

- 是否先评估**元数据损坏程度**，再决定修还是绕？
- 轻度损坏是否先试**修复**（BPB、双表、$MFTMirr、备份超级块）？
- 修复前是否做了**只读镜像**？
- 是否确认没有「残留索引可用」就直接去签名扫描？
- 提取过程是否**容错**，坏文件不拖垮整体？
- 一致性检查（`chkdsk` / `fsck`）是否放在修复之后？
- 签名扫描的局限（丢文件名、碎片拼不全）是否向用户说明？

## 8 小结

- 文件系统损坏分**目录、索引、BPB、元数据错位**四种形态。
- 策略分三档：**修复元数据 → 用残留索引提取 → 按签名挖原始数据**。
- FAT 双表、NTFS 的 $MFTMirr、EXT 的备份超级块——**冗余副本是修复的首选弹药**。
- 元数据全损时走**签名扫描**，代价是丢失文件名、目录结构与碎片完整性。
- 提取过程必须**容错**：坏文件不拖垮整体，最后给出成功/失败报告。
- 主线判断：**先评估「哪部分元数据还活着」，再决定修、绕还是挖**。

- 判断优先级的一句话：**先评估「哪部分元数据还活着」，再决定修、绕还是挖**——先修、再绕、最后挖。

- 收束一句话：**「元数据还活着多少」决定一切——先修、再绕、最后挖**。
