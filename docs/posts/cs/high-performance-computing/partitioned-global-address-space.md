## 为什么从 PGAS 开始

前面我们见识了两种极端：

**共享内存**（OpenMP）好写但扩展难，**消息传递**（MPI）能扩展但难写。

能不能兼得两者？

**分区全局地址空间（PGAS，Partitioned Global Address Space）**模型正是这个折中：

它给程序员**全局地址空间**的便利，又保留**数据分区**的局部性控制。

代表语言有 UPC、Coarray Fortran、Chapel、X10，近年还有面向 C++ 的扩展。

<span class="marginnote">PGAS 是「CCNUMA 硬件在软件层的投影」：硬件把内存物理分片、逻辑统一，PGAS 语言把地址空间逻辑分区、语义统一——两者互为镜像。</span>

本节讲清 PGAS 的思想、单边通信、以及它与 MPI/OpenMP 的位置关系。

## 1 从两难出发：共享 vs 分布式

把两种经典模型摆在面前：

**共享内存（SMP/OpenMP）**：一个统一地址空间，谁都能读写任何变量。编程自然，但总线与缓存一致性把扩展性焊死。
**分布式内存（MPI）**：地址空间彼此隔离，只能靠显式消息交换。可扩展，但程序员得亲手安排每一次数据流动。

一句话总结两难：

**共享内存把「难」留给硬件，分布式内存把「难」留给程序员。**

PGAS 的立场是第三条路：**把「共享」的语言还给程序员，把「分区」的事实也告诉他。**

## 2 PGAS 的核心思想

**PGAS（分区全局地址空间）**模型假设：

存在一个**逻辑上全局的地址空间**，所有进程都能「看见」；
但这个空间被**静态划分**，每个进程**拥有（own）**其中一块；
访问「自己的」数据是本地操作，快；访问「别人的」数据是远程访问，慢但**合法且自然**。

程序员获得两个好处：

**易写**：远程数据可以直接读写，不用像 MPI 那样显式 send/recv；
**可控**：数据放在哪个进程的「家」里，由程序员决定——局部性这把钥匙还在自己手里。

**辨析｜易错点：** PGAS 的「全局地址空间」≠ 真正的共享内存。

远程访问**不透明**：它仍然要花网络时间，只是**语法上**像本地访问。

把 PGAS 当 OpenMP 用（疯狂远程读写），性能会崩塌。

## 3 单边通信：put 与 get

PGAS 的远程访问通过**单边通信（one-sided communication）**完成：

**put**：把我的一小块数据**写到**另一个进程的地址空间里；
**get**：从另一个进程的地址空间**读**一小块数据到本地。

为什么叫「单边」？

因为**只有发起方参与**：

不需要对方的进程同时执行一个「接收」操作来配对。

对比 MPI：

MPI 的 send/recv 是**双边（two-sided）**的——收发双方必须同时到场，像两个人打电话。

单边通信像**发快递**：寄出方写好地址交给网络，收件人不在家也能送达。

<span class="marginnote">单边通信天然规避了 MPI 里最常见的死锁：收发不配对。但也带来新的问题——你无法知道对方「什么时候读完了」，于是需要显式的同步与 fence（屏障）。</span>

**工程直觉：** 单边通信让「生产者-消费者」「稀疏更新」这类不对称模式写起来自然得多。

## 4 典型语言：UPC / Coarray Fortran / Chapel

PGAS 不是一个语言，而是一族语言，各有侧重：

**UPC（Unified Parallel C，统一并行 C）：**

C 语言的 PGAS 扩展。

用关键字声明数据的分区属性：

```c
shared int a[N];             // 全局共享数组，分片分布到所有进程
shared [BLOCK] int b[M];     // 按 BLOCK 大小分块分布
int *mine = &a[MYTHREAD];    // 每个进程直接访问自己那片
```

**Coarray Fortran（CAF）：**

Fortran 的 PGAS 扩展，语法最贴合科学计算。

把数组声明成 coarray（协维度），用方括号下标访问远程镜像：

```fortran
real :: x(n)[*]            ! 协维 [*] 声明 coarray
x(1)[me+1] = 1.0           ! 远程写：把值写到邻居进程的镜像
y = x(1)[me-1]             ! 远程读：读邻居进程的 x(1)
```

**Chapel / X10：**

从零设计的 PGAS 语言，主打「多范式」：既能写共享风格，也能写分片风格，还内建数据并行与任务并行。

<span class="marginnote">Chapel 的著名卖点是「一个语言覆盖所有并行风格」；X10 则强调「async/finish」任务模型。二者更接近研究性语言，生产界主力仍是 UPC 与 Coarray Fortran。</span>

## 5 公式解析：数据局部性与远程访问代价

PGAS 的性能分析围绕一句话展开：

**本地访问快，远程访问慢。**

设：

- $t_{\text{local}}$：访问本地数据的延迟；
- $t_{\text{remote}}$：访问远程数据的延迟；
- $f$：程序中远程访问的占比。

一个 PGAS 程序的平均数据访问延迟近似为：

$$T_{\text{avg}} = (1 - f) \cdot t_{\text{local}} + f \cdot t_{\text{remote}}$$

拆三步理解：

- **第一步，看本地项**：$(1-f) \cdot t_{\text{local}}$，占比越高越该优化——访存局部性直接乘进公式；
- **第二步，看远程项**：$f \cdot t_{\text{remote}}$，远程延迟通常比本地慢一两个数量级；
- **第三步，做权衡**：若 $t_{\text{remote}} = 100 \cdot t_{\text{local}}$，那么 1% 的远程访问就会让平均延迟翻倍——**局部性不是可选项，是性命攸关**。

这给出 PGAS 编程的两条铁律：

**数据放对「家」、计算跟着数据走。**

## 6 核心对比：三种并行模型

| 维度 | OpenMP（共享） | MPI（消息） | PGAS |
| --- | --- | --- | --- |
| 地址空间 | 统一共享 | 各自独立 | 全局但分区 |
| 远程数据访问 | 语法透明 | 需 send/recv | 语法透明（put/get） |
| 同步 | 共享变量 + 锁 | 消息配对 | 显式 barrier/fence |
| 局部性控制 | 弱 | 强 | 强 |
| 易写性 | 高 | 低 | 中高 |
| 可扩展性 | 差 | 好 | 好 |

**核心结论：** PGAS 想拿走 MPI 的「难写」，保留它的「能扩展」。

代价是：远程访问的代价不再显式，程序员得自己心里有数。

## 7 小结

- **PGAS** 提供全局地址空间，但明确分区、每进程拥有自己的领地。
- **单边通信** put/get 让远程读写语法自然，且无收发配对死锁。
- 代表语言：**UPC、Coarray Fortran、Chapel/X10**。
- 平均访问延迟 $T = (1-f)\,t_{\text{local}} + f\,t_{\text{remote}}$，**局部性决定生死**。
- 铁律：**数据放对家、计算跟着数据走；别把 PGAS 当真共享内存。**
