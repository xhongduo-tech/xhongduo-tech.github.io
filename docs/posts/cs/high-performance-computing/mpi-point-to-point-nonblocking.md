## 为什么从点对点开始

集体通信适合「全体一起干」，但很多并行程序需要**两两之间**的精准沟通：

把边界数据递给邻居、把中间结果传给下一阶段。

这就是**点对点通信（point-to-point communication）**，MPI 最底层的通信能力。

它也是并行程序里最容易写出死锁的地方。

更进阶的玩法是**非阻塞通信**：

让数据在后台传输，处理器同时继续算——把「等消息」的时间偷回来。

<span class="marginnote">点对点通信是分布式系统的「元语言」：一切更高级的模式（流水线、ring、树）都由它拼出来。</span>

本节把阻塞收发、死锁、非阻塞三件事讲透。

## 1 阻塞收发：Send 与 Recv

最朴素的通信是同步收发：

```c
MPI_Send(buf, count, datatype, dest, tag, comm);
MPI_Recv(buf, count, datatype, source, tag, comm, &status);
```

六个参数要弄明白：

**buf 与 count**：要发的数据指针与元素个数；
**datatype**：元素类型（`MPI_INT`、`MPI_DOUBLE` 等）；
**dest / source**：对方的 rank；
**tag**：消息标签，用来区分不同用途的消息；
**comm**：通信子；
**status**：接收方查询发送方与标签的信息。

`MPI_Send` 与 `MPI_Recv` 是**阻塞**的：

调用后进程原地等待，直到消息真正到达、数据抄进缓冲区。

`MPI_Send` 的阻塞语义取决于实现与消息大小：

**小消息**：常先拷贝到系统缓冲，立即返回；
**大消息**：必须等接收方「准备好」才开始传输，即**会阻塞**。

**辨析｜易错点：** 不要把「阻塞」理解成「慢」。

阻塞是为了保证**数据一致性**——返回时数据要么已发走、要么已收到。

## 2 死锁现场：为什么互相等

阻塞通信最经典的坑是「互相等待」：

```c
/* 进程 0 */
MPI_Send(buf, n, MPI_INT, 1, tag, comm);                 // 先发
MPI_Recv(buf, n, MPI_INT, 1, tag, comm, &status);        // 后收

/* 进程 1 */
MPI_Send(buf, n, MPI_INT, 0, tag, comm);                 // 先发
MPI_Recv(buf, n, MPI_INT, 0, tag, comm, &status);        // 后收
```

两个进程都先 `发送`，都等着对方先 `接收`——**互相等待，谁也不让步**。

若消息足够大（不进入系统缓冲），这就是一个标准的**死锁（deadlock）**。

三个解法：

**改变顺序**：0 先发后收，1 先收后发——交错开，谁也不会等死；
**用 `MPI_Sendrecv`**：同时发起发送与接收，一次调用解决配对；
**用非阻塞通信**：发完后不等，先做别的，稍后再检查。

<span class="marginnote">死锁的本质是「资源循环等待」，与操作系统里哲学家就餐问题是同一个病根（见 cs/os 课程）。MPI 的死锁更隐蔽：它发生在消息级，报错信息常常延迟到超时才出现。</span>

## 3 Sendrecv：同时收发

`MPI_Sendrecv` 把「发」和「收」打包进一次调用：

```c
MPI_Sendrecv(sendbuf, sendcount, sendtype, dest, sendtag,
             recvbuf, recvcount, recvtype, source, recvtag,
             comm, &status);
```

它同时执行发送与接收，由库内部处理好配对。

上面那个死锁例子，用 `MPI_Sendrecv` 重写后两个进程都能顺利推进。

**核心直觉：** 只要「先发后收」会互相堵，就换成 `MPI_Sendrecv`。

它是工程上处理「邻居交换边界」这类对称通信的标准做法。

## 4 非阻塞通信：Isend 与 Irecv

阻塞通信最大的浪费在于**等待**：

等接收时，处理器闲着；等发送确认时，计算也停了。

**非阻塞通信（non-blocking communication）**把「发出请求」与「确认完成」分开：

```c
MPI_Isend(buf, count, datatype, dest, tag, comm, &request);
```

同样地：

```c
MPI_Irecv(buf, count, datatype, source, tag, comm, &request);
```

两个常用完成检查：

- `MPI_Wait(&request, &status)`：**阻塞式**等待该请求完成；
- `MPI_Test(&request, &flag, &status)`：**轮询式**查一下完成了没，没完成立即返回，不阻塞。

**辨析｜易错点：** 非阻塞不代表「不用等」——只是**把等的时间让给了计算**。

在 `MPI_Wait`/`MPI_Test` 之前**不要**读写缓冲区，否则读到的是半途数据，这是非阻塞编程最常见的竞态。

## 5 公式解析：通信计算重叠

非阻塞通信的价值用公式最清楚。

设每个时间步需要：

- 计算时间 $T_c$；
- 通信时间 $T_m$。

**阻塞版本**每个时间步串行做事，总时间为：

$$T_{\text{block}} = T_c + T_m$$

**非阻塞版本**让通信与计算重叠，总时间为两者中的**较大者**：

$$T_{\text{overlap}} = \max(T_c, T_m)$$

拆三步理解：

- **第一步，看阻塞版**：先算、再传，时间相加；
- **第二步，看重叠版**：算的同时后台传，总时间被较长的一方决定；
- **第三步，算收益**：两者之比 $T_{\text{block}}/T_{\text{overlap}}$ 在 $T_c \approx T_m$ 时接近 2——**近乎翻倍的吞吐**。

这正是流水线并行的数学根基：

**通信与计算重叠，是并行程序从「能用」走向「快」的分水岭。**

## 6 核心对比：阻塞与非阻塞

| 维度 | 阻塞通信 | 非阻塞通信 |
| --- | --- | --- |
| 调用返回时机 | 完成才返回 | 立即返回 |
| 数据可用性 | 返回即可用 | 需 `MPI_Wait`/`MPI_Test` 确认 |
| 正确性风险 | 死锁 | 竞态（过早读写） |
| 计算与通信 | 串行 | 可重叠 |
| 编程复杂度 | 低 | 高 |
| 典型场景 | 简单交换、小规模 | 流水线、大规模、性能敏感 |

**工程直觉：** 正确性优先——先把阻塞版调对，再改非阻塞去榨性能。

性能瓶颈往往集中在一两个通信密集的循环里，不值得处处非阻塞。

## 7 小结

- **阻塞收发** `MPI_Send`/`MPI_Recv` 保证数据一致性，但可能死锁。
- **死锁**源于循环等待，解法：调顺序、`MPI_Sendrecv`、非阻塞。
- **非阻塞** `MPI_Isend` + `MPI_Irecv`，把等待让给计算。
- 重叠后每步时间从 $T_c + T_m$ 降到 $\max(T_c, T_m)$。
- 铁律：**先对再快；非阻塞改早了反而难调。**
