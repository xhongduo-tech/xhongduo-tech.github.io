## 为什么从混合并行开始

一台现代超算不是「一台大机器」，而是一座**分层的塔**：

- 几千个**节点**，节点间用高速网络相连（MPI 的地盘）；
- 每个节点一块或多块 **CPU**，每颗 CPU 有多个**核**（OpenMP 的地盘）；
- 每个核又有 **SIMD 指令**，节点里还可能插着 **GPU**（CUDA 的地盘）。

**纯 MPI** 在每个节点上放一个进程，浪费了节点内部的核与加速器。

**混合并行（hybrid parallelism）**的策略是：

**用 MPI 管节点之间，用 OpenMP/CUDA 管节点内部。**

让每一层硬件都有活干。

<span class="marginnote">混合并行的口号是「MPI+X」：X 是 OpenMP、CUDA 或两者并用。几乎所有冲刺 exascale 的代码（气候、燃烧、分子动力学）都走这条路。</span>

## 1 并行层次：从机柜到 SIMD

先看清一座超算里的全部并行来源：

| 层级 | 硬件 | 并行工具 | 粒度 |
| --- | --- | --- | --- |
| 节点间 | 高速网络 | MPI | 进程（几十~几千） |
| 节点内 | 多核 CPU | OpenMP | 线程（每核 1~2） |
| 单核内 | SIMD 指令 | 编译器自动向量化 | 向量宽度（2~16） |
| 加速器 | GPU | CUDA | 上万线程 |

每一层都对应一种并行风格，也都有各自的通信/同步代价。

**设计原则：** 在同一层里做事要快（缓存友好、带宽友好），跨层移动数据要省（能少搬就少搬）。

混合并行的核心工作，就是**为每个问题找到「数据怎么分到各层」的最优方案**。

## 2 MPI + OpenMP：机间进程、机内线程

最经典的混合模式是「每节点 1 个 MPI 进程 + 节点内 OpenMP 线程」。

```c
// 每节点 1 个 MPI 进程；节点内线程数由 OMP_NUM_THREADS 控制
MPI_Init(&argc, &argv);
MPI_Comm_rank(MPI_COMM_WORLD, &rank);

#pragma omp parallel for                    // 节点内：多线程并行
for (int i = 0; i < n; ++i)
    local[i] = compute(i);

MPI_Allreduce(local, global, n, MPI_DOUBLE, MPI_SUM, MPI_COMM_WORLD);  // 节点间：MPI
```

这个方案的好处：

- **MPI 进程数大幅减少**：从「每核一进程」降到「每节点一进程」，消息数量与同步开销随之锐减；
- **节点内通信走共享内存**：不经过网络，快且省；
- **内存更省**：多个 OpenMP 线程共享一份数据副本，而多个 MPI 进程各有一份副本。

**公式解析：** 假设每节点有 $c$ 个核、共 $p$ 个节点。

纯 MPI 需要 $p \times c$ 个进程，混合只需 $p$ 个进程，通信消息数约按 $c$ 倍缩减：

$$N_{\text{pure}} \approx c \cdot N_{\text{hybrid}}$$

- **第一步，看纯 MPI**：每个核一个进程，通信矩阵是 $(pc)^2$ 量级；
- **第二步，看混合**：每节点一进程，通信矩阵是 $p^2$ 量级；
- **第三步，比一比**：节点数越多、核越密，混合省下的通信量越可观。

但要注意：`MPI_Allreduce`、`MPI_Barrier` 等全局操作仍需要所有进程参与，**进程少了并不代表同步消失**，只是参与方少了。

## 3 MPI + CUDA：一个节点一块 GPU

当节点里插着 GPU，混合模式变成「每节点一个 MPI 进程，把热计算卸载到 GPU」。

典型的数据流是：

1. MPI 进程接收属于本节点的数据分片；
2. 数据从 CPU 内存拷进显存；
3. GPU kernel 完成重计算；
4. 结果拷回 CPU，再经 MPI 与其他节点交换。

```c
// 1. MPI 接收本节点数据分片
MPI_Recv(h_data, n, MPI_DOUBLE, src, tag, MPI_COMM_WORLD, &status);
// 2. 拷入显存
cudaMemcpy(d_data, h_data, n * sizeof(double), cudaMemcpyHostToDevice);
// 3. GPU kernel 完成重计算
kernel<<<grid, block>>>(d_data, n);
cudaDeviceSynchronize();
// 4. 拷回 CPU，再经 MPI 与其他节点交换
cudaMemcpy(h_data, d_data, n * sizeof(double), cudaMemcpyDeviceToHost);
MPI_Send(h_data, n, MPI_DOUBLE, dst, tag, MPI_COMM_WORLD);
```

**核心原则：数据在哪，计算就在哪。**

GPU 处理大块稠密数据极快，但**搬运数据进出显存很贵**。

所以混合编程要尽量把数据「留在 GPU 上」：

能用 GPU 完成的通信（如 NCCL 的 GPU 直连）就不回 CPU，能用一块 kernel 干完的就别拆成三块。

<span class="marginnote">NCCL 是 NVIDIA 的 GPU 集合通信库，实现 GPU 上的 all-reduce、广播等操作。大模型训练正是「MPI 的思想 + NCCL 的实现」在 GPU 集群上的翻版。</span>

## 4 数据在哪，计算就在哪

混合并行最容易犯的错误，是**数据在层级间来回搬**。

一条经验法则：**每次跨层搬移都花钱（延迟 + 带宽），算法设计要按「搬运次数」来优化，而不是按「计算量」。**

具体地说：

- 节点内尽量用共享内存协作，别为了「统一」把每块数据都发去网络；
- 节点间只交换**必要的最小数据**——通常是边界条，而不是整块数据；
- GPU 上的热循环要「长」：把足够大的计算留在显存里连续做完。

**辨析｜易错点：** 混合并行**不是**「能开的并行开关全打开」。

每层并行都有启动与同步开销，盲目叠加可能更慢。

判断标准只有一个：**新增一层并行后，端到端时间是否真的下降**。

## 5 核心对比：纯 MPI 与混合并行

| 维度 | 纯 MPI | 混合并行（MPI+X） |
| --- | --- | --- |
| 节点内并行 | 无（浪费多核） | OpenMP/CUDA 接管 |
| MPI 进程数 | 每核一个 | 每节点一个 |
| 节点内通信 | 走网络 | 走共享内存/显存 |
| 内存占用 | 高（每进程一份副本） | 低（线程共享） |
| 编程复杂度 | 中等 | 高 |
| 性能上限 | 受通信量限制 | 更高（层内层外都优化） |

**工程结论：** 小规模问题纯 MPI 够用；**节点核数越多、规模越大，混合并行的优势越明显**。

## 6 小结

- 现代超算是**分层机器**：节点间 MPI、节点内 OpenMP、GPU 用 CUDA。
- **混合并行（MPI+X）**让每层硬件都参与，进程数按核数缩减。
- MPI+CUDA 的关键是**把数据留在 GPU 上**，少做跨层搬运。
- 铁律：**数据在哪，计算就在哪；按搬运次数优化，不按计算量。**
- 别盲目叠加并行，**端到端时间下降才算赢**。
