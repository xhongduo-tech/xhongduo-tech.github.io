## 为什么从同步与归约开始

上一篇说 OpenMP「默认共享变量」是竞态的根源。

这一篇就直面它：

多个线程同时更新同一个变量，会发生什么？

答案是**数据竞争（data race）**——结果取决于线程执行的先后顺序，程序「跑十次坏三次」。

同步机制（临界区、原子操作、屏障）把竞争关进笼子。

而**归约（reduction）**则是「多线程合算一个汇总值」的最优解：

比任何同步都更快、更干净。

<span class="marginnote">数据竞争是「时间上的竞态」：两个线程的读写交错次序未定义，中间状态会互相覆盖。它与 MPI 里过早读缓冲区的错误是同一家族的病。</span>

## 1 数据竞争现场

看一个经典错误：

```c
double sum = 0.0;
#pragma omp parallel for
for (int i = 0; i < N; i++) {
    sum += a[i];      // 多个线程同时读写 sum
}
```

`sum += a[i]` 在底层是三步：**读 sum → 加 a[i] → 写回 sum**。

两个线程同时执行这三步就会互相覆盖：

线程 A 读到的 sum 可能还没算上线程 B 刚加的增量。

结果比真实值小，且每次运行可能不同。

**这就是数据竞争（data race）。**

**辨析｜易错点：** 数据竞争 ≠ 死锁。

死锁是「互相等待、谁也动不了」，数据竞争是「同时动手、结果随机」。

后者不报错、不崩溃，只给出**悄悄变错**的结果，是并行程序里最难抓的 bug 之一。

## 2 临界区与原子操作

对付「同时写同一变量」，第一板斧是**互斥**。

**`#pragma omp critical`：临界区。**

一次只允许一个线程进入，其他线程排队等待：

```c
#pragma omp parallel for
for (int i = 0; i < N; i++) {
    #pragma omp critical
    sum += a[i];
}
```

正确，但慢——每次累加都要排队拿锁。

**`#pragma omp atomic`：原子操作。**

把「读-加-写」合并成一条不可分割的硬件操作，只对简单运算生效：

```c
#pragma omp parallel for
for (int i = 0; i < N; i++) {
    #pragma omp atomic
    sum += a[i];
}
```

比 critical 快得多，因为它没有锁队列、直接让硬件保证原子性。

<span class="marginnote">`atomic` 只支持加减乘、位运算这类单条指令；碰到函数调用、复杂表达式就得退回 `critical`。硬件原子指令（CAS、fetch-and-add）是操作系统课程里锁的实现基础。</span>

## 3 屏障与 ordered

除了互斥，还有**对齐**需求：

让所有线程在某个点停下来等齐——这就是**屏障（barrier）**。

- `omp for`、`omp sections` 的**末尾自带隐式屏障**；
- 显式屏障用 `#pragma omp barrier`，所有线程到达后才一起放行；
- 想跳过 `for` 末尾的隐式屏障，用 `nowait` 子句。

屏障的用途：

确保「别人算完」这个前提成立——比如第二阶段的输入依赖第一阶段所有线程的输出。

**`#pragma omp ordered`** 则强制「按循环顺序执行」：

```c
#pragma omp for ordered
for (int i = 0; i < N; i++) {
    #pragma omp ordered
    process_in_order(i);   // 这一句严格按 i 从小到大执行
}
```

适用于「计算可以并行，但输出必须有序」的场景。

<span class="marginnote">ordered 会严重牺牲并行度：它让语句退化成近似串行。能用独立缓冲再排序，就别用 ordered。</span>

## 4 归约：reduction 子句

同步能解决正确性，却牺牲了性能——每加一个数都排队。

真正的工程答案是**归约子句（reduction clause）**：

```c
double sum = 0.0;
#pragma omp parallel for reduction(+:sum)
for (int i = 0; i < N; i++) {
    sum += a[i];
}
```

编译器自动完成三件事：

1. **每个线程私有一份 `sum`**，各自累加自己的那份；
2. 并行区结束时，**各线程的私有副本按操作符合并**（这里是相加）；
3. 合并结果写回共享变量 `sum`。

归约支持的操作符：

`+`、`*`、`-`、`max`、`min`、`&`、`|`、`^` 等。

**核心直觉：** reduction 把「多线程争抢一个变量」变成「各自算、最后合」。

没有锁、没有原子、没有等待，只有一次 O(线程数) 的收尾合并。

## 5 代码解析：并行求和

把三种写法摆在一起对比：

```c
/* 写法一：错（数据竞争） */
#pragma omp parallel for
for (...) sum += a[i];

/* 写法二：对但慢（临界区排队） */
#pragma omp parallel for
for (...) { #pragma omp critical
    sum += a[i]; }

/* 写法三：对且快（归约） */
#pragma omp parallel for reduction(+:sum)
for (...) sum += a[i];
```

三步读懂归约写法：

- **第一步，声明 `reduction(+:sum)`**：告诉编译器「sum 要累加，请做私有+合并」；
- **第二步，循环体照写**：`sum += a[i]` 不变，编译器会在背后把它改到线程私有副本上；
- **第三步，收尾自动**：所有线程算完后，各副本相加写回原变量——程序员不用写任何同步代码。

**辨析｜易错点：** reduction 要求操作满足**结合律**（浮点不完全满足）。

严格说浮点加法不可结合，并行求和与串行求和可能差一两个最低位——科学计算里这叫「不同归约顺序、不同舍入」，通常可接受，但敏感场景要留意。

## 6 核心对比：三种保护手段

| 手段 | 语义 | 性能 | 适用 |
| --- | --- | --- | --- |
| `critical` | 临界区互斥 | 慢（排队） | 任意代码块 |
| `atomic` | 单指令原子更新 | 快 | 简单运算 |
| `reduction` | 私有副本 + 归并 | 最快 | 累加/求最值等汇总 |

**工程直觉：** 汇总类计算一律用 `reduction`；单变量简单更新用 `atomic`；复杂临界区才用 `critical`。

同步是并行性能的隐形税，交得越少越好。

## 7 小结

- **数据竞争**是多个线程同时读写同一变量，结果随机且难抓。
- **critical** 提供任意代码的互斥，**atomic** 用硬件保证单指令原子。
- **barrier** 让全员对齐，**ordered** 强制按顺序执行（慎用）。
- **reduction** 是最优归约：私有副本 + 收尾合并，无锁无等待。
- 铁律：**能归约就别同步，能原子就别临界区。**
