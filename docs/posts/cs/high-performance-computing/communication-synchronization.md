## 为什么从通信与同步开始

任务分解好了，处理器分好工了，接下来它们得**协作**。

协作只有两个动作：

- **通信（communication）**：把数据从一台处理器搬到另一台；
- **同步（synchronization）**：让处理器在约定的时刻「对齐」。

这两个动作是并行程序的灵魂，也是绝大多数 bug 的来源。

时序一乱，数据就错；顺序一错，程序就死锁。

<span class="marginnote">分布式系统课程里的「时钟与顺序」问题（见 cs/distributed-systems），在并行机上以更简单的形态出现——但死锁、竞态、活锁这些病症是一样的。</span>

本节把通信与同步的「基本词汇」讲透，为下一篇的 MPI/OpenMP 编程打底。

## 1 通信的基本模型

并行机上的通信，最通用的形态是**消息传递（message passing）**：

一个进程**发送（send）**一条消息，另一个进程**接收（receive）**它。

一次 send/receive 是**点对点通信（point-to-point）**。

按会不会阻塞，分两类：

**阻塞通信（blocking）**：发送方把数据交出去后才继续；接收方拿到数据才返回。语义简单，但可能互相等待。
**非阻塞通信（non-blocking）**：调用立刻返回，数据「稍后」在后台传输，用**完成检查**确认。并行度高，但编程复杂。

通信的两个关键代价参数：

**延迟（latency）**：发起一条消息的固定开销；
**带宽（bandwidth）**：单位时间能传的数据量。

小消息被延迟支配，大消息被带宽支配——这个二分法是后面所有通信优化的出发点。

## 2 集体通信

当**所有**进程都要参与通信时，就进入**集体通信（collective communication）**的领域。

它的口号是「一句话让全队行动」：

| 操作 | 语义 | 数据方向 |
| --- | --- | --- |
| broadcast | 根进程把一条数据发给所有人 | 一 → 多 |
| scatter | 根进程把自己的数据**分片**发给每人 | 一 → 多（每片不同） |
| gather | 每人把一片数据**汇合**给根进程 | 多 → 一 |
| all-gather | 汇合后根进程再把完整数据**广播**回去 | 多 → 多 |
| reduce | 每人给一片数据，在根进程上做归约（求和/最大值） | 多 → 一（算完） |
| all-reduce | 归约后把结果广播给每个人 | 多 → 多（算完） |
| barrier | 全员等齐，之前谁也别往下走 | 同步 |

<span class="marginnote">all-reduce 是大模型分布式训练里最热的词：梯度求和的跨卡版本就是 all-reduce，只是换了个名字叫「梯度同步」。</span>

每个集体操作都有高效的实现算法（树状、桶状、环状），复杂度远低于「每人各发各收」的朴素做法。

## 3 同步机制

同步是「对齐时间」，但机器里没有全局时钟，只能靠**事件**实现。

最常见的同步原语：

- **barrier（屏障）**：所有进程到达后才一起放行，是集体同步的化身；
- **lock / unlock（锁）**：互斥访问共享资源，防止两个进程同时写同一块数据；
- **signal / wait（信号量）**：进程间发送「我好了」的通知，协调先后次序。

锁与屏障的差别要分清：

- **屏障是全员对齐**，谁也别想先走；
- **锁是互斥占位**，一次只放一个进临界区，其他人照常干别的。

用错语义，就会产生两类典型故障：

**死锁（deadlock）**：两个进程互相等对方手里的资源，谁都动不了。

**竞态（race condition）**：两个进程同时读写同一数据，结果取决于执行时序——程序「有时对、有时错」，最难调试。

## 4 公式解析：通信成本模型

一次点对点通信的时间，工程上常用线性模型近似：

$$T_{\text{comm}} = \alpha + \frac{n}{\beta}$$

拆开看：

- **第一步，$\alpha$（alpha）**：延迟，即发一条**空消息**的固定开销——握手、路由、进入协议栈都要时间，与数据量无关。
- **第二步，$n/\beta$**：传输时间，数据量 $n$ 除以带宽 $\beta$。
- **第三步，相加**：小消息时 $\alpha$ 主导，大消息时 $n/\beta$ 主导。

这个模型的推论极其实用：

**把许多小消息合并成一条大消息（消息合并），省掉的是多次 $\alpha$。**

假设 $m$ 条小消息各 $n/m$ 字节，合并后时间：

$$T_{\text{merged}} = \alpha + \frac{n}{\beta} \;\ll\; m\alpha + \frac{n}{\beta} = T_{\text{separate}}$$

只要 $m\alpha$ 显著大于 $\alpha$，合并就稳赚不赔。

## 5 核心对比：集体通信怎么选

| 需求 | 该用哪个操作 |
| --- | --- |
| 根进程要通知所有人 | broadcast |
| 根进程把数组分片下发 | scatter |
| 收集各片拼成数组 | gather |
| 每人拿到**完整**汇总 | all-gather |
| 归约求和、只让根进程拿结果 | reduce |
| 归约求和、**人人**拿结果 | all-reduce |
| 全员对齐后才继续 | barrier |

**辨析｜易错点：** broadcast 与 scatter 最容易混。

broadcast 发的是**同一份**数据，scatter 发的是**每个人不同的一片**。

记住一句话：**broadcast 复制，scatter 分发。**

## 6 小结

- **点对点通信**分阻塞与非阻塞，代价由**延迟 $\alpha$** 与**带宽 $\beta$** 刻画。
- **集体通信**把「全队协作」封装成原语：broadcast/scatter/gather/all-gather/reduce/all-reduce/barrier。
- **同步**靠屏障（全员对齐）与锁（互斥占位），用错语义会引发**死锁**与**竞态**。
- 通信成本 $T = \alpha + n/\beta$，**消息合并**是省 $\alpha$ 的第一优化。
- 铁律：**先想对语义，再谈性能；死锁竞态是并行程序的头号杀手。**
