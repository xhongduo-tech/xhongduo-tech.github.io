## 为什么从「巴别塔」开始

回顾本专题全部技术，你会发现一个扎眼的事实：接入层有 ZigBee/LoRa/NB-IoT，应用层有 MQTT/CoAP/HTTP，标识有 EPC/Handle，安全有 TLS/DTLS……**协议的世界是碎片化的**。<span class="marginnote">塔嫩鲍姆那句调侃绝非玩笑：IoT 生态至今有数百个标准与数百个联盟组织，行业壁垒与厂商锁定向来严重。互操作性的意义在于——当你的路灯、电梯、电表、门锁来自不同厂商时，它们能否在一个平台上协同工作。这是「物联网」中「网」字的题眼。</span>本篇先把「互操作」拆成层次，再给出标准化的全景地图，最后回答那个务实的问题：标准到底由谁来定、该怎么选。

## 1 互操作性的五个层次

**互操作性（interoperability）**：不同系统之间交换信息并正确使用信息的能力。它不是一个开关，而是**分层**的，越往上越难、也越有价值：

1. **设备层互操作**：物理接入能通——天线对上频段、电气特性匹配（如都支持 802.15.4）。
2. **网络层互操作**：数据包能路由——IPv6、6LoWPAN 让不同接入技术的设备共享 IP 语义。
3. **语法层互操作**：数据结构能被双方解析——消息格式、编码一致（JSON、CBOR、Protobuf）。
4. **语义层互操作**：数据含义被双方理解——「温度 25.5」中的 25.5 用的是摄氏还是华氏？是瞬时值还是均值？这需要**本体（ontology）**定义概念。<span class="marginnote">语义互操作是今天的最大缺口：设备 A 的 `temp: 25.5` 与设备 B 的 `temperature: 25.5` 语法上能解析，语义上却可能是「摄氏度/华氏度」「瞬时/均值」两种东西。这正是 W3C Web of Things 与 SAREF 本体要解决的最后一公里。</span>
5. **平台层互操作**：业务服务能对接——不同云平台的设备、数据能互相调用与迁移。

## 2 标准化组织全景：谁在定规矩

物联网标准不是一个组织制定的，而是**多组织分工 + 事实标准并存**的生态：

| 组织 | 管辖范围 | 代表性产出 |
| --- | --- | --- |
| IEEE | 物理/链路层 | 802.15.4（ZigBee 物理层）、802.11（Wi-Fi） |
| IETF | 互联网协议 | CoAP（RFC 7252）、6LoWPAN、DTLS、RPL |
| 3GPP | 蜂窝通信 | NB-IoT、LTE-M、5G NR |
| oneM2M | 平台层互操作 | 统一服务层（CSE/AE 架构） |
| OCF / OMG | 应用层互操作 | OCF 设备规范、DDS |
| W3C | Web 与语义 | Web of Things、Thing Description |
| ETSI | 欧洲标准 | M2M 架构、TC SmartM2M |
| ISO/IEC | 通用标准 | IoT 参考架构（ISO/IEC 30141） |

**易错点：** 不要把「标准」与「联盟/开源项目」混为一谈。ZigBee、MQTT、LoRaWAN 严格说都是**事实标准（de facto standard）**——由联盟推广、市场认可，而非 ISO/ITU 这样的**法定标准（de jure standard）**。事实标准常常更快落地，但可能受联盟专利政策约束。<span class="marginnote">MQTT 的演化是两种标准的合流样本：1999 年由 IBM 发明，2014 年由 OASIS 标准化，2016 年成为 ISO 标准（ISO/IEC 20922）——从事实标准「转正」为法定标准。这类「市场先跑、机构后收编」的路径在互联网界屡见不鲜。</span>

## 3 语义互操作：让机器「听懂」数据

语法层只保证「格式对」，语义层要求「意思对」。实现语义互操作的两件套是**数据模型（data model）**与**本体（ontology）**：

**数据模型**：规定字段名、单位、类型——如 IPSO Smart Objects 为每种传感器定义了统一资源模型（温度资源、湿度资源各有固定 URI 与语义）。
- **本体**：用形式化的概念关系描述领域——如 SAREF（Smart Applications REFerence）为智能家居/建筑/能源定义共享概念；W3C 的 Thing Description 用 JSON-LD 描述设备的能力与交互方式，让设备「自描述」<span class="marginnote">「自描述」是语义互操作的最高形态：设备上线后，平台读取它的 Thing Description 就能知道它能干什么、怎么调用，而无需预先人工配置——这彻底改变了「对接新设备要写专属驱动」的局面，是 W3C Web of Things 的核心思想。</span>。

## 4 核心要点：互操作性的五层与标准化分工

（无公式主题，用表格复盘全篇核心）

| 互操作层 | 需要什么 | 谁来定 |
| --- | --- | --- |
| 设备层 | 频段、调制、电气 | IEEE 802.15.4/802.11 |
| 网络层 | IP 语义、路由 | IETF（6LoWPAN、RPL） |
| 语法层 | 编码、消息格式 | IETF/oneM2M（CBOR、JSON、CoAP） |
| 语义层 | 本体、数据模型 | W3C、SAREF、IPSO |
| 平台层 | 服务 API、统一服务层 | oneM2M、云厂商事实标准 |

这张表就是「IoT 互操作性地图」：从下到上，标准逐渐从「物理刚性」走向「语义柔性」，难度与价值同步递增。

## 5 辨析：统一平台 vs 协议网关 vs 语义互操作

面对碎片化，业界有两条互补路线：

**平台收敛（platform convergence）**：oneM2M 这类统一服务层，让所有垂直应用跑在同一套中间件上——「把差异收进平台」。
- **多协议网关（protocol gateway）**：在边缘用网关把 ZigBee/Modbus/LoRa 等各种协议翻译成统一格式——「把差异拦在边缘」。

**易错点：** 平台收敛解决「软件层互操作」，协议网关解决「接入层互操作」，二者不是二选一而是分层配合：网关负责接入侧翻译，平台负责数据侧统一，语义本体负责让两者「说的是一回事」。任何单点方案都治不了「巴别塔」，因为巴别塔是**横跨所有层**的问题。<span class="marginnote">这也回扣了第一篇的参考模型：互操作性问题在不同层有不同答案，而参考模型正是给「哪一层的哪个问题归谁管」提供坐标系的工具。</span>

## 6 小结

- **互操作性分五层**：设备、网络、语法、语义、平台；越往上越难，语义层是当前最大的缺口。
- **标准化是多组织分工**：IEEE/IETF/3GPP 管技术，oneM2M/OCF 管平台，W3C/SAREF 管语义；「事实标准」与「法定标准」是两种不同路径。
- **语义互操作**靠数据模型（IPSO）与本体（SAREF、W3C Thing Description）实现设备「自描述」。
- 统一平台与多协议网关是互补的两条路线，分层配合才能真正把「巴别塔」重新拼回「全球物联网」。
- 参考模型的意义在此闭环：它不止是理解 IoT 的地图，也是给互操作问题「定位归责」的坐标系。
