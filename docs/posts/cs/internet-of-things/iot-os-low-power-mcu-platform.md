## 为什么从「设备里的系统」开始

应用层协议跑在设备上，而设备是**低功耗 MCU（微控制器）**：几 MHz 到几百 MHz 的 CPU、几十 KB 到几 MB 的 RAM、由纽扣电池或能量收集供电。<span class="marginnote">与通用 Linux 服务器不同，物联网终端通常没有 MMU、没有磁盘、不能随便换电池——这决定了它上面的「操作系统」是完全不同的物种。</span>在这片贫瘠的土地上，RIOT、Contiki(-NG) 与 FreeRTOS 三个系统各自给出了自己的答案。本篇回答三个问题：为什么要上操作系统、它们如何调度任务、以及如何做到「几个月不换电池」。

## 1 裸机 vs RTOS：什么时候需要「操作系统」

早期嵌入式开发是**裸机（bare-metal）**：一个 `while(1)` 主循环轮询所有事件。裸机简单、零开销，但有两个硬伤：事件响应时延不可预测（一个耗时的传感器读取会阻塞其他事件）；多任务逻辑难以组织。<span class="marginnote">主循环 + 状态机的裸机写法在极简单的遥控器、玩具里仍然大量存在——「越简单越好」是嵌入式的第一原则，不要为用 OS 而用 OS。</span>

当设备需要同时做「收 MQTT 报文 + 采样温湿度 + 驱动显示 + 定时上传」时，就需要 **RTOS（实时操作系统）**。RTOS 的承诺是：**任务响应时延有上界**——这是它与通用操作系统最大的区别，通用系统追求吞吐量，实时系统追求「准时」。

这种「前后台（foreground/background）+ 中断」的经典结构值得说清：主循环是「后台」，中断服务程序（ISR）是「前台」。前台只做最紧急、最短暂的事（置标志、收数据），复杂的处理放回后台轮询——否则一个长 ISR 会掐死所有实时性。RTOS 的任务调度，本质是把「手工拆分前后台」的功夫自动化了：谁来做、何时做、做多久，由调度器说了算。

RTOS 的代价是**上下文切换开销**：每次任务切换要保存/恢复寄存器与栈，毫秒级任务的切换耗时通常在几微秒量级——任务越短，这个比例越刺眼，所以「太碎的任务」要合并。

## 2 三个主角：FreeRTOS、RIOT 与 Contiki-NG

| 系统 | 定位 | 内核特征 | 网络栈 | 适合谁 |
| --- | --- | --- | --- | --- |
| **FreeRTOS** | 通用嵌入式 RTOS | 抢占式 + 合作式调度，极简、开源 | 需自行配协议栈 | 入门最快、生态最大 |
| **RIOT** | 物联网专用 RTOS | 模块化内核，支持线程级与微内核两种模式 | 原生 MQTT/CoAP/6LoWPAN | 需要完整 IoT 协议栈的节点 |
| **Contiki-NG** | 资源受限网络 OS | 事件驱动 + 可选 protothread | 6LoWPAN、CoAP、RPL 网络 | 研究用途、超低内存节点 |

三者共享一个关键设计：**模块化**。系统内核只占几 KB，协议栈按需裁剪进固件——「缺什么编什么」，这是面向体积受限设备的必答题。<span class="marginnote">RIOT 的口号是「把 Linux 的开发体验带进物联网」：它支持 POSIX 风格 API、模块化构建（Kconfig）、原生模拟器，让开发者能在 PC 上先跑通网络逻辑再烧进板子。</span>

FreeRTOS 的「生态红利」最明显：Amazon 收购后推出 FreeRTOS Kernel + 云集成，配合 ESP-IDF、Arduino 等板级框架，几乎任何主流 IoT 芯片都有现成的移植。**对大多数「先跑起来」的产品，FreeRTOS 是默认答案；只有当你需要原生 6LoWPAN/CoAP 或极致内存时才考虑 RIOT/Contiki-NG。**

## 3 任务、调度与通信

RTOS 的核心概念三件套：

**任务（task）**：一个独立执行的代码单元，各有自己的栈（stack）。栈大小是嵌入式内存预算的「大头」，每个任务几百字节到几 KB。
- **调度器（scheduler）**：决定哪个任务此刻占用 CPU。常见策略是**优先级抢占**：高优先级任务就绪立即打断低优先级任务。Linux 的 CFS（完全公平调度）在嵌入式里并不常见——因为实时性优先于公平性。
- **任务间通信（IPC）**：队列（queue）、信号量（semaphore）、互斥量（mutex）。共享资源要用互斥量保护，否则出现竞态——与通用操作系统完全相同的问题，只是资源更稀缺。<span class="marginnote">互斥量在嵌入式里有一个著名的坑——<strong>优先级反转</strong>：低优先级任务持有锁，高优先级任务被它阻塞。经典的解法是<strong>优先级继承</strong>协议，FreeRTOS 内置支持，这是实时系统与普通系统的又一个分水岭。</span>

三者还有一个共同的内存特征：**没有 MMU、没有虚拟内存**——任务直接跑在物理地址上，一个任务写穿栈就会覆盖邻居。现代 MCU 常用 MPU（内存保护单元）给关键任务划隔离区，但在几 KB 内存上仍属奢侈品。**嵌入式内存安全的核心不是「防止溢出」，而是「让溢出尽快被发现」（看门狗 + 栈检查）**——这与桌面系统「让溢出不产生危害」的思路正好相反。

## 4 低功耗：休眠状态与能量预算

功耗是 MCU 平台的第一公民。绝大多数时间设备应该「睡觉」：现代 MCU 提供多种**睡眠模式（sleep modes）**——普通 sleep（CPU 停、外设活）、deep sleep（几乎全停）、off（仅 RTC 唤醒）。<span class="marginnote">以 STM32L 系列为例：运行态约 1 mA@3.3V，deep sleep 可低至 0.3 µA——差了三个数量级。低功耗设计的全部技巧，本质就是「尽量在 deep sleep 里待着」。</span>

能量预算（power budget）是工程设计的基础：纽扣电池约 200 mAh，设备若平均电流 2 mA，理论寿命 100 小时；若平均电流降到 20 µA，寿命延长到 10000 小时（约一年）。**平均电流**才是关键——所以通信要「醒来就猛发、发完就睡」，这正是 MQTT/CoAP「短报文」设计的物理动机。

用**占空比（duty cycle）**算一笔账：设备每 60 秒醒一次，醒来花 200 ms 完成「上电 + 采样 + 发送 + 休眠」，占空比 = 0.2/60 ≈ 0.33%。运行态电流 10 mA、休眠态 5 µA，则平均电流 ≈ 10 mA × 0.0033 + 5 µA × 0.9967 ≈ 38 µA——与一直开着（10 mA）相比差了 260 多倍。**低功耗工程的本质是「把占空比压到尽可能低」**，而这又要求通信协议快进快出，正是前面各篇反复强调「短报文」的最终理由。

再往极致走，还有**能量收集（energy harvesting）**：太阳能板、压电片、温差发电把环境能量攒进电容/电池，设备只在「攒够了」时醒来工作——它把「占空比」变成「可用能量的函数」。这类设备连换电池都不需要，但代价是软件必须容忍「随时可能没电」。

与休眠配合的另一项技术是**动态电压频率调节（DVFS）**：任务重时满频满压、任务轻时降频降压——它把「空闲即省」延伸到「半忙也省」。现代 MCU 在低主频下电流可再降一个量级，代价是计算变慢，所以 DVFS 的策略本质是「用时间换能量」。

## 5 公式解析：RMS 可调度性判定

调度器能否保证「准时」，有一个著名判定定理。设系统有 $n$ 个周期任务，第 $i$ 个任务的执行时间 $C_i$、周期 $T_i$，采用**速率单调调度（RMS，Rate Monotonic Scheduling）**——周期越短优先级越高——则全部任务可调度的充分条件是：

$$
U = \sum_{i=1}^{n} \frac{C_i}{T_i} \leq n\,(2^{1/n} - 1)
$$

- **第一步，$C_i/T_i$ 是第 $i$ 个任务的处理器利用率**：每周期执行 $C_i$，周期 $T_i$，占比就是比值。
- **第二步，左边求和得总利用率 $U$**：所有任务的总需求占比。
- **第三步，右边是 RMS 的利用率上界**：$n=1$ 时上界为 1（单任务可满载）；$n=2$ 时上界约 0.828；$n \to \infty$ 时上界趋向 $\ln 2 \approx 0.693$。<span class="marginnote">这个结论由刘与莱兰（Liu &amp; Layland, 1973）给出：即使 RMS 是最优的静态优先级算法，任务多时也只能保证约 69% 的 CPU 利用率——剩下 31% 必须「空着」，否则就有任务要超时。实时系统里 CPU 空转不是浪费，而是保证。</span>

代入一组数字：设 3 个任务，执行时间/周期分别为（1 ms, 10 ms）、（2 ms, 20 ms）、（3 ms, 50 ms），利用率 $U = 0.1 + 0.1 + 0.06 = 0.26$。$n=3$ 时 RMS 上界约 0.780，0.26 ≪ 0.780，判定为可调度。若把第三个任务换成（30 ms, 50 ms），$U = 0.1 + 0.1 + 0.6 = 0.8 > 0.780$——虽然总利用率没到 1，RMS 仍可能漏掉截止期。**「上界」的含义正在于此：超过它，必有任务迟到**，工程上要为峰值负载留足余量。

## 6 辨析：RTOS 与嵌入式 Linux 的分野

物联网设备界长期存在「RTOS vs 嵌入式 Linux」之争，其实二者根本不冲突：

| 维度 | RTOS（FreeRTOS/RIOT） | 嵌入式 Linux（Yocto/Buildroot） |
| --- | --- | --- |
| 硬件要求 | 几 KB RAM、无 MMU 也可 | 需 MMU、数 MB RAM、数 MB Flash |
| 实时性 | 微秒级可预测 | 一般（需 RT 补丁才可达 ms 级） |
| 启动时间 | 毫秒级 | 秒级 |
| 系统复杂度 | 单进程多任务 | 完整多进程、虚拟内存 |
| 适用场景 | 传感器节点、可穿戴 | 网关、边缘计算盒子 |

**易错点：** 认为「加个 RTOS 就实时了」——不，调度只是前提，时延上界还取决于中断屏蔽时间、关调度区间与内存访问；同样的任务集在两次配置不同的内核上，实时性可以差一个数量级。

实际选型的顺序通常是：**先定实时性要求与内存预算，再定是否需要网络协议栈，最后在 FreeRTOS 与 RIOT/Contiki-NG 之间二选一**。若只做「传感器 + 定时上报」，裸机或 FreeRTOS 就够；若要做「6LoWPAN 组网 + CoAP 服务」，RIOT 或 Contiki-NG 的原生协议栈能省下数月移植时间；而「既要原生协议栈、又要生态成熟」的项目，往往在 FreeRTOS 上加装第三方网络栈——选型并非非此即彼。

## 7 术语速查表

| 术语 | 含义 |
| --- | --- |
| RTOS | 实时操作系统，任务响应时延有上界 |
| 裸机（bare-metal） | 主循环 + 状态机，无操作系统 |
| 任务（task） | 独立执行单元，各有自己的栈 |
| 抢占调度 | 高优先级任务就绪即打断低优先级 |
| 优先级反转 | 低优先级持锁阻塞高优先级 |
| RMS | 速率单调调度，周期越短优先级越高 |
| sleep 模式 | CPU/外设按需关停的省电状态 |
| MPU | 内存保护单元，隔离任务内存 |
| 看门狗 | 软硬件定时器，超时即复位系统 |

## 8 小结

- **裸机 vs RTOS**：事件多、要求实时性时上 RTOS；RTOS 与 Linux 的关键差异是「时延有界」而非「功能更多」。
- **FreeRTOS**（通用极简）、**RIOT**（IoT 协议栈原生）、**Contiki-NG**（研究/超低内存）三者按网络栈与定位选型。
- 低功耗 = 「尽量 deep sleep」；能量预算用平均电流估算，通信「猛发快睡」。
- RMS 利用率上界 $n(2^{1/n}-1)$ 说明：任务越多，越要为实时性留出 CPU 余量。
- **前后台结构**是理解中断与任务分工的基础：长 ISR 是实时性杀手；任务切换有微秒级开销，太碎的任务要合并。
- 低功耗 = 压低占空比；能量收集让设备「不用换电池」，代价是软件要容忍随时断电。
- FreeRTOS 生态最成熟，是多数产品的默认选择；DVFS 与休眠共同构成「时间换能量」的功耗双手段。
- 实时系统看的是「最坏情况时延」而非「平均吞吐」——能用 RMS 上界预判的任务集，就不要靠赌运气。
