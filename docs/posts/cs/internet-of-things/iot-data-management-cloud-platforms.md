## 为什么从「数据瀑布」开始

前几篇完成了采集（感知层）、传输（接入层）、预处理（边缘层），现在数据像瀑布一样涌向云端。一台电梯每年上报的时序数据可达 GB 级，一座城市的传感器网络每秒产生百万级记录。<span class="marginnote">这些数据有三个与生俱来的特征：<strong>海量</strong>（数量级远超传统业务数据）、<strong>时序</strong>（几乎每条都带时间戳、按时间追加）、<strong>异构</strong>（不同厂商、不同语义、不同采样率混在一起）。这三点决定了 IoT 数据管理不能简单沿用传统数据库的方案。</span>本篇回答：数据到了云端，如何被接收、存储、组织，最终变成业务价值。

## 1 数据流：从设备到价值的三级管道

任何 IoT 云平台的数据路径都是同一条「三级管道」：

1. **接入（Ingest）**：MQTT broker / CoAP 网关接收设备上报，完成鉴权与协议转换，写入消息管道。这一级要求「高吞吐、低延迟、不丢消息」。
2. **处理（Process）**：流式处理（如 Apache Kafka + 流计算）对实时数据做过滤、聚合、窗口计算；批式处理（如 Spark）对历史数据做离线分析。<span class="marginnote">流与批的分工是数据工程的经典课题：流处理回答「刚刚发生了什么」（秒级），批处理回答「这段时间整体怎样」（小时/天级）。两种范式的取舍详见第二级《大数据系统》专题。</span>
3. **存储与服务（Store &amp; Serve）**：时序数据进时序数据库，设备元数据进关系库/图库，最终以 API 与仪表盘的形式输出给应用。

## 2 时序数据库：IoT 数据的第一存储选择

**时序数据库（TSDB，Time-Series Database）** 是专为「随时间追加、按时间查询」设计的存储，代表有 InfluxDB、TimescaleDB、TDengine、Prometheus（监控场景）。它与关系型数据库的差异是结构性的：<span class="marginnote">时序库的三大设计：<strong>列式存储</strong>（按时间分段、按列压缩，写入吞吐高）、<strong>持续下采样</strong>（老数据自动降精度，控制体积）、<strong>按时间范围分区</strong>（查询只扫相关分区）。这些设计都服务于同一个事实：IoT 数据的读写模式是「持续追加 + 时间窗口扫描」。</span>

| 维度 | 关系型（MySQL/PostgreSQL） | 时序库（InfluxDB/TDengine） |
| --- | --- | --- |
| 数据模型 | 表 + 外键 + 事务 | 测点（measurement）+ 标签 + 时间戳 |
| 写入模式 | 随机更新/删除 | 海量追加，几乎不更新 |
| 查询模式 | 任意条件 JOIN | 按时间范围与标签过滤 |
| 压缩比 | 低 | 高（列式 + 差值编码） |

**易错点：** 时序库不能取代关系库，二者各司其职——设备上报的实时数值进时序库，设备档案、用户、订单这类「实体关系」数据仍该留在关系库里，再由平台把二者关联起来。

## 3 云平台的五件套能力

主流 IoT 云平台（AWS IoT Core、Azure IoT Hub、华为云 IoTDA、阿里云 IoT Platform 等）提供的核心能力高度收敛，可用五件套概括：<span class="marginnote">这五件套恰好对应我们前几篇的所有主题：接入层（MQTT/CoAP）、标识层（设备唯一 ID 与证书）、边缘层（设备影子与规则）、存储层（时序与对象存储）、应用层（API 与可视化）。云平台本质上是「把前几篇讲的一切标准化成服务」。</span>

1. **设备接入与认证**：设备注册、证书鉴权、MQTT/CoAP 接入，保证只有合法设备能说话。
2. **设备管理**：固件升级（OTA）、远程配置、在线状态监控。
3. **设备影子（Device Shadow）**：云端缓存设备的期望状态与实际状态，解决「设备离线时如何接受指令」——设备连上网后自动同步影子。
4. **规则引擎与数据流转**：声明式规则把设备数据转给时序库、对象存储、函数计算等下游。
5. **数据服务与可视化**：时序查询 API、告警、仪表盘。

## 4 数字孪生：数据平台的价值出口

当「设备数据 + 设备模型」被组织成可查询、可仿真、可预测的数字映射时，就构成了**数字孪生（digital twin）**：物理世界的每个实体，在平台上有一个实时同步其状态的数字副本。<span class="marginnote">数字孪生不是「3D 模型」，而是「数据组织方式」：把设备属性、时序状态、空间关系、历史事件统一进一个可编程的对象。它让「电梯的实时状态」与「历史故障模式」可以放在同一个对象里推理——见独立专题《数字孪生》。</span>数据平台的一切存储与处理，最终都在为这样的数字映射服务。

## 5 公式解析：IoT 数据量估算

设计平台前必须先算清楚「要扛多少数据」。单个设备的上报数据率由三个参数决定：

$$
R = f_s \times b \times n
$$

- **第一步，$f_s$ 是采样/上报频率（次/秒）**：10 秒一次 → $f_s = 0.1$；1 秒一次 → $f_s = 1$。它是数据量的第一放大器。<span class="marginnote">举例：10 万个传感器各每 10 秒上报一条、每条 100 字节，则平台需吞下 $10^5 \times 0.1 \times 100 = 10^6$ 字节/秒 = 1 MB/s，一天约 86 GB，一年约 31 TB——这就是「数据瀑布」的量级。下采样与边缘聚合正是为了砍 $f_s$ 与 $b$。</span>
- **第二步，$b$ 是单条记录的字节数**：协议载荷 + 时间戳 + 设备 ID + 遥测值。协议头就是上上篇讲的「开销」，选轻量协议直接缩小 $b$。
- **第三步，$n$ 是设备数量**：系统的规模因子。三者相乘即总数据率，决定时序库的写入压力与存储成本。

**易错点：** 数据量估算必须包含「每条记录的元数据」（设备 ID、时间戳、质量标志），它往往占单条记录的一半以上——只按「业务字段」估量会低估平台容量一半以上。

## 6 小结

- IoT 数据的三重特征：**海量、时序、异构**，决定了数据管道的「接入—处理—存储服务」三级结构。
- **时序数据库**是 IoT 第一存储选择（追加式写入 + 时间窗口查询），与关系库是分工而非替代。
- 云平台五件套：接入认证、设备管理、设备影子、规则引擎、数据服务；**设备影子**解决离线指令同步。
- **数字孪生**是数据平台的价值出口——把物理实体组织成可推理的数字映射。
- 数据率公式 $R = f_s \times b \times n$ 是平台容量设计的第一笔账，别忘了算元数据开销。

在下一节，我们把视线从「数据怎么流动」转向「坏人怎么入侵」——物联网安全与隐私：为什么密码学在这个世界里变成了「跷跷板上的平衡术」。
