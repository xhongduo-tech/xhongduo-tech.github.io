## 为什么从「设备与平台的语言」开始

无线协议把数据搬到了网上，但设备与平台之间还需要**共同语言**：数据长什么样、如何请求、谁来订阅。这就是应用层协议的职责。<span class="marginnote">应用层协议是「最后的十厘米」——它直接决定你写的物联网代码是否与云平台互通。同一块开发板，选 MQTT 还是 HTTP，数据流架构完全不同。</span>物联网设备的应用层世界由三个主角统治：**MQTT**（发布/订阅）、**CoAP**（受限 REST）与 **HTTP**（传统 Web）。它们的共同设计哲学，恰好是拉姆斯那句「少而更好」——在几百字节的内存里，任何冗余都是致命的。

## 1 两种通信范式：请求/响应 与 发布/订阅

先分清两大类范式，这是理解三种协议的地图：

**请求/响应（Request/Response）**：客户端问，服务器答。HTTP 与 CoAP 都属于这一类。简单直接，但客户端必须「主动」，服务器无法主动把变化推给客户端。
- **发布/订阅（Publish/Subscribe）**：消息的生产者与消费者彻底解耦，中间有一个**代理（broker）**按主题（topic）转发。MQTT 属于这一类。<span class="marginnote">发布/订阅模式是分布式系统解耦的经典手段：发布者不关心谁在听，订阅者不关心谁在说，双方只通过主题名耦合。它天然适配「成千上万传感器向一个平台上报」的 IoT 场景，参见第二级《分布式系统》与《消息队列》专题。</span>

IoT 的核心矛盾是「海量设备要主动上报，还要被随时下行控制」——发布/订阅几乎是为这个矛盾量身定做的，这正是 MQTT 成为物联网事实标准的原因。

## 2 MQTT：低功耗发布/订阅的事实标准

**MQTT（Message Queuing Telemetry Transport，消息队列遥测传输）**，1999 年由 IBM 的安迪 · 斯坦福-克拉克（Andy Stanford-Clark）与 Arcom 的阿尔伦 · 尼珀（Arlen Nipper）设计，2014 年成为 OASIS 标准。三个关键词：**TCP 连接、主题订阅、三种 QoS**。

**结构**：客户端连上 broker，发布消息到主题（如 `home/livingroom/temp`），其他订阅了该主题的客户端收到副本。broker 是星型拓扑的中心，负责主题过滤与转发。
- **QoS 三个等级**：QoS 0 至多一次（丢了不管）；QoS 1 至少一次（ACK 确认，可能重复）；QoS 2 恰好一次（四步握手，保证不重不漏）。等级越高，越可靠，代价是越多的往返与状态存储。<span class="marginnote">MQTT 报文头只有 2 字节，5 字节起步的固定报头使它在 2G 时代的慢速连接上也能流畅工作——「轻量」是 MQTT 设计的灵魂。</span>
**持久会话与遗嘱消息**：遗嘱消息（LWT）在设备异常断线时替它发布一条「我死了」的消息，让平台及时感知设备离线——这是设备监控的关键能力。

**主题通配符与保留消息**：MQTT 支持主题层级（`home/livingroom/temp`）与两个通配符——`+` 匹配单层（`home/+/temp` 订阅所有房间的温度）、`#` 匹配多层（`home/#` 订阅整个 home 下的所有主题）。**保留消息（retained message）**让 broker 记住某主题的最后一条消息，新订阅者一上线就能拿到设备当前状态，而不是空等下一次上报——这常是「设备状态同步」的最省事实现。

一个具体的 QoS 选型例子：温度遥测（每秒一条、丢一条无妨）用 QoS 0 即可；设备 OTA 升级指令（丢一条就坏）必须 QoS 1/2；而「门锁开合」这类控制命令，QoS 1 的重发可能造成重复执行，所以要么用 QoS 2，要么在应用层做幂等。**QoS 只是传输层的保证，应用层还要自己处理「重复」与「乱序」**——这是最容易踩的坑。

## 3 CoAP：受限网络的 REST

**CoAP（Constrained Application Protocol，受限应用协议）**，IETF RFC 7252，专为内存几 KB、功耗微瓦的节点设计。它把 HTTP 的 REST 语义（GET/POST/PUT/DELETE）搬到 **UDP** 上，用紧凑的二进制头（4 字节）替代 HTTP 的文本头。

- **确认消息**：CoAP 的消息类型分 CON（可确认）、NON（不可确认）、ACK、RST。CON 消息用「简单停等重传」保证可靠——比 TCP 的拥塞控制简单得多，适合内存极度受限的节点。
- **资源发现**：`/.well-known/core` 支持节点自描述资源列表，设备上电后平台可以发现它支持哪些资源——这是与 HTTP 语义互操作的桥。
- **与 HTTP 的翻译**：CoAP 与 HTTP 之间有标准映射（CoAP 到 HTTP proxy），使得受限节点也能接入 Web 体系。<span class="marginnote">CoAP 使用 DTLS（基于 UDP 的 TLS）做安全传输；MQTT 则多走 TLS over TCP。两者的安全纵深都会在本专题《物联网安全与隐私》中展开。</span>

CoAP 还有一个常被忽略的杀手级扩展——**Observe（RFC 7641）**：客户端可以「订阅」一个资源，服务器在资源变化时主动推送，而不是每次轮询。这相当于把发布/订阅的一部分能力装进了请求/响应框架——受限节点也能实现「变化即通知」，是传感器上报的又一个轻量选项。

## 4 HTTP：传统但笨重的「标准答案」

**HTTP** 是 Web 的基石，但它在 IoT 场景有三个硬伤：TCP 三次握手 + 每次请求的 HTTP 头（几百字节）开销巨大；请求/响应模型让服务器无法主动推送；状态管理（Cookie/会话）对嵌入式客户端过重。它的用武之地被压缩到：**设备管理接口、云端 API 之间的服务调用、以及浏览器端控制面板**。<span class="marginnote">HTTP/2 的帧多路复用与 HTTP/3 的 QUIC 都改善了一些痛点，但本质仍是请求/响应，取代不了 MQTT 在设备侧的地位——这提醒我们：协议选型看的是「范式是否匹配」，而非「版本新旧」。</span>

一个实用的判定：**如果请求是「人在浏览器里发起」，用 HTTP 准没错；如果请求是「设备在电池里发起」，就要优先 MQTT/CoAP**——人不在乎几百字节的协议头，电池在乎。

## 5 公式解析：协议的「载荷效率」

三种协议的核心差异之一是**固定开销**。定义载荷效率为「有效载荷占总字节的比例」：

$$
\eta = \frac{L_{\text{payload}}}{L_{\text{payload}} + L_{\text{overhead}}}
$$

- **第一步，$L_{\text{payload}}$**：真正的业务数据。一个温湿度读数常只有 4–20 字节——物联网业务数据极其短小，这正是问题的根源。
- **第二步，$L_{\text{overhead}}$**：协议头与封装。HTTP 一个 POST 请求的头部通常 200–800 字节；MQTT 固定报头仅 2 字节、可变报头与主题名一般几十字节；CoAP 头 4 字节。
- **第三步，代入体会**：当载荷 20 字节时，HTTP 的 $\eta \approx 20/400 \approx 5\%$，MQTT 约 30–50%，CoAP 约 70%。<span class="marginnote">这解释了为什么 MQTT/CoAP 是设备侧之王：同样的电池，95% 的无线电能量花在传输协议头上，是一种灾难性的浪费——低功耗的本质是「少说废话」。</span>

再用 OTA 升级感受量级差异：一次 100 KB 的固件升级，CoAP 拆成约 5000 个 20 字节的块、额外开销 ≈ 5000 × 4 字节头部 = 20 KB；同样的数据走 HTTP，头部开销轻松超过载荷本身。**载荷越小、报文越频繁，协议头占比就越致命**——这是固件升级偏爱「块传输 + 紧凑头」的原因。

## 6 报文字段速览：三种协议的一次对照

把同一台设备的同一句「温度 25.5 °C」分别用三种协议发送，直观感受各自的开销：

| 维度 | MQTT | CoAP | HTTP |
| --- | --- | --- | --- |
| 传输 | TCP 流 | UDP 数据报 | TCP 流 |
| 固定头 | 2 字节 | 4 字节 | 请求行 + 数百字节头 |
| 主题/资源 | 主题字符串（如 `dev/001/temp`） | URI 路径（如 `/temp`） | URL 路径 |
| 载荷 | 任意字节（常 JSON/CBOR） | 任意字节（常 CBOR） | 文本/JSON |
| 典型确认 | 一次往返（PUBACK） | 停等重传 | 三次握手 + 请求 + 响应 |

同一条业务数据，三种协议的头开销从几字节到几百字节不等——**在「每秒上报一次」的海量场景里，这个差距就是电池寿命的差距**。

## 7 辨析：MQTT vs CoAP vs HTTP 选型矩阵

| 维度 | MQTT | CoAP | HTTP |
| --- | --- | --- | --- |
| 传输 | TCP（可靠） | UDP + 简单重传 | TCP |
| 范式 | 发布/订阅 | 请求/响应 | 请求/响应 |
| 头部开销 | 2 字节起 | 4 字节 | 数百字节 |
| 可靠性 | QoS 0/1/2 | CON 确认 | 依赖 TCP |
| 消息模型 | 主题 | 资源 URI | 资源 URI |
| 最佳场景 | 海量上报 + 下行控制 | 极度受限节点、边缘互联 | 云端 API、Web 管理 |

**易错点：** 很多人误以为 MQTT 一定比 CoAP 好。其实二者定位不同：MQTT 强于「海量设备经 broker 汇聚」，CoAP 强于「极受限节点之间的直接互操作（如传感器之间互相读写资源）」。两者经常同场出现：LoRaWAN 终端 → CoAP 网关 → MQTT broker → 云平台，是一条经典的协议接力链。

## 8 术语速查表

| 术语 | 含义 |
| --- | --- |
| broker | 发布/订阅模式中的消息代理，按主题转发 |
| QoS | 服务质量等级，0/1/2 对应至多一次、至少一次、恰好一次 |
| LWT | 遗嘱消息，设备异常断线时替它发布的离线通知 |
| retain | 保留消息，broker 记住主题最后一条消息 |
| REST | 资源化接口风格，GET/POST/PUT/DELETE |
| DTLS | 基于 UDP 的 TLS，CoAP 的安全传输层 |
| Observe | CoAP 的资源订阅扩展，资源变化主动推送 |

看懂这张表，MQTT/CoAP 选型时的大部分术语障碍就清除了。

## 9 小结

- 应用层两大范式：**请求/响应**（HTTP、CoAP）与**发布/订阅**（MQTT），后者天然匹配海量设备上报与双向控制。
- **MQTT**：TCP + 主题 + QoS 0/1/2 + 遗嘱消息，IoT 事实标准；**CoAP**：UDP + REST + 4 字节头，为极度受限节点设计；**HTTP**：开销大、范式不匹配，退守云端 API 与 Web。
- 载荷效率公式 $\eta = \frac{L_{\text{payload}}}{L_{\text{payload}} + L_{\text{overhead}}}$ 揭示了「低功耗 = 少说废话」的工程本质。
- 现实系统常是三层接力：CoAP 做边缘互操作、MQTT 做设备—平台汇聚、HTTP 做云端服务接口。
- **报文速览提醒**：协议头占比随报文变短而急剧上升，「紧凑头」是 IoT 应用层协议的生存之本。
- **主题通配符、保留消息、Observe 订阅**让「海量、低频、状态同步」这类场景有了省电又可靠的默认解。
