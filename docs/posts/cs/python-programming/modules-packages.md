## 为什么从模块开始

上一节的函数让逻辑可复用，但所有代码还挤在一个文件里。程序一大，就需要**拆分**：把不同职责放进不同文件，各自维护、彼此导入。这个「拆文件、再组装」的机制，就是**模块（module）** 与**包（package）**。

官方 Python 教程第 6 章系统讲解了 `import` 的机制。这一节学四件事：什么是模块、`import` 有哪几种形态、`__name__ == "__main__"` 是怎么回事、以及包如何组织目录。

## 1 模块：一个 .py 文件就是一个命名空间

**模块（module）**：任何一个 `.py` 文件都是一个模块，文件名就是模块名。模块里的函数、类、变量构成它自己的**命名空间**——`import` 后通过 `模块名.名字` 访问，不会污染你的全局命名。

```python
# pizza.py
def make_pizza(size, *toppings):
    print(f"制作 {size} 英寸披萨：{toppings}")

# main.py
import pizza
pizza.make_pizza(12, "mushrooms")
```

**重点：`import` 有缓存。** 一个模块在同一个进程里只会被执行一次（字节码缓存于 `__pycache__`），之后 `import` 只是把已加载的模块对象绑定到名字——这也解释了为什么第二次导入更快。模块被导入时，其顶层代码会立即执行一遍，所以**顶层只放定义、不放有副作用的代码**。这正是「可导入的模块」与「直接运行的脚本」的分野，我们将在下一节用 `__name__` 把它规范化。

模块的**文档字符串**也值得养成习惯：文件顶部用 `"""模块用途与用法"""` 说明这个模块做什么、怎么用，`help(模块名)` 会原样显示它。一个「有说明的模块」与「没说明的模块」，协作成本天差地别——docstring 是给下一个读代码的人（包括六个月后的自己）写的。<span class="marginnote">Python 3.3 起 `__pycache__` 目录存放编译出的 `.pyc` 字节码。这正好印证了《起步》一节说的「解释型语言也有字节码层」——模块的导入快慢就藏在缓存里。</span>

## 2 import 的四种形态

| 写法 | 作用 | 调用方式 |
| --- | --- | --- |
| `import mod` | 导入整个模块 | `mod.func()` |
| `from mod import func` | 只导入某个名字 | `func()` 直接用 |
| `from mod import a, b, c` | 导入多个名字 | `a`、`b`、`c` 直接用 |
| `import mod as m` | 起别名 | `m.func()` |

`as` 别名常用于处理命名冲突或过长模块名。**辨析｜易错点：** `from mod import func` 之后，若你在文件里另写了同名 `func`，会**遮蔽**导入的名字——`from ... import ...` 引入的名字是可被覆盖的绑定，而 `import mod` 的名字空间几乎不会冲突。

PEP 8 对导入还有一条布局约定：**所有 `import` 放在文件顶部**，按「标准库 → 第三方库 → 本地模块」三组排列，组间空行分隔。这让文件的依赖一眼可见，也避免了「用到才导入」造成的隐晦循环依赖。

**辨析｜易错点：** **循环导入**（模块 A 导入 B、B 又导入 A）在启动时会导致 `ImportError`。避免之道有三：把共享常量与工具抽进独立模块、把导入挪到函数内部、或干脆重新设计依赖方向。循环导入的根治方案永远是「让依赖单向化」——这背后是模块划分的艺术：每个模块只依赖更基础的东西，形成清晰的层次。<span class="marginnote">`from mod import *` 会导入模块里所有不以 `_` 开头的名字，被称为「通配导入」。它省事但危险——你不知道导入了什么，容易悄悄覆盖已有名字。PEP 8 建议避免，至少要用模块的 `__all__` 显式声明白名单。</span>

## 3 __name__ 与 __main__：脚本与库的两栖身份

一个 `.py` 文件既能被「当作脚本直接运行」，也能被「当作模块被导入」。如何让同一份代码两种用法都正确？答案藏在 `__name__` 里：

```python
# greeting.py
def say_hello():
    print("Hello!")

if __name__ == "__main__":      # 只有直接运行时才进入
    say_hello()
```

**重点：`__name__` 是模块的内置属性。** 直接运行时它的值是 `"__main__"`；被导入时它的值是模块名（如 `"greeting"`）。所以 `if __name__ == "__main__":` 是「仅当作为主程序直接运行时才执行」，被导入时则跳过。

```bash
python greeting.py     # 输出 Hello!（作为脚本）
python -c "import greeting"   # 无输出（作为模块导入）
```

这是 Python 项目的标准「双入口」写法：定义部分永远可导入，演示/测试/入口逻辑放在 `if __name__ == "__main__":` 之下。

与之配套的还有 `python -m 模块名` 的**模块运行**方式——它「作为模块」运行文件，同时把文件所在目录加入 `sys.path`。`python -m venv`、`python -m pip` 都是这种用法；`-m` 让包内的相对导入能被正确解析，是命令行工具的标准写法。

## 4 包：用目录组织模块

**包（package）**：一个包含模块文件的目录，用来组织大量模块。传统上目录需含 `__init__.py` 表明身份；Python 3.3 后即使没有它，命名空间包也能工作。

```
project/
├── main.py
└── sound/
    ├── __init__.py
    ├── formats/
    │   ├── __init__.py
    │   └── wavread.py
    └── effects/
        ├── __init__.py
        └── echo.py
```

导入方式与模块一致，用点号表示层级：

```python
from sound.formats import wavread      # 绝对导入
from . import echo                     # 相对导入：从当前包导入
```

**辨析｜易错点：** 相对导入（`from . import x`、`from .. import y`）只在**包内部**有效，且 `.` 表示当前包、`..` 表示上一层。顶层脚本里不能用相对导入（它没有包上下文），这是「为什么我把这段逻辑放进一个包后反而报错了」的常见原因。<span class="marginnote">import 的搜索顺序是：内置模块 → `sys.path` 中的路径（含脚本所在目录、`PYTHONPATH`、站点包目录）→ 沿途的包。`sys.path` 可用 `python -m site` 查看。依赖装在 `site-packages`，正是《虚拟环境与包管理》一节的舞台。</span>

`__init__.py` 的角色也常被误解：它不只是「包存在的标记」，而是**包的初始化代码**所在——包被导入时它最先执行，常用来集中导出 `from package import *` 应公开的名字（通过 `__all__` 声明），或初始化包级共享状态。一个空 `__init__.py` 则单纯「声明这是包」。

**重点：包是「目录 + 命名空间」，模块是「文件 + 命名空间」。** 二者只是组织层级不同，导入语义完全一致——路径的每一段都是命名空间，`.` 分隔层级。理解这一层，`from sound.formats import wavread` 就能读成「从 `sound.formats` 包里取 `wavread` 模块」。

## 5 小结

- 一个 `.py` 文件就是一个**模块**；`import` 后通过「模块名.名字」访问其命名空间。
- `import` 有缓存：同进程内模块只执行一次，顶层代码导入时即运行。
- 四种导入形态：`import mod`、`from mod import x`、多名字导入、`as` 别名。
- `__name__ == "__main__"` 让一个文件既能当脚本跑、也能被导入复用。
- **包**是组织模块的目录；相对导入 `from . import x` 只在包内有效。
- `from sound.formats import wavread` 读作「从包取模块」：包即目录、模块即文件，导入语义一致。
- `python -m 模块名` 以模块身份运行，能正确解析包内相对导入，是命令行工具的标准写法。
