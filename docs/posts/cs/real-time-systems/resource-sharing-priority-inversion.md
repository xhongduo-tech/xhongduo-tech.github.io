## 为什么从资源共享开始

前四节我们都在「任务独立」的理想温室里讨论调度：没有共享数据、没有互斥、没有临界区。但真实系统里任务从不孤立——传感器任务写共享缓冲区，控制任务读同一块数据，两个任务要访问同一个设备寄存器。互斥锁（mutex）由此登场，而它一登场，就撕碎了 RM 与 EDF 的全部假设：**一个低优先级任务持锁时，高优先级任务即使就绪也只能干等**。<span class="marginnote">这正是《操作系统》里同步互斥问题在实时约束下的严峻形态：那里我们关心「死锁不发生」，这里我们还要加一条——「阻塞有界、且可分析」。两种关切叠加，才构成实时资源共享的完整问题。</span>本章先看清问题本身：优先级反转是什么、为何「无界」、会带来多可怕的后果。

## 1 共享资源与临界区

**共享资源（shared resource）**：被多个任务访问的数据、设备或服务，如共享缓冲区、打印机、总线控制器。**互斥（mutual exclusion）**：任何时刻最多只有一个任务能访问该资源，访问期间其他任务被排斥在外。

实现互斥的标准手段是**临界区（critical section）**：任务执行到访问共享资源的代码段，须先获取该资源对应的锁；持锁期间其他任务若请求同一把锁，将被阻塞，直到持锁任务释放锁。<span class="marginnote">这里的「阻塞」是任务因等锁而暂停，与被更高优先级任务抢占不同：抢占是「技不如人」让位，阻塞是「资源被占」让位。调度分析要分别计算二者的时间。</span>

在无实时约束的系统里，互斥只需保证正确性——谁先谁后无所谓。实时系统则多一个要求：**等待锁的时间必须有一个已知的、尽量小的上界**。这个上界叫**阻塞时间（blocking time）**，它会进入每个任务的可调度性分析：任务的响应时间 = 执行时间 + 被抢占时间 + 被阻塞时间。

## 2 优先级反转：一次「长幼颠倒」的灾难

**优先级反转（priority inversion）**：高优先级任务 H 需要访问资源 R，而 R 正被低优先级任务 L 持有，H 只能等待 L 释放——此时 H 的「优先级」形同虚设，它被一个低优先级任务按在等待队列里。严格来说，「高优先级等低优先级」本身不算错（这是互斥的必然代价），**问题在于等待可能被无限拉长**。经典的三个任务场景讲清了拉长的机制：

设三个任务：高优先级 H、中优先级 M、低优先级 L，均周期释放，H 与 L 共享资源 R：

1. **L 先到**，进入临界区，持有 R。
2. **H 到达**，请求 R 被阻塞，处理器转给……此时若按优先级，M 应该执行。
3. **M 到达**（不碰 R），它优先级高于 L，于是抢占 L，占用处理器。L 持锁却无法前进，R 被它牢牢攥在手里。
4. **H 继续等**：它等的不是 L，而是「等 L 能运行」，可 L 被 M 无限抢占——只要 M 周期性地到来，L 就永远轮不到执行，H 也就永远等不到 R。

于是 H 的阻塞时间不再由 L 的临界区长度决定，而是取决于 **M 的执行**——与 H 毫不相干的 M。这就是**无界阻塞（unbounded blocking）**。从 H 的视角看，它的优先级被「反转」了：本该最高，实际排在 M、L 之后。

辨析｜易错点：**优先级反转 ≠ 高优先级等待低优先级。** 等待本身不可避免（互斥使然），真正的病根是**中优先级任务的插队放大了等待**。无界阻塞的三个主角缺一不可：低优先级持锁者 + 中优先级抢占者 + 高优先级等锁者。

## 3 公式解析：阻塞时间进入可调度性分析

把阻塞量化，是解决反转问题的第一步。设任务 $T_i$ 一次执行中至多可能被阻塞 $B_i$（最坏情况下等待锁的时间），则 $T_i$ 的**最坏响应时间**满足：

$$
R_i = C_i + B_i + (\text{被高优先级任务抢占的时间})
$$

关键项是阻塞项 $B_i$。若不加任何协议，$B_i$ 可能被中优先级任务拉成「无界」——数学上写不出上界。而加上合适的资源共享协议后，$B_i$ 被约束为一个可计算的有限值，于是可调度性条件多出一条：

$$
\forall i: \quad D_i \geq R_i = C_i + B_i + \text{抢占}
$$

逐步拆解：

- **第一步，识别 $B_i$**：$B_i$ 是 $T_i$ 因等锁而阻塞的最坏时间。它来自 $T_i$ 可能请求的每个资源，取所有资源的最坏情况之和。
- **第二步，比较 $B_i$ 与 $C_i$**：没有协议时，$B_i$ 由别的任务的执行时间决定，可能与 $T_i$ 毫无关系——这是「无界」的数学含义。协议的作用就是把 $B_i$ 拉回到「与持锁者临界区相关」的合理范围内。
- **第三步，重新审视可调度性**：一旦 $B_i$ 无界，$D_i \geq R_i$ 无法验证，此前 RM/EDF 的利用率界全部失效。**只要存在共享资源，可调度性分析就必须显式计入阻塞项**——这是资源共享对实时分析的第一个冲击。

## 4 案例：火星探路者的优先级反转

1997 年 7 月，NASA 的**火星探路者（Mars Pathfinder）**着陆火星，开始探测。几天后，任务系统开始周期性**整体复位**——数据丢失，任务被迫中断。工程师们远程排查，发现真凶正是优先级反转。

探路者的软件运行在 VxWorks 实时操作系统上，飞船的信息总线由一个**共享互斥量**保护，任务间通过它交换数据。一个低优先级的气象数据收集任务偶尔持锁，随后高优先级的通信任务请求该锁被阻塞；此时一个中优先级的任务频繁运行，把持锁的低优先级任务压住——高优先级任务等锁等到超时，看门狗（watchdog）误判系统卡死，触发复位。<span class="marginnote">这起事故的教训常被总结为「测试没跑出最坏情形」：地面测试里反转时间太短，从没触发过看门狗；直到火星上两个任务恰好长时间相遇，系统才以整机复位的方式「买单」。</span>

修复方案几乎不花一改代码的事——把 VxWorks 的互斥量改为启用**优先级继承**（我们下一节的主角之一），反转被抑制，探路者此后顺利完成了整个 90 天探测任务。这个案例的价值在于：**优先级反转不是理论玩具，而是真实航天器的故障。**

## 5 抑制反转的策略谱系

问题清楚了，对策分两大流派：

**封锁低优先级执行（direct inheritance / 优先级继承）**：当高优先级任务被低优先级任务阻塞时，把低优先级任务的优先级临时提升到高优先级的水平，让它尽快执行完临界区、释放资源。中优先级任务因此无法再插队。<span class="marginnote">优先级继承是「头疼医头」：谁挡了高优先级的路，就把谁临时抬上去。它实现简单、无需预知资源关系，但可能引起链式提升与额外分析难度。</span>

**防止并发访问（priority ceiling / 天花板协议）**：预先规定「持有某资源的任务，其优先级不得低于可能请求该资源的所有任务中的最高者」，从根上杜绝低优先级持锁挡住高优先级的情形。天花板协议更系统、阻塞更小，但需要离线分析资源的使用关系。

**PIP 与 PCP 的快速对照**：

| 维度 | 优先级继承（PIP） | 优先级天花板（PCP / ICPP） |
| --- | --- | --- |
| 提升对象 | 阻塞发生时，只抬升持锁者 | 持锁者按资源天花板值抬升 |
| 提升时机 | 动态，被阻塞时才生效 | 静态，进入临界区即生效（ICPP） |
| 能否防死锁 | 否，可能循环等待 | 是，天花板切断循环等待 |
| 需要的资源信息 | 无需预知 | 需离线枚举资源竞争关系 |
| 阻塞上界 | 有界但偏大 | 更小、更紧凑 |
| 实现成本 | 低，多数 RTOS 一行启用 | 较高，需编译期计算天花板 |

两条路线的细节、变体与可调度性影响，是下一节的完整主题。今天只需记住：**协议的目的只有一个——把 $B_i$ 从「无界」拉回「有界且可算」。**

## 6 诊断优先级反转与预防设计清单

**现场诊断**：优先级反转在运行现场的特征是「高优先级任务长时间不执行，但处理器并不空闲」。排查手段：

1. 用跟踪工具记录各任务的执行段与阻塞点，观察高优先级任务是否长时间处于「等锁」状态；
2. 对比该时段的处理器占用——若处理器被中优先级任务占满而高优先级任务饿着，基本可判定反转；
3. 复现时掐断中优先级任务的负载，若高优先级任务立刻恢复响应，则反转成立。

**术语速查表**：

| 术语 | 含义 | 关联协议 |
| --- | --- | --- |
| 临界区 | 访问共享资源的互斥代码段 | 所有协议 |
| 阻塞时间 | 任务等锁的时间上界 | 可调度性分析的输入 |
| 无界阻塞 | 阻塞被中优先级拉长、无上界 | 问题根源 |
| 优先级反转 | 高优先级被低优先级持锁者间接拖延 | 现象 |
| 优先级继承 | 阻塞时抬升持锁者优先级 | PIP |
| 优先级天花板 | 资源竞争关系的静态编码 | PCP / ICPP |

**预防性设计清单**：

1. 尽量减少共享资源数量与临界区长度——临界区越短，阻塞上界越小；
2. 需要共享时，默认启用 ICPP 互斥（多数 RTOS 一行配置）；
3. 为每个任务的可调度性分析显式计入 $B_i$，而不是指望「应该不会碰巧出事」；
4. 硬实时场景避免动态创建资源与锁，保持资源关系离线可知。

辨析｜易错点一：**看门狗超时 ≠ 系统死机。** 探路者事故里系统硬件正常，只是高优先级任务被饿到看门狗超时。现场排障时，先查「优先级反转导致的饿死」，再查「真的死机」。

辨析｜易错点二：**继承协议不是万能的。** PIP 能抑制反转但不能防死锁；PCP 能防死锁但要求资源关系已知。选协议前先回答「我能否离线枚举资源使用关系」。

辨析｜易错点三：**阻塞时间与执行时间不能混为一谈。** $B_i$ 是「等锁」，$C_i$ 是「执行」，可调度性公式里分开计。把阻塞塞进执行时间会让分析失真，且无法定位反转。

## 7 小结

- **共享资源**用互斥保护，实时系统要求等待锁的**阻塞时间有界且可分析**。
- **优先级反转**是高优先级任务被低优先级持锁任务间接阻塞，中优先级任务的插队使阻塞**无界化**。
- 阻塞时间 $B_i$ 进入可调度性条件 $D_i \geq C_i + B_i + \text{抢占}$；无协议时 $B_i$ 无界，协议的作用是把它拉回有界可算。
- 抑制反转的两条路线：**优先级继承**（PIP）与**优先级天花板**（PCP / ICPP）；PIP 简单但不防死锁，PCP 更系统但需要离线资源关系。

在下一节，我们将兑现「有界阻塞」的承诺——走进优先级继承（PIP）与优先级天花板（PCP / ICPP）的完整机制、变体与各自的可调度性分析。
