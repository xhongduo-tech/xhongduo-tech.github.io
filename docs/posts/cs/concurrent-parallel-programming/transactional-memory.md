## 为什么从事务内存开始

写了整整十课锁，这一课反问一句：**锁，是不是正确的方式？** 锁的缺陷一箩筐：容易忘、容易死锁、粒度难选、组合困难。数据库界早就给出另一种答案——**事务**：一串操作要么全部生效、要么全部回滚，并发正确性交给系统。**事务内存（Transactional Memory, TM）**把这个想法搬进共享内存编程：程序员写 `atomic { ... }`，系统负责原子性、隔离性与可扩展性。Herlihy §17 讲它的抽象模型、实现机制与**无等待事务**的构造——我们用「环形缓冲 + 排他锁」这个经典案例把它讲透。

## 1 锁的痛，事务的解

锁的三个结构性缺陷：

1. **正确性难以组合**：两段各自正确的加锁代码拼在一起，可能死锁或竞态——锁是「全局的」正确性，局部无法保证。
2. **粒度两难**：锁太少→争用大；锁太多→开销大且易死锁。
3. **优先级反转与饿死**：锁的顺序天然偏向某些线程。

**事务内存**的承诺：程序员只声明「这段代码是原子事务」，运行时保证——**要么整个事务像一次原子操作一样提交（commit），要么一个字节都不改、回滚重试（abort）**。<span class="marginnote">事务的三个经典性质 ACID 在 TM 里取其二：原子性（全成或全败）与隔离性（并发事务互不看见中间态）。持久性不是共享内存的职责——内存本就易失；一致性由程序员负责。</span>

```c
atomic {                          /* 声明一个事务 */
    x = x + 1;
    y = y - 1;   /* 要么两条都生效，要么都不生效 */
}
```

## 2 冲突与回滚：乐观并发的基础

事务的正确性建立在**冲突（conflict）**检测上：两个事务访问同一内存地址、且至少一个是写，就冲突。TM 采用**乐观**策略：

事务先**猜测执行**（speculatively），改动写进**事务本地缓冲区（transactional buffer）**，不直接落盘到共享内存；
- 提交时检测是否与其他已提交事务冲突：**无冲突→原子提交**；有冲突→**回滚重试**（通常让后到者 abort）。

**核心要点：** 乐观 vs 悲观正是 TM 与锁的哲学分水岭——锁是「先申请再动手」（悲观），TM 是「先动手再验证」（乐观）。低争用时 TM 接近零开销（无锁进入、无阻塞），高争用时反复 abort 反而比锁更糟。<span class="marginnote">乐观并发与上一课《并发数据结构》里「乐观链表：先遍历后验证」同源——都是「默认没人改，出错重来」。数据库的乐观锁、Git 的冲突合并，也共享这套「验证再提交」的骨架。</span>

## 3 实现的两条路：软件与硬件

**软件事务内存（STM, software TM）**：全部用软件实现。每个事务维护一份**读集（read set）**与**写集（write set）**，提交时按冲突检测协议（如「先锁写集、再验证读集」）决定成败。灵活、无需硬件支持，但每次读写都有簿记开销，常数因子大。

**硬件事务内存（HTM, hardware TM）**：用 CPU 的缓存与缓存一致性协议实现事务。典型如 Intel TSX、Arm TME：事务的读写**天然由缓存行**承载，缓存行被逐出或他核修改即自动 abort。开销小、隔离性强，但有**容量限制**（写集太大、缓存行不够就 abort）与**不可预测性**。<span class="marginnote">现实工程常把两者合体：HTM 快但容量有限，STM 慢但无容量限制——「HTM 优先，容量超了就退回 STM」的混合事务内存（Hybrid TM）兼顾两者。</span>

## 4 经典案例：环形缓冲 + 排他锁

Herlihy §17 用一个具体例子演示「事务如何简化并发设计」：**环形缓冲区**，支持 `enq`/`deq`，用一把排他锁保护，再加**谓词（predicate）**约束「满则等空位、空则等物品」——这正是《信号量与生产者-消费者》用三个信号量手搓的那个问题，只是这次用事务声明式地写：

```c
void enq(item){
    atomic {
        while (count == n) return;      /* 满了就放弃 */
        buf[head] = item;  head = (head+1)%n;  count++;
    }
}
```

**关键对比**：信号量方案要程序员精确编排 P/V 次序，一个顺序错就死锁；事务方案只要声明原子，运行时负责重试与回滚，**「满则等」被降级为「满了就 abort」**——正确性从「人工排布同步」变成「系统兜底重试」。代价是：高争用下 abort 重试的浪费，比信号量阻塞更烧 CPU。<span class="marginnote">这个例子精准地展示了并发编程两种哲学的成本结构：锁是「阻塞换简单」，事务是「重试换简单」。当临界区短、争用低，事务赢；当临界区长、争用高，锁赢——没有银弹，只有权衡。</span>

## 5 无等待事务：把理论之墙推到底

TM 能否做到**无等待**（每个事务有限步内必提交）？这要请回《并发对象与同步原语相对能力》的**共识数**。Herlihy 证明：

> **任何支持无等待事务提交的 TM 系统，必然能用它实现共识；因此它的底层必须拥有无限共识数（如 CAS）。**

**公式解析**中的判定式可以这样写：设 TM 能实现 $n$ 个事务的无等待提交，则它实现了 $n$ 线程共识，于是底层原语的共识数满足

$$
\text{CN}(\text{TM 原语}) \ge n \quad\Rightarrow\quad \text{CN}(\text{TM 原语}) = \infty
$$

- **第一步，读蕴含**：无等待提交 = 每个事务有限步成功 = 一次「所有线程一致选定一个结果」——这正是共识的定义。
- **第二步，看结论**：若某原语只支持有限共识数（如 test-and-set 只有 2），用它实现 TM 就最多支持 2 线程无等待；要做到任意多线程无等待，底层必须有 CAS/LL/SC。
- **第三步，用直觉**：这解释了为什么现实 HTM（Intel TSX）底层就是缓存一致性协议——它间接获得了「无限共识数」般的表达能力，才敢宣称无等待式的事务性。<span class="marginnote">这又是「共识数定能力」的又一次证明：TM 再好，也逃不出原语共识数的天花板。Herlihy 用一条定理，把硬件原语、对象层次、事务内存串成了一条完整的逻辑链。</span>

## 6 辨析｜易错点：事务不是锁的免费替代

**回滚的开销**：abort 后事务的改动要全部撤销，写集越大撤销越贵——「长事务」在 TM 里是毒药。
- **不可见副作用**：事务内不能做 `printf`、发网络、改全局计数器——这些副作用无法回滚，称为「不可事务化」（irreversible）副作用。
- **容量限制**：HTM 写集超缓存行即 abort，无界结构不能直接塞进硬件事务。

**易错点一句话：** 事务适合「短、快、少冲突」的临界区；临界区里藏着 I/O 或不可回滚副作用时，事务要么不能用、要么白给。<span class="marginnote">这也是为什么 TM 至今是「学术 + 硬件特性」多于「全行业默认」：`std::atomic` 的 RMW 复合、数据库的存储过程，各自在合适的地方接管了「原子性」——TM 是这场接力里最新的一棒。</span>

## 7 小结

- 锁的三痛：**难组合、粒度两难、易饿死**；TM 用「声明原子性」把正确性交给运行时。
- **事务**：全成或全败 + 隔离；乐观执行、冲突检测、回滚重试。
- 两条实现路：**STM**（软件簿记读集写集，灵活但常数大）与 **HTM**（缓存行承载，快但有容量上限）。
- 环形缓冲 + 排他锁案例说明：事务把「满则等」降级为「满则 abort」，用重试换简单。
- **无等待事务 ⇒ 底层共识数无穷**：TM 的极限仍由硬件原语决定（Herlihy 定理）。

在下一节，我们俯视整个并发大厦的地基：当线程各写各的、缓存与内存各有缓冲，**你看到的内存到底是哪一份**？「顺序一致」「线性一致」「弱内存序」如何定义——那是《内存一致性与顺序》。
