## 为什么从条件变量开始

信号量能表达「等资源」，但用起来要小心翼翼——`P/V` 的配对全靠程序员自觉，错一次就埋下死锁。霍尔 1974 年提出**管程（monitor）**，把「锁 + 条件变量」封装成语言级结构，Java 的 `synchronized`、C++ 的 `std::condition_variable` 都是它的直系后代。这一课我们先讲条件变量是什么、为什么需要它，再用它啃下并发课程的经典骨头——**读者-写者问题**，最后厘清它与信号量的异同。

## 1 为什么锁不够：等一个「条件」怎么办

考虑一个需要「队列非空才取元素」的程序。用锁只能保证「互斥」，但「队列空」不是锁能表达的状态——你需要**等到队列非空**。朴素方案是忙等：

```c
lock();
while (queue_is_empty()) { unlock(); /* 让出，再抢 */ lock(); }
dequeue();
unlock();
```

这既浪费 CPU（反复抢锁），又可能让同一个线程反复抢到锁而饿死别人。**条件变量（condition variable）**专门解决「等一个条件」：它与一把互斥锁绑定，提供两个操作——`wait` 释放锁并睡眠，直到被 `signal` 唤醒再重新获取锁。<span class="marginnote">`wait` 的神奇之处在于「原子地释放锁 + 睡眠」：它不会让其他线程在你睡眠后还拿不到锁，从而避免「睡眠了但锁还被自己攥着」的死锁。</span>

## 2 管程：锁 + 条件变量的封装

**管程（monitor）**：一种并发抽象，把「数据 + 互斥锁 + 条件变量」打包，所有方法由同一把锁保护，方法内部可以 `wait` / `signal`。经典范式是 **while + wait** 的循环等待：

```c
std::mutex m;  std::condition_variable cv;  std::queue<int> q;

void enqueue(int v){
    { std::lock_guard g(m); q.push(v); }
    cv.notify_one();                 /* 唤醒一个等空位的线程 */
}
int dequeue(){
    std::unique_lock lk(m);
    while (q.empty()) cv.wait(lk);   /* 空则睡，醒来再查 */
    int v = q.front(); q.pop();
    return v;
}
```

三个要点：

**循环而非 if 等待**：被唤醒后条件可能已被别人抢走，必须**重查条件**——`while` 是铁律。
- **`notify` 在释放锁后调用**：避免唤醒一个立刻又要阻塞的线程，减少无谓的上下文切换。
- **锁保护数据结构，条件变量表达条件**：分工明确，这就是管程的全部哲学。<span class="marginnote">霍尔管程用「signal 即转移控制权」，梅萨管程（Mesa）用「signal 只提醒、被唤醒者重新抢锁」。现代语言几乎全是 Mesa 语义——所以必须用 while 重查，这条看似啰嗦的循环实则是正确性的命根子。</span>

## 3 读者-写者问题：两种共享的博弈

**读者-写者问题（readers-writers）**：一块共享数据被两类线程访问——**读者**只读、任意多个读者可同时进入；**写者**独占、读者与写者、写者与写者都互斥。它不再是一把锁能解决的简单互斥，而是「读写两类权限」的博弈，有两大经典变体：

**读者优先（readers-preference）**：只要还有读者在，新读者就能进，写者可能被饿死。
- **写者优先（writers-preference）**：一旦有写者等待，新读者必须排队，避免写者长时间饿死；代价是读者延迟变大。

| 变体 | 读者行为 | 写者行为 | 倾向 |
| --- | --- | --- | --- |
| 读者优先 | 有读者就进 | 等所有读者走光 | 读多写少时吞吐高 |
| 写者优先 | 有写者在等就排队 | 优先处理写者 | 写多读少或写者敏感 |

读者优先的实现用两个计数：`read_count` 记录读者数，一把 `write_mutex` 管写者，一把 `read_mutex` 保护 `read_count` 本身。<span class="marginnote">注意这里的嵌套：读者要「先保护计数再决定是否申请写锁」，顺序搞反或漏锁，就退化成普通的互斥或引入死锁——读者-写者是练习「锁的层级」最好的题目。</span>

## 4 用条件变量写读者优先

以读者优先的读者动作为例：

```c
void read(){                                   void write(){
    unique_lock lk(m);                             unique_lock lk(m);
    while (writers_waiting) cv.wait(lk);           /* 写者优先变体 */ 
    readers++;                                     while (readers > 0)
    lk.unlock();                                   cv_writer.wait(lk);
    /* 读共享数据 */                                /* 独占写 */
    lk.lock();                                     writers_waiting = false;
    readers--;                                     cv_reader.notify_all();
    if (readers == 0) cv_writer.notify_one();      cv_writer.notify_one();
}                                                }
```

**关键：读者把「加读计数」与「读数据」分开**，前者在锁内瞬间完成，后者在锁外进行——这样多个读者才能在锁外并行读取；只有最后一个读者离开时，才唤醒等待的写者。整个程序正确性仍然落在上一课那套「不变量 + 唤醒关系」证明框架里：互斥由锁保证，活性由「最后一个读者必须 notify」保证。<span class="marginnote">现代现实中的读者-写者锁（`pthread_rwlock_t`、Java `ReadWriteLock`）就是这里的工程化产品：读者共享临界区、写者独占，配以公平策略避免两端饥饿。</span>

## 5 辨析｜易错点：条件变量与信号量的区别

条件变量与信号量表面都「等一个东西」，内核完全不同：

**是否有记忆**：信号量带计数器（有记忆），`V` 之后即使没人等，计数也 +1；条件变量**不带记忆**，`notify` 时没人等在等，这次唤醒就**丢失**。因此条件变量必须配「条件」使用（while 重查），信号量不必。
- **是否要锁**：条件变量的 `wait` 必须持有锁才能调用（释放+睡眠要原子）；信号量的 `P/V` 无需预先持锁。
- **适用场景**：信号量擅长「管理资源数量」，条件变量擅长「等待条件成立」——生产者-消费者两者皆可，但用条件变量写的版本更不易错。<span class="marginnote">一句话记牢：<strong>信号量有记忆、条件变量无记忆。</strong> 无记忆的补偿办法就是 while 重查条件——正因为醒来时条件未必成立。</span>

## 6 公式解析：读者-写者的进展保证

读者-写者方案的正确性常写成一组**串行条件**。设 $R$ 为并发读者集合、$W$ 为写者，两个读者可并行的充要条件是：不存在写者同时在场。形式化：

$$
R \cap W = \emptyset, \qquad |W| \le 1 \;\Rightarrow\; \text{并行合法}
$$

- **第一步，读公式**：任何时刻，读者集合与写者集合不相交（不能边读边写）；写者至多一个（不能同时两个写）。
- **第二步，拆解**：$R \cap W = \emptyset$ 就是「读写互斥」的集合表述；$|W| \le 1$ 就是「写写互斥」。两个条件合起来，恰好是读者-写者比「普通互斥」多出来的那部分共享度。
- **第三步，看活性**：公式保证的是安全；活性（写者不会被读者永久饿死）则由「最后一个读者唤醒写者」的 notify 关系承担——所以**读代码时盯着最后一个读者**，就是检查读者优先方案活性最有效的方法。

## 7 小结

- **条件变量**：与锁绑定、提供 `wait`/`notify`，用于「等待条件成立」；**while 重查条件是铁律**。
- **管程**：数据 + 锁 + 条件变量的一体化封装，是 Java/C++ 同步的祖先；现代用 Mesa 语义。
- **读者-写者问题**：读者可并行、写者独占；读者优先/写者优先两变体的取舍在「谁更怕饿」。
- 读者实现把「加计数」与「读数据」拆到锁内外，实现读者并行。
- **辨析**：信号量有记忆、条件变量无记忆；无记忆靠 while 重查补偿。
