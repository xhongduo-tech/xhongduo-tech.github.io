## 为什么从线程开始

你的手机、服务器、GPU 集群都是多核的；大模型的推理要同时喂给几千张卡，单线程显然走不到 AGI。可「同时做很多事」这件事，操作系统的教科书把它从进程讲起，却要在**线程（thread）**这里才真正切开并发的地表。为什么？因为进程这个容器太重了——每次切换都要换整个地址空间；而线程才是「轻量级进程」，是让多个执行流共享同一个地址空间的机制。<span class="marginnote">进程与线程的关系，第二级《操作系统》专题已系统讲过（进程模型、上下文切换、虚拟内存）；本篇从并发视角重讲，重点放在「多个执行流如何交错」上。</span>理解线程如何创建、如何调度、如何共享内存，是后面一切互斥、信号量、并发数据结构的地基。

## 1 从进程到线程：一次「变轻」的改造

一个**进程（process）**是操作系统分配资源的单位：它拥有独立的虚拟地址空间、文件描述符表、信号处理函数。每个进程至少包含一条**执行流（thread of control）**。当进程只含一条执行流时，它就是传统意义上的单线程程序。

多进程并发早已存在，代价却高昂：每次上下文切换都要切换页表、刷新 TLB、把 CPU 流水线拖冷。<span class="marginnote">一次进程上下文切换在现代硬件上要数百纳秒，还要付出缓存与 TLB 失效的隐性开销；线程切换只换寄存器组与栈指针，快一个数量级。</span>而**线程**的概念是：把「执行流」从进程里拆出来单独管理。同一进程内的所有线程：

**共享**同一地址空间、全局变量、打开的文件与信号处理器；
- **各自独立**拥有线程 ID、寄存器集合（含程序计数器 PC）、栈、栈指针。

于是**两个线程读同一个全局变量，看到的是同一块内存**——这既是并发编程的威力所在，也是万恶之源：下一课《共享变量与互斥》的所有故事，都从这「共享」二字开始。

把进程与线程放进一张表，差异一目了然：

| 维度 | 进程 | 线程 |
| --- | --- | --- |
| 资源粒度 | 独立虚拟地址空间、独立页表 | 共享进程的地址空间与页表 |
| 切换成本 | 换页表 + 刷新 TLB，数百纳秒起步 | 只换寄存器组与栈指针，快一个数量级 |
| 通信方式 | 管道 / 消息队列 / 显式共享内存 | 直接读写共享变量，零拷贝 |
| 故障隔离 | 一个进程崩溃不影响别的进程 | 一个线程写坏内存可能拖垮整个进程 |
| 调度单位 | 以进程为容器、线程为执行单元 | 真正的调度对象是线程 |

这张表回答了「为什么要线程」：进程给的是**隔离**，线程给的是**共享与轻量**。两者不是替代关系，而是互补——服务器通常一个进程内开几十条线程，用进程隔离不同服务、用线程并行同一服务。

## 2 逻辑流与并发

用 CS:APP 的语言，每条线程在执行时会产生一条**逻辑流（logical flow）**——程序计数器 PC 所取值的序列。**并发（concurrency）**指多条逻辑流的执行在时间上重叠。这个定义有两个层次：

- 在单核上，多条逻辑流**交错（interleaved）**执行：操作系统用时间片让它们分时占有 CPU，宏观上「同时」，微观上轮流。
- 在多核上，各逻辑流可以真正**并行（parallel）**执行：同一时刻有多条流在跑。

**并发与并行是两个不同的概念：并发是「结构」，并行是「执行」**——一个程序可以写成并发结构，但在单核上并不会真正并行。今天几乎所有教科书都会强调这一区分，因为它决定了你思考问题的方式：并发问题（交错导致的竞态）在单核上同样存在，而并行问题（如何分摊负载）只在多核上出现。

## 3 线程的 API：创建、等待与终止

POSIX 线程（pthread）是 Unix 世界的事实标准，CS:APP 用它来承载全部并发案例。三个核心操作：

```c
pthread_create(&tid, NULL, thread_fn, &arg);   /* 创建线程，入口为 thread_fn */
pthread_join(tid, &retval);                     /* 等待线程终止，回收结果 */
pthread_exit(NULL);                             /* 终止当前线程 */
```

`pthread_create` 返回后，新线程与主线程**并发**地开始执行 `thread_fn`，参数 `arg` 以 `void*` 传入，返回值同样以 `void*` 传出。<span class="marginnote">线程模型的真谛：`thread_fn` 就是一个「独立的 main」，它有自己的栈与参数，却与兄弟线程共享全局堆。后续所有并发程序的形态，都是「若干这样的函数在共享内存上跳舞」。</span>

主线程在 `main` 返回时若仍有存活线程，进程会直接终止——所以主线程通常要 `pthread_join` 等齐所有线程再退出。这也暗示了并发程序的一个基本纪律：**先想清楚谁等待谁、谁向谁汇报，再写代码。**

### 一个完整的 spawn-and-join 例子

把三件套拼在一起，就得到并发程序的「最小骨架」——创建、并行、join 收尾：

```c
#define NUM 8
void *worker(void *arg){
    long id = (long)arg;
    printf("worker %ld starts\n", id);
    return (void *)(id * id);          /* 用返回值回报结果 */
}
int main(void){
    pthread_t tids[NUM];
    for (long i = 0; i < NUM; i++)
        pthread_create(&tids[i], NULL, worker, (void *)i);
    for (int i = 0; i < NUM; i++) {
        void *ret;
        pthread_join(tids[i], &ret);   /* 等齐每一个线程 */
        printf("joined %d, ret = %ld\n", i, (long)ret);
    }
    return 0;
}
```

注意两个细节。第一，参数用 `(void *)i` 把整数塞进 `void*`、返回时再解出来——`void*` 是线程间传递任意数据的「通用信封」，但也意味着编译器不再帮你检查类型，写错类型只能靠纪律。第二，`pthread_join` 不只等线程结束，还能取走它返回的指针；主线程把 `return 0` 放在所有 join 之后，就是为了保证「先收齐、再退场」。

## 4 并发执行的三类代价

并发带来吞吐，也带来三类必须正视的代价：

**上下文切换的开销**。即使并发写得很对，切换本身也花钱：保存/恢复寄存器、调度器运行、缓存失效。线程数不是越多越好——这引出「并发度等于核心数」的朴素直觉，在《并行算法与工作窃取》一篇中会量化成 work/span 模型。

**共享变量的竞态**。两个线程同时执行 `x = x + 1`，因为这条语句在机器层面是「读-改-写」三步，交错后可能丢失一次更新。这是下一课的主角，这里先立住一个词：**竞态（race condition）**，即程序的输出依赖于线程执行的不可控交错。

**正确性难以验证**。交错的数量随线程数指数增长，测试几乎不可能穷尽——所以并发正确性要靠「不变量 + 证明」来保证，这正是 Herlihy 教材反复强调的思想。

## 5 公式解析：并发能换来多少加速

「开多少线程才值得？」最经典的量化工具是**阿姆达尔定律（Amdahl's Law）**。设程序可并行部分占比为 $p$（$0<p<1$），用 $n$ 个核心执行，加速比为：

$$
S(n) = \frac{T_1}{T_n} = \frac{1}{(1-p) + \frac{p}{n}}
$$

拆解这条公式：

- **$T_1$**：单核上的执行时间；**$T_n$**：$n$ 核上的执行时间。
- **$(1-p)$**：不可并行部分的占比，无论多少核都必须串行，它设定了加速比的天花板。
- **$\frac{p}{n}$**：可并行部分被 $n$ 核均摊后的理想耗时——这里隐含「负载完全均匀」的乐观假设。
- 当 $n \to \infty$ 时，$S(n) \to \frac{1}{1-p}$：**即使 90% 的代码可并行，最大加速也只有 10 倍**。这就是「并发不是万能药」的数学证据。

再举一个具体数字：$p = 0.95$，$n = 16$，则 $S(16) = 1/(0.05 + 0.95/16) = 1/(0.05 + 0.0594) \approx 9.1$。16 个核心只换来 9.1 倍——那 5% 的串行部分把所有核心都拖成了看客。<span class="marginnote">阿姆达尔定律是并发课程的「第一句坏消息」，它告诉你：先找可并行度，再谈并行；优化串行部分的收益，往往大于继续堆核。</span>

再看一张「核数换加速比」的速查表（取 $p = 0.9$），感受增长曲线的平坦化：

| 核心数 $n$ | $S(n)$ | 相比 $n$ 的差距 |
| --- | --- | --- |
| 2 | 1.82 | 已不到 2 |
| 4 | 3.08 | 明显小于 4 |
| 8 | 4.71 | 连 6 都不到 |
| 16 | 6.40 | 16 核只换来 6.4 倍 |
| 64 | 8.94 | 逼近天花板 $1/(1-p)=10$ |

纵轴被 10 封顶，横轴再堆核也只是贴着天花板爬——这就是阿姆达尔定律让人「越并行越泄气」的原因。它还顺带解释了工程界的惯例：把串行部分优化到极致（比如缩短临界区、减少 I/O 等待），往往比买更贵的多核机器划算。

### 术语速查

| 术语 | 一句话定义 |
| --- | --- |
| 逻辑流 | 一条执行流中 PC 取值的序列 |
| 并发 | 多条逻辑流的执行在时间上重叠（结构属性） |
| 并行 | 多核上同一时刻多条流真正同时执行 |
| 线程 | 进程内的独立执行流，共享地址空间、各有独立栈 |
| 竞态 | 结果依赖不可控交错、输出不可预测 |
| 阿姆达尔定律 | $S(n)=1/((1-p)+p/n)$，串行部分设定了加速比天花板 |

## 6 小结

- **线程**是进程内的轻量级执行流，共享地址空间、各有独立栈与寄存器。
- **并发**是逻辑流时间重叠的结构属性，**并行**是多核上的同时执行——二者不同。
- pthread 三件套：`create` / `join` / `exit`，主线程负责收尾。
- 并发三大代价：切换开销、竞态、正确性难验证。
- **阿姆达尔定律** $S(n) = 1/((1-p)+p/n)$ 量化了串行部分对加速比的天花板效应。
