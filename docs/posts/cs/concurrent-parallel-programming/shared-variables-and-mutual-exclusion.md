## 为什么从共享变量开始

上一课我们说线程共享同一地址空间——这是并发的威力。可威力从不免费：当两个线程对同一个变量执行「读-改-写」，结果就不再确定。CS:APP 用一句很准的话点题：**并发程序的主要 bug 来自「读-改-写」操作被错误地拆分**。这一课我们把问题讲透：什么是共享变量、什么是竞态、什么是临界区，以及互斥如何把它焊死。这三件事是理解信号量、锁、CAS 之前必须扫清的雷。

## 1 共享变量的定义：先问「谁在引用它」

**共享变量（shared variable）**：如果一个变量被多线程引用，且其中至少一个线程是写，那么这个变量就是共享变量。<span class="marginnote">注意「至少一个写」这个限定：多线程只读一个变量不会产生竞态，反而是安全的、可以放心共享的。</span>

但「共享」不是物理属性，而是**引用关系**的产物。C 里区分的关键是内存中实体的概念：全局变量、堆中对象天然可被多线程引用；而**栈变量不属于线程共享范围**——因为每个线程有自己的栈。可如果某个线程把局部变量的**地址**传给了另一个线程，局部变量就摇身一变成为共享变量：

```c
int *ptr;                 /* 全局指针 */
void *t2_main(void *arg){ printf("%d\n", *ptr); }   /* 读共享对象 */
int main(){
    int local = 42;       /* main 的栈变量 */
    ptr = &local;         /* 把地址"泄漏"给别的线程 */
    pthread_create(&tid, NULL, t2_main, NULL);
}
```

CS:APP 由此给出判断方法：**变量是否共享，取决于多个线程是否以「至少一个写」的方式引用它**，而不是它定义在全局还是栈上。这是本课第一个易错点，也是很多「明明声明了局部变量却崩了」bug 的根因。

## 2 竞态：输出取决于交错

**竞态（race condition）**：程序的最终结果依赖于多条执行流交错的具体次序，因而不可预测。

以计数器为例。设共享变量 `cnt` 初始为 0，两个线程各自循环执行 $N$ 次 `cnt++`。直觉上最终 $cnt = 2N$，实际却常常小于 $2N$。原因在于 `cnt++` 在机器指令层面不是一步，而是三步：

$$t \leftarrow \text{读 } cnt;\qquad t \leftarrow t + 1;\qquad cnt \leftarrow \text{写 } t$$

两个线程各执行一次 `cnt++`，如果交错成「读A、读B、写A、写B」，则两次更新都从同一个旧值 0 出发，最终只写成 1——**一次更新被吞掉了**。<span class="marginnote">这就是「丢失更新（lost update）」：三步操作被另一线程的同类操作从中劈开。它不是一个理论玩具——银行转账、秒杀库存、日志水位线，全都栽在这种三步拆分上。</span>

## 3 临界区与互斥：把原子性焊回来

解决办法不是把「读-改-写」真的变成机器级单指令（这交给硬件），而是约定**任何线程在对共享状态做一组操作时，其他线程不得中途插入**。由此引出两个概念：

**临界区（critical section）**：访问共享变量的一段代码，一次只允许一个线程进入执行。
**互斥（mutual exclusion）**：保证同一时刻至多一个线程位于临界区的机制。

互斥是正确性的**安全性质（safety）**：它管的是「坏交错不发生」。但只有安全还不够——若线程 A 进了临界区再不出来，B 永远等死。所以互斥方案还必须满足两条**活性（liveness）**要求：

| 性质 | 含义 | 违反时的症状 |
| --- | --- | --- |
| **互斥** | 至多一个线程在临界区 | 数据损坏、结果错误 |
| **无死锁** | 若线程要进临界区，它迟早能进 | 程序挂起不动 |
| **无饥饿** | 每个申请者最终都能进入 | 个别线程永远等不到 |
| **无忙等** | 进程可在临界区外让出 CPU | CPU 空转、功耗上升 |

**辨析｜易错点：** 互斥只解决「不被打断」，不解决「谁先进」。两个线程同时申请，顺序仍不确定——但这次顺序只影响输出先后，不影响正确性。<span class="marginnote">安全性质（互斥）与活性性质（不死锁、不饥饿）是并发证明的两根支柱，Herlihy 全书几乎每一章都在对这两根支柱做花样翻新的考验。</span>

## 4 一条朴素但错误的互斥尝试

为了说明问题为何棘手，试试最直观的做法：用一个共享标志位 `flag` 表示「有人在使用」，进入前轮询它：

```c
while (flag) ;      /* 忙等：flag==1 就一直转 */
flag = 1;           /* 声称占用 */
/* …… 临界区 …… */
flag = 0;           /* 释放 */
```

这里 `while(flag)` 与 `flag = 1` 是两条独立指令。线程 A 刚判断完 `flag == 0`，还没写入 1 时，线程 B 也判断到 `flag == 0`——两个人都认为「没人用」，同时闯入临界区。**加锁操作自身也面临同样的读-改-写竞态**，这就是「自旋锁初版必挂」的原因，也预告了为什么互斥最终要靠硬件原语（`test-and-set`、`CAS`）来落地。这个问题在《锁的实现与 CAS》一课正面解决。

## 5 公式解析：多线程计数丢失更新量

丢失更新不是玄学，可以量化。设 $N$ 个线程各自对共享计数器做 $K$ 次 `cnt++`，每次 `cnt++` 的读-改-写是原子的、可交错。当所有交错等概率时，期望的最终计数值与理想值 $NK$ 之差，体现了竞态的「确定性」：

$$
E[C] = K + (N-1) \cdot \frac{K(K+1)}{2} \quad\text{当 } K \ll N \text{ 时的近似}
$$

这条式子不必背，值得拆解的是它背后的两件事：

- **第一步，理解模型**：每次 `cnt++` 从旧值读到新值写，若某线程的读发生在另一次更新的写之后，它读到新值；若发生在写之前，就把它覆盖。
- **第二步，理解直觉**：当 $K$ 很小而 $N$ 很大时，更新大量「撞车」，期望计数值远小于 $NK$——丢失更新不是少数事件，而是**统计必然**。
- **第三步，理解对策**：任何「用正确结果减去期望损失」的补救都是脆弱的；唯一稳的出路是让整个 `cnt++` 落入互斥保护，这正是下一课信号量与之后锁的使命。

## 6 小结

- **共享变量**：被多线程以「至少一个写」的方式引用；栈变量被传址后也算共享。
- **竞态**：结果依赖不可控交错；`cnt++` 的「读-改-写」三步拆分是竞态的典型温床。
- **临界区 + 互斥**：安全性质；互斥之上还要**无死锁、无饥饿**等活性性质。
- **加锁动作自身也会竞态**：朴素的 `while(flag); flag=1` 必挂，需要硬件原子原语来落地。
- 丢失更新可量化，且在小写大读的场景下接近必然——**必须靠同步机制根除，而非靠概率碰运气**。

在下一节，我们用代克斯特拉发明的最优雅同步工具——**信号量**，把互斥与「让出 CPU」统一起来，并用它实现经典的**生产者-消费者**问题。
