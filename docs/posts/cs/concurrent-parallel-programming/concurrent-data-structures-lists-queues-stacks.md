## 为什么从并发数据结构开始

理论已经齐了：锁、CAS、共识数、无等待/无锁的保证层次。这一课让理论落地成**能跑的代码**——链表、队列、栈，三种最基础的数据结构，在并发世界里各有一套从「加锁」到「无锁」的进化史。我们以链表为主线（它是 Herlihy §9 的核心），从最简单的「一把大锁」走到 Harris 的无锁链表，再纵览 Michael-Scott 队列与 Treiber 栈，最后点出每个无锁方案都要面对的共同敌人——**ABA 问题**。

## 1 从大锁到细粒度锁：链表的三种加锁策略

并发链表的第一版最简单：一把全局锁包住所有操作。正确、好写，但**瓶颈**——所有线程串行化，等于没用并发。于是有了三种递进的加锁策略：

- **粗粒度锁（coarse-grained）**：整个链表一把锁。简单但不可扩展。
- **细粒度锁（fine-grained / hand-over-hand）**：每个节点一把锁。遍历时「手握手」地加锁：锁住 $A$ 和 $B$，改完再前移。并发度提高，但要小心两处死锁：**加锁顺序必须一致**、**不能锁住自己正在释放的节点**。
- **乐观锁（optimistic）**：先不加锁地遍历，找到目标后再验证「走过的路径没变」，验证通过才加锁修改；验证失败就重试。<span class="marginnote">乐观策略的思想是「低争用时不设防」：大部分时候没人改动，先做再说，出错重来。这与数据库的乐观并发控制、以及 Git 的「先改后合并冲突」同源。</span>

细粒度与乐观策略的正确性论证（Herlihy 用「可达性引理」）说明一个普适原则：**并发数据结构的难点不在写代码，而在证明代码在所有交错下都正确。**

## 2 懒删除（lazy deletion）：把删除拆成两步

删除是并发链表的难点：你没法「瞬时」把节点从链表里摘掉，中间态可能让别的线程看到断裂。**懒删除**给出经典解法——把「删除」拆成两步：

1. **逻辑删除（logical removal）**：把节点的 `marked` 标志置真。这之后该节点对查询「不可见」，但仍链在表上。
2. **物理删除（physical removal）**：真正把节点从链表中摘除。

读者检查 `marked`，一旦发现被标记就视为已删除。这样查询可以与删除并发进行，删除操作自身只需要锁住相邻两节点。懒删除引出一个更优美的推论：**如果连「标记」都用 CAS 做、连锁都去掉，就得到无锁链表。**

## 3 Harris 的无锁链表：两步 CAS 的艺术

**Harris 链表**（Tim Harris, 2001）只用一个 CAS 就能让链表「无锁」——诀窍在于让每个删除操作先用 CAS 打上「逻辑删除」标记，再物理摘除：

**插入 D 到 A、B 之间**：先 `CAS(D.next, B, D)` 把 D 接到 B 前，再 `CAS(A.next, B, D)` 让 A 指向 D。
- **删除 B**：先用 CAS 把 B 的 `marked` 置真（逻辑删除），再用 CAS 把 A 的 next 从 B 改到 B.next（物理删除）。

![Harris 无锁链表的插入操作](/images/concurrent-parallel-programming/concurrent-data-structures-lists-1.svg)

为什么两步 CAS 就安全？因为**任何时刻至多一个线程能成功执行「A.next 由 B 改为 D」的 CAS**，失败的线程重试即可；而查询只读不写，天然安全。<span class="marginnote">Harris 链表是「无锁数据结构」的开山作品之一：它证明用 CAS 就能构建支持无锁并发增删查的链表。之后的跳表、哈希表无锁实现都以它为技术底座，我们在《并发哈希表与跳表》还会用同一套思想。</span>

## 4 队列与栈：无锁家族的另两位

**Michael-Scott 队列（MS-queue, 1996）**：用哨兵头尾节点，入队 `enq` 用 CAS 把新节点链到尾部，出队 `deq` 用 CAS 推进头指针。它是 Java `ConcurrentLinkedQueue` 的祖本。<span class="marginnote">MS-queue 的关键技巧是「尾指针可能落后于真实尾部」，因此 enq 之前要先把尾指针 CAS 到正确位置——用一次「修复」的 CAS 换整个结构的无锁。</span>
- **Treiber 栈（Treiber, 1986）**：无锁栈用一个 `top` 指针 + 一个 CAS：`pop` 时 `CAS(top, old, old->next)`，失败重试。它是所有无锁栈的原型。

这两个结构的共同模式呼之欲出：**所有变更都归结为对「入口指针」的单个 CAS + 失败重试。** 栈只有一个入口（top），所以最简单；队列有两个入口（head/tail），所以要多一份「修尾」的功夫。

## 5 公式解析：无锁操作的正确性——线性化点

无锁数据结构正确性的标准证明工具是**线性化（linearizability）**：每个并发方法调用，都存在一个「时刻点」（**线性化点**），使得按这些点排序后的执行结果等价于某个顺序执行。

$$
\text{每个操作} \xrightarrow{\text{取其 CAS 成功的那一瞬间}} \text{该瞬间即线性化点}
$$

- **第一步，找点**：对 Harris 插入而言，线性化点是 `CAS(A.next, B, D)` **成功**的那一刻；对 Treiber 的 pop，是 `CAS(top, old, old->next)` 成功的那一刻。
- **第二步，验证等价**：因为 CAS 成功是**全有或全无**的（要么换要么不动），把每个成功时刻当成「该操作发生」，得到的顺序一定对应某个合法顺序执行。
- **第三步，落到代码**：写无锁结构时，先问自己「每个操作的线性化点是哪一次 CAS」；答不出来，说明设计还没成型。<span class="marginnote">线性化不止是无锁结构的工具——上一课《并发对象与同步原语相对能力》里的 wait-free/lock-free 层次，正是基于「是否存在线性化点」来定义的。它是贯穿 Herlihy 全书的正确性语法。</span>

## 6 辨析｜易错点：ABA 问题为何专盯无锁

用 CAS 重试，撞上 **ABA 问题**：A 读取 `top = T`，另一个线程把 `T` 弹出、压入新节点、又压回 `T`，`top` 还是 `T`。A 的 `CAS(top, T, ...)` 以为「没人动过」而成功——可链表结构已被别人改过，A 引用的 `T->next` 可能早已失效。

**核心：CAS 只能发现「值变了」，发现不了「变过又变回来」。** 对策三条：加**版本号**（C++ `std::atomic` 用双字比较）、改用 **LL/SC**（Arm 上检测地址变化）、或避免复用被 CAS 引用的节点内存（把旧节点留给 GC）。<span class="marginnote">ABA 是面试与实战里的「老熟人」：Java 的 `AtomicStampedReference` 就是为了给引用打上版本戳。写无锁算法时，把「谁可能复用被引用对象」列进检查清单，能避免绝大多数隐性损坏。</span>

## 7 小结

- 并发链表从**粗粒度锁 → 细粒度锁（hand-over-hand）→ 乐观锁** 逐级提升并发度，也逐级提高证明难度。
- **懒删除**把删除拆成「逻辑标记 + 物理摘除」两步，为无锁化铺路。
- **Harris 链表**用两次 CAS（插入）/ 两次 CAS（删除）实现无锁增删查；**MS-queue** 与 **Treiber 栈**是队列与栈的无锁原型。
- 正确性用**线性化点**证明：每次操作取其 CAS 成功瞬间为发生时刻。
- **ABA 问题**是无锁的头号敌人：CAS 发现不了「变过又变回来」，需版本号 / LL/SC / GC 兜底。

在下一节，我们把无锁思想扩展到**更宽的键值结构**：用「条纹锁」给哈希表的桶加细粒度保护，再用跳表的概率分层让无锁并发成为可能——那是《并发哈希表与跳表》。
