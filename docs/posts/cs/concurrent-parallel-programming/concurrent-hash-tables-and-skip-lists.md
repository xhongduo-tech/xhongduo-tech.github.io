## 为什么从哈希表与跳表开始

上一课的无锁链表是「窄」结构——只有一个入口、一条链。真实世界的并发容器要支持按键查找，于是需要两种「宽」结构：**哈希表**（桶 + 键哈希）与**跳表**（有序 + 概率分层）。Herlihy §11–§12 教我们两件事：如何给哈希表做**条纹锁**（striped lock）让它可扩展；如何用上一课的**无锁链表技术**直接构建无锁跳表，从而同时获得查找、删除与排序。这一课我们把「桶」「层」「概率」三个词彻底讲清。

## 1 并发哈希表：桶多了，锁怎么办

哈希表的基本形态：一个**桶数组**，键经哈希函数 $h$ 映射到下标，桶内用链表挂冲突键。并发的难点在于**读写同一个桶**。方案分三档：

- **一把大锁**：整个表一把锁，查找、插入全串行——正确但不可扩展。
- **每桶一锁**：每个桶一把锁。并发度大幅提升，但桶数量固定，表增长时要重新哈希，锁要随桶迁移，实现复杂。
- **条纹锁（striped lock）**：维护 $L$ 把锁（$L$ 远小于桶数），把 $\text{桶 } i$ 的锁定为 $\text{锁 } (i \bmod L)$。锁比桶少，内存省、初始化快，且重哈希时只需锁住「正在搬动的桶」。

**辨析｜易错点：** 条纹锁的代价是**假共享**——两个不同桶映射到同一把锁，本可并行却被串行化。$L$ 取多少是工程权衡：$L$ 太大浪费、太小争用；实践中常取 $L \approx \text{核心数} \times 4$ 左右。<span class="marginnote">条纹锁的「哈希到锁」思想无处不在：数据库的行级锁、Redis 的槽位锁、GPU 的 bank 分配，都是「把 N 个资源映射到 M 把锁」这一模式的不同化身。</span>

用一个具体数字感受条纹锁的取舍。设桶数 1024、锁数 64，则第 $i$ 个桶受锁 $(i \bmod 64)$ 保护，每把锁平均管辖 16 个桶。两个**不同**桶映射到同一把锁的概率约为 $1/64$，比「一把大锁」的确定性串行低两个数量级；若把锁数提到 1024（等于每桶一锁），内存翻倍、冲突却只降一点点——「锁比桶少一个量级」通常就是最划算的工作点。

四种方案用一张表收束：

| 方案 | 并发度 | 重哈希难度 | 适用场景 |
| --- | --- | --- | --- |
| 一把大锁 | 极低 | 简单 | 只读为主、规模小 |
| 每桶一锁 | 高 | 锁要随桶迁移 | 写多、规模稳定 |
| 条纹锁 | 较高 | 只需锁住搬动中的桶 | 规模大、动态扩容 |
| 无锁 | 最高 | CAS 逐桶迁移 | 高吞吐核心路径 |

## 2 无锁哈希表：桶本身就是一条无锁链表

真正的无锁哈希表（**lock-free hash set**）把上一课的 **Harris 无锁链表**直接当作每个桶的结构——桶数组的每个槽就是一条无锁链表。于是：

**查找**：哈希到桶，沿无锁链表走，全程只读，天然安全。
- **插入**：在对应桶的链表上做 CAS 插入。
- **删除**：在链表的 marked 标记删除。
- **重哈希**：表满时把桶数组翻倍，逐个桶把元素「搬」进新桶——搬桶用 CAS 保证原子迁移。

关键洞察：**一旦桶内是 Harris 链表，整个哈希表就继承了无锁性。** 而桶数组的翻倍扩容用「迁移指针」把新老桶相连，避免「老桶没搬完、新查找却找不到」的窗口。无锁哈希表因此兼具查找 O(1) 期望、插入无锁、且支持动态扩容——这就是 Java `ConcurrentHashMap` 的高层蓝图。

无锁扩容的「迁移窗口」值得多说一句：扩容时新老桶数组并存，查找要先看新桶、查不到再回退老桶，只有迁移完成才回收老桶。这个「双数组 + 回退查询」的模式，把「扩容与查询并发」变成安全的渐进式迁移——`ConcurrentHashMap` 的扩容正是这一思路的工程化。

负载因子（load factor）决定伸缩时机：当平均桶长超过阈值（如 0.75），就触发重哈希把桶数组翻倍。并发场景由此引出一个连锁问题——翻倍过程中每个桶都要锁或 CAS 迁移，表越大、重哈希越贵；所以工程上要么「扩容分批做」（渐进式），要么「一开始给足桶数」，把重哈希推迟到几乎不发生。

## 3 跳表：用概率把「有序」变便宜

跳表（skip list）解决一个老大难：**既要有序查找 O(log n)，又要支持并发插入删除**。平衡树（AVL/红黑）要旋转，旋转在并发下非常难做；跳表则靠**概率**达到同样的平均高度。

**跳表**：对有序链表增加若干层「快速通道」。每个新节点以概率 $p$（通常 $p = \frac{1}{2}$）提升到上一层。查找从最高层开始，沿着「尽量向右、不行就下降」的规则走到目标。直觉：高层节点少、跳得远，低层节点多、精确定位。

- **期望高度**：$E[\text{height}] = O(\log_{1/p} n)$。
- **期望查找代价**：$O(\log n)$，与平衡树同阶，但**没有旋转**。
- **插入**：先找位置，再按随机层数把节点挂到各层——纯指针操作，天然适配 CAS。<span class="marginnote">跳表由普格 1990 年发明，是「用随机化换简单」的教科书案例：期望复杂度与平衡树相当，却免去旋转与再平衡的代码复杂度。Redis 的有序集合 zset、LevelDB 的内存表，都用跳表。</span>

### 用一组具体数字把「跳」走一遍

设有序链表存 `{3, 7, 12, 19, 25, 31, 40}`，查找 25：

- **第 2 层（假设只有 3 与 31）**：从 3 出发，31 大于 25，向右失败，下降到第 1 层；
- **第 1 层（有 3、7、12、25、31）**：从 3 向右，依次 7、12、25——命中；
- **对比普通链表**：要从 3 一路数到第 5 个才能找到 25；跳表借助高层「跳过 7、12」，比较次数从 5 降到 2。

这就是「高层快速逼近、低层精确定位」的分层直觉：每次「向右失败就下降」一步，期望只走 $O(\log n)$ 步。

## 4 无锁跳表：把每层当一条无锁链表

Herlihy 的无锁跳表把跳表解剖成**一组有序链表的栈**——每一层是一条有序链表，上层是下层的「快速通道」。然后套用上一课的全部武器：

每层的查找用 Harris 无锁链表的方式遍历；
- 插入先加最高层，再用 CAS 逐层往下加（**先高层后低层**的顺序保证可见性）；
- 删除同样用 marked 标记 + 物理摘除，且要**自顶向下**逐层清理。

**核心要点：** 无锁跳表把「无锁链表」复用为构件，把「多层的复杂」降维成「每层都是同一套动作」。这正说明上一课的 Harris 链表不是终点，而是构件。<span class="marginnote">Java 的 `ConcurrentSkipListMap` 就是这种思想的工业成品：既有序、又无锁、还能区间查询，是并发容器的全能选手。</span>

## 5 公式解析：跳表的期望高度

跳表的高度为何是 $O(\log n)$？设节点以概率 $p$ 升层，第 $k$ 层有节点当且仅当该节点连续升层 $k$ 次。对 $n$ 个节点，第 $k$ 层节点数的期望为

$$
E[N_k] = n \cdot p^{k}
$$

- **第一步，理解模型**：每个节点到达第 $k$ 层需要 $k$ 次「掷币成功」，概率 $p^k$；期望节点数就是 $n \times p^k$。
- **第二步，求最高层**：当 $n p^k < 1$ 时，该层平均不足一个节点——于是最高层出现在 $k \approx \log_{1/p} n$，即**高度随 $\log n$ 增长**。
- **第三步，看代价**：查找时每层至多横向走 $O(1/p)$ 步（几何分布的期望），所以总查找代价 $O\left(\frac{1}{p}\log_{1/p} n\right)$；取 $p=\frac12$ 即 $O(\log n)$。<span class="marginnote">这个推导是「随机化算法期望分析」的样板：先定几何模型，再求期望数量，最后导出高度——它也是后头《并行算法》里概率分析的前奏。</span>

再套一组数验证：取 $p = \frac12$、$n = 16$，则 $E[N_k] = 16 \times (1/2)^k$。第 4 层的期望节点数是 $16 \times (1/2)^4 = 1$，即顶层平均只有一个节点；$\log_2 16 = 4$，恰好对应「4 层以上基本没有节点」——高度随 $\log_2 n$ 增长的结论被数字直接印证。若把 $n$ 翻到 1 万，顶层在 $k \approx \log_2 10000 \approx 13$ 附近消失，查找代价仍是十几步量级，与平衡树打平。

### 术语速查

| 术语 | 一句话定义 |
| --- | --- |
| 桶数组 | 哈希表主体，键经哈希函数映射到桶下标 |
| 条纹锁 | 用 $i \bmod L$ 把桶映射到 $L$ 把锁 |
| 假共享 | 不同桶映射到同一把锁，本可并行却被串行化 |
| 无锁哈希表 | 桶数组 + 每桶一条 Harris 无锁链表 |
| 负载因子 | 平均桶长阈值，越过即触发重哈希 |
| 跳表 | 概率分层的有序链表，期望查找 O(log n) |
| 期望高度 | $E[N_k] = n p^k$，顶层平均节点数随对数增长 |

## 6 小结

- 并发哈希表三档：**大锁 → 每桶一锁 → 条纹锁**；条纹锁用 $i \bmod L$ 映射桶到锁，代价是假共享。
- **无锁哈希表** = 桶数组 + 每桶一条 Harris 无锁链表；扩容用 CAS 逐桶迁移。
- **跳表**用概率分层达到 $O(\log n)$ 查找，免去平衡树旋转，天然适配无锁。
- **无锁跳表** = 一叠无锁有序链表，插入先高层后低层、删除自顶向下标记清理。
- 跳表期望高度 $E[N_k] = n p^k$，导出高度与查找代价均为 $O(\log n)$。

在下一节，我们从「单个容器」转向「多线程之间的依赖」：当若干线程各自持锁又互相等待，就可能集体停摆——那就是《死锁检测与预防》，死锁的四个必要条件与两条经典对策将正面登场。
