# 内存一致性与顺序

## 为什么从内存一致性开始

全专题的最后一课，回到一切的地基：**多核看到的共享内存，到底是一致的吗？** 硬件为了性能给每个核配了缓存与写缓冲，于是「写一个变量」到「别人读到」之间隔着一整套缓存一致性协议与指令重排。程序员若不知道这些规矩，就会写出「明明加了锁还出错」的离奇 bug。Herlihy §3 与 CS:APP §12 交汇于此：**顺序一致（sequential consistency）、线性一致（linearizability）、缓存一致性（coherence）、以及 C/C++ 内存序（memory order）**——这一课把这些概念捋成一条从「理想」到「现实」的谱系。

## 1 直觉的破灭：你以为的「马上可见」并不存在

考虑这个被反复引用的场景：线程 A 先写 `x=1` 再写 `y=1`，线程 B 循环等 `y==1` 后读 `x`。直觉上 B 一定读到 `x==1`？**不一定。** 原因有二：

- **编译器重排**：在不破坏单线程语义的前提下，编译器可以把 `y=1` 挪到 `x=1` 之前。
- **硬件重排与写缓冲**：CPU 的写缓冲（store buffer）让写操作先落本地、再异步刷到内存——顺序在别的核看来可能颠倒。

于是「看似等 `y` 再读 `x`」的程序，可能在真机上是「`x` 还是旧值」。这不是 bug，而是**内存模型**没有承诺你「写后读」跨线程有序。<span class="marginnote">这类 bug 极难复现（依赖时序、优化级别、CPU 型号），是并发程序里「幽灵 bug」的主要来源。理解内存模型，是给这类 bug 装 X 光机的唯一办法。</span>

把上面的场景写成可跑的具体形态——两个共享变量 `x`、`y` 初始为 0：

```c
/* 线程 A */                        /* 线程 B */
x = 1;                             while (y == 0) ;   /* 自旋等 y 变 1 */
y = 1;                             print(x);          /* 看到的一定是 1 吗？ */
```

| 内存模型 | `print(x)` 的可能值 |
| --- | --- |
| 顺序一致 / `seq_cst` | 必然是 1 |
| x86 TSO | 可能打印 0（`x=1` 还滞留在 A 的写缓冲） |
| 弱模型（Arm / `relaxed`） | 可能打印 0，且 A 内两条写的顺序也可颠倒 |

**为什么「等到 `y==1`」还不够**：A 的两条写在写缓冲里是异步刷出的，B 看见 `y=1` 时，`x=1` 可能还没到达内存——「等到标志位」只能保证「标志位已刷出」，保证不了「标志位之前写的数据也已刷出」。这正是后面 `acquire`/`release` 存在的理由。

## 2 顺序一致性：先想清楚「理想世界」

在讨论现实之前，兰波特 1979 年定义了理想模型——**顺序一致性（sequential consistency）**：

> 多线程程序的执行结果，等价于把所有操作按**某一个全局顺序**逐一执行的结果；且该顺序与每个线程自身的程序顺序一致。

形式化：存在一个全局排列 $\pi$，使得

$$
\text{所有操作按 } \pi \text{ 执行} \quad\land\quad \forall \text{线程 } T:\ \pi \text{ 保持 } T \text{ 内的程序序}
$$

- **第一步，读第一项**：存在一条「全场排序」，所有线程的操作都能排进这条线——多核执行被还原成一个「单核顺序执行」。
- **第二步，读第二项**：这条线不得颠倒任何线程内部的先后（程序序保持）。两条合起来：**「全局一致 + 局部有序」**。
- **第三步，做判断**：顺序一致性是正确性基准，但**对性能太奢侈**——它要求所有写立即全局可见，等于废掉写缓冲与大部分重排，所以真实硬件不保证它。<span class="marginnote">兰波特给出这个定义时就把「顺序一致」当作语义契约而非性能目标：程序员按它推理程序，系统只需保证「存在一个合法重排」——之后的一切模型，都是「放松到什么程度」的谱系。</span>

## 3 线性一致 vs 顺序一致 vs 缓存一致：别混为一谈

三个高频术语必须分清：

| 概念 | 保证 | 关注对象 |
| --- | --- | --- |
| **顺序一致（SC）** | 存在保持程序序的全局排列 | 整个执行历史 |
| **线性一致（linearizability）** | 全局排列还须「实时一致」（每操作的线性化点落于其调用区间内） | 整个执行历史（更强） |
| **缓存一致（cache coherence）** | 只保证**单个存储位置**：对其的写有全序、读读到最新写 | 单个变量的历史 |

**核心要点：** 缓存一致性只管「同一个变量」——它保证 `x` 的写在所有核上以同一顺序生效；但它**不管不同变量之间的关系**，即不保证 `x` 与 `y` 的写顺序一致。所以「`x` 一致、`y` 一致」，不等于「`x` 和 `y` 一起一致」——**缓存一致 < 顺序一致**。<span class="marginnote">线性一致比顺序一致多一条「实时」约束：操作的生效时刻必须落在它的调用起止之间，不能「历史完成后才补一个早于调用的生效点」。并发数据结构正确性证明（见《并发数据结构》）用线性一致；系统级推理用顺序一致；硬件底层只有缓存一致。</span>

## 4 现实的内存模型：从强到弱

因为顺序一致太贵，真实架构给出**放松模型**，按「放松程度」排列：

**TSO（Total Store Order，x86 实践）**：只放松「写后读」——CPU 的写缓冲允许你先读到自己的新写、别人稍后才看到。对大多数直觉而言，TSO 很接近 SC，只在一个方向作弊。<span class="marginnote">TSO 是 x86 的「事实内存模型」：有写缓冲、无读重排。它离 SC 只差「写缓冲可见性延迟」一步，所以 x86 上很多 x=1/y=1 的经典实验都能得到「符合直觉」的结果——这反而让 x86 程序员对内存序麻痹大意。</span>
**弱内存模型（weak / relaxed）**：如 Arm、PowerPC 及 C++11 的 `relaxed` 序——写与读都可重排、都可被缓冲，几乎只保证「单地址的原子性」。要让程序正确，程序员**必须显式**插入内存屏障（fence）或使用带序的原子操作。

于是 C/C++ 给出**原子操作 + 内存序**的 API：`memory_order_relaxed`（无顺序承诺）、`memory_order_acquire`/`release`（配对建立「写后读可见」）、`memory_order_seq_cst`（默认，最强的全局一致序）。<span class="marginnote">`acquire/release` 是工业界最常用的一对：release 写在「我发布数据之后」，acquire 读在「我消费数据之前」，两者配对形成 happen-before——读者保证能看到写者 release 之前的所有写。这正是互斥锁、自旋锁内部真正在用的东西。</span>

把这四种序放进一张速查表，按「承诺的强度」从上到下排列：

| 内存序 | 承诺 | 典型用途 |
| --- | --- | --- |
| `memory_order_relaxed` | 仅单位置的原子性，无任何顺序保证 | 计数器、统计量、独立标志位 |
| `memory_order_acquire` | 之后的读写不得被重排到 acquire 之前 | 消费端：读标志位后再读数据 |
| `memory_order_release` | 之前的写不得被重排到 release 之后 | 生产端：写数据后再置标志位 |
| `memory_order_seq_cst` | 所有原子操作一个全局统一顺序（默认） | 强一致同步、需要「看得到彼此」的协议 |

选型口诀：**只有一个位置的数据，用 `relaxed`；要发数据再通知别人读，用 `release` + `acquire`；要让全体原子操作同一条全局时间线，用 `seq_cst`。** 绝大多数业务代码直接默认 `seq_cst`，性能敏感处才逐档放松——这也正是「先写对，再调快」的顺序。

## 5 公式解析：顺序一致与线性一致的差距

把两者的差距用「实时约束」一句话公式化。设操作 $o$ 的调用时刻为 $t^{o}_{\text{call}}$、返回时刻为 $t^{o}_{\text{ret}}$，其线性化点时刻为 $t^{o}_{\text{lin}}$，则线性一致额外要求

$$
t^{o}_{\text{call}} \;\le\; t^{o}_{\text{lin}} \;\le\; t^{o}_{\text{ret}}
\qquad\text{（线性化点落在调用区间内）}
$$

- **第一步，读公式**：操作不能被「挪到比自己更早的时刻」——线性化点必须在自己调用开始之后、返回之前。
- **第二步，对照顺序一致**：顺序一致只要求存在某个全局排列，可以自由挑选排列位置（只要不破坏程序序）；线性一致**限定**了排列位置必须在实时区间内，排除了「历史结束后才补一个早于调用的生效」的取巧。
- **第三步，用直觉**：线性一致=顺序一致+实时约束。并发对象的线性化点分析（《并发数据结构》里「CAS 成功的那瞬间」）之所以能用来证明正确性，正是因为线性一致给出了「调用区间内的一个明确生效时刻」。

## 6 辨析｜易错点：为什么加锁还不够

- **锁只保护临界区**：锁内外的内存序（尤其弱模型下）仍需原子操作与 fence 来保证「解锁后的写对解锁者可见」。
- **`volatile` 不是原子操作**：C 的 `volatile` 只抑制编译器重排与缓存，不提供多线程原子性——它挡不住硬件的写缓冲与重排，用它做同步是经典误区。
- **读-改-写必须原子**：即便顺序一致，`x++` 这类复合操作仍会交错——内存模型只管「单个原子操作的可见性」，不管「几条指令的组合」。

**易错点一句话：** 内存模型解决「原子操作可见的顺序」，互斥解决「复合操作不可打断」——两者分工，缺一不可。<span class="marginnote">这也是为什么标准答案永远是「用 `std::atomic` + 合适的 memory_order，或用锁」：靠直觉编排共享变量，在弱内存模型上几乎必然翻车。全专题的每一课，最后都汇进这同一句纪律。</span>

## 7 小结

- 硬件（写缓冲、重排）让「写后读」跨线程未必有序——**直觉与内存模型有差距**。
- **顺序一致**：存在保持程序序的全局排列（兰波特）；**线性一致**：再加「线性化点落在调用区间内」。
- **缓存一致**只保单变量的写全序，管不了多变量间的顺序——**缓存一致 < 顺序一致**。
- 现实模型谱系：**TSO**（x86，放松写后读）→ **弱模型**（Arm/C++ relaxed，几乎全放）。
- C/C++ 用 `memory_order` 显式声明：`relaxed` / `acquire`-`release` / `seq_cst`；`volatile` 不是原子，锁与内存序各管一段。

到这里，《并发与并行编程》专题的十三篇博文画上句号：从线程与互斥，到信号量、锁、CAS、无锁数据结构，再到死锁、并行算法、屏障、事务内存与内存模型——你手里的这套「先直觉、再严格、最后落到工具」的方法，足以支撑你进入操作系统、分布式系统与高性能计算的任何一面。
