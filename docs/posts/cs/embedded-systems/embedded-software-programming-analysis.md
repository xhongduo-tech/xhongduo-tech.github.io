## 为什么从程序分析开始

前面讲的都是「机器怎么工作」，这一篇回到**人怎么给它写程序**。桌面开发者写错了代码，重试一次就好；嵌入式工程师写的代码要固化在芯片里跑十年，还得算清楚它用多少周期、多少字节、多少焦耳。Wolf 教材第 5 章的三件套——**编译、性能分析、功耗分析**——构成了嵌入式软件工程的度量基础：不度量，就不能改进（还记得上一篇开尔文勋爵的话吗）。这一篇把「C 代码一行行怎么变成电路里的一个个周期」彻底讲透，也为下一篇《软硬件协同设计》的「把热点搬到硬件」提供分析依据。

## 1 为什么嵌入式软件仍然以 C 为主

嵌入式程序主流语言是 C，原因非常实际：

- **接近硬件**：指针、位运算、寄存器映射直接表达，行为可预测。
- **编译器成熟**：GCC / Clang 的 ARM 后端优化已经极强，多数场景不输手写汇编。
- **可移植**：同一份 C 代码可跨 MCU、跨架构编译。

C 与硬件的距离由**编译器**弥合。编译优化级别是一条刻度：`-O0`（不优化，调试友好）、`-O2`（常规优化）、`-Os`（为代码体积优化）、`-Oz`（激进压体积）。**选哪个级别，是在「可调试性、性能、代码体积」之间权衡**，而不是默认选项。

<span class="marginnote">调试与优化是一对矛盾：`-O2` 会把变量优化没、把函数内联掉，断点都断不干净。嵌入式调试常见做法是「发布前用 -O2/-Os 再跑一轮完整回归」——因为「优化后行为改变」本身就是嵌入式 C 程序最常见的隐蔽 bug 来源。</span>

## 2 公式解析：程序执行时间模型

性能分析的第一块基石，是把「程序跑了多久」拆成三个可分别优化的因子：

$$
T_{\text{exec}} = \text{IC} \times \text{CPI} \times T_{\text{clock}}
$$

- **IC（指令计数，instruction count）**：程序执行了多少条指令。由算法 + 编译器决定。
- **CPI（每条指令平均周期数）**：平均一条指令花几个时钟周期。由处理器结构（流水线、缓存、分支预测）决定。
- **$T_{\text{clock}}$（时钟周期）**：硬件时钟决定，$T_{\text{clock}} = 1/f$。

三者相乘就是程序总耗时。**优化的本质就是压低这三项**：

- 减少 IC：换更好的算法（如把 $O(n^2)$ 排序换成 $O(n \log n)$）、让编译器少生成冗余指令。
- 降低 CPI：改善缓存局部性（让数据更可能命中）、减少分支（用条件执行代替分支）、减少内存访问。
- 提高频率 $f$：降低 $T_{\text{clock}}$，但受功耗与散热约束（见《功耗管理》一篇）。

举个数字：某循环执行 10 万条指令，CPI 平均 1.5，时钟 100 MHz：

$$
T_{\text{exec}} = 10^5 \times 1.5 \times 10^{-8}\ \text{s} = 1.5\ \text{ms}
$$

**易错点：** 千万别以为「指令少 = 更快」。一条复杂指令可能 CPI 很高，几条简单指令加起来反而快。**优化要看的永远是指令数与 CPI 的乘积，而不是单看哪一项**。

## 3 代码体积与内存映射

MCU 的 Flash 往往只有几十 KB 到几 MB，**代码体积是硬预算**。C 程序编译后按段落进不同区域：

| 段 | 内容 | 存放位置 |
| --- | --- | --- |
| `.text` | 可执行代码 | Flash（非易失） |
| `.rodata` | 只读常量 | Flash |
| `.data` | 已初始化全局变量 | Flash 中备份，启动时拷贝到 RAM |
| `.bss` | 未初始化全局变量 | RAM（清零后使用） |
| `.stack` / `.heap` | 栈与堆 | RAM |

`map 文件` 记录了每个函数、每个变量在最终镜像里的地址与大小——**嵌入式工程师看 map 文件，就像财务看预算表**。

控制体积的手段：`-Os`/`-Oz` 编译、去掉调试信息、避免过度模板/内联、用 16 位 Thumb 指令（ARM 的压缩指令集，代码密度高）。**辨析：** 内联（inline）是一把双刃剑——它省去调用开销（降 CPI），但每处调用都复制一份代码（涨 `.text`）。「内联热点函数、保持冷函数外置」是工程平衡点。

## 4 性能分析：找出热点

盲目优化代码前，先回答：**时间花在哪？** 三种主流手段：

- **插桩（instrumentation）**：在函数入口/出口插入计时代码，直接统计每个函数耗时。精确但会改变被测量程序的时序（测量者效应）。
- **硬件计数器**：利用 CPU 内置的性能计数器（周期数、缓存命中、分支预测失败）采样，代价小、可信度高。
- **周期级仿真（cycle-accurate simulator）**：逐周期模拟目标处理器，能给出最坏执行时间的上界，但慢。

与性能分析并行的还有嵌入式特有的**时间分析**：为实时调度（见《实时调度理论》）提供任务参数 $C_i$——**最坏执行时间（WCET）**。<span class="marginnote">WCET 的求取是硬实时领域的专门学问：既要考虑最坏输入，又要考虑缓存与分支预测的最坏状态，还要考虑中断抢占。现代工具链（如基于抽象解释的 aiT）给出的是「数学上可信的上界」，而不是「碰巧测到过的最坏值」——这正是硬实时「数学保证」的来源。</span>WCET 不是「测得最快的几次」的平均，而是「最坏输入 + 最坏缓存状态 + 最坏中断」下的上界。它是硬实时系统「数学保证」的输入，也是性能分析最难的形态。

## 5 功耗分析：能量模型

嵌入式程序优化的第三维是能量。把执行时间与功耗乘起来：

$$
E_{\text{task}} = P_{\text{avg}} \times T_{\text{exec}}
$$

- **$P_{\text{avg}}$**：程序运行时的平均功耗，主要来自动态功耗 $\alpha C V^2 f$（见《功耗管理》）。
- **$T_{\text{exec}}$**：程序执行时间，由上式的 IC × CPI × T 决定。

两条推论让「省能量的编程」变得有趣：

- **指令少 + 访存多 vs 指令多 + 访存少**：缓存未命中去取一次主存，能量远高于在寄存器里多算几条指令。**从能量角度看，缓存友好性比指令条数更重要**。
- **忙完就睡**：能量 = 功耗 × 时间，所以「快速算完、立刻深睡」往往比「慢慢算」更省——这正是上一篇 DVFS 反直觉结论的软件侧版本。
- **能量感知编译（energy-aware compilation）**：现代编译器可以针对「每次任务的能量」而非「时间」做优化，因为两者的最优解不一定相同。

## 6 小结

- 嵌入式以 **C 为主**，编译优化级别是「可调试性、性能、体积」的权衡。
- 执行时间 **$T = \text{IC} \times \text{CPI} \times T_{\text{clock}}$**，优化要同时压低三项，不能只看指令数。
- 内存按 **.text / .data / .bss / 栈堆** 分段落放，map 文件就是内存预算表。
- 性能分析三件套：**插桩、硬件计数器、周期级仿真**；硬实时还需要 **WCET** 上界。
- 任务能量 **$E = P \times T$**：缓存友好 + 忙完即睡，是嵌入式省能量的两条编程纲领。
