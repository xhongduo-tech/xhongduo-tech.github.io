## 为什么从实时操作系统开始

一个处理器要同时伺候很多「老板」：一边读传感器，一边算控制量，一边刷新显示，一边等通信。谁先谁后、谁不许被饿死——这就是**调度**问题。前两篇讲了处理器与存储这两块硬件，这一篇第一次把「软件如何管理硬件」摆上台面：**实时操作系统（RTOS）** 如何在共享的 CPU 上让多个任务准时地轮流运行。它是本专题的枢纽——上一篇的中断、这一篇的任务，将共同支撑下一篇的《实时调度理论》与更后面的《功耗管理》《协同设计》。在课程上，它也是第三级《操作系统》在「实时约束」下的加强版。

## 1 从裸机到 RTOS：为什么需要操作系统

最早的嵌入式软件是**裸机（bare metal）**。最简单的组织方式是**超级循环（super loop）**：

```c
while (1) {
    read_sensor();    /* 轮询传感器 */
    compute_control();
    refresh_display();
}
```

如果每个函数都不耗时，超级循环足够。但一旦某段代码要等很久（比如等通信超时），**后面所有任务都会被堵住**。改进版是**前后台系统**：一个主循环做「后台」，中断服务程序（ISR）做「前台」——紧急的事放进中断，普通的事留在循环。前后台的问题在于：**后台任务之间无法互相暂停**，一个慢任务照样会延迟其他任务。

**RTOS 的答案是把「任务」抽象成独立实体**，由**调度器（scheduler）**决定某个时刻谁运行，并且支持**抢占**：高优先级任务一到，立刻打断低优先级任务。

<span class="marginnote">「抢占（preemption）」是 RTOS 与超级循环的分水岭。超级循环里的函数只能「自愿让位」，RTOS 里的任务可以被「强制让位」——这保证了高优先级事件不被低优先级任务拖累。</span>

## 2 任务、上下文与状态机

**任务（task / thread）**：一个拥有独立执行流、独立栈的软件单元。每个任务由**任务控制块（TCB）**管理，TCB 记录它的栈指针、状态、优先级、寄存器现场。

任务在其生命周期里处于几个状态：

```
运行（running）→ 被高优先级任务打断 → 就绪（ready）
运行（running）→ 等待某个事件/资源 → 阻塞（blocked）
阻塞（blocked）→ 事件到达 → 就绪（ready）
```

**上下文切换（context switch）**：把一个任务的全部寄存器现场保存进它的栈，再把另一个任务的现场恢复出来。切换频率越高，实时响应越及时，但 CPU 花在切换上的时间也越多——这个代价用公式算，见第 5 节。

## 3 调度器与调度策略

**调度器**的核心规则通常是：**就绪任务里，谁的优先级高谁运行**。围绕「优先级从哪来」，出现了两类策略：

**静态优先级**：优先级在创建任务时定死。经典策略是**速率单调（RM）**——周期越短、优先级越高。
- **动态优先级**：优先级随运行情况变化。经典策略是**最早截止期限优先（EDF）**——谁的截止期限最近谁先跑。

RM 与 EDF 的可调度性分析是实时理论的绝对核心，下一篇专门展开。这里先立住概念：**调度策略回答「现在跑谁」，「可调度性分析」回答「这么跑，会不会有任务错过期限」**。后者不是靠试，是靠数学保证——这是硬实时系统区别于普通程序的地方。

## 4 互斥、信号量与优先级反转

任务们共享资源（同一个变量、同一个外设），必须防止**竞态（race condition）**。最常用的工具是**信号量（semaphore）**与**互斥锁（mutex）**：任务进入临界区前 P 操作（获取），离开时 V 操作（释放），保证任意时刻只有一个任务碰共享资源。

但「高优先级任务抢到锁前被挡在临界区外」会引出一个著名陷阱——**优先级反转（priority inversion）**：

1. 低优先级任务 L 持有锁，正在临界区里慢慢干；
2. 高优先级任务 H 到达，需要这把锁，只好阻塞等待；
3. 中优先级任务 M 到达，它不需要锁，于是把 CPU 抢走，L 被 M 打断，无法尽快释放锁；
4. 结果：**H 被一个中优先级任务 M 卡住了**——优先级彻底颠倒。

1997 年的火星探路者（Mars Pathfinder）着陆后反复复位，最后查明正是优先级反转：一个低优先级的通信任务被中优先级任务无限期延误，导致高优先级总线管理任务等不到锁，触发了看门狗复位。<span class="marginnote">火星探路者事件是嵌入式史上最著名的真实案例：地面团队在地球上复现了问题，用<strong>优先级继承（priority inheritance）</strong>——让持有锁的 L 临时「继承」等待者 H 的优先级去跑完临界区——当天就把补丁上传到了 1 亿公里外的火星。</span>

与优先级反转并列的还有**死锁（deadlock）**：两个任务各自持有一把锁、又互相等待对方释放。死锁的四要件（互斥、持有并等待、不可剥夺、循环等待）在嵌入式并发里同样适用。

**辨析｜易错点：** 优先级反转不是信号量的 bug，而是「低优先级被中优先级抢占」的调度后果；消灭它的关键不是换锁，而是**让锁的持有过程不被无关任务打断**——优先级继承与**优先级上限协议（priority ceiling）**就是为此设计。

## 5 公式解析：上下文切换的代价

抢占式调度不是免费的。设任务的一次完整切换（保存 + 恢复）耗时为 $t_{\text{ctx}}$，每个任务一次运行的平均有效时长为 $t_{\text{exec}}$，则 CPU 花在切换上的时间占比：

$$
\eta = \frac{t_{\text{ctx}}}{t_{\text{exec}} + t_{\text{ctx}}}
$$

- **$t_{\text{ctx}}$**：纯开销，与任务本身的计算无关，通常几微秒到几十微秒。
- **$t_{\text{exec}}$**：任务真实干活的时间。注意 RTOS 的**时间片（tick）**决定了一次运行的最长时长，$t_{\text{exec}}$ 不会无限大。
- **$\eta$**：调度开销占比。它提醒我们：**任务切得越碎、切换越频繁，有效算力损失越大**。

举个例子：切换开销 50 μs，任务每 2 ms 切换一次，则：

$$
\eta = \frac{50}{2000 + 50} \approx 2.4\%
$$

2.4% 看着不多，但如果把时间片切到 500 μs，$\eta$ 就涨到 9%。**换取的实时性收益与付出的切换开销，是一笔需要明算的账**。

## 6 小结

- 从**超级循环 / 前后台**到 **RTOS**，核心飞跃是「任务独立 + 抢占」。
- 任务的三种状态 **运行 / 就绪 / 阻塞**，由**上下文切换**维系。
- 调度策略回答「现在跑谁」，**可调度性分析**回答「会不会错过期限」——后者由数学保证。
- **优先级反转**是高优先级被无关中优先级卡住的调度陷阱，靠**优先级继承 / 上限协议**解决。
- 切换开销 $\eta = t_{\text{ctx}}/(t_{\text{exec}}+t_{\text{ctx}})$ 是实时系统的隐性税。
