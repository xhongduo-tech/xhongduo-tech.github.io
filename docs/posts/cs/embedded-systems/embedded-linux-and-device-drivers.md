## 为什么从嵌入式 Linux 开始

前面两篇讲了 RTOS：小而专、实时性强、一切尽在掌握。但当你面对的路由器、机顶盒、汽车信息娱乐屏、机器人——需要文件系统、网络协议栈、图形界面、几百种驱动时，自己写 RTOS 应用是低效的。**嵌入式 Linux** 是另一种主流答案：把一个成熟通用操作系统裁剪到嵌入式设备上，用「生态」换「确定性」。设备驱动则是 Linux 与硬件之间的「翻译官」——操作系统不会认芯片，它只认驱动。这是 Heath《嵌入式系统设计》第 7 章的主线，也是从「裸机思维」跨向「系统思维」的一步。

## 1 为什么嵌入式要用 Linux

Linux 进入嵌入式领域的理由很实际：

- **能力完整**：进程、虚拟内存、文件系统、TCP/IP、多核调度开箱即用。
- **开源可裁剪**：通过内核配置（menuconfig）去掉不需要的子系统，把内核裁到几 MB。
- **驱动生态**：成千上万现成驱动，遇到新硬件只需写薄薄一层。
- **开发效率**：用户态用 GNU 工具链，调试、联网、文档都成熟。

代价同样明显：Linux 是**通用 OS，不是硬实时 OS**。它有进程调度、虚拟内存、页缓存，这些带来不可预测的延迟。工程上的折中方案：

| 需求 | 选型 |
| --- | --- |
| 硬实时、微秒级响应、资源极小 | 裸机 / RTOS（FreeRTOS、RT-Thread） |
| 功能丰富、非实时或软实时 | 嵌入式 Linux |
| 既要 Linux 又要硬实时 | 实时补丁（PREEMPT_RT）、双系统并存 |

<span class="marginnote">PREEMPT_RT 补丁把内核里几乎所有不可抢占的临界区改造成可抢占，让 Linux 的实时性从「软」逼近「硬」；但「逼近」不等于「保证」——真正微秒级硬实时场合，工业界仍倾向于专用 RTOS。</span>

## 2 从开机到跑起来：启动流程

嵌入式 Linux 的启动像一场接力赛，每个阶段换一个「运动员」：

```
Bootloader（U-Boot）→ 内核（kernel）→ 根文件系统（rootfs）→ init → 应用程序
```

**U-Boot**：第一阶段引导程序，初始化 DRAM、串口，把内核镜像从 Flash/SD/eMMC 读入内存并跳转执行。<span class="marginnote">芯片厂商随开发板发布的板级支持包（BSP）就是「让内核在这块具体板子上跑起来」的全部软件集合：bootloader、内核补丁、设备树、驱动与配置文件。它决定了你的嵌入式 Linux 工程从哪条路起步。</span>
- **内核**：解压、初始化硬件、挂载根文件系统、启动第一个用户进程 `init`（常由 BusyBox 提供）。
- **设备树（Device Tree）**：一份 `.dts` 文本描述了整块板子「有什么硬件、地址在哪、中断连到哪」，编译成 `.dtb` 二进制交给内核。硬件变了改设备树，不必重编译内核。
<span class="marginnote">设备树把「硬件配置」从内核源码里剥离出来：换一块外设布局相同的板子，常常只要改 `.dts` 重新编译设备树、内核一行不动。厂商发布「开发板 BSP」时，核心交付物里必有一份设备树源码——它是嵌入式 Linux 工程最先要读的文档之一。</span>

嵌入式开发还有一个关键动作：**交叉编译（cross-compile）**——在性能强大的主机（x86）上编译目标板（ARM）的程序。工具链、目标文件、目标体系结构三者必须配套，是新手踩坑的高发区。

## 3 设备驱动的角色

**设备驱动（device driver）**：内核里的一段代码，把某个具体硬件抽象成操作系统标准接口。用户程序不直接摸寄存器，而是通过 `open / read / write / ioctl` 访问「设备文件」。

按数据特征驱动分三类：

- **字符设备（char device）**：按字节流读写，如串口、GPIO、LED。用**主设备号 / 次设备号**标识。
- **块设备（block device）**：按块读写、可随机访问、有缓存，如 SD 卡、eMMC。
- **网络设备（net device）**：走内核网络栈，用 `net_device` 结构描述。

写驱动要填一张「方法表」——内核里的 `file_operations` 结构，把用户态的系统调用映射到驱动函数：

```c
struct file_operations fops = {
    .open = my_open,
    .read = my_read,
    .write = my_write,
    .ioctl = my_ioctl,
};
```

驱动可以**编译进内核**，也可以做成**模块（module）**：用 `insmod` 运行时加载、`rmmod` 卸载，不用重启就换驱动——这是驱动调试期最常用的手段。驱动运行在**内核态**，与用户态之间有权限边界：内核态能直接碰硬件寄存器，但也意味着一个野指针就能搞死整个系统。

方法表之外，驱动还靠一张**资源表**工作：设备树告诉它「寄存器基址在哪、中断号是多少、时钟与 GPIO 接在哪个控制器」，驱动只负责「按表操作」。引脚、地址、中断这些差异全被设备树消化，驱动逻辑保持通用——这是嵌入式 Linux 能用一个内核支持成百上千种板子的关键：**硬件差异数据化，驱动逻辑通用化**。

## 4 中断处理：上半部与下半部

硬实时场景里，中断处理是性能与确定性的主战场。Linux 把一次中断处理拆成两半：

- **上半部（top half）**：真正的 ISR。要求**极快返回**，只做最紧急的事（读硬件状态、清中断标志），因为执行期间更高优先级中断可能被屏蔽。
- **下半部（bottom half）**：把不紧急的重活推迟执行。常见机制：`tasklet`、`workqueue`、软中断（softirq）。下半部可以睡、可以被抢占，慢慢干。

**辨析｜易错点：** 一个经典红线是**中断上下文里不能睡眠**——不能调用 `kmalloc(..., GFP_KERNEL)`（可能睡眠）、不能拿睡眠锁、不能做耗时的磁盘 I/O。凡是可能睡眠的操作，都只能放进下半部。很多新手驱动「死机」就死在这一条。

中断里的并发问题也更凶险：ISR 可能打断正在运行的进程，两者若共享数据，就产生**竞态**。内核因此提供**自旋锁（spinlock）**与**互斥锁（mutex）**：自旋锁在「不会睡眠的短临界区」用，互斥锁在「可以睡眠的长临界区」用——用反了，轻则性能崩塌，重则死锁。

## 5 公式解析：中断负载对 CPU 的占用

中断虽然「省心」，但也是有代价的。设中断频率为 $f$（每秒次数），每次完整处理（上半部 + 下半部）耗时为 $t_{\text{int}}$，则 CPU 花在处理中断上的比例：

$$
\eta_{\text{int}} = f \cdot t_{\text{int}}
$$

- **$f$**：中断到达频率。它由硬件事件决定，比如串口每收到 1 字节来一次中断。
- **$t_{\text{int}}$**：单次中断处理的平均耗时。
- **$\eta_{\text{int}}$**：中断对 CPU 的占用率。它揭示了中断方式的一个隐藏开销——**高频率小事件（每字节一中断）可能比轮询更浪费**。

算一笔账：串口 1 Mbps，每 8 位一中断，则 $f = 125{,}000$ 次/秒；若每次处理 20 μs，则：

$$
\eta_{\text{int}} = 125{,}000 \times 20\,\mu\text{s} = 2.5 = 250\%
$$

超过 100%！这说明**单字节中断的 CPU 根本扛不住全速串口**。工程解法正是上一篇提过的 **DMA + 批中断**：硬件攒够一批数据再通知一次 CPU，把 $f$ 降两个数量级。这也解释了为什么现代驱动几乎都带 DMA。

这个数字也解释了中断设计的另一条铁律——**中断服务要极快返回**：中断期间高优先级中断被屏蔽、其他进程被冻结，任何拖延都会直接抬升 $\eta_{\text{int}}$ 与系统的整体响应时间。把可推迟的工作全部推给下半部，正是为了让「最贵的时间段」尽量短。

## 6 小结

- 嵌入式 Linux 用**生态与能力**换取确定性，与 RTOS 按「实时性需求」分工。
- 启动是接力赛：**U-Boot → 内核 → 根文件系统 → init**；硬件描述靠**设备树**。
- 驱动把硬件抽象成 `file_operations` 接口，分**字符 / 块 / 网络**三类，可编译进内核或做模块。
- 中断处理拆成**上半部（快）与下半部（慢）**；中断上下文**不能睡眠**。
- 中断占用率 $\eta_{\text{int}} = f \cdot t_{\text{int}}$，高频中断靠 **DMA + 批量通知**解决。

在下一节，我们把目光从「功能」转向「能量」：**功耗管理与低功耗设计**——嵌入式系统为什么把每一毫瓦都看得比金子重。
