## 为什么从语言虚拟机开始

第十八篇进入**运行时**的最后一环——**语言虚拟机（language virtual machine, VM）**：一个抽象的「执行机器」，语言编译到它的**字节码（bytecode）**，VM 负责解释或即时编译执行。VM 让语言获得**跨平台性**（Write Once, Run Anywhere）、**安全边界**（字节码受 VM 检查）、与**运行时服务**（GC、JIT、反射）。从 1970 年代的 **p-code**（Pascal 的中间代码）到 **JVM**、**BEAM**、**WebAssembly**——VM 的演化是「中间表示 + 运行时服务」不断精致的历程。<span class="marginnote">VM 的定位：语言编译器<strong>不对着真实 CPU 编译</strong>，而对着一台「虚拟 CPU」编译——虚拟 CPU 的指令集（字节码）再由 VM 解释/编译到真实 CPU。好处：<strong>一次编译、处处运行</strong>（字节码跨平台）；坏处：多一层间接（性能损失，靠 JIT 弥补）。「VM = 语言与硬件的适配层」。</span>

## 1 为什么需要虚拟机

三种主要动机：

- **可移植性**：编译到字节码而非机器码——字节码在任何有 VM 的平台上运行。Java 的「一次编写，处处运行」靠 JVM。
- **安全与隔离**：VM 在字节码执行前**验证**它（类型检查、边界检查）——Java 字节码被验证后才运行，防恶意代码。
- **运行时服务**：GC、异常处理、反射、JIT——VM 统一提供，语言无需每平台重写。<span class="marginnote">VM 与「编译到机器码」的取舍：原生编译（C/Rust）零抽象层、最快，但每平台单独编译、无运行时保护；VM 牺牲一层间接，换可移植 + 安全 + 运行时服务。现代语言（Go、Rust）用「编译到原生 + 链接时优化」避开 VM；Java/C#/Python 用 VM 换生态与安全。「性能 vs 便利」的经典选择。</span>

## 2 p-code：虚拟机史的起点

**p-code（pseudo-code，伪代码）**：1970 年代 Pascal 编译器的中间代码——Pascal 源码编译成 p-code，再由 p-code 解释器执行。UCSD Pascal 用它在不同机器上运行同一份程序。

p-code 的遗产：

- 首次证明「中间代码 + 解释器」模式可行——编译器可移植（只需移植解释器）。
- 首次分离「编译前端」与「执行后端」——后来 JVM、CLR 的思想原型。
- 教学意义：p-code 机器是「面向栈的虚拟机」——与 JVM 同构。<span class="marginnote">p-code 的名字易误导（pseudo-code 在 PLT 里通常指「伪代码/算法描述」）——这里的 p-code 特指 Pascal 的中间字节码。「编译到中间表示、再解释执行」的模式由此奠基，今天每种主流语言都有自己的「p-code」：Python 的 `.pyc` 字节码、Ruby 的 YARV 指令、Lua 的 bytecode。</span>

## 3 面向栈的虚拟机：VM 的主流形态

多数 VM（JVM、CPython、Lua VM）是**面向栈的虚拟机（stack-based VM）**：所有操作在**操作数栈**上进行——指令从栈取操作数、把结果压回栈。

```
指令序列（JVM 字节码）:
iconst_1    ; 把常量 1 压栈
iconst_2    ; 把常量 2 压栈
iadd        ; 弹出 1、2，相加，把 3 压栈
```

执行 `1 + 2`：两条压栈 + 一条加法。面向栈的设计：

- **指令紧凑**：无需显式操作数寄存器——操作数隐含在栈顶。
- **实现简单**：栈 + 分派循环。
- **代价**：每次运算都要「压栈/弹栈」——比寄存器机器（真实 CPU）多内存往返。<span class="marginnote">JVM 是面向栈的，而真实 CPU 是<strong>面向寄存器的</strong>（操作数在寄存器里）。面向栈的字节码紧凑、易生成、易验证（JVM 设计目标）；面向寄存器的字节码（Dalvik/Android、Lua 5.0+）更贴近硬件、解释更快。「栈 vs 寄存器」是字节码设计的第一分叉——JVM 选了栈（简单 + 可验证），现代 VM 有向寄存器倾斜的趋势。</span>

## 4 公式解析：VM 的执行模型

VM 执行可以形式化为「取指-分派循环」。设字节码程序 $P$、程序计数器 $pc$、操作数栈 $S$、局部变量表 $L$：

$$
\text{exec}(P) = \text{loop: } \text{op} = P[pc];\ \text{exec\_op}(\text{op}, S, L);\ pc += \text{size}(\text{op})
$$

以 `iadd` 为例：

$$
\text{exec\_op}(\text{iadd}) = \text{pop } a,\ \text{pop } b,\ \text{push } (a + b)
$$

三步拆解：

- **第一步，取指**：从程序计数器位置取一条指令——`iconst_1`、`iadd` 都是字节码指令。
- **第二步，分派**：`exec_op` 按指令类型执行——`iadd` 从栈弹两个、加、压回。
- **第三步，推进**：程序计数器前移，取下一条——**循环往复直到程序结束**。**「VM = 一条指令一条指令地执行字节码的循环」**——它本身就是一个「程序」，模拟一台「虚拟 CPU」。

**辨析｜易错点：** VM 解释执行的性能：每个字节码指令的「取指 + 分派」都有开销（switch 跳转、栈操作）。**JIT（即时编译）**把热点字节码编译成机器码，绕过解释循环——「先解释快启动，再编译热点快执行」。**「VM 慢在解释循环，JIT 把慢的变快」**——这是现代 VM 性能的枢纽（下一节 JVM 详讲）。

## 5 VM 的现代谱系

| VM | 语言 | 字节码 | 特点 |
| --- | --- | --- | --- |
| JVM | Java/Kotlin/Scala | class 文件 | 最成熟、JIT 极致 |
| CLR | C#/F# | IL | 微软生态 |
| CPython | Python | `.pyc` | 字节码 + 全局锁 |
| BEAM | Erlang/Elixir | BEAM 指令 | 容错并发（下一节） |
| V8 | JavaScript | Ignition 字节码 | JIT（TurboFan） |
| WebAssembly | 多种 | wasm | 面向 Web（最后一节） |

<span class="marginnote">VM 的未来：<strong>Wasm 把「虚拟指令集」标准化为浏览器的通用目标</strong>；GraalVM 让 JVM 运行多语言（Truffle 框架解释其他语言）；「多语言运行时」——VM 从「一语言一虚拟机」走向「一虚拟机多语言」。「VM 是语言的中间表示 + 运行时服务的载体」，这个思想正扩展到语言之外的领域（浏览器、区块链、AI 推理引擎）。</span>

## 6 解释器 vs 编译器 vs VM：实现的谱系

「VM」常与「解释器」「编译器」混淆——三者是「执行一个程序」的三种策略，构成一条谱系：

**纯解释器（interpreter）**：直接读**源码**、边解析边执行（早期 Python/JS）。无中间表示，启动快，但每个操作都现场解析——慢。

**编译 + 直接执行**（C/Rust）：源码编译成**机器码**，直接跑。最快，但平台相关、需单独编译。

**VM 路线**（Java/Python/WebAssembly）：源码编译成**字节码**（中间表示），VM 解释/JIT 执行字节码。介于两者之间——字节码比源码好解析（快于纯解释）、比机器码可移植（跨平台）。

| 路线 | 中间表示 | 执行 | 平台 | 速度 |
| --- | --- | --- | --- | --- |
| 纯解释 | 无 | 解析源码 | 源码级可移植 | 慢 |
| 编译原生 | 机器码 | 直接 | 平台相关 | 最快 |
| VM | 字节码 | 解释 + JIT | 字节码可移植 | 中 |

**辨析｜易错点：** **「解释型语言」与「编译型语言」的二分已过时**——Python 现在也编译成字节码再执行；JS 的 V8 是 JIT 编译；Java 混合解释 + JIT。**「现代语言几乎都走『编译到中间表示 + 混合执行』」**——纯解释/纯编译是两极，VM 是主流中间态。「语言是解释还是编译」问错了问题——正确的问题是「它编译到什么，用什么执行」。

## 7 小结

- **语言虚拟机** = 抽象执行机器：编译到字节码、VM 解释/JIT 执行——可移植 + 安全 + 运行时服务。
- **p-code** 是 VM 史的起点——「中间代码 + 解释器」模式奠基，JVM/CLR 的思想原型。
- **面向栈的 VM** 是主流（JVM、CPython）：操作在操作数栈上进行——指令紧凑、实现简单。
- VM 执行 = 取指-分派循环；JIT 把解释循环的热点编译成机器码——「先解释后 JIT」是性能枢纽。
