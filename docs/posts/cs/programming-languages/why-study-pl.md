## 为什么从学习语言原理开始

这个网站的主线是「从极限到大模型」：从数学的根基出发，一路走到算法与数据结构，再走向当代人工智能。走到第三级「计算机基础」，一道绕不开的门槛是——**这些算法，到底用什么表达？** 答案正是**程序设计语言（programming language）**：人与机器之间的契约语言，也是全部计算思想最终的栖身之所。<span class="marginnote">从第一级《集合的概念》到第三级《数据结构》，我们一直在用「符号」描述数学对象；程序设计语言则把这种描述变成可执行的计算。某种意义上，语言设计是继「数学符号」之后，人类发明的第二套思考工具。</span>

很多人会问：我直接学一门具体语言不就行了吗？这就像「我直接背单词就能学英语」——可以入门，却永远停留在模仿层。本专题不做「Python 速成」，而是把语言当成研究对象：它为什么长成这样、有哪些可以量化的好坏标准、不同的设计选择如何塑造了今天我们手里的每一门语言。这正是 Sebesta《程序设计语言原理》开篇要回答的问题。

## 1 为什么学语言原理：四条理由

「会写」与「懂得为什么这样设计」是两件事。Sebesta 在第 1 章给出了学语言原理的理由，我们归并为四条。<span class="marginnote">教材原列六条：增强表达想法的能力、为选择语言提供背景、提高学习新语言的能力、理解实现（implementation）的含义、更好地使用已会语言、推动计算科学整体进步。归并为四条后更便于记忆。</span>

**其一，提升抽象能力。** 每种语言都是一层抽象：汇编把机器指令抽象成助记符，C 把内存抽象成变量，Python 把过程抽象成几乎没有样板的表达式，Haskell 把计算抽象成纯函数。掌握的语言视角越多，面对一个问题时你手里的「思维工具箱」就越大——佩利斯那句名言正是在提醒这一点：**语言会反过来塑造你思考问题的方式**。<span class="marginnote">「语言的边界就是世界的边界」并非只属于语言学。写惯了 C 的人初次接触 Haskell 的列表推导，或写惯了 Python 的人初次接触 Rust 的所有权系统，都会经历一次认知重组——这正是学习新范式的价值。</span>

**其二，理解语言设计中的权衡。** 没有完美的语言，只有不同的取舍。静态类型换来早期纠错，却牺牲了快速原型；自动垃圾回收换来安全，却付出一部分性能；语法简洁换来上手快，却把更多约定藏进惯例。学语言原理，就是学会看清每项特性的**两端**：它解决了什么问题、又引入了什么新问题。

**其三，提升挑选与评估语言的能力。** 今天团队选型面对的是几十种仍在活跃演进的语言。没有评价标准，选择就只能靠「熟」与「流行度」。第 2 节要讲的可读性、可写性、可靠性、成本，正是把「我喜欢」翻译成「它在这些维度上更优」的标尺。

**其四，深入实现机制，为《编译原理》铺路。** 作用域、类型系统、闭包、异常——每一个语言特性背后都有一份运行时实现。为什么递归有调用栈开销？为什么闭包要捕获词法环境？为什么 Python 的全局解释器锁（GIL）会限制并行？这些问题的答案，一半在语言设计，一半在实现，恰好是第三级《编译原理》专题从《编译器的结构：分析与综合》开始要逐一落地的内容。学语言原理，等于先拿到「设计意图」，再去《编译原理》里看「工程实现」。

## 2 语言的评价标准：可读性、可写性、可靠性、成本

评价一门语言，Sebesta 给出四个核心标准，它们不是四个独立的「打分项」，而是互相牵制的设计轴。

**可读性（readability）**：程序生命周期的大部分成本在维护，而维护的第一步是读懂。影响可读性的子因素有：整体简洁性、正交性、数据类型丰富度与语法设计。**正交性（orthogonality）** 指「少量机制可自由组合」的程度——C 中 `a[i]` 与 `*(a + i)` 等价，就是下标与指针运算正交的一个例子；组合越多，可读性越好，但也越需要谨慎。

**可写性（writability）**：把想法写成程序的便利程度。简洁与正交同样帮到它，此外还有表达力与对抽象的支持。Python 的列表推导式 `[x * x for x in nums]` 一行写完「对每个元素平方」，就是可写性的典型体现。

**可靠性（reliability）**：程序按规范运行的概率。受类型检查、异常处理与别名（aliasing）影响：Java 用强类型与异常把「空指针」与「非法参数」显式化，比 C 语言「错误全靠返回值与约定」更可靠；而指针别名带来的隐蔽互相干扰，正是 C 系语言可靠性偏低的重要原因。

**成本（cost）**：一笔总账——培训、编写、编译、执行、语言实现系统、由不可靠导致的事故、以及长期维护。<span class="marginnote">「成本」不是单指运行速度：一次由类型错误引发的线上事故，往往贵过十年的编译时间。这也是可靠性必须单列一档的原因。</span>

**辨析｜易错点：** 四个标准常常互相打架。追求可写性会牺牲可读性（Perl 的隐式变量 `$_` 极简却难读），追求可靠性会牺牲性能（数组越界检查是有代价的）。所以评价语言不存在「总分」，只有「在哪些维度上更优、愿意为哪些维度付多少成本」——这正是下一节三种写法要展示的具体画面。

## 3 同一求和，三种写法：范式差异的第一次照面

先不背概念，看同一个小程序——计算 $1$ 到 $n$ 的和——在三种语言里的样子。它几乎不涉及任何「高级特性」，却已经暴露了三种范式的气质。

```c
/* C —— 命令式：显式循环 + 可变累加器 */
int sum_1_to_n(int n) {
    int s = 0;
    for (int i = 1; i <= n; ++i)
        s += i;              /* 状态被逐次改写 */
    return s;
}
```

```python
# Python —— 站在中间：可以写循环，更地道的写法是交给内置函数
def sum_1_to_n(n):
    return sum(range(1, n + 1))   # 表达「做什么」，而非「怎么做」
```

```haskell
-- Haskell —— 函数式：没有赋值语句，计算是表达式的求值
sum1ToN :: Int -> Int
sum1ToN n = sum [1 .. n]     -- [1..n] 构造列表，sum 折叠求和
```

三个版本对应三种哲学。C 把求和描述为**步骤**：建一个累加器，循环里一次次改写它——这是对冯·诺依曼机器的直接模仿；Haskell 把求和描述为**关系**：结果就是「1 到 n 这个列表的和」，交给机器去求值；Python 站在中间，既允许你写循环，也鼓励你直接声明意图。<span class="marginnote">同样一个需求，「命令式」强调怎么做，「函数式」强调是什么，「逻辑式」则强调断言是否成立——第 5 节的核心对比表会把这四个方向并排摆开。</span>

## 4 语言的演进与编程范式概览

把「权衡」放进时间轴，就看到了语言演化史。它不是简单的「越新越好」，而是**同一批设计问题被不同时代、不同语言反复回答**的历史。

- **1950 年代**：Fortran（1954，约翰 · 巴科斯）——第一个被广泛使用的高级语言，面向科学计算，名字就来自 Formula Translation；Lisp（1958，麦卡锡）——第一个函数式语言，把 λ 演算搬上机器。
- **1960 年代**：Algol 60 奠定块结构、递归与 BNF 文法描述，是「描述语言的语言」；COBOL 面向商业数据处理。
- **1970 年代**：C（1972，里奇）与 Pascal 把「结构化的命令式」推向成熟；Smalltalk（艾伦 · 凯）成为第一个完整的面向对象语言；Prolog（1972）开启逻辑式程序设计。<span class="marginnote">Prolog 得名自法语 Programmation en Logique（逻辑式程序设计）：程序不是「做事的步骤」，而是「关于世界的事实与规则」，计算交给机器的推导。</span>
- **1980 年代**：C++ 把面向对象装进系统语言；Ada 追求超可靠（导弹、航空语境）。
- **1990 年代**：Java（跨平台 + 托管内存）、Python（多范式 + 胶水）、Haskell（纯函数式）、JavaScript（浏览器脚本），语言进入「多范式融合」与「网络」时代。
- **2000 年代以后**：Rust 用所有权系统挑战「安全与性能不可兼得」，Go 用 goroutine 拥抱并发，TypeScript 给 JavaScript 补上渐进类型。

把这四十年压缩成四条脉络，就是四个**编程范式（programming paradigm）**：

- **命令式（imperative）**：以「语句 + 可变状态」为核心，程序是操作序列——冯·诺依曼机器的抽象。
- **面向对象（object-oriented）**：命令式的自然延伸，叠加数据抽象、继承与动态绑定，以「对象 + 消息」组织程序。
- **函数式（functional）**：计算 = 数学函数的求值，强调引用透明（引用透明性）与无副作用。
- **逻辑式（logic）**：计算 = 从事实与规则中推导结论，程序是对「知识」的声明。

需要强调：范式不是互相排斥的标签，而是抽象的不同方向。现代主流语言几乎都是多范式的——Python 同时支持命令式、面向对象与函数式写法，这也是它能成为「胶水语言」的原因。

## 5 公式解析（本章以「核心对比表」替代）：四种编程范式特征对照

本主题没有需要逐项拆解的核心公式；按编辑章程第 5 节，无公式的主题以「核心要点表格」替代公式解析。下面这张表就是本章的「公式」，我们照例把它拆成三步来读。

| 维度 | 命令式（C / Pascal） | 面向对象（Java / C++） | 函数式（Haskell / Scheme） | 逻辑式（Prolog） |
| --- | --- | --- | --- | --- |
| 计算模型 | 存取数据并逐步改写（冯·诺依曼） | 对象之间收发消息 | 数学函数的求值 | 从事实与规则中推导结论 |
| 程序的基本单元 | 语句、赋值 | 对象、类、方法 | 表达式、函数 | 事实、规则、查询目标 |
| 状态处理 | 显式可变状态 | 对象封装的可变状态 | 无副作用、引用透明 | 一次绑定、不可覆写 |
| 主要抽象手段 | 过程抽象 | 数据抽象、继承、多态 | 高阶函数、函数组合 | 声明式描述「是什么」 |
| 回答的核心问题 | 怎么做（how） | 谁对谁负责（who） | 是什么（what） | 是否成立（whether） |

- **第一步，读「计算模型」一行**：四种范式其实是四种「计算是什么」的答案。命令式认为是「状态的逐步改写」，于是算法被写成循环与赋值；函数式认为是「表达式的求值」，于是程序被写成嵌套的函数调用；逻辑式认为是「从已知推出未知」，于是程序被写成待证明的命题。面向对象则在命令式底座上把「改状态的权限」分发到对象之间。
- **第二步，读「状态处理」一行**：这是分歧最深的一行。命令式与面向对象都接受可变状态，区别只在状态藏在全局还是封装在对象里；函数式把状态「消灭」——引用透明的表达式在任何时刻求值结果一致；逻辑式更进一步，变量一旦绑定就不可覆写，程序里根本没有「先赋值再改值」这回事。
- **第三步，读「回答的核心问题」一行**：把前两行收束成一个词——命令式问 how，面向对象问 who，函数式问 what，逻辑式问 whether。这四个问题对应了第 3 节三种写法的直觉，也预告了本专题第十一篇（面向对象）、第十二篇（函数式）、第十三篇（逻辑式）的内容。

## 6 小结

- 学语言原理的四个动机：**提升抽象能力、理解设计权衡、提升挑选与评估能力、深入实现机制**。
- 评价语言的四个标准：**可读性、可写性、可靠性、成本**；它们不是独立打分项，而是相互牵制的设计轴。
- 范式是抽象的不同方向，不是互斥标签：命令式问「怎么做」，面向对象问「谁负责」，函数式问「是什么」，逻辑式问「是否成立」。
- 语言演化是同一批设计问题被反复回答的历史；现代语言多是**多范式融合**。

在下一节，我们把评价标准展开成一篇完整的《编程语言的四大评价标准》。而在更远处，当你想看清「设计意图」如何变成「可运行的机器行为」，第三级《编译原理》将从《编译器的结构：分析与综合》开始，把语言原理的每一个概念翻译成编译器里的词法、语法与语义阶段——本专题负责设计，编译原理负责实现。
