## 为什么从惰性求值开始

我们此前默认的求值方式是**严格求值（eager/strict evaluation）**——表达式一出现就求值。**惰性求值（lazy evaluation）**反过来：**表达式不被求值，直到它的值真正被需要**。这个看似简单的反转带来惊人的后果：可以表达无限数据结构、可以写出「自然」的流式算法、可以让条件分支只算需要的一支。Haskell 是纯惰性语言的代表；而 Python 的生成器、Rust 的迭代器、JavaScript 的 `??` 短路，都是惰性的局部渗透。理解惰性，是理解「按需计算」这一普适优化思想的关键。<span class="marginnote">惰性求值的直觉：「表达式是配方，不是成品」。严格语言先把配方烤成成品再传递；惰性语言传递配方，谁吃谁烤。`head [1..]` 在 Haskell 里立刻返回 1——`[1..]` 是无限列表，但 `head` 只需第一个元素，其余永不生成。</span>

## 1 严格 vs 惰性：何时求值

**严格求值（strict evaluation）**：函数实参在进入函数体之前求值。

```python
def f(x): return 1
f(expensive())   # expensive() 先执行，即使 f 不用 x
```

**惰性求值（lazy evaluation）**：实参不求值，只有函数体**用到它时**才求值；若从未用到，永不求值。

```haskell
f x = 1
f (expensive)    -- expensive 不被求值：f 不用 x
```

三种「用到才求」的机制：

- **call-by-name**：每次用到都重新求值（纯替换）。
- **call-by-need**（Haskell）：用到时求值一次，缓存结果——**共享**。
- **短路求值**：`&&`/`||` 跳过已定结果的一侧——最局部的惰性。<span class="marginnote">Haskell 用的是 call-by-need：惰性 + 缓存。`f x = x + x` 中 `x` 求值一次、两处共享结果，而非求值两次。call-by-need 保证「惰性不求值多余」且「求值不重复」——这是惰性与纯函数（无副作用）的黄金组合：副作用没有时，缓存是安全的。</span>

## 2 惰性的惊人后果：无限数据结构

惰性让「无限列表」成为普通值：

```haskell
nats = [1..]              -- 无限自然数
evenNats = filter even nats
take 5 evenNats           -- → [2,4,6,8,10]
```

`nats` 是无限列表，但 `take 5` 只逼出前 5 个——**惰性让「定义无限」与「使用有限」优雅共存**。这不是语法糖，而是求值策略的直接结果：列表是「配方」，取前 5 个元素 = 只执行配方的一部分。

**辨析｜易错点：** 无限结构在严格语言里是死循环（`[1..]` 永不返回），在惰性语言里是普通值。**「惰性让『潜在无限』成为一等公民」**——流、生成器、事件序列都能表达为无限列表，消费方决定取多少。

## 3 惰性的代价与陷阱

惰性不是免费的：

- **空间泄漏（space leak）**：未求值的表达式积累在内存（thunk），若某值一直不用，thunk 堆积——内存占用异常。<span class="marginnote">惰性的经典陷阱：`foldl (+) 0 [1..1000000]` 在 Haskell 里会积累一百万个 thunk（空间泄漏），`foldl'`（严格版）才能线性内存。惰性 + 大列表需要「严格性控制」——Haskell 的 `seq`、`!` 注解、`foldl'` 都是「在需要时强制求值」的工具。</span>
- **性能不可预测**：求值顺序由「需要」驱动，而非书写顺序——分析复杂度更困难。
- **与副作用冲突**：惰性 + 打印/写文件的副作用 = 副作用发生时机不可预测——所以惰性语言必须是纯函数式（副作用隔离到 IO）。

**辨析｜易错点：** 惰性 ≠ 缓存一切。惰性是「用到了才求」，缓存是「求了复用」。call-by-need 两者皆有（用到了求一次、复用）；但「求值时机不可预知」让**调试困难**——`printf` 插在惰性代码里可能不触发或乱序。**「惰性语言里，副作用代码几乎无法预测」**——这是它要求纯函数的深层原因。

## 4 公式解析：惰性求值的语义

惰性可以形式化为「把表达式变成 thunk，需要时强制（force）」。设求值上下文需要值 $v$：

$$
\text{thunk}(e) = \text{未求值的 } e, \qquad \text{force}(\text{thunk}(e)) = \text{eval}(e) \text{（并缓存结果）}
$$

以 `take n xs` 为例：

$$
\text{take}\ 0\ xs = [\ ], \qquad \text{take}\ (n+1)\ (x:xs) = x : \text{take}\ n\ xs
$$

三步拆解：

- **第一步，thunk 化**：所有实参先包成 thunk（未求值）。`take 5 evenNats` 中的 `evenNats` 是 thunk——它的「求值配方」被保存而非结果。
- **第二步，按需 force**：`take` 的递归需要 `evenNats` 的头，才 force 它一次，得到「2 : 剩余」——剩余仍是 thunk。**每步只逼出所需的一个元素**。
- **第三步，共享缓存**：call-by-need 下，force 过的 thunk 记住结果——后续引用直接复用。**「惰性 = thunk 化 + 按需 force + 结果共享」**是完整的求值模型。

**辨析｜易错点：** 惰性与「非确定性」无关——纯函数下惰性不改变结果（只有性能差异）。**「惰性改变何时计算，不改变算什么」**：对纯函数程序，严格与惰性结果相同（Church-Rosser 定理）；但含副作用时结果可能不同——这正是惰性要求纯的原因。

## 5 惰性在现代语言中的渗透

- **Python**：生成器（`yield`）、`itertools`、`range`——惰性的迭代协议。
- **Rust**：迭代器默认惰性——`iter().filter().map()` 不执行，`.collect()` 才触发。
- **SQL/Spark**：查询计划惰性——`SELECT`/RDD 转换不执行，`.collect()`/`.show()` 触发。
- **JS**：`??`/`&&` 短路、函数参数默认值按需求值。<span class="marginnote">「惰性」是数据管线的普遍优化思想：Spark 把转换攒成 DAG、SQL 把查询攒成计划，最后才执行——「描述完整、执行一次」。它与函数式的「数据流」图景同构，也是大规模数据处理系统高效的原因之一。</span>

## 6 小结

- **严格求值**先算后用；**惰性求值**用到才算——「表达式是配方，不是成品」。
- 惰性的三个层次：**call-by-name**（每次重算）、**call-by-need**（算一次共享）、**短路**（跳过无用侧）。
- 惰性让**无限数据结构**成为普通值，是流式算法的表达基础。
- 代价：空间泄漏、性能不可预测、副作用不可控——所以惰性语言必是纯函数式；现代语言用生成器/迭代器/查询计划做局部渗透。
