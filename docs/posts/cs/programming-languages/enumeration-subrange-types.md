## 为什么从枚举类型开始

在类型金字塔里，用户自定义类型的第一块砖是**枚举类型（enumeration type）**：把一组有名字的常量聚成一个类型。它看似简单，却是一个重要的设计转折——此前类型都是「语言的」，从此用户有了「命名自己世界」的能力。枚举的每一步设计抉择（用什么表示、能否迭代、是否可与整数混用、能否携带数据）都映照出语言对类型安全的立场。<span class="marginnote">枚举是「类型即抽象」的最小案例：把 `0/1/2` 变成 `RED/GREEN/BLUE`，可读性暴涨、且编译器能在你写 `if (color == 42)` 时报错——只要你愿意放弃与整数的自由混用。</span>

## 1 枚举类型的基本形式

**枚举类型（enumeration type）**：用户列出所有可能取值，每个取值是一个命名的常量。

Ada 的写法是所有语言中最纯粹的：

```
type weekday is (mon, tue, wed, thu, fri, sat, sun);
```

C 系语言用 `enum`：

```c
enum weekday { MON, TUE, WED, THU, FRI, SAT, SUN };
```

默认情况下 C 把枚举常量依次赋为整数 `0, 1, 2, ...`，也可以显式指定：`enum weekday { MON = 1, TUE, ... }`。<span class="marginnote">C 的枚举「默认即整数」埋下了类型安全的漏洞：`MON == 0` 成立、`MON + 1` 也合法。Java 的 `enum` 走向另一端——每个枚举常量是独立对象，不能与整数互转。</span>

## 2 设计问题：三个分岔

**是否与整数兼容？** 这是最大的分岔。

- **弱枚举（C/C++ 传统）**：枚举值就是整数，可以参与算术、比较、互转。灵活但危险——`color + 5` 毫无意义却合法。
- **强枚举（Java、Rust、C++11 的 `enum class`）**：枚举与整数**不可隐式转换**，必须显式 `as` 或构造。类型检查把「用错枚举」提前到编译期。

**能否迭代与取值？** Ada 支持 `for d in weekday loop` 直接遍历；C 只能靠整数值循环。能否求出「下一个/上一个」（`weekday'Succ(tue)`）是 Ada 的特色能力。

**能否携带数据？** 现代函数式语言与 Rust 把枚举升级为**代数数据类型**：每个变体（variant）可以附带字段。<span class="marginnote">Rust 的 `enum Message { Quit, Move { x: i32, y: i32 }, Write(String) }` 不是「枚举常量」而是一族<strong>有形状的值</strong>——每个变体是一个不同的构造器。这是「枚举」在类型理论上的当代形态，我们在第四篇讲判别联合时会系统展开。</span>

## 3 子范围类型：给值域戴上紧箍咒

**子范围类型（subrange type）**：从一个有序类型中截取一段连续区间作为新类型。Ada 直接内建：

```
type weekdays is weekday range mon .. fri;
type small is integer range 1 .. 100;
```

子范围类型做的事有两件：

- **范围检查**：把值赋给子范围变量时，运行时检查是否越界，越界则抛异常。`small s := 200;` 在 Ada 中直接运行时错误。<span class="marginnote">这是「约束」作为类型的一部分的思想：类型不仅说「是什么」，还说「允许哪些」。子范围把「数值合法区间」这个业务规则下沉到类型系统，而非交给每个函数手写 `if` 判断。</span>
- **子类型关系**：子范围类型是其基类型的**子类型（subtype）**——任何子范围的值都能安全用于基类型的位置（赋值、传参），反过来不行。<span class="marginnote">「子类型可替换基类型」这条性质，是第五篇协变与逆变的种子：它描述的是「值集合的包含关系」对「程序位置」的影响。</span>

## 4 公式解析：子范围与类型安全

子范围类型的核心价值可以用一个等式表达：**子范围检查 = 静态的集合包含 + 动态的边界验证**。

$$
\forall\ v : \text{small},\quad v \in [1, 100] \iff \text{valid}
$$

三步拆解：

- **第一步，静态部分**：编译器知道 `small` 的值集合是 $[1,100]$ 的子集，因此在「子范围变量传给基类型参数」这类位置上**静态**放行，无需检查——集合包含关系是编译期已知事实。
- **第二步，动态部分**：运行时把任何非子范围来源的值赋给 `small` 变量时，检查 $v \in [1,100]$，失败则报错。
- **第三步，组合效果**：静态放行保性能，动态检查保正确。两者的分工恰是「能静态证明的尽量静态，不能的用运行时兜底」这一普适原则的实例。

**辨析｜易错点：** 子范围类型不是「新类型」而是「子类型」。在 Ada 里 `small` 的值可赋给 `integer` 变量，但把 `integer` 变量赋给 `small` 需要运行时检查。许多初学者把「子范围」误当成一种独立的类型——它本质是**带约束的同一类型**。这与面向对象里「子类是父类的特殊化」共享同一个子类型概念。

## 5 枚举与子范围的今天

- **Java**：`enum` 是完整的类——可带字段、方法、接口；`EnumSet` 用位向量高效表示枚举集合。
- **Rust/C++11**：强类型枚举 + 可携带数据的代数枚举；`#[repr(u8)]` 等属性控制底层表示。<span class="marginnote">枚举的底层表示对 FFI（跨语言互操作）很关键：C 枚举占 `int`，Rust 枚举若带数据则占用「最大变体 + 判别标记」，不能直接映射回 C。</span>
- **TypeScript**：字符串枚举与数字枚举并存；`union of literal types`（`type Color = "red" | "green"`）是枚举的另一种形态。
- **子范围**：主流语言内建者少，但「区间类型」「约束类型」在 F#（`1..100` 区间）、D 语言与数据库 CHECK 约束中以不同形式延续着同一思想。

## 6 枚举与业务建模：状态机视角

枚举在工程中最重要的用途是**状态机建模**——用枚举约束「一个值只能取有限几种状态」：

**状态的枚举**：订单状态 `PENDING → PAID → SHIPPED → DELIVERED`——用枚举定义所有可能状态：

```rust
enum OrderState { Pending, Paid, Shipped, Delivered }
```

**禁止非法状态**：`OrderState` 只能取这四个值——「不可能出现『第五种状态』」（不像字符串，`"paid!"`、`"PAID "` 都可能混进来）。**「枚举把『合法值集合』锁死在类型里」**——这是它相对字符串/整数状态的最大优势。

**状态转换检查**：配合 `match`（穷尽匹配），编译器强制处理每个状态——`match state { Pending => ..., Paid => ..., Shipped => ..., Delivered => ... }`——**「漏了一个状态就编译不过」**。

**辨析｜易错点：** 用**字符串/整数**表示状态是常见的反模式：`state = "paid"` 拼错成 `"paied"` 编译期不报、运行时才炸。**「凡是有穷状态集，优先枚举而非字符串」**——「让非法值不可表示」比「运行期检查非法值」可靠得多。这条原则（用类型约束状态空间）贯穿「类型驱动设计」的全部实践——枚举是它最小也最常用的一步。

## 7 小结

- **枚举类型**把命名常量聚成类型；核心设计分歧是**是否与整数兼容**与**能否携带数据**。
- 弱枚举灵活但危险，强枚举（Java/Rust）把类型安全放在第一位。
- **子范围类型**从有序类型截取区间，用**运行时检查**保证越界即报错。
- 子范围是**子类型**而非新类型，其「值集合包含 → 可替换」性质预演了第五篇的协变思想。
