## 为什么从实现方法开始

「语言」是设计，「实现」是把它变成机器能跑的东西。同一门语言可以有多种实现——C 有 GCC 与 Clang，Python 有 CPython 与 PyPy——而实现的路线直接决定了语言的速度、错误发现的时机、可移植性与调试体验。**理解实现方法，才能解释许多「为什么」**：为什么 C 程序跑得快，却要在运行前把所有错误查完？为什么 Python 能立刻给出反馈，却跑得慢？为什么 Java 号称「一次编写，到处运行」？

## 1 纯编译：一次翻译，原生执行

**编译（compilation）**：用一个叫**编译器（compiler）**的程序，把**源程序（source program）**整体翻译成**目标机器码（machine code）**，翻译完成后目标程序直接由硬件执行。GCC 编译 C：

```console
$ gcc -O2 -o hello hello.c    # 编译：源程序 → 可执行机器码
$ ./hello                     # 执行：硬件直接运行
```

编译是一条流水线，逐阶段把源程序「降级」为机器码：

1. **词法分析（lexical analysis）**：把字符流切成一个个记号（token）——关键字、标识符、运算符、字面量。
2. **语法分析（syntax analysis）**：按文法把记号流组装成**语法树（parse tree）**，回答「记号序列是否符合语法」。
3. **语义分析（semantic analysis）**：检查类型、作用域等**静态语义**，回答「语法上正确，含义上是否合法」。
4. **中间代码与优化**：生成与机器无关的中间表示，并做常数折叠、公共子表达式消除等优化。
5. **代码生成（code generation）**：把中间表示映射成目标机器的指令，同时分配寄存器与内存。

真正的 C 工具链比「编译」还要多两步：**预处理**（`#include`、`#define` 的文本展开，见第 5 节）与**链接**（linking）——编译只产出目标文件（`.o` / `.obj`），要把多个目标文件与标准库合并成最终可执行文件，还需要链接器。这一层解释了「编译快、链接慢」的工程体验，也解释了为什么改动一个头文件常常触发大面积重编译。

**优点**：执行速度快（原生机器码）；大部分错误在**编译期**就被拦截，运行时意外少。
**缺点**：编辑—编译—运行周期长；目标代码与平台绑定，跨平台要重编译；编译开销大。

## 2 纯解释：边读边执行

**纯解释（pure interpretation）**：不用先生成机器码，**解释器（interpreter）**直接读取源程序并立即执行——读一条语句，理解它，做它，再读下一条。早期 BASIC 是典型：你敲一行 `PRINT "HELLO"`，回车它就执行。<span class="marginnote">注意区分两个词：解释器（interpreter，执行解释的语言实现系统）与解释（interpretation，一种实现方法）。「解释型语言」是日常说法，严格说应是「以解释方式实现的语言」——同一门语言可以被解释，也可以被编译，见第 4 节辨析。</span>

**优点**：调试友好，出错时直接定位到出错语句；反馈即时，特别适合交互式环境；无需「编译产物」，源码即程序，天然可移植。
**缺点**：慢——每条语句每次执行都要重新「读一遍、理解一遍」；运行时才发现语法/类型错误；难以做全局优化。

## 3 混合实现：先编译成字节码，再解释/再编译

纯编译怕不灵活、纯解释怕慢，于是诞生了**混合实现（hybrid implementation）**：**先把源程序编译成一种与机器无关的中间码——字节码（bytecode），再由一个虚拟机（virtual machine）去解释或编译执行字节码。**

Java 的路线：

```console
$ javac Hello.java       # 编译：源程序 → 字节码（Hello.class）
$ java Hello             # JVM 解释/JIT 编译执行字节码
```

Python 的路线更隐蔽但本质相同：`.py` 源文件首次执行时被 CPython 编译成 `.pyc` 字节码，随后由 Python 虚拟机逐条解释执行。<span class="marginnote">Python 通常被称作「解释型语言」，但严格说 CPython 是「编译到字节码 + 解释字节码」的混合实现。真正的纯解释器在 Python 生态里几乎绝迹。</span>

**即时编译（JIT）**：混合实现的进阶。JVM 会统计哪些字节码被**反复执行（热点代码）**，把它们**在运行时编译成机器码**缓存起来——于是 Java 程序越跑越快，「冷启动慢、热启动快」的秘密就在这里。现代 JavaScript 引擎（V8）也走这条路：解析源码 → 生成字节码 → 解释执行，热点函数被 JIT 编译成机器码。PyPy 更进一步：它把整个 Python 解释器都交给 JIT 编译，长跑的程序往往比 CPython 更快——**同样的语言，换个实现，性能天差地别**。

**.NET（C#）**是同一思路的另一实现：源码被编译成中间语言（IL），再由 CLR 在运行时编译成本地代码。**「编译一次，运行到任何装有虚拟机的平台」**——这正是 Java 与 .NET 都宣称「跨平台」的机制基础。

## 4 三种路线的权衡

| 维度 | 纯编译（C） | 纯解释（早期 BASIC） | 混合实现（Java / Python） |
| --- | --- | --- | --- |
| 执行速度 | 最快 | 最慢 | 中（热点 JIT 后接近编译） |
| 错误发现时机 | 编译期（早） | 运行到才知（晚） | 编译期发现语法/类型，运行时发现逻辑 |
| 可移植性 | 差（重编译） | 好（源码即程序） | 好（字节码 + 虚拟机） |
| 调试体验 | 需要调试器 | 直接定位出错行 | 较好 |
| 典型产物 | 机器码可执行文件 | 源码 | 字节码文件（.class / .pyc） |

**辨析｜易错点：** 把「编译/解释」与「快/慢」直接划等号是常见误区。现代语言几乎都是混合实现：连传统上「纯编译」的 C 也可以有解释器（如 Cling）用于交互式教学；Python 可以用 Cython 或 Numba 编译成机器码。**「编译型语言」与「解释型语言」的标签是历史惯性，不是语言本身的属性，而是某个实现的选择。**

## 5 实现谱系的旁支：预处理、源到源翻译与 REPL

编译与解释不是实现方法的全部，谱系的边界上还站着几个重要的「旁支」。

**预处理（preprocessing）**。严格说，预处理发生在编译之前：C 的 `#include`、`#define` 等指令由预处理器先行展开，把「文本层面的替换」做完，真正的编译器才开始工作。

```c
/* hello.c 源文件 */
#include <stdio.h>              /* 预处理器将整行替换为 stdio.h 的全部内容 */
#define MAX(a, b) ((a) > (b) ? (a) : (b))

int main(void) {
    int n = MAX(3, 5);          /* 展开为 int n = ((3) > (5) ? (3) : (5)); */
    printf("%d\n", n);
    return 0;
}
```

**源到源翻译（source-to-source translation，转译）**。有些「编译器」的输出不是机器码，而是另一门高级语言——TypeScript 编译成 JavaScript、早期 C++（cfront）编译成 C、Kotlin 可以编译成 JavaScript。这类转译器（transpiler）让新语言能借用旧语言的运行时与生态，是语言推广的常用策略。

**REPL（Read-Eval-Print Loop）**。解释器的交互式形态——读入一行、求值、打印结果，再循环。Python、Ruby、Node.js 的交互式命令行都是 REPL。它把「解释」的优点发挥到极致：没有编辑-编译-运行的等待，每敲一行立即反馈，特别适合探索与教学。<span class="marginnote">REPL 与「脚本」文化紧密相连：Python 的交互式环境 + 脚本文件双模式，正是「解释式实现的即时反馈」与「文件化复用」的结合。</span>

把这三者纳入视野后，实现方法就成了一条连续的谱系：纯编译在左端，纯解释在右端，中间是被预处理、转译、字节码、JIT 层层填充的过渡带。所谓「语言是编译型还是解释型」，更多是在问「这个实现落在谱系的哪一段」。

## 6 公式解析：把编译看成函数管道

编译流水线可以用一个「函数的复合」精确表达。设源程序为 $S$，目标机器码为 $M$，五个阶段是五个函数：词法 $L$、语法 $P$、语义 $A$、优化 $O$、代码生成 $G$。于是

$$
M = G\big(\,O\big(\,A\big(\,P\big(\,L(S)\,\big)\big)\big)\big)
$$

逐项拆解：

- **第一步，从内向外读**：$L(S)$ 把源字符流变成记号流；$P$ 把记号流变成语法树；$A$ 在语法树上做类型与作用域检查；$O$ 改写中间代码使其更快；$G$ 最终产出机器码。每一层消费上一层的结果，输出恰好是下一层的输入——这正是「管道（pipeline）」。
- **第二步，读复合的代价**：任一阶段报错，整个复合式失败——所以编译错误的信息必然追溯到具体阶段（「第 3 行语法错误」来自 $P$，「类型不匹配」来自 $A$）。这解释了为什么编译器报错能如此精确。
- **第三步，读它与解释的对比**：解释执行可以写成 $\text{Exec}\big(S, \text{输入}\big)$——解释器每次运行都把「理解源程序」这一步现场重做；编译则把「理解」提前、一次完成，运行时只剩机器码的直接执行。**两者的本质差别，是「翻译一次、执行多次」与「边翻译边执行」的分工。**

## 7 小结

- 三种实现路线：**纯编译**（整体翻译成机器码）、**纯解释**（边读边执行）、**混合实现**（编译成字节码 + 虚拟机解释/JIT）。
- 编译是一条五阶段流水线：**词法 → 语法 → 语义 → 优化 → 代码生成**，可用函数复合 $M = G(O(A(P(L(S)))))$ 精确表达。
- **JIT** 在运行时把热点字节码编译成机器码，是 Java、JavaScript 高性能的秘密。
- **易错点**：「编译型/解释型」是实现的属性而非语言的属性；现代语言几乎都是混合实现。
