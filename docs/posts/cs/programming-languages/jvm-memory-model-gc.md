## 为什么从 JVM 内存模型开始

上一节看了 JVM 的执行机制；这一节看它的**内存管理**——两个系统：**内存模型（memory model）**——运行时内存如何分区（栈、堆、元空间）；**垃圾回收器体系（GC system）**——堆内存如何回收（分代、多种 GC 算法）。JVM 的 GC 是工业界最成熟的：从 Serial 到 CMS、G1、ZGC——一部「如何让回收更快、停顿更短」的演进史。理解 JVM 内存模型与 GC，是调优 Java 应用（内存、停顿、吞吐）的前提，也是「追踪式回收」理论在工业的完整落地。<span class="marginnote">JVM 内存分区一句话：<strong>线程私有区（虚拟机栈、程序计数器）随线程生死，线程共享区（堆、元空间）随应用生死</strong>。堆是 GC 的主战场（几乎一切对象都在这）；「栈管运行，堆管存储」——Java 的运行时内存就是这两大部分。</span>

## 1 JVM 内存区域

**运行时数据区（runtime data area）**按线程私有/共享划分：

**线程私有**：

- **程序计数器（PC）**：当前执行指令地址——线程切换恢复现场用。
- **虚拟机栈（JVM stack）**：方法调用的栈帧——局部变量、操作数栈、返回地址。**栈溢出（StackOverflowError）**发生在这里。
- **本地方法栈**：native 方法的栈。

**线程共享**：

- **堆（heap）**：几乎所有对象实例——**GC 的主战场**。
- **方法区 / 元空间（metaspace）**：类元数据、常量池、静态变量——Java 8 起从堆分离到本地内存（元空间）。<span class="marginnote">「元空间（metaspace）」是 Java 8 的改动：原来「永久代（PermGen）」在堆里（大小固定、易 OOM），现在元空间用<strong>本地内存</strong>（大小受物理内存限制）——「类元数据不再占用堆，堆给对象用」。`OutOfMemoryError` 的两大来源：堆不够（对象多）与元空间不够（类多）。</span>

## 2 堆的分代与对象生命周期

JVM 堆按「年龄」**分代**（回顾分代回收）：

```
堆:
┌──────────────┬─────────────────────────┐
│  新生代      │       老年代            │
│ Eden + 2×Survivor │                    │
└──────────────┴─────────────────────────┘
```

- **新生代（young）**：新对象先进 `Eden`；Minor GC（新生代回收）把存活对象复制到 `Survivor`；幸存 N 次晋升老年代。
- **老年代（old）**：长寿对象；Major/Full GC 回收——少发生但耗时长。

**对象分配**：优先 Eden → 幸存者 → 老年代——「对象越年轻，回收越频繁（复制式）」。<span class="marginnote">分代的设计依据是<strong>弱分代假说</strong>：大多数对象早死（`new` 的临时对象很快不可达）。新生代用「复制式回收」——只搬幸存者（少），快；老年代用「标记-压缩」——活对象多不搬，偶尔整理。「分而治之」让 GC 成本与「存活对象数」而非「堆大小」挂钩。</span>

## 3 GC 算法的演进：从停顿到并发

JVM 的 GC 器谱系（按停顿时间演进）：

| GC | 时代 | 策略 | 停顿 |
| --- | --- | --- | --- |
| Serial | 单线程 | 复制 + 标记压缩 | 全 STW |
| Parallel | 多线程 | 并行回收 | 全 STW（吞吐优先） |
| CMS | 并发标记 | 并发标记清除 | 低停顿（碎片） |
| G1 | 分区域 | 区域化 + 并发 | 可预测停顿 |
| ZGC/Shenandoah | 超低停顿 | 染色指针/读屏障 | 毫秒级 |

**G1（Garbage First）**是当前默认：把堆分成**区域（region）**，优先回收「垃圾最多」的区域——**停顿可预测**（`-XX:MaxGCPauseMillis` 目标）。<span class="marginnote">G1 的「Garbage First」：把堆切成许多小区域（region），每区域独立管理——GC 时<strong>只回收垃圾最多的区域</strong>，而非全堆。「停顿可预测」让 GC 目标从「尽量快」变成「给定时间内回收最多垃圾」——对延迟敏感服务（交易、推荐、AI 推理后端）至关重要。ZGC 更进一步，用染色指针做到「停顿不随堆大小增长」。</span>

## 4 公式解析：GC 停顿的权衡

GC 的调优本质是「**吞吐 vs 停顿**」的权衡。设总运行时间 $T$、GC 时间 $G$：

$$
\text{吞吐量（throughput）} = \frac{T - G}{T} \quad \text{（越接近 1 越好）}
$$

$$
\text{停顿（pause）} = \max(\text{单次 GC 时间}) \quad \text{（越小越平稳）}
$$

三步拆解：

- **第一步，吞吐**：吞吐 = 应用干活时间占比——GC 时间越少，吞吐越高。**Parallel 优化吞吐**（GC 一次干完，总时间少）。
- **第二步，停顿**：停顿 = 单次最长的「暂停应用」——影响响应延迟。**G1/ZGC 优化停顿**（把大停顿拆小，但 GC 总时间可能更长）。
- **第三步，看取舍**：**吞吐与停顿不可兼得**——「GC 干得少」吞吐高但单次可能久；「GC 干得碎」停顿低但总开销大。**「选 GC = 选吞吐还是选停顿」**——批处理要吞吐（Parallel），在线服务要停顿（G1/ZGC）。

**辨析｜易错点：** 「Full GC」不是「必然发生」——它只在老年代满、元空间满或显式 `System.gc()` 时触发。**Full GC 通常停顿最长**（标记-压缩全堆）——调优目标是「减少 Full GC 频率」（调堆大小、修泄漏）。**「GC 调优不是让 GC 不跑，而是让 GC 跑得恰如其分」**——太多（停顿多）、太少（内存压力/OOM）都不对。

## 5 内存泄漏与调优实践

- **内存泄漏**：Java 有 GC 但仍可能泄漏——「对象被无意的引用保持」（静态集合存对象、监听器未移除、缓存未清理）——GC 认为可达，实际无用。`OutOfMemoryError` 的前兆。
- **调优工具**：`jmap`/`jstat`/MAT/VisualVM——看堆占用、GC 频率、对象分布。
- **关键参数**：`-Xms`/`-Xmx`（堆大小）、`-XX:+UseG1GC`、`-XX:MaxGCPauseMillis`（停顿目标）。
- **现代实践**：默认 G1 + 合理堆大小 + 监控 GC 日志——「大多数应用无需深度调优，只需监控 + 防泄漏」。<span class="marginnote">「Java 内存泄漏」的典型：全局 `static Map` 不断加条目、未注销的事件监听器、`ThreadLocal` 没清理、缓存无限增长。GC 管「不可达」，管不了「可达但无用」——「泄漏 = 引用该断没断」。调优的起点是「先确认不是泄漏，再谈 GC 参数」——参数救不了泄漏。</span>

## 6 内存溢出的常见场景与排查

JVM 的 `OutOfMemoryError`（OOM）是生产事故的常客——识别场景是排查的第一步：

**堆溢出（`Java heap space`）**：对象太多/太大——内存泄漏（引用该断没断）或堆太小。排查：堆转储（`-XX:+HeapDumpOnOutOfMemoryError`）+ MAT 分析「谁占着对象」。

**元空间溢出（`Metaspace`）**：类太多（动态生成类、反射加载）——元空间不够。排查：减少动态类、增大 `-XX:MaxMetaspaceSize`。

**栈溢出（`StackOverflowError`）**：递归无限/嵌套太深——不是 OOM 而是「栈满」。排查：找无限递归。

**直接内存溢出（`Direct buffer memory`）**：NIO 的 `DirectByteBuffer` 用满——不受堆管理。

| 溢出 | 症状信息 | 主因 |
| --- | --- | --- |
| 堆 | `Java heap space` | 泄漏 / 堆小 |
| 元空间 | `Metaspace` | 类太多 |
| 栈 | `StackOverflowError` | 无限递归 |
| 直接内存 | `Direct buffer memory` | NIO 用尽 |

**辨析｜易错点：** **「OOM 不都是泄漏」**——也可能是「堆太小」「对象确实多」「一次性加载大文件」。排查顺序：**先看是不是泄漏**（MAT 分析可达性）→ 不是泄漏再看堆大小是否合理 → 最后考虑优化对象结构。**「先确诊再调参」**：盲目 `-Xmx` 调大堆，可能掩盖泄漏、或导致 GC 停顿更久。「OOM 是结果，原因是设计问题（泄漏）或容量问题（配置）——两种修法不同」。

## 7 小结

- **JVM 内存分区**：线程私有（PC、虚拟机栈、本地方法栈）+ 线程共享（堆、元空间）——栈管运行、堆管存储。
- **分代堆**：新生代（Eden + Survivor，复制回收）+ 老年代（标记压缩）——弱分代假说的工业落地。
- **GC 演进**：Serial → Parallel（吞吐）→ CMS/G1（停顿可预测）→ ZGC（毫秒级）——「停顿随堆增长」被逐步打破。
- GC 调优 = 吞吐 vs 停顿的权衡；Full GC 要减频；「泄漏靠修引用，参数靠监控」——先防泄漏再调参。
