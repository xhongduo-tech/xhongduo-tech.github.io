## 为什么从形式化语义开始

语法描述让编译器知道「什么串是合法程序」，属性文法补上了「类型对不对」。但还有一个更根本的问题悬而未决：**一个程序「做」了什么？** 我们通常依赖直觉——读一读代码，凭经验猜它打印什么。可一旦程序复杂起来（并发、指针别名、异常），直觉就会失效。**形式化语义（formal semantics）**要把「程序的含义」变成精确的数学对象，从而能够证明、能够比较、能够推理。这是 PLT（程序设计语言理论）的学术心脏，也是后续操作语义、指称语义、公理语义三大家族的共同入口。<span class="marginnote">对大多数工程师而言，形式化语义最实际的回报是：当你理解了三种语义框架，编译器手册里那些「未定义行为」条款、语言标准里晦涩的措辞，都变得可验证而非可争论。</span>

## 1 为什么自然语言描述不够

程序设计语言标准通常用**自然语言**描述语义，例如 C 标准说「两个 unsigned int 相加的结果按模 `$2`^{32}$ 取余」。自然语言有三个致命弱点：

**歧义**：一句话可以有两种读法，编译器实现者可能各取所需；
**不完备**：标准无法穷举所有边界情形，于是留下「未定义行为」的灰色地带；
**不可证明**：没法用数学推理「这段代码一定满足某性质」。

**形式化语义的动机**：把语义写成数学对象，让「程序的含义」参与数学推导，进而支撑**程序验证（program verification）**、**编译器正确性**与**语言设计的前置分析**。<span class="marginnote">今天「用形式化方法验证编译器」已从理论走向实践：CompCert 是用机器证明过的 C 编译器，其核心就是给 C 的操作语义与目标汇编语义之间建立严格的等价关系。</span>

## 2 语义的三种视角：一座三角架

三种主流形式化语义分别从三个角度回答「程序意味着什么」：

**操作语义（operational semantics）**：程序意味着「如何在状态机上一步步执行」。它给出一个抽象机器，描述每条语句怎样改变机器状态。<span class="marginnote">最贴近「程序会怎么跑」的直觉，也最容易在解释器中直接实现——Python 官方解释器本质上就是 C 语言写的一个操作语义引擎。</span>

**指称语义（denotational semantics）**：程序意味着「它映射到的数学函数」。每条程序片段被翻译成一个数学对象（通常是函数），语言的语义就是把程序翻译成这些数学对象的**指称函数**。<span class="marginnote">最抽象、最接近纯数学，适合证明「两个程序是否等价」——因为它们被映射成同一个数学函数当且仅当行为相同。</span>

**公理语义（axiomatic semantics）**：程序意味着「它支持哪些断言推理」。它不管程序怎么执行，只给出规则，让你从「执行前成立的前置条件」推出「执行后成立的后置条件」。<span class="marginnote">公理语义不是为了实现语言，而是为了<strong>证明程序的性质</strong>——它回答的是「能否证明程序正确」，而非「程序怎样运行」。</span>

## 3 三者的适用场景对照

| 维度 | 操作语义 | 指称语义 | 公理语义 |
| --- | --- | --- | --- |
| 核心问题 | 程序如何执行 | 程序表示什么函数 | 程序满足什么性质 |
| 数学对象 | 抽象状态机 | 数学函数 | 逻辑断言 |
| 主要用途 | 实现解释器、定义语言 | 程序等价、语义研究 | 程序验证、Hoare 逻辑 |
| 难度入口 | 最直观 | 需处理递归定义的良基性 | 需处理循环不变式 |
| 代表作 | 结构化操作语义（SOS） | Scott 域论 | Hoare 逻辑 |

**辨析｜易错点：** 初学者常以为「三种语义是三种对立的说法」。实际上它们描述**同一个**程序的不同投影，且在良好设计下相互一致：一个语言的操作语义与指称语义应当「匹配」（程序在这两种语义下行为相同），公理语义的规则应当被操作语义「成立」（每条推理规则确实保真）。三者互为校验，构成一个整体。

## 4 公式解析：语义的映射结构

三种语义的共同骨架可以用同一个公式概括——**语义函数把「语法」映射到「语义域」**：

$$
\llbracket \cdot \rrbracket : \text{Program} \to \text{SemanticDomain}
$$

三步拆解这条式子：

- **第一步，读记号**：$\llbracket P \rrbracket$ 读作「程序 $P$ 的语义」或「$P$ 的指称」。双括号表示「我们说的不是这个符号串本身，而是它的含义」。
- **第二步，看方向**：箭头的左边是语法对象（程序文本），右边是语义域。语义域随框架而变——操作语义里它是一组「状态转移」，指称语义里它是「状态函数 $State \to State$」，公理语义里它是「断言集合」。
- **第三步，看作用**：这个映射必须是**组合的（compositional）**——即 $P = P_1; P_2$ 的语义由 $P_1$ 与 $P_2$ 的语义组合而来，而不必重新看一遍 $P$ 的全部文本。组合性是形式语义与「字符串匹配」的根本区别，也是它能用于规模推理的原因。

**辨析｜易错点：** 写 $\llbracket P \rrbracket$ 时，$P$ 是**程序文本**而非程序的输出。初学者常把「语义」混同于「运行结果」；实际上语义是文本到数学对象的**函数**，运行结果只是该对象在具体输入下的值。区分「函数的定义」与「函数在某点的取值」，是进入形式语义的第一课。

## 5 一个例子的三种视角

用一个最小的例子「把 x 加 1 再赋回 x」（即 `x = x + 1`）看三种语义如何各说各话：

**操作语义**：给出转移规则——状态 $\sigma$ 下，先求 $x+1$ 得 $v$，新状态中 $x$ 指向 $v$：$\langle x = x+1, \sigma \rangle \Rightarrow \sigma[x \mapsto \sigma(x)+1]$。它描述了「怎么一步步执行」。

**指称语义**：给出状态函数——$\llbracket x = x+1 \rrbracket = \lambda \sigma.\ \sigma[x \mapsto \sigma(x)+1]$。它说「这条语句是一个状态变换函数」，不关心步骤。

**公理语义**：给出断言规则——对任何后置条件 $Q$，赋值公理给出 $\{Q[(x+1)/x]\}\ x = x+1\ \{Q\}$。它说「这条语句把『关于新值的断言』转成『关于旧值的断言』」。

三个视角描述的**是同一个程序**：操作语义看「轨迹」、指称语义看「函数」、公理语义看「断言」——但三者在这个例子上给出的结论**完全一致**（$x$ 的新值都是 $\sigma(x)+1$）。**「三种语义是同一枚硬币的三个面」**——这就是上一节「相互校验」的具体例证。

## 6 形式语义的价值边界

形式语义如此强大，但也要知道它**不做什么**——避免「形式化万能」的误解：

**它验证「程序符合规格」，不保证「规格符合需求」**：公理语义能证明「程序满足前置/后置条件」，但「这个规格是不是用户真正想要的」是需求工程问题，语义学管不了。

**它针对「语言语义」，不覆盖「实现细节」**：操作语义给的是「抽象机器的行为」，真实实现的性能、资源、并发时序不在语义范围内。「语义对了」不等于「实现高效」。

**它适合「小而关键」的核心，不适合「整个大系统」**：对一个排序函数做形式验证是可行的；对一个百万行的企业系统做完整形式验证，成本仍不可接受。**「形式语义用在小而关键处（协议、核心算法、语言定义），而非处处都用」**。

| 语义能 | 语义不能 |
| --- | --- |
| 证明程序符合规格 | 保证规格符合需求 |
| 定义语言含义 | 保证实现高效 |
| 验证核心算法 | 覆盖整个大系统 |

**辨析｜易错点：** 「有形式语义 = 程序一定正确」是过度承诺。形式语义提供的是**「在给定规格下可证明正确」**的能力——规格本身的正确性、实现的正确性（编译/运行）、以及「证明没有写错」都仍是人工环节。**「形式化提高正确性的概率与可检验性，不消灭错误的可能」**——它是强大的工具，不是魔法。

## 8 小结

- 自然语言语义的三大缺陷是**歧义、不完备、不可证明**，形式化语义逐一克服。
- 三大语义家族：**操作语义**（如何执行）、**指称语义**（是什么函数）、**公理语义**（满足什么性质）。
- 三种语义同指一个程序、**相互校验**，并非对立学说。
- 核心记号是语义映射 $\llbracket \cdot \rrbracket$，它必须是**组合的**，才能支撑规模化推理与程序验证。

在下一节，我们将深入三大家族的第一支：**操作语义**——看它如何用一台抽象状态机，把「执行」本身写成严格的数学。
