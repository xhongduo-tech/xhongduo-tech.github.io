## 为什么从数据类型开始

一台计算机的存储里只有 0 和 1，可程序员写的却是「整数、字符串、日期、订单」。这中间靠的正是**数据类型（data type）**：给一段比特加上「如何解释、支持哪些运算」的契约。**数据类型**：一个数据对象的**集合**，连同作用于该集合成员的**运算**，以及在存储中的**表示方式**。<span class="marginnote">三个成分缺一不可：类型不只是值的集合，还携带运算与表示。「同样是 32 位」——当它是 `int` 就做整数加法，当它是 `float` 就做浮点加法，当它是地址就做指针运算——含义完全不同。</span>而**类型检查（type checking）**，是语言防止「把类型 A 的值当类型 B 用」这道安全网的织法，它决定了程序里的错误是在编译期被抓住、还是在运行期突然爆炸。

## 1 类型的三副面孔

**值的集合**：类型界定「哪些值合法」。`bool` 只有 `true`/`false`；`signed char` 只有 $[-128, 127]$ 的 256 个整数。<span class="marginnote">超出集合的值不是「非法输入」而是「无法表示」——这就是整数溢出发生的根源：运算结果不属于结果类型的集合，语言只能截断或报错。</span>

**运算的集合**：类型决定「能做什么」。字符串可以做拼接 `+`、求长度 `.length`，却不能做除法 `/`。类型检查的实质，就是验证「这个运算作用于这些操作数是否合法」。

**值的表示**：类型决定「如何在存储中编码」。同数值 `65`，作为 `char` 是 ASCII 的 `'A'`，作为 `int` 是整数六十五。表示方式不同，同样的比特串读出不同意义。

## 2 类型错误与类型检查器

**类型错误（type error）**：程序执行中，运算被施加到不合适的类型的值上，如 `"hello" - 5`。**类型检查器（type checker）**的目标就是「尽量早地发现类型错误」。

类型检查的时机分两派：

**静态类型检查（static type checking）**：在编译期完成。检查器读取每个表达式的类型，若发现类型错误，程序**根本不编译**。<span class="marginnote">静态检查的哲学是「错误的程序不该有机会运行」。代价是表达力受限——某些合法但「类型难表达」的程序会被误杀。</span>

**动态类型检查（dynamic type checking）**：在运行期完成。执行到该运算时再检查操作数类型，不对则抛异常。<span class="marginnote">动态检查的哲学是「能跑就跑，错在出错时暴露」。代价是错误发现晚、且类型错误只在特定路径执行时才会暴露——测试覆盖不到的路径可能藏着定时炸弹。</span>

## 3 类型检查的核心问题：何时检查

一个程序里处处是类型信息的流动，检查器要回答三个时间问题：

| 问题 | 答案的分类 | 例子 |
| --- | --- | --- |
| 检查发生在何时？ | 编译期（静态）或运行期（动态） | Java 在编译期查类型，Python 在运行期 |
| 变量有无固定类型？ | 类型绑定在声明时固定，或随赋值变化 | C 的变量类型固定，Python 的变量「只是名字」 |
| 何时做类型推导？ | 显式注解或由编译器推导 | Java 要写类型注解，Haskell 几乎全靠推导 |

这三问合起来决定了一门语言的「类型气质」。<span class="marginnote">把三问交叉起来想：C 是「编译期 + 固定 + 显式」，Python 是「运行期 + 不固定 + 无注解」，Haskell 是「编译期 + 固定 + 推导」。这不是巧合——三者的选择互相咬合，形成不同的设计哲学。</span>

## 4 公式解析：类型检查的推导规则

类型检查可以像语义学那样写成推理规则。类型环境（type environment）$\Gamma$ 是一个「变量 → 类型」的映射，判断「在环境 $\Gamma$ 下，表达式 $e$ 具有类型 $\tau$」写作：

$$
\Gamma \vdash e : \tau
$$

读作「$\Gamma$ 派生（proves）$e$ 的类型为 $\tau$」。三条基本规则：

$$
\frac{}{\Gamma \vdash n : \text{int}}, \qquad
\frac{\Gamma(x) = \tau}{\Gamma \vdash x : \tau}, \qquad
\frac{\Gamma \vdash e_1 : \tau_1 \quad \Gamma \vdash e_2 : \tau_2 \quad \tau_1 = \tau_2}{\Gamma \vdash e_1 + e_2 : \tau_1}
$$

三步拆解：

- **第一步，认识符号**：$\vdash$（读作「派生」或「推出」）把「已知的类型环境」与「要证明的类型命题」分开。左侧是前提，右侧是结论。
- **第二步，读第一条**：字面量 $n$ 无需任何前提就具有类型 `int`——横线上方为空，表示这是**公理**，无条件成立。
- **第三步，读第三条**：要证明 $e_1 + e_2$ 是类型 $\tau_1$，须先证 $e_1, e_2$ 分别有类型 $\tau_1, \tau_2$ 且两者相等。**类型检查器不过是在机械地应用这些规则**——从上到下递归地构建类型推导树，叶子都是公理。这正是 Hindley-Milner 类型推导（第五篇）的雏形。

**辨析｜易错点：** 「类型检查」与「类型推导」不是一回事。**检查（checking）**是在类型已标注的前提下验证一致性；**推导（inference）**是在没有任何标注时，由表达式的形状自动求出类型。C 语言大体是检查，Haskell/SML 则是推导。混淆二者是常见误区。

## 5 类型检查的实例：一个推导树

把第 4 节的推理规则用起来，完整推导 `2 + 3` 的类型（环境 $\Gamma$ 为空）：

$$
\frac{
\frac{}{\Gamma \vdash 2 : \text{int}} \quad
\frac{}{\Gamma \vdash 3 : \text{int}} \quad
\text{int} = \text{int}
}{
\Gamma \vdash 2 + 3 : \text{int}
}
$$

这是一棵**类型推导树（typing derivation tree）**：叶子是公理（字面量 2、3 有类型 `int`），内部节点应用规则（加法规则），根是结论（`int`）。类型检查器的工作，就是**尝试构建这样一棵树**——能建成就通过，建不成（某处类型不匹配）就报错。

再看一个**会失败**的例子 `2 + "a"`：加法规则要求两个操作数类型相同，但 `"a"` 的类型是 `String`，`int ≠ String`——树建不到根，类型错误。**「类型检查 = 尝试构建类型推导树」**——这是理解一切类型检查器（Java、Haskell、Rust 的编译器）的统一视角。

## 6 类型的价值：从错误预防到文档

- **提前抓错**：静态类型把大量低级错误从「深夜线上事故」变成「编译器的红色报错」。
- **契约与文档**：类型签名本身就是最准确的文档——签名即规格。<span class="marginnote">类型签名比注释可靠：注释会过时，编译器会强制签名与实现一致。类型是「机器可检查的文档」。</span>
- **优化的基础**：类型告诉编译器值的宽度与运算语义，是寄存器分配、指令选择的前提。
- **抽象的依据**：类型系统是后面「泛型」「接口」「ADT」一切抽象构造的地基——没有类型，无法谈论「一批类型共同的运算」。

## 7 小结

- **类型** = 值的集合 + 运算 + 表示；类型检查验证「运算作用于合法类型」。
- 类型错误分**静态**（编译期发现）与**动态**（运行期发现）；三问（何时查、变量固定否、推导或标注）决定类型气质。
- 类型检查器的工作 = **构建类型推导树**：$\Gamma \vdash e : \tau$ 的规则集。
- 类型的价值：**提前抓错、契约文档、优化基础、抽象地基**——「机器可检查的文档」。
