## 为什么从动态绑定开始

继承让子类可以**重写（override）**父类方法；但「`animal.speak()` 到底调用哪个实现」——父类声明处的那个，还是子类重写的那个？答案取决于**绑定（binding）**：若在**编译期**按静态类型绑定（静态绑定），永远调父类的；若在**运行期**按对象实际类型绑定（动态绑定），调用子类的。**动态绑定（dynamic binding）**是子类型多态（第五篇）在运行时的实现机制，也是 OOP「消息多态性」的引擎。这一节把它讲透：虚表怎么工作、为什么需要它、以及「消息的多态性」如何让同一行代码在不同对象上表现不同。<span class="marginnote">动态绑定的必要性：`Animal a = new Dog(); a.speak();` 编译期只知道 `a` 的静态类型是 `Animal`，但 `a` 实际指向 `Dog`——要调 `Dog.speak()`，只能在运行时「看 a 到底是谁」再决定。这就是「运行时查类型」的动态绑定。</span>

## 1 静态绑定 vs 动态绑定

**静态绑定（static binding）**：方法调用在**编译期**确定——按变量的静态类型决定调用哪个实现。

```java
Animal a = new Dog();
a.speak();   /* 静态类型 Animal：若静态绑定，调用 Animal.speak() */
```

**动态绑定（dynamic binding）**：方法调用在**运行期**确定——按对象的**实际类型**决定调用哪个实现。C++/Java 的**虚方法（virtual method）**、Python 的全部方法、Smalltalk 的全部消息都走动态绑定。<span class="marginnote">关键区分：<strong>静态类型</strong>（声明时的类型，编译期可知）vs <strong>动态类型</strong>（对象运行时的实际类型）。动态绑定 = 按动态类型选实现。C++ 里只有 `virtual` 方法才动态绑定，非虚方法静态绑定——「哪些方法多态」是语言设计决策。</span>

## 2 虚表：动态绑定的实现

动态绑定的标准实现是**虚方法表（virtual method table, vtable）**：每个类有一张「方法指针表」，对象里存一个指向其类的虚表的指针。

```
Dog 对象                  Dog 类虚表
+----------+             +-------------+
| vptr ────────→          | speak → Dog::speak |
| 字段...  |             | fetch → Dog::fetch |
+----------+             +-------------+
```

调用 `a.speak()`：运行时沿 `a` 的 `vptr` 找到 `Dog` 的虚表，取 `speak` 槽位的函数指针，调用它——**一次指针间接寻址**。<span class="marginnote">虚表的代价：每次虚调用多一次间接寻址（表查找），且对象多一个 `vptr` 字段（空间开销）。非虚调用无此开销——这就是「虚 vs 非虚」的性能差异来源。C++ 默认非虚、显式 `virtual`，正是「零开销原则」的体现：不为不需要的多态付代价。</span>

## 3 消息的多态性：同一消息，多种回应

**消息的多态性（polymorphism）**：不同对象对**同一消息**给出**各自**的响应——因为每个对象按自己的类决定实现。

```java
List<Animal> zoo = List.of(new Dog(), new Cat());
for (Animal a : zoo) a.speak();   /* Dog 汪汪，Cat 喵喵 */
```

这段代码只有一行 `a.speak()`，但运行结果随元素实际类型而变——**「一行代码，多种行为」正是多态性的定义**。它让「面向接口编程」成为可能：代码只依赖 `Animal` 的契约，却能驱动任意子类的行为。<span class="marginnote">消息多态性把「控制反转」带进方法调用：调用者只发送消息，不决定实现——「谁接收，谁决定」。这为框架设计奠基：框架定义接口、调用消息，插件提供实现。Java 的 `Listener`、C++ 的虚析构函数、Smalltalk 的整全消息模型都是它的应用。</span>

## 4 公式解析：动态分派的语义

动态绑定可以形式化为「按动态类型查表」：

$$
\text{dispatch}(m, o) = \text{vtable}(\text{dynamic-type}(o))[m]
$$

调用消息 $m$ 的完整语义：

$$
\text{call}(m, o, a_1, \dots, a_k) = \big(\text{vtable}(\text{dynamic-type}(o))[m]\big)(o, a_1, \dots, a_k)
$$

三步拆解：

- **第一步，找动态类型**：`dynamic-type(o)` 是对象 `o` 的**运行时实际类型**——不是静态类型，是 `new` 出来的那个类。
- **第二步，查虚表**：`vtable(dynamic-type(o))[m]` 从该类型的虚表取 `m` 槽位——子类重写过的槽位已指向子类实现。
- **第三步，带 self 调用**：方法调用把对象本身作为第一个参数（`this`/`self`）传入——方法内能访问接收者的状态。**「动态类型 + 虚表 + self」三条合起来，就是消息分派的全部**。

**辨析｜易错点：** 构造器里的虚调用陷阱：C++/Java 在**构造器内调用虚方法**时，动态类型是「当前正在构造的类」——若子类尚未构造完，可能调到「字段还没初始化」的子类方法。**「构造期间不要调用可重写方法」**是 OO 设计的著名戒律（Effective Java 第 19 条），源自动态绑定与构造顺序的相互作用。

## 5 动态绑定与语言设计

- **C++**：`virtual` 显式声明——默认静态绑定，虚方法才动态绑定（零开销原则）。
- **Java**：方法默认动态绑定；`final` 方法/类禁止重写（静态绑定优化）。
- **Python**：一切方法动态绑定——高度灵活，代价是性能与可静态分析性低。
- **Rust**：无继承；`dyn Trait` 提供「运行时分派」（虚表式），`impl Trait`/泛型提供「静态分派」（单态化）——**两种分派显式选择**。<span class="marginnote">Rust 把「静态 vs 动态分派」变成显式选择：泛型（单态化）静态分派、`dyn Trait`（虚表）动态分派。这是「零成本抽象」哲学的延伸——用什么分派、付什么代价，由程序员明说。</span>

## 6 动态绑定的经典应用与反模式

动态绑定是 OO 的引擎，但用得好与不好差别巨大：

**好应用——策略模式**：一组算法（`Comparator`、`Strategy`）通过接口 + 动态绑定互换——`Collections.sort(list, comparator)` 中 `comparator` 的 `compare` 动态分派，排序算法与比较策略解耦。

**好应用——模板方法**：父类定义骨架（非虚方法），钩子方法（虚方法）由子类实现——框架的「留给子类填空」模式。

**反模式——自用（self-use）陷阱**：父类构造函数或方法内部调用虚方法，子类重写后行为出人意料——「构造期间虚调用」前面已警告，方法内部的自用虚调用同样要小心。

**反模式——脆弱的基类（fragile base class）**：基类的「小改动」因动态绑定影响所有子类——改一个虚方法的实现，所有重写它的子类行为都变。**「继承 + 动态绑定 = 基类与子类的紧密耦合」**。

**辨析｜易错点：** 动态绑定让「读代码」变难：`a.speak()` 编译期不知道调哪个实现，要「跳到运行时类型」看——**「动态绑定的代价是可读性与静态分析的损失」**。IDE 的「查找实现」缓解了它，但「方法调用与实现的关系不静态可见」仍是 OO 的固有成本。「静态语言 + 动态绑定」是「类型检查的静态 + 行为选择的动态」的混合——理解这个混合，就理解了 OO 的威力与脆弱。

## 8 小结

- **静态绑定**编译期按静态类型选实现；**动态绑定**运行期按对象实际类型选实现。
- 虚表（vtable）是动态绑定的标准实现：对象带 `vptr`，调用经一次间接寻址。
- **消息的多态性** = 同一消息、不同对象各自响应——「一行代码，多种行为」。
- 分派公式：`dispatch(m,o) = vtable(dynamic-type(o))[m]`；构造期内避免虚调用是著名戒律。
