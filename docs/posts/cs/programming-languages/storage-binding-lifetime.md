## 为什么从存储绑定开始

作用域回答「名字在哪可见」，这一节回答「存储从哪来、到哪去」——**存储绑定（storage binding）**与**生存期（lifetime）**。变量的地址何时被分配（绑定）、何时被回收（解绑），决定了一个变量的「寿命」。这个看似底层的机制，正是栈帧、堆分配、垃圾回收、所有权这些大话题的统一入口：所谓「变量的生存期」，就是它绑定的存储从分配到释放的时间区间。<span class="marginnote">作用域是<strong>空间</strong>概念（名字在哪可见），生存期是<strong>时间</strong>概念（存储何时有效）。两者经常重合（局部变量「出了作用域即死」）但不必然——闭包捕获的变量出了作用域仍活着，静态变量与作用域无关地长命。理解这对「时空」概念的分合，是内存模型的地基。</span>

## 1 变量的四类生存期

按存储绑定方式，变量分为四类：

**静态变量（static variable）**：存储在整个程序运行期间存在。C 的全局变量、`static` 局部变量在**程序启动前**绑定存储，程序结束才解绑。生存期 = 整个程序。<span class="marginnote">静态变量的存储是「编译期可确定」的——通常放在可执行文件的 BSS/数据段。正因为地址固定，静态变量是「跨函数保持状态」的最简单手段（如计数器），但也带来线程安全问题。</span>

**栈变量（stack variable）**：存储绑定在进入块/函数时分配，离开时释放。局部变量默认走这条路径，生存期 = 所在的执行块。

**堆变量（heap variable）**：存储由显式分配（C 的 `malloc`、Java 的 `new`）或语言机制创建，释放靠手动 `free`、垃圾回收或所有权。

**显式堆变量 vs 隐式堆变量**：C 的 `malloc` 是显式；Java `new` 创建的对象由 GC 自动回收（隐式）。

## 2 生存期与作用域的四种组合

塞贝斯塔指出，作用域与生存期可以正交组合，产生四种截然不同的变量「性格」：

| 组合 | 例子 | 行为 |
| --- | --- | --- |
| 作用域局部 + 生存期局部 | C 局部变量 | 离开块即失效，最常见 |
| 作用域局部 + 生存期长 | C 的 `static` 局部变量 | 名字只在块内可见，但存储跨调用存活 |
| 作用域全局 + 生存期全局 | C 全局变量 | 处处可见、全程存活 |
| 作用域全局 + 生存期局部 | （少见） | 名字全可见但存储可能已失效——通常是 bug |

<span class="marginnote">「作用域局部 + 生存期长」的 `static` 局部变量是隐藏的状态：`counter` 每次调用都递增，但 `counter` 在函数外不可见。它是「函数级全局状态」，解释了为什么静态局部变量在并发下要加锁。</span>

## 3 存储分配与释放的机制

**栈分配（stack allocation）**：进入块/函数，栈指针下移分配帧；退出时上移释放。顺序、高效（一条加减指令）、**后进先出**。<span class="marginnote">栈的 LIFO 特性决定了它只能放「生存期严格嵌套」的变量——先入者后出。递归调用正是靠栈帧嵌套实现的。栈分配是 C/C++/Rust 局部变量的默认机制，几乎零开销。</span>

**堆分配（heap allocation）**：在堆上找空闲块分配，任意顺序分配与释放。灵活但需要管理：手动释放（C）、GC（Java/Python）、所有权（Rust）三种模式决定「何时能回收」。

## 4 公式解析：生存期与「悬垂」的关系

生存期管理失当导致的最经典错误是**悬垂引用（dangling reference）**——引用已解绑存储的变量。用「存储绑定生命周期」可以精确定义它：

$$
\text{dangling}(r) \;\Longleftrightarrow\; \exists\ v : r \text{ 指向 } v \text{ 的存储} \land \text{lifetime}(v) \text{ 已结束}
$$

三步拆解：

- **第一步，读条件**：引用 $r$ 仍持有指向变量 $v$ 的地址，但 $v$ 的**生存期已结束**（存储已被解绑/回收）。
- **第二步，看根源**：悬垂 = 「名字/引用的**引用期**超过了被引变量的**生存期**」。栈局部变量返回指针（函数返回后栈帧销毁）、`free` 后继续用指针，都是「引用期 > 生存期」的实例。
- **第三步，看解法谱系**：三种主流解法对应「让生存期长过引用期」——GC 推迟回收直到无人引用（生存期被拉长）、Rust 借用检查在编译期证明「引用不越过被引者的寿命」、C 靠程序员自律。**悬垂问题 = 生存期管理问题**。

**辨析｜易错点：** 作用域结束 ≠ 生存期结束。词法作用域结束时，被**闭包捕获**的变量仍可能存活（生存期被拉长）；被 `static` 修饰的局部变量作用域结束但存储还在。**「变量名看不见了」与「变量存储回收了」是两回事**——这正是一节开头「时空分离」的体现。

## 5 生存期与现代内存管理

- **GC 语言**（Java/Python/Go）：运行时追踪哪些对象「不可达」，不可达即回收——程序员不必手动解绑，生存期由可达性决定。<span class="marginnote">可达性定义生存期：只要还有引用能到达对象，它就有生存期。GC 消灭了「手动释放过早」的悬垂，代价是「回收过迟」的内存占用与停顿——「何时回收」永远在权衡。</span>
- **Rust**：所有权 + 生命周期标注，把「生存期」变成类型系统可检查的性质——`'a` 生命周期参数是「引用的有效区间」，编译器证明它不超出被引用对象的生存期，从而**无 GC 也无悬垂**。
- **手动管理**（C/C++）：完全由程序员控制 `malloc`/`free`，性能最佳但最易出错——悬垂、泄漏、双重释放。

## 6 生存期与并发的交汇

生存期不仅是内存话题，还深刻影响**并发**——「变量何时释放」与「多个线程何时访问」的相互作用：

**静态变量的线程安全**：`static` 局部变量生存期=整个程序、作用域=函数内——「全局共享的隐藏状态」。两个线程同时调用 `inc()`（static 计数器）→ 竞态（回顾并发篇）。**「生存期长 + 作用域窄」的静态变量是并发的雷区**——它在函数里「看不见」但共享。

**闭包与逃逸**：闭包捕获的变量生存期被拉长到「闭包被使用时」——若闭包被多个线程共享（跨线程传递），被捕获变量的**并发访问**成为问题（Rust 的 `Send`/`Sync` trait 正是检查「跨线程共享的变量是否安全」）。

**栈上的变量不能跨线程共享**：栈帧随线程死——一个线程的局部变量地址传给另一线程，就是「悬垂 + 跨线程访问」双重错误。

**辨析｜易错点：** 生存期与并发的交叉规律：**「生存期越短的东西越安全，生存期越长越要小心共享」**——栈局部变量（短命）天然线程私有；静态/闭包捕获（长命）天然共享、要同步。「变量被谁看到」由作用域定，「活多久」由生存期定，「能否并发安全地共享」由两者共同决定。



## 7 栈与堆在现代语言中的形态

「栈 vs 堆」在现代语言中不再是「运行时细节」，而是上升为**类型/语法层**的显式选择：

**值类型 vs 引用类型**（C#/Swift）：`struct`（值，栈或内联）与 `class`（引用，堆）。**「选 struct 还是 class = 选栈还是堆」**——值类型快但拷贝，引用类型共享但有 GC。

**Rust 的显式选择**：局部变量默认栈上；堆分配必须显式 `Box::new`/`Rc`——「栈是默认，堆是显式」。「`i32`（值，栈）vs `Box<i32>`（堆）的类型差异，让「在哪分配」成为类型系统的一部分。

**逃逸分析（escape analysis）**：JVM 的 JIT 优化——若对象「不逃逸」出函数（不被返回/共享），就分配在**栈上**而非堆——「逻辑上是堆对象，物理上栈分配」。**「编译器的逃逸分析在调和『堆的灵活』与『栈的快』」**。

| 语言 | 栈/堆选择 | 机制 |
| --- | --- | --- |
| C#/Swift | struct/class | 类型决定 |
| Rust | `T`/`Box<T>` | 类型决定 |
| Java | 全堆 + 逃逸分析 | JIT 优化 |
| Python | 全堆 | 无栈对象 |

**辨析｜易错点：** 「栈上分配」不等于「没有堆」——逃逸分析失败（对象逃逸）仍要堆。**「栈 vs 堆的选择，本质是『生命周期是否嵌套』的选择」**：嵌套（短命）用栈，自由（长命）用堆。「现代语言把栈堆选择从『运行时偶然』变成『类型层显式』」——这让我们对「内存在哪分配」有掌控，而不是被动接受。

## 8 小结

- **存储绑定**决定变量存储的分配与释放，**生存期**是存储有效的时间区间。
- 四类变量：**静态 / 栈 / 显式堆 / 隐式堆**，生存期分别由程序、块、手动、GC 决定。
- 作用域（空间）与生存期（时间）正交组合出四种「性格」，`static` 局部变量是经典例子。
- **悬垂引用 = 引用期超过生存期**；GC（拉长生存期）、所有权（编译期证明）、手动管理是三种解法谱系。
