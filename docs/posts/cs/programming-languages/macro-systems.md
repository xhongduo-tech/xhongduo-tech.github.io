## 为什么从宏系统开始

**元编程（metaprogramming）**——「写程序的程序」——的第一种形态是**宏（macro）**。宏在**编译期展开**：一段「宏定义」在编译时被替换成代码，从而让程序员扩展语言的语法。从 C 的文本宏（`#define`）到 Lisp 的代码即数据，再到 Rust 的声明式与过程式宏，「宏」经历了从「危险文本替换」到「安全 AST 操作」的进化。这一节重点看两种宏的对比：**文本宏（textual macro）**（C 风格，简单但危险）与**卫生宏（hygienic macro）**（Scheme/Rust，安全可靠）。<span class="marginnote">宏 vs 函数：函数在<strong>运行期</strong>调用、操作值；宏在<strong>编译期</strong>展开、操作代码。「宏把『代码变换』提前到编译期」——它可以做函数做不到的事（改变语法结构、按类型生成代码），但必须保证展开后仍合法。「宏是语法层的函数」。</span>

## 1 文本宏：C 的 #define

**文本宏（textual macro）**：编译器在预处理阶段做**文本替换**——把宏名替换成宏体。

```c
#define SQUARE(x) ((x) * (x))
#define MAX(a, b) ((a) > (b) ? (a) : (b))
#define BUFFER_SIZE 1024
```

文本宏的缺陷（著名）：

- **括号陷阱**：`SQUARE(2 + 3)` 若宏体是 `(x)*(x)` 展开为 `2+3*2+3`——需小心加括号。
- **副作用重复**：`MAX(i++, j++)` 中 `i++` 出现两次——自增两次。
- **无作用域**：宏是全局的，会「污染」名字空间。

<span class="marginnote">文本宏的「文本替换」本质决定了它的脆弱：它不知道语法、不管作用域、不检查类型。`MAX(a, b)` 里 `a`、`b` 出现两次——若实参是 `i++` 这种带副作用的表达式，会执行两次。这就是「宏替换不是函数调用」——它没有「一次求值」的语义。</span>

**辨析｜易错点：** 文本宏的变量捕获问题：`#define SWAP(a,b) { int tmp = a; a = b; b = tmp; }` 中的 `tmp` 可能与外部变量冲突；且宏体里的 `a`、`b` 若与外部同名变量混淆——**文本宏无视作用域**。C 程序员因此给宏临时变量加「怪异前缀」（`_tmp`）或改用内联函数。

## 2 卫生宏：安全的 AST 操作

**卫生宏（hygienic macro）**：宏在**语法树（AST）层面**操作，且**自动处理变量捕获**——宏展开的变量不会意外捕获调用者的名字。Scheme/Racket 的 `syntax-rules`、Rust 的 `macro_rules!` 是代表。

```rust
macro_rules! my_vec {
    ($($x:expr),*) => {{
        let mut v = Vec::new();
        $(v.push($x);)*
        v
    }};
}

let v = my_vec![1, 2, 3];   // 展开为构造 Vec 的代码
```

卫生宏的关键：

- **作用于 AST**：`$x:expr` 匹配「一个表达式」——按语法结构匹配，而非文本。
- **卫生性（hygiene）**：宏内引入的名字不会与调用处冲突——宏的变量「自动改名」隔离。<span class="marginnote">「卫生」指宏的「清洁性」：宏内部引入的临时变量（如 `my_vec` 里的 `v`）不会意外「捕获」或「被捕获」调用处的同名变量。Scheme 的卫生宏由<strong>词法作用域自动保证</strong>（宏展开的名字按定义处的环境解析）——这是它相对 C 文本宏的决定性安全改进。</span>

## 3 宏与函数：分工与边界

| 维度 | 宏 | 函数 |
| --- | --- | --- |
| 展开时机 | 编译期 | 运行期调用 |
| 操作对象 | 代码（AST） | 值 |
| 能做 | 改变语法、生成代码、延迟求值 | 计算、抽象 |
| 求值 | 实参可延迟/重复/不展开 | 实参先求值 |
| 可调试性 | 差（展开后难追踪） | 好 |

**辨析｜易错点：** 宏的「延迟求值」能力是函数没有的：`my_assert!(cond)` 若写成宏，条件**只在检查时**求值；若写成函数，实参**先求值再传入**——`assert!` 要能「条件为真时不求值错误消息」，必须是宏（或传闭包）。**「宏能控制实参的求值时机，函数不能」**——这是宏不可替代的核心原因。

## 4 公式解析：宏展开的语义

宏展开可以形式化为「编译期的树重写」。设宏 $M$ 有模式 $\rho$ 与模板 $\tau$，匹配表达式 $e$：

$$
\text{expand}(M(e)) = \tau[\text{bind}(\rho, e)] \quad \text{（把 } e \text{ 绑定到模式变量，代入模板）}
$$

卫生性条件：模板里的变量 $x$ 不捕获调用上下文：

$$
\text{hygienic} \iff \text{模板变量按宏定义处的作用域解析} \quad \text{（非调用处）}
$$

三步拆解：

- **第一步，模式匹配**：`$x:expr` 是模式，匹配调用处的表达式——`my_vec![1,2,3]` 匹配 `$x=1,2,3`。
- **第二步，模板实例化**：把匹配绑定代入模板——生成「构造 Vec 的代码」。展开 = 一次 AST 重写。
- **第三步，卫生保证**：模板中的变量（`v`、`Vec`）按**定义处**的词法环境解析——调用者即使有同名 `v` 也不冲突。**「卫生 = 宏的变量有自己独立的作用域」**——文本宏缺的正是这条。

**辨析｜易错点：** 宏展开后代码仍要**通过类型检查**——宏不是「绕过编译器」，而是「编译器跑两遍：先展开宏，再检查结果」。**「宏生成代码，生成物仍需合法」**——错误的宏会展开出类型错误/语法错误，调试时看到的是展开后的代码（可用 `cargo expand`、`gcc -E` 查看）。

## 5 宏的现代实践

- **Rust 声明式宏 `macro_rules!`**：模式匹配的卫生宏；`vec!`、`println!` 都基于它。
- **Rust 过程式宏**：`#[derive]`、`#[test]`、`async_trait`——**函数式**操作 TokenStream，可做任意代码变换（更强的元编程）。
- **C++ 模板**：模板元编程（下一节）——编译期计算，宏的「类型级」表亲。
- **Lisp/Scheme**：defmacro/syntax-rules——宏的祖师爷，代码即数据让宏天然强大。<span class="marginnote">现代趋势：<strong>「宏要安全」</strong>。Rust 的 `macro_rules!` 是卫生的，过程式宏要求显式处理；C++ 用模板+constexpr 替代危险宏；Julia 的宏也走「AST 卫生」。宏从「文本替换的便利工具」进化为「语法扩展的正规机制」——语言设计者意识到：给用户语法扩展权是巨大的力量，必须配上安全的约束。</span>

## 6 小结

- **宏**在编译期展开、操作代码——「语法层的函数」，能改变语法、控制求值时机。
- **文本宏**（C `#define`）：文本替换——括号陷阱、副作用重复、无作用域。
- **卫生宏**（Scheme/Rust）：AST 操作 + 自动处理变量捕获——宏变量有独立作用域。
- 宏 vs 函数：宏能延迟/重复求值实参；宏生成代码仍需通过类型检查；现代宏走向「安全」方向。
