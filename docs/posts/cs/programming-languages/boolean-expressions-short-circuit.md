## 为什么从布尔表达式开始

算术表达式处理数值，而程序的「决策」靠另一族表达式：**关系表达式**（比较两个值，产出真假）与**布尔表达式**（用 `&&`/`||`/`!` 组合真假）。它们的特殊之处在于：布尔运算不必总是「算到底」——`false && anything` 已经是 `false`，`true || anything` 已经是 `true`，于是语言可以**短路（short-circuit）**：跳过第二个操作数的求值。短路求值看似是性能优化，实则是**控制流机制**——无数程序依赖 `if (p != null && p.x > 0)` 这种「先判空再用」的模式，若语言不短路，第二半会在 `p == null` 时崩溃。<span class="marginnote">短路求值把一个布尔表达式变成「隐形的 if」：`a && b` 等价于「若 a 则求 b，否则直接 false」。这使布尔表达式获得控制流能力，也引入「副作用求值」的语义问题——第二个操作数的副作用可能发生，也可能不发生。</span>

## 1 关系表达式：比较的产物

**关系表达式（relational expression）**：用关系运算符（`<`、`<=`、`>`、`>=`、`==`、`!=`）比较两个操作数，结果是布尔值。

设计问题集中在：

- **可比较性**：哪些类型可以比较？数值全可比较；字符串是否可比较按字典序（C 用 `strcmp`，Python/Java 直接 `<`）；对象是否可比较由 `==` 语义决定（Java 的 `==` 比较引用、`equals` 比较内容，Python 的 `==` 比较内容）。<span class="marginnote">Java 的 `==` vs `equals` 是经典陷阱：`new Integer(1) == new Integer(1)` 为 `false`（引用不同），而 `1 == 1`（基本类型）为 `true`。关系运算符的「含义」在引用类型上变得暧昧——这是值语义与引用语义的直接冲突。</span>
- **链式比较**：Python 支持 `a < b < c`（数学式链式），C/Java 不支持（`a < b < c` 被解析为 `(a < b) < c`，把布尔当数比较）。<span class="marginnote">C 的 `a < b < c` 是「先算 `a < b` 得 0/1，再拿 0/1 与 c 比较」——一个静默的错误。Python 的链式比较是数学直觉的正确实现。</span>

## 2 布尔表达式与短路

**布尔表达式（boolean expression）**：由布尔运算符 `&&`（与）、`||`（或）、`!`（非）连接的关系表达式或布尔值。

**短路求值（short-circuit evaluation）**：求值 `a && b` 时，若 `a` 为 `false` 则直接得 `false`，不再求 `b`；求值 `a || b` 时，若 `a` 为 `true` 则直接得 `true`，不再求 `b`。

```c
if (p != NULL && p->count > 0) { ... }   /* p 为空时第二半不求值，安全 */
if (i != 0 && n / i > 10) { ... }        /* 避免除零 */
```

**辨析｜易错点：** 不是所有语言都短路。**Ada 默认不短路**——`and`/`or` 总是求值两侧，除非显式写 `and then`/`or else`。在 Ada 里 `if (p /= null and p.all.count > 0)` 在 `p` 为空时仍会求第二半而崩溃。**「布尔运算是否短路」是语言语义承诺，用错语言会写出「看起来安全实则崩溃」的代码**。

## 3 短路与副作用

短路求值带来一个微妙的语义问题：**第二个操作数的副作用**。

```c
int i = 0;
if (true || (i = 5)) { }   /* i 仍是 0：|| 短路，右侧没执行 */
if (false && (i = 5)) { }  /* i 仍是 0：&& 短路 */
```

在短路语言里，「右侧操作数是否执行」取决于左侧结果——因此**右侧操作数内不应放置有副作用的表达式**（依赖它执行与否的代码，逻辑上「悬」在求值结果上）。

**辨析｜易错点：** 在**非短路**语言（或对**非短路运算符**）里，两侧**一定**都求值——`a || b` 中 `b` 的副作用必然发生。依赖「短路保证副作用不发生」的代码，移植到非短路语言会静默改变行为。**副作用 + 短路 = 未指定行为的地雷**。

## 4 公式解析：短路的真值语义

短路的语义可以用「部分求值」精确刻画。设 `⊥` 表示「不求值（副作用不发生）」：

$$
\text{true} \land b = b, \qquad \text{false} \land b = \text{false} \quad (\text{第二个 } b \text{ 不求值})
$$

$$
\text{true} \lor b = \text{true} \quad (\text{第二个 } b \text{ 不求值}), \qquad \text{false} \lor b = b
$$

三步拆解：

- **第一步，读恒等式**：`true ∧ b` 的值取决于 `b`（所以要求 `b`）；`false ∧ b` 恒为 `false`（不必求 `b`）。
- **第二步，对照短路**：这四条恒等式**就是**短路规则——「结果已定」的一侧直接返回，不再求另一侧。短路不是「优化」，而是真值函数本身的性质。
- **第三步，看推广**：`a && b` 等价于 `if a then b else false`；`a || b` 等价于 `if a then true else b`。**布尔运算符 = 隐式的条件表达式**——这是短路最深刻的理解，也是函数式语言把 `&&` 直接定义成条件表达式的原因。

**辨析｜易错点：** 非短路语言（Ada 默认、及所有位运算 `&`/`|`）求值 `a && b` 时两侧**必求**——其真值语义是「全函数」：任何输入都有结果，副作用必发生。写代码前先确认「这个 `&&` 到底短路吗」，是跨语言开发的第一常识。

## 5 现代语言的布尔设计

- **Python**：`and`/`or` 短路，且**返回操作数本身**（`0 or "x"` → `"x"`，`"a" and "b"` → `"b"`）——布尔运算符变成了「选择器」。<span class="marginnote">Python 的 `and`/`or` 返回值而非布尔，是「短路 + 值语义」的合成：`x or default` 成了「取 x，若 falsy 则取 default」的惯用法。这模糊了「逻辑运算」与「取值」的界限，被许多风格指南视为可读性陷阱。</span>
- **Rust**：`&&`/`||` 短路且**只接受布尔**操作数（不把非零当 true）。
- **C++17**：`&&`/`||` 短路且固定从左到右求值（早期 C 顺序未指定）。
- **SQL**：`AND`/`OR` 短路语义不保证（优化器自由重排）——写 `WHERE` 条件不要依赖求值顺序。

## 6 布尔表达式的可读性陷阱

布尔表达式虽简单，却有一批「看着对、实则错」的模式——值得单列：

**德摩根错误**：`!(a && b)` 误写成 `!a && !b`——正确是 `!a || !b`。**「否定与逻辑运算符的分配」是最常见的逻辑错误**。

**比较链误解**：`a < b < c` 在 C 里是 `(a < b) < c`（布尔当数比）——Python 里才是数学链式。**「同一种写法，不同语言不同含义」**。

**`==` 与 `===`**：JS 的 `==` 做类型转换（`"5" == 5` 为真）、`===` 严格比较。**「宽松相等 + 短路 = 双重隐晦」**——大多数语言风格指南建议用严格相等。

**可读性建议**：用**命名中间变量**替代长布尔链：

```python
is_eligible = age >= 18 and not banned
if is_eligible:   # 比 if age >= 18 and not banned 更可读
    ...
```

**辨析｜易错点：** 布尔表达式是「程序里密度最高、最容易『想当然』的地方」——「一眼看不出对错的布尔表达式，就是该重构的信号」。**「布尔逻辑要『写得像句子』而非『挤成一团』」**：命名变量、加括号、拆短链——可读性的回报在 debug 时百倍返还。

## 7 小结

- **关系表达式**比较值产出布尔；`==` 在值语义/引用语义语言里含义不同。
- **布尔表达式**由 `&&`/`||`/`!` 组合；**短路求值**跳过已定结果的一侧。
- 短路不只是优化，而是**控制流机制**：`a && b` = `if a then b else false`。
- 非短路语言（Ada）与短路语言的行为不同；**副作用 + 短路**是未指定行为的地雷。
