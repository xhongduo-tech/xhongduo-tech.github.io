## 为什么从设计因素开始

上一节我们有了评价语言的四个标准。但标准的背后还缺一个追问：**语言为什么长成今天这样？** Sebesta 给出两个长期支配力量：**计算机体系结构（computer architecture）**与**编程方法学（programming methodology）**。前者回答「语言为什么被迫像机器」，后者回答「语言为什么极力摆脱像机器」。这两股力量一拉一扯，塑造了从 Fortran 到 Rust 的每一门命令式语言，也解释了为什么函数式语言始终是「少数派的反叛」。

## 1 冯·诺依曼体系结构：命令式语言的遗传基因

今天的计算机绝大多数仍是**冯·诺依曼结构**：程序与数据存放在**同一块内存**里，CPU 不断地**取指令 → 译码 → 执行**，按顺序处理。1945 年冯·诺依曼在 EDVAC 报告中提出「存储程序」思想——把程序本身当作数据放进内存，机器才能自动运行。

这一结构对语言设计的影响是决定性的。命令式语言的三根支柱，恰好对应冯·诺依曼机器的三个部件：

- **变量（variable）** ↔ **内存单元（memory cell）**：变量是内存单元的「替身」，`int x;` 就是「给我一块能放整数的内存」。
- **赋值（assignment）** ↔ **存储（store）**：`x = x + 1` 就是把内存里的旧值取出来加 1 再存回去。
- **顺序执行（sequential control）** ↔ **取指-执行周期（fetch-execute cycle）**：语句一个接一个执行，对应 CPU 一条接一条执行指令。

所以「命令式（imperative）」这个名字的准确含义是：**用「改变存储」来描述计算**。它是最贴合冯·诺依曼机器的语言风格，也是历史最悠久、至今最主流的风格。<span class="marginnote">高级语言没有把「取指-译码-执行」这一整套机器细节暴露给程序员——那是汇编语言干的事——但它把机器层面的「存储-读取-写入」抽象成了「变量-取值-赋值」。这种「保留骨骼、隐去肌肉」的关系，正是体系结构影响的实质。</span>

## 2 一个变量，三种语言的三种人生

用同一个 `x = x + 1` 看三种层次，感受体系结构的影子从浓到淡。

```c
x = x + 1;   /* C：直接就是「读内存、加一、写回」的高级形态 */
```

```python
x = x + 1    # Python：语义同上，但 CPython 的字节码虚拟机替你管理类型与内存
```

```haskell
let x' = x + 1 in ...   -- Haskell：没有「改写」，而是产生一个新名字 x'，旧 x 永不改变
```

C 与 Python 都是命令式的：赋值语句存在，变量就是存储的别名。Haskell 放弃赋值，改成「绑定新名字」——这是对「存储」这个概念的彻底告别。**体系结构决定了命令式语言必须存在；而函数式语言的价值，恰恰在于证明「不必如此」。**

## 3 冯·诺依曼瓶颈：当 CPU 等着数据

内存与 CPU 之间只有一条数据通路，而内存的读写速度远慢于 CPU——**CPU 常常在等数据**，这个矛盾被称为**冯·诺依曼瓶颈（von Neumann bottleneck）**。指令和数据要一块块地从内存搬到 CPU，一切计算都受限于这条通路。

这一瓶颈的后果远超硬件。1977 年巴科斯在图灵奖演讲《能否把程序设计从冯·诺依曼风格中解放出来？》里断言：程序效率、语言设计、甚至程序员思考方式，都被「必须把一切变成对存储的读写」所绑架。函数式语言（第十二篇《函数式编程》）试图摆脱它——用表达式求值取代「读改写」序列；GPU 与向量机则从硬件侧缓解它——用宽通路一次搬运一批数据。<span class="marginnote">巴科斯（John Backus）是 Fortran 之父，也是 1977 年图灵奖得主。他晚年最重要的贡献不是 Fortran，而是这篇「反冯·诺依曼」演讲——语言设计史上最著名的「叛逆宣言」之一。</span>

## 4 编程方法学：从 goto 的废墟上长出结构化

体系结构回答「机器需要什么」，编程方法学回答「**人怎样思考才不容易出错**」。1960 年代，goto 泛滥让大型程序变成「一碗意大利面」，没人能读懂控制流。1968 年，迪科斯彻写信给 CACM，标题就是《Go To Statement Considered Harmful》，主张：**一个程序块只允许一个人口和一个出口，顺序、选择、循环三种结构足以表达一切控制流**。

这场「结构化编程」运动直接改写了语言设计。ALGOL 60 已经给出块结构与 `if-then-else`；Pascal、C 把「结构化语句」变成标配；Ada 进一步限制 goto 的使用范围。**语言特性的诞生往往不是「发明」，而是「把被证明有效的方法学固化成语法」。** <span class="marginnote">结构化编程的方法学三件套——顺序、选择、循环——在第八篇《语句级控制结构》里会被系统化：为什么现代语言都提供 if/switch/while/for，为什么 goto 被降级为「必要时才用的逃生舱」。</span>

## 5 方法学的下一章：数据抽象、面向对象与并发

结构化编程解决「控制流怎么写」，1970 年代后方法学把焦点转向「**数据怎么组织**」：

- **数据抽象（data abstraction）**：把数据与操作它的一组函数打包成一个单元（抽象数据类型），对外隐藏实现。Simula 67 的类、Ada 的包、C++ 与 Java 的类，都是这一方法学的语法化。
- **面向对象（object-oriented）**：在数据抽象之上加入**继承**与**动态绑定**，让代码能「对扩展开放」——Smalltalk 把它推到极致。
- **并发与安全（concurrency &amp; safety）**：2000 年后，多核普及让「并发」成为方法学中心词，Go 的 goroutine、Rust 的所有权系统、Erlang 的 Actor 模型应运而生。

把这两条线索并排，就得到一张「方法学 → 语言特性」的映射表（本章核心要点表）：

| 时代 | 主导方法学 | 催生的语言特性 | 代表语言 |
| --- | --- | --- | --- |
| 1950s | 机器直译、科学计算 | 表达式、子程序、循环 | Fortran |
| 1960s | 可读性觉醒 | 块结构、递归、BNF 描述 | ALGOL 60 |
| 1970s | 结构化编程 | 顺序/选择/循环、限制 goto | Pascal、C |
| 1970s | 数据抽象 | 类、包、封装 | Simula 67、Smalltalk |
| 1980s | 可靠性优先 | 强类型、任务、异常 | Ada、C++ |
| 1990s | 网络与多范式 | 字节码、GC、脚本化 | Java、Python、JavaScript |
| 2000s+ | 并发与安全 | goroutine、所有权、async/await | Go、Rust、Kotlin |

读这张表的方法在第 6 节给出。

## 6 公式解析：取指周期与「程序 = 状态改写」

体系结构的影响可以浓缩成两条「公式」。第一条描述机器的节律，第二条描述命令式语言对它的模仿。

**机器的节律**：一个取指-执行周期用时

$$
T_{\text{cycle}} = t_{\text{取指}} + t_{\text{译码}} + t_{\text{执行}}
$$

- $t_{\text{取指}}$：从内存读出下一条指令并送入 CPU 的时间；
- $t_{\text{译码}}$：CPU 识别这条指令做什么的时间；
- $t_{\text{执行}}$：真正运算的时间。

其中 $t_{\text{取指}}$ 由冯·诺依曼瓶颈主导——内存带宽是上限。这条式子是示意性的教学模型，真实 CPU 用流水线让多条指令并行，但「周期由取指、译码、执行三阶段构成」的基本结构没有变。

**语言的模仿**：命令式程序可以压缩成一条「方程式」：

$$
\text{命令式程序} \equiv \text{变量} + \text{赋值} + \text{顺序执行}
$$

- 读左边：命令式程序是「操作序列」；
- 读右边：操作序列的三个基本动作，一一对应第 1 节的内存单元、存储、取指执行；
- 完整读：**赋值是命令式语言的原子动作，它把一个存储单元的内容换成新值——这正是「冯·诺依曼风格」的语言学签名。** 函数式语言取消了这一项，所以它不再是命令式。

**辨析｜易错点：** 体系结构的影响是「倾向」而非「宿命」。Haskell 也运行在冯·诺依曼机器上，最终也被编译成机器码——但它**语义上**不描述「读改写」，而是描述「表达式求值」，由编译器负责把它映射到存储。反过来说，一个语言被贴上「函数式」「解释型」标签，都不改变一件事：只要目标机是冯·诺依曼机，实现就绕不开存储与顺序，差别只在「语言层面你看到的是哪种模型」。

## 7 小结

- 命令式语言的三根支柱——**变量、赋值、顺序执行**——直接对应冯·诺依曼结构的**内存单元、存储、取指执行**。
- **冯·诺依曼瓶颈**让 CPU 等数据，也迫使语言设计者思考「能否摆脱读改写模型」。
- 编程方法学是语言特性的孵化器：**结构化编程 → 顺序/选择/循环；数据抽象 → 类；并发 → goroutine/所有权**。
- 两股力量方向相反：体系结构把语言「拽向机器」，方法学把语言「拉向人」；语言设计就是在这两股力之间找平衡点。

在下一节，我们将从「设计」转到「实现」：一门语言写出来之后，怎样变成机器能跑的代码？编译、解释与混合实现三种路线各自如何工作、各有什么代价——这是《语言的实现方法：编译、解释与混合实现》的内容，也是第三级《编译原理》专题的直接入口。
