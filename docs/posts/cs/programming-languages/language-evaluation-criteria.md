## 为什么从评价标准开始

上一节《学习程序设计语言原理的意义》把「可读性、可写性、可靠性、成本」四个标准摆上了桌面。这一节要往下钻一层：**每个标准到底由哪些可分析的子因素构成，四个标准之间如何互相牵制，以及——最实际的——怎样用它们去比较两门具体的语言。** 评价标准不是考试打分表，而是设计哲学的地图：读懂了它，你就知道为什么 Perl 写起来爽、读起来痛，为什么 Ada 又贵又可靠，为什么 Python 能在工程与教学之间站稳脚跟。

这一节还会第一次用到「决策公式」——一个把所有标准合成单个数量的启发式框架。它本身不是课本公式，而是把「语言选型」这个**多目标决策**问题显式化的工具，也是理解后面所有语言特性的坐标轴。

## 1 可读性：程序首先是写给人读的

**可读性（readability）**：程序被**读与理解**的容易程度。SICP 那句话说得极端而准确：机器只是「顺带」执行，程序的读者——包括六个月后的你自己——才是第一受众。Sebesta 把可读性拆成四个子因素。

**整体简洁性（overall simplicity）**。恰到好处的简洁，指「用尽量少的构造表达尽量多的计算」。但简洁有两个方向：构造太少，表达力不足，任何程序都得绕远路；构造太多，同一件事有多种写法，读者永远在猜测作者用的是哪一种。C 里 `i = i + 1`、`i += 1`、`i++`、`++i` 都合法——四倍的语法表面，换来的是四倍的阅读负担。<span class="marginnote">Python 的哲学是「只有一种明显的方式去做一件事」（There should be one obvious way to do it），简洁性由此成为它的第一设计目标。对比 C 的多种写法，正是「简洁性」这个子因素在起作用。</span>

**正交性（orthogonality）**。正交性指「少量机制之间可以自由、无例外地组合」的程度。C 中数组与指针几乎可以互换：`a[i]` 与 `*(a + i)` 等价，这是下标与寻址两个机制的**正交组合**。正交性越强，可读性越好——因为读者只需掌握少数规则，再用组合规则去推导一切。但正交性也有代价：C 的数组下标、指针算术与类型转换自由组合，稍不留神就写出不可读、不可维护的代码。

**数据类型（data types）**。充足而贴切的数据类型让意图显式化。看到 `enum { MONDAY, TUESDAY, ... }`，读者立刻知道变量只能取一周的某天；看到 `double`，读者知道这是浮点。反例是早期 Fortran 的**隐式类型**：I、J、K、L、M、N 开头的变量默认整型，其余默认实型——省了声明，却让类型信息消失在惯例里，今天没有人会为它辩护。

**语法设计（syntax design）**。语法影响「形式」与「意义」的对应是否自然。保留字（reserved word）比特殊字（special word）可读：`if`/`while` 一眼便知，而 APL 用希腊字母与特殊符号写成的程序，`∇`/`∊` 之类一个符号一段含义，上手前必须查表。<span class="marginnote">语法设计的两个层面：标识符形态（能否用长而有意义的名字）与语句形式（是否贴近自然语言）。Fortran 早期忽略大小写、空格受限，`X = Y` 与 `X=Y` 都合法，都是语法设计欠佳的史例。</span>

**辨析｜易错点：** 可读性不是「注释越多越好」。注释多往往说明代码本身读不懂，而可读性恰恰要求代码**不靠注释**也能被读懂。可读性评估的对象是「语言的设计」，不是「某个程序员的习惯」——但语言的子因素最终会放大或缩小程序员写出可读代码的可能性。

## 2 可写性：想法到程序的距离

**可写性（writability）**：把**想法变成程序**的容易程度。它同样受简洁性与正交性影响，此外还有两个关键子因素。

**表达力（expressivity）**：语言能否用紧凑的方式表达常用运算。Python 的列表推导式

```python
squares = [x * x for x in range(10)]
```

在 C 里要三行：先声明数组，再写 for 循环逐元素赋值，最后还要记得边界。表达力正是「说一次 vs 说很多次」的距离。

**对抽象的支持（abstraction）**：过程、函数、类、高阶函数……语言支持的抽象机制越强，可写性越高，因为读者可以把复杂度推给「定义处」，调用处保持干净。<span class="marginnote">抽象是把「写一次、用多处」变成语言特性的能力：C 只有函数抽象，C++/Java 加入类抽象，Scheme/Haskell 的一等函数让「把函数当参数传来传去」也成为可能。可写性随抽象层级的升高而上升。</span>

**辨析｜易错点：** 可写性与可读性并不总是一致。APL 是反例：它的矩阵运算一行写完十行 Fortran 的活，可写性极高；但那一行里的每个符号都承载多重含义，读者几乎无法在不查参考卡的情况下读懂。**可写性高的语言可能可读性极低**——这正是 Perl 口碑两极分化的根源。所以「简洁」在两个标准里是同一项资产，但「表达力」在可读性这里可能是负债。

## 3 可靠性：程序按规范运行的保证

**可靠性（reliability）**：程序在一切环境下都**按规范运行**的概率。它有三个主要影响因素。

**类型检查（type checking）**。在编译期或运行期检查「操作数的类型是否匹配」，能提前拦截一类数量可观的错误。编译期检查的 Java 里 `int x = "abc"` 直接编译失败；而 Python 要到运行时才在赋值处抛 `TypeError`。<span class="marginnote">「编译期检查比运行期检查早一步发现问题」——这是第四篇《数据类型》与第五篇《类型系统深入》反复出现的主题。检查越早，错误越便宜。</span>

**异常处理（exception handling）**。程序能优雅地拦截运行时异常，还是只能崩溃？Java 的 `try/catch` 让「可能出现异常」成为显式路径：

```java
try {
    int[] a = new int[5];
    a[10] = 1;                       // 越界：抛出异常
} catch (ArrayIndexOutOfBoundsException e) {
    System.out.println("越界: " + e.getMessage());
}
```

而 C 的惯用做法是函数返回错误码、调用方逐个检查——检查一旦被跳过，错误就悄悄扩散。把「错误」显式化，本身就是可靠性的来源。

**别名（aliasing）**。当同一块存储可以被多个名字访问，改动一个名字会「意外」影响另一个。C 里两个指针指向同一块内存，一个函数改了它，另一个变量悄悄跟着变——这是隐蔽的可靠性杀手，也是 Rust 所有权系统（第十五篇《内存管理》）要根治的问题。

**辨析｜易错点：** 可靠性会「传染」自可读性与可写性。可读性差 → 维护者改错地方 → 引入缺陷；可写性好 → 更容易写出「正确意图的表达」。所以四个标准不是并列的四个抽屉，而是互相影响的一张网——这正是下一节要建立的总账模型。

## 4 成本：一笔总账，而不只是运行速度

**成本（cost）**：语言生命周期的**全部开销**，不是单指运行快慢。Sebesta 列出的项目至少有七项：培训、编写、编译、执行、语言实现系统、可靠性事故、长期维护。

**培训成本**：Python 新手两周能上手，Ada 需要一个季度的系统训练。
**编写与编译成本**：编写速度受可写性影响；编译成本与语言、编译器优化级别相关。
**执行成本**：运行速度与内存占用。
**实现系统成本**：编译器/解释器是否免费、是否跨平台、工具链是否成熟。
**可靠性事故成本**：银行系统一次类型错误的线上事故，可能贵过十年的编译时间。<span class="marginnote">这就是「可靠性必须单列一档」的原因：很多可靠性缺陷没有「即时可见」的代价，它们的代价是期望意义上的——事故发生概率乘以事故损失。</span>
- **维护成本**：程序生命周期 70% 以上的开销发生在发布之后，这又把成本拉回可读性。

## 5 公式解析：把四个标准合成一张决策表

四个标准怎么用？把它看成**多目标决策**：理想语言在每个维度都最优，但现实中不存在。我们可以写一个「决策启发式」，把四维向量投影成一维数值，用于不同语言之间的相对比较：

$$
U(L) = w_{\text{读}}\,\text{Read}(L) + w_{\text{写}}\,\text{Write}(L) + w_{\text{可靠}}\,\text{Rel}(L) - w_{\text{成本}}\,\text{Cost}(L)
$$

其中 $\text{Read}, \text{Write}, \text{Rel}, \text{Cost}$ 都是**归一化到 $[0,1]$ 的单项评分**，权重满足 $w_{\text{读}} + w_{\text{写}} + w_{\text{可靠}} + w_{\text{成本}} = 1$。逐项拆解：

- **第一步，读各项评分**：每个单项本身是复合指标。以 $\text{Read}$ 为例，它是第 1 节四个子因素——简洁性、正交性、数据类型、语法设计——的某种聚合。因此「给可读性打分」的前提，是先给它的子因素打分。
- **第二步，读权重 $w$**：权重不是语言的性质，而是**使用语境的投影**。国防承包商造飞机控制软件，把 $w_{\text{可靠}}$ 拉到接近 1；创业公司做快速原型，把 $w_{\text{写}}$ 抬高；大厂维护十年老系统，$w_{\text{读}}$ 与 $w_{\text{成本}}$ 说了算。同一门语言，在不同语境下的 $U$ 完全不同。
- **第三步，读减号**：成本是**负效用**，所以它前面的系数是负的。把「成本」也写进求和式是它的价值所在——否则决策者会下意识只比较三个收益维度，忘了代价。
- **第四步，明确它的身份**：这是启发式工具，不是可测量的物理量。它不能回答「Python 比 Java 好」，却能回答「在我们团队的具体语境下，哪门语言的相对效用更高」。语言选型是工程决策，不是考试。

用这个框架，把四门语言放进一张对比表（评分是示意性的主观判断，用于展示方法而非定论）：

| 维度 | Python | C | Java | Haskell |
| --- | --- | --- | --- | --- |
| 可读性 | 强 | 中 | 中偏强 | 中（概念密度高） |
| 可写性 | 强 | 中 | 中 | 强（表达力高） |
| 可靠性 | 中偏弱（动态类型） | 中偏弱（指针/别名） | 强（强类型+异常） | 强（纯函数无副作用） |
| 成本（含维护） | 低 | 中（执行快但维护贵） | 中 | 中（学习曲线陡） |

这张表的读法与公式相同：**每一格都不是「事实」，而是「某语境下的判断」**。给创业公司快速原型选型，Python 的 $U$ 值最高；给航天系统选型，Ada 与 Rust 的 $U$ 值最高。标准的意义，是把「我熟」翻译成「在哪些维度上更优」。

## 6 小结

- 可读性由**整体简洁性、正交性、数据类型、语法设计**四个子因素构成，第一读者是维护者。
- 可写性受**简洁性、正交性、表达力、抽象支持**影响；可写性高不代表可读性高（APL、Perl）。
- 可靠性取决于**类型检查、异常处理、别名**三个因素，且会受可读性与可写性传染。
- 成本是**总账**：培训、编写、编译、执行、实现系统、可靠性事故、维护七项。
- 四个标准通过**加权决策公式**合成单值，权重反映使用语境——没有「最好」的语言，只有「在某语境下相对更优」的语言。

在下一节，我们将追问：**这些标准是从哪里来的？** 为什么命令式语言都长着「变量 + 赋值 + 顺序执行」的骨架，为什么今天的语言都拼命支持面向对象与函数式？答案藏在两个长期支配力量里：计算机的体系结构，与编程方法学的演进。这正是《影响语言设计的因素》的内容。
