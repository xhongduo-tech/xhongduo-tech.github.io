## 为什么从语法与语义开始

第一篇的五篇博文给了我们一把评价语言的尺子：可读性、可写性、可靠性、成本。但尺子本身还不够——要真正「评价」一门语言，必须先能**精确地描述**一门语言。描述语言的**语法**（程序长什么样）与**语义**（程序意味着什么），是语言设计、编译实现与程序验证共同的出发点。这一节先把「语法」与「语义」这两个最基本的概念立住；从下一节起，我们会用形式化的工具——上下文无关文法、BNF——把「语法」精确地写下来。

这一节还会与自然语言反复对照：人类语言靠约定俗成，语法含糊、语义多义；程序设计语言则必须做到「形式可判定、意义可执行」。从「句子」到「记号」再到「文法」，这一整套词汇将贯穿本专题后面所有章节。

## 1 语言：句子的集合

**语言（language）**：由句子（sentence）构成的集合；**句子**：由某种字符表中的字符组成的字符串（string）。这个定义来自形式语言理论，它把「语言」从日常语感里剥离出来，变成一个纯粹的数学对象。

- **字符表（alphabet）$\Sigma$**：语言允许出现的字符集合。例如 $\Sigma = \{0, 1\}$ 是二进制串的基本字符表。
- **字符串（string）$\Sigma^{*}$**：由 $\Sigma$ 中字符拼成的任意长度字符串的全体，包括空串 $\varepsilon$。
- **语言 $L$**：$\Sigma^{*}$ 的一个子集，写作 $L \subseteq \Sigma^{*}$。

注意，「句子」在这里不必「有意义」——形式语言只关心**形式**。比如 $\{0,1\}^{*}$ 里的任何一个字符串都是「句子」，哪怕它不代表任何数值。真正要紧的是规则：我们要找一种**有限的**规则集合，让它恰好生成**全部**合法句子，又不生成任何非法句子。这种规则集合就叫**文法（grammar）**。<span class="marginnote">这是形式语言与自然语言语法的分水岭：日常说「这句话不合语法」靠的是语感；形式语言里，「句子是否属于语言」必须由有限的规则机械判定。有限的规则生成无限的语言，正是「以小博大」的第一次体现——文法虽小，却能覆盖无穷多个程序。</span>

**核心要点**：一门程序设计语言的全部「语法合法程序」构成一个形式语言；描述这个形式语言的规则，就是它的文法。

## 2 语法（syntax）：形式上的规则

**语法（syntax）**：规定「哪些字符串构成合法程序」的规则集合。语法只关心形式，不关心意义。

语法内部又分两个层面：

**词法（lexical）层面**：字符如何组成词法单元。例如 `sum = sum + 2` 里的 `sum`、`=`、`+`、`2` 是四个词法单元。
**句法（syntactic）层面**：词法单元如何组成表达式、语句与整个程序。

为了把这两个层面讲清楚，Sebesta 引入一对容易混淆的概念——**词法单元（lexeme）**与**记号（token）**。

**词法单元（lexeme）**：源程序里实际的字符序列，是「字面」。**记号（token）**：词法单元的类别，是「词性」。看一个例子：

| 源程序片段 | 词法单元（lexeme） | 记号（token） |
| --- | --- | --- |
| `sum = sum + 2` | `sum` | IDENT（标识符） |
| `sum = sum + 2` | `=` | ASSIGN_OP（赋值运算） |
| `sum = sum + 2` | `+` | ADD_OP（加法运算） |
| `sum = sum + 2` | `2` | INT_LITERAL（整数字面量） |

若把词法分析的结果摊开，就是一条记号流——编译器在语法阶段看到的正是它，而非原始字符：

```
IDENT  ASSIGN_OP  IDENT  ADD_OP  INT_LITERAL
  sum       =       sum     +         2
```

词法单元是字符层面的「具体」，记号是类别层面的「抽象」。编译器先做**词法分析（lexical analysis）**，把字符流切成词法单元并归类成记号；再做**语法分析（syntax analysis / parsing）**，把记号流组装成语法结构。<span class="marginnote">记号就像自然语言里的「词性」（名词、动词），词法单元就像具体的「词」（苹果、吃）。词性有限，词却无限；编译器在语法阶段处理的是「词性」而非每一个具体的「词」。</span>词法分析与语法分析的切分是编译前端的第一步，也是第四级《编译原理》专题的主角——这里只需记住一条流水线：**字符 → 记号 → 语法结构**。<span class="marginnote">词法分析器（scanner）处理字符层，语法分析器（parser）处理记号层；二者按「先切词、后造句」的顺序协作，是几乎所有语言实现共享的骨架。</span>

**辨析｜易错点：** 「词法」与「语法」不是同一件事的两种叫法。词法规则处理「哪些字符能拼成记号」（如标识符必须以字母开头），语法规则处理「哪些记号能拼成句子」（如赋值语句必须是 <变量> = <表达式>` 的形式）。把「标识符不能以数字开头」错当成语法规则，是初学编译原理最常见的混淆——前者在扫描阶段就被拦下，后者要到分析阶段才被检查。

## 3 语义（semantics）：意义上的规则

**语义（semantics）**：程序的意义，即程序「意味着什么」。

「意义」并不只有一种。Sebesta 把语义分成两大类，它们对应两道不同时点的检查关卡：

**静态语义（static semantics）**：与执行过程无关、但必须在运行前满足的意义约束。典型如「类型兼容性」：`int x = "hello";` 在 C 里编译期就要被拒绝，因为它违反「赋值两侧类型必须兼容」的约束。静态语义虽叫「语义」，却不在运行时发挥作用，只在编译期被检查。
**动态语义（dynamic semantics）**：程序执行时才体现的意义。表达式 `3 + 4` 的结果是多少、`if (x > 0)` 语句会走哪个分支、函数调用会触发哪些副作用——这些都发生在运行时。

把同一处「类型错误」放在两门语言里，能立刻看出这道分界线的位置：

```java
int x = 0;
x = "hello";   // 编译错误：String 不能赋给 int，静态语义检查拦截
```

```python
x = 0
x = "hello"    # 运行期不报错（动态类型）
print(x + 1)   # 到使用时才抛 TypeError——动态语义才暴露
```

同样的「把字符串塞给数值变量」，Java 在编译期就拒绝，Python 要到运行期才可能暴露问题。这不是谁更聪明，而是两家把检查放在静态还是动态语义的**设计取舍**。

静态语义与动态语义的分界线，正是编译期与运行期的分界线。<span class="marginnote">「静态」= 运行之前，「动态」= 运行之中。静态语义错 → 编译失败，程序根本跑不起来；动态语义错 → 程序能编译，但运行时行为不符合预期，甚至崩溃。</span>把更多约束放到静态语义的语言更早暴露错误，也更可靠——这与第一篇《评价标准》里「编译期检查比运行期检查更便宜」的结论正好呼应。

## 4 语法合法，语义未必正确：三道关卡

把两道关卡放在一起看，最能体会「语法合法 ≠ 语义正确」：

`int y = 1 / 0;`（除零）—— 语法上完全合法，静态语义也合法（类型没毛病），但动态语义在运行时表现为「除零错误」。
`a[100] = 0;`（数组越界）—— C 里语法与静态语义都通过，动态语义却是「越界访问」，行为未定义。

**重点：语法、静态语义、动态语义是三道不同的合法性关卡。** 语法的任务是「说清形式」，语义的任务是「规定意义」；一门语言的设计选择，往往就是在这些轴上做权衡——把更多检查提前到静态语义（编译期）的语言（Java、Rust）更可靠，把检查推迟到动态语义（运行期）的语言（Python、Ruby）更灵活。判断一段代码「对不对」，先要问清是在哪一道关卡上判。

## 5 为什么要形式化：把「合法」变成可判定

对自然语言，我们凭语感判断句子是否通顺；对程序设计语言，这远远不够。编译器必须在有限步内机械地回答「这份程序是否合法」，于是「合法」必须成为**可判定（decidable）**的数学性质。这正是形式化文法的意义：它不是「更好的描述」，而是把「合法」从语感翻译成规则。

**自然语言的困境**：歧义、例外、边界模糊。「高个子」「差不多」「语气重」都无法机械判定；同一个句子可以有完全相反的两种解读。
**程序设计语言的要求**：规则要**完备**（每个合法程序都能被生成）、**封闭**（每个被生成的都是合法程序）、**判定高效**（编译要在有限步内完成）。这三条，自然语言一条都做不到。
**文法层级预览**：乔姆斯基（Noam Chomsky）在 1956 年给出文法的四个层级——正则文法、上下文无关文法、上下文有关文法、短语结构文法，表达力逐层增强。**上下文无关文法（context-free grammar, CFG）**正是描述程序设计语言语法的标准工具：它的表达力足以覆盖程序里的嵌套与递归结构，又足够简单，能被高效的算法解析。<span class="marginnote">乔姆斯基文法层级是形式语言理论的第一张地图：正则文法描述「词法」层（标识符、数字），上下文无关文法描述「句法」层（表达式、语句），更高的两层在程序设计语言里很少用到。第四级《编译原理》专题会沿着这条线展开。</span>

**核心要点**：形式化的目的，是让「这句话属于这门语言吗」成为一个能由机器判定、且判定代价可控的问题。判断的引擎，就是下一节要精确定义的上下文无关文法。

## 6 公式解析：语法产生语言，语言是句子的集合

把前三节压缩成一个公式，就是形式语言理论对「语言」的定义：

$$
L(G) = \{\, w \in \Sigma^{*} \mid S \overset{*}{\Rightarrow} w \,\}
$$

读作「文法 $G$ 产生的语言 $L(G)$，是所有能从开始符号 $S$ 出发、经过若干步推导得到的终结符串 $w$ 的集合」。逐项拆解：

- **第一步，认识 $\Sigma^{*}$ 与 $w$**：$\Sigma$ 是字符表，$\Sigma^{*}$ 是它的全体字符串；$w \in \Sigma^{*}$ 表示「$w$ 是一个字符串」，也就是一个候选的句子。
- **第二步，认识 $S$**：$S$ 是文法的**开始符号（start symbol）**，一切推导的起点。一个句子是否属于语言，要看能不能从 $S$ 一步步推出它。
- **第三步，认识 $\overset{*}{\Rightarrow}$**：符号 $\Rightarrow$ 表示「一步推导」——把某个非终结符替换成它对应的产生式右部；星号 $*$ 表示「零步或更多步」。于是 $S \overset{*}{\Rightarrow} w$ 的意思是：从 $S$ 出发，经过有限步替换，最终得到字符串 $w$。
- **第四步，读懂整体**：花括号右边的条件把「句子」筛选出来——只有**能被文法推出来**的字符串 $w$ 才属于 $L(G)$。文法是有限的规则，语言可能是无限的集合；$L(G)$ 正是这两者之间的桥梁。

**核心要点**：语法、文法、语言三者就此连成一条线——**语法是规则，文法是规则的数学形式，语言是规则生成的全部句子**。下一节我们把「文法」做成精确的数学对象（上下文无关文法），再下一节学会用 BNF 把它写下来；这条线走到尽头，就是编译器如何判定「你的程序是否合法」。

## 7 小结

- **语言**是句子的集合，**句子**是字符表上的字符串；**文法**是有限的规则集合，它恰好生成合法句子。
- **语法（syntax）**描述形式，分**词法**（字符 → 记号）与**句法**（记号 → 句子）两层。
- **词法单元（lexeme）**是具体的字符序列，**记号（token）**是它的类别；编译器先词法分析、再语法分析。
- **语义（semantics）**描述意义，分**静态语义**（编译期检查的类型等约束）与**动态语义**（运行时的行为）。
- 语法合法、静态语义合法，都不保证动态语义正确——三道关卡依次通过，程序才「合法且有意义」。
- 形式语言定义 $L(G) = \{ w \in \Sigma^{*} \mid S \overset{*}{\Rightarrow} w \}$ 把「语法、文法、语言」串成整体。

在下一节，我们把「文法」形式化：什么是**上下文无关文法**，如何从开始符号一步一步推导出句子，推导与语法树之间是什么关系——这是把这一节的公式落到实处的第一步。
