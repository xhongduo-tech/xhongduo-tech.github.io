## 为什么从二义性开始

上一篇文章结束时，我们留下了一个悬而未决的问题：EBNF 的 `{ }` 能说清「可以重复」，却说不清重复产生的结构（谁先结合、谁先算）。这一节把这个问题正面拆开。它其实是一个更一般的病症的实例——**文法二义性（ambiguity）**：同一个句子，文法允许它长出两棵不同的语法分析树。编译器必须给每个句子一个确定的结构，否则程序的行为无从谈起。优先级与结合性，正是语言设计者用来「治愈」二义性的两味药：一个靠层叠文法，一个靠递归方向。

## 1 二义性：同一句子，两棵语法树

**二义性（ambiguity）**：如果文法 $G$ 存在某个句子 $w \in L(G)$，使 $w$ 有两棵不同的语法分析树，那么 $G$ 是有二义的（ambiguous）。

考虑一个「天然有病」的文法：

```
E -> E + E | E * E | ( E ) | id
```

它看起来简洁漂亮，但句子 `id + id * id` 能推出**两种**不同的结构——分别对应「先算加法」与「先算乘法」两种解释。写出两个不同的最左推导：

```
推导甲：                       推导乙：
E                              E
=> E + E                       => E * E
=> id + E                      => E + E * E
=> id + E * E                  => id + E * E
=> id + id * E                 => id + id * E
=> id + id * id                => id + id * id
```

两串推导在中间一步调换了展开顺序，最终却得到同一个句子——于是这个句子拥有两棵不同的语法树：一棵让 `+` 在树顶（加法先做），一棵让 `*` 在树顶（乘法先做）。**机器不知道你想要哪一个**，这就是二义性致命的本质。<span class="marginnote">二义性是<strong>文法</strong>的性质，不是单个句子的性质：`id` 这个句子在 `E -> E + E | ...` 下只有一棵树，但只要<strong>存在一个</strong>句子有两棵树，整个文法就有二义。判定「一个任意给定的上下文无关文法是否有二义」是<strong>不可判定</strong>的（无法写出通用算法）——这是形式语言理论里著名的负面结论。</span>

**辨析｜易错点：** 二义性 ≠ 「有多种写法」。语言允许 `i = i + 1` 与 `i += 1` 并存是多写法，每个写法各自有唯一结构；二义性是**同一个写法**能对应多个结构。多写法靠风格约束，二义性必须靠文法重写根除。

## 2 悬空 else：现实里臭名昭著的二义性

二义性不只在教科书里，它就藏在每个 `if-else` 程序员的身边。考虑文法片段：

```
<stmt> -> if <expr> then <stmt>
        | if <expr> then <stmt> else <stmt>
        | <other>
```

句子 `if a then if b then x = 1 else y = 2` 只有**一个**写法，却有两种合理解读——`else` 到底挂靠内层 `if` 还是外层 `if`：

```
解读甲（else 配最近的 if）：            解读乙（else 配最远的 if）：
if a then                              if a then
  if b then x = 1                         if b then x = 1
  else y = 2                              else y = 2
```

这就是著名的**悬空 else（dangling-else）**问题。<span class="marginnote">悬空 else 是语法设计史上的经典教训：Algol 60 的原始文法就在此栽过跟头，其官方解决是把「then 后面不允许直接跟 if 语句」写进文法；C、Java 则用一条非形式规则「else 与最近的未匹配 if 结合」来消歧；Python 干脆用缩进把 `if` 与 `else` 的配对固化在词法里，让问题无从发生。三种方案，是「文法消歧」「声明式消歧」「结构消歧」的三个样本。</span>

**核心要点**：二义性一旦出现，编译器就面临两难——要么拒绝程序（把责任推给程序员），要么擅自选一种解读（把结构强加给程序员）。工业语言几乎总是选后者，并靠**非形式规则**（如「else 配最近 if」）把歧义按下去，但规则与文法分离，正是隐患的温床。

## 3 运算符优先级：用层叠文法重写

回到 `id + id * id`。我们真正想要的是「`*` 先算」，即让语法树长成「`+` 在树顶、`*` 的子树更深」的形状。最干净的做法不是加一句「乘法优先」，而是**重写文法**，把不同优先级的运算放进不同的层：

```
E -> E + T | T          // 加法层：最宽
T -> T * F | F          // 乘法层：更紧
F -> ( E ) | id         // 因子层：最紧
```

现在 `id + id * id` 的推导**只有一种**：

```
E
=> E + T                // 加法层先展开
=> T + T                // 左 T 下钻到乘法层
=> F + T                // 再下钻到因子层
=> id + T
=> id + T * F           // 乘法层：T -> T * F
=> id + F * F
=> id + id * F
=> id + id * id
```

对应的语法树正是上一篇《上下文无关文法与推导》里的那张图：`*` 的子树嵌在 `+` 的右子树里，结构唯一。**优先级由此被编码进规则的层次里**——越靠近因子层（`F`）的运算绑定得越紧，越靠外层（`E`）的运算绑得越松。<span class="marginnote">这套「E → T → F」的层叠文法几乎原样出现在所有命令式语言的语法规范里，包括 Pascal、C 与 Java 的运算符优先级表。你只要记住一句话：<strong>优先级 = 语法的层次</strong>。</span>为什么必须重写文法，而不是在解析后「调整」树？因为调整意味着解析器先产出歧义结构再事后修正，复杂且易错；文法层把优先级说死，解析器从一开始就得到唯一结构。

## 4 结合性：用递归方向固定结构

优先级解决了「不同运算符谁先算」，但同类运算符连续出现时，还有第二个维度：**结合性（associativity）**。`a - b - c` 到底是 $(a-b)-c$ 还是 $a-(b-c)$？两者结果完全不同。

**结合性由递归方向决定**：

- **左结合（left associative）**：用**左递归**。`E -> E - T | T` 迫使减法向左结合，`a - b - c` 长成 `(a - b) - c`。
- **右结合（right associative）**：用**右递归**。`E -> T - E | T` 迫使减法向右结合，`a - b - c` 长成 `a - (b - c)`。

看两种文法下的推导差异（只写关键几步）：

```
左结合（E -> E - T | T）：            右结合（E -> T - E | T）：
E                                    E
=> E - T                             => T - E
=> E - T - T     （E 继续向左长）      => T - T - E   （E 继续向右长）
```

绝大多数语言对加减乘除取**左结合**，因为数学里减法、除法本身向左结合；而对**赋值**取右结合：`a = b = c = 0` 解析为 `a = (b = (c = 0))`，恰好符合「从右向左赋值」的直觉。<span class="marginnote">Fortran 的指数运算取右结合，于是 2 的 3 次方再取 3 次方被读作 2 的 9 次方；而 C 干脆没有指数运算符。Rust 在 2016 年把取余运算的优先级调整到与乘除同层——这些版本史反复印证一件事：<strong>优先级与结合性必须显式定死</strong>。</span>

**辨析｜易错点：** 回到上一篇的结论——EBNF 的 `{ addop term }` 只声明「加减可以重复」，**不决定**重复结果左结合还是右结合。若规范只给 EBNF 而不补一条「加减左结合」，`a - b - c` 就重新变回二义。**EBNF 消了递归的可见性，连带消掉了结合性的编码**——这是语言规范写作中最容易被遗漏的一环。

## 5 公式解析：二义性的形式定义

把二义性写成一句精确的命题：

$$
G \text{ 是有二义的} \iff \exists\, w \in L(G):\quad \bigl|\,\text{ParseTrees}(w)\,\bigr| \ge 2
$$

逐项拆解：

- **第一步，读右端的存在量词**：$\exists\, w \in L(G)$ 表示「存在某个句子 $w$」。注意是「存在」，不是「所有」——只要有一个句子长两棵树，文法就算有二义。
- **第二步，读 $\text{ParseTrees}(w)$**：它表示「$w$ 的全部语法分析树的集合」。$\bigl|\text{ParseTrees}(w)\bigr| \ge 2$ 即「$w$ 的语法树至少有两棵」。
- **第三步，读 $\iff$**：等号左边「$G$ 有二义」与等号右边「存在句子拥有至少两棵语法树」互为充要条件——这正是第 1 节定义的符号化。
- **第四步，补上等价变形**：对上下文无关文法有一个经典事实——**「$w$ 有两棵不同的语法树」当且仅当「$w$ 有两个不同的最左推导」**。因此上面这条定义也可以写成「存在 $w$ 有两个不同的最左推导」，两种说法等价，语法树版本更直观，推导版本更可操作。

**核心要点**：二义性的判决标准只有一个——**句子是否对应唯一的语法结构**。优先级与结合性的全部文法重写（第 3、4 节），目的都是让每个合法句子恰好拥有一棵语法树，从而把上面公式右端的「$\ge 2$」压成「$= 1$」。

## 6 小结

- **二义性**：存在某个句子 $w$ 拥有至少两棵不同的语法树（等价地，两个不同的最左推导）；判定任意 CFG 是否二义不可计算。
- **悬空 else** 是现实中最著名的二义性；工业语言用「else 配最近 if」等**非形式规则**消歧，Python 用缩进在结构上根治。
- **优先级**靠**层叠文法**表达：`E → T → F`，越靠因子层的运算绑定越紧；语法层次即优先级。
- **结合性**靠**递归方向**表达：左递归 → 左结合（加减乘除），右递归 → 右结合（赋值、指数）。
- EBNF 的 `{ }` 表达重复时**不编码结合性**，语言规范必须另行声明，否则二义复现。
- 二义性判据 $\exists w: |\text{ParseTrees}(w)| \ge 2$ 把全部文法设计努力指向一个目标：让每个句子恰好一棵树。
