## 为什么从副作用开始

前面的章节反复警告「表达式里别放副作用」。现在正面回答：**副作用（side effect）**是什么，为何既是能力的来源又是bug的温床？求一个表达式本应「算出一个值」；但如果求值过程还**改变了某个状态**（改了变量、写了文件、打了日志），那就是副作用。副作用让程序能「做事」，却破坏了数学表达式的**引用透明性（referential transparency）**——同一个表达式在不同时刻求值，结果可能不同。函数式语言选择「消灭副作用」，命令式语言选择「驯服副作用」，而这中间的每一个设计（求值顺序、函数纯度、异常边界）都在回答：副作用该放在哪、何时发生、可不可以被看见。<span class="marginnote">引用透明性：表达式在相同环境下求值必得相同结果，且可被其值安全替换。`f(x) + f(x)` 在纯函数下等于 `2 × f(x)`，有副作用时则不一定——编译器也因此不能做这类替换优化。副作用是「替换性」的敌人。</span>

## 1 副作用的来源

表达式求值过程中的状态改变来自两类：

**函数副作用（function side effect）**：函数不仅返回值，还改变非局部状态——改全局变量、写文件、改传入对象的字段、打印输出。

```python
counter = 0

def bump():            # 函数副作用：返回值的还改了全局变量
    global counter
    counter += 1
    return counter
```

**表达式副作用（expression side effect）**：求值表达式本身改变状态——自增 `i++`、复合赋值 `x += 1`、函数调用中的赋值。<span class="marginnote">`i++` 的值是「自增前的 i」，`++i` 的值是「自增后的 i」，但两者都改变 i 本身——这就是「表达式产生值」与「副作用改变状态」并存的最小例子。</span>

## 2 副作用与求值顺序：灾难的组合

当副作用遇上**未指定的求值顺序**，程序行为就变成「编译器彩票」：

```c
int i = 0;
int x = i++ + i++;    // 同一表达式内两次修改 i，无顺序点：未定义行为
```

C 标准对「同一表达式内多次修改同一变量且无顺序点」定义为**未定义行为（undefined behavior）**——编译器可以给出任何结果。原因：`+` 的两个操作数求值顺序未指定，`i++` 的自增发生在何时无法确定。<span class="marginnote">「未定义行为」是 C/C++ 对编译器最大的授权：它允许优化器假设「这种代码不存在」，从而做出激进重排。代价是写出这种代码的程序「什么都可能发生」——这是 C 系最危险也最强大的设计。</span>

**辨析｜易错点：** 副作用的问题在于「谁先发生」不可控。即便在顺序确定的语言（Java 从左到右），`f() + g()` 中 `f()` 的副作用也必然先于 `g()`——但若 `f`、`g` 共享状态，结果仍难预料（`f` 改的量可能影响 `g` 的输入）。**「确定顺序」只解决「谁先谁后」，不解决「副作用间的相互依赖」**。

## 3 纯函数与引用透明

函数式语言给出的根本解法是**纯函数（pure function）**：

**纯函数**：满足两条——① 相同输入必得相同输出（无状态依赖）；② 不产生可观察的副作用（不改全局、不写 IO）。

**纯函数的好处**：

**可替换性**：`f(x)` 可安全替换成它的值——编译器可缓存（记忆化）、可重排、可并行。
**可测试性**：不需要设置全局状态，`f(2)` 永远是同一个结果。
**可推理性**：读代码只需看函数体，无需追踪外部状态。<span class="marginnote">纯函数是「数学函数」在程序语言里的化身——`f(x) = x²` 的图景，正是指称语义里「程序是状态函数」的哲学落地。Haskell 把纯函数作为默认，副作用通过单子（Monad）显式封装（第十二篇详讲）。</span>

## 4 公式解析：引用透明的形式定义

引用透明可以精确表述：设 $E$ 是表达式，$\sigma$ 是求值前的存储，$\sigma'$ 是求值后的存储，$v$ 是结果值：

$$
E \text{ 引用透明} \;\Longleftrightarrow\; \forall \sigma,\ \text{eval}(E, \sigma) = (v, \sigma) \quad (\text{存储不变})
$$

即「求值只产出值 $v$，存储 $\sigma$ 原封不动」。

三步拆解：

- **第一步，读等式**：求值结果是一对 `(值, 新存储)`。引用透明要求**新存储 = 旧存储**（$\sigma$ 不变）——求值不改变任何状态。
- **第二步，看推论**：若存储不变，则 $E$ 在任何环境下求值都得同一值 $v$——`E` 可替换为 `v`。这就是「可替换性」的来源。
- **第三步，看反面**：有副作用的 $E$ 使 $\sigma \neq \sigma'$——值 $v$ 仍可算，但「求值改变了世界」。于是 `f(x) + f(x)` 中两次 `f(x)` 的副作用叠加，结果不再等于 `2 × f(x)`。**引用透明的破坏 = 可替换性的丧失**。

**辨析｜易错点：** 「纯函数」与「无副作用」是硬币两面，但概念层次不同：**引用透明**是性质（表达式可替换），**纯函数**是实现（函数满足条件），**副作用**是现象（状态改变）。一个打印日志的函数返回值可测，但它不纯——因为它改变了「输出流」这个状态。

## 5 语言对副作用的策略谱系

| 语言 | 副作用策略 | 典型机制 |
| --- | --- | --- |
| Haskell | 默认禁止，副作用显式封装 | IO 单子、`pure` 函数 |
| Rust | 默认允许，但「可变性」显式 | `mut` 关键字、借用检查隔离可变 |
| Java/C++ | 默认允许，靠纪律约束 | `final`/`const`、函数式接口 |
| C | 允许，且留下未定义行为 | 顺序点规则约束表达式副作用 |
| 现代趋势 | 「显式副作用」 | `IO`/`Effect` 类型、纯函数库 |

<span class="marginnote">Rust 的「默认不可变」是命令式语言里的独特设计：变量默认 `let`（不可变），要可变才写 `let mut`。它不是消灭副作用，而是让「谁可以变」在类型层显式可见——副作用从「暗处」搬到「明处」。</span>

## 6 副作用的管理策略

面对副作用，语言和工程各有应对——「不是消灭，而是管理」。四种主流策略：

**策略一：隔离（isolation）**——纯核心 + 副作用边界：

```python
def compute(data):          # 纯核心：无副作用，好测试
    return sorted(data)

def main():                 # 副作用集中在边界
    raw = read_file("input.txt")     # IO
    result = compute(raw)            # 纯计算
    write_file("out.txt", result)    # IO
```

「能纯的尽量纯，副作用推到外层」——函数式架构的核心实践。

**策略二：显式标注**——让副作用可见：Rust 的 `mut`、Swift 的 `inout`、TypeScript 的 `async`——「副作用发生的位置在类型/语法层可见」。

**策略三：封装**——把副作用包进抽象：类的方法（状态封装）、IO 单子（Haskell 把副作用类型化）、`Promise`/`Future`（异步副作用）——「副作用被容器管理」。

**策略四：纪律**——命名约定与审查：`_` 前缀表示「内部可变」、code review 关注「谁改了共享状态」——最弱但最常见。

| 策略 | 机制 | 强度 |
| --- | --- | --- |
| 隔离 | 纯函数分层 | 强 |
| 显式标注 | `mut`/`inout` | 中 |
| 封装 | 单子/容器 | 中 |
| 纪律 | 命名约定 | 弱 |

**辨析｜易错点：** **「消除副作用 ≠ 消除程序的能力」**——程序必须打印、读文件、发网络请求。副作用无法消除，只能**管理**：「隔离」让它集中在边界、「标注」让它可见、「封装」让它可控。「没有副作用」是理想，「副作用可管理」是现实——**「引用透明是目标，副作用管理是手段」**。

## 7 小结

- **副作用**是求值过程改变状态；来源包括**函数副作用**（改全局、IO）与**表达式副作用**（`i++`、复合赋值）。
- 副作用 + 未指定求值顺序 = **未定义行为**；「确定顺序」只解决先后，不解决相互依赖。
- **纯函数**（同输入同输出 + 无副作用）带来可替换、可缓存、可并行、可测试。
- **引用透明** = 求值不改变存储；其丧失 = 可替换性的丧失。语言策略从「默认禁止」（Haskell）到「显式可变」（Rust）谱系分明。
