## 为什么从错误处理对比开始

程序必然出错——错误处理的机制设计，是语言对「失败」这一常态的态度宣言。三种主流范式主导了五门语言：**异常（exceptions）**（Java、C++、Python）——错误「抛出」沿调用栈传播；**Result 类型**（Rust）——错误作为「返回值」显式处理；**多返回值 + 显式检查**（Go）——错误作为第一个返回值逐个检查。三种范式对「错误是否显式、传播是否自动、是否可忽略」给出不同答案——它们各自的安全性与便利性，是语言设计中最能体现「取舍」的部分。<span class="marginnote">一句话区分：<strong>异常是「隐式的错误传播」</strong>（函数不声明也会抛，调用者不处理也会继续上抛），<strong>Result 是「显式的错误值」</strong>（错误就在返回类型里，必须处理），<strong>Go 是「显式的多返回值」</strong>（`err` 第一、逐处检查）。「错误越显式越安全，越隐式越便利」——三者在这条光谱上取点。</span>

## 1 异常：隐式的错误传播

**异常（exception）**：错误作为「异常对象」抛出，沿调用栈向上传播，直到被 `catch` 捕获。Java/C++/Python 采用。

```java
try {
    int x = Integer.parseInt(s);   // 可能抛 NumberFormatException
} catch (NumberFormatException e) {
    // 处理：转换失败
}
```

异常的优点：

- **自动传播**：中间层函数无需处理错误——错误一路传到「能处理的地方」。
- **分离错误逻辑**：正常流程与错误处理分开（try/catch 块）。
- **携带丰富信息**：异常对象可带类型、消息、堆栈。

代价：

- **隐式性**：函数不声明异常（Java 的 checked 例外除外）——调用者不知道会抛什么。
- **性能**：抛出异常开销大（构建栈回溯）。
- **忽略风险**：`catch` 后吞掉异常——静默失败。<span class="marginnote">「受检异常（checked exception）」是 Java 的独特设计：方法必须声明 `throws XxxException`，调用者必须处理或再声明——「错误在类型里显式」。它曾是革命，但因「被迫处理」的繁琐被广泛批评（许多库用 `RuntimeException` 绕过）。C++/Python 用「非受检异常」——调用者可不处理。受检 vs 非受检，是「显式 vs 便利」的另一战场。</span>

## 2 Result：错误作为返回值

**Result 类型**：函数返回「成功值或错误值」——Rust 的 `Result<T, E>` 是判别联合：

```rust
fn parse_int(s: &str) -> Result<i32, ParseError> {
    // Ok(value) 或 Err(error)
}

let r = parse_int("42");
match r {
    Ok(v) => println!("{v}"),
    Err(e) => eprintln!("parse failed: {e}"),
}
```

Result 的优点：

- **显式性**：错误在**返回类型**里——`Result<i32, ParseError>` 一眼看出「可能失败」。
- **强迫处理**：编译器要求处理 `Err` 分支（穷尽匹配）——错误不可静默忽略。
- **类型安全**：错误是类型化的值，可携带任何信息。

代价：

- **传播繁琐**：每层都要处理/传播——用 `?` 运算符简化（`?` 遇到 `Err` 自动返回）。
- **阅读负担**：到处是 `Result`——「错误处理代码淹没业务逻辑」。<span class="marginnote">Rust 的 `?` 运算符解决了「传播繁琐」：`let v = parse_int(s)?;` 遇到 `Err` 立即从函数返回——「自动传播」但<strong>显式可见</strong>（返回类型是 `Result`）。`?` 是「异常式传播的便利 + Result 式显式的安全」的结合体——这是错误处理设计的最优解之一，Kotlin 的 `runCatching`、Swift 的 `try?` 都类似。</span>

## 3 Go：多返回值 + 显式检查

**Go 的错误处理**：函数返回「结果 + error」两个值，调用者**逐个显式检查**：

```go
f, err := os.Open("x.txt")
if err != nil {
    return err    // 显式传播
}
defer f.Close()
```

Go 哲学的「显式性」：

- 错误是**普通值**（`error` 接口）——可比较、可存、可传。
- 每个可能出错的调用后**必须检查**（`if err != nil`）。
- 无异常、无 `try/catch`——错误处理是最朴素的「返回值 + if」。

**辨析｜易错点：** Go 的错误处理被批评「冗长」（`if err != nil` 风暴），但设计者有意为之——**「显式优于隐式」**：每个错误点都清晰可见，没有「隐藏的传播」。代价：容易「忘了检查」或「检查了但没正确处理」。**「Go 用代码量换心智负担」**——错误处理啰嗦，但每处都明明白白。

## 4 公式解析：三种范式的错误可见性

三种范式可以用「错误是否在函数签名中可见」精确对比。设函数 $f$ 可能失败：

**异常**：

$$
f : A \to B \quad \text{（签名看不出会失败——错误隐式）}
$$

**Result**：

$$
f : A \to \text{Result}\langle B, E \rangle \quad \text{（签名显式声明可失败）}
$$

**Go 多返回值**：

$$
f : A \to \langle B, \text{err} \rangle \quad \text{（err 是显式返回值）}
$$

三步拆解：

- **第一步，异常不可见**：`f : A → B` 签名不含错误——调用者无法从类型知道「会抛异常」。**「隐式传播的代价是签名不可见」**。
- **第二步，Result 可见**：返回类型 `Result<B, E>` 明说「可能失败」——调用者被迫面对。**「错误在类型层面显式」**。
- **第三步，Go 朴素可见**：多返回值让 `err` 成为普通返回——可见但不强制（可忽略 `_`）。**「可见性光谱：异常 < Go < Result」**——显式程度越高，错误越难被忽略，但代码越繁琐。

**辨析｜易错点：** 异常 vs Result 的「可忽略性」：异常可被「吞掉」（`catch` 后不处理）或「静默上抛」；Result 必须 `match` 或 `?`——**无法在类型层面忽略**。「Rust 的错误不可忽略（编译期），Java 的异常可吞掉（运行期）」——这是「错误是否被强制处理」的本质差异。

## 5 错误处理的设计光谱

| 语言 | 范式 | 显式性 | 传播 | 关键机制 |
| --- | --- | --- | --- | --- |
| Java | 异常 | 中（受检部分显式） | 自动 | try/catch、checked |
| C++ | 异常 | 低（非受检） | 自动 | try/catch、RAII 清理 |
| Python | 异常 | 低 | 自动 | try/except |
| Rust | Result | 高 | 显式（`?`） | `Result`、`match`、`?` |
| Go | 多返回 | 高 | 显式 | `if err != nil` |

<span class="marginnote">现代趋势：「Result + 传播糖」正在流行——Rust 的 `?`、Swift 的 `try?`、Kotlin 的 `runCatching`、TypeScript 的 `Result` 风格——「错误显式 + 传播便利」兼得。「可恢复错误用 Result、不可恢复错误用 panic/崩溃」是 Rust 的分层：「业务错误显式处理、程序 bug 直接崩溃」——把错误分成「该处理的」与「不该处理的」。</span>

## 6 小结

- **异常**（Java/C++/Python）：隐式传播、分离错误逻辑——但签名不可见、可被吞掉。
- **Result**（Rust）：错误是显式返回值——类型可见、强迫处理；`?` 简化传播。
- **Go 多返回值**：`err` 作为普通值显式检查——每处可见，但代码冗长。
- 错误可见性光谱：**异常 < Go < Result**；显式程度越高越安全越繁琐；现代趋势是「Result + `?` 式传播糖」。
