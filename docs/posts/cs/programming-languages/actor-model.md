## 为什么从 Actor 模型开始

上一节的消息传递还停留在「发送/接收」原语；**Actor 模型**把它升级为一套完整的并发世界观：**并发程序 = 一群自主的 Actor 通过异步消息协作**。每个 Actor 有自己的状态、邮箱与行为，只响应消息、不共享任何东西。它由休伊特 1973 年提出，经 Erlang 发扬光大（电信级容错），如今是分布式系统、微服务、以及大数据流处理的流行模型。理解 Actor，就理解了「无共享并发」在工业界的完整形态：如何创建、如何通信、如何容错。<span class="marginnote">Actor 的三原则（Hewitt）：① Actor 之间只通过<strong>异步消息</strong>通信；② 每个 Actor 处理消息时<strong>独占自己的状态</strong>（无共享）；③ Actor 可以<strong>创建新 Actor</strong> 并<strong>改变自己的行为</strong>。这三条构成「自治实体 + 消息协作」的完整图景。</span>

## 1 Actor 的三要素

**Actor（行动者）**：一个并发计算实体，由三部分组成：

- **状态（state）**：Actor 私有的数据——只有自己可访问。
- **行为（behavior）**：收到消息时的处理逻辑（可改变状态、发消息、创建 Actor）。
- **邮箱（mailbox）**：收到的消息队列——异步送达，先到先处理（或按选择）。

```elixir
defmodule Counter do                    # Elixir（Erlang VM）
  def loop(count) do
    receive do
      {:increment, from} ->
        send(from, {:ok, count + 1})
        loop(count + 1)                 # 更新状态，继续循环
    end
  end
end
```

Actor 的「loop」模式：接收消息 → 处理 → 递归调用自身（携带新状态）——**状态在递归参数里流转**，无共享可变状态。<span class="marginnote">Actor 的状态更新靠「递归重入」而非「修改变量」：`loop(count+1)` 开启「下一个自己」，携带新状态。这继承了函数式「状态即参数」的哲学——Actor 里没有共享的可变内存，只有每个 Actor 自己的状态流转。</span>

## 2 消息的异步性与有序性

Actor 通信是**异步**的：发送方发完即走，消息进接收方邮箱。<span class="marginnote">Erlang 对同一发送方到同一接收方的消息保证<strong>顺序性</strong>——但不同发送方之间的顺序不保证。这个「单源有序」保证让协议设计可预测（请求-响应对不乱序），又保留异步的灵活性。</span>

```erlang
Pid ! {msg, self()},   % 发送（! 是发送运算符）
receive
  {reply, Result} -> Result   % 接收并模式匹配
end
```

发送方把自己的 `Pid` 放进消息——接收方处理完后回消息给发送方。**请求-响应（request-reply）**模式靠「把回信地址带上」实现。

## 3 Actor 的容错哲学：让它崩溃

Actor 模型最独特的贡献是**容错**：**「让它崩溃（let it crash）」**——Actor 状态出错时，不试图挽救，而是**直接崩溃**，由**监督者（supervisor）**重启它。

```
supervisor
  ├─ worker1（崩溃 → 监督者重启）
  └─ worker2
```

Erlang 的「监督树（supervision tree）」：监督者监控子 Actor，子崩溃即重启（或升级处理）。**错误隔离**——一个 Actor 崩溃不影响其他 Actor（它们不共享状态）。<span class="marginnote">「让它崩溃」是反直觉但深刻的哲学：与其在错误状态里继续（状态可能已被污染），不如干净地重启。因为 Actor 无共享状态，重启一个 Actor 不牵连他人。这是「错误隔离 + 快速失败 + 自动恢复」的组合，让 Erlang 系统做到「九十九个九」的可用性。</span>

## 4 公式解析：Actor 系统的行为

Actor 系统的整体行为可以形式化为「消息驱动的状态迁移」。设 Actor $a$ 有状态 $s$、行为 $f$，收到消息 $m$：

$$
f(s, m) = \langle s', \ \text{msgs}' \rangle \quad \text{（新状态 + 发出的消息）}
$$

系统的并发执行：

$$
\text{system}(t+1) = \bigcup_{a} f_a(s_a(t), \ m_a(t)) \quad \text{（各 Actor 独立推进）}
$$

三步拆解：

- **第一步，单 Actor 迁移**：收到消息 $m$，行为 $f$ 产出新状态 $s'$ 与一组新消息（发给其他 Actor）。**一次收信 = 一次状态迁移**。
- **第二步，系统推进**：所有 Actor 并行执行自己的迁移——它们之间**只经消息耦合**（$m$ 来自其他 Actor 的 msgs'），无共享数据。
- **第三步，看并发正确性**：因为 Actor 间无共享状态，**迁移可以任意交错而互不干扰**——并发正确性由「无共享」结构性保证，无需锁。「**每个 Actor 单线程处理消息，Actor 之间无共享**」——这就是 Actor 模型正确性的全部基础。

**辨析｜易错点：** Actor 保证「单个 Actor 内消息串行处理」，**不保证**「全局顺序」。不同 Actor 的处理交错不受控制——因此**跨 Actor 的全局状态一致性需要显式协议**（如两阶段提交）。「Actor 模型不是分布式事务的银弹」——它解决「无共享并发」，不解决「跨实体一致性」。

## 5 Actor 模型的工业实现

- **Erlang/Elixir**：Actor 的工业标准——BEAM 虚拟机每 Actor 一进程（轻量），监督树容错。
- **Akka**（JVM）：Java/Scala 的 Actor 框架——`ActorSystem`、`Props`、`ask`/`tell`。
- **Orleans**（.NET）：Virtual Actor——「让 Actor 看起来总在运行」的云原生抽象。
- **现代影响**：微服务、「分布式实体」、以及 LLM 多智能体框架（Actor 思想的软件形态）。<span class="marginnote">Actor 模型已从「并发语言机制」演化为「分布式架构思想」：微服务（每个服务是自治实体、消息通信）、事件驱动架构（异步消息）、以及多智能体系统（每个 agent 独立决策、消息协作）都带有 Actor 的影子。「自治 + 消息 + 容错」是分布式软件的组织范式。</span>

## 7 小结

- **Actor** = 状态 + 行为 + 邮箱；只经异步消息通信，无共享数据。
- **消息异步送达邮箱**；单源有序；请求-响应靠「携带回信地址」实现。
- **容错哲学「让它崩溃」**：Actor 崩溃即重启，监督树隔离错误——无共享让重启不牵连他人。
- 系统行为 = 各 Actor 独立的状态迁移，经消息耦合；「单 Actor 串行 + 跨 Actor 无共享」是并发正确性的结构性保证。
