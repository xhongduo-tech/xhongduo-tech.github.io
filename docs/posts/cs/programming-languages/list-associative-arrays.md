## 为什么从列表与关联数组开始

数组的下标必须是连续整数，这是它的枷锁。真实数据往往需要两种更自由的形态：**列表**——长度随时可变、可以插入删除的同质序列；**关联数组**——用任意键（而非 0..n-1 的整数）寻址的容器。这两者构成了现代编程的「日常容器」：Python 的 `list` 与 `dict`、Rust 的 `Vec` 与 `HashMap`、Go 的 `slice` 与 `map`。<span class="marginnote">数组是「内存的语法」，列表是「生活的语法」：没有几个程序会在运行前知道最终要放多少元素。语言的抽象级别，正体现在它是否把「动态长度」与「任意键」做进类型与库的一等位置。</span>

## 1 列表：可变长度的同质序列

**列表（list）**：同质元素的序列，长度可动态变化，支持在任意位置插入、删除。<span class="marginnote">「同质」继承自数组——但注意函数式语言（Scheme、Haskell）的 `list` 是<strong>不可变</strong>的链表：`cons`（把新元素接到头部）是 $O(1)$，随机访问却是 $O(n)$。同样是「list」，命令式语言的 list 与函数式的 list 数据结构完全不同。</span>

不同语言的「列表」实现差异巨大：

| 语言 | 类型 | 底层实现 | 复杂度画像 |
| --- | --- | --- | --- |
| Python | `list` | 动态数组 | 尾部增删 $O(1)$ 均摊，头部 $O(n)$ |
| Java | `ArrayList` | 动态数组 | 同上 |
| Java | `LinkedList` | 双向链表 | 头尾 $O(1)$，中间访问 $O(n)$ |
| Scheme | `list` | 单链表（不可变） | `cons`/`car`/`cdr` 全 $O(1)$ |
| Rust | `Vec` | 动态数组 | 尾部 $O(1)$，所有权语义内建 |

**辨析｜易错点：** 同样叫「列表」，Python 的 `list` 是动态数组——下标访问是 $O(1)$ 随机访问，但头部插入是 $O(n)$；而 Scheme 的 list 正好相反。**看名字猜复杂度是危险的**：一定要看底层结构。语言手册说的「list」可能不是链表。

## 2 关联数组：任意键的寻址

**关联数组（associative array）**：把「键」映射到「值」的容器，键的类型不限为整数，可以是字符串、元组等。<span class="marginnote">在不同语言里它叫法各异：Python 的 `dict`、Rust 的 `HashMap`、Java 的 `HashMap`、Perl 的 `hash`、JavaScript 的对象/`Map`。叫法不同，本质一致：<strong>键 → 值</strong>的查询结构。</span>

```python
scores = {}                # 空字典
scores["alice"] = 95       # 用字符串键寻址
scores["bob"] = 87
print(scores["alice"])     # 95
```

关联数组的语义约定：

**键唯一**：同一键只对应一个值，后写覆盖前写。
**查询语义**：查不存在的键时行为分歧——Python 抛 `KeyError`，Rust 的 `HashMap::get` 返回 `Option`，JavaScript 返回 `undefined`。<span class="marginnote">「缺键时返回什么」是类型系统的试金石：Rust 用 `Option` 把「可能没有」显式编码进类型，强迫调用者处理缺失；Python 抛异常把错误推向运行期。前者静态、后者动态——这呼应第五篇静态/动态类型之争。</span>

## 3 关联数组的实现：哈希表

关联数组的经典实现是**哈希表（hash table）**：对键做哈希函数得到桶号，桶里存「键值对」。

**哈希表的三个部件**：

**哈希函数 $h$**：把任意键映射到 $[0, m-1]$（$m$ 为桶数）。<span class="marginnote">好哈希要「均匀」：相近的键也尽量散到不同的桶，避免退化。字符串哈希、加密哈希都是围绕这一目标的设计。</span>
**冲突解决**：两个不同键映射到同一桶（**冲突/collision**）时怎么办——链地址法（每个桶一条链）或开放寻址（线性探测）。<span class="marginnote">Python 用开放寻址，Java `HashMap` 用链地址 + 树化（桶链过长时转红黑树，见第三级《数据结构》的红黑树）。</span>
- **负载因子与扩容**：元素数超过「桶数 × 负载因子」时重哈希扩容，均摊后插入仍是 $O(1)$。

## 4 公式解析：哈希表的期望查询时间

设桶数为 $m$、元素数为 $n$，**负载因子（load factor）**为 $\alpha = n/m$。在「简单一致哈希」假设下，期望的冲突次数：

$$
\mathbb{E}[\text{探针数}] = \frac{1}{1 - \alpha} \quad (\text{开放寻址})
$$

三步拆解：

- **第一步，理解 $\alpha$**：负载因子是「每个桶平均装多少元素」。$\alpha$ 接近 0 时空桶多、探针少；$\alpha$ 接近 1 时几乎满，冲突剧增。
- **第二步，看公式含义**：开放寻址下平均探针数是 $\frac{1}{1-\alpha}$。当 $\alpha = 0.5$ 时平均 2 次探针；$\alpha = 0.9$ 时平均 10 次——**代价在接近满桶时指数级恶化**，所以哈希表会提前扩容（Python 在 $\alpha \approx 2/3$ 时扩容）。
- **第三步，看均摊结论**：虽然单次插入可能 $O(n)$（扩容拷贝），但扩容不频繁，**均摊后所有操作仍是 $O(1)$**。这就是哈希表「平均 $O(1)$」的严格含义。

**辨析｜易错点：** 哈希表的 $O(1)$ 是**期望意义**下的，不是最坏情况。若哈希函数设计差或键分布恶意（如字符串都哈希到同一桶），会退化为 $O(n)$——这就是**哈希洪泛（hash flooding）**拒绝服务攻击的原理，现代语言在哈希函数中引入随机种子来防御。

## 5 从容器到语言设计

- **可哈希性**：作为键的类型必须可哈希且不可变——Python 要求键是「可哈希对象」，元组可以当键、列表不行（列表可变）。
- **迭代顺序**：哈希表不保证顺序。Python 3.7 起 `dict` 保持插入顺序（实现细节升格为语言保证），Rust `HashMap` 不保证。<span class="marginnote">「依赖迭代顺序的代码」在换语言/换版本后可能静默变化——容器语义的微小差异是跨语言移植最常见的暗坑。</span>
- **一等公民**：Python/Ruby/JS 把字面量语法做进语言（`{...}`），使关联数组成为最自然的编程对象；Rust/Java 则需通过泛型容器显式构建。

## 6 容器选择的工程经验

列表与关联数组的「选型」有一批成熟经验——按操作特征选容器：

**列表选型**：尾部增删、随机访问为主 → 动态数组（Python `list` / Rust `Vec`）；头部/中部频繁插入删除 → 链表（Java `LinkedList`）。但注意——**现代实践「几乎总是用动态数组」**：链表的内存不连续导致缓存不友好，实际性能常不如数组；除非有「大量中间插入」且测得是瓶颈。

**关联数组选型**：`HashMap`（哈希，O(1) 期望）适合「按键查值」；`TreeMap`/`BTreeMap`（平衡树，O(log n)）适合「需要有序遍历」；`dict`/`LinkedHashMap` 适合「保持插入顺序」。**「哈希快但无序，树慢但有序」**——按「要不要顺序」选。

| 需求 | 推荐 | 理由 |
| --- | --- | --- |
| 尾部增删 + 随机访问 | 动态数组 | O(1) 均摊 + 缓存友好 |
| 中间频繁插入 | 链表 | O(1) 插入（已知位置） |
| 按键查值 | 哈希表 | O(1) 期望 |
| 有序遍历 + 查值 | 平衡树 | O(log n) + 有序 |

**辨析｜易错点：** **「容器选错 = 性能灾难」**：在动态数组头部插入是 O(n)（移动所有元素）——百万元素插入一次就卡顿。「读代码时看容器类型就能预估复杂度」——`list.insert(0, x)` 在 Python 里是 O(n)，很多人误以为 O(1)。「选容器 = 声明复杂度预算」，容器类型本身就是算法复杂度的文档。

## 7 小结

- **列表**是可变长度同质序列，但「list」底层可能是动态数组或链表——复杂度画像天差地别。
- **关联数组**用任意键寻址，是「键 → 值」的查询结构；缺键语义因语言而异。
- 经典实现是**哈希表**：哈希函数 + 冲突解决 + 负载因子扩容，均摊 $O(1)$。
- 哈希的 $O(1)$ 是**期望意义**；哈希洪泛攻击利用退化情形，随机种子是防线。
