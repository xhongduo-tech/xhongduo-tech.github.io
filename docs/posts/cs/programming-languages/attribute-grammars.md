## 为什么从属性文法开始

我们已经学会用上下文无关文法（CFG）描述程序的**语法**——`E → E + T` 这类产生式决定了哪些符号串是合法的表达式。但语法只能回答「长什么样」，回答不了「是什么意思」。`int x = "abc";` 在 C 语言里能通过语法检查却违反类型规则，「变量在使用前必须声明」这类约束完全在语法之外。它们属于**静态语义（static semantics）**：编译阶段就能检查、却无法用 CFG 表达的含义规则。**属性文法（attribute grammar）**正是描述静态语义的经典工具，它由克努斯在 1968 年提出，是连接「语法」与「语义」的第一座桥梁。<span class="marginnote">属性文法把语义信息「挂在」语法树上：每个语法结点携带若干属性，通过规则在这些属性之间传递计算。它与后面要学的类型检查、代码生成都有着直接的血缘关系。</span>

## 1 从语法树到属性

上下文无关文法的分析过程会产出一棵**语法分析树（parse tree）**：内部结点是语法符号（非终结符），叶子是终结符。<span class="marginnote">属性文法不改变语法结构本身——它只往这棵树上「贴标签」。同一个 CFG 加上不同的属性规则，就能描述完全不同的语义，这正是「语法与语义分离」思想的体现。</span>

**属性（attribute）**：与语法树中某个结点相关联的任意信息片段，例如该表达式的结果类型、变量的地址、语句的代码长度。

**属性文法（attribute grammar）**：一个属性文法 $AG = (CFG, A, R, C)$，其中：

$CFG$ 是底层的上下文无关文法；
$A$ 是属性集合，每个属性归属于某个文法符号；
$R$ 是**语义规则（semantic rules）**集合，每条规则与一条产生式绑定；
$C$ 是**谓词集合（predicates）**，用于表达静态语义约束。

## 2 综合属性与继承属性

属性按「从哪来」分成两大类，这是本节的枢纽：

**综合属性（synthesized attribute）**：由产生式**右侧**的子结点计算出来，向上传递。<span class="marginnote">「自下而上」：子结点的信息汇总成父结点的信息。例：表达式的类型由操作数类型综合而来，代码长度由子代码段长度求和得到。</span>

**继承属性（inherited attribute）**：由产生式**左侧**的父结点（或兄弟结点）传入，向下传递。<span class="marginnote">「自上而下」：上下文信息渗入子结点。例：变量声明的符号表信息必须传给使用它的语句——「这个标识符是什么类型」往往继承自外层声明的环境。</span>

判断技巧：看属性值依赖谁。**凡是依赖自己子树内部的信息，是综合属性；凡是依赖父结点或兄弟结点带进来的上下文，是继承属性**。

## 3 表达式求值：一个经典例子

设 CFG 为：

$$E \to E_1 + T \;\mid\; T, \qquad T \to T_1 * F \;\mid\; F, \qquad F \to (E) \;\mid\; \text{digit}$$

定义综合属性 `val`（表达式的数值），语义规则如下：

| 产生式 | 语义规则 |
| --- | --- |
| $E \to E_1 + T$ | $E.\text{val} = E_1.\text{val} + T.\text{val}$ |
| $E \to T$ | $E.\text{val} = T.\text{val}$ |
| $T \to T_1 * F$ | $T.\text{val} = T_1.\text{val} \times F.\text{val}$ |
| $T \to F$ | $T.\text{val} = F.\text{val}$ |
| $F \to (E)$ | $F.\text{val} = E.\text{val}$ |
| $F \to \text{digit}$ | $F.\text{val} = \text{digit}.\text{lexval}$ |

整棵树自底向上求值：`2 + 3 * 4` 的分析树中，最底层 `2`、`3`、`4` 的 `val` 由 `digit.lexval` 综合而来，`3` 与 `4` 向上综合成 `T.val`（`3 × 4 = 12`），再与 `2` 综合成根结点 `E.val`（`2 + 12 = 14`）。<span class="marginnote">注意加法的右结合（$E \to E_1 + T$）如何让乘法比加法先综合：<strong>属性求值顺序完全由语法结构决定</strong>，这比手工写求值器更系统、更可证明。</span>

## 4 属性文法与静态语义检查

属性文法最常见的工业用途是**类型检查**。以声明语句 `int x;` 为例，可定义：声明结点有一个继承属性 `expected_type` 向下传给标识符，标识符再综合出一个 `actual_type` 返回给声明结点，最后用**谓词**验证两者相等：

$$\text{declare\_type} \to \text{type}\ \text{id}: \quad \text{predicate}(\text{id.type} = \text{type.name})$$

谓词不产生新属性，只做「成立 / 不成立」的断言。编译器中，属性求值器逐结点执行规则，一旦某个谓词不满足，就报出**静态语义错误**——例如「赋值类型不匹配」「变量未声明」。<span class="marginnote">现代编译器并不真的为每个语法树执行属性规则，而是把它翻译成符号表查表 + 类型检查代码。但属性文法是理解这些检查「在算什么」的最佳模型——也是生成式编译器（如 YACC 的语义动作）的理论原型。</span>

## 5 公式解析：属性求值顺序

求值顺序问题可以用一个依赖图来理解。**属性依赖图（dependency graph）**的每个结点是一个属性实例，边 $A \to B$ 表示「$B$ 的值需要先知道 $A$」。对所有综合属性，依赖边都从子结点指向父结点，因此：

$$
\text{一个只含综合属性的属性文法，求值顺序就是后序遍历}
$$

三步拆解这条结论：

- **第一步，翻译**：每个产生式的语义规则 $X.\text{val} = f(Y_1.\text{val}, \dots)$ 都变成依赖图里的多条边 $Y_i \to X$。
- **第二步，观察方向**：所有边都从「语法树中的后代」指向「祖先」，因而无环。
- **第三步，得到算法**：对语法树做一次**后序遍历**（先子树、后父结点），每访问一个结点就执行它的语义规则，即可保证所有属性在用到时已经算好。

**辨析｜易错点：** 综合属性与继承属性的混合会破坏「后序遍历就够」的简单局面。若某规则同时需要继承属性与综合属性，依赖图可能有环（如 `A` 的继承属性依赖 `B` 的综合属性、而 `B` 的继承属性又依赖 `A` 的综合属性），此时不存在合法的求值顺序。实际编译器通过限制继承属性的来源（只允许来自父结点与左兄弟）来保证无环。

## 6 属性求值器：从理论到编译

理论属性文法的「求值」在实际编译器中是怎么做的？**属性求值器（attribute evaluator）**是执行语义规则的组件，有几种实现策略：

**树遍历求值（tree-walking evaluator）**：按依赖顺序遍历语法树执行规则。纯综合属性用后序遍历；含继承属性时先「从上到下」传继承属性、再「从下到上」综合。

**递归下降求值（recursive-descent evaluator）**：与递归下降语法分析结合——每个非终结符对应一个递归函数，属性作为函数参数（继承属性传入）与返回值（综合属性传出）。

**生成式求值器（generated evaluator）**：用工具（如 YACC、ANTLR）从属性文法**自动生成**求值代码——语法分析器 + 语义动作一次产出。这是工业编译器的主流做法：`$$`（综合）与 `$1`、`$2`（右部成分）就是属性规则的工程形态。

| 求值策略 | 适用 | 例子 |
| --- | --- | --- |
| 树遍历 | 教学/原型 | 手写属性求值 |
| 递归下降 | 手工编译器 | 手写递归下降 + 属性传参 |
| 自动生成 | 工业编译 | YACC/ANTLR 语义动作 |

**辨析｜易错点：** 属性文法与「语义动作（semantic action）」的关系：YACC 的 `$$ = `$1` + `$2`` 语义动作就是属性规则的「命令式实现」——它在归约时执行，用 `$$`/`$n` 引用属性。**「属性文法是语义动作的理论原型，语义动作是属性文法的工程实现」**——理解属性文法，读 YACC/ANTLR 的语义动作就一目了然。

## 7 小结

- **属性文法** = CFG + 属性集合 + 语义规则 + 谓词，用于描述静态语义。
- 属性分两类：**综合属性**（子结点向上汇总）与**继承属性**（父结点/上下文向下传入）。
- 求值通过**属性依赖图**排序；纯综合属性可后序遍历求值。
- 谓词用于**静态语义检查**（类型一致性、声明约束），是现代编译器符号表与类型检查的理论原型。
