## 为什么从 BEAM 开始

如果说 JVM 是「高性能通用」的代表，**BEAM（Bogdan/Björn's Erlang Abstract Machine）**就是「容错并发」的极致——Erlang/Elixir 的运行时，为「99.999% 可用性」的电信系统而设计。BEAM 的独特之处：**进程**（轻量、隔离、百万级）、**消息传递**（进程间不共享）、**监督树**（崩溃自动恢复）。这三个机制让 Erlang 系统做到「出了问题不宕机」——这与 JVM「出问题重启 JVM」、Rust「出问题编译期拦」都不同，是「运行时容错」的哲学。理解 BEAM，是理解「如何构建永不宕机的系统」。<span class="marginnote">BEAM 的出身：爱立信为<strong>电信交换机</strong>设计——交换机不能宕机（电话不能断）。于是 BEAM 的核心目标是「<strong>软件容错</strong>」：进程崩溃是常态、隔离是默认、恢复是自动。与 JVM 的「GC 管内存」不同，BEAM 把「容错」作为运行时的一等公民——「不是不出错，而是错了也不停」。</span>

## 1 进程：轻量隔离的执行单元

**BEAM 进程（process）**：轻量并发单元——**不共享任何内存**，每个进程有独立的堆与栈。

- **百万级**：进程极轻（几 KB），一台机器可运行数百万个——「一请求一进程」天然可行。
- **完全隔离**：进程间不共享状态——一个进程崩溃不影响其他（无共享即无连锁）。
- **GC 独立**：每个进程有自己的堆——GC 只在**单个进程**内发生，不影响其他进程（无全局停顿）。<span class="marginnote">BEAM 进程 ≠ OS 线程 ≠ goroutine：比线程轻（无内核参与）、比 goroutine 更隔离（独立堆、独立 GC）。「进程 = 内存隔离 + 崩溃隔离」——这是 Erlang 容错的基础：「一个进程的崩溃不会污染邻居」。对比 JVM：线程共享堆（一个 OOM 全崩），BEAM 进程独立堆（一个进程 OOM 只死自己）。</span>

## 2 消息传递：无共享通信

BEAM 进程间**只通过消息传递**通信——异步、不共享：

```elixir
send(pid, {:hello, self()})   # 发送消息
receive do
  {:hello, from} -> send(from, :hi)
end
```

消息传递的设计：

- **异步**：发送方不阻塞——消息进接收方邮箱。
- **不可变数据**：消息是不可变值——发送「副本/所有权」，无别名风险。
- **选择性接收**：`receive` 按模式匹配选取消息——可以跳过不相关的消息。<span class="marginnote">「无共享」让 BEAM 的并发正确性「免费」：没有锁、没有竞态、没有数据竞争——因为根本没有共享数据。对比 JVM（锁 + 竞态）与 Rust（编译期检查）——BEAM 用「结构性消除」：不共享，就不需要同步。「消息传递 + 不可变」是 BEAM 并发安全的三位一体。</span>

## 3 监督树：崩溃自动恢复

**监督树（supervision tree）**：BEAM 容错的灵魂——进程按树组织，**监督者（supervisor）**监控子进程，子崩溃即按策略重启：

```
Application 监督者
├── worker1（崩溃 → 重启）
├── worker2
└── 子监督者
    ├── worker3
    └── worker4
```

**「让它崩溃（let it crash）」**哲学：worker 出错不试图挽救，直接崩溃；监督者负责重启（或升级处理）。错误被**隔离 + 恢复**——系统整体继续运行。<span class="marginnote">「让它崩溃」的深层逻辑：出错时的进程状态已不可信（可能半更新），修复它不如重启它（进程无状态、从初始化重来）。监督树的「重启策略」（一次性、逐个、随机）与「强度限制」（1 秒内重启 N 次则升级）让「恢复」可控。「可用性不是不崩，而是崩了能自动回来」——这是电信级可靠性的精髓。</span>

## 4 公式解析：BEAM 的调度模型

BEAM 的并发调度可以用「协作式 + 递减预算」刻画。每个进程有**减少量预算（reduction budget）**：

$$
\text{每进程每轮调度执行} \le R \ \text{reductions} \quad \text{（R 默认约 4000 次调用）}
$$

$$
\text{预算用尽} \Rightarrow \text{进程被抢占，调度器换下一进程}
$$

三步拆解：

- **第一步，协作式调度**：进程自己执行，直到「预算用尽」——不是被内核打断（非抢占），而是「到点让位」（协作）。
- **第二步，公平性**：每个进程每轮有相等的预算 R——保证「百万进程都能推进」，无进程饿死。
- **第三步，看 IO 等待**：进程在**消息队列空**（等消息）或**IO 等待**时，不占预算（休眠）——**「等 IO 不耗 CPU」**，这让百万「等消息的进程」几乎零开销。**「BEAM 调度 = 公平预算 + 等待不耗」**——这是它支撑海量并发进程的机制。

**辨析｜易错点：** BEAM 进程是**协作式**调度，不是抢占式——**单个进程内的 CPU 密集长计算**会占住它所在的调度线程（不会自动让位）。「百万进程适合 IO 密集；CPU 密集长任务要拆小或移到 NIF（native）」——「协作式 = 进程自己负责不霸占」是 BEAM 的使用常识。

## 5 BEAM 的工程位置与影响

- **电信与消息系统**：WhatsApp（5 亿用户，每台机器百万连接）、RabbitMQ、CouchDB——「高可用 + 高并发」场景。
- **Elixir/Phoenix**：Web 框架——「百万连接 WebSocket」成为卖点。
- **对现代并发的影响**：Actor 模型（前面讲过）、「进程隔离 + 监督恢复」的哲学，深刻影响微服务与云原生设计（Kubernetes 的「Pod 崩溃重启」与监督树异曲同工）。<span class="marginnote">BEAM 的思想已溢出 Erlang 生态：<strong>「崩溃隔离 + 自动恢复」</strong>就是 Kubernetes 的 Pod/Deployment 模型、「熔断 + 重试」的微服务模式——「系统级容错」成为现代架构共识。Actor 模型的工业实现（Akka）、以及「消息传递优先」的并发哲学，都从 BEAM 的实践中获得验证。VM 不只是执行代码——BEAM 证明了 VM 可以承载「容错哲学」。</span>

## 6 热代码升级：BEAM 的独门绝技

BEAM 有一项其他 VM 少有的能力——**热代码升级（hot code upgrade）**：**不重启系统**地替换运行中的代码模块。电信系统不能停机升级，BEAM 因此支持「运行中换代码」：

**机制**：每个模块可以同时存在**两个版本**（current 与 old）；新调用用新版本，仍在跑的旧进程用旧版本跑完。`code:load_file(module)` 或 Elixir 的 `recompile` 触发升级。

**版本协调**：进程可以「等到安全点再切换」（`sys:suspend`、`code_change` 回调）——「让进程在已知状态完成版本迁移」。

**实践**：Erlang/Elixir 系统（WhatsApp、RabbitMQ）靠它做到「升级不宕机」——「零停机部署」是 BEAM 的招牌能力。

| 能力 | BEAM | JVM | 原生（C/Rust） |
| --- | --- | --- | --- |
| 热代码升级 | 内建 | 需外部工具（Arthas） | 需动态加载库 |
| 进程崩溃恢复 | 监督树内建 | 线程崩溃即 JVM 崩 | 进程崩溃即程序崩 |

**辨析｜易错点：** 热升级不是「随便换代码就行」——「两个版本同时存在」意味着**数据结构兼容**要设计（新版本要能读旧版本的状态）。「热升级的便利建立在『向后兼容』的纪律上」——这不是免费的魔法，而是「电信级可靠性」要求下的设计。「能热升级 ≠ 该频繁热升级」——它解决「无法停机」的场景，不是「懒得重新部署」的借口。

## 7 小结

- **BEAM 进程**：轻量、百万级、独立堆——完全隔离，「崩溃不传染」。
- **消息传递**：异步、不可变、无共享——「不共享就不需要同步」，并发安全结构性保证。
- **监督树**：worker 崩溃 → supervisor 重启——「让它崩溃」+ 自动恢复，可用性靠「能回来」而非「不崩」。
- BEAM 调度 = 公平预算 + 等待不耗 CPU——支撑海量并发进程；协作式调度要求「进程不霸占」；容错哲学影响现代云原生架构。
