## 为什么从算术表达式开始

第七篇进入语句级的世界，而一切语句的「计算内核」是**表达式（expression）**——由运算符与操作数组成的求值单元。算术表达式的两个核心机制是**优先级（precedence）**与**结合性（associativity）**：它们决定 `a + b * c` 先算哪个、`a - b - c` 向左还是向右。我们在第二篇《二义性、运算符优先级与结合性》里已经从文法角度看过它们，这一节从「求值顺序」的角度看：优先级解决「算哪个」，结合性解决「同级的先算哪个」，而**操作数求值顺序**是第三条常常被忽略的规则。<span class="marginnote">这三条规则的分工：<strong>优先级</strong>决定运算符之间的先后（`*` 先于 `+`），<strong>结合性</strong>决定同级运算符的先后（`-` 向左结合），<strong>操作数顺序</strong>决定一个运算符内左右操作数谁先求值。前两条几乎人人皆知，第三条却是无数隐蔽 bug 的来源。</span>

## 1 优先级：运算符的等级

**优先级（precedence）**：运算符之间的求值次序。`a + b * c` 中 `*` 优先级高于 `+`，等价于 `a + (b * c)`。

各语言的优先级体系大同小异（都继承数学惯例），但细节不同：

| 运算符类别 | C/Java | Python |
| --- | --- | --- |
| 乘法类 | `* / %` | `* / // %` |
| 加法类 | `+ -` | `+ -` |
| 移位 | `<< >>` | `<< >>` |
| 关系 | `< <= > >=` | `< <= > >=` |
| 相等 | `== !=` | `== !=` |
| 逻辑与 | `&&` | `and` |
| 逻辑或 | `\|\|` | `or` |

**辨析｜易错点：** Python 的 `and`/`or` 优先级**低于**比较运算——所以 `a < b and b < c` 无需括号。而 C 的位运算 `&`、`^`、`|` 优先级在比较之下、逻辑之上，`a & b == c` 被解析为 `a & (b == c)`——这是 C 新手最常见的表达式陷阱之一。**优先级表必须查，不要猜**。

## 2 结合性：同级的先后

**结合性（associativity）**：当多个同优先级运算符并列时，结合顺序。

- **左结合（left associative）**：`a - b - c` = `(a - b) - c`。减法、除法、取模、C 的赋值。
- **右结合（right associative）**：`a = b = c` = `a = (b = c)`。赋值、幂运算（Python `**`）、一元负号。

<span class="marginnote">结合性由文法决定（第二篇讲过）：左递归文法产生左结合，右递归产生右结合。特别地，Python 的幂运算是右结合（2 的「3 的 2 次方」次方等于 512 而非 64），而 C 没有幂运算符——语言差异是真实的。</span>

**辨析｜易错点：** 浮点运算**不满足结合律**：`(a - b) - c` 与 `a - (b - c)` 在浮点下结果不同（舍入）。左结合是「语法规定」，不是「数学恒等」——编译器也**不能**把浮点 `a - b - c` 重新结合（除非确认无舍入影响），这限制了优化空间。

## 3 操作数求值顺序：被忽略的第三条规则

**操作数求值顺序（operand evaluation order）**：一个运算符的左右操作数，谁先求值？`f() + g()` 中先调 `f` 还是先调 `g`？

不同语言的策略：

- **C/C++**：**未定义**。`f() + g()` 先调谁由编译器决定——若 `f` 与 `g` 有共享状态副作用，结果不确定。
- **Java**：**从左到右**固定，且保证「先完整求值左操作数」。
- **Python**：从左到右。
- **Haskell**：惰性求值（第十二篇详讲），操作数可能根本不求值。

<span class="marginnote">C 故意把操作数顺序留为「未指定」，给编译器优化（寄存器分配、重排）最大自由；代价是依赖顺序的程序是未定义行为。Java 选择「从左到右」牺牲一点优化，换取可预测语义——这是「性能 vs 可预测」的又一权衡实例。</span>

## 4 公式解析：中缀表达式的求值模型

中缀表达式的求值可以理解为一个递归过程：按优先级与结合性把表达式折叠成语法树，再自底向上求值。

$$
\text{eval}(E) = \begin{cases}
v & E \text{ 是数字/变量} \\
\text{apply}(\text{op},\ \text{eval}(E_1),\ \text{eval}(E_2)) & E = E_1\ \text{op}\ E_2
\end{cases}
$$

三步拆解：

- **第一步，分解**：表达式按「优先级最低的运算符」拆成两半——`a + b * c` 拆成 `a` 与 `b * c`（`+` 优先最低）。
- **第二步，递归**：两半分别递归求值。`b * c` 内部再按优先级拆 `b`、`c`。树的形状完全由优先级与结合性决定。
- **第三步，组合**：自底向上应用运算。**树中「先算」的节点 = 优先级高或结合性先的运算符**——语法树的形状就是求值顺序的可视化。

**辨析｜易错点：** 表达式求值顺序的「语法树」与「操作数顺序」是两层：语法树决定运算符应用的先后（结构层），操作数求值顺序决定同一运算符两个参数谁先算（叶子层）。`f() * g()` 中 `*` 的两边谁先求值是操作数顺序问题，与优先级无关——**别把三层规则混成一层**。

## 5 从表达式到语言设计

- **括号**：`()` 覆盖一切优先级，是最终逃生口；可读性优先时宁可多用括号。
- **复合运算符**：`+=`、`*=` 结合赋值与运算（下一节细讲）。
- **求值副作用**：`i++ + i++` 在 C 是未定义行为，在 Java 是确定结果——**表达式内禁止有副作用的表达式（副作用），是现代语言的趋势**（第七篇末尾专文讨论）。<span class="marginnote">「优先级表 + 括号」是表达式的语法衣装；「求值顺序确定性」是语义品质。现代语言（Rust、Swift）倾向让求值顺序完全确定、并劝阻「赋值表达式作值用」（Rust 的赋值返回 `()`），把整类顺序 bug 从语言层面消灭。</span>

## 6 求值顺序与确定性编程

表达式求值顺序的三个层面（优先级、结合性、操作数顺序）合起来决定了一个程序的**确定性**——「同一代码，是否每次运行结果相同」：

**确定性编程的诉求**：可复现的 bug 才能可靠调试。C 的未指定操作数顺序让 `f() + g()` 结果不确定；Java/Python 的从左到右让行为可预测——**「确定性越高，程序越可调试」**。

**现代语言的趋势**：把求值顺序**完全指定**（Java、C# 从左到右；Rust 明确「表达式求值顺序」）；且**劝阻副作用**（Rust 的赋值返回 `()`、Swift 的 `-Wunused-value`）。

**浮点的不确定性**：即便顺序指定，浮点的**结合律不成立**仍让「数学等价」的程序给出不同结果——`(a+b)+c` vs `a+(b+c)` 舍入不同。「编译器不能重排浮点运算」是优化与正确性的拉锯点。

**辨析｜易错点：** **「看懂求值顺序 = 看懂程序的一半」**：`i++ + i++` 在 C 是未定义行为（不要问它等于几）；在 Java 是确定值（左先右后，结果为 0 + 1 = 1 类）。**「同一种写法，跨语言行为不同」**——写跨语言代码前，先确认目标语言的三层求值规则。「依赖求值顺序的程序是脆弱的」——最好的写法是「不依赖顺序：一个表达式只改一个状态」。

## 7 小结

- **优先级**决定不同运算符的先后；**结合性**决定同级运算符的先后；**操作数顺序**决定两参数谁先求值——三层规则缺一不可。
- 结合性分左/右，由文法决定；浮点运算不满足结合律，限制重排优化。
- 操作数求值顺序因语言而异：C 未指定，Java/Python 从左到右。
- 表达式的求值 = 按优先级/结合性建**语法树**再自底向上求值；可读性优先时多用括号。
