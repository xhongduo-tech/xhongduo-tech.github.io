## 为什么从形参与实参开始

上一节建立了子程序的基本模型；这一节看参数的「编排」——实参与形参如何一一对应。三种对应协议主导着各语言：**位置参数**（按顺序对应，最古老）、**关键字参数**（按名字对应，可读性最佳）、**默认参数**（省略时取默认值）。这些协议不是表面语法——它们决定了调用的可读性、健壮性（参数顺序错了怎么办）、以及 API 的可演化性（加了新参数会不会破坏旧调用）。<span class="marginnote">参数协议的本质是「接口契约」：调用方承诺「传这些」，实现方承诺「收这些」。位置参数把契约压在「顺序」上（易错），关键字参数把契约压在「名字」上（稳健），默认参数给契约留了「可选项」。</span>

## 1 位置参数：按顺序对应

**位置参数（positional parameter）**：实参按**声明的顺序**与形参一一对应——第一个实参配第一个形参，依此类推。

```python
def move(x, y): ...
move(3, 5)      # x=3, y=5（按位置）
```

位置参数是最古老、最普遍的协议（C、Java、Rust 的普通参数都是）。优点是简洁；缺点是**顺序即语义**——`move(5, 3)` 与 `move(3, 5)` 语法同样合法，含义却可能完全不同。<span class="marginnote">位置参数的脆弱性在「同类型多参数」时最突出：`draw(red, green, blue)` 传反了颜色，编译器毫无察觉。这是「魔法参数」问题的根源——很多语言因此引入关键字参数来补救。</span>

**辨析｜易错点：** 位置参数的顺序是**接口契约的一部分**。重构时调换形参顺序，所有调用点必须同步调整——若漏改一处，程序静默得到错误结果（类型仍匹配）。**「改参数顺序」是破坏性变更**，与改函数名同级。

## 2 关键字参数：按名字对应

**关键字参数（keyword / named parameter）**：实参用**形参的名字**标记，与顺序无关。

```python
def move(x=0, y=0): ...
move(y=5, x=3)     # 关键字：顺序可颠倒
move(3, y=5)       # 混合：位置在前，关键字在后
```

关键字参数的价值：

- **可读性**：`move(y=5, x=3)` 一眼看出「x 是 3，y 是 5」——调用即文档。
- **稳健性**：顺序颠倒不影响正确性。
- **可演化**：新增形参不会破坏按名字调用的旧代码。<span class="marginnote">Python、Ruby、Swift、Kotlin 支持关键字参数；C、Java、Rust 不支持（Rust 用「命名结构体参数」的惯用法近似）。「关键字参数是否支持」直接影响 API 的长期可维护性——Python 大量库依赖它保持向后兼容。</span>

**辨析｜易错点：** 混合使用时，**位置参数必须在关键字参数之前**（`move(3, y=5)` 合法，`move(x=3, 5)` 语法错误）。且关键字参数的名字必须是**形参的实际名字**——形参改名会破坏所有按名字的调用。**「关键字参数把契约从顺序移到名字」——名字成为新的接口面**。

## 3 默认参数：省略的优雅

**默认参数（default parameter）**：形参带默认值，调用时可省略——省略时使用默认值。

```python
def greet(name, greeting="Hello"): ...
greet("Alice")              # greeting 用默认 "Hello"
greet("Bob", "Hi")          # 显式覆盖
```

默认参数的设计决策：

- **默认值求值时机**：默认值在**定义时**求值一次（Python 的默认值在函数定义时绑定——可变默认值 `def f(x=[])` 是经典陷阱！）<span class="marginnote">Python 的 `def f(x=[])` 中 `[]` 在定义时创建<strong>一次</strong>，所有调用共享同一个列表——修改它会在多次调用间「串味」。这是 Python 最著名的坑之一，惯用法是 `def f(x=None): x = [] if x is None else x`。</span>
- **省略规则**：省略中间参数靠关键字——`f(a=1, c=3)` 才能跳过 `b`。
- **与重载的关系**：默认参数是「重载的替代品」——一个 `greet(name, greeting="Hello")` 抵得上两个重载版本。

## 4 公式解析：参数绑定与参数协议

参数绑定可以形式化为「实参列表到形参环境的映射」。设形参列表 $[f_1, \dots, f_k]$，实参以「位置 + 关键字」混合给出，则绑定：

$$
\rho_{\text{param}} = \bigcup_{i=1}^{k} \{f_i \mapsto \text{resolve}(f_i)\}
$$

其中：

$$
\text{resolve}(f_i) = \begin{cases}
\text{按位置提供的第 } i \text{ 个实参} & \text{若未以关键字提供} \\
\text{关键字 } f_i \text{ 对应的实参} & \text{若以关键字提供} \\
\text{默认值} & \text{若完全省略}
\end{cases}
$$

三步拆解：

- **第一步，并集**：最终参数环境是每个形参绑定的并集——每个形参恰好被绑定一次（否则报错：缺参或重复绑定）。
- **第二步，三条路**：每个形参的值来自三选一——位置、关键字、默认值。优先级（通常）：关键字 > 位置 > 默认；但「同一形参既给位置又给关键字」是错误。
- **第三步，看约束**：协议的合法性约束——位置参数连续、关键字参数不重复、必填参数不能省略。**编译器/解释器在调用时验证这些约束，违反即报错**——参数协议因此是「可检查的契约」。

**辨析｜易错点：** 「缺参数」「多参数」「重复提供」是三类典型调用错误。C 对「实参多于形参」不检查（旧式函数声明更危险）；Python 会精确报错 `TypeError: missing 1 required positional argument`。**「实参数目必须匹配形参数目」是大多数语言的调用期检查项**。

## 5 现代语言与参数协议的演化

| 语言 | 位置 | 关键字 | 默认 | 备注 |
| --- | --- | --- | --- | --- |
| C | ✅ | ❌ | ❌ | 顺序即一切 |
| Java | ✅ | ❌ | ❌（靠重载） | 重载模拟默认 |
| Python | ✅ | ✅ | ✅ | 三种协议齐备 |
| Kotlin | ✅ | ✅ | ✅ | 命名参数 + 默认值 |
| Rust | ✅ | ❌ | ❌ | 靠结构体 + builder 模式 |
| Swift | ✅ | ✅（标签） | ✅ | 外部标签是语言特色 |

<span class="marginnote">一个趋势：<strong>参数协议正从「顺序」走向「名字」</strong>。Python/Kotlin/Swift 的关键字参数、Rust 的命名结构体参数（`Config { x: 3, y: 5 }`）、Go 的「函数选项」模式，都是「让调用更可读、更抗错」的努力。语言的成熟度，部分体现在它把参数协议设计得多稳妥。</span>

## 6 小结

- **位置参数**按顺序对应，简洁但「顺序即语义」，重排是破坏性变更。
- **关键字参数**按名字对应，可读、稳健、可演化；位置参数必须在前。
- **默认参数**让省略合法；注意默认值求值时机（Python 可变默认值陷阱）。
- 参数绑定 = 「位置 / 关键字 / 默认」三选一的并集；缺参、多参、重复提供是调用期检查项。
