## 为什么从静态与动态类型检查开始

上一节把「强 / 弱」与「静态 / 动态」这对正交轴拆开；这一节专门攻「静态 vs 动态」这一轴。**类型检查（type checking）**的时机——编译期还是运行期——是语言设计里最影响开发体验的分歧之一：它决定了「错误何时被抓住」，「IDE 能给你多少提示」，以及「把大型代码库安全重构有多容易」。两派各有铁杆支持者，而真实世界里的现代语言正在互相靠近：TypeScript 给 JavaScript 补静态检查，Python 有了类型标注与 mypy，Java 引入 `var` 局部推导。理解这一轴，是理解语言「性格」的钥匙。<span class="marginnote">这一争论的实质是「错误发现时机 vs 表达灵活性」的权衡。静态检查把大量低级错误拦在编译门外，代价是有些「合法但难表达」的程序写不出来；动态检查给足自由，代价是错误潜伏到运行期、需要更充分的测试。</span>

## 1 静态类型检查：编译期的守门员

**静态类型检查（static type checking）**：在编译期检查所有表达式与语句的类型一致性，不运行程序。<span class="marginnote">「静态」指「不执行也可见」：编译器靠类型推导与声明，在生成机器码之前就知道 `x + 1` 中的 `x` 是 `int` 还是 `string`。错误在开发期（甚至键入时）即被 IDE 标红。</span>

静态检查的好处：

- **错误前置**：`int x = "abc";` 在编译期被拒，绝无可能进入生产。
- **文档与契约**：类型签名是机器可检查的规格。
- **安全重构**：改名、改签名时，编译器列出所有受影响处——大规模重构的底气。<span class="marginnote">「改一个字段名，编译器帮你找出所有用到的地方」——这是静态类型给重构的最大红利。在动态语言里，同样的重构只能靠全局搜索 + 测试覆盖，漏一处就可能线上爆炸。</span>
- **性能基础**：类型信息让编译器选择正确的指令与内存布局。

静态检查的代价：表达力受限——某些「运行时才知道类型」的模式（如读取 JSON、反射调用）难以静态表达，需要运行时兜底或类型断言。

## 2 动态类型检查：运行期的自由

**动态类型检查（dynamic type checking）**：类型在运行期才检查，变量本身不带类型，但每个值带类型；运算执行时检查操作数类型。<span class="marginnote">Python 的变量 `x` 没有类型，`x = 1` 后 `x = "a"` 完全合法——类型属于<strong>值</strong>而不属于<strong>名字</strong>。动态语言的「动态」正指「类型绑定到值、随时可变」。</span>

动态检查的好处：

- **快速原型**：不用先想清类型，写起来行云流水。
- **鸭子类型（duck typing）**：`if it quacks, treat it as a duck`——只要对象有 `quack` 方法就能调用，无需继承关系。接口的「结构」取代「名义」。
- **处理异构数据**：JSON、配置、协议数据天然「类型不定」，动态语言直接处理。

动态检查的代价：

- **错误延迟**：`"abc" + 5` 只有执行到那一行才报错，测试没覆盖的路径藏着雷。
- **重构困难**：改名后编译器不会帮你找到所有引用点。
- **性能**：每次运算都要查类型，运行时开销高于静态；优化空间受限（JIT 通过「类型反馈」部分弥补）。

## 3 一个程序，两条检查路径

同一个概念错误在两类语言中的命运对比：

| 程序片段 | 静态语言（Java） | 动态语言（Python） |
| --- | --- | --- |
| `String s = 5;` | 编译错误，程序不产出 | 合法：`s` 只是名字 |
| `s.toUpperCase()` | 编译错误（`int` 无此方法） | 若 `s` 是 `int`，运行期 `AttributeError` |
| `list.get(0)` 越界 | 运行期 `IndexOutOfBoundsException` | 运行期 `IndexError` |

<span class="marginnote">注意第三行：<strong>越界检查</strong>与类型检查无关——Java 静态类型仍要运行期检查数组边界。所以「静态」不是「所有检查都提前」，而是「类型检查提前」。</span>

## 4 公式解析：检查时机与错误暴露

静态检查可以形式化为「在类型推导树中验证可定型性」：

$$
\text{StaticCheck}(e) \;\equiv\; \exists\ \tau : \Gamma \vdash e : \tau \quad \text{（编译期可判定的推导）}
$$

$$
\text{DynamicCheck}(e) \;\equiv\; \text{执行到 } e \text{ 时} \; \text{check}(e.\text{操作数类型})
$$

三步拆解：

- **第一步，静态公式**：$\Gamma \vdash e : \tau$ 存在推导，则 $e$ 类型合法。它是对**所有可能输入**的判定——只要程序文本能推出类型，就放行，与运行时数据无关。
- **第二步，动态公式**：检查延迟到「执行到该表达式」的**具体数据**上——检查的是「此刻操作数的实际类型」。
- **第三步，看信息量**：静态检查在**程序层**工作（不依赖数据），动态检查在**值层**工作（依赖数据）。因此静态能保证「对所有输入安全」，动态只能保证「对执行到的路径安全」——这是两者错误发现能力的根本差异。

**辨析｜易错点：** 「动态类型」不意味「没有类型」。Python 的每个值都有类型，类型错误照样存在——只是**检查时机**在运行期。说「Python 无类型」是常见误传；准确说法是「Python 变量无静态类型」或「Python 是动态强类型」。

## 5 走向融合：类型标注与渐进类型

现代语言正在弥合这道鸿沟：

- **类型标注（type annotation）**：Python 3 的 `def f(x: int) -> str:` 配合 `mypy`/`pyright` 做静态检查——把「动态语言 + 可选静态检查」变成现实，即**渐进类型（gradual typing）**：部分代码有注解、静态检查，其余保持动态。<span class="marginnote">渐进类型的核心约定：有注解的代码按静态规则检查，没注解的按动态处理，两类代码可互调。mypy 对大型 Python 代码库的推进，是「动态语言主动向静态靠拢」的最强证据。</span>
- **类型推导**：C++ `auto`、Java `var`、Rust `let x = ...` 让编译器替你写类型——静态检查不牺牲，敲击减少。
- **局部静态分析**：IDE 与 linter 对动态语言做「尽力而为」的静态推断，缩小盲区。

## 6 静态与动态：IDE 与开发体验的分野

静态/动态类型的差异，最直观地体现在**开发工具**（IDE、调试器）上——这是「哪类语言更好」争论的实际落点：

**静态语言的 IDE 体验**：类型已知 → **代码补全**（提示可用方法）、**跳转定义**、**重构安全**（改名后编译器列出所有引用）、**即时报错**（键入时标红）。IntelliJ（Java）、Rust Analyzer（Rust）把这套做到极致——「类型是 IDE 的燃料」。

**动态语言的 IDE 体验**：类型运行期才知 → 补全靠「推断」（可能不准）、重构靠搜索 + 测试。但动态语言有**交互式优势**——REPL（Python 的 `python`、Node 的 `node`）即写即跑，探索性编程流畅。Jupyter 的「动态 + 交互」是研究工作的理想形态。

| 体验 | 静态 | 动态 |
| --- | --- | --- |
| 补全 | 精确（类型已知） | 推断（可能不准） |
| 重构 | 编译器兜底 | 搜索 + 测试 |
| 即时报错 | 键入即标红 | 运行才暴露 |
| 交互探索 | 需编译/标注 | REPL 天然 |

**辨析｜易错点：** **「静态语言未必比动态语言『难写』」**——现代静态语言（Rust/Kotlin/TS）的类型推导让「不用写类型」也成为可能；而动态语言（Python + mypy）也在补静态检查。**「两派都在学对方的长处」**——静态学「少写类型」（推导），动态学「早检查」（标注）。选型不是选「阵营」，而是选「这个项目的错误容忍度 × 开发节奏」——「要稳选静态，要快选动态，两者都要就选推导强的静态」。

## 7 小结

- **静态类型检查**在编译期查类型，错误前置、契约明确、重构安全；代价是表达力受限。
- **动态类型检查**在运行期查类型，原型快、鸭子类型灵活；代价是错误延迟、重构难、有运行期开销。
- 静态/动态的差异本质是**检查发生在程序层还是值层**——静态覆盖所有输入，动态只覆盖执行到的路径。
- 现代趋势是**融合**：类型标注、`auto`/`var` 推导、渐进类型，把两种哲学的长处拼在一起。
