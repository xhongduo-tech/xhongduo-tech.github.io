## 为什么从 goto 开始

在结构化编程的叙事里，**goto** 是那个著名的反面角色。1968 年，迪杰斯特拉发表《Go To Statement Considered Harmful》，引爆了计算机史上最著名的一场论战。但 goto 的故事远比「禁用」丰富：它为什么被发明（最原初的控制手段）、为何被批判（破坏结构）、又为何至今没有完全消失（多重重循环跳出、错误处理、状态机）。这一节把这个经典问题讲透，并看到它真正的遗产——**结构化编程**如何重塑了程序设计语言的控制结构。<span class="marginnote">论战的背景是「软件危机」：1960 年代大型软件（如 IBM System/360 的 OS）频频失控。迪杰斯特拉认为 goto 的「任意跳转」是程序无法理解与验证的元凶——他的解决方案是让控制结构「可证明」。</span>

## 1 goto：最原初的控制手段

**goto（无条件跳转）**：把控制流无条件转移到程序中任意一个标签处。它是低级语言（汇编）的「跳转指令」在高级语言里的直接继承——最早的高级语言（Fortran、COBOL）都以内建。

```c
int i = 0;
loop:                  // 标签
    i++;
    if (i < 10)
        goto loop;     // 无条件跳转到标签
```

goto 的「能力」：跳到任何地方、跳出多层循环、实现状态机、实现异常跳转。它表达力极强——**这正是问题所在**。

## 2 迪杰斯特拉的批判

1968 年论文的核心论证：

**可读性**：goto 让程序的「静态文本」与「动态执行顺序」脱节——阅读者不能从上到下理解程序。
**可验证性**：程序的正确性证明依赖「局部推理」（只看一小块就能判定性质）。goto 让控制流任意穿越，局部推理失效——**程序不可分解**。
**结构性**：goto 把程序变成「一锅跳转汤」，无法用嵌套层次组织。

迪杰斯特拉的处方：控制结构应**有且仅有**顺序、选择、循环三种，且都满足单入口单出口——这样程序可以「从外到内逐层理解」。<span class="marginnote">迪杰斯特拉后续提出了「结构化编程（structured programming）」一词，并与以 goto 为传统的大型软件工程派（如克努特）论战。克努特承认大多数 goto 有害，但指出某些场合（如错误处理）goto 比嵌套 return 更清晰——论战以「goto 应克制而非绝对禁止」告终。</span>

## 3 Böhm-Jacopini 定理：goto 并非必需

1966 年，Böhm 与 Jacopini 证明了关键定理（上一节已提及）：**任何程序的控制流都可以只用顺序、选择、循环三种结构表达**——因此 goto 在表达能力上并非必需。

这一定理的深远意义：

它给了「禁用 goto」以**数学合法性**：不是风格偏好，而是「表达能力不减」。
它催生了 Pascal、Ada 等「结构化优先」的语言——goto 被保留但受严格限制。
它为现代控制结构（顺序、选择、循环）的统治地位提供了理论基石。<span class="marginnote">定理的严格版本需要「辅助变量」（如布尔标记）来模拟某些 goto 模式——例如「提前退出」需要 `found` 标志配合 `break`。这说明「不用 goto」偶尔要付出「额外变量」的代价——现代语言的带标签 `break`/`continue` 正是把这些模式的代价收回来的受控结构。</span>

## 4 goto 的现代用途：残存的合理性

完全消灭 goto 的语言很多（Python、Java、Rust），但 C/C++ 仍保留，且有几个公认的合理场景：

**多层循环跳出**：从嵌套三层以上的循环中跳出，goto 比「逐层 break + 标志」清晰：

```c
for (int i = 0; i < n; i++) {
    for (int j = 0; j < n; j++) {
        for (int k = 0; k < n; k++) {
            if (found(i, j, k))
                goto done;      // 一次跳出三层
        }
    }
}
done:
printf("found\n");
```

**错误处理**：C 没有异常，`goto cleanup` 是「统一释放资源」的惯用法（Linux 内核风格）：

```c
int *buf = malloc(1024);
if (!buf) goto cleanup;
if (read(fd, buf, 1024) < 0) goto cleanup;
// ... 处理数据 ...
cleanup:
free(buf);     // 统一释放资源
return err;
```

<span class="marginnote">现代语言用「受控的 goto」替代裸 goto：Java 的带标签 `break`、Python 的异常、Rust 的带标签循环、异常机制（`try`/`catch`）本质上是「跨越任意深度的受控跳转」。这些结构保留了 goto 的「逃离能力」，却限制「只能向后/向外跳」，从而保住结构可读性。</span>

## 5 公式解析：goto 如何破坏结构

用控制流图说明 goto 的危害。设一个程序的控制流图 $G = (N, E)$，**结构化程序**要求图可分解为嵌套的「单入口单出口」子图：

$$
G \text{ 结构化} \;\Longleftrightarrow\; G \text{ 的强连通分量构成嵌套树，且每个分量为单入单出}
$$

goto 引入**任意边** $u \to v$（$v$ 在 $u$ 的任意深度），可能使：

$$
\exists\ \text{边 } u \to v : \text{depth}(v) \notin \{\text{depth}(u), \text{depth}(u)+1\}
$$

三步拆解：

- **第一步，结构化条件**：结构化程序的边只连接「相邻层级」——从外层进入内层（+1）或内层返回外层（−1），且对应结构的入口/出口。
- **第二步，goto 的破坏**：goto 可以跳到任意深度（目标深度与源深度无关）——这条边不是结构化的入口/出口边，破坏「嵌套树」性质。
- **第三步，看后果**：破坏嵌套树后，图不可按「层级」分解，局部推理与静态分析失效。**「goto 有害」的形式化表述：它引入破坏嵌套树性质的任意边**。

**辨析｜易错点：** 单层循环内 goto 到循环出口，其实与 `break` 等价——危害不大。**goto 的真正危害是「跳入」**（跳到循环/块内部的中途）与「任意深度跨越」。现代语言保留 goto 时（C/C++），也禁止「跳入作用域跳过初始化」等危险跳转——「向后跳」受限，保证结构化基本盘不破。

## 6 小结

- **goto** 是无条件跳转，继承自汇编，表达力极强——「能跳到任何地方」正是其危害来源。
- **迪杰斯特拉 1968** 论证 goto 破坏可读性与可验证性，提出「三种结构」处方。
- **Böhm-Jacopini 定理**证明 goto 表达力上并非必需——结构化是「表达能力不减」的严格选择。
- goto 在现代仍有少数合理用途（多层跳出、错误清理），现代语言用**带标签 break、异常**等「受控 goto」替代裸 goto。
