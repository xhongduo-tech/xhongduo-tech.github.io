## 为什么从并发开始

现代程序不再「单线执行」：服务器同时服务百万请求、UI 线程与后台线程并行、多核 CPU 并行计算。**并发（concurrency）**是「多个执行流同时推进」的语言支持。第十四篇的系统主题由此展开：先立三个基本概念——**任务（task）**、**同步（synchronization）**、**竞争（race）**。这三者构成理解一切并发机制（信号量、管程、Actor、channel）的坐标：并发程序里有什么在跑（任务）、它们如何协调（同步）、出问题时是什么样（竞争）。<span class="marginnote">「并发（concurrency）」与「并行（parallelism）」常被混用：并发是「多个流交错推进」（逻辑概念，单核也可），并行是「真正同时执行」（物理概念，需多核）。并发是程序设计问题，并行是硬件执行问题——一个程序可以并发而不并行（单核轮转）。</span>

## 1 任务与线程

**任务（task）**：一个独立的执行单元——有自己的指令流、栈与状态。语言层面，任务用**线程（thread）**或**协程（coroutine）**实现。

```java
Thread t = new Thread(() -> { ... });   // Java：新线程
t.start();
```

**并发程序的本质**：多个任务交错执行。交错（interleaving）的顺序不固定——**这既是并发的灵活性，也是竞争的根源**。

**辨析｜易错点：** 「同时执行」的假象：单核上任务其实是「快速切换」的（时间片轮转），不是真同时。多核上才可能真并行。**「并发程序的正确性不能依赖交错顺序」**——正确程序必须在任何交错下都正确（这与卫式命令的非确定性一脉相承）。

## 2 同步：协调任务

**同步（synchronization）**：让多个任务「协调步调」的机制——控制「谁先谁后」与「谁能否进临界区」。

两类同步需求：

**互斥（mutual exclusion）**：同一时刻只有一个任务访问**共享资源**——防止两个线程同时修改同一数据结构。

**条件同步（condition synchronization）**：任务**等待某个条件成立**才继续——如生产者等队列不满、消费者等队列非空。

<span class="marginnote">互斥保护「数据的完整性」（同一刻只有一个写者），条件同步管理「依赖关系」（等条件再继续）。经典比喻：互斥是「厕所门锁」（一人进，他人等），条件同步是「排队叫号」（条件满足才轮到你）。两者常结合使用——管程（monitor）就是「互斥 + 条件变量」的统一封装。</span>

## 3 竞争与竞态条件

**竞争（race condition）**：程序的**结果依赖任务交错顺序**——不同交错产生不同结果。这是并发 bug 的头号来源。

```java
// 两个线程同时执行：counter++ （读→加→写三步）
int old = counter;     // 两个线程可能读到同一个 old
counter = old + 1;     // 都写回同一个值——丢失一次递增！
```

`counter++` 不是原子的——它是「读、加、写」三步。两个线程交错时可能同时读到 5、同时写回 6——**丢失更新**。结果取决于交错顺序 = 竞态。<span class="marginnote">「原子操作（atomic operation）」是不可分割的操作——要么完整执行，要么不执行。`counter++` 非原子；`AtomicInteger.incrementAndGet()` 原子。竞态的本质：<strong>非原子操作被并发交错打断</strong>。修复 = 用原子操作或互斥把「读改写」包成临界区。</span>

## 4 公式解析：交错与竞态

竞态可以形式化为「操作的交错产生多可能结果」。设操作 $A$（读）与 $B$（写回），两线程的交错：

$$
\text{交错}_1: A_1, B_1, A_2, B_2 \;\Rightarrow\; \text{counter} = 7
$$

$$
\text{交错}_2: A_1, A_2, B_1, B_2 \;\Rightarrow\; \text{counter} = 6 \quad \text{（丢失更新）}
$$

三步拆解：

- **第一步，拆操作**：`counter++` = 读 $A$、加、写回 $B$——不是一步。
- **第二步，枚举交错**：两个线程的 $A_1 B_1 A_2 B_2$ 与 $A_1 A_2 B_1 B_2$ 都合法（交错顺序自由）——但结果不同（7 vs 6）。
- **第三步，定义竞态**：**若不同交错产生不同结果，则该代码有竞态**。正确的并发程序要求「所有交错结果一致」——这需要同步保证「$A_i B_i$ 不被另一线程的读写插入」（互斥）。

**辨析｜易错点：** 竞态 ≠ 死锁。竞态是「结果不确定」（可能错），死锁是「全部卡住」（确定地错）。竞态通常来自「未加锁的共享写」，死锁来自「锁的循环等待」。**「竞态是并发 bug 之一，不是全部」**——还有死锁、活锁、饥饿，各有机制与对策。

## 5 并发模型概览与语言支持

主流并发模型（本专题后续几节逐一展开）：

| 模型 | 核心思想 | 代表 |
| --- | --- | --- |
| 共享内存 + 锁 | 共享数据，锁保证互斥 | Java/C++ 线程 + synchronized |
| 管程（Monitor） | 互斥 + 条件变量封装 | Java `synchronized`/`wait/notify` |
| 消息传递 | 任务间不共享，靠消息通信 | Erlang、Go channel、Actor |
| Actor 模型 | 万物皆 actor，消息信箱 | Erlang、Akka |
| 软件事务内存 | 事务化内存操作，冲突自动重试 | Clojure、Haskell STM |

<span class="marginnote">现代趋势：<strong>「少共享，多通信」</strong>。共享内存 + 锁容易出错（竞态、死锁、忘记解锁），消息传递/不可变数据从根上消除共享——Go 的 channel、Rust 的「Send + Sync」类型系统、Erlang 的「进程间不共享」都指向这个方向。但共享内存的高性能（低延迟、少拷贝）让它仍是底层主流。</span>

## 6 并发 bug 的图谱

并发编程的错误不止竞态——完整图谱值得认清，便于对症下药：

**竞态（race condition）**：结果依赖交错顺序——「不确定的错」。修复：同步/原子操作。

**死锁（deadlock）**：任务互相等待对方持有的锁——「确定地卡住」。修复：锁顺序规范、超时、避免嵌套锁。

**活锁（livelock）**：任务都在动但互相谦让、无法推进——「忙个不停但没进展」。修复：随机退避。

**饥饿（starvation）**：某个任务永远轮不到资源（被高优先级任务挤占）——「有人一直等」。修复：公平调度。

| 错误 | 症状 | 本质 | 对策 |
| --- | --- | --- | --- |
| 竞态 | 结果不确定 | 交错影响结果 | 同步 |
| 死锁 | 全体卡住 | 循环等待 | 锁顺序/超时 |
| 活锁 | 都在动没进展 | 互相谦让 | 随机退避 |
| 饥饿 | 部分一直等 | 调度不公 | 公平策略 |

**辨析｜易错点：** **「并发 bug 最难的不是修，是复现」**——竞态可能跑一万次才出现一次（特定交错才触发），测试难以覆盖。**「并发正确性要靠『设计保证』而非『测试碰运气』」**：优先用「不可变数据」「消息传递」「无共享」从结构上消灭竞态，而不是靠反复测试「碰巧对」。「死锁与竞态常共存」——修好竞态（加锁）可能引入死锁，反之亦然；并发调优是在多类风险间权衡。

## 7 小结

- **任务**是独立执行单元（线程/协程）；并发 = 多个任务交错推进，正确性不能依赖交错顺序。
- **同步**协调任务：**互斥**（保护共享资源）与**条件同步**（等待条件成立）。
- **竞争（race）** = 结果依赖交错顺序；根源是**非原子操作被并发打断**（读-改-写三步）。
- 并发模型谱系：共享内存 + 锁 → 管程 → 消息传递 → Actor → STM；「少共享、多通信」是现代趋势。
