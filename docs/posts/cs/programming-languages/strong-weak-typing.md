## 为什么从强类型与弱类型开始

「Python 是强类型」「C 是弱类型」——这类说法在程序员社区流传甚广，却常常是鸡同鸭讲：有人说的「强」指静态，有人说的「强」指不隐式转换。要把类型安全讲清楚，必须先给「强 / 弱」一个精确的坐标。**类型安全（type safety）**是一个语言性质：是否保证程序不会发生「把 A 类型的值当 B 类型用」这类运行期错误。沿着这条线，「强 / 弱」与「静态 / 动态」是两对正交的概念——本文先把它们拆开，再组装回各语言的真实图景。<span class="marginnote">常见误区：「静态类型 = 强类型」。其实静态/动态说的是<strong>检查时机</strong>，强/弱说的是<strong>安全保证</strong>。Java 是静态 + 偏强，C 是静态 + 偏弱，Python 是动态 + 偏强——组合远比二元划分丰富。</span>

## 1 类型安全的精确定义

**类型安全（type safety）**：语言保证程序中**不存在**把值按错误类型操作的情况。塞贝斯塔给出的经典定义是「语言的类型系统不会让一个类型的值被当作另一类型使用」。

类型安全是「无未定义行为」的类型侧表达：一个类型安全的语言里，每个运算的每个操作数都在该运算可接受的类型范围内，因此不会出现「把 `float` 位模式当 `int` 读」这类灾难。<span class="marginnote">C 的类型不安全主要来自三类口子：`union` 的自由重解释、指针的强制类型转换（`int*` 转 `char*`）、数组越界。这些「逃逸阀」本身是特性（贴近硬件、表示级互操作），但代价是类型安全被局部放弃。</span>

## 2 强类型：不隐式接受错误操作

**强类型（strongly typed）**：语言不允许「把一个类型的值隐式当作另一类型」做操作，除非有显式转换。

「强」的关键词是**不隐式**：`"abc" + 5` 在强类型语言里要么编译错、要么抛异常，而不会静默地得到某个怪值。<span class="marginnote">注意「强」与「绝不转换」是两回事：Python 是强类型，但 `int + float` 会隐式提升为 float——因为这种提升<strong>保真</strong>（每个 int 都能精确表示为 float 的一部分）且语义清晰。强类型禁止的是「有损/无意义的隐式转换」。</span>

**弱类型（weakly typed）**：语言允许大量隐式转换，甚至允许「按另一种类型的位模式」解释值。C 的 `void*` 任意强转、联合的重解释、以及 `0` 到任何指针的隐式转换，都是弱类型的体现。

## 3 强 / 弱 vs 静态 / 动态：两对正交轴

这两组概念常被混为一谈，必须分开：

- **静态 / 动态类型**：检查发生在**编译期还是运行期**（第六篇将细讲）。
- **强 / 弱类型**：程序能否发生**类型不安全**的操作（与检查时机无关）。

用一张表把常见语言放进去：

| 语言 | 检查时机 | 强度 | 说明 |
| --- | --- | --- | --- |
| C | 静态 | 弱 | 编译期查类型，但 `union`/强转/越界留口子 |
| Java | 静态 | 强 | 编译期查 + 运行期 `ClassCastException` 兜底 |
| Python | 动态 | 强 | 运行期查，隐式转换极少且明确 |
| JavaScript | 动态 | 弱 | `1 + "2"` → `"12"`，宽松转换是出名的坑 |
| Rust | 静态 | 强 | 编译期 + 所有权，运行期几乎零类型风险 |
| Haskell | 静态 | 强 | 隐式转换近乎为零 |

<span class="marginnote">JavaScript 的 `1 + "2" == "12"`、`"5" * 3 == 15` 正是弱类型的教科书案例——它隐式地在字符串与数字之间换来换去，语义对新手极不直观。Python 的 `"abc" + 5` 直接抛 `TypeError`——强类型「宁死不屈」。</span>

## 4 公式解析：强类型的形式刻画

类型安全可以用「良类型程序不卡住」来严格表述——这与操作语义的「卡住（stuck）」概念接上了：

$$
\text{Type Safety} \;\equiv\; \forall\ e,\ \Gamma \vdash e : \tau \;\Longrightarrow\; e \not\to \text{stuck}
$$

三步拆解：

- **第一步，读前提**：$\Gamma \vdash e : \tau$ 表示「在类型环境 $\Gamma$ 下，$e$ 具有类型 $\tau$」——即 $e$ 通过了静态类型检查。
- **第二步，读结论**：$\not\to \text{stuck}$ 表示「$e$ 在运行时不会卡住」——每个可执行的步骤都在转移关系中有定义，不会遇到「无法继续的非法状态」。
- **第三步，连起来**：这条定理（如 Wright-Felleisen 的「安全 = 进展 + 保存」）说：**静态类型检查通过的程序，运行时绝不会因类型错误而卡住**。这就是「强类型」的严格内核——检查通过即安全。弱类型语言的这条定理不成立：检查通过了，运行时仍可能重解释内存。

**辨析｜易错点：** 「类型安全」不等于「内存安全」，也不等于「无 bug」。类型安全只保证「不做类型非法操作」，不保证「逻辑正确、不越界（在无边界检查时）、无死锁」。把类型安全当成「程序不会错」的保证，是对它的过度解读。

## 5 从强弱光谱看语言设计

- **强类型 + 静态**（Rust、Haskell、Java）：错误尽量在编译期暴露，运行期兜底检查仍保留。
- **强类型 + 动态**（Python、Ruby）：灵活但错误推迟到运行期，需要测试覆盖。
- **弱类型 + 静态**（C、C++）：贴近硬件、性能优先，类型安全部分让位于表示级自由。
- **弱类型 + 动态**（JavaScript、PHP）：上手快、胶水强，但类型错误隐蔽，催生了 TypeScript 等「收紧」方言。<span class="marginnote">TypeScript 的崛起正说明市场对「弱 + 动态」的容忍有限：给 JavaScript 加上静态类型层，是在不换运行时的情况下把「弱」往「强」方向拉。语言演化的历史，很多时候是「类型安全程度」此消彼长的历史。</span>

## 6 类型强弱的真实案例

把「强弱」落到具体代码，看同一段逻辑在不同语言的命运。计算「字符串拼接一个数字」：

**JavaScript（弱）**：

```js
console.log("count: " + 5);   // "count: 5"——自动转字符串
```

**Python（强）**：

```python
print("count: " + 5)          # TypeError: can only concatenate str...
```

JS 的 `+` 静默把数字转字符串——**方便但隐晦**（`"5" + 3` 是 `"53"`，`"5" * 3` 是 `15`，同一 `5` 在两个运算符下命运不同）。Python 直接拒绝——**错误暴露而非静默猜**。

再看 C 的「弱」：

```c
int x = 300;
char c = (char)x;   // 300 截断为 44（300 mod 256）——有损但合法
```

**「弱类型把『错误』变成『隐式行为』」**：C 的窄化截断、JS 的类型自动转换，都是「语言替你猜、猜错不吭声」的形态。强类型则是「猜不了就报错，让你自己说清楚」。**「强弱的实践意义：错误是『静默的怪值』还是『响亮的异常』」**——这两者的调试成本天差地别。

## 7 小结

- **类型安全**：程序不会把值按错误类型操作；「强 / 弱」衡量这一保证的程度，「静态 / 动态」衡量检查时机，两对概念正交。
- **强类型**拒绝不安全的隐式转换；**弱类型**允许重解释与宽松转换。
- 类型安全的严格形式是「良类型程序不卡住」——静态检查通过即无运行期类型错误。
- 四个象限（强/弱 × 静态/动态）都真实存在语言，各有取舍；TypeScript 是「向强收紧」的当代例证。
