## 为什么从 BNF 开始

上一节我们把文法写成了数学对象 $G = (V, T, P, S)$，还用 `→` 这样的记号写了产生式。但那只是顺手为之——现在我们给它一个正式的名字：**BNF**。它是描述程序设计语言语法的事实标准，诞生于 1950 年代末、为描述 Algol 60 而设计，至今仍是语言规范（标准文档、参考手册）最常用的语法记号。这一节先讲 BNF 本身，再讲它的改良版 EBNF：二者描述的能力完全相同，但 EBNF 更易读、更接近语言设计者的思考方式。

## 1 BNF：一种描述文法的元语言

**BNF（Backus-Naur Form，巴科斯-瑙尔范式）**：一种**元语言（metalanguage）**——用来描述其他语言（对象语言）语法的一种语言。它的两个名字来自两位缔造者：**约翰 · 巴科斯（John Backus）**，Fortran 之父，1959 年率先提出；**彼得 · 瑙尔（Peter Naur）**，Algol 60 报告的主编，1960 年把巴科斯的记号系统化，用于撰写 Algol 60 的语法。<span class="marginnote">「元语言 vs 对象语言」是一对贯穿整个程序语言理论的概念：写词法规则的元语言、描述语义的元语言、甚至撰写这篇博文所用的中文，都在各自的层面当「元」角色。BNF 是最早进入工程实践的一种。</span>

BNF 的产生式（production）形如：

```
<assign> ::= <var> = <expr>
```

`::=`（或 `→`）读作「定义为」，左边是一个非终结符，右边是它的可能形式。
尖括号 `<>` 包裹的是非终结符；不带尖括号的符号是终结符。
竖线 `|` 表示「或」，把多个右部合并成一条规则。

看 Sebesta 的经典例子——描述赋值语句：

```
<assign> → <var> = <expr>
<var>    → A | B | C
<expr>   → <var> + <expr> | <var>
```

第一条读作「赋值语句定义为：一个变量，一个 `=`，一个表达式」。第二条「变量定义为 A 或 B 或 C」。第三条「表达式定义为『变量加表达式』，或直接是一个变量」——它用**递归**表达「任意多个加号连成的式子」：`A + B + C` 可以由此推出。<span class="marginnote">注意 `=` 是对象语言（被描述的语法）里的符号，而 `::=` 是元语言（BNF 自身）的符号——两者的分界要分清，初学时常把 `=` 与 `::=` 混用。</span>

## 2 或、递归与重复：BNF 的三种表达手段

BNF 的元符号只有三类，全部表达手段都从它们派生：

**选择（choice）**：用竖线 `|`，表示「要么……要么……」。如 `<var> → A | B | C`。
**递归（recursion）**：用「产生式右部再次出现左部」来表达重复与嵌套。递归的方向还决定了结合方向：
**左递归（left recursion）**：右部以左部开头，如 `E → E + T | T`，列表向左生长；
**右递归（right recursion）**：右部以左部结尾，如 `E → T + E | T`，列表向右生长。<span class="marginnote">左递归与右递归不只影响推导的「方向」，更决定运算的结合性——左递归的加法是左结合（`(a+b)+c`），右递归是右结合（`a+(b+c)`）。这个伏笔在下一篇文章《二义性、运算符优先级与结合性》里正式引爆。</span>
**重复（repetition）**：BNF **没有**专门的重复元符号，只能靠递归表达。例如「标识符 = 一个字母，后面跟零个或多个字母或数字」：`</var>`

```
<ident> → <letter>
        | <ident> <letter>
        | <ident> <digit>
<letter> → a | b | c | ... | z
<digit>  → 0 | 1 | ... | 9
```

这样写虽然精确，但读起来费力：为了表达一个平凡的「重复」，我们被迫写满四行递归。<span class="marginnote">「递归能表达重复，但重复不一定非要递归」——这是 BNF 最笨拙的地方，也是 EBNF 出现的直接动机。你能一眼看出上面这组规则生成的是「字母开头、字母数字混合」的标识符吗？能，但要数好几行。</span>

**辨析｜易错点：** 递归的方向与重复的语义不是一回事。上面的标识符文法用左递归，生成的仍是「字母 + 若干字母/数字」的串，方向只影响「生成」的展开方式与（在运算符文法里）结合性，不影响语言的**集合**。别把「递归方向」与「语言是什么」混为一谈。

## 3 EBNF：为可读性而生的扩展

**EBNF（Extended BNF，扩展 BNF）**：在 BNF 之上增加三个「语法糖」元符号的记号体系，由**尼古拉斯 · 沃斯（Niklaus Wirth）**在 1977 年提出，用于描述 Pascal 的语法：

| 元符号 | 含义 | 例子 |
| --- | --- | --- |
| `{ }` 花括号 | 重复零次或多次 | ``{ <digit> }`` 表示零个或多个数字 |
| `[ ]` 方括号 | 可选，出现零次或一次 | `[ + \| - ]` 表示可有可无的正负号 |
| `( )` 圆括号 | 分组 | `x ( + \| - ) y` 表示 `x` 后跟 `+` 或 `-` |

用 EBNF，第 2 节的标识符规则缩成两行：

```
<ident> → <letter> { <letter> | <digit> }
<letter> → a | b | c | ... | z
```

读作「标识符定义为：一个字母，后跟零个或多个『字母或数字』」。花括号把「重复」从递归里解放出来，规则一眼可读。EBNF 的「扩展」是**表示法的扩展，不是表达力的扩展**：任何 EBNF 规则都能机械地翻译回普通 BNF，反之亦然——两者描述的是同一类文法（上下文无关文法）。<span class="marginnote">把 `{ α }` 翻译回 BNF，就是引入一个新非终结符 `A'`，配规则 `A' → α A' | ε`（ε 为空串）；所以 EBNF 是「语法糖」，它让语言设计者写得快、读得懂，但没给语言理论增加任何新东西。</span>

## 4 公式解析：递归与重复的等价

EBNF 花括号与 BNF 递归的等价，可以用一对规则看清楚：

$$
\text{EBNF：}\; E \to T\, \{ +\, T \} \qquad \Longleftrightarrow \qquad \text{BNF：}\; E \to T \mid E + T
$$

逐项拆解：

- **第一步，读 EBNF 一侧**：$E \to T \{ + T \}$ 表示「一个 $T$，后跟零个或多个 $+T$」。它生成的串是 $T$、$T+T$、$T+T+T$、……无限多个，但写法只有一条。
- **第二步，读 BNF 一侧**：$E \to T \mid E + T$ 是左递归，展开后同样是 $T$、$T+T$、$T+T+T$、……两条规则生成**同一个集合**。
- **第三步，确认等价的方向**：$\Longleftrightarrow$ 说的是「生成的语言相同」，即对任意串 $w$，$w \in L(E_{\text{EBNF}})$ 当且仅当 $w \in L(E_{\text{BNF}})$。这是「表示法等价」的严格含义。
- **第四步，注意不等价的层面**：语言相同 ≠ 结构相同。$T \{ + T \}$ 的展开过程**不决定**加法是左结合还是右结合——EBNF 把结合性信息抹掉了；而左递归的 $E \to T \mid E + T$ 明确编码了左结合。**EBNF 方便描述「集合」，却要另外声明「结构」**（如「加法左结合」），这是它与 BNF 最微妙的差别。

**核心要点**：EBNF 与 BNF 在「生成什么语言」上等价，在「编码什么结构」上不等价。读 EBNF 时，重复、可选的语法糖只告诉你能拼出哪些句子；句子的**层次**（谁先算、谁结合谁）需要靠分层文法与结合性约定另行给出——这正是下一篇文章的全部主题。

## 5 用 EBNF 描述一个微型表达式语言

把上一篇文章的三层文法改写成 EBNF，一套带优先级与重复的表达式语言长这样：

```
<expr>   → <term> { <addop> <term> }
<addop>  → + | -
<term>   → <factor> { <mulop> <factor> }
<mulop>  → * | /
<factor> → ( <expr> ) | <ident> | <number>
```

逐行读出来：

- 表达式（`<expr>`）是一个因子，后跟零个或多个「乘除号 + 因子」；
- 因子（`<factor>`）是一个因子，后跟零个或多个「乘除号 + 因子」；
- 因子（`<factor>`）是括号里的表达式、标识符或数字。

与上一节纯 BNF 的写法相比，花括号 `{ }` 让「任意多个操作数」从递归里解放出来，五条规则讲清了全部语法，且每一行都能直接翻译成人话。**这种「层叠文法」正是优先级的 EBNF 表达**：`+`/`-` 被埋在 `addop` 层，`*`/`/` 在 `mulop` 层，语法上先结合的就先被包进更深的规则——层次本身就在说话。<span class="marginnote">对语言设计者，EBNF 既是规范又是文档；对编译器实现者，EBNF 规则几乎可以直接翻译成递归下降解析器的函数——每个非终结符对应一个函数，花括号对应循环。这是第四级《编译原理》专题「自顶向下语法分析」的蓝图。</span>

**辨析｜易错点：** ```{ <mulop> <factor> }``` 里的 `{ }` 只声明「乘除可以无限重复」，并不声明重复的结果是左结合还是右结合。实际语言通常额外规定「相同优先级的运算左结合」；若语言规范只给 EBNF 而不给结合性声明，同一个式子就能被解析成不同结构——歧义由此产生。下一篇文章正是从「歧义」讲起。

## 6 小结

- **BNF** 是描述语法的**元语言**，由巴科斯与瑙尔为 Algol 60 首创；核心符号是 `::=`、`<>` 与 `|`。
- BNF 的表达手段是**选择（`|`）、递归（左/右）与靠递归表达的重复**。
- **EBNF** 在 BNF 上增加 `{ }`（重复）、`[ ]`（可选）、`( )`（分组）三个语法糖，由沃斯为 Pascal 提出。
- EBNF 与 BNF **生成的语言完全相同**，但 EBNF 抹掉了结合性等结构信息——它描述「集合」，不自动描述「结构」。
- **层叠文法**（`expr`/`term`/`factor`）用规则的层次编码运算符优先级；`{ }` 编码重复；结合性需另行约定。
- 对语言设计者，EBNF 是规范与文档；对实现者，它近乎递归下降解析器的直接蓝图。

在下一节，我们直面语法理论里最关键的病症：**二义性**。为什么同一个句子能长出两棵语法树，悬空 `else` 为何臭名昭著，优先级与结合性如何用文法重写来根治歧义——这正是 BNF 从「能描述」走向「该怎样描述」的一课。
