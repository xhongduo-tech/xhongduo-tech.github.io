## 为什么从追踪式回收开始

引用计数靠「局部计数」判断生死，有循环引用盲区。**追踪式垃圾回收（tracing garbage collection）**换了一个全局视角：**从根集出发，标记所有可达对象；不可达的就是垃圾，全部回收**。它彻底解决循环引用（不可达即回收），代价是「扫描时程序暂停」（STW，stop-the-world）。这一节看三个经典追踪算法——**标记-清除（mark-sweep）**、**复制式（copying）**、**分代回收（generational）**——它们构成了 JVM、Go、Python 等所有主流 GC 的算法谱系。<span class="marginnote">追踪式回收的核心思想：<strong>不数「被引用几次」，只看「从根还能不能到」</strong>。从根（全局变量、栈、寄存器）出发遍历引用图，能到达的标记为「活」，剩下的全是垃圾——无论它们是否互相引用。「全局可达性」取代「局部计数」，循环引用问题迎刃而解。</span>

## 1 标记-清除：最基础的追踪回收

**标记-清除（mark-sweep）**：两个阶段：

1. **标记（mark）**：从根集出发，遍历引用图，把可达对象打上标记。
2. **清除（sweep）**：线性扫描堆，把未标记的对象回收（加入空闲列表）。

```text
mark(root):                        # 标记阶段：从根集出发
    if root 未标记:
        标记 root
        for 每个被 root 引用的对象 o: mark(o)

sweep(heap):                       # 清除阶段：线性扫描堆
    for 每个对象 obj in heap:
        if obj 未标记:
            free(obj)              # 不可达 = 垃圾，回收
```

标记-清除的代价：**堆碎片**——回收后空闲块不连续（如上面的空位），后续分配要找合适块；**两次扫描**（标记遍历 + 清除扫堆）。<span class="marginnote">标记-清除的「清除」不移动对象——内存出现碎片（fragmentation）：大量小空闲块分散各处，大对象难分配。这是「非移动式回收」的通病。解法要么「压缩」要么「复制式回收」——把活对象挪到一起，消灭碎片。</span>

## 2 复制式回收：移动以除碎片

**复制式回收（copying collection）**：把堆分成两半（from-space / to-space）。回收时：

1. 从根出发，把可达对象**逐个复制**到 to-space（并更新指针）。
2. 交换 from/to——旧 from 整体成为空闲区。

复制式回收的特点：

**消除碎片**：活对象被紧凑排列在 to-space——无碎片，分配只需「移动指针」（bump allocation）。
**只处理活对象**：遍历成本与「活对象数量」成正比，而非堆大小。
**代价**：**堆利用率减半**（两半中一半空着）；复制有移动开销。

<span class="marginnote">复制式回收是「以空间换时间」：多浪费一半堆，换来「无碎片 + 分配 O(1)」。它特别适合「存活率低」的场景——大量对象很快死掉，复制只搬少数幸存者。若存活率高（对象都长寿），复制几乎白费（搬一堆活对象）——这是它不适合作「老年代」策略的原因。</span>

## 3 分代回收：多数对象早逝

**分代回收（generational GC）**：基于**弱分代假说（weak generational hypothesis）**——「大多数对象在年轻时死亡」。堆按「年龄」（经历的回收次数）分代：

```java
// JVM 的分代堆：按对象年龄分成两代
YoungGeneration young;   // 新对象先分配到这里，频繁回收（复制式）
OldGeneration   old;     // 幸存 N 次回收后晋升到这里，少回收（标记-清除 + 压缩）
```

回收策略：**新代**频繁回收（复制式，快速清掉短命对象）；**老代**少回收（标记-清除 + 压缩，活对象多不移动）。对象幸存 N 次回收后晋升老代。<span class="marginnote">分代回收是工业 GC 的标配（JVM、Go、Python 都分代）：它把「回收频率」与「对象年龄」挂钩——新代天天清、老代偶尔清。代价是「跨代引用」要处理（老对象指向新对象需记在记忆集 remembered set 里，回收新代时别漏了它）。「弱分代假说 + 分而治之」让回收成本大幅下降。</span>

## 4 公式解析：可达性判定与回收

追踪回收的核心是**可达性判定**。设根集 $R$、引用图边集 $E$，对象 $o$ 可达当且仅当：

$$
\text{reachable}(o) \iff \exists\ r \in R : (r \to o) \in E^*
$$

（$E^*$ 是引用关系的传递闭包——从某个根出发、沿引用走任意步可达。）

标记算法：

$$
\text{mark}(o) = \begin{cases}
\text{已标记} & \Rightarrow \text{跳过} \\
\text{未标记} & \Rightarrow \text{标记 } o \text{，对每个 } o \to o' \text{ 递归 mark}(o')
\end{cases}
$$

三步拆解：

- **第一步，可达即活**：从根出发沿引用图能到达的，就是活对象——标记遍历实现这个判定。
- **第二步，标记的递归**：mark(root)（从根集出发）深度优先遍历引用图——遇到未标记的标记它、继续深入其引用；已标记的跳过（防循环）。
- **第三步，清除未标记**：扫描后，未标记对象 = 从根不可达 = 垃圾 = 回收。**「标记算可达、清除收不可达」**——追踪回收的完整逻辑，循环引用在「不可达」下自然被清（环内无根可达，全被清除）。

**辨析｜易错点：** 追踪回收**处理循环引用**：两个对象互相引用（A 指向 B、B 指向 A）且无根可达时，标记阶段两者都不可达（不从根出发），清除阶段一并回收。**这正是追踪式相对引用计数的决定性优势**——它看「从根的可达性」而非「计数」，环在全局视角下无处遁形。

## 5 GC 的现代工程：停顿与并发

- **停止世界（stop-the-world）**：标记/清除时暂停程序（STW）——停顿时长是 GC 的关键指标。
- **增量/并发回收**：把标记与程序执行交错（JVM 的 CMS/G1、Go 的并发 GC）——减少停顿，换复杂度。
- **ZGC/Shenandoah**：超低停顿 GC——染色指针、读屏障，让 GC 停顿接近毫秒级。
- **Go**：并发标记 + 非分代？不——Go 用混合写屏障实现「并发标记 + 分代-ish」的平衡。<span class="marginnote">现代 GC 的战场是「停顿时间」：从「秒级 STW」到「毫秒级并发」。JVM 的 G1、ZGC，Go 的并发 GC，都是「标记-清除/复制 + 并发化 + 读写屏障」的组合。「停顿可控性」决定 GC 能否用于延迟敏感系统（如大模型推理服务的 Java/Kotlin 栈）。</span>

## 6 小结

- **追踪式回收**从根集出发标记可达对象，不可达即垃圾——全局视角解决循环引用。
- **标记-清除**：标记可达 + 扫描回收——简单但有碎片。
- **复制式**：活对象搬到另一半——无碎片、分配快，但堆减半、存活率高时低效。
- **分代回收**：按弱分代假说分代——新代频繁复制、老代偶尔压缩；现代 GC 用并发化 + 读写屏障把停顿压到毫秒级。
