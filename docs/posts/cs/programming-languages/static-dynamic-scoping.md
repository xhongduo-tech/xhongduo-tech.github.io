## 为什么从作用域开始

绑定告诉我们「名字与实体何时关联」；**作用域（scope）**则回答「一个名字在程序的哪一段可见」——即绑定在**空间**上的有效范围。两种主流机制对峙了半个世纪：**静态作用域（词法作用域）**按**代码结构**决定名字归属，是 C、Java、Python、Rust、Haskell 等几乎所有主流语言的选择；**动态作用域**按**调用序列**决定，只在少数语言（早期 Lisp、Perl、bash）残留。为什么词法作用域赢了？它给「名字的含义」一个**可预测、可静态分析**的答案——这是现代 IDE 跳转定义、编译器优化、闭包实现的共同地基。<span class="marginnote">一句话区分：词法作用域问「这个 x 写在哪个函数里」，动态作用域问「此刻是谁在调用链上」。前者看<strong>代码</strong>，后者看<strong>运行时调用栈</strong>——同一段代码在两个机制下可以给出完全不同的名字解析结果。</span>

## 1 静态（词法）作用域

**静态作用域（static / lexical scoping）**：一个名字绑定到哪个实体，由**程序文本的结构**决定——名字的解析只看它嵌套在哪段代码中，与运行时调用序列无关。

```python
x = 0                        # 模块级 x

def outer():
    x = 1                    # outer 局部 x
    def inner():
        print(x)             # 词法作用域：按文本嵌套查找
    inner()

outer()                      # 输出 1
```

上面的代码里的 x 按「文本嵌套」向上查找：先在 inner 自身找，再到 outer，再到模块级。<span class="marginnote">词法作用域的名字查找在<strong>编译期</strong>即可确定（因为文本结构是静态的）——编译器知道每个名字指向哪个声明，因此能静态检查、优化，IDE 也能「跳到定义」。这正是词法作用域成为主流的技术原因。</span>

## 2 动态作用域

**动态作用域（dynamic scoping）**：一个名字绑定到哪个实体，由**运行时的调用序列**决定——名字解析时沿调用栈向下找「最近一次给这个名字赋值的」实体。

```python
# 以下伪代码示意「动态作用域」语义（Python 本身是词法作用域）
def read_x():
    print(x)                 # 沿调用栈向上找最近绑定的 x

def set_and_call(v):
    x = v                    # 在当前调用栈上绑定 x
    read_x()                 # 打印 v——x 解析到调用者的绑定

set_and_call(2)              # 2
set_and_call(3)              # 3
```

同一个 `read_x`，如果从另一个「设置了不同 `x`」的函数调用，`x` 的结果就不同——**名字的含义随调用历史漂移**。<span class="marginnote">动态作用域的「好处」是灵活：子函数可直接访问调用者的变量，无需传参；「坏处」是灾难：名字含义不可静态预测，改一个全局变量可能影响所有调用方，排查 bug 如大海捞针。早期 Lisp 用它，后来几乎全转向词法作用域。</span>

## 3 两者的对比

| 维度 | 静态（词法）作用域 | 动态作用域 |
| --- | --- | --- |
| 名字解析依据 | 代码嵌套结构 | 运行时调用序列 |
| 解析时机 | 编译期可确定 | 运行期才可知 |
| 可读性 | 高（看代码即知） | 低（要追踪调用链） |
| 可静态优化 | 是 | 否 |
| 代表语言 | C/Java/Python/Rust | 早期 Lisp、Perl、bash |
| 与闭包的关系 | 天然契合 | 闭包难以实现 |

**辨析｜易错点：** 动态作用域与「全局变量」不是一回事。全局变量是「一个作用域里的一个绑定」，谁都能读；动态作用域是「同一名字在不同调用上下文绑定到不同实体」。区别在于：全局变量在词法作用域里照常解析（按文本找最外层），动态作用域则无视文本结构、沿调用栈找。<span class="marginnote">Python 里你看到全局变量 x 仍按词法规则解析（模块级），不是动态作用域。真正动态作用域的标志是：<strong>调用者影响了被调用函数里的名字含义</strong>——Perl 的局部变量、Emacs Lisp 的特殊变量。</span>

## 4 公式解析：名字解析算法

词法作用域的名字解析可以形式化为「沿嵌套链查找」：

$$
\text{resolve}(x, \text{scope}) = \begin{cases}
x \in \text{bindings}(\text{scope}) & \Rightarrow \text{bindings}(\text{scope})[x] \\
\text{scope} \text{ 有外层} & \Rightarrow \text{resolve}(x, \text{outer}(\text{scope})) \\
\text{否则} & \Rightarrow \text{undeclared error}
\end{cases}
$$

三步拆解：

- **第一步，当前作用域**：先看 x 是否在**当前作用域**的绑定表（bindings）里，有则返回该绑定。
- **第二步，向外爬**：没有则递归到**外层作用域**——词法作用域的外层由「文本嵌套」固定，与运行时调用无关。
- **第三步，到底报错**：爬到最外层还没有，报「未声明」错误。**这条递归链完全由源码静态确定**，因此编译器能预先把每个 x 都「翻译」成具体的绑定——这就是词法作用域可静态分析、可优化的形式化基础。

**辨析｜易错点：** 「最近的绑定」在词法作用域是「文本上最近的嵌套」；在动态作用域是「时间上最近的调用者」。两套规则共享「沿链查找」的框架，差别只在**链由什么构成**（嵌套文本 or 调用栈）——这是区分两种作用域最凝练的方式。

## 5 为什么词法作用域赢了

- **可预测性**：代码即文档，名字含义不随调用环境漂移——阅读、审查、调试都更可靠。
- **静态分析**：编译期确定绑定，是类型检查、优化、IDE 跳转、重构工具的前提。
- **闭包的基础**：词法作用域 + 一等函数让「捕获环境」可静态理解，是现代函数式与事件驱动编程的地基（第九篇闭包详讲）。<span class="marginnote">动态作用域的语言很难实现「真正」的闭包：闭包需要记住「定义时的环境」，而动态作用域偏要在「调用时」找环境——两者根本冲突。词法作用域成为主流，部分原因就是它让闭包成为可能。</span>

## 6 作用域在现代语言中的实践细节

词法作用域在现代语言里有一批「细节设计」——它们决定了实际编程的体验：

**Python 的 LEGB 规则**：局部（Local）→ 外层（Enclosing）→ 全局（Global）→ 内置（Builtin）——名字按这条链解析。Python 的**赋值**与**读取**规则不同：读名字沿 LEGB 找；给名字赋值默认创建**局部**（除非 global/nonlocal 声明）。

**JS 的 let/const vs var**：let/const 块作用域（词法），var 函数作用域 + 提升。**「var 是函数作用域、let 是块作用域」**——ES6 之后用 let/const 是标准。

**Rust 的遮蔽**：let x = 1; let x = 2;——新 let 创建新变量、遮蔽旧名。**「遮蔽 ≠ 修改」**：旧变量仍在（只是名字被占用），不可变绑定得以保持。

| 语言 | 作用域单位 | 特殊机制 |
| --- | --- | --- |
| C | 块 | 无（遮蔽简单） |
| Python | 函数 + 块(部分) | LEGB、global/nonlocal |
| JS | 函数（var）/块（let） | 提升、TDZ |
| Rust | 块 | let 遮蔽惯用 |

**辨析｜易错点：** **「作用域是『找名字』，遮蔽是『藏名字』」**——读代码时「当前这个名字指哪个声明」是作用域分析的第一直觉。遇到「改了变量但没生效」的 bug，多半是「名字被遮蔽，改的不是你以为的那个」。「IDE 的跳转定义」就是作用域分析的自动化——**「能跳对定义，就理解了作用域」**。

## 7 小结

- **静态（词法）作用域**按代码嵌套解析名字，编译期可确定，可预测、可优化、可静态分析。
- **动态作用域**按调用序列解析名字，灵活但不可预测，是历史遗留。
- 两者共用「沿链查找」框架，差别在链是**嵌套文本**还是**调用栈**。
- 词法作用域胜出的关键：可预测性 + 静态分析 + **闭包**的可行性。
