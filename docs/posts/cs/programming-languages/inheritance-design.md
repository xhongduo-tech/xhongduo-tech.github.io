## 为什么从继承开始

OOP 的三个基本概念（对象、类、消息）已经立稳；**继承（inheritance）**是第四个支柱——它让一个类**复用并扩展**另一个类的属性和方法，形成「类层次」。继承的设计充满抉择：**单继承**（一个类只有一个父类，Java/C#/Smalltalk）还是**多继承**（一个类可有多个父类，C++/Python）？继承是「is-a」还是「has-a」？继承的可见性（公有/保护/私有继承）？这一节聚焦最核心的分歧——单继承与多继承，以及多继承带来的「菱形问题」。<span class="marginnote">继承的本质是<strong>代码复用 + 类型子类型</strong>的双重承诺：子类「继承」父类的实现（复用），同时「is-a」父类（可替换，子类型多态）。这两种承诺经常纠缠——过度使用继承复用实现，会造成脆弱的类层次。</span>

## 1 继承的动机：复用与多态

**继承（inheritance）**：子类获得父类的属性和方法，并可添加或重写（override）自己的成员。

```java
class Animal { void speak() {...} }
class Dog extends Animal { void fetch() {...} }   /* Dog 拥有 speak + fetch */
```

继承的两大价值：

- **代码复用**：公共逻辑放父类，子类只写差异——`Dog` 不必重写 `speak`。
- **子类型多态**：`Animal a = new Dog()`——子类对象可用于父类位置，动态绑定到子类方法。

**辨析｜易错点：** 继承 vs 组合（composition）：继承是「is-a」（狗是一种动物），组合是「has-a」（狗有一个项圈）。**「优先组合，少用继承」**是 OO 设计的成熟经验——组合更灵活（运行时可选、不锁死类型层次），继承更直接但僵化。多数「继承灾难」源于把「has-a」误建模成「is-a」。

## 2 单继承：简单但局限

**单继承（single inheritance）**：一个类最多一个直接父类。Java、C#、Smalltalk、Kotlin 采用。

优点：

- **清晰的类层次**：所有类形成一棵树（Java 的 `Object` 是根），无歧义。
- **方法查找简单**：沿一条链向上找，无「撞车」可能。
- **实现简单**：虚表（vtable）布局直接。

局限：

- **表达能力受限**：一个「鸟」既要「飞行动物」又要「宠物」，单继承只能选其一——于是需要接口/混入补足（后面专文）。<span class="marginnote">单继承的「局限」催生了接口（Java）与协议（Swift）——「实现单继承，类型可多实现」。接口提供「契约」的多继承，类提供「实现」的单继承——这一折中成为 Java/C# 的主流方案。</span>

## 3 多继承：强大但危险

**多继承（multiple inheritance）**：一个类可有多个直接父类。C++、Python 采用。

```python
class FlyingAnimal: ...
class Pet: ...
class Bird(FlyingAnimal, Pet): ...    # 同时继承两个类
```

多继承的价值：**聚合多种能力**——`Bird` 同时拥有「飞行」与「宠物」的属性和方法，无需接口的间接性。

危险——**菱形问题（diamond problem）**：

```
       Animal
      /      \
  Mammal    Pet
      \      /
       Dog
```

`Dog` 继承 `Mammal`（继承 `Animal`）与 `Pet`（也继承 `Animal`）——`Animal` 的成员在 `Dog` 里**出现两份**。`dog.speak()` 调用哪个 `speak`？`Animal` 的字段在 `Dog` 里是一份还是两份？

<span class="marginnote">菱形问题的根源是「同一祖先被两条路径继承」——DAG（有向无环图）而非树，使「哪个成员生效」产生歧义。C++ 用「虚拟继承（virtual inheritance）」合并重复基类，Python 用「MRO（方法解析顺序）+ C3 线性化」给出唯一顺序——各有各的复杂度。</span>

## 4 公式解析：菱形问题的冲突

菱形继承的方法解析可以形式化为「继承图上的查找」。设继承关系形成 DAG，类 $C$ 的方法查找：

$$
\text{lookup}(C, m) = \begin{cases}
m \in \text{own}(C) & \Rightarrow \text{own}(C)[m] \\
C \text{ 有父类} & \Rightarrow \text{lookup}(\text{parent}(C), m) \\
\text{否则} & \Rightarrow \text{error}
\end{cases}
$$

单继承下 `parent(C)` 唯一，查找无歧义；多继承下 `C` 有多个 `parent`——查找顺序必须定义。

三步拆解：

- **第一步，单继承**：`parent(C)` 只有一个，沿唯一链向上——无歧义。
- **第二步，多继承**：多个 `parent`，先查谁？C++ 按「声明顺序」、Python 按「C3 线性化」——**语言必须规定一个全局顺序**把 DAG 压平成一条链。
- **第三步，看菱形**：`Dog` 的两条父链都到 `Animal`——若语言不合并（C++ 非虚继承），`Animal` 出现两份（数据重复）；若合并（虚继承/MRO），`Animal` 唯一但初始化顺序复杂。**「菱形问题 = 继承图非树时的二义性」**，每个多继承语言都要用额外机制消解。

**辨析｜易错点：** 多继承的「重复基类」有两种后果：数据重复（每个 `Animal` 字段两份）与语义歧义（`speak` 从哪条路径来）。Python 的 MRO 保证「每个类在序列中只出现一次」且「子类优先于父类」——它把菱形问题转化为「线性顺序问题」，但 MRO 本身也是初学者理解的黑箱。**「多继承不是免费的：你要么付复杂度，要么付歧义」**。

## 5 现代语言的对策：从多继承到接口与混入

面对多继承的复杂度，现代语言普遍「放弃实现多继承，保留契约多继承」：

| 语言 | 实现继承 | 契约多继承 | 机制 |
| --- | --- | --- | --- |
| Java | 单继承 | 接口多实现 | `implements A, B` |
| C# | 单继承 | 接口多实现 | `: IA, IB` |
| C++ | 多继承 | （多继承本身） | `virtual` 继承 |
| Python | 多继承 | （多继承本身） | MRO + mixin |
| Rust | （无类继承） | trait 多实现 | `impl A for T, impl B for T` |

<span class="marginnote">趋势：<strong>接口/协议/trait 取代「实现多继承」</strong>——「继承实现」保持单链简单，而「继承契约」可以多路（一个类实现多个接口）。Rust 甚至完全抛弃类继承，用 trait + 组合替代——「组合优于继承」的极端形态。多继承的实现复杂度，让大多数现代语言选择「契约多、实现单」。</span>

## 6 小结

- **继承** = 代码复用 + 子类型多态的双重承诺；「is-a」与「has-a」要分清（优先组合）。
- **单继承**简单清晰（一棵树、无歧义），但表达能力受限，催生接口补足。
- **多继承**聚合多种能力，但引入**菱形问题**——同一祖先经两路径继承的二义性。
- 菱形问题靠 C++ 虚继承、Python MRO 等机制消解，复杂度高；现代语言普遍「实现单继承 + 契约多继承」。
