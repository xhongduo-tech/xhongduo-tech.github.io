## 为什么从命名封装开始

ADT 封装了「数据与操作」；但大型程序还有另一种封装需求——**名字的归属**。当两个库都定义 `List`、`Map`，如何共存？**命名空间（namespace）/ 包（package）**把名字组织进「命名空间」，让「同名不同源」的名字安然共处。它看似只是「改名」的机制，实则是模块化编程的关键：命名空间既是**避免冲突**的容器，又是**组织代码**的边界，还常常承载**可见性控制**（包内可见 vs 外部可见）。<span class="marginnote">命名空间的本质是「限定名（qualified name）」：`std::vector` 中的 `std` 是命名空间，`vector` 是其中的名字。把「全局名字空间」打散成多个「局部命名空间」，冲突面从「全程序」缩小到「一个命名空间内」。</span>

## 1 为什么需要命名空间

程序规模增长带来的**名字冲突（name collision）**：

两个库都导出 `List`、`Map`——直接冲突。
全局名字空间被各方污染——`count`、`date` 这类短名被抢。

没有命名空间的代价（早期 C 的困境）：

```c
/* 早期 C：所有全局符号共用一个名字空间 */
int count;              /* 库 A 的全局量 */
int count;              /* 库 B 也定义了 count —— 重复定义，链接错误 */
```

**命名空间（namespace）**：一组名字的命名容器，容器间名字互不干扰。

```cpp
namespace A { int count; }   // 库 A 的 count
namespace B { int count; }   // 库 B 的 count —— 互不干扰

A::count = 1;                // 限定名访问
B::count = 2;
```

## 2 命名空间的机制

**命名空间机制**由两个操作组成：

**导入（import）**：把名字引入当前作用域——`using`（C++）、`import`（Python/Java）。
**限定访问**：用「命名空间 :: 名字」明确指路——`std::vector`、`java.util.List`。

各语言实现对比：

| 语言 | 命名单元 | 导入语法 | 别名 |
| --- | --- | --- | --- |
| C++ | `namespace` | `using` / `using namespace` | `namespace X = Y;` |
| Java | `package` | `import` | 无 |
| Python | 模块/包（`module`/`package`） | `import` / `from ... import` | `import x as y` |
| Rust | `mod`/`crate` | `use` | `use m::x as y` |
| Go | `package` | `import` | 包名即引用名 |

<span class="marginnote">命名空间的一个设计问题：<strong>是否「扁平」还是「分层」</strong>。Java/Python 支持「点号分层」（`java.util.List`），C++ 的 namespace 可嵌套但常用扁平。分层命名空间（包路径）让「层级即组织」，是大型代码库的组织骨架。</span>

## 3 命名空间与可见性：包作为封装边界

命名空间不仅是名字容器，还常与**可见性控制**绑定：

- **Java**：包是可见性单位——`package`-private（默认）成员仅包内可见。
- **Python**：模块是可见性边界——`_` 前缀（下划线）约定模块私有。
- **Rust**：`mod` + `pub`——模块内默认私有，`pub` 显式导出。

**辨析｜易错点：** 命名空间 ≠ 封装。命名空间解决「名字冲突」，封装解决「实现隐藏」——两者可以独立。一个 `public` 的命名空间成员名字不冲突，但内部完全可见；一个 `private` 的封装成员即使有命名空间也对外隐藏。**「命名空间管名字，封装管可见性」**——Java 的 `public` 类（命名空间可见）可以有 `private` 字段（封装隐藏），两者互补。

## 4 公式解析：限定名解析

命名空间的名字解析可以形式化。设名字空间层级 $N_1 \supset N_2 \supset \dots$，限定名 $N_1.N_2.\dots.n$ 的解析：

$$
\text{resolve}(N_1.N_2.\dots.n) = \text{在 } N_1 \text{ 中查 } N_2 \text{，在 } N_2 \text{ 中查 } N_3,\ \dots,\ \text{最后在 } N_k \text{ 中查 } n
$$

三步拆解：

- **第一步，逐级下钻**：限定名从左到右逐级进入命名空间——`java.util.List` 先进 `java`、再进 `util`、取 `List`。每级把查找范围缩小一个命名空间。
- **第二步，看冲突消除**：两个 `List`（`java.util.List` 与 `myapp.List`）因「完整路径」不同而区分——**冲突在「最内层名字」处，由「外层路径」消解**。
- **第三步，看解析顺序**：不带限定符的名字（裸 `List`）按「当前导入」解析——导入的命名空间被「展开」进当前作用域；多个导入同名时仍冲突，需用限定名。**「限定名无歧义，裸名可能歧义」**——所以大型代码库偏好限定名。

**辨析｜易错点：** 通配导入（`using namespace std;`、`import java.util.*;`）把整个命名空间「摊平」进当前作用域——虽然方便，但**重新引入冲突**（两个通配导入引入的同名者打架）。「限定名优先、通配导入克制」是现代代码风格（Google C++ 风格指南建议避免 `using namespace`）。

## 5 命名空间的现代实践

- **Rust 的模块系统**：`mod` 嵌套 + `pub` 导出 + `use` 引入——模块既是命名空间又是封装边界，且**文件系统即模块树**。
- **Go 的包**：包名即命名空间，导入路径唯一；「小接口 + 包级封装」是其哲学。
- **Python 的包**：目录 + `__init__.py` 构成包；`from . import x` 相对导入。
- **Java 的模块系统（JPMS）**：`module-info.java` 在包之上再加一层「模块」——命名空间之上再分「依赖边界」。

<span class="marginnote">命名空间从「解决冲突的工具」演化为「代码组织与依赖治理的骨架」：Java 的 JPMS、Rust 的 crate/module、Go 的 package 都是「命名空间 + 可见性 + 依赖」的复合体。「名字该怎么组织」已从技术问题上升为架构问题。</span>

## 6 小结

- **命名空间**把名字组织进容器，解决「同名不同源」的冲突；核心操作是**导入**与**限定访问**。
- 语言实现：C++ `namespace`、Java/Python 包、Rust `mod`/`crate`、Go `package`——分层 vs 扁平各有取舍。
- 命名空间 ≠ 封装：前者管名字冲突，后者管实现隐藏；两者互补（public 类型 + private 字段）。
- 限定名解析 = 逐级下钻命名空间；通配导入重新引入冲突，限定名优先是现代实践。
