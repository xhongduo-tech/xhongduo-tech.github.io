## 为什么从函数式语言实现开始

函数式语言没有循环，一切重复靠递归——那么「跑一个递归 100 万次的函数」会不会爆栈？答案是「看实现」：**尾调用优化（tail call optimization, TCO）**把「尾位置」的递归调用翻译成跳转（循环），栈不增长。这既是函数式编译器的关键优化，也是「递归能否承担循环角色」的实现保证。此外，函数式语言还有一系列实现问题——惰性求值的图归约（thunk）、闭包的堆分配、严格性分析。这一节聚焦两个核心：**尾递归**与**求值策略的实现**。<span class="marginnote">「尾调用优化」的普适价值：任何语言里，`return f(x)` 形式的尾调用都可以不用新栈帧——复用当前帧直接跳转。Java 至今不做 TCO（安全原因），Rust/JS（严格模式）有部分 TCO，函数式语言（Scheme/Haskell）则<strong>强制</strong> TCO——因为它没有循环，TCO 是递归的生存前提。</span>

## 1 尾递归：递归的最后一步是调用自身

**尾递归（tail recursion）**：递归调用出现在函数的**尾部**（`return f(...)` 的位置）——调用后不再做任何操作。

```scheme
;; 非尾递归：乘在递归之后
(define (fact n) (if (= n 0) 1 (* n (fact (- n 1)))))

;; 尾递归：递归调用是最后一步
(define (fact-tr n acc)
  (if (= n 0) acc
      (fact-tr (- n 1) (* n acc))))   ; 尾位置
```

非尾递归 `fact 5` 的求值：`5 * (4 * (3 * ...))`——**乘法在递归返回后才做**，需要保存每一层栈帧。尾递归 `fact-tr` 用**累积参数（accumulator）**把「待做的事」提前算好，递归调用无需保存状态。<span class="marginnote">「累积参数」是把非尾递归转尾递归的标准手法：把「返回后还要做的运算」变成「已经算好的部分结果」传给下一层。`fact-tr` 的 `acc` 保存「乘到目前的积」，递归本身不再需要回溯计算——于是可以优化为循环。</span>

## 2 尾调用优化：递归变循环

**尾调用优化（TCO）**：若一个调用处于**尾位置**（调用后立即返回其结果），编译器可**复用当前栈帧**——不压新帧，直接跳转到被调函数。

```
fact-tr(5, 1)
  → fact-tr(4, 5)      # 复用帧，不压栈
  → fact-tr(3, 20)
  → ... 
  → fact-tr(0, 120)    # 栈深度恒为 1！
  → 120
```

效果：**尾递归函数的空间复杂度从 O(n) 降到 O(1)**——100 万次递归也不爆栈。尾递归 + TCO = 函数式语言里的「循环」：表达为递归、执行为迭代。<span class="marginnote">TCO 的普适形式是<strong>尾调用（tail call）</strong>——不只递归，任何 `return f(x)` 都可优化。但「尾<strong>递归</strong>优化」特别重要，因为它是「递归承担循环角色」的实现保证。Scheme 标准<strong>强制</strong>实现 TCO，Haskell 的惰性让尾部求值自然「延迟」，Rust 用 `#[must_use]` 语法配合迭代器更常用显式循环而非递归。</span>

## 3 求值策略的实现：惰性的图归约

惰性求值（上一节）的实现机制是**图归约（graph reduction）**：表达式表示成图（共享子表达式），求值 = 把图归约成弱头范式（WHNF）。

```haskell
xs = map square [1..]     -- thunk：未求值，保存配方
head xs                   -- 只逼出第一个 square 1
```

实现要点：

- **thunk**：未求值的表达式，封装「配方」。
- **按需 force**：需要值时才归约 thunk；归约结果**就地更新**（update in place）——后续引用直接读结果（call-by-need 的共享）。
- **WHNF**：归约到「最外层构造器出现」即可——`1 : rest` 的 `rest` 仍是 thunk。

**辨析｜易错点：** 惰性实现的「空间泄漏」源于 thunk 堆积：`foldl (+) 0 [1..n]` 中每个 `+` 都变成嵌套 thunk，内存 O(n)。**严格性分析（strictness analysis）**让编译器识别「肯定会被用到的参数」，提前求值避免 thunk——这是 GHC 的重要优化，也是「为什么 `foldl'` 比 `foldl` 省内存」的底层原因。

## 4 公式解析：尾递归优化的正确性

TCO 的正确性可以形式化：尾位置调用与原调用**语义等价**——尾调用后无操作，所以「复用帧」与「新建帧」产生相同结果。

设 $f$ 的尾调用为 `return g(x)`，则：

$$
\text{eval}(f, \sigma) = \text{eval}(g(x), \sigma') \quad \text{（$f$ 与 $g$ 共享最终结果）}
$$

$$
\text{TCO}: \text{栈深度}(f \to g) = 1 \quad \text{（而非 2）}
$$

三步拆解：

- **第一步，语义等价**：尾调用后 $f$ 没有后续操作，$f$ 的结果 = $g(x)$ 的结果——所以「帧可以扔掉」。
- **第二步，空间收益**：正常调用 $f$ 压帧、$g$ 再压帧（深度 2）；TCO 复用 $f$ 的帧（深度 1）。递归链上每层省一帧——O(n) 变 O(1)。
- **第三步，看前提**：TCO 的前提是「**尾位置**」——调用后不能有清理、回溯、等待。`(* n (fact (- n 1)))` 中 `fact` 不在尾位置（乘在等待），不能优化。**「尾位置的判定」是编译器能否优化的分水岭**。

**辨析｜易错点：** 「尾递归」与「尾调用」：尾递归是「尾调用且调用自身」的特例。**所有尾调用都可 TCO，不只是递归**——`return g(x)`（调用别的函数）同样可优化。把 TCO 局限在「递归」是常见误解；函数式语言里相互尾调用（A 尾调 B、B 尾调 A）也能 O(1) 空间。

## 5 函数式语言的实现技术一览

- **闭包实现**：捕获环境存堆（第九篇已述），函数值 = 代码指针 + 环境指针。
- **类型擦除/单态化**：Haskell 用类型类字典（typeclass dictionary）传递方法表；Rust 单态化生成专用代码。
- **STG 机**：GHC 的 Spineless Tagless G-Machine——惰性函数式语言的抽象机器，thunk 与更新操作的经典实现。<span class="marginnote">GHC（Haskell 编译器）把 Haskell 编译到 STG（无标签的无脊柱 G 机），再经 C/LLVM 到机器码。STG 是「图归约」的具体机器化：每个 thunk 一个堆对象，被逼值时「更新」成结果。理解 STG 的要点是「共享 + 按需」——它是惰性求值的工程实现蓝本。</span>
- **编译策略**：惰性语言编译难（求值顺序不可预测），GHC 用「严格性分析 + 内联 + 融合」把大量惰性代码优化成严格的机器码。

## 6 小结

- **尾递归**：递归调用在尾部 + 累积参数——把「返回后待做」提前算完。
- **尾调用优化（TCO）**复用帧、O(n) 栈变 O(1)——递归承担循环角色的实现保证；Scheme 强制、JS/Rust 部分支持。
- **惰性实现** = 图归约：thunk 保存配方、按需 force、结果就地更新（共享）；WHNF 是最低归约要求。
- 函数式实现技术还包括闭包堆分配、类型类字典、STG 抽象机；「尾位置判定」是能否优化的分水岭。
