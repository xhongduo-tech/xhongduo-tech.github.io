## 为什么从绑定开始

上一节把变量拆成「名称 + 地址 + 类型 + 值」四个属性。但属性不会凭空存在——每个属性都要在某个时刻被「确定」下来：`x` 这个名字何时关联到一个地址？它的类型何时定死？它的值何时写入？**绑定（binding）**就是「属性与实体之间的关联」，而**绑定时间（binding time）**回答「这种关联在何时建立」。绑定时间把语言设计从「写什么」提升到「何时决定什么」的维度——它解释了为什么 Python 变量可随意换类型而 C 不能，为什么静态数组长度必须编译期已知。<span class="marginnote">「绑定时间」是 PLT 的一把万能钥匙：几乎任何「为什么这门语言这样」的问题，都可以翻译成「它在哪个阶段做这个决定」。越早绑定越高效、越静态；越晚绑定越灵活、越动态——语言的全部性格，就是一部绑定时间的谱系。</span>

## 1 绑定：属性与实体的关联

**绑定（binding）**：一个属性与其实体之间的关联。例：

- 名称 `x` 绑定到变量（名称→变量绑定）；
- 变量绑定到类型 `int`（变量→类型绑定）；
- 变量绑定到存储地址（变量→存储绑定）；
- 变量绑定到当前值（变量→值绑定）。

**绑定时间（binding time）**：绑定被建立的时刻。塞贝斯塔列举了从早到晚的主要绑定阶段：

| 阶段 | 例子 |
| --- | --- |
| 语言设计时 | `+` 的含义、语法规则、关键字 |
| 语言实现时 | `int` 的字长、栈布局约定 |
| 编译时 | 静态数组长度、常量折叠、类型检查 |
| 链接时 | 全局符号与库函数的地址 |
| 加载时 | 程序装入内存的基址 |
| 运行时 | 动态数组长度、变量的值、动态分派 |

<span class="marginnote">一条贯穿线索：<strong>语言设计时的绑定最「早」最固化</strong>（`+` 永远是加法），运行时的绑定最「晚」最灵活（`x` 此刻等于多少）。「早绑定」付出灵活性换取效率与可检查性，「晚绑定」反之——编译器、解释器、JIT 的许多策略，本质都是在调整某个属性的绑定时间。</span>

## 2 静态绑定与动态绑定

沿绑定时间划出两大阵营：

**静态绑定（static binding）**：在运行前（编译期或更早）完成。

- 变量的**类型**（C、Java 声明时固定）；
- 静态数组的**长度**；
- 非虚方法的**调用目标**（编译期确定地址）。

**动态绑定（dynamic binding）**：在运行时完成。

- 变量的**值**（每次赋值都在绑定）；
- 动态数组的**长度**；
- 虚方法的**调用目标**（运行时查虚表）。

**辨析｜易错点：** 「静态类型」与「静态绑定」是相关但不同的概念。静态类型说的是「变量有固定类型」，静态绑定说的是「属性在运行前确定」。一个变量可以类型静态（C 的 `int`）却在运行时绑定新值——**「类型静态」不影响「值动态」**。把两者混为一谈，是常见的概念滑坡。

## 3 类型绑定：声明时绑定 vs 赋值时绑定

变量何时获得类型，是语言最重要的绑定时间选择之一：

**显式类型声明（explicit declaration）**：`int x;`——编译期绑定类型，静态类型检查的前提。<span class="marginnote">C、Java 的变量必须在用前声明类型。Fortran 甚至允许「隐式声明」（未声明的名字默认 `I–N` 开头的整型）——历史上制造过无数拼写 bug，现代语言几乎都要求显式或推导。</span>

**类型推导（type inference）**：`let x = 5;`（Rust/Swift）——编译期绑定，但类型由初始化式推导，不需手写。

**隐式声明（implicit declaration）**：Python `x = 5`——类型**绑定到值**而非变量，变量本身无类型，运行时随赋值变化。这是「绑定时间最晚」的类型策略。

## 4 公式解析：绑定的形式化

绑定可以用「环境」概念形式化。**环境（environment）**是把名称映射到实体的函数：

$$
\rho : \text{Name} \to \text{Entity}, \qquad
\rho(x) = \langle \text{type}, \text{address}, \text{value} \rangle
$$

**赋值**是「更新环境中的值分量」：

$$
\rho' = \rho[x \mapsto \langle \text{type}(x), \text{addr}(x), v \rangle]
$$

三步拆解：

- **第一步，环境是函数**：$\rho$ 把每个名字映射到它的实体（含类型、地址、值）。读变量 = 查 $\rho(x)$。
- **第二步，赋值是环境更新**：$\rho[x \mapsto \dots]$ 表示「除了 x 的分量替换成新值，其余不变」。赋值**不改变**名称与类型的绑定，只改变**值**的绑定——这正是「值绑定最晚、随时可改」的形式化。
- **第三步，看绑定时间差异**：若类型绑定在环境创建时就固定（静态），则 $\rho(x).\text{type}$ 恒定；若类型也随赋值变化（动态），则 $\rho'$ 连类型一起换——**两种语言策略在同一个 $\rho$ 记号下只差「更新的分量不同」**。

**辨析｜易错点：** 绑定与**赋值**的边界：绑定是「建立关联」，赋值是「改变值分量」。`int x;` 是绑定（名字→变量+类型），`x = 5;` 是赋值（值分量更新）。C 的声明与赋值分离，Python 的 `x = 5` 同时「首次绑定」与「赋值」——但概念上仍应分开。

## 5 绑定时间与设计权衡

- **早绑定（编译期）**：类型安全、可优化、错误前置；代价是灵活性受限（不能运行期改类型）。
- **晚绑定（运行期）**：灵活、动态、可处理异构数据；代价是性能开销、错误延迟。
- **混合策略**：现代语言普遍「类型早绑定、值晚绑定」；「虚方法晚绑定、非虚方法早绑定」；「静态检查为主、运行时兜底」。<span class="marginnote">JIT 编译是「重新调整绑定时间」的极致：HotSpot 先解释（晚绑定、快启动）再编译热点（早绑定、快执行）。绑定时间不是宿命——现代运行时可以动态迁移。</span>

## 6 小结

- **绑定**是属性与实体的关联，**绑定时间**是关联建立的时刻，从语言设计到运行时构成一条谱系。
- 绑定时间分**静态**（运行前）与**动态**（运行时）；「静态类型」≠「静态绑定」。
- 类型绑定三策略：**显式声明 / 类型推导 / 隐式声明**，分别对应编译期与运行期。
- 环境模型 $\rho : \text{Name} \to \text{Entity}$ 把赋值看成「只改值分量的环境更新」；绑定时间差异即「更新哪些分量」。
