## 为什么从 IaC 开始

CD 流水线把"代码"送到"基础设施"上——但**基础设施本身**怎么管理？传统做法是运维手工配置服务器（SSH 进去敲命令），不可复现、不可审计。**基础设施即代码（Infrastructure as Code, IaC）**把基础设施（服务器、网络、数据库、负载均衡）也用**代码描述**，从而享受版本控制、评审、测试、自动化的一切红利。这一节讲 IaC 的三大支柱与主流工具。

## 1 基础设施即代码：把"环境"变成"代码"

**基础设施即代码（IaC）**：用**声明式或编程式的代码**来描述与配置基础设施，代替手工操作。

IaC 带来的能力（对应第 12 章 SCM 的"可复现"）：

- **可版本化**：基础设施代码进 Git，历史可追溯、可回滚。
- **可评审**：改基础设施走 PR 评审（第 14 章）——"改环境"和"改代码"同流程。
- **可重复**：同一代码重建出**一模一样**的环境（开发/测试/生产一致）。
- **可自动化**：环境创建与销毁被流水线驱动——CI/CD 的"环境准备"环节自动化。

**辨析｜易错点：** IaC 的第一个误解是"**IaC 只是把命令写成脚本**"。**脚本是命令的序列（过程式），IaC 描述"目标状态"（声明式）**——真正的 IaC 说"我要 3 台 web 服务器 + 1 个负载均衡"，工具自动把当前状态调整到目标状态，而不是"执行这 10 条命令"。判断标准：**这份代码是描述"要什么"，还是描述"怎么敲"？** 描述"要什么"才是 IaC。

## 2 IaC 的两大范式：声明式与过程式

- **声明式（declarative）**：描述**目标状态**，工具负责"如何达到"。代表：Terraform、CloudFormation、Kubernetes（YAML）。优点：**幂等**（多次执行结果一致）、自动收敛；缺点：抽象高、调试困难。
- **过程式（imperative）**：描述**执行步骤**。代表：Shell 脚本、Ansible（部分）、Puppet 早期。优点：灵活、直观；缺点：不幂等（多跑一次可能出错）、容易漂移。

**辨析｜易错点：** 声明式与过程式的核心差别是**幂等（idempotency）**：声明式"跑十次结果一样"（幂等），过程式"跑十次可能跑挂"（非幂等）。**幂等是 IaC 的黄金性质**——因为基础设施操作要能重复执行（重试、重建、一致性检查）。**优先选声明式**，除非场景需要过程式的细粒度控制。<span class="marginnote">Terraform 的"状态文件（state）"是理解声明式 IaC 的关键：<strong>工具记录"当前实际是什么"（state），与"代码想要的"（config）对比，算出差异并执行变更</strong>。这就是"目标状态 → 收敛"的机制。这也解释了 IaC 的两个常见坑：<strong>state 要妥善保管</strong>（丢了就等于失忆）、<strong>别手工改环境</strong>（绕过 IaC 的修改会让 config 与 state 脱节——"漂移"）。</span>

## 3 配置管理工具：基础设施的日常运维

**配置管理（configuration management）**工具管"已存在环境的日常状态"——软件安装、配置文件、服务启停：

- **Ansible**：**无代理**（SSH 直连）、过程式为主、简单易学。
- **Puppet / Chef**：代理制、声明式为主、规模大时强。
- **SaltStack**：分布式、速度快。

配置管理工具的定位与 IaC 工具互补：**IaC 管"环境怎么创建"（Terraform 建云资源），配置管理管"建好后上面装什么"（Ansible 装应用、配服务）**——现代实践中常组合使用（Terraform 建基础设施 + Ansible 配服务器 + Kubernetes 管容器编排）。

**辨析｜易错点：** IaC 工具与配置管理工具常被混为一谈——**Terraform 管"创建云资源"（VM、网络、数据库），Ansible 管"在已有资源上配置"（装包、改配置）**。一句话：**IaC 管"环境的地基"，配置管理管"地基上的装修"**。选型不是"二选一"，而是按职责组合。

## 4 IaC 与 CI/CD 的融合

IaC 在 CI/CD 流水线里的角色：

- **环境即流水线**：测试环境、预发环境用 IaC 自动创建，用完自动销毁——环境生命周期自动化。
- **基础设施也跑 CI**：IaC 代码提交后，跑"配置校验、语法检查、计划预览（terraform plan）"——基础设施变更也过验证。
- **不可变基础设施（immutable infrastructure）**：不"修改"现有服务器，而是**重新创建**新实例部署新配置——"修不如重建"，消灭漂移。

**辨析｜易错点：** 传统运维是"**可变基础设施**"（登录服务器改配置），现代 DevOps 倾向"**不可变基础设施**"（不修改，直接重建）。**不可变模式把"配置漂移"从根上消灭**——环境永远等于代码描述的样子。判断标准：**你的生产环境能否"删了重建"出一模一样的？** 能，就是不可变；不能，就是手工漂移。

## 5 小结

- **IaC** 用代码描述基础设施，享受版本化、评审、可重复、可自动化。
- IaC ≠ 脚本：**声明式描述"目标状态"**（幂等）优于过程式命令序列。
- 声明式（Terraform/K8s）幂等可收敛，过程式灵活但易漂移——**幂等是 IaC 的黄金性质**。
- **配置管理工具**（Ansible/Puppet）管"已有环境的日常配置"，与 IaC 工具互补。
- **不可变基础设施**：修不如重建，从根上消灭配置漂移。
- IaC 融入 CI/CD：环境自动化创建/销毁，基础设施变更也过验证与评审。
