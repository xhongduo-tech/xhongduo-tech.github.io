## 为什么从界面分析开始

上一节给了三条黄金规则，但"规则"要在"理解"之上才有用。**界面分析**是界面设计的第一步：在画任何界面之前，先回答三个问题——**用户是谁、要完成什么任务、在什么环境下用**。跳过这一步的界面设计，等于不看说明书就组装机器。

## 1 用户分析：不是"用户"而是"用户们"

**用户分析（user analysis）**要识别**不同的用户类别**，而不是笼统的"用户"。同一个系统通常有多类用户，需求各不相同：

- **新手用户**：需要引导、提示、逐步向导。
- **熟练用户**：需要快捷键、直接操作、信息密度高。
- **专家用户**：需要批处理、脚本、深层定制。

**辨析｜易错点：** 最常见的错误是"为一个用户设计"——设计者通常默认用户和自己一样（会打代码、懂术语），做出"开发者友好、真实用户痛苦"的界面。用户分析的核心方法是**用户画像（persona）**：给每类用户建一个带名字、背景、目标、技术水平的虚拟角色，设计时不断问"王阿姨会怎么用这个界面？"<span class="marginnote">用户画像（persona）由 Alan Cooper 提出，是把"抽象用户"变成"具体人物"的工具：一个有名字、照片、性格、痛点、使用场景的虚构角色。它让设计讨论从"用户可能喜欢 X"变成"李会计每天录入 200 张发票，她会怎么理解这个表单？"——抽象的争论瞬间变得可检验。</span>

## 2 任务分析：用户到底在做什么

**任务分析（task analysis）**回答"用户用系统完成什么、怎么一步步完成"。核心方法：

- **任务分解**：把大任务拆成子任务序列——"下单"拆成"选商品→填地址→选支付→确认"。
- **频率与重要性**：区分高频任务与低频任务，高频任务放在界面最顺手的位置。
- **任务场景**：回到第 3 章的"场景建模"——界面任务分析可以直接复用需求阶段的用例与场景。

**辨析｜易错点：** 任务分析 ≠ 功能清单。功能清单是"系统有什么"，任务分析是"**用户怎么用系统达成目标**"。两者的差别体现在界面：按功能组织的界面是"菜单树"，按任务组织的界面是"流程引导"。例如照片应用按"任务"组织（"分享照片"是一个任务）比按"功能"组织（"打开→选择→压缩→上传"四个菜单）更贴近用户心智。

## 3 环境分析：在哪用、用什么设备

**环境分析（environment analysis）**考察系统使用的物理与社会环境：

- **物理环境**：室内还是室外、光线、噪音、是否移动中。
- **设备环境**：屏幕尺寸、输入方式（触屏/鼠标/键盘）、网络带宽。
- **社会与组织环境**：单用户还是多人协作、是否在监管下使用、安全要求。

环境直接决定界面形态：**野外作业的巡检系统**（强光、戴手套、单手操作）需要大按钮、高对比度、语音反馈；**银行柜员的交易系统**（固定终端、密集操作）需要快捷键、高信息密度。<span class="marginnote">环境分析在移动与 IoT 时代尤为关键：同一套界面在手机竖屏、平板横屏、车载屏幕、可穿戴设备上的表现天差地别。响应式设计、渐进式 Web 应用（PWA）、多模态交互（语音+触控）都是"环境分析"的产物——先弄清环境约束，再选择界面形态。</span>

## 4 分析结果如何驱动设计

界面分析的产出是一份**分析输入文档**，直接喂给设计阶段：

| 分析 | 产出 | 驱动什么 |
| --- | --- | --- |
| 用户分析 | 用户画像、用户类别 | 界面复杂度、引导强度、术语 |
| 任务分析 | 任务分解、频率矩阵 | 信息布局、流程设计 |
| 环境分析 | 环境约束清单 | 设备适配、交互形态 |

<span class="marginnote">这与需求工程的分析模型一脉相承：用户画像近似"参与者"，任务分解近似"用例"，环境约束近似"非功能性需求"。界面分析不是新学科，而是<strong>把需求分析聚焦到"人机交互"这一维</strong>。第 3 章的分析做得好，界面分析就水到渠成。</span>

## 5 小结

- **界面分析**先于设计：回答用户是谁、任务是什么、环境怎么样。
- **用户分析**用**用户画像**区分用户类别，避免"为一个用户设计"。
- **任务分析**把任务分解成子任务，按频率与重要性组织界面。
- **环境分析**考察物理、设备、社会环境，决定界面形态。
- 分析产出（画像、任务分解、环境约束）直接驱动设计决策。
- 界面分析与需求分析一脉相承，是"人机交互"维度的聚焦。
