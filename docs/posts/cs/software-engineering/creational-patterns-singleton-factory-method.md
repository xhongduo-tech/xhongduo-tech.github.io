## 为什么从单例与工厂方法开始

创建型模式共五个（单例、工厂方法、抽象工厂、建造者、原型），核心思想一致：**把"创建对象"与"使用对象"分离**，让创建逻辑不污染业务代码、让换一种对象不牵连所有调用方。这一节讲最常用的两个：**单例**（全局唯一）与**工厂方法**（延迟到子类决定实例化哪个类）。

## 1 单例模式：全局唯一实例

**单例（Singleton）**：保证一个类**只有一个实例**，并提供一个全局访问点。

经典实现三要素：

1. **私有构造方法**：外部无法 `new`（实例化）。
2. **静态实例变量**：持有唯一实例。
3. **静态获取方法**：`getInstance()` 首次创建、后续复用。

典型实现（懒汉式）：`private static Singleton instance;` 加 `public static synchronized Singleton getInstance() { if (instance == null) instance = new Singleton(); return instance; }`——判空后懒加载，返回唯一实例。

适用场景：**日志、配置管理、线程池、数据库连接池**——这些对象全局唯一、共享状态，重复创建既浪费又可能造成状态冲突。<span class="marginnote">单例的争议在于它常被当作"全局变量的合法化"：隐式的全局依赖让测试困难（难替换）、并发时要处理线程安全（双重检查锁、枚举实现等）。现代实践的倾向是<strong>用依赖注入容器管理单例生命周期</strong>，而不是在类里硬编码 `getInstance()`——"单例"作为"一个实例"的语义保留，"全局可访问"的机制被 DI 替代。</span>

**辨析｜易错点：** "只有一个实例" ≠ "必须是单例模式"。如果唯一性靠容器/框架保证（Spring 的默认单例 bean、进程内只启动一次），就不需要手写单例。单例的**代价**（全局状态、难测试）只在确实需要"全局唯一 + 全局访问"时才值得付。

## 2 工厂方法：让子类决定造哪个

**工厂方法（Factory Method）**：定义一个创建对象的接口，**让子类决定实例化哪个类**——把"创建哪个对象"的决策延迟到子类。

结构：

**Product**（产品接口）定义产品行为；**ConcreteProduct** 实现具体产品；**Creator**（抽象创建者）声明工厂方法 `factoryMethod()`；**ConcreteCreator** 重写 `factoryMethod()`，返回具体产品实例。

**辨析｜易错点：** 工厂方法 ≠ "一个静态工具方法返回对象"。**静态工厂（static factory）**只是一个便捷封装（如 `Integer.valueOf(int)`）；**工厂方法模式**的核心是**多态**——调用方依赖抽象创建者，具体创建哪个产品由子类运行时决定。判断标准：**是否存在"创建者子类"在替换创建逻辑？** 没有，就只是静态工厂。

适用场景：框架的"钩子"设计——框架定义创建接口，使用者通过子类定制创建的产品。经典例子：文档应用里 **Application** 与 **Document**——**Application** 的工厂方法 `createDocument()` 由子类（**WordApplication**、**SpreadsheetApplication**）决定返回 **WordDocument** 还是 **SpreadsheetDocument**。<span class="marginnote">工厂方法的收益是<strong>OCP 的实现</strong>：新增一种产品 = 新增一个创建者子类 + 产品类，调用方代码不动。代价是类的数量膨胀（每个产品配一个创建者）。当产品种类多到类爆炸时，就该考虑用抽象工厂或简单的参数化工厂。</span>

## 3 单例与工厂方法的关系

两种模式经常**组合**出现：工厂方法内部创建的产品，常用单例保证唯一；而"创建逻辑集中"的工厂本身，也常实现为单例。

| 维度 | 单例 | 工厂方法 |
| --- | --- | --- |
| 回答的问题 | 实例唯一吗？ | 造哪个类？ |
| 关键机制 | 私有构造 + 静态访问 | 抽象创建者 + 子类多态 |
| 变化点 | 唯一性、线程安全 | 产品类型 |
| 主要代价 | 全局状态、难测试 | 类数量膨胀 |

**辨析｜易错点：** 创建型模式里的"单例+工厂"常见，但别把"工厂是单例"当成模式本身。单例解决"实例数"，工厂解决"选择哪个类"——两个正交问题，各自独立评估是否该用。

## 4 实战：一个支付系统的工厂方法

把工厂方法用在最典型的场景——**支付渠道创建**。需求：系统要支持支付宝、微信、银联三种支付方式，且未来很可能增加新渠道。

**朴素实现**：在业务代码里 `if (type == "alipay") new AlipayPay() else if (type == "wechat") new WechatPay()...`——每新增一个渠道，所有调用点都要改这个 if 链，且新渠道的初始化逻辑散落各处。

**工厂方法**：定义 `PayFactory.createPay(type)`，由它负责 if-else 分支与初始化；业务代码只调 `factory.createPay(type)`。新增支付宝渠道 = 新增 `AlipayPay` 类 + 在工厂的 if 里加一行，**业务代码零改动**。更进一步，把工厂拆成 `AlipayPayFactory`、`WechatPayFactory`（每个子类工厂创建一种产品），连 if 都消除——这是"工厂方法"与"简单工厂"的差别：**简单工厂用分支，工厂方法用继承**。

**辨析｜易错点：** 工厂方法与单例的搭配有个经典陷阱：**把单例当作"隐藏全局变量"的万能工具**。`PayFactory.getInstance()` 被到处调用，测试时无法替换成 mock（第 8 章），系统悄悄多了隐式依赖。正确做法：单例只保证"全局唯一"，**依赖注入**（构造函数传入）比"到处 getInstance()"更可测。**"全局唯一"和"隐式全局依赖"是两回事——前者是单例的职责，后者是单例被滥用的症状。**

## 5 数值算例：工厂方法消除的重复

用一个数字感受工厂的价值。设支付方式有 3 种、每种需要"初始化 + 验签 + 下单"三步：

- **不用工厂**：N 个调用点各写一遍"初始化 + 验签 + 下单"的组装代码。3 种支付 × 5 个调用点 = 15 处重复组装；每新增一种支付，5 个调用点都要加分支。
- **用工厂**：组装代码集中在工厂一处，调用点只写"创建并调用"。**15 处重复 → 1 处**；新增支付 = 1 处改动。

这个"从分散到集中"的对比，是创建型模式（第 6 章）最朴素的价值证明：**把"怎么创建"收拢到一处，让"用"和"造"解耦**。工厂方法解决的是"创建逻辑随产品种类扩散"的问题——当创建逻辑简单、产品种类固定时，用最直接的方式即可，不必套工厂。

## 6 单例与工厂方法的关系

把这两个模式放在一起看，它们常被同时误用，也常被正确地搭配使用：

**误用**：单例 + 工厂 = 一个"全局支付工厂"，到处 `PayFactory.getInstance().createPay(...)`。测试时无法替换，隐式依赖遍地——这是"反模式"（第 12 章）里"单例泛滥"的典型形态。

**正确搭配**：单例只用于"确实全局唯一"的对象（日志器、配置管理器、数据库连接池）；工厂负责"创建产品"，**它的唯一性不该靠单例强加，而该靠注入**——需要单例工厂时，在应用入口创建一次，通过依赖注入传给使用方，而不是让使用方自己 `getInstance()`。<span class="marginnote">这条"<strong>入口创建、依赖注入</strong>"的纪律，是第 4 章"依赖倒置"与第 8 章"可测性"的交叉点：当对象能通过构造函数传入而非自己拉取时，测试就能注入 mock，系统就<strong>从"静态绑定"变成"可替换"</strong>。单例的"全局唯一"没有错，错的是"全局可被任意处访问"。</span>

**辨析｜易错点：** 判断一个单例是否健康，问一句：**"测试时我能替换它吗？"** 能——它只是"全局唯一"的实现；不能——它成了"隐藏的全局状态"，测试、并行、重用都会被它绊倒。**单例的价值在唯一，风险在隐式——把"隐式"变"显式"（注入），就是健康单例的全部秘密。**

## 7 术语速查表

| 术语 | 一句话定义 | 关键要点 |
| --- | --- | --- |
| 单例 | 全局唯一实例 | 唯一性靠"私构造+静态实例" |
| 工厂方法 | 子类工厂各建一种产品 | 用继承消除分支 |
| 简单工厂 | 一个工厂用分支建产品 | 用 if/switch，非 GoF 模式 |
| 隐式全局依赖 | 到处 getInstance() | 单例被滥用的症状 |
| 依赖注入 | 通过构造/参数传入依赖 | 让单例变可测 |

**辨析｜易错点：** 单例还有一个并发层面的坑——**多线程下的懒加载竞态**。经典的"先判空再创建"在并发下可能创建两个实例。对策有：尽早初始化（类加载时就建好）、用双重检查锁定、或干脆用语言内置的单例语义（如模块级单例）。**单例的"唯一性"在单线程下是平凡的，在并发下需要刻意保证**——这是把它误当"随手可用的便利设施"时最容易被咬的地方。

## 8 小结

- **创建型模式**的核心：把"创建"与"使用"分离，让对象创建不绑定具体类。
- **单例**保证全局唯一实例：私有构造 + 静态访问；注意线程安全与测试成本。
- 单例的语义（一个实例）可交给 DI 容器，不必手写 `getInstance()`。
- **工厂方法**让子类决定实例化哪个类，靠多态落实 OCP。
- 工厂方法 ≠ 静态工厂；判断标准是有没有"创建者子类在替换创建逻辑"。
- 单例管"实例数"，工厂管"造哪个类"，两问题正交、常组合使用。

- 单例的健康判据："测试时能否替换它"——能则只是唯一实现，不能则是隐藏全局状态。
- 单例与工厂的正确搭配：入口创建一次 + 依赖注入，而不是到处 getInstance()。
- 工厂方法用继承消除分支，简单工厂用 if——分清楚，别混着叫。
- 支付系统的例子：工厂让"新增渠道"从改 N 个调用点变为 1 处，组装逻辑收拢。
- 单例并发注意：懒加载竞态要用尽早初始化/双重检查锁定/语言内置单例来防。
- 工厂方法的价值验证：创建逻辑从"散布 N 处"收拢为"集中 1 处"，用与造解耦。
- 一句话记忆：单例管"唯一"，工厂管"怎么造"——各司其职，别互相绑架。
