## 为什么从配置管理开始

软件项目里"改动"是常态：代码在改、文档在改、配置在改、需求在改。**软件配置管理（SCM, Software Configuration Management）**回答一个关键问题：**面对持续的变化，如何保证"当前状态是什么、谁改的、怎么回到正确状态"是可控的？** 它是版本控制的工程框架——版本控制是工具，SCM 是管理这些工具与流程的纪律。

## 1 配置管理的对象：配置项

**配置项（Configuration Item, CI）**：软件过程中**需要受控管理**的对象——代码、文档、数据、配置、构建脚本、工具链。

不是所有文件都是配置项：**只有"可能变化、且变化需要被跟踪"的资产才值得纳入 SCM**。临时文件、生成物（如编译产物）一般不纳入管理（或作为可再生成物）。

**辨析｜易错点：** 配置项 ≠ 只有源代码。**需求文档、设计文档、测试用例、配置文件、部署脚本、第三方依赖锁定**都是配置项——它们与代码一同演化、一同需要版本控制。"只管理代码、不管理文档与配置"是 SCM 最常见的缺口：代码回了版本，环境配置散落各处，一样无法复现。

## 2 基线：受控的里程碑

**基线（baseline）**：一组配置项在**特定时间点**的**正式受控状态**——基线之后的变更必须走正式变更控制流程。

一个项目有多个基线，随阶段推进：

- **需求基线**：SRS 经评审后冻结，之后的需求变更须走变更流程。
- **设计基线**：架构与详细设计文档受控，作为编码的依据。
- **代码基线**：里程碑版本的代码冻结（如某个 release 分支），改动需评审。
- **发布基线**：交付给用户的正式版本，进入维护与变更管理。

**辨析｜易错点：** 基线 ≠ 快照。快照只是"某个时刻的备份"，**基线是"经过评审、被正式接受、之后变更必须受控"的里程碑**。基线的意义在于**把"变化的世界"锚定成"可回溯的节点"**——基线上出问题，能精确知道"从哪个版本开始变坏了"；基线前的随意改动不用追责，基线后的改动必须有记录（呼应第 3 章需求基线、第 9 章变更管理）。<span class="marginnote">基线是"变更控制"的前提：没有基线，就没有"变更"的参照物——任何改动都算"正常进行"，无法判断"是不是不该改"。有了基线，"从这个基线开始，改任何配置项都要走变更流程、要记录、要评审"。第 3 章的需求基线、第 12 章的代码基线，都是同一套"受控演化"机制在不同产物上的落地。</span>

## 3 SCM 的五项任务

Pressman 给出 SCM 的核心任务：

**配置标识（identification）**：定义哪些是配置项、如何命名、如何组织。
**版本控制（version control）**：管理配置项的多个版本，支持回溯、分支、合并（下一节）。
**变更控制（change control）**：对基线后的变更做评估、批准、实施、验证（对应第 3 章变更管理）。
**配置审计（configuration audit）**：检查"实际的配置项"与"记录的配置项"是否一致——防止"以为改了、实际没改"或"改了没记录"。
**状态报告（status reporting）**：记录并报告每个配置项的当前状态——"哪个版本在测试、哪个在发布"。

**辨析｜易错点：** SCM 最容易被忽略的是**配置审计**——团队天天提交代码（版本控制做得好），却从不审计"构建出的东西到底包含哪些配置项、是否与记录一致"。**"能复现"是 SCM 的终极目标**：任意时刻，团队都应能从配置项恢复到当时的可构建状态。判断标准：**"上周三线上那个版本"能不能从仓库精确重建？** 不能，SCM 就有缺口。

## 4 SCM 在现代工程的位置

现代工程里 SCM 的形态：

**版本控制**：Git 等（第 12 章《版本控制模型》）。
**制品管理**：构建产物、依赖的版本化存储（Maven Central、npm、容器镜像仓库）。
**CI/CD 集成**：每次提交的构建、测试、部署都由 SCM 驱动的流水线完成（第 13 章）。
**环境管理**：配置、密钥、基础设施的版本化（第 13 章 IaC）。

<span class="marginnote">SCM 的思想在云原生时代全面扩张：<strong>不仅代码要版本化，基础设施、配置、数据模型、模型权重都要版本化</strong>——"Everything as Code"（第 13 章 IaC）的本质，就是把 SCM 的"受控管理"扩展到软件系统的一切资产。今天的"配置管理"早已超出源代码的范畴，成为"可复现、可审计、可回滚"的工程根基。学 SCM，学的是一套"应对变化"的普遍方法，工具只是载体。</span>

## 5 数值算例：一次"复现"事故的 SCM 账

SCM 的价值在出问题时最直观。假设线上出了个只在特定配置下出现的 bug，团队需要重建"上周三线上那个版本"：

| SCM 做得好的团队 | SCM 有缺口的团队 |
| --- | --- |
| 仓库有 release 标签 + 构建产物归档，一条命令重建 | 代码能回滚，但配置文件散落在个人电脑里 |
| 依赖版本已锁定（lock 文件），构建可复现 | 依赖漂移，昨天还编译过的今天编不过 |
| 配置审计确认"记录与实际一致" | 事后核对才发现少改了一个配置文件 |
| 结论：2 小时定位根因 | 结论：花 2 天"考古"重建环境，bug 仍定位不清 |

**"能复现"不是一句口号，而是 SCM 五件事合力的结果**：标识（知道哪些是配置项）、版本控制（能取回旧版本）、变更控制（知道谁改了什么）、审计（确认记录与实际一致）、状态报告（知道当前各版本状态）。缺任何一件，复现链条就断。这正是为什么成熟的 SCM 实践把"依赖锁定、构建可复现、制品归档"看得和代码版本化同等重要。

**辨析｜易错点：** 很多团队把 SCM 等同于"用 Git"，以为代码入了 Git 就万事大吉。**Git 只覆盖了"版本控制"这一件事**——配置、依赖、构建环境、部署脚本的管理，都需要在 Git 之外补上（锁文件、IaC、制品库）。判断标准：**"clone 仓库 → 一条命令构建 → 得到完全一致的运行版本"能不能成立？** 不能，SCM 就有缺口。

## 6 核心对比表：SCM 五项任务

| 任务 | 回答的问题 | 主要手段 | 失败后果 |
| --- | --- | --- | --- |
| 配置标识 | 哪些资产要管、怎么命名组织 | 配置项清单、命名规范 | 有文件没被纳入管理，改动失控 |
| 版本控制 | 历史怎么记录、怎么回溯 | Git、SVN（下一节） | 无法回溯，改错了回不去 |
| 变更控制 | 基线后的改动受不受控 | CCB、变更流程 | 随意改动，版本混乱 |
| 配置审计 | 记录与实际一致吗 | 构建核对、审查 | "以为改了"实际没改，线上出错 |
| 状态报告 | 现在各版本处于什么状态 | 状态表、仪表盘 | 不知哪个版本在测、哪个在发布 |

## 7 常见误区速查表

| 误区 | 正解 |
| --- | --- |
| "SCM = 用 Git" | Git 只覆盖版本控制一项；配置、依赖、构建环境都要 SCM 管理 |
| "配置项只有源代码" | 文档、配置、测试、部署脚本都是配置项，须一并受控 |
| "基线 = 快照" | 快照只是备份；基线是"经评审、之后变更必须受控"的里程碑 |
| "版本控制 = 备份" | 备份复制文件；版本控制记录变更历史，能回答"为什么变成这样" |
| "SCM 是开发后期的事" | SCM 从需求阶段就启动，贯穿全生命周期 |
| "能复现只是口号" | "clone → 构建 → 得到一致版本"是可验证的工程标准 |
| "配置审计可有可无" | 不做审计，"以为改了实际没改"的线上事故就防不住 |
| "Everything as Code 与 SCM 无关" | IaC 正是把 SCM 的受控管理扩展到基础设施与配置 |

## 8 数值算例：基线是如何"冻结"范围的

用网上书店项目演示基线的建立与作用。假设需求评审通过，SRS 形成**需求基线**：

| 阶段 | 是否受基线控制 | 变更成本 | 场景 |
| --- | --- | --- | --- |
| 基线前 | 否（随意调整） | 低 | 需求还在打磨，改需求不用走流程 |
| 基线后 | 是（必须走变更控制） | 中 | 评审通过后，改"支持支付宝"要 CR + CCB 审批 |
| 发布基线后 | 是（受严格变更控制） | 高 | 线上版本冻结，改动走补丁流程 |

**基线的意义在于"冻结"不是"禁止"**：基线前需求可以自由演化（此时改动便宜），基线后改动必须受控（此时改动有代价、有记录）。团队因此**在最便宜的时候完成需求打磨，在最贵的阶段守住稳定性**——这正是配置管理与第 3 章需求管理共用的"受控演化"逻辑。

**辨析｜易错点：** 基线不是越早立越好。**立得太早**，需求还没打磨完就被冻结，团队被流程困住；**立得太晚**，范围失控无人约束。判断标准：**这条基线对应的产物是否已通过评审、可以被稳定引用？** 是，才值得立基线。

## 9 小结

- **SCM** 管理软件过程中所有可能变化的资产，让"当前是什么、谁改的、如何恢复"可控。
- **配置项**包括代码、文档、配置、测试、部署脚本等——不止源代码。
- **基线**是经评审、受正式控制的里程碑，基线后变更必须走变更流程。
- 基线 ≠ 快照：快照是备份，基线是"受控起点"。
- SCM 五项任务：**标识、版本控制、变更控制、审计、状态报告**。
- **能复现**是 SCM 的终极目标；现代 SCM 已扩展到"Everything as Code"。
