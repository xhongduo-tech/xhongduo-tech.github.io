## 为什么从 SRS 开始

需求工程前几步的产出——访谈记录、用例、模型——是"素材"。而**软件需求规格说明（Software Requirements Specification, SRS）**把素材凝结成一份**正式的、可评审的、可签署的文档**。它是设计、编码、测试的共同基准，也是客户与开发者之间关于"到底做什么"的契约。这一节讲清楚：SRS 该包含什么、怎么写才合格、常见陷阱在哪。

## 1 SRS 的读者与用途

一份 SRS 有**五类读者**，各取所需：

- **客户与用户**：核对系统是否满足诉求。
- **项目经理**：据此规划范围、估算工作量。
- **设计人员**：据此做体系结构与模块设计。
- **测试人员**：据此编写验收测试用例。
- **维护人员**：日后修改功能时回到 SRS 查"原意"。

五类读者要求 SRS 必须是**分层的**：高层面向业务（背景、范围、目标），中层面向设计（功能需求、性能指标），底层面向测试（每个需求可验证）。<span class="marginnote">SRS 的"分层"与文档的可追溯性直接相关：业务层的一句话，要能下钻到系统层的具体需求，再下钻到测试用例。没有分层，SRS 就是一坨无法追查的平铺文本。</span>

## 2 SRS 的典型结构

IEEE 830 与 Pressman 给出的 SRS 骨架高度一致，核心章节如下：

1. **引言**：目的、范围、定义、缩写、参考资料。
2. **总体描述**：产品视角、用户特征、运行环境、约束与假设。
3. **具体需求**：功能性需求、外部接口需求、性能需求、质量属性（可用性、安全、可维护性）、设计约束。
4. **附录**：分析模型、数据字典、待定问题清单。

其中第 3 章是心脏，功能性需求通常按"用例/功能模块"组织，每个需求给出唯一编号（如 `FR-001`）以支持追踪。<span class="marginnote">需求编号是“需求管理”的锚点：没有编号，变更管理、追踪矩阵、测试映射全部无从谈起。`FR` 前缀标识功能性需求，`NFR` 标识非功能性需求，是业界常见约定。</span>

## 3 好 SRS 的七个特征

Pressman 沿用 IEEE 的定义，给出 SRS 的**七个质量特征**，这也是评审 SRS 的检查单：

| 特征 | 含义 | 反例 → 正例 |
| --- | --- | --- |
| 正确 | 如实反映需求 | 「系统应快」→「查询 ≤ 1s」 |
| 无歧义 | 唯一解释 | 「大约」「等」禁用 |
| 完整 | 无遗漏需求 | 缺异常处理 |
| 一致 | 内部不矛盾 | 两处性能指标冲突 |
| 可验证 | 可测 | 「界面友好」不可测 |
| 可追踪 | 能溯源 | 无来源、无编号 |
| 可修改 | 变更成本低 | 需求平铺一团 |

**辨析｜易错点：** 初学者最爱犯的是"把 SRS 写成设计说明书"——在 SRS 里规定"用 Redis 缓存""采用微服务拆分"。SRS 应描述**做什么（what）**，把**怎么做（how）**留给设计文档。需求里一旦混入技术方案，客户与开发者都会误以为需求是技术决策，后续调整必然扯皮。判断标准：**删掉这句技术描述，用户需求还成立吗？成立就说明它不属于 SRS。**

## 4 编写的工程实践

写 SRS 有六条工程实践可循：

1. **以分析模型为输入**：用例、类图、状态图、DFD 都已就绪，SRS 的"具体需求"章节照此组织，不凭空造。
2. **先写高层再细化**：先完成引言与总体描述，再逐章细化，避免细节先入。
3. **模板化**：用团队统一的 SRS 模板，缺的章节一目了然。
4. **持续维护**：SRS 不是一次交付就完事，需求变更后要同步更新并重新评审。
5. **可追踪矩阵**：建立「业务需求 ↔ 系统需求 ↔ 用例 ↔ 测试」的映射表。
6. **与原型结合**：复杂界面需求配原型图，文字+图像比纯文字准确得多。<span class="marginnote">第 2 章讲的原型模型在这里闭环：原型是 SRS 的"可视化附录"。把原型截图放进 SRS，用户确认的是"看得见的东西"，比抽象文字可靠得多——这也正是"无歧义"最难达成的界面需求领域的破局点。</span>

## 5 SRS 与敏捷的张力

传统项目把 SRS 当作交付物；敏捷项目则常宣称"不需要 SRS"。这里的真相是：

- 敏捷**不写厚重的、一次性的 SRS**，但把需求拆成**用户故事 + 验收标准（acceptance criteria）**，写在 Backlog 里，每迭代更新。
- 复杂领域（合规、航空、金融）仍然需要正式 SRS，作为监管与审计的凭证。

**辨析｜易错点：** "敏捷 = 不要文档"是最危险的误读。敏捷反对的是**过重的、不随代码演化的文档**，不反对"记录需求"。敏捷团队用验收标准替代 SRS 正文，本质是把 SRS 的"可验证"特征贯彻到每个故事——两者的差距在形式，不在精神。

## 6 一个 SRS 片段示例：好坏对照

看一个具体需求条目在"好 SRS"与"坏 SRS"下的写法，胜过十段抽象论述。以"图书检索"功能为例：

**坏写法**：「系统应提供快速、友好的图书检索功能。」——「快速」「友好」无法验证，测试人员无法据此写用例，设计人员不知道性能指标。

**好写法**：

- **FR-101 图书检索**：读者输入书名、作者或 ISBN 中的任意一项，系统应返回匹配的馆藏列表。
- **FR-102 检索性能**：对馆藏规模 ≤ 100 万条的数据，检索响应时间应 ≤ 1 秒（P95），且支持同时 100 个并发检索请求。
- **FR-103 检索排序**：默认按相关度排序；无匹配时返回空列表并提示"未找到"。

这三条各有编号、可验证（FR-102 可写成性能测试）、无歧义（"≤ 1 秒"而非"快速"）。**同一个功能，坏写法一句话，好写法三条可测的需求**——SRS 的质量差异，本质上就是"可验证"特征的落实程度差异。

**辨析｜易错点：** 好写法的代价是"看起来更啰嗦"——但这正是 SRS 的职责：它不追求文学性，追求**可判定的契约**。每一条需求都应该能回答"我怎么证明你做到了"；回答不出的需求，要么重写，要么根本不该写进 SRS。

## 7 核心对比表：SRS 与用户故事

| 维度 | 正式 SRS | 用户故事 + 验收标准 |
| --- | --- | --- |
| 载体 | 正式文档（可签署、可评审） | Backlog 条目 |
| 粒度 | 系统级、完整、编号 | 故事级、短期、迭代内可完成 |
| 生命周期 | 里程碑式评审、基线化 | 持续演化、每迭代重排 |
| 变更成本 | 需走变更流程 | 重新排优先级即可 |
| 适合场景 | 合规、外包、监管、复杂领域 | 敏捷迭代、产品快速演进 |
| 共同内核 | 都要"可验证"——都要回答"如何证明做到" | 同左 |

**辨析｜易错点：** 别把"敏捷用故事"理解成"敏捷不需要规格"。**故事的验收标准（acceptance criteria）就是迷你版 SRS**——它把"可验证"下沉到每个故事。一个没有验收标准的用户故事，与一句"系统应友好"的坏需求并无二致。形式可以轻，可验证性不能丢。

## 8 常见误区速查表

| 误区 | 正解 |
| --- | --- |
| "SRS = 设计说明书" | SRS 写做什么，怎么做属于设计文档，混入技术方案会扯皮 |
| "SRS 是写一次就完事" | SRS 要随需求变更持续维护并重新评审 |
| "'快速'也算需求" | 无法验证的需求等于没写，要量化成可测指标 |
| "敏捷不需要 SRS" | 敏捷用故事 + 验收标准承载同等精神，反对重文档非记录 |
| "SRS 越厚越好" | SRS 追求可判定的契约，不追求文学性，按需分层 |
| "需求编号没必要" | 编号是需求管理锚点，变更、追踪、测试映射都靠它 |
| "SRS 是客户的事" | SRS 服务五类读者（客户/管理/设计/测试/维护） |
| "验收标准可写实现细节" | 验收标准写可观察结果，用户/测试者能独立验证 |

## 9 小结

- **SRS** 是需求工程的正式产出，服务客户、管理、设计、测试、维护五类读者。
- 典型结构：引言 → 总体描述 → 具体需求 → 附录；功能需求按模块组织并编号。
- 好 SRS 具备**七个特征**：正确、无歧义、完整、一致、可验证、可追踪、可修改。
- SRS 只写**做什么**，不写**怎么做**——技术方案属于设计文档。
- 以分析模型为输入、用模板、配原型、维护追踪矩阵，是编写的核心实践。
- 敏捷用**故事 + 验收标准**承载同等精神，反对的是重文档而非记录需求。
