## 为什么从代码评审开始

第 11 章讲了正式技术评审（FTR）——代码评审是 FTR 在代码上的具体化，也是现代工程里**最日常、最频繁**的质量活动。它不是"挑刺"，而是一套有明确价值主张的协作机制。这一节讲代码评审的**价值**（为什么值得做）与**正式流程**（怎么做才有效）。

## 1 代码评审的价值：不止是找 bug

代码评审的回报远超"找出缺陷"：

- **缺陷发现**：研究发现，代码评审能发现 60%–90% 的常见缺陷——尤其是设计、逻辑与可读性问题（自动化测试测不到的类型）。
- **知识传播**：评审是**团队学习的最高频场景**——新人学规范、老手分享技巧、全员熟悉代码。
- **规范执行**：编码规范、架构约束在评审中落地——比文档更有执行力。
- **质量文化**：写的人知道"会被看"，自然更认真；看的人建立"共同标准"。
- **冗余保险**：关键代码至少两人熟悉，降低"单点知识"风险（呼应风险管理）。

**辨析｜易错点：** 代码评审 ≠ "找 bug 的比赛"。把评审做成"抓错误大会"会让人抵触，反而降低质量。**评审的价值大头在"知识传播与标准共识"**——发现缺陷只是副产品。判断标准：**评审是否让团队越来越一致、越来越会协作？** 只有"抓错"的评审，长期看是负资产。

## 2 正式评审流程：从提交到合并

现代代码评审（PR 评审）的标准流程：

1. **提交 PR**：开发者完成功能，提交 Pull Request（含描述、测试、关联需求）。
2. **CI 自动检查**：构建、测试、静态分析自动跑（第 13 章 CI）——机器先筛低级问题。
3. **评审者审查**：1–3 位评审者阅读代码，发表评论（问题、建议、疑问）。
4. **对话与修改**：作者回应评论、修改代码、补充测试——评审是"对话"不是"判决"。
5. **批准与合并**：评审者批准，PR 合并入主干（第 12 章分支保护）。
6. **善后**：评审中发现的问题跟踪关闭（不留悬空问题）。

**辨析｜易错点：** 评审最常被跳过或走形式的是"**只看 diff 不回上下文**"——评审者对着代码逐行看，却不知道"这段代码为什么存在、要满足什么需求"。**好的评审要"带上下文"看**：先读 PR 描述与需求，再看实现是否符合意图，最后才看细节。判断标准：**评审意见是"这里不符合规范"（表层）还是"这里没满足需求/有设计问题"（深层）？** 只有表层意见的评审，价值有限。

## 3 评审的粒度与范围

评审多大才合适？核心原则是**"PR 要小"**：

- **小 PR（200–400 行以内）**：评审者能完整理解，意见质量高，合并快。
- **大 PR（上千行）**：评审者抓不住重点，意见泛泛，拖延——最终"盲批"。
- **独立功能一个 PR**：一个 PR 只做一件事（功能、修复、重构分开），评审目标清晰。

**辨析｜易错点：** "PR 小"不是天生的，是**设计出来的**——**功能拆小、重构与功能分开、连续小步提交**。一个上千行的 PR 往往意味着"憋了太久没提交"（违背第 13 章 CI 的频繁提交）。判断标准：**评审者能在合理时间（如 30 分钟内）完整理解这个 PR 吗？** 不能，PR 就该拆。<span class="marginnote">小 PR 与第 8 章"小步"、第 9 章"熟悉度守恒"、第 12 章"分支短小"是同一原则的不同切面——<strong>软件工程里"小步"几乎是万能的解药</strong>：小变更易评审、易测试、易回滚、易定位问题。把大工作拆成小步，是资深工程师最核心的习惯之一。</span>

## 4 评审文化与心理安全

评审要有效，文化比流程更重要：

**对事不对人**：评论的是"代码"，不是"写代码的人"——用"这段逻辑"不用"你写错了"。
**无责备氛围**：评审是"共同让代码更好"，不是"找出谁的问题"。
**作者不辩解**：收到意见先理解意图，再决定采纳或解释——评审不是答辩会。
**评审者不强势**：多数意见是"建议"而非"命令"，作者有权解释为什么这样写。

**辨析｜易错点：** 评审文化的两大杀手是"**居高临下的评论**"（让作者防御）与"**畏惧权威不敢评论**"（让评审失效）。判断标准：**团队里新人敢不敢在评审中提出"这个设计可能有问题"？** 不敢，评审文化就出了问题。<span class="marginnote">心理学在评审中的体现：<strong>建设性反馈的"三明治"结构</strong>（先肯定 → 再提问题 → 再鼓励）远胜于"直接批评"；"我有个疑问，这段逻辑…"比"你这里错了"更容易被接受。评审的语言艺术不是客套，而是<strong>让反馈能真正被接收</strong>——反馈没被接收，评审就是零。这与第 13 章"无责备的事故复盘"是同一套心理安全文化。</span>

## 5 实战：一次代码评审的完整流程

把评审的价值落到实处，看一次"好的评审"长什么样。假设开发者提交了一个"订单取消"功能的改动：

**评审前**：作者自测 + 提供简短说明（改了什么、为什么、测了什么）。**评审前先把背景写清楚，评审就成功了一半**——评审者最怕的是面对一大坨没有说明的 diff。

**评审中**：评审者按顺序读——先看整体设计意图（这个改动解决什么问题、结构是否合理），再看关键逻辑（边界、异常、并发），最后看命名与风格。发现的每个问题都**区分严重级**：必须改（逻辑错误、安全漏洞）、建议改（可维护性）、可忽略（风格偏好）。**评审的价值密度在"必须改"这一档**，用 80% 精力盯逻辑错误，而不是在缩进上纠缠。

**评审后**：作者回应每条意见——改、不改、或解释为什么不改。**"驳回"是允许的**：评审意见是建议不是命令，作者有最终解释权，但必须给出理由。达成一致后合并，测试与 CI 把关。

**辨析｜易错点：** 评审最大的敌人是"走过场"——点赞式通过、无人深究。对策是把评审当成**作者与评审者的共同责任**：作者有义务把 diff 拆小、写好说明；评审者有义务真读。另一个坑是"评审现场开会改代码"——评审只讨论、不修改，改动留在会后由作者完成并重新提交，否则评审会退化成"集体验代码"。**评审是设计讨论，不是代码编辑现场。**

## 6 一份可复用的评审清单

把经验沉淀成清单，新人也能照着执行：

| 检查项 | 追问 |
| --- | --- |
| 逻辑正确 | 边界条件、异常路径、并发是否考虑 |
| 安全问题 | 输入校验、权限、敏感信息泄露 |
| 可维护性 | 命名清楚、函数小、无重复逻辑 |
| 测试覆盖 | 新逻辑有没有对应测试、边界测没测 |
| 架构一致 | 是否违背已有模式、是否加不必要的抽象 |

这张清单配合第 14 章的代码坏味道与静态分析工具使用，评审就从"看感觉"变成"照单抓问题"。**把"评审该看什么"写下来，是让评审从个人经验变成团队能力的关键一步。**

**辨析｜易错点：** 评审还有一个常被低估的价值——**知识共享**。评审让每个成员读到别人的代码、理解系统的各个角落，团队对代码的"共同所有权"由此建立：没人会因某段代码只有一个人懂而成为瓶颈（第 12 章"英雄主义依赖"反模式）。所以评审频率要高、diff 要小、参与要广——**把评审当学习机制，而不是审核关卡**，它就不只是一个质量工具，还是团队成长工具。

**与轻量评审的衔接：** 第 14 章"结对编程与轻量级代码审查"是正式评审的日常化变体——结对时每时每刻都在"实时评审"，pull request 审查则是"异步评审"。两者的关系是：**日常小步用轻量审查，里程碑大改动用正式评审**，覆盖不同粒度，共同守护代码质量。

## 7 小结

- 代码评审的价值：**找缺陷、传知识、立规范、建文化、降单点风险**。
- 评审 ≠ 找 bug 比赛——知识传播与标准共识是更大头。
- 正式流程：**提交 PR → CI 自动检查 → 评审对话 → 修改 → 批准合并 → 跟踪关闭**。
- 评审要**带上下文**看（先需求后实现），不只挑表层问题。
- **PR 要小**：小步易评审、易测试、易回滚——"小步"是工程万能的解药。
- 评审文化：**对事不对人、无责备、不辩解、不强势**——心理安全决定评审是否有效。

- 评审流程三阶段：评审前写清背景、评审中分级给意见、评审后逐条回应。
- 意见分三档（必须改/建议改/可忽略），80% 精力盯逻辑错误而非风格。
- 评审是设计讨论不是编辑现场；作者有权驳回，但必须给理由。
- 评审的隐性价值是知识共享：小 diff、高频次、广参与，共同所有权由此建立。
- 评审清单沉淀团队经验：把"该看什么"写下来，评审就从感觉变成清单。
- 评审与轻量审查衔接：日常小步用轻量，里程碑大改用正式，覆盖不同粒度。
- 评审三问定位：这个改动解决什么问题、结构是否合理、关键逻辑边界是否安全。
- 评审失败的两大征兆：点赞式通过（走过场）与现场改代码（退化集训码）。
- 评审意见可以驳回，但必须给理由——作者有解释权，讨论要收敛。
- 评审是"设计讨论"不是"代码编辑现场"：改动由作者会后完成并重新提交。
- 评审价值三合一：找缺陷、传知识、建共同所有权——不只质量，更是团队机制。
- 配套清单（第 14 章坏味道 + 静态分析工具）让评审照单抓问题而非凭感觉。
- 评审的产出是"意见与决策记录"：合并前意见都收敛，不留悬而未决的问题。
