# 构建管理与发布管理

## 为什么从构建与发布开始

SCM 管理了"源代码的版本"，但用户用不到源码——他们用**构建产物（artifact）**。**构建管理**把源码变成可运行的制品，**发布管理**把制品部署到生产环境。这一节讲构建的可靠性、制品的版本化、以及"可复现发布"这一工程目标。

## 1 构建管理：从源码到制品

**构建（build）**：把源代码**编译、打包**成可部署的制品（二进制、镜像、安装包）的过程。

现代构建管理的核心要求：

- **可重复构建（reproducible build）**：同一源码 + 同一环境 → 同一制品。这是"可复现"原则在构建层的落地。
- **依赖锁定**：锁定第三方依赖的精确版本（如 **package-lock.json**、**requirements.txt** 锁定版本），防止"昨天能构建、今天不能"。
- **构建脚本版本化**：构建过程本身（**构建脚本、Dockerfile**、CI 配置）也进版本控制——构建不能是"某台机器上的手动操作"。
- **构建产物版本化**：制品有唯一版本标识（如 **镜像 tag、Git 提交 SHA**），与源码提交关联。

**辨析｜易错点：** 构建的经典反模式是"**在我机器上能跑**"——构建只在某台开发者机器上成功，换台机器就失败。根源通常是**依赖不锁定、环境不统一、构建过程不脚本化**。判断标准：**新人拉代码能不能一条命令构建成功？** 不能，构建管理就有缺口。<span class="marginnote">"可重复构建"的深层意义是"<strong>可追溯</strong>"：每个制品都能说清"由哪次提交、哪个依赖版本、哪套构建脚本产生"。这让我们能回答发布管理最关键的三个问题——"线上跑的是什么版本""这个版本包含哪些代码""出问题时该回滚到哪"。可重复构建，是"可回滚"的前提，也是第 13 章 IaC 的基础。</span>

## 2 制品管理：构建产物的版本化仓库

**制品管理（artifact management）**把构建产物存进**版本化的制品仓库**：

**制品仓库**：Maven Central、npm registry、Docker Registry（镜像仓库）、PyPI 等——不只存，还管版本、元数据、权限。
**不可变制品（immutable artifact）**：制品**发布后不可修改**——要改就出新版本。这是制品管理的第一原则。
**制品与源码关联**：每个制品记录它对应的源码提交（build metadata），保证可追溯。

**辨析｜易错点：** "制品不可变"是最常被违反的纪律——有人直接改线上制品的文件、有人覆盖旧版本号。**一旦制品可被改写，"线上跑的是什么"就永远说不清了**——你回滚到 1.0.0，但 1.0.0 已被悄悄改过。判断标准：**制品仓库里的每个版本号，是否永远指向同一份内容？** 不是，就是制品管理失守。

## 3 发布管理：从制品到生产

**发布（release）**：把验证过的制品部署到目标环境的过程。发布管理的核心：

**发布流水线**：制品经过**测试环境 → 预发环境 → 生产环境**的逐级验证（第 13 章 CD 流水线）。
**发布策略**：蓝绿部署、金丝雀发布、滚动更新——降低发布风险（第 5 章高可用与第 13 章 CD）。
**版本语义化（SemVer）**：**MAJOR.MINOR.PATCH**——主版本破坏性变更、次版本向后兼容的新功能、补丁是向后兼容的修复。
**回滚预案**：每个发布都有"出问题怎么办"——回滚到上一制品或修复发布。

**辨析｜易错点：** 发布管理最容易混淆的是**"部署（deployment）"与"发布（release）"**——**部署是"把制品装上"，发布是"让用户使用"**。现代实践用**功能开关（feature flag）**把两者解耦：代码先部署到位，但功能默认关闭，逐步灰度放量——**"部署了但没发布"让发布风险变得可控**。<span class="marginnote">发布管理是"配置管理 + 测试 + 部署"三者的汇合点：<strong>版本控制保证"代码可追溯"，测试保证"制品可信任"，部署策略保证"上线可控制"</strong>。一个健康的发布流程，让"上线"从"心惊胆战的大动作"变成"频繁的小步快跑"——这正是第 13 章持续交付的目标。发布管理不是发布当天的临时工作，而是从"提交"就开始设计的持续能力。</span>

## 4 小结

- **构建**把源码变成制品，核心要求是**可重复构建**：同一源码+环境→同一制品。
- 构建反模式是"在我机器上能跑"：**依赖锁定、脚本版本化、环境统一**是解药。
- **制品管理**把产物存进版本化仓库，第一原则是**制品不可变**。
- 制品要记录对应的**源码提交**，保证可追溯、可回滚。
- **发布**是制品经测试→预发→生产的逐级验证，配套蓝绿/金丝雀等发布策略。
- **部署 ≠ 发布**：功能开关解耦两者，让发布风险可控。
