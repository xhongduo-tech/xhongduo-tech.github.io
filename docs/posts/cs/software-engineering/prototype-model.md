# 原型模型（快速原型与演化式原型）

## 为什么从原型模型开始

前两节的瀑布与增量模型有一个共同前提：**需求至少大体上说得清**。瀑布要求需求一次冻结，增量要求能切出第一批发什么。但软件工程里最麻烦的场景恰恰是：**客户自己也说不清要什么**。他只能说「我要一个像微信的东西」「我要一个更聪明的助手」——抽象、含糊、充满矛盾。

这一节的主角**原型模型（prototyping model）**就是为了需求模糊而生的。它的核心思想朴素到近乎直觉：**与其花几个月写一份没人能看懂的需求文档，不如花几天做一个能看的、能点的、能用的雏形，让客户「看见」需求长什么样**。<span class="marginnote">注意这里发生了一次认知范式的转换：瀑布假设「需求可以被预先完整描述」，原型则认为「需求只能在交互中被逐步发现」。这不是技术差异，而是对「需求到底从哪来」的根本分歧——这一分歧正是后面敏捷宣言的哲学基础。</span>

原型模型内部又分两种走向：用完就扔的**快速原型**，和不断长大的**演化式原型**。理解二者的区别，是这一节的关键。

## 1 需求模糊的困境：为什么文档解决不了

当需求模糊时，用传统方式「把需求写清楚」为什么注定失败？因为在需求不明的前提下，**文档只是把模糊翻译成了看似精确的文字**。客户读需求文档时点头，不是因为理解了，而是因为**抽象的条文无法触发他脑中的具体画面**。

一个经典场景：客户说「报表要『友好』」，开发写下「报表须友好显示」。这个条目在文档评审会上毫无争议地通过，直到第一版界面出来，客户才发现「友好」指的是「一屏放下、带图表、可导出」，而开发理解的是「字体大一点」。**歧义在文档阶段不可见，只在可交互的实物面前显形**。

**核心要点：** 原型模型的根本主张是——**需求不是被「写」出来的，而是被「看」出来的**。任何抽象描述都存在解释空间，只有把界面、流程、交互做成一个看得见摸得着的东西，双方才站在同一事实基础上讨论。这与第一级数学里「数形结合」的直觉完全一致：抽象的式子（需求文档）配上具体的图形（原型），理解才可能对齐。<span class="marginnote">「形」在这里就是原型。对一个定义不明的对象，数学家用反例与构造，软件工程师用原型——本质上都是在给抽象一个可检验的具体实例，让模糊无处藏身。</span>

## 2 原型过程：快速造一个「看得见的需求」

Pressman 把原型过程组织成一轮**小型的迭代回路**，它复用框架活动的骨架，但每个活动都被「快」字支配：

1. **沟通**：与客户初步沟通，收集对系统的整体印象与主要功能清单——注意这里不追求完整，只求抓主干。
2. **快速策划**：制定一个极简计划，明确「这次原型做哪几个界面、走通哪几条流程」。
3. **建模（快速设计）**：只做**够用即可**的设计——关注用户可见的界面、交互与数据流，暂不关心内部架构、性能、安全性。
4. **构建原型**：用尽量低的成本快速实现上述可见部分。
5. **部署与反馈**：把原型交给客户试用，收集意见；根据反馈回到第 1 步，修改原型。

如此循环，直到客户对「系统该长什么样」达成共识。**整个循环强调速度优先于质量**——原型阶段刻意忽略的那些属性（可维护性、性能、健壮性）不是不重要，而是现在讨论它们为时过早。

**辨析｜易错点：** 原型 ≠ 第一个正式版本。按 Pressman 的经典区分，原型阶段的目的是**澄清需求**，不是**交付产品**。把原型当成「粗糙的第一版然后慢慢补」，与「原型用来确认需求、确认后重写」是两种完全不同的策略——这正是下一节要讲的快速原型与演化式原型的分水岭。

## 3 快速原型（抛弃型原型）：探路与确认需求

**快速原型（throwaway / rapid prototyping）**，也叫**抛弃型原型**：它的任务只有一个——**把需求试出来**。一旦需求被确认，原型的历史使命完成，**整体抛弃，正式系统按确认好的需求从头写**。

布鲁克斯「计划好扔掉一个版本」说的正是它。为什么辛苦做出的东西要扔掉？因为**原型是为「看清问题」造的，不是为「解决问题」造的**。为了快，原型里的代码是能跑就行、界面是拼凑的、结构是临时的；拿它当正式系统的地基，等于在沙地上盖楼——那些被牺牲掉的性能、健壮性、可维护性，终有一天会以技术债的形式连本带利地讨回来。

快速原型的典型适用场景：

客户无法描述界面与交互，需要「先看见再确认」；
技术方案可行但需求边界模糊，需要快速对齐；
用来演示可行性、向决策者争取预算。

**重点：** 快速原型把「确认需求」这件最容易被敷衍的事，变成一次**可以验收的工程活动**。它的产物不是代码，而是**一份被验证过的需求共识**。<span class="marginnote">这正是原型模型对瀑布的最大贡献：瀑布里「需求评审通过」常常只是签字仪式，原型却让需求在真实交互中被检验。用第 8 章的术语说，原型是「需求的测试」——先用最便宜的手段验证假设，再进入高成本的正式开发。</span>

## 4 演化式原型：原型即产品

**演化式原型（evolutionary prototyping）** 走的是另一条路：**不抛弃原型，而是让原型在反馈中逐步长大，最终直接演化为正式产品**。它的起点是一个「粗而全」的骨架版本，之后每一轮迭代都在这个骨架上添加血肉、修正缺陷、优化体验，直到满足要求为止。

演化式原型与上一节的**迭代模型**几乎同构——区别在于定位：迭代模型强调的是「同一范围逐轮精化」的过程形态，演化式原型强调的则是「原型从一开始就是产品的一部分」这一**资产策略**。<span class="marginnote">这里要特别小心概念边界：演化式原型、增量模型、迭代模型在真实项目里高度重叠，Pressman 自己也在不同版本里反复调整这些术语的边界。考试或写作时，抓住「是否抛弃原型」这一个判断点即可：<strong>快速原型=抛弃，演化原型=保留长大</strong>。</span>

演化式原型擅长处理这样的项目：**客户需要尽快看到一个能用的东西，且愿意在很长一段时间里与开发团队共同打磨**。互联网产品的 MVP（最小可行产品）模式就是演化式原型的当代化身——第一版粗糙但能跑，之后靠用户反馈持续演进，几乎没有「推倒重写」的时刻。

## 5 核心对比表：快速原型 vs 演化式原型

两条路线在同一个起点分叉，走向截然不同的终点：

| 维度 | 快速原型（抛弃型） | 演化式原型 |
| --- | --- | --- |
| 目的 | 澄清需求 | 交付产品 |
| 原型的命运 | 确认需求后整体抛弃 | 保留并逐步长大 |
| 代码质量要求 | 低，够快就行 | 高，它将成为正式代码 |
| 适用需求 | 需求模糊、边界不明 | 需求模糊但可逐步明确 |
| 与客户的关系 | 确认即分离 | 长期共同演进 |
| 主要风险 | 投入被「浪费」在抛弃物上 | 结构腐化、技术债累积 |
| 类比 | 写草稿、做样机 | MVP 持续迭代 |

**辨析｜易错点：** 快速原型「抛弃」不等于「浪费」。扔掉的只是原型代码，收获的是**一份被验证的需求**与**一次低成本的试错**——这比在正式系统上返工便宜得多。真正的浪费是「用抛弃型原型的标准代码，却指望它扛起正式产品的质量」，以及它的反面「把演化式原型当成随便写的草稿，结果架构迅速腐化」。<span class="marginnote">两条路线的代码标准截然不同，这是最容易踩的坑。判断标准只有一个：<strong>这份代码会不会进入正式产品？会，就按正式标准写；不会，才允许怎么快怎么来。</strong>在动手写原型之前先想清楚这个问题，能省下后来几周的重写时间。</span>

**辨析｜易错点：** 原型不能交付给客户作为最终产品，但「客户把原型当真」恰恰是原型模型最著名的失败模式。当快速原型做得太逼真，客户会误以为「已经完成 80% 了」，于是拒绝为后续的正式开发继续投入。**应对办法是在动手前就与客户约定原型的性质与边界**——告诉客户：这是用来确认需求的示意图，不是产品的雏形。沟通上的这个小小约定，常常决定原型项目的成败。

## 6 核心要点：原型的价值、成本与适用场景

把两种原型放在适用性坐标里看：

| 情形 | 推荐路线 | 原因 |
| --- | --- | --- |
| 界面与交互说不清 | 快速原型 | 先让客户看见，再确认 |
| 技术方案可行、需求边界模糊 | 快速原型 | 用最低成本锁定需求 |
| 客户要尽快能用、愿意共同打磨 | 演化式原型 | MVP 模式，边用边长 |
| 系统庞大、模块众多 | 分模块原型 | 对高风险模块单独做原型验证 |
| 需求虽模糊但有强约束（性能/安全） | 原型 + 瀑布/螺旋 | 原型探路，正式结构用更严格的模型 |

**重点：** 原型的价值在于**用最小成本消除最大不确定性**——它把「需求」这一软件工程里最贵的错误源头，用几天时间暴露在阳光下。但原型的成本也不容低估：快速原型需要时间、需要客户高度参与，且容易在「正式版什么时候开始」上产生争议。因此**原型很少作为唯一的全过程模型**，更常见的用法是把它嵌入其他模型——瀑布的前端做原型确认需求，螺旋的每一圈用原型化解风险。

## 7 原型模型在「从极限到大模型」中的投影

大模型应用开发几乎绕不开原型——而且两种原型在这里都有清晰的对应物：

**提示词与界面的快速原型**：先用低成本的 prompt 模板 + 假数据搭一个 demo，验证「这个 AI 功能到底该长什么样」；确认后再投入正式的工程化开发。这正是快速原型的思路——demo 用完就扔，正式实现从头写。
**模型能力验证的原型**：在花大钱训练大模型之前，先用小模型、少数据做一轮「可行性验证」——能不能收敛、效果大致如何。这是演化式原型思想在训练前的低成本预演。<span class="marginnote">这也解释了为什么 AI 团队如此依赖「先跑通再优化」：训练成本太高，任何需求假设都值得先用最便宜的方式验证一次。原型模型的成本哲学——先花小钱试错、再花大钱投入——正是大模型时代最紧缺的能力。</span>

当你面对一个说不清需求的 AI 需求方时，最快的推进方式不是写需求文档，而是三天内给他一个**能点、能看、能触发他真实反馈**的 demo——这正是原型模型教给我们的第一课。

还要记住原型与「正式开发」之间那条被反复强调的边界：**原型阶段结束的标志，不是「代码写完了」，而是「需求共识达成了」**。用「需求是否被验证」而不是「代码是否完成」来判断原型是否该收尾，能避免两种典型事故——原型永无止境地改下去，或者需求尚未确认就匆忙进入正式开发。

## 8 小结

- 原型模型为**需求模糊**而生：需求不是被「写」出来的，而是被「看」出来的。
- 原型过程是一轮**快速循环**：沟通 → 快速策划 → 快速设计 → 构建原型 → 反馈，速度优先于质量。
- **快速原型（抛弃型）**：用来澄清需求，确认后整体抛弃，产物是「被验证的需求共识」。
- **演化式原型**：原型保留并逐步长大为正式产品，即 MVP 模式，要求代码按正式标准写。
- 两条路线在「是否抛弃原型」这一点上分叉，这是分辨二者的关键。
- 主要陷阱：**客户把原型当真**、**原型代码标准错配**；应在动手前约定原型性质。
- 原型常嵌入其他模型：瀑布前端、螺旋圈内，作为消除需求不确定性的手段。

在下一节，我们把「风险」正式摆上台面：原型化解需求风险，但项目的风险远不止需求一种。当风险本身成为过程组织的中心时，就得到本章最复杂的模型——**螺旋模型与风险驱动开发**。
