## 为什么从极限编程开始

上一节我们认识了 Scrum——它给出了一副「团队怎么转」的骨架：角色、事件、工件。但 Scrum 有一个刻意的留白：**它几乎不告诉你代码到底该怎么写**。一个团队可以严格照着 Scrum 开每一个会、交每一个增量，却依然写出又臭又乱的代码、积压一堆没拆的技术债。

**极限编程（Extreme Programming，XP）** 恰好补上这块拼图。它由 Kent Beck 在 1990 年代提出，是敏捷家族里**最「工程化」的一个**：Scrum 管的是「节奏」，XP 管的是「每一个小时都在做什么」——两个人一起写代码、先写测试再写实现、随时重构、天天集成。如果说敏捷宣言是宪法、Scrum 是政体，那么 **XP 就是「把宪法落实到日常生活的具体法令」**。<span class="marginnote">在「从极限到大模型」的坐标里，XP 也最贴近工程实践：现代 AI 工程的「先写评测再训模型」「数据管线的持续集成」「prompt 版本的可复现」，几乎都能在 XP 的实践里找到原型。它把「如何把好习惯变成肌肉记忆」这件事讲得最透。</span>

XP 还承担着一次「澄清」：很多人以为敏捷 = 没有纪律地快速堆代码。XP 恰恰是反例——它把「测试、评审、集成、重构」这些最需要自律的实践，变成了**每一天的默认动作**。读完这一节你会明白：**敏捷不是放低了纪律的标准，而是把纪律搬进了每一个小时。**

## 1 为什么叫「极限」：C3 项目与 Beck

XP 诞生于一个真实的救火现场。1990 年代中期，克莱斯勒公司（Chrysler）的薪资系统项目 C3（Comprehensive Compensation System）濒临失败——负责开发的团队一年没产出可用的东西，代码质量一团糟。Kent Beck 临危受命加入，他没有推倒重来，而是把一堆「早该做却没做」的软件工程好习惯**加倍、放大、贯彻到极端**，最终让这个一度被判死刑的项目成功交付。

「极限」的含义就在这里。Beck 的逻辑是：**如果某件好事的程度还不够，那我们就把它做到极致**——

- 如果代码评审有好处，就**永远**评审——两个人在同一台电脑上写每一行代码（结对编程）。
- 如果测试有好处，就**先写测试、处处测试**——测试先行，所有代码都由测试来定义「完成」。
- 如果设计有好处，就把它变成**每天**的事——不搞「先设计后编码」，而是让设计伴随编码增量演进（简单设计）。
- 如果集成有好处，就**天天**集成、随时集成——不等到最后一刻才把所有代码拼起来。
- 如果客户反馈有好处，就**让客户坐在团队里**——现场客户，随问随答。

**重点：** 「极限」不是「极端地加班、极端地拼命」，而是**把已知有效的好实践推到它们能起作用的最大强度**。每一项 XP 实践，都可以被这句话解释清楚：它是某个常识性好习惯的「极限放大版」。这个理解方式，比死记硬背十二项实践的名字重要得多。<span class="marginnote">C3 项目后来成为了《重构》一书的试验场，Martin Fowler 在 C3 上的观察直接促成了重构理论的形成。而「结对编程」之所以能被如此高调地推广，也与 C3 团队的实际收益密切相关——这些问题在本专题《PSP 与结对编程》《代码评审与重构》等章节会继续展开。</span>

## 2 五个价值观

XP 的第一版提出四个价值观，第二版（2004，与 Cynthia Andres 合著）补上了第五个：

1. **沟通（Communication）**：软件项目的大部分失败源于误解——需求没说清、设计没传达到、进度没同步。XP 用结对编程、现场客户、计划游戏等实践，**把沟通嵌进工作本身**，而不是寄望于文档。
2. **简单（Simplicity）**：只做「当前已知需要」的事，不预测未来、不做「可能用得上」的设计。**YAGNI**（You Aren't Gonna Need It，你其实用不到）是它的口号——把简单当成持续的纪律，而不是懒惰的借口。
3. **反馈（Feedback）**：要**即时**、**具体**的反馈。测试给你「这一秒代码对不对」的反馈，客户给你「这周方向对不对」的反馈，结对伙伴给你「我刚才想得对不对」的反馈。反馈越快，纠偏越便宜。
4. **勇气（Courage）**：有反馈撑腰，才有勇气做对的事——该重构就重构（哪怕代码刚写好）、该扔掉就扔掉、该如实告诉客户「估少了」就如实说。**勇气不是鲁莽，而是「反馈充足时敢于行动」**。
5. **尊重（Respect）**：每个人——无论资历、无论角色——的贡献都值得被认真对待。前四个价值观都以尊重为底座：你不尊重伙伴，就不可能与他把代码写好；你不尊重客户，就不会在意他到底要什么。<span class="marginnote">五个价值观构成一个自洽的整体：沟通让信息流动，反馈让流动的信息变成行动依据，简单让你敢行动，勇气让你在反馈下果断行动，而尊重让这一切在团队里持续发生。缺了任何一个，其余四个都会走样。</span>

**价值观与第十二节实践的关系**：价值观是「为什么」，实践是「怎么做」。Beck 强调，价值观若不能落到实践上就是空话——沟通靠结对与现场客户落地，反馈靠测试与持续集成落地，简单靠简单设计与 YAGNI 落地，勇气靠重构落地。**每一项实践都可以反向追问：「它在放大哪个价值观？」** 答不上来的实践，往往就是团队里的形式主义。

## 3 十二项核心实践：把价值观做成习惯

XP 把价值观落实为一组**工程实践**。Pressman 教材沿用的是经典的十二项，这里给出全表，并标注每项「极限」在哪儿：

| 实践 | 一句话 | 「极限」在哪 |
| --- | --- | --- |
| 计划游戏（Planning Game） | 客户写故事，团队估工作量并排优先级 | 计划变成持续进行的游戏，而非一次性文档 |
| 小型发布（Small Releases） | 每次只发布少量功能，尽快让客户用上 | 发布周期压到最短 |
| 隐喻（Metaphor） | 用一套共享的比喻描述系统（如「管道」） | 用共用的语言统一全体对架构的理解 |
| 简单设计（Simple Design） | 只做当前需要的最简设计 | 设计从「预先的」变成「持续的」 |
| 测试先行（Test-First） | 先写失败测试，再写让它通过的代码 | 测试从「事后验证」变成「先行定义」 |
| 重构（Refactoring） | 不改变行为地持续改进内部结构 | 重构从「大版本前的清理」变成「每天」 |
| 结对编程（Pair Programming） | 两人一台电脑，一人写、一人审、实时轮换 | 代码评审从「会后」变成「实时」 |
| 集体所有权（Collective Ownership） | 任何成员都能改任何代码 | 所有权从「我的模块」扩展到「我们的系统」 |
| 持续集成（Continuous Integration） | 每次改动都立刻集成、立刻跑测试 | 集成从「里程碑」变成「每天数次」 |
| 可持续节奏（Sustainable Pace） | 保持能无限期维持的工作强度（40 小时周） | 「按时下班」被写进实践，而非口头提倡 |
| 现场客户（On-Site Customer） | 客户代表常驻团队，随问随答 | 客户协作从「开会」变成「在身边」 |
| 编码标准（Coding Standards） | 全队用同一套编码规范 | 规范从「各写各的」变成「统一约定」 |

**重点：** 这十二项实践不是孤立的，而是**互相咬合的一整套**。举例来说：没有「测试先行」，「持续集成」就无从谈起（每次集成靠什么验证？）；没有「编码标准」，「集体所有权」就会退化成「谁改谁遭殃」；没有「简单设计」，「重构」就会永无休止。**XP 的价值在于组合效应**——抽掉任何一根柱子，其他柱子都会跟着松动。<span class="marginnote">注意本专题的叙事分工：测试先行会在第 8 章《自动化测试与测试驱动开发（TDD）》展开，重构会在第 14 章《代码评审与重构》展开，结对编程已在《个人软件过程（PSP）与结对编程》做过专题。今天这一节只负责「把它们放进同一张蓝图」。</span>

用一个 **XP 工作日的切片**把十二项实践串起来：上午，程序员阿林与阿哲结对开工，先为「用户上传 CSV 文件」写一个**注定失败的测试**（测试先行）——文件为空时要给出友好报错；测试红了之后，阿林写最小实现，阿哲在一旁实时评审（结对编程），改完立刻跑全量测试并**集成**进主干（持续集成）。下午，客户代表发现某条业务规则理解有误，团队没有恐慌：因为测试网已经铺好，改实现的同时**重构**掉那处被误读的命名（重构），旧测试与新测试一起保护这次改动（简单设计 + 编码标准让改动成本最低）。傍晚六点，团队准时下班（可持续节奏）——**不是活儿少，而是每一项实践都在让「改对」这件事变得便宜**。<span class="marginnote">这个切片里没有「写设计文档」「排里程碑」「开需求评审会」——不是这些事没发生，而是它们被<strong>碎片化地</strong>融进了每一天：计划游戏里定方向，隐喻里对齐理解，小型发布把「客户什么时候能用到」变成近在眼前。</span>

## 4 核心对比表：Scrum vs XP

同为敏捷框架，Scrum 与 XP 常被混为一谈，实则分工不同。把它们并排看：

| 维度 | Scrum | 极限编程（XP） |
| --- | --- | --- |
| 关注层次 | 团队组织与过程节奏 | 工程实践与代码质量 |
| 角色 | PO / SM / 开发团队 | 客户 / 程序员 / 教练（角色更扁平） |
| 周期 | Sprint（2–4 周） | 迭代（1–3 周），常与发布对齐 |
| 需求表达 | 产品待办列表 + 用户故事 | 用户故事 + 隐喻 + 计划游戏 |
| 工程实践 | 刻意不规定 | **硬性规定**（结对、测试先行、持续集成……） |
| 检查机制 | 站会 + 评审 + 回顾 | 测试反馈 + 持续集成 + 结对评审 |
| 代码所有权 | 团队共同负责 | **集体所有权**，人人可改 |
| 强调的价值观 | 承诺、专注、开放、尊重、勇气 | 沟通、简单、反馈、勇气、尊重 |

**重点：** 一句话区分两者——**Scrum 管理「盒子」，XP 管理「盒子里的代码」**。Scrum 刻意保持「工程中立」，不规定怎么写代码，以便适配各种技术栈；XP 则把「怎么写代码」当作头等大事。实践中两者经常叠用：用 Scrum 的骨架组织迭代，用 XP 的实践保证每个迭代里代码不腐坏。**它们不是二选一的竞争关系，而是互补关系**。<span class="marginnote">互补性也体现在二者对「变化」的防守策略上：Scrum 用「短周期 + 评审」从外部接住变化，XP 用「测试 + 重构 + 持续集成」从内部接住变化。前者防止「做错方向」，后者防止「改不动代码」。</span>

## 5 辨析｜易错点：XP 的三个误读

1. **XP ≠ 无计划、无架构、不写文档**。XP 的「简单设计」强调「只做当前需要」，但它要求**每一次设计都认真做**，只是不必提前预测所有需求；「隐喻」正是为了给系统一个共享的架构图像。**简单 ≠ 粗糙**：简单是在「够用」与「猜测未来」之间选择前者，粗糙则是该做的设计也不做。
2. **测试先行 ≠ 用测试取代设计**。写失败测试之前，你仍然需要想清楚「这段代码要承担什么职责」——测试是在**帮你澄清设计**，而不是替你做设计。没有设计的测试先行，会产出「为测试而写、结构僵硬」的代码。
3. **结对编程 ≠ 两倍人力成本**。结对的实时评审省下了事后评审与返工，且知识在两人间流动。实测表明结对初期有成本，但缺陷密度下降、知识共享的收益通常在项目中期回本。**真正的浪费是「一人写、无人审、事后大改」**。
4. **XP ≠ 只适合小团队**。XP 确实对「现场客户」「全员结对」这类高带宽沟通有较高要求，小型团队最容易满足——但它的工程内核（测试先行、持续集成、简单设计、重构）早已被放大到大厂与开源社区。**实践可以分环境裁剪，价值观不分**：今天任何一个现代工程团队所遵循的「先写测试、频繁集成、保持代码整洁」，本质上都是 XP 的遗产。

## 6 XP 在「从极限到大模型」中的投影

XP 的实践几乎可以逐条映射到现代机器学习工程：

- **测试先行 → 评测先行**：训练之前先写好评测集与评估脚本（就像先写失败测试），模型达到评测标准才算「完成」。这是「以评测定义进度」的 XP 精神。
- **持续集成 → 持续评测**：每一次数据改动、每一次 prompt 调整都立刻跑一遍回归评测，防止「模型能力回退」——这正是 XP 持续集成在大模型场景的直接翻版。
- **简单设计 → 从基线模型起步**：先用一个简单基线（baseline）跑通端到端，再逐步加复杂度。**YAGNI 在训练成本昂贵的领域尤其重要**——每一份多余的数据清洗、每一个多余的模块，都在烧钱。
- **结对编程 → 结对做数据与 prompt**：标注规范、prompt 模板这种高度依赖经验判断的工作，两人一起做的质量与一致性远高于单人闭门造车。
- **集体所有权 → 可复现的实验管线**：团队任何成员都能跑通、复现任何实验（版本控制 + 环境锁定），相当于「任何成员都能改任何代码」的数据科学版本。<span class="marginnote">反过来，XP 也提醒 AI 团队一条容易被忽略的纪律：<strong>勇气</strong>。当数据实验证明某条路走不通时，敢不敢把写好的代码删掉、把训到一半的模型停掉——这是大模型工程里最难、也最值钱的「勇气」。</span>

需要强调的是：XP 对大模型的指导，**不在「照搬实践」，而在「借用其纪律」**。数据标注与模型评估的节奏远比代码迭代慢，直接套用「每小时跑一次测试」并不现实；但「先定义成功标准再做改动」「每次改动都让旧结果可复现」「保持实验代码整洁以便随时重构」——这些原则在训练成本以万元计的领域，价值只会更高。

## 7 小结

- **XP** 由 Kent Beck 在 1990 年代从救火项目 **C3** 中提炼，核心理念是把好习惯**推到极限**：「如果某件事有效，就把它做到最大强度」。
- 五个价值观：**沟通、简单、反馈、勇气、尊重**；简单与勇气分别用 **YAGNI** 与「有反馈才行动」来落实。
- 十二项核心实践互相咬合：计划游戏、小型发布、隐喻、简单设计、**测试先行**、重构、结对编程、集体所有权、**持续集成**、可持续节奏、现场客户、编码标准。
- 与 Scrum 的关系：**Scrum 管节奏、XP 管代码**，常组合使用；核心差异在「是否硬性规定工程实践」。
- 三大误读要警惕：XP ≠ 无架构、测试先行 ≠ 取代设计、结对编程 ≠ 两倍成本。
- 对 AI 工程：评测先行、持续评测、基线起步、结对做数据与 prompt、可复现管线，都是 XP 的直接投影。
- 一句话总纲：**敏捷不是放低纪律，而是把纪律拆成每天可执行的原子动作**——XP 就是这套原子动作最完整的清单。
