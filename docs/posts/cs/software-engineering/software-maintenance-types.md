# 软件维护的类型：改正性、适应性、完善性与预防性

## 为什么从维护类型开始

前面所有章节都在讲"如何把软件做出来"，这一章转向"软件交付之后"——它占了软件一生成本的大头（业界常引用的数字是 **50%–70% 的维护成本**）。维护不是"修 bug"这么简单，它有明确的类型划分，每一类的成因、频率与工作方式都不同。这一节讲软件维护的**四种类型**。

## 1 改正性维护：修 bug

**改正性维护（corrective maintenance）**：**发现并修正已提交软件的缺陷**——包括编码错误、设计错误、需求理解错误。这是最直觉的"修 bug"。

- **触发**：缺陷被发现（用户报障、测试发现、监控告警）。
- **频率**：是维护中**最常见**的一类（常占 20% 左右）。
- **特点**：常与"缺陷优先级"相关——严重缺陷要立即修，轻微缺陷排队。

**辨析｜易错点：** 改正性维护 ≠ "发现所有 bug 都修"。要按**严重度与影响面**排优先级：阻塞核心流程的立即修，边缘小缺陷纳入迭代。乱修小 bug 会挤占新功能与更重要维护的时间——维护也是要排期、要取舍的工程活动。

## 2 适应性维护：适应环境变化

**适应性维护（adaptive maintenance）**：**修改软件以适应其运行环境的变化**——硬件升级、操作系统更新、数据库版本变化、外部接口变更。

- **触发**：环境变了（新的 OS 版本、新的编译器、新的浏览器）。
- **本质**：不是改功能，而是**让软件在新环境里继续正确运行**。
- **例子**：把系统从 Java 8 升级到 Java 17、适配新版 Chrome 的 API 变更。<span class="marginnote">适应性维护与"技术债"密切相关：技术债越重，环境一变就越痛——老的框架停止维护、旧的依赖有安全漏洞，逼着你做适应性维护。反过来，<strong>把依赖升级当作常规工作</strong>（第 13 章 DevOps 的依赖更新习惯）能把"被迫的大升级"拆成"频繁的小升级"，大幅降低适应性维护的冲击。</span>

## 3 完善性维护：增加与改进

**完善性维护（perfective maintenance）**：**增加新功能、改进已有功能、提升性能与可用性**——让软件"变得更好"，而不只是"保持可用"。

**触发**：用户新需求、业务发展、性能优化诉求。
**占比**：在多数统计中，完善性维护是**占比最大**的一类（常达 50% 以上）。
**本质**：它和"新功能开发"的界限很模糊——区别只在"同一软件的增量演进"。

**辨析｜易错点：** 很多人以为"维护 = 修 bug"，但数据恰恰相反：**完善性维护（加功能、改体验）才是维护工作的大头**。这揭示了一个观念：维护期不是"停滞期"，而是软件**持续演化的主战场**——这与第 9 章《Lehman 定律》"程序必须持续演化否则衰败"的观点直接呼应。

## 4 预防性维护：防止未来的问题

**预防性维护（preventive maintenance）**：**预防缺陷与退化，提高可维护性**——主动改进软件的内部结构，而不是等出问题再修。

**手段**：重构（第 14 章）、代码评审、文档更新、冗余清理、防御性编码。
**类比**：像汽车的定期保养——不是等抛锚了再修，而是定期换机油、查刹车。
**反例**：因为"能跑就不要动它"而拒绝预防性维护，正是技术债积累的根源。

**辨析｜易错点：** 预防性维护最难推进，因为它**没有立即可见的产出**——重构后的代码"看起来一样"，短期内没有新功能也没有修 bug，于是管理者常认为"浪费时间"。但预防性维护的价值恰恰在于**降低后续所有维护的成本**：结构变清晰，下一次完善性维护和改正性维护都更快更安全。<span class="marginnote">预防性维护与"技术债"概念互为镜像：技术债是"过去偷的懒，未来要还"，预防性维护是"现在花的力，未来能省"。成熟的团队把"每次改动顺手清理"作为纪律（鲍伊定律：像营地一样，离开时比来时更干净），而不是等专门的"重构月"。预防性维护最好的形态，是<strong>融入日常开发而非独立项目</strong>。</span>

## 5 四种维护的对比

| 类型 | 目的 | 触发 | 常见占比 |
| --- | --- | --- | --- |
| 改正性 | 修缺陷 | 缺陷被发现 | ~20% |
| 适应性 | 适应环境变化 | 环境升级 | ~25% |
| 完善性 | 增加/改进功能 | 新需求 | ~50% |
| 预防性 | 防止未来问题 | 主动改进 | ~5% |

（占比为业界常见参考，不同系统差异很大。）

**辨析｜易错点：** 四类维护的边界不是绝对的——一次改动可能兼有"适应新环境"与"完善功能"两个目的。**分类的价值不在贴标签，而在管理**：不同类别的维护需要不同的优先级、排期与资源。例如"改正性"维护要快（影响用户），"预防性"维护要稳（不能引入回归），"完善性"维护要排期（跟随迭代节奏）。给维护分类，是为了**让维护也成为有计划、可管理的工程活动**，而不是救火式的随机动作。

## 6 数值算例：维护成本的构成与杠杆

用一个假想的 5 年生命周期项目，感受四种维护的占比与投入。假设总开发成本为 100 万元，5 年内总维护成本约 150 万元（约 1.5 倍），按四种类型拆分：

| 维护类型 | 占比 | 5 年成本（示意） | 主要驱动因素 |
| --- | --- | --- | --- |
| 改正性 | ~20% | 30 万 | 缺陷密度、测试覆盖率 |
| 适应性 | ~25% | 37 万 | 技术债、环境变化频率 |
| 完善性 | ~50% | 75 万 | 业务演进速度、产品路线 |
| 预防性 | ~5% | 8 万 | 团队的维护纪律 |

读这张表有两个杠杆：**其一，完善性维护是大头**——说明维护期本质是"业务持续演进期"，团队 50% 的维护工时在做新功能，这与"维护=修bug"的直觉完全相反；**其二，预防性维护占比极小（~5%），但杠杆巨大**——它拉低的是改正性（缺陷更少）与适应性（结构更易改）的成本。**把 1 元投在预防性维护上，往往能省下 3–5 元的改正性与适应性成本**——这就是"早做便宜"（第 1 章缺陷成本表）在维护期的复现。

**辨析｜易错点：** 别把这张表的占比当成"应该分配的比例"——它是**现状描述**，不是**目标**。恰恰相反，成熟的团队会**主动提高预防性维护的投入**（哪怕超过 5%），用结构投资换未来成本的下降。维护管理的艺术，就是在这四类之间找到"现在花多少力、未来省多少钱"的平衡。

## 7 术语速查表

| 术语 | 英文 | 一句话定义 |
| --- | --- | --- |
| 改正性维护 | Corrective Maintenance | 发现并修正已交付软件的缺陷 |
| 适应性维护 | Adaptive Maintenance | 修改软件以适应环境变化 |
| 完善性维护 | Perfective Maintenance | 增加新功能、改进已有功能与性能 |
| 预防性维护 | Preventive Maintenance | 主动改进内部结构、预防未来问题 |
| 软件维护 | Software Maintenance | 交付后对软件进行的全部修改活动 |
| 缺陷 | Defect | 软件中的错误或偏差 |
| 环境变化 | Environment Change | 硬件、OS、依赖库等运行环境的变化 |
| 技术债 | Technical Debt | 为短期速度而欠下的未来返工成本 |
| 重构 | Refactoring | 行为不变、结构变好的修改 |
| 鲍伊定律 | Boy Scout Rule | 离开时比来时更干净（随手清理） |
| 回归 | Regression | 修改引入的新缺陷 |
| 维护成本 | Maintenance Cost | 交付后投入的人力与资金 |

## 8 核心对比表：四种维护的识别口诀

| 类型 | 一句话口诀 | 触发信号 | 典型动作 |
| --- | --- | --- | --- |
| 改正性 | 坏了要修 | 用户报障、测试失败 | 定位缺陷、修复、回归 |
| 适应性 | 环境变了要跟上 | OS/依赖/硬件升级 | 升级代码适配新环境 |
| 完善性 | 更好要加 | 新需求、优化诉求 | 加功能、改体验 |
| 预防性 | 没坏也要护 | 主动的定期改善 | 重构、清理、补文档 |

**辨析｜易错点：** 一次改动常同时兼有多个目的（"升级框架"既是适应性也是预防性），贴标签不是目的——**分类的价值在管理**：改正性要快、适应性要排期、完善性跟迭代、预防性要有纪律。判断标准：**面对一次维护需求，先问"它是修、是跟、是加、还是护"**，再决定优先级与资源。

## 9 小结

- 维护占软件生命周期成本的 **50%–70%**，是软件工程的主战场。
- **改正性维护**修缺陷，按严重度排优先级。
- **适应性维护**适应环境变化，技术债越重越被动。
- **完善性维护**增加与改进功能，通常是占比最大的一类。
- **预防性维护**主动改进内部结构，降低未来维护成本。
- 分类的价值在管理：不同维护类型需要不同的优先级、排期与资源。
