## 为什么从决策表开始

等价类与边界值处理"单个输入"，但真实业务往往是**多个条件组合决定一个动作**——"已登录 && VIP && 满减活动"决定折扣。条件组合爆炸，靠直觉测很容易漏。这一节的两个工具专门对付"多条件逻辑"：**决策表（decision table）**用表格穷举条件组合，**因果图（cause-effect graph）**用图形梳理条件与结果的关系。

## 1 决策表：把条件组合摊平

**决策表（decision table）**用表格列出**所有条件的组合**及其对应的**动作**，常用于逻辑规则复杂、if/else 层层嵌套的需求。

决策表四要素：

- **条件桩（condition stub）**：列出所有条件（左上）。
- **动作桩（action stub）**：列出所有可能动作（左下）。
- **条件项（condition entry）**：每个条件在每种组合下的取值（右上）。
- **动作项（action entry）**：每种组合应执行的动作（右下）。

以"购书折扣"为例（条件：是否 VIP、是否满 100 元；动作：9 折、8 折、无折扣）：

| 条件/动作 | 1 | 2 | 3 | 4 |
| --- | --- | --- | --- | --- |
| VIP？ | 是 | 是 | 否 | 否 |
| 满 100？ | 是 | 否 | 是 | 否 |
| 折扣 | 8 折 | 9 折 | 9 折 | 无 |

4 个条件组合全部列出，每条组合一行——**不漏不重**，这是决策表的最大价值。

**辨析｜易错点：** 决策表的条件数 $n$ 对应 $2^n$ 种组合——条件一多，表格指数膨胀。工程实践用两个手段压缩：**忽略不可能组合**（"已登录"且"未登录"不可能同时为真）与**使用"无关项"（don't care）**——某条件不影响结果时用 $2^n$ 标记，多行合并。**全列出是完整性的保障，合并是实用性的选择**。

## 2 决策表的构造步骤

构造决策表的四步：

1. **列出所有条件**：把需求里的判定条件逐一提取。
2. **列出所有动作**：把条件触发的动作逐一提取。
3. **生成组合矩阵**：按 $2^n$ 穷举条件组合，填入动作。
4. **化简合并**：合并动作相同的行、标注无关条件。

每条规则（行）就是一条测试用例——**决策表到测试用例是"一表一测"的直接映射**。<span class="marginnote">决策表与需求分析的联系：第 3 章"行为建模"里的业务规则，用自然语言写在 SRS 里容易有歧义；翻译成决策表后，规则的不完整（某组合漏了动作）、不一致（同组合两个动作）立刻暴露。<strong>决策表既是测试设计工具，也是需求验证工具</strong>——测不出歧义时，先回头改需求。</span>

## 3 因果图：从原因到结果的图形梳理

**因果图（cause-effect graph）**处理更复杂的关系：条件（原因）之间可能有**约束**，结果（效果）之间也可能互相影响。因果图用图形表示原因与结果的关系：

**恒等**：原因出现 → 结果出现。
**非**：原因不出现 → 结果出现。
**或（OR）**：任一原因出现 → 结果出现。
**与（AND）**：全部原因出现 → 结果出现。

原因之间还有**约束**（排除关系）：`E`（互斥，至多一个为真）、`I`（包含，至少一个为真）、`O`（唯一，恰有一个为真）、`R`（要求，一个出现则另一个必出现）。

方法步骤：**列原因与结果 → 画因果图 → 把因果图转成决策表 → 由决策表生成测试用例**。

**辨析｜易错点：** 因果图与决策表不是二选一，而是**同一逻辑的两副面孔**——因果图适合"梳理"（画关系、找约束），决策表适合"穷举"（列组合、映射用例）。实践中常因果图先行、决策表落地。**当条件之间存在约束（互斥、依赖）时，纯决策表会生成大量不可能组合，因果图的约束正好帮上忙**。

## 4 决策表 vs 因果图

| 维度 | 决策表 | 因果图 |
| --- | --- | --- |
| 形式 | 表格（条件×组合） | 有向图（原因→结果） |
| 擅长 | 穷举条件组合 | 表达条件约束与关系 |
| 优势 | 完整、直接映射用例 | 直观、支持约束 |
| 局限 | 条件多则指数膨胀 | 图复杂难读 |
| 关系 | 因果图可转成决策表 | 决策表是因果图的落地 |

**关键判断：条件少而规则多 → 决策表直接上；条件之间有复杂约束 → 因果图先梳理**。<span class="marginnote">决策表与因果图的共同本质，是把"藏在 if/else 里的隐性逻辑"<strong>显式化</strong>。需求评审时给出一张决策表，比给一段"如果……并且……那么……否则如果……"的自然语言，能省下大量理解成本。这也是为什么很多团队的接口文档、规则引擎配置（如优惠券系统）直接采用"决策表"形态——显式逻辑才是可验证、可维护的逻辑。</span>

## 5 小结

- **决策表**用条件桩、动作桩、条件项、动作项穷举条件组合，不漏不重。
- 决策表构造四步：列条件 → 列动作 → 生成组合矩阵 → 化简合并。
- 条件组合指数增长时，用"忽略不可能组合"与"无关项"压缩。
- **因果图**用恒等/非/或/与表达原因结果，用 `E`/`I`/`O`/`R` 表达条件约束。
- 因果图适合梳理约束，决策表适合穷举落地，常配合使用。
- 决策表与因果图把隐性逻辑显式化，既是测试工具也是需求验证工具。
