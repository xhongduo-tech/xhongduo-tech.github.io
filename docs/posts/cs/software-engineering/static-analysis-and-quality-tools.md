## 为什么从静态分析开始

前面的评审与重构都靠"人眼"，但人眼有限——低级错误（未用变量、空指针风险、风格不一致）逐行看既累又易漏。**静态代码分析（static code analysis）**用工具**在运行前**检查代码，把机器擅长的部分交给机器，人专注设计与逻辑。这一节讲静态分析的类型、工具生态，以及"机器与人怎么分工"。

## 1 静态分析：运行前的自动检查

**静态代码分析（static analysis）**：**不运行程序**，仅通过分析代码**文本与结构**来发现问题的技术。与之相对的是**动态分析**（运行程序观察行为，如测试、性能剖析）。

静态分析能发现的问题类型：

- **语法与风格**：格式不规范、命名不一致、死代码（lint 类）。
- **潜在缺陷**：空指针解引用、资源泄漏、未初始化变量、类型不安全（编译器静态检查的增强版）。
- **安全漏洞**：注入、XSS、不安全的加密、危险的 API 使用（安全扫描器）。
- **复杂度与坏味道**：圈复杂度、过长方法、重复代码（质量度量，第 15 章）。

**辨析｜易错点：** 静态分析 ≠ 编译。**编译检查"语法与类型是否合法"，静态分析检查"代码是否可能出问题"**——编译保证"能跑"，静态分析帮助"少出事"。判断标准：**工具报的每个问题，都值得人看吗？** 不值得（误报太多）的工具会让人"报警疲劳"——工具要会**配置规则、抑制误报**，否则沦为一堆没人看的警告。

## 2 工具生态：从 lint 到安全扫描

按用途分层：

- **Linter（代码规范）**：ESLint（JS）、Pylint（Python）、Checkstyle（Java）、golangci-lint（Go）——风格、坏味道、潜在 bug。
- **编译器静态检查**：编译器（GCC、Clang）、类型检查器（TypeScript、MyPy）——类型错误在编译期拦截。
- **缺陷分析器**：SpotBugs（Java）、SonarQube（多语言）——深度缺陷模式。
- **安全扫描**：Semgrep、CodeQL、Snyk、OWASP Dependency-Check——注入、漏洞、危险依赖。
- **格式化器**：Prettier、Black、gofmt——风格统一交给机器，结束"格式之争"。

**辨析｜易错点：** 工具不是越多越好——**每个工具都有误报率与维护成本**。成熟团队的策略是"**少而精 + 持续调教**"：选 1–2 个主力工具，配置团队的规则集，**抑制确认的误报**，让剩余的告警都"值得看"。判断标准：**工具告警量是否可控、每条是否可行动？** 告警上千、大半误报的工具，比没有更糟。

## 3 机器与人的分工：自动化先筛、人工审设计

静态分析在质量体系里的定位，是"**机器先筛、人审设计**"：

- **机器负责**：低级、可穷举的问题——风格、明显 bug、安全模式、复杂度超标。
- **人负责**：设计合理性、需求符合度、可读性、可维护性——机器看不出的"深层"。

<span class="marginnote">这个分工是"<strong>人机各司其职</strong>"的典范：机器擅长"枚举"（检查所有模式是否匹配），人擅长"判断"（这个设计好不好）。把枚举交给机器，人才能在评审里专注判断——<strong>评审的价值密度因此大幅提升</strong>（第 14 章《代码评审》）。现代工具链把这个分工固化进 CI：静态分析作为流水线第一关（第 13 章），低级问题自动拦截，能到人工评审的 PR 已经"过了机器关"。</span>

**辨析｜易错点：** 静态分析 ≠ "用了工具就不用评审"。**工具能抓"模式"，抓不了"意图"**——一个设计糟糕但风格规范的类，静态分析一片绿，人眼一看满是问题。**工具是评审的"预筛器"，不是评审的替代品**。判断标准：**你的 PR 评审，是在看"机器没看到的问题"还是在重复"机器已报的问题"？** 前者是健康分工，后者是工具没配好。

## 4 静态分析与 CI/质量的集成

静态分析的最佳实践是与工程流程集成：

- **提交时**：git hook 跑 lint/format——低级问题不进仓库。
- **CI 中**：静态分析作为流水线第一关（第 13 章）——不绿不合并。
- **质量门**：复杂度/覆盖率阈值由工具把关（第 15 章）。
- **趋势追踪**：静态分析告警量随时间下降，是代码质量在变好的证据。

**辨析｜易错点：** "工具全绿 = 代码没毛病"是最危险的错觉——**静态分析只覆盖它规则集里的问题，覆盖面有限**。判断标准：**把静态分析的结果当"已知问题清单"而不是"健康证明"**——绿了只是"这组规则没问题"，不等于"代码没问题"。**工具是"底线"，不是"天花板"**。

## 5 小结

- **静态分析**在运行前分析代码结构，发现风格、缺陷、安全、复杂度问题。
- 静态分析 ≠ 编译：编译保证"能跑"，静态分析帮助"少出事"。
- 工具生态：**linter（规范）、编译器检查、缺陷分析器、安全扫描、格式化器**。
- 工具要"**少而精 + 持续调教**"——抑制误报，让告警都可行动。
- 分工：**机器枚举、人审设计**——工具是评审的预筛器，不是替代品。
- 工具全绿 ≠ 代码健康——静态分析是"底线"，不是"天花板"。
