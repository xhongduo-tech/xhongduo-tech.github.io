## 为什么从解释器与迭代器开始

这一节的两个模式一个"高端"、一个"普及"：**解释器**用于定义一门小型语言的语法并解释执行；**迭代器**用于统一地遍历集合而无需暴露内部结构。前者在编译器（第三级《编译原理》）与领域专用语言里大显身手，后者是每一种语言集合框架的标配。

## 1 解释器：给领域定义一门小语言

**解释器（Interpreter）**：给定一门语言，**定义其文法表示**，并定义一个解释器来解释该语言中的句子。

结构：**Expression** 定义解释接口 **interpret()**；**TerminalExpression（终结符）**与 **NonterminalExpression（非终结符，含子表达式）**实现它；**Context** 携带解释所需的全局信息；客户端构建**抽象语法树（AST）**并调用解释。

适用场景：**重复出现、且可用文法描述的领域问题**——如正则表达式引擎、SQL 解析、配置文件解析、布尔表达式计算。当"某种语言/表达式"在你的领域频繁出现时，解释器把解析与求值结构化。<span class="marginnote">解释器模式的本质是<strong>文法 → 类结构</strong>：文法的每条规则映射成表达式类，AST 由这些类组合而成，由 `interpret()` 递归求值。它的代价是<strong>类爆炸</strong>（每条文法规则一个类）与解析复杂性——所以实战中很少手写解释器，而是用解析器生成器（ANTLR、Yacc）或现成的表达式库。解释器模式的<strong>思想</strong>（文法映射类、递归求值）比它的<strong>实现</strong>更值得学——那是编译原理的入门雏形。</span>

**辨析｜易错点：** 解释器模式 ≠ "写一个解释器程序"。GoF 的解释器特指"**用类结构表示文法 + 递归求值**"的特定方案。现代实践中，选择**解析器生成器**或**AST 框架**往往更合适——模式的价值在于理解"文法-类-求值"三者的对应，而非强行手写。

## 2 迭代器：统一地遍历集合

**迭代器（Iterator）**：提供一种方法**顺序访问一个聚合对象中的各元素**，而**不暴露其内部表示**。

结构：**Iterator** 接口声明 **next()**、**hasNext()**（及可选 **remove()**）；**ConcreteIterator** 实现遍历逻辑；**Aggregate（聚合）**提供 **iterator()** 返回迭代器。

```java
// 迭代器接口
interface Iterator<T> {
    boolean hasNext();
    T next();
}

// 具体迭代器：封装数组遍历逻辑
class ArrayListIterator<T> implements Iterator<T> {
    private T[] items;
    private int idx;
    ArrayListIterator(T[] items) { this.items = items; }
    public boolean hasNext() { return idx < items.length; }
    public T next() { return items[idx++]; }
}

// 聚合对象：对外只提供 iterator()，不暴露内部存储
class ArrayList<T> {
    Iterator<T> iterator() { return new ArrayListIterator<>(items); }
}
```

迭代器让**遍历与集合解耦**：换一种遍历方式（顺序、倒序、过滤）不需要改集合本身，集合的内部结构（数组、链表、树）被迭代器隔离。客户端只依赖 **Iterator** 接口。<span class="marginnote">迭代器的现代形态是“<strong>语言内建</strong>”：Python 的迭代器协议（`__iter__`/`__next__`）、Java 的 `Iterable`/`Iterator`、C# 的 `IEnumerable` 与 `IEnumerator`。生成器（`yield`）更是把迭代器的“惰性求值”能力带进了函数——生成器按需产出一个元素，内存占用从 O(n) 降到 O(1)。这正是迭代器模式的终极胜利：它如此成功，以至于成为语言的语法。</span>

**辨析｜易错点：** 迭代器 ≠ 索引循环。索引循环（如 `for (i = 0; i < n; i++)`）依赖集合“可随机访问 + 已知长度”的内部假设；迭代器只要求“逐个给出元素”。对链表、树、无限流（惰性序列），迭代器是唯一通用的遍历方式。判断标准：**遍历逻辑能否与集合内部结构解耦？** 能，就用迭代器。

## 3 解释器 vs 迭代器

| 维度 | 解释器 | 迭代器 |
| --- | --- | --- |
| 核心 | 用类结构表示文法并求值 | 统一遍历集合、隐藏内部 |
| 应用 | 小语言、表达式、规则引擎 | 所有集合遍历、生成器 |
| 关键机制 | 文法→类→递归 interpret | Iterator 接口 + 惰性求值 |
| 现代形态 | 解析器生成器、AST 库 | 语言内建 for-each、yield |
| 代价 | 类爆炸、解析复杂 | 弱（已被语言吸收） |

**辨析｜易错点：** 两个模式分别面向"读（解析）"与"走（遍历）"，共同点是都提供"统一的接口面对复杂内部"。解释器让客户端面对"语言"，迭代器让客户端面对"序列"——抽象的目标不同，别混。

## 4 数值算例：为一个小表达式搭解释器

把解释器跑一个最小实例。需求：支持含 `+`、`-`、括号与变量的简单算术表达式求值，如 `(a + 2) * b`。

**词法（token 化）**：把字符串切成记号——`(`、`)`、`+`、`*`、`a`、`2`、`b`。
**语法（AST 构建）**：递归下降或栈式解析，把记号组织成一棵语法树：`*` 节点下挂 `+` 节点（左 `a`、右 `2`）与 `b`。
**求值（解释）**：对每个语法树节点定义 `evaluate(环境)`——数字节点返回字面值，变量节点查环境表，`+` 节点返回两子树求值之和，`*` 同理。传入环境 `{a: 3, b: 4}`，则 `(3+2)*4 = 20`。

这里的"解释器"就是**把语法树结构映射为求值行为**：新增一种运算符（如取负 `-x`）= 新增一个语法节点类 + 它的 `evaluate` 方法，解析器无需改动——这正是解释器模式"语法可扩展"的收益。代价也很明显：**解释执行比编译慢几个数量级**，所以解释器模式只适合"小语言、规则灵活、无需极致性能"的场景。

**辨析｜易错点：** 别把"解释器模式"理解成"写一个编译器"。解释器模式针对的是**"领域内的小语言"**——配置表达式、规则引擎、查询语法——而不是通用编程语言。判断标准：**这个语言有几种"语句"？** 十几种以内、且常变，解释器划算；上百种，就该走真正的编译工具链。

## 5 术语速查表

| 术语 | 一句话定义 | 关键要点 |
| --- | --- | --- |
| 语法树 | 表达式的树形结构 | 叶子是数字/变量，内部节点是运算符 |
| 解释 | 遍历语法树求值 | 与编译相对，逐节点执行 |
| 迭代器 | 顺序访问集合而不暴露内部结构 | 惰性求值，统一接口 |
| 外部迭代器 | 客户端主动调用 next() | 控制权在客户端 |
| 内部迭代器 | 迭代逻辑封装在容器内 | 控制权在容器 |

## 6 常见误区速查

解释器与迭代器都是"小而有用"的模式，误用集中在三个地方：

**把解释器当成通用解析方案**：系统的"语言"其实固定不变，却先搭好解释器框架。判据：**语法会不会真的扩展？** 几年都不新增一条语法规则，用简单的硬编码解析更省。
**迭代器只在"集合"里用**：迭代器模式的精髓是"把遍历抽象出来"——它也能用在文件行遍历、数据库游标、惰性生成的无限序列上。**凡是"有一个序列要按顺序访问"的地方，都值得考虑迭代器，而不只是内存里的 list。**
**混淆"迭代器"与"生成器"**：生成器是迭代器的**一种高效实现**（惰性、状态保存于函数），两者解决的问题相同，实现层次不同。用编程语言自带语法（如 Python 的 `for`、迭代协议）就已经是在用迭代器模式，不必自己再造轮子。

**辨析｜易错点：** 判断迭代器用得好不好，看一句话：**"客户端能不能不关心集合内部结构就遍历它？"** 能——遍历被正确抽象；不能——客户端被绑死在具体集合类型上，换个数据结构就要改遍历代码。这正是迭代器"隐藏结构、统一接口"的全部意义。

**辨析｜易错点：** 解释器的性能困境值得一个数字。对一个含 1000 个节点的表达式，解释器逐节点虚拟分派求值，常比一段手写的直接计算慢 10–100 倍；但对"规则变化频繁、每次只处理少量表达式"的领域（如优惠规则、查询条件），这点开销换来的是"改规则不用改代码"。**用解释器的判断标准从来不是"快不快"，而是"规则会不会变、变起来贵不贵"。**

## 7 小结

- **解释器**用类结构表示文法、递归求值，适用于可文法化的小语言。
- 解释器的现代实践是解析器生成器与 AST 库；模式的价值在"文法-类-求值"的对应。
- **迭代器**提供统一遍历、隐藏集合内部，支持惰性求值。
- 迭代器已成为语言内建特性（for-each、yield），是模式被语法吸收的典范。
- 解释器管"读语言"，迭代器管"走结构"——目标不同。
- 两个模式都服务"小而灵活"的场景：语法规模小用解释器，集合访问要统一用迭代器。
- 判断解释器是否划算：问"规则会不会变、变起来贵不贵"，而不是问"快不快"。
- 迭代器的判据：客户端能否不关心集合内部结构就完成遍历——能，遍历才被正确抽象。
