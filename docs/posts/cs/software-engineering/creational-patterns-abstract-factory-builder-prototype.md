## 为什么从抽象工厂开始

上一节讲了单例与工厂方法，本节补齐创建型其余三个：**抽象工厂**（一系列相关对象的统一创建）、**建造者**（复杂对象的分步构造）、**原型**（用克隆代替构造）。三者解决"创建"问题的三个不同侧面——"系列"、"步骤"、"复制"。

## 1 抽象工厂：创建一"族"相关对象

**抽象工厂（Abstract Factory）**：提供一个接口，用于创建**一系列相关或相互依赖的对象**，而不指定它们的具体类。

结构：抽象工厂接口声明一组创建方法（如 `createButton()`、`createTextField()`），每个具体工厂（**WindowsFactory**、**MacFactory**）返回一整族配套产品（Windows 风格按钮+输入框、Mac 风格按钮+输入框）。

适用场景：**需要保证"配套一致性"**——比如跨平台 UI 组件、不同数据库的访问对象。调用方只依赖抽象工厂与抽象产品，不关心当前是哪个平台/哪种实现。<span class="marginnote">抽象工厂与工厂方法的分工：<strong>工厂方法</strong>管"单个产品的类型选择"，<strong>抽象工厂</strong>管"一族产品的整体一致性"。GUI 框架是经典例子——切换主题（Windows → Mac）时，按钮、菜单、滚动条必须整套换，抽象工厂让这套换在"换工厂"一处完成。新增产品（加一种组件）会改动抽象工厂接口——这是它的主要代价（OCP 在"产品维度"受限）。</span>

**辨析｜易错点：** 抽象工厂与工厂方法别混淆——工厂方法**一个方法一个产品**；抽象工厂**一组方法一族产品**。抽象工厂常"用工厂方法实现"（每个创建方法内部用工厂方法），但职责范围不同：一个是"选类型"，一个是"保配套"。

## 2 建造者：复杂对象的分步构造

**建造者（Builder）**：将复杂对象的**构造过程**与它的**表示**分离，使同样的构造过程能创建不同的表示。

结构：**Director**（导演）控制构造步骤顺序，**Builder** 接口定义各步骤（`buildPartA()`、`buildPartB()`），具体 **ConcreteBuilder** 实现不同表示（如 **TextBuilder**、**HTMLBuilder**），最终 **Product** 产出成品。

典型流程：`Director.construct(builder)` → `builder.buildPartA()` → `builder.buildPartB()` → `builder.getResult()`（返回 **Product**）。

**辨析｜易错点：** 建造者 ≠ 工厂。工厂**一步到位**返回对象；建造者**分步设置**、步骤可灵活组合，适合对象字段多、构造参数混乱的场景。现在很多语言用"链式调用"（`builder.setA(...).setB(...).build()`）实现了建造者思想，让复杂对象的构造清晰可读——比动辄十几个参数的构造方法好得多。判断标准：**构造是否需要"分步 + 可选步骤"？** 需要则建造者，否则工厂更简单。

## 3 原型：用克隆代替构造

**原型（Prototype）**：通过**复制现有实例**来创建新对象，而不是通过 `new` 构造。

适用场景：**创建成本高或构造复杂**的对象（深拷贝大数据结构），或需要"基于某个模板微调"（复制一个默认配置再改两项）。核心机制是 `clone()`（浅拷贝/深拷贝需按需实现）。<span class="marginnote">原型的现代使用往往是<strong>隐式的</strong>：JSON 的 `JSON.parse(JSON.stringify(obj))`、数组的 `slice()`、配置的"复制默认值再覆盖"都是原型思想。它的权衡是<strong>拷贝语义</strong>：浅拷贝共享引用（改一个影响另一个），深拷贝成本高。用原型前必须想清楚"复制到什么深度"——这是它最常出 bug 的地方。</span>

**辨析｜易错点：** 原型 ≠ 简单复制。复制本身简单，**原型模式的要点是"让复制成为创建的主要途径"**——调用方不 `new` 而是 `clone()` 一个原型。如果创建成本不高，直接 `new` 更简单，不必为了"用模式"而克隆。

## 4 三种模式的对比

| 维度 | 抽象工厂 | 建造者 | 原型 |
| --- | --- | --- | --- |
| 回答的问题 | 一族对象怎么配套 | 复杂对象怎么分步造 | 新对象怎么低成本复制 |
| 关键机制 | 一族创建方法 | 步骤方法 + 导演 | clone() |
| 典型场景 | 跨平台 UI、数据库族 | 复杂配置对象 | 大对象、模板复制 |
| 主要代价 | 加产品要改接口 | 类数量多 | 拷贝语义陷阱 |

**辨析｜易错点：** 五个创建型模式常被放在一起考"选哪个"——决策口诀：**看变化点**。变化在"单个类型"用工厂方法；在"一族配套"用抽象工厂；在"构造步骤"用建造者；在"复制成本"用原型；在"全局唯一"用单例。**先找变化点，再选模式**，而不是反过来。

## 5 实战：三个创建型模式的分工

把抽象工厂、建造者、原型放进同一个真实系统——**跨平台 UI 框架**，看它们各管什么。

- **抽象工厂**：创建"一组配套产品"。`GuiFactory` 有 `createButton()`、`createCheckbox()`，`WindowsFactory`、`MacFactory` 各产出一套配套控件。客户端只认 `GuiFactory` 接口，换平台 = 换工厂，**整组产品的配套性由工厂保证**（Windows 按钮不会配 Mac 复选框）。
- **建造者**：创建"构造过程复杂、分步骤的对象"。一个报表对象要依次设置标题、表头、数据、样式——`ReportBuilder` 一步步 `setTitle()`、`setData()`、`setStyle()`，最后 `build()`。**建造者把"复杂对象的构造步骤"从客户端剥离**，新增一种报表类型 = 新增一个 builder。
- **原型**：创建"代价高、需要复制现有对象"的对象。深拷贝一份复杂的图表配置作为起点，再微调——**原型让"创建"变成"复制 + 调整"**，避免重新构造全部默认值。

**辨析｜易错点：** 三个模式都解决"创建"，但抓手不同：抽象工厂管**配套**（一组产品），建造者管**步骤**（复杂构造），原型管**代价**（复制而非重建）。判断标准：**"我要创建的是什么关系？"** 配套产品组用抽象工厂、分步复杂对象用建造者、贵对象快速复制用原型。三者在"创建"这个总主题下各司其职，选错会直接造成过度设计。

## 6 数值对比：创建模式消除的重复

用一个数量级感受抽象工厂的收益。设系统有 3 种平台 × 5 种控件：

- **不用抽象工厂**：客户端里每处 `if (platform == Windows) new WindowsButton()`……控件创建逻辑散落在 N 个调用点，每新增一个平台，所有调用点都要改。
- **用抽象工厂**：每平台一个工厂类，客户端只调 `factory.createButton()`。**新增平台 = 新增一个工厂 + 一组产品类，调用点零改动**；控件创建从"散布"收拢为"每平台一处"。

这个"从 N 处分散到 1 处集中"的变化，正是抽象工厂降低耦合的量化体现——它把"平台"这个变化维度隔离在工厂层。**创建逻辑集中一处，是三种创建型模式的共同收益。**

## 7 三个模式的决策对照

把三个创建型模式放进一张决策表，选型时直接查：

| 你的处境 | 用哪个 | 一句话理由 |
| --- | --- | --- |
| 需要创建"一组配套产品" | 抽象工厂 | 保证配套性、换组即换工厂 |
| 对象构造复杂、分步骤 | 建造者 | 构造步骤剥离、可复用 |
| 复制现有对象比重建便宜 | 原型 | 复制+微调，避免重造默认值 |
| 只是单一产品、构造简单 | 工厂方法/直接 new | 不需要过度设计 |
| 需要全局唯一实例 | 单例（配合第 4 章） | 唯一性保证，但别当隐藏全局 |

**辨析｜易错点：** 创建型模式最容易犯的错是"为创建而创建"——构造很简单（一个 `new` 就够）也要套抽象工厂。判据回到第 12 章"问题优先"：**"产品种类会不会真的增长？配套关系是否真的存在？"** 不增长、不配套，直接用最直白的构造。创建型模式的价值在"创建逻辑会随变化扩散"时兑现，而不是作为"专业感"的装饰。

**一个记忆锚点：** 抽象工厂管"一组产品怎么配"、建造者管"一个复杂对象怎么造"、原型管"一个贵对象怎么复制"——**三个模式，三个"创建痛点"**。对照痛点选模式，比背结构图可靠得多。

## 8 术语速查表

| 术语 | 一句话定义 | 关键要点 |
| --- | --- | --- |
| 抽象工厂 | 创建一组配套产品的工厂 | 保证产品族配套 |
| 产品族 | 属于同一套方案的产品集合 | 如 Windows 按钮+复选框 |
| 建造者 | 分步构造复杂对象 | 构造步骤与对象分离 |
| 原型 | 复制现有对象而非重建 | 深拷贝 + 微调 |
| 克隆 clone | 原型模式的核心操作 | 深浅拷贝要分清 |

**辨析｜易错点：** 原型模式的深浅拷贝是最经典的坑：**浅拷贝只复制引用，共享内部对象**；对一个含列表、嵌套对象的图表原型做浅拷贝，改一个副本会污染所有副本。**原型必须实现深拷贝（或不可变成员共享）**，否则"复制+微调"会变成"复制+连锁改坏"。判断标准：克隆后修改副本，原对象是否受影响？不受——深拷贝对了；受影响——浅拷贝泄漏了。

## 8 小结

- **抽象工厂**创建一族相关对象，保证配套一致性；代价是加产品要改接口。
- **建造者**把构造过程与表示分离，分步构造复杂对象；链式调用是其现代形态。
- **原型**用克隆代替构造，适合高成本对象与模板复制；警惕拷贝深度。
- 工厂方法管"选类型"，抽象工厂管"保配套"，建造者管"分步骤"，原型管"低成本复制"。
- 创建型模式的决策口诀：**先找变化点，再选模式**。

- 抽象工厂管"配套产品组"、建造者管"复杂构造步骤"、原型管"贵对象快速复制"。
- 选型口诀：配套用抽象工厂、分步用建造者、复制用原型、简单直接 new。
- 创建模式是"问题优先"：产品不增长、无配套，就别为模式而模式。
- 数据对比：抽象工厂让"新增平台"从改 N 个调用点变为 0 个——变化被隔离在工厂层。
- 三个模式共同收益：把"怎么创建"收拢到一处，让"用"与"造"解耦。
