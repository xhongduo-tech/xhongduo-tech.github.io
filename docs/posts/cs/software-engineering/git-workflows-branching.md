## 为什么从 Git 工作流开始

上一节说"Git 没有唯一真相源，工作流靠约定"。这一节就讲最流行的两套约定：**Git Flow**（面向版本发布、分支严谨）与 **GitHub Flow**（面向持续交付、极简分支）。它们回答同一个问题：**团队多人并行开发时，怎么组织分支、怎么合并，才能既不冲突又保持主干稳定？**

## 1 分支与合并的基础概念

- **分支（branch）**：独立开发线，从某提交分出。
- **合并（merge）**：把分支变更并入目标分支，分**快进合并（fast-forward）**与**三路合并（merge commit）**。
- **变基（rebase）**：把分支的基点移到最新提交上，历史更线性（但改写历史要谨慎）。
- **拉取请求（Pull Request, PR）**：GitHub 的协作机制——在合并前发起请求，供**代码评审**与讨论（第 14 章）。

**辨析｜易错点：** merge 与 rebase 是 Git 新手最困惑的选择：**merge 保留"分叉并汇合"的真实历史**（记录"这是一条功能分支并进来的"），**rebase 让历史线性**（像是直接在当前主线上一路提交）。原则：**合并到主干用 merge（保留历史真实），整理自己的分支用 rebase（历史干净）**。已经推送分享的分支**不要 rebase**——改写共享历史会害惨协作者。

## 2 Git Flow：严谨的版本发布流

**Git Flow** 用**多分支体系**管理从开发到发布的完整流程：

- **main / master**：始终可发布的稳定版本。
- **develop**：集成的开发主干——功能都合到这里。
- **feature/* 分支**：从 develop 分出，开发单个功能，完成后**合回 develop**。
- **release/* 分支**：从 develop 分出，做发布前准备（修 bug、版本号），完成后**合回 develop 与 main**。
- **hotfix/* 分支**：从 main 分出，紧急修复线上 bug，完成后**合回 main 与 develop**。

<span class="marginnote">Git Flow 的优雅在于"<strong>每条分支都有明确职责</strong>"：feature 管开发、develop 管集成、release 管发布准备、hotfix 管紧急修复、main 管稳定。它的代价是<strong>分支多、流程重</strong>——每发一版要处理多个分支的合并。Git Flow 适合<strong>版本化发布</strong>的产品（如软件发行版、需长期维护多版本），对应第 2 章的版本化发布节奏。</span>

## 3 GitHub Flow：极简的持续交付流

**GitHub Flow** 把分支策略砍到极致，只有两条规则：

1. **main 分支始终可部署**——任何时刻 main 都是健康的。
2. **一切改动都从 main 开分支，做完合回 main**——没有 develop、没有 release、没有 hotfix。

流程：**从 main 开 feature 分支 → 开发 → 提 PR → 评审 → 合并回 main → 自动部署**。

GitHub Flow 的哲学：**把"发布准备"从分支流程中拿掉，交给 CI/CD**（第 13 章）——主干始终可部署，发布就是"部署当前 main"。它适合**持续部署**的 Web 产品（随时上线、快速迭代）。

**辨析｜易错点：** Git Flow vs GitHub Flow 的选择，本质是"**发布节奏**"的选择——**需要精细管理版本发布（多版本并存、发布窗口）用 Git Flow；追求持续部署（随时上线）用 GitHub Flow**。很多团队犯的错是"选 Git Flow 却做着持续部署的事"（流程重、拖慢节奏），或"用 GitHub Flow 却需要多版本维护"（main 撑不住多版本）。**流程要与发布节奏匹配**，而不是照搬流行。

## 4 分支策略的核心纪律

无论选哪种 Flow，几条**通用的分支纪律**不变：

**主干始终可部署/可发布**：main 永远健康，坏的改动不允许进主干。
**分支尽量小、尽量短**：大分支合并冲突爆炸，小分支小步快跑（呼应第 9 章"小步"）。
**合并前必须通过 CI**：测试不绿不合并（第 13 章持续集成）。
**合并前必须评审**：PR 评审是质量闸门（第 14 章代码评审）。
**保护主干分支**：禁止直接向 main 推送，只能通过 PR 合并。

**辨析｜易错点：** 分支策略最容易失败的场景是"**分支太久没合并**"——一个 feature 分支开了两个月，main 已经走了很远，合并时冲突海量、谁也看不懂。**分支的寿命要短**（几天内合回主干），这是"持续集成"的核心纪律——**频繁集成，冲突才小**（第 8 章集成测试策略）。<span class="marginnote">分支策略与测试策略（第 8 章）、代码评审（第 14 章）、CI/CD（第 13 章）四者是一套互相咬合的系统：<strong>分支定义"改动怎么组织"，评审定义"改动怎么把关"，CI 定义"改动怎么验证"，CD 定义"改动怎么上线"</strong>。单学分支策略而不配评审与 CI，主干照样会被烂代码污染。成熟团队把这四件事当作一个整体设计——这就是"工程基础设施"。</span>

## 5 实战：三种工作流选型对照

把分支策略放在一起，按团队规模与发布节奏选型：

| 工作流 | 核心机制 | 适合团队 | 特点 |
| --- | --- | --- | --- |
| Git Flow | 长驻 develop + 特性分支 + 发布分支 | 版本化发布、多版本维护 | 严谨但流程重 |
| GitHub Flow | 一个 main + 短命特性分支 | 持续部署的敏捷团队 | 简单轻量 |
| GitLab Flow | main + 环境分支/发布分支 | 需要环境/版本标签 | 折中方案 |

**辨析｜易错点：** 选型不是"越新越好"。**Git Flow 的"重"在持续部署团队里是负担**（每个发布都要过 release 分支的仪式），而 GitHub Flow 的"轻"在"必须固定版本号交付客户"的场景里又不够用。判断标准两条：**多久发一次版？是否需要同时维护多个线上版本？** 高频持续部署选轻的，低频版本化交付选重的。**分支策略要匹配发布节奏，而不是匹配流行度。**

## 6 分支策略背后的工程纪律

分支策略不是"画图"，背后是三件硬纪律：

**分支保护**：main/develop 禁止直接推送，必须走合并请求（MR/PR）+ 评审（第 14 章）——**保护分支是把"无人把关的合并"变成"可评审的变更"**。
**小步合并**：特性分支尽量短命（几天内合并），避免"大杂烩分支"——分支越长，合并冲突越多，这正是第 13 章 CI 消灭的"集成地狱"在分支层的重演。
**删除善后**：合并后删除特性分支，避免"僵尸分支"堆积——**分支是临时的协作文档，不是永久的代码存档**（历史由提交与标签记录，不是由分支记录）。

**辨析｜易错点：** 分支策略最容易翻车的地方是"**分支很多但从不保护**"——图上有几十条分支，实际却没人走评审、主线随意直推。**分支策略的价值 80% 在"保护与纪律"，20% 在"画分支图"**。把分支保护、小步合并、删除善后三条纪律立住，无论选哪种命名风格，团队都不会乱。

## 7 分支策略与版本控制的整体观

分支策略不是孤立的"画图课"，它和版本控制的整体设计咬合：

- **分支管"并行开发"**：多人同时改不同特性，靠分支隔离。
- **标签/基线管"发布版本"**：发布的快照用 tag 记录，可随时回滚（第 12 章基线）。
- **合并记录管"协作历史"**：merge 提交记录"谁把什么并进了哪"，配合评审（第 14 章）与 CI（第 13 章）形成完整链路。

**辨析｜易错点：** 一个常见的误解是"分支越多=协作越强"。实际相反：**分支越多、合并越难，冲突概率越高**。成熟的团队倾向于"小分支、短生命周期、频繁合并主线"——让 main 保持"随时可发布"的状态，正是第 13 章持续交付的前提。**分支策略的目标是"让主线永远稳定可发布"，而不是"把每个人的工作隔离到永远"。**

**一个自查清单：** 检查团队的分支实践：**主线能否随时发布？特性分支是否短命？合并是否走评审+CI？删除分支是否及时？** 四个"是"，分支策略才是健康的——否则就回到了"分支堆成山、合并靠运气"的老路。

## 8 小结

- 分支与合并：**merge 保留真实历史，rebase 让历史线性**；共享分支不要 rebase。
- **PR** 是合并前的评审与讨论机制。
- **Git Flow**：main / develop / feature / release / hotfix 多分支体系，适合**版本化发布**。
- **GitHub Flow**：只有 main + 功能分支，靠 CI/CD 保证主干可部署，适合**持续部署**。
- Flow 的选择匹配**发布节奏**：要版本管理用 Git Flow，要随时上线用 GitHub Flow。
- 通用纪律：**主干可部署、分支短小、合并前过 CI、过评审、保护主干**。

- 分支策略要匹配发布节奏：高频持续部署选轻的，低频版本化交付选重的。
- 分支保护+小步合并+删除善后三件套，比画分支图更重要。
- 分支目标：主线永远稳定可发布——这是持续交付（第 13 章）的前提。
- 分支管并行、标签管版本、合并管历史：三者咬合才是完整的版本控制观。
- 自查四问：主线可发布、分支短命、合并走评审+CI、删除及时。
- 三种工作流对照：Git Flow 重、GitHub Flow 轻、GitLab Flow 折中——按发布节奏选。
- 保护分支 + 小步合并 + 删除善后，是比"选哪种命名"更重要的纪律。
- 分支策略 80% 的价值在保护与纪律，20% 在画图。
- 一句话记忆：分支管并行、标签管版本、合并管历史，三者构成版本控制整体观。
