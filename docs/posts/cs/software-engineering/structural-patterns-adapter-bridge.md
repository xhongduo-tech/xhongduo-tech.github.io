## 为什么从适配器与桥接开始

结构型模式共七个（适配器、桥接、组合、装饰、外观、享元、代理），关注"**类与对象如何组合成更大的结构**"。这一节讲前两个：**适配器**（让不兼容的接口配合工作）与**桥接**（把抽象与实现分离，让两者独立变化）。它们都处理"接口不匹配/抽象与实现纠缠"的问题，但解法不同。

## 1 适配器：让不兼容的接口配合

**适配器（Adapter）**：将一个类的接口转换成客户期望的另一个接口，使原本因接口不匹配而无法协作的类能一起工作。

结构：`Target`（客户期望的接口）、`Adaptee`（已有的不匹配实现）、`Adapter`（转换者——实现 Target，内部调用 Adaptee）。

**辨析｜易错点：** 适配器有两种实现——**对象适配器**（组合：Adapter 持有 Adaptee）与**类适配器**（继承：Adapter 继承 Adaptee）。对象适配器更灵活（不绑定继承）、更常用；类适配器在"需要覆盖 Adaptee 行为"时才值得。判断标准：**组合优于继承**（第 4 章），默认选对象适配器。

适用场景：**接入遗留系统或第三方库**——老代码的接口与新系统不匹配，用适配器包一层，新系统代码不改、老系统不动。<span class="marginnote">适配器在现实中的例子：电源转换插头、USB-C 转 HDMI。软件里的典型是"把第三方支付 SDK 的接口适配成自己系统的支付接口"——这样换支付供应商时只换适配器，业务代码不变。注意适配器与<strong>外观（Facade）</strong>的区别：适配器是"转换接口"，外观是"简化接口"——一个为了兼容，一个为了简化。</span>

## 2 桥接：把抽象与实现分开变化

**桥接（Bridge）**：将**抽象部分**与**实现部分**分离，使它们可以独立地变化。

结构：抽象层有 `Abstraction`（高层逻辑）与 `Implementor`（实现接口），`Abstraction` 持有 `Implementor` 的引用（组合），两者各有独立继承树——抽象维度扩展不影响实现维度，反之亦然。

经典例子：**图形与绘制**。抽象维度是"形状"（圆形、方形、三角形），实现维度是"绘制方式"（矢量、光栅）。不用桥接时，"圆形+矢量"、"圆形+光栅"……每个组合一个类，$3 \times 2 = 6$ 个类；用桥接，形状类 3 个 + 绘制类 2 个，$3 + 2 = 5$ 个类，且新增一种形状或绘制方式，各自加一个类即可，互不影响。<span class="marginnote">桥接解决的正是<strong>"多维变化"的组合爆炸</strong>。类数量从"笛卡尔积"降到"算术和"。判断何时用桥接：<strong>系统要沿两个（或多个）正交维度独立扩展</strong>——形状与绘制、平台与业务、设备与驱动。如果只有一个维度在变，桥接就是过度设计。</span>

**辨析｜易错点：** 桥接与适配器的区别常被混淆：**适配器让"已存在的"两个不匹配接口配合**（事后补救）；**桥接是"设计时就分离"抽象与实现**（事前规划）。适配器改"不兼容"，桥接拆"纠缠"——一个翻译，一个分家。

## 3 适配器 vs 桥接

| 维度 | 适配器 | 桥接 |
| --- | --- | --- |
| 目的 | 让不匹配的接口协作 | 让抽象与实现独立变化 |
| 时机 | 事后（已有不兼容代码） | 事前（设计时分离） |
| 类比 | 转换插头 | 遥控器与电视解耦 |
| 结构 | Target + Adaptee + Adapter | Abstraction + Implementor |
| 主要收益 | 兼容存量代码 | 消解多维变化的组合爆炸 |

**关键判断：是"接口不匹配"（适配器）还是"两个维度会独立变化"（桥接）？** 前者用适配器，后者用桥接。

## 4 小结

- **适配器**把不匹配的接口转成客户期望的接口，用于接入遗留系统与第三方库。
- 对象适配器（组合）默认优于类适配器（继承）。
- **桥接**把抽象与实现分离，让两个维度独立扩展，消解组合爆炸。
- 桥接在"多维正交变化"时用，单维变化时是过度设计。
- 适配器管"不兼容"（事后翻译），桥接管"纠缠"（事前分离）。
- 结构型模式的共同主题：**用组合调整结构，让变化被隔离**。
