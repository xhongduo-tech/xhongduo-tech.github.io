## 为什么从适配器与桥接开始

结构型模式共七个（适配器、桥接、组合、装饰、外观、享元、代理），关注"**类与对象如何组合成更大的结构**"。这一节讲前两个：**适配器**（让不兼容的接口配合工作）与**桥接**（把抽象与实现分离，让两者独立变化）。它们都处理"接口不匹配/抽象与实现纠缠"的问题，但解法不同。

## 1 适配器：让不兼容的接口配合

**适配器（Adapter）**：将一个类的接口转换成客户期望的另一个接口，使原本因接口不匹配而无法协作的类能一起工作。

结构：**Target**（客户期望的接口）、**Adaptee**（已有的不匹配实现）、**Adapter**（转换者——实现 Target，内部调用 Adaptee）。

**辨析｜易错点：** 适配器有两种实现——**对象适配器**（组合：Adapter 持有 Adaptee）与**类适配器**（继承：Adapter 继承 Adaptee）。对象适配器更灵活（不绑定继承）、更常用；类适配器在"需要覆盖 Adaptee 行为"时才值得。判断标准：**组合优于继承**（第 4 章），默认选对象适配器。

适用场景：**接入遗留系统或第三方库**——老代码的接口与新系统不匹配，用适配器包一层，新系统代码不改、老系统不动。<span class="marginnote">适配器在现实中的例子：电源转换插头、USB-C 转 HDMI。软件里的典型是"把第三方支付 SDK 的接口适配成自己系统的支付接口"——这样换支付供应商时只换适配器，业务代码不变。注意适配器与<strong>外观（Facade）</strong>的区别：适配器是"转换接口"，外观是"简化接口"——一个为了兼容，一个为了简化。</span>

## 2 桥接：把抽象与实现分开变化

**桥接（Bridge）**：将**抽象部分**与**实现部分**分离，使它们可以独立地变化。

结构：抽象层有 **Abstraction**（高层逻辑）与 **Implementor**（实现接口），**Abstraction** 持有 **Implementor** 的引用（组合），两者各有独立继承树——抽象维度扩展不影响实现维度，反之亦然。

经典例子：**图形与绘制**。抽象维度是"形状"（圆形、方形、三角形），实现维度是"绘制方式"（矢量、光栅）。不用桥接时，"圆形+矢量"、"圆形+光栅"……每个组合一个类，$3 \times 2 = 6$ 个类；用桥接，形状类 3 个 + 绘制类 2 个，$3 + 2 = 5$ 个类，且新增一种形状或绘制方式，各自加一个类即可，互不影响。<span class="marginnote">桥接解决的正是<strong>"多维变化"的组合爆炸</strong>。类数量从"笛卡尔积"降到"算术和"。判断何时用桥接：<strong>系统要沿两个（或多个）正交维度独立扩展</strong>——形状与绘制、平台与业务、设备与驱动。如果只有一个维度在变，桥接就是过度设计。</span>

**辨析｜易错点：** 桥接与适配器的区别常被混淆：**适配器让"已存在的"两个不匹配接口配合**（事后补救）；**桥接是"设计时就分离"抽象与实现**（事前规划）。适配器改"不兼容"，桥接拆"纠缠"——一个翻译，一个分家。

## 3 适配器 vs 桥接

| 维度 | 适配器 | 桥接 |
| --- | --- | --- |
| 目的 | 让不匹配的接口协作 | 让抽象与实现独立变化 |
| 时机 | 事后（已有不兼容代码） | 事前（设计时分离） |
| 类比 | 转换插头 | 遥控器与电视解耦 |
| 结构 | Target + Adaptee + Adapter | Abstraction + Implementor |
| 主要收益 | 兼容存量代码 | 消解多维变化的组合爆炸 |

**关键判断：是"接口不匹配"（适配器）还是"两个维度会独立变化"（桥接）？** 前者用适配器，后者用桥接。

## 4 数值算例：组合爆炸从哪来

把桥接的价值放成数字，最有说服力。假设系统要支持 $m$ 种形状、$n$ 种绘制方式，并且两者要任意组合：

- **不用桥接（继承爆炸）**：每种「形状 × 绘制」组合都要一个类，总类数为 $m \times n$；
- **用桥接（组合解耦）**：形状类 $m$ 个、绘制类 $n$ 个，总类数为 $m + n$。

以 $m = 4, n = 3$ 为例：继承方案 $4 \times 3 = 12$ 个类，桥接方案 $4 + 3 = 7$ 个类。表面只差 5 个，但再看**扩展**——每新增一种形状：继承方案要新增 $n = 3$ 个组合类，桥接方案只需新增 1 个形状类；每新增一种绘制方式同理。**类数量的增长从「乘法」降为「加法」，这正是桥接的核心收益**。<span class="marginnote">推广到三个正交维度：$l \times m \times n$ 对 $l + m + n$。维度越多、每维变体越多，桥接节省的类数量就越可观——这也解释了为什么跨平台 UI 框架（如 Qt 的「控件 × 绘制引擎」）几乎都用桥接。</span>

## 5 一个对象适配器的具体形态

对象适配器在代码里的结构很固定，值得看一遍。假设要给遗留的 `OldPaymentApi` 包一层新系统的 `PaymentGateway` 接口：

```python
class PaymentGateway:                 # Target：客户期望的接口
    def pay(self, amount): ...

class OldPaymentApi:                  # Adaptee：遗留的不匹配实现
    def charge(self, amount, memo): ...

class PaymentAdapter(PaymentGateway): # Adapter：转换者
    def __init__(self, legacy):
        self._legacy = legacy         # 持有 Adaptee（组合）
    def pay(self, amount):
        self._legacy.charge(amount, memo="adapter")  # 内部转调
```

这个形态回答了三个问题：**Target** 是客户看到的接口、**Adaptee** 是换不掉的存量代码、**Adapter** 完成「接口翻译」。换一家支付供应商时，只需新增一个 Adapter，业务代码对 `PaymentGateway` 的调用一字不改——这正是适配器「兼容存量」的价值落点。

## 6 一个选择场景：该用适配器还是桥接

把两个模式放进同一个真实项目，看"选型"是怎么发生的。假设你的团队要为多种**业务领域**（订单、库存、报表）对接多种**外部系统**（两家云、一个本地遗留系统）：

**第一步判断：接口能不能改？**
- 外部系统的接口是"已存在、改不了"的 → 这是**适配器**的场景：为每个外部系统写一个 Adapter，把它们统一成你定义的 `ExternalGateway` 接口。换新供应商 = 新增一个 Adapter，业务代码不动。

**第二步判断：会不会出现"两个维度独立扩展"？**
- 如果除了外部系统，你的**业务领域**本身也在增长（加新领域、加新操作），并且"领域 × 外部系统"的组合会爆炸 → 在适配器之上再加**桥接**：`Abstraction`（领域操作）持有 `Implementor`（外部系统接口），两个维度独立加类，组合数从乘法降为加法。

**答案常常是两者结合**：桥接负责"领域与外部系统的解耦"，适配器负责"每个具体外部系统的接口翻译"。这个例子说明，模式不是互相排斥的选项，而是可以**分层叠加**的组合语法——先判断"接口是否可改"，再判断"是否多维独立变化"。

**辨析｜易错点：** 最常见的选型错误是"拿到不匹配就上适配器、拆不开就上桥接"——没先判断"接口改不改得动"与"变化维度有几个"。**适配器的前提是"存量接口不可改"，桥接的前提是"两个正交的独立变化维度"**——前提不成立，模式就是生搬硬套。

## 7 术语速查表

| 术语 | 英文 | 一句话定义 |
| --- | --- | --- |
| 适配器 | Adapter | 把不匹配的接口翻译成客户期望的接口 |
| 对象适配器 | Object Adapter | 用组合持有 Adaptee，更灵活、更常用 |
| 类适配器 | Class Adapter | 用继承复用 Adaptee，仅在需覆盖行为时用 |
| 桥接 | Bridge | 把抽象与实现拆成两个独立维度 |
| 抽象维度 | Abstraction | 高层逻辑（如形状），持有一个 Implementor 引用 |
| 实现维度 | Implementor | 底层实现（如绘制方式），可独立扩展 |
| 组合爆炸 | Combinatorial Explosion | 多维独立变化下，类数量按乘法增长的困境 |

## 8 常见误区速查表

| 误区 | 正解 |
| --- | --- |
| "适配器 = 桥接" | 适配器改不兼容（事后翻译），桥接拆纠缠（事前分离） |
| "类适配器更好" | 对象适配器（组合）默认更灵活，类适配器仅在需覆盖行为时用 |
| "没有不匹配也套适配器" | 适配器前提是"存量接口不可改"，否则是过度设计 |
| "桥接 = 所有类都抽象" | 桥接只在两个正交维度独立扩展时值得，否则过度设计 |
| "适配器能改接口" | 适配器把接口翻译成客户期望，不改变被适配对象本身 |
| "桥接解决接口不匹配" | 桥接解决"抽象与实现纠缠"，接口不匹配是适配器的事 |
| "模式选型凭感觉" | 先问"接口改不改得动""变化维度有几个"，再选模式 |
| "组合爆炸没救" | 桥接把类数量从乘法降为加法，维度越多收益越大 |

## 9 小结

- **适配器**把不匹配的接口转成客户期望的接口，用于接入遗留系统与第三方库。
- 对象适配器（组合）默认优于类适配器（继承）。
- **桥接**把抽象与实现分离，让两个维度独立扩展，消解组合爆炸。
- 组合爆炸：$m \times n$ 对 $m + n$，维度越多桥接收益越大。
- 适配器管「不兼容」（事后翻译），桥接管「纠缠」（事前分离）。
- 结构型模式的共同主题：**用组合调整结构，让变化被隔离**。
