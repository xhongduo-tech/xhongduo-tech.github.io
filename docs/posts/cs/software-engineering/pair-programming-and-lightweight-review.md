## 为什么从结对编程开始

上一节的 PR 评审是"**异步**"的（写完再看），这一节的两种实践把质量把关**前移**：**结对编程**（两人同步写，边写边评）与**轻量级代码审查**（高频、快速、轻量的日常审查）。它们与正式评审互补，构成"从同步到异步、从轻到重"的完整评审光谱。

## 1 结对编程：两人一台机器

**结对编程（pair programming）**（极限编程 XP 的实践）：**两名程序员在同一台机器上协作完成一个任务**——一名"驾驶员（driver）"负责打字，一名"领航员（navigator）"负责思考与审视，定期互换角色。

- **驾驶员**：专注当前代码的细节——怎么把这一步写对。
- **领航员**：关注更大画面——这段代码为什么存在、下一步做什么、有没有更好的设计、哪里可能出错。

**辨析｜易错点：** 结对 ≠ "一个人写另一个人看手机"。**有效的结对是持续对话**——驾驶员与领航员频繁讨论，领航员随时可以接管键盘。另一个误解是"结对 = 效率减半"——**结对在"简单机械任务"上确实低效，在"复杂有风险任务"上反而省时**（减少返工、减少评审时间、知识即时传递）。判断标准：**这个任务"思考密度"高吗？** 高，结对值得；低（机械实现），单人更快。

## 2 结对编程的价值与变体

结对的四大价值：

- **即时评审**：边写边被审视，缺陷在产生的瞬间被发现（最极致的"左移"）。
- **知识流动**：结对是最高效的"传帮带"——新手上手、老手带教、团队知识去中心化。
- **集体代码所有权**：代码不是"某个人的"，团队人人熟悉，降低单点风险。
- **专注度提升**：有人在场，走神与偷懒都会减少。

现代变体：

- **远程结对**：共享屏幕/编辑器（VS Code Live Share）支持分布式结对。
- **导航式结对**：驾驶员长期打字，领航员轮换——适合某人不熟代码库时。
- **乒乓结对**：A 写测试、B 写实现让它通过、A 再写下一个测试——TDD 与结对的结合。

<span class="marginnote">结对与第 1 章《PSP 与结对编程》呼应——结对编程是 PSP（个人软件过程）在团队层面的延伸：<strong>PSP 管"个人如何有纪律地开发"，结对把这种纪律变成"两个人互相监督与补充"</strong>。邹欣《构建之法》特别强调结对的价值：<strong>代码不是个人财产而是团队资产</strong>——结对让"写代码的人"与"懂代码的人"重合，消灭"写的人不懂、懂的人没写"的断层。</span>

## 3 轻量级代码审查：高频快速

**轻量级代码审查（lightweight code review）**：比正式评审（第 11 章 FTR）更轻、更频繁的日常审查——**每个变更都快速过一遍**，而不是等到里程碑才大审一次。

轻量审查的形态：

**PR 评审**（上一节）：最常见，作为合并闸门。
**走查（walkthrough）**：作者带着评审者过一遍改动，讲解思路、答疑。
**工具化审查**：静态分析 + 自动化规则先过机器，人工只看机器看不出 的设计与逻辑。

**辨析｜易错点：** 轻量审查 vs 正式评审不是"二选一"而是**分级使用**：**日常小改动用轻量审查（PR 快评），关键里程碑（架构、核心模块、安全敏感代码）用正式评审（FTR 会议）**。把所有改动都拉去开正式评审会，是资源浪费；只在大里程碑评审、日常放任，是质量漏洞。判断标准：**变更的风险与重量匹配审查的形式**——风险高才上重武器。

## 4 评审光谱：从同步到异步

| 形态 | 时机 | 成本 | 反馈速度 | 适用 |
| --- | --- | --- | --- | --- |
| 结对编程 | 事中（同步） | 高 | 即时 | 复杂/高风险任务、带教 |
| 轻量 PR 审查 | 事后（异步） | 低 | 小时级 | 日常所有变更 |
| 正式 FTR | 里程碑（异步） | 高 | 天级 | 架构、关键设计 |
| 工具化审查 | 持续（自动） | 极低 | 秒级 | 规范、低级问题 |

**辨析｜易错点：** 完整的质量工程**四者并用**——工具筛低级、PR 审日常、结对攻难点、FTR 把关键。**只用一种是常见的失衡**：只靠工具漏掉设计问题，只靠 PR 漏掉结对才有的"即时纠正"，只靠 FTR 频率太低。<span class="marginnote">选择结对还是 PR 审查，业界有经典争论（"结对优于评审" vs "异步评审更高效"），但成熟结论是<strong>按任务匹配</strong>：<strong>探索性、高风险、知识不共享的任务用结对</strong>（实时思维碰撞）；<strong>常规、独立、低风险的任务用 PR 评审</strong>（异步省人时）。两者不是对手，是"同步协作"与"异步协作"两个工具，放进同一个工具箱。而邹欣提醒的更重要的一点：<strong>无论哪种形式，"让代码被至少另一个头脑看过"是不可妥协的底线</strong>——单干不评审，是质量的第一杀手。</span>

## 5 数值算例：结对的时间账

结对的成本是明摆着的——两个人在同一任务上投入时间。它值不值，要看省下了什么。给一个简化的对比：

| 场景 | 单人 + 事后 PR 评审 | 结对编程 |
| --- | --- | --- |
| 编码时间 | 10 天 | 7 天（两人一起，沟通减少返工） |
| 评审/返工时间 | 3 天（PR 往返 + 修问题） | 0.5 天（边写边审，问题当场消掉） |
| 知识传递 | 需另行安排讲解 | 结对过程即时完成 |
| 总投入（人日） | 13 | 14（约 7 天 × 2 人） |

单人路线总人日看似略少，但它没算三笔隐形成本：**缺陷晚发现的放大成本**（第 1 章"越晚越贵"）、**知识交接的额外工时**、**单点风险**（关键代码只有一人懂）。对一个复杂度高、有新人参与、团队依赖这个模块的任务，结对多花的 1 个人日，往往换来的是"少一次上线事故"——这笔账在风险高的地方尤其划算。

**辨析｜易错点：** 有人用"结对 = 两倍成本"否决结对，这是把"投入"当成了"浪费"。**结对真正的成本是"两个人暂时只产出一个人的产出"，但收益是"一次产出接近无缺陷 + 知识双人化"**。判断是否结对，不是算人均产出，而是算"返工 + 事故 + 交接"的总账。机械重复的编码（复制粘贴、批量替换）结对纯属浪费；而探索式、高风险、新人加入的任务，结对是性价比最高的投资。

## 6 核心对比表：三种审查方式的分工

| 维度 | 结对编程 | PR 评审 | 正式评审（FTR） |
| --- | --- | --- | --- |
| 时序 | 事中（同步） | 事后（异步） | 里程碑（异步） |
| 反馈速度 | 即时 | 小时级 | 天级 |
| 成本 | 高（两人全程） | 低（审一次） | 高（召集会议） |
| 发现缺陷类型 | 逻辑、设计、即时思路问题 | 逻辑、风格、接口问题 | 架构、一致性、合规问题 |
| 最适合 | 复杂、高风险、带教 | 常规日常变更 | 关键里程碑 |
| 本质 | 协作生产 | 事后把关 | 集体决策 |

## 7 常见误区速查表

| 误区 | 正解 |
| --- | --- |
| "结对 = 一人写一人看" | 有效结对是持续对话，领航员随时可以接管键盘 |
| "结对 = 效率减半" | 机械任务上确实低效，复杂高风险任务上反而省时 |
| "结对 = 每个人都必须用" | 按任务匹配：探索/高风险用结对，常规独立用 PR 评审 |
| "PR 评审能替代结对" | 结对提供即时纠正与知识流动，PR 是异步事后把关 |
| "所有变更都开 FTR" | 评审形式要与风险匹配，日常小改动用轻量审查 |
| "轻量审查 = 随便看看" | 轻量也是评审，同样要有记录与跟进，不是走过场 |
| "结对只适合新手" | 老手结对同样收益：即时评审、去中心化、减少单点 |
| "代码被看过一次就行" | "代码被另一个头脑看过"是底线，且要持续、及时 |

## 8 数值算例：结对 vs 单人的质量账

把结对与单人的质量差异算成数字。假设两个开发者 A、B 各实现同一个复杂模块：

| 指标 | 单人（A 写、B 事后评审） | 结对（A+B 一起写） |
| --- | --- | --- |
| 编码时间 | 10 天 | 8 天 |
| 事后评审/返工 | 3 天 | 0.5 天 |
| 发现的设计缺陷 | 4 个（评审时才发现） | 1 个（写的时候就纠正） |
| 知识分布 | 只有 A 懂 | A、B 都懂 |
| 总人日 | 约 13 | 约 16.5 |

**结对多花 3.5 人日，但买回"缺陷更少 + 知识双人化 + 单点风险消失"**——尤其对关键模块，一个上线后才发现的设计缺陷，返工成本远不止 3.5 人日。这就是"复杂高风险任务上结对反而省时"的量化依据：**结对不是花双倍钱，而是用可预期的成本买更低的返工风险**。

**辨析｜易错点：** 结对的收益在"复杂、高风险、知识不共享"的任务上成立；对机械重复的编码，结对纯属浪费。**判断标准：这个任务"思考密度"高吗？** 高，结对；低（简单实现、批量修改），单人 + PR 评审更划算。

## 9 小结

- **结对编程**：驾驶员+领航员同步协作，边写边审——最极致的"左移"。
- 结对价值：**即时评审、知识流动、集体所有权、专注度**；复杂任务上结对反而省时。
- 结对变体：远程结对、导航式、乒乓结对（与 TDD 结合）。
- **轻量级代码审查**：PR 评审、走查、工具化审查——日常高频的快速把关。
- 评审光谱：**结对（同步事中）→ PR（异步事后）→ FTR（里程碑）→ 工具（持续自动）**。
- 四者并用、按风险匹配；**"代码被另一个头脑看过"是不可妥协的底线**。
