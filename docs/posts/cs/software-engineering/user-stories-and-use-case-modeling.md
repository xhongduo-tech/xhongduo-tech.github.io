## 为什么从用户故事开始

需求获取得到的素材是零散的对话记录。接下来要做的是**分析**：把它们变成既能让用户看懂、又能驱动设计与测试的结构化表达。这一节介绍两种最常用的分析载体——**用户故事**（敏捷世界）与**用例**（UML 世界）。它们回答同一个问题：**系统为谁、在什么场景下、完成什么有价值的事？**

## 1 用户故事：三要素与 INVEST

**用户故事（user story）**是敏捷中需求的基本单位，标准格式是：

$$作为\ <角色>，我希望\ <功能>，以便\ <价值>$$

三个要素缺一不可：**角色**回答"为谁"，**功能**回答"做什么"，**价值**回答"为什么"。例如：「作为读者，我希望按书名模糊搜索馆藏，以便快速找到我想借的书。」<span class="marginnote">故事的价值在于<strong>提示对话</strong>：它故意写得简短模糊，目的是让团队在迭代计划会上与用户现场讨论细节，而不是把细节冻结在文档里。一句完整的需求描述 + 口头细化，胜过一份没人读的长文档。</span>

好故事要满足 **INVEST** 六条准则：

| 字母 | 含义 | 解释 |
| --- | --- | --- |
| I | Independent | 故事之间尽量独立，便于排序与并行 |
| N | Negotiable | 是协商的起点，而非冻结的契约 |
| V | Valuable | 对用户有可感知的价值 |
| E | Estimable | 团队能估计其规模 |
| S | Small | 足够小，能在单个迭代内完成 |
| T | Testable | 有明确的验收标准 |

**辨析｜易错点：** 把用户故事写成技术任务（「重构订单模块的数据库层」）是常见错误。故事必须站在**用户价值**角度；技术任务应作为实现细节挂在故事之下，而不是替代故事。

## 2 从故事到用例

**用例（use case）**是更正式的分析模型：它描述**一个参与者与系统交互以达成目标**的一组场景。用例由四部分构成：

**参与者（actor）**：与系统交互的外部角色——人、外部系统、定时器等。
**前置条件（precondition）**：用例开始前必须为真的状态。
**主成功场景（main flow）**：最典型、顺利达成目标的步骤序列。
**备选流（alternative flow）**：异常与分支路径（失败、取消、权限不足等）。

用例的经典叙事风格是「参与者执行……系统响应……」的交替步骤。例如「借书」用例的主流程：读者出示借书证 → 系统验证证件有效 → 读者提交图书 → 系统检查借阅限额 → 系统登记借出并更新库存 → 系统打印凭证。<span class="marginnote">用例与场景建模的关系：用例是<strong>场景的容器</strong>。一个用例通常包含一个主场景和多个备选场景，UML 用顺序图把每个场景画出来（见《行为建模》一节）。先故事、后场景、再用例，是一条自然的细化路径。</span>

## 3 用例图与用例文本

UML 提供**用例图（use case diagram）**，用图形把参与者与用例的关系画出来：

**角色**画成小人（stick figure），**用例**画成椭圆，**系统边界**画成方框。
参与者在方框外，用例在方框内，连线表示「参与者发起某用例」。
**include（包含）**表示子流程被复用，**extend（扩展）**表示可选分支在特定条件下插入。

用例图的价值在于**一页纸呈现系统全景**——谁和系统有哪些交互。但图只是封面，真正的细节在**用例文本（use case specification）**里。Pressman 建议用例文本至少包含：用例名、参与者、前置条件、后置条件、主流程、备选流程、业务规则。<span class="marginnote">后置条件常被忽略，但它决定测试断言：用例成功完成后系统处于什么状态。测试工程师正是靠前置/后置条件设计验证用例的测试——这是需求与测试的第一次握手。</span>

## 4 用例建模的粒度与数量

用例建模最常见的争论是**粒度**：一个用例应该多粗、多细？

**太粗**：「管理图书」把增删改查全塞进一个用例——无法测试、无法估计。
**太细**：把「输入作者姓名」「点击保存按钮」各算一个用例——信息熵极低。

实践标准：**一个用例应该对应参与者的一个有始有终、可交付价值的业务目标**。「借书」是一个目标；「输入书名」不是。<span class="marginnote">一个中型系统通常有 20–60 个用例。数量失控往往是粒度失控的征兆——当用例数量膨胀到几百个，多半是把步骤当成了用例。</span>

**辨析｜易错点：** 用例与用户故事不是二选一。敏捷项目常用故事做规划、再为复杂流程写用例文本；传统项目则直接以用例为需求主体。两者的共同内核都是**场景驱动的需求表达**——把「系统是什么」翻译成「用户与系统如何协作」。

## 5 小结

- **用户故事**用「作为……我希望……以便……」三要素表达需求，靠 INVEST 准则评判质量。
- 故事是**对话的占位符**，故意简短，细节在迭代中口头补全。
- **用例**由参与者、前置/后置条件、主成功场景与备选流构成，比故事更正式。
- **用例图**呈现系统全景，**用例文本**承载真实细节，二者互补。
- 用例粒度以「参与者的完整业务目标」为准，避免过粗或过细。
- 故事与用例的**共同内核是场景驱动**：把系统需求翻译成「人与系统如何协作」。
