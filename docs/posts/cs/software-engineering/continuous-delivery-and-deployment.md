# 持续交付与持续部署（CD）

<div class="epigraph">

## 为什么从 CD 开始

CI 保证了"每次提交都被验证"，但验证完的制品**怎么到用户手里**？这一节的两个概念回答这个问题：**持续交付（Continuous Delivery）**——制品随时可发布；**持续部署（Continuous Deployment）**——通过测试的改动自动发布到生产。它们的区别正是"一键发布"与"自动发布"。

## 1 从 CI 到 CD：验证之后的旅程

- **CI** 止于"验证"：提交 → 构建 → 测试 → 产出**已验证的制品**。
- **CD** 接管"交付"：已验证的制品 → 部署到测试/预发环境 → **随时可发布**。

**辨析｜易错点：** CI 与 CD 最常被混为一谈——**"我们上了 CI/CD"**经常只做了 CI。判断标准：**你的流水线是否把制品自动部署到了测试/预发环境，并且"一键就能发布到生产"？** 没有，就还停在 CI。<span class="marginnote">一句话分清三者：<strong>CI 问"这次提交坏了没有"，持续交付问"这个版本随时能发吗"，持续部署问"这版改动要不要人点按钮才上线"</strong>。CI 是验证，持续交付是"可发布的能力"，持续部署是"发布动作的自动化"。</span>

## 2 持续交付：随时可发布的资产

**持续交付（Continuous Delivery, CD）**：**每个通过测试的版本都具备"可发布到生产"的能力**——发布与否由人工决策（按业务节奏点按钮）。

核心价值：

**发布成为低成本动作**：不再需要"发布准备周"——每次提交都产出"可发布版本"。
**发布是业务决策而非技术负担**：想发就发（市场时机、业务节奏），不再受"发布要准备很久"掣肘。
**小步发布**：每次发布的内容小，风险小，回滚简单（呼应 Lehman"小步"）。

## 3 持续部署：通过测试自动上线

**持续部署（Continuous Deployment）**：**通过全部测试的改动，自动部署到生产环境**——不需要人工批准，测试通过即上线。

**进一步**：把"发布决策"也自动化了——消除了最后的人工环节。
**前提**：测试要足够可靠（测试金字塔健全）、发布策略要安全（蓝绿/金丝雀）、监控要到位（出问题能快速发现与回滚）。
**适用**：Web 服务、SaaS——高频迭代、自动回滚能力强的产品。

**辨析｜易错点：** 持续部署 ≠ "没有质量把关"。它只是把"把关"从"人工决策"换成"**自动化验证 + 自动回滚**"——**没有可靠的自动化测试与回滚机制，就不该上持续部署**。判断标准：**如果自动发布的版本出问题，系统能在几分钟内自动/半自动恢复吗？** 不能，说明持续部署的基础还不成熟。<span class="marginnote">持续部署与持续交付的选择，本质是"<strong>对自动化的信任度</strong>"问题：信任测试能拦住问题 + 回滚能兜住意外，就上持续部署；需要人工把关（合规、业务节奏），就用持续交付。很多团队从持续交付起步，等测试与监控成熟后再平滑到持续部署——<strong>这是"逐步信任自动化"的成熟路径</strong>。</span>

## 4 发布策略：让自动上线更安全

无论持续交付还是持续部署，发布策略决定"上线"的安全性：

**蓝绿部署（blue-green）**：两套环境（蓝/绿），新版本部署到空闲环境，验证后切换流量——回滚就是切回去，秒级。
**金丝雀发布（canary）**：先让新版本接管少量流量，观察监控，确认健康后再逐步放量——"小规模试错"。
**滚动更新（rolling）**：逐个实例替换，服务不中断——渐进升级。
**功能开关（feature flag）**：代码先部署，功能后开放——"部署"与"发布"解耦（第 12 章）。

**辨析｜易错点：** 发布策略不是"选一个最好的"，而是**按风险与场景组合**：新功能用金丝雀（观察数据）、基础设施升级用滚动（最小冲击）、大版本用蓝绿（快速回滚）、紧急修复用"全量+立即监控"。**判断标准：发布策略是否与"出问题的代价"匹配？** 代价越高，策略越要保守。<span class="marginnote">发布策略与第 5 章高可用架构（冗余、故障转移）同源：<strong>发布策略本质是"把发布当作一次受控的故障演练"</strong>——蓝绿的金丝雀、金丝雀的逐步放量，都是"让风险以可控的方式暴露"。真正成熟的发布文化，是把"发布失败"当作正常事件来设计（有预案、能回滚、监控到位），而不是祈祷发布不出错。</span>

## 5 数值算例：流水线每省一分钟值多少钱

把 CD 的收益量化成一个具体模型。设团队每天发布一次，一次手动发布要 2 小时、自动流水线只要 15 分钟。

- **每次省下 105 分钟**；假设团队 10 人、每人月成本折合到分钟，一年约 250 个工作日，**每年省下的工时 ≈ 250 × 105 分钟 ≈ 260 小时/人**。
- 更重要的不是"省时间"，而是**缩短"从想法到上线"的周期**：手动流程下，功能写好后要排队等发布窗口（常以天计）；CD 让"合并即待发布"，周期从"天"压缩到"小时"。**周期越短，反馈越快**——需求错了、bug 藏在哪，尽早暴露，返工成本指数下降（第 11 章质量成本）。

**辨析｜易错点：** CD 常被误解为"部署得越快越好"。真正约束发布频率的不是工具，而是**信心**——你对"这次发布不会出事"有多确定。CD 的价值恰恰在于**把信心做足**：自动化测试把关、灰度发布小步放量、监控与回滚兜底。**没有这些保障的"快速发布"是鲁莽，有保障的"快速发布"才是 CD。** 所以 CD 不是 CI 之后顺手加的按钮，而是一整套"可信快速发布"的能力建设。

## 6 术语速查表

| 术语 | 一句话定义 | 关键区别 |
| --- | --- | --- |
| 持续交付 CD | 每次提交都处于"可发布"状态 | 发布是"随时可以"，不一定自动 |
| 持续部署 | 通过测试自动部署到生产 | 发布"无人按钮" |
| 部署流水线 | 构建→测试→部署的自动化链路 | 每一段都有质量门 |
| 金丝雀发布 | 先给少量用户放量新版本 | 观察后再全量 |
| 蓝绿部署 | 新旧两套环境切换 | 秒级回滚 |

## 7 部署安全的最后一公里

CD 让"发布更频繁"，但频繁不等于随便。最后一公里靠三件套兜底：

**监控（第 13 章）**：发布后立刻看关键指标——错误率、延迟、成功率。**没有监控的快速发布等于蒙眼开车**；指标异常是第一道警报。
**回滚预案（第 12 章）**：一键回滚到上一版本。**蓝绿部署让回滚从"重新部署旧版"变成"切回旧环境"**，秒级完成。
**功能开关**：把"部署"与"发布"解耦——新功能代码先部署但不激活，开关打开才对用户生效。这样即使开关后发现问题，关掉开关即可，**连回滚都省了**。

**辨析｜易错点：** 这三个兜底常被当成"上线前的临时操作"，其实它们是**CD 体系的固定组成部分**：没有监控、回滚、开关，发布频率一提上来就会出事。**CD 的正确姿势是"快发布 + 稳兜底"的组合**——发布快是为了缩短反馈，兜底稳是为了快而不慌。把这两件事绑在一起看，CD 才不是危险的自杀式冲刺，而是成熟的工程能力。

## 8 从 CI 到 CD 的进阶路径

CD 不是一步到位的，团队通常沿这条路渐进：

1. **先有 CI（第 13 章）**：提交即构建、即测试，让"代码能跑"成为每提交的默认事实。没有这个地基，CD 无从谈起。
2. **再自动部署到测试/预发布**：把"部署测试环境"从手工变成流水线的一环——这一步已经消灭了"我机器上是好的"。
3. **最后才谈自动发布到生产**：只有在监控、回滚、灰度都就位后，生产自动部署才安全。**很多团队停在第 2 步、保留"生产要人点头"的手动闸门，是完全合理的成熟选择**——发布频率与信心匹配，而不是盲目追求全自动。

**辨析｜易错点：** 这条进阶路径的启示是：**"全自动部署"不是 CD 的终点，而是 CD 能力成熟后的结果**。把顺序搞反——先上自动发布、再补监控回滚——就是在裸奔。成熟的团队会诚实地回答"我们现在的信心允许发布多快"，然后让流水线的自动化程度**跟信心走，而不是跟口号走**。CD 与其说是"速度工程"，不如说是"信心工程"。

## 8 小结

- **CI** 验证提交，**持续交付**保证"随时可发布"，**持续部署**让"发布自动化"。
- **持续交付**：通过测试的版本具备可发布能力，发布由人工按业务节奏决策。
- **持续部署**：通过测试自动上线，前提是可靠的测试与自动回滚。
- 持续部署 ≠ 无质量把关——把关从"人工决策"换成"自动化验证+回滚"。
- 发布策略：**蓝绿**（快速回滚）、**金丝雀**（小规模试错）、**滚动**（渐进升级）、**功能开关**（部署发布解耦）。
- 发布策略与风险代价匹配，成熟文化把"发布失败"当作正常事件来设计。

- 持续交付 = 随时可发布；持续部署 = 自动发布——区别在"是否要人按按钮"。
- CD 的约束是信心而非工具：测试把关、灰度放量、监控回滚，缺一不可。
- 兜底三件套：监控、回滚预案、功能开关——快发布 + 稳兜底才是完整 CD。
- 进阶路径：先 CI → 再自动部署测试/预发布 → 最后才谈生产自动发布，自动化跟信心走。
- 收益算例：每次发布省 105 分钟、周期从天压缩到小时，返工成本指数下降。
- CD 的本质是"信心工程"：发布频率与"不会出事"的确定程度匹配。
- 蓝绿/金丝雀是发布策略：切换环境秒级回滚、小步放量观察，都是信心放大器。
- 功能开关让"部署"与"发布"解耦：代码先上线、开关后生效，出问题关开关即可。
- 发布管理的底线两条：制品不可变、环境可切换——无论用哪种策略都不破。
- CD 是"速度 × 信心"的乘积：缺了任一因子，快速发布都会变成风险。
- 生产发布保留"人点头"的手动闸门是成熟选择，不必为全自动而全自动。
- 一句话收束：持续交付管"随时可发布"，持续部署管"自动发布"，监控回滚开关兜底。
