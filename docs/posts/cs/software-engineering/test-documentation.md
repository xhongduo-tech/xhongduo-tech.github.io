## 为什么从测试文档开始

自动化与 TDD 改变了测试执行，但**测试的策划与总结**仍然需要文档承载：**测试计划（test plan）**在测试开始前定义"测什么、怎么测、谁测、何时完"，**测试报告（test report）**在测试结束后回答"测了什么、发现什么、能发布吗"。这一节讲这两份关键文档的结构与用途。

## 1 测试计划：测试的"需求规格"

**测试计划（test plan）**是测试活动的纲领，IEEE 829 给出了标准结构，核心章节：

- **测试范围**：测哪些功能/模块，明确**不测**什么（范围收缩要审批）。
- **测试策略**：各级别（单元/集成/系统）测什么技术（白盒/黑盒）。
- **资源与分工**：人员、环境、工具、时间安排。
- **入口与出口准则**：什么时候开始测、测到什么程度算"测完了"。
- **风险与应急**：环境风险、进度风险及其应对。
- **交付物**：测试用例集、缺陷报告、测试报告。

**辨析｜易错点：** 测试计划最常被跳过或写空。**"入口/出口准则"是测试计划里最有工程价值的部分**——它把"测试完没完"从感觉变成判断标准：「出口准则：P0 用例 100% 通过、P1 通过率 ≥ 95%、无未关闭的严重缺陷」。没有出口准则，测试可以无限延长，也可以草草收场——两者都是灾难。

## 2 出口准则：可发布性的判断

**出口准则（exit criteria）**是"测试做完了"的操作化定义，常见维度：

- **用例执行率**：计划用例执行了百分之多少。
- **通过率**：P0/P1 用例通过比例。
- **覆盖率**：语句/分支覆盖率达标（第 8 章《测试覆盖率》）。
- **缺陷状态**：严重缺陷全部修复并验证、遗留缺陷有明确处置。

**辨析｜易错点：** "没有严重缺陷" ≠ 可以发布。"没有严重缺陷"只是必要条件，还要看**覆盖与通过率**——一个"没怎么测、所以没发现严重缺陷"的系统，出口准则照样可能"满足"。**出口准则必须是"测充分 + 测过得了"的双重标准**，不能只盯缺陷数量。

## 3 测试报告：测试的"验收报告"

**测试报告（test report）**总结测试执行结果，回答三个问题：

- **测了什么**：执行的用例范围、环境、数据。
- **发现了什么**：缺陷统计（按严重度、模块分布）、遗留问题清单。
- **结论**：是否满足出口准则、是否建议发布。

典型结构：执行摘要 → 用例执行统计 → 缺陷分析 → 覆盖率报告 → 结论与建议。<span class="marginnote">测试报告最重要的读者不是测试组，而是<strong>发布决策者</strong>——他们靠报告判断"能不能上"。因此报告的<strong>结论必须明确</strong>："建议发布""条件发布（修复某 P1 后）""不建议发布"——给结论时要有数据支撑（通过率、残留缺陷），别用"基本没问题"这种模糊话。报告让"发布决策"从拍脑袋变成看数据。</span>

## 4 从计划到报告的闭环

测试文档不是两份孤立的文件，而是**测试管理闭环**的两端：

**测试计划 → 测试执行 → 测试报告 → 缺陷分析 → 反馈修订下一轮测试计划**

测试报告里的缺陷分析（哪个模块 bug 多、哪类缺陷高发）会**反馈回下轮计划**：把测试资源向缺陷聚集处倾斜（呼应"错误聚集性"原则）。<span class="marginnote">测试文档与第 10 章项目管理的度量衔接：测试计划中的"工作量估算"与测试报告中的"缺陷密度"（每千行代码的缺陷数）都是项目度量（第 15 章）的输入。测试文档不只是测试组内部文件——它同时是<strong>项目管理、质量保证（第 11 章）、发布管理</strong>的共同依据。</span>

**辨析｜易错点：** 测试文档 ≠ "写完存档的八股文"。计划要真的指导执行（写了的要测、测了的要记），报告要真的支撑决策（结论明确、数据翔实）。**"计划与实际脱节、报告与决策脱节"是测试文档最常见的死法**——文档只有被使用，才有价值。

## 5 数值算例：出口准则怎么定才不空

把出口准则从"感觉"变成可判定的数字。假设一个网上书店系统，测试计划里写定的出口准则：

| 维度 | 门槛 | 判定示例 |
| --- | --- | --- |
| 用例执行率 | 计划用例 100% 执行 | 500 条计划用例，执行了 500 条 |
| 通过率 | P0 100%、P1 ≥ 95%、P2 ≥ 90% | P0 全过，P1 有 3 条失败 → 不达标 |
| 覆盖率 | 语句 ≥ 80%、分支 ≥ 70% | 语句 82%、分支 71% → 达标 |
| 缺陷状态 | 严重缺陷全修复并回归验证 | 2 个 P1 缺陷未关闭 → 不达标 |

**写下来的门槛让"测试完没完"变成布尔判断**——执行完对照一张表逐条打勾，达标即"可进入发布评审"，不达标就明确"缺什么、补什么"。这比"感觉测差不多了"可靠得多：它把发布决策从"主管拍板"变成"数据+准则的判定"。

**辨析｜易错点：** 出口准则最常见的两个失误：**一是门槛定得太高**（100% 用例通过、100% 覆盖），导致永远不达标、被迫"改准则放水"——准则失去公信力；**二是门槛定得太松**（只要求"无严重缺陷"），让"没怎么测"的系统也轻松过关。正确的做法是**按风险定准门槛**：核心功能 P0 全过，边缘功能 P2 允许按处置放行——准则是"可达到且有意义"的平衡点。

## 6 核心对比表：测试计划与测试报告

| 维度 | 测试计划 | 测试报告 |
| --- | --- | --- |
| 时机 | 测试开始前 | 测试结束后 |
| 回答 | 测什么、怎么测、谁测、何时完 | 测了什么、发现什么、能否发布 |
| 角色 | 测试的"需求规格"与纲领 | 测试的"验收报告" |
| 关键内容 | 范围、策略、入口/出口准则 | 执行统计、缺陷分析、结论建议 |
| 主要读者 | 测试团队、项目经理 | 发布决策者、管理层 |

**辨析｜易错点：** 计划与报告如果对不上，说明测试管理失效——**计划里承诺要测的，报告里必须能对上**（执行了多少、为什么没全测）；报告里发现的缺陷，计划里应有对应的测试意图。一份对不上计划的报告，只是"事后记录"而非"测试闭环"。判断标准：**把计划与报告并排看，能否讲出一个完整的故事？** 讲不出，闭环没闭合。

## 7 常见误区速查表

| 误区 | 正解 |
| --- | --- |
| "测试计划是走流程的八股文" | 计划要真指导执行：写了的要测、测了的要记 |
| "没有严重缺陷就能发布" | 还要看覆盖率与通过率，"没测够所以没发现"不算达标 |
| "出口准则只要'测完了'" | 出口准则要"测充分 + 测过得了"双重达标 |
| "测试报告是测试组的内部文件" | 报告的主要读者是发布决策者，结论要明确有数据 |
| "入口/出口准则可有可无" | 没有出口准则，测试可无限延长也可草草收场，都是灾难 |
| "计划写完就存档" | 计划与报告要对得上，对不上说明测试管理失效 |
| "报告结论写'基本没问题'就够" | 结论必须明确（建议发布/条件发布/不建议）+ 数据支撑 |
| "测试文档不用随项目演化" | 计划与报告要随测试执行动态更新，与决策挂钩 |

## 8 数值算例：一份出口准则的判定过程

把出口准则的"逐条打勾"走一遍。假设测试计划定的出口准则为：P0 100% 通过、P1 ≥ 95%、语句覆盖 ≥ 80%、无未关闭的严重缺陷。测试结束后统计：

| 准则 | 目标 | 实际 | 判定 |
| --- | --- | --- | --- |
| P0 通过率 | 100% | 100% | 达标 |
| P1 通过率 | ≥ 95% | 94% | **不达标** |
| 语句覆盖 | ≥ 80% | 82% | 达标 |
| 严重缺陷 | 全部关闭 | 2 个 P1 未关 | **不达标** |

**结论：不建议发布**，需补齐 3 条 P1 用例 + 处理 2 个未关闭缺陷后复审。这份判定让"能不能发布"从"主管感觉"变成"逐条对照的布尔结果"——每个不达标项都指向明确的补救动作。这就是"出口准则是测试计划最有工程价值部分"的含义。

**辨析｜易错点：** 准则的判定要**留证据**：通过率、覆盖率来自测试报告的实际统计，不是口头"差不多"。同时别把"严重缺陷全部关闭"当作唯一标准——它只是出口条件之一，还要看覆盖与通过率（"没测够所以没发现"不算达标）。

## 9 小结

- **测试计划**定义范围、策略、资源、入口/出口准则、风险与交付物。
- **入口/出口准则**是测试计划最有工程价值的部分，把"测完没完"变成判断标准。
- 出口准则要"**测充分 + 测过得了**"双重达标，不能只盯缺陷数量。
- **测试报告**回答"测了什么、发现什么、能否发布"，结论要明确、数据要支撑。
- 计划→执行→报告形成闭环，缺陷分析反馈下轮计划。
- 测试文档同时服务项目管理、质量保证与发布管理——被使用才有价值。
