## 为什么从测试用例管理开始

前面几节讲了测试技术与级别，这一节回到**测试工程的日常**：测试用例（test case）如何被**设计、评审、组织、维护**。邹欣《构建之法》给软件测试一个清醒的定位：**测试不是"找 bug 的临时活动"，而是和写代码同等重要的工程活动**——测试用例就是测试工程师的代码，值得像代码一样设计、评审与版本管理。

## 1 测试用例的设计要素

一条合格的测试用例（test case）应包含：

- **前置条件**：执行前系统的状态（数据、环境、配置）。
- **输入数据**：测试的具体输入。
- **执行步骤**：如何操作（对黑盒是操作序列，对白盒是调用路径）。
- **预期结果**：可判定的期望输出或状态变化。
- **实际结果与状态**：执行后记录，与预期对比。

**辨析｜易错点：** 测试用例最常被写坏的是**预期结果**——写成"系统应该正常工作"这种不可判定的话。预期结果必须**具体可断言**：「返回 HTTP 200 且 JSON 含字段 `borrowId`」或「库存数量减 1 且借阅记录新增一行」。**不可断言的预期结果 = 没写预期结果**。

## 2 测试用例的组织：测试集与分层

测试用例不是散沙，而是按结构组织：

- **按功能模块**：每个业务模块一组用例，便于追踪需求。
- **按优先级**：P0（核心功能，阻塞发布）、P1（重要功能）、P2（次要）——**回归与冒烟时按优先级取舍**。
- **按测试级别**：单元、集成、系统用例分开管理（第 8 章《测试级别》）。
- **关联需求**：每条用例可追溯到需求 ID（对应第 3 章的追踪矩阵）。<span class="marginnote">测试用例与需求的<strong>双向追踪</strong>是测试管理的核心不变量：正向问"这个需求有测试吗"，反向问"这条测试为什么存在（为哪个需求）"。没有追踪的用例是"孤儿用例"——它测的东西可能早已不是需求，维护它纯属浪费。用需求追踪矩阵（RTM）把用例挂到需求上，是测试管理的骨架。</span>

## 3 测试用例的评审

邹欣特别强调**测试用例评审**——测试用例和代码一样需要同行评审：

**评审目标**：用例是否覆盖需求？预期结果是否可判定？是否存在冗余或遗漏？
**评审方式**：用例走查会，设计者讲解、测试与开发共同质疑。
**评审的价值**：在写代码前就发现"需求没测到"或"用例设计错了"，远比执行后返工便宜。

**辨析｜易错点：** "用例评审"最容易被跳过，因为它看起来"不产生代码"。但正是用例评审能在**测试执行之前**暴露两个大问题——**覆盖盲区**（需求没对应用例）与**误判**（预期结果写错，测试"正确地测了错误预期"）。把用例评审当成测试质量的第一道关卡，是《构建之法》反复强调的工程纪律。<span class="marginnote">评审用例时的"测试者心态"很重要：不是检查"用例有没有写对格式"，而是模拟执行——<strong>逐条走查"如果我按这条用例操作，我真的能判断通过/失败吗？"</strong>。走不通、判不了的用例，执行时一定出问题。好的用例评审，是测试工程师与开发工程师共同做的一次"预演"。</span>

## 4 测试用例的维护：与代码一起演化

测试用例是"活的资产"，必须与代码同步维护：

**需求变更** → 更新相关用例、增删对应的测试。
**缺陷修复** → 把复现用例加入回归集。
**代码重构** → 行为不变则用例应仍通过；若重构改了接口，同步更新用例。
**定期清理** → 删除失效、冗余、无价值的用例，防止测试集臃肿。

**辨析｜易错点：** 测试用例最危险的死法有两种：**"僵尸用例"**（一直在跑、但断言早已失效、永远绿，给人虚假安全感）与**"孤儿用例"**（测的东西已不存在）。两者的共同根源是**用例没有随代码演化**。判断标准：**这条用例能指到它测的需求/代码吗？指不到，就该更新或删除**。<span class="marginnote">把测试用例当代码维护，意味着它也进<strong>版本控制</strong>、也做<strong>评审</strong>、也写<strong>文档</strong>（这一节与第 12 章配置管理、第 14 章代码评审都直接连通）。现代测试框架把用例与代码放在同一仓库、同一提交里，正是"用例即代码"的落地：测试与实现一起提交、一起评审、一起演化为同一份资产的左膀右臂。</span>

## 5 数值算例：用例评审的经济账

用例评审的收益，同样可以用"早发现便宜"来算。假设一个模块有 100 条测试用例，若不做评审，其中 10% 的用例存在"预期结果写错"或"覆盖盲区"：

| 对照 | 用例评审 | 不评审 |
| --- | --- | --- |
| 发现问题的时点 | 测试执行前（评审会） | 测试执行后 / 缺陷逃逸 |
| 修复成本 | 改一条用例，约 0.5 人时 | 执行中发现误判，重写 + 重跑，约 3 人时 |
| 10 个问题总成本 | 约 5 人时（评审会约 4 人时） | 约 30 人时 + 可能漏测逃逸到生产 |

**一次 4 人时的用例评审，换回约 25 人时的返工节省，杠杆约 1:6**——而且还没算"覆盖盲区导致的缺陷逃逸"这一项最贵的隐性成本（一个需求没测到，等用户报出来时是 40–100 倍）。这正是《构建之法》强调用例评审的工程理由：**在"最便宜的时候"发现"用例本身错了"**。

**辨析｜易错点：** 有人觉得"用例评审是测试团队的事，开发不用参加"——恰恰相反，**开发参加用例评审的价值最高**：开发最清楚实现细节与边界条件，能一眼看出"这条用例测不到那个关键分支"或"预期结果与实现语义不符"。用例评审的本质是"测试与开发的共同预演"，少一方都不完整。

## 6 核心对比表：测试用例 vs 源代码

| 维度 | 测试用例 | 源代码 |
| --- | --- | --- |
| 角色 | 描述"系统应如何表现" | 实现"系统如何表现" |
| 是否需要设计 | 是——用例即测试者的设计 | 是 |
| 是否需要评审 | 是——用例评审 | 是——代码评审 |
| 是否需要版本控制 | 是——随代码同仓 | 是 |
| 是否需要维护 | 是——随需求与代码演化 | 是 |
| 质量度量 | 覆盖率、误判率、缺陷发现率 | 圈复杂度、可维护性 |

**把测试用例当"一等公民"来管理**，是《构建之法》的核心主张：它和源代码享有同等的设计、评审、版本化、维护待遇。现实中"代码进仓库、用例散在 Excel"的团队，恰恰把最重要的质量资产排除在了工程管理之外——**用例即代码，不是修辞，是可操作的工程纪律**。

## 7 常见误区速查表

| 误区 | 正解 |
| --- | --- |
| "用例是测试工程师的私事" | 用例是团队资产，开发应参与评审（最懂实现边界） |
| "预期结果写'系统正常'就行" | 预期必须具体可断言，否则等于没写 |
| "用例设计完就不用维护" | 用例随代码演化：需求变更新、缺陷补回归、定期清理 |
| "用例评审浪费时间" | 评审在测试前发现覆盖盲区与误判，杠杆约 1:6 |
| "用例越多越好" | 冗余用例增加维护成本，僵尸用例制造虚假安全感 |
| "测试集不用版本控制" | 用例即代码，应随代码同仓、同评审、同版本管理 |
| "孤儿用例无伤大雅" | 测无所指的用例是浪费，应删除或挂回需求 |
| "覆盖率达标就测充分了" | 覆盖率只是必要非充分，还要看断言质量与需求覆盖 |

## 8 数值算例：一条用例的完整结构

把测试用例的要素落到一条具体的"图书检索"用例上，看什么才算"可断言"：

| 要素 | 内容 |
| --- | --- |
| 用例 ID | TC-1011 |
| 前置条件 | 馆藏数据库已加载 100 万条测试数据，检索服务在线 |
| 输入数据 | 关键词「三体」，页码 1，每页 20 条 |
| 执行步骤 | 1) 打开检索页；2) 输入关键词；3) 点击检索 |
| 预期结果 | 返回 HTTP 200；结果列表含《三体》三部曲；按相关度排序 |
| 实际结果 | （执行后填写，与预期对比） |
| 状态 | 通过 / 失败 / 阻塞 |

**每条要素都可判定**：前置条件可准备、输入可给出、步骤可执行、预期可断言。这正是"预期结果必须具体可断言"的实操——「返回 200 + 含《三体》」是可判定的，「检索正常」则不可。

**辨析｜易错点：** 别小看"实际结果"这一栏——**它是缺陷报告的源头**。实际与预期不符时，实际结果 + 输入 + 环境就是一条缺陷复现路径，直接进入缺陷跟踪与回归集。一条结构完整的用例，同时是测试凭证、缺陷证据与回归素材——这再次说明"用例即代码"：它要被维护、被版本化、被评审。

## 9 小结

- 测试用例要素：**前置条件、输入数据、执行步骤、预期结果、实际结果**。
- 预期结果必须**具体可断言**，不可判定的预期等于没有预期。
- 测试集按**模块、优先级、级别、需求追踪**组织，P0/P1/P2 支撑回归取舍。
- **测试用例评审**在测试执行前发现覆盖盲区与误判，是质量第一道关卡。
- 测试用例随代码**演化**：需求变更新、缺陷补回归、重构同步、定期清理。
- 警惕**僵尸用例**（永远绿）与**孤儿用例**（测无所指）——用例即代码，要进版本控制、做评审。
