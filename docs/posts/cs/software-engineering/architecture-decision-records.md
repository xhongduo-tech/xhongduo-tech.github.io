## 为什么从决策记录开始

架构是一连串**决策**的累积：用什么语言、选什么数据库、服务怎么拆、缓存要不要上。但这些决策常在会上口头拍板、随后被遗忘——半年后没人记得"为什么当初选它"，于是出现两种灾难：要么没人敢改（不知道理由），要么随便改（不知道代价）。**体系结构决策记录（Architecture Decision Record, ADR）**就是给每个决策建立"出生证明"，让架构决策**可追溯、可质疑、可演化**。

## 1 为什么需要 ADR

没有 ADR 的架构决策有三个典型症状：

- **决策蒸发**：讨论时理由充分，落地后理由消失，只剩结论。
- **僵尸决策**：环境已变、决策已过时，但没人知道该重审，于是一直沿用。
- **反复横跳**：不同时期的人对同一问题各选一次，架构在选项间摇摆。

ADR 解决的是"**记忆与上下文**"问题：它把决策当时的**背景、选项、理由、后果**固化下来，让后人能回答三个问题——"为什么选它""当时放弃了什么""什么条件下该重审它"。<span class="marginnote">ADR 的一个隐蔽价值是<strong>降低新人成本</strong>：新架构师接手系统，读一遍 ADR 集合就理解了系统的"决策史"，不用靠考古代码去猜。对长期维护的团队，ADR 集合就是架构的"编年史"。</span>

## 2 ADR 的标准结构

Michael Nygard 给出的经典 ADR 结构，通常 5–7 节：

| 章节 | 内容 | 说明 |
| --- | --- | --- |
| 标题 | 决策的一句话 | 如"用 PostgreSQL 作为主存储" |
| 状态 | Proposed / Accepted / Deprecated / Superseded | 决策的生命周期 |
| 背景（Context） | 面临的问题与约束 | 为什么需要决策 |
| 决策（Decision） | 最终选择是什么 | 清晰、明确 |
| 后果（Consequences） | 正面与负面结果 | 权衡的显式记录 |
| （可选）替代方案 | 考虑过但放弃的选项 | 为什么放弃 |
| （可选）重审条件 | 什么信号触发重审 | 防僵尸决策 |

ADR 的编号常用 `ADR-001`、`ADR-002` 递增，并按主题分组维护。<span class="marginnote">一个高质量 ADR 的"后果"部分最有含金量：它必须<strong>同时写正面与负面</strong>。只写好处、不写代价的 ADR 是在粉饰决策——未来重审时，你恰恰需要知道"这个决策牺牲了什么"来判断是否该换。</span>

## 3 技术选型的决策框架

ADR 最常见的用武之地是**技术选型**（选语言、框架、数据库、中间件）。技术选型的系统化流程：

1. **明确需求与约束**：性能、团队熟悉度、生态、许可证、成本——先列评估标准。
2. **候选调研**：列出候选方案，收集关键事实（成熟度、社区、维护状态）。
3. **对照评分**：按标准给每个候选打分，标注"一票否决项"（许可证、安全漏洞）。
4. **做决策并写 ADR**：写下背景、选项、理由与后果。
5. **设置复审点**：6–12 个月后复审一次，检查决策是否仍然成立。

**辨析｜易错点：** 技术选型的最大陷阱是**"流行驱动"**——因为某技术热门就选它，却说不清它解决了你的什么具体问题。判断标准：**每个技术选择都应能回答"它为哪条业务/质量需求服务，代价是什么"**。答不出的选择，就是跟风。另一个陷阱是**"选型=绑定"**：低估了技术栈的锁定成本——换数据库比换数据库驱动贵得多，选型时要把"切换成本"写进后果。

## 4 决策记录与架构演化的闭环

ADR 与架构评估（上一节 ATAM）、配置管理（第 12 章）形成闭环：

- **ATAM 暴露权衡** → 产生决策需求 → **ADR 记录决策**。
- 决策变更时，旧 ADR 标记为 `Superseded`，新 ADR 承接背景与理由。
- 重审信号触发（性能不达标、技术停止维护、团队能力变化）→ 重新评估 → 新 ADR。

**辨析｜易错点：** ADR ≠ 设计文档。设计文档描述"系统是什么样"（图纸），ADR 描述"为什么这样决定"（决策史）。一个系统的架构设计文档可能一年不变，ADR 却可能一个月新增好几条——两者是不同性质、不同节奏的产物，别混在一份文档里。ADR 的轻量性正是它的生命力：**每份 ADR 一两页、一事一议**，重了就不写了。<span class="marginnote">现代实践中 ADR 常与<strong>代码评审</strong>绑定：提交涉及架构决策的代码时，要求附带（或引用）ADR，评审者据此理解"为什么要这么改"。ADR 从"事后补文档"变成"评审的输入"——它从归档工具升级成了协作机制。</span>

## 5 小结

- **ADR** 为每个架构决策建立"出生证明"，记录背景、决策、后果与替代方案。
- 没有 ADR 的典型症状：**决策蒸发、僵尸决策、反复横跳**。
- 经典 ADR 结构：标题、状态、背景、决策、后果、（可选）替代方案与重审条件。
- ADR 的**后果章节必须同时写正面与负面**，牺牲了什么要记清楚。
- **技术选型**用「明确约束 → 调研 → 评分 → 决策 + ADR → 复审」五步走，警惕流行驱动。
- ADR 与 ATAM、配置管理闭环：评估产生决策，ADR 记录决策，重审触发演化。
