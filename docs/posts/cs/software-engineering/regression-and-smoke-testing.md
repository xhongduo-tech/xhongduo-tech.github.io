# 回归测试与冒烟测试

## 为什么从回归与冒烟开始

软件被改，是常态。每一次改动都潜伏着一个风险：**修好 A 却弄坏了 B**。这一节的两个测试类型专门应对"改动"——**回归测试（regression testing）**验证改动没破坏已有功能，**冒烟测试（smoke testing）**在改动后快速检查"最核心的功能还活着吗"。它们是版本迭代、发布流程里的守门员。

## 1 回归测试：改动不破坏旧功能

**回归测试（regression testing）**：在软件**修改后**重新执行测试，验证修改没有引入新的缺陷、没有破坏原有功能。

**辨析｜易错点：** 回归测试不是"一种测试类型"而是一种"测试时机与策略"——它重跑已有用例，但**不是全部用例**。回归测试的设计要点：

- **回归集的选择**：不是所有历史用例都重跑（太多、太慢），而是**优先重跑受改动影响的功能**相关的用例。
- **回归集的维护**：每发现一个 bug，修复后**把该 bug 的用例加入回归集**——防止同类 bug 再次漏网。
- **回归的自动化**：回归测试是自动化收益最大的测试——手工重跑几十遍同样的用例既不现实也易错。<span class="marginnote">回归集是团队的"历史保险库"：它累积了所有曾经出错、曾被修复的教训。<strong>每次修 bug 都把复现用例沉淀进回归集</strong>，回归集就越长越有价值——这也是"测试驱动修复"的实践：先写一个能复现 bug 的失败用例，再修复让它变绿，这个用例从此守卫这条功能线。</span>

## 2 冒烟测试：发布前的"能不能活"

**冒烟测试（smoke testing）**：对软件**主要功能路径**进行快速、浅层的检查，确认"基本功能能跑起来"，不值得深测。"冒烟"之名来自硬件：**通电后如果冒烟，就不用再测了**——先验证"能通电"，再谈"性能如何"。

**范围**：核心业务流程的"happy path"（主路径），不覆盖分支与异常。
**时机**：每次新构建、每次发布前、CI 的第一关。
**目的**：快速判断"这个版本值不值得继续测"——不值得就把时间省下来。

**辨析｜易错点：** 冒烟测试 ≠ 回归测试。**冒烟测"还能不能活"（浅、快、主路径），回归测"有没有被改坏"（深、全、受影响功能）**。冒烟通过不代表没问题，只代表"可以进入更深的测试"。把冒烟当回归，会让核心路径之外的功能无人守护；把回归当冒烟，则会让发布带着深层回归风险。

## 3 两者在发布流程中的位置

一个典型的发布前测试序列：

1. **冒烟测试**——快速检查核心主路径，判断"这个版本值不值得继续测"。
2. **回归测试**——重跑受改动影响的用例，确认改动没破坏旧功能。
3. **集成测试**——验证模块间的接口与协作。
4. **系统测试**——在真实环境中做最终验收。

冒烟是"快速否决器"，回归是"历史守护者"，集成系统是"最终验收"。<span class="marginnote">在 CI/CD 流水线（第 13 章）里，冒烟与回归有固定座位：<strong>提交触发 → 编译 → 冒烟（分钟级）→ 单元+回归（分钟到十分钟级）→ 集成测试 → 部署到测试环境</strong>。冒烟失败直接拦截，回归失败阻止合并——它们把"发布风险"前置成"提交风险"，这是 DevOps 的核心理念：<strong>越早发现，成本越低</strong>。</span>

## 4 数值算例：回归集该多大

回归集的选择是个真实的工程权衡——测少了漏缺陷，测多了拖慢流水线。给一个简化但典型的数量级：

假设一个系统共有 5000 个自动化用例，全量回归需要 40 分钟。日常提交触发的 CI，团队只能接受 10 分钟以内的反馈。于是：

| 回归策略 | 用例数 | 运行时间 | 覆盖风险 |
| --- | --- | --- | --- |
| 全量回归 | 5000 | 40 分钟 | 全覆盖，但每次提交都太慢 |
| 受影响功能回归 | 约 800 | 8 分钟 | 覆盖本次改动的相关功能，有针对性 |
| 冒烟 + 全量（夜间） | 300 + 5000 | 3 分钟 + 40 分钟 | 白天快速反馈，夜间补全量 |

实践中常见的是**分层**：每次提交跑「冒烟 + 受影响回归」（分钟级），合并到主干或夜间跑「全量回归」（小时级）。**回归集不是越大越好，而是"与该改动的风险匹配"**——改一处 UI 文案不必跑全部支付用例，改支付核心逻辑就必须跑支付相关的整条回归链。

**辨析｜易错点：** 两个常见的错误方向：一是「为省时间而删回归集」，删掉的是对历史 bug 的守护，等于把已修复的问题放回危险区；二是「为了覆盖率而不加区分地全跑」，40 分钟的反馈让开发者干脆不跑，回归形同虚设。判断标准始终是：**每次改动，能不能在可接受的反馈时间内，覆盖到最可能被它破坏的功能？**

## 5 核心对比表：冒烟、回归与冒烟变体

| 维度 | 冒烟测试 | 回归测试 | 冒烟变体（契约冒烟/冒烟+） |
| --- | --- | --- | --- |
| 目的 | 核心功能「能不能活」 | 改动「有没有改坏」 | 在冒烟基础上验证关键接口契约 |
| 深度 | 浅——主路径即可 | 深——覆盖受影响功能 | 中——主路径 + 关键接口 |
| 时机 | 每次构建、发布前、CI 第一关 | 每次改动后、发布前 | 构建后、冒烟之后 |
| 失败含义 | 「别继续测了」——快速否决 | 「改动有问题」——阻止合并 | 「接口不匹配」——阻止集成 |
| 用时 | 分钟级 | 分钟到小时级 | 分钟级 |

**辨析｜易错点：** 冒烟测试最容易犯的错是把它当回归用——**冒烟只测「活着」，不测「没被改坏」**。一个冒烟全绿的版本，核心路径之外可能藏着深度回归缺陷。反过来，把回归当冒烟（发布前只跑回归不跑冒烟）会浪费大量时间在「根本不该测的版本」上。正确姿势：**冒烟决定"值不值得测"，回归决定"有没有测出问题"**，两者先后衔接、各司其职。

## 6 回归与冒烟的工程配套

要让回归与冒烟真正成为发布的守门员，需要几项配套实践：

**稳定的测试数据**：回归测试最怕"测试环境数据不干净"——同一个用例这次过、下次挂，全因数据状态漂移。**固定种子数据 + 每个用例独立清理**，是回归稳定性的前提。

**测试分层与分级**：把用例按「冒烟 / 快速回归 / 全量」分级，配不同触发时机（提交 / 合并 / 夜间），让反馈时间与风险匹配。

**与 CI/CD 集成**：把冒烟设成流水线第一道闸门（失败直接拦截），回归设成合并闸门（失败阻止合并）。**让「发布风险」前置成「提交风险」**——问题在提交时被抓住，比在发布时被抓住便宜一个数量级。

**失败即隔离**：回归一红，团队应把「修复回归」当作最高优先级，而不是在红着的基础上继续堆新提交——红灯不灭，风险就在累积。

## 7 常见误区速查表

| 误区 | 正解 |
| --- | --- |
| "回归测试 = 重跑全部用例" | 应精选受影响功能相关的用例，全跑太慢且无针对性 |
| "冒烟测试 = 回归测试" | 冒烟测"能不能活"（浅快），回归测"有没有改坏"（深全） |
| "冒烟通过 = 没问题" | 冒烟只证明主路径活着，不代表可以进入深度测试 |
| "回归集越大越好" | 回归集要与改动风险匹配，分提交/合并/夜间分层执行 |
| "回归集不用维护" | 每修一个 bug 都把复现用例加入回归集，它是历史保险库 |
| "回归是手工活" | 回归是自动化收益最大的测试，手工重跑不现实 |
| "冒烟只在上线前跑" | 冒烟应作为 CI 第一关，每次提交都触发 |
| "红灯可以先放着" | 回归红灯要最高优先级修复，红灯不灭风险在累积 |

## 8 核心对比表：测试类型的时机与职责

| 测试类型 | 触发时机 | 核心职责 | 失败含义 |
| --- | --- | --- | --- |
| 冒烟测试 | 每次构建后、发布前 | 核心主路径能否运行 | 版本不值得继续测 |
| 回归测试 | 每次改动后 | 改动是否破坏旧功能 | 改动引入了缺陷 |
| 集成测试 | 模块组合后 | 接口与协作是否正确 | 模块接缝出问题 |
| 系统测试 | 发布前 | 真实环境是否达标 | 系统级属性不满足 |

**辨析｜易错点：** 这些类型不是"各测各的"，而是**在流水线里接力**：提交触发冒烟（快速否决）→ 改动触发回归（守历史）→ 合并触发集成（验接缝）→ 发布触发系统（总验收）。把某一类放错位置（比如把系统测试当冒烟跑在每次提交），要么反馈太慢、要么把关太松。**判断标准：每个测试类型的"时机 × 职责"是否匹配？**

## 9 小结

- **回归测试**在改动后重跑受影响用例，验证没破坏旧功能。
- 回归集要**精选受影响功能**并持续累积 bug 复现用例，自动化收益最大。
- **冒烟测试**快速检查核心主路径"还能不能活"，是发布的第一道快速否决器。
- 冒烟测"存活"（浅快），回归测"无破坏"（深全），各司其职。
- 发布序列：冒烟 → 回归 → 集成/系统 → 发布。
- 在 CI 里，冒烟与回归把"发布风险"前置成"提交风险"。
