## 为什么从简化条件开始

上一节的提炼/搬移/重组数据管"代码块"，这一节专门对付两类最常见的复杂来源：**条件表达式（if/switch）**与**方法调用（函数调用的签名与关系）**。它们是坏味道"switch 过多""过长参数列表""神秘命名"的直接对手——也是日常重构里最常操作的两块。

## 1 简化条件表达式：让分支可读

条件表达式重构的核心手法：

- **分解条件表达式（Decompose Conditional）**：把复杂的条件与分支各自提炼成函数——`isLeapYear(date)` 代替一大串 `year % 4 == 0 && (year % 100 != 0 || year % 400 == 0)`。
- **合并条件表达式（Consolidate Conditional）**：多个条件走向同一结果时合并——减少重复分支。
- **卫语句取代嵌套条件（Replace Nested Conditional with Guard Clauses）**：把"层层嵌套的 if"改成"先检查异常条件、提前返回"的卫语句。
- **以多态取代条件表达式（Replace Conditional with Polymorphism）**：switch 按类型分派 → 用策略/状态模式（第 6 章）——消灭 switch 坏味道。

**辨析｜易错点：** 卫语句与嵌套 if 的选择是经典困惑：**主流程用嵌套（强调"正常路径"，异常放分支），前置校验用卫语句（强调"先拦异常"）**。判断标准：**条件是在"校验前置条件"（用卫语句提前返回）还是"分支不同行为"（保持正常分支结构）？** 把校验写成深嵌套，是把简单的防御复杂化了。<span class="marginnote">"以多态取代条件"是条件重构的<strong>终极形态</strong>：当 switch 按类型分派逻辑时，用多态（第 6 章策略/状态模式）把每个分支变成独立类。它的收益：加新类型不用改 switch（OCP）、每个分支独立测试。代价：类数量增加。判断标准：<strong>switch 是否经常因"加新类型"而修改？</strong> 是，就值得转多态；只是两三个分支、很少变，直接 if 更简单——<strong>重构也要避免过度设计</strong>。</span>

## 2 简化方法调用：让调用清晰

方法调用相关的重构手法：

- **改名函数（Rename Function）**：名字不清就改名——调用清晰的第一步。
- **改变函数声明（Change Function Declaration）**：调签名——参数增减、参数顺序，让签名表达真实契约。
- **移除参数 / 引入参数（Remove / Add Parameter）**：参数不再需要就删，需要就加。
- **以查询取代参数（Replace Parameter with Query）**：参数可以从对象内部算出来，就不用调用方传——减少调用方负担。
- **保持对象完整（Preserve Whole Object）**：调用方有整个对象，就传对象而不传散参数——减少参数列表。

**辨析｜易错点：** 方法调用的重构核心是**"接口即契约"**（第 4 章接口三原则）：签名是调用方与被调方的约定，**改签名会影响所有调用方**——所以改签名要走"先加新签名、再迁移调用方、最后删旧签名"的过渡（或在 IDE 里一次性全局安全替换）。判断标准：**这个签名是否准确表达了"调用方需要什么、被调方承诺什么"？** 签名含糊，调用就处处含糊。

## 3 处理关系：把散落调用理清

关系层的方法调用重构：

- **搬移函数到更合适的类**：某方法更该属于别的类（上一节搬移）。
- **提炼模块（Extract Module）**：一组高度相关的函数与数据组成新模块/类。
- **内联（Inline）**：函数太薄、只有一层转发时，内联回调用处——去掉无意义的间接层。

**辨析｜易错点：** 内联是"提炼"的反向——**提炼是"太胖要拆"，内联是"太薄要合"**。判断标准：**这个函数是否只是"转发一下、没有增加价值"？** 是的间接层就是噪音，内联掉。**抽象的度**（第 4 章 SoC 的权衡）在这里体现：过度抽象（每个函数只转发）与抽象不足（一切塞进一个函数）同样有害——重构的目标是"**合适的抽象度**"。

## 4 数值算例：卫语句如何让复杂度可见

把「嵌套 if 改卫语句」的效果量化，最直观的指标是**圈复杂度（cyclomatic complexity，第 15 章）**。设一个函数有 $p$ 个前置校验、$q$ 条正常分支，嵌套写法的判定数（predicates）约为 $p + q$；改卫语句后**判定数不变，但嵌套深度从 $O(p+q)$ 降到 $O(1)$**——每个卫语句立刻返回，主流程只剩一条平铺的路径。

以取款函数为例：校验「账户存在、余额足够、未冻结、额度未超」，每多一层嵌套，读者就要在心里维护一层缩进栈。改为四个卫语句后，**每个异常条件一行拦住，主流程只剩「扣款 → 记流水 → 返回」三行**。嵌套深度与维护成本的关系近似线性：深度每加一，出错的概率与阅读耗时都明显上升——这正是「用平铺替代嵌套」在工程上的理由。<span class="marginnote">一个经验法则：<strong>缩进深度超过三层的函数，几乎都可以拆</strong>——要么提炼子函数（上一节），要么改成卫语句。圈复杂度在 10 以上的函数，读起来就已经像在「解码」而非「阅读」了。</span>

## 5 一个「签名即契约」的迁移实例

改签名之所以危险，是因为它牵一发动全身。以一个真实场景演示「先加新、再迁移、后删旧」的三步过渡：

```python
# 旧签名：传散参数，调用方逐个拼
def render_report(title, author, year, month, day):
    ...

# 第一步：加新签名（保持对象完整），旧签名转调
def render_report(title, author, date):
    ...

# 第二步：逐个迁移调用方 render_report(t, a, meta.date)
# 第三步：确认无调用方后，删除旧签名
```

三步中每一步都可独立提交、可独立回滚，**任何一步出错都被限制在一个小改动里**。相比「一步到位地改签名」，这种过渡把「一次性的大风险」拆成了「三次可验证的小风险」——这也是大型重构（下一节）的通用节奏：**每次改动都保持系统可运行**。

## 6 核心对比表：嵌套 if 与卫语句

| 维度 | 嵌套 if | 卫语句（Guard Clauses） |
| --- | --- | --- |
| 结构 | 条件层层缩进，正常路径深埋内层 | 异常条件先行拦截，主流程平铺在最外层 |
| 可读性 | 缩进每深一层，阅读负担线性上升 | 每个守卫一行拦住一种异常，主流程一目了然 |
| 语义 | 强调"分支关系"（if-else 并列） | 强调"前置校验"（不符合就返回） |
| 出错的常见点 | 括号配对、else 归属、漏分支 | 守卫顺序（先检查依赖它的条件） |
| 圈复杂度 | 判定数与嵌套深度共同膨胀 | 判定数不变，但嵌套深度降到 O(1) |
| 适用 | 行为确实并列、需要共享上下文的场景 | 前置校验、先决条件、防御式编程 |

**辨析｜易错点：** 卫语句不等于"禁止嵌套"。**当多个分支确实是在处理"同一个问题的不同行为"（而非前置校验）时，嵌套的 if-else 是更准确的表达**——强行压平会失去"这些分支是对等选择"的信息。卫语句只用于「先决条件不满足就立即退出」的那类判断。判断标准始终是：**这段 if 是在"守卫边界"，还是在"分派行为"？** 前者用卫语句，后者保持分支。

## 8 常见误区速查表

| 误区 | 正解 |
| --- | --- |
| "条件越简单 = 越没 if" | 简化是让分支可读可扩展，不是消灭 if |
| "卫语句 = 禁止嵌套" | 行为并列的分支用嵌套更准，卫语句只管前置校验 |
| "所有 switch 都转多态" | 只在"switch 常因新类型而改"时值得，否则过度设计 |
| "改签名一步到位" | 改签名影响所有调用方，要走"先加新、再迁移、后删旧" |
| "签名是小事" | 签名即契约，含糊的签名让调用处处含糊 |
| "内联 = 删函数" | 内联只针对"太薄的转发层"，有间接价值的不能内联 |
| "条件覆盖 = 分支覆盖" | 分支覆盖看判定结果，条件覆盖看子条件取值，互不包含 |
| "重构要避免过度抽象" | 目标是合适的抽象度，过度抽象与抽象不足同样有害 |

## 9 小结

- **简化条件**：分解、合并、卫语句、多态取代 switch——让分支可读、可扩展。
- **卫语句 vs 嵌套**：校验前置条件用卫语句提前返回，行为分支配正常分支结构。
- **以多态取代条件**是条件重构的终极形态，但只在「switch 常因新类型而改」时值得。
- **简化方法调用**：改名、改签名、增删参数、以查询取代参数、保持对象完整。
- **签名即契约**：改签名影响所有调用方，要走「先加新、再迁移、后删旧」的过渡。
- **内联**是提炼的反向——「太薄的间接层」要合掉；目标是**合适的抽象度**。
