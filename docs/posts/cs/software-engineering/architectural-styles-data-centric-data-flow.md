## 为什么从架构风格开始

上一节讲了体系结构的描述（4+1 视图），这一节开始讲它的**词汇表**——**体系结构风格（architectural style）**：一类系统的组织"母题"，每种风格针对一类反复出现的结构问题。Pressman 把风格归为四大类：数据为中心、数据流、调用-返回、面向对象、层次、事件驱动。这一节讲前两类：**以数据为中心**与**数据流**风格。

## 1 以数据为中心的风格：大家都来读写"黑板"

**以数据为中心（data-centered）**的风格包含两种变体：**仓库（repository）**与**黑板（blackboard）**。

- **仓库风格**：一个中央**数据存储（repository）**，多个独立构件从它读写数据。<span class="marginnote">仓库风格的典型是数据库应用：应用模块、报表模块、管理模块各自读写中央数据库，彼此不直接通信。它的好处是数据一致、共享简单；代价是中央存储成为性能与可用性瓶颈，构件间耦合被"通道化"到数据模型上。</span>
**黑板风格**：数据与**求解逻辑（knowledge source）**动态协作——多个专家构件监听黑板，当数据满足触发条件时贡献自己的结果。黑板是仓库的动态变体，适用于**无固定算法路径**的问题。

黑板风格的名场面是**语音识别 / 信号处理**：多个专家模块各自识别特征、把部分结果写到黑板，其他模块基于半成品继续加工，最终拼出完整识别结果。<span class="marginnote">黑板的精髓是"<strong>问题状态即共享数据</strong>"：没有谁控制全局流程，流程由"谁的条件被满足"动态决定。这使它适合那些没有确定算法、靠试探性推理的问题——也是"竞争性架构"（比赛谁先出答案）的思想源头。</span>

**辨析｜易错点：** 仓库 ≠ 黑板。仓库的数据是被**主动读写**的（构件主动拉取），黑板的专家是被**事件触发**的（条件满足自动响应）。把黑板做成仓库，就失去了"动态协作"的灵活性；把仓库做成黑板，则白白引入复杂的事件机制。

## 2 数据流风格：数据沿着管道流动

**数据流（data flow）**风格把系统组织成**流水线**：数据从输入流入一系列**过滤器（filter）**，每道过滤器加工后交给**管道（pipe）**传给下一道。因此也叫**管道-过滤器（pipe-and-filter）**风格。

经典例子：Unix 命令行。「cat file | grep key | sort」——每个命令是一个过滤器，管道（`|`）连接它们；数据（文本行）从 cat 流向 grep，再流向 sort 等。<span class="marginnote">管道-过滤器的优点：<strong>可组合性</strong>（过滤器可自由拼装）、<strong>可重用性</strong>（每个过滤器独立）、<strong>可并行</strong>（多级流水可并发）。代价：过滤器间传递的数据格式要统一（耦合到"管道协议"），且难以表达交互式、有状态的处理。</span>

数据流风格的变体还有**批处理（batch sequential）**：前一步的完整输出是下一步的完整输入，步骤之间没有实时流动——古老而稳定的报表、ETL 处理就是批处理。

**辨析｜易错点：** 管道-过滤器与**链式职责（责任链）**容易混淆：管道的每个过滤器**都会处理数据**并传给下一个；责任链的每个处理者**有权决定"处理或交给下一个"**——一个请求只被一个环节处理。前者是"分工接力"，后者是"逐级转交"。

## 3 两种风格的对比

| 维度 | 数据为中心（仓库） | 数据流（管道-过滤器） |
| --- | --- | --- |
| 数据地位 | 中央存储，构件围绕它 | 数据流动，构件加工它 |
| 构件关系 | 通过存储间接耦合 | 通过管道顺序耦合 |
| 控制流 | 构件主动读写（或事件触发） | 数据被动逐级推进 |
| 优点 | 一致性、共享简单 | 可组合、可并行、可重用 |
| 代价 | 中央瓶颈 | 数据格式耦合、难表达交互 |
| 典型场景 | 数据库系统、共享状态 | Unix 管道、ETL、流处理 |

**关键判断：你的系统是"围绕数据组织"还是"沿着流程组织"？** 前者用仓库，后者用管道。<span class="marginnote">现代大数据与流处理（Kafka + Flink 等）可以看作数据流风格的现代复兴：数据以事件流的形式在处理器间流动，每个处理器是"有状态的过滤器"。管道-过滤器四十年前的直觉，今天在实时数据管道里依然成立——架构风格的生命力远超具体技术。</span>

## 4 实战：给你的系统选数据风格

判断系统该用哪种数据风格，用一个"数据流动性"测试：**数据是"被各方反复读写"（仓库/黑板），还是"沿一条固定管道逐级加工"（数据流）？**

| 系统特征 | 适合风格 | 理由 |
| --- | --- | --- |
| 多模块共享同一份核心数据 | 仓库（数据为中心） | 一致性由中央存储保证 |
| 问题无固定算法、需多方协作探索 | 黑板 | 动态求解、无中央调度者 |
| 数据按固定步骤逐级转换 | 管道-过滤器 | 每级可独立替换与并行 |
| 大数据批处理、离线报表 | 批处理 | 吞吐优先，无需实时交互 |

**辨析｜易错点：** 最常见的选型错误是"为了用管道而造管道"——数据其实被多个组件共享、却被硬拆成流水线，结果每个过滤器都要重新拉取全量数据，一致性与性能两头亏。反过来，把真正逐级加工的数据硬塞进中央仓库，也会让"每级加工"变成"反复读写共享区"的争用。**风格跟着数据的"流型"走，而不是跟着流行术语走。**

一个可以对照的真实案例：编译器的前端处理就是典型的管道-过滤器——词法分析 → 语法分析 → 语义分析 → 中间代码生成，每一级吃上一级的产物、产出下一级的输入，级与级之间不共享可变数据。而一个操作系统内核则更接近"仓库 + 事件"的混合：进程表、文件表是共享仓库，调度与中断是事件驱动。**先问"数据在哪流动"，再谈"用哪种风格"，选型就不容易跑偏。**

## 5 数值算例：风格决定延迟与吞吐的边界

用一个极端但清晰的数量级感受两种风格的差异。设一条数据处理链有 4 个加工级、每级处理一份数据要 2 秒：

- **管道-过滤器（串行）**：整条链路处理一份数据约 $4 \times 2 = 8$ 秒；但管道天然可并行——4 个过滤器各跑一个实例，流水线吞吐约等于"每 2 秒产出一份成品"，**延迟 8 秒、吞吐 0.5 份/秒**。
- **仓库（共享中央存储）**：4 个模块都要读写中央数据库，每份数据两次落盘，单份延迟可能更短（各模块各管一段），但当并发高时，**中央存储的锁与 I/O 成为吞吐瓶颈**——这正是"仓库瓶颈在中央"的量化含义。

这个算例告诉我们：**数据流风格把吞吐压到"最慢一级的吞吐"，数据仓库把吞吐压到"中央存储的并发上限"**。选型时要先算清楚自己系统的瓶颈会先落在哪一头——是级与级之间的串行等待，还是中央存储的竞争。把这句话装进工具箱，你就不会在"该用管道还是仓库"上凭感觉拍板。

**辨析｜易错点：** 别把"管道"等同于"性能快"。管道的吞吐优势来自**并行与流水线**，而它的延迟反而比顺序执行更长（要填满流水线）。要实时低延迟、数据被多方共享，仓库/黑板往往更合适；要大批量、可流水化，管道更合适。**"快"和"适合"是两个维度，先辨清需求再选型。**

## 6 术语速查表

| 术语 | 一句话定义 | 关键约束 |
| --- | --- | --- |
| 数据仓库 | 各组件共享的中央数据存储 | 一致性靠中央，瓶颈在中央 |
| 黑板 | 多方协作、动态求解的共享工作区 | 无固定算法、无中央调度 |
| 管道-过滤器 | 数据沿过滤器链逐级加工 | 组合/并行/重用，数据格式耦合 |
| 批处理 | 数据成批、离线、按序处理 | 吞吐优先，无交互 |
| 数据流型 | 数据在系统中的移动方式 | 决定风格选择的第一判据 |

## 7 练习：三个系统的风格判断

把概念落到判断力上，下面三个系统你会怎么选？

1. **一个证券行情推送系统**：行情数据不断到达，多个展示终端、风控模块都要读同一份最新行情，且希望任意终端故障不影响其他终端。判据：数据被多方**共享且实时**——走**仓库**（或仓库+事件发布订阅），让共享数据有单一事实来源。
2. **一个日志清洗流水线**：采集 → 解析 → 脱敏 → 聚合 → 入仓，每步只吃上一步的输出。判据：数据**沿固定管道逐级加工**——走**管道-过滤器**，每级可独立扩容、替换、并行。
3. **一个自然语言对话系统**：多个专家模块（意图识别、实体抽取、情感判断）对同一段输入共同给出线索，没有一个模块能独立定案。判据：**无固定算法、需多方协作探索**——走**黑板**，各模块在黑板上读写假设、逐步收敛。

做完这三题，你应该能体会到：风格选择不是审美题，而是**"数据的流型"的函数**。能针对真实系统说清"为什么是这种风格"，这一节的功夫才算真正上身。

## 8 拓展：数据风格在分布式世界的变形

现代分布式系统没有"单机中央存储"，但两种风格以变形继续存在：

- **仓库的分布式变形**：共享数据库被换成"各服务自有的库 + 事件总线同步"（第 5 章微服务里的"数据独立"），或者干脆用统一的分布式缓存/数据湖做共享层。母题没变——"围绕一份共享数据协作"，变的只是"共享"的实现方式。
- **管道-过滤器的分布式变形**：就是消息队列驱动的流式流水线——每个服务消费上游事件、产出下游事件，Kafka 一类的消息中间件充当过滤器之间的"管道"。**流水线思维从单机搬到了集群**，这也正是第 13 章持续集成流水线（build → test → deploy）的雏形。

理解这一点，你就知道"学风格"不是学历史名词，而是学一套**在任何规模下都成立的组织直觉**：无论机器是一台还是一万台，先问"数据在哪流动、谁和谁共享"，架构的骨架就大致定型了。

## 9 小结

- **以数据为中心**的风格把数据放中央，构件围绕它读写：**仓库**（主动读写）与**黑板**（事件触发、动态协作）。
- **数据流风格**把数据沿管道逐级加工：**管道-过滤器**（Unix 管道的原型）与**批处理**。
- 仓库的优点是一致性、共享简单，瓶颈是中央存储；黑板的优点是无固定算法时的动态求解。
- 管道-过滤器的优点是组合、并行、重用，代价是数据格式耦合。
- 仓库管"围绕数据"，管道管"沿着流程"——先判断你的系统是哪一类。

- 选型第一问：数据是被多方共享（仓库/黑板），还是沿固定管道加工（数据流）？
- 分布式世界里的变形：共享层仓库、消息队列管道——风格直觉在任意规模都成立。
