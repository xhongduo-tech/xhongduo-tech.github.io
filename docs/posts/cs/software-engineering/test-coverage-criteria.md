# 测试覆盖率：语句、分支、路径与条件覆盖

## 为什么从测试覆盖率开始

"测试充分了吗？"不能靠感觉回答。**测试覆盖率（test coverage）**给出量化答案：已执行的代码占全部代码的多少。但"覆盖率"不是一个指标，而是一族指标——语句、分支、路径、条件，各有各的"盲区视角"。这一节讲清这四种覆盖率、它们的关系与陷阱。

## 1 四种覆盖率

以这段代码为例（前面白盒测试用过的例子）：

```c
cin >> a >> b;
if (a > 1 && b < 0)
    x = a * b;      // 语句 1：真分支
else
    x = a - b;      // 语句 2：假分支
y = x + 1;          // 语句 3
```

- **语句覆盖（statement coverage）**：每个**可执行语句**至少执行一次。测试 `a=5, b=-1` 执行语句1、3，语句2 没执行——语句覆盖不要求覆盖假（else）分支。
- **分支覆盖（branch coverage）**：每个**判定分支**（真/假）至少走一次。需测**真分支（条件成立）**与**假分支（条件不成立）**两条，覆盖真/假两支。
- **条件覆盖（condition coverage）**：每个**条件的每个取值**至少一次。对 `a > 1 && b < 0`，要让 `a > 1` 真/假各一次、`b < 0` 真/假各一次。
- **路径覆盖（path coverage）**：每条**独立路径**至少走一次——最严格，也是基本路径测试的目标。

**辨析｜易错点：** 分支覆盖 ≠ 条件覆盖。分支覆盖看"整个判定的结果"（真/假），条件覆盖看"每个子条件的取值"。对 `a > 1 && b < 0`，分支覆盖只要“整体真一次、整体假一次”；条件覆盖要求 `a > 1` 与 `b < 0` 各自的真假都被验证——**条件覆盖比分支覆盖更细，但两者都不自动包含对方**。

## 2 覆盖率的强弱关系

四种覆盖率构成**强度阶梯**：

$$
\text{语句覆盖} \le \text{分支覆盖} \le \text{路径覆盖}
$$

**辨析｜易错点：** 更严格的覆盖**通常但未必**包含更宽松的覆盖——路径覆盖一定满足语句覆盖，但**分支覆盖与条件覆盖互不包含**（要同时满足两者需要专门设计）。工程师常犯的错误是**"把语句覆盖当充分标准"**——语句覆盖是最弱的标准，它甚至不要求覆盖所有判定分支，覆盖率 100% 的语句覆盖也测不出“分支逻辑错误”。

## 3 覆盖率与质量的关系

- **覆盖率低 ≠ 质量差，覆盖率高 ≠ 质量好**。覆盖率只是"测到了多少结构"，不保证"测对行为"——测了一条语句但断言错了，覆盖率照计。
- **覆盖率是"必要非充分"**：低覆盖率肯定有盲区；高覆盖率只是"盲区少了"，不含"缺陷没了"。
- **覆盖率的工程用法**：团队定**覆盖率门槛**（如语句覆盖 ≥ 80%、分支覆盖 ≥ 70%），作为 CI 的守门指标——低于门槛的提交不允许合并。<span class="marginnote">覆盖率门槛要有<strong>"目标化"的智慧</strong>：对高风险模块（支付、权限）要求高覆盖，对低风险模块（工具函数、样板代码）放低要求——<strong>按风险分配覆盖目标</strong>，而不是一刀切 "100%"。盲目追求 100% 覆盖，会诱导写"凑行数的假测试"，反而稀释测试质量。覆盖率是仪表盘，不是方向盘。</span>

## 4 覆盖率的测量工具

现代工具自动插桩统计覆盖率：

**C/C++**：gcov、lcov。
**Java**：JaCoCo、Cobertura。
**Python**：coverage.py。
**JavaScript**：Istanbul / nyc。

这些工具给出**结构级覆盖**（语句/分支/条件），配合 **CI**（第 13 章）在每次提交后生成覆盖率报告、按门槛拦截。<span class="marginnote">除了"结构覆盖"，还有一类"行为覆盖"：需求覆盖（每条需求有测试对应，对应第 3 章的追踪矩阵）与缺陷覆盖（每个历史 bug 有回归用例）。完整的测试充分性判断 = <strong>结构覆盖 + 需求覆盖 + 缺陷覆盖</strong> 三个维度，结构覆盖率只是最容易量化的那一项。</span>

## 5 数值算例：四种覆盖率各要几个用例

把四种覆盖率对同一段代码的"用例需求量"算出来，最能看清它们的强弱。沿用第 1 节的示例——含一个 `if (a > 1 && b < 0)` 判定的三语句代码：

| 覆盖率 | 需要覆盖的点 | 最少用例数 | 示例用例 |
| --- | --- | --- | --- |
| 语句覆盖 | 3 条语句 | 1 组 | `a=5, b=-1`（只走真分支） |
| 分支覆盖 | 判定真、假 | 2 组 | `(5,-1)` 真 + `(0,0)` 假 |
| 条件覆盖 | 2 个条件各自真假 | 2 组 | `(5,-1)` 与 `(0,0)` 恰好也满足 |
| 路径覆盖 | 所有独立路径 | 与路径数相等 | 随分支增多指数增长 |

注意一个反直觉的点：**对单个 `&&` 条件，2 组用例能同时满足分支覆盖与条件覆盖**——但换成 `if (a > 1 || b < 0)` 或嵌套判定，条件覆盖往往需要更多用例，且两者不再互相包含。**判定结构越复杂，四种覆盖率所需的用例数差距越大**——这正是"覆盖率要按结构选"的原因：对简单判定用分支覆盖够用，对复杂判定要提升到条件甚至路径覆盖。

**辨析｜易错点：** 别被"最少用例数"误导——**最少用例数只是"达标下限"，不是"质量保证"**。用 2 组用例达到 100% 条件覆盖，只能证明"这 2 个条件各自真假都被测过"，证明不了"真实数据下系统行为正确"。覆盖率指标描述的是"结构遍历程度"，**它和"行为正确性"是两回事**——覆盖率是必要不充分的又一个实例。

## 6 核心对比表：四种覆盖率

| 维度 | 语句覆盖 | 分支覆盖 | 条件覆盖 | 路径覆盖 |
| --- | --- | --- | --- | --- |
| 覆盖对象 | 可执行语句 | 判定分支 | 子条件取值 | 独立路径 |
| 强度 | 最弱 | 中 | 中（细分） | 最强 |
| 最少用例 | 1 组即可 | 每个分支 1 组 | 每个条件取值 1 组 | 与路径数相同 |
| 典型盲区 | 假分支逻辑 | 子条件组合 | 判定组合 | 随分支指数膨胀 |
| 工具支持 | 广泛 | 广泛 | 中等 | 较少（路径爆炸） |

## 7 常见误区速查表

| 误区 | 正解 |
| --- | --- |
| "覆盖率 100% = 没 bug" | 覆盖率只是结构遍历程度，不含"行为正确" |
| "语句覆盖是最充分的标准" | 语句覆盖最弱，甚至不要求覆盖所有判定分支 |
| "分支覆盖 = 条件覆盖" | 分支覆盖看整个判定结果，条件覆盖看子条件取值 |
| "覆盖率越高越好" | 盲目追求 100% 会诱导写凑行数的假测试 |
| "覆盖率低 = 质量差" | 低覆盖必有盲区，但要结合测试投入与断言质量看 |
| "所有模块用同一覆盖率门槛" | 应按风险分配：支付/权限高覆盖，工具函数放低 |
| "覆盖率是质量证明" | 覆盖率是仪表盘不是方向盘——指出盲区，不保证正确 |
| "结构覆盖够了" | 完整充分性 = 结构覆盖 + 需求覆盖 + 缺陷覆盖 |

## 8 数值算例：覆盖门槛的团队设定

把"按风险设定覆盖门槛"落成一个团队的决策示例。假设一个电商系统，各模块风险不同：

| 模块 | 风险等级 | 语句覆盖门槛 | 分支覆盖门槛 | 理由 |
| --- | --- | --- | --- | --- |
| 支付模块 | 高 | ≥ 90% | ≥ 80% | 资金相关，缺陷代价大 |
| 订单模块 | 高 | ≥ 85% | ≥ 75% | 核心业务链路 |
| 商品浏览 | 中 | ≥ 70% | ≥ 60% | 缺陷影响面小 |
| 工具函数 | 低 | ≥ 50% | ≥ 40% | 简单样板，收益有限 |

**门槛按风险分层，而不是一刀切 100%**：对高风险模块严格，对低风险放行，把有限的测试资源投向风险最高的地方。同时用 CI 守门（第 13 章）：低于门槛的提交不合并——覆盖率从"汇报指标"变成"强制约束"。

**辨析｜易错点：** 门槛要"可达且有意义"：定得太高（100%）导致永远不达标、被迫放水；定得太低形同虚设。**每季度回顾门槛**：若覆盖总在达标线附近徘徊，说明门槛设得不够有区分度——真正的目标是引导测试资源向风险倾斜，不是追求一个好看的数字。

## 9 小结

- **语句覆盖**最弱（每条语句一次），**分支覆盖**（每分支一次）、**条件覆盖**（每条件取值一次）、**路径覆盖**最严（每条独立路径一次）。
- 覆盖率强度阶梯：语句 ≤ 分支 ≤ 路径；分支与条件**互不包含**。
- 覆盖率是"必要非充分"：低覆盖必有盲区，高覆盖不代表无缺陷。
- 工程用法：**按风险设定覆盖门槛**，由 CI 守门，而非盲目 100%。
- 完整充分性 = 结构覆盖 + 需求覆盖（追踪矩阵）+ 缺陷覆盖（回归集）。
- 覆盖率是仪表盘，不是方向盘——它指出盲区，不保证正确。
