## 为什么从层次与事件驱动开始

前面的风格要么围绕数据、要么围绕控制流。这一节的两种风格，分别引入了两个塑造现代软件的最重要思想：**层次（layered）**让依赖有方向，**事件驱动（event-driven）**让组件松耦合到"互不相识"。它们一个管"纵向的分层"，一个管"横向的解耦"，共同支撑了从 Web 应用到微服务的当代架构形态。

## 1 层次风格：单向依赖的分层

**层次结构（layered）风格**把系统分成若干**层（layer）**，每一层只使用其直接下层提供的服务，只为其上层提供服务——**依赖是单向向下的**。

经典的 Web 三层架构：

**表现层（Presentation / UI）** → **业务逻辑层（Business Logic）** → **数据访问层（Data Access / DAO）**，依赖单向向下。

层次风格的好处：

- **关注点分离**：每层只关心自己的职责（SoC 的架构级落地）。
- **可替换性**：换 UI 框架不影响业务层；换数据库不影响上层。
- **可测试性**：每层可单独测试，下层用 mock 替代。
- **标准化**：层间接口清晰，多人可并行开发各层。

代价：**层次越多，调用链越长、性能损耗越大**；严格的单向依赖有时需要"透传"（上层直接传给下层的数据，中间层被迫转发）。<span class="marginnote">关于"跨层调用"有著名的<strong>层间规则之争</strong>：严格分层禁止跨层直接调用（UI 不能直接碰 DAO），宽松分层允许上层穿透。折中实践是"依赖倒置版分层"：下层依赖上层定义的接口（如 Repository 接口由领域层定义、数据层实现），既保住单向依赖，又避免底层细节污染上层——这是 DIP 在分层架构里的标准应用。</span>

**辨析｜易错点：** "分层"不等于"按技术切分"。真正的分层按**抽象层次**切分（UI → 应用 → 领域 → 基础设施），每层的语义边界是"职责的抽象级别"；按"后端/前端/测试"切是"按物切"，不是分层。判断标准：**相邻层的接口是否表达了"更抽象的职责"？**

## 2 事件驱动风格：组件互不相识

**事件驱动（event-driven）**风格的核心：**组件不直接调用对方，而是发布（publish）事件；其他组件订阅（subscribe）感兴趣的事件，在事件发生时被通知**。<span class="marginnote">事件驱动的关键特征是<strong>间接通信</strong>：发布者不知道谁在听，订阅者不知道谁在发——双方只依赖"事件类型"这个契约。GUI 系统是经典例子：按钮点击事件被框架分发，业务代码只注册"当点击发生时执行什么"，按钮本身不依赖任何具体处理器。</span>

三种变体：

**事件处理**：单一事件流，处理器监听并响应。
**隐式调用（implicit invocation）**：事件发布后由注册表自动分发给所有订阅者。
**消息总线 / 消息队列**：事件通过中间件（MQ）传递，支持跨进程、异步、削峰。

事件驱动的优点：**松耦合**（发布订阅互不相识）、**可扩展**（新订阅者即插即用，符合 OCP）、**异步**（发布者不等处理完成）。代价：**控制流不透明**（读代码看不见事件从哪来）、**调试困难**（时序与并发问题）、**最终一致性**（订阅者可能延迟处理）。

**辨析｜易错点：** 事件驱动 ≠ 全部异步消息队列。事件可以是**进程内同步**的（观察者模式，第 6 章）也可以是**跨进程异步**的（消息总线）。两者的共性在"发布-订阅"关系，差别在传输与同步性。把同步观察者升级成消息队列，是常见却未必必要的架构决策——异步会引入一致性成本，只在真正需要解耦与削峰时才上。

## 3 两种风格的组合与取舍

| 维度 | 层次风格 | 事件驱动风格 |
| --- | --- | --- |
| 关系 | 上下分层、单向依赖 | 发布订阅、互不相识 |
| 耦合 | 层间显式接口 | 事件契约，高度松耦合 |
| 控制流 | 显式、可追踪 | 隐式、难追踪 |
| 适合 | 业务稳定、流程清晰 | 业务多变、需要解耦扩展 |
| 代价 | 层多性能损耗 | 一致性、可调试性 |

现代大型系统**两者并用**：内部用分层组织领域逻辑，跨模块/跨服务用事件驱动解耦。<span class="marginnote">典型形态：<strong>"分层 + 事件"混合架构</strong>——分层保证纵向的职责清晰，事件驱动保证横向的模块解耦。例如订单系统：订单服务内部分层，但"订单已支付"这个事件通过 MQ 广播给库存、通知、统计服务。层次管纵轴，事件管横轴，两轴正交。</span>

## 4 实战：给系统做"层次与事件"体检

把两个概念变成可执行的动作。对一个你熟悉的系统（哪怕是课程作业），按三步体检：

**第一步，画分层**：自上而下列出系统的层次。健康的层次应满足三条：**单向依赖**（上层只依赖下层）、**抽象级别递减**（上层抽象、下层具体）、**层间用接口隔开**。常见毛病是"跳过层调用"——Controller 直接绕过 Service 去访问 DAO，层次形同虚设。<span class="marginnote">判断分层是否健康有一个"依赖箭头检验"：画一张依赖图，把所有箭头<strong>从下往上数</strong>，如果存在跨层箭头或环，分层就破了。每修一处"跨层调用"，就是在给可维护性加分——这是第 4 章"单向依赖"原则在架构层的直接落地。</span>

**第二步，找事件**：系统里有哪些"不请自来"的变化？新订单、库存告警、用户登录……这些如果靠"每层轮询状态"，就是缺了事件驱动；改成发布-订阅，组件之间就解耦了。判断标准：**新增一个订阅者，要不要改发布者的代码？** 要——事件还没真正解耦；不要——事件驱动用对了。

**第三步，做取舍**：把"分层管纵轴、事件管横轴"写进架构文档，明确"哪些变化走层内接口、哪些走事件"。这一步的价值是把隐性的设计直觉变成显性的团队共识。

**辨析｜易错点：** 事件驱动最常见的坑是**滥用**：把本可以同步调用的简单请求也改成事件，结果排查问题时"一个请求变成一团乱麻"，违背了事件驱动"松耦合"的初衷。**事件用于"需要解耦、允许异步、关注点正交"的场景**；顺序强依赖、需要即时回执的调用，老老实实走同步接口。

## 5 分层与事件驱动：一张对照速查

把两个风格摆在一起，最常被问的三个问题一次说清：

| 问题 | 层次风格 | 事件驱动 |
| --- | --- | --- |
| 组织依据 | 抽象级别（从高到低） | 关注点正交（谁关心什么） |
| 依赖方向 | 上层依赖下层，单向 | 发布者与订阅者互不相识 |
| 扩展方式 | 新增层内模块 | 新增订阅者 |
| 主要收益 | 可理解性、可替换 | 松耦合、可扩展 |
| 主要代价 | 层级僵化、跨层绕路 | 控制流不透明、最终一致 |

**辨析｜易错点：** 层次风格和事件驱动不是"二选一"，而是**两个正交的轴**。一个系统可以既有"Controller → Service → DAO"的层次纵轴，又有"订单事件广播给通知服务、报表服务"的事件横轴。判断它们是否健康的共同标准只有一条：**每次新增需求，改动是否被局限在小范围**——动纵轴（加层内逻辑）不该动横轴（事件订阅），反之亦然。

**一个记忆锚点：** 分层管"纵"，事件管"横"。画一张坐标系，横轴是"谁关心这个变化"（事件），纵轴是"谁依赖谁"（层次）——绝大多数现代系统的架构图，都可以在这张坐标系里找到自己的位置。

## 6 一个动手练习：重构一处"跨层调用"

把理论变成手感，做一次真实的"分层体检"。找一段你手头的三层代码（Controller → Service → DAO），回答三个问题：

1. **有没有绕过 Service 直连 DAO？** 有——把它收回 Controller → Service → DAO 的正常链路，并问一句"为什么当初绕过"：若是为了快，写进注释，让后人知道这是有意的权衡；若只是图省事，这就是要修的第一处。
2. **新增一个事件订阅方，改了几个文件？** 三个以上——事件还没解耦，应该只新增订阅者一个文件。若发布者被改，说明事件携带的"消息结构"不够通用，先收敛消息协议。
3. **层次之间用的是接口还是具体类？** 具体类——换实现就要改调用方，违反第 4 章"面向接口"。改成接口注入，层次才真的可替换。

这一轮体检做完，你对"层次管纵、事件管横"的理解就不再停留在概念，而是能对着真实代码说出"这里哪里破了、该怎么修"。**架构素养的养成，靠的是这种一次次的小体检，而不是背下概念清单。**

**辨析｜易错点：** 还有一种常见混淆是"事件驱动"与"消息队列"划等号。消息队列只是事件的**传输载体**，事件驱动的灵魂是**语义**——发布者不关心谁消费、消费方各自订阅。用队列却还是"点对点指定消费者"的，本质还是同步调用的异步化，解耦收益有限。真正的判断标准始终是那句：**发布者改代码时，需要知道订阅者存在吗？** 不需要——事件驱动；需要——只是换了传输方式的调用。

## 7 小结

- **层次风格**按抽象级别分层，依赖单向向下：表现 → 业务 → 数据访问。
- 分层的收益是关注点分离、可替换、可测试；代价是层间透传与性能损耗。
- 分层按**抽象级别**切分，不是按技术物切分。
- **事件驱动**用发布-订阅解耦组件，发布者与订阅者互不相识。
- 事件驱动收益是松耦合与可扩展，代价是控制流不透明与最终一致性。
- 现代架构"分层管纵轴、事件管横轴"，两者正交组合。
- 判断健康的共同标准：每次新增需求，改动被局限在小范围（动纵轴不碰横轴，反之亦然）。
- 依赖箭头检验：图中出现跨层调用或环，说明层次已破。

- 事件 ≠ 消息队列：队列是传输载体，事件是"发布者不知订阅者"的语义。
- 层次与事件是正交轴：纵轴管抽象级别，横轴管关注点解耦。
