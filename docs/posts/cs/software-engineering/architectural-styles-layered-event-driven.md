## 为什么从层次与事件驱动开始

前面的风格要么围绕数据、要么围绕控制流。这一节的两种风格，分别引入了两个塑造现代软件的最重要思想：**层次（layered）**让依赖有方向，**事件驱动（event-driven）**让组件松耦合到"互不相识"。它们一个管"纵向的分层"，一个管"横向的解耦"，共同支撑了从 Web 应用到微服务的当代架构形态。

## 1 层次风格：单向依赖的分层

**层次结构（layered）风格**把系统分成若干**层（layer）**，每一层只使用其直接下层提供的服务，只为其上层提供服务——**依赖是单向向下的**。

经典的 Web 三层架构：

```
表现层（UI）        ← 接收输入、展示输出
     ↓ 调用
业务逻辑层（Service） ← 业务规则、事务
     ↓ 调用
数据访问层（DAO）    ← 读写数据库
```

层次风格的好处：

- **关注点分离**：每层只关心自己的职责（SoC 的架构级落地）。
- **可替换性**：换 UI 框架不影响业务层；换数据库不影响上层。
- **可测试性**：每层可单独测试，下层用 mock 替代。
- **标准化**：层间接口清晰，多人可并行开发各层。

代价：**层次越多，调用链越长、性能损耗越大**；严格的单向依赖有时需要"透传"（上层直接传给下层的数据，中间层被迫转发）。<span class="marginnote">关于"跨层调用"有著名的<strong>层间规则之争</strong>：严格分层禁止跨层直接调用（UI 不能直接碰 DAO），宽松分层允许上层穿透。折中实践是"依赖倒置版分层"：下层依赖上层定义的接口（如 Repository 接口由领域层定义、数据层实现），既保住单向依赖，又避免底层细节污染上层——这是 DIP 在分层架构里的标准应用。</span>

**辨析｜易错点：** "分层"不等于"按技术切分"。真正的分层按**抽象层次**切分（UI → 应用 → 领域 → 基础设施），每层的语义边界是"职责的抽象级别"；按"后端/前端/测试"切是"按物切"，不是分层。判断标准：**相邻层的接口是否表达了"更抽象的职责"？**

## 2 事件驱动风格：组件互不相识

**事件驱动（event-driven）**风格的核心：**组件不直接调用对方，而是发布（publish）事件；其他组件订阅（subscribe）感兴趣的事件，在事件发生时被通知**。<span class="marginnote">事件驱动的关键特征是<strong>间接通信</strong>：发布者不知道谁在听，订阅者不知道谁在发——双方只依赖"事件类型"这个契约。GUI 系统是经典例子：按钮点击事件被框架分发，业务代码只注册"当点击发生时执行什么"，按钮本身不依赖任何具体处理器。</span>

三种变体：

- **事件处理**：单一事件流，处理器监听并响应。
- **隐式调用（implicit invocation）**：事件发布后由注册表自动分发给所有订阅者。
- **消息总线 / 消息队列**：事件通过中间件（MQ）传递，支持跨进程、异步、削峰。

事件驱动的优点：**松耦合**（发布订阅互不相识）、**可扩展**（新订阅者即插即用，符合 OCP）、**异步**（发布者不等处理完成）。代价：**控制流不透明**（读代码看不见事件从哪来）、**调试困难**（时序与并发问题）、**最终一致性**（订阅者可能延迟处理）。

**辨析｜易错点：** 事件驱动 ≠ 全部异步消息队列。事件可以是**进程内同步**的（观察者模式，第 6 章）也可以是**跨进程异步**的（消息总线）。两者的共性在"发布-订阅"关系，差别在传输与同步性。把同步观察者升级成消息队列，是常见却未必必要的架构决策——异步会引入一致性成本，只在真正需要解耦与削峰时才上。

## 3 两种风格的组合与取舍

| 维度 | 层次风格 | 事件驱动风格 |
| --- | --- | --- |
| 关系 | 上下分层、单向依赖 | 发布订阅、互不相识 |
| 耦合 | 层间显式接口 | 事件契约，高度松耦合 |
| 控制流 | 显式、可追踪 | 隐式、难追踪 |
| 适合 | 业务稳定、流程清晰 | 业务多变、需要解耦扩展 |
| 代价 | 层多性能损耗 | 一致性、可调试性 |

现代大型系统**两者并用**：内部用分层组织领域逻辑，跨模块/跨服务用事件驱动解耦。<span class="marginnote">典型形态：<strong>"分层 + 事件"混合架构</strong>——分层保证纵向的职责清晰，事件驱动保证横向的模块解耦。例如订单系统：订单服务内部分层，但"订单已支付"这个事件通过 MQ 广播给库存、通知、统计服务。层次管纵轴，事件管横轴，两轴正交。</span>

## 4 小结

- **层次风格**按抽象级别分层，依赖单向向下：表现 → 业务 → 数据访问。
- 分层的收益是关注点分离、可替换、可测试；代价是层间透传与性能损耗。
- 分层按**抽象级别**切分，不是按技术物切分。
- **事件驱动**用发布-订阅解耦组件，发布者与订阅者互不相识。
- 事件驱动收益是松耦合与可扩展，代价是控制流不透明与最终一致性。
- 现代架构"分层管纵轴、事件管横轴"，两者正交组合。
