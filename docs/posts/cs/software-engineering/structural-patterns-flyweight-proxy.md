## 为什么从享元与代理开始

这是结构型模式的最后两个。**享元**解决"海量细粒度对象的共享"，**代理**解决"对对象的间接访问控制"。一个面向性能（内存），一个面向边界（控制），是完全不同的两类问题，但都通过"再包一层结构"实现。

## 1 享元：共享对象的内蕴状态

**享元（Flyweight）**：通过**共享**支持大量细粒度对象，把对象状态拆成两部分——**内蕴状态（intrinsic）**（可共享、不随环境变）与**外蕴状态（extrinsic）**（随环境变、由调用方传入）。

经典例子：**文本编辑器渲染字符**。一篇文档可能有上万个字符对象，每个都含字体、字号、颜色——内存爆炸。用享元：字符本身（"a"、"b"、"c"……）是内蕴状态，每字符只建一个对象共享；位置、颜色等外蕴状态由渲染时传入。<span class="marginnote">享元的本质是"<strong>对象共享 + 状态分离</strong>"：把不可变、可复用的部分做成共享单例，把可变的部分移到外部。它的现代变体无处不在：字符串常量池、整数缓存（`Integer` 的缓存）、数据库连接池——都是"共享可复用资源"的思想。判断用不用享元：<strong>对象数量是否巨大、且存在大量可共享的重复状态</strong>。</span>

**辨析｜易错点：** 享元 ≠ 单例。单例是"全局只有一个实例"；享元是"同类对象共享同一实例，但外蕴状态各不相同"。享元工厂（FlyweightFactory）按内蕴状态建池，同一内蕴状态返回同一实例——池的思想是关键，别把它和单例混为一谈。

## 2 代理：给访问加一层控制

**代理（Proxy）**：为另一个对象提供**替身或占位符**，以控制对这个对象的访问。

结构：**Subject**（接口）、**RealSubject**（真实对象）、**Proxy**（替身，持有 RealSubject 引用，转发调用并在前后附加控制）。

代理的四种常见用途：

**虚拟代理（Virtual Proxy）**：**懒加载**——真实对象创建成本高时，先放占位，第一次真正使用时才创建。
**远程代理（Remote Proxy）**：代表远程对象（RPC 的本地桩）。
**保护代理（Protection Proxy）**：访问控制——校验权限后再转发。
**智能引用（Smart Reference）**：附加操作（计数、锁、日志）。<span class="marginnote">代理在框架里无处不在：ORM 的懒加载代理（访问属性才查库）、Spring AOP 的动态代理、网络请求的缓存代理。它与装饰的区别（上一节）：装饰<strong>改行为</strong>（加功能），代理<strong>管访问</strong>（控制边界）——同一结构、不同意图。</span>

**辨析｜易错点：** 代理 vs 适配器：适配器**改接口**（让不匹配的接口可用），代理**保持接口**（同一接口、加控制）。代理 vs 外观：外观是"简化入口"，代理是"替身控制"。判断标准：**接口变没变？变了是适配器；接口没变、只是加了控制，是代理。**

## 3 享元 vs 代理：性能与控制

| 维度 | 享元 | 代理 |
| --- | --- | --- |
| 目的 | 减少对象数量（省内存） | 控制对象访问（管边界） |
| 机制 | 共享内蕴状态 + 外蕴状态外置 | 占位符 + 转发 + 附加控制 |
| 典型场景 | 海量字符/节点/缓存 | 懒加载、远程、权限、日志 |
| 主要代价 | 状态分离增加复杂度 | 间接层带来调用开销 |
| 现代变体 | 缓存池、字符串驻留 | 动态代理、ORM 懒加载 |

**辨析｜易错点：** 两个模式都"多了一层结构"，但目标相反：享元是**减**（少建对象），代理是**加**（多一层控制）。用错了方向，要么内存照旧爆炸，要么平白多一层间接。

## 4 数值算例：享元能省多少内存

把享元的收益算成数字。假设渲染一篇 10 万字的文档，每个字符对象占 $S$ 字节（含字体、字号、颜色等字段）。**不用享元**：每出现一个字符就建一个对象，内存约 $10^5 \times S$；**用享元**：内蕴状态只按「不同字符」建——中英文常用字符集不过几千个，设 $K$ 为不同字符数，内存约 $K \times S$，加上外蕴状态（位置、颜色）以轻量方式传入。

以 $S = 32$ 字节、$K = 2000$ 为例：非享元 $10^5 \times 32 = 3.2$ MB；享元约 $2000 \times 32 = 64$ KB——**节省两个数量级**。这个量级对比就是享元的全部说服力：<span class="marginnote">数字背后的直觉是「把重复的不可变状态拿出来共享」。代价是对象身份变得微妙——共享实例没有独立身份，所以外蕴状态必须由外部传入，<strong>不能放进共享对象内部</strong>。这一条违反了就是内存照旧爆炸，还把共享的逻辑搞乱。</span>当对象数以百万计、且重复状态占比高时，享元几乎总是值得。

## 5 一个虚拟代理的代码形态

虚拟代理的「懒加载」结构，用一段代码看得最清楚：

```python
class Image:                       # Subject：接口
    def display(self): ...

class RealImage(Image):            # RealSubject：昂贵的真实对象
    def __init__(self, path):
        self._data = load_from_disk(path)   # 昂贵的加载
    def display(self): ...

class ImageProxy(Image):           # Proxy：替身，延迟创建
    def __init__(self, path):
        self._path = path
        self._real = None          # 先不加载
    def display(self):
        if self._real is None:
            self._real = RealImage(self._path)  # 首次使用时才加载
        self._real.display()
```

在图片浏览器的列表页，`ImageProxy` 让成百上千的缩略图**占位不加载**；只有真正点开大图时才走 `RealImage` 的昂贵路径——启动速度与内存都因此大幅改善。懒加载的代价是「第一次访问有延迟」，所以要按「延迟是否可接受」来决定用不用虚拟代理。

## 6 结构型七模式的意图速记

把七个结构型模式放进一张表，便于整体把握与选型：

| 模式 | 一句话意图 | 核心结构 | 典型场景 |
| --- | --- | --- | --- |
| 适配器 | 让不匹配的接口配合 | Target + Adaptee + Adapter | 接入遗留系统、第三方库 |
| 桥接 | 抽象与实现独立变化 | Abstraction + Implementor | 形状×绘制、平台×业务 |
| 组合 | 部分-整体统一处理 | Component + Leaf + Composite | 文件系统、UI 组件树 |
| 装饰 | 动态叠加功能 | Component + Decorator | 咖啡配方、I/O 流 |
| 外观 | 复杂子系统的统一入口 | Facade + 子系统类 | 框架模板类、编译入口 |
| 享元 | 共享内蕴状态省内存 | Flyweight + 工厂池 | 海量字符、缓存池 |
| 代理 | 替身控制访问 | Subject + RealSubject + Proxy | 懒加载、权限、RPC |

**选型的主线是"接口与状态"**：接口不匹配→适配器；多维独立变化→桥接；树形递归→组合；功能叠加→装饰；子系统太乱→外观；对象太多→享元；访问要控制→代理。**结构型模式的共同主题，是用组合调整结构、把变化隔离在最小半径**——它们与第 4 章的"高内聚低耦合"、第 4 章的 SOLID 原则是同一个设计哲学在不同层面的展开。

## 7 术语速查表

| 术语 | 英文 | 一句话定义 |
| --- | --- | --- |
| 享元 | Flyweight | 共享内蕴状态、外置外蕴状态以支持海量对象 |
| 内蕴状态 | Intrinsic State | 可共享、不随环境变的不可变部分 |
| 外蕴状态 | Extrinsic State | 随环境变、由调用方传入的部分 |
| 享元工厂 | Flyweight Factory | 按内蕴状态建池，同一状态返回同一实例 |
| 代理 | Proxy | 为对象提供替身，在转发前后附加控制 |
| 虚拟代理 | Virtual Proxy | 懒加载：首次真正使用时才创建真实对象 |
| 保护代理 | Protection Proxy | 先做权限校验再转发访问 |

## 8 小结

- **享元**把对象拆成内蕴（共享）与外蕴（外置）状态，通过共享支持海量细粒度对象。
- 内存对比：$10^5 \times S$ 对 $K \times S$，重复状态占比高时省出数量级。
- 享元 ≠ 单例：享元按内蕴状态建池，同类对象共享实例但外蕴状态各异。
- **代理**为对象提供替身，控制访问：虚拟（懒加载）、远程、保护、智能引用。
- 代理保持接口、加控制；适配器改接口；装饰改行为；外观简化入口。
- 享元「省内存」，代理「管边界」——目标相反，勿混。
