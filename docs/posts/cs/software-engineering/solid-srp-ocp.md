## 为什么从 SOLID 开始

上一节的"内聚耦合"给了度量，这一节的 **SOLID** 给处方。SOLID 是面向对象设计最著名的五条原则的首字母缩写，由 Robert C. Martin（Bob 大叔）系统化提出。它回答一个日常问题：**加一个功能时，代码为什么越改越烂？** 五条原则分别从不同角度抑制"改烂"。这一节讲前两条：**单一职责（S）**与**开闭原则（O）**——最基础、也最容易被误读的两条。

## 1 单一职责原则（SRP）：一个类只有一个改变的理由

**单一职责原则（Single Responsibility Principle, SRP）**：**一个类应该只有一个引起它变化的原因，即只有一个职责**。

职责（responsibility）不是"功能"而是"**改变的动机（reason to change）**"。判断方法：**问"这个类会因为几种不同的需求变化而被修改？"答案 > 1，就违反了 SRP**。

以经典的 **Employee（员工）** 类为例：它同时承载"业务规则（算工资）""报表格式化（转 JSON/HTML）""持久化（存数据库）"三类职责——三股不同的变化力量（改工资规则、改报表格式、换数据库）都会迫使它修改。<span class="marginnote">三类职责合一，是"上帝类（God Class）"的温床：类越长、依赖越多、测试越难写，任何一处改动都可能踩雷。SRP 的解法是拆：业务规则归 <strong>EmployeeService</strong>`，格式化归 <strong>EmployeeReportFormatter</strong>`，持久化归 <strong>EmployeeRepository</strong>——每个类只有一个改变的理由。</span>

**辨析｜易错点：** SRP ≠ "一个类只做一个函数"。**Employee 类** 可以有"算工资、算税金、算休假"多个方法——它们都属于"员工业务规则"这一**同一个改变理由**。SRP 的粒度是"改变的理由"而非"方法的数量"。

## 2 开闭原则（OCP）：对扩展开放，对修改关闭

**开闭原则（Open-Closed Principle, OCP）**：**软件实体（类、模块、函数）应该对扩展开放，对修改关闭**。含义是：**新增功能应通过"增加新代码"实现，而不是"修改已有代码"**。

直觉：已发布、已测试、已被同事依赖的代码，改它意味着重测、回归、风险。所以设计者希望**老代码永远不改，新功能靠加**——加新子类、加新策略、加新实现，而不是在 **if-else / switch** 里再插一条分支。

经典例子：画图程序计算面积——用 **if-else 判断图形类型** 计算，每加一种图形就要改这段判断。按 OCP 重构：定义抽象 **Shape 接口**，每种图形实现自己的 **area()**；加新图形 = 加新类，计算代码一字不改。<span class="marginnote">这里的载体是<strong>多态（polymorphism）</strong>：基类或接口定义"扩展点"，具体实现各自封闭。OCP 在工程上的体现是"扩展点"设计——接口、策略模式、依赖注入，都是给未来的变化预留位置。</span>

## 3 SRP 与 OCP 的因果

两条原则有深刻的因果联系：

**SRP 是 OCP 的前提**：只有每个类职责单一、改变理由唯一，"通过增加新类实现扩展"才可行——因为扩展往往意味着"新增一个职责实现"。
**OCP 是 SRP 的收益**：职责分离后，系统对变化的应对从"改老代码"转向"加新代码"，自然对扩展开放。

**辨析｜易错点：** OCP 最著名的误读是"设计时预测所有变化、到处预留扩展点"。这会造出抽象泛滥、过度设计的系统。OCP 的正确姿势是**"被变化驱动"**：先写出简单直接的代码，**当第二个相似变化真正出现时**，才抽象出扩展点——业界称之为"三次法则（rule of three）"或"YAGNI（你不会需要它）"。<span class="marginnote">这一平衡（OCP 与 YAGNI 的张力）正是设计经验的核心：预留太少，加功能就改老代码；预留太多，系统死于抽象。成熟做法是把 OCP 主要用在<strong>变化频繁或明确可预期</strong>的方向（如支付渠道、插件机制），其余方向保持简单。</span>

## 4 一条容易混淆的孪生原则

与 SRP 相邻的还有一条**接口分离（ISP）**与**依赖倒置（DIP）**，它们属于下一节的内容。这里先指出一个常被混淆的配对：

- **SRP** 关心**一个类**的职责个数。
- **接口隔离（ISP）** 关心**一个接口**的方法个数——接口要小、专，客户端不应被迫依赖它不用的方法。

一句话：SRP 约束**实现者**，ISP 约束**使用者**。很多人把两者混为一谈，因为它们都指向"拆分"，但拆的对象不同：一个拆类，一个拆接口。

## 5 数值算例：OCP 的扩展代价

把「开闭」的收益算成维护成本。设想一个画图程序，目前支持圆形、方形、三角形三种图形，每加一种图形，`area()` 计算要么改一次 if-else、要么加一个新类：

- **if-else 版本**：三种图形共 1 个 `area()` 函数、内含 3 条分支。加第 4 种图形，要**修改**这个函数（加 1 条分支）——已有 3 种图形的代码被触碰，全部相关用例要重跑（第 8 章回归测试）。
- **多态版本（OCP）**：1 个 `Shape` 接口 + 3 个实现类。加第 4 种图形，要**新增** 1 个类，已有 3 个类一字不改——只对新类写测试。

两种方案在「第 4 种图形出现时」的成本差别，正是 OCP 的价值：**一个「改」+ 全量回归，一个「加」+ 局部测试**。当图形类型增长到第 10 种、第 20 种时，if-else 版本每次新增都要重测全部历史分支，多态版本永远只测新类——扩展的边际成本从「随规模上升」变成「恒定」。<span class="marginnote">这正是第 8 章「回归集」与 OCP 的交叉点：<strong>OCP 设计让回归集保持小</strong>——改动越少，需要重跑的用例越少。这也是为什么「开闭」不只是美学，而是直接作用于测试成本的工程决策。</span>

## 6 一个 SRP 重构的完整案例

把 SRP 从"拆类"落到具体代码。假设一个 `Employee` 类同时承担"业务规则 + 报表格式化 + 持久化"三件事，常见的长这样（示意）：

```python
class Employee:
    def compute_pay(self): ...      # 算工资（业务规则）
    def to_json(self): ...          # 转 JSON 上报（格式化）
    def save(self): ...             # 存数据库（持久化）
```

**它有三股不同的改变力量**：改工资规则要动 `compute_pay`，改报表格式要动 `to_json`，换数据库要动 `save`——同一个类被三类需求拉扯。按 SRP 拆成三个类：

```python
class Employee:
    def compute_pay(self): ...      # 只剩业务规则，改变理由唯一

class EmployeeReportFormatter:
    def to_json(self, employee): ...  # 格式化独立成类

class EmployeeRepository:
    def save(self, employee): ...     # 持久化独立成类
```

拆分后的收益立即可见：**改报表格式不再触碰业务规则类**，`Employee` 的测试不再被格式化与数据库代码污染；三类变化各自独立演进、独立测试。这就是 SRP 的实操——**当"改变的动机"多于一个时，沿着动机拆类**。

**辨析｜易错点：** SRP 拆分的边界不是"代码行数"而是"改变的理由"。**如果 `compute_pay`、`to_json`、`save` 永远一起变（比如这只是个内部工具类、从不需要单独改某一部分），拆开反而是过度设计**。SRP 的正确用法是"按真实的变化需求拆"，不是"按方法功能机械地拆"——这与 OCP 的"被变化驱动"是同一哲学。

## 7 术语速查表

| 术语 | 英文 | 一句话定义 |
| --- | --- | --- |
| 单一职责 | Single Responsibility | 一个类只有一个引起它变化的原因 |
| 开闭原则 | Open-Closed | 对扩展开放、对修改关闭 |
| 改变的理由 | Reason to Change | 判断 SRP 的粒度：几种需求会迫使类修改 |
| 扩展点 | Extension Point | 为未来变化预留的接口/抽象位置 |
| 上帝类 | God Class | 职责过多、过长的类（SRP 的反面） |
| 三次法则 | Rule of Three | 出现两个相似变化后再抽象扩展点 |

## 8 常见误区速查表

| 误区 | 正解 |
| --- | --- |
| "SRP = 一个类只做一件事" | SRP 粒度是"改变的理由"，一个类可以有多个相关方法 |
| "OCP = 预测所有变化" | OCP 要被变化驱动，第二个相似变化出现才抽象扩展点 |
| "SRP = ISP" | SRP 约束实现类，ISP 约束接口，拆的对象不同 |
| "OCP 用 if-else 也行" | OCP 靠多态与扩展点，加新类型不改老代码 |
| "拆得越细越好" | 过度拆分造出抽象泛滥，YAGNI 防止过度设计 |
| "扩展点越多越灵活" | 预留太多系统死于抽象，只在频繁变化方向预留 |
| "加需求就得改老类" | OCP 设计下加新功能靠"加新类"，老类一字不改 |
| "重构后不用验证" | 用回归测试与度量证明结构确实变好 |

## 9 小结

- **SRP**：一个类只有一个改变的理由；判断靠「几种需求会迫使它修改」。
- SRP 的粒度是**改变的理由**，不是方法的数量。
- **OCP**：对扩展开放、对修改关闭——新增功能靠「加代码」而非「改代码」。
- OCP 的实现载体是**多态与扩展点**，但应用要**被变化驱动**，防止过度设计。
- 扩展成本对比：if-else「改 + 全量回归」vs 多态「加 + 局部测试」，边际成本从上升变恒定。
- SRP 与 OCP 互为因果：职责单一支撑扩展开放，扩展开放回报职责分离；SRP 管「拆类」，ISP 管「拆接口」。
