# 重构手法：提炼、搬移与重组数据

## 为什么从重构手法开始

上一节识别了坏味道，这一节讲**怎么治**——**重构（refactoring）**的具体手法。重构的定义是：**在不改变软件可观察行为的前提下，改进代码结构**。Fowler 给出了几十种手法，按操作类型分几组。这一节讲最基础也最常用的一组：**提炼（Extract）**、**搬移（Move）**、**重组数据（Reorganize Data）**。

## 1 重构的前提：测试保护

在讲手法之前，必须先立一条铁律：**重构必须有测试保护**。

重构的定义是"行为不变"——但"行为不变"靠什么保证？**靠测试**。没有测试的重构是"盲改"：你改了结构，但不知道行为变没变，直到上线崩了才知道。<span class="marginnote">重构的标准循环是"<strong>测试先行</strong>"：重构前先确保该代码有测试（没有就补），重构时<strong>小步修改、每步跑测试</strong>，测试红了立刻回退。这与第 8 章 TDD 的"红-绿-重构"无缝衔接——TDD 用测试驱动写代码，重构用测试保护改代码。<strong>没有测试保护的重构不是重构，是赌博</strong>。</span>

**辨析｜易错点：** "重构"这个词被滥用了——很多人把"重写这段代码"也叫重构。**重构是"小步、行为不变、测试保护"的修改**；重写是"推倒重来、行为可能变"。两者目标不同、风险不同：**重构安全但要耐心，重写快但危险**。判断标准：**这次修改，测试能证明行为没变吗？** 能证明才是重构。

## 2 提炼：拆出方法、类与变量

**提炼（Extract）**是重构的第一手法，对付"过长方法、过大类、重复代码"：

- **提炼函数（Extract Function）**：把一段逻辑从方法中抽成独立方法——消除过长方法与重复。
- **提炼类（Extract Class）**：把一个类的一部分字段与方法抽成新类——消除过大类。
- **提炼变量（Extract Variable）**：把表达式的一部分抽成有名字的变量——消除神秘表达式。
- **引入参数对象（Introduce Parameter Object）**：把一组散参数封装成对象——消除过长参数列表。

**公式解析**：提炼的本质是"**给一段逻辑一个名字，并把它隔离出来**"。以提炼函数为例：原方法中的一段独立逻辑

$$
f(x) = \text{step1}(x) + \text{step2}(x)
$$

把 $\text{step1}$ 提炼成方法 $g(x)$ 后：

$$
f(x) = g(x) + \text{step2}(x)
$$

**行为完全相同，但 $g$ 现在可单独测试、可复用、可命名**——这就是重构"行为不变、结构变好"的数学表达。<span class="marginnote">提炼的选择标准值得想清楚：<strong>不是"代码长了就提炼"，而是"这段逻辑有一个清晰意图、可以独立命名"时才提炼</strong>。为提炼而提炼会把方法拆得稀碎（"每三行一个方法"）。Fowler 的判断标准：<strong>提炼出的方法能用一个好名字表达其意图</strong>——能命名，才值得提炼；命名不出来，说明这段逻辑还不清晰。</span>

## 3 搬移：把代码放到它该在的地方

**搬移（Move）**类重构对付"依恋情结、霰弹式修改、功能错位"：

**搬移函数（Move Function）**：一个方法过度使用别的类的数据，就把它搬过去——治"依恋情结"。
**搬移字段（Move Field）**：字段放在错误的类里，搬去它真正所属的类。
**搬移语句到调用方/被调用方（Move Statements）**：把相关语句移到更合适的位置。

**辨析｜易错点：** 搬移的判断标准是"**这段代码的"宿主"是谁**"——它读写谁的数据多、和谁一起变化，就住在谁家。判断"依恋情结"的标准：**一个方法里，用自己的字段多，还是用别的对象的字段多？** 用别人的多，它就想搬家。搬移不是"乱搬"，是**让代码住在它数据与责任的家**——搬对了，内聚上升、耦合下降。

## 4 重组数据：让数据表达更清晰

**重组数据（Reorganizing Data）**类重构对付"数据表达不清"：

**封装变量（Encapsulate Variable）**：把直接暴露的字段封装成访问方法——控制读写、便于加逻辑。
**拆分变量（Split Variable）**：一个变量被复用为多个不同含义——各自独立命名。
**改名（Rename Variable / Function / Class）**：让名字表达真实意图——最便宜也最容易被忽略的重构。
**以查询取代派生变量（Replace Derived Variable with Query）**：不存"可计算的值"，改为需要时算——消除不一致。

**辨析｜易错点：** 改名是最简单却最被低估的重构——"**命名是代码最重要的文档**"（第 4 章"神秘命名"坏味道）。一个准确的名字省去读者大量推理。判断标准：**新人读你的变量名/函数名，能猜出它干什么吗？** 猜不出，就该改名。改名看似微小，但积累起来是代码可读性的最大杠杆。<span class="marginnote">重组数据提醒我们一个深刻观点：<strong>数据结构比算法更值得精心设计</strong>（呼应第 5 章数据建模）。重构时优先把"数据怎么表达"想清楚——字段放对类、名字起对、可计算的不冗余存储——往往比优化算法更提升可维护性。很多"难以修改"的代码，病根不在逻辑，在数据表达得一团糟。</span>

## 5 小结

- **重构** = 行为不变、结构变好；**必须有测试保护**——没测试的重构是赌博。
- 重构是"小步、行为不变、测试保护"的修改；重写是"推倒重来"，两者不同。
- **提炼**（函数/类/变量/参数对象）治"过长与重复"；提炼的标准是"能起好名字"。
- **搬移**（函数/字段/语句）治"依恋与错位"，让代码住在"数据与责任的家"。
- **重组数据**（封装/拆分/改名/查询替代）治"数据表达不清"；**改名是最被低估的重构**。
- 数据结构比算法更值得精心设计——很多难改的代码病根在数据表达。
