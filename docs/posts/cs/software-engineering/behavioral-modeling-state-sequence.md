## 为什么从行为建模开始

场景与类模型画出了系统的"静态骨架"：有哪些参与者、哪些类、什么关系。但软件是**活的**——对象随时间改变状态，多个对象在同一时间点相互协作。**行为建模（behavioral modeling）**捕捉这个动态面，核心工具是**状态图（state diagram）**与**顺序图（sequence diagram）**：前者管"单个对象的状态演化"，后者管"多个对象间的消息时序"。

## 1 状态图：对象的生命周期

**状态图**描述一个对象在生命周期内经历的状态及其转换。四要素：

- **状态（state）**：对象满足某条件、等待某事件时的可区分情况，如「图书：在馆 / 借出 / 预约中 / 丢失」。
- **事件（event）**：触发状态转换的外部刺激，如「借出」事件。
- **转换（transition）**：在事件驱动下从状态 A 到状态 B 的迁移，常带守卫条件（guard）。
- **初始状态与终止状态**：实心圆起点与靶心终点。

一个典型的状态转换：`在馆 --[读者借出]--> 借出 --[读者归还]--> 在馆`，其中「读者借出」是事件，借出前后系统要执行的动作（登记、改库存）可以挂在转换上标注。<span class="marginnote">状态图的建模口诀：<strong>找状态变化，找触发事件，找守卫条件</strong>。最容易漏的是"隐藏状态"——比如「借出」状态下还有「逾期未还」这个子状态，它触发罚款动作。状态图建模越细，后面测试的"状态覆盖"越完整。</span>

**辨析｜易错点：** 状态与事件容易搞混。状态是**持续存在的条件**（"在馆"是一个持续状态），事件是**瞬间发生的刺激**（"点击借出"是瞬间动作）。"系统正在处理请求"是状态；"用户点击了提交"是事件。把事件当状态，状态图会画成一张混乱的步骤清单。

## 2 顺序图：对象间的消息时序

**顺序图**以**时间为纵轴**，画出一组对象及其生命周期线，对象间的**消息（message）**用带箭头的水平线表示，从上到下构成时序。<span class="marginnote">顺序图的生命线画成竖虚线，顶端是对象框；消息箭头按时间从上往下排。同步调用用实心箭头，异步消息用空心箭头，返回消息用虚线箭头。这些记号虽小，却表达了"谁在等谁"——异步设计里调用方不等结果继续做别的事，是并发与响应性设计的雏形。</span>

「借书」用例的顺序图大致是：

```
读者       界面        借阅控制器     图书         库存
 |--检索--->|          |              |             |
 |          |--查询--->|              |             |
 |          |<--书目---|              |             |
 |--借出--->|          |              |             |
 |          |--校验--->|--检查--->    |             |
 |          |          |<--可借------|             |
 |          |          |--减库存------------------>|
 |          |<--成功---|              |             |
```

顺序图的价值在于**暴露协作逻辑**：谁能直接调谁、谁必须经过谁（依赖关系）、消息是同步还是异步、有没有循环与分支。它是"职责分配"的沙盘——控制器该不该替读者直接改库存？顺序图上一目了然。

## 3 两种图的协作分工

| 维度 | 状态图 | 顺序图 |
| --- | --- | --- |
| 关注点 | 单个对象的生命周期 | 多个对象的交互时序 |
| 表达 | 状态 + 事件 + 转换 | 对象 + 消息 + 时间 |
| 揭示 | 隐藏状态、非法转换 | 职责分配、依赖关系 |
| 测试价值 | 状态覆盖、转换覆盖 | 接口契约、时序错误 |

**辨析｜易错点：** 状态图与顺序图不是"二选一"，而是**互补视角**。对复杂状态的对象（订单、任务、连接）用状态图；对一次具体用例的协作过程用顺序图。真正容易犯的错误是**画错图的对象粒度**——状态图只对一个对象画，顺序图要画出参与用例的所有对象；把状态图画成"系统级"就会含糊不清。

## 4 行为模型如何服务下游

行为建模不是摆设，它直接喂养设计与测试：

- **状态图 → 状态相关测试**：每个状态、每条转换、每个守卫条件都是一条测试用例的素材——「在馆状态下借出应成功，借出状态下再借出应被拒」。
- **顺序图 → 接口设计**：消息即方法调用，顺序图里的每条消息都会变成接口方法，消息参数即方法签名。
- **状态图 → 持久化设计**：需要区分状态的对象，通常在数据库里有一个"状态字段"——状态枚举的定义要回到状态图核对。<span class="marginnote">这与第 8 章《软件测试》的路径覆盖、第 4 章《面向对象设计》的职责分配构成一条完整链条：分析阶段的行为模型，就是设计阶段与测试阶段的行为基准。</span>

## 5 小结

- **状态图**描述单个对象的生命周期：状态、事件、转换、守卫条件、初始与终止状态。
- 状态是**持续条件**，事件是**瞬间刺激**，二者不可混淆。
- **顺序图**以时间纵轴表达对象间的消息时序，揭示职责分配与依赖。
- 状态图管"单个对象的演化"，顺序图管"多个对象的协作"，互为补充。
- 行为模型直接服务下游：状态图喂测试覆盖，顺序图喂接口设计。
