## 为什么从行为建模开始

场景与类模型画出了系统的"静态骨架"：有哪些参与者、哪些类、什么关系。但软件是**活的**——对象随时间改变状态，多个对象在同一时间点相互协作。**行为建模（behavioral modeling）**捕捉这个动态面，核心工具是**状态图（state diagram）**与**顺序图（sequence diagram）**：前者管"单个对象的状态演化"，后者管"多个对象间的消息时序"。

## 1 状态图：对象的生命周期

**状态图**描述一个对象在生命周期内经历的状态及其转换。四要素：

- **状态（state）**：对象满足某条件、等待某事件时的可区分情况，如「图书：在馆 / 借出 / 预约中 / 丢失」。
- **事件（event）**：触发状态转换的外部刺激，如「借出」事件。
- **转换（transition）**：在事件驱动下从状态 A 到状态 B 的迁移，常带守卫条件（guard）。
- **初始状态与终止状态**：实心圆起点与靶心终点。

一个典型的状态转换：**在馆 → 借出**，其中「读者借出」是事件，借出前后系统要执行的动作（登记、改库存）可以挂在转换上标注。<span class="marginnote">状态图的建模口诀：<strong>找状态变化，找触发事件，找守卫条件</strong>。最容易漏的是"隐藏状态"——比如「借出」状态下还有「逾期未还」这个子状态，它触发罚款动作。状态图建模越细，后面测试的"状态覆盖"越完整。</span>

**辨析｜易错点：** 状态与事件容易搞混。状态是**持续存在的条件**（"在馆"是一个持续状态），事件是**瞬间发生的刺激**（"点击借出"是瞬间动作）。"系统正在处理请求"是状态；"用户点击了提交"是事件。把事件当状态，状态图会画成一张混乱的步骤清单。

## 2 顺序图：对象间的消息时序

**顺序图**以**时间为纵轴**，画出一组对象及其生命周期线，对象间的**消息（message）**用带箭头的水平线表示，从上到下构成时序。<span class="marginnote">顺序图的生命线画成竖虚线，顶端是对象框；消息箭头按时间从上往下排。同步调用用实心箭头，异步消息用空心箭头，返回消息用虚线箭头。这些记号虽小，却表达了"谁在等谁"——异步设计里调用方不等结果继续做别的事，是并发与响应性设计的雏形。</span>

「借书」用例的顺序图大致是：

```text
读者     借阅界面    借阅控制器     图书      借阅记录
 │        │            │           │          │
 │──借书──→│            │           │          │
 │        │──校验读者──→│           │          │
 │        │            │──查询在馆─→│          │
 │        │            │←──在馆────│          │
 │        │            │──登记借出───────────→│
 │        │←──借出成功──│           │          │
 │←──显示──│            │           │          │
```

顺序图的价值在于**暴露协作逻辑**：谁能直接调谁、谁必须经过谁（依赖关系）、消息是同步还是异步、有没有循环与分支。它是"职责分配"的沙盘——控制器该不该替读者直接改库存？顺序图上一目了然。

## 3 两种图的协作分工

| 维度 | 状态图 | 顺序图 |
| --- | --- | --- |
| 关注点 | 单个对象的生命周期 | 多个对象的交互时序 |
| 表达 | 状态 + 事件 + 转换 | 对象 + 消息 + 时间 |
| 揭示 | 隐藏状态、非法转换 | 职责分配、依赖关系 |
| 测试价值 | 状态覆盖、转换覆盖 | 接口契约、时序错误 |

**辨析｜易错点：** 状态图与顺序图不是"二选一"，而是**互补视角**。对复杂状态的对象（订单、任务、连接）用状态图；对一次具体用例的协作过程用顺序图。真正容易犯的错误是**画错图的对象粒度**——状态图只对一个对象画，顺序图要画出参与用例的所有对象；把状态图画成"系统级"就会含糊不清。

## 4 行为模型如何服务下游

行为建模不是摆设，它直接喂养设计与测试：

**状态图 → 状态相关测试**：每个状态、每条转换、每个守卫条件都是一条测试用例的素材——「在馆状态下借出应成功，借出状态下再借出应被拒」。
**顺序图 → 接口设计**：消息即方法调用，顺序图里的每条消息都会变成接口方法，消息参数即方法签名。
**状态图 → 持久化设计**：需要区分状态的对象，通常在数据库里有一个"状态字段"——状态枚举的定义要回到状态图核对。<span class="marginnote">这与第 8 章《软件测试》的路径覆盖、第 4 章《面向对象设计》的职责分配构成一条完整链条：分析阶段的行为模型，就是设计阶段与测试阶段的行为基准。</span>

## 5 实战：为一笔订单画行为模型

把状态图与顺序图用在同一个真实对象上——**一笔电商订单**。它的行为模型长这样：

**状态图（对象的生命周期）**：`已创建` → `已支付` → `已发货` → `已送达`；分支点有 `已支付 → 已取消`（用户取消）、`已发货 → 退货中`（退货申请）；事件驱动状态迁移——`payment_confirmed` 触发 `已创建 → 已支付`，`goods_shipped` 触发 `已支付 → 已发货`。<span class="marginnote">状态图的要点是<strong>把"状态"与"动作"分开</strong>：状态是"对象处在什么位置"，动作是"进入状态时做什么"。比如订单进入"已发货"时发短信、进入"已取消"时释放库存——这些动作挂在<strong>迁移或进入</strong>上，而不是散落在业务代码里。这样"对象能到达哪些状态、哪些迁移合法"就一目了然，非法迁移（比如从"已送达"直接"取消"）在设计阶段就能被发现。</span>

**顺序图（一次用例的时序）**：`placeOrder()` 用例——客户端 → 订单服务 → 支付服务 → 库存服务 → 订单服务 → 客户端，画清每条消息的先后与返回。

两张图合起来回答两个不同的问题：**状态图答"对象一生能经历什么"（纵向、跨用例）**，**顺序图答"一个用例里谁和谁怎么协作"（横向、单场景）**。画完订单的这两张图，第 3 章的用例建模（第 3 章）就从"文字描述"变成了"可验证的行为规格"。

**辨析｜易错点：** 别把顺序图画成"流程图"。顺序图的主角是**对象与消息**，不是"if-else 分支"；一张顺序图应聚焦一个用例的正常路径与一个关键异常路径。把流程图逻辑塞进顺序图，图就失去"时序"的焦点。**记住分工：分支状态归状态图，协作时序归顺序图。**

## 6 术语速查与建模纪律

把两种图的关键术语与常见误区收进一张表：

| 术语/误区 | 一句话辨析 |
| --- | --- |
| 状态 | 对象的"位置"，由事件触发迁移 |
| 迁移 | 状态之间的合法转变，可挂动作 |
| 顺序图 | 一次用例中对象间的消息时序 |
| 生命线 | 顺序图中一个对象随时间的一条竖线 |
| 误区一 | 把状态图当流程图——状态图无"分支判断"逻辑 |
| 误区二 | 把顺序图当时序调度图——它不画条件分支 |
| 误区三 | 只画正常路径——异常/回滚路径才是设计重心 |

**辨析｜易错点：** 行为建模最常见的失败是"画得太满"。状态图把每个细节都画成状态（连"正在加载"都算），顺序图把所有分支都铺上去，图就失去沟通价值——它不再是"设计文档"，而成了"代码复述"。**好的行为模型只画"有设计决策"的地方**：状态图画出非法迁移与关键回滚，顺序图画出跨模块的协作时序。图的价值在于暴露设计问题，不在于覆盖所有细节。

**与第 3 章的联系：** 行为建模（第 3 章《基于场景的分析模型》之后）把用例的"文字故事"转成"可执行验证的行为规格"——状态图验证对象的合法生命周期，顺序图验证一次协作的时序。这两张图就是第 5 章 4+1 视图里"动态视图"的两个主角。

## 7 一个自查清单：画图前先想三件事

动手画状态图或顺序图之前，先过一遍这三问，能省下大量返工：

1. **"这个对象需要状态吗？"** 如果一个类从头到尾只有一个状态（比如纯计算工具类），画状态图是过度建模——状态图只对"生命周期有意义"的对象（订单、会话、任务）有价值。
2. **"这个用例的关键协作是哪几步？"** 顺序图只画"跨对象、有时序约束"的几步；纯属一个对象内部的方法调用链，画进顺序图是噪音。
3. **"异常与回滚画了吗？"** 如果一张图只有 happy path，它漏掉了建模最有价值的部分——系统在异常下的行为，恰恰是状态图与顺序图最该暴露的地方。

这三问的背后是一条总原则：**行为模型是"设计工具"，不是"文档装饰"。** 它存在的意义是让你在写代码前发现非法状态、漏掉的回滚、混乱的时序——而不是写完之后再给代码画一张复述图。带着这个判断标准去画图，每张图都会替你在设计阶段抓住几个 bug。

## 8 小结

- **状态图**描述单个对象的生命周期：状态、事件、转换、守卫条件、初始与终止状态。
- 状态是**持续条件**，事件是**瞬间刺激**，二者不可混淆。
- **顺序图**以时间纵轴表达对象间的消息时序，揭示职责分配与依赖。
- 状态图管"单个对象的演化"，顺序图管"多个对象的协作"，互为补充。
- 行为模型直接服务下游：状态图喂测试覆盖，顺序图喂接口设计。
