# 代码坏味道（Bad Smells）识别

## 为什么从坏味道开始

评审时你"觉得这段代码不舒服"，但说不清为什么——这就是**坏味道（code smell）**。坏味道不是错误（程序能跑），而是**设计问题的信号**——它预告着未来改动的困难。识别坏味道是重构的第一步：**先命名味道，才能决定怎么治**。这一节讲坏味道的分类与识别方法（呼应第 6 章"反模式"——坏味道是反模式的"症状"，反模式是坏味道的"病理"）。

## 1 坏味道的本质

**坏味道（bad smell / code smell）**：代码中**暗示更深层问题**的表面特征——不是 bug，而是"可能导致 bug 或阻碍修改"的征兆。

坏味道的三个特点：

- **可感知**：有经验的开发者一眼（或一闻）就能察觉。
- **非错误**：程序运行正常，坏味道不影响当前功能。
- **预警性**：坏味道指向未来——下次修改这里时，问题会爆发。

**辨析｜易错点：** 坏味道 ≠ bug。**bug 是"现在错"，坏味道是"将来会错或难改"**——一个坏味道可能永远不变成 bug，但它持续地提高修改成本（呼应第 9 章维护成本）。判断标准：**这段代码会让"下次改动"更困难吗？** 会，就是坏味道。好工程师不只看"现在对不对"，还看"将来好不好改"。

## 2 常用的坏味道清单（上）：代码级

Fowler 在《重构》里列了二十多种坏味道，按出现频率分几组：

**第一组：重复与长**
- **重复代码（Duplicated Code）**：同一逻辑出现在多处——改一处忘另一处是最经典的 bug 来源。
- **过长方法（Long Method）**：方法太长、逻辑太多——长的本质是"职责太多"，需要提炼。
- **过长参数列表（Long Parameter List）**：参数太多——数据应被封装成对象。
- **过大类（Large Class）**：类职责过多、字段太多——上帝类的雏形（第 6 章反模式）。

**第二组：依赖与耦合**
- **依恋情结（Feature Envy）**：一个方法过度使用**别的类**的数据——它更想住在别人家。
- **霰弹式修改（Shotgun Surgery）**：改一处需求要动 N 个类——变更被散弹打散（低内聚）。
- **平行继承体系（Parallel Inheritance Hierarchies）**：每给 A 加一个子类，B 也要加一个——耦合的继承树。

**第三组：判断与对象**
- **switch/if 过多（Switch Statements）**：大量 switch 按类型分派——该用多态（策略/状态模式）。
- **神秘命名（Mysterious Name）**：名字看不懂——命名是代码可读性的第一要素。
- **临时字段（Temporary Field）**：某字段只在特定情况下有意义——暗示对象被强行拼凑。

<span class="marginnote">坏味道识别的关键心态：<strong>看到坏味道不是"抓谁的错"，而是"发现代码在向你求助"</strong>。Fowler 用"味道"这个词非常精准——它不是"错误清单"（可以量化判定），而是"经验信号"（需要嗅觉判断）。识别坏味道的能力来自<strong>大量阅读好代码与坏代码的经验</strong>：读得越多，闻到异味的灵敏度越高。这也是代码评审（上一节）的隐藏价值——<strong>评审是练习坏味道嗅觉的最佳场所</strong>。</span>

## 3 坏味道的分组逻辑：它们指向什么

坏味道不是随机的，它们往往指向**更深的设计问题**：

| 坏味道组 | 指向的设计问题 | 对应的原则 |
| --- | --- | --- |
| 重复代码 | 抽象缺失 | DRY（不要重复自己） |
| 过长方法/过大类 | 职责过重 | 单一职责（SRP） |
| 依恋情结/霰弹式修改 | 内聚低、耦合高 | 高内聚低耦合 |
| switch 过多 | 类型分派僵化 | 多态（OCP） |
| 过长参数列表 | 数据未被封装 | 对象封装 |

**辨析｜易错点：** 坏味道是"症状"，背后的"病"是**违反设计原则**（第 4 章）。**治坏味道不能只消症状，要治到原则层面**——把重复代码去重而不抽出合适的抽象，只是换了个地方重复。判断标准：**重构后，设计原则（SRP、OCP、内聚耦合）是变好了，还是只是表面变干净了？** 治标不治本的重构，是"化粪池倒进游泳池"。

## 4 实战：一次"消灭坏味道"的改造

把坏味道的识别落到具体代码。看一段典型的"复制的味道"：

```
// 三个地方几乎相同的折扣计算
function discountVIP(price) { return price * 0.9; }
function discountMember(price) { return price * 0.95; }
function discountNew(price) { return price * 0.9; }
```

这里同时有**复制粘贴**（discountVIP 与 discountNew 一模一样）与**魔法数字**（0.9、0.95 含义不明）。改造：抽出一个 `discount(price, rate)`，用常量 `VIP_RATE = 0.9`、`MEMBER_RATE = 0.95` 取代裸数字；"新客同 VIP 折扣"则用一个配置 `{new: VIP_RATE}` 表达，而不是复制代码。改造后：**删除重复、数字有名字、策略可配置**——三个坏味道一次清掉。

**辨析｜易错点：** 坏味道的识别要警惕"误报"。一段只出现一次的重复不必抽（"三次原则"：至少重复三次才值得抽）；一个含义在上下文中很清楚的数字不必立刻改常量。**坏味道是"重构的信号"，不是"必须立即执行的判决"**——它的价值在于提示你"这里可能有设计问题"，最终由你对变更成本与收益的判断决定动不动手。这才是"坏味道"作为一个概念的精髓：它把"说不清的不适"变成"可讨论的清单"。

## 5 术语速查表

| 坏味道 | 一句话症状 | 常见对应重构 |
| --- | --- | --- |
| 复制粘贴 | 同段逻辑散落多处 | 提炼函数/提炼类 |
| 长函数 | 函数过长得一口气读不完 | 提炼函数、拆分 |
| 长参数列表 | 参数多到难以理解 | 引入参数对象 |
| 魔法数字 | 裸数字含义不明 | 用常量/枚举替换 |
| 特性嫉妒 | 一个方法频繁访问别的类的数据 | 搬移函数 |
| 霰弹式修改 | 改一处需求动 N 个文件 | 搬移函数到职责所在处 |

## 6 坏味道、重构与测试的关系

坏味道不是终点——它是指向重构的路标，而重构必须由测试保驾护航：

**坏味道（发现问题）→ 重构（第 14 章手法）→ 测试（保证改坏了立刻红）**。这条链解释了为什么三者在第 14 章被放在一起：坏味道告诉你"哪里该动"，重构教你"怎么动"，自动化测试（第 8 章）给你"动错的保险"。**没有测试的重构是走钢丝**——改完不知道有没有改坏，返工风险极高；而测试先行（TDD，第 8 章）让重构可以大步前进。

**辨析｜易错点：** 识别坏味道与"吹毛求疵"的边界在于**它是否影响变更成本**。一个不影响改动、纯粹个人偏好的写法不是坏味道；坏味道的特征是"**将来某次改动会因为它变贵**"——复制粘贴让一次修复要改 N 处、长函数让理解一处逻辑要读半天。判断时问一句：**"如果下个需求要动这里，我会不会因为它多花时间？"** 会——它是坏味道，值得处理；不会——放过它，别让重构瘾绑架了节奏。

## 7 小结

- **坏味道**是暗示设计问题的表面特征：不是 bug，而是"将来会难改"的预警。
- bug 是"现在错"，坏味道是"将来难改"——好工程师两者都看。
- 常用坏味道：**重复代码、过长方法、过长参数、过大类**（重复与长）；**依恋情结、霰弹式修改、平行继承**（依赖耦合）；**switch 过多、神秘命名、临时字段**（判断与对象）。
- 坏味道分组指向设计问题：重复→DRY、过长→SRP、依恋/霰弹→内聚耦合、switch→多态。
- 识别靠**经验嗅觉**，评审是练习嗅觉的最佳场所。
- **治坏味道要治到原则层面**——消症状不治本，等于换地方重复。

- 坏味道是"重构的信号"不是判决：识别它，再判断是否动手。
- 判断标准：下个需求要动这里时，会不会因为它多花时间？会——值得处理。
- 坏味道→重构→测试是闭环：没有测试安全网的重构是走钢丝。
- 常见坏味道速记：复制粘贴、长函数、长参数、魔法数字、特性嫉妒、霰弹式修改。
- 三次原则：同一逻辑重复三次才值得抽象，避免过度抽取。
- 坏味道是"代码在喊疼"：它自己不会报错，但会让下一次改动变贵。
- 识别练习：给复制粘贴、长函数、魔法数字各配一个"改造前→后"的例子，就掌握了判据。
