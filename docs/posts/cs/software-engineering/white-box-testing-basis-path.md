## 为什么从白盒测试开始

黑盒测试把软件当"黑箱"只看输入输出，**白盒测试（white-box testing）**则打开箱子、基于**内部逻辑结构**设计测试用例。它回答的问题很直接：**代码的每一条逻辑路径都被验证过了吗？** 这一节讲白盒测试的核心技术——**基本路径测试（basis path testing）**，以及它的三个关键数学概念：流图、圈复杂度、独立路径。

## 1 从代码到流图

白盒测试的第一步是把代码映射成**程序流图（flow graph）**：把每条语句抽象成节点，把控制转移（**顺序、分支、循环**）抽象成有向边。

```c
cin >> a >> b;
if (a > 1 && b < 0)
    x = a * b;      // 语句 1：真分支
else
    x = a - b;      // 语句 2：假分支
y = x + 1;          // 语句 3
```

对应流图：4 个节点，4 条有向边——节点2 分别指向节点3（真）与节点4（假）。

**辨析｜易错点：** 流图 ≠ 流程图。流程图画"业务步骤"（含处理框、输入输出框），流图只画**控制结构**（判定节点与边）——它是专门为"数路径"而生的抽象。把复合条件（`a > 1 && b < 0`）当作**单个判定节点**还是拆开，直接影响路径计数，这是画流图最常见的分歧点。

## 2 圈复杂度：路径的下界

**圈复杂度（cyclomatic complexity）**（McCabe 提出）度量程序的控制流复杂度，同时给出**独立路径数**——它回答了"至少需要多少条测试用例"。

计算公式（三种等价形式）：

$$
V(G) = E - N + 2
$$

$$
V(G) = P + 1
$$

$$
V(G) = \text{判定节点数} + 1
$$

其中 $E$ 是边数、$N$ 是节点数、$P$ 是判定节点数。

**公式解析**：对上述流图，$E = 4$，$N = 4$，于是 $V(G) = 4 - 4 + 2 = 2$；判定节点 $P = 1$，$V(G) = 1 + 1 = 2$。两种算法殊途同归。**独立路径（independent path）**是至少引入一条新边的路径，圈复杂度恰好等于独立路径数——所以至少需要 $V(G)$ 条测试用例才能覆盖全部独立路径。<span class="marginnote">圈复杂度的直觉：它数的是"程序里有多少个独立的分叉"。一个没有 $V(G)$ 的线性程序，$V(G) = 1$，一条路径走到底；每多一个判定，复杂度 +1，需要的测试用例 +1。这也是第 15 章《代码质量度量》的主角之一——圈复杂度 > 10 的模块通常被认为"该重构了"。</span>

## 3 基本路径测试的四步

**基本路径测试（basis path testing）**让测试者保证覆盖所有独立路径，四步走：

1. **画流图**：从代码或详细设计画出程序流图。
2. **算圈复杂度**：$V(G) = E - N + 2$，得到独立路径数与测试用例数的下界。
3. **导出独立路径**：列出所有基本路径（至少含一条新边）。
4. **设计用例**：为每条路径准备能走通它的输入数据。

**辨析｜易错点：** 基本路径覆盖 ≠ 全路径覆盖。独立路径的集合覆盖了"每条边至少被走一次"，但**独立路径的组合可能无限多**（循环迭代次数不同就是新路径）——基本路径测试在"覆盖率"与"可行性"之间取了工程平衡。**路径覆盖是白盒的极致理想，基本路径是可落地的近似**。

## 4 控制结构测试：深入分支与循环

基本路径之外，白盒还有针对**特定控制结构**的技术：

**条件测试（condition testing）**：把复合条件拆开，验证每个子条件为真/为假——抓"条件中运算符写错"。
**数据流测试（data flow testing）**：跟踪变量的"定义→使用"路径，检查"使用未定义变量""定义后未使用"等缺陷。
**循环测试（loop testing）**：针对循环结构——零次、一次、多次、最大次、最大次 ±1——覆盖循环边界。简单循环、嵌套循环、串接循环各有测试策略。<span class="marginnote">循环测试的边界设计非常实用：一个普通的 `for` 循环至少应测<strong>循环体从未执行、恰好执行一次、执行很多次、恰好在循环边界处停止、以及边界值加减 1</strong>——这五种情况覆盖了"循环边界条件"的绝大多数 bug。它与黑盒的边界值分析（下一节）是"内部边界"与"输入边界"的两个互补视角。</span>

## 5 小结

- **白盒测试**基于内部逻辑设计用例，回答"每条逻辑路径都被验证了吗"。
- **流图**把代码抽象成节点与边，专为数路径而生，不同于流程图。
- **圈复杂度** $V(G) = E - N + 2 = P + 1$，等于独立路径数，是测试用例数的下界。
- **基本路径测试**四步：画流图 → 算复杂度 → 导出独立路径 → 设计用例。
- 基本路径覆盖是"每条边至少一次"的工程近似，不是全路径覆盖。
- **控制结构测试**（条件、数据流、循环）深入分支与循环，抓特定结构缺陷。
