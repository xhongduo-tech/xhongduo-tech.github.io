# 持续集成（CI）：流水线与实践

## 为什么从持续集成开始

第 8 章讲集成测试时提到"持续集成（CI）是现代化集成文化"。这一节系统展开：**CI 是什么、流水线怎么搭、有哪些关键实践**。CI 是 DevOps 自动化的第一环——它让"每次代码提交"都被自动构建与验证，把"集成风险"从发布前提前到提交时。

## 1 持续集成：每天集成、每次提交验证

**持续集成（Continuous Integration, CI）**：**每次代码提交到主干，都自动触发构建与测试**，快速反馈"这次提交是否破坏了什么"。

它的核心理念：**集成不是结束时的"大爆炸"，而是持续的小步**——集成拖得越久，冲突与错误堆积越多（"集成地狱"）；集成越频繁，每次差异越小、问题越好定位。

**辨析｜易错点：** CI 不是"自动化测试工具"。工具（Jenkins、GitHub Actions、GitLab CI）是承载，CI 是**纪律**——**团队必须频繁提交（不要开大分支）、提交后立即关注 CI 结果（红了就修）**。买了工具不守纪律，CI 退化成"自动跑测试的服务器"，"集成地狱"依旧。

## 2 CI 流水线的典型阶段

一条 CI 流水线（pipeline）通常包含：

```
提交代码 → 检出 → 依赖安装 → 静态检查（lint）→ 单元测试 → 构建制品 → （可选）集成测试 → 报告
```

每个阶段都是**快速反馈的一环**：

- **静态检查**：秒级——语法、风格、明显问题（第 14 章静态分析）。
- **单元测试**：分钟级——功能正确性（第 8 章）。
- **构建**：验证"能打出制品"（第 12 章）。
- **集成测试**：验证模块协作（第 8 章）。

**辨析｜易错点：** CI 流水线的设计原则是"**快速反馈优先**"——**最早失败的阶段放最前面**，让开发者最快知道"坏在哪"。常见的反模式是"流水线跑 40 分钟最后才报错"——开发者提交后等半天才知道失败，反馈就失去了及时性。判断标准：**从提交到"知道坏没坏"要多长时间？** 越短越好（理想是几分钟内）。

## 3 CI 的关键实践

Martin Fowler 总结的 CI 实践清单（核心几条）：

1. **频繁提交到主干**：每天至少提交一次到主干，保持主干始终"可集成"。
2. **小步提交**：每次提交尽量小，便于定位问题。
3. **提交后立即构建**：CI 自动触发，无需人工。
4. **坏了就修**：CI 红了是"最高优先级"——不修就让主干继续长"坏代码"。
5. **测试是 CI 的守护**：没有自动化测试，CI 只能"构建"，不能"验证"。
6. **可视化状态**：CI 状态大屏/徽章，让全团队看见"现在绿不绿"。

<span class="marginnote">CI 的心理模型是"<strong>主干的健康是团队资产</strong>"：不健康的主干（红了不修、大分支堆积）会让所有人踩在坏地基上。所以 CI 的第一纪律是"红了就修、绿了才走"——<strong>宁可停下手头的新功能，也要先把 CI 修绿</strong>。这与第 8 章"错误聚集"、第 9 章"小步"一脉相承：<strong>质量问题的处理要即时，不能累积</strong>。</span>

## 4 CI 与分支策略的配合

CI 与第 12 章的 Git 工作流咬合：

- **提交到功能分支**：分支也跑 CI（验证"这个功能分支合进去安全吗"）。
- **PR 合并前**：CI 必须绿——**"测试不绿不合并"**是分支保护的基本规则。
- **合入主干**：主干 CI 再次验证——确保"合并后主干依然健康"。

**辨析｜易错点：** CI 最大的误区是"**只在主干跑 CI**"——功能分支不跑，合并时才发现问题，CI 的"早发现"价值就大打折扣。正确姿势：**每个 PR 都跑 CI（PR 检查），合入主干再跑一次（主干保护）**——两层闸门，把问题挡在合并前与合并后。判断标准：**一个 PR 在合并前，CI 是否已经告诉评审者"绿不绿"？** 没有，评审就在盲审。

## 5 小结

- **CI**：每次提交自动构建+测试，把集成从"收尾大爆炸"变成"持续小步"。
- CI 是**纪律**（频繁提交、红了就修），工具只是承载。
- 流水线阶段：**静态检查 → 单测 → 构建 → 集成测试**，快速反馈优先。
- CI 关键实践：**频繁小步提交、坏了就修、测试守护、状态可视化**。
- CI 与分支策略配合：**PR 跑 CI、主干保护、绿了才合**。
- 主干的健康是团队资产，红 CI 要即时修，不能累积。
