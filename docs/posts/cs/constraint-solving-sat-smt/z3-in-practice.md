## 为什么选 Z3 作为实战对象

前六篇把 SAT、CDCL、SMT、DPLL(T) 的理论讲完了。理论的终点是工具。在众多 SMT 求解器中，微软研究院的 **Z3**（2008 年起，de Moura 与 Bjørner 主导）是事实上的工业标准：它免费开源、支撑了微软 Azure 的验证基础设施，也被符号执行、程序验证、云配置等海量系统当作引擎。<span class="marginnote">Z3 的名字取自德国数学家恩斯特 · 策梅洛（Ernst Zermelo）的 Z 公理系统（Zermelo set theory），de Moura 借此致敬「公理化地建立严密推理」的精神。它最初服务于微软内部，2012 年后开源并成为 SMT-COMP 竞赛的常胜军。</span>

Z3 的核心是 **SMT-LIB 2.0** 语言：一种统一描述 SAT/SMT 问题的规范（Kroening & Strichman 第 13 章专门讲解）。学会 SMT-LIB，等于学会了「用 Z3 的语言提问」；而掌握 Z3 的 API（Python 的 `z3-solver` 最常用），就能把求解器嵌入自己的程序。

## 1 从 SMT-LIB 到 Python API

SMT-LIB 的语法干净直观。一个线性整数算术问题长这样：

```
(declare-const x Int)
(declare-const y Int)
(assert (and (<= (+ x y) 4) (>= x 1) (>= y 1)))
(check-sat)
(get-model)
```

`declare-const` 声明变量，`assert` 添加约束，`check-sat` 问是否可满足，`get-model` 取反例模型。Z3 会回答 `sat` 并给出一个赋值，或回答 `unsat`。<span class="marginnote">`check-sat` 在 SMT 语义下就是问「是否存在一个理论模型使所有断言为真」——SAT 的布尔可满足性被完整推广到理论层。Z3 还支持 `push`/`pop` 的断言栈，可做增量式求解，这是符号执行逐条路径查询的核心依赖。</span>

在 Python 中同样直接：

```python
from z3 import *
x, y = Ints('x y')
s = Solver()
s.add(x + y <= 4, x >= 1, y >= 1)
s.check()            # sat
s.model()            # [x = 1, y = 1]
```

Z3 的多语言绑定（Python、C、C++、Java、.NET、Rust）让它可以嵌入任何验证工具链。学会「声明变量—加断言—check-sat—读模型」这个四步循环，Z3 的大多数实战场景都覆盖了。

## 2 Z3 的引擎结构：不只一个求解器

Z3 之所以「高效」，是因为它内部是**一系列策略化组件**的组合，而非单一算法：

- **理论求解器**：EUF（并查集）、线性算术（扩展单纯形）、位向量（位展开 + 字级简化）、数组、浮点等，各司其职。
- **量词处理**：对带量词的一阶公式，Z3 用 **E-matching**（模式匹配式量词实例化）与 **MBQI**（Model-Based Quantifier Instantiation）逼近不可判定的一般情形。
- **策略与 tactic 框架**：Z3 把算法组织成可组合的 `tactic`，例如 `(then (simplify) (solve-eqs) (bit-blast) sat)` 这样的策略链，让用户按需拼接求解流程。

一个工程上极其重要的性质是**可证明性（proof generation）**：当 Z3 判定 `unsat` 时，它能输出一份形式化证明——这使 Z3 可以被嵌入更高层的验证框架（如 Dafny、F*），它们把 Z3 的结果当成可信算子的输入。<span class="marginnote">可证明性让 Z3 从「黑盒工具」升级为「可审计的推理器」：Dafny、Boogie、F*、Why3 这些验证框架都要求 Z3 输出证明或至少能被反复核对——这正是形式化方法（第三级专题）与本专题的接口。</span>

## 3 符号执行：把程序变成约束

Z3 最著名的应用之一，是充当**符号执行（symbolic execution）**的引擎。传统测试让程序跑在具体输入上，只能覆盖一条执行路径；符号执行让输入保持为**符号表达式**，把程序运行时每条分支条件累积成一个**路径约束（path condition）**，然后用 Z3 判定哪些具体输入能让某条路径可达。

以经典例子看：

```
y = x * 2
if y > 10:
    assert y < 100   # 这条断言会失败吗？
```

符号执行把 `x` 当作符号变量，走到 `if` 时路径约束是 $2x > 10$；Z3 判定它可满足并给出模型（如 $x=6$），于是这条分支被覆盖。对断言 $y<100$，符号执行问「是否存在 $x$ 使 $2x>10$ 且 $2x\ge100$」——Z3 判为可满足（如 $x=50$），说明断言确实可被击穿。<span class="marginnote">这正是 KLEE、angr、SymCC 等工具的核心循环：符号执行维护路径约束，每遇到分支就调用 Z3 判定「两边各自可不可满足」，把程序的所有行为空间压缩成一系列可求解的约束系统。</span>

## 4 公式解析：路径约束的增量维护

符号执行里对 Z3 的使用有一个性能关键点——**增量求解**。程序路径上每多一条分支，路径约束就多一个合取项：

$$
\pi_0 = \top,\qquad \pi_{k+1} = \pi_k \land c_k
$$

**逐步拆解**：第一步，路径一开始的约束为空真 $\top$。第二步，每遇到一个分支条件 $c_k$，路径约束扩展为 $\pi_k \land c_k$（走真分支）或 $\pi_k \land \neg c_k$（走假分支）。第三步，用 `push` 保存当前状态、`assert` 加入新约束、`check-sat` 判定是否还有具体输入——这利用了 Z3 的**增量 API**，避免每次从零重建求解状态。第四步，若 `unsat`，说明该路径不可能由任何具体输入触发，符号执行即剪掉这条分支。

增量求解把「每条路径一个完整求解任务」变成「沿路径逐步扩展同一个求解会话」，是符号执行能处理深路径的关键工程优化——它直接对应 Z3 API 里 `push`/`pop` 的设计。

## 5 用 Z3 求最优：MaxSMT 的实战入口

Z3 不仅能判断「可不可满足」，还能求「最优化解」——这就是第 9 篇 MaxSAT 在 SMT 世界里的对应物 **MaxSMT**。Z3 的 `Optimize` 类把「目标函数」直接纳入求解：

```python
from z3 import *
o = Optimize()
x, y = Ints('x y')
o.add(x + y <= 4, x >= 1, y >= 1)
o.maximize(x + y)        # 目标：最大化 x + y
o.check()
o.model()                # [x = 3, y = 1]  → 最优值 4
```

这个片段展示了 Z3 实战的第五种操作：`maximize`/`minimize` 声明目标，`Optimize` 迭代求解最优。它的内部原理是反复调用 `check-sat` 并在每次可满足后收紧目标边界，直到收敛——正是第 9 篇「二分搜索 + 增量」思想的工业实现。<span class="marginnote">`Optimize` 还支持 `soft` 约束与优先级：给软约束一个权值，Z3 会返回「在满足硬约束的前提下，让软约束加权违约最小」的解——这正是 Weighted MaxSAT 的语义。配置求解、资源分配类问题的「最优可行方案」，在 Z3 里往往一行 API 即可表达。</span>

理解这一层，Z3 就从「判断工具」升级为「优化引擎」——它不仅能验证「程序对不对」，还能帮你找到「满足约束下哪个方案最好」，这与第 11 篇的应用场景直接衔接。

## 6 Z3 在程序验证中的典型用法

| 场景 | 把什么交给 Z3 | Z3 回答什么 |
| --- | --- | --- |
| 断言检查 | 路径约束 ∧ 断言否定 | 反例 / 无反例 |
| 数组越界 | 下标不等式 | 越界实例 / 证明安全 |
| 循环不变式 | 归纳基座 + 归纳步 | 成立 / 反例 |
| 整数溢出检测 | 位向量算术 + 溢出条件 | 溢出触发输入 |
| 函数等价 | 两实现输出不相等条件 | 不等实例 / 等价 |

每一行都对应真实工程：微软的 **Boogie/Dafny** 把程序翻译成验证条件（verification condition）后交给 Z3；**F*、Why3** 用它做交互式证明的自动化助手。Z3 不只是一款软件，它是「把推理自动化」这个愿景的通用引擎——这也正是本专题前六篇全部理论的意义所在。

**一个实战提示**：实际使用 Z3 时，最常遇到的坑是把「证明不了」当成「命题为假」。`check-sat` 返回 `unknown`（例如遭遇不可判定片段或超时）时，Z3 没有给出结论，需要换策略、加超时、或改用可判定片段重试——把 `unknown` 和 `unsat` 混为一谈，是程序验证系统里最危险的错误来源之一。

## 7 小结

- **Z3** 是微软研究院的工业级开源 SMT 求解器，支撑 Azure 验证、符号执行、程序验证等海量系统。
- **SMT-LIB 2.0** 是统一的求解器交互语言；四步循环「声明—断言—check-sat—取模型」覆盖绝大多数实战。
- Z3 内部是**多理论求解器 + 量词处理 + tactic 策略链**的组合，而非单一算法。
- **符号执行**把程序路径编码为路径约束，用 Z3 判定路径可达性与断言安全性，是 KLEE/angr 的核心引擎。
- **可证明性**与**增量求解**（push/pop）让 Z3 能被可信地嵌入更上层的验证框架。

在下一节，我们将视角从「以 SAT/SMT 为中心」转向「以约束为中心」的另一大传统——约束规划（CP）。全局约束、传播器如何与 SAT/SMT 互相融合，是两个求解范式的世纪之遇。
