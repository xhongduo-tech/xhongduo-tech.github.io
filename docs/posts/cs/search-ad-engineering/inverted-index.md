## 为什么从倒排索引开始

上一课我们站在一万米高空看了整条流水线，这一课落地到它的枢纽：**倒排索引（inverted index）**。它是搜索引擎最核心的数据结构，也是把「离线把活干完」这条哲学变成现实的地方。<span class="marginnote">Manning 教材第1章第一节就用一个电影数据库的例子带出倒排索引，第2章紧接着讲词典与倒排表的全部细节。本章就是这两章（再加上第4、5章的构建与压缩）的一次合并深潜。</span>如果你只从本专题带走一个数据结构，那就是它——因为在第三级《数据结构》里你学过的树、哈希、跳表，在这里全都变成了它的零件。理解倒排索引，你才能真正理解「检索为什么这么快」。

## 1 从文档到倒排表的翻转

想象你手上有 10 部小说的全文，想知道「孤独」这个词出现在哪些书里、各出现几次。最笨的办法是逐本翻开找，这就是**正向索引（forward index）**——每个文档一行，列它包含的词。但查询要的是反方向：给定词，找文档。于是我们把方向翻转：

**倒排索引 = 词典（dictionary / vocabulary）+ 倒排表（postings list）。** 词典收录语料里出现过的所有词项；每个词项挂一条倒排表，表里按升序记录它出现在哪些文档（docID），以及可选的位置与词频。<span class="marginnote">「倒排」是相对正排而言的。正排「文档→词」用于文档存储与展示，倒排「词→文档」用于查询。Manning 第1章用 term-document matrix 来讲解这个翻转：把矩阵按行存就是正排，按列存就是倒排。</span>

举一个教科书式的最小例子。三篇文档：

- $d_1$：The quick brown fox
- $d_2$：The quick red fox
- $d_3$：Brown fox jumps

经过分词与词干化，得到词典 `brown, fox, jumps, quick, red, the`，倒排表为：`brown → [1,3]`、`fox → [1,2,3]`、`jumps → [3]`、`quick → [1,2]`、`red → [2]`、`the → [1,2]`。查询 `quick AND fox` 只需分别取 `quick` 与 `fox` 两条倒排表求交，得 $[1,2]$，全程没有翻过任何一篇文档全文。<span class="marginnote">这就是「离线多干活、在线少干活」的第一次落地：倒排表的构建成本在建立索引时一次性支付，查询时只做「查表 + 求交」，与文档总数几乎无关，只与命中的候选规模有关。</span>

这个最小例子藏着两件值得记住的事。其一，**词典本身必须是可快速定位的数据结构**——教科书给出哈希表与字典树两种主流实现，前者查询 $O(1)$、后者支持前缀匹配；第三级《数据结构》里的知识第一次在「工业级数据结构」里有了归属。其二，**倒排表有序性（docID 升序）是后面所有优化（跳表、gap 压缩、求交）的前提**——没有有序，压缩与加速都无从谈起。顺序，是索引里最便宜的免费午餐。

## 2 词典：压缩前的词汇学

倒排表是骨架，词典是灵魂。语料的词项分布服从一个被反复验证的经验定律——**Zipf 定律**：把词按频次从高到低排序，第 $r$ 高频的词，其出现频次约正比于 $1/r$。<span class="marginnote">Zipf 定律意味着「少数高频词占大头，海量低频词占长尾」。英语语料里，最常用的几百个词就覆盖了相当比例的 token 出现次数；而词典里却有几十万个只出现一次的词。</span>这个分布直接决定了词典该长什么样：**高频词让 stop word 策略有价值，长尾词让压缩必不可少。**

在把词典写进磁盘之前，还要完成一组**词汇学决定**，Manning 第2章花了大量篇幅：

| 处理 | 干什么 | 例子 |
| --- | --- | --- |
| 标记化（tokenization） | 把字符流切成词 | "New York" 是 1 个词还是 2 个？ |
| 停用词（stop words） | 丢弃无区分力的高频词 | the、a、的、了 |
| 归一化（normalization） | 把等价写法归并 | USA / U.S.A / usa |
| 词干化（stemming） | 把词形变化归并 | running / runs → run |

**辨析｜易错点：** 停用词表不是越大越好。删掉太多词会破坏短语查询与位置信息（比如 "The Who" 乐队名）。现代引擎更倾向保留所有词，而把「不重要的词」交给打分模型去压低权重——**从「物理删除」走向「软降权」**，这个思路在后面 LTR 里会再次出现。

中文的词汇学决定与英文不同：中文没有空格分词，`北京`、`高铁` 需要**中文分词器**先用词典或统计模型切出词边界；「北京/高铁/时刻」还是「北/京/高铁」直接决定倒排表的形态。分词的好坏在中文搜索里就是检索质量的天花板，这也是第4课《查询理解与改写》会把分词列为第一项的原因。

## 3 跳表：让求交快一个数量级

查询 `AND` 求交要同时遍历两条倒排表。朴素的线性合并是 $O(|A|+|B|)$，但对高频词而言，$|A|$、$|B|$ 可能有百万级，而真正相交的部分可能只有几十。Manning 第2.3节给出的加速结构是**跳表指针（skip pointers）**。

**跳表的基本思想：在倒排表里每隔若干项存一个「跳跃指针」，指向更远处的表项。** 求交时若指针指向的 docID 仍小于另一条表的当前项，就直接跳到指针处，跳过中间一大段。<span class="marginnote">跳表与第三级《数据结构》里的跳表（skip list）同名不同物：倒排表跳表是「跳跃步长固定的有序数组加速」，后者是「随机多层链表」。别混为一谈。</span>步长 $b$ 的选取是个经典权衡：跳得太疏省空间但跳不动，跳得太密则加速有限，教科书给出经验上 $b \approx \sqrt{|P|}$ 量级为宜。

用一个数字感受跳表的价值。假设 `北京` 的倒排表有 2 亿项、`高铁` 有 2000 万项，两表真正相交约 30 万项。线性合并至少要扫 2 亿次比较；若在 `北京` 的表上每隔约 4471 项（$\sqrt{2\times 10^7}$ 量级）放一个跳指针，大部分「不可能相交」的区间可以整段跳过，实际扫描量能压到几百万量级——快一到两个数量级。这就是「为有序数据建索引」的杠杆。

求交还可以按**启发式排序**再做一层优化：总是先用最短的倒排表开始，即所谓的 `smallest-first` 策略。先求两条最短的表，再用结果与更长的表相交，能让中间候选规模始终被压到最小——这是「先选最小集合」这条算法直觉在信息检索里的教科书应用。

## 4 位置信息与短语查询

倒排表只存 docID 时，可以回答「哪些文档含词」；但用户会搜短语，如「北京 大学」。若 `北京` 与 `大学` 都出现但不在相邻位置，就不该算命中。解决办法是给倒排表再加一层：**位置信息（positional postings）**——每条记录存「文档内第几个位置出现」。
<span class="marginnote">Manning 第2.4节给出了 position + docID 的三种方案对比：biword（把相邻词对当新词）、positional index（记录每个词的位置）、以及两者混合。位置信息让索引体积显著变大，于是又回到压缩的话题。</span>

有了位置信息，短语查询 `"北京 大学"` 的求交就从「看是否同文档」升级为「看 docID 相同且位置差为 1」。求交时维护一个位置游标滑动匹配，最坏情况 $O(|A|+|B|)$ 即可完成——这正是教科书常用来展示「数据结构决定查询复杂度」的经典案例。

位置信息的另一大用途是**邻近查询（proximity search）**：要求两个词出现在相距 5 个词以内的同一句子。搜索引擎对这类「软短语」需求（如搜索「姚明 妻子」）通常不是硬过滤，而是作为打分信号的一部分——相关度模型（下一课）会把「词间距」这种精细结构折算成分数，而不是粗暴地一刀切。

## 5 索引构建：BSBI 与 SPIMI

语料是千万级文档时，内存装不下整个词典加倒排表。Manning 第4章给出两条经典路线：

**BSBI（Blocked Sort-Based Indexing，分块排序索引）**：把文档分成若干块，每块在内存里建倒排、排序、写盘，最后把各块的倒排表按词合并。代价是每一轮都要对块内词项排序，排序开销随块数增长。<span class="marginnote">BSBI 名字里的关键词是「排序」：它先让每个块内部的倒排表有序，块与块之间的合并就退化成有序归并——这正是你在第三级《数据结构》与《算法》里学过的归并排序在多机数据上的复刻。</span>

**SPIMI（Single-Pass In-Memory Indexing，单遍内存索引）**：内存里每遇到一个新词就分配一条倒排表并**当场按出现顺序追加**，不再预先排序；写完盘后只做「词典合并 + 倒排表拼接」。因为跳过了全局排序，SPIMI 比 BSBI 更快，也更能处理词典无法整体装入内存的情形。<span class="marginnote">SPIMI 是现代 MapReduce 式倒排构建（如分布式建索引）的直接前身：每个 reducer 处理一组词的倒排表片段，最后归并。你在第三级《分布式系统》里学的分治思想，在这里有了最具体的形态。</span>

## 6 公式解析：变量字节编码的压缩

倒排表在磁盘上如何压缩？教科书给出的经典方案是**基于文档间隔（gap）的变量字节编码（variable byte encoding，VarByte）**。先看间隔：docID 有序，相邻两篇文档的差往往很小——

$$
\text{gap}_i = \text{docID}_i - \text{docID}_{i-1}, \qquad \text{docID}_0 = 0
$$

逐项拆解这一步的本质：

- **第一步，为什么用间隔**：有序 docID 的原始值动辄 $10^9$，但相邻间隔平均可能只有个位数。把大整数换成小整数，是压掉冗余的第一层。
- **第二步，变量字节**：固定 4 字节存一个 int 对短间隔是浪费。VarByte 每个字节只用 7 位存数据、最高位做「是否续字节」的标记，于是 `5` 只需 1 字节，而 `300` 需要 2 字节。
- **第三步，效果量级**：对真实语料，用间隔 + VarByte，倒排表体积通常可压到原码长的一半以下；再叠加文档频次（df）的倒排表本身已按长度排序——**高频词的倒排表短（因 stop word），长倒排表都是低频长尾，压缩对它们收益最大。**

词典本身的压缩是另一套功夫：**前端编码（front coding）**把「同前缀」的词合并存储（如 `automata, automate, automatic` 共享 `automat`），或把整部词典做成**字典树（trie）**。Manning 第5章对这三者（gap、VarByte、front coding）各有详细数据，是「以空间换时间」的完整教材。

## 7 索引更新：动态倒排与分段合并

真实搜索引擎的索引不是建一次就完事，而是**持续更新**：新页面被抓取、旧页面被删除。教科书与工业界给出了「静态索引」到「动态索引」的演进：

- **最简单：重建**。小语料可行，大语料不可行——重建一次可能要数小时。
- **改良：辅助倒排（auxiliary index）**。新文档写入内存里的小倒排表，查询时同时查主索引与辅助索引再合并；辅助表大到阈值就并入主索引。
- **工业界主流：分段合并（segmented / log-structured）**。索引由多个段（segment）组成，段内不可变，新数据只写新段；后台定期用**归并（merge）**把若干小段合成大段。读放大（一个查询要查多个段）由合并策略压住，写路径则永远是「顺序追加」。<span class="marginnote">这套「写新段 + 后台合并」的结构，与你在第三级《数据库》里见到的 LSM-Tree 如出一辙。搜索引擎的索引就是数据库的表的远亲——理解其中一个，另一个立刻上手。</span>

删除与更新再叠加一层复杂度：段不可变意味着删除要用**墓碑（tombstone）**标记，真正的清理留到合并时。这些细节提醒我们：索引不只是数据结构，更是一套**存储系统的设计**。

段多了以后，「一个查询要查几个段」就成了新的开销来源。工业界的对策是**段合并策略的调优**（如分层合并、按大小合并），以及把「经常一起被查的段」放在同一台机器上以摊薄网络开销。另一个工程细节是**段级别的统计元数据**：每个段单独维护词典与统计量，查询时先在各段分别检索、再合并结果——这相当于把「单机倒排索引」放大成了「分布式倒排索引」，也是第6课向量索引、第11课广告系统工程都会复用的分片思想。

## 8 小结

- **倒排索引 = 词典 + 倒排表**，是「词→文档」的翻转映射，让查询复杂度与文档总数解耦。
- 词项分布服从 **Zipf 定律**：少数高频词占大头、海量低频词占长尾，直接决定 stop word 与压缩策略。
- **跳表指针 + smallest-first 求交**把 AND 查询从线性合并加速到接近「只扫相交部分」。
- 短语查询靠**位置信息**，位置信息推高体积，于是回到压缩。
- 构建用 **SPIMI/BSBI**，更新用**辅助索引 / 分段合并**；离线完成得越彻底，在线查询越快。
- 词典用**前端编码、字典树**，倒排表用 **gap + 变量字节编码**压缩，整体可瘦身一半以上。
- 一段顺口的复盘：**有序 → 可跳表 → 可压缩 → 可求交**，四个词串起了本课全部内容；下一课你会看到，倒排表里还能顺便存下 tf、df 这类打分要用的统计量。
- 倒排索引既是数据结构，也是存储系统：词典、倒排表、位置表、元数据各司其职，压缩与分段合并让它能扛住 Web 规模。

在下一节，我们将回答一个更本质的问题：**候选集拿到了，凭什么给这篇文档打高分？**——从布尔模型、向量空间模型到 BM25，进入检索模型的世界。
