## 为什么从例行工作排程开始

数据库每天凌晨要备份、日志每周要归档、证书每月要检查到期——这些「到了点就该干」的事，不该靠人记，而该交给系统的**排程（scheduling）**机制。Linux 给出两个工具：**`at`** 处理「一次性、未来某个时刻」的任务，**`crontab`** 处理「周期性、反复发生」的任务。crontab 是每台服务器上「自动化」的起点：几乎每个生产系统都挂着一堆 cron 任务，而 `cron` 的五个时间字段，也是理解排程语法的一把万能钥匙——连 Kubernetes 的 CronJob 用的都是同一套字段。<span class="marginnote">排程思想不只属于 Linux：Kubernetes 的 CronJob、GitHub Actions 的 schedule、数据库的定时任务，字段格式与「分 时 日 月 周」大同小异。学会 cron 五字段，等于学会了整个生态的排程语言。</span>

## 1 一次性任务：at

**`at`** 让任务在指定的未来时间执行一次，之后不再出现。基本用法：

```bash
at now + 5 minutes          # 5 分钟后执行（然后输入命令，ctrl-d 结束）
at 14:30                    # 今天 14:30
at 23:00 08/20/2026         # 指定日期
atq                         # 列出待执行的任务队列
atrm 3                      # 删除编号为 3 的待执行任务
```

`at` 的守护进程 `atd` 每分钟检查一次任务队列。任务执行时的工作目录、环境变量由创建时的快照决定。<span class="marginnote">`at` 适合「晚点提醒」「错峰执行」这类一次性场景。交互输入命令后必须 `Ctrl-D` 结束输入，`atq` 可随时查看排队中的任务。</span>

**易错点**：`at` 任务执行时的输出默认会**以邮件形式发给用户**——很多服务器没配邮件服务，输出就悄悄丢了。想让结果可见，在任务里重定向到文件：`echo "备份完成" > /tmp/at-result.log`。<span class="marginnote">「未来某个时刻」用自然语言就能描述：`at noon`、`at teatime`（16:00）、`at now + 2 hours`。这是 at 相比 cron 语法最友好的一点。</span>

## 2 周期任务：crontab

**`crontab`** 是「cron table」——一张周期性任务表。每个用户一份，用 `crontab -e` 编辑、`crontab -l` 查看、`crontab -r` 清空：

```bash
crontab -e            # 编辑当前用户的 crontab（默认 vim）
crontab -l            # 列出当前用户的全部任务
crontab -r            # 删除当前用户全部任务
```

每一行一个任务，格式是：

```
分  时  日  月  周    命令
```

**公式解析：cron 的五个时间字段**

$$
\underbrace{\min}_{0{-}59} \quad \underbrace{\text{hour}}_{0{-}23} \quad \underbrace{\text{day-of-month}}_{1{-}31} \quad \underbrace{\text{month}}_{1{-}12} \quad \underbrace{\text{day-of-week}}_{0{-}7}
$$

拆解这条公式：

- **第一步，看分钟**：`min` 取值范围 0–59，决定「每小时的哪一分钟」执行。`0` 表示整点。
- **第二步，看小时**：`hour` 取 0–23；`*` 表示「任意值」，于是 `0 * * * *` 表示**每小时的第 0 分钟**执行一次。
- **第三步，看日期**：`day-of-month` 取 1–31、`month` 取 1–12；`0 2 1 * *` 表示每月 1 号凌晨 2 点执行。
- **第四步，看星期**：`day-of-week` 取 0–7，0 与 7 都表示周日；**当「日」与「星期」同时被指定时是「或」的关系**——`30 3 15 * 1` 会在每月 15 号以及每个周一都执行，而不是「且」。

典型的行：

| crontab 行 | 含义 |
| --- | --- |
| `0 2 * * *` | 每天凌晨 2 点整 |
| `*/10 * * * *` | 每 10 分钟一次（`*/n` = 每 n 个单位） |
| `30 3 * * 1` | 每周一凌晨 3:30 |
| `0 0 1 * *` | 每月 1 号零点 |
| `@daily` | 等价于 `0 0 * * *`（每天零点） |

特殊语法还有三种常用缩写：

| 写法 | 含义 |
| --- | --- |
| `1-5` | 范围：1 到 5（如小时字段 `9-18` = 早 9 点到晚 6 点每个整点） |
| `1,15` | 枚举：只在这些值执行（如 `0 2 1,15 * *` = 每月 1 号与 15 号凌晨 2 点） |
| `@reboot` | 每次开机时执行一次 |

**重点**：`@reboot` 与普通时间字段任务不同——它不依赖分时日月周，而是在系统启动完成后触发一次，常用于「开机把必要环境准备好」，如挂载检查、同步时钟。

**易错点**：cron 的星期字段里 0 与 7 都是周日，1–6 才是周一到周六。把备份安排在周日写成 `0 3 * * 7` 与 `0 3 * * 0` 都对，但写成 `0 3 * * 1` 就成了周一——星期与直觉相反是排程事故的高发点。

## 3 at 与 crontab：什么时候用哪个

**核心对比表：at 与 crontab**

| 维度 | at | crontab |
| --- | --- | --- |
| 场景 | 一次性、未来某个时刻 | 周期性、反复发生 |
| 语法 | 自然时间描述 | 五字段排程 |
| 守护进程 | atd | cron / crond |
| 队列查看 | atq | crontab -l |
| 删除 | atrm 编号 | crontab -e 删行 或 -r |

选型一句话：**今天 14:00 要跑一次迁移，用 `at`；每晚备份、每周清理，用 crontab。**

## 4 排错：任务到底跑没跑

三个问题，三条命令：

```bash
crontab -l                        # 1. 任务真的写进去了吗
systemctl status cron             # 2. cron 服务在跑吗（Debian 系叫 cron，RHEL 系叫 crond）
grep CRON /var/log/syslog         # 3. 有没有执行记录（RHEL 系看 /var/log/cron）
```

**易错点**：crontab 里的环境与登录 shell 完全不同——`PATH` 默认很窄，脚本里调用的 `mysql`、`python3` 等命令要写**绝对路径**，或在脚本开头 `export PATH=...`。<span class="marginnote">脚本输出默认以邮件发给用户，没配邮件服务时就悄悄丢了。所以 cron 任务里几乎总是写成 `command >> /var/log/xxx.log 2>&1`——把输出落盘、错误也一并记下，日志文件才是任务真正的「答卷」。</span>

## 5 小结

- **at 一次性、crontab 周期性**：一次任务用 `at`，反复任务用 `crontab`。
- **cron 五字段**：分 时 日 月 周；`*` 任意、`*/n` 每 n 个、「日」与「周」同时给是「或」。
- **crontab 三命令**：`-e` 编辑、`-l` 查看、`-r` 清空；每个用户各一份。
- **环境陷阱**：cron 的 PATH 很窄，命令写绝对路径；输出重定向到文件而不是依赖邮件。
- **排错三板斧**：`crontab -l`、服务状态、`/var/log/cron`（或 syslog）。
