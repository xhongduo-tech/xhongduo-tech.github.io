## 为什么从进程与信号开始

到目前为止我们看到的都是「命令」——但它们敲下去之后发生了什么？每条命令其实都触发了一个**进程（process）**：程序被加载进内存、分配 PID、占用 CPU 与内存、最后退出。而「程序好好的却卡住」「服务挂了但不知道是谁杀的」这类排障，全靠进程观测与**信号**机制。本章先学会看（`ps`、`top`），再学会控制（`kill` 与各种信号），最后掌握把任务放后台跑的三种姿势（`&`、`bg`、`nohup`）——它们是写守护脚本与理解 systemd 的前置知识。

## 1 进程：程序的运行态

**进程（process）** 是正在执行的程序实例，每个进程有一个全局唯一的 **PID（Process ID）**。Linux 进程树从 PID 1 的 `systemd`（或 `init`）开始，父进程 fork 出子进程，形成一棵树。<span class="marginnote">每个进程还有一个 <strong>PPID</strong>（父进程 PID）——`ps -o pid,ppid,cmd` 能看清父子关系。父进程先退出而子进程还没退出时，子进程会被过继给 PID 1，成为「孤儿进程」，由 systemd 负责收尸。</span>

**进程状态**是观测的关键，`ps` 输出的 `STAT` 列常见：

| 状态码 | 含义 |
| --- | --- |
| `R` | Running，正在运行或可运行 |
| `S` | Sleeping，可中断睡眠（等 I/O 或事件） |
| `D` | 不可中断睡眠（通常卡在磁盘 I/O） |
| `Z` | Zombie，僵尸进程（已结束但父进程没回收） |
| `T` | 停止（被信号暂停） |

**易错点**：僵尸进程（Z）不占 CPU，但占着 PID 表项。少量 Z 是正常现象；大量堆积说明父进程没调用 `wait` 回收——通常重启那个父进程即可清空。

## 2 观测进程：ps 与 top

**`ps`**（process status）是「拍快照」：某一时刻的进程列表。裸 `ps` 只显示当前终端自己的进程，常用的完整形态：

```bash
ps aux                 # 所有用户的所有进程（BSD 风格）
ps -ef                 # 全格式（System V 风格）
ps aux --sort=-%mem    # 按内存占用从大到小排
ps -eo pid,ppid,cmd    # 自定义列
```

`ps aux` 输出里 `USER PID %CPU %MEM VSZ RSS TTY STAT START TIME COMMAND`——`%CPU` 是瞬时占用，`RSS` 是物理内存（KB），`COMMAND` 是命令行。<span class="marginnote">`ps` 与 `top` 的差别：ps 是快照、top 是动态刷新。找「现在有谁在跑」用 ps，盯「谁在吃 CPU/内存」用 top。`ps -p PID` 精确查一个进程。</span>

**`top`** 每几秒刷新一次，实时展示 CPU、内存与各进程排行。最常用的交互按键：`P` 按 CPU 排序、`M` 按内存排序、`k` 杀进程、`q` 退出。现代 Linux 常装 `htop`——彩色、可滚动、可树状，是 top 的友好替代。

**找进程的两个快捷键**：`pgrep` 按名字反查 PID，`pstree` 以树状展示父子关系：

```bash
pgrep -l nginx           # 列出名字含 nginx 的 PID 与名字
pgrep -f "uwsgi.*8080"   # 按完整命令行匹配
pstree -p                # 进程树 + PID，一眼看清父子
```

`pgrep -f` 尤其好用：你记得命令行里有 `8080` 却不知道进程名时，它能按完整命令行捞出来。配 `kill $(pgrep nginx)` 可以「按名字杀」，等价于 `pkill nginx`。

## 3 公式解析：kill 与信号

**信号（signal）** 是内核发给进程的异步通知，`kill` 命令正是「发信号」的工具——名字叫 kill，但它的大多数用法**不是杀死进程**，而是通知进程「发生了某件事」。常用信号：

| 信号 | 编号 | 默认行为 | 用途 |
| --- | --- | --- | --- |
| `HUP` | 1 | 终止 | 让守护进程重读配置 |
| `INT` | 2 | 终止 | 等价 Ctrl-C |
| `KILL` | 9 | 强制终止 | 不可捕获、不可忽略 |
| `TERM` | 15 | 终止 | 优雅退出，默认信号 |
| `CONT` | 18 | 继续 | 恢复暂停的进程 |

**信号处理的两步模型**：

$$
\text{发送：} \;\; kill -15 \text{ PID} \;\longrightarrow\; \text{进程收到 TERM} \;\longrightarrow\; \text{自行清理并退出}
$$

$$
\text{兜底：} \;\; kill -9 \text{ PID} \;\longrightarrow\; \text{内核直接回收，无任何清理}
$$

拆解这条链路：

- **第一步**：`kill -TERM PID`（`-15` 可省略）是**默认信号**，进程收到后有机会保存状态、关闭文件后自行退出。
- **第二步**：进程若挂死或忽略 TERM，`kill -9 PID` 由内核强制回收——**不可捕获、不可忽略**，但也不给任何清理机会。
- **第三步**：原则是先 15 后 9：先给优雅机会，等几秒没反应再强制。

**易错点**：`kill -9` 不是第一选择。数据库、服务类进程被 `-9` 强杀可能丢数据或留下脏状态。先 `kill PID`（TERM），不行再 `kill -9 PID`。`kill -l` 列出全部信号名。<span class="marginnote">`killall 进程名` 按名字杀所有匹配进程，`pkill -f 模式` 按完整命令行匹配。这些「批量」工具比逐个敲 PID 高效，但也更容易误伤——`pkill -f` 尤其要确认模式写对了，否则可能连自己的命令都杀了。</span>

## 4 前台与后台：& 与 jobs

终端里运行的命令默认占用**前台**：它没跑完你就干不了别的。把任务丢到**后台**，有三种典型姿势：

```bash
long_task &              # 后台运行，立即回到提示符
jobs                     # 查看当前会话的后台作业
fg %1                    # 把作业 1 调回前台
bg %1                    # 让暂停的作业 1 在后台继续跑
```

**核心对比表：三种「后台」的差别**

| 方式 | 与终端的关联 | 注销后 | 适用 |
| --- | --- | --- | --- |
| `cmd &` | 仍读终端、输出到终端 | 会被 SIGHUP 终止 | 短期任务 |
| `bg` / `fg` | 同一会话内调度 | 同上 | 临时切换前后台 |
| `nohup cmd &` | 忽略 HUP、输出进文件 | **继续运行** | 长期任务 |

**易错点**：`cmd &` 之后直接关终端，进程会收到 SIGHUP 信号而死。想要**关掉终端后任务继续**，用 `nohup cmd &`（或把它交给 systemd）。`nohup` 默认把输出写到 `nohup.out`。<span class="marginnote">`nohup` 是「no hangup」——它让进程忽略 SIGHUP。更现代的选择是 `setsid`（脱离会话）或直接交给 systemd 管理。`Ctrl-Z` 暂停前台进程后，`bg` 可让它到后台继续，`fg` 再调回来。</span>

## 5 小结

- **进程是运行中的程序**：PID 唯一标识、PPID 指认父进程、状态列 `R/S/D/Z/T` 是诊断入口。
- **ps 是快照、top 是动态**：`ps aux --sort=-%mem` 找占用大户，`htop` 是更友好的 top。
- **kill 是发信号**：默认 `-15`（TERM）优雅退出，`-9`（KILL）强杀兜底——先 15 后 9。
- **后台三姿势**：`cmd &` 会话内后台、`bg/fg` 前后台切换、`nohup cmd &` 注销后仍跑。
- **僵尸进程不可怕**：少量 Z 正常，大量堆积重启父进程即可。
