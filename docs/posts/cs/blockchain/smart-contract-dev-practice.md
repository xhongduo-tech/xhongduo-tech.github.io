## 为什么从开发实践开始

语法是语言，实践是纪律。智能合约的开发流程与 Web 开发有本质差别：**部署不可回滚、执行要付钱、测试是安全生命线**。这一节走通一条最小而完整的开发链路——环境搭建、编写、测试、部署、交互——并强调那些「普通开发习惯里致命」的反模式。学完本节，你就能亲手部署自己的第一个合约。

## 1 开发环境与工具链

主流工具链（2026 年）：

| 工具 | 用途 | 说明 |
| --- | --- | --- |
| **Hardhat** | 开发框架 | 内置本地节点、编译、脚本，主流选择 |
| **Foundry** | 开发框架 | Rust 编写，极快，`forge` 测试/部署一体 |
| **Remix** | 在线 IDE | 浏览器即用，适合教学与原型 |
| **MetaMask** | 钱包 | 管理私钥、签名交易、连接 DApp |
| **Ethers.js / viem** | 客户端库 | 与节点交互、构造/签名/发送交易 |
| **Sepolia** | 测试网 | 免费测试币，模拟主网环境 |

**最小开发流程**：`npx hardhat init` 创建项目 → 编写合约 → `npx hardhat test` 跑测试 → 部署脚本 → `npx hardhat run scripts/deploy.js --network sepolia`。

## 2 从测试网到主网

**为什么先上测试网？** 主网部署即不可变、且花钱；测试网（Sepolia）让你在近乎真实的环境里验证合约行为，成本为零。<span class="marginnote">「部署不可回滚」意味着一次合约 bug 可能直接损失真金白银：2020 年以来 DeFi 被黑损失累计超百亿美元。测试网的意义不是走流程，而是把「便宜的失败」集中在部署前。</span>

**部署的本质**：部署 = 发出一笔 `to` 为空地址、`data` 为合约字节码的交易。交易被打包后，新合约地址由「发件人地址 + nonce」确定性推导：

$$
\text{contract\_address} = \text{keccak256}(\text{RLP}(sender, nonce))[12:]
$$

**公式解析：部署地址如何推导**

- **第一步**：`sender` 是部署者地址，`nonce` 是部署者账户的当前 nonce。
- **第二步**：两者做 RLP 编码后取 Keccak-256 哈希。
- **第三步**：取哈希的后 20 字节作为合约地址。同一个部署者、同一个 nonce 只会得到唯一地址——**地址可预测**（CREATE 操作码）。`CREATE2` 操作码则允许自定义 salt 预计算地址，用于「确定性部署」。

## 3 测试：不只是单元测试

合约测试分三层：

1. **单元测试**：验证函数行为——用断言（如 Hardhat 的 Chai）检查返回值、事件、状态变更。
2. **集成测试**：多个合约交互——如测试一个 DEX 合约与 Token 合约联动。
3. **分叉测试（fork testing）**：本地拉取主网状态，在副本上模拟真实环境，验证合约与已部署协议的兼容性。

```javascript
// Hardhat + ethers 的典型测试
const { expect } = require("chai");

it("should increment", async function () {
  const Counter = await ethers.getContractFactory("Counter");
  const counter = await Counter.deploy();
  await counter.increment();
  expect(await counter.count()).to.equal(1);
});
```

**测试优先的安全观**：合约的每个 `require`/`if` 分支都要有对应测试；边界值（`0`、最大 `uint256`、重复调用）都要覆盖。审计者看你的测试覆盖率，就像法官看你的证据链。<span class="marginnote">好的测试还会用「攻击者视角」写：测试「未授权的调用者试图提款应该 revert」这类否定用例——很多合约在「快乐路径」完美、在「恶意路径」崩溃。</span>

## 4 安全最佳实践清单

写合约时把这些当作强制规范：

- **检查-效果-交互（Checks-Effects-Interactions）**：先校验条件，再修改状态，最后调外部合约——这能防御绝大多数重入攻击（见《区块链安全》）。
- **优先 pull 模式**：让用户自己取款（`withdraw()`），不要合约主动 `push` 转账——减少「调用栈攻击」面。
- **拒绝外部依赖裸用**：`require(amount > 0)` 而不是依赖未校验的 `msg.value`；所有数学运算注意溢出（0.8 已默认检查，`unchecked` 慎用）。
- **权限控制**：用 OpenZeppelin 的 `Ownable`/`AccessControl`，不要手写 `if (msg.sender != owner) revert`。
- **事件（event）必须发**：链上状态变更要 emit 事件，方便链下索引与监控。
- **暂停开关（pause）**：复杂合约应有 `pausable` 紧急熔断机制，给升级留缓冲。

## 5 升级模式：代理合约

合约不可变，但业务需要升级。标准方案是**代理模式**：

- **代理合约（proxy）**：用户交互的地址，通过 `delegatecall` 把调用转发给逻辑合约。
- **逻辑合约（implementation）**：存放实际代码；升级 = 部署新逻辑合约 + 更新代理指向。
- **`delegatecall` 的关键语义**：逻辑合约的代码在**代理的存储上下文**中执行——逻辑合约里的状态变量必须与代理的布局完全一致（否则存储错位）。

**辨析｜易错点：`delegatecall` 是 Solidity 里最危险的特性之一。** 它让被调用方代码以调用方存储运行，一旦逻辑合约里有「改 `owner`」之类的操作，攻击者可能通过代理篡改任意状态。现代实践是：逻辑合约锁死初始化（`initializer` 只跑一次）、用 `UUPS` 模式把升级权限收归治理。**另一个易错点：「升级」不等于「修 bug 自由」**——如果升级需要权限，合约就不是「去中心化的」了；治理与安全之间需要显式权衡。

## 6 部署、验证与交互

1. **部署**：脚本里配置私钥与 RPC，广播部署交易。
2. **验证（verify）**：把源码上传到区块浏览器（Etherscan），让用户能核对「链上字节码 = 你声称的源码」。
3. **交互**：前端用 ethers/viem 读取合约（`call`，免费）或写状态（`sendTransaction`，付 Gas）。
4. **监控**：用事件监听、子图（The Graph）索引链上数据。

**开源即信任**：不验证源码的合约，用户无法确认它到底在干什么——「神秘合约」是安全审计的红灯。

## 7 从开发到审计的交付清单

把「写完合约」到「安全上线」的完整链路整理成一张可勾选的清单——这是工程纪律的落地：

**开发阶段**：

- [x] 用 OpenZeppelin 库（`Ownable`、`ReentrancyGuard`、`SafeERC20`）而非手写轮子。
- [x] 所有外部调用放在状态更新之后（Checks-Effects-Interactions）。
- [x] 数学运算依赖 0.8 默认检查，`unchecked` 块有注释说明为什么安全。

**测试阶段**：

- [x] 单元测试覆盖全部 `require` 分支与边界值（0、最大值、溢出）。
- [x] 否定用例：未授权调用、超额度、重入尝试都应 revert。
- [x] 集成测试：与真实 Token/DEX 合约交互；分叉测试在主网副本上跑。
- [x] 用 Slither / Mythril 做静态分析，用 Foundry 的 fuzz 做随机输入测试。

**部署与上线**：

- [x] 先在测试网（Sepolia）完整走一遍部署 + 交互。
- [x] 源码在区块浏览器验证（Etherscan verify），确保「链上字节码 = 开源源码」。
- [x] 部署后立刻用 `cast`/`hardhat console` 冒烟测试（owner、pause、基本函数）。
- [x] 配置监控：事件监听、链上警报、关键参数变更告警。

**审计与保险**：

- [x] 上线前完成至少一家第三方审计；高风险合约做两轮独立审计。
- [x] 设置 bug 赏金（bug bounty），把「找漏洞」从「地下黑产」变成「有偿服务」。
- [x] 评估是否需要保险（如 Nexus Mutual、Unslashed 的智能合约保险）。<span class="marginnote">「审计 + 赏金 + 保险」构成「风险转移三角」：审计降低「漏洞概率」，赏金缩短「发现时间」，保险覆盖「残余损失」。没有一个环节能单独保证安全，但三者叠加能把「单点失败」变成「多层防线」。对 DeFi 合约，「没有保险」本身就是一个需要向用户披露的风险项。</span>

**「写完」的定义**：一份合约「写完」不是「语法通过」，而是「通过了测试、审计、冒烟、监控四项」——**安全上线 = 代码 + 测试 + 审计 + 运营的联合交付**。

**辨析｜易错点：「审计通过」不是「无漏洞」的承诺，而是「审计范围内的最佳已知」**。审计报告常附「已知问题」与「建议」，不等于「必然安全」。**另一个易错点：升级（代理）不等于「无风险修复」**——代理模式引入了「delegatecall 存储布局」的新风险面；「能升级」恰恰意味着「升级本身可能被攻击」（如 2021 年 PAID Network 通过升级加入恶意逻辑）。「可升级」是把「不可变」的安全换成了「治理权限」的安全——两者各有代价。

## 8 小结

- 工具链以 **Hardhat / Foundry** 为主，配 **Sepolia 测试网**与 ethers/viem；部署 = 发一笔含字节码的交易。
- 合约地址由 **sender + nonce 的哈希**确定性推导；`CREATE2` 允许预计算地址。
- 测试分**单元 / 集成 / 分叉**三层，安全视角的否定用例不可省。
- 安全规范：**检查-效果-交互、pull 模式、权限控制、事件、暂停开关**；升级用**代理 + delegatecall**，但 delegatecall 本身是危险面。
- 部署后**不可回滚**——测试网不是流程，是安全的廉价保险。
