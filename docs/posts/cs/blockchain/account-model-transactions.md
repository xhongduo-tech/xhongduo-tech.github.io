## 为什么从账户模型开始

上一节说了以太坊是「状态机」，但它的「状态」长什么样？比特币用 **UTXO（未花费输出）** 模型，以太坊改用**账户余额（account balance）**模型。这个看似简单的选择，深刻影响了编程体验与安全模型：账户模型让合约可以直接读余额、改余额，但也引入了重放攻击与随机数（nonce）管理问题。这一节把两类模型摆开对比，再把以太坊交易的完整生命周期拆开。

## 1 UTXO 与账户模型的对比

**UTXO 模型（比特币）**：账本是一堆「未花费输出」的集合。每笔交易的输入引用之前的 UTXO，输出产生新的 UTXO。余额 = 你名下所有 UTXO 之和。

**账户模型（以太坊）**：账本是一张「地址 → 余额」的表。交易直接从一个账户扣钱、往另一个账户加钱。

| 维度 | UTXO（比特币） | 账户（以太坊） |
| --- | --- | --- |
| 状态形态 | 输出集合 | 地址→余额表 |
| 余额计算 | 扫描所有 UTXO 求和 | 直接读账户字段 |
| 并发/并行 | 天然适合并行（互不依赖） | 顺序执行，共享状态 |
| 合约开发 | 脚本受限 | 直接读写状态 |
| 隐私 | 较好（地址易换） | 余额聚合易追踪 |
| 复杂度 | 简洁（无状态） | 状态管理复杂 |

**为什么以太坊选账户模型？** 因为合约需要「账户」这种持久的、可读写的状态容器——一个 DEX 合约要记录每个人的流动性份额，UTXO 那种「一次性输出」模型极难表达。<span class="marginnote">UTXO 的并行性常被比特币社区视为优点：两笔不相关的交易可以并行验证；而以太坊的状态是全局的，任何交易都可能触碰任何合约，只能串行执行。这也是「UTXO 适合支付、账户模型适合编程」的根源。</span>

## 2 两类账户

以太坊有两类账户：

- **外部账户（EOA, Externally Owned Account）**：由私钥控制，**余额、nonce** 两个字段，可以发起交易（只能由私钥签名触发）。
- **合约账户（Contract Account）**：由代码控制，字段含**余额、nonce、存储根（storage_root）、代码哈希（code_hash）**，不能主动发起交易，只能被 EOA 或其他合约调用。

| 字段 | EOA | 合约账户 |
| --- | --- | --- |
| 私钥 | 有 | 无 |
| 能否发起交易 | 能 | 不能（只能被调用） |
| 代码 | 无 | 有（字节码） |
| 存储 | 无 | 有（持久化键值对） |

**公式解析：状态转换函数**

以太坊黄皮书定义交易如何改变状态：

$$
\sigma' = \Pi(\sigma, T)
$$

- **第一步**：$\sigma$ 是当前世界状态，$T$ 是一笔经签名的交易。
- **第二步**：$\Pi$ 执行完整状态转换：验证签名 → 扣发件人余额与 Gas 预付款 → 若目标地址无账户则创建 → 执行合约代码（若是合约调用）→ 更新 nonce → 得出新状态 $\sigma'$。
- **第三步**：每个节点独立执行 $\Pi$，若结果与区块头承诺的 `state_root` 不一致，则拒绝该区块。**状态转换的确定性是共识的最后一环。**

## 3 交易的完整结构

一笔以太坊交易（类型 0/1/2，以类型 2 的 EIP-1559 为例）包含：

| 字段 | 含义 |
| --- | --- |
| `nonce` | 发件人已发送的交易数，**防重放**的关键 |
| `from` | 发件人地址（由签名恢复） |
| `to` | 收件人（合约调用时为合约地址） |
| `value` | 转账金额（wei） |
| `data` | 调用数据（函数选择器 + 参数编码） |
| `gasLimit` | 本次执行允许消耗的 Gas 上限 |
| `maxFeePerGas` / `maxPriorityFeePerGas` | 单价上限与矿工小费 |
| `signature` | 私钥对以上字段的签名 |

**Nonce 为何重要**：如果交易没有 nonce，攻击者可以「重放」——把你的一笔转账原样再广播一次，钱被扣两次。nonce 使每笔交易都有唯一序号，已用过的序号不再有效。<span class="marginnote">nonce 必须严格等于该账户「已发送交易数」：太小会被拒绝（序号已用），太大要等前面所有交易确认（阻塞）。这是钱包实现里最容易出错的地方——多笔交易并发时 nonce 管理不当会导致交易「卡住」。</span>

**解析 data 字段**：合约调用时，`data` 的前 4 字节是**函数选择器**（函数签名哈希的前 4 字节），其后是 ABI 编码的参数。例如 `transfer(address,uint256)` 的选择器是 `0xa9059cbb`。

## 4 交易生命周期

一笔交易从发出到确认：

1. **签名与广播**：钱包构造交易、用私钥签名、广播到 P2P 网络。
2. **验证与池化**：节点验证签名、nonce、余额足够，加入交易池（mempool）。
3. **打包执行**：矿工/验证者按 Gas 价格排序打包，在 EVM 中执行。
4. **状态更新与确认**：区块广播，各节点重放验证状态根，交易被纳入链上。
5. **不可逆（最终）**：PoS 下 2/3 质押确认后进入最终状态，不可回滚。

**辨析｜易错点：合约账户不能「主动」发起交易。** 所有链上执行都由 EOA 的交易触发；合约只能通过 `CALL` 调用其他合约，不能自己定时执行、不能自己发起转账。因此「合约自动执行」都是「被外部交易触发后的联动执行」。另一个易错点：**地址 ≠ 账户**——同一私钥可以控制多个地址，一个地址对应一个账户；「私钥即控制权」在账户模型下同样成立，丢失私钥即丢失该地址下的全部资产。

## 5 从账户到智能合约生态

账户模型为以太坊带来了「可组合性（composability）」：一个合约可以自由读取、调用另一个合约，DeFi 的「乐高积木」因此成为可能——这正是 UTXO 模型难以实现的。下一节，我们学习在这些账户上写程序的语言：**Solidity 语法基础**。

## 6 交易签名与 EIP-712

交易不只是「数据」，它必须被私钥**签名**才有效。理解签名在以太坊的落地，有两个层次：

**原始交易的签名（RLP 编码）**：以太坊交易用 RLP（Recursive Length Prefix）序列化后，做 Keccak-256 哈希，再被私钥签名，得到 `(v, r, s)`。节点从签名恢复出 `from` 地址并验证——**发件人不是「填进去」的，是从签名「算出来」的**。这意味着：

- 任何人都无法「伪造」一笔不是自己私钥签名的交易。
- 交易的 `from` 字段实际由签名推导，恶意节点无法篡改「谁发的」。

**EIP-712 结构化签名**：直接对「原始交易字段」签名存在 UX 问题——用户看到的是「一堆十六进制」，无法确认「我到底在签什么」。EIP-712 定义「**结构化数据签名**」：把「可读的语义字段」（如「批准 amount 给 spender」）编码成标准格式再签名，钱包里展示「人类可读的交易意图」，用户确认后签名。<span class="marginnote">EIP-712 是「链下授权 + 链上执行」的基础：DApp 让用户离线签一个「结构化授权」（如「同意出售这个 NFT」），再把签名交给合约执行——用户只签「意图」，不必支付 Gas。它的安全价值在于「签名内容可读、可防钓鱼」——如果钱包展示的字段与你期望的不一致，你就不该签名。这也是 2022 年 OpenSea 钓鱼攻击利用「盲签」骗走 NFT 的原因：用户签名了「看不懂的内容」。</span>

**签名在以太坊的「三种用途」**：

1. **交易签名**：授权「转账/调用合约」——付 Gas、写状态。
2. **消息签名**：登录 DApp（「我是这个地址的持有者」）、托管证明——不付 Gas、不写状态。
3. **结构化签名（EIP-712）**：授权「链下意图」——如 Permit（ERC-2612 的「无 Gas 授权」）、订单签名、多签提案签名。

**公式解析：交易哈希与签名的验证链**

$$
\text{txhash} = \text{Keccak-256}(\text{RLP}(T)), \qquad \text{from} = \text{ecrecover}(\text{txhash}, v, r, s)
$$

- **第一步**：交易 $T$ 的字段做 RLP 编码，再哈希得 `txhash`。
- **第二步**：`ecrecover`（EVM 预编译）从 `(v, r, s)` 恢复出签名者的公钥，再哈希成地址。
- **第三步**：若恢复出的地址 = 交易声称的 `from`，签名有效。**注意 `ecrecover` 的一个经典坑**：对「任何哈希」都能恢复出一个「看起来合理的地址」——合约若用 `ecrecover` 验证「签名者是否为特定人」，必须同时检查「恢复出的地址是否等于期望地址」，否则可能接受「伪造地址」的签名。

**辨析｜易错点：签名 ≠「授权一切」，「盲签」是最大的钓鱼面。** 用户签了「看不懂的内容」，可能等于把资产支配权交给攻击者（2022 年 OpenSea 的 Seaport 钓鱼就是利用「让用户签一个合约调用」）。**另一个易错点：`v` 值（27/28 或 0/1）不是可忽略的元数据**——它决定「椭圆曲线点的符号」，漏掉/改错 `v` 会恢复出错误的地址。钱包与合约实现里，`v` 的解析错误是「签名失效/地址错乱」的常见原因。

## 7 小结

- **UTXO**（比特币）是「输出集合」模型，适合支付、天然并行；**账户模型**（以太坊）是「地址→余额」表，适合合约编程。
- 账户分**外部账户（EOA）**与**合约账户**：前者有私钥可发起交易，后者只有代码、被动调用。
- 状态转换 $\sigma' = \Pi(\sigma, T)$ 必须**确定性**，节点重放比对状态根。
- 交易含 `nonce`、`value`、`data`、`gasLimit` 等字段；**nonce 防重放**、data 携带调用参数。
