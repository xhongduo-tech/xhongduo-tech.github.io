## 为什么先辨析「相关」

上一节我们立住 ILP 的坐标系，指出四类限制因素里最难缠的是**相关（dependence）**。这一节把相关彻底讲清——因为**整个第二篇的技术（记分板、Tomasulo、重命名、推测）本质上都是在与相关博弈**。<span class="marginnote">记分板与 Tomasulo 处理数据相关（[[scoreboard-dynamic-scheduling]]、[[tomasulo-algorithm]]），寄存器重命名消除名相关（[[register-renaming]]），分支预测对付控制相关（[[branch-prediction-1bit-2bit]]）。本节是它们的共同地基。</span>

先记住一条总原则：**只有「数据真正流动」的依赖才不可消除；纯属「名字撞车」的依赖可以改名消掉；「该不该执行」的依赖只能靠预测来赌。** 下面逐一展开。

## 1 三种数据相关的精确定义

考察两条指令 $i$（在前）与 $j$（在后），若它们访问同一个寄存器/存储器位置，就构成相关。按读写方向分三种：

| 相关类型 | 英文 | 方向 | 判据 | 能否消除 |
| --- | --- | --- | --- | --- |
| **真相关（RAW）** | Read After Write | $i$ 写、$j$ 读 | $j$ 需要 $i$ 产出的值 | **不能**，只能等待或转发 |
| **反相关（WAR）** | Write After Read | $i$ 读、$j$ 写 | 顺序错开会读到旧值 | 能，寄存器重命名 |
| **输出相关（WAW）** | Write After Write | $i$ 写、$j$ 写 | 顺序错开最终结果就错 | 能，寄存器重命名 |

**核心概念**：**RAW（真相关）**也叫流相关，是唯一代表**数据真实流动**的相关——$j$ 要用的值由 $i$ 产生，这就是依赖的本来面目。<span class="marginnote">「RAW」按时间顺序读：R 在 A 之后，先写后读，所以是 Read After Write。WAR 是先读后写，WAW 是写写——名字容易记反，背下「<strong>真正的数据流只有 RAW</strong>」就能防错。</span>

举个具体的例子。设三条指令：

```asm
ADD  R1, R2, R3    ; ① 写 R1
SUB  R4, R1, R5    ; ② 读 R1
MUL  R1, R6, R7    ; ③ 写 R1
```

第一条→第二条是 RAW（R1 的数据在流动，必须等）；第一条→第三条是 WAW（都写 R1）；第二条→第三条是 WAR（第二条读 R1、第三条写 R1）。

检测相关只需看「位置 + 方向」，不看数值大小——编译器无法预知运行时的值，所以一切按最坏情况判断。这也是为什么「寄存器重命名能消除 WAR/WAW」而「RAW 不能」：RAW 的依赖是**运行时的数据流**，重命名换不掉；WAR/WAW 的依赖是**编译期的名字冲突**，换名即消。

把三条指令按读写方向画成一张依赖图会更清晰：**RAW 是实线（数据真实流动），WAR/WAW 是虚线（名字约束）**。实线不可断，虚线可以重画——「虚线靠重命名改画、实线靠转发与等待」就是整个动态调度的几何直觉。

## 2 为什么只有 RAW 是「真」相关

关键洞察：**WAR 与 WAW 之所以「相关」，只是因为在某个固定的寄存器文件里，两个互不相干的值恰巧用了同一个名字。** 把其中一个值换个寄存器放，两个相关立刻消失：

```asm
ADD  R1, R2, R3    ; ① 写 R1
SUB  R4, R1, R5    ; ② 读 R1（RAW 保留：真的要用①的结果）
MUL  R8, R6, R7    ; ③ 改写 R8，不再写 R1——WAW、WAR 同时消失
```

改名（**寄存器重命名**）就是硬件运行时自动做这件事。而 RAW 无法改名消除——因为**数据真的要从 $i$ 流到 $j$**，唯一的缓解是把 $i$ 的结果**转发（forwarding/bypassing）**给 $j$，让 $j$ 不必等 $i$ 写回寄存器。

**辨析｜易错点：** 「反相关（WAR）」这个名字容易误导。它不表示数据反向流动，而是**访问次序相反**：先读后写。如果先执行写、后执行读，读到的就是新值——所以次序反了才出问题，故称「反相关」。它和 RAW 完全不同源，靠重命名可 100% 消除。

**转发（forwarding/bypassing）**把 RAW 的等待从「等写回寄存器」压缩到「等结果算出来」：结果一产生就从功能单元输出端直送后续指令的输入端，省去「写回再读」的完整周期。**转发不消除 RAW，只缩短 RAW 的可见延迟**——调度器仍要保证读在写之后（或借重命名错开），只是不必等寄存器文件。

## 3 控制相关：分支带来的特殊依赖

数据相关约束「顺序」，**控制相关（control dependence）**约束「选择」：分支指令决定它后面的指令是否应该执行。如：

```asm
BEQZ  R1, skip      ; 若 R1 == 0 则跳过下一条
DADD  R2, R2, R3    ; 仅当分支不跳时才执行
```

DADD 是否执行，取决于 BEQZ 的结果。这构成控制相关，处理方式分两条路：

**保守派**：等分支判定完再取后续指令——流水线要停顿（分支延迟）。指令少但效率低。
**投机派**：**分支预测**——猜一个方向先执行，猜对了白赚时间，猜错了冲刷流水线、付出惩罚。现代处理器 95%+ 的预测正确率让投机成了主流。<span class="marginnote">注意控制相关与数据相关的本质差别：数据相关无法「猜」出结果，控制相关可以「猜」方向。猜错了有惩罚，但<strong>正确率足够高时期望收益为正</strong>——这正是分支预测器研究的全部理由。</span>

控制相关的惩罚也要量化：设分支预测准确率 95%、分支频率 20%、惩罚 20 周期，则分支造成的平均惩罚为 $0.20 \times 0.05 \times 20 = 0.20$ 个 CPI；准确率跌到 90%，惩罚翻倍到 0.40——**预测器的一个百分点，就是处理器吞吐的若干个百分点的涨落**。这也是为什么现代处理器的预测器要一路做到 99%+。

还有一个隐蔽的控制相关来源：**异常与中断**。指令可能在任何位置被外部事件打断，处理器必须保证「被打断后能精确恢复」——这正是 [[precise-exceptions-speculation-recovery]] 的主题。**控制相关不止来自分支，也来自「程序流的非局部改变」**。

## 4 循环中的相关：循环携带依赖

循环是 ILP 的主战场，也藏着最隐蔽的相关。若循环体内部的一条指令依赖**上一次迭代**某指令的结果，就构成**循环携带相关（loop-carried dependence）**，把迭代串成一条链：

```asm
Loop:  L.D    F0, 0(R1)     ; 取 a[i]
       ADD.D F2, F2, F0    ; sum += a[i]——F2 依赖上一次迭代的 F2 → 循环携带相关
       DADDUI R1, R1, #8
       BNE    R1, R3, Loop
```

这种相关把迭代串成一条**链**，严重限制并行度：即使有 4 发射，这段循环的迭代也只能一个一个推进。对策要么改写算法（消除链），要么靠后面的循环级并行与向量化（见 [[loop-level-parallelism-dependency]]）。<span class="marginnote">判断循环能否并行，就看循环体之间是否存在循环携带相关。无相关的循环（如 $a[i] = a[i] + 1$）才能被向量化或分配到多个核上。</span>

把循环携带相关的代价算成数字。设循环体内部只有一条 RAW 链（如 `sum += a[i]` 的加法链），一次迭代的依赖链长 $L$ 个周期。即使 4 发射，**迭代间距（initiation interval）也不能小于 $L$**——这是关键路径决定的。若 $L = 4$、循环共 $N = 10^6$ 次迭代，总耗时至少 $4N$ 周期；把和式拆成两路累加（`sum1`、`sum2`），两条链并行推进，总耗时约 $2N$——**把「串行累加」改成「分治并行」，是循环级并行最朴素也最有效的胜利**。

循环携带相关的另一种形态是**访存别名**：`a[i]` 与 `b[j]` 若可能在运行时指向同一地址，编译器就认为它们之间可能有 RAW/WAR——即便源程序里看不出。解决靠指针别名分析或运行时检查，**保守假设**仍是默认立场。

循环携带相关的强度还取决于链上指令数：`sum += a[i]` 是「单步链」；若循环体是 $y = f(g(x))$ 的多步依赖，链长就是 $f$、$g$ 两步之和。**链越短、并行度越高**——许多数值算法刻意改写累加顺序、改用分治或前缀和，本质都是在缩短关键路径。

## 5 相关如何被化解：一张总表

把所有相关与其对策放在一起：

| 相关类型 | 产生根源 | 化解手段 | 硬件/软件 |
| --- | --- | --- | --- |
| RAW | 数据真实流动 | 转发、等待、调度 | 硬件转发 + 动态/静态调度 |
| WAR | 寄存器名字撞车 | 寄存器重命名 | 硬件（Tomasulo、重命名） |
| WAW | 寄存器名字撞车 | 寄存器重命名 | 硬件（Tomasulo、重命名） |
| 控制相关 | 分支的选择性执行 | 分支预测 + 推测执行 | 硬件（预测器）+ 软件（调度） |
| 资源冲突 | 硬件单元不足 | 加宽功能单元、多端口 | 硬件成本权衡 |

**辨析｜易错点：** 自动检测这些相关的通用方法是**下标分析（subscript / index analysis）**：把数组访问 $a[i]$ 与 $a[j]$ 抽象成「$i$ 与 $j$ 的取值范围」，若两者可能取到同一地址、且访问次序可能颠倒，就报告冲突。现代编译器的向量化与循环并行都建立在这套分析上（见 [[loop-level-parallelism-dependency]]）。它的第一准则是**保守**——宁可少并行，不可错并行：分析不出「无相关」就不并行，而不是反过来。

资源冲突与数据相关也常被混为一谈：**资源冲突是「硬件不够用」，相关是「数据有依赖」**。4 发射的处理器若只有 2 个整数 ALU，三条无相关的整数指令也会因资源不足而排队——相关分析管不到这里，由调度器负责。诊断性能瓶颈时先分清「等数据」还是「等硬件」，排查方向完全不同。

## 6 小结

- 三种数据相关：**RAW（真相关，数据流动）**、**WAR（反相关）**、**WAW（输出相关）**；只有 RAW 不可消除。
- 检测方法：看两条指令对同一位置是**先写后读、先读后写、还是写写**。
- **寄存器重命名**把 WAR/WAW 变成历史：改名后相关消失，见 [[register-renaming]]。
- **控制相关**约束「是否执行」，靠分支预测投机解决；猜错有惩罚。
- **循环携带相关**把迭代串成链，是循环并行的头号障碍。
- 一个程序能被挖掘多少 ILP，几乎取决于「RAW 链有多长 + 分支有多难猜」。
