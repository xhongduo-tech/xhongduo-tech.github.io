## 为什么编译器能「优化 Cache」

硬件预取是被动观察，编译器则是**主动重排**。编译器在编译期知道数组布局与循环结构，可以把循环的**访问次序**改成对 Cache 更友好——而**程序计算的结果完全不变**。这类优化往往能带来数量级的访存改善，因为**它直接改的是访存模式本身**。<span class="marginnote">这节是 [[cache-optimization-prefetching]] 的「软件版」：硬件在运行时猜，编译器在编译期算。两者互补——<strong>编译器改顺序，硬件抓漏网</strong>。它也是 [[loop-level-parallelism-dependency]] 的前置：先让访存友好，再谈并行。</span>

## 1 循环交换：让内层循内存连续

看一个典型双循环（C 数组按行优先）：

```c
// 坏：内层沿 i 遍历 → 步长 M，空间局部性差
for (j = 0; j < M; j++)
    for (i = 0; i < N; i++)
        a[i][j] = b[i][j] + c;

// 循环交换后：内层沿 j 遍历 → 连续访问，Cache 友好
for (i = 0; i < N; i++)
    for (j = 0; j < M; j++)
        a[i][j] = b[i][j] + c;
```

**核心概念**：**循环交换（loop interchange）**把内外层循环对调，让**最内层循环沿内存连续方向**遍历——空间局部性最好的访问方式。代价是必须保证交换不改变结果（可交换性由编译器分析确认）。

行优先的代价模型：现代 CPU 一次取一个 cache line（64 字节 ≈ 16 个 `double`），内层连续访问时每 16 次运算只有 1 次缺失；按步长 M 的列访问则几乎每次缺失——**同一条赋值语句，访问次序决定了约 16 倍的缺失差距**，这就是循环交换存在的全部理由。

## 2 分块（Blocking/Tiling）：让数据留在 Cache

矩阵乘法是分块的教科书案例。朴素三重循环：

```c
for (i = 0; i < N; i++)
    for (j = 0; j < N; j++)
        for (k = 0; k < N; k++)
            c[i][j] += a[i][k] * b[k][j];
```

问题：B 的列访问破坏局部性，每个 B[k][j] 都可能被反复搬入搬出。**分块**把矩阵切成 $B \times B$ 的小块：

```c
for (i = 0; i < N; i += B)
    for (j = 0; j < N; j += B)
        for (k = 0; k < N; k += B)
            for (ii = i; ii < i + B; ii++)
                for (jj = j; jj < j + B; jj++)
                    for (kk = k; kk < k + B; kk++)
                        c[ii][jj] += a[ii][kk] * b[kk][jj];
```

**核心概念**：**分块（blocking / tiling）**把数据切成**恰好放得进 Cache 的小块**，让每个数据块在 Cache 里被**反复重用**后才被换出。块大小 $B$ 的选取准则：**参与计算的若干块要能同时装进 Cache**（通常取「3 块恰好容纳」）。<span class="marginnote">分块的本质是「<strong>人为制造时间局部性</strong>」：把对同一小块数据的多次访问压缩在它还在 Cache 的时间里完成。对矩阵乘法，分块可以把缺失数从 $O(N^3)$ 级别压到 $O(N^3 / B)$——快几倍到几十倍。</span>

## 3 更多变换：融合、展开、数据布局

- **循环融合（loop fusion）**：把两个遍历同一数据的循环并成一个，数据只装载一遍。
- **循环展开（loop unrolling）**：摊薄循环开销，也给调度器更多并行机会——对 Cache 收益间接。
- **数据布局变换**：把**结构体数组（AoS）**换成**数组结构体（SoA）**，让访存沿同一字段连续——向量化与 Cache 都受益。

```c
// AoS：结构体数组——同一字段的成员在内存里互相隔开
struct Point { float x, y, z; };
struct Point pts[N];                // pts[i].x, pts[i].y 不连续

// SoA：数组结构体——同一字段连续存放
struct Points { float x[N], y[N], z[N]; };
struct Points pts;                  // pts.x[i] 连续 → 向量化与 Cache 双受益
```

编译器对这几招的执行顺序也讲究：先做依赖分析确认安全，再选变换，最后用 `-O2`/`-O3` 级别的代价模型估算收益——**「收益不确定就不改」是编译器的默认立场**。GCC/LLVM 的自动向量化与循环分发（loop distribution）都建立在这套保守框架上。

## 4 公式解析：分块把缺失砍到多少

朴素矩阵乘法每算一个 $C[i][j]$ 要把一整行 A、一整列 B 搬进来，总缺失数约：

$$
\text{Miss}_{\text{朴素}} \approx 2N^3 \quad(\text{每个元素反复缺失})
$$

分块后（块大小 $B$，且 $3B^2$ 能装进 Cache），每个 $B\times B$ 块只在第一轮载入，之后全部命中：

$$
\text{Miss}_{\text{分块}} \approx \frac{2N^3}{B}
$$

- **第一步，看朴素**：$C[i][j]$ 的 $k$ 循环里，A 行、B 列的元素反复换入换出，几乎每次都要缺失。
- **第二步，看分块**：$A$ 与 $B$ 的块载入 Cache 后，$B^2$ 次内层运算都命中——缺失被摊销到 $B$ 个元素上。
- **第三步，选 $B$**：$B$ 越大缺失越少，但 $3B^2$ 超过 Cache 容量就适得其反——**$B \approx \sqrt{C/3}$ 是甜点位**。

套一组实数。设 $N = 1000$，数据是双精度（8 字节），Cache 能容纳 $C = 32\text{ KB}$。由 $3B^2 \times 8 \le 32768$ 解得 $B \le \sqrt{32768/24} \approx 37$，取 $B = 32$。朴素缺失约 $2 \times 10^9$ 次，分块后约 $\frac{2 \times 10^9}{32} = 6.25 \times 10^7$——**下降 32 倍**。若贪心取 $B = 64$，则 $3 \times 64^2 \times 8 = 98\text{ KB}$ 塞不进 32 KB 的 Cache，块在计算中途被换出，缺失数反而回升——**B 不是越大越好，是「恰好装下」最好**。

## 5 编译器如何证明「交换安全」

循环交换不是无脑对调——编译器必须**证明交换后结果不变**（依赖分析，见 [[loop-level-parallelism-dependency]]）：

- 检查内外循环的**依赖方向**：若交换后依赖会「从后往前」读，结果就错。
- 经典判据：**交换后内层循环仍是「正向扫描」**（依赖方向不反转）。
- 判断不了就**拒绝交换**——宁可不优化，不能优化错。

**辨析｜易错点：** 循环交换的目的不是「让代码好看」，而是**让内层沿内存连续方向访问**（空间局部性）。C 数组行优先，内层循环就该走行（列下标 j 变化）；矩阵乘里把 k 循环放内层是另一个经典——**「哪个循环放最内层」本身就是性能设计的核心决策**。另一个易错点是分块与硬件无关：块大小 $B$ 的甜点位依赖**实际 Cache 容量与替换策略**，写死的 $B$ 换一台机器就可能失效——编译器通常做**自动调优（tuning）**，在若干候选 $B$ 上实测选最优，而不是靠一条公式猜。

## 6 小结

- 编译器改**访存次序**不改**结果**，就能做体系结构级优化。
- **循环交换**让内层循内存连续，喂饱空间局部性。
- **分块**让数据块在 Cache 里被重用，矩阵乘法缺失从 $O(N^3)$ 降到 $O(N^3/B)$。
- 融合、展开、**AoS→SoA** 是同一家族的其他招式。
- 编译器优化与硬件预取互补：改顺序 + 抓漏网。
