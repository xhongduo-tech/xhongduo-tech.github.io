## 为什么虚拟内存是「翻译引擎」

虚拟内存让每个进程拥有独立的地址空间、并支持内存分页换入换出（「操作系统」分类里的经典内容）。但体系结构的视角是**性能**：CPU 每访问一次内存，都要把**虚拟地址翻译成物理地址**——若翻译本身很慢，整台机器就废了。<span class="marginnote">翻译的「缓存」叫 <strong>TLB（Translation Lookaside Buffer）</strong>，它就是虚拟内存世界的 L1 Cache——用 [[locality-principle]] 做靠山，把「查页表」变成「查 TLB」。RISC-V 的 Sv39 多级页表（[[riscv-privileged-architecture]]）就是本节的软件侧对应。</span>

## 1 从虚拟地址到物理地址：页表与多级页表

**核心概念**：虚拟地址被切成**虚拟页号（VPN）**与**页内偏移**；VPN 查**页表**得到**物理页号（PPN）**，PPN + 偏移 = 物理地址。

页表有多大？64 位地址 + 4 KB 页 → 每个进程理论上有 $2^{52}$ 个页——**单级页表根本装不下**。于是用**多级页表（hierarchical page table）**：像树一样逐级索引，只有用到的页才分配表项。

```text
虚拟地址（如 Sv39）：
┌─────────┬─────────┬─────────┬─────────┐
│ 一级索引 │ 二级索引 │ 三级索引 │ 页内偏移 │
└────┬────┴────┬────┴────┬────┴────┬────┘
     ▼         ▼         ▼         ▼
 ┌──────┐  ┌──────┐  ┌──────┐
 │ 顶级表 │→ │ 二级表 │→ │ 页表   │ → 物理页 → 物理地址
 └──────┘  └──────┘  └──────┘
   按需分配：未用到的地址空间不建表 → 省内存
```

**多级页表的好处**：未用到的地址空间**不占内存**（每级表按需分配），且每级表项可以携带权限位、脏位、访问位——供缺页与写回使用。

## 2 TLB：页表项的缓存

**核心概念**：**TLB（Translation Lookaside Buffer）**：缓存最近用到的**页表项（PTE）**，让「翻译」大多时候直接命中。它按**虚拟页号**索引，条目含物理页号与权限位。

典型容量：数十到数千项；组织上常为**全相联**（因为页数少、命中判断快）或大组相联。
**TLB 命中**：一个周期拿到物理地址，访存继续。
**TLB 缺失**：要**页表遍历（page table walk）**——逐级查页表（硬件自动，或软件陷入）。一次缺失可能要多级内存访问，代价几十到上百周期。

## 3 TLB 优化：把缺失率打下来

TLB 缺失代价大，所以一堆优化瞄准「少缺」：

**大页（huge pages）**：用 2 MB/1 GB 的大页替代 4 KB，**一项 TLB 覆盖更大的连续空间**——TLB 缺失率直降。数据库与虚拟化负载的经典利器。
**多级 TLB（L1/L2 TLB）**：小的 L1 TLB（快） + 大的 L2 TLB（容量），像 Cache 一样分层。
**Victim TLB / 二级 TLB 预取**：为 TLB 缺失提供备用与预取。
**TLB 一致性**：OS 改页表时要能**冲刷对应 TLB 项**（TLB 无效化，tlb shootdown），保证翻译不过期。<span class="marginnote">页表与 TLB 的同步是 OS 与硬件协作的经典接口：写 PTE 后必须刷 TLB，否则「改了权限不生效」。RISC-V 用 SFENCE.VMA、x86 用 CR3 重载/INVLPG——<strong>每一种 ISA 都把它做成显式指令</strong>。</span>

## 4 地址翻译与 L1 Cache：VIPT

翻译发生在访存路径上，会**增加 L1 命中时间**吗？设计的关键是让翻译与 L1 索引**并行**：

**VIPT（Virtual Index, Physical Tag）**：用**虚拟地址的索引位**（页内偏移，翻译前后相同）选 L1 组，同时并行查 TLB；等翻译出物理地址后只用来**比较标签**。索引不依赖翻译 → 翻译不串行于 L1 访问。
**PIPT（Physical Index, Physical Tag）**：等翻译完再索引，简单但命中时间更长。

VIPT 的前提是 **L1 组数 × 块大小 ≤ 页大小**（索引位落在页内偏移里）——否则不同虚拟地址会映射到同一物理地址却落进不同组（别名问题）。<span class="marginnote">这就是为什么 L1 不能做得「无限大」的另一个硬约束：<strong>L1 索引位必须藏在页内偏移内，否则要么别名要么翻译串行</strong>。小 L1 的第三个理由。</span>

## 5 公式解析：带 TLB 的平均访存

$$
\text{访存时间} = T_{\text{TLB命中}} + M_{\text{TLB}} \times T_{\text{遍历}} + T_{\text{Cache}}
$$

（忽略细节，直观形式）

- **第一步，看 $T_{\text{TLB命中}}$**：翻译本身的时间，通常与 L1 访问**并行**（VIPT），不算进关键路径。
- **第二步，看 $M_{\text{TLB}} \times T_{\text{遍历}}$**：TLB 缺失时多付的页表遍历时间。$M_{\text{TLB}}$ 越小越好——**大页、多级 TLB 就是冲它去的**。
- **第三步，看 $T_{\text{Cache}}$**：翻译完成后 L1 的命中/缺失成本照旧。**TLB 优化不改变 Cache 本身，只减少翻译侧的额外负担**。

## 6 数值算例：大页让 TLB 多盖 512 倍的地址

设 TLB 有 64 项，比较不同页大小下的**总覆盖范围**：

- **4 KB 页**：$64 \times 4\,\text{KB} = 256\,\text{KB}$——工作集稍大就到处缺失。
- **2 MB 大页**：$64 \times 2\,\text{MB} = 128\,\text{MB}$——**覆盖提升 512 倍**。
- **1 GB 巨页**：$64 \times 1\,\text{GB} = 64\,\text{GB}$——几乎全覆盖。

$$
\text{覆盖} = \text{TLB 项数} \times \text{页大小}
$$

**要点**：数据库/虚拟化负载的工作集常达 GB 级——4 KB 页下 TLB 缺失如雨，每缺一次就是几十上百周期的页表遍历；**改用大页，同样的 TLB 硬件把缺失率压掉几个数量级**。这就是「大页是 TLB 优化第一招」的原因。

## 7 常见误区再辨析

- **「页越大越好」**：大页省 TLB 但**粒度粗**——小对象也占一整页、换入换出浪费内存；**大页要按工作集特征选**。
- **「多级页表比单级慢」**：有 TLB 时多级遍历只在缺失时发生；单级表虽「快」却巨大到放不下——**多级换的是空间，不是命中时间**。
- **「TLB 缺失 = 访问内存」**：TLB 缺失要先**遍历页表**（可能再缺内存页，触发缺页中断）——它比普通 Cache 缺失贵得多，这正是它值得专门优化的原因。
- **「VIPT 的别名只是理论问题」**：别名会导致一个物理页被映射进两组——**Linux 的页面着色（page coloring）**就是为规避它，是真实工程问题。

## 8 术语速查

| 术语 | 含义 |
| --- | --- |
| TLB | 页表项的缓存 |
| 虚拟页号（VPN） | 虚拟地址中的页号部分 |
| 物理页号（PPN） | 页表映射得到的物理页号 |
| 多级页表 | 树形逐级索引的页表 |
| 页表遍历（walk） | TLB 缺失后逐级查页表 |
| 大页（huge pages） | 2 MB/1 GB 的大粒度页 |
| VIPT | 虚拟索引 + 物理标签 |
| 别名（aliasing） | 同物理页映射到多组 |

## 9 小结

- **虚拟内存 = 翻译引擎**；多级页表按需分配，省空间。
- **TLB** 缓存页表项，命中一个周期、缺失几十到上百周期。
- TLB 优化主线：**大页降缺失率、多级 TLB 分层、Victim 与预取、一致性冲刷**。
- **VIPT** 让翻译与 L1 索引并行，不串行加命中时间；别名约束 L1 大小。
- TLB 缺失的代价决定了「翻译优化」与「数据优化」同等重要。

在下一节，我们把虚拟化再推一层——**虚拟机的存储保护与地址转换加速**。单进程的「虚拟→物理」已经够复杂，虚拟机要在其上再叠一层「客户→宿主」的翻译——TLB 优化的问题会以放大版重新出现。
