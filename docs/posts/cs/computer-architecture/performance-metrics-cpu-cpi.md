## 为什么先要定义「性能」

上一节我们立下了「以大概率事件为快」的量化原则，也拿到了优化判据的公式。但公式里的「时间」到底怎么算？一台「快」的计算机，快在哪个数上？——这是本节要解决的**度量地基**。

Hennessy 与 Patterson 在《量化研究方法》第 1 章反复强调一个反直觉的事实：**绝大多数关于「哪个机器更快」的争论，都死于度量定义不清。** 有人用主频比快慢，有人报 MIPS 数字，有人甩出每秒多少亿次运算——这些数字经常互相打架，而且都可以被刻意「调大」。本节的使命是：把「性能」拆成有严格物理定义、不可造假的量，并让你看清 MIPS 这类宣传数字为什么危险。

## 1 响应时间与吞吐量：性能的两副面孔

**性能（performance）**不是单一的量，它至少有两副面孔：

- **响应时间（response time）**，也叫**执行时间（execution time）**：完成一个任务所花的总时间。对用户而言，「快」最朴素的意义就是它——点一下，多久出结果。
- **吞吐率（throughput）**，也叫**带宽（bandwidth）**：单位时间内完成的任务数。对数据中心而言，每秒能服务多少个请求才是「性能」。

**重点：两副面孔经常不能兼得。** 一台服务器把 8 个请求并行处理，吞吐率变成 8 倍，但单个请求的响应时间并没有缩短，甚至因为排队而变长。<span class="marginnote">这就是第三级《数据库》与第八篇《仓库级计算机》里「延迟与吞吐的取舍」的雏形：在线服务要压低尾延迟（用户感知），批量分析要追求总吞吐（成本感知）。同一台机器，衡量目标不同，结论可以相反。</span>定义性能前，先问清楚你要的是哪一个。

本书（以及本专题）默认的「性能」指**响应时间**。两台机器 $X$、$Y$，若 $X$ 比 $Y$ 快 $n$ 倍，定义是：

$$
n = \frac{\text{Execution time}_Y}{\text{Execution time}_X}
$$

## 2 CPU 时间：什么才算「干完了活」

执行时间内部还要再切一刀，因为程序在机器上跑的时间并不都是它的功劳。用 `time` 命令看一个程序，通常得到三个数：

- **墙钟时间（wall-clock / elapsed time）**：从开始到结束的全部时间，包含等待 I/O、被其他进程抢占的空档。
- **用户 CPU 时间（user CPU time）**：真正花在程序自己指令上的 CPU 时间。
- **系统 CPU 时间（system CPU time）**：程序请求内核帮忙（读文件、分配内存、网络收发）而花在操作系统上的 CPU 时间。

**核心概念：CPU 时间（CPU time）**：用户 CPU 时间与系统 CPU 时间之和，是「CPU 真正为这个程序干活」的时间。它剔除了等待与调度噪声，是最能反映处理器本身快慢的量。<span class="marginnote">为什么系统时间也算？因为操作系统执行的内核代码，同样在消耗这台机器的处理器周期。衡量「机器」而不是「程序」，就该两者都算。第三级《操作系统》会详细讲进程调度、系统调用如何影响这两部分时间。</span>

**辨析｜易错点：墙钟时间 ≠ CPU 时间。** 一个以 I/O 为主的程序，墙钟时间可能 10 秒、CPU 时间只有 0.5 秒——它大部分时间在等磁盘。优化它的处理器毫无意义，瓶颈在存储系统（本专题第四篇）。反过来，一个计算密集程序两者几乎相等。所以任何性能报告必须先声明量的是哪一种时间。

## 3 CPU 时间等式：三个可调的旋钮

CPU 时间由三个量相乘而来，这是全书第一重要的公式：

$$
\text{CPU time} = \text{IC} \times \text{CPI} \times \text{Cycle time}
$$

- **指令数（instruction count, IC）**：程序总共执行了多少条指令。由**指令集架构（ISA）与编译器**决定：同一个程序，CISC 指令更强大、条数更少；RISC 指令更简单、条数更多。
- **每条指令的平均时钟周期数（cycles per instruction, CPI）**：执行一条指令平均需要的时钟周期数。由**微架构与存储系统**决定：流水线、缓存、乱序执行都影响它。
- **时钟周期（cycle time）**：一个时钟周期多少秒，即主频的倒数（$1 / f$）。由**工艺与实现**决定。

**重点：三个旋钮互相纠缠，不能孤立调节。** 这是本节的第一个大坑。降低 IC（用更强的指令）往往抬高 CPI；提高主频往往让 CPI 也变差（因为更紧的时序迫使缓存做小、流水线做浅）。谈「调快哪个旋钮」，必须放进 CPU time 的乘积里整体看，这正是量化的意义。<span class="marginnote">第三级《编译原理》是 IC 与 CPI 博弈的主战场：编译器可以选择循环展开（条数变多但 CPI 变好），也可以选择指令合并（条数变少但 CPI 变差）。「编译优化到底有没有用」，最终要回到 CPU time 这一个数上来裁决。</span>

## 4 公式解析：CPU 时间 = 指令数 × CPI × 时钟周期

把 CPU 时间等式拆成两步，理解每个因子的单位，就能体会到它为什么无法造假的干净：

$$
\text{CPU time} = \text{Clock cycles} \times \text{Cycle time}
= \frac{\text{Instructions}}{\text{Program}} \times \frac{\text{Clock cycles}}{\text{Instruction}} \times \frac{\text{Seconds}}{\text{Clock cycle}}
$$

- **第一步，指令数 × CPI = 总时钟周期数**：程序一共 $IC$ 条指令，每条平均花 $CPI$ 个周期，总共 $IC \times CPI$ 个周期。单位是「周期」，与「秒」还差一步。
- **第二步，总周期数 × 周期时长 = 秒**：每个周期 $\text{Cycle time}$ 秒，于是 $IC \times CPI \times \text{Cycle time}$ 秒。若用主频 $f = 1/\text{Cycle time}$，可写成 $IC \times CPI / f$。
- **第三步，单位的漂亮消去**：$\frac{\text{指令}}{\text{程序}} \times \frac{\text{周期}}{\text{指令}} \times \frac{\text{秒}}{\text{周期}}$——三个分母分别与上一项分子相消，最后只剩「秒/程序」。**任何一个真实机器报出的 CPU 时间，都必须能这样严格地消掉单位**；凡是消不干净、多出来的「每秒XX亿次」之类的宣传数字，都隐含着定义上的可操纵空间。

代一个具体例子。机器主频 $f = 2\text{ GHz}$（即 $\text{Cycle time} = 0.5\text{ ns}$），程序 $IC = 10^9$ 条指令，平均 $CPI = 1.5$：

$$
\text{CPU time} = 10^9 \times 1.5 \times 0.5 \times 10^{-9}\,\text{s} = 0.75\,\text{s}
$$

如果把主频提到 $3\text{ GHz}$ 而 CPI 不变，CPU time 变成 $0.5\,\text{s}$；但如果高主频迫使缓存缩水、CPI 涨到 2.0，CPU time 反而变成 $10^9 \times 2.0 \times (1/3\times 10^9) \approx 0.67\,\text{s}$——只快了 12%，而不是「频率提升 50%」。

## 5 加权 CPI：指令混合的平均

现实的程序由多种指令构成，CPI 是对各指令类的加权平均。设指令分成 $n$ 类，第 $i$ 类指令的条数为 $I_i$，其平均周期数为 $CPI_i$：

$$
\text{CPI} = \frac{\sum_i CPI_i \times I_i}{IC} = \sum_i CPI_i \times \frac{I_i}{IC}
$$

**加权 CPI 是「以大概率事件为快」在性能公式里的直接体现**：占指令流比例大（$I_i/IC$ 大）的那类指令，它的 $CPI_i$ 对总 CPI 的贡献也最大，优化它就最划算。算一个混合指令的例子，机器主频 $2\text{ GHz}$：

| 指令类 | 占比 $I_i/IC$ | 单条 CPI |
| --- | --- | --- |
| 整数运算 | 0.50 | 1.0 |
| 访存 | 0.30 | 2.5 |
| 分支 | 0.15 | 2.0 |
| 浮点运算 | 0.05 | 4.0 |

$$
\text{CPI} = 0.50 \times 1.0 + 0.30 \times 2.5 + 0.15 \times 2.0 + 0.05 \times 4.0
= 0.50 + 0.75 + 0.30 + 0.20 = 1.75
$$

若 $IC = 10^9$，则 $\text{CPU time} = 10^9 \times 1.75 \times 0.5\,\text{ns} = 0.875\,\text{s}$。注意访存类只占 30% 的指令，却贡献了 $0.75$，占总 CPI 的 43%——所以存储系统优化（第四篇全部内容）常常比「更快的算术单元」更值钱。

## 6 MIPS 的陷阱与 FLOPS 的分工

**核心概念：MIPS（million instructions per second，每秒百万条指令）**：

$$
\text{MIPS} = \frac{IC}{\text{CPU time} \times 10^6} = \frac{f}{\text{CPI} \times 10^6}
$$

MIPS 的问题在于：**它度量的是「机器执行了多少条指令」，而不是「程序做完了没有」。** H&P 用下面这个经典例子一针见血：

**辨析｜易错点：MIPS 可以与性能完全反向。** 两台机器运行同一程序。机器 A：$IC = 2\times 10^8$ 条，用时 100 秒，MIPS = $2\times10^8/(100\times10^6) = 2$。机器 B：$IC = 3.6\times10^8$ 条，用时 120 秒，MIPS = $3.6\times10^8/(120\times10^6) = 3$。**B 的 MIPS 更高（3 > 2），但 B 更慢（120 s > 100 s）。** 一台「每秒执行更多指令」的机器，完全可能跑一个程序更慢——因为指令更长、更琐碎、或者架构不同导致 IC 暴增。

MIPS 的三个致命伤：

- **指令粒度不统一**：不同 ISA 的一条指令，工作量天差地别。RISC 机器天然比 CISC 机器 MIPS 高，但快不快是另一回事。
- **依赖具体程序**：同一个机器，换一个程序，MIPS 变；拿 MIPS 跨机器比，等于拿「各自的菜谱」比「上菜速度」。
- **无法反映 I/O 与存储**：MIPS 只数指令，不数数据搬运。

社区里甚至有人把 MIPS 戏称为 **Meaningless Indicator of Processor Speed（毫无意义的处理器速度指标）**。<span class="marginnote">MIPS 曾是真·营销武器：1990 年代厂商在广告里竞相比 MIPS，为了把数字做大，甚至可以挑一个特别有利于自己的小程序来「校准」。这正是下一节《基准测试程序》要建立规矩的原因——度量必须由独立的、公认的工作负载来背书。</span>

**辨析｜易错点：FLOPS 不是 MIPS 的替身，而是另一个角度的宣传数字。** FLOPS（每秒浮点运算次数）度量的也是「机器干了多少浮点运算」，同样不度量「程序做完了没有」。它在科学计算与深度学习领域比 MIPS 有意义（因为这类负载几乎全是浮点运算），但仍然要区分「峰值 FLOPS」与「实际 FLOPS」——上一节峰值吞吐公式算出的就是前者，实际能拿到几分之几，取决于数据能否喂得进计算单元。

## 7 小结

- **性能**至少有两副面孔：**响应时间**（本书默认）与**吞吐率**，二者经常不可兼得。
- **CPU 时间** = 用户 CPU 时间 + 系统 CPU 时间，剔除了等待与调度噪声；墙钟时间 ≠ CPU 时间。
- **CPU 时间等式** $\text{CPU time} = \text{IC} \times \text{CPI} \times \text{Cycle time}$，三个因子互相纠缠，只能放进乘积里整体看。
- **加权 CPI** $\text{CPI} = \sum_i CPI_i \cdot I_i/IC$ 是「以大概率事件为快」在性能公式里的投影——占比大的指令类决定总 CPI。
- **MIPS 的陷阱**：它度量「执行了多少指令」而非「任务是否完成」，可以出现「MIPS 更高反而更慢」的悖论，跨架构比较尤其危险。
- 唯一可靠的性能判据：**在真实目标工作负载上的 CPU 时间**。

度量终于有了不造假的定义，但还有一个环节没解决：**「真实目标工作负载」由谁说了算？** 下一节《基准测试程序：SPEC、TPC 与基准测试的选择》，我们来看业界如何用公认的基准测试，让「度量」从论文走向商战。
