## 为什么方向之外还要「目标」

前面的预测器都只回答一个布尔问题：**跳不跳**。但跳转指令真正要落地，还得回答第二个问题：**往哪跳**。在深流水线里，如果每次都要等到译码阶段把 PC 相对偏移算出来才知道目标地址，取指阶段就被拖住了。<span class="marginnote">方向预测（[[branch-prediction-1bit-2bit]]、[[tournament-tage-predictors]]）解决「该不该跳」，本节解决「跳去哪」。两者相加才是完整的取指预测。</span>

更麻烦的是**返回指令（RET）**：它的目标是「调用点之后的那条指令」，调用点可能成百上千个——同一段函数代码从哪被调用，就返回到哪。**目标地址根本不在指令里**，靠前两类机制都猜不准。这一节的两个主角正是为这两件事而生的。

## 1 BTB：把目标地址缓存下来

**核心概念**：**分支目标缓冲区（Branch Target Buffer, BTB）**：一张以「分支指令 PC」为索引的小缓存，每个条目存：目标地址（+ 方向预测位，视设计而定）。

取指时并行查 BTB：

**命中**：立刻知道「这是分支、该不该跳、目标在哪」——下一拍直接按目标取指，**零停顿**。
**未命中**：取到的不是已知分支，照常顺序取指，待译码后把目标地址**登记进 BTB**，供下次使用。

BTB 的命中率取决于容量与分支集大小；现代 BTB 有数千到数万条目，配合**多路组相联**结构。它还顺带承担**间接跳转**的预测（switch-case 跳转表、虚函数调用的目标），把「目标」一并缓存。<span class="marginnote">BTB 与普通 Cache 的差别在于它缓存的是<strong>「预测信息」而不是「数据」</strong>，错了不产生数据错误、只产生性能损失——这是它敢用宽松索引的根本原因。</span>

## 2 为什么返回指令是特例

返回指令（RET）的目标是动态的：CALL 把返回地址压栈，RET 从栈中把它弹出。用 BTB 猜返回目标会怎样？

```asm
main:   jal   ra, func        ; 调用点 A：返回地址 = 这里下一条
...
again:  jal   ra, func        ; 调用点 B：返回地址 = 这里下一条
...
func:   ...
        jalr  x0, ra, 0       ; ret：目标 = ra，这次是 A 的下一条，下次是 B 的下一条
```

BTB 对同一段 RET 指令只能记一个目标——今天从 a 来、明天从 b 来，**同一段 RET 的目标不断变化**，BTB 必错一半以上。

## 3 返回地址栈（RAS）：硬件栈来救场

**核心概念**：**返回地址栈（Return Address Stack, RAS）**：一块**按 LIFO 管理**的小硬件栈，专门预测返回目标：

遇到 CALL：把返回地址**压栈**。
遇到 RET：**弹栈**，弹出的地址就是预测目标，同时按此取指。

因为调用返回天然是「先进后出」的括号结构，RAS 的预测几乎总是对的——**准确率轻松 99%+**。它只需要一个很小的栈（现代处理器 16–48 项），因为嵌套调用深度通常有限。

**辨析｜易错点：** RAS 与 BTB 各管一段：**RAS 只服务 CALL/RET 的返回目标，BTB 服务普通条件分支与间接跳转**。有些设计把 RAS 也算作「BTB 的一种」，但机制完全不同（栈 vs 缓存）。考题说「用 LIFO 栈预测返回地址」指的一定是 RAS。

## 4 推测世界的 RAS：错了怎么滚

RAS 与推测执行结合时有个隐患：**如果一条 CALL 是猜错方向的、或是投机取指下来的，压栈就压错了**，会污染后续所有 RET 的预测。对策：

投机压栈/弹栈**只影响预测，不影响架构状态**（真正的返回地址由调用约定里的寄存器/内存承担）。
预测失败（方向猜错）时，**把 RAS 栈顶回退到分支之前的快照**——用「检查点（checkpoint）」记录栈指针，按需恢复。<span class="marginnote">这与 [[register-renaming]] 的 RAT 快照、[[hardware-speculation-rob]] 的 ROB 冲刷是同一套「投机状态快照」哲学的又一实例：<strong>所有推测结构都必须支持无损回滚</strong>。</span>

## 5 核心对比表：BTB vs RAS

> 本节为纯概念主题，以核心对比表替代公式解析。

| 维度 | BTB | RAS |
| --- | --- | --- |
| 服务对象 | 条件分支、间接跳转 | CALL/RET 的返回目标 |
| 数据结构 | 以 PC 索引的缓存 | LIFO 硬件栈 |
| 条目内容 | 目标地址（+方向位） | 返回地址 |
| 预测原理 | 历史目标复用 | 调用/返回的括号匹配 |
| 典型准确率 | 高（分支目标稳定时） | 99%+ |
| 推测恢复 | 无需回滚（只缓存） | 需要栈顶快照回滚 |

**辨析｜易错点：** 条件分支的**方向**（跳不跳）与**目标**（跳哪去）是两件事，方向由预测器管、目标由 BTB 管。对于 PC 相对跳转，目标其实可以直接用 PC+偏移算出，BTB 的价值是**省掉这次加法、提前一拍**；对间接跳转与返回，BTB/RAS 的价值才是真正「无法即时计算」。

## 6 数值算例：BTB 命中率值多少钱

设分支约占指令 20%、BTB 未命中时取指停顿 2 周期：

- **BTB 命中率 90%**：每条指令平均代价 $= 0.2 \times 0.10 \times 2 = 0.04$ CPI。
- **BTB 命中率 95%**：代价 $= 0.2 \times 0.05 \times 2 = 0.02$ CPI——**省一半**。
- **BTB 命中率 99%**：代价 $= 0.2 \times 0.01 \times 2 = 0.004$ CPI——几乎可忽略。

$$
\Delta\text{CPI} = \underbrace{0.2}_{\text{分支占比}} \times \underbrace{(1-\text{命中率})}_{\text{未命中率}} \times \underbrace{2}_{\text{停顿}}
$$

**要点**：BTB 的命中率从 90% 提到 99%，省下约 0.036 CPI——对 1 的基线 CPI 是 3.6% 的全局提速。**看似「只是预测」的小结构，命中率就是真金白银**；这也解释了为什么现代 BTB 做到数千条目的规模。

## 7 常见误区再辨析

- **「BTB 预测方向」**：BTB 主要缓存**目标地址**，方向常由预测器另管；有的设计把方向位也放进去，但二者职责不同。
- **「RAS 就是一个小缓存」**：RAS 是 **LIFO 栈**，靠调用/返回的括号匹配工作——不是按 PC 索引的缓存。
- **「间接跳转没法预测」**：间接跳转的目标虽动态，但常常稳定（同一 switch 分支重复执行）——BTB 靠历史目标即可命中。
- **「投机压栈会写坏架构栈」**：RAS 只是**预测结构**，真正的返回地址仍在架构寄存器/内存里——投机压栈错了只需回滚预测。

## 8 术语速查

| 术语 | 含义 |
| --- | --- |
| BTB | 分支目标缓冲区 |
| 间接跳转 | 目标来自寄存器的跳转 |
| RAS | 返回地址栈 |
| CALL / RET | 调用/返回指令 |
| LIFO | 后进先出 |
| 投机压栈 | 预测执行中的压栈操作 |
| 检查点（checkpoint） | 推测结构的可回滚快照 |
| 取指停顿 | BTB 未命中造成的取指气泡 |

## 9 小结

- **BTB** 缓存「分支 PC → 目标地址」，让取指阶段零停顿拿到跳转方向与目标。
- **返回指令目标动态可变**，BTB 无能为力；**RAS** 用 LIFO 栈精确模拟调用/返回括号结构。
- RAS 准确率 99%+，是现代处理器标配的廉价高收益结构。
- 投机执行下，RAS 需要**栈顶快照回滚**，与 RAT/ROB 的恢复哲学一致。
- 方向预测 + 目标预测（BTB/RAS）合起来，才构成完整的取指预测体系。

在下一节，我们从「怎么猜、猜哪去」转向「每周期发射几条」——**多发射处理器：超标量（Superscalar）与超流水线**。方向与目标都预测准了，硬件才能放心大胆地每个周期多取、多发、多执行几条指令。
