## 为什么还有人把调度交给编译器

上一节的超标量让**硬件**在运行时找并行——灵活，但代价高昂：保留站、ROB、发射逻辑占面积与功耗。另一个极端是把这件事**提前到编译期**：编译器一次看一大段代码、做依赖分析，把互相独立的指令**打包**成一条超长指令，硬件只需要机械地「拆包执行」。这就是 **VLIW**。<span class="marginnote">VLIW 的哲学与 [[superscalar-superpipelined]] 针锋相对：超标量把复杂度放在硬件，VLIW 把复杂度放在编译器。双方竞争的是同一件事——「谁来决定每周期发射哪几条指令」。</span>

## 1 VLIW 的机制：一条指令装四条

**核心概念**：**VLIW（Very Long Instruction Word）**：把若干条互相独立的操作**静态打包**进一条超长指令字，指令字里每个**槽位（slot）**对应一个功能单元。取出一条长指令 = 同时发射 $w$ 条操作。

```text
一条 256 位 VLIW 指令字（4 个槽位，各对应一个功能单元）：
┌──────────┬──────────┬──────────┬──────────┐
│ 槽 0     │ 槽 1     │ 槽 2     │ 槽 3     │
│ 整数 ALU │ 整数 ALU │ 访存     │ 分支     │
└──────────┴──────────┴──────────┴──────────┘
取出这一条指令 = 同时向 4 个功能单元各发出 1 条操作
```

每个槽位在流水线的固定位置各就各位。硬件没有发射逻辑、没有保留站、没有乱序引擎——**取指、解码、发射全是机械动作**。这是 VLIW 最大的卖点：**简单、低功耗、可预测的时序**。

## 2 为什么 VLIW 难写：三个硬骨头

编译器打包的前提是**知道每条指令的延迟**，并保证同字内无依赖。三个现实问题：

**依赖检查要极其保守**：Cache 未命中、分支是否跳，编译期都看不见，只好按最坏情况填 NOP。
**代码膨胀**：并行度不足的指令组要用 NOP 填满槽位。打包成 $w$ 宽后，原本 $n$ 条指令占 $\lceil n/w \rceil$ 个字，但**每字的空槽全浪费**。并行度低时，代码体积比顺序执行还大。
**二进制不兼容**：功能单元数量一变、延迟一变，整个打包就得重来——**升级硬件 = 重新编译所有软件**。<span class="marginnote">这是 VLIW 在通用计算里最致命的一击：体系结构承诺的「软件兼容」在 VLIW 里做不到。Itanium 的失败很大程度上就栽在这里。</span>

**辨析｜易错点：** VLIW 不是「乱序执行的一种」。它恰恰是**完全有序**的——顺序由编译器排版定死，硬件一字不改地照做。说「VLIW 由硬件动态重排指令」是错的。

## 3 历史：Multiflow 与 i860 的兴衰

**Multiflow Trace 700**（1987）：把「trace scheduling」思想落地——把最热路径上的基本块串成 trace 打包。在科学计算上表现亮眼，但通用软件生态没跟上，公司 1990 年倒闭。
**Intel i860**（1989）：双发射 VLIW 微处理器，编译器支持不佳，实际性能远逊设计值。
教训：**VLIW 的成败系于编译器**。编译器写不出足够好的并行调度，硬件再简单也白搭。

## 4 EPIC / IA-64：VLIW 的工程化尝试

Intel 与 HP 在 1990 年代合作推出 **IA-64 / Itanium**，用「显式并行指令计算（Explicitly Parallel Instruction Computing, EPIC）」包装 VLIW 思想：

**显式并行**：指令组（bundle）里明确标注哪些可并行，编译器把依赖信息**直接写进指令字**。
**显式投机（speculation）**：硬件提供投机支持（如 speculative load），编译器显式使用。
**断言（predication）**：把分支转换成「条件执行」，消除分支本身。
**软件流水（software pipelining）**：编译器把循环展开并错位排布，让每次迭代的载荷重叠——用软件模拟硬件流水。

Itanium 在服务器市场耕耘多年，最终因编译器难以发挥 EPIC 威力、二进制兼容问题、功耗与性能不敌 x86 动态超标量而淡出。<span class="marginnote">Itanium 的落幕常被误读为「静态多发射全盘失败」。实际上 VLIW 在<strong>嵌入式 DSP、GPU 调度内核、以及部分 AI 加速器</strong>里活得很好——凡是「编译器可控、负载规则、功耗敏感」的场景，VLIW 仍是优选。</span>

## 5 核心对比表：超标量 vs VLIW

> 本节为纯概念主题，以核心对比表替代公式解析。

| 维度 | 超标量（动态） | VLIW/EPIC（静态） |
| --- | --- | --- |
| 谁找并行 | 硬件（发射队列） | 编译器（打包） |
| 硬件复杂度 | 高（保留站/ROB） | 低（机械拆包） |
| 功耗 | 高 | 低 |
| 代码膨胀 | 无 | 有（NOP 填充） |
| 二进制兼容 | 好 | 差（硬件变了要重编） |
| 适用 | 通用计算 | DSP、嵌入式、负载规则场景 |

**公式解析（NOP 浪费的量化）**：设发射宽度 $w$，编译器在某段程序里能静态挖出的平均并行度 $p$（$p \le w$），则有用槽位占比 $\frac{p}{w}$。若 $p=2$、$w=4$，一半槽位是 NOP——**代码体积翻倍，且执行时间并未缩短**。这就是「并行度不足时 VLIW 反而不如顺序执行」的数学本质。

## 6 小结

- **VLIW** 把多条独立操作打包进一条长指令字，槽位对应功能单元，硬件机械执行。
- 三大硬骨头：**编译期看不到的动态延迟、NOP 造成的代码膨胀、硬件变更导致二进制不兼容**。
- 历史教训：Multiflow、i860、Itanium 的成败都系于**编译器能否挖出足够并行**。
- **EPIC**（IA-64）用显式并行、显式投机、断言、软件流水包装 VLIW 思想。
- VLIW 在通用计算失利，但在 DSP、嵌入式与规则负载里持续成功——**简单与低功耗是它永远的王牌**。
- 动态与静态调度并非二选一：现代超标量处理器里，编译器也做**指令调度**，与硬件乱序互补。
