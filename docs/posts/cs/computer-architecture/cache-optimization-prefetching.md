## 为什么预取是「防患于未然」

非阻塞 Cache 把缺失延迟**藏**起来，预取更进一步：**在数据真正被用到之前就把它取进 Cache**，让「该用时」直接命中。对规律访存（数组遍历、流式处理），预取几乎把缺失代价**归零**——这是所有 Cache 优化里潜在收益最大的一种。<span class="marginnote">预取依赖 [[locality-principle]] 的空间局部性，更依赖「<strong>访存模式可预测</strong>」。可预测才有得猜，猜得准才不浪费带宽。它与 [[branch-prediction-1bit-2bit]] 一样，都是「预测 + 验证」家族的成员。</span>

## 1 硬件预取：让硬件自己学会「下一步」

硬件预取器（hardware prefetcher）在 CPU 里常驻，悄悄观察访存流、自动发起预取：

**下一行预取（next-line / sequential）**：访问块 $i$ 后顺手取 $i+1$——最简单，对顺序流（数组、指令流）有效。现代 CPU 的「流预取器（streamer）」就是它的加强版：检测到连续若干次顺序访问后，开始规律预取。
**步长预取（stride）**：记录每个 PC 的访存步长（如每次都 +64 字节），预测下一个地址并预取。处理数组行遍历、结构体数组特别有效。
**相关预取（correlation / PC-based）**：记录「访问 A 之后总跟着访问 B」的历史，据此预取 B。对指针追逐、链表这类不规则访存有效。

<strong>辨析｜易错点：</strong> 硬件预取**不做指令，只观察与执行**——它不需要软件配合，但只能识别「已经被硬件识别出的模式」。指针对追逐、图遍历这类「内存里藏着地址」的访问，普通预取器抓不住。

## 2 编译器预取：把「提前取」写进程序

编译器在**编译期**就看出访存模式，主动插入**预取指令**（如 x86 的 `prefetcht0`、ARM 的 `pld`/`prfm`）：

```c
for (i = 0; i < n; i++) {
    __builtin_prefetch(&a[i + 25]);   /* 提前 25 个元素发预取 */
    s += a[i];
}
```

预取指令把数据取进 Cache，但**不改变程序语义**（不产生数据依赖）——它只是一句「建议」，硬件可无视。编译器要决定**预取距离**：提前多远发预取，才恰好覆盖缺失延迟。

## 3 预取的代价：带宽与污染

预取不是免费的：

**带宽占用**：预取用掉的内存/互连带宽，可能与真实请求抢资源——预取过度反而拖慢。
**Cache 污染（pollution）**：预取来的数据若根本没用，会**挤掉有用的数据**，推高缺失率。
**功耗**：无谓的预取白耗电。

所以好的预取策略都带**抑制逻辑**：检测到预取不命中/不使用时，自动降低预取强度或关闭。<span class="marginnote">这正是「以大概率事件为快」的又一次应用：<strong>预取只在模式规律时开足马力，模式混乱时就收手</strong>。Intel 处理器上不同的负载打开/关闭预取的性能差异可达 20%+。</span>

## 4 公式解析：预取距离

$$
k = \left\lceil \frac{L}{c} \right\rceil
$$

- **第一步，看分子 $L$**：一次 Cache 缺失的延迟（如 100 周期）——预取必须提前这么多周期发出。
- **第二步，看分母 $c$**：循环里每个元素消耗的周期数（如 4 周期/元素）。
- **第三步，求距离**：$k = \lceil 100/4 \rceil = 25$——**提前 25 个元素预取**，第 $i$ 次迭代去预取 $A[i+25]$，等用到 $A[i+25]$ 时数据正好到位。

距离太短：数据还没回来就撞上缺失；太长：数据可能被挤出去、且浪费提前量。**$k$ 是「预取让数据恰好按时到达」的甜点位**，编译器与硬件预取器都在估这个数。

## 5 核心对比表：硬件 vs 编译器预取

> 本节为纯概念主题，以核心对比表替代公式解析。

| 维度 | 硬件预取 | 编译器预取 |
| --- | --- | --- |
| 谁发起 | CPU 硬件引擎 | 编译器插指令 |
| 需不需要软件 | 不需要 | 需要编译期分析 |
| 可识别模式 | 顺序/步长/相关 | 任意可见的静态模式 |
| 代价控制 | 硬件抑制逻辑 | 编译期启发式 |
| 动态性 | 可随负载调整 | 编译后固定 |
| 现代处理器 | 几乎都有（streamer 等） | 配合使用 |

**辨析｜易错点：** 预取指令**不阻塞程序执行**（fire-and-forget），这是它与普通 Load 的本质区别。普通 Load 有数据依赖要等结果；预取只是「取来放着」。看到「预取指令参与数据流」的说法是错的。

## 6 数值算例：预取距离的账

设缺失延迟 $L = 200$ 周期、循环每元素 $c = 8$ 周期：

- **预取距离**：$k = \lceil L/c \rceil = \lceil 200/8 \rceil = 25$——提前 25 个元素发预取。
- **太短（$k=10$）**：数据在用到前只提前了 80 周期，还差 120 周期——**照样缺失**。
- **太长（$k=50$）**：提前 400 周期，数据可能在 Cache 里被挤掉，或白白占用带宽——**浪费**。

$$
k = \left\lceil \frac{L}{c} \right\rceil = \left\lceil \frac{200}{8} \right\rceil = 25
$$

**要点**：$k$ 是「预取让数据恰好按时到达」的甜点位——**太短救不了缺失，太长浪费带宽**。真实系统还要随负载动态调整 $k$，因为 $L$ 和 $c$ 都随系统状态变化。

## 7 常见误区再辨析

- **「预取一定提升性能」**：对规律访存是；对随机/不规则访存，预取白占带宽还可能挤掉有用数据——**反而变慢**。
- **「硬件预取比编译器好」**：各有盲区——硬件看不见编译期就知道的模式，编译器看不见运行时才显现的模式；**两者互补**。
- **「预取指令参与数据依赖」**：预取是 fire-and-forget，不产生数据依赖、不改变语义——它只是「建议」。
- **「预取越多越好」**：带宽有限，预取过猛会挤占真实请求——**抑制逻辑与强度控制是关键**。

## 8 术语速查

| 术语 | 含义 |
| --- | --- |
| 硬件预取 | CPU 硬件引擎自动预取 |
| 下一行预取 | 访问块 i 后顺手取 i+1 |
| 步长预取 | 按固定步长预测下一个地址 |
| 相关预取 | 记录 A 后总跟着 B 的历史 |
| 编译器预取 | 编译器插入 prefetch 指令 |
| 预取距离 k | 提前多少个元素发预取 |
| Cache 污染 | 预取挤掉有用数据 |
| 流预取器 | 检测顺序流后规律预取 |

## 9 小结

- **预取**提前把数据取进 Cache，把缺失延迟「防」掉；对规律访存收益巨大。
- **硬件预取**：下一行、步长、相关三种由浅入深；只认已被识别的模式。
- **编译器预取**：插预取（prefetch）指令，靠编译期分析 + 预取距离 $k = \lceil L/c \rceil$。
- 代价：**带宽占用、Cache 污染、功耗**——需要抑制逻辑与启发式。
- 预取把「可预测的访存」变成「免费」；模式不可预测时，回归被动缺失。

在下一节，我们看预取思想的软件版全集——**编译器优化（循环交换、分块）**。预取是「硬件/指令层面提前取」，编译器优化则是「在循环结构层面改变访存顺序」——两者从不同高度让数据更靠近。
