# 动态调度基础：记分板（Scoreboard）算法

<div class="epigraph">

## 为什么从记分板开始

上一节讲清了相关：RAW 必须等，WAR/WAW 可以改名。问题是谁来做「等」与「改名」？两条路线：**静态调度**让编译器在编译期排好序，**动态调度**让硬件在运行时根据真实数据流重排指令。<span class="marginnote">静态调度的代表是 VLIW（[[vliw-epic]]），它信任编译器；动态调度的鼻祖就是本节主角——1964 年 CDC 6600 的<strong>记分板</strong>，世界上第一台真正乱序执行的机器。</span>

为什么动态调度更优？因为**编译期看不到的数据依赖，运行时全都能看到**——Cache 命中与否、分支跳不跳、指令实际占用功能单元多久，只有硬件知道。记分板就是「硬件在运行时排指令顺序」的第一个完整方案，也是理解 Tomasulo、ROB 一切复杂机制的脚手架。

## 1 记分板的三张表

记分板（scoreboard）的核心是一组状态表，记录「谁该做什么」：

- **指令状态表（instruction status）**：每条已发射指令处于哪个阶段（发射/读操作数/执行/写结果）。
- **功能单元状态表（functional unit status）**：每个功能单元当前忙不忙、在执行什么操作、源/目的寄存器是谁（字段：Busy、Op、Fi、Fj、Fk、Qj、Qk、Rj、Rk）。
- **寄存器结果状态表（register result status）**：每个寄存器「正被哪个功能单元写入」。

这三张表让硬件能回答两个关键问题：**Fj/Fk 的值现在可用吗？** 若某个源寄存器正被别的功能单元预定写入（Qj ≠ 0），就必须等。这套机制与后续 Tomasulo 的**保留站**高度相似——区别在于记分板把「等待」放在功能单元入口，而 Tomasulo 把「等待」移到取指之后的保留站里。

## 2 记分板的四步流水

每条指令在记分板中分四步走：

1. **发射（Issue）**：若功能单元空闲且没有结构冲突，就从指令队列取一条指令、登记到功能单元状态表。**发射必须按程序顺序进行**（in-order issue），否则可能被 WAR/WAW 纠缠。
2. **读操作数（Read operands）**：当**所有**源操作数都可用（没有正在写它们的指令）时，立即读取——**这一步可以乱序**。
3. **执行（Execute）**：功能单元运算。若有数据依赖（前一条还在写），就等到结果可用；运算时间按单元而异。
4. **写结果（Write result）**：结果写回寄存器文件。**若存在一条尚未读该寄存器的更早指令（WAR），写结果必须等待**，否则会破坏旧的读取。

**核心概念**：乱序执行只发生在第 2–4 步，**发射永远有序**。记分板通过「读操作数乱序、写结果等待」来安全地乱序——这是它最精妙、也最容易被忽略的一点。

## 3 记分板如何对付三类相关

对照上一节的相关分类：

- **RAW**：靠第 3 步等待解决——功能单元在源寄存器 `Fj/Fk` 尚未就绪（`Qj` 非空）时阻塞。
- **WAR**：靠第 4 步的「写结果等待」解决——若有待读该寄存器的更早指令未读，写结果推迟。
- **WAW**：靠第 1 步的「发射顺序」解决——因为发射有序，不会出现两条写同一寄存器的指令乱序写结果。<span class="marginnote">注意记分板用「顺序发射」来挡 WAW，代价是阻塞流水线；Tomasulo 用寄存器重命名「绕开」WAW，完全不阻塞——这是两者的关键差异。</span>

再看一个经典例子（H&P 教材原例，F2 正是碰撞点）：

```
LD    F6, 34(R2)   ; 载入
LD    F2, 45(R3)   ; 载入
MULTD F0, F2, F4   ; 乘法，依赖上面的 F2
SUBD  F8, F6, F2   ; 减法，依赖两个载入
DIVD  F10, F0, F6  ; 除法，依赖乘法
ADDD  F6, F8, F2   ; 加法，与 MULTD 构成 WAW（都写 F0? 不，写 F6，与 DIVD 无冲突）
```

实际的执行时序里，`ADDD` 因 `DIVD` 占用除法单元会等待、`MULTD` 因等待 F2 会延迟——**每条指令的发射/读/执行/写各自错开**。这正是动态调度相对顺序执行的收益：一条被卡住，后面的无关指令照跑。

## 4 记分板的局限：为什么它只是「基础」

记分板开了乱序执行的先河，但有三道硬伤，也是它与 Tomasulo 的分水岭：

- **WAR/WAW 靠阻塞，不靠消除**：顺序发射与写结果等待会白白卡住后续无关指令，性能损失明显。
- **功能单元入口排队**：等待的操作数锁在功能单元状态里，若同一单元被长指令占用，后续短指令也进不来。
- **无硬件推测**：记分板不投机执行分支后的指令，控制相关的停顿依然在。

正是这些局限，催生了把「等待」前移、用重命名消除名相关的 **Tomasulo 算法**。

## 5 核心对比表：记分板 vs Tomasulo

> 本节为纯概念主题，以核心对比表替代公式解析。

| 维度 | 记分板（CDC 6600） | Tomasulo（IBM 360/91） |
| --- | --- | --- |
| 等待操作数的位置 | 功能单元入口 | 保留站（独立缓冲） |
| 名相关（WAR/WAW） | 阻塞等待 | **寄存器重命名消除** |
| 数据转发 | 直接转发 | 通过公共数据总线（CDB）广播 |
| 发射顺序 | 按程序序 | 按程序序 |
| 冲突检测 | 集中式记分板 | 分布式保留站 |
| 推测执行 | 不支持 | 不支持（本机）；配合 ROB 支持 |

**辨析｜易错点：** 「乱序执行」常被误以为等于「不按程序序发射」。两者都会**按序发射、乱序完成**；真正的区别在于名相关处理：记分板挡住 WAR/WAW，Tomasulo 改名后**让它们直接消失**。看到题目说「该处理器通过重命名消除 WAR」，指的一定是 Tomasulo 系，而不是记分板。

## 6 小结

- **记分板**是 1964 年 CDC 6600 的动态调度方案，用三张状态表追踪每条指令与每个功能单元。
- 四步流水：**发射（有序）→ 读操作数（可乱序）→ 执行 → 写结果**。
- RAW 靠等、WAR 靠写结果推迟、WAW 靠顺序发射——全部通过阻塞解决。
- 局限：名相关不消除只阻塞、操作数排队在功能单元入口、无推测执行。
- 记分板的价值是**范式**：硬件在运行时重排指令。后续一切乱序机制都从这里长出来。

在下一节，我们看 Tomasulo 如何用**保留站 + 寄存器重命名 + 公共数据总线**把记分板的阻塞变成绕过——这是乱序执行的第二次飞跃。
