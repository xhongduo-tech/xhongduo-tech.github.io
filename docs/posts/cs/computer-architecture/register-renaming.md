## 为什么把重命名单独讲

上一节我们看到 Tomasulo 用保留站「隐式」完成了重命名。但现代处理器用的是一种**显式**方案：物理寄存器堆 + 重命名映射表。为什么要把这个机制单独拎出来？因为**它是 WAR/WAW 相关唯一的真正解法，也是乱序处理器与精确异常衔接的枢纽**。<span class="marginnote">回顾 [[data-name-control-dependencies]]：WAR 与 WAW 只是「名字撞车」，不是数据流动。重命名就是给它们换名字——一句「改名」背后，是映射表、物理寄存器池、空闲列表一整套硬件的分工。</span>

理解重命名，你才看得懂现代 CPU 的微架构图里为什么寄存器堆那么大（物理寄存器远比架构寄存器多），也才能回答「乱序执行出错了怎么回滚」这种经典面试题。

## 1 架构寄存器 vs 物理寄存器

指令集规定的寄存器（如 RISC-V 的 32 个通用寄存器）叫**架构寄存器（architectural register）**——这是软件能看到的「名字」。芯片内部实际存放数据的寄存器叫**物理寄存器（physical register）**——这才是硬件真正的「容器」。

**核心概念**：**寄存器重命名（register renaming）**：把架构寄存器名动态映射到物理寄存器上，让两个需要「同一个名字」但数据无关的操作，实际写到**两个不同的物理寄存器**里。映射关系存在**重命名映射表（RAT, Rename Alias Table）**中。

为什么能这样做？因为指令集只承诺「程序按序执行时看到的结果」，而乱序执行只要保证**最终写回该名字的值**正确即可——中间过程把值存在哪个物理寄存器里，软件管不着。

## 2 三件套：映射表、物理寄存器堆、空闲列表

显式重命名需要三样硬件：

**重命名映射表（RAT）**：每个架构寄存器 → 当前指向的物理寄存器。发射指令时查它得到源操作数的最新版本。
**物理寄存器堆（physical register file）**：比架构寄存器多得多（如 32 个架构寄存器配 200+ 物理寄存器），容纳「多个尚未退役的同名值」。
**空闲列表（free list）**：管理哪些物理寄存器还没被占用。

一条写指令 `ADD R6, R2, R3` 的重命名流程：

1. 从空闲列表**分配**一个新物理寄存器 $p_{new}$。
2. 查 RAT：读 R2 → $p_j$，读 R3 → $p_k$（作为源操作数）。
3. 更新 RAT：R6 → $p_{new}$。
4. 等指令完成后，若旧物理寄存器不再被任何在途指令引用，**释放**回空闲列表。

**辨析｜易错点：** 释放旧物理寄存器的时机最容易被误解。不是「写指令一执行完就释放」，而是**确保没有更早的指令还要读它**。常见实现是让 RAT 里被替换的旧映射随指令在**重排序缓冲（ROB）**里退役时释放——所以重命名与 [[hardware-speculation-rob]] 总是绑在一起出现。

## 3 一个具体的例子：WAR 如何消失

看这段指令，正是上一节循环体的片段：

```asm
MUL  F10, F6, F2    ; 读 F6（发射最早，读到循环体开始时的旧值）
ADD  F6, F4, F8     ; 写 F6 → 分配 p20
SUB  F6, F6, F2     ; 读 F6（p20）+ 写 F6 → 分配 p21
```

在顺序寄存器堆里，`ADD` 与 `SUB` 抢同一个 F6，必须串行。重命名后：

`ADD` 写物理寄存器 $p_{20}$，RAT 中 F6 → $p_{20}$。
`SUB` 写物理寄存器 $p_{21}$，RAT 更新 F6 → $p_{21}$。
`MUL`（更早发射）读的是**它发射时刻 RAT 里 F6 的映射**，即 $p_{20}$ 之前的值——不受影响。

两个 F6 的「值」各住各的物理寄存器，**WAW 与 WAR 凭空消失**，迭代之间可以重叠执行。RAW 呢？`SUB` 等 `ADD` 的结果仍要等——那是真数据流，重命名管不了，由数据转发解决。

## 4 重命名与精确异常：为什么需要 ROB

乱序执行的一个难题：**如何保证异常时能精确恢复**？按序执行时，异常发生时指令i是第 i 条；乱序执行时，指令可能已经执行到很后面，异常现场被「打乱」了。

重命名在这里扮演关键角色：**每次写架构寄存器时，RAT 里被替换的旧映射被记录下来**。当要恢复精确状态时，只需把 RAT 回退到异常指令之前的快照，物理寄存器堆里的值全都还在（没有被覆盖，只是映射关系变了）。配合重排序缓冲（ROB）按程序序提交，异常时硬件能瞬间「回到」异常前的精确状态。<span class="marginnote">这就是重命名与 [[precise-exceptions-speculation-recovery]] 的关系：<strong>没有重命名，乱序执行无法做到精确异常</strong>；有了它，回滚只是一次映射表恢复。</span>

## 5 核心对比表：隐式重命名 vs 显式重命名

> 本节为纯概念主题，以核心对比表替代公式解析。

| 维度 | Tomasulo 隐式重命名 | 显式重命名（现代处理器） |
| --- | --- | --- |
| 映射对象 | 架构寄存器 → 保留站/缓冲区 | 架构寄存器 → 物理寄存器 |
| 值存放处 | 保留站/缓冲区 | 物理寄存器堆 |
| 何时消除 WAR/WAW | 发射时占新保留站 | 发射时分配新物理寄存器 |
| 精确恢复 | 需配合 ROB 回滚 | RAT 回退 + ROB 按序退役 |
| 代表 | IBM 360/91 | Intel Core、ARM Cortex-A 系列 |

**辨析｜易错点：** 重命名**消除的是名相关（WAR/WAW）**，对真相关（RAW）无能为力。看到「重命名可以消除 RAW」的说法，一定是错的——RAW 只能靠转发（forwarding）或等待缓解。

## 6 小结

- **架构寄存器是名字，物理寄存器是容器**；重命名就是名字→容器的动态映射。
- 三件套硬件：**RAT（映射表）**、**物理寄存器堆**、**空闲列表**。
- WAR/WAW 在发射时通过分配新物理寄存器**直接消失**；RAW 依然要等。
- 旧物理寄存器的释放时机要等到「无人再读」，通常随 ROB 退役进行。
- 重命名 + ROB 是**精确异常**的基石：回滚 = 映射表恢复。

在下一节，我们把重命名与动态调度拼进「投机执行」的完整框架——这就是**硬件推测（Speculation）与重排序缓冲区（ROB）**。
