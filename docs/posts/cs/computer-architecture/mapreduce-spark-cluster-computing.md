## 为什么集群框架是 WSC 的「应用程序」

[[warehouse-scale-computer]] 说 WSC 的软件栈像 OS；集群计算框架（MapReduce、Spark）就是跑在这「OS」上的**应用程序形态**——它把「整仓算力」组织成一次分布式计算。本节从**体系结构**的视角看这些框架：它们如何利用数据局部性、如何容错、如何对抗掉队者。<span class="marginnote">[[tail-latency]] 的掉队者问题在这里再次登场：MapReduce 的「推测执行（speculative execution）」就是对抗慢节点的标准手段。</span>

## 1 MapReduce：模型与实现

**核心概念**：**MapReduce**（Google, 2004）把一切分布式计算抽象成三步：

```text
输入分片 1 ──→ Map ──┐
输入分片 2 ──→ Map ──┼──→ Shuffle（按 key 分组，跨网络）──→ Reduce ──→ 输出
输入分片 3 ──→ Map ──┘
```

**Map 节点**：读输入分片，逐条处理。
**Shuffle 阶段**：中间结果按 key 分发（跨网络）。
**Reduce 节点**：聚合每个 key。

**为什么它适合 WSC**：Map 之间**完全独立**（天然并行）、数据**只读一次**（适合磁盘流式）、容错靠**重算**（不保存中间状态）。它是「把问题切成海量独立小任务」的教科书——与 [[ilp-concepts-limits]] 里「任务级并行」完美契合。

## 2 数据局部性：把计算搬向数据

**核心概念**：**数据局部性（data locality）**——**调度器优先把 Map 任务分到「数据所在的服务器」**，让计算在本地读盘，而不是把数据跨网络搬过来。

```text
数据块 A 存放在节点 1 ──→ Map 任务 A 优先调度到节点 1（本地读盘，不搬数据）
数据块 B 存放在节点 2 ──→ Map 任务 B 优先调度到节点 2（本地读盘，不搬数据）
```

**收益**：本地读 vs 网络读相差 **10–100 倍**。MapReduce 的成功一半靠这个「调度靠近数据」的机制——**用调度换带宽，是 WSC 的第一优化**。

## 3 容错与掉队者

**任务失败重算**：某节点挂了，调度器把它的任务**重新调度**到别的节点，从输入重跑——**不保存中间状态，失败即重算**。
**推测执行（speculative execution）**：某任务明显比同批任务慢（**掉队者**，可能是慢盘/坏节点），调度器**并行再跑一份**，用先完成的那个。这正是 [[tail-latency]] 治理里「对冲」思想在批处理中的版本。<span class="marginnote">掉队者的危害在批处理里同样致命：<strong>整个作业等最慢的任务</strong>。推测执行用「少量冗余计算」换「整批不被拖死」——与在线服务的对冲请求是同一哲学。</span>

## 4 从 MapReduce 到 Spark：内存迭代

MapReduce 的痛点是**中间结果落盘**：每轮 Map/Reduce 都要写盘、读盘。**Spark** 用 **RDD（弹性分布式数据集）** 把中间结果**留在内存**：

- **迭代计算快**：机器学习、图算法要反复扫数据，内存版快 10–100 倍。
- **血统（lineage）容错**：不复制中间数据，**记录「怎么算出来的」，坏了就从血统重算**——用「重算代价」换「复制代价」。
- **DAG 调度**：把算子组织成有向无环图，一次调度多阶段。

**核心概念**：MR 用「全量落盘」换「简单容错」，Spark 用「内存 + 血统」换「快」——**同一批硬件，框架的存储策略决定数量级的性能差**。

## 5 核心对比表：MR vs Spark

> 本节为纯概念主题，以核心对比表替代公式解析。

| 维度 | MapReduce | Spark |
| --- | --- | --- |
| 中间结果 | **落盘** | 内存（RDD） |
| 容错 | 重算（无状态） | **血统重算** |
| 迭代/交互 | 慢（每轮落盘） | 快（内存） |
| 调度 | 阶段式 | DAG |
| 适用 | 海量离线批处理 | 迭代/交互/流式 |

## 6 数值算例：数据局部性到底值多少钱

设 1 TB 输入、本地盘读带宽 10 GB/s、网络带宽 1 GB/s：

- **全部本地读**：$10^{12}/10^{10} = 100$ 秒。
- **全部网络搬**：$10^{12}/10^9 = 1000$ 秒——**慢 10 倍**。
- **90% 本地 + 10% 网络**：$0.9 \times 100 + 0.1 \times 1000 = 190$ 秒——比全网络快 5 倍以上。

$$
T = \frac{D \times (1-\text{本地率})}{B_{\text{网络}}} + \frac{D \times \text{本地率}}{B_{\text{本地}}}
$$

**要点**：把本地率从 0 提到 90%，总时间从 1000 秒压到 190 秒——**调度器「把任务派到数据身边」这一个动作，就是约 5 倍的提速**。这也是为什么数据局部性被称作 WSC 的第一优化。

## 7 常见误区再辨析

- **「MapReduce 已死」**：作为编程模型已过时，但**分治 + 数据局部性 + 重算容错**的思想贯穿 Spark、Flink 等一切现代框架。
- **「Shuffle 无所谓」**：Shuffle 是跨网络的全量中间数据搬运，往往是**作业最大的时间开销**——Spark 优化 shuffle（桶聚合、跳过落盘）正是为此。
- **「内存一定比磁盘好」**：内存快但贵且易失；血统重算与持久化之间要做权衡——**不是永远内存最优**。
- **「集群框架只看 CPU 算力」**：数据规模远超算力时，**I/O 与网络**才是瓶颈——调度、压缩、局部性比多几颗核更有效。

## 8 术语速查

| 术语 | 含义 |
| --- | --- |
| MapReduce | Map → Shuffle → Reduce 的分布式计算模型 |
| 数据局部性（data locality） | 把任务调度到数据所在节点 |
| Shuffle | 中间结果按 key 分发（跨网络） |
| 推测执行（speculative execution） | 并行重跑掉队任务，取先完成者 |
| RDD | Spark 的弹性分布式数据集（内存） |
| 血统（lineage） | 记录数据「怎么算出来」以支持重算 |
| DAG 调度 | 把算子组织成有向无环图一次调度 |
| 掉队者（straggler） | 明显慢于同批任务的任务 |
| 分片（split） | 把输入切成的独立数据块 |
| 组合器（combiner） | 在 Map 端先做局部聚合、减少 Shuffle 量 |

## 9 小结

- 集群框架 = WSC 的「应用程序形态」，把整仓算力组织成一次计算。
- **MapReduce** 三步：Map（独立并行）→ Shuffle → Reduce（聚合）。
- **数据局部性**：调度器把任务分到数据所在节点，本地读比网络读快 10–100 倍。
- 容错靠**重算**；掉队者靠**推测执行**（批处理的「对冲」）。
- **Spark** 用内存 RDD + 血统容错，迭代计算快 10–100 倍。
- 框架的存储策略（落盘 vs 内存）决定性能量级——**硬件相同，软件定胜负**。

在下一节，我们把 WSC 与商业模型接轨——**云计算与 WSC 的经济学**。集群框架解决「怎么算」，经济学解决「怎么划算」——两者的交集，正是云计算的商业模式。
