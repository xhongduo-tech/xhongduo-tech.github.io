## 为什么虚拟化把翻译变成「两级」

虚拟机让**多个客户操作系统**跑在**一个宿主机**上，由**虚拟机监视器（Hypervisor）**调度。客户机的内核以为自己在管理物理内存，实际上它管理的是**客户物理地址（guest physical）**，真正的物理地址由 Hypervisor 掌控——于是**一个地址要翻译两遍**：客户虚拟地址 → 客户物理地址 → 宿主物理地址。<span class="marginnote">上一节 [[tlb-optimization-multilevel-paging]] 的翻译是「虚拟→物理」；虚拟化把它变成「虚拟→物理(客户)→物理(宿主)」。两级翻译是虚拟化性能的老大难，也是硬件虚拟化加速的主战场。</span>

## 1 两级翻译的困境

一个访存的完整旅程：

1. 客户虚拟地址 → 客户页表 → 客户物理地址。
2. 客户物理地址 → 宿主页表 → 宿主物理地址。

如果每次访存都真的查两遍页表，性能就完了。关键是**把两级翻译的成果缓存下来**，让翻译大多时候一步到位。

## 2 影子页表：软件翻译的代价

早期（无硬件支持）的做法是**影子页表（shadow page table）**：Hypervisor 维护一张「客户虚拟地址 → 宿主物理地址」的**直接映射表**，把两级翻译**预先合并**成一级。

**好处**：客户机跑的时候只查一张表，翻译路径与原生一样快。
**致命代价**：客户 OS 一旦**修改自己的页表**（创建进程、换页），Hypervisor 必须**陷入（VM exit）**、更新影子表——**每次页表修改都是一次完整虚拟化开销**。页表修改频繁时，性能惨不忍睹。<span class="marginnote">影子页表是「<strong>用软件把复杂藏起来</strong>」的极致：透明，但每个陷阱都贵。它是理解硬件加速价值的参照系。</span>

## 3 嵌套分页：硬件来翻译两级

**核心概念**：**嵌套分页（nested paging）**，AMD 叫 **NPT（Nested Page Tables）**、Intel 叫 **EPT（Extended Page Tables）**：硬件直接**同时维护两张页表**（客户页表 + 宿主页表），访存时硬件自动遍历两级——**客户 OS 改自己的页表时不需要陷入 Hypervisor**，因为它改的就是硬件直接用的那张表。

代价是：TLB 缺失时要**遍历两级页表**（可能 4+4 次内存访问）。于是硬件又加了一招——**嵌套 TLB（nested TLB）**：专门缓存「客户虚拟→宿主物理」的最终结果，让大多数翻译仍然一步到位。

## 4 TLB 的虚拟化：VPID 与少冲刷

虚拟化下 TLB 有个新问题：**切换虚拟机时要不要刷 TLB？** 客户 A 与客户 B 的同一个虚拟地址映射到不同物理页，不刷就串台。但**每次切换都刷 TLB**，切换成本暴涨。

硬件解法是 **VPID/ASID 标签**：TLB 每个条目打上「属于哪个虚拟机/进程」的标记，命中时校验标签——**不同虚拟机共享 TLB 却互不干扰，切换不用刷**。<span class="marginnote">这与多进程共享 TLB 的 ASID 技术同源：<strong>用标签代替「切换即冲刷」</strong>。VM 切换从「全刷 TLB」变成「标个新 VPID」，切换开销大降。</span>

## 5 IOMMU：虚拟化 I/O 的最后一块

内存翻译完了，I/O 呢？客户机直接访问设备时，设备发出的 DMA 地址也要从「客户物理地址」翻译成「宿主物理地址」。**IOMMU**（Intel VT-d / AMD IOMMU）在设备与内存之间架一道地址翻译 + 权限检查：

设备 DMA 地址经 IOMMU 翻译后访问真实内存。
IOMMU 同时提供**设备级隔离**（某个 DMA 只能碰它被允许的页）——安全性与翻译兼得。<span class="marginnote">IOMMU 是「[[spectre-meltdown-side-channel]] 之外」的另一条安全战线：没有它，恶意/出错的 DMA 可以直写任意内存。<strong>云计算里「设备直通」与安全隔离全靠在它身上</strong>。</span>

## 6 核心对比表：影子页表 vs 嵌套分页

> 本节为纯概念主题，以核心对比表替代公式解析。

| 维度 | 影子页表 | 嵌套分页（NPT/EPT） |
| --- | --- | --- |
| 翻译路径 | 一张合并表 | 硬件遍历两级 |
| 客户改页表 | **必须陷入 Hypervisor** | 不需要陷入 |
| 硬件需求 | 无（纯软件） | CPU 支持（AMD-V/Intel VT-x） |
| TLB 缺失代价 | 较低（单级遍历） | 较高（两级遍历） |
| 嵌套 TLB | 无 | 有（缓存最终结果） |
| 现代 Hypervisor | 已基本弃用 | **默认选择** |

## 7 数值算例：两级翻译的 TLB 缺失账

设 TLB 命中率 99%、命中 1 周期；原生缺失惩罚（4 级页表遍历）约 100 周期，虚拟化下要遍历两级页表、缺失惩罚升到约 200 周期：

- **原生访存**：$\text{AMAT} = 1 + 0.01 \times 100 = 2$ 周期。
- **虚拟化访存**：$\text{AMAT} = 1 + 0.01 \times 200 = 3$ 周期——慢 50%。

但真实负载的 TLB 命中率常高达 99.9%：

- **原生**：$1 + 0.001 \times 100 = 1.1$；**虚拟化**：$1 + 0.001 \times 200 = 1.2$——差距缩到约 9%。

**结论**：两级翻译的代价几乎全部押在 **TLB 缺失率**上——命中率越高，虚拟化开销越小。这正是硬件加装**嵌套 TLB**、并用 **VPID 避免切换冲刷**的根本动机：把缺失率压住，虚拟化的成本就接近消失。

## 8 常见误区再辨析

- **「影子页表一定更慢，嵌套分页一定更快」**：只对了一半。嵌套分页省掉「客户改页表→陷入」的开销，却把 TLB 缺失代价变贵；若负载频繁创建进程、页表频繁变更，影子页表反而可能占优。**两者是不同工作负载下的取舍**。
- **「开了 EPT 就一定快」**：虚拟机内大量 TLB 未命中时，两级遍历很贵，必须有嵌套 TLB 兜底。
- **「切换 VM 必须刷 TLB」**：有了 VPID/ASID 标签，命中时校验标签即可，不必全刷。
- **「IOMMU 只是性能问题」**：它首先是**安全边界**——没有它，一个出错或被攻陷的 DMA 设备可以直写宿主机任意内存。

实际云主机的经验是：EPT 下内存虚拟化开销通常被控制在个位数百分比，而影子页表在页表频繁变更的负载上可能高达 20%–30%——这就是现代 Hypervisor 普遍转向嵌套分页的原因。

## 9 虚拟化的整体性能图景

现代硬件虚拟化把「翻译」与「隔离」都搬进了硬件，软件层的虚拟化开销被压到极低。完整拼图是：

- **地址**：EPT/NPT + 嵌套 TLB 完成两级翻译并缓存最终结果。
- **切换**：VPID 标签避免 VM 切换时全刷 TLB。
- **I/O**：IOMMU 翻译 DMA 地址并做设备级隔离。
- **网络/存储**：virtio、SR-IOV 等半虚拟化与直通技术进一步削掉软件开销。

**核心概念**：性能关键不是「某一个加速点」，而是「每一层都不再频繁陷入」——只要 Hypervisor 从访存、切换、I/O 三条路径上退出来，虚拟机的性能就逼近原生。这也是「以大概率事件为快」在虚拟化中的体现：把 99% 的路径做成硬件快路，只让少数真实边界事件慢下来。

## 10 术语速查

| 术语 | 含义 |
| --- | --- |
| 虚拟机监视器（Hypervisor） | 调度多个客户 OS 的软件层 |
| 客户物理地址（guest physical） | 客户 OS 看到的「物理地址」 |
| 影子页表（shadow page table） | 软件把两级翻译合并成一张表 |
| 嵌套分页（nested paging） | 硬件同时遍历客户/宿主两张页表 |
| EPT / NPT | Intel / AMD 的嵌套分页实现 |
| VPID / ASID | 给 TLB 条目打虚拟机/进程的标签 |
| IOMMU | 设备侧地址翻译与隔离（VT-d / AMD-Vi） |
| VM exit | 从客户机陷入 Hypervisor 的事件 |

## 11 小结

- 虚拟化的地址翻译是**两级**：客户虚拟 → 客户物理 → 宿主物理。
- **影子页表**软件合并两级，客户改页表就陷入——开销大。
- **嵌套分页（NPT/EPT）**让硬件遍历两级，客户改页表零陷入；嵌套 TLB 缓存最终结果。
- **VPID/ASID 标签**让 VM 切换不刷 TLB。
- **IOMMU** 给 I/O 也上翻译与隔离，虚拟化与安全兼顾。
- 硬件虚拟化加速的演进主线：**把软件模拟的翻译搬进硬件，同时缓存翻译结果**。

在下一节，我们下潜到内存芯片内部——**主存技术：DRAM 的内部组织（Bank、行缓冲）**。虚拟化解决的是「地址怎么翻译」，DRAM 解决的是「翻译出来的物理地址怎么被高效访问」，两者一上一下，正好补全存储层次的中段。
