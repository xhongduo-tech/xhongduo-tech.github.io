## 为什么压缩是 RISC-V 的必修课

RISC-V 的定长 32 位指令带来解码极简（[[riscv-integer-instruction-set]]），但代码密度成了软肋——同样的程序，ARM 有 16 位的 Thumb、x86 有变长编码，而 RISC-V 每指令 4 字节，**代码体积大、指令 Cache 与取指带宽都吃亏**。嵌入式存储紧张、移动端功耗敏感，代码密度直接折成成本。<span class="marginnote">注意上一节 B/J 型分支立即数「最低位隐藏 0」的伏笔：跳转目标按 2 字节对齐，正是为 16 位压缩指令预留的。压缩与整数基础集在设计之初就是一体。</span>

## 1 四象限布局：一眼认出压缩指令

C 扩展的编码诀窍在**最低两位**：

| 指令低 2 位 | 含义 | 长度 |
| --- | --- | --- |
| `00` | 压缩指令（Quadrant 0） | 16 位 |
| `01` | 压缩指令（Quadrant 1） | 16 位 |
| `10` | 压缩指令（Quadrant 2） | 16 位 |
| `11` | 标准 32 位指令 | 32 位 |

**核心概念**：处理器在**取指阶段**先看最低 2 位：`11` 是标准指令，其余三种都是 16 位压缩指令。压缩指令与标准指令可以**混排**在指令流里，取指宽度按 2 字节粒度对齐（配合指令 Cache 按 16 位边界取指）。<span class="marginnote">四象限划分让「16/32 位混排」在硬件上几乎零开销：取指单元只需要一位多路选择。这是 C 扩展比「单独一种压缩模式」优雅的地方。</span>

## 2 常见压缩指令：用 16 位表达高频操作

16 位只有 16 位，容不下两个 5 位寄存器号 + 操作码，于是压缩指令做了两个取舍：

**寄存器子集**：很多压缩指令只编址 **x8–x15**（3 位编码），部分指令只用 x1（ra）或 x5（t0）。
**合并操作**：把「操作码 + 寄存器 + 小立即数」压进一个字段。

常用压缩指令一览（均能展开成等价的 32 位指令）：

| 压缩指令 | 等价标准指令 | 说明 |
| --- | --- | --- |
| `c.lw` | `lw rd', uimm(rs1')` | rd'、rs1' ∈ x8–x15，5 位立即数 |
| `c.sw` | `sw rs2', uimm(rs1')` | 存储 |
| `c.addi` | `addi rd, rd, imm` | rd'=rs1'，6 位立即数 |
| `c.li` | `addi rd, x0, imm` | 装载立即数 |
| `c.j` | `jal x0, offset` | 无条件跳转 |
| `c.beqz` | `beq rs1', x0, offset` | 与 0 比较的分支 |
| `c.mv` | `add rd, x0, rs2` | 寄存器搬移 |

**辨析｜易错点：** 压缩指令**不是新指令**，而是标准指令的**短编码**——语义完全由展开后的标准指令决定。写汇编时你可以直接用标准指令，编译器会替你挑出能被压缩的那些；想手动控制才写 `c.` 前缀形式。

## 3 展开机制：压缩指令如何「等价」

以 `c.lw` 为例，看它如何展开：

```asm
c.lw  rd', uimm(rs1')      ; 16 位压缩指令：rd'、rs1' ∈ x8–x15
  │ 解码器展开（补全成 32 位标准指令）
  ▼
lw    rd', uimm(rs1')      ; 语义完全相同：把 rs1'+uimm 地址的字读入 rd'
```

**第一步，识别**：低 2 位 `10`、funct3 为 `010` → 是 `c.lw`。
**第二步，解寄存器**：rd'、rs1' 各 3 位，映射到 x8–x15。
**第三步，拼立即数**：6 位立即数 uimm 按 [6][5][4:3][2] 拆散存放，展开时拼回并符号扩展——与 [[riscv-integer-instruction-set]] 里立即数「错位共享」同一思路。

解码器要么**当场展开成标准 uop**（现代乱序核心），要么**直接按语义执行**（简单核心）。代码语义上，压缩指令与标准指令**完全等价**——这是 C 扩展正确性的基石。

## 4 收益与代价的量化

**核心对比表：压缩带来的权衡**

| 维度 | 无 C 扩展 | 启用 C 扩展 |
| --- | --- | --- |
| 指令长度 | 全 32 位 | 16/32 位混排 |
| 代码体积 | 基准 | **约缩小 20–30%** |
| 指令 Cache 命中率 | 基准 | 上升（同样空间装更多代码） |
| 取指带宽 | 基准 | 更省（一次取 8 字节可装多条） |
| 解码复杂度 | 低 | 略增（区分 16/32 位） |
| 分支对齐 | 4 字节 | 2 字节 |

**公式（代码密度收益）**：设程序中可压缩指令占比 $c$、压缩率 $r$（约 50%，16/32），则代码体积因子 $\approx 1 - c \times (1-r)$。若 $c = 0.5$，$r = 0.5$，则体积缩小到 $0.75$——**省约 25%**。<span class="marginnote">省下来的不是纸面数字：指令 Cache 命中率上升、取指带宽压力下降、嵌入式 Flash/存储成本下降——对 IoT 芯片，这 25% 可能就是「够不够塞进一颗 MCU」的分界线。</span>

代价主要是**解码复杂度与对齐处理**。但 RISC-V 的四象限设计把代价压到极低，所以 **RV64GC 等主流配置几乎都默认带 C**。

## 5 数值算例：压缩省下的取指账

设程序 25 万条指令、无压缩时每指令 4 字节、取指一次 16 字节：

- **无 C 扩展**：程序 1 MB，取指 16 B/周期 = 4 条/周期 → 最少 **62,500 取指周期**。
- **启用 C 扩展**：程序约 750 KB、平均每指令 3 字节，取指 16 B ≈ 5.3 条/周期 → **约 47,000 取指周期**。

$$
\text{取指周期} \approx \frac{\text{程序字节数}}{\text{每周期取指字节}}
$$

**要点**：代码缩小 25%，指令 Cache 同容量能装更多、取指带宽每周期喂进更多指令——**对取指带宽紧张与指令 Cache 命中率敏感的负载，这是实打实的提速**。加上嵌入式存储省下的成本，C 扩展的 25% 就非常值钱。

## 6 常见误区再辨析

- **「压缩指令是新指令」**：它是标准指令的**短编码**，语义完全等价于展开后的标准指令——不是新操作。
- **「压缩会破坏对齐」**：四象限 + 2 字节对齐是设计时一体规划的，混排零切换成本——**对齐不是问题**。
- **「C 扩展只为嵌入式」**：代码密度对**指令 Cache、取指带宽**同样重要——高性能核也默认带 C。
- **「16 位装不下什么」**：用「寄存器子集 + 操作合并」表达**最高频**的指令（load/store/分支/移动）——**够用且最常用**。

## 7 术语速查

| 术语 | 含义 |
| --- | --- |
| C 扩展 | RISC-V 的 16 位压缩指令扩展 |
| 四象限 | 低 2 位区分 16/32 位指令 |
| 寄存器子集 | 只编址 x8–x15（3 位） |
| 操作合并 | 操作码+寄存器+小立即数合一 |
| 展开 | 压缩指令补全成标准指令 |
| 代码密度 | 同一程序占多少字节 |

## 8 小结

- **C 扩展**用 16 位指令表达高频操作，目标是**代码密度**。
- 四象限布局：低 2 位 `11` = 32 位，`00`/`01`/`10` = 16 位；混排零切换成本。
- 压缩靠两招：**寄存器子集**（x8–x15）+ **操作合并**（`c.addi`、`c.lw`…）。
- 压缩指令**语义等价**于展开的标准指令；解码器当场展开或直读。
- 典型收益 **20–30% 代码缩小**，代价是解码与对齐略增；主流配置默认启用。
- 代码密度是 [[isa-quantitative-evaluation]] 里「指令集量化评估」的核心指标之一。

在下一节，我们转向另一类数据并行指令——**向量指令体系结构：向量长度无关编程模型**。C 扩展优化的是「指令多短」，向量指令优化的是「一条指令管多少数据」——一个省体积、一个省条数，是 RISC-V 灵活性的两个侧面。
