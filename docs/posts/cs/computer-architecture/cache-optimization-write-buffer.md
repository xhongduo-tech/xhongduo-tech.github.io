# 高级 Cache 优化（七）：合并写缓冲区与流水化访问

## 为什么写比读更麻烦

读缺失可以靠预取、关键字优先隐藏；**写**却有一个读没有的问题：写不仅要更新 Cache，最终还要**把数据写到下一层**（写直达）或在**换出时写回**（写回）。每一次写向内存传播都要占用带宽、都可能让处理器**停顿**。更麻烦的是，现代处理器每周期要完成多条写——**Cache 的写端口根本不够用**。<span class="marginnote">写路径与读路径在 [[memory-hierarchy-amat]] 里是对称的，但工程上写更难：<strong>写多了要合并、要缓冲、要转发</strong>。本节全是「写侧」的补丁，也是存储控制器（[[memory-controller-scheduling]]）处理的起点。</span>

## 1 写缓冲：让写不阻塞

**核心概念**：**写缓冲（write buffer）**：位于 Cache 与下一层之间的一小队缓冲寄存器，把要写出的数据**暂存**，让处理器不用等下一次写实际完成。

写直达 Cache：每次写都要下发内存，写缓冲把「写内存」变成「写缓冲」，快得多。
写回 Cache：换出脏块时，先把块送进写缓冲，Cache 立即可用。

**写缓冲满时处理器停顿**——所以写缓冲要有足够的吞吐，并配合**合并**减少占用。

## 2 写合并：一次事务带走多笔写

**核心概念**：**写合并（write merging）**：写缓冲在等待下发时，检查**相邻地址的写**是否落在同一块/同一地址——若是，就**把它们合并成一条**，只发一次内存事务。

经典场景：程序连续写同一块的几个字——

```c
// 连续写同一 16 字节块的 4 个字
block.word0 = a;
block.word1 = b;
block.word2 = c;
block.word3 = d;
// 写缓冲把相邻的 4 条写合并为一条 16 字节事务
```

四条写合并成一条 16 字节的写——**带宽省 4 倍，内存事务数省 4 倍**。合并的前提是写缓冲能**逐字节标记**哪些字节有效（byte-enables），只发送真正写过的部分。<span class="marginnote">对「逐字段更新一个结构体」的代码，写合并能把成百次小写并成几次整块写——<strong>这是写侧性能的隐形大头</strong>。</span>

## 3 Store-to-Load 转发：写缓冲的贴心功能

写缓冲还兼职一个关键功能：**store-to-load forwarding（写后读转发）**。处理器刚写了某个地址、又立刻读它时，读不必等写真正下发——**直接从写缓冲里拿到新值**。

这对 [[data-name-control-dependencies]] 里的 RAW 依赖至关重要：没有转发，`SW`（存储字）后紧跟的 `LW`（装载字）要么等写完成、要么读到旧值。写缓冲让「刚写的立即可读」，且顺序正确。

**辨析｜易错点：** 写合并与 store-to-load 转发**不是一回事**。合并是「把多个写攒成一条下发」（优化带宽）；转发是「读直接拿写缓冲里的值」（优化延迟）。前者管下行，后者管上行。

## 4 流水化（分体）访问：一周期多个访存

现代乱序处理器**每周期要完成多次 Cache 访问**（发射宽度个 Load/Store）。单块 SRAM 阵列一周期只能服务一次访问——不够用。解法是**分体（banking）**：把 Cache 阵列拆成多个独立 bank，像内存条分 bank 一样，**不同 bank 的访问可并行**。

```text
Cache 阵列拆成多个独立 bank：

┌─────────┬─────────┬─────────┬─────────┐
│ Bank 0  │ Bank 1  │ Bank 2  │ Bank 3  │
└─────────┴─────────┴─────────┴─────────┘

访问 A 落 Bank 0、访问 B 落 Bank 2 → 同周期并行
访问 A 与访问 C 同落 Bank 0       → 排队（bank 冲突）
```

**核心概念**：**流水化/分体访问**让 Cache 在**一个周期内服务多个访问**，只要它们落在不同 bank。这既提吞吐，也让 Cache 能跟上超标量发射宽度。冲突（同周期访问同一 bank）仍要排队——**bank 的划分与冲突率是访存设计的关键权衡**，与 [[dram-internal-organization]] 的 bank/行缓冲是同构思想。

## 5 核心对比表

> 本节为纯概念主题，以核心对比表替代公式解析。

| 机制 | 解决的问题 | 手段 | 收益 |
| --- | --- | --- | --- |
| 写缓冲 | 写阻塞处理器 | 暂存写、后台下发 | 写不再停顿 |
| 写合并 | 带宽与事务数 | 同块写拼成一条 | 带宽省数倍 |
| Store-to-Load 转发 | 写后读 RAW | 从写缓冲直接取 | 消除写读等待 |
| 分体访问 | 每周期多次访存 | Cache 拆 bank | 吞吐按 bank 数提升 |

## 6 数值算例：写合并省下的带宽

设写缓冲每次下发都有固定事务开销，数据带宽按「有用字节」算：

- **不合并**：连续写 16 字节块的 4 个字 → 4 次事务，每次只带 4 字节——**有效带宽利用率低**。
- **合并**：4 条写拼成 1 条 16 字节事务——**事务数省 4 倍，带宽利用翻数倍**。

$$
\text{事务数}:\quad \text{不合并} = 4,\qquad \text{合并} = 1
$$

**要点**：写合并的本质是**把「多次小写」变成「一次大块写」**——对「逐字段更新结构体」「凑整块再刷」的代码，这是写侧性能的隐形大头。现代处理器靠写缓冲的**字节有效标记（byte-enables）**精确合并，只发真正写过的部分。

## 7 常见误区再辨析

- **「写缓冲就是缓存」**：写缓冲只**暂存待下发**的写，不提供读命中——它是「排队」，不是「存储」。
- **「写合并是软件做的」**：硬件写缓冲自动合并相邻写；程序员只需保证**连续写同一块**（布局相邻），硬件自会合并。
- **「Store-to-Load 转发会出错」**：转发必须保证顺序语义正确——硬件按程序序检查「读的是否是最近写」；乱序推测下靠 ROB 兜底。
- **「分体越多越好」**：bank 越多冲突越少，但面积与端口成本上升——**与 DRAM 的 bank 一样是权衡**。

## 8 术语速查

| 术语 | 含义 |
| --- | --- |
| 写缓冲 | 暂存待下发写的小缓冲 |
| 写合并 | 相邻小写拼成一条大事务 |
| byte-enables | 逐字节有效标记 |
| Store-to-Load 转发 | 读直接取写缓冲里的新值 |
| 分体（banking） | Cache 拆成多个独立 bank |
| bank 冲突 | 同周期访问同一 bank 排队 |
| 写直达 / 写回 | 写是否立即下发内存 |

## 9 小结

- **写缓冲**把写变成「暂存 + 后台下发」，处理器不阻塞。
- **写合并**把同块的小写拼成一条事务，省带宽。
- **Store-to-Load 转发**让刚写的值立即可读，处理写后读 RAW。
- **分体（banked）访问**让 Cache 一周期服务多个访问，跟上超标量宽度。
- 写侧优化的主线：**少发事务（合并）、少等待（缓冲/转发）、多并行（分体）**。
