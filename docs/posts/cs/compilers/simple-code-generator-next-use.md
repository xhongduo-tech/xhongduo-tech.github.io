## 为什么从简单代码生成器开始

完整的代码生成器复杂得吓人，但龙书给了一台「小而全」的**简单代码生成器**：假设目标机有无限可用的寄存器，逐个处理三地址指令，用「**下次引用信息（next-use information）**」判断一个寄存器何时可以释放。它麻雀虽小，五脏俱全——指令选择、寄存器管理、内存溢出，全在这台小机器的骨架里。<span class="marginnote">这台简单生成器是「从零写后端」的最佳教材：它展示了代码生成的核心循环——对每条 IR，找寄存器、生成指令、更新描述；也展示了「活跃值占寄存器、死值让位」的朴素原则。理解它，就能读懂真实后端（LLVM/GCC）的寄存器分配在解决什么更深的问题。</span>

## 1 下次引用信息：判断死活的依据

对每条三地址指令，为每个操作数计算两个属性：

**下次引用（next-use）**：指令 `x = y op z`（编号 i）之后，`y`、`z` **下一次被引用**的指令编号；若之后不再被引用，为「无」（∞）。
含义：`y`、`z` 的结果若「之后还会用」，它们占用的寄存器不能释放；若「之后不再用」（死），寄存器可让位。

**活跃性**：指令 `x = y op z` 执行后，若 `x` 在之后还会被用，`x` 是**活跃（live）**的，需保存其值；否则是死的，不必保存——省掉一次存储指令。

**计算方向**：从基本块**末尾往前扫**——后面的引用信息先知道，才能算前面的。对指令 `x = y op z`：

先记录 `y`、`z` 的当前「下次引用」。
然后**更新**：`y`、`z` 的下次引用 = 本指令；`x` 的下次引用 = 未定义（x 在此被定值，之前的下次引用作废）。<span class="marginnote">「倒着扫」是这类分析的通用方向：一个变量的「下次使用」取决于它之后的代码，所以从后往前传播。这正是第八篇活跃变量分析的雏形——那是在流图上做同样的「从出口往入口」传播。</span>

## 2 寄存器描述与地址描述

简单生成器维护两套「知识」：

**寄存器描述（register descriptor）**：每个寄存器当前装着哪些变量的值（一个寄存器可同时装多个值，若它们当前相等）。
**地址描述（address descriptor）**：每个变量当前的值存放在哪里——寄存器？内存？还是两者都有。

这两套描述让生成器能回答：翻译 `x = y op z` 时，y、z 在哪（寄存器直接取，还是要 LOAD）、结果放哪、溢出时该存哪个值。<span class="marginnote">「两套描述」是代码生成的记账系统：寄存器侧记「谁在寄存器」，变量侧记「值在哪」。它们保持同步更新——生成的每步都改描述。真实后端的「value tracking」就是这两套描述的超集。</span>

## 3 代码生成算法：getReg 与主循环

生成一条 `x = y op z` 的步骤：

1. **取寄存器**：为 x 调 `getReg`——若 y 的寄存器不再需要（y 死），复用；否则若 z 的可用，用之；否则分配空闲寄存器；都没有则**溢出**一个（把某个死值存回内存）。
2. **保证操作数可用**：y、z 若不在寄存器，LOAD 进寄存器。
3. **生成指令**：`ADD/OP x, y, z`；更新两个描述。
4. **处理死值**：y（或 z）若死，其寄存器标「空闲」；x 若活，登记 x 在目标寄存器。

getReg 的逻辑是「复用死寄存器 > 用空闲寄存器 > 溢出」的优先级链——朴素但有效。<span class="marginnote">getReg 的优先级里藏着寄存器分配的哲学：死值让位最便宜（不产生任何额外指令），空闲次之，溢出最贵（要多生成存储/加载）。真实寄存器分配（图着色）就是这套逻辑的全局化——从「块内看」升级到「跨块看活跃区间」。</span>

## 4 公式解析：getNextUse 的计算

对基本块，倒序扫描每条指令 `x = y op z`：

$$\text{next\_use}(y) = \text{之前记录的 } y \text{ 的下次引用}, \qquad \text{随后更新: } \text{next\_use}(y) = i,\ \text{next\_use}(z) = i,\ \text{next\_use}(x) = \text{无}$$

- **第一步，读取**：本指令用 y、z——它们在**之前**（块内更靠后的指令）的下次引用，就是本指令需要的「下次引用信息」。
- **第二步，更新**：执行本指令后，y、z 在本指令被「消费」了一次，所以它们的下次引用变成本指令；x 被定值，它之前的引用信息作废。
- **第三步，活/死判定**：若 `x` 的下次引用为无，则 x 的定值是死的——生成代码时不必保存 x 的值。

**「倒扫 + 先读后更新」让每次引用的信息恰好反映「之后的真实使用」**——这条计算是活跃变量分析的局部特例。

## 5 一个完整的生成示例

对基本块：

```text
t = a + b
u = t + c
v = u + d
```

倒扫得：`t` 在 `u = t + c` 后不再用（死）；`u` 在 `v = u + d` 后死；`a`、`b`、`c`、`d` 的引用信息逐层传递。生成时：

- `t = a + b`：a、b 从内存 LOAD 到 r1、r2，ADD 得 r1，t 在 r1。
- `u = t + c`：t 在 r1 直接用（t 用过这次就死，r1 可继续用）；c LOAD 到 r2，ADD r1 ← r1 + r2，u 在 r1。
- `v = u + d`：类似，最终 v 在 r1，若 v 活则 STORE。

全程只用 **2 个寄存器**——因为「死值及时让位」，每个中间值用完即放。这就是下次引用信息带来的收益：**寄存器压力最小化**。<span class="marginnote">注意这个示例「2 个寄存器跑完整个块」的巧合不是运气：倒扫保证每个临时值在最后一次使用后立即释放，所以寄存器需求被压到「同时活跃值的最大个数」。这正是「下次引用信息 = 活跃性的局部视图」的直接红利。</span>

## 6 溢出与「寄存器不够」的边界

简单生成器能无压力运行的前提是「寄存器够用」。当同时活跃值超过寄存器数时，必须**溢出**：把一个活值存回内存、腾出寄存器。看这个场景——只有 2 个寄存器 r1、r2，需要翻译 `t = a + b; u = t + c;` 且 t、u 都活跃：

- `t = a + b`：LOAD a→r1、LOAD b→r2、ADD r1←r1+r2。t 在 r1，活跃。
- `u = t + c`：t 在 r1 可用；c 需要 r2——r2 现在装着 b 的残留值（b 已死），直接用 r2 LOAD c。ADD r1←r1+r2，u 在 r1——2 个寄存器够用。
- 若第 3 条 `v = u + d` 也要同时活 3 个值：r1、r2 不够 → 必须把 u（或 t）先 STORE 到内存，腾出 r1 给 v——**溢出**。<span class="marginnote">「溢出的选择 = 挑最不划算占寄存器的值」：通常选「活跃区间最短」或「使用频率最低」的——让它住内存，把寄存器让给更活跃的值。这个「牺牲谁」的判断，就是真实寄存器分配（图着色）里「溢出候选」的核心逻辑——简单生成器用朴素启发式，全局分配器用精确代价。</span>

**要点**：溢出的时机 = 「需要寄存器但全在忙」；溢出的选择 = 「挑最不划算占寄存器的值」（活跃区间最短、使用频率最低）。这台简单生成器「块内看」的溢出是局部的，真实分配器的溢出是全局的（跨块看活跃区间）。

**辨析｜易错点：** 别把「溢出」当「错误处理」——它是寄存器稀缺的正常响应，任何真实编译器都在做。区别只在「溢出谁」的质量：溢出得聪明，代码就紧凑；溢出得笨，就多出访存指令。

## 7 思考与练习

**练习 1 倒扫 next-use**：对基本块 `t = a + b; u = t + c; v = u + d;`，倒扫计算每个变量的「下次引用」，标出在每条指令处谁活谁死。

**练习 2 getReg 决策**：在练习 1 的翻译中，逐步执行「getReg：复用死寄存器 > 空闲 > 溢出」，验证「死值及时让位」让寄存器压力降到最低。

**练习 3 两套描述**：翻译 `t = a + b` 时，维护「寄存器描述」与「地址描述」的每一步更新——标出「y 在寄存器吗」「x 该放哪」的查询。

**练习 4 溢出演示**：若只有 2 个寄存器，翻译需要 3 个同时活跃值的表达式——标出溢出点与插入的 LOAD/STORE，数一数多花的指令。<span class="marginnote">「溢出是寄存器的税」：寄存器不够时把某个活值存回内存、用前再加载——每条溢出插两条访存指令。练习 4 让你亲眼看到「寄存器稀缺的代价」——这也是为什么「死值及时释放」能省钱：它减少了同时活跃值，减少了溢出。</span>

**练习 5 活跃区间**：把练习 1 的「下次引用信息」扩展成每个变量的「活跃区间」（定值到最后一次使用的跨度）——为第七篇「寄存器分配 = 区间不重叠可共享」做铺垫。

**练习 6 局限性**：说明这个简单生成器「块内看」的局限——跨块的值它怎么处理？（预告：全局活跃变量分析 + 图着色）

**常见误区**：

- **误区一**：以为「next-use 是运行时信息」——它是编译期倒扫算出的静态信息。
- **误区二**：忘记「先读后更新」——倒扫时先取 y、z 的原下次引用，再更新为本指令。
- **误区三**：忽视「活跃才保存」——x 若在定值后不活跃，不必 STORE，省一条指令。

**延伸**：简单生成器的「活跃值占寄存器、死值让位」与第八篇「活跃变量分析」、第七篇「图着色」是三级递进——把「下次引用 → 活跃区间 → 冲突图」的演化写成一页，总结「寄存器管理的三层」。

## 8 小结

- **简单代码生成器**假设无限寄存器、逐条翻译 IR，靠两套描述（寄存器/地址）记账。
- **下次引用信息**倒扫基本块算出：每个操作数之后是否还会用、何时用——决定寄存器能否让位。
- **getReg 优先级**：复用死寄存器 > 空闲寄存器 > 溢出；死值让位最便宜。
- 活跃值占寄存器、死值及时释放——寄存器压力被压到「同时活跃值的最大个数」。
- 这台小机器是真实寄存器分配（图着色、活跃区间）的启蒙：理解它，就理解了后端的核心张力。
