## 为什么从编译器的结构开始

学「从极限到大模型」的人迟早会撞上一个朴素的困惑：我写下的 `position = initial + rate * 60`，到底是怎么变成 CPU 里那串 0 和 1 的？答案的载体，就是**编译器（compiler）**。它是计算机科学里少有的「一座小型的完整世界」：一个编译器同时用到形式语言理论、自动机、文法、图论、数据流分析，又要处理符号表、中间表示、寄存器分配这些纯工程问题。<span class="marginnote">龙书把编译器称为「理论如何落进实践」的最佳标本：正则表达式与有限自动机在这里变成真正的词法分析器，上下文无关文法在这里变成真正的语法分析器。</span>

这门课（第三级《编译原理》）的第一篇，不急着写代码，而是先把「编译器长什么样」的总图画出来。理解了分析与综合的两阶段骨架，后面每一章——词法、语法、语义、中间代码、优化、代码生成——都只是往这张图里填血肉。今天这一篇，就是给整个专题打地基。

## 1 编译器是什么：一门语言的翻译官

**编译器（compiler）**：把某种**源语言（source language）**写成的程序，整体翻译成等价的、用另一种**目标语言（target language）**写成的程序。源语言通常是比较高级的语言（C、Python），目标语言通常是更接近机器的语言（汇编、机器码），但也可以是另一种高级语言（比如把 TypeScript 编译成 JavaScript）。

「等价」两个字是关键：翻译前后，程序所表达的**语义（semantics）**必须保持不变。于是我们可以把编译器抽象成一个映射：

$$
\mathrm{Compiler}: L_{\mathrm{src}} \longrightarrow L_{\mathrm{tgt}}, \qquad \mathrm{sem}(c(p)) = \mathrm{sem}(p)
$$

意思是：对任意源程序 $p$，编译结果 $c(p)$ 与 $p$ 具有相同的语义。这个等式虽然抽象，却抓住了编译器的全部道德底线——**不许在翻译中改变程序的本意**。<span class="marginnote">「语义保持不变」是理想化的说法：实际编译器可能优化掉冗余计算、改变求值顺序，但只要可观察行为一致，就算「等价」。编译器正确性验证至今仍是研究前沿。</span>

## 2 两阶段模型：分析与综合

**编译器由「分析」与「综合」两大阶段构成**——这是龙书第 1 章给出的第一张骨架图。

**分析（analysis）**，又称**前端（front end）**：在不改变程序含义的前提下读懂源程序——把源程序分解成组成元素，加上语法结构，再翻译成一种**中间表示（intermediate representation，IR）**。
**综合（synthesis）**，又称**后端（back end）**：根据中间表示构造出目标程序——对 IR 做优化，再把它翻译成目标机器代码。

**前端关心「这程序是什么意思」，后端关心「这机器怎么执行」。** 这一刀切得极漂亮：前端只依赖语言、不依赖机器；后端只依赖机器、不依赖语言。于是：

同一门语言要移植到新机器，只需换一个后端；
同一台机器要支持多门语言，只需挂多个前端。

这正是现代 LLVM 架构的精神祖先：Clang（C 家族前端）、rustc（Rust 前端）共用同一套优化器与后端，见本专题第十一篇《LLVM 架构》。<span class="marginnote">「前端可换、后端可换」的模块化思想，与软件工程里的关注点分离（separation of concerns）一脉相承。龙书把分析与综合的边界画在「中间表示」上——中间表示就是前后端之间的契约（interface）。</span>

## 3 分析（前端）：从字符流到中间表示

龙书用一个贯穿全书的经典例子带我们走一遍。下面这条赋值语句，就是我们要编译的源程序：

```c
position = initial + rate * 60
```

### 词法分析

**词法分析（lexical analysis）**：读入源程序的字符流，把它们分组为有意义的词素序列——**记号（token）**。<span class="marginnote">「60」和「rate」在字符层面都是字母数字串，但词法分析要能区分：60 是数字常量，rate 是标识符。词法阶段只关心「怎么分组」，不关心「这样分组合不合法」——后者是语法分析的职责。这个边界是初学编译原理最容易含糊的地方，第二篇会用整章厘清。</span>

对上面的语句，词法分析输出记号流：

```
<id,1> = <id,2> + <id,3> * <num,60>
```

其中 <id,1>` 代表标识符 `position`，<+>` 代表运算符 `+`，<num,60>` 代表数字常量 60。

### 语法分析

**语法分析（syntax analysis / parsing）**：根据语言的语法规则（文法），把记号流组织成**语法树（syntax tree）**。语法树揭示了记号之间的层次关系——`rate * 60` 是乘法的结果，再与 `initial` 相加，最后赋给 `position`。这一步对应第三篇《语法分析》的全部内容：上下文无关文法、递归下降、LR 分析等。

### 语义分析

**语义分析（semantic analysis）**：检查程序的**静态语义**是否正确——变量是否已声明、类型是否匹配、运算是否合法。它借助**符号表（symbol table）**记录每个标识符的类型与属性。<span class="marginnote">语句 `position = initial + rate * 60` 里，如果 `rate` 是浮点数而 `60` 是整数，语义分析会判定需要一个类型转换，并在语法树上插入显式的转换结点。类型检查是第四、五篇的核心话题，也对应第三级《程序设计语言》里「静态类型检查 vs 动态类型检查」的讨论。</span>

### 中间代码生成

**中间代码生成（intermediate code generation）**：把带语义标注的语法树翻译成**中间表示**。最常见的中间表示之一是**三地址码（three-address code）**——每条指令至多含一个运算符和三个地址：

```
t1 = rate * 60
t2 = initial + t1
position = t2
```

三地址码像汇编，又不绑定任何具体机器——这就是它作为前后端契约的原因。到这一步，前端的工作结束。

## 4 综合（后端）：从中间表示到目标代码

### 代码优化

**代码优化（code optimization）**：在不改变程序语义的前提下，让 IR 变得更「好」——通常指更快、更省空间。优化器会发现上面的三地址码里，`intToReal 60` 是常量转换，可以预先算好；于是第一步消失，代码变成：

```
t1 = rate * 60.0
t2 = initial + t1
position = t2
```

**优化是一门关于「等价变换」的科学**：数据流分析、公共子表达式消除、循环优化……这些构成了本专题第八篇的全部篇幅。今天的重点只在于：优化发生在后端，它作用的对象是中间表示，而不是源程序，也不是最终机器码。<span class="marginnote">「机器无关优化」作用于 IR，因而天然可移植；「机器相关优化」发生在代码生成阶段，依赖具体指令集。这个分工在第八篇与第七篇里分别展开。</span>

### 代码生成

**代码生成（code generation）**：把优化后的 IR 翻译成目标机器的指令序列，并做**寄存器分配（register allocation）**——决定哪些中间值留在寄存器、哪些压进内存。最终产出一份可以交给汇编器的目标代码。代码生成是第七篇的主题。

## 5 编译器与解释器：两种执行模型

读完前后端，不妨退一步：**编译并不是程序执行的唯一方式**。

**编译器**：先把整个源程序翻译成目标代码，翻译完之后，执行的是目标代码本身——「先全部翻译，再执行」。
**解释器（interpreter）**：不事先整体翻译，而是直接一条一条地取源程序（或其某种中间形式）来分析并执行——「边翻译边执行」。

两者各有代价与收益：编译启动慢（要经历整个流水线），但翻译只做一次、执行快；解释启动快、跨平台方便（只要目标平台有解释器），但每条语句都要反复分析、执行慢。

**辨析｜易错点：** 解释器也要做「词法、语法、语义」这套分析工作，并不是把分析省略了。区别不在「做不做分析」，而在「分析完之后，是把结果一次性固化成目标代码（编译），还是立即执行分析结果（解释）」。<span class="marginnote">现代语言几乎都是混合模型：Java 先把源码编译成字节码（bytecode，一种面向 JVM 的中间表示），JVM 再解释或 JIT（即时编译）执行字节码。Python 也先编译成 .pyc 字节码再解释。本专题第十篇《JIT 编译》会专门展开。</span>混合实现的内在权衡，正是第三级《程序设计语言》第一篇第 4 条「语言的实现方法：编译、解释与混合实现」的完整话题。

## 6 语言处理流水线：预处理器、汇编器与链接器

编译器不是孤军奋战的。在一个典型的 C 工具链里，从源码到可执行程序要经过一条更长的流水线（见上方示意图的下排）：

**预处理器（preprocessor）**：在编译器之前工作，负责展开宏（`#define`）、包含头文件（`#include`）、条件编译（`#ifdef`）等纯文本层面的变换，输出「纯化后」的源程序。
**编译器**：把纯化后的源程序编译成汇编语言程序（我们前五节讲的流水线，正是这一步内部的结构）。
**汇编器（assembler）**：把汇编程序翻译成**可重定位机器代码（relocatable machine code）**——代码里引用外部函数的地址还是「空的」，等着被填。
**链接器（linker）**：把多个可重定位目标文件与库合并，解析彼此之间的引用，最终产出可执行文件。
（可选）**加载器（loader）**：把可执行文件装载进内存并启动。

**辨析｜易错点：** 汇编器与编译器都要「把一种语言翻译成机器码」，但汇编器的输入是汇编语言——每条汇编指令几乎一一对应一条机器指令，翻译几乎是机械查表；编译器的输入是高层次语言，一条语句要翻译成很多条机器指令，还要做优化。把「编译」与「汇编」混为一谈，是初学者最常见的口误。机器码如何被 CPU 真正执行，则是第三级《计算机组成原理》的主题。

## 7 核心流程表：一条语句的完整旅程

前几节分别讲了前端与后端，这里把整条管线汇总成一张表，作为本节的「公式解析」——对无公式的主题，一张核心流程表就是最有力的索引。以 `position = initial + rate * 60` 为例：

| 阶段 | 所属 | 输入 | 输出 | 一句话作用 |
| --- | --- | --- | --- | --- |
| 词法分析 | 前端 | 字符流 `position = initial + rate * 60` | 记号流 `id = id + id * num` | 把字符分组为记号 |
| 语法分析 | 前端 | 记号流 | 语法树 | 按文法组织记号的层次结构 |
| 语义分析 | 前端 | 语法树 | 带类型标注的语法树 | 检查静态语义、维护符号表 |
| 中间代码生成 | 前端 | 标注后语法树 | 三地址码等中间表示 | 生成与机器无关的 IR |
| 优化 | 后端 | 中间表示 | 优化后的中间表示 | 等价变换，使代码更好 |
| 代码生成 | 后端 | 优化后 IR | 目标代码（汇编/机器码） | 翻译成目标机器指令并分配寄存器 |

读这张表，请把注意力放在「**输入→输出**」的层层传递上：每一阶段的输出恰好是下一阶段的输入，像一条装配线。这条装配线的第一个产品（词法分析）是字符流的整理，最后一个产品（代码生成）是可交给汇编器的目标代码。<span class="marginnote">表中「前端」与「后端」的分界线画在中间表示处——这正是第 2 节那张骨架图的具体化。记住这条线，后面学 LLVM 时你会再次见到它：LLVM IR 就是现代编译器重新画出的这条分界线。</span>

## 8 小结

- **编译器**把源语言程序翻译成语义等价的目标语言程序，抽象成一个映射 $\mathrm{Compiler}: L_{\mathrm{src}} \to L_{\mathrm{tgt}}$。
- 编译器分**分析（前端）**与**综合（后端）**两阶段：前端读懂程序并生成中间表示，后端基于中间表示构造目标代码。
- 前端含**词法、语法、语义、中间代码生成**四步；后端含**优化、代码生成**两步。
- **编译器**先整体翻译再执行，**解释器**边翻译边执行；现代语言多用编译到字节码再解释 / JIT 的混合模型。
- 在完整工具链中，编译器只是**预处理器 → 编译器 → 汇编器 → 链接器**流水线的一环。

在下一节，我们将来到这条流水线的第一步：**词法分析**——如何把源程序的字符流，切成有意义的记号流。
