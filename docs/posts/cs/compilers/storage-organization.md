## 为什么从存储组织开始

中间代码生成完，程序还只是「意图」。真正运行时，每个变量、每次调用都需要**真实的内存**。存储组织（storage organization）回答：程序运行时的内存如何划分、谁负责哪块、变量分配在哪。它是运行时环境的「地基」，也是理解活动记录、堆管理、垃圾回收的起点。<span class="marginnote">「存储」这个词提醒我们编译器的双重身份：它既是语言翻译器，也是资源规划师——把源语言的抽象名字（变量、数组、对象）翻译成真实内存的地址与区域。运行时的崩溃（段错误、栈溢出、OOM）几乎都能追溯到存储组织的某个约定被破坏。</span>

## 1 运行时内存的四大区域

一次运行的程序，其内存（进程地址空间）被划分成几块功能区域：

**代码区（code）**：存放编译后的机器指令。通常只读、固定大小，由加载器装入。
**静态数据区（static data）**：存放全局变量、静态变量、常量与编译器生成的表。**编译期就知道大小**，地址固定。
**栈区（stack）**：存放活动记录——每次过程调用的局部数据。**后进先出**，随调用增长、随返回收缩。
**堆区（heap）**：存放动态分配的数据（`malloc`、`new` 的对象）。**生存期不固定**，显式或由垃圾回收器管理。

「代码 + 静态 + 栈 + 堆」四区的划分，是绝大多数语言运行时的事实标准。<span class="marginnote">栈与堆相向生长是经典布局：栈从高地址向下长，堆从低地址向上长，两者在中间相遇时内存耗尽。这个「相遇」决定了可用的动态内存总量——理解它，就理解了为什么递归太深会栈溢出、分配太多会 OOM。</span>

## 2 静态分配：编译期决定的地址

**静态分配（static allocation）** 在**编译期**决定变量的地址：全局变量、静态局部变量的位置在编译时就能算出并固定下来。

优点：**零运行期开销**——没有分配/释放动作，地址是常量。
局限：大小必须在编译期已知；不支持递归（每次调用的局部变量不能共享同一块存储）；不支持动态数据结构。

C 语言的 `static` 变量、全局变量都用静态分配；Fortran 早期版本整门语言全静态分配——简单，但限制了递归。<span class="marginnote">「静态分配不支持递归」是理解栈式分配动机的最短路径：递归时同一函数的多层调用需要<strong>各自的</strong>局部变量空间，而静态分配只有一块，无法区分层次。于是「调用一次、开辟一层」的栈式分配应运而生。</span>

## 3 栈式分配与堆式分配

**栈式分配（stack allocation）**：每次过程调用，在栈顶压入一个**活动记录（activation record）**；返回时弹出。局部变量的地址 = 栈指针 + 编译期已知的偏移。

完美适配**递归**与**嵌套调用**：调用深度即栈深度。
分配/释放只需移动栈指针——**O(1)**。
局限：**不可向外返回**——被调函数创建的数据，一旦返回就失效。

**堆式分配（heap allocation）**：数据生存期不服从「后进先出」时（对象被返回给调用者、被多个结构共享），必须用堆：

分配/释放的**时间与顺序由程序控制**。
谁来释放？显式（C 的 `free`、C++ 的 `delete`）或自动（垃圾回收，第九篇）。

**辨析｜易错点：** 栈与堆不是「语言类型」的固有属性，而是「生存期」的服务商——局部变量通常栈式，但 C 里 `malloc` 的局部指针指向堆数据；Java 的对象全在堆，引用在栈。判断标准只有一个：**数据会不会活过创建它的那个过程调用**。<span class="marginnote">「活过调用就得进堆」是一条通用判据：返回给调用者的数据、存进全局结构的数据、被闭包捕获的变量——它们在调用结束后仍被引用，只能放堆。Rust 的所有权系统，本质上是在编译期把「该进堆的」显式标注出来（`Box<T>`、`Vec<T>` 等），把栈堆决策做成类型的一部分。</span>

## 4 公式解析：栈与堆的地址组织

设地址空间从 $0$ 到 `$2`^{n}-1$，经典布局为：

$$\text{栈指针 } sp \text{ 从高端 } 2^n-1 \text{ 向下增长},\qquad \text{堆指针 } hp \text{ 从低端 } 0 \text{ 向上增长}$$

$$\text{可用动态内存} = (sp - hp) \text{ 的剩余空间},\qquad sp < hp \text{ 时内存耗尽}$$

- **第一步，相向布局**：栈向下、堆向上，共享同一块「自由区」——动态内存总量是两者的可伸缩空间，而非固定分割。
- **第二步，栈的分配式**：调用 = `push`（压入活动记录）；返回 = `pop`（弹出活动记录）。无需搜索空闲块，O(1)。
- **第三步，堆的分配式**：堆需要空闲块管理（首次适配、最佳适配等），分配是**搜索**而非指针加减——这是堆管理（后两节）的核心成本。

**这个「栈向下、堆向上」的布局解释了栈溢出与堆耗尽**：无限递归让 `sp` 无限下降，疯狂 `malloc` 让 `hp` 无限上升，终在中间相撞。

## 5 存储组织与语言设计

存储组织不是中立的工程细节，它塑造语言能力：

| 组织方式 | 支持的能力 | 代价 |
| --- | --- | --- |
| 全静态 | 简单、快、无运行时 | 无递归、无动态结构 |
| 栈 + 堆 | 递归、嵌套、动态对象 | 需运行时支持 |
| 堆 + GC | 任意生存期、闭包、对象共享 | GC 暂停、内存开销 |

语言在「静态/栈/堆 + 有无 GC」上的取舍，决定了它的表达力与运行时形态。<span class="marginnote">例：C 语言只用「栈 + 显式堆」，所以它没有闭包（需要堆分配的捕获环境）；Java/Python 有 GC，所以对象、闭包、共享结构都放开手脚。存储组织就是语言能力的「底层预算」。</span>

## 7 思考与练习

**练习 1 四区归类**：把以下数据归类到「代码/静态/栈/堆」：全局变量、`static` 局部变量、函数局部变量、`malloc` 的对象、字符串常量、机器指令。

**练习 2 生存期判据**：用「数据会不会活过创建它的调用」判断 `malloc` 的对象、函数返回值、全局缓存——各该进栈还是堆？<span class="marginnote">「活过调用必进堆」是存储分配的总判据：被返回的对象、存进全局结构的数据、被闭包捕获的变量——它们在调用结束后仍被引用，栈会回收它们，只能进堆。想通这条判据，C 的 `malloc`、Java 的对象、Rust 的 `Box` 就都有了统一的解释。</span>

**练习 3 递归的存储**：解释「全静态分配为什么不能支持递归」——同一函数两层调用的局部变量需要各自的空间，静态分配只有一块。

**练习 4 相向布局**：画出「栈向下、堆向上」的地址空间图，标出「相遇点」——并解释无限递归（栈溢出）与疯狂 malloc（堆耗尽）分别如何逼近相遇点。

**练习 5 语言设计**：对比「全静态」「栈+堆」「堆+GC」三种组织各自支持/不支持的语言特性（递归、闭包、动态对象），写成一页对照表。

**练习 6 工程观察**：在 Linux 上运行 `readelf -S`（或 `objdump -h`）命令看可执行文件的段（text/data/bss），把「代码区」「静态数据区」与 ELF 段对应起来。

**常见误区**：

- **误区一**：以为「局部变量一定在栈」——`static` 局部变量在静态区，生命周期是全局的。
- **误区二**：把「栈」与「堆」当语言类型——它们是「生存期服务商」，由「数据是否活过调用」决定。
- **误区三**：忽略「静态区包含常量」——字符串常量、只读表也在静态区，且常被放只读页。

**延伸**：运行时内存四区与第三级《操作系统》的「进程地址空间、ELF 段、brk/mmap」是同一张图——把「编译器的存储组织」与「OS 的内存管理」对接，说明「谁规划布局、谁提供物理内存」。

## 8 小结

- 运行时内存四大区：**代码区、静态数据区、栈区、堆区**，各司其职。
- **静态分配**在编译期定址，零开销但不支持递归与动态结构。
- **栈式分配**用活动记录匹配调用层次，O(1) 分配、适配递归，但数据不能逃出调用。
- **堆式分配**服务「活过调用」的数据，分配靠空闲块搜索，释放显式或 GC。
- 栈向下、堆向上的**相向布局**决定动态内存总量，也解释栈溢出与 OOM。
- 存储组织塑造语言能力：静态/栈/堆 + 有无 GC 的组合，就是运行时形态。
