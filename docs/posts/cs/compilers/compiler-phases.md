# 编译器的各阶段：一条语句的六道工序

## 为什么从六道工序开始

上一篇《编译器的结构》给了编译器一张总图：**前端分析、后端综合**，中间夹着一条中间表示。但那是一张「骨架图」——每一块骨骼到底怎么干活，还没有细看。今天这篇就把六道工序逐一拆开，看每一道工序的**输入是什么、输出是什么、负责解决什么问题、会在哪里报错**。

用一个新鲜的例子贯穿全文，而不是重复上一篇的 `position = initial + rate * 60`。温度换算这条语句信息量刚好合适：

```c
celsius = 5 * (fahr - 32) / 9;
```

它既有标识符、有数字常量、有括号，还有混合类型（`fahr` 是浮点数，`32`、`5`、`9` 是整数）——足够让六道工序都「有点事干」。读完这篇，你会获得一个关键区分：**阶段（phase）是概念上的工序，遍（pass）是机器实际扫过程序的次数**。这两者的差别，是后面理解编译器演化（从单遍到多遍）的钥匙。

## 1 一眼看完全程：六道工序的输入输出

先把结论摆出来。上面的温度语句经过六道工序，输出依次是：

| 工序 | 输入 | 输出 | 一句话职责 |
| --- | --- | --- | --- |
| 词法分析 | 字符流 | 记号流 | 把字符切成词 |
| 语法分析 | 记号流 | 语法树 | 把词拼成句子结构 |
| 语义分析 | 语法树 | 标注后的语法树 | 检查「这句话通不通」 |
| 中间代码生成 | 标注语法树 | 三地址码等 IR | 翻成机器无关的表述 |
| 代码优化 | IR | 优化后的 IR | 等价变换，让它更好 |
| 代码生成 | 优化后 IR | 目标代码 | 翻译成目标机器指令 |

这张表每行都是「上一行的输出，正好是这一行的输入」。下面逐行展开。读的时候请带着三个问题：**它解决什么问题？它用哪些数据？它怎么报错？**

## 2 词法分析：把字符流切成记号

**词法分析（lexical analysis）**：读入源程序的字符流，按照词法规则把它们分组为有意义的**词素（lexeme）**序列，并为每个词素生成一个**记号（token）**。<span class="marginnote">记号由两部分构成：<strong>记号名（token name）</strong>是抽象的类别（标识符、关键字、数字常量、运算符），<strong>属性值（attribute value）</strong>是具体的词素内容。龙书反复强调这个二分：词法分析器报告「这里出现一个标识符」，属性值才告诉后续阶段「这个标识符叫 fahr」。</span>

对温度语句，词法分析的产物是：

```text
id1 = 5 * ( id2 - 32 ) / 9 ;
```

其中 `id1` 代表 `celsius`，`id2` 代表 `fahr`；`5`、`32`、`9` 是数字常量记号，`=`、`*`、`(`、`)`、`/`、`;` 各是一个运算符或分隔符记号。

词法分析遵循的规则是**正则表达式**描述的——标识符、数字、关键字的「形状」都能用正则语言刻画。它的实现通常是一条「状态机」：从正则表达式构造 NFA，再确定化为 DFA，让 DFA 在字符流上跑。这正是本专题第二篇《词法分析》的全部内容，也与你学过的第二级《离散数学》里的有限自动机一一对应。<span class="marginnote">为什么词法要单独设一道工序而不是并入语法？一是效率：记号级处理比字符级快得多，语法分析不必逐字符讨论；二是模块化：词法规则集中在一处，改关键字、加注释语法都不碰语法分析器。</span>

**辨析｜易错点：** 词法分析**不做「这样组合起来合不合语法」的判断**。`(` 和 `)` 是否匹配、运算符前后是不是该有操作数，词法分析器一概不管——它只负责「分组」，合法性与否是下一道工序的职责。这个边界是初学者最容易搞混的地方。

词法错误通常极少，典型是**非法字符**：输入里出现语言字母表之外的字符（比如中文字符混进标识符、未转义的 `@`）。此时词法分析器报「无法识别的字符」，并把错误信息连同位置交给错误处理器（下一篇详谈）。

## 3 语法分析：给记号搭出层次骨架

**语法分析（syntax analysis / parsing）**：根据语言的**文法（grammar）**，把记号流组织成一棵**语法树（syntax tree）**，揭示记号之间的层次关系。<span class="marginnote">「文法」就是一组产生式规则，例如 $E \to E + T \mid T$、$T \to T * F \mid F$、$F \to \text{id} \mid \text{num} \mid (E)$。它回答「哪些记号序列是合法的句子」——这正是第二级《离散数学》里形式语言与文法的内容，第三篇《语法分析》将整章展开。</span>

温度语句的语法树形状如下（为可读性省去部分中间结点）：

```text
        =
      /   \
   id1      /
          /   \
        *      9
       / \
      5   -
         / \
      id2   32
```

这棵树表达了两件事：第一，`(fahr - 32)` 是一个整体，先算；第二，`5 * (fahr - 32)` 先于 `/ 9` 结合。**语法树把「计算的优先级」变成了「树的高低」**——越深的结点越先执行。括号在词法阶段被读进来，在语法阶段就已经完成了它的使命：它决定了树的形状，此后无需再出现。

语法分析分两大家族：**自顶向下**（从起始符号出发，试图用产生式推导出记号串，代表是递归下降分析）与**自底向上**（从记号串出发，试图归约到起始符号，代表是 LR 分析）。前者直观易写、后者更强大。两大家族在第三篇各占一半篇幅。

**辨析｜易错点：** 语法分析只检查**结构**是否合法，不检查**含义**是否合理。`x = y * z;` 结构完全合法，但若 `y` 根本没声明、或 `y` 是字符串，语法分析不会抱怨——那是语义分析的活。

语法错误是最常见的一类编译错误：括号不匹配、缺分号、表达式不完整等。如何「优雅地」报错、报完错还能继续往下找错，是错误恢复策略的主题（下一篇有专门一节）。

## 4 语义分析：检查「这句话通不通」

**语义分析（semantic analysis）**：在语法树的基础上检查**静态语义（static semantics）**——那些无法用文法表达、却能在编译期检查的规则：变量是否已声明、类型是否匹配、运算是否合法、函数调用参数个数是否一致。<span class="marginnote">判断「类型是否匹配」需要知道每个名字的类型，而类型的档案就存在<strong>符号表（symbol table）</strong>里。语义分析是符号表的主要使用者与维护者——下一篇《符号表与错误处理》会专门讲它。</span>

对温度语句，语义分析发现 `fahr` 是浮点数而 `32`、`5`、`9` 是整数：`fahr - 32` 是浮点数减整数，需要把 `32` 转成浮点数；`5 * (...)` 同理。于是它**在语法树上插入显式的类型转换结点**，产出「标注后的语法树」：

```text
celsius = (inttofloat(5) * (fahr - inttofloat(32))) / inttofloat(9)
```

**语义分析不改变程序「能做什么」，只把程序「做了什么」变得更明确**——类型转换被显式化，后续的中间代码生成就有了依据。类型检查的系统理论（类型等价、类型转换、重载解析）对应第五篇《中间代码生成》的类型系统章节，也与第三级《程序设计语言》的静态类型检查互为表里。

语义错误的典型：**未声明标识符、类型不匹配、重复声明、越界数组下标**等。这类错误比语法错误更难定位，因为错误往往不在「发生处」而在「来源处」——比如把一个 `int` 传给需要 `float*` 的函数。好的编译器会回溯报出「这里类型不匹配：期望 float\*，实际得到 int」。

## 5 中间代码生成：翻成机器无关的表述

**中间代码生成（intermediate code generation）**：把标注后的语法树翻译成一种**中间表示（intermediate representation，IR）**。龙书的主角是**三地址码（three-address code）**：每条指令至多含一个运算符和三个地址。温度语句的三地址码如下：

```text
t1 = inttofloat(32)
t2 = fahr - t1
t3 = inttofloat(5)
t4 = t3 * t2
t5 = inttofloat(9)
t6 = t4 / t5
celsius = t6
```

每条指令形如「`t = x op y`」，读起来像汇编，却不绑定任何具体指令集。<span class="marginnote"><strong>为什么要造一个中间表示？</strong> 因为「前端不依赖机器、后端不依赖语言」这条分界线必须有个物质载体，IR 就是那个载体。C 源码 → IR → x86 指令，与 C 源码 → IR → ARM 指令，前端可以一字不改。现代 LLVM 把这条线画得更加明确：LLVM IR 成了前后端之间的正式契约，见第十一篇。</span>

除了三地址码，常见 IR 还有**语法树本身**、**DAG（无环有向图，可合并公共子表达式）**与**静态单赋值（SSA）**——最后一种是现代编译器（LLVM、GCC）的主流，第五篇会展开。此刻只需记住：**IR 是前端工作的终点，后端工作的起点**。

## 6 优化与代码生成：让它更快，再变成机器能懂的

**代码优化（code optimization）**：在不改变语义的前提下，对 IR 做**等价变换**，使程序更快、更省空间。温度语句里可以优化：`inttofloat(5)`、`inttofloat(9)`、`inttofloat(32)` 都是**常量**，可以在编译期就算出结果，于是三处转换被折叠成常量本身。优化后的三地址码明显变短：

```text
t1 = fahr - 32.0
t2 = 5.0 * t1
celsius = t2 / 9.0
```

**优化是「关于等价变换的科学」**：常量折叠、公共子表达式消除、循环不变式外提、寄存器分配前的活跃变量分析……这些构成第八篇《机器无关优化》的骨架。今天只强调一点：优化作用在 **IR** 上，既不动源程序也不动最终机器码，这是它能跨机器复用的根本原因。

**代码生成（code generation）**：把优化后的 IR 翻译成目标机器的指令序列。它要解决**指令选择**（`t2 = 5.0 * t1` 翻译成哪条乘指令）、**寄存器分配**（这些临时值留在寄存器还是压进栈？）、**指令调度**（如何排列指令以充分利用流水线）。这是第七篇的主题，也是编译器中「离机器最近」的环节——它一头连着 IR，一头连着第三级《计算机组成原理》的指令集与寄存器模型。

## 7 公式解析：编译器是六次函数的复合

六道工序各自把一种表示映射成另一种表示，因此整个编译器可以用**函数复合**写成一个干净的等式：

$$
\mathrm{Compiler} = \mathrm{CodeGen} \circ \mathrm{Optimize} \circ \mathrm{IRGen} \circ \mathrm{Semantic} \circ \mathrm{Parser} \circ \mathrm{Lexer}
$$

逐步拆解：

- **第一步，看懂记号**：$\circ$ 是函数复合，$f \circ g$ 表示「先 $g$ 后 $f$」。所以右边的 $\mathrm{Lexer}$ **最先**作用于源程序，$\mathrm{CodeGen}$ **最后**作用于最内层结果。
- **第二步，看每个函数的「定义域与值域」**：$\mathrm{Lexer}:\text{字符流} \to \text{记号流}$，$\mathrm{Parser}:\text{记号流} \to \text{语法树}$，$\mathrm{Semantic}:\text{语法树} \to \text{标注语法树}$，$\mathrm{IRGen}:\text{标注语法树} \to \text{IR}$，$\mathrm{Optimize}:\text{IR} \to \text{IR}$，$\mathrm{CodeGen}:\text{IR} \to \text{目标代码}$。前一个的值域恰好是后一个的定义域——**这就是第 1 节那张表能用「输入→输出」串成链的原因**。
- **第三步，读出结构**：这个等式把「编译器」定义成了**六次映射的串联**。它同时解释了前端与后端的边界：前四个函数只涉及「语言知识」（词法规则、文法、类型规则），后两个函数才涉及「机器知识」。无论六步在物理上如何实现（一次扫过还是六次扫过），这个抽象关系都不变。

**这个等式的意义不在计算，而在看清「接口」**：每一对相邻函数之间都有一个确定的数据结构（记号流、语法树、IR），这些数据结构就是阶段之间的**契约**。只要契约不变，任何一段都可以单独替换——这正是编译器模块化的数学表达。

## 8 阶段与遍：概念上六步，实现上可以合并

读完六道工序，还差最后一个关键区分：**阶段（phase）** 与 **遍（pass）**。

- **阶段**是概念上的工序：六道工序是六个阶段，它们之间的界线由「表示形态」决定（字符流、记号流、语法树、IR……）。
- **遍**是实际的物理过程：指编译器**从头到尾读一遍它的输入**（可以是源程序，也可以是某种中间表示），并产生一份输出。

两者**不是一一对应的**。一个阶段可以由多个遍完成（优化常常要来回扫很多遍）；反过来，多个阶段也可以合并进一个遍——比如一边读入字符流，一边做词法、语法、生成代码，全程只扫一遍源程序。这就是**单遍编译器（single-pass compiler）**。<span class="marginnote">单遍编译器很诱人：只读一遍源码，内存占用极小、编译极快，适合早期内存只有几千字节的机器。但它的代价是语言设计必须让步：所有名字必须「先声明后使用」，否则一遍之内没法知道一个名字的类型。为什么语言会为此牺牲表达能力、又为什么今天的编译器都转向多遍——这是下一篇的姊妹话题《编译器的演化》。</span>

**辨析｜易错点：** 说「某个编译器是 N 遍的」，指的是物理扫过的次数，**不是**概念阶段的个数。把「阶段」和「遍」当成一回事，是读完「六道工序」后最常见的误读。阶段数由语言决定，遍数由实现者决定——同一个 C 编译器，可以做成单遍、也可以做成八遍，语义不变，只是工程质量与编译时间不同。

## 9 小结

- 六道工序：**词法（字符流→记号流）→ 语法（记号流→语法树）→ 语义（语法树→标注语法树）→ 中间代码（→IR）→ 优化（IR→IR）→ 代码生成（→目标代码）**。
- 词法只负责**分组**，不判断合法性；语法检查**结构**，语义检查**静态语义**；三者报错范围严格分工。
- 优化与代码生成作用于 **IR** 而不是源程序，这是前后端解耦、可跨机器复用的根基。
- 整个编译器是六次函数的复合：$\mathrm{CodeGen} \circ \mathrm{Optimize} \circ \cdots \circ \mathrm{Lexer}$，阶段之间的数据结构就是契约。
- **阶段是概念、遍是物理**：单遍编译器把多道工序压进一次扫描，多遍编译器让每遍更专注——两者的权衡是编译器演化史的主线。

在下一节，我们将追着两件贯穿所有工序的东西跑一趟：一件是**符号表**——编译器靠它记住每个名字的档案；另一件是**错误处理**——编译器靠它在出错时依然优雅。这就是《符号表管理与错误处理》。
