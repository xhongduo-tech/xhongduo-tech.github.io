## 为什么从活动记录开始

存储组织划好了「栈区归调用」的宏观格局，现在要问微观结构：**一次调用在栈上占多大、放什么、怎么找到自己的数据？** 答案是一种叫**活动记录（activation record, AR）** 的数据块——每次过程调用在栈顶压入一个 AR，里面装这一次调用的全部私密数据。它是栈式分配的「基本单位」，也是理解调用序列、非局部访问、参数传递的枢纽。<span class="marginnote">「活动」一词取自「一次激活」：同一个函数被递归调用两次，就有两个活动记录——虽然代码是同一份，但数据是两份。AR 是「代码与数据分离」的物理实现：代码共享，数据各自。</span>

## 1 活动记录的字段

一个典型活动记录按一定顺序排列的字段包括：

| 字段 | 内容 |
| --- | --- |
| **返回地址** | 调用结束后回到的指令位置 |
| **动态链（控制链）** | 指向调用者的活动记录（栈上「谁调我」） |
| **静态链（访问链）** | 指向词法外层过程的活动记录（「我的逻辑外层是谁」） |
| **参数** | 实参的值或地址 |
| **局部数据** | 局部变量、临时变量 |
| **保存的机器状态** | 被调方要还原的寄存器等 |

字段的**确切布局是编译器的私有约定**——只要同一个编译器前后一致，字段次序可以灵活安排。<span class="marginnote">注意「动态链」与「静态链」是一对容易混淆的概念：动态链沿<strong>调用历史</strong>走（谁实际调用了我），静态链沿<strong>词法嵌套</strong>走（源代码里我定义在谁里面）。递归时两者重合，嵌套函数时两者分岔——下一节讲非局部名字访问时它们各自登场。</span>

## 2 调用序列：一场接力

**调用序列（call sequence）** 是「调用一条语句」时，调用方与被调方**分头执行**的动作序列。三地址码层的 `param`/`call`/`return`，在机器层对应一组具体动作：

**调用方（caller）负责**：
1. 把实参放入参数区（栈顶上方）。
2. 保存返回地址（压栈）。
3. 跳转到被调函数入口。

**被调方（callee）负责**：
4. 分配 AR：压入局部数据与保存的状态。
5. 执行函数体。
6. 恢复状态、把返回值放回约定位置。
7. 跳回返回地址；调用方清理参数区（或被调方清理，随约定）。

「谁压参数」「谁清栈」的组合形成不同的**调用约定**：cdecl（调用方清理）、stdcall（被调方清理）、SysV（寄存器传参优先）等。<span class="marginnote">「谁清理参数区」看似小事，却影响变长参数、栈平衡与安全：cdecl 让调用方清理，故 `printf` 这类变长参数可行；stdcall 被调方清理更省空间。现代 x86-64 的 SysV 用寄存器传前六个参数，栈只剩溢出的部分——调用序列的设计，是性能与灵活的权衡史。</span>

## 3 栈指针与帧指针

栈式分配的核心是两根指针：

- **栈指针 `sp`**：指向当前栈顶。压 AR 时下移、弹 AR 时上移。
- **帧指针 `fp`**：指向当前 AR 的固定基准位置（通常指向一个已知偏移的字段）。

为什么需要 `fp`？因为 `sp` 在函数内**会动**（压临时变量、嵌套调用会改变 `sp`），而 `fp` 在函数执行期间**不变**——局部变量的地址用 `fp + 常量偏移` 访问，稳定可靠。<span class="marginnote">「sp 动、fp 不动」是帧指针存在的全部理由：`sp` 相当于「活动的指尖」，`fp` 相当于「固定的腰杆」。现代编译器常在函数内不改变 `sp`（用寄存器保存栈深度），从而可以省略 `fp`（省略帧指针优化），省出一个寄存器、减少一条指令。</span>

## 4 公式解析：帧内变量的访问

若 AR 的布局是「帧指针向高地址依次是参数、返回地址、……，向低地址是局部数据」，则第 $i$ 个参数与第 $j$ 个局部变量的地址：

$$\text{参数}_i:\ fp + k_{\text{param}} + i \times w, \qquad \text{局部}_j:\ fp - k_{\text{local}} - j \times w$$

- **第一步，基准**：`fp` 是当前 AR 的固定基准，一切偏移从它出发——编译期就确定每个变量相对 `fp` 的偏移量。
- **第二步，正负方向**：参数区通常在 `fp` 上方（高地址），局部数据在下方（低地址）——方向由 AR 布局约定决定，编译器统一即可。
- **第三步，偏移预计算**：每个名字在编译期查符号表得到偏移，运行时只需 `fp ± 偏移` 一次访存——**变量访问 = 基址 + 常量偏移**，这是栈式分配极快的原因。

**「编译期定偏移、运行期只做加减」是栈式分配的效率承诺**——它把名字解析压缩成一条带偏移的访存指令。

## 5 调用序列与编译器后端

调用序列不是运行时写的——它是**编译器生成的代码**。每次 `call` 翻译时，编译器吐出「压参数、存返回地址」的前缀；每个函数入口吐出「建 AR」的序言（prologue），出口吐出「拆 AR、恢复、返回」的尾声（epilogue）。

- **序言（prologue）**：保存调用者状态、压低 `sp` 建帧、必要时存 `fp`。
- **尾声（epilogue）**：恢复寄存器、回收帧、跳回返回地址。

**重点是**：活动记录与调用序列是「编译器生成的运行期约定」——前端生成意图，后端把它变成机器指令，而约定本身要前后端精确对齐。<span class="marginnote">调试器（gdb）、异常处理、`setjmp/longjmp` 都依赖 AR 布局与帧链的稳定：调试器靠「帧指针链」回溯调用栈，异常处理靠它定位 handler。AR 不只是运行期数据结构，更是工具链共享的「调用史档案」。</span>

## 7 思考与练习

**练习 1 设计 AR**：为一个函数 `int f(int a, int b) { int x, y; ... }` 设计活动记录布局——标出参数、返回地址、局部数据的相对位置与正负方向。

**练习 2 调用序列**：写出「调用方」与「被调方」各自的职责清单（压参数、存返回地址、建帧、恢复、返回），标出哪些动作由谁完成。

**练习 3 fp 的必要性**：解释为什么需要帧指针 `fp` 而 `sp` 不够——函数内 `sp` 会动（压临时、嵌套调用），`fp` 固定，局部访问靠 `fp + 偏移` 稳定。

**练习 4 帧内偏移**：对练习 1 的 AR，写出「第 i 个参数」「第 j 个局部变量」相对 `fp` 的偏移公式——编译期定偏移、运行期只做加减。

**练习 5 调用约定**：对比「调用者清理」与「被调者清理」两种约定，各说一个适用场景（变长参数 vs 节省空间）——并说明为什么 `printf` 需要调用者清理。<span class="marginnote">「谁清理参数区」是调用约定的核心分歧：`printf` 参数个数运行时才知，被调者不知道要清多少，所以必须调用者清理（cdecl）；参数个数固定的函数可让被调者清理（stdcall），省一次栈操作。现代 x86-64 SysV 用寄存器传前几个参数，栈清理的争论被部分绕开——但「约定」的重要性不变。</span>

**练习 6 工程观察**：用 `gcc -S` 或 `clang -S` 看一个简单函数的序言/尾声，找「压 sp、存 fp、恢复、返回」对应的汇编指令。

**常见误区**：

- **误区一**：以为「返回地址存哪都一样」——它必须在调用时压栈、返回时弹栈，位置由调用约定固定。
- **误区二**：把「动态链」与「访问链」混淆——一个沿调用史、一个沿词法嵌套（第六篇后文）。
- **误区三**：忽视帧指针——优化后可省略 fp（用 sp + 固定偏移），但调试器依赖帧链。

**延伸**：活动记录的「帧 = 数据块 + 链」与第六篇「栈式分配」、第五篇「过程调用翻译」是三段连续——把「三地址码的 param/call」到「机器层的调用序列」的展开过程写成一页。

## 8 小结

- **活动记录（AR）** 是一次调用在栈上的数据块：返回地址、链、参数、局部数据、保存状态。
- **调用序列**是调用方与被调方分工执行的动作序列；「谁清参数」等选择构成调用约定。
- **栈指针 `sp`** 指向栈顶、会动；**帧指针 `fp`** 指向当前帧、固定——局部访问靠 `fp + 偏移`。
- 变量访问 = **基址 + 编译期定好的常量偏移**，一次访存即可，栈式分配因此高效。
- 序言/尾声是编译器生成的建帧/拆帧代码，也是调试器、异常处理依赖的「调用史档案」。
