## 为什么从测试与错误诊断开始

玩具编译器的最后一步，是证明「它是对的」——以及「它错得清楚」。**测试**系统地验证每个阶段（词法、语法、语义、代码生成）的输出；**错误诊断**让「坏输入」得到可读、可定位的反馈。编译器是「累积复杂度」极高的程序：一个小 bug（优先级错、符号表漏查）可能让正确的程序跑出错误结果。测试与诊断，是这门「精密工程」的护栏。<span class="marginnote">「编译器测试是对其他程序的测试的工具」是个有趣的递归：测试编译器需要「预期输出」，而预期输出来自「我们相信这个程序该算什么」——所以编译器测试天然是「对拍 + 人工预期」的组合。LLVM 的 lit 测试框架、GCC 的 torture 测试，都是这套思想的工业版——ToyLang 只要几百行测试，就够「证明能跑」。</span>

## 1 测试的类型

ToyLang 的测试分四层，对应四个阶段：

| 测试层 | 测什么 | 怎么做 |
| --- | --- | --- |
| **词法测试** | 记号切分正确 | 输入源码 → 检查记号流 |
| **语法测试** | AST 结构正确 | 输入源码 → 检查 AST（转储后对比） |
| **语义测试** | 错误被正确报告 | 输入坏程序 → 检查错误信息 |
| **代码生成测试** | 输出程序行为正确 | 编译 → 运行 → 检查结果 |

**代码生成测试的黄金标准**：**Golden test（金标准测试）**——给输入程序，运行编译产物，把「输出」与「预期输出」对比：

```
测试: fib(10) 应输出 55
输入:  print(fib(10));
预期:  55
```

编译 + 运行 + 对比——这是「编译器最终正确」的直接证明。<span class="marginnote">「Golden test 是编译器正确性的最高证词」：`print(fib(10))` 编译出来运行，输出 55 才过关。它验证的是「整条链」（词法→语法→语义→代码生成→运行）的端到端正确性——比单独测某层更有说服力。玩具编译器的测试框架可以朴素到「一个 shell 脚本 + 一堆 .txt 预期」，机制与 LLVM lit 一致。</span>

## 2 测试驱动开发

写编译器的推荐节奏是**测试先行**：

1. **先写测试**：`fib(5) → 5`、`a+b*c → 优先级正确`、`未声明变量 → 报错`。
2. **再写实现**：让测试通过。
3. **每加特性先加测试**：新增 `while` 前，先写 `while` 的测试。

**关键收益**：

- **回归保护**：改了词法器，之前的语法测试立刻告诉你「有没有破坏」。
- **特性清单即测试清单**：测试文件就是「语言功能的验收单」。
- **bug 即测试**：发现 bug → 先写复现它的测试 → 再修——bug 从此「进了档案」。

**测试的组织**：每个阶段一个测试目录（`test/lexer/`、`test/parser/`、`test/codegen/`），用「输入 → 预期输出」的黄金文件结构。<span class="marginnote">「bug 即测试」是编译器开发的高效心法：每个修掉的 bug 都变成一条回归测试，确保「这个 bug 永不复发」。LLVM 的 bug 修复几乎必带一个 lit 测试用例，ToyLang 也应如此——编译器 bug 常隐藏在「上次改坏的东西」里，测试档案就是防回归的城墙。</span>

## 3 错误诊断：让坏输入错得清楚

错误诊断的质量，决定开发者体验。ToyLang 的诊断规范：

**好的错误信息三要素**：

1. **位置**：`test.tl:3:5`——第 3 行第 5 列。
2. **期望 vs 实际**：`期望 ';'，得到 '}'`。
3. **上下文**（可选）：显示出错的那行源码 + 指向的 `^`。

```
test.tl:3:5: 错误: 期望 ';'，得到 '}'
    x = 1 }
        ^
```

**错误信息的设计原则**：

- **说人话**：「未声明的标识符 x」比「symbol not found: x」对用户更友好。
- **具体**：「期望 ';' 得到 '}'」比「语法错误」有用十倍。
- **不撒谎**：报错位置要准，别把错报到不相干的行。

**错误恢复**（词法/语法层）：报错后跳到同步点继续——一次运行多报几个错，而不是「错一停」。<span class="marginnote">「错误信息是编译器写给用户的说明书」：GCC 早年以「Error: parse error before '}'」被吐槽，Clang 以「test.c:3:5: expected ';' after expression」+ 高亮行 + 脱字符成为标杆。诊断质量是「工程品味」的体现——ToyLang 把「位置 + 期望/实际 + 上下文」三件套做齐，就是合格的门面。</span>

## 4 公式解析：诊断信息的结构

一条诊断 = 三要素的结构化组合：

$$\text{诊断} = \underbrace{\text{位置}}_{\text{file:line:col}} + \underbrace{\text{级别}}_{\text{error/warning}} + \underbrace{\text{消息}}_{\text{期望 vs 实际、上下文}}$$

- **第一步，位置**：`file:line:col`——定位到字符级，用户一眼知道「哪错了」。
- **第二步，级别**：`错误`（阻断编译）与 `警告`（提示但放行）分开。
- **第三步，消息**：先「期望 vs 实际」，再给「出错行 + `^` 指向」——**可行动**：用户知道「缺什么」。

**「位置 + 级别 + 可行动消息」是诊断的结构化配方**——从 ToyLang 到 Clang，诊断都长这个骨架。

## 5 集成测试与持续打磨

测试与诊断的收尾工作：

- **端到端测试**：一个脚本跑「编译 + 运行 + 对比输出」全套。
- **失败模式测试**：每个错误类型（未声明、重复声明、参数不匹配、语法错）都要有测试用例。
- **边界测试**：空程序、极长表达式、嵌套极深——别让编译器在边界崩溃。
- **诊断测试**：不仅测「报错」，还要测「报错信息对不对」（错误类型、位置）。

**收尾心态**：玩具编译器「写完」的标志不是「能编译 hello」，而是「有一组测试证明它各处正确、有一组诊断让它错得清楚」——这才是一台「可信的编译器」的雏形。<span class="marginnote">「编译器成熟的标志是测试与诊断，不是新特性」：加特性容易，保证「加了不坏」才难。ToyLang 的终点不是「更多功能」，而是「一套能证明正确、能定位错误的工程闭环」——这恰好也是真实编译器团队每天都在做的事：在测试与诊断的护栏里，安全地演化。</span>

## 6 小结

- **测试四层**：词法（记号流）、语法（AST）、语义（错误报告）、代码生成（运行结果）。
- **Golden test 是正确性的最高证词**：编译 + 运行 + 对比预期输出——端到端验证整条链。
- **测试先行**：先写测试再写实现，特性即测试清单，**bug 即回归测试**。
- **诊断三要素**：位置（`file:line:col`）、级别（error/warning）、可行动消息（期望 vs 实际 + `^` 指向）。
- 收尾标志：**端到端测试 + 失败模式测试 + 边界测试 + 诊断测试**——可信编译器的雏形。

至此，我们从词法分析一路走到玩具编译器收尾——**本专题全部条目完成**。
