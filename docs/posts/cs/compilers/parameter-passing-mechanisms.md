## 为什么从参数传递机制开始

活动记录里有个「参数区」，但参数怎么从实参进入形参，是语言设计的一个**深层分叉**：是拷贝值？是传地址？还是干脆传一个「怎么算出这个值」的配方？不同选择决定了被调函数改形参时，调用者的变量会不会跟着变——这直接影响程序员的心智模型与编译器的代码生成。<span class="marginnote">「实参与形参的关系」是编程语言原理（PL）里最经典的话题之一，也是跨语言混用最容易踩坑的地方：C 传值、Java 传「引用值」、C++ 的引用、Python 传对象引用、Swift 的 inout——每个机制都有微妙的语义差别，而编译器必须逐一实现这些差别。</span>

## 1 传值与传引用

**传值（call-by-value）**：把实参的**值**拷贝进形参。被调方改形参不影响调用方的变量——隔离干净。

```c
void inc(int x) {
    x = x + 1;      /* 改的是副本 */
}
int a = 5;
inc(a);
/* a 仍是 5 */
```

实现：参数区存一份拷贝。开销 = 拷贝成本（大结构体传值很贵）。

**传引用（call-by-reference）**：把实参的**地址**传给形参。被调方通过地址读写调用方的变量——修改会「穿透」回去。

```c
void inc(int *x) {
    (*x) = (*x) + 1;    /* 通过地址改原变量 */
}
int a = 5;
inc(&a);
/* a 变成 6 */
```

实现：参数区存地址，被调方每次用形参都解引用。开销 = 一次间接访存，但无拷贝。<span class="marginnote">「传引用」是 C 指针传参、C++ 引用的共同底层：本质都是「传地址」。区别在语法糖与安全检查——C++ 引用语法上像值、语义是别名；C 指针显式 `&`/`*`。理解「传引用 = 传地址」，就能看穿所有变体。</span>

## 2 传名与复制恢复

**传名（call-by-name）**：不计算实参，而是把「计算实参的代码」本身传给形参——**每次用到形参时，现场重算实参**。这是 ALGOL 60 的经典机制，也是**惰性求值（lazy evaluation）** 的鼻祖。

```c
int i = 3;
void p(by-name y) {
    i = 0;
    print(y);   /* 此处 y 现场重算：i + 5 = 5 */
}
p(i + 5);       /* 实参是「配方」i+5，不是值 8 */
```

副作用恐怖：若实参是 `i++`，形参出现三次就加三次；若实参含 `i` 且循环改 `i`，值实时变化。**传名**几乎已退出历史舞台，但它的思想活在函数式语言的惰性求值里（Haskell）。

**复制恢复（copy-restore / copy-in copy-out）**：调用开始时把实参值**拷入**形参；返回时把形参的**最终值拷回**实参。像是「传值的进入 + 传引用的离开」。

与传引用的差别：**修改只在返回时一次性生效**——若函数中途崩溃或读取他人地址，行为不同。
与传值的差别：形参的修改能「带出来」。
现代语言少用（Ada 的 `in out` 参数近之）。<span class="marginnote">复制恢复的「进入拷入、返回拷出」像一次「借读还写」：被调方工作在自己的副本上，结束时把结果写回。它的边界情况（两个实参别名同一变量、形参取地址）会产生与传引用不同的行为——这些边角案例正是编译原理教材钟爱的考点。</span>

## 3 四种机制对比

| 机制 | 进入 | 返回 | 修改是否穿透 | 实现成本 |
| --- | --- | --- | --- | --- |
| 传值 | 拷值入参 | 无 | 否 | 拷贝成本 |
| 传引用 | 传地址 | 无 | 是（即时） | 间接访存 |
| 传名 | 传「重算代码」 | 无 | 视实参而定 | 每次使用重算 |
| 复制恢复 | 拷值入参 | 拷回 | 是（返回时） | 两次拷贝 |

**辨析｜易错点：** 传引用与复制恢复都能「让修改生效」，但时机不同：前者**即时**（函数内任何改动立即可见），后者**返回时一次性**（函数内看到的是副本）。对「函数内读取实参的当前值」这类操作，两者可能给出不同结果——这是考题最爱的地方。<span class="marginnote">另一个易错点：传引用与传值对「形参被赋值」的语义——传值改副本、传引用改原变量。但注意「引用本身被重新赋值」与「引用指向的值被改」是两回事：`x = y` 让 x 重新绑定，与 `*x = y` 写入 x 所指位置，语义天差地别。</span>

## 4 公式解析：传名的 thunk 实现

传名的工程实现：把实参包成一个**thunk**——一段「计算实参」的闭包代码，形参每次使用就调用它。

$$\text{形参 } x \text{ 的每次使用} \Rightarrow \text{调用 } \text{thunk}_x() \text{ 重新计算实参}$$

- **第一步，绑定**：调用时，不把实参值放入参数区，而是放入一个指向「实参计算代码 + 环境」的 thunk 指针。
- **第二步，重算**：函数体内每用一次 `x`，就是一次 thunk 调用——重新执行实参表达式。
- **第三步，后果**：实参被重算的次数 = 形参被使用的次数；若实参有副作用，结果随使用次数漂移——这就是传名「难以预料」的根源，也是它被淘汰的原因。

**thunk 是「把表达式当成值传递」**——今天的闭包、惰性求值、生成器都沿用了「延迟计算」这一核心思想。

## 5 各语言的现实选择

| 语言 | 机制 | 备注 |
| --- | --- | --- |
| C | 传值；数组退化为传指针 | 无引用语法，`&`/`*` 手动 |
| C++ | 传值 + 传引用 `&` + 传 const 引用 | 引用即别名 |
| Java | 传值（对象传引用值） | 「对象引用按值传」，易误解 |
| Python/JS | 传对象引用（本质传引用值） | 「对象共享」语义 |
| Swift | inout 参数（复制恢复变体） | 显式 `inout` |

「Java 到底传值还是传引用」是经典面试题：**对象引用是按值传的**——方法内改引用本身不影响调用方，但通过引用改对象内容会穿透。<span class="marginnote">这个「引用按值传」的微妙性，源自「变量 = 存储位置」与「变量 = 值的别名」两种心智的冲突。编译器实现上，一切参数最终都是「拷贝进参数区」——拷的是值还是地址，由语言语义决定；理解这一层，面试与调 Bug 都受益。</span>

## 6 小结

- **传值**：拷值入参，修改不穿透；**传引用**：传地址，修改即时穿透。
- **传名**：传「重算配方」，用一次算一次——副作用难测，已近淘汰，思想活在惰性求值。
- **复制恢复**：进入拷入、返回拷出，修改「返回时一次性」生效。
- 传名用 **thunk**（实参计算闭包）实现；「延迟计算」思想延续到闭包与生成器。
- 现实语言是各机制的组合：C 传值、C++ 引用、Java/Python「引用按值传」——实现上都是「拷贝进参数区」，拷值或拷地址由语义定。
