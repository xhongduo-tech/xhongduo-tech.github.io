## 为什么从词法分析器开始

第二篇《词法分析》是编译器前端的第一站。在上一篇的编译器结构图里，词法分析是整条流水线的第一个盒子：输入是源程序字符流，输出是记号流。你可能觉得它「很简单」——把字符分组而已。但正是这个「简单」，让它成了计算机科学里形式语言理论第一次全面落地的战场：正则语言、有限自动机、状态最小化……这些抽象概念在这里全部变成可运行的代码。

今天先不碰正则与自动机的细节，回答两个更基础的问题：**词法分析器在编译器里到底干什么？它对外暴露什么样的接口？** 把「作用与接口」钉死，后面再往里填实现，才不至于迷路。<span class="marginnote">龙书 §3.1 的标题就叫「词法分析器的作用」（The Role of the Lexical Analyzer）。注意龙书的行文顺序：先讲角色与接口，再讲记号、模式与词素，最后才落到正则与自动机——这是「先有分工，后有实现」的教学次序，我们照此推进。</span>

## 1 词法分析器：语法分析器的左膀右臂

**词法分析器（lexical analyzer / lexer / scanner）**：读入源程序的**字符流**，把它切分成有意义的**记号（token）**序列，并把记号交给语法分析器。

它在编译器中扮演的角色，龙书写得很清楚：词法分析器是语法分析器的**一个子程序**，由语法分析器在需要时调用——经典实现里，`getNextToken()` 每被调用一次，就返回下一个记号。

**辨析｜易错点：** 常见误区是把「词法分析」和「语法分析」混为一谈。界限在于**处理对象与表达能力**：词法分析处理的是**字符级**结构（一个记号内部的形态），用**正则语言**描述；语法分析处理的是**记号级**结构（记号如何组成句子），用**上下文无关文法**描述。正则语言是上下文无关语言的真子集——**凡是能用正则描述的，都能用文法描述；反之不然**（比如括号要成对出现，正则就描述不了）。<span class="marginnote">这条「正则 ⊂ 上下文无关」的包含关系是形式语言理论的第一个里程碑。计算理论的严格层级（Chomsky 谱系）见第二级《计算复杂性理论》，那里会证明为什么「成对括号」不能由正则语言描述。</span>

## 2 词法分析器要做的五件事

把一个词法分析器的职责清单列全，是理解「接口该设计成什么样」的前提：

- **读入字符流，产生记号流**：把连续字符按规则分组。`rate * 60` 产生三个记号：标识符、乘号、数字常量。
- **过滤空白与注释**：空格、制表符、换行、`// ...`、`/* ... */` 不是记号的组成部分，词法分析器把它们「吃掉」，不传给语法分析器。<span class="marginnote">注释是否由词法层处理，因语言而异。C 语言注释可跨行、可嵌套，词法层通常简单丢弃；而脚本语言里注释可能出现在两词之间，交给词法层处理最自然。</span>
- **与符号表交互**：识别出标识符时，把它登记进**符号表（symbol table）**，并返回一个指向对应表项的指针，作为该记号的值。
- **报告词法错误**：遇到不属于任何记号的字符（如 C 程序里出现 `@`）时，报告「非法字符」这类**词法错误**。
- **识别字面量并转换**：数字常量、字符串字面量在词法阶段被识别，并由词法分析器完成「字符串 → 内部值」的转换。

**重点：** 词法分析器是「**分词器**」，不是「分类器」。它不仅要回答「这是什么类型」，还要给出「这个具体词素的值」——类型与值合在一起，才构成一个完整的记号。只分类不取值，后面的语义分析与代码生成将无从下手。

## 3 接口设计：getNextToken 与向前看

词法分析器与语法分析器之间的契约，是一个很薄的函数：

```c
/* 词法分析器对外接口：返回下一个记号及其属性值 */
Token getNextToken(void);
```

**记号（token）**在接口层面是一个「类型 + 属性值」的二元组：类型说明它是标识符、数字还是运算符；属性值携带具体信息——标识符在符号表中的位置、数字常量的数值、运算符本身。

语法分析器调用它时，还可能遇到一种情况：**需要「向前看」（lookahead）一个记号才能决定下一步动作**。于是接口常常要配一个「放回」机制（`ungetToken`，或靠输入缓冲实现）：多读的那个记号要能退回给下一次调用。这为第三篇的 LL(1)、LR 分析埋下了伏笔——那里的 lookahead 记号，是决定分析方向的关键。<span class="marginnote">「向前看 + 放回」是几乎所有流式接口的共同主题：正则匹配器、JSON 解析器、甚至 bash 的词法分析都靠这一个机制把「多读一口」的代价摊平。输入缓冲如何支持这种放回，正是本篇第三节《输入缓冲与哨兵技术》的主题。</span>

### 一次完整的接口对话

纸上谈兵不如走一遍。以第一篇贯穿全书的赋值语句为例：

```c
position = initial + rate * 60;
```

词法分析器按语法分析器的请求，依次返回如下记号：

```c
Token t;
t = getNextToken();  /* t.type = ID,  t.attr = 指向 position 的符号表项 */
t = getNextToken();  /* t.type = '=', t.attr = 无 */
t = getNextToken();  /* t.type = ID,  t.attr = 指向 initial 的符号表项 */
t = getNextToken();  /* t.type = '+', t.attr = 无 */
t = getNextToken();  /* t.type = ID,  t.attr = 指向 rate 的符号表项 */
t = getNextToken();  /* t.type = '*', t.attr = 无 */
t = getNextToken();  /* t.type = NUM, t.attr = 值 60 */
t = getNextToken();  /* t.type = ';', t.attr = 无 */
```

注意两件事：**空白字符完全消失在记号流里**——它们被词法层吞掉，语法分析器根本看不见；**数字 `60` 的类型是 `NUM`，属性是数值 60**——字符串到数值的转换已在词法层完成。语法分析器只需看 `t.type` 就能决定归约动作，需要具体值时再取 `t.attr`，两者各司其职。这样一个薄薄的接口，就是词法阶段与语法阶段之间的全部契约。

## 4 为什么把词法分析从语法分析中独立出来

词法与语法完全可以合并——一次性从字符流直接建立语法树。但几乎所有编译器都把它们分开，理由有四条：

- **简化设计**：词法层面的模式用**正则语言**表达比用文法简洁得多，且正则语言有最有效的识别算法（线性时间、常数空间）。
- **提高效率**：词法分析是整个编译流水线中最「琐碎」的部分，独立出来后可用专门优化的线性算法快速跑，不必让昂贵的语法分析器逐字符处理。
- **增强可移植性**：字符集、行尾符、转义规则等平台差异被隔离在词法层，后端不必关心。
- **模块化与复用**：一门语言换了词法规则，只需改词法分析器；同一个词法分析器也可服务多个前端工具（静态检查器、代码美化器、文档生成器）。

**辨析｜易错点：** 「合并」是不是永远更差？不。**手写递归下降的语法分析器**常常把词法与语法**融合**成一个函数——每读一个字符立即判断。这样省去了记号流的内存往返，代价是**失去了词法阶段的独立优化与错误定位**。现代编译器的经验是：**清晰边界胜过微小的内存节省**，除非你的目标是教学演示或解释器原型。<span class="marginnote">解释器（如 CPython）常采用「一次扫描、逐句解释」的混合结构，词法与语法交错执行；编译器的经典结构则严格分段。这条差异在上一篇《编译器、解释器与混合执行模型》里已经铺过。</span>

把词法分析与语法分析的边界再压实一遍，用一张对照表收尾：

| 维度 | 词法分析 | 语法分析 |
| --- | --- | --- |
| 处理对象 | 源程序字符流 | 记号流 |
| 描述语言 | 正则语言（正则定义） | 上下文无关文法（CFG） |
| 识别模型 | 有限自动机（DFA） | 下推自动机（LR / LL 分析器） |
| 主要输出 | 记号流 | 语法树 |
| 时间复杂度 | O(n) 线性 | 一般 O(n)，需分析表支持 |
| 生成工具 | Lex / Flex | Yacc / Bison |

读这张表，请抓住最后一行的对比：**词法与语法各自有专属的生成工具**——这正是上一篇《编译器构造工具》讲的分工，在这里的具体落地。

## 5 公式解析：词法分析 = 正则语言的成员判定

词法分析器的全部工作，抽象成一句话：**判断一个字符串是否属于某个正则语言**。所谓正则语言，是由正则表达式定义的语言，其构造规则恰好是这三条：

$$
L(\epsilon) = \{\epsilon\}, \qquad L(r_1 \mid r_2) = L(r_1) \cup L(r_2), \qquad L(r_1 r_2) = L(r_1) L(r_2), \qquad L(r^*) = L(r)^*
$$

逐项拆解：

- **$\epsilon$ 与空串**：$L(\epsilon) = \{\epsilon\}$ 表示「只含空串的语言」。空串是任何字符串的「零长度前缀」，在正则运算里充当单位元。
- **$r_1 \mid r_2$ 是并**：匹配「$r_1$ 或 $r_2$」——语言是两者的并集。例如 `if | else` 匹配 `if` 或 `else`。
- **$r_1 r_2$ 是连接**：先匹配 $r_1$ 再匹配 $r_2$——语言是两者逐对拼接。例如 `letter digit` 匹配「一个字母后跟一个数字」。
- **$r^*$ 是闭包**：$r$ 重复任意次（含 0 次）。例如 `digit*` 匹配任意长度的数字串，包括空串。

这三条规则就像「构造积木」：**任何正则语言都能由空串、单个符号，以及并、连接、闭包三种运算组合出来**。词法分析器本质上是一个判定器：对每个记号类型都有这样一个正则语言；对输入的每个词素，词法分析器判断它属于哪个语言、进而归入哪个记号。这一判断过程由**有限自动机**完成——那是下一课的主角。<span class="marginnote">「正则语言由并、连接、闭包闭包地构造」这条性质，保证了词法分析总能被实现为<strong>有限自动机</strong>：状态数有限，因此只需常数空间、线性时间。这正是词法分析能做得如此快、如此简单的根本原因。</span>

## 6 小结

- **词法分析器**读入字符流、输出记号流，是语法分析器的子程序，核心接口是 `getNextToken()`。
- 它负责**分词、过滤空白与注释、登记符号表、报告词法错误、转换字面量**；空白与注释**不是**记号。
- 词法分析处理**字符级**结构，用**正则语言**；语法分析处理**记号级**结构，用**上下文无关文法**——两者不可混为一谈。
- 独立出词法分析的理由：**简化设计、提高效率、增强可移植、模块复用**。
- 词法分析抽象为**正则语言成员判定**，由并、连接、闭包三种运算构造，可用**有限自动机**在常数空间内完成判定。
