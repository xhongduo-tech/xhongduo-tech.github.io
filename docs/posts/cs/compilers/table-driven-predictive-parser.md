## 为什么从表驱动预测分析器开始

上一节的预测分析表给每个「（非终结符，记号）」组合指好了唯一的路。但「查表」落在代码里是什么样？朴素递归下降是函数互相调用，而表驱动是**一张表 + 一个显式栈**的通用引擎——文法变化时只换表、不换引擎。这正是生成器（Yacc 之于 LR、工具之于 LL）能做「一次生成、处处复用」的原因。

**非递归的表驱动预测分析器（nonrecursive predictive parser）** 把递归调用栈换成显式数据结构栈，把 if/else 决策换成查表。它更接近机器的本性：循环 + 栈 + 表，三个零件拼出一台确定性分析器。<span class="marginnote">显式栈还有工程红利：递归深度不受调用栈限制（深层嵌套表达式不会爆栈），且分析器可以随时暂停、保存、恢复——这对增量编译器、IDE 的实时语法高亮特别有价值。</span>

## 1 三件套：输入、栈、表

分析器的全部状态由三件东西构成：

**输入缓冲区**：从左到右读的记号流，末尾有一个特殊记号 `$` 表示结束。
**记号栈**：自底向上依次是 `$`、$S$（开始符号），此后弹出的每个符号代表「必须处理的东西」。栈顶是当前焦点。
**分析表** $M$：$(非终结符, 终结符) \to$ 产生式 或 error，上一节构造完成。

分析器的动作由**栈顶与当前输入记号**共同决定，一共四种：匹配、展开、接受、报错。<span class="marginnote">记忆口诀：栈顶如果是终结符，就「对一对、吃进去」；如果是非终结符，就「查一查、展开它」。`$` 相遇 `$` 则功德圆满。</span>

## 2 主循环算法

形式化地写出主循环：

```
把 $ 压栈，再压入开始符号 S（$ 在底）
repeat:
  X = 栈顶符号
  a = 当前输入记号
  if X 是终结符:
      if X == a: 弹出 X，输入前进一格
      else: 报错
  else if X 是非终结符:
      if M[X, a] = X → Y1...Yk:
          弹出 X
          逆序压入 Yk...Y1（若 Yi 为 ε 则不压入）
      else: 报错
  else:  # X == $
      if a == $: 接受
      else: 报错
```

关键一步是**逆序压栈**：产生式右侧 $Y_1Y_2\cdots Y_k$ 中，$Y_1$ 必须最先处理，所以最后压入。<span class="marginnote">逆序压栈就是把「展开产生式」翻译成栈操作：非终结符在栈顶被换成它的右侧，同时保证最左符号最先被处理——这正好复现了最左推导的顺序。</span>

## 3 一个完整的运行轨迹

用文法 $E \to T\,E'$、$E' \to +T\,E' \mid \varepsilon$、$T \to F\,T'$、$T' \to \times F\,T' \mid \varepsilon$、$F \to (E) \mid \textbf{id}$ 分析 `id + id * id`：

| 步骤 | 栈（顶在右） | 输入 | 动作 |
| --- | --- | --- | --- |
| 1 | `$ E` | `id + id * id $` | 展开 $E \to T E'$ |
| 2 | `$ E' T` | `id + id * id $` | 展开 $T \to F T'$ |
| 3 | `$ E' T' F` | `id + id * id $` | 展开 $F \to \textbf{id}$ |
| 4 | `$ E' T' id` | `id + id * id $` | 匹配 id |
| 5 | `$ E' T'` | `+ id * id $` | 展开 $T' \to \varepsilon$ |
| 6 | `$ E'` | `+ id * id $` | 展开 $E' \to + T E'$ |
| … | … | … | … |
| 末 | `$` | `$` | 接受 |

第 5 步是精髓：$T'$ 看到 `+` 不属于 FIRST(它)，但属于 FOLLOW($T'$)，于是**选 ε 候选放行**——一个「什么都没发生」的展开，让栈把位置让给 $E'$。<span class="marginnote">ε 展开在轨迹里表现为「栈顶非终结符被弹掉、什么都不压」。看起来像偷懒，实则是表里写好的合法决策——没有它，$T'$ 会永远堵在栈顶，输入永远无法前进。</span>

## 4 公式解析：分析器的不变式

表驱动分析器正确性的核心是一条**不变式（invariant）**：分析过程中，

$$\text{栈中的符号串} \Rightarrow_{lm}^* \text{输入中尚未消费的部分}$$

$$\text{且 } \text{已消费的输入} \cdot \text{由匹配弹出的终结符串} = \text{已分析前缀}$$

- **第一步，语义**：栈里装的是「输入剩下部分的最左句型」。栈顶的最左非终结符正是要展开的，这保证「查表展开」永远是在追踪一条**合法的**最左推导。
- **第二步，匹配守恒**：每当终结符从栈顶匹配输入并弹出，输入前进一格——两边同时消耗，绝不倒退，所以不存在回溯。
- **第三步，归纳**：初始时栈 `$ S`、输入 `w $`，$S \Rightarrow_{lm}^* w$ 显然成立；每一步展开或匹配都保持不变式；最终栈 `$`、输入 `$` 时，推导完成。

**这条不变式把「分析器正确」归结为「每一步都保持成立」**——正是它保证了线性时间、无回溯。若某步违反（表项为空），就是语法错误，分析器停在一个明确的位置上。

## 5 错误恢复：让分析器爬起来继续

分析器总会遇到坏输入。**错误恢复（error recovery）** 的目标是：报错后尽量跳到「安全点」继续分析，以便一次运行报出多个错误。表驱动分析器常用的恢复策略：

- **恐慌模式（panic mode）**：报错后，从栈顶弹出非终结符，直到找到 FOLLOW 集合含当前记号的符号，再继续。实现简单，误报可控。
- **短语级恢复**：根据文法做局部修正（插入/删除/替换记号），更精细但复杂。
- **错误产生式**：在文法里显式加入「错误产生式」，把常见错误结构当作合法结构处理，错误信息定制化。<span class="marginnote">真实编译器（如 GCC、Clang）几乎都用恐慌模式 + 大量手工同步逻辑：它们的目标不是「优雅修复」，而是「别因为一个错误就停止诊断」。多报一个错误，程序员就少一次编译往返。</span>

**辨析｜易错点：** 错误恢复不是「把错误程序改对」，而是「继续诊断」——恢复后分析出的树未必对应任何合法程序，所以恢复路径上的语义动作要小心触发。好编译器会把「错误点」单独标记，绝不据此生成代码。

## 7 思考与练习

**练习 1 走表分析**：用第十三节里那张预测表，手工走完 `id + id * id` 的完整分析轨迹（至少 12 步），每步记录「栈、输入、动作」三列——这是理解表驱动的最扎实训练。

**练习 2 逆序压栈**：解释为什么展开 `A → X_1 X_2 X_3` 时要「逆序压入 $X_3X_2X_1$」？若顺序压入，分析会怎样？用手工走一遍错误版本，观察卡在哪一步。

**练习 3 不变式验证**：在练习 1 的轨迹里，每步检查不变式「栈中符号串是未消费输入的最左句型」——至少验证三处，体会「不变式」不是空话。<span class="marginnote">「不变式检查」是理解算法的最高杠杆：每走一步都问「栈 + 输入」还满足不变式吗？满足，分析就合法；某一步违背，就是查表或压栈出了错。程序员调试分析器，就是找「哪一步破坏了不变式」。</span>

**练习 4 错误恢复**：给表驱动分析器实现「恐慌模式」错误恢复——报错时从栈顶弹出非终结符，直到当前记号属于它的 FOLLOW。用一个坏输入 `id + + id` 测试，观察报错后能否继续分析。

**练习 5 表 vs 递归下降**：用第十二节与第十三节的两种实现跑同一文法同一输入，对比「调用栈」与「记号栈」的轨迹——找出每一步的对应关系，写成一张对照表。

**练习 6 工程思考**：为什么手写编译器的作者常选「递归下降」而非「表驱动」？提示：错误信息质量、调试体验、对文法改动的容忍度——读一小段 Clang 或 rustc 的语法分析器代码找实证。

**延伸**：表驱动的「查表 → 动作」模式，在第八十七节「LLVM pass 流水线」里也有对应——pass 的调度表、指令选择表，都是「表驱动决策」。找一个实例，说说「用表表达决策」的通用价值。

## 8 小结

- **表驱动预测分析器** = 输入缓冲区 + 记号栈 + 分析表；四种动作：匹配、展开、接受、报错。
- 主循环按**栈顶类型**分流：终结符匹配，非终结符查表，`$` 相遇 `$` 接受。
- **逆序压栈**把「展开产生式」翻译成栈操作，恰好复现最左推导。
- 正确性由**不变式**保证：栈中符号串始终是「未消费输入」的最左句型，匹配双向消耗、永不回溯。
- **错误恢复**（恐慌模式、短语级、错误产生式）让分析器报错后继续；目标是多诊断而非修复。
