## 为什么从语法制导翻译方案开始

SDD 把属性规则写在产生式旁边，是一种**声明式**规范——「谁依赖谁」清楚，但没交代「动作代码何时执行」。编译器需要的是**命令式**的安排：分析到哪一步、就执行哪段动作，就像 Yacc 里 `{ `$$` = `$1` + `$3`; }` 那样嵌入规则中间。

**语法制导翻译方案（syntax-directed translation scheme, SDT）** 就是带**语义动作（semantic action）** 的上下文无关文法：把程序片段直接嵌入产生式右侧的任意位置，用花括号标记。它把「规则」变成「步骤」，是 SDD 到可执行分析器的最后一步翻译。<span class="marginnote">SDT 与 SDD 的关系：SDD 是「要算什么」（声明），SDT 是「什么时候算」（执行）。同一 SDD 可以对应多个 SDT——动作放的位置不同，执行时机就不同，正确性受限于依赖关系。</span>

## 1 动作嵌入：SDT 的形态

一条 SDT 产生式长这样：

$$E \to E_1 + T \ \{ \texttt{print}('+'); \}$$

或者更典型地带赋值：

$$E \to E_1 + T \ \{ E.\text{val} = E_1.\text{val} + T.\text{val};\ \}$$

花括号里的动作是**任意程序片段**：打印、赋值、查符号表、生成代码都行。动作可以出现在产生式右侧的任何位置——开头、中间、末尾——执行时机由「分析器到达该位置」决定。<span class="marginnote">「动作位置」是 SDT 与 SDD 的本质区别：SDD 的规则在归约完成后统一执行，SDT 的动作在<strong>分析推进的特定时刻</strong>执行——可能提前到归约之前（动作在产生式中间时）。这个「提前」是 SDT 表现力的来源，也是它易错的来源。</span>

## 2 动作的执行时机

在自顶向下分析中，SDT 动作在**展开产生式、从左到右匹配符号时**依次执行——动作位置即执行时机。在自底向上（LR）分析中，动作**附着在产生式右侧的某个位置**，分析器把「到达该位置」实现为：在该位置的左侧符号全部进栈后，插入一个「动作记号」到输入流/栈，遇到就执行。<span class="marginnote">LR 实现「中间动作」的机制：把动作变成产生式右侧的特殊符号（如 $M \to \varepsilon$，并给 $M$ 挂动作），归约到 $M$ 时执行。这样「中间动作」被降级成「右侧为空的归约」——Bison 的 `%empty` 中间动作就是这个技巧。</span>

一个例子——中缀到后缀的 SDT：

$$E \to E_1 + T \ \{ \texttt{print}('+'); \}, \qquad E \to T, \qquad T \to \textbf{id} \ \{ \texttt{print}(\textbf{id}.lexval); \}$$

对 `a+b+c`，自底向上分析中 `print(a)`、`print(b)` 随归约执行，`print(+)` 在 `E→E+T` 归约时执行——输出恰好是 `ab+c+`，即后缀表达式。**翻译与归约同步完成**。

## 3 后缀翻译方案：LR 的舒适区

当 SDD 是 S-属性定义时，存在一个**标准 SDT**：把所有动作放在产生式**末尾**——动作「综合属性计算」，随归约执行。这叫**后缀翻译方案（postfix translation scheme）**。

$$E \to E_1 + T \ \{ E.\text{val} = E_1.\text{val} + T.\text{val}; \}$$

因为 S-属性定义的所有属性都在归约时可算，末尾动作完全够用，且**与 LR 分析天然兼容**——归约发生时右侧符号的属性全在语义栈，直接取用。<span class="marginnote">Bison 的规则动作 `{ `$$` = `$1` + `$3`; }` 就是后缀动作。这也是为什么「S-属性定义 + 后缀 SDT」是最常见的组合：简单、正确、一趟完成。</span>

**辨析｜易错点：** 后缀方案不是「所有动作都必须放末尾」——是「S-属性定义的动作放末尾一定正确」。若 SDD 含继承属性，动作放末尾往往太迟（依赖值尚未算出），必须放到产生式中间——那时 SDT 就不再是后缀方案，而要求 L-属性之类的顺序保证。

## 4 公式解析：动作位置的正确性条件

动作执行时机由分析顺序决定，正确性归结为：**动作用到属性时，该属性必须已求值**。对 LR 分析 + 后缀动作：

$$\text{归约 } A \to \alpha \text{ 时} \quad \alpha \text{ 的全部属性已求值} \Rightarrow \text{末尾动作可直接计算 } A \text{ 的属性}$$

- **第一步，LR 的时序**：LR 分析归约时，$\alpha$ 各符号的子树已分析完毕，它们的属性（综合）已入语义栈。所以末尾动作取 `$1..`k` 是安全的。
- **第二步，继承属性的麻烦**：若 $A$ 有继承属性要在归约前传给子树，末尾动作来不及——必须在分析中更早的位置执行。这正是「中间动作」存在的理由。
- **第三步，判据**：检查每个动作使用的每个属性，若它在动作执行时刻尚未求值，就调整动作位置或改 SDD。这条「用时已求值」的检查，是 SDT 设计的唯一硬约束。

**「用时已求值」是把 SDD 翻译成 SDT 的总准则**——位置选对了，SDT 与 SDD 语义一致；选错了，编译结果就错。

## 5 SDT 的设计流程

实践中的设计路径：

1. 先写 SDD（声明「算什么」），尽量用 S-属性或 L-属性子类。
2. 判断分析类型：LR 选后缀动作；LL 选「动作按 L-属性顺序摆放」。
3. 有继承属性时，用中间动作/复制规则把它落到产生式内部。
4. 逐动作检查「用时已求值」，有违例就调位置或重写 SDD。

这套流程在后两节分别针对 LL 与 LR 具体展开。<span class="marginnote">「先声明后执行」的节奏贯穿整个第四篇：SDD 管语义正确，SDT 管时序正确，分析器管结构正确——三个层次各司其职，这是语法制导翻译几十年来长盛不衰的原因。</span>

## 7 思考与练习

**练习 1 中置动作**：对产生式 $E \to E_1 + T\ \{ \text{print}('+')\}$，说明「动作在产生式中间」与「在末尾」的执行时机差异——用 `a+b+c` 各跑一遍，看输出是否不同。

**练习 2 用时已求值**：对一个「动作要读 `E2` 的属性但 `E2` 还没分析」的 SDT，指出问题所在——并说明「该把动作挪到哪」才能满足判据。

**练习 3 后缀方案**：把一个 S-属性定义的 SDD 写成后缀 SDT（所有动作放末尾），用 LR 分析验证「归约时右侧属性已就绪」——这是最常见的正确组合。

**练习 4 ε 归约实现**：把产生式 $A \to \alpha\ M\ \beta$（$M \to \varepsilon$ 带动作）翻译成 Bison 的中间动作语法，编译观察「中间动作被改造成什么」。<span class="marginnote">「中间动作 = ε 归约」是 LR 实现中置动作的机制：动作被包进一个「右侧为空的产生式」，LR 分析到该位置时归约这个 ε 产生式、执行动作。所以「动作在中间」的时序保证 = 「归约到那个 ε 符号」的时序——一切都能用 LR 的既有机制解释。</span>

**练习 5 SDD vs SDT**：把同一 SDD 写成两个 SDT（一个把动作放前、一个放后），分析哪个正确哪个错——体会「声明与执行的分离」。

**练习 6 工具实验**：在 Bison 里写一个「带中间动作的翻译」，用 `--report=all` 观察生成的项集，找「动作记号」对应哪个 ε 归约。

**常见误区**：

- **误区一**：以为「SDT 就是 SDD」——SDD 声明「算什么」，SDT 声明「何时算」；同一 SDD 可对应多个 SDT。
- **误区二**：把「后缀动作」当成「永远正确」——只对 S-属性定义正确；含继承属性时放末尾太迟。
- **误区三**：忽视「用时已求值」——动作位置选错，编译结果就错。

**延伸**：SDT 的「动作位置 = 执行时机」与第七篇「递归下降的动作插入位置」、Bison 的「`$$` 赋值时机」是同一件事——把「动作时机」在 LL 与 LR 两种分析器里的实现方式写成对照表。

## 8 小结

- **SDT** = 带语义动作（花括号代码段）的上下文无关文法；动作嵌入产生式任意位置。
- **执行时机**由动作位置决定：LL 随展开执行，LR 靠「中间动作记号」把中置动作降级为 ε 归约。
- **后缀翻译方案**把 S-属性定义的动作放末尾，与 LR 归约天然同步——最常见的组合。
- 动作位置正确的判据是**「用时已求值」**：用到属性时它必须已算好，否则调位置或改 SDD。
- 设计流程：SDD → 选分析类型 → 摆放动作 → 逐动作检查时序。
