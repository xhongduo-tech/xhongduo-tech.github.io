# 引用计数及其循环引用问题

## 为什么从引用计数开始

追踪式 GC（标记-清扫）有个「不优雅」的点：它不知道垃圾何时产生，只能周期性扫全堆。**引用计数（reference counting）** 走了完全相反的路线：**每个对象实时记录「有多少引用指向我」**，计数归零的那一刻，对象立刻被回收——垃圾**即时**发现，无需全堆扫描。<span class="marginnote">「追踪式周期扫、引用计数即时清」是两条路线的哲学差异：追踪式是「事后清理」（定期找垃圾），引用计数是「实时更新」（每次引用变化就记账）。引用计数在 Python、Swift、Objective-C 里大量使用——因为它<strong>可预测</strong>、<strong>无停顿</strong>，对交互式系统特别友好。</span>

## 1 引用计数的机制

**引用计数（reference counting, RC）** 的规则：

- 每个对象头存一个**计数** `rc`：当前指向它的引用数。
- **创建**：对象初始 `rc = 1`（创建者持有）。
- **引用赋值** `x = y`：`y 指向的对象的 rc += 1`；`x` 原来指向的对象的 `rc -= 1`。
- **计数归零**：`rc == 0` 时回收对象，并**递归递减**它引用的所有对象的计数——因为被回收对象持有的引用也随之消失。

```c
// 伪码: x = y
rc(y)++;            // 新引用 +1
rc(x)--;            // 旧引用 -1
if (rc(x) == 0) free(x);   // 归零即回收
```

回收是**立即**的、**局部**的——只影响被回收对象及其引用链，不扫全堆。<span class="marginnote">「归零即回收」带来一个隐藏好处：<strong>确定性析构</strong>——`rc` 归零的瞬间，对象的析构函数立即执行。这正是 C++ 的 RAII、Swift/Python 的析构语义的来源；相比之下，追踪式 GC 的对象「何时析构」不确定（由 GC 轮次决定）。对持有外部资源（文件、锁）的对象，确定性很重要。</span>

## 2 引用计数的优缺点

**优点**：

- **无停顿（STW）**：回收是增量进行的——每个赋值操作顺带调整计数，不集中暂停。
- **即时回收**：垃圾一旦产生（计数归零）立刻回收，内存占用可预测。
- **局部性好**：操作只涉及被改引用的对象，不碰全堆。
- **实现简单**：计数增减 + 归零递归释放。

**缺点**：

- **每次赋值都要改计数**：读写计数的开销让每个引用操作变重。
- **循环引用泄漏**：两个对象互相引用，即使外部无引用，计数也不归零——**致命缺陷**（下节详述）。
- **递归释放可能深**：释放一个对象链式触发大量递归释放，可能栈溢出（延迟释放缓解）。

**辨析｜易错点：** 引用计数的「即时回收」是优点也是陷阱——它让「对象被回收」成为每次赋值都可能发生的事件，程序员（和编译器）必须处理「计数归零的回调」，这对性能敏感代码是额外负担。<span class="marginnote">Python 用「引用计数 + 分代追踪兜底」的组合：主回收靠计数（即时），循环引用靠追踪 GC 定期清理（兜底）。Swift 用「ARC + 弱引用」让程序员显式打破环。真实世界的 RC 几乎都配了一个「处理循环引用」的补充机制。</span>

## 3 循环引用问题：RC 的阿喀琉斯之踵

**循环引用（circular reference）**：对象 A 引用 B，B 引用 A——环上每个对象的计数都 ≥1，即使外部完全没有引用指向这个环：

```
外部 (无引用)
  ↓
  A ──→ B
  ↑     │
  └─────┘
```

- A 的 `rc = 1`（被 B 引用），B 的 `rc = 1`（被 A 引用）。
- 外部引用消失后，A、B 的计数仍是 1——**永不归零，永不回收**。
- 结果：**循环引用 = 内存泄漏**（对纯 RC）。

根因：RC 只能看到「局部」的引用关系（谁指向我），看不到「全局」的可达性——从根出发，A、B 组成的环整体不可达，但每个成员的局部计数非零。<span class="marginnote">「RC 只数指向、追踪式看连通」是循环引用问题的本质：环的不可达性是一个<strong>全局</strong>事实，而 RC 维护的是<strong>局部</strong>事实（每对象被指几次）。局部信息无法推出全局结论——这是 RC 无法摆脱循环引用的数学原因。追踪式 GC 从根出发遍历，天然「看穿」整个环。</span>

## 4 公式解析：RC 的守恒律

引用计数的正确性依赖一条**守恒律**：任意时刻，对象 $O$ 的计数等于「当前指向它的引用数」：

$$rc(O) = |\{ \text{引用 } r \mid r \text{ 当前指向 } O \}|$$

- **第一步，不变量**：每建立一个新引用，`rc` 加一；每删除一个引用，`rc` 减一——计数始终等于「活引用数」。
- **第二步，归零语义**：`rc(O) = 0` ⇔ 没有任何引用指向 O ⇔ O 不可达（在无环世界里）——所以「归零即回收」是正确的。
- **第三步，环的破绽**：环上每个对象有「环内引用」所以 `rc ≥ 1`，但整个环从根不可达——**局部计数非零，全局不可达**，守恒律在环上失效。

**守恒律在无环世界成立、在环上失效**——这就是 RC「看似完美、实则漏环」的数学根源。

## 5 解决循环引用的策略

RC 的循环引用不是死局，业界有数种解法：

- **弱引用（weak reference）**：不增加计数、不阻止回收的引用（Swift 的 `weak`、C++ 的 `weak_ptr`）——环里用弱引用打破环。程序员要判断「哪里该弱」。
- **追踪式兜底**：RC 为主，周期性跑一次追踪 GC 清理环（Python 的分代回收、Objective-C 的 Autorelease + 追踪补充）。
- **所有权分层**：Rust 用「所有权 + 借用」静态打破环（`Rc` + `Weak`），把「环需要弱引用」变成编译期规则。

**重点是**：RC 从未被「纯用」，真实语言都配补充机制——环是它的天然短板，必须外部补丁。<span class="marginnote">「环里用弱引用」是 RC 世界的程序员纪律：`weak` 声明即「这个引用不负责持有」——于是环上至少一个方向是弱引用，计数能归零。Swift、Rust 的设计都把「打破环」的责任部分交回程序员，这是 RC 哲学的延续：可预测性优先，复杂边界由人把握。</span>

## 6 小结

- **引用计数**：每对象实时记「指向我的引用数」，归零即回收——即时、局部、无 STW。
- 优点：**确定性析构、即时回收、实现简单**；缺点：每次赋值开销、**循环引用泄漏**、递归释放深。
- **循环引用**：环上计数永不归零，纯 RC 下成泄漏——根因是「局部计数无法推出全局不可达」。
- 守恒律 `rc = 活引用数` 在无环世界成立、在环上失效。
- 解法：**弱引用**、**追踪式兜底**、**所有权分层**——真实语言几乎都配补充机制。
