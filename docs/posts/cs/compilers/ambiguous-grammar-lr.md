## 为什么从二义文法在 LR 分析中的应用开始

前几节我们花了大力气消除二义、改写文法。但编译实践有一条反直觉的经验：**某些二义文法不但不该消除，反而是更好的选择。** 表达式文法 $E \to E+E \mid E\times E \mid (E) \mid \textbf{id}$ 只有 4 条产生式，而无二义的等价文法需要 6–8 条还带新非终结符。文法更小、分析树更浅、语义动作更直接。

关键问题变成了：分析器遇到「又移进又归约」的冲突时，**凭什么做选择？** 答案是把「优先级」「结合性」这两条语言设计决策，作为**独立的规则**交给分析器——不改文法，只改表。<span class="marginnote">这套做法把「语法结构」与「运算符语义」解耦：结构归文法管，优先级归声明管。Yacc/Bison 的 `%left`/`%right`/`%nonassoc` 声明就是这套思想的工业实现——几乎所有教科书和真实语言都这么干。</span>

## 1 为什么保留二义文法

对比两种写法：

**无二义（分层）**：
$$E \to E+T \mid T, \quad T \to T\times F \mid F, \quad F \to (E) \mid \textbf{id}$$

**二义（扁平）**：
$$E \to E+E \mid E\times E \mid (E) \mid \textbf{id}$$

扁平的优点：

- **产生式少**：语义动作（生成中间代码）只需挂在 $E$ 一个非终结符上，代码量小。
- **分析树浅**：树高 ≈ 运算符个数，而非分层后按优先级的深度；便于某些基于树的优化。
- **文法稳定**：新增运算符只加一条产生式 + 一行优先级声明，不必重构分层。

**辨析｜易错点：** 保留二义 ≠ 允许歧义存在。二义文法会产生冲突，冲突必须被「优先级 + 结合性」规则**完全消解**；若消解不完（表里还有冲突），分析器就还是二义的——那才是不可接受的。<span class="marginnote">「用二义文法但配上完整优先级声明」的分析器，行为上等价于某台 LR 分析器——它只是把「选哪棵树」的决定从文法挪到了表里。关键是声明必须覆盖全部冲突点。</span>

## 2 优先级与结合性消解移进-归约冲突

在 $E \to E+E$ 的文法上，状态「已读 $E+E$，输入是 `×`」时发生冲突：

- **移进** `×`：把 `E+E` 先归约成 $E$ 再乘——意味着 `+` 先算，`×` 后算。
- **归约** $E \to E+E$：意味着先算 `+`……等一下，归约 $E\to E+E$ 是在算 `+`，移进是在等 `×`。若 `×` 优先级高，应当**移进** `×`（让 `×` 更深、先算）；若 `+` 优先级高，应当**归约**。

规则：**运算符优先级比较——优先级高的那个优先被「内部化」**。若栈顶运算符（待归约的 $+$）优先级低于输入运算符（$×$），则移进，让 `×` 先算；反之归约。<span class="marginnote">一个记忆法：`a + b × c` 里你想先算 `×`，所以读到 `×` 时要「把它收进去」（移进），而不是「把 + 先结算掉」（归约）。移进 = 让后者更深 = 后者先算。</span>

**结合性**处理相同优先级的运算符：

- **左结合**：`a - b - c` 应算成 $(a-b)-c$，即读到第二个 `-` 时**归约**（先结算左边）。
- **右结合**：`a = b = c`（赋值）应算成 $a=(b=c)$，即读到第二个 `=` 时**移进**（让右边更深）。

## 3 悬空 else：一个无法用优先级解决的冲突

`if-then-else` 的移进-归约冲突发生在「已读 `if E then S`，输入是 `else`」：

- **移进** `else`：把 `else` 归给内层 `if`（就近匹配）。
- **归约** `S` 相关产生式：把内层 `if` 先结算，`else` 留给外层。

几乎所有语言要求**就近匹配**（内层优先）→ 选择**移进**。这个决策无法用「优先级表」表达（else 不是运算符），而是作为一条**默认规则**硬编码：**遇到移进-归约冲突且无优先级声明时，Yacc 默认偏向移进**。<span class="marginnote">这就是 Bison 的「shift 优先」默认：它恰好实现了悬空 else 就近匹配，但会把真正的二义也悄悄「修」掉——所以工具会打印冲突警告，提醒你「有冲突但我替你选了」。生产项目应当把警告数压到零，并显式声明意图。</span>

## 4 公式解析：优先级规则的动作选择

设输入运算符为 $a$、栈顶待归约运算符为 $b$、优先级函数为 $\text{prec}$，则冲突时：

$$\text{动作} = \begin{cases} \text{归约} & \text{若 } \text{prec}(b) > \text{prec}(a) \text{，或 } \text{prec}(b) = \text{prec}(a) \text{ 且 } b \text{ 左结合} \\ \text{移进} & \text{若 } \text{prec}(b) < \text{prec}(a) \text{，或 } \text{prec}(b) = \text{prec}(a) \text{ 且 } b \text{ 右结合} \\ \text{报错} & \text{若 } b, a \text{ 结合性为 nonassoc（如 C 的比较链）} \end{cases}$$

- **第一步，优先级比大小**：`×` 高于 `+` → `b=+`、`a=×` 时 `prec(b)<prec(a)` → 移进，`×` 更深、先算。
- **第二步，同级看结合性**：`-` 对 `-`，左结合 → 归约（先结算左边）；赋值 `=` 对 `=`，右结合 → 移进（右边深）。
- **第三步，nonassoc**：`a < b < c` 在 C 里非法——声明 nonassoc 后，同级遇到就报错，不选任何一边。

**这条规则把「运算符语义」变成查表动作**，二义文法的冲突从此有了唯一答案。

## 5 二义文法的工程注意事项

用二义文法 + 声明，有几个必须守住的纪律：

- **冲突警告视为错误**：Bison 报告冲突 = 你的声明没覆盖全，必须逐条核查，直到零冲突。
- **声明要精确到符号**：优先级声明挂在终结符上（`%left '+'`），且可用 `%prec` 给具体产生式临时指定优先级——处理一元负号、`if-else` 等特殊情况。
- **别用二义处理「非运算符结构」**：悬空 else、数组下标这类结构能用默认移进解决，但复杂的上下文敏感语法（C 的声明歧义）靠文法层解决更稳。<span class="marginnote">C 语言的「声明 vs 表达式」歧义是语法层无法用优先级解决的经典案例——它需要符号表信息（标识符是否是类型名），所以 C 分析器得在分析中查符号表。这是「二义」从结构走向语义的更深一层。</span>

## 7 思考与练习

**练习 1 优先级消解**：对 $E \to E+E \mid E \times E$，声明「$\times$ 高于 $+$、都左结合」，解释 `id + id × id` 的分析中「读到 `×` 时为何移进、读到 `+` 时为何归约」——用优先级规则逐点推演。

**练习 2 结合性**：把 `+` 改成右结合，重推 `id + id + id`——比较「左结合归约」与「右结合移进」两种决策对应的树。

**练习 3 悬空 else**：用 Bison（或手写推演）验证「默认移进」如何实现 else 就近匹配——再试着用「显式声明」覆盖默认行为，看两种做法的差异。

**练习 4 nonassoc**：声明 `<` 为 nonassoc，分析 `a < b < c`——为什么它报错而不选任何一边？提示：nonassoc 意味着「同优先级连续出现」本身就是非法。<span class="marginnote">nonassoc 是「拒绝结合」的第三种状态：左结合归约、右结合移进、nonassoc 报错。它的典型用途是 `a < b < c`——在 C 里这不是「左结合的比较」而是「类型错误」，nonassoc 让编译器在语法层就拒绝它。</span>

**练习 5 冲突清零纪律**：用 Bison 编译一个含二义表达式的文法，观察冲突警告；再逐条加 `%left`/`%right` 声明，直到警告清零——体会「警告清零」的工程纪律。

**练习 6 二义的边界**：构造一个「优先级声明也消解不了」的二义文法（如悬空 else 与某种嵌套的组合），说明为什么——提示：有些二义来自「文法结构」，而非「运算符优先级」。

**延伸**：二义文法 + 优先级声明 = 「把语义决策从文法挪到表」——联系第八十八节「LLVM 的 pass 表」与第七节「词法 DFA 表」，总结「表驱动决策」在编译器里出现的三个层次。

## 8 小结

- **保留二义文法**的收益：文法更小、树更浅、语义动作更集中；代价是冲突必须靠规则消解。
- **优先级**解决「不同运算符」的移进-归约冲突：高优先级被移进（更深、先算）。
- **结合性**解决「同优先级」：左结合归约、右结合移进；nonassoc 报错。
- **悬空 else**靠「默认移进」就近匹配，不靠优先级表。
- 工程纪律：**冲突警告清零**、声明覆盖全部冲突点、`%prec` 处理特殊产生式；结构语义（如 C 声明歧义）仍需符号表辅助。
