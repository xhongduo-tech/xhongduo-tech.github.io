## 为什么从执行模型开始

前两篇我们钻进编译器内部，把六道工序和两个基础设施看了个透。现在退后一步，问一个更根本的问题：**一段程序到底可以怎么「跑起来」？** 答案不只一种——可以先把整段翻译成机器码再执行（编译），可以边翻译边执行（解释），也可以先翻译成一种中间形态、再由虚拟机执行（混合）。这三种**执行模型（execution model）**决定了你写的代码在真实世界里的启动速度、运行速度、跨平台能力和静态检查的强度。

龙书在第 1 章就把编译器和解释器并排介绍，因为它们共享同一套「分析」工作。现代语言的现实是：几乎没有人再走「纯编译」或「纯解释」的极端，而是把两者拼成混合模型——Java 编成字节码再 JIT，Python 先编成字节码再解释，JavaScript 由 V8 边解释边即时编译。这一篇把三种活法的账算清楚，后面第十篇《JIT 编译》才有立足点。

## 1 编译执行：一次翻译，反复执行

**编译执行（compiled execution）**：程序在运行**之前**，由编译器一次性翻译成目标机器代码；运行时执行的是机器代码本身。<span class="marginnote">这里的「编译」指完整经历六道工序（第三级里你已经很熟的流程）；「目标机器代码」可以是直接执行的机器码，也可以像 C 那样先落到汇编、再经汇编器与链接器组装成可执行文件——那条流水线在《编译器的结构》里已见过。</span>

编译执行的收益，龙书概括得很直接：

- **执行速度快**：翻译只做一次，运行时没有任何额外的「理解」开销，机器码贴近硬件。
- **静态检查充分**：类型检查、未声明变量检查都在编译期完成，错误在运行前就暴露。
- **运行期开销极低**：不需要携带解释器，产物就是一份目标代码。

代价同样清晰：

- **启动慢**：每次改动源码都要重新编译，大型工程的一次完整编译可能以分钟计。
- **跨平台差**：机器码绑定指令集与操作系统，换平台必须重新编译（「write once, compile anywhere」）。
- **编译期占内存**：编译一个大文件，符号表、语法树、IR 都要驻留内存。

C、C++、Rust、Go 是典型代表。Rust 甚至把静态检查推向了极致——借用检查（borrow checker）在编译期就排除内存安全问题，这比任何运行时手段都更早、更彻底。

## 2 解释执行：边翻译边执行

**解释执行（interpreted execution）**：程序不预先整体翻译，而是由**解释器（interpreter）**一条一条地取出程序（或其某种内部表示）来分析并立即执行。

**辨析｜易错点：** 解释器**并没有省略分析**。它在执行每条语句之前，同样要做词法、语法、语义上的处理——只不过「分析完就立刻执行，不把分析结果固化成目标代码」。区别不在「做不做分析」，而在「分析结果是一次性落地为可复用代码，还是用完即弃」。这是初学者最普遍的误解：以为解释型语言「没有编译阶段」。恰恰相反，解释器内部时刻在跑着一个小型编译器。

纯解释执行的好处：

- **启动极快**：不需要先跑完整个编译流水线，打开就能执行。
- **跨平台**：只要目标平台有解释器，同一份源码直接运行。
- **交互友好**：适合 REPL、脚本、科学计算里的试错循环。

代价：

- **执行慢**：每一条语句每次执行都要重新分析一遍，循环体里的语句被反复「读解」。
- **缺少提前静态检查**：类型错误往往到运行那一行才暴露。
- **运行时开销大**：要一直带着解释器这份「软件」跑。

早期 BASIC、早期的 Lisp（1960 年麦卡锡的解释器）都是纯解释的典型。今天几乎没有大语言走纯源码解释的极端，而是普遍转向下一节讲的「先编译成中间形态再解释」。

## 3 公式解析：一个循环体里的成本账

编译与解释的性能差别，用一条在循环里的语句就能算清楚。设源程序里有一条语句 $S$，它处于一个执行 $n$ 次的循环中。

**编译执行**的总时间是：编译开销（只付一次）加上 $n$ 次机器码执行：

$$
T_{\text{编译}} = T_{\text{编译一次}} + n \cdot t_{\text{机器}}
$$

**解释执行**的总时间是：每一次执行都先分析、再执行：

$$
T_{\text{解释}} = n \cdot \big(t_{\text{分析}} + t_{\text{解释执行}}\big)
$$

逐步拆解：

- **第一步，看编译一侧**：$T_{\text{编译一次}}$ 与 $n$ 无关——不管循环跑一万次还是一亿次，编译都只做一次。这就是「一次翻译，反复执行」的数学形态：翻译成本被 $n$ 次执行**摊薄**。
- **第二步，看解释一侧**：$t_{\text{分析}}$ 被 $n$ 乘上了——循环体里的语句每次迭代都要重新走一遍分析。$n$ 越大，这一项的占比越重。
- **第三步，比较两者的主项**：当 $n$ 很大时，$T_{\text{编译}}$ 由 $n \cdot t_{\text{机器}}$ 主导，而 $t_{\text{机器}}$ 是硬件指令的执行时间；$T_{\text{解释}}$ 由 $n \cdot t_{\text{解释执行}}$ 主导，而解释执行每条语句通常要付出数百个机器周期的开销。两者差出**一个数量级甚至更多**，这就是「解释型慢、编译型快」的由来。
- **第四步，读出的洞察**：当 $n$ 很小时（脚本跑一次就结束），$T_{\text{编译一次}}$ 反而可能超过 $T_{\text{解释}}$ 的全部成本——**解释型适合小任务、编译型适合大循环**。而这个「临界点」正是 JIT（即时编译）的动机：运行时先解释，发现某段代码被反复执行（$n$ 很大），再把它编译成机器码——让大 $n$ 的部分吃编译红利，小 $n$ 的部分省启动开销。<span class="marginnote">这个公式还解释了为什么「预热（warm-up）」在 JVM、V8 里是真实存在的现象：程序刚启动时主要靠解释跑，热点被编译后性能才「热身」上来。理解预热，等于理解了一整类 JIT 调优话题的根。</span>

## 4 混合执行模型：Java 与 .NET 的先编后解

真正的现代语言几乎全是**混合执行模型（hybrid model）**：先用编译器把源码翻译成一种**字节码（bytecode）**——面向虚拟机（VM）的中间表示，再由虚拟机解释或即时编译执行。

Java 的路径最经典：

```text
源代码 (.java)  ── javac ──▶  字节码 (.class)  ── JVM ──▶  逐条解释 或 JIT 编译 ──▶  本机码
```

这里有个关键的**两级分离**：`javac` 把源码编成平台无关的字节码，这一步是「编译」；JVM 装载字节码后，可以选择逐条解释，也可以把热点方法即时编译成本机码。于是 Java 拿到了「一次编译，处处运行」——字节码是平台的，JVM 才是平台相关的；换平台只需换 JVM，不用改字节码。<span class="marginnote">`.class` 文件本质上是一种精心设计的 IR：它带符号表信息（常量池）、带可校验的类型信息（因此字节码可以做字节码校验器这道额外的安全检查）。把「可执行文件」换成「带元数据的字节码」，是语言实现史上的一步大棋。</span>

.NET（C# 等）走的是同一条路：C# 先编译成 IL（Intermediate Language，中间语言），再经 CLR（公共语言运行时）执行或 JIT 到本机码。**「编译到字节码 + 虚拟机运行时」**自此成为现代语言的默认配方：它同时获得了编译型的跨阶段检查与解释型的跨平台性。

## 5 Python 的真相：先编译，再解释

Python 是「混合模型」的另一个样本，却常常被误称为「纯解释型语言」。真相是：

```text
源码 (.py)  ── CPython 编译 ──▶  字节码 (.pyc)  ── CPython 虚拟机 ──▶  逐条解释执行
```

当你运行 `hello.py`，CPython **先把源码编译成字节码**（缓存到 `__pycache__/hello.pyc`），然后在 CPython 虚拟机里逐条解释执行这些字节码。<span class="marginnote">如果你曾经疑惑过 `__pycache__` 目录里那些 `.pyc` 文件是什么——那就是 Python 编译器产出的字节码缓存。只要源码没变，下次运行就直接加载 `.pyc`，跳过重新编译，这正是「翻译只做一次」思想在脚本语言里的落地。</span>

**辨析｜易错点：** 「Python 是解释型语言」这句话作为日常说法无伤大雅，但作为技术判断是错的。**「编译型 / 解释型」描述的是一种实现方式，不是语言本身的性质**——同一门语言既可以有编译器，也可以有解释器，甚至两种都有。C 语言同样存在解释器（如 picoc），Python 也一直有努力把源码直接编译成机器码的项目（如 Nuitka、Cython）。判断一个具体实现是编译还是解释，看它「分析之后是否把结果固化为可复用代码」，而不是看语言的名声。这个「语言 vs 实现」的区分，是第三级《程序设计语言》反复强调的元概念。

## 6 JavaScript 与 JIT：动态语言的性能突围

JavaScript 把混合模型推向了最激进的形态。它诞生于浏览器，天生要「下载即运行」，没有任何预编译环节；又要跑出足够快的性能，因为现代网页应用的计算量巨大。

V8 的路线是**分层**的：

1. 解析源码，构建 AST 与字节码；
2. **Ignition** 解释器先逐条执行字节码，保证「下载即能跑」；
3. 运行中做**热点探测（profiling）**：记录哪些函数被反复调用；
4. 对热点代码，交给 **TurboFan** JIT 编译器编译成优化的机器码；
5. 若运行时的假设（如「这个变量一直是整数」）被打破，则**去优化（deoptimize）**，退回解释执行，再用更通用的版本重新编译。

这一整套「解释兜底 + 热点编译 + 运行时假设 + 去优化」的机制，让一门动态语言逼近静态编译语言的性能。它把第 3 节那个公式用到了极致：**小 $n$ 的部分（冷代码）留在解释器，大 $n$ 的部分（热点）吃编译红利**。<span class="marginnote">「去优化」是 JIT 世界里最精妙也最昂贵的操作：被编译成机器码的热点代码发现「哦，这个值其实不是整数，是字符串」，只能把执行回滚到解释器、丢掉优化版本的假设。理解去优化，是理解 V8、JVM C2 等 JIT 引擎「性能为什么有时会突然掉下来」的钥匙——第十篇会专门展开。</span>

## 7 三张面孔，一张表

把三种执行模型放在一起对比，各自的「性格」一目了然：

| 维度 | 编译执行（C/C++/Rust） | 解释执行（早期 BASIC） | 混合：字节码+VM（Java/Python/JS） |
| --- | --- | --- | --- |
| 翻译时机 | 运行前，一次性 | 运行时，逐条 | 先编译成字节码，运行时再解释/JIT |
| 启动速度 | 慢（先编译） | 快 | 快（字节码已就绪） |
| 峰值性能 | 最高 | 低 | 中到高（JIT 可达接近编译） |
| 跨平台 | 差（需重新编译） | 好（有解释器即可） | 好（有 VM 即可） |
| 静态检查 | 最充分 | 几乎没有 | 部分（字节码层仍可校验） |
| 运行时开销 | 极低 | 高（反复分析） | 中（VM 本身有开销） |

读这张表，请抓住一条主线：**三种模型其实是同一条「翻译成本 vs 执行成本」坐标轴上的三个采样点**。纯编译把翻译成本一次付清、换取最低执行成本；纯解释把翻译成本分摊到每次执行；混合模型用「先翻译成轻量字节码、再按需重翻译成机器码」在两点间做精细调节。现代语言之所以都往混合靠拢，正是因为程序体量的现实：既有只跑一次的启动路径（要解释的快），又有反复执行的热点路径（要编译的快）。

## 8 小结

- 三种执行模型：**编译**（先全部翻译再执行）、**解释**（边翻译边执行）、**混合**（先编译成字节码，再由 VM 解释或 JIT）。
- **解释器并没有省略分析**，区别只在「分析结果是否固化为可复用代码」。
- 成本公式 $T_{\text{编译}} = T_{\text{编译一次}} + n \cdot t_{\text{机器}}$ 与 $T_{\text{解释}} = n \cdot (t_{\text{分析}} + t_{\text{解释执行}})$ 说明：循环越深，编译越划算；任务越短，解释越划算。
- Java/.NET/Python 都是「先编字节码、VM 再执行」的混合模型；**「编译型 / 解释型」是实现方式，不是语言性质**。
- V8 的分层执行（Ignition 解释 + TurboFan JIT + 去优化）是把成本公式用到极致的现代标本。

在下一节，我们将回望编译器自身的历史：**它怎么从「只扫一遍源码」的单遍编译器，演化成今天「来回扫很多遍」的多遍编译器**——这段演化史，正是本节所有权衡的时间展开。
