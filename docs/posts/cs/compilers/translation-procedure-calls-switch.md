## 为什么从过程调用翻译开始

第五篇的收尾篇讲两类「结构性」翻译：**过程调用**把控制权与数据交给另一段代码，**switch** 把多路分支组织成高效跳转。前者是运行时环境的入口（第六篇的主题），后者是控制流翻译的高阶形态。两者都是「把源语言的结构便利，翻译成机器层的显式动作」。<span class="marginnote">过程调用是编译器里「约定」最多的翻译：参数怎么放、返回地址记哪、寄存器谁保存——这些合起来叫<strong>调用约定（calling convention）</strong>，是前端 IR 与后端汇编之间最需要精确对齐的接口。理解三地址层的调用翻译，是理解真实调用约定的前奏。</span>

## 1 过程调用的三地址码序列

一次调用 `p(a1, a2, a3)` 在三地址码层展开为：

```
param a1
param a2
param a3
call p, 3
t1 = return_value      # 若有返回值
```

- **param x**：把实参 `x` 放入「传参位置」（可能是栈、寄存器或专用参数区）。
- **call p, n**：调用 `p`，`n` 是实参个数——被调函数要知道参数数量（变长参数尤其需要）。
- **返回**：`return y` 把 `y` 放入返回位置；调用后 `t1 = return_value` 取回。<span class="marginnote">`n` 这个「参数个数」对变长参数函数（如 `printf`）至关重要——被调方靠它决定从哪里开始取参数、以及如何对齐。三地址码里显式记录 n，把「参数数量」变成调用指令的一部分，是这段翻译的细节匠心。</span>

**语义前提**：过程调用翻译假设存在一个「运行时环境」——参数区、返回地址、活动记录（activation record）。这些正是第六篇要展开的存储组织；此处只需知道三地址码把「调用的意图」完整表达。

## 2 参数传递与返回值的细节

参数传递翻译涉及实参与形参的**对应**：

- **传值**：`param x` 传 `x` 的**值**——翻译成「把 x 拷贝到形参位置」。
- **传引用/传地址**：`param &x` 传 `x` 的**地址**——被调方通过地址读写原变量。
- **数组参数**：C 里传数组名 = 传首元素指针（数组退化为指针），`param base` 即首地址。

返回值类似：`return y` 把 `y` 放入固定位置（寄存器 `rax`/`$v0` 或调用约定的返回槽），调用点 `t1 = return_value` 取走。

**辨析｜易错点：** 「先求实参、再传」还是「边传边求」是顺序语义问题；多个 `param` 与求值顺序（从左到右/从右到左）在不同语言里不同。三地址码的 `param` 序列隐含了这个顺序，翻译时必须按语言语义排定，不能随缘。

## 3 switch 语句的两种翻译策略

`switch (E) { case c1: S1; case c2: S2; ... default: Sd }` 有两种典型实现：

**级联比较（cascade）**：

```
t = E
if t == c1 goto L1
if t == c2 goto L2
...
goto Ldefault
```

简单、占空间小，但 O(n) 次比较——分支多时慢。

**跳转表（jump table）**：

```
t = E
if t < c_low or t > c_high goto Ldefault
goto table[t - c_low]      # 下标取跳转目标
```

`table` 是「每个 case 值对应的目标地址表」，一次查表 O(1) 跳转。适用于 case 值**稠密**（连续或接近连续）的场合。<span class="marginnote">跳转表是「稀疏数组」思想的经典应用：用空间换时间。C 编译器对 `case 1..100` 的稠密 switch 生成跳转表，对稀疏 case（`1, 1000, 50000`）退回级联比较或二分——现代 LLVM/GCC 会结合两者做「比较-跳转树」。</span>

## 4 公式解析：跳转表的时间权衡

跳转表翻译的地址计算：

$$\text{addr} = \text{table\_base} + (E - c_{\min}) \times \text{指针宽}$$

- **第一步，范围检查**：先验 $E$ 在 $[c_{\min}, c_{\max}]$ 内，否则跳 `default`——越界先兜底。
- **第二步，偏移换算**：$E - c_{\min}$ 把值映射到 0 起始的区间，乘指针宽得表内字节偏移，加表基址得目标地址。
- **第三步，权衡**：表占 $\approx (c_{\max}-c_{\min}+1) \times \text{指针宽}$ 字节。区间大则表大；区间小则表高效。编译器据此在「级联」与「跳转表」间做选择——稠密用表、稀疏用级联。

**跳转表把「多路比较」变成「一次访存 + 一次跳转」**——这也是「用表驱动决策」思想在编译层的又一次胜利，与词法分析表、LR 分析表同源。

## 5 从翻译到运行时

过程调用翻译留下的「参数区、返回地址、活动记录」都是待实现的约定——它们的实现是第六篇的内容。此处先立住三点：

- **调用序列（call sequence）**：调用方与被调方分头执行的固定动作序列（压参数、跳转、压返回地址、建活动记录）。
- **活动记录（activation record）**：一次调用需要的全部运行期数据的存放区——参数、局部变量、临时、返回地址、保存的寄存器。
- **控制与数据两流**：控制流（call/return）与数据流（参数/返回值）在翻译层就被分开表达，运行时各司其职。

**重点是**：过程调用翻译是三地址码的「最后一块拼图」，它把编译器从「表达式世界」带入「过程世界」——下一节起，我们进入**运行时环境**，看这些约定如何落地为内存布局。<span class="marginnote">这也回答了「为什么第六篇紧接着第五篇」：三地址码里 `param`/`call`/`return` 只是「意图」，存储组织、活动记录、栈帧才是「实现」。没有运行时环境的支撑，调用翻译只是一纸空文。</span>

## 6 小结

- **过程调用**翻译为 `param` 序列 + `call p, n` + `return` + 取返回值；`n` 记录参数个数。
- 传参分**传值**（拷值）与**传引用**（传址）；数组参数按首地址传。求值顺序须按语言语义排定。
- **switch 两种策略**：级联比较（O(n)、省空间）与**跳转表**（O(1)、占空间），编译器按稠密度选型。
- 跳转表 = 范围检查 + 偏移换算 + 表寻址；「表驱动决策」思想与词法/LR 分析表同源。
- 过程调用翻译留下的**活动记录、调用序列**等约定，是第六篇运行时环境要实现的接口。
