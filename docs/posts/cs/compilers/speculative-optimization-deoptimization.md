## 为什么从推测优化与去优化开始

JIT 的独家优势是「看着跑再优化」——但它不只「看」，还**赌**：赌「这个变量还会是整数」、赌「这个分支还走老路」、赌「这个对象还是这个类」。赌对了，特化代码飞一样快；赌错了，就得**去优化（deoptimization）**——放弃特化代码，退回到保守但正确的执行路径。推测与去优化是 JIT 的「冒险与保险」：没有推测，动态语言快不起来；没有去优化，推测一出错程序就崩。<span class="marginnote">「推测优化」是对「运行时观察」的升级：观察不止用于「知道现状」，还用于「赌未来」。JIT 赌「常见类型持续常见」「热分支持续热」——赌注写在守护条件里，守护失败就反悔（去优化）。这套「大胆假设、小心验证」的机制，让动态语言的性能逼近静态语言。</span>

## 1 推测优化的思想

**推测优化（speculative optimization）**：基于**运行时观察**，对「未来会怎样」做出假设，按假设编译出特化代码：

**类型特化**：观察到 `x` 一直是 `int`，就编译「整数加法」的代码，假设 `x` 继续是 `int`。
**分支预测特化**：观察到某分支 99% 走真路径，就把真路径内联、把假路径变成「慢路径」。
**类层级特化**：观察到 `l` 总是 `ArrayList` 实例，就**内联虚方法**（直接调用 ArrayList 的实现），假设 `l` 还是 ArrayList。

每个推测都带着**守护（guard）**：进入特化代码前检查假设——`x 是 int`——检查失败就跳出。

**重点是**：推测优化的收益来自「赌对了的多数情况」；正确性由「守护 + 去优化」保证——赌错时安全撤退，而不是崩溃。<span class="marginnote">「类型特化」是推测优化的最大金矿：Java 的 `l.get(i)` 调用 `List.get` 虚方法，若运行时 l 总是 ArrayList，JIT 能把虚方法调用内联成直接调用——省掉动态分派。这正是「C++ 的虚函数开销」在 JIT 下可以被推测性消除的原因——运行时信息换了静态知识。</span>

## 2 去优化：反悔的机制

**去优化（deoptimization / bailout）**：守护条件失败时，把执行从「特化机器码」退回到「更保守的执行形态」——通常是**解释器**（或较低层的编译代码）。

去优化的流程：

1. **守护失败**：特化代码中的某个守护检查不通过。
2. **暂停**：记录当前状态（变量值、栈信息、程序计数器）。
3. **状态还原**：把特化代码里的「寄存器/栈布局」翻译回解释器的「逻辑状态」——需要**帧重映射（frame rewriting）**。
4. **切换**：从解释器的正确位置继续执行（相当于「从守卫失败的假设处重新开始，用保守方式」）。

**关键**：去优化不是「重新编译」，而是「回到解释器重跑这一段」——正确性由解释器兜底，速度损失只在赌错的那一次。<span class="marginnote">「帧重映射」是去优化的技术核心：特化代码的栈帧（寄存器分布、优化掉的值）与解释器的栈帧（完整变量）完全不同。去优化时要「翻译」这两种帧——把机器码帧里的值还原成解释器需要的逻辑变量。这个「帧翻译」是 JIT 里最精巧的部分之一。</span>

## 3 去优化的代价与权衡

**代价**：

守护检查本身有**开销**（每次进入特化代码都查一次）。
去优化瞬间**慢**：回解释器 + 帧重映射 + 重新解释。
频繁去优化 = **抖动（thrashing）**：不断「特化 → 赌错 → 去优化 → 再特化」，性能反而更差。

**权衡**：

守护要**便宜**：检查得足够快，别让「省下的动态分派」被「守护检查」吃掉。
去优化要**少见**：只在「假设大概率成立」时才推测——推测的概率估计来自 profiling。

**辨析｜易错点：** 去优化不是「错误」，是「赌输的保险」——它的存在让推测变得**安全**。没有去优化，编译器只能保守（不推测），动态语言就快不起来。理解「推测与去优化是一体两面」，就理解了 JIT 性能的核心机制。<span class="marginnote">「抖动」是推测优化最怕的病：`x` 一会儿是 int、一会儿是 string 的变量，特化代码反复赌输，每次赌输都付「去优化 + 重解释」的账——比不特化还慢。V8 等用「类型反馈 + 去优化计数」抑制抖动：去优化次数多了就放弃特化，回到通用代码。推测系统要有「记性」，不能无脑赌。</span>

## 4 公式解析：守护的收益条件

设特化代码每次执行省 $\Delta$（相对通用代码），守护检查成本 $c$，假设被满足的概率 $p$，去优化成本 $d$（每次赌输），则推测的期望收益：

$$\text{期望收益} = p \times \Delta - (1-p) \times d - c$$

$$\text{值得推测} \iff p \times \Delta > (1-p) \times d + c$$

- **第一步，赢的账**：$p$ 概率下，每次省 $\Delta$。
- **第二步，输的账**：$(1-p)$ 概率下去优化，付 $d$。
- **第三步，固定开销**：每次执行都付守护检查 $c$。
- **第四步，决策**：期望收益 > 0 才值得推测——概率估计（profiling）驱动决策。

**「期望收益 > 0」是推测的决策公式**——它不是「赌不赌」的哲学，而是「概率 × 收益 − 失败成本」的账本。

## 5 推测优化的边界与演进

**推测的边界**：

- **不可恢复的假设**：若推测基于「对象是 final 类」，而类加载器可能加载子类（JVM 的「类层级变化」）——需要**依赖追踪**：记录推测依赖了什么，依赖变化时使特化代码失效。
- **浮点假设**：推测「无 NaN/无舍入」能加速，但语言语义不允许——只能在特定模式（fast-math）下推测。
- **内联的推测**：内联虚方法后，若后续加载了新类打破假设，已编译的代码要**失效（invalidation）**。

**现代演进**：V8 的 TurboFan 用「**精确类型反馈 + 去优化 + 分层**」组合；JVM 的 C2 用「**依赖追踪 + 使失效**」。推测优化的工程核心是「**记录依赖、失效管理、去优化路径**」三件套。<span class="marginnote">「依赖追踪」是推测优化的进阶保险：C2 推测「B 没有子类」，会把这个假设<strong>登记</strong>；若运行时加载了 B 的子类，JVM 使所有依赖该假设的已编译代码失效，下次执行回到解释器重新编译。这套「推测 + 依赖登记 + 失效」比朴素去优化更进一步——它让「类层级变化」这种「几乎不发生但可能发生」的假设也敢赌。</span>

## 6 一个「推测 → 赌输 → 去优化」的完整走查

把推测、守护、去优化的全流程落在一个具体例子上。JS 代码 `result = x + 1`，profiling 显示 x 一直是整数。

- **推测编译**：JIT 为 `x + 1` 生成「整数加法」特化代码，并插入守护 `if (typeof x !== 'number') goto slowpath`。
- **赌对（99% 情况）**：x 是整数，守护通过，直接执行整数加法——快路径，一条加法指令。
- **赌输（1% 情况）**：某次 x 变成了字符串。守护失败，跳转 slowpath。
- **去优化**：记录当前状态（寄存器里的值、程序计数器），把特化栈帧**重映射**回解释器帧（整数 x 的寄存器值 → 解释器的变量槽），回解释器从 `x + 1` 重新解释执行——这次按字符串语义（字符串拼接），结果正确。
- **事后**：去优化计数 +1；若频繁赌输（如 x 在 int/string 间来回变），JIT 放弃该点的特化，永久走通用代码——抑制抖动。<span class="marginnote">「去优化计数」是推测系统的记性：赌输一次可以原谅（可能是一次性的异常），赌输多次就说明「这个假设不成立」——JIT 停止对该点特化。这个「用失败历史调整赌注」的机制，让推测系统能从错误中学习，避免反复付「赌输」的账。</span>

**要点**：这条链的每一步都在「赌错时保持正确」：守护是「随时能发现赌错」的哨兵，去优化是「赌错后的安全撤退」，去优化计数是「防止反复赌输」的记性。三者缺一，推测优化就不可靠。

**辨析｜易错点：** 去优化的「正确性」不是「重跑这段代码」这么简单——它必须保证「重跑起点与赌输点语义一致」：如果特化代码已经执行了部分副作用（如写了一个全局），重跑不能重复副作用。所以去优化通常发生在「副作用边界」（如方法调用点），而非任意指令处。

## 7 思考与练习

**练习 1 类型特化**：设 `x` 的 profile 显示「一直是 int」，说明 JIT 如何为 `x + 1` 生成「整数加法」特化代码——以及守护条件是什么（`x 是 int`）。

**练习 2 期望收益**：用公式「$p \times \Delta > (1-p) \times d + c$」算一个具体例子——设 $p=0.99$、$\Delta=5$、$d=100$、$c=1$，判断是否值得推测。

**练习 3 帧重映射**：解释去优化的「帧重映射」——特化代码的栈帧（寄存器分布）与解释器帧（完整变量）怎么互相翻译。

**练习 4 抖动**：构造一个「类型来回变」的变量场景，说明特化代码反复赌输、反复去优化——并讨论「去优化计数」如何抑制抖动。<span class="marginnote">「抖动 = 推测系统的振荡」：`x` 一会儿 int、一会儿 string，特化代码每次赌输都付「去优化 + 重解释」的账——比不特化还慢。V8 等用「类型反馈 + 去优化计数」：赌输多次就放弃特化，回到通用代码。推测系统要有记性，不能无脑赌。</span>

**练习 5 依赖追踪**：说明「类层级假设」的失效——C2 推测「B 无子类」后加载了子类，已编译代码如何被使失效（依赖登记 + invalidation）。

**练习 6 调研**：读 V8 的「TurboFan + 去优化」或 JVM 的「C2 依赖追踪」文档，找一个真实的「推测 + 去优化」流程——把本节的机制映射到工业实现。

**常见误区**：

- **误区一**：把「去优化」当「错误」——它是赌输的保险，没有它推测就不安全。
- **误区二**：以为「推测越多越好」——每次守护检查有成本、每次赌输有去优化账；期望收益 < 0 就不值得。
- **误区三**：忽略「不可恢复的假设」——类层级变化类假设需要依赖追踪，不是简单去优化能处理。

**延伸**：推测优化与第四级《计算机体系结构》的「分支预测」「推测执行」是同一思想——CPU 也「赌分支方向、赌错就冲刷流水线」。把「编译器的推测 + 去优化」与「CPU 的推测 + 冲刷」对比，找「赌 + 反悔」的共性。

## 8 小结

- **推测优化**基于运行时观察「赌未来」：类型特化、分支特化、类层级内联——按假设编译特化代码。
- 每个推测带**守护**：进入特化代码前检查假设。
- **去优化**是守护失败时的撤退：帧重映射 + 回解释器重跑——正确性由解释器兜底。
- 期望收益公式：期望收益 $> 0$ 才值得推测；频繁去优化是**抖动**，用反馈抑制。
- 进阶：**依赖追踪 + 失效**让「类层级变化」类假设也可推测；推测是 JIT 让动态语言变快的核心。
