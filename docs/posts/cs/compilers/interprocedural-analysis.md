## 为什么从过程间分析开始

前几节的分析都在**单个过程**内进行：函数被当成「黑盒」，调用点只关心「实参传进去、返回值出来」。但真实程序的性能瓶颈常跨函数——常量在函数间传递、循环不变计算藏在被调函数里、小函数频繁被调。**过程间分析（interprocedural analysis, IPA）** 跨过函数边界，把整个程序当作分析对象。<span class="marginnote">「过程内分析把函数当黑盒，过程间分析拆开黑盒」——这是 IPA 的根本转变。代价是分析对象从「一个 CFG」变成「一张调用图」：分析规模变大、函数间数据流要沿调用边传播、还有递归与间接调用的难题。收益则是对齐了「程序的真实运行」。</span>

## 1 从过程内到过程间

**过程内分析（intraprocedural）**：以单个函数的 CFG 为对象。安全假设——被调函数可能修改任何它「能看到」的东西，所以调用点会**杀死**很多信息（如 `f()` 之后，全局变量/被传地址的变量的可用表达式全失效）。

**过程间分析（interprocedural）**：把整个程序的所有函数连成**调用图（call graph）**，分析沿调用边传播信息。收益：

- 调用点不再「全杀」——知道 `f` 不改 `x`，`x` 的常量知识就能跨过调用。
- 常数可以跨函数传播、冗余可以跨函数消除。
- 小函数的优化（内联）需要过程间信息决定值不值。

**辨析｜易错点：** 过程间分析不是「更大号的单函数分析」——它要处理**递归**（调用图有环，需要不动点）、**间接调用**（函数指针、虚方法，调用图不唯一）、**别名**（同一内存被多个名字引用）。这些让 IPA 从「技术活」变成「研究级难题」。<span class="marginnote">「间接调用让调用图不确定」是 IPA 的头号难题：`p = cond ? f : g; p()`——编译期不知道调哪个，只能保守地「都考虑」，于是分析精度下降。现代编译器用「CHA/RTA/指针分析」层层收紧间接调用的候选集——精度与规模的永恒权衡。</span>

## 2 调用图：程序的函数级骨架

**调用图（call graph）**：结点是函数，边是「可能调用」关系——`f → g` 表示 `f` 可能调用 `g`。

```
   main
  /    \
 foo    bar
  \    /
   baz
```

调用图回答「谁可能调用谁」，是 IPA 的骨架。对**直接调用**（`f()` 名字已知），边唯一；对**间接调用**（函数指针、虚方法），边是「可能目标」的集合——用 CHA（类层次分析）或指针分析收紧。

**调用图的用途**：死函数检测（不被调用的函数）、内联候选识别、递归检测、以及所有过程间数据流的「传播通道」。<span class="marginnote">「调用图是程序的高层地图」：它把「函数级」的控制流画出来，与 CFG 的「指令级」互补。调试器、剖析器、IDE 的重构工具都用调用图——编译器的 IPA 只是它的重工业应用。</span>

## 3 过程间数据流分析

IPA 的数据流分析与过程内同构，只是信息在**调用边**上传播。关键问题是「跨过程的信息传递」：

- **沿调用进入（参数/返回值）**：实参的常量 → 形参；`return` 的值 → 调用点。这叫「**沿边传播（edge propagation）**」。
- **沿调用返回（上下文）**：被调函数的分析结果要**带上下文**——同一个函数被不同实参调用，结果不同。于是有「**上下文敏感（context-sensitive）**」分析：为每个「调用点 × 函数」分别分析，而不是为函数只分析一次。

**上下文敏感 vs 不敏感**：

- 不敏感：函数分析一次，结论对所有调用通用——快，但粗（不同实参混在一起）。
- 敏感：按调用上下文分别分析——准，但状态爆炸（同一函数 × 每个调用点）。

**辨析｜易错点：** 「函数分析一次」的不敏感分析在递归下是安全的（不动点），但精度差；敏感分析在递归下要小心「上下文无限」——通常限制上下文深度（k-限制）。<span class="marginnote">「上下文敏感」是 IPA 精度的分水岭：`add(1,2)` 与 `add(x,y)` 对 `add` 内部分析的结论完全不同，不敏感分析只能取两者的并集（保守但浪费）。现代编译器用「克隆 + 摘要」平衡：热函数克隆几份带上下文的副本，冷函数用不敏感摘要。</span>

## 4 公式解析：过程间传播的框架

设调用图 $C$、函数 $F$ 的入口/出口信息，过程间数据流的「沿边传播」：

$$\text{in}(F, c) = \text{translate}_{c}(\text{实参信息}), \qquad \text{out}(F, c) = \text{transfer}_{F}(\text{in}(F, c))$$

- **第一步，上下文绑定**：对每个调用点 $c$，把实参信息「翻译」成被调函数 $F$ 的形参信息——这是跨边界的「赋值」。
- **第二步，函数内转移**：在 $F$ 的 CFG 上跑过程内的数据流分析，从形参信息出发得到返回值/副作用信息。
- **第三步，回传调用点**：$F$ 的结果（返回值、修改的变量）再沿调用边**回传**给调用点——更新调用点之后的可用信息。

**「实参进入、结果回传」是过程间传播的完整闭环**——每个函数是黑盒，但黑盒的输入输出沿调用图精确对接。

## 5 过程间优化的经典应用

IPA 支撑一批高价值优化：

- **常量跨函数传播**：`f(42)` 里的 42 传入 `f` 的形参，`f` 内部用形参的地方可折叠。
- **内联（inlining）**：把小函数体直接插入调用点——减少调用开销，更让调用点的常量/别名知识「流进」函数体。IPA 决定「哪些函数值得内联」。
- **死函数消除**：调用图上不可达的函数整个删除。
- **副作用分析（mod/ref）**：知道 `f` 不改全局变量 `g`，则调用点之后 `g` 的常量知识得以保留。
- **尾调用优化、库函数内建**：把常见库调用替换为内建实现。

**重点是**：IPA 的价值在「跨边界的知识」，而代价是分析规模与间接调用的不确定性——现代编译器（LLVM 的 `-O3` 中的内联与 mod/ref 分析）在精度与编译时间之间精心权衡。<span class="marginnote">「内联」是 IPA 最亲民的成果：`-O3` 下编译器把 `add(a,b)` 的十几行体直接铺进调用点，省掉调用开销，还让 `a+b` 参与调用点的常量传播。内联决策（内联谁、内联多深）本身就是一个基于调用图的分析问题——IPA 环环相扣。</span>

## 7 思考与练习

**练习 1 画调用图**：给一个含 4 个函数的小程序（含递归与直接调用），画出调用图——标出「递归环」与「不可达函数」。

**练习 2 间接调用**：对 `p = cond ? f : g; p();`，说明调用图里 `p` 的目标为什么「不确定」——以及 CHA/指针分析如何收紧候选集。

**练习 3 沿边传播**：对 `int add(int a, int b) { return a + b; }` 与调用 `add(3, 4)`，写「实参进入 → 函数内转移 → 结果回传」的传播过程——标出「上下文绑定」在哪一步。

**练习 4 上下文敏感**：对比「不敏感（函数分析一次）」与「敏感（按调用点分别分析）」——用 `add(3,4)` 与 `add(x,y)` 两个调用点说明精度差异。<span class="marginnote">「上下文敏感是 IPA 精度的分水岭」：不敏感分析把 `add(3,4)` 与 `add(x,y)` 的结果混在一起（取并集），保守但浪费——`3+4=7` 能折叠的信息被 `x+y` 的未知性淹没。敏感分析按调用点分别算，能发现「这个调用点一定是 7」，但状态数随调用点爆炸——所以用「克隆 + 摘要」平衡。</span>

**练习 5 内联决策**：解释「内联谁」为什么需要 IPA——根据调用图的「调用频率 × 函数体大小 × 内联收益」做权衡，写一个决策准则。

**练习 6 mod/ref 分析**：若分析证明 `f` 不改全局 `g`，说明「调用点之后 g 的常量知识得以保留」——这与「保守假设 f 可能改一切」的对比。

**常见误区**：

- **误区一**：以为「IPA 只是更大的单函数分析」——它要处理递归（环）、间接调用（不确定）、别名，难度是研究级的。
- **误区二**：把「不敏感」当「永远够用」——不敏感快但粗，热代码需要敏感分析。
- **误区三**：忽视调用图的不确定——间接调用让「可能目标」成集合，分析精度随之下降。

**延伸**：调用图与第三级《软件工程》的「模块依赖图」、第四级《分布式系统》的「服务调用链」同构——把「调用图上的分析」（谁调用谁、环在哪）与「依赖图上的分析」对比，找「图结构支撑系统理解」的共性。

## 8 小结

- **过程间分析（IPA）** 跨过函数边界，把整个程序作为分析对象；过程内分析则把函数当黑盒。
- **调用图**是 IPA 的骨架：结点是函数、边是「可能调用」；间接调用用 CHA/指针分析收紧。
- 过程间数据流沿调用边传播：**实参进入、结果回传**；上下文敏感分析按调用点分别分析。
- 上下文敏感（准但贵）vs 不敏感（快但粗）；递归与间接调用是 IPA 的两大难题。
- IPA 支撑**跨函数常量传播、内联、死函数消除、mod/ref 分析**等高级优化。
