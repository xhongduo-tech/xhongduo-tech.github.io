## 为什么从目标机器模型开始

代码生成器不能对着真实 CPU 的所有怪癖编程——它需要一台**简化的目标机器模型**：几个寄存器、一组指令形态、一套寻址方式、一个代价函数。这台模型够「抽象」以便分析，够「精确」以便生成的代码能映射回真实机器。<span class="marginnote">「模型 vs 真实」的抽象是编译器后端的基本功：教科书用一台「带无限寄存器的抽象机」推导算法，再用「有限寄存器 + 溢出」逼近真实；现代后端用 LLVM 的 TableGen 描述指令集。理解模型，就是理解「抽象如何保留本质、简化噪音」。</span>

## 1 一台简单的目标机模型

龙书引入一台简洁抽象机，足以说明代码生成的全部核心机制：

**寄存器**：若干通用寄存器（如 `R0`、`R1`、`R2`），以及专门的 `SP`（栈指针）、`FP`（帧指针）。
**指令**：
运算：`OP dst, src`（如 `ADD`、`SUB`）
加载/存储：`LD` / `ST`
跳转：`JMP`、`JGT`
调用：`CALL`、`RET`、`HALT`
**寻址方式**：直接（`x`）、寄存器（`R`）、间接/索引（`*R`、`a(R)`）、常量（`#c`）。

这台模型「麻雀虽小，五脏俱全」——真实指令集的所有类别它都有，但每种只有一种形态。<span class="marginnote">「每种指令只有一种形态」是抽象机的设计取舍：真实 x86 有几十种寻址组合，抽象机只保留最核心的几种，让代码生成的算法可以专注「选什么指令」，而非淹没在寻址组合的海洋里。</span>

## 2 指令代价模型

**指令代价（instruction cost）** 是代码生成决策的量化依据。龙书用「代价 = 指令的内存字数量」这一朴素度量：

`OP R1, R2`：代价 1（操作码 + 两个寄存器字段，1 个字）。
`OP R1, x`：代价 2（`x` 是内存地址，需额外字）。
`OP R1, *R2`：代价 2（间接寻址）。
`OP R1, #c`：代价 2（常量 c 占一个字）。
`OP R1, a(R2)`：代价 3（基址+偏移，两个字放地址部分）。

**代价 ≈ 指令长度 ≈ 访存次数**——这个近似虽粗糙，却抓住了「代码质量」的实质：指令越长、访存越多，越慢越占空间。<span class="marginnote">现代代价模型更精细（执行周期、流水线冲突、缓存行为），但「代价驱动选择」的结构不变。理解字代价模型，就理解了「为什么要用寄存器」「为什么复杂寻址可能更省」——一切选择都是代价函数上的最优化。</span>

## 3 寻址模式：把访存压进一条指令

目标机的**寻址模式（addressing mode）** 决定了「一条指令能访问多复杂的地址」。常见的：

| 模式 | 形式 | 语义 | 代价 |
| --- | --- | --- | --- |
| 直接 | `x` | 内存地址 x 的内容 | 2 |
| 寄存器 | `R` | 寄存器内容 | 1 |
| 间接 | `*R` | 以 r 内容为地址的内存 | 2 |
| 常量 | `#c` | 立即数 c | 2 |
| 索引 | `a(R)` | 地址 a + r 内容 | 3 |

「索引寻址 `a(R)`」是数组访问的福音：`a[i]` 若下标 `i` 已在寄存器，一条 `LD R0, a(R1)` 完成——基址、下标、寻址全压进一条指令，省掉显式的加法。<span class="marginnote">寻址模式是「指令集设计影响编译器设计」的最佳例证：有索引寻址，数组访问的代码就短一截；没有，就得先生成地址（加法）再 `LD`。RISC 刻意减少寻址模式换取每周期一条指令，CISC 用复杂寻址换指令条数——模型的差异，就是代码生成的差异。</span>

## 4 公式解析：指令代价的构成

以 `ADD R0, a(R1)` 为例，指令代价是其操作数与寻址方式的函数：

$$\text{cost}(ADD\ \text{dst}, \text{src}) = 1 + \text{addr\_cost}(\text{src}), \qquad \text{addr\_cost}(r) = 0,\ \text{addr\_cost}(x) = 1,\ \text{addr\_cost}(a(r)) = 2$$

- **第一步，基准**：操作码 + 目标寄存器占 1 个字。
- **第二步，源操作数的地址字**：寄存器源不占额外字；内存/常量/索引源各占 1–2 个额外字。
- **第三步，选择依据**：把同一个 IR 的不同翻译方案各算一遍代价，选最小者——「代价函数 + 枚举」就是指令选择的机械过程。

**代价模型的精妙在于把「代码好坏」变成可计算的数**——于是优化有了目标函数，编译器可以系统地追求最优。

## 5 从模型到真实后端

教科书的抽象机如何通向真实编译器？

- **寄存器的数量**：抽象机假设足够，真实机器有限——第八篇的「寄存器分配」专门处理溢出。
- **指令形态**：真实指令集有更多变体，但「IR 模式 → 指令模式」的映射框架不变。
- **代价模型升级**：真实后端用周期模型 + 依赖图（调度），但「选最小代价覆盖」的骨架保留。

**重点是**：目标机器模型是代码生成器的「世界观」——模型定得好，算法就能在正确的抽象层工作；LLVM 的 Target 描述、GCC 的机器描述（`.md` 文件），都是「目标机模型」的工程化实现。<span class="marginnote">理解「模型驱动代码生成」的架构，对阅读现代后端至关重要：LLVM 的指令选择、寄存器分配、指令调度都是<strong>数据驱动</strong>的——换一台机器，换一套描述，编译器主体代码几乎不动。这就是「目标机模型」思想的工业巅峰。</span>

## 7 思考与练习

**练习 1 算代价**：给直接、寄存器、间接、常量、索引五种寻址各算指令代价（内存字数），排序——体会「寄存器最便宜、索引最贵」。

**练习 2 寻址翻译**：把 `a[i]`（下标 `i` 已在寄存器）翻译成抽象机指令——用索引寻址一条完成 vs 先用加法算地址，对比两条路线的指令条数与代价。

**练习 3 模型抽象**：解释「每种指令只有一种形态」的抽象机为什么够用——真实指令集几十种寻址，抽象机只留核心，算法专注「选什么」而非「组合」。

**练习 4 代价驱动选择**：对同一个 IR（如 `a = b + c`），列出目标机至少三种翻译，用代价模型选出「最优」——体会「代价函数 + 枚举 = 指令选择」。

**练习 5 RISC vs CISC**：对比「RISC 少寻址模式、多指令」与「CISC 复杂寻址、少指令」——用代价模型说明「模型差异如何影响代码生成」。

**练习 6 现代代价**：读一段 LLVM 的指令代价模型（或 CostModel 文档），找「周期/吞吐」的代价度量——对比教科书「内存字数」的简化。

**常见误区**：

- **误区一**：以为「指令越少越好」——指令条数 ≠ 代价，复杂寻址指令更贵（多内存字）。
- **误区二**：把「抽象机」当「真实机」——模型是简化，真实后端用周期模型。
- **误区三**：忽视寻址模式的作用——索引寻址让数组访问省掉显式加法，这是「指令集影响编译器」的核心。

**延伸**：目标机模型的「寄存器 + 寻址 + 代价」与第七篇「寄存器分配」「指令选择」是一体——把「模型」当作后端的「世界观」，说明「换机器 = 换模型描述」如何让主算法复用（LLVM TableGen 的架构动机）。

## 8 小结

- **目标机器模型** = 寄存器 + 指令形态 + 寻址方式 + 代价函数，是代码生成器对机器的抽象。
- 抽象机含运算、加载/存储、跳转、调用四类指令与五种寻址模式。
- **指令代价**用「内存字数量」度量：寄存器源最便宜，索引寻址最贵。
- 寻址模式把访存压进单条指令：索引寻址让数组访问省掉显式加法。
- 真实后端（LLVM/GCC）用**数据驱动的机器描述**，把「目标机模型」工程化，换机器不改主算法。
