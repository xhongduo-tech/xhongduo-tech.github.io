## 为什么从编译器的演化开始

前一篇末尾我们留下了一个悬念：单遍编译器「只扫一遍源码」，省时省内存，为什么今天的编译器几乎全是多遍的？要回答这个问题，只看原理是不够的——必须回到历史现场，看当时的**硬件约束**如何逼出了单遍设计，又是怎样的需求把这层设计撑破。

这一篇是「编译器概述」的收官：用一段编年史把前三篇的知识串成一条时间线。读完你会明白，**编译器结构不是工程师凭空设计的，而是被内存大小、机器速度、语言复杂度这些「时代约束」一层层塑形出来的**。而这种「理解约束如何塑造设计」的视角，正是从编译原理走向 LLVM、JIT 等现代专题时最需要的思维工具。<span class="marginnote">龙书第 1 章在讨论语言演化时反复出现一个主题：语言特征与编译技术互相成就——语言敢不敢加一个特性，取决于编译器能不能高效实现它；编译器能力长了，语言才有底气进化。</span>

## 1 先驱：编译器是怎么被「造」出来的

**编译器（compiler）**这个词，最早来自**葛丽丝 · 霍珀（Grace Hopper）**。1951—1952 年，她在 UNIVAC I 上完成了 **A-0 系统**——一个能把符号化的数学表达式「编译」成机器指令的程序。霍珀管这个过程叫 compilation（汇编成册），这个词从此沿用下来。<span class="marginnote">A-0 还不是现代意义上的「把高级语言翻译成机器语言」——它更像一个子程序链接器，把常用的数学子程序按符号调用装配起来。但「用程序来自动生成程序」这个思想，是霍珀最早钉下的旗帜。</span>

真正的里程碑是 **FORTRAN**。1954—1957 年，约翰 · 巴克斯（John Backus）领导的 IBM 团队开发了第一个功能完整的编译器。FORTRAN 编译器之所以伟大，在于它证明了**「编译出来的代码可以和手写汇编一样快」**——当时 IBM 704 上的 FORTRAN 程序性能只比手写汇编差一点点，这彻底打消了业界「自动翻译一定浪费性能」的怀疑。龙书特别提到，FORTRAN 团队花了 18 个人年才完成编译器，而当时用 FORTRAN 写科学计算的门槛已经低到普通工程师可用的程度——**用人力换生产力，是编译器最早的性价比论证**。

## 2 单遍编译：一条流水线上走完

早期硬件极其拮据：一台机器的内存可能只有几千字节，磁盘也慢得可怜。在这种约束下，**把源程序从头到尾读一遍就完成编译**成了最诱人的方案——**单遍编译（single-pass compilation）**：词法、语法、语义、代码生成被交织进同一次扫描，边读源码边出目标代码。

![单遍编译与多遍编译的对比](/images/compilers/compiler-evolution-1.svg)

单遍编译的收益是实打实的：**编译快、内存省**——不需要把整个程序的语法树或 IR 存下来再处理，读一段、生成一段、丢弃一段。但它逼出了一个硬约束：

**单遍可行 ⇔ 每个名字在使用之前必须已经声明。** 因为编译器「正在读第 $k$ 行」时，它手里只有前 $k-1$ 行的信息。如果一个名字在后面才声明、前面就用，单遍编译器根本来不及知道它的类型，无法生成正确的代码。<span class="marginnote">这个约束像一只看不见的手，塑造了早期语言的设计：Pascal 要求变量在过程开头集中声明、要求函数定义必须位于调用之前；C 也要求先声明后使用（原型机制正是为此）。「语言为什么这么设计」的答案，常常要回到编译器当时的单遍现实里去找。</span>

用一段最小代码体会这个约束。单遍编译器读到第 2 行 `print(x)` 时，它必须立刻知道 `x` 是什么类型、存放在哪：

```c
/* 单遍友好：先声明，后使用 */
int x = 1;
print(x);
```

而一旦把声明挪到使用之后：

```c
print(x);        /* 错误：x 尚未声明，单遍编译器此刻无从下手 */
int x = 1;
```

第二段代码在今天任何编译器里都能编译（多遍编译器可以先扫完整个文件，把符号表建齐，再回头生成代码），但在单遍编译器里就是死路。**「声明必须提前」不是语法美学的偏好，而是单遍编译器给语言开出的账单。**

## 3 多遍编译：让每一遍都更专注

当内存从几千字节涨到几兆、几十兆，另一个约束开始松绑：**编译器不再必须「一遍走完」，可以把中间表示完整地存下来，反复加工。** 于是**多遍编译（multi-pass compilation）**成为主流——每遍从头到尾读入上一遍的输出，完成一道相对专注的工序，再写出新的表示。

多遍带来的不是「慢的坏处」，而是「快的好处被重新分配」：

- **每遍更简单**：一遍只做一件事（比如这一遍只算活跃变量），正确性更容易保证，bug 更容易定位。
- **可以来回优化**：优化几乎天然是多遍的——做完一遍优化，代码结构变了，还能再优化一轮。单遍编译根本没机会「回头看」。
- **可以支持复杂语言**：有了完整的符号表与 IR，前向引用、跨函数优化、类型推断这些「需要全局信息」的语言特性才成为可能。

代价也在明处：**编译时间变长**（多次扫描多份数据）、**内存占用变大**（整棵 IR 驻留）。这正是前一篇讲的「阶段 vs 遍」的物理注脚——**阶段数由语言决定，遍数由工程权衡决定**。<span class="marginnote">现代编译器并非无脑多遍：Clang/GCC 都提供 `-O0`（少优化、少遍、编译快）到 `-O3`（多遍深度优化、编译慢）的档位；而 LLVM 的优化流水线则由上百个 pass 组成，每个 pass 做一件小事——这就是「多遍」在今天的极端形态，第十一篇再展开。</span>

## 4 公式解析：单遍的可行性条件

把「单遍编译」的约束写成一个判定条件，是理解整个演化的钥匙。设符号 $x$ 的声明位置为 $\mathrm{decl}(x)$、使用位置为 $\mathrm{use}(x)$（都按源码顺序编号），则：

$$
\text{单遍可行} \iff \forall x,\ \mathrm{decl}(x) < \mathrm{use}(x)
$$

逐步拆解：

- **第一步，看全称量词**：$\forall x$ 表示「对程序里的每一个名字」。单遍编译要成立，**所有**名字都得满足同一个条件——只要有一个名字「先用后声明」，整个单遍方案就崩塌。
- **第二步，看不等号的方向**：$\mathrm{decl}(x) < \mathrm{use}(x)$ 是「声明先于使用」。为什么必须严格小于？因为单遍编译器是「边读边生成」的：读到 $\mathrm{use}(x)$ 那一刻，它需要 $x$ 的类型来决定生成什么指令，而那个信息只存在于声明处——如果声明还在后面没读到，编译器就两手空空。
- **第三步，读「⟺」的等价意味**：这个条件是**充要**的。它同时指出了两条路：要么语言设计上强制「先声明后使用」（让条件恒真），要么放弃单遍、改为多遍（让条件不再必要）。**历史上两条路都走过**——Pascal、C 选前者，Algol 68、现代语言选后者。
- **第四步，读出演化的动力**：当语言越来越复杂、程序越来越长，「先声明后使用」的限制愈发难以接受，多遍编译就成了「拿编译时间换表达自由」的必然交易。**公式里的这个 $\mathrm{decl} < \mathrm{use}$，就是整部编译器演化史的轴心。**

## 5 一段编年史：语言与编译器的共同演化

把几个关键节点排成时间线，编译器与语言互相成就的脉络一目了然：

| 年份 | 事件 | 对编译器结构的意义 |
| --- | --- | --- |
| 1951–52 | 霍珀的 A-0 系统 | 开创「编译」概念：程序自动生成程序 |
| 1957 | IBM FORTRAN 编译器 | 第一个完整编译器，证明编译产出可达手写性能 |
| 1958–60 | Algol 58 / Algol 60 | 用 BNF 正式描述语言语法，语法分析从「手艺」变成「科学」 |
| 1960 | Lisp 解释器（麦卡锡） | 解释执行模型的先驱，直接催生后来的 JIT 思想 |
| 1960s–70s | 单遍编译盛行的年代 | 内存约束下，Pascal、C 等语言被迫「先声明后使用」 |
| 1970s | Smalltalk / Self | 动态语言兴起，埋下「运行时即时编译」的种子 |
| 1980s–90s | 多遍 + 优化编译器成熟 | GCC 等开源编译器把多遍流水线变成标配 |
| 1990s | Java 字节码 | 「编译到平台无关字节码 + VM 执行」的混合模型成为主流 |
| 2000s | LLVM 的诞生 | IR 被正式化为前后端契约，pass 流水线成为一门工程学问 |

其中 Algol 60 值得单独说一句。它用 **BNF（巴科斯范式，Backus–Naur Form）** 正式描述了整门语言的语法——这是第一次「用一套形式语言来定义另一门语言」。由此，语法分析从「每个编译器作者的手艺」变成了「可以系统研究的科学」：文法、推导、二义性这些概念成为可计算的对象。今天你学的上下文无关文法，正是从 Algol 60 这次「语言的自描述」里长出来的。用形式化描述取代直觉约定，是编译原理成为一门学科的分水岭。

这条时间线还藏着三个反复出现的主题：

- **约束驱动结构**：内存小 → 单遍；内存够 → 多遍；运行时灵活 → 解释/JIT。编译器结构每一次大改，都是因为某个约束松绑或某个需求出现。
- **语言与编译器互为因果**：没有 BNF，就没有系统的语法分析理论；没有多遍编译器，就没有今天的类型推断、跨函数优化。语言敢提出什么需求，取决于编译技术接不接得住。
- **性能是永恒的议题**：从 FORTRAN「证明编译不慢」，到 V8「证明动态语言也能快」，半个多世纪里编译器最核心的使命始终没变——**让程序在目标机器上跑得足够好**。

## 6 现代：多遍之上的新生态

今天，单遍/多遍的争论早已尘埃落定——现代编译器几乎都是「多遍 + 深度优化」，但单遍的思想并没有消失，而是换了一种身份存续：**解释器对语句的逐条处理，本质上就是一种「以语句为单位的单遍」**；而 IDE 里「改一行代码，马上重新分析」的增量编译，追求的也是单遍的即时性。<span class="marginnote">增量编译与语言服务器（LSP）在概念上是单遍精神在现代的重生：不重新编译整个工程，只重编译被改动的那个函数——「最小化需要扫描的范围」这个目标，和当年单遍编译器「尽量少扫」的思路一脉相承。详见第十一篇 LLVM 与现代开发工具链。</span>

更深远的变化是：编译器的职责从「生产可执行文件」扩展到「服务」——把语法树、符号表、诊断信息作为 API 提供给 IDE、静态分析工具、格式化器。Clang 的 `-fsyntax-only`、各种 language server，都是把「编译器当作基础设施」来用。这条演化线告诉我们：**编译器没有过时，它只是从「一次性的翻译工具」长成了「语言生态的底座」。** 后面第十二篇《手写一个玩具编译器》，你会在动手时重新体会这一切——从单遍的简单开始，再一步步引入符号表、IR、优化，复刻这段跨越半个世纪的演化。

**辨析｜易错点：** 别把「单遍」与「快」划等号。单遍在**特定历史约束**（内存极小、无需深度优化）下是快的；但到了现代，一个不做优化、只扫一遍的编译器，产出代码可能比多遍优化后的慢十倍以上——「编译快」换来的是「执行慢」。所以单遍今天几乎只在**解释器逐条执行**与**增量编译**的形态里存续：它们的「一遍」都是为即时反馈服务的。**判断一个编译器「好不好」，永远要问它服务的场景是「编译要快」还是「跑起来要快」。**

## 7 小结

- **编译器**一词源自霍珀的 A-0 系统；第一个完整编译器是 1957 年的 IBM FORTRAN。
- **单遍编译**：一次扫描完成所有工序，编译快、内存省，但要求 $\mathrm{decl}(x) < \mathrm{use}(x)$——每个名字先声明后使用。
- **多遍编译**：把中间表示存下来反复加工，每遍更专注，能优化、能支持复杂语言，代价是编译时间与内存。
- 可行性条件 $\forall x,\ \mathrm{decl}(x) < \mathrm{use}(x)$ 是编译演化的轴心——单遍时语言被迫让步，多遍后语言重获自由。
- 语言与编译器**互为因果**：BNF 催生了系统化语法分析，多遍编译催生了类型推断与全局优化。
- 今天编译器从「翻译工具」长成「语言生态底座」：多遍流水线、JIT、增量编译、LSP 服务并存，单遍的即时性精神也在其中延续。
