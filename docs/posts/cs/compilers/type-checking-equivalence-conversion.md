## 为什么从类型检查开始

有了类型表达式这门「类型语言」，接下来要让类型发挥作用：**程序里每个表达式是否类型正确？** 这由**类型检查（type checking）** 回答——它像一台「类型级」的求值器，沿语法树为每个表达式算出类型，并验证运算两侧的类型相容。<span class="marginnote">类型检查与「普通求值」惊人相似：普通求值算「值」，类型检查算「类型」——两者都从叶子向上综合。区别是值随输入变化，类型在编译期就确定。把「类型」想象成一种运行在编译期的求值，类型检查的一切都顺理成章。</span>

## 1 类型综合：沿着语法树算类型

**类型综合（type synthesis）**：从叶子的类型，沿语法树算出每个表达式的类型。用 SDL（属性规则）表达：

$$\begin{aligned} E &\to E_1 + E_2 & E.type &= \text{if } E_1.type = E_2.type = \text{integer then integer else type\_error} \\ E &\to E_1 = E_2 & E.type &= \text{if } E_1.type = E_2.type \text{ then boolean else type\_error} \\ E &\to \textbf{id} & E.type &= \text{lookup}(\textbf{id}.name) \\ E &\to \textbf{num} & E.type &= \text{integer} \end{aligned}$$

每个「if 条件成立」的检查就是一次类型检查；条件不成立则报 `type_error`。编译器逐规则执行，一旦某处得到 `type_error`，就报告类型错误。<span class="marginnote">`E.type` 是综合属性（子算父），所以类型检查可以随 LR 归约一趟完成。这与求值「一趟分析、一趟翻译」完全同构——类型检查是翻译的「合法版本」。</span>

错误定位的粒度取决于规则分得有多细——规则越细（如 `+` 只接受两个 integer），错误消息越精确（「右操作数应为 integer，实为 float」）。这是「规则分解程度」决定「诊断质量」的例子，与词法、语法阶段的错误处理一脉相承：想让用户少猜一次，就要把规则拆得更细。

## 2 类型等价：同一性的判定

检查「两侧类型相同」时，得先定义「相同」：

**结构等价（structural equivalence）**：展开类型名后，类型表达式结构相同。`array(10, integer)` 与 `array(10, integer)` 结构等价；`pointer(real)` 与 `pointer(real)` 结构等价。
**名字等价（name equivalence）**：类型必须「同一个定义」才等价。Pascal 中 `link` 与 `node`（结构相同但定义不同）名字等价不成立。

**辨析｜易错点：** 结构等价下 `T1` 和 `T2` 可互赋，名字等价下不行——两个 `struct` 定义即使字段相同，名字等价也视为不同类型（防止误混）。多数语言取混合：基本类型结构等价、复合类型名字等价。递归类型（如 `list`）只能靠名字等价或指针间接层打破无限展开——结构等价会陷入无穷递归。<span class="marginnote">C 语言是混合策略的典型：两个字段相同的 `struct` 名字不等价（不可互赋），但 `typedef` 的别名与原类型结构等价。而 Ada 默认名字等价、Pascal 混用——「等价策略」是语言设计里的一个隐性开关，影响程序能写什么。</span>

## 3 类型转换：让不相等的类型相遇

程序里 `1.0 + 2` 是合法的吗？多数语言说合法，但要**转换**：把 `2` 提升为 `float` 再相加。编译器要做两件事：

**强制转换（coercion）**：静默把 `int` 变 `float`（「隐式转换」，规则由语言定）。
**cast（显式转换）**：程序员写的显式转换，通常更「危险」（可截断、可重解释），编译器只做类型标注与宽度检查。

转换在 IR 里体现为**一条显式的转换指令**：`t = (float) i`（把整数 `i` 提升为浮点）。类型检查规则要为转换生成这条指令——「转换后的类型」进入后续计算。<span class="marginnote">隐式转换是类型系统里的「暗流」：`1 / 2` 在 C 里得 0（整数除法）、`1.0 / 2` 得 0.5——同一个 `/`，操作数类型不同，语义不同。类型检查必须把转换显式化，否则后端无法生成正确的指令。</span>

## 4 公式解析：类型检查规则的形式化

类型检查规则可写成「推导规则」（类似逻辑推理）：

$$\frac{E_1 : \text{integer},\ E_2 : \text{integer}}{E_1 + E_2 : \text{integer}}$$

- **第一步，读法**：横线上方是**前提**（各子表达式的类型），横线下方是**结论**（整个表达式的类型）。`E : T` 读作「E 有类型 T」。
- **第二步，匹配**：编译器递归地「匹配」每个表达式的推导规则——先算子类型（前提），再判结论，不符则类型错误。
- **第三步，转换并入**：规则可加「前提带转换」的变体，如 `E_1 : int`、`E_2 : float` 时结论是 `float`，并生成 `int \to float` 转换指令。

**这套「类型推导规则」就是类型检查器的「文法」**——类型检查器本身是一个小型语言处理程序，处理的对象是类型而非字符。

## 5 类型检查的进阶应用

类型检查不只是「加减法的合法性」：

- **重载决议**：运算符 `+` 对 `int`、`float`、`string`（连接）有不同实现，类型检查选哪个——按参数类型匹配重载集。
- **函数调用的形实结合**：实参类型与形参类型逐一比对，不匹配则报错或转换。
- **指针与数组的关系**：C 里数组名退化为首元素指针，类型检查得实现这条退化规则。
- **安全类型系统**：Rust 的借用检查、Haskell 的参多态，都在基础类型检查之上加层——理解基础，才能理解这些进阶。

**重点是**：类型检查的「检查 + 转换」机制是编译器的通用骨架，从简单语言到 Haskell 的类型推导，都是它的扩展。<span class="marginnote">Haskell 的「类型推导」（HM 算法）能自动算出表达式的类型而不必显式标注——它是类型综合的高级形态：不只从叶子向上综合，还能「从上向下推断」并生成多态类型。理解基础类型检查，是理解 HM 推断的第一步。</span>

## 6 类型系统设计中的等价策略对照

「等价策略」是语言设计里的一个隐性开关，值得列一张对照表看清它的影响：

| 策略 | 判定依据 | 代表语言 | 典型后果 |
| --- | --- | --- | --- |
| 结构等价 | 展开后类型表达式相同 | Modula-2、多数纯理论系统 | 结构相同的不同定义可互赋，灵活但易误用 |
| 名字等价 | 必须同一个类型定义 | Ada（默认）、Java 引用类型 | 更严格，防止「长得像就混用」 |
| 混合策略 | 基本类型结构等价、复合类型名字等价 | C、Pascal（部分） | 兼顾灵活与安全，工业最常见 |

**一个具体例子**：C 里 `typedef int Age;` 与 `int` 结构等价——`Age` 只是别名，可以互相赋值；而两个字段相同的 `struct {int x; int y;}` 若定义两次，名字等价下不可互赋。这种「别名宽松、结构严格」的取舍，正是混合策略的日常体验。<span class="marginnote">值得注意：<strong>typedef 别名的宽松是刻意的</strong>——它让「可读性别名」不影响类型系统，而「结构类型」需要真正的身份。若把别名也做成名字等价，写 `typedef int Age;` 就还得写一堆转换函数，别名机制便失去了意义。</span>

**强制转换链**：`1.0f + 2` 的隐式转换不是一步到位，而是按语言的「提升阶梯」逐级走：`int → long → float → double`。类型检查器对每个二元运算检查「两侧能否提升到公共类型」，能则生成一串转换指令、不能则报错。C 的整数提升、Java 的数值提升，都是这张阶梯的具体实例。

**数值算例**：`5 / 2` 在 C 里是整数除法得 2，而 `5.0 / 2` 先把 2 提升为 double 再做浮点除法得 2.5——同一个斜杠，两侧类型不同，编译出的 DIV 指令族也不同。这就是「类型检查生成转换指令」的直接后果：类型决定了机器码的形态，而不是相反的「运行期猜类型」。

**辨析｜易错点：** 强制转换与 cast 不是一回事：强制是编译器按规则静默插入，cast 是程序员显式写出。一个常见的坑是「把强制转换当成无条件安全」——`long` 转 `int` 会截断高位，`double` 转 `float` 会丢精度，这类「变窄转换」（narrowing）在多数语言里不是静默允许的，需要显式 cast 或告警。

## 7 思考与练习

**练习 1 类型综合**：对表达式 `1 + 2.0 * 3`（设所有常量均为 `float`），用类型综合规则逐结点算出类型，标出每一步的「前提检查」与「隐式转换」点。

**练习 2 结构 vs 名字等价**：设 `S1 = struct{int x; int y;}`、`S2 = struct{int x; int y;}`——分别用结构等价与名字等价判定 `S1` 与 `S2` 是否等价，各说一个「允许/拒绝」的程序例子。

**练习 3 递归类型**：解释 `list` 为什么只能用「名字等价 + 指针」打破无限展开——若强行结构等价，展开 `list` 会发生什么？

**练习 4 强制转换**：对 `1 / 2` 与 `1.0 / 2`，写出类型检查后生成的转换指令（`int→float` 等），说明两者的除法指令为何不同。<span class="marginnote">这是「类型决定指令」的直接演示：`1 / 2` 是整数除法（得 0），`1.0 / 2` 把 1.0 保持、把 2 提升为 float 后做浮点除法（得 0.5）——类型检查把「提升」变成显式指令，后端才知道选哪条 DIV。</span>

**练习 5 推导规则匹配**：把「类型推导规则」（前提/结论形式）应用到 `x + 1`（设所有字面量均为 `integer`），写出完整的推导树——每条规则如何「匹配」表达式的每个子结构。

**练习 6 类型错误定位**：给一段含类型错误的小程序，运行你的类型检查器（或 gcc -Wall），观察错误信息指向的位置与消息——体会「类型检查器在哪里停」。

**常见误区**：

- **误区一**：以为 `1 / 2` 与 `1.0 / 2` 是「同一个 `/` 运算」——类型检查后它们生成完全不同的指令。
- **误区二**：把结构等价与名字等价混用——多数语言「基本类型结构等价、复合类型名字等价」，混用会做出错误的等价判定。
- **误区三**：忘记转换生成指令——类型检查不只是「通过/报错」，它还要产出 `int→float` 这样的显式转换指令。

**延伸**：类型推导规则与第 4 篇「属性文法」的依赖图同构——类型是综合属性，推导规则是语义规则。把「类型检查 = 类型级求值」这句话展开：普通求值算值、类型检查算类型，两者共享后序遍历的骨架。

## 8 小结

- **类型检查** = 沿语法树「算类型」（类型综合），每个运算检查两侧相容，不符则报 `type_error`。
- **类型等价**：结构等价（展开比较）vs 名字等价（同一性）；多数语言混合，递归类型靠指针/名字等价。
- **类型转换**：隐式强制（提升）生成显式转换指令，显式 cast 只标注+宽度检查。
- 类型检查规则可形式化为**推导规则**（前提/结论），编译器像处理文法一样匹配规则。
- 进阶应用：重载决议、形实结合、数组退化、多态类型——都是基础机制的组合扩展。
- **等价策略对照**：结构/名字/混合三种策略是语言设计的隐性开关；变窄转换（long→int）不是无条件安全。
