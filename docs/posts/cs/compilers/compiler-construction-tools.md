## 为什么从构造工具开始

前四篇我们把编译器「解剖」了一遍：结构、阶段、符号表、执行模型。解剖之后，一个更实际的问题浮上来：**编译器本身是怎么写出来的？** 用手写每一个字符的扫描、每一条递归下降、每一张 LR 分析表，还是让工具替我们把脏活干完？

答案是：现代编译器几乎都是「半自动」的。词法分析器由 Lex 类工具生成，语法分析器由 Yacc 类工具生成，而这批工具背后的共同思想——**用语言描述语言，再自动生成识别器**——正是「编译器-编译器（compiler-compiler）」这个词的来历。这一篇是第一篇的收官：它把前四篇的「蓝图」变成「工厂」，也为你理解后面第二、三篇为什么那样设计埋下伏笔。<span class="marginnote">龙书 §1.5 把构造工具分为五类：扫描器生成器、语法分析器生成器、语法制导翻译工具、自动代码生成器、数据流分析框架。今天先抓两条主线：词法工具与语法工具，其余顺带点名。</span>

## 1 手写还是生成：一个根本的取舍

先问一个最朴素的问题：一个编译器里，哪些部分值得手写，哪些部分应该交给工具？

**判断标准只有一个——「正则的、机械的、重复的工作交给工具；启发式的、需要全局判断的工作留给人」。** 依据这个标准，编译器前端的分工几乎是现成的：

- **词法分析**：字符分组是纯机械的正则识别，交给**扫描器生成器（scanner generator）**，如 Lex / Flex。
- **语法分析**：文法的分析表构造是算法化的，交给**语法分析器生成器（parser generator）**，如 Yacc / Bison。
- **语义分析与优化**：类型检查、作用域、数据流分析高度依赖程序语义与全局信息，工具难以通用化，基本**手写**。
- **代码生成与寄存器分配**：有**自动代码生成器**与优化框架可用，但现代生产级编译器（GCC、LLVM）几乎都手工实现，因为性能收益巨大。

**辨析｜易错点：** 「工具生成」不等于「质量差」。早期观点认为生成的词法分析器比手写的慢，但现代 Flex 生成的扫描器基于手工优化的 DFA 表，与手写代码性能相当甚至更快。工具的真正代价是**生成代码晦涩难读**，调试时要跨过一层抽象。<span class="marginnote">这正是一对经典矛盾：手写代码可读、可控、便于内联优化；生成代码规范、更新快、不易手误。工程上常做「混合」：手写核心识别逻辑，用工具生成表驱动部分。LLVM 里的 TableGen 就是「用描述语言生成 C++ 表与代码」的现代版本，见本专题第十一篇《LLVM 架构》。</span>

## 2 三类核心工具：词法、语法与语法制导翻译

### 扫描器生成器：Lex / Flex

**扫描器生成器**的输入是一组**正则定义（regular definition）**——描述记号长什么样；输出是一个**确定有限自动机（DFA）**驱动的词法分析器。它的原理正是第二篇的核心内容：正则表达式 → NFA → DFA → 最小化，最终变成一张「状态 × 输入」的转移表。

```
正则定义（输入）      →  Lex 工具      →  词法分析器（C 代码）
letter  → [A-Za-z_]         │                   │
digit   → [0-9]             │                   │
id      → letter (letter|digit)*
```

`letter`、`digit` 是缩写，`id` 由它们拼接而成——这种「用名字指代子表达式」的写法就是**正则定义**，下一课《正则表达式与正则定义》会系统展开。正则语言与有限自动机的严格定义，则见第二级《离散数学》与《计算复杂性理论》的对应章节。<span class="marginnote">「正则表达式 → 自动机 → 可执行扫描器」这条流水线，正是正则表达式引擎（grep、JavaScript 的 RegExp）的内核。你每天都在用的 `/\d+/` 背后，就是编译器构造工具第一次学会的本领。</span>

### 语法分析器生成器：Yacc / Bison

**语法分析器生成器**的输入是**上下文无关文法（CFG）**加上每条文法的**语义动作（semantic action）**；输出是一个 LR 分析器。Yacc 的名字「Yet Another Compiler-Compiler」——又一个编译器-编译器——直接宣布了自己的野心：给它文法，它还你一个能识别该语言的编译器骨架。

下面是一段经典的 Yacc 输入，为四则运算表达式构造一个求值器：

```yacc
%token NUMBER
%left '+' '-'
%left '*' '/'

%%
expr   : expr '+' term   { $$ = $1 + $3; }
       | term            { $$ = $1; }
       ;
term   : term '*' factor { $$ = $1 * $3; }
       | factor          { $$ = $1; }
       ;
factor : '(' expr ')'    { $$ = $2; }
       | NUMBER          { $$ = $1; }
       ;
%%
```

`%%` 之前是声明区（记号、结合性），之间是文法规则，之后是辅助函数。每条规则末尾的花括号就是**语义动作**——`$1`、`$3` 引用右部第 1、3 个文法符号的值，`$$` 是归约后左部符号的值。**Yacc 负责把文法变成能识别该语言的表驱动分析器，语义动作则把「识别出什么结构」翻译成「算出什么结果」。** 这就是「语法制导翻译」的第一次真身亮相。

### 语法制导翻译工具与编译器-编译器

**语法制导翻译（syntax-directed translation）**：在语法分析的同时，根据文法规则执行语义动作，从而把源语言翻译成目标表示——这是 Knuth 在 1968 年经典论文《The Semantics of Context-Free Languages》中奠定的思想，也是 Yacc 类工具的理论内核。

**编译器-编译器（compiler-compiler）**，字面上是「编译器的编译器」：给它一门语言的形式描述（词法 + 文法 + 语义动作），它生成一个能把该语言翻译成目标表示的编译器。<span class="marginnote">「compiler-compiler」一词由 Brooker 与 Morris 在 1960 年代提出，泛指从语言规范自动生成编译器的系统；Yacc 是其中最成功的实现，以至于今天说「编译器-编译器」，基本就是指 Yacc/Bison 这类语法分析器生成器。</span>**易错点：** 「编译器-编译器」并不「编译」编译器，而是**生成**编译器——它生产的是源代码（分析器程序），不是编译器的机器码。

## 3 公式解析：一条推导，理解「文法 → 识别器」

工具的核心承诺是：给定文法 $G$，自动构造一个识别语言 $L(G)$ 的分析器。为了看清这个承诺，我们亲手「识别」一次输入。用上面的表达式文法 $G$：

$$
E \to E + T \mid T, \qquad T \to T \times F \mid F, \qquad F \to (E) \mid \mathbf{id}
$$

问：字符串 $\mathbf{id} + \mathbf{id} \times \mathbf{id}$ 是否属于 $L(G)$？我们给出它的最左推导——每一步都替换当前最左的非终结符：

$$
E \;\Rightarrow\; E + T \;\Rightarrow\; T + T \;\Rightarrow\; F + T \;\Rightarrow\; \mathbf{id} + T \;\Rightarrow\; \mathbf{id} + T \times F
$$
$$
\;\Rightarrow\; \mathbf{id} + F \times F \;\Rightarrow\; \mathbf{id} + \mathbf{id} \times F \;\Rightarrow\; \mathbf{id} + \mathbf{id} \times \mathbf{id}
$$

拆解这条推导的四个要点：

- **每一步替换的是哪个符号？** 永远是最左的非终结符。最左推导与 LR 分析器的移进-归约过程一一对应——Yacc 生成的正是「从右向左读这条推导」的分析器。
- **文法如何保证运算优先级？** $E \to E+T$ 允许加法，而 $T$ 的出现强制乘号先于加号归约。**优先级由文法的层次结构编码，不由分析器决定**——这是「文法即规范」的直观体现。
- **推导存在 ⇒ 字符串属于语言。** 找到一个最左推导就证明了 $L(G)$ 的成员资格；而分析器做的正是**反向**工作：给定字符串，构造这条推导。
- **工具的价值**：没有 Yacc，你要为每个文法手写分析表；有了 Yacc，你只需描述文法与语义动作，**表构造与分析器骨架自动完成**。

## 4 工具如何建造工具：自举与 T 型图

生成器本身也是程序，谁来写生成器？答案是「层层递进」的工程智慧：最早用汇编手写，然后用简单编译器编译更复杂的语言，再用该语言写自己的编译器。

**自举（bootstrapping）**：用语言 X 写的 X 编译器，去编译它自己。这是「鸡生蛋」问题的经典解法，GCC、rustc、Go 都是自举的。<span class="marginnote">自举的起点常被称为「第一阶段编译器」：先用另一种已存在的语言实现一个最小的 X 编译器，之后所有版本的 X 编译器都用 X 写、由这个最小的编译器启动编译。</span>

**T 型图（T-diagram）** 是描述跨语言编译的紧凑记号：横杠上方是「源语言 → 目标语言」，横杠下方是实现语言。例如「用 C 实现的、把 Pascal 编译成 MIPS 机器码的编译器」写作：

$$
\boxed{\;\text{Pascal} \to \text{MIPS}\; \atop \;\text{实现于 C}\;}
$$

多个 T 型图可以**组合**：只要 A 编译器由语言 M 实现、能产生语言 B 的代码，B 编译器又由 B 实现、能产生语言 C 的代码，就能推出「A 到 C」的编译器。**T 型图组合是「编译器如何跨平台、如何自举」的严格推理工具**，也是这门课里真正用到「图」的地方——这里的图是工程图，而非算法图。

## 5 小结

- **编译器构造工具**把「正则的、机械的、重复的」工作自动化：词法用扫描器生成器，语法用分析器生成器，语义与优化多手写。
- **Lex / Flex** 输入正则定义、输出 DFA 驱动的词法分析器；**Yacc / Bison** 输入文法 + 语义动作、输出 LR 分析器。
- **编译器-编译器**（Yacc）接收语言规范、生成编译器骨架，**不**“编译”编译器本身。
- 一条**最左推导** $E \Rightarrow^* \mathbf{id} + \mathbf{id} \times \mathbf{id}$ 证明了字符串属于 $L(G)$，也对应 LR 分析器的移进-归约过程——**文法层次结构编码了优先级**。
- 编译器自身的构造依赖**自举**与 **T 型图组合**，这是「用工具造工具」的终极形式。
