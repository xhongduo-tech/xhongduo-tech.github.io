## 为什么从符号表与错误处理开始

上一篇把六道工序走了一遍。细心的读者会发现，六道工序都在反复追问两个问题：**「这个名字是谁？」**——词法分析要问、语义分析要问、代码生成也要问；**「出错了怎么办？」**——任何一道工序都会遇到不合法的输入。

第一个问题的答案，装在一张贯穿全编译器的表里——**符号表（symbol table）**；第二个问题的答案，是编译器的**错误处理（error handling）**机制。龙书把符号表称为「编译器中所有阶段都要访问的中心数据结构」，把错误处理称为「使编译器真正可用」的品质。这一篇就把这两个「配角」请到台前——它们不是某一道工序，而是**六道工序共用的基础设施**。

## 1 符号表：编译器的记忆

**符号表（symbol table）**：一张把**标识符（identifier）**映射到其**属性（attribute）**的数据结构。属性里记录着这个名字的一切档案：类型、作用域、声明的存储位置、参数个数与类型、如果是函数则包括返回值类型等。<span class="marginnote">「符号」这个词沿用自编译理论：词法分析输出的记号里，标识符类的每个具体名字就是一个「符号」。把名字装进表里、再查表取出属性——这个「插入-查找」模式，正是第四篇《语法制导翻译》与第五篇《类型检查》反复依赖的基本操作。</span>

各阶段与符号表的关系各不相同：

- **词法分析**：把每个标识符首次出现时记入表中，用一个整数（符号表下标）作为它的「身份证」。
- **语义分析**：查表得到类型，做类型检查；把类型、存储布局等信息写回表中。
- **中间代码生成与代码生成**：从表中读出每个名字的存储位置，把符号名翻译成「地址」。

**辨析｜易错点：** 符号表不是「语义分析阶段的私有数据」。龙书强调它是所有阶段的共享结构——词法阶段可能只关心「这个名字是否出现过」，语义阶段关心「它的类型」，代码生成阶段关心「它存放在哪」。**同一个名字，不同阶段读出的属性不同**；这正说明符号表是一个「逐步被填充」的活文档，而不是一次建好就冻结的静态表。

符号表本身的实现也要讲究效率：一个大型程序动辄几十万个标识符，插入与查找必须近乎常数时间，因此常用**哈希表**；需要按序输出（比如生成调试信息）时则用**二叉搜索树**。哈希表的分桶、装载因子这些话题，正是第三级《数据结构》里讲的实现细节——编译器的符号表就是它们最典型的应用场景。

## 2 作用域：名字的领土

名字不是全局唯一的。「声明在哪个范围里可见」由**作用域（scope）**决定。现代语言几乎都是**词法作用域（lexical scope）**：一个名字的可见范围由源码的文本结构决定——声明所在的块（block），以及嵌套在它内部的块。

看下面这段块结构代码（示意，用 C 风格）：

```c
{
  int x = 1;            // 外层 x
  {
    int x = 2;          // 内层 x，遮蔽（shadow）外层
    print(x);           // 读出 2
  }
  print(x);             // 读出 1
}
```

内层声明了同名的 `x`，它在内层遮蔽了外层的 `x`，内层结束后外层 `x` 重新可见。**名字解析遵循「最近嵌套规则（closest nested rule）」**：查找一个名字时，从当前最内层作用域向外逐层找，第一个命中者胜出。<span class="marginnote">「遮蔽」不是错误，而是语言刻意提供的表达力：一个循环里的临时变量 `i` 不需要为避让外层 `i` 而改名。真正的问题是「重复声明」——在<strong>同一层</strong>声明两个同名变量才是错误，编译器必须能区分「同层冲突」与「跨层遮蔽」，这是符号表作用域设计要解决的核心难题。</span>

这一条规则能走多远？想想递归、想想函数里再定义函数（嵌套函数），作用域就成了一棵**嵌套的树**。如何高效地维护这棵树上的「当前可见层」，是下一节数据结构设计的直接动力。

## 3 符号表的两类实现

维护嵌套作用域，主要有两类经典实现，龙书第 1 章与第 2 章都作了对比。

**实现 A：每个作用域一张表 + 表栈。** 进入一个块时，新建一张表压入栈顶；离开时弹出。查找名字时从栈顶往下逐表查。优点：离开作用域时整张表直接丢弃，实现简单；缺点：查一次名可能要翻多张表。

**实现 B：单张表 + 作用域编号。** 所有名字都放进同一张表，每条记录附带它所属的作用域编号；再用一个「当前作用域栈」辅助删除。进入块时压入新编号，离开时把属于该编号的记录删掉。优点：单表结构简单、缓存友好；缺点：删除操作要按编号清理，比弹栈麻烦。

两类实现的对比如下：

| 维度 | A：每作用域一表 + 表栈 | B：单表 + 作用域编号 |
| --- | --- | --- |
| 进入作用域 | 新建表、压栈 | 压入新编号 |
| 离开作用域 | 直接弹栈丢弃 | 按编号删除记录 |
| 查找 | 栈顶向下逐表查 | 单表直接查（再核对可见性） |
| 实现难度 | 低 | 中 |
| 现代编译器使用 | 常见（AST 式的分析常配套使用） | 常见（符号表集中管理） |

无论哪种实现，它们都只回答一个问题：**此刻可见的名字集合是什么？** 这是语义分析做「未声明变量」检查的物理基础。

## 4 公式解析：名字解析的查找链

「最近嵌套规则」可以写成一个递归的查找过程。设当前作用域为 $S_1$，它的外层依次是 $S_2, S_3, \ldots, S_k$（最外层是全局作用域），那么名字 $x$ 的解析过程是：

$$
\mathrm{resolve}(x) =
\begin{cases}
\mathrm{attr}(x) & \text{若 } x \text{ 在 } S_1 \text{ 中有记录}\\
\mathrm{resolve}(x) & \text{从 } S_2 \text{ 继续（递归）}\\
\text{「未声明」错误} & \text{若 } x \text{ 在 } S_1,\ldots,S_k \text{ 中都无记录}
\end{cases}
$$

逐步拆解：

- **第一步，看分支结构**：这个式子表达了「从里向外」的次序。$S_1$ 是最内层，最先被检查；只有 $S_1$ 里没有 $x$，才轮到 $S_2$；逐层外推，直到全局作用域 $S_k$。
- **第二步，看「第一个命中者胜出」**：一旦在某层 $S_i$ 找到 $x$ 的记录，立即返回它的属性 $\mathrm{attr}(x)$，**不再向外继续**。这正是「遮蔽」的数学表达——内层有 `x`，外层那个同名 `x` 就永远不被读到。
- **第三步，看出错路径**：如果一路查到最外层都没有，就报「未声明标识符」。注意错误发生在**名字解析时**，而「是否真的用错」要等类型检查阶段再定——先解决「它存在吗」，再解决「它的类型对吗」，两个问题分层处理。

用一个具体例子验证。对第 2 节的代码，在 `print(x)` 处查找 `x`：

| 查找次序 | 作用域 | 是否命中 | 结果 |
| --- | --- | --- | --- |
| 1 | 内层块 | 命中 `x = 2` | 返回内层 `x`，遮蔽生效 |
| 2（外层 `print` 处） | 外层块 | 命中 `x = 1` | 返回外层 `x` |

**这条查找链是符号表全部作用域逻辑的浓缩**——无论用「表栈」还是「作用域编号」实现，物理上的查找路径都和这个公式一一对应。

## 5 错误处理：编译器必须优雅地失败

写完符号表，另一半基础设施是错误处理。龙书反复强调一个观点：**只有对合法程序进行正确翻译是不够的，编译器还必须把不合法的程序以清晰的诊断信息拒之门外。**

先给错误分类。按「在哪个阶段被发现」分：

- **词法错误**：非法字符、字符串未闭合。通常在词法分析时就地发现。
- **语法错误**：括号不匹配、缺分号、表达式残缺。语法分析阶段发现，最常见。
- **语义错误**：未声明变量、类型不匹配、重复声明。语义分析阶段发现。
- **逻辑错误**：程序语法语义都合法，但跑起来结果不对。**编译器永远无法检出**——它根本不在编译期的管辖内。

**辨析｜易错点：** 前三种是「编译期错误」，第四种是「运行期错误」，混为一谈是初学者的通病。编译器的职责止步于第三种：能抓住的编译期错误尽量抓住，抓不住的逻辑错误只能留给调试器。这也是为什么「静态检查能多早做就多早做」成为语言设计的信条——一个类型错误如果在编译期就暴露，省下的调试时间是巨大的。

错误处理的目标不是「发现一个错误就停」，而是三件事：**准确**（定位要准，别报错报在错误行）、**可读**（诊断信息让人一眼看懂）、**延续**（报完一个错误还能继续找下一个）。最后一条最微妙：一个 `(` 不匹配，可能让语法分析器认为整个文件都错了——如何处理「一个错误引发的连锁误报」，就是下一节的内容。

## 6 语法错误的恢复策略

语法错误是「延续性」矛盾最尖锐的地方。龙书给出四种经典的**错误恢复（error recovery）**策略，按能力与复杂度递进：

- **恐慌模式（panic mode）**：发现错误后，不断丢弃输入记号，直到遇到一组「同步记号」——通常是分号 `;` 或 `}`，因为它们是语句或块的天然边界。此后假定语法已「同步」，从新起点继续分析。<span class="marginnote">恐慌模式实现最简单、最常被采用，代价是可能漏报它跳过的那些记号里的错误。它像「大扫除」：把错误周围清空，让状态回到一个可信的锚点。编译器「宁可漏报不可乱报」的保守哲学在此体现。</span>
- **错误产生式（error production）**：在文法里显式加入专门描述「常见错误形态」的产生式，比如「表达式缺右操作数」这种高频错误。分析器遇到这种形态时，照常构建语法树，但树里带上一个错误结点，同时生成诊断。优点：能精确定位、还能继续建树；代价：要为每种常见错误手写产生式。
- **局部修正（local correction）**：对错误处做最小改动（插入一个缺失的分号、删除一个多余的逗号、把 `,` 替换成 `;`），然后尝试继续。许多 IDE 的「自动修复」提示就源于这类策略的灵感。
- **全局修正（global correction）**：从理论上找「使整个程序改动最少的修正」，代价高昂，实际编译器极少完整实现，但它是研究编译器「最小错误代价」的经典问题。

**辨析｜易错点：** 恐慌模式与错误产生式的分工不要混淆。恐慌模式是「放弃这一片、跳到同步点」；错误产生式是「把错误当成一种允许的结构来处理」。前者是**跳过**，后者是**吸收**。设计一个语法分析器时，通常混合使用：用错误产生式吸收高频小错，用恐慌模式兜底处理大崩塌。

## 7 语义错误与诊断的艺术

语义错误没有「同步点」可以依托，处理策略更依赖符号表的状态：检查「未声明变量」时，一旦查无此名，就报错并把该名**临时登记**为一种「占位类型」，让分析继续推进，避免同一个名字被反复报错。这类「报一次、止痛药」的细节，是编译器工程经验的体现。<span class="marginnote">现代编译器在此基础上又往前走了一大步：Clang 会提示「你是否想用 fahr 而不是 fahre？」——根据编辑距离在符号表里找「最接近的候选名」。这正是符号表（作为全部已知名字的集合）在错误诊断中的第二次用武之地。自然语言处理里的「拼写纠正」，与这里的「相近标识符提示」，用的是同一套编辑距离思想。</span>

诊断信息的质量可以这样衡量：一个新手面对报错，是「秒懂」还是「一脸茫然」。好的诊断信息包含三要素——**位置**（第几行第几列）、**事实**（期望什么、实际是什么）、**线索**（可能的修正方向）。编译器把「拒绝坏程序」这件事做到多好，直接决定语言的开发者体验，也间接决定语言的流行度。今天，这一套能力还被「语言服务器协议（LSP）」搬进了 IDE：编辑器里实时波浪线、悬停看类型，本质都是让编译器以「服务」的形态持续工作——这个话题在第十一篇《LLVM 架构》与《程序设计语言》的「开发环境」一节还会重逢。

## 8 小结

- **符号表**是把标识符映射到属性的中心数据结构，六道工序共用、逐步填充；实现常用哈希表（查得快）或二叉搜索树（可有序输出）。
- 名字可见性由**词法作用域**决定；解析遵循**最近嵌套规则**——从最内层向外，第一个命中者胜出。
- 维护嵌套作用域的两类实现：**每作用域一表 + 表栈** 与 **单表 + 作用域编号**，核心差别在「离开作用域时如何删除」。
- 错误分**词法、语法、语义（编译期）** 与 **逻辑（运行期）** 四类；编译器只能管前三种。
- 语法错误恢复四策略：**恐慌模式、错误产生式、局部修正、全局修正**；语义错误处理依赖符号表状态，追求「报一次、可延续」。
- 好的诊断 = 位置 + 事实 + 线索；现代编译器的错误提示（如相近标识符建议）直接改善语言体验。

在下一节，我们将离开「编译器内部」，站在更高的视角问一个被前两篇反复暗示的问题：程序执行的三种活法——**编译、解释与混合**，到底各有什么代价与收益。
