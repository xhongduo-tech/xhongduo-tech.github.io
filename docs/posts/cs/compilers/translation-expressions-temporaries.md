## 为什么从表达式翻译开始

三地址码有了「词汇表」（指令家族）和「语法」（四元式），现在要回答：**从表达式树到指令序列，机器如何自动翻译？** 答案又一次落在语法制导翻译上——用 S-属性 SDD，把「生成指令」写成文法规则的语义动作，翻译随归约一趟完成。<span class="marginnote">表达式翻译是中间代码生成的「hello world」：它小到一眼看穿，却又包含了临时变量管理、指令拼接、顺序保证三个后续都要用的机制。把表达式翻译吃透，数组、控制流、过程的翻译只是它的延伸。</span>

## 1 表达式 → 三地址码的 SDD

核心思想：**表达式结点的综合属性 code 是「计算它的三地址码序列」，addr 是「存放结果的地址」。** 子表达式的 code 拼接成父表达式的 code。

$$\begin{aligned} E &\to E_1 + E_2 & E.addr &= \texttt{newtemp()} \\ && E.code &= E_1.code \ \Vert\ E_2.code \ \Vert\ [E.addr = E_1.addr + E_2.addr] \\ E &\to -E_1 & E.addr &= \texttt{newtemp()} \\ && E.code &= E_1.code \ \Vert\ [E.addr = \texttt{uminus}\ E_1.addr] \\ E &\to (E_1) & E.addr &= E_1.addr \\ && E.code &= E_1.code \\ E &\to \textbf{id} & E.addr &= \textbf{id}.name,\ E.code = [] \end{aligned}$$

- code：子表达式翻译成的指令序列（综合属性，拼接上抛）。
- addr：结果所在位置——对标识符（id）就是名字本身，对运算表达式是新生成的临时变量。<span class="marginnote">code 和 addr 是两个配合默契的综合属性：code 是「完整指令流」，addr 是「当前值的存放处」。拼接符 $\Vert$ 表示「先算左子树，再算右子树，最后算父运算」——这个顺序正是求值语义（左到右）。</span>

## 2 临时变量的分配与回收

每个「中间结果」都需要一个临时变量，但**不必每个表达式一个永久名**。龙书给出了优雅的计数方案：

**newtemp 每次生成新名 t_i，但一个优化：临时变量可以复用。** 若用「当前活跃临时数」作为计数器，表达式翻译时按「左子树 + 右子树 + 1」的需求分配，能让临时变量数最小——原则是**右子树的临时变量可以在左子树算完后复用**（因为左子树结果已在 E_1.addr 里，它的临时变量不再需要）。

$$E \to E_1 + E_2 \text{ 所需临时数} = \max(\text{temp}(E_1), 1 + \text{temp}(E_2))$$

直觉：先算 $E_1$，用若干临时；算完把结果放 $E_1.addr$，这些临时释放；再算 $E_2$ 时可复用。所以 $E_2$ 需要 1（它自己）加上右子树内部所需。<span class="marginnote">这个「右子树优先复用左子树临时」的规律，是寄存器分配里「寄存器可以复用」的早期版本：编译器总在问「哪些值在那一刻还活着」。活跃变量分析（第八篇）会把它系统化。</span>

## 3 声明语句的翻译：类型与宽度

表达式之外，声明也要翻译成 IR——因为数组、记录的布局（偏移量）必须在编译期算出。声明翻译的 SDD 通常用继承属性传递当前偏移：

$$D \to T\ \textbf{id}; \quad \textbf{id}.offset = D.offset, \quad D.offset = D.offset + T.width$$

- width：类型占用的存储宽度（int 4、double 8、数组 = 元素宽 × 长度）。
- 每个变量记录它的偏移量（在符号表里），下一个变量的偏移自动累加。

对数组 int a[10]：宽度 = 4 × 10 = 40；double b[50]：宽度 = 8 × 50 = 400。记录（struct）的宽度 = 字段宽度之和。<span class="marginnote">「偏移量 = 前面所有变量的宽度和」是编译器给每个变量分配存储的根基，也是数组寻址翻译（下一节）的前奏。声明翻译看似平淡，实则是「布局问题」的第一次登场——C 的内存布局、Rust 的 repr、JVM 的对象头，全从这里演化。</span>

## 4 公式解析：临时变量计数的归纳

证明「$E$ 至多需要 $\text{temp}(E)$ 个临时变量」：

$$\text{temp}(E_1 + E_2) = \max(\text{temp}(E_1),\ 1 + \text{temp}(E_2))$$

- **第一步，左子树**：先算 $E_1$，需要 $\text{temp}(E_1)$ 个临时；算完结果存入 $E_1.addr$（一个地址），这些临时全部**不再被需要**——可释放。
- **第二步，右子树**：算 $E_2$ 时，那 $1$ 是「存放 $E_2$ 结果」的一个临时，再加上 $E_2$ 内部递归需要的 $\text{temp}(E_2)$。注意此时可复用 $E_1$ 释放的临时。
- **第三步，取最大值**：整个过程临时数峰值 = max(左子树峰值, 右子树峰值 + 1)——因为两边不同时活跃。

**这条归纳既是上限证明，也是实际分配算法**：翻译器按此计数，就能用**最少**的临时变量完成任务——这在寄存器匮乏的真实机器上是实打实的收益。

## 5 翻译的次序：求值顺序与副作用

表达式翻译的指令顺序由 SDD 的 code 拼接次序决定：**先左后右**。但对有副作用的语言（C/C++），求值顺序是语义问题：C 规定不确定、Java 规定从左到右——IR 生成必须**尊重语言定义的求值顺序**。<span class="marginnote">求值顺序是 IR 生成的隐藏陷阱：同一个表达式，交换左右子树代码位置，副作用的先后就变了。编译器要么严格按语言语义（Java），要么明确「未定义」（C），绝不能「随缘」——否则优化器一重排，语义就漂移。</span>

**辨析｜易错点：** 括号规则 $E \to (E_1)$ 对 $E_1$ 直接取 $E.addr = E_1.addr$，不新建临时——括号不产生值，只是分组。很多新手在这里多生成一条无意义的复制指令。翻译的纪律是「**不加无副作用的指令**」，这与后端「去死代码」精神一脉相承。

## 7 思考与练习

**练习 1 翻译实例**：对表达式 a * (b + c)，用 S-属性 SDD 完整翻译成三地址码——写出每步的 code 拼接与 addr 取值，标出每个临时变量的作用域。

**练习 2 临时计数**：对 a + b * c，用「max(左, 1+右)」公式算最少需要的临时变量数，再手工翻译验证——体会「右子树复用左子树临时」的分配。

**练习 3 括号不生成指令**：验证 a + (b * c) 与 a + b * c 翻译出相同的三地址码——E → (E_1) 这条规则让括号「零成本」，说明「不加无副作用指令」的纪律。

**练习 4 声明翻译**：对 int a; double b; int c;，用「偏移累加」规则算出每个变量的偏移与总存储大小——体会 width 的递归计算（数组 = 元素宽 × 长度）。

**练习 5 求值顺序**：对 a[i] = f(a[i] + 1)，按「先左后右」的 SDD 翻译，标出 a[i] 的读、f 的调用、a[i] 的写三条指令的次序——讨论若语言规定「先右后左」翻译会怎么变。

**练习 6 与运行时对接**：翻译结果里的临时变量在第六篇「活动记录」里存在哪？——临时变量是帧里的槽，用帧指针 + 偏移访问。把三地址码的临时变量映射到 AR 的槽位。

**常见误区**：

- **误区一**：以为每个子表达式都要一个「永久」临时变量——实际可复用，计数公式把需求压到最少。
- **误区二**：给纯分组（括号）生成复制指令——E → (E_1) 让它零成本，多生成是浪费。
- **误区三**：忽略求值顺序——SDD 的 code 拼接次序即语义；乱序翻译会改变副作用发生顺序。

**延伸**：临时变量计数公式「右子树复用左子树」与第七篇「寄存器分配」的活跃区间、第八篇「活跃变量」是同一思想——「复用不再活的值」。把三处「复用」写成一页对比，总结「值生命周期管理」在编译器的三个层次。

## 8 小结

- 表达式翻译用 **S-属性 SDD**：code（指令序列）与 addr（结果地址）两个综合属性随归约拼接上抛。
- 中间结果存**临时变量**；按「先左后右、右子树复用左子树临时」计数，可用**最少**临时数完成翻译。
- **声明翻译**用继承属性传偏移，width 为每个变量定布局；数组/记录宽度递归计算。
- 临时计数可**归纳证明**为上限且可达，翻译器据此分配。
- 指令顺序即求值顺序，**必须尊重语言语义**；括号、纯分组不产生指令。
