# 分代垃圾回收（Generational GC）

<div class="epigraph">

## 为什么从分代回收开始

复制式回收「存活率低才划算」，而大多数程序恰好有这样一个特征：**绝大部分对象刚创建不久就死亡**（临时对象、中间结果），只有少数活得久。**分代垃圾回收（generational GC）** 抓住这个规律——**弱代假设（weak generational hypothesis）**——把堆按「年龄」分成几代，对年轻代频繁回收（复制式，便宜），对老年代少回收（标记-清扫，贵）。这是 JVM、.NET、Go 等现代 GC 的事实标准。<span class="marginnote">「弱代假设」是一条经验规律而非数学定理：对象存活概率随年龄递减——活过第一轮回收的对象，大概率还会继续活。分代 GC 就是「押注」这条规律：把最频繁、最便宜的回收留给「死亡大户」年轻代，把昂贵的回收留给「幸存者」老年代。</span>

## 1 弱代假设与分代堆

**弱代假设**：多数对象出生即死（存活时间短），少数长寿。

**分代堆（generational heap）** 按对象年龄分区：

**年轻代（young generation）**：新对象都分配在这。空间小、回收频繁。
**老年代（old generation）**：在年轻代挺过多轮回收的对象被「晋升（promote）」到这。空间大、回收稀少。

回收策略也按代分工：

**年轻代回收（minor GC）**：复制式——存活率低，搬起来便宜，频繁做。
**老年代回收（major GC）**：标记-清扫/标记-整理——存活率高，偶尔做。

**晋升规则**：对象在年轻代存活若干轮（或达到年龄阈值）后，复制到老年代。<span class="marginnote">「年轻代复制、老年代标记」的组合是分代的精髓：复制式怕存活率高，就把它用在存活率低的年轻代；标记-清扫不怕存活率高（清扫扫全堆但标记只走引用），就留给老年代。两个算法的短板恰好互补——分代是「对症下药」的工程智慧。</span>

## 2 年轻代回收的流程

一次**年轻代回收（minor collection）**：

1. 从「年轻代根」出发遍历：年轻代内部的根（局部变量等）+ **老年代指向年轻代的引用**（跨代引用）。
2. 存活对象复制到 **survivor 区（幸存区）**；达到晋升年龄的复制到**老年代**。
3. 整轮回收只处理年轻代——**老年代纹丝不动**。

关键挑战：**老年代里可能有引用指向年轻代对象**——如果不处理，GC 会把「被老年代引用的年轻对象」误判为垃圾。

**记忆集（remembered set）**：为老年代维护一个「记录：哪些老年代对象持有指向年轻代的引用」的集合。年轻代回收时，把记忆集里的老年代对象当作根，一起遍历——不用扫整个老年代。<span class="marginnote">「记忆集」是分代 GC 的关键数据结构：它把「老年代 → 年轻代」的跨代引用<strong>记录下来</strong>，让年轻代回收只需扫描记忆集，而不是扫整个老年代。代价是每次老年代写入指向年轻代的引用时，要维护记忆集（写屏障）。「用写屏障的记账，换回收时的省扫描」——空间换时间。</span>

## 3 跨代引用与写屏障

**跨代引用（cross-generational reference）**：老年代对象指向年轻代对象。它威胁分代正确性：年轻代回收若不看老年代，会错杀被老年代引用的对象。

**写屏障（write barrier）**：拦截「老年代对象写入指向年轻代的引用」的写操作，把被写的老年代对象记入记忆集：

```text
// 伪码：老年代对象 a 写入指向年轻代对象的引用 newRef
if (inOldGen(a) && inYoungGen(newRef)) {
    rememberSet.add(a);   // 把被写的老年代对象记入记忆集
}
```

写屏障保证：**任何可能产生的跨代引用都被记忆集记录**——于是年轻代回收时，记忆集就是「老年代侧的根」。

**辨析｜易错点：** 记忆集是「近似保守」的：它可能记录「已经不再指向年轻代的引用」（对象死后没清理）——但**多记无害**（只是多扫几个根），**漏记致命**（会错杀活对象）。所以写屏障宁可多记，绝不漏记。<span class="marginnote">「宁可多记不可漏记」是记忆集的设计原则：多记的代价是回收时多扫几个老年代对象（小开销），漏记的代价是错杀活对象（程序崩溃）。这个「保守但不失正确」的原则贯穿所有 GC 优化——正确性永远优先于性能。</span>

## 4 公式解析：分代的成本模型

设存活率为 $s$、年轻代回收频率为 $f$，则分代的收益来自「把昂贵回收换成便宜回收」：

$$\text{单次年轻代回收成本} = O(\text{年轻代存活对象}), \qquad \text{高频做} f \text{ 次}$$

$$\text{老年代回收成本} = O(\text{老年代大小}), \qquad \text{低频做} F \text{ 次}, \quad F \ll f$$

- **第一步，成本结构**：年轻代回收只花「年轻代存活对象」的钱（复制式），老年代回收花「全堆」的钱（清扫）。
- **第二步，频率分配**：垃圾大多在年轻代，所以年轻代高频回收（便宜 × 多次）把大部分垃圾清掉；老年代低频回收（贵 × 少次）兜底。
- **第三步，净收益**：总成本 ≈ 便宜 × 高频 + 贵 × 低频——远小于「全堆高频回收」的朴素方案。

**「把回收频率对准死亡分布」是分代的总账**：对死亡最集中的年轻代高频地做便宜回收，是对弱代假设的最大化利用。

## 5 分代的挑战与调和

分代 GC 不是免费午餐，它的挑战：

- **记忆集的维护开销**：写屏障让每次跨代写多一步——现代实现用**卡片标记（card marking）** 近似记忆集（把老年代按 512 字节分「卡片」，脏卡片记入位图），摊销开销。
- **晋升策略**：晋升太急 → 老年代塞满过早；太缓 → 年轻代堆积。现代 GC 用**动态年龄阈值**（如 G1 的「存活率目标」）。
- **大对象**：超大对象直接进老年代（晋升昂贵），避免反复复制。

**重点是**：分代是「押注弱代假设」的工程赌注——假设成立则高效，假设不成立（存活率普遍高）则退化。多数真实程序押注成立，所以 JVM/Go/.NET 都选了分代。<span class="marginnote">「ZGC、Shenandoah」等现代 GC 甚至宣称「不分代」（ZGC 最早不分代）——它们用并发 + 染色指针等技术让「全堆回收」也足够快，绕过对弱代假设的依赖。但 G1、分代 ZGC 仍回归分代——因为「年轻代高频便宜回收」实在太香。分代是「经验赢了理论」的经典案例。</span>

## 7 常见误区与延伸

**常见误区**：

- **误区一**：以为「分代 = 两个堆」——是「按年龄分区 + 不同回收策略」，不是简单的两块内存。
- **误区二**：忽视「跨代引用」——老年代指向年轻代的引用若不被记忆集记录，年轻代回收会错杀活对象。
- **误区三**：以为「写屏障是慢的」——卡片标记等近似实现把屏障开销摊销到「标记一张卡」，比精确记忆集便宜。
- **误区四**：把「弱代假设」当「定理」——它是经验规律；存活率普遍高时（大对象、长生命周期），分代退化。

**延伸**：分代的「按年龄分区 + 高频便宜回收」与第四级《大模型部署》的「KV 缓存分级（热/温/冷）」、第三级《操作系统》的「LRU 老化」是同一思想——「资源按热度分层」。把「年轻代/老年代」类比「L1/L2 缓存」或「热/冷数据」，找「分层」的共性。

**练习提示**：解释「为什么年轻代回收用复制式、老年代用标记-清扫」——各自应对「存活率低」与「存活率高」的匹配，用成本公式写出理由。

## 8 小结

- **弱代假设**：多数对象出生即死——分代 GC 的押注依据。
- **分代堆**：年轻代（小、高频回收、复制式）+ 老年代（大、低频回收、标记式）；存活对象晋升。
- **跨代引用**威胁年轻代回收的正确性；**记忆集**记录老年代 → 年轻代的引用，作为年轻代回收的额外根。
- **写屏障**拦截跨代写、维护记忆集；**宁可多记、绝不漏记**。
- 分代把回收频率对准死亡分布：便宜 × 高频 + 贵 × 低频；现代实现用卡片标记、动态晋升等调和代价。
