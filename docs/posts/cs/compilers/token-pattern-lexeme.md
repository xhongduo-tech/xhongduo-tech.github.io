## 为什么从记号、模式与词素开始

上一课说词法分析器「读字符、吐记号」。但「记号」到底是什么？一个 `count`、一个 `3.14`、一个 `>=`，它们凭什么属于不同的记号？词法分析器凭什么把 `count` 认成标识符而不是关键字？——回答这些问题，需要一套精确的词汇：**记号（token）、模式（pattern）、词素（lexeme）**。

龙书把这组三分法放在词法分析的第一节，绝非偶然。它是「语言描述（模式）↔ 语言实例（词素）↔ 语言类别（记号）」三层的严格分离，也是后续正则表达式、有限自动机、以及一切「识别器」设计的逻辑起点。<span class="marginnote">这个三分法不止属于编译器：正则匹配、文本编辑器语法高亮、甚至大模型的分词器（tokenizer）都在做同一件事——把「模式描述」与「具体实例」区分开。NLP 里的 tokenization 与编译器的词法分析是同一思想的近亲，对应第四级《大模型原理》的词表与分词一节。</span>

## 1 三个概念的精确定义

**词素（lexeme）**：源程序中与某个模式相匹配的**字符序列实例**。它是具体的文本——`count`、`3.14`、`<=` 都是词素。

**模式（pattern）**：描述一个记号的词素可能长什么样的**规则**，通常用正则定义给出。它是抽象的规则——「以字母开头的字母数字串」「数字串」「关系运算符」。

**记号（token）**：一组具有相同结构特征（即能匹配同一模式）的**词素的类别名**，它是词法分析器返回的抽象单元——`<id>`、`<number>`、`<relop>`。<span class="marginnote">三者关系可类比语言学：模式是「类型」（type），词素是「实例」（token/occurrence），记号是「范畴」（category）。索绪尔区分能指与所指，编译器则把「写法」（词素）与「身份」（记号类型）分离——用不同的语言，讲同一个「分而治之」的故事。</span>

**一句话记住三者：词素是「这段话长什么样」，模式是「什么样的才算」，记号是「它被算作哪一类」。** 同一个模式可以匹配无数词素，无数词素归并成一个记号类型。词素是源码里真实出现的那一串字符，模式是你写进工具规范里的那一条规则，记号是语法分析器手里拿到的那一个抽象单元。

## 2 一个例子走通三者

龙书的经典例子：对下面这行 C 语句做词法分析。

```c
printf("total = %d\n", score + 4);
```

把它切分出的每个词素、匹配的模式、归入的记号，列成对照表：

| 词素（Lexeme） | 模式（Pattern） | 记号（Token） |
| --- | --- | --- |
| `printf` | 以字母开头的字母数字串 | `<id, 指向 printf 的符号表项>` |
| `"total = %d\n"` | 双引号括起的任意字符串 | `<literal, 字符串值>` |
| `(` | 左括号字符 | `(` |
| `,` | 逗号字符 | `,` |
| `score` | 以字母开头的字母数字串 | `<id, 指向 score 的符号表项>` |
| `+` | 加号字符 | `+` |
| `4` | 数字串 | `<number, 值 4>` |
| `)` | 右括号字符 | `)` |
| `;` | 分号字符 | `;` |

**注意记号列里的「属性值」**：`<id, …>` 的第二个分量是**属性（attribute）**——对标识符是符号表项指针，对数字是数值，对字符串是字面量本身。**记号 = 记号类型 + 属性值**：类型决定「怎么归类」，属性决定「归完类后还保留什么信息」。语法分析器只关心类型（`id`、`number`），而代码生成需要属性（标识符指向谁、数值多大）。<span class="marginnote">属性值是记号与符号表、常数表之间的桥梁。龙书刻意区分「token 类型」与「token 值」：同一个 `<id>` 类型对应成千上万不同的属性值，正如同一个「名词」范畴可容纳无数具体的词。</span>

![记号、模式与词素：三层映射](/images/compilers/token-pattern-lexeme-1.svg)

上图把「词素 → 模式 → 记号」的映射画成一条流水线：具体的 `score`、`60` 先被模式 `letter(letter|digit)*`、`digit+` 认领，再归并成抽象的 `<id>`、`<number>` 记号，最后带上各自的属性值交给语法分析器。

## 3 记号的类别：语言自己定义的词汇

一门语言的记号类型集合，就是这门语言在词法层面的「字母表上的分类」：

- **关键字（keyword）**：如 `if`、`else`、`while`、`return`——有固定含义的词。
- **标识符（identifier）**：程序员自定义的名字，如 `count`、`score`、`printf`。
- **字面量（literal）**：数字常量（`60`、`3.14`）、字符串常量（`"total"`）、字符常量。
- **运算符（operator）**：`+`、`-`、`*`、`==`、`<=`、`&&` 等。
- **分隔符（punctuation）**：`( ) { } ; ,` 等。

**重点：** 关键字与标识符共享同一个词素形态——都是字母数字串。二者的区分是**策略性的，不是形态性的**：词法分析器识别出「标识符形态」后，再去查一张**关键字表**，命中则归入关键字记号，否则归入标识符。<span class="marginnote">这张关键字表通常组织成哈希表或排序数组。识别顺序也有讲究：先按<strong>最长匹配原则</strong>吃下尽可能长的词素，再查关键字表——这样 `while1` 不会被误判成 `while` 加 `1`。最长匹配原则在《正则表达式与正则定义》与自动机课程里会再次出现。</span>

在真实编译器中，记号类型就是一组整数常量，词法分析器返回的类型值往往是一个枚举：

```c
typedef enum {
    T_ID,       /* 标识符 */
    T_NUMBER,   /* 数字常量 */
    T_PLUS,     /* + */
    T_MUL,      /* * */
    T_IF,       /* 关键字 if */
    T_ELSE,     /* 关键字 else */
    T_LPAREN,   /* ( */
    T_RPAREN,   /* ) */
    T_SEMI,     /* ; */
    /* ... */
} TokenType;
```

枚举值在词法与语法之间相当于一份**双方都认得的词典**：词法分析器说 `T_ID`，语法分析器就知道「这里来了个标识符」。新增一个记号类型，只需在枚举里加一项，并补上对应的正则模式——这正是「规范驱动」的工具化开发方式：**改一行描述，重新生成一遍，分析器就拥有了新的词汇。**

## 4 关键字与标识符：保留字的辨析

**保留字（reserved word）**：不允许当作标识符使用的关键字。C 语言里 `if` 是保留字——你不能写 `int if = 3;`。但并非所有语言都把关键字设为保留字。

**辨析｜易错点：** Fortran 的早期版本里，关键字**不是**保留字——`IF` 既可以当关键字，也可以当变量名，由上下文（位置）决定含义，语法分析器得靠语境才能判别。而 C、Java、Python 的做法简单粗暴：**关键字一律保留**，词法层一旦匹配就归入关键字记号，永不当作标识符。**「保留字」是语言的策略选择，不是词法分析的必然结论。** 现代语言（如 Rust）甚至把「未来可能成为关键字」的词也一并保留，避免语言演化时破坏已有代码。<span class="marginnote">把关键字设为保留字是一把双刃剑：好处是编译器实现简单、人类读者歧义少；坏处是语言扩张词汇时，旧代码可能因撞上新增保留字而失效。这也是为什么 `async`、`await` 等新关键字常引发「破坏性变更」的争论。</span>

## 5 公式解析：一条正则定义如何匹配一个词素

记号模式的标准写法是**正则定义**。以标识符为例：

$$
\mathbf{id} \to \mathbf{letter}\,(\mathbf{letter} \mid \mathbf{digit})^*, \qquad
\mathbf{letter} \to A \mid B \mid \cdots \mid Z \mid a \mid \cdots \mid z \mid \_, \qquad
\mathbf{digit} \to 0 \mid 1 \mid \cdots \mid 9
$$

这条定义说：标识符 = 一个字母（或下划线），后接零个或多个「字母或数字」。我们用输入 `score` 走一遍匹配过程：

- **第一步，读第一个字符 `s`**：它属于 $\mathbf{letter}$，匹配正则定义的第一段。此时已消耗一个字母，位置推进到 `c`。
- **第二步，读 `c`**：它是 $\mathbf{letter}$ 的一部分，能匹配 $(\mathbf{letter} \mid \mathbf{digit})^*$ 的第一次迭代。位置推进到 `o`。
- **第三步，读 `o`、`r`、`e`**：每个都是 $\mathbf{letter}$，各匹配 $(\cdots)^*$ 的一次迭代。位置到达字符串末尾。
- **第四步，输入结束**：$(\cdots)^*$ 选择**零次迭代**结束。整个 `score` 被完整匹配，判定它属于 $\mathbf{id}$ 的语言——**词素 `score` 匹配模式 $\mathbf{id}$**。

拆解这条正则定义的四个要点：

- **$\mathbf{letter}$ 与 $\mathbf{digit}$ 是缩写**：正则定义允许用名字（$\mathbf{letter}$）代替正则表达式，层层展开后仍是纯正则表达式——**缩写不增加表达能力，只增加可读性**。
- **$(\cdots)^*$ 的「贪婪」与「零次」**：星号闭包允许任意次重复，包括 0 次。匹配到末尾后，闭包选 0 次迭代恰好结束——**匹配的终点由「能否继续 + 输入是否耗尽」共同决定**。
- **为什么不写成 $\mathbf{letter}^*$？** 那会允许「以数字开头」的串或纯数字串，与「标识符必须以字母或下划线开头」的直觉不符。**正则定义把约束精确编码**，漏掉一个字符类别，就会放进来一类非法词素或挡掉一类合法词素。
- **与 DFA 的衔接**：正则定义能机械地转换成 NFA / DFA，词法分析器在 DFA 上跑这个匹配过程——每一步「读字符、决定状态」正是状态转移。接下来几篇会完成这条「正则 → 自动机」的完整通道。

## 6 小结

- **词素（lexeme）**是具体字符序列，**模式（pattern）**是词素的形状规则，**记号（token）**是词素的类别名——「长什么样」「什么样的算」「算作哪类」三层分离。
- **记号 = 记号类型 + 属性值**；类型供语法分析器使用，属性值（符号表指针、数值）供后续阶段使用。
- 记号分**关键字、标识符、字面量、运算符、分隔符**；关键字与标识符形态相同，靠**查关键字表**区分。
- **保留字**是语言的策略选择：C 系一律保留，Fortran 早期不保留、靠上下文判别。
- 正则定义 $\mathbf{id} \to \mathbf{letter}(\mathbf{letter}\mid\mathbf{digit})^*$ 精确刻画了标识符，其匹配过程即词法分析在自动机上的运行。

在下一节，我们将回答词法分析器的一个「性能级」问题：它要快速读入源程序字符，又要支持「多读一口再放回」，**字符流怎么组织才高效**？——这就是**输入缓冲与哨兵技术**。
