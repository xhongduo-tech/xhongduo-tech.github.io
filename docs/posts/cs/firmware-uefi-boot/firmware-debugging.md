## 为什么从调试开始

固件调试是整个专题的「最后一公里」，也是最不性感却最要命的能力。固件工程师的日常不是写漂亮代码，而是面对「板子黑屏了，可能死在启动链的任何一段」的现场。这一节把调试工具箱摊开：**串口日志**（看软件走到哪）、**POST code**（看硬件停在哪）、**JTAG/SWD**（看 CPU 此刻在跑什么）。

《Embedded Firmware Solutions》全书的实操部分都在反复演示这套流程——从 coreboot 的 `cbmem` 到 UEFI 的 DEBUG 串口输出，再到 JTAG 探测。<span class="marginnote">调试固件与调试普通程序有本质差异：固件运行在「OS 和调试器都不存在」的环境里，常见的 print 断点、符号调试器都可能不可用。所以固件调试的第一课是：<strong>先把「能输出一行字」的能力建出来</strong>。</span>

## 1 固件调试的特殊困难

对比应用调试，固件调试有四个「无」：

- **无 OS**：printf、gdb、core dump 全都依赖 OS，而固件在 OS 之前运行；
- **无稳定内存**：SEC/PEI 阶段连 DRAM 都还没点亮，代码活在 Cache-as-RAM 里；
- **无显示**：显卡初始化之前，屏幕是黑的，可能连 BIOS 字符都没有；
- **无符号表**：闭源二进制（FSP/AGESA）内部无法单步，只能看行为。

正是这「四个无」，把固件调试从「看代码」逼成「看行为」：多数时候你面对的不是「哪行代码写错了」，而是「系统停在哪一步、那个步的预期产物是什么」。固件工程师的调试笔记，本质是在给每个里程碑记「预期输出」。

因此固件调试的核心思想是**分阶段降维**：先用「最便宜的观察手段」（串口、POST code）确定问题落在启动链的哪一段，再用「最贵的工具」（JTAG、逻辑分析仪）在确认的段里深挖。<span class="marginnote">这也是为什么前面每节都强调「先判断这是哪一段」——SEC/PEI 阶段是汇编 + CAR，DXE 阶段才有 C 驱动的符号，ARM 则要到 TF-A BL31 之后才有完整的串口输出。判断段位决定了工具箱里该抽哪件武器。</span>

## 2 串口日志：固件的 printf

串口是固件最通用、最便宜的输出通道。x86 平台通常用 **16550 UART**，映射到 I/O 端口 `0x3F8`（COM1）；嵌入式板卡则把 UART 引脚引到排针。

公式解析：串口的**位时间（bit time）**决定波特率与传输速度的关系：

$$
T_{\text{bit}} = \frac{1}{\text{baud}}, \qquad T_{\text{frame}} = (1 + 8 + 1 + 1) \times T_{\text{bit}}
$$

三步拆解：

- **第一步，`baud` 是什么**：波特率是每秒传输的信号码元数。最常用的 `115200` 波特，对应每位 `1/115200 ≈ 8.68 μs`。
- **第二步，一帧有几位**：典型 8N1 格式 = 1 起始位 + 8 数据位 + 1 停止位（可能加 1 校验位）。所以一个字节占 `11 × 8.68 μs ≈ 95.5 μs`。
- **第三步，工程含义**：波特率越高传输越快，但长线干扰越严重。固件现场调试习惯用 **115200**（x86 串口）或 **9600/57600**（部分嵌入式），日志量大时宁可降波特率保可靠。

**固件的调试日志输出**在 EDK II 里是 `DEBUG()` 宏，配合 `PcdDebugPrintErrorLevel` 控制开关与级别；coreboot 用 `printk()`，输出进 **cbmem** 控制台，可在 OS 里用 `cbmem -c` 回读——即使串口没接，日志也留在内存里等事后取。

EDK II 还有一个「预构建调试」技巧：把**串口驱动在编译期就编进 SEC 的临时段**，让日志从启动最早期（CAR 阶段）就能输出。这是「先让板子开口说话」在 EDK II 里的落地：很多「死得无声无息」的失败，一旦能从第一毫秒打日志，定位时间就从小时级降到分钟级。<span class="marginnote">EDK II 的 DEBUG 信息分级（`DEBUG_INIT`/`DEBUG_INFO`/`DEBUG_ERROR`…）对应不同的打印开关，发布固件通常只开 ERROR 级；调试时把级别提到 VERBOSE，能观察到驱动绑定的每一步。</span>

## 3 POST code：黑盒时代的信号灯

在串口都还没起作用的阶段（比如 CAR 建立之前），工程师靠 **POST code（开机自检码）** 定位：固件在关键里程碑处往诊断端口写一个字节，外部设备（诊断卡/LED）把它显示出来。

- 传统 x86 用 I/O 端口 **`0x80`**，一块插在 PCI/ISA 槽上的「POST 卡」就能显示两位十六进制；
- 现代平台输出到 **LPC/eSPI** 上的诊断口，或直接编码进主板上的 4–8 颗 LED；
- 每个厂商（AMI、Insyde、Phoenix）有自己的一套 code 表，但**「卡在哪个 code = 死在启动链哪一段」**是通用读法。

以 AMI 的 UEFI 码表为例，几个常见位置：`0x02`–`0x0F` 附近是 SEC/PEI 早期，`0x10`–`0x2F` 是 PEI 内存初始化区，`0x50` 前后是 DXE 核心，`0x62`–`0x68` 是 BDS 枚举外设……**一旦看到卡在「内存初始化」段，直接转去查 SPD、FSP、DIMM 供电**，问题范围瞬间收窄。

**易错点｜辨析：** POST code 只能告诉你「代码执行到了某里程碑」，**不能告诉你为什么没往下走**。`卡在 A9（内存初始化）` 可能是 SPD 读不到、可能是训练超时、可能是 FSP 未正确调用——code 是定位用的路标，不是结论。下一步通常是接上串口看 FSP 的详细报错。<span class="marginnote">POST code 的另一个价值是<strong>可被记录</strong>：很多服务器把每次引导的最后一个 POST code 存进 NVRAM 或 BMC 的 SEL 日志，远程管理员不插卡也能看「上次卡在哪」。对「现场没人、机器黑了」的运维场景，这几乎是唯一线索。</span>

## 4 JTAG/SWD：让 CPU 停下来回答问题

当「软件日志 + 硬件路标」都指向一个深层问题（如时序、DMA 配置、异常向量）时，需要让 CPU **停下来**，这就是硬件调试器：

- **JTAG**：通用边界扫描/调试接口，x86 服务器常经 **ITP（Intel In-Target Probe）** 连接，能读寄存器、下断点、看内存；
- **SWD**：ARM 的串行调试接口（比 JTAG 引脚少），配合 OpenOCD 与 GDB 即可在嵌入式板上断点调试；OpenOCD 还能读写板载 Flash，让「JTAG 直接烧录 + 调试」合二为一，省掉反复拔插烧录器的痛苦；
- **逻辑分析仪/示波器**：观察 SPI Flash 访问、SMBus SPD 读取、PCIe 复位时序这些**信号级**行为。

x86 服务器的 JTAG 实践也有讲究：**ITP（In-Target Probe）** 不只是「能下断点」，它还能在 **SEC/PEI 阶段就接管 CPU**——此时串口可能还没通、POST code 还只在 CAR 里。配上 ITP 的脚本化（`WinDbg` 或 Intel 的调试工具），工程师可以把「卡死在 `FspInitEntry` 内部」这类问题，从「猜」变成「直接看寄存器现场」。

<span class="marginnote">JTAG 调试固件的价值是「能在 OS 出现前看 CPU 正在执行什么」——比如在 `FspInitEntry` 内部卡死，串口无声、POST code 停在原地，JTAG 直接读出指令指针，立刻知道代码停在哪条指令上。代价是设备昂贵、接线麻烦、需要芯片级授权（Intel 的 JTAG 常要签 NDA 才解锁）。</span>

## 5 组合策略：一套现场排障流程

把上面的工具串成一个可复用的工作流：

| 现象 | 首选工具 | 次选工具 | 定位目标 |
| --- | --- | --- | --- |
| 完全黑屏、无任何输出 | POST 卡 / LED | 逻辑分析仪测复位 | 上电是否正常 |
| 有 code 但卡住 | POST code 表 + 串口 | FSP 日志 | 定位到阶段 |
| 串口有输出但死循环 | DEBUG 级别调高 | JTAG 抓 PC | 定位到函数 |
| 偶发不稳定 | 降低时序/降频 | 示波器看信号 | 定位到信号 |

**核心对比表**（纯概念主题，以表代替公式）：三类工具的能力边界：

| 维度 | 串口日志 | POST code | JTAG/SWD |
| --- | --- | --- | --- |
| 需要什么 | UART 引脚 | 诊断卡/LED | 调试器 + 授权 |
| 能看到 | 软件执行流 | 里程碑 | CPU 内部状态 |
| 开销 | 低 | 极低 | 高 |
| 时机 | DRAM 后（或 ARM 的 UART 早期） | 最早期 | 任意时刻 |
| 典型场景 | 日常开发 | 现场快速定位 | 疑难时序/死锁 |

工程经验是：**90% 的固件问题在「串口日志 + POST code」这一层就能定位**；JTAG 是为剩下那 10% 的深层问题保留的重武器。而剩下那 10% 里，多数又集中在「时序、DMA、电源」这三类信号级问题——它们天然要上示波器或 JTAG。

另一条经验是关于「日志礼仪」的：**每条调试日志都要带上阶段标签**。固件没有 OS 的日志框架，但工程师自己约定 `[SEC]`、`[PEI]`、`[DXE]` 前缀后，一段启动日志就能按阶段切成几段——**「日志分阶段打，问题分阶段查」**，是新手最容易忽略、也最见效的习惯。初学者最该先学会的是「让板子开口说话」——把串口接好、把 DEBUG 级别调对、把 POST 卡插上，这是所有固件调试的地基。

## 6 小结

- 固件调试的困难是**四个「无」**：无 OS、无稳定内存、无显示、无符号表，应对之道是**分阶段降维**。
- **串口**是通用输出通道：EDK II 用 `DEBUG()`、coreboot 写进 cbmem；波特率决定字节时序（`T_bit = 1/baud`）。
- **POST code**（`0x80` 端口/诊断卡/LED）是黑盒阶段的信号灯，定位「死在哪一段」，不能给结论。
- **JTAG/SWD** 让 CPU 停下来：读寄存器、下断点，处理深层时序与死锁。
- 组合策略：黑屏 → POST 卡；卡住 → 串口 + code 表；死循环 → JTAG。**让板子开口说话**是固件调试的第一课。
- 调试日志要**带阶段前缀**（`[SEC]/[PEI]/[DXE]`）；POST code 常被存进 NVRAM/BMC SEL，远程也能看「上次卡在哪」。
- EDK II 可把串口驱动**编进 SEC 临时段**，让日志从 CAR 阶段就开始；coreboot 的 `cbmem -c` 可回读无串口时的日志。
- 用 **AMI 码表**快速把 POST code 翻译成阶段：`0x10–0x2F` 内存初始化、`0x62–0x68` BDS 枚举，定位范围瞬间收窄。
- **ITP（In-Target Probe）**能在串口未通、POST code 未出时就接管 CPU——把「卡在 FSP 内部」从猜测变成直接看寄存器现场。
- 90% 的固件问题在「串口 + POST code」层就能定位；剩下 10% 集中在时序、DMA、电源这三类信号级问题，需要示波器或 JTAG。
- OpenOCD 让 **SWD 调试与 Flash 烧录合二为一**，省掉反复拔插烧录器的痛苦。
- 用 `flashrom` 备份/恢复固件 ROM，是所有「改固件前先备份」习惯的落点。
