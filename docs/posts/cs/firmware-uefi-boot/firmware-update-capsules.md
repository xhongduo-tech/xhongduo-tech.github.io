## 为什么从固件更新开始

固件是平台的「第一段代码」，所以固件更新也是最危险的操作：**更新中断一次，机器就可能变砖**。现代平台对「怎么把新固件安全地写进 Flash」投入了大量设计——UEFI capsule、单调计数防回滚、A/B 分区、失败自动恢复。这一节把整套机制拆开。

《Embedded Firmware Solutions》第6章专门讲 FSP 与 UEFI 集成时的 capsule 更新流程；本节把它的概念抽出来，补充现代平台通用的防回滚与恢复设计。<span class="marginnote">为什么固件更新比软件更新凶险？普通软件更新失败最多蓝屏，重装即可；固件更新失败意味着「下一个上电时刻，CPU 从 Flash 读到的可能是半截代码」——机器可能在复位向量处就卡死，没有任何回退入口。</span>

## 1 更新链路全景

一条完整的固件更新链路要回答四个问题：

1. **谁来发起**：OS 厂商（Windows Update/Linux fwupd）、OEM 工具、Web 端到端恢复；

<span class="marginnote">一个反直觉但常见的事实：<strong>很多「固件更新失败」其实发生在「OS 层确认」这一步</strong>——capsule 已正确交给固件，但重启后固件因版本检查、签名不符或 Flash 保护位拒绝写入，于是更新被静默跳过。排查固件更新失败，先看「固件有没有真的收到 capsule」，而不是急着重刷。</span>
2. **怎么传输**：在运行中的 OS 里把新镜像交给固件；
3. **怎么验证**：确认新镜像合法、未篡改、版本不倒退；
4. **怎么落盘**：安全地把新内容写进 SPI Flash，保证掉电不坏。

**UEFI Capsule（胶囊）** 是 UEFI 对「第2、3、4步」的标准化回答。OS 调用 Runtime 服务 `UpdateCapsule()`，把一个或多个 **EFI_CAPSULE_HEADER** 描述的内存块交给固件，固件在**下一次重启**时按 `FMP`（Firmware Management Protocol）定义的方式把内容刷进 Flash。

capsule 本身有清晰的**结构化语义**：`EFI_CAPSULE_HEADER` 声明 GUID、容量、标志（是否跨重启持久、是否含依赖），其后跟着实际的镜像载荷与可选签名。**「胶囊」这名字很贴切——它像一枚封装了「新固件 + 元数据 + 签名」的药丸，交给固件在安全的时机（下一次引导早期）服用**。

<span class="marginnote">capsule 的巧妙之处是「跨重启传递」：OS 运行期间 Flash 的一部分正被运行时服务占用，直接写不安全；于是把新镜像先放在内存里，标记「重启后处理」，重启后固件在 OS 介入之前把 capsule 落盘——这一步在 DXE 早期完成，此时还没有任何 OS 代码在跑。</span>

## 2 认证：只有「对」的镜像才能进 Flash

固件更新最怕的不是失败，而是**更新成恶意镜像**。所以 capsule 在写入前必须被验证，验证核心是数字签名链：

$$
\text{Verify}: \; \sigma(\text{SHA-256}(\text{FirmwareImage})) \;\xrightarrow{\text{PK/KEK/db}} \; \text{accept / reject}
$$

三步拆解：

- **第一步，算哈希**：`SHA-256(镜像)` 得到固定长度摘要，任何一位改动都会改变摘要——这是「镜像完整性」的保证。
- **第二步，验签名**：镜像携带的签名 `σ` 用公钥验签，验出「这个摘要确实来自持有私钥的合法厂商」——这是「镜像来源」的保证。
- **第三步，对密钥库**：签名证书必须落在 **db** 白名单、且不在 **dbx** 黑名单里（复用安全启动的密钥体系，见《安全启动》）。通过才允许刷写。

**易错点｜辨析：** 「更新失败回滚」「更新被恶意镜像替换」是两种不同风险。更新失败是「工程可靠性」问题（幂等、恢复、重试），更新被替换是「安全」问题（签名、防回滚、信任根）——把两者混为一谈，会在设计更新机制时顾此失彼。**回滚**防的是「把 1.5 刷回 1.4」（可能引入已修复的漏洞），**替换**防的是「把 1.5 刷成攻击者伪造的 1.5」。现代固件同时防两者：前者靠版本校验/单调计数，后者靠签名。

## 3 防回滚：单调计数与版本锁

**防回滚（Anti-Rollback）** 的核心思想是「固件只能越来越新」：

- **单调计数器（Monotonic Counter）**：Flash 里有一块只增不减的计数器，每次成功更新 +1。新镜像必须携带「比当前计数更大」的版本，否则拒绝；
- **版本号 + 安全降级位**：TEE/SoC 里常有一根 **eFuse** 熔丝位，烧断后某些旧版本被永久锁死——即使系统被攻破，也改不回脆弱旧固件。

<span class="marginnote">Android 生态的术语是 <strong>AVB（Android Verified Boot）</strong> 的 rollback index：每版系统带一个不断增长的整数，设备存储当前最小可接受值，只允许装「rollback index ≥ 当前值」的镜像。思路与 UEFI 单调计数完全同构。</span>

## 4 A/B 分区：失败也能回退

对手机、路由器等嵌入式设备，业界通用的是 **A/B（双槽）分区**方案：

- Flash 里同时维护 **A、B 两份固件**，启动时按「健康标记」选择其中一份；
- 更新时写**非活动槽**（比如当前跑 A，就写 B），写完设置「B 为下一启动槽」；
- 若 B 启动失败（内核起不来、自检异常），固件自动回退到 A，并在下次尝试 A。

这个设计把「更新中断/更新损坏」的风险从「变砖」降为「多一次重启」。结合 **capsule 双镜像 + FMP**，x86 平台也越来越多地采用类似的冗余策略——特别是对远程管理无法人工救砖的服务器。

A/B 有一个代价常被低估：**Flash 容量翻倍**。每个可回退的固件都要准备两份完整镜像，在固件动辄 16–32 MB、且 ME/描述符区又不可动的今天，A/B 对存储预算是个实打实的压力。因此不少 x86 平台用「**单槽 + 冗余备份区**」的折中：主镜像加一块可启动的 mini-recovery 镜像，兼顾安全与容量。

### 从 ESRT 到 fwupd：更新如何被 OS 管理

现代 OS 并不直接摸 FMP，而是经 **ESRT（EFI System Resource Table）** 发现「这台机器有哪些可更新固件」。ESRT 是一张 ACPI 风格的表格，列出每个固件资源（BIOS、ME、PD、微码等）的 GUID、版本与状态。OS 据此生成更新清单：

- Linux 的 **fwupd**（GNOME Software 后端）读 ESRT，匹配厂商 capsule 包，`fwupdmgr update` 一站式完成「下载 → 校验 → UpdateCapsule → 重启刷写」；
- Windows 的 WU（Windows Update）同样经 ESRT 推送固件更新，多数「驱动更新里冒出的 BIOS 更新」就是这么来的。

**ESRT 是「OS 与固件之间的更新契约」**：它把「能更新什么、现在什么版本」从固件内部暴露给 OS，让固件更新像软件更新一样可管理、可追踪、可审计。

## 5 恢复路径：万一还是坏了

再完善的机制也挡不住「写 Flash 的一瞬间掉电」。所以平台必须备最后防线：

- **Recovery 跳线/按键**：强制从恢复介质（U 盘、专用 Flash 区）加载最小固件，重刷主区；
- **双 BIOS**：主板焊两块 Flash，主区损坏时从备份区引导；

最后一条工程提醒：**任何更新机制都要先做「断电演练」**。厂商在发布固件前，会反复测试「刷写到第 37% 时断电」「刷写完成但校验失败」这类最坏情况——因为更新代码本身也是固件的一部分，它和它要更新的对象一样，必须被反复验证。
- **云端恢复**：Chromebook、部分笔记本在「检测到固件损坏」时自动联网拉取官方镜像重装。

**核心对比表**（纯概念主题，以表代替公式）：三种更新路径的取舍：

| 维度 | Capsule（UEFI） | A/B 分区 | 传统烧录器 |
| --- | --- | --- | --- |
| 典型场景 | 服务器/PC OS 内更新 | 手机、嵌入式 | 工厂、维修站 |
| 中断容忍 | 需要恢复机制 | 高（有回退槽） | 低（人工重烧） |
| 防回滚 | 单调计数 | rollback index | 无（靠流程） |
| 认证 | FMP + 签名 | AVB 签名 | 人工 |
| 运维成本 | 低 | 中（双倍 Flash） | 高（需拆机） |

还有一个容易被忽略的工程点：**更新的原子性**。SPI Flash 只能按扇区擦写，而固件卷往往横跨多个扇区——「擦了一半掉电」是变砖的最常见原因。所以现代固件更新要么**先写副本区、完成后再原子切换**，要么**把更新设计成「可重入」**（重启后若发现镜像不完整，自动回到上一份）。「更新必须要么全成、要么全不成」，是固化进平台设计里的第一原则。

## 6 小结

- 固件更新链路分**发起、传输、验证、落盘**四段，UEFI capsule 用 `UpdateCapsule()` + FMP 标准化了后三段。
- capsule 在**下一次重启的 DXE 早期**落盘，避开 OS 运行期对 Flash 的占用。
- 认证 = `SHA-256` 摘要 + 数字签名 + db/dbx 白黑名单；**防回滚**靠单调计数与版本锁。
- 更新失败先查「固件有没有真的收到 capsule」，而不是急着重刷——很多失败发生在 OS 层确认之后、固件落盘之前。
- **A/B 双槽**把「更新失败」从变砖降级为「自动回退重启」。
- 最后防线是恢复跳线、双 BIOS 与云端恢复。
- **ESRT + fwupd/WU** 把「固件更新」纳入 OS 的软件更新体系；A/B 双槽的代价是 Flash 容量翻倍，x86 常用「单槽 + mini-recovery」折中。
- 更新必须**原子化**：先写副本、成功后再切换，否则「擦到一半掉电」就是变砖的第一现场。
- 发布前的**断电演练**（刷到一半掉电、校验失败）是固件更新 QA 的必做项。

在下一节，我们把目光从「怎么更新」转向「怎么防护」：BIOS rootkit、Intel ME/PSP 的争议与边界——固件安全是整个平台的信任基石，也是最常被误解的一层。更新机制的安全一面（签名、防回滚、密钥库），正是下一节展开攻击面的起点。
