## 为什么从启动链开始

上一节立住了「固件是一串可组合的引导层」这个心智模型。现在把它落到 x86 上：从 CPU 复位到操作系统拿到控制权，现代固件严格按 **PI 架构（Platform Initialization Architecture）** 划分成几个阶段——SEC、PEI、DXE、BDS、TSL、RT。<span class="marginnote">PI 规范是 UEFI Forum 发布的兄弟规范：UEFI 规范定义「OS 可见的世界」，PI 规范定义「OS 之前的内部组织」。EDK II 是两者的开源参考实现，也是《Embedded Firmware Solutions》全书实操的地基。</span>

这条链的价值在于：**它把「鸡生蛋、蛋生鸡」的问题拆成了一个个可验证的里程碑**。每个阶段只依赖前一个阶段留下的明确定义的数据结构（HOB），于是固件工程师可以把系统推进到一个又一个「可调试的稳定点」。

## 1 RESET：从哪一条指令开始

x86 的启动起点是物理事实。CPU 复位后，指令指针被强制置为：

$$
\text{RESET} = 0xFFFFFFF0 = 2^{32} - 16
$$

对这个数字做三步拆解：

- **第一步，理解 `2^{32}`**：x86 复位后处于实模式，但早期只访问 20 位地址；现代 CPU 在复位瞬间会临时映射到 4 GB 地址空间的顶端，即 `0xFFFFFFF0`。
- **第二步，为什么是减 16**：`0xFFFFFFF0` 离 4 GB 终点只差 16 字节。这 16 字节装不下任何逻辑，只够放一条跳转指令——这就是**复位向量（reset vector）**。芯片组把这段地址别名到 Flash 里，所以 Flash 的最高 16 字节处存放着跳到固件真入口的 `JMP`。
- **第三步，隐含结论**：固件必须把自己的入口安排在 `4 GB - 16` 这个地址能看到的地方。这个「物理地址别名」机制从 8086 时代一路沿用至今，是整条启动链第一个「约定大于代码」的产物。

复位向量之后、固件正式跑起来之前，CPU 自己还有一小段「家务」：**加载微码补丁（microcode patch）**。x86 CPU 内部其实运行着一层不可见的微码，早期批次常带 bug，厂商通过发布新微码在启动早期「打补丁」。微码由固件（或 OS）在冷启动时载入，这也是为什么「升级 BIOS」常与「修复 CPU 漏洞」并列出现——很多 Spectre/Meltdown 类漏洞的缓解，实际是跟着固件一起发布的微码更新。

## 2 SEC：信任根与临时内存

**SEC（Security Phase，安全阶段）** 是复位向量之后执行的第一段代码，也是 PI 架构里最接近硬件的部分。它只做四件事：

1. 处理一切复位类事件（冷启动、热重启、S3 唤醒）；
2. 建立**临时内存**——典型手法是 Cache-as-RAM（CAR）：把 CPU 的 L2 缓存当作普通内存来读写，既当栈又当堆；
3. 定位并传递**引导固件卷（Boot Firmware Volume）**的位置；
4. 作为**根信任**的起点：从这里开始，后续每一段代码都由前一段度量。

<span class="marginnote">SEC 常被比喻成「方舟上的第一颗种子」：它自身不能被信任链验证（没有更早的程序了），所以它必须足够小、足够硬、改动足够少。CRTM（Core Root of Trust for Measurement）一词指的就是这第一段可度量代码。</span>

SEC 结束时，把 PEI 需要的入口信息装进一个叫 **PPI（PEI-to-PEI Interface）** 的链表，转交给 PEI 阶段。此时系统的「内存」还只是 CPU 缓存——真正的 DRAM 一颗都还没点亮。

SEC 还有一层身份：**安全启动的度量起点（CRTM）**。后续每一个引导组件在交给下一阶段前，都被度量并扩展进 TPM 的 PCR（见本专题《安全启动》）。正因为 SEC 是最早执行、又不可自我验证的代码，它必须来自可信任的引导固件卷——这也是为什么固件卷的完整性从启动第一刻起就要被锁住。

## 3 PEI：点亮内存

**PEI（Pre-EFI Initialization，EFI 预初始化）** 阶段的目标只有一个：**初始化永久内存（DRAM），并为 DXE 铺路**。

PEI 由 PEI 核心与一批 **PEIM（PEI Module）** 组成。PEIM 以「谁声明自己需要什么（PPI）」的方式互相发现：<span class="marginnote">PEIM 之间的依赖用 PPI 声明，先被调用的 PEIM 产出的 PPI 供后续 PEIM 消费。这个「生产者—消费者」模式在 DXE 阶段被放大成协议总线，是整个 UEFI 体系的核心组织方式。</span>

- 芯片组的 PEIM 读 SPD（Serial Presence Detect）信息、执行内存训练（见本专题《内存初始化》）；
- 内存控制器的 PEIM 把 DRAM 纳入系统地址空间；
- PEI 核心把所有结果整理成**描述内存与固件卷位置的 Hand-Off Block（HOB）列表**。

这里出现了一个贯穿全链的概念——**固件卷（Firmware Volume, FV）**：Flash 里存放固件模块的容器。PEI/DXE 的代码并不是「一个 ROM 里的一个程序」，而是分散在一个或多个 FV 里、带元数据的模块集合（类似「固件世界的文件系统」）。引导时固件卷由 Boot Firmware Volume（BFV）优先加载，其余卷按需被发现——这正是「模块化」在启动链里的落点。

PEI 哲学上要求「越薄越好」：只做把平台点亮到 DXE 能跑的最小工作，把复杂逻辑留给 DXE。

内存点亮后还藏着一个易被忽略的里程碑：**把代码与数据从 Cache-as-RAM 迁到真正的 DRAM**。CAR 里运行的栈、堆、PEI 核心必须在 DRAM 就绪后整体「搬个家」，再停用缓存伪装。这个「临时内存到永久内存」的切换发生在 PEI 阶段的末尾，是启动链上最容易出「离奇 bug」的地方——任何遗漏的依赖（指针仍指向 CAR 地址）都会在 DXE 阶段以难以追踪的方式爆发。<span class="marginnote">S3 恢复（睡眠唤醒）也在 PEI 阶段：S3 时固件不重跑完整 POST，而是只恢复内存内容与基本设备状态，几秒钟内回到 OS——这是 PEI 的另一个主要应用场景。</span>

## 4 DXE：驱动执行环境

PEI 把 HOB 列表交出去后，系统进入 **DXE（Driver Execution Environment，驱动执行环境）**。DXE 由三部分组成：

- **DXE 基础（Foundation）**：提供 Boot Services（启动服务）、Runtime Services（运行时服务）与 DXE Services；
- **DXE 分发器（Dispatcher）**：按依赖顺序发现并执行 DXE 驱动；
- **DXE 驱动**：初始化处理器、芯片组与平台组件，把内存、控制台、存储、网络等能力抽象成 **Protocol**。

DXE 阶段还承担了一个「看起来像小事、实则是关键」的职责：**生成状态码（Status Code）**。固件在每个里程碑处发布状态码——它们被送到串口、POST 卡或日志区，正是《调试手段》一节里串口日志与 POST code 的出处。没有 DXE 阶段这套「边走边报告」的机制，工程师将完全无法在黑屏故障里定位问题。

DXE 与 PEI 的本质区别是规模与自由：PEI 只能依赖 PPI 链，DXE 则可以完全用 C 语言编写大型驱动，并通过协议总线动态扩展。**BDS（Boot Device Selection，启动设备选择）** 在 DXE 基础上运行，负责执行平台启动策略：枚举控制台、按 `BootOrder` 变量顺序尝试引导项。

DXE 阶段还引入了另一个高特权角色——**SMM（System Management Mode，系统管理模式）**。SMM 是一套独立于主操作系统的处理器模式：硬件事件（如 ACPI 电源管理、热插拔）触发 **SMI 中断**，CPU 切进 SMRAM 里的固件代码执行，结束后切回原现场。SMM 对 OS 几乎不可见、运行在最高特权，是平台里「比内核还深」的一层代码——它的安全边界会在本专题《固件安全》一节重点讨论。<span class="marginnote">SMM 的存在常让初学者困惑：「固件不是已经交棒给 OS 了吗？」其实 SMM 是「OS 在世却绕开 OS」的固件代码：它靠硬件 SMI 激活，不依赖 OS 调度。这解释了为什么历史上 SMM 是攻击者垂涎的隐藏层——见《固件安全》里 SMM rootkit 一节。</span>

DXE 阶段结束时，系统已经具备完整的 Boot Services——但 OS 一旦调用 `ExitBootServices()`，这些 Boot Services 的内存就会被回收，系统进入 **TSL（Transient System Load，临时系统加载）**，把控制权交给 OS Loader。

DXE 分发器还有一个值得注意的行为：**它按依赖（dependency）而不是按文件顺序执行驱动**。每个 DXE 驱动在固件卷里声明自己的 `[Depex]`（依赖表达式，如「需要某 Protocol 已安装」），分发器构建一张有向依赖图，反复扫描直到所有可达驱动都被执行。这保证了「驱动 A 依赖驱动 B」时，无论固件卷里谁先谁后，B 一定先跑——这也是 UEFI 能热插拔、能延迟加载驱动的基础。

## 5 从 BDS 到 OS：一次接力

整个链条可以用一张时序表概括：

| 阶段 | 核心任务 | 临时状态 | 产物 |
| --- | --- | --- | --- |
| SEC | 建立信任根与 CAR | 缓存当内存 | 引导固件卷入口 |
| PEI | 点亮 DRAM、S3 恢复 | PPI + HOB | HOB 列表 |
| DXE | 协议总线、驱动 | Boot/Runtime 服务 | 完整服务表 |
| BDS | 选启动项、建控制台 | BootOrder 变量 | 引导介质 |
| TSL | 加载 OS Loader | 已 ExitBootServices | 内核内存布局 |
| RT | 运行时服务 | 常驻内核 | 变量、计时、重置 |

读完这张表，值得停下来问一句：**为什么要分成这么多阶段？** 答案藏在「资源逐级解锁」里——启动早期没有 DRAM、没有大容量存储、没有中断控制器，代码只能在极窄的环境里做极少量的事；每解锁一项资源，就多一个「更舒适」的阶段来承接下一项初始化。分阶段不是设计洁癖，而是**把「逐步解锁硬件资源」这件事变成可管理、可调试、可度量的工程**。

另外，启动链还必须容纳**异常路径**：固件更新（capsule）、恢复（recovery）、S3 都可能在引导早期介入。所以现代 PI 固件的六阶段并非「一条直线走到底」，而是带着**分支**的图——这也是为什么调试时「先定位阶段」比「瞎看日志」高效得多。

还有一条接力线容易被忽略：**内存地图的交接**。传统 BIOS 用中断 `INT 15h/E820` 把「哪段内存可用、哪段被保留」告诉 OS；UEFI 则通过 `GetMemoryMap()` 返回 EFI 内存描述符数组。OS 内核拿到的第一张「物理内存地图」，其实是固件在 PEI/DXE 阶段一点一点拼出来的——**内存布局的最终解释权，一直攥在固件手里**。

**易错点｜辨析：** 很多人以为「BIOS 自检」是一个程序从头跑到尾。实际上 PI 架构把它切成六段，每段有不同的代码形态、不同的内存策略、不同的服务范围。**看一条启动日志时，先判断它在哪一段**——是 CAR 里跑的 SEC/PEI，还是 HOB 已就绪的 DXE，这决定了你该用哪种调试手段（见本专题《调试手段》）。

## 6 小结

- x86 复位向量固定在 `0xFFFFFFF0 = 2^{32} - 16`，那里只有一条跳转指令，整条启动链由此开始。
- **SEC** 建立信任根与 Cache-as-RAM 临时内存；**PEI** 点亮 DRAM 并产出 HOB 列表。
- **DXE** 提供 Boot/Runtime Services 与协议总线，**BDS** 按 `BootOrder` 选择启动项。
- 各阶段靠**明确定义的数据结构（PPI、HOB、Protocol）**接力，而非共享全局变量。
- OS 调用 `ExitBootServices()` 后，Boot Services 消失，进入 TSL/RT 阶段——固件的「治理」就此移交操作系统。
- 把这条链记成一张「里程碑图」：**复位向量 → CRTM/SEC → CAR → PEI/DRAM → HOB → DXE/协议 → BDS → ExitBootServices → OS**，每一步都有明确的产物与可调试的检查点。
- 顺带一提 **S3 唤醒**是启动链的「快捷模式」：休眠唤醒不重跑完整 POST，固件只做「恢复内存镜像 + 重新初始化显示/存储」，通常几秒内回到 OS——理解这条链后，你会明白为什么 S3 比冷启动快这么多。
- 微码补丁在复位后、固件正式跑起来之前加载——这就是为什么「升 BIOS」常与「修 CPU 漏洞」绑在一起。

在下一节，我们跳出 x86 特定的六阶段，进入 UEFI 体系本身：驱动模型、Protocol 总线、UEFI Shell 与变量服务——这是理解固件如何「接口化」的关键。
