## 为什么从时间推进机制开始

仿真就是「在虚拟时间里重演系统」，所以整个引擎的心脏是**仿真时钟**——它怎么走、走到哪、停下来处理什么，决定了模型的正确性与效率。<span class="marginnote">同一个物理系统可以用三种不同的世界观来仿真：站在「事件」看、站在「活动」看、站在「实体」看。三者殊途同归，但代码结构与调试难度差别很大。理解它们，等于拿到了阅读一切仿真软件（SimPy、Arena、AnyLogic）源码的钥匙。</span>这一篇把三种经典推进机制讲透，并给出选型准则。它对接第一篇的「实体、状态、事件」四件套，也呼应第二级《操作系统》里调度器的设计思路——事件循环与 FEL 几乎是操作系统就绪队列的孪生兄弟。

## 1 仿真时钟推进的两种策略

仿真时钟不是真实时钟，它只记录**模型时间**（model time），跳过多余的闲时。推进方式有两种根本不同的哲学。

**固定步长推进（fixed-increment）**：时钟每前进一个固定 $\Delta t$ 就停下来，检查这段时间内有没有状态变化发生。适合状态连续演化的系统，也用于把离散问题近似化——但步长选大了会漏事件，选小了又浪费计算。

**下一事件推进（next-event）**：时钟直接跳到**下一个事件发生的时刻**，处理完该事件，再从所有待处理事件中挑最早的下一个。两次事件之间状态不变，所以中间的时间全部跳过。<span class="marginnote">下一事件推进是离散事件仿真的主流。它之所以高效，正因为利用了「状态只在事件时刻跳变」这一事实——时间被压缩成一段段跳跃，而不是一格格扫描。</span>

离散事件系统仿真默认采用**下一事件推进**，它的心跳数据结构是**未来事件表（Future Event List, FEL）**。（若只能带走一句话：**离散事件仿真默认「下一事件推进」，而把它执行好，靠的就是一张高效的 FEL。**）

## 2 事件调度法（Event Scheduling）

**事件调度法**以**事件**为基本单位组织仿真：每一类事件都有一个处理子程序，仿真器反复执行「取最早事件 → 推进时钟到该时刻 → 执行该事件的处理逻辑」。

核心数据结构是 FEL：一张按时间排序的「待发生事件」清单。每个事件记录三要素：**发生时刻、事件类型、相关实体的指针**。

处理一个「顾客到达」事件时，处理器要做三件事：

1. **更新状态**：把顾客加入队列、更新队列长度 $N(t)$；
2. **调度新事件**：计算该顾客的服务完成时刻，把一个「服务结束」事件插入 FEL；
3. **可能调度另一类事件**：计算下一位顾客的到达时刻，把下一个「到达」事件插入 FEL。

于是 FEL 不断「消费事件、又生出新事件」，像一台永不停摆的机器。<span class="marginnote"><strong>FEL 插入与取出的效率决定仿真速度</strong>。线性表插入是 $O(n)$，堆（heap）能把取最小与插入都做到 $O(\log n)$——仿真语言内部几乎都选堆实现。这与操作系统用优先队列调度进程是同一件事。</span>

实际实现里 FEL 的每个条目还常带**优先级键**：同一时刻的多个事件先按优先级排序，再按进入 FEL 的先后排序——这保证「同时事件」的处理顺序确定、可复现，不会随迭代次序漂移。

## 3 活动扫描法（Activity Scanning）

**活动扫描法**换了一个世界观：不再等事件上门，而是**周期性地检查「活动」发生的条件**。每个**活动（activity）**由两部分定义：**条件（condition）**与**动作（action）**。

例如「服务开始」这个活动：条件是「服务台空闲 且 队列非空」；动作是「取出队首顾客、服务台置忙、调度服务完成时间」。仿真器在每个时刻扫描所有活动的条件，条件成立的就把动作执行一遍，直到本轮没有任何条件可满足，再推进时钟。

活动扫描的优缺点与事件调度正好互补：

**优点**：条件直接建模了真实规则，因果逻辑直观，适合条件变化频繁的系统。
**缺点**：每个时刻都要扫描**全部**活动，大量时间花在检查不成立的条件上；且若条件在同一时刻连锁成立，可能出现执行次序上的微妙歧义。

活动扫描特别适合「条件驱动」的系统：库存补货——只要库存低于红线就补货——这类规则用条件描述，比拆成事件链更自然。

## 4 过程交互法（Process Interaction）

**过程交互法**把视角从「系统」转向「实体」：每个实体是一段**进程（process）**，它沿着自己的生命周期一路「经历」事件，遇到需要等待的情况就挂起，条件满足再继续。

顾客的进程大致长这样：到达 → 若服务台忙则等待 → 占用服务台 → 服务 → 释放服务台 → 离开。写成伪码：

```
process customer():
    arrive()                        # 到达，登记进入系统
    if server is busy: wait(queue)  # 忙则挂起在队列上
    seize(server)                   # 占用服务台
    use(service_time)               # 服务耗时，模拟器自动调度
    release(server)                 # 释放服务台
    depart()                        # 离开
```

这里 `use(service_time)` 这一行，仿真引擎会自动生成「服务完成」事件并把进程挂起——**进程被挂起时，控制权交还给仿真器**；事件发生时，被唤醒的进程从断点继续执行。<span class="marginnote">「挂起-唤醒」是过程交互法的灵魂，它与操作系统里的<strong>协程 / 用户级线程</strong>几乎同构——SimPy 在 Python 里正是用 `yield` 实现的，而 Python 的 `asyncio` 事件循环也与它神似。学懂了过程交互，等于同时学懂了协程调度。</span>

过程交互法最贴近人的直觉，是 Arena、SimPy 等主流工具默认采用的范式。

不过过程交互也有代价：每个挂起进程都保存着一份完整的调用栈（当前位置 + 局部变量），数千个并发顾客就是数千份栈；而事件调度法只保存状态与 FEL，内存更省——这是高性能仿真倾向事件调度的又一原因。

## 5 三阶段法（Three-Phase Method）

工程上常用一种综合方案：**三阶段法**。它把事件分成两类：

**A 类（定时事件 / B 事件）**：在确定时刻必定发生的事件，如「到达」——时间一到就执行，无需检查条件。
**B 类（条件事件 / C 事件）**：条件满足才发生的事件，如「服务开始」——要扫描条件。

每一轮循环固定三段：**A 段**把到期的定时事件全部执行；**B 段**反复扫描条件事件，直到没有条件可满足；**C 段**推进时钟到下一 A 类事件的时刻。

三阶段法把「确定性」与「条件性」分层处理，既保留了活动扫描的表达力，又避免了它的盲目扫描——是工业级仿真引擎中最稳健的实现之一。

举个例子：银行柜台的「顾客到达」是 A 类事件——时间一到必然发生，无需检查条件；「开始服务」是 B 类事件——要等「服务台空闲 且 队列非空」才发生。三阶段法的每一轮循环：A 段执行到期的到达，B 段反复扫描「能否开始服务」，C 段把时钟推进到下一个到达时刻。<span class="marginnote">这样一来，到达的确定性由 A 段保证，服务启动的条件性由 B 段覆盖，两类逻辑各司其职、互不混淆——这正是三阶段法在工程上比纯活动扫描稳健的原因。</span>

## 6 核心对比：三种机制的取舍（纯概念主题）

本主题无复杂公式，用一张核心对比表替代公式解析：

| 维度 | 事件调度 | 活动扫描 | 过程交互 |
| --- | --- | --- | --- |
| 世界观 | 系统视角：事件 | 系统视角：活动 | 实体视角：进程 |
| 推进节拍 | 下一事件推进 | 扫描 + 时间推进 | 事件推进 + 挂起/唤醒 |
| 主要结构 | 未来事件表 FEL | 活动条件表 | 进程栈 / 挂起队列 |
| 表达复杂规则 | 中（需拆成事件链） | 强（条件即规则） | 强（顺序直观） |
| 时间开销 | 低，$O(\log n)$ 堆 | 高，每步全表扫描 | 中 |
| 典型语言 | 手写仿真 / SimPy 底层 | 老式仿真语言 | Arena / SimPy / AnyLogic |

**选型准则：** 新手与复杂业务流程优先**过程交互**；需要精细控制与最高性能选**事件调度**；规则高度条件化且变化频繁时考虑**活动扫描**。<span class="marginnote">三者在表达力上是<strong>等价的</strong>——同一个系统用三种方法都能建出正确模型，差别只在写起来顺不顺手、跑起来快不快。不要纠结「哪种更高级」，而要问「哪种让我更少出错」。</span>

**辨析｜易错点：** FEL 中同一时刻可能排着多个事件，处理顺序称为**同时事件的定序（tie-breaking）**。顺序不同可能导致状态路径不同——例如「到达」与「服务完成」同时发生，先处理哪个会改变这一时刻的队长统计。规则应当预先定死（如先处理服务完成），并在文档中写明。

## 7 小结

- 时钟推进有两种：**固定步长**（易漏事件）与**下一事件**（离散系统主流）。
- **事件调度法**以 FEL 为心脏，反复「取最早事件 → 推进时钟 → 执行处理」；FEL 用堆实现可做到 $O(\log n)$。
- **活动扫描法**周期性扫描活动条件，适合条件驱动系统，但每步全表扫描开销高。
- **过程交互法**把每个实体建模成一段进程，挂起-唤醒与协程同构，是主流工具默认范式。
- **三阶段法**把「确定到达」与「条件服务」分层处理，是工业级引擎最稳健的实现。
- **同时事件定序（tie-breaking）**要预先定死并写进文档，否则队长统计随处理顺序漂移。
