## 为什么从 PlusCal 与工程实践开始

TLA+ 表达力强但符号化，劝退了很多工程师。**PlusCal** 是 Lamport 设计的「算法语言」——它长得像伪代码（变量声明、赋值、进程、标号），却能被翻译成 TLA+ 用 TLC 验证。它让「写形式化规约」的门槛降到「会写伪代码」。本篇也是形式化验证篇的收官——回到工程实践，回答「什么时候值得用、怎么用」。<span class="marginnote">PlusCal（发音 "plus-cal"）由 Lamport 在 2009 年随 TLA+ 2 发布。它不取代 TLA+——PlusCal 描述「算法流程」，TLA+ 描述「系统性质」，前者被工具翻译成后者再交给 TLC。亚马逊、微软、MongoDB 的工程师用它验证真实系统。</span>

## 1 PlusCal：把规约写成伪代码

PlusCal 的代码长这样（一个简单的「两个进程递增共享计数」）：

```tla
---- MODULE Increment ----
EXTENDS Naturals, TLC

(* --algorithm increment
variables
  x = 0;

process P \in 1..2
begin
  inc:
    x := x + 1;
end process;

end algorithm *)
====================
```

关键语法：

`variables x = 0;`：声明共享变量。
`process P \in 1..2`：定义一组进程，`\in 1..2` 生成两个进程实例。
`x := x + 1;`：赋值（非原子——PlusCal 会在每条语句之间插入「可能的交错点」）。
标号（label）：标号间的语句是**原子的**——标号定义「状态转移的粒度」。

**PlusCal 与 TLA+ 的关系**：翻译器把两个进程对 `x` 的交错执行展开成 TLA+ 状态机，TLC 检查所有可达状态（x 的合法取值）。如果期望「两个进程都加一，x 最终 = 2」，而模型显示 x 可能 = 1（两个进程同时读到 0）——**交错 bug 被自动抓到**。

PlusCal 的语法糖（`when`、`either`、`with`）让它能表达复杂的并发流程，而「标号 → 原子粒度」让工程师精确控制「哪些步骤可能交错」——这是 PlusCal 建模的核心能力。

## 2 PlusCal 建模一个共识协议

用 PlusCal 写「简化 Paxos」的骨架，感受它描述真实协议的流畅度：

```tla
---- MODULE PaxosSkeleton ----
EXTENDS Naturals, TLC

(* --algorithm Paxos
variables
  chosen = {};  \* 已选择的值集合

process Proposer = "p1"
begin
  propose:
    with v \in {0, 1} do
      chosen := chosen \cup {v};
    end with;
end process;

process Acceptor \in 1..2
begin
  learn:
    await chosen /= {};
end process;

end algorithm *)
====================
```

拆解：

**两个进程类**：Proposer（提议者）与 Acceptor（接受者）——对应 Paxos 的角色。
**`with v \in {0, 1}`**：非确定性地选一个提议值——模拟「提议任意值」。
**`await chosen /= {}`**：Acceptor 等「某个 Proposer 已选择」——模拟「学到已提交的值」。
**原子粒度**：标号 `propose`、`learn` 定义「一步」——Proposer 的提议是一步原子，Acceptor 的等待与学习是一步原子。

这个骨架可以验证一致性不变量（所有 chosen 相同）——如果 PlusCal 模型显示「两个 Acceptor 学到的值不同」，说明协议缺了「多数派相交」的约束——**用 PlusCal 推演协议，bug 在建模阶段就暴露**。真实 Paxos 的 PlusCal 规约加上轮次号、多数派投票、消息队列，几百行内可以完整建模。

## 3 工程实践：什么时候用、怎么用

形式化方法在工程里的正确姿势是「**用在该用的地方**」：

**什么时候值得用**：

**核心协议**：共识、事务、分布式锁、复制协议——错误代价高，且测试测不出边界。
**设计阶段**：写代码之前验证设计——改设计的成本远低于改代码。
**复杂交错**：任何「并发 + 网络 + 故障」组合的系统——交错空间大，人工推理不可靠。

**实践流程**（亚马逊/微软的经验）：

1. **从设计开始**：用 PlusCal 描述算法流程，TLA+ 定义正确性——在写第一行实现代码之前。
2. **渐进建模**：无故障 → 消息丢失 → 崩溃恢复——每层验证，bug 在哪层暴露就修哪层。
3. **反例驱动修复**：TLC 给反例 → 看懂交错 → 修设计或修实现 → 重新验证。
4. **模型与代码对照**：实现代码按模型的结构写，保证「模型验证的性质」在代码里成立。

**不用的地方**：业务 CRUD、无状态逻辑、错误代价可容忍的应用——测试 + 代码审查足够，不必上形式化。<span class="marginnote"><strong>辨析｜易错点：</strong>形式化验证不是「代替测试」，而是「在设计层穷举 + 实现层测试」的组合。亚马逊的经验：TLA+ 主要价值是「设计阶段的思考工具」——写规约强迫你精确、TLC 强制你面对边界——即使不跑 TLC，写 TLA+ 的过程本身就能发现设计漏洞。</span>

## 4 形式化方法的现实价值与局限

**价值**：

- **抓测试测不出的 bug**：Raft 成员变更、ZooKeeper 不一致——都是「交错」型 bug，TLA+ 是少数能系统性抓它们的工具。
- **无歧义的设计文档**：TLA+ 规约是「可执行的精确设计」——比自然语言设计文档强得多，还能当测试的「oracle」（预期行为）。
- **倒逼设计清晰**：写规约迫使你把「隐含假设」（消息顺序、故障模型）显式化——很多 bug 在显式化时就消失了。

**局限**：

- **模型 ≠ 实现**：验证的是抽象模型，实现细节（内存模型、IO 调度、GC）不在模型里——模型安全的系统实现仍可能有 bug。
- **学习曲线**：TLA+/PlusCal 需要专门学习；「抽象粒度」的判断依赖经验。
- **状态爆炸**：完整系统无法穷举，只能验证「缩小的模型」——结论的推广需要论证。

**结论**：形式化方法不是「银弹」，而是「核武器」——**贵、强、只对特定目标用**。分布式系统的核心协议正是它的最佳目标：错误代价极高、测试覆盖失效、而模型规模可控。

## 5 公式解析：形式化验证的投资回报

把「要不要形式化」写成成本收益模型。设设计 bug 的修复成本 $C_{\text{fix}}$、形式化验证的投入 $C_{\text{formal}}$、测试遗漏概率 $P_{\text{miss}}$：

$$
\text{ROI} = \frac{P_{\text{miss}} \times C_{\text{fix}}}{C_{\text{formal}}}
$$

拆解：

- **$P_{\text{miss}} \times C_{\text{fix}}$**：如果不验证，设计 bug 溜进实现后的「期望修复成本」——概率 × 代价。
- **$C_{\text{formal}}$**：写规约 + 跑 TLC 的投入——对核心协议通常是「人天到人周」量级。
- **ROI > 1 就该做**：当「bug 溜走的期望损失」大于「验证成本」——核心协议（共识/事务）的 bug 可能造成「数小时停机 + 数据损坏」，$C_{\text{fix}}$ 巨大；而 $C_{\text{formal}}$ 相对小——ROI 显著大于 1。
- **业务 CRUD 不该做**：$C_{\text{fix}}$ 小（重启就修）、$P_{\text{miss}}$ 低（测试够用）——ROI < 1，形式化是浪费。

这条式子的工程含义：**形式化验证是「高风险协议」的保险，不是「常规代码」的装饰**。判定「要不要用」的公式很简单：**这个系统的 bug 溜到生产，代价有多大？** 代价巨大 → 值得形式化；代价可控 → 测试足够。分布式系统的核心协议恰好属于前者——这也解释了为什么 TLA+/PlusCal 在分布式领域（而非普通 Web 开发）成为标配。<span class="marginnote">「从极限到大模型」的收尾呼应：整本分布式系统教科书从「为什么需要分布式」讲到「如何证明分布式正确」——形式化验证是这条知识链的终点：它把「可信」建立在「可证」之上。与全站主线（从数学极限到大模型）一致：<strong>每个领域的尽头，都是「把直觉变成证明」</strong>。</span>

## 6 小结

- **PlusCal**：类伪代码的算法语言，翻译成 TLA+ 交给 TLC 验证——降低形式化门槛。
- 核心能力：`process` 定义进程、标号定义原子粒度、`either` / `await` 表达并发与等待。
- 工程实践：**核心协议（共识/事务/锁）在设计阶段验证**，渐进建模，反例驱动修复。
- 价值：抓测试测不出的交错 bug、无歧义设计文档、倒逼假设显式化。
- 局限：模型 ≠ 实现、学习曲线、状态爆炸——不是银弹，是「核武器」。
- 选型公式：**ROI = P(遗漏) × C(修复) / C(验证)**——高风险协议值得形式化，常规代码测试足够。
