# 次级索引的分区：局部索引与全局索引

## 为什么从次级索引的分区开始

前几篇的分区都假设「按主键查」——给定键就能定位分区。可真实查询几乎总是「按非主键字段查」：用户表按 `user_id` 分区，却要按 `email` 查账号；订单表按 `order_id` 分区，却要按 `customer_id` 查订单。**次级索引（secondary index）**就是为这种查询建的索引，而它**天然与主键分区冲突**——索引的键不是分区键，数据散落在所有分区。<span class="marginnote">DDIA 把次级索引的分区策略分成两派：<strong>局部索引（本地索引）</strong>——每个分区只管自己那一片的索引；<strong>全局索引</strong>——索引独立于数据分区，按索引键再分一次。两派各解决一半问题，也各留下一个痛点。</span>

## 1 局部索引：分区内自建索引

**局部索引（local index / 本地索引）**：每个分区只索引**本分区**的数据。查询时不知道数据在哪个分区，就**把查询广播到所有分区**，各分区在自己的索引里查，返回结果，客户端合并——这叫**分散/聚集（scatter/gather）**。

- **优点**：写简单——数据写到哪个分区，索引就在哪个分区更新，无跨分区写。
- **缺点**：**读昂贵**——一次次级索引查询要扫描所有分区（scatter），再合并结果（gather）。分区多时，读延迟随分区数线性增长。

典型实现：**按文档分区的次级索引**（如 MongoDB 的默认、Elasticsearch 的每个分片自建倒排索引）。Elasticsearch 的搜索正是 scatter/gather 的典范——一个查询打到所有分片，各分片返回 top-N，协调节点合并排序。它好用是因为搜索场景「宁要全扫也要相关性」，而 OLTP 的点查用 scatter/gather 就太贵了。<span class="marginnote"><strong>辨析｜易错点：</strong>scatter/gather 的「gather」有经典的合并语义问题：若每个分区只返回 top-N，合并后可能丢掉全局 top-N——因为某个分区的局部 top-N 之外的数据可能在全局排更前。搜索系统的「分布式 top-K」因此需要每分片返回更多候选（top-K×分片数）再精确合并。</span>

## 2 全局索引：按索引键再分一次

**全局索引（global index）**：次级索引**独立于数据分区**，按**索引键**再分一次——`email` 索引按 email 哈希分区，`customer_id` 索引按 customer_id 哈希分区。每个索引分区覆盖「索引键的一段范围」，但不覆盖「对应的数据」——数据在别的分区，索引指向它。

- **优点**：**读是点查**——给定索引键，哈希定位到索引分区，一次读取。没有 scatter/gather。
- **缺点**：**写跨分区**——写一条数据，要更新数据分区 + 所有相关索引分区。一个写变成多个分布式写，且写入不同分区不是原子的。

全局索引的写问题引出一个经典分叉：**同步更新 vs 异步更新**。

- **同步更新（同步全局索引）**：写数据时同步更新所有索引，保证索引即时一致。代价是写变慢、且跨分区写入需要事务（否则部分成功部分失败）。
- **异步更新（异步全局索引）**：数据先写主分区，索引后台异步重建。写快，但**索引暂时滞后**——按索引查可能查不到刚写的数据（读己之写问题又回来了）。DynamoDB 的 GSI（全局二级索引）默认就是异步更新，有「最终一致」的读语义。<span class="marginnote">全局索引的「写放大」是它的硬伤：每写一条数据要更新数据分区 + N 个索引分区，写吞吐被索引数稀释。DynamoDB 的 GSI 上限（一个表最多 20 个 GSI）与「每个 GSI 有自己的吞吐配额」就是对这个代价的工程承认。</span>

## 3 局部 vs 全局：一张对照表

| 维度 | 局部索引（本地索引） | 全局索引 |
| --- | --- | --- |
| 索引范围 | 每个分区索引本分区数据 | 索引独立分区，覆盖全部数据 |
| 写路径 | 数据 + 索引同分区，无跨分区写 | 数据 + 多个索引分区，跨分区写 |
| 读路径 | 广播到所有分区（scatter/gather） | 按索引键点查，一次定位 |
| 一致性 | 数据与索引天然一致 | 同步（原子难）或异步（滞后） |
| 典型系统 | Elasticsearch 分片、MongoDB | DynamoDB GSI、HBase 二级索引 |
| 适用 | 搜索、分析（可接受全扫） | OLTP 点查（要低延迟） |

通读要点：**局部索引把麻烦放在「读」，全局索引把麻烦放在「写」**。选哪派取决于读写比与查询模式——读多写少、点查多 → 全局；写多读少、可接受全扫 → 局部。

## 4 公式解析：两类索引的读写代价

把「读 / 写代价」写成「分区数与索引数的函数」，看清取舍。设数据分区 $P$ 个，次级索引 $I$ 个：

$$
C_{\text{local}} = \underbrace{P}_{\text{读：广播所有分区}} + \underbrace{1}_{\text{写：数据+索引同区}}, \qquad
C_{\text{global}} = \underbrace{1}_{\text{读：索引点查}} + \underbrace{1 + I}_{\text{写：数据 + I 个索引分区}}
$$

拆解：

- **局部索引**：读要访问 $P$ 个分区（广播 + 合并）；写只碰 1 个分区（数据与索引同住）。$P$ 大时读是灾难。
- **全局索引**：读只碰 1 个索引分区（点查）；写要碰 $1 + I$ 个分区（数据 + 每个索引各一个分区）。$I$ 大时写是灾难。
- **关键取舍**：局部索引的代价随**分区数** $P$ 涨，全局索引的代价随**索引数** $I$ 涨——「数据切得多」还是「索引建得多」，决定了哪派更划算。

这条式子的工程读数：**分区系统里，次级索引的代价不由「单次查询」决定，由「分区数与索引数的规模」决定**。设计时要么限制分区数（局部索引适用），要么限制索引数（全局索引适用）——两头都想多，系统就两头都疼。<span class="marginnote">现代系统常走「混合」：核心查询路径建全局索引（点查快），长尾查询靠局部索引 + 全扫（可接受慢）。DynamoDB「LSI（本地二级索引）+ GSI（全局）」的组合正是这个混合策略的工程化——LSI 保「同分区范围查询」，GSI 保「任意键点查」。</span>

## 5 小结

- **次级索引**按非主键字段查数据，与主键分区天然冲突——数据散落在所有分区。
- **局部索引**（本地索引）：每区自建索引，读要 scatter/gather 全扫，写简单；适合可接受全扫的场景。
- **全局索引**：索引独立分区，读是点查，写要跨多分区（数据 + 索引），且同步写难原子、异步写会滞后。
- 取舍本质：**局部把麻烦放读端（代价随分区数涨），全局把麻烦放写端（代价随索引数涨）**。
- 混合策略（LSI + GSI）是现代系统的常见答案：核心路径点查，长尾全扫。
