## 为什么从 Redlock 的争议开始

分布式锁的「正确性」到底怎么保证？2016 年，Redis 作者 **Salvatore Sanfilippo（antirez）** 提出 **Redlock** 算法（跨多个 Redis 节点获取锁），却被 **Martin Kleppmann（DDIA 作者）** 公开质疑——这场论战成了分布式系统正确性论证的经典教材。理解它，胜过读十篇分布式锁博客。<span class="marginnote">论战脉络：antirez 2015 年发布 Redlock（Reddit 上有详述），Kleppmann 2016 年 2 月写《How to do distributed locking》质疑其安全性，antirez 回帖辩护，双方各执一词。没有「官方裁决」，但这场论战把「分布式锁的正确性」拆解得极其透彻。</span>

## 1 Redlock 算法是什么

**Redlock** 的思路：单个 Redis 节点可能故障导致锁丢失，那就**跨 N 个独立 Redis 节点**（如 5 个）获取锁，多数派成功才算拿到。

流程：

1. 客户端向 **N 个 Redis 节点**依次发送 `SET key value NX PX ttl`（若不存在则设置，带 TTL）。
2. 只要 **超过 N/2 个节点**设置成功，且总耗时 < TTL，就认为**拿到了锁**。
3. 释放锁：向所有节点发 `DEL key`。

设计目标：**即使个别 Redis 节点故障（丢锁、崩溃），多数派仍能保证「同一时刻只有一个客户端持有锁」**——它试图用「多数派」给 Redis 锁加上「容错」。

## 2 Kleppmann 的质疑：锁安全性被击穿

Kleppmann 指出 Redlock 的两个致命问题：

**问题一：锁过期与 GC 暂停**（与第 6 篇脑裂/围栏相同）：

1. 客户端 A 拿到 Redlock（多数派成功）。
2. A 被 GC 暂停 30 秒（或网络延迟），期间锁 TTL 到期。
3. 客户端 B 获取锁成功（多数派）。
4. A 恢复后继续写，B 也在写——**两个客户端同时持有锁，互斥被击穿**。

**Redlock 没有解决「锁过期」问题**——多数派只保证「获取锁时的互斥」，不保证「持有期间的互斥」。GC 暂停让 A「以为还有锁」，TTL 到期让锁「实际已被释放」——这个时间差 Redlock 无法关闭。

**问题二：时钟跳跃**。Redlock 依赖「节点间的 TTL 计时」——但 Redis 节点可以重启、时钟可以跳变。若一个节点重启后时钟回拨，它可能「接受一个早已过期的锁请求」，破坏「TTL 到期才可重新获取」的保证。<span class="marginnote"><strong>辨析｜易错点：</strong>Kleppmann 不是反对「分布式锁」本身，而是反对「Redlock 声称的『安全』」——他的论证是：Redlock 和「单 Redis 锁」面对过期问题时是同样脆弱的，多数派没有买到「更安全」，只买到了「更可用」。他主张：<strong>要安全的锁，就用带围栏令牌的方案</strong>（etcd/ZooKeeper），或接受「锁不是绝对互斥」。</span>

## 3 antirez 的反驳：锁的语义分歧

antirez 的反驳（2016 年 2 月）核心是**「锁的用途不同，正确性标准不同」**：

- **Kleppmann 的模型**：锁保护「**必须在互斥下执行**」的临界区（如「写文件」「改数据库」）——锁失效 = 数据损坏。
- **antirez 的模型**：Redlock 保护的通常是「**短临界区**」（如「抢一个任务」「递增值」）——锁失效的窗口极小，且「锁过期」在任何分布式锁（包括 etcd）里都存在。

antirez 承认「GC 暂停下没有绝对安全」，但他认为：

1. 单机 Redis 锁的故障模式是「节点挂了锁丢」——Redlock 修复的是这个（用多数派）。
2. Kleppmann 说的「GC 暂停 + 过期」是**所有 TTL 锁的通病**，不是 Redlock 特有的。
3. 工程上「锁 + 短临界区 + 可容忍的极小失效概率」是可接受的——过度追求理论安全会牺牲实用性。

**论战的实质分歧**：不是「Redlock 有没有漏洞」（有），而是「这个漏洞在你的业务里要不要命」——**正确性标准取决于锁保护的临界区价值**。<span class="marginnote">论战还纠缠了一个技术细节：antirez 认为「锁的 TTL 计时用 Redis 的单调时钟」能防时钟跳跃，Kleppmann 指出「节点重启后时钟恢复可能回拨」。Redis 后来确实把 TTL 计时改成了单调时钟（避免 NTP 跳变影响），但「重启回拨」的极端情形仍存在——这个细节说明：<strong>分布式锁的安全性论证，连「用什么时钟」都要较真</strong>。</span>

## 4 更安全的替代方案：数据库锁 + 围栏

避开 Redlock 争议的务实答案是「用更可信的协调服务 + 围栏令牌」：

- **etcd / ZooKeeper / Chubby 锁**：共识复制的锁服务——锁状态由多数派维护，单节点故障不影响；配合**租约**自动释放、**围栏令牌**防过期写。
- **数据库锁**：用单机数据库的 `SELECT FOR UPDATE` 或「唯一约束 + 版本号」实现——单点但强一致；或用 PostgreSQL 的 advisory lock。
- **关键原则**：无论哪种锁，**拿锁后的操作要短 + 幂等 + 配围栏令牌**——锁只解决「谁有资格」，围栏解决「过期后谁安全」。

DDIA 与 Kleppmann 的共识：**如果锁真的保护「关键数据」，那么「互斥」必须由「资源端」而非「锁本身」最终保证**——资源端校验围栏令牌，让「过期持有者」的写被拒绝，这才是兜底。<span class="marginnote">「数据库锁 vs 分布式锁」的另一维度：数据库锁（`SELECT FOR UPDATE`）把「互斥」与「数据」绑在一起——锁失效即事务失败，语义清晰；分布式锁把「互斥」与「数据」分离——锁可能过期而数据照写，语义模糊。<strong>对「绝对关键」的数据，数据库锁更稳；对「协调用途」的锁（选主、任务分配），分布式锁够用</strong>。</span>

## 5 公式解析：锁失效的期望损失

把「Redlock 之争」沉淀成「选锁方案」的决策模型。设锁的失效概率 $p_{\text{fail}}$、失效时临界区损坏的代价 $C_{\text{corrupt}}$、锁方案的部署成本 $C_{\text{deploy}}$：

$$
E[\text{损失}] = p_{\text{fail}} \times C_{\text{corrupt}} + C_{\text{deploy}}
$$

拆解：

- **Redlock 的场景**：$p_{\text{fail}}$ 很小（多数派 + 短临界区），$C_{\text{corrupt}}$ 也很小（任务重复执行可幂等处理）——总损失可接受。
- **关键数据场景**：$C_{\text{corrupt}}$ 巨大（余额错乱、订单损坏）——即使 $p_{\text{fail}}$ 极小，$E[\text{损失}]$ 也大——必须用「围栏 + 资源端校验」把 $C_{\text{corrupt}}$ 降到 0（过期写被拒绝）。
- **决策含义**：选锁方案不只看 $p_{\text{fail}}$，更看「失效时你损失多少」。**Redlock 适合「失效损失小」的锁，不适合「失效损失大」的锁**——这不是 Redlock 的缺陷，是「所有无围栏锁」的共性。

这条式子的工程含义：**Redlock 之争的实质是「$C_{\text{corrupt}}$ 该归谁管」**——antirez 认为「小损失场景 Redlock 够用」，Kleppmann 认为「如果锁要安全，就必须配围栏」。两者都对，差别在「你的锁保护的到底是什么」。**结论：先量化「锁失效的代价」，再选锁方案；代价大的，无论 Redlock 还是 etcd，都要配围栏令牌兜底**。<span class="marginnote">这场论战留给分布式工程师的最大遗产不是「谁对谁错」，而是一套<strong>审视正确性论证的方法</strong>：找出系统对时钟/暂停/重启的假设，检查「假设被违背时系统还安全吗」。这套方法（Kleppmann 在 DDIA 第 8 章系统化）比任何具体锁方案都更值钱。</span>

## 6 小结

- **Redlock**：跨 N 个 Redis 节点多数派获取锁，试图用容错换安全性。
- Kleppmann 质疑：**GC 暂停 + TTL 过期**让「两个客户端同时持锁」——多数派买不到绝对互斥；时钟跳跃进一步破坏 TTL 语义。
- antirez 反驳：锁失效是所有 TTL 锁的通病；Redlock 修复的是「单节点丢锁」；短临界区 + 小损失场景够用。
- 论战实质：**正确性标准取决于锁保护的临界区价值**——小损失场景可接受，大损失场景必须围栏。
- 更安全的替代：etcd/ZooKeeper 锁（共识 + 租约 + 围栏令牌）、数据库锁（互斥与数据绑定）。
- 方法论遗产：审视任何分布式方案的「时钟/暂停/重启假设」——这套方法比 Redlock 本身更重要。
