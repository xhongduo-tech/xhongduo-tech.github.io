## 为什么从 GFS 开始

前面的理论（复制、分区、容错）需要一个「合体」的例子来落地。**GFS（Google File System）**就是那个里程碑——2003 年的论文确立了「以大规模商用硬件 + 软件容错构建分布式存储」的范式，直接影响 HDFS、Ceph，也孕育了 MapReduce 与 Bigtable。它是分布式系统「理论照进现实」的第一课。<span class="marginnote">GFS 论文（Ghemawat, Gobioff, Leung, SOSP 2003）是分布式系统领域被引用最多的论文之一。它回答的问题在当时极其激进：<strong>用廉价易坏的机器，构建永不中断的大规模文件系统</strong>。它证明了「软件容错 + 硬件廉价」可以赢过「硬件昂贵 + 软件简单」。</span>

## 1 设计动机与整体架构

GFS 面对的工作负载有三个特征：

**大文件**：GB 级文件为主，小文件存在但非重点。
**顺序追加写为主**：数据生成（日志、爬虫输出）大多是「追加」，随机覆盖写很少。
**读多、流式读为主**：大块顺序读，而不是小随机读。

架构上，GFS 采用**单主 + 多块服务器（chunkserver）**：

**单个主节点（master）**：保存所有元数据（文件名 → 块 → 位置），负责命名、权限、块管理、垃圾回收。主节点不承担数据流——数据直接客户端↔chunkserver 传输。
**多个 chunkserver**：把文件切成 **64MB 的块（chunk）**，每块默认 **3 副本** 存在不同 chunkserver 上。
**客户端**：先从主节点拿「块位置」（元数据），再直接跟 chunkserver 传数据——**元数据与数据分离**是 GFS 的性能关键。

为什么 64MB 大块？因为工作负载是大文件流式读写——大块减少元数据条目数、减少「寻找块」的开销、让客户端一次建立的长连接传输更多数据。<span class="marginnote"><strong>辨析｜易错点：</strong>GFS 的单主节点不是「单点故障」——主节点有自己的「影子主（shadow master）」与操作日志副本，挂了能恢复。但「单主」确实是 GFS 的<strong>扩展性瓶颈</strong>（所有元数据操作集中一点），也是后来 Spanner/CockroachDB 试图用「多点主」克服的局限。</span>

### 数值算例：64MB 大块省了什么

设 1 TB 的文件、每块 64MB：

- **块数** = $10^{12} / 64\times 10^6 \approx 15625$ 块——主节点只需维护约 1.5 万条元数据（每条约 100 字节），总量约 1.5MB，可常驻内存。
- 若用 4KB 小块：块数 = 2.5 亿条，元数据数百 GB——主节点内存都放不下。

这就是「大块」的量化理由：**块越大，元数据越少、内存越小、一次定位能读的数据越多**。代价是「小文件」场景块被浪费（一个 1KB 文件也占 64MB 的逻辑块）——所以 GFS 明确「小文件不是重点」。

### 术语速查表

| 术语 | 一句话含义 |
| --- | --- |
| chunk（块） | GFS 的 64MB 基本存储单元 |
| chunkserver | 存块的服务器 |
| master（主节点） | 存全部元数据的单点 |
| 影子主（shadow master） | 主节点的热备副本 |
| 记录追加（record append） | 原子追加，保证「至少一次」 |
| 租约（lease） | 主副本对块的临时写权限 |

## 2 复制与容错：三个副本 + 自动恢复

GFS 的容错模型朴素而有效：

**每块 3 副本**：分别放在**不同机架**的 chunkserver 上——单个机架断电/交换机故障不丢数据。
**副本复制（re-replication）**：chunkserver 心跳丢失 → 主节点判定它下线 → 该服务器上的块副本数不足 → 主节点调度重新复制，补齐 3 副本。
**块完整性校验（checksum）**：每块按 64KB 分片存校验和，读时验证，损坏则从其他副本修复。
**主节点选主**：主节点挂掉后，影子主接管——但 GFS 的故障转移不是「自动多数派」：它用「租约 + 慢速重启」保证一致性，比 Raft 式自动选主「粗糙」但当时够用。

**复制策略的启示**：GFS 不追求「复杂的一致性协议」，而用「简单复制 + 自动补齐」获得高可用——**在「副本数」上做冗余，比在「协议复杂度」上做文章更便宜**。这是分布式存储设计的重要一课：先保证「数据有足够的冗余」，再谈一致性。

## 3 一致性模型：宽松的写一致性

GFS 的一致性模型是「被批评最多、也最务实」的部分：

**元数据（主节点）**：强一致——单主节点串行处理所有元数据操作。
**数据（文件内容）**：**宽松的最终一致**——写操作成功返回时，**不保证所有副本立即可见**；读可能看到「部分写入」或「旧数据」，但 GFS 承诺「一次写要么在所有副本上生效，要么都不生效」（用「记录追加（record append）」保证「原子追加」）。

GFS 用**记录追加（record append）**替代随机覆盖写，绕开了大部分一致性问题：

记录追加：客户端把数据追加到文件末尾，GFS 保证「**至少一次**」——一次追加的数据作为一条完整记录被写入，即使中途失败也可能产生重复记录（客户端负责去重）。
随机覆盖写是 GFS 的「不推荐用法」——它的一致性保证更弱。

**工程启示**：GFS 把「一致性强弱」当作**设计参数**而不是「必须满足的公理」——对元数据强一致、对数据最终一致、对追加操作给「至少一次」，把一致性成本花在「需要的地方」。<span class="marginnote">GFS 的一致性设计引来许多批评（HDFS 吸取教训，在部分场景加强保证），但它的思路被广泛继承：<strong>把「强一致」留给元数据，「弱一致」留给海量数据</strong>。MapReduce 之所以能在 GFS 上可靠运行，正是因为「读旧数据」对批处理无害（重算即可）——弱一致与批处理语义天然契合。</span>

## 4 写流程：控制流与数据流分离

一次写操作（追加）的流程展示了 GFS 的巧妙设计：

1. 客户端向主节点请求「文件末尾块」的位置与租约持有者。
2. 主节点返回块所在的所有 chunkserver 位置，指定**主副本（primary）**（持有租约）。
3. **数据流**：客户端把数据发给最近的 chunkserver（链式转发到所有副本）——数据沿「客户端 → 最近的副本 → 下一副本」的链传播，不与控制流混在一起。
4. **控制流**：客户端把写请求发给 primary，primary 决定写入顺序，通知其他副本。
5. 所有副本写入成功后，primary 回复客户端「成功」。

**控制流与数据流分离**是 GFS 的性能关键：数据按「最近节点优先」的链传播，充分利用带宽；控制流走主节点/主副本，保证「写顺序一致」。这个设计被 Ceph、很多分布式存储继承。<span class="marginnote">链式数据传播（pipeline）的精髓：客户端不是「并发发给所有副本」，而是「发给最近的，再由它转发」——每条链上一跳收到数据即可转给下一跳，整体吞吐≈链路吞吐，同时避免「客户端同时扛 N 个副本的带宽」。这个技巧在 MapReduce 的 shuffle、RDMA 传输里反复出现。</span>

### 链式传播的数值账

设 3 副本、单跳带宽 $B$ = 100 MB/s，客户端到最近副本延迟低、副本间延迟 1ms：

- **并发直发**：客户端同时往 3 个副本各发一份，客户端出口带宽需 $3B$ = 300 MB/s——客户端成为瓶颈。
- **链式转发**：客户端只发一份到最近副本，该副本收下后转给下一个，再转给第三个。总耗时 ≈ 3 × (1MB 传输 + 1ms) ≈ 30ms + 2ms——**客户端带宽只需 $B$**，吞吐≈单链路带宽。

结论：**链式传播把「客户端带宽瓶颈」转移到「单条链路」**，用「多跳延迟」换「客户端不被压垮」。这正是大规模复制系统的标准数据面设计。

### GFS 一致性分层对照

| 对象 | 一致性 | 机制 |
| --- | --- | --- |
| 元数据 | 强一致 | 单主串行处理 |
| 数据（随机写） | 宽松最终一致 | 3 副本异步复制 |
| 记录追加 | 至少一次 | 原子追加 + 客户端去重 |

## 5 小结

- **GFS** 用「单主元数据 + 多 chunkserver 数据」的架构，服务大文件、顺序追加、流式读的负载。
- **64MB 大块 + 3 副本跨机架**：减少元数据、扛单机架故障；副本自动补齐 + 校验和修复。
- **一致性分层**：元数据强一致、数据宽松最终一致、记录追加「至少一次」——把成本花在需要的地方。
- **控制流与数据流分离**：数据链式传播、控制走主副本——性能关键设计。
- 启示：先保证「数据冗余」，再谈「一致性协议」；「弱一致 + 批处理语义」可以可靠共存。
- GFS 是分布式存储的范式奠基：HDFS、Ceph 与后续系统都站在它的肩膀上。
