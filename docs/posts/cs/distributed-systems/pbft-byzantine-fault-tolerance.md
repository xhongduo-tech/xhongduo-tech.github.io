## 为什么从拜占庭容错开始

Raft 与 Paxos 处理的是**崩溃故障（crash fault）**——节点死了就安静地死了。可若节点「活着但撒谎」——发送矛盾消息、篡改数据、合谋作恶——崩溃容错协议就全盘崩溃。**拜占庭容错（Byzantine Fault Tolerance, BFT）**处理的就是这种最坏的故障模型。**PBFT** 是第一个实用的 BFT 共识协议，也是区块链共识（Tendermint、HotStuff）的理论祖先。<span class="marginnote">「拜占庭将军」是 Lamport 在 1982 年提出的思想实验：拜占庭帝国的军队分驻多支，将军们只能靠信使通信，必须就「进攻还是撤退」达成一致，但其中可能有叛徒故意传递假消息。这个比喻精确刻画了「节点作恶」的分布式难题。</span>

## 1 拜占庭故障模型：与崩溃故障的差别

**崩溃故障（crash fault）**：节点停止工作，不再发任何消息。**拜占庭故障（byzantine fault）**：节点可能做任何事——不响应、延迟响应、发送错误或矛盾的消息、合谋、伪装成其他节点。

对比两者的关键差异：

| 维度 | 崩溃故障 | 拜占庭故障 |
| --- | --- | --- |
| 节点行为 | 停止 | 任意（包括撒谎） |
| 故障节点数上限 | 任意多（≤ n-1） | < n/3 |
| 消息可信度 | 可信（如实执行协议） | 不可信 |
| 典型场景 | 数据中心服务器 | 去中心化网络、敌对环境 |
| 协议 | Raft、Paxos | PBFT、Tendermint |

**为什么拜占庭容错需要 n ≥ 3f+1 个节点（f 个故障）**？因为作恶节点会「分裂人格」——向不同节点发送不同消息。一个 f=1 的三节点系统里，若一个节点作恶，向 A 说「进攻」、向 B 说「撤退」，忠诚者无法分辨哪个是真相；四节点（3f+1）时，忠诚者可以通过「交叉核对」识别并忽略撒谎者。<span class="marginnote"><strong>辨析｜易错点：</strong>「n ≥ 3f+1」是同步通信假设下的必要下界，它的证明思路是「如果 f 个作恶 + f 个可能被作恶者迷惑的忠诚节点」形成「3f 个不可信」，还剩 1 个才足够仲裁。直观记法：<strong>为了容忍 f 个撒谎者，你需要 3f+1 个人</strong>。</span>

## 2 PBFT 的核心机制：三阶段 + 视图

**PBFT（Practical Byzantine Fault Tolerance，实用拜占庭容错）**由 Castro 与 Liskov 在 1999 年提出，是第一个把 BFT 从「理论不可能」推进到「工程可用」的协议。它在**视图（view）**的框架下运行：每个视图有一个主节点（primary），主节点负责提议；其余为副本（replica）。

一次共识要经过**三阶段**：

**Pre-prepare**：主节点把请求 $m$ 广播给所有副本，声明「本视图第 $n$ 个请求是 $m$」。
**Prepare**：每个副本收到 pre-prepare 后，向其他副本广播「我认可请求 $m$」——收到 **2f+1 个**（含自己）Prepare 消息即进入 prepared 状态。
**Commit**：副本向所有人广播「我准备好了」——收到 **2f+1 个** Commit 后，执行请求并向客户端返回。

为什么需要 **2f+1**？因为在 f 个节点可能撒谎的世界里，「多数」必须是「超过 f 个坏节点 + f 个可能被迷惑的好节点」的临界值。2f+1 保证：**任何两个「法定人数」集合都相交于至少一个诚实节点**——这是拜占庭世界里「多数派相交」的对应物。<span class="marginnote">PBFT 的工程意义在于把消息复杂度控制到 $O(n^2)$（每轮全员广播），在 1999 年的硬件上可用于局域网；而更早的拜占庭协议是指数级的，完全不可用。Castro 与 Liskov 因此拿了 2005 年 SOSP 时间检验奖——「Practical」三个字值千金。</span>

## 3 视图切换：主节点作恶怎么办

主节点也可能作恶（乱提议、不提议、给不同副本不同消息）。PBFT 的应对是**视图切换（view change）**：

副本发现主节点异常（超时未收到合理提议，或收到矛盾提议），广播 view-change 消息，声明「当前视图的主节点不可信」。
收到 **2f+1 个** view-change 后，进入下一个视图，选出新的主节点。
新主节点从各副本收集「已 prepare 但未 commit」的请求，把它们带入新视图重新提议——保证已部分达成一致的请求不丢失。

视图切换是 PBFT 的活性保障：它让系统在「主节点作恶」时仍能继续推进。但注意，视图切换本身也可能被作恶节点干扰——所以它同样需要 2f+1 的门槛。<span class="marginnote">对比 Raft：Raft 的任期切换靠「日志最新者当选」的安全限制；PBFT 的视图切换靠「2f+1 签名确认 + 请求重放」的拜占庭门槛。两者的精神一致——「换人时把已达成的一致性交接好」——但实现机制完全不同，因为 PBFT 要防的不是沉默而是撒谎。</span>

## 4 公式解析：法定人数与容错界

把「为什么 2f+1」写成集合论的容错计算。设总节点 $n$，故障（拜占庭）节点 $f$，法定人数 $q$：

$$
q = 2f + 1, \qquad n \ge 3f + 1 \;\Rightarrow\; q \le n - f
$$

拆解：

- **法定人数 $q = 2f+1$**：prepare/commit 都需要 $q$ 个确认。其中最多 $f$ 个是撒谎者，所以「诚实确认」至少 $2f+1 - f = f+1$ 个——超过「可能被迷惑」的数量。
- **两个法定人数相交**：$q + q - n = (2f+1) + (2f+1) - (3f+1) = f+1 \ge 1$——任意两次共识的确认者集合必然共享至少 $f+1$ 个节点，其中至少 1 个是诚实节点，它记住了前一次共识的结果。
- **$n \ge 3f+1$** 是让 $q \le n-f$ 成立的必要条件：法定人数不能大到「超过诚实节点总数」，否则诚实节点永远凑不够数。

这条式子的工程含义：**拜占庭共识的「多数」是 2f+1，而崩溃共识的「多数」是 n/2+1——两者相差的正是「防备撒谎者」的冗余**。在拜占庭世界里，你不仅要防坏人的票，还要防「被坏人迷惑的好人」的票，所以门槛抬高了。<span class="marginnote">区块链为什么选 PBFT 家族而不选 Raft？因为区块链面对的「节点」是匿名、可作恶的矿工/验证者——崩溃容错假设「所有节点可信」在这里不成立。但 PBFT 的 $O(n^2)$ 通信让它在万级节点下不可扩展，于是有了 HotStuff（$O(n)$）、DAG-BFT 等现代改进。</span>

## 5 小结

- **拜占庭故障** = 节点任意行为（撒谎、矛盾、合谋）；**崩溃故障** = 节点停止。两者需要不同的共识。
- **拜占庭容错需要 n ≥ 3f+1**：为了容忍 f 个撒谎者，需要 3f+1 个节点；法定人数为 **2f+1**。
- **PBFT 三阶段**：Pre-prepare → Prepare → Commit，每阶段 2f+1 确认，保证「两个法定人数相交于诚实节点」。
- **视图切换**处理主节点作恶：2f+1 个 view-change 换视图，已达成一致的请求带入新视图重放。
- 对比：Raft 防沉默，PBFT 防撒谎；PBFT 是区块链共识（Tendermint/HotStuff）的理论祖先。
