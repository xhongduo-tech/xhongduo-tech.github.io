# 按键范围分区与按哈希分区

<div class="epigraph">

## 为什么从范围分区与哈希分区开始

分区键定了「用哪个字段分区」，接下来要定「这个字段的取值怎么映射到分区」——这是分区策略。两种基本策略：**按键范围分区**把键值域切成连续的段，每段一个分区；**按哈希分区**把键值哈希后散落到分区。一个保顺序、一个保均匀，各有所长，也各有代价。<span class="marginnote">DDIA 把「范围分区 vs 哈希分区」与「键 vs 复合键」组合成一张决策矩阵：范围分区适合范围查询（时间序列），哈希分区适合点查询与均匀负载。真实系统（Bigtable、Cassandra、MongoDB 分片）都在这个矩阵里选位。</span>

## 1 按键范围分区：切值域

**按键范围分区（range partitioning）**：把键的值域按大小切成若干连续的区间，每个区间对应一个分区。比如按时间戳切：`[t0, t1)` 一个分区，`[t1, t2)` 一个分区。给定键，二分查表定位分区。

**优点：范围查询友好**。查「一月份的所有日志」只需访问存一月数据的那一个（或少数几个）分区，顺序扫描即可——不需要跨分区聚合。时序数据（日志、监控、事件流）是它的天然主场。

**缺点：热点倾斜**。数据分布不均匀时，某些区间数据多、流量大。最致命的场景是**时序热点**——如果按时间切，当前时刻的数据总是写到「最新」那个分区，而旧分区无人问津：**写永远打在一个分区上**，系统退化成单点。<span class="marginnote"><strong>辨析｜易错点：</strong>「范围分区」与「范围查询」不是一回事。范围分区是存储布局（相邻键放同区），范围查询是查询类型。范围分区让「同范围的查询」变成单分区扫描，但前提是查询范围与分区边界对齐——跨边界查询仍要访问多个分区。</span>

## 2 按哈希分区：打散键

**按哈希分区（hash partitioning）**：对键计算哈希函数，再把哈希值映射到分区——哈希值对分区数取模（`hash(key) % N`）或哈希到环形空间分段。哈希让分布均匀的键散落到所有分区，**消除范围分区的热点**。

**优点：负载均匀**。只要哈希函数质量好、键值分布多样，数据与流量就近似均匀地摊到所有分区——扩展性最好。

**缺点：范围查询失效**。相邻键的哈希值随机，排序信息被哈希打散。查「一月所有日志」要扫**所有分区**再合并——跨分区聚合昂贵。哈希分区只擅长**点查询**（给确切键取值）。

DDIA 的折中方案：**哈希复合键**。用 `(user_id, timestamp)` 做复合键，哈希时只对 `user_id` 哈希、`timestamp` 保序——同一用户的记录按时间有序落在同一分区，既消除了「用户分布不均」的热点，又保住了「单用户时间范围查询」的能力。Bigtable/Cassandra 的 row key 设计大量使用这个技巧。<span class="marginnote">哈希分区有个隐蔽问题：<strong>哈希函数的均匀性 ≠ 业务负载的均匀性</strong>。哈希让「键的取值」均匀，但若业务热点是「少数大 V 用户」，这些键的哈希值虽然分散，每个大 V 的流量仍集中在其键对应的分区——哈希只均匀「键空间」，不均匀「访问模式」。</span>

### 数值算例：时序数据的写热点

设一个按「时间戳」范围分区的监控系统，分区边界按小时切：`[10:00, 11:00)` 一个分区，`[11:00, 12:00)` 一个分区……

- **写入行为**：所有新数据的时间戳都在「当前小时」，于是此刻的写全部落在「当前分区」上——**写永远打在一个分区**。若当前分区每秒写 1000 条，其它分区每秒 0 条，系统退化成单点写入。
- **改用哈希（对时间戳哈希）**：写入均匀摊到所有分区，但「查一小时的日志」要扫全部分区再合并——范围查询被毁。

要两全，用复合键 `(sensor_id, timestamp)`：先按 `sensor_id` 哈希分区（写均匀），再在分区内按 `timestamp` 有序（单传感器的时间范围查询仍是顺序扫描）。**这就是「用键结构同时解决热点与范围」的样板**——也是所有分区系统 row key 设计的通用套路。

### 分区键选择常见错误

| 错误 | 后果 | 正确做法 |
| --- | --- | --- |
| 用高基数字段当范围分区键 | 范围查询跨太多分区 | 用时间/ID 等有序维度 |
| 用低基数字段当哈希键 | 分区数量被基数卡住 | 复合键垫高基数 |
| 键分布均匀但访问有热点 | 哈希救不了访问热点 | 加后缀打散热点键 |
| 范围查询跨边界 | 仍要扫多个分区 | 设计边界对齐查询范围 |

## 3 两种策略的对比

| 维度 | 按键范围分区 | 按哈希分区 |
| --- | --- | --- |
| 映射方式 | 值域切连续段 | 哈希值映射 |
| 范围查询 | 好（单分区扫） | 差（跨分区聚合） |
| 点查询 | 好（二分定位） | 好（哈希定位） |
| 负载均匀性 | 差（分布不均即倾斜） | 好（哈希打散） |
| 时序热点 | 严重（写打最新分区） | 无 |
| 典型系统 | Bigtable、HBase、RocksDB | Cassandra、Dynamo、MongoDB（哈希分片） |

通读要点：**范围分区卖「顺序」，哈希分区卖「均匀」**。选哪边取决于查询模式：以「按范围扫」为主选范围，以「按点取」为主选哈希；要两者兼得，用复合键做「哈希前缀 + 顺序后缀」。

## 4 公式解析：两种分区的查询代价

把「范围查询」在两种分区下的代价写清楚。设共 $P$ 个分区，一个覆盖 $k$ 个键的范围查询：

$$
C_{\text{range}} = 
\begin{cases}
O(\log P + \text{分区内扫描}) & \text{范围分区：二分定位 + 单区扫} \\
O(P \cdot \text{每区扫描}) & \text{哈希分区：所有分区各扫一段再合并}
\end{cases}
$$

拆解：

- **范围分区**：二分定位到起点分区（$O(\log P)$），然后顺序扫到终点——代价与「覆盖的分区数」成正比，通常远小于 $P$。
- **哈希分区**：无法定位，**所有 $P$ 个分区都要扫一遍**再合并——代价与分区总数成正比，随系统扩容线性增长。
- **关键结论**：范围查询在哈希分区下的代价是「全表扫 + 合并」，在 $P$ 很大时是灾难；而范围分区的代价取决于「查询范围与分区边界的对齐程度」。

这条式子的工程含义：**选分区策略，先问「范围查询是主路径还是边缘需求」**。时序/日志系统范围查询是主路径 → 范围分区（但要用「时间 + 其它维度」复合键缓解写热点）；KV 缓存系统全是点查询 → 哈希分区。**没有「更好」的策略，只有「更匹配查询模式」的策略**。<span class="marginnote">工程细节：范围分区的边界是「分区配置」不是「数据属性」，边界选择影响查询对齐度。动态边界（数据多自动切分）与固定边界（预定义）各有利弊——这是下一篇「再平衡」的伏笔：范围分区的切分与合并是再平衡的核心操作。</span>

### 术语速查表

| 术语 | 一句话含义 |
| --- | --- |
| 分区键（partition key） | 决定数据进哪个分区的字段 |
| 范围分区 | 键值域切连续段，保顺序 |
| 哈希分区 | 键哈希后散落，保均匀 |
| 复合键 | 哈希前缀 + 顺序后缀 |
| 时序热点 | 当前时间戳总写最新分区 |
| 点查询 / 范围查询 | 取单键 / 扫一段键 |

选型时记住一句口诀：**「顺序」与「均匀」二选一，复合键兼得但更贵**——哈希前缀解决热点、顺序后缀保范围查询，代价是键结构变复杂、跨用户范围查询依然失效。理解这一层权衡，读后面 Cassandra/Dynamo 的分区实现时就能直接对上号。

## 5 小结

- **范围分区**切值域：范围查询好、点查询好；但分布不均会倾斜，时序数据写打最新分区。
- **哈希分区**打散键：负载均匀、点查询好；但范围查询退化为全分区扫描 + 合并。
- **复合键**（哈希前缀 + 顺序后缀）两头兼顾：Cassandra/Bigtable 的 row key 设计核心。
- 选型判据：**查询模式**——范围为主选范围，点取为主选哈希；没有绝对更好。
- 哈希均匀「键空间」不保证均匀「访问模式」，大 V 热点哈希解决不了。
- 时序系统用「时间」范围分区会写打最新分区——必须用「时间 + 其它维度」复合键打散。
- 口诀：「顺序」与「均匀」二选一，复合键兼得但更贵、跨用户范围查询仍失效。
- 范围分区的边界是配置不是数据属性：动态边界（自动切分）与固定边界各有利弊，是再平衡的伏笔。
- 哈希「键空间」均匀 ≠ 访问模式均匀：大 V 热点靠加后缀打散，哈希本身解决不了。
- 选型判据第一问：范围查询是主路径还是边缘需求——时序系统避不开写热点，必用复合键。
- 点查询两派都好；差别只在范围查询与负载均匀——先数清楚查询构成再选型。
- 哈希复合键是「哈希前缀 + 顺序后缀」：同一用户的记录按时间有序、且写均匀摊开。
- 范围分区「二分定位 + 单区扫」与哈希「全分区扫 + 合并」的代价差距随分区数放大。

- **哈希复合键的完整形态**：`(user_id, timestamp)` 让同一用户的记录按时间有序、且写均匀摊开——Cassandra 的 row key、Bigtable 的 rowkey 设计都是这个套路。
