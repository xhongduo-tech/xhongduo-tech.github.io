## 为什么从 2PC 开始

分布式事务要「跨机器原子性」：要么所有参与者都提交，要么都回滚。**两阶段提交（2PC, two-phase commit）**是最经典的解法——引入一个**协调者（coordinator）**，分「准备」与「提交」两阶段，收集所有参与者的意愿后统一裁决。它是 XA、MySQL/PostgreSQL 分布式事务、很多消息系统「事务消息」的底层。<span class="marginnote">2PC 由 Gray 在 1978 年系统化，是分布式数据库事务的事实标准协议。它的全部价值与全部缺陷都浓缩在「两阶段」里：阶段一收集意愿，阶段二广播裁决——而「收集到一半协调者崩溃」就是它的死穴。</span>

## 1 两阶段的流程

设事务涉及协调者 C 与参与者 $P_1, P_2, \ldots, P_n$。

**阶段一：准备（prepare / 投票）**

1. 协调者向每个参与者发 `prepare` 请求。
2. 每个参与者**执行事务但不提交**——把变更写入本地日志（可回滚），然后向协调者回复 `yes`（愿意提交）或 `no`（想回滚）。
3. **关键**：参与者一旦回复 `yes`，就承诺「我能提交、也愿意等你的最终裁决」——它把决定权交给了协调者，本地不能再反悔。

**阶段二：提交/中止（commit/abort）**

4. 协调者汇总所有意愿：**全部 `yes`** → 广播 `commit`；**任一 `no`**（或超时）→ 广播 `abort`。
5. 参与者收到 `commit` → 提交本地事务；收到 `abort` → 回滚；并向协调者 ack。

两阶段的语义保证：**只要所有参与者都健康，事务要么全提交要么全回滚**——因为「提交」只在所有人都投票 `yes` 后发生，而投了 `yes` 的参与者不会自行回滚。<span class="marginnote"><strong>辨析｜易错点：</strong>2PC 的「参与者投 yes」不等于「提交」。投 yes 是「承诺」——承诺「我准备好提交了，等你裁决」。这个承诺把「提交决策权」从参与者手里拿走，交到协调者手里——所以协调者崩溃时，参与者不能自行决定，只能等待。这就是阻塞问题的根源。</span>

## 2 协调者崩溃：阻塞问题

2PC 最著名的缺陷是**阻塞（blocking）**：**协调者崩溃时，所有参与者都被卡住**。参与者已投 `yes`、在等 `commit/abort`——协调者却没了。参与者无法自行决定：

- 自行提交？——其他参与者可能收到 `abort`，两边不一致。
- 自行回滚？——协调者可能正要发 `commit`，其他参与者已提交。

**无论参与者怎么选，都可能选错**——因为决定权在协调者手里，而协调者死了。于是参与者只能**无限等待**协调者恢复（阻塞），事务挂起，其持有的资源（锁、日志）也一直不释放，可能连锁拖垮整个系统。

缓解办法：

- **协调者持久化状态**：协调者把「已收到谁的 yes」落盘，恢复后重建决策——减少「协调者丢状态」导致的永久不确定。
- **协商恢复（heuristic）**：参与者等不及了，跟其他参与者「商量」——多数派定了就跟随。但这可能违背「全部 yes 才 commit」的语义，产生**启发式决策（heuristic decision）**的不一致。

DDIA 的结论很硬：**2PC 的阻塞问题没有完美解，只有缓解**——因为它的本质是「协调者单点」，而任何单点都可能崩溃。<span class="marginnote">「阻塞」的实际代价：一个事务挂起几秒甚至几小时，期间它持有的数据库锁不释放——后续所有碰这些行的事务全部排队。生产事故里，「协调者崩溃引发全局锁死」是分布式数据库的经典事故类型。这就是为什么现代系统想尽办法<strong>避免 2PC</strong>（用 Saga 或 Percolator）。</span>

## 3 2PC 与共识：为什么不是一回事

2PC 经常被误认为「一种共识」。区别很关键：

- **共识**（Raft/Paxos）：多数派即可达成决策，**容忍 f 个节点故障**——部分节点挂了照样推进。
- **2PC**：**所有**参与者都必须健康——任何一个挂了，事务就无法完成（要么等它，要么 abort）。2PC **不保证「提交」的活性**，它只保证「要么全提交要么全回滚」的**安全性**。

用 FLP 的语言：2PC 是「全参与者的同步」协议，不是「多数派的异步容错」协议。它在「参与者全部在线」时正确，但**任何一个参与者崩溃都会导致事务失败或阻塞**——这正是它不能用于「容忍节点故障的复制」的原因。复制系统要用共识（多数派），事务系统用 2PC（全体）——两者目标不同，不可互换。<span class="marginnote">这也是「2PC + 复制」的组合为什么复杂：若每个参与者本身是复制组（如 MySQL 半同步 + 2PC），协调者要等的是「每个复制组的多数派」，而不是单个参与者——于是「2PC 的全体性」被「共识的多数派」软化，系统才同时拥有原子性与可用性。现代分布式数据库（如 TiDB、CockroachDB）正是「Raft 组 + 2PC 之上层」的组合。</span>

## 4 公式解析：2PC 的可用性边界

把 2PC 的「全体健康」要求写成概率，看它在真实世界意味着什么。设每个参与者可用性 $p$，共 $n$ 个参与者：

$$
P(\text{2PC 事务可完成}) \le p^n, \qquad P(\text{某参与者崩溃}) = 1 - p^n
$$

拆解：

- 2PC 需要**所有**参与者同时健康，所以成功率是 $p^n$。
- $p = 0.99, n = 5$：成功率 $0.99^5 \approx 0.95$——**5% 的事务会因某个参与者故障而失败/阻塞**。$n = 10$：降到 90%。
- 对比共识：多数派即可，成功率 ≈ 二项分布的多数概率，$p=0.99$ 时接近 100%。
- **工程含义**：2PC 的可用性随参与者数指数下降——**参与者越少越安全**，这也是「事务操作最小化 + 参与者最少化」的数学根据。

这条式子的工程读数：**2PC 的可用性 = 所有参与者的可用性之积**。参与者多了，任何一个出问题就拖垮整个事务。所以真实系统要么把分布式事务的参与者压到最少，要么用「每个参与者自带复制组」把单个参与者的可用性提到 99.99%+。<span class="marginnote">这也解释了「单数据库实例 + 2PC 就够用」的现象：若参与者是两个 MySQL 实例（各自有本地复制组），$p$ 是「复制组的可用性」而不仅是「单实例的可用性」——复制组由共识保证高可用，2PC 只协调两组之间。分层设计让每层都用对工具。</span>

## 5 小结

- **2PC**：协调者 + 两阶段（准备收集意愿 → 提交/中止广播裁决），保证「全提交或全回滚」的安全性。
- 参与者投 `yes` = 承诺等待裁决，把决定权交给协调者——这是协议的核心机制。
- **阻塞问题**：协调者崩溃时参与者无法自行裁决，只能无限等待——单点即死穴。
- 缓解：协调者持久化、协商恢复；但阻塞没有完美解。
- 2PC ≠ 共识：2PC 要全体健康（无活性保证），共识要多数派（容忍故障）——目标不同不可互换。
- 可用性 = $p^n$，随参与者数指数下降——参与者最少化是第一原则。
