# 分区的动机与分区键选择

<div class="epigraph">

## 为什么从分区开始

复制把同一份数据放到多台机器，但每台机器存的还是「全量数据」——数据总量超过单机容量时，复制也无济于事。**分区（partitioning / sharding）**把数据**切成互不相交的子集**，每个子集放到一台（或多台复制的）机器上：每台机器只存一片，数据总量就能横向长到机器数的容量之和。<span class="marginnote">分区与复制是正交的两维：分区决定「每一份数据在哪」，复制决定「每一份数据有几份」。每个分区可以独立复制（每个分片有自己的副本组）——这是 Cassandra、HBase、MongoDB 分片集群的通用架构。</span>

## 1 分区的动机：容量与并行度

两个动机：

**容量（capacity）**：单机装不下全部数据。分区后每台机器只存一部分，总容量 = 机器数 × 单机容量——数据量增长，加机器即可。
**并行度（parallelism）**：单机的 CPU/磁盘/网络撑不起全部请求。分区后每个分区的读写只落在对应机器上，吞吐 = 机器数 × 单机吞吐。

但分区不是免费的：**跨分区的操作变难了**。单机数据库里一条 SQL 可以 JOIN 任意两张表；分区后数据在不同机器，JOIN 要跨机器聚合（shuffle），昂贵且延迟高。分区的设计目标因此是：**让绝大多数操作只涉及单个分区**，把跨分区操作压缩到最小。<span class="marginnote">「大多数操作单分区」是分区设计的第一原则。DDIA 用「社交应用」举例：把每个用户的全部数据（发帖、评论、点赞、资料）放到同一个分区，读「某用户的完整主页」就是单分区操作；跨用户查询（如「所有用户的粉丝数排名」）则要跨分区聚合，属于牺牲项。</span>

## 2 分区键：数据放哪儿的依据

**分区键（partition key）**是每行数据里用来决定「这行去哪个分区」的字段。它像数据库的「主键的地图」：给定分区键，路由到唯一分区。

选分区键的标准：

**热点要分散**：分区键的取值要尽量均匀，避免「一个值扛了大部分流量」。若用「用户 ID」做键，大 V 用户会形成热点分区。
**关联数据要同区**：经常一起被读的数据最好共享分区键，避免跨分区读。社交场景用「用户 ID」，购物车场景用「买家 ID」，时间线场景用「用户 ID + 时间范围」。
**写入要有局部性**：批量写入同一分区比分散到多区便宜。

DDIA 的经典例子：**「发帖 + 评论」按发帖 ID 分区**——一条帖子的所有评论都进同一分区，读「某帖子的全部评论」单分区完成；但「某用户的全部帖子」要跨分区扫。**「按用户 ID 分区」则相反**——用户的所有帖子同区，但「某帖子的评论」可能跨分区。**选哪个，取决于查询模式更偏哪个方向**。<span class="marginnote"><strong>辨析｜易错点：</strong>分区键选错是最贵的架构错误，因为改分区键 = 全量数据重新分布。DDIA 强调：分区键通常不能是「一个字段」，而是一个<strong>复合键</strong>——如 `<strong>`(user_id, post_id)——让「按用户查」走用户前缀、「按帖查」走完整键，两头兼顾。</span>

## 3 数据倾斜与热点

分区后的负载可能严重不均匀——**数据倾斜（skew）**。典型场景：

- **热点键（hot key）**：一个分区键值被海量访问——明星的一条微博、一个爆款商品、一个高并发直播间。
- **分区不均衡**：哈希不均匀、数据增长不均衡，导致某些分区数据多/请求密。

倾斜的代价：**一个分区变成瓶颈，整个系统的吞吐被它卡死**——分区数再多，最热的分区仍是天花板。缓解手段：

- **热点键拆细**：给热点键追加随机后缀，把它拆成多个子键（如 **`hotkey_0`、`hotkey_1`**），让流量分散到多个分区——代价是「读这个键」要多查询多个分区再合并。
- **二级缓存**：热点数据加一层缓存（Redis/本地缓存），把读流量从存储层分流。
- **监控与告警**：实时监控每个分区的 QPS/延迟，倾斜出现时人工介入。

DDIA 把倾斜称为「分区系统最难根治的问题」：**它把「单机瓶颈」变成了「单分区瓶颈」**——如果你不能容忍单机瓶颈，就必须能容忍单分区瓶颈，除非用「热点拆细」这类补救。

## 4 公式解析：分区数与热点的关系

把「分区数如何决定吞吐上限」建模。设共 $P$ 个分区，每个分区容量上限 $C$、吞吐上限 $T$，总数据量 $D$、总吞吐 $Q$：

$$
P \ge \max\!\left(\frac{D}{C},\; \frac{Q}{T}\right), \qquad \text{但瓶颈} = \max_{\text{分区 } p}(T_p)
$$

拆解：

- **下界**：分区数至少能装下数据（$D/C$）且能扛住吞吐（$Q/T$）——两个方向各自的最小值。
- **真实瓶颈**：不是「平均吞吐」，而是**最热分区的吞吐** $\max_p T_p$——只要一个分区超过 $T$，系统整体受限。
- **均匀时**：$T_p = Q/P$，$P$ 越大越安全；**倾斜时**：$T_p$ 被热点拉爆，加分区救不了——因为热点数据只在一个分区里。

这条式子的工程结论：**分区系统的扩展性上限 = 「数据能多均匀」**。均匀分布时加分区就扩容；一旦出现热点，加机器只增加「空转分区」，瓶颈分毫不减。所以分区设计的第一要务不是「分多少」，而是「热点怎么办」。<span class="marginnote">这也是「一致性哈希 + 虚拟节点」存在的原因之一：它让数据分布更均匀，减少「随机倾斜」；但「业务性热点」（明星、爆品）是哈希解决不了的，只能靠拆细键与缓存。区分「随机倾斜」与「热点倾斜」，是分区运维的第一课。</span>

## 5 小结

- **分区**把数据切成互不相交的子集，解决「单机容量/吞吐不够」；与复制正交。
- 第一原则：**绝大多数操作单分区**；跨分区 JOIN 是昂贵牺牲。
- **分区键**决定数据去向；选键要看「热点分散、关联同区、写入局部」三标准。
- **数据倾斜**是分区系统的顽疾：热点键把瓶颈从「单机」变成「单分区」，加机器无效。
- 缓解倾斜：热点键拆细、二级缓存、监控告警。
- 扩展性上限 = 「数据能多均匀」；先想清楚热点怎么办，再谈分多少区。
