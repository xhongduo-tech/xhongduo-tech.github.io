## 为什么从流批一体与 Lambda/Kappa 开始

流处理快但可能不准，批处理准但慢——现实业务往往「既要准又要快」。**Lambda 架构**用「批 + 流两套栈并行」解决；**Kappa 架构**用「一套流栈」简化。而「流批一体」（Flink 的路线）试图在引擎层面终结这场选择。理解三种架构，就是理解「准与快」在系统设计层面的全部妥协。<span class="marginnote">Lambda 架构由 Nathan Marz 在 2011 年提出（Storm 作者），Kappa 由 Jay Kreps 在 2014 年提出（Kafka 作者）。两者都是「大数据实时化」的架构答案——Lambda 用两套栈、Kappa 用一套栈，争论的焦点是「要不要维护两套代码」。</span>

## 1 Lambda 架构：批 + 流并行

**Lambda 架构**的核心：**同一份数据，用两套路径同时处理，合并结果**。

- **批层（batch layer）**：定期（小时/天）全量重算——准确、完整，但延迟高。
- **速度层（speed layer）**：实时增量计算——快、但不完整，只覆盖「批层还没算到的最近数据」。
- **服务层（serving layer）**：把「批层的历史结果」与「速度层的增量结果」**合并**，对外提供「准且新」的查询。

**优点**：正确性有批层兜底（重算即可），实时性有速度层覆盖——「鱼与熊掌兼得」。

**缺点**（批评者的核心攻击）：

- **两套代码**：同一业务逻辑要在批（如 Spark）与流（如 Flink）各写一遍——**逻辑重复，容易漂移**。
- **合并的缝隙**：批结果与流结果如何衔接（边界对齐）是易错点。
- **维护成本**：两套栈、两套运维、两套调试——复杂度翻倍。

Krepp 对 Lambda 的著名批评：**「Lambda 架构的批层和速度层计算同一件事，却要维护两份代码，任何 bug 都可能在两套里出现两次」**。

## 2 Kappa 架构：一套流栈解决一切

**Kappa 架构**的主张：**只保留流处理层，用「日志」作为统一的数据源**——把「批」重新想象成「从某个时间点重放的流」。

核心思想：

- **日志是唯一真相**：所有数据进入 Kafka（日志），它是「可重放的历史」。
- **一套流代码**：业务逻辑只写一份（如 Flink/Kafka Streams）。
- **重算是重放**：需要「重新算全量」时，不是跑批作业，而是**从日志的开头重放**——同一套流代码，只是读的是全量日志。

**为什么可行**：日志（Kafka）天然可重放——「批处理」退化为「从 0 重放的流处理」。数据处理不再是「批 vs 流」两种范式，而是「流处理 + 不同的重放起点」。

**优点**：一套代码、一套运维、无合并缝隙——简洁得多。

**缺点**：

- **重放的代价**：全量重放要重新处理所有历史数据——比批处理的全量重算可能更贵（流处理每事件开销 > 批处理每记录开销）。
- **状态重建**：重放时要从头重建状态，耗时与历史长度成正比——所以 Kappa 实践里仍需要「周期快照」加速（不是纯流）。

Kappa 的现实形态：**「流为主 + 快照加速重放」**——用快照避免「从远古重放」，用日志保证「可重放」能力。<span class="marginnote"><strong>辨析｜易错点：</strong>Kappa 不是「没有批处理」，而是「用流引擎重放日志来模拟批」——批的结果仍然存在（从 0 重放的流 = 全量计算），只是不再用「另一套批代码」。所以 Kappa 没有消灭「重算」这个操作，只是消灭了「另一套代码」。理解这一点，就理解了 Kappa 的适用边界。</span>

## 3 流批一体：引擎层面的统一

**流批一体（stream-batch unification）**（Flink 的路线）在引擎层面实现统一：

- **一个引擎**：Flink 用一套执行引擎处理「有界流（批）」与「无界流（流）」。
- **同一套 API**：批作业与流作业用同一套代码、同一套语义（窗口、状态、水印）。
- **统一容错**：批与流共享「检查点」机制——批是「终点明确的流」。

对比三种方案：

| 维度 | Lambda | Kappa | 流批一体（Flink） |
| --- | --- | --- | --- |
| 代码套数 | 两套（批 + 流） | 一套（流） | 一套（流/批同 API） |
| 数据源 | 批读 HDFS、流读 Kafka | 日志（Kafka）重放 | 有界/无界统一 |
| 重算方式 | 批作业 | 日志重放 | 有界流重跑 |
| 复杂度 | 高（两套栈） | 中 | 低 |
| 典型代表 | 早期实时数仓 | Kafka + Kafka Streams | Flink |

**趋势**：流批一体是方向——它把「要不要两套栈」的架构问题变成了「一个引擎」的工程问题。但「一体化」也意味着「批的精细优化」（SQL 优化器、列式读取）要让位给「流的通用执行」——批作业可能没有专用批引擎快。

## 4 公式解析：三种架构的「准快」权衡

把「准与快」的权衡写成统一公式。设数据的「最终准确值」为 $V_{\text{final}}$，某时刻的近似值为 $V_{\text{approx}}$：

$$
\text{误差} = |V_{\text{approx}} - V_{\text{final}}|, \qquad
\text{三种架构都在最小化「误差 × 延迟」的某种组合}
$$

拆解：

- **Lambda**：$V_{\text{approx}}$ = 批层历史值 + 速度层增量——**误差随「批层周期」变化**：批层越频繁，误差越小但批成本越高。两套代码的一致性是误差的隐性来源。
- **Kappa**：$V_{\text{approx}}$ = 流层的近似结果——**误差来自流处理本身的近似**（水位线允许延迟内的迟到数据）；最终准确值 = 从 0 重放的结果。
- **流批一体**：$V_{\text{approx}}$ = 有界流重跑的结果——**重跑即精确**（确定性），误差理论上为 0；代价是「重跑的成本」。
- **共性**：所有架构都在「误差（准确性）」与「延迟/成本」之间滑动——**没有「既零误差又零延迟」的免费午餐**，只有「把误差放在哪层」的取舍。

这条式子的工程含义：**选架构本质是选「误差的容忍方式」**——Lambda 用「批层周期」控误差（接受「周期内不完整」）、Kappa 用「流近似」控误差（接受「迟到修正」）、流批一体用「重跑」控误差（接受「重算成本」）。没有最好的架构，只有「你的误差容忍模式」匹配的架构。<span class="marginnote">业界现实：<strong>大多数「实时数仓」是 Lambda 的务实变体</strong>——流算「最近 N 小时」，批算「全量」，合并查询；Kappa 与流批一体是演进方向，但「两套栈 + 定期校准」仍然是数据团队的默认选择（因为它最简单可靠）。「理想架构」与「默认架构」之间，差着「维护成本」的考量。</span>

## 5 小结

- **Lambda**：批 + 流两套栈并行，批兜底正确、流覆盖实时——两套代码、维护成本高。
- **Kappa**：日志（Kafka）为唯一真相，一套流代码 + 日志重放模拟批——简洁但要付重放成本。
- **流批一体**：Flink 一套引擎处理有界/无界流——批是终点明确的流，API 统一。
- 对比：代码套数（2/1/1）、数据源（HDFS+Kafka/Kafka/统一）、重算方式（批作业/重放/重跑）。
- 误差的容忍方式决定选型：批层周期（Lambda）、流近似（Kappa）、重跑（流批一体）。
- 务实现实：「批 + 流 + 定期校准」仍是数据团队默认——理想架构与默认架构之间差着维护成本。
