# 三阶段提交（3PC）与其假设

<div class="epigraph">
<p>3PC 想用「多一个阶段」修复 2PC 的阻塞——它成功了，条件是：网络不会分区，而且所有参与者都活得好好的。</p>

## 为什么从 3PC 开始

2PC 的阻塞问题源于「协调者崩溃后参与者无法裁决」。**三阶段提交（3PC, three-phase commit）**加了一个中间阶段，目标是让系统在协调者或参与者崩溃时**还能自行收敛**——不让事务无限阻塞。可这个改进是有代价的：**3PC 依赖两个强假设**，而这两个假设在真实分布式系统里恰恰不成立。理解 3PC = 理解「阻塞问题的根治为何这么难」。<span class="marginnote">3PC 由 Skeen 与 Stonebraker 在 1979 年提出，比 2PC 更少被实现——因为它的假设太苛刻。DDIA 用 3PC 作为「理论优雅 vs 工程现实」的经典案例：它证明了「要消除阻塞，必须付出什么」，也证明了「那个代价多数系统付不起」。</span>

## 1 3PC 的三个阶段

3PC 在 2PC 的「准备（vote）」与「提交/中止（commit/abort）」之间插入一个**预提交（pre-commit）**阶段：

**阶段一：CanCommit（能否提交）**——协调者问所有参与者「你们能提交吗」，参与者只回答「能/不能」，**不锁定资源、不写日志**。
**阶段二：PreCommit（预提交）**——若所有人都说「能」，协调者广播 pre-commit 消息；参与者收到后**执行事务并持久化**（锁定资源、写日志），但**不最终提交**，回复 ack。
**阶段三：DoCommit（最终提交）**——协调者收到所有 ack 后广播 commit（DoCommit）消息；参与者提交并回复。

与 2PC 的关键差异：**提交裁决被推迟了**。在阶段二结束后、阶段三开始前，所有参与者都知道「大家都同意了」（pre-commit 已广播），此时即使协调者崩溃，参与者也能根据「是否收到过 pre-commit」来判断「应该提交还是中止」——**有了自行裁决的依据**，阻塞被打破。

## 2 3PC 如何避免阻塞：状态可裁决

3PC 的设计思想：**让每个参与者持有的状态足够多，以至于协调者消失时它们能独立推断出正确决策**。

参与者收到过 pre-commit → 说明「所有人都已同意」→ 协调者若崩溃，继续提交是安全的（因为所有人都准备好了）。
参与者没收到 pre-commit → 说明「还有人不确定」→ 中止是安全的（没人期望提交）。

这个「状态足够 → 决策可推断」的思路，正是 3PC 消除阻塞的机制。对比 2PC：参与者投出 yes（同意）后只有「等待」，没有任何状态能帮它推断裁决——所以只能干等。

但注意：**3PC 的「可裁决」依赖于「网络不会分裂参与者」**——如果网络分区把参与者分成两半，一半收到 pre-commit、一半没收到，两半会做出相反的决策——这就破坏了原子性。这正是 3PC 的第一个致命假设。<span class="marginnote"><strong>辨析｜易错点：</strong>3PC 消除的是「协调者崩溃」的阻塞，不是「网络分区」的阻塞。协调者挂了，参与者靠状态自决；但网络分区了，参与者连「通信」都做不到，状态自决的前提（大家能交流）就失效了——分区下 3PC 照样会不一致。它只是把「阻塞」换成了「在有同步假设下的非阻塞」。</span>

### 数值算例：协调者崩溃后 3PC 如何自决

设协调者 C、参与者 P1、P2，事务 T：

- **t0**：C 发 CanCommit，P1、P2 回「能」。
- **t1**：C 广播 PreCommit，P1 收到、P2 收到，均进入「预提交」状态并持久化。
- **t2**：C 在发 DoCommit 前崩溃。
- **P1、P2 的行为**：都「收到过 PreCommit」→ 知道所有人都已同意 → 协调者失联后各自**继续提交**。事务原子地完成，没有阻塞。

对比 2PC 在同样位置：参与者收到的是 Prepare（同意），随后协调者崩溃，参与者既不敢提交（没收到最终 commit）也不敢中止（已承诺同意）——只能等协调者复活。**3PC 把「是否同意过」从「投票里的 yes」升级为「全体确认过的 PreCommit」，这一状态差异就是阻塞与否的分水岭**。

### 2PC 与 3PC 对照

| 维度 | 2PC | 3PC |
| --- | --- | --- |
| 阶段 | Prepare → Commit | CanCommit → PreCommit → DoCommit |
| 协调者崩溃 | 参与者阻塞 | 参与者状态自决 |
| 网络分区 | 阻塞（不一致风险低） | 不一致（可能提交一半） |
| 假设 | 协调者最终恢复 | 网络不分区 + 故障可检测 |
| 工程采用 | 广泛（数据库） | 极少 |

## 3 3PC 的两个假设：它们为什么苛刻

3PC 的非阻塞性建立在两个假设上：

**假设一：网络不会分区，或分区能被忽略**。3PC 的「状态自决」依赖参与者之间能互相通信。若网络分区，两半参与者各自裁决，可能一半提交、一半中止——原子性崩溃。而网络分区是分布式系统的物理现实（第 2 篇），这个假设在真实环境基本不成立。

**假设二：所有参与者的故障模型是「崩溃-停止」且可检测**。3PC 假设「节点要么工作、要么停止」，停止后可以靠超时检测出来。但真实世界的「慢节点」会让超时误判——把「还活着但很慢」误判成「死了」，从而做出错误的自决。这个假设的严厉程度与 FLP 的「完全异步不可解」一脉相承：**要消除阻塞，就得对「慢 vs 死」有确定的判断**，而现实里没有。

DDIA 的结论：**3PC 的假设在工程上过于理想，因此几乎没有被大规模采用**——它最大的价值是理论上的：证明了「要非阻塞原子提交，代价是同步假设」。<span class="marginnote">理论上的落点：非阻塞原子提交（NBAC）问题在「部分同步」模型下可解，在「完全异步」下不可解——这是 FLP 的姊妹结果（Guerraoui 的 NBAC 分类）。3PC 是「部分同步模型」里 NBAC 的一个实现尝试；真实系统不选 3PC，不是它不够聪明，而是它的假设不接地气。</span>

## 4 公式解析：分区下的 3PC 不一致

把「分区如何击穿 3PC」写成严格推导。设事务有参与者 $P_1, P_2$，网络分区把 $P_1$ 与协调者 C 隔开、$P_2$ 与 C 连通：

$$
\text{阶段二：C 发 pre-commit 给 } P_2 \text{（收到），给 } P_1 \text{（丢失）} 
\Rightarrow P_2 \text{ 决定提交，} P_1 \text{ 决定中止}
$$

拆解：

- $P_2$ 收到 pre-commit → 状态「已同意」→ 协调者失联后按协议**提交**。
- $P_1$ 没收到 pre-commit → 状态「未同意」→ 协调者失联后按协议**中止**。
- **结果**：$P_2$ 提交、$P_1$ 中止——**同一个事务在两个参与者上结果相反，原子性被打破**。
- **根因**：3PC 的「状态自决」假设参与者之间能交换状态，而分区阻止了交换——状态自决在分区下从「安全推断」退化成「随机猜测」。

这条式子的工程含义：**3PC 用「状态自决」治好了「协调者崩溃」的病，却把「网络分区」的病灶暴露得更直接**。真实系统的做法因此转向「不依赖全体的协议」：要么共识（多数派，容忍分区的一侧继续服务），要么 Saga（放弃原子性，接受补偿）——两边的路都不完美，但都比「假设网络不分」诚实。<span class="marginnote">对比 2PC 与 3PC 在分区下的行为：2PC 在分区下「阻塞」（等，不一致风险低但不可用），3PC 在分区下「不一致」（不阻塞但可能提交一半）——这是「可用性」与「原子性」在事务协议里的又一次 CAP 式权衡。多数系统宁可 2PC 的阻塞，也不愿 3PC 的不一致。</span>

### 术语速查表

| 术语 | 一句话含义 |
| --- | --- |
| 2PC | 两阶段提交：Prepare → Commit |
| 3PC | 三阶段提交：CanCommit → PreCommit → DoCommit |
| 预提交（pre-commit） | 全体同意后、最终提交前的过渡状态 |
| 状态自决 | 参与者凭自身状态推断提交/中止 |
| 阻塞（blocking） | 协调者崩溃后参与者无限等待 |
| 原子性 | 事务要么全提交要么全中止 |

### 辨析：3PC 为什么没成为主流

3PC 的「非阻塞」很有吸引力，为什么数据库不用？因为它的两个假设（网络不分区、故障可检测）几乎总是被违反——**为了消除「协调者崩溃」这种低频故障的阻塞，它引入「网络分区」这种高频场景下的原子性破坏**。这是把「小病的代价」换成「大病的风险」：多数系统宁愿 2PC 偶尔阻塞，也不愿 3PC 在分区时悄悄提交一半。工程上「保守的慢」常优于「激进的错」。

## 5 小结

- **3PC**：CanCommit → PreCommit → DoCommit 三阶段，用「状态自决」消除协调者崩溃的阻塞。
- 机制：参与者根据「是否收到 pre-commit」独立推断提交/中止——不需要等协调者。
- **假设一：网络不分区**——分区下两半参与者各自裁决，原子性崩溃。
- **假设二：故障是崩溃-停止且可检测**——慢节点会触发超时误判，自决出错。
- 两个假设在真实分布式系统都不成立，因此 3PC 很少被采用；其价值在于理论：证明非阻塞提交需要同步假设。
- 2PC 分区下阻塞、3PC 分区下不一致——可用性与原子性的事务版 CAP。
- 3PC 把「是否同意过」升级为「全体确认过的 PreCommit」——这一状态差异就是阻塞与否的分水岭。
- 工程结论：多数系统宁要 2PC 的「保守的慢」，也不要 3PC 在分区时的「激进的错」。
- 2PC 阻塞、3PC 不一致、共识容忍分区——三条路里「多数派」路线在真实系统胜出。
- NBAC（非阻塞原子提交）在部分同步可解、完全异步不可解——与 FLP 一脉相承。
- 3PC 是「部分同步模型里 NBAC 的一次实现尝试」，思路优雅、假设苛刻、工程少用。
