# 因果一致性（Causal Consistency）

<div class="epigraph">
<p>因果性才是分布式系统里唯一不可放弃的排序——放弃它，人类读者就会在聊天里看到「未来的回复」。</p>

## 为什么从因果一致性开始

顺序一致保证「共同全序」，但代价仍然不小，而且把并发事件硬排了序。因果一致换了一个问题：**哪些顺序是应用真的不能放弃的？**答案是因果顺序——一个人发出的消息、它引用的数据、它基于的读，这些之间的先后若被颠倒，应用就出错了。**因果一致性（causal consistency）**只保证 happens-before 的因果序，对并发事件不排任何序——每个进程可以自由地以任意顺序观察并发事件。<span class="marginnote">因果一致的研究脉络：COPS（2011）、Eiger、Gentle Rain 等系统证明「因果一致可以做到线性一致的十分之一延迟、并保持分区可用」。它是「弱一致但足够语义正确」的代表，也是社交网络、IM 等应用的天然选择。</span>

## 1 定义：只排因果序

系统是**因果一致**的，如果存在一个**偏序**（happens-before），使得：

所有有因果关系的操作，按因果顺序被所有进程看到——**若 $a \to b$，任何进程看到 $b$ 时必然已看到 $a$**；
并发操作（$a \not\to b$ 且 $b \not\to a$）没有顺序约束——不同进程可以以不同顺序观察它们。

因果一致的本质是：**把「必须的顺序」从全序缩小到偏序**。它承认并发事件没有客观先后，因此不强制排序——这让它比顺序一致/线性一致便宜得多，也让它在语义上「恰好匹配」人类直觉：聊天里你只会看到「先问题、后回答」，但两条并发无关的推送谁先谁后无所谓。<span class="marginnote">因果一致最著名的动机例子：微博/聊天场景。A 发帖「我要离职了」，B 回复「恭喜！」，C 若先看到回复再看到原帖，就是违反因果一致。这种「回复先于原帖」的荒谬是因果一致要消灭的，而它与性能的矛盾则被 COPS 等系统证明可以调和。</span>

### 数值算例：一个因果颠倒的判定

设聊天室有三个操作：

- $a$：「我离职了」→ 由 A 发出。
- $b$：「恭喜！」→ B 基于读到 $a$ 后回复，于是 $a \to b$。
- $c$：「周末聚餐？」→ C 独立发出，与 $a$、$b$ 都并发。

副本必须满足的约束：**任何进程看到 $b$ 前必须先看到 $a$**。而 $c$ 可以在任意位置插入。若某副本展示顺序是「$c$ → $b$ → $a$」，用户先看到回复、后看到原帖——违反因果一致；若顺序是「$a$ → $c$ → $b$」或「$c$ → $a$ → $b$」都合法，因为 $c$ 与 $a$、$b$ 并发，可自由插入。这个例子说明：因果一致「排哪些序」与「哪些序自由」都写在偏序里，判定完全机械化。

### 一致性档位对照

| 保证 | 排序范围 | 分区行为 | 典型实现 | 延迟成本 |
| --- | --- | --- | --- | --- |
| 最终一致 | 不排任何序 | 任意副本可写 | DNS、Dynamo | 最低 |
| 因果一致 | 只排因果序 | 分区可用（依赖传播） | COPS、Eiger | 低 |
| 顺序一致 | 排全序（逻辑序） | 需协调 | 中间件 | 中 |
| 线性一致 | 排全序（真实时间） | 需多数派 | Raft、Spanner | 高 |

## 2 因果一致与最终一致的区别

因果一致常被误认为「就是最终一致」。区别在于**对因果错乱的容忍**：

**最终一致**只保证「停止写后收敛」——收敛过程中可能暂时出现因果颠倒（先看到回复、后看到原帖）。
**因果一致**保证「**任何时刻**都不出现因果颠倒」——回复永远在原帖之后可见。

收敛与不颠倒不是一回事：最终一致系统允许「短暂的时间窗口内因果乱序」，只是最终对齐；因果一致把这个窗口直接堵死。代价是系统必须**跟踪并传播因果依赖**——每个操作要携带「它依赖哪些更早的操作」，副本收到操作时若发现因果前件缺失，必须等待。

工程实现上有两条路：

**显式依赖追踪**（COPS 风格）：写操作携带依赖键列表，副本按依赖顺序执行，缺前件则阻塞等待。
**因果序列号**（PSI/Eiger 风格）：用**版本向量**或**依赖向量**给每个键的版本编号，副本只允许「因果已完整」的版本可见。<span class="marginnote"><strong>辨析｜易错点：</strong>「携带依赖」不是免费的——它在<strong>消息体积</strong>与<strong>可见性延迟</strong>上付出代价。因果一致性并没有绕开「因果信息必须跨节点传播」这一物理事实，只是把传播成本从「全序协调」降到了「依赖传播」。这也是为什么它比线性一致便宜、又比裸最终一致贵。</span>

## 3 因果一致 + 读己之写 = 会话因果一致

因果一致有一个非常实用的加强版本：**会话因果一致（causal consistency + read-your-writes）**。它额外要求：

**读己之写**：本会话写过的数据，本会话随后必能读到；
**单调读**：本会话读到的数据版本不倒退（不会先读到新、再读到旧）。

这两个保证叠加在因果一致之上，正好覆盖了绝大多数「单用户应用」的需求：用户发完消息立刻能看到、刷新不倒退、多设备之间因果不乱。DDIA 把这类「以会话为边界的因果保证」视为弱一致性里性价比最高的一档——**它给了应用「几乎像强一致」的体验，却允许系统保持分区可用与低延迟**。<span class="marginnote">会话保证由 Terry et al. 在 1994 年提出，是「弱一致性系统如何取悦用户」的经典答案。今天的移动端同步、本地缓存 + 云端存储（如 CouchDB/PouchDB）大量使用会话因果一致：设备离线也能写，联网后按因果顺序合并，用户几乎感知不到「最终一致」。</span>

### 一个版本向量的数值算例

设两副本 $X$、$Y$ 各持版本向量 $[x, y]$（$x$ 记录来自 $X$ 的写次数，$y$ 记录来自 $Y$ 的写次数）：

- 初始 $X = [0,0]$，$Y = [0,0]$。
- 客户端在 $X$ 写一次 → $X = [1,0]$。
- 客户端又在 $Y$ 写一次（基于 $X$ 的同步结果）→ $Y = [1,1]$。

此时 $[1,0]$ 与 $[1,1]$ 的因果判定：$[1,0] < [1,1]$（逐分量不超过且不全等），所以 $X$ 的写是 $Y$ 的写的前件——任何副本展示 $Y$ 的写前必须先有 $X$ 的写。若两个分量互有领先（如 $[2,1]$ 与 $[1,2]$），则判定为**并发**，可任意顺序展示。这就是「依赖集合压缩成一次向量比较」的直观版。

## 4 公式解析：因果可见性的判定

把「副本能否安全展示操作 $b$」写成依赖检查。设 $b$ 的因果前件集合为 $\text{deps}(b)$，副本 $X$ 当前已可见操作集合为 $\text{seen}(X)$：

$$
b \text{ 可见于 } X \;\Longleftrightarrow\; \text{deps}(b) \subseteq \text{seen}(X)
$$

拆解：

- $\text{deps}(b)$：$b$ 依赖的所有先前操作（它的 happens-before 前件）。聊天回复依赖原帖，转账依赖余额读取。
- $\text{seen}(X)$：副本 $X$ 已经应用并对外可见的操作集合。
- 判定：**只有当前件全部到位，$b$ 才能可见**——缺任何一个前件就阻塞。这正是「因果不颠倒」的机制保证。
- 用版本向量实现时，$\text{deps}(b)$ 压缩成一个向量，判定退化为一次向量比较——$O(\text{副本数})$，这就是 COPS 的实现核心。

工程读数：因果一致的延迟代价 = **等待缺失前件**的时间。前件通常已经在路上（同一客户端刚发的写），所以多数情况下几乎无感；只有当跨数据中心传播慢时，才会出现可见性延迟。<span class="marginnote">对比线性一致：线性一致的延迟代价 = 等待<strong>多数派共识确认</strong>（每个操作都等）；因果一致的延迟代价 = 等待<strong>因果前件到达</strong>（只有依赖缺失时等）。在广域网下，前者是每个写的固定开销，后者是稀疏的偶发等待——量级差异由此而来。</span>

### 术语速查表

| 术语 | 一句话含义 |
| --- | --- |
| happens-before 偏序 | 因果关系：$a \to b$ 表示 $b$ 依赖 $a$ |
| 因果一致性 | 只保证因果序，并发不排序 |
| 依赖集合 $\text{deps}(b)$ | $b$ 的全部因果前件 |
| 版本向量 | 记录各副本版本号，用于因果判定 |
| 会话因果一致 | 因果一致 + 读己之写 + 单调读 |
| COPS | 首个可分区可用的因果一致存储系统 |

因果一致是「谱系中间价位的甜点」：它比最终一致多一份语义承诺（不颠倒因果），却只付「依赖传播」的代价，不必付「全序协调」的代价。理解它，等于理解了「弱一致世界里哪个弱字不能砍」——下一节我们会把剩下的承诺压缩到极限，看**最终一致 + 会话保证**能把体验托到什么高度。

## 5 小结

- **因果一致性**：只排 happens-before 因果序，并发事件不排序——每个进程可自由观察并发事件。
- 与最终一致的区别：最终一致允许「收敛过程中的因果乱序」，因果一致**任何时刻都不颠倒因果**。
- 实现路径：显式依赖追踪（COPS）或因果序列号（版本向量），代价是「依赖传播」与「前件等待」。
- **会话因果一致** = 因果一致 + 读己之写 + 单调读，是弱一致性里性价比最高的一档，适配绝大多数单用户应用。
- 相比线性一致，因果一致把「每个操作的协调」换成「稀疏的依赖等待」，广域网下延迟优势巨大。
