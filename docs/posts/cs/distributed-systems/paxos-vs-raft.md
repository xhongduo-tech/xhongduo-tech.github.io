## 为什么从 Paxos 与 Raft 的对比开始

前面五篇把 Basic Paxos、Multi-Paxos、Raft 三件套拆完了。现在把它们放回同一张桌子：它们解决同一个问题（复制日志的共识），却在「可理解性、选主方式、工程细节」上分道扬镳。对比不是为了分高下，而是为了**看清共识问题的本质结构**——哪个零件是必须的、哪个只是风格选择。这篇还汇总工程实现要点，把「读懂论文」变成「能写对代码」。<span class="marginnote">6.824 的经典教学路线是「先 Paxos 后 Raft」：Paxos 给出共识的抽象骨架，Raft 给出可实现的工程封装。理解了「Paxos 是骨架、Raft 是皮肤」这个关系，再去看任何新共识变体都不慌。</span>

## 1 一张对比表：同一骨架，两种皮肤

| 维度 | Basic/Multi-Paxos | Raft |
| --- | --- | --- |
| 核心抽象 | 轮次号 + 两阶段 | 任期 + 随机超时选主 |
| Leader | 可有多个 proposer 竞争 | 强 leader，同一任期唯一 |
| 选主 | 无显式协议（隐式于 Prepare） | 显式选主（Leader Election）模块 |
| 日志一致性 | 依赖多数派相交推导 | 显式 AppendEntries 一致性检查 |
| 提交方式 | 隐式（接受即可能提交） | 显式 leaderCommit 水位 |
| 成员变更 | 论文未详述 | Joint consensus / 单节点变更 |
| 可理解性 | 出名的难 | 为可理解性而设计 |
| 典型实现 | Chubby、PaxosDB | etcd、Consul、TiKV |

通读要点：**两者共享的骨架**是「多数派 + 单调递增的轮次/任期 + 已接受值/日志的传递」；**分歧点**全是「把隐式变显式」的工程选择。Raft 没有发明新数学，只是把 Paxos 的每个角落都命名、模块化、可测试。<span class="marginnote"><strong>辨析｜易错点：</strong>「Raft 是 Paxos 的简化版」是常见误读。Raft 不是简化——它引入了 leader 限制、选举限制、提交限制等<strong>额外的约束</strong>（甚至更严格），换来的是「证明的局部化」。更准确的说法是：Raft 是「把 Paxos 的隐式决策全部显式化」的工程重写。</span>

### 为什么「可理解性」如此值钱

Paxos 论文出名地难读：Lamport 最初用寓言形式写「议会故事」，被拒稿多年。难读的代价不是「学者受罪」，而是**工程正确性**——共识算法是分布式系统里最容易被「实现得看似正确、实际有 bug」的部分。Raft 的设计目标就是让每个模块可独立推理：

- 选举：一个节点一个任期一票 → 唯一 leader。
- 复制：日志前缀匹配 → 一致性检查局部化。
- 安全：选举限制 + 提交限制 → 已提交不丢失。

**可理解性直接兑换成可验证性**：模块边界清晰，意味着可以用 TLA+ 模型检验、用 Jepsen 故障注入、用单元测试覆盖每个状态迁移。对生产系统来说，「读得懂」就是「信得过」的第一步。

## 2 工程实现要点：正确性之外的大坑

把共识跑对，论文只是第一步。生产级实现还要处理一堆「论文没写但必须对」的细节：

**持久化**：任期、投票、日志必须落盘。崩溃恢复后，若丢了任期/投票记录，可能在同一个任期投两次票 → 选出两个 leader。Raft 论文强调「持久化是安全性的组成部分，不是性能优化」。
**磁盘 fsync 顺序**：先写日志再 fsync，ack 才能发。日志没落盘就 ack，节点崩溃会「丢失已确认的提交」——这违反安全性。多数派 ack 的前提是「多数派已持久化」。
**时间常数**：心跳间隔 vs 选举超时 vs 网络抖动，三个数量级要拉开，否则频繁误判选举（颠簸）。
**快照与日志压缩**：慢 follower 追赶、新节点加入，全靠快照；快照与日志的边界处理是 bug 高发区。
**只读请求**：读也要走一致性——从 leader 读能保证线性一致，但 leader 可能已过期（分区中）。安全的读要么走 quorum 读，要么用 readIndex/lease 机制。
**领导权转移的客户端交互**：客户端把请求发给旧 leader（已过期），旧 leader 可能不知道新 leader 已产生——需要客户端重定向与新 leader 协商。<span class="marginnote">etcd 的代码是这些要点的活教材：它把「快照、压缩、WAL、选举超时随机化」全部实现得教科书级。而「只读请求」这一条，Raft 论文留白最多，6.824 的 lab 3 专门考察——分区中旧 leader 的读必须被正确拒绝或延迟。</span>

## 3 性能与可扩展性：共识的物理边界

共识系统的吞吐与延迟有硬边界，理解它们才能做容量规划：

**每笔写必须 fsync 到多数派磁盘**：磁盘 IO 是吞吐主瓶颈。批量提交（一次 fsync 攒 N 条日志）能把吞吐从每写一次 fsync 提升一个数量级。
**延迟 ≈ 多数派往返 + fsync**：局域网 1–3ms，跨地域 50–100ms。共识的延迟下限由「最远多数派」决定，不是平均。
**可扩展性是「写路径不可扩展」**：所有写走 leader，leader 是单点瓶颈。读可以拆出去（learner/只读副本），写永远串行。要横向扩写，只能分区（sharding）——把不同键分到不同共识组。

工程结论：**共识 = 正确性的成本中心**。架构上要把「需要共识的操作」压缩到最小集合（锁、元数据、配置、强一致读），其余流量走无共识路径。<span class="marginnote">这也是「为什么不是所有数据都用 etcd」的答案：etcd 3 副本的写吞吐在万级 QPS、延迟毫秒级——对元数据足够，对业务数据远远不够。真实架构里共识层是「小而硬」的，业务数据放「大而软」的存储，两者各司其职。</span>

## 4 公式解析：吞吐与延迟的工程权衡

把共识系统的吞吐建模成「批量大小与延迟」的函数。设单次 fsync 代价为 $F$，网络往返为 $R$，批大小 $b$：

$$
\text{Throughput} \approx \frac{b}{F + R}, \qquad \text{Latency}_p \approx R + \frac{b}{\text{log rate}}
$$

拆解：

- 吞吐：每批处理 $b$ 条，代价是「一次 fsync + 一次往返」；$b$ 越大吞吐越高，但……
- 延迟：批内第 $p$ 条要等「批攒满或超时」，$b$ 越大尾延迟越高。
- **最优批大小**：让「攒批的等待」与「fsync 的摊薄」平衡——流量大时批自然变大（吞吐优先），流量小时立即发（延迟优先）。

这条式子的工程读数：**吞吐与延迟是一对旋钮，批大小是它们之间的变速杆**。生产系统普遍用「超时驱动的批」：「攒满 N 条就发，否则最多等 T 毫秒」——流量大时批自然攒满（吞吐优先），流量小时超时兜底（延迟优先），在两种压力下自适应。Raft 论文没规定怎么批，但所有实现都内置了这个权衡。<span class="marginnote">对比单机数据库：单机写一次 fsync 约 0.1–1ms，共识要多数派 fsync 约 2–6ms（三副本局域网）。这「3–10 倍」的写放大就是强一致复制的物理价签——设计时要么接受它，要么把「可弱一致」的数据挡在共识系统之外。</span>

### 数值算例：写放大的账

设三副本共识集群，单次 fsync $F=1$ms、网络往返 $R=1$ms：

- **不批量**：每笔写延迟 ≈ $F+R$ ≈ 2ms，吞吐 ≈ 1/2ms ≈ 500 写/s（单 leader 上限）。
- **批量 100 条**：每批一次 fsync + 一次往返，吞吐 ≈ 100/2ms ≈ 5 万写/s——**提升两个数量级**。
- **代价**：批内第 99 条要等「攒满 100 条或超时」——尾延迟上升；流量低谷时靠超时兜底、批变小。

工程上「攒 N 条或等 T ms」把两种压力都兜住：**流量大时吞吐优先、流量小时延迟优先**。这就是为什么所有生产 Raft 实现（etcd、TiKV）都有「批 + 流水线」机制。

## 5 对照表：共识家族的变体地图

Basic Paxos 与 Raft 之外，共识还有一个「变体家族」，各在某个维度做了取舍：

| 变体 | 改变 | 代价 / 收益 |
| --- | --- | --- |
| Multi-Paxos | 选一个 leader，日志条目走 Accept | 摊薄选主成本，写路径单 leader |
| Flexible Paxos | 准备用多数派、接受用更小的法定人数 | 提升可扩展性，相交条件变化 |
| EPaxos | 无 leader，利用「不冲突命令可并发」 | 低延迟，但实现复杂 |
| ZooKeeper / Zab | 显式 epoch + 广播 | 与 Raft 同代独立设计 |
| Raft | 强 leader + 显式选主 + 成员变更 | 可理解性优先，成为工程主流 |

**一句话读懂变体地图**：所有变体都在这几个旋钮上做文章——「要不要 leader」「法定人数取多少」「成员变更怎么做」「能否并发提交」。理解 Basic Paxos 的骨架后，每个变体就是「拧一个旋钮」的产物。

**辨析｜易错点：**「变体越多越先进」是误解。实际工程里 90% 的共识系统用的就是「Raft 或 Raft 变体」——因为可理解性、工具链、社区成熟度远比「理论上更优的算法」值钱。EPaxos 等无 leader 方案的研究价值高，但部署复杂度让它们难以普及。<span class="marginnote">选共识实现的现实清单：etcd（Raft + 开源）、ZooKeeper（Zab + 协调语义）、TiKV（Raft + 分布式事务）、CockroachDB（Raft + SQL）。<strong>在工业界，「正确实现 + 维护活跃」比「算法理论更优」重要得多</strong>——这是 6.824 与生产实践共同教给工程师的一课。</span>

## 6 小结

- Paxos 与 Raft **同骨架**（多数派 + 轮次/任期 + 值传递），**异皮肤**（Raft 把隐式显式化，更强 leader、显式选主、显式提交）。
- 工程要点：**持久化、fsync 顺序、时间常数、快照、只读一致性、客户端重定向**——都是正确性的组成部分。
- 写路径不可扩展：写走 leader + 多数派 fsync，吞吐受磁盘与网络限制；读可外拆，写要扩只能分区。
- 批大小是吞吐/延迟之间的变速杆；「攒 N 条或等 T ms」是自适应的标准解法。
- 共识层应「小而硬」，业务数据放「大而软」的存储——共识是成本中心，不是流量主干。
- 可理解性兑换可验证性：模块边界清晰 → TLA+ 模型检验、Jepsen 注入、单元测试全覆盖。
- 只读请求是 Raft 论文留白最多的地方：分区中旧 leader 的读必须被拒绝或延迟。
- 三副本共识写放大 3–10 倍是强一致复制的物理价签：要么接受，要么把可弱一致的数据挡在共识外。
