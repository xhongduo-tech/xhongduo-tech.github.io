# 一致性哈希与虚拟节点

<div class="epigraph">
<p>缓存集群加一台机器，不该让一半缓存失效——一致性哈希让「增删节点」的代价从「全部重排」降到「邻近一小段」。</p>

## 为什么从一致性哈希开始

朴素哈希分区 $P$ 有一个致命问题：**分区数 $P$ 一变，几乎所有的键都要换分区**。缓存集群从 5 台扩到 6 台，取模哈希（mod P）让 5/6 的键重新映射——缓存大面积失效，数据库被打穿。**一致性哈希（consistent hashing）**就是为了让「增删节点」只影响邻近的一小部分键而设计的。<span class="marginnote">一致性哈希由 Karger 等人在 1997 年为 Web 缓存提出，后来成为 Dynamo、Cassandra、Memcached 集群、以及无数负载均衡系统的标准。它的核心贡献是：把「增删节点的影响范围」从「全部键」压缩到「哈希环上的一小段」。</span>

## 1 哈希环：把键与节点放在同一个圆上

一致性哈希把所有键与节点映射到**同一个哈希环（hash ring）**上：

1. 用一个哈希函数把节点（如 IP、主机名）映射到环上的一个位置——节点「坐在」环上。
2. 把键哈希到环上的位置——键「落在」环上。
3. **归属规则**：每个键属于「沿顺时针方向遇到的第一个节点」。

环上的结构：键 $K_1$ 落在节点 A 与 B 之间，顺时针遇到的第一个节点是 B → $K_1$ 属于 B；键 $K_2$ 落在 B 与 C 之间 → 属于 C。整个环被节点切成若干「弧段」，每段上的键属于段尾的节点。

哈希环的关键性质由此而来：**增删一个节点，只影响它的前驱与后继之间的那一段弧**。新增节点 D 插在 B 与 C 之间，只把「B 与 C 之间的键」从 C 分给 D——其余键一概不动。相比朴素取模哈希的全量重排，这是数量级的改进。<span class="marginnote"><strong>辨析｜易错点：</strong>「一致性哈希」的「一致性」指的是「哈希结果随节点集合变化的一致性」，不是「数据副本的一致性」。它解决的是「键到节点的映射稳定性」，与分布式一致性问题（CAP/共识）完全是两码事——名字像，语义无关。</span>

## 2 两个工程痛点：负载不均与热点

哈希环朴素实现有两个问题：

**问题一：负载不均**。节点数少时，哈希的随机性让「节点在环上的间距」很不均匀——可能一个节点扛了 60% 的键，另一个只扛 5%。5 个节点还好，3 个节点时严重失衡。

**问题二：热点数据**。即使分布均匀，某个键被海量访问时，它所在的节点仍是热点——一致性哈希本身不解决「业务热点」问题，只解决「映射稳定」问题。

### 数值算例：3 节点裸环的失衡

设 3 个节点随机落在环上，节点间距服从「随机三段切分」：

- 三段长度的分布：最大段平均约占全环的 $1/2$ 左右（随机切三段，最长的段期望约 55%）——**一个节点可能扛走一半以上的键**。
- 而理想均匀是每个节点各占 33%。

这就是「节点数少时裸环严重失衡」的量化：**随机落在环上的节点，其覆盖的弧段方差很大**。5 个节点时最长段降到约 45%，仍不理想；要到 10+ 个节点才接近均匀。**vnode 正是为「少节点也要均匀」而生的**。

## 3 虚拟节点：把负载摊匀

**虚拟节点（virtual nodes, vnodes）**是解决负载不均的标准手段：**每个物理节点在环上放置多个「虚拟」位置**——`A-0`、`A-1`、`A-2`……每个虚拟节点都参与哈希映射。比如 Dynamo 默认每个物理节点 128–256 个 vnode。

虚拟节点的效果：

**负载更均匀**：物理节点的键份额 = 它的所有 vnode 在环上覆盖的弧段之和。vnode 多时，各物理节点的份额趋近于均匀——这是「大数定律」在环上的体现。
**增删的粒度更细**：新增一个物理节点 = 在环上洒一批 vnode，它从所有邻居手里各「抢」一小段——影响范围被进一步摊薄，不会像单节点那样「整个弧段搬移」。
**加权能力**：给机器配不同数量的 vnode，就能让它承担不同比例的负载——大机器多配 vnode，小机器少配。

代价：**路由表变大**——节点到 vnode 的映射要维护；Cassandra 每个 vnode 就是一片数据，vnode 太多则元数据膨胀。<span class="marginnote">Cassandra 的 vnode 默认 256 个/节点，配合「每个分区有自己的复制组」；Dynamo 的 vnode 是「键空间的一段」。两者细节不同，思想一致——「一个物理节点用多个虚拟位置参与映射」。这个技巧还用于负载均衡、分布式缓存等一切「增删节点要稳」的场景。</span>

## 4 公式解析：增删节点的影响比例

把一致性哈希「增删只影响一部分」量化。设环上共有 $N$ 个节点，新增一个节点时，它随机落在一个弧段上，抢走该弧段的键。期望影响比例：

$$
E[\text{affected}] = \frac{1}{N+1}
$$

拆解：

- 环上 $N$ 个节点把环切成 $N$ 段；新增节点落在每段上的概率 ≈ 该段长度占比。
- 它抢走「落点所在那一段」的键，而那一段平均占全环的 $1/N$ 份额。
- 期望受影响比例 $= 1/(N+1)$——**节点越多，增删影响越小**。
- 对比朴素哈希（取模）：$P$ 从 $N$ 变 $N+1$ 影响比例 $\approx N/(N+1) \approx 100\%$——**一致性哈希把影响从「几乎全部」降到「约 1/N」**。

这条式子的工程含义：**一致性哈希的「稳」随节点数增长而增强**。100 个节点的集群，增删一台只影响约 1% 的键——这个「局部性」就是 Memcached 集群、Dynamo 分区能在不停服的前提下弹性扩缩的根本原因。<span class="marginnote">虚拟节点的加入把「影响比例」进一步摊薄：物理节点增删时，影响的是「它在各 vnode 上的邻居弧段」，多个小段叠加，整体影响更平滑、更可控——这是工程上几乎都用 vnode 而不用裸环的原因。</span>

### 术语速查表

| 术语 | 一句话含义 |
| --- | --- |
| 一致性哈希 | 键与节点同环，键顺时针归属首个节点 |
| 哈希环（ring） | 节点与键共享的循环哈希空间 |
| 虚拟节点（vnode） | 物理节点在环上的多个虚拟位置 |
| 取模哈希 | 朴素哈希，增删节点全量重排 |
| 影响比例 | 增删节点时重映射的键比例 |

## 5 一致性哈希 vs 范围/哈希分区的定位

一致性哈希不是范围分区/哈希分区的替代，而是「哈希分区」的**稳定性增强版**：

普通哈希分区：映射简单、分布均匀，但增删节点全量重排。
一致性哈希：保持哈希的均匀性（配合 vnode），同时让增删节点的影响局部化。
它不改变「键 → 分区」的定位方式（仍是哈希），只改变「分区 → 节点」的组织方式（环 + vnode）。

因此一致性哈希特别适合**节点集合频繁变化**的场景：缓存集群（扩容/故障频繁）、无主复制存储（Dynamo/Cassandra 的键到分区映射）、负载均衡（请求到后端节点的稳定分配）。而「节点集合稳定、需要范围查询」的场景，仍用范围分区更合适。<span class="marginnote">DDIA 对一致性哈希的评价很务实：它保证了「增删节点时，大部分键原地不动」这个稀缺性质，代价是「键的定位多一层环查找」与「vnode 元数据」。对「缓存打穿」「集群弹性」这类问题，这是其他策略给不了的。</span>

## 6 小结

- **朴素哈希（取模）** 增删节点全量重排；**一致性哈希**把影响压缩到「环上邻近一段」。
- 机制：节点与键都哈希到环上，键顺时针归属遇到的第一个节点。
- **虚拟节点**让物理节点用多个位置参与映射——负载更均匀、增删更平滑、可加权。
- 期望影响比例 $= 1/(N+1)$，随节点数增长而下降——弹性扩缩的数学基础。
- 一致性哈希适合「节点集合频繁变化」；范围查询场景仍用范围分区更合适。
- 裸环少节点时严重失衡：3 节点最长弧段可占一半以上，vnode 正是为此而生。
- vnode 还能加权：大机器多配 vnode、小机器少配，实现按容量的负载分配。
- 影响比例 1/(N+1) 随节点数下降——100 节点增删一台只影响约 1% 的键。
- 朴素取模哈希增删节点影响 ≈ 全部键；一致性哈希把它压到 ≈ 1/N——数量级改进。
- 适合缓存集群、无主复制、负载均衡等「节点集合频繁变化」场景。
- 归属规则：键顺时针遇到的第一个节点；新增节点只影响其前驱与后继之间的弧段。
- 物理节点用多个 vnode 参与映射：负载更均匀、增删更平滑、可配权——工程标配。
- 「一致性」指映射随节点集合变化的稳定性，与 CAP/共识的「一致性」无关。
- 哈希环本身不解决业务热点：热点键仍需拆细或缓存兜底。
- 环上节点把环切成弧段，键顺时针归属段尾节点——归属规则简单且稳定。
- 一致性哈希是「哈希分区」的稳定性增强版：映射仍哈希，只是「分区→节点」改用环组织。
- 期望影响比例 1/(N+1)：100 节点增删一台只影响约 1% 的键。

- **裸环 vs vnode 的边界**：节点 ≥ 10 且分布要求不苛刻时裸环可用；少节点或要加权时必用 vnode。
