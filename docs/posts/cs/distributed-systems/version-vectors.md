# 版本向量（Version Vectors）在副本系统中的应用

<div class="epigraph">

## 为什么从版本向量开始

向量时钟解决了「并发检测」，可它的维度是「进程数」——进程会崩、会重启、会随集群扩容增减，进程 ID 集合不稳定。而副本系统真正关心的是「**哪个副本持有哪个版本**」。于是有了**版本向量（version vector）**：维度从「进程」换成「副本」，专门跟踪每个副本对一条数据贡献过多少版本。<span class="marginnote">版本向量与向量时钟长得一模一样（每个副本一个格子），语义却不同：向量时钟跟踪「进程间的因果进度」，版本向量跟踪「副本对同一键的版本贡献」。DDIA 第5章明确指出这一区分，避免两者混用。</span>

## 1 副本系统的版本困境

考虑一个无主复制的键值存储，键 `cart` 有三个副本 A、B、C。客户端可以向任意副本写。若 A 写 `["牛奶"]`，随后客户端向 B 写 `["牛奶", "面包"]`，B 把版本传播给 A——这是因果更新，后写覆盖先写，没有冲突。麻烦的是**并发写**：

客户端 1 向副本 A 写 `["牛奶"]`（购物车场景）；
同时客户端 2 向副本 B 写 `["面包"]`；
两个写互为并发（没有因果联系），A 不知道 B 的写，B 也不知道 A 的写。

如果系统只存「最新值」，这俩写会互相覆盖，丢了一个用户的操作。**正确做法是保留两个版本**：`[]` 有并发后代 `["牛奶"]` 与 `["面包"]`，等客户端或反熵机制来合并。版本向量就是给每个版本贴「它是谁写出来的、在哪些副本上进化过」的标签，让「并发后代」可以被精确识别。<span class="marginnote"><strong>辨析｜易错点：</strong>「并发」在这里指的是写与写之间没有因果，而不是时间上同时发生。A 先写、B 后写但 B 没看到 A 的写，二者仍是并发——版本向量判断的是因果，不是墙钟先后。</span>

## 2 版本向量怎么工作

对每个键，系统维护一个版本向量 $V = [v_A, v_B, v_C]$，维度是副本集合。三条规则：

**写**：客户端（或副本）写值时，$V[\text{self}] \leftarrow V[\text{self}] + 1$，新值连同新向量一起保存。
**读**：读到当前值与向量，返回给客户端。
**合并（合并写）**：客户端把两个并发版本合并成新值，新向量逐维取 max，然后 $V[\text{self}] \leftarrow V[\text{self}] + 1$——表明「我看到了你们两边，现在产生了一个新版本」。

两个版本的先后判定与向量时钟完全一致：**一个向量逐维不小于另一个 → 后写覆盖先写；两个向量各有反超 → 并发，保留双版本**。区别只在维度含义：$v_A$ 不是「进程 A 的总事件数」，而是「副本 A 对这个键的写次数」。

一个具体的演算：初始 $V = [0,0,0]$，键 `cart` 值 `[]`（空购物车）。

设备 1 向 A 写：$V = [1,0,0]$，值 `["牛奶"]`。
设备 2 向 B 写：$V = [0,1,0]$，值 `["面包"]`。`["牛奶"]` 与 `["面包"]` 不可比较 → 并发，两个版本都保留。
客户端读到两个版本，合并为 `["牛奶", "面包"]`，新向量 $[1,1,0]$（逐维 max 再 A 自增得 $[2,1,0]$，取决于谁写）。
此后任何副本看到 `["牛奶", "面包"]` 都知道它覆盖了 `["牛奶"]` 与 `["面包"]`——因为逐维都不小于它们。<span class="marginnote">关键性质：<strong>单调性</strong>。新版本的向量在每一维都不小于旧版本，版本史形成一张偏序格。系统永远不需要「删」版本向量，只需在收敛时让新向量支配旧向量。</span>

### 数值算例：一次完整的并发合并

设副本 A、B、C，键 `cart` 初始 `[]`、向量 $[0,0,0]$：

1. **设备 1 → A**：写 `["牛奶"]`，向量 $[1,0,0]$。
2. **设备 2 → B**：写 `["面包"]`，向量 $[0,1,0]$。
3. **A 与 B 同步**：$[1,0,0]$ 与 $[0,1,0]$ 互有反超 → **并发**，两版本都保留。
4. **客户端读到两版本**：合并为 `["牛奶","面包"]`，向量 $[1,1,0]$；写回 C，C 向量更新为 $[1,1,0]$。
5. **此后任意副本**：看到 `["牛奶","面包"]` 的向量 $[1,1,0]$ 逐维 ≥ `["牛奶"]` 的 $[1,0,0]$ 与 `["面包"]` 的 $[0,1,0]$ → 判定为「后写」，旧版本作废。

没有一条用户操作被静默丢弃——这就是版本向量「保留合并语义」的价值。

### 术语速查表

| 术语 | 一句话含义 |
| --- | --- |
| 版本向量 | 维度=副本数，$v_A$=副本 A 对该键写次数 |
| 并发版本 | 两向量互为反超，各自有独有贡献 |
| 单调性 | 新向量每维 ≥ 旧向量，版本史成偏序格 |
| LWW | 最后写入获胜，并发时时间戳最大者胜 |
| 反熵 | 副本间后台比对、收敛版本 |

## 3 与 LWW 的关系：都保留还是只留一个

**最后写入获胜（LWW，last-writer-wins）**是另一种冲突处理：不管并发与否，**只保留时间戳最大的那个版本**。它不保留版本历史，实现简单，但会**静默丢失并发写**——两个用户同时改同一配置，后写者的「成功」把先写者覆盖得无影无踪。

版本向量与 LWW 不是互斥，而是**决策依据**：

版本向量负责回答「这两个版本是并发还是因果」；
若并发，系统可（a）保留双版本交给上层合并（如 Riak），或（b）用 LWW 强制二选一（时间戳最大者胜）。

用版本向量的系统通常「先检测并发、再决定策略」；只用 LWW 的系统「根本不检测并发」。工程取舍是：**购物车、文档编辑这类需要合并语义的数据用版本向量 + 合并；计数器、配置覆盖这类「后写必然正确」的数据用 LWW 即可**。<span class="marginnote">DDIA 提醒：LWW 的「胜出」依赖可信的时间戳。若用客户端墙钟做判据，时钟回拨会让「旧写」冒充「新写」胜出；用 Lamport 时间戳或副本单调计数器更稳。这也解释了为什么 Dynamo 里 LWW 用的是「高水位标记 + 向量时钟」而不是裸墙钟。</span>

## 4 公式解析：并发版本的判定

把「两版本是否并发」写成向量比较。设版本 $v_1$ 携带向量 $V_1$，版本 $v_2$ 携带 $V_2$：

$$
\text{concurrent}(v_1, v_2) \;\Longleftrightarrow\; \neg(V_1 \le V_2) \land \neg(V_2 \le V_1)
$$

拆解：

- $V_1 \le V_2$ 表示「$V_1$ 逐维都不大于 $V_2$」——$v_2$ 的版本史包含了 $v_1$，$v_1$ 已过时。
- 两个「不大于」都不成立：存在维度 $i$ 使 $V_1[i] > V_2[i]$（$v_1$ 知道 $i$ 副本的更新），又存在维度 $j$ 使 $V_1[j] < V_2[j]$（$v_2$ 知道 $j$ 副本的更新）——双方各有对方不知道的进度 → **并发**。
- 判定的代价是 O(n)：n 是副本数。副本数远小于进程数（副本通常个位数到数十个），所以版本向量比向量时钟更可落地。

这条式子的工程含义：**并发是「各有独有贡献」的同义语**。合并规则的目标就是造出一个「同时吸收双方贡献」的新版本，其向量逐维取 max——这正是 CRDT 的合并操作在版本维度上的对应。

### 辨析：版本向量在什么场景会「长胖」

版本向量的一个实用代价：**版本数量可能失控**。若并发写不断产生、又不及时合并，键会积累大量「兄弟版本」（sibling），Riak 称之为「sibling explosion」。缓解手段：设「兄弟版本上限」，超过即强制合并（可能丢语义）；或提示应用尽快合并；或用 CRDT 自动合并。**版本向量给了「精确识别并发」的能力，却没给「版本不增长」的承诺**——工程上要配套清理策略。

## 5 对照表：向量时钟家族的三兄弟

向量时钟、版本向量、点积（dot product）机制是同一族尺子，用一张表分清：

| 维度 | 向量时钟 | 版本向量 | 点积 / 点格 |
| --- | --- | --- | --- |
| 维度 = | 进程数 | 副本数 | 副本数 |
| 跟踪什么 | 进程间的因果进度 | 副本对键的版本贡献 | 键的版本代数 |
| 典型场景 | 跨进程因果检测 | 副本系统冲突检测 | Dynamo 的冲突检测 |
| 处理进程增减 | 难（维度不稳定） | 需槽位压缩 | 需增删维护 |
| 典型系统 | 早期分布式系统 | Riak 系 | Dynamo、Voldemort |

**一句话分清**：向量时钟管「谁先谁后的因果」，版本向量管「哪个副本写了多少版」，点积是版本向量的商用简化——Dynamo 用「高水位标记 + 向量」做 LWW 判据，本质仍是版本向量的思想。

**辨析｜易错点：**三者的数据结构长得一样（每维度一格），容易混用——用「维度含义」记：进程 → 向量时钟，副本 → 版本向量，商用键值 → 点积/向量。混淆的后果是「维度增减逻辑写错」，在集群扩容时出隐蔽 bug。<span class="marginnote">DDIA 的精确说法：<strong>版本向量 = 向量时钟应用于「单键的副本演进」</strong>，维度从「进程」收缩到「副本」。这个收缩让它在副本数可控的键值系统里更实用——这也是它与「多进程、多副本交错」的通用向量时钟的分野。</span>

## 6 小结

- **版本向量**：维度 = 副本数，$v_A$ = 副本 A 对该键的写次数；是向量时钟在副本系统里的特化。
- 写自增己格、读返回当前向量、合并逐维取 max 再自增——**单调性**保证版本史形成偏序格。
- **并发检测**：两向量互为反超即并发，系统应保留多版本而非静默覆盖。
- 与 LWW 的关系：版本向量负责「判并发」，LWW 负责「并发时二选一」；是否需要合并语义决定用哪个。
- 代价 O(副本数)，比向量时钟更可落地；Riak、Dynamo 系系统用它跟踪购物车、文档等可合并数据。
- 版本向量的尺寸随副本数增长，副本集合变化（增删）时需要「槽位压缩」管理。
- LWW 的判据要可信时间戳：用单调计数器/高水位标记，别用裸墙钟（时钟回拨会让旧写胜出）。
- 版本向量给「精确识别并发」的能力，没给「版本不增长」的承诺——需配套清理策略防 sibling explosion。
- 与 CRDT 是绝配：版本向量识别并发，CRDT 提供可交换合并，无锁收敛。
- 购物车/文档要合并语义用版本向量 + 合并；计数器/配置「后写必胜」用 LWW 即可。
- 并发判定是 O(副本数)：副本数远小于进程数，比向量时钟更可落地。
