## 为什么从分布式系统开始

从「极限」走到「大模型」，中间隔着很长的技术栈；分布式系统是其中最像「地基」的一层。今天每一个大模型，都是在一支 GPU 集群上训练出来的：训练数据被切到几千个节点上并行喂给模型，梯度经集合通信在集群里汇总，参数按层或按张量分片存放<span class="marginnote">第四级《AI 基础设施》会系统展开「数据并行、张量并行、流水线并行」与 NCCL 集合通信——它们全部建立在分布式系统的概念之上。学完本篇专题，你再去看那些训练框架的架构图，会认出每一块在讲什么。</span>。换句话说，「多台机器如何像一个整体那样工作」，是理解大模型训练与推理的第一块踏板。

这一节我们先回答最朴素的问题：到底什么叫分布式系统？为什么人们宁可忍受它的麻烦，也要把系统拆成多台机器？拆开之后，代价又是什么？

## 1 分布式系统的定义

**分布式系统（distributed system）**：由一组相互独立、通过网络连接的计算机（每个参与协作的计算机称为**节点（node）**）组成，它们通过传递消息相互协作，共同完成一个**单一逻辑任务**，并对使用者表现为一个连贯的整体。<span class="marginnote">另一种经典表述来自塔嫩鲍姆（Andrew S. Tanenbaum）：「分布式系统是若干独立计算机的集合，但对用户而言表现为一个单一的连贯系统。」这句话与 MIT 6.824 课堂上给出的精神一致——<strong>对使用者隐藏内部结构</strong>。</span>

这个定义里藏着三个不可省略的要素：

- **多节点**：参与协作的计算机不止一台，且彼此独立——任何一台都可以自主运行、崩溃或重启，而不必事先「通知」其他节点。
- **消息传递**：节点之间不共享内存、不共享磁盘，唯一的交流方式是经由网络收发消息。因此分布式系统是**基于消息传递（message passing）**的模型，这与我们在操作系统里熟悉的**共享内存**并发模型有根本区别。
- **单一逻辑任务**：对使用者而言，整个系统只是一台「逻辑上唯一的机器」。你搜索、下单、上传文件，并不知道背后是几百台机器在分工。

与之配套，还有一条常被忽略的隐含要求：**对外的一致性外观（transparency）**。使用者不应感知到内部有多少节点、哪个节点在服务、节点之间如何协调——系统内部的一切复杂性都应该被封装起来。<span class="marginnote">兰波特的名言点破了分布式系统的另一面：正因为「对外像一台机器」，所以<strong>任何一台远端节点的故障都会以某种方式传导到你面前</strong>——这是本专题反复出现的主题。</span>

**辨析｜易错点：**「多台电脑联网」不等于「分布式系统」。办公室里三台各自运行 Excel 的电脑不是分布式系统，因为它们在各自完成各自的逻辑任务；只有多台机器**协作完成同一个逻辑任务**时，才构成分布式系统。区分的关键，不是「机器多」，而是「任务是否单一、协作是否必要」。

把定义再咀嚼一遍，就能嗅到分布式系统的特殊气味：单机系统里，「整个系统是否正常」是一个可以立刻回答的问题——你总能访问到自己的内存与磁盘。分布式系统却失去了这种确定性：当你在节点 A 上，节点 B 是否还活着、它是否处理了你发去的请求，都只能靠推理与猜测。对整座博客而言，分布式系统是计算机组成、操作系统与计算机网络三门课在「多机」尺度上的交汇——单机里的进程、内存、时钟、中断这些概念，到了网络上都被重新发明了一遍。

## 2 动机：为什么要把系统拆开

把本来可以放在一台机器里的系统拆成多台机器，看起来是自找麻烦。人们这么做，主要有三个动机。先看一个具体的场景：搜索引擎要把全网网页建成倒排索引，数据量以 PB 计，任何一台机器都装不下。于是索引被切成上万片、分布在成千上万台机器上；一次查询要同时问遍这些机器，再汇总排序。对使用者而言，这仍然只是「搜索一下」——但这背后已是标准的分布式系统。

### 扩展性（Scalability）

一台机器的能力是有上限的：CPU 主频逼近物理极限，单机内存、磁盘容量、网络带宽都受制于硬件与成本。当负载增长——用户变多、数据变大、请求变频繁——**垂直扩展（scale up）**即更换更强的机器，很快就会撞上「钱不够」「机器不够快」的双重天花板。**水平扩展（scale out）**则换一条路：加机器。多台普通机器合起来，负载可以按需分摊。DDIA 第 1 章讨论的数据密集型系统——社交网络、电商、搜索引擎——几乎都是靠「加机器」长大的。<span class="marginnote">可扩展性不是免费的：加一台机器，就多一份协调成本与故障风险。第 7 篇《分区与再平衡》会讨论数据如何被切分到机器上；第 6 篇《复制》讨论如何冗余副本。</span>

### 可用性（Availability）

把鸡蛋放在一个篮子里，篮子坏了就全没了。一台物理硬盘的**年故障率**（AFR）通常在 1%～4%，一台机器由 CPU、内存、电源、风扇、网卡等几十个部件组成，任何一个老化都会让整机停机。当一个集群有成千上万台机器时，「每天都有机器在坏」不是假设，而是日常。为了在部分硬件失效时服务仍可用，就要把数据与计算**复制**到多台机器上——一台挂了，另一台顶上。<span class="marginnote">可用性常被量化成「几个九」：一年 8760 小时，99.9% 的可用性允许约 8.76 小时停机，而 99.999%（五个九）只允许约 5.26 分钟。五到六个九是金融、电信系统追求的目标，靠单机几乎不可能达到。</span>

### 资源共享（Resource Sharing）

有些资源昂贵到不适合人人独占：一块上万瓦的 GPU、一套海量存储、一个企业级数据库、一份全网数据集。分布式系统让许多用户**共享**同一批昂贵资源，并按需分配——云计算的「资源池」、分布式文件系统、GPU 算力调度，本质都是共享。这与单机上的「多进程分时共享 CPU」思想同源，只是把共享的范围从一台机器扩大到了整个集群。

小结这三个动机：**扩展性**解决「机器不够强」，**可用性**解决「机器不可靠」，**资源共享**解决「资源太昂贵」。三者往往叠加出现——现代互联网公司几乎没有哪个系统只为了其中一个而分布式。更值得注意的是，它们并不彼此独立：扩展性常靠复制与分片实现，而这同时提升了可用性；资源共享则让许多小用户也能用上超大规模算力。到了大模型时代，三者合流，构成了整个 AI 基础设施的底座。

## 3 挑战：拆开之后的代价

分布式系统的一切复杂性，都源于一个朴素的事实：**节点之间只能通过不可靠的网络、用不可靠的时钟、在可能部分失效的机器上协作。**这是本专题后续所有主题的总纲。

### 部分失效（Partial Failure）

在一台计算机里，硬件出错通常是「全有或全无」：内存条坏了，操作系统直接蓝屏，整台机器停止工作，你面对的是一种明确的整体状态。分布式系统则不同——**部分失效**指的是：某些节点已经崩溃，而其他节点仍在正常运行。系统可能同时处于「一半存活、一半死亡」的状态，而且没有任何一个节点能立刻、确切地知道别处的真实情况。<span class="marginnote">部分失效是分布式系统与单机系统最本质的分野。第 2 条《核心挑战：部分失败与不确定性》会专门展开它的后果：不确定性让「系统现在处于什么状态」成为一个无法即时回答的问题。</span>

### 不可靠网络（Unreliable Network）

节点间的消息经由网络传输，而网络是共享的、拥塞的、丢包的。一条消息可能被丢失、被延迟很久、被重复送达、被打乱顺序。更麻烦的是，发送方永远无法区分三种情况：消息根本没到、消息到了但响应丢了、对方处理了但响应很慢。于是超时（timeout）成了唯一手段，可**超时本身是一种猜测**——设短了误判对方故障，设长了白白等待。具体的量级也很说明问题：数据中心内的往返时延通常以毫秒计，但跨机房可能上百毫秒，公网上丢包与抖动更是常态。工程上常见的手法是用「重试 + 幂等」来对冲这种不确定性：

```python
def send_with_retry(send, request_id, body, tries=3):
    """幂等重发：每次请求带上唯一 ID，服务端据 ID 去重。"""
    for i in range(tries):
        try:
            return send(request_id=request_id, body=body)
        except NetworkTimeout:
            # 超时 ≠ 失败：对方可能已处理，只是响应丢了
            continue
    raise DistributedError("所有重试均超时，结果未知")
```

这段代码背后是一条分布式系统的重要原则：**由于网络不可靠，任何「一次成功的调用」都不能被假设为恰好执行一次**。幂等性、超时与重试的完整讨论在第二篇《RPC 与通信》。

### 无全局时钟（No Global Clock）

单机系统里，处理器共享同一块主板上的时钟，事件可以精确排序。分布式系统里，每个节点有**自己的**时钟，即使靠 NTP 同步也存在毫秒级偏差与漂移——于是「两个事件谁先发生」在物理上没有一个全局答案。很多问题（谁先写入？谁先加锁？日志如何排序？）在单机上是理所当然的，在分布式系统里却需要专门的机制。这正是第三篇《逻辑时钟与事件排序》要解决的问题。

### CAP 的引子

说到分布式系统的权衡，绕不开 CAP 定理：在网络**分区**（partition，即节点间连不上）的前提下，你只能在**一致性（Consistency）**与**可用性（Availability）**之间二选一。注意，网络分区不是「是否可能」的问题，而是「何时发生」的问题——因此真正可选的只有 C 与 A。<span class="marginnote">CAP 常被误读成「三者永远只能取其二」。更准确的说法是：分区发生时你被迫在 C 与 A 之间做选择；分区没有发生时，C 与 A 可以兼得。完整解读在本专题第 1 篇第 7 条《CAP 定理及其正确解读》。</span>这一结论将贯穿后面所有一致性章节，是分布式系统「没有免费的午餐」的最早警告。

## 4 核心对比表：集中式 / 并行 / 分布式

本主题没有核心公式，取而代之，我们用一张对照表来锚定「分布式」在计算机系统光谱中的位置。读懂这张表，就是读懂了「为什么分布式是另一种东西」。

| 维度 | 集中式系统 | 并行系统 | 分布式系统 |
| --- | --- | --- | --- |
| 组成 | 一台计算机 | 一台计算机内的多处理器/多核 | 多台独立计算机，网络相连 |
| 内存 | 独占 | 共享内存（总线/互联） | 各节点私有，靠消息传递 |
| 通信方式 | 进程内调用 | 共享内存 + 锁/同步原语 | 网络消息（可能丢失、延迟、乱序） |
| 故障语义 | 全有或全无（整体宕机） | 通常整体失效 | **部分失效**，节点独立故障 |
| 时钟 | 单一时钟 | 共享主板时钟 | 各节点独立时钟，无全局时钟 |
| 追求目标 | 单机处理能力 | 单个计算任务的**加速**（缩短时延/提高吞吐） | 扩展性、可用性、资源共享 |
| 典型例子 | 家用台式机 | 一台 8 核服务器跑多线程矩阵计算 | 搜索引擎、Kafka 集群、大模型训练集群 |

**重点：集中式系统是「一个故障域」，分布式系统是「多个独立故障域」。** 并行系统介于两者之间——它像集中式一样共享内存与时钟，失败时通常整体失效，但它又像分布式一样拆散任务、协同完成，因此并行算法与分布式算法共享大量思想。现代系统往往「两头都占」：一台服务器内是多核并行，一个集群内是分布式。

**辨析｜易错点：**「并行」与「分布式」经常被混用。它们的分水岭是**是否共享内存**：并行系统共享内存、共用一个时钟，目标是让一个计算任务跑得更快（Amdahl 定律的领域）；分布式系统不共享内存、没有全局时钟，目标是规模、可用性与共享。一个 MapReduce 任务两者兼有——它在多台机器上并行执行（是并行的），也通过消息协调、容忍部分失效（是分布式的）。<span class="marginnote">并行与分布式之间的桥梁是「并行算法 = 分布式算法 + 共享内存假设」。从并行转向分布式时，你失去的是「读写同一内存」这一便利，获得的是「永不单点失效」的可能——这是后续章节反复上演的交换。</span>

这张表也解释了为什么分布式系统学起来「别扭」：它的难点不在新概念多，而在**熟悉的直觉逐个失效**——你不能再靠「读内存」「看时钟」「查进程状态」来回答问题，每一条都要换成消息、超时与协商。从下一篇起，我们会逐一重建这些直觉。

## 5 小结

- **定义**：分布式系统是多个独立节点通过网络、以消息传递协作完成**单一逻辑任务**，并对使用者表现为一个整体。
- **动机**：扩展性（加机器应对负载）、可用性（复制对抗失效）、资源共享（共享昂贵算力与数据）。
- **挑战总纲**：部分失效、不可靠网络、无全局时钟——三者让「系统处于什么状态」成为难题，也让 CAP 权衡无法回避。
- **定位**：分布式系统位于集中式与并行之间：不共享内存、无全局时钟、故障是部分的，这是它与前两者的本质区别。
- **前后衔接**：分布式系统的根在操作系统与计算机网络（第三级），果在第四级《AI 基础设施》的分布式训练与《大模型部署》。
- **前景**：本专题后续将从通信、时钟、一致性到共识、复制、分区与经典系统逐一展开；这些概念最终将汇入第四级《AI 基础设施》的分布式训练。

在下一节，我们将深入最核心的挑战本身——**部分失败与不确定性**：为什么分布式系统里「知道某台机器是否还活着」都如此之难。
