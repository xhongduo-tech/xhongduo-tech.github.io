## 为什么从可串行化与 SSI 开始

写倾斜暴露了快照隔离的盲区：SI 检测不到「读-写依赖」。要堵上这个盲区，就需要**可串行化（serializable）**——隔离级别的顶端。但传统的可串行化实现（两阶段锁）贵且易死锁。**SSI（Serializable Snapshot Isolation，可串行化快照隔离）**在 2009 年后成为主流答案：它保留 SI 的高性能（读写不互锁），同时通过检测「读-写依赖」把结果提升到可串行化。<span class="marginnote">SSI 的关键论文是 Cahill、Rohm、Strohm 2009 年的《Serializable Isolation for Snapshot Databases》，PostgreSQL 从 9.1 起用它实现 `SERIALIZABLE` 级别。它是「既要性能又要正确性」的现代妥协——Oracle 至今不提供可串行化，PostgreSQL 靠 SSI 做到了。</span>

## 1 可串行化的定义：为什么它是圣杯

**可串行化（serializable）**：一组并发事务的执行结果，等价于这些事务按**某个串行顺序**逐个执行的结果。

推论：

不存在「并发才出现的异常」——写倾斜、脏读、幻读、丢失更新全部消失。
应用可以像「单用户系统」一样推理——不需要理解并发语义，逻辑简单。

可串行化是最强的隔离保证，但实现历来很贵。传统两条路：

**两阶段锁（2PL, two-phase locking）**：读锁 + 写锁，事务结束时统一释放。实现简单，但读写互锁（读堵写、写堵读），并发度低、易死锁。
**串行执行**：整个数据库单线程跑事务（VoltDB、Redis 事务）。绝对可串行化，但吞吐被单线程锁死。

SSI 的野心：**不用全局锁，也能接近可串行化**——保留 SI 的读写并行，只在中止率上付一点代价。

## 2 可串行化的不同含义：一把容易混的尺子

「可串行化」在不同语境含义不同，容易混淆：

**SQL 标准里的 SERIALIZABLE**：语义模糊的旧定义（只针对幻读），PostgreSQL 老版本实现它只到「读已提交」强度。
**理论可串行化**：严格的「等价于某串行顺序」——本文的定义，也是 SSI 的目标。
**分布式事务的可串行化**：跨分区事务的结果等价于某串行顺序——比单库可串行化更难（涉及 2PC 与复制）。

DDIA 的提醒：**「数据库写了 SERIALIZABLE」不等于「真的可串行化」**——要看实现机制。PostgreSQL 9.1 之前的 SERIALIZABLE 只是名义；用 SSI 之后才是真可串行化。

## 3 SSI 的核心：检测读-写依赖

SI 放行写倾斜是因为只查「写-写交集」。SSI 的改进：**额外检测「读-写交集」**——如果事务 T1 读了一行，事务 T2 在 T1 之后提交并写了这行，且 T1 还要写，那么 T1 可能基于过时的读做了决定。

SSI 追踪两种危险依赖：

**读写依赖（read-write dependency）**：T1 读了某行 → T2 写了该行并提交。若 T1 的写基于这次读，T1 的决定可能过时。
**写读依赖（write-read dependency）**：T2 写了某行 → T1 读了该行的旧版本。若 T1 的写基于这个旧读，也可能出问题。

检测到「危险的读-写依赖」后，SSI 不立即中止，而是**标记（flag）**事务为「有风险」；当风险事务提交时，如果其写集合与风险源冲突，就**中止并回滚**，让应用重试。

**SSI 的取舍**：它不保证「永远不会多中止」，只保证「被中止的事务重试后会成功」——通过「把写倾斜变成事务中止 + 重试」，把「静默错误」变成「显式失败」。<span class="marginnote"><strong>辨析｜易错点：</strong>SSI 是「乐观」的——它假定冲突少，只在提交时检测。冲突多时中止率飙升，吞吐暴跌（retry 风暴）。SSI 的适用前提是「读多写少、写冲突稀疏」；高冲突场景（热点行高并发写）用 2PL 或串行执行更稳。选 SSI 前先估冲突率。</span>

## 4 SSI 与 2PL 的对比

| 维度 | 两阶段锁（2PL） | SSI（可串行化快照隔离） |
| --- | --- | --- |
| 锁 | 读锁 + 写锁全程持有 | 无锁（快照读） |
| 读写互斥 | 互斥（读堵写、写堵读） | 不互斥（读写并行） |
| 死锁 | 可能（需检测与回滚） | 无死锁（提交时检测） |
| 失败模式 | 锁等待 / 死锁回滚 | 提交时中止 + 应用重试 |
| 冲突场景 | 高冲突仍稳定 | 高冲突中止率飙升 |
| 代表实现 | MySQL InnoDB、SQL Server | PostgreSQL 9.1+ |

通读要点：**2PL 把正确性放在「执行前」（锁住），SSI 把正确性放在「执行后」（检测）**。前者稳但堵，后者快但靠重试兜底。现代数据库默认选择「快 + 可重试」，因为大多数工作负载写冲突稀疏。

## 5 公式解析：SSI 的可串行化判定

把「事务可安全提交」写成 SSI 的判定。设事务 $T$ 的读集合 $R_T$、写集合 $W_T$，系统检测到的「与 $T$ 有读-写依赖的其他已提交事务」集合为 $D_T$：

$$
\text{Commit}(T) \iff W_T \cap \left( \bigcup_{U \in D_T} W_U \right) = \emptyset
$$

拆解：

- $D_T$：与 $T$ 有「读-写依赖」的已提交事务——它们写了 T 读过的行。
- 判定：若 $T$ 要写的行，与「依赖事务 $U$ 写过的行」无交集 → 提交安全；有交集 → $T$ 的决定可能基于过时读 → **中止**。
- **这正是写倾斜的封堵**：医生值班例子里，T1 读了 B 行（$U$ 依赖）、T1 写 A 行——$T$ 与 $U$ 的写集合若重叠（都写了同一行）就中止；SI 漏掉的是「写-写不重叠但读-写重叠」——SSI 把「读-写依赖」并入 $D_T$，检测范围扩大。

这条式子的工程含义：**SSI 的本质是「把读-写依赖转化为提交时的写-写检查」**——它不阻止并发，只在中止率里体现冲突。正确性靠「宁可错杀（多中止），不可错放（放行写倾斜）」——被误杀的事务重试即可，放行则会静默出错。<span class="marginnote">PostgreSQL 的 SSI 实现细节：它用「predicate lock」在索引/表粒度追踪读集合（不是每行，太贵），用「读写冲突标记」记录依赖。粒度的粗化会<strong>误报</strong>（中止本可提交的事务）但不<strong>漏报</strong>（不会放行走倾斜）——用多中止换不漏错，是可串行化的经典工程取舍。</span>

## 6 数值走查：写倾斜怎么被 SSI 抓住

把「医生值班」这个经典例子用数字走一遍。设值班表记录两个医生是否在值班：A 行 `on_call=true`、B 行 `on_call=true`；规则是「至少一个在值班」，下班条件是「读两行确认至少一个 true，然后把另一个置 false」。

事务 T1（医生甲下班）：读 A、B → 均 true → 决定「把 A 置 false」。事务 T2（医生乙下班）：读 A、B → 均 true → 决定「把 B 置 false」。两个事务并发。

- **快照隔离**：T1 与 T2 都基于同一快照（A=true, B=true）做决定，写集合 {A} 与 {B} 无交集 → SI 判定「无冲突」→ 都提交 → 最终 A=false, B=false，**值班表空，规则被破坏**。
- **SSI**：T1 读了 B 行（T2 也写 B），T1 与 T2 存在「读-写依赖」。按第 5 节的简化判定，T1 的写集合 {A} 与 T2 的写集合 {B} 无交集——表面看可不中止，这就是 SI 漏掉的情形。

这里要点出 SSI 的真实做法：**PostgreSQL 的 SSI 在「危险结构」出现时才中止**——更精确的判定是：T1 读 B → T2 写 B，且 T2 读 A → T1 写 A，形成一个「读-写依赖环」。环上两个事务若都提交，结果就不可串行化。于是 SSI **中止其中一个**（T1 或 T2），另一个重试后成功——值班表最终保住了「至少一个在值班」。

这个走查说明了两件事：**第一，SI 漏掉写倾斜是因为只查写-写交集；第二，SSI 用「读-写依赖 + 环」来抓它**——判定比第 5 节的简化式更精细，但思想一致：把「读-写依赖」纳入冲突检测，宁可中止一个事务，也不放行不可串行的结果。

## 7 术语速查表：可串行化的词汇

| 术语 | 一句话含义 |
| --- | --- |
| 可串行化（serializable） | 并发结果等价于某串行顺序 |
| 两阶段锁（2PL） | 读写锁全程持有，事务结束统一释放 |
| 快照隔离（SI） | 每事务读一个快照，写-写冲突才中止 |
| 读-写依赖 | 一事务读、另一事务写同一行的依赖 |
| 写-写冲突 | 两事务改同一行的冲突（SI 检测） |
| 谓词锁（predicate lock） | 按查询条件粒度追踪读集合（SSI 用） |
| 中止重试 | 冲突事务回滚，应用重新执行 |

**一句话记住 SSI**：快照隔离 + 读-写依赖检测 = 可串行化——它保留了「读写并行」，把正确性放在「提交时检测 + 中止重试」，用「多中止」换「不漏错」。

**辨析｜易错点：**「SSI 中止的事务重试后会成功」不总是真——若两个事务形成稳定的读-写依赖环（互为依赖），重试可能反复中止（活锁）。高冲突热点下 SSI 的中止率会「雪崩」，这是它不如 2PL 稳的根源。<span class="marginnote">PostgreSQL 与 MySQL 的路线对照：PostgreSQL 用 SSI 实现真 `SERIALIZABLE`；MySQL InnoDB 用 2PL（锁 + 间隙锁）实现接近可串行化。<strong>同一个 SQL 标准词，两种实现哲学</strong>——一个「先放行后检测」，一个「先锁定后执行」——记住这一点，读两者文档就不迷惑。</span>

## 8 小结

- **可串行化**：并发事务结果等价于某串行顺序——消灭一切并发异常，应用可当单用户系统推理。
- 传统实现：**2PL**（读写互锁，稳但堵）、**串行执行**（单线程，吞吐受限）。
- **SSI** 保留 SI 的读写并行，额外检测**读-写依赖**，冲突时提交中止 + 重试。
- SSI 把「静默错误（写倾斜）」变成「显式失败（中止）」——用可重试的中止换正确性。
- 取舍：冲突稀疏时 SSI 最优，高冲突时中止率飙升——选前先估冲突率。
- 语义提醒：数据库写 `SERIALIZABLE` 不等于真可串行化——看实现机制（SSI 还是名义）。
