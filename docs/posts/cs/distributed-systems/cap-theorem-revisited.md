# CAP 定理及其正确解读

## 为什么从 CAP 定理开始

上一篇我们度量了性能、可用性与可扩展性。可当数据被复制到多台机器上，「同一份数据在不同机器上不一致」就成了日常。CAP 定理是被引用最多、也**被误解最多**的分布式定理。它说：网络分区不可避免，分区时你必须在一致性与可用性之间二选一。<span class="marginnote">在 6.824 与 DDIA 里，CAP 都只是开场白而非结论：它指出「你总得放弃点什么」，却没有告诉你放弃之后怎么活得更好——那正是后面所有复制、共识、最终一致性技术要做的事。</span>

## 1 三个字母的真实含义

CAP 三个字母分别指：

**C —— 一致性（Consistency）**：这里的定义是**线性一致性**，即读到的必须是最近一次写入的值，所有节点看起来像一台单机。
**A —— 可用性（Availability）**：**每个**收到的请求都必须得到响应，且响应必须是非错误结果——不能因为节点间联系不上就拒绝服务。
**P —— 分区容忍性（Partition Tolerance）**：网络分区（消息丢失、节点失联）发生时，系统仍能继续运行。

关键在 P 的性质：分区不是一种「选择」，而是物理现实——网络会丢包、会断、会慢，你无法禁止分区发生。**你只能决定分区发生时，系统表现得像一致的系统，还是像可用的系统。**<span class="marginnote"><strong>辨析｜易错点：</strong>很多文章把 CAP 说成「三选二」，仿佛可以在 C、A、P 中任选两个。但 P 不可弃——你不可能「不要分区容忍」，因为网络故障由物理世界决定。真正的选择永远是「分区时保 C 还是保 A」。</span>

### 常见误读清单

CAP 是分布式领域被误读最严重的结论，把流传最广的几种误读与正解并排：

| 流行说法 | 正确理解 |
| --- | --- |
| 「CAP 让你三选二，C、A、P 任选两个」 | P 不可选，真正二选一的是 C 与 A，且只在分区窗口期 |
| 「系统要么是 CP，要么是 AP」 | 同一系统可为不同操作提供不同保证，分区时行为才暴露取向 |
| 「数据库 CP 就比 AP 高级」 | 只是取向不同：付出可用性换一致，反之亦然，与好坏无关 |
| 「没有分区时也能谈 CAP 取舍」 | 无分区时 C 与 A 可以兼得，CAP 的取舍只在分区窗口生效 |
| 「CAP 能指导具体数据建模」 | CAP 只划边界不给出路，真正指导实践的是后面的复制、共识、事务技术 |

这张表的意义在于：**把 CAP 当「诊断工具」而非「设计蓝图」**。面试或架构评审里被问「这系统是 CP 还是 AP」时，正确的回应是先追问「分区的瞬间，你希望这笔操作怎么表现」，而不是脱口而出一个静态标签。

## 2 为什么三者不可兼得

设想两个节点 $N_1$ 与 $N_2$，各自存着变量 $x$，初始值都是 $N_1$。现在客户端向 $N_1$ 写入 $N_2$，$N_1$ 成功响应；随后网络把 $N_1$ 与 $N_2$ 隔断（分区）。此时客户端向 $N_2$ 发起读 $x$ 的请求，只有两种可能：

**保一致性**：$N_2$ 知道自己的 $x$ 是过期的 $N_1$，于是拒绝响应（或阻塞等待 $N_1$ 恢复）——这违反了可用性（请求没得到非错误响应）。
**保可用性**：$N_2$ 返回自己看到的旧值——但这违反了线性一致性（读到了旧值）。

两条路都被堵死，所以**当分区发生时，C 与 A 无法同时满足**。这是一个物理性结论，不依赖任何实现细节。<span class="marginnote">1999 年 Brewer 在 PODC 提出该猜想，2002 年 Gilbert 与 Lynch 给出严格证明。证明的关键假设是「有限异步通信」——你无法确定对端到底是死了还是只是慢，这正是部分失败问题在 CAP 里的投影。</span>

这个反例并不需要「两个节点都收到写」这么强的条件——只要**一个读请求落在与写侧隔离的节点上**就足够。写侧成功响应之后，读侧既无法得知这次写，又无法证明「没有发生过写」，于是一致与可用只能二选一。理解到这一层，你就能解释为什么「多数派 + 故障切换」能缓解而不是消灭问题：把「两节点」换成「三节点」，分区时占多数的那个分区仍可安全读写，损失的只剩少数派分区的可用性——CAP 的取舍被「压进」了少数派，而不是凭空消失。

## 3 CAP 的正确打开方式

把 CAP 简化成「P 不可选，分区时在 C 和 A 之间选」之后，正确的决策框架浮现出来：

**分区不存在时，系统可以同时是「一致且可用」的**——C 与 A 的冲突只在分区发生的窗口期出现。所以真正的工程问题是：**你的系统愿意在分区期间承受多少不一致，以换取多少可用性？**据此系统大致分为三类：

- **CP 系统**：分区时拒绝部分读写，优先保证一致性。典型如 ZooKeeper、etcd、Spanner（分区时牺牲可用性）。
- **AP 系统**：分区时继续接受读写，返回可能过期的数据，事后收敛。典型如 Dynamo、Cassandra、CouchDB。
- **CA 系统**：无分区的单机或少数派系统——严格说「CA」在分布式语境下几乎不存在，因为分区总会来。

**辨析｜易错点：**不要用 CAP 给系统贴永久标签。同一个系统在不同操作、不同时段可以是 CP 或 AP——例如 Cassandra 可调一致性，选 QUORUM 时偏 CP，选 ONE 时偏 AP。CAP 描述的是**某个操作在分区瞬间的行为**，不是系统的静态分类。

### 数值算例：分区时的一次完整决策

假设一个三副本系统保存账号余额，三台机器分处两个机房。某刻机房 A 与机房 B 之间的专线断掉（分区），余额副本 $r_A$、$r_B$ 失去联系，副本 $r_C$ 在机房 A 内仍与 $r_A$ 连通。

此时一位用户在机房 B 发起「扣款 500 元」的写请求，落到 $r_B$。系统必须立刻决定：

- **选 C（CP 行为）**：$r_B$ 无法确认「余额是否已被机房 A 侧扣过」，于是拒绝这笔写，返回「服务暂时不可用」。代价是 $r_B$ 侧所有读写停摆，直到分区恢复。
- **选 A（AP 行为）**：$r_B$ 基于本地已知余额直接扣款并返回成功。代价是：若机房 A 侧此前已用旧余额扣过同一账户，分区恢复后余额必然对不上——需要靠补偿或合并规则兜底。

把数字放进来：账户原余额 1000 元，机房 A 已扣 300，机房 B 又扣 500。AP 方案下 A 侧认为余额 700、B 侧认为余额 500——**两边都不对，且没有一个副本持有真相**。这正是「最终一致」里「最终」二字的代价：系统承诺分区恢复后收敛，却无法承诺收敛前每个读都正确。<span class="marginnote">注意这里的扣款例子如果发生在支付系统，往往要选 CP 或采用「预留 + 冲正」模式——因为资金数据不可「静默覆盖」。这正是后面第 8 篇事务与 Saga 补偿出现的现实动机。</span>

### 术语速查表

| 术语 | 全称 / 别名 | 一句话含义 |
| --- | --- | --- |
| CAP | Consistency / Availability / Partition tolerance | 分区时在一致与可用之间二选一 |
| Linearizability | 线性一致性 | 所有操作像在单一时刻点串行执行 |
| CP / AP | Consistent-Partition / Available-Partition | 分区时的两种行为取向 |
| PACELC | Partition + Availability / Consistency Else Latency-Consistency | 无分区时还要在时延与一致间取舍 |
| Quorum | 法定多数 | 读写需多数副本确认的约定 |

### CAP 之外：PACELC

CAP 只谈「分区发生时」的取舍，却回避了一个更常见的问题：**没有分区时，要不要为了降低时延而牺牲一致性？** PACELC 补上这一问——它读作「若分区（P），则在可用 A 与一致 C 之间权衡；否则（Else），在时延 L 与一致 C 之间权衡」。

一个贴近生活的例子：电商购物车。绝大多数时候网络正常，若每步加购都等跨数据中心确认（保 C），用户会感到明显卡顿；若只写本地副本立即返回（保 L），不同设备上的购物车会短暂不一致，但靠 CRDT 或合并能很快收敛。PACELC 提醒我们：**一致性的代价在无分区时依然存在，只是换了个形式——时延**。它与 CAP 一起，才是完整的设计坐标。

## 4 公式解析：从「2 选 1」到「P 恒成立」

把上面的二选一论证压缩成一条逻辑链：

$$
\underbrace{(C \land A)}_{\text{同时满足}} \Rightarrow \neg P \qquad \Longleftrightarrow \qquad P \Rightarrow \neg (C \land A)
$$

拆解这行式子：

- **第一行左边**：若系统同时满足一致性 C 与可用性 A——每个读都返回最新值、每个请求都有响应——那么分区不可能发生。因为一旦分区，上面的 $N_1$/$N_2$ 反例就会立即推翻 C 或 A。
- **第一行右边**：由逆否命题，**若分区会发生（P 为真），则 C 与 A 至少牺牲一个**。
- **工程读数**：$\neg (C \land A)$ 不是 $\neg C \lor \neg A$ 的二选一那么简单——它说的是**在分区的那个瞬间**二选一。分区结束后，系统可以（也应该）重新变得又一致又可用。

补一句关于证明假设的话：Gilbert 与 Lynch 的证明依赖**异步通信模型**——消息可能延迟任意长、可能丢失、没有统一时钟。若允许「延迟有上界」的同步假设，分区检测与一致决策都能可靠完成，CAP 的张力随之消失；现实系统大多落在二者之间的**部分异步**区间（见《系统模型》篇），这正是「理论上无解、工程上有解」的根源。<span class="marginnote">这也是为什么 6.824 反复强调：不要因为 CAP 就放弃设计——分布式系统的艺术，就是在「不可能三角」的缝隙里，把不可能变成「几乎不可能、但足够好」。</span>

## 5 小结

- CAP 三个字母：**一致性**（线性）、**可用性**（每请求都有响应）、**分区容忍**（分区时继续运行）。
- **P 不可选**：分区是物理现实，只能决定分区时保 C 还是保 A。
- 二选一有严格证明：分区时存在一个节点持有过期数据，保 C 就拒绝服务（失 A），保 A 就返回旧值（失 C）。
- CAP 不是静态标签：同一系统可对不同操作提供不同保证；分区结束后 C 与 A 可以兼得。
- CAP 的价值是划定边界，不是给出答案——答案在后面的复制、共识与最终一致性技术里。
- 「多数派 + 故障切换」能把 CAP 的取舍压进少数派分区，但不能消灭它——这是理解 Quorum、Raft 的起点。
