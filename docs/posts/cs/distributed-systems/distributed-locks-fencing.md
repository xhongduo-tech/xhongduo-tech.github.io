## 为什么从分布式锁的正确性开始

Chubby、ZooKeeper、Redis 都提供「分布式锁」——但「拿到锁」到底意味着什么？这个问题比看起来深得多。**分布式锁的正确性**不只是「互斥」，还要回答：锁会过期吗？过期后安全吗？**租约（lease）与围栏令牌（fencing token）**是分布式锁正确的两件套——缺了任何一个，锁都可能变成「虚假的安全感」。<span class="marginnote">Martin Kleppmann 的《How to do distributed locking》是分布式锁领域被引用最多的文章——它用「GC 暂停导致锁过期」的例子，揭示了「锁 + 无围栏」的经典 bug，并引发了对 Redis Redlock 的大论战（第 11 篇 Redlock）。理解分布式锁，从正确性定义开始。</span>

## 1 分布式锁要保证什么

分布式锁的正确性需要三个性质（参照 Chubby 论文）：

**互斥性（Mutual Exclusion）**：**同一时刻最多一个客户端持有锁**——这是锁的根本。
**安全性（Safety）**：只有持有锁的客户端能访问受保护资源（临界区）。
**活性（Liveness）**：锁最终能被获取（不会死锁）；持有者崩溃后锁能释放。

**关键难点**：分布式锁在「无全局时钟、无共享内存、网络不可靠」的世界里实现「互斥」——它不像进程内锁那样「内核保证」，而是「协议保证」。而协议保证的互斥，可能被以下因素击穿。

## 2 锁过期：互斥的第一杀手

**锁过期（lock expiry）**：分布式锁有 TTL——持有者必须在期限内续约，否则锁被释放给他人。过期本身不是 bug（它是「崩溃自动释放」的机制），但**过期时机可能被「假死」触发**：

经典的「GC 暂停」场景：

1. 进程 A 获取 Redis 锁，开始处理任务。
2. A 被 JVM 垃圾回收**暂停 30 秒**——期间它「活着但失聪」，无法续约。
3. 锁 TTL 到期，进程 B 获取锁，开始处理同一任务。
4. A 从 GC 恢复，**仍认为锁在自己手里**，继续写数据。
5. 结果：A、B 同时写——互斥被击穿，数据损坏。

**根因**：A 的「持有锁」是「它以为的持有」，而锁的「实际状态」已经在它失聪期间变了。**锁过期是客观的，客户端感知是滞后的**——这个时间差就是互斥被击穿的窗口。<span class="marginnote"><strong>辨析｜易错点：</strong>「GC 暂停」不是分布式锁独有的问题——任何「持有者可能长时间不响应」的场景（网络分区、进程冻结、调度器延迟）都会触发同样的过期。所以「修复 GC」不是答案，答案是「接受过期不可避免，设计防护」。</span>

## 3 租约：让过期「可知可调」

**租约（lease）**把「持有时长」变成协议的一部分：

获取锁时，锁带一个**截止时间**（如「10 秒内有效」）。
持有者必须周期性**续约**；过期未续 → 锁自动释放。
**所有参与者遵守同一规则**：新获取者只在「旧锁已过期」后才拿到锁。

租约让「过期」从「隐蔽的意外」变成「协议的一部分」——参与者知道「锁最迟到什么时候失效」，可以在设计中利用这个边界。但它**不消除过期风险**：GC 暂停照样让持有者错过续约，锁照样被别人拿走。

**租约的正确用法**：**把「锁过期」当作「随时可能发生」来设计受保护操作**——临界区的动作要么足够短（在锁有效期内完成），要么配「围栏」让过期后的写失效。

## 4 围栏令牌：锁过期后的最后防线

**围栏令牌（fencing token）**解决「锁过期后持有者还在写」的问题：

1. 每次成功获取锁，锁服务签发一个**单调递增的令牌**（token = 1, 2, 3…）。
2. 持有者访问受保护资源时**携带令牌**。
3. **资源端校验令牌**：只接受「令牌 ≥ 当前已知最大」的访问，拒绝旧令牌。

GC 场景的补救：A 拿到 token=1，B 拿到 token=2。A 从 GC 恢复后携带 token=1 写数据——资源端看到「当前最大是 2」，**拒绝 A 的写**。B 的 token=2 写正常通过——数据损坏被防住。

**为什么围栏能兜底**：它把「谁有资格写」的判断从「持有者自认为」移到「资源端强制」——而资源端的判断依据是「单调令牌」，不依赖持有者的感知或时钟。**锁可以过期，但过期的令牌写不进资源**——这就是「最后防线」的含义。<span class="marginnote">围栏令牌要求「资源端配合校验」——如果资源是「不支持令牌校验的存储」（比如裸 Redis、无鉴权 API），围栏就失效。这是「端到端」原则：正确性要靠协议两端（锁服务签发 + 资源端强制）共同保证，缺一环就白搭。DDIA 第 8 章专门强调了这个「端到端」性质。</span>

## 5 公式解析：锁过期与围栏的配合

把「锁 + 围栏」的正确性写成时序条件。设锁 TTL 为 $L$，持有者 $A$ 的持有区间 $[t_0, t_1]$，令牌 $T_A$、$T_B$：

$$
T_B > T_A \;\land\; \text{资源端只接受最大令牌} \;\Rightarrow\; \text{A 过期后的写 } (T_A) \text{ 被拒绝}
$$

拆解：

- **令牌单调性**：每次获取锁令牌递增——B 的令牌必然大于 A 的。
- **资源端校验**：只接受「令牌 ≥ 已见最大」——A 的旧令牌 $T_A$ 必然被拒。
- **关键**：这个拒绝**不依赖任何时间判断**——A 是否过期、A 是否以为自己在持有期内，都与拒绝逻辑无关；只比「令牌序号」。
- **配合租约**：租约保证「锁最终会被释放」（活性），围栏保证「过期的持有者无法造成破坏」（安全性）——两件套各管一头。

这条式子的工程含义：**分布式锁的正确性 = 租约（活性）+ 围栏（安全）**。租约处理「锁会不会永远卡住」，围栏处理「过期后会不会写坏」。只做互斥、不做租约 → 崩溃死锁；只做租约、不做围栏 → 过期后数据损坏。**完整方案是「互斥锁 + 租约 + 围栏令牌」三件套**。<span class="marginnote">这也解释了为什么「分布式锁」的正确实现比表面看起来复杂：它不只是「一个 key 谁抢到算谁的」，而是「互斥协议 + 过期机制 + 令牌审计」的完整系统。理解了这套结构，就能评估任何「分布式锁方案」是否完整——Redlock 的争议（下一篇）正是围绕「它的互斥保证是否真的成立」展开的。</span>

## 6 小结

- 分布式锁三性质：**互斥性、安全性、活性**——在网络不可靠下靠协议而非内核保证。
- **锁过期**是「崩溃自动释放」的机制，但 GC 暂停/网络分区会让持有者「以为还有锁」——互斥被击穿。
- **租约**把持有时长变成协议一部分：过期可知可调；但不消除过期风险。
- **围栏令牌**：锁服务签发单调递增令牌，资源端拒绝旧令牌——过期后的写被兜底拒绝。
- 正确性 = **互斥锁 + 租约（活性）+ 围栏（安全）**三件套，缺一不可。
- 围栏要求资源端配合校验（端到端）——不支持令牌校验的资源，围栏失效。
