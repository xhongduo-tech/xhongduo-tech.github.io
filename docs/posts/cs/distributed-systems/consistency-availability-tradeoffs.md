## 为什么从权衡实践开始

前面几篇把一致性模型从强到弱摆了一整排。可现实中不存在「选一个模型用到底」的系统——一家公司的架构里，订单走强一致、商品浏览走弱一致、库存走折中。**权衡实践**讲的就是：面对具体业务，怎么把一致性与可用性这对矛盾翻译成可执行的架构决策。<span class="marginnote">本篇是第 4 篇一致性问题的收官：把「线性一致、因果一致、最终一致」这些抽象名词，落成「什么时候用 etcd、什么时候用 Redis 异步、什么时候用可调一致性」的具体选择。</span>

## 1 权衡的本质：不是二选一，是「按数据」配置

CAP 定理告诉我们在分区瞬间必须放弃 C 或 A。但「放弃」发生在**哪个粒度**？成熟系统的答案是：**放弃发生在每一条数据、每一个操作的粒度上**，而不是整个系统。

同一个系统可以同时提供：

**强一致**的操作：账户余额读写、库存扣减、分布式锁。
**弱一致**的操作：商品推荐、点赞计数、浏览历史。
**中间态**：因果一致、读己之写、会话保证。

这正是「可调一致性（tunable consistency）」的哲学：Cassandra 每个查询可选 **`ONE`**（单副本写、最快）到 **`ALL`**（全副本写、最稳）之间的任意档位，**`QUORUM`** 居中。<span class="marginnote">「按数据配置一致性」的经典工具是「一致性层级图」：把业务数据按「不一致的代价」分类——金融数据在顶层（必须强一致），社交数据在底层（容忍最终一致），中间按风险逐级分类。分类越细，总成本越低。</span>

## 2 决策框架：四问定模型

面对一条新数据，用四个问题把它的需求钉死：

1. **读旧了会怎样？** 直接造成钱/信任损失 → 强一致；只是体验稍差 → 弱一致。
2. **谁会读它？** 只有写入者自己读 → 读己之写就够；跨用户共享 → 至少因果一致。
3. **写冲突的后果？** 覆盖会丢业务数据（购物车）→ 版本保留 + 合并；后写必胜（计数器）→ LWW 即可。
4. **可用性底线？** 分区时能不能拒绝写 → 能拒绝走 CP，必须继续服务走 AP。

一个真实的推演：**电商库存**。读旧了会超卖（问题 1 答案：强一致）；但「超卖」的严格性其实取决于业务——严格库存走强一致（etcd/单机事务），宽松库存（超卖后取消订单）可以走最终一致加异步对账。**同一个领域，不同公司、不同场景，答案不同**——这就是权衡实践最核心的认知。<span class="marginnote"><strong>辨析｜易错点：</strong>「强一致 = 安全」是错觉。强一致也会因锁竞争、热点、协调开销带来超时与不可用。弱一致 + 事后对账（补偿）常常比「假装强一致」更可靠——设计目标是「可度量的正确 + 可接受的失败」，不是某个抽象标签。</span>

## 3 权衡的经典搭配：架构模式速查

把常见需求与推荐架构对照：

| 业务需求 | 推荐一致性 | 典型组件 | 分区行为 |
| --- | --- | --- | --- |
| 分布式锁 / 选主 / 配置 | 线性一致 | etcd、ZooKeeper | CP：少数派拒绝 |
| 订单 / 支付 / 库存强校验 | 事务 / 线性一致 | 单机 DB + 2PC、Spanner | CP：分区时暂停写 |
| 社交时间线 / 消息 | 因果一致 + 会话 | Cassandra、CRDT、COPS | AP：继续服务 |
| 计数器 / 点赞 / 推荐 | 最终一致 | Redis 异步、Dynamo | AP：继续服务 |
| 缓存 / 搜索索引 | 最终一致 + TTL | CDN、ES 异步刷新 | AP：读旧可容忍 |

这张表的通读要点：**强一致组件通常有状态且需要共识（CP），弱一致组件通常无状态或异步（AP）**。架构设计的很大一部分工作，就是把「必须强一致的部分」尽量压缩到最小、并放在最可靠的组件里，其余全部放到弱一致层摊薄成本。<span class="marginnote">经典业界案例：Facebook 的 TAO、Google 的 YouTube 计数、微博的 feed 都是「强一致收口 + 弱一致铺开」：核心账本强一致，展示层最终一致，靠异步对账保证「最终不丢」。</span>

## 4 公式解析：权衡的成本函数

把「一致性级别」与「总成本」建模，帮决策者看清代价结构：

$$
C_{\text{total}} = \underbrace{\sum_{d \in D_{\text{strong}}} c_{\text{coord}}(d)}_{\text{强一致数据的协调成本}} + \underbrace{\sum_{d \in D_{\text{weak}}} p_{\text{stale}}(d) \cdot \text{cost}_{\text{incorrect}}(d)}_{\text{弱一致数据的错误代价}}
$$

拆解：

- $D_{\text{strong}}$：走强一致的数据集。$c_{\text{coord}}(d)$ 是每个操作付的协调成本（共识轮次、多数派往返、锁等待）——随强一致数据量线性增长。
- $D_{\text{weak}}$：走弱一致的数据集。$p_{\text{stale}}(d)$ 是读到旧值的概率，$\text{cost}_{\text{incorrect}}(d)$ 是读到旧值造成的损失。
- **最优配置**：把 $d$ 放到「总代价最小」的一侧——强一致太贵就转弱，弱一致错误代价太高就转强。

这条式子的工程结论：**权衡不是「统一选强还是统一选弱」，而是逐条数据做局部最优**。多数系统的误区是「用统一策略管理全部数据」，浪费了「弱数据」本可省下的成本，也承受了「强数据」被弱策略坑的风险。<span class="marginnote">这也解释了为什么现代数据库都在加「可调一致性」旋钮：把选择权交给应用，让每个查询自己声明「我愿付多少协调费、能承受多少旧读」。工具给的是旋钮，架构师给的是每条数据的档位。</span>

## 5 小结

- 权衡的粒度是**每一条数据、每一个操作**，不是整个系统——可调一致性由此而来。
- 决策四问：读旧了会怎样、谁在读、写冲突后果、可用性底线——把需求翻译成模型。
- 经典搭配：锁/配置/强校验走 CP（etcd/ZK/Spanner），社交/计数/缓存走 AP（Cassandra/Redis/Dynamo）。
- 架构主旋律：**强一致收口到最小核心，弱一致铺开到最大范围**，靠异步对账保证最终不丢。
- 总成本 = 强一致协调成本 + 弱一致错误代价，逐条数据做局部最优，别用统一策略一刀切。
