## 为什么从 LWW 与 CRDT 开始

多主与无主复制都会遭遇并发写冲突，而冲突解决只有两大流派：**LWW（last-writer-wins）**——时间戳最大的写胜出，其余丢弃；**CRDT（Conflict-free Replicated Data Type）**——用满足交换律/结合律/幂等的合并函数，让所有并发版本「合成一个」，谁也不丢。这篇把两派拆开看：LWW 的机制与陷阱，CRDT 的设计与代数基础。<span class="marginnote">LWW 是分布式存储里最常见的默认配置（Dynamo、Cassandra、Riak 默认都带它）；CRDT 则是「无冲突合并」的理论正确解。理解两者的差别，本质上是理解「用删除换简单」与「用代数换完整」的工程取舍。</span>

## 1 LWW：最后一个写的赢

**LWW（last-writer-wins，最后写入获胜）**的规则一句话：**比较每个写的「版本号」，最大者胜出，其余丢弃**。版本号通常是时间戳（物理或逻辑时钟）。

机制流程：每次写携带版本号；系统保存「最大版本号 + 对应值」；读返回该值；两个并发写到达，保留版本号大的，丢弃另一个。

**优点**：

实现极简——不需要版本向量、不需要多值存储、不需要合并逻辑。
收敛保证明确——无论同步顺序如何，最终留下版本号最大的写。
存储省——每个键只存一个值。

**致命缺陷：静默丢失**。两个用户并发改同一配置，时间戳小的那个写「成功返回」了（LWW 系统也确认它写成功了），但同步后它的值被覆盖——**用户以为写成功了，数据却消失了**。这不是 bug，是 LWW 的语义。

**LWW 的隐蔽陷阱**：如果版本号用**客户端物理时钟**，时钟回拨的客户端会「用旧写覆盖新写」——一个时钟慢了 10 分钟的客户端，它的写永远「输」，除非系统用可靠的单调时钟（Lamport 时间戳、HLC、TrueTime）。<span class="marginnote"><strong>辨析｜易错点：</strong>「最大版本号胜出」里的版本号必须全局可比、单调递增。用墙钟做 LWW 是灾难：节点时钟漂移导致「新写被旧写覆盖」毫无征兆。生产系统要么用 Lamport/HLC 逻辑时钟，要么接受「时钟同步良好」的强假设。</span>

## 2 CRDT：把合并写进数据结构

**CRDT（Conflict-free Replicated Data Type，冲突自由复制数据类型）**是一类**专门为并发合并设计的数据结构**，它的合并操作满足三条代数性质：

**可交换（commutative）**：$\text{merge}(a,b) = \text{merge}(b,a)$
**可结合（associative）**：$\text{merge}(\text{merge}(a,b),c) = \text{merge}(a,\text{merge}(b,c))$
**幂等（idempotent）**：$\text{merge}(a,a) = a$

三条性质合起来保证：**任何副本以任何顺序合并任何并发写，最终收敛到同一个值**——不需要锁、不需要协调、不需要版本裁决。CRDT 的价值就是「把冲突变成加法」。

常见的 CRDT 及其合并规则：

| CRDT | 语义 | 合并操作 |
| --- | --- | --- |
| **G-Counter**（增长计数器） | 每个副本记自己的增量，总值 = 各副本增量之和 | 逐副本取 max |
| **PN-Counter**（可增减计数器） | 增长与减少分开两个 G-Counter | 逐维取 max |
| **G-Set**（增长集合） | 只增不删的集合 | 并集 |
| **2P-Set / OR-Set**（可删集合） | 集合 + 已删元素墓碑 | 并集 + 墓碑去重 |
| **LWW-Register** | 每个值带时间戳，合并取最新 | 版本比较后取新 |

CRDT 的关键设计难题是**删除（tombstone）**：G-Set 只能加不能删，要支持删除就得记录「删除墓碑」，而墓碑会让集合无限增长——这是 2P-Set 和 OR-Set 的复杂来源。<span class="marginnote">CRDT 分为两类：<strong>基于状态（state-based / CvRDT）</strong>——副本间同步整个状态，合并取 join；<strong>基于操作（operation-based / CmRDT）</strong>——副本间同步操作日志，操作设计成可交换。前者简单但状态大，后者高效但要求消息可靠有序。Riak 的 CRDT、Redis 的 CRDT（6.2+）、Automerge 是典型实现。</span>

## 3 什么时候用 LWW，什么时候用 CRDT

选型判据一句话：**这个数据「输掉一次写」会造成业务损失吗？**

**用 LWW**：计数器（点赞同接丢弃旧计数没问题）、配置覆盖（后写必然正确的）、缓存、标签/状态位。特点是「最后一次写 = 最正确的写」。
**用 CRDT**：购物车（并发添加的物品必须都保留）、文档/列表（并发编辑的插入都要保留）、日历、白名单。特点是「每次写都有独立贡献，不能丢」。
**折中**：LWW-Register 常用于「CRDT 化但保留后写必胜」的场景——用可靠时钟做版本号，既收敛又可控。

DDIA 的清醒提醒：**CRDT 不是银弹**——它假设「合并」有业务意义。如果并发写根本不是「能合并」的关系（比如两个客户端往同一账户转了不同金额），合并反而掩盖了真实语义，此时需要**事务或业务层裁决**，不是 CRDT 能解决的。<span class="marginnote">实操经验：把「能合并的数据」与「不能合并的数据」分开建模。购物车条目、白名单、标签 → CRDT；余额、订单状态、权限 → 事务/共识。用「数据是否可交换合并」给数据分类，是设计无冲突复制系统最重要的第一步。</span>

## 4 公式解析：OR-Set 的合并不变量

拿最常用的 **OR-Set**（Observed-Remove Set，可删集合）做公式拆解。OR-Set 的每个元素是「值 + 唯一 ID」，删除时把该 ID 加入墓碑：

$$
\text{merge}(S_1, S_2) = (S_1.\text{elems} \cup S_2.\text{elems}) \setminus (S_1.\text{dead} \cup S_2.\text{dead})
$$

拆解：

- $S_i.\text{elems}$：副本 $i$ 看到的存活元素（值 + 唯一 ID）。
- $S_i.\text{dead}$：副本 $i$ 看到的已删元素 ID（墓碑）。
- 合并 = 存活元素取并集，再减去所有墓碑——**被任一副本删除的元素，在所有副本上都被删除**。
- **为什么不会「删而复生」**：元素有唯一 ID，删除记录 ID；合并时 ID 一旦进墓碑，任何并集都不再包含它——除非删除后又被重新添加（生成新 ID，视为新元素）。

这条不变式的工程含义：**OR-Set 的删除是「单调」的**——删除操作一旦被某副本看见，就永远不会被并发添加复活。这是「无冲突」的精确含义：并发操作无论以什么顺序合并，都不会产生「先删后加又复活」的矛盾。对比 LWW 的「静默覆盖」，OR-Set 保留了「每个用户的操作结果」而只对冲突做「可交换的合并」。<span class="marginnote">OR-Set 的经典应用是分布式购物车：两个设备并发添加/删除物品，OR-Set 保证「你加的物品不会因我删除另一件而被波及」——每个用户的操作都以可交换的方式被合并，购物车收敛且不丢操作。这也是 Riak 的 Flags/Maps 与 Redis CRDT 的基础。</span>

## 5 数值算例：购物车里的 LWW 与 OR-Set

把抽象落到两个设备同时操作一个购物车的场景。设购物车初始含「牛奶」。

- 设备 A：加「鸡蛋」；设备 B：加「面包」，两操作并发（互为不可比较）。
- **LWW**：两个写各带时间戳，取时间戳大的一个。若 A 的写胜出，购物车 = {牛奶, 鸡蛋}——**面包静默消失**。用户 B 明明看到「加面包成功」，刷新后面包没了。
- **OR-Set**：A 加 {鸡蛋:ID1}，B 加 {面包:ID2}，合并 = 并集 {牛奶:ID0, 鸡蛋:ID1, 面包:ID2}——**两个操作都被保留**。

再看「先删后加」的并发：

| 并发操作 | LWW 结果 | OR-Set 结果 |
| --- | --- | --- |
| A 删除「牛奶」、B 加「牛奶」 | 看时间戳，删或加一方胜出，结果不确定 | 新添加生成新 ID，旧 ID 进墓碑 → 「先删后加」= 加回来（新 ID 存活） |
| A 删除「面包」（已见 ID2）、B 并发加「面包」 | 时间戳大者胜 | 删除进墓碑 + 新加是新 ID → 面包存活（并发加 = 新元素） |

中间一行的 OR-Set 结果值得多说一句：**OR-Set 的「删」只对「已见到的元素」生效**。A 删除的是「面包:ID2」，B 并发添加的是「面包:ID3」——ID2 进墓碑，ID3 是新元素，所以面包「删而复存」。这不是 bug，而是「删除必须基于所见版本」的语义：**你只能删掉你见过的东西**。

这张表的工程含义：LWW 把「并发」压成「二选一」，OR-Set 把「并发」展开成「各取所长」。判断用哪个，回到第 3 节的判据——**每次写是否有独立贡献**：购物车的「加」是贡献，「删」对特定 ID 也是贡献，所以 OR-Set 天然匹配；而「配置项最后一次覆盖」不是贡献，LWW 反而更合理。

### 从代数性质看「重试安全」

三条代数性质里，**幂等**（$\text{merge}(a,a)=a$）最容易被工程忽视，却是「重试安全」的保证。消息重发、网络重传在分布式系统里是常态——一个合并操作如果非幂等，重放一次就会把结果算两遍。G-Counter 逐副本取 max 天然幂等：重复合并同一个增量，max 不变；LWW 的「取时间戳最大」也幂等：同一写重复应用，结果不变。**「无冲突复制」能落地，正是因为合并函数对这些「重复」免疫**——这也是为什么 CRDT 系统可以大胆重发消息，而不必担心副作用翻倍。

另一个容易踩的坑是「**CRDT 的合并必须最终覆盖全部副本**」——网络分区期间只能合并部分副本，未合并的部分在后续合并中迟早补上（幂等 + 结合保证补上后结果一致），但「读到的瞬间」可能只是部分合并的结果。所以 CRDT 提供的是「**最终收敛**」，不是「任何时刻都收敛」——读侧要明白这一点，别把 CRDT 当成线性一致的替代品。

## 6 小结

- **LWW**：版本号最大者胜，其余丢弃。简单、收敛、省存储；但**静默丢写**，且依赖可靠的单调时钟。
- **CRDT**：合并函数满足可交换、可结合、幂等 → 与合并顺序无关，天然收敛；不丢任何并发写。
- 常用 CRDT：G-Counter（计数取 max）、G-Set/OR-Set（集合并集 + 墓碑）、LWW-Register（版本比较）。
- 选型判据：**「输掉一次写」是否造成业务损失**——可丢用 LWW，不可丢用 CRDT。
- CRDT 不是银弹：只能合并「有合并语义」的数据；余额、状态这类数据仍要事务或共识。

- **重试安全靠幂等**：合并函数的幂等性让消息重放不翻倍——CRDT 与 LWW 都因此能大胆重发；但 CRDT 提供的是「最终收敛」，不是「任何时刻都收敛」。
