## 为什么从 ZooKeeper 开始

Chubby 是 Google 内部的，开源世界的对应物是 **ZooKeeper**——Hadoop 生态、Kafka、HBase、大量分布式系统的协调底座。它把「协调服务」实现为一个**高可用的分层命名空间（类似文件系统）**，用 **Zab 协议**（一种类 Raft 的共识）复制状态。理解 ZooKeeper = 理解「如何用一个共识复制的状态机服务所有协调需求」。<span class="marginnote">ZooKeeper 论文（Hunt et al., USENIX ATC 2010）是继 Chubby 之后最成功的协调服务设计。它的 Zab 协议与 Raft 同年（2008）设计、独立发展，是「领导者 + 日志复制」共识的另一个独立实现——与 Raft 的思想高度相似，但时序机制不同。</span>

## 1 数据模型：高可用的命名空间

ZooKeeper 的数据模型是一个**分层的命名空间**（znode 树）：

- **znode（ZooKeeper 数据节点）**：树上的节点，可存数据（通常几百字节）、可有子节点。
- **持久节点（persistent）**：显式删除才消失。
- **临时节点（ephemeral）**：创建它的会话结束（或崩溃）时自动删除——**用「临时节点」感知成员存活**。
- **顺序节点（sequential）**：创建时自动追加单调递增的序号——**用「序号」实现队列与公平锁**。

**读写语义**：

- 读：客户端可读任意副本（快，但可能旧——ZooKeeper 保证「单调读」，不保证每个读都是最新的）。
- 写：**必须走 leader**，leader 通过 Zab 广播给所有副本，**多数派确认后原子生效**——写是强一致的。
- **watch（监视）**：客户端对 znode 设置 watch，节点变化时收到通知——**变更订阅**，无需轮询。

ZooKeeper 的一致性：**线性化的写 + 单调的读**——写操作全局有序（走共识），读操作可能旧但「看到的不倒退」。这是「协调服务」够用的强度：协调逻辑（选主、锁、队列）主要依赖「写有序 + 变更通知」。

## 2 Zab 协议：广播与恢复

**Zab（ZooKeeper Atomic Broadcast，ZooKeeper 原子广播）** 是 ZooKeeper 复制的核心协议，与 Raft 同属「领导者 + 日志」家族，但机制不同：

**正常模式（广播）**：

- 一个 **leader** 接收所有写请求，给每个请求分配**单调递增的事务 ID（zxid）**。
- leader 把事务广播给所有 follower（像 Raft 的 AppendEntries）。
- **多数派确认后提交**——所有副本按 zxid 顺序应用事务。

**恢复模式（选主）**：

- leader 失效（follower 心跳超时）→ 进入恢复模式，重新选主。
- **关键：新 leader 必须「最新」**——其日志必须包含所有已提交事务（zxid 最大的日志）。
- 新 leader 把「自己的历史」同步给其他副本（对齐日志），然后才进入广播模式。

**Zab 与 Raft 的核心差异**：Raft 用「任期（term）+ 随机超时选举 + 日志匹配」，Zab 用「epoch（时代，zxid 的高位）+ 显式选主 + 日志同步」。两者解决同一问题（复制状态机的共识），但 Zab 更强调「广播的有序性」——ZooKeeper 的写顺序即 zxid 顺序，天然线性化。<span class="marginnote"><strong>辨析｜易错点：</strong>Zab 的「epoch + zxid」与 Raft 的「term + log index」是同一个思路的不同命名：zxid 的高 32 位是 epoch（第几个领导时代），低 32 位是时代内的序号——「时代 + 序号」构成的单调有序标识，正是「领导者时代」思想的体现。读 Zab 文档时把它翻译成 Raft 的词汇，大部分就通了。</span>

## 3 ZooKeeper 的读写优化：为什么快

ZooKeeper 能服务大规模协调场景（如 Kafka 的元数据、HBase 的 Region 定位），因为它做了关键的性能优化：

- **读不阻塞写**：读走任意副本（或 leader），不需要共识——读吞吐随副本数扩展。
- **写走 leader + 多数派确认**：写是强一致的，但吞吐被「一次广播 + 多数派 fsync」限制——所以 ZooKeeper 适合「读多写少」的协调负载。
- **顺序写优化**：Zab 的日志是顺序追加，配合批量提交（攒 N 个写一次广播），写吞吐可上万。
- **follower 读的时序保证**：follower 读可能旧，但 ZooKeeper 用「follower 与 leader 的同步点」保证「看到过 X 的客户端不会倒退」——单调读。

**为什么协调负载「读多写少」**：协调场景（元数据、配置、成员）的写入是低频的（配置很少变），读取是高频的（每次请求都要查）。ZooKeeper 的「写强一致 + 读扩展」恰好匹配——这也是「协调服务」与「业务存储」的负载形态差异。

## 4 一致性保证：线性写 + 单调读的边界

ZooKeeper 对外承诺的一致性（写线性 + 读单调）有一组明确的边界，理解它才能正确使用：

- **写是线性的**：所有写操作全局有序——`create`、`delete`、`setData` 的顺序对所有客户端一致。
- **读是单调的**：客户端一旦看到某个值，之后不会看到更旧的——不会「倒退」。
- **读可能旧**：follower 读不保证「最新」——刚写的值可能要过一会才在某个 follower 上可见。
- **sync 操作**：客户端想「强制读最新」，可以调 `sync`（让 follower 先同步到 leader 的最新状态）——牺牲一点性能换强一致读。

**边界的使用**：选主、锁、队列这些协调逻辑**依赖写的线性化**（谁先 create 谁赢），不依赖「每个读都最新」——所以「读可能旧」不影响它们的正确性。ZooKeeper 的文档明确建议：「读多写少 + 依赖写有序」的应用用它，需要「每个读都最新」的应用要另想办法。<span class="marginnote">「读可能旧」与「写线性」的组合常被误解：有人以为 ZooKeeper 是「强一致存储」——不是，它只是「写强一致 + 读弱一致」。把 ZooKeeper 当「高可用数据库」用（大量写、读必须最新）会踩坑——它是「协调服务」，不是「数据库」。</span>

## 5 公式解析：Zab 的提交延迟

把「ZooKeeper 写延迟」量化，理解它的性能边界。设多数派大小 $q$、leader 到最远 follower 的往返 RTT、单次 fsync 代价 $F$：

$$
\text{写延迟} \approx 2 \times \text{RTT}_{\max} + F \qquad \text{（leader 广播 → 多数派 fsync → ack 回 leader）}
$$

拆解：

- **广播往返**：leader 发事务到最远 follower 要一个 RTT，收到 ack 再一个 RTT——写延迟由**最远多数派**决定。
- **fsync**：follower 落盘要一次 fsync——这是磁盘延迟。
- **批处理**：攒 N 个事务一次广播，延迟被 N 摊薄，吞吐上升——但单事务延迟不变。
- **对比**：读延迟 ≈ 本地读（页缓存）——几乎为 0。所以 ZooKeeper 的「读快写慢」是结构性的。

这条式子的工程含义：**ZooKeeper 是「为读优化的协调服务」**——读几乎免费，写要付「多数派往返 + fsync」。用它做协调（低频写、高频读）性能极好；拿它当「高频写的业务存储」就是错配。这也是「协调服务」与「数据存储」的负载适配问题：**选服务前先看你的读写比**。<span class="marginnote">ZooKeeper 的实际吞吐数字：3 节点集群、顺序写批量下写吞吐可达上万 TPS，读吞吐更高——对协调负载绰绰有余。但它扛不住「热点写」（单 znode 高频写，走 leader 串行）——协调设计时要把「高频写」拆成「低频写 + 高频读」的模式。</span>

## 6 小结

- **ZooKeeper**：高可用的分层命名空间（znode 树），协调服务的事实标准。
- 数据模型：持久/临时/顺序节点 + watch 订阅——临时节点感知存活、顺序节点实现队列/公平锁。
- **Zab 协议**：领导者 + zxid 广播（正常）+ 恢复选主（新 leader 必须最新）——类 Raft 共识的独立实现。
- 一致性：**线性化的写 + 单调的读**——写走共识、读走副本，读可能旧但不倒退。
- 性能：读快写慢（多数派往返 + fsync）——为「读多写少」的协调负载优化。
- 边界：是「协调服务」不是「数据库」；需要「每个读都最新」的场景要另配 sync 或换存储。
