## 为什么从 ZooKeeper 的典型应用开始

上一节讲了 ZooKeeper 的「积木」（znode 树、watch、临时节点、顺序节点）。这一节看「拼法」——**选主、配置分发、分布式队列**三种最经典的应用模式。理解这些模式，你就掌握了「用协调服务解决分布式协调问题」的全部套路。<span class="marginnote">这些模式是 ZooKeeper 文档与论文里的经典「recipes」（菜谱）：每种模式 = 「一两个 znode + 若干 watch + 一个不变量」。HBase 的 Region 分配、Kafka 的 controller 选主、Kafka 老版本的 broker 注册，全是这些模式的直接应用。</span>

## 1 选主（Leader Election）

**问题**：多个候选节点竞争「谁是主」——只有一个能赢，崩溃后要自动转移。

**ZooKeeper 实现**（用临时顺序节点）：

1. 每个候选者在路径 **`/election`** 下创建**临时顺序节点**（**`c_0000000001`、`c_0000000002`**…）。
2. **序号最小的节点 = 主节点**——谁创建的序号最小谁当主。
3. 其他候选者 watch **比它序号小的那个节点**；被 watch 的节点消失（主崩溃 → 临时节点自动删除）→ 触发候选者重新检查，序号最小者接管。

**为什么这个模式好**：

临时节点让「崩溃自动退出竞争」——主崩溃，它的 znode 自动消失，watch 自动通知。
顺序节点让「选主公平」——先来者序号小，先当主；主挂了，序号次小者接任，无需重新竞争。
**无单点、无轮询**——全靠 watch 推送。

**关键正确性**：多个候选同时创建临时顺序节点，**写是线性的**（ZooKeeper 保证），所以「最小序号 = 最早创建」的判定是确定的——不会有两个节点都以为自己是主。<span class="marginnote"><strong>辨析｜易错点：</strong>「临时节点选主」与「用锁选主」的差别：临时节点方案<strong>没有 TTL 过期问题</strong>——节点只在「会话结束」时删除，而不是「超时」删除。所以「GC 暂停导致的锁过期」在 ZooKeeper 选主里影响更小（会话超时通常几十秒，且可以配置）。但「会话超时」本身仍是边界——超时后 znode 被删，其他节点接管，旧主恢复后必须检查「自己还是不是主」。</span>

## 2 配置分发（Configuration Management）

**问题**：系统配置（数据库地址、功能开关、限流阈值）需要**统一管理、实时生效、高可用**。

**ZooKeeper 实现**：

1. 把配置写成**持久节点**：**`/config/db_url`、`/config/feature_switch`**。
2. 客户端启动时读配置，并对配置节点设置 **watch**。
3. 配置变更 → ZooKeeper 写节点（线性化）→ watch 触发 → 客户端收到通知 → 重新读配置并生效。

**为什么好**：

**实时推送**：配置一变，所有订阅者几乎同时收到通知——不用轮询。
**高可用**：配置存在 ZooKeeper（共识复制）里，单个 ZooKeeper 节点挂了配置不丢。
**版本化**：写配置时 ZooKeeper 带版本号，可以用「条件写」避免「旧配置覆盖新配置」。

**与「配置文件 + 部署」的对比**：配置文件靠「发布 + 重启」生效，ZooKeeper 配置靠「watch + 热更新」生效——**变更从「小时级」压缩到「秒级」**。这也是「配置中心」（Apollo、Nacos、etcd 配置）的通用模式。

## 3 分布式队列与公平锁

**问题**：多个消费者按顺序取任务（队列），或多个请求按顺序获得资源（公平锁）。

**ZooKeeper 实现**（用顺序节点 + watch）：

1. 生产者创建**顺序节点**：**`task_0000000001`、`task_0000000002`**…——**序号即入队顺序**。
2. 消费者读 **`/queue`** 下最小序号的节点，取走任务并删除；同时 watch 次小节点。
3. 公平锁：竞争者创建顺序节点，**序号最小者获锁**；释放后（删除节点），watch 者接棒——**先到先得**，无饥饿。

**队列与公平锁的统一**：它们都建立在「**顺序节点的序号 = 全局顺序**」上——入队/加锁的顺序由 ZooKeeper 的线性化写保证，节点消失（任务消费/锁释放）由 watch 通知。这个模式在分布式任务调度、资源互斥里极其常用。<span class="marginnote">「顺序节点 = 全局顺序」是这个模式的核心：ZooKeeper 保证 create 顺序节点的序号单调递增且全局一致——所以「序号」就是「时间序」的可靠替代（不需要时钟，第 3 篇的逻辑）。这也是「逻辑时钟」思想在协调服务里的直接落地：<strong>序号代替时间戳，顺序代替时钟</strong>。</span>

## 4 模式背后的统一思想

三个模式（选主、配置、队列）背后是同一套思想，提炼出来就是「ZooKeeper 协调的四个积木」：

| 积木 | 用途 | 关键性质 |
| --- | --- | --- |
| **持久节点** | 存配置、元数据 | 生命周期由显式删除控制 |
| **临时节点** | 感知成员存活（选主） | 会话结束自动消失 |
| **顺序节点** | 全局顺序（队列/公平锁） | 序号单调递增、全局一致 |
| **watch** | 变更订阅（配置推送） | 实时通知、免轮询 |

**组合规则**：

选主 = 临时 + 顺序 + watch。
配置 = 持久 + watch。
队列/公平锁 = 顺序 + watch。

理解了这四个积木与组合规则，任何「分布式协调问题」都能映射到 ZooKeeper 的解法——这就是「协调服务」作为通用基础设施的价值。<span class="marginnote">这套模式的边界也要看清：ZooKeeper 的 watch 是<strong>一次性</strong>的（触发后要重新设置）——所以「读 + watch + 再检查」要循环使用，防止「读与 watch 之间漏掉变更」。ZooKeeper 文档明确要求「先设置 watch 再读数据」的顺序，否则可能错过中间发生的变更——这是实现细节里最容易出 bug 的地方。</span>

## 5 公式解析：选主接管的时间

把「ZooKeeper 选主故障转移的速度」量化。设主节点崩溃，临时节点在**会话超时 $S$** 后删除，watch 触发到新主接管用时 $T_{\text{react}}$：

$$
\text{故障转移时间} \approx S + T_{\text{react}} \approx S + (\text{watch 触发} + \text{创建新节点} + \text{检查最小序号})
$$

拆解：

- **$S$（会话超时）**：主崩溃后，ZooKeeper 要等「会话超时」才删临时节点——这是故障转移的主要延迟（默认几十秒，可配小些）。
- **$T_{\text{react}}$**：watch 触发 → 候选者重新检查 → 创建节点 → 判定最小序号的反应时间（毫秒级）。
- **权衡**：$S$ 小则接管快，但「网络抖动导致会话误判过期」的概率高（活节点被误判死）；$S$ 大则误判少，但故障接管慢。
- **工程读数**：ZooKeeper 选主的故障转移时间 ≈ 会话超时——**会话超时是「故障接管速度」与「误判风险」之间的旋钮**。

这条式子的工程含义：**协调服务的「故障转移时间」与「误判概率」共享同一个参数（会话超时）**。想要「秒级接管」，就要接受「网络抖动可能误判」；想要「绝不误判」，就要等「几十秒」。这是分布式系统「没有免费午餐」在协调服务上的又一次体现——选主方案的调优本质上是在这个旋钮上找位置。<span class="marginnote">这也是「为什么很多系统用 etcd 替代 ZooKeeper」的动机之一：etcd 的租约（lease）机制把「会话超时」的语义做得更灵活（TTL 可配、可续租），让故障转移的「速度/误判」旋钮更容易调。但底层思想完全相同——「超时即释放」+「通知接管」。</span>

## 6 小结

- **选主**：临时 + 顺序节点 + watch——最小序号当主，崩溃自动转移。
- **配置分发**：持久节点 + watch——变更实时推送、免轮询、高可用。
- **队列/公平锁**：顺序节点 + watch——序号即顺序，先到先得、无饥饿。
- 四个积木：持久/临时/顺序节点 + watch——协调问题的通用拼装件。
- 统一思想：**序号代替时间戳**（逻辑时钟落地）、**watch 代替轮询**、**临时节点代替心跳**。
- 故障转移时间 ≈ 会话超时——「接管速度」与「误判风险」共享同一个旋钮。
