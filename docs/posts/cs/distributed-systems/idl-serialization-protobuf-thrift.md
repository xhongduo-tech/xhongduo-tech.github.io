## 为什么从 IDL 与序列化开始

上一篇讲了 RPC 的骨架，stub 要把参数序列化成字节流。序列化格式的选择是 RPC 框架里最影响工程体验的一环：字段重命名会不会破坏兼容？新增字段老客户端能不能继续跑？多语言之间怎么保证一致的解读？**IDL（接口定义语言）**与**二进制序列化格式**就是回答这些问题的标准答案。<span class="marginnote">本篇对标 DDIA 第4章「数据编码」：它把序列化放在「数据流：消息、服务、数据库」的大框架里讨论。Protobuf、Thrift、Avro 三足鼎立，本篇聚焦前两者，Avro 在《大数据》相关篇章再展开。</span>

## 1 IDL：一份文件，八方语言

**IDL（Interface Definition Language，接口定义语言）**：一种与具体编程语言无关的描述语言，用来声明数据结构与远程接口的签名。一个典型的 Protobuf 消息长这样：

```proto
message User {
  string user_id = 1;
  string name   = 2;
  int32  age    = 3;
}
```

这份文件由 `protoc` 编译器处理，为每种目标语言生成对应的类与序列化代码。Java、Go、Python、C++ 客户端拿到的是各自语言的 `User` 类，但它们在网络上交换的字节流格式完全一致。<span class="marginnote"><strong>辨析｜易错点：</strong>IDL 不等于「数据格式」。IDL 管「长什么样、怎么生成代码」，序列化格式管「字节流怎么排」。同一份 IDL 可以有多种 wire format；Protobuf 的 IDL 与二进制编码是配套发布，容易混为一谈。</span>

## 2 字段编号：兼容性的命门

Protobuf 与 Thrift 的序列化格式有一个共同的核心设计——**每个字段都被编上数字编号**（如 `user_id = 1`），而不是用字段名字符串。字节流里记录的是「编号 + 值」，字段名只存在于 IDL 文件里。这带来两个决定性的好处：

- **空间省**：传输整数编号而非字符串名。`name` 这个名字要 4 字节，编号 `2` 只要 1 字节。
- **兼容演化**：新增一个字段 `email = 4`，老版本代码不知道它，却仍能正确跳过并解析其它字段；删除字段只需保留其编号不再复用。

于是演进规则水到渠成：**加字段只加新编号，绝不复用旧编号；删字段只保留编号；改字段类型要谨慎**（Protobuf 提供兼容类型表）。这套规则保证了「向后兼容」——新写的消息旧代码能读，旧消息新代码也能读。<span class="marginnote">这正是分布式系统里「滚动升级」的基石：微服务里 100 个实例不可能同时切换版本，新旧版本必须能在一段时间内互读消息。没有字段编号与兼容规则，滚动升级就是一场拆炸弹。</span>

## 3 Protobuf 的二进制编码：Varint 与 Tag

Protobuf 的 wire format 逐字段编码为「**Tag-Value**」对。Tag 是字段编号与类型的合体：低 3 位存 wire type（决定值的编码方式），高位右移存字段编号。

以字段 `user_id = 1`（string 类型，wire type 2）为例，Tag 字节为 `0x0A`（编号 1 左移 3 位 `0x08` 再或上类型 `2`）。其后的值是变长整数编码：

$$
\text{varint}(n) = \text{每 7 位一组，低组在前，最高位作续位}
$$

拆解 varint：

- 整数按 7 位切成一组，组内高位（第 8 位）作为**续位（continuation bit）**：为 1 表示后面还有字节，为 0 表示这是最后一组。
- 小整数只占 1 字节：`300` 的二进制是 `10 0101100`，切两组，低位组 `0101100` 补续位 `1` → `10101100`，高位组 `0000010` 补续位 `0` → `00000010`，故 300 编码为 `AC 02`。<span class="marginnote">Varint 的设计哲学是「小数字便宜」：绝大多数业务数据（ID、计数、状态码）都小，1 字节就能装下；只有大数字才付出更多字节。这种对真实分布的倾斜让 Protobuf 在典型负载下体积远小于 JSON。</span>

**Thrift** 的编码类似：每个字段是「类型字节 + 字段编号 + 值」，也带 varint 风格的长度前缀。Protobuf 用隐式类型（在 IDL 里声明），Thrift 显式写类型字节——细节有差别，思想同源。

## 4 公式解析：为什么 JSON 不如 Protobuf 紧凑

拿「用户点赞计数」这个真实场景对比两种编码的体积。一个字段 `likes = 123456789`：

$$
\text{JSON: } \underbrace{\text{`"likes":123456789`}}_{17\text{ 字节}} \qquad \text{Protobuf: } \underbrace{\text{`08 15 CD 5B 07`}}_{5\text{ 字节}}
$$

逐项拆解：

- JSON 里字段名 `"likes"` 以明文字符串形式出现在每条消息里——7 个字符；数字 9 位字符，加冒号引号逗号，共 17 字节。
- Protobuf 里 Tag 字节 `08`（编号 1，varint 类型）表头 1 字节；`123456789` 的 varint 是 `15 CD 5B 07` 共 4 字节。字段名只在 IDL 文件里出现一次，网络上传的是编号。
- 单条消息差异只有 12 字节，但在每秒百万级消息的流水线上，再乘以重复的字段名，体积差距可达 30%–50%，同时 CPU 解析成本也随字段名字符串比较而上涨。

这不是说 JSON 一无是处——它的可读性、自描述性（不需要 IDL 就能看懂）在调试、日志、外部 API 场景无可替代。**选型原则是：机器对机器、高吞吐、多语言 → 二进制 + IDL；人对机器、低吞吐、要可读 → JSON。**<span class="marginnote"><strong>辨析｜易错点：</strong>「用 JSON 做 RPC」本身没错，错的是把 JSON 直接当长期 API 契约却不做版本管理。即便用 JSON，也应该有类似 IDL 的 schema 文档与兼容规则，否则字段改名、删除都会在升级时静默炸掉。</span>

## 5 小结

- **IDL** 用语言无关的声明统一接口与数据结构，由代码生成器产出各语言 stub——多语言协作的基石。
- **字段编号**是 Protobuf/Thrift 兼容性的命门：字节流传编号而非名字，因此空间省、能演化。
- 演化规则：**只加不删**、编号不复用、类型替换走兼容表——这是滚动升级与长期演进的前提。
- Protobuf 的 wire format 是 **Tag-Value** + **varint**：小数字 1 字节，大数字才变长。
- 与 JSON 的体积对比说明：机器间高吞吐选二进制，人可读场景选 JSON；选 JSON 也要管好 schema。
