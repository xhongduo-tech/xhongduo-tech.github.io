## 为什么从 TLA+ 开始

上一节立了「形式化验证」的目标，这一节学它的主力工具：**TLA+**（Temporal Logic of Actions，动作时序逻辑）——Lamport 设计的规约语言。它的核心思想极简：**把系统描述成「状态机」，把正确性描述成「不变量 + 时序性质」**，然后用 TLC 模型检验器穷举验证。理解了 TLA+，你就拥有了「把分布式协议写清楚」的语言。<span class="marginnote">TLA+ 是 Lamport 在 1990 年代为「精确描述系统」而设计的语言，配套 TLC 模型检验器。它被亚马逊用于验证 DynamoDB、S3 等核心系统的设计——亚马逊工程师的著名报告说「TLA+ 帮我们发现了多个用测试测不出的设计 bug」。</span>

## 1 系统 = 状态机

TLA+ 的第一个信念：**任何分布式系统都可以描述成一个状态机**——由「状态（state）」与「状态转移（transitions）」组成。

**状态（state）**：系统在某个时刻的「变量取值」——比如 leader 是谁、日志有多长、变量 `x` 的值是什么。
**状态转移（action）**：系统从状态 A 到状态 B 的一次变化——比如「leader 追加一条日志」「follower 收到心跳」「节点崩溃」。
**行为（behavior）**：状态与转移交替构成的序列——一条「执行轨迹」。

在 TLA+ 里写系统，就是写「初始状态集合」+「一组允许的状态转移」——**系统的所有可能行为 = 从初始状态出发、沿允许转移走出的所有路径**。这个「所有路径」正是模型检验要穷举的对象。

## 2 不变量与安全性质

**不变量（invariant）**是「**每个状态都必须满足**」的条件——坏状态永远不该出现。典型的分布式不变量：

线性一致：「任意时刻至多一个 leader」。
共识安全：「已提交的日志条目永远不会被覆盖」。
事务正确：「余额永远 ≥ 0」。

TLA+ 里检查不变量：写一个布尔表达式 `Inv`（如「恰好一个 leader」），TLC 穷举所有可达状态，检查每个状态该不变量是否成立——**任何一个状态违反，就报错并给出「反例路径」**。

不变量是「安全性（safety）」的形式化：**「坏事永不发生」**。它只能防「坏状态」，不能保证「好事最终发生」——后者需要时序性质。

## 3 时序逻辑与活性

**时序逻辑（temporal logic）**描述「**随时间演化的性质**」——不只是「某个状态满足」，而是「沿着行为，某些事最终发生或不发生」。

两个核心时序算子：

**□（always，永远）**：`□P` 表示「在行为的每一个状态，P 都成立」——安全性质。
**◇（eventually，最终）**：`◇P` 表示「在行为的某个未来状态，P 成立」——活性性质。
组合：`□◇P` = 「从任意时刻看，P 最终都会发生」——强活性，如「leader 最终会被选出」「请求最终会被处理」。

活性性质的形式化：**「好事最终发生」**。检查活性比不变量难（TLC 要检测「是否永远卡在某个没达成 P 的循环」），但它是「系统不会死锁」的保证。

**安全 vs 活性**：不变量防「坏状态」（安全），时序性质保证「好进展」（活性）——**分布式协议的正确性 = 安全 + 活性**。Raft 的「选举安全」是不变量，Raft 的「最终选出 leader」是活性。

## 4 一个最小的 TLA+ 例子

看一个「递增计数器」的最小规约，感受 TLA+ 的语法：

```tla
---- MODULE Counter ----
EXTENDS Naturals

VARIABLE x

Init == x = 0
Next == x' = x + 1
Spec == Init /\ [][Next]_x

Inv == x >= 0
====================
```

拆解：

`x'`：**下一个状态**的 x（primed 表示「转移后的值」）——动作描述「现在与下一个状态的关系」。
`Next`：允许的转移——这里只有「x 加一」。
`[][Next]_x`：**每一步要么是 Next，要么 x 不变**——「保持稳定或按规则推进」。
`Inv`：待验证的不变量——TLC 检查「所有可达状态 x ≥ 0」是否成立。

这个例子太小，但展示了 TLA+ 的全部骨架：**变量 + Init（初始）+ Next（转移）+ Spec（行为集）+ Inv（不变量）**。任何分布式协议（Paxos、Raft、2PC）都是这个骨架的放大版——变量更多、转移更复杂、不变量更精细。<span class="marginnote"><strong>辨析｜易错点：</strong>TLA+ 的 `Next` 描述的是「<strong>可能</strong>的转移」，不是「必须」的转移——系统在每个状态「选择」一条允许的转移执行。所以 TLA+ 建模的是「所有可能的执行」，而不是「某条特定的执行」——这正是它比「测试一条路径」强大的原因：它穷举的是「所有选择」。</span>

## 5 公式解析：TLA+ 与逻辑的对应

把 TLA+ 的核心概念映射到标准逻辑，理解它的表达力：

$$
\text{TLA+ 规约 } \mathcal{S} = \text{Init} \land \Box[\text{Next}]_{vars} \land \text{时序条件}
$$

拆解：

- **Init**：状态公式——描述「允许的初始状态集合」。
- **$\Box[\text{Next}]_{vars}$**：时序公式——「从每个状态出发，下一步要么执行 Next（某个允许的转移），要么变量不变」——这就是「状态机」的时序表达。
- **时序条件**：可加 `WF_vars(Next)` / `SF_vars(Next)`（弱/强公平性）——「如果某动作持续可执行，最终会被执行」——用于建模「活性」的合理假设。
- **正确性 = 规约蕴含性质**：TLA+ 验证的命题是「**规约 $\mathcal{S}$ 蕴含性质 $P$**」——「所有符合规约的行为都满足 $P$」——用 TLC 穷举检验。

这条式子的工程含义：**TLA+ 把「验证正确性」变成「验证一个逻辑蕴含」**——系统行为（$\mathcal{S}$）与正确性质（$P$）都是形式化公式，验证就是「证明蕴含成立」。这个「形式化」带来的好处：**无歧义**（不像自然语言）、**可自动化**（TLC 穷举）、**可反例**（蕴含不成立时给出违反路径）。<span class="marginnote">Lamport 反复强调的「简单性」：TLA+ 的核心只有「状态机 + 时序逻辑」两个概念——不像一些形式化方法引入复杂的类型系统与代数结构。他认为「能用一个状态机描述的系统，就该用状态机描述」——TLA+ 的简洁是它的力量，也是它「易学难精」的原因（抽象要恰到好处）。</span>

## 6 小结

- **TLA+ 的信念**：系统 = 状态机——状态 + 转移 + 行为。
- **不变量**：每个状态必须满足的条件——「坏事永不发生」（安全性）。
- **时序逻辑**：`□`（永远）与 `◇`（最终）——「好事最终发生」（活性）。
- 最小规约骨架：`Init / Next / Spec / Inv`——变量、初始、转移、行为集、不变量。
- **正确性 = 规约蕴含性质**：所有符合规约的行为都满足性质——用 TLC 穷举检验。
- TLA+ 简洁（状态机 + 时序逻辑）而强大（穷举所有选择）——分布式协议的形式化语言。
