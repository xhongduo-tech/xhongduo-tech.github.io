## 为什么从 RPC 开始

分布式系统里节点之间要「说话」。可让每个应用自己拼 TCP 报文、解析字节流、处理粘包，既痛苦又易错。**RPC（远程过程调用，Remote Procedure Call）**把跨节点的通信伪装成一次普通的函数调用：你在本地写 **`add(1, 2)`**，编译器与运行时替你把参数打包、发到远端、等结果、解包返回。<span class="marginnote">RPC 的思想可追溯到 1976 年 Xerox PARC 的 Cedar 系统，Nelson 的博士论文把它理论化。今天它已是分布式应用的事实标准——从 gRPC 到 Thrift，从微服务到内部 API，全是 RPC 的子孙。</span>

## 1 RPC 的核心抽象：让远程调用像本地调用

本地函数调用有三件事：**传参**（压栈）、**执行**（跳转）、**返回**（取返回值）。RPC 想让远程调用也有同样的体验，于是在两者之间插入一条「透明层」——**stub（桩）**。调用方只跟 client stub 打交道，client stub 把调用「包装」成网络消息发出；对端 server stub 收下消息、解包、调用真正的函数、再把结果包装成响应发回。<span class="marginnote"><strong>辨析｜易错点：</strong>RPC 的「透明」是有限度的。本地调用要么成功要么抛异常，远程调用还会「成功但结果丢了」（响应在网络中丢失）。把 RPC 完全当本地调用写，是分布式系统十大谬误里的头号陷阱——见《分布式计算的谬误》。</span>

一次完整的 RPC 调用沿这条链路走：

1. 客户端调用 client stub 的本地函数 **`add(1, 2)`**；
2. client stub 把函数名与参数**序列化**成字节流（marshalling）；
3. 传输层（通常 TCP）把字节流发给服务端；
4. server stub **反序列化**，还原参数，调用真实函数；
5. 服务端执行完毕，把返回值序列化回传；
6. client stub 反序列化，把结果交回给调用者。

## 2 序列化：Marshalling 与 Unmarshalling

**序列化（marshalling）**：把内存中的数据结构（结构体、列表、哈希表）转换成字节序列，以便在网络上传输或在磁盘上存储；**反序列化（unmarshalling）** 是它的逆过程。RPC 的正确性直接取决于双方对字节格式理解一致。

序列化要解决的核心问题是**格式约定**：字节流里哪个字段在哪个偏移、多长、什么类型。这引出一个关键概念——**IDL（接口定义语言）**：用一份与语言无关的接口文件描述函数签名与数据结构，再由代码生成器为每种语言产出 stub。这样 Go 写的客户端和 Java 写的服务端能对同一份 IDL 达成精确一致的协议。<span class="marginnote">「语言无关的接口 + 代码生成」是 RPC 框架的骨架：Protobuf、Thrift、Cap'n Proto 都遵循这一模式。下一节我们专门拆解 IDL 与序列化格式的设计。</span>

## 3 RPC 的传输层与语义

RPC 通常跑在 **TCP** 之上（面向连接、可靠、有序），也可以跑在 UDP 或 HTTP 上。传输层之上，RPC 还要处理**调用语义**——网络不可靠，一次调用可能遇到三种结局：

- **至多一次（at-most-once）**：发一次，丢了就丢了，调用方超时后收到错误。
- **恰好一次（exactly-once）**：发且只发一次。理论上需要分布式事务才能严格做到，工程上几乎不存在。
- **至少一次（at-least-once）**：发，确认不到就重发；被调用方可能收到重复执行。配合**幂等**实现，是工程上最实用的选择。

为什么「恰好一次」如此难？因为发送方无法区分「响应丢了」和「服务端没处理」——这是部分失败问题在 RPC 层的投影。**只要重试，就可能重复；要不重复，就不能重试；不重试，就可能失败。**工程答案通常是：接受「至少一次」，把被调用方写成**幂等**的。

## 4 公式解析：一次 RPC 的延迟构成

一次 RPC 的端到端延迟可以粗略分解为：

$$
T_{\text{rpc}} = t_{\text{ser}} + t_{\text{net}} + t_{\text{proc}} + t_{\text{deser}} + t_{\text{queue}}
$$

逐项拆解：

- $t_{\text{ser}}$：客户端序列化参数的时间，与数据大小、格式复杂度成正比。
- $t_{\text{net}}$：网络往返时间（RTT），受物理距离限制——跨洲一次 RTT 上百毫秒，无法靠优化代码消除。
- $t_{\text{proc}}$：服务端真正执行函数的时间。
- $t_{\text{deser}}$：服务端反序列化 + 客户端反序列化返回值的时间。
- $t_{\text{queue}}$：双方在队列/缓冲区里的等待时间——负载高时这一项会吞噬其余全部。

这条式子的工程教训：**网络延迟占大头时，压缩序列化字节数、批量请求、用连接复用，收益远大于优化服务端代码**；而 $t_{\text{queue}}$ 提醒我们 RPC 延迟服从长尾分布，超时参数必须参照 p99 而非平均。<span class="marginnote">序列化格式的选择直接写进这条式子：JSON 可读但体积大、解析慢；Protobuf/Thrift 紧凑、解析快但需代码生成。工业界常用「小负载 JSON 够用、大流量上二进制」的折中。</span>

## 5 小结

- **RPC** 把远程调用伪装成本地调用，靠 **stub 桩**做透明的打包、传输、解包。
- 调用链路：序列化 → 传输 → 反序列化 → 执行 → 序列化 → 返回。
- 远程调用只有三种语义：**至多一次、至少一次、恰好一次**；「恰好一次」在无协调下不可严格实现。
- 工程上常用「**至少一次 + 幂等**」组合：重试带来的重复执行由被调用方去重。
- RPC 延迟 = 序列化 + 网络 + 执行 + 反序列化 + 排队；网络与排队决定长尾，优化要先抓大头。
- RPC 的「透明」有限度：它掩盖不了部分失败，只掩盖得了字节级细节。
