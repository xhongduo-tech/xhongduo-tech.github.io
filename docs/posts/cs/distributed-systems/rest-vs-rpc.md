# REST 与 RPC 的取舍

<div class="epigraph">

## 为什么从 REST 与 RPC 的取舍开始

RPC 篇我们一直强调「让远程调用像本地调用」。可还有一种完全不同的哲学——**REST**——它反其道而行：不隐藏远程性，而是把「在网络上操作资源」明明白白地建模出来。微服务时代，REST 与 RPC 并肩统治着服务间通信，选谁不选谁，背后是对**耦合方式、可缓存性、可演化性**的取舍。<span class="marginnote">REST 由 Roy Fielding 在 2000 年博士论文《Architectural Styles and the Design of Network-based Software Architectures》中定义，本意是描述 Web 的架构风格；RPC 的哲学则深植于函数式思维。理解二者的差异，本质是理解「资源」与「动作」两种抽象的分野。</span>

## 1 两种世界观：资源 vs 动作

**RPC** 把远程能力建模为**函数调用**：`createOrder(userId, items)`、`payOrder(orderId)`。接口描述的是「动词」——对系统做什么操作。客户端像调用本地函数一样组织参数，依赖的是「这个动作的服务端实现」。

**REST（Representational State Transfer，表述性状态转移）**把一切建模为**资源**：`/orders/123`、`/users/42`。接口描述的是「名词」——系统里的对象。客户端通过标准化的 HTTP 方法操作资源：`GET` 读、`POST` 新建、`PUT` 整体替换、`PATCH` 局部更新、`DELETE` 删除。状态转移发生在服务器，客户端拿到的只是资源的**表述（representation）**。<span class="marginnote"><strong>辨析｜易错点：</strong>「用 HTTP + JSON」不等于「REST」。REST 是六条架构约束（客户端-服务端、无状态、可缓存、统一接口、分层、按需代码）的组合，多数自称 REST 的 API 只做到了「用 HTTP 动词」，连资源链接（HATEOAS）都很少实现。工程上我们常说的「RESTful」其实是「类 REST 的 HTTP JSON API」。</span>

## 2 核心差异对照

| 维度 | REST（资源为中心） | RPC（函数为中心） |
| --- | --- | --- |
| 抽象单位 | 资源 / 名词 | 方法 / 动词 |
| 调用方式 | HTTP 动词 + URL | 函数名 + 参数 |
| 耦合对象 | 资源结构与表示 | 服务端函数签名 |
| 可缓存性 | 天然（HTTP 缓存、CDN） | 难（POST 语义不幂等） |
| 契约表达 | URL 结构 + 媒体类型 | IDL（Protobuf/Thrift） |
| 性能 | 文本编码、开销偏大 | 二进制、紧凑高效 |
| 适合场景 | 对外公开 API、浏览器 | 内部高吞吐、多语言服务间 |

这张表的每一行都是一次取舍：REST 牺牲了紧凑性与「直接调用」的便利，换来了统一接口、可缓存、可浏览；RPC 牺牲了可缓存与自描述，换来了性能与强类型。<span class="marginnote">REST 的「无状态」约束意味着服务器不保存会话状态，每个请求自足——这让水平扩展变得极简单（任意副本都能服务任意请求），代价是状态要么放客户端要么放数据库。这是 REST 与可扩展性的天然亲和力。</span>

## 3 可演化性：哪个更好升级

分布式系统的接口迟早要变，**可演化性（evolvability）**是比性能更现实的取舍标准。

- **REST 的演化靠 URL 版本化**：`/v1/orders` 与 `/v2/orders` 并存，老客户端继续用 `/v1`，新客户端切 `/v2`。资源模型稳定时，新增子资源或字段往往**非破坏性**——加个字段老客户端忽略即可。
- **RPC 的演化靠 IDL 兼容规则**：字段编号不复用、只加不删（见 IDL 篇）。二元化的优势是演化规则可以被编译器强制检查——改坏了一个字段，构建直接失败，而不是运行时才爆。

结论不是「谁更能演化」，而是**演化机制不同**：REST 依赖媒体类型与 URL 约定（约定优于配置，靠纪律），RPC 依赖 IDL 编译器（规则强制，靠工具）。<span class="marginnote">实践中两者常混用：对外用 REST 给第三方，对内用 gRPC 给自家微服务。因为第三方要可读、可调试、可缓存（REST 优势），而内部流量大、要求强契约（RPC 优势）。一套系统两套接口并不罕见。</span>

## 4 公式解析：接口耦合度

把「接口对调用方的束缚程度」量化为一个粗略指标——**耦合度**，定义为一处接口改动时需要同步改动的调用方比例：

$$
C_{\text{coupling}} = \frac{\text{受影响调用方数}}{\text{总调用方数}}
$$

拆解：

- 分子「受影响调用方」取决于接口改动是**破坏性**还是**非破坏性**。REST 里给资源加字段通常非破坏（$C \approx 0$）；删除字段则破坏（$C \to 1$）。
- RPC 里改函数签名（加必填参数）往往破坏；按 IDL 规则**加可选字段**则非破坏。
- 工程目标是让**演化路径上的改动尽量非破坏**，使 $C$ 保持低位——这比「选 REST 还是 RPC」更本质：**决定耦合度的不是风格，而是你有没有遵守非破坏演化纪律**。<span class="marginnote">这也是「契约测试」（contract testing）的动机：在部署前自动验证调用方与服务端对契约的理解一致。无论 REST 还是 RPC，契约漂移都是分布式系统里最隐蔽的故障源之一。</span>

## 5 小结

- **REST** 以资源为中心，靠 HTTP 动词 + URL 操作「名词」；**RPC** 以函数为中心，靠函数名 + 参数执行「动词」。
- REST 优势：统一接口、天然可缓存、可浏览、无状态易扩展；RPC 优势：紧凑高效、强类型、契约由编译器强制。
- 可演化性机制不同：REST 靠 URL 版本化与媒体类型纪律，RPC 靠 IDL 字段编号规则。
- **耦合度的决定因素是「非破坏演化纪律」，而不是风格本身**。
- 实践常态：**对外 REST，对内 gRPC**；两套接口服务于两类调用方。
