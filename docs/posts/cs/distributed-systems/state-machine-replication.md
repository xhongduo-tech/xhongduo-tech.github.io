## 为什么从状态机复制开始

共识（Raft/Paxos）、复制日志、检查点恢复——前面这些机制最终都服务于同一个抽象：**状态机复制（State Machine Replication, SMR）**。它是「让一组副本表现得像一台可靠的机器」的通用范式：**所有副本从同一初始状态出发，按同一顺序执行同一命令序列，则它们的状态必然相同**。掌握了 SMR，你就掌握了分布式容错的顶层设计。<span class="marginnote">SMR 由 Lamport 1978 年提出思想、Schneider 1990 年系统化，是 Raft/Paxos/Zab 所有复制共识协议的「幕后理论」。理解 SMR = 理解「共识为什么能带来容错」——共识排定顺序，SMR 消费顺序。</span>

## 1 SMR 的核心：确定性 + 顺序

SMR 的正确性由两个条件保证：

**确定性（determinism）**：给定相同的状态与命令，状态机的输出与下一个状态完全确定——系统时间、随机数、时钟读取这类**非确定性**操作必须被排除或提前物化。
**顺序一致性（total order）**：所有副本按**完全相同的顺序**应用命令。

两个条件合起来：**初始相同 + 命令相同 + 顺序相同 → 状态永远相同**。哪怕其中几个副本崩溃了，只要大多数副本还按同一顺序执行，整个系统就「看起来」是一个可靠的单机。

为什么这两个条件就够了？因为「状态」是「初始状态 + 命令序列」的确定函数——命令序列相同，函数值就相同；副本的崩溃/恢复只是「在某个中间点暂停」，只要它能重新同步命令序列，就能追到与别人一致的状态。<span class="marginnote"><strong>辨析｜易错点：</strong>SMR 的「确定性」是硬性要求，也是实现里最容易被破坏的一环。副本各自调用 `time.Now()`、读取本地环境变量、用本地随机种子，都会让「同一命令在不同副本产生不同结果」——状态瞬间分叉。工程上要么把这类调用「物化」（在 leader 处取值，随命令传播），要么禁止。Raft 论文明确要求命令必须确定性。</span>

## 2 SMR 的架构：复制日志是命令序列

SMR 的工程实现就是「复制日志 + 应用状态机」：

**复制日志（replicated log）**：共识协议（Raft/Paxos）维护一条日志——日志条目就是**命令**，顺序由共识保证（每个条目有唯一序号）。
**状态机（state machine）**：每个副本把日志条目录入状态机，输出响应并更新状态。
**客户端交互**：客户端把命令发给 leader；leader 把命令写进日志；日志被多数派复制并提交后，状态机执行命令，leader 把结果返回客户端。

一条命令的完整旅程：

1. 客户端把命令发给 leader；
2. leader 把命令追加到复制日志，并同步给多数派副本；
3. 多数派确认后，leader 将该日志条目标记为已提交；
4. 各副本按同一顺序把日志条目应用到自己的状态机；
5. leader 把执行结果返回给客户端。

**关键的容错性质**：只要日志的「前缀」在多数派上一致（Raft 的日志匹配性质），那么「已提交的条目」在哪个副本上执行结果都相同——**部分副本崩溃不影响整体正确性**，因为幸存副本各自的状态机仍按同一顺序前进。

## 3 确定性命令的工程处理

非确定性命令是 SMR 实现的头号坑。标准处理手法：

**Leader 单点执行**：非确定性计算只在 leader 执行，把**结果**（不是表达式）写进日志——`time.Now()` 变成 leader 算好的时间戳，随命令传播。各副本应用同一个值，确定性恢复。
**禁止直接使用**：状态机代码里不调用系统时间、随机数、环境变量——所有外部输入必须来自命令本身。
**隔离与注入**：测试环境强制注入「确定性」检查——同一命令在双副本上跑，输出必须一致（差分测试）。

DDIA/Raft 论文的提醒：**非确定性是 SMR 实现 bug 的第一来源**——比网络故障更隐蔽，因为它「平时不炸、关键时刻分叉」。生产级实现（etcd、TiKV）都内置「确定性检查」来防这类回归。

## 4 检查点与快照在 SMR 里的角色

SMR 的日志无限增长，需要检查点压缩（上一篇讲过）：

状态机周期性生成**快照**（当前状态 + 日志序号）。
旧日志被截断，恢复时「加载快照 + 重放快照之后的日志」。
**慢副本/新副本**：leader 直接发快照（InstallSnapshot），让它们跳过大部分历史快速追齐。

SMR + 快照的组合是「有限存储 + 无限历史」的解法：**日志保证「从快照点之后」的重放能力，快照保证「任意时刻」的恢复起点**。Raft 的快照、etcd 的 snapshot、Kafka 的 log compaction 都是这个骨架。<span class="marginnote">快照还有一个隐藏作用：<strong>让新副本加入集群变便宜</strong>——不用回放从系统诞生到现在的全部日志，leader 发一个快照就追上了。这也是「SMR 可扩展」的基石：副本数可以动态调整，因为加入成本 = 快照大小，而不是历史总量。</span>

## 5 公式解析：SMR 的正确性条件

把「状态机复制为什么一致」写成严格条件。设副本 $i$ 的初始状态 $S_i(0)$、命令序列 $C_i$、状态转移函数 $\delta$：

$$
\text{若 } S_i(0) = S_j(0) \;\land\; C_i = C_j \;\Rightarrow\; \forall k:\; \delta(S_i(k-1), C_i(k)) = \delta(S_j(k-1), C_j(k))
$$

拆解：

- **初始相同**：$S_i(0) = S_j(0)$——所有副本从同一状态出发。
- **命令序列相同**：$C_i = C_j$——每个位置执行同一条命令。
- **确定性**：$\delta$ 是函数（同一输入同一输出）——状态转移不含随机性。
- **结论**：逐位置归纳，任意时刻副本 $i$、$j$ 的状态相同——这就是「状态机复制」的一致性保证。

这条式子的工程含义：**SMR 把「保证副本一致」转化为「保证三个前提」**——初始状态、命令序列、确定性。初始状态靠「快照分发」，命令序列靠「共识协议」，确定性靠「工程纪律」。**共识只解决第二个前提**，另外两个同样关键却常被忽视——这也解释了为什么「共识正确了，系统还会不一致」：很可能是初始状态或确定性出了问题。<span class="marginnote">SMR 的「响应」也有讲究：客户端拿到的是「leader 上执行的结果」，而该命令已被多数派提交——所以响应本身是安全的。若客户端把命令发给「过期 leader」（分区中的旧主），它的响应可能不反映最新状态——这就是为什么 SMR 系统要配「fencing token」或「readIndex」保证客户端不与过期主交互（第 6 篇脑裂与围栏）。</span>

## 6 小结

- **状态机复制**：初始相同 + 命令相同 + 顺序相同 → 状态永远相同——容错的顶层范式。
- 架构 = **复制日志（共识排顺序）+ 状态机（按序执行）**；部分副本崩溃不影响整体。
- **确定性是硬要求**：非确定性命令由 leader 物化结果随命令传播，禁止副本各自取随机/时间。
- **快照 + 日志截断**：有限存储 + 无限历史；新副本靠 leader 发快照快速追齐。
- 三个前提：初始状态（快照）、命令序列（共识）、确定性（纪律）——共识只解决其一。
- SMR 是所有复制共识协议的幕后理论：理解它，Raft/Paxos/Zab 的设计就豁然开朗。
