## 为什么从开发引擎与工具链开始

前面九节把 VR/AR/XR 的原理讲完了：感知、几何、光学、跟踪、交互、移动、音频、触觉、AR 算法。但「原理」离「一个能跑起来的体验」之间，还隔着一层**工程**——用什么写、怎么跑、跑在哪些设备上。这一节讲工业界的真实答案：Unity 与 Unreal 两大引擎、OpenXR 这一套统一接口，以及 WebXR 这条「浏览器里的 XR」路线。<span class="marginnote">这一节是「从理论到实践」的桥梁：你读过的每一块原理（注视点渲染、ATW、平面检测、HRTF），在这里都能找到对应的引擎开关、插件与 API 调用。</span>它不是教你写代码，而是给你一张「工具地图」：知道该去哪找工具、各工具管什么、为什么工具链正在走向统一。

先给整条工具链一个层级观：**底层是设备运行时（headset runtime，厂商提供）→ 中间是开放标准（OpenXR 接口）→ 上层是引擎（Unity/Unreal 或 WebXR 库）→ 最顶是内容与交互层（你写的代码与资产）**。越往上越通用、越接近产品，越往下越具体、越接近硬件。读本节时带上这张层级图，就不会在「引擎、SDK、标准、插件」这些词之间迷路。

## 1 引擎的角色：XR 开发的「操作系统」

**游戏引擎（game engine）**在 XR 里扮演的角色，类似操作系统之于应用：它提供场景管理、渲染、物理、音频、输入、资源管线等基础设施，让你专注「做什么体验」而不是「怎么写渲染器」。LaValle《Virtual Reality》第 2 章把引擎列为 VR 系统的关键软件层——虚拟世界生成器（virtual world generator）——理由是它把《三维几何与图形学基础》里的全部数学和《实时渲染管线》的全部流程打包成了「配置项」：你设置「开注视点渲染」而不是自己写 GPU 内核。

引擎的 XR 支持通常是**插件架构**：核心引擎不知道「头显」是什么，通过「XR 插件」接入具体设备的运行时。这样一次开发、多设备运行——你的 Unity 工程既可以构建到 Quest，也可以构建到 PC VR 或手机 AR，只要装了对应的 XR 插件。这套「引擎 + 插件」的抽象，是理解整个工具链的第一把钥匙。<span class="marginnote">插件架构的两面性：好处是「一套代码多端发布」，坏处是「抽象层会漏」——某个设备独有的能力（如 Vision Pro 的眼动、Quest 的手势）需要额外的「高级功能插件」才能用，抽象层永远追不上硬件创新。</span>

## 2 Unity 与 Unreal：两条主流路线

**Unity** 是当前 XR 内容的绝对主力，尤其是消费级 VR（Quest 生态的大多数内容都是 Unity 写的）。它用 C# 写逻辑、组件化组织对象，上手门槛低；官方的 **XR Interaction Toolkit** 提供了一套开箱即用的交互组件——射线、抓取、传送、手柄输入映射，直接对应我们《交互范式与 3D UI》讲过的各种技术，你甚至不必从零实现它们。<span class="marginnote">Unity 的 XR 管理（XR Management）负责「一次配置、多设备构建」：勾选 Quest/PC 的 XR 插件，构建目标选 Android/Windows，剩下的运行时差异由引擎层消化。</span>

**Unreal** 在**画面上限**上更强——Nanite 虚拟化几何与 Lumen 全局光照让高保真场景成为可能，很多「电影级」VR 演示与高端项目选它。它用 C++ 与可视化蓝图（Blueprint）双轨开发，蓝图让非程序员也能搭交互逻辑。Unreal 的 **XR 插件**与 Meta、Valve 深度集成，同样支持一套工程多设备。

**生态资产**是引擎之争的另一面：Unity 有庞大的 **Asset Store**（数十万可买/免费的模型、材质、脚本、XR 模板），Unreal 有 **Fab 市场**（收购 Quixel 后接管的资源平台）。对中小团队，「用现成资产快速搭场景」往往比「从零建模」省 80% 的时间——这直接影响《前沿应用与伦理》里「XR 内容生产成本」的讨论。而大团队反而要警惕资产依赖：同质化资产会让作品「长着一张脸」。

选引擎没有绝对答案，两条经验法则：**追求「快速上线、生态量大、多端一致」选 Unity；追求「画面极致、复杂光照、C++ 工程」选 Unreal**。对学习而言，Unity 更合适——它的 XR 交互组件让你把本专题的原理逐个「点开验证」。

在引擎内部，XR 渲染的「管线开关」也是一份本专题的实践索引：**多视图渲染（single-pass instanced）**对应《三维几何与图形学基础》的双眼渲染优化，**注视点渲染（foveated rendering）**对应《人类感知系统》的中央凹结构，**动态分辨率（dynamic resolution）**与**异步时间扭曲（ATW）**对应《头显硬件与光学》的时延预算。当你在一份渲染设置面板上看到这些开关，其实是在「配置」前面几章讲过的生理与光学原理——这正是「工具是原理的封装」的最好例证。

## 3 OpenXR：把设备差异挡在门外

2019 年之前，XR 开发最大的痛是**SDK 碎片化**：Oculus SDK、SteamVR SDK、Windows MR SDK 各写各的，换设备 = 重写一大片代码。**OpenXR**（Khronos Group 于 2019 年发布的开放标准）终结了这个局面：它定义了一套**厂商无关的 API**，应用只面向 OpenXR 编程，各设备厂商提供自己的 OpenXR 运行时（runtime）实现——Meta 的 Quest 运行时、Valve 的 SteamVR、微软的 Windows Mixed Reality、甚至 WebXR 都实现了同一套语义。<span class="marginnote">OpenXR 是 Khronos 的第三个「gl」式标准（前两个是 OpenGL 与 Vulkan），它的成功在于「进场早、厂商广」：Meta 与 Valve 这两大死对头在 OpenXR 上罕见地达成一致，因为双方都受不了 SDK 战争。</span>

OpenXR 的诞生也有一段教科书级的行业史：2017 年 Khronos 组建 AR/VR 工作组，Meta（当时的 Oculus）、Valve、微软、HTC 等巨头罕见地坐回同一张谈判桌——因为**「SDK 分裂」已经贵到让所有人想逃**。2019 年 1.0 发布，此后 Oculus SDK 与 SteamVR 原生 SDK 陆续被官方「降级」为 OpenXR 之上的兼容层。到 2024 年，Quest、Vive、Index、Pico、Vision Pro 都提供 OpenXR 运行时，**「面向 OpenXR 开发」已成为 XR 的事实标准**。<span class="marginnote">这场统一与《计算机网络》里「协议分层」的逻辑同构：设备差异是「物理层」，OpenXR 是「传输层」，引擎是「应用层」——每一层只认上一层的接口，互相解耦。</span>

OpenXR 的关键抽象包括：

- **Instance 与 Session**：应用初始化并建立与运行时的会话。
- **Space（空间）**：位姿参照系（局部、舞台、视图等），对应《跟踪与位姿估计》的坐标系概念。
- **Actions（动作）**：把「手柄扳机」「握拳手势」映射成语义化的「抓取」「射击」——**你的代码只认识语义，不认识具体设备按钮**，设备换了你不用改。
- **Frame loop（帧循环）**：每帧由运行时决定「何时渲染哪只眼、何时提交」，把《头显硬件与光学》的时延预算交还给运行时管理。

其中 Frame loop 值得多看一眼：应用调用 `xrBeginFrame` → 查询头显姿态 → 渲染左右眼 → 调用 `xrEndFrame` 把纹理交给运行时。**运行时在帧结尾替你做两件关键的事**：畸变校正（把引擎渲染的画面按镜组畸变表重投影）与异步时间扭曲（如果渲染晚了，用最新姿态重投影旧帧）——这正是《头显硬件与光学》与《三维几何与图形学基础》讲过的时延补偿，在标准层被制度化地内置了。

对开发者最大的红利是**跨设备**：写一套 OpenXR 应用，Quest、Vive、Index、Pico 都能跑；引擎（Unity/Unreal）也把 OpenXR 作为首选 XR 后端，插件架构与 OpenXR 在「抽象设备」这一点上理念完全一致。

## 4 WebXR：浏览器里的 XR

**WebXR**（W3C 标准）把 XR 搬进浏览器：用户打开网页，授权后头显/手机就进入 XR 会话，无需安装任何应用。它基于 WebGL/WebGPU 渲染，配合 **Three.js** 等库，用 JavaScript 就能做完整的 VR/AR 体验。<span class="marginnote">WebXR 的杀手锏是「零安装 + 免分发」：链接即用、跨平台、天然可分享，特别适合教学演示、展厅、协作工具这类「不想让用户装 App」的场景；代价是性能上限低于原生（浏览器开销、内存限制）。</span>

WebXR 的使用模型也直接体现本专题原理：`navigator.xr.requestSession('immersive-vr')` 请求沉浸式 VR 会话，会话里用**参考空间（reference space）**管理位姿（对应坐标系统一）、用**输入源（XRInputSource）**处理手柄与手势（对应交互范式）、每帧提交左右眼渲染目标（对应双目录渲染）。**A-Frame**（基于 Three.js 的 HTML 标签式框架）进一步把门槛降到「写 HTML 就能出 VR」，是 WebXR 教学的最短路径。

WebXR 与原生开发的取舍：**原型与轻交互选 WebXR，重度体验（高保真、复杂交互、低时延）选原生 + OpenXR**。值得注意，Vision Pro 自带 Safari 的 WebXR 支持，让 WebXR 第一次在「旗舰级」设备上成为一等公民。

一个能立刻上手的最小 WebXR 例子（概念层）：用 Three.js 建一个 `renderer`，`navigator.xr.requestSession('immersive-vr', { optionalFeatures: ['local-floor', 'hand-tracking'] })` 进入会话，把 `renderer.xr.enabled = true` 后，Three.js 会自动处理「每帧查询头部位姿 + 双目录渲染 + 提交给浏览器」——你的核心工作量从「写渲染器」降为「摆场景」。这正是引擎与 WebXR 协作的理想形态：**平台负责「怎么进世界」，你负责「世界里有什么」**。

## 5 XR 项目的工程实践

无论选哪条工具链，真实项目都要过一遍相似的工程流程——这部分就是 Sherman & Craig 在系统实现章节、Jerald《The VR Book》第 30–33 章「迭代设计」反复强调的内容：

**性能剖析（profiling）**是 XR 开发的第一课。前面讲过「90 Hz × 双眼 × 20 毫秒」的预算，工程上就要用 GPU 剖析工具（Unity 的 Frame Debugger、Unreal 的 Insights、Meta 的性能 HUD）逐帧查看「哪一行超标」。最常见的三大瓶颈：**Draw Call 过多**（合并网格、用实例化）、**全屏后处理太重**（关掉 SSR 换手工反射）、**CPU 抢了 GPU 的帧**（把物理、寻路挪到异步线程）。<span class="marginnote">很多「看起来不复杂」的 XR 场景跑不动，不是画面太华丽，而是 Draw Call 爆炸——一个空场景开双眼渲染后，所有静态物体最好合并进一两个 Draw Call，才配得上 90 Hz。</span>

一张 90 Hz 头显的典型预算表，能帮你在剖析时定位问题：

| 环节 | 理想占比 | 超标时的手感 |
| --- | --- | --- |
| 场景几何 + 光照 | 约占 40–50% | 掉帧、画面撕裂 |
| 后处理 / 特效 | 约占 15–25% | 时延升高、重影 |
| CPU 逻辑（物理/AI/网络） | 约占 20% | 卡顿、交互迟滞 |
| 资源加载 / 内存 | 稳定即可 | 卡顿、黑屏闪断 |

**资产管线（asset pipeline）**是另一大隐性工程：建模软件导出的高精度网格动辄数百万三角形，必须**减面（decimation）**到几万以内才能在移动头显上跑；贴图要压缩（ASTC 等）、材质要统一（避免每物体一个材质球）。很多项目 60% 的优化工作发生在「资产进引擎之前」——这也是为什么团队里要有专门的 TA（技术美术）岗位，负责「把漂亮的艺术转成能跑的资产」。

**构建与多端发布**：一套工程要能构建到 Quest（Android/APK）、PC VR（Windows）甚至 WebXR（浏览器），关键是**平台抽象**——输入用 OpenXR 动作、渲染用通用管线、资源按平台做变体。CI/CD 自动构建是团队标配，否则每次手动改构建配置都容易出错。

**调试的独特难点**：XR 里「戴上头显就看不到日志」。工程上的解法是**运行时可视化调试**——在虚拟空间里放「调试面板」（实时显示位姿、FOV、帧率），以及**日志回放**（把一次会话的输入流录下来，离线复现 bug）。**异步时间扭曲的副作用调试**（ATW 导致画面「鬼影」）尤其难定位，往往要一台高速相机同步录制才能还原真相。

**测试与人体因素**：XR 测试不能只看「能跑」，还要看**晕不晕、累不累**——这正是《移动与导航技术》里 SSQ 问卷的用途。团队里要有「易晕测试员」专门负责在各种移动方案下试玩，把「开发者觉得舒服」和「用户觉得舒服」之间的鸿沟补上。

**自动化测试在 XR 里的困境**：传统游戏的单元测试能覆盖逻辑，但「头显视角下这帧画面对不对」几乎无法自动化——于是业界用「黄金帧对比 + 手动走查 + 录回放」三件套：每改一次渲染，自动抓取指定场景的截图与基线对比；交互流程由真人走查；bug 复现靠「输入流录放」而不是让测试员反复戴头显。XR 测试的质量，往往取决于这个「录回放」基础设施做得多好。

## 6 核心对比表：引擎与工具链

| 维度 | Unity | Unreal | WebXR |
| --- | --- | --- | --- |
| 语言 | C# | C++ / 蓝图 | JavaScript |
| 画面上限 | 高 | 极高（Nanite/Lumen） | 中 |
| XR 接口 | XR Management + 插件 | XR 插件 / 模板 | WebXR API |
| 上手门槛 | 低 | 中高 | 最低 |
| 性能 | 高 | 高 | 受浏览器限制 |
| 典型场景 | Quest 游戏、企业应用 | 电影级演示、高端项目 | 原型、教学、展厅、分享 |
| 优势 | 生态大、组件全、多端 | 画质天花板、蓝图可视化 | 零安装、免分发、跨平台 |

三行之外还有一个共同的底层：**它们最终都生成「OpenXR 兼容的二进制 + 头显运行时」**——无论走哪条路，工程交付物都要经过同一条 OpenXR 抽象层落到具体设备。这也是为什么「懂 OpenXR 的概念」比「会某个引擎的按钮」更值钱：工具会换代，抽象层的理念不会。

## 7 小结

- 引擎 = XR 开发的**操作系统**，把渲染、物理、输入、资源全部打包成配置项。
- **Unity**（C#、XR Interaction Toolkit）生态最大、上手快；**Unreal**（C++/蓝图、Nanite/Lumen）画质天花板。
- **OpenXR**（2019，Khronos）终结 SDK 碎片化：空间、动作、帧循环三大抽象让「一套代码多设备」。
- **WebXR** 把 XR 搬进浏览器，零安装、免分发，适合原型、教学与展厅。
- 选型法则：**快速多端选 Unity，极致画质选 Unreal，轻量分享选 WebXR**；底层全走 OpenXR。
- 引擎再方便，也要能读引擎的文档定位「注视点渲染」「平面检测」「HRTF」这些原理的开关——原理不牢，工具是黑盒。
- 工程实践三件套：**性能剖析（逐帧找瓶颈）、资产管线（进引擎前减面压缩）、录放回放测试**。
- 工具链分层：**运行时 → OpenXR → 引擎 → 内容**，越上层越通用、越接近产品。
- 生态资产（Asset Store / Fab）大幅降低内容成本，也带来同质化风险。
- 测试要覆盖**多设备矩阵 + 录回放**，尤其不能只测「开发者觉得舒服」的设备。

在下一节，我们将进入 XR 最迷人的应用——**化身与社交 VR**：avatar 具身感、多用户同步与网络时延补偿，看虚拟世界如何「住进两个人」。
