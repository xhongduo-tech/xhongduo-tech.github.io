## 为什么光照成了瓶颈

实时渲染的光照公式（Blinn-Phong / PBR）本身不贵，但「**每个片元 × 每个光源**」的组合爆炸：一帧有百万片元 × 几百个光源 = 上亿次光照计算。**前向渲染（forward rendering）** 对每个片元遍历所有光源，光源一多就超预算。**延迟渲染（deferred rendering）** 换个思路：**先把几何存进 G-Buffer，再统一做光照**——光源多了也不怕。<span class="marginnote">前向渲染的瓶颈是「<strong>片元 × 光源</strong>」：每个片元着色时都要遍历所有光源——光源数线性增加成本。延迟渲染的解法是「<strong>解耦几何与光照</strong>」：第一阶段只写几何属性（位置、法线、颜色）到 G-Buffer，第二阶段对每个光源只处理「它影响的屏幕区域」——光源数不再乘到所有片元上。</span>

本节对比前向与延迟两条管线，讲清它们的结构差异、各自优劣与适用场景。

## 1 前向渲染：边画边照亮

**前向渲染** 是经典管线：每个片元在片元着色器里「一次算完」——取材质、遍历光源、算光照、输出颜色。

```text
// 前向渲染：片元着色器逐光源累加
for (mesh : scene)
    for (fragment : rasterize(mesh))
        vec3 color = vec3(0.0);
        for (light : scene.lights)          // 片元 × 光源
            color += shade(fragment, light);
        fragment.color = color;             // 一次写入帧缓冲
```

**优势**：简单、内存占用小、天然支持 MSAA、透明排序直观。**劣势**：片元 × 光源的复杂度——光源一多（几十上百），每个片元都要遍历所有光源，成本爆炸。<span class="marginnote">前向渲染的「乘法」困境：<strong>片元数（百万）× 光源数（上百）= 上亿次光照求值</strong>——即使每次求值很便宜，总量也扛不住。前向渲染的优化手段是「光源剔除」（只算影响该物体的光源）与「分块」（tiled），但本质仍是「每片元 × 每光源」的结构。</span>

## 2 延迟渲染：先 G-Buffer 再光照

**延迟渲染** 把光照推迟，分两个阶段：

**G-Buffer 阶段**：不照亮，只把几何信息写进多张缓冲（G-Buffer）：

位置（或深度）
法线
漫反射颜色（albedo）
材质参数（金属度、粗糙度）
其他（AO、发光）

**光照阶段**：读 G-Buffer，对每个像素做光照——**每个光源只需要处理屏幕上一个区域**（光源投影到屏幕的包围盒），而不必遍历全部片元。

```text
// 延迟渲染两阶段
// Pass 1：G-Buffer 阶段——只写几何，不算光照
for (mesh : scene)
    for (fragment : rasterize(mesh))
        gbuffer.position = fragment.position;
        gbuffer.normal   = fragment.normal;
        gbuffer.albedo   = fragment.albedo;
        gbuffer.material = vec2(fragment.metalness, fragment.roughness);

// Pass 2：光照阶段——读 G-Buffer，每个光源只处理其屏幕区域
for (light : scene.lights)
    for (pixel : light.screen_bounds)       // 光源投影的包围盒
        g = load_gbuffer(pixel);
        pixel.color += shade(g, light);
```

光源数不再乘到所有片元——**延迟渲染能同时处理成百上千个光源**。<span class="marginnote">「延迟」的含义：<strong>把「光照」从「几何渲染时」推迟到「几何渲染后」——先攒货（G-Buffer），再统一照灯</strong>。光照阶段的每个光源只处理「它影响的屏幕区域」，光源之间的计算解耦。这让光源数从「乘到全部片元」变成「加在屏幕上」——几十上百个动态光源的实时场景，只有延迟渲染扛得住。</span>

## 3 G-Buffer 的内存与带宽

延迟渲染的代价在**存储与带宽**：G-Buffer 多张全屏缓冲，每帧写入 + 读取：

常见配置：位置（16 位浮点 RGBA）、法线（16 位 RG）、albedo（8 位 RGB）、材质（8 位 RG）等——总计约 100+ 字节/像素。
1080p 下 G-Buffer 约几十 MB，带宽压力大。
现代实现用「压缩 G-Buffer」（减少缓冲张数、降低位宽）缓解。

「多存一次」换「光源自由」——延迟渲染是典型的「空间/带宽换时间」交易。<span class="marginnote">G-Buffer 的带宽是延迟渲染的头号成本：<strong>每帧要写一次、读多次全屏缓冲，1080p 的 G-Buffer 数据量约几十 MB——在移动端/带宽受限平台上，这个成本可能吃掉一半预算</strong>。现代引擎用「紧凑 G-Buffer」（位置从深度重建、法线用八面体编码、材质参数打包）把带宽压到最低。</span>

## 4 延迟渲染的三个经典难题

延迟渲染解决了「光源数」，却引入新问题：

**难题一：无法硬件 MSAA**。G-Buffer 阶段不照亮，MSAA 在几何阶段用子采样点写 G-Buffer，光照阶段却按像素算——子采样信息丢失，MSAA 失效。解法：TAA（时间抗锯齿）、FXAA 等后处理反走样。

**难题二：透明物体**。G-Buffer 只能存「最近的表面」，无法存「半透明物体的多层信息」。解法：透明物体**退回前向渲染**（延迟 + 前向混合，deferred + forward 透明 pass）。

**难题三：带宽压力**。多张全屏缓冲的读写，带宽敏感平台吃力。<span class="marginnote">「延迟渲染的三个坑」是它不完美的证据：<strong>MSAA 失效（几何阶段子采样在光照阶段对不上）、透明物体要回退前向、G-Buffer 带宽大</strong>。现代引擎因此常用「混合」——不透明物体走延迟、透明物体走前向、反走样用 TAA——「<strong>没有银弹，只有组合</strong>」再次应验。</span>

## 5 前向 vs 延迟：对比与选型

| | 前向渲染 | 延迟渲染 |
| --- | --- | --- |
| 光照时机 | 片元着色时 | 推迟到 G-Buffer 后 |
| 光源数 | 少（十几个） | 多（成百上千） |
| 内存/带宽 | 低 | 高（G-Buffer） |
| MSAA | 支持 | 不支持（用 TAA） |
| 透明物体 | 天然 | 要回退前向 |
| 适用 | 移动端、光源少 | 桌面、光源密集 |

**选型规律**：光源少、平台带宽有限（移动端）用前向；光源密集、追求质量（桌面/主机）用延迟；现代引擎常用「前向 + 延迟」混合。<span class="marginnote">「前向省带宽、延迟省光源」是选型的天平：<strong>移动端 GPU 带宽稀缺、场景光源少 → 前向胜出（省带宽、可 MSAA）；桌面 GPU 带宽充裕、场景光源密 → 延迟胜出（光源自由、质量高）</strong>。现代引擎（UE、Unity）按平台/场景自适应切换，或做「分块前向」（tiled forward）——用计算着色器对屏幕分块剔除光源，让前向也能扛多光源。</span>

## 6 延迟渲染与后处理的衔接

延迟渲染还有一个隐藏优势：**G-Buffer 是后处理的「免费原料」**：

SSAO/HBAO 直接读 G-Buffer 的深度 + 法线（上一节）。
延迟光照在 G-Buffer 上做，可以在光照时访问法线/深度做各种效果。
屏幕空间效果（SSR、SSGI）都建立在 G-Buffer 之上。

G-Buffer 让「屏幕空间技术」有了统一的数据来源——这是延迟渲染对现代渲染的更大贡献。<span class="marginnote">「G-Buffer 是屏幕空间技术的粮仓」：<strong>SSAO 读深度法线、SSR 读位置法线颜色、SSGI 读全 G-Buffer——延迟渲染产出的 G-Buffer 让一大批「屏幕空间」效果（上一节 AO、后面的实时 GI 近似）有了现成的几何数据</strong>。这也是为什么现代引擎哪怕不「延迟」，也常保留一个「类似 G-Buffer」的缓冲来喂后处理。</span>

## 6 延迟渲染的扩展：Tile-based Deferred 与混合方案

延迟渲染不是终点，工程上它还有「进阶形态」——理解这些扩展，你就知道「现代引擎怎么用延迟」。

**分块延迟（Tile-based Deferred）**：把屏幕切成小块（tile），每块的光源列表「剔除」到「只影响该块的光源」：

- 每块用一个「光源索引列表」——像素光照时只遍历「影响自己块」的光源。
- 光源从「全屏遍历」变成「块内遍历」——上千光源也能实时。

**延迟光照（Deferred Lighting）**：不完全存 G-Buffer，而是「先算光照再存」——把光照结果 + 材质参数分开存，减少 G-Buffer 带宽。变体很多，目标都是「省带宽」。

**混合方案（Forward+ / Deferred + Forward）**：

- **不透明物体**：走延迟（多光源友好）。
- **透明物体**：走前向（延迟存不了多层透明）。
- **Forward+**：前向 + 分块光源剔除——「前向的简单 + 延迟的光源数」——移动端流行。

**辨析｜易错点：** 两个工程坑：

1. **「延迟 = 万能」**——延迟在透明、MSAA、带宽上有硬伤——「延迟 + 前向混合」是主流，纯延迟少见。
2. **「G-Buffer 越全越好」**——G-Buffer 张数越多带宽越大——「够用的 G-Buffer」（位置从深度重建、法线压缩）是现代设计。

**「延迟渲染的工程 = 分块剔除 + 混合管线 + G-Buffer 压缩」**——理解了扩展，你就知道「为什么现代引擎的渲染器是『延迟为主、前向补充』的混合体」。

## 7 小结

- **前向渲染**：边画边照亮，片元 × 光源——光源一多就爆炸；省带宽、支持 MSAA。
- **延迟渲染**：先写 G-Buffer、后统一光照——光源自由，但 G-Buffer 带宽大。
- G-Buffer 存位置/法线/颜色/材质，光照阶段每个光源只处理屏幕局部区域。
- 三大难题：MSAA 失效、透明物体回退前向、带宽压力。
- 选型：移动端前向、桌面延迟、现代引擎混合；G-Buffer 是屏幕空间技术的粮仓。
