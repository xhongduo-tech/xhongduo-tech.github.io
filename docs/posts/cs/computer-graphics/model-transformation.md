## 为什么需要模型变换

我们手里有一堆三维模型：茶壶、坦克、角色。每个模型在它的**局部坐标系（object / model space）**里定义——原点在模型中心，坐标轴跟着模型走。但场景里有十几个模型，各自有不同的位置、朝向、大小，必须把它们**统一摆进同一个世界坐标系**。<span class="marginnote">局部坐标的意义是「建模时不关心位置」：茶壶的壶嘴在 $(0.3, 0.5, 0)$ 是固定的，至于这个点在世界里在哪里，由模型变换说了算。这让同一份模型数据可以被复制、缩放、旋转后任意摆放。</span>

**模型变换（model transformation）** 就是「局部 → 世界」这一步：用一个 $4 \times 4$ 矩阵 $M$，把每个顶点从模型自己的坐标系搬到世界坐标系。它是渲染管线里第一个被施加到顶点上的矩阵。

## 1 模型变换的三件套：S-R-T

把「局部 → 世界」拆成三个有直觉的操作：先缩放、再旋转、最后平移。写作：

$$
\mathbf{M} = \mathbf{T}\;\mathbf{R}\;\mathbf{S}
$$

从右往左读：先缩放（模型自身大小）→ 旋转（摆朝向）→ 平移（放位置）。<span class="marginnote">S-R-T 顺序为什么是行业惯例？因为它符合「由内向外」的思考方式：模型先在自己身体上缩放，再被旋转成世界朝向，最后被搬到世界坐标里的某个位置。若顺序颠倒，「平移后再缩放」会让位置也跟着被放大。</span>

设模型中心在局部原点，那么：

- **缩放 $\mathbf{S}(s_x, s_y, s_z)$**：把模型放大到期望尺寸。可能均匀（一个角色大一号）也可能非均匀（一辆车被压扁成轿车）。
- **旋转 $\mathbf{R}$**：通常是三个坐标轴旋转的复合（欧拉角）或四元数，决定模型朝向哪。
- **平移 $\mathbf{T}(t_x, t_y, t_z)$**：把模型放到世界坐标 $(t_x, t_y, t_z)$。

复合后，模型上任意一点 $v_{\text{local}}$ 的世界坐标是：

$$
v_{\text{world}} = \mathbf{T}\mathbf{R}\mathbf{S}\; v_{\text{local}}
$$

## 2 为什么拆成 S-R-T 而不是直接给一个矩阵

你可能问：直接手工写一个 $4 \times 4$ 矩阵不也能把模型摆好？为什么要拆成三件套？理由有三：

- **可理解性**：缩放值、旋转角、平移量是「人话」，一个 16 个数组成的矩阵是「天书」。拆开后动画师调整一个旋转角即可，不必重写矩阵。
- **可移植性**：同一个模型可以在不同位置用「相同的缩放、不同的平移」复用；旋转可以随时间插值（旋转矩阵插值难，但旋转角可以）。<span class="marginnote">旋转随时间变化时，用欧拉角/四元数插值都比直接插值矩阵自然得多——矩阵的 9 个旋转元素并非独立自由，逐元素插值会得到「既不旋转也不缩放」的畸变矩阵。</span>
- **层级复用的地基**：模型变换常常不是单层——一个机械臂的每个关节都有自己的 S-R-T，外层关节的变换要复合内层关节的变换。把每层拆成 S-R-T，层级复合才有清晰的递归结构。

## 3 模型变换与坐标系嵌套

真实场景几乎都是嵌套的：坦克在战场上有自己的位置，炮塔相对坦克车体旋转，炮管相对炮塔俯仰。这就是**层级变换（hierarchical transformation）**：

$$
v_{\text{world}} = \mathbf{M}_{\text{tank}}\,\mathbf{M}_{\text{turret}}\,\mathbf{M}_{\text{barrel}}\; v_{\text{barrel-local}}
$$

每个子部件先在自己的局部系里定义，再经过「祖先链」一路变换到世界。<span class="marginnote">这段链条在图形学 API 里表现为变换栈（transform stack）或场景图（scene graph）：每个节点存一个「相对父节点的局部变换」，世界变换 = 父链上所有局部变换连乘。现代引擎普遍用这种树结构组织场景。</span>

层级变换最重要的性质：**修改祖先的变换，会带动所有后代一起动**。转动炮塔，炮管跟着转；移动坦克，炮塔炮管都跟着走——这正是「局部」与「世界」的相对性在工程上的体现。

## 4 公式解析：把局部点送进世界坐标系

以「缩放到 2 倍、绕 y 轴转 90°、平移到 (3, 0, 5)」为例，复合矩阵展开为：

$$
\mathbf{M} = \mathbf{T}(3,0,5)\;\mathbf{R}_y(90^\circ)\;\mathbf{S}(2,2,2)
$$

代入一个局部点 $v = (1, 0, 0)^\top$，逐步追踪：

- **第一步，缩放**：$\mathbf{S}(2,2,2)\,v = (2, 0, 0)^\top$。模型点被放大到 2 倍。
- **第二步，旋转**：$\mathbf{R}_y(90^\circ)\,(2,0,0)^\top$。绕 $y$ 轴转 90°，$x$ 轴指向 $z$ 负方向，得 $(0, 0, -2)^\top$。
- **第三步，平移**：$\mathbf{T}(3,0,5)\,(0,0,-2)^\top = (3, 0, 3)^\top$。加上平移量，落到世界坐标 $(3, 0, 3)$。

**辨析｜易错点：** 三个最常见的模型变换错误，全部来自「顺序」：

1. **平移放最右**：写成 $\mathbf{S}\mathbf{R}\mathbf{T}$，模型先被平移再被旋转，结果「位置也被旋转」——模型绕世界原点转而非绕自身中心转。
2. **非均匀缩放与旋转混用**：先旋转再非均匀缩放，会把「旋转后的模型」压扁到缩放轴上，造成模型扭曲；若想沿模型自身轴缩放，必须先缩放再旋转。
3. **忘记处理法线**：模型矩阵作用于法线会破坏垂直性（非均匀缩放时尤其严重），法线需要用法线变换（$\mathbf{M}^{-T}$），这在《凹凸贴图》一节展开。

## 5 模型变换的逆：世界 → 局部

渲染管线里不仅需要「局部 → 世界」，也需要反向：「世界 → 局部」。例如要把一个世界坐标里的光源位置换算到模型局部系，以便做光照计算。逆变换就是：

$$
\mathbf{M}^{-1} = \mathbf{S}^{-1}\,\mathbf{R}^{-1}\,\mathbf{T}^{-1} = \mathbf{S}(1/s_x,1/s_y,1/s_z)\;\mathbf{R}^\top\;\mathbf{T}(-t_x,-t_y,-t_z)
$$

注意逆矩阵的顺序也反转了：先抵消平移、再旋转还原、最后缩放置原。<span class="marginnote">逆变换的「顺序反转」是矩阵代数与直觉的又一次碰撞：穿衣服是先穿内衣再穿外套，脱衣服则要先脱外套再脱内衣——复合变换的逆就是反序取逆。</span>在许多场合（拾取、投影变换、逆向渲染）「世界 → 局部」与「局部 → 世界」成对出现，理解逆变换等于再理解一遍模型变换。

## 6 模型变换的工程实践：层级与场景图

模型变换在真实引擎里几乎总是「层级」的——把工程形态展开，看「一个模型怎么被放进世界」。

**场景图（scene graph）**：引擎用一棵树组织场景，每个节点有「相对父节点的局部变换」：

```
世界
 └─ 坦克（位置、朝向）
     ├─ 炮塔（相对车体旋转）
     │   └─ 炮管（相对炮塔俯仰）
     └─ 履带（滚动动画）
```

- 每个节点的世界变换 = 从根到它的局部变换连乘。
- **移动坦克 → 炮塔、炮管、履带全跟着动**——层级变换的「改父动子」。

**引擎里的 Transform 组件**：现代引擎（Unity/UE）把「位置 + 旋转 + 缩放」打包成 Transform，默认就是「父子的相对值」：

```
Transform world = parent.world * local
local = T(位置) * R(旋转) * S(缩放)
```

**为什么「局部 + 世界」双份**：局部值让「编辑方便」（炮管转 30° 是局部旋转），世界值让「渲染直接」（顶点乘世界矩阵）——「编辑用局部、渲染用世界」是标准分工。

**辨析｜易错点：** 三个工程坑：

1. **Transform 的缩放「污染」子节点**——父节点非均匀缩放，子节点的旋转/位置被「拉伸」——「非均匀缩放 + 旋转层级」是场景图的经典 bug（子物体「变形」）。
2. **世界变换的缓存失效**——改了父节点，所有后代的「世界缓存」要重算——「脏标记 + 惰性更新」是标准实现。
3. **层级深度的浮点误差**——深层节点连乘累积误差，远处物体「抖动」——用「世界锚点」或「双精度」缓解。

**模型变换是「场景组织的数学」**——理解了 S-R-T 与层级连乘，你就知道「引擎的场景图在算什么东西」。

## 7 小结

- **模型变换 = 缩放 × 旋转 × 平移（S-R-T）**，把顶点从局部系搬进世界系。
- 复合顺序从右往左：**先缩放、再旋转、最后平移**，顺序错误是头号 bug。
- 场景是**层级嵌套**的：世界变换 = 祖先链上各局部变换连乘，改父动子。
- 逆变换 $\mathbf{M}^{-1}$ 反序取逆，用于「世界 → 局部」的换算。
