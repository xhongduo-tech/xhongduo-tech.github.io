## 为什么从 LLMOps 开始

前七节讲的 MLOps 是为「自训模型」设计的：自己准备数据、自己训练、自己部署。而大模型时代带来了完全不同的形态——**基础模型（foundation model）** 由少数大厂预训练好，大多数团队**不训练模型，只调用模型**。于是「运维一个模型」变成了「运维模型周围的一圈系统」：提示词、评估、护栏、上下文工程。这套围绕大模型应用的全生命周期工程实践，就是 **LLMOps（LLM Operations）**。它不是 MLOps 的替代品，而是 MLOps 在大模型语境下的新分支：训练环节大幅收缩，评估与安全的权重前所未有地上升。<span class="marginnote">一句话定位：MLOps 管理「模型的诞生与服役」，LLMOps 管理「模型的使用与约束」。对绝大多数团队，后者是日常，前者是偶尔。</span>

LLMOps 还有一个与传统 MLOps 截然不同的特点：**「模型」本身不可控，但「行为」必须可控**。传统 MLOps 里你拥有权重，可以任意改造；LLMOps 里大多数团队只是基础模型的使用者，改不了权重，只能通过提示、上下文、护栏与评估去「驯化」它。这带来一种新的工程心态：**不追求「让模型永远正确」，而是追求「让模型出错时可发现、可拦截、可回退」**。这个心态会贯穿本节与下一节。

## 1 提示管理：提示词是「新的代码」

在小模型时代，产品逻辑写在代码里；在大模型时代，大量产品逻辑写在了**提示词（prompt）**里。提示词决定模型的角色、任务、输出格式与行为边界，因此它必须像代码一样被管理：

**提示即版本**。一句提示词的改动，可能让输出质量大幅变化。所以提示词要进版本库、可 diff、可回滚、可追溯——每一条线上提示词都要能回答「是谁、在何时、为什么改成这样」。

**提示即模板**。生产环境的提示词几乎从不是一条静态文本，而是「模板 + 变量」：`<system>` 定义角色，`<user>` 填充用户输入，业务字段、检索结果（RAG）、历史对话作为变量注入。模板与渲染逻辑分离，测试时才不会把「变量格式错误」误判成「模型变笨」。

**提示注册表（prompt registry）**：集中管理所有提示词的版本、上线状态（dev/staging/prod）、与模型的绑定关系（哪个提示词配哪个模型版本）。它与 MLflow Model Registry 同构——**提示词就是 LLMOps 里的「模型」**。<span class="marginnote">业界已有配套工具（如 LangSmith、PromptLayer），原理都和模型注册表一致：版本、阶段流转、审计日志。把「提示词」当一等公民管理，是 LLMOps 区别于 MLOps 最直观的一点。</span>

**辨析｜易错点：** 常见错误是把提示词「写死在产品代码里」。一旦要 A/B 测试两个提示词、或紧急回滚上一版提示词，写死版本只能改代码重新发版，发布周期以小时计。正确做法是**提示词与代码解耦**，存注册表、运行时拉取，改提示词像改配置一样分钟级生效。

## 2 评估体系：没有真值，怎么知道模型好不好

传统 ML 有明确的标签与离线指标（精度、召回）。LLM 的生成式输出**没有唯一正确答案**，评估因此成了 LLMOps 最核心也最难的工程。一套成熟的评估体系分三层：

**基准集（golden set）评估**：人工构造一批「输入 → 期望行为」的高质量样例（几十到几百条），每次提示词或模型变更后，在这套基准集上跑一遍，看「通过率」是否变化。这是最低成本、最稳定的回归防线——它的价值不是精确，而是**快速发现退化**。<span class="marginnote">基准集要随业务演进持续扩充：每次线上翻车的 case 都应沉淀进基准集，让它越来越难、越来越代表真实世界。业界把这套机制叫「回归防护网」。</span>

**模型即裁判（LLM-as-judge）**：用一个大模型去评价另一个模型/应用的输出，按打分标准（相关性、忠实度、有害性等）给出分数或比较。成本低、可规模化，但**有偏**——裁判模型有自己的偏好，需抽样人工复核对齐。

**在线评估（online eval）**：A/B 测试、真实用户反馈、延迟与成本监控。离线评估再全，也要在线数据验证「真实世界里到底行不行」。

## 3 公式解析：评估的双闸门——均值要达标，最差不能崩

LLM 评估最容易被一个现象误导：**平均分很高，但个别 case 灾难性失败**——比如客服助手平均分 8.5 分，却对某类敏感问题给出了危险回复。所以生产级门禁必须是「双闸门」：

$$
\text{EvalScore} = \frac{1}{N} \sum_{i=1}^{N} s_i , \qquad
\text{通过条件：} \text{EvalScore} \geq \theta \ \text{且} \ \min_{i} s_i \geq \epsilon
$$

逐项拆解：

- **第一步，明确 $s_i$**：$s_i$ 是基准集中第 $i$ 条用例的评估得分（可来自人工、LLM-as-judge 或二者加权），取值范围统一到 $[0, 1]$ 或 $[0, 10]$。
- **第二步，看懂均值闸 $\theta$**：$\text{EvalScore} \geq \theta$ 保证整体质量不低于门槛。它衡量「平均水平」。
- **第三步，看懂最低分闸 $\epsilon$**：$\min_i s_i \geq \epsilon$ 保证**最差的一条用例也不能崩**。它衡量「最坏情况」，专治「高平均掩盖低尾」。
- **第四步，体会两道闸的分工**：均值闸是「够不够好」，最低分闸是「安不安全」。对客服、医疗、金融这类高风险场景，$\epsilon$ 往往比 $\theta$ 更重要——一次灾难性输出足以毁掉整个产品的信任。<span class="marginnote">「最差不能崩」在安全语境下的具体化：即使基准集整体通过，若任何一条触发「有害内容」「隐私泄露」「越权」类用例得分过低，门禁必须一票否决。安全类用例应单独分组、单独设最低分阈值。</span>

## 4 安全护栏：模型的「安全带」

大模型会「发挥」出不受控的输出：生成有害内容、泄露提示词中的敏感信息、被越狱提示（jailbreak）诱导、产生幻觉冒充事实。**安全护栏（guardrails）** 是加在模型前后的规则层，分两道：

**输入护栏（input guardrails）**：在提示词进入模型前拦截。包括 **PII 脱敏**（识别并掩码手机号、身份证、邮箱）、**越狱检测**（识别对抗性提示模式）、**话题/权限过滤**（超出业务允许范围的请求直接拒绝）、**上下文长度与成本控制**。

**输出护栏（output guardrails）**：在模型输出返回用户前校验。包括 **内容审核**（涉黄暴恐、仇恨言论）、**格式校验**（要求 JSON 就必须能 parse）、**事实性检查**（对高风险声明引用原文比对）、**敏感信息复现检测**（防止模型吐回训练数据里的隐私）。<span class="marginnote">护栏要「可编排、可回退」：两条输入规则 + 三条输出规则组成一个流水线，像 CI/CD 里的质量门禁一样可单独启停、可版本化。生产事故往往是「某条护栏被临时关掉后忘了开」——护栏的启停必须留审计日志。</span>

**辨析｜易错点：** 两个极端都常见。一个是**「裸奔」**——相信模型内置的安全对齐就够，不做任何外部护栏；另一个是**「过度过滤」**——护栏规则过严，把正常业务请求也拦掉，产品体验大幅受损。正确姿态是**分层防御**：模型的内部对齐是底座，外部护栏是保险丝，而「护栏误伤率」本身也要进监控指标。

## 5 核心对比表：MLOps 与 LLMOps

本主题以体系对比为主，用核心对比表替代额外公式解析。

| 维度 | MLOps（自训模型） | LLMOps（基础模型应用） |
| --- | --- | --- |
| 核心资产 | 数据集、模型权重 | 提示词、上下文、评估集、护栏 |
| 训练环节 | 核心工作流 | 基本外包（微调是可选增强） |
| 主要风险 | 数据漂移、模型退化 | 幻觉、越狱、隐私泄露、不可控生成 |
| 版本管理对象 | 代码 + 数据 + 权重 | 提示词 + 模型版本 + 评估集 + 护栏 |
| 评估方式 | 离线标签 + 在线指标 | 基准集 + LLM-as-judge + 在线反馈 |
| 发布粒度 | 模型版本晋升 | 提示词/配置变更即可发布 |

**辨析｜易错点：** 一个系统性误判是「把传统 MLOps 的流程原样套到 LLMOps」——没有标签、没有离线指标、发布主体是提示词而非模型，生搬硬套会导致评估无处下手、门禁形同虚设。反过来，也不要把 LLMOps 当成「只要调 API 就万事大吉」——**评估与护栏不建，模型越强，翻车的破坏力越大**。

## 6 LLM 应用的可观测性：看不见模型，也要看得见行为

LLM 应用是「黑箱里的黑箱」：你调用的是别人训练好的模型，连它的内部状态都看不到。可观测性因此成了 LLMOps 的刚需，至少要记录四类信息：

**第一，输入输出全链路日志**：系统提示词、用户输入、检索到的上下文、模型输出、护栏拦截结果，一次不落地记录。出问题时，能回放「当时模型看到了什么、说出了什么、为什么被拦」。

**第二，成本与延迟的逐请求追踪**：每次调用记录 token 用量（输入/输出）、模型版本、延迟。token 用量直接对应账单，延迟直接对应体验——这两项是 LLM 应用「看不见模型」时少数能硬度量的东西。<span class="marginnote">成本追踪在 LLMOps 里的地位被显著抬高：LLM 按 token 计费，一个「上下文越塞越长的 RAG 应用」可能悄悄把单次成本翻几倍。把「每请求 token 成本」画成时序图，是 LLM 应用成本治理的第一步。</span>

**第三，护栏拦截统计**：输入护栏拦了多少、输出护栏拦了多少、各是哪种类型（PII、越狱、有害内容）。拦截率的异常波动，往往预示着新攻击模式或误伤业务。

**第四，质量抽检与反馈回路**：对输出做抽样人工评估或 LLM-as-judge 评估，把「质量分数」也当成时序指标盯。质量下滑趋势，通常先于用户投诉出现。

**辨析｜易错点：** LLM 日志里几乎必然包含敏感信息（用户输入可能含手机号、身份证）。所以 LLM 可观测性从第一天就要做**日志脱敏**——记录时把 PII 掩码，需要时再按审计流程解明。否则「为了监控而记录的日志」本身就成了隐私事故源。

## 8 小结

- **LLMOps** 是大模型应用的全生命周期工程实践：不训练模型，而是运维「模型 + 提示 + 评估 + 护栏」一圈系统。
- **提示词是新的代码**：要进版本库、走注册表、与代码解耦，改动分钟级生效。
- 评估分三层：**基准集（回归防线）→ LLM-as-judge（规模化）→ 在线评估（真实验证）**。
- 发布门禁要**双闸门**：均值达标 $\text{EvalScore} \geq \theta$ 且最差不崩 $\min s_i \geq \epsilon$
