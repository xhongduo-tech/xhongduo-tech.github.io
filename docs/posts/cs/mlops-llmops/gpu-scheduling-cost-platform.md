## 为什么从 GPU 调度与平台选型开始

前九节讲的全是「怎么把模型工程化地做出来、发出去、盯起来」，但一切模型都要落在算力上，而 GPU 是机器学习流水线里**最贵、最稀缺、最难共享**的资源。一个团队可以容忍代码丑一点、流程糙一点，却无法容忍 GPU 利用率只有 20%——那是真金白银在空转。本节的三个问题层层递进：**怎么把 GPU 高效地分出去（调度）？怎么把每一分钱花在刀刃上（成本）？这些能力是自建还是买托管（平台选型）？** 答好这三个问题，MLOps 的「成本与治理」闭环才算真正合拢。<span class="marginnote">MLOps 讲到最后会收敛到经济学：一切自动化（CI/CD、监控、重训）本质上都是在用「工程投入」换「GPU 与人工的节省」。算不清这笔账，工具堆得越多越亏。</span>

本节还承接一个更宏观的问题：**MLOps 平台建设的节奏**。很多团队在「什么都没有」时就想一步到位搭 Kubeflow、买托管平台，结果陷入工具泥潭。正确的节奏是「**按需演进**」：先在笔记本上跑通实验，再补数据版本与实验跟踪，再上流水线，最后才谈集群调度与平台——每一步都等「痛点真实出现」再动手。GPU 调度与平台选型是这个演进链的最后一环，也是成本最大的一环，所以更要把前面的工程基础打好再上马。

## 1 GPU 为什么难调度

传统 CPU 任务在容器编排里很好处理：容器按需启停，节点共享内存。GPU 却带来三重约束：

**第一，稀缺与独占**。GPU 是硬件卡，一张卡通常被一个训练任务独占（或按卡粒度划分），不能像 CPU 那样细粒度分时共享。

**第二，资源「排他性强」**。训练任务需要「整组 GPU + 高速互联」——8 卡训练需要 8 张卡在同一节点或同一机架内，网络拓扑决定了「能用哪几张卡」。调度器不能只看「有空卡」，还要看「卡与卡之间是否连得起来」。

**第三，排队与优先级**。GPU 不够用时，任务要排队。谁先跑？预训练大任务优先还是在线小任务优先？这需要**队列与优先级机制**，而默认的 Kubernetes 调度器并不擅长这些。<span class="marginnote">GPU 调度的本质是「多目标优化」：最大化利用率、最小化排队、兼顾优先级与公平性（fairness）。纯手写调度很难兼顾，所以社区出现了专门为 ML 设计的调度器，如 Kueue 与 Volcano。</span>

## 2 Kubernetes 上的 ML 调度：Kueue 与 Volcano

Kubernetes 是事实上的 ML 资源底座，但它原生调度面向「微服务」而非「训练任务」。两个项目补上了这层能力：

**Kueue**（云原生计算基金会项目）：引入 **队列（queue）** 概念。训练任务不是直接提交到集群，而是**排进队列**，由队列策略决定何时、以什么资源配额放行。Kueue 支持按租户/团队划分配额、任务抢占（高优先级挤掉低优先级）、以及「排队等待」与「真正运行」的分离——**排队不占资源，运行才占**。

**Volcano**（华为云开源）：为高性能计算场景设计，支持**批量调度**（同时为一批任务找到资源，一起启动）、**gang scheduling**（整组任务要么一起被调度、要么一起等待，解决「8 卡训练少 1 卡就全卡住」的问题）、以及**资源抢占与回收**。<span class="marginnote">「gang scheduling」解决的是分布式训练的经典死局：8 个 worker 都就绪才能开始，若调度器只分到 7 张卡就启动，第 8 个 worker 永远在等，7 张卡反而被占用。先凑齐一组再一起放行，是训练型调度的标配。</span>

**工程要点**：调度策略要「分层」——Kubernetes 管容器与节点，Kueue/Volcano 管训练任务队列，上层 CI/CD 只管「把任务交给队列」。调度与流水线解耦后，训练团队可以「提交即走」，不用自己盯着资源。

## 3 成本优化的四条杠杆

GPU 成本优化的核心是「提高有效利用率」——让每张卡真正在算、在算有用的东西。四条杠杆按性价比排序：

**第一条，占位实例（spot/preemptible instances）**。云厂商的闲置 GPU 通常以 3–7 折出售，但可被随时回收。适配策略：可容错的任务（批量推理、可断点续训的预训练）优先用占位实例；在线服务与不可中断的关键训练用按需实例。<span class="marginnote">「可断点续训」是占位实例能省钱的前提——训练脚本要支持周期 checkpoint，实例被回收后从最近检查点恢复，损失最多一个 checkpoint 间隔的算力。没有断点续训就盲目上占位实例，回收一次全盘重来，反而更贵。</span>

**第二条，自动扩缩容（autoscaling）**。推理服务按流量伸缩 GPU 副本；训练按队列积压扩缩集群。白天高峰扩、夜间缩，避免「按峰值固定备卡」。

**第三条，模型压缩**。量化（INT8/FP8）、蒸馏、剪枝让同一个模型用更少显存与算力跑，直接降低每请求成本。对大模型尤其有效——一个量化后的模型可能省下 50% 推理成本。

**第四条，批处理与复用**。推理侧做动态批处理（continuous batching，把多请求合并成一次前向）；训练侧用更大 batch、更好并行策略（数据/张量/流水线并行）提高单卡吞吐。加上前文的调度排队，让 GPU 空闲时间压到最低。

## 4 公式解析：训练成本的三因子与利用率的隐藏项

成本优化要可计算。一次训练任务的总成本，是最朴素的「三因子乘积」：

$$
\text{Cost}_{\text{train}} = n_{\text{GPU}} \cdot c_{\text{GPU}} \cdot t_{\text{hours}}
$$

逐项拆解：

- **第一步，明确 $n_{\text{GPU}}$**：任务占用的 GPU 卡数。卡越多训练越快，但通信开销上升，存在「加速比天花板」——不是卡越多越划算。
- **第二步，明确 $c_{\text{GPU}}$**：每卡每小时价格。按需实例最贵，占位实例 3–7 折，自建 GPU 还要摊上机房、电力与运维。<span class="marginnote">一个常被忽略的对比维度：自建 GPU 的「每小时成本」= 硬件折旧 + 电费 + 机房 + 运维人力摊薄，云上按需则是「即用即付、无需运维」。小规模团队买云，大规模稳定负载自建，往往是成本曲线的两个最优解。</span>
**第三步，明确 $t_{\text{hours}}$**：训练墙钟时长。它由模型规模、数据量、并行策略共同决定。
**第四步，读出隐藏项——利用率**：三因子是**已运行**成本；真正的账单还要乘上「资源空转」系数。若集群利用率只有 50%，相当于 $c_{\text{GPU}}$ 隐含翻倍。所以成本优化的第一优先级不是砍 $t_{\text{hours}}$，而是**把利用率从 50% 抬到 85%**——这恰好是调度（第 2 节）与四条杠杆（第 3 节）的工作。

## 5 核心对比表：MLOps 平台选型

本主题以工程选型为主，用核心对比表替代额外公式解析。平台选型的本质是「自建 vs 托管」的取舍：

| 维度 | 托管平台（Vertex AI / SageMaker） | 自建（Kubeflow / 自管 K8s） | 混合 |
| --- | --- | --- | --- |
| 上手成本 | 最低，开箱即用 | 高，需 K8s 运维团队 | 中 |
| 灵活性 | 低，受平台能力约束 | 高，任意定制 | 中高 |
| 成本模式 | 按用量付费，单价高 | 固定成本，规模越大越省 | 分层 |
| GPU 调度 | 平台内置队列 | 自管 Kueue/Volcano | 关键负载自管 |
| 数据主权 | 数据在云厂商环境 | 完全自主 | 敏感数据自管 |
| 适用阶段 | 小团队、快速验证 | 大规模、长期稳定负载 | 大部分中大型团队 |

**辨析｜易错点：** 平台选型最常见的错误是**「以团队大小代替负载特征」**来决策。正确的判据是**「负载是否稳定、规模是否够大」**：负载小且波动（起步期）→ 托管；负载大且稳定（成熟业务）→ 自建摊薄成本；两者之间 → 混合，把「瓶颈与关键负载」自管，把「弹性与长尾」交给托管。另一常见误判是「平台能解决 MLOps」——**平台解决基础设施，不解决流程**：评估门禁、漂移监控、模型治理照样要自己建，托管只是帮你省了 K8s 这张床，被子还得自己盖。

## 6 GPU 资源运营的度量：把「钱花哪了」变成数字

成本优化的前提是把成本「看得见」。成熟的资源运营会建立三个度量：

**第一，利用率（utilization）**：GPU 实际计算时间占总占用时间的比例。50% 利用率意味着「一半的钱买了空闲」。利用率要按「节点 + 任务 + 团队」三维度聚合，才能定位是「谁的集群在空转」。

**第二，成本归属（cost attribution）**：把 GPU 账单摊回具体团队、项目、模型。没有归属，就没有人愿意优化——「反正公司出钱」。按团队分账后，「谁的模型贵」一目了然，优化动力自然产生。<span class="marginnote">成本归属的粒度要细到「模型」而非「团队」：只归到团队，团队内部仍无人对单个模型的贵贱负责；归到模型，数据科学家才会认真评估「这个实验值不值一张卡跑三小时」。</span>

**第三，单位成本（unit cost）**：把总成本摊到业务单位上，如「每 1000 次预测的成本」「每次微调的平均成本」「每百万 token 的推理成本」。单位成本让「贵不贵」有了跨周期、跨方案的可比性——量化模型上线后单位成本下降了多少，就是它的经济价值。

**辨析｜易错点：** 三个度量最容易被误用的是「一个数字打天下」——「看整体利用率就够了」。实际上整体利用率高可能掩盖「某个团队独占大量 GPU 且利用率极低」。成本治理要做到「**分账到人、指标到模型**」，否则优化无从下手。

最后补一句组织层面的实践：成本优化不是纯技术问题，而是**跨团队机制**。云账单的「Cost Explorer」与标签（tag）体系要在资源创建时就强制打上「团队/项目/用途」标签，否则事后再分账永远对不上；而「谁花钱」与「谁受益」要绑定——跑实验的数据科学家能看到自己项目的单位成本，才会主动清理闲置任务。把「成本」做成**每个提交的人都能看见的指标**，比任何技术优化都更能改变行为。

## 8 小结

- GPU 调度难在**稀缺、拓扑约束、排队优先级**；Kubernetes 之上用 **Kueue（队列配额）** 与 **Volcano（批量/gang 调度）** 补能力。
- 成本优化的四条杠杆：**占位实例（前提是可断点续训）、自动扩缩容、模型压缩、批处理与并行**。
- 训练成本 $\text{Cost} = n_{\text{GPU}} \cdot c_{\text{GPU}} \cdot t_{\text{hours}}$，但真正的账单要再乘「利用率」系数——**把利用率从 50% 抬到 85%，比砍时长更划算**。
- 成本治理的三个度量缺一不可：**利用率（定位空转）、成本归属（分账到模型）、单位成本（跨方案可比）**。
- 平台选型看「负载是否稳定、规模是否够大」，而非团队大小：小且波动 → 托管，大且稳定 → 自建，中间 → 混合。
- **gang scheduling** 解决「8 卡训练少 1 卡就全卡住」的死局：先凑齐一组再一起放行，是训练型调度的标配。
- 成本优化是**跨团队机制**而非纯技术问题：资源从创建起就打「团队/项目」标签，分账到模型，让每个提交的人都能看见自己的单位成本。

到这里，「从极限到大模型」这条主线中的 MLOps 与 LLMOps 专题就画上句号了。回看全篇，我们沿着生命周期走完了一整圈：概念与角色（第1篇）立起地图，数据版本与实验跟踪（第2、3篇）奠定可复现，流水线、CI/CD、部署（第4、5、6篇）实现自动化与安全上线，监控（第7篇）盯住退化，LLMOps（第8、9篇）把整套纪律迁移到大模型应用，最后用 GPU 调度与平台选型（本篇）算清成本账。学完这十章，你手中已经有了一套「把模型从笔记本搬进生产、再养到退役」的完整工程工具箱——接下来无论面对自训模型还是大模型应用，都能回答「先管什么、再管什么、怎么算账」。
