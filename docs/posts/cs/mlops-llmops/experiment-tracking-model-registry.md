## 为什么从实验跟踪开始

数据有了版本（上一节），下一步的问题是：**当数据科学家把几十次实验跑下来，凭什么判断哪一次最好？** 没有实验跟踪时，团队靠的是「笔记本文件名 + `v2_final_真的final`」，结果三天后谁也说不出某个指标对应哪组超参数、哪份数据、哪段代码。**实验跟踪（experiment tracking）** 为每一次训练建立一份完整档案：参数、指标、产物、代码、数据快照，一次不落。它是「可复现」从数据层向上延伸的第二站。<span class="marginnote">一个被反复引用的行业数据：数据科学团队约 20%–40% 的时间花在「找回过去实验的信息」上。实验跟踪工具把这部分时间几乎压到零，是把时间还给建模本身的最划算投资。</span>

实验跟踪还有一个常被忽视的收益：**团队协作的公共语言**。当「谁都能看到每次实验的参数与指标」，数据科学家之间的沟通就从「你看我这个结果咋样」变成「跑一下实验 ID `exp_231` 对照」。它把个人经验沉淀成组织资产——新人加入团队，翻一遍历史实验，就理解了团队踩过的坑与当下的最优基线。这也是为什么本专题把实验跟踪放在「数据版本」之后、作为可复现性的第二根支柱。

## 1 一次实验要记录什么：五类信息缺一不可

一次实验的档案至少包含五类信息，缺任一类都无法完整复现：

**参数（parameters）**：超参数、数据路径、模型架构配置。它是实验的「输入」。

**指标（metrics）**：损失、精度、召回、AUC、训练时长等。它是实验的「输出」。

**产物（artifacts）**：模型权重文件、可视化曲线、特征重要性图、日志。它是实验的「实物」。

**代码与依赖（code & environment）**：git commit hash、Python 包版本、运行脚本。它是实验的「环境」——换了依赖版本，同一份代码结果可能不同。<span class="marginnote">依赖锁定的重要性常被低估：`numpy` 从 1.x 升到 2.x 就可能改变随机数序列与数值结果。实验跟踪里记录「环境」与记录「指标」同等重要，否则复现时处处踩坑。</span>

**数据版本（data version）**：与上一节 DVC 的联动点——实验档案应记录训练数据的 DVC 哈希，使「代码 + 数据 + 参数」三位一体。

## 2 MLflow：一整套开源的实验生命周期工具

**MLflow** 是目前最流行的开源实验管理平台，由 Databricks 于 2018 年开源。它把「实验管理」拆成四个松耦合组件，每个都可以单独使用：

**MLflow Tracking**：记录参数、指标与产物的 API 与 UI。数据科学家在训练脚本里调用 `mlflow.log_param(...)`、`mlflow.log_metric(...)`、`mlflow.log_artifact(...)`，其余交给后端存储。<span class="marginnote">Tracking 的存储后端可插拔：本地文件、SQLite、PostgreSQL 或云对象存储。团队规模小可从本地起步，规模化后再迁移——这是 MLflow 设计的精髓：组件解耦，渐进采用。</span>

**MLflow Projects**：把实验封装成可复现的运行单元。一个 project 用 `MLproject` 文件声明环境（conda/Docker）与入口命令，保证「换台机器也能跑」。

**MLflow Models**：定义模型打包格式。一个模型目录 = 模型文件 + `MLmodel` 描述文件（含依赖与签名），可以被多语言、多推理引擎加载。

**MLflow Model Registry**：模型版本管理的中枢。模型从「实验产物」变成「注册表里可治理的资产」，支持阶段流转（Staging → Production → Archived）与备注、审批。

## 3 公式解析：模型注册表的晋升门控

模型注册表解决了「选哪个模型上线」，但**选**必须建立在可量化的规则上，而不是「感觉这个好」。一个典型的生产门控（promotion gate）是：

$$
\Delta = m_{\text{cand}} - m_{\text{champ}} , \qquad
\text{晋升条件：} \Delta \geq \delta
$$

逐项拆解：

- **第一步，明确 $m$ 是什么**：$m$ 是模型在**离线评估集**上的主指标，比如验证集 AUC 或线上回归的兜底指标。它必须与业务目标对齐，且由固定版本的评估脚本计算，保证可比。
- **第二步，理解 $m_{\text{champ}}$**：这是当前线上服役的冠军模型（champion）的指标。候选模型（candidate）要上位，必须先打赢现任冠军。
- **第三步，看懂阈值 $\delta$**：$\delta$ 是**最小优势门限**。它通常设为一个正的小数（如 0.01 的 AUC 提升），作用有两点：一是过滤「随机噪声带来的假提升」，二是为「上线风险」留出裕量——候选模型赢得太少，不值得冒部署风险。
- **第四步，体会门控的工程意义**：把「晋升」写成一条显式不等式，等于把**人工决策变成可审计的规则**。谁晋升、为什么晋升、卡在哪个指标上，全部有据可查。这也是模型注册表与「手动拷贝权重」的本质区别。

这道门控还可以叠加「多指标同时达标」：$m_1 \geq m_{1,\text{min}}$ 且 $m_2 \geq m_{2,\text{min}}$，让精度、召回、延迟同时过关，才允许晋升。<span class="marginnote">实战里常见教训是「只看离线指标不看延迟」：一个精度更高但推理慢 3 倍的模型，在在线场景可能更差。所以晋升门控里通常同时含「质量指标」与「性能指标」两类。</span>

## 4 核心对比表：MLflow 与 W&B 怎么选

本主题以工具工程为主，用核心对比表替代额外公式解析，给出选型依据。

| 维度 | MLflow | Weights & Biases（W&B） |
| --- | --- | --- |
| 定位 | 开源、可自托管、端到端生命周期 | 云优先的实验管理，偏研究与团队协作 |
| 组件覆盖 | Tracking + Projects + Models + Registry | Tracking + Sweeps + Reports + Artifacts |
| 注册表 | 内置 Model Registry，阶段流转成熟 | Artifacts 侧重数据/模型版本，注册偏向轻量 |
| 超参搜索 | 需配合 Optuna 等 | 内置 Sweeps，深度集成 |
| 数据/代码托管 | 本地或私有云均可 | 默认云端（可自托管企业版） |
| 适合场景 | 需要数据主权、深度定制、全链路治理 | 快速迭代、可视化报告、研究型团队 |

**辨析｜易错点：** 两种工具都能记录参数与指标，但**不能互相替代注册表功能**。若团队同时需要「实验对比」与「生产模型治理」，常见组合是：研究阶段用 W&B 加速迭代，进入生产阶段以 MLflow Registry 作为唯一事实来源（single source of truth）。另一个易错点是把注册表当垃圾桶——**只有通过评估门控的模型才应晋升到 Production 阶段**，否则注册表很快会被几十个「看起来能用的版本」污染。

## 5 实战：一次「从实验到上线」的完整旅程

假设你刚跑完一个新的推荐模型实验，要让它上线。实验跟踪与注册表如何协同？分五步：

**第一步，登记实验**：训练脚本把参数、指标、git commit 与数据版本全部记入 Tracking。此时实验只是「档案」，与线上无关。

**第二步，注册候选**：实验达标后，把产物注册为模型版本，stage 置为 None（未进入任何阶段），并附上指标与实验链接。注册表开始接管这个模型。

**第三步，过评估门控**：在独立评估集上跑晋升门控 $\Delta \geq \delta$，同时检查「性能指标」（延迟、显存）是否达标。两关都过，才将 stage 流转为 Staging。

**第四步，金丝雀观察**：Staging 模型部署到预发环境，与线上冠军模型并行观察；数据科学家在面板上对比两者输出，确认无回归后批准进入 Production。

**第五步，归档与审计**：被替换的旧 Production 版本自动流转为 Archived。任何一次阶段流转都留审计记录——「什么时候、谁、为什么把哪个版本提上去」，随时可查。

这条流程的关键在于：**实验跟踪管「过程」，注册表管「状态」**——跟踪回答「发生过什么」，注册表回答「现在谁在线、谁在等」。两者数据同源，但职责分离。

**辨析｜易错点：** 一些团队把「注册」与「上线」混为一谈——注册只是「登记」，不代表「服务在跑」。注册表与部署系统要显式打通：只有 stage = Production 的版本才允许被推理服务加载；否则会出现「注册表说 A 在线、实际服务跑的是 B」的假象，治理就失了意义。

## 6 术语速查表

| 术语 | 一句话含义 | 关键词 |
| --- | --- | --- |
| 实验跟踪 | 为每次训练建立参数/指标/产物档案 | 参数、指标、产物、环境、数据 |
| MLflow | 开源实验管理平台，四组件松耦合 | Tracking / Projects / Models / Registry |
| 模型注册表 | 模型版本治理中枢 | 阶段流转、审批、审计 |
| 晋升门控 | $\Delta = m_{\text{cand}} - m_{\text{champ}} \geq \delta$ | 可审计的晋升规则 |
| Staging/Production/Archived | 候选 / 线上 / 归档三阶段 | 流转留痕 |
| 过程 vs 状态 | 跟踪管过程，注册表管状态 | 职责分离、数据同源 |

## 7 小结

- 一次实验的档案 = **参数 + 指标 + 产物 + 代码环境 + 数据版本**，五类缺一不可。
- **MLflow** 由四个松耦合组件构成：Tracking、Projects、Models、Model Registry，支持渐进采用。
- 模型注册表用 **晋升门控** $\Delta \geq \delta$
