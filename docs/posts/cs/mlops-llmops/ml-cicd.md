## 为什么从 CI/CD for ML 开始

流水线（上一节）把训练自动化了，但「训练出模型」不等于「安全上线」。传统软件早就用 **CI/CD（Continuous Integration / Continuous Delivery，持续集成 / 持续交付）** 把「提交代码 → 自动测试 → 自动部署」变成了铁律；而机器学习直到最近才把这套纪律迁移过来，并且发现**照搬会失效**——因为 ML 的「代码」里藏着数据与模型这两类传统 CI 从不测试的对象。<span class="marginnote">「照搬失效」的典型例子：传统 CI 测试「代码改动不会破坏功能」，而 ML 的一次改动（哪怕只是一行特征代码）可能让 100 个下游模型同时漂移。ML 的 CI/CD 必须测试「数据」与「模型行为」，而不只是「代码」。</span>

CI/CD 对机器学习的另一个价值是**发布频率**。传统 ML 团队「三个月发一次模型」，每次发布都像搬家一样兴师动众；而成熟的 CI/CD 让「每周发一次、甚至随数据变化自动发」成为常态。发布越频繁，单次发布的改动越小、风险越低、回滚越容易——这恰好呼应了前文「把上线的风险切成小份」的思路。CI/CD 不是锦上添花的工程洁癖，而是让模型「随数据呼吸」的前提。

## 1 什么是「流水线的流水线」

机器学习系统的 CI/CD 之所以复杂，是因为它把两层流水线叠在一起：

**第一层：软件流水线（software pipeline）**。训练代码、服务代码、配置的每次提交，都要触发：单元测试 → 构建镜像 → 集成测试。这一层与传统 CI/CD 几乎相同。

**第二层：模型流水线（model pipeline）**。数据更新或代码变更后，重新训练 → 评估 → 质量门禁 → 注册 → 部署。这一层是 ML 特有的。

**CI/CD for ML 的定义**：为这两层流水线建立统一的自动化与门禁，使得「每一次代码或数据变更，都以可复现、可回滚的方式，安全地反映到生产环境」。业界把它拆成三个 C：

**CI（持续集成）**：代码与数据变更后，自动跑测试并构建可部署的模型产物。
**CD（持续交付/部署）**：把通过门禁的模型自动或半自动发布到生产。
**CT（持续训练）**：新数据到来时自动触发重训，让模型跟上分布变化。<span class="marginnote">「持续训练」是 ML 独有的第三个 C：传统软件不会因数据变化而重写行为，模型会。Google 在 2019 年把 CT 与 CI/CD 并列为 MLOps 的三大支柱，强调「模型要随数据呼吸」。</span>

## 2 ML 的测试金字塔：从「单测」到「漂移测试」

传统测试金字塔是「单元测试 → 集成测试 → 端到端测试」。ML 在这三层之上又叠加了专属的测试面：

**数据测试（data tests）**：校验新数据的 schema、类型、取值分布、缺失率是否符合预期。工具如 Great Expectations、TFX Data Validation。这是 ML 测试里成本最低、收益最高的一层——大多数上线事故源于坏数据。<span class="marginnote">数据测试可以简单到「age 列没有负数」「邮箱列格式合法」，也可以复杂到「新一批数据的均值与训练期相差不超过 3σ」。关键是把它写进 CI，数据一进来就先过校验，而不是等训练跑完才发现。</span>

**模型测试（model tests）**：对模型行为本身做断言——在固定测试集上精度不低于阈值、对敏感样本（如极端 case）输出稳定、训练可复现（同参数同数据结果一致）。

**集成测试（integration tests）**：验证「模型 + 特征服务 + 推理引擎」整条链路能跑通，特征取值与模型签名匹配。

**回归与漂移测试（regression & drift tests）**：在评估集上对比新模型与冠军模型的指标差；对线上采样的特征分布做漂移检测，超过阈值即阻断发布。

## 3 公式解析：质量门禁的「木桶效应」

把一道道门禁串起来，就得到一个关键事实：**整体通过率是各门禁通过率的乘积**。

$$
P_{\text{release}} = \prod_{i=1}^{K} p_i
$$

逐项拆解：

- **第一步，明确 $K$ 与 $p_i$**：$K$ 是质量门禁的总数——数据校验、单元测试、评估阈值、漂移检查……$p_i$ 是第 $i$ 道门禁的通过概率。
- **第二步，理解乘积的含义**：模型要发布，必须**同时**通过所有门禁，所以各概率相乘。如果每道门禁通过率都是 0.95，五道门禁的整体通过率是 $0.95^5 \approx 0.774$——接近四分之一的机会被某道门卡住。
- **第三步，读出工程教训**：门禁越多越安全，但**积压发布**的代价也越高。发布频率低时，团队会为了「赶发布」而放松门禁——这是 CI/CD 纪律溃败的开始。
- **第四步，落到设计**：门禁要「少而准」。优先保留**最能拦截真实事故**的少数几道（数据校验、评估阈值、漂移检查），而非面面俱到却每道都很松。<span class="marginnote">实践中常见反向操作：团队先加了一堆「看起来严格」的门禁，结果发布太慢，于是集体决定「紧急情况下可跳过门禁」。跳过一次就有第二次，最终门禁形同虚设。门禁设计的原则是：宁可少而严，不可多而虚。</span>

## 4 核心对比表：传统 CI/CD 与 ML CI/CD

本主题以工程实践为主，用核心对比表替代额外公式解析。

| 维度 | 传统 CI/CD | ML CI/CD |
| --- | --- | --- |
| 触发源 | 代码提交 | 代码提交 + 数据更新 + 新标注 |
| 测试对象 | 代码行为 | 代码 + 数据 + 模型行为 |
| 部署产物 | 二进制 / 服务 | 模型权重 + 服务镜像 + 特征版本 |
| 测试确定性 | 结果确定（同一代码同一行为） | 概率性（同代码可能不同指标） |
| 回滚对象 | 代码版本 | 模型版本 + 数据版本 + 代码版本 |
| 上线后验证 | 功能冒烟测试 | 在线评估 + 漂移监控（见后文） |

**辨析｜易错点：** 最大误判是「把训练代码接进 CI 就算 ML CI/CD」。真正的分水岭有三条：**数据变更是否也触发流水线？模型是否进注册表并走晋升门禁？线上是否有漂移监控闭环？** 三者缺一，就只是「披着 CI 外衣的脚本」。另一常见误判是把「离线指标通过」当成「可以上线」——离线通过只代表「在历史数据上合格」，上线后数据分布变了照样失效，所以 CI 必须与「在线监控 + 快速回滚」配对使用。

## 5 一个例子：数据变更如何触发整条 CI/CD

传统 CI 由「代码提交」触发，ML CI 还要能被「数据变更」触发。看一个具体流程：

**事件**：凌晨 2 点，上游账单表完成当日更新，DVC 数据版本从 `v31` 变为 `v32`。

**触发**：流水线监听数据仓库的事件通知，检测到新版本数据，自动启动一次训练流水线——不需要任何人手动点击。

**数据测试**：新数据先过数据校验：行数在预期范围、必填字段无缺失、`age` 列无负值。若校验失败，流水线直接终止，并给数据团队发告警——「坏数据」在训练前就被拦下。

**训练与评估**：校验通过后触发重训；新模型在测试集上评估，跑晋升门控（与冠军模型对比）。

**发布决策**：门控通过 → 模型进注册表 Staging → 金丝雀观察 → 全量上线；门控不通过 → 流水线静默终止，线上冠军模型继续服役，团队收到「新模型未达标」的报告。

这个例子的要点：**整条链没有任何人工步骤**，唯一的「人」出现在门控不过时——这才是「持续」二字的含义。数据变了，系统自动响应；系统不能自动判断的，才轮到人。

**辨析｜易错点：** 有人把「自动重训」误当成「自动上线」。两者必须分开：**重训可以全自动，上线必须有门禁与金丝雀**。数据一变就训练、训练完就全量替换线上模型，等于把「数据分布变化」的风险全部押在离线评估上——一旦离线指标失真，线上立刻翻车。安全姿势是：训练自动，发布受控。

**工具链一句话**：ML CI/CD 不必从零搭建——通用 CI（GitHub Actions、GitLab CI、Jenkins）负责「软件流水线」层；数据校验用 Great Expectations / TFX Data Validation；模型评估与门控复用实验跟踪（MLflow）的评估 API；部署编排与 Argo CD / Flux（GitOps）打通。要点不在「用哪个工具」，而在**让代码、数据、模型三类变更都走同一道自动化闸门**——工具的拼法可以各异，纪律的骨架必须一致。

## 6 术语速查表

| 术语 | 一句话含义 | 关键词 |
| --- | --- | --- |
| CI / CD / CT | 持续集成 / 持续交付 / 持续训练 | 模型随数据呼吸 |
| 测试金字塔 | 数据 → 模型 → 集成 → 回归漂移 | 数据层性价比最高 |
| 数据测试 | 校验 schema、分布、缺失率 | 拦坏数据于训练前 |
| 质量门禁 | 多重校验串成的发布闸门 | $P = \prod p_i$ |
| 木桶效应 | 整体通过率 = 各门禁通过率乘积 | 门禁宜少而准 |
| 自动重训 ≠ 自动上线 | 训练可自动，发布须受控 | 门禁 + 金丝雀 |

## 7 小结

- ML 的 CI/CD 是**「软件流水线 + 模型流水线」的双层叠加**，对应 CI / CD / CT 三个 C。
- ML 测试金字塔 = **数据测试 + 模型测试 + 集成测试 + 回归漂移测试**，数据测试是性价比最高的一层。
- 质量门禁的整体通过率满足 $P_{\text{release}} = \prod p_i$：门禁越多越安全、但也越积压发布，原则是**宁可少而严，不可多而虚**。
- ML CI 的触发源比传统多一个：**数据变更也要触发流水线**；整条链无人工步骤，唯一的「人」出现在门控不过时。
- **自动重训 ≠ 自动上线**：训练可以全自动，发布必须经过门禁与金丝雀——安全姿势是「训练自动，发布受控」。
- ML 测试的性价比排序：**数据测试 > 模型测试 > 集成测试 > 漂移回归测试**——大多数上线事故源于坏数据，所以数据层最该先投入。
- 门禁设计原则是**「宁可少而严，不可多而虚」**：先堆一堆松门禁、再在赶发布时集体跳过，最终门禁形同虚设。
- 工具链不必从零搭建：通用 CI + Great Expectations 校验数据 + MLflow 评估门控 + GitOps 部署，要点是让「代码、数据、模型」三类变更都走同一道自动化闸门。

在下一节，CI/CD 把模型推到了「可以上线」的门口，接下来是上线本身：**模型部署模式**——批推理、在线服务与影子/金丝雀发布，看同一份权重如何在延迟、成本与风险之间选出一条合适的上线路径。
