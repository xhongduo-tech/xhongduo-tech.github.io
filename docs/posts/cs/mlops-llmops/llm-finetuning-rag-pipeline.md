## 为什么从微调与 RAG 的工程化开始

上一节我们建立了 LLMOps 的整体框架：提示管理、评估、护栏。但在真实产品里，**「怎么让基础模型适配我的业务」**才是最常被问起的工程问题。主流答案有两条：**微调（fine-tuning）**——把模型权重继续训练到更适配你的数据与风格；**RAG（Retrieval-Augmented Generation，检索增强生成）**——不碰权重，而是把相关知识检索出来塞进提示词的上下文。两条路各有利弊、常被混用，而它们的**流水线工程化**——数据怎么准备、流程怎么编排、效果怎么评估——正是本节的焦点。<span class="marginnote">一句话先给直觉：RAG 回答「模型不知道但文档里有」的问题（知识类、时效类），微调回答「模型能知道但做得不够好」的问题（风格、格式、能力类）。知识进 RAG，能力进微调。</span>

两条路还有一个重要的工程差异：**迭代速度**。RAG 的改动周期以天计——改分块、换嵌入、调提示，当天就能验证效果；微调的改动周期以周计——准备数据、训练、评估、防遗忘，一个循环下来要好几天。这意味着**在不确定该用哪条路时，先试 RAG 是更快的试错路径**；当 RAG 已经把「知识」喂足、仍差「能力」时，再上微调补那最后一块。这种「先 RAG 后微调」的工程节奏，是大模型落地最稳妥的默认顺序。

## 1 微调的工程化：参数高效与数据治理

全参数微调大模型成本极高，工业界的主流是**参数高效微调（PEFT）**，其中 **LoRA（Low-Rank Adaptation，低秩适配）** 最流行：冻结原权重，只训练插入的小规模低秩矩阵，可训练参数通常不到总量的 1%，显存与训练时间大幅下降。

一条成熟的微调流水线包含四道工序：

**第一，数据准备与治理**。构造「指令-输出」对：指令数据（instruction data）告诉模型「做什么」，偏好数据（preference data）告诉模型「哪个更好」（供 DPO 等对齐方法使用）。数据要清洗、去重、去敏感信息、配版本——复用前文 DVC 的数据版本管理。<span class="marginnote">微调数据质量压倒数量：几百条高质量指令对，胜过几万条含噪声数据。业界经验是「数据先做人工质检，合格率过阈值再上流水线」，与 ML CI/CD 的数据测试一脉相承。</span>

**第二，训练与跟踪**。用 LoRA 训练，配实验跟踪记录超参（秩、学习率、步数）与损失曲线，产物是「基础模型 + LoRA 适配器」的组合，而非完整权重。适配器只有几十 MB，便于版本化与分发。

**第三，评估门禁**。微调完的模型要在**独立基准集**上过双闸门（复用上一节的均值 + 最低分），并做「灾难性遗忘」检查——对比微调前后在通用能力基准上的表现，防止「学会业务却忘了常识」。

**第四，合并与部署**。把 LoRA 适配器与基础模型合并成推理权重，或运行时动态加载适配器，再走前文的部署模式与监控。

**辨析｜易错点：** 最常见的误判是「模型不够聪明 → 先微调再说」。如果问题是「知识缺失」或「信息过时」，微调只会把新知识「背」进权重，更新一次要重训一次，成本高、时效差——这是 RAG 的战场。微调只该用于「行为风格、输出格式、特定能力」这类稳定不变的适配。

## 2 RAG 流水线：让模型「带上资料回答」

RAG 的思路是在**生成时注入相关知识**，让模型像「开卷考试」一样回答。它由离线与在线两段构成：

**离线索引段（ingestion）**：
**解析与分块（chunking）**：把文档解析成文本，按语义切成块（chunk）。块太小则上下文碎片化、检索信号弱；块太大则噪声多、成本高。业界常用 300–800 token 的块，配重叠（overlap）避免切断语义。
**向量化（embedding）**：用嵌入模型把每个块转成稠密向量。嵌入模型的选择直接影响检索质量。
**入库（indexing）**：向量写入向量数据库（Milvus、Qdrant、pgvector），同时可建关键词倒排索引（BM25），两者组合成「混合检索」底座。

**在线检索段（retrieval + generation）**：
- 用户提问 → 向量化 → 在向量库做近似最近邻检索 →（可选）混合检索与重排序（rerank）→ 取 Top-K 块。
- 把「问题 + 检索到的上下文 + 提示词」拼装进上下文窗口 → 模型生成回答 → 经过输出护栏后返回用户。<span class="marginnote">RAG 里最容易被忽视的是「检索不到就闭嘴」的兜底：当检索置信度太低时，应让模型回答「资料中没有相关信息」，而不是强行编造。这个兜底逻辑与护栏层配合，是抑制幻觉的关键。</span>

**工程化的关键**是让「索引更新」和「线上检索」成为可监控的流水线：文档更新触发重新分块嵌入、向量库版本化、检索质量定期回归——它本质上是把前文 MLOps 的生命周期管理迁移到了「文档知识库」上。

## 3 公式解析：Recall@k——检索质量的标尺

RAG 的上限由检索决定——**检索不到，生成再强也白搭**。度量检索质量最常用的指标是 **Recall@k**：

$$
\text{Recall@k} = \frac{| \text{relevant} \cap \text{retrieved}_k |}{| \text{relevant} |}
$$

逐项拆解：

- **第一步，明确 $\text{relevant}$**：对一条测试问题，人工标注出「真正相关的文档块」集合，数量记为 $|\text{relevant}|$。
- **第二步，明确 $\text{retrieved}_k$**：检索系统返回的 Top-$k$ 块集合。$k$ 通常取 3–10。
- **第三步，看懂分子**：$| \text{relevant} \cap \text{retrieved}_k |$ 是「相关块里，被检索系统捞回来的个数」。
- **第四步，得到召回率**：比值越高，说明检索越能把相关文档捞回来。若一个问题有 4 个相关块，Top-5 检索捞回 3 个，则 $\text{Recall@5} = 3/4 = 0.75$
