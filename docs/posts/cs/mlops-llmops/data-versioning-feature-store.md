## 为什么从数据版本管理开始

上一节我们把机器学习生命周期画成了一条八阶段的闭环，结论是「模型 = 代码 + 数据 + 超参数 + 权重」。其中 **数据** 是变量最多、最不可控的一环：数据集每天在更新、标注在迭代、上游管道在改动，而当你事后想复现一次实验时，第一个问题永远是——**当时用的到底是哪一份数据？** 这就是数据版本管理要解决的问题。它回答的是「可复现性」的根基：没有数据版本，一切复现都是空谈。<span class="marginnote">Google 的一项调查显示：数据质量问题（而非算法问题）是机器学习生产事故的最主要来源。数据版本管理不是「洁癖」，而是 MLOps 的第一道防洪堤。</span>

把「数据版本」想清楚还有一层现实收益：**成本与效率**。没有版本管理时，团队应对「数据变了」只有两种笨办法——要么把新数据复制一份另存（存储爆炸），要么直接覆盖旧数据（历史丢失）。DVC 的内容寻址让「同一数据只存一份、版本间只存差异」成为可能，数据工程师终于可以像开发者管理代码分支一样管理数据分支：实验用临时分支，稳定后用主干。

## 1 为什么 Git 管不住数据

数据科学家最初的冲动是「把数据放进 Git 就好了」。这个冲动会撞上三个硬约束：

**第一，体积。** Git 的设计目标是文本代码的差异跟踪，动辄几十 GB 的数据集会让仓库膨胀到无法 clone，`.git` 目录比数据本身还大。

**第二，差异语义。** Git 对文本做行级 diff；而数据集的一行 CSV 可能只是「多了几行新样本」，二进制权重文件更是完全不可 diff。版本之间的「差异」对 Git 毫无意义。

**第三，大文件锁与并发。** 多人同时向同一个大文件写入，Git 的 merge 机制在大对象上几乎失效。

于是出现了两种解法。一种是 **Git LFS（Large File Storage）**：把大文件内容存到远端，Git 仓库里只留一个指针文件。它解决了体积，却没有解决「数据与代码、超参数的联合版本」问题——LFS 里的指针和模型的对应关系，仍要靠人肉约定。真正的解法是 **内容寻址（content-addressed）存储**，这正是 DVC 的核心思想。

## 2 公式解析：内容寻址——「数据指纹」怎么来

DVC（Data Version Control）把「版本」从「基于时间线的目录」改成了「基于内容的哈希」。它的一切建立在下面这条式子上：

$$
id = H(\text{content})
$$

逐项拆解：

- **第一步，看清 $H$ 是什么**：$H$ 是一个密码学哈希函数，DVC 用的是 SHA-256。它把一个任意长度的字节串，映射成一个固定长度（256 位）的十六进制字符串，例如 `4f8a…9c21`。
- **第二步，理解「同一性」**：对同样的内容，$H$ 永远给出同样的 $id$；内容只要改一个字节，$id$ 就完全改变。<span class="marginnote">这就是「内容寻址」的含义：文件的地址（id）由内容本身决定，而不是由「放在哪个目录、叫什么名字」决定。同一个文件，在任何人机器上算出的 id 都一致。</span>
**第三步，看懂 DVC 的存储布局**：DVC 把数据文件按 $id$ 存入缓存与远端存储，Git 仓库里只提交一个小到几 KB 的 `.dvc` 元数据文件，里面记着 $id$、文件路径与哈希。于是「数据版本」在 Git 里就是一个可以 diff、可以回滚的文本小文件。
**第四步，体会它的推论**：因为 $id$ 只取决于内容，**相同的数据永远只存一份**（去重）；删除某版本只需删指针，数据仍可按需从缓存恢复。这让「多份数据版本并存」变得廉价。

这条式子的威力在于：**Git 记录的是「发生了什么」，DVC 记录的是「数据是什么」。** 两者互补，才构成可复现实验的完整坐标。

## 3 特征平台：让「离线训练」与「在线推理」用同一份特征

数据版本管理解决「数据可复现」，而 **特征平台（feature store）** 解决「特征一致」。先看一个经典事故：

数据科学家在离线训练时用「用户过去 7 天消费金额」作为特征，模型效果很好。上线时，在线服务需要实时计算这个特征，结果工程师的 SQL 写法和离线版本差了一个 `WHERE` 条件——离线特征分布与在线特征分布不再一致，模型精度骤降。这种「训练-服务偏差（training-serving skew）」是生产机器学习最常见的坑之一。<span class="marginnote">训练-服务偏差指训练时看到的特征分布与服务时实际喂给模型的特征分布不一致。它可能来自特征定义差异、数据窗口差异、或时区/去重等细节。特征平台的目标，就是用「同一份特征定义」把偏差从根上消除。</span>

特征平台的三个核心组件：

**特征存储（feature storage）**：把特征分为两类。**离线存储（offline store）** 存放大批量、面向训练的历史特征，通常是列式存储（Parquet 文件、数据湖）；**在线存储（online store）** 存放低延迟、面向推理的最新特征，通常是键值数据库（Redis、DynamoDB）。

**特征注册表（feature registry）**：统一登记每个特征的名字、定义、来源、口径与版本，相当于特征的「字典」。训练与推理代码都从注册表取定义，而不是各自写各自的 SQL。

**时间点正确性（point-in-time correctness）**：训练一个「预测明天是否流失」的模型时，某个样本的特征必须是「样本发生时刻已知的信息」，不能偷看未来。举例：样本日期是 6 月 1 日，那么「7 天消费特征」必须只统计 5 月 25 日至 5 月 31 日，哪怕 6 月 2 日的数据已经入库。特征平台在离线和在线两侧同时保证这条规则，否则模型会学到「未来的信号」，线上必然失效。<span class="marginnote">时间点正确性是特征平台里最隐蔽也最致命的细节：一旦离线特征「偷看未来」，离线评估指标会虚高，上线后立刻崩盘。这也是为什么「特征统一管理」比「每人自己算」更安全。</span>

## 4 核心对比表：DVC 与特征平台的分工

数据版本管理与特征平台经常被混为一谈，本主题以工程概念为主，用一张核心对比表替代公式解析，厘清二者分工。

| 维度 | DVC 数据版本管理 | 特征平台 |
| --- | --- | --- |
| 管理对象 | 数据集、模型权重、流水线产物 | 特征的定义、取值与分布 |
| 核心目标 | 可复现：实验能原样重跑 | 一致：训练与推理用同一份特征 |
| 版本粒度 | 整个数据集的快照 | 单个特征的口径与版本 |
| 服务对象 | 训练流水线 | 训练 + 在线推理两条链路 |
| 典型工具 | DVC、LakeFS、Delta Lake | Feast、Tecton、Amundsen |
| 时间维度 | 快照的历史 | 时间点正确性的保证 |

**辨析｜易错点：** 一种常见误解是「把特征也放进 DVC 就相当于有特征平台」。特征平台的价值不止于「存」，而在于「同一份定义同时服务训练与推理」，并保证时间点正确性——这是版本管理工具不提供的。另一类误判是「先建平台再搬数据」：成熟的实践是**先从单条特征管起**，等确有跨团队复用需求时再上平台，避免为工程而工程。

## 5 数据血缘与 DVC 实战清单

版本管理回答「数据长什么样」，**数据血缘（data lineage）** 回答「数据从哪来、流到哪去」。血缘把「上游表 → 特征 → 模型」画成一张依赖图：模型 A 用了特征 B，特征 B 来自表 C，表 C 由任务 D 生成。这张图的价值在事故现场体现——线上指标异常，顺着血缘图能一路追到「任务 D 改了上游口径」。与 DVC 的快照式版本互补：血缘是「流动的视图」，版本是「静止的切片」。

DVC 的日常使用只有四五个命令，先跑通再谈复杂：

```bash
dvc init                          # 初始化，生成 .dvc 配置
dvc add data/raw/train.parquet    # 登记数据，生成 几KB 的 .dvc 元数据
git add data/raw/train.parquet.dvc
dvc remote add -d store s3://my-bucket/dvc-store
dvc push                          # 数据本体上传远端，仓库只留指针
dvc checkout                      # 换机器后，按元数据拉取对应版本
```

这套流程的要诀是「**Git 管元数据，DVC 管数据本体**」：`.dvc` 文件进 Git 参与评审与回滚，数据本体进对象存储。任何一次 `dvc add` 之后，数据版本的「坐标」就固化在了一个可 diff 的文本文件里——这正是可复现实验最朴素也最坚实的底座。

**辨析｜易错点：** DVC 不是「备份工具」。把 `dvc push` 当成「定期备份」用，会错过它真正的价值——**版本间的可回溯与可复现**。另一常见误用是「把 dvc 缓存目录塞进 Git」：缓存目录体积巨大，违背了 DVC 设计初衷，应始终配置在 `.gitignore` 之外，交给远端存储。

## 6 术语速查表

| 术语 | 一句话含义 | 关键词 |
| --- | --- | --- |
| 内容寻址 | 用内容哈希做文件地址，同内容同 id | SHA-256 |
| Git LFS | 用指针文件替代大文件的 Git 扩展 | 只解决体积，不解决联合版本 |
| DVC | 数据版本控制：Git 管元数据，DVC 管本体 | `.dvc` 元数据文件 |
| 特征平台 | 统一特征定义，训练与推理共用同一份特征 | 根治训练-服务偏差 |
| 离线/在线存储 | 大批历史特征 / 低延迟最新特征 | 列式存储 / 键值库 |
| 时间点正确性 | 特征只用样本时刻已知的信息 | 禁止偷看未来 |
| 数据血缘 | 数据从哪来、流到哪去的依赖图 | 事故排障溯源 |

## 7 小结

- Git 管不住数据的三重障碍：**体积、差异语义、并发**；Git LFS 只解决体积，不解决联合版本。
- **内容寻址** $id = H(\text{content})$
