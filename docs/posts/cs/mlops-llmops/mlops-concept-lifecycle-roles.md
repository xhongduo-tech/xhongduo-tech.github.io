## 为什么从 MLOps 的概念开始

这个专题叫「MLOps 与 LLMOps」，但要回答「MLOps 到底解决什么问题」，得先看清一个尴尬的现实：**模型在实验室里跑通，与模型在生产里产生价值，是两件截然不同的事**。《Introducing MLOps》开篇就给出一个刺眼的行业数据——超过一半的组织创建的模型从未上线。原因不在算法：数据科学家写出了漂亮的模型，却没有人把它稳定地训练、部署、监控、迭代成一项服务。**MLOps（Machine Learning Operations，机器学习运维）** 就是为这条「从实验到生产」的鸿沟而生的工程学科：把软件工程里的 DevOps 纪律迁移到机器学习上，让模型像软件一样可复现、可测试、可监控、可治理。<span class="marginnote">「从极限到大模型」整条主线走到这里，终于从「怎么把模型做出来」转向「怎么把模型养起来」。MLOps 是这道转折的门槛：此前所有的建模本领，都要经它变成可持续的生产能力。</span>

MLOps 出现在本专题的最前面，还有一个更实际的原因：**后面每一篇文章都是这个概念的分支**。数据版本、实验跟踪、流水线编排、CI/CD、部署、监控、LLMOps……它们分别回答「怎么管数据」「怎么管实验」「怎么自动化」「怎么安全上线」「怎么盯退化」——而这些问题的总纲，正是本节要立起来的概念骨架。先把这张地图画清楚，后面十章才不至于迷失方向。

## 1 MLOps 是什么：让模型「像软件一样被运营」

给 MLOps 下一个工作定义：**MLOps 是把 DevOps 实践（持续集成、持续交付、自动化、监控、协作）应用到机器学习系统的工程方法，目标是以可重复、可治理的方式，让模型持续产生业务价值。** 它回答的不是「模型怎么训」，而是「模型怎么上线、怎么活着、怎么体面地退役」。

传统软件工程早已确立一套纪律：代码进版本库、改动跑自动化测试、构建产物可追溯、线上服务被监控、出问题能回滚。MLOps 把这套纪律搬运过来，却发现**照搬会失效**——因为机器学习系统里除了「代码」，还多了两样传统软件从不需要治理的对象：

- **数据**：数据集会更新、标注会迭代、上游口径会改变，模型的行为被数据牵着走。
- **模型**：模型不是「写出来」而是「训出来」的，它有自己的版本、指标与失效方式。

所以 MLOps 的真实命题是：**把「代码 + 数据 + 模型」三样东西作为一个整体，持续地、可靠地交付与维护。** 这也是为什么本专题后续会一章一章地拆解数据版本、实验跟踪、模型注册——它们都是「治理的对象变多了」的直接后果。<span class="marginnote">一个直观的类比：DevOps 管的是「一段确定的程序」，MLOps 管的是「一份由数据训练出来的、行为会随世界变化的程序」。多出来的不确定性，正是 MLOps 所有复杂性的源头。</span>

围绕这个命题，业界长出了一批专用工具：DVC 管数据版本、MLflow 与 W&B 管实验与模型注册、Kubeflow 与 Airflow 管流水线、Seldon 与 Triton 管模型服务、Prometheus 与 Grafana 管监控。这些工具本身并不神秘——它们共同的特点是**为「数据与模型」这两个传统软件没有的对象提供版本、测试、追踪与治理能力**。本专题后续章节会逐一展开它们，但请始终记得：工具只是表象，命题才是核心——让三样对象作为一个整体持续交付。

## 2 机器学习生命周期：五阶段的闭环

MLOps 不是一套零散工具，而是一条**生命周期（lifecycle）**。《Introducing MLOps》把它概括为五个阶段，像齿轮一样咬合成一个闭环：

**第一阶段，开发（Build）**。数据科学家探索数据、做特征工程、训练候选模型、对比实验。这一阶段的特点是**发散**——想法多、实验多、试错多，成果是「若干个还不错的模型」。

**第二阶段，预生产（Preproduction）**。从众多候选里挑出最有希望的那个，做上线前的准备：评估是否满足业务指标、检查可复现性与可审计性、做安全与风险审查、为它准备运行环境。这一阶段是**收敛**的——从「可能行」收窄到「就它了」。<span class="marginnote">预生产是传统 MLOps 里最容易被跳过的阶段：团队训出满意的模型就急着部署，把「评估、审查、测试」全略过。可正是这道闸门，决定了线上出问题时有据可查，还是只能靠猜测。</span>

**第三阶段，部署（Deployment）**。把通过审查的模型打包、接入 CI/CD 流水线、发布到生产环境。这里要回答「用什么推理范式、按什么策略上线」——正是本专题《模型部署模式》一章的主题。

**第四阶段，监控（Monitoring）**。模型上线后持续观测：数据漂移、概念漂移、性能退化、业务指标异常。监控回答「模型还好吗」，是重训决策的证据来源。

**第五阶段，治理（Governance）**。贯穿始终的一层：模型的版本、审计记录、责任归属、公平性解释与合规。治理回答「出了问题算谁的、查不查得清」。

五个阶段的价值不在「画一张漂亮的图」，而在它揭示了三个关键事实：**第一，这是个闭环**——监控发现问题，反馈回开发与预生产，触发再训练；**第二，成本集中在后半段**——一个模型 80% 的生命周期在部署之后，却往往只有 20% 的团队投入；**第三，阶段间要留「闸门」**——每一阶段结束都要有明确的放行条件，而不是「感觉差不多了就往前走」。

用一个风控场景串起五个阶段：银行训练「信用卡违约预测」模型——开发阶段在历史账单数据上对比了逻辑回归、XGBoost 与神经网络；预生产阶段确定采用 XGBoost，跑完可复现性与公平性审查；部署阶段通过 CI/CD 上线到评分服务；监控阶段发现「疫情期间」用户还款行为的输入分布整体移动，PSI 指标亮红灯；治理阶段据此记录了「哪个版本的模型、依据什么监控证据、在何时被替换」。整条链的每一环都有据可查——这才是生命周期闭环的完整样子，也是后面章节要逐一落地的工程细节。

## 3 角色分工：谁在「养」一个模型

生命周期要有人跑，而 ML 系统最特殊的一点是**没有一个人能独立完成全生命周期**。数据科学家、数据工程师、软件工程师、运维各自掌握一段，必须协作。这一点让 MLOps 从诞生起就是「跨角色学科」。《Introducing MLOps》专门用一章列举了参与者的画像，按职责可以归纳为四类：

**数据科学家（data scientist）**：负责开发与预生产——探索数据、训练模型、评估候选。他们是模型的「生身父母」，但往往对「部署到哪个环境、怎么监控」不熟悉。

**数据工程师（data engineer）**：负责数据侧——建设数据管道、保证数据质量与版本、维护特征。他们的产出是「模型能吃到稳定、正确、可复现的数据」。

**软件 / ML 工程师（software / ML engineer）**：负责把模型工程化——编写训练与服务代码、打包镜像、搭 CI/CD 流水线、实现监控与告警。他们是「模型与生产系统之间的翻译官」，本专题的大多数工具（DVC、MLflow、Kubeflow、Airflow）都是这个角色的日常。

**运维与平台团队（DevOps / platform team）**：负责基础设施——集群、GPU 调度、存储、权限与安全。他们提供「地基」，让上面三类人不用自己造轮子。<span class="marginnote">为什么讲 MLOps 必须讲角色？因为「责任空白」是线上事故最常见的根源——数据科学家以为部署有人管，运维以为模型有人盯，结果谁都没管。角色分工的意义，是让生命周期的每一段都有一个「明确的负责人」。</span>

**辨析｜易错点：** 很多团队以为「招一个全栈数据科学家」就能覆盖所有角色。现实是：一个人能同时把模型训好、把流水线搭稳、把监控盯住、把治理做齐的极少。更稳妥的做法是**接受分工、定义接口**——数据科学家交付「模型 + 评估报告」，ML 工程师交付「服务 + 监控面板」，双方以「模型注册表」为契约衔接（这正是后面实验跟踪一章的落点）。

## 4 四个 C：MLOps 的核心流程

如果把生命周期拆到「动作」这一层，业界（Google 的 MLOps 实践指南与《Introducing MLOps》均采用）习惯用四个以 C 开头的词来概括 MLOps 反复执行的核心流程。它们是本专题后续多章的骨架：

**CI（Continuous Integration，持续集成）**：代码、数据、配置每次变更后，自动跑测试并构建可部署的产物。ML 里这个「产物」除了服务镜像，还有**模型本身**——训练脚本、数据版本、评估结果的任何变化都要被自动验证。本专题《CI/CD for ML》一章会专门展开。

**CD（Continuous Delivery / Deployment，持续交付 / 部署）**：把通过测试的模型安全地发布到生产。对 ML 而言关键是「安全」——模型发布要比代码发布更谨慎，所以有了金丝雀、影子发布等策略（见《模型部署模式》）。

**CT（Continuous Training，持续训练）**：新数据到来时自动触发重新训练，让模型跟上世界的变化。这是 ML 独有的第三个 C——传统软件不会因为数据变了就重写行为，模型会。<span class="marginnote">CT 不是「每天重训一次」那么机械。它的真正难点是「判断该不该重训」——数据漂移指标到了什么程度值得花一次 GPU 成本？这正是《模型监控》一章与监控告警联动的地方。</span>

**CM（Continuous Monitoring，持续监控）**：模型上线后持续观测漂移、性能与业务指标，并把信号反馈给 CT 作为重训扳机。监控让「训练—部署—监控—再训练」的闭环真正转起来，而不是跑一次就结束。

四个 C 与五阶段生命周期是同一件事的两张视图：生命周期讲「模型的一生」，四个 C 讲「让这一生循环起来的过程」。把它们都记在心里，再回头看本专题的章节目录——数据版本、实验跟踪、流水线、CI/CD、部署、监控——你会发现在每一章里都能找到四个 C 的影子。

## 5 MLOps 成熟度：从 Level 0 到 Level 2

概念讲清楚了，还要回答一个落地问题：**一个团队的 MLOps 做到什么程度才算「合格」？** Google 在 2020 年前后给出过一个被广泛引用的**成熟度模型（maturity model）**，把团队的自动化程度分成三级，非常适合作自我评估：

**Level 0：手工流程（Manual）**。数据科学家在笔记本里训练模型，训练与部署靠手动运行脚本，实验靠文件名区分，模型靠「复制粘贴权重文件」上线。这个级别的问题不是「不专业」，而是**不可复现**——两个月后没人能说清某版模型是怎么来的。它是 MLOps 的起点，绝大多数团队从这里起步。

**Level 1：训练流水线自动化（Automated ML pipeline）**。引入数据版本、实验跟踪与训练流水线（正是本专题前四章的工具）：训练自动触发、产物可追溯、模型进注册表。但**部署仍是手工的**——模型要靠人工批准后手动发布。此级别解决了「能不能复现」，尚未解决「能不能快速、安全地发布」。

**Level 2：CI/CD 流水线自动化（CI/CD pipeline automation）**。在 Level 1 之上，把部署也接入自动化：训练产物自动构建镜像、自动跑质量门禁、自动做金丝雀发布与回滚。这一级才是「完整 MLOps」——模型像软件一样随数据呼吸，几乎不需要人工干预。<span class="marginnote">成熟度的意义是给团队一个「现在在哪、下一步去哪」的路线图。多数团队卡在 Level 0 到 Level 1 的跃迁——不是工具难，而是「先搭数据版本，还是先上流水线」容易选错。Google 的建议与本专题的章节顺序一致：先数据与实验，再流水线，最后 CI/CD。</span>

**辨析｜易错点：** 成熟度模型最容易被误读为「Level 2 一定最好」。事实是**每一级都对应一种组织规模与负载**：两三个人的小团队硬上完整 CI/CD，运维负担可能超过收益。成熟的团队会「按需演进」——等痛点真实出现（发布事故、复现困难、回滚太慢）再升一级，而不是为了「达到 Level 2」而造轮子。这正呼应了本专题最后一章《GPU 资源调度、成本优化与 MLOps 平台选型》里「平台选型要看负载特征而非团队大小」的结论。

## 6 核心对比表：软件交付 vs 模型交付

本主题以概念辨析为主，用核心对比表替代公式解析，把 MLOps 与它模仿的对象放在同一张表里看清差异。

| 维度 | 传统软件（DevOps） | 机器学习系统（MLOps） |
| --- | --- | --- |
| 交付物 | 代码 + 二进制 | 代码 + 数据 + 模型权重 + 特征定义 |
| 行为来源 | 写出来的，确定 | 训出来的，概率性 |
| 上线后是否变化 | 基本不变 | 随数据分布变化而退化 |
| 测试对象 | 代码行为 | 数据质量 + 模型行为 + 代码行为 |
| 版本管理 | 代码版本 | 代码 + 数据 + 模型三者的联合版本 |
| 回滚 | 回滚代码 | 回滚模型版本（还要考虑数据版本） |
| 迭代频率 | 代码驱动 | 数据驱动 + 模型驱动，天然更频繁 |

这张表读出的核心结论只有一条：**MLOps 的一切复杂性，都源于「数据与模型成为一等公民」。** 此后每一章的工具——DVC 管数据、MLflow 管实验与模型、Kubeflow/Airflow 管自动化——都是这张表的某个格子落地的工程解。你可以把本专题当成本表的「逐格展开」来读。

## 7 小结

- **MLOps** 是把 DevOps 纪律迁移到机器学习系统的工程学科，目标是让模型像软件一样**可复现、可测试、可监控、可治理**。
- 模型与代码的根本差异：模型是**训出来的、概率性的、会随世界变化的**，这决定了 MLOps 要同时治理「代码 + 数据 + 模型」三样对象。
- 机器学习生命周期是五阶段闭环：**开发 → 预生产 → 部署 → 监控 → 治理**；监控发现问题，反馈回去触发再训练，循环不止。
- 生命周期各阶段必须由**不同角色**接力：数据科学家、数据工程师、ML 工程师、运维平台团队，用「模型注册表」等契约衔接，堵住责任空白。
- MLOps 的核心流程可概括为**四个 C**：CI（持续集成）、CD（持续交付 / 部署）、CT（持续训练）、CM（持续监控），与五阶段生命周期互为表里。
- 团队可用 **Level 0–2 成熟度模型**自评：手工流程 → 训练流水线自动化 → CI/CD 自动化；逐级演进，不硬上。
- 章节导航：数据版本 → 实验跟踪 → 流水线 → CI/CD → 部署 → 监控 → LLMOps，正是生命周期在「开发—预生产—部署—监控—治理」五阶段上的逐段展开。

在下一节，我们进入生命周期「开发」阶段的第一步：**数据版本管理（DVC）与特征平台**——先回答那个最基础的问题：当时训练用的，到底是哪一份数据？这一问看起来简单，却是整个「可复现」大厦的第一块砖，也是《Introducing MLOps》生命周期闭环能否落地的第一道闸门。
