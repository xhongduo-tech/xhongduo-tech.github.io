## 为什么从流水线编排开始

数据有了版本、实验有了档案、模型有了注册表，接下来要把这些环节**串成一条自动运行的流水线**。如果每个环节还是靠工程师半夜手动点按钮、跑 `cron` 脚本，那么一次「数据更新 → 训练 → 评估 → 部署」就要消耗人工盯守数小时，还容易在凌晨三点出岔子。**机器学习流水线（ML pipeline）** 把数据获取、特征工程、训练、评估、部署定义成一组有依赖关系的任务；**编排（orchestration）** 负责按依赖关系调度这些任务、处理失败与重试、保证幂等与可观测。<span class="marginnote">「编排」与「工作流」两个词常被混用：编排强调「谁按什么顺序调谁、失败怎么办」，是控制面；工作流强调「整个任务的拓扑」，是数据面。本专题按业界惯例，以「编排」统称两者。</span>

还有一个更隐蔽的理由让编排成为刚需：**机器学习任务的不确定性**。一次训练可能跑十分钟，也可能因为资源排队跑六小时；可能一次成功，也可能在凌晨三点因节点抖动失败。如果这些任务靠「人盯着跑」，团队的时间就被无尽的等待吞噬。编排器把「启动、重试、失败通知、依赖关系」全部接管，让人从「操作员」变回「工程师」——这才是流水线编排真正的价值：把人从重复劳动中解放出来。

## 1 流水线的基础：有向无环图（DAG）

一切编排器的核心数据结构是 **DAG（Directed Acyclic Graph，有向无环图）**：每个节点是一个任务，每条边是「前驱完成后才能运行」的依赖。

以一次自动重训为例：

`ingest`（拉取新数据）→ `validate`（数据质量校验）→ `feature`（特征工程）→ `train`（训练）→ `evaluate`（评估）→ `register`（写入模型注册表）→ `deploy`（部署）。

其中 `validate` 失败时可以直接中止整条链——**上游的失败要能向下游传播，这是「无环」之外 DAG 的第二条铁律**。编排器据此决定哪些任务要重跑、哪些任务要跳过。

**辨析｜易错点：** 新手常把 DAG 的「无环」当成形式要求，其实它的意义在语义层：**如果任务 A 依赖任务 B、任务 B 又依赖任务 A，调度就无解**。在 ML 场景里，「训练依赖评估结果」和「评估依赖训练产物」是同一个环的两条边——正确做法是把「评估」拆成「先产指标、再判门控」两个阶段，让依赖变成单方向。

## 2 Airflow：以「调度」为核心的通用编排器

**Apache Airflow** 是最广泛使用的开源编排器，由 Airbnb 于 2014 年开源。它的设计围绕三个概念：

**DAG 文件即代码**：一个 DAG 就是一个 Python 文件，声明任务节点与依赖。DAG 文件本身进 Git，天然可审查、可回滚。

**任务由 Operator 承载**：每个节点是一个 operator——`PythonOperator` 执行 Python 函数，`BashOperator` 执行 shell 命令，`KubernetesPodOperator` 在 Kubernetes 里跑一个容器。ML 团队常把训练脚本容器化后，用 `KubernetesPodOperator` 跑在 GPU 集群上。<span class="marginnote">Airflow 的调度模型是「时间驱动」：`schedule_interval` 决定何时触发一次运行。它擅长「周期性任务」（每晚重训、每小时特征刷新），但不太擅长「事件驱动」的即时响应——后者通常交给事件流系统或专用编排器。</span>

**失败重试与 SLA**：每个任务可配置 `retries` 与 `retry_delay`，编排器自动重跑失败任务；还能声明 `sla`，任务超时未完成即触发告警。

Airflow 的优势是生态成熟、调度语义清晰；短板是它「会调容器，但不关心容器里跑的是不是模型」——模型特定的能力（实验跟踪、模型注册、漂移监控）需要外部工具补齐。

## 3 公式解析：重试如何把「单次不靠谱」变成「整体可靠」

编排器对抗失败的第一件武器是**自动重试**。它的收益可以用一条简单的概率公式刻画：

$$
P_{\text{final}} = 1 - (1-p)^{r+1}
$$

逐项拆解：

- **第一步，明确 $p$**：$p$ 是某个任务**单次运行成功**的概率。例如一个训练任务单次成功率是 0.8，即 $p = 0.8$。
- **第二步，理解 $(1-p)$**：这是单次运行**失败**的概率，即 0.2。
- **第三步，看懂指数 $(r+1)$**：$r$ 是允许重试的次数，加上首次尝试共 $r+1$ 次机会。各次尝试互相独立时，「全部失败」的概率是 $(1-p)^{r+1}$。
- **第四步，得到最终成功率**：$P_{\text{final}} = 1 - (1-p)^{r+1}$。代入 $p = 0.8,\ r = 3$，得 $1 - 0.2^4 = 1 - 0.0016 = 0.9984$——**四次机会把 80% 的成功率抬到 99.84%**。

这条式子的工程直觉：**编排器用「廉价的重跑」换「昂贵的守夜」**。但公式也提示了边界——若失败来自「代码 bug」而非「瞬时抖动」，重试不会提高成功率（各次不独立），此时该做的是修复与告警，而不是无限重试。<span class="marginnote">实战经验：重试次数设 2–3 次为宜，且要配置「重试间隔指数退避」。对「数据校验失败」这类确定性错误，重试是浪费资源；对「GPU 节点被抢占」这类瞬时错误，重试收益最大。区分二者是编排调优的第一课。</span>

## 4 Kubeflow：面向机器学习的 Kubernetes 原生编排

**Kubeflow** 是运行在 Kubernetes 之上的机器学习工具链。与 Airflow 的「调度一切任务」不同，Kubeflow 把机器学习生命周期的组件**深度绑定 Kubernetes**：训练任务跑成 K8s Job，推理服务用 K8s Service 暴露，GPU 由 K8s 调度。

Kubeflow 的核心是 **KFP（Kubeflow Pipelines）**：用 Python DSL 定义流水线，每个组件（component）是一个**自包含的容器镜像**，组件之间通过「产物 + 元数据」传递数据。KFP 还内置实验追踪、产物浏览与 `Artifact` 缓存——同一个组件输入相同则直接复用上次结果，省去重复计算。<span class="marginnote">KFP 的组件缓存与 DVC 的内容寻址殊途同归：都靠「输入内容相同 → 结果相同」跳过重复工作。区别是 DVC 管数据文件，KFP 管「组件输入输出」的产物缓存。</span>

**Airflow 还是 Kubeflow？** 这不是非此即彼。业界常见分层：**Airflow 当「总调度」，Kubeflow 当「模型专用执行环境」**——Airflow 的 DAG 里某个节点调用 Kubeflow 跑一次训练，两者各司其职。选型的核心问题只有一个：**调度对象是「通用任务」还是「机器学习工作负载」**。通用任务多（报表、数仓同步、ETL）选 Airflow；机器学习组件多、深度依赖 GPU 与 K8s，选 Kubeflow。

## 5 核心对比表：三大编排器一表看清

本主题以编排工程为主，用核心对比表替代额外公式解析。

| 维度 | Airflow | Kubeflow Pipelines | Argo Workflows |
| --- | --- | --- | --- |
| 定位 | 通用任务调度 | ML 专用、K8s 原生 | K8s 原生通用工作流 |
| 调度模型 | 时间驱动（cron 式） | 事件/按需驱动 | 事件/按需驱动 |
| 任务单元 | Operator（含 K8s Pod） | 容器组件（component） | 容器模板 |
| 模型能力 | 无（需外接） | 内置实验跟踪、产物缓存 | 无（通用） |
| 生态成熟度 | 极高、插件丰富 | 中、与 Kubeflow 全家桶绑定 | 中高、被 ArgoCD 家族带动 |
| 最佳场景 | 周期性 ML + 通用数据管道 | 深度 K8s/GPU 的模型训练链 | 云原生环境里的通用工作流 |

**辨析｜易错点：** 三个工具都叫「编排」，但能力边界不同。最常见的误选是「团队已用 Airflow，就把模型训练也塞进去」——可行，但要接受 Airflow 不管 GPU 调度、不管模型注册、不管漂移监控，这些要逐一外接。反向的误选是「一上来就上 Kubeflow 全家桶」，为一个季度跑一次的实验维护整套 K8s 基建，成本远高于收益。

## 6 编排的工程细节：幂等与可观测

一条能长期跑的流水线，除了 DAG 与重试，还要具备两个工程品质：

**幂等（idempotency）**：同一个任务重跑多次，结果必须一致、且不产生副作用堆积。举例：训练任务每次都要「清洗数据」——如果清洗逻辑是「往表里插入不重复的行」，用 `INSERT IF NOT EXISTS` 就是幂等，用普通 `INSERT` 就会越积越多。流水线里每一个任务都要回答同一个问题：**「我重跑一遍，会不会把系统搞坏？」** 不能回答的任务，要么改写为幂等，要么用「先删后写」的模式兜底。

**可观测（observability）**：任务失败时，第一反应不该是「翻日志」，而是「看面板」。成熟的编排体系会为每次运行记录：任务状态（成功/失败/重试中）、耗时、资源占用、产物地址，以及运行间的依赖图。这样一次失败能快速回答：**失败的是哪个任务、卡了多久、上游是什么、下游会不会受影响**。

**辨析｜易错点：** 幂等与重试是配套的——**只有幂等的任务才敢大胆重试**。反过来，非幂等任务在「重试」面前会放大灾难：一次失败重跑，重复插入了两批数据，下游模型被污染。所以编排的黄金法则是：先保幂等，再谈重试。

## 7 术语速查表

| 术语 | 一句话含义 | 关键词 |
| --- | --- | --- |
| DAG | 任务节点 + 依赖边的有向无环图 | 依赖单向、失败传播 |
| 编排 | 按依赖调度任务、处理失败与重试 | 控制面 |
| Airflow | 通用周期性调度器 | 时间驱动、Operator |
| Kubeflow KFP | ML 专用、K8s 原生的流水线 | 容器组件、产物缓存 |
| 幂等 | 同一任务重跑多次结果一致 | 先幂等、再重试 |
| gang scheduling | 整组任务一起调度或一起等待 | 防「少一张卡死局」 |
| 重试公式 | $P_{\text{final}} = 1 - (1-p)^{r+1}$ | 对确定性错误无效 |

## 8 小结

- **流水线编排**把生命周期各环节定义成 DAG 并自动调度，核心能力是**依赖管理、失败重试、幂等与可观测**。
- DAG 的「无环」在语义上等于「依赖单向」，循环依赖要用「拆分阶段」化解。
- 自动重试的收益公式 $P_{\text{final}} = 1 - (1-p)^{r+1}$
