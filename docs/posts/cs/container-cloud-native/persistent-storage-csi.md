## 为什么数据要「另立门户」

前几节课反复强调：**Pod 是可抛弃的**，容器里的可写层随时会丢。但现实世界有大量「丢了就完了」的数据——数据库的记录、消息队列的积压、模型的权重。持久化存储解决的就是：**让数据的生命周期独立于 Pod 的生命周期**。它是「无状态应用可抛弃」这一命题的另一半——正因为数据被搬到了外面，应用进程才能放心地被反复销毁重建。

## 1 卷：Pod 与数据的桥梁

**核心概念：卷（Volume）**：挂载进 Pod 的存储单元，生命周期与 Pod 相同（Pod 没了卷可能还在）。卷把「进程看到的文件路径」与「真实存储的位置」解耦：

- **emptyDir**：Pod 内共享的临时目录，Pod 删除即清空——给同 Pod 多容器交换数据用。
- **hostPath**：挂宿主机目录——仅测试用，生产有节点绑定问题。
- **网络存储**：真正重要的卷，来自存储系统（云盘、NFS、Ceph）——数据存在**集群之外**，Pod 没了、节点没了，数据还在。

判断卷用哪种，问一个问题：**数据跟谁活？** 跟 Pod 活 → emptyDir；跟宿主机活 → hostPath；跟集群活 → 网络存储。<span class="marginnote">容器 → 卷 → 存储系统的三层解耦，是「位置无关」哲学的具体化：应用不再关心数据在本地还是远端，只认一个挂载点。这与前面「后端服务可替换」「镜像内容寻址」是同一条主线。</span>

| 卷类型 | 生命周期 | 典型场景 |
| --- | --- | --- |
| `emptyDir` | 随 Pod | 同 Pod 容器间交换、缓存 |
| `hostPath` | 随节点 | 测试、访问宿主机文件 |
| 网络存储（PV） | 独立于节点 | 数据库、共享文件 |

卷的「挂载」还有一个容易被忽略的细节——**subPath 与挂载语义**：`subPath` 让你只把卷里的某个子目录挂进容器，避免多个容器把同一个卷根目录互相覆盖；而整卷挂载会「遮住」容器镜像里原本在该路径的内容。理解这点，很多「改了镜像没生效」的怪问题都能解释清楚。

顺带把「为什么不能把数据写进容器可写层」说透：容器镜像分层是**只读共享**的，每个容器自己的可写层随容器销毁而消失；即使节点还在，`docker cp` 这种恢复手段也无法规模化成运维流程。**可写层只适合「重建即重来」的临时状态**——真正的数据，必须越过容器层、挂在卷上，这就是「另立门户」的技术根源。

## 2 PV、PVC 与 StorageClass：把「存储」变成一门语言

Pod 不该直接指定「我要 AWS 的 gp3 盘、50GB」——那样 Pod 就和具体存储绑定死了。Kubernetes 用三个对象把「要什么」与「怎么提供」分开：

**PersistentVolume（PV）**：管理员提供的**一块具体存储**（云盘、NFS 卷），集群里的资源。
- **PersistentVolumeClaim（PVC）**：应用**声明**的存储需求——「我要 50GB，可读写多节点」。声明式思维第 N 次出现：不指定哪块盘，只描述需求。
- **StorageClass**：**动态供应**的配方——「要哪种盘（`gp3`/`ssd`/`nfs`）、多少 IOPS」。PVC 引用 StorageClass，由 provisioner 自动创建 PV 并绑定。

声明式 + 动态供应的效果：开发者写一个 PVC，集群自动准备好一块盘，Pod 挂载即用。**存储从「运维手工准备」变成了「按需自助申请」**——这与其他对象的声明式模型完全同构。

**辨析｜易错点：回收策略决定「释放后的命运」**。PVC 删除后，PV 的去向由 `persistentVolumeReclaimPolicy` 决定：`Retain`（保留，管理员手动处理）、`Delete`（删除底层存储，云盘类默认）、`Recycle`（已废弃）。把 `Delete` 当成默认认知，会让「以为 PV 还会回来」的人翻车——**数据安全第一条：先想清楚删了 PVC，底层数据会不会一起没**。

数值感受一下「动态供应的成本账」：一个 20 副本的微服务，若每副本都申请一块 100 Gi 云盘，按 gp3 计费每月就是一笔不小的开支；而把「工作负载」与「状态」拆开（无状态副本不挂盘，只有真正有状态的组件挂盘），账单能差出一个数量级。**存储成本是云账单里最容易被「顺手申请」撑大的一项**——声明式让申请变容易，也让人更容易忘记回收。

## 3 CSI：存储插件的通用接口

Kubernetes 不能认识全世界每一种存储（云盘、SAN、NFS、对象存储……）。答案是接口：**CSI（Container Storage Interface）**——存储厂商只要实现一组 gRPC 接口（`CreateVolume`、`DeleteVolume`、`Mount`、`Unmount`），就能无缝接入 Kubernetes。CSI 驱动部署为 DaemonSet/StatefulSet，对外是标准接口，对内是任意实现。<span class="marginnote">CSI 与 CRI（容器运行时接口）、CNI（网络接口）并称 Kubernetes 的「三驾马车」：<strong>插件化把生态的多样性变成了接口下的可选实现</strong>。这是分布式系统设计里的「适配器模式」在存储领域的落地。</span>

CSI 接口要保证的三件事：**幂等**（重复调用不产生副作用）、**可恢复**（失败后状态可查询）、**协调**（与快照、扩容、加密等操作协同）。存储驱动是生产事故的重灾区，所以接口规范被设计得极其保守。

选型时把需求对到具体卷：

| 需求 | 推荐 | 理由 |
| --- | --- | --- |
| 临时缓存 / 容器间共享 | `emptyDir` | 随 Pod 生灭，零成本 |
| 单副本数据库 | 云盘 PV（RWO） | 块存储低延迟，动态供应 |
| 多副本共享文件 | NFS / CephFS PV（RWX） | 文件系统天然支持多节点写 |
| 冷数据 / 备份 | 对象存储 + CSI 驱动 | 低成本、可跨集群 |

**选型的核心问题是「谁写、怎么写、多快、多贵」**——回答完这四问，卷类型基本就定了。

## 4 公式解析：持久化的绑定关系

存储的绑定可以用一个简洁的关系式描述：

$$
\text{Bound}(PV, PVC) \iff \text{capacity}(PV) \ge \text{request}(PVC) \land \text{mode}(PV) \supseteq \text{mode}(PVC)
$$

- $\text{capacity}(PV) \ge \text{request}(PVC)$：PV 容量要覆盖 PVC 的请求。
- $\text{mode}(PV) \supseteq \text{mode}(PVC)$：PV 的访问模式要兼容 PVC 要求的模式。
- 绑定后 PVC 与 PV 一对一，Pod 通过 PVC 引用。

访问模式（access modes）是一张必须记牢的对照表：

| 模式 | 读写方式 | 典型场景 |
| --- | --- | --- |
| `ReadWriteOnce` (RWO) | 单节点读写 | 单副本数据库 |
| `ReadOnlyMany` (ROX) | 多节点只读 | 共享配置、模型权重 |
| `ReadWriteMany` (RWX) | 多节点读写 | 共享文件系统、日志聚合 |

三步拆解：

- **第一步，容量约束**：PVC 是「需求声明」，PV 是「供给」，绑定是**供需匹配**——这与其他任何资源的调度（CPU、内存）是同一套语言。
- **第二步，模式约束是硬性的**：访问模式由底层存储能力决定（块存储天然只能 RWO，文件系统才能 RWX）。**在创建 PVC 前想清楚访问模式，是数据库上云最常见的架构决策**。
- **第三步，动态 vs 静态**：静态供应 = 管理员先建好 PV 等 PVC 来绑；动态供应 = StorageClass 按 PVC 现场造。生产中几乎总是用动态供应。

绑定时序也值得写一遍：创建 PVC → 若声明了 `storageClassName`，provisioner 据此新建 PV 并绑定；若无动态供应，控制平面在已存在的 PV 里做容量与模式匹配 → 绑定成功后 PVC 进入 `Bound`，Pod 挂载即用。**整个过程中应用永远只写 PVC，从没见过 PV 的名字**——「需求与供给的分离」是它全部价值所在。

举个具体例子：PVC 声明 `50 Gi` 且模式 `RWO`。若集群里恰好有一个 80 Gi 的闲置 PV（`RWO`），它会匹配并绑定；若没有一个满足的 PV 但配置了动态 StorageClass，provisioner 会现造一块 50 Gi 的云盘并绑定。若 PVC 声明 `RWX` 而底层只有块存储，绑定会一直 `Pending`——**模式不匹配时，不是「排队等」，而是「永远等」**，这是排障时最容易被忽略的一环。<span class="marginnote">PVC 停留在 <code>Pending</code> 有两大典型原因：<strong>没有满足容量/模式的 PV</strong>，或 <strong>StorageClass 没有 provisioner</strong>。前者加盘，后者装 CSI 驱动——这两个方向一查，90% 的「挂不上盘」都能定位。</span>

## 5 有状态应用的配套：StatefulSet

「持久化 + 多副本」需要稳定身份：Pod 被重建后还要认领**同一块**数据。这就是 **StatefulSet** 的职责——它给 Pod 稳定名字（`db-0`、`db-1`）与**稳定的 PVC 绑定**（每个副本有自己的卷，重建后重新挂回）。配合分布式系统课里的分片模式，StatefulSet 是「数据库上 K8s」的基本骨架。

StatefulSet 与 **Headless Service**（`clusterIP: None`）是天生一对：Pod 得到 `db-0`、`db-1` 这样的稳定 DNS 名（`db-0.db.default.svc`），主从复制、分片定位都能「按名字」完成，而不是靠探测 IP。有状态应用的上云，本质是把「随机 IP + 易变名字」换成「稳定身份 + 稳定存储」——这正是 StatefulSet + Headless + PVC 三件套共同提供的。

**辨析｜易错点**：StatefulSet 的卷**不会**随 Pod 删除而自动删除——删除 StatefulSet 默认保留 PVC，这是有意设计（怕误删数据）。**清理数据要手动删 PVC**——新手删了 StatefulSet 以为数据清了，结果账单还在跑。

**补充｜延伸：数据保护**。持久化不等于「不会丢」——磁盘、可用区都可能故障。生产级的配套是**快照（snapshot）**与**备份**：CSI 快照 API 可以对 PV 打一致性快照，配合 Velero 之类的工具做整集群备份与灾难恢复。**「数据活下来」分两层：Pod 之外要活（持久化），机房之外还要能活（备份）**——后者往往被低估。

**补充｜延伸：容量扩容与 Operator**。多数 CSI 驱动支持 `allowVolumeExpansion`——PVC 的请求容量可以事后调大，PV 随之在线扩容，文件系统自动扩展。这是「存储声明式」的又一处落地：改一个字段，底层自动跟上。但**只能扩不能缩**（缩容破坏文件系统安全），所以规划容量时留余量、用监控观察水位。再往外一层，StatefulSet 只提供了「稳定身份 + 稳定卷」的骨架，真正复杂的运维逻辑（备份、扩容、主从切换、故障修复）由 **Operator** 编码进 Kubernetes——它本身就是控制器，watch 集群状态、按自定义逻辑调谐；数据库、消息队列、缓存都有成熟的官方 Operator，越是有状态、越需要自动化，它的价值越大。

## 6 小结

- **卷**把「进程看到的路径」与「真实存储」解耦；数据跟谁活就选哪种卷。
- **PV/PVC/StorageClass** 把「要什么」「怎么提供」分离，动态供应让存储自助化。
- **CSI** 是存储插件的统一接口，幂等、可恢复、可协调是其底线。
- 绑定关系：容量与访问模式都要匹配；访问模式由底层存储决定，模式不匹配会永久 `Pending`。
- **StatefulSet** 提供稳定身份与稳定卷绑定；删它**不删卷**，清理要手动删 PVC。
- 持久化之上还要有**快照与备份**，才能扛住机房级故障。
- `subPath` 与整卷挂载语义不同，理解了它才能解释「改了镜像没生效」的怪问题；回收策略决定 PVC 删除后底层数据去留。
- **扩容只能增不能缩**：规划留余量、监控看水位，比事后精算更实际；存储成本是云账单里最容易被「顺手申请」撑大的一项——无状态副本不挂盘、只给真正有状态的组件挂盘，账单能差一个数量级。
- StatefulSet + Headless Service + PVC 三件套提供「稳定身份 + 稳定存储」，是数据库上云的基本骨架；Operator 再把运维逻辑也自动化。
