## 为什么从 channel 开始

goroutine 让并发「分得开」，但分开了还得「合得上」——多个 goroutine 之间如何传数据、如何同步？Go 的答案是 **channel（通道）**：一种类型化的、能安全传值的管道。发送与接收在 channel 上完成，同时解决「传数据」与「同步时机」两个问题。<span class="marginnote">对标《Go语言圣经》第8章：第8.4节「通道」是整个并发模型的心脏。channel 的命名源自 CSP（通信顺序进程）模型——Hoare 在 1978 年提出的并发范式，Go 把它实现成语言原语。这也是「通过通信共享内存，而非共享内存来通信」的落点。</span>

channel 在本专题的位置：它是 goroutine 之间**唯一的推荐通信方式**，与下一节 select、后面的数据竞争紧密相连。理解「channel 是同步点」这一点，是理解 Go 并发正确性的钥匙。

## 1 channel 基础：类型化的管道

**channel（通道）** 用 `chan` 关键字声明，是「同类型值的先进先出队列」。创建用内建函数 `make`：

```go
ch := make(chan int)          // 无缓冲通道
ch2 := make(chan string, 3)   // 容量 3 的有缓冲通道
```

三种基本操作——发送、接收、关闭：

```go
ch <- 42        // 发送（send）：把 42 送入通道
x := <-ch       // 接收（receive）：从通道取一个值
close(ch)       // 关闭（close）：不再有值可送
```

**核心概念：channel 是「同步 + 传值」的组合体。** 发送与接收不只是「放数据」，它们还是同步事件——这正是无缓冲 channel 的精髓。

**容易忽略的规则：**

- channel 是**类型**：`chan int` 与 `chan string` 是不同类型，不能互用。
- 零值是 `nil` channel：`var ch chan int` 是 `nil`，对它发送或接收会**永久阻塞**。
- channel 可以比较：两个 channel 相同当且仅当是同一个（同一引用）。

## 2 无缓冲 channel：同步点

**无缓冲（unbuffered）channel** 没有容量。发送与接收是**配对进行**的：一次发送会阻塞，直到有接收者取走；一次接收会阻塞，直到有发送者送入。

```go
func main() {
	ch := make(chan int)

	go func() {
		ch <- 42        // 发送：阻塞，直到 main 接收
	}()

	x := <-ch           // 接收：与上面的发送同步配对
	fmt.Println(x)      // 42
}
```

**重点：** 无缓冲 channel 是**同步机制**。`ch <- 42` 与 `<-ch` 必须同时就位，两边的 goroutine 在这一刻「握手」。这种同步性让它成为「goroutine 之间时序控制」的工具——上一节 goroutine 的「完成信号 `done <- struct{}{}`」正是靠这个特性。

**为什么 `struct{}` 常用于信号通道？** 空结构体不占任何内存，纯粹当「事件的标记」用，语义是「我完成了」，不传任何值。

**辨析｜易错点：** 无缓冲 channel 发送方会**永久阻塞**，如果没有接收者。经典的死锁：

```go
ch := make(chan int)
ch <- 42    // 永久阻塞：没有人接收！程序死锁
```

编译器甚至能静态检测部分此类死锁。记住：**无缓冲 channel 的发送需要「同时有人在接收」**。

## 3 有缓冲 channel：异步队列

**有缓冲（buffered）channel** 有容量，可以装下若干个值再消费。发送只在**缓冲区满**时阻塞，接收只在**缓冲区空**时阻塞。

```go
ch := make(chan int, 2)
ch <- 1    // 不阻塞：缓冲区空
ch <- 2    // 不阻塞：还有 1 个空位
// ch <- 3 // 阻塞：缓冲区已满（2 个），无接收者
```

**核心对比：无缓冲 vs 有缓冲**

| 维度 | 无缓冲 | 有缓冲 |
| --- | --- | --- |
| 容量 | 0 | `make(chan T, n)` 指定 |
| 发送 | 必须等接收者（同步） | 缓冲未满即可（异步） |
| 接收 | 必须等发送者 | 缓冲非空即可 |
| 语义 | 同步、握手 | 缓冲、解耦 |
| 典型用途 | 同步信号 | 工作队列、限流 |

有缓冲 channel 适合「生产者—消费者」模式：生产者快速填充缓冲，消费者按自己的节奏消费，二者互不阻塞太长时间。**但要小心缓冲并不能「无限解耦」**——生产者若远快于消费者，缓冲区很快填满，生产者依旧阻塞。

**易错点：** 有缓冲 channel 的容量是「预先分配的量」，不是「吞吐的保证」。给多大缓冲、要不要缓冲，取决于「同步语义是否需要」——需要严格的先后保证就用无缓冲，需要解耦就用有缓冲。

## 4 单向通道：方向的声明

channel 可以声明为**单向**——只读或只写。这是 Go 类型系统的细化，用于在函数参数中表达「我只能发」或「我只能收」的意图：

```go
// 只能发送（写入）的通道
func sendOnly(ch chan<- int) {
	ch <- 42
}

// 只能接收（读取）的通道
func recvOnly(ch <-chan int) {
	x := <-ch
	fmt.Println(x)
}
```

**转换规则：** 双向通道**可以**赋给单向通道（自动转换），反向不行——`chan int` 能传给 `chan<- int` 参数，但 `chan<- int` 不能当 `chan int` 用。

```go
ch := make(chan int)
go sendOnly(ch)   // OK：chan int 自动转为 chan<- int
recvOnly(ch)      // OK
```

**重点：** 单向通道不是「新的通道类型」，而是「对既有通道视角的收窄」——它把「既能发又能收」的通道，在某处限定为「只能发」或「只能收」，从类型层面防止误用。这与接口的思想一脉相承：**限制能力 = 减少错误**。

**关闭（close）** 是发送方的权利：只有发送方应关闭通道。关闭后：

- 发送会 panic（向已关闭通道发送）。
- 接收会一直取走已缓冲的值，取完后返回零值。
- 判断通道是否关闭：`v, ok := <-ch`，`ok` 为 false 表示已关闭且已取空。

## 5 公式解析：channel 的容量守恒

**channel 的操作可以抽象成容量守恒**：有缓冲 channel 在任何时刻

$$
0 \le \text{len}(ch) \le \text{cap}(ch)
$$

其中 `len(ch)` 是当前缓冲的元素数，`cap(ch)` 是容量。发送增加 `len`，接收减少 `len`。以 `make(chan int, 2)` 为例：

- **第一步，初始态**：`len=0`，`cap=2`，缓冲区空闲 2 个。
- **第二步，两次发送**：`len=2`，`cap=2`，缓冲区满——第三次发送阻塞。
- **第三步，一次接收**：`len=1`，可再次发送。
- **第四步，守恒解释**：`len` 永远夹在 `0` 与 `cap` 之间，这正是「满则阻塞、空则阻塞」的数值表述。

这条不等式把「channel 何时阻塞」翻译成了算术：发送前检查 `len == cap`（满），接收前检查 `len == 0`（空）。对无缓冲 channel，`cap=0`，所以 `len` 恒为 0——发送和接收永远直接握手，不经过缓冲。**一条公式同时解释了两类 channel**。

## 6 小结

- **channel** 是类型化的 FIFO 管道：发送 `ch <- v`、接收 `v := <-ch`、关闭 `close(ch)`。
- 无缓冲 channel 是**同步点**：发送与接收必须配对，双方在此握手。
- 有缓冲 channel 提供**异步解耦**：发送满则阻塞、接收空则阻塞。
- 单向通道 `chan<-`（只写）、`<-chan`（只读）收窄视角，双向可自动转单向。
- 只有发送方关闭通道；向已关闭通道发送会 panic。
- `v, ok := <-ch` 用 `ok` 判断通道是否已关闭。
