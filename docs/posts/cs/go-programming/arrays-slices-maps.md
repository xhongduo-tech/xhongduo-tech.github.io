## 为什么从复合数据类型开始

单个变量只能存一个数，真实程序需要成批的数据：一批分数、一行文本、一张查询表。Go 用三类**复合数据类型（composite types）**承担这个任务：**数组（array）**是定长序列，**slice** 是可变长度的「数组切片」，**map** 是键值映射。三者的关系层层递进——slice 建在数组之上，map 是哈希表的语言级封装。<span class="marginnote">对标《Go语言圣经》第4章：这一章先讲数组，再讲 slice，最后讲 map，顺序本身就是设计逻辑——slice 是「对数组的窗口」，理解了底层数组，slice 的容量、扩容、共享语义才有根。</span>

这三类容器在本专题的位置很关键：后续的《结构体与 JSON 序列化》讲「如何把零散数据打包」，而本篇讲「如何把同质数据成批存放」。更重要的是，slice 的引用语义是理解 Go 内存模型的第一站——它直接牵连第2篇的 goroutine 与数据竞争。

## 1 数组：定长的值

**数组（array）** 是定长的、同类型元素的序列，长度是类型的一部分。<span class="marginnote">与 C 相同的是数组是「值」，与 C 不同的是 Go 的数组长度写死在类型里：`[3]int` 与 `[4]int` 是<strong>不同</strong>的类型，不能互相赋值。这也是为什么 Go 里几乎不直接用数组、而用 slice。</span>

```go
var a [3]int              // 全零：[0 0 0]
a[0] = 1
fmt.Println(a[2])         // 0

b := [3]int{1, 2, 3}      // 复合字面量初始化
c := [...]int{1, 2, 3}    // 用 ... 让编译器数长度
```

**重点：** 数组是**值类型**——把它赋给另一个变量，会**拷贝整个数组**，而不是共享。`b := a` 之后改 `b`，`a` 不受影响。

```go
a := [3]int{1, 2, 3}
b := a
b[0] = 100
fmt.Println(a[0])   // 1：a 未被改动，值拷贝
```

这一语义与 C 相同、与 Python 的 list（引用）不同，是 Go 初学者的第一处「反直觉」。数组值拷贝意味着大数组作为函数参数会整份复制，所以实际代码几乎不用数组做参数，而是用 slice。

## 2 slice：数组上的可变窗口

**slice** 是变长序列，由三部分组成：**指针**（指向底层数组某元素）、**长度（len）**、**容量（cap）**。它不拥有数据，只是对底层数组的一段「视图」。<span class="marginnote">slice 是「指针+长度+容量」的三元组，这在《Go语言圣经》第4.2节用一张内存图讲得极透。记住：slice 头本身很小（24 字节），复制 slice 头很便宜，但多个 slice 可能共享同一个底层数组。</span>

```go
a := [...]int{0, 1, 2, 3, 4, 5}
s := a[2:5]        // s 指向 a[2:5] = [2 3 4]
fmt.Println(s)     // [2 3 4]
fmt.Println(len(s), cap(s))   // 3 4
```

**切片表达式 `a[low:high]`** 生成新 slice，包含 `a[low]` 到 `a[high-1]`。容量从 `low` 数到底层数组末尾。

**核心对比：数组 vs slice**

| 维度 | 数组 | slice |
| --- | --- | --- |
| 长度 | 定长，类型的一部分 | 变长 |
| 赋值 | 值拷贝整个数组 | 复制 slice 头，共享底层数组 |
| 传参 | 整份拷贝（昂贵） | 拷贝 slice 头（便宜） |
| 扩容 | 不支持 | `append` 自动扩容 |
| 比较 | `==` 可比较 | 不能 `==`，只能与 `nil` 比 |

**辨析｜易错点：** slice 的共享语义是双刃剑。修改共享的底层数组，所有指向它的 slice 都会「看见」变化：

```go
s1 := []int{1, 2, 3, 4, 5}
s2 := s1[1:3]      // s2 = [2 3]
s2[0] = 99         // 修改底层数组 a[1]
fmt.Println(s1)    // [1 99 3 4 5]：s1 也变了！
```

解决之道是**复制**：`s2 := append([]int(nil), s1[1:3]...)` 或 `copy`。需要独立数据时务必显式复制，这是 slice 共享语义下最实用的纪律。

## 3 append：扩容与增长策略

**`append`** 在 slice 末尾追加元素，返回新 slice。当容量不够时，它分配一块更大的底层数组并拷贝旧元素：

```go
var s []int
s = append(s, 1, 2, 3)     // s = [1 2 3]
s = append(s, 4)           // 容量不够时自动扩容
```

`append` 的扩容策略在《Go语言圣经》中是「通常翻倍，但并非保证」。扩容意味着**分配新数组 + 拷贝旧元素**，这在大量追加时是性能热点——因此预先用 `make([]int, 0, 100)` 声明容量是常见优化。

**要点：** `append` 的返回值必须重新赋给变量（`s = append(s, x)`）。这是因为容量不足时底层数组变了，旧 slice 头仍指向旧数组——不用返回值就是「往旧数组上追加」，可能静默丢数据。这个「总是用返回值」的习惯，能避开一大类难以察觉的 bug。

## 4 map：键值映射

**map** 是键到值的映射，底层是哈希表。<span class="marginnote">对照第一级《基础数学》的函数概念：map 正是「定义域（键）到值域（值）」的有限实现；而 Python 的 dict、C++ 的 unordered_map 都是同一思想的工程化。理解 map 是哈希表，就理解了它的 O(1) 平均查找与无序遍历。</span>

```go
ages := map[string]int{
	"alice": 31,
	"bob":   34,
}
ages["carol"] = 32        // 新增或更新

v, ok := ages["alice"]    // 双返回值：值 + 是否存在
if ok {
	fmt.Println(v)
}
```

**四个关键操作：**

| 操作 | 写法 | 说明 |
| --- | --- | --- |
| 插入/更新 | `m[k] = v` | 键不存在则新增 |
| 查询 | `v := m[k]` | 键不存在返回零值 |
| 查询+存在性 | `v, ok := m[k]` | `ok` 为 true 表示存在 |
| 删除 | `delete(m, k)` | 键不存在也无害 |

**辨析｜易错点：** map 的查询有一个陷阱——`v := m[k]` 在键不存在时返回**零值**，无法区分「值是 0」与「键不存在」。要区分，必须用 `v, ok := m[k]` 双返回值。另一个纪律：**map 不是并发安全的**，多个 goroutine 同时读写会数据竞争——这将在第2篇《数据竞争与竞态检测》与《sync 包》中系统解决。

## 5 公式解析：slice 容量与内存地址

slice 的寻址可以用一条「指针 + 偏移」公式概括：

$$
\text{slice} = (\text{ptr},\ \text{len},\ \text{cap}), \qquad
a[i] \iff *(\text{ptr} + i)
$$

对 `s := a[2:5]`（`a` 是 `[6]int`）：

- **第一步，定位指针**：`ptr = &a[2]`，指向底层数组下标 2 的元素。
- **第二步，计算长度**：`len = 5 - 2 = 3`，表示可访问 `a[2]`、`a[3]`、`a[4]`。
- **第三步，计算容量**：`cap = 6 - 2 = 4`，表示不需要重新分配就最多能扩到下标 5。
- **第四步，越界检查**：下标 `i` 合法当且仅当 `0 ≤ i < len`；`cap` 只约束「还能 append 到哪」。

这条公式解释了为什么 slice 的切取、扩容、越界行为都是「算术可预测」的：一切都在指针与偏移的语言里。理解它，也就理解了为什么 `a[i:j:k]`（三索引切片）可以精确控制容量——`cap = k - i`。

## 6 小结

- 数组是**定长的值类型**，`[3]int` 与 `[4]int` 是不同类型；赋值整份拷贝。
- slice 是「指针 + 长度 + 容量」的窗口，**共享底层数组**，复制 slice 头很便宜。
- `append` 在容量不足时自动扩容并返回新 slice——**务必用返回值**。
- map 是哈希表：查询键不存在返回零值，用 `v, ok := m[k]` 区分。
- map 非并发安全；共享底层数组时需显式 `copy` 以获得独立数据。
- 三类容器的选型：定长用数组、变长序列用 slice、键值映射用 map。
