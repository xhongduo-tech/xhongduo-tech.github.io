## 为什么 CPU 虚拟化是整个专题的地基

一台「虚拟的机器」最核心的部件是 CPU。把客户 OS 想象成一位以为自己在驾驶飞机的飞行员——它要执行特权指令、改页表、开关中断，
而这些动作在虚拟化世界里都必须由 VMM 替它把关。**CPU 虚拟化解决的就是「客户 OS 的特权操作如何既被允许、又被拦截」**。
这一节讲透教科书正解——陷入模拟，以及它为什么在 x86 上彻底失灵，为下一节的内存虚拟化与再下一节的硬件辅助虚拟化埋下伏笔。

## 1 敏感指令与特权指令：可虚拟化的钥匙

先建立两个概念。一台机器的指令里有两类特殊指令：

**特权指令（privileged instruction）**：只在最高特权级（如 x86 的 ring 0）执行、
在用户态执行会触发陷阱的指令——如加载页表基址 `MOV CR3`、`HLT`、开关中断。

**敏感指令（sensitive instruction）**：行为「依赖特权级」或「暴露特权状态」的指令。判断标准是：
它的行为（效果或产生的状态）会因运行特权级不同而改变。

两者的关系是虚拟化的钥匙，因为**虚拟化的基本套路——陷入模拟——要求「客户 OS 试图执行的敏感指令，必须落入 VMM 手里」**。

**陷入模拟（trap-and-emulate）**：让客户 OS 在比 ring 0 更低的特权级运行；当它执行特权指令时，
CPU 因权限不足自动陷入（trap）VMM；VMM 模拟这条指令的效果（代替客户执行、或修正结果），再让客户 OS 接着往下跑。

## 2 Popek-Goldberg 定理：可虚拟化的充要条件

1974 年，Popek 与 Goldberg 把上面的直觉严格化，给出系统虚拟化的充要条件：

**一台传统第三代计算机是可虚拟化的，当且仅当它的敏感指令集合是特权指令集合的子集。**

拆开读：

- **必要性**：如果存在一条敏感指令不是特权指令——它在用户态执行时不会陷入——那么陷入模拟就没法拦截它，等价性被破坏，虚拟化不可能正确。
- **充分性**：如果所有敏感指令都是特权指令，那么陷入模拟就能保证「敏感操作一律落入 VMM」，等价性、资源控制、效率三性质同时成立。

这条定理一锤定音：**可虚拟化是机器的属性，不是软件的技巧**。IBM 的 S/370 天然可虚拟化，所以 VM/370 
能用纯粹的陷入模拟跑得又快又稳；而 x86 在 2005 年之前不是一台可虚拟化的机器。

## 3 x86 的麻烦：非虚拟化的 17 条指令

x86 设计于 1978 年，从未考虑过虚拟化。后来人们发现，x86 
存在**敏感但不特权**的指令——它们在用户态执行时**不会陷入**，却会暴露特权状态、破坏虚拟机的隔离。经典清单包括：

- `SGDT / SIDT / SLDT`：在用户态读取全局描述符表、中断描述符表、局部描述符表的基址。客户 OS 可以据此推断 VMM 的真实内存布局，甚至算出 VMM 自身的位置。
- `PUSHF / POPF`：在用户态读写标志寄存器。客户 OS 可以用它们读取中断标志 `IF`——在虚拟化环境里，它看到的 IF 与真实硬件不一致，暴露出「我在虚拟机里」。
- 段寄存器相关的某些操作、`VERR/VWERR` 等验证指令，也属此类。

这类指令被统称为 **x86 的非虚拟化指令（non-virtualizable instructions）**，
是硬件辅助虚拟化（VT-x）出现之前 x86 虚拟化的头号障碍。<span class="marginnote">为什么说「暴露虚拟机身份」是问题？很多闭源软件当年用这类指令做「反虚拟机检测」——比如游戏反作弊、DRM 与恶意软件。虚拟化的等价性要求客户程序无法可靠区分真机与虚机，这些指令恰恰撕开了这个口子。</span>

这段历史有个值得记住的细节：这些问题指令大多出现在**实模式（real mode）遗留下的老指令**上——x86 为了向后兼容 
1978 年的 8086，把一堆「在用户态其实不该出现」的指令保留成了敏感而非特权。**兼容包袱是 x86 不可虚拟化的根本原因**，
而这正是后来硬件虚拟化扩展要专门补课的对象。

## 4 公式解析：陷入一次要花多少钱

陷入模拟的性能瓶颈，在「陷入」本身。设客户程序执行一条指令 $I$，其原生执行耗时为 $t$。在虚拟化环境下，若 $I$ 是敏感指令，总耗时变为：

$$
T_{\text{sim}} = t + t_{\text{trap}} + t_{\text{emulate}} + 
t_{\text{resume}}
$$

拆三步：

- **第一步，$t_{\text{trap}} + t_{\text{resume}}$ 是模式切换的固定税**：从客户机模式切到 VMM、保存现场，再从 VMM 切回客户机、恢复现场。早期系统一次切换可上千周期，是纯粹的开销。
- **第二步，$t_{\text{emulate}}$ 是模拟指令的软件成本**：VMM 要解码这条指令、判断语义、代为执行，等价于解释一条指令，开销远大于原生 $t$。
- **第三步，总成本的量级**：一条原生 1–2 周期的指令，被陷入模拟后可能变成数百周期。**所以陷入模拟只适合「敏感指令比例极低」的工作负载**——这正是 Popek-Goldberg 定理中「效率」性质的物理含义：$f$（直接执行比例）必须接近 1。

这也是为什么 CPU 设计者后来引入专门的虚拟化模式（VT-x 的 VMX 模式、VM entry/exit）来压低 $t_{\text{trap}}+t_{\text{resume}}$——那是硬件辅助虚拟化一节的正文。

**辨析｜易错点：** 「陷入模拟」与「二进制翻译」常被混为一谈。陷入模拟靠**硬件机制**捕获特权指令——客户 OS 原样执行，
指令碰到权限墙自动弹进 VMM；二进制翻译靠**软件改写**——VMM 预先翻译指令流，把敏感指令直接替换成对 VMM 的调用。
一个是「让 CPU 去拦」，一个是「改掉指令再去跑」。VT-x 出现后，主流路线回到陷入模拟（有硬件撑腰）；之前 VMware 
靠的是二进制翻译。

## 6 没有陷入怎么办：x86 虚拟化的三条出路

在 VT-x 诞生前，要在 x86 上做虚拟化，工程师们有三条路：

**二进制翻译**：VMware 的答案。用翻译器把客户指令流改写，敏感指令在翻译时就变成对 VMM 的调用，从根上绕开「不陷入」
的问题。<span class="marginnote">代价是翻译与缓存管理的复杂度，以及必须维护客户 OS 对「真实硬件」的感知一致性。详见《二进制翻译与动态翻译》。</span>

**半虚拟化**：Xen 的答案。干脆修改客户 OS——把敏感指令全部换成对 VMM 的显式调用（hypercall）。不依赖陷入，
性能好，但要改操作系统。半虚拟化在内存与 I/O 领域至今仍有巨大价值，见《半虚拟化与硬件内存虚拟化》与《I/O 虚拟化》。

**硬件辅助**：Intel 与 AMD 的答案。改变 CPU 本身——加入一个「客户机模式」，让 x86 
的敏感指令在这种模式下全部陷入。VT-x 于 2005 年落地，x86 终于成为一台可虚拟化的机器，详见《硬件辅助虚拟化 
Intel VT-x》。

把三条路放在一起还能看到一个清晰的工程规律：**当「让硬件符合理论」太贵时，就「让软件绕开硬件」；当「绕开」的成本积累到不可接受时，再回头改造硬件**。
二进制翻译是前者（绕），VT-x 是后者（改）。虚拟化四十年的演进，就是在「软件聪明」与「硬件配合」之间来回拨动的钟摆。

这条规律放在更远处也成立。CPU 虚拟化里「软件先绕、硬件后补」的剧本，在 GPU 虚拟化、
网络虚拟化（软件定义网络之后又出现智能网卡）、以及存储虚拟化（软件 RAID 之后又出现硬件控制器）里一再重演。
**读虚拟化史最值钱的一课，就是记住这个钟摆：当软件复杂到失控，下一个机会永远属于硬件；当硬件固化到僵化，下一个机会永远属于软件。**

## 7 小结

- **特权指令**只在 ring 0 执行、用户态会陷入；**敏感指令**行为依赖特权级或暴露特权状态。
- **陷入模拟**：客户 OS 降权运行，特权指令触发陷阱落入 VMM，VMM 模拟后交回控制权。
- **Popek-Goldberg 定理**：可虚拟化 ⟺ 敏感指令 ⊆ 特权指令。可虚拟化是机器属性，不是软件技巧。
- **x86 的 17 条非虚拟化指令**（`SGDT/SIDT/SLDT`、`PUSHF/POPF` 等）敏感但不特权，在用户态不陷入，破坏了虚拟化的等价性。
- 陷入成本模型 $T_{\text{sim}} = t + t_{\text{trap}} + t_{\text{emulate}} + t_{\text{resume}}$：模式切换是固定税，模拟指令是软件成本。
- x86 的三条出路：**二进制翻译**（VMware）、**半虚拟化**（Xen）、**硬件辅助**（VT-x）。
