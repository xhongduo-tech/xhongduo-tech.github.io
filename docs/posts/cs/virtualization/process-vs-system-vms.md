## 为什么单独开一节讲两种类型

上一节给出了分类的骨架：进程虚拟机与系统虚拟机。但「知道分类」和「能设计出分类里的每种方案」是两回事。
这一节把两种虚拟机各自拆开——它们内部由哪些部件组成、各自面临什么核心难题、历史上哪些系统是它们的最佳范例。布鲁克斯说「没有银弹」，
虚拟化正是如此：不存在一个万能的虚拟化方案，两类虚拟机解决的是两类完全不同的需求，用着两套完全不同的技术栈。

## 1 进程虚拟机：给单个程序造一个「家」

**进程虚拟机（process VM）**：在宿主操作系统上以一个普通进程的形式存在，为**单个客户程序**提供完整运行时环境。
客户程序不感知宿主 OS，它只「看得见」进程虚拟机提供的接口。

进程虚拟机有两条分支，按「客户与宿主的 ISA 是否相同」划分：

- **同 ISA 的进程虚拟机**：客户与宿主指令集相同，只需重定向系统调用与库。典型例子是 **Wine**——让 Windows 程序在 Linux 上跑。Wine 拦截 Windows 程序发起的 Win32 API 调用与系统调用，翻译成 Linux 的对等操作，CPU 指令本身不做任何翻译。
- **跨 ISA 的进程虚拟机**：客户与宿主指令集不同，需要把客户机指令翻译成宿主指令。历史名例包括 DEC 的 VEST（把 VAX 程序移植到 Alpha）与苹果的 Rosetta（PowerPC 程序在 x86 的 Mac 上运行，后来 x86 程序在 Apple Silicon 上运行）。**这类进程虚拟机靠的是二进制翻译，正是下一节的主题。**

无论哪条分支，进程虚拟机都要做三件事：**加载客户程序**（解析它的可执行文件格式，往往与宿主格式不同）、
**运行客户代码**（解释或翻译）、**提供运行时服务**（内存分配、系统调用路由、错误处理）。<span class="marginnote">JVM 与 .NET CLR 也属于进程虚拟机，但它们服务的「客户程序」是用高级语言编译出的字节码，而非原生二进制——这构成了特殊的一个分支「高级语言虚拟机」，见后续专节。</span>

把 Wine 与 Rosetta 并排看，就能看清同 ISA 与跨 ISA 的本质差异。Wine 面对的是「指令相同、系统不同」：
Windows 程序是 x86 机器码，Linux 也是 x86，指令直接执行；Wine 的战场全在系统调用层——把 Win32 
API 逐个翻译成 Linux 等价物，工作量是「一张大而全的映射表」。Rosetta 面对的是「指令与系统都不同」：
PowerPC 程序要先被翻译成 x86 指令，再处理系统调用差异——工作量多了一个「指令翻译」维度，靠的正是下一节的二进制翻译。

## 2 系统虚拟机：给整套操作系统造一台「机器」

**系统虚拟机（system VM）**：在物理硬件之上插入 VMM，VMM 之上同时运行多个完整的客户操作系统。每个客户 OS 
都坚信自己独占整台机器——它管理自己的「物理内存」、调度自己的「CPU」、驱动自己的「磁盘」，而这些其实都是 VMM 变出来的假象。

系统虚拟机同样按 ISA 异同分两支：

**同 ISA**：客户 OS 与硬件同构，VMM 用陷入模拟或硬件辅助让特权指令落进自己手里处理。绝大多数系统虚拟机属于这一类——VMware、KVM、VirtualBox。
- **跨 ISA**：历史上有 IBM 用 RISC 模拟旧主机、苹果用 x86 跑摩托罗拉时代的老系统等先例。这类系统虚拟机既要翻译指令，又要翻译设备，复杂度极高，今天已很少见。

系统虚拟机的核心挑战与进程虚拟机完全不同：**进程虚拟机只关心「一个程序的接口」，系统虚拟机要同时管住内存、中断、时钟、设备、DMA——它必须重建整台机器的硬件语义**。
VMware Workstation 之所以是划时代产品，就在于它把这种「重建」做到了可以在普通 PC 上量产。

## 3 系统虚拟机的早期巅峰：IBM VM/370

理解系统虚拟机最好的教材，是 1972 年的 IBM VM/370。它的架构教科书级地清晰：

- **CP（Control Program）** 是 VMM，直接跑在 S/370 硬件上，负责虚拟化 CPU、内存与设备。
- **CMS（Cambridge Monitor System）** 是一个极精简的单用户操作系统，作为 CP 之上的客户运行。每个用户一个 CMS 实例，一台大型机同时服务几十上百个会话。

为什么今天研究虚拟机还绕不开它？因为 VM/370 是**同 ISA、陷入模拟**路线的完美范例，而 S/370 
恰好是一台「可虚拟化」的机器——它的所有敏感指令都是特权指令，会陷入 CP。<span class="marginnote">对比之下，20 多年后 x86 的可虚拟化问题反而要倒逼 CPU 厂商改硬件（VT-x）或让软件绕道（二进制翻译），这正是《硬件辅助虚拟化 Intel VT-x》一节要讲的波折。</span>VM/370 还提出了一整套至今沿用的理念：内存超售（memory overcommit）、按需分配、客户机间隔离。

VM/370 的形态也被后人提炼成专有名词——**多道程序虚拟机（multiprogramming system VM）**：
一台硬件上同时运行多台系统虚拟机，每一台是一个完整的操作系统实例。这与今天云上一台宿主机跑几十台虚机是同一形态。
区别只在于规模与硬件：VM/370 面向分时共享的大型机，KVM 面向按需租赁的数据中心——**形态四十年前就定型了，变的只是价格与规模**。


## 4 Popek 与 Goldberg 的三性质

无论哪一类虚拟机，要成为合格的「副本」，都必须满足 1974 年 Popek 与 Goldberg 提出的三个性质：

**等价性（equivalence）**：客户程序在虚拟机中运行的行为，
应与在真实机器上运行一致——包括对外可观察的时序之外的全部语义。一个例外被允许：资源相关指令（如读取时钟）可以给出不同的值，
只要不影响正确性。

**资源控制（resource control）**：VMM 对资源有完全的控制权，任何客户程序都无法绕过 VMM 独占资源。
隔离由此而来：客户程序不能读写其他虚拟机或 VMM 自己的内存。

**效率（efficiency）**：绝大多数指令直接在真实硬件上执行，只有少数指令需要 VMM 软件介入。这是「高效」的定义，
也是把虚拟机与「纯模拟器」区分开的标准。

三性质合起来，给「什么是合格的虚拟机」立了界碑。**等价性管行为、资源控制管安全、效率管性能**——后面每一节的虚拟化技术，
都能在三个性质里找到它的职责归属。

## 5 公式解析：效率性质如何量化

效率性质要求「大多数指令直接执行」。设虚拟机运行中执行的指令总数为 $N$，其中直接在硬件上执行的指令数为 $N_{\text{direct}}$，需要陷入 VMM 处理的指令数为 $N_{\text{trap}}$，$N = N_{\text{direct}} + N_{\text{trap}}$。若单条指令在硬件上直接执行耗时 $t$，陷入并模拟耗时 $t + t_{\text{trap}}$，则总执行时间：

$$
T_{\text{vm}} = N_{\text{direct}} \cdot t + N_{\text{trap}} \cdot 
(t + t_{\text{trap}}) = N \cdot t \cdot \left[ 1 + (1 - f) \cdot 
\frac{t_{\text{trap}}}{t} \right]
$$

其中 $f = N_{\text{direct}} / N$ 是**直接执行比例**。拆三步：

- **第一步，看 $f$**：若 $f$ 接近 1（几乎所有指令直接执行），方括号里的第二项趋于 0，$T_{\text{vm}} \approx Nt$，即接近原生速度。效率性质要求的就是 $f$ 尽量接近 1。
- **第二步，看 $t_{\text{trap}}/t$**：陷入处理往往比指令本身贵几十到几百倍（一次模式切换可能上千周期）。所以哪怕 $1-f$ 只有千分之一，若陷入极慢，总开销依然可观。
- **第三步，两种压低开销的路线**：硬件辅助虚拟化压低 $t_{\text{trap}}$（一次陷入更快）；半虚拟化、批量操作压低 $1-f$（减少陷入次数）。两条路线贯穿本专题后半部分。

**辨析｜易错点：** 有人把「进程虚拟机」与「普通进程」画等号，把「系统虚拟机」与「多进程」画等号——这是错的。
普通进程共享一个内核与同一套内存管理，而进程虚拟机给客户程序一个**隔离的运行时**；系统虚拟机给客户 OS 
一整套**隔离的硬件视图**。区别在「隔离到什么程度」，不在「有几个程序在跑」。

## 6 两种类型的选型逻辑

什么时候用进程虚拟机，什么时候用系统虚拟机？一条实用判据：

- 要**跨平台跑一个应用**（Java 程序到处跑、Windows 游戏在 Linux 跑）→ 进程虚拟机，重量轻、起步快。
- 要**隔离运行一整套操作系统**（云上的租户、测试不同内核、跑一个不兼容的旧系统）→ 系统虚拟机，隔离彻底、但需要完整内核。
- 要**在裸机上榨出极致性能与密度**（数据中心）→ 系统虚拟机中的 VMM 直接跑在硬件上（Type 1），下一节讲 Hypervisor 类型时会展开。

选型背后其实是一条更本质的判断：**你需要的是「跨平台的兼容」还是「机器级的隔离」？** 进程虚拟机做兼容——同一个程序在不同的 
OS 与硬件上行为一致；系统虚拟机做隔离——不同的系统在同一块硬件上互不干扰。云计算的「多租户」需要的是后者，
所以云底层的隔离工具几乎全是系统虚拟机；而「一次编写到处运行」的软件工程需要的是前者，所以 JVM 的舞台在应用层。
两种需求永远同时存在，两种虚拟机也就永远并行发展。

值得提醒的是，两条路并不互斥：现代大语言模型服务的部署栈恰恰是**进程虚拟机（Python 运行时）→ 系统虚拟机（KVM 租户）→ 容器（部署单元）**三层叠加。
理解每层虚拟的是什么、隔离的是什么，是读懂这条工程栈的前提。

## 7 小结

- **进程虚拟机**虚拟单个程序的 **ABI/API** 世界，分同 ISA（Wine 式重定向）与跨 ISA（Rosetta、VEST 式翻译）两支。
- **系统虚拟机**虚拟整套操作系统的 **ISA** 世界，由 **VMM** 重建 CPU、内存、设备、中断的全部硬件语义。
- **IBM VM/370**（CP + CMS）是同 ISA 陷入模拟路线的教科书范例。
- **Popek & Goldberg 三性质**：等价性（行为）、资源控制（安全）、效率（性能），是评判一切虚拟机的标尺。
- 效率量化公式 $T_{\text{vm}} = Nt[1 + (1-f)\cdot t_{\text{trap}}/t]$：压低陷入时间或压低陷入频率，是所有虚拟化优化方向的两大出口。

在下一节，我们深入进程虚拟机与跨 ISA 系统虚拟机共同的底层技术——**二进制翻译**：一条客户指令，究竟是怎么变成宿主指令的。
