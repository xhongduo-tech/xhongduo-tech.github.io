## 为什么二进制翻译是虚拟化的「手艺人技术」

前面两节反复提到：跨 ISA 的虚拟机、以及 x86 上无法陷入模拟的敏感指令，都要靠**二进制翻译**解决。
如果说陷入模拟是虚拟化的「正道」，二进制翻译就是虚拟化的「手艺」——它不讲理论上的干净利落，靠的是工程上的聪明取舍。这一节讲清楚：
为什么纯解释太慢、静态翻译有死穴、动态翻译如何绕开这些死穴。

## 1 从解释到翻译：性能的三级跳

把客户机指令变成宿主机指令，有两种极端策略。

**解释（interpretation）**：每执行一条客户指令，就「读取出它、分析它、模拟它的行为」。
代价是灾难性的——每条指令都要经历取出、解码、模拟三个步骤，且**每次都重来一遍**。解释执行通常比原生慢 10–100 倍。
<span class="marginnote">纯解释在今天并未绝迹：它仍是嵌入式脚本、JVM 早期的兜底路径。但它绝不可能是高性能方案，只适合「跑起来就行」的场景。</span>

**翻译（translation）**：把客户机指令**先批量转换成宿主机指令，再执行转换结果**。翻译只做一次，
翻译产物可以反复执行。翻译又分两种：

- **静态二进制翻译（static binary translation）**：离线、整体翻译。程序还没跑，就把整个可执行文件翻完。听着完美，实则布满暗礁。
- **动态二进制翻译（dynamic binary translation，DBT）**：运行时、按需翻译。程序跑到哪，翻译到哪。

QEMU 的 TCG、苹果 Rosetta、VMware 在 VT-x 普及前的 CPU 虚拟化、Transmeta 的 
Crusoe 芯片——全是动态翻译的实例。

Transmeta Crusoe 是其中最激进的一个：它干脆把 x86 指令**交给一个翻译软件层（Code Morphing Software）**去解释成自家 VLIW 芯片的指令，
硬件本身只负责跑翻译产物。Crusoe 商业上不算成功，但它的理念——「用软件翻译把复杂 ISA 的兼容包袱甩给硬件」
——预演了后来整个 DBT 行业的手法。

## 2 静态翻译的三个死穴

静态翻译听起来最优：离线慢慢翻，怎么优化都行。但它有一个致命假设——**翻译器必须知道程序的所有代码在哪里**。真实世界偏偏破坏这个假设：

**代码发现问题（code discovery）**：程序的分支目标可以是运行时才计算出来的（间接跳转 `jmp eax`）、
代码可以藏在数据里被复制执行、还可以靠修改程序计数器的技巧跳进指令中间。翻译器不知道「哪里是代码的起点」，就可能漏翻、错翻。

**自修改代码（self-modifying code）**：程序运行时改写自己的指令——这在老汇编代码里是正经写法。
翻译产物是固定的，程序改了原代码，翻译器无从知晓。

**精确异常（precise exceptions）**：程序出异常时，调试器期望能精确定位「执行到哪一条指令」。
翻译后执行顺序被打乱，原指令与宿主指令不再一一对应，异常定位变得极其困难。

静态翻译在学术上优雅，在工程上几乎总是翻车。**真正的解法是动态翻译：把「知道代码在哪」的问题推迟到运行时，程序真正要执行哪段，才翻译哪段。**

## 3 动态二进制翻译：基本块 + 翻译缓存

**动态二进制翻译**的流程，以 QEMU 为例：

1. 程序执行到一段尚未翻译的客户机代码——**基本块（basic block）**，即一段没有分支进入、没有分支退出、执行完必然顺序走完的指令序列。
2. 翻译器把基本块转成中间表示，再从中间表示生成宿主指令，存入**翻译缓存（translation cache / code cache）**。

3. 宿主直接执行翻译产物。
4. 执行到基本块末尾的分支时，查翻译缓存：**这段代码翻译过吗？** 翻译过就直接跳进对应的宿主代码；没翻译过就再翻译一块。

关键在第三步之后：**同一段客户代码只要被翻译一次，就能被反复执行无数次**。
翻译的成本被摊薄了——这正是动态翻译能在实践中接近原生性能的根本原因。频繁执行的热点路径（循环体）
还可以被重新翻译成更激进的优化版本（追踪、trace 技术），让性能进一步逼近原生。

```
客户机代码                    翻译缓存（宿主代码）
┌──────────┐   翻译（一次）   ┌──────────────┐
│ 基本块 A  │ ──────────────▶ │ 宿主代码 A    │ ◀──── 执行 n 次
└──────────┘                 └──────────────┘
```

## 4 公式解析：翻译成本如何被摊薄

设一个基本块有 $k$ 条客户指令，翻译它一次花费 $C_{\text{trans}}$ 时间，翻译出的宿主代码执行一次花费 $t_{\text{exec}}$。若程序执行这个基本块 $n$ 次，动态翻译的总代价：

$$
T_{\text{DBT}} = C_{\text{trans}} + n \cdot t_{\text{exec}}
$$

而纯解释的总代价是：

$$
T_{\text{interp}} = n \cdot k \cdot c_{\text{interp}} \approx n 
\cdot k \cdot 10\,t_{\text{exec}}
$$

拆三步看：

- **第一步，看 $n$ 小时**：若基本块只执行一次（$n=1$），动态翻译反而不如解释——白白多付了 $C_{\text{trans}}$。所以**执行一次就退出的冷代码，翻译纯属浪费**。
- **第二步，看 $n$ 大时**：翻译成本 $C_{\text{trans}}$ 被 $n$ 次执行均摊，每个基本块的平均成本 $\approx t_{\text{exec}} + C_{\text{trans}}/n$，$n$ 越大越接近原生。**动态翻译赌的就是：程序 90% 的时间花在 10% 的代码上（热点）。**
- **第三步，为什么解释输定了**：解释每次执行都要重新解码，常数 $c_{\text{interp}} \approx 10\,t_{\text{exec}}$ 甩不掉；翻译只付一次解码钱。只要热点代码执行次数够多，翻译必然胜出。

这就是为什么动态翻译是今天所有高性能跨平台方案的唯一选择——QEMU、Rosetta、早期的 VMware 全部如此。

## 5 动态翻译的自我纠错能力

动态翻译还有一个静态翻译完全不具备的优势：**它能在运行时修正自己的错误判断**。
翻译器可以带着保守的假设翻译一段代码（比如「这个寄存器内容不变」），在代码前插入检查点；
执行时一旦发现假设被破坏（有指令改了那个寄存器），就丢弃这段翻译、用更保守的方式重翻。这种「先快速猜、错就重来」的策略，
在二进制翻译里叫 **speculation**（推测执行）。

**辨析｜易错点：** 动态二进制翻译（DBT）与 **JIT 编译（just-in-time compilation）** 
是两回事。JIT 的输入是**高级语言的字节码或中间表示**（如 Java 字节码），翻译器是语言运行时的一部分；DBT 
的输入是**另一套机器的原生二进制**，翻译器是虚拟化层。一个在「语言层」，一个在「机器层」。Rosetta 与 QEMU 
做的是后者。

## 6 二进制翻译与虚拟化：VMware 的历史性选择

回到 CPU 虚拟化：x86 有几十条敏感却不特权的指令（如读取段描述符的 `SGDT/SIDT`），它们不会陷入，
却在虚拟机里必须被拦截。2000 年代初期，VMware 无法依赖硬件（VT-x 尚未出现），于是用**动态二进制翻译**统一处理：
**普通指令直接执行，敏感指令在翻译时被改写为对 VMM 的调用**。VMware 的翻译器对每条指令打标签——「安全，直接执行」
「有风险，运行时检查」「必须改写成 VMM 调用」——在保证正确性的同时把性能损失压到最低。<span class="marginnote">这场「软件硬做」的工程让 VMware 撑过了没有硬件辅助的年代；等到 VT-x 出现，二进制翻译这条路线才逐渐让位于「陷入模拟 + 硬件模式」。完整故事见《硬件辅助虚拟化 Intel VT-x》一节。</span>

这套「给每条指令贴风险标签」的思想至今仍是动态翻译器的核心工程方法：标签越细，就能把越多指令放行给硬件直接执行，
陷入与改写的比例就越低，性能就越接近原生。VMware 把这项技术叫作 **DCE（direct cache execution）** 的变体，
实质就是在「正确性」与「放行量」之间做逐指令的精细权衡。

再补一个动态翻译与现代编译的家族谱系：**动态二进制翻译、JIT 编译、即时特化（runtime specialization）、追踪编译（tracing JIT）**，
共享同一个祖先——「程序跑起来之后，观察它的真实行为，再按观察结果优化」。浏览器 JavaScript 引擎的 V8、Python 
的 PyPy、LLVM 的 ORC JIT、以及今天大模型推理框架里把 Python 热点算子即时编译到 GPU 的 Triton，
全部属于这个家族。**「观察 → 优化 → 缓存优化结果」这条循环，是从二进制翻译到 AI 框架编译器的通用心法**。

## 7 小结

- **解释**每次重解码，慢 10–100 倍；**翻译**一次转换、反复执行，是高性能跨平台的唯一现实路径。
- **静态翻译**受制于代码发现、自修改代码、精确异常三个死穴，工程上几乎不可行。
- **动态二进制翻译**以**基本块**为单位、按需翻译、存入**翻译缓存**，热点代码重复受益。
- 成本模型 $T_{\text{DBT}} = C_{\text{trans}} + n\,t_{\text{exec}}$：翻译成本被执行次数摊薄，赌的是二八定律（10% 的代码跑 90% 的时间）。
- 动态翻译可**推测执行、自我纠错**；它不等于 JIT，一个是机器层翻译，一个是语言层编译。
- VMware 曾用动态翻译在无硬件辅助的 x86 上实现虚拟化，是「软件硬做」的巅峰案例。
