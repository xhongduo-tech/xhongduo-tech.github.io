## 为什么要把真实设备直接交给虚拟机

上一节我们看到：设备模拟靠软件「演硬件」，virtio 靠前后端配合，都绕不开 VMM 的参与。
而**设备直通**的思路截然不同——把真实物理设备直接交给虚拟机，让客户驱动直接操作硬件。它性能逼近裸机，但带来一个致命安全难题：
设备 DMA 时会写入它自己编的地址，如果这个地址落在别的虚拟机或 VMM 的内存里怎么办？这一节的主角是两样东西：**VT-d 的 IOMMU**（负责安全）与 **SR-IOV**（负责让一块网卡能分给很多台虚拟机）。


## 1 设备直通：性能巅峰与安全漏洞

**设备直通（device passthrough / device assignment）**：VMM 
把一块物理设备（或它的一个功能）整块划给某个虚拟机，客户 OS 直接加载该设备的原生驱动，直接操作设备寄存器、直接接收设备中断、
设备 DMA 直接访问客户内存。数据路径上**一行 VMM 代码都不跑**——这是它的性能近乎裸机的原因。

但直通立刻撞上一个安全问题：**DMA 是无地址检查的**。真实设备 DMA 写入的地址，是客户驱动填的「客户物理地址」。
在没有保护时，一块被直通的网卡完全可以 DMA 到宿主机的任意内存——把其他虚拟机、甚至 VMM 自己的内存读穿、写烂。
这等于把一个**不受约束的地址写入器**塞进了系统的心脏。

## 2 VT-d 与 IOMMU：给 DMA 上一道「影子页表」

Intel 的解法是 **VT-d（Virtualization Technology for Directed I/O）**，
核心是 **IOMMU（I/O 内存管理单元）**——一个专门管设备 DMA 地址翻译与隔离的硬件组件：

**DMA 地址重映射（DMA remapping）**：IOMMU 拦截所有设备 DMA，把设备提交的**客户物理地址（GPA）**翻译成**真实物理地址（HPA）**，
再去访问内存。客户驱动以为自己直接 DMA 到了自己的内存，实际经过 IOMMU 的翻译。<span class="marginnote">把 IOMMU 想成「DMA 世界的 MMU」：CPU 的内存访问由 MMU/EPT 翻译，设备的内存访问由 IOMMU 翻译——两条翻译路径，各配各的「影子页表」。</span>

**设备隔离（device isolation）**：每个设备/功能关联一张 IOMMU 页表，只允许它 DMA 
到自己虚拟机的那块内存。即便设备被攻破，它的 DMA 能力也被限定在一张白名单里——跨虚拟机的 DMA 攻击在硬件层面被掐死。

**中断重映射（interrupt remapping）**：设备的中断（MSI/MSI-X）也要经 IOMMU 校验与重定向，
防止一个虚拟机的设备把伪造中断注入其他虚拟机。

VT-d 让「把真实设备交给虚拟机」从危险动作变成了标准操作。AMD 的对等物叫 **AMD-Vi**（也叫 IOMMU）。
<span class="marginnote">IOMMU 的存在还顺手解决了一个兼容性细节：老设备的 DMA 地址位数往往有限（如 32 位），而现代机器内存远大于 4 GB。IOMMU 可以把设备提交的 32 位地址重映射到高位物理内存，让老设备在新机器上正常工作——这就是「IOMMU 的地址窗口」价值。</span>

为什么 CPU 的 MMU 保护不了 DMA？因为 **DMA 绕过了 CPU**：设备直接通过总线访问内存，不经过 MMU 
的页表翻译。传统上「内存访问必须过地址翻译」这个假设，只在 CPU 发起的访问上成立；设备发起的访问（DMA）此前完全是「裸奔」的。
IOMMU 就是把「地址翻译 + 权限检查」这一层，从 CPU 复制到了设备侧——**CPU 有 MMU，设备有 IOMMU，虚拟化的隔离才算闭环**。


## 3 SR-IOV：一块网卡拆成几十块

直通解决了性能，但代价是「一块设备只服务一台虚拟机」。数据中心里几十台虚拟机抢一块网卡，怎么办？**SR-IOV（Single Root I/O Virtualization）** 在设备内部把一块物理设备拆成多个「虚拟设备」：

- **物理功能（PF，Physical Function）**：设备自带的完整功能，由 VMM 管理（配置、固件、控制）。
- **虚拟功能（VF，Virtual Function）**：设备提供的一个精简功能实例，具有独立的配置空间、寄存器、DMA 地址空间与中断能力。一块高端网卡可拆出 16、64、128 甚至更多个 VF。

每个 VF 被直通给一台虚拟机，客户驱动直接操作 VF 的寄存器，**数据面的多路复用由硬件（设备内建交换逻辑）完成**，VMM 
完全不在数据路径上。共享一条物理链路，但每个 VF 看起来都像一块独立网卡。

![SR-IOV：物理功能拆成多个虚拟功能，分别直通给虚拟机](/images/virtualization/io-virtualization-sriov-vtd-1.svg)

SR-IOV 是 PCIe 规范定义的通用机制，网卡（Intel、Mellanox/NVIDIA、Broadcom）、NVMe 
控制器、GPU（NVIDIA 的 vGPU、SR-IOV GPU）都支持。

## 4 公式解析：直通到底快多少

设一次 I/O 操作的端到端耗时分解为「CPU 发指令 + 数据路径 + 中断」。设备模拟与直通的差异集中在 CPU 参与度上：

$$
T_{\text{io}} = T_{\text{cpu-path}} + T_{\text{device}} + T_{\text{irq}}
$$

三块逐一对比：

- **$T_{\text{cpu-path}}$（客户驱动发 I/O 的 CPU 路径）**：模拟时，每笔 I/O 客户驱动要陷入 VMM 模拟寄存器、走反弹缓冲拷贝；直通时，客户驱动直接写设备寄存器，一条指令直达硬件。**这一项相差数十倍**。
- **$T_{\text{device}}$（设备服务耗时）**：两种方式都由真实硬件执行，接近相同——这正是直通性能的底气来源。
- **$T_{\text{irq}}$（中断送达）**：模拟的中断要经 VMM 注入调度；直通的中断经 MSI-X 与中断重映射直接到 vCPU。直通省掉一次调度往返。

因此可写出量级对比：设模拟路径 CPU 占用为 $C_{\text{emul}}$，直通为 $C_{\text{pass}}$，实测中 $C_{\text{pass}} \approx C_{\text{emul}} / 10$ 甚至更低——**同样的吞吐，直通只花十分之一的 CPU**。这也是为什么高吞吐网络（云主机 100G 网卡、NVMe 存储、GPU 直通）几乎全部走 SR-IOV 或直通。

## 5 直通与 SR-IOV 的边界

技术并非银弹，直通有几个绕不开的限制：

- **数量硬上限**：可直通的 VF 数量由硬件决定（比如 64 个 VF），**超卖**（比 VF 数更多的虚拟机共享）做不到——想共享，就得回 virtio。
- **迁移受限**：SR-IOV 直通的虚拟机的网卡上下文绑定在物理设备上，**热迁移**（把虚机迁到另一台宿主机）非常困难，因为 VF 换不掉。这是云厂商在大规模弹性伸缩时仍保留 virtio 的原因。
- **需要硬件支持**：IOMMU、SR-IOV 都要 CPU 芯片组与设备端同时支持，旧硬件无法受益。
- **管理面仍在 VMM**：PF 的配置、固件升级、VLAN 管理仍由 VMM 负责——**VMM 退出数据路径，但不退出控制路径**。

这些限制在现实工程里演变成了一套「性能与灵活」的分工：**控制面（管理、迁移、快照）走 virtio，数据面（高速网络、存储、GPU）走 SR-IOV 直通**。
云厂商的虚拟网卡（如 AWS 的 Nitro、阿里云的硬件加速卡）就是这种分工的极致形态——网络数据面用硬件直通跑满，
管理面用软件保持弹性。直通解决性能，软件保留灵活，两者不是对手而是搭档。

这套「数据面交给硬件、控制面留在软件」的分工，也直接塑造了大模型训练与推理的云上形态：**GPU 必须直通**（SR-IOV 
vGPU 或整卡直通），因为一次梯度同步的毫秒级延迟都损失不起；**RDMA/InfiniBand 必须直通**，
因为多机多卡通信不能过 VMM 的软件路径；而编排、镜像、生命周期管理全部走软件。可以说，**没有直通，就没有今天能在云上规模训练大模型的基础设施**——这是 I/O 虚拟化与「从极限到大模型」主线最近的一次握手。


**辨析｜易错点：** VT-d 与 SR-IOV **不是同一个东西**。VT-d（含 IOMMU）解决的是「直通的安全问题」
——DMA 翻译与设备隔离；SR-IOV 解决的是「设备可划分性」——把一块设备拆成多块。一个直通一台虚拟机，也可以直通多个 VF 
给多个虚拟机，两者配套使用：SR-IOV 提供 VF，VT-d 让 VF 的直通安全。

## 6 小结

- **设备直通**：真实设备/功能直接交给虚拟机，客户驱动直连硬件，数据路径无 VMM。
- **VT-d 的 IOMMU**：给设备 DMA 做 **GPA→HPA** 翻译（DMA 重映射），并做**设备隔离**与**中断重映射**——直通的安全保障。
- **SR-IOV**：**PF** 拆出多个 **VF**，每个 VF 独立配置空间与 DMA 能力，可分别直通给不同虚拟机；多路复用由硬件完成。
- 性能模型：直通把 I/O 的 **CPU 路径与中断路径**省到接近零，同吞吐下 CPU 占用约为模拟的十分之一。
- 边界：VF 数量硬上限、热迁移困难、需硬件支持、管理面仍在 VMM。
- **VT-d ≠ SR-IOV**：前者保安全，后者保可划分，两者配套。

补充一个工程判断：**什么时候该直通，什么时候该回 virtio？** 经验法则是——先看吞吐需求与 CPU 预算。若虚拟机的 I/O 
吞吐要求高（网络满速率、NVMe 全速、GPU 通信），且这台机器不需要频繁迁移，直通是明确选择；若集群要弹性伸缩、热迁移、超卖，
virtio 的灵活性更值钱。直通把「性能」买断，virtio 把「灵活」留下——两者之间没有免费午餐。
