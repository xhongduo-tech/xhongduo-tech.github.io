## 为什么内存虚拟化最反直觉

CPU 虚拟化的问题好懂——权限不够就陷入。但内存虚拟化会遇到一个「双重现实」：客户 OS 以为自己在管物理内存，
而它管的「物理内存」其实只是 VMM 画出来的一层假象。于是地址从两维变成三维：**客户虚拟地址 → 客户物理地址 → 真实物理地址**。
这一节讲清楚这套三层翻译如何运作、影子页表如何用「写保护 + 同步」维护它，以及它的性能代价在哪里。

## 1 三维地址：谁来管哪一层

先明确分工。系统虚拟机里有两个「地址空间的老板」：

**客户 OS 的职责**：把**客户虚拟地址（Guest Virtual Address，GVA）**翻译成**客户物理地址（Guest Physical Address，GPA）**——它通过维护自己的页表（guest page table）做到这一点。客户 OS 坚信 GPA 就是真实内存的地址，它据此调度、换页、分配。

**VMM 的职责**：把**客户物理地址（GPA）**翻译成**真实物理地址（Host Physical Address，HPA）**——真实内存由 VMM 独占分配，
客户 OS 的「物理内存」只是 VMM 从真实内存里划出的一块区域。

完整的翻译链条：

$$
\text{GVA} \xrightarrow{\text{客户页表}} \text{GPA} 
\xrightarrow{\text{VMM}} \text{HPA}
$$

麻烦在于：**硬件（MMU + TLB）只认一个「当前页表」**。它无法同时跑两级翻译——至少，在没有硬件辅助（EPT/NPT）
的年代，它不能。于是 VMM 必须让硬件「只看得到」一层页表，而这一层页表要同时体现两级的翻译结果。

## 2 影子页表：让硬件只看一层

**影子页表（shadow page table）**：VMM 为每个客户进程维护一张「影子」页表，直接建立 **GVA → HPA** 的映射——把客户页表（GVA→GPA）与 VMM 自己的页表（GPA→HPA）合成一张表，
喂给硬件。<span class="marginnote">「影子」的意象：硬件 TLB 填充时实际使用的，是这张影子表；客户 OS 的页表只是「影子」的原型，不再被硬件直接使用。</span>

但这里有个递归难题：**客户 OS 会不断修改它自己的页表**（加载新进程、换页、写保护页）。如果 VMM 不跟着改，
影子表就过时了。怎么知道客户 OS 改了什么？答案是**写保护**：

1. VMM 把客户页表所在的物理页设为**只读**，并记录「哪些页是页表页」。
2. 客户 OS 任何一次写页表（比如改一个 PTE），都会触发**写保护缺页异常**。
3. 异常陷入 VMM，VMM 检查并**同步**对应的影子页表项，然后恢复写权限、让客户 OS 重试这条写指令。

这就是影子页表的核心机制：**写保护 + 陷阱 + 同步**。每改一个页表项，就要陷入 VMM 一次。

## 3 影子页表的四个代价

机制听起来优雅，代价却堆成了山：

- **同步陷入频繁**：每次客户 OS 改页表（进程切换、分配内存、换页）都要写保护缺页 + VMM 同步。上下文切换密集的负载下，这可能是最重的虚拟化开销之一。
- **TLB 刷新风暴**：影子页表换掉时，硬件 TLB 里对应的旧映射全部失效。客户 OS 每切换一次进程，TLB 就要清一遍——在虚拟化前它也要清，但现在清得更勤、清得更大。
- **影子表内存翻倍**：每个进程都要维护「客户页表 + 影子页表」两份元数据，页表本身也是内存，VMM 要为它们多付出成倍的内存。
- **页表结构差异**：若客户与宿主的页表格式（如 32 位与 64 位、两级与四级）不同，VMM 还要做格式转换，同步成本进一步上升。

其中「TLB 刷新风暴」尤其值得展开。虚拟化前，一次进程切换只需清空本进程的旧映射；虚拟化后，
客户进程切换意味着**影子页表整体换掉**，硬件 TLB 里与之相关的项全部作废。若多个虚拟机在同一物理 CPU 上轮转，彼此的 
TLB 项互相污染、反复刷新——**这是软件虚拟化年代 CPU 利用率上不去的一个隐性杀手**。硬件后来用 TLB 
打标签（VPID/ASID）专治此症，见《半虚拟化与硬件内存虚拟化 EPT/NPT》一节。

## 4 公式解析：一次 TLB 填充要多少内存访问

先把原生情况写清楚。设页表有 $L$ 级（如 x86-64 的 4 级），一次 **TLB 缺失填充**需要逐级查页表：

$$
N_{\text{native}} = L \ \text{（次内存访问）}
$$

在影子页表下，硬件仍然只走一层页表——影子页表本身，所以 TLB 填充的访问次数**不变**，仍是 $L$。这是影子页表最得意的一点：**数据路径上没有额外的一层翻译**。真正的成本在维护侧。设客户 OS 每修改 $M$ 条页表项，就触发 $M$ 次写保护缺页，每次缺页 VMM 的同步代价为 $C_{\text{sync}}$（含陷入、比较、更新影子项、恢复权限、重试），则维护总代价：

$$
C_{\text{maintain}} = M \times C_{\text{sync}}
$$

拆三步：

- **第一步，看 $L$ 与访问次数**：TLB 填充 $N_{\text{native}} = L$，影子页表不增加它——硬件性能在「读路径」上不吃亏。
- **第二步，看 $C_{\text{sync}}$**：一次同步要经历「写保护缺页 → VMM 陷入 → 定位页表页 → 改影子项 → 恢复权限 → 返回重试」，是几百到上千周期的软件操作，比一次内存访问贵几个数量级。
- **第三步，看 $M$**：$M$ 由客户 OS 的行为决定——进程切换时它常批量更新页表。若 VMM 能把多次更新**批量**处理（先收进队列再一起同步），$M \times C_{\text{sync}}$ 可以显著摊薄。这正是半虚拟化（显式 hypercall 批量更新）的出发点之一。

**辨析｜易错点：** 影子页表**不是**「客户 OS 用它自己的页表直接跑」。客户页表（GVA→GPA）映射的「物理地址」
是假的，喂给硬件会直接翻译到错误的位置，甚至落到 VMM 的私密内存里。**真正喂给 MMU 的永远是 VMM 合成的那张影子表**；
客户自己的页表只扮演「待同步的原型」。这一点想通了，也就理解了为什么写保护缺页是影子页表方案的核心命脉。

## 6 影子页表与内存超售

影子页表还支撑了虚拟化的一项关键能力——**内存超售（memory overcommit）**。客户 OS 以为它有 4 GB 
内存，VMM 实际只给它 2 GB，差的 2 GB 由 VMM 统一调配。为此 VMM 常使用 **气球驱动（balloon driver）**：在客户 OS 里装一个伪驱动，
当宿主机内存紧张时，「气球」膨胀、向客户 OS 申请页面并交还 VMM；VMM 把这些页重新分配给其他虚拟机。<span class="marginnote">气球驱动把「回收客户内存」从 VMM 的单方面动作，变成了客户 OS 与 VMM 的合作——客户 OS 仍然相信自己在正常管理内存，只是「可用的物理内存变少了」。</span>影子页表为这套交换提供了地址层面的保证：客户页被回收后，GPA 对应的 HPA 变化，VMM 同步影子表即可。

这里还可以追问一句：为什么 VMM 不直接告诉客户 OS「你只有 2 GB」？因为**虚拟化的等价性要求客户 OS 不能感知到它在虚拟机里**——如果客户 OS 发现物理内存与硬件配置不符，
可能触发 license 检查、降级运行或直接拒绝启动。所以超售必须靠「VMM 单方面调整客户可见的物理内存」完成，
气球驱动只是实现手段之一。另一个经典手段是**内存压缩与去重**：多台虚拟机跑同一个 Linux 内核，
相同页面在物理内存里只存一份（内存页共享），影子页表同步这些页面的引用关系即可。

**辨析｜易错点：** 不要把「超售」理解成「VMM 撒谎但不影响正确性」。超售是**有代价的资源复用**：
当多个虚拟机同时要满配额时，VMM 必须回收或换出页面，客户 OS 会感受到内存压力与性能波动——「看起来有 4 GB」
并不等于「随时能拿到 4 GB」。把超售想成航空公司卖超卖机票：平时相安无事，高峰期就要有人在候机厅等位。

讲到这里，影子页表的技术全景就齐了：**它一面在「读路径」上保持硬件单层翻译的高效，一面在「写路径」上用写保护与同步扛下全部复杂性，还顺手支撑了超售与页共享这些关键能力**。
它是软件虚拟化年代「用复杂度换兼容性」的代表作，也是理解为什么后来者（EPT、IOMMU、容器页表）都把「让硬件做更多」
当作方向的背景板。掌握了影子页表，再看 EPT 与 IOMMU，
就像已经看过手摇纺车再看自动织机——**你知道每一针原本是怎么落下的**。

## 7 小结

- 系统虚拟化下的地址是**三维**的：GVA →(客户页表) GPA →(VMM) HPA。
- **影子页表**把两级翻译合成一张 **GVA→HPA** 的直接表喂给硬件，硬件只需一层页表。
- 同步机制 = **写保护 + 陷阱 + 同步**：客户 OS 每次改页表都触发写保护缺页，VMM 随之更新影子表。
- 四大代价：**同步陷入频繁、TLB 刷新风暴、影子表内存翻倍、页表格式差异**。
- 读路径开销 $N = L$ 不增加；维护开销 $C_{\text{maintain}} = M \times C_{\text{sync}}$，批量同步是压价关键。
- 影子页表支撑**内存超售**与**气球驱动**，是 VMware 时代内存虚拟化的核心武器。

在下一节，我们把影子页表的方案「换血」——**半虚拟化**主动配合的批量更新，以及 **EPT/NPT** 让硬件直接做两级翻译：
内存虚拟化从软件大战进入硬件时代。
