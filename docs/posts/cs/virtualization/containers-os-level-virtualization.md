## 为什么容器不需要 Hypervisor

前十一节讲的都是「机器级」虚拟化：每个虚拟机里都装一整套操作系统，各自管理各自的「物理内存」与 CPU。
容器的思路完全不同——**不虚拟硬件，只虚拟操作系统视角**：所有容器共享同一个 Linux 内核，每个容器只获得一个「隔离的视角」
与「限定的资源」。它轻快到可以在毫秒级启动、在单机上塞上千个，而这也是整个专题的收尾：从虚拟一台机器，到虚拟一个世界。

## 1 操作系统级虚拟化：一个内核，多个「用户空间」

**操作系统级虚拟化（OS-level virtualization）**，也叫容器化：在**单一操作系统内核**之上，
创建多个相互隔离的用户态实例——容器。每个容器拥有自己的文件系统、进程、网络栈与用户空间，但**不拥有内核**：它们共享宿主内核，
由宿主内核负责进程调度、内存管理与设备驱动。

历史上有几代实践：1979 年的 `chroot` 只是改了根目录（一个「目录视图」）；2000 年的 FreeBSD Jails 
加上了进程与网络隔离；2004 年 Solaris Zones 把资源管理也收进去；Linux 侧的 VServer、OpenVZ、
LXC（2008）逐步完善。真正引爆容器的是 **Docker（2013）**——它把「打包、分发、运行」的体验做到了极致，再加上 
**Kubernetes** 把容器编排成集群，容器就此成为现代软件部署的事实标准。<span class="marginnote">历史脉络值得记住：隔离的需求一直都在，Docker 的贡献不是发明隔离，而是把隔离包装成了「镜像 + 一条命令」的开发者体验。</span>

## 2 两大内核机制：namespaces 与 cgroups

Linux 容器由两个内核机制撑起来，缺一不可：

**命名空间（namespaces）**：决定容器**看到什么**。每个容器有自己的一份视图：

**PID namespace**：容器里的进程从 1 号开始编号，看不到其他容器的进程——每个容器都像一台独立的机器，有自己的 init 进程。
- **Mount namespace**：容器有自己独立的文件系统挂载视图，`/` 根目录是它的镜像层。
- **Network namespace**：每个容器有自己的网络栈、IP 地址与端口空间——网络互不冲突。
- **UTS、IPC、User namespace**：主机名、消息队列、用户 ID 映射各自隔离。

命名空间的实现很朴素：进程描述符里挂一串「指向内核对象（PID 表、挂载表、网络栈）的指针」。容器创建时，
内核复制这些指针为新对象——**「隔离」不是复制进程，而是复制「看待世界的视角」**。<span class="marginnote">这也解释了为什么容器开销极小：创建命名空间只是内核里几个数据结构的新实例，不需要加载新内核、不需要虚拟硬件，成本就是几个对象的分配与初始化。</span>

**控制组（cgroups）**：决定容器**能用多少**。cgroup 限制并统计容器可用的 CPU 份额、内存上限、I/O 
带宽、进程数。容器不能超过配额，宿主机据此公平调度。

**namespaces 管「视野」，cgroups 管「配额」**——两句话，容器机制的核心就到手了。

## 3 Docker 镜像：分层文件系统

Docker 把容器变成可复制的产物——**镜像（image）**：

- 镜像由多层只读文件系统叠加而成（**overlayfs** 等联合文件系统），每一层对应一次构建步骤（装依赖、复制代码、设入口）。
- 运行时在镜像之上加一层可写层，容器退出后丢弃。
- 分层让镜像**极致复用**：一百个服务共享同一层基础镜像，只下载各自不同的几层。推送与拉取只需传输差异层。

这套设计解决了「环境一致」这个部署世纪难题：**开发机、测试机、生产机上跑的是同一个镜像，行为一致**。

## 4 容器 vs 虚拟机：本质不是「轻」，是「共享内核」

| 维度 | 容器 | 虚拟机 |
| --- | --- | --- |
| 内核 | 共享宿主内核 | 各自独立内核 |
| 启动时间 | 毫秒级 | 秒级 |
| 内存开销 | MB 级 | GB 级 |
| 单机密度 | 成百上千 | 几十 |
| 隔离强度 | 共享内核，边界薄 | 硬件隔离，边界硬 |
| 性能损失 | ≈1–5% | 5–20%+ |
| 代表性技术 | Docker、containerd | KVM、Xen、ESXi |

![容器 vs 虚拟机：共享内核 vs 独立内核](/images/virtualization/containers-os-level-virtualization-1.svg)

**容器快、密、省，但隔离比虚拟机薄**——这是二者最重要的差别。虚拟机之间隔着硬件（EPT、IOMMU、设备直通），
一个内核崩溃不影响隔壁；容器之间只隔着内核的几个数据结构，**共享同一个内核 = 共享同一个攻击面**。
一个容器里的漏洞一旦拿到内核权限，理论上是整个宿主机的沦陷。

**辨析｜易错点：** 「容器是轻量虚拟机」是流传最广的错误类比。容器**不虚拟化任何硬件**——没有虚拟 CPU、虚拟内存、
虚拟设备；容器里的进程就是普通 Linux 进程，只是被装进了一套隔离视图里。`docker exec` 里跑的 `ps`，
看到的就是宿主内核里的真实进程。

## 5 公式解析：容器的密度优势从哪来

设一台宿主机有物理内存 $R$，一个虚拟机的固定开销（内核 + 设备驱动 + 基础服务）为 $M_{\text{vm}}$，一个容器的固定开销（进程 + 库 + 运行时的额外占用）为 $M_{\text{ct}}$，且 $M_{\text{vm}} \gg M_{\text{ct}}$（实测一个精简虚拟机内核约数百 MB，一个容器仅几 MB 到几十 MB）。可容纳的最大数量：

$$
N_{\text{vm}} \approx \frac{R}{M_{\text{vm}}}, \qquad 
N_{\text{ct}} \approx \frac{R}{M_{\text{ct}}}, \qquad 
\frac{N_{\text{ct}}}{N_{\text{vm}}} \approx 
\frac{M_{\text{vm}}}{M_{\text{ct}}} \approx 10\text{–}100
$$

拆三步：

- **第一步，虚拟机为什么贵**：每台虚拟机都要**重复支付一整套内核与系统软件**——同一个 Ubuntu 内核在每台虚机里各装一份，这是纯开销。
- **第二步，容器为什么便宜**：容器不重复装内核，共享那份已被宿主付过费的内核；每加一个容器，只多付进程与库的边际成本。
- **第三步，密度差一个量级**：$N_{\text{ct}}/N_{\text{vm}} \approx M_{\text{vm}}/M_{\text{ct}}$，实际数量级在 10–100 倍。这就是大模型推理服务能在一台 A100 上并排跑几十个模型容器、而虚拟机只能跑几个的原因。

## 6 容器与虚拟机的混合：各自的归宿

现实世界没有非此即彼：

- **云上的「裸容器」**：容器直接跑在宿主机内核上（Docker、containerd），追求密度与启动速度，用 **seccomp、AppArmor/SELinux、User namespace** 加固这层薄隔离。
- **「虚拟机里的容器」**：云端给租户的往往还是虚拟机（因为要隔离不可信的租户），租户在虚拟机里再跑容器——**虚拟机提供租户间的硬隔离，容器提供租户内的灵活部署**。这是 AWS EKS、阿里云 ACK 的真实形态：一层 VM 保安全，一层容器保灵活。
- **Kata Containers / gVisor 等「安全容器」**：用轻量虚拟机或用户态内核（沙箱）把每个容器包一层，兼得容器的轻与虚拟机的硬隔离——但付出相应的性能与内存代价。

选择判据一句话：**需要「共享内核的轻量隔离」就上容器；需要「不可信工作负载的硬隔离」就上虚拟机；在云的租户边界，往往是两者叠用**。

还有一个工程细节值得展开：**容器镜像的分层**。Dockerfile 里每一个 `RUN`/`COPY` 语句生成一层，
层与层之间用联合文件系统叠加；运行时对上层做写时复制。这意味着：拉取一个镜像时只传输「没有的层」，构建时只重跑「改动的层」
——缓存复用率极高。大模型训练团队每天要改的是训练代码那一层，而 PyTorch 镜像、CUDA 层、基础 OS 层全部命中缓存，
几分钟就能完成环境分发。**镜像分层的工程回报，是「一层变更，全网秒级同步」**——这是容器能在 AI 工程里普及的隐藏推力。

## 7 小结

- **操作系统级虚拟化**：一个内核、多个隔离用户空间，容器 = 隔离视图 + 限定资源，不需要 VMM。
- 两大内核机制：**namespaces** 管「看到什么」（PID/Mount/Network…），**cgroups** 管「能用多少」（CPU/内存/I/O）。
- **Docker 镜像**用分层只读文件系统实现极致的复用与环境一致。
- 容器与虚拟机的本质差别是**共享内核 vs 独立内核**：快、密、省，但隔离薄。
- 密度公式 $N_{\text{ct}}/N_{\text{vm}} \approx M_{\text{vm}}/M_{\text{ct}} \approx 10$–$100$：不重复付内核钱，是容器密度优势的根源。
- 生产实践是**混合架构**：虚拟机做租户硬隔离，容器做租户内灵活部署；安全容器（Kata、gVisor）试图兼得两者。

至此，本专题从「虚拟一台机器」（进程虚拟机、系统虚拟机、Hypervisor、CPU/内存/I/O 虚拟化、硬件辅助）
走到了「虚拟一个操作系统视角」（容器）。回望十二节，有一条主线贯穿始终：**每一种虚拟化都是「接口」与「隔离」的一场交易——虚拟化到什么接口，就要在那一层承担隔离的代价**。如果你顺着这条线想清楚了 VM/370、VT-x 与 Docker 各自「虚拟了什么、隔离了什么、付了什么代价」，这个专题就算真正读透了。

把这条主线再拧紧一层，就能提炼出判断一切「虚拟化产品」的三问：**它虚拟的接口是哪一层？它依赖什么机制维持隔离（硬件权限、页表翻译、还是内核命名空间）？它为「高效」牺牲了什么（兼容、迁移、还是安全性）？** 三问答得上来，
任何新技术——无论是 GPU 分区、微服务沙箱还是所谓「超轻量运行时」——都能被快速归位，而不是被包装话术带着走。这，
才是十二节虚拟化真正想训练出的判断力。

下一步，是把镜头拉回这些技术反复借用的地基——**操作系统本身**。进程、虚拟内存、系统调用、中断——本专题里每一处「陷入」「缺页」
「DMA」都是在借用这些概念；在计算机基础的下一个专题里，我们将逐个拆解它们的原始定义与完整实现。
