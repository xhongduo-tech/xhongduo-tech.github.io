## 为什么 I/O 虚拟化是「最短的那块木板」

CPU 虚拟化有陷入模拟，内存虚拟化有影子页表与 EPT，而 I/O 虚拟化面对的是千奇百怪的真实设备——网卡、磁盘、USB、
GPU，每一个都有自己的寄存器、中断、DMA 语义。**虚拟化的性能瓶颈几乎总是先出现在 I/O 上**：一个跑满 CPU 
的虚拟机可能仍然感觉「卡」，因为磁盘与网络路径上有太多软件模拟在拖后腿。这一节从最基础的**设备模拟**讲起，讲清楚它怎么工作、
为什么慢，为下一节的 SR-IOV 直通做铺垫。

## 1 I/O 虚拟化的三条路线总览

虚拟机的客户 OS 想用一块磁盘或网卡，有且只有三条路：

**设备模拟（device emulation）**：VMM 在软件里仿造一台真实设备（比如一块古老的 e1000 网卡、一块 
IDE 磁盘），客户 OS 用它自带的原生驱动去驱动这台「假设备」。不需要改客户 OS，兼容性最好——代价是每笔 I/O 都过软件。

**半虚拟化 I/O（paravirtualized I/O）**：客户 OS 里装一个专用前端驱动（frontend），与 
VMM 侧的后端（backend）通过共享内存队列通信。代表是 Linux 世界的 **virtio**——比纯模拟快得多，
但要装驱动。

**设备直通（device passthrough / assignment）**：把真实物理设备直接划给一个虚拟机，
客户驱动直接操作硬件，VMM 完全不碰数据路径。最快，但有数量与灵活性限制。下一节《I/O 虚拟化 SR-IOV / VT-d 
直通》专门讲它。

## 2 设备模拟的工作原理

设备模拟是 I/O 虚拟化的起点，也是理解后两条路线的参照物。VMM 模拟一台设备，需要模拟它的全部三块：

**寄存器与 MMIO/PIO**：客户 OS 访问设备寄存器（端口 I/O 或内存映射 I/O），触发陷入或由 VMM 截获。
VMM 解析这次访问——是读状态寄存器？写命令寄存器？——再返回一个模拟值。一个设备几百个寄存器，每个都要有语义。

**中断**：真实设备发中断通知 CPU。模拟设备的中断要由 VMM 在恰当的时候**重新注入（reinject）**给客户 OS。
客户 OS 的中断处理程序以为收到了硬件中断，实际收到的只是 VMM 发的一个「假信号」。

**DMA**：真实设备绕过 CPU 直接读写内存。模拟设备没有真实 DMA 能力，VMM 
必须**代为搬运**数据——把客户内存里的数据拷到真实设备，或反之。

QEMU 是设备模拟的教科书实现：它模拟 e1000、virtio-net、IDE、VGA 等几十种设备，
每个模拟设备本质是一段「用软件重现设备数据手册」的代码。<span class="marginnote">「模拟设备 = 用软件复刻一份设备数据手册」这句话值得反复咀嚼：设备厂商给每个寄存器写清语义（读返回什么、写触发什么动作、中断何时置位），模拟器就把这些语义逐条用 C 代码实现。客户 OS 的驱动只认寄存器语义，不认物理硬件。</span>

模拟还有一个常被忽略的层次：**设备固件的模拟**。一块模拟网卡除了寄存器，还有自己的 ROM/固件、EEPROM、MAC 
地址与能力协商过程；VGA 设备要模拟显示内存与模式切换。每多模拟一个层次，就多一分出错的空间，
也多为攻击者提供一个入口——设备模拟也因此常年是虚拟化安全漏洞的重灾区。

## 3 公式解析：设备模拟的一次 I/O 贵在哪

设客户 OS 发起一次网络发送。在原生环境下，驱动写设备寄存器、设备 DMA 取数据、完成后发中断——总耗时 $T_{\text{native}}$。在设备模拟下：

$$
T_{\text{emul}} = T_{\text{native}} + \underbrace{N_{\text{trap}} 
\cdot t_{\text{trap}}}_{\text{寄存器访问}} + 
\underbrace{C_{\text{copy}} \cdot t_{\text{mem}}}_{\text{DMA 
模拟搬运}} + \underbrace{t_{\text{irq}}}_{\text{中断注入}}
$$

拆三步：

- **第一步，$N_{\text{trap}} \cdot t_{\text{trap}}$**：客户驱动每读一个状态寄存器、每写一个命令寄存器，都要陷入 VMM 一次。驱动一忙，$N_{\text{trap}}$ 轻松上百，乘上每次陷入几百周期，量级惊人。
- **第二步，$C_{\text{copy}} \cdot t_{\text{mem}}$**：模拟 DMA 时 VMM 要把数据在客户内存与真实缓冲之间搬运。拷贝是内存带宽的事，看似便宜，但**每一步拷贝都多绕一次数据路径**，还可能引入额外的锁与同步。
- **第三步，$t_{\text{irq}}$ 与中断风暴**：模拟设备的中断注入要经过 VMM 调度，一次中断的完整旅程远长于硬件中断。高吞吐场景（网络收包）下，中断风暴可能把 CPU 拖满——这就是后来**中断合并、多队列**等技术的由来。

量级参考：一条千兆网络路径上，设备模拟的 CPU 开销常比原生高一个数量级；这也是为什么虚拟化环境里「网卡」
往往是最先被换掉的东西——换成 virtio 或直通。

还有一类常被低估的 I/O 开销：**时钟与中断的虚拟化**。客户 OS 依赖时钟中断做调度与超时，模拟环境里时钟中断的注入路径长、
抖动大；客户 OS 收到的「墙钟时间」还要与真实时间对齐，VMM 要做时间戳的换算与补偿。现代硬件（VT-x 的 TSC 
scaling、APICv）专门处理这类「时间与中断」的虚拟化开销——它们不产生数据吞吐，却在每一次调度、每一个超时里悄悄征税。

为什么这类「看不见的税」值得单独强调？因为**模拟方案里 CPU 空闲时也未必真闲**。客户 OS 的时钟中断照常到达、
定时器照常触发，VMM 要为它们逐个模拟、逐个注入——一台「看似空闲」的模拟虚拟机，可能仍在以可观的比例消耗 CPU。
这正是虚拟化与容器的一个深刻分野：**容器没有虚拟硬件，自然也没有这层「模拟硬件心跳」的税**（详见本专题末篇《容器与操作系统级虚拟化》）。
判断一个负载适不适合虚拟化，先看它对时钟与中断的敏感度，往往比看吞吐更准。

## 4 DMA 地址的坑：客户物理地址不是真地址

设备模拟最隐蔽的难题在 DMA。真实设备 DMA 时写入的是**真实物理地址**，但客户驱动给设备下命令时，
填的是**客户物理地址（GPA）**。两者不同！VMM 的应对：

- **反弹缓冲（bounce buffer）**：VMM 在真实内存里准备一块连续缓冲，把客户数据先拷进去，把这块缓冲的**真实地址**交给真实设备做 DMA。数据来回复制，安全但慢。
- **地址翻译（地址重映射）**：VMM 维护一张「客户 DMA 地址 → 真实地址」的映射表，DMA 请求到达时查表改写。省掉拷贝，但表项有限、命中不中要看运气。

无论哪种，DMA 都是设备模拟里绕不开的软件路径。<span class="marginnote">这个「客户看到的地址 ≠ 硬件看到的地址」的难题，在设备直通里由 <strong>IOMMU</strong>（VT-d）在硬件上解决——下一节会看到，IOMMU 本质是给 DMA 也配了一张「影子页表」。</span>

反弹缓冲的拷贝成本有一个直观的量级：一次 4 KB 的数据来回，就是两次 4 KB 的内存拷贝，加上锁与屏障，通常在微秒级。
看起来不贵，但网络收包的节奏是**每帧都要这么来一遍**——一个跑满的 10Gbps 网卡每秒处理约百万帧，微秒级开销乘以百万帧，
CPU 直接耗尽。这就是为什么高性能虚拟化最终必须把 DMA 路径从「软件搬运」升级为「硬件翻译」（IOMMU）或「硬件直通」
（SR-IOV）。

## 5 半虚拟化 I/O：virtio 的诞生

纯设备模拟太慢，硬件直通又太死板，中间地带是半虚拟化 I/O。2008 年随 KVM 一同进入 Linux 的 
**virtio** 是标准答案：

- 客户 OS 装 **virtio-net / virtio-blk 前端驱动**，VMM 侧提供对应**后端**。
- 前后端通过**共享内存环形队列（virtqueue）**通信：驱动把「请发送这个数据包」的请求写进队列，后端从队列取走，发完再放回一个完成通知。
- 一次请求只需要**一次通知 + 一次释放**，不必反复陷入寄存器；数据用**零拷贝**（必要时直接引用客户页）传递。

virtio 的性能比设备模拟提升一个数量级，代价是客户 OS 必须装驱动——好在现代 Linux/Windows 都内置了 
virtio 驱动，代价趋近于零。**今天主流云主机的默认网卡与磁盘就是 virtio 半虚拟设备**，不是模拟出来的老网卡。

**辨析｜易错点：** virtio **不是**设备模拟。模拟设备在「演一台真实硬件」，virtio 在「和 VMM 直接谈生意」
——virtio 设备在物理世界不存在，它是专门为虚拟化设计的通信协议。客户驱动不是「原生驱动」，而是「虚拟机感知驱动」。

## 6 小结

- I/O 虚拟化三路线：**设备模拟**（兼容好、慢）、**半虚拟化 I/O**（virtio，快、需驱动）、**设备直通**（最快、最灵活）。
- 设备模拟要重建三样东西：**寄存器/MMIO**、**中断注入**、**DMA 搬运**。
- 性能模型 $T_{\text{emul}} = T_{\text{native}} + N_{\text{trap}}t_{\text{trap}} + C_{\text{copy}}t_{\text{mem}} + t_{\text{irq}}$：陷入多、拷贝多、中断路径长，是模拟慢的三大根因。
- **反弹缓冲**与**地址重映射**解决「GPA ≠ 真实地址」的 DMA 难题，但都在软件里绕。
- **virtio** 用共享内存队列 + 零拷贝，把 I/O 性能拉回接近原生，是现代云主机的事实标准。

在下一节，我们走到 I/O 虚拟化的性能顶点——**SR-IOV 与 VT-d 直通**：把真实网卡直接交给虚拟机，
让数据路径上一行 VMM 代码都不跑。
