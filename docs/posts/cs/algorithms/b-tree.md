# B 树：定义、性质与磁盘友好的查找结构

## 为什么从 B 树开始

二叉搜索树在外部模型下每层一次 I/O，$N = 10^9$ 时 30 层 = 30 次磁盘访问——太慢。**B 树**把每个节点扩容成一个**磁盘块**（装几百个关键字），树高骤降到 $\log_B N$（约 3–4 层），**一次查找只需 3–4 次 I/O**。<span class="marginnote">B 树是数据库与文件系统的统治级索引结构：MySQL 的 InnoDB、PostgreSQL 的索引、文件系统的目录结构、Linux 的 page cache 全部用它。它的全部设计都围绕「一次节点访问 = 一次磁盘 I/O」——节点大（一整块）、树矮（$\log_B N$）、扇出高。</span>

这一课定义 B 树、它的性质与搜索算法、以及「为什么高扇出 = 少 I/O」的定量分析。

## 1 B 树的定义

**B 树**：一棵「多路搜索树」，每个节点是一个**磁盘块**。参数 $t$（**最小度数**）定义结构：

每个**内部节点**有至多 $2t-1$ 个关键字、至少 $t-1$ 个关键字（根除外）。
每个节点有「关键字数 + 1」个孩子。
**所有叶子在同一层**（高度平衡）。
关键字有序：节点内 $k_1 < k_2 < \cdots < k_n$，孩子子树的关键字范围夹在相邻关键字之间。

例：$t = 2$（每个节点 1–3 个关键字、2–4 个孩子）的 B 树叫 **2-3-4 树**。<span class="marginnote">「最小度数 $t$」是 B 树的「密度旋钮」：$t$ 越大节点越满、树越矮、但单节点越大。磁盘上 $t$ 常取「让一个节点恰占一个块」的值（如 100–1000）。$t=2$ 时退化为熟悉的 2-3-4 树，便于教学；$t$ 大时才是工程形态。这个「$t$ 决定树高」的参数化与 d 叉堆的「d」、基数排序的「r」异曲同工。</span>

## 2 B 树的高度

**定理**：含 $n$ 个关键字、最小度数 $t \ge 2$ 的 B 树，高度满足

$$h \le \log_t \frac{n+1}{2}$$

- **直觉**：根至少 1 个关键字；高度 $h$ 时节点数最少的情形是「每层节点数最少」（$t-1$ 个关键字、$t$ 个孩子）——总数 ≤ 下界，反解出 $h$。
- **对比**：二叉搜索树高度 $\log_2 n$；B 树 $\log_t n$。$t = 100$ 时 $\log_{100} n = \log_2 n / \log_2 100 \approx \log_2 n / 6.6$——**矮 6 倍多**。<span class="marginnote">「$t$ 大则树矮」是 B 树磁盘友好的根源：树高 = 查找的 I/O 次数（每层一次）。$n = 10^9$、$t = 100$：$\log_{100} 10^9 \approx 4.5$——<strong>一次查找 5 次 I/O 内完成</strong>。对比二叉搜索树 30 次。这就是「高扇出换矮树」的全部价值。</span>

## 3 B 树的搜索

```
B-TREE-SEARCH(x, k)
1  i = 1
2  while i ≤ x.n and k > x.key[i]
3      i = i + 1
4  if i ≤ x.n and k == x.key[i]
5      return (x, i)
6  elseif x.leaf
7      return NIL
8  else
9      DISK-READ(x.c[i])          // 孩子指针在磁盘上，访问前必须读块
10     return B-TREE-SEARCH(x.c[i], k)
```

**每次下降一层读一个块**——$O(\log_t n)$ 次 I/O（= 树高）。节点内线性扫描 $O(t)$（块内 CPU，不计 I/O）。<span class="marginnote">搜索的 I/O 就是树高：每层一次 $O(t)$。节点内 $O(t)$ 的线性扫描在内存里几乎免费（块已读入）。所以 B 树查找的「代价语言」是：<strong>I/O = 树高 $\log_t n$，CPU = 节点内扫描 $O(t \log_t n)$</strong>——磁盘瓶颈下 I/O 主导。</span>

**辨析｜易错点：** B 树的「孩子指针」在磁盘上，访问孩子必须 `DISK-READ`——**别把节点当成已在内存**。B 树算法与内存树的差别就在「每次下降前先读块」；漏掉 DISK-READ 是「把外部当内存」的实现错误。

## 4 公式解析：为什么高度是 $\log_t (n+1)/2$

自底向上数最少节点数。高度 $h$ 时各层最少节点数：

$$1 + 2 + 2t + 2t^2 + \cdots + 2t^{h-1} = 1 + 2\sum_{i=0}^{h-1} t^i = 1 + \frac{2(t^h - 1)}{t-1}$$

- **第一步，逐层最少**：根最少 1 个关键字；第 1 层最少 2 个节点；第 $i$ 层最少 $2t^{i-1}$ 个节点（每节点最少 $t-1$ 关键字 → 每节点最少 $t$ 个孩子）。
- **第二步，总关键字下界**：最少关键字数 $= \sum$（各层节点数 × 每节点最少 $t-1$）$\ge 1 + (t-1)\cdot 2\sum t^{i-1} = 1 + 2(t^h - 1)$。
- **第三步，反解**：$n \ge 1 + 2(t^h - 1) \Rightarrow h \le \log_t((n+1)/2)$。

**要点**：高度下界来自「每层节点数的最少增长」——**$t$ 越大，每层能「装下」更多节点，树越矮**。这个 $\log_t$ 是 B 树全部性能的理论根源。<span class="marginnote">工程里 B 树的「每节点一块」还有额外收益：<strong>顺序遍历友好</strong>——叶子层的兄弟块在磁盘上相邻，范围查询（range query）顺序读叶块，I/O 接近「扫一遍」。B 树因此同时擅长「点查询」与「范围查询」——这是它压过哈希索引的实战优势（哈希只能点查）。</span>

## 5 数值算例：树高到底有多矮

拿 $n = 10^9$（十亿个关键字）对比不同最小度数 $t$ 下的树高上界 $h \le \log_t((n+1)/2)$：

| 最小度数 $t$ | 单节点关键字数 | $n=10^9$ 的树高上界 | 一次查找的 I/O 数 |
| --- | --- | --- | --- |
| 2（2-3-4 树） | 1–3 | $\log_2(5\times10^8) \approx 29$ | ≈ 29 |
| 100 | 99–199 | $\log_{100}(5\times10^8) \approx 4.35$ | ≤ 5 |
| 1000 | 999–1999 | $\log_{1000}(5\times10^8) \approx 2.9$ | ≤ 3 |

算一算 $t=100$ 那行：$\log_{100}(5\times10^8) = \frac{\ln 5 + 8\ln 10}{\ln 100} = \frac{1.61 + 18.42}{4.61} \approx 4.35$。<span class="marginnote">对比红线：二叉搜索树在十亿规模下要 30 层、30 次 I/O；B 树把 30 压到 5——<strong>6 倍差距</strong>，这正是数据库索引的生死线。一次机械硬盘随机读约 8–10 毫秒：30 次 = 300 毫秒，5 次 = 50 毫秒——肉眼可感的差别。工程上 $t$ 的选择由「一个磁盘块能塞几个关键字」决定（块 4–16 KB，关键字 + 指针约百字节，$t$ 常在几百）。</span>

**要点**：树高每减一，就是少一次磁盘 I/O。**「高扇出」不是技术癖好，而是把 I/O 次数从对数底 2 换到对数底 $t$ 的工程刚需**——这也解释了为什么数据库绝不用二叉搜索树做磁盘索引。

## 6 小结

- **B 树**：多路搜索树，最小度数 $t$，节点 = 磁盘块，叶子同层。
- **高度** ≤ $\log_t((n+1)/2)$——高扇出 → 矮树 → 少 I/O。
- **搜索**：每层 `DISK-READ` 一次，$O(\log_t n)$ 次 I/O（= 树高）。
- 数值算例：$n=10^9$ 时 $t=2$ 树高约 29、$t=100$ 树高约 4.35——十亿规模的查找从 30 次 I/O 压到 5 次。
- 节点内 $O(t)$ 线性扫描是内存 CPU，磁盘瓶颈下可忽略。
- $t=2$ 是 2-3-4 树；$t$ 大是工程形态；范围查询友好（叶块相邻）。


**速查表**：

| 参数 | 含义 | 对性能的影响 |
| --- | --- | --- |
| 最小度数 $t$ | 节点关键字数下限/上限 | $t$ 大 → 树矮、I/O 少、节点大 |
| 节点 = 磁盘块 | 一次节点访问 = 一次 I/O | 树高即查找 I/O 次数 |
| 叶子同层 | 高度平衡的保证 | 查找代价稳定 |
| $n$ | 关键字总数 | 高度 $\le \log_t((n+1)/2)$ |
| 内节点关键字数 | $t-1$ 到 $2t-1$ | 决定「满/半满」的密度区间 |

**辨析｜易错点：** B 树与二叉搜索树的关键差别不在「孩子数」而在「访问模型」——B 树把「一个节点」当成「一块磁盘 I/O」的计价单位，所以它的平衡是「I/O 的平衡」。$t$ 越大单节点越贵但树越矮，磁盘上取「一个块恰好装一个节点」的值。

**数值快照**：$n = 10^9$、$t = 100$ 时树高 ≤ 4.35，一次查找 ≤ 5 次 I/O；机械盘每次随机读约 8–10 毫秒，5 次 ≈ 50 毫秒，对比二叉搜索树的 30 次 ≈ 300 毫秒——「高扇出换矮树」是实打实的墙钟时间。


**延伸｜B+ 树**：工程数据库（InnoDB）更常用 **B+ 树**——数据全在叶子、内部节点只存索引键。它的查找与 B 树同复杂度，但叶子串成链表，范围查询顺序读相邻叶块，I/O 接近「扫一遍」；内部节点不存数据，单块能装更多索引键、树更矮。理解 B 树（内部存数据）与 B+ 树（数据下沉到叶）的差别，是数据库索引设计的下一步。


- 磁盘模型提醒：一次「节点访问」就是一次 I/O，B 树的全部设计都围绕「把树高压到 $\\log_t$」。
- 相关结构：B+ 树（数据沉叶）、B* 树（分裂时借兄弟）、LSM 树（写优化）——理解 B 树的权衡是索引设计的起点。
