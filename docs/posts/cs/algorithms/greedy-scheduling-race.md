## 为什么从调度与竞态开始

并行篇的最后一块拼图是两面：**调度**保证「并行真的快」（贪心调度定理的严格证明），**竞态条件**提醒「并行可能错」（并发写同一内存的 bug）。<span class="marginnote">调度与竞态是并行的「性能面」与「正确性面」。贪心调度定理给「$T_P \le T_1/P + T_\infty$」的严格证明——它是「并行接近线性加速」的理论承诺；竞态条件则让「正确性」成为并行编程的第一道坎——$T_P \le T_1/P + T_\infty$ 并行写同一数组可能出灾难。两课合一，并行算法才完整。</span>

这一课给出贪心调度定理的完整证明、并深入「确定性竞态」与「确定性算法」的概念。

## 1 贪心调度定理：完整证明

**定理**：$P$ 个处理器上的贪心调度满足 $T_P \le T_1/P + T_\infty$。

**证明（两步论证）**：

**完全步（complete step）**：$P$ 个处理器都忙。完成 $T_1$ 总工作量最多需要 $T_1/P$ 个完全步——每步完成 $P$ 个单位工作量。
**非完全步（incomplete step）**：至少一个处理器空闲。CLRS 引理证明：**非完全步必然执行了当前「关键路径」上下一步的所有就绪任务**——即每个非完全步把「未完成的关键路径长度」至少减 1。关键路径总长 $T_\infty$，所以非完全步 ≤ $T_\infty$。<span class="marginnote">非完全步的论证是定理的精华：当有处理器空闲时，说明「就绪任务数 < $P$」；而关键路径的下一步任务必然是就绪的——所以空闲处理器会去执行它。每个非完全步都「啃掉」关键路径上的一段，总步数被 $T_\infty$ 封顶。这个「有空闲必啃关键路径」是贪心调度的最优性质。</span>

两类步数相加：$T_P \le T_1/P + T_\infty$。

**辨析｜易错点：** 贪心调度不等于「最优调度」——它只是「任何时刻尽量多开工」的贪心策略，但定理保证它**不比最优差太多**（上界 $T_1/P + T_\infty$ 对任意调度都成立，尤其对贪心成立）。「贪心」在这里是「尽可能填满处理器」，不是「按某种启发式选任务」——理解这一点，定理的普适性就清楚了。

## 2 数值算例：一个 DAG 的调度

用一个具体并行 DAG 验证定理。设 $T_1 = 9$（9 个单位工作）、$T_\infty = 4$（关键路径 4 段），处理器 $P = 2$。

- **定理上界**：$T_P \le 9/2 + 4 = 8.5 \Rightarrow T_2 \le 9$。
- **加速比下界**：$S_P = T_1/T_P \ge 9/9 = 1$——这个例子太小，加速不明显。
- **加大规模再看**：若 $T_1 = 100$、$T_\infty = 10$、$P = 4$，则 $T_4 \le 100/4 + 10 = 35$，$S_4 \ge 100/35 \approx 2.86$。若 $P$ 再小到 2，$T_2 \le 50 + 10 = 60$，$S_2 \ge 100/60 \approx 1.67$——处理器翻倍，加速比从 1.67 提到 2.86，接近线性。

**要点**：处理器数 $P$ 越小、并行度 $T_1/T_\infty$ 越大，加速比越接近 $P$。**并行度是「理论天花板」，处理器数是「实际投入」，两者的比值决定你能多接近线性加速**。<span class="marginnote">数字背后的直觉：$T_1/P$ 是「理想线性加速」的时间，$T_\infty$ 是「串行关键路径」无法压缩的时间。两者相加——你的总时间不可能快过「关键路径」（再多处理器也快不了），也不可能快过「总工作平分」（处理器有限）。贪心调度同时逼近两个下界，所以上界是二者之和。</span>

## 3 公式解析：定理给出的「接近线性加速」条件

$$T_P \le \frac{T_1}{P} + T_\infty, \qquad S_P = \frac{T_1}{T_P} \ge \frac{T_1}{T_1/P + T_\infty} = \frac{P}{1 + P T_\infty/T_1}$$

- **第一步，上界代入**：把贪心调度的上界代入加速比定义。
- **第二步，化简**：分子分母同除 $T_1$。
- **第三步，观察**：当 $P \ll T_1/T_\infty$（并行度远大于处理器数）时，$PT_\infty/T_1 \approx 0$，$S_P \ge P$——**接近线性加速**。

**要点**：**「处理器数 ≪ 并行度」是线性加速的定量条件**。贪心调度定理把「并行多快」从经验变成可计算的保证。<span class="marginnote">推论（并行扩展性）：若 $P \le T_1/T_\infty$，则 $T_P \le 2T_1/P$——「处理器数不超过并行度」时，贪心调度达到至少一半的线性加速。这是并行算法的实用验收标准：并行度够、处理器不多、贪心调度就够快。</span>

## 4 确定性竞态：并行 bug 的根源

**竞态条件（race condition）**：两个逻辑上并行的操作**同时访问同一内存位置**，且至少一个是写操作，结果依赖调度顺序——**不可预测**。

**确定性竞态（deterministic race）**：即使每次运行结果碰巧相同（比如写相同的值），并行访问同一位置仍是竞态——它违背「确定性算法」的定义：**同样的输入必须产生同样的输出**（无论调度顺序）。<span class="marginnote">「结果碰巧对」≠「没有竞态」：若 $x$ 与 $y$ 并行执行 $y$（写同一位置但相同值），每次结果都是 1——看似无害。但 CLRS 强调：<strong>确定性算法要求「无论调度如何输出相同」</strong>，而并行的「写同一位置」依赖调度时序，即使值相同也是竞态。竞态的本质是「输出与调度顺序有关」，而非「结果错了」。</span>

**例（矩阵乘法的并行归约竞态）**：若把 $C[i][j] = \sum_k A[i][k]B[k][j]$ 的内层 $k$ 循环写成多个 $C[i][j]$ 任务各自 $C[i][j] = \sum_k A[i][k]B[k][j]$——多个任务同时读写 $C[i][j]$，产生竞态（值可能丢失更新）。正确做法是「每个任务写独立的临时变量，最后归约」或「同步访问」。

## 5 公式解析：矩阵乘法的正确并行 vs 竞态版

**竞态版**（每个 $k$ 直接累加进共享 $C[i][j]$）：

$$C[i][j] \mathrel{+}= A[i][k]\,B[k][j] \quad\text{（多个 } k \text{ 并行）} \Rightarrow \text{竞态}$$

**正确版**（各 $k$ 写独立局部变量 $t_k$，最后求和）：

$$C[i][j] = \sum_{k} t_k, \qquad \text{各 } t_k \text{ 独立计算}$$

- **第一步，竞态分析**：并行 $k$ 任务同时写同一 $C[i][j]$——读-改-写三部曲被打断，丢失更新。
- **第二步，修复**：每个 $k$ 任务写自己的局部变量（无共享写），最后串行/并行归约求和。
- **第三步，确定性**：修复后输出与调度无关——确定性竞态消除。

**要点**：**「写共享位置」是竞态的根源，修复 = 消除共享写**（局部变量 + 归约）或同步（锁/原子）。<span class="marginnote">工程实践：并行归约用「分治 + 局部累积 + 最后合并」是最自然且无锁的写法；避免「多个并行任务直接写同一累积变量」。理解「确定性竞态」后，写并行代码的第一自检就是「每个并行任务只写自己的内存」——这个习惯比任何工具都可靠。</span>

**辨析｜易错点：** 竞态是**调度相关**的——可能「这次跑对、下次跑错」，是间歇性 bug 的头号来源。**调试竞态不能靠「多跑几次看结果」**——要用确定性检查（如 Cilksan 的「确定性检查器」或 ThreadSanitizer）检测「并行访问同一位置」。别把「碰巧对」当成「没有竞态」。

## 6 术语速查

| 术语 | 含义 |
| --- | --- |
| 工作 $T_1$ | 总计算量（单处理器串行时间） |
| 跨度 $T_\infty$ | 关键路径长度（无限处理器的并行时间） |
| 贪心调度 | 任何时刻尽量填满处理器的调度 |
| 完全步 | 所有处理器都忙的时间步 |
| 非完全步 | 有处理器空闲的时间步 |
| 竞态条件 | 并行访问同一位置且至少一写 |
| 确定性竞态 | 即使结果相同也违反「同输入同输出」 |

**辨析｜易错点：** 不要把「$T_\infty$」误解为「运行时间」——它是「无限处理器下的理想并行时间」，是**关键路径**的长度。$T_\infty$ 只取决于依赖结构，与处理器数无关；它是加速比的「不可压缩下限」。理解了「$T_\infty$ 是结构属性而非运行指标」，调度定理的每一项都有清晰含义。

## 7 常见疑问快速答疑

**问：$T_1$ 和 $T_\infty$ 怎么测？** 串行运行（或逐个执行所有任务）得 $T_1$；把「无依赖可并行」的任务摊开、只计关键路径得 $T_\infty$。它们都是「任务图的属性」，不依赖具体机器——先画 DAG，再算两个数。

**问：为什么叫「贪心」调度？** 因为它在每一步「贪心地」尽量多开工（有就绪任务就派空闲处理器）。它不预测未来、不追求最优，但定理保证它足够好——「贪心 + 可证明的界」是并行调度里的主流范式。

**问：竞态一定能被检测到吗？** 检测工具（Cilksan/ThreadSanitizer）能报「并行访问同一位置」，但要有足够的测试覆盖不同调度顺序才能暴露。**没有工具能证明「无竞态」**——只有「确定性检查器 + 逻辑审查」相结合，才接近可靠。

**问：为什么「结果碰巧对」也算竞态？** 因为结果依赖「读-改-写」的时序：若未来调度变了（换了机器、优化了编译器），读-改-写被打断，结果就不同。确定性算法的承诺是「同输入必同输出」——时序敏感就违反承诺，哪怕当前恰好每次都对。

**问：锁能解决所有竞态吗？** 能消除「数据竞态」，但会引入「死锁」「活锁」等新问题，且损害并行度。优先「消除共享写」（局部变量 + 归约），锁是最后手段——「少共享」比「会加锁」更符合并行设计的本质。

## 8 小结

- **贪心调度定理**：$T_P \le T_1/P + T_\infty$——完全步（推进工作）+ 非完全步（啃关键路径）。
- **线性加速条件**：$P \ll$ 并行度 $T_1/T_\infty$；推论 $P \le T_1/T_\infty \Rightarrow T_P \le 2T_1/P$。
- **竞态条件**：并行访问同一位置且至少一写，结果依赖调度——不可预测。
- **确定性竞态**：即使值相同也违反「同输入同输出」的确定性要求。
- 修复：消除共享写（局部变量 + 归约）；调试用确定性检查器而非「多跑几次」。
- $T_\infty$ 是关键路径（结构属性），不是运行指标——它是加速比的不可压缩下限。
- 贪心调度是「尽量填满处理器」的策略，不预测未来但可证明足够好。
- 锁能除竞态但引入死锁等新问题——「少共享」优于「会加锁」。
- 没有工具能证明「无竞态」——确定性检查器 + 逻辑审查才接近可靠。
