## 为什么从 HTTP 开始

如果说 Web 是互联网最成功的应用，那 **HTTP（HyperText Transfer Protocol，超文本传送协议）** 就是这台应用的「会话语言」。它是应用层**最重要、最普及**的协议——你浏览的每个网页、提交的每个表单、加载的每张图片，背后都是 HTTP 请求与响应。<span class="marginnote">HTTP 是一个<strong>「请求-响应」模式</strong>的应用协议：<strong>客户端发请求、服务器回响应，一问一答</strong>。它的设计极其简洁——基于 TCP、无状态、文本报文。正是这种简洁，让它统治 Web 三十多年。学 HTTP，要从「报文长什么样」与「请求方法有哪些」入手。</span>

这一节讲：**HTTP 的特点、请求/响应报文结构、请求方法与状态码。**

## 1 HTTP 的基本特点

**HTTP**：万维网的应用层协议，定义浏览器与服务器之间交换报文的规则。它的特点：

**请求-响应模式**：客户端发请求，服务器回响应，一问一答。
**基于 TCP**：HTTP/1.x 跑在 TCP 之上（80 端口，HTTPS 为 443）。
**无状态（stateless）**：服务器不记住之前的请求——每个请求都是独立的。<span class="marginnote">「无状态」是 HTTP 的基因：<strong>服务器不保留「上次会话」的记忆</strong>。好处是简单、可扩展（服务器无需维护状态、可以随意横向扩展）；坏处是「记不住你是谁」——所以后来有了 Cookie、Session 来「伪造」状态（下一节专讲）。「<strong>无状态是设计，Cookie 是补丁</strong>」是对 HTTP 状态问题的最好概括。</span>

**辨析｜易错点：** **HTTP 基于 TCP 但 HTTP 本身是无状态的**——「基于 TCP」说的是传输方式，「无状态」说的是会话记忆，两者不矛盾。另外，HTTP/1.x 是**文本协议**（报文可读），HTTP/2/3 是二进制协议（第 9 章）。**「HTTP 报文是人类可读的文本」**是理解报文结构的前提。

## 2 HTTP 请求报文：客户端的「订单」

HTTP 请求报文由三部分组成：**请求行 + 首部行 + 实体主体**。

**请求行**的格式：

```text
GET /index.html HTTP/1.1
```

**方法**（GET）：要做什么操作。
**URL**（/index.html）：要哪个资源。
**版本**（HTTP/1.1）：协议版本。<span class="marginnote">请求报文三部分：<strong>请求行（方法 + URL + 版本）、首部行（键值对，如 <code>Host</code>`、<code>User-Agent</code>`、<code>Cookie</code>）、实体主体（POST 时携带的数据，GET 通常为空）。首部行以「字段名: 值」的形式给出请求的附加信息。</strong></span>

**常见的首部字段**：

| 首部 | 含义 |
| --- | --- |
| Host | 目标主机（HTTP/1.1 必填） |
| User-Agent | 客户端软件标识 |
| Accept | 客户端接受的内容类型 |
| Content-Type | 实体主体的类型 |
| Cookie | 携带会话状态 |

**辨析｜易错点：** **HTTP/1.1 必须带 Host 首部**——因为一台服务器可以托管多个域名（虚拟主机），服务器靠 Host 区分「你要访问哪个网站」。**「Host 是虚拟主机的门牌」**是理解现代 Web 托管的关键。

## 3 请求方法：HTTP 的「动词」

HTTP 定义了一组请求方法（动词），最常用的：<span class="marginnote">HTTP 方法本质是「对资源做什么」的语义标签：<strong>GET 取、POST 提交、PUT 整体更新、DELETE 删除、HEAD 只要头</strong>。理解方法的关键是「语义」——GET 是「读」，POST 是「写」，它们对资源的含义不同，也就决定了缓存、幂等等行为。</span>

| 方法 | 语义 | 是否携带数据 | 说明 |
| --- | --- | --- | --- |
| GET | 获取资源 | 否（参数在 URL） | 读操作、可缓存 |
| POST | 提交数据 | 是（实体主体） | 写操作、不缓存 |
| PUT | 整体更新 | 是 | 幂等 |
| DELETE | 删除资源 | 否 | 幂等 |
| HEAD | 只要响应头 | 否 | 像 GET 但无正文 |

**辨析｜易错点：** GET 与 POST 是最高频的考点：**GET 的参数放在 URL 里、可见、可缓存、用于读；POST 的参数放在主体里、隐蔽、不可缓存、用于写**。还有一个易错点：**「幂等（idempotent）」**——GET/PUT/DELETE 重复执行结果相同（幂等），POST 不幂等（重复提交会重复创建）。**「GET 读、POST 写、幂等性」**是 HTTP 方法的核心语义。

### 一个完整请求报文示例

把上面讲的拼成一份真实可见的 HTTP 请求报文：

```text
POST /login HTTP/1.1
Host: www.example.com
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64)
Content-Type: application/x-www-form-urlencoded
Content-Length: 26

username=alice&password=123
```

**辨析｜易错点：** 报文首部与正文之间**必须空一行（CRLF）**——这是报文结构的分界。`Content-Length` 告诉接收方正文有多少字节；空行之前是「首部行」，空行之后是「实体主体」。**「空行是首部与正文的分水岭」**是阅读任何 HTTP 报文的第一步。

## 4 HTTP 响应报文：服务器的「回执」

响应报文由：**状态行 + 首部行 + 实体主体** 组成。状态行的格式：

```text
HTTP/1.1 200 OK
```

**状态码**是三位数字，按首位分五类：<span class="marginnote">状态码是服务器给客户端的「体检报告」：<strong>2xx 成功、3xx 重定向、4xx 客户端错误、5xx 服务器错误</strong>。常考的：<strong>200 OK（成功）、301 永久重定向、302 临时重定向、304 未修改（用缓存）、404 未找到、403 禁止、500 服务器内部错误、502 网关错误、503 服务不可用</strong>。抓包/排障时，看状态码第一位就能定位「问题在客户端还是服务器」。</span>

| 状态码范围 | 含义 | 常见例子 |
| --- | --- | --- |
| 1xx | 信息 | 100 Continue |
| 2xx | 成功 | 200 OK |
| 3xx | 重定向 | 301、302、304 |
| 4xx | 客户端错误 | 400、403、404 |
| 5xx | 服务器错误 | 500、502、503 |

**辨析｜易错点：** **4xx 与 5xx 的区分是「责任方」**：4xx 是「你的请求有问题」（404 资源不存在），5xx 是「服务器自身出问题了」（500 内部错误）。**「4 是你错，5 是我错」**是记忆口诀。另外，**304 Not Modified** 很特殊——它不是错误，而是「你可以用缓存」的指示，与 Web 缓存机制密切相关（下一节）。

### 一次真实的「请求-响应」往返

把请求与响应串成一个完整回合（以访问 `www.example.com` 为例）：

| 方向 | 报文 | 关键内容 |
| --- | --- | --- |
| 客户端 → 服务器 | `GET / HTTP/1.1` + `Host: www.example.com` | 请求默认页 |
| 服务器 → 客户端 | `HTTP/1.1 200 OK` + `Content-Type: text/html` | 返回网页正文 |

**辨析｜易错点：** 一个完整的 Web 访问背后是**无数个这样的回合**——网页里的每张图片、每个脚本都会再发一次请求（HTTP/1.1 靠持久连接复用同一条 TCP）。**「打开一个网页 = 发起几十个 HTTP 请求」**，这是理解 Web 性能优化的起点，也是下一节持久连接要解决的痛点。

## 5 小结

- **HTTP 特点**：请求-响应、基于 TCP、无状态、文本报文。
- **请求报文**：请求行 + 首部行 + 实体主体；Host 首部必填。
- **请求方法**：GET（读）、POST（写）、PUT（更新）、DELETE（删除）、HEAD（只要头）。
- **响应报文**：状态行 + 首部行 + 实体主体。
- **状态码**：1xx 信息、2xx 成功、3xx 重定向、4xx 客户端错、5xx 服务器错。
- **黄金记忆**：4xx 是你错，5xx 是我错；GET 读、POST 写。
