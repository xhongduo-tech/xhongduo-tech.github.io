# 计算机网络体系结构：协议与分层

## 为什么从体系结构开始

互联网里有数以亿计的设备，来自不同厂商，运行不同系统，却能在毫秒级互相通信。靠什么？靠大家都遵守同一套"规矩"。而这套规矩绝不是一张纸能写完的——从电信号到网页，要协调的事情实在太多，任何一台机器都扛不住"一次性规定所有细节"。

计算机科学家想出的办法，是把通信这件超级复杂的事**切成一层一层的梯子**：每一层只解决一类问题，层与层之间通过清晰的小口子衔接。这就是**计算机网络体系结构**。

这一节是整个专题的"脚手架"：后面所有章节——物理层、数据链路层、网络层、运输层、应用层——都是在给这架梯子的某一级做特写。先把架子搭明白，后面每一块砖才放得进去。它也是理解"为什么协议要设计成那样"的总钥匙：**任何协议的取舍，几乎都能回到"这一层该管什么、不该管什么"的分工上来**——比如为什么 IP 不保证可靠而 TCP 保证可靠，答案就藏在这套分工里。

## 1 协议：网络的"语言规范"

**网络协议（network protocol）**：为进行网络中的数据交换而建立的规则、标准或约定。它回答一个朴素的问题——两台机器凭什么能"互相听懂"？

答案与两个人对话是同一件事。对话要有语法（词怎么排列成句）、要有语义（每个词是什么意思）、要有先后次序（你说完我再说）。网络协议对应地也有**三要素**：

| 要素 | 回答的问题 | 网络中的例子 |
| --- | --- | --- |
| **语法（syntax）** | 数据与控制信息的结构或格式 | 分组的首部字段怎么排、各占多少位 |
| **语义（semantics）** | 发出何种控制信息、完成何种动作、做出何种应答 | 路由器收到"目的不可达"该如何反应 |
| **时序（timing / 同步）** | 事件实现顺序的详细说明 | 先发 SYN 再发 ACK，先后次序不能乱 |

**协议三要素缺一不可**：格式对但含义理解错，是语义出错；含义对但顺序乱，是时序出错；顺序对但字段错位，是语法出错。任何一个出错，两台机器都无法正常对话。<span class="marginnote">"语法/语义/时序"与程序设计语言里的 syntax/semantics 一脉相承：语法管形式，语义管含义，时序管过程。这也是为什么学网络的人往往对编译原理、形式语言有一种天然的亲切感——它们在第二级《程序设计语言原理》里有更严格的展开。</span>

**辨析｜易错点：** 协议是一种**水平约定**——它约束的是"同一层"的两台机器如何对话。我们常说"机器 A 与机器 B 之间跑着 TCP 协议"，指的是两台机器各自的传输层在对等通信，而不是说协议横跨了某一台机器的所有层。把"协议"想成一条横线、把"层"想成一条竖线，是建立体系结构心智的第一步。

## 2 分层：把复杂通信拆成梯子

协议解决了"如何说话"，但通信涉及的问题实在太多，单一协议无法胜任。于是网络采用**分层（layering）**：把庞大复杂的通信问题，划分成若干个较小的、局部的问题，每层解决一部分，层与层之间靠接口衔接。

**分层的好处**可以列出五条：

1. **各层独立**：某层的实现改动，不影响其他层——换一种物理介质，不必重写上层逻辑。
2. **灵活性好**：每层可以选择最合适的实现方式。
3. **结构上可分割**：各层可以单独开发、单独测试。
4. **易于实现和维护**：问题被局部化，调试只盯一层。
5. **促进标准化**：层间接口固定，不同厂商的产品可以互连。

分层的边界怎么划？原则是：**每层功能应明确、相对独立；层间接口清晰、信息量尽量少；层数适中**——太多则开销大，太少则每层过于复杂。

用寄一封信来感受分层的分工：你只负责写信（应用层的事），邮局把信装进信封、决定走哪个邮局（网络层的路由），运输车队把邮袋搬到下一站（数据链路层的相邻传送），司机只管开车、对信里写了什么毫不知情（物理层的透明比特传输）。**每一层都对上一层的"内容"无感，只做好自己那一跳**——这正是分层让庞大系统可维护、可替换的根源。

**辨析｜易错点：** 分层不是免费的午餐。每一层都要给自己的数据加一个**首部（header）**，这些首部不是有效载荷，是纯开销。分层让结构清晰，但**清晰是有代价的**——这正是后文"公式解析"要算的账。<span class="marginnote">还记得分组交换那篇文章里"分组 = 切片 + 首部"吗？那个首部就是分层层层叠加的结果。数据每穿过一层，就多戴一顶"帽子"，到线路上时已经戴了好几顶。</span>

## 3 数据在层间怎么走：封装与解封装

分层的"梯子"不是摆设，数据真的要从梯子顶上爬到梯子脚下。这个过程有两个方向相反的动作。

**封装（encapsulation）**：发送方的高层数据要送到网络上，必须**自上而下**逐层穿越。每一层收到上一层的数据，先把它当成"载荷"，然后**加上本层的首部**，再交给下一层。就像寄快递：货物（应用数据）先包一层泡沫（某一层首部），再放进纸箱（另一层首部），再贴上快递单（又一层首部）——一层套一层。

**解封装（decapsulation）**：接收方拿到比特流，**自下而上**逐层向上。每一层剥掉属于自己的首部，把剩下的"载荷"交给上一层。剥到最顶层时，剩下的正是当初那份应用数据。

这两句是整门课的"主干道"：

**发送端：应用数据 → 逐层加首部 → 比特流上线路；接收端：比特流 → 逐层剥首部 → 应用数据。**

用一个 5 层模型算一笔具体的账：应用层生成 100 字节数据，运输层加 20 字节 TCP 首部，网络层加 20 字节 IP 首部，数据链路层再加 18 字节以太网首部——到线路上时，一个 100 字节的消息已经膨胀成 158 字节的帧。**你发出去的有效载荷只占约 63%**，这就是"分层税"的直观版。

**辨析｜易错点：** 封装时每一层加的是"自己那层的首部"，接收时每一层剥的也是"自己那层的首部"——**首部必须与本层对应，不能跨层剥**。运输层只能读懂运输层首部（端口号），网络层只能读懂网络层首部（IP 地址）。这也是为什么抓包工具里，同一个数据包能看到一层套一层的首部，每一层都各管一段。<span class="marginnote">这条封装/解封装的流水线，是下一节《五层协议体系结构与封装、解封装》的主角。今天先把"每层戴帽、逐层摘帽"的方向感记住，后面读帧格式、IP 数据报格式、TCP 报文段格式时就不会迷路。</span>

## 4 公式解析：分层是有代价的——首部开销

假设应用进程产生 $D$ 字节的用户数据。数据要穿过 $N$ 层，每一层给它加上 $H_i$ 字节的首部（$i = 1, 2, \dots, N$），然后交给下一层。最终送上链路的总数据量为

$$
D_{\text{总}} = D + \sum_{i=1}^{N} H_i
$$

定义**首部开销率**为首部占总数据量的比例：

$$
r = \frac{\sum_{i=1}^{N} H_i}{D + \sum_{i=1}^{N} H_i} \times 100\%
$$

逐步拆解：

- **第 1 步，理解 $D_{\text{总}}$**：$N$ 层、每层加 $H_i$ 字节首部，总首部就是 $\sum H_i$，加上原始数据 $D$，得到线路上实际传送的字节数。$N$ 越大、每层首部越厚，总数据越膨胀。
- **第 2 步，理解开销率 $r$**：分子是首部总量，分母是总数据量，比值就是"有多少比特是在为分层买单"。$r$ 越接近 0 越划算。
- **第 3 步，代入两组数字感受量级**：假设每层首部 $H = 20$ 字节、共 5 层（五层协议模型），则总首部 $= 100$ 字节。若用户数据 $D = 100$ 字节，则 $r = 100/(100+100) = 50\%$——**一半带宽花在首部上**；若 $D = 1460$ 字节（一个典型的大 IP 分组），则 $r = 100/(1460+100) \approx 6.4\%$——开销可以接受。

**这就是"小包大开销"的根源**：交互式短消息（如一条 ping、一次 DNS 查询）本身只有几十字节，首部开销却可能超过一半；而大数据块传输时，开销被摊薄。设计协议时，人们不得不在"层数带来的清晰"与"首部带来的开销"之间权衡——这也是为什么现实世界最终没有采用层数最多的那个模型，而选择了更精简的体系（下一节讲 OSI 时会看到）。

这笔账还能解释一个日常现象：以太网把单个数据帧的有效载荷上限（MTU）定在 1500 字节附近，就是"层数、首部、效率"三方博弈的产物——定太大，一旦出错重传代价高；定太小，首部开销占比飙升。**每个协议参数背后，几乎都站着一个类似的开销公式。**

## 5 两种服务体系：面向连接与无连接

分层把通信拆开，但还有一个横切的问题：**层与层之间提供的是什么样的服务？** 计算机网络的经典二分法由此而来。

**面向连接服务（connection-oriented service）**：通信前先"握手"建立连接，双方确认状态后开始传输，结束再释放。它的典型形象是**打电话**——先拨号接通，再说话，最后挂断。可靠性高，但有建立连接的开销。

**无连接服务（connectionless service）**：直接发送数据，每个数据单元独立寻址、独立传输，不必事先建立连接。它的典型形象是**寄信**——写好地址投进邮筒就行，信与信之间互不依赖，但也可能丢失、乱序。

**辨析｜易错点：** "面向连接"不等于"可靠"，"无连接"不等于"不可靠"。面向连接只是说"通信前有状态协商"，可靠性还要看层内协议怎么实现；无连接虽然不建立连接，但上层可以通过确认与重传把不可靠变可靠。**连接性说的是"怎么组织通信"，可靠性说的是"怎么弥补错误"——两个维度，别混在一起。** 这一对概念在网络层会以"虚电路 vs 数据报"的身份再次登场，在传输层则分别由 TCP（面向连接）与 UDP（无连接）继承。

现实中两者常常并存：浏览网页用面向连接的 TCP，因为网页文件一个字节都不能少；视频通话用无连接的 UDP，因为宁可丢一帧画面，也不愿为了重传而让整场会议卡顿——**应用的需求决定了它选择哪种服务**。这个"需求驱动选择"的思路，到应用层讲 HTTP、RTP 时会反复出现。<span class="marginnote">四篇文章前我们讲过电路交换"面向连接"、分组交换"无连接"——那就是这个二分法第一次露面。现在它在"服务体系"的层面正式被定义，后面网络层、传输层还会各深化一次。</span>

## 6 小结

- **网络协议**：为数据交换建立的规则；三要素是**语法、语义、时序**，缺一不可。
- **分层**：把复杂通信拆成多层梯子；五条好处——独立、灵活、可分割、易实现维护、促标准化。
- **分层有代价**：每层加首部，开销率 $r = \sum H_i / (D + \sum H_i)$；小包时开销可超 50%。
- **服务体系**：面向连接（电话）与无连接（寄信），连接性与可靠性是两个正交维度。
- **封装与解封装**：发送端逐层加首部、接收端逐层剥首部，首部必须与本层对应、不能跨层剥。
- **下一步**：实体、协议、服务与服务访问点的精确定义，将在这套脚手架上继续搭建。

分层、封装、两种服务——这三个词已经把计算机网络体系的骨架讲完了。接下来我们去看历史上最完整、也最"教科书级"的一架梯子——**OSI 七层参考模型**：它把分层思想推到了极致，也正因为层数太多，最终没能成为互联网的实际标准。
