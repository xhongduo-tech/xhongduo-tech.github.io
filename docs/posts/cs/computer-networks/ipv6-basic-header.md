## 为什么从 IPv6 开始

IPv4 地址只有 32 位——约 43 亿个，早已枯竭（NAT 只能缓解，不能根治）。**IPv6（Internet Protocol version 6）** 把地址扩到 **128 位**，同时还对首部做了大刀阔斧的简化。<span class="marginnote">128 位地址的数量级：$2^{128} \approx 3.4 \times 10^{38}$，足够给地球上每一粒沙子分配数以亿计的地址。但 IPv6 的变革不止于「地址变长」——它把首部结构也重新设计，去掉了校验和、去掉了分片字段，让路由器转发更快。理解 IPv6 = 理解「新一代 IP 的设计哲学」。</span>

这一节讲：**IPv6 地址表示、地址类型、首部格式与 IPv4 的对比。**

## 1 IPv6 地址表示：冒号十六进制

IPv6 地址长 **128 位**，写成 **8 组 4 位十六进制数**，组间用冒号隔开：

$$
\text{2001:0db8:0000:0000:0000:ff00:0042:8329}
$$

**压缩规则**：<span class="marginnote">两条压缩规则要记牢：① <strong>每组前导的 0 可以省略</strong>（`0db8` → `db8`）；② <strong>连续的全 0 组可以用 `::` 代表一次</strong>（`2001:db8::ff00:42:8329`）。但 `::` 只能使用一次——否则无法确定它代表几组 0。</span>

**规则一（省略前导 0）**：每组开头的 0 可以去掉，如 `0db8` → `db8`。
**规则二（双冒号压缩）**：连续的全 0 组可压缩为 `::`，且**只能压缩一次**。

**辨析｜易错点：** 压缩规则的坑：① `::` **只能出现一次**——写两次就分不清每组有多少 0；② 前导 0 可省、**末尾的 0 不能省**（`1000` 不能写成 `1`）；③ 判定地址长度：把 `2001:db8::ff00:42:8329` 展开回 8 组才能数位。**「`::` 只能用一次」是最常考的规则。**

### 一个数值例子：压缩与展开

把 `2001:0db8:0000:0000:0000:ff00:0042:8329` 压缩成最短形式：

| 步骤 | 地址 | 规则 |
| --- | --- | --- |
| 原始 | 2001:0db8:0000:0000:0000:ff00:0042:8329 | — |
| 省前导 0 | 2001:db8:0:0:0:ff00:42:8329 | 规则一 |
| 压缩全 0 组 | 2001:db8::ff00:42:8329 | 规则二（`::` 替换 3 组 0） |

反向验证：把 `2001:db8::ff00:42:8329` 展开，数出完整 8 组，正好 128 位。**「能压缩就能展开、能展开就能数位」**——做地址长度题时，先把 `::` 展开再数，绝不会错。

## 2 IPv6 的地址类型：单播、多播、任播

IPv6 取消了广播（broadcast），地址类型变为三种：<span class="marginnote">IPv6 用「多播」取代了「广播」——广播（发给所有人）是 IPv4 的粗放做法，IPv6 的多播只发给「加入特定组」的成员，更精准。新增的「任播（anycast）」是 IPv4 没有的：<strong>任播地址对应一组机器，路由会选「最近」的一台交付</strong>——CDN、DNS 的「就近服务」常靠任播实现。</span>

| 类型 | 含义 | IPv4 对应 |
| --- | --- | --- |
| 单播（unicast） | 一对一的地址 | 单播 |
| 多播（multicast） | 一对组，发给组内成员 | 多播 + 广播 |
| 任播（anycast） | 一对组中「最近」的一个 | 无 |

**辨析｜易错点：** **IPv6 没有「广播地址」**——这是它与 IPv4 的一个显著差别。IPv6 多播地址前缀为 `FF00::/8`。另外，IPv6 的本地链路地址 `fe80::/10` 类似 IPv4 的「私有链路本地」，`::1` 是环回地址（对应 `127.0.0.1`）。

## 3 IPv6 首部：40 字节固定，简洁为王

IPv6 基本首部**固定 40 字节**，比 IPv4 的可变首部简洁得多。关键字段：

| 字段 | 位数 | 含义 |
| --- | --- | --- |
| 版本（Version） | 4 | 恒为 6 |
| 流量类别（Traffic Class） | 8 | 类似 IPv4 的 TOS |
| 流标签（Flow Label） | 20 | 标识同一条流的报文（QoS 用） |
| 载荷长度（Payload Length） | 16 | 首部之后的字节数 |
| 下一个首部（Next Header） | 8 | 类似 IPv4 的协议字段，指向上层或扩展首部 |
| 跳数限制（Hop Limit） | 8 | 类似 IPv4 的 TTL |
| 源地址/目的地址 | 各 128 | 地址占首部大部分 |

**辨析｜易错点：** IPv6 首部相对 IPv4 的**三删一加**：<span class="marginnote"><strong>删除</strong>了首部校验和（每跳不用重算校验）、删除了分片字段（分片移到扩展首部，由源主机做，路由器不再分片）、删除了选项字段（选项放扩展首部）。<strong>增加</strong>了流标签（20 位，标记同一条流）。这些删除让<strong>路由器转发更简单、更快</strong>——「中间路由器只做转发，不做杂活」是 IPv6 的设计哲学。</span>

- **无首部校验和**：IPv6 首部没有校验和——每跳不必重算，转发更快。可靠性交给链路层与上层。
- **无分片字段**：IPv6 的分片只在**源主机**做（通过扩展首部），路由器不再分片——减少了「中途分片」的脆弱性。
- **扩展首部**：IPv6 用「下一个首部」链式挂接扩展首部（路由、分片、认证等），按需携带。

**辨析｜易错点：** IPv6 的「无校验和」与「无分片」常被误解为「不安全/不完整」——其实它们是把这些工作**重新分配**了：校验交给链路层（CRC）与上层（TCP/UDP 校验），分片交给源主机。**「IPv6 让路由器更纯粹」**是理解首部简化的钥匙。

## 4 IPv4 vs IPv6：一张表

| 对比维度 | IPv4 | IPv6 |
| --- | --- | --- |
| 地址长度 | 32 位 | 128 位 |
| 地址表示 | 点分十进制 | 冒号十六进制 |
| 首部长度 | 可变（20–60 字节） | 固定 40 字节 |
| 首部校验和 | 有 | 无 |
| 分片 | 路由器可分片 | 只源主机分片 |
| 广播地址 | 有 | 无（用多播取代） |
| 地址配置 | DHCP | 可自动配置（SLAAC） |
| 安全性 | IPsec 可选 | IPsec 设计内置 |

**辨析｜易错点：** 一个常见误解是「IPv6 自动加密」——**IPv6 只是把 IPsec 作为设计内置（可选），并不是所有 IPv6 流量都加密**。另一个误解是「IPv6 就是地址长一点」——它同时重构了首部、分片、地址配置（SLAAC 无状态自动配置）等一整套机制。**「IPv6 是一次架构升级，不止是地址扩容」**是理解它的正确姿势。

### SLAAC：无状态自动配置

IPv4 时代设备地址靠 DHCP（服务器分配）；IPv6 引入 **SLAAC（Stateless Address Autoconfiguration）**——设备自己生成地址，不需要服务器「审批」：

1. 设备先构造**本地链路地址** `fe80::/10`（接口标识由 MAC 派生或随机生成）。
2. 向路由器的**多播地址**发送「路由器请求」，拿到前缀（如 `2001:db8:1::/64`）。
3. 前缀 + 接口标识拼接出**全局单播地址**，再做**重复地址检测（DAD）**确认无人占用。

**辨析｜易错点：** **SLAAC 是「无状态」的——路由器不记录谁拿了哪个地址**，这跟 DHCP 的「有状态分配 + 租约管理」完全不同。但实际网络中两者常并存：**SLAAC 给地址，DHCPv6 再下发 DNS 等额外配置**。**「无状态管地址、有状态管配置」**是现代 IPv6 双轨配置的常态。

补充一个细节：SLAAC 用「路由器请求/通告（RS/RA）」报文交互，RA 里还带「地址生命周期」等参数；DAD 则是向「被请求结点多播组」发一个探询报文，若无人应答才确认地址唯一。**「先自建、后探测、无冲突才用」**——这套自动配置流程是 IPv6「即插即用」能力的核心。

## 5 小结

- **IPv6 地址**：128 位，冒号十六进制（8 组），两条压缩规则，`::` 只能一次。
- **地址类型**：单播、多播、任播；无广播（多播取代）；`::1` 环回。
- **IPv6 首部**：固定 40 字节，无校验和、无分片字段，有流标签。
- **三删一加**：删校验和/分片/选项（进扩展首部），加流标签。
- **设计哲学**：路由器更纯粹——只转发，杂活交给源主机与上层。
- **对比 IPv4**：不止地址扩容，还有首部、分片、配置、安全的全方位升级。
