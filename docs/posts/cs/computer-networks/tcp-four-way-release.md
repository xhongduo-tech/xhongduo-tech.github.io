## 为什么从四次挥手开始

连接建立要三次握手，释放则要**四次挥手（four-way handshake）**。为什么挥手比握手多一次？因为 TCP 是**全双工**的——两个方向的传输是独立的，**每一方向都要单独关闭**。<span class="marginnote">四次挥手的过程：<strong>A 说「我发完了」（FIN），B 回「知道了」（ACK）；B 说「我也发完了」（FIN），A 回「知道了」（ACK）</strong>。两个方向各一次 FIN + 各一次 ACK，就是四次。中间 A 的 FIN 与 B 的 ACK 之间，连接还处于「半关闭」状态——B 还能继续给 A 发数据。</span>

这一节讲：**四次挥手的每一步、为什么需要四次、以及 TIME_WAIT 状态的秘密。**

## 1 四次挥手的全过程

设 A 主动关闭连接：

1. **A → B：FIN**。A 发送 `FIN=1, seq=u` 的报文段，进入 **FIN_WAIT_1** 状态。「我的数据发完了，我要关闭我的发送方向。」
2. **B → A：ACK**。B 发送 `ACK=1, seq=v, ack=u+1` 的报文段，进入 **CLOSE_WAIT** 状态。A 进入 **FIN_WAIT_2**。「收到你的 FIN，我确认。」
3. **B → A：FIN**。B 的数据也发完了，发送 `FIN=1, ACK=1, seq=w, ack=u+1` 的报文段，进入 **LAST_ACK** 状态。「我也发完了，可以关了。」
4. **A → B：ACK**。A 发送 `ACK=1, seq=u+1, ack=w+1` 的报文段，进入 **TIME_WAIT** 状态。B 收到后进入 **CLOSED**。<span class="marginnote">关键状态：<strong>FIN_WAIT_2（A 等 B 的 FIN）</strong>与 <strong>TIME_WAIT（A 等最后的 ACK 确认生效）</strong>。B 在 CLOSE_WAIT 期间还可以继续向 A 发数据——因为 B 的发送方向还没关。这个「A 关了发送、B 还能发」的窗口就是「半关闭（half-close）」。</span>

**辨析｜易错点：** 第 2 步的 ACK 与第 3 步的 FIN **是两个独立的报文**——B 的 ACK 只确认「收到 A 的 FIN」，B 的 FIN 是「B 自己的数据发完」后才发的。**「ACK 与 FIN 分开」正是四次挥手比三次握手多一次的原因**。若 B 恰好也没有数据要发，2、3 步可以合并，但标准流程是四次。

## 2 为什么必须是四次：半关闭的本质

TCP 是**全双工**的，一条连接包含**两个独立的数据流**（A→B 与 B→A）。关闭也必须分别处理：

A 发 FIN 只表示「A→B 方向的流结束了」——A 不再发数据，但 A 还可以**收** B 的数据。
B 回 ACK 只表示「确认 A 的 FIN」——B 还可以继续给 A 发数据。
等 B 也发完，B 发 FIN 关闭「B→A」方向；A 回 ACK 收尾。

**辨析｜易错点：** **三次握手为什么是三次、四次挥手为什么是四次**，可以对比记忆：握手时双方「同时确认」彼此，一次 SYN 触发的应答能带另一个方向的需求（SYN+ACK 合并），所以 3 次；挥手时两个方向的「我要关了」是**异步发生**的（A 先发完、B 后发完），FIN 与 ACK 无法始终合并，所以 4 次。**「握手是同步的，挥手是异步的」**是最本质的解释。

## 3 TIME_WAIT 状态：挥手的「余韵」

第四次挥手后，主动关闭方（A）进入 **TIME_WAIT** 状态，要**等待 2 倍 MSL**（报文最大生存时间）后才真正 CLOSED。为什么？

**让最后的 ACK 可靠送达**：如果第 4 步的 ACK 丢了，B 会重发 FIN；A 在 TIME_WAIT 期间能再回一次 ACK。若 A 立即关闭，重发的 FIN 将无人应答。
**让旧报文段在网络中自然消亡**：等待 2×MSL，确保连接期间的所有报文段都在网络中消失，不会「残留」污染后续连接。<span class="marginnote">MSL（Maximum Segment Lifetime）是报文段在网络中的最长存活时间（通常 2 分钟量级）。所以 <strong>TIME_WAIT 通常持续约 4 分钟</strong>——这就是为什么服务器大量主动关闭连接后，会出现大量「TIME_WAIT」状态的连接：它们在等旧报文消亡，不是「僵尸」，是「守夜人」。这个状态在网络排障中极常见。</span>

**辨析｜易错点：** TIME_WAIT 是**主动关闭方**才进入的状态——被动关闭方（B）收到最后的 ACK 后直接 CLOSED。**「TIME_WAIT 是主动方的状态」**是最常考的点。另外，TIME_WAIT 的时长是 **2×MSL**，不是 1×MSL——因为要覆盖「最后一次 ACK 丢失 + B 重发 FIN」的最坏情况。

## 4 挥手相关的异常与排障

四次挥手在现实中会遇到各种「意外」：<span class="marginnote">常见异常：① <strong>CLOSE_WAIT 堆积</strong>——对端发了 FIN，但本地应用一直没关闭 socket，连接卡在 CLOSE_WAIT（应用层 bug 的信号）；② <strong>FIN_WAIT_2 长期不释放</strong>——对端一直不发 FIN（可能是半关闭挂起）；③ <strong>RST 代替 FIN</strong>——异常终止时用 RST 立即断开，不完成挥手。排障时看到大量 CLOSE_WAIT，第一反应是「应用没关 socket」。</span>

| 状态 | 可能的问题 |
| --- | --- |
| CLOSE_WAIT 堆积 | 应用未关闭 socket（最常见） |
| FIN_WAIT_2 悬挂 | 对端半关闭未完成 |
| TIME_WAIT 过多 | 大量短连接主动关闭（正常但占资源） |
| RST 出现 | 异常终止、端口未监听 |

**辨析｜易错点：** RST 不是「挥手的替代品」——它是「异常中断」：端口未监听、连接超时、安全拦截时用 RST 立即终止，**不经历四次挥手**。**「正常关闭走 FIN，异常中断走 RST」**是一句话判别。

## 5 三次握手与四次挥手：一张对比表

把「相识」与「告别」并排看，最能看清二者的对称与不对称：<span class="marginnote"><strong>握手 = 同步 + 确认</strong>：SYN 与 SYN+ACK 各带一个序列号，一次应答同时确认对方的 SYN，所以 3 次；<strong>挥手 = 各自关闭</strong>：两个方向的 FIN 异步到达，且 B 的 ACK 只确认「收到 FIN」、不替自己的 FIN 表态，所以 4 次。<strong>「握手合并确认，挥手分开声明」</strong>是记住「3 对 4」的最短口诀。</span>

| 维度 | 三次握手（建立） | 四次挥手（释放） |
| --- | --- | --- |
| 报文数 | 3 | 4 |
| 触发方式 | 双方同时「可通」 | 双方各自「发完」 |
| 应答可否合并 | SYN 与 ACK 可合并为 SYN+ACK | FIN 与 ACK 通常分开（除非双方同时关闭） |
| 双方状态 | 同步（SYN_SENT ↔ SYN_RCVD） | 异步（各自 FIN_WAIT ↔ CLOSE_WAIT） |
| 结束后状态 | 进入 ESTABLISHED | 主动方 TIME_WAIT，被动方 CLOSED |
| 遗留对象 | 无 | TIME_WAIT（2×MSL） |

**辨析｜易错点：** 有一种「四次挥手变三次」的例外：**若 A 与 B 同时发起关闭**（两个 FIN 交叉），则双方都会进入 CLOSE_WAIT/LAST_ACK 与 FIN_WAIT，此时 FIN 与 ACK 可以合并，变成「两个 FIN + 两个 ACK 交叉」的收尾——但它依然不是「三次」，本质仍是每个方向各一次 FIN。**「遇到同时关闭时挥手次数会变，但每个方向必须有一次 FIN」**是判断标准。

## 6 关闭连接在真实应用里的样子

挥手不只是状态机，它直接影响程序行为：<span class="marginnote"><strong>Linux 的 <code>close()</code></strong>` 触发正常 FIN 流程；<strong><code>SO_LINGER</code></strong>` 选项可以把「优雅关闭」改成「立即 RST」；服务端大量的短连接会制造 <strong>大量 TIME_WAIT</strong>，运维常用 <code>net.ipv4.tcp_tw_reuse</code> 等参数缓解。<strong>「一个连接的生老病死，都写在 socket 系统调用的返回值里」</strong>。</span>

- **优雅关闭**：程序调用 `close()` 后，内核代发 FIN，走完四次挥手；若 socket 发送缓冲区还有数据，会先发完再 FIN。
- **异常关闭**：调用方 `close()` 但发送缓冲区有未确认数据、或对端已不可达，内核可能改发 RST，跳过挥手直接断开。
- **半关闭**：`shutdown(SHUT_WR)` 只关闭发送方向，接收方向保持——正是本节讲的「半关闭」在系统调用层面的实现，常用于「我发完了、但还要读你的数据」的场景。
- **大量 TIME_WAIT**：高并发短连接服务（如一次性的 API 调用）主动 close 后，本机 TIME_WAIT 会堆积；这是「正常但占端口资源」的现象，排障时不要误判为泄漏。

**辨析｜易错点：** 很多面试题问「TIME_WAIT 多了怎么办」。答案分两步：先确认是不是「正常的短连接主动关闭」；如果是，再谈内核参数（`tcp_tw_reuse`、`tcp_tw_recycle`）与改用长连接/让对端先关闭等方案。**「先判断是否正常，再谈优化」**——上来就改内核参数是排障大忌。

## 7 术语速查：挥手的全部关键词

把挥手涉及的状态与参数汇成一张速查表，考前扫一眼就能定位：<span class="marginnote"><strong>速查用法</strong>：看到「连接释放」题，先判断「谁主动关闭、当前在哪个状态」，再查该状态的进入条件与下一步。<strong>四个常考状态 = FIN_WAIT_1、FIN_WAIT_2、CLOSE_WAIT、LAST_ACK + TIME_WAIT</strong>。</span>

| 术语 | 状态/含义 | 关键点 |
| --- | --- | --- |
| FIN_WAIT_1 | A 已发 FIN，等 B 的 ACK | 主动关闭方 |
| FIN_WAIT_2 | A 收到 ACK，等 B 的 FIN | 半关闭窗口期 |
| CLOSE_WAIT | B 收到 FIN，等应用关 socket | 应用层 bug 高发地 |
| LAST_ACK | B 已发 FIN，等 A 的 ACK | 被动方最后一站 |
| TIME_WAIT | A 等 2×MSL | 主动方独有 |
| MSL | 报文段最长生存时间 | 通常 2 分钟量级 |
| SO_LINGER | socket 选项 | 可把关闭改为立即 RST |

**辨析｜易错点：** 判断「谁进 TIME_WAIT」时，记住一个镜像规律：**握手时被动方进 SYN_RCVD，挥手时主动方进 TIME_WAIT**——「主动发起的一方承担收尾义务」，因为只有它知道「最后的 ACK 是否可能丢失」。**「谁发起、谁守夜」**是 TIME_WAIT 归属的终极口诀。

## 8 小结

- **四次挥手**：FIN → ACK → FIN → ACK，每个方向单独关闭。
- **为什么四次**：全双工、两方向异步关闭，FIN 与 ACK 无法始终合并。
- **半关闭**：一方 FIN 后另一方还能继续发数据（CLOSE_WAIT 期间）。
- **TIME_WAIT**：主动关闭方的状态，持续 2×MSL（约 4 分钟），保证 ACK 可靠与旧报文消亡。
- **异常处理**：正常关闭走 FIN，异常中断走 RST；CLOSE_WAIT 堆积 = 应用没关 socket。
- **排障坐标**：卡在哪个状态，就指向哪一类问题。

最后留一个复习锚点：**背四次挥手，就背「两个方向、各自 FIN、主动方守夜」这十二个字**——把十二个字展开，就是本节全部内容。TCP 的连接管理是「面向连接」的完整画像，而这张画像的另一半——可靠传输与滑动窗口——正是我们在接下来几节要揭开的面纱。

顺手练一道题检验掌握：**「服务器上 CLOSE_WAIT 堆积说明什么？」** 答案应是「有连接收到了对端的 FIN，但服务器进程一直没调用 `close()` 关闭自己的 socket」——先想到「状态卡在哪」，再想到「对应什么代码行为」，挥手排障就从「背状态名」升级成了「诊断思维」。
