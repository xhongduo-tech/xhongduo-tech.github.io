# HTTP/2：二进制分帧、多路复用与头部压缩（HPACK）

<div class="epigraph">

## 为什么从 HTTP/2 开始

HTTP/1.1 用了二十年，暴露了性能瓶颈：**队头阻塞、头部冗余、单连接串行**。2015 年 **HTTP/2** 发布，**不改变 HTTP 的语义（方法、状态码、首部都兼容），只改变「传输方式」**——从「文本」变成「二进制分帧」，从而实现了多路复用。<span class="marginnote">HTTP/2 的核心思想：<strong>「语义不变、传输重构」</strong>——应用层的 GET/POST/200 等都照旧，但<strong>底层把 HTTP 报文拆成「帧」在一条连接上并行传输</strong>。这就像同一栋楼的收件还是那些（语义），但快递系统从「一车一送」变成了「一车多箱分拣」（传输）。</span>

这一节讲：**HTTP/1.1 的问题、HTTP/2 的二进制分帧、多路复用、HPACK 头部压缩。**

## 1 HTTP/1.1 的三座大山

HTTP/1.1 的三个性能问题：<span class="marginnote"><strong>① 队头阻塞（HOL blocking）</strong>：一条连接上「发一个等一个」，前一个响应慢了，后面的全排队等着——即使服务器能同时算好。<strong>② 头部冗余</strong>：每个请求都带大量重复的首部（Cookie、User-Agent），浪费带宽。<strong>③ 连接受限</strong>：浏览器对每域名连接数有限制，且建立多条连接开销大。<strong>「一个慢响应拖垮整条连接」</strong>是 HTTP/1.1 队头阻塞的写照。</span>

**队头阻塞**：一条连接串行，前一个慢、后面全堵。
**头部冗余**：每个请求重复携带大量首部。
**连接数受限**：浏览器限制每域名并发连接数。

**辨析｜易错点：** **HTTP/1.1 的「队头阻塞」发生在应用层**——它说的是「HTTP 响应排队」，不是「TCP 的队头阻塞」（那是另一层的问题，HTTP/3 才处理）。**「HTTP/1.1 在一条连接里串行，慢的挡了快的」**是对队头阻塞最直白的描述。

## 2 二进制分帧：把报文拆成「帧」

**二进制分帧层（binary framing layer）**：HTTP/2 不再发送文本报文，而是把每个 HTTP 报文（请求/响应）**拆分成一个个二进制「帧（frame）」**。<span class="marginnote"><strong>帧的类型</strong>：<strong>HEADERS 帧</strong>（首部）、<strong>DATA 帧</strong>（数据）、<strong>SETTINGS</strong>（参数协商）等。<strong>每个帧携带「流标识（stream ID）」</strong>——表明它属于哪个「流」。<strong>二进制的好处</strong>：解析更快（不用逐字符解析文本）、格式更紧凑。<strong>「文本报文是给机器读的散文，二进制帧是给机器读的表格」</strong>。</span>

**帧（frame）**：HTTP/2 传输的最小单位，二进制格式。
**帧类型**：HEADERS（首部）、DATA（数据）等。
**流标识**：每帧带 stream ID，标明属于哪个流。

**辨析｜易错点：** **HTTP/2 的帧与 TCP 的报文段、以太网的帧是不同层的概念**——HTTP/2 的帧是「应用层的报文切块」，装进 TCP 报文段传输。**「HTTP/2 帧是 TCP 报文段里的『内容』」**。另一个易错点：**HTTP/2 仍然基于 TCP**——它优化的是「TCP 之上怎么组织 HTTP 数据」，没动 TCP 本身。

## 3 多路复用：一条连接上的「并行赛道」

**多路复用（multiplexing）**：一条 TCP 连接上，**多个「流（stream）」交错传输**——每个流对应一个请求-响应，帧按流标识交错复用同一条连接。<span class="marginnote"><strong>多路复用的效果</strong>：浏览器只需一条 TCP 连接，就能并行发多个请求；服务器可以乱序返回、客户端按流重组。<strong>相比 HTTP/1.1 的「排队」</strong>，HTTP/2 是「并行交错」——慢的响应不再挡住快的。<strong>连接数减少</strong>：一条连接代替多条，减少握手与慢启动开销。<strong>「一条连接上，多个请求齐头并进」</strong>是 HTTP/2 最直观的改进。</span>

**流（stream）**：一个请求-响应的双向数据流。
**交错传输**：多个流的帧交错在同一条连接上。
**乱序返回**：服务器可以按任意顺序返回各流的响应。

**辨析｜易错点：** **多路复用 ≠ 无队头阻塞**——HTTP/2 消除了「HTTP 层的队头阻塞」，但 TCP 层的队头阻塞仍在（一个 TCP 段丢了，后面的段都堵着等重传）。**「HTTP/2 消了应用层的队头阻塞，TCP 层的还在——那是 HTTP/3 的战场」**是 HTTP/2 局限性的准确描述。

## 4 HPACK：头部压缩

**HPACK**：HTTP/2 的**头部压缩**技术，解决「头部冗余」问题。<span class="marginnote"><strong>HPACK 的思路</strong>：① <strong>静态表</strong>——常用首部（如 method: GET、:status: 200）编成固定索引，只需传索引号；② <strong>动态表</strong>——会话中出现的首部存入共享表，后续相同首部用索引引用；③ <strong>哈夫曼编码</strong>——剩余字符串压缩。<strong>效果</strong>：首部从几百字节压到几十字节。<strong>「HPACK 让首部从『每次重发』变成『索引引用』」</strong>。</span>

- **静态表**：常用首部固定索引，传索引不传文本。
- **动态表**：会话内首部共享，重复引用。
- **哈夫曼编码**：压缩剩余字符串。

**辨析｜易错点：** **HPACK 的「动态表」是双端同步的**——发送方与接收方维护相同的动态表，靠「递增更新」保持同步。**「HPACK 靠『表』压缩，表的同步是正确性的关键」**。另一个易错点：**头部压缩不是「省一点」，是「数量级」**——把重复几百字节的头部压到几十字节，对移动网络尤其重要。

## 5 小结

- **HTTP/1.1 三座大山**：队头阻塞、头部冗余、连接数受限。
- **二进制分帧**：HTTP 报文拆成二进制帧，解析更快、传输更紧凑。
- **多路复用**：一条连接多个流并行交错，慢的响应不挡快的。
- **HPACK**：静态表 + 动态表 + 哈夫曼，头部从「重发」变「引用」。
- **HTTP/2 的边界**：消除了 HTTP 层队头阻塞，TCP 层队头阻塞仍在。
- **核心思想**：语义不变、传输重构——应用层的接口照旧，底层的组织方式重写。
