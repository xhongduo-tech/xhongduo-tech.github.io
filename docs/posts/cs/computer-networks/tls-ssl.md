## 为什么从 TLS 开始

前面学了加密、签名、证书——现在把它们**组装成一套完整的协议**：**TLS（Transport Layer Security，运输层安全协议）**，即 HTTPS 中那个 S 的底层。它是网络安全知识的总集成，也是现代互联网安全的基石。<span class="marginnote"><strong>TLS</strong> 是 <strong>SSL（Secure Sockets Layer）</strong>的继任者——SSL 曾因漏洞被弃用，TLS 是它的标准化继承。它工作在<strong>应用层与运输层之间</strong>：对上层（HTTP）提供「加密的可靠通道」，对下层（TCP）透明。<strong>你每天访问的 HTTPS，就是「HTTP + TLS」</strong>。TLS 的核心是两个子协议：<strong>握手协议</strong>（建信任、商密钥）与<strong>记录协议</strong>（加密传输数据）。</span>

这一节讲：**TLS 的位置、握手协议的流程、记录协议的工作。**

## 1 TLS 在哪一层：运输层与应用层之间

TLS 不是一个「第 X 层」协议——它**介于应用层与运输层之间**：<span class="marginnote"><strong>TLS 的位置</strong>：对应用层（HTTP）而言，TLS 是「安全的传输管道」；对运输层（TCP）而言，TLS 是「它的一个用户」。所以 HTTPS = HTTP（应用）+ TLS（安全）+ TCP（传输）。<strong>TLS 把「加密」从应用层下沉到「运输层之上」</strong>——任何应用协议（HTTP、FTP、SMTP）都可以套上 TLS 获得加密（HTTPS、FTPS、SMTPS）。<strong>「TLS 是给应用协议加的一层安全外套」</strong>。</span>

从协议栈的角度看，一次 HTTPS 请求的报文是层层包裹的：**HTTP 报文 →（TLS 加密，变成 TLS 记录）→ TCP 报文段 → IP 数据报 → 以太网帧**。对 TCP 而言，它看不到任何加密痕迹，TLS 只是又一个「应用数据」；对 HTTP 而言，它把数据交给 TLS 就不再操心安全。**TLS 的透明性正是它的设计目标**——加一层安全外套，却不改变上下的接口。

**辨析｜易错点：** TLS 与 HTTP 的关系是「HTTPS = HTTP over TLS」——不是「TLS 是 HTTP 的一部分」。**「TLS 可被任何应用协议复用」**是它的通用性所在。另一个易错点：**TLS 不能「自己跑」**——它必须跑在某个可靠传输（TCP）之上，本身不提供传输功能。

## 2 握手协议：建信任、商密钥

TLS 握手的核心目标：**① 验证服务器身份（证书）；② 协商加密参数；③ 生成并交换会话密钥。** 简化版的握手流程：<span class="marginnote"><strong>① ClientHello</strong>：客户端发「我支持的 TLS 版本与加密套件」；<strong>② ServerHello + 证书</strong>：服务器选好参数，把自己的数字证书发给客户端；<strong>③ 客户端验证证书</strong>（上一节的四步验证），若通过，生成「预主密钥」，用服务器的公钥加密后发给服务器；<strong>④ 双方从预主密钥派生出会话密钥，并互相确认握手完成</strong>。之后所有数据用会话密钥对称加密传输。<strong>「握手管信任与密钥，记录管数据加密」</strong>。</span>

1. **ClientHello**：客户端发送支持的版本与加密套件列表。
2. **ServerHello + 证书**：服务器选定参数，发送数字证书。
3. **证书验证 + 密钥交换**：客户端验证证书，生成「预主密钥」，用服务器公钥加密发送。
4. **会话密钥就绪**：双方从预主密钥派生出会话密钥，握手完成。

**辨析｜易错点：** **TLS 握手里的「公钥加密」只用于传「预主密钥」这一个秘密**——之后海量数据都用派生的会话密钥做对称加密（这就是混合加密在 TLS 里的落地）。**「TLS = 公钥认证身份 + 公钥传密钥 + 对称加密数据」**是对 TLS 架构的一句话总结。另一个易错点：**TLS 1.3 简化了握手**（减少往返次数），但「验证证书 + 交换密钥」的本质不变。

## 3 记录协议：数据的安全封装

握手完成后，正式数据传输由**记录协议（record protocol）** 负责。每个「记录」的加密流程：<span class="marginnote"><strong>记录协议的工作</strong>：把应用数据<strong>分片</strong> → 对每片<strong>压缩</strong>（可选）→ <strong>加 MAC</strong>（完整性校验）→ <strong>对称加密</strong>（机密性）→ 加记录头发送。<strong>接收方反向操作</strong>：解密 → 验证 MAC（防篡改）→ 解压 → 重组交付。<strong>「先算 MAC 再加密，接收端先解密再验 MAC」</strong>——加密保机密、MAC 保完整，两者缺一不可。</span>

1. **分片**：把应用数据切成记录大小的块。
2. **加 MAC**：对每片计算完整性校验码。
3. **加密**：用会话密钥对称加密（密文 + MAC 一起）。
4. **发送**：加记录头（类型、版本、长度）发送。

**辨析｜易错点：** **记录协议把「机密性（加密）+ 完整性（MAC）」一起打包**——这就是 TLS 能同时防「窃听」与「篡改」的原因。**「加密 + MAC 是 TLS 记录的双保险」**。另一个易错点：**记录协议与握手协议是 TLS 的两半**——握手负责「开始前的谈判」，记录负责「开始后的传输」，它们共用同一套连接状态。

## 4 TLS 的安全价值：解决什么问题

把前面学的安全目标与 TLS 对应起来：<span class="marginnote"><strong>机密性</strong>：数据用会话密钥加密，窃听者看到的是密文。<strong>完整性</strong>：每条记录带 MAC，篡改会被立即发现。<strong>真实性</strong>：证书验证服务器身份，防止「连到假网站」的中间人攻击。<strong>前向保密</strong>：现代 TLS 用「临时密钥交换（ECDHE）」，即使服务器私钥泄露，历史会话也无法被解密。<strong>「TLS 是 CIA 三目标 + 防中间人的完整实现」</strong>。</span>

| 安全目标 | TLS 的实现 |
| --- | --- |
| 机密性 | 记录协议对称加密 |
| 完整性 | 记录协议 MAC |
| 真实性 | 握手协议证书验证 |
| 防中间人 | 证书绑定公钥，防偷换 |
| 前向保密 | 临时密钥交换（ECDHE） |

**辨析｜易错点：** **TLS 的「防中间人」依赖证书验证**——如果证书验证被绕过（如用户忽略证书警告），中间人攻击依然可能成功。**「TLS 的安全性 = 密码学 + 证书验证 + 用户不犯傻」**是三合一的。

## 5 小结

- **TLS/SSL**：应用层与运输层之间的安全协议；HTTPS = HTTP + TLS。
- **握手协议**：ClientHello → ServerHello + 证书 → 证书验证 + 密钥交换 → 会话密钥就绪。
- **记录协议**：分片 → MAC → 加密 → 发送；加密保机密、MAC 保完整。
- **混合加密落地**：公钥验证身份 + 公钥传预主密钥 + 对称加密数据。
- **安全价值**：机密性、完整性、真实性、防中间人、前向保密。
- **HTTPS 的本质**：HTTP 套上 TLS——小绿锁背后是完整的信任与加密体系。
