## 为什么从 AQM 与 RED 开始

TCP 拥塞控制靠「丢包当信号」工作，但**丢包发生在哪？** 在路由器的输出队列里。传统路由器用**队尾丢弃（tail drop）**——队列满就丢新到的包。这个看似简单的策略，藏着一个严重的病：**全局同步（global synchronization）。**<span class="marginnote"><strong>队尾丢弃的病症</strong>：队列一旦满，紧接着到达的多个连接的数据报被一起丢弃——这些连接的发送方几乎同时检测到丢包、几乎同时退让，又几乎同时重新增长——形成「一起堵、一起退、一起冲」的同步振荡，带宽利用率骤降。<strong>主动队列管理（AQM）</strong>就是为了治这个病：不等队列满，提前、随机、轻微地丢弃，让各 TCP 流「错峰退让」。</span>

这一节讲：**队尾丢弃的问题、AQM 思想、以及最经典的 RED 算法。**

## 1 队尾丢弃与全局同步

**队尾丢弃（tail drop）**：路由器输出队列满时，**丢弃新到达的数据报**。问题有三：<span class="marginnote">① <strong>全局同步</strong>——队列满时被丢的是「一起来」的多个流，它们同时退让、同时恢复，造成吞吐振荡；② <strong>不公平</strong>——流量大的流丢得多但恢复快，某些流可能饿死；③ <strong>全丢/全放</strong>——队列在「接近满」与「刚清空」之间大幅波动，时延抖动大。这三个问题本质上都是「反应太晚、太一刀切」。</span>

**全局同步**：多个流同时丢包、同时退让、同时增长，振荡。
**不公平**：队尾丢弃对「排队晚」的流不利。
**时延抖动**：队列在满与空之间剧烈摆动。

**辨析｜易错点：** 队尾丢弃的「全局同步」是拥塞控制理论里的经典案例——它说明：**即使每个 TCP 流都正确实现了拥塞控制，路由器「一刀切丢包」的时机也会让它们互相踩踏**。**「丢包的时机与方式」和「丢包本身」同样重要**——这正是 AQM 的出发点。

### 一个直观例子：为什么队尾丢弃会「全局同步」

设路由器的队列能装 50 个包，三条 TCP 流 A、B、C 同时在跑：

- **阶段一**：队列逐渐填到 50，满。
- **阶段二**：下一个到达的包（无论是 A、B 还是 C 的）被队尾丢弃——三条流几乎同时「感知」到丢包。
- **阶段三**：A、B、C 几乎同时进入退让，又几乎同时重新增长，再次同时把队列填满……

**辨析｜易错点：** 问题不在「丢包」，而在「**一批包同时被丢**」——三条流的拥塞信号高度同步。**「队尾丢弃丢的是『后到的』，而 AQM 丢的是『随机挑的』」**——随机性正是打破同步的关键，这也解释了为什么 AQM 的丢弃要「随机」而不是「按序」。

补一句直觉收束：**AQM 是「把一次惨烈的集体车祸，拆成多次轻微的小剐蹭」**——后者看起来损失更多（丢的包更多次），但每次都只伤一条流、且给 TCP 足够时间平滑响应，总吞吐与时延反而更好。**「小步快跑胜过一步到位」**在这套机制里体现得淋漓尽致。

再把「信号分级」串进拥塞控制的主线：**超时 = 重信号（cwnd 归 1）、三个重复 ACK = 中信号（cwnd 减半）、AQM 提前丢/ECN 标记 = 轻信号（更早、更轻微地通知）**。AQM 的价值正是把「晚而重的信号」提前成「早而轻的信号」——同一套「分级响应」思想，从端系统延伸到路由器。

## 2 主动队列管理（AQM）：提前、轻微、分散

**主动队列管理（AQM，Active Queue Management）**：路由器**不等队列满**，在队列长度超过某个阈值时，**提前丢弃（或标记）一部分数据报**，向 TCP 发送方「提前打招呼」。

AQM 的目标：<span class="marginnote"><strong>提前</strong>——在队列未满时就释放拥塞信号，避免「满则全丢」；<strong>轻微</strong>——每次只丢少量包，不让任何流遭受重创；<strong>分散</strong>——随机选择丢弃对象，让不同流「错峰退让」、避免全局同步。AQM 的思想是「把拥塞信号从「灾难性」变成「渐进式」」——这与你快恢复里学到的「分级响应」一脉相承。</span>

**提前**：队列未满就发出信号，避免溢出。
**轻微**：小比例丢弃，不重创单条流。
**分散**：随机丢弃，让各流错峰退让。

**辨析｜易错点：** AQM 的目的**不是提高吞吐**，而是**降低时延与抖动**——通过「早丢少量」避免「晚丢大量」，让队列保持短而稳。**「AQM 用一点点吞吐换低时延」**是它的工程取舍。

## 3 RED：随机早期检测

**RED（Random Early Detection，随机早期检测）**：最经典的 AQM 算法。它维护**平均队列长度**（用指数加权平滑，滤掉突发波动），据此**概率性丢弃**：

**平均队列长度 < min_th**：不丢（队列很空）。
**min_th ≤ 平均队列长度 < max_th**：以一定概率丢（概率随队列长度线性增大）。
**平均队列长度 ≥ max_th**：全部丢弃（队列已接近失控）。<span class="marginnote">RED 的三个参数：<strong>min_th、max_th、max_p</strong>（最大丢弃概率）。丢弃概率在 min_th 与 max_th 之间从 0 线性升到 max_p——<strong>「队列越长，丢得越狠」</strong>。这个「温和的、渐进式的信号」让不同 TCP 流在不同时刻被丢，从而错峰退让、避免全局同步。</span>

**公式解析：RED 的丢弃概率**

设平均队列长度为 $\bar{q}$，则：

$$
p = \begin{cases} 0 & \bar{q} < \min_{th} \\ \dfrac{\bar{q} - \min_{th}}{\max_{th} - \min_{th}} \cdot p_{\max} & \min_{th} \le \bar{q} < \max_{th} \\ 1 & \bar{q} \ge \max_{th} \end{cases}
$$

- **第一步，看区间**：$\bar{q}$ 落在三个区间之一，决定丢不丢。
- **第二步，看中间段**：丢弃概率从 0 线性升到 $p_{\max}$——队列越长越可能丢。
- **第三步，为什么用「平均」队列**：直接看瞬时队列会被突发流量带偏；平均队列滤掉突发，反映「趋势」而非「瞬间」。<span class="marginnote">RED 用「平均队列长度」而非「瞬时队列长度」，是它精妙之处：<strong>短时的突发（如一个 Web 页面的几个包）不应触发丢弃，只有持续拥塞（平均队列涨）才该发信号</strong>。这个「趋势 vs 瞬间」的思想，与 RTT 估计里的「指数加权平滑」如出一辙。</span>

**辨析｜易错点：** RED 的丢弃是**概率性**的——即使 $\bar{q}$ 在中间区间，也不是「必丢」，只是「有概率丢」。**「RED 丢包是随机抽签，不是排队报销」**。另外，RED 丢弃的对象是**随机选的**，不针对特定流——这让各流的退让时机自然错开。

## 4 从 RED 到现代 AQM：CoDel

RED 虽经典，但参数调优（min_th、max_th、max_p）在真实环境里很棘手。现代 AQM 的代表是 **CoDel（Controlled Delay，控制时延）**：<span class="marginnote">CoDel 的思路很「现代」：<strong>不盯队列长度，盯「排队时延」</strong>——如果数据报在队列里停留的最小时延超过目标值（如 5ms），就认为拥塞，开始丢弃，且丢弃间隔随时间缩短。它<strong>几乎无需参数调优</strong>，已内置于现代 Linux 的 `fq_codel` 队列规则中——你家的路由器很可能就在用它。</span>

- **CoDel**：以「排队时延」为信号，超过目标值就丢，无需繁琐调参。
- **fq_codel**：CoDel + 公平队列，现代 Linux 默认队列规则。

**辨析｜易错点：** RED 用「队列长度」，CoDel 用「排队时延」——**一个看空间、一个看时间**。CoDel 之所以好调参，是因为「时延目标」比「队列长度阈值」更接近真实体验（用户感受到的是时延，不是队列）。**「从 RED 到 CoDel，是从『看队列』到『看体验』的进化」**。

## 5 公式解析：一组 RED 参数的具体表现

光看公式太抽象，代入数字感受 RED 的行为。设 $\min_{th}=20$ 包、$\max_{th}=60$ 包、$p_{\max}=0.1$：<span class="marginnote"><strong>代入算一算</strong>：平均队列 $\bar{q}=30$ 时，$p = \frac{30-20}{60-20} \times 0.1 = 0.025$，即每个包有 2.5% 概率被丢；$\bar{q}=50$ 时，$p = \frac{50-20}{40} \times 0.1 = 0.075$（7.5%）。<strong>队列越长，丢包概率线性爬升</strong>——TCP 流因此收到「越来越强的拥塞信号」。</span>

- **第一步，代入 $\bar{q}=30$**：$p = \frac{30-20}{60-20} \times 0.1 = 0.025$。
- **第二步，代入 $\bar{q}=50$**：$p = \frac{50-20}{60-20} \times 0.1 = 0.075$。
- **第三步，理解效果**：拥塞加重时，被随机丢弃的包变多，各 TCP 流「感知到拥塞」的概率上升——但它们被丢的**时间点不同**，退让也就错开，避免了一窝蜂地同时退。
- **第四步，对比队尾丢弃**：队尾丢弃是在 $\bar{q}$ 冲到队列上限时一次性丢一批；RED 是从 20 到 60 之间就「温水煮青蛙」式地开始丢——**一个炸、一个渐**。

**辨析｜易错点：** RED 参数若设得太激进（$p_{\max}$ 过大），会在网络并不拥塞时也大量丢包，浪费吞吐；设得太保守则退化成近似队尾丢弃。**「参数调优是 RED 的双刃剑」**——这也是 CoDel 主张「免调参」的原因。

## 6 AQM 与端到端拥塞控制的配合

AQM 不是独立工作的——它站在 TCP 拥塞控制的「上游」：<span class="marginnote"><strong>完整链条</strong>：TCP 发送方增长拥塞窗口 → 路由器队列变长 → AQM 提前丢/标记包 → TCP 收到信号（丢包或显式拥塞通知 ECN）→ 发送方减窗。<strong>AQM 负责「发出信号」，TCP 负责「响应信号」</strong>。ECN（显式拥塞通知）让路由器「标记」而非「丢弃」包——把「丢包才知拥塞」升级为「打标即知拥塞」，避免了丢包本身的开销。</span>

- **信号发出**：AQM 决定「丢谁、什么时候丢」。
- **信号传输**：丢包信号随 TCP 重传机制传递，或经 ECN 标记随 ACK 返回。
- **信号响应**：TCP 的拥塞避免/快恢复据此调整窗口。

**辨析｜易错点：** AQM 在路由器上做，TCP 拥塞控制在端系统做——**两者必须配合**：若端系统不用 TCP（如 UDP 视频流），AQM 的「丢包信号」对它毫无约束力。**「AQM 治路由器，TCP 治端系统，中间靠信号耦合」**——理解这条链，AQM 与拥塞控制就不是两件事，而是一件事的两端。

## 7 小结

- **队尾丢弃的病症**：全局同步、不公平、时延抖动。
- **AQM 思想**：提前、轻微、分散地发出拥塞信号，避免「满则全丢」。
- **RED**：按平均队列长度概率丢弃——低于 min_th 不丢、中间线性增、超过 max_th 全丢。
- **RED 的精妙**：用「平均」滤掉突发，用「概率」分散丢弃时机。
- **CoDel**：以排队时延为信号，几乎免调参，现代 Linux 默认。
- **延伸**：AQM 是「分级响应、渐进信号」思想在网络中间的体现——与 TCP 的端到端拥塞控制配合。
