## 为什么从 Web 缓存开始

Web 流量的特点是「**二八定律**」：20% 的网页被访问 80% 的次数——热门页面、图片、脚本被无数用户反复请求。如果每次都让请求跨越大半个互联网打到源服务器，带宽与时延都不可承受。**Web 缓存（Web cache）** 的答案：**把热门资源缓存到离用户近的地方，命中就直接返回。**<span class="marginnote">Web 缓存的本质是「<strong>就近复用</strong>」：<strong>代理服务器（或浏览器、CDN）保存源服务器的响应副本，后续相同请求直接命中缓存返回</strong>。它同时服务三方：用户（更快）、运营商（省带宽）、源服务器（减压力）。这与你 DNS 缓存的思想一脉相承——「缓存」是互联网「以空间换时间」的通用手段。</span>

这一节讲：**缓存怎么工作、代理服务器的角色、以及条件 GET 如何保证缓存不 stale。**

## 1 Web 缓存的位置：浏览器到服务器之间

缓存放哪？有三个层次：<span class="marginnote"><strong>浏览器缓存</strong>（最近）、<strong>代理服务器缓存</strong>（中间，企业/ISP 部署）、<strong>CDN 缓存</strong>（全球分布式，离用户最近的边缘节点）。三者的共同逻辑是「把副本放在离用户近的地方」。你访问一个网站时，请求可能被浏览器缓存、代理缓存、CDN 边缘缓存依次「拦截」——命中任何一个就直接返回，不必打到源站。</span>

| 缓存位置 | 谁部署 | 特点 |
| --- | --- | --- |
| 浏览器缓存 | 用户本机 | 最近、最快，但只服务单用户 |
| 代理服务器缓存 | 企业/ISP | 服务一网段用户，省出口带宽 |
| CDN 缓存 | 内容分发商 | 全球边缘，离用户最近（第 9 章） |

**辨析｜易错点：** 缓存的位置越靠近用户，时延越低，但「服务范围」越小。**浏览器缓存服务一个人、代理缓存服务一栋楼、CDN 服务一片区域**——它们层层叠加，构成「多级缓存」体系。**「多级缓存」是计算机体系结构里存储器层次思想在 Web 的翻版**（你会在《计算机组成原理》里见到同样的「缓存层级」）。

## 2 代理服务器：缓存的「执行者」

**代理服务器（proxy server）**：位于**客户端与源服务器之间**的中间服务器，替客户端转发请求、缓存响应。它的角色有两类：<span class="marginnote"><strong>正向代理</strong>：代表客户端访问互联网——客户端的请求先到代理，代理再请求源站。企业里用它做访问控制、缓存、匿名化。<strong>反向代理</strong>：代表服务器对外服务——客户端的请求先到反向代理，代理再转发给后端的源服务器。网站常用反向代理做负载均衡、缓存、安全防护。<strong>「正向代理替用户、反向代理替服务器」</strong>是最本质的区分。</span>

- **正向代理**：替客户端上网（缓存、过滤、加速）。
- **反向代理**：替服务器接客（负载均衡、缓存、防护）。

**辨析｜易错点：** 正向代理与反向代理的区分常考：**正向代理站在客户端这边（用户配置它），反向代理站在服务器这边（域名指向它）**。一个「替用户办事」，一个「替服务器办事」——方向反了，角色就错了。**「正向藏用户，反向藏服务器」**是记忆口诀。

## 3 条件 GET：缓存如何保持「新鲜」

缓存最怕「stale」（过期数据）——用户看到旧版本怎么办？HTTP 用**条件 GET（conditional GET）** 解决：<span class="marginnote">条件 GET 的精髓：<strong>缓存的副本不直接判定「可用」，而是带着「版本凭证」去问源服务器「我没变吧？」</strong>凭证是 <code>If-Modified-Since</code>（时间戳）或 <code>If-None-Match</code>（ETag 实体标签）。源服务器比对后：没变 → 回 <strong>304 Not Modified</strong>（缓存继续用，不传正文）；变了 → 回 <strong>200 + 新内容</strong>（更新缓存）。<strong>「304 是节省流量的确认函」</strong>——它没传正文，只传了一个「没变」的信号。</span>

条件 GET 的流程：

1. 浏览器请求 → 代理缓存有副本，但不确定是否新鲜。
2. 代理向源服务器发条件请求：`GET /page.html If-Modified-Since: 上次时间`。
3. 源服务器比对：**没变** → 回 `304 Not Modified`（无正文）；**变了** → 回 `200` + 新内容。
4. 304 时代理直接用缓存副本，不下载新正文——省带宽、省时间。

**辨析｜易错点：** **304 不是错误状态码，它是「确认没变」**——它属于 3xx 重定向类，但语义是「你用缓存吧」。另一个易错点：**条件 GET 省的是「正文传输」，不省「验证请求本身」**——每次仍要发一次轻量请求去确认。**「304 用一次轻请求换省一次重传输」**是条件 GET 的性价比模型。

## 4 缓存的失效与一致性

缓存要保证「最终一致」，靠几样机制：<span class="marginnote"><strong>TTL/Expires</strong>：资源声明「多久过期」，过期前缓存可直接用、不用验证；<strong>条件 GET</strong>：过期后向源站验证；<strong>Cache-Control</strong>：服务器声明「能否缓存、缓存多久」（如 <code>max-age</code>、<code>no-cache</code>）。这套「<strong>过期前直接用、过期后验证用、服务器说不让缓存就不缓存</strong>」的机制，让缓存既高效又一致。</span>

| 机制 | 作用 |
| --- | --- |
| Cache-Control / Expires | 服务器声明缓存策略（能否缓存、多久过期） |
| TTL | 过期前直接命中，过期后验证 |
| 条件 GET（If-Modified-Since / If-None-Match） | 过期后向源站验证，304 确认没变 |
| 强制刷新 / 版本号 URL | 绕开缓存、强制更新（加 `?v=2`） |

**辨析｜易错点：** **缓存一致性不是「实时」的，而是「最终一致」的**——缓存资源在 TTL 内可能短暂显示旧版本，这是「用缓存」的必然代价。**「缓存是性能与新鲜度的权衡」**——要极新鲜就少缓存，要极快就多缓存。**「缓存不保证实时，只保证最终一致」**是理解一切缓存系统的核心。

## 5 小结

- **Web 缓存**：把热门资源缓存到离用户近的地方，命中直接返回。
- **三级缓存**：浏览器缓存、代理缓存、CDN 缓存，层层叠加。
- **代理服务器**：正向代理替用户（缓存/过滤），反向代理替服务器（负载均衡/防护）。
- **条件 GET**：带 `If-Modified-Since`/`If-None-Match` 问源站，没变回 304。
- **304 的语义**：确认没变、省正文传输，不是错误。
- **一致性**：TTL 过期前直接用、过期后验证；缓存是「性能 vs 新鲜度」的权衡。
