## 为什么从流量控制开始

发送方可以高速连发，但**接收方不一定处理得过来**——如果接收方的接收缓冲区满了，继续发来的数据只能丢弃，还得重传，反而更糟。**流量控制（flow control）**：**让发送方的发送速率适应接收方的接收能力。**<span class="marginnote">流量控制与第 4 章网络层学的「拥塞控制」要区分开：<strong>流量控制管「对端能不能收」（接收方能力），拥塞控制管「网络通不通」（链路拥塞）</strong>。前者看对方的窗口，后者看网络的丢包。一个是「对端的刹车」，一个是「网络的刹车」。</span>

这一节讲：**接收窗口 rwnd 机制、滑动窗口的运作、以及窗口为 0 时的「僵局」处理。**

## 1 流量控制的机制：接收窗口 rwnd

TCP 首部的**窗口（Window）字段**是流量控制的执行依据——它由**接收方**填写，告诉发送方：**「我的接收缓冲区还能装多少字节，你最多还能发多少。」**<span class="marginnote">接收方每回一个报文段，就把当前「还能收的字节数」写进窗口字段——这个值叫 <strong>rwnd（receive window，接收窗口）</strong>。发送方把自己的发送窗口限制为 min(自己的拥塞窗口 cwnd, rwnd)，即「既能发多少由 rwnd 兜底」。<strong>rwnd = 接收缓冲大小 − 已收到未读的数据</strong>，随接收方的消费速度动态变化。</span>

**接收方**：动态更新 rwnd，写进每个报文段的窗口字段。
**发送方**：控制「在途未确认数据」≤ rwnd，超过就停发。

**辨析｜易错点：** 窗口字段是**接收方**写的、**发送方**遵守的——**「窗口 = 对方的许可额度」**。另外，**rwnd 与拥塞窗口 cwnd 是两个不同的窗口**：rwnd 管「接收方能力」，cwnd 管「网络容量」，发送方实际可发 = min(rwnd, cwnd)。**「两个窗口取小」**是 TCP 发送速率的完整公式。

## 2 滑动窗口的运作：一进一出

设初始 rwnd = 3000，MSS = 1000。发送方有 5 个报文段（5000 字节）要发：

1. 发送窗口 = min(rwnd, cwnd) = 3000，所以**只能先发 3 个报文段**（3000 字节），后 2 个等着。
2. 接收方收到 3000 字节、应用读走了 2000 字节，rwnd 变为 1000（还剩 1000 缓冲）。
3. 接收方回 ACK，窗口字段 = 1000。发送方**发送窗口收缩到 1000**，只能再发 1 个报文段。
4. 如此反复——**发送量永远被 rwnd 卡住**，接收方处理多快，发送方就能多快。<span class="marginnote">这个「一进一出」的比喻：<strong>接收缓冲区像蓄水池，应用读走水（释放缓冲），发送方才能注水（发送新数据）。rwnd 就是「还能注多少水」的水位计</strong>。流量控制让 TCP 成为「接收方驱动」的自适应系统——接收方处理能力就是发送方的速率上限。</span>

**辨析｜易错点：** **rwnd 是动态收缩/扩张的**——接收方缓冲区紧张时 rwnd 变小甚至为 0，处理完数据后 rwnd 恢复。发送方必须**时刻遵守最新的 rwnd**，不能「按老窗口一直发」。**「窗口会变，不是定值」**是流量控制区别于「固定窗口协议」的关键。

## 3 窗口为 0 的僵局：持续计时器

最棘手的情况：**rwnd = 0**——接收方缓冲区满了，发送方必须停止发送。这时有个隐患：<span class="marginnote">如果发送方停了，接收方处理完数据后回一个「窗口更新报文」（rwnd 变大），但<strong>这个窗口更新报文如果丢了</strong>，发送方还在傻等——双方就陷入「死锁」：发送方等窗口更新，接收方以为发送方知道窗口已更新。为避免死锁，TCP 在 rwnd=0 时启动<strong>持续计时器（persist timer）</strong>：周期性地发送<strong>「窗口探测报文」</strong>，逼接收方重新回报当前 rwnd。</span>

- **问题**：rwnd=0 后，若窗口更新报文丢失，双方死锁。
- **解决**：**持续计时器**周期探测——发送方定时发 1 字节的探测报文，接收方被迫回复当前 rwnd，打破僵局。

**辨析｜易错点：** 「持续计时器」与「重传计时器」是不同的：**重传计时器管「数据丢了重发」，持续计时器管「窗口为 0 时打破僵局」**。探测报文只占 1 字节、只问「窗口现在多少」，不传业务数据。**「窗口为 0 不是终点，是等待探测的起点」**。

## 4 流量控制 vs 拥塞控制：一张表

| 对比维度 | 流量控制 | 拥塞控制 |
| --- | --- | --- |
| 控制对象 | 接收方的接收能力 | 网络的拥塞程度 |
| 依据 | rwnd（接收方窗口） | cwnd（拥塞窗口）+ 丢包 |
| 谁驱动 | 接收方动态上报 | 发送方自适应调整 |
| 解决什么问题 | 接收方缓冲区溢出 | 网络丢包、链路拥塞 |
| 手段 | 限制发送窗口 ≤ rwnd | 慢开始、拥塞避免、快恢复 |

**辨析｜易错点：** 一句口诀：**「流量控制管对端，拥塞控制管网」**。二者最终都通过「调节发送窗口」起作用，但**信息源不同、目标不同**。考试最爱问「两者区别」，从「控制对象」与「依据」两个维度回答最稳。

## 5 一个完整算例：追踪 rwnd 的变化

设接收缓冲区大小为 4000 字节，MSS = 1000，应用每收到 2000 字节就读取一次。<span class="marginnote">这个例子演示了「<strong>接收方驱动</strong>」：发送速率完全由接收方的消费节奏决定——应用读得快，rwnd 恢复得快，发送方就能快。把 TCP 想象成一个由接收端「拧阀门」的自适应水管，就抓住了流量控制的本质。</span>

- **t = 0**：缓冲空，rwnd = 4000。发送方可发 4 段。
- **发送 4 段（4000 字节）后**：缓冲满，rwnd = 0。发送方必须停。
- **应用读走 2000**：缓冲剩 2000，接收方在下个 ACK 里写 rwnd = 2000。发送方恢复发送 2 段。
- **应用再读走 2000**：rwnd 回到 4000，发送方满速。

观察：**发送方的发送速率，完全由接收方的消费节奏决定**——接收方读得快，rwnd 恢复得快，发送方就能快。这就是「流量控制是接收方驱动」的直观含义。

**辨析｜易错点：** rwnd 的更新是「接收方在下一个报文段里捎带」的，不是独立报文——所以**发送方看到的 rwnd 总是「滞后一小段」的**。在快速消费场景下这个滞后影响小，但在慢速接收时会造成短暂的发送停顿。**「rwnd 是异步上报的，永远带着一点滞后」**是理解真实 TCP 的重要细节。

## 6 UDP 需要流量控制吗

把流量控制放到对比中更能看清它的位置：

- **UDP**：无流量控制、无拥塞控制、无可靠交付——接收方缓冲区满了，后来的数据报直接丢弃，丢就丢了（应用自己负责）。这正是 UDP「轻」的原因，也是它在实时场景（音视频、游戏）被选中的原因。
- **TCP**：用 rwnd 保「不溢出不丢」，用确认重传保「不丢不错」——**流量控制是 TCP「可靠」的前提之一**：如果缓冲区溢出丢数据，再强的重传也是白费。
- **中间态（QUIC）**：QUIC 在 UDP 之上实现了流量控制与可靠传输——再次证明「UDP 是白板，能力由上层自己加」。

**辨析｜易错点：** **「UDP 不丢包」是误解**——UDP 也会丢，只是它「不负责」丢。流量控制、可靠传输是 TCP 的选择，不是网络的必然。**「可靠与流量控制是协议的选择，不是信道的性质」**是把 TCP 与 UDP 看透的一句话。

## 7 发送窗口的完整公式与糊涂窗口

TCP 发送方的实际发送窗口 = min(拥塞窗口 cwnd, 接收窗口 rwnd)。它回答了「我能发多少」，但要防一个「蚂蚁搬家」问题：

**糊涂窗口综合症（silly window syndrome）**：如果接收方的应用「挤牙膏式」地读数据（一次读 1 字节），rwnd 就会一点一点变大（比如从 0 到 1、再到 2），发送方也一字节一字节地发——每次传输都只带极少的有效载荷，而 TCP/IP 首部固定开销不变，**吞吐被浪费殆尽**。

**缓解手段**：
- **接收方侧**：延迟确认 + 只有当 rwnd 增大到「值得发」（≥ 一个 MSS 或缓冲区一半）才通告窗口更新——「攒够了再放行」。
- **发送方侧**：只有当 rwnd 足够大（能装下至少一个完整报文段）时才发送——「不够大就继续等」。

**辨析｜易错点：** 糊涂窗口的本质是「窗口以小块逐步打开，导致小报文段浪费带宽」——它与 rwnd=0 的死锁是两回事：**死锁是「窗口不打开」，糊涂窗口是「窗口开得太碎」**。两者都靠「延迟通告/延迟发送」的思路解决。

## 8 术语速查

| 术语 | 含义 |
| --- | --- |
| 流量控制 | 让发送速率适应接收方能力 |
| rwnd | 接收窗口，接收方通告的剩余缓冲 |
| cwnd | 拥塞窗口，发送方对网络容量的估计 |
| 发送窗口 | min(rwnd, cwnd) |
| 持续计时器 | rwnd=0 时周期探测窗口更新 |
| 窗口探测 | 1 字节探测报文，问「窗口现在多少」 |
| 糊涂窗口综合症 | 窗口小块打开导致小报文段浪费 |
| 延迟确认 | 攒一会再确认，避免窗口碎开 |

## 9 小结

- **流量控制**：让发送速率适应接收方能力，防缓冲区溢出。
- **rwnd**：接收方写进窗口字段的「还能收多少」，动态变化。
- **发送窗口 = min(rwnd, cwnd)**：两个窗口取小，兼顾对端能力与网络容量。
- **滑动运作**：接收方消费释放缓冲 → rwnd 变大 → 发送方才能多发。
- **窗口为 0**：持续计时器周期探测，打破「窗口更新丢失」的死锁。
- **与拥塞控制区别**：流量控制管对端，拥塞控制管网。
- **算例结论**：发送速率由接收方消费节奏决定，「接收方驱动」的直观体现。
- **UDP 对照**：UDP 不负责丢，流量控制是协议选择而非信道性质。
- **糊涂窗口**：窗口碎开浪费带宽，靠延迟确认/延迟发送缓解。
- **一句话**：流量控制是「对端能收多少」，拥塞控制是「网络能通多少」。
