## 为什么从 PPP 的状态与认证开始

上一节我们看了 PPP 的三大部分与帧格式，那是「静态结构」。但一条 PPP 链路是有**生命周期的**：它从「静止」到「可传数据」要经过一系列状态转换，还要在必要时验证双方身份。<span class="marginnote">这一节把 PPP 讲「活」：<strong>状态机</strong>描述链路怎么一步步建立、使用、关闭；<strong>认证协议</strong>（PAP/CHAP）回答「怎么确认对方是自己人」。理解了状态机，你不仅懂了 PPP，还提前预习了 TCP 的三次握手状态机——「协议状态机」是网络协议的标准骨架。</span>

这一节重点：PPP 的链路状态转换、以及 PAP 与 CHAP 两种认证方式的原理与安全差异。

## 1 PPP 链路的五个状态

PPP 链路的状态机（简化版）包括五个关键状态：

| 状态 | 做什么 |
| --- | --- |
| 静止（Dead） | 链路物理层未就绪，无通信 |
| 建立（Establish） | LCP 协商链路参数（MRU、认证方式等） |
| 认证（Authenticate） | 按协商的认证协议验证身份（可选） |
| 网络（Network） | NCP 协商网络层参数（如 IP 地址） |
| 打开（Open） | 链路可用，传输网络层数据 |

**状态转换路径**：静止 → 建立（物理层就绪，发 LCP 配置请求）→ 认证（协商了认证则进入）→ 网络（认证通过）→ 打开（NCP 配置完成）。任何阶段失败，都回到静止或建立重新协商。<span class="marginnote">状态机的核心价值：<strong>任何一步出问题，链路都到不了「打开」</strong>。拨号失败时你能在状态机里定位——是 LCP 协商没通过（协议不匹配）、还是认证失败（密码错）、还是 NCP 失败（IP 冲突）。「协议状态机 = 排障地图」这个思想贯穿所有网络协议。</span>

**辨析｜易错点：** 认证不是必选项——PPP 的认证阶段**可选**，由 LCP 协商决定。很多教材把认证画成必经步骤，实际取决于配置。另一个易错点：**「打开」状态才传网络数据**，前面所有阶段传的都是控制报文（LCP/NCP/认证报文），不是 IP 数据报。

### LCP 到底在协商什么

「建立」阶段的核心是 LCP（Link Control Protocol）的配置协商。它通过「配置请求/配置确认/配置拒绝/配置否决」四种报文来回协商，典型参数包括：

| 参数 | 含义 | 例子 |
| --- | --- | --- |
| MRU | 最大接收单元 | 1500 字节 |
| 认证协议 | 是否认证、用哪种 | 无 / PAP / CHAP |
| 异步字符映射 | 控制字符转义 | 链路层透明传输相关 |
| 魔数（magic number） | 检测环路 | 随机数比对 |

**辨析｜易错点：** LCP 协商是「**先对齐再传数据**」——双方参数不一致就来回否决重提，直到双方都接受才进入下一阶段。**「协商不通过，链路建不起来」**是 PPP 状态机严格性的体现，也是它与「直接发数据」的无连接协议的本质差别。

## 2 PAP：简单的明文认证

**PAP（Password Authentication Protocol，密码认证协议）**：最朴素的认证方式。

被认证方把**用户名和密码明文**发送给认证方。
认证方核对，返回「认证成功」或「认证失败」。

PAP 的优缺点一目了然：实现简单，但**不安全**——密码在链路上明文传输，监听者能直接看到；而且 PAP 在链路生命周期内可能被**反复发送**（某些实现），重放攻击风险高。<span class="marginnote">「明文密码上链路」在任何安全语境下都是大忌。PAP 只适合「链路本身可信」或「不担心被监听」的低安全场景。它存在的意义更多是作为「最简单实现」的对照物。</span>

**辨析｜易错点：** PAP 的缺陷有两个层面：① **明文传输**（被动监听可窃取）；② **无防重放**（截获的认证报文可以重放）。教材常把这两点并列为 PAP 的软肋。与之对比，CHAP 就是为了解决这两点而生的。

## 3 CHAP：挑战-握手认证

**CHAP（Challenge Handshake Authentication Protocol，挑战握手认证协议）**：不传密码，而是用「挑战-应答」机制。

**CHAP 的三次握手过程：**

1. **挑战**：认证方发送一个**随机挑战值（challenge）**给被认证方。
2. **应答**：被认证方用密码与挑战值一起做**散列运算（如 MD5）**，把散列结果发回。
3. **验证**：认证方用自己掌握的密码做同样的运算，比对结果一致则通过。

**CHAP 的安全性来源：**

**密码不上链路**：链路上只传「挑战值」与「散列结果」，密码从未出现。
**挑战值每次随机**：即使截获一次应答，也无法重放——因为下次挑战值不同，散列结果必然不同。
**周期性重认证**：CHAP 可在连接期间周期性重复挑战，抵御会话劫持。<span class="marginnote">CHAP 的巧妙之处是「不传密码、传证明」：密码只存在于两端本地，链路上流动的是「我能算出这个散列值」的证据。这与你手机支付「不传密码、传一次性验证码」的思路同源——后来 TLS 的握手、RSA 签名认证都是这套「零知识证明」思想的后代。</span>

**辨析｜易错点：** CHAP 的散列运算需要双方**共享同一个密码**——它是**共享密钥**认证，不是公钥认证。别把 CHAP 与公钥体制混淆：CHAP 的前提是「认证方与被认证方事先知道同一个秘密」，安全地分配这个秘密是另外的问题（见第 7 章密钥分配）。

### 一个数值例子：CHAP 的散列流程

设共享密码为 `s3cret`，认证方发出随机挑战 `c = 12345`，被认证方用 MD5 计算：

$$
\text{应答} = \text{MD5}(\text{s3cret} \;\|\; 12345)
$$

- **第一步，挑战**：认证方发 `12345`（每次随机，本次不同下次也不同）。
- **第二步，应答**：被认证方对「密码 + 挑战值」做散列，返回 128 位摘要。
- **第三步，比对**：认证方用自己手里的密码做同样的散列，两个摘要一致则通过。

**辨析｜易错点：** 被认证方**不需要把密码发出去**，只需证明「我能算出正确的摘要」。即使监听者截获了 `12345` 与摘要，**下次挑战值不同、摘要必然不同**，无法重放。**「挑战值随机 = 防重放，散列运算 = 密码不上链路」**，这两条就是 CHAP 安全性的全部来源。

最后给一节做个小结式的对照：**PAP 是「一次性的、明文的」，CHAP 是「可重复的、带挑战的」**。PAP 只在建链时认证一次；CHAP 可以在连接期间反复挑战，随时验证对端仍然「活着且可信」——这弥补了「建链时通过、会话中途被劫持」的漏洞。

## 4 PAP vs CHAP：一张表分清

| 对比维度 | PAP | CHAP |
| --- | --- | --- |
| 传输内容 | 用户名 + 明文密码 | 随机挑战值 + 散列结果 |
| 密码是否上链路 | 是（明文） | 否 |
| 防窃听 | 无 | 强 |
| 防重放 | 无 | 强（挑战值随机） |
| 是否周期性重认证 | 否 | 是 |
| 复杂度 | 简单 | 较复杂 |
| 安全性 | 低 | 高 |

**辨析｜易错点：** 常考的一句话总结：**PAP 是「把密码告诉对方」，CHAP 是「向对方证明我知道密码而不说出密码」**。另外，CHAP 的「挑战-应答」思想会反复出现：后面讲网络认证（如 RADIUS、WPA2）、TLS 握手时，都是这个模式的变体——**「不传秘密、传证明」是认证的通用范式**。<span class="marginnote">PAP 与 CHAP 是 PPP 认证的「教学双星」，但今天真实网络中更常见的是更现代的协议（如 EAP 家族）。理解 PAP/CHAP 的价值在于建立「认证机制」的认知框架——后面的网络安全章节会反复用到。</span>

## 5 小结

- **PPP 状态机**：静止 → 建立（LCP）→ 认证（可选）→ 网络（NCP）→ 打开；任何一步失败都到不了「可传数据」。
- **状态机=排障地图**：在哪一步失败，就能定位哪一类问题。
- **PAP**：明文传用户名密码，简单但不安全，有窃听与重放两大软肋。
- **CHAP**：挑战-握手，密码不上链路，随机挑战防重放，可周期重认证。
- **黄金对比**：PAP「说出密码」，CHAP「证明知道密码」。
- **范式延伸**：「不传秘密、传证明」是认证的通用范式，将出现在 TLS、WPA 等场景。
