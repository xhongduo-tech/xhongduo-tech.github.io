## 为什么从 TCP 首部开始

TCP 的所有「智慧」都写在它的首部里——可靠、排序、窗口、连接管理，全靠这些字段协作。**TCP 报文段 = TCP 首部 + 数据**，首部固定 **20 字节**（不含选项）。<span class="marginnote">读懂 TCP 首部，等于拿到一张「TCP 全部机制的索引图」：<strong>序号管排序、确认号管确认、窗口管流量、六个标志位管连接</strong>。抓包时你看到的每一行 TCP 字段，都能在这张表里找到它服务的机制。</span>

这一节逐字段解剖 TCP 首部，重点是六个标志位与序号/确认号。

## 1 TCP 首部：20 字节的布局

TCP 首部的固定部分（20 字节）按顺序如下：

| 字段 | 位数 | 含义 |
| --- | --- | --- |
| 源端口 | 16 | 发送进程端口 |
| 目的端口 | 16 | 接收进程端口 |
| 序号（Sequence Number） | 32 | 本报文段数据首字节的字节流序号 |
| 确认号（Acknowledgment Number） | 32 | 期望收到的下一字节序号（表示此前字节都收到了） |
| 数据偏移（Data Offset） | 4 | 首部长度（单位 4 字节），最小 5 |
| 保留 | 6 | 保留字段 |
| 标志位 | 6 | URG、ACK、PSH、RST、SYN、FIN |
| 窗口（Window） | 16 | 接收方愿意接收的字节数（流量控制） |
| 校验和 | 16 | 伪首部 + TCP 首部 + 数据的校验 |
| 紧急指针（Urgent Pointer） | 16 | 紧急数据末尾位置（配合 URG） |
| 选项（Options） | 可变 | 如 MSS、时间戳、SACK |

**辨析｜易错点：** **序号与确认号都是 32 位，且都以「字节」为单位**——这是 TCP 与链路层「按帧编号」最大的不同。**确认号 = 期望收到的下一字节的序号**（不是「已收到的最大序号」），它隐含了「此前所有字节都收到了」——这就是**累积确认**。把「确认号指向下一字节」记牢，三次握手的理解就顺了。

## 2 六个标志位：TCP 的「开关」

TCP 首部有六个控制标志位，各管一件事：<span class="marginnote">六个标志位是 TCP 抓包分析的核心：<strong>SYN 建连、FIN 断连、ACK 表示确认号有效、RST 异常复位、PSH 立即交付、URG 紧急数据</strong>。其中 SYN 与 FIN 特别重要——三次握手的每一步、四次挥手的每一步，都是靠它们的组合来标记的。背熟「SYN/FIN 管连接，ACK 管确认，RST 管异常」就够用了。</span>

| 标志 | 含义 |
| --- | --- |
| SYN | 同步序号，建立连接时置 1 |
| FIN | 释放连接，表示发送方数据已发完 |
| ACK | 确认号有效（几乎所有报文段都置 1，握手除外） |
| RST | 复位连接（异常终止、拒绝连接） |
| PSH | 立即把数据交付应用（不缓冲） |
| URG | 紧急数据有效（配合紧急指针） |

**辨析｜易错点：** 最容易混淆的是 **ACK 标志位与「确认号字段」**——ACK 标志位是「确认号是否有意义的开关」，确认号是「具体确认到哪」的数字。**三次握手的 SYN 报文不带数据但带序号**——这个「SYN 也要占一个序号」的细节，是四次挥手与序号计算里的高频考点。

## 3 序号与确认号：可靠传输的「坐标」

TCP 可靠性的坐标体系：

- **序号（seq）**：本报文段**数据首字节**在整个字节流中的位置。首字节序号由「初始序号（ISN）+ 已发送字节数」决定。
- **确认号（ack）**：**期望收到的下一个字节的序号**。发回 ack = n 意味着「n-1 及以前的字节都正确收到了」。

**公式解析：确认号的累积语义**

$$
\text{ack} = \text{已收到数据的下一字节序号} \;\Rightarrow\; \text{收到 ack = n 表示序号 < n 的字节全部到达}
$$

- **第一步，看 ack 指向**：ack = n，指「我期望收到序号为 n 的字节」。
- **第二步，隐含语义**：因为字节流是按序确认的，所以「n-1 及以前全部收到」——这就是**累积确认**。
- **第三步，与链路层对比**：GBN 的累积确认也是「ack n 代表 n 及以前全到」，TCP 沿用了这个思想，但粒度是「字节」而非「帧」。<span class="marginnote">累积确认的美妙：<strong>接收方不需要逐段确认，一个 ack 就能确认一大片数据</strong>——既省了确认报文，又让「确认丢失」不那么可怕（后续 ack 会覆盖）。但它的代价是：丢失中间一段时，后续整片都无法被确认——这正是快重传机制要应对的场景。</span>

**辨析｜易错点：** **SYN 与 FIN 报文各占一个序号**——它们虽不带应用数据，但在序号空间里算「一个字节」。这导致四次挥手时 FIN 之后的确认计算要 +1。**「SYN/FIN 吃序号」**是 TCP 序号计算题里最常漏掉的 +1。

## 4 窗口字段与紧急指针

**窗口（Window）**：16 位，**接收方告知对方「我还能收多少字节」**——这是流量控制的核心字段（下一节讲）。值越大，发送方能发的越多。
**紧急指针（Urgent Pointer）**：配合 URG=1，指出紧急数据在报文段中的末尾位置——用于「带外数据」（如 Telnet 的中断指令）。<span class="marginnote">窗口字段只有 16 位（最大 65535），高速长链路下不够用——所以后来加了「<strong>窗口缩放选项（Window Scale）</strong>」把窗口左移放大，这正是「带宽-时延积大 → 窗口需要大」的工程体现（第 4 章讲过最优窗口 = 带宽-时延积 + 1）。</span>

**辨析｜易错点：** 窗口是**动态变化**的——接收方处理得快，窗口就大；处理不过来，窗口就缩小甚至为 0。**「窗口是接收方对发送方的『许可额度』」**，不是固定值。抓包时窗口不断变化，正反映接收方的实时处理能力。

## 5 小结

- **TCP 首部**：固定 20 字节；源/目的端口、序号、确认号、数据偏移、标志位、窗口、校验和、紧急指针。
- **序号/确认号**：32 位、以字节为单位；确认号 = 期望的下一字节（累积确认）。
- **六个标志位**：SYN/FIN 管连接、ACK 管确认、RST 管异常、PSH 管立即交付、URG 管紧急。
- **窗口字段**：接收方给发送方的「还能收多少」额度，流量控制的核心。
- **SYN/FIN 吃序号**：各占一个序号，挥手时的 +1 计算不能漏。
- **抓包速记**：SYN/FIN 管连接，seq/ack 管可靠，window 管流量。
