## 为什么从 TCP 的编号开始

上一节说了「序号防重复」，但 TCP 的序号有一个其他协议没有的特点：**它以「字节」为单位编号**——不是给「报文段」编号，而是给**每一个字节**编号。这带来了极其精确的可靠性与确认能力。<span class="marginnote">TCP 的字节编号是整个可靠传输的坐标轴：<strong>报文段的序号 = 它第一个字节的序号；确认号 = 期望的下一字节序号</strong>。因为坐标精确到字节，TCP 可以「任意切段、按序重组、精确确认」——这是链路层「按帧编号」做不到的精细度。</span>

这一节把字节编号、累积确认、捎带确认讲透。

## 1 字节编号：每个字节都有「身份证」

TCP 把应用层交付的字节流**逐字节编号**：

- 首字节的序号由**初始序号（ISN，Initial Sequence Number）**决定（随机生成，防猜测攻击）。
- 报文段的序号 = 该段**首字节**的序号。
- 报文段数据的字节范围 = [序号, 序号 + 数据长度 - 1]。

**公式解析：报文段序号怎么定**

$$
\text{seq} = \text{ISN} + \text{已发送的数据字节数} \quad (\text{建连后从 ISN+1 起})
$$

- **第一步，看 ISN**：三次握手时双方各自随机选一个初始序号。
- **第二步，SYN 占一字节**：建连时 SYN 报文占一个序号（ISN），第一个数据字节序号是 ISN+1。
- **第三步，逐段累加**：每发一个报文段，序号就「前进」该段数据的字节数。<span class="marginnote">这个公式解释了抓包时看到的「seq 越来越大、且不是连续整数」——因为不同报文段的数据长度不同，序号跳的步长也不同。<strong>「序号 = ISN + 已发字节数」</strong>是分析一切 TCP 序号问题的总公式。</span>

**辨析｜易错点：** **序号以字节为单位，不是以报文段为单位**——一个报文段「吃掉」多少序号，取决于它带多少字节数据。**ACK 报文不带数据，不占序号**；但 **SYN/FIN 报文各占一个序号**。做序号计算题时，「SYN/FIN 要 +1」是最常被漏掉的项。

## 2 累积确认：一个 ACK 确认一大片

**累积确认（cumulative acknowledgment）**：TCP 的确认号 **ack = 期望收到的下一字节序号**，隐含「**序号小于 ack 的所有字节都正确收到了**」。

$$
\text{发送方收到 ack = n} \;\Rightarrow\; \text{字节 [0, n-1] 全部安全到达}
$$

**累积确认的好处**：<span class="marginnote"><strong>确认报文少</strong>：一个 ack 覆盖一大片，不必逐段确认；<strong>抗确认丢失</strong>：即使某个 ack 丢了，下一个 ack 的「更大确认号」会自动覆盖它——只要序号更大的确认到了，前面的数据就算确认了。这两个优点让累积确认在工程上非常省事。</span>

- **少**：一个 ack 覆盖整个已确认区间，不必逐段回报。
- **抗丢**：确认号单调递增，丢了某个 ack 也没关系，后续更大的 ack 会「覆盖」它。

**辨析｜易错点：** 累积确认的**代价**：如果中间丢了数据段（如 seq 1000–2000 丢了，但 2000–3000 到了），接收方只能确认到 999——**后续数据虽然到了，也无法被确认**，因为它们不连续。这正是「快重传」要解决的：接收方连续收到 3 个「重复 ack（都指向 1000）」时，发送方就知道 1000 丢了，立即重传，不用等超时。

## 3 捎带确认：顺路带个信

TCP 是**全双工**的——两个方向都在传数据。于是确认可以**捎带（piggyback）**在反向的数据报文段里：<span class="marginnote">A 收到 B 的数据，要回确认；恰好 A 也有数据要发给 B——那就在发给 B 的报文段里「捎带」上确认号。这样<strong>确认不占用额外报文</strong>，效率大增。但捎带需要「恰好有反向数据」；没有时，TCP 会延迟一小段时间（如 200ms）等反向数据，等不到就单独发确认。</span>

- 反向恰好有数据 → 确认号捎带在数据报文段里。
- 反向没数据 → 等一个短延迟（如 200ms）后单独发 ACK。

**辨析｜易错点：** 捎带确认是「优化」，不是「必须」——**它依赖反向流量恰好存在**。现代实现里，接收方通常「延迟确认」（等 40–200ms 合并多个 ACK）来减少确认报文数。**「延迟确认 + 捎带确认」都是为减少 ACK 开销的工程技巧**，不影响累积确认的语义。

## 4 一个完整例子：字节编号与确认

设 A 发送 3000 字节给 B，MSS=1000，ISN=1000（简化）：

| 报文段 | seq | 数据 | 长度 |
| --- | --- | --- | --- |
| 段 1 | 1001 | 字节 0–999 | 1000 |
| 段 2 | 2001 | 字节 1000–1999 | 1000 |
| 段 3 | 3001 | 字节 2000–2999 | 1000 |

- B 收到段 1、段 2，回 ack=3001（期望下一字节是 3000 号，即 seq 3001）。
- 若段 2 丢失、段 3 到达，B 只能回 ack=2001（字节 2000 还没到），段 3 被缓存。
- 发送方收到 3 个重复的 ack=2001 → 立即重传段 2（快重传）。<span class="marginnote">注意这里的细节：<strong>接收方对「不连续的已到数据」缓存但不确认</strong>——确认号只反映「连续收到」的边界。这就是累积确认的精确含义：它确认的是「连续的字节前缀」，而不是「所有已到达的字节」。</span>

**辨析｜易错点：** **确认号只认「连续的字节前缀」**——乱序到达的数据即使正确，也不会推高确认号。所以「确认号前进」=「接收方字节流又推进了一段」，这是观察 TCP 进展的窗口。

## 5 小结

- **字节编号**：每个字节一个序号；报文段 seq = 首字节序号 = ISN + 已发字节数。
- **SYN/FIN 占序号**：各占一个字节的序号空间，计算时记得 +1。
- **累积确认**：ack = 期望的下一字节，隐含「小于 ack 的全到」；省报文、抗丢 ACK。
- **确认的边界**：只确认「连续的字节前缀」，乱序数据缓存但不确认。
- **捎带确认**：全双工下把确认搭在反向数据里；延迟确认合并 ACK 减少开销。
- **快重传伏笔**：重复 ack 触发快速重传，是解决「丢段卡确认」的关键。
