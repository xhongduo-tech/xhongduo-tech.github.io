## 为什么从 TCP 概述开始

UDP 只做了「进程寻址」，可靠性原样交给应用。但绝大多数应用（网页、文件、邮件）都**需要可靠有序**的传输——它们需要 **TCP（Transmission Control Protocol，传输控制协议）**。TCP 是互联网可靠传输的代名词，也是本章篇幅最重的主角。<span class="marginnote">TCP 要解决的根本问题：<strong>在「尽力而为、可能丢包乱序」的 IP 之上，提供「可靠、有序、不重不漏」的字节流</strong>。它靠一整套机制实现：编号与确认、超时重传、滑动窗口、流量控制、拥塞控制。这一节先立「总论」，后面逐篇拆解。</span>

这一节讲：**TCP 的五大特点、TCP 连接的逻辑本质、面向字节流的含义。**

## 1 TCP 的五大特点

**TCP**：面向连接的、端到端的、可靠的全双工字节流协议。它的特点：

**面向连接**：通信前必须先建立连接（三次握手），通信后释放连接（四次挥手）。
**点对点**：TCP 连接是「一对一」的——一条连接只连接两个端点，不支持一对多广播。
**可靠交付**：通过编号、确认、重传，保证数据无差错、不丢失、不重复、按序到达。
**全双工**：双方可以同时发送与接收数据，各有一条独立的发送/接收通道。
**面向字节流**：把应用层数据看成**连续的字节流**，TCP 自己负责切段（分段）、排序、重组。<span class="marginnote">「面向字节流」的含义：应用层交付给 TCP 的数据是一串字节，<strong>TCP 不保证「一次 send 对应一次 recv」</strong>——它把字节流切成合适大小的报文段发送，接收方重组后按流交付。这与 UDP 的「面向报文」形成鲜明对比（UDP 保留报文边界，TCP 只有流）。</span>

**辨析｜易错点：** TCP 的「可靠」不是「网络可靠」——**网络仍然是尽力而为的 IP**，可靠是 TCP 通过「确认 + 重传」在端系统之间**挣来的**。另外，**TCP 是全双工但点对点**：一条连接两个端点、双向都可传，但不能像广播那样一对多。**「点对点 + 全双工」**是两个不冲突的特点。

## 2 TCP 连接：逻辑上的「虚拟管道」

**TCP 连接**：一条**逻辑上的连接**——它不像电路交换那样占用真实物理线路，而是**通信双方各自维护的一堆状态**（发送/接收序号、窗口、缓冲区等）。

TCP 连接由四元组唯一标识：<span class="marginnote"><strong>（源 IP，源端口，目的 IP，目的端口）</strong>。四条全相同的两端的两个套接字之间，才构成一条 TCP 连接。这也解释了为什么一台服务器（IP 固定、端口 80）能同时服务海量客户端——每个客户端是不同四元组，各自是独立连接。</span>

**辨析｜易错点：** TCP 连接是「**端系统维护的状态集合**」——中间的路由器不知道、也不维护任何 TCP 连接状态。**「连接存在两端，不在网络中」**是理解 TCP 连接本质的一句话。所以「连接断了」往往是两端的状态失配（超时、RST），而不是网络中某条线断了。

## 3 面向字节流：TCP 怎么处理数据

TCP 把应用数据当作字节流处理，收发两端各有一把「尺子」：

**发送端**：把字节流**分段**成合适大小的报文段（MSS，最大报文段长度），为每个字节编号，发送。
**接收端**：收到报文段，**按字节序号排序、去重**，重组出连续的字节流交付给应用。<span class="marginnote">TCP 的编号以「字节」为单位——<strong>每个字节都有自己的序号</strong>（首字节序号即报文段的序号）。这让 TCP 能精确地「排序、去重、确认到字节」——比链路层的「按帧编号」精细得多。第 5 章下一节「编号与确认」会展开这套字节序号的细节。</span>

**辨析｜易错点：** TCP 的「流」没有边界——**应用层两次 send 的数据，可能被 TCP 合进一个报文段，也可能被拆成多个**。所以接收方不能假设「一次 recv 就是一次 send 的数据」。**「TCP 是流，不是报文」**是它与 UDP 最本质的行为差异，也是网络编程里最容易踩的坑。

**辨析｜易错点：** TCP 的可靠性与**流量控制、拥塞控制**是不同层面的问题：**可靠性是「保证不丢不乱」，流量控制是「接收方处理不过来时放缓」，拥塞控制是「网络堵了时放缓」**。三套机制在 TCP 里协同但目标不同——**「可靠管对端、流量管接收、拥塞管网」**是一句话分工。

## 5 TCP 与 UDP：一对「性格相反」的兄弟

| 对比维度 | TCP | UDP |
| --- | --- | --- |
| 连接 | 面向连接（握手） | 无连接 |
| 可靠性 | 可靠、有序、不重不漏 | 尽力而为 |
| 数据边界 | 面向字节流（无边界） | 面向报文（有边界） |
| 流量/拥塞控制 | 有 | 无 |
| 首部开销 | 20 字节起 | 8 字节 |
| 典型应用 | 网页、文件、邮件 | 音视频、DNS、游戏 |

**辨析｜易错点：** **「TCP 可靠所以更好」是常见误区**——音视频、实时游戏恰恰需要 UDP：它们宁可丢一帧也不要「等重传造成的延迟」。**「可靠是代价换来的，实时场景不总是买账」**。选择 TCP 还是 UDP，本质是「可靠性」与「低延迟/低开销」的权衡。

## 6 算例：四元组如何区分海量连接

设一台 Web 服务器 IP 是 203.0.113.10、端口 80，同一时刻有 10000 个客户端在下载网页。这 10000 条连接怎么区分？

每条连接的四元组（源 IP、源端口、目的 IP、目的端口）都不同——因为**每个客户端的源 IP 与源端口不同**。即使用户 A 的两次请求都到服务器的 80 端口，它们的源端口也不一样（操作系统随机分配）。**「目的端相同，靠源端区分」**是端口多路复用/分用的精髓——一台服务器用一个端口服务海量客户端，全靠四元组的唯一性。

**辨析｜易错点：** 四元组区分的是「连接」，不是「进程」——同一进程可以发起多条连接。**「四元组标识连接，端口标识进程」**：端口决定数据交给哪个进程，四元组决定是哪个连接。理解这两层，网络编程的「多路复用/分用」就清楚了。

## 7 一段历史：TCP 是谁设计的

TCP 的历史值得知道，因为它解释了很多「为什么这么设计」：

- **TCP/IP 的诞生**：1970 年代，Vint Cerf 与 Bob Kahn 在 ARPANET 项目中设计出 TCP/IP 体系，1983 年 ARPANET 正式改用 TCP/IP——这就是现代互联网的起点。
- **早期 TCP 承担一切**：最早的 TCP 既要可靠传输、又要寻址路由，后来才拆成 TCP 与 IP 两层——「职责分离」从互联网诞生起就是核心思想。
- **为什么能成功**：TCP/IP 免费开放、由文档（RFC）驱动、足够健壮，能在异构网络间通用——**「开放标准 + 简单分层」是它战胜其他协议的关键**。

**辨析｜易错点：** 别把「TCP/IP」当成「一个协议」——它是**一整个协议族**，TCP 和 IP 只是其中最出名的两个。**「TCP/IP 是家族，TCP 是其中负责可靠传输的一员」**——这个命名习惯今天仍常让人误会。

## 8 动手观察：你的电脑上有多少 TCP 连接

打开终端输入 `netstat -n`（或 `ss -tn`），你会看到密密麻麻的 TCP 连接，每一行就是一条：

- **本地地址 + 远程地址**：正是四元组的呈现（本地 IP:端口 → 远程 IP:端口）。
- **状态列**：ESTABLISHED（已建立）、LISTEN（监听）、TIME_WAIT（等待关闭）——对应第 5 章后面讲的状态机。
- **观察发现**：一个浏览器开着，你通常能看到几十条 ESTABLISHED 连接——全是四元组各不相同的独立连接。

**辨析｜易错点：** `ss -tn` 里出现的「TIME_WAIT」不是故障——它是连接关闭后等待旧报文消失的状态，属于正常现象。**「看到 TIME_WAIT 别慌，看到大量 SYN_SENT 才要警惕」**——前者正常，后者可能连不上。

## 10 小结

- **TCP 五大特点**：面向连接、点对点、可靠、全双工、面向字节流。
- **可靠是挣来的**：在尽力而为的 IP 之上，靠确认 + 重传实现端到端可靠。
- **连接的本质**：两端维护的状态集合，不在网络中；四元组唯一标识。
- **面向字节流**：TCP 只管字节流，自己分段、排序、重组；与 UDP 的面向报文相反。
- **机制全景**：编号确认、超时重传、连接管理、滑动窗口、拥塞控制协同工作。
- **TCP vs UDP**：可靠是代价换来的，实时场景宁丢不慢，选择看需求。
- **四元组算例**：目的端相同靠源端区分，一台服务器用一端口服务海量客户端。
- **历史坐标**：Cerf 与 Kahn 的 TCP/IP 是互联网的起点，开放标准 + 简单分层。
- **动手观察**：ss/netstat 里每条连接都是四元组，TIME_WAIT 是正常状态。
