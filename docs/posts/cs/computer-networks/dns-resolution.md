## 为什么从 DNS 解析过程开始

上一节看到了 DNS 的层次结构，这一节看**查询到底怎么执行**。DNS 解析有两种查询方式：**递归查询（recursive query）与迭代查询（iterative query）**。它们的区别，是「谁来替你把问题问到底」。<span class="marginnote">理解递归与迭代，最好的类比是「问路」：<strong>递归 = 你问 A，A 帮你一路问到 Z 再回来告诉你；迭代 = 你问 A，A 只说「去问 B」，你再去问 B，B 说「去问 C」……你自己一站一站地问</strong>。前者省你的腿，后者省对方的脑。</span>

这一节讲：**两种查询的机制、主机与本地服务器的配合、以及解析过程的完整例子。**

## 1 递归查询：帮我问到底

**递归查询（recursive query）**：查询者把问题**交给一个服务器**，由这个服务器**代替查询者**去问其他服务器，直到得到答案，再**原路返回**。

- 主机 → 本地域名服务器：**递归查询**——主机把问题整个甩给本地服务器，等最终答案。
- 本地服务器 → 根/权威服务器：通常用**迭代查询**——本地服务器自己「跑腿」。<span class="marginnote">关键区分：<strong>主机问本地服务器，用的是递归</strong>——主机只想知道「www.example.com 的 IP 是多少」，它不关心中间过程；<strong>本地服务器问根/TLD/权威，通常用迭代</strong>——本地服务器自己逐站问下去。所以「递归还是迭代」不是全局属性，而是<strong>「每一条查询边」自己的属性</strong>。</span>

**递归的优点/缺点**：对查询者省事（只问一次）；对被询问者压力大（要替你问到底）。

## 2 迭代查询：告诉我去问谁

**迭代查询（iterative query）**：被询问的服务器**不替你去问**，而是返回「下一站该问谁」的**指引**，由**查询者自己**去问下一站。

- 本地域名服务器 → 根服务器：迭代。根返回「.com 的 TLD 服务器地址」。
- 本地域名服务器 → TLD 服务器：迭代。TLD 返回「example 的权威服务器地址」。
- 本地域名服务器 → 权威服务器：迭代。权威返回最终 IP。<span class="marginnote">为什么本地服务器对上级多用迭代？因为「谁查询谁负担」：<strong>迭代把跑腿的负担放在查询者（本地服务器）身上</strong>，根与 TLD 服务器只需「指路」，不用替所有查询者全程跑腿——否则根服务器会被全世界的查询请求压垮。迭代查询是「让重活由查询者自己干」的负载分担设计。</span>

**辨析｜易错点：** 递归与迭代不是「二选一」——**同一次解析里两者同时存在**：主机 → 本地是递归，本地 → 上级是迭代。教材常考「指出哪一段是递归、哪一段是迭代」，答题要点是**看「谁替谁跑腿」**：被询问者跑腿 = 递归，查询者自己跑腿 = 迭代。

## 3 完整解析过程：一次查询的「全旅程」

以用户输入 `www.example.com` 为例，完整过程：

```
用户主机
   │  ① 递归查询
   ▼
本地域名服务器
   │  ② 迭代：问根，根指路 .com
   ▼
根域名服务器 ────► ③ 返回 .com TLD 服务器地址
   │  ④ 迭代：问 .com，.com 指路 example
   ▼
.com TLD 服务器 ──► ⑤ 返回 example 权威服务器地址
   │  ⑥ 迭代：问 example 权威，拿到最终 IP
   ▼
example 权威服务器 ─► ⑦ 返回 www.example.com 的 IP
   │  ⑧ 递归返回给用户
   ▼
用户主机获得 IP
```

**辨析｜易错点：** 一条规律记牢：**「主机到本地是递归，本地往上全迭代」**——绝大多数真实场景都是这个组合。另外注意**缓存的影响**：如果本地服务器缓存里已有答案，②–⑦ 全被跳过，直接返回——**缓存让 90% 的查询只走一步**。**「缓存命中 = 少跑腿」**是 DNS 快的根本原因。<span class="marginnote">现实中还有一个「转发」的变体：本地服务器若配置了「转发器（forwarder）」，它会把请求<strong>递归地转发</strong>给上游（如运营商的公共 DNS），让上游替它解析——这是递归与迭代之外的第三种形态「<strong>递归转发</strong>」，在企业网络里很常见。</span>

## 4 DNS 的报文与端口

DNS 报文**不区分「查询/响应」的格式**——同一个报文格式，靠标志位区分是查询还是响应。关键字段：<span class="marginnote">DNS 报文头部的关键标志：<strong>QR</strong>（0=查询，1=响应）、<strong>Opcode</strong>（操作类型）、<strong>AA</strong>（权威应答）、<strong>RD/RA</strong>（递归期望/可用）。问题区、回答区、权威区、附加区四个「区」承载具体记录。<strong>DNS 默认用 UDP 53</strong>——一次查询一个往返，UDP 足够；响应太大或需可靠时改用 TCP。</span>

- **默认 UDP 53**：查询响应快、开销小。
- **可切 TCP 53**：响应超长（如 DNSSEC）或区域传输（zone transfer）时用 TCP。

**辨析｜易错点：** **DNS 默认是 UDP 53**，但「DNS 一定用 UDP」是错的——超长响应与区域传输要用 TCP。**「UDP 为主、TCP 兜底」**是对 DNS 传输方式最准确的描述。另一个考点：**DNS 报文是「无状态」的**——靠「标识符（ID）」把查询与响应配对，客户端发多个查询，靠 ID 区分哪个响应对应哪个查询。

## 5 小结

- **递归查询**：被询问者替你问到底——主机问本地服务器用递归。
- **迭代查询**：被询问者只指路，查询者自己跑腿——本地服务器问上级用迭代。
- **黄金规律**：主机到本地是递归，本地往上全迭代。
- **缓存的作用**：命中缓存直接返回，跳过全部层级——DNS 快的根本。
- **DNS 报文**：查询/响应同格式，靠标志位区分；默认 UDP 53、超长用 TCP。
- **递归转发**：本地服务器可配置转发器，把请求递归交给上游。
