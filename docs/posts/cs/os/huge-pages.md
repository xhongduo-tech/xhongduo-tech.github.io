## 为什么从大页开始

分页用 4KB 小页带来精确与共享，但现代应用动辄用 GB 级内存：**页表项数量与页数成正比**，4KB 页下 1GB 内存就要 262144 个页表项；TLB 只能缓存几百项，命中率惨不忍睹。**大页（Huge Page）**用 2MB/1GB 的大页替代 4KB 小页——**页表缩小、TLB 命中率提升**，是现代高性能内存管理的关键优化。<span class="marginnote">回顾《分页》的权衡：页小则精确但页表大、TLB 命中差；页大则页表小、TLB 命中好但内部碎片大。大页就是把「页大小」往大推的工程选择，专为「大内存、大程序」服务。</span>

## 1 大页为什么快：页表与 TLB 的账

设进程占 $S$ 字节内存，页大小 $P$，页表项数：

$$N_{pte} = \frac{S}{P}$$

- 页大小 $P$ 从 4KB → 2MB（512 倍），页表项数降为 **1/512**。
- 页表项减少 → 分层页表的层级遍历更快、占用更小。
- **TLB 覆盖范围（TLB reach）= 页大小 × TLB 项数**——页越大，同样 TLB 覆盖的内存越多。

**公式解析：TLB 覆盖范围**

$$\text{TLB reach} = \text{TLB 项数} \times \text{页大小}$$

- 设 TLB 有 512 项。
- 4KB 页：TLB reach $= 512 \times 4\text{KB} = 2\text{MB}$——TLB 只能覆盖 2MB 内存，访问大数组时疯狂 miss。
- 2MB 大页：TLB reach $= 512 \times 2\text{MB} = 1\text{GB}$——TLB 覆盖 1GB，大程序也能命中。

**结论**：**TLB 覆盖范围 = TLB 项数 × 页大小**。页越大，TLB 覆盖越大，缺页/TLB miss 越少——这是大页性能收益的数学根源。

### 数值算例：一个 1GB 进程的页表账

设进程占 1GB（1024MB）内存，比较两种页大小下的页表规模与 TLB 覆盖：

| 指标 | 4KB 小页 | 2MB 大页 |
| --- | --- | --- |
| 页表项数 | 1024MB ÷ 4KB = 262144 项 | 1024MB ÷ 2MB = 512 项 |
| 单级页表大小（每项 8B） | 约 2MB | 约 4KB |
| TLB 覆盖（512 项 TLB） | 2MB | 1GB |

结论很直观：**页表从 2MB 缩到 4KB（512 倍），TLB 从只能盖住 2MB 到盖满整个进程**。多级页表下还有一层收益：页表级数可以变少，地址转换的访存次数随之下降——**大页是「一个改动，三处收益」：页表小、TLB 命中高、转换快**。

## 2 大页的代价与使用方式

**大页的代价**：

- **内部碎片变大**：2MB 页若只用 1.5MB，浪费 0.5MB（25%）；4KB 页最多浪费 2KB（0.05%）。**页越大碎片越狠**。
- **分配粒度粗**：大页必须连续物理内存（2MB/1GB 连续），内存碎片化时分配失败。
- **按需分页变粗**：请求 1GB 大页时，虽然仍是按需调入，但粒度是 1GB 的块——局部性差时浪费。

**内部碎片到底差多少？** 一个进程只用掉页内一半空间：4KB 页浪费 2KB，2MB 页浪费 1MB——绝对量差了 512 倍。但对 GB 级大进程而言，1MB 的浪费占比是千分之一量级，可接受；对内存碎片化或小进程密集的系统，这 512 倍会被放大成可见压力。**大页的碎片代价是「按比例看可忽略、按场景看要警惕」。**

**显式大页（Huge Pages, Linux）**：管理员预留大页池（`/proc/sys/vm/nr_hugepages`），应用用 `mmap` 时指定 `MAP_HUGETLB` 或 `SHM_HUGETLB` + 大页对齐地址。数据库（MySQL、PostgreSQL）、JVM（大堆）常显式启用。

### 显式大页的配置路径

以 Linux 为例，启用显式大页一般走三步：

1. **预留大页池**：`echo 512 > /proc/sys/vm/nr_hugepages` 预留 512 个 2MB 大页（共 1GB）；`/sys/kernel/mm/hugepages/` 下可查看与调整。
2. **分配方式**：应用用 `mmap` 时加 `MAP_HUGETLB` 标志并传入大页对齐地址，或用共享内存 `SHM_HUGETLB`；大页池不足时分配失败，因此**预留量要覆盖峰值需求**。
3. **挂载使用**：`mount -t hugetlbfs` 挂载 hugetlbfs，数据库/JVM 在其中创建文件映射即可获得大页。

**易错点**：大页池是「物理连续 + 预留」的——预留太多挤占普通内存，太少则应用因大页耗尽而失败。**预留量需要结合 workload 动态调整**，这是 DBA 与内核工程师调优时最常见的手工操作。

**辨析｜易错点：** 「大页 = 更快的内存」是过度简化。大页真正省的是**地址转换**（页表遍历 + TLB miss），而非内存本身的带宽与延迟——顺序大块访问时转换开销占比高、收益明显；随机小对象访问时转换开销本就不大，大页的收益被内部碎片抵消，甚至为负。**大页优化的是「翻译效率」，不是「存储速度」**，对症下药才有效。

## 3 透明大页（THP）：自动使用大页

**透明大页（THP, Transparent Huge Pages）**：内核**自动**把合适的大块内存合并成 2MB 大页，应用无需修改——「透明」指应用无感知。

- 后台 `khugepaged` 线程扫描进程的页表，把「连续且兼容」的小页合并成大页。
- 应用层面零改动，享受大页的 TLB 收益。

**THP 的争议**：

- **合并与拆分有开销**：THP 在运行时合并页、在缺页时可能拆分大页，额外 CPU 消耗。
- **大页碎片影响实时性**：大页分配/合并延迟不稳定，实时应用可能受损。
- 因此 **THP 常被数据库/实时系统关闭**（启动参数 `transparent_hugepage=never`），显式管理大页更可控。

### THP 的三种模式

Linux 的 THP 并非只有「开/关」两态，`/sys/kernel/mm/transparent_hugepage/enabled` 可设三档：

- **always**：内核尽力把内存合并成 2MB 大页，最激进，收益最大、COW 风险也最大。
- **madvise**：只有调用 `madvise(MADV_HUGEPAGE)` 的地址区域才使用大页——把选择权交给应用，是「既要收益又要可控」的折中，**多数生产环境推荐**。
- **never**：完全禁用 THP，适合对延迟抖动敏感的场景（Redis、实时系统）。

三档正好对应三种心态：**全都要（always）、让我挑（madvise）、全不要（never）**。理解三档，就理解了 THP 争论的本质——不是「大页好不好」，而是「**由谁来决定用不用大页**」。

**辨析｜易错点：** 「THP 一定比小页快」是过度乐观。**THP 在「大块顺序访问 + 大内存」场景收益显著，在「小块随机访问 + 内存碎片」场景可能因合并/拆分开销与碎片而变慢**。数据库社区对 THP 的态度分化，很多生产环境显式关闭 THP、改用显式 Huge Pages——**「自动」不等于「总是最优」，量化场景再决定**。<span class="marginnote">大页的经典案例：Redis 官方文档建议关闭 THP——因为 Redis 用 `fork` + COW 做持久化，THP 大页在写时复制时要整页复制，2MB 大页的复制成本是 4KB 的 512 倍，COW 性能暴跌。<strong>技术没有银弹，只有「场景 → 权衡 → 决策」。</strong></span>

## 4 核心对比表：小页 vs 大页 vs THP

| 维度 | 4KB 小页 | 2MB/1GB 显式大页 | 透明大页 THP |
| --- | --- | --- | --- |
| 页表项数（1GB 内存） | 262144 | 512 | 同大页 |
| TLB 覆盖（512 项 TLB） | 2MB | 1GB | 1GB |
| 内部碎片 | 极小 | 较大 | 较大 |
| 应用改动 | 无 | 需显式指定 | 无（自动） |
| 控制性 | — | 强（手动池） | 弱（自动合并） |
| 适用 | 通用 | 大内存、数据库、JVM | 通用但有争议 |

## 5 小结

- **大页**（2MB/1GB）把页表项数降为 1/512，**TLB 覆盖范围 = TLB 项数 × 页大小**显著提升——「一个改动，三处收益」：页表小、TLB 命中高、转换级数少。
- 大页代价：**内部碎片大、需连续物理内存、按需分页粒度粗**；碎片代价「按比例可忽略、按场景要警惕」。
- **显式大页**：`nr_hugepages` 预留池 + `MAP_HUGETLB`/`SHM_HUGETLB` + hugetlbfs，三步配置；预留量要覆盖峰值需求。
- **透明大页 THP**：内核自动合并小页为大页，应用无感，但有合并/拆分开销。
- THP 三档：**always / madvise（推荐）/ never**——争论的本质是「由谁来决定用大页」。
- 大页优化的是**翻译效率**而非存储速度；虚拟化下 Guest 大页让 Host EPT 表项同降 1/512，收益翻倍。
- THP 在 COW 等场景可能反噬性能（Redis 建议关闭）——**量化场景再决策**。
