## 为什么从上下文切换开始

上一节我们认识了 PCB，说它保存着进程的「现场」。这一节回答：**现场怎么被存进去，又怎么被换出来？** 这就是**上下文切换（context switch）**——操作系统制造「多个程序同时运行」错觉的核心魔术。CPU 只有一个，进程成千上万，靠的就是在进程之间高速「换人」，每次换人都快到你感觉不到。<span class="marginnote">上下文切换与《进程状态模型》互为表里：状态转换是「逻辑上」的搬家，上下文切换是「物理上」的换场。就绪 → 运行的转换，物理动作就是一次上下文切换。</span>

## 1 什么是上下文

**上下文（context）**：一个进程在某一时刻的完整运行现场，包括三部分：

**CPU 寄存器**：通用寄存器、程序计数器（PC）、程序状态字（PSW）、栈指针（SP）。
**内存映射**：进程的地址空间（页表基址寄存器 CR3 等）。
**内核上下文**：进程在内核态时保存的内核栈指针等。

**上下文切换（context switch）**：把当前进程的上下文保存进它的 PCB，再从目标进程的 PCB 恢复其上下文，使 CPU 转而执行目标进程的过程。

## 2 上下文切换的步骤

一次典型切换分三步：

1. **保存现场**：把当前进程的 PC、寄存器、状态字压入内核栈，再写入当前进程的 PCB。
2. **切换地址空间**：把页表基址寄存器换成新进程的，TLB 随之失效。
3. **恢复现场**：从新进程的 PCB 读出寄存器与 PC，CPU 从新进程的断点继续执行。

看起来简单，但每一步都有代价：保存/恢复寄存器、切换页表使 TLB 全部作废、内核栈切换、可能还要清空各类缓存。<span class="marginnote">TLB（快表）是地址转换的高速缓存，进程切换后里面全是旧进程的映射，必须作废重填——这是上下文切换隐藏成本的大头之一，见第八篇《快表 TLB》。</span>

**上下文切换时间（context switch time）**：完成一次切换所需的时间，典型为几微秒。它依赖硬件支持：寄存器越多、缓存越大，切换越贵。**切换频率 × 切换时间 = 系统花在「换人」上的纯开销**，这部分时间不执行任何用户代码，所以调度器要尽量减少无谓切换。

## 3 调度队列：PCB 排队的三种队

进程从创建到终止，一直在不同的**调度队列（scheduling queue）**之间迁移，对应上一篇的状态：

**就绪队列（ready queue）**：所有就绪进程的 PCB 队列。常以链表实现，头指针指向第一个 PCB。
**等待队列（wait queue）**：因等待某事件（I/O 完成、信号量、定时器）而阻塞的进程队列。通常**每个事件一种队列**，方便事件发生时精准唤醒。
**设备队列（device queue）**：等待某设备的进程队列，本质是等待队列的一种特例（如等待磁盘的队列）。

**队列的迁移就是状态的迁移**：进程创建 → 入就绪队列；被调度 → 出就绪队列上 CPU；请求 I/O → 入该设备的等待队列；I/O 完成 → 中断唤醒，回到就绪队列。

## 4 核心对比表：两种调度形式

调度器的动作分为两个层次，容易混为一谈：

| 维度 | 长期调度（作业调度） | 短期调度（CPU 调度） |
| --- | --- | --- |
| 决策频率 | 低（秒~分钟级） | 高（毫秒级，每次切换） |
| 控制什么 | 从磁盘作业中选谁进入内存 | 从就绪队列选谁上 CPU |
| 决定什么 | 进程创建速率、多道程度 | 谁立即运行 |
| 实现位置 | 较少见（现代多为按需创建） | 每个操作系统必备 |

（部分教材还提**中期调度**，即交换，见第八篇《交换技术》。）

**辨析｜易错点：** 「上下文切换 = 模式切换」是最常见误区。**模式切换（user↔kernel）只改变特权级，不换进程**——中断处理、系统调用都是模式切换，切换时仍服务同一进程，现场由内核栈保存，不必动 PCB；**上下文切换才换进程**，要动 PCB 与地址空间。**模式切换比上下文切换便宜得多**，一次系统调用只是模式切换，不是上下文切换。<span class="marginnote">这个区分极其重要：你写程序调用 <code>read()</code>，是模式切换；两个进程轮流跑，是上下文切换。前者纳秒~微秒级，后者通常贵一个数量级，因为要动 TLB。</span>

## 5 数值算例：上下文切换的纯开销

上下文切换是**纯开销**——切换期间 CPU 不执行任何用户代码。系统在这上面的总浪费由公式给出：

$$\text{开销占比} = \frac{\text{切换时间} \times \text{每秒切换次数}}{\text{总时间}} = t \times f$$

代入具体数看量级：

| 每秒切换 $f$ | 单次切换 $t$ | 开销占比 | 场景 |
| --- | --- | --- | --- |
| 1000 次/s | 5 μs | $0.5\%$ | 常规分时系统，可接受 |
| 5000 次/s | 20 μs | $10\%$ | 时间片过短，明显浪费 |
| 100000 次/s | 10 μs | $100\%$ | CPU 全在切换，用户代码几乎不跑 |

第三个场景正是「**时间片太小导致系统慢死**」的极端演示：时间片 1 ms、切换 10 μs 时，切换占比 $= 10\,\mu s / 1\,ms = 1\%$；时间片压到 100 μs，占比飙到 $10\%$。**这就是调度器时间片不能无限小的根本原因**——它给上下文切换开销设了下限。现代系统把时间片定在 1–10 ms 量级，就是在「响应性」与「切换开销」之间取平衡。<span class="marginnote">Linux 的 CFS 默认目标延迟约 20 ms、最小粒度约 1 ms，时间片随进程数动态伸缩——本质就是「按进程数分摊这 20 ms，同时保住 1 ms 的最小切换间隔」。</span>

## 6 术语速查

| 术语 | 含义 |
| --- | --- |
| 上下文 | 进程在某一时刻的完整现场：寄存器 + PC + 状态字 + 地址空间 + 内核栈 |
| 上下文切换 | 存旧 PCB、换地址空间、恢复新 PCB，CPU 转而执行另一进程 |
| 模式切换 | 用户态 ↔ 内核态的特权级变化，不换进程 |
| 就绪队列 | 就绪进程 PCB 的队列，链表实现 |
| 等待队列 | 因等待事件而阻塞的进程队列，每个事件一种 |
| 设备队列 | 等待某设备的进程队列，是等待队列的特例 |
| 切换时间 | 完成一次上下文切换的耗时，典型几微秒 |

## 7 什么时候会触发上下文切换

上下文切换并非随意发生，主要有四类触发时机：

1. **主动让出**：进程调用阻塞式系统调用（`read()` 等 I/O、`sleep()`）——自己从就绪队列进入等待队列，调度器换下一个。
2. **时间片耗尽**：进程用完时间片，被调度器换下，重新入队。
3. **抢占**：更高优先级进程就绪（如高优先级任务到达），抢占式调度立即切换。
4. **进程终止**：进程退出，PCB 回收，无需再恢复它的现场。

**辨析｜易错点：** 「每次中断都会上下文切换」是常见误解。**中断处理只做模式切换**——CPU 保存现场进入内核、执行中断服务例程、然后多半回到同一个进程继续执行，整个过程**不换进程、不动 PCB**。只有在中断处理后调度器判定「该换人了」（如更高优先级进程就绪）时，才追加一次真正的上下文切换。**中断是模式切换的触发器，上下文切换是调度决策的结果，二者不在同一层次。**<span class="marginnote">理解这条链：定时器中断 → 模式切换进入内核 → 时钟驱动调度器 → 若当前进程时间片用完则上下文切换。所以「一次时钟中断」通常导致「一次模式切换 + 可能一次上下文切换」。</span>

**补充：同进程内的线程切换更便宜**。同一进程的线程共享地址空间，因此线程之间的上下文切换**不必切换页表**（地址空间不变），只需保存与恢复线程自己的寄存器与栈——省掉了「换页表 + 刷新 TLB」这两步重活。这也正是「线程比进程轻」的物理来源，细节见第四篇《线程概念与多线程的优势》。

## 8 小结

- **上下文** = 寄存器 + PC + 状态字 + 地址空间 + 内核栈；**上下文切换** = 存旧 PCB、换地址空间、恢复新 PCB。
- 切换三步：**保存现场 → 切换页表 → 恢复现场**；切换时间典型几微秒，是调度器的纯开销。
- **调度队列**包括就绪队列、等待队列（含设备队列），进程在队列间迁移即状态迁移。
- **长期调度**决定谁进内存，**短期调度**决定谁上 CPU，两者频率差几个数量级。
- **上下文切换 ≠ 模式切换**：模式切换不换进程，便宜得多。
- 开销占比 $t \times f$：时间片越小切换占比越高，这给时间片设了下限。
- 中断只做模式切换，是否追加上下文切换取决于调度器的换人决策。
- 触发时机四类：主动让出、时间片耗尽、抢占、进程终止。
