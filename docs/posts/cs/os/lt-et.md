## 为什么从 LT/ET 开始

epoll 有两种触发模式：**水平触发（LT）**与**边缘触发（ET）**。它们决定「一个就绪事件被报告几次」，直接关系到编程模型的正确性——ET 的高性能诱惑下藏着经典的「必须读完」陷阱。这一节把两者讲清，并给出工程建议。<span class="marginnote">回顾《epoll 内核实现》：就绪 fd 被回调挂进就绪链表。LT 与 ET 的区别在于「<strong>fd 保持就绪时，是否被反复报告</strong>」——LT 只要数据没读完就一直在链上，ET 只在「就绪状态变化」时挂一次链。</span>

## 1 水平触发 LT：状态持续则持续通知

**水平触发（LT, Level-Triggered）**：fd **处于就绪状态**期间，每次 `epoll_wait` 都会报告它。

- socket 有数据 → 就绪 → epoll_wait 返回它。
- **即使你这次没读完**，下次 epoll_wait **还会返回它**（数据还在，状态仍就绪）。
- **select/poll 都是水平触发**。

**LT 的特性**：

- **安全**：数据没读完就会一直通知——**不怕漏读**。
- **编程简单**：读了部分数据没关系，下次继续。

## 2 边缘触发 ET：状态变化才通知

**边缘触发（ET, Edge-Triggered）**：只在 fd **从「不就绪」变为「就绪」的瞬间**报告一次。

- socket 有数据到达（从空到有数据 = 状态变化）→ 通知一次。
- **如果你没把数据读完**，剩下的数据**不会再通知**——直到**新数据到达**（新的状态变化）才再次通知。

**ET 的陷阱（经典 bug）**：

```c
// ET 模式错误写法：读一次就不读了
n = read(fd, buf, 1024);
// 假设 socket 有 10KB 数据，只读了 1KB
// 剩下 9KB 不会再被通知（没有新数据到达）
// → 数据永远读不完，连接「卡死」
```

**ET 的正确写法：必须循环读到 EAGAIN**：

```c
// ET 模式正确写法：读到读不动为止
while (1) {
    n = read(fd, buf, sizeof(buf));
    if (n > 0) 处理(buf);
    else if (n == 0) { /* EOF */ break; }
    else if (errno == EAGAIN) break;   // 读空了，退出
}
```

**ET 的原理**：就绪链表只在「状态跳变」时挂 fd——**读完后 fd 变成「不就绪」**，但**没有新数据时不会再次跳变**，所以不会重新挂链。**「读完 + 读到 EAGAIN」是 ET 的纪律。**

## 3 为什么有人用 ET：性能与响应

**ET 的优势**：

- **减少 epoll_wait 返回次数**：同样数据量，LT 可能返回多次（每次没读完），ET 只在变化时返回——**系统调用更少**。
- **配合非阻塞 + 循环读**：一次就绪通知把数据全部读走——**高效**。

**ET 的代价**：

- **必须用非阻塞 fd**：因为要循环读到 EAGAIN，阻塞 fd 会卡在读上。
- **编程易错**：忘记循环读 = 数据丢失/卡死。
- **调试困难**：ET 的「不重复通知」让 bug 难以复现。

**nginX 的实践**：nginx 在 Linux 上用 **ET 模式**（高性能），但要求**每个连接都是非阻塞**且**循环读满**——**ET 是「高手的工具」，用对性能好，用错是灾难**。

**公式解析：LT vs ET 的通知次数**

设 socket 持续有数据、进程每次只读 1KB、总数据 $D$ KB、每次处理 1KB：

$$\text{LT 通知次数} = D \quad \text{（每次 epoll_wait 都报）}$$

$$\text{ET 通知次数} = \text{数据到达的「批次」数} \quad \text{（每次到达只报一次）}$$

- **LT**：数据没读完就一直在就绪链上——**每次 epoll_wait 都返回**，通知次数 = 读取次数。
- **ET**：只在「数据从无到有」时通知——**一次通知读完所有数据**，通知次数 = 到达批次数。

**直觉**：**LT 是「持续警报」，ET 是「一次性警铃」**。ET 省的是「重复通知」的系统调用，代价是「必须一次处理完」的责任。**高性能高责任，是 ET 的写照。**

**辨析｜易错点：** 「ET 比 LT 快，所以无脑用 ET」是危险的过度优化。**ET 的收益在高频大流量下明显，但它的「必须读完」纪律极易写错**——一个忘记循环读的 bug 就是连接卡死。**多数场景 LT 够用且安全**；ET 适合「确实需要极致性能且团队能守住纪律」的场景。**正确性 > 性能，先 LT 跑通，再按需 ET。**

## 4 核心对比表：LT vs ET

| 维度 | 水平触发 LT | 边缘触发 ET |
| --- | --- | --- |
| 通知条件 | 状态持续就绪 | **状态变化瞬间** |
| 未读完数据 | 下次继续通知 | **不通知（等新数据）** |
| 读法 | 可分批读 | **必须循环读到 EAGAIN** |
| 需要非阻塞 | 不必（推荐） | **必须** |
| 系统调用数 | 多 | **少** |
| 编程难度 | 低 | 高（易错） |
| 典型 | select/poll、多数应用 | nginx 等高性能服务 |

## 5 小结

- **LT**：就绪期间持续通知——安全、简单，数据没读完还会报。
- **ET**：只在状态变化时通知一次——**必须循环读到 EAGAIN**，否则数据卡死。
- ET 必须**非阻塞 fd** + **循环读满**——高手的工具。
- LT 通知次数 = 读取次数；ET 通知次数 = 数据到达批次数——ET 省系统调用。
- **正确性优先**：多数场景用 LT，极致性能且纪律严谨才用 ET。
