## 为什么从管程开始

上一节的结论是「信号量太自由，容易用错」。Dijkstra 的同事、图灵奖得主 **Hoare** 与 **Brinch Hansen** 在 1970 年代提出**管程（monitor）**：把「锁 + 共享数据 + 对数据的操作」打包成一个语言级结构，**编译器自动加锁**，程序员不再手动 `P`/`V`（`wait`/`signal`）。这是并发编程从「工具箱」走向「语言机制」的关键一步。<span class="marginnote">回顾《信号量》：它的痛点是没有所有权、释放容易遗漏。管程的答案是「把临界区保护写进语法」——你在管程里写的方法，编译器自动保证同一时刻只有一个线程在执行。</span>

## 1 管程的定义：锁 + 数据 + 方法

**管程（monitor）**：一种高级同步结构，把**共享数据、对其操作的函数、以及互斥机制**封装在一起。管程保证：**同一时刻只有一个进程在管程内执行其方法**——互斥由语言/运行时自动保证，程序员不需要也不应该手动加锁。

```java
class BoundedBuffer {
    private int[] buf = new int[10];   // 共享数据
    private int count = 0;

    public synchronized void deposit(int x) {  // 互斥方法：编译器自动加锁
        while (count == buf.length) { wait(); } // 条件变量：满则等
        buf[count++] = x;
        notifyAll();                            // 唤醒等待的消费者
    }
}
```

管程的三个组成部分：

1. **互斥**：管程本身自带「门」，一次只放一个进程进来。
2. **条件变量（condition variable）**：管程内的「休息室」，让进程等特定条件。
3. **条件操作**：`wait` 与 `signal`/`broadcast`，只在管程内可用。

**关键**：`wait`/`signal` 不再是全局自由函数，而是**只能在管程内调用**——这把「同步操作」限制在了「有锁保护」的范围内，杜绝了「忘了加锁就操作共享数据」这类错误。

## 2 条件变量：管程里的「休息室」

**条件变量（condition variable）**：与某个条件（如「缓冲区不满」「队列非空」）绑定的等待队列。条件变量上的两个操作：

**wait**：当前进程**释放管程锁并睡眠**，挂到该条件变量的等待队列上。
**signal**（`notify`）：唤醒该条件变量上的**一个**等待进程（若有）。
**broadcast**（`notifyAll`）：唤醒全部等待进程。

**wait 的语义是「原子地放锁 + 睡眠」**：进程必须同时「让出锁」和「睡下」，否则别的进程进不了管程、永远无法把条件变好。这是条件变量与普通忙等循环的本质区别。<span class="marginnote">「wait 必须原子地放锁睡觉」是条件变量的灵魂：如果先睡再放锁，睡着的进程占着锁，没人能进管程改条件，它就永远醒不来。现代实现里 wait 在进入等待队列后自动释放锁，唤醒时再重新拿锁。</span>

**signal 的语义与互斥的冲突**：`signal` 唤醒等待者时，等待者想进管程，但唤醒者还在管程里——谁先执行？Hoare 语义是「唤醒者立刻让出，等待者立刻进」（公平但频繁切换）；Mesa 语义是「唤醒者继续，等待者排队再进」（简单，但等待者醒来要**重新检查条件**）。Java 的 `notify`、pthread 的 `pthread_cond_signal` 都是 Mesa 语义，因此**被唤醒后必须用 while 循环重新检查条件**，不能用 if。

**辨析｜易错点：** 「被唤醒 = 条件一定满足了」是经典错误。**Mesa 语义下，signal 只是「提示你条件可能好了」，不保证一定好**——唤醒者可能又改了条件，或另一个线程抢先消费了资源。所以标准写法必须是：

```java
while (buffer.isEmpty()) {
    wait();      // 被唤醒后回到这里，重新检查条件
}
// 条件确实满足，安全消费一个元素
```

用 `if` 判断会在「虚假唤醒」或「条件已变化」时出错——这是 Java 并发面试最经典的坑。

## 3 管程 vs 信号量：一场历史的对话

| 维度 | 信号量 | 管程 |
| --- | --- | --- |
| 互斥责任 | 程序员手动 `P`/`V` | 语言自动保证 |
| 同步 | 任意计数器 | 条件变量 |
| 出错概率 | 高（易漏释放） | 低（锁进语言） |
| 跨进程 | 内核信号量可跨进程 | 语言管程一般限同进程线程 |
| 实现 | 内核/库 | 编译器 + 运行时 |

**管程的代价**：

**通用性略降**：管程通常面向**同进程内的线程**（Java `synchronized`、pthread `mutex`+`cond`），跨进程同步仍需信号量或 IPC。
**引入新概念**：条件变量、虚假唤醒、Mesa/Hoare 语义，学习曲线不低。
**编译器依赖**：需要语言支持（或库的严格约定）。

**设计启示**：管程把「正确性的一部分」从程序员手里收进语言——这是并发编程史上「从工具到机制」的进化。现代语言的并发设计几乎都继承管程：Java `synchronized`、Python `threading.Condition`、Go 的 `sync.Mutex`、Rust 的 `std::sync::Mutex`。<span class="marginnote">Go 官方甚至推荐「不要通过共享内存来通信，而要通过通信来共享内存」——这是对「共享数据 + 锁」模型（管程的根基）的又一次范式反思，催生了 channel 这种「消息传递式同步」。</span>

## 4 管程的三个经典组件

用「生产者-消费者」的管程实现看清组件协作（完整代码见第六篇《生产者-消费者问题》）：

```java
class BoundedBuffer {
    private int[] buf = new int[10];
    private int in = 0, out = 0, count = 0;

    public synchronized void put(int x) {
        while (count == buf.length) { wait(); }  // 满则等
        buf[in] = x; in = (in + 1) % buf.length; count++;
        notifyAll();
    }
    public synchronized int get() {
        while (count == 0) { wait(); }           // 空则等
        int x = buf[out]; out = (out + 1) % buf.length; count--;
        notifyAll();
        return x;
    }
}
```

- **互斥**由 `synchronized` 保证：`put` 与 `get` 不会同时执行。
- **条件变量**是隐式的：`wait()` 的线程挂在管程的等待集合上。
- **while 循环**处理虚假唤醒与条件变化。

**辨析｜易错点：** 「用 `if` 判断一次就够」在单生产单消费且无虚假唤醒时碰巧对，但**并发环境下绝不成立**。`notifyAll` 唤醒多个等待者，它们竞争进入，先进入者可能已把资源消费光，后进入者必须 `while` 重新检查。**`while` 是条件变量的纪律，不是可选优化。**

## 5 小结

- **管程** = 共享数据 + 互斥方法 + 条件变量，互斥由语言自动保证。
- **条件变量**提供 `wait`（原子放锁+睡眠）与 `signal`/`broadcast`（唤醒）。
- **Mesa 语义**下唤醒后必须 **`while` 重新检查条件**，用 `if` 是经典错误。
- 管程把互斥收进语言，比信号量难用错；代价是跨进程同步能力弱。
- 现代语言（Java/Python/Go/Rust）的同步机制几乎都是管程思想的继承。
