## 为什么从死锁检测开始

预防与避免都是「事前」——它们要牺牲利用率或预知需求。检测与恢复是「事后」——**允许死锁发生，定期检查，发现后处理**。它适合「死锁罕见但代价可承受」的系统：数据库系统天天这么做（检测到死锁就回滚一个事务）。<span class="marginnote">回顾《死锁处理方法》的四种策略：预防（立法）、避免（执法）、检测（巡警）、忽略（鸵鸟）。检测策略的合理性前提是「死锁不常发生」——若死锁频繁，检测加恢复的代价会超过预防。</span>

## 1 检测算法的思路：找环的机械化

死锁检测的核心是「判断资源分配图是否有环」。对**多实例资源**，图论找环要转化成「模拟资源释放」，与银行家算法的安全性算法结构几乎一样，但**不需要最大需求信息**：

**多实例资源检测算法**：

1. Work = Available（当前可用）。
2. 对每个进程 $P_i$，若 **Allocation[i] ≠ 0**（有资源）则 Finish[i] = false，否则 Finish[i] = true（无资源者不构成死锁）。
3. 找 i：Finish[i] = false 且 **Request[i] ≤ Work**（它当前的请求能被满足）。
找到：**假设它完成，Work += Allocation[i]**，Finish[i] = true，重复。
4. 找不到新 i 时：**若存在 Finish[i] = false 的进程，说明它被死锁**——它的请求永远无法被满足。

**与银行家算法的区别**：检测用**当前实际请求 Request**（不是最大需求 Need），且**不做分配预演**——它只判断「当前有没有进程被卡死」。

**单实例资源**的检测更简单：直接用资源分配图找环（见《资源分配图》），有环即死锁——因为单实例资源的环必然死锁。

## 2 检测时机：什么时候跑检测算法

检测算法有开销，不能无脑每毫秒跑。三个常见时机：

**周期性检测**：每隔固定时间（如 1 小时）跑一次。周期短则发现快，但开销大；周期长则开销小，但死锁可能僵持很久。
**资源请求被拒时**：当某进程的资源请求无法立即满足（它被阻塞），就触发检测——死锁发生时必然有进程在等待，这是事件驱动检测的合理性。
**CPU 利用率骤降时**：死锁会让所有进程阻塞，CPU 利用率跌到谷底——这是一个「免费」的检测信号。<span class="marginnote">「CPU 利用率骤降 → 可能死锁」是个聪明的启发：正常系统 CPU 不会无故闲置，一旦利用率跌破阈值，多半有进程集体卡住。数据库与服务器监控用「僵死进程数」「锁等待超时」作为检测信号，是同一思想的工程化。</span>

**检测时机的权衡**：检测越频繁，发现越快、死锁僵持越短，但检测本身消耗 CPU；检测越稀疏，开销越小，但死锁可能让系统「假死」很久。

## 3 检测算法的手工演练

用一个小例子走一遍（$n=3$ 进程，$m=2$ 类资源，Available = (0,0)）：

| 进程 | Allocation | Request（当前请求） |
| --- | --- | --- |
| $P_0$ | (0,1) | (0,0) |
| $P_1$ | (2,0) | (2,0) |
| $P_2$ | (3,0) | (0,0) |

1. Work = (0,0)。找 Request ≤ Work 且未完成的进程。
   - $P_0$：Request (0,0) ≤ (0,0) ✓，且 Allocation ≠ 0。释放：Work += (0,1) = (0,1)，Finish[0]=true。
   - $P_1$：Request (2,0) ≤ (0,1)？否。
   - $P_2$：Request (0,0) ≤ (0,1) ✓。释放：Work += (3,0) = (3,1)，Finish[2]=true。
2. 再扫：$P_1$：Request (2,0) ≤ (3,1) ✓。释放：Work += (2,0) = (5,1)，Finish[1]=true。
3. 全部 Finish = true → **无死锁**。

若中间卡住，Finish=false 的进程就是死锁进程。

## 4 核心对比表：检测算法 vs 银行家算法

| 维度 | 死锁检测 | 银行家算法 |
| --- | --- | --- |
| 时机 | 事后（死锁发生后） | 事前（分配前） |
| 输入 | 当前 Request（实际请求） | Need（最大需求） |
| 动作 | 判断当前是否有死锁 | 预演分配、拒绝不安全 |
| 是否需要预知 | **否** | **是（Max）** |
| 结果 | 报告死锁进程 | 批准或拒绝请求 |
| 复杂度 | 较低 | 较高 |

**辨析｜易错点：** 「检测算法找到死锁 = 系统立刻瘫痪」是误解。**检测只是「发现」，处理是下一步**（见下一篇《死锁恢复》）。而且检测算法的判定依赖 Request——若某进程的 Request 无法满足，检测才认定它「卡死」；若进程自己也在推进，它不构成死锁。**检测报告的是「当前被卡住且无法释放的进程」，不是「历史上死过一次的进程」。**

另一个易错点：**检测周期与死锁僵持时长直接相关**。若检测周期太长，死锁可能僵持几小时——对交互系统不可接受；所以「请求被拒时检测」这种事件驱动方式往往比纯周期性检测更实用。

## 5 小结

- **死锁检测算法**：模拟「谁能被满足、谁释放」，判断是否有进程永远卡住；不需要最大需求。
- 多实例资源用「模拟释放」，单实例资源用「找环」即可。
- **检测时机**三选：周期性、请求被拒时（事件驱动）、CPU 利用率骤降时。
- 检测只「发现」不「处理」，恢复是下一篇的话题。
- 检测策略适合「死锁罕见且可承受恢复代价」的系统（如数据库）。
