## 为什么从信号量开始

Mutex 是一把「只能一个人进的锁」，但现实中的共享资源往往允许多个访问者：一个水池有 5 个取水口，一个服务器能同时接 1000 个连接。**信号量（semaphore）**是 Dijkstra 1965 年提出的更一般同步原语——用一个整数计数器表达「还剩多少资源可用」，把「互斥」推广成「限流」。<span class="marginnote">回顾 Mutex：它是「二元」的资源访问控制。信号量是它的推广：不只有 0/1，而是任意整数 N——既能当锁（N=1），又能当「资源池计数器」（N>1）。</span>

## 1 信号量的定义：一个计数器 + 两个原子操作

**信号量（semaphore）**：一个整型变量 `S` 加上两个原子操作 **`wait`（P，proberen 荷兰语「测试」）** 与 **`signal`（V，verhogen「增加」）**。

```c
// wait(S)：请求资源
while (S <= 0)        // 没有资源就等待（或睡眠）
    ;                 
S--;                  // 拿到一个资源

// signal(S)：释放资源
S++;                  // 归还一个资源
```

**关键**：`S` 的测试与自减必须**原子**（用硬件原语或关中断保护），否则 `wait` 本身也会竞态。现代实现里 `wait`/`signal` 是内核提供的系统调用或库函数，内部用锁 + 等待队列实现——**阻塞型信号量的 `wait` 会让进程睡眠，而非忙等**。

## 2 二元信号量：信号量当锁用

**二元信号量（binary semaphore）**：计数器 $S$ 只能取 0 或 1，功能等价于互斥锁。

- `S = 1`：资源可用。
- `wait(S)`：若 S=1 则取走（S→0）进入；若 S=0 则等待。
- `signal(S)`：S 从 0 变回 1，释放。

与 Mutex 的区别要讲清楚：

| 维度 | 二元信号量 | 互斥锁 Mutex |
| --- | --- | --- |
| 释放者 | 任何进程可 `signal` | 必须是持有者 `unlock` |
| 所有权 | 无 | **有所有权** |
| 用途 | 同步 + 互斥 | 互斥（临界区保护） |

**辨析｜易错点：** 「二元信号量 = 互斥锁」在「效果」上对，在「语义」上不对。**Mutex 有所有权概念**——只有持有者能释放，防止别人乱放锁；二元信号量没有所有权，任何进程都能 `signal`。工程上**临界区保护用 Mutex，同步（A 做完 B 才做）用信号量**，二者不可混用——这正是《生产者-消费者》里二元信号量「让路」的原因。

## 3 计数信号量：资源池计数器

**计数信号量（counting semaphore）**：计数器 $S$ 可取任意非负整数，表示**可用资源的数量**。

经典用法——限流资源池：

```c
// 池中有 5 个连接可用
counting_semaphore conn_pool(5);

// 每次使用连接：
wait(conn_pool);        // 有连接则取一个，无则等待
/* 用连接 */
signal(conn_pool);      // 用完归还
```

- `S` 初始为 5：前 5 个 `wait` 都能立即通过（S 减到 0）。
- 第 6 个 `wait` 阻塞，直到有人 `signal` 归还。

计数信号量同时实现了**互斥（S 初始化 1）**、**同步（让一个进程等另一个完成）**、**资源计数（S 初始化 N）**三种能力——这是它「瑞士军刀」称号的由来。<span class="marginnote">Python 的 `threading.Semaphore(5)`、Java 的 `Semaphore(5)` 都是计数信号量，常用于限流（同时最多 5 个任务）与连接池。它比你想象的更常见：数据库连接池、线程池限流都是它的应用。</span>

## 4 信号量解决同步：顺序的「接力棒」

信号量最精妙的应用是**让两个进程严格按顺序执行**。设进程 A 先执行、B 后执行：

```c
// 全局：semaphore sync = 0;

// A 进程
...A 的代码...
signal(sync);       // ① A 完成，发信号

// B 进程
wait(sync);         // ② B 等信号（S 初始 0，必等）
...B 的代码...
```

因为 `sync` 初始为 0，B 的 `wait` 必然先阻塞；直到 A 执行 `signal` 使 S 变 1，B 才被放行——**B 严格在 A 之后执行**。这就是「同步（synchronization）」的字面实现：不用共享数据，只用信号量的计数语义安排先后顺序。<span class="marginnote">这个「初始 0 的二元信号量当接力棒」的模式，正是《生产者-消费者》同步的核心：full 信号量初始 0，保证消费者不会在无数据时取出；empty 信号量初始 N，保证生产者不会塞爆缓冲区。</span>

## 5 核心对比表：信号量的能力矩阵

| 应用 | S 初值 | 语义 |
| --- | --- | --- |
| 互斥 | 1 | 一次一个进程进临界区 |
| 同步 | 0 | 后执行者等先执行者发信号 |
| 资源计数 | N | 最多 N 个进程同时使用资源 |
| 限流 | N | 同时最多 N 个任务在跑 |

**辨析｜易错点：** 「信号量不会死锁」是严重误解。**信号量用错照样死锁**——两个进程各自 `wait` 对方已持有的信号量，互相等下去。信号量的危险在于它太自由：没有所有权、没有自动释放，用错顺序或漏掉 `signal` 都会出问题。Dijkstra 自己也承认信号量「很难用对」，这促成了管程的诞生（下一篇）。

## 6 小结

- **信号量** = 整型计数器 + 原子操作 `wait`（P，取资源）与 `signal`（V，还资源）。
- **二元信号量**（S∈{0,1}）当锁用；与 Mutex 的区别是**无所有权**、任何进程可释放。
- **计数信号量**（S=N）当资源池/限流用，N 个资源并发可用。
- 初始 0 的信号量可做**同步接力棒**，强制进程按序执行。
- 信号量用错照样死锁，「很自由」也「很难用对」，促使管程诞生。
