## 为什么从 IPC 经典机制开始

上一篇给了 IPC 的抽象框架（共享内存 vs 消息传递），这篇落地到具体机制。管道、FIFO、消息队列、共享内存段——这四个名字在系统编程里天天见，但它们的区别、适用场景、以及「谁跟谁是一家的」常常让人混淆。把这四兄弟认全，你对 IPC 的理解就完成了从「概念」到「工具」的跃迁。<span class="marginnote">这四种机制可以分成两派：管道/FIFO/消息队列是「消息传递派」，共享内存段是「共享内存派」。记住这个分派，就记住了它们一半的性格。</span>

## 1 管道（pipe）：有血缘关系的单向管道

**管道（pipe）**：内核维护的一块环形缓冲区，一端写、一端读，数据先进先出。管道是 Unix 最古老的 IPC，shell 里的管道（`|`）就是它：管道把 grep 的输出接到 wc 的输入。

**单向**：数据只能从写端流向读端。
**有血缘**：无名管道只在**父子进程/兄弟进程**之间用，因为管道创建时返回的两个文件描述符要通过继承传给子进程。
**流式**：没有消息边界，写端写入的字节流被读端按任意大小读出。

一个最小示例——父子进程通过管道传递数据（C 语言）：

```c
int fd[2];
pipe(fd);                        /* fd[0] 读端，fd[1] 写端 */

if (fork() == 0) {               /* 子进程：写 */
    close(fd[0]);                /* 关闭读端 */
    write(fd[1], "hello", 5);
} else {                         /* 父进程：读 */
    close(fd[1]);                /* 关闭写端 */
    read(fd[0], buf, 5);
}
```

**辨析｜易错点：** 管道**只能单向**。想双向通信必须建两根管道，或者用下文的 socketpair（双向管道）。另一个易错点：**读端先关，写端再写会收到 SIGPIPE 信号**——shell 里 `yes | head` 中的 `yes` 就是被 SIGPIPE 干掉的，这是 Unix 优雅处理「下游不要了」的机制。

**管道的容量与原子性**：Linux 无名管道默认缓冲区约 64 KB，写端写入超过容量会阻塞，直到读端消费腾出空间——**管道自带背压**：下游处理慢，上游自动减速。另一个关键数字是 `PIPE_BUF`：POSIX 规定**写入不超过 `PIPE_BUF`（Linux 为 4096 字节）的写是原子的**——要么整条写入，要么完全不写。<span class="marginnote">多个写者并发向同一管道写小块数据时，`PIPE_BUF` 内的写保证不与其他写交错——这是「一次写一条完整消息」的协议基础。超过 `PIPE_BUF` 的写可以分多次完成，读端可能读到「半条」。</span>「容量 64 KB + 原子性 4096 字节」这两个数字，是理解管道背压与并发写的基础。

## 2 FIFO（命名管道）：没有血缘也能用

**FIFO（命名管道 / named pipe）**：用文件系统的名字标识的管道，用 `mkfifo()` 创建。它解决了无名管道「必须有亲缘关系」的限制——**任意两个进程，只要知道 FIFO 的名字，就能通过它通信**。

与管道的读写语义完全相同（先进先出、流式、单向）。
但以「文件」形式出现在文件系统中，`ls -l` 能看到类型为 `p` 的文件。
常用于「客户端-服务器」模型：服务器创建 FIFO 供客户端写入请求。

**管道 vs FIFO 只有一点本质差别：有无名字、能否跨血缘。** 其余语义一致。<span class="marginnote">FIFO 在文件系统里露脸，但数据并不落盘——数据仍在内核缓冲区里，FIFO 的名字只是「门牌号」。这是「把内核对象伪装成文件」的典型，见第十二篇《文件系统》里「一切皆文件」的再讨论。</span>

## 3 消息队列：有边界的消息邮局

**消息队列（message queue）**：内核维护的、按消息单元组织的数据链表。与管道不同，消息队列**有消息边界**——每条消息独立存在，可带类型，可优先级；接收方按类型选择接收。

例如，进程 A 发送一条类型为 `1` 的消息（`msgsnd`），进程 B 可以用 `msgrcv` 的 type 参数 **只取类型 1** 的消息，而类型 2、3 的消息留在队列里——这是管道（字节流，无法分类）做不到的。

- **有界**：每条消息长度固定上限，队列总量受限，满了 send 阻塞或失败。
- **有类型**：接收时可只取某种类型的消息，天然支持「按主题订阅」。
- 进程退出不销毁队列（除非显式删除），生命周期独立于进程——这点与管道不同。
- **显式清理**：队列要 `msgctl(IPC_RMID)` 显式删除，且有内核上限（`msgmni`/`msgmax`）；忘记清理会占着内核内存——这是它在现代系统中地位下降的原因之一，共享内存与套接字更常用。

## 4 共享内存段：最快的 IPC

**共享内存段（shared memory segment）**：内核分配一块物理内存，多个进程把它映射进各自的地址空间，直接读写。System V 的 `shmget`/`shmat` 与 POSIX 的 `shm_open`+`mmap` 是两种主流 API。

- **最快**：数据不拷贝、不过内核，直接访存。
- **最危险**：没有内核内置同步，需要信号量等原语配合（见第六篇）。
- 共享内存段也是 `mmap` 的亲戚——`mmap` 映射匿名内存或文件都能当作共享内存用，详见第九篇《内存映射文件》。

**辨析｜易错点：** 「消息队列和共享内存都是 System V IPC，所以它们一样快」——错。**消息队列每次收发都要把消息复制进/出内核，共享内存建立映射后零拷贝**，性能差一个量级。选择原则：高频大块数据用共享内存，低频结构化小消息用消息队列。

**数值直觉：一次 4 KB 消息的拷贝成本**。消息队列送一条 4 KB 消息：要「用户 → 内核（`msgsnd`）→ 用户（`msgrcv`）」**两趟拷贝 + 两次系统调用**；共享内存建好后读写是**纯内存访问**（零系统调用、零拷贝）。<span class="marginnote">每秒百万条消息的高频场景，两趟拷贝的吞吐差距可达一个数量级——这就是高性能 IPC 最终都倾向共享内存或 mmap 的原因（Kafka 的零拷贝、Redis 共享页都是这个思路）。</span>「拷贝在哪发生」决定了 IPC 的速度下限：**能少拷一次就快一截**，这是贯穿所有 IPC 机制的性能主线。

**共享内存的同步实战**：`shmat` 之后，两个进程直接读写同一段内存——没有内核同步，必须自配。典型组合是「共享内存 + 信号量/互斥锁」：写者先拿锁再写，读者拿锁再读。<span class="marginnote">这是「用共享内存做 IPC」的经典陷阱：<strong>忘了加锁 = 竞态；加错锁粒度 = 死锁</strong>。共享内存把「同步」的责任从内核转移给了开发者——快，是要付复杂度代价的。</span>生产环境更现代的组合是 `mmap` + 原子操作 / futex。共享内存还有「命名字空间」问题：System V 用 `shmget` 的键标识、POSIX 用 `/name`——键冲突与遗忘清理是常见的运维坑。

**一句话记住这四兄弟**：管道与 FIFO 是「带水的管子」（单向、流式），消息队列是「贴了标签的邮包」（有边界、有类型），共享内存段是「合用的白板」（零拷贝、自管同步）——四者速度递增、复杂度也递增，选型永远在「简单够用」与「极致性能」之间权衡。

## 5 核心对比表：四种机制一览

| 维度 | 管道 | FIFO | 消息队列 | 共享内存段 |
| --- | --- | --- | --- | --- |
| 亲缘要求 | 必须 | 不需要 | 不需要 | 不需要 |
| 数据形态 | 字节流 | 字节流 | 有边界消息 | 原始内存 |
| 方向 | 单向 | 单向 | 双向（各自发） | 双向（各自读写） |
| 同步机制 | 内核（阻塞） | 内核（阻塞） | 内核（阻塞/非阻塞） | 用户自配信号量 |
| 速度 | 中 | 中 | 慢（两拷贝） | 最快 |
| 生命周期 | 随进程 | 随名字存在 | 显式删除 | 显式删除 |

**记忆线索**：管道与 FIFO 是「单向字节流」，区别只在有没有名字；消息队列是「有边界的邮局」；共享内存段是「零拷贝的白板」，快但要自己管同步。

**术语速查表**：

| 术语 | 含义 |
| --- | --- |
| 管道（pipe） | 有亲缘关系的单向字节流 |
| FIFO / 命名管道 | 有文件系统名字的管道 |
| 消息队列 | 有边界、有类型的消息单元 |
| 共享内存段 | 多进程映射同一物理内存 |
| `PIPE_BUF` | 保证原子性的最大写长度（Linux 4096B） |
| SIGPIPE | 写已无读端的管道收到的信号 |
| `msgsnd`/`msgrcv` | System V 消息队列收发调用 |
| `shmget`/`shmat` | System V 共享内存创建/映射 |

## 6 小结

- **管道**：有亲缘关系、单向、字节流；`pipe()` 创建。
- **FIFO**：管道 + 文件系统名字，跨血缘可用；`mkfifo()` 创建。
- **消息队列**：有消息边界与类型，可选择性接收；`msgget`/`msgsnd`/`msgrcv`。
- **共享内存段**：映射同一物理内存，零拷贝最快，需自配信号量同步。
- 两派记忆：管道/FIFO/消息队列是消息传递派，共享内存段是共享内存派。

**选择指南**：低频、小消息、求可靠 → 管道 / FIFO / 消息队列；高频、大块、求极速 → 共享内存段；跨网络 → 套接字（下一篇）。这四兄弟没有高下之分，只有「匹配负载」之别——**选错模型比实现错误更伤性能**，比如在低频场景硬上共享内存，只是白付了同步的复杂度。
