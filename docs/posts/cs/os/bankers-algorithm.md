## 为什么从银行家算法开始

上一节的安全状态是「概念」，这一节把它做成**可执行的算法**。银行家算法（Banker's Algorithm）是 Dijkstra 1965 年提出的死锁避免算法——**只有把系统留在安全状态的分配才被批准**。它的名字来自银行隐喻：银行家不能把钱贷到「放不出去又收不回来」的地步。虽然现实中很少用（需要预知最大需求），但它是理解「安全状态判定」的标准算法，也是操作系统课程的必修经典。<span class="marginnote">回顾《死锁避免》：安全状态 = 存在安全序列。银行家算法就是在每次分配前跑一遍「找安全序列」的判断——只不过它用矩阵与向量高效地做这件事。</span>

## 1 数据结构：四个矩阵

银行家算法维护四组数据（设 $n$ 个进程、$m$ 类资源）：

- **Available[m]**：每类资源的**可用实例数**。
- **Max[n][m]**：每个进程对每类资源的**最大需求**。
- **Allocation[n][m]**：每个进程**当前已分配**的实例数。
- **Need[n][m]**：每个进程**还需要的**实例数，其中 **Need[i][j] = Max[i][j] − Allocation[i][j]**。

例子（$n=5$，$m=4$ 的经典教材数据，只列两个进程示意）：

| 进程 | Allocation | Max | Need（=Max−Alloc） |
| --- | --- | --- | --- |
| $P_0$ | (0, 1, 0, 0) | (0, 6, 5, 2) | (0, 5, 5, 2) |
| $P_1$ | (1, 0, 2, 0) | (2, 0, 3, 0) | (1, 0, 1, 0) |

Available 初始如 (1, 5, 2, 0)。**Need 是整个算法的燃料**——判断「谁的需求能被满足」就看它。

## 2 安全性算法：判定当前状态是否安全

安全性算法的步骤（核心循环）：

1. 设 Work = Available（可用资源快照），Finish[i] = false 全部未完成。
2. 找一个 i，使 **Finish[i] = false 且 Need[i] ≤ Work**。
   - Need[i] ≤ Work 表示「每类资源：还需要 ≤ 可用」，即当前可用资源能喂饱 $P_i$。
3. 若找到，让 $P_i$ 完成：**Work += Allocation[i]**（释放它的资源），Finish[i] = true，回到步骤 2。
4. 若找不到新的 i：
   - 所有 Finish 都为 true → **安全**，安全序列为释放顺序。
   - 否则 → **不安全**。

**这就是「找安全序列」的机械化**：不断找「现有资源能满足的进程」，释放它，循环。找到安全序列 = 安全状态。

## 3 公式解析：Need 与安全判定的向量比较

核心关系就一个：

$$\text{Need}[i] = \text{Max}[i] - \text{Allocation}[i], \qquad \text{可行判据}: \text{Need}[i] \le \text{Work}$$

- **Need[i]**：$P_i$ 还差多少资源才能达到最大需求。
- **Max[i]**：$P_i$ 宣称的峰值需求（前提：进程必须如实申报，这是算法可行性的假设）。
- **Allocation[i]**：$P_i$ 已占的资源。
- **Need[i] ≤ Work**：对每一类资源，$P_i$ 的剩余需求都不超过当前可用——这时让 $P_i$ 完成是安全的。
- 向量比较是**逐分量 ≤**：$(1,2) \le (2,3)$ 成立，但 $(2,1) \le (2,0)$ 不成立。

**直觉**：银行家「借钱」的逻辑——只有当「你差的每一笔钱，我现在都拿得出来」时才贷给你；而你还钱（释放资源）后，我才有更多钱贷给下一个。**先喂饱最饿的人，他吃完归还的资源再去喂别人。**

## 4 资源请求算法：分配前预演

当进程 $P_i$ 请求资源 $Request[i]$ 时，三步检查：

1. **$Request[i] \le Need[i]$？** 请求超过宣称需求 → 非法，拒绝。
2. **$Request[i] \le Available$？** 现有资源不够 → 让 $P_i$ 等待。
3. **预演分配**：假装批准，更新
   $$Available \mathrel{-}= Request[i], \quad Allocation[i] \mathrel{+}= Request[i], \quad Need[i] \mathrel{-}= Request[i]$$
   然后跑**安全性算法**。若新状态安全 → 真正批准；若不安全 → **回滚预演，拒绝请求**，$P_i$ 等待。

**每一步分配都用「预演 + 安全判定」把关**，系统因此永远停留在安全状态。

**辨析｜易错点：** 「银行家算法 = 安全性算法」是常见混淆。**两者不同**：安全性算法只判断「当前状态安不安全」（一个算法）；资源请求算法在每次请求时「预演分配 + 调安全性算法」决定是否批准（一个策略）。前者是判据，后者是决策。

另一个易错点：**算法要求进程如实申报 Max，且运行中不能超过**。现实中进程很难预告峰值需求——所以银行家算法「理论上最优、工程上难用」。**算法的价值在思想：分配前预演、拒绝不安全、让系统永不进入危险区。**

## 5 单资源 vs 多资源：复杂度对照

| 维度 | 单资源类 | 多资源类 |
| --- | --- | --- |
| 数据结构 | 标量 Available、一维数组 | 向量 Available、矩阵 Max/Alloc/Need |
| 比较 | 数值比较 | 逐分量向量比较 |
| 安全性判断 | 简单排队判断 | 循环扫描矩阵（$O(n^2 m)$） |
| 教学价值 | 帮助理解安全序列 | 完整的多资源银行家算法 |

**设计启示**：单资源版本适合教学入门，多资源版本才接近真实（一台机器有多种资源：CPU 时间、内存页、文件描述符、设备）。复杂度从标量到矩阵，本质是把「还差多少」从一维变成多维。

## 6 数值算例：教科书五进程的完整判定

用《操作系统概念》的经典数据（5 个进程、3 类资源 A/B/C，总量 (10,5,7)）走一遍安全性算法：

| 进程 | Allocation | Max | Need (=Max−Alloc) |
| --- | --- | --- | --- |
| $P_0$ | (0,1,0) | (7,5,3) | (7,4,3) |
| $P_1$ | (2,0,0) | (3,2,2) | (1,2,2) |
| $P_2$ | (3,0,2) | (9,0,2) | (6,0,0) |
| $P_3$ | (2,1,1) | (2,2,2) | (0,1,1) |
| $P_4$ | (0,0,2) | (4,3,3) | (4,3,1) |

已分配总量 (7,2,5)，故 **Available = (10,5,7) − (7,2,5) = (3,3,2)**。逐轮扫描：

| 轮次 | 选中 | 判据 Need ≤ Work | Work 更新后 |
| --- | --- | --- | --- |
| 1 | $P_1$ | (1,2,2) ≤ (3,3,2) ✓ | (3,3,2)+(2,0,0) = (5,3,2) |
| 2 | $P_3$ | (0,1,1) ≤ (5,3,2) ✓ | (5,3,2)+(2,1,1) = (7,4,3) |
| 3 | $P_4$ | (4,3,1) ≤ (7,4,3) ✓ | (7,4,3)+(0,0,2) = (7,4,5) |
| 4 | $P_0$ | (7,4,3) ≤ (7,4,5) ✓ | (7,4,5)+(0,1,0) = (7,5,5) |
| 5 | $P_2$ | (6,0,0) ≤ (7,5,5) ✓ | (7,5,5)+(3,0,2) = (10,5,7) |

五个进程全部完成 → **状态安全，安全序列 $\langle P_1, P_3, P_4, P_0, P_2 \rangle$**。<span class="marginnote">注意 $P_0$ 的 Need (7,4,3) 比初始 Available (3,3,2) 大——第一轮根本喂不饱它，必须等前面的进程完成、Work 涨起来才轮到。这正是安全性算法的核心洞察：<strong>「先喂饱最饿的人（当前能喂饱的），他吃完归还，再去喂下一个」</strong>——若存在这样的次序，系统就安全。</span>若某一步没有任何进程满足 Need ≤ Work，就立刻判定不安全——那正是「所有人都在等别人放资源」的死锁预告。

## 7 术语速查表

| 术语 | 含义 | 一句话记忆 |
| --- | --- | --- |
| Available | 每类资源的可用数 | 银行家手里的钱 |
| Max | 进程的最大需求 | 借钱的峰值 |
| Allocation | 已分配的资源 | 已经借出的 |
| Need | 还差多少（=Max−Alloc） | 还要借多少 |
| 安全性算法 | 判定状态是否安全 | 找安全序列 |
| 资源请求算法 | 分配前预演+判定 | 不放心就不贷 |
| Work | 可用资源快照 | 判定中的临时余额 |

## 8 小结

- 银行家算法维护 **Available / Max / Allocation / Need** 四个矩阵，核心是 **Need = Max − Allocation**。
- **安全性算法**：循环找 Need ≤ Work 的进程，模拟完成释放，全完成即安全。
- **资源请求算法**：请求检查 → 预演分配 → 安全性判定，不安全则拒绝。
- **银行家算法 = 资源请求策略 + 安全性判据**，两者合体才完整。
- 前提是进程**如实申报最大需求**，现实难满足，故以思想价值著称。
