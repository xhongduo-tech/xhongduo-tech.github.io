## 为什么从读者-写者问题开始

生产者-消费者用「一个缓冲区」解决了「放与取」。但现实里有另一类共享：**多个进程读同一份数据，偶尔有人写**。数据库、文件缓存、配置表都是这样。读者-写者问题的核心洞察是：**「读」与「读」可以并发，「读」与「写」必须互斥，「写」与「写」必须互斥**——因为读不改数据，多读无害。<span class="marginnote">回顾生产者-消费者：它把「互斥」用在所有访问上（放、取都独占）。读者-写者问题的进步是：识破了「读不改变状态」这一事实，允许读者并发——这是「读写锁」的哲学起点。</span>

## 1 问题定义与规则

**读者-写者问题（readers-writers problem）**：多个进程共享一个数据对象，其中一些是**读者**（只读），一些是**写者**（读写）。约束：

**读者-读者**：可并发（同时读）。
**读者-写者**：互斥（读时不能写，写时不能读）。
**写者-写者**：互斥（不能同时写）。

问题的**难点**不在「互斥」——读者-写者与写者-写者互斥用普通锁即可——而在「如何让多个读者同时进入，而写者一来就全体让路」。用朴素的一把锁实现，读者之间也会被互斥，就失去了「多读并发」的意义。

## 2 经典解法：读者优先（readers-preference）

**读者优先**：只要有一个读者在读，后续读者都可以进入；写者必须等所有读者离开后才能写。

```c
semaphore rw_mutex = 1;   // 大门锁：写者独占，第一个读者也要拿
semaphore mutex = 1;      // 保护 read_count
int read_count = 0;       // 当前读者数

/* 写者 */
wait(rw_mutex);
/* 写操作 */
signal(rw_mutex);

/* 读者 */
wait(mutex);
read_count++;
if (read_count == 1) wait(rw_mutex);   // 第一个读者锁门
signal(mutex);
/* 读操作 */
wait(mutex);
read_count--;
if (read_count == 0) signal(rw_mutex); // 最后一个读者开门
signal(mutex);
```

**思想拆解**：

**`rw_mutex` 是「大门的锁」**：写者独占它；**第一个读者**进入时也要拿它（把写者挡在外面），**最后一个读者**离开时释放它。
**`read_count` 记账读者数**：读者之间靠它判断「我是第几个」，只有第一个读者需要抢 `rw_mutex`，后续读者直接进入。
**`mutex` 保护 `read_count`**：多个读者同时修改计数器，需要互斥。

**效果**：读者读时，写者被挡在 `rw_mutex` 外；读者可以并发涌入。<span class="marginnote">这个方案对应的就是「读写锁（rwlock）」的读者模式：读锁让读者共享进入，写锁独占。数据库的共享锁（S）与排他锁（X）也是同一模型。</span>

## 3 读者优先的代价：写者饥饿

读者优先方案有个严重问题：**写者可能被饿死**——只要读者不断到达，`read_count` 永远不为 0，`rw_mutex` 永远被第一个读者占着，写者永远等不到。

这是「优先」二字的必然代价：**给读者优先，写者就饿；给写者优先，读者就等**。公平性必须在两个方向上权衡。

**写者优先（writers-preference）**：写者一到就封锁新读者，让已排队的写者优先完成。实现更复杂（要额外信号量管理写者队列），但避免了写者饥饿。数据库系统常采用**写者优先或公平策略**——因为写操作不及时完成，系统数据会过时。

**辨析｜易错点：** 「读者优先方案完全正确」只对一半——它满足互斥与前进，但**不满足写者的有限等待**（写者可能无限期等待）。对照《临界区问题》的三原则，这是「有限等待」被破坏的典型。**读多写少的系统中读者优先可以接受，但写者不能无限饿死是工程底线。**

## 4 核心对比表：读者优先 vs 写者优先

| 维度 | 读者优先 | 写者优先 |
| --- | --- | --- |
| 读者可并发 | 是 | 是 |
| 新读者到达时 | 立即进入 | 有写者等待则排队 |
| 写者等待 | 可能**无限期**（饥饿） | 有界 |
| 实现复杂度 | 低 | 高 |
| 适用场景 | 读极多、写可容忍延迟 | 写需及时、公平性重要 |

## 5 公式解析：读写锁的并发度

读写锁的价值可以用并发度量化。设读者到达率 $\lambda_r$、平均读时间 $R$，写者到达率 $\lambda_w$、平均写时间 $W$。若用普通互斥锁（读写都独占），系统吞吐约：

$$\text{吞吐}_{互斥} = \frac{1}{\lambda_r R + \lambda_w W + \cdots}$$

而读写锁让读者并行，读者占用的「有效时间」不再是 $\lambda_r R$ 而是近似 $\max(\lambda_r R \cdot \text{重叠度}, \ldots)$——**多个读者共享同一段时间**，等效于把读者的串行时间压缩。

- 当读者占比极高（$\lambda_r \gg \lambda_w$）时，读写锁的收益趋近「读者免费」——这是缓存、配置、元数据服务广泛使用 rwlock 的原因。
- 当写者频繁时，读写锁的复杂同步（计数、唤醒）可能反而拖慢系统。

**直觉**：读写锁适合「**读多写少且读很耗时**」的场景；「读多写多」时收益有限，「写多」时不如普通锁。选型要量数据，不能只看名字。

## 6 小结

- **读者-写者问题**：读者可并发、读写互斥、写写互斥——「共享读、独占写」。
- 读者优先方案：`rw_mutex`（大门锁）+ `read_count`（读者数）+ `mutex`（保护计数）。
- 第一个读者锁门、最后一个读者开门，写者全程被挡。
- **读者优先会让写者饥饿**，写者优先避免饥饿但实现复杂。
- 读写锁适合**读多写少且读耗时**的场景，选型需量化读者/写者比例。
