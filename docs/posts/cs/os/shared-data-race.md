## 为什么从竞态条件开始

多线程/多进程之所以危险，不是因为「同时执行」，而是因为**共享数据**。当两个执行流同时读写同一个变量，结果就不再确定——这被称为**竞态条件**。它是第六篇《进程同步》要解决的核心问题的「病症」，也是从「并发」走向「同步」的必经关口。<span class="marginnote">回顾《线程概念》的权衡：线程共享地址空间让通信快，也让「同时写一个变量」成为可能。竞态条件就是「共享」这一便利所付的利息。</span>

## 1 共享数据与临界资源

**共享数据（shared data）**：多个进程/线程可以并发访问的数据。在共享内存 IPC 里是共享的内存区，在线程里是全局变量、堆对象。

**临界资源（critical resource）**：一次只允许一个执行流访问的共享资源。比如共享计数器、文件末尾指针、缓冲区。

**临界区（critical section）**：访问临界资源的那段代码。进程进入临界区前要请求许可，用完离开要释放许可。

**竞态条件（race condition）**：多个执行流**并发**访问同一共享数据，且**最终结果取决于访问的具体时序**（谁先谁后）时发生的错误。同一个程序，这次跑对、下次跑错，就是竞态条件的典型症状。<span class="marginnote">竞态条件的可怕在于「不总是发生」：它只在特定指令交错时出错，单测常常测不出来，只有高并发压测才现形。这就是并发 bug 调试地狱的根源。</span>

### 为什么要共享数据

共享不是「坏设计」，恰恰相反，它是效率的源泉：线程共享地址空间，避免进程间昂贵的 IPC；共享计数器用于统计；共享缓冲区用于生产者-消费者。**问题不在「共享」，而在「共享时没有同步」**——共享是收益，同步是代价，竞态条件就是「只拿了收益、没付代价」时的灾难。

现代语言的应对：Go 的 goroutine + channel、Rust 的所有权与借用检查、Java 的并发工具类，都是在「共享数据」前设一道「要么不共享、要么安全共享」的闸门。

### 共享与隔离的取舍

| 维度 | 共享数据 | 线程局部数据（TLS） | 进程独立 |
| --- | --- | --- | --- |
| 通信成本 | 最低（直接读变量） | 无共享 | 高（IPC） |
| 竞态风险 | 高 | 无（每线程一份） | 无（地址空间隔离） |
| 适用 | 高频协作（缓冲、计数） | 每线程状态（errno、缓存） | 强隔离任务 |

## 2 为什么共享数据会出错：指令交错的破坏

来看经典的计数器例子。counter++ 在机器层面是三条指令：

```
load   counter, R1    ; ① 读 counter 到寄存器
add    R1, #1         ; ② 寄存器加 1
store  R1, counter    ; ③ 写回 counter
```

两个线程并发执行 counter++，可能交错成这样：

| 步骤 | 线程 A | 线程 B | counter 实际值 |
| --- | --- | --- | --- |
| 1 | 读 counter（=5） | | 5 |
| 2 | | 读 counter（=5） | 5 |
| 3 | 加 1 → 6 | | 5 |
| 4 | 写 counter ← 6 | | **6** |
| 5 | | 加 1 → 6 | 6 |
| 6 | | 写 counter ← 6 | **6** |

两条 counter++ 本应把 5 变成 7，结果却变成 6——**一次更新被覆盖丢失了**。原因：线程 B 读到的还是旧值 5，A 已经写回 6，B 的「加一」基于过期数据。

**核心认识：单条高级语言语句（counter++）在指令层面是「读-改-写」三段，并非原子操作。** 并发执行时这些子操作可以任意交错，交错就会产生错误结果。<span class="marginnote">「读-改-写」不原子，是竞态条件的物理根源。同步的本质，就是给这「读-改-写」三段加一道「互斥」的闸门，让它们整体上像一次原子操作。</span>

再举一个「银行转账」的例子，两个线程并发给同一账户执行 `balance = balance - 100`：

| 步骤 | 线程 A | 线程 B | balance |
| --- | --- | --- | --- |
| 1 | 读 balance（=500） | | 500 |
| 2 | | 读 balance（=500） | 500 |
| 3 | 减 100 → 400 | | 500 |
| 4 | | 减 100 → 400 | 500 |
| 5 | 写 balance ← 400 | | 400 |
| 6 | | 写 balance ← 400 | **400** |

两次取款本应把 500 减到 300，结果却是 400——**一次取款凭空消失了**。这说明竞态条件不只是「计数器差一」的学术问题，它意味着真实系统里**钱与数据的真实丢失**。

**辨析｜易错点：** 「把 counter++ 换成一条原子指令就万事大吉」是重要但不充分。原子指令只保证「单次操作的原子性」；若逻辑是「读旧值 → 判断 → 写新值」的多步复合操作（如 `if (count > 0) count--`），单条原子指令仍不够，需要锁或 CAS 循环把「复合操作」整体原子化——**原子性是「操作粒度」的属性，不是「数据」的属性**。

## 3 竞态条件的分类与危害

竞态条件按数据访问模式大致分两类：

- **读-写竞争（data race）**：一个线程写、另一个线程读/写同一变量，无同步。结果未定义，可能读到半更新状态。
- **丢失更新（lost update）**：两个线程基于同一旧值各自计算，后写覆盖先写，一次更新永久丢失（如上例）。

危害范围从「结果错误」到「数据损坏」再到「系统崩溃」，且**极难复现与定位**——它依赖精确的时序，运行时调度稍有变化就不再出现。这也是为什么并发 bug 被认为是软件工程里最贵的 bug 之一。

**辨析｜易错点：** 「加了 volatile 就安全了」是流传很广的误解。volatile 只是告诉编译器「别把这个变量缓存到寄存器，每次真去内存读」，它**保证可见性，但不保证原子性**。volatile 的 counter++ 依然是读-改-写三段，依旧会丢更新。**正确工具是锁、原子操作（见第六篇《硬件同步原语》）或 CAS。**

### 竞态条件的真实场景

- **服务器计数**：在线用户数、请求计数并发自增，丢更新导致统计失真。
- **共享缓存/缓冲**：多线程写同一缓冲区，指针交错覆盖已写入的数据。
- **懒初始化**：`if (instance == null) instance = new Singleton()` 多线程下可能 new 出多个实例（double-checked locking 是经典反例）。
- **引用计数**：并发增减引用计数，可能过早归零导致内存被提前释放（use-after-free）。

这些场景的共同模式：**「检查—修改—写回」三步被并发打散**。识别出这个模式，就识别出了竞态条件——这是并发编程最重要的「症状识别」能力。

## 4 核心对比表：几个易混概念

| 概念 | 定义 | 解决手段 |
| --- | --- | --- |
| 共享数据 | 多执行流并发访问的数据 | — |
| 临界区 | 访问临界资源的代码段 | 同步原语保护 |
| 竞态条件 | 结果依赖时序的并发错误 | 互斥、原子性 |
| 数据竞争 | 无同步的并发读写同一变量 | 同步、TLS、原子操作 |

**一条主线**：共享数据 → 需要临界区 → 临界区并发执行 → 竞态条件 → 需要互斥。理解这条因果链，你就知道第六篇《进程同步》的全部工具（锁、信号量、管程）都是在「临界区」这个环节做文章。

**自查清单**：看到并发代码，先问三个问题——这段数据会被几个执行流同时碰？碰的时候有没有锁或原子操作护住「读-改-写」整段？如果没护住，后果是什么（错值？崩溃？）。**把「共享数据」找出来，并发安全的半场就赢下了。**

## 5 小结

- **临界区**是访问临界资源的代码段；**竞态条件**是并发访问共享数据导致的「结果依赖时序」的错误。
- 竞态条件的物理根源：**counter++ 是「读-改-写」三段，不原子，可被任意交错**。
- 典型症状是**丢失更新**，且 bug 偶发、难复现、高并发才现形；银行转账例子说明它意味着真实数据的丢失。
- **volatile 只保证可见性、不保证原子性**，防不了竞态。
- **原子性是操作粒度的属性**：复合操作（判断-修改-写回）需要锁或 CAS 整体原子化。
- 共享是收益、同步是代价；TLS 与进程隔离是「不共享」的两条退路。
- 识别「检查—修改—写回被并发打散」的模式，是并发 bug 症状识别的第一步。
- 治理主线：**共享数据 → 临界区 → 竞态 → 互斥**，第六篇的全部工具都在临界区做文章。
