## 为什么从操作系统的发展历史开始

我们已经读过《操作系统的目标与作用》：操作系统的核心是**分配资源**与**控制程序执行**。但「目标」回答的是「为什么要有操作系统」，而「历史」回答的是「操作系统为什么长成现在这个样子」。今天看来理所当然的设计——作业排队、进程切换、时间片、实时响应——没有一样是凭空发明出来的，全部是对具体痛点的回应：计算机太贵了，所以要让它的每一秒都不浪费；用户等得太久了，所以要分时；导弹制导错过截止期就完了，所以要实时。

这段历史能把整个操作系统专题的后续章节串成一条因果链：**多道程序引出进程与调度，分时引出时间片轮转，实时引出截止期调度，而双模式操作是这一切得以安全运转的底座。** 看懂这段历史，后面每一章都是在给这条链补细节。

## 1 没有操作系统的时代：人肉调度

1940 至 1950 年代的计算机（如 ENIAC）没有操作系统，甚至没有我们今天意义上的编译器。程序以插线板接线和穿孔卡片的形式进入机器，一次一个程序，由操作员手工装填。这个阶段叫作**串行处理（serial processing）**：

- 用户必须预约上机时间，在机房物理地操作机器；
- 一个程序运行期间，机器完全归它所有，其他程序只能在门外排队；
- 装卡片、启动、取结果之间的**装卡时间（setup time）**，往往远远超过程序本身的运行时间。

串行处理有两个致命问题。其一是**调度（scheduling）**：用户按预约轮流上机，机器在人换人之间频繁空闲。其二是**准备时间**：每次换程序都要重新接线、装卡片、排开关。在计算机一台造价几十万美元的年代，这样的利用率是完全不可接受的。

**重点：串行处理浪费的不是「程序运行时间」，而是「两次运行之间的切换时间」。** 操作系统历史上的第一个使命，就是消灭这种切换上的浪费——让人去做人擅长的事（想问题），让机器去做机器擅长的事（跑程序）。

## 2 批处理系统：让作业自己排队

1950 年代中期，人们发明了**批处理（batch processing）**：把一批**作业（job）**交给一个常驻内存的监控程序（monitor），由监控程序自动地「一个跑完，装入下一个」。通用汽车公司在 1956 年为 IBM 701 开发了一套批处理系统，被公认为最早的批处理系统之一；其后是 FORTRAN 监控系统（FMS，1957）、IBM 的 IBSYS（面向 IBM 7094），以及里程碑式的 IBM OS/360——1964 年随 System/360 家族发布，是第一个规模庞大、统治一代人的商用操作系统家族。

监控程序的工作，可以浓缩成一段极简的伪代码：

```text
loop
    把下一个作业从输入队列装入内存
    把控制权转交给该作业
    等待作业结束或出错
    把输出写到打印机，清理内存
end loop
```

这就是**单道批处理（single-stream batch）**：内存里永远只有一个作业，CPU 与 I/O 设备仍然大量地互相等待对方。操作员的存在形式变了——从「操作机器」变成「操作读卡机与打印机」——但「人」仍在环路里。

**辨析｜易错点：批处理并不意味着「没人参与」。** 操作员依然要装卡片、分发输出；但**在作业运行期间，用户无法与作业交互**。程序出错，只能等运行结束看打印出来的输出。批处理消灭了装卡时间，却牺牲了交互性——这正是后面分时系统要回答的问题。

下面这张表把早期演化收拢成一眼能看完的脉络：

| 时代 | 代表系统/硬件 | 关键动机 | 留下的遗产 |
| --- | --- | --- | --- |
| 串行处理（1940s–1950s） | ENIAC、早期插线板机器 | 无 | 暴露「切换太贵」 |
| 批处理（1950s–1960s） | GM/IBM 701、FMS、OS/360 | 消除装卡时间 | 监控程序、作业队列 |
| 多道程序（1960s） | OS/360 MFT/MVT | 填满 CPU 空闲 | 进程、调度、内存保护 |
| 分时（1960s–1970s） | CTSS、MULTICS、UNIX | 交互与响应 | 时间片、shell、Unix 哲学 |
| 实时（1970s–至今） | 各类 RTOS | 保证截止期 | 硬实时/软实时、优先级 |

## 3 多道程序：填满 CPU 的空闲

单道批处理下，CPU 利用率依然可怜。原因在于：一个作业一旦发起磁盘读取，CPU 就只能空转等 I/O 完成，而 I/O 比 CPU 慢几个数量级——一次磁盘寻道约几毫秒，够 CPU 执行上百万条指令。

**多道程序（multiprogramming）** 的思路是：内存里同时驻留多个作业，当一个作业等待 I/O 时，CPU 立刻切换到另一个作业执行。这不是「同时执行」——单核仍是逐条执行指令——而是**「随时保证 CPU 有事可做」**，宏观上提高系统的吞吐量。多道程序能成立，靠的正是前面《中断机制与中断处理流程》一节讲过的硬件基础：I/O 完成时设备发出中断，CPU 才被告知「刚才那个作业又能跑了」，从而切换回来。

多道程序对操作系统提出了三个新要求，它们构成了后续三篇的主题：

- **内存保护**：多个作业共存于内存，必须防止它们相互越界——引出第八篇内存管理。
- **调度**：同时有多个可运行作业，该让谁先跑？——引出第五篇 CPU 调度。
- **进程管理**：OS 必须为每个作业记住「它上次跑到哪条指令」，这就是进程控制块 PCB——引出第三篇进程。

**重点：多道程序把「作业」从一个静止的卡片堆，变成了一个需要被持续跟踪、反复调度、妥善保护的动态实体。** 「进程」这个概念，就是在多道程序的需求里诞生的。

## 4 分时系统：人人一台机器的幻觉

多道程序追求吞吐，但批处理用户仍然要等——几分钟到几小时。1960 年代初，MIT 的 CTSS（Compatible Time-Sharing System，兼容分时系统）开创了**分时（time-sharing）**：把 CPU 时间切成极小的**时间片（time slice）**，轮流分给每个交互用户。由于切换足够快（几十毫秒量级），每个用户都感觉「整台机器都是我的」——实际上大家在共享一台昂贵的主机。CTSS 之后是 MULTICS（MIT 与贝尔实验室、GE 合作），再往后就是 UNIX。

**辨析｜易错点：多道程序与分时都做「切换」，但目的截然不同。** 多道程序的目的是**最大化 CPU 利用率**（面向吞吐量）；分时的目的是**最小化响应时间**（面向交互体验）。分时可以被理解为「多道程序的交互化版本」——两者的核心机制（进程切换、调度队列）完全相同，差别在调度策略的目标函数。这个区别会在第五篇调度算法里反复出现：FCFS 偏多道、时间片轮转偏分时。

分时系统的血统直接通向现代操作系统：CTSS → MULTICS → UNIX → Linux。1969 年，肯·汤普森（Ken Thompson）在贝尔实验室一台闲置的 PDP-7 上写出 UNIX 的雏形；1973 年他与丹尼斯·里奇（Dennis Ritchie）用 C 语言重写，UNIX 从此开枝散叶。<span class="marginnote">UNIX 家族谱：AT&amp;T 系统 V 与加州大学伯克利分校的 BSD 两线分流；1991 年林纳斯·托瓦兹发布 Linux，直接受 MINIX 与 UNIX 启发。本专题第十五篇到第十八篇的 Linux 专题，追根溯源都在这一条线上。</span>

## 5 实时系统与走向现代

随着工业控制、航天、嵌入式计算需求出现，出现了**实时操作系统（real-time operating system, RTOS）**：系统必须在**确定的时间界限（deadline）**内完成对事件的响应，否则后果不可接受。

- **硬实时（hard real-time）**：错过截止期即灾难。例如导弹制导、汽车安全气囊触发、医疗监护。
- **软实时（soft real-time）**：错过截止期不致命，但服务质量下降。例如视频播放、在线游戏、音频流。

**辨析｜易错点：实时 ≠ 快。** 「快」是平均意义上的性能；「实时」是**保证最坏情况下也能在截止期内完成**。一个平均延迟很低、但偶尔卡顿 100 毫秒的系统，绝对不满足硬实时要求。实时调度（速率单调 RM、最早截止期优先 EDF）将是我们第五篇末与独立实时专题的内容。

此后的操作系统在三个方向上继续演化：**并行与分布式系统**（多处理器与集群，下一节的主题）；**移动与嵌入式环境**（Android、iOS 本质上是 Linux 派生的系统栈）；**云计算与虚拟化**（把一台物理机抽象成可弹性分配、可迁移的资源池）。<span class="marginnote">从「从极限到大模型」这条主线的视角看：每次操作系统演进的驱动力，都是「算力太贵、人时太贵、错不起」三者之一。当代大模型训练集群对 GPU 利用率的精细调度，本质上是多道程序思想在分布式尺度上的复活。</span>

## 6 公式解析：多道程序能把 CPU 利用率提到多高

多道程序最大的卖点是有据可查的性能提升。假设内存中有 $n$ 个进程，每个进程在一段时间内有比例 $p$ 的时间在等待 I/O。那么某一时刻**所有进程都在等 I/O、CPU 无事可做**的概率约为 $p^n$，于是 CPU 利用率为：

$$U = 1 - p^n$$

逐步拆解：

- **$p$**：单个进程「处于 I/O 等待」的时间占比。磁盘、网络远比 CPU 慢，典型的 $p$ 可能高达 0.8。
- **$p^n$**：假设各进程的等待互相独立，则 $n$ 个进程**同时**都在等待的概率是 $p$ 连乘 $n$ 次。这正是 CPU 空闲的瞬间。
- **$1 - p^n$**：CPU 不空闲——即至少有一个进程可运行——的概率，也就是 CPU 利用率。

代入数值看趋势：$p = 0.8$ 时，$n = 1$ 的利用率只有 $0.2$；$n = 4$ 时约为 $1 - 0.4096 \approx 0.59$；$n = 8$ 时约为 $1 - 0.1678 \approx 0.83$。<span class="marginnote">注意<strong>递减收益</strong>：进程从 1 个加到 4 个，利用率提高约 39 个百分点；从 4 个加到 8 个只提高约 24 个百分点。多道程序的「度」并非越多越好——内存有限，进程太多反而互相挤占内存，这就是第九篇「抖动（thrashing）」的先声。</span>

**重点：多道程序提升的是「系统利用率」，不是「单个程序的运行速度」。** 单个程序跑完甚至可能更慢（要排队等调度），但系统整体的吞吐量——单位时间完成的作业数——大幅上升。这正是操作系统在「效率」维度上的核心价值，也把它与「让单个程序更快」的编译器优化、体系结构设计在目标上区分开来。

## 7 小结

- 串行处理时代：人肉调度，浪费在**装卡时间与机器空闲**。
- 批处理：常驻**监控程序**自动排队作业，消灭装卡时间，但**牺牲交互**。
- 多道程序：内存驻留多作业，**利用 I/O 等待间隙切换 CPU**，目标是**吞吐量**。
- 分时：时间片轮流分配，目标是**响应时间**，血统链 CTSS → MULTICS → UNIX → Linux。
- 实时：**保证截止期**而非平均快慢，分硬实时与软实时。
- 多道程序的收益可用 $U = 1 - p^n$ 定量刻画，且**收益递减**。
