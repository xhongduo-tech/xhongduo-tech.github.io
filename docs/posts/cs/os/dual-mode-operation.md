## 为什么从双模式操作开始

前面讲过，中断是 CPU 与设备协作的枢纽，多道程序让多个作业共存于内存。但一个关键问题一直被回避：**凭什么一个写错的用户程序不能把整个系统搞崩？** 假设某个程序执行了「关机」或「清空内存」的指令，而硬件不设防，那么任何进程都能为所欲为——操作系统作为「资源分配者」的权威就荡然无存，多道程序带来的并发与共享也失去了安全前提。

**双模式操作（dual-mode operation）** 就是答案，也是操作系统安全性的第一块基石。它贯穿后面所有章节：系统调用、内存保护、文件访问控制、虚拟化，无一不是「模式」概念的延伸。这一节把原理讲透，后面到处都会用到。

## 1 为什么要分「用户态」与「内核态」

把程序分成「可信的」与「不可信的」，是保护最朴素的想法。操作系统自己——内核（kernel）——运行在**内核态（kernel mode）**，也叫**系统态（system mode）、特权态**；用户的应用程序运行在**用户态（user mode）**，也叫**目态**。

**重点：分模式的目的有两层——保护操作系统免受错误用户程序的侵害，同时保护用户程序彼此免受侵害。** 一个程序越界读写另一个进程的内存，同样是灾难。双模式把「能碰硬件、能碰一切」的特权收窄给内核，用户程序的一切敏感操作都必须**请求**内核代办，自己不能直接执行。

这里的关键是：光靠软件约定是不够的，因为一个恶意程序可以无视任何约定。所以模式必须是**硬件状态**——CPU 在取指、执行时都要检查当前模式，硬件在源头上拦截特权指令的非法执行。这就引出了模式位。

## 2 模式位：硬件里的一比特宪法

现代 CPU 至少有一个**模式位（mode bit）**，通常位于处理器的控制寄存器（如 x86 的 MSR 或标志位）：

- 模式位 = 0：**内核态**，可执行全部指令、访问全部内存。
- 模式位 = 1：**用户态**，只能执行非特权指令、访问受限内存。

硬件在两种情况下**自动**切换模式，不需要（也不允许）普通程序参与：

- 发生**中断**或**陷阱（trap）**时：硬件把模式位置 0，转入内核态的中断/异常处理程序；
- 从内核返回用户程序时：硬件把模式位置回 1。<span class="marginnote">模式位切换是<strong>硬件行为</strong>，不是软件行为。用户程序无法直接修改模式位，因为「修改模式位」本身就是一条<strong>特权指令</strong>——在用户态执行它，会立刻触发一个非法指令陷阱，把控制权交给内核。</span>

**特权指令（privileged instruction）** 指只能在内核态执行的指令，典型例子包括：

控制 I/O 设备（启动磁盘、设置 DMA 描述符）；
设置或修改内存管理寄存器（基址/界限寄存器、页表基址寄存器）；
管理时钟与定时器；
开启或关闭中断；
停机（halt）指令；
修改模式位本身。

**辨析｜易错点：不是所有「与硬件有关的指令」都是特权指令。** 读一个普通内存地址、做一次整数加法，用户态完全可以执行。特权指令的判定标准是「**这个操作能否被恶意程序用来破坏其他进程或系统本身**」。读时钟可能是非特权的（省一次系统调用，这就是 vDSO 的起源），但「改时钟」必须特权——否则任何程序都能篡改调度器的时间依据。

**一个具体例子：为什么应用不能直接读磁盘**。硬盘控制器寄存器、DMA 描述符所在的 I/O 地址空间，只有内核态才能访问。用户程序想读文件，唯一的路是 `open`/`read` 系统调用——内核先做权限检查，再把磁盘数据拷进用户缓冲区。**「所有硬件访问都必须经过内核」是双模式的直接推论**，也是文件系统、网络栈得以安全运行在用户态程序之上的根本原因。

## 3 指令分级：从 2 级到多级保护环

双模式是最简单的二分。真实硬件常常提供更多级别：Intel x86 提供 **4 个保护环（protection rings）**——ring 0 最内层（内核态），ring 3 最外层（用户态），ring 1、2 大多闲置。<span class="marginnote">保护环的核心是「编号越小、特权越大」。操作系统跑在 ring 0，应用跑在 ring 3，中间两环历史上留给设备驱动或安全敏感的子系统，但现代操作系统几乎不用——要么全进 ring 0（宏内核），要么驱动也进用户态（微内核）。</span>

虚拟化把这一模型又推进一步：为了在普通用户态之上再隔出一个「能运行完整操作系统」的特权域，Intel 与 AMD 加入了 VT-x / AMD-V 扩展，引入 **VMX root（宿主模式）** 与 **VMX non-root（虚拟机模式）** 两个新模式，俗称 **ring -1**。它让我们第十八篇《虚拟化与容器》能安全地在同一台物理机上同时运行多个完整的操作系统——每个虚拟机的「内核态」在宿主看来，都只是一个受限的普通程序。

保护环还能解释一个经典现象：用户态程序为什么不能随意执行 `cli` 关中断——因为它运行在 ring 3，而 `cli` 是 ring 0 才可执行的特权指令，在用户态执行会立刻触发通用保护异常（#GP）。

**重点：双模式不是操作系统的发明，而是硬件提供的一种「特权梯度」。** 操作系统选择二分或分环来使用它；虚拟化则重新定义了一层新的梯度。概念一以贯之：**越敏感的操作，越需要更高的特权级，越要由更可信的代码来执行。**

## 4 从用户态到内核态：trap 与系统调用

用户程序想读文件，但它不能直接操作磁盘——那是特权指令。怎么办？**系统调用（system call）** 是用户程序合法进入内核态的唯一通道。

流程是这样的：用户程序调用库函数 `read()` → 库函数把参数放进寄存器并填入系统调用号 → 执行一条**陷阱指令**（x86-64 上是 `syscall`，老版本是 `int 0x80`）→ CPU 硬件切换到内核态、跳转到内核预先注册的入口 → 内核校验参数、执行文件系统操作 → 返回前切回用户态。

```
read(fd, buf, count)         // 用户态：库函数把参数放进寄存器，填入系统调用号
    ↓ syscall 指令             // 陷阱指令：硬件切换到内核态
system_call 入口               // 内核态：查表、校验参数、执行、返回
    ↓ iret 返回                // 切回用户态
```

你看到的是两个「函数调用」，实际每次都是一次**用户态 → 内核态 → 用户态**的完整往返，包含模式切换、参数检查与内核执行。库函数 `read`/`write` 只是掩盖这个过程的外壳。<span class="marginnote">正因为每次系统调用都要切换模式，<strong>系统调用比普通函数调用贵一到两个数量级</strong>。这也是内核提供 <strong>vDSO</strong>` 的原因：像 <code>gettimeofday</code>` 这类只读内核数据的调用，可以直接映射进用户态执行，省掉整趟模式切换。我们在第十五篇《Linux 专题：系统调用》展开。</span>

内核入口收到系统调用号后，第一步是查一张**系统调用表**确认编号合法，第二步逐个校验参数——比如 `buf` 指针是否指向用户可写的内存——第三步才真正执行文件系统操作。参数校验绝不是走过场：不校验的话，用户程序可以诱骗内核把内核内存当成缓冲区来写，这正是攻击者梦寐以求的漏洞。从陷阱指令到参数校验到执行再到返回的完整路径，我们会在第十五篇《系统调用原理》里画出整张图。

硬件中断同样会把 CPU 拖进内核态：磁盘完成 DMA 后发出中断，CPU 自动切到内核态执行中断处理程序。注意方向：**中断是从当前执行流「被拖进内核态」，但处理完返回时，硬件恢复的正是被打断的那个进程的上下文**——用户程序通常感觉不到自己被「打断」过。

**数值直觉：一次系统调用的代价**。x86-64 上 `syscall` 指令本身约 100 ns，但加上用户态→内核态的模式切换、参数校验、内核执行、返回，一次系统调用整体约 **1–10 µs**——比普通函数调用（约 1–10 ns）贵两到三个数量级。<span class="marginnote">这正是 vDSO、futex 用户态快速路径、io_uring 批量提交这些优化的动机：<strong>每省一次模式切换，就省掉约 1 µs 的固定成本</strong>。高频调用（读时钟、加锁、日志）是这类优化的富矿——第十五篇《Linux 专题：系统调用》会逐一展开。</span>

## 5 计时器：把失控的程序拉回来

模式与特权解决了「用户程序不能碰敏感指令」，但还差最后一个问题：**用户程序进入死循环怎么办？** 没有外力干预，CPU 会永远停在用户态的死循环里，操作系统连插手的机会都没有。

答案是**定时器（timer）**：操作系统在启动时设置定时器，每隔一个固定时间（时间片）产生一次定时器中断，把控制权**强制**交回内核。内核借此检查「当前进程是不是跑超时了」，超时就换下一个进程。这就是分时系统与时间片轮转的硬件基础——也是上一节历史里「分时」能成立的底层保障。以 Linux 为例，`CONFIG_HZ=250` 意味着定时器中断每秒触发 250 次（约 4 ms 一次），每次中断都可能触发一次调度判断——**这是时间片轮转的物理节拍**。

**数值直觉：一个时间片能做什么**。Linux 的 CFS 给每个进程的时间片约 4–6 ms（按 vruntime 加权，不是固定值）。在 1 GHz 的核上，一个时间片足够执行约 **400–600 万条指令**——够处理几百次函数调用、一次小规模的数据库查询。所以「分时」不是把 CPU 切成均等的毫秒块，而是给每个进程一段「够完成一小段有意义工作」的窗口；多进程轮流各跑一个窗口，用户的体验就是「所有程序同时都在跑」。<span class="marginnote">定时器中断是操作系统「抢回控制权」的最后手段。它必须属于<strong>特权指令</strong>范畴：如果用户程序能关闭定时器，那么整个系统就永远回不来了。所以「设置定时器」只能由内核完成，用户进程只能被动接受定时器中断。</span>

**辨析｜易错点：用户态程序不能「关闭中断」，只能「屏蔽本进程的信号」。** 屏蔽信号（如 `sigprocmask`）是进程自己的选择，影响的是信号递送；而 CPU 层面的「关中断」（x86 的 `cli` 指令）只有内核态可用，影响的是整个 CPU 对硬件中断的响应。两者一个是软件机制、一个是硬件特权，完全不是一回事。反过来说，内核态也并非处处「特权」——现代内核用 RCU、seqlock 等技巧让多数临界路径尽快完成，把特权停留时间压到最短，这同样是「特权最小化」思想在时间维度上的体现。

## 6 公式解析：双模式下的内存访问检查

双模式与内存保护是配套出场的。设模式位 $m$（0 = 内核态，1 = 用户态），进程的基址与界限分别为 $B$、$L$，那么 CPU 对地址 $A$ 的一次访问是否放行，可以写成：

$$\text{ok}(A) = \begin{cases} \text{true}, & m = 0 \\ \text{true}, & m = 1 \ \text{且}\ B \le A < B + L \\ \text{false}, & m = 1 \ \text{且}\ (A < B \ \text{或}\ A \ge B + L) \end{cases}$$

逐步拆解：

- **$m = 0$（内核态）**：放行一切地址访问。内核需要能访问全部内存——包括各用户进程的内存——才能替它们完成系统调用。
- **$B \le A < B + L$（用户态、命中合法区间）**：$A$ 落在本进程的内存区间内，放行。$B$ 是起始地址，$L$ 是区间长度，合法地址是一个**半开区间** $[B, B+L)$，即含左端、不含右端。
- **$A$ 越界（用户态、出界）**：拒绝访问，并触发一个**陷阱**把控制权交给内核——这就是「段错误（segmentation fault）」的硬件来源。内核或进程自己的信号处理程序再决定如何处置。

**重点：在用户态，一次越界访问不是被悄悄忽略，而是被硬件主动拦截并上交内核。** 模式位让 CPU 在每次访存前都能做一次检查——这就是「保护」的底层机制。理解了这条公式，你就理解了段错误为何存在，也理解了缓冲区溢出攻击为什么首先得突破模式与地址检查这两道防线——第十四篇《保护与安全》会从攻击者视角再讲一遍。

## 7 小结

- 双模式把程序分成**内核态**（特权）与**用户态**（受限），目的是相互保护。
- **模式位**是硬件状态：中断/陷阱时硬件自动切入内核态，返回时切回用户态。
- **特权指令**只能在内核态执行；「修改模式位」本身也是特权指令。
- x86 提供 **4 级保护环**；虚拟化新增 **VMX root / non-root（ring -1）**，是模式的再一次扩展。
- **系统调用**是用户态进入内核态的唯一合法通道，代价是模式切换。
- **定时器**保证内核能抢回失控的 CPU；「关中断」与「屏蔽信号」是两码事。
- 内存访问检查 $\text{ok}(A)$ 由模式位与基址/界限共同决定，越界访问触发陷阱。
