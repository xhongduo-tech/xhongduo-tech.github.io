## 为什么从伙伴系统开始

动态分区的首次/最佳/最坏适应都依赖「扫空闲链表」，合并碎片也要扫描。**伙伴系统（buddy system）**给出一种更优雅的分配策略：**内存块永远按 2 的幂次大小切分，分配时切成「刚好够」的最小 2 次幂块，释放时与它的「伙伴」合并**。它兼顾了分配速度与碎片控制，是 Linux 内核物理内存分配（页框分配器，page allocator）的基础。<span class="marginnote">回顾《动态分区》：扫链表找空闲块、合并碎片都要遍历。伙伴系统用「2 次幂分层 + 固定伙伴」把「找块」与「合并」都变成 O(1)/O(log n)——用规则换速度。</span>

## 1 伙伴系统的核心机制

**伙伴系统**：内存被组织成大小为 2 的幂次的空闲块链表（1KB、2KB、4KB、…、最大块）。分配与释放遵循严格的「切半/合并」规则。

**分配**：请求大小为 $s$ 的块 → 找最小的 $2^k \ge s$ 的空闲块：

1. 若该大小的链表有块，直接取一个。
2. 若没有，从**更大一级**（$2^{k+1}$）取一个块，**对半切成两个 $2^k$ 的伙伴块**，一个分配出去，一个挂回 $2^k$ 空闲链表。
3. 若更大一级也没有，继续向更大级别找，逐级切半。

**释放**：释放一个 $2^k$ 块 → 检查它的**伙伴**是否也空闲：

伙伴也空闲 → **合并成 $2^{k+1}$ 块**，再检查新块（$2^{k+1}$）的伙伴……
伙伴被占用 → 直接挂回 $2^k$ 链表。

**什么是伙伴**：两个大小相同、来自同一次「对半切」的相邻块互为伙伴。它们的地址关系是：**伙伴块与它相差恰好一个块大小**。判定伙伴的关键性质——**两个伙伴的地址在「块大小」这一位上互补**（一个是 0、另一个是 1）。<span class="marginnote">伙伴判定的巧妙：设块大小为 $2^k$，地址按 $2^k$ 对齐。两个相邻的 $2^k$ 块互为伙伴，当且仅当它们「拼起来」是恰好 $2^{k+1}$ 的块。硬件上只需异或一个位即可判断——这是伙伴系统 O(1) 合并的物理基础。</span>

### 伙伴地址的具体例子

设内存起始地址 0，1MB 内存按 2 次幂切分。地址 0x30000（192KB）处的一个 64KB 块：

- 它的伙伴是地址 0x20000（128KB）处的 64KB 块——两者地址相差恰好 64KB（一个块大小）。
- 在 64KB 这一位上：0x20000 的该位是 0，0x30000 的该位是 1——**互补即伙伴**。
- 合并后是 128KB 块（0x20000~0x3FFFF），其伙伴是 0x00000~0x1FFFF 的 128KB 块。

**判定实现**：伙伴地址 = 本块地址 异或 块大小（`buddy = addr ^ size`）——一条位运算，O(1) 完成。这就是伙伴系统「合并不扫描」的硬件依据。Linux 的实现以 `struct free_area` 管理每一级空闲链表（`/proc/buddyinfo` 可直接查看各级空闲块数量），分配时从「最低满足级」取块、缺则向上切；每级链表还按**迁移类型**（可移动 / 可回收 / 不可移动）分开维护，避免不可移动页长期困住大块。

## 2 示例：分配与合并的手工演练

设内存 1MB，按 2 的幂切分（最大块 1MB）。

**请求 70KB**：最小 $2^k \ge 70$KB 是 128KB。128KB 链表空 → 从 256KB 切：256KB → 两个 128KB，一个分配，一个挂回。

**请求 35KB**：最小 $2^k \ge 35$KB 是 64KB。64KB 链表空 → 从 128KB（刚挂回的）切：128KB → 两个 64KB，一个分配，一个挂回。

**释放 70KB 的块**（128KB 块）：伙伴（同批切出的另一个 128KB）空闲 → 合并回 256KB；再看 256KB 的伙伴（来自同批切出的）……若空闲继续合并。

**碎片控制**：伙伴系统把块整齐地按 2 次幂管理，分配是「切半」，释放是「伙伴合并」——不需要扫描整个空闲表找合并对象，**合并总是发生在「地址相邻 + 大小相同 + 来自同一父块」的伙伴之间**。

**公式解析：伙伴系统的「内部碎片上界」**

请求大小 $s$ 会得到最小 $2^k \ge s$ 的块，最坏浪费：

$$\text{最大内部碎片} = 2^k - s < s$$

- **$2^k$**：分配的块大小（最小满足的 2 次幂）。
- **$s$**：实际请求大小。
- 因为 $2^k$ 是「最小的 ≥ s 的 2 次幂」，$2^k < 2s$，所以碎片 < $s$——**最坏情况下浪费接近请求大小的一半**。

**直觉**：请求 70KB 分到 128KB，浪费 58KB（45%）。伙伴系统的内部碎片比分页严重，但远小于固定分区——它用「按 2 次幂取整」的代价换来了 O(1) 的合并效率。Linux 内核对此的缓解：把不同用途（DMA、普通、高内存）分开，并用 slab/slub 分配器做细粒度复用。

## 3 伙伴系统的优缺点

**优点**：

- **分配/释放快**：切半与合并都是 O(log n)，无需扫描链表。
- **合并高效**：伙伴规则让合并只检查「一个地址」即可判定。
- **外部碎片小**：2 次幂的整齐结构让碎片最小化（不是零）。

**缺点**：

- **内部碎片**：按 2 次幂取整，请求 70KB 拿 128KB，浪费。
- **切块累积**：反复分配释放会产生大量不同大小的碎片块，管理复杂。
- 2 次幂大小限制：不能按任意大小分配。

**辨析｜易错点：** 「伙伴系统没有碎片」是误解。**伙伴系统仍有内部碎片（2 次幂取整）与一定外部碎片**，只是它把两者都控制得很好。它在内核里的真正搭档是 **slab 分配器**：伙伴系统管「页框级别的块」，slab 管「页框内部的细碎对象」（结构体、缓存）——分层配合才完整。<span class="marginnote">Linux 的内存分配是「伙伴系统 + slab/slub」两层：伙伴系统按 2 次幂分配物理页，slab 把一页切给同类型小对象反复复用（如 `task_struct`、`dentry`）。理解伙伴系统，就理解了一半的内核物理内存管理。</span>

### slab 分配器如何补齐伙伴系统

伙伴系统的粒度是「2 次幂的页框」，对内核里大量小对象（`task_struct`、`dentry`、`inode`）太浪费——slab 分配器弥补：

- **slab（缓存）**：为每种对象类型维护一个缓存，缓存由若干页组成；对象分配/释放从缓存中快速取放。
- **对象复用**：对象释放后留在缓存里，下次分配直接复用——避免反复分配/释放页框。
- **初始化开销**：首次创建对象才调用构造函数，复用免构造。

**典型流程**：内核要 `task_struct` → 查 slab 缓存，有则取现成对象，无则从伙伴系统申请新页补充缓存。**伙伴系统管「页」，slab 管「页里的对象」——大小两个尺度的分工**，这是 Linux 内存分配的精髓。此外页框分配器还按**内存域（zone）**维护多套伙伴链表——ZONE_DMA、ZONE_NORMAL 等各管一片，保证 DMA 设备能分配到低地址物理内存。

**伙伴系统的生态位**：在伙伴系统之上，内核还有 vmalloc（非连续页的虚拟地址分配）与 kmalloc（slab 上的小对象分配）——伙伴系统是它们的「底层供应商」：**任何物理页都要先经伙伴系统取得，再被上层细化成具体用途**。理解这条「伙伴管页、上层细化」的流水线，内核物理内存管理的全貌就清晰了。

## 4 核心对比表：伙伴系统 vs 动态分区

| 维度 | 动态分区（适应算法） | 伙伴系统 |
| --- | --- | --- |
| 块大小 | 任意 | **2 的幂次** |
| 查找 | 扫空闲链表 | 按级别取块，缺则切半 |
| 合并 | 扫描相邻块 | 只查固定伙伴 |
| 分配复杂度 | O(n) | O(log n) |
| 内部碎片 | 无（精确匹配） | 有（2 次幂取整） |
| 外部碎片 | 有 | 较小 |

## 5 小结

- **伙伴系统**：内存按 2 次幂切块，分配取「最小够用」、释放与固定伙伴合并。
- 伙伴判定：同大小、相邻、来自同一次切半；硬件上 `buddy = addr ^ size` 一条位运算 O(1) 判定。
- 分配：找最小够用 $2^k$ 块，缺则从大一级切半逐级切——O(log n)；释放：伙伴空闲则合并再查上一级。
- 最大内部碎片 < 请求大小一半（$2^k - s < s$）；请求 70KB 拿 128KB 浪费 45%。
- 优点：分配/释放 O(log n)、合并无需扫描；缺点：2 次幂取整的内部碎片与大小限制。
- **slab 分配器**为每种对象维护缓存、释放后复用——伙伴系统管「页」、slab 管「页内对象」，两尺度分工。
- Linux 用「伙伴系统（页框级）+ slab（对象级）」两层配合，page allocator 以伙伴系统为核心。
