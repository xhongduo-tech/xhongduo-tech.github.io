## 为什么从线程模型开始

上一节我们定义了线程，但留了一个关键问题：**程序员用线程库（如 pthread）创建的线程，操作系统内核看得见吗？** 答案是「不一定」。用户态创建的线程与内核管理的线程之间需要建立映射，而这个映射方式——**多线程模型**——决定了系统的并发能力、阻塞行为与可移植性。<span class="marginnote">线程有两个世界：用户态（库管理的线程）与内核态（内核调度的线程）。线程模型就是这两个世界之间的「对应关系」，它决定了「用户线程阻塞时，内核知不知道」。</span>

先看一个具体场景把问题钉死：一个网络服务器进程为了处理并发请求，用线程库开了 **8 个用户线程**。这 8 个线程在内核眼里是什么？如果内核只看到「1 个可调度的线程」，那就是多对一；看到「8 个」，就是一对一；看到「4 个」（少于 8），就是多对多。**同一个进程、同样的 8 个线程，仅仅因为线程库与内核的配合方式不同，系统的并发上限就差出数量级。** 这正是本节的三个模型要回答的问题。

还有一个容易忽略的观察角度：**「多」与「一」分别指谁**。映射关系左边的 M 是用户线程（库管的、内核看不见的），右边的 N 是内核线程（内核管的）。一个模型叫「多对一」，说的是「许多用户线程共同依附于一个内核线程」，而不是反过来。把主宾关系记反，后面读教材就全乱了。

## 1 多对一模型（Many-to-One）

**多对一模型**：多个用户级线程映射到**一个**内核线程上。线程管理全在用户态库完成，内核只看到「一个线程」。

创建、调度、切换都在用户态，**非常快**——无需陷入内核。
但**一个用户线程阻塞（如系统调用等待 I/O），整个进程的所有线程全部阻塞**，因为内核眼里只有一个线程，它阻塞了进程就停了。
且多核无益：内核只调度一个线程，无法让多个用户线程真正并行。

**结论**：多对一模型几乎绝迹（曾用于 Green Threads 等），只在特定的库级实现里残留。<span class="marginnote">许多语言早期的「协程/绿线程」（Green Threads）就是多对一模型：轻快但一阻塞全停，所以 Go 的 goroutine、Erlang 进程都转向了内核线程支持或运行时接管。多对一的历史价值是提醒我们「用户态调度」的天花板。</span>

用一个具体数字把多对一的致命弱点钉死。假设这个服务器进程的 8 个线程要并发读 8 个不同的网络连接，而其中第 3 个连接恰好慢（TCP 重传，要等几百毫秒）。多对一下，第 3 个线程发起的 `read` 陷入内核，内核发现「唯一的那个线程」要等 I/O，于是把它挂起——**进程内其余 7 个就绪线程全部失去执行机会**，因为它们都在用户态的同一个就绪队列里等这一个内核线程。8 个请求里只慢一个，结果 8 个全部卡住。这就是多对一「一阻塞、全阻塞」的具象化。

为什么会出现这种「内核只认一个线程」的实现？因为线程管理完全在用户态库手里：库用一个「运行时」（runtime）统一调度所有用户线程，切换只涉及保存/恢复寄存器与栈指针，**不经过系统调用**。代价就是内核完全不知道「还有 7 个线程等着」，阻塞发生时内核只能按「整个进程」来处理——它眼里根本没有「第 3 个线程」这个概念。

## 2 一对一模型（One-to-One）

**一对一模型**：每个用户线程映射到一个内核线程。

一个线程阻塞**不影响**其他线程——每个用户线程有独立的内核线程承载，阻塞只停自己。
支持真正的多核并行。
代价：**每创建一个用户线程就要创建一个内核线程**，内核线程有内核态开销（内核栈、调度），线程数量受系统限制，创建过多会拖垮系统。

Linux 的 **NPTL（Native POSIX Thread Library）** 采用一对一模型——`pthread_create` 内部通过 `clone` 系统调用直接创建一个内核线程。这也意味着 Linux 上「线程数」受内核资源约束，`ulimit -u`（`/proc/sys/kernel/threads-max`）控制进程/线程数量上限。<span class="marginnote">一对一模型让「一个线程一个阻塞点」成为可能，但线程创建成本上升。这正是「线程池」要解决的问题——预先建好固定数量的线程复用，而不是每次任务来临时现建（见第四篇《隐式线程》）。</span>

一对一的代价有多具体？**内核线程每次创建要分配独立的内核栈（Linux 默认约 8 MB 虚拟地址空间，实际物理按需分配）、tls 结构、调度实体，且创建要陷入内核**——实测 Linux 上 `pthread_create` 一次约需 2–10 微秒，而用户态线程切换只需几十纳秒。更关键的约束是数量：`pthread` 默认栈 8 MB 意味着 10 万个线程就要 800 GB 虚拟地址空间，还没算内核资源。所以一对一模型下，「开几千个线程」很常见，但「开几十万个」就不现实——那是用户级线程的地盘。

## 3 多对多模型（Many-to-Many）与两级模型

**多对多模型**：M 个用户线程映射到 N 个内核线程上（M > N）。用户线程由库调度，内核线程由内核调度；库把一个用户线程「贴」到某个空闲内核线程上执行。

综合两头的优点：**阻塞只影响被阻塞的那个内核线程**，其余用户线程可换到别的内核线程继续跑；线程创建仍是用户态级别的，轻快。
多核并行能力受 N 限制（N 个内核线程最多并行 N 路）。

**两级模型（two-level model）**是多对多的变体：允许某些用户线程**独占**绑定到某个内核线程（相当于临时一对一），其余走多对多。Solaris 早期的实现就用两级模型。

两级模型的动机很实用：**让少数「关键线程」享受一对一的好处，其余普通线程享受多对多的轻快**。比如一个 GUI 进程里，UI 渲染线程对延迟极敏感，可以独占一个内核线程保证不被换走；而后台的计算线程则几十个共享几个内核线程，够用就好。

多对多的调度发生在**两级**：用户态库维护自己的就绪队列，把 M 个用户线程分派到 N 个内核线程上；内核只负责调度 N 个内核线程到 N 个 CPU 核。读者不妨做一个思想实验：还是那 8 个线程、4 个内核线程（M:N = 8:4）。第 3 个线程阻塞时，库里的调度器**立刻**把队列中下一个就绪的用户线程「贴」到第 3 个占用的那个内核线程上——整个过程不经过内核，耗时只是用户态的一次上下文切换。8 个请求里慢一个，损失的只是 4 路并行中的一路，其余 7 个请求照常推进。<span class="marginnote">这个「阻塞后立刻在用户态换人」的动作，正是用户级线程的杀手锏：内核只感知 N 个线程，N 个线程里谁在跑、谁换了人，内核一概不知。</span>

**今天的现实版图**：Windows 的线程实现是一对一（每个用户线程直接映射内核线程）；Linux 的 NPTL 是一对一；macOS/Darwin 用 Mach 线程也是一对一。也就是说，**主流操作系统实际上都选了「一对一」**——多对多理论上更美，但实现复杂（库与内核的协作、调度优先级映射都难调），Linux、Windows 都曾尝试过又放弃，最终只保留在少数运行时（Go、Java 虚拟线程的调度）里。这提醒我们：**教材讲三种模型是给你「设计空间」，而工程选型往往被兼容性与实现成本推着走。**<span class="marginnote">Java 19 引入的虚拟线程（Virtual Threads）就是多对多思想的现代复兴：百万级用户线程由 JVM 调度到少量平台线程上，阻塞时 JVM 挂起虚拟线程、释放平台线程——本质是本节 M:N 模型在 JVM 里的再实现。</span>

## 4 核心对比表：三种模型

| 维度 | 多对一 | 一对一 | 多对多 |
| --- | --- | --- | --- |
| 映射关系 | M : 1 | 1 : 1 | M : N |
| 用户线程创建 | 最快（纯用户态） | 慢（要建内核线程） | 快（用户态为主） |
| 一个线程阻塞 | **全部阻塞** | 仅自己阻塞 | 仅所在内核线程阻塞 |
| 多核并行 | 不可能 | 完全支持 | 支持（受 N 限制） |
| 代表系统 | 早期 Green Threads | Linux NPTL、Windows | Solaris（早期）、ThreadFork |

**辨析｜易错点：** 「线程模型可以随便选」是误解。模型由**线程库 + 内核的配合**决定，不是程序员写代码能选的：Linux 的 pthread 固定一对一，你选不了多对一。但**用户级线程（协程）可以由用户程序自己实现**——Go 的 goroutine 本质是「语言运行时的用户级线程 + M:N 映射到内核线程」，所以 goroutine 极轻、可上百万个。

另一个易错点：**「用户级线程」与「内核级线程」是两种实现层次，不是两种语言特性**。任何语言都可以用库实现用户级线程（没有内核线程的轻量调度），但只有依托内核线程才能享受多核并行与独立阻塞。<span class="marginnote">这个区分是理解「为什么 Go 能开 100 万 goroutine 而 C 的 pthread 开 1 万就吃力」的钥匙：goroutine 是用户级 + 多对多，pthread 是内核级 + 一对一。用户级省的是「内核线程」这层资源。</span>

## 5 数值算例：三种模型的调度开销

把三个模型的代价摆在同一张数字表上，比文字对比更直观。以下是一个进程 8 个用户线程、单核受测的典型量级（不同系统差异较大，关注量级差而非精确值）：

| 指标 | 多对一 | 一对一 | 多对多 |
| --- | --- | --- | --- |
| 线程切换开销 | 约 10–100 ns（纯用户态） | 约 0.5–10 µs（陷入内核） | 用户态切换时同多对一 |
| 创建 1000 个线程 | 很快（不建内核线程） | 慢（建 1000 个内核线程） | 快（只建少数内核线程） |
| 1 个线程阻塞 | 8 个全停 | 只停 1 个 | 停所在内核线程，库内换人 |
| 8 线程 × 4 核并行 | 不可能 | 8 路 | 最多 4 路 |
| 线程数上限 | 几乎不受内核限制 | 受内核资源与地址空间限制 | 用户级可到十万级 |

**读表方法**：多对一赢在「切换快、创建快」，输在「一阻塞全停、不能并行」；一对一赢在「独立阻塞、满并行」，输在「每个线程都重」；多对多试图在两行之间取一个平衡点——用少量内核线程承载海量用户线程。

**辨析｜易错点：** 「goroutine 是一对一模型」是常见误读。Go 的 goroutine 由运行时调度器（GMP 模型）管理，初始栈仅约 2 KB、可动态增长，一个进程通常只创建与 CPU 核数相当的**内核线程**（默认 `GOMAXPROCS`），把上百万 goroutine 映射到这些内核线程上执行——这是典型的多对多（M:N）实现，不是一对一。**「线程是内核级还是用户级」要看它在哪一层调度，而不看它的语言。**<span class="marginnote">GMP 里 G 是 goroutine，M 是内核线程，P 是逻辑处理器。调度器把 G 分配到 P 上，P 再交给 M 执行——P 的数量就是并行的天花板，这个设计与本节的 M:N 模型一脉相承，也是第三级《Go 语言编程》里并发编程的地基。</span>

## 6 术语速查表

| 术语 | 含义 | 一句话记忆 |
| --- | --- | --- |
| 用户级线程 | 由线程库在用户态管理、内核不可见 | 内核不知道它存在 |
| 内核级线程 | 由内核调度、有独立内核栈 | 内核调度的最小单位 |
| 多对一模型 | M 个用户线程 → 1 个内核线程 | 轻快，但一阻塞全停 |
| 一对一模型 | 1 个用户线程 → 1 个内核线程 | 独立阻塞，但每个线程都重 |
| 多对多模型 | M 个用户线程 → N 个内核线程（M>N） | 折中方案 |
| 两级模型 | 多对多 + 部分线程独占绑定 | 给关键线程开小灶 |
| NPTL | Linux 的原生 POSIX 线程库，一对一 | Linux 上 pthread 的实现 |
| GMP | Go 运行时调度模型（G/M/P） | goroutine 的多对多实现 |

## 7 小结

- **多对一**：M 个用户线程 → 1 个内核线程，最轻但一阻塞全停、无法并行，几近淘汰。
- **一对一**：1 用户线程 → 1 内核线程，独立阻塞、支持并行，但有内核开销，Linux NPTL 采用。
- **多对多**：M 用户线程 → N 内核线程，兼得轻快与部分并行，是理论最优解。
- 两级模型 = 多对多 + 独占绑定。
- **用户级线程 vs 内核级线程**是理解 Go goroutine、协程与 pthread 差别的关键。
- **判读模型先看「谁在调度」**：内核能调度的是内核级线程，用户态库调度的是用户级线程，两者对应关系就是线程模型。
- **工程现实**：主流操作系统（Linux、Windows、macOS）实际都选了一对一；多对多的现代复兴在 Go 的 GMP 与 Java 虚拟线程里。
- **内核线程数 = 并行上限**：无论用户态开多少线程，能同时跑的不过内核线程数（及 CPU 核数），理解这个天花板就不会被「线程数虚高」欺骗。

在下一节，我们来认识程序员每天实际调用的线程接口——**线程库：Pthreads、Java 线程与 Windows 线程**。那里我们将看到：无论底层是哪种模型，pthread 的 API 都尽量对上层隐藏映射细节——但模型决定了「你的程序能开多少并发」，这个天花板你最好在写第一行多线程代码之前就想明白。
