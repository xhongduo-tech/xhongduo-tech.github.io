## 为什么从 FCFS 开始

调度算法家族里，**先来先服务（FCFS）**是最自然、最没有野心的一个——先到先服务，就像银行柜台排队。它简单到几乎不需要解释，但正是这份简单暴露了调度的核心难题，也给了我们理解后续所有算法的「基准线」。<span class="marginnote">回顾《调度基本概念》：FCFS 属于<strong>非抢占式</strong>调度——进程一旦上 CPU，除非自己让出（等 I/O 或结束），不会被换下。它的排队哲学直接继承自「先来先服务」的队列模型。</span>

## 1 FCFS 的定义与实现

**先来先服务（FCFS, First-Come, First-Served）**：就绪队列中的进程按到达顺序排队，调度器每次从队头取一个进程执行，直到该进程**自动让出 CPU（阻塞或终止）**才轮到下一个。

实现极其简单：就绪队列就是一个 FIFO 队列。**调度器 = 取队头，进程 = 用到底**。

```text
就绪队列（FIFO）：[P1, P2, P3, …]   // 按到达顺序入队

while (就绪队列非空) {
    进程 = 队头出队;      // 取队头
    进程.run();          // 用到底（直到阻塞或终止）
}
```

**关键性质**：FCFS 是**非抢占的**——没有时间片，没有优先级，不打断正在运行的进程。

## 2 工作示例：用数字看 FCFS 的公平与不幸

假设三个进程依次到达，各需 CPU 时间如下：

| 进程 | 到达时间 | CPU 突发 |
| --- | --- | --- |
| P1 | 0 | 24 |
| P2 | 1 | 3 |
| P3 | 2 | 3 |

FCFS 的执行顺序是 P1 → P2 → P3（按到达序），甘特图：

```text
甘特图（P1 → P2 → P3）：
|────── P1（24）──────|─ P2（3）─|─ P3（3）─|
0                     24         27         30
```

计算等待时间（进入就绪队列到首次上 CPU 的时间）：

P1：等待 0
P2：等待 24 - 1 = 23
P3：等待 24 + 3 - 2 = 25

平均等待时间 = (0 + 23 + 25) / 3 = **16**。

现在把进程顺序换一下，变成 P2、P3、P1 先到（突发短的先到）：

```text
甘特图（P2 → P3 → P1，短突发先到）：
|─ P2（3）─|─ P3（3）─|────── P1（24）──────|
0          3          6                     30
```

平均等待时间 = (0 + 0 + 6) / 3 = **2**。

**同一个任务集，仅仅因为到达顺序不同，平均等待时间从 16 降到 2**——FCFS 对「长突发先到」毫无防御力。这就是著名的**护航效应（convoy effect）**：一个长进程霸占 CPU，后面所有短进程全部排队干等，整个系统的响应性被拖垮。<span class="marginnote">护航效应的现实版：一个人在银行办一笔大额复杂业务（长突发），后面买咖啡、交话费的人（短突发）全部排队等。FCFS 让 CPU 密集型进程像「慢速船」一样拖着整支船队，I/O 密集的交互程序体验极差。</span>

## 3 FCFS 的优缺点

**优点**：

- **实现最简单**，FIFO 队列即全部逻辑。
- **公平**：按到达序，没有人插队。
- **无饥饿**：每个进程最终都会被服务到。

**缺点**：

- **护航效应**：长突发进程阻塞后续所有短进程，平均等待时间高。
- **对交互不友好**：一个 CPU 密集进程可能让所有交互程序等上几分钟。
- **非抢占**：即使有更高优先级的新进程到达，也不能打断当前进程。

## 4 公式解析：周转时间与等待时间

调度指标里，两个最基本的时间概念需要分清楚：

**周转时间（turnaround time）**：从进程到达，到进程完成，总共花的时间。

$$
T_{\text{turnaround}} = T_{\text{completion}} - T_{\text{arrival}}
$$

**等待时间（waiting time）**：进程在就绪队列里排队的时间，不含执行时间。对于非抢占的 FCFS，它等于周转时间减去 CPU 突发：

$$
T_{\text{wait}} = T_{\text{turnaround}} - T_{\text{burst}}
$$

回到上一节的第一个例子（P1/P2/P3，到达序），把三项指标补全：

| 进程 | 到达 | 突发 | 完成 | 周转 | 等待 |
| --- | --- | --- | --- | --- | --- |
| P1 | 0 | 24 | 24 | 24 | 0 |
| P2 | 1 | 3 | 27 | 26 | 23 |
| P3 | 2 | 3 | 30 | 28 | 25 |

平均周转时间 = (24 + 26 + 28) / 3 = **26**，平均等待时间 = 16，两者之差 (24+3+3)/3 = 10 正是平均突发时间。<span class="marginnote">平均周转时间 − 平均等待时间 = 平均突发时间，这个恒等式在任何调度算法下都成立（只要进程的执行时间不因调度而改变）。它常用来交叉验证指标是否算错。</span>

再看把到达顺序换成 P2、P3、P1（到达时间相应变为 0、1、2）的第二例：完成时刻分别为 3、6、30，周转时间为 3、5、28，平均 **12**；等待时间 0、2、4，平均 **2**。<span class="marginnote">FCFS 在排队论里就是经典的 M/M/1/FCFS 模型——若到达服从泊松过程、服务时间服从指数分布，平均等待时间有闭式解 $W = \frac{\rho}{\mu - \lambda}$（$\rho$ 为利用率）。调度算法与排队论共享同一套语言，这条连线见第三级《概率论》专题。</span>同一套任务，仅顺序不同，平均等待从 16 掉到 2、平均周转从 26 掉到 12——**让短突发先到，就是给系统打了一针「排障针」**。

## 5 核心对比表：FCFS 的评价定位

用《调度基本概念》的准则给 FCFS 打分：

| 准则 | FCFS 表现 | 原因 |
| --- | --- | --- |
| CPU 利用率 | 高 | 进程用到底，切换少 |
| 吞吐量 | 中 | 长进程拖后腿 |
| 平均等待时间 | 差 | 护航效应 |
| 响应时间 | 差 | 短进程可能等很久 |
| 公平性 | 好 | 严格先来后到 |
| 实现复杂度 | 最低 | FIFO 队列 |

**辨析｜易错点：** 「FCFS 是公平的，所以它好」是片面看法。FCFS 的「公平」是**时间上的公平**（按到达序），不是**体验上的公平**（人人响应快）。对交互系统来说，让短任务等长任务是最大的不公。**公平的形态有多种——轮转的公平、短任务的公平、优先级的公平——FCFS 只是最朴素的一种**，这也是后续算法存在的理由。

## 6 小结

- **FCFS**：按到达顺序排队，进程用到底才让出，**非抢占**、FIFO 队列实现。
- **护航效应**：长突发进程让后续短进程集体等待，平均等待时间飙升。
- 同一任务集因到达顺序不同，平均等待时间可从 16 降到 2——顺序敏感。
- 周转时间 $T_{\text{completion}} - T_{\text{arrival}}$，等待时间 $T_{\text{turnaround}} - T_{\text{burst}}$，两者之差恒等于平均突发时间。
- 优点：简单、公平、无饥饿；缺点：护航效应、交互体验差。
- FCFS 是调度的「基准线」，后续算法都在弥补它的短处。
