## 为什么从 Reactor 开始

epoll 给了「多路复用」的原语，但「怎么用」需要一套**编程模式**——**Reactor 模式**。它是事件驱动编程的核心骨架：**一个线程循环等待事件（epoll_wait），把事件分派给对应的处理器**。nginx、Redis、Netty 全用这个模式支撑高并发。这一节是第十七篇 epoll 专题的「应用层」。<span class="marginnote">回顾《epoll API》的事件驱动循环：epoll_wait → 遍历就绪事件 → 处理。Reactor 就是这个循环的<strong>系统化封装</strong>——它把「事件到来 → 找到对应处理器 → 执行」组织成可扩展的模式。<strong>多路复用是「机制」，Reactor 是「模式」。</strong></span>

## 1 传统 vs 事件驱动：一个连接一个线程的困境

**传统阻塞模型**（每连接一线程）：

- 每个连接一个线程，线程阻塞在 read 上（回顾《I/O 模型》）。
- **1 万连接 = 1 万线程**——线程开销巨大（内存、上下文切换），并发上限低。

**事件驱动模型**（Reactor）：

- **一个线程**用 epoll 监视所有连接。
- 事件（可读/可写）到来 → 分派给对应处理器 → 处理完继续等下一个事件。
- **1 万连接 = 1 个线程 + 1 万个 fd**——线程开销与连接数无关。

**核心转变**：**从「每个连接一个执行流」到「所有连接共享一个执行流」**——用「事件循环」替代「线程阻塞」。

## 2 Reactor 模式的结构

**Reactor 模式**的三大组件：

- **Reactor（反应堆）**：事件循环——epoll_wait 等待事件，把事件**分派**给对应 handler。
- **Handler（处理器）**：处理特定事件的回调——每个连接/事件有自己的 handler。
- **Acceptor（接受器）**：专门处理「新连接到来」事件的 handler——accept 新连接并注册。

**工作流程**：

epoll_wait 等待事件 → 有新连接？ → Acceptor 接收并注册 handler
                  ↘ 可读/可写？ → 分派给对应 handler 处理

**代码骨架（概念）**：

```c
/* Reactor 事件循环骨架 */
while (1) {
    int n = epoll_wait(epfd, events, MAXEVENTS, -1);   /* 等待事件 */
    for (int i = 0; i < n; i++) {
        if (events[i].data.fd == listen_fd) {
            accept_new_conn();    /* Acceptor：接收新连接并注册 handler */
        } else {
            dispatch(events[i]);  /* 分派给该连接对应的 handler 处理 */
        }
    }
}
```

## 3 事件驱动的关键：状态机与非阻塞

Reactor 里的每个连接要能「处理一半停住，下次事件再来继续」——因为一个线程要服务所有连接，**不能在某个连接上阻塞**。

**非阻塞 + 状态机**：

- 每个连接用**非阻塞 fd**（回顾《LT/ET》：非阻塞是事件驱动的前提）。
- 每个连接维护**状态**（正在读哪、写哪、解析到哪）——事件到来时**从上次状态继续**。
- **「一个连接的处理」被拆成「多个事件驱动的步骤」**——这就是**状态机（state machine）**。

**公式解析：事件驱动 vs 线程的并发度**

设 $C$ 个连接，线程数 $T$：

$$\text{阻塞模型：} T = C \quad \text{（每连接一线程）}$$

$$\text{事件驱动：} T = 1\text{~几} \quad \text{（连接数与线程无关）}$$

- 阻塞：线程数 = 连接数，1 万连接要 1 万线程。
- 事件驱动：**几个线程服务所有连接**——线程数固定（如 CPU 核数），连接数只受 fd 上限限制。

**直觉**：**事件驱动把「并发度」从「线程数」转移到「事件数」**——线程是昂贵的资源，事件是廉价的。**「用有限的线程处理无限的事件」是事件驱动压倒线程模型的根本。**

**辨析｜易错点：** 「事件驱动 = 不用线程」是误解。**Reactor 通常仍然多线程**——主 Reactor 收事件，worker 线程池处理耗时逻辑（避免阻塞主循环）。**「单线程事件循环」适合 CPU 快、I/O 多的场景（Redis）；「多 Reactor + 线程池」适合复杂处理（Netty）。** 事件驱动改的是「每个连接不再占一个线程」，不是「完全不用线程」。

## 4 Reactor 的变体：多线程化

| 变体 | 结构 | 适用 |
| --- | --- | --- |
| 单 Reactor | 一个线程收事件 + 处理 | 简单、I/O 密集（Redis） |
| 主从 Reactor | 主 Reactor 收连接，从 Reactor 处理 | 大型服务 |
| Reactor + 线程池 | 事件循环 + 业务线程池 | 计算密集（Netty） |

**Netty 的多线程 Reactor**：主 Reactor 接受连接，多个子 Reactor 各自 epoll 处理已建立连接的 I/O，业务逻辑放线程池——**「接受」与「处理」分离，避免主循环被拖慢**。

## 5 核心对比表：阻塞模型 vs Reactor

| 维度 | 每连接一线程 | Reactor 事件驱动 |
| --- | --- | --- |
| 线程数 | = 连接数 | 固定（几个） |
| 连接数上限 | 受线程资源限制 | 受 fd 上限限制 |
| 阻塞 | 线程阻塞在 read | **非阻塞 + 状态机** |
| 编程模型 | 同步线性代码 | 事件回调 |
| 典型 | 简单服务 | nginx、Redis、Netty |

| 术语 | 含义 | 一句话记忆 |

## 7 小结

- **Reactor 模式**：一个事件循环（epoll）+ 事件分派 + 处理器——单线程扛高并发。
- 三大组件：**Reactor（事件循环）、Handler（处理器）、Acceptor（接连接）**。
- 事件驱动把**并发度从「线程数」转移到「事件数」**——线程固定、事件无限。
- 关键纪律：**非阻塞 fd + 状态机**（处理可中断、可继续）。
- 变体：单 Reactor（Redis）、主从 Reactor、Reactor + 线程池（Netty）。
