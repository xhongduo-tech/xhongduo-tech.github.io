## 为什么从套接字与 RPC 开始

前面四种 IPC 都默认「同一台机器」。但现代系统的协作早就跨出了单机：浏览器请求云服务器、微服务互相调用、容器跨节点通信。这一节把 IPC 推向「远程化」——**套接字（socket）**让通信与「对方在哪台机器」解耦，**RPC** 再把「网络通信」伪装成「函数调用」。这是从操作系统通往计算机网络与分布式系统的桥。<span class="marginnote">套接字是「进程间通信」与「网络通信」的交叉点：本机两个进程也能用套接字通信（Unix domain socket），它的抽象统一了本地与远程——这正是「一切皆文件」思想在网络领域的延伸。</span>

RPC 的「伪装成本地调用」也带出了一个分布式系统最深的难题：**网络是不可靠的**——消息可能丢失、重复、乱序，而本地调用不会。RPC 框架（gRPC 等）处理了「传输」的可靠性，但「业务语义」的幂等、超时、补偿仍要应用自己设计。**RPC 解决了「怎么传」，没解决「传了之后怎么办」**。

## 1 客户机-服务器模型

**客户机-服务器模型（client-server model）**：一种协作模式，**服务器**是提供服务的进程，持续监听请求；**客户机**是请求服务的进程，发起调用。几乎所有网络服务（Web、数据库、消息队列）都采用这个模型。

角色分工：

**服务器**：创建套接字 → 绑定地址端口 → 监听 → 接受连接 → 处理请求 → 回复。被动等待，通常长期运行。
**客户机**：创建套接字 → 连接服务器 → 发送请求 → 接收响应。主动发起，通常用完即走。

这个模型的好处是**职责清晰、易于扩展**：服务器可以开多线程/多进程并发处理多个客户（见第四篇《线程》）；客户机互不感知、互不影响。

## 2 套接字（Socket）：通信的端点

**套接字（socket）**：网络通信的端点抽象。一对套接字（客户端一个、服务器端一个）构成一条逻辑通道，数据从一端写入、从另一端读出。套接字由「IP 地址 + 端口号」唯一标识通信的双方。

套接字按类型分两类：

**流式套接字（SOCK_STREAM）**：基于 TCP，面向连接、可靠、字节流。
**数据报套接字（SOCK_DGRAM）**：基于 UDP，无连接、不可靠、有消息边界。

一个典型的 TCP 服务器骨架（概念示意）：

```c
int s = socket(AF_INET, SOCK_STREAM, 0);   /* 创建流式套接字 */
bind(s, &addr, sizeof(addr));               /* 绑定地址与端口 */
listen(s, 128);                             /* 进入监听 */
int c = accept(s, NULL, NULL);              /* 阻塞等待客户端连接 */
```

**辨析｜易错点：** 「套接字 = 网络」是常见窄化理解。套接字可以走网络（`AF_INET`），也可以**不走网络**——`AF_UNIX`（Unix domain socket）让同一台机器的进程通过文件系统路径通信，速度比 TCP 回环快得多，且是 Docker、nginx、数据库本地访问的常用通道。<span class="marginnote">Unix domain socket 常驻「/var/run」或「/tmp」下，<code>ls -l</code>` 看到类型为 <code>s</code>` 的文件。它是「本机高效 IPC」与「网络 IPC」的桥梁——同一个 API，两种运输方式。</span>

### 连接的生命周期（TCP）

流式套接字的连接不是凭空出现，它经历「建立 → 通信 → 关闭」三阶段：

1. **建立**：三次握手（SYN → SYN-ACK → ACK）确认双方就绪。
2. **通信**：双向字节流，可靠有序传输。
3. **关闭**：四次挥手释放资源。

**对操作系统而言**：每个连接都占用资源（文件描述符、内核缓冲区）——**连接是「对象」，需要创建与销毁**。这就是为什么高并发服务器要管理连接池、复用连接（HTTP keep-alive、gRPC 长连接）——**建立连接的代价远高于传输几个字节**。

### 本机进程也用套接字：Unix domain socket

- **数据不经过网络栈**：不走 TCP/IP 协议栈、不涉及 IP 端口，速度比 TCP 回环快数倍。
- **权限用文件系统控制**：socket 文件有属主与权限，天然复用「一切皆文件」的保护模型。
- **典型应用**：Docker 的 socket、nginx 与后端进程的本地通信、数据库本地连接。

**一句话**：Unix domain socket 是「本机高效 IPC」与「网络 IPC」之间的桥——同一个 socket API，本地用文件路径、远程用 IP + 端口。**理解它，就理解了「一切皆文件」与「网络抽象」是如何统一的**。

## 3 RPC：把网络调用伪装成函数调用

**远程过程调用（RPC, Remote Procedure Call）**：一种让程序像调用本地函数一样调用远程机器上的函数的机制。程序员写 `add(1, 2)` 这样的函数调用，实际这个函数的实现在另一台机器上。

一次 RPC 的旅程（传统 RPC 模型）：

1. **客户端**调用本地桩（stub）函数 `add(1, 2)`。
2. 桩把参数**序列化（marshalling）**成字节流（参数打包成能传输的格式）。
3. 通过网络把请求发给**服务器端的桩**。
4. 服务器桩**反序列化**参数，调用真正的 `add` 函数实现。
5. 返回值同样序列化、回传、反序列化，回到客户端调用点。

所以 RPC 的本质是：**本地桩 + 网络传输 + 序列化**。**序列化**是把内存中的数据结构变成字节流（JSON、Protobuf、gRPC 的二进制编码等），是 RPC 性能的关键。<span class="marginnote">现代 RPC 代表是 gRPC（Google 出品，基于 HTTP/2 + Protobuf）与 Thrift。容器与微服务架构里，服务间调用几乎全是 gRPC——你会在大模型部署、分布式系统专题反复碰到它。</span>

**RPC 的经典陷阱**：

- **延迟不可预知**：本地调用微秒级，远程调用毫秒级甚至更糟，且可能超时。
- **失败语义不同**：本地函数要么成功要么失败，远程调用可能「执行了但响应丢了」——无法区分。
- **指针与引用失效**：本地传指针是同一地址空间，远程必须传值或引用 ID。

### 现代 RPC：IDL 与 gRPC

传统 RPC 的「手写桩 + 手写序列化」繁琐易错，现代 RPC 用 **IDL（接口描述语言）** 自动化：

- **IDL 定义接口**：`service Greeter { rpc SayHello(HelloRequest) returns (HelloReply); }`——接口先声明，代码由工具生成。
- **自动生成桩**：gRPC 从 IDL 生成客户端桩与服务端骨架，序列化用 Protobuf（紧凑二进制）。
- **传输层**：gRPC 基于 HTTP/2——多路复用、双向流、头部压缩，比传统 RPC 的「每条连接一个请求」高效得多。

**在微服务里**：服务间调用几乎全是 gRPC——**IDL 让「接口即契约」成为可能**，序列化效率高，长连接复用成本低。**理解 RPC 的演进（手写 → IDL 自动化），就是理解「分布式调用如何走向工程化」**。

## 4 核心对比表：本机 IPC vs 远程通信

| 维度 | 管道/消息队列/共享内存 | 套接字（网络） | RPC |
| --- | --- | --- | --- |
| 是否跨机器 | 否 | 是 | 是 |
| 程序员的视角 | 直接操作数据/消息 | 操作字节流 | **函数调用** |
| 序列化 | 不需要 | 需要（应用层做） | 框架自动做 |
| 错误处理 | 同步阻塞/内核错误 | 网络错误需应用处理 | 需处理超时、重复、丢失 |
| 性能 | 高 | 中低（网络开销） | 中低（+序列化开销） |

**设计启示**：RPC 的「伪装成本地调用」是双刃剑——它极大简化了分布式编程，却也掩盖了本地与远程的本质差异（延迟、失败、并发）。有经验的架构师会在团队里立规矩：**「远程调用看起来像本地调用，但永远不要按本地调用的假设去写」**——这是分布式系统所有血泪教训的第一条。

## 5 小结

- **客户机-服务器模型**：服务器监听、客户机发起，网络服务的通用骨架（Web、数据库、消息队列）。
- **套接字**是通信端点，`SOCK_STREAM`（TCP）可靠有序，`SOCK_DGRAM`（UDP）无连接；TCP 连接三阶段：握手建立 → 双向字节流 → 挥手关闭，连接是占用资源的「对象」。
- **AF_UNIX** 让本机进程用文件路径通信，不走网络栈、快于 TCP 回环——Docker/nginx/数据库本地访问常用。
- **RPC** = 本地桩 + 网络传输 + 序列化，把远程调用伪装成本地函数调用。
- **现代 RPC**：IDL 定义接口 → 自动生成桩 → Protobuf 序列化 → HTTP/2 传输（gRPC），微服务间调用的事实标准。
- RPC 的三大陷阱：**延迟不可预知、失败语义不清、指针失效**。
- RPC 解决「怎么传」，不解决「传了之后怎么办」——幂等、超时、补偿仍要应用设计。
- 本机 IPC 与远程通信的边界正在模糊，但「延迟与失败的不可靠性」始终是远程的本质。
