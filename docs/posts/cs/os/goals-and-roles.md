## 为什么从操作系统开始

在第三级《编译原理》里，我们把源码变成了机器码——但机器码被放进 CPU 之后，接下来的事就不再由编译器负责了：「程序跑在哪个 CPU 核心上」「内存够不够放」「文件存到磁盘的哪个扇区」「怎么上网」。这一大摊没人管的脏活、累活，统一由**操作系统（operating system）**接管。它是计算机里最基础、最庞大的系统软件，也是「从极限到大模型」这条主线上，从程序通向硬件的必经关口。

更远处还有一层呼应：今天训练一个大模型动辄调用几千张 GPU，把算力、显存、网络分给成百上千个训练任务的那套系统——调度器、资源管理器——本质上就是把操作系统的思想放大到整个数据中心。这一点我们在《AI基础设施》（第四级）里会正面遇到，今天这篇讲的是那个「更大的操作系统」在单机上的最小版本。<span class="marginnote">一句话预告：Kubernetes 之于数据中心，正如操作系统之于一台机器——都是「资源管理者」。等到第四级你会反复看见今天这些词汇：调度、虚拟化、配额、命名空间。</span>

## 1 什么是操作系统：两种视角

**核心概念**：**操作系统（operating system，OS）**：位于应用程序与计算机硬件之间、管理计算机软硬件资源、并为应用程序提供公共服务的系统软件（system software）。

《操作系统概念》（恐龙书）第 1 章的第一句话，把它的定位说得很朴素：操作系统是管理计算机硬件的软件。紧接着又补了一句——它同时是**用户与计算机硬件之间的中介（intermediary）**。中介这个词值得停一下：它意味着操作系统不干活给谁看，而是一手牵硬件、一手牵应用，把两边接起来。

正是这个「两边」，给出了理解操作系统的**两种视角**。

**视角一：资源管理者（resource manager）。** 向下看，计算机是一堆稀缺资源：CPU、内存、磁盘、网络。多个程序同时运行，都要用它们，于是操作系统扮演**资源分配器（resource allocator）**——决定谁先用 CPU、谁占哪块内存、文件落哪个扇区，用完了再收回来。<span class="marginnote">恐龙书把这种视角称为「控制程序（control program）」：防止程序出错、滥用硬件，保证整个系统不被任何一个程序拖垮。管好资源，是操作系统的第一本职。</span>

**视角二：扩展的虚拟机（extended machine）。** 向上看，没有任何软件包装的**裸机（bare machine）**对应用程序极其不友好：程序要直接面对设备控制器的寄存器、中断向量表、物理内存地址，稍有不慎就踩坏别的程序。操作系统把这一切丑陋细节藏起来，给每个程序呈现一台更简单、更理想、仿佛自己独占的「虚拟机」——程序只管用虚拟的 CPU、虚拟的内存、抽象的文件，细节全交给操作系统。<span class="marginnote">「扩展的虚拟机」思想的源头常追溯到 Dijkstra 与早期分时系统；OSTEP 用「虚拟化（virtualization）」一词表达了同样的主张：操作系统把 CPU 虚拟化成许多个、把内存虚拟成每个进程独享的大空间。这是全书的主题句。</span>

![操作系统在硬件与应用之间：资源管理者与扩展的虚拟机](/images/os/goals-and-roles-1.svg)

两种视角不是两套操作系统，而是同一枚硬币的两面：**向下看，它是资源管理者；向上看，它是扩展的虚拟机。** 后面每一章——进程、内存、文件、设备——都可以从这两个角度各读一遍：一边问「资源怎么分」，一边问「抽象怎么给」。

## 2 操作系统的目标：方便、有效、可扩展、开放

操作系统的好坏由什么衡量？恐龙书第 1 章给出了四类目标，前两个来自用户与系统的立场，后两个来自发展的眼光。

- **方便性（convenience）**：让计算机更容易使用。图形界面、命令补全、一键安装——都是为了把「会用电脑」的成本压下来。
- **有效性（efficiency）**：高效利用硬件资源，追求高利用率（utilization）与高吞吐量（throughput）。同一台机器尽量多跑任务、少闲置。
- **可扩展性（extensibility）**：方便地增加新功能、支持新硬件。操作系统的生命靠这一点延续：USB 设备即插即用、文件系统支持新格式、驱动按需加载，都依赖模块化设计。<span class="marginnote">现代操作系统的可扩展性高度依赖<strong>可加载内核模块（loadable kernel module）</strong>：Linux 里插一块网卡，对应驱动以 .ko 模块的形式在运行时装进内核，而不是重编整个内核。第十六篇会从进程角度再见模块。</span>
- **开放性（openness）**：采用公开、标准化的接口，让不同厂商的软硬件能互相配合、程序可移植。UNIX 一族的可移植性，靠的就是 POSIX 这样的标准接口。

**辨析｜易错点：** **方便性与有效性常常互相打架。** 图形界面方便，但渲染它要占用 CPU；极致的资源利用率（比如无界面的批处理、抢占式调度榨干每一微秒）又往往牺牲用户体验。操作系统的每一次设计抉择，几乎都是在「让用户舒服」与「让硬件满负荷」之间取一个平衡点——这个权衡会贯穿全书：内存换速度、缓存换吞吐、虚拟化换隔离，都是类似的交易。

一个具体的例子：早期的**批处理**系统把效率拉到极致——作业排成队、一个接一个地跑，机器几乎不停歇，但用户要等很久才能拿到结果，交互体验趋近于零；后来的**分时**系统牺牲一点吞吐，换来每个用户「独占一台机器」的幻觉，方便性大幅提升。操作系统的发展史，很大程度上就是这台钟摆在两端的摆动，见本专题第六篇《操作系统的发展历史》。<span class="marginnote">「多道程序」「分时」「实时」这些常听到的词，本质上都是对方便性与有效性这对矛盾给出的不同解。先记住这对矛盾，后面的调度、内存、文件篇章都会反复回到它。</span>

## 3 五大功能：进程、内存、文件、设备、用户接口

把「资源管理者」往下落一层，操作系统对资源的管理具体化为**五大功能**。下表是全书的地图：每一行的「典型机制」都是本专题后面一整篇的内容。

| 功能 | 核心职责 | 典型机制（对应篇章） |
| --- | --- | --- |
| 进程管理 | 进程的创建与撤销、CPU 调度、同步与通信 | PCB、上下文切换、信号量、管道（第三、四、六篇） |
| 内存管理 | 内存的分配与回收、地址转换、保护 | 分页、页表、TLB、虚拟内存（第八、九篇） |
| 文件管理 | 文件的创建/删除/读写、目录与权限 | 文件系统、inode、访问控制列表（第十一、十二篇） |
| 设备管理 | 设备分配、驱动、缓冲与 I/O 调度 | 设备控制器、DMA、中断（第十三篇） |
| 用户接口 | 向用户与应用提供使用入口 | shell、图形界面、系统调用 API（本篇与第二篇） |

读这张表，请把注意力放在「职责」与「机制」的对应上：**每一行都是一个资源域，每一种机制都是把该资源分好、抽象好的具体手艺。** 五个领域看似并列，实则共享同一套底层支撑——中断、时钟、地址转换——这些基础设施正是下一篇《计算机系统组成与硬件结构》的内容。现在我们逐行看一个最有代表性的细节：

- **进程管理**：**进程（process）**是「正在运行中的程序」。CPU 只有几个核心，而进程成百上千，把 CPU 时间分给谁、怎么换来换去不卡顿，是进程管理的事。
- **内存管理**：内存是所有程序的公共舞台。操作系统要把有限的内存切成片，让每个程序各居其位、互不踩踏，还要在内存不够时腾挪——这就是「把物理内存抽象成虚拟地址空间」的由来。<span class="marginnote">内存管理是「扩展的虚拟机」最生动的例子：每个进程都以为自己独占一整块连续内存，其实它只是被映射到了物理内存的某个角落，甚至部分在磁盘上。第九篇《虚拟内存》专门讲这套「骗局」怎么维持。</span>
- **文件管理**：磁盘上本是一堆无意义的扇区，文件管理把它们组织成「文件」与「目录」这种人们熟悉的单位，并负责权限与共享。
- **设备管理**：打印机、显卡、网卡千奇百怪，设备管理用一个统一的接口（打开、读写、关闭）把它们全部收编，应用不必关心背后是哪家厂商的芯片。
- **用户接口**：最直观的是 shell 与图形界面；但更深一层，**系统调用接口**才是程序与操作系统打交道的主窗口——它正是下一节的主角。

## 4 操作系统在计算机系统中的位置：内核、系统调用与双模式

把视角拉远，一台计算机自下而上可以分成四层：**硬件 → 内核 → 系统程序 → 应用程序**（见图中的分层示意）。系统程序（shell、编译器、系统库）与应用程序都运行在用户态，它们共同栖身于内核之上；而内核之下，直接就是硬件。

- **内核（kernel）**：操作系统中常驻内存、直接管理硬件、执行特权指令的核心部分。<span class="marginnote">「操作系统」与「内核」并非同义词：内核是操作系统常驻内存的核心，而像 shell、系统库、许多工具程序其实运行在用户态，也被算作操作系统的组成部分。</span>
- **系统调用（system call）**：应用程序请求内核服务的正式通道。程序想要读文件、开进程、发网络包，都得通过系统调用「委托」内核去办。
- **双模式引子**：CPU 提供一个**模式位（mode bit）**，把执行状态分成**用户态**与**内核态**。涉及硬件的**特权指令（privileged instruction）**——改页表、关中断、启动设备——只有内核态能执行。用户态程序一旦碰了特权指令，CPU 会触发异常，把控制权交回内核。这就是操作系统自我保护的第一道防线。

看一个最真实的例子。下面这段 C 代码调用 `read()` 从标准输入读 512 字节：

```c
#include <unistd.h>

char buf[512];
ssize_t n = read(0, buf, sizeof(buf));  /* 从标准输入读，最多 512 字节 */
```

应用程序看到的只是一个朴素的「读数据」抽象。但 `read` 经过系统库后，会触发一条陷入指令（在 x86-64 上是 `syscall`），CPU 的模式位从 1 翻到 0，进入内核态，由内核去和设备控制器打交道；读完后切回用户态，把数据交回缓冲区。**这一趟「穿越」——用户态陷入内核态、办完事再回来——正是操作系统在系统中位置的直观体现。**<span class="marginnote">系统调用不是普通函数调用：函数调用在同一地址空间里跳转，系统调用要切换特权级、保存现场，代价高一个数量级。所以内核才提供了缓冲、批量读、页缓存这些优化。用 `strace` 工具能亲眼看到进程的每一次系统调用，见第十五篇 Linux 专题。</span>至于编译器产出的可执行文件如何被操作系统装载进内存、变成运行中的进程，是第三级《编译原理》第十六篇与《操作系统》第三篇共同的话题。

## 5 核心对比表：用户态与内核态

**操作系统这一章没有公式；对无公式的主题，一张核心对比表就是最有力的「公式解析」。** 双模式是理解「操作系统凭什么管住应用、又凭什么保护自己」的关键，我们把它拆成一张对照表：

| 比较维度 | 用户态（user mode） | 内核态（kernel mode） |
| --- | --- | --- |
| 执行的代码 | 应用程序、shell、系统库 | 内核（进程/内存/文件/设备管理） |
| CPU 模式位 | 1 | 0 |
| 特权指令 | 不可执行 | 可以执行（关中断、改页表、启停设备） |
| 可访问的资源 | 受限：只能访问自己的地址空间 | 全部：内存、寄存器、设备控制器 |
| 进入 / 退出 | 被中断、异常或系统调用「切走」 | 处理中断、异常、系统调用时进入 |

把这张表当作公式一样逐项拆解：

- **第一步，读模式位**：CPU 里的一个二进制位是 0 还是 1，决定当前处于哪种状态。0 表示内核态，1 表示用户态——这是整个双模式机制的物理开关。
- **第二步，认特权指令**：改页表、关中断、直接控制设备这类「危险操作」被标记为特权指令。用户态一旦执行，CPU 不会照做，而是触发**非法指令异常**，把控制权交给内核裁决——越权行为在硬件层面就被拦下了。
- **第三步，走陷入（trap）**：应用要内核办事，唯一的正式通道是**系统调用**。它故意触发一次陷入，让 CPU 从用户态切到内核态，执行内核预先写好的服务例程，办完再切回用户态。

**辨析｜易错点：** 用户态程序并非「什么都做不了」，它照样能执行算术、访问自己的内存——被禁止的只是那些会破坏隔离的特权操作。**「用户态不能碰特权指令」不是纪律，而是硬件强制**：模式位是 CPU 的一部分，违背它就会产生异常。这套双模式的完整硬件细节（中断、异常、模式切换的代价），我们在第一篇第 8 条《用户态与内核态》与下一篇《计算机系统组成与硬件结构》中展开。<span class="marginnote">模式位的思想可追溯到 1961 年的 Burroughs B5000 等早期机型；现代 RISC-V 甚至有机器态、监管态、用户态三档。多一层模式，多一层隔离，也就多一层保护。</span>

## M 小结

- 操作系统是管理计算机软硬件资源、为应用程序提供公共服务的系统软件；**向下看是资源管理者，向上看是扩展的虚拟机**。
- 四大目标：**方便性、有效性、可扩展、开放**；其中方便与有效常常互相权衡。
- 五大功能：**进程管理、内存管理、文件管理、设备管理、用户接口**——它们是全书的地图。
- 系统分层：硬件 → **内核** → 系统程序 → 应用；应用通过**系统调用**请求内核服务。
- **双模式**（用户态 / 内核态）配合**模式位**与**特权指令**，是操作系统自我保护的第一道防线。

在下一节，我们将往下走进第一层：**计算机系统的组成与硬件结构**——CPU、内存、I/O 设备如何组织，操作系统又是站在哪些硬件机制之上运转的。

而把「资源管理」放大到数据中心，正是第四级《AI基础设施》的主题：当应用变成训练任务、资源变成 GPU 集群，那个「更大的操作系统」叫作调度器——到那时，今天学的资源分配、虚拟化与命名空间，都会以集群的规模再次登场。
