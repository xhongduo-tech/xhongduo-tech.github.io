## 为什么从磁盘调度开始

磁盘 I/O 的主要成本是**寻道**（磁头移动）。当多个 I/O 请求排队时，**先服务谁**直接决定磁头总移动距离——这就是**磁盘调度（disk scheduling）**。它与 CPU 调度同源而异：CPU 调度优化「等待时间」，磁盘调度优化「磁头移动距离」。这一节看最朴素的两个算法：**FCFS**（先到先服务）与 **SSTF**（最短寻道优先）。<span class="marginnote">回顾 CPU 调度：FCFS、SJF、SCAN…… 磁盘调度几乎是同一族算法的「寻道版」——判据从「突发长度」换成「磁道距离」。你可以对照着学，事半功倍。</span>

## 1 磁盘调度的目标与模型

**磁盘调度（disk scheduling）**：决定磁盘请求队列中先服务哪个请求，以减少磁头移动（寻道时间）、提高吞吐、降低响应时间。

**评估指标**：**磁头总移动距离（总寻道量）**——距离越短，总服务时间越短。

**经典示例请求队列**：磁道号 $98, 183, 37, 122, 14, 124, 65, 67$，磁头初始在 **53**，移动方向向外（磁道号增大方向）。

每个算法我们算它的总寻道距离。

## 2 FCFS：先到先服务

**FCFS（First-Come, First-Served）**：按请求到达顺序服务，不重排。

按队列顺序服务：98 → 183 → 37 → 122 → 14 → 124 → 65 → 67。

**总寻道距离**：

$$|53-98| + |98-183| + |183-37| + |37-122| + |122-14| + |14-124| + |124-65| + |65-67|$$

$$= 45 + 85 + 146 + 85 + 108 + 110 + 59 + 2 = 640$$

**FCFS 的优劣**：

- **优点**：公平、实现简单、无饥饿。
- **缺点**：**完全不优化寻道**——磁头在 53→183→37 之间来回大跨度移动，总距离很大。FCFS 是磁盘调度的「基准线」，几乎所有算法都优于它。

**类比**：电梯只按「谁先按的楼层」停，完全不顺路——从 1 楼去 20 楼送文件，又从 20 楼下到 2 楼取文件，来回跑。

## 3 SSTF：最短寻道时间优先

**SSTF（Shortest-Seek-Time-First）**：每次选择**离当前磁头位置最近**的请求服务。

从 53 开始，逐次选最近：

1. 53 → **65**（12）→ **67**（2）→ **37**（30）→ **14**（23）→ **98**（84）→ **122**（24）→ **124**（2）→ **183**（59）

**总寻道距离**：

$$12 + 2 + 30 + 23 + 84 + 24 + 2 + 59 = 236$$

比 FCFS 的 640 大幅改善——**SSTF 有效减少了寻道**。

**SSTF 的问题**：

- **饥饿**：如果新请求不断落在磁头附近，远处磁道的请求可能永远轮不到（对照 CPU 调度的 SJF 饥饿）。
- 是「贪心」算法：每次局部最优，不保证全局最优。

**辨析｜易错点：** 「SSTF 与 CPU 调度的 SJF 对应」是很好的类比，但要注意差别：**SSTF 的「最短」是「离当前位置最近」，SJF 的「最短」是「总执行时间最短」**——一个看距离、一个看时长。不过**两者都有饥饿问题**（贪心 + 局部最优），这个教训是共通的。

## 4 核心对比表：FCFS vs SSTF

| 维度 | FCFS | SSTF |
| --- | --- | --- |
| 选择依据 | 到达顺序 | 离磁头最近 |
| 总寻道（示例） | 640 | 236 |
| 公平性 | 好 | 差（可能饥饿） |
| 吞吐 | 低 | 高 |
| 是否贪心 | 否 | 是（局部最优） |
| 实现 | 最简 | 中（需维护排序） |

**设计启示**：FCFS 与 SSTF 的对比再次揭示调度算法的永恒矛盾——**公平 vs 效率**。SSTF 靠「偏心」换效率，却制造饥饿；下一篇的 **SCAN/电梯算法** 试图「既高效又公平」——像电梯一样顺路服务，同时保证不会有人被饿死。

## 5 小结

- **磁盘调度**优化磁头移动（寻道）——评估指标是总寻道距离。
- **FCFS**：按到达序，公平但寻道巨大（示例 640）。
- **SSTF**：每次选最近磁道，寻道大幅减少（示例 236），但可能**饥饿**。
- 二者是「公平 vs 效率」的基线，SCAN 家族试图两者兼得。
- 与 CPU 调度同构，但判据是「距离」而非「时长」。
