## 为什么从 I/O 硬件开始

文件系统最终要落到磁盘、键盘、网卡等**设备**上。操作系统与设备打交道的接口，就是 **I/O 系统**。这一节先认识硬件的分工：**设备控制器**（设备的「大脑」）与**设备驱动**（内核里的「翻译官」），以及设备的两种基本分类——**字符设备与块设备**。这是第十三篇 I/O 系统的地基。<span class="marginnote">回顾《计算机系统组成》：CPU 通过总线与设备通信。I/O 系统回答「CPU 到底怎么跟设备说话」——答案是：通过设备控制器（硬件）与设备驱动（软件）的协作。设备不是 CPU 直接操作的裸线。</span>

I/O 系统的复杂性在于「设备种类的爆炸」：磁盘、键盘、网卡、声卡、USB 控制器……物理机制天差地别。I/O 系统的全部工作，就是把这些「异质」收敛成「同质」的接口——这一节先建立「控制器 / 驱动 / 设备」三层心智，后面的缓冲、调度、假脱机才有着落。

## 1 设备控制器：设备的「小 CPU」

**设备控制器（device controller）**：每个设备（或其接口卡）上的硬件，负责管理设备的具体操作。CPU 不与设备直接交互，而是与控制器交互。

**控制器的组成**：

- **寄存器组**：状态寄存器（设备状态）、数据寄存器（传输数据）、控制寄存器（发命令）。
- **本地缓冲**：设备与总线之间的数据暂存区（如网卡 RAM）。
- **固件**：控制器的内部逻辑。

**CPU 与控制器通信**的三种方式（回顾第一篇《输入输出结构》）：

- **端口映射 I/O**：用专用 I/O 指令读写控制器寄存器。
- **内存映射 I/O**：把控制器寄存器映射到内存地址空间，普通读写即可访问。
- **DMA**：控制器直接与内存交换数据，CPU 只在开始/结束时介入（见《I/O 控制方式》）。

**典型流程（磁盘读）**：CPU 写控制寄存器「读块 123」→ 控制器把块读入本地缓冲 → 通过 DMA 把数据送到内存 → 置状态「完成」→ 发中断通知 CPU。

### 寄存器组的细节

控制器寄存器是 CPU 与设备对话的「信箱」：

| 寄存器 | 作用 | 读写方向 |
| --- | --- | --- |
| 状态寄存器 | 设备是否忙、是否完成 | 读 |
| 数据寄存器 | 传输的数据 | 读写 |
| 控制寄存器 | 发命令（读哪块、做什么） | 写 |

**轮询 vs 中断的起源**：CPU 可以「反复读状态寄存器直到不忙」（轮询），也可以「让设备完成时发中断通知我」（中断驱动）——两者的差异见下一节《I/O 控制方式》。**寄存器是对话的基础，轮询 / 中断是对话的节奏。**

## 2 设备驱动：内核里的「翻译官」

**设备驱动（device driver）**：内核中为某类设备提供的软件模块——它把**统一的设备接口**翻译成**特定控制器的寄存器操作**。

**驱动的角色**：

- 向上：对内核其他部分暴露**统一接口**（`open`/`read`/`write`）。
- 向下：把接口调用翻译成**控制器的寄存器读写**。

**驱动的作用**：内核不必为每个设备写一套逻辑——**设备制造商提供驱动，内核提供接口**。这实现了「设备可插拔」：换一块新网卡，装个驱动，其余不变。

**辨析｜易错点：** 「设备驱动 = 设备控制器」是常见混淆。**控制器是硬件**（设备上的芯片/固件），**驱动是软件**（内核里的模块）——驱动指挥控制器，控制器操作设备。**「驱动」这个动词也常被误用**：驱动不是「让设备转起来」的魔法，而是「把内核的请求翻译成控制器能懂的寄存器命令」的翻译官。

### 驱动的分层：直接驱动与抽象驱动

驱动内部也不是铁板一块：

- **直接驱动（device driver）**：面向具体型号的控制器，翻译寄存器操作（如 `e1000` 网卡驱动）。
- **抽象驱动 / 协议驱动**：面向「一类设备的协议」，与具体硬件解耦（如 SCSI 协议驱动之上挂各种厂商设备）。
- **通用框架**：Linux 的设备模型（`struct device`、`struct driver`）把驱动挂进内核的统一框架，支持热插拔与自动绑定。

**一句话**：驱动是「控制器寄存器操作」与「内核统一接口」之间的翻译层；具体到抽象之间还有一层「协议驱动」——这就是「可插拔设备」得以成立的软件基础。

## 3 字符设备与块设备：两大分类

设备按数据访问方式分两类：

- **块设备（block device）**：以**固定大小的块**为单位访问（如磁盘、SSD）。可随机访问任意块；数据有寻址。Linux 中设备文件如 `/dev/sda`。
- **字符设备（character device）**：以**字节流**为单位访问，无固定块、无随机寻址（如键盘、鼠标、串口）。Linux 中如 `/dev/tty`、`/dev/random`。

| 维度 | 块设备 | 字符设备 |
| --- | --- | --- |
| 访问单位 | 块（4KB 等） | 字节流 |
| 随机访问 | 可（按块寻址） | 不可（流式） |
| 缓冲 | 有（页缓存） | 可有可无 |
| 典型 | 磁盘、SSD | 键盘、串口、声卡 |
| Linux 设备文件 | `/dev/sda`（b 类型） | `/dev/tty`（c 类型） |

**例外**：网卡是「**网络设备**」——它既不是块设备也不是字符设备，按「数据包」访问，有独立的 `socket` 接口。

**辨析｜易错点：** 「所有设备要么是块要么是字符」是过度简化。**网络设备是第三类**（按包、无块寻址）；还有「伪设备」（`/dev/null`、`/dev/zero` 只是内核的功能入口，不是真硬件）。**分类是「接口的抽象」，不是「硬件的本质」**——同一硬件可以同时暴露字符与块接口。

### 设备文件：一切皆文件的落点

Linux 用**设备文件**把设备「伪装」成文件，用户用 open/read/write 操作设备：

- **块设备文件**：`/dev/sda`（类型 b），通过它读写磁盘块。
- **字符设备文件**：`/dev/tty`（类型 c），字节流式读写。
- **主次设备号**：主设备号标识驱动（哪类设备），次设备号标识具体实例（第几块盘）——`ls -l /dev/sda` 能看到 `b 8:0`，8 是主号、0 是次号。

**设计启示**：「设备 = 文件」不是营销话术，而是操作系统把「设备访问」统一到文件接口的工程实现——**应用不需要知道背后是键盘还是磁盘，只需 open/read/write**。这是「一切皆文件」的落点，也是《文件保护》里「设备也能设权限」的原因。

## 4 核心对比表：CPU ↔ 控制器 ↔ 驱动

| 层次 | 是什么 | 做什么 |
| --- | --- | --- |
| 设备 | 物理外设 | 实际执行 I/O（读盘、打印） |
| 控制器 | 硬件芯片/固件 | 管理设备，提供寄存器与缓冲 |
| 设备驱动 | 内核软件 | 统一接口 ↔ 寄存器操作翻译 |
| 内核 I/O 子系统 | 通用层 | 调度、缓冲、错误处理（见后几节） |

**设计启示**：I/O 的层次化——**「统一接口（驱动）+ 具体实现（控制器）+ 物理设备」**——是操作系统「一切皆文件」的根基：无论设备多千奇百怪，经过驱动这一层，都变成统一的**文件接口**。你会在《I/O 软件的层次结构》里看到更完整的层级。

**术语速查**：

| 术语 | 含义 |
| --- | --- |
| 设备控制器 | 设备上的硬件「大脑」（寄存器 + 缓冲 + 固件） |
| 设备驱动 | 内核软件，统一接口 ↔ 寄存器操作翻译 |
| 块设备 | 按固定块随机访问（磁盘 / SSD） |
| 字符设备 | 按字节流访问（键盘 / 串口） |
| 网络设备 | 按数据包访问（网卡） |
| DMA | 控制器与内存直接交换，CPU 只介入首尾 |

## 5 小结

- **设备控制器**：设备的硬件「大脑」——寄存器 + 本地缓冲 + 固件，CPU 通过它操作设备。
- 三类寄存器：**状态（读）、数据（读写）、控制（写）**——CPU 与设备的「信箱」。
- **设备驱动**：内核软件翻译官，把统一接口翻译成控制器寄存器操作；内部还有「直接驱动 → 协议驱动 → 设备模型框架」的分层。
- 通信方式：端口映射 I/O、内存映射 I/O、**DMA**；轮询 / 中断是「怎么知道设备完成」的两种节奏。
- **块设备**按块随机访问（磁盘），**字符设备**按字节流（键盘）；网卡是网络设备。
- **设备文件**把设备伪装成文件（主设备号 = 驱动、次设备号 = 实例），open/read/write 统一操作——「一切皆文件」的落点。
- I/O 层次化：统一驱动接口 + 具体控制器 + 物理设备，支撑「一切皆文件」。
