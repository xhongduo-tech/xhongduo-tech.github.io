## 为什么从 SCAN 家族开始

SSTF 高效但会饥饿——远处磁道的请求可能永远等不到。**SCAN（电梯算法）**家族给出「既高效又公平」的方案：**磁头沿一个方向移动，顺路服务沿途请求，到达端点（或没有请求）后反向**——像电梯顺路载客，谁都不饿。这一节看四个成员：SCAN、C-SCAN、LOOK、C-LOOK。<span class="marginnote">回顾 SSTF 的饥饿：贪心「最近者先」饿死远的。SCAN 的公平性来自「顺序服务」——磁头扫过去一定经过你的磁道，绝不会跳过，所以<strong>没有饥饿</strong>。</span>

电梯算法的名字来自真实电梯：电梯不理会「谁先按的」，只按「当前方向顺路」载客——这保证任何楼层的人最终都能等到电梯，这正是「无饥饿」的来源。把「电梯」换成「磁头」、把「楼层」换成「磁道」，就是磁盘调度。

沿用上一节的队列：$98, 183, 37, 122, 14, 124, 65, 67$，磁头初始 53，方向向外（增大）。

## 1 SCAN（电梯算法）

**SCAN**：磁头沿一个方向移动，服务沿途的所有请求，到达**最外/最内磁道**才反向。

初始 53 向外（增大方向），一路服务：53 → **65, 67, 98, 122, 124, 183**（继续到最外端 199 或 200）→ 反向 → **37, 14**（到最内端 0）。

设磁道范围 0~199，SCAN 到最外 199 后反向。

**总寻道距离**：

$$(199-53) + (199-0) = 146 + 199 = 345$$

（向外扫到 199，再反向往内扫到 0——注意要到端才反向，所以会扫过空磁道。）

**SCAN 的特点**：

- **无饥饿**：磁头双向扫过，每个磁道都会经过。
- 代价：**到达端后才反向**——即使端外没有请求，也要白白走到端（浪费寻道）。

### 服务顺序一览

把四个算法在这组数据上的**服务顺序**列出来，差距一眼可见：

| 算法 | 服务顺序 | 总寻道 |
| --- | --- | --- |
| SCAN | 65→67→98→122→124→183→(199)→37→14→(0) | 345 |
| C-SCAN | 65→67→98→122→124→183→(199)→(0)→14→37 | 382 |
| LOOK | 65→67→98→122→124→183→(→14→37) | 299 |
| C-LOOK | 65→67→98→122→124→183→(→14→37) | ~299 |

**读法**：括号里的数字是「空走」（返回途中不服务）。SCAN/C-SCAN 的 199 与 0 是「到端」，LOOK/C-LOOK 的 183 与 14 是「最远请求」——**后者少走「到端却无请求」的冤枉路**。

## 2 C-SCAN（循环扫描）

**C-SCAN（Circular SCAN）**：磁头只在一个方向服务请求，到达一端后**直接快速返回另一端**（返回途中不服务），再继续单向服务。

从 53 向外：服务 65, 67, 98, 122, 124, 183 → 到 199 → **快速回到 0**（不服务）→ 服务 14, 37 → 结束。

**总寻道距离**：

$$(199-53) + (199-0) + 37 = 146 + 199 + 37 = 382$$

**C-SCAN 的动机**：**均匀等待时间**。SCAN 在折返处附近的磁道等待时间极短，另一端的磁道等待时间极长——不均匀。C-SCAN 用「返回不服务」换取**各磁道等待时间更均匀**（都约等于「扫一个整程」）。

### 等待时间的均匀性

为什么「均匀」重要？看两个极端：

- **SCAN**：磁头在折返处附近频繁折返，那些磁道的请求等待极短；而另一端的磁道要等磁头「扫一个来回」，等待极长——**两端磁道等待方差大**。
- **C-SCAN**：所有磁道的请求都等「大约一个整程」——**等待时间趋同**，方差小。

对「各磁道请求量均匀」的负载（如文件系统的批量扫描），C-SCAN 的均匀等待意味着**没有磁道被系统性饿慢**；对「热点磁道」负载，均匀反而牺牲了热点，SCAN 更好。**「均匀 vs 响应热点」是 C-SCAN 与 SCAN 的分野。**

## 3 LOOK 与 C-LOOK：别走到头

**LOOK / C-LOOK** 是对 SCAN / C-SCAN 的优化：**只走到最远的请求处就反向，不走到物理端点**——「看一眼」最远的请求在哪，到那就折返。

- **LOOK**：SCAN + 走到「最远请求」处反向。
- **C-LOOK**：C-SCAN + 走到「最远请求」处返回。

**LOOK 版本计算**：初始 53 向外，最远请求 183。

总寻道：$(183-53) + (183-14) = 130 + 169 = 299$（向内最远请求 14）。

**LOOK/C-LOOK 的收益**：**省掉了「到端却无请求」的白走**——比 SCAN/C-SCAN 总寻道更短。现代磁盘调度几乎都用 LOOK/C-LOOK 变体。<span class="marginnote">「LOOK」的名字来自「look ahead」——磁头看一眼前方还有没有请求，没有就到最远的请求为止，不再傻走到端点。<strong>用「前方有没有货」代替「物理端点」做折返点，是这类优化的共同思想。</strong></span>

**辨析｜易错点：** 「LOOK 一定比 SCAN 好」在寻道距离上成立，但要权衡——**LOOK 的折返点随请求动态变化，可能导致某个方向的请求在折返后「绕远」**。不过现代系统几乎都选 LOOK：省下的寻道远多于潜在的绕远，且实现同样简单。**「到最远请求就折返」是磁盘调度的默认工程选择。**

## 4 四个算法的对比

| 算法 | 服务方向 | 折返点 | 总寻道（示例） | 等待均匀性 |
| --- | --- | --- | --- | --- |
| SCAN | 双向 | 物理端点 | 345 | 不均匀 |
| C-SCAN | 单向 + 快速返回 | 物理端点 | 382 | 均匀 |
| LOOK | 双向 | 最远请求 | 299 | 较均匀 |
| C-LOOK | 单向 + 快速返回 | 最远请求 | ~299 | 均匀 |

（对比：FCFS 640，SSTF 236——SSTF 在这组数据上最好，但有饥饿风险；LOOK/C-LOOK 在公平与效率间更均衡。）

**辨析｜易错点：** 「SCAN 家族一定比 SSTF 寻道短」不成立——**在特定请求分布下 SSTF 可能更短，但 SSTF 会饥饿。** SCAN 家族的价值是「**以略多的寻道换取无饥饿的公平**」。工程上现代 OS 与磁盘控制器（NCQ）都用近似 LOOK 的调度——公平优先，效率次之。

另一个易错点：**「SCAN 和 C-SCAN 的区别是服务方向」**——SCAN 双向都服务，C-SCAN 只单向服务、返回不服务。**C-SCAN 牺牲一点寻道换等待均匀**，适合「各磁道请求量相当」的负载（如文件系统批量扫描）。

### 现代磁盘：NCQ 时代的调度

现代磁盘（含 SSD）用 **NCQ（Native Command Queuing，原生命令队列）**：设备内部可以排队几十条命令，由控制器**自己**重排顺序（近似 LOOK / 最短寻道优先），而不是等操作系统逐条调度。

**这意味着什么**：

- 操作系统层仍可做调度，但**最终执行顺序由设备决定**——OS 调度与设备调度是两层。
- 对 SSD，NCQ 的意义从「减寻道」变成「**合并写入、摊平随机 I/O**」——因为无寻道，调度目标变为「减少写放大」。
- 对应用的影响：**批量提交 I/O（让设备有队可排）比逐个同步 I/O 更高效**——这正是异步 I/O 与 io_uring 等机制的价值所在（见 Linux 专题《io_uring》）。

## 5 小结

- **SCAN（电梯）**：磁头双向扫描、沿途服务、到端折返——无饥饿但等待不均（两端磁道等待方差大）。
- **C-SCAN**：单向服务 + 快速返回不服务——等待时间均匀，适合均匀负载；热点负载反而 SCAN 好。
- **LOOK / C-LOOK**：折返点从「物理端点」优化为「最远请求」，少走冤枉路——现代调度默认选择。
- 服务顺序表：SCAN 到端折返、C-SCAN 返回不服务、LOOK/C-LOOK 到最远请求折返。
- **NCQ 时代**设备内部自调度，OS 调度与设备调度是两层；对 SSD 调度目标变为「减少写放大」。
- 家族价值：**以略多寻道换公平无饥饿**，是工业磁盘调度的主流。
- 与 SSTF 对比：SSTF 寻道短但饥饿，SCAN 家族公平但略慢；例子数据 FCFS 640、SSTF 236、LOOK 299。
