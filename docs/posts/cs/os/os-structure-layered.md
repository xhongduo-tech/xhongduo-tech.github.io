## 为什么从操作系统结构开始

系统调用定义了内核「对外长什么样」，但这只是面子。真正决定一个操作系统能否长期演进、能否被维护、能否在几百万行代码里找出 bug 的，是它**内部怎么组织**——内核的骨架。上一节我们讲了服务入口，这一节我们俯瞰骨架本身：同样是「管理进程、内存、文件」，不同的操作系统内部可以长成完全不同的样子。<span class="marginnote">「结构决定可维护性」是软件工程的核心命题，操作系统正是这门学问最极端的学生——它不能轻易停机，错误代价极高，因而结构选择比普通软件更生死攸关。</span>

一个操作系统的结构选择，本质是在回答三个问题：模块之间如何分工？依赖关系如何约束？错误如何隔离？

这三个问题没有标准答案——MS-DOS 选择了「不分」，THE 选择了「分层」，Linux 选择了「分层 + 模块」的混合。把「操作系统结构」放进全课程坐标系：它和《软件工程》的架构模式、《计算机网络》的分层协议是同一枚硬币——**用边界与依赖约束大规模系统的可维护性**。这也是为什么它被安排在「系统调用」之后：先知道内核对外提供什么，再关心它内部怎么长。

## 1 简单结构：MS-DOS 与早期 Unix

**简单结构（monolithic / simple structure）**：把内核所需的全部功能堆在一个大型可执行文件里，模块之间没有严格的层次约束，任何模块都可以直接调用任何其他模块的代码与数据。

MS-DOS 是简单结构的典型：应用程序、设备驱动、文件系统逻辑混在同一个二进制里，没有明确的模块边界。早期 Unix（1969—1970 年）也相当简单——内核与系统程序一起编译，能分成文件系统、进程管理、设备管理几个部分，但各部分之间没有强制分层。<span class="marginnote">「Monolithic」一词中文常译「单体内核」或「宏内核」。注意它描述的是「编译期就捆死、无边界」的组织方式，而非功能多寡——现代 Linux 也是宏内核，但模块化程度远高于早期 Unix。</span>

**优点**：直接调用，无边界开销，性能最好；代码量小的时候清晰易懂。
**缺点**：模块边界模糊，一处改动可能影响全局；错误隔离差，驱动崩溃拖垮整个内核；难以扩展为大规模系统。

### 简单结构为什么能活下来

简单结构在 1970 年代并非「偷懒」，而是**合理选择**：那时的操作系统只有几万行代码，一个程序员能读懂全部；性能是压倒性诉求，直接调用零开销是最优解；且硬件简单，不需要复杂隔离。**当系统小到「一眼看全」时，结构化的收益抵不上成本**——这是工程上的「简单性优先」原则。

它的衰落是规模逼出来的：当内核长到百万行、上千个模块，无边界结构让「改一处、崩全盘」变得不可接受，分层的时代到来了。

## 2 分层结构：把内核切成蛋糕

**分层结构（layered structure）**：把操作系统按抽象层级组织，底层是硬件，顶层是用户接口，每一层只依赖其下方的一层，层间通过定义良好的接口通信。1970 年代 Dijkstra 设计的 **THE 系统** 是第一个分层操作系统，共分六层；之后的 VENIX 与 Windows NT 的早期设计也采用了分层思想。

每一层就像一个「被服务的层」：

第 0 层：进程调度与内存分配（最贴近硬件）
第 1 层：内存管理
第 2 层：操作员—进程通信
第 3 层：I/O 管理
第 4 层：用户程序
第 5 层：操作员控制台

THE 六层从下往上，每一层都建立在下一层之上，像一个「俄罗斯套娃」：第 0 层分配 CPU 与内存，第 1 层管理页表，第 2 层让操作员与进程通过消息通信……每一层只使用下一层提供的操作，**不跨层、不回头**。这套设计的直接收益是**可验证性**——想确认第 3 层正确，只需假定第 2 层以下都正确，自底向上逐层证明。

**分层的关键收益是「层内隔离」**：调试时从底层往上逐层验证，上层出错不用怀疑下层；修改某层内部实现时，只要接口不变，其他层不受影响。<span class="marginnote">分层思想远不止于操作系统：网络协议栈的 TCP/IP 四层、计算机体系结构的分级存储器层次，都是同一招——用接口隔离变化，用层级控制依赖。你在《计算机网络》中还会反复见到它。</span>

**代价**：每层都要经过下层服务才能触达硬件，链路过长导致性能损失；而且层间职责划分并不总清晰——「文件系统到底该在第几层？」这类问题会让分层退化为名义分层。

### 分层结构在现实中的身影

严格分层很少完整落地，但它的**精神**无处不在：

- **Unix/Linux 的用户态—内核态二分**是最粗的一层划分；内核内部又按「系统调用层 → VFS 虚拟文件系统层 → 具体文件系统 → 设备驱动」组织——每一层只依赖其下层的接口。
- **微内核的「服务进程」**把「层」变成「进程」，层次边界升级为进程边界（见《微内核结构及其优缺点》）。
- **网络协议栈（TCP/IP）**是分层最严格的领域：每一层只与相邻层通信，接口（socket）高度稳定。

**一句话**：严格分层是「理想模型」，现实系统是「务实分层」——保留层间依赖约束，但允许少量横向调用，换取性能与灵活性。

**术语速查**：

| 术语 | 含义 | 代表 |
| --- | --- | --- |
| 简单结构 | 无边界、直接调用 | MS-DOS、早期 Unix |
| 分层结构 | 严格层级依赖 | THE、VENIX |
| 模块化宏内核 | 分层 + 模块插拔 | Linux |
| 微内核 | 服务进程隔离 | QNX、seL4 |
| 混合内核 | 宏 + 微组件 | Windows、macOS |

## 3 从简单到分层：一条抽象阶梯

把两个极端放在一起看，就理解了结构演进的逻辑：

| 维度 | 简单结构 | 分层结构 |
| --- | --- | --- |
| 模块边界 | 无强制边界 | 严格层级依赖 |
| 依赖方向 | 任意互调 | 只允许向下依赖 |
| 调试策略 | 整体调试 | 自底向上逐层验证 |
| 性能开销 | 最低 | 每层增加间接性 |
| 可维护性 | 代码量小时尚可 | 适合大型系统 |
| 错误隔离 | 差，一处崩溃全域崩 | 较好，层内相对隔离 |

**辨析｜易错点：** 分层结构 ≠ 层次分明就万事大吉。实际系统中「环形依赖」几乎必然出现——例如文件系统需要内存管理分配缓冲，而内存管理的换页又需要把页写到磁盘、访问文件系统。为此，操作系统普遍采用「层间允许少量横向调用」的务实分层，而不是教科书式的严格分层。**纯粹的严格分层只在教学与协议栈中成立，工程上总是要破例。**

## 4 核心对比表：结构选择的三维权衡

用一张表总结不同结构对应的问题定位：

| 关注点 | 简单结构给出 | 分层结构给出 |
| --- | --- | --- |
| 性能至上 | 直接调用、零间接 | 每层有开销 |
| 可靠性第一 | 难保证 | 层内隔离 |
| 快速演进 | 改动波及面大 | 接口稳定则安全 |
| 学习调试 | 简单直观 | 依赖图清晰 |

后文将要讲的**微内核**、**可加载内核模块**与**混合内核**，都是对「简单」与「分层」两种极端的补救——它们试图同时要性能、可维护性与可扩展性。理解这两个极端，是看懂所有后续内核结构的坐标原点。

### 结构选择的决策框架

面对「我的系统该选哪种结构」，可以用三个问题快速定位：

| 判断维度 | 倾向简单结构 | 倾向分层/模块化 |
| --- | --- | --- |
| 代码规模 | 小（万行级） | 大（十万行以上） |
| 性能敏感度 | 极敏感 | 可接受少量间接 |
| 演进预期 | 基本不变 | 长期持续演进 |
| 隔离需求 | 无 | 强（驱动/模块多） |

**工程判断**：规模小、性能苛刻 → 简单；规模大、要演进 → 分层；既要性能又要扩展 → 模块化宏内核（下一篇的主线）。结构选择不是「哪个更高级」，而是「**哪个匹配当前约束**」。

## 5 小结

- **简单结构**把所有功能揉在一个二进制里，性能最好、边界最少，适合小系统；其衰落是「规模逼出来」的。
- **分层结构**按依赖方向切成自底向上的层级，每层只向下依赖，调试与维护性好，但有性能损耗与职责划分难题。
- THE 系统是第一个分层 OS，六层自底向上、每层只依赖下一层；分层带来**可验证性**（逐层证明正确）。
- 分层思想跨领域通用：网络协议栈、存储器层次、VFS 文件系统栈都是同构思路。
- 严格的纯粹分层在工程中不现实，环形依赖需要务实破例——现实是「务实分层」。
- 结构选择看约束：规模小选简单、规模大选分层、要扩展选模块化。
- 简单与分层是**微内核、模块化、混合结构**的坐标原点，后续几篇将逐一展开。
