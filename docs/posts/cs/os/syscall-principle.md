## 为什么从系统调用原理开始

Linux 专题从系统调用开始——因为它是用户态与内核态的唯一合法接口。第一篇《系统调用的类型与实现原理》给了概貌，这一节把 **Linux 上的完整路径**逐层展开：库函数 → 封装 → `syscall` 指令 → 内核入口 → 系统调用表 → 处理函数 → 返回。这是理解 Linux 内核的第一块基石。<span class="marginnote">回顾《用户态与内核态》：模式位决定特权级。系统调用是「翻模式位」的合法途径——它由 <strong>CPU 指令（`syscall`）</strong> 触发，硬件完成模式切换，这是与普通函数调用（不改模式）的本质区别。</span>

## 1 完整路径总览

一次 `read()` 从用户到内核的旅程：

```
用户态：
  ① 应用调用 read(fd, buf, n)
  ② libc 封装：把参数放入寄存器，系统调用号放入 rax
  ③ 执行 syscall 指令
        │  CPU 硬件：切换到内核态，跳转内核入口
内核态：
  ④ entry_SYSCALL_64：保存用户态现场
  ⑤ 查系统调用表 sys_call_table[rax]
  ⑥ 调用 sys_read 处理函数（参数校验、执行）
  ⑦ 结果写入 rax，恢复现场
        │  sysret 指令：切换回用户态
用户态：
  ⑧ read() 返回
```

**关键**：①→② 在用户态，③ 是硬件切换点，④→⑦ 在内核态，⑧ 回到用户态。**全程一次模式切换（user→kernel→user）**。

## 2 参数传递：寄存器约定

系统调用与普通函数调用不同——**它不用栈传参，用寄存器**：

- **rax**：系统调用号（`read` = 0、`write` = 1、`open` = 2）。
- **rdi/rsi/rdx/r10/r8/r9**：第 1~6 个参数。
- **返回值**：写入 rax；负值表示错误（`errno`）。

```c
// syscall 指令的 libc 封装（概念）
long read(int fd, void *buf, size_t count) {
    long ret;
    asm volatile("syscall"
        : "=a"(ret)
        : "a"(__NR_read), "D"(fd), "S"(buf), "d"(count)
        : "rcx", "r11", "memory");
    return ret;
}
```

**为什么用寄存器**：进入内核前**不能依赖用户栈**（内核栈是另一套）——寄存器是「跨模式传递参数」的最可靠方式。**参数数量上限 6 个**，超过则用内存传递。

**辨析｜易错点：** 「系统调用参数压栈」是常见误解。**系统调用参数走寄存器（而非用户栈）**——因为切换模式后用户栈不可信。**「rax = 系统调用号」是内核找到处理函数的钥匙**（回顾系统调用表）。

## 3 内核入口：从 `syscall` 到处理函数

`syscall` 指令执行后，硬件做三件事：

1. **切换模式位**：用户态 → 内核态。
2. **保存返回地址**：把下一条指令地址存入 `rcx`（供 `sysret` 用）。
3. **跳转固定入口**：跳到 MSR（`LSTAR`）指定的内核入口——`entry_SYSCALL_64`。

**入口函数做的事**：

- 保存用户态寄存器（现场）。
- 切换到**内核栈**。
- 从 rax 取系统调用号，**查系统调用表**：

$$\text{处理函数} = sys\_call\_table[\text{rax}]$$

- 校验：系统调用号是否越界（合法范围）。
- 调用处理函数（如 `sys_read`），处理函数做**参数校验**（指针是否在用户空间、fd 是否合法）再执行。
- 结果放回 rax，恢复现场，执行 `sysret` 返回用户态。

**系统调用表（sys_call_table）**：一张「系统调用号 → 内核函数指针」的表（见《系统调用表》）。**它是「号码」与「实现」的映射**——用户传号，内核查表。

**设计启示**：整个机制的本质是「**用寄存器传递 + 用硬件翻模式 + 用表寻址**」——每一项都为了「安全 + 快」：寄存器传参快且跨模式可靠，硬件切模式快且不可伪造，表寻址让系统调用可扩展（新调用 = 加表项）。

## 4 核心对比表：系统调用 vs 函数调用（Linux 视角）

| 维度 | 普通函数调用 | Linux 系统调用 |
| --- | --- | --- |
| 模式 | 全程用户态 | 用户↔内核切换 |
| 触发 | `call` 指令 | `syscall` 指令 |
| 参数传递 | 栈 + 寄存器 | 寄存器（rax 装调用号） |
| 目标定位 | 函数地址 | sys_call_table[rax] |
| 开销 | 纳秒级 | 数百纳秒~微秒 |
| 安全校验 | 无（信任） | 内核强制校验 |

**辨析｜易错点：** 「系统调用每次都要查磁盘/设备」是误解。**系统调用是「进入内核」的机制，执行什么取决于调用号**——`getpid()` 系统调用可能只是读内核变量（微秒级）；`read()` 才可能触发 I/O。**「系统调用慢」主要慢在模式切换本身，不是慢在「调用即 I/O」。**

## 5 小结

- 系统调用完整路径：**库封装 → 寄存器装参 → syscall → 硬件切模式 → 查表 → 处理 → sysret 返回**。
- 参数走**寄存器**：rax = 系统调用号，rdi/rsi/rdx = 参数，返回在 rax。
- `syscall` 指令由硬件完成模式切换，跳到内核固定入口。
- 内核查 **sys_call_table[rax]** 找到处理函数，做参数校验后执行。
- 系统调用慢在**模式切换本身**，不是「调用即 I/O」。
