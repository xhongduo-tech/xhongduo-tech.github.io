## 为什么从无锁编程开始

Mutex 与信号量统治了并发半个世纪，但它们都有个共同问题：**抢不到锁就要睡眠，睡眠就要上下文切换**。在高并发、短临界区场景，睡眠的代价反而成了瓶颈。于是诞生了**无锁编程（lock-free programming）**——不用锁，靠 CAS 等原子指令「乐观重试」，让线程从不睡眠。这一篇我们看无锁的甜头，也看它的两个著名陷阱：ABA 问题与优先级反转。<span class="marginnote">回顾《硬件同步原语》：CAS 是「比较-条件写」原子指令，无锁编程的基石。它把「加锁-改-解锁」变成「读-试-重试」——代价是可能做无用功，收益是从不睡眠。</span>

## 1 无锁编程：乐观的循环

**无锁编程**：不使用互斥锁，而用原子指令（CAS、fetch-add）直接操作共享数据。若操作失败（并发改动），重试而非等待。

经典的无锁栈（Treiber 栈）核心：

```c
void push(Node *node) {
    Node *old;
    do {
        old = top;              // 读当前栈顶
        node->next = old;       // 新节点的 next 指向当前栈顶
    } while (!CAS(&top, old, node));  // 若 top 没变则换成 node，否则重试
}
```

**无锁的本质**：不「等」，而是「试」。CAS 失败说明别人动了，重读重试即可。优点是：

- **不睡眠、不切换**：线程永远在跑，没有上下文切换开销。
- **无死锁**：没有锁，就没有「持锁等待」的死锁结构。
- **可扩展性好**：高并发下性能更平滑（锁是「所有人排队」，无锁是「各自尝试」）。

代价：

- **编程极难**：无锁数据结构的正确性极难证明。
- **活锁可能**：极端情况下所有线程反复重试，谁也没进展。
- **ABA 陷阱**（见下节）。

**辨析｜易错点：** 「无锁 = 无等待 = 更快」是过度简化。**无锁在「低竞争」时接近原子操作、在「高竞争」时可能因为疯狂重试而变慢**；且无锁代码极难写对，**能用锁解决就别用无锁**——它是「锁成为瓶颈」时的备选，不是默认选项。<span class="marginnote">工程上的铁律：先测量，再优化。绝大多数并发代码用锁就够；只有当剖析证明锁的睡眠/切换是瓶颈（如超高频计数器、日志热点），才值得上无锁。Go 的 `sync/atomic`、Java 的 `AtomicInteger` 是「安全用无锁」的入口。</span>

## 2 CAS 的 ABA 问题：恶魔藏在中间态

**ABA 问题**：CAS 比较的是「值相等」，但**值相等不代表「没变过」**——值可能从 A 变成 B 再变回 A，CAS 误以为「没人动过」，于是成功写入，造成错误。

无锁栈的 ABA 实例：

1. 线程 X 读 `top = A`。
2. 线程 Y 弹出 A，又压入新节点 A'（地址恰好复用 A），再弹出，栈顶回到 A。
3. X 的 CAS 比较 `top == A` → 相等 → 写入新节点。
4. 但 `A->next` 已经被 Y 改过（或 A 已被释放），X 写入的链表是**悬空/损坏的**。

**A → B → A 的中间变化被 CAS 的「只看当前值」蒙蔽了**。

防御手段：

- **带版本号的原子指针**：`std::atomic<T*>` 不行，要用「指针 + 版本计数器」打包成 128 位原子量（`std::atomic<double_width>` / Java `AtomicStampedReference`）——每次修改版本号 +1，CAS 同时比较「值 + 版本」。
- **风险内存管理（hazard pointers）**：保证被弹出的节点不立即释放，杜绝地址复用。
- **把 ABA 改造成「逻辑上不可能」**的结构（如避免释放与复用）。

**辨析｜易错点：** 「ABA 只在无锁栈里有」是误解。**任何依赖「CAS 值相等即未变」的并发结构都可能中招**——只要存在「改走又改回」的可能。数据库乐观锁里的版本号、Redis 的 WATCH 都是同一防御思想的体现。

## 3 优先级反转：高优先级进程被低优先级拖死

**优先级反转（priority inversion）**：一个高优先级进程被一个低优先级进程（间接）阻塞的异常现象——高优先级要拿的锁，被低优先级进程持有，而低优先级进程又正被中等优先级进程抢占，于是高优先级进程反而等最久。

经典场景：

1. 低优先级 L 持有锁。
2. 高优先级 H 到达，想拿锁，阻塞等待 L 释放。
3. 中等优先级 M 到达（M 不需要锁），抢占 L——L 无法运行，锁无法释放。
4. H 被「最不重要」的 M 无限期拖住。

**危害**：在实时系统里，这等于「最紧急的任务被最不紧急的任务拖死」——火星探路者号（Mars Pathfinder，1997）曾因优先级反转频繁复位系统，是这一问题的著名事故。<span class="marginnote">火星探路者的故障复盘催生了「优先级继承」在实时内核中的普及。事故根因：一个共享内存总线上的低优先级任务持锁，被高优先级通信任务等待，中间任务抢占导致反转。工程界由此把优先级继承写进了 POSIX 实时扩展。</span>

**两种对策**：

- **优先级继承（priority inheritance）**：低优先级进程持有锁时，**临时继承**等待者的最高优先级，直到释放锁。这样 M 抢不动 L，L 尽快完成，H 尽快获锁。
- **优先级置顶（priority ceiling）**：持有锁的进程直接把优先级抬到「可能访问该锁的所有进程的最高优先级」。

Linux 的 `pthread_mutex` 支持 `PTHREAD_PRIO_INHERIT` 属性，实时系统（RT-Linux、VxWorks）普遍启用优先级继承。

## 4 核心对比表：无锁与锁的战争

| 维度 | 互斥锁 | 无锁（CAS 循环） |
| --- | --- | --- |
| 等锁方式 | 睡眠/自旋 | 失败重试 |
| 上下文切换 | 有（睡眠唤醒） | 无 |
| 死锁 | 可能 | 结构性无死锁 |
| 编程难度 | 低 | 极高 |
| ABA 风险 | 无 | 有 |
| 适用 | 默认选择 | 锁为瓶颈的高并发热点 |

## 5 小结

- **无锁编程**用 CAS 循环「读-试-重试」，不睡眠、无死锁，但极难写对。
- **ABA 问题**：值「A→B→A」让 CAS 误判未变，导致链表悬空；用**版本号**或风险指针防御。
- **优先级反转**：高优先级被低优先级持锁、再被中优先级抢占而无限等待。
- 对策：**优先级继承**（持锁者临时继承高优先级）与**优先级置顶**。
- 工程铁律：**先测量再上无锁**，锁能解决就用锁。
