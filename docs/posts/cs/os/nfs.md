## 为什么从 NFS 开始

文件共享的工程实现，最经典的是 **NFS（Network File System）**。它由 Sun 在 1984 年提出，如今是 Unix/Linux 世界网络文件共享的事实标准。NFS 架构回答三个问题：**文件系统怎么跨网络暴露？客户端怎么访问？崩溃/断电怎么处理？** 它是「网络 × 文件系统」交叉地带的完美案例。<span class="marginnote">回顾《文件共享》：NFS 是「远程文件访问」的代表——服务器集中存数据，客户端挂载后透明访问。回顾《文件系统层次结构》：NFS 挂在 VFS 之下，是 VFS 的一个「插件文件系统」——应用无感知。</span>

## 1 NFS 的架构：服务器 + 客户端

**NFS（Network File System）**：一种分布式文件系统协议，让客户端像访问本地文件一样访问**远程服务器**上的文件。

**两部分**：

- **NFS 服务器**：导出（export）若干目录，管理真实文件数据。
- **NFS 客户端**：挂载服务器导出的目录，通过 RPC 向服务器发起文件操作。

**工作流程**：

1. 服务器配置导出：`/etc/exports`（exports 文件）。
2. 客户端挂载：`mount -t nfs 192.168.1.10:/data /mnt`。
3. 客户端访问 `/mnt` 下的文件 → 通过 **RPC**（回顾 RPC）发给服务器 → 服务器在 `/data` 上执行 → 返回结果。

**协议分层**（NFS 栈）：

```
客户端                                  服务器
──────────────────────────            ──────────────────────────
应用（VFS：通用文件接口）
NFS 客户端（文件操作 → RPC 调用）
RPC / XDR（远程过程调用与序列化）
TCP/IP ──────────── 网络 ────────────  TCP/IP
                                        RPC / XDR
                                        NFS 服务器（执行远程操作）
                                        本地文件系统（ext4/XFS）
```

**关键点**：客户端与服务器都是「VFS 下的一个文件系统」——**NFS 客户端是「网络文件系统」，NFS 服务器是「把本地目录导出」**。两边都通过 RPC 通信。

## 2 无状态协议：NFS 的可靠性哲学

**NFS 的核心设计（早期 NFSv2/v3）**：**无状态（stateless）服务器**。

- 服务器**不记住**客户端「打开了哪些文件、位置在哪」——每次 RPC 请求自带完整参数（文件句柄、偏移、长度）。
- 服务器崩溃后重启：**不需要恢复任何会话状态**——客户端重发请求即可继续。

**优点**：

- **崩溃恢复简单**：服务器无状态，重启即恢复服务，客户端感知不到。
- **服务器可水平扩展**：无状态意味着任意服务器都能响应任意请求。

**代价**：

- **客户端要做更多**：自己维护打开文件的状态、缓存、写回。
- **一致性弱**：缓存与无状态结合 = 弱一致性（回顾《文件共享》的 NFS 语义）。

**NFSv4 的转向**：现代 NFSv4 引入**有状态**（open 状态、锁、回调），支持更复杂的语义（文件锁、委托）与更好的缓存一致性——**「无状态的简单」让位给「有状态的强大」**。

**辨析｜易错点：** 「NFS 客户端读文件每次都要走网络」是误解。**NFS 客户端有本地缓存**（页缓存）——读过的块留在缓存，命中就不发 RPC；缓存一致性靠「检查服务器是否修改」（属性缓存 + 定时检查）。**「每次访问都走网络」是无缓存时代的旧 NFS，现代 NFS 大量依赖客户端缓存。**

## 3 文件句柄与挂载协议

**文件句柄（file handle）**：NFS 中标识「一个文件」的不透明标识——由文件系统标识、inode 号、世代号（generation）组成。RPC 请求用文件句柄代替路径（路径解析已在打开时完成）。

**挂载协议（mount protocol）**：

1. 客户端向服务器发挂载请求（路径）。
2. 服务器返回**根文件句柄**。
3. 客户端用根句柄 + 相对路径逐步解析，最终拿到目标文件句柄。

**幂等性（idempotency）**：NFS 用幂等操作应对网络重传——`read`/`write`（带偏移）是幂等的（同一请求重发结果相同），服务器可安全处理重传；非幂等操作（如 `create`）需要谨慎处理重复。

**数值算例：一次 NFS read 的完整往返**。客户端读文件偏移 4096 处的 8 KB（2 个页），缓存未命中：

1. 应用发起 `read(fd, buf, 8192)`。
2. NFS 客户端查页缓存未命中 → 构造 RPC 请求：文件句柄 + 偏移 4096 + 长度 8192。
3. RPC 经 XDR 序列化 → TCP 发往服务器（本地网络约 0.1–1 ms 一跳）。
4. 服务器解包 → 在本地文件系统读 8 KB → 序列化返回。
5. 客户端把结果填入页缓存 → 应用拿到数据。

**观察**：一次未命中读 ≈ 1 个 RPC 往返（网络延迟 ×2 + 服务器本地读）；而命中缓存时**零网络开销**。<span class="marginnote">这就是 NFS 性能的平衡点：缓存命中率决定「网络延迟」被摊薄多少。读多写少的负载（源码树、配置文件）命中率高，NFS 体验接近本地；纯随机大量写入则频繁刷新，往返成本暴露无遗。</span>现代 NFS 的页缓存把「每次访问都走网络」变成了「只有缓存未命中才走网络」。

**崩溃恢复的数值直觉**：无状态服务器重启只需秒级——它不保存任何会话。若客户端正写一半时服务器崩溃，客户端只需在服务器恢复后**重发未确认的请求**；写操作带偏移、幂等，重发不会造成重复写入。<span class="marginnote">对比有状态协议（如 SMB 早期）：服务器要记住打开文件列表，崩溃后必须重建会话状态，恢复逻辑复杂得多。</span>「无状态 + 幂等」把崩溃恢复从「恢复会话」简化成「重发请求」——这是分布式系统里最优雅的取舍之一。

## 4 核心对比表：NFS 分层组件

| 层 | 职责 | 关键机制 |
| --- | --- | --- |
| 客户端 VFS | 挂载、路径解析 | dentry/inode 缓存 |
| NFS 客户端 | 翻译文件操作 | RPC 调用、句柄 |
| RPC/XDR | 远程过程调用与数据编码 | XDR 序列化 |
| NFS 服务器 | 执行远程操作 | 导出目录、句柄管理 |
| 服务器 VFS | 落到本地文件系统 | ext4/XFS |

**设计启示**：NFS 展示了「**用分层协议解决跨网络问题**」的范式——每个层次只做一件事，层间用明确定义的接口（RPC + XDR）通信。这与《计算机网络》的协议分层、VFS 的插件式文件系统完全同构。**「无状态 + 幂等 + 缓存」是 NFS 可靠性的三支柱**——这套组合在分布式系统里被反复使用。

**术语速查表**：

| 术语 | 含义 |
| --- | --- |
| export | 服务器导出的目录（`/etc/exports`） |
| mount | 客户端挂载远程目录 |
| RPC | 远程过程调用，客户端—服务器通信基础 |
| XDR | 外部数据表示，跨机数据序列化格式 |
| 文件句柄 | 标识远程文件的不透明标识 |
| 幂等操作 | 重复执行结果不变（可安全重传） |
| 无状态服务器 | 不保存客户端会话状态（v2/v3） |

## 5 小结

- **NFS**：服务器导出目录、客户端挂载访问，经 **RPC** 通信。
- 客户端与服务器都是 VFS 下的文件系统——「网络文件系统」与「本地导出」。
- **无状态服务器**（v2/v3）：崩溃恢复简单、可水平扩展；v4 转向有状态（锁、委托）。
- **文件句柄**替代路径做远程标识；操作**幂等**以应对重传。
- 客户端有缓存（弱一致），「无状态 + 幂等 + 缓存」是 NFS 可靠性的三支柱。
