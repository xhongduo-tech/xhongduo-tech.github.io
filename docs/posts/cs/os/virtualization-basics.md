## 为什么从虚拟化基础开始

回顾《虚拟机与 Hypervisor》——本篇（第十八篇）在 Linux 上深入虚拟化与容器。这一节先立框架：**虚拟化的三种实现方式**——全虚拟化、半虚拟化、硬件辅助虚拟化。它们的区别核心是「**客户 OS 是否知道自己是虚拟机、特权指令怎么处理**」。这是理解 KVM、QEMU 与容器隔离的坐标原点。<span class="marginnote">回顾《Hypervisor》：Type-1 直接管硬件、Type-2 跑在宿主上。虚拟化方式的划分是「<strong>如何让客户 OS 的特权指令被安全截获</strong>」——全虚拟化用二进制翻译、半虚拟化让客户配合、硬件辅助用 CPU 扩展。<strong>「指令截获」是虚拟化的核心难题。</strong></span>

## 1 虚拟化的核心难题：特权指令

**客户 OS（guest OS）**以为自己独占机器——它会执行**特权指令**（关中断、改页表、读写特权寄存器）。但客户 OS 运行在**用户态/低特权级**（被 hypervisor 控制），特权指令会**触发异常**——hypervisor 必须**截获并模拟**这些指令。

**Popek-Goldberg 定理**（1974）：如果指令集架构的**敏感指令（sensitive instructions）都是特权指令**（在低特权级执行会 trap），则可以用「**陷入-模拟（trap-and-emulate）**」实现高效虚拟化。**问题是：x86 早期并非如此**——部分敏感指令在低特权级**静默失败**（不 trap），导致「陷入-模拟」失效。这正是三种虚拟化方式要绕开的坑。

## 2 三种虚拟化方式

**① 全虚拟化（full virtualization）**：

- 客户 OS **不知道自己被虚拟化**（无需修改）。
- hypervisor 用**二进制翻译（binary translation）**：把客户 OS 的敏感指令**动态替换**成安全调用序列。
- **优点**：客户 OS 不改，兼容最好。
- **缺点**：翻译有开销——早期性能差。VMware Workstation（软件）是代表。

**② 半虚拟化（paravirtualization）**：

- 客户 OS **知道自己被虚拟化**，主动**配合**——把特权操作改成「调用 hypervisor 接口」（hypercall）。
- **优点**：性能好（不用翻译，直接调用）。
- **缺点**：**客户 OS 必须修改**——Linux 要编入 paravirt 支持，Windows 不支持（封闭）。
- Xen 是代表——客户 OS 通过 `hypercall`（陷入指令）请求特权操作。

**③ 硬件辅助虚拟化（hardware-assisted）**：

- **CPU 提供虚拟化扩展**：Intel **VT-x**、AMD **SVM**——新增「**根模式/非根模式**」。
- 客户 OS 运行在**非根模式**，特权指令**自动陷入根模式**（hypervisor）——**不需要翻译、不需要改客户 OS**。
- **优点**：**性能接近原生 + 客户 OS 不改**——现代虚拟化的标准。
- KVM + QEMU 就是硬件辅助虚拟化（见下篇）。

**公式解析：三种方式的「陷阱成本」**

设一次特权操作的成本：

$$\text{全虚拟化} = T_{翻译} + T_{trap}, \qquad \text{半虚拟化} = T_{hypercall}, \qquad \text{硬件辅助} = T_{VMEXIT}$$

- **全虚拟化**：二进制翻译（慢）+ 陷入。
- **半虚拟化**：客户主动 hypercall（快，但要改客户）。
- **硬件辅助**：VMEXIT（CPU 硬件快速陷入，接近原生）。
- **硬件辅助用「硬件扩展」同时获得「不改客户 + 快」**——所以它胜出。

**直觉**：三种方式是「**谁来处理特权指令**」的三答案——**翻译（hypervisor 软件）、配合（客户主动）、硬件（CPU 扩展）**。硬件辅助让 CPU 直接支持「客户模式」，是成本最低、兼容最好的方案。<span class="marginnote">x86 虚拟化的「先难后易」史：早期因「敏感指令不 trap」而只能用翻译（全虚拟化），Xen 用「改客户」（半虚拟化）绕开，Intel/AMD 随后把「陷入」做进 CPU（VT-x/SVM），一劳永逸。<strong>「硬件把软件难题做掉」是性能优化的终极形态</strong>——你在 TLB、原子指令、futex 上看到的都是同一条路。</span>

## 3 对比：三种方式

| 维度 | 全虚拟化 | 半虚拟化 | 硬件辅助 |
| --- | --- | --- | --- |
| 客户 OS 修改 | 不需要 | **需要** | 不需要 |
| 特权指令处理 | 二进制翻译 | hypercall | **VMEXIT（硬件）** |
| 性能 | 差（翻译开销） | 好 | **接近原生** |
| 兼容性 | 最好 | 差（OS 要改） | 好 |
| 代表 | 软件 VMware | Xen | **KVM/QEMU** |

**辨析｜易错点：** 「KVM 是全虚拟化」是常见简化。**KVM 是硬件辅助虚拟化**——它依赖 VT-x/SVM 的根/非根模式；KVM 内部也可以用半虚拟化优化（如 virtio 设备、`kvm-clock` 半虚拟化时钟）。**「KVM = 硬件辅助为主 + 半虚拟化设备为辅」**。另一个易错点：**「半虚拟化已淘汰」**——半虚拟化的思想（客户配合、hypercall）在现代仍然重要：virtio、`kvm-clock`、容器的 vDSO 都有它的影子。

## 4 核心对比表：三种方式的选择

| 场景 | 推荐 | 理由 |
| --- | --- | --- |
| 兼容一切 OS | 硬件辅助（KVM） | 不改客户 + 快 |
| 极致性能、可改客户 | 半虚拟化设备 | 减少虚拟化开销 |
| 教学/无硬件支持 | 全虚拟化（软件） | 无需 CPU 扩展 |

## 5 小结

- 虚拟化核心难题：**特权指令如何被截获**——Popek-Goldberg 定理给出「陷入-模拟」的理论条件。
- **全虚拟化**：二进制翻译敏感指令，不改客户但慢。
- **半虚拟化**：客户主动 hypercall 配合，快但必须改客户。
- **硬件辅助**：VT-x/SVM 的根/非根模式，VMEXIT 快且不改客户——**现代标准**。
- 半虚拟化的思想仍在：virtio 设备、hypercall 是现代虚拟化的补充。
