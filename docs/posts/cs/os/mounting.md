## 为什么从挂载开始

文件系统不是只有一个——每个磁盘分区、每块 U 盘、每个网络共享都是**独立的文件系统**，各自有根目录。用户要访问它们，必须先**挂载（mount）**：把某个文件系统「接进」当前目录树的某个位置。挂载是「多文件系统如何组成一个统一命名空间」的机制。<span class="marginnote">回顾树形目录：一棵树只有一个根（`/`）。但系统里实际有多个文件系统（根分区、`/home` 分区、U 盘、NFS 共享）——挂载让这些「独立的树」都「长在」主树的节点上，用户无感知地访问。</span>

## 1 挂载的基本概念

**挂载（mount）**：把一个文件系统连接到当前目录树的某个已存在目录上，使该目录成为访问这个文件系统的入口。

- **挂载点（mount point）**：被挂载文件系统所连接的目录。如把 U 盘挂到 `/mnt/usb`，则访问 `/mnt/usb` 就是访问 U 盘。
- **设备（device）**：被挂载的存储源——`/dev/sda1`（分区）、`/dev/nvme0n1`（SSD）、`server:/export`（网络文件系统）。

```bash
$ mount /dev/sdb1 /mnt/usb      # 把 U 盘（/dev/sdb1）挂载到挂载点 /mnt/usb
$ mount                          # 查看挂载表
```

**挂载后的效果**：`/mnt/usb` 及其子路径的访问全部落到 `/dev/sdb1`（U 盘）这个文件系统上——用户只看到一个统一的目录树，感觉不到「不同文件系统」的边界。

## 2 挂载表与挂载语义

**挂载表（mount table）**：内核维护的「哪些设备挂到了哪些挂载点」的记录。Linux 中 `/proc/mounts`、`/etc/fstab`（开机自动挂载配置）都是挂载表的呈现。

**挂载的语义细节**：

- **覆盖**：挂载点目录**原本的内容在挂载期间被隐藏**（被新文件系统的根覆盖）；卸载后原内容恢复。
- **嵌套挂载**：可以在已挂载的文件系统内部再挂载别的文件系统——挂载树是递归的。
- **同设备多次挂载**：同一设备可挂到多个挂载点（访问同一内容）。

**辨析｜易错点：** 「挂载点目录必须是空目录」是常见误解。**挂载点可以是任意目录，不要求空**——挂载后该目录原有内容被「遮蔽」，卸载后重现。**危险在于：把重要设备挂到非空目录，会「看不见」原目录内容，若往里写数据，写进了新文件系统，原目录内容没被破坏但被隐藏**——这是误操作事故的常见来源。

## 3 挂载与引导：根文件系统怎么来

引导时有个「鸡生蛋」问题（回顾《引导与启动》）：**挂载需要文件系统驱动，而根文件系统本身也要被挂载**。

Linux 的解决：`initramfs`（初始内存根文件系统）——引导时先挂载内存中的迷你根，它包含挂载真实根所需的驱动；然后挂载真实根、`pivot_root` 切换。

**多文件系统的挂载顺序**（mount order）：根 `/` 最先挂载，之后按依赖顺序挂载其他（`/boot`、`/home`、NFS 等）。

## 4 核心对比表：挂载的常见文件系统类型

| 文件系统 | 用途 | 特点 |
| --- | --- | --- |
| ext4 | Linux 根分区 | 日志、成熟稳定（见 ext4 篇） |
| XFS | 大文件、高吞吐 | 优秀的扩展性 |
| tmpfs | 临时文件 | 基于内存，重启即失 |
| proc/sysfs | 内核信息 | 虚拟文件系统，非磁盘 |
| NFS | 网络共享 | 跨机器文件访问 |
| FAT32/exFAT | U 盘、跨平台 | 兼容性最好 |

**设计启示**：挂载机制让「存储设备」与「目录树」解耦——**设备可以热插拔、可以换，目录结构不动**。这种「逻辑命名空间 vs 物理设备」的分离，与「逻辑地址 vs 物理地址」的解耦如出一辙：**系统设计的精髓在于分层与解耦**。

## 5 小结

- **挂载**：把文件系统接到目录树某节点（挂载点），统一命名空间。
- 挂载点目录**原有内容被遮蔽**，卸载后恢复——不要求空目录。
- **挂载表**记录「设备 → 挂载点」映射（`/proc/mounts`、`/etc/fstab`）。
- 根文件系统经 `initramfs` 引导挂载，解决「先有鸡还是先有蛋」。
- 挂载实现「设备与目录树解耦」，热插拔不影响命名空间。
