## 为什么从进程间通信开始

前面我们强调进程彼此隔离——每个进程有独立地址空间，一个进程不能直接读写另一个进程的内存。但隔离不是目的，协作才是：shell 要把命令结果传给管道后的程序，数据库要响应客户端的查询，浏览器标签页之间要同步状态。**隔离是前提，通信是需求**。进程间通信（IPC）正是「在隔离的进程之间搭桥」的全部学问。<span class="marginnote">IPC 的两种基本范式——共享内存与消息传递——不仅统治经典 OS，也是现代一切分布式系统通信设计的原型。你在《计算机网络》与《分布式系统》里看到的 RPC、消息队列，都是本篇概念的远亲。</span>

## 1 IPC 的两种基本模型

**进程间通信（IPC, Inter-Process Communication）**：让独立进程之间交换数据与同步动作的机制。按「数据怎么到对方手里」，IPC 分两大类：

**共享内存（shared memory）**：多个进程把同一块物理内存映射进各自地址空间，一方写、一方读，数据直接可见。
**消息传递（message passing）**：进程通过内核提供的「邮局」互发消息，数据由内核搬运，进程之间不共享任何内存。

用比喻：共享内存是「共同挂一块白板」，谁都能写、谁都能读；消息传递是「互寄信件」，发信人把信交给邮局（内核），收信人从邮局取信。<span class="marginnote">共享内存 = 同步 + 合作靠进程自己；消息传递 = 通信 + 同步都由内核保证。共享内存更快但更危险，消息传递更安全但更慢——这个权衡贯穿整个 IPC 专题。</span>

## 2 共享内存：最快的方式

**共享内存**要求进程显式声明「这块区域我们共用」，之后通信就是普通内存读写。

生产者的典型写法（概念示意）：

```c
/* 生产进程：写入共享内存 */
int fd = shm_open("/share", O_CREAT | O_RDWR, 0600);
ftruncate(fd, SIZE);
char *p = mmap(NULL, SIZE, PROT_READ | PROT_WRITE,
               MAP_SHARED, fd, 0);
strcpy(p, "hello");        /* 直接写，消费者立即可见 */
```

共享内存的**优点**是快：数据不经过内核拷贝，一旦建立映射，读写就是普通访存。**缺点**是难：读与写谁先谁后、缓冲区满没满，全靠进程自己用同步原语协调——这就是第六篇《进程同步》要解决的问题；若不加同步，就会出现竞态条件。

**辨析｜易错点：** 「共享内存 = 不用同步」是完全错误的。恰恰相反，**共享内存是竞态条件的温床**——两个进程同时读写同一变量，结果取决于指令交错的顺序。共享内存只负责「看得见」，不负责「不乱来」；同步是用户程序的责任。

共享内存的经典应用是**生产者—消费者**：生产者往缓冲区写、消费者从缓冲区读，用信号量/互斥锁协调「满/空」状态（第六篇《进程同步》会系统展开）。用共享内存实现的生产者—消费者吞吐极高，是消息队列、网络栈等一切高性能数据通路的内核思路——Redis 的多进程通信、浏览器的多进程渲染、数据库的共享缓存，本质都是「共享内存 + 同步」这套组合。

## 3 消息传递：更安全的方式

**消息传递**中，进程之间不共享内存，通过内核中转消息。核心操作两个：**`send`（发送）** 与 **`receive`（接收）**。消息传递机制按三对性质分类：

**同步性**：阻塞式（send 等对方 receive 完才返回）vs 非阻塞式（send 发出即返回）。
**定址方式**：直接定址（指定对方进程号）vs 间接定址（发到共享的「信箱」）。
**缓冲容量**：零容量（必须握手）、有界容量、无界容量。

**三对性质的实际组合**：具体机制就是这三个旋钮的取值。Linux 的**管道**是「阻塞 + 间接定址（无名字）+ 有界容量」；**消息队列**是「可选阻塞 + 间接定址（有名字）+ 有界容量」；而普通 `read`/`write` 系统调用则是「同步 + 直接定址 + 由文件缓冲」。**拿到一个 IPC 机制，先问这三个旋钮怎么拨**，它就在整个消息传递家族里定了位——下一节的管道、FIFO、消息队列、共享内存段都会按这个框架展开。

消息传递的**优点**是安全与简单：内核隔离消息、自动同步、适合分布式环境（两个进程可以不在同一台机器）。**缺点**是慢：每次通信都要复制进内核再复制出内核，两次拷贝。

**消息传递与分布式系统**：消息传递不要求双方在同一台机器，这正是它成为分布式系统通信基石的原因。RPC（远程过程调用）、消息队列（Kafka/RabbitMQ）、微服务之间的 HTTP 调用，都是「消息传递」思想在不同抽象层的体现——你将在《计算机网络》里学的网络协议，本质就是跨机的消息传递：报文在主机间传递，协议栈扮演「跨机邮局」的角色。**同一套「发消息、收消息、内核/协议栈中转」的骨架，从单机一直延伸到全球互联网。**<span class="marginnote">「消息要过内核」是消息传递慢的根源。本专题 Linux 篇里 <code>io_uring</code>`、<code>sendfile</code>` 等一切优化，本质上都在「减少进内核的次数」。而共享内存建立后可以完全不过内核，这就是它快的根本原因。</span>

## 4 核心对比表：共享内存 vs 消息传递

| 维度 | 共享内存 | 消息传递 |
| --- | --- | --- |
| 数据搬运 | 直接访存，零拷贝 | 经内核两次拷贝 |
| 速度 | 最快 | 较慢 |
| 同步责任 | 用户进程自己负责 | 内核内置 |
| 编程难度 | 高（易出竞态） | 低（原语清晰） |
| 适用场景 | 同一台机器、高频协作 | 跨机、低频或要求隔离 |
| 典型实现 | POSIX `shm_open`、`mmap` | 管道、消息队列、套接字 |

**设计启示**：两种模型并非二选一。现代系统常混合使用——`mmap` 映射文件兼得共享内存的速度与文件系统的持久化；高性能消息库（如 ZeroMQ）在内部用共享内存加速消息传递。**「快与安全」的权衡是理解所有 IPC 具体机制的主线。**

## 5 数值算例：共享内存比消息传递快多少

设两个进程要来回传 1 KB 数据，各自的开销模型如下：

| 通信方式 | 每次传输的开销 | 说明 |
| --- | --- | --- |
| 共享内存 | 约 0.1–0.5 μs | 映射建立后是纯访存，无内核介入 |
| 消息传递 | 约 10–20 μs | 两次内核拷贝 + 两次上下文切换 |

消息传递的 10–20 μs 里，大头是：数据**拷进内核再拷出内核**（两次 memcpy），加上 send/receive 各一次**模式切换与调度**。共享内存把这四步全部省掉——代价是建立映射的一次性开销（`shm_open` + `mmap` 约几十微秒）以及后续**同步责任全归自己**。

**选择判据**：高频、小数据、长时间协作 → 共享内存值得（一次性建映射摊薄后很划算）；低频、大数据、或要求强隔离 → 消息传递更省心。**「快与安全」的权衡是理解所有 IPC 具体机制的主线**——这句话在后面的每一篇（管道、消息队列、套接字）都会反复验证。

## 6 术语速查

| 术语 | 含义 |
| --- | --- |
| 进程间通信（IPC） | 独立进程之间交换数据与同步动作的机制 |
| 共享内存 | 多进程映射同一块物理内存，直接读写 |
| 消息传递 | 经内核中转的消息收发，数据不共享 |
| 竞态条件 | 多进程同时读写共享数据，结果取决于交错顺序 |
| 阻塞式 send | 对方 receive 完成后才返回 |
| 直接定址 | 消息指定接收进程号 |
| 间接定址 | 消息发往共享信箱，由信箱转交 |

## 7 小结

- IPC 两大范式：**共享内存**（直接可见、最快、需自己同步）与**消息传递**（内核中转、安全、较慢）。
- 共享内存把「可见」与「同步」分离，同步完全交给用户，是竞态温床。
- 消息传递按**同步性、定址方式、缓冲容量**三对性质分类。
- 共享内存零拷贝所以快，消息传递过内核所以安全；两者常被混合使用。
- 数值：1 KB 来回传，共享内存约 0.1–0.5 μs，消息传递约 10–20 μs，差一个数量级以上。
- 三个旋钮「同步性、定址方式、缓冲容量」给每个消息传递机制定位。
- 生产者—消费者是共享内存的经典舞台，靠信号量/互斥锁协调满空。
- `mmap` 共享映射是共享内存的标准实现，`shm_open` 打开共享对象。
- 现代系统常混合两者：`mmap` 兼得共享速度与文件持久化，ZeroMQ 用共享内存加速消息传递。
- RPC、消息队列、HTTP 调用都是「消息传递」思想在分布式世界的延伸。
- 消息传递三旋钮——同步性、定址方式、缓冲容量——给具体机制定位。
- 共享内存的代价是竞态风险，消息传递的代价是拷贝与上下文切换。
- `shm_open` + `mmap` 的共享内存路径在 POSIX 里是标准实现。
- 理解 IPC 主线的钥匙：**快 vs 安全的权衡**。
