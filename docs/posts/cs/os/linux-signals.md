## 为什么从信号机制开始

回顾《线程问题》里的信号：它是进程级事件通知。这一节在 Linux 上把它讲透——**信号的产生、递送、处理**三个阶段的完整流程，以及默认动作与自定义处理。<span class="marginnote">回顾《线程问题》：异步信号发进程、同步信号发肇事线程。信号是 Linux 进程通信与控制的古老而重要的机制——<strong>理解「产生→挂起→递送→处理」四阶段，是理解 kill、Ctrl-C、Segfault 的原理</strong>。</span>

## 1 信号的产生：谁在发信号

**信号（signal）**：内核或进程发送给进程的**异步事件通知**。常见信号：

| 信号 | 默认动作 | 触发场景 |
| --- | --- | --- |
| `SIGINT` | 终止 | Ctrl-C |
| `SIGTERM` | 终止 | `kill` 默认 |
| `SIGKILL` | 终止（不可捕获） | 强杀 |
| `SIGSEGV` | 终止 + core | 非法内存访问 |
| `SIGPIPE` | 终止 | 写已关闭的管道 |
| `SIGCHLD` | 忽略 | 子进程终止 |

**信号的产生来源**：

- **硬件异常**：除零（SIGFPE）、非法访问（SIGSEGV）——CPU 触发。
- **终端**：Ctrl-C（SIGINT）、Ctrl-\（SIGQUIT）。
- **软件**：`kill(pid, sig)`、`raise(sig)`、`alarm()` 定时。
- **内核事件**：SIGCHLD（子进程退出）、SIGPIPE。

**产生 ≠ 立即处理**：信号产生后**挂起（pending）**在进程的信号队列里，**稍后才递送**——这是「异步」的本质。

## 2 信号的递送：从挂起到处理

**信号的生命周期**：

```
产生（pending 置位） → 递送（delivered） → 处理（handler）
```

- **挂起（pending）**：信号产生，但进程还没被调度/还没到检查点——存在进程的 pending 位图。
- **递送（delivery）**：进程从内核态返回用户态时，内核检查 pending 信号，**选择一个处理**。
- **处理（handling）**：按信号的处理动作执行。

**阻塞（block）**：进程可以用 `sigprocmask` **屏蔽**某些信号——被屏蔽的信号保持 pending，**不递送**直到解除屏蔽。

**处理动作三种**：

1. **默认动作**：终止、忽略、停止（core dump）。
2. **忽略**：什么都不做（SIGCHLD 默认忽略）。
3. **自定义处理函数**：调用用户注册的 `signal handler`。

**递送时机**：**从内核态返回用户态时**检查并递送——内核态中信号被记录但不立即处理（避免在内核态跑用户代码）。

**公式解析：信号的位图与检查**

进程的 pending 信号用**位图**表示：

$$\text{pending} = \bigcup_{\text{信号} i} \text{bit}_i$$

- 每个信号一位——`SIGINT` 是位 2、`SIGKILL` 是位 9…
- 产生信号 = 置位；递送处理 = 清位。
- **同种信号只记一位**——**同信号多次产生合并为一次**（非实时信号不排队）。

**直觉**：位图让「信号有无」的判断是 O(1) 位运算——内核返回用户态时查 pending 位图即可。**普通信号的「合并」语义**是它不可靠的原因之一：`SIGCHLD` 可能丢了多次（多次子进程退出只记一次），实时信号（RT signals）才排队。

**辨析｜易错点：** 「kill 就是杀死」是常见误解。**`kill(pid, sig)` 是「发信号」**——发 `SIGTERM` 是请求终止（可捕获、可忽略），发 `SIGKILL` 才是强制杀（不可捕获）。**「kill」是历史命名（早期只用于杀），现代是通用信号发送器。**另一个易错点：**SIGKILL 与 SIGSTOP 不可被捕获、阻塞或忽略**——它们是内核保留的「最后一击」。

## 3 信号处理：进入处理函数

**自定义信号处理**：

```c
void handler(int sig) { printf("got %d\n", sig); }
signal(SIGINT, handler);   // 注册处理函数
```

**处理流程**：

1. 进程从内核态返回用户态，发现 SIGINT pending。
2. 内核**保存现场**，跳到 `handler` 执行（用户态）。
3. `handler` 返回后，**恢复现场**，进程从被中断处继续。

**信号处理的限制（异步安全）**：处理函数在「任意时刻」打断主程序——**只能调用异步安全函数**（`write`、`_exit`），**不能调用 `printf`/`malloc`/`lock`**（可能重入导致死锁或损坏——见下一篇《信号处理函数与可重入问题》）。

## 4 核心对比表：信号的三个阶段

| 阶段 | 做什么 | 关键机制 |
| --- | --- | --- |
| 产生 | 置 pending 位 | 硬件异常、kill、终端 |
| 递送 | 从内核返回用户态时检查 | pending 位图 |
| 处理 | 默认/忽略/自定义函数 | handler 执行 |

**设计启示**：信号是「**内核与进程的异步通知协议**」——它让「外部事件（Ctrl-C、子进程退出、硬件错误）」能打断进程的任意执行点。它的**异步性既是能力也是危险**（处理函数随时打断），这引出了信号处理与可重入的经典难题（下一篇）。

## 5 小结

- 信号是异步事件通知，三阶段：**产生（置位）→ 递送（返回用户态检查）→ 处理**。
- 常见信号：SIGINT/SIGTERM/SIGKILL/SIGSEGV/SIGCHLD；`kill` 是「发信号」不是「杀」。
- **阻塞**的信号保持 pending 不递送；同种普通信号合并为一次。
- 处理动作：默认 / 忽略 / 自定义函数；SIGKILL 与 SIGSTOP 不可捕获。
- 信号处理是异步打断——只能调**异步安全**函数。
