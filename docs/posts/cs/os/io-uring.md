## 为什么从 io_uring 开始

epoll 解决了「等就绪」，但它仍是「**同步**」模型——**用户要自己调 read/write**。**io_uring**（Linux 5.1+）把 I/O 推向真正的**异步**：用户提交「读请求」，内核在数据**拷贝完成**后通知——**不只是等就绪，连数据都帮你搬好**。它是 Linux 异步 I/O 的新范式，正在重塑高性能存储与网络。<span class="marginnote">回顾《I/O 模型》：epoll 是「非阻塞 + 同步」——内核通知就绪，用户自己 read；<strong>io_uring 是「异步」——内核通知完成，数据已就位</strong>。io_uring 用「<strong>共享环形队列</strong>」让提交与完成都零系统调用（或极少），是「能不进内核就不进内核」哲学的极致。</span>

## 1 传统异步 I/O 的问题

在 io_uring 之前，Linux 异步 I/O（AIO）有致命缺陷：

- **`libaio` 的 AIO**：对普通文件（buffered I/O）**常常是同步的**——会阻塞；只对 `O_DIRECT` 才真正异步。
- **接口复杂**、限制多、性能一般。

**epoll 的局限**：它只告诉你「**可以读**」——**真正的 `read`/`write` 系统调用仍要你自己做**，且 read 可能再次阻塞（数据没完全就绪）。

**io_uring 的目标**：**真正的、彻底的异步**——**提交请求后，用户完全不用管，内核把数据拷好再通知**。

## 2 io_uring 的机制：两对共享环

**io_uring** 的核心：内核与用户**共享两块环形队列**（通过 mmap 映射）：

- **SQ（Submission Queue，提交队列）**：用户**提交** I/O 请求（写 SQ 项，SQE）。
- **CQ（Completion Queue，完成队列）**：内核**回报**完成结果（写 CQ 项，CQE）。

```text
用户进程                            内核
  │  mmap 映射两块共享环形队列          │
  ▼                                  ▼
┌────────────────────────────────────────┐
│  SQ（提交队列）：用户写 SQE → 内核消费   │
│  CQ（完成队列）：内核写 CQE → 用户读取   │
└────────────────────────────────────────┘
     提交与完成都不再需要逐请求的进程切换
```

**io_uring 的调用方式**：

- **`io_uring_setup()`**：创建 SQ/CQ 环。
- **`io_uring_enter()`**：提交 SQ 中的请求（可批量）。
- **`io_uring_wait_cqe()`**（liburing 封装）：等待完成。
- 现代内核支持 **IORING_SETUP_SQPOLL**：**内核线程轮询 SQ，用户提交请求甚至不需要 `io_uring_enter` 系统调用**——提交也零系统调用。

## 3 为什么 io_uring 快：零拷贝 + 零系统调用

**io_uring 的三重优化**：

**① 批量提交**：一次 `io_uring_enter` 提交多个请求——系统调用次数大幅减少。

**② 真正的异步**：I/O 操作在内核后台执行，数据**拷贝完成**后写 CQE——**用户不用自己 read，不用等就绪**。

**③ SQPOLL 模式**：内核线程**主动轮询** SQ——**用户提交请求不进内核，完成结果不进内核**（读 CQ 也是内存操作）。

**公式解析：io_uring 的系统调用次数**

设处理 $N$ 个请求：

$$\text{传统（每请求）} = N \text{ 次 read/write} + N \text{ 次 epoll}$$

$$\text{io\_uring（批量）} = \lceil \frac{N}{\text{批大小}} \rceil \text{ 次 io\_uring\_enter} + 0 \text{（SQPOLL 时）}$$

- 传统：每请求至少一次系统调用（read）——N 个请求 N 次。
- io_uring：**批量提交**，N 个请求合并成几次系统调用；**SQPOLL 下甚至零系统调用**。
- **系统调用次数的量级下降 = 模式切换开销的消除**（回顾《系统调用指令》每次切换 ~0.5µs）。

**直觉**：io_uring 把「每请求一次系统调用」变成「一批请求一次（甚至零次）」——**这是「批量」思想（回顾《缓冲技术》的攒批）在异步 I/O 上的极致应用**。

**数值算例：一次提交 1024 个请求**。设一个数据库进程要读 1024 个 4 KB 的块：

- **传统 read**：1024 次 `read` 系统调用，每次约 0.5 µs 模式切换 → 仅切换就约 0.5 ms，加上每请求的完成等待。
- **io_uring**：写 1024 个 SQE 进 SQ，**一次 `io_uring_enter` 提交** → 1 次系统调用，内核异步执行；SQPOLL 模式下连这次 `enter` 都省了。
- **系统调用从 1024 次降到 1 次（甚至 0）**——对海量小 I/O 负载（数据库、对象存储、网关），这是数量级的提升。

**代价与前提**：io_uring 的收益来自「能批量、能异步」的负载。零星单请求、需要立即结果的场景，io_uring 的 ring 初始化与复杂度反而更重——**它适合高吞吐、可并发的 I/O 密集场景**。<span class="marginnote">现实中 PostgreSQL、RocksDB、nginx 的高性能分支都已接入 io_uring；而普通小工具直接 read 即可——「复杂机制用在值得的地方」是工程常识。</span>

**辨析｜易错点：** 「io_uring 会淘汰 epoll」是言之过早的论断。**io_uring 与 epoll 解决不同层次的问题**——epoll 是「多路复用」（管一堆连接的等待），io_uring 是「异步 I/O」（提交与完成解耦）。**现代方案常两者结合**：epoll 管连接事件，io_uring 管数据读写。且 io_uring 较新，生态（库、驱动支持）仍在成熟。**「新范式」是方向，「立即取代」是误判。**

## 4 核心对比表：epoll vs io_uring

| 维度 | epoll | io_uring |
| --- | --- | --- |
| 模型 | 多路复用（等就绪） | **异步（通知完成）** |
| 用户职责 | 自己 read/write | **只提交请求、收结果** |
| 系统调用 | 每次 epoll_wait | **批量、SQPOLL 下零次** |
| 数据搬运 | 用户 read | **内核完成** |
| 文件支持 | socket/pipe 为主 | **普通文件 + socket** |
| 生态成熟度 | 成熟 | 发展中 |

**设计启示**：io_uring 的哲学是「**把 I/O 的每一步都从用户态挪进内核，然后用共享队列消除边界成本**」——它是「能不进内核就不进内核」与「共享数据避免拷贝」两大思想的合体。它的成功提示我们：**系统性能优化的极限，是「用户与内核几乎无边界地协作」**。

**术语速查表**：

| 术语 | 含义 |
| --- | --- |
| SQ | 提交队列（用户写请求） |
| CQ | 完成队列（内核写结果） |
| SQE | 提交队列项（一个 I/O 请求） |
| CQE | 完成队列项（一次完成结果） |
| `io_uring_setup` | 创建 ring（映射共享内存） |
| `io_uring_enter` | 提交 SQ 中的请求 |
| SQPOLL | 内核线程轮询 SQ，提交零系统调用 |
| `O_DIRECT` | 绕过页缓存的直接 I/O |

## 5 小结

- **io_uring**：Linux 5.1+ 的异步 I/O 框架——提交与完成解耦，内核通知「完成」而非「就绪」。
- 机制：**SQ（提交环）+ CQ（完成环）**共享队列，mmap 映射。
- 三重优化：**批量提交、真正异步、SQPOLL 零系统调用**。
- 系统调用从「每请求一次」降到「一批一次/零次」——消除模式切换开销。
- 与 epoll 互补（连接事件 + 数据 I/O），生态仍在成熟。
