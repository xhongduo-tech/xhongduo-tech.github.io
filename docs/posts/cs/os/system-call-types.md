## 为什么从系统调用开始

上一节我们确立了用户态与内核态的双模式结构：用户程序不能直接执行特权指令，否则就破坏了系统的安全边界。可是应用程序终归要读文件、建进程、发网络包，这些操作全都触碰硬件。**系统调用（system call）就是用户态程序请求内核代劳的唯一合法通道**——它是操作系统对外提供的「服务合同」，也是我们从「操作系统的概念」走向「操作系统如何真的工作」的第一道门。<span class="marginnote">双模式操作见本专题《用户态与内核态：双模式操作与特权指令》。系统调用是那节课的「下一跳」：模式位怎么翻，就在这一次跳转里。</span>

几乎所有你在用户态做的「系统级」操作，最终都汇聚到一个系统调用上。理解它，等于拿到了阅读整个操作系统的钥匙。

## 1 什么是系统调用

**系统调用（system call）**：操作系统内核向用户态程序提供的、经过安全审查的服务入口，用户程序通过它请求内核执行特权操作。程序员平时不直接写系统调用，而是调用**应用程序编程接口（API，Application Programming Interface）**——C 语言的 printf、scanf 背后各自对应一次 write、read 系统调用。

这里有三层要分清：

**API**：程序员看到的函数接口，由语言库提供，可移植。
**系统调用**：内核的服务入口，由操作系统定义，与硬件架构相关。
**ABI（应用二进制接口）**：二进制层面约定好的调用约定——参数放哪个寄存器、系统调用号是多少。同一个操作系统上，用任何语言写出的程序最终都要按 ABI 翻译成相同的系统调用序列。<span class="marginnote">ABI 是「二进制兼容」的源头。你的程序只要遵循 ABI，就能在同样内核版本的机器上跑，这正是 Linux 发行版之间二进制兼容的基础。</span>

**系统调用是用户态与内核态之间唯一的合法边界**。除此之外的任何「进内核」方式（除中断、异常等硬件事件）都不被允许，这正是双模式设计的意义所在。

## 2 系统调用的类型：五大家族

恐龙书把系统调用按功能分成五大类。我们用 Linux 的实例说话：

| 类别 | 职责 | Linux 典型调用 |
| --- | --- | --- |
| 进程控制 | 创建、执行、结束进程，等待子进程 | fork、execve、exit、wait |
| 文件管理 | 打开、读写、关闭、定位文件 | open、read、write、close、lseek |
| 设备管理 | 请求与释放设备，读写设备 | open、close、read、write |
| 信息维护 | 查询时间、进程号、系统参数 | gettimeofday、getpid、getrusage、uname |
| 通信 | 进程间消息传递、共享内存、网络 | shmget、msgsnd、socket |

注意设备管理与文件管理在 Linux 中高度重合——因为 Unix 的哲学是「一切皆文件」，设备也以文件方式访问。<span class="marginnote">「一切皆文件」让 read/write 一簇系统调用通吃文件、设备、管道、套接字。这一抽象极大的简化了用户态编程，代价是设备特有的操作只能靠 ioctl 打补丁——这是经典的系统设计权衡。</span>

## 3 系统调用的实现原理：完整路径

一次系统调用从库函数调用开始，走完整条路大约经历六步：

1. 用户程序调用库函数 printf，它把格式串整理好，准备调用 write 的封装。
2. 库函数把系统调用号（如 write 是 1）存入寄存器，再执行一条特殊的**陷入指令**（trap，x86-64 上是 syscall），触发一次软中断。
3. CPU 切换到内核态：保存用户态现场（寄存器、程序计数器、栈指针），按中断向量表跳入内核的**系统调用处理程序**。
4. 内核根据系统调用号查**系统调用表**，找到对应的内核函数（如 sys_write）。
5. 内核函数校验参数——文件描述符是否合法、缓冲区指针是否在用户地址空间内——然后执行真正的读写硬件操作。
6. 结果写入返回值寄存器，恢复用户态现场，sysret 返回用户态，printf 拿到返回值继续执行。

**系统调用号 + 系统调用表 + 陷入指令**是这套机制的三块基石：陷入指令负责「翻模式位」，系统调用号负责「选服务」，系统调用表负责「找函数」。<span class="marginnote">每次系统调用都有一次用户态↔内核态的往返，代价通常在几百纳秒到微秒级——比普通函数调用慢一两个数量级。这正是后文「为什么要有 vDSO 加速 gettimeofday」的动机，见 Linux 专题《vDSO 与 gettimeofday 的用户态加速》。</span>

## 4 核心对比表：系统调用 vs 普通函数调用

这是一个纯概念主题，公式不多，但差别极重要，用对比表代替公式解析：

| 维度 | 普通函数调用 | 系统调用 |
| --- | --- | --- |
| 执行模式 | 全程用户态 | 用户态 → 内核态 → 用户态 |
| 地址空间 | 同一进程地址空间 | 跨越用户空间与内核空间 |
| 触发方式 | call 指令 | 陷入指令（syscall/sysret） |
| 参数检查 | 由库函数自行约定 | 内核强制校验，防恶意参数 |
| 开销 | 纳秒级 | 数百纳秒至微秒级 |
| 返回值错误 | 库函数自定 | 统一返回 -1 并置 errno 错误码 |

**辨析｜易错点：** 很多人以为「系统调用失败会抛异常」。实际上系统调用失败不抛异常，而是返回负值并把错误码写入 errno 全局变量，由库函数检查后决定是否打印错误信息——许多程序从不检查 write 的返回值，这是绝大多数「写入失败静默丢失」bug 的根源。

## 5 小结

- **系统调用**是用户态请求内核服务的唯一合法入口，分为**进程控制、文件管理、设备管理、信息维护、通信**五大类。
- API、系统调用、ABI 三层概念：程序员面向 API，二进制层面落实为 ABI。
- 实现路径六步：库封装 → 陷入指令 → 模式切换 → 查系统调用表 → 参数校验与执行 → 返回用户态。
- 系统调用比普通函数调用慢一两个数量级，因为要跨越模式边界与地址空间。
- 失败不抛异常，而是返回负值并置 errno——这是写健壮代码必须养成的检查习惯。
