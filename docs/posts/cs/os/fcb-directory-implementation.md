## 为什么从文件控制块开始

前面讲文件系统的层次与布局，但「一个文件在磁盘上到底是什么」还没揭开。答案是：**文件由一个文件控制块（FCB）加上若干数据块组成**。FCB 是文件的「户口本」，目录是「查号台」，两者共同回答了「文件名 → 数据在哪」的完整链条。这一节是理解文件系统一切后续主题（分配、索引、ext4）的地基。<span class="marginnote">回顾《文件概念》的属性：名称、标识符、位置、大小、权限。FCB 就是这些属性的磁盘载体；Linux 的 FCB 叫 <strong>inode</strong>，ls -i 能看到它的编号。</span>

## 1 文件控制块 FCB / inode

**文件控制块（FCB, File Control Block）**：文件系统为每个文件维护的数据结构，集中存放该文件的全部**元数据**。Unix/Linux 中叫 **inode（index node）**。

**inode 包含的内容**：

文件类型与权限（rwx）。
属主与组。
文件大小。
时间戳（创建、修改、访问）。
**指向数据块的指针**（直接块、间接块——见《索引分配》）。
链接计数（回顾《目录结构》的硬链接）。

**辨析｜易错点：** 「文件名在 inode 里」是经典误解。**inode 不存文件名！** 文件名存在**目录**里，inode 只存元数据与数据指针。**「文件」= inode + 数据块；「名字」只是目录里指向 inode 的一个条目。** 这也解释了硬链接：多个名字指向同一 inode。

## 2 目录实现：名字 → inode 的映射

**目录（directory）**的实现在磁盘上就是一个**特殊的文件**，内容是「目录项」的列表。每个**目录项（directory entry, dentry）**包含：

**文件名**（或名称 + 长度）。
**inode 号**（指向该文件的 inode）。

目录文件的内容就是一连串这样的目录项：

```
目录文件的内容（一串目录项）：
┌────────────┬──────────┬───────┬─────────┐
│ 文件名     │ inode 号 │ 长度  │ 类型    │
├────────────┼──────────┼───────┼─────────┤
│ hello.c    │   42     │  8    │ file    │
│ readme.md  │    7     │  9    │ file    │
│ src        │  100     │  3    │ dir     │
└────────────┴──────────┴───────┴─────────┘
```

对照 C 语言的结构体，目录项在磁盘上大致是这样排布的：

```c
struct dir_entry {
    uint32_t inode;        /* inode 号：指向该文件的元数据 */
    uint16_t rec_len;      /* 本条目长度（含对齐填充） */
    uint8_t  name_len;     /* 文件名长度 */
    uint8_t  file_type;    /* 文件类型：普通/目录/符号链接… */
    char     name[];       /* 文件名（变长，紧跟其后） */
};
```

**查找流程**：打开 /home/x/docs → 遍历目录，找到名为 hello.c 的条目 → 拿到 inode 42 → 从 inode 42 找到数据块 → 访问数据。

**目录的两种实现方式**：

**线性列表（linear list）**：目录项顺序存放。简单，但查找 O(n)、删除要打标记（空闲位）。
**哈希表（hash table）**：按文件名哈希定位。查找快，但冲突处理与扩展复杂。

**两种方式对比**：线性列表适合小目录，哈希表适合大目录——现代文件系统（ext4）用「目录索引（htree/B-tree）」在目录项上建索引，平衡两者。

## 3 从名字到数据：完整链路

一次 open("/a/b/c") 的寻址之旅：

1. **解析路径**：从根目录 / 开始，找 a 条目 → inode。
2. 读 a 的 inode → 读 a 目录内容 → 找 b 条目 → inode。
3. 读 b 的 inode → 读 b 目录内容 → 找 c 条目 → inode。
4. 读 c 的 inode → 得到数据块指针列表。
5. 建立 file 对象（fd），记录位置，返回 fd。

**每一步都涉及「读 inode → 读目录/数据」**——所以路径解析是多次磁盘访问，这也是 open 比 read/write 贵得多的原因。<span class="marginnote">路径解析的代价是「一层目录一次读」：打开 /a/b/c 需要读根目录找 a、读 a 找 b、读 b 找 c，至少 3 次 inode + 目录读。<strong>目录缓存（dentry cache）</strong>缓存「路径段 → inode」的映射，让重复的路径解析命中缓存、绕过磁盘——这是文件系统性能的关键优化之一。</span>

## 4 核心对比表：FCB/inode vs 目录项

| 维度 | inode（FCB） | 目录项（dentry） |
| --- | --- | --- |
| 内容 | 元数据 + 数据指针 | 文件名 + inode 号 |
| 存文件名 | **不存** | 存 |
| 与文件的关系 | 1 文件 1 inode | 多个目录项可指向同一 inode |
| 磁盘位置 | inode 区 | 目录文件的数据块 |
| 作用 | 文件的「户口本」 | 名字的「查号台」 |

**记忆主线**：**inode 是文件的本体（数据 + 元数据），目录项只是「名字 → inode」的索引**。删除文件 = 从目录删条目 + inode 链接计数减到 0；改名 = 改目录里的名字，不动 inode 与数据。

## 5 小结

- **inode/FCB**：文件的元数据集中地——类型、权限、大小、时间戳、**数据块指针**，但不存文件名。
- **目录**是「文件名 → inode 号」的映射表，实现用**线性列表或哈希表**。
- 打开文件 = **路径解析**（逐层目录查找）+ inode 定位 + 数据块访问。
- 硬链接的多个名字共享同一 inode；删除靠**链接计数**归零。
- dentry 缓存加速重复路径解析——文件系统性能的关键。
