## 为什么从资源分配图开始

上一篇结尾说「死锁 ⇔ 资源分配图有环」。这一节我们把这张图画出来，练成「看图断案」的技能——这是死锁检测、避免（银行家算法）的基础。资源分配图是理解死锁的最直观工具：**一眼看环，心中有数。**<span class="marginnote">回顾死锁四条件：图里的「环」正是「循环等待」的可视化。图的画法不复杂，但「有环必有死锁吗？」「多实例资源的环呢？」这两个追问是本节的重点。</span>

## 1 图的构成：两类节点、两类边

**资源分配图（resource-allocation graph）** 是有向二分图：

- **节点**：
  - **进程节点**：圆形（如 $P_1$、$P_2$）。
  - **资源节点**：矩形；矩形内的小点表示该资源的**实例数**（1 点 = 1 个实例）。
- **边**：
  - **请求边**：$P_i \rightarrow R_j$，进程 $P_i$ 请求资源 $R_j$（指向资源）。
  - **分配边**：$R_j \rightarrow P_i$，资源 $R_j$ 的一个实例已分配给进程 $P_i$（指向进程）。

例如，$P_1 \rightarrow R_1$ 表示 $P_1$ 正在等待 $R_1$；$R_2 \rightarrow P_2$ 表示 $R_2$ 的一个实例已归 $P_2$ 使用。图中边只有这两种方向，不会出现进程到进程或资源到资源的边。

**读图的规则**：请求边指向资源，分配边指向进程。一条「资源实例 → 进程」的分配边用实心点标注占用的是哪个实例。

### 画一张图的步骤

1. 画出所有进程节点（圆）与资源节点（矩形，内含实例点）。
2. 对每个「已分配」：画分配边「资源实例 → 进程」。
3. 对每个「正在等待」：画请求边「进程 → 资源」。
4. 检查：图中所有边只有这两种方向；一个资源实例只能拥有一条分配边（已被占用就不能再分配）。

**读图时的两个核对点**：请求边总是指向资源、分配边总是指向进程；实例点被占用（有分配边）后不能再分配给别人——这两条是画图不出错的关键。

## 2 画图示例与判死锁的定理

一个死锁的经典图（两个进程、两个单实例资源）：

$$P_1 \xrightarrow{请求} R_1 \xrightarrow{分配} P_2 \xrightarrow{请求} R_2 \xrightarrow{分配} P_1$$

即：$P_1$ 持有 $R_2$、请求 $R_1$；$P_2$ 持有 $R_1$、请求 $R_2$——构成环 $P_1 \rightarrow R_1 \rightarrow P_2 \rightarrow R_2 \rightarrow P_1$，**死锁**。

**核心定理（判据）**：

- **若图中无环 → 无死锁。** 环是死锁的必要条件。
- **若图中每个资源都只有一份实例，且有环 → 死锁。** 单实例资源的环必然死锁。
- **若图中存在多实例资源，且有环 → 可能死锁，可能不死锁。** 需要进一步分析（环内进程能否借到多余实例）。<span class="marginnote">「单实例有环必死锁，多实例有环待定」是本节的钥匙。多实例资源的环里，若环外资源实例充足，环内进程可能逐步完成并释放资源，环就「解开」了——这正是银行家算法要判定的「安全状态」。</span>

**辨析｜易错点：** 「图里有环就等于死锁」是初学者最常见的错判。**环是多实例场景下只是「死锁嫌疑」，不是「死锁定罪」**。必须区分资源实例数：单实例环 = 死锁确定；多实例环 = 需要算法进一步验证。死锁检测算法就是靠「模拟释放资源」来给多实例环「定罪或洗冤」。

### 多实例资源的例子：有环但未必死锁

设资源 $R$ 有 2 个实例，进程 $P_0$、$P_1$ 各持有一个实例，且互相等待对方（构成环 $P_0 \rightarrow R \rightarrow P_1 \rightarrow R \rightarrow P_0$）：

- **环中进程**：$P_0$ 持有 1 个 $R$、等 1 个 $R$；$P_1$ 同理。环内两个实例都被占用，谁都无法再申请——**此时确会死锁**。
- **但若环外有进程持有 $R$ 的实例**：环内进程可能从环外进程释放的实例中借到一个，环被解开。

**判定的实质**：多实例场景下，「有环」只是提示「候选死锁集合」，是否真的死锁要看**环内进程能否从「环外的空闲实例 + 环外进程将来释放的实例」中凑够需求**。这正是《死锁检测算法》要做的事——模拟「先满足能完成的进程」，看环是否松动。

### 死锁判定速查

| 情况 | 结论 |
| --- | --- |
| 图中无环 | 无死锁 |
| 单实例资源 + 有环 | **必然死锁** |
| 多实例资源 + 有环 | 可能死锁，需检测算法验证 |

**辨析｜易错点：** 「无环就一定安全」是正确的，但要小心——**无环只是「此刻无死锁」，不代表以后不死锁**：进程将来的申请可能让图出现环。资源分配图是「当下快照」，检测「未来」要预演（避免）或等它发生（检测）。

## 3 分析方法：两种用途

资源分配图有两种用法：

**用途一：死锁检测（事后）**

周期性地画当前资源分配图。
若发现「单实例资源的环」→ 已死锁 → 执行死锁恢复（见第七篇《死锁恢复》）。
若发现「多实例资源的环」→ 跑死锁检测算法（模拟资源释放）确认。

**用途二：死锁避免（事前）**

在**每次资源分配前**，先画「假设分配后的图」。
若分配后出现环 → 拒绝分配（这个请求可能引发死锁）。
若不出现环 → 允许分配。
这就是银行家算法的图论直觉：**分配前先「预演」，避免走入死胡同**。<span class="marginnote">「事前预演」思想远不止于死锁：数据库事务在提交前的冲突检测、操作系统的预拷贝、甚至 AI 里的「模拟规划」都是「先预演再动手」。银行家算法把它做到极致——见第七篇《银行家算法》。</span>

### 检测算法的图论视角

死锁检测算法本质是对图的「可满足性松弛」：

1. 找所有「当前请求都能被满足」的进程（其请求边指向的资源有实例可用）。
2. 假设该进程完成，删除它的所有请求边与分配边（资源实例归还）。
3. 重复直到没有可完成的进程。
4. 若仍有进程的边无法删除 → 死锁（这些进程就是死锁进程）。

**一句话**：检测 = 反复「删掉能完成进程的边」，删不干净剩下的就是死锁——这比「肉眼看环」更严谨，也正好是《死锁检测算法》的实现骨架。

**辨析｜易错点：** 区分「请求边」与「分配边」的方向是画图的第一道坎——**请求边从进程指向资源（进程「想要」资源），分配边从资源指向进程（资源「已给」进程）**。一条边画反，环就画不出来，死锁就看不见。自检方法：看见「进程 → 资源」是「等待」，看见「资源 → 进程」是「占用」。

## 4 核心对比表：单实例 vs 多实例资源

| 维度 | 单实例资源 | 多实例资源 |
| --- | --- | --- |
| 示例 | 打印机、一把叉子 | 连接池（5 槽）、内存页框 |
| 图中表示 | 1 个点 | 多个点 |
| 有环 ⇒ 死锁？ | **是（必然）** | **不一定（需验证）** |
| 检测手段 | 看图找环 | 银行家算法/检测算法 |
| 是否可剥夺 | 通常否 | 部分可（如内存可换出） |

## 5 小结

- 资源分配图 = 进程节点 + 资源节点（带实例点）+ 请求边/分配边（二分图）。
- **无环 ⇒ 无死锁**；**单实例有环 ⇒ 死锁**；**多实例有环 ⇒ 待定**——资源实例数决定「环 = 死锁」是否成立。
- 画图四步：画节点 → 分配边 → 请求边 → 核对方向；请求边「进程→资源」= 等待，分配边「资源→进程」= 占用。
- 多实例环的死活看环外实例能否借给环内——「模拟释放」才能定罪，这是检测算法的骨架。
- 死锁检测（事后）：反复删「能完成进程」的边，删不干净剩下的即死锁。
- 死锁避免（事前）：分配前预演，有环则拒绝——银行家算法的图论直觉。
- 无环只是当下无死锁，不代表未来不死锁——检测是快照，避免是预演。
- 资源分配图是死锁章节的统一语言：预防/避免/检测/恢复都对应图上的一种操作。
