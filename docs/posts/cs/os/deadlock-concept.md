## 为什么从死锁开始

同步解决「同时抢」的问题，但还有一类更隐蔽的灾难：**谁也没出错，但大家一起卡死**。哲学家进餐里，五个人同时举起左叉的场景就是预告。这一节我们把死锁从「事故」变成「可以诊断的疾病」——先认识它，再给出它存在的**四个必要条件**。这四个条件是整个死锁章节的总纲：所有预防、避免、检测策略，都在跟这四个条件较劲。<span class="marginnote">回顾《哲学家进餐》：全部左叉 = 死锁现场。那次的结论是「破坏循环等待」。本篇把「循环等待」放进更完整的框架——死锁四条件，是死锁章节的地图。</span>

## 1 什么是死锁

**死锁（deadlock）**：一组进程中的每个进程都在等待一个事件，而该事件只能由这组进程中的另一个进程触发，导致所有进程都无法继续推进的状态。

经典例子——**两个线程，两把锁**：

```c
/* 线程 A */            /* 线程 B */
lock(&lock1);          lock(&lock2);
lock(&lock2);   /* →   lock(&lock1);   ← 各持一锁、互等另一把 */
```

A 等 B 放锁2，B 等 A 放锁1——**互相等待，谁也不松手**，两个线程永远阻塞。这就是最简死锁。

与饥饿的区别（回顾《优先级调度》的辨析）：

**死锁**：一组进程**都**无法推进（集体僵死）。
**饥饿**：部分进程推进，某个进程永远轮不到（个别慢性死亡）。
**活锁（livelock）**：进程都在动，但都在做无用功，谁也无法进展（两个人在窄巷里互相让路，让来让去谁都过不去）。

**死锁在真实系统里并不罕见**。数据库两个事务「各更新一张表、再更新对方的表」、分布式系统里两个节点互等对方的锁、线程池中任务 A 等任务 B 而 B 在排队等线程——这些都是死锁的日常形态。<span class="marginnote">一个经典的「锁顺序」经验法则：<strong>所有代码按同一顺序获取锁（如先 lock1 后 lock2），循环等待就被系统性消除</strong>。这不是消掉某个条件，而是让「环」根本画不出来——工程上最常见的死锁预防手段，代价只是统一一个约定。</span>这也是为什么「代码审查必问锁顺序」——死锁通常不是玄学事故，而是「锁的获取顺序不统一」的必然结果。

## 2 四个必要条件

死锁发生必须**同时**满足四个条件（缺一不可）：

**互斥（mutual exclusion）**：资源一次只能被一个进程使用。若资源可共享（如只读文件），不会死锁。
**持有并等待（hold and wait）**：进程持有至少一个资源，同时等待获取其他进程持有的资源。
**不可剥夺（no preemption）**：已分配的资源不能被强行夺走，只能由持有者自愿释放。
**循环等待（circular wait）**：存在一个进程等待环——$P_0$ 等 $P_1$ 的资源、$P_1$ 等 $P_2$ 的资源、…、$P_{n-1}$ 等 $P_0$ 的资源。

**核心命题**：**死锁发生 ⇔ 四条件同时成立。** 反过来说，**只要破坏任一条件，死锁就不可能发生**——这就是下一节《死锁预防》的全部策略来源。

**一个记忆法**：四条件可压缩成「**一独占、二边占边等、三不让、四成环**」——资源互斥（条件1）、持着资源还要别的（条件2）、谁都不肯放手（条件3）、最后兜成一个圈（条件4）。写并发代码时心里默念这八个字，就能快速判断「这里会不会死锁」。<span class="marginnote">把哲学家进餐对号入座：叉子互斥（条件1）、每人持左叉等右叉（条件2）、叉子不能抢（条件3）、五人构成等待环（条件4）。四条俱全 → 死锁。解法（限制 4 人就餐、奇偶取叉）破坏的是条件4。</span>

**辨析｜易错点：** 「四条件是死锁的充要条件」只在**资源是「非共享、不可剥夺」**的经典模型下成立；现实系统（数据库、文件系统）里循环等待可能因「等待超时」而中断，死锁未必「永久」。但操作系统课程的经典模型坚持「四条件 ⇔ 死锁」，这是分析的基准。**记住方向：四条件是「同时成立才死锁」，不是「任一成立就死锁」。**

另一个易错点：**「单进程死锁」**——一个进程持有一个资源、再请求自己的另一个资源（不自量力），也会自我死锁。所以「死锁至少两个进程」的说法不严谨，更准确说「至少一个资源持有环」。

## 3 死锁的本质：资源分配图上的环

死锁的图论本质：把**进程与资源**画成二分图，边表示「持有」或「请求」，那么——

**死锁 ⇔ 资源分配图中存在环。**

- 若环上每个资源都**只有一份实例**（如一把叉子、一台打印机），环即死锁。
- 若某个资源有**多份实例**（如 5 个连接池槽位），环不一定死锁——可能环内进程之间还能借到多余实例。

图论表达让死锁从「玄学」变成「可判定」：检查图里有没有环，就能判断会不会死锁。这是下一篇《资源分配图》的主线。

## 4 核心对比表：死锁 vs 饥饿 vs 活锁

| 维度 | 死锁 | 饥饿 | 活锁 |
| --- | --- | --- | --- |
| 进程状态 | 全部阻塞 | 部分推进、个别挨饿 | 都在跑但无进展 |
| 起因 | 互相等待、循环等待 | 优先级/策略偏心 | 谦让过度、互相让路 |
| 能否自行恢复 | 否（需外部干预） | 是（条件变化后可能） | 是（随机退避可能解） |
| 占不占 CPU | 不占（阻塞） | 不占（被饿） | 占（空转） |

## 5 数值算例：一台打印机、一台扫描仪，四个条件逐个验证

把四条件放到一台真实的「打印机 + 扫描仪」机器上验证。设 P1 要打印扫描过的文档（先持扫描仪、再要打印机），P2 要先打印再扫描（先持打印机、再要扫描仪）：

| 条件 | P1 持扫描仪、P2 持打印机时是否成立 |
| --- | --- |
| 互斥 | ✓ 打印机、扫描仪各一次只能被一个进程使用 |
| 持有并等待 | ✓ P1 持扫描仪同时等打印机；P2 持打印机同时等扫描仪 |
| 不可剥夺 | ✓ 资源只能由持有者自愿释放 |
| 循环等待 | ✓ P1 → 打印机 ← P2 → 扫描仪 ← P1，构成两进程环 |

四条同时成立 → **死锁必然发生**。反过来，只要破坏一条就能救活：让某个进程先释放再请求（破持有并等待）、让系统能抢资源（破不可剥夺）、或者统一资源获取顺序（破循环等待）。**这组例子把「抽象的四条件」落成了可以逐一打勾的清单**——以后排查死锁，就按这四行来。<span class="marginnote">现实版：数据库里两个事务各更新一张表、再更新对方的表，就会复现这台打印机扫描仪的困局。InnoDB 检测到这种环就回滚一个事务，本质就是「打破循环等待」。</span>

## 6 术语速查

| 术语 | 含义 |
| --- | --- |
| 死锁 | 一组进程互相等待、谁也无法推进 |
| 互斥 | 资源一次只能被一个进程使用 |
| 持有并等待 | 持有资源的同时等待其他资源 |
| 不可剥夺 | 资源只能由持有者自愿释放 |
| 循环等待 | 存在进程等待环 |
| 饥饿 | 个别进程永远轮不到资源 |
| 活锁 | 进程都在动但都在做无用功 |
| 等待超时 | 现实系统中打破循环等待的常用手段 |

## 7 小结

- **死锁** = 一组进程互相等待、谁都等不到对方释放，集体僵死。
- **四必要条件**：互斥、持有并等待、不可剥夺、循环等待，**缺一不可，同时成立即死锁**。
- 破坏任一条件即可防死锁——这是下一节预防策略的总纲。
- 图论本质：**资源分配图中的环**；单实例资源环即死锁。
- 数值：打印机 + 扫描仪场景四条件逐个打勾，全成立即死锁。
- 单进程也可能自我死锁——「至少一个资源持有环」比「至少两进程」更准确。
- 多实例资源环不一定是死锁，可能环内还能借到多余实例。
- 死锁 vs 饥饿 vs 活锁：集体僵死 / 个别挨饿 / 空转无进展。
- 死锁四条件的意义在于「可诊断」：从玄学事故变成可判定的疾病。
- 数据库 InnoDB 检测到锁等待环就回滚事务，本质是打破循环等待。
- 排查死锁就按四条件清单逐一打勾，破坏任一条即可解困。
