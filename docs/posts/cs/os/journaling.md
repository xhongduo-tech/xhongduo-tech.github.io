## 为什么从日志文件系统开始

缓冲与缓存让写先落内存，但这带来一个致命问题：**崩溃时，内存里的数据没了，磁盘上的文件系统可能停在「写了一半」的中间态**——比如 inode 更新了、数据块没写；或者数据块写了、inode 没更新。文件系统必须能恢复一致。**日志（journaling）**是解决「崩溃一致性」的标准方案：**先把「将要做的修改」记进日志，再执行修改；崩溃后重放日志，恢复一致。**<span class="marginnote">回顾缓冲的代价：延迟落盘 → 崩溃丢数据。日志不解决「数据丢没丢」，解决的是「<strong>文件系统结构的一致性</strong>」——元数据（inode、目录、位图）不能停在半更新状态，否则文件系统损坏、数据找不回。日志是「结构保险」。</span>

## 1 崩溃一致性问题

没有日志时，一次「创建文件」涉及多处磁盘写：

- 写 inode（新文件的元数据）。
- 写目录（加入新文件名条目）。
- 写位图（标记数据块已分配）。

**崩溃发生在任意两步之间**，磁盘就会停在不一致状态：

- inode 写了、目录没写 → 文件「幽灵」存在（inode 孤儿）。
- 目录写了、inode 没写 → 目录项指向不存在的 inode。
- 位图与分配不一致 → 块被重复分配或永久泄漏。

**传统恢复（fsck）**：启动时**全盘扫描**，检查每个 inode、每个目录、每块位图，找出不一致并修复。**缺点**：大磁盘全盘扫描要几分钟到几小时——不可接受。

**日志（journaling）**：把「先记录、后执行」引入文件系统，崩溃恢复变成「重放日志」，秒级完成。

## 2 日志的原理：先记录，后执行

**日志文件系统（journaling file system）**：在磁盘上划一块**日志区（journal）**。任何「修改文件系统结构」的操作分三步：

1. **写日志**：把「本次修改的描述」（如「新建文件 foo：inode X、目录项 Y、位图 Z」）顺序写入日志区，标记为 **pending（待提交）**。
2. **提交（commit）**：日志写完，写入**提交记录**——这是「修改生效」的原子标志点。
3. **执行（checkpoint）**：把修改真正应用到磁盘的实际位置（inode、目录、位图），完成后标记日志条目可重用。

**崩溃恢复**：

- 扫描日志区。
- 找到**已提交**但**未应用完**的条目 → **重放（redo）**它们，让修改落盘。
- 找到**未提交**的条目 → **丢弃**（修改从未生效，无需应用）。

**结果**：崩溃后文件系统要么「修改没发生」（未提交被丢弃），要么「修改完整发生」（已提交被重放）——**没有中间态**。恢复只需扫日志，秒级完成。

## 3 日志的两种模式

- **元数据日志（metadata journaling，ext3/4 默认）**：只把**元数据**（inode、目录、位图）写入日志，**数据块本身不写日志**。数据块可以先刷盘（或靠 fsync 保证）。优点：日志小、写快；缺点：崩溃时**文件内容可能丢，但结构一致**。
- **全数据日志（data journaling）**：元数据**和**数据都写日志。优点：数据和结构都一致；缺点：**每次写都是双份**（日志 + 实际位置），性能大幅下降。

**辨析｜易错点：** 「日志保证数据不丢」是常见误解。**默认的元数据日志只保证「结构一致」，不保证「数据不丢」**——崩溃时缓存里的数据可能没写盘。要数据不丢，需要 fsync + 全数据日志或应用层保证。**日志是「结构保险」，不是「数据保险」。**

## 4 公式解析：日志的写放大

设一次元数据更新包含 $M$ 个元数据块（inode、目录、位图），全数据日志还要加 $D$ 个数据块：

$$\text{写入量} = \begin{cases} 2M & \text{元数据日志（日志 + 实际）} \\ 2(M + D) & \text{全数据日志} \end{cases}$$

- **元数据日志**：写日志 $M$ + 实际应用 $M$ = $2M$。
- **全数据日志**：写日志 $(M+D)$ + 实际应用 $(M+D)$ = $2(M+D)$。
- 全数据日志的写放大是元数据日志的 $(M+D)/M$ 倍——**所以默认用元数据日志**。

**直觉**：日志的本质是「**写双份换一致性**」——付出 2 倍的元数据写入，换取「崩溃可秒恢复」。**用 I/O 换安全**，是现代存储系统的普遍交易。

## 5 核心对比表：日志 vs fsck

| 维度 | 传统 fsck | 日志 |
| --- | --- | --- |
| 恢复方式 | 全盘扫描修复 | 重放日志 |
| 恢复时间 | 分钟~小时 | **秒级** |
| 是否需全盘检查 | 是 | 否 |
| 写开销 | 无（恢复时才扫） | **写双份元数据** |
| 现代使用 | 启动前兜底 | ext4/XFS/NTFS 标配 |

**设计启示**：日志的核心思想是「**预写日志（Write-Ahead Logging, WAL）**」——先把意图记下来，再执行。它不只在文件系统里：**数据库（Redo/Undo 日志）、分布式系统（预写日志）、消息队列**全在用同一招。理解了文件系统日志，你就理解了 WAL 的通用模式。

## 6 小结

- 崩溃一致性：多步元数据写可能停在中间态，导致文件系统损坏。
- **日志**：先写「修改描述」到日志区 → 提交 → 应用；崩溃后重放已提交、丢弃未提交。
- **元数据日志**（默认）：只记元数据，结构一致但数据可能丢；**全数据日志**：数据也记，性能大降。
- 写放大 2 倍——「写双份换一致性」。
- 日志 = **WAL（预写日志）**，与数据库、分布式系统的日志同源。
