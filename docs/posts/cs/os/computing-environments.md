## 为什么从计算环境开始

上一节讲了操作系统如何在**时间**上做文章——批处理、多道程序、分时。这一节讲操作系统如何在**空间**上做文章：CPU 从一个变成多个，机器从一台变成一群。今天随手一台笔记本就是 8 核 16 核，云上的大模型训练任务横跨上千块 GPU——**理解「多处理器」与「集群」的差别，是理解现代操作系统运行的硬件前提**，也是后面「多处理器调度」「负载均衡与处理器亲和性」两节的地基。

注意本节标题里的「计算环境」不是指某个软件环境，而是指**硬件拓扑**——CPU 怎么连、内存怎么共享、整机之间怎么通信。操作系统必须知道这些拓扑，才能正确地分配资源；而调度、内存管理、同步这些后续主题，几乎每一项都会回到「运行在多处理器上还是单处理器上」这个变量。

## 1 单处理器系统：一切模型的原点

**单处理器系统（single-processor system）** 只有一颗 CPU，执行通用指令集，通过总线访问一块内存。它是我们此前《计算机系统组成与硬件结构》《存储结构》等节隐含的假设模型。

**重点：纯粹的「单处理器」如今几乎绝迹——但这不代表这个概念过时。** 因为多处理器、多核系统上，每个核心执行的仍然是「单处理器逻辑」：先把一个 CPU 调度好，才谈得上多个 CPU 的协同。单处理器模型是理解一切并行结构的原子单位，就像集合论里「单个元素」是理解全体集合的原子单位一样。

与此相关的一类硬件是**专用处理器（special-purpose processor）**，例如早期的显卡 GPU、磁盘控制器上的处理器、键盘控制器。它们受主 CPU 指挥，执行自己的指令集，通常不运行通用操作系统，而是按主 CPU 的命令完成特定子任务。<span class="marginnote">今天的 GPU 早已不是「专用处理器」那么简单：CUDA 让 GPU 变成通用并行计算引擎，是大模型训练算力的主角。它属于第四级《AI 基础设施》专题的内容，这里只需知道：操作系统把这些设备当作「可指挥的从设备」，而非「平等的处理器」。</span>

## 2 多处理器系统：共享内存的紧耦合

**多处理器系统（multiprocessor system）** 指一台计算机里装有两个或更多处理器，它们**共享同一块内存与总线**，通常运行同一份操作系统副本。这种「紧密耦合（tightly coupled）」让处理器之间的协作以内存读写完成，速度比网络通信快几个数量级。

教材把多处理器分成两类：

**非对称多处理（asymmetric multiprocessing, AMP）**：一个主处理器负责全局调度，其余处理器执行分派下来的任务。主从关系明确、实现简单，但主处理器是瓶颈。
**对称多处理（symmetric multiprocessing, SMP）**：每个处理器地位平等，各自运行一份操作系统副本，通过共享内存协作。现代系统几乎都是 SMP。<span class="marginnote">SMP 下「每个处理器跑自己的 OS 副本」带来一个棘手问题：<strong>两个 CPU 同时发出系统调用、同时修改内核的同一个链表怎么办？</strong>这正是第六篇《进程同步》的核心命题——信号量、自旋锁等原语就是为这种并发访问而生的。</span>

为什么要多处理器？教材给出三个理由：

**增加吞吐量（throughput）**：同时干更多活。但收益不是线性的——两个处理器很少能带来两倍吞吐，这就是 Amdahl 定律的警告。
**规模经济（economy of scale）**：多处理器共享机箱、电源、外设，比买多台独立机器便宜。
**增加可靠性（reliability）**：一个处理器故障，系统还能降级继续运行。这种能力叫**优雅降级（graceful degradation）**；而能自动检测故障、自动接管失败模块的系统，称为**容错（fault-tolerant）**系统。

## 3 多核、UMA 与 NUMA：多处理器的三种长相

「多处理器」只是一个抽象名词，具体硬件至少有三种形态，初学者最容易搞混：

**多核（multicore）**：多个 CPU 核封装在同一块芯片上，共享片内缓存与内存控制器。今天的笔记本、手机、服务器几乎都是多核，它是「最便宜的多处理器」。
**UMA（统一内存访问，uniform memory access）**：所有处理器访问内存的延迟相同，经典 SMP 总线架构即是 UMA。优点是实现简单、程序无需感知；缺点是与核数同步增长的内存带宽会成为瓶颈。
**NUMA（非统一内存访问，non-uniform memory access）**：每个处理器「亲近」自己本地那一块内存，访问本地内存快、访问远端内存慢。NUMA 要求调度器感知内存位置，否则一个线程被调度到「陌生」的核上，访问本地数据就变成了跨节点访问，性能骤降。

**辨析｜易错点：多核 ≠ 多处理器 ≠ 多线程。** 「多处理器」是机器里有多颗物理 CPU；「多核」是一颗芯片里塞了多个核（在操作系统眼里也算多个处理器）；「多线程」是一个程序同时执行多条控制流，它可以跑在单核上靠时间片**假装**并行，也可以真·并行地跑在多核上。三个词分属硬件、硬件、软件三个层面，别混着用。

多核还有一个甜蜜的麻烦：**缓存一致性（cache coherence）**。核 A 改写了内存里一个变量，核 B 的缓存里可能还存着旧值——到底谁说了算？硬件用一致性协议（如经典 MESI 协议）保证所有核最终看到同一份最新值。<span class="marginnote">缓存一致性是第三级《计算机组成原理》与体系结构专题的核心内容，这里只记住结论：<strong>硬件协议保证了「缓存里的值最终一致」，但无法保证「两个核同时读写时程序不会出错」</strong>——后者必须由软件用原子操作与同步原语解决，这正是第六篇的主题。</span>

## 4 集群系统：用网络把整机连起来

如果多处理器是「一台机器里多个 CPU」，那么**集群（clustered system）**就是「多台完整机器通过网络协作」。它们是**松散耦合（loosely coupled）**的：各自有独立的内存、磁盘与操作系统，彼此通过消息传递通信，不共享内存。

集群按用途分三类，容易混为一谈：

| 类型 | 目标 | 工作机制 |
| --- | --- | --- |
| 高可用（HA）集群 | 服务不中断 | 主节点故障，备节点接管 |
| 负载均衡集群 | 分摊压力 | 把请求分发给多个节点 |
| 高性能计算（HPC）集群 | 算力汇聚 | 把一个巨型任务切碎，多节点并行算 |

注意「高可用」与「负载均衡」并不互斥：对称高可用集群本身就是天然的负载均衡器。分类的边界在实践中常常模糊——一家网站既要求服务不中断、又要求分摊流量，通常是把两者合流进同一个系统。

高可用集群内部又有两种组织方式：**非对称（asymmetric）**——一个节点处于热备（hot standby）状态，平时不干活，主节点故障才接管；**对称（symmetric）**——两个节点都干活、互为备份，一个挂了另一个扛下全部请求，天然具备负载均衡能力。<span class="marginnote">注意这里的「对称/非对称」与多处理器里的 SMP/AMP 命名同源、含义类似：一个是<strong>系统级</strong>的冗余策略，一个是<strong>CPU 级</strong>的协作方式。对比记忆最有效，但别把两者的层级搞混。</span>

**辨析｜易错点：集群与多处理器最大的差别是「耦合度」。** 多处理器共享内存，通信靠内存读写，延迟微秒级；集群的节点各自有独立内存，通信靠网络，延迟毫秒级甚至更差。后果是决定性的：集群里的程序**不能**像多线程那样共享一个全局变量，只能显式地交换消息。这个「共享内存 vs 消息传递」的分叉，直接奠定了分布式程序设计的风格，也是第三级《分布式系统》专题的起点。

集群还常与**存储区域网络（storage-area network, SAN）**配合：多台机器通过高速网络共享同一批磁盘阵列，既获得存储的集中管理与冗余，又保持各自计算能力的独立。SAN 让「计算集群」与「存储池」解耦，是现代数据中心的基本骨架。

**辨析｜易错点：集群 ≠ 分布式系统，但二者高度重叠。** 集群强调「一组机器为同一目标协作」，分布式系统更强调「对外看起来像一台机器」。高可用集群、HPC 集群都是集群；而像搜索引擎那样把成千上万台机器伪装成一块「巨型磁盘」与「巨型 CPU」，则是分布式系统。可以说，集群是分布式的常见物理形态，分布式是集群的抽象目标——这个区分到第三级《分布式系统》专题会进一步展开。

## 5 走向现代：移动、嵌入式与云

篇幅所限，这里把现代计算环境的多样性收拢成一句话：**操作系统的「计算环境」早已不只是台式机，而是从手表里的嵌入式 RTOS，到云端弹性伸缩的虚拟机集群的整个光谱。** 单处理器、多处理器、集群三种模型不是互相替代，而是层层嵌套——云数据中心的物理机是多处理器，这些多处理器机器再组成集群，集群之上再跑虚拟机与容器。第十八篇《虚拟化与容器》会把这套嵌套彻底拆开：虚拟化在「一台机器」之上再造出多台虚拟机器，把多处理器与集群的思想又推进了一层。

此外，现代计算环境还要加上**移动与嵌入式**这一支：它们受制于电池与功耗预算，调度与任务管理都要考虑能耗，这是台式机时代几乎不存在的维度；而**实时与物联网**则把「在截止期内完成」的要求推广到最边缘的设备。硬件拓扑的多样性，决定了操作系统设计的多样性——这正是接下来几篇要逐步展开的地图。

## 6 公式解析：Amdahl 定律

多处理器到底能换来多少加速？这个问题由阿姆达尔在 1967 年用一条公式回答：设一个程序中**可以并行化**的部分占比为 $P$，不可并行的串行部分占比为 $1 - P$，用 $N$ 个处理器执行，则加速比为

$$S = \frac{1}{(1 - P) + \dfrac{P}{N}}$$

逐步拆解：

- **$P$**：可并行部分的时间占比。例如矩阵乘法里彼此独立的分块计算，它们可以被摊到 $N$ 个核上。
- **$1 - P$**：串行部分的时间占比。$P + (1 - P) = 1$，整个程序的执行时间被归一化为 1。
- **分母中的 $(1 - P)$**：串行部分**原样保留**——它无法受益于更多处理器。
- **$P / N$**：并行部分用 $N$ 个处理器后的理想耗时——假设无通信开销、负载完全均衡。
- **分母 $(1 - P) + P/N$**：并行后的总时间 = 串行部分 + 并行部分被 $N$ 整除。
- **取倒数**：原时间（1）除以新时间，即加速比。

代入数值感受一下：设 $P = 0.5$（一半可并行）、$N = 8$，则 $S = 1 / (0.5 + 0.5/8) = 1 / 0.5625 \approx 1.78$。**8 个处理器只换来 1.78 倍**——另一半串行时间锁死了收益。再看乐观情形，$P = 0.9$（90% 可并行）、$N = 16$：$S = 1 / (0.1 + 0.9/16) = 1 / 0.15625 = 6.4$，仍然远不到 16。当 $N \to \infty$ 时，$S$ 趋近于 $1 / (1 - P)$，这是并行加速的**硬上限**——串行部分占 10%，上限就是 10 倍。

| 可并行占比 $P$ | $N = 2$ | $N = 8$ | $N = 16$ | 上限 $1/(1-P)$ |
| --- | --- | --- | --- | --- |
| 0.5 | 1.33 | 1.78 | 1.88 | 2 |
| 0.8 | 1.67 | 3.33 | 4.44 | 5 |
| 0.9 | 1.82 | 4.71 | 6.40 | 10 |<span class="marginnote">Amdahl 定律假设问题规模固定，属于固定负载的强扩展（strong scaling）。若允许问题规模随处理器数目一起增长（固定时间的弱扩展，weak scaling），Gustafson 定律给出更乐观的结论——大模型训练正是靠「把批次切得更大、模型并行切分得更细」逼近弱扩展的收益。这两条定律在第三级《并行计算》与第四级《AI 基础设施》专题会反复出现。</span>

**重点：Amdahl 定律不是「多处理器没用」，而是「多处理器只对可并行部分有效」。** 工程上的应对之道有两条：一是把串行占比 $1 - P$ 压小（减少锁、减少串行依赖、隐藏通信）；二是让 $N$ 尽量大，把串行占比摊薄。这两条思路会反复出现在后续调度与分布式章节里，也是我们看任何「并行性能报告」时首先要问的问题：**加速比相对理想线性差了多少，差在哪一部分？**

## 7 小结

- 单处理器是基础模型，多处理器/多核是它的自然延伸；GPU 等是「从设备」而非「平等处理器」。
- **SMP**：所有 CPU 平等共享内存，现代主流；**AMP**：主从结构，主处理器是瓶颈。
- 多核、UMA、NUMA 是「多处理器」的三种具体形态；NUMA 要求调度器感知内存位置。
- 缓存一致性协议保证多核看到一致的内存视图，但「并发修改」仍需软件同步原语。
- **集群**是网络连接的松散耦合系统，分高可用、负载均衡、HPC 三类，常配 SAN。
- 集群通信靠网络（毫秒级），多处理器通信靠内存（微秒级）——耦合度决定程序设计风格。
- Amdahl 定律 $S = \dfrac{1}{(1-P)+P/N}$：加速比受串行部分 $(1-P)$ 锁死，$N \to \infty$ 时上限为 $1/(1-P)$。

在下一节，我们回到操作系统自身的设计：无论硬件是单核还是多核，OS 都必须先回答一个更根本的安全问题——**如何把「用户程序」与「操作系统自己」隔开**。这就是**用户态与内核态**的双模式操作。
