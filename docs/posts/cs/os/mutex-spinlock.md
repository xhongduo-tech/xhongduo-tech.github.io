## 为什么从互斥锁与自旋锁开始

硬件原语给了我们原子操作，但直接拿 Test-and-Set 写代码太原始——于是操作系统与语言库把它们包装成两类最常用的锁：**互斥锁（Mutex）**与**自旋锁（Spinlock）**。两者的差别一句话：**抢不到锁时，Mutex 让线程睡觉，Spinlock 让线程死等。** 这一节把这两兄弟的机制、选型与陷阱讲透。<span class="marginnote">回顾《硬件同步原语》：TS 实现的自旋是「忙等」。Mutex 与 Spinlock 的区别，本质上就是「忙等 vs 睡眠」的区别——它是「等一把锁」这件事上最根本的工程权衡。</span>

## 1 互斥锁（Mutex）：抢不到就睡觉

**互斥锁（mutex, mutual exclusion）**：一把「一次只能一个持有者」的锁。线程拿锁（`lock()`），用毕还锁（`unlock()`）。若锁已被占：

线程**睡眠（阻塞）**，让出 CPU。
锁释放时，**唤醒**一个等待线程。

```c
pthread_mutex_lock(&mutex);     /* 抢不到就睡眠，让出 CPU */
/* …… 临界区 …… */
pthread_mutex_unlock(&mutex);   /* 释放锁，唤醒等待者 */
```

Mutex 的三个要素：

**原子抢锁**：拿锁用硬件原语（CAS）实现，保证并发安全。
**等待队列**：抢不到锁的线程挂入队列睡眠，不烧 CPU。
**唤醒机制**：解锁时从队列中唤醒等待者。

**Mutex 的开销**：拿锁/放锁快（原子指令 + 快速路径），但「抢不到 → 睡眠 → 唤醒」要两次上下文切换（睡下去一次、醒来一次），代价是微秒级的。<span class="marginnote">pthread_mutex 有「自适应」优化：先自旋一小会儿，还抢不到才睡。这把「短临界区用自旋、长临界区用睡眠」两种策略合进了同一把锁——现代用户态锁普遍这么做。</span>

## 2 自旋锁（Spinlock）：抢不到就死等

**自旋锁（spinlock）**：抢锁失败时**原地循环重试**（自旋），直到抢到为止，线程不睡眠、不切换上下文。

```c
while (test_and_set(&lock)) ;   /* 忙等：原地自旋，直到拿到锁 */
/* …… 临界区（必须极短）…… */
lock = 0;                        /* 释放锁 */
```

自旋锁的适用条件：

- **临界区极短**（几十条指令内）：自旋几十纳秒就能拿到锁。
- **持有者不会睡眠**：若持有者睡着，自旋者会无限烧 CPU 等一个醒不来的人。
- **单核上不能抢占**：单核自旋锁需关中断，否则死锁。

**为什么有时自旋更快**：睡眠-唤醒的两次上下文切换是微秒级，而短临界区自旋可能只有几十纳秒——**与其睡下去再醒，不如转圈等到锁释放**。内核里大量短临界区（保护链表头、计数器）都用自旋锁。

**辨析｜易错点：** 「自旋锁比互斥锁好」是大错特错——**自旋锁省的是切换开销，烧的是 CPU 时间**。临界区一长，自旋者空转烧 CPU，比睡眠浪费得多；且自旋锁持有者若被抢占或睡眠，等待者会「死等」到天荒地老（甚至死锁）。**自旋锁只属于「极短临界区 + 持有者不睡眠」的场景，用户态程序几乎不该用裸自旋锁。**

## 3 选型原则与对比

| 维度 | 互斥锁 Mutex | 自旋锁 Spinlock |
| --- | --- | --- |
| 等待方式 | 睡眠，让出 CPU | 忙等，占着 CPU |
| 抢不到的开销 | 两次上下文切换（微秒级） | 空转烧 CPU（纳秒级起） |
| 适合临界区 | 中长、可能阻塞 | 极短、不可阻塞 |
| 持有者可否睡眠 | 可以 | **不可以**（会死锁） |
| 内核/用户态 | 用户态主力 | 内核短临界区主力 |
| 公平性 | 有等待队列，较公平 | 无队列，饥饿可能 |

**选择口诀**：临界区短且无阻塞 → 自旋；临界区长或可能阻塞 → 互斥。

## 4 死锁与锁的正确姿势

锁用不对，最经典的下场是**死锁**（详见第七篇）。常见错误：

- **忘记解锁**：异常路径没释放锁，其他人永远等不到。
- **锁的顺序不一致**：两个线程以相反顺序拿两把锁，互相卡死。
- **自旋锁持有者睡眠**：转圈者永远等不到。

**工程铁律**：

1. **锁的粒度越小越好**：只在临界区期间持有锁，别把无关代码包进去。
2. **锁的顺序全局一致**：多把锁时按固定顺序获取，避免死锁。
3. **用 RAII/作用域释放**：C++ 的 `std::lock_guard`、Go 的 `defer`、Python 的 `with` 语句，让异常也能解锁。

**辨析｜易错点：** 「锁能解决所有并发问题」是幻觉。**锁解决「互斥」，不解决「顺序与组合逻辑」**——两个线程各自持锁却互相等对方的锁（死锁）、或者拿着锁做与共享数据无关的事（性能与正确性双双受损）。锁是工具，用错场景比不用更糟。

## 5 小结

- **Mutex**：抢不到锁就睡眠，让出 CPU；用硬件原语 + 等待队列 + 唤醒实现。
- **Spinlock**：抢不到锁就忙等转圈，不睡眠；只适合极短临界区。
- 选型：**短且无阻塞用自旋，长或可能阻塞用互斥**。
- 自旋锁持有者不能睡眠，否则等待者死等甚至死锁。
- 锁的正确姿势：粒度小、顺序一致、RAII 释放；锁解决互斥而非一切。
