## 为什么从操作系统服务概览开始

前三节我们回答了「操作系统凭什么存在」（目标与作用）、「它运行在什么硬件上」（系统结构、中断、存储、I/O、计算环境）。这一节回到最朴素的用户视角：**操作系统到底替我们做了什么？** 打开文件、打印输出、分配内存、报告错误、让多个程序同时运行互不干扰——这些「服务」是操作系统与用户之间的契约。读懂这份契约，后续的章节（系统调用、进程、内存、文件系统）就都是在解释「每一项服务具体是怎么实现的」。

这一节也是从「操作系统是什么」过渡到「操作系统如何被编程」的桥：服务是抽象承诺，而**系统调用（system call）** 是兑现承诺的编程接口。下一节《系统调用的类型与实现原理》会深入兑现的细节。

## 1 服务的菜单：操作系统为用户做什么

《操作系统概念》把操作系统服务归纳为**面向用户的六大类**与**面向系统的三大类**。先看用户能直接感知到的：

| 服务 | 含义 | 一个栗子 |
| --- | --- | --- |
| **用户界面** | 命令行（CLI）、图形（GUI）、批处理界面 | 终端窗口、桌面系统 |
| **程序执行** | 把程序装入内存并运行，能正常结束或异常结束 | 双击运行一个 App |
| **I/O 操作** | 让程序读写设备，而不必知道设备细节 | `printf` 把字符送到屏幕 |
| **文件系统操作** | 创建、删除、读写、重命名文件与目录 | `cp a.txt b.txt` |
| **通信** | 同一台机器或网络上进程之间交换数据 | 两个程序互发消息 |
| **错误检测** | 检测 CPU、内存、I/O、程序自身的错误并处理 | 除零、磁盘写失败 |

**重点：这些服务有两个共性——它们把「硬件的复杂性」包装成「简单的操作」，并且大多以系统调用的形式提供给程序。** 用户程序不必关心磁盘扇区怎么定位、显存怎么映射，只要说「我要读这个文件」，剩下的交给内核去协调设备。

<span class="marginnote">「错误检测」最容易低估：操作系统不仅要检测硬件错误（如磁盘坏扇区、内存校验错），还要检测<strong>程序错误</strong>（除零、越界、非法指令）。后者中的很多检测其实由<strong>硬件陷阱</strong>触发，再交给内核或进程的信号处理程序——我们上一节《用户态与内核态》讲的内存越界陷阱，就是典型的程序错误检测实例。</span>

## 2 面向系统自身的三类服务

除了直接服务用户，操作系统还要**服务自己**——保证整个系统公平、高效、安全地运转。这三类服务是内务，用户通常感知不到，但没有它们系统会立刻失序：

- **资源分配（resource allocation）**：CPU、内存、文件、I/O 设备都是稀缺资源，操作系统决定「谁、在何时、得到多少」。多用户系统要按配额公平分配；单用户系统也要防止一个失控进程吃光全部内存。
- **记账（accounting）**：记录每个用户、每个进程使用了多少 CPU 时间、多少内存、多少磁盘。多用户系统据此计费；单用户系统用于统计与性能调优，`top`、`ps` 背后的数据源就在这里。
- **保护与安全（protection and security）**：保证一个进程不能访问未经授权的资源，同时外部攻击者不能侵入系统。<span class="marginnote">保护与安全的区别常被忽略：<strong>保护（protection）</strong>是进程与进程、用户与资源之间的访问控制，属于「内务」；<strong>安全（security）</strong>是应对外部入侵（病毒、蠕虫、拒绝服务攻击），属于「边防」。第十四篇《保护与安全》会分别展开这两条线。</span>

**辨析｜易错点：资源分配 ≠ 调度。** 调度（scheduling）通常特指 **CPU 时间**的分配，是资源分配里最精细、最核心的一块；资源分配还覆盖内存、文件、设备等更广义的资源。教材把它们分开讲，是为了让你看清「CPU 调度只是资源管理的一个子问题」——第五篇会专注这一个子问题，而本篇先建立全貌。

三类面向系统的服务有一个共同点：它们不产生用户看得见的结果，却是系统长期稳定运行的隐形前提。缺了资源分配，进程会互相饿死；缺了记账，没人知道资源被谁吃掉了；缺了保护与安全，一切都不可信。

## 3 三层结构：服务、系统调用与系统程序

「操作系统服务」这个短语下面其实压着三个不同的层次，初学者最容易混成一锅：

1. **服务（services）**：抽象的能力描述，如「读写文件」。它回答「**能做什么**」。
2. **系统调用（system call）**：编程接口，是服务的内核入口，如 POSIX 的 `read()`。它回答「**怎么请求**」。
3. **系统程序（system program）**：运行在用户态的工具程序，内部调用系统调用，给终端用户提供现成命令，如 `cp`、`ls`。它回答「**谁来替你按按钮**」。

```bash
cp report.pdf archive/    # 系统程序 cp：在用户态运行，内部多次调用系统调用
ls -l archive/            # 系统程序 ls：读取目录信息并格式化输出
rm -rf /tmp/build         # 系统程序 rm：删除目录树
```

`cp` 的背后是一连串系统调用：`open` 源文件、`open` 目标文件、循环 `read` 一块、`write` 一块、最后 `close` 两个文件。用户只需要记住 `cp` 这一个命令名，甚至不需要知道系统调用的存在。

**重点：用户 → 系统程序 → 系统调用 → 内核服务，是一条完整的调用链。** 系统程序让你不必写 C 代码就能调用系统服务；系统调用让你不必知道内核实现细节；内核服务则是这条链的终点。<span class="marginnote">很多「命令」其实是精心编写的系统程序：文件管理（<code>cp</code>、<code>mv</code>、<code>rm</code>、<code>mkdir</code>）、状态查询（<code>date</code>、<code>ps</code>、<code>who</code>）、程序加载（可执行文件双击即加载）、通信（<code>ssh</code>、<code>ping</code>）、压缩（<code>gzip</code>、<code>tar</code>）。Linux 上它们通常由 coreutils 等用户态软件包提供——操作系统并不把这些工具放进内核。</span>

## 4 系统调用的界面：服务如何兑现

如果说服务是菜单，系统调用就是**点菜的方式**。系统调用按功能分成六类（《操作系统概念》第 2 章）：

- **进程控制（process control）**：创建/终止进程、加载/执行程序、等待进程结束。如 `fork`、`exec`、`wait`。
- **文件管理（file management）**：创建、打开、读写、关闭、删除文件。如 `open`、`read`、`write`、`close`。
- **设备管理（device management）**：请求、释放、读写设备。Unix 把设备当文件处理，所以设备管理常复用文件管理的系统调用。
- **信息维护（information maintenance）**：获取/设置系统时间、进程状态、系统参数。如 `getpid`、`gettimeofday`。
- **通信（communication）**：进程间交换数据，如管道、共享内存、消息传递。
- **保护（protection）**：设置文件权限与访问控制。如 `chmod`。

这六类合起来，正好覆盖了第一节「服务的菜单」里列出的每一项——服务是目的，系统调用是手段。记住这个对应关系，读后续章节时你就知道每一章是在给哪个服务补实现细节。

**辨析｜易错点：系统调用不是「给程序员的函数库」，而是「内核提供的接口」。** 两者的关键差别在**模式切换**：库函数（如 `strlen`）在用户态原地执行，不切换模式；系统调用（如 `read`）每次都要陷入内核，再原路返回。这正是上一节《用户态与内核态》强调的切换成本——优化程序时，「减少系统调用次数」与「降低算法复杂度」同样值得重视，前者常常是后者的几十倍常量开销。

## 5 为什么操作系统不把所有事都做了

看完服务列表，一个自然的问题是：为什么操作系统不把 `cp`、`tar`、甚至编译器都做进内核？答案是「方便」与「安全、灵活」之间的权衡：

- **瘦内核**：内核越小，处于特权态的代码越少，被 bug 或攻击击中的面就越小——这是微内核思想的出发点，见第四篇《微内核结构及其优缺点》。
- **可替换性**：文件系统、shell、编译器都是用户态程序，用户可以换掉、可以升级，不必重装内核。`bash` 换成 `zsh`，不需要动内核。
- **故障隔离**：系统程序崩溃不会拖垮内核——`rm` 写错了顶多删错文件，不会让整个系统蓝屏。

<span class="marginnote">「尽量把功能放到用户态」的原则，就是<strong>最小特权（least privilege）</strong>原则在系统设计上的体现，也是 Unix 哲学「做一件事并做好」的由来。我们第四篇讲内核结构时会看到：内核与用户态的这条分界线到底画在哪里，正是各种架构流派（宏内核、微内核、混合内核）争论的焦点。</span>

## 6 公式解析：一次系统调用的时间去哪了

既然系统调用这么贵，它到底贵在哪？把一次系统调用的全程时间拆开：

$$T_{\text{syscall}} = T_{\text{setup}} + T_{\text{trap}} + T_{\text{dispatch}} + T_{\text{service}} + T_{\text{return}}$$

逐步拆解：

- **$T_{\text{setup}}$**：用户态开销——库函数把参数压栈/放入寄存器、写入系统调用号。
- **$T_{\text{trap}}$**：陷入内核的开销——执行陷阱指令、硬件切换模式位、保存现场（通用寄存器、程序计数器等）。这是普通函数调用**没有**的一项。
- **$T_{\text{dispatch}}$**：内核按系统调用号查表、校验参数（指针是否合法、越界即返回错误码）。校验是安全必需的，但也是开销。
- **$T_{\text{service}}$**：真正的服务执行时间，例如把磁盘数据拷贝进用户提供的缓冲区。
- **$T_{\text{return}}$**：从内核返回用户态——恢复现场、切回用户模式。

对比普通函数调用只需「跳转 + 压栈 + 返回」，系统调用多出的 $T_{\text{trap}} + T_{\text{dispatch}} + T_{\text{return}}$ 就是「保护」的显式成本。

**重点：安全不是免费的——每一次系统调用，都在为上一节的「双模式保护」买单。** 这也解释了为什么性能敏感的程序会尽量减少系统调用次数、改用批量接口（如 `readv`/`writev`、更大的缓冲区），以及为什么 `epoll`、`io_uring` 这类「批量 + 异步」I/O 能成为高性能服务器的核心武器（见第十七篇《io_uring》）。<span class="marginnote">现代硬件上一次系统调用约几百纳秒到几微秒，是普通函数调用的<strong>几十到上千倍</strong>。先把这一差距量化记在心里，再回头看 epoll 与 io_uring 的优化动机，你会更有体感。</span>

## 7 小结

- 操作系统服务分**用户服务**（界面、程序执行、I/O、文件系统、通信、错误检测）与**系统服务**（资源分配、记账、保护与安全）。
- **服务 / 系统调用 / 系统程序**是三个层次：菜单、点菜方式、替你按按钮的工具。
- 系统调用按功能分**六类**：进程控制、文件管理、设备管理、信息维护、通信、保护。
- 系统调用与库函数的本质差别是**模式切换**；「减少系统调用」是性能优化的常识。
- 内核保持「瘦」是出于安全、灵活与故障隔离的考虑——**最小特权**原则。
- 一次系统调用的开销可用 $T_{\text{syscall}} = T_{\text{setup}} + T_{\text{trap}} + T_{\text{dispatch}} + T_{\text{service}} + T_{\text{return}}$ 建模，保护有显式成本。

在下一节，我们将离开「服务是什么」的平面图，进入「服务怎么实现」的施工图——从**系统调用的类型**到**用户态到内核态的完整路径**，把这一节所说的「兑现承诺」落到具体的机制上。
