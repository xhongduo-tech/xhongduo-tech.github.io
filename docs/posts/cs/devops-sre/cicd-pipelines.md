## 为什么从 CI/CD 开始

第 9 篇讲了「变更要安全地流动」，第 10 篇第一法讲了「价值流要快」。但「快且安全」的落地形态是什么？答案是**一条自动化的流水线**——从你敲下 `git push` 的那一刻起，代码就自动进入「构建 → 测试 → 部署 → 观测」的轨道，全程不需要人扛着包跑来跑去。这条轨道就是 **CI/CD（持续集成 / 持续交付）**。

CI/CD 是前面所有理论（canary、回滚、错误预算、反馈回路）在**工程底座**上的交汇点。它也是这一专题里最「工具向」的一篇——但工具只是载体，我们要抓住的是**流水线设计的原则**：每一段做多少、怎么做门禁、怎么回滚，这些原则与具体工具无关。<span class="marginnote">Gene Kim 在《DevOps 手册》里反复强调：deployment pipeline 是组织「对部署的恐惧」的良药——流水线不是自动化工具，是一套「每次变更都被验证、每次部署都可逆」的制度。</span>

## 1 三个概念：CI、CD、持续部署

**CI（Continuous Integration，持续集成）**：代码**频繁地合并**到主干（每天多次），每次合并都**自动构建 + 自动测试**。<span class="marginnote">「集成」的对象是冲突与回归：分支待得越久，合并时的冲突越多、回归越隐蔽。CI 的哲学是「小步快跑，天天集成」，让冲突每天发生、每天解决，而不是发布前一次性爆发。</span>

**CD（Continuous Delivery，持续交付）**：CI 通过后，代码**随时可以部署到生产**——部署是「按按钮」而不是「求神拜佛」。**Continuous Deployment（持续部署）**更进一步：连按钮都不用按，CI 通过自动上线。

| 阶段 | 干什么 | 人要不要管 |
| --- | --- | --- |
| CI | 合并即构建 + 测试 | 自动 |
| CD（交付） | 随时可部署，手动触发 | 按一下 |
| 持续部署 | 测试过就自动上线 | 全自动 |

三者是**递进关系**：没有 CI 的 CD 是空中楼阁，没有 CD 的 CI 只是「自动编译」。而「自动上线」之所以能安全，靠的是第 9 篇的 canary 与回滚——**流水线的自动，必须搭配发布策略的谨慎**。

## 2 流水线的五个阶段

一条典型流水线长这样：

```
git push → 构建(build) → 单元测试(unit) → 集成/冒烟测试 → 镜像/产物归档 → 部署到 staging → 冒烟验证 → 金丝雀 → 生产
```

拆成五个关键阶段，每个阶段回答一个问题：

1. **构建（build）**：把代码变成**不可变的产物**（第 9 篇的 hermetic build）。这里的关键是**可重现**：同一 commit 永远产出同一产物。
2. **测试（test）**：单元测试跑逻辑、集成测试跑模块协作。**易错点：** 测试不是「跑一遍」就完——流水线必须把测试设为**门禁（gate）**：失败即红灯、即阻止进入下一阶段。<span class="marginnote">门禁是流水线的「法官」：允许绿灯批量放行、红灯一票否决。没有门禁的流水线只是一条「自动化传送带」，不是「质量闸门」——这又回到第一法（第 10 篇）「快不是砍门禁」。</span>
3. **交付（package/publish）**：把通过的产物**归档到制品库**（artifact repository），带唯一版本号。这一步让「回滚」有了对象：回滚 = 部署上一个版本号。
4. **部署（deploy）**：把产物部署到目标环境。**staging（预发）先验证，再上生产**；生产侧配合 canary / staged rollout（第 9 篇）。
5. **验证与观测（verify）**：部署后自动跑冒烟验证 + 接上监控（第 14 篇），确认新版本「真的在干活」。**易错点：** 很多流水线到「部署完成」就停了，却漏了「部署后验证」——部署成功 ≠ 服务正常，必须用真实指标确认。

## 3 工具地图：Jenkins、GitLab CI 与 ArgoCD

工具是原则的载体，把常见工具摆进流水线坐标里，你就有了选择地图：

| 工具 | 类型 | 特点 | 适用 |
| --- | --- | --- | --- |
| Jenkins | CI 调度器 | 插件生态庞大，自由度高 | 复杂、异构的流水线 |
| GitLab CI | 内置 CI/CD | 与代码仓库一体化，`.gitlab-ci.yml` 即代码 | 单一平台团队 |
| ArgoCD | **GitOps** 控制器 | 以 Git 为唯一事实源，声明式同步到集群 | Kubernetes 环境 |
| GitHub Actions | CI/CD | 仓库原生，marketplace 丰富 | GitHub 团队 |

**关键区分：CI 工具与 CD 工具不一定同源。** 很多团队用 GitLab CI 做 CI，用 ArgoCD 做 CD——前者负责「构建与测试」，后者负责「把声明好的状态同步到生产」。

**GitOps 是 CD 的当代主流形态**：**以 Git 仓库里的声明（desired state）为唯一事实源，控制器自动把集群收敛到该状态**——改生产 = 改 Git 仓库 = 走 MR review = 自动同步。<span class="marginnote">GitOps 的核心价值是把「变更管理」统一进代码工作流：第 9 篇要求的「可审查、可回滚」，在 GitOps 里天然成立——回滚 = revert 一次 commit，审计 = 翻 MR 历史。ArgoCD 就是这个模式的控制器。</span>

## 4 流水线即代码：从「点按钮」到「写配置」

现代流水线的关键纪律：**流水线本身必须是代码**——Jenkinsfile、`.gitlab-ci.yml`、GitHub Actions 的 YAML，都进版本库、走 review。<span class="marginnote">这条纪律把第 5 篇的「自动化 + 版本化」落到了开发工具自身：流水线会被重构、会被评审、会像代码一样演进——这就是「吃自己的狗粮」。手工在 Web UI 里攒的流水线，没有人能 review，也没有人能回滚。</span>

**公式解析：流水线的吞吐。** 流水线有多快，直接影响变更面。设单次提交的平均验证时长为 $t$，日均提交数为 $N$：

$$
\text{吞吐（每日通过的提交）} = \frac{N \cdot w}{1 + \frac{N \cdot t}{C}}
$$

- $C$：流水线并行能力（能同时跑多少条）。
- $w$：通过率（门禁放行比例）。

直觉：**当 $N \cdot t > C$（提交量 × 时长超过并行容量）时，流水线开始排队，吞吐不再随提交增长**——这就是「流水线拥堵」。它给出的工程结论很实用：流水线**先求快（压缩 $t$）、再求并行（扩大 $C$）**；而排队中的坏消息是**红灯会让整个队列等待**——这正是「测试要快、要分层（快测慢测分离）」的理由。

## 5 流水线的三代演进：从脚本到平台

认识流水线的演进脉络，能帮你判断「自己团队的工具该往哪走」：

**第一代：脚本驱动的发布**——发布靠维护人员跑一串 shell 脚本。灵活但**不可审查、不可复现**：脚本在哪台机器上、依赖什么环境，都只有写脚本的人知道。这正是第 13 篇 IaC 要消灭的「宠物」式做法。

**第二代：CI/CD 工具**——Jenkins、GitLab CI 把「构建、测试、部署」固化进流水线定义文件，可版本化、可 review、可复用。绝大多数团队停在这一代，已经能获得大部分收益。

**第三代：平台与 GitOps**——流水线不再是「管发布的人」的工具，而变成**面向全体开发者的自助平台**：开发提交代码，平台自动完成构建、测试、灰度、观测；CD 由 GitOps 控制器（如 ArgoCD）把声明状态同步到生产。**这一代把「发布」从「有人负责的操作」变成「无人值守的制度」。**

**易错点：** 不是三代都要走完。判断标准是**组织的发布频率与规模**：小团队第二代足够；发布频繁、多人并行的大团队才需要第三代。**工具升级的代价必须由「发布摩擦」的下降来偿还**——为了「赶时髦」迁移到 GitOps，是常见的时间黑洞。最后补充一个反直觉的结论：**流水线本身不是目标，发布的安全与速度才是**——工具只是把第 9 篇的「小步、可回滚、可观测」原则制度化；把流水线当目的，就本末倒置了。一个实用的起步建议：**先保证「每个 commit 都能一键回滚」，再谈「自动发布」**——没有可回滚的基线，流水线跑得越快，翻车越响。

**延伸：流水线的成功标准。** 怎么判断流水线建得好不好？三个信号：**第一，绿灯率**——多数提交一次通过门禁，说明代码质量与测试质量都健康；**第二，从提交到生产的时长**——它直接反映发布摩擦；**第三，回滚的容易程度**——出问题 30 秒内能不能回到上一个版本。这三个信号比「流水线用了什么工具」重要得多，因为它们直接对应第 10 篇第一法的「流动」质量。还有一个反直觉的信号：**流水线越「无聊」越好**——稳定复现、极少人工干预的流水线才是好流水线；天天要人盯着、手动救火的流水线，本身就是 Toil（第 4 篇）。最后：把流水线的健康度本身也做成 SLI（第 2 篇）——绿灯率、时长、回滚时长进仪表盘（第 14 篇），流水线就拥有了自己的「错误预算」。

## 6 小结

- **CI**：频繁合并 + 自动构建测试；**CD**：随时可部署；**持续部署**：全自动上线。
- 流水线五阶段：**构建 → 测试（门禁）→ 交付（制品库）→ 部署（staging→canary→生产）→ 验证观测**。
- 工具各有定位：**Jenkins/GitLab CI 管 CI，ArgoCD（GitOps）管 CD**；GitOps 以 Git 为唯一事实源。
- **流水线即代码**：Jenkinsfile/YAML 进版本库走 review，才能被 review、被回滚。
- 吞吐受并行容量约束（$N \cdot t > C$ 即拥堵）：先压缩单次时长，再扩大并行。

- 三代演进：**脚本 → CI/CD 工具 → 平台/GitOps**；不是每代都要走完，按发布频率与规模选。
- 工具升级的代价必须由**「发布摩擦」的下降**来偿还——为赶时髦迁移，是常见的时间黑洞。
- **流水线不是目的，发布的安全与速度才是**——先保证一键回滚，再谈自动发布。

在下一节，我们把「部署的目标对象」也代码化：服务器、网络、数据库这些基础设施，凭什么能用 Git 管理、用代码审查——这就是 **基础设施即代码**。流水线解决了「代码怎么进生产」，而 IaC 回答「生产本身怎么被代码管」——两者合起来，才是「一切皆代码」的完整拼图。
