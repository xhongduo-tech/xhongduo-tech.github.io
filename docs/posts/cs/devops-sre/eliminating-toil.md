## 为什么从 Toil 开始

上一篇我们看到：SRE 团队「最多一半时间做手工运维」是 Google 的宪法。但「最多一半」只是一个帽子，**帽子底下装什么、装多少，才是真正的考题**。一个 SRE 从早到晚的活儿，哪些是必须做的、哪些是越做越糟的？这需要一把手术刀，把日常劳动切成「有长期价值」和「没有长期价值」两堆——那把手术刀就是 **Toil 的判定标准**。

理解 Toil，是理解 SRE「软件化运维」的入口：**只有先识别出哪些劳动值得消灭，自动化（第 5 篇）才有明确的对象**。这也是它排在本书第 5 章、紧跟在风险与预算之后的原因——预算管「我们敢冒多少风险」，Toil 管「我们的精力花在哪里」。

## 1 定义：Toil 不是「辛苦」，是「重复且没有持久价值」

**Toil（苦工/琐碎劳动）**：运维工作中那些**手动的、重复的、可以自动化的、战术性的、没有持久价值**的工作。<span class="marginnote">SRE Book 第 5 章给的定义是：Toil is the kind of work tied to running a production service that tends to be manual, repetitive, automatable, tactical, devoid of enduring value, and that scales linearly as a service grows。六个特征缺一不「准」。</span>关键词是**「没有持久价值」**——做完一次，世界没有变得更好，下次还得重来。

判别 Toil 的**六条特征**（Google 的官方清单，命中越多越该消灭）：

| 特征 | 含义 | 反例（不算 Toil） |
| --- | --- | --- |
| 手动（Manual） | 需要人手去操作 | 自动化后无需人 |
| 重复（Repetitive） | 周期性地反复出现 | 每次都不一样的调查 |
| 可自动化（Automatable） | 机器可以做 | 需要人类判断的取舍 |
| 战术性（Tactical） | 被动响应，无规划 | 有明确设计目标的工作 |
| 无持久价值（No enduring value） | 做完不留财富 | 写监控、写文档、修 bug |
| 线性增长（O(scale)） | 业务翻倍它跟着翻倍 | 一次性的架构改造 |

**易错点：累 ≠ Toil，Toil ≠ 所有运维工作。** 一次通宵排查线上事故，虽然累，但带来了**对系统的深刻理解**，这是工程资产；而每天点 30 次「重启这五个节点」的按钮，虽然轻松，却是纯 Toil——因为它既训练不了判断力，也没有改善系统。<span class="marginnote">Google 有一句犀利的表述：a system that requires a human to fix it is a system that will fail again——维修动作本身不改进系统，只推迟下一次同样的维修。</span>判断标准是「做完之后世界变了没有」，不是「累不累」。

## 2 为什么 Toil 是可靠性的隐形杀手

Toil 的坏处绝不只是「浪费人力」。它从三个方向腐蚀系统：

1. **耗尽容错预算（工作量的预算）**：每个 SRE 每周都有隐性预算。大量 Toil 意味着没有时间做改进，错误预算之外的「能力预算」同样告急。<span class="marginnote">SRE Book 建议把 Toil 占总工作量的比例也设成 SLO 来监控：Google 的经验是 SRE 的 Toil 占比应低于 50%，理想是低于 25%，高于 50% 则团队陷入「纯消防」状态。</span>
2. **让团队失去学习**：重复劳动不产生认知升级。做了一年「重启脚本」，你对系统的理解不比第一天多。
3. **放大故障风险**：手工操作是失误高发区。越是关键时刻（半夜、高压），手工步骤越多越容易出错——**Toil 本身就是事故源头**。

第三条尤其反直觉：**SRE 手工劳动越多，系统越脆弱**。因为手工步骤不可测试、不可回滚、不可审查，本质上是一条「待执行的 bug」。

## 3 消灭 Toil：自动化之前的四步

消灭 Toil 有清晰的优先级，自动化只是其中一环：

1. **买（Buy）**：用现成产品或托管服务替换自建维护——「云上买不到人力，但能买到托管」。
2. **改产品（Change the product）**：修改产品行为，让某个运维步骤彻底消失。比如「每周手工合并分区表」——把分区策略改对，合并需求就不存在了。<span class="marginnote">这条最有意思：Google 官方也承认，有些 Toil 的根源是产品设计——e.g. 一个每天需要人工清理临时文件的系统，正确解法不是写清理脚本，而是让产品自己管理生命周期。</span>
3. **自动化（Automate）**：写脚本、建平台，把步骤交给机器。这是第 5 篇的主场，但记住——**自动化的前提是步骤已经稳定可描述**，把不稳定的流程自动化，只是把混乱提速。
4. **放任不管（Leave it）**：真的低危、低频的步骤，评估后保留——不是所有 Toil 都值得消灭，预算要花在刀刃上。

**辨析｜易错点：** 优先级不能反过来。常见的失败模式是**一上来就写自动化脚本**，结果：产品行为本可以改掉的需求，被脚本永久固化成了系统负担。**先问「能不能让这件事不再存在」，再问「能不能让机器来做」**——消灭（eliminate）优于自动化（automate）。

## 4 公式解析：什么时候值得自动化

Toil 消灭的决策，可以写成一道成本账。设某项操作：

$$
E(\text{人工}) = n \times t \times c, \qquad E(\text{自动化}) = \frac{C_a}{T}
$$

- $n$：每周发生次数（frequency）。
- $t$：每次人工处理耗时。
- $c$：人工的单位成本（工程师时薪）。
- $C_a$：开发自动化方案的总投入；$T$：自动化方案的生命周期（用多少周摊薄）。

直觉：**当每周人工成本 × 生命周期，大于一次性自动化投入时，就该自动化**。SRE Book 里的经验判据是「人工时间占比」：某项操作消耗的工程师时间占总工时比例超过 50%（或绝对量可观），就值得投入自动化。<span class="marginnote">Google 给出的简化法则：如果某项工作「足够耗时、足够频繁、足够稳定」，就写工具；反之，写在 wiki 里作为 runbook 即可。完美的自动化是追求目标，但不是每个按钮都值得建一座工厂。</span>

**注意公式隐藏的陷阱**：$n$（频率）是会变的。业务翻倍时，Toil 线性翻倍（这是 Toil 的第六特征），于是「今天算下来不划算的自动化，明年就划算了」——**决策要在「未来负载」上做，而不是「当前负载」**。这与第 8 篇容量规划的「按峰值规划」是同一个道理。

## 5 识别 Toil：一套可以拿去用的自我检查

「这是不是 Toil」不该靠感觉，SRE Book 给的工具是一套**可打分的检查表**。每周花 15 分钟，把上周做的运维任务列出来，逐条过六问：

| 问题 | 是 → 加 1 分 |
| --- | --- |
| 需要人手去执行吗？（手动） | 是 |
| 是不是每周都要重复做？（重复） | 是 |
| 机器是否本可以替我做？（可自动化） | 是 |
| 是否是被动响应、没有规划？（战术性） | 是 |
| 做完之后，系统是否没有变得更好？（无持久价值） | 是 |
| 业务量翻倍时，它是不是也翻倍？（线性增长） | 是 |

**得分 ≥ 4 的任务，就是该消灭的 Toil**，进入消灭优先级（买 → 改产品 → 自动化 → 放任，见 §3）。得分 1–2 的低频操作，写进 runbook 留待观察即可。

实战中 Google 还给出了一个补充指标：**团队每个季度的 Toil 占比**（Toil 工时 ÷ 总运维工时）。占比高于 50% 时，团队事实上处于「救火模式」，任何改进计划都会落空；理想区间是 25% 以下。把 Toil 占比当作 SLO 来追踪，是让「消灭 Toil」这件事从口号变成指标的落法。

容易忽略的盲区：**Toil 常常披着「必要」的外衣**——「必须有人盯着这十来个 cron 任务，因为没人写自动化」。这时要追问的不是「该不该盯」，而是「为什么没人写自动化」——答案往往是优先级被一次次「救火」挤掉。**把 Toil 记进 backlog、排进迭代，和记 bug 一样正经**——它本来就是系统缺陷的一部分，详见第 9 篇「变更要可回滚、可自动化」的视角。

**延伸：Toil 与团队结构的因果。** Toil 占比高，往往不只是「自动化不够」——它常常是**组织结构的信号**：如果某个系统的 Toil 常年压不低，追问「为什么没人有权改它」，答案往往是「责任分散、没人有授权」。Google 的经验：**给 Toil 高的服务指定明确的 owner，是压降 Toil 的第一步**——有主人，才有消灭它的动力；没主人，它只是「大家的事」。另一个细节：**消灭 Toil 要防止「自动化孤儿」**——自动化脚本没人维护、没人测试，三年后变成新的 Toil（修脚本的时间比手工操作还长）。这就是第 5 篇「自动化要像产品一样迭代」的原因。最后提醒：Toil 的消灭不是「一次突击」，而是「持续的对账」——把 Toil 占比放进季度复盘（第 6 篇）的议程，让它像 SLO 一样被追踪、被设目标。

## 6 小结

- **Toil**：手动、重复、可自动化、战术性、无持久价值、线性增长的手工劳动。
- 判定标准是「做完世界变没变」，**不是累不累**；通宵排障不算 Toil，天天点重启算。
- Toil 从**能力预算、团队学习、故障风险**三个方向腐蚀可靠性。
- 消灭优先级：**买 → 改产品 → 自动化 → 放任**，先消灭后自动化。
- 自动化决策做成成本账：$\text{人工成本} \times \text{生命周期} > \text{自动化投入}$ 就该自动化。

- **Toil 占比可用 SLO 追踪**：高于 50% 即「救火模式」，理想区间在 25% 以下。
- 消灭优先级永远是**买 → 改产品 → 自动化 → 放任**，先让「这件事不再存在」，再谈「让机器来做」。
- Toil 常常披着「必要」的外衣，要像记 bug 一样把它记进 backlog——它本就是系统缺陷的一部分。

在下一节，我们把「自动化」这个大词展开：它到底带来什么、何时不做、以及**简单性**为什么是可靠性的前提——这就是 **自动化与简单性**。Toil 识别出「该消灭的活儿」，而自动化与简单性提供「怎么消灭得干净」的答案。
