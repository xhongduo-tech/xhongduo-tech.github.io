## 为什么从流处理模型开始

上一节 Kafka 把「事件」持久化成了日志，但日志只是**载体**——真正要让数据活起来，需要在流上做**连续计算**：实时聚合、窗口统计、告警触发。而流计算的第一课，是比批处理多出一个惊人的麻烦：**没有「固定边界」**。批处理对一个表跑 SQL，数据集合是静止的；流处理面对的是无穷事件，**「算到哪算完」「哪条数据算迟到」**成了全新问题。Hueske & Kalavri《Stream Processing with Apache Flink》第 2 章用一整章回答「一分钟到底是什么」，第 6 章讲窗口算子；Kleppmann《DDIA》第 11 章则从「推理时间」的角度讲透事件时间与窗口。**这一节是所有流计算（Flink、Kafka Streams、Spark Streaming）共同的理论地基。**

## 1 三种时间：事件时间、摄取时间、处理时间

一个事件从产生到被处理，至少经历三个时刻，流计算把「按哪个时间分组」彻底显式化：

- **事件时间（event time）**：事件真实发生的时刻，由事件自己携带（如埋点里的 `ts` 字段）。
- **摄取时间（ingestion time）**：事件到达消息系统（如 Kafka）的时刻，由系统打上。
- **处理时间（processing time）**：事件被流处理引擎处理的时刻，即机器本地时钟。

三种时间的差别在「乱序与延迟」上暴露无遗。网络抖动、客户端离线、批量上传，都会让事件**乱序到达**——`ts=10:01` 的事件可能在 `ts=10:00` 之后很久才到。若按处理时间聚合「10 点这一分钟」，会得到错误的边界：10:01 的数据被分进 10:02 的窗口，10:00 延迟到的数据被算进 10:01。<span class="marginnote">Kleppmann 在《DDIA》第 11 章特意举了手机埋点的例子：用户在地铁里离线，到站后手机一口气上传几百条带时间戳的事件——这时处理时间与事件时间可能相差数小时。**「事件发生时刻」才是业务关心的时刻**，处理时间只是引擎的辅助信息。</span>结论很干脆：**要做正确的流计算，必须用事件时间 + 容错机制（水位线）。**

## 2 水位线：事件时间的时钟

问题随之而来：事件时间无序，引擎怎么知道「10:00 这个窗口的数据到齐了，可以计算了」？答案是**水位线（watermark）**——一个流上的标记，声明「**事件时间早于水位线的事件，之后不会再有（或极少再有）**」。它本质是「引擎对事件时间进度的一种带误差的估计」。

**水位线（watermark）与事件时间的关系式**：设流中已观测到的最大事件时间为 $T_{\max}$，允许的最大乱序延迟为 $D$，则

$$
W(t) = T_{\max} - D
$$

引擎一旦收到时间戳为 $T_{\max}$ 的事件，就把水位线推进到 $T_{\max} - D$，随后**所有结束时间早于 $W(t)$ 的窗口立即触发计算**。分三步理解：

- **第一步，为何是「减去」而非「等于」**：若 $W = T_{\max}$，等于断言「永远不迟到」——一条晚到的数据就会永远错过已触发的窗口。减去 $D$ 是**用「多等一会儿」换「迟到数据大多能进对窗口」**。
- **第二步，谁决定 $D$**：$D$ 来自对数据源延迟分布的估计。$D$ 越大，迟到数据进对窗口的概率越高，但结果越晚产出（延迟越大）；$D$ 越小，结果越及时，但迟到丢弃越多。
- **第三步，晚于水位线的数据怎么办**：超出 $W$ 才到达的数据属「迟到数据」，默认丢弃，但 Flink 可把它们路由到**旁路输出（side output）**做修正或重算。

**辨析｜易错点：** 水位线不是「某条数据的属性」，而是**跟随流推进的全局标记**——它由 Flink 的 `WatermarkStrategy` 周期性地随记录下发，下游算子按「收到的最大水位线」推进自己的时钟。混淆「水位线」与「事件时间」是流计算最常见的入门错误。

## 3 窗口语义：聚合的容器

聚合必须落在有限集合上，于是流计算用**窗口（window）**把无穷流切成有限块。三大类窗口语义来自《Stream Processing with Apache Flink》第 6 章：

- **滚动窗口（tumbling window）**：固定长度、互不重叠，如每 5 分钟一个窗口 `[00:00, 00:05)`。
- **滑动窗口（hopping / sliding window）**：固定长度、固定间隔滑动，窗口之间重叠，如每 1 分钟滑动一个 5 分钟窗口——用于「最近 5 分钟的移动平均」。
- **会话窗口（session window）**：不按时间长度，而按「活跃间隙」切分——超过 `gap` 无事件就收口。适合用户行为分析（一次访问 = 一段连续活跃）。<span class="marginnote">窗口语义的选择是「业务问题翻译」：要固定时间粒度选滚动/滑动，要「连续活动段」选会话。Kafka Streams、Spark Structured Streaming 的窗口 API 与 Flink 一一对应，学一套通三家。</span>

窗口内聚合的经典实现是**增量聚合**（`reduce`/`aggregate`）加**触发（trigger）**：数据逐个进入窗口做增量更新，水位线越过窗口末尾时触发最终输出——既算得及时，又不会为每个元素全量重扫。

## 4 Exactly-Once：从「单算子」到「端到端」

窗口算错了能重算，但**算重了**怎么办？传递语义在流计算里同样有三档，Flink 的目标是**精确一次（exactly-once）**。其三层含义：

- **算子内**：每个事件只被状态更新一次——靠**分布式快照（Checkpoint）**实现，失败后从快照恢复，重放日志但用状态去重。
- **端到端**：消费 Kafka → 计算 → 写回 Kafka/数据库，全程不重不漏——需要**两阶段提交**（Kafka 事务 + Flink 的 TwoPhaseCommitSinkFunction）协同。
- **关键限定**：精确一次是「有状态算子 + 可回放源 + 支持两阶段提交的汇」三者齐全才成立。若汇是普通文件或无法原子提交的系统，只能退化为**至少一次**。<span class="marginnote">Kleppmann《DDIA》第 11 章强调：精确一次常被宣传为「不会出错」，实则是「通过原子提交或幂等把错误掩盖」。设计时先问「我的终点能不能参与两阶段提交」，再谈语义承诺。</span>

## 5 小结

- **事件时间 / 处理时间 / 摄取时间**三者分离，正确流计算必须以事件时间为准。
- **水位线**是事件时间的带误差时钟：$W = T_{\max} - D$，用「多等 $D$」换迟到数据进对窗口。
- **滚动 / 滑动 / 会话**三类窗口对应三种聚合业务，选择窗口语义就是翻译业务问题。
- **精确一次**需「状态快照 + 可回放源 + 两阶段提交汇」三者齐全，否则退化为至少一次。
- 流处理模型的本质：**在无穷、乱序、会失败的世界里，把「什么时候算完」变成可控制、可恢复的工程决策**。

在下一节，我们把这些模型装进 Flink 的引擎里——看看**状态后端、Checkpoint 算法与异步屏障**是如何把「理论语义」落地成「每 30 秒一次不阻塞计算的一致性快照」的。
