## 为什么从流批一体开始

前面几节我们各学了一手：Kafka 管流、Flink 算流、湖仓存批。

可现实中它们必须**协同**：同一份业务既要有 T+1 的批量对账，又要有秒级实时看板，两套逻辑各自维护——这就是 **Lambda 架构**的宿命。

这一节回答一个彻底的问题：**能不能只用一套系统、一套 SQL，同时表达「批」与「流」？**

Kleppmann《Designing Data-Intensive Applications》第 10 章讲批处理、第 11 章讲流处理、第 12 章展望二者的统一；Apache Flink 的 Flink SQL 则是「统一」最完整的工程实现。**流批一体不是新瓶子装旧酒，而是把「流是默认、批是流的特殊情况」这个视角真正产品化。**

## 1 Lambda 架构：批流双轨的代价

Nathan Marz 在 2011 年提出 **Lambda 架构**：同一份数据同时跑两条轨道：

- **批处理层**（Spark/Hive）：精确、可重算、覆盖全量。
- **速度层**（Storm/Flink）：低延迟、近似、只覆盖最新窗口。
- **服务层**：把两者结果合并输出给查询。

它的代价是三份：

- **逻辑写两遍**：同一聚合的批版与流版必须各自实现并保持一致。
- **结果难对账**：批结果与流结果口径不同，用户不知道信哪个。
- **运维翻倍**：两套作业、两套监控、两套调优。

Jay Kreps 在 2014 年的博客《Questioning the Lambda Architecture》里直指：**如果流处理能做到「精确、可重算」，就根本不需要两条轨道**——这是 Kappa 架构的思想宣言。<span class="marginnote">Lambda 最反直觉的地方是：两个「都对」的答案会同时出现在一张报表上。Marz 最初用「批结果为准、速度层只补最新数据」调和，但这等于把「不一致」转嫁给使用者，问题没消失，只是换了位置。</span>

Lambda 并非纸上谈兵——它曾支撑 Twitter 的实时分析（Marz 的 BackType 被 Twitter 收购后成为 Storm 的来源之一）。这套「批求准、流求快」的务实分工在 2010 年代前半段是唯一现实解，因为当时的主流流引擎（Storm 的 at-least-once、早期 Spark Streaming 的微批）确实做不到「精确且可重算」。**是流引擎的成熟，才让 Kappa 从理想变成可行**——架构的进化永远跟着引擎的能力走。

## 2 Kappa 架构：一切皆流

**Kappa 架构**（Kreps 提出）的立场极简：**把整个数据处理做成一条流**。

数据先进 Kafka（保留期调长，作为「可重放的日志」），Flink/Spark Structured Streaming 消费它做计算，结果写下游。需要「重算历史」？不是另开批作业，而是**换一个消费位点（offset）从头再跑一遍流**——因为 Kafka 日志还在，流作业本身就能回放历史。

- **优点**：一套逻辑、一套运维、天然流式；回放即重算，历史对账靠重跑。
- **代价**：重跑历史要等流作业追完数据，时间成本高；因此 Kappa 常与「周期性地把状态快照成批结果」结合（如 Flink 定时把窗口结果写入 Iceberg），即「Kappa 为主体、批为结果物化」。

**辨析｜易错点：** Kappa 不是说「批没了」，而是说「**批被实现成一条流的慢速回放**」——批与流不再是两套引擎，而是同一引擎对同一份日志的两种消费方式。

Kleppmann 第 12 章把这概括为「流和批在收敛：批处理框架加上了流式处理能力，流式框架也处理有界数据」——两边相向而行，中间就是流批一体。

## 3 统一 SQL：动态表与查询不变式

「逻辑写一遍」的技术落地是 **Flink SQL**。

Flink 用**动态表（dynamic table）**统一批与流的视角：SQL 查询的输入输出都是「随时间变化的表」：

- **批查询**是无界表的特例（数据静止）。
- **流查询**是无界表的持续求值。

同一句 `SELECT region, SUM(amount) FROM orders GROUP BY region`，在批上是「对全量跑一次」，在流上是「对每批到达的订单增量更新」——**同一套 SQL、同一套语义**。

背后的理论支柱是**动态表 → 变化日志（changelog）**的双向映射：对表做的每条 `INSERT`/`UPDATE`/`DELETE` 都是一条流事件，反过来流事件可被还原成表。这直接呼应 Kleppmann 第 11 章的「数据库与流」——**表是流的物化，流是表的日志**。<span class="marginnote">Flink 还支持<strong>状态查询（table lookup）</strong>与物化视图，把「SQL 查询的结果」也做成持续更新的视图——这与湖仓表格式的「快照 = 物化结果」、以及后文《实时数仓实践》里「实时分层」的思想完全同构：<strong>处处都是物化视图</strong>。</span>

### 统一 SQL 的代价与局限

统一不是免费的：**有状态流 SQL（聚合、Join）需要配置状态 TTL 与水位线**，而批 SQL 没有这些概念——同一个查询在两种模式下，语义参数并不完全相同。

另外，**不是所有批 SQL 都能自然地流化**：如三表以上的大 Join、需要全量重扫的相关子查询，在流模式下要么状态爆炸、要么语义受限。工程现实是「能统一的核心算子统一，边界算子在两种模式各自实现」，Flink 的 Planner 会尽量把差异藏进优化器。

### Flink SQL 怎么「同时」做批和流

Flink 的 `TableEnvironment` 同时接受**有界数据源**与**无界数据源**：对批表执行 `INSERT INTO` 是一次性作业，对流表执行同样的 SQL 是持续作业。**优化器生成的执行计划只差「边界」**——同一个算子（如聚合、Join）在两种模式下复用同一套实现，这就是「统一」在工程上的真正含义，也是 Kappa 架构「一套逻辑」的语法保证。

## 4 核心对比表：Lambda 与 Kappa

| 维度 | Lambda 架构 | Kappa 架构 |
| --- | --- | --- |
| 核心主张 | 批 + 流双轨并行，服务层合并 | 一切皆流，批是流的回放 |
| 提出 | Nathan Marz，2011 | Jay Kreps，2014 |
| 逻辑套数 | 两套（批逻辑 + 流逻辑） | 一套 |
| 历史重算 | 重跑批作业（快） | 重放 Kafka 日志（较慢） |
| 结果一致性 | 需人工对账，易口径不一 | 单一来源，天然一致 |
| 运维成本 | 高（双作业双监控） | 低（单作业） |
| 适用场景 | 历史遗留、强批依赖 | 新建系统、实时为主、日志可久存 |

**辨析｜易错点：** 选 Kappa 不等于可以无限重跑——Kafka 保留期（默认 7 天）会吃掉历史日志，真正的「长历史重算」仍需把日志转存到 Iceberg 再触发历史作业。

**生产正解往往是混合**：Kappa 做实时主链路，批作业负责补数、初始回填与审计对账，二者共享同一套 Flink SQL 与同一张 Iceberg 表。

### 一个真实形态：Flink SQL 写入湖仓

以「实时订单汇总表」为例：Flink SQL 从 Kafka 读订单流，`GROUP BY` 后周期性把结果 `INSERT INTO iceberg_catalog.ods.order_daily`（Iceberg 表）。这套 SQL 用**批模式**跑一遍就是全量回填，用**流模式**跑起来就是实时增量——同一个 `.sql` 文件、同一张表、两种跑法。**表本身成了批与流的共同落点**，下游 BI 与特征平台无需关心数据是批来还是流来。

### 术语速查表

| 术语 | 英文 | 一句话含义 |
| --- | --- | --- |
| Lambda 架构 | Lambda architecture | 批 + 流双轨并行 |
| Kappa 架构 | Kappa architecture | 一切皆流，批是流的回放 |

## 5 小结

- **Lambda 架构**用批 + 流双轨换取「又准又快」，代价是逻辑两遍、结果难对账、运维翻倍。
- **Kappa 架构**主张一切皆流：Kafka 日志可重放，重算 = 换 offset 重跑，一套逻辑一套运维。
- **流批一体**的工程载体是 **Flink SQL**：动态表把批（有界）与流（无界）统一为同一查询语义。
- 「表是流的物化，流是表的日志」是打通数据库、消息系统、湖仓的共同世界观。
- 现实选型多为混合：Kappa 主实时链路 + 批作业补数对账，共享同一 SQL 与同一张表。
