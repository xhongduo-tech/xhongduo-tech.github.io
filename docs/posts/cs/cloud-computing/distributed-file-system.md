## 为什么从分布式文件系统开始

前面的块、文件、对象存储，在云厂商那里几乎都不是「一块盘」，而是**分布式文件系统**在背后支撑——数据被切碎、复制、分散在成千上万台机器上。这一篇讲清分布式文件系统的核心架构：**它如何让海量数据跨机器存放、如何容错、如何保证一致性**。理解了它，你不仅看懂了云存储的底层，也把第三级《分布式系统》的副本与一致性理论接到了具体工程上。

## 1 单机文件系统的天花板

单机文件系统（ext4、NTFS）的设计前提是「一块盘在我眼前」：目录树、块分配、读写都在本地。它的天花板有三个：

- **容量有限**：单盘容量再大也有限，海量数据放不下。
- **吞吐有限**：单盘的 I/O 带宽是硬瓶颈。
- **故障不可逆**：磁盘坏了数据就没了，除非人工备份。

分布式文件系统（DFS）要解决的就是这三件事：**把数据分布到多台机器、聚合多机的带宽、用副本对抗故障**。它对外仍呈现「一个文件系统」，但内部是几百上千台机器的协作。<span class="marginnote">DFS 给上层的关键承诺是<strong>透明性</strong>：应用看到的是一个普通目录树，读写方式与本地文件系统一致——机器分布、副本、故障恢复都被藏在接口后面。这与「抽象即接口」的主线思想完全一致：实现越复杂，接口越简单。</span>

## 2 经典架构：GFS 的两层模型

**分布式文件系统**：在多台机器上协同提供统一文件命名空间与数据存储的系统。其中最经典的参考是谷歌的 **GFS（Google File System）**，它的架构奠定了现代 DFS 的模板：

**Master（元数据节点）**：保存文件系统的**全部元数据**——目录结构、每个文件分成了哪些块、每块在哪些机器上。它是「大脑」，但不存数据。
**ChunkServer（数据节点）**：真正存储文件数据块的机器，每块默认存 3 个副本，分布在不同的机架上。

一次读文件的流程：客户端向 Master 问「这个文件在哪」→ Master 返回块位置 → 客户端直接与 ChunkServer 通信取数据。**关键设计：数据不经过 Master**——Master 只做「导航」，数据流量走数据节点，从而把控制路径与数据路径彻底分开。<span class="marginnote">GFS 的「Master 只导航、数据不中转」是分布式存储性能的关键决策：如果所有数据都经 Master 转发，Master 立刻成为瓶颈。这正是对象存储那篇里「元数据与数据分离」的鼻祖。后来 HDFS、Ceph 都继承了这套两分法。</span>

## 3 分片、副本与一致性

DFS 的三个核心机制：

**分片（sharding/chunking）**：每个文件按固定大小（如 GFS 的 64 MB）切成块，均匀分布到多台机器，天然并行读写、聚合带宽。
**副本（replication）**：每块存多份（默认 3 份），放在不同机架/可用区——单机、单机架故障都不丢数据。副本也带来读性能的扩展：同一块可从多个副本并发读。
**一致性**：写操作如何让所有副本一致？GFS 采用「主副本（primary）+ 租约（lease）」模型——写请求先到主副本，主副本定序后同步给从副本，从而保证「追加写」的强一致与并发读的一致性。<span class="marginnote">「主副本 + 租约」是分布式一致性的经典实现：租约保证在一段时间内只有一个主副本拥有写权，避免「双主」脑裂。这与第三级《分布式系统》里的 Raft 选举同源——都是「选一个领导，别选两个」。DFS 的「顺序一致」面向块数据，比通用分布式事务简单，因此能撑起巨大的吞吐。</span>

## 4 核心要点对比：DFS 与单机文件系统

| 维度 | 单机文件系统 | 分布式文件系统 |
| --- | --- | --- |
| 容量 | 单盘上限 | 近乎无限（加机器） |
| 吞吐 | 单盘带宽 | 聚合多机带宽 |
| 容错 | 无自动冗余 | 多副本自动容错 |
| 一致性 | 本地强一致 | 面向块/追加的定序一致 |
| 复杂度 | 简单 | 高（副本、恢复、均衡） |
| 代表 | ext4、NTFS | GFS、HDFS、Ceph |

**辨析｜易错点：** DFS 的一致性不是「数据库事务级」的。它是**文件系统级**的一致性——保证「写进去的块读得到、并发追加不交错」，但不提供「多文件事务」。把 DFS 当关系型数据库用（期待跨文件原子性）是常见误区。要事务，得在 DFS 之上再叠数据库层，这正是云数据库服务（第三篇最后一篇）要做的事。<span class="marginnote">现代云对象存储（S3）与分布式文件系统的血缘：S3 的「桶+对象」可以看成 DFS 的去目录化变体——去掉目录树，只留 key，牺牲「目录操作」，换来更极致的大规模。存储产品的演化路径，本质上是在「表达能力」与「可扩展性」之间不断调位置。</span>

## 5 读路径与写路径：一次 I/O 的旅程

把 DFS 的机制串成「一次读写怎么走」，比背组件名更有效。以 GFS 模型为例：

**一次读操作**：

1. 客户端向 Master 问：「文件 F 的第 3 块在哪？」
2. Master 返回「在 ChunkServer A、B、C」。
3. 客户端直接向最近的 A 发读请求，取回数据。

**一次写操作（追加写）**：

1. 客户端问 Master：「文件 F 想追加数据，写哪块？」
2. Master 指定一个 ChunkServer 作为**主副本（primary）**，返回主副本与其余从副本的位置。
3. 客户端把数据推给所有副本（链式推送，形成写流水线），但**只有主副本定序**。
4. 主副本把数据按序同步给从副本，全部成功后确认——保证所有副本一致。

**读直接走数据节点、写由主副本定序**——这两条就是 DFS 性能与一致性的设计精髓。<span class="marginnote">注意写路径的细节：<strong>数据可以推给所有副本，但「顺序」由主副本一个人定</strong>。如果每个副本各自定序，并发写就会乱套。这个「单点定序」正是分布式系统里「一个领导拍板」的又一次体现——和 Raft 的 Leader、K8s 控制器的「单一期望」如出一辙。</span>

**辨析｜易错点：** DFS 的「追加写为主、随机改写为辅」是它的设计前提——GFS 假设文件「写一次、读很多次、偶尔追加」。如果你的负载是「频繁随机改写文件中的小块」，DFS 的块级复制会造成巨大的写放大，性能骤降。**把 DFS 当「随机改写型」存储用，是用错场景**——随机改写的高性能需求，应该用块存储（见《块存储与文件存储》）。

## 6 DFS 的现代形态：HDFS、Ceph 与对象化

GFS 之后，分布式文件系统演化出几条路线，各有侧重：

**HDFS（Hadoop 分布式文件系统）**：GFS 的开源翻版，专为**大数据批处理**设计——大块（128 MB）、追加写为主、跑 MapReduce/Spark。它是大数据生态（Hive、Spark、HBase）的存储底座，也是「数据湖」最早的形态。

**Ceph**：新一代统一分布式存储，**同时提供对象、块、文件三种接口**——一套系统，既能当对象存储（S3 兼容）、又能当云盘（块）、又能当共享文件（NFS）。它用 **CRUSH 算法**做数据分布（不依赖中心查表，直接计算数据在哪），去掉单一 Master，扩展性与可用性更强。

| 系统 | 出身 | 接口 | 特点 |
| --- | --- | --- | --- |
| GFS | 谷歌论文 | 文件 | 两分法鼻祖 |
| HDFS | Hadoop 开源 | 文件 | 大数据批处理 |
| Ceph | 开源 | 对象/块/文件 | 统一存储、无中心 |
| 云对象存储 | 厂商闭源 | 对象 | S3 API、无限扩展 |

**辨析｜易错点：** 「分布式文件系统」与「对象存储」的界限在现代越来越模糊——Ceph 与云对象存储都提供 S3 接口。区别在于**定位**：DFS 强调「文件语义」（目录、挂载、追加），对象存储强调「HTTP API + 海量扁平 key」。选型时问「我要文件协议还是 HTTP API」即可。<span class="marginnote">这条演化线揭示了存储的规律：<strong>接口在收敛、能力在融合</strong>——一个存储系统越来越想「通吃对象/块/文件」。Ceph 的「无中心」设计（CRUSH 直接计算数据位置）也值得注意：它用「确定性计算」取代「查表」，是分布式系统「<strong>用算法替代中心协调</strong>」的经典案例，与一致性哈希（《负载均衡》）同源。</span>

## 7 一致性语义：DFS 保证什么、不保证什么

理解 DFS，最关键的是「**它的一致性边界在哪**」——保证什么、不保证什么，决定你能把它用在什么场景。

**DFS 保证的**：

**块/文件级一致性**：一次写入完成后，任何客户端读到的都是「写入后的完整数据」。
**追加写的有序性**：并发追加时，所有客户端看到相同的追加顺序（靠主副本定序）。
**副本最终一致**：短暂的复制延迟后，各副本收敛到同一数据。

**DFS 不保证的**：

**跨文件事务**：写文件 A 和写文件 B 不是一个原子操作——没有「要么都成、要么都败」。
**强一致的目录操作**：目录列表在副本延迟下可能暂时不一致。
**随机改写的高性能**：对块内随机改写支持差（写放大）。

| 保证 | 不保证 |
| --- | --- |
| 单文件写后读一致 | 跨文件事务 |
| 追加写有序 | 目录强一致 |
| 副本最终一致 | 随机改写高效 |

**辨析｜易错点：** 把 DFS 当「分布式事务数据库」用，是最大的错配——需要**跨文件原子性**（如「转账 = 改两个账户文件，要么都成要么都败」）时，DFS 给不了。这种需求要上**数据库的事务**（见《云数据库服务》）。**DFS 的价值在「海量数据的可靠存储与聚合吞吐」，不在「业务级一致性」**。<span class="marginnote">这条「一致性边界」的思考，是分布式系统的通用素养：<strong>任何分布式系统都有「强在哪、弱在哪」的边界</strong>——DFS 强在块级一致、弱在跨文件事务；数据库强在事务、弱在扩展；缓存强在快、弱在一致。看懂「边界」，才知道每个组件该放哪、不该放哪。</span>

## 8 小结

- DFS 解决单机文件系统的三大天花板：**容量、吞吐、容错**。
- 经典架构（GFS）：**Master 管元数据、ChunkServer 存数据**，数据不经过 Master。
- 三大机制：**分片**（聚合带宽）、**多副本**（跨机架容错）、**主副本+租约**（写定序）。
- DFS 一致性是**文件系统级**，不是事务级——要事务得再叠数据库层。
- 对象存储可看作 DFS 的「去目录化」变体，两者共享元数据/数据分离的骨架。

- DFS 与分布式系统的呼应：**分片、副本、一致性，是你在《分布式系统》学到的三大机制在存储上的直接落地**——DFS 是分布式理论最「具体」的应用场。
