## 为什么从计算虚拟化开始

上一篇确立了 Hypervisor 的框架。这一篇进入最硬核的部分：Hypervisor 如何虚拟化 **CPU 与内存**这两大计算核心。CPU 虚拟化解决「一颗核怎么分时给多台虚拟机用」，内存虚拟化解决「每台虚拟机都以为自己在用一整块连续内存、彼此还不冲突」。这两件事是理解云主机性能差异的钥匙——为什么有些云主机「超卖」得厉害、为什么 ECS 的规格有「独享型」与「共享型」之分，答案都在这里。

一个预习提示：CPU 与内存的虚拟化，本质都是「**欺骗客户机**」——让它以为独占硬件。CPU 用「时间片」骗它独占核，内存用「两级页表」骗它独占物理内存。理解「虚拟机活在善意谎言里」这个视角，后面所有机制都顺理成章。

## 1 CPU 虚拟化：vCPU 是时间片上的分身

**vCPU（虚拟 CPU）**：虚拟机看到的「一颗 CPU」，本质是 Hypervisor 用**分时调度**在物理核上切出的逻辑概念。一台 4 核物理机，可以切成 8 个、16 个 vCPU，每个 vCPU 绑定一台虚拟机——物理核轮流执行各虚拟机的线程，快得让每台虚拟机都以为自己在独占 CPU。<span class="marginnote">这就是「超卖」（overcommit）的由来：物理核数固定，vCPU 总数可以远超它。正常负载下所有虚拟机互不察觉；一旦多台虚拟机同时高负载，就会争夺物理核，性能互相拖累——「吵闹邻居」（noisy neighbor）问题。共享型云主机便宜，就是这个原因。</span>

CPU 虚拟化的调度策略通常采用**时间片轮转 + 优先级/配额**：Hypervisor 给每台虚拟机设定权重（weight）与上限（cap），确保一台虚拟机再疯也占不满整台物理机。对延迟敏感的虚拟机，还可以用 **CPU 亲和性（CPU affinity）** 把 vCPU 固定绑定到指定物理核，减少上下文切换的抖动。

## 2 内存虚拟化：多份「假的物理内存」

内存虚拟化要解决的难题是**地址空间叠床架屋**。正常情况下，操作系统通过页表把**虚拟地址（VA）**翻译成**物理地址（PA）**。引入虚拟机后，出现了三层地址：

- **GVA**：客户机里的虚拟地址（guest virtual address），客户机 OS 用自己的页表翻译它。
- **GPA**：客户机看到的「物理地址」（guest physical address），其实就是虚拟机在物理机上的**虚拟内存**。
- **HPA**：真正的物理机物理地址（host physical address）。

关键矛盾：客户机 OS 以为自己写的页表把 GVA 映到了 GPA（真实的物理内存），但 GPA 对物理机而言只是一段虚拟内存，还要再被 Hypervisor 翻译一次到 HPA，才能落到真实的物理内存条上。

## 3 公式解析：GVA → GPA → HPA 的两级翻译

把这条地址翻译链写成「公式」，是理解内存虚拟化的核心：

$$
\text{GVA} \;\xrightarrow{\text{guest 页表}}\; \text{GPA} \;\xrightarrow{\text{host 页表}}\; \text{HPA}
$$

逐步拆解这条链：

- **第一步，GVA → GPA**：这是客户机 OS 自己完成的翻译，用的页表由客户机内核维护，与普通进程的地址翻译完全一样。
- **第二步，GPA → HPA**：这是 Hypervisor 负责的翻译。它把每台虚拟机的一段 GPA 空间，映射到物理机物理内存的某个区域，实现隔离与交换。
- **第三步，两层合并**：一次内存访问要经历两次查表，开销巨大。因此虚拟化必须引入硬件缓存（下面第 4 节），否则性能不可接受。

## 4 两种实现：影子页表与 EPT

为加速两级翻译，历史上出现过两种方案：

| 方案 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **影子页表（shadow page table）** | Hypervisor 把两级页表合并成一张「GVA → HPA」的直接映射，客户机改页表时 VMM 同步重建影子页表 | 无需硬件支持，兼容旧 CPU | 页表切换频繁时开销大 |
| **EPT / NPT**（Intel EPT / AMD NPT） | CPU 硬件原生支持两级地址翻译，CR3 指向的客户机页表 + 硬件维护的 EPT 页表 | 性能接近裸机，无需影子同步 | 需要较新 CPU |

**辨析｜易错点：** 影子页表会带来「页表同步」问题——客户机每改一次页表（比如进程切换），VMM 都要捕获并重建影子页表，这就是「上下文切换放大」的开销来源。而 EPT 把两级翻译交给硬件 MMU，客户机页表切换不再触发 VMM 干预。<span class="marginnote">这也是为什么「虚拟化是否接近原生性能」在内存这一项的关键，取决于硬件 EPT 是否开启。云厂商的实例规格里若标注「内存虚拟化：EPT 开启」，通常意味着更可预测的性能。CPU 虚拟化同样依赖硬件辅助（VT-x），两件套缺一不可。</span>

## 5 超卖与性能隔离：共享型实例的生意经

理解了 vCPU 是时间片之后，就能看清云主机的一个关键商业机制——**超卖（overcommit）**。云厂商通常不会按「1 物理核 = 1 vCPU」卖，而是**让 vCPU 总数远超物理核数**，赌大多数客户不会同时跑满。这台账是这样的：

| 超卖比 | 含义 | 典型场景 |
| --- | --- | --- |
| 1:1 | 不超卖，vCPU 数 = 物理核数 | 独享型/高保障实例 |
| 1:2 ~ 1:4 | 适度超卖 | 通用型实例 |
| 1:8 以上 | 高倍超卖 | 低价共享型实例 |

**辨析｜易错点：** 超卖的风险是「**吵闹邻居**」——同台物理机上，若其他虚拟机突然满载，你的 vCPU 就会被挤占，性能骤降却查不出原因。为此云厂商用两类机制做**性能隔离**：

**配额（limits）**：给每台虚拟机设 CPU 上限，防止一台吸干整机。
**权重（weights）**：物理核紧张时按权重分配——高权重实例（更贵）优先拿到计算时间。

**给你的选型启示**：高负载、延迟敏感的业务（数据库、交易系统）选**独享型**（不超卖、有配额保障）；开发测试、弹性外围负载选**共享型**（便宜、性能可波动）。「为什么同样是 4 核，价格差一倍」——答案就在超卖比与隔离策略里。<span class="marginnote">内存同样有超卖：精简供给（thin provisioning）让「声明的内存」之和超过物理内存，靠「大多数客户用不满」的统计假设运转。内存超卖比 CPU 超卖更危险——CPU 慢只是变慢，<strong>内存不足会触发 OOM 或 swap</strong>，直接拖垮实例。因此内存超卖通常比 CPU 谨慎得多。</span>

## 6 内存回收：气球、交换与页共享

内存虚拟化除了「地址翻译」，还要解决一个更实际的问题：**物理内存有限，怎么高效地在虚拟机之间分配与回收**。

**气球（ballooning）**：Hypervisor 在每个虚拟机里放一个「气球驱动」（virtio-balloon）。当某台虚拟机内存闲置时，气球**膨胀**（向虚拟机「借」走内存），Hypervisor 把这些内存**回收**给别的虚拟机用；虚拟机内存紧张时，气球**收缩**，把内存还回去。**「气球」是可伸缩的借贷工具**——它让内存分配跟着需求实时浮动，是内存超卖的实现基础。

**交换（swapping）**：虚拟机内内存不足时，客户机操作系统把自己的部分内存**换到磁盘**（swap），牺牲性能保住运行。这是「最后一层缓冲」——能跑，但很慢。

**透明页共享（Transparent Page Sharing，TPS）**：多台虚拟机跑相同的操作系统与库，**相同内容的页在物理内存里只存一份**（写时才复制分家）——靠内容哈希发现重复页。这能省下可观的内存，尤其当很多虚拟机基于同一镜像创建时。<span class="marginnote">气球与页共享是「<strong>内存的金融系统</strong>」：气球是「活期借贷」，页共享是「共享仓库」，swap 是「高利贷」（贵但能救急）。三者配合，让「物理内存 vs 声明的内存」的差额被安全地撑起来——这也是共享型实例内存规格「看起来便宜」的内部原因。</span>

**辨析｜易错点：** 内存回收不是免费的。**气球与 swap 都意味着「某刻可能慢一下」**——内存紧张时，虚拟机可能突然变卡（swap 抖动）。因此对延迟敏感的核心应用，仍建议**独享型内存**（不超卖、不回收），避免「内存争抢」的不确定性。内存的「共享」与「独享」，是云主机规格定价的重要分水岭。

## 7 NUMA 与大页：虚拟化性能的进阶细节

CPU/内存虚拟化的性能优化，两个「进阶但常见」的细节值得知道：

**NUMA（非一致内存访问）**：现代服务器有多个 CPU 插槽，每个插槽「就近」连接一部分内存——访问本地内存快、访问远端内存慢。虚拟化要避免「vCPU 跑在插槽 1、内存却在插槽 2」的远端访问。**NUMA 感知调度**（vCPU 与其内存尽量在同一插槽）能显著降低内存访问延迟，是高性能实例的重要优化。

**大页（Huge Pages）**：内存分页越大，TLB（快表）能覆盖的内存越多、缺页越少。虚拟化场景下，**EPT（二级页表）的 TLB 开销是性能关键**——启用 2 MB/1 GB 大页，能把「两级地址翻译」的开销大幅压缩，内存密集负载（数据库、JVM）收益尤其明显。

| 优化 | 解决什么 | 收益场景 |
| --- | --- | --- |
| NUMA 感知 | 跨插槽内存访问 | 内存密集、多核 |
| 大页 | TLB 命中率 | 数据库、大数据 |

**辨析｜易错点：** 这两项优化**默认不一定开启**——很多云实例的默认配置没有开大页，或 NUMA 拓扑对虚拟机关闭。对性能敏感负载，选「开启了大页/NUMA 感知」的实例规格或调优参数，往往比升规格更划算。<span class="marginnote">这些「进阶细节」的意义不在让你去配，而在让你<strong>读懂云主机规格与性能差异</strong>：为什么同样 8 核 16 G，不同实例类型跑数据库的吞吐差一大截——<strong>规格表上不写的优化（NUMA、大页、超卖比），才是真实性能的分水岭</strong>。这也是「独享型 vs 共享型」实例价差的技术来源。</span>

## 8 小结

- **CPU 虚拟化**：vCPU 是物理核上的**分时切片**，超卖是共享型实例便宜的根本原因。
- **内存虚拟化**：引入 **GVA / GPA / HPA 三层地址**，需要两次翻译。
- 地址链：$\text{GVA} \to \text{GPA} \to \text{HPA}$，客户机管前段、VMM 管后段。
- **影子页表**合并两级翻译但有同步开销；**EPT/NPT** 由硬件原生支持，是现代主流。
- 计算虚拟化两件套：**VT-x（CPU）+ EPT（内存）**，共同决定虚拟化性能上限。

- 计算虚拟化与存储虚拟化的平行关系：**CPU 靠分时切、内存靠翻译切、存储靠池化切**——「物理→逻辑」的切分魔法，在三大资源上一一上演；下一篇就是最后一块拼图。

- 核心记忆点：**计算虚拟化两件套 = VT-x（CPU）+ EPT（内存）**——硬件辅助让虚拟化接近裸机。
