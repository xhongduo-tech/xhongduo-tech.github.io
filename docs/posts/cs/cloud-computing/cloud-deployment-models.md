## 为什么从部署模型开始

服务模型回答「云卖什么」，部署模型回答「**云部署在哪里、开放给谁用**」。同一套 IaaS 技术，既可以由阿里云对外售卖（公有云），也可以由某家银行在自己的数据中心内部署（私有云），还可以两者打通（混合云）。这篇讲清四种部署模型的边界与适用场景——它是理解企业真实上云路径的钥匙。

一个生活化的类比：服务模型像「租房子还是买房」（租到什么程度），部署模型像「房子在市中心还是郊区、对外开放还是自家住」（在哪、给谁）。**两套问题正交**——你可以在市中心租一间只给自己住的房子（公有云的资源、私有云的用法），也可以在市郊自建一栋对外开放的楼（私有云的技术、公有云的形态）。

## 1 一个维度，四个答案

部署模型本质上由一个维度决定：**云资源归谁所有、物理位置在哪、对谁开放**。NIST 依据这三点，把部署模型分为四种：公有云、私有云、混合云、社区云。<span class="marginnote">注意：部署模型与服务模型是<strong>正交</strong>的——公有云也可以提供 IaaS 或 SaaS，私有云同样可以按 PaaS 的形态对外服务。两者分别回答「在哪、给谁」与「给到什么程度」，不要混为一谈。</span>

## 2 公有云与私有云：天平的两端

**公有云（public cloud）**：云基础设施由第三方服务商拥有并运营，对一般公众或大型产业集团开放，按需售卖。用户按用量付费，无需自建机房。典型如 AWS、阿里云、Azure。

**私有云（private cloud）**：云基础设施为单一组织专有使用，可自行管理或由第三方代管，物理位置可在组织内部或外部。用户（该组织）获得最大控制权与隔离性，但需要自己承担资源池化的全部建设与运维成本。

**辨析｜易错点：** 「私有云」不是「自建机房换个名字」。判断一朵云是否成立，要看它是否具备上一篇的五条核心特征（按需自助、资源池化、弹性、计量）。许多所谓「私有云」实际只是虚拟化集群，缺了自助门户与计量，就不算真正的云。**私有云是「具备云特性的专属基础设施」，而非简单的一堆虚拟机**。<span class="marginnote">公有云与私有云的取舍可概括为：公有云把<strong>规模效应</strong>卖给你（别人分摊成本、你来享受低价），私有云把<strong>控制权</strong>卖给你（数据不出内网、安全合规可控）。一句话：公有云省心，私有云安心。</span>

## 3 混合云与社区云：折中与联盟

**混合云（hybrid cloud）**：两种或以上不同部署模型（典型是公有云 + 私有云）通过标准化或专有技术绑定，使数据与应用可在两者间迁移。它同时继承公有云的弹性与私有云的安全：日常稳态负载跑在私有云，突发峰值「爆」到公有云——这个操作俗称**云爆发（cloud bursting）**。<span class="marginnote">云爆发是混合云最典型的场景：电商大促时私有云容量不足，把多出来的流量动态溢流到公有云，扛过峰值再缩回来。它把「弹性」从单朵云内扩展到跨云之间，是《多云与混合云策略》一篇的先行预览。</span>

**社区云（community cloud）**：云基础设施由**若干有共同关切的组织**（如同行业、同监管要求的机构）共同使用与管理，成员分摊成本、共享资源。典型如若干家银行共建的金融云、多所高校共建的科研云。它介于公有云（面向所有人）与私有云（面向单组织）之间，是「联盟式的私有云」。

## 4 核心要点对比：四种部署模型

| 维度 | 公有云 | 私有云 | 混合云 | 社区云 |
| --- | --- | --- | --- | --- |
| 资源归属 | 服务商 | 单一组织 | 服务商+组织 | 共同关切组织群 |
| 服务对象 | 公众/多租户 | 单组织内部 | 组织为主 | 联盟成员 |
| 控制权 | 低 | 高 | 中（按负载分配） | 中 |
| 弹性 | 最强 | 受自有容量限制 | 强（可爆发到公云） | 受联盟容量限制 |
| 典型成本 | 按用量付费 | 自建成本高 | 私有成本+弹性用量 | 成员分摊 |
| 适用 | 互联网应用 | 强监管/核心数据 | 稳态+峰值并存 | 同业共建 |

这张表背后的决策逻辑其实很简单：**安全敏感的放私有云，规模弹性的放公有云，两个都要就混合云，几家同行的共享诉求用社区云**。<span class="marginnote">现实中「多云」（multi-cloud，同时用多家公有云）与混合云常被混用：混合云强调「公+私」的打通，多云强调「同时用多家厂商」以规避锁定与单点故障。两者的区别在《多云与混合云策略》再细辨。</span>

## 5 部署模型实战：一家金融机构的云路径

部署模型不是抽象的四个词，而是一条**被现实逼出来的路径**。以一家中型银行的上云为例：

- **第一阶段 · 私有云守核心**：监管要求数据不出境、核心账务系统强隔离。银行自建私有云，承载交易与核心数据——控制权第一，弹性排后。
- **第二阶段 · 公有云接外围**：网银前端、营销活动、大数据分析这些**非核心、高弹性**负载，放到公有云——按需弹性、成本低。
- **第三阶段 · 混合云打通**：私有云与公有云之间拉专线，实现「云爆发」——大促时外围流量溢流到公有云；同时公有云作为**异地灾备**，核心数据定期同步过去。
- **社区云的呼应**：如果几家中小银行联合共建一个金融云，共享安全等级与监管流程，那便是一朵社区云。

| 阶段 | 驱动因素 | 部署模型 |
| --- | --- | --- |
| 核心系统 | 合规、数据主权 | 私有云 |
| 外围系统 | 弹性、成本 | 公有云 |
| 大促峰值 | 容量不足、云爆发 | 混合云 |
| 同业共建 | 分摊成本、共享合规 | 社区云 |

**辨析｜易错点：** 现实中的部署模型**不是单选，而是组合**——同一家企业通常同时拥有私有云与公有云（这就是混合云），还可能参与社区云。唯一不会出现的情况是「一家企业只有一个部署模型」。上云规划的第一步不是选模型，而是**把负载分类**：哪些必须私有、哪些可以公有、哪些需要打通。<span class="marginnote">分类的标准只有两个词：<strong>数据敏感度与弹性需求</strong>。敏感度高 + 弹性低 → 私有；敏感度低 + 弹性高 → 公有；两个都高 → 混合云打通。先分类，再选型，部署模型自然浮现。</span>

## 6 数据主权与部署模型

部署模型的背后，藏着一个日益重要的力量——**数据主权（data sovereignty）**：数据受其存储地法律管辖。这直接决定了「云放哪」。

**数据出境的约束**：许多国家的法律要求「某些数据不得出境」。中国《数据安全法》《个人信息保护法》要求重要数据与个人信息存储在中国境内；欧盟 GDPR 限制欧盟公民数据流向境外。于是：

- 处理中国境内数据的企业，必须用**在中国有数据中心、通过等保**的云（阿里云、华为云）。
- 服务全球用户的跨国企业，要在**多个区域**分别部署，数据「留在本地、就近处理」——这本身就是「按数据地域切分」的多云/混合云架构（见《多云与混合云策略》）。

**私有云与社区云的数据主权动机**：银行、政务、医疗的数据敏感度极高，法律或行业监管要求「数据不出内网」——这正是私有云、社区云存在的**第一驱动**。不是「私有云技术更好」，而是「数据主权要求它」。

| 数据敏感度 | 典型数据 | 部署倾向 |
| --- | --- | --- |
| 高（受监管） | 金融交易、医疗档案、政务数据 | 私有云/社区云，境内 |
| 中（业务敏感） | 客户信息、经营数据 | 混合云（境内公有） |
| 低（可公开） | 静态内容、公开分析 | 公有云，可跨境 |

**辨析｜易错点：** 「数据在哪」比「数据是谁的」更容易被忽略。很多企业盯着「上云省不省钱」，却忘了先回答「法律允许数据放哪」——合规不过关，省下的钱可能变成罚款。**部署模型的第一个决定因素不是技术，是合规**。<span class="marginnote">数据主权也是「<strong>云厂商选择</strong>」的地缘含义：国内外云厂商的合规资质、数据中心布局，决定了它们各自能服务谁。这也是为什么全球云市场「本土厂商 + 全球巨头」并存——<strong>数据主权天然保护了每个区域的本土云生态</strong>。</span>

## 7 部署模型与云厂商的产品对应

四种部署模型不是抽象名词，每家云厂商都有对应的产品线。对照起来记，会清晰很多：

| 部署模型 | 云厂商产品 |
| --- | --- |
| 公有云 | AWS、Azure、阿里云、华为云本身的全部服务 |
| 私有云 | AWS Outposts、Azure Stack、华为云 Stack、阿里云专有云 |
| 混合云 | AWS Direct Connect + VPC、Azure Arc、阿里云专有云 + 公共云互通 |
| 社区云 | 阿里云金融云、行业云（政府、教育） |

**从这张表能看出两个趋势**：

1. **私有云产品「云化」**：今天的私有云产品（Outposts、Azure Stack）不再是一套独立技术，而是**把公有云的技术栈打包、搬到客户机房**——客户得到「和公有云一模一样的 API 与管理界面」，但数据留在本地。**「私有云 = 公有云的同款技术，放在自己家里」**。
2. **混合云是默认答案**：几乎每家都提供「专线 + 统一管理」，把公有与私有打通——因为绝大多数企业的现实就是「既要公有云的弹性，又要私有云的合规」。

**辨析｜易错点：** 「私有云产品」与「自建虚拟化集群」的区别，在前文已经强调过（五条核心特征）。值得补充的是：**厂商的私有云产品通常自带「云的 API 与体验」**——你在私有云上用的还是那套 IAM、那套控制台、那套计量——这正说明「私有云 = 具备云特性的专属部署」，而不是「一堆虚拟机的名字」。<span class="marginnote">「<strong>同一套技术栈，从公有云搬到私有云</strong>」这个趋势，让「公有云/私有云」的边界变得模糊——未来越来越多的企业会拥有「<strong>一致体验的多朵云</strong>」：数据在哪、合规怎么定，决定哪朵云负责哪块。这正是《多云与混合云策略》的起点。</span>

## 8 小结

- 部署模型由**归属、位置、开放对象**一个维度决定。
- **公有云**：服务商所有、对公众开放、按量付费；**私有云**：单组织专有、控制权最大。
- **私有云 ≠ 虚拟化集群**，必须满足五条核心特征才算真云。
- **混合云** = 公有+私有，核心价值是**云爆发**；**社区云** = 共同关切组织的联盟共享。
- 选型口诀：敏感进私有、弹性进公有、两者兼顾用混合。

- 部署模型与体系架构的衔接：**部署模型回答「云放在哪」，体系架构回答「云里面长什么样」**——前者是「选址」，后者是「内部构造」，下一篇正式进入云内部。

- 核心记忆点：**部署模型由「归属、位置、开放对象」一个维度决定**——先给负载分类，模型自然浮现。
