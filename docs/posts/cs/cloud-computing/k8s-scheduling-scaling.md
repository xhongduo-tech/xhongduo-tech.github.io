## 为什么从调度与伸缩开始

前面几篇覆盖了 K8s 的骨架、编排与网络存储，这一篇收束第二篇的最后一环：**调度与伸缩**。调度回答「一个新 Pod 应该放到哪台节点」，伸缩回答「业务量变化时副本数怎么跟着变」。这两个机制是云「弹性」承诺在容器层的兑现——理解了它们，你就明白了 K8s 如何在一千台节点上自动、理智地安排几万个 Pod。

一个直觉起点：调度是「**静态决策**」（Pod 创建那一刻定下来放哪），伸缩是「**动态决策**」（运行中持续调整数量）。两者一静一动，构成集群的「自动管理」——这也是 K8s 之所以叫「平台」而非「工具」的原因：它把「放哪、放几个」都做成了可声明、可自动化的能力。

## 1 调度器的工作：为 Pod 找家

当用户创建 Pod，kube-scheduler 从 API server 拿到待调度 Pod，开始「找家」——从集群所有节点里选一个**合适的**。调度分两步走，本质是一个两阶段的决策：

1. **过滤（filtering）**：先把**硬性条件**不满足的节点剔除。比如节点资源不足、有污点（taint）禁止调度、Pod 要求特定亲和性而节点不满足——不合条件的全部出局。
2. **打分（scoring）**：对剩余节点按**软性偏好**打分，选出最合适的。比如资源剩余多、副本尽量分散（反亲和）、尽量靠近已有副本（亲和）。

**调度器遵循的是「够用就好」而非「最优」**：调度发生在 Pod 创建时，此后节点负载会动态变化，一次打分只是快照。这与你学过的最优化不同——这里追求的是**近似最优 + 确定性**，而不是全局最优解。<span class="marginnote">K8s 调度的「过滤+打分」本质是<strong>约束满足问题</strong>的贪心近似：硬约束做剪枝，软约束做排序。这个两阶段范式在第三级《操作系统》的进程调度（先合法后择优）、以及分布式任务调度里都能看到同构的思想。</span>

## 2 调度策略：亲和性、污点与容忍

生产调度不只是「看资源」，还有几类精细控制手段：

- **节点选择器（nodeSelector）**：最简单，按节点标签硬性挑选（如「GPU 节点」）。
- **节点亲和性（node affinity）**：软/硬两级偏好，如「尽量放在可用区 A，但放不下也别死等」。
- **Pod 亲和性/反亲和性（pod affinity/anti-affinity）**：控制 Pod 之间的聚散——反亲和让副本分散到不同节点（高可用），亲和让相关 Pod 放一起（低延迟）。
- **污点与容忍（taint/toleration）**：节点打污点「标记特殊」，只有声明「我能容忍」的 Pod 才能调度上来——常用于把「有 GPU」或「被运维维护中」的节点隔离出来。

**辨析｜易错点：** 污点与容忍是「排斥」，亲和性是「吸引」，方向相反但经常被混用。污点是**节点主动拒绝**，亲和性是**Pod 主动偏好**。一个 Pod 没声明容忍，就进不了打了污点的节点；一个 Pod 声明了偏好，调度器只是「尽量」满足，不保证。

## 3 伸缩：HPA 与 Cluster Autoscaler

K8s 的伸缩发生在**两个层面**，各自解决不同的问题：

| 伸缩机制 | 伸缩对象 | 依据 | 作用 |
| --- | --- | --- | --- |
| **HPA**（Horizontal Pod Autoscaler） | Pod 副本数 | CPU/内存/自定义指标 | 业务负载变化时加/减副本 |
| **VPA**（Vertical Pod Autoscaler） | Pod 资源配额 | 历史用量 | 调整单副本的 CPU/内存 |
| **Cluster Autoscaler** | 节点数 | 待调度 Pod 是否积压 | 节点不够时云厂商加机器 |

其中最重要的是 **HPA 与 Cluster Autoscaler 的配合**：业务量上来 → HPA 发现副本数不够 → 增加 Pod → 节点资源不够 → 新 Pod 一直 Pending → Cluster Autoscaler 发现积压 → 向云厂商申请新节点 → Pod 落位运行。这套「**应用伸缩 → 集群伸缩**」的联动，正是云弹性最完整的体现。<span class="marginnote">观察这个联动链条会发现：HPA 只看见「副本数」，看不见「节点数」；Cluster Autoscaler 只看见「Pending Pod」，看不见「业务量」——两个组件各自只懂一小块，靠「Pending」这个信号耦合。这就是分布式系统里经典的<strong>松耦合 + 显式信号</strong>设计。</span>

## 4 核心要点对比：三种伸缩的粒度

| 维度 | HPA | VPA | Cluster Autoscaler |
| --- | --- | --- | --- |
| 对象 | Pod 副本数 | 单 Pod 资源 | 集群节点数 |
| 触发 | 业务指标（QPS/CPU） | 资源利用率 | Pod Pending 积压 |
| 时间尺度 | 分钟级 | 分钟级 | 分钟级（含云节点拉起） |
| 适用 | 无状态微服务 | 有状态单实例 | 集群整体容量 |

**辨析｜易错点：** HPA 只能水平伸缩**无状态**应用——数据库这类有状态应用不能随便加减副本（数据一致性会崩）。对数据库，要么用 VPA 垂直扩容，要么用更专门的数据库集群方案。别把「自动伸缩」当成万能药，**伸缩的前提是应用本身可以无痛增减**。

## 5 驱逐与自愈：Pod 的生存守护

调度负责「把 Pod 放上去」，但节点会变坏、资源会耗尽——K8s 还需要一套「把 Pod 妥善搬走」的机制：**驱逐（eviction）**。

**节点压力驱逐**：当节点的内存、磁盘、PID 逼近耗尽时，kubelet 主动**驱逐**一些 Pod，为系统腾出空间。驱逐按优先级（QoS 等级）排序：**先杀 BestEffort（无资源保障）→ 再杀 Burstable（部分保障）→ 最后才动 Guaranteed（完全保障）**。这正是《计算虚拟化》里「资源保障分级」思想在 K8s 的延续——**越贵、越有保障的 Pod，越晚被杀**。<span class="marginnote">一个容易被忽略的细节：驱逐时 kubelet 会先发「优雅终止信号」（SIGTERM），给 Pod 一段宽限期完成在途请求、保存状态，超时才强杀（SIGKILL）。这呼应了《云原生概念与 12 要素》的「易处理」——<strong>优雅退出让 Pod 的死亡不产生可见损伤</strong>。</span>

**节点故障处理**：如果整个节点宕机，控制器检测到「节点失联」后，会在一段时间后把该节点上的 Pod 标记为终止并在**其他节点重建**——因为 Pod 有副本控制器兜底（Deployment 保证数量），重建是自动的。

**PDB：优雅的主动驱逐**：节点要维护、升级时，运维主动驱逐节点上的 Pod。为避免「一次性把所有副本都赶走导致服务中断」，可用 **PodDisruptionBudget（PDB）** 声明「任何时刻至少保持 N 个副本可用」——kubelet 会等副本就绪后再驱逐下一个。**主动驱逐也要守规矩**，这正是高可用设计在运维操作里的落地。

**辨析｜易错点：** 驱逐 ≠ 故障。**驱逐**是系统**主动**清退 Pod（压力大、维护节点），**故障**是 Pod **被动**消失（崩溃、节点宕机）。两者最终都靠控制器重建，但驱逐有优雅终止与 PDB 约束，故障没有——理解区别，才能正确设计「副本数」与「PDB」。

## 6 多集群与联邦：从单集群到集群网络

一个 K8s 集群有规模上限（几千节点、几万 Pod 已是极限），且「所有鸡蛋放一个篮子」有单点风险。生产实践于是出现**多集群**：

- **环境隔离**：dev/staging/prod 各一个集群，互不影响、互不拖累。
- **可用性**：多集群跨可用区/跨地域部署，一个集群故障，流量切到其他集群。
- **规模与性能**：把应用拆到多个集群，每个集群保持可控规模。

**多集群的管理挑战**：多个集群是「多份 K8s」，运维复杂度成倍。解决思路是**平台抽象**：用 GitOps（配置仓库驱动）统一声明各集群的期望状态，用集群注册中心统一纳管。更进一步的 **KubeFed（联邦）**把多个集群组织成一个逻辑集群，一套声明下发到所有集群。<span class="marginnote">多集群与《多云与混合云策略》高度相关：不同集群跑在不同云上（AWS 一个、阿里云一个），就是「多云 + K8s」的组合——K8s 的「<strong>标准化接口</strong>」让跨云多集群成为可能。你会看到，多云落地的技术底座，几乎都是「Terraform 管资源 + K8s 管集群」这对标准抽象。</span>

**辨析｜易错点：** 多集群不是「为了多而多」。**单集群够用就别拆**——多集群让网络互通、服务发现、监控告警全部复杂化。只有当「单集群规模/可用性/环境隔离」真成问题时，才值得引入。这与《多云与混合云策略》的选型逻辑完全一致：**复杂度是逐步买入的，按需引入，别一步到位**。

## 7 实战：GPU 任务怎么被调度

把调度知识落成一个具体场景——**GPU 推理任务的调度**。K8s 调度 GPU 节点靠的是「标签 + 资源 + 亲和性」三件套的配合：

1. **节点打标签**：GPU 节点打上 `gpu=yes` 标签（安装 GPU 驱动后自动或手动标注）。
2. **声明 GPU 资源**：Pod 在 `resources.limits` 里声明需要 `nvidia.com/gpu: 1`——调度器把它当作一种特殊资源，**只把 Pod 放到「有富余 GPU」的节点**。
3. **节点选择器/亲和性**：`nodeSelector: {gpu: yes}` 硬性指定「只去 GPU 节点」。

实际生产里还会叠加亲和性：**让「互为上下游」的推理服务与模型加载服务尽量同节点**（减少网络往返），让「GPU 推理副本」与「GPU 训练任务」**反亲和**（避免抢 GPU 显存）。<span class="marginnote">「资源声明」是调度器决策的依据——Pod 不声明 `nvidia.com/gpu`，调度器就不知道它需要 GPU，可能把它放到没有 GPU 的节点上导致「起不来」。<strong>调度的前提是「把需求说清楚」</strong>——这也是声明式思想的延续：不描述需要什么，系统就不知道怎么给你。</span>

**辨析｜易错点：** GPU 是「整卡分配」的——一个 Pod 声明 1 张 GPU，就独占整张卡（除非用支持 MIG 分片的新卡）。所以「很多小任务要 GPU」时，浪费会很大（每个任务占一整张卡）。方案是「<strong>按需申请 + 共享调度</strong>」（如支持 GPU 分时/分片），这是 K8s GPU 调度的进阶话题。

## 8 小结

- 调度两阶段：**过滤**（硬约束剪枝）→ **打分**（软偏好择优）。
- 精细策略：**亲和性**（吸引）、**污点/容忍**（排斥）、节点选择器。
- 伸缩三层：**HPA**（Pod 副本）、**VPA**（单 Pod 资源）、**Cluster Autoscaler**（节点数）。
- HPA 与 Cluster Autoscaler 靠「Pending 信号」联动，构成完整的云弹性闭环。
- 伸缩的前提是应用**无状态可增减**，数据库不能随便水平扩。

- 调度的价值观：**调度器「选节点」的本质是「在约束里做资源分配」**——这个思想从进程调度到云调度一脉相承，理解一次，处处受用。

- 核心记忆点：**调度是「创建时定位置」，伸缩是「运行中调数量」**——一静一动，共同构成 K8s 的自动管理。
- 面试常见问法：「**HPA 与 Cluster Autoscaler 的关系**」——答「HPA 加 Pod、Pod Pending 触发 CA 加节点」的联动链条即满分。
- 与后续的衔接：弹性伸缩是云「弹性」承诺在容器层的兑现，与成本篇的「弹性省成本」直接相关。
- 自查练习：**画一条「HPA 加副本 → 节点不够 → CA 加节点 → Pod 落位」的链路**——能画通，说明真理解弹性闭环。
- 调度的两个阶段可浓缩为八个字：**先过滤（硬约束）、再打分（软偏好）**。
- 伸缩的完整链条是「**应用层 HPA → 集群层 CA → 云平台加节点**」——三层联动，云弹性才真正落地。
