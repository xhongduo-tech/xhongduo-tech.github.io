## 为什么从基础设施即代码开始

手动在云控制台点鼠标建虚拟机、配安全组、建数据库——一两台还行，几十台就是灾难：不可复现、不可审查、不可回滚，还容易漂移。**基础设施即代码（IaC）**把这一切改写：基础设施的定义从「点击」变成**代码**，从而获得代码的全部好处——版本化、评审、自动化、可复现。这一篇以 Terraform 为例，讲清 IaC 的心智模型。

「为什么基础设施要变成代码」的答案，与「为什么应用代码要进 git」完全同构：**能版本化，就能回溯；能评审，就能把关；能重放，就能复现**。手动点击是「口口相传的操作」，代码是「白纸黑字的契约」——IaC 的本质，是把「运维操作」升级成「工程资产」。

## 1 IaC：把「点鼠标」变成「写声明」

**基础设施即代码（Infrastructure as Code，IaC）**：用**声明式的代码/配置文件**描述云资源（虚拟机、网络、数据库、权限），由工具自动创建与更新这些资源，取代手工操作。

IaC 与手动的本质差异：

- **可复现**：一份配置，在开发、测试、生产环境重复执行，得到一致的资源。
- **可审查**：基础设施变更走代码评审（Code Review），改什么一目了然、有人把关。
- **可回滚**：出问题恢复上一版配置，重跑一次即可。
- **可审计**：所有变更留在 git 历史里，谁在何时改了什么，可追溯。

IaC 是「声明式运维」的体现——你描述**想要的最终状态**，工具负责「怎么从现状到达那里」。这正是你在 K8s 里反复见到的声明式思想，从应用扩展到了整个基础设施。<span class="marginnote">IaC 与 K8s 声明式的区别：K8s 的声明式管「集群内」，IaC 管「云平台上」——Terraform 可以创建整个 K8s 集群本身（EKS/ACK），也可以创建 VPC、数据库、CDN。两者是「建房子的」与「装修的」关系。</span>

## 2 Terraform 的核心三件套

**Terraform** 是 HashiCorp 出品的事实标准 IaC 工具，三大核心概念：

**配置（HCL 代码）**：用声明式语言描述「我要什么资源」。一个「创建一台 EC2 + 一个安全组」的配置就是几十行 <code>.tf</code> 文件。
**状态（state）**：Terraform 保存一份「当前真实资源」的映射（存本地或远程后端），记录每个资源与云上实体的对应关系。**状态是 Terraform 的「账本」**——它知道什么已建、什么要改。
**计划（plan）**：<code>terraform plan</code> 对比「期望配置」与「当前状态」，输出一份「将创建 X、修改 Y、删除 Z」的变更清单，供人审查。

**核心流程**：write → plan → apply → 更新状态。每次 apply 前先 plan，让你**在动手前看清所有变更**——这是 IaC 比手动操作安全的关键。<span class="marginnote">状态文件是 IaC 的灵魂也是弱点：如果状态丢了，Terraform 就「失忆」了，不知道资源谁建的。生产实践必须把状态存到<strong>远程共享后端</strong>（如 S3 + DynamoDB 锁、Terraform Cloud），并加锁防多人并发冲突——这是分布式系统「共享状态」问题的又一实例。</span>

## 3 公式解析：一次 apply 的生命周期

把 Terraform 的「从代码到资源」写成一个转化链：

$$
\text{配置（.tf）} \;\xrightarrow{\text{plan}}\; \text{变更计划} \;\xrightarrow{\text{apply}}\; \text{真实资源} \;\xrightarrow{\text{update}}\; \text{状态（state）}
$$

逐步拆解这条链：

- **第一步，plan**：Terraform 读配置、读状态，做**差异对比**（diff），产出「要创建/修改/删除什么」的计划，并让用户确认。
- **第二步，apply**：按计划调用云厂商 API 创建/更新/删除资源。执行过程是**幂等**的——同一配置重复 apply，第二次不会有任何变更（因为状态已与配置一致）。
- **第三步，update state**：apply 成功后，把真实资源的标识（实例 ID、IP 等）写回状态文件，供下次对比。
- **关键性质：声明式幂等**——配置是「期望状态」，工具持续收敛，这与 K8s 控制回路的「期望→实际」闭环完全同构。

## 4 核心要点对比：IaC vs 手工控制台

| 维度 | 手工控制台 | 基础设施即代码 |
| --- | --- | --- |
| 可复现性 | 差（靠人记忆） | 强（代码即真相） |
| 变更审查 | 无 | 代码评审 + plan 清单 |
| 回滚 | 手动逆向操作 | 重跑旧版本配置 |
| 漂移检测 | 靠巡检 | 自动对比状态 |
| 自动化 | 难 | 天然 CI/CD 集成 |
| 学习成本 | 低 | 中高 |

**辨析｜易错点：** IaC 不是「把点击过程录制成脚本」。录制脚本是**命令式**（一步步照做），配置漂移或环境不同就失效；IaC 是**声明式**（描述结果），工具自动算出怎么做。两者的差别，正是《云原生概念与 12 要素》里声明式与命令式的差别——**声明「要什么」，而不是「怎么做」**。<span class="marginnote">IaC 与 CI/CD 是天然搭档：提交代码 → CI 跑 plan（预览变更）→ 人工批准 → CD 执行 apply。云上「<strong>基础设施变更也走流水线</strong>」是现代平台工程的标准形态——它与下一篇《CI/CD 与 DevOps》互相成就。</span>

## 5 模块化与多环境：让 IaC 规模化

一个团队把「所有资源」写进一个 <code>.tf</code> 文件，很快会变成几千行的巨石——IaC 也需要像代码一样**模块化**与**环境管理**。

**模块（module）**：把「可复用的资源组」封装成模块，如「创建一个 VPC 及其子网」「创建一套 K8s 集群」。不同项目复用同一模块，保证一致性（大家都用同一套标准建网络），改一处即全量升级。**模块是 IaC 的「函数」**——参数化、可复用、版本化。

**多环境管理**：用**workspace**或**目录分拆**管理 dev/staging/prod 三套环境。关键原则：

**环境间隔离**：dev 的变更不影响 prod（状态文件分开 + 后端隔离）。
**尽量一致**：dev 与 prod 用同一套模块、同一份代码，只是参数不同——「环境漂移」（dev 与 prod 差很多）是 IaC 最隐蔽的失败。
**prod 受保护**：生产环境的 apply 走审批流（人工 review plan），不让 dev 顺手改坏。

**辨析｜易错点：** IaC 引入了「**漂移（drift）**」——有人绕过 IaC 手动改了资源（控制台点了一下），代码与真实状态就不一致了，下次 <code>terraform plan</code>` 会显示大量差异。应对靠**持续对账**（定期 <code>terraform plan</code>` 检测漂移）与**治理规则**（禁止手动改云资源、只允许走 IaC）。<span class="marginnote">漂移是 IaC 的头号敌人：代码说「应该这样」，云上「实际上是那样」，中间差出来的，就是事故隐患。成熟团队会把「<strong>每次 plan 是否有意外差异</strong>」作为 CI 的一个检查项——有差异就报警，把漂移扼杀在萌芽。</span>

## 6 IaC 生态：Ansible、Pulumi 与配置管理

Terraform 是「供应（provision）资源」，但 IaC 的生态比它更宽——**配置管理（configuration management）**是另一个重要分支。

**配置管理**（Ansible、Chef、Puppet、SaltStack）解决的是「**资源创建之后，怎么把软件装好、配置好**」——Terraform 建好一台虚拟机，Ansible 在这台虚拟机上装 Nginx、写配置、启动服务。两者**分工互补**：

| 工具 | 类型 | 管什么 | 语言 |
| --- | --- | --- | --- |
| Terraform | 基础设施供应 | 云资源（VM/网络/存储） | HCL |
| Ansible | 配置管理 | 机器内软件与配置 | YAML |
| Pulumi | 基础设施供应 | 云资源（同 Terraform） | 通用编程语言（Python/TS） |

**Pulumi** 值得一提：它和 Terraform 一样做「基础设施供应」，但用**通用编程语言**（Python、TypeScript、Go）写配置——比 HCL 多了循环、函数、类型检查，适合「基础设施逻辑复杂、需要编程能力」的团队。<span class="marginnote">「供应」与「配置管理」的区别可以用盖房子类比：<strong>Terraform 是「打地基、起框架」（把资源建出来），Ansible 是「装修、通电、安家具」（把机器配置好）</strong>。现代实践常「Terraform + Ansible」组合：Terraform 建好基础设施，Ansible 初始化机器。云原生的容器场景里，这步又被「镜像 + K8s」取代了（镜像把「配置」固化进构建期）——但两者思想相同：<strong>一切可复现、可版本化</strong>。</span>

**辨析｜易错点：** 别把「配置管理」当「基础设施供应」——用 Ansible 去建云资源（勉强能但反直觉），或用 Terraform 去管机器内软件（也别扭）。**工具按职责分工，是最省心的 IaC 实践**。

## 7 小结

- **IaC**：用声明式代码描述云资源，取代手工操作，获得**可复现、可审查、可回滚、可审计**。
- Terraform 三件套：**配置**（HCL）、**状态**（账本）、**计划**（变更预览）。
- 核心流程：**write → plan → apply → 更新状态**，声明式幂等。
- 状态文件要存**远程后端 + 加锁**，否则失忆或并发冲突。
- IaC 是声明式运维的体现，与 K8s 声明式一脉相承，与 CI/CD 天然集成。

- IaC 与 CI/CD 的衔接：**IaC 让「环境」可进流水线，CI/CD 让「变更」可进流水线**——两者合起来，基础设施与应用才能一起「从提交到上线」。

- 核心记忆点：**Terraform 三件套 = 配置（声明）+ 状态（账本）+ 计划（预览）**——声明式幂等是灵魂。
- 面试常见问法：「**terraform plan 和 apply 的关系**」——答「plan 预览 diff、apply 执行 diff、状态随之更新」即过关。
- 与后续的衔接：IaC 让「环境」可进流水线，正是 CI/CD 让「变更」自动化的前提——二者合流才是完整交付。
- 自查练习：**解释「为什么 apply 是幂等的」**——配置是期望状态、状态是对照账本，两者一致则无事可做，即幂等。
- 一句总结：**声明要什么，而非怎么做**——这句话同时适用于 Terraform、K8s 与整个云原生。

在下一篇，我们把「变更自动化」推到极致——**CI/CD 与 DevOps**，看从代码提交到上线的完整流水线。IaC 自动化的是「资源的变更」，CI/CD 自动化的是「代码的变更」——**下一篇把两者放进同一条流水线，就构成了现代交付的全部骨架**。
