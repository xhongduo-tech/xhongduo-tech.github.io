## 为什么从核心特征开始

上一篇我们确立了云计算的 NIST 定义，但「可配置资源池」「按需获取」这些词还是抽象的。这一篇把 NIST SP 800-145 给出的**五条核心特征**逐条拆开：按需自助服务、广泛网络接入、资源池化、快速弹性、可计量服务。这五条不是并列的装饰，而是一套**互相咬合的机制**——少了任何一条，云都会坍缩成「远程机房」。学完这一篇，你会具备判断「某个产品是不是真云」的标尺。

先给一个整体的预感：这五条可以归成两组。**前三**（按需、接入、池化）回答「云怎么运转」——它是怎么把资源供给变得自助、怎么把能力送到你面前、怎么在物理上共享；**后两**（弹性、计量）回答「云凭什么值得用」——它凭什么能按实际需求伸缩、凭什么能按用量收钱。分组理解，比五条平铺更好记。

## 1 按需自助服务与广泛网络接入

**按需自助服务（on-demand self-service）**：用户无需与服务商人工交互，即可自行开通、配置、调整计算资源。对应的产品形态是控制台、CLI 与 API——一个 HTTP 请求就能创建一台虚拟机。**广泛网络接入（broad network access）**：能力通过标准网络协议（HTTP/HTTPS）提供，支持从手机、笔记本、工作站的任意异构客户端访问。

这两条合起来回答了「云怎么用」：**接口标准化 + 供给自动化**。与自建机房相比，从「提交工单、等审批、上架机器」的数周流程，压缩到「敲一条命令」的秒级流程。<span class="marginnote">「按需自助」能成立的前提是服务商把「开通」做成幂等 API 而非人工流程。这背后是控制面（control plane）与数据面（data plane）的分离——控制面只负责编排，数据面才承载流量。这个分离思想在云网络与 K8s 里反复出现。</span>

## 2 资源池化与快速弹性

**资源池化（resource pooling）**：提供商的计算资源被汇入一个多租户共享的池子，按需动态地分配给不同用户；用户通常不知道（也不必知道）资源的确切物理位置。物理隔离被**逻辑隔离**取代——你我可能共用同一台物理机，但在各自虚拟机里互不可见。

**快速弹性（rapid elasticity）**：资源可以快速、弹性地扩缩，对用户而言能力「看起来是无限的」，可随时购买任意数量。弹性包含两个方向：**水平伸缩**（加/减机器数量）与**垂直伸缩**（升级/降级单机规格）。弹性是云最有价值的单一特性——它把「为峰值买机」变成「为实际用量付费」。

**辨析｜易错点：** 「弹性」不等于「能扩容」。传统机房也能扩容，但那是**规划式扩容**（提前数月采购、按峰值预留）；云的弹性是**反应式扩容**——业务量涨了，几分钟内自动多拉起几十台机器，业务量跌了再缩回来。弹性测的不是上限，而是**伸缩的速度与粒度**。

## 3 可计量服务

**可计量服务（measured service）**：云系统通过计量能力自动控制和优化资源使用，对存储、处理、带宽、活跃用户账户等进行测量，按使用量向服务商与用户透明计费。常见的计量单位有：

| 资源类型 | 计量单位 | 典型计费方式 |
| --- | --- | --- |
| 计算 | vCPU·小时 | 按实例运行时长 |
| 存储 | GB·月 | 按存储量按月 |
| 网络 | GB 流量 | 按出方向流量 |
| 函数计算 | 请求次数 × 运行时长 | 按调用计费 |

计量的意义在于把 IT 支出从**资本支出（CapEx）**转为**运营支出（OpEx）**：不再一次性购买服务器，而是每月按账单付钱。这既是财务模型的转变，也是「按需」在商业上的落地——**没有计量，就没有真正的按需付费**。

## 4 核心要点对比：五个特征如何互相支撑

纯概念主题，用一张表看五个特征的「输入—输出」闭环：

| 特征 | 解决什么问题 | 不满足时会怎样 |
| --- | --- | --- |
| 按需自助服务 | 供给慢 | 回到工单审批流程 |
| 广泛网络接入 | 访问不便 | 只能现场使用，云不成立 |
| 资源池化 | 利用率低 | 回到物理隔离的闲置浪费 |
| 快速弹性 | 峰谷波动 | 为峰值买单，成本失控 |
| 可计量服务 | 成本不可见 | 无法按量计费，商业模式崩塌 |

这五条构成一个正反馈环：**资源池化**提供了弹性的物理前提，**按需自助**让弹性可以被用户即时触发，**计量**让弹性产生的成本可结算，**广泛接入**让这一切通过网络交付。<span class="marginnote">把这个环想清楚，就理解了「云为什么是平台而不仅仅是技术」：五个特征里四个是工程能力，而「可计量」是商业模式。云既是分布式系统的产品化，也是会计学在 IT 上的应用。</span>

## 5 弹性预算：一个数字例子

把「弹性省钱」落到数字上，感受会更具体。假设某电商业务的服务器需求是：**平均 20 台、大促峰值 100 台、平时低谷 10 台**，每台实例折算每月成本 1000 元。

**传统采购（按峰值规划）**：一次买 100 台备着。一年成本：

$$100 \text{ 台} \times 12 \text{ 个月} \times 1000 \text{ 元} = 120\ \text{万元}$$

但 100 台里常年只有 20 台在干活，**80 台（80% 的资产）大部分时间闲置**——钱花了，机器闲着。

**云弹性（按需伸缩）**：平时 20 台，低谷缩到 10 台，大促自动涨到 100 台扛过峰值再缩回。假设 10% 的时间在峰值、90% 的时间在均值：

$$(100 \times 0.1 + 20 \times 0.9) \text{ 台} \times 12 \text{ 个月} \times 1000 \text{ 元} = 33.6\ \text{万元}$$

同样是服务同样的业务量，**成本从 120 万降到约 34 万**——省下的正是「为峰值预留却常年闲置」的那部分。<span class="marginnote">这个例子里最关键的假设是「<strong>应用能被自动伸缩</strong>」——无状态、可横向扩展、有健康检查。如果应用是有状态的单体，加机器也扛不住峰值，那云弹性对你无效，该先做应用改造（见第四篇《云原生概念与 12 要素》）。</span>

**辨析｜易错点：** 弹性省钱有个前提——**你的负载真的会波动**。如果业务量恒定，弹性毫无意义，反而应该用预留/包年拿折扣（见《云成本优化》一篇）。「为波动买单」还是「为恒定拿折扣」，是成本优化的第一个分叉口。

## 6 可用性、区域与 SLA：把「可靠」写成数字

五条特征里「资源池化与弹性」还隐含着一个维度的设计——**物理上把云放在哪、坏了怎么办**。云厂商把基础设施按三层组织：

- **区域（Region）**：一个独立的地理位置（如华北一、弗吉尼亚北部），包含多个可用区。区域之间完全隔离，跨区域做**灾备**。
- **可用区（Availability Zone，AZ）**：一个区域内独立的电力、网络与机房单元，相互之间延迟低但故障隔离——一个可用区断电，另一个不受影响。
- **边到边（Edge）**：遍布各地的 CDN 节点，离用户最近，只管加速。

**高可用的正确姿势：跨可用区部署**。一个应用至少要部署在两个可用区，负载均衡（LB）把流量分发到各区——某个可用区故障，流量自动切到其他区，用户无感。**只部署在一个可用区，就谈不上高可用**。

**SLA（服务水平协议）**：云厂商对「可用性」的书面承诺，通常以「几个 9」表示：

| SLA | 年度不可用时间 | 含义 |
| --- | --- | --- |
| 99.9%（三个 9） | 约 8.76 小时 | 入门级 |
| 99.95% | 约 4.38 小时 | 常用企业级 |
| 99.99%（四个 9） | 约 52.6 分钟 | 关键业务 |

**辨析｜易错点：** 99.9% 听起来很高，换算成时间是一年 **8.76 小时**的宕机——对核心交易系统来说不可接受。而且**厂商 SLA 只是「赔钱」，不是「保证不出事」**：违约赔偿往往只是费用折扣，弥补不了业务损失。<span class="marginnote">真正的高可用要靠「<strong>多层冗余 + 快速切换</strong>」，而不是指望厂商 SLA。业界经验是「<strong>永远假设区域会挂</strong>」——所以关键数据要跨区域复制、关键应用要跨区部署、还要有演练。SLA 是保险，架构才是保障。</span>

## 7 小结

- 五条核心特征：**按需自助、广泛接入、资源池化、快速弹性、可计量服务**。
- 按需自助 = 标准化 API + 供给自动化；广泛接入 = 标准网络协议交付。
- 资源池化以**逻辑隔离**取代物理隔离；弹性以**水平伸缩**为主、反应式触发。
- 弹性 ≠ 能扩容，而是**伸缩速度与粒度**；计量把 CapEx 变为 OpEx。
- 五条特征互相咬合：池化是前提、自助是触发、弹性是能力、计量是闭环。

- 五条特征的可检验性：**每一条特征都能用一个「能不能」提问来检验**——能不能自助开通、能不能网络接入、能不能池化、能不能快速伸缩、能不能计量。下一篇的服务模型，正是这些能力「被切到哪一层」的问题。

- 核心记忆点：**五条特征不是「清单」，而是「闭环」**——按需触发弹性、弹性消耗计量、计量支撑付费、付费反哺资源池。
- 面试常见问法：「**说出一条特征，并解释没有它云会怎样**」——能答出「没有弹性 → 为峰值买单」这类因果，才算真懂。
- 与后续的衔接：五条特征中的「可计量」是成本篇（FinOps）的前提，「弹性」是伸缩篇的前提——它们会反复出现。
- 自查练习：**给身边一个「号称云」的产品做五问体检**——按需？接入？池化？弹性？计量？缺哪个、为什么缺，说清楚就是真懂。
- 五条特征可浓缩为三个词：**自助、弹性、计量**——其余两条（接入、池化）是它们的支撑条件。
- 这三个词也是判断「真云 vs 假云」的最短标尺——**没有自助就没有按需，没有弹性就没有省心，没有计量就没有商业模式**。
- 复习提示：下一篇《云服务模型》将解释「为什么同一朵云能按三种方式卖」——带着五条特征去读，理解会更连贯。

在下一篇，我们从「云长什么样」进入「云卖什么」——IaaS、PaaS、SaaS 三种服务模型，理解云能力被交付的三种切法。核心特征定义了「云是什么」，服务模型则定义了「云把什么卖给你、你接管什么」——**从「能力」走向「切分」**。
