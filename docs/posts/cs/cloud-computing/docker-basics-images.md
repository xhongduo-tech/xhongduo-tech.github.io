## 为什么从 Docker 开始

上一篇讲清了容器与虚拟机的差异，这一篇落地点：**Docker**——把容器从「内核机制」变成「工程师日常工具」的那层封装。Docker 的神奇之处在于三个概念：**镜像（image）**把应用和依赖打包成标准化制品，**容器（container）**是镜像的运行实例，**镜像仓库（registry）**让镜像像代码一样分发共享。学完这一篇，你就掌握了「容器化」的核心心智模型，Kubernetes 只是把这份心智放大到集群规模。

## 1 Docker 的三件套：镜像、容器、仓库

**Docker 镜像（image）**：一个**只读**的、分层打包的模板，包含应用代码、运行环境、依赖库与配置。**Docker 容器（container）**：镜像的运行实例，在镜像之上加一个**可写层**——进程改动写入可写层，镜像本体不被污染。**镜像仓库（registry）**：存放与分发镜像的服务（Docker Hub、阿里云容器镜像服务 ACR）。

三件套构成一个清晰的流水线：**镜像 = 图纸，容器 = 按图纸造出来的房子，仓库 = 图纸库**。你拉取（`docker pull`）镜像 → 创建并运行（`docker run`）容器 → 房子开始住人（进程运行）。销毁容器，房子拆掉，图纸还在。<span class="marginnote">「镜像只读、容器可写」是 Docker 最优雅的设计：同一镜像可以同时跑一万个容器，互不干扰——因为每个容器的改动都只落在自己那层可写层上。这就是容器密度能上百上千的底层原因：<strong>基础层被所有人共享</strong>。</span>

## 2 镜像分层：UnionFS 的复用魔法

镜像是**分层的**，这是 Docker 与虚拟机镜像的根本区别。构建镜像时，每一条指令生成一层；多层的文件系统通过 **UnionFS（联合文件系统）** 叠加起来，对外呈现为一个完整的文件系统。

分层带来两个巨大收益：

- **复用与共享**：多个镜像共享底层的基础镜像层（如 `ubuntu` 层），物理磁盘只存一份。拉取新镜像时，已存在的层直接复用，网络与磁盘开销骤降。
- **增量分发**：更新应用时只推「变化的那几层」，而不是整个镜像——这在 CI/CD 频繁发布时是决定性的效率优势。<span class="marginnote">分层就像「乐高积木」：<strong>公共积木（基础层）大家共用，只有你独有的积木才占你自己的空间</strong>。Docker 的镜像仓库按层寻址、按层去重，几万个基于同一基础镜像的应用，实际存储量远小于各自体积之和。</span>

## 3 公式解析：从 Dockerfile 到容器

把「源码 → 运行中的容器」写成一条转化链：

$$
\text{Dockerfile} \;\xrightarrow{\text{build}}\; \text{镜像（分层）} \;\xrightarrow{\text{run}}\; \text{容器（可写层 + 进程）}
$$

逐步拆解：

- **第一步，Dockerfile**：一个声明式文本，逐行描述如何构建镜像。每一条指令（`FROM`、`COPY`、`RUN`、`EXPOSE`）生成一个镜像层，是「镜像的源代码」。
- **第二步，build**：`docker build` 逐层执行 Dockerfile，产物是只读的**镜像**，推送到仓库后可在任何装了 Docker 的机器上 `pull`。
- **第三步，run**：`docker run` 在镜像之上叠一个**可写层**，并启动容器内的主进程。容器停止后，可写层默认被丢弃——容器因此是**无状态**的。
- **补一句**：容器需要持久化的数据（如数据库文件），要挂载**数据卷（volume）**——把宿主机目录或专用卷映射进容器，让数据活着，容器死了不心疼。

## 4 核心命令与日常心智模型

Docker 的命令虽多，但核心只有一组心智模型：

| 阶段 | 命令 | 作用 |
| --- | --- | --- |
| 构建 | `docker build -t myapp .` | 按 Dockerfile 构建镜像并打标签 |
| 拉取 | `docker pull nginx` | 从仓库下载镜像 |
| 运行 | `docker run -d -p 8080:80 nginx` | 后台运行容器，映射端口 |
| 查看 | `docker ps` | 列出运行中的容器 |
| 停止/删除 | `docker stop` / `docker rm` | 停止并删除容器 |
| 打包分发 | `docker push myapp` | 把镜像推送到仓库 |

**辨析｜易错点：** 容器是**临时**的——`docker run` 起的容器默认不留数据、不留日志。数据库这类有状态服务直接跑在容器里是反模式：重启容器 = 丢数据。正确姿势是**把数据挂进 volume、把配置注入环境变量**，让容器保持无状态、可随时替换。这条「无状态化」原则，正是下一课 K8s 调度一切的前提。<span class="marginnote">「容器无状态 + 数据外置」是云原生时代的铁律：Kubernetes 能随时杀掉、重建、迁移容器，前提是容器本身不携带任何「记忆」。你会看到这个概念在《Pod/Service/Deployment 编排》与《云原生概念与 12 要素》里反复强化。</span>

## 5 镜像仓库与供应链安全

镜像可以随处跑，也意味着镜像可能**到处出问题**——镜像供应链已成为安全攻防的新前线。几个必须理解的概念：

- **镜像仓库（registry）**：镜像的分发中心。公有仓库（Docker Hub）方便但鱼龙混杂；企业生产几乎都使用私有仓库（阿里云 ACR、Harbor），配合访问控制与镜像扫描。
- **镜像标签（tag）**：`nginx:latest` 中的 `latest`。**别在生产用 `latest`**——它指向的镜像会变，导致「昨天能跑今天不能跑」。
- **不可变标签**：用「应用名 + 提交号/版本号」做标签（如 `myapp:1.2.3-abc1234`），每个版本镜像不可变，可追溯、可回滚。

**多阶段构建（multi-stage build）**是镜像瘦身与安全的标配：用「构建阶段」装编译工具编译出产物，再用「运行阶段」从干净基础镜像拷贝产物——最终镜像只含运行所需，**不含编译工具与源码**，又小又安全。

| 实践 | 解决的问题 | 一句话 |
| --- | --- | --- |
| 多阶段构建 | 镜像体积大、含多余文件 | 只留运行时产物 |
| 固定基础镜像版本 | 基础镜像漂移 | 锁 `nginx:1.27` 而非 `latest` |
| 镜像扫描 | 依赖含已知漏洞 | 推送前扫 CVE |
| 签名与信任 | 镜像被篡改 | 校验来源与完整性 |

**辨析｜易错点：** 「镜像扫描一遍没漏洞」不等于「供应链安全」——你依赖的基础镜像、父镜像、甚至构建工具本身都可能被投毒。完整的供应链安全是**信任链**：锁版本、验签名、扫漏洞、做 SBOM（软件物料清单）四件事一起做。<span class="marginnote">镜像供应链与《云安全与合规》的共享责任模型对应：云厂商管「仓库平台安全」，你管「镜像内容安全」——<strong>扫描、签名、锁版本、审依赖</strong>都是你自己的责任。著名的软件供应链攻击（如依赖混淆、恶意 npm 包）正是从这条链的薄弱环节打进来的。</span>

## 6 Docker Compose：把「多容器应用」写成一份文件

Docker 的威力不止于单容器——一个现代应用往往由**前端、后端、数据库、缓存**多个容器组成。**Docker Compose** 用一份 `docker-compose.yml` 声明整套应用，`docker compose up` 一键拉起。

一个最小示例（示意）的骨架：

```yaml
services:
  web:
    build: .
    ports:
      - "8080:80"
    depends_on:
      - db
  db:
    image: mysql:8
    environment:
      MYSQL_ROOT_PASSWORD: secret
    volumes:
      - db-data:/var/lib/mysql
volumes:
  db-data:
```

这份文件做了三件关键的事：**声明服务**（web 与 db 两个容器）、**声明依赖**（web 依赖 db）、**声明持久化**（`db-data` 卷保住数据库数据）。Compose 自动创建内部网络让容器互相发现（`web` 通过服务名 `db` 访问数据库），完全不需要手动配 IP。<span class="marginnote">Compose 的价值在于「<strong>把环境定义成代码</strong>」：新同事 clone 代码后 `docker compose up` 就得到完整开发环境，不用看几十页的「环境搭建文档」。这与《基础设施即代码》是同一个思想——<strong>环境是代码、可复现、可版本化</strong>——只是粒度从「云资源」降到了「本地容器」。</span>

**辨析｜易错点：** Compose 是「本地/单机编排」，不是「生产编排」。它在**一台机器**上管理容器，没有故障自愈、没有跨节点调度、没有滚动更新——这些是 Kubernetes 的事（见《Kubernetes 架构与核心对象》）。正确用法：**开发环境用 Compose 快速起整套依赖，生产环境用 K8s 编排**。别用 Compose 扛生产，也别用 K8s 跑本地开发——工具各归其位。

## 7 小结

- Docker 三件套：**镜像**（只读模板）、**容器**（可写运行实例）、**仓库**（分发中心）。
- 镜像是**分层的**，通过 UnionFS 叠加；分层带来**复用、共享、增量分发**三大优势。
- 转化链：**Dockerfile → build → 镜像 → run → 容器**。
- 容器默认**无状态**，持久化靠**数据卷**挂载。
- 命令心智模型：build / pull / run / ps / stop / push。

在下一篇，我们把单机容器放大到集群——**Kubernetes 架构与核心对象**，看 Google 如何用十年 Borg 经验，把「跑容器」变成「编排容器」。
