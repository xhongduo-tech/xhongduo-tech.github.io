## 为什么从 Kubernetes 开始

Docker 解决「单机跑容器」，但生产环境有几十上百台机器，容器要分发、调度、故障自愈、自动伸缩——单靠 Docker 忙不过来。**Kubernetes（K8s）** 是谷歌基于内部系统 Borg 开源出来的容器编排平台，如今已是云原生的「事实标准操作系统」。这一篇先立起 K8s 的整体骨架：**谁在管（控制面）、谁在干活（工作节点）、管什么（核心对象）**。骨架立住后，下一课才谈具体的编排细节。

一个背景先补上：K8s 不是「几个工程师造的新工具」，而是**谷歌内部 Borg 系统十年经验的公开版**——谷歌每天在 Borg 上调度海量容器，K8s 是把这套经过大规模验证的设计思想开源。这也是为什么 K8s 一出生就显得「体系完整」：它不是从零设计，而是「成熟系统的开源复制」。

## 1 K8s 是什么：声明式编排

**Kubernetes**：一个开源的容器编排平台，负责容器的**部署、调度、伸缩、自愈与服务发现**。它的核心哲学是**声明式（declarative）**：你告诉它「我想要什么状态」（比如「跑 3 个 nginx 副本」），它负责持续让实际状态收敛到期望状态——不需要你告诉它「怎么一步步做」。<span class="marginnote">声明式 vs 命令式（imperative）是 K8s 最重要的心智转变：命令式像「一步步指挥」，声明式像「写下目标，系统自己对齐」。这个「期望状态 → 实际状态」的闭环，就是分布式系统里的<strong>控制回路（control loop）</strong>，也是管理面组件的设计灵魂。</span>

K8s 的架构分为**控制面（control plane，管理者）**与**工作节点（worker node，执行者）**两大部分。

## 2 控制面：集群的「大脑」

控制面由四个核心组件组成，每个都只负责一件事：

| 组件 | 职责 | 一句话理解 |
| --- | --- | --- |
| **etcd** | 集群状态的权威存储 | 集群的「数据库」，存所有对象的期望状态 |
| **kube-apiserver** | 唯一入口，处理所有请求 | 集群的「前台」，所有操作都走它 |
| **kube-scheduler** | 决定 Pod 落在哪个节点 | 集群的「分配员」，看资源、看约束 |
| **kube-controller-manager** | 运行各类控制器，收敛状态 | 集群的「监工」，让现实对齐期望 |

`etcd` 是这一切的地基：它是一个分布式键值存储，保存着集群的**全部状态**。控制面组件彼此通过 API server 交互，自己几乎不直接通信——这让整个系统高度解耦、可插拔。<span class="marginnote">等一会：控制面组件之间「只通过 etcd/API 交流」，是不是有点眼熟？这正是第三级《分布式系统》里「用共识日志作为唯一事实源」的经典结构——etcd 用 Raft 共识保证多副本一致，控制面坏了某个组件可换可重启，状态不丢。</span>

## 3 工作节点：集群的「肌肉」

每个工作节点上运行着三个组件，负责真正跑容器：

- **kubelet**：节点上的「代理人」，负责接收 API server 下发的 Pod 规格，调用容器运行时把容器拉起来，并持续上报状态与健康。
- **kube-proxy**：负责集群网络规则，把访问 Service 的流量转发到对应的 Pod，是负载均衡的网络实现者。
- **容器运行时（container runtime）**：真正创建和运行容器的底层引擎（containerd、CRI-O、Docker 兼容层）。

一句话概括分工：**控制面「决定」要什么，工作节点「执行」并「回报」**。kubelet 是连接两者的神经末梢——它不断把节点与 Pod 的真实状态回报给控制面，控制面据此判断是否需要干预。

## 4 三大核心对象：Pod、Deployment、Service

K8s 的一切能力都体现在**对象（object）**上，其中最核心的三个是：

- **Pod**：调度的**最小单元**，一个或多个紧密耦合的容器共享网络命名空间与存储卷。同一 Pod 内的容器共享 IP、共享 localhost、共享挂载卷——它们是「同居」的。
- **Deployment**：描述「期望的副本数与更新策略」的控制器对象。它保证指定数量的 Pod 副本始终存在，并负责**滚动更新**（不中断服务的版本升级）与**回滚**。
- **Service**：稳定的**访问入口**。Pod 的 IP 会随创建/销毁而变，Service 提供一个固定 IP + DNS 名，把请求负载均衡到一组标签匹配的 Pod 上。

**辨析｜易错点：** Pod 是「最小调度单元」不等于「最小运行单元是容器」——两者经常被混淆。一个 Pod 可以只装一个容器，也可以装多个；但它们永远**一起调度、一起伸缩、共享网络**。把「容器」当调度单元、或把「整个 Deployment 当调度单元」，都是常见的理解偏差。<span class="marginnote">这三个对象的关系可以记成一句话：<strong>Deployment 管「有多少个 Pod」，Service 管「怎么找到这些 Pod」，Pod 管「里面住着哪些容器」</strong>。下一篇《Pod/Service/Deployment 编排》会把三者的生命周期与相互配合完整展开。</span>

## 5 控制回路的秘密：控制器模式

K8s 声明式哲学的执行引擎，是遍布控制面的**控制器（controller）**。理解「控制器模式」，就理解了 K8s 的心脏。

**控制器模式**：一个控制器负责「一类对象」，它不断执行一个三拍循环：

1. **观察（observe）**：读取对象的**期望状态**（如「3 个副本」）与**实际状态**（当前只有 1 个 Pod）。
2. **对比（diff）**：算出差距（差 2 个）。
3. **纠正（act）**：执行操作缩小差距（再创建 2 个 Pod），然后回到第 1 步。

这个「观察-对比-纠正」循环永不停歇——即使你手动删掉一个 Pod，控制器几秒内就会补一个新的，因为「期望 3 个」从未改变。<span class="marginnote">控制器模式是分布式系统「<strong>声明式收敛</strong>」的工程化身：系统不靠「一次性指令」而是靠「持续对齐」工作。这与第三级《分布式系统》里的「自愈」「状态机复制」同源——K8s 把「自愈」做成了通用的平台机制，任何对象都能被对应控制器自动修复。</span>

**控制器为什么叫「-controller-manager」**：控制面里运行着许多控制器（Deployment 控制器、ReplicaSet 控制器、Namespace 控制器……），由 `kube-controller-manager` 统一承载。每个控制器只盯着自己那类对象，互不干扰——**单一职责 + 消息驱动**，是这套体系能稳定运行的关键。

**辨析｜易错点：** 别把「控制器」与「调度器」混淆。**控制器**负责「数量对不对」（副本收敛），**调度器**负责「Pod 放哪台节点」（位置决策）。控制器发现缺 2 个 Pod → 创建 Pod 对象 → 调度器为它们选节点。一个管「有多少」，一个管「在哪跑」，前后衔接、各司其职。

## 6 Namespace 与资源配额：集群内的「租户管理」

一个 K8s 集群常被多个团队/多个应用共享——如何互不干扰？靠 **Namespace（命名空间）**与**配额（Quota）**。

**Namespace**：集群内的**逻辑分区**，把对象（Pod、Service、Deployment）按命名空间隔离。`kube-system` 放系统组件，`prod`、`dev` 分别放不同环境。对象的名字只需在**同一 Namespace 内唯一**——两个环境可以用同名 Service 而互不冲突。<span class="marginnote">Namespace 是「集群内的多租户」——与云上 VPC（《云网络》）是「云内的多租户」同一个思想在不同层级的表现：<strong>大共享空间里，用逻辑边界切出独立小空间</strong>。理解「逻辑隔离」这条主线，从 Hypervisor 的 VM 到云 VPC 到 K8s Namespace 就串起来了。</span>

**资源配额（ResourceQuota）**：给每个 Namespace 设**资源上限**——这个团队最多能用多少 CPU、多少内存、多少个 Pod。配额的目的是**防止一个团队吃光整个集群**，这与云上「账户配额」（《云计算的体系架构》里管理层的配额检查）是同一个防护逻辑。

**LimitRange**：再进一步，给 Namespace 内**每个容器**设默认的资源请求/限制——防止某个 Pod 声明超大的资源挤占他人。

**辨析｜易错点：** Namespace 提供的是「逻辑隔离」，不是「安全隔离」——两个 Namespace 的 Pod 依然共享内核与网络（除非配网络策略）。把 Namespace 当「安全边界」用是误解；它管的是「组织与资源」，安全隔离要另配 NetworkPolicy。<span class="marginnote">生产实践里「一个环境一个 Namespace、每个 Namespace 有配额与预算」是标准姿势——它让集群资源可归属、可限制、可审计。这也呼应了《云成本优化（FinOps）》的标签思想：<strong>资源要能归属到团队，才谈得上管理与优化</strong>。</span>

## 7 托管还是自建：K8s 的两种用法

理解 K8s 架构后，落地时的第一个选择是「**自建 K8s 还是用托管 K8s**」——这决定你要不要养控制面。

**自建 K8s（如 kubeadm 部署）**：自己部署控制面（etcd、API server、scheduler、controller-manager）、自己管升级与备份。**控制权最大、自由度高**，但运维负担重：etcd 要备份、控制面要高可用、版本要升级、证书要续期——每个都是运维大坑。

**托管 K8s（如 AWS EKS、阿里云 ACK、华为云 CCE）**：云厂商代管控制面——etcd、API server、scheduler 全部由云负责高可用与升级，你只管**工作节点与工作负载**。控制权少一些（无法改控制面组件），但运维负担骤降。

| 维度 | 自建 K8s | 托管 K8s |
| --- | --- | --- |
| 控制面运维 | 自己扛 | 云厂商管 |
| 升级 | 手动、有风险 | 云托管、可灰度 |
| 控制权 | 全 | 工作负载层 |
| 适用 | 特殊定制、离线 | 绝大多数生产 |

**辨析｜易错点：** 托管 K8s 不等于「全托管」——**节点池、工作负载、网络策略、安全加固仍是你的责任**（共享责任模型的又一次体现）。「用了托管 K8s 就什么都不管」是误解；它只是把「控制面」这一段外包，其余照旧。<span class="marginnote">这也解释了为什么云厂商的托管 K8s 如此受欢迎：<strong>它把 K8s 最「重」、最不产生业务价值的部分（控制面运维）外包出去，留下你真正关心的部分（工作负载）</strong>。与托管数据库（RDS）、托管消息队列是同一个「外包非核心运维」逻辑——本专题的「托管化」主线在这里第三次出现。</span>

## 8 小结

- **Kubernetes**：容器编排平台，核心哲学是**声明式**——你声明期望状态，系统持续收敛。
- 架构两分：**控制面**（etcd、API server、scheduler、controller-manager）与**工作节点**（kubelet、kube-proxy、容器运行时）。
- `etcd` 用 Raft 共识存集群状态，是「唯一事实源」。
- 三大核心对象：**Pod**（调度最小单元）、**Deployment**（副本+更新）、**Service**（稳定访问入口）。
- 分工口诀：控制面决定、节点执行回报、对象描述期望。

- 架构与对象的关系总结：**控制面与工作节点是「骨架」，Pod/Deployment/Service 是「血肉」**——骨架决定「谁管谁」，血肉决定「管什么」；下一篇把血肉拼装成一次真实部署。

- 核心记忆点：**控制面决定、节点执行回报、对象描述期望**——「谁管谁、管什么」一句话说清 K8s。
- 自查练习：**说清「控制器」与「调度器」的分工**——控制器管「数量」，调度器管「位置」，一前一后。
