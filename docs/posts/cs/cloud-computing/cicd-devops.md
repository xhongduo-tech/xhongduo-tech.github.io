## 为什么从 CI/CD 与 DevOps 开始

IaC 让基础设施变自动化，这一篇把「变更到上线」的整条链路也自动化。**DevOps** 是打破开发（Dev）与运维（Ops）壁垒的文化与工具链，**CI/CD** 是它的核心工程实现：**持续集成**（每次提交都自动验证）、**持续交付/部署**（验证通过就自动上线）。理解这条流水线，你就理解了现代软件「一天发布几十次」是怎么做到的。

先给一个反常识：**CI/CD 的价值不在「快」，而在「稳」**——因为自动化让每次变更都走同样的质量关卡，风险被摊薄到每次小改动里。手动发布是「把风险攒到一次大爆炸」，流水线发布是「把风险切成很多小份逐个消化」。快只是结果，稳才是原因。

## 1 DevOps：文化先行，工具落地

**DevOps**：一种软件开发方法论与文化，强调开发、运维、质量团队**紧密协作**，通过自动化把「从代码到上线」的周期缩到最短，并让整个过程**可重复、可度量**。

DevOps 的转变来自传统模式的痛点：开发写代码「扔过墙」，运维负责部署、疲于应付——上线慢、责任互相推诿、环境不一致（「在我这能跑」）。DevOps 的核心破局是三个「一起」：**一起定标准、一起担责任、一起用工具**。而工具链的骨架，就是 CI/CD 流水线。<span class="marginnote">DevOps 不是某个工具，而是「<strong>协作方式 + 自动化</strong>」的组合。衡量它成效的经典指标是 <strong>DORA 四项</strong>：部署频率、变更前置时间、变更失败率、恢复服务时间。四者齐看才完整——「每天上线」不如「每天上线还不炸」。</span>

## 2 CI：持续集成

**持续集成（Continuous Integration，CI）**：每当开发者把代码**合并到主干**，自动触发构建与测试，尽早发现集成问题。核心价值是「**早发现、早修复**」：把「集成的痛苦」从项目后期（几十个分支合到一起爆炸）提前到每次小提交。

CI 的典型流水线阶段：

1. **检出代码**：从 git 拉取最新提交。
2. **构建**：编译、打包、生成制品（artifact）。
3. **测试**：跑单元测试、静态检查、代码规范。
4. **报告**：失败立即通知提交者，阻断合并。

CI 的黄金规则：**主干保持绿色**——任何破坏主干的提交都必须立刻修复，否则「红色」会传染给所有人。<span class="marginnote">CI 背后的思想是「<strong>频繁的集成比迟来的完美更安全</strong>」：每次小改动都验证，问题就停留在「上一次改动」的小范围内，排障范围被压缩到最小。这与你学过的「分治」思想暗合——把验证切碎，故障就能被快速定位。</span>

## 3 CD：持续交付与持续部署

**持续交付（Continuous Delivery）**：CI 通过后，制品自动进入「随时可发布」状态——发布到预发布环境验证，但**上线到生产仍需人工审批**。**持续部署（Continuous Deployment）**：更进一步，验证通过就**自动上线生产**，全程无人干预。

两者的区别就在「最后一步是否要人点按钮」：

| 阶段 | 动作 | 是否人工 |
| --- | --- | --- |
| 持续集成 CI | 构建 + 测试 | 自动 |
| 持续交付 CD | 制品就绪 + 预发布验证 | 生产发布需审批 |
| 持续部署 CD | 生产发布也自动化 | 全自动 |

**安全网是 CD 的前提**：敢自动上线，是因为有完善的自动化测试、灰度发布、监控告警与一键回滚兜底。**没有安全网的持续部署，是拿生产做赌注**。<span class="marginnote">发布策略是 CD 的技术细节：<strong>蓝绿发布</strong>（新旧两套环境瞬间切换）、<strong>金丝雀发布</strong>（先放 1% 流量观察再全量）、<strong>滚动发布</strong>（逐批替换）。配合《可观测性》的指标与追踪，CD 才能在出问题时快速发现并回滚。</span>

## 4 核心要点对比：一条完整的交付流水线

| 阶段 | 输入 | 输出 | 质量关卡 |
| --- | --- | --- | --- |
| 提交代码 | 代码变更 | git 提交 | 无 |
| CI 构建测试 | 提交 | 制品 + 测试报告 | 测试全绿 |
| 镜像构建 | 制品 | 容器镜像 | 扫描漏洞 |
| 预发布部署 | 镜像 | 预发布环境 | 集成测试、冒烟 |
| 生产发布 | 镜像 | 生产环境 | 审批/自动 + 灰度 |
| 监控反馈 | 线上指标 | 反馈报告 | 告警、回滚判断 |

这条流水线把「上线」从「一个月一次的仪式」变成「一天几十次的日常」——每次变更都经过同样的质量关卡，风险被均匀分散到每次小改动中。<span class="marginnote">流水线的自动化工具遍地开花：GitHub Actions、GitLab CI、Jenkins、阿里云效。选择不重要，<strong>重要的是把「手动重复」一个个消灭</strong>——每个还需要人手工执行的环节，都是下一次事故的候选点。IaC（上一篇）正是让「部署环境」也进入流水线的关键。</span>

## 5 从手动到流水线：一次部署的自动化蜕变

把「部署一次」的两种版本并排看，CI/CD 的价值会非常具体。假设一个团队要发布「用户中心」的新版本。

**手动时代的发布（典型的周五下午）**：

1. 开发写完代码，打包成 war 包，发到群里「谁能帮忙部署一下」。
2. 运维下载包，登服务器，停服务，替换文件，重启。
3. 手工跑几条 SQL 更新数据库。
4. 出问题：回滚？手动恢复旧包 + 旧数据。谁改了什么？聊天记录里翻。
5. 整个流程 2 小时，还容易出错。

**流水线时代的发布（同一件事）**：

1. 代码 push 到主干 → CI 自动构建、跑全部测试 → 构建镜像。
2. 镜像推送、扫漏洞 → CD 自动部署到预发布 → 自动跑冒烟测试。
3. 人工在 CI 界面点「批准发布」→ 金丝雀 1% 流量 → 观察指标 → 自动全量。
4. 出问题：点「回滚」，CD 自动切回上一版本镜像——2 分钟。
5. 谁改了什么：git 提交记录 + 流水线日志，全程留痕。

| 维度 | 手动发布 | 流水线发布 |
| --- | --- | --- |
| 时长 | 小时级 | 分钟级 |
| 出错概率 | 高（靠人） | 低（靠自动化） |
| 回滚 | 手忙脚乱 | 一键执行 |
| 可追溯 | 无 | 全留痕 |

**辨析｜易错点：** 流水线不是「把命令写进脚本」就叫 CI/CD——**质量关卡**（测试、扫描、审批、灰度）才是流水线的灵魂。没有关卡、把脚本串联起来的「伪流水线」，只是把手动操作自动化了，该出的错一个不少。<span class="marginnote">「流水线的价值在关卡，不在自动化」——自动化负责「快」，关卡负责「稳」。一个经典的比例感：<strong>流水线 80% 的时间花在「验证」上，只有 20% 花在「部署」上</strong>。测试越充分，线上越安心，发布越频繁。</span>

## 6 GitOps：让 Git 成为唯一的「事实源」

CI/CD 自动化了「构建与部署」，但还留着一个问题：**谁来决定集群的期望状态**？GitOps 给出答案——**Git 仓库就是唯一的真相**。

**GitOps**：把「集群的期望状态」（部署什么、几个副本、什么配置）写成声明式配置（YAML），**存进 Git**。一个「调谐器」（如 Argo CD、Flux）持续监视 Git 与集群：

1. Git 有变更（比如改了副本数）→ 调谐器把变更同步到集群。
2. 集群漂移了（有人手动改了集群）→ 调谐器把它**拉回 Git 声明的状态**。

**GitOps 与 CI/CD 的分工**：CI 负责「构建镜像、跑测试、推镜像」；GitOps 的调谐器负责「把 Git 里的期望状态应用到集群」。发布 = **改 Git + 合并 PR**——版本管理、代码评审、回滚（revert Git）全部复用代码工程的标准动作。<span class="marginnote">GitOps 的深层价值是「<strong>把运维变成 git 操作</strong>」：任何变更都有 PR 评审、有历史记录、可一键 revert——运维过程第一次获得了与代码同等的「可审查性」。这与《基础设施即代码》一脉相承：<strong>先是基础设施是代码，然后是集群状态是代码，最终一切声明都可版本化</strong>。</span>

**辨析｜易错点：** GitOps ≠ 「用 git 管文件」。GitOps 的核心是「**以 Git 为事实源 + 持续调谐**」——没有「调谐器把漂移拉回来」这一环，只是「用 git 存 YAML」，不是 GitOps。判据很简单：**你手动改了集群，它会不会被自动纠正？** 会，才是 GitOps。

## 7 小结

- **DevOps**：打破开发运维壁垒的文化 + 自动化工具链，用 DORA 四指标衡量成效。
- **CI**：每次提交自动构建测试，主干保持绿色，**早发现早修复**。
- **CD**：持续交付（人工审批上线）→ 持续部署（全自动上线）。
- 发布策略：**蓝绿、金丝雀、滚动**；安全网（测试/监控/回滚）是 CD 的前提。
- 流水线的本质：把「从代码到上线」的每个手动环节消灭，让发布变成日常。

- DevOps 的终极目标：**把「上线」从「仪式」变成「日常」**——当发布像喝水一样平常，团队就能把精力从「怎么发」转移到「做什么」；这正是《云原生概念与 12 要素》所定义的应用，在交付环节的必然要求。
