## 为什么从 CDN 开始

负载均衡让「多台服务器」像一个入口，CDN 则更进一步：把**内容本身**复制到离用户最近的地方。你在北京访问一个部署在硅谷的网站，为什么很多资源却是「秒开」？因为 CDN 在离你最近的边缘节点就把它缓存好了。理解 CDN 的三个机制——**缓存、就近调度、回源**——你就明白了现代互联网「快」的秘诀，也理解了云厂商的边缘产品线（CloudFront、阿里云 CDN）。

先给一个朴素原理：**网络请求的快慢，第一决定因素是「距离」**——光在光纤里跑 1 万公里要 50 毫秒，来回就是 100 毫秒以上。CDN 的整个设计，本质上都在回答一个问题：**怎么把内容搬到离用户足够近，让「距离」不再是瓶颈**。

## 1 CDN 是什么：内容搬到用户家门口

**CDN（Content Delivery Network，内容分发网络）**：在全球/全国部署大量**边缘节点（edge node）**，把源站（origin）的内容**缓存**到这些节点上，让用户从**离自己最近的节点**获取内容，而不是每次都长途跋涉回源站。

它解决的问题本质上是**物理距离**：光速是恒定的，北京到硅谷的往返时延约 150 毫秒，而北京到同城的边缘节点可能只要 10 毫秒——对图片、视频、网页静态资源而言，这个差距就是「卡」与「顺」的区别。CDN 不做计算，只做「把热内容搬到离用户近的地方」这一件事。<span class="marginnote">CDN 的适用对象几乎全是<strong>读多写少、可缓存</strong>的内容：图片、视频、JS/CSS、静态页面、软件安装包。动态接口（个性化数据）无法缓存，通常仍直连源站——所以一个网站的架构常常是「<strong>动态走源站、静态走 CDN</strong>」。</span>

## 2 核心机制：缓存、TTL 与回源

CDN 的工作闭环由三个机制构成：

1. **缓存（caching）**：边缘节点把源站内容复制一份存到本地。缓存的内容带 **TTL（存活时间）**，到期后失效。
2. **命中与回源（origin fetch）**：用户请求到达边缘节点——**缓存命中**就直接返回（极快）；**缓存未命中**（没缓存或已过期）才向源站「回源」取内容，取到后缓存并返回。
3. **刷新与预热**：源站内容更新后，可主动让 CDN「刷新」（清掉旧缓存）或「预热」（提前把新内容推到边缘）。

**缓存命中率**是 CDN 的核心指标——命中率越高，回源越少，用户体验越好、源站压力越小。<span class="marginnote">TTL 是缓存一致性的「粗糙开关」：TTL 太短 → 频繁回源，省不了多少；TTL 太长 → 用户看到旧内容。对<strong>静态资源</strong>（文件名带版本号 `app.js?v=123`）可以设长 TTL，内容更新时改 URL 强制回源——这是前端工程的标准做法，也呼应了《对象存储》里「一次写入、整体替换」的思维。</span>

## 3 就近调度：DNS 与 GSLB

用户请求如何被引导到「最近的节点」？靠**全局负载均衡（GSLB）**，通常基于 **DNS 调度**：用户解析域名时，CDN 的 DNS 服务根据用户的地理位置与网络状况，返回**最优边缘节点**的 IP。同一域名在不同地区会解析出不同 IP——这正是「就近」的落地机制。

更精细的调度会综合**网络延迟、节点负载、链路质量**做实时决策：北京的联通用户可能被分到联通线路的边缘节点，四川的用户被分到成都节点——这就是「智能调度」。<span class="marginnote">CDN 调度用的是「<strong>谁离你近、谁网络好，就把你指给谁</strong>」——这与第三级《计算机网络》里 DNS 的迭代查询一脉相承，只是决策从「权威服务器」转移到了「智能调度系统」。如今 Anycast（多节点共享一个 IP）也让调度的粒度更细。</span>

## 4 核心要点对比：CDN 缓存 vs 源站直连

| 维度 | 直连源站 | CDN 分发 |
| --- | --- | --- |
| 访问时延 | 取决于源站距离 | 取决于最近边缘节点 |
| 源站压力 | 全部请求都打到源站 | 大部分在边缘消化 |
| 抗突发 | 差（易被打爆） | 强（边缘分布式承接） |
| 内容一致性 | 天然最新 | 受 TTL 影响 |
| 成本 | 源站带宽费高 | CDN 流量费 + 更低回源 |

**辨析｜易错点：** CDN 不是「加速器」，而是「缓存分发器」——它对**动态、个性化内容几乎无效**。把登录后的个人数据塞进 CDN 缓存，会酿成「A 用户看到 B 用户数据」的严重事故。正确边界：**公开的、可缓存的静态内容交给 CDN；私有的、实时的动态内容留在源站**。<span class="marginnote">CDN 还有一个常被忽视的价值：<strong>安全</strong>。它分布式的边缘节点天然能<strong>吸收 DDoS 流量</strong>——攻击请求在边缘就被拦住，打不到源站。现代 CDN 普遍内置 WAF 与 DDoS 防护，成为网站安全的第一道防线，这与第四篇《云安全与合规》直接衔接。</span>

## 5 动态内容与边缘计算：CDN 的下半场

CDN 最初只服务静态内容，但「边缘」的价值远不止缓存。两条演进路径值得注意：

**动态加速（dynamic acceleration）**：对无法缓存的动态 API，CDN 通过**智能路由**选一条网络质量最好的链路回源（避开拥塞的公网路径），配合 TCP 优化、连接复用，把「动态请求」也提速——虽然不能缓存，但能让「回源的路」更快更稳。这解决了「静态走 CDN、动态走源站」模型里动态部分体验差的问题。

**边缘计算（edge computing）**：更进一步，CDN 节点不再只是「读缓存」，而是**能跑代码**——边缘函数（如 CloudFront Functions、阿里云边缘函数）在离用户最近的节点上执行逻辑：改写请求、鉴权、A/B 分流、图片实时处理。数据不用回源站，在边缘就处理完。

| 能力 | 缓存（传统 CDN） | 动态加速 | 边缘计算 |
| --- | --- | --- | --- |
| 对象 | 静态内容 | 动态请求 | 计算逻辑 |
| 位置 | 边缘节点 | 边缘智能回源 | 边缘执行 |
| 价值 | 省流量、降延迟 | 优化回源路径 | 就近计算 |

**辨析｜易错点：** 边缘计算 ≠ 替换后端。边缘函数适合**轻量、无状态、与请求强相关**的逻辑（鉴权、改写、灰度）；重计算、有状态、需要访问核心数据库的业务，仍应放在中心后端。把「数据库查询」塞进边缘函数，只会把「分布式系统的复杂度」挪到边缘——这不是边缘计算的正确用法。<span class="marginnote">边缘计算与《函数即服务（FaaS）》同构：都是「按需运行的函数」，只是运行位置从「中心云」移到了「边缘节点」。可以理解成<strong>FaaS 的地理分布版</strong>——同一个函数，中心跑就是 FaaS，边缘跑就是边缘函数。云厂商的边缘产品线，正是把无服务器的思想推向离用户更近的地方。</span>

## 6 回源与缓存一致性：CDN 的「翻新」艺术

CDN 的缓存一旦过期或不一致，用户就会看到「旧内容」。管理缓存一致性，是 CDN 运维的核心手艺。三种手段：

| 手段 | 做法 | 适用 |
| --- | --- | --- |
| **TTL 过期** | 缓存自然到期后重新回源 | 内容更新不频繁 |
| **主动刷新（purge）** | 手动/API 清掉指定 key 的缓存 | 紧急更新（如改了价格） |
| **版本化 URL** | 文件名带版本号，新版本新 URL | 静态资源发布 |

**回源策略的几个关键设计**：

- **源站保护（origin shield）**：让边缘节点**统一从一个「上层节点」回源**，而不是每个边缘节点都直接打源站——把「N 个边缘的零星回源」聚合成「1 个上层的集中回源」，源站压力骤降。
- **回源失败兜底**：源站临时故障时，边缘节点应**继续服务「稍旧的缓存」**（stale-while-revalidate），而不是返回错误——「宁可给旧的，不可给错的」。

**辨析｜易错点：** 缓存一致性没有银弹，关键是「**分清楚哪些内容更新敏感**」：

- **静态资源**（图片、JS/CSS）：版本化 URL + 长 TTL，几乎不用管。
- **半静态**（新闻页、商品详情）：短 TTL（几分钟）或主动刷新。
- **动态**（购物车、个人中心）：**不上 CDN**，直接回源。

把「内容更新频率」和「缓存策略」对应起来，就不会出现「改了商品价格用户却看到旧价」的事故。<span class="marginnote">「版本化 URL + 长 TTL」与「主动刷新」是两种互补哲学：前者「<strong>换新钥匙开新锁</strong>」（新 URL 强制回源），后者「<strong>砸旧锁换新锁</strong>」（清缓存强制回源）。生产实践通常两者混用——发布走版本化，紧急修复走刷新。理解这套，CDN 的一致性就不难管了。</span>

## 7 HTTPS 与 CDN 的配合：证书放在哪

静态内容走 CDN 后，**HTTPS 证书**的部署位置成为一个常见问题——证书放在源站还是 CDN？

**证书放在 CDN（标准做法）**：CDN 边缘节点持有证书并终止 TLS——用户与 CDN 之间是 HTTPS（安全），CDN 与源站之间可以走 HTTPS 也可以走内部网络。好处：**用户看到的是「CDN 的证书 + CDN 的 IP」**，源站 IP 被隐藏（安全）、TLS 握手在边缘完成（快）。

**证书放在源站**：CDN 只做转发、不解密——适合「内容必须端到端加密、CDN 不可见明文」的合规场景，但边缘缓存就无法基于内容做处理。

| 做法 | 谁终止 TLS | 优势 | 代价 |
| --- | --- | --- | --- |
| 证书在 CDN | 边缘节点 | 隐藏源站、握手快 | CDN 可见明文 |
| 证书在源站 | 源站 | 端到端加密 | 边缘难处理内容 |

**辨析｜易错点：** 「证书放在 CDN 就意味着 CDN 能看到你的数据」——对普通静态内容这不是问题（本来就公开），但**敏感数据（如个人页面）必须评估**。标准做法是「**公开内容证书放 CDN、私密内容走端到端**」，二者按内容类型分流，而不是一刀切。

## 8 小结

- **CDN**：把源站内容缓存到边缘节点，让用户就近获取，解决**物理距离**问题。
- 三机制闭环：**缓存（带 TTL）→ 未命中回源 → 命中直返**；命中率是核心指标。
- **就近调度**靠 DNS/GSLB：按地理位置与网络状况返回最优边缘节点。
- 适用边界：**静态可缓存内容走 CDN，动态个性化内容留源站**。
- CDN 兼有安全价值：边缘节点天然吸收 DDoS，内置 WAF。

- CDN 与 LB 的分工：**LB 负责「把请求分给后端」，CDN 负责「把内容搬到离用户近的地方」**——一个管访问分配、一个管内容就近，两者常搭配构建高性能入口。
