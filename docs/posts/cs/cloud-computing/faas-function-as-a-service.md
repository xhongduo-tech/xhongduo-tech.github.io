## 为什么从 FaaS 开始

第四篇讲无服务器与云原生，第一个登场的是一朵「最颠覆」的云：**FaaS**。前面三篇无论虚拟机还是容器，你都得「租一台机器、把应用放上去跑」；FaaS 把这个前提也取消了——**你只写一个函数，平台负责在请求到来时把它跑起来**。这是云抽象阶梯的顶点，也是「按量付费」最极致的形态。理解 FaaS，你就理解了 Serverless 的全部起点。

先给一个直觉：FaaS 把「运行单元」从「机器」缩小到了「函数」——这是云计算一路「抽象阶梯」的顶点。回看整条线：物理机 → 虚拟机 → 容器 → 函数，**每一级都更小、更轻、更按需**。FaaS 是这条线「抽象到极致」的形态：连「常驻」都不需要了，有请求才醒来。

## 1 FaaS：只写函数，不碰服务器

**FaaS（Function as a Service，函数即服务）**：一种事件驱动的计算服务，开发者上传**单个函数**（一段代码 + 运行时），平台在**事件触发**时自动执行它，用完即销毁，按**执行次数与时长**计费。代表产品：AWS Lambda、阿里云函数计算 FC、Azure Functions。

FaaS 与容器/虚拟机的本质区别：

- **没有常驻进程**：容器与虚拟机是「一直运行的机器」，FaaS 是「被调用时才醒来的函数」。空闲时不占资源、不花钱。
- **看不到服务器**：连「容器」这个单位都省了——平台管理运行时，你只写业务逻辑。
- **自动伸缩到极致**：平台根据并发请求自动拉起函数实例，从 0 到十万并发都是平台的事。

**一次调用的生命周期**：用户请求 → 触发事件 → 平台按需创建执行环境 → 运行你的函数 → 返回结果 → 环境回收。<span class="marginnote">FaaS 的「按需运行、用完即毁」把云计算「按用量付费」推向了极端：你没有预订任何资源，只有真实调用发生时才产生费用。这在<strong>流量极不均匀</strong>的场景（定时任务、偶发请求、处理消息）里省钱效果惊人——平时几乎零成本。</span>

## 2 冷启动：无服务器的代价

FaaS 最大的软肋是**冷启动（cold start）**：平台为执行函数需要准备运行环境（拉镜像、初始化运行时、加载代码），这段准备时间会加在请求延迟上。冷启动时间从几十毫秒到几秒不等，取决于语言与运行时大小。

为了缓解冷启动，平台维护**暖实例池（warm pool）**：预先初始化好一批环境，请求到来时直接复用。但长时间空闲或突发流量仍会触发冷启动。**对延迟敏感的用户请求（如在线支付回调），冷启动是必须考虑的因素**；对异步任务（如处理消息、生成报表），冷启动无感。<span class="marginnote">冷启动是 FaaS 与「常驻容器」之间的经典权衡：<strong>省了空闲成本，付了启动延迟</strong>。业界应对有「预留并发」（预置实例）与「函数常驻」等折中方案——把 FaaS 的按需性与关键路径的低延迟调和起来。Java/Python 的冷启动通常比 Node.js 慢，选语言也是优化项之一。</span>

## 3 公式解析：FaaS 的计费模型

FaaS 计费是云上最「透明」的模型，可以写成一个公式：

$$
\text{费用} = \sum_{\text{每次调用}} \big(\text{执行次数单价} + \text{运行时长} \times \text{配置内存} \times \text{单价} \big)
$$

逐步拆解：

- **执行次数单价**：每万次调用收固定的「次数费」，与你是否空闲无关，只与调用量相关。
- **运行时长 × 配置内存**：按「函数实际执行了多少秒」计费，且与配置的内存规格成正比——内存配得越大、执行越久，费用越高。
- **注意「运行时长的粒度」**：计费按**实际执行时间**（往往精确到 1 ms 的倍率），函数不运行就不计费——这是 FaaS 与「包月租机」的根本差异。

**辨析｜易错点：** FaaS 计费里最反直觉的是「**配置内存 × 运行时长**」：你配置 2 GB 内存，即使函数只用了 100 MB，也按 2 GB 计费。因此**内存配得恰到好处**（既满足需要、又不虚高）是 FaaS 成本优化的关键杠杆——这与第四篇《云成本优化（FinOps）》一脉相承。<span class="marginnote">一个常见的成本误区是「FaaS 一定比虚拟机便宜」。对<strong>持续高并发</strong>的负载，FaaS 的单次调用价格累计起来可能远超一台常驻实例；FaaS 真正的省钱场景是<strong>低频、突发、不均匀</strong>的负载。选型不是「FaaS 取代一切」，而是「负载形态决定计算形态」。</span>

## 4 核心要点对比：FaaS vs 容器 vs 虚拟机

| 维度 | 虚拟机 | 容器 | FaaS |
| --- | --- | --- | --- |
| 运行单元 | 完整 OS | 应用进程 | 单个函数 |
| 常驻性 | 常驻 | 常驻/可伸缩 | 按需唤醒 |
| 伸缩粒度 | 实例级 | 副本级 | 函数级（极细） |
| 计费 | 按小时 | 按容器运行时长 | 按调用次数+时长 |
| 空闲成本 | 照付 | 照付 | 零 |
| 冷启动 | 无（常驻） | 秒级 | 毫秒~秒级 |
| 适用 | 长生命周期服务 | 微服务 | 事件驱动、低频突发 |

**选型逻辑一目了然**：**一直要跑的服务**用容器或虚拟机；**来了才跑、跑完就走的任务**用 FaaS。现实中两者常组合——核心在线服务用容器常驻，周边事件处理（图片压缩、消息通知、定时任务）交给 FaaS。<span class="marginnote">FaaS 与微服务的边界在逐渐融合：现代 FaaS 平台已支持自定义容器镜像、支持长时运行与流式响应，「函数」与「容器」的界限越来越模糊。但<strong>心智模型仍然清晰</strong>：FaaS 强调「事件驱动、按量计费」，容器强调「部署控制、常驻运行」。</span>

## 5 FaaS 的限制与适用边界

FaaS 不是万能钥匙，它有四道「硬边界」，越过任何一道都会难受：

| 限制 | 内容 | 越界后果 |
| --- | --- | --- |
| **冷启动延迟** | 突发时新实例要初始化 | 用户请求变慢 |
| **执行时长上限** | 单次运行有超时（如 5–15 分钟） | 长任务被强制中断 |
| **无状态约束** | 函数不该保存本地状态 | 状态丢失、结果错误 |
| **平台锁定** | 事件源与运行时绑定平台 | 迁移成本高 |

**适用边界一句话**：FaaS 擅长「**事件驱动、短时、无状态、负载不均匀**」的工作——图片处理、消息通知、定时任务、API 后端、Webhook。它不擅长「**长时运行、有状态、延迟极敏感、持续高负载**」的工作——那些该用容器或虚拟机。

**一个真实的错误示范**：把「数据管道里跑 2 小时的批量任务」写成 FaaS 函数，跑到一半被超时杀掉——正确做法是**拆成事件驱动的小步**（一条消息处理一条记录）或换用容器跑长任务。<span class="marginnote">无服务器并不意味着「一切皆函数」——现代最佳实践是「<strong>混合形态</strong>」：在线核心服务用 K8s 容器常驻，事件处理用 FaaS，长任务用容器 Job。选型的关键不是「哪个更先进」，而是「<strong>负载的形态决定计算形态</strong>」——这个判断原则，贯穿整个云计算专题。</span>

**辨析｜易错点：** FaaS 的「无状态」不是「不能存数据」，而是「**不能依赖本地状态**」——函数每次运行可能在不同实例上，本地文件、内存变量都不可靠。需要持久化就显式连数据库/对象存储，把状态放在函数之外。这是 FaaS 应用设计的头号纪律。

## 6 FaaS 与微服务的结合：混合形态实践

FaaS 不是微服务的替代品，而是微服务体系的「补充兵种」。成熟系统常把它们组合：

**典型组合一：API 层用 FaaS**。REST API 的每个端点是一个函数——负载不均匀的 API（大部分时间请求稀疏）用 FaaS 成本最低，请求来时自动伸缩，空闲时零成本。适合内部工具 API、管理后台、低频接口。

**典型组合二：事件处理用 FaaS**。对象存储上传 → 触发函数做图片压缩/视频转码；消息队列有消息 → 触发函数做后续处理；定时任务 → 函数每天凌晨跑一次报表。这些都是「事件驱动」的天然 FaaS 场景（见《事件驱动架构》）。

**典型组合三：K8s 常驻 + FaaS 补位**。核心在线服务用 K8s 容器常驻（稳定、可控），周边事件处理（通知、图片处理、异步任务）用 FaaS——**常驻容器保核心，按需函数接外围**。

| 负载形态 | 推荐计算形态 |
| --- | --- |
| 持续高并发 | 容器/虚拟机常驻 |
| 低频/突发/不均匀 | FaaS |
| 事件驱动处理 | FaaS |
| 长时运行任务 | 容器 Job |

**辨析｜易错点：** 别在「一个服务」里既用容器又用 FaaS 做同样的事——那只是两套部署的重复。组合的判据是**按负载形态分工**：同一功能，如果它是高频核心路径，用容器；如果是低频外围处理，用 FaaS。**「混用」的前提是「分工清楚」**。<span class="marginnote">FaaS 与容器之争的成熟结论是「<strong>都不是银弹，按负载选型</strong>」：容器赢在「可预测、可控」，FaaS 赢在「按需、省钱」。真正成熟的团队不站队，而是「<strong>给每类负载找最合适的运行形态</strong>」——这也是云计算专题反复强调的主旋律：选型看负载，不看流行。</span>

## 7 小结

- **FaaS**：只写函数，事件驱动执行，按调用次数与时长计费——云抽象的顶点。
- 与容器/虚拟机差异：**无常驻进程、看不到服务器、自动伸缩到极致**。
- **冷启动**是最大软肋，暖实例池缓解；延迟敏感场景要预留并发。
- 计费公式：**次数费 + 配置内存 × 运行时长**；内存配置是成本优化杠杆。
- 选型：常驻负载用容器、事件/突发负载用 FaaS，两者常组合。

- FaaS 的思维转变总结：**从「部署一个服务」到「写一个函数」**——你不再管理运行单元，只提供「当事件发生时执行的逻辑」，这是云计算「抽象阶梯」的顶点。

- 核心记忆点：**FaaS 的适用边界 = 事件驱动 + 短时 + 无状态 + 负载不均匀**；长时/有状态/极低延迟请用容器。
- 自查练习：**判断「数据库迁移任务」适不适合 FaaS**——长时运行 + 有状态，答案是不适合，该用容器 Job。
