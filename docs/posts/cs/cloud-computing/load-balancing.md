## 为什么从负载均衡开始

应用要扛住高并发，必然横向扩展出多台实例——但用户只敲一个域名，谁来把请求分到各台实例？这就是**负载均衡（LB）**的职责。它是云架构里「入口的单点」：所有流量先到 LB，再被分发到后端。理解 LB，你就掌握了高可用架构的第一块基石。它也是 K8s 里 Service 的 LoadBalancer 类型、以及 CDN 边缘节点背后的共同机制。

## 1 为什么需要负载均衡

单台服务器的处理能力有限（CPU、内存、连接数都有上限），扛不住海量请求。解法是横向扩容：部署 N 台相同实例。但这样带来两个问题：**用户访问谁**？**某台挂了怎么办**？

负载均衡在这两者之间充当「调度中心」：

- **分发流量**：按策略把请求分给各实例，避免某一台过载。
- **屏蔽故障**：定期健康检查，把挂掉的实例从转发列表中摘除，请求只发给活着的实例。
- **单一入口**：用户只面对 LB 的地址，后端实例对用户透明——想加机器、换机器都不影响用户。

**负载均衡（load balancer）**：一种将流量按策略分发到多台后端服务器、并自动剔除故障节点的网络设备或服务。<span class="marginnote">LB 让「后端实例」变成可任意替换的「资源池」——这与你学过的云弹性一脉相承：加一台实例进 LB，吞吐就上去；减一台，用户无感。LB 是「无状态横向扩展」得以成立的关键黏合剂。</span>

## 2 负载均衡的层级：L4 与 L7

按工作在 OSI 模型的层级，LB 分为两大类：

**四层负载均衡（L4，传输层）**：基于 IP 与端口转发，不解析报文内容。转发快、开销低，但不能按 URL 做细粒度分发。代表：AWS NLB、阿里云 NLB。
**七层负载均衡（L7，应用层）**：解析 HTTP/HTTPS 报文，可按 URL、域名、Header、Cookie 做智能分发，还内置 SSL 卸载、重写、限流。代表：AWS ALB、阿里云 SLB（七层）。

四层管「数据包去哪」，七层管「请求该归谁」——后者的决策能力远强于前者，但处理开销也大。<span class="marginnote">一个直观例子：四层 LB 只能把「所有到 <code>80 端口</code> 的流量」分给后端；七层 LB 可以把「`/api/*` 的请求分给 API 集群、`/static/*` 的请求分给静态集群」。微服务场景几乎必须用七层，因为路由要靠 URL 与路径决定。</span>

## 3 健康检查、会话保持与伸缩

LB 的三个「隐藏机制」决定了它的可靠性：

**健康检查（health check）**：LB 定期向后端发探测请求（如 GET <code>/health</code>），连续失败就把节点摘除，恢复后再加回。这是「自动容错」的引擎。
**会话保持（session stickiness）**：有些应用要求同一用户的请求始终打到同一台后端（如本地会话）。LB 通过 Cookie 或源 IP 哈希实现「粘性会话」。注意：这牺牲了负载均衡的均匀性。
**弹性伸缩联动**：LB 通常与自动伸缩组配合——负载升高时伸缩组加实例，LB 自动把新实例纳入转发；负载下降时缩容，LB 自动摘除。

**辨析｜易错点：** 会话保持与负载均衡**天然冲突**。开启粘性会话后，某个用户的流量始终打在同一台实例，那台实例成为单点。云原生实践是**让应用无状态**（会话存 Redis、JWT 无状态化），从而关掉粘性会话、换取真正均匀的负载——这正是《云原生概念与 12 要素》「无状态、可水平扩展」原则在 LB 场景的回响。<span class="marginnote">健康检查的路径设计有讲究：不要只探测「进程还活着」，要探测「服务真的能处理请求」——一个经典的坑是健康检查打到静态页面，进程活着但业务线程池已满，LB 仍把流量送过去，导致「LB 显示健康、用户请求超时」。</span>

## 4 核心要点对比：L4 与 L7 负载均衡

| 维度 | L4（传输层） | L7（应用层） |
| --- | --- | --- |
| 工作层级 | 传输层（IP/端口） | 应用层（HTTP/HTTPS） |
| 决策依据 | IP、端口 | URL、域名、Header、Cookie |
| 性能 | 高（不解析内容） | 中（需解析报文） |
| 功能 | 简单转发 | SSL 卸载、路径路由、限流 |
| 典型产品 | NLB | ALB、SLB 七层 |
| 适用 | 海量连接、TCP/UDP | Web 应用、微服务 |

**选型直觉**：需要极致吞吐与低延迟、不关心内容 → 四层；需要按路径/域名路由、做 SSL 卸载与精细化控制 → 七层。<span class="marginnote">现代云 LB 还支持<strong>跨可用区部署</strong>：LB 本身是多活冗余的，单可用区故障时流量自动切到其他区。加上后端实例分布在多个可用区，就构成「LB 多活 + 后端跨区」的高可用架构——这是云上「同城双活」的基本形态。</span>

## 5 负载均衡算法：把请求分给谁

LB 的「均衡」靠什么算法实现？几种经典算法各有权衡：

| 算法 | 原理 | 适用 | 局限 |
| --- | --- | --- | --- |
| **轮询（Round Robin）** | 请求轮流分给每个后端 | 后端能力相同 | 不感知负载差异 |
| **加权轮询** | 按权重分配（强的多分） | 后端规格不同 | 权重靠经验 |
| **最少连接** | 分给当前连接最少的后端 | 长连接、处理时间不均 | 需实时统计 |
| **IP 哈希** | 按源 IP 哈希固定后端 | 天然会话保持 | 负载可能不均匀 |
| **一致性哈希** | 哈希环 + 虚拟节点 | 缓存类场景 | 实现复杂 |

**辨析｜易错点：** 轮询是「看起来公平」，但对**处理时长不均匀**的请求并不公平——A 请求要 1 秒、B 请求要 10 秒，轮询会让处理慢的后端堆积。**最少连接**才是「按实际负载分」的算法。而 **IP 哈希**用「哈希固定」实现了会话保持，但代价是负载可能严重不均（某个 IP 段请求多，某台后端就超载）。<span class="marginnote">一致性哈希值得多说一句：它让「后端增减」只影响少量 key 的映射（而不是全部重排），是分布式缓存（如 Redis 集群）、分布式存储（数据分片）的经典算法——你在《分布式系统》与《数据结构》（哈希）里都会再遇到它。LB 只是它的众多应用场景之一。</span>

**算法之外，LB 还有个隐藏决策：会话保持（session stickiness）**。云原生实践倾向于**应用无状态化**（会话外置到 Redis、JWT 无状态），从而摆脱粘性会话，让 LB 真正均衡。这里的原则与《负载均衡》正文一致：**均衡的敌人是状态**——谁保留本地状态，谁就拖累均衡。

## 6 健康检查与故障演练：让「自愈」可信

负载均衡的可靠性，靠的不是「配置一次」，而是「持续验证」。两个工程实践决定了高可用是否真的成立：

**健康检查的精细设计**：

**检查什么**：不要只探「进程活着」（TCP 端口通），要探「**服务真的能干活**」——探测一个会打到数据库/业务逻辑的端点（如 GET <code>/ready</code> 内部再查一次 DB）。否则「LB 显示健康、用户请求超时」的经典事故就会发生。
**检查频率**：太快（如每秒）浪费资源、误杀慢启动；太慢（如 5 分钟）故障发现不及时。通常 5–15 秒一次、连续 2–3 次失败摘除、连续 2–3 次成功恢复。

**优雅摘除（graceful drain）**：节点要下线（维护、缩容）时，LB 应**先停止给它分新流量**，等它处理完在途请求（连接排空）再真正下线——否则「正在处理的请求」被硬切断。这个「先断新、再等旧」的顺序，是滚动发布与缩容不惊动用户的关键。

**故障演练（chaos testing）**：高可用配置最怕「**纸面高可用**」——配置了，但从没验证过。故障演练（如 Netflix 的 Chaos Monkey）**故意随机杀掉实例、整台机器**，验证系统是否真的能自愈。演练暴露的往往是「健康检查配错了」「依赖服务没有冗余」这类真实问题。<span class="marginnote">「演练过的高可用才算高可用」——这在《云安全与合规》的应急响应里同样成立：<strong>没演练过的预案，出事时大概率用不上</strong>。把「故意搞破坏」变成常规工程实践，是云原生团队与「看着配置齐全」团队的分水岭。</span>

## 7 LB 自身的高可用：别让入口变成单点

负载均衡是「入口的单点」——如果 LB 本身挂了，后端再健康也白搭。所以**LB 自己也要高可用**。云厂商的做法：

**LB 多活冗余**：云 LB（如 AWS ALB、阿里云 SLB）在可用区级别多活部署——同一 LB 在多个可用区各有实例，任一区故障，流量由其他区接管，**LB 本身不是单点**。
**跨可用区分发**：LB 可以把流量分发到多个可用区的后端实例——某区后端全挂，流量自动切到其他区。

**一张「高可用架构」的标准拼图**：

```
          用户
           │
           ▼
   ┌───────────────┐
   │  DNS（解析到 LB）│
   └───────┬───────┘
           ▼
   ┌──────────────────────────┐
   │  负载均衡（跨可用区多活）     │
   └──────┬────────────┬───────┘
          ▼            ▼
   可用区 A        可用区 B
   ├ Web 副本 ─┐    ├ Web 副本 ─┐
   ├ 应用副本  ─┤    ├ 应用副本  ─┤
   └ 数据库    ┘    └ 数据库    ┘
   每层都有健康检查，故障自动摘除
```

**辨析｜易错点：** 高可用是「**层层递进的冗余**」——DNS 解析到 LB、LB 多活、后端多副本、每层都有健康检查。任何一层是单点，整个链路就脆弱。检查自己的架构：**每一层都冗余了吗？每一层的故障都会被自动摘除吗？** 有一层答不上来，高可用就还有缺口。<span class="marginnote">这又回到《云计算的核心特征》的弹性与《云计算的体系架构》的可用区设计——<strong>高可用不是某个组件的属性，而是「从 DNS 到后端每一层都不留单点」的整体工程</strong>。云给了你工具（LB 多活、跨区部署），用不用、用得对不对，是你自己的事。</span>

## 8 小结

- LB 三大职责：**分发流量、屏蔽故障、提供单一入口**。
- 两类层级：**L4**（IP/端口，快而糙）、**L7**（URL/路径，精而慢）。
- 关键机制：**健康检查**（自动摘除故障）、**会话保持**（粘性，但牺牲均匀）、**弹性联动**。
- 云原生最优解是**无状态应用 + 关掉粘性会话**，换真正均匀的负载。
- 高可用组合：**LB 跨可用区多活 + 后端跨区部署**。

- LB 的位置感：**LB 是「入口的单点」，但不是「性能的瓶颈」**——好的 LB 自己就是多活冗余的，它把压力转发给后端，把故障隔离在自己之外。

在下一篇，我们来到云网络的最后一站——**内容分发网络（CDN）**，看离用户最近的「云」如何把内容送到家门口。如果说 LB 解决的是「多台后端怎么分流量」，CDN 解决的则是「内容怎么提前放到用户身边」——**一个是分配请求，一个是搬运内容，两者共同构成「快」的入口**。
