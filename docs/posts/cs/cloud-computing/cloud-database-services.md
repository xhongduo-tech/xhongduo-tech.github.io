## 为什么从云数据库开始

第三篇的收官之作是数据库。传统上，数据库是最难「上云」的部分——它要求低延迟、强一致、高可用，而这些都与「分布式」天然冲突。云厂商把它做成了**托管服务（RDS、PolarDB、Cloud SQL）**：你把「要什么数据库」告诉云，云把「安装、备份、高可用、扩缩容」全部代管。这一篇讲清数据库服务化的三件套与选型，同时把第三篇的存储主线收束——数据库正是建立在块存储与分布式系统之上的最高层。

数据库为什么「最难上云」值得想一下：存储只要「数据不丢」，网络只要「流量能通」，而数据库要的是「在数据不丢的基础上，还要事务正确、并发有序、查询快速」——它是**把「可靠」与「语义」叠在一起的最高层**。这也解释了为什么云数据库是托管服务里技术含量最高、也最受信任检验的一类。

## 1 从自建数据库到托管数据库

自建数据库（自己买机器、装 MySQL、配主从、做备份）要面对一整串运维难题：版本升级、打补丁、主备切换、数据备份、容量规划、故障恢复——每一项都是高风险、高成本的操作。**托管数据库服务（managed database service）** 把这一切打包成「服务」：

- 你声明：**引擎**（MySQL/PostgreSQL/Oracle 等）、**规格**（几核几 G）、**容量**（多少 GB）。
- 云代管：**高可用主备、自动备份、监控告警、一键扩缩容、自动故障切换**。

托管数据库把「数据工程」外包给平台，让应用团队聚焦业务。它本质上是 PaaS 在数据库领域的落地——你只管 schema 与 SQL，平台管一切运行细节。<span class="marginnote">「数据库即服务」（DBaaS）是 PaaS 的一个特例：把<strong>责任链切到数据库之上</strong>——云管到引擎、你管到 schema。你在《云服务模型》里学的「共享责任模型」在这里的具体化：云保证「数据不丢、服务可用」，你负责「数据模型正确、访问权限合理」。</span>

## 2 数据库服务化的三件套

托管数据库最核心的三个能力，正是自建最痛苦的三件事：

| 能力 | 自建时要做什么 | 托管后云做什么 |
| --- | --- | --- |
| **高可用（主备）** | 自己搭主从、写切换脚本 | 自动主备 + 秒级故障切换 |
| **备份与恢复** | 自己写 cron、定期全量+增量 | 自动快照 + 时间点恢复（PITR） |
| **扩缩容** | 停机换大机器、迁移数据 | 在线变配，分钟级生效 |

**核心机制**：云数据库的高可用通常基于**主备复制**——主实例提供读写，备实例实时同步（半同步/异步），主实例故障时自动提升备实例为新主（通常几十秒内完成）。备份则靠**快照 + 二进制日志**：快照提供「某时刻全量」，日志提供「此后所有增量」，两者结合可实现**时间点恢复**——把数据库恢复到过去任意一分钟的状态。<span class="marginnote">「快照 + 日志 = 任意时间点恢复」是数据库备份的黄金组合，与《块存储与文件存储》里的快照、以及分布式系统的「状态机复制」思想完全同构：<strong>全量快照打底、增量日志续上</strong>。这也是金融系统「误删数据可回滚」的技术根基。</span>

## 3 NoSQL 与云原生数据库

关系型数据库解决「事务与强一致」，但面对超大规模并发与灵活结构时力不从心，云上因此长出了两条新路线：

**NoSQL 数据库**：放弃（或弱化）事务与 SQL，换取**水平扩展**与**低延迟**。代表：AWS DynamoDB、阿里云 Tair（兼容 Redis）、MongoDB 托管。典型场景：会话、缓存、订单流水、物联网数据。
**云原生数据库**：为云而生的新一代关系型数据库，用分布式存储 + 计算分离重构 MySQL/PostgreSQL。代表：AWS Aurora、阿里云 PolarDB。它们把「计算节点与存储集群分离」，存储自动多副本、计算可独立扩缩，兼容 MySQL 协议，性能远超传统单机数据库。

**辨析｜易错点：** 「云原生数据库」不是「装在云上的 MySQL」，而是**存储计算分离的分布式架构**。传统 MySQL 的数据在本地磁盘，Aurora 的数据在分布式存储层（自动 3 副本）——写入先落存储层多个副本才确认，单机故障不丢数据。它保留了 SQL 与事务，却获得了 NoSQL 式的扩展性，是当前关系型数据库在云上的主流方向。<span class="marginnote">Aurora 的存储计算分离，本质是把你学的两块知识焊在一起：<strong>分布式文件系统</strong>（多副本存储层）+ <strong>关系型数据库</strong>（SQL 引擎）。底层存储负责可靠，上层引擎负责语义——「存储与计算解耦」是云数据库最重要的架构趋势。</span>

## 4 核心要点对比：三种数据库形态

| 维度 | 自建数据库 | 托管 RDS | 云原生/Serverless 数据库 |
| --- | --- | --- | --- |
| 运维成本 | 最高 | 中 | 低 |
| 高可用 | 自己搭 | 自动主备 | 存储层自动多副本 |
| 扩展性 | 垂直为主 | 垂直 + 只读副本 | 存储与计算独立扩展 |
| 一致性 | 完全自控 | 引擎保证 | 引擎保证 |
| 典型产品 | 自己装的 MySQL | RDS、云数据库 | Aurora、PolarDB |

**选型直觉**：小规模、要省钱、团队有 DBA → 自建或托管 RDS；核心业务、要极致的可靠与弹性 → 云原生数据库；海量 KV 或灵活结构 → NoSQL。<span class="marginnote">云数据库的下一步是 <strong>Serverless 数据库</strong>：不预购规格，按实际用量计费、秒级伸缩到 0——数据库也加入了「无服务器」阵营。这与第四篇《函数即服务》的无服务器思想同源：<strong>从「预订资源」到「按量即用」</strong>，把云的弹性延伸到数据层。</span>

## 5 迁移上云：从自建到托管的路径

「托管数据库很香，但我的数据在自建库里，怎么过去？」数据库迁移是上云最高风险的操作之一，常见三种路径：

| 迁移方式 | 做法 | 停机时间 | 适用 |
| --- | --- | --- | --- |
| **全量导出导入** | dump 导出 + 导入 | 长（数小时） | 数据量小、可停机 |
| **数据迁移服务（DMS）** | 全量 + 增量实时同步 | 短（分钟级） | 在线迁移、减少停机 |
| **双写 + 切换** | 新旧库同时写，校验后切流量 | 零（灰度切） | 核心系统、零容忍停机 |

**关键机制：增量同步**。任何「零停机迁移」都依赖**日志复制**——新库从旧库的 binlog/WAL 连续消费增量变更，让新旧数据保持一致，直到切换时刻。<span class="marginnote">增量同步用的「日志」正是《分布式文件系统》《云数据库》里反复出现的「<strong>快照 + 日志 = 时间点一致</strong>」思想：全量快照打底，日志续上增量。数据库迁移 = 一次「从头到尾」的复制 + 持续「追日志」的同步——理解这套，就看懂了 DMS 这类工具的设计。</span>

**迁移的黄金顺序**：

1. **小流量试点**：先迁一个非核心库，走通流程、摸清坑。
2. **全量 + 增量**：用 DMS 迁核心库，同步追平增量。
3. **灰度切换**：把一部分读流量切到新库，比对结果。
4. **回滚预案**：切换出错能立刻切回旧库（旧库保留到稳定期）。
5. **清理下线**：稳定运行 1–2 周后，再下线旧库。

**辨析｜易错点：** 迁移最大的坑是「**一次性大爆炸**」——周末抽一个窗口，全量导完直接切，出事就只能通宵回滚。成熟的迁移永远「**小步快跑 + 随时可回滚**」，把「一次豪赌」拆成「多次小切换」。<span class="marginnote">迁移还有一个常被忽略的准备项：<strong>应用层改造</strong>。如果应用代码里硬编码了数据库 IP、用了旧库专属的 SQL 方言，迁移后可能「连得上却跑不对」。真正稳妥的迁移，要先做应用侧的可移植性检查——这呼应了《云原生概念与 12 要素》的「后端服务可替换」原则。</span>

## 6 只读副本与读写分离：扩展读负载

数据库的扩展瓶颈通常先出现在**读**上（读多写少是常态）。云数据库解决读扩展的标准手段是**只读副本（read replica）**：

**读写分离**：主实例处理写请求，N 个只读副本处理读请求，应用通过不同连接地址访问。读流量可以水平扩展，写保持单点（强一致）。

| 维度 | 主实例 | 只读副本 |
| --- | --- | --- |
| 读写 | 读写 | 只读 |
| 数量 | 1 | 可多个 |
| 数据来源 | 业务写入 | 主实例异步/半同步复制 |
| 故障 | 触发主备切换 | 可随时增减 |

**辨析｜易错点：** 只读副本的复制是**异步**的（或半同步）——**刚写入主库的数据，读副本可能暂时读不到**。这带来一个经典问题：写后立即读（如「提交订单后刷新看到订单」）如果被路由到延迟的副本，会出现「看不到刚写的数据」。解法是**关键读走主库**（或等一写延迟）——读写分离的「一致性权衡」必须被应用层感知。

**再进一步的分片（sharding）**：写也到瓶颈时，把数据按 key（如用户 ID）水平切到多个数据库实例——每个实例只存一部分数据，写压力被分散。但分片引入跨片查询、全局唯一 ID、数据再平衡等复杂度，通常**只在单库实在扛不住时才上**。<span class="marginnote">从「单库 → 主备 → 读写分离 → 分片」是一条「按压力逐步升级」的路线，每一步都引入复杂度：主备要管切换、读写分离要管一致性、分片要管路由。<strong>数据库扩展的艺术是「在压力逼你之前，绝不提前引入下一级复杂度」</strong>——这与《云成本优化》的「按需引入」是同一原则。</span>

## 7 小结

- 托管数据库 = **DBaaS**：云管到引擎、你管到 schema，责任链切分清晰。
- 三件套能力：**自动高可用（主备）、自动备份（快照+日志=PITR）、在线扩缩容**。
- **NoSQL** 牺牲事务换水平扩展；**云原生数据库**用存储计算分离兼顾 SQL 与扩展。
- 选型口诀：核心业务云原生、海量 KV 用 NoSQL、省钱省心托管 RDS。
- 数据库是存储主线的最顶层——块存储供底、分布式系统供可靠性、SQL 引擎供语义。

- 数据库在云中的位置：**它是「最难的托管化对象」**——既要低延迟、强一致，又要高可用、可扩展；理解了云数据库，就理解了托管化能力的极限。

- 核心记忆点：**云数据库的三大价值 = 自动高可用 + 自动备份（PITR）+ 在线扩缩容**——这三样正是自建最痛的。
- 面试常见问法：「**主备切换多久？备份能回滚到任意时刻吗**」——答「快照+日志=时间点恢复」即懂核心。
- 与后续的衔接：数据库是「最难托管化」的对象，理解了它，「托管化」的能力边界就清楚了。
- 自查练习：**说清「主备切换」与「只读副本」的区别**——前者管「写的高可用」，后者管「读的扩展」，两个机制别混。
- 一句总结：**核心业务云原生、海量 KV 用 NoSQL、省钱省心托管 RDS**——三条路线各归其位。

至此，第三篇**云存储与云网络**的七篇全部完成。接下来进入第四篇——**无服务器与云原生**，从最颠覆的形态讲起：函数即服务（FaaS）。存储与网络是云的「资源面」，第四篇将转向「应用面」——**资源面回答「云能提供什么」，应用面回答「应用该如何被构建、交付与运行」**。
