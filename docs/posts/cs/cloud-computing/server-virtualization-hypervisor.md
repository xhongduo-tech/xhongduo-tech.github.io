## 为什么从虚拟化开始

上一篇讲资源池时，我们反复提到「物理资源被虚拟化切分」——现在就来拆开这个黑箱。**虚拟化**是云计算所有能力的地基：弹性靠它（随时创建/销毁虚拟机）、多租户靠它（一台物理机多人共享）、计费靠它（按虚拟资源计量）。这一篇聚焦最核心的**服务器虚拟化**，回答一个问题：一台物理机，凭什么能同时跑多个互不干扰的完整操作系统？

给个直觉入口：一台物理机跑多个系统，最朴素的想法是「让系统们轮流用硬件」——但操作系统不是「轮流用」，它假定自己独占整个机器、直接操作硬件。虚拟化要解决的正是这个矛盾：**让多个「以为自己在独占」的操作系统，安全地共享一台真实机器**。

## 1 虚拟化：把一个物理资源变成多个逻辑资源

**虚拟化（virtualization）**：通过一层软件将物理资源抽象成多个逻辑资源，或把多个物理资源聚合成一个逻辑资源，使资源对上层呈现统一的逻辑形态。对服务器虚拟化而言，**一台物理机 → 多台虚拟机（VM）**，每台虚拟机拥有独立的虚拟 CPU、内存、磁盘与网卡，内部运行着完整的操作系统（客户操作系统，guest OS）。

连接物理资源与虚拟机的这层软件就是 **Hypervisor（虚拟机监控器，VMM）**：它运行在最高特权级，负责**资源的分时调度、虚拟硬件的模拟、以及对客户机特权指令的拦截处理**。<span class="marginnote">VMM（Virtual Machine Monitor）与 Hypervisor 是同一概念的两个名字：学术界爱用 VMM，厂商爱用 Hypervisor（如 VMware ESXi、KVM、Xen）。它的核心不变量是「等价性」：客户机里跑的程序，其结果应与在裸物理机上运行完全一致，只是慢了。</span>

## 2 Hypervisor 的两种形态

按运行位置，Hypervisor 分为两类：

**Type-1 裸机型（bare-metal）Hypervisor**：直接运行在物理硬件之上，本身就是一个微内核操作系统。虚拟机作为普通进程在其上运行。性能最高，用于生产环境。代表：VMware ESXi、KVM、Xen、微软 Hyper-V。

**Type-2 宿主型（hosted）Hypervisor**：运行在宿主操作系统之上，作为普通应用程序。适合开发与测试，性能有损耗。代表：VirtualBox、VMware Workstation、Parallels Desktop。<span class="marginnote">把 Type-2 类比成「应用层程序」，把 Type-1 类比成「操作系统本身」，就能立刻想通两者的性能差：Type-1 的调度者是硬件，Type-2 的调度者是宿主操作系统——中间隔了一层，资源争夺就多了一层。</span>

## 3 虚拟化的三把钥匙：特权级、拦截、模拟

服务器虚拟化要解决的**根本难题**是：客户机操作系统里的特权指令（如改中断向量表、操作页表、关中断）本应只在物理机上最高特权级执行，现在却要交给 Hypervisor 仲裁。历史上有三种解法：

**特权级与陷阱（trap-and-emulate）**：让客户机运行在非最高特权级，其特权指令一旦执行就触发**陷阱**（trap），陷入 Hypervisor，由 Hypervisor 模拟执行后返回。这是理论最优雅的方案，但需要 CPU 架构配合。
**二进制翻译（binary translation）**：VMware 的早期方案。在客户机指令**执行前**，Hypervisor 扫描特权指令并**翻译**成安全的等价指令序列，避免运行时陷阱的开销。
**硬件辅助虚拟化（hardware-assisted）**：Intel VT-x / AMD-V 在 CPU 里新增了 **VMX/V-SVM 指令集**与专门的**虚拟机运行态（VMX non-root）**，让客户机可以在「准特权」状态下运行，特权敏感操作由硬件自动陷入 VMM。<span class="marginnote">硬件辅助是现代虚拟化的主流（KVM 依赖它）。它把「拦截特权指令」从软件翻译变成了硬件机制，性能接近裸机。对 CPU 特权级（ring 0–3）的理解来自第三级《操作系统》：虚拟化等于在 ring 0 下方再挖了一层 ring -1。</span>

## 4 核心要点对比：两类 Hypervisor 与三种虚拟化方式

| 维度 | Type-1 裸机 | Type-2 宿主 |
| --- | --- | --- |
| 运行位置 | 直接于硬件上 | 宿主 OS 之上 |
| 性能 | 接近裸机 | 有额外开销 |
| 适用场景 | 生产、云数据中心 | 开发、测试、桌面 |
| 代表产品 | ESXi、KVM、Xen、Hyper-V | VirtualBox、VMware Workstation |

| 虚拟化方式 | 原理 | 时代 |
| --- | --- | --- |
| Trap-and-emulate | 特权指令触发陷阱，VMM 模拟 | 理论模型 |
| 二进制翻译 | 执行前翻译特权指令 | 软件虚拟化时代 |
| 硬件辅助 | CPU 提供 VMX 指令与虚拟运行态 | 现代主流 |

**辨析｜易错点：** 虚拟化 ≠ 模拟。**模拟（emulation）**是完整翻译整套指令集（如在 x86 上模拟 ARM），与客户机指令集可能不同；**虚拟化**要求客户机指令集与物理机一致，Hypervisor 只拦截**特权敏感指令**。前者慢几个数量级，后者接近原生速度。虚拟化是对「同等指令集」的调度与隔离，不是翻译。

## 5 虚拟化的性能代价与优化

「接近裸机」是虚拟化的目标，但不是免费的。理解性能代价从哪来，才能看懂云主机规格差异背后的原因。虚拟化的主要开销有三个来源：

| 开销来源 | 产生原因 | 缓解手段 |
| --- | --- | --- |
| **CPU 虚拟化开销** | 特权指令的拦截与陷入 | 硬件辅助（VT-x），开销趋近于零 |
| **内存虚拟化开销** | 两级地址翻译、TLB 抖动 | EPT 硬件翻译 + 大页 |
| **I/O 虚拟化开销** | 虚拟网卡/磁盘要经 VMM 转发 | 半虚拟化驱动、SR-IOV 直通 |

其中 **I/O 虚拟化**是差距最大的环节：早期全虚拟化下，一次网络读写要经过 VMM 多次上下文切换，性能可能只剩裸机的一半。三个时代的三级跳：**软件模拟**（最慢）→ **半虚拟化**（客户机用特制驱动，主动配合 VMM，如 virtio）→ **硬件直通**（SR-IOV 把物理网卡切成多个虚拟网卡直连虚拟机，接近裸机）。

**辨析｜易错点：** 「云主机性能不如物理机」是刻板印象——在**硬件辅助 + 半虚拟化 + SR-IOV** 这三件套齐备的现代虚拟化栈上，计算密集负载已接近裸机（损耗常 <5%），差距主要残留在**极端 I/O 密集与抖动敏感**场景。<span class="marginnote">这也是云厂商「裸金属服务器」存在的理由：对极致性能、或需要直接操作硬件的负载（数据库、高性能计算、某些加密），放弃虚拟化层，把整台物理机租给你——用「失去弹性」换「无虚拟化损耗」。裸金属是虚拟化光谱的另一端。</span>

## 6 虚拟机迁移与高可用：虚拟化的超能力

虚拟化在「切分资源」之外，还解锁了两个物理机时代不可能的能力——**迁移**与**高可用**。

**在线迁移（live migration）**：让一台虚拟机**在运行中**从一台物理机搬到另一台，业务不中断。原理是「内存预拷贝」：

1. 先复制虚拟机的全部内存到目标物理机。
2. 期间内存继续变化，迭代复制「变化的部分」，直到变化量足够小。
3. 极短的一次暂停，切换 CPU 状态到目标机，业务无缝继续。

**迁移的价值**：物理机要维护、升级、淘汰时，先把它上面的虚拟机「热迁移」走，再关机维修——**运维操作不再需要停机窗口**。这就是「云厂商可以在你不知情时维护底层硬件」的原因。

**高可用（HA）**：配合**共享存储**与**心跳检测**，Hypervisor 监控每台物理机——某台宕机，其上虚拟机**自动在另一台物理机上重启**（秒级~分钟级），无需人工介入。这是云主机「故障自动恢复」的第一层保障。

**辨析｜易错点：** 在线迁移 ≠ 无感容灾。迁移是「**主动的、平滑的**」搬家；故障后重启是「**被动的、有中断的**」重建——后者会丢失迁移中的内存状态（未落盘的数据）。「云主机故障了数据不丢」，靠的不是 Hypervisor，而是**分布式存储的副本**（见《分布式文件系统》）——内存态和持久态是两回事，别混为一谈。<span class="marginnote">在线迁移对<strong>性能敏感的负载</strong>（数据库）仍有风险：迁移瞬间的「暂停」可能造成可感知的抖动。因此云厂商通常对「独享型/高保障」实例的底层维护更谨慎，有时会提示「实例需停机维护」而不是强行热迁移——<strong>虚拟化的能力存在，用不用要按负载权衡</strong>。</span>

## 7 Hypervisor 的选型：KVM 与 VMware

理解了虚拟化的原理，落地时面对的第一个现实选择是「**用什么 Hypervisor**」。主流方案里两个代表：

**KVM（Kernel-based Virtual Machine）**：Linux 内核自带的虚拟化模块，开源、免费、被几乎所有云厂商用作底座（AWS 的 Nitro、阿里云、OpenStack 都基于它）。它与 Linux 生态深度集成，性能优秀，是**公有云的事实标准**。

**VMware ESXi**：商业虚拟化巨头，功能成熟（迁移、高可用、资源池化管理做得很完善），适合**企业私有云/传统数据中心**，但商业授权成本高。

| 维度 | KVM | VMware ESXi |
| --- | --- | --- |
| 开源 | 是 | 否（商业） |
| 云厂商使用 | 主流底座 | 较少 |
| 管理工具 | 需搭配 OpenStack/自研 | 自带 vCenter |
| 适用 | 公有云、开源栈 | 企业私有云 |

**辨析｜易错点：** 别把「Hypervisor 选型」和「云平台选型」混为一谈——选 KVM 只是选了「虚拟化引擎」，你还得配调度（OpenStack/K8s）、网络、存储，才成「云」。**Hypervisor 是云的「发动机」，不是「整车」**。<span class="marginnote">这里有个行业洞察：<strong>虚拟化已「商品化」——Hypervisor 不再是差异化的来源</strong>。KVM 开源免费、性能足够，云厂商的竞争早已上移到「存储、网络、调度、服务」这些更高层（见《云计算的体系架构》）。理解「底层商品化、上层差异化」这条产业规律，就理解了云的商业结构。</span>

## 8 小结

- **虚拟化**：一层软件把物理资源抽象为多个逻辑资源；**Hypervisor** 是这层软件。
- **Type-1 裸机型**（ESXi/KVM）性能最好、用于生产；**Type-2 宿主型**（VirtualBox）用于开发测试。
- 核心难题是**拦截客户机特权指令**，解法演进：trap-and-emulate → 二进制翻译 → **硬件辅助（Intel VT-x）**。
- 硬件辅助虚拟化让客户机运行在「ring -1」，性能接近裸机。
- 虚拟化 ≠ 模拟：前者调度同指令集，后者翻译异指令集。

- Hypervisor 篇的收获总结：**虚拟化的本质是「一层软件 + 一个不变量」**——软件是 Hypervisor，不变量是「客户机与裸机行为等价」；记住这个，后面的 CPU/内存/存储虚拟化都只是「为保持等价而做的工程」。

- 核心记忆点：**Type-1 裸机虚拟化用于生产，Type-2 宿主型用于开发**——性能与易用的一次取舍。
