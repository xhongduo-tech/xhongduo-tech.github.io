## 为什么从对象存储开始

第三篇讲云存储与云网络，最经典也最重要的产品就是**对象存储**——AWS S3 是它的事实标准，今天互联网上几乎每一张图片、每一个视频、每一次备份，都跑在某个对象存储上。为什么块存储和文件存储「卷不动」的海量数据，对象存储却游刃有余？答案藏在它的**接口模型与系统架构**里。这一篇把 S3 模型拆透，你会理解「为什么对象存储是云的压舱石」。

一个数字先给个直观：一块普通云盘（块存储）的容量上限是「块设备的物理上限」，而对象存储的容量是「近乎无限」——因为它的数据被分散在成千上万台机器上。**「海量」是对象存储的第一属性**，理解它为什么能海量，就是这篇的主线。

## 1 桶与对象：一个扁平的名字空间

S3 模型只有两个核心概念：

- **桶（bucket）**：一个容器，存放对象的顶层命名空间。桶名**全局唯一**（所有用户共享一个名字空间，如 <code>my-company-images</code>）。
- **对象（object）**：数据的存储单元，由 **key**（对象名，类似路径）+ **value**（数据）+ **元数据**（类型、大小等）组成。

数据在桶里通过 key 定位，像文件系统里的路径。关键设计是**名字空间是扁平的**——所谓的「目录」只是 key 字符串里带 <code>/</code> 的**约定俗成**，并不存在真正的目录层级。<span class="marginnote">S3 的扁平命名空间是一次反直觉的设计：文件系统里目录是真实存在的树状结构，而对象存储里一切都是一层 key。好处是<strong>海量扩展极其简单</strong>——不需要维护目录树，只需要一个能索引亿级 key 的查表系统；坏处是没有「重命名目录」这类操作（要一个个复制对象）。</span>

## 2 S3 的接口哲学：HTTP + 无状态

S3 通过 **HTTP REST API** 访问：用 <code>GET</code>`/<code>PUT</code>`/<code>DELETE</code> 请求一个 URL 就完成读写删除。这带来三个深远后果：

**任何语言的任何客户端都能用**——SDK、curl、浏览器都行，不用装文件系统驱动。
**天然适合互联网服务**——CDN、静态网站托管、图片处理都可以直接挂在 S3 上。
**无状态**——每个请求独立，不需要维持连接，系统可以任意水平扩展。<span class="marginnote">HTTP 接口是对象存储与块/文件存储的本质区别之一：块存储走 SCSI/NVMe 块协议、文件存储走 NFS/SMB 文件协议，都要求「先挂载、后使用」；对象存储则「免挂载、直接调 API」——这也是为什么对象存储能成为互联网的基础设施而块存储不能。</span>

一致性上，S3 提供**强一致读**（写入后立刻读到自己写的数据），但多副本之间的传播与跨区域的复制仍是**最终一致**的——这来自分布式系统「一致性 vs 可用性」的权衡，可回看第三级《分布式系统》的 CAP 讨论。

## 3 系统架构：元数据与数据分离

对象存储能撑起「无限大」的秘密，在于**元数据服务与数据存储的彻底分离**：

**元数据服务（control path）**：维护「key → 数据位置」的映射，是海量索引系统，负责路由每个请求。
**数据存储层（data path）**：真正存放对象数据的分布式集群，把对象切片、多副本存放。

一次 <code>GET</code> 请求的旅程：客户端先查元数据服务找到对象存在哪个存储节点 → 再从存储节点取数据。元数据与数据分离，使两边可以**独立水平扩展**：数据多了加存储节点，key 多了扩展元数据索引。<span class="marginnote">「元数据与数据分离」是分布式存储的经典架构，我们在第三级《分布式文件系统》也会遇到同样的分离（元数据节点 + 数据节点）。它的收益是<strong>控制路径与数据路径解耦</strong>：寻址开销（控制）与吞吐（数据）互不拖累，海量小对象也能高效定位。</span>

## 4 核心要点对比：对象存储与块/文件存储

| 维度 | 对象存储（S3） | 块存储（EBS） | 文件存储（EFS） |
| --- | --- | --- | --- |
| 访问方式 | HTTP API，免挂载 | 挂载为块设备 | 挂载为目录 |
| 名字空间 | 扁平的桶+key | 无（裸块） | 树状目录 |
| 扩展性 | 近乎无限 | 卷级上限 | 受挂载协议限制 |
| 一致性 | 最终一致为主 | 强一致 | 强一致 |
| 成本 | 极低（GB 级单价） | 较高（性能导向） | 中 |
| 典型场景 | 静态资源、备份、数据湖 | 数据库、系统盘 | 共享协作 |

**辨析｜易错点：** 对象存储**不能直接跑数据库**——它的接口是「整对象读写」，不支持数据库需要的随机小粒度写与并发事务。S3 适合「一次写入、多次读取、整体替换」的数据（图片、日志、备份），而数据库要用块存储。把对象存储当「能挂载的硬盘」用，是用错对象存储最常见的误区。<span class="marginnote">一个常被忽视的 S3 特性是<strong>存储分层</strong>：热数据（标准）、冷数据（低频）、归档数据（最便宜、取回慢）。数据越冷越便宜，这是对象存储商业模型的核心——成本随访问频率自动优化，是 FinOps 的经典抓手。</span>

## 5 存储分层与生命周期管理

对象存储「便宜」的完整故事，藏在**存储分层（storage tiers）**里——同一份数据，越冷越便宜，代价是取回越慢：

| 层级 | 特性 | 单价 | 取回 | 典型数据 |
| --- | --- | --- | --- | --- |
| 标准层 | 低延迟、频繁访问 | 最高 | 即取 | 网站图片、活跃文件 |
| 低频访问层 | 访问少但要有 | 约 1/2 | 秒级（收取回费） | 月度报表、日志 |
| 归档层 | 几乎不访问、要留档 | 最低（约 1/5） | 分钟~小时 | 合规存档、历史备份 |

**生命周期规则（lifecycle policy）**自动完成「数据变冷」的迁移：比如「标准层放 30 天 → 自动转低频 → 90 天后转归档 → 1 年后删除」。你可以只管「数据该留多久」，迁移由系统自动执行。

**辨析｜易错点：** 分层优化的核心是「**只给真正热的数据付热价**」。常见的浪费是「所有数据都放标准层」——备份、日志、历史快照这类访问极低的数据占大头，却按最贵的价格存着。一次生命周期梳理，常常能省下 30%–50% 的存储账单。<span class="marginnote">这里有一个与《云成本优化（FinOps）》直接挂钩的洞察：<strong>存储成本优化的本质是「按访问频率对号入座」</strong>。热数据贵得有理由（低延迟），冷数据便宜得合理（取回慢）。把数据放进「恰好够用」的层级，是对象存储成本治理的第一课。</span>

**生命周期规则还有个隐藏收益——合规**：法律要求的「数据保留 7 年」可以直接配成「归档层保留 7 年」，到期自动删除——把「合规要求」翻译成「存储规则」，既省心又不怕审计。

## 6 版本控制、静态网站与更多 S3 玩法

S3 模型的表达能力比想象中强，几个常见玩法：

**版本控制（versioning）**：开启后，对同一 key 的每次写入都会**保留历史版本**——误删/误改可以随时恢复到一个旧版本。这是「对象级的快照」，也是数据保护的重要一环。配合**生命周期规则**，还可以「只保留最近 N 个版本」。

**静态网站托管**：把网站的 HTML/CSS/JS 传进一个桶，开启「静态网站托管」，S3 就直接成为一个 HTTP 网站——**不需要服务器**。配合 CDN 与自己的域名，一个低成本、高可用的静态站点就建成了。这印证了对象存储「HTTP 接口」的天生优势：它本来就是为 Web 而生的。

**其他常用特性**：

**预签名 URL（presigned URL）**：给一个对象生成**限时有效的临时访问链接**，无需公开桶——「私有内容分享给指定用户」的标准做法。
**事件通知**：对象被上传/删除时触发事件（接入函数计算），是事件驱动架构的天然数据源。
**加密**：服务端加密（SSE/KMS），数据落盘即加密。

**辨析｜易错点：** 静态网站托管 ≠ 动态网站。S3 只提供「文件原样返回」，没有后端逻辑、没有数据库——动态内容（登录、个性化）做不了。正确组合是「**静态资源 + 托管 → 对象存储，动态接口 + 业务 → 计算服务**」，各司其职。<span class="marginnote">预签名 URL 是对象存储「既私有又可分享」的关键机制：<strong>桶保持私有，但给指定对象签发一张限时门票</strong>——票上有签名、有过期时间。这在文件下载、上传授权、视频点播里是标配，也是「访问控制」在对象存储上的经典实现，与《云安全与合规》的「最小权限」一脉相承。</span>

## 7 对象存储的安全实践：桶别裸奔

对象存储是云上「最容易裸奔」的服务——默认配置下，一个公开读的桶就能把全公司数据暴露在公网。三件必须做的事：

| 安全实践 | 做法 | 防什么 |
| --- | --- | --- |
| **默认私有** | 桶默认不公开，公开需显式声明 | 数据意外暴露 |
| **桶策略最小化** | 用最小权限策略，不设 `<code>`* 通配 | 越权访问 |
| **服务端加密** | 开启 SSE/KMS 加密 | 落盘数据被读 |

**辨析｜易错点：** 「桶公开」与「桶私有」不是「一个开关」，而是「一组策略的组合」——桶策略、对象 ACL、IAM 权限三者叠加决定谁能访问。**安全审计时最容易漏的是「对象 ACL」**——桶设了私有，但某个对象被单独设了公开，一样泄露。正确姿势是「**默认全部私有 + 显式最小公开**」，并且定期扫描公开桶。<span class="marginnote">「公开读桶」是云安全事故的「头号网红」——国内外都发生过「数据库备份桶公开、被爬虫扫到、全量泄露」的案例。<strong>对象存储默认私有，是云厂商的默认安全设计；所有「公开」都应该是深思熟虑后的显式动作</strong>。这与《云安全与合规》的「最小暴露」原则一脉相承。</span>

## 8 小结

- 对象存储模型：**桶（全局唯一）+ 对象（key/value/元数据）**，名字空间扁平。
- 接口哲学：**HTTP REST + 无状态**，免挂载、任何客户端可用。
- 架构关键：**元数据服务与数据存储分离**，两侧独立水平扩展。
- 与块/文件存储的取舍：对象存储**无限扩展、廉价、面向海量非结构化数据**，但不支持小粒度随机写。
- S3 是对象存储的事实标准，OSS、OBS、Blob Storage 都是它的同构实现。

- 对象存储的定位提醒：**它是「互联网数据的仓库」，不是「运行应用的磁盘」**——应用要随机小粒度写，就得用块存储；这正是下一篇要讲的。

- 核心记忆点：**对象存储 = 桶 + key + HTTP**，扁平命名空间是它「海量」的第一秘密。

在下一篇，我们看另外两种存储形态——**块存储与文件存储**，它们如何在云上服务数据库与共享协作场景。对象存储赢在「海量、廉价、HTTP」，但它覆盖不了「低延迟随机读写」与「多机共享目录」——**这三种存储各管一摊，下一篇把另外两摊补齐，你就有完整的存储选型地图**。
