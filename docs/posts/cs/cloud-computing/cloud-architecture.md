## 为什么从体系架构开始

前四篇讲了云是什么、有哪些特征、卖什么、放哪里，都是「从外面看云」。这一篇把镜头拉进云内部，看一朵云**由哪些部件组成、各部件如何分工**。这个架构框架非常稳定：无论 AWS、Azure 还是阿里云，宏观上都遵循「前端接入、服务交付、管理中枢、资源池化、物理底座」的五层结构。理解了它，后续每一篇（虚拟化、存储、网络、无服务器）都只是往这五层的某一格里填细节。

用一张「熟悉的地图」帮你定位：你已经学过的操作系统，也是分层的（硬件 → 内核 → 系统调用 → 应用）；云的架构同样分层，只是把「内核」换成了「管理层 + 资源池」。**分层是计算机系统通用的组织方式**——这一篇的云架构，是你已熟悉的分层思想在「数据中心尺度」上的重演。

## 1 宏观切面：前端、管理层与后端

一朵云从使用者的视角可以切为三块：

- **前端（front end）**：用户与云交互的界面——Web 控制台、命令行工具（CLI）、API、移动端 App。它负责把用户的意图翻译成云后端的操作。
- **后端（back end）**：提供服务的物理与逻辑实体——数据中心里的服务器、存储阵列、网络设备，以及其上承载的虚拟化资源池与服务组件。
- **管理层（management layer）**：连接前端的控制指令与后端的资源操作的中枢，负责计费、监控、安全、编排等「横切」职责。

**辨析｜易错点：** 许多人把「云架构」理解成一张服务清单（有 EC2、有 S3、有 RDS），那是**产品列表**，不是**体系架构**。体系架构要回答的是**这些服务之间如何组织、谁来管理、资源如何流转**——管理层正是容易漏掉的那一环。<span class="marginnote">把一朵云类比成一台电脑：前端是键盘鼠标（输入设备），后端是 CPU 与内存（算力），管理层则是操作系统（调度、记账、隔离）。「操作系统」这层经常被用户忽略，却是云区别于裸资源堆的关键。</span>

## 2 资源池：云的「算力肌肉」

资源池位于后端的核心，由**计算资源池、存储资源池、网络资源池**构成。物理资源经过虚拟化技术被切分成细粒度单元，动态分配给不同租户：一台物理机可以跑几十台虚拟机，一块物理盘可以切成多个云盘，一张物理网卡可以通过虚拟交换机分出多个虚拟网络。

资源池化带来两个关键性质：**一是利用率提升**——多租户错峰共享，把平均利用率从自建机房的 5%–15% 拉到 60% 以上；**二是弹性成为可能**——加一台物理机就是往池子里注水，用户的虚拟资源可以随时从池中取用。<span class="marginnote">「池」的比喻很精确：你从池子里取水时不关心水来自哪根水管、水池在哪。这正是资源池化的产品承诺——用户感知到的是「无限可用」，服务商感知到的是「统一调度」。池与调度，是第二篇《虚拟化技术》的主角。</span>

## 3 管理层：云的「大脑」

管理层横跨前端与后端，承担五类横切职责：

| 管理职能 | 干什么 | 对应产品/机制 |
| --- | --- | --- |
| 计费与结算 | 计量用量、出账单 | 账单中心、按量计费 |
| 监控与告警 | 采集指标、发现异常 | CloudWatch、云监控 |
| 安全与认证 | 身份认证、权限控制 | IAM、访问密钥 |
| 服务编排 | 按需创建/销毁资源 | 资源编排、自动化脚本 |
| 多租户隔离 | 租户间逻辑隔离 | VPC、租户 ID、配额 |

管理层是云的「操作系统」：用户敲一条命令创建虚拟机，这条命令先到达管理层，经过**认证 → 配额检查 → 编排调度 → 计量登记**四步，才真正落到资源池里创建资源。<span class="marginnote">管理层的「先记账后干活」顺序值得记住：云的任何操作都要先过<strong>认证与配额</strong>两道闸，这保证了一个租户的失控操作不会挤爆整个池子——这是分布式系统里「准入控制」（admission control）思想在云上的体现，可回看第三级《分布式系统》中的过载保护。</span>

## 4 服务层：把能力交付出去

服务层把资源池与管理层的能力包装成上一篇讲的三种服务模型对外交付：IaaS 暴露虚拟资源，PaaS 暴露运行环境，SaaS 暴露完整应用。服务层本身是「薄」的一层——它不产生算力，只是**把底层的资源与管理能力翻译成用户可用的产品**。云厂商的竞争，很大程度发生在这一层：同样的 IaaS 能力，谁的 API 更稳定、控制台更好用、生态更完整。

## 5 一次云操作的生命周期：从点击到资源就绪

把前面的五层串起来，看一次「在控制台创建一台虚拟机」的完整旅程。这一步看似平凡，实际是云架构五层协作的缩影：

1. **前端**：你在控制台填好规格（CPU、内存、系统镜像、VPC），点「创建」——前端把请求打包成 API 调用，发给管理层的 API server。
2. **认证与配额**：API server 先验证你的身份（IAM 令牌），再检查配额——你还有没有创建实例的额度、规格是否在允许范围内。**不符合就直接拒绝**，资源不会多占一分。
3. **编排调度**：通过校验后，编排组件把「创建一台虚拟机」分解成子任务：挑物理机（调度）、分配虚拟 CPU 与内存、从镜像仓库克隆系统盘、挂虚拟网卡。
4. **计量登记**：从实例创建那一刻起，计量组件开始计时——这台实例从此刻起按小时计费，账单从这里累加。
5. **资源池落地**：虚拟化层在选定的物理机上真正拉起虚拟机，网络层在 VPC 里分配 IP。几秒到几十秒后，实例进入运行状态，前端显示「运行中」。

**辨析｜易错点：** 这条链路上，最容易出问题的不是「创建」本身，而是**配额与计量的缺失**——如果云没有「认证→配额→编排→计量」这套管理层流程，任何人都能无限制开资源、成本无法归属，云立刻退化成「一群人共用的裸机房」。管理层不是云的装饰，而是**云之所以成其为云**的制度层。<span class="marginnote">把「创建虚拟机」换成「创建数据库」「创建函数」，你会发现旅程几乎一样——<strong>云的每一个资源创建都走同一套管理层流程</strong>。这就是为什么云架构的学习可以从「一朵云内部怎么处理一次请求」入手：理解了一次，就理解了全部。</span>

## 6 云的扩展性设计：为什么云能「看起来无限」

回到「为什么用户感觉云是无限资源」这个出发点。云的扩展性不是魔法，而是一组**设计决策**的叠加：

**水平扩展（horizontal scaling）**：不加配置，而是**加机器**。单台机器有物理上限，但「一千台 8 核机器」没有。云把「扩展」从「升级单机」变成「增加实例」，配合负载均衡分发流量——这是云能无限扩展的第一支柱（见《负载均衡》）。

**无状态（stateless）**：能水平扩展的前提是应用**不保存本地状态**——任何实例都能处理任何请求，加实例不加包袱。这是云原生应用的第一铁律（见《云原生概念与 12 要素》）。

**分片（sharding）**：数据量超越单机时，把数据按 key 切到多台机器——每台只存一部分，查询只找对应那台。对象存储、分布式数据库都用分片撑起「海量」。

**最终一致（eventual consistency）**：为了可用性，云上很多系统放宽「强一致」——多副本数据「最终」会一致，但某一瞬间可能不同（见《分布式文件系统》）。这是用「一致性」换「可扩展性」的经典权衡。

| 设计 | 解决什么 | 代价 |
| --- | --- | --- |
| 水平扩展 | 容量与吞吐上限 | 分布式复杂度 |
| 无状态 | 扩展无痛 | 状态外置的工程成本 |
| 分片 | 单机数据上限 | 跨片查询与重分布 |
| 最终一致 | 可用性与扩展 | 一致性的短暂松弛 |

**辨析｜易错点：** 「云无限扩展」是产品话术，不是工程事实。**每个具体组件都有自己的天花板**：数据库的连接数、LB 的并发、单个对象桶的请求速率——扩展是「把天花板抬高到够用」，不是「消灭天花板」。<span class="marginnote">一个成熟的架构师看待云，不是「相信它无限」，而是「<strong>知道每个组件何时到顶、怎么拆开再扩</strong>」。这套「拆了再扩」的能力——无状态化、分片、缓存、队列削峰——是云计算在架构层面的真正学问，也是后续第三篇、第四篇反复出现的主题。</span>

## 7 对照练习：用五层框架读一家云的控制台

学到这，做一个「**用框架看真实产品**」的练习：打开任意一家云厂商的控制台（免费账号即可），把看到的产品分类进五层框架。

| 控制台里看到的产品 | 属于哪一层 |
| --- | --- |
| 云服务器 ECS / EC2 | 资源池（计算） |
| 云盘、对象存储、文件存储 | 资源池（存储） |
| VPC、负载均衡、CDN | 资源池（网络）/ 服务层 |
| 云数据库、消息队列、函数计算 | 服务层 |
| IAM、访问控制、操作审计 | 管理层 |
| 账单中心、预算告警 | 管理层（计量） |

做完这个分类，你会有一个顿悟：**产品再多，也逃不出「资源池 + 服务层 + 管理层」三个大盒子**——云厂商看似繁多的产品线，不过是往这三个盒子里填格子。掌握了框架，面对任何云厂商的产品地图都不再发怵。

**辨析｜易错点：** 分类时最常纠结的是「某些产品横跨两层」——比如负载均衡既是网络资源、又算服务。没关系，**框架是「理解的角度」，不是「严格的抽屉」**。一个产品落在哪层不重要，重要的是你能用它组织起「谁提供资源、谁交付能力、谁负责管理」的全局观。框架的价值在于「防迷失」，不在「求精确」。<span class="marginnote">这个练习还揭示了一件事：<strong>不同云厂商的「五层布局」几乎相同</strong>——因为大家都按同一套工程规律在构建（计算/存储/网络是基础、服务层是差异化、管理层是运营必需）。所以「<strong>学会一家云，迁移到另一家只需学产品名</strong>」——这就是《主流云平台概览》里「命名对照表」能成立的深层原因。</span>

## 8 小结

- 云架构的宏观五层：**前端、服务层、管理层、资源池、物理底座**。
- 前端管接入、服务层管交付、管理层管协调、资源池管算力、物理层管硬件。
- 管理层是云的「大脑」：**认证 → 配额 → 编排 → 计量**是每个操作的标准流程。
- 资源池化的两个性质：**高利用率**与**弹性**。
- 云架构是产品清单之上的一层「组织逻辑」，别把服务列表当架构。

- 架构篇的方法论：**用「五层框架」读任何一朵云**——前端接入、服务交付、管理中枢、资源池化、物理底座，这个框架对 AWS、阿里云、私有云同样适用，下一篇就是用它读各家产品。

- 核心记忆点：**云架构五层 = 前端 + 服务层 + 管理层 + 资源池 + 物理底座**——管理层是常被忽略的「大脑」。

在下一篇，我们对照三家主流云平台（AWS/Azure/阿里云/华为云），看看这套架构在不同厂商手里长成了什么具体形态。架构是「蓝图」，厂商是「按蓝图盖起来的楼」——**同一张蓝图，各家盖出了不同户型；对照着看，蓝图的价值才真正显现**。
