## 为什么从数据库开始

前面的课程里，数据一直在「流动」：在网络里被分组、被路由。但还有另一类基本需求——数据要被**存下来、反复查**：你的订单记录、社交账号、这篇文章本身，都得在程序关闭之后依然存在。**数据库（database）**与**数据库管理系统（DBMS）**，就是负责「长期组织、高效查询、安全并发」的那一层。

它是今天一切应用的底座：电商的购物车、银行的转账、大模型的训练数据，全住在数据库里。而且数据库几乎是「理论与实践结合最紧」的计算机课程——上一节的索引、上上节的树、再往前的 ACID 事务，都会在这里汇合。<span class="marginnote">数据库思想也延伸到了「数据库之外」：文件系统要像数据库一样做崩溃恢复，消息队列要像数据库一样保证不丢消息，「把一切软件都做成数据库」甚至是一句流行的设计口号。</span>

## 1 从文件到数据库：为什么需要 DBMS

最简单的存储是**文件**：程序把数据写进文本或二进制文件，用时再读。但文件方式有两个致命弱点：**格式耦合**（每个程序都得自己约定文件的格式，换程序就换格式）与**缺乏管理**（没有统一查询、没有并发控制、没有备份）。

**数据库管理系统（DBMS）**把「存」和「用」彻底分开：程序只对着数据模型提问，由 DBMS 负责物理存储、索引、并发、安全与恢复。对比一下：

| 维度 | 文件存储 | 数据库管理系统 |
| --- | --- | --- |
| 数据格式 | 每个程序自己定 | 统一的数据模型 |
| 查询能力 | 靠程序自己扫文件 | 声明式查询语言（SQL） |
| 并发控制 | 基本没有 | 事务与锁 |
| 崩溃恢复 | 靠自己 | 日志 + 恢复机制 |
| 安全性 | 依赖操作系统 | 权限、视图、加密 |

**辨析｜易错点：** 数据库 ≠ 一堆数据文件。数据库是「数据 + 管理数据的系统」的整体；一个 Excel 表格不算数据库，因为 Excel 不提供事务、并发、标准查询语言这些管理能力。<span class="marginnote">「把逻辑与物理分开」这个老主题第三次出现：文件把数据暴露给程序，DBMS 把数据包在系统里。数据独立性（逻辑与物理分开）正是关系模型的创始人科德（E. F. Codd）反复强调的初心。</span>

## 2 关系模型：表、行、列

今天的主流数据库几乎都是**关系型（relational）**，源于科德 1970 年的经典论文。核心思想：**用一张张二维表（relation）组织数据**。

**表（table）**：一类实体的集合，比如「学生」「订单」；
**行（row）**：一条具体记录，比如某个学生；
**列（column）**：一个字段，比如「姓名」「学号」；
- **主键（primary key）**：能唯一标识一行的列（或列组合），比如「学号」；
- **外键（foreign key）**：指向另一张表主键的列，用来表达表之间的联系，比如「订单」表里的「学生学号」。

**辨析｜易错点：** 主键必须是**唯一且非空**的。身份证号、学号常作主键；而「姓名」不适合当主键——会重名。主键的选取看似小事，却决定了数据能否被可靠引用，这是数据库设计的第一课。<span class="marginnote">表之间的「外键」是关系模型表达联系的唯一手段：不靠指针、不靠嵌套，就靠「存对方的主键」。这套简洁设计让关系模型统治数据库半个世纪，直到 NoSQL 时代才被重新审视。</span>

**数据模型（data model）**就是「用什么结构组织数据」：关系模型用表，还有文档模型（JSON 嵌套，如 MongoDB）、键值模型（Redis）、图模型（Neo4j）。

「关系型 vs NoSQL」的选型争论，本质是「结构化强的数据用表、灵活多变的数据用文档/图」——没有银弹，只有适配。这也呼应数据结构一章的结论：**先问数据的「形状」是什么，再选容器。**

## 3 查询：SQL 与关系运算

有了表，怎么查？关系模型给出了几个基本运算，而 **SQL** 就是把它们写下来的语言。三个最核心的运算：

**选择（select）**：挑出满足条件的**行**，如「年龄 ≥ 18 的学生」；
**投影（project）**：挑出关心的**列**，如只要「学号、姓名」两列；
**连接（join）**：把两张表按关联条件**拼起来**，如把「学生」与「订单」按学号连成一张大表。

SQL 把它们写进一句声明式语句——你只描述「要什么」，不描述「怎么找」：

```sql
SELECT 学生.姓名, 订单.商品
FROM 学生 JOIN 订单 ON 学生.学号 = 订单.学号
WHERE 学生.年龄 >= 18;
```

**辨析｜易错点：** SQL 是**声明式**语言：你告诉数据库「要什么」，数据库的优化器自己去想「怎么最快找到」。这与我们写的命令式程序（一步步告诉机器怎么做）是两种思维。<span class="marginnote">「声明式 vs 命令式」是编程范式的分水岭，第四级《程序设计语言》会系统讲。你在 SQL 里少写一个 `WHERE`，就可能把全表拉回来——所以读懂执行计划是 DBA 的基本功。</span>

**索引（index）**：查询慢了怎么办？给常用列建索引。索引是数据库维护的一份「旁路」结构（常见是 B+ 树或哈希），让查找从「全表扫描」变成「沿索引跳」。这正复用了《数据结构》一章的树与哈希表。<span class="marginnote">索引不是免费的：每次插入、更新、删除都要同步维护索引，写变慢、磁盘变多。所以「为每列都建索引」不是优化，是灾难。索引该建在「查询频繁但更新少」的列上——这是调优的平衡木。</span>

## 4 事务与 ACID：数据库如何保证不犯错

多用户并发访问时，最怕「交叉更新」：两个人同时改同一个账户余额，一个把另一个的修改覆盖掉。数据库用**事务（transaction）**解决——一组操作要么全做、要么全不做，并且要求满足 **ACID** 四性：

**原子性（Atomicity）**：事务内操作不可分割，失败就整体回滚（rollback）；
**一致性（Consistency）**：事务执行前后，数据都满足所有约束（如余额不能为负）；
**隔离性（Isolation）**：并发事务互不干扰，好像串行执行一样；
- **持久性（Durability）**：事务一旦提交，结果永久保存，即使断电也不丢。

<span class="marginnote">ACID 是「把可靠性做进系统」的教科书答案。作为对比，分布式系统为保证可用性常会放宽隔离性——所谓 BASE 思想，这是第三级《分布式系统》CAP 定理的核心议题。</span>

**辨析｜易错点：** 原子性与持久性容易混：原子性管「失败时」——失败要整体回滚；持久性管「成功后」——成功要落盘不丢。一个管「不半途而废」，一个管「不事后悔账」。数据库靠**日志**（先记日志再改数据）同时实现两者，这是恢复技术的核心，第三级《数据库》专题深挖。

## 5 公式解析：索引为什么让查询变快

一个包含 $N$ 行的表，不带索引的查询（如按主键之外的列找）最坏要**全表扫描**，比较 $N$ 次；而建了 B+ 树索引后，沿树往下找只需约 $\log N$ 次比较。

$$
\text{全表扫描：} O(N) \qquad \text{索引查找：} O(\log N)
$$

拆三步看：
- **第一步，回忆数据结构**：B+ 树是「矮胖」的平衡树，高度 $h \approx \log_d N$（$d$ 是每个节点的子节点数，数据库里可达上千）。
- **第二步，代入数量级**：$N = 10^6$ 时，$\log_{1000} 10^6 = 2$——两次就能定位到叶节点；而全表扫描要 100 万次。
- **第三步，看清收益来源**：索引把「不知道在哪，只好全翻一遍」变成「知道去哪，直接跳过去」。**数据量越大，索引的收益越悬殊**——这也是为什么大表必须建索引、小表建了也白搭。

**辨析｜易错点：** 索引优化的是「等值查询与范围查询」，但它救不了「写法本身低效」的查询——比如在索引列上做函数运算（`WHERE UPPER(name) = 'X'`）会绕过索引。**索引是放大器，不是魔法**；查询怎么写，数据库才怎么走。

## 6 数据库设计：范式与反冗余

数据库要建得好，还得做设计。**范式（normal form）**是一套消除冗余与更新异常的设计规范，入门记前三范式的直觉即可：

- **第一范式（1NF）**：每列只存一个值，不再嵌套；
- **第二范式（2NF）**：非主键列完全依赖主键，不依赖主键的一部分；
- **第三范式（3NF）**：非主键列之间不互相依赖（不存「可以算出来的列」）。

**辨析｜易错点：** 范式不是越高越好。过高的范式化让查询要 JOIN 很多张表，反而变慢；实际工程常用「反范式化」——故意存一点冗余，换取查询少 JOIN。**范式是理论理想，反范式是工程妥协，好设计是在两者间找平衡。**<span class="marginnote">「冗余 vs 一致」的权衡会反复出现：数据库要消除冗余保一致，缓存系统却故意复制数据换速度。同一枚硬币的两面，在不同语境下各有正解。</span>

## 7 小结

- DBMS 把「存」与「用」分开，提供**统一查询、并发控制、崩溃恢复、安全**；文件存储没有这些能力。
- 关系模型用**表、行、列、主键、外键**组织数据；关系运算三件套是**选择、投影、连接**。
- SQL 是**声明式**语言：描述「要什么」，优化器决定「怎么找」；索引把全表扫描 $O(N)$ 变成沿树查找 $O(\log N)$，但索引有维护成本，不是越建越好。
- 事务的 **ACID** 四性保证并发下不犯错；设计上用**范式**消除冗余、用**反范式**换查询性能，好设计是两者的平衡。
- 选型看数据「形状」：结构化强的数据用关系表，灵活多变的用文档/键值/图模型——**先问形状，再选数据库**。
