## 为什么从计算机网络开始

前六节全部假设程序跑在**一台**机器上。但从本节起，无数台机器要彼此连接——你发一条消息，数据要穿越数台路由器、跨过大洋、在几毫秒内到达对方的手机。**计算机网络（computer network）**研究的就是「多台自治计算机如何互联通信」。

这是整条技术栈上最「大」的一层：操作系统之上的所有现代应用——Web、即时通讯、短视频、大模型 API——都建立在网络之上；而分布式系统、云计算、大数据、区块链，全部是「网络 + 机器」的组合拳。<span class="marginnote">你可能会觉得「网络」离你很远，但其实你每天都在用它的三种核心思想：<strong>协议</strong>（大家都遵守同一套规矩）、<strong>分层</strong>（每层只管自己的事）、<strong>分组</strong>（大块数据拆成小块发）。本节把这三件事讲透。</span>

## 1 网络怎么互联：节点、链路与分组交换

先立三个最基础的概念：
**节点（node）**：网络中的一台设备，可以是电脑、手机，也可以是路由器、交换机；
**链路（link）**：连接两个节点的通道，可以是有线（光纤、铜缆）或无线（Wi-Fi、蜂窝）；
**协议（protocol）**：节点之间通信必须共同遵守的规则——报文格式怎么定、谁先说话、出错怎么办。

**分组交换（packet switching）**是互联网最核心的机制：把要发送的数据切成一个个小的**分组（packet）**，每个分组独立地在网络里「逐跳」转发，到达目的地后再重组。与传统的**电路交换**（像打电话一样先占一条专线）相比，分组交换**按需共享线路**，不同用户的分组可以交错在同一条链路上传输——这叫**统计复用**，效率高得多。<span class="marginnote">分组交换的思想是把「一次大的资源占用」换成「许多小块的资源竞争」。它让网络资源几乎不被浪费，代价是每个分组都要带「源地址、目的地址」的头部开销，且可能乱序到达、需要重组——后面讲 TCP 时这两个代价都会回来。</span>

网络应用还有两种组织模式值得分清：**客户端-服务器（client-server）**模式里，服务器集中提供服务、客户端请求服务，Web 是最典型的例子；**对等（peer-to-peer，P2P）**模式里，每个节点既当客户端又当服务器，资源共享、无中心，BT 下载、区块链都属此类。<span class="marginnote">「有中心 vs 无中心」是两种哲学：中心化好管理、好计费，但有单点故障；去中心化更抗打击，但协调困难、难监管。这个权衡在分布式系统与区块链专题会被反复拉扯。</span>

**辨析｜易错点：** 分组交换 ≠ 一定要可靠。分组在路由器里可能因队列爆满被丢弃，也可能走不同的路导致乱序。**「分组交换负责尽力转发，可靠性由上层协议保证」**——这就是分层要解决的问题。

## 2 分层：把网络拆成一层层抽象

网络太复杂，没有人能同时处理「比特怎么在光纤里变成光」「IP 地址怎么路由」「网页怎么渲染」全部问题。解决办法是**分层（layering）**：每一层只依赖下一层的服务、只向上一层提供服务，层内怎么实现，别人不关心。这是本节乃至整个计算机科学最值得学会的思想之一。<span class="marginnote">分层的价值：<strong>任何一层都可以单独替换、演进</strong>。比如把底层从铜缆换成光纤，上层的 HTTP、TCP 完全无感。今天 IPv4 到 IPv6 的过渡之所以能进行，也正是因为「IP 层」被隔离在中间，上下层都不用改。</span>

两套经典模型，教科书几乎必对比：

| 层次 | OSI 七层 | TCP/IP 四层 | 例子 |
| --- | --- | --- | --- |
| 应用 | 应用层 | 应用层 | HTTP、DNS、SMTP |
| 表示/会话 | 表示层、会话层 | （并入应用层） | 加密、会话管理 |
| 传输 | 传输层 | 传输层 | TCP、UDP |
| 网络 | 网络层 | 网络层（互联网层） | IP |
| 链路 | 数据链路层 | 链路层（网络接口层） | 以太网、Wi-Fi |
| 物理 | 物理层 | （并入链路层） | 光纤、电信号 |

OSI 是理论参考模型（七层，严谨但复杂），TCP/IP 是互联网实际使用的模型（四层，实用）。教材的通行做法：先记 TCP/IP 四层，再了解 OSI 把「表示」「会话」独立出来。

**辨析｜易错点：** 「分层」不是「必须按七层逐层走」。数据在发送端是**自上而下**逐层加头（封装），接收端**自下而上**逐层去头（解封装）——中间的网络设备（路由器）只看网络层及以下，只有真正的端点才看完整的应用数据。**「封装/解封装」是理解一切抓包工具（如 Wireshark）的前提。**

## 3 网络层：IP 地址与路由

互联网层负责「把分组从源送到目的」，主角是**IP 协议（Internet Protocol）**。

**IP 地址**：给每个网络接口编一个全局可寻址的编号。IPv4 是 32 位，写成点分十进制如 `192.168.1.1`，总共约 43 亿个——早已不够用；IPv6 是 128 位，写成 `2001:0db8:85a3::8a2e:0370:7334` 这样的十六进制组，数量多到「给地球每粒沙子都能分一堆」。<span class="marginnote">「43 亿个地址不够用」催生了 NAT（网络地址转换）：家里几十台设备共用一个公网 IPv4 地址，靠端口号区分内网谁是谁。IPv6 想消灭 NAT，但「私网共享」已成惯性，过渡期漫长。你在家里路由器的后台看到的 `192.168.x.x`，就是私有地址。</span>

**路由（routing）**：分组每到一个路由器，路由器查**路由表**，决定下一跳转给谁。这有点像快递分拣：每个分拣中心只知道「往哪个方向送更近」，无需知道整个物流网络——**局部决策，全局可达**。路由表靠路由协议（如 BGP）动态维护，第三级《计算机网络》专门展开。值得注意：互联网上「你的流量走哪条路」并不是固定的——路由器会因拥塞、故障动态改道，这也是「分组交换」比「固定电路」健壮得多的地方。

**DNS（域名系统）**：人记不住 IP，于是有了「名字 → 地址」的翻译服务。`www.example.com` 经 DNS 查到一个 IP 地址，浏览器才能发请求。DNS 是全世界最大的分布式数据库之一，查询时会逐级缓存，让常用域名「秒查」。<span class="marginnote">DNS 是「把可读名字解析成机器地址」的鼻祖。同样的模式还出现在手机通讯录（名字 → 号码）与「服务发现」（服务名 → 实例地址）里——命名与寻址分离，是分布式系统的基本功。</span>

## 4 传输层：TCP 与 UDP 的分工

传输层在端到端之间提供通信服务，两大协议分工明确。先认识一个配套概念：**端口（port）**。IP 地址定位「哪台机器」，端口号定位「那台机器上的哪个进程」——一个 IP 加一个端口（如 `192.168.1.10:443`）才能唯一确定一个通信端点。

Web 服务器默认占 80（HTTP）与 443（HTTPS），所以你的浏览器只需知道域名，端口几乎从不手输——「IP 定位主机、端口定位进程」这个分工，是一切网络服务的命名基础。

**TCP（传输控制协议）**：**可靠、有序、面向连接**。发送前先**三次握手**建立连接（SYN → SYN-ACK → ACK），之后每个分组都带序号，接收方确认、缺失就重传，保证数据按序无损到达。代价是握手与确认的开销。<span class="marginnote">为什么握手要三次而不是两次？两次握手无法确认「双方都能收也能发」；三次握手还能防止「失效的旧连接请求突然到达」造成错误建立。多一次往返，买来可靠性与防错，这笔账值得。</span>

**UDP（用户数据报协议）**：**无连接、不可靠、尽力而为**。不握手、不确认、不重传，发就完了。代价是可能丢包、乱序，收益是低延迟、开销小。

| 维度 | TCP | UDP |
| --- | --- | --- |
| 连接 | 面向连接（三次握手） | 无连接 |
| 可靠性 | 确认、重传、有序 | 不保证 |
| 延迟 | 较高（有开销） | 低 |
| 典型应用 | Web、邮件、文件传输 | 视频直播、语音通话、DNS |

**辨析｜易错点：** 视频通话用 UDP 不奇怪——画面掉一帧，重传反而更卡，宁可丢一帧也不等。**「可靠」不一定是最好的，「快且可容忍丢失」也是一种工程设计**。选 TCP 还是 UDP，本质是「可靠性 vs 低延迟」的权衡。

TCP 还承担着「不让网络被自己挤爆」的职责：它用**拥塞控制**动态调整发送速率——网络好时试探着加快，检测到丢包就立刻减半退让。可以说，TCP 的每个连接都像一个「有礼貌的司机」：不抢道、遇堵就减速、路通了再逐步提速。<span class="marginnote">互联网能容纳上亿并发连接而不整体崩溃，TCP 的拥塞控制功不可没——它把「避免拥塞」的责任从路由器摊到了每个发送端。这也是网络课程里最值得细读的算法群之一。</span>

## 5 应用层：Web 与 HTTP

应用层离我们最近。**HTTP（超文本传输协议）**是 Web 的语言：浏览器发起请求（`GET /index.html`），服务器返回响应（状态码 + 内容）。`200` 表示成功，`404` 表示找不到资源，`500` 表示服务器出错。<span class="marginnote">HTTP 是无状态协议——服务器不记得上一个请求是谁发的。为此 Web 引入 Cookie：服务器发一个小凭证，浏览器存着，下次请求带上，服务器就「认得你」了。无状态 → 会话状态，这个演进是所有登录系统的地基。</span>

HTTP 的请求动词也值得认识：`GET` 只读资源（浏览器访问网页），`POST` 提交数据（登录、发帖），`PUT` 更新，`DELETE` 删除。语义清晰、各司其职，是设计 Web API 的基本盘。

**HTTPS** 是 HTTP 加上 TLS 加密：先协商密钥，再加密传输，防止中间人窃听与篡改。你地址栏的小锁图标，意味着「这条连接的内容，只有你和服务器能读懂」——它的原理会在《信息安全与隐私保护》一节详细拆解。

**辨析｜易错点：** HTTP 跑在 TCP 之上，TCP 跑在 IP 之上——这是教科书最常见的层次示例。抓包看一个 HTTPS 请求，你会看到最外层是 TCP 的三次握手与 TLS 握手，之后才是加密的应用数据。**每一次「打开网页」，都是四层协议一次完整的协作。**

## 6 公式解析：一个请求的延迟从哪里来

「网络快不快」取决于延迟，而延迟是四部分之和：

$$
\text{总延迟} = \text{传输延迟} + \text{传播延迟} + \text{排队延迟} + \text{处理延迟}
$$

逐步拆解：
- **传输延迟**：把分组「推」进链路的时间 = 分组大小 ÷ 带宽。链路越宽，这个越小。
- **传播延迟**：信号在介质里「跑」到对端的时间 = 距离 ÷ 传播速度（光纤约 $2\times10^8$ m/s，接近光速）。北京到上海约 1200 km，光在这段光纤上单程约 6 ms——**地理距离是延迟的下限，物理定律把它写死了**。
- **排队延迟**：分组在路由器队列里等待转发的时间，取决于当时的拥塞程度——四个延迟里唯一「波动大」的一项。
- **处理延迟**：路由器检查头部、查路由表、决定转发方向的时间，通常很小。

**辨析｜易错点：** 光纤快，指的是**传播延迟**小，但它并不降低**传输延迟**——把 10 GB 数据「推」进链路，100 Mbps 与 1 Gbps 的差别全在传输延迟里。**「带宽」决定一次能推多少，「延迟」决定一比特要跑多久**，两件事各管一摊，是网络学习里最容易被混为一谈的一对概念。

**算一笔账**：从上海向纽约传 100 MB 数据。光纤距离约 1.5 万公里，光往返约 15 ms 上下；若链路是 1 Gbps，传输延迟约 0.8 秒。于是「传完」主要花在传输延迟上——带宽是瓶颈；而游戏延迟、视频通话的「卡顿」，几乎全来自传播与排队——物理距离是瓶颈。**分清「瓶颈在带宽还是距离」，就能判断该升级线路还是该换服务器位置**，这正是 CDN（内容分发网络）把内容搬到离你更近的地方的原因。

## 6 小结

- 分组交换按需共享线路（统计复用），代价是带地址头、可能乱序——**可靠性交给上层协议**。
- 分层是网络的第一思想：**TCP/IP 四层 vs OSI 七层**；封装/解封装让数据逐层加头、逐层去头。
- 网络层用 **IP 地址** 寻址、路由器逐跳转发；DNS 做「名字 → 地址」的翻译。
- 传输层两大协议：**TCP 可靠有序**（三次握手、确认重传、拥塞控制），**UDP 快而尽力**（直播、语音）。
- 应用层以 **HTTP** 为代表，请求动词 GET/POST/PUT/DELETE 语义清晰；HTTPS 在 HTTP 外加一层 TLS 加密。
- 延迟四件套 = **传输 + 传播 + 排队 + 处理**；带宽决定「推多少」，延迟决定「跑多久」。
