## 为什么要自动收集无用单元

手动管理内存（malloc/free）常犯两类错误：**忘释放**（内存泄漏）与**重复/过早释放**（悬空指针）。于是有了**无用单元收集（garbage collection, GC）**：系统自动识别「再也无法被程序访问到的内存」，把它收回。GC 的核心问题只有一个：**怎样判断一块内存「没用了」？** 答案是**可达性**——从一组「根」（全局变量、栈上变量、寄存器）出发，能沿指针链到达的对象就是「活着的」，到不了的就是垃圾。本节介绍两种基本策略：**标记-清除（mark-sweep）**与**引用计数（reference counting）**，它们是 JVM、Python、CPP 智能指针的公共地基。

## 1 可达性：判定垃圾的标准

在 GC 语境里，「无用」不等于「没人显式释放」，而是**不可达（unreachable）**：

- **根（root）**：程序当前能直接访问的对象——全局/静态变量、调用栈上的局部变量、寄存器。
- **可达对象**：从根出发，沿对象的指针字段能到达的所有对象。
- **垃圾（garbage）**：不可达的对象——程序今后不可能再访问到它。

**重点：垃圾判定是「图遍历」问题——从根集出发 BFS/DFS，未访问到的结点就是垃圾。** GC 的正确性，就是把「可达性」定义与「程序语义」对齐。<span class="marginnote">「可达性判定」就是<strong>图的连通性判定</strong>：对象是顶点、指针是边、根是源点集。DFS/BFS 从根扫一遍，标记所有可达对象——<strong>数据结构的遍历，直接就是 GC 的骨架</strong>。这也解释了 GC 为什么在数据结构教材里有一席之地。</span>

## 2 标记-清除（Mark-Sweep）

两阶段算法：

**标记（mark）**：从根集出发遍历所有可达对象，给每个打上「存活」标记；
**清除（sweep）**：线性扫描整个堆，把「未标记」的对象当作垃圾回收（放入空闲表）。

```c
void Mark(Object *p) {                 /* 标记：递归标记可达对象 */
    if (p == NULL || p->marked) return;
    p->marked = TRUE;
    for (每个指针字段 f 属于 p)
        Mark(p->f);                    /* 递归标记孩子 */
}

void MarkSweep() {
    for (每个根 r) Mark(r);            /* 标记阶段：从根集出发 */
    for (堆中每个对象 p) {
        if (!p->marked) Free(p);       /* 清除阶段：未标记即垃圾 */
        else p->marked = FALSE;        /* 复位，为下一轮准备 */
    }
}
```

**重点：标记-清除是「两趟扫描」——一趟遍历图、一趟扫描堆。** 标记是「从根出发的遍历」，清除是「对全堆的线性过滤」。<span class="marginnote">标记-清除与《稀疏矩阵快速转置》的「两趟法」神似：<strong>第一趟收集信息（标记/统计），第二趟按信息落位（清除/填充）</strong>。「先统计、再处理」是线性算法的通用两步舞。</span>

## 3 公式解析：标记-清除的复杂度与缺陷

设堆中有 $n$ 个对象、可达对象为 $r$ 个：

$$
T_{\text{标记}} = O(r), \qquad T_{\text{清除}} = O(n), \qquad T_{\text{总}} = O(n)
$$

- **第一步，读标记**：遍历可达对象图，每个可达对象访问一次——$O(r)$。
- **第二步，读清除**：必须扫描全堆（$n$ 个对象）才能找出「未标记」的——$O(n)$。
- **第三步，读缺陷**：①**需要停顿**——两趟都要暂停程序（STW, stop-the-world）；②**内存碎片**——回收的空间不连续，可能还得靠下一节的「存储紧缩」；③**分配在清除时被推迟**。<span class="marginnote">「停顿」是标记-清除的头号工程问题。<strong>现代 GC（JVM、Go）用「增量标记」「并发标记」把停顿摊薄</strong>——把「两趟扫描」切成小步，穿插在程序执行间隙。算法不变，工程化把「暂停」变成了「渐进」。</span>

## 4 引用计数（Reference Counting）

另一种思路：每个对象记一个「被引用的次数」：

新建对象引用计数 = 1；
每次有新的引用指向它，计数 +1；
每次引用被删除/覆盖，计数 -1；
**计数归 0 = 无人引用 = 立即回收**。

**辨析｜易错点：引用计数管不住「循环引用」。** 若 A 指向 B、B 又指向 A，两者互相引用但外部再无引用——计数都 ≥1，永不归零，形成**内存泄漏**。**标记-清除能识别这种「环状垃圾」**（不可达即回收），引用计数不能。这是两种策略最关键的差异。<span class="marginnote">循环引用是引用计数的阿喀琉斯之踵。C++ 的 `shared_ptr` 因此配套 `weak_ptr`（不增加计数）来打破环；Python 的 GC 在引用计数之外叠加了「分代 + 标记-清除」来处理环。<strong>引用计数管「直接无人用」，标记-清除管「间接不可达」</strong>——两者常被组合使用。</span>

## 5 标记-清除 vs 引用计数

两种策略是「判垃圾时机」的两极：

| 维度 | 标记-清除 | 引用计数 |
| --- | --- | --- |
| 判定时机 | 堆满时集中扫描 | 引用变化时立即判定 |
| 垃圾判定 | 不可达（图遍历） | 计数为 0 |
| 停顿 | 需要（STW） | 无停顿（增量） |
| 循环引用 | 能处理 | 不能 |
| 额外空间 | 每对象 1 标记位 | 每对象 1 计数器 |
| 适用 | JVM、Go | Python、C++ shared_ptr、PHP |

三条规律：第一，**标记-清除「按需集中」、引用计数「实时分散」**——前者摊顿、后者摊开销。第二，**循环引用是分水岭**：凡可能成环的数据结构（图、双链表、缓存），引用计数都可能泄漏，需配合可达性方案。第三，**现代运行时常组合**：JVM 分代 + 标记-清除 + 标记-整理，Python 引用计数 + 分代 GC。<span class="marginnote">「实时 vs 批量」的取舍在计算机里无处不在：<strong>引用计数是「每个动作即时结算」，标记-清除是「定期总清算」</strong>。内存、缓存、数据库日志，都是这两种结算哲学的反复上演。</span>

## 6 小结

- 垃圾判定 = **可达性**：从根集出发遍历，不可达即垃圾——本质是图遍历。
- 标记-清除：两趟扫描（标记可达、清除垃圾），$O(n)$，需停顿、有碎片。
- 引用计数：实时增减计数，归零即回收；**无法处理循环引用**。
- 循环引用是两者分水岭：标记-清除能收环状垃圾，引用计数不能。
- 组合使用：Python（引用计数 + 分代 GC）、C++（shared_ptr + weak_ptr）。
- 现代 GC 用增量/并发标记缓解停顿。
