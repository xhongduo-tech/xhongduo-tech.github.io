## 为什么文件也能「按哈希组织」

内存哈希表靠「算地址」平均 $O(1)$ 查找。**散列文件（hash file / direct file）**把同一思想搬到磁盘：**记录的关键字经过哈希函数，直接算出它在磁盘上的桶（bucket）地址**。查找 = 算地址 + 一次桶 I/O——平均 $O(1)$，比索引文件还快。但磁盘环境给哈希提出新约束：桶是「一块或多块」的物理单位、冲突用「桶溢出链」解决、装填因子高时「文件重新组织」代价巨大。散列文件适合「等值查找为主」的场景，是数据库「哈希索引」的存储形态。

## 1 散列文件的组织

- **桶（bucket）**：一个或几个物理块组成的存储单位，是哈希地址对应的「家」；
- **哈希函数**：把关键字映射到桶号，如 `h(key) = key % B`（$B$ 为桶数）；
- **冲突解决**：一个桶装不下，用**溢出桶**（链式）承接。

查找流程：算桶号 → 读桶 → 桶内（及溢出桶链）找关键字。

**重点：散列文件的最小 I/O 单位是「桶」而非「块」——一次哈希 + 一次桶读取，就是平均查找代价。**<span class="marginnote">「桶 = 磁盘上的哈希槽」是散列文件的核心概念：<strong>桶的大小按「一次 I/O 值得读多少」设计（通常 1 块到几块）</strong>。桶太小，溢出频繁；桶太大，读多浪费。<strong>桶大小是散列文件的空间/时间旋钮</strong>。</span>

## 2 散列文件的查找与插入

**查找**：算桶号，读入该桶；桶内顺序找；不在则沿溢出链找；链尽则不存在。
**插入**：算桶号，桶内有空位则放；满则追加到该桶的溢出桶（链尾或链头）。
**删除**：找到记录，标记删除或从链上摘除。

```text
HashSearch(key):
  b = h(key)                     // 算桶号
  读入桶 b                       // 一次桶 I/O
  while 桶内未找到 key 且该桶溢出链非空:
      沿溢出链读下一个桶         // 溢出才多读一次 I/O
  return 命中记录的位置  或  「不存在」
```

**重点：散列文件的查找「平均一次桶 I/O」，最坏退化为「沿溢出链扫」（全冲突时）。** 这完全是内存哈希表的磁盘翻版——只是「桶」替代了「槽」、溢出链替代了冲突链表。<span class="marginnote">「散列文件 = 内存哈希表的磁盘版」是理解它的最短路径：<strong>槽→桶、冲突链表→溢出桶链、装填因子→桶利用率</strong>。内存哈希的一切分析（§9.10 的 ASL 公式）都可以搬过来，只是「一次访问」从内存变成了「一次磁盘 I/O」——贵得多，所以桶的利用率更需小心控制。</span>

## 3 公式解析：散列文件的查找代价

设桶数 $B$、记录 $n$ 条、平均每个桶（含溢出）装 $\alpha = n/B$ 条：

$$
ASL_{\text{成功}} \approx 1 + \frac{\alpha}{2} \quad (\text{桶内顺序找}), \qquad
T = O(\text{桶 I/O 次数})
$$

- **第一步，读「一次桶 I/O 起步」**：成功查找至少读一个桶（含记录的那个），溢出才多读。
- **第二步，读「$\alpha$ 的代价」**：$\alpha$ 是平均桶装载量，$\alpha$ 越大，桶内/溢出链越长——与链地址法哈希表的 ASL 公式同形（$1 + \alpha/2$）。
- **第三步，读「磁盘版的特殊性」**：内存里 $\alpha=1$ 很轻松；磁盘上溢出桶多一次 I/O 就贵得多，所以**散列文件的 $\alpha$ 要压得更低（如 0.5~0.7）**。<span class="marginnote">「<strong>同样的 $\alpha$，内存能忍、磁盘不能</strong>」是散列文件的关键教训：<strong>内存访问便宜，溢出链多走几步无所谓；磁盘 I/O 贵，每次溢出都是真金白银</strong>。所以散列文件宁可多留空桶（低 $\alpha$），也要减少溢出——<strong>空间换 I/O</strong>。</span>

## 4 散列文件的更新与重组

**插入**：桶内放或溢出链追加，均摊 $O(1)$ 桶 I/O——比索引文件（索引表维护）便宜；
**删除**：标记删除，简单；
**重组**：$\alpha$ 过高时，把文件「重新哈希」——桶数加倍、全部记录重算桶号——$O(n)$ 代价，但偶发可接受。

**辨析｜易错点：散列文件「不能有序遍历、不能范围查询」。** 哈希打散了物理顺序，散列文件只支持「等值查找」——按关键字区间查、按顺序扫，都不是它的菜。**有序需求 → 回到顺序/索引文件，等值需求 → 散列文件。**<span class="marginnote">「<strong>散列换不了有序性</strong>」是它的边界：<strong>哈希 ≈ 等值加速，B+树 ≈ 有序 + 范围</strong>。数据库里两者并存——<strong>主键用 B+树（支持范围），辅助等值查询用哈希索引</strong>。选索引前先问：等值多还是范围多？</span>

## 5 核心对比表：三种随机文件组织

| 维度 | 索引文件 | ISAM/VSAM | 散列文件 |
| --- | --- | --- | --- |
| 查找方式 | 索引折半 + 取记录 | B+树 / 多级索引 | 哈希计算 + 桶读 |
| 平均代价 | $O(\log m)$ + 1 I/O | $O(\log_m n)$ I/O | $O(1)$ 桶 I/O |
| 范围查询 | 支持（索引有序） | 支持（顺序集） | **不支持** |
| 插入 | 索引维护 | B+树分裂 | 桶/溢出链 |
| 适用 | 通用主键查询 | 大文件、范围 + 等值 | 等值高频 |

**重点：散列文件是「等值查找」的极致——比索引文件更快（免折半）、比 B+树更快（免树下行），但牺牲有序性。** 用它的前提很清楚：**这个文件的查询全是「按主键取记录」**。<span class="marginnote">「散列 vs 树」是数据库索引的永恒对决：<strong>等值查询多 → 哈希索引；范围/排序/前缀查询 → B+树</strong>。MySQL 的哈希索引、Redis 的哈希槽、Cassandra 的分区键，都是「散列文件思想」的分布式/数据库版本——<strong>散列文件的智慧，从未过时</strong>。</span>

## 6 可扩充哈希：从「重组」到「目录 + 桶分裂」

「$\alpha$ 太高就全部重哈希」在内存里可以接受，磁盘文件 $O(n)$ 的重组则难以承受——于是出现了**可扩充哈希（extendible hashing）**：

1. **目录（directory）**：一张含 $2^d$ 项的表，$d$ 是全局深度，每项指向一个桶；
2. **按位取址**：取关键字哈希值的低（或高）$d$ 位作为目录下标，一次目录访问定桶；
3. **桶分裂（split）**：某桶装不下时，只分裂那一个桶（该桶局部深度加一），必要时目录翻倍——**只有被分裂的桶要搬数据**。

$$

\text{分裂代价} = O(\text{被分裂桶的记录数}), \qquad \text{其余桶零成本}

$$

- **第一步，读「分裂是局部的」**：普通散列文件重组是「全部记录重算桶号」，可扩充哈希只需搬「爆掉的那个桶」。
- **第二步，读「目录翻倍」**：所有桶的局部深度一致时，分裂才需要目录翻倍；翻倍只复制指针、不搬数据。
- **第三步，读「与内存哈希的呼应」**：可扩充哈希把「文件重组」降成「桶分裂」，与内存哈希表按装载因子动态扩容（本专题《哈希表工程实现》一节）是同一思想——**用「局部搬家」替代「全量重排」，摊还成本低得多**。

**辨析｜易错点：可扩充哈希的地址是「变长的」。** 查找时先按目录（$d$ 位）取桶，桶内再按局部深度验证——同一个桶可能被多个目录项指向。**目录随数据增长而翻倍，文件总空间随之波动，但平均查找仍是「一次目录读 + 一次桶读」的 $O(1)$ 量级。**<span class="marginnote">「<strong>可扩充哈希 = 目录 + 桶分裂</strong>」是散列文件的工程化进阶：<strong>它把「偶尔全量重组」换成「频繁局部分裂」，摊还成本更低</strong>。线性哈希（linear hashing）是另一个变体——桶按顺序轮流分裂，无需目录。<strong>两者都是「把重哈希的账分期付掉」</strong>。</span>

**辨析｜易错点：散列文件 vs 索引文件的「主键查询」路径。** 索引文件要先在索引表里折半（$O(\log m)$）再取记录；散列文件一次哈希直接定位桶（$O(1)$）——等值查询散列更快。但索引文件支持「有序扫描」而散列不行。**若查询「只有等值」用散列，若有「范围 / 排序」用索引**——这是文件选型的第一问。

**术语速查表**

| 术语 | 含义 |
| --- | --- |
| 桶（bucket） | 哈希地址对应的存储单位 |
| 溢出桶链 | 桶满时的链式承接 |
| 装填因子 α | 平均每桶记录数 |
| 可扩充哈希 | 目录 + 桶分裂，局部重组 |
| 线性哈希 | 桶轮流分裂，无需目录 |

## 7 小结

- 散列文件：哈希函数算地址，记录按哈希地址入桶，冲突用溢出桶链。
- 查找：算桶号 + 一次桶 I/O，平均 $O(1)$；最坏退化沿溢出链。
- ASL ≈ $1 + \alpha/2$；磁盘上 $\alpha$ 要压更低（空间换 I/O）。
- 更新便宜（桶/溢出链）；重组 = 桶数加倍 + 全部重哈希，$O(n)$。
- **不能有序遍历、不支持范围查询**——等值查找的专用加速。
- 对比：索引/树支持有序，散列支持等值最快——按查询形态选。
