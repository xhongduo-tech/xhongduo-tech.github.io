## 为什么查找值得专门一篇

程序一半以上的时间花在「找东西」：在数组里找值、在数据库里按主键找记录、在内存里按地址找页。**查找（search）**由此成为数据结构性能的主战场——从最朴素的顺序查找 $O(n)$，到折半查找 $O(\log n)$，再到哈希表的平均 $O(1)$，每一次提升都是「用结构换时间」。本节从**静态查找表**入手：表建好后不再增删，只做「查」。第一个算法**顺序查找（sequential search）**最简单，却是「平均查找长度（ASL）」这套度量体系的起点——后续所有查找算法的优劣，都用 ASL 这把尺子量。

## 1 查找表与静态/动态之分

**查找表（search table）**：同一类型数据元素构成的集合，数据元素间松散（只求「在不在」）。

按操作分两类：

- **静态查找表（static search table）**：只做**查询**——查某元素是否存在、取它的属性。表建好后不增删。
- **动态查找表（dynamic search table）**：查询之外还要**插入与删除**——表的形态随操作变化（二叉排序树、B 树即此类）。

**重点：静态表「只查不改」，动态表「边查边改」。** 是静是动，决定选什么结构：静态用数组/索引，动态用树/哈希。<span class="marginnote">「静态 vs 动态」是查找篇的总纲：<strong>静态表可以预付一切代价做预排序、建索引；动态表则要结构本身支持增删</strong>。折半查找（下节）只能用在静态有序表上，二叉排序树则为了动态而生。</span>

## 2 顺序查找：从第一个找到最后一个

**顺序查找（sequential search）**：从表的一端开始，逐个与给定值 $key$ 比较，找到即返回位置，扫完未找到则失败。

```c
int SeqSearch(SSTable ST, KeyType key) {
    for (i = ST.length; i >= 1; i--)
        if (ST.elem[i].key == key) return i;   /* 找到，返回下标 */
    return 0;                                   /* 未找到 */
}
```

**辨析｜易错点：经典实现用「哨兵」免去越界判断。** 把 `ST.elem[0].key` 设为待查值作为哨兵，循环从尾部往前扫：

```c
ST.elem[0].key = key;                          /* 哨兵：必在表中找到 */
for (i = ST.length; ST.elem[i].key != key; i--);   /* 无需判 i 越界 */
return i;                                      /* 若 i==0 则未找到 */
```

哨兵让循环省掉每次比较 `i >= 1`——当表很长、查找频繁时，省下的比较次数相当可观。<span class="marginnote">哨兵是「<strong>用边界条件换循环开销</strong>」的经典：<strong>在数组头/尾放一个必定命中的值，让循环条件少一个判断</strong>。它是程序设计里最古老也最有效的微优化之一——只为一个「循环更短」。</span>

## 3 公式解析：顺序查找的平均查找长度

**平均查找长度（ASL, Average Search Length）**：查找成功时，平均比较次数。

设表长 $n$，每个元素查找概率相等（$1/n$），第 $i$ 个元素需比较 $i$ 次：

$$
ASL_{\text{成功}} = \sum_{i=1}^{n} p_i c_i = \frac{1}{n}\sum_{i=1}^{n} i = \frac{n+1}{2}
$$

- **第一步，读 $c_i = i$**：从表头扫到第 $i$ 个元素，恰好比较 $i$ 次。
- **第二步，读求和**：等概率下，成功查找平均要比较 $\frac{n+1}{2}$ 次——**约表长的一半**。
- **第三步，读失败情形**：未找到要比较 $n+1$ 次（含与哨兵的那次）。若把「失败查找」也算进来，代价更高。<span class="marginnote">「平均比较表长一半」是顺序查找的天花板——<strong>它不利用任何结构信息，无论数据多么有序</strong>。这个「$O(n)$ 天花板」正是折半查找、哈希表存在的理由：它们通过「利用有序性」或「直接计算地址」突破线性墙。</span>

## 4 核心对比表：静态表的三种查找方法预览

静态查找表上有三种典型方法，本节起逐一展开，先给全景：

| 方法 | 前提 | 平均查找长度 | 特点 |
| --- | --- | --- | --- |
| 顺序查找 | 无 | $O(n)$，$(n+1)/2$ | 最简单，表无序可用 |
| 折半查找 | 表有序 | $O(\log n)$ | 利用有序性，需随机存取 |
| 分块查找 | 块间有序 | $O(\log m + s/2)$ | 折中：块内无序、块间有序 |

三条规律：第一，**「数据的有序性」是查找提速的第一桶金**——有序表的折半查找直接把 $O(n)$ 降到 $O(\log n)$。第二，**静态表的查找方法不增删数据**，因此能承受「预排序」的一次性成本。第三，**三者共用「ASL」这把尺子**——后面所有动态结构（二叉排序树、B 树、哈希）的优劣，都换算成 ASL 来比较。<span class="marginnote">「先定尺子，再量算法」是本节的方法论：<strong>ASL 让「哪个查找方法更好」从感觉变成数值</strong>。有了这把尺子，二分 5 次、顺序 500 次、哈希 1 次，一比较高下立判——查找篇后面全是这个框架。</span>

## 5 从顺序查找到更大的图景

顺序查找虽慢，却是「无结构数据」下唯一的选择，也是一切查找的兜底。它的「逐个比较」思想，在以下场景依然活跃：

- **无序小表**：$n$ 小的时候，顺序查找的常数极小，实际不输复杂算法；
- **链表上的查找**：链表无法随机存取，折半查找派不上用场，只能顺序；
- **暴力匹配的基础**：串的朴素匹配、图的无序搜索，都是「逐个试」。

**重点：学会顺序查找，是学会「识别哪些数据可以跳过」的前提**——折半查找「每次跳过一半」、哈希「直接跳过」，都是在顺序查找的「逐个」基础上加速。<span class="marginnote">「加速 = 跳得更多」是一条贯穿查找篇的红线：<strong>顺序找「不跳」，折半「跳一半」，分块「先跳块」，哈希「一步到位」</strong>。记住这条线，你就能把后面所有查找方法串成一条进化链。</span>

## 6 小结

- 查找表分**静态**（只查）与**动态**（边查边改），决定结构选型。
- 顺序查找：逐个比较，表无序可用；哨兵优化循环。
- ASL（成功，等概率）= $(n+1)/2$，约表长一半。
- 失败查找要比较 $n+1$ 次。
- 查找加速的实质 = 「跳得更多」：顺序→折半→分块→哈希。
- ASL 是度量一切查找方法的统一尺子。
