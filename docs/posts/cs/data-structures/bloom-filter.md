# 布隆过滤器

## 为什么需要「概率性」的集合

判断「一个元素在不在集合里」——哈希表 $O(1)$，但一个元素要存整个 key（几十字节）。当集合有几十亿元素、还分布在分布式系统里，「精确存储」的空间与查询成本难以承受。**布隆过滤器（Bloom filter）**用「**位数组 + 多个哈希函数**」回答「在不在」，每个元素只占几个**比特**，且查询是「可能在，或者一定不在」：

- **若返回「不在」：一定不在**（不漏报）；
- **若返回「在」：可能误报**（有假阳性，无假阴性）。

它用「**可控的误报率**」换「**极致的小空间**」——是缓存穿透防护、URL 去重、分布式系统的「存在性预判」标配。**布隆过滤器 = 哈希思想在「成员判断」上的空间革命。**

## 1 布隆过滤器的原理

设位数组长度 $m$、$k$ 个独立哈希函数。插入元素 $x$：

1. 计算 $k$ 个哈希值 $h_1(x), h_2(x), \cdots, h_k(x)$；
2. 把这 $k$ 个位置在位数组里**全部置 1**。

查询元素 $y$：

1. 计算同样 $k$ 个哈希值；
2. 若**任一**位置为 0 → $y$ **一定不在**（该位从未被插入置过 1）；
3. 若**全部**位置为 1 → $y$ **可能在**（也可能是其他元素「恰好」把这些位置都置了 1）。

```c
void Insert(BitSet *B, int x) {
    for (i = 0; i < k; i++) set_bit(B, h[i](x));   /* k 个位置全部置 1 */
}
int Query(BitSet *B, int x) {
    for (i = 0; i < k; i++)
        if (!get_bit(B, h[i](x))) return NOT_EXIST; /* 任一为 0：一定不在 */
    return POSSIBLY_EXIST;                          /* 全为 1：可能在 */
}
```

**重点：布隆过滤器不做「精确比较」，只问「这些位是不是都被碰过」。** 置 1 操作是「累积」的——多个元素共享位，所以有假阳性；但查询时「任一位置 0」能铁证「不在」——所以无假阴性。<span class="marginnote">「<strong>置 1 只增不减 → 只有假阳性、没有假阴性</strong>」是布隆过滤器的最关键性质：<strong>位被置 1 后就再也不会变回 0（除非删除支持）</strong>。因此「某位置 0」意味着「从来没有任何已插入元素碰过它」——查询元素若需要这个位而它是 0，则必不在。<strong>这个「单向累积」是不漏报的根源</strong>。</span>

## 2 公式解析：误报率与参数

设 $n$ 个元素、位数组 $m$ 位、$k$ 个哈希函数。误报率（假阳性率）近似：

$$
f \approx \left(1 - e^{-kn/m}\right)^k
$$

- **第一步，读「$kn/m$」**：$kn$ 是总置位次数，除以 $m$ 得「平均每个位被置的次数」，$e^{-kn/m}$ 是「某位仍为 0」的概率。
- **第二步，读「$1 - e^{-kn/m}$」**：某位为 1 的概率；$k$ 次全为 1 的概率 = 误报率。
- **第三步，最优参数**：给定 $m$、$n$，使 $f$ 最小的哈希函数数 $k^* = (m/n)\ln 2$，此时 $f_{\min} \approx 0.6185^{m/n}$。**想让误报率降到 $1\%$，每个元素约需 $9.6$ 位。**<span class="marginnote">「$k^* = (m/n)\ln 2$、每位元素约 9.6 位达到 1% 误报」是布隆过滤器的两个工程常数：<strong>「1% 误报 / 9.6 位每元素」让空间代价可预测</strong>。对比存整个 key（几十字节），布隆过滤器省了 1~2 个量级——<strong>这就是「用误报换空间」的量化账单</strong>。</span>

## 3 布隆过滤器 vs 哈希表

| 维度 | 哈希表 | 布隆过滤器 |
| --- | --- | --- |
| 存储 | 完整 key | 位数组（每元素几位） |
| 误判 | 无 | **有假阳性、无假阴性** |
| 删除 | 支持 | **不支持**（或需计数布隆） |
| 空间 | 大 | 极小 |
| 查询 | 精确 | 概率性 |
| 适用 | 需要取回元素 | 只问「在不在」 |

**重点：布隆过滤器不存数据本身——它只存「足迹」。** 需要「取出元素」用哈希表，只问「存在与否」用布隆过滤器。二者常配合：布隆过滤器先挡掉「一定不在」的查询，命中的再去查真实存储。<span class="marginnote">「先布隆、后真实存储」是经典的缓存穿透防护：<strong>查询先过布隆过滤器，「不在」直接拒绝（省掉数据库访问）；「可能在」才真正查库</strong>。命中误报最多浪费一次查询，漏报则完全不可能——<strong>把最贵的查询用最便宜的结构挡在前面</strong>。</span>

## 4 变体与限制

- **计数布隆过滤器（counting Bloom filter）**：每个位换成计数器，支持删除（减计数）——但空间增大几倍；
- **可伸缩布隆过滤器（scalable BF）**：元素变多时，动态增加位数组（分层），控制误报率不涨；
- **限制一：不能删除**——普通布隆过滤器的置 1 不可逆；
- **限制二：不能枚举**——不知道「具体哪些元素在」。

**辨析｜易错点：布隆过滤器的误报率会随插入增长。** 插入越多，位数组中 1 越密，假阳性越高。**必须按「预期最大元素数」设计 $m$**——插多了误报率就失控。<span class="marginnote">「<strong>误报率随插入增长</strong>」让布隆过滤器必须「按峰值设计」：<strong>$m$ 按最大预期 $n$ 定，而不是按当前 $n$ 定</strong>。这与哈希表「装填因子到了就扩容」不同——布隆过滤器不能简单扩容（已置的位无法重哈希），所以「<strong>一开始就给够空间</strong>」是设计铁律。</span>

## 5 布隆过滤器的应用

- **缓存穿透防护**：Redis 前的「存在性预判」，挡住不存在的 key 打穿缓存；
- **URL 去重 / 爬虫**：判断 URL 是否已抓取，空间比哈希集合省一个量级；
- **垃圾邮件 / 内容过滤**：黑名单成员判断；
- **分布式系统**：HBase、Cassandra 用布隆过滤器加速「行是否存在」的判断，减少磁盘 I/O；
- **大模型 RAG 去重**：判断文档/块是否已被索引。

**重点：凡是「问一句『在不在』就能省一大笔查询/空间」的场景，布隆过滤器都值得考虑**——它把「存在性」这一最基础的问题，做到了空间与时间的极致。<span class="marginnote">「布隆过滤器是『<strong>空间换时间、误报换空间</strong>』的三重交易」——<strong>一个元素几比特、一次查询几个哈希、可控的误报率</strong>。从「精确」到「概率」的这一步退让，换来的是在大数据量级上的可行性——<strong>在大数据场景，「够好」常常比「精确」更值钱</strong>。</span>

## 6 小结

- 布隆过滤器：位数组 + $k$ 个哈希函数；插入全置 1、查询全 1 才「可能在」。
- 无假阴性、有假阳性；误报率 $f \approx (1 - e^{-kn/m})^k$。
- 最优 $k^* = (m/n)\ln 2$；1% 误报约需 9.6 位/元素。
- 不存数据、不能删除、不能枚举；按峰值设计 $m$。
- 与哈希表配合：布隆挡「一定不在」，真实存储处理「可能在」。
- 应用：缓存穿透防护、URL 去重、HBase/Cassandra 加速、RAG 去重。
