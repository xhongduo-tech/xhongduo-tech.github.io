## 为什么 Redis 的 ZSET 用跳表不用红黑树

**ZADD 要按 score 排序、ZRANGE 要按序输出、ZSCORE 要按成员查**——有序集合（ZSET）的所有操作，红黑树和跳表都能做。但 Redis 的源码注释明确写着：「跳表比平衡树实现简单、调试容易、且期望复杂度相同，还天然支持范围查询的相邻遍历」。本节把跳表与平衡树做**工程级**对比，并拆解 Redis 选跳表的五个理由——它是「数据结构选型」的经典案例分析，结论就是那句：「**同样能行的时候，选更简单的**」。

## 1 功能对比：都能做什么

| 操作 | 跳表 | 红黑树 |
| --- | --- | --- |
| 查找 key | 期望 $O(\log n)$ | $O(\log n)$ |
| 插入 / 删除 | 期望 $O(\log n)$ | $O(\log n)$ |
| 找最小 / 最大 | $O(\log n)$（最左/最右） | $O(\log n)$ |
| 有序遍历 | 底层链从头到尾 $O(n)$ | 中序 $O(n)$ |
| 找前驱 / 后继 | $O(\log n)$（层内移动） | $O(\log n)$ |
| 区间查询 | **天然支持**（底层链扫区间） | 需中序部分遍历 |

**重点：两者的功能几乎重叠，唯独「区间查询」跳表占优**——底层的完整有序链表让「从某处开始扫一段」直接高效；红黑树做区间扫描要走中序，代码更绕。<span class="marginnote">「<strong>区间查询是跳表的隐藏优势</strong>」：<strong>ZRANGE 就是「从底层链的某个位置开始顺序走」，跳表一句话就能实现；红黑树做同样的事要维护中序游标</strong>。<strong>「底层链」让跳表天然是「有序集合 + 顺序扫描」二合一</strong>。</span>

## 2 实现复杂度对比：跳表碾压

**红黑树**：插入 5 条性质、删除 4 类兄弟情形、旋转 + 变色——**实现约 300~500 行，Bug 高发**；
**跳表**：插入 = 查位 + 抛硬币 + 逐层插；删除 = 查位 + 逐层摘——**实现约 100 行，几乎无状态机**。

**重点：跳表的「无旋转、无染色、无情形表」让实现与调试成本低一个量级。** 对「追求正确性 > 极致性能」的系统（Redis），这个优势是决定性的。<span class="marginnote">「<strong>实现的简单性，是最被低估的工程价值</strong>」：<strong>红黑树的删除有 4 类情形、每类又有对称版，极易写错；跳表没有情形，逻辑线性展开</strong>。<strong>「同样性能、一半代码」</strong>——Redis 作者的选择很务实：少 300 行易错代码，比省那一点常数重要得多。</span>

## 3 复杂度保证：确定 vs 期望

| 维度 | 红黑树 | 跳表 |
| --- | --- | --- |
| 平衡机制 | 确定性（旋转 + 染色） | 概率性（随机层数） |
| 最坏查找 | $O(\log n)$ 铁保 | $O(n)$ 理论、概率 $2^{-n}$ |
| 平均查找 | $O(\log n)$ | 期望 $O(\log n)$ |
| 退化风险 | 无 | 可忽略 |

**重点：红黑树「铁保」、跳表「概率保」——但对任何实际输入，跳表的退化概率可忽略。** 这就是「同样能行」的含义：**期望性能相同，而跳表的「几乎一定 $O(\log n)$」在工程里等于 $O(\log n)$**。<span class="marginnote">「<strong>可忽略的概率 = 实际的保证</strong>」是工程对随机化的宽容：<strong>$2^{-n}$ 的退化概率，比 CPU 位翻转概率还低——工程上没人会为它买单</strong>。<strong>所以跳表的「期望」在工程语境里可以当「保证」用</strong>，而它换来的实现简单是实打实的。</span>

## 4 Redis 选跳表的五个理由

1. **实现简单、调试容易**——比红黑树短一大截，不易出 Bug；
2. **期望复杂度与平衡树同级**——都是 $O(\log n)$，常数也可接受；
3. **天然支持范围查询**——ZRANGE 靠底层链顺序扫；
4. **并发友好**——跳表可无锁/细粒度，Redis 虽单线程但思路一致；
5. **可定制性**——跳表的层结构便于扩展（如支持 rank、自定义打分）。

**重点：Redis 的选型逻辑是「在性能达标的前提下，选最简单的」**——跳表满足了 $O(\log n)$ 的性能底线，又在实现、范围查询、可维护性上全面占优，红黑树没有赢的理由。<span class="marginnote">「<strong>Redis 的答案是『够用 + 简单』</strong>」：<strong>它不需要红黑树的确定性最坏保证（概率退化可忽略），更需要跳表的短代码与范围查询</strong>。<strong>选型不是「谁最强」，而是「谁最合适」</strong>——Redis 的注释里那句「他们也许是对的」耐人寻味，工程选择永远带着取舍。</span>

## 5 跳表 vs 平衡树的选型指南

| 场景 | 选谁 |
| --- | --- |
| 需要确定性的最坏保证（内核、实时系统） | 红黑树 |
| 要简单可维护、能接受概率保证 | 跳表 |
| 范围查询 / 有序扫描频繁 | 跳表（底层链） |
| 并发读写下，无锁实现 | 跳表 |
| 查多写少的严格平衡 | AVL |
| 语言标准库的有序容器 | 红黑树（std::map） |

**重点：选型的判断顺序是「先看最坏要求，再看实现成本」**——内核要铁保选红黑树；应用层要省心选跳表；两者都不绝对，看负载与团队。<span class="marginnote">「<strong>数据结构选型 = 需求清单 × 实现预算</strong>」：<strong>把「最坏要求、范围查询、并发、代码量、团队熟练度」列成清单，对着表勾选</strong>。<strong>没有「最好」，只有「在你的约束下最合适」</strong>——这是整门数据结构课的元结论，跳表 vs 红黑树只是它的一次具体演绎。</span>

## 6 小结

- 功能重叠：查找、增删、极值、遍历双方都能 $O(\log n)$。
- 区间查询跳表占优（底层链顺序扫）。
- 实现：跳表 ~100 行、红黑树 300~500 行且易错。
- 保证：红黑树确定性、跳表概率性（退化 $2^{-n}$ 可忽略）。
- Redis 选跳表五理由：简单、同级性能、范围查询、并发、可定制。
- 选型顺序：先看最坏要求、再看实现成本——「够用 + 简单」常常胜出。
