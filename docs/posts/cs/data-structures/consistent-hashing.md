## 为什么分布式分片不能「简单取模」

单机哈希表 `hash(key) % N` 好用，但分布式缓存/存储里，$N$ 是**结点数、会变**。$N$ 从 4 变成 5，`hash(key) % 5` 与 `hash(key) % 4` 几乎对每个 key 都不同——**绝大多数数据要搬家**。缓存一旦大规模重映射，就是「缓存雪崩」。**一致性哈希（consistent hashing）**把 key 与结点都映射到同一个「哈希环」上，key 归「顺时针遇到的第一个结点」管。结点增减时，**只有环上相邻的一小段 key 需要搬家**——重映射量从「几乎所有」降到「1/N」。一致性哈希是 Memcached 分片、分布式数据库分片、负载均衡的经典方案。

## 1 哈希环与虚拟结点

**一致性哈希**的做法：

1. 把哈希函数的输出空间（如 $0 \sim 2^{32}-1$）看成一个**首尾相接的环**；
2. 把每个结点（服务器）用 `hash(结点标识)` 放到环上；
3. 每个 key 用 `hash(key)` 算出环上的位置，沿**顺时针**找到第一个结点，它就是这个 key 的「主人」。

**重点：key 的归属由「环上的顺时针最近结点」决定——这是一致性哈希的全部规则。**<span class="marginnote">「<strong>环 + 顺时针</strong>」把「$N$ 个槽」变成「$N$ 个点」：<strong>取模哈希的槽是「整数区间」，一致性哈希的槽是「环上的弧段」</strong>。每个结点负责「从它逆时针到上一结点」之间那段弧的 key——<strong>弧段是连续的，所以移动是局部的</strong>。</span>

## 2 结点增减时的「最小重映射」

加入一个结点、删除一个结点，影响范围多大？

- **取模哈希**：$N \to N+1$，几乎所有 key 的归属都变；
- **一致性哈希**：新增结点 $P$ 落在环上某处，只有「顺时针归 $P$ 的那一小段弧」上的 key 从原结点迁到 $P$——**平均影响 $1/(N+1)$ 的 key**。

**公式解析：一致性哈希的重映射比例**

$$
\text{重映射比例} \approx \frac{1}{N} \qquad \text{（每个结点负责环的 } 1/N \text{）}
$$

- **第一步，读「$1/N$」**：环被 $N$ 个结点均分，每个结点管 $1/N$ 的弧段。增删一个结点，只影响它相邻的弧段。
- **第二步，读「与取模的对比」**：取模是「$1 - 1/N$」几乎全部；一致性哈希是「$1/N$」——差距随 $N$ 放大。
- **第三步，读「为什么好」**：缓存场景里，重映射 = 缓存失效 + 回源打库。$1/N$ 的重映射让「增删结点」从「雪崩事件」变成「局部扰动」。<span class="marginnote">「$1/N$ vs $1-1/N$」是分布式分片的两种命运：<strong>取模哈希增结点等于「推倒重来」，一致性哈希增结点等于「局部微调」</strong>。这个差异在缓存、数据库分片、负载均衡里，决定了一次扩缩容是「灾难」还是「例行维护」。</span>

## 3 虚拟结点：解决「不均」与「雪崩」

朴素一致性哈希有两个问题：

1. **结点分布不均**：结点少时，哈希随机落点可能让某些结点管很大一段弧，负载不均；
2. **热点雪崩**：某结点故障，它的 key 全部顺时针压给下一结点，下一结点可能被压垮（连锁雪崩）。

**解法：虚拟结点（virtual node）**——每个物理结点在环上放「多个」哈希位置（如每个结点 100~200 个虚拟点），key 归属按「顺时针遇到的第一个虚拟点」判：

- **负载更均匀**：虚拟点让每个物理结点的「弧段」更接近等分；
- **雪崩可分担**：一个物理结点故障，它的虚拟点把 key 分散给「多个」顺时针邻居，而不是压给一个结点。<span class="marginnote">「虚拟结点 = <strong>用随机抽样近似均匀</strong>」：<strong>每个物理结点放 $k$ 个虚拟点，环上点越多，各结点弧段越接近 $1/N$</strong>。这就像「抛硬币次数越多越接近 1/2」——<strong>用冗余的随机位置，逼近均匀的负载</strong>。</span>

## 4 一致性哈希 vs 取模哈希

| 维度 | 取模哈希 `%N` | 一致性哈希 |
| --- | --- | --- |
| 重映射比例 | $1 - 1/N$（几乎全部） | $1/N$（局部） |
| 负载均衡 | 天然均匀（槽均分） | 依赖虚拟结点 |
| 实现 | 极简 | 环 + 虚拟点，稍复杂 |
| 结点增减 | 灾难性重排 | 局部重排 |
| 适用 | 结点固定的静态场景 | 结点频繁增减的分布式 |

**重点：静态定长用取模、动态伸缩用一致性哈希。** 单机哈希、固定集群用取模最简单；云环境、缓存集群、自动扩缩容必须一致性哈希。<span class="marginnote">「静态 vs 动态」的分野再次出现：<strong>取模是「数组式分片」（槽固定），一致性哈希是「链表式分片」（点可插拔）</strong>。数据结构的「静态/动态」哲学，直接决定分布式系统「能不能平滑扩容」。</span>

## 5 一致性哈希的应用全景

- **分布式缓存**：Memcached/Redis 集群的 key 分片——增删缓存结点不必全量重排；
- **分布式数据库**：数据分片（shard）的定位——Cassandra、Dynamo 的「环」架构直接源自一致性哈希；
- **负载均衡**：把「请求 hash 值」映射到后端结点——同一用户始终打到同一后端；
- **P2P 网络**：DHT（分布式哈希表）——Chord 协议的一致性哈希变体。

**重点：一致性哈希是「分布式哈希表（DHT）」的核心数据结构**——把「key → 结点」的映射做成可伸缩、可容错的环。它是「从极限到大模型」主线上，数据结构在「分布式」这个量级的直接延伸。<span class="marginnote">「从单机哈希到一致性哈希」是「<strong>数据结构的横向扩展</strong>」：<strong>单机哈希表 → 槽固定；分布式哈希 → 环可伸缩</strong>。大模型训练的分布式参数存储、推荐系统的特征分片，背后都是这套「环 + 虚拟结点」的智慧——<strong>哈希结构并没有变，变的是「槽」从数组变成了环</strong>。</span>

## 6 小结

- 一致性哈希：key 与结点都上「哈希环」，key 归顺时针第一个结点。
- 重映射比例 ≈ $1/N$——增删结点只影响局部弧段，远优于取模的 $1-1/N$。
- 虚拟结点：每物理结点多个哈希点，负载更均、故障可分担。
- 取模适合静态定长，一致性哈希适合动态伸缩。
- 应用：分布式缓存、数据库分片、负载均衡、DHT/Chord。
- 「槽从数组变环」是哈希结构的横向扩展。
