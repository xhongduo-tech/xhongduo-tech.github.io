## 为什么需要「按属性」查询

前面所有文件组织都按**主关键字**（唯一键）组织——查学号很快，查「性别 = 男」却要全表扫。**多关键字文件（multi-keyword file）**解决「按次关键字/属性查询」：为每个常用属性建索引，把「具有某属性值的记录」组织成链表或倒排表。它的两种形态——**多重表文件**（属性值链 + 主索引）与**倒排文件**（属性值 → 记录号集合）——是现代**数据库二级索引**与**搜索引擎倒排索引**的直接祖先。学完本节，数据结构课程的「文件」篇收官，而「按属性检索」这一互联网核心能力的故事才刚刚开始。

## 1 次关键字索引：为什么一个索引不够

一条记录有多个字段：学号（主关键字）、专业、性别、入学年份（次关键字）。查询可能按任意字段发起：

- 按学号查 → 主关键字查询，主索引足够；
- 按专业查 → 次关键字查询，需要「专业」的索引；
- 按「专业 + 性别」查 → **多关键字**组合查询。

**重点：每个常用次关键字都要一个索引——「按什么查，就建什么索引」。** 这是多关键字文件的出发点，也是数据库「二级索引」的设计原则。<span class="marginnote">「<strong>查询的属性 = 需要的索引</strong>」是一条工程铁律：<strong>建索引不是越全越好，而是「按查询模式建」</strong>。为每个属性都建索引，插入删除要维护的索引就爆炸——所以「常见查询用索引，冷门查询用扫描」。这个权衡贯穿数据库索引设计。</span>

## 2 多重表文件

**多重表文件（multilist file）**：为主关键字建主索引，为每个次关键字建「**属性链表**」——把所有「同属性值」的记录用链指针串起来：

记录中为每个次关键字设一个「链指针域」；
属性索引表：每个「属性值」一项，存该值的链头地址；
查「专业 = 计算机」：查属性索引 → 得链头 → 沿链扫出全部计算机专业记录。

```text
属性索引表「专业」：                    记录内嵌「专业链」指针：
  计算机   → 记录3 ─┐             记录3 ─→ 记录7 ─→ 记录12 ─→ NULL
  软件工程 → 记录1 ─┤             （同专业链，从链头一路扫）
  ...
```

**重点：多重表文件用「记录内嵌链指针」把同属性记录串成链，查属性 = 查链头 + 沿链扫。** 一条记录可能同时在多个属性链上（专业链 + 性别链）——链指针域的数量 = 次关键字的数量。<span class="marginnote">多重表文件的「<strong>链指针内嵌</strong>」让「按属性取记录」成为可能，但也带来代价：<strong>每个属性链都要在记录里占一个指针域，插入删除要同时维护所有链</strong>。属性越多，记录越大、维护越贵——这是「索引不免费」的直观体现。</span>

## 3 倒排文件

**倒排文件（inverted file）**：不把链指针嵌在记录里，而是**单独建表——「属性值 → 记录号集合」**：

```text
倒排表（属性值 → 记录号集合）：
  专业 = 计算机   → {3, 7, 12}
  专业 = 软件工程 → {1, 5}
  性别 = 男       → {1, 3, 7, 9}
  性别 = 女       → {2, 5, 12}
```

查找「专业 = 计算机 且 性别 = 男」：取两个集合 {3,7,12} ∩ {1,3,7,9} = {3,7}，直接得结果记录号。

**重点：倒排文件的关键操作是「集合求交」**——多个属性的倒排表取出记录号集合，做交/并运算，快速得到满足组合条件的记录。这就是搜索引擎「关键词 AND 关键词」的底层机制。<span class="marginnote">「倒排」一词的含义：<strong>正常索引是「记录 → 属性值」，倒排表是「属性值 → 记录号集合」——方向反过来</strong>。搜索引擎的倒排索引（词 → 文档列表）正是由此得名。<strong>「属性值 → 记录集合」这个翻转，让「按内容找文档」成为可能</strong>。</span>

## 4 公式解析：倒排文件的组合查询

设两个属性的命中集合为 $A$、$B$（记录号集合），组合查询「同时满足」为求交：

$$
A \cap B: \quad T = O(|A| + |B|) \quad \text{（双指针归并求交）}
$$

- **第一步，读「集合求交」**：两个有序记录号集合，双指针一趟归并（像归并排序的 Merge），代价 $O(|A|+|B|)$。
- **第二步，读「与全表扫对比」**：全表扫要 $O(n)$ 次 I/O；倒排只需读两个倒排表项（2 次 I/O）+ 求交——**当命中集远小于全表时，倒排碾压全扫**。
- **第三步，读「交集的代价比例」**：$|A|+|B|$ 比 $n$ 小多少，倒排就快多少——**这是「倒排快」的量化来源**。<span class="marginnote">「求交快 ⇔ 命中集小」是倒排的适用条件：<strong>属性选择性强（命中少）时倒排极其高效；选择性强弱 = 属性值的区分度</strong>。搜索引擎的关键词大多命中少，所以倒排是它的不二选择；若查询命中大半张表，全表扫反而更划算。</span>

## 5 核心对比表：多重表文件 vs 倒排文件

| 维度 | 多重表文件 | 倒排文件 |
| --- | --- | --- |
| 结构 | 记录内嵌链指针 + 属性链头索引 | 独立倒排表（属性值→记录号集合） |
| 记录冗余 | 每条记录多若干指针域 | 记录本身无额外域 |
| 组合查询 | 多条链同步遍历 | 集合求交 |
| 修改维护 | 链指针同步更新 | 倒排表项增删 |
| 典型应用 | 早期数据库 | 搜索引擎、全文检索 |

**重点：倒排文件用「独立的倒排表」换「记录零冗余 + 集合运算」**——是现代主流（搜索引擎）的选择；多重表文件作为经典形态，其「按属性链」思想仍活在数据库的某些索引里。<span class="marginnote">「<strong>冗余内嵌 vs 独立索引</strong>」是索引设计的根本二选一：<strong>内嵌链指针省查询但涨记录、独立倒排表零冗余但多维护</strong>。现代系统几乎全选「独立索引」（B+树、倒排表）——因为「记录要瘦、索引可肥」是存储系统的基本审美。</span>

## 6 小结

- 多关键字文件：为每个常用次关键字建索引，支持按属性查询。
- 多重表文件：记录内嵌链指针，属性值 → 链头 → 沿链扫。
- 倒排文件：独立倒排表「属性值 → 记录号集合」，组合查询 = 集合求交。
- 求交代价 $O(|A|+|B|)$，命中集小时碾压全表扫。
- 倒排是搜索引擎的底层机制（词 → 文档列表）。
- 设计权衡：内嵌冗余 vs 独立索引——现代系统选独立索引。
