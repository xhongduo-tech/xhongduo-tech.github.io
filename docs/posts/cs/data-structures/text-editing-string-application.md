## 为什么用文本编辑当例子

前面几节把串的定义、存储、匹配都讲完了——它们到底合起来能干什么？**文本编辑**是最自然的回答。一段文档不是一长条无法管理的字符流，而是**按行组织的串**：每行是一个串，行与行之间又构成一个线性表。光标定位、查找替换、插入删除，全都落在「行表 + 每行的串」这两层结构上。严蔚敏教材用这个例子，把「串的存储 + 模式匹配 + 线性表」三块知识缝合成一个真实系统。它也预告了现代编辑器（Vim、VS Code）背后的基本数据组织。

## 1 文本编辑器的数据组织：行表

整个文本被组织成一张**行表（line list）**：表的每一行是一个串（一行的内容），行表本身是这些串的线性表。

```c
typedef struct {
    char *content;   /* 一行文本（一个串） */
} Line;

typedef struct {
    Line *lines;     /* 动态数组，每个元素指向一行 */
    int   n;         /* 当前行数 */
    int   cap;       /* 容量 */
} LineList;
```

行表可以用顺序存储（一个数组，每个元素指向一行的字符串），也可以用链式存储（每行一个结点）。选哪种，取决于编辑操作的特点：

- **随机跳到第 $k$ 行**：顺序行表 $O(1)$，链式行表需遍历 $O(k)$。
- **在任意位置插入/删除一行**：顺序行表需整体移动后续行指针，链式行表改指针即可。

实际编辑器多采用「**行块 + 指针**」的折中：行表用动态数组存指针，每行内容独立分配。数组支持快速定位行号，行内容按需伸缩。<span class="marginnote">现代编辑器（如 VS Code）底层常用<strong>分片串（piece table）或 rope</strong>：把文档切成若干「片段」，片段之间用树或链表组织。频繁的编辑只增删片段、不复制大段文本。这是「行表」思想在超大型文件上的进化。</span>

## 2 编辑操作如何落到串运算

文本编辑的每条命令，都翻译成行表与串上的一组操作：

| 编辑命令 | 底层操作 |
| --- | --- |
| 光标移动到第 $k$ 行第 $c$ 列 | 行表定位 + 串内偏移 |
| 插入一段文字 | 在当前行串中插入子串，或分裂成两行 |
| 删除几个字符 | 当前行删除子串 |
| 查找单词 | 当前行 / 全文串匹配（模式匹配） |
| 替换单词 | 模式匹配找位置 + 删除子串 + 插入子串 |
| 删除一行 | 行表删除该行结点 |

**重点：编辑器的「每一次按键」，最终都递归地落到「串的插入/删除/查找」这三个原语上。** 所以串运算的实现质量，直接决定编辑器的流畅度。<span class="marginnote">这就是「抽象数据类型的威力」：编辑器开发者只需要知道「行」是一个支持插入删除查找的串，不需要关心它底层是定长数组还是 rope。接口稳定，实现可换——绪论里 ADT「接口与实现分离」思想的落地。</span>

## 3 公式解析：行表 + 串的位置换算

行式文本的定位，本质是「二维坐标 ↔ 一维偏移」的换算。设光标在第 $k$ 行（从 1 起）第 $c$ 列（从 1 起），各行的长度为 $L_1, L_2, \cdots$，则该位置在整个文本流中的全局偏移为：

$$
\text{offset} = \sum_{i=1}^{k-1} L_i + (c - 1)
$$

- **第一步，读第一项 $\sum_{i=1}^{k-1} L_i$**：它累加前 $k-1$ 行的全部字符数，把光标带到第 $k$ 行的行首。
- **第二步，读第二项 $c-1$**：行内从列 1 到列 $c$ 之间还有 $c-1$ 个字符，加上即得全局位置。
- **第三步，体会「为什么不用存全局偏移」**：编辑器保存的是「行号 + 列号」，每次换算都现场求和——因为编辑会频繁改变行长度，若缓存全局偏移，任何一行改动都会让后续所有偏移失效。**存「行 + 列」的二维坐标，是让局部编辑不必波及全局的关键。**<span class="marginnote">「<strong>局部坐标不因局部编辑而失效</strong>」是文本编辑数据组织的核心不变量。它和数据库里的「相对引用」、文档里的「锚点」是同一思想：能不用绝对位置就不用绝对位置。</span>

## 4 查找替换：模式匹配的用武之地

全文查找 = 从第 1 行到最后一行，逐行做串的模式匹配；找到后若需**全部替换**，还要配合「下一个匹配位置」的循环。一个工程细节：**替换会改变行长度与行号，循环时必须小心坐标漂移**——替换完一处，后续查找的起点要更新，否则可能重复替换或漏掉。<span class="marginnote">替换的坐标漂移问题，与《文件》篇里「更新文件时行号失效」、数据库「更新游标失效」是同一类问题：<strong>引用在数据变更后需要重新锚定</strong>。工程师常以「从后往前替换」或「记录绝对偏移」规避。</span>

## 5 从行表编辑器到更现代的结构

行表 + 串的模型有两个进化方向：

**rope / piece table**：把大文档切成片段，插入删除只改片段边界，避免整行复制——适合超大型文件与并发编辑。
**间隙缓冲（gap buffer）**：在光标处预留一块「间隙」，插入删除都在间隙里进行，光标附近的编辑 $O(1)$——Emacs 的经典选择。

它们与「行表」不是替代关系，而是对「编辑发生在光标附近」这一局部性规律的进一步利用。理解了行表，就理解了这些现代结构的出发点。<span class="marginnote">数据结构的演进常常是「<strong>为局部性而设计</strong>」：缓存、间隙缓冲、rope，全在赌「访问/修改集中在一个小区域」。这个赌注，是存储系统性能优化的普遍主题。</span>

## 6 小结

- 文本编辑的数据组织 = **行表**（线性表）+ **每行一个串**。
- 行表选顺序/链式取决于「定位 vs 插删」的侧重；现代编辑器用分片串/rope。
- 编辑命令全部递归落到底层**串原语**：插入、删除、查找、替换。
- 位置换算：全局偏移 = 前 $k-1$ 行长度之和 + 列偏移；存「行+列」使局部编辑不失效。
- 查找替换要防**坐标漂移**：替换改变行长，需重新锚定后续起点。
- 行表 → rope / 间隙缓冲的演进，都是「为局部性而设计」。
