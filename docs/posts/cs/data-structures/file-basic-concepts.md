## 为什么数据结构要管「文件」

前面讲的数据结构都活在内存里——程序一结束，数据就没了。**文件（file）**把数据持久化到外存，让数据在程序之间、程序与程序之间流转。从数据结构视角看，文件是「**外存上的线性表/查找表**」：记录（记录 = 数据元素）、关键字（主关键字/次关键字）、物理记录与逻辑记录的分层。文件的**组织方式**（顺序、索引、散列、倒排）决定「增删改查」的代价——这正是查找篇的「静态/动态表」思想在外存上的延伸。本节立起文件的基本概念，为后面六种文件组织铺路。

## 1 文件与记录

**文件（file）**：由**性质相同的记录（record）**构成的集合。每个记录是若干**数据项（字段, field）**的组合。

- **逻辑记录**：用户视角的一条记录——数据项的集合；
- **物理记录（块, block）**：外存读写的最小单位——一次 I/O 取出的数据；
- **主关键字（primary key）**：唯一标识一条记录的数据项（如学号）；
- **次关键字（secondary key）**：不唯一、用于辅助查找的数据项（如性别、专业）。

**主关键字与次关键字的对称性**：按主关键字组织 → 每条记录有「唯一住址」，支持精确查找；按次关键字组织 → 一个值对应多条记录，产生「倒排」需求。**主关键字决定「文件的主组织」，次关键字决定「附加索引要不要建」**——数据库里「主键索引」与「二级索引」的分工，源头就在这里。一个文件只能有一个主组织方式，但可以建无数个次关键字索引，这正是 §12.6 多关键字文件的出发点。

**重点：一个逻辑记录可能跨多个物理块，也可能多个逻辑记录挤在一个物理块里——「逻辑/物理」的映射由文件组织方式决定。**

**定长记录与变长记录**：定长记录所有字段长度固定（如学号 10 字节 + 姓名 20 字节 + 成绩 4 字节 = 34 字节），块内记录边界固定，第 $k$ 条记录的地址可直接用「基址 + $k \times 34$」算出——这是顺序文件随机访问的前提。变长记录（如变长字符串、可选字段）块内边界不定，需要额外的「记录长度前缀」或「偏移表」才能定位下一条记录。**「定长 → 可算术定位，变长 → 需遍历或索引」**，是记录层面最根本的分界——它决定后续文件组织的取舍。

**记录跨块（spanned）与不跨块（unspanned）**：允许一条记录跨两个物理块（spanned）能省空间（不浪费块尾空隙），但读取一条记录可能要做两次 I/O；不跨块（unspanned）每条记录只在块内、浪费块尾一点空间，但一次 I/O 必得完整记录。**「省空间 vs 保原子 I/O」的权衡**，是文件物理设计里天天遇到的取舍。<span class="marginnote">「逻辑记录 vs 物理块」的分层与《串的表示》的「定长/块链」同构：<strong>逻辑单位（记录/串）与物理单位（块/结点）是两套尺寸</strong>。文件的组织设计，本质上就是「决定逻辑记录如何映射到物理块」——映射得好，I/O 就少。</span>

## 2 文件的逻辑结构

按记录间的关系，文件分两类逻辑结构：

**记录式文件**：记录之间有「顺序/树/图」等结构，如定长记录的顺序文件、树形目录；
**流式文件**：不区分记录，就是一个字节流（如可执行文件、日志）。

**重点：数据库的数据文件、操作系统的普通文件，分别对应「记录式」与「流式」**——两种范式的分界，决定了文件系统要不要「解释记录结构」。

**这层分界对上层意味着什么？** 流式文件（如 `.txt`、`.exe`、`.mp4`）的「内容解释权」在应用程序手里——操作系统只保证字节的读写与落盘，不关心字节含义。记录式文件（如数据库表文件）则需要「记录管理器」来解释：从物理块里按字段切出记录、识别主关键字、维护索引。**因此数据库引擎（InnoDB、RocksDB）本质上是「在流式磁盘上搭建记录式层」的软件**——这正是《数据库》专题里「存储引擎」一词的由来。<span class="marginnote">「记录式 vs 流式」是「结构化的数据 vs 无结构的字节流」之分：<strong>数据库要「按字段查」，必须记录式；操作系统不在乎字节含义，流式即可</strong>。到《数据库》篇学「记录与页」时，这个分界会以「定长/变长记录」的面貌重现。</span>

## 3 文件的组织方式分类

按「记录在外存上的排列与索引方式」，文件组织分四类：

**顺序文件**：记录按物理顺序依次存放（§12.2）；
**索引文件**：记录无序存放，另建索引表定位（§12.3）；
**直接存取文件（散列文件）**：按关键字直接算出地址（§12.5）；
**多关键字文件**：支持按多个关键字查询（§12.6，多重表/倒排）。

**重点：文件组织 = 查找篇的「静态查找表」在外存上的翻版**——顺序=顺序查找，索引=分块/索引查找，散列=哈希查找，倒排=按次关键字查找。每一类文件，都能在内存查找表里找到对应物。

**为什么「物理顺序」不等于「逻辑顺序」**：文件记录在磁盘上的排列由「存放时」决定，而逻辑顺序（按主关键字升序）是「使用者期望的」。顺序文件要求两者一致——插入一条记录可能要把整段后续记录后移，这就是顺序文件「插删难」的根源。索引文件则把「物理顺序」与「逻辑顺序」解耦：数据随便放，索引表记录逻辑序与物理址的映射。**「解耦物理与逻辑」是索引、散列等高效组织的共同手段**，这个思想贯穿整个文件篇。<span class="marginnote">「<strong>文件的组织方式 = 查找结构的外存版</strong>」是本节最重要的一句话：<strong>顺序文件 → 线性表，索引文件 → 索引表，散列文件 → 哈希表，倒排文件 → 多关键字索引</strong>。把内存查找学透了，文件组织就是「把结构搬到磁盘 + 处理块 I/O」。</span>

## 4 核心对比表：四种文件组织预览

四种组织的总览：

| 组织方式 | 存取方式 | 查找代价 | 插入/删除 | 典型场景 |
| --- | --- | --- | --- | --- |
| 顺序文件 | 顺序 | 折半/顺序 $O(\log n)$~$O(n)$ | 麻烦（需重排） | 日志、定长批量 |
| 索引文件 | 索引 + 随机 | $O(\log n)$（索引折半） | 索引表更新 | 数据库主键查询 |
| 散列文件 | 按地址直接 | 平均 $O(1)$ | 哈希冲突处理 | 快速等值查找 |
| 倒排文件 | 按次关键字 | 次键索引 | 索引维护 | 全文检索、标签查询 |

三条规律：第一，**「查找方式」决定「组织方式」**——要顺序查用顺序文件、要随机查用索引/散列、要按属性查用倒排。第二，**插入删除越方便，往往查找越复杂**（顺序难插、散列好插）；第三，**现代数据库是「多种组织」的组合**——主键 B+树索引 + 辅助索引 + 堆文件，各司其职。<span class="marginnote">「现代数据库 = 多组织组合」的预览：<strong>堆文件存数据、B+树做主索引、二级索引支持次关键字、哈希索引做等值加速</strong>。学完本篇四种文件组织，你就拿到了数据库存储引擎的地图——专题篇《B+树在 MySQL InnoDB 中的落地》会把这套组合具体化。</span>

## 5 文件与「从极限到大模型」主线的连接

**数据库**：数据文件 + 索引文件是 InnoDB 的地基（专题篇 B+树）；
**搜索引擎**：倒排文件是全文检索的核心（信息检索篇）；
**大模型**：训练数据的存储、模型参数的 checkpoint、KV cache 的落盘，全是「文件组织 + 块 I/O」；
**分布式系统**：分片、副本、日志文件（WAL），都在处理「文件持久化」。

**重点：文件组织是「数据如何在外存上安家」的系统学问**——它把内存数据结构的智慧，延伸到「断电不丢」的尺度。

**一个通用的「介质切换」思维**：同一批数据，放在不同介质上，你会选择不同的结构——放内存用哈希表（快、断电丢），放 SSD 用 B+树（持久、支持范围），放对象存储（如 S3）用「目录 + 分片」。**介质决定了结构**，这是「从极限到大模型」知识体系里反复出现的主题：数据在 CPU 缓存、内存、磁盘、网络之间流动，每换一层都要重新选择结构与度量单位。文件篇正是这套思维的第一个完整演习场。<span class="marginnote">「持久化」让数据结构的边界从「一次程序运行」扩展到「程序的世代」：<strong>哈希表进程结束即失，散列文件断电仍在</strong>。大模型的权重、数据库的记录、搜索引擎的倒排，全部靠「文件」这一层承载——<strong>数据结构 + 文件组织，才构成完整的数据全生命周期</strong>。</span>

## 6 数值算例：一次 I/O 能读多少记录

文件的代价单位是「块 I/O」——一次磁盘读写取一个物理块。设每条逻辑记录 100 字节，物理块 4 KB（4096 字节），则一块能装 $\lfloor 4096/100 \rfloor = 40$ 条记录。

**场景一（顺序读）**：要读完 100 000 条记录（全部文件），需要 $100000/40 = 2500$ 次块 I/O。若磁盘每次读块约 5 ms，总耗时约 12.5 秒——**顺序读的代价 = 文件大小 / 块大小**。

**场景二（随机查一条）**：顺序文件里查第 $k$ 条记录，最坏要把前面 $k$ 条所在的块全部读一遍——查第 50 000 条要读 $50000/40 = 1250$ 个块。而**索引文件**先读索引表（折半定位），再只读目标块——平均约 2–3 次块 I/O。**同一查询，顺序文件 1250 次、索引文件 3 次，这就是「组织方式决定代价」最直观的对比。**<span class="marginnote">这个数字对比值得反复回味：<strong>内存里我们比「比较次数」，文件里我们比「块 I/O 次数」</strong>——因为一次磁盘访问比一次内存访问慢几个数量级。<strong>「把 I/O 次数压下来」是所有文件组织设计的出发点</strong>，顺序、索引、散列、倒排，全在围绕它做文章。</span>

## 7 术语速查表：文件基本概念

| 术语 | 含义 | 与内存结构的对应 |
| --- | --- | --- |
| 逻辑记录 | 用户视角的一条记录 | 数据元素 |
| 物理块 | I/O 的最小单位 | 数组的一段 |
| 主关键字 | 唯一标识记录 | 查找键 |
| 次关键字 | 非唯一、辅助查找 | 辅助索引键 |
| 记录式文件 | 记录有结构 | 线性表/树 |
| 流式文件 | 无结构字节流 | 字符串 |

**三句收束**：第一，**文件是「外存上的查找表」**——它的组织方式（顺序/索引/散列/倒排）对应查找篇的顺序查找/索引查找/哈希查找/次关键字查找。第二，**逻辑记录与物理块的映射是文件设计的主战场**——映射得好，I/O 少，查询快。第三，**评价文件组织的指标是「块 I/O 次数」而非「比较次数」**——存储介质决定了性能的度量单位。<span class="marginnote">「<strong>度量单位随存储介质而变</strong>」是贯穿文件篇的主线：<strong>内存论比较、磁盘论 I/O、网络论往返</strong>。<strong>这套「换介质换度量」的思维，在大模型训练（显存/内存/磁盘的梯度流）里同样成立</strong>——数据结构的分层思维，最终长成系统的分层思维。</span>

## 8 小结

- 文件 = 性质相同记录的集合；记录 = 数据项的组合。
- 逻辑记录 vs 物理块：用户视角 vs I/O 单位。
- 主关键字唯一、次关键字辅助——决定查找方式。
- 记录式 vs 流式文件：结构化 vs 字节流。
- 四种组织：顺序、索引、散列、多关键字（倒排）。
- 文件组织 = 查找结构的外存版；数据库 = 多组织的组合。
- 定长记录可算术定位，变长记录需前缀/偏移表——记录层面最根本分界。
- spanned 省空间、unspanned 保原子 I/O——物理设计的取舍。
- 介质决定结构：内存哈希、磁盘 B+树、对象存储分片。

在下一节，我们学最简单也最基础的一种——**顺序文件**。它是所有文件组织的地基：理解了「物理顺序 = 逻辑顺序」的约束与代价，才能理解索引、散列、倒排各在「解耦物理与逻辑」上走了多远。
- 主关键字唯一住址、次关键字产生倒排——主组织与附加索引的分工。
- 一个文件一个主组织、可多个次关键字索引。
