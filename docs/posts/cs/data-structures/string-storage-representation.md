## 为什么存储方式值得单独一节

上一节定义了串的 ADT，本节解决「串到底怎么存」。同一个逻辑上的「字符序列」，落到内存里至少有三种画法：**定长顺序存储**（数组 + 长度）、**堆分配存储**（动态申请、按需扩展）、**块链存储**（链表 + 每结点装一段字符）。三者各有代价——定长简单但会截断，堆分配灵活但多一次间接，块链可拼接却浪费在指针上。选择哪种，直接决定串的「求子串」「连接」「模式匹配」能跑多快。本节是「存储结构决定运算代价」在串上的完整案例。

## 1 定长顺序存储

定长顺序存储用一块**固定大小**的连续空间存放串，另设一个长度变量：

```c
#define MAXSTRLEN 255                /* 定长上限 */
typedef unsigned char SString[MAXSTRLEN + 1];   /* 下标 0 存串长，字符从 1 起 */
```

这里有一个经典约定：**下标 0 单元存放串的长度**，字符从下标 1 开始。这样串长 `s[0]` 可 $O(1)$ 取得，而下标运算 `s[i]` 直接定位第 $i$ 个字符。

**辨析｜易错点：截断（truncation）。** 若操作结果超过 `MAXSTRLEN`，定长存储只能截断多余字符——**这是定长顺序存储的根本缺陷**。连接时结果可能被截断，求子串取超长部分也会截断。<span class="marginnote">定长存储的「截断」相当于预先给串上了限：短文本够用，长文本吃亏。它换来的是<strong>常数时间的随机访问</strong>——`s[i]` 一次寻址。这是数组型存储的永恒交易：<strong>访问快、扩张难</strong>。</span>

## 2 堆分配存储

堆分配存储把字符空间放在**堆（heap）**上，用一个结构体记录「指针 + 长度」：

```c
typedef struct {
    char *ch;      /* 指向堆上按需分配的空间 */
    int  length;   /* 串长 */
} HString;
```

`ch` 指向一块按需分配的空间；需要更长时，重新分配并复制旧内容，**不存在截断问题**。串的连接、替换等运算的规模可以任意。

**重点：堆分配让「变长串」成为可能，代价是每一次重分配都是一次 $O(n)$ 的复制。** 若在循环里反复连接小串，会产生大量重复复制——这正是编程里 `StringBuffer`/`StringBuilder`（缓冲拼接）要解决的问题。<span class="marginnote">堆分配串是「<strong>长度动态</strong>」的存储模型，与后续《动态存储管理》篇讲的堆区分配同一套机制。它也是 C 语言里 `malloc` 动态串的天然载体——标准库字符串函数的返回值几乎都是这种形态。</span>

## 3 块链存储

块链存储用链表存串：每个结点存**一块**字符，外加一个指针。结点大小可取 1 或 >1：

```c
#define BLOCK_SIZE 4          /* 块大小 */
typedef struct Block {
    char ch[BLOCK_SIZE];      /* 一块字符 */
    struct Block *next;       /* 下一块 */
} Block;

typedef struct {
    Block *head;              /* 链头 */
    int   length;             /* 串长 */
} LString;
```

**重点：块大小是空间与时间的权衡。** 块越小，指针域占比越高、空间浪费越大；块越大，访问特定位置的遍历代价越高。若块大小为 1，退化成「每个结点一个字符」的普通链表，指针开销占大头——块链存储因此在现代语言中很少直接使用。<span class="marginnote">块链的「块」思想并未消失：文件系统的磁盘块、数据库的分块、B 树的结点，全是「<strong>以块为粒度管理数据</strong>」。它把随机访问的代价交给遍历，却把拼接（连接）变成指针操作。块越大，越接近数组；块越小，越像链表。</span>

## 4 核心对比表：三种存储方式

三种存储方式并排，各自的取舍一目了然：

| 维度 | 定长顺序 | 堆分配 | 块链 |
| --- | --- | --- | --- |
| 存储单元 | 固定数组 | 堆上动态空间 | 链表结点块 |
| 随机访问 | $O(1)$ | $O(1)$ | $O(n)$（需遍历） |
| 长度上限 | 固定，超长截断 | 动态，可扩展 | 动态 |
| 串连接 | 可能截断 | 需重分配复制 | 改指针即可 |
| 额外开销 | 几乎无 | 结构体 + 堆管理 | 每块一个指针域 |
| 适用场景 | 定长短串 | 一般文本处理 | 频繁拼接、罕见访问 |

从表中读出三条规律。第一，**没有免费的午餐**：随机访问快，扩张必然难（定长、堆分配）；扩张容易，随机访问必然慢（块链）。第二，**堆分配是现代字符串（C++ `std::string`、Python `str`）的主流模型**——它兼顾动态长度与 $O(1)$ 访问，牺牲的是重分配时的复制。第三，**块链的指针开销在小字符场景下难以接受**，其「块」思想反而以 B 树、文件块等形态在别处大放异彩。

## 5 存储结构如何影响串运算

同样的串运算，在不同存储下代价不同：

**求子串 SubString**：定长与堆分配是「拷贝一段连续内存」，$O(len)$；块链要跨块拷贝，还要处理块边界，更慢且更易错。
**求长度 StrLength**：定长读 `s[0]`、堆分配读 `length`，均 $O(1)$；块链要维护长度计数或遍历计数。
**模式匹配 Index**：三种存储都支持，但块链的随机访问缺陷会让匹配更慢——下一节的朴素匹配按「字符下标」推进，顺序存储下天然高效，块链下则需块内偏移换算。<span class="marginnote">模式匹配之所以是串的「性能标杆」，正是因为它对「按位置取字符」的频繁依赖：<strong>随机访问能力直接决定匹配速度</strong>。这解释了为什么几乎所有模式匹配算法都假设串是顺序存储。</span>

## 6 小结

- 三种存储：**定长顺序**（数组+长度，超长截断）、**堆分配**（堆上动态空间，可扩展）、**块链**（链表+块，指针开销大）。
- 定长与堆分配随机访问 $O(1)$；块链随机访问需遍历。
- 堆分配是动态字符串的主流模型，重分配需 $O(n)$ 复制。
- 块大小是块链的权衡杠杆；块的思想在文件系统与 B 树中延续。
- 存储结构决定串运算代价：求长度、求子串、模式匹配各有不同表现。
