## 为什么哈希还要「分析」

哈希查找的流程一句话：**算地址 → 冲突就按解法找**。但「平均多少步」取决于装填因子 $\alpha$、冲突解法与哈希函数质量——这不是凭感觉能估的。本节把哈希查找的**完整流程**、**成功与失败的 ASL**、以及**各因素如何影响性能**系统分析一遍。结论会澄清一个常被误解的事实：**哈希表的 $O(1)$ 不是免费的，它在 $\alpha$ 低时成立；$\alpha$ 升高，一切按公式恶化**。理解这套分析，才算真正「会用」哈希表。

## 1 哈希查找的完整流程

查找关键字 $key$：

1. 计算地址 $addr = H(key)$；
2. 看 $addr$ 处：若为空 → 不存在；若关键字相等 → 找到；否则 → **冲突处理**；
3. 开放定址法：按探测序列继续找（线性/二次/伪随机）；链地址法：沿该桶链表逐个比；
4. 找到空位/链尾 → 查找失败。

**重点：哈希查找的「比较次数」= 探测/链表扫描的次数，由冲突决定。** 无冲突时 1 次，冲突越多越接近顺序查找。<span class="marginnote">「哈希查找 = 哈希计算 + 冲突消解」两步。<strong>哈希计算是常数，冲突消解是变量</strong>——所以哈希表性能分析的全部焦点，都落在「冲突消解要花多少步」上。这正是上一节两种冲突解法被反复对比的原因。</span>

## 2 公式解析：成功与失败的平均查找长度

设装填因子 $\alpha = n/m$，哈希函数均匀。两种冲突解法下的 ASL：

$$
\begin{aligned}
\text{链地址法} &: \quad ASL_{\text{成功}} \approx 1 + \frac{\alpha}{2}, \qquad ASL_{\text{失败}} \approx \alpha \\
\text{线性探测} &: \quad ASL_{\text{成功}} \approx \frac{1}{2}\left(1 + \frac{1}{1-\alpha}\right), \qquad ASL_{\text{失败}} \approx \frac{1}{2}\left(1 + \frac{1}{(1-\alpha)^2}\right)
\end{aligned}
$$

- **第一步，读「与 $\alpha$ 的关联方式」**：链地址是**线性**关联（$1+\alpha/2$），线性探测是**双曲**关联（分母 $1-\alpha$）。
- **第二步，代入 $\alpha = 0.5$**：链地址成功 1.25，线性探测成功 1.5——两者都「接近 1」。
- **第三步，代入 $\alpha = 0.9$**：链地址成功 1.45，线性探测成功 ≈ 5.5、失败 ≈ 50——**线性探测在 $\alpha=0.9$ 时已经不可用**。<span class="marginnote">「线性增长 vs 爆炸增长」的差异，是选冲突解法的决定性依据：<strong>若装填因子可能升高，链地址法安全得多</strong>。这也解释了为什么 Java 的 HashMap 把 $\alpha$ 定在 0.75、到 0.75 就扩容——<strong>在爆点之前扩容，是哈希表的养生之道</strong>。</span>

## 3 影响哈希查找性能的三个因素

1. **哈希函数的质量**：分布越均匀，冲突越少。除留余数法选好 $p$，字符串加权取好系数，都是「均匀化」手段；
2. **装填因子 $\alpha$**：越高越挤、越慢——是最可控的旋钮；
3. **冲突解决的方法**：链地址稳、开放定址敏。

**重点：三个因素中，$\alpha$ 是「最可操作」的**——哈希函数写好后难改，冲突解法建表前定死，唯有装填因子能通过「扩容」动态调控。

一个常见的实操问题：「$\alpha$ 设多大合适？」工程共识是——**链地址法控制在 0.7–1.0，开放定址法控制在 0.5–0.75**。Python 的 dict 在 $\alpha$ 达 2/3 时扩容，Java 的 HashMap 在 0.75 时扩容，正是这套经验的体现：**在曲线「抬头」之前扩容，成本最小**。反过来，若你的场景允许更高的 $\alpha$（如只读、元素全在内存），可以关掉自动扩容以省内存——但一定要先读本节公式，确认自己知道代价是什么。工程哈希表的核心机制（扩容 + 重新哈希）就是围绕 $\alpha$ 展开的。<span class="marginnote">「扩容 + 重哈希」是哈希表工程实现的心脏：<strong>$\alpha$ 超阈值 → 表长翻倍 → 所有元素重新插入</strong>。重哈希 $O(n)$，但均摊到每次插入是 $O(1)$——这正是哈希表「均摊 $O(1)$」的数学基础。专题篇《哈希表工程实现》会完整算这笔均摊账。</span>

## 4 辨析｜易错点：哈希查找的几个常见误区

**误区一：「哈希表查找恒为 $O(1)$」**：错。平均 $O(1)$ 依赖 $\alpha$ 与函数均匀；最坏（全部冲突）是 $O(n)$。
**误区二：「装填因子可以接近 1」**：开放定址法不行（探测爆炸），链地址法勉强可以，但链太长仍慢。
**误区三：「哈希表可以有序遍历」**：错。哈希地址无序，哈希表不支持范围查询——有序需求要回到 BST/B 树。
**误区四：「哈希函数越复杂越好」**：错。计算快 + 分布均匀才是目标；过度复杂反而拖慢常数。

**误区五：「失败查找和成功查找一样贵」**：错。失败查找往往更贵——判定不存在要探测到空位或链表尾，线性探测下失败 ASL 约是成功的 $(1+\alpha)$ 倍。**数据库索引的「探测空位」成本，正是哈希索引在大量等值缺失场景下变慢的原因。**

**误区六：「扩容后性能自动恢复」**：错。扩容要重哈希全部元素，$O(n)$ 的一次性开销不小；频繁扩容的「抖动」比稳定高 $\alpha$ 更伤性能——**所以工程表会用「翻倍扩容 + 均摊」平滑成本，而不是每次微调**。<span class="marginnote">「平均 $O(1)$、最坏 $O(n)$、无法有序」三条边界，是哈希表的完整画像。<strong>要有序 → 别用哈希；怕最坏输入 → 随机化哈希或控制 $\alpha$</strong>。认清边界，哈希表才能用在刀刃上。</span>

## 5 从哈希分析到工程实践

**语言内置哈希表**：Python `dict`、Java `HashMap`、C++ `unordered_map`——都是「哈希 + 链地址（或树化桶）+ 动态扩容」；
**数据库哈希索引**：等值查询用哈希索引最快，但范围查询用 B+树；
**分布式哈希**：一致性哈希（专题篇）解决「结点增删时最小化重映射」。

**重点：本节的分析框架——$\alpha$、冲突、ASL——直接迁移到工程哈希表。** 看懂这些公式，就能理解为什么哈希表要扩容、为什么某些负载会让哈希表变慢。

在「从极限到大模型」的知识链条里，哈希分析还预告了两件大事：**其一**，分布式缓存的一致性哈希，本质是「把哈希的键空间切段」以最小化结点增删时的重映射；**其二**，布隆过滤器靠「多个哈希位」判定存在性，其误判率分析同样是 $\alpha$ 型公式。**哈希是数据结构的基石，哈希分析是这套基石的地基。**

## 5 从哈希分析到工程实践<span class="marginnote">哈希分析是「<strong>从平均到工程</strong>」的模板：<strong>一个平均指标（ASL）背后藏着负载因子、冲突策略、最坏边界三件事</strong>。学会这套分析，你拿到任何「XX 表」都能问出关键问题——装多满？冲突怎么办？最坏多糟？</span>

## 6 数值算例：把平均查找长度手算一遍

设表长 $m=11$，哈希函数 $H(key) = key \bmod 11$，用**线性探测**解决冲突，按顺序插入 47、7、29、11、16、92、22、8、3。逐个算地址：

- 47 → 3（空）占位；7 → 7；29 → 7 冲突，探测 8；11 → 0；16 → 5；92 → 4；22 → 0 冲突，探测 1；8 → 8 冲突，探测 9；3 → 3 冲突，探测 4（92）→ 5（16）→ 6 空位。

**成功查找的探测次数**分别是：47 一次、7 一次、29 两次、11 一次、16 一次、92 一次、22 两次、8 两次、3 四次。加起来 15，于是

$$
ASL_{\text{成功}} = \frac{1}{9}(1+1+2+1+1+1+2+2+4) = \frac{15}{9} \approx 1.67
$$

**对照公式**：$\alpha = 9/11 \approx 0.818$，代入线性探测公式 $\frac12(1+\frac1{1-\alpha}) \approx 3.25$——实测 1.67 明显小于渐近估计，因为公式描述的是「长期平均、表接近满」时的行为，而本例表还空着两格。**这提醒我们：公式给的是趋势与上界，具体数值要按实际表与插入序列逐项累加。**<span class="marginnote">手算一次 ASL，胜过背公式十遍：<strong>把每个 key 的探测次数列成一行、逐项相加、除以总数</strong>，就是成功 ASL 的全部算法。<strong>失败 ASL 则要对「每个空位能落入的探测序列」逐项算</strong>——面试里能当场写出这条链，就说明真的懂了哈希。</span>

## 7 术语速查表：哈希查找分析常用词

| 术语 | 含义 | 对性能的影响 |
| --- | --- | --- |
| 装填因子 $\alpha$ | 已存元素数 / 表长 | 越高越慢，是首要旋钮 |
| 成功 ASL | 找到任一元素平均探测次数 | 衡量「查得到」的成本 |
| 失败 ASL | 判定不存在平均探测次数 | 衡量「查不到」的成本 |
| 线性探测 | 冲突后逐个往后找 | 易聚集，$\alpha$ 高时爆炸 |
| 链地址 | 冲突元素挂进同桶链表 | 线性退化，$\alpha$ 高也稳 |
| 再哈希 | 扩容后全部元素重插 | 摊还后 $O(1)$，扩容的核心 |

**一张表收住哈希分析**：性能由「装多少（$\alpha$）+ 怎么处理冲突（解法）+ 哈希函数是否均匀（质量）」三件事共同决定；而工程上能动的只有 $\alpha$（扩容）。**看到任何哈希表，先问三个问题——装多满？冲突怎么办？最坏多糟？** 答得出这三问，哈希分析就过关了。<span class="marginnote">「<strong>装多满、冲突咋办、最坏多糟</strong>」三问，是把哈希分析迁移到任何「XX 表」的通用探针——<strong>它同样适用于 B+树、跳表与布隆过滤器</strong>。数据结构分析的终点，是养成「问对问题」的习惯。</span>

## 8 小结

- 哈希查找 = 算地址 + 冲突消解；比较次数由冲突决定。
- 实测 ASL 常小于公式渐近值：公式给趋势与上界，具体数值要逐项累加。
- $\alpha$ 工程共识：链地址 0.7–1.0、开放定址 0.5–0.75。
- 链地址 ASL：成功 $1+\alpha/2$、失败 $\alpha$——线性关联。
- 线性探测 ASL：成功 $\frac12(1+\frac1{1-\alpha})$、失败 $\frac12(1+\frac1{(1-\alpha)^2})$——双曲关联。
- $\alpha$ 是哈希性能最可操作的旋钮；扩容重哈希使其均摊 $O(1)$。
- 边界：平均 $O(1)$、最坏 $O(n)$、不支持有序。
- 工程哈希表（dict/HashMap/unordered_map）都遵循本节的分析框架。
- 手算 ASL：逐 key 记探测次数 → 求和 → 除以元素数。
- 三问探针：装多满（$\alpha$）？冲突怎么办（解法）？最坏多糟（边界）？

在下一节，我们进入查找篇之后的大章——**第十篇 内部排序**，先从排序概述与稳定性开始。哈希篇到这一节收尾：从哈希函数、冲突解法到性能分析，**「算地址 → 消冲突 → 估成本」的完整链路已闭环**；带着这个分析框架进入排序，你会习惯性地追问每种排序的「最好/最坏/平均」三态成本。
