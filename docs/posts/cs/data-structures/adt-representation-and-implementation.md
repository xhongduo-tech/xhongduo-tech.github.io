## 为什么从「表示与实现」开始

上一节我们把数据结构钉成了二元组 $(D, S)$，又指出 ADT 是补上操作集 $P$ 的三元组。可「抽象」不能只停在概念层——它必须落成**一份能看、能写、能实现的规格说明**，否则无从谈分工。这一节就用严蔚敏教材的招牌例子「复数 ADT」走完整条链：先写规格说明，再用 C 语言实现。

这条「先定接口、后写实现」的纪律，正是大模型工程里最常见的分工：PyTorch 的 `Tensor` 暴露一套张量运算接口，底层用 CUDA、用 FlashAttention、用张量并行去实现，调用方一概不关心。ADT 就是这套纪律在数据结构的第一次显形。

## 1 ADT 规格说明的书写格式

严蔚敏给抽象数据类型规定了一份**三段式规格说明**，形如：

```text
ADT 复数 {
    数据对象：D = { e1, e2 | e1, e2 ∈ float }
    数据关系：R = { <e1, e2> | e1 是实部，e2 是虚部 }
    基本操作：
        Create(&C, x, y)    操作结果：构造复数 C = x + yi
        Add(C1, C2)         操作结果：返回复数 C1 与 C2 之和
        Sub(C1, C2)         操作结果：返回复数 C1 与 C2 之差
        Mul(C1, C2)         操作结果：返回复数 C1 与 C2 之积
        GetReal(C)          操作结果：返回复数 C 的实部
        GetImag(C)          操作结果：返回复数 C 的虚部
} ADT 复数
```

三段各有讲究：

- **数据对象 $D$**：说明这个数据类型处理的元素集合。对复数就是「一对实数」，写作 $\{ e_1, e_2 \mid e_1, e_2 \in \text{float} \}$。
- **数据关系 $R$**：说明元素内部怎么组织。复数里 $e_1$ 是实部、$e_2$ 是虚部，一个有序对 $<e_1, e_2>$ 就定死了结构。
- **基本操作 $P$**：逐一列出这个数据类型对外提供的能力。每个操作注明**参数表**与**操作结果**，只写「做什么」，不写「怎么做」。<span class="marginnote">注意两个参数的区别：`Create(&C, ...)` 里带 `&` 的是<strong>引用参数</strong>，意思是「这个参数会被函数改写」，调用后 $C$ 真的被构造好了；`Add(C1, C2)` 里不带 `&` 的是<strong>赋值参数</strong>，函数只读它们、不改动。C 语言没有引用语法，引用参数要用指针 `*` 来模拟——下面实现时看得更清楚。</span>

**初始条件 / 操作结果**是规格说明的「契约」：使用者在调用前应当保证初始条件成立，实现者必须保证操作结果兑现。<span class="marginnote">这就是后来的前置条件（precondition）与后置条件（postcondition）思想，也是形式化验证、测试驱动开发的雏形。规格说明写得好，使用者和实现者就能在不见面、不交流的情况下各自放心地工作。</span>

## 2 用 C 语言实现复数 ADT

规格说明只是「合同」，要实现它，C 语言的做法是：**用结构体表示数据对象，用一组全局函数表示基本操作**。

```c
/* 复数 ADT 的实现：复数 = 直角坐标 (实部, 虚部) */
typedef struct {
    float re;   /* 实部 */
    float im;   /* 虚部 */
} Complex;

/* 构造：把 x + yi 写进 *C 指向的变量 */
void Create(Complex *C, float x, float y) {
    C->re = x;
    C->im = y;
}

/* 相加：返回 (a+c) + (b+d)i */
Complex Add(Complex c1, Complex c2) {
    Complex sum;
    sum.re = c1.re + c2.re;
    sum.im = c1.im + c2.im;
    return sum;
}

/* 相乘：返回 (ac-bd) + (ad+bc)i */
Complex Mul(Complex c1, Complex c2) {
    Complex prod;
    prod.re = c1.re * c2.re - c1.im * c2.im;
    prod.im = c1.re * c2.im + c1.im * c2.re;
    return prod;
}

float GetReal(Complex c) { return c.re; }
float GetImag(Complex c) { return c.im; }
```

注意 `Create` 为什么收指针：它要**改写**调用者的变量，必须拿到变量的地址，这正是规格说明里 `&C` 的 C 语言翻译。`Add`、`Mul` 只读参数、返回新值，于是用赋值参数即可。

## 3 信息隐藏：换一种内部表示，接口不动

ADT 最值钱的地方，是**使用者只看规格说明，内部表示可以随时更换**。上面实现用的是「直角坐标」$(re, im)$。我们完全可以换成「极坐标」$(r, \theta)$，其中 $r$ 是模长、$\theta$ 是辐角：

$$
re = r \cos \theta, \qquad im = r \sin \theta
$$

用极坐标实现时，`GetReal`、`GetImag` 的代码会变（要调用三角函数），`Mul` 反而变得极简单——两个复数相乘，**模长相乘、辐角相加**：

$$
(r_1 \angle \theta_1) \cdot (r_2 \angle \theta_2) = r_1 r_2 \, \angle (\theta_1 + \theta_2)
$$

**关键点：无论内部怎么换，`Create(&C, x, y)`、`Add`、`Mul` 这些接口的名字、参数、语义全部不变。** 使用者的代码一行都不用改。这就是帕纳斯说的「信息隐藏」——把「用直角坐标还是极坐标表示复数」这个设计决策，封装在实现内部，不让它泄漏到接口之外。<span class="marginnote">真实世界的复现：早期 C 标准库的复数运算、以及无数数值库，都经历过「换表示而不换接口」的重构。哪一天你重构了内部结构而外部测试全部通过，你就体验到了 ADT 的威力。</span>

## 4 公式解析：复数乘法公式是怎么从接口内部长出来的

`Mul` 的实现看起来是四行代码，背后是一条实打实的代数公式。把两个复数展开相乘：

$$
(a + b\mathrm{i})(c + d\mathrm{i})
$$

分三步拆解：

- **第一步，按多项式乘法展开**：把括号拆开，逐项相乘

$$
(a + b\mathrm{i})(c + d\mathrm{i}) = ac + ad\,\mathrm{i} + bc\,\mathrm{i} + bd\,\mathrm{i}^2
$$

- **第二步，代入 $\mathrm{i}^2 = -1$**：虚数单位的关键性质让 $bd\,\mathrm{i}^2$ 变成 $-bd$，于是

$$
ac + ad\,\mathrm{i} + bc\,\mathrm{i} - bd
$$

- **第三步，合并实部与虚部**：实部是 $ac - bd$，虚部是 $ad + bc$，得到

$$
(a + b\mathrm{i})(c + d\mathrm{i}) = (ac - bd) + (ad + bc)\,\mathrm{i}
$$

对照代码里的 `prod.re = c1.re * c2.re - c1.im * c2.im`，正是 $ac - bd$；`prod.im` 正是 $ad + bc$。**ADT 的「黑盒」只是把数学公式装进了函数**——接口屏蔽的是实现细节，但实现必须忠于数学事实，这正是对「准确性」的要求。

**辨析｜易错点：** 初学者常把「规格说明」当成可执行代码去背，这是本节的第一个坑。规格说明里 `Add(C1, C2)` 只声明「返回两复数之和」，至于这个和怎么算，规格说明一个字都不管。第二个坑是**混淆赋值参数与引用参数**：分不清「函数要改你的变量」和「函数只是读你的变量」，就会漏写指针，导致 `Create` 无效——改了半天，调用者的复数根本没被构造出来。

## 5 小结

- ADT 用**三段式规格说明**书写：数据对象 $D$、数据关系 $R$、基本操作 $P$；每个操作写「参数表 + 初始条件 / 操作结果」。
- 基本操作的参数分**赋值参数**（只读）与**引用参数**（可改写，C 里用指针模拟）。
- C 语言实现 ADT 的范式：**结构体表示数据对象，全局函数表示基本操作**。
- **信息隐藏**：换内部表示（直角坐标 ↔ 极坐标）不影响接口，使用者代码不动。
- 复数乘法 $(a+b\mathrm{i})(c+d\mathrm{i}) = (ac-bd) + (ad+bc)\,\mathrm{i}$ 是 `Mul` 实现背后的数学。

在下一节《算法和算法分析》中，数据结构这具「骨架」将迎来它的「灵魂」：给定一个问题，如何写出有穷、确定、可行的求解步骤，又如何判断一个算法的好坏。
