## 为什么还要两种「进阶」存储

邻接表给出度方便、逆邻接表给入度方便——可两者都只装「半张图」。而邻接表存无向图时，同一条边在两条链里各出现一次，找「一条边的另一头」要两头跑。两个痛点催生两种专门结构：**十字链表**把有向图的「出弧链 + 入弧链」合进同一张表；**邻接多重表**让无向图的**每条边只存一份**，边与边共享结点。前者让「找入度/出度」都能 $O(1)$ 起步，后者让「删边、遍历邻边」不必同步两份。它们与《稀疏矩阵的十字链表》思想同源，是「多视图、少冗余」的工程结晶。

## 1 十字链表：有向图的「出入合一」

**十字链表（orthogonal list）**用于有向图。每个**弧结点**存弧的信息 + 两个方向的链指针：

```c
typedef struct ArcBox {
    int tailvex, headvex;         /* 弧尾、弧头顶点在顶点表中的位置 */
    struct ArcBox *hlink, *tlink; /* hlink：指向弧头相同的下一条弧（入弧链）
                                     tlink：指向弧尾相同的下一条弧（出弧链） */
    InfoType info;                /* 权值等信息 */
} ArcBox;
```

每个**顶点结点**存两个链头：

```c
typedef struct VexNode {
    VertexType data;
    ArcBox *firstin, *firstout;   /* 指向第一条入弧 / 第一条出弧 */
} VexNode;
```

**重点：一个弧结点同时挂在「出弧链」与「入弧链」上——出度和入度都能从链头出发线性访问。** 这正是把邻接表与逆邻接表合并成一张表的效果。<span class="marginnote">十字链表与《稀疏矩阵的十字链表》结构几乎同名同构：矩阵十字链表用「行链 + 列链」，图的十字链表用「出弧链 + 入弧链」。<strong>「一个实体、两条正交链」是通用的多视图组织法</strong>。</span>

## 2 邻接多重表：无向图的「边只存一次」

**邻接多重表（adjacency multilist）**用于无向图，解决「邻接表边存两份」的问题。每条**边**用一个结点表示，存两个端点与两个链指针：

```c
typedef struct EBox {
    int ivex, jvex;               /* 边的两个顶点 */
    struct EBox *ilink, *jlink;   /* 分别指向依附于 ivex / jvex 的下一条边 */
    InfoType info;                /* 权值 */
} EBox;
```

每个**顶点结点**存一条「该顶点依附的边链」的头：

```c
typedef struct VexBox {
    VertexType data;
    EBox *firstedge;              /* 指向第一条依附于该顶点的边 */
} VexBox;
```

**重点：无向图的每条边只占一个结点，却被两端的两个顶点共享**——删一条边只需摘掉这一个结点，且必然同时从两个顶点的链里消失。这消除了邻接表「边存两份、删边要删两处」的同步负担。<span class="marginnote">邻接多重表的「边对象」是一次性的、双向共享的。这像极了数据库里的「关联表 + 外键索引」：<strong>关系本身是一等对象，两端各持索引指向它</strong>——删除关系时，两端索引自动失效。</span>

## 3 公式解析：三种无向图存储的空间对比

对 $n$ 个顶点、$e$ 条边的无向图，三种存储的空间开销：

$$
\begin{aligned}
S_{\text{邻接矩阵}} &= \Theta(n^2) \\
S_{\text{邻接表}} &= O(n + 2e) \quad (\text{每条边两个弧结点}) \\
S_{\text{邻接多重表}} &= O(n + e) \quad (\text{每条边一个边结点})
\end{aligned}
$$

- **第一步，读邻接表**：无向图每条边在两条链各出现一次，故 $2e$ 个弧结点——「边存两份」的代价。
- **第二步，读邻接多重表**：边结点只建一个，$e$ 个——空间直接减半（省的正是那重复的一份）。
- **第三步，读「查边」的补偿**：邻接多重表空间省了，但「判断 $u,v$ 是否相邻」仍需沿 $u$ 的边链找 $v$，$O(\text{度})$；矩阵仍是 $O(1)$。<span class="marginnote">一句话选型：<strong>邻接多重表适合「边频繁增删、需要按边操作」的稀疏无向图</strong>（如网络拓扑管理、图的动态演化），矩阵适合静态稠密图。空间省的背后是「边对象」的显式化——想对「边」本身做操作（改权、删边、遍历所有边）时，它的价值才完全显现。</span>

## 4 辨析｜易错点：四张表别搞混

图存储家族容易混淆，用一张表厘清定位：

| 结构 | 适用图 | 主要优点 | 主要代价 |
| --- | --- | --- | --- |
| 邻接矩阵 | 稠密图 | 查边 $O(1)$ | 空间 $\Theta(n^2)$ |
| 邻接表 | 一般图 | 空间 $O(n+e)$ | 无向图边存两份 |
| 十字链表 | 有向图 | 出入度都易得 | 弧结点 4 域，较复杂 |
| 邻接多重表 | 无向图 | 边只存一份、易删边 | 判相邻需遍历 |

四条规律：**有向图 → 邻接矩阵或邻接表或十字链表；无向图 → 邻接矩阵或邻接表或邻接多重表。** 关键判断：「要不要 $O(1)$ 判相邻？」（矩阵）、「要不要频繁删边？」（多重表）、「要不要同时进出度？」（十字链表）。<span class="marginnote">这份「选型表」也回答了前两节埋下的伏笔：<strong>存储结构的每个变体，都是针对一个具体痛点的定向修补</strong>。理解了痛点，就不必死记结构——「什么结构治什么病」，比「结构长什么样」更重要。</span>

## 5 从存储到算法：为什么存储选择影响复杂度

图算法的复杂度，高度依赖「遍历邻居」的代价：

- 用邻接表/十字链表/多重表：DFS 是 $O(n+e)$，Dijkstra 朴素版是 $O(n^2)$、堆优化版 $O((n+e)\log n)$；
- 用邻接矩阵：DFS 是 $O(n^2)$（每步要扫整行找邻居）。

**重点：先定存储，再谈算法复杂度。** 图算法的复杂度表达式里，$e$ 的每一项都依赖「能否直接遍历邻居」——这是邻接矩阵 $O(n^2)$ 与邻接表 $O(n+e)$ 差距的根源。接下来的 DFS、BFS、Dijkstra、Prim 全部建立在这个选择之上。<span class="marginnote">这条「存储 → 复杂度」的因果链是图篇的暗线：<strong>每一章的算法，默认用邻接表表述；若改矩阵，所有 $O(e)$ 都变 $O(n^2)$</strong>。读算法证明时盯住「邻居怎么来的」，就能看懂它的复杂度从哪来。</span>

## 6 小结

- 十字链表：有向图的出弧链 + 入弧链合一，出入度都 $O(1)$ 起步。
- 邻接多重表：无向图每条边**只存一份**，两端共享，删边省事。
- 空间对比：矩阵 $\Theta(n^2)$，邻接表 $O(n+2e)$，多重表 $O(n+e)$。
- 选型：有向图选十字链表、无向图选邻接多重表，按「痛点」决定。
- 图算法复杂度依赖存储：邻接表 DFS $O(n+e)$，矩阵 $O(n^2)$。
- 先定存储、再谈算法，是图篇的暗线。
