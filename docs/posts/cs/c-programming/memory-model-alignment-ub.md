## 为什么从内存模型讲起

前面十几节我们反复提到「栈」「堆」「数据段」「未定义行为」，这一节把它们收拢成一张**进程内存全景图**，并直面 C 最隐蔽的危险——**未定义行为（undefined behavior, UB）**。<span class="marginnote">理解内存布局，就能回答「局部变量放哪、全局变量放哪、`malloc` 的内存从哪来、栈为什么会溢出」；理解未定义行为，就能解释「为什么我的程序偶尔崩、偶尔不崩」。这两者合起来，是 C 程序员从「会写」到「写得安全」的分水岭。</span>这一节讲透四段式内存布局、结构体对齐的实战规则，以及 UB 的三大类与防御策略。

## 1 进程的内存布局

一个运行中的 C 程序，其虚拟内存从高地址到低地址大致分为几段：

![进程内存布局：栈从高地址向下增长，堆从低地址向上增长，中间是代码段与数据段](/images/c-programming/memory-model-alignment-ub-1.svg)

| 段 | 存放内容 | 增长方向 | 生命周期 |
| --- | --- | --- | --- |
| **栈（stack）** | 局部变量、函数调用帧 | 高 → 低 | 函数调用期间 |
| **堆（heap）** | `malloc` 分配的内存 | 低 → 高 | 分配到 `free` |
| **BSS 段** | 未初始化全局/静态变量 | —— | 整个程序 |
| **数据段（data）** | 已初始化全局/静态变量 | —— | 整个程序 |
| **代码段（text）** | 机器指令 | —— | 整个程序 |

几个关键事实：

**栈向下增长、堆向上增长**——两者相向而行。堆 `malloc` 太多、栈递归太深，会在中间「撞车」，这就是**内存耗尽**的物理含义。
**未初始化全局变量在 BSS**，自动**零初始化**（第 2 篇讲过）；已初始化的在数据段。
- **字符串字面量在只读数据区**——所以 `char *s = "hi";` 不能改（第 3 篇讲过）。

## 2 栈与堆：各自的脾气

**栈（stack）**：由编译器自动管理。函数调用压栈帧、返回弹栈帧（《函数》一节的调用栈）。特点：

- 快（压栈/弹栈就是移动指针）；
- 空间有限（默认通常 8 MB，Linux），**深递归或超大局部数组会栈溢出（stack overflow）**；
- 生命周期自动——函数返回，局部变量即失效。

```c
void bad(void)
{
    int huge[1000000];   /* 约 4 MB：接近栈上限 */
    huge[0] = 1;         /* 小递归几次就会栈溢出崩溃 */
}
```

**堆（heap）**：由程序员管理。`malloc`/`free` 分配/释放。特点：

- 慢一些（要搜索空闲块）；
- 空间大（受限于物理内存/虚拟地址空间）；
- 生命周期由你掌控——不 `free` 就泄漏（第 3 篇）。

选型的工程直觉：**小、短命、生命周期规整的数据用栈；大、长命、数量动态的数据用堆**。

## 3 对齐：结构体的隐藏填充

第 3 篇公式解析预告了对齐，这里讲透规则。**对齐（alignment）** 指「变量的地址必须是其对齐值的倍数」——CPU 访问按边界对齐的数据最快，部分架构访问未对齐数据直接崩溃。

```c
struct S {
    char  c;    /* 对齐 1 */
    int   i;    /* 对齐 4，必须从 4 的倍数地址开始 */
    char  d;    /* 对齐 1 */
};
```

布局推演（64 位、`int` 4 字节）：

- `c` 在偏移 0；
- `i` 需从 4 的倍数开始 → 偏移 4~7（偏移 1~3 是**填充 padding**）；
- `d` 在偏移 8；
- 总大小对齐到最大对齐 4 的倍数 → **`sizeof(S) == 12`**。

重排成员 `int i; char c; char d;` 则 `sizeof` 降到 **8**。**工程规则：结构体里大成员在前、小成员在后，能减少填充**。<span class="marginnote">对齐也影响动态分配：`malloc` 保证返回的地址对齐到「能放下任何基本类型」的边界（通常是 8 或 16 字节），所以 `malloc` 的结果可以安全存 `double`。结构体的填充会让 `sizeof` 与「成员之和」不一致——网络协议结构体要逐字节打包时，会用到 `#pragma pack` 或序列化字段。</span>

**为什么对齐重要**：除了性能，还有 ABI 兼容性——不同编译器对同一结构体的布局可能不同，跨编译器/跨语言共享结构体时，填充字节是陷阱。

## 4 未定义行为：C 的灰色地带

**未定义行为（undefined behavior, UB）**：C 标准「不予规定」的行为。一旦触发，**编译器可以做任何事**——可能崩溃、可能静默出错、可能恰好正常、可能在优化后行为诡异。

标准说「未定义」，意味着「允许一切后果」：程序可能继续运行、可能崩溃、可能格式化你的硬盘（理论上）。**UB 是 bug，不是特性**。三类常见 UB：

**第一类：越界与悬垂**。

```c
int arr[3] = {1, 2, 3};
arr[5] = 100;        /* 越界：UB */

int *p = malloc(4);
free(p);
*p = 1;              /* use-after-free：UB */
```

**第二类：有符号溢出与除零**。

```c
int a = 2147483647;
a + 1;               /* 有符号溢出：UB（不是「自动变成负数」！） */
int b = 5 / 0;       /* 除零：UB */
```

**第三类：解引用空指针与指针越界运算**。

```c
int *p = NULL;
*p = 1;              /* 解引用 NULL：UB */

int *q = arr + 100;  /* 指针越界到数组外：UB（即使不解引用） */
```

**UB 为什么危险**：编译器在优化时**假设代码不含 UB**。比如：

```c
int check(int *p) {
    if (p == NULL) return 0;
    return *p + 1;
}
```

若调用方总是 `check(ptr)` 且 `ptr` 可能为 `NULL`，编译器可能基于「`*p` 已解引用故 `p` 非空」推断 `p != NULL`，进而**删除空指针检查**——优化让 UB 的后果从「段错误」变成「悄悄跳过安全检查」。这类「UB 驱动的优化」是安全研究的热点。<span class="marginnote">正因为 UB 是「编译器随便做」，同样的代码在不同优化级别（`-O0` vs `-O2`）下表现可能截然不同——「换个编译选项程序就正常了」往往说明你在 UB 边缘试探。用 `-fsanitize=undefined,address` 编译，运行时检测出越界/溢出等 UB，是排雷利器。</span>
