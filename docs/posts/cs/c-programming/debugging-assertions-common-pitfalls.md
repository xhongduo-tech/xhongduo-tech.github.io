## 为什么从调试开始

学到这里，你已经会用指针、数组、结构体与函数指针写出像样的程序了。而一旦程序「能跑」，真正的战争才开始——**调试（debugging）**。C Primer Plus 没有单独一章叫「调试」，但它的每个章节都在反复警告同一个道理：C 给你接近硬件的威力，也把犯错的自由交给你。C 不像 Python 那样到处报 `TypeError`，许多错误只是「行为诡异」而程序照样运行。<span class="marginnote">在 C 里，很多错误不产生任何报错：写越界可能悄悄破坏内存，读到未初始化变量得到的是垃圾值。编译器给不了提示，只能靠系统方法去定位——这正是本节要教的。</span>学完这一节，你会拥有一套排查 C 程序错误的工具箱：断言、调试器、以及一张「最常踩的坑」清单。

## 1 错误的三道防线

写 C 程序时，错误要在尽可能早的阶段被拦住。防线从早到晚有三道：

- **编译期**：语法错误、类型不匹配，编译器当场报错。用 `-Wall -Wextra` 把警告全打开——很多潜在的 bug 会在这里现形。
- **运行期**：断言（assert）在程序运行到不变量被破坏时立刻停下。
- **观察期**：调试器（gdb）与打印语句在问题发生时帮你看到现场。

**好的 C 程序员不追求「一次写对」，而是把每一道防线都用足。** 每消除一条警告、每加一条断言，都让 bug 提前一步现形，成本远低于事后追查。

## 2 断言：assert 与 NDEBUG

`assert` 是 C 标准库（`<assert.h>`）提供的**运行期检查**：当括号里的表达式为假（0）时，程序立刻打印错误信息并终止：

```c
#include <assert.h>

void push(Stack *s, int v) {
    assert(s != NULL);              /* 前置条件 */
    assert(s->top < s->capacity);   /* 不变量 */
    s->data[s->top++] = v;
}
```

**断言表达的是「这里必须成立」的约定**：入参非空、索引在界内、指针已分配。它把「假设」变成「可验证的检查」——一旦假设被打破，立刻定位到行，而不是让 bug 在千里之外爆炸。<span class="marginnote">断言与 `if` 检查的区别：`assert` 是给开发者的「内部契约」，发布时通常会被关闭；`if` 是对用户输入的「运行时防护」，永远保留。两种用途别混。</span>

发布时用 `#define NDEBUG`（编译选项 `-DNDEBUG`）即可让所有 `assert` 变为空操作——不损失性能，也不影响正确性，因为**断言绝不应当有副作用**（别写 `assert(++i > 0)`）。<span class="marginnote">断言的哲学：它是「应该永真」的检查，不是「处理异常」的机制。对外部输入（文件名、用户输入）要用 `if` 优雅处理；对内部不变量（指针非空、索引合法）才用 `assert` 强硬断言。</span>

## 3 第一类陷阱：内存与指针

C 的陷阱多到可以写一本书，这里按类别把最高频的挑出来。

**越界访问（off-by-one）**：数组下标从 0 开始，长度为 `n` 的数组合法下标是 `0..n-1`。写 `a[n]` 是越界——C 不检查，它只是悄悄写坏相邻内存。C Primer Plus 反复强调的 `for (i = 0; i < n; i++)` 写法，正是为了对齐「0 起、n 止、开区间」的约定。

**使用未初始化变量**：局部变量不自动清零，初值是「未知的旧数据」。`int total; total += x;` 把垃圾值加进 `total`，结果不可预测。<span class="marginnote">这正是 `-Wall` 能救你的地方：`warning: 'total' is used uninitialized`。把警告当错误看（`-Werror`），这类坑在编译期就被铲除。</span>

**悬空指针（dangling pointer）**：`free` 之后继续使用那块内存：

```c
int *p = malloc(sizeof(int));
free(p);
*p = 42;   /* 未定义行为：p 已悬空 */
```

释放后把指针置 NULL（`p = NULL`），是防「二次释放」「悬空使用」的简单纪律。

**缓冲区溢出**：`strcpy` 不检查目标长度，`char buf[8]; strcpy(buf, "too long");` 直接写穿 `buf`。凡拷贝字符串优先用 `strncpy`/`snprintf`，见《字符串与字符串函数》。

## 4 第二类陷阱：运算符与语义

**整数除法**：`5 / 9` 是 0（两个整数相除舍去小数），要浮点结果必须让至少一个操作数是浮点，见《第一个 C 程序与编译流程》的温度表。

**`=` 与 `==` 混淆**：`if (x = 5)` 不是比较而是赋值，表达式值恒为 5（真），条件永远成立。C Primer Plus 的建议是常量写在左边：`if (5 == x)`——若手误写成 `if (5 = x)`，编译器会直接报错。

**短路求值被滥用**：`a && b` 中若 `a` 为假则 `b` 不求值。`if (p != NULL && *p == 1)` 先判空再解引用——顺序错了会解引用空指针。

**scanf 忘取地址**：`scanf("%d", x);` 少了 `&`，把值写进了一个「假的地址」，程序多半当场崩溃或静默写坏内存。`%s`、`%d` 等转换都要对应「变量的地址」。

## 5 公式解析：段错误的退出码

调试时你会反复看到程序的「死法」，其中一个著名的数值是 139：

$$
\text{退出码} = 128 + \text{信号编号}
$$

- **128 的来历**：shell 约定，进程被信号杀死时，退出码等于 `128 + 信号号`。
- **信号 11 = SIGSEGV**：段错误，程序访问了非法内存（越界、悬空指针、解引用 NULL）。
- **合成**：`128 + 11 = 139`。所以看到 `$?` 为 139，就知道程序死于段错误。

同理：`128 + 8 = 136` 是 SIGFPE（除以零等浮点异常），`128 + 6 = 134` 是 SIGABRT（`assert` 触发后程序自杀）。<span class="marginnote">在 shell 里 `echo $?` 或让 CI 记录退出码，是判断「程序怎么死的」的第一手证据——比盯着屏幕找崩溃点快得多。这也是《第一个 C 程序与编译流程》里退出码契约的延续。</span>

## 6 调试器：gdb 的四个基本命令

打印语句（`printf` 调试）简单但被动：你得先猜哪里出错，再插打印、重编、重跑。**调试器（debugger）**让你在程序运行中暂停、观察、单步。以 gdb 为例，四个命令覆盖八成需求：

| 命令 | 作用 |
| --- | --- |
| `break 行号/函数名` | 设断点，程序跑到这里暂停 |
| `run 参数` | 运行程序（带上命令行参数） |
| `print 表达式` | 查看变量/表达式的当前值 |
| `next` / `step` | 单步执行（step 进入函数，next 跳过） |

先 `gcc -g prog.c -o prog`（`-g` 生成调试信息），再 `gdb ./prog`。段错误发生时，`gdb` 直接告诉你崩在第几行、各变量什么值——这比 139 这个数字精确得多。**「printf 调试」与「调试器」不是对手**：打印语句适合快速探测，调试器适合精确定位，高手两者兼用。

## 7 让工具替你找错：-Wall、-Werror 与静态分析

调试的最高境界，是让错误在编译期就被工具拦下来。C 编译器比想象中更「懂」你的代码，只是默认不声张：

- **`-Wall -Wextra`**：打开全部常见警告。未初始化变量、无意义的 `if (x = 5)`、格式串与实参类型不匹配，都会被指出。
- **`-Werror`**：把所有警告升级为错误。这一招彻底堵死「先跑起来再说」的侥幸——警告不再能拖延。
- **`-fsanitize=address,undefined`**：GCC/Clang 的**运行时消毒器**。它会给程序插入检查代码，越界访问、释放后使用、整数溢出在发生的瞬间就崩溃并打印原因，而不是让 bug 潜伏到几天后。<span class="marginnote">AddressSanitizer 是谷歌 2012 年开源的内存错误检测器，如今已是 Linux 内核与大型 C 项目 CI 的标配。一行编译选项，换来的是「内存错误当场爆炸」的待遇。</span>

**辨析｜易错点：消毒器是调试工具，不是发布配置。** 它让程序变慢数倍、占用更多内存，只该在调试与测试阶段开启。发布版本用普通 `-O2` 编译，两者互不冲突。

把这些选项组合起来，一次调试会话的完整姿势是：

```bash
gcc -g -Wall -Wextra -Werror -fsanitize=address,undefined prog.c -o prog
./prog        # 错误当场现形
```

C 的困难在于「错了不报」，而这些工具的哲学恰恰是「把不报的错变成报」。**让编译器与消毒器替你盯内存与类型，把人的精力留给逻辑错误**——这才是现代 C 调试的正确打开方式，也是《链接、库与 Makefile》里 `CFLAGS` 常常写满警告开关的原因。

## 8 小结

- 错误有三道防线：编译期警告、运行期断言、观察期调试器；用足每一道。
- `assert` 断言「内部不变量必须成立」，发布用 `-DNDEBUG` 关闭；断言不得有副作用。
- 内存陷阱：越界、未初始化、悬空指针、缓冲区溢出——`-Wall`、置 NULL、`strncpy` 各挡一路。
- 语义陷阱：整数除法、`=` 与 `==`、短路求值、`scanf` 忘 `&`。
- 退出码 `128 + 信号号`：139 段错误、134 断言自杀，shell 的 `$?` 是第一手死因。
- gdb 四件套：`break`/`run`/`print`/`next`，配合 `-g` 编译即可精准定位。
