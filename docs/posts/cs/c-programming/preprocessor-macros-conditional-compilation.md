## 为什么从预处理开始

第一个 C 程序里我们已经说过，编译的第一道工序是**预处理**：所有以 `#` 开头的指令，都在真正编译开始前被处理掉。预处理器的名声毁誉参半——用得好，它是跨平台与调试的有力工具；用坏了，它制造出无法阅读的代码。C Primer Plus 用整整一章（第16章）来讲它，因为几乎每个真实项目都要面对 `#include`、宏与条件编译。这一节把它们讲透，也顺带回答「`#define` 到底改了什么」这个总被误解的问题。

## 1 预处理器的四条主线

C 语言的预处理指令有很多条，但绝大部分工作可以归为四类：

**文件包含（file inclusion）**：`#include <stdio.h>` 把头文件内容原样粘贴到当前位置。尖括号 `<...>` 在系统包含路径里查找，双引号 `"..."` 先在当前目录找、找不到再去系统路径——这个区别正是很多「找不到头文件」报错的根源。<span class="marginnote">头文件的作用不止是拿到函数声明：它让多个源文件共享同一份声明，避免「各写各的」导致签名不一致。头文件的设计问题在《头文件、多文件程序与编译单元》有专题讨论。</span>

**宏定义（macro definition）**：`#define` 定义文本替换规则，包括对象宏与函数式宏，下面两节细讲。

**条件编译（conditional compilation）**：`#ifdef`、`#ifndef`、`#if`、`#elif`、`#else`、`#endif` 让一段代码「只在某些条件下被编译」。

**其他指令**：`#undef` 取消宏、`#error` 主动报错、`#pragma` 给编译器提示、`#line` 重置行号。它们使用频率低，但关键时刻救场。

**预处理发生在编译之前：它输入源码、输出「展开后的源码」。** 想看展开结果，用 `gcc -E`——许多宏的诡异行为，一展开就一目了然。

## 2 对象宏：给魔法数字起名字

对象宏（object-like macro）形式最简单：`#define 名字 替换文本`。

```c
#define PI 3.141592653589793
#define BUFSIZE 4096
#define MAX(a, b) ((a) > (b) ? (a) : (b))
```

前两个是对象宏：编译前，源码里所有 `PI` 都会被替换成那一长串数字。它和常量（`const`）的区别值得说清：**宏是编译期的纯文本替换，`const` 是运行期的具名存储对象**。宏不占内存、没有类型，只是「长得像变量」的替换文本；`const` 有类型、有作用域、可以被取地址。

命名约定上，宏名习惯用全大写（`BUFSIZE`），变量用小写或驼峰——读者一眼就能分辨「这是个宏」还是「这是个变量」。

## 3 函数式宏：快，但危险

第三行 `#define MAX(a, b) ...` 是**函数式宏（function-like macro）**：它带参数，调用时像函数，但本质仍是文本替换。它比函数快——省去调用与返回的开销——因此早期的 C 程序常拿它替代小函数。但它的陷阱也极其著名：

- **参数必须全部加括号**：`#define SQUARE(x) x*x`，调用 `SQUARE(a+b)` 会展开成 `a+b*a+b`，结果完全错误。正确的写法是 `((x)*(x))`。
- **参数可能被求值多次**：`MAX(i++, j)` 里 `i++` 可能被执行多次，行为与直觉相悖。<span class="marginnote">这是函数式宏最阴险的地方：它「看不出是函数」，却有函数没有的副作用风险。现代编译器对 `inline` 函数的内联优化，已让「用宏替代小函数」的动机大幅减弱。</span>
- **末尾不能有分号**：`#define CALL(x) do { fn(x); } while (0)` 的惯用法，是为了让宏在使用处像一条语句一样安全。

**规则：能不用函数式宏就不用；一旦使用，参数与整体都要加括号。**

## 4 公式解析：MAX 宏为什么要双括号

把 `MAX` 的写法当「公式」拆开，能一次看懂所有括号的来历：

$$
\text{MAX}(a, b) = \bigl((a) > (b) \,?\, (a) : (b)\bigr)
$$

- **内层括号 `(a)`、`(b)`**：保证参数作为一个整体参与运算，而不被周围运算符「拆散」。`MAX(x & 0xFF, 1)` 若写成 `x & 0xFF > 1 ? ...`，运算符优先级会让结果面目全非。
- **外层大括号**：让整个宏表达式作为一个单元，可以被赋值、被嵌套：`MAX(MAX(a,b), c)` 才不会错位。
- **三元运算符 `?:`**：`条件 ? 真 : 假` 是 C 里唯一的三元运算符，它「求值一次条件、只算分支之一」——这正是 `MAX` 作为表达式能返回值的原因。

对比 `MAX(i++, j)`：若 `i < j` 为假，则 `i++` 在 `(a) > (b)` 里求值一次、在 `(b)` 分支里又求值一次——两次自增，这就是「参数被多次求值」的活生生例子。

## 5 核心对比表：`#ifdef` 与 `#if`

条件编译有两条主要路线，它们解决的问题不同：

| 判别标准 | `#ifdef NAME` / `#ifndef NAME` | `#if 表达式` |
| --- | --- | --- |
| 判断对象 | 宏**是否已定义** | 算术表达式是否非 0 |
| 典型用途 | 头文件保护、调试开关 | 平台/版本分支 |
| 配套写法 | 与 `#define` 搭配 | 与 `defined` 运算符搭配 |
| 例子 | `#ifdef DEBUG` | `#if defined(__linux__)` |

头文件保护（include guard）是每个头文件开头的标配：

```c
#ifndef MY_HEADER_H
#define MY_HEADER_H
/* ... 声明 ... */
#endif
```

它保证同一个头文件在一次编译里只被展开一次，防止重复声明。<span class="marginnote">C11 还引入了 `#pragma once`，作用与 include guard 相同、写法更短；但传统 guard 的可移植性更好，是绝大多数项目的默认选择。</span>调试开关则常写成：

```c
#ifdef DEBUG
    printf("x = %d\n", x);
#endif
```

编译时加 `-DDEBUG` 就打开了调试输出，不加则这些 `printf` 根本不会进入目标代码——**条件编译让「一份源码、多种构建」成为可能**，这是从 C 走向系统编程那条路的第一步。

## 6 标准预定义宏与 #undef / #error

预处理器的工具箱里，还有几个不常提但关键时刻好用的成员。

**标准预定义宏（predefined macro）**：编译器自动提供的宏，最常见的有 `__FILE__`（当前文件名）、`__LINE__`（当前行号）、`__func__`（当前函数名）、`__DATE__`/`__TIME__`（编译时间）。它们可以拼进日志：

```c
fprintf(stderr, "%s:%d in %s: 断言失败\n", __FILE__, __LINE__, __func__);
```

**`__FILE__` 与 `__LINE__` 是在预处理阶段就地替换的**——这正是 `assert` 报错时能精确指出「哪个文件哪一行」的原因，标准库内部也用的是它们。<span class="marginnote">`__func__` 不是宏而是 C99 引入的隐式标识符，其余都是宏。这些符号让我们不必手写「文件名 + 行号」的日志前缀，属于「编译器帮你打工」的典型例子。</span>

**`#undef`**：取消一个已定义的宏。常用于「先定义再重定义」的局部覆盖，也用于头文件里「用完即弃」的临时宏——这能避免宏泄漏到其他编译单元。

**`#error`**：主动制造一个编译错误，带一行消息。它与条件编译连用，形成「版本检查」：

```c
#if !defined(__STDC__)
#error 需要标准 C 编译器
#endif
```

一旦条件不满足，编译立刻失败并打印消息。这比「编译到一半才报奇怪的错」友好得多——**让错误在最显眼的地方炸出来，是预处理器的另一种体贴**。

## 7 小结

- 预处理是编译前的第一道工序：`#include` 做文件包含，`#define` 做文本替换，条件编译决定哪些代码被编译。
- 对象宏是给魔法数字命名；函数式宏快，但有「参数多次求值」「忘记加括号」两大陷阱。
- `#ifdef`/`#ifndef` 判断宏是否定义，`#if` 判断表达式真假；`defined` 运算符可组合二者。
- 头文件保护 `#ifndef ... #endif` 防止重复包含；`-DNAME` 在命令行定义宏，配合调试开关很实用。

在下一节，我们将进入第三篇的主角——**指针基础与指针运算**。指针是 C 语言真正「站起来」的地方，也是理解内存模型的钥匙；请确认宏与预处理的知识已经就位，因为后面大量头文件、接口与宏技巧都建立在它们之上。
