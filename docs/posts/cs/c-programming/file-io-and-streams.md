## 为什么从文件输入输出开始

前面的博文里，程序的数据要么来自键盘，要么写向屏幕——它们统称**标准输入输出（standard I/O）**。但真实程序要跟磁盘文件、网络、管道打交道：读取配置文件、写入日志、加载数据。K&R 第7章的关键洞见是：**无论数据来自终端、文件还是管道，在 C 里都用同一个抽象——流（stream）**。学完这一节，你会拥有「读文件 → 处理 → 写文件」的完整能力，也会第一次理解「一切皆文件」的 Unix 哲学如何落实在 C 的标准库中。

## 1 流：一个统一的数据通道

**流（stream）**：一个有序的字节序列，是程序与外部设备之间交换数据的抽象通道。程序不关心数据实际来自键盘还是磁盘，它只对着流读写。<span class="marginnote">终端、文件、管道、套接字在 C 标准库眼里都是「流」。这套抽象与 Unix「一切皆文件」一脉相承——K&R 第8章《从 C 到系统编程》里你会看到它的底层形式：文件描述符。</span>

C 程序启动时自动获得三条流：

| 流 | 名称 | 默认去向 | 文件指针 |
| --- | --- | --- | --- |
| 标准输入 | stdin | 键盘 | `stdin` |
| 标准输出 | stdout | 屏幕 | `stdout` |
| 标准错误 | stderr | 屏幕 | `stderr` |

**stderr 与 stdout 的去向可以不同**：在 shell 里执行 `./prog > out.txt 2> err.txt`，stdout 写进 `out.txt`，stderr 写进 `err.txt`。这让你能把正常输出与错误信息分流——是工程上区分「结果」与「诊断」的基础。<span class="marginnote">`printf` 写的是 stdout，`fprintf(stderr, ...)` 写的是 stderr。前者被重定向时错误信息也不会丢，后者总会出现在终端上——调试期这是救命的设计。</span>

## 2 打开与关闭：fopen 与 fclose

读写文件的第一步是**打开（open）**它，得到一个 `FILE *` 文件指针：

```c
FILE *fp = fopen("data.txt", "r");
if (fp == NULL) {
    fprintf(stderr, "无法打开 data.txt\n");
    return 1;
}
```

`fopen` 有两个参数：文件名与**模式（mode）**。最常用的模式：

| 模式 | 含义 | 若文件不存在 |
| --- | --- | --- |
| `"r"` | 只读 | 返回 NULL（失败） |
| `"w"` | 只写（清空原有内容） | 创建新文件 |
| `"a"` | 追加写（保留原有内容） | 创建新文件 |
| `"r+"` | 读写（不清空） | 返回 NULL |
| `"w+"` | 读写（清空） | 创建新文件 |

**每一个 `fopen` 都要配一个 `fclose`**：关闭时把缓冲区里的数据真正刷到磁盘，并释放文件指针占用的资源。忘关文件在长跑程序里会耗尽文件描述符——这是一个经典的内存泄漏之外的「资源泄漏」。

## 3 读取与写入：字符、行与格式化

标准库为流提供了三套读写函数，按粒度排列：

**按字符**：`fgetc(fp)` 读一个字符，`fputc(c, fp)` 写一个字符。读到文件末尾返回 `EOF`（通常是 -1）。`getchar()` 就是 `fgetc(stdin)` 的简写。<span class="marginnote">读字符时必须用 `int` 接收 `fgetc` 的返回值，而不是 `char`——因为 `EOF` 这个「哨兵值」超出了 `char` 的表示范围，用 `char` 可能把 `EOF` 截断成普通字符而陷入死循环。</span>

**按行**：`fgets(buf, n, fp)` 从流中读一行到 `buf`（最多 `n-1` 个字符，自动补 `'\0'`）；`fputs(s, fp)` 写一行。

```c
char line[1024];
while (fgets(line, sizeof line, fp) != NULL) {
    /* 处理每一行 */
}
```

`fgets` 读到文件末尾返回 NULL，因此上述循环是「逐行读文件」的标准写法。

**按格式化**：`fprintf(fp, ...)` 与 `fscanf(fp, ...)` 是 `printf`/`scanf` 的流版本。格式化输出到文件、从文件格式化读取，靠的就是它们。

## 4 公式解析：文件大小与缓冲区的关系

文件读写涉及一个实用公式：**读完一个文件需要多少次 `fread`**，取决于文件大小与缓冲区大小：

$$
\text{次数} = \left\lceil \frac{\text{文件字节数}}{\text{缓冲区字节数}} \right\rceil
$$

- **分子**：文件的总字节数，比如一个 1000 字节的文本文件。
- **分母**：每次读取的缓冲区大小，比如 `fread(buf, 1, 256, fp)` 的 256。
- **上取整 $\lceil \cdot \rceil$**：因为最后不足一整块的部分也要再读一次——1000 字节、每次 256，需要 4 次（256+256+256+232），而不是 `1000/256 ≈ 3` 次。

`fread` 的返回值就是「实际读到的元素个数」：读到文件末尾那一轮，返回值可能小于请求的个数。**判断是否读完，要看返回值而不是自己数**——`feof(fp)` 只在读取失败或触底之后才为真，这是初学者常踩的「多读一次」陷阱。

## 5 错误处理：feof 与 ferror

文件 I/O 会失败：磁盘满了、权限不够、文件被删。判断失败有两种方式：

- **`feof(fp)`**：流是否已到文件末尾（触底）。
- **`ferror(fp)`**：流是否发生了错误（除触底外的其他失败）。

区别很关键：`while (!feof(fp)) { ... }` 这种写法是错的——`feof` 要等一次实际读取失败后才会置位，循环体会多执行一次。<span class="marginnote">正确姿势：把读取本身放进条件里，如 `while (fgets(buf, n, fp) != NULL)`，返回值本身就是信号。K&R 与所有 C 教材都强调：用返回值判断结束，而不是用 `feof` 抢先判断。</span>

## 6 核心对比表：字符、行、格式化与二进制

| 维度 | 按字符 | 按行 | 按格式化 | 二进制 |
| --- | --- | --- | --- | --- |
| 代表函数 | `fgetc`/`fputc` | `fgets`/`fputs` | `fscanf`/`fprintf` | `fread`/`fwrite` |
| 数据形态 | 单个字符 | 一行文本 | 有格式的文本 | 原始字节 |
| 典型用途 | 逐字符处理 | 逐行读配置 | 文本数据交换 | 结构体、数组存盘 |
| 结束信号 | `EOF` | NULL | 匹配失败/EOF | 返回元素个数 |

实际项目中四个层次常常混用：读配置用行 + 格式化，存二进制数据结构用 `fread`/`fwrite`。理解「流」这一层抽象后，换设备不换代码——同一套函数既读键盘也读文件，这正是 C 标准库把 I/O 做「薄」的智慧。

## 7 小结

- **流（stream）**是统一的字节序列抽象：终端、文件、管道都长一个样，stdin/stdout/stderr 三条流启动即就位。
- 用 `fopen` 打开、模式分 `"r"`/`"w"`/`"a"`/`"r+"`/`"w+"`；每个 `fopen` 都要配 `fclose`。
- 读写按粒度分三套：字符（`fgetc`/`fputc`）、行（`fgets`/`fputs`）、格式化（`fscanf`/`fprintf`）。
- **用读取函数的返回值判断结束，而不是 `feof`**；`feof`/`ferror` 区分「触底」与「出错」。
- 文件 I/O 会失败，`NULL` 返回值与错误检查是 C 程序员的第二天性。
