## 中断可以「嵌套」吗

响应一个中断时，新中断又来——两种策略：**单重中断**（处理完当前再响应下一个）与**多重中断（嵌套中断）**（高优先级中断打断低优先级服务程序）。现代系统几乎都支持多重中断，靠**中断屏蔽（masking）**管理嵌套的秩序。本课讲单/多重中断的区别、中断屏蔽的实现与优先级管理。<span class="marginnote">「多重中断」让实时系统能保证「高优先级事件不被低优先级拖延」——比如时钟中断（时间关键）可以打断慢速 I/O 的中断服务。嵌套的代价是栈加深、现场多次保存——每层中断都要一套现场。</span>

## 1 单重中断 vs 多重中断**单重中断**：

响应一个中断后**关中断**，处理完恢复现场才开中断，再响应下一个。
特点：简单（无需嵌套栈），但**低优先级中断可能被长时间拖延**（若当前中断处理慢）。

**多重中断（嵌套）**：

响应中断后**开中断**（或按需开），允许更高优先级的中断打断当前服务程序。
特点：实时性好（高优先级优先），但需要**优先级判断 + 现场多层保存**。

**核心概念：单重 = 处理完再开门；多重 = 开门让更急的先进来**。<span class="marginnote">多重中断的「优先级」是动态的：通常约定「新中断的优先级高于当前正在处理的才允许打断」。低优先级中断在服务过程中被高优先级打断，形成「中断嵌套栈」——越深优先级越高，返回时逐层弹出。</span>

## 2 中断屏蔽的机制**中断屏蔽（masking）**：通过控制「允许哪些中断打断当前」，实现嵌套的秩序。

两种屏蔽方式：

**CPU 级**：中断允许标志 IF——IF=0（关中断）屏蔽所有可屏蔽中断。
**设备/优先级级**：中断屏蔽寄存器（IMR）——按位屏蔽指定设备/优先级的中断。

**中断控制器（如 8259A）的屏蔽**：每个中断源有一个屏蔽位，置 1 则该中断被屏蔽——CPU 可以「选择性地不听某些设备的请求」。

**核心概念：屏蔽是「选择性失聪」**——关 IF 是全部不听，设 IMR 是挑着不听。<span class="marginnote">8259A 的 IMR 是 8 位寄存器，每位对应一路 IRQ：置 1 屏蔽该路。中断服务程序里还可以用「嵌套优先级」：设置当前服务的中断优先级，只有高于它的新中断才能打断。这套「可编程屏蔽」让中断管理极其灵活。</span>

## 3 多重中断的处理流程以「服务 A 时来高优先级 B」为例：

1. 响应 A：关中断、保存现场、开中断（允许嵌套）。
2. 服务 A 中，B 请求：B 优先级 > A → 响应 B。
3. 响应 B：保存 A 的现场、服务 B、恢复 A 的现场。
4. 继续服务 A，直到完成。

```
A 中断响应（关中断 → 保存现场 → 开中断）
        │
        ▼
A 服务程序中 ──B 请求（优先级更高）──▶ 响应 B（保存 A 现场）
                                           │
                                           ▼
                                        服务 B
                                           │
                                           ▼
                                        恢复 A 现场
                                           │
        ◀──────────────────────────────────┘
        ▼
    继续 A 服务
```

**关键条件：只有 B 的优先级高于 A 才打断**——否则 B 排队等 A 处理完。<span class="marginnote">「嵌套的判定」由中断控制器硬件完成：它比较「当前服务的中断优先级」与「新请求的优先级」，高则发响应、低则挂起。这个「优先级比较」硬件是多重中断的核心逻辑——也是《中断请求、判优与响应》里判优电路的延伸。</span>

## 4 公式解析：嵌套中断的响应保证设中断 A 的服务时间 $T_A$，中断 B（更高优先级）到达频率 $r_B$：

$$\text{A 的总服务时间} = T_A + \text{B 打断的总次数} \times T_B$$

$$= T_A + (r_B \times T_A) \times T_B$$

逐项拆解：

- **第一步，打断次数**：A 服务期间 B 到达的次数 ≈ $r_B \times T_A$。
- **第二步，打断开销**：每次打断要额外花 $T_B$（B 的服务时间）。
- **第三步，最坏情况**：若 B 频繁且慢，A 会被拖得很长——**低优先级中断的延迟被高优先级中断放大**。

**核心结论：嵌套让「低优先级服务时间」被高优先级抢占——实时分析要算最坏情况**。<span class="marginnote">这是实时系统调度分析（响应时间分析）的核心公式：任务 A 的响应时间 = 自身执行 + 被高优先级任务抢占的时间。实时调度（RMS 等）的可行性分析就是验证「最坏响应时间 < 截止期限」——中断嵌套是这个理论的最简模型。</span>

## 5 辨析｜易错点：多重中断与屏蔽**辨析｜易错点：**

- **多重中断不是默认开启的**：默认响应后关中断（单重），要支持嵌套需在服务程序里显式开中断。
- **「关中断」与「屏蔽」不完全等价**：关 IF 屏蔽一切可屏蔽中断；屏蔽寄存器只屏蔽指定源。实时系统两者都用。
- **中断嵌套的栈**：每层中断用一套现场（压栈），深度 = 嵌套层数——栈空间要够。
- **优先级反转**：低优先级中断持锁时被高优先级打断，高优先级等锁——实时系统的经典问题，需优先级继承解决。

## 6 拓展：优先级反转与实时系统的教训
多重中断的核心风险是**优先级反转（priority inversion）**：
- 低优先级中断持有一个锁，高优先级中断来了想拿同一把锁——高优先级被低优先级「堵住」。
- 更糟的是中等优先级中断可以打断低优先级，让高优先级「绕远路」等待。

经典案例是火星探路者（1997）：高优先级的科学任务被低优先级任务持有的锁阻塞，系统反复复位。修复靠**优先级继承**：低优先级任务临时「继承」高优先级的优先级，直到释放锁。

**核心概念：多重中断的「优先级」不只是响应顺序，还牵涉到锁与共享资源的时序**——中断嵌套越深，这类问题越复杂。

**辨析｜易错点：**「关中断」能防止嵌套，但关太久会延迟真实中断——实时系统要求「关中断时间有上界」。嵌套要开中断，但要靠「优先级比较」控制谁能打断——不是「开中断就乱套」。

## 7 补充：多重中断速记- 单重：处理完再开门；多重：高优先级可打断低优先级。
- 屏蔽两层：IF（全屏蔽）+ IMR（选择性屏蔽）。
- 嵌套判定：新中断优先级 > 当前才打断，由中断控制器比较。
- 低优先级服务时间被高优先级抢占放大。
- 优先级反转用优先级继承解决（火星探路者教训）。

## 8 一句话回顾- 单重处理完再开门，多重让高优先级插队。
- 屏蔽 = IF 全屏蔽 + IMR 选择性屏蔽。
- 嵌套靠优先级比较，优先级反转靠优先级继承。

## 9 一句话回顾- 单重 vs 多重：处理完再开门 vs 高优先级插队。
- IF 全屏蔽 + IMR 选择性屏蔽。
- 优先级反转用继承解决。

## 10 小结- **单重中断**：处理完再开门，简单但低优先级可能被拖。
- **多重中断**：高优先级可打断低优先级，实时性好，需嵌套栈。
- **中断屏蔽**：IF（全屏蔽）与 IMR（选择性屏蔽）两层机制。
- 嵌套判定：新中断优先级 > 当前才打断——由中断控制器比较。
