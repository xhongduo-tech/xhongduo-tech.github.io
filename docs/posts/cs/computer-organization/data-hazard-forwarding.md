## 为什么「数据依赖」让流水线停摆

流水线里相邻两条指令若**数据相关**——后一条要用前一条的结果，而结果还没写回——后一条在 EX 阶段会读到**旧值**。这就是**数据冒险（data hazard）**。数据冒险是三类冒险里最频繁、最影响性能的。本课讲三种数据冒险（RAW/WAR/WAW）、两种解决手段（**停顿**与**数据前递**），以及为什么「前递（旁路）」是现代 CPU 的主力武器。<span class="marginnote">「依赖」的英文 RAW（Read After Write）——后读前写：必须等前一条写完才能读。流水线里 30–50% 的指令是 LOAD/STORE 与算术，数据冒险出现频率极高，是流水线性能的头号制约。</span>

## 1 三种数据依赖| 类型 | 含义 | 方向 |

| --- | --- | --- |
| RAW（写后读） | 后一条要读前一条写的寄存器 | 真依赖，必须等 |
| WAR（读后写） | 后一条写前一条读的寄存器 | 假依赖（乱序时才出现） |
| WAW（写后写） | 两条写同一寄存器 | 假依赖（结果顺序无关） |

**RAW 是真冒险**：指令顺序执行时必须满足「先写后读」，流水线要停顿或前递。
**WAR/WAW 是假冒险**：顺序执行时天然满足，只在乱序执行/多发射时成为问题（见《寄存器重命名》）。

**核心概念：RAW 是数据冒险的主角**——`sub` 中 `%rax` 要读 `旧值`，而 `add` 在 WB 才写 `%rax`。<span class="marginnote">「假冒险」的名字有欺骗性：它们不是逻辑上的依赖，只是「硬件资源（寄存器名）复用」带来的伪约束。乱序执行的解法是「寄存器重命名」——给每个逻辑寄存器更多物理寄存器，消除 WAR/WAW。</span>

## 2 数据冒险的三种场景在五级流水线里，按冲突发生的阶段分：

**EX 冒险**：`add` 的 EX 阶段算出的结果，紧邻的 `sub` 在 ID 已经读了旧值——最常见。
**MEM 冒险**：LOAD 的 MEM 阶段才取到数据，紧邻的下一条在 EX 用了旧值。
**写后写/读后写**：多发射时出现。

**重点：数据冒险的严重程度取决于「两指令间距」**——间隔越大（中间隔了几条无关指令），越可能自然躲开（结果已写回）。<span class="marginnote">编译器会「调度指令」：把无关指令插到相关指令之间，拉开距离，让结果有时间写回——这叫「指令调度（instruction scheduling）」，是编译器优化流水线友好度的核心手段。硬件前递 + 软件调度双管齐下。</span>

## 3 解决方案一：停顿（stall）**停顿（stall）**：检测到数据冒险时，让后一条指令在 ID 阶段**等一拍**，直到结果写回。

```
时钟周期:   1    2    3    4    5    6
add:       IF   ID   EX   MEM  WB
sub:            IF   ▢    ID   EX   MEM  WB
                     ↑
                 停顿一拍（等 add 的结果写回）
```

**优点**：实现简单。**缺点**：每停一拍 CPI+1，性能损失大——因为大多数程序都有大量数据依赖。

**核心结论：停顿是「万不得已」的方案**——它正确但慢，现代 CPU 只在「前递解决不了」时用（如 LOAD 后紧邻使用，LOAD 结果 MEM 阶段才有，前递不了）。<span class="marginnote">「LOAD-use 冒险」是停顿的典型：`LOAD` 后紧邻 `ADD`——LOAD 的结果在 MEM 阶段才出来，下一条 EX 就要用，前递也来不及，只能停一拍。这是数据冒险里最贵的一种，编译器会尽量把无关指令插在中间。</span>

## 4 解决方案二：数据前递（旁路）**数据前递（forwarding/bypassing）**：把结果在「算出来的那一刻」直接旁路给需要的指令，**不等写回**。

EX 阶段算完，结果不走「写回寄存器堆」的常规路径，而是**直接旁路**到后续指令的 EX 输入。
硬件：数据通路加「旁路多路选择器（MUX）」，冒险检测单元判断「结果可旁路」。

```
时钟周期:   1    2    3    4    5    6
add:       IF   ID   EX   MEM  WB
sub:            IF   ID   EX   MEM  WB
                        │
              EX 算出的结果经旁路 MUX 直接送 sub 的 EX 输入（不等写回）
```

**优点**：绝大多数 RAW 冒险**零停顿**解决。**缺点**：需要旁路 MUX 与检测逻辑，增加数据通路的复杂度与延迟。<span class="marginnote">前递的本质是「缩短数据的可见路径」：结果在 EX/MEM 阶段就能被消费，而不是非要等 WB 写回寄存器堆再读。现代 CPU 的 ALU 输入前多了一组 MUX，就是旁路的物理存在。CS:APP 的 Y86-64 处理器设计里，前递是核心加分项。</span>

## 5 公式解析：前递解决不了的冒险前递对「EX 结果 → EX 使用」有效，但对 LOAD-use 无效（LOAD 结果在 MEM 才有）：

```
时钟周期:   1    2    3    4    5    6
LOAD:      IF   ID   EX   MEM  WB
ADD:            IF   ID   ▢    EX   MEM  WB
                         ↑
              LOAD 结果 MEM 阶段才有，前递来不及 → 停一拍
```

设 LOAD 后紧邻使用的概率为 $p$，前递消除其余冒险，则平均停顿：

$$\text{平均停顿} = p \times 1 \ (\text{LOAD-use 停顿})$$

逐项拆解：

- **第一步，前递覆盖**：`EX` 的冒险（add 到 sub）被旁路，零停顿。
- **第二步，前递盲区**：`LOAD-use` 的冒险（结果 MEM 才有）前递不了，停一拍。
- **第三步，平均代价**：只算 LOAD-use 的停顿概率。

**核心结论：前递 + 停顿的分工——前递解决「算完即用」，停顿兜底「LOAD 刚取到就要用」**。<span class="marginnote">统计上，LOAD-use 停顿约占指令流的 10–20%，每停一拍 CPI 相应增加。编译器调度（把不相关指令插进 LOAD 与使用之间）能把这部分降到一半以下——软硬协同的例子。</span>

## 6 考点速记：数据冒险三问**问一：三类依赖？** RAW（真，后读前写必须等）、WAR/WAW（假，乱序才成问题）。

**问二：两种解法？** 停顿（等一拍）与**数据前递/旁路**（结果算出来直接给需求方，不等写回）。

**问三：前递的盲区？** LOAD-use——LOAD 结果 MEM 阶段才有，紧邻使用前递不了，只能停顿。

**五条必记**：

- 前递硬件：ALU 输入前加旁路 MUX，冒险检测单元判断「可旁路」。
- 前递覆盖「算完即用」（EX 冒险）；LOAD-use 是唯一常态停顿源。
- 编译器「指令调度」：把无关指令插到相关指令之间拉开距离。
- 假冒险（WAR/WAW）由寄存器重命名消除（乱序执行）。
- 停顿代价直接进 CPI：CPI = 1 + 停顿/指令。

**辨析｜易错点：**RAW 是真依赖（逻辑必须），WAR/WAW 是假依赖（名字冲突）——Tomasulo 重命名消除假依赖，前递加速真依赖，两者配合。

- 自测 3：前递与停顿怎么分工？

## 7 一句话回顾- RAW 真依赖、WAR/WAW 假依赖。
- 前递解决算完即用、停顿兜底 LOAD-use。
- 编译器调度 + 硬件前递双管齐下。

> 一句话：前递解决算完即用、停顿兜底 LOAD-use。
> 一句话：RAW 真依赖、WAR/WAW 假依赖。

## 8 小结- 三种依赖：**RAW（真）**、WAR/WAW（假，乱序才成问题）。
- 数据冒险最常见形态：EX 冒险（算完即用）、MEM 冒险（LOAD 后紧邻用）。
- **停顿**：等一拍，简单但 CPI+1。
- **前递（旁路）**：结果算出来直接旁路给需求方，零停顿解决绝大多数 RAW。
- 前递盲区：LOAD-use 冒险，只能停顿 + 编译器调度缓解。

- RAW 真依赖、WAR/WAW 假依赖
- 前递解决算完即用
- 停顿兜底 LOAD-use
- 编译器调度拉开距离
- 旁路 MUX+检测逻辑
- CPI = 1 + 停顿/指令
- LOVE-use 占指令流 10-20%
- 假依赖由重命名消除
