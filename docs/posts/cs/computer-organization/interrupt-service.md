## 中断服务程序该「做多少事」

上一课 CPU 已经「赶到现场」（中断响应），本课看服务程序本身：它**保存/恢复现场、处理设备、返回**。一个核心设计问题是——**服务程序该在里面做多少工作？** 做少了处理不完，做多了阻塞系统。本课讲中断服务程序的完整结构、与主程序的数据交换、以及「上半部/下半部」的现代拆分思想。<span class="marginnote">「中断服务程序要短」是铁律：它运行在被打断程序的上下文、占用中断窗口，越长越阻塞其他中断与主程序。现代 Linux 把中断处理拆成「上半部（top half，快）」「下半部（bottom half，慢）」，正是「服务程序尽量短」的工程落实。</span>

## 1 中断服务程序的完整结构```c

void interrupt_handler(void) {
    // 1. 保存被中断程序的寄存器现场（硬件已保存 PC/PSW）
    save_registers();

    // 2. 处理设备：读状态、读写数据
    process_device();

    // 3. 发中断结束（EOI）给中断控制器
    send_EOI();

    // 4. 恢复现场
    restore_registers();

    // 5. 中断返回（iretd）
    iret;
}
```

**核心概念：中断服务程序的五段式**——保存、处理、EOI、恢复、返回。其中 **EOI（End of Interrupt）** 必须发给中断控制器，否则后续中断被阻塞。<span class="marginnote">「忘记发 EOI」是嵌入式/驱动开发里的经典 bug：中断控制器以为 CPU 还在忙，其他中断全部被屏蔽——系统看似「卡死」。8259A 的 `out 0x20, 0x20` 就是发 EOI 的经典操作。这段细节看似小，实际坑无数。</span>

## 2 服务程序与主程序的数据交换中断处理的核心是把设备数据交给主程序：

- **共享内存/环形缓冲**：设备数据写入环形缓冲，主程序（进程）稍后取——中断服务程序只「放」，主程序「取」。
- **信号量/标志**：中断置位一个标志，主程序轮询该标志再处理。

**关键约束：中断服务程序不能调用会阻塞的函数**（sleep、锁、分配内存）——因为它运行在中断上下文，不能睡眠、不能等锁。<span class="marginnote">「中断上下文不能睡眠」是驱动开发的铁律：中断处理程序不能 `sleep`、不能拿会阻塞的锁、不能用可能触顶页面的 malloc——因为「没人在它后面调度」。所以中断处理只能做「快事」：搬数据、置标志、发 EOI，重活留给下半部或进程上下文。</span>

## 3 上半部与下半部现代操作系统把中断处理拆成两半：

- **上半部（top half，硬中断）**：关中断状态下快速处理——保存数据、应答设备、发 EOI，立即返回。要求毫秒级完成。
- **下半部（bottom half，软中断）**：开中断状态下稍后处理——数据解释、协议处理、唤醒进程。可以慢、可以阻塞。

**核心概念：上半部快进快出、下半部从容善后**——上半部保证「设备不丢数据、系统不被阻塞」，下半部把重活推迟到安全时机。<span class="marginnote">Linux 的下半部机制有多个：softirq（软中断）、tasklet、workqueue。网卡收包就是经典例子：硬中断只把包搬进内存环形缓冲就返回，软中断再做协议解析——否则 GB/s 的网络流量会让 CPU 死在中断处理里。</span>

## 4 公式解析：中断开销与设备速率设每包中断处理（上半部）耗时 $T_{isr}$、设备包速率 $r$：

$$\text{中断 CPU 占用} = r \times T_{isr}$$

$$\text{可承受的最大速率} = \frac{1}{T_{isr}}$$

逐项拆解：

- **第一步，每包代价**：每次中断从响应到返回的总时间。
- **第二步，占用率**：速率 × 每包代价——包越快，CPU 越忙。
- **第三步，极限**：速率超过 $1/T_{isr}$，CPU 全在中断处理——系统崩溃（活锁）。

例：每包中断 2μs，可承受 500K 包/秒；GB 网卡 1.5M 包/秒——**中断频率太高，必须合并**。

**核心结论：高速设备的中断频率可能压垮 CPU**——解法是「中断合并（interrupt coalescing）」与「NAPI/轮询」。<span class="marginnote">「中断风暴」是高吞吐网络的真实问题：每包一次中断，CPU 忙于响应中断反而收不了包。现代网卡驱动用「中断合并」（攒一批包再中断一次）与「NAPI」（忙时切换轮询、闲时恢复中断）——把中断频率降到 CPU 能承受的水平。这是「中断 vs 轮询」在现代的再平衡。</span>

## 5 辨析｜易错点：中断服务程序**辨析｜易错点：**

- **服务程序里的「现场保存」与硬件保存不同**：硬件只存 PC/PSW，通用寄存器由服务程序开头/结尾自己存。
- **EOI 不是可选项**：不发 EOI，中断控制器认为中断没结束，屏蔽后续中断。
- **服务程序不能 sleep/拿锁**：中断上下文没有调度器——「能阻塞的代码绝不能出现在硬中断里」。
- **上半部/下半部的「下半部」不是「后一半时间」**：它是「推迟到安全上下文处理的那部分工作」——概念上完全不同的执行环境。

## 6 拓展：Linux 中断上下文的「不能做的事」Linux 中断服务程序（硬中断）的约束是驱动开发的常识：

- **不能睡眠**：中断上下文没有调度器，「睡下去没人叫醒」。
- **不能拿自旋锁之外的重锁**：等锁会阻塞整个中断路径。
- **不能做可能缺页的内存分配**：`malloc` 可能触发缺页（要睡眠），要用 `GFP_ATOMIC`。
- **不能做慢速操作**：磁盘 I/O、网络收发都不行——只做「搬数据、置标志、发 EOI」。

**核心概念：硬中断是「最短路径」**——它只保证「不丢数据、及时应答」，重活交给下半部或进程上下文。

**辨析｜易错点：**「上半部快、下半部慢」不是「时间先后」而是「执行环境」——上半部在关中断的内核上下文，下半部在开中断的安全上下文。硬中断里绝不能调用任何可能睡眠的函数，这是铁律。
