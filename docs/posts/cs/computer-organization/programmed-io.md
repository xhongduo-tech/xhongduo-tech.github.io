## 为什么最简单的方式「最浪费」

I/O 方式的第一步是**程序查询（programmed I/O）**：CPU 循环读设备状态寄存器，直到「就绪」才读写数据。它正确、简单，但让 CPU 陷入无意义的轮询等待。理解程序查询，是理解「为什么需要中断」的起点——它的缺点正是中断要补的洞。<span class="marginnote">程序查询也叫「轮询（polling）」：CPU 反复「问候」设备。它的致命伤是「忙等（busy-wait）」——CPU 把宝贵的执行时间浪费在「问设备好了没」上，设备没准备好就一直在空转。</span>

## 1 程序查询的流程以「CPU 从输入设备读一个字节」为例：

1. CPU 读**状态寄存器**，检查「数据就绪（ready）」位。
2. 未就绪 → 回到第 1 步（**轮询等待**）。
3. 就绪 → CPU 读**数据寄存器**，取走数据。
4. 需要时写**控制寄存器**（发下一命令）。

```c
while ((status_reg & READY) == 0)   // 反复读状态寄存器，检查就绪位
    ;                               // 未就绪：忙等轮询
data = data_reg;                    // 就绪：读数据寄存器取走数据
```

**核心概念：程序查询的本质是「CPU 主动、反复检查」**——CPU 控制一切，设备被动应答。<span class="marginnote">查询接口的硬件很简单：状态寄存器（一位 ready 位）+ 数据寄存器 + 少量控制逻辑。查询的软件更简单：一条循环 + 一个分支。但「简单」的代价是 CPU 时间——设备慢时，CPU 大部分时间在空转轮询。</span>

## 2 查询接口的组成程序查询接口的核心部件：

**状态寄存器**：含「就绪/忙/错误」位，CPU 读它判断。
**数据缓冲寄存器**：暂存数据。
**控制逻辑**：产生设备读写控制信号。

**重点：查询接口不需要中断逻辑、不需要 DMA 逻辑**——它是最简接口，CPU 通过「读状态 → 读写数据」完成全部交互。<span class="marginnote">「状态寄存器 + 数据寄存器」是查询接口的最小配置。查询方式的判断依据就是状态位——`ready`（就绪）位为 1 才可读写。这也是《I/O 接口》一课「三大寄存器」里最核心的两个。</span>

## 3 查询方式的性能代价设设备就绪前平均等待 $W$ 个周期，每次查询（读状态+判断）花 $q$ 个周期：

$$\text{CPU 轮询开销} = \frac{W}{q} \times q = W \quad \text{周期/次传输}$$

**重点：轮询期间 CPU 除了「问设备」什么也干不了**——若设备平均 1ms 就绪、查询一次 100 周期，CPU 要空转约 100 万周期等一个字节。

**核心概念：忙等（busy-wait）是查询方式的天花板**——CPU 利用率在慢速设备下惨不忍睹。<span class="marginnote">例：键盘 10 字符/s、CPU 3GHz——每字符轮询约 3 亿周期空转。这就是为什么「键盘这种慢设备绝不能用轮询」——除非系统没别的事干（早期单任务系统）或设备极快（寄存器状态变化毫秒内可查）。</span>

## 4 公式解析：查询方式 CPU 利用率设设备数据率 $r$（每秒传输次数）、每次轮询耗时 $q$、设备就绪时间 $T_d$：

$$\text{CPU 用于轮询的比例} = \frac{q/T_d}{1/r} \times \frac{q}{?} \Rightarrow \approx r \cdot q$$

简化模型（每次传输轮询一次，轮询循环每次迭代 $c$ 周期）：

$$\text{CPU 占用} \approx r \cdot c \quad (\text{每次传输耗 c 周期})$$

逐项拆解：

- **第一步，传输频率**：每秒 $r$ 次传输。
- **第二步，每次代价**：每次传输前轮询 $c$ 周期（可能多轮询几次）。
- **第三步，占用率**：$r \times c$——设备越快（r 大），CPU 越忙。

例：串口 115200 bps ≈ 14.4KB/s，若每字节轮询 100 周期、CPU 3GHz：

$$\text{占用} = 14400 \times 100 / 3\times10^9 \approx 0.05\%$$

快设备（如 1GB/s 网卡）：每字节 100 周期 → 占用 33%——**高速设备让查询方式直接不可用**。

**核心结论：查询方式的 CPU 占用率随设备速率线性增长**——低速设备可用，高速设备必须换中断/DMA。<span class="marginnote">这就是为什么网卡（GB/s 级）绝不用轮询而用中断 + DMA，而键盘鼠标（低速）在现代系统里其实也是「中断 + 轮询混合」（有数据时中断、中断处理里轮询清空缓冲）。「设备速度决定 I/O 方式」是选择的第一法则。</span>

## 5 辨析｜易错点：查询方式要点**辨析｜易错点：**

- **查询是「CPU 主动」，中断是「设备主动」**：这是查询与中断的本质区别。
- **查询方式也能正确工作**：正确性没问题，问题是**效率**——它不是「错」，是「浪费」。
- **查询不一定比中断简单**：设备多时，CPU 要轮流查询所有设备，调度逻辑也麻烦。
- **「轮询」在现代依然存在**：网卡驱动收包、协程/事件循环（select/poll）都是轮询思想——轮询在「设备快、等待短」时反而高效。

## 6 拓展：轮询在现代系统的「复活」轮询看似被中断取代，但现代系统里它以新形态回归：- **事件循环**：Node.js、select/poll/epoll——程序主动「轮询」就绪事件，而非每事件一个线程。
- **NAPI**：网卡高流量时关闭中断、改为轮询收包——轮询在高负载下反而高效。
- **自旋锁**：多核同步里的自旋等待，本质是「轮询锁状态」。

**核心概念：轮询的适用条件是「等待时间短、频率高」**——此时轮询的确定性（无中断切换开销）优于中断。中断适合「低频、长等待」，轮询适合「高频、短等待」——两条曲线相交，选择看场景。

**辨析｜易错点：**「查询方式一定比中断差」是错的——若设备响应极快（如寄存器状态变化 < 中断切换开销），轮询反而快。判断标准是「等待时间 vs 中断开销」。

## 7 补充：程序查询速记- 流程：读状态 → 未就绪轮询 → 就绪读写数据。
- 接口：状态寄存器 + 数据寄存器，硬件最简。
- 忙等是致命缺点——CPU 在慢速设备上空转百万周期。
- CPU 占用 ≈ 设备速率 × 每次轮询代价。
- 轮询在现代「复活」：事件循环、NAPI、自旋锁。

## 8 一句话回顾- 查询 = CPU 主动轮询状态寄存器，忙等浪费。
- 高速设备下占用率随速率线性爆炸。
- 轮询在现代以事件循环/NAPI 形态复活。

## 9 核心公式
- 流程：读状态→轮询→读写数据。
- CPU 占用 ≈ r × c（速率 × 每字节轮询代价）。
- 高速设备下占用率线性爆炸。
- 轮询在现代复活：事件循环、NAPI。

## 10 小结- 程序查询流程：**读状态 → 未就绪则轮询 → 就绪则读写数据**。
- 查询接口：状态寄存器 + 数据寄存器，硬件最简。
- **忙等**是查询的致命缺点：CPU 在慢速设备上空转百万周期。
- CPU 占用率 ≈ 设备速率 × 每次轮询代价——高速设备下不可用。
- 「设备速度决定 I/O 方式」：低速可轮询，高速要中断/DMA。
