## 为什么单体时代的不变量会瓦解

单体里，一次请求的生命周期在一个进程内：一条日志流、一份调用栈、一个线程 ID，问题定位几乎就是「打开日志 + 打断点」。微服务把这一切拆没了——**一次用户请求会穿越 N 个服务、N 份日志文件、N 台机器**，传统「日志 + 监控」的工具链对「这条请求为什么 3 秒才返回」无能为力。

Newman 在《Building Microservices》第 8 章把这个问题系统化：**可观测性（observability）**不是「更多日志」，而是「系统内部状态能否从外部输出被推断出来」。本专题第 1 篇原则⑦「高度可观测」在这里落地。我们按三个层次展开：日志（离散事实）、指标（聚合统计）、链路追踪（单次请求的完整旅程）。<span class="marginnote">「可观测性」一词来自控制论：一个系统若其状态可从输出唯一确定，则它是可观测的。软件领域借用了这层严格含义——只看 metrics 曲线看不出「哪一行代码慢」，要能回答这种问题才算可观测。</span>

「可观测性」常被误解成「监控得更好」，但它其实是一道更硬的问题：**从系统的外部输出，能不能唯一推断出系统的内部状态？** 本课先把三支柱讲清楚，再重点落在链路追踪——因为它是唯一能回答「这一次请求为什么慢」的工具，也是本专题里与并发、网络、时序结合得最紧的一课。

## 1 三根支柱：日志、指标、追踪

| 支柱 | 回答的问题 | 形态 | 成本 |
| --- | --- | --- | --- |
| 日志（Logs） | 具体发生了什么 | 离散事件文本 | 最便宜，但信息爆炸 |
| 指标（Metrics） | 系统的健康趋势 | 聚合数值（延迟/错误/饱和度） | 便宜，适合告警 |
| 追踪（Traces） | 这一次请求走过了什么 | 结构化的 span 树 | 昂贵，需要采样 |

**重点：三者不是替代关系，而是互补。** 指标告诉你「订单接口 P99 延迟在恶化」（趋势），追踪帮你「定位恶化的是哪一个调用」（归因），日志给你「那个调用里到底发生了什么」（细节）。一套完整的可观测性 = 三者的协同，缺一不可。

三支柱的分工可以一句话记：**指标抓「是不是出事了」，追踪抓「是哪一个请求出事了」，日志抓「那个请求里到底发生了什么」。** 三者分别回答「趋势、归因、细节」三个递进的问题——缺一层，故障排查就会在某一环断掉。

## 2 关联 ID：把分散的日志粘起来

日志的天然弱点是被服务切碎。**关联 ID（correlation ID）** 是这个问题的廉价解法：**为每次请求生成一个全局唯一 ID，随请求上下文在服务间传递，所有服务写日志时都带上它。** 于是「这个 ID 的所有日志」就能把一次请求的完整旅程拼回来。<span class="marginnote">关联 ID 的实现很简单——HTTP 头（如 `X-Request-Id`）、消息的 header 字段——但要求所有服务都遵守约定并自动传递。约定缺失的团队，往往在故障时才发现「两个服务日志里根本没有共同的键」。契约（第 14 篇）在这里以「日志契约」的形式出现。</span>

关联 ID 的另一个关键点是**约定必须成为跨团队的契约**：`X-Request-Id` 从网关注入，所有服务自动透传并写进日志，最好 SDK 化后让每个服务零手工接入。没有约定的团队，往往在故障当晚才发现「两个服务的日志里根本没有共同的键」——到那时才补，代价极高。

关联 ID 是追踪的「轻量版」：它只保证「日志可关联」，不保证「调用间的因果关系与耗时结构」。要看到后者，需要真正的分布式追踪。

## 3 分布式追踪：给每次请求画一棵树

**分布式追踪（distributed tracing）**：为跨越多个服务的请求建立一棵**调用树**——每个服务的每次处理记录为一个 **span**，span 间通过父子关系组成树，整棵树（连同所有 span 的时序与耗时）称为一个 **trace**。

span 携带的关键字段（以 OpenTelemetry 数据模型为例）：

| 字段 | 含义 | 示例 |
| --- | --- | --- |
| `trace_id` | 整棵调用树共享的标识 | 128 位随机数 |
| `span_id` | 本 span 自己的标识 | 64 位随机数 |
| `parent_span_id` | 父 span 的标识，根 span 为 null | 指向调用方 |
| `name` / `kind` | 操作名与角色（客户端/服务端） | `GET /orders/:id` |
| `start_time` / `duration` | 开始时刻与耗时 | 精度到纳秒 |
| `status` / `attributes` | 结果（OK/ERROR）与业务标签 | `http.status_code=200` |

**传播（propagation）**：调用方在出站请求里注入 `trace_id` 与 `span_id`，被调用方取出后创建自己的 span，`parent_span_id` 指回调用方——**追踪上下文就这样随业务流量在服务间自动接力**。<span class="marginnote">标准化的产物是 OpenTelemetry：它统一了 span 的数据模型、传播协议（W3C Trace Context）与 SDK，使「多语言、多供应商」的追踪可以互通。W3C Trace-Context 头 `traceparent` 与 HTTP 的 keep-alive、代理链一样，是「横跨进程的信息必须标准化才能活着穿过」的又一例证。</span>

有了调用树，两个老大难问题迎刃而解：

- **延迟归因**：树里每一层的耗时一目了然——「3 秒里 2.6 秒花在调用支付服务的 span 上」，问题直接被钉死在某一段。
- **错误定位**：哪个服务抛了异常、在树的哪一层，路径可还原，不再靠人工翻 N 份日志猜。

更进一步，trace 还让「请求画像」成为可能：同一接口的耗时分布、慢分支的占比、依赖的健康度，都能从 trace 聚合出来——**trace 不只在排障时有用，它本身就是一份最细粒度的性能数据**。

## 4 公式解析：追踪的存储账单

追踪好是好，但它的代价要用算术算清。每秒写入存储的 span 数：

$$N = R \times s \times p$$

其中 $R$ 是每秒请求数，$s$ 是每个请求平均产生的 span 数，$p$ 是采样后保留的比例（$0 < p \le 1$）。三步拆解：

- **第一步，先算全量**：$R = 10{,}000$ 次/秒、每个请求平均 $s = 20$ 个 span 时，全量是 $N = 200{,}000$ span/秒。
- **第二步，乘上单 span 大小**：若平均每个 span 序列化后约 1 KB，每秒要写约 200 MB——一天就是 17 TB 量级，绝大多数系统全量存不起。
- **第三步，看采样这个杠杆**：把 $p$ 设为 1%（$p = 0.01$），每秒降到 2 MB、一天约 170 GB，回到可接受区间。**采样率每降一个数量级，存储成本就降一个数量级——这是追踪经济学里最直接的旋钮。**

**重点：$p$ 不是均匀地选，而是「按价值选」。** 出错的 trace、超慢的 trace 一定要保留（$p=1$），健康的 trace 才按比例抽样——这正是下一节「尾部采样」的动机。

这套算术也解释了为什么采样不是可选项：**可观测性的目标不是「全量数据」，而是「对排障有用的数据」**——保留错误与慢请求的完整调用树，比保留 100% 的健康请求更有价值。

## 5 采样：追踪的代价必须被管理

追踪的隐形代价是**存储与流量爆炸**：一个高流量系统每秒产生数百万 span，全量存储不可承受。于是有了**采样（sampling）**——只保留一部分 trace：

- **头部采样（head sampling）**：请求刚进来就决定存不存，简单，但会导致「慢请求」这一最需要留痕的样本可能被随机漏掉。
- **尾部采样（tail sampling）**：等 trace 结束再统一决策，可做到「凡是出错或超慢的 trace 必存，健康的按比例抽样」——精确，但需要缓冲与集中决策，成本高。
- 工程常态是**「全量采集 + 按需保留」的折中**：头部采样降量，对错误与慢 trace 做例外提升。

还有一类工程化的进阶：**基于优先级的采样**——给每个 span 打优先级标签（错误 > 慢 > 常规），采样器按优先级分配保留预算，实现「错误必留、慢的尽量留、健康的随机留」的三级梯度，让每一分存储都花在最值得保留的 trace 上。

**辨析｜易错点：指标监控不能替代追踪。** 指标能告诉你「P99 在恶化」，却答不出「恶化的是哪一条调用路径」——因为指标天然丢弃了「哪次请求」这个维度。追踪补上的正是这个维度；这也解释了为什么三支柱缺一不可。

**辨析｜易错点：追踪 ≠ 性能剖析。** 追踪记录「一次请求的调用结构」；性能剖析（profiling）统计「CPU/内存花在哪段代码」。两者都看「时间去哪了」，但粒度不同：追踪在进程间、剖析在函数内。生产系统两者都要，别用一个替代另一个。

## 6 术语速查：可观测性的词汇表

| 术语 | 一句话定义 | 记忆锚点 |
| --- | --- | --- |
| 日志（Logs） | 离散事件文本，回答「发生了什么」 | 具体事实 |
| 指标（Metrics） | 聚合数值，回答「趋势如何」 | 可告警的统计量 |
| 追踪（Traces） | 单次请求的调用树，回答「这次怎么走的」 | span 树 |
| 关联 ID | 随请求传播的全局唯一 ID，粘合分散日志 | 日志的胶水 |
| span | 一次服务处理的记录（父子关系成树） | 树的一个节点 |
| 采样 | 只保留部分 trace 以控制存储成本 | 留贵的、扔便宜的 |
| 头部 / 尾部采样 | 请求开头决定 / 请求结束再决定存不存 | 快而粗 / 精而贵 |
| OpenTelemetry | 统一 span 模型、传播协议与 SDK 的标准 | 可观测的事实标准 |

## 7 小结

- 可观测性三支柱：**日志（发生了什么）、指标（趋势如何）、追踪（这次请求走了什么）**——互补而非替代。
- **关联 ID** 是廉价的日志粘合剂，靠「随请求传播 + 全链路写日志」拼回完整旅程。
- **分布式追踪**用 `trace_id / span_id / parent_span_id` 构造调用树，直接定位**延迟归因与错误路径**。
- **OpenTelemetry** 统一了 span 模型、传播协议与 SDK，是跨语言可观测的事实标准。
- **采样**是追踪的经济学：全量采集不可承受，按「错误必存 + 健康抽样」折中。
