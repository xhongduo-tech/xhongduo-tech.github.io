## 为什么地址会成为一个问题

单体时代不存在「服务发现」：进程地址就是配置里那一行 `localhost:8080`，写死即可。微服务把这个问题推上台面：**一个服务通常有多个实例，实例的 IP 与端口会因扩缩容、故障迁移、灰度发布而不断变化。** 调用方如果手里握着写死的地址，扩缩容就变成了一次配置变更事故。

Richardson 在《Microservices Patterns》第 4 章给出系统解法：**服务注册表（service registry）+ 服务发现（service discovery）**。它回答两个问题：实例把「我在这里」写进哪里？（注册）；调用方从哪知道「它在哪」？（发现）。<span class="marginnote">这个问题在计算机网络里早有原型：DNS 把「名字→地址」的动态映射交给分布式解析系统，让「换 IP 不换名字」。服务发现是 DNS 在「进程级、秒级变化」尺度上的重演——差别在于 DNS 的 TTL 是分钟级，而服务实例的生命周期常常只有几分钟。</span>

## 1 注册表：一张动态的地址簿

**服务注册表（service registry）**：保存服务实例网络地址（以及元数据）的数据库，实例启动时写入、续租、退出时删除。它本质上就是一张**动态 DNS 表**。

注册表要满足三个工程要求：

**高可用**：所有调用的第一步都依赖它，它必须多副本部署——Eureka、Consul、etcd、Zookeeper 都是常见载体。
- **近实时性**：健康实例列表必须跟上实际状态，否则调用方会打到已死实例。实现靠**心跳**：实例定期续租（lease），超时未续租的实例被注册表剔除。<span class="marginnote">心跳与租约是分布式系统的基础构件：Zookeeper 会话、Kubernetes 的 liveness probe、TCP 保活都是同一种「用周期信号证明我还活着」的机制。第二级《操作系统》的进程监控与《计算机网络》的 TCP 定时器会反复见到它。</span>
**区分健康与存活**：注册表最好能区分「进程活着但拒绝服务」——只做 TCP 探活不够，业务级健康检查（health endpoint）才准确。这关系到调用方是否把流量打进一个「半死」的实例。

**辨析｜易错点：注册表与网关不是同一件事。** 网关负责「路由 + 横切关注点」，注册表负责「告诉路由：目标在哪」。网关是发现机制的**消费方**，不是注册表本身。很多落地系统里网关内嵌了注册表客户端，两者常常被误认为一体。

## 2 两种发现方式：客户端式与服务端式

按「谁去查注册表」，发现机制分两类：

**客户端发现（client-side discovery）**：客户端（或调用方）自己查注册表，拿到候选实例列表后按负载均衡策略挑一个直接调用。

- 优点：不需要额外跳点，架构简单，延迟最低。
- 缺点：每种语言/每个客户端都要实现「查注册表 + 负载均衡」逻辑——技术栈越杂，重复实现越多。Netflix OSS（Eureka + Ribbon）是它的经典代表。

**服务端发现（server-side discovery）**：客户端不查注册表，只把请求发给一个固定的负载均衡器/网关；由它查注册表并把请求转发给某个实例。

- 优点：客户端完全无感，只需知道负载均衡器地址；负载均衡逻辑集中一处，可统一治理。
- 缺点：多一跳；负载均衡器成为新的可扩展性与可用性焦点。**Kubernetes 的 Service + kube-proxy + DNS 就是服务端发现的现代实现**——Service 提供一个稳定 VIP，真正的 Pod 地址由 kube-proxy 维护。

| 维度 | 客户端发现 | 服务端发现 |
| --- | --- | --- |
| 谁查注册表 | 客户端 | 负载均衡器 / 网关 |
| 客户端复杂度 | 高 | 低 |
| 跳数 | 最少 | 多一跳 |
| 治理集中度 | 分散 | 集中 |
| 代表作 | Netflix Eureka+Ribbon | Kubernetes Service、Consul 服务端模式 |

**重点：两种方式无优劣，取决于技术栈的统一程度与运维能力。** 语言栈统一、追求极致延迟，选客户端式；技术栈杂、希望把负载均衡收归一处治理，选服务端式。Kubernetes 生态里服务端发现已事实成为默认。

## 3 两种注册方式：自注册与第三方注册

按「谁往注册表里写」，注册又分两类：

**自注册（self-registration）**：实例自己负责注册与注销——启动时写、心跳续租、退出时删。

- 优点：简单直接，不用额外组件。
- 缺点：注册逻辑散落在每个服务的实现里，改注册策略要改所有服务。

**第三方注册（third-party registration）**：由一个独立组件（registrar）负责监控实例的生命周期并代为注册。典型例子是 Kubernetes 的 sidecar 模式，或者独立的代理进程去探测「旁边」的服务是否存活再注册。

- 优点：业务代码零侵入，注册逻辑集中一处。
- 缺点：多一个必须正确运行的组件——**registrar 自己也要高可用**，否则它挂了，健康实例也会被误删。

## 4 谁在使用发现机制

发现机制不是孤立的，它嵌入一条完整链路：**客户端 →（发现）→ 负载均衡 →（发现）→ 目标实例**。在本专题里你会发现它反复被复用：

- **API 网关**（第 3 篇）查注册表决定把请求路由给哪个实例。
- **客户端调用库**（如 gRPC 的 resolver、Ribbon）查注册表做客户端负载均衡。
- **服务网格的数据面**（Envoy、Linkerd）代理每个服务的进出流量，在代理里完成服务端发现——这是把「服务端发现」下沉到每个服务的网络栈，是今天大规模微服务的主流形态。<span class="marginnote">服务网格把发现、熔断、可观测性统一收进代理，业务代码几乎不再关心网络——这与「面向切面编程把横切关注点从业务代码里抽出来」是同一个架构心智。第 12 篇讲弹性模式时，你会再次遇到服务网格这个「无处不代理」的视角。</span>

## 5 一个重要的分辨：发现 ≠ 路由策略

**辨析｜易错点：服务发现只解决「目标在哪」，不解决「选哪个」。** 从候选列表里挑一个实例的策略——随机、轮询、最少连接、一致性哈希、按 zone 就近——是**负载均衡（load balancing）**的职责，与发现正交但常被混谈。一个合格的生产系统要同时具备：注册表（在哪）、发现机制（怎么查）、负载均衡策略（选谁）。

## 6 小结

- 微服务实例地址**动态变化**，写死地址必然走向故障，所以需要**服务注册表 + 服务发现**。
- 注册表是**动态 DNS**，用**心跳续租**维持近实时性，最好支持业务级健康检查。
- 发现分**客户端式 / 服务端式**：前者客户端自己查表，后者由负载均衡器查表；Kubernetes 是服务端式的事实标准。
- 注册分**自注册 / 第三方注册**：前者简单但逻辑分散，后者零侵入但 registrar 自身要高可用。
- 发现与**负载均衡策略**是两件事，生产系统两者都要。
