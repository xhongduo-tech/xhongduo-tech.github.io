## 为什么安全要从「边界」讲起

单体安全相对简单：一个进程、一个入口、一份会话。微服务把安全的面摊开了——N 个服务、N 个入口（哪怕收进网关，服务间还有横向流量）、身份要在多个进程之间流转。Newman 在《Building Microservices》第 9 章给的安全策略可以浓缩成一个判断：**微服务的安全核心不在「每个服务都自己做安全」，而在于把信任边界划清楚，再在边界上用力。**<span class="marginnote">安全模型与第 3 篇网关、第 8 篇服务发现天然咬合：网关是外部信任边界的天然落点，服务网格是内部边界的落点。本专题的架构决策，到安全这里会看到它们「顺便」承担安全职责的一面。</span>

本课的路线图：先分清「认证/授权/会话」三件事（安全的最小词汇表），再谈两种信任边界（外部 vs 内部），最后落到微服务特有的问题——**服务与服务之间的信任怎么建立**。

## 1 三个词，先分清

**认证（Authentication, AuthN）**：回答「你是谁」——验证身份。常见手段：口令、短信验证码、TOTP、OAuth2 的授权码流程。

**授权（Authorization, AuthZ）**：回答「你能做什么」——验证权限。常见模型：RBAC（基于角色的访问控制）、ABAC（基于属性的访问控制）。

**会话（Session）**：回答「上次认证的结果怎么记住」——把认证结果变成可被后续请求携带的凭证，而不是每次请求都重输密码。

**辨析｜易错点：AuthN 和 AuthZ 是两个系统，不是两个词。** 一个用户可以认证成功但授权失败（登录了但没有权限）；授权必须**基于认证结果逐请求校验**。把两者混在一个中间件里，是安全漏洞最常见的温床。

## 2 外部信任边界：认证尽量收在边界做

对外的安全策略，核心一句话：**能在外边界做的，就别让每个服务重复做。**

**认证收敛到边界**：登录、OAuth2/OIDC 授权码流程、令牌签发，统一放在身份提供方（Identity Provider, IdP）与 API 网关/边界代理上。服务内部假设「进来的请求已认证」——它只管授权与业务。
- **令牌的选择**：主流是 **JWT（JSON Web Token）**——由 IdP 签名的自包含令牌，携带用户标识与声明（claims），服务拿到后验签即可信任，**无需再回调 IdP**（无状态校验）。<span class="marginnote">JWT 的「自包含」是它的全部优点与全部风险：不用查会话，但被签名的内容就是「真理」，一旦签发算法配置失误（如将公钥当私钥、alg=none 漏洞），攻击者可以自行伪造。2022 年多个 JWT 库曝出的算法混淆漏洞，根源都是「信任签名结果却不验证签发方」。</span>
**授权下沉到服务**：权限判断依赖业务上下文（这笔订单是不是你的），所以授权通常留在各服务内，用 JWT 里的声明做依据——但这要求**服务不盲信 JWT 声明**，而是校验签发方与时效。

## 3 内部信任边界：从「信任内网」到「零信任」

传统模型假设「内网可信」——边界防火墙之内，服务间默认互信。微服务打破了这个假设：**任何一个服务被攻破，攻击者就可能横向移动到其他服务。** 于是有了**零信任（Zero Trust）**：不默认信任任何来源（包括内网），对每个请求都验证。

**服务间认证（service-to-service authentication）**：内部流量也需要凭证。主流做法：

- **mTLS（mutual TLS）**：双向 TLS——不仅客户端验证服务器，服务器也验证客户端证书。两个服务各自持有证书，建立连接时互相验明正身。服务网格（Envoy、Linkerd）把 mTLS 自动化到「每个 Pod 都自动注入证书」，业务代码零感知。<span class="marginnote">mTLS 的信任根是「证书签发机构（CA）+ 证书轮换」：证书要短期有效、定期轮换，否则被窃的证书就是永久的通行证。证书管理本身是专门的工程领域（如 cert-manager、SPIFFE/SPIRE），它把「网络层信任」和「身份层信任」绑定在了一起。</span>
- **短时令牌 + 身份注入**：服务拿到由 IdP 签发的短时服务令牌（几分钟有效期），调用时携带，目标服务验签。

**重点：内部边界的目标不是「加密所有流量」本身，而是「让攻击面从『整个内网』缩小到『单个被攻破的服务』」。** mTLS 保证了「谁在通话」，还要配合最小权限：即使身份验证通过，服务也只授给完成任务所需的最小权限。

## 4 边界防护的落地清单

把前几节收敛成可执行的防护清单：

1. **全链路 TLS**：公网与内网流量都加密（mTLS 更佳），不信任裸 HTTP 的内网。
2. **认证在边界收敛**：IdP + 网关统一做认证与令牌校验，服务专注授权与业务。
3. **逐请求授权**：认证 ≠ 授权，每个敏感操作都按业务上下文校验权限。
4. **最小权限**：服务只被授予它需要的权限；密钥按服务、按环境隔离。
5. **密钥管理**：密码、证书、API Key 绝不进代码仓库，统一由密钥管理系统（如 Vault）保管与轮换。
6. **纵深防御**：即使 JWT 被窃、某个服务被攻破，内部仍有 mTLS、最小权限、审计日志兜底——**攻击者要同时突破多层，而不是一层。**

**辨析｜易错点：把安全外包给网关 ≠ 网关即安全。** 网关做认证、限流、TLS 终止，是「边界防护」；但**业务级授权、数据防越权、日志审计**必须由服务承担。以为「网关挡在前面就安全了」，等于把整栋楼的安全寄托在一道门上。

## 5 小结

- 先分清三件事：**认证（你是谁）、授权（你能做什么）、会话（怎么记住）**——AuthN 与 AuthZ 是两个独立系统。
- 外部边界策略：**认证收敛到 IdP + 网关**，令牌用 JWT 无状态校验，授权按业务上下文留在服务内。
- 内部边界策略：**零信任 + mTLS**，让攻击面从「整个内网」缩小到「单个服务」。
- 落地六清单：全链路 TLS、边界认证、逐请求授权、最小权限、密钥统一管理、纵深防御。
- 安全不是「做一次」，而是**每一层、每一次请求都要重复的纪律**。
