## 为什么接口是微服务唯一的「可见面」

微服务之间不共享代码、不共享数据库，唯一公开的「可见面」是**接口（API）**——第 3 篇网关、第 8 篇安全、第 13 篇数据交换，全部以接口为媒介。于是出现一个尖锐的问题：**没有一处测试能同时看到「提供方」和「消费方」的实现，谁来保证两边的默契不被破坏？**

单体里这个问题被「都在一个仓库里」掩盖了——编译错误直接暴露接口漂移。微服务把提供方与消费方拆成不同团队、不同代码库、不同发布节奏，**接口漂移成为最常见也最隐蔽的故障源**。Newman 在《Building Microservices》§8 与 Richardson 各自给出了同一套答案的两个侧面：**契约测试**（证明接口没变坏）与 **API 版本管理**（接口真变坏时怎么办）。<span class="marginnote">Hyrum's Law：当你的接口有足够多使用者，它的每一个可观察行为都会被某些人依赖——哪怕那是 bug。微服务界面的极端形态：契约不仅是「文档上写的」，还是「所有消费方实际依赖的」。这决定了契约必须被显式管理，而非靠文档自觉。</span>

接口治理的本质，是把「两边的默契」从隐性的代码依赖，变成显性的、可验证的、可演化的契约。本课从「契约是什么」讲起，经「怎么用测试守住契约」，到「契约守不住时怎么办」——这正是接口工程从成本到维护的完整闭环。而这一切的前提，是先把「契约」这个词钉死：它既是文档，又是测试，还是版本决策的依据，下面的每一节都从它出发。

一句话总结本课的立场：**接口治理的目标不是「永远不变」，而是「变而不伤」**——让提供方自由演化，让消费方不被破坏。后面的小节分别给出「怎么证明没变坏」「真变坏了怎么办」「怎么系统地管」的答案。

## 1 契约：提供方与消费方之间的一份「合同」

**契约（contract）**：提供方（服务）与消费方（调用它的服务/客户端）之间关于接口行为的**双方约定**——请求结构、响应结构、错误码、语义（幂等与否）、以及「什么可以变、什么不能变」。

契约测试的第一性洞察是：**接口兼容性不是「提供方觉得没变」就成立，而是「所有消费方依赖的行为都还在」才成立。** 提供方改了个字段名自以为无碍，消费方按旧字段名解析就直接崩溃。<span class="marginnote">「所有消费方依赖的行为」清单从哪来？不是文档，而是<strong>消费者驱动契约（Consumer-Driven Contracts, CDC）</strong>：由消费方把「我依赖什么」写成契约文件，提供方据此验证。契约的方向反转了——不是提供方宣布「你能用什么」，而是消费方声明「我用什么，你必须保住」。</span>

一份完整契约至少要回答四个问题：**接口形状**（端点、方法、请求/响应结构、字段类型）、**语义**（是否幂等、成功与错误码的含义、超时与重试约定）、**演变规则**（什么可加、什么不可改、弃用流程）、**质量承诺**（SLA、限流、配额）。文档写不全的地方，恰恰要靠契约测试钉死——这四问也是写契约测试时天然的检查清单。

## 2 契约测试：不用拉起对方也能验证默契

**契约测试（contract test）**：在**不启动对方服务**的前提下，分别验证「消费方调用方式符合契约」与「提供方响应方式符合契约」，从而让接口漂移在 CI 里、在部署前被发现，而不是在全链路联调时才爆炸。

以业界标准工具 Pact 为例，工作方式是一条双向验证链：

1. **消费方侧**：在测试里写下「我这么调用、期望这样的响应」，生成一份**契约文件（Pact 文件）**。
2. **契约文件发布**到共享的契约仓库（Pact Broker）。
3. **提供方侧**：针对契约文件里的每个期望写**提供方测试**——用真实提供方代码跑契约，验证它确实满足消费方期望。
4. **不匹配 → 立刻红**：任一方违约，CI 当场失败，在发布前拦截。

契约测试让「跨服务的集成正确性」从「昂贵的端到端测试（第 7 篇）」里剥离出来：**它是唯一在低成本前提下验证真实协作的层级**，因此是微服务测试金字塔的承重墙。<span class="marginnote">契约测试的能力边界也要诚实：它验证「接口的请求-响应匹配」，验证不了「行为语义一致」（比如两边对「超时重试策略」的理解）、验证不了「分布式时序」。契约只管接口，不管运行时——运行时正确性仍要靠集成与端到端测试。</span>

一个具体例子：结算服务（消费方）在 Pact 测试里写下「当我 `GET /v2/orders/{id}` 时，期望 200 与 `{ "id": 3, "total": 199.9 }`」，这份期望连同请求被发布到 Pact Broker。提供方拿到契约后，用真实的订单服务跑这些交互，断言响应结构符合期望。某天提供方把 `total` 改名 `amount`，提供方测试立刻变红——**接口漂移在 CI 里被拦截，而不是在全链路联调时才爆炸**。

契约测试的成本也要纳入考量：它需要维护契约文件与 Broker、需要消费方与提供方两个团队对齐发布节奏。但当接口数量超过十几条、消费方超过两三个时，这套成本几乎总是小于「全链路联调被接口漂移反复打断」的代价——**契约测试买的，是把协作问题前置到 CI 里的确定性**。

契约测试还有一个隐蔽收益：它是消费方与提供方之间的「活文档」，而且机器可读、始终新鲜。新成员入职、跨团队协作，与其读一份可能过期的接口文档，不如直接读契约文件——文档会漂，契约测试不会。

## 3 API 版本管理：接口注定要变，怎么变不伤人

契约能保证「没变之前不漂移」，但**业务必然要求接口演化**——加字段、改语义、换结构。版本管理的目标不是「不变」，而是「提供方自由演化，消费方不被破坏」。两条经典策略：

**① 兼容性版本策略（additive versioning）**：只做**向后兼容**的变更——加新字段（可缺省）、加新端点、弃用而非删除旧字段。旧消费方永远能正常工作。
- 优：消费方零升级成本，演进最顺滑。
- 劣：接口会积累历史包袱，演进速度受「最老消费方」限制。

「兼容性策略」的典型动作清单：加新字段（可缺省、提供默认值）、加新端点、加可选参数、把「删除字段」改成「弃用字段」（继续返回但标注 deprecated）。这套动作让旧消费方在绝大多数情况下零改动——**向后兼容是一种「只许加法」的纪律**。

**② 主版本策略（breaking versioning）**：做破坏性变更时，**发布新主版本**（如 `/v2/orders`），新老版本并存，老消费方继续用旧版，直到完成迁移。
- 优：接口可以彻底重设计，不被旧包袱绑死。
- 劣：多版本并存增加维护与部署成本，必须配套**版本退役（deprecation）策略**——明确「旧版维护到何时、如何通知迁移」。

一个具体的退役节奏：T0 发布 v2 并公告 v1 将于 T0+6 个月停止接受新写入、T0+12 个月完全下线；期间 v1 只修安全漏洞、不增功能。**把「退役」变成排期里的显式里程碑，而不是让老版本无限期拖下去**——无限期并存才是版本管理最大的隐性成本。

**辨析｜易错点：「不删字段」不等于「向后兼容」。** 字段还在但语义变了（如 `price` 从含税改成不含税），旧消费方依然会拿到错数据。向后兼容要同时守住「结构」与「语义」两层——这正是 Hyrum's Law 的另一面：使用者依赖的往往是行为，而不是文档。

**重点：版本并存期，恰恰是第 11 篇「滚动发布中新旧版本短暂共存」的同题放大。** 生产系统应尽量把「向后兼容」作为默认姿势，主版本跳升作为明确、有节奏、有公告的例外事件，而不是随手为之。

## 4 版本号放在哪里：三种载体的取舍

「发布新版本」的第一个问题不是「怎么变」，而是「版本号放哪」。三种主流载体：

| 载体 | 示例 | 优点 | 缺点 |
| --- | --- | --- | --- |
| URL 路径 | `/v2/orders` | 最直观，可缓存、可路由 | 路径长期并存，迁移后旧路径仍在 |
| 媒体类型 | `Accept: application/vnd.orders.v2+json` | 路径干净，一个端点多版本 | 不直观，调试与缓存不友好 |
| 查询参数 | `/orders?version=2` | 实现最简单 | 语义最弱，易与业务参数混淆 |

**工程上默认首选 URL 路径版本**：它让「新旧版本的请求」在运维层面（日志、监控、路由、缓存）天然可分，也与第 11 篇「滚动发布中新旧版本短暂共存」的需求吻合——版本号跟着请求走，而不是藏在头的语义里。媒体类型版本适合「同一个资源、形态差异很大」的极端场景，查询参数版本则几乎只在内部接口应急时用。三个载体也不是互斥的：实践中常见「URL 路径管主版本 + 媒体类型管子版本」的组合，把「重大变化」与「细微演进」分两层管理。

版本策略与发布策略的联动值得再强调一次：**主版本跳升应当与第 11 篇的灰度、回滚预案一起排期**——先让新版本在小流量下接受真实契约检验，再逐步放量，最后才谈旧版本退役。接口演化不是一次「改代码」，而是一次「多版本共存的运营事件」。

## 5 一套可落地的接口治理组合

把本课工具与全专题已有部件组合成一份行动清单：

1. **契约先行**：接口变更从「改代码」前移到「改契约」——先更新契约测试，再改实现，让契约成为演化的先行者。
2. **消费者驱动**：让消费方维护「我依赖什么」，提供方必须守住；重大变更先看哪些消费方受影响（Pact Broker 的 can-i-deploy 会直接回答「能安全上线吗」）。
3. **默认向后兼容**：加字段不加删；删除走「弃用 → 公告 → 退役」三步。
4. **版本与发布联动**：主版本跳升要配灰度（第 11 篇）、配通知窗口、配旧版退役期限。
5. **把契约放 CI**：契约测试接入流水线（第 7 篇），让「接口没漂移」成为每次发布的自动门禁。

接口治理的成熟度有一个可观察的梯度：从「接口靠文档自觉」到「接口有契约测试门禁」再到「消费方驱动 + 版本退役有排期」。**每一步都是在把「隐性默契」变成「显性契约」**——这正是本课标题里「治理」二字的全部含义。治理不是一次性的，而是每次发布都要重复执行的动作。

## 6 术语速查：接口治理的词汇表

| 术语 | 一句话定义 | 记忆锚点 |
| --- | --- | --- |
| 契约 | 提供方与消费方关于接口行为的双方约定 | 双方签的合同 |
| 消费者驱动契约（CDC） | 由消费方声明「我依赖什么」，提供方据此验证 | 契约方向反转 |
| Pact | 主流的契约测试工具（双向验证） | 一条契约文件两端测 |
| Pact Broker | 契约文件的共享仓库，含「能否安全部署」查询 | 契约的中央档案 |
| 向后兼容 | 旧消费方在新版本下仍能正常工作 | 只加不改不删 |
| 弃用（deprecation） | 明示旧版将退役并给出迁移路径 | 有节奏地告别 |
| 幂等 | 同一请求重复执行结果相同 | 重试安全 |
| can-i-deploy | Pact Broker 的「契约兼容性检查」，回答能否安全上线 | 上线前的绿灯 |

## 7 小结

- 接口是微服务唯一可见面，**接口漂移**是分布式中最隐蔽的故障源——编译错误没了，默契就成了猜。
- **契约**是双方的显式约定；契约兼容性的判据是**「所有消费方依赖的行为还在」**，而不是「提供方觉得没变」。
- **契约测试**（Pact 双向验证）在**不拉起对方**的前提下验证协作，是测试金字塔的承重墙。
- **版本管理**两条路：默认**向后兼容**（加不改删），破坏性变更走**主版本并存 + 退役策略**。
- 契约先行 + 消费者驱动 + 进 CI，让接口演化成为有纪律的流程而不是事故。

本专题到此收官：从设计原则、边界、网关、发现，到事务、事件、测试、安全、观测、一致性、部署、弹性、数据、契约——十四节课走完了一个微服务系统从「为什么拆」到「怎么守住」的完整闭环。而这一切的底色，始终是那句老话：**架构是权衡的艺术，边界是权衡的落点。**
