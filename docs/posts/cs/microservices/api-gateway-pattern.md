## 为什么客户端需要一个「城门」

服务拆分之后，第一个工程问题立刻浮现：**客户端（浏览器、手机 App、第三方）面对多少个服务，就得写多少套调用逻辑。** 一个下单页面可能要依次调用户、购物车、库存、价格四个服务；每个服务都要做认证；每个服务的接口都在演进。Richardson 在《Microservices Patterns》第 8 章给出了经典解法：**API 网关（API gateway）**——把「多对多」的混乱收敛成「客户端到网关、网关到服务」的两段式结构。

这一节在专题里的位置很重要：前面两篇回答了「边界怎么划」，从这篇开始回答「边界之间怎么通」。网关是服务间通信的第一个模式，也是服务发现的天然入口（下篇）、安全的天然边界（第 8 篇）——它是一张反复出现的牌。

读 Richardson 这一章有个背景知识：**网关方案不是「一个」，而是一个家族——单体时代的负载均衡器、ESB（企业服务总线）、今天的 API 网关与服务网格里的 ingress，都是「入口收敛」思想在不同时代的不同形态。** 理解了这个家族，就明白网关的职责边界从来不是「技术规定的」，而是「团队想让它承载多少横切关注点」决定的。

还要把网关放进全专题的坐标里：**网关是「服务通信」的第一站，但不是最后一站。** 它处理「客户端到服务」的入口；服务与服务的通信、数据交换，还要靠第 4 篇的服务发现、第 5 篇的 Saga、第 6 篇的事件总线分别治理——网关收敛的是「外部入口的混乱」，内部网状调用的混乱由后续各篇接管。<span class="marginnote">「网关」的灵感来自计算机网络里的默认网关：局域网内所有对外的流量都汇聚到一个出口。这里把同一个心智从「网络层」搬到了「应用层」——第二级《计算机网络》里学过的概念，在架构层会再次相遇。</span>

## 1 没有网关的日子

先看问题的全貌。假设四个服务各有接口，直接暴露给客户端，会发生什么：

**调用爆炸**：一个界面要拼装来自多个服务的数据，客户端要了解每个服务的地址、协议、数据模型——客户端从「消费方」变成了「知道一切的集成方」。
- **重复实现**：认证、限流、日志、CORS，每个服务各做一遍；升级认证方案要改所有服务。
- **安全面摊开**：每个服务都暴露在公网上，攻击面等于服务数量。
- **协议与格式强绑**：内部服务可能用 gRPC、Thrift，客户端却只认 HTTP/JSON——协议翻译散落各处。

**重点：这些问题本质上都是「集成逻辑被放错了地方」。** 集成逻辑（谁调谁、怎么鉴权、怎么聚合）不该属于任何单一业务服务——它是横切关注点，需要一个专门的入口层来承载。

集成逻辑散落的另一个隐性代价是**「改一处要动全站」**：升级鉴权方案、加一个公共请求头、统一错误码——每改一次都要在 N 个服务里重复劳动，而且永远有漏改的服务。这个「横切关注点重复实现」的问题，会在第 3 节职责清单里被收敛成网关的「必须做」项。

## 2 网关：反向代理之上再加职责

**API 网关（API gateway）**：位于客户端与后端服务之间的一个入口层组件，它是**唯一的入口**，负责路由、协议转换、横切关注点（认证、限流、聚合、日志）与必要的聚合封装，然后转发到内部服务。

Richardson 的方案里，网关与**反向代理**是血缘关系：反向代理解决了「请求该去哪个后端」，网关在此基础上又承担了应用层的职责。<span class="marginnote">从反向代理到 API 网关的演变是历史事实：Nginx 在 2000 年代中期解决静态资源与负载均衡，后来的 Kong、Traefik、Envoy 一步步把鉴权、限流、熔断搬进代理层，网关概念就此成形。</span>

网关的核心设计决策是：**它只是「路由 + 横切关注点」的哑网关，还是也做「聚合」的胖网关？**

| 风格 | 网关职责 | 典型场景 |
| --- | --- | --- |
| 哑网关（dumb） | 只路由、鉴权、限流，不做业务聚合 | 后端服务接口已足够贴近客户端 |
| 胖网关（smart） | 额外做响应聚合、协议翻译、编排 | 移动端需要一次请求拿到多服务数据 |

胖网关能极大改善客户端体验（一次往返代替多次往返），代价是网关里开始出现业务逻辑，渐渐变成新的耦合点。**Golden rule：能不聚合就别聚合；必须聚合时，把聚合代码当成普通服务来维护**——它同样需要自己的测试与版本管理。

实践中判断「哑还是胖」有个简单的自检问题：**打开网关代码，能不能在五分钟内说清它做了什么？** 若网关里有循环依赖、业务分支、数据库查询，它就已经胖得越界了——胖网关的「业务逻辑」应该只限于「聚合与裁剪」，而不是「业务规则」。

## 3 网关的典型职责清单

把网关职责归纳成一张清单，它会同时出现在「必须做」「可做」「绝不能做」三栏：

**必须做**：路由、身份认证与授权、TLS 终止、限流（rate limiting）、访问日志、请求/响应协议转换（HTTP↔gRPC）。
- **可做**：响应聚合、缓存、灰度分流（A/B 与 canary）、静态资源托管、错误码统一。
- **绝不能做**：在网关里写核心业务规则。网关一旦承载「业务判断」，它就会变成一个新的单体入口，之前的边界全部白拆。<span class="marginnote">Netflix 的 Zuul、Amazon 的 API Gateway、Kubernetes 的 Ingress Controller 都是现成的网关实现——但工具只是载体，职责边界的设计才是本节的实质。选择现成网关比自己写快一个数量级，除非你的聚合需求极其特殊。</span>

把「必须做」拆开看，每一项都对应一个独立的能力域：**路由**需要服务发现（第 4 篇）做输入，**限流**需要排队论常识（第 12 篇会展开），**认证**需要与身份提供方对接（第 8 篇），**协议转换**需要同时处理 HTTP/gRPC/Thrift 三套编解码。网关本质上是「横切关注点的能力容器」——容器里装什么、装多厚，就是这一节的全部权衡。

## 4 Backends for Frontends：每个客户端一座城门

单座网关有个著名痛点：桌面 Web、iOS、Android 对同一数据的需要差异巨大——移动端要精简字段省流量，桌面端要完整对象。一座网关被三方的需求拉扯，要么臃肿，要么为最低共同需求而劣化。

Sam Newman 与 Phil Calçado 等人提出的解法是 **BFF（Backends for Frontends）模式**：**不是一座城门，而是每种客户端各有一座专用网关**——web-bff、mobile-bff、partner-bff 各管各的聚合与裁剪。<span class="marginnote">BFF 是「按调用方切分接口」思想的产物，与面向对象里的「接口隔离原则」（ISP）同源：不要强迫客户端依赖它用不到的接口。它在某些大厂也演化为「Server-Driven UI」的前置层。</span>

**辨析｜易错点：BFF 不等于「给每个团队都开一座新网关」。** BFF 之间的差异应来自「客户端的消费形态差异」，而非「内部团队的组织差异」。为讨好内部团队而复制出多套几乎相同的网关，只会让运维与治理成本翻倍。

BFF 的最佳实践是把「裁剪逻辑」也当作一等公民：**它虽然薄，但仍然需要自己的测试、版本与发布管道**——一个夹在客户端与后端之间的哑翻译层，反而会因为「没人认真维护」而成为新的故障源。这与第 3 节「胖网关逻辑当普通服务维护」是同一句叮嘱。

## 5 网关的代价

网关不是免费的。认清代价才不会被它反噬：

- **单点风险**：网关是所有流量的必经之路，它一挂，全线瘫痪。必须高可用部署、多副本、并配合第 12 篇的熔断与负载保护。
- **多一跳延迟**：每经过网关多一次网络往返。胖网关做聚合时，客户端省掉的多次往返通常能抵消这一跳，但哑网关场景下要明确接受这笔开销。
- **成为瓶颈**：限流、TLS 加解密都在网关上做，它容易先于业务服务耗尽 CPU。网关的容量规划要按「全站峰值流量」而不是「单个服务流量」来做。
- **契约管理压力**：网关若悄悄改了请求语义，消费者无感，内部服务却要适配——网关版本与 API 版本（第 14 篇）必须严格联动。

再补一条常被忽略的**「网关是事实上的强一致点」**：所有请求都过网关，网关的配置就成了全站行为的事实标准——一条错误的路由规则、一个写错的限流阈值，影响的是全部服务。因此网关变更要走「小步灰度 + 自动回滚」，比业务服务变更更谨慎。

最后记住网关的「四高」心智：**高可用、高吞吐、高安全、高可观测**——它承担了全站最重要的横切职责，任何一项的缺失都会在峰值时以事故的形式偿还。

## 6 数值算例：网关的容量与延迟账

网关不是免费的（第 5 节），用数字看它到底贵在哪。假设一个下单接口，客户端直连时平均延迟 180 ms（网络与序列化 60 ms、业务 120 ms），拆出网关后多一跳 15 ms：

- **哑网关场景**：总延迟 180 + 15 = 195 ms，多约 8%。代价透明，收益是集中鉴权与限流。
- **胖网关聚合场景**：客户端原先要串行调用户、购物车、库存、价格四个服务，共约 480 ms；网关并行聚合 + 裁剪后 240 ms，客户端只付 255 ms——**省了将近一半**。

| 场景 | 客户端感知延迟 | 相对直连 |
| --- | --- | --- |
| 直连四服务 | 480 ms | 基准 |
| 哑网关 | 195 ms | 略增 |
| 胖网关聚合 | 255 ms | 省 47% |

**重点：网关「多一跳」的代价是常数级的（十几毫秒），而聚合省下的常常是倍数级的（几百毫秒）。** 这就是为什么「能不聚合就别聚合，但需要聚合时胖网关的收益往往碾压那一跳的开销」——第 2 节的 Golden rule 在这里有了具体数字。

容量账同样直白：假设全站峰值 10 000 QPS，限流、TLS 终止都在网关上做。网关单实例能扛 2 000 QPS，就必须至少 5 个副本起步，还要预留 50% 冗余应对峰值抖动——**网关容量按「全站峰值」而不是「单服务峰值」规划**，这是它与普通服务最本质的区别。

顺便解释网关限流为什么必须「共享状态」：多个副本各自限流会互相抵消——每个副本都按 2 000 QPS 放行，总量就超了。所以限流计数必须放进共享的缓存/存储（如 Redis），并容忍其本身的故障：**限流器自己的高可用，常常比被限流的服务更值得投资。

这一节的结论最终可以压缩成一句话：**网关是把「横切复杂度」集中购买、再统一摊销的地方**——买不买、买多厚，取决于你的客户端形态与全站流量，而答案几乎总是「该买，但别让它在聚合上失控」。**

## 7 小结

- **API 网关**是客户端与后端之间的唯一入口层，解决「多对多」的调用爆炸与横切关注点分散。
- 网关分**哑（只路由+横切）与胖（额外聚合）**两种风格；能哑则哑，聚合逻辑当普通服务维护。
- 职责三栏：**必须做（路由/鉴权/限流/协议转换）、可做（聚合/缓存/灰度）、绝不能做（业务规则）**。
- **BFF**：按客户端消费形态各设一座网关；差异来自消费形态而非内部组织。
- 代价清单：**单点、多一跳、瓶颈、契约压力**——网关越高可用越值得投入。
- 网关的延迟账与容量账：**多一跳是常数级，聚合收益是倍数级；容量按全站峰值规划**。
- 网关是**横切关注点的能力容器**：路由/限流/认证/协议转换各有专属能力域，装多厚由团队权衡。
