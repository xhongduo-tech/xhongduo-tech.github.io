## 为什么一致性是一个「光谱」而不是「开关」

前几篇反复出现「最终一致性」这个说法：Saga 的补偿、事件驱动的同步、CQRS 的读模型——全都建立在一个假设上：**系统暂时不一致是可以接受的，只要最终一致。** 这一节把这个假设摆上台面，回答三件事：为什么强一致在分布式里这么贵？最终一致到底意味着什么？怎么量化地聊「多久最终」？

Newman 在《Building Microservices》第 11 章与 Richardson 各用自己的方式讨论了同一约束，而它们的理论根都在 **CAP 定理**。本课把 CAP 讲准，再把它展开成「一致性光谱」，让「选一致性」从玄学变成工程决策。<span class="marginnote">CAP 是 Eric Brewer 在 2000 年 PODC 上提出的猜想，两年后被 Seth Gilbert 与 Nancy Lynch 严格证明。它是分布式理论里被引用最广、也误解最多的定理——本课的任务就是把它从口号还原成精确命题。</span>

再给它配一张「预算表」的直觉：**一致性不是免费的，但不同级别的「一致性价格」差别极大**。本课要建立的，正是「该付多少、付给谁、值不值」的判断力——读完你应能对任何一个分布式系统问出：它的一致性承诺是什么？代价是什么？付得起吗？

## 1 CAP：三选二的真正含义

**CAP 定理**：在一个**异步网络模型**的分布式系统里，一致性（Consistency）、可用性（Availability）、分区容错性（Partition tolerance）三者，网络分区发生时，只能同时满足其二。

先把三个词钉死：

**C（一致性）**：读操作返回的必须是**最新写入**的结果——所有节点对同一份数据的视图瞬时一致（严格来说指「线性一致性」）。
- **A（可用性）**：每个请求都必然得到**非错误**的响应——即使它返回的是过期数据。
- **P（分区容错）**：系统在网络分区（部分节点之间的消息丢失）下**仍然继续运行**。

**重点：P 不是可选项，而是物理现实。** 网络一定会分区（交换机故障、丢包、GC 停顿），所以「三选二」实际是「分区发生时，在 C 和 A 之间选一个」。**不存在「既保证强一致又保证可用」的分布式系统**——这不是工程限制，是信息论意义上的不可能。

**辨析｜易错点：CAP 只在分区发生时才启动。** 网络正常时，你完全可以「又一致又可用」。CAP 不是「日常运行在三态之一」，而是「分区的瞬间，系统被迫表态」——把 CAP 当成「平时就在三选二」是流传最广的误读。另一个高频误读是把这里的 C 和数据库的 C（ACID）混为一谈：ACID 的 C 是「约束满足」，CAP 的 C 是「读到的必是最新」，两者是不同词汇表里的同形词。

## 2 为什么「强一致」在分布式里这么贵

如果强一致这么「正」，为什么微服务都不用它？因为它的代价藏在实现里。要做到**线性一致性**（linearizability），读写必须经过一个「谁先谁后」的全局裁决——要么靠一个总控（变成单点），要么靠锁定与多数派协议（quorum）：<span class="marginnote">多数派协议的代价公式很直观：要在 2n+1 个副本上保证「读到的一定是最新的」，写操作必须让 n+1 个副本确认（Raft、Paxos 都是这个框架）。2n+1 带来的是一份数据 2n+1 份的存储、网络与协调开销——「一致性从来不是免费的」这句话在此是字面意义的。</span>而跨多个**服务**（各自独立数据库）的强一致，还要叠加分布式事务的锁与协调（第 5 篇已论证其不可行）。**强一致的本质是「让整个系统串行化」，串行化 = 吞吐与可用性的天花板。** 微服务之所以普遍选最终一致性，不是因为「不强」的愿望，而是「强」的账单付不起。

算一笔账：一个需要线性一致性的关键数据，若用 5 副本多数派（$W=3, R=3$），意味着每写一次要等 3 个副本确认、每读一次要访问 3 个副本——存储是 1 副本的 5 倍，每次操作都多付两轮网络往返。若这份数据的吞吐是每秒 10,000 次，quorum 直接把延迟与基础设施成本同时放大。这就是为什么「强一致」在业务里常被当作「稀缺资源」来用：只在余额、库存这类真正不可妥协的地方开启。

## 3 一致性光谱：从强到最终

把一致性画成一条光谱，工程上真正有用的粒度就清楚了：

| 层级 | 含义 | 代价 | 典型场景 |
| --- | --- | --- | --- |
| 线性一致性 | 读到的必是最新，全局有统一时序 | 极高（quorum/总控） | 账户余额？往往也不用它 |
| 顺序一致性 | 各进程看到的操作顺序一致 | 高 | 分布式锁、共识层 |
| 因果一致性 | 有因果关系的操作保持相对顺序 | 中 | 评论系统、社交时间线 |
| 最终一致性 | 没有新写入后，各副本经同步收敛到一致 | 低 | 缓存、CQRS 读模型、Saga |

把这四级翻译成「用户的感受」：**线性一致性像单机**——你写到什么，任何人立刻读到什么；**顺序一致性像「黑板」**——大家看到一致的先后次序，但次序未必符合你直觉里的墙钟时间；**因果一致性像「朋友圈」**——你只能看到你该看到的因果先后；**最终一致性像「新闻」**——发布后，各个读者在不同时间点看到同一则消息。

这张光谱也顺带回答了「为什么很多系统声称自己是最终一致，却在 SLA 里只写可用性」：当强一致过于昂贵，工程会优先保 A（可用性）与 P（分区容错），把 C 延后到同步窗口里完成——这是分布式世界里最日常的取舍。

**重点：最终一致性不是「不管一致性」，而是「约定一致性何时达成」的明确工程承诺。** 一个专业的最终一致系统会回答四个问题：**多久收敛（收敛时延）？收敛前读到多旧的数据（staleness 上界）？写冲突怎么办（冲突消解）？异常时怎么发现（不一致的观测）？** 回答不了这四个问题的「最终一致」，才是真正危险的「最终不一致」。

## 4 公式解析：多数派读写 W+R>N

最终一致要能收敛，靠的是副本之间的同步；而「读写要等多少副本、才能保证读到最新」，可以用一个公式刻画——**多数派（quorum）条件**：

$$W + R > N$$

其中 $N$ 是副本总数，$W$（write quorum）是写操作必须等到确认的副本数，$R$（read quorum）是读操作必须访问的副本数。三步拆解：

- **第一步，理解不等式 $W+R>N$ 的含义**：它保证任意一次「被 $W$ 个副本确认的写」与任意一次「读了 $R$ 个副本的读」**必然共享至少一个副本**——在那个重叠的副本上，读要么直接命中最新值，要么能沿同步链路拿到最新值。于是「读到的一定包含已确认的最新写」在结构上被保证（前提是各副本按一致顺序应用写操作）。
- **第二步，套一个具体数字**：$N=3$ 时，取 $W=2, R=2$（都是多数派），$W+R=4>3$，读写必交。这正是 Raft、Paxos 以及众多 KV 存储默认「三副本」的理由：三副本是「多数派仍是多数派」的最小规模。
- **第三步，看清代价**：$W=2$ 意味着每次写要等两个副本的往返才返回，$R=2$ 意味着每次读要访问两个副本——吞吐与延迟都随 $W,R$ 增大而上升。**「一致性 = 花在同步上的资源」这句话，在这里有了最直白的算式**。若取 $W=1, R=1$，$W+R=2 \le N$，读写不重叠，正是纯最终一致（每个读只碰到一个可能落后的副本）的形态。

**重点：CAP 回答「分区时被迫选哪一边」，quorum 回答「无分区时怎么让『最新』可证」——它们是互补的两个工程侧面。** 前者是哲学，后者是把哲学落成可配置的参数。

## 5 最终一致的两种典型落地

**读写路径的最终一致**：CQRS 里命令模型提交后，事件异步同步到读模型（第 6 篇）。这一段的最终一致由**事件投递可靠性 + 幂等消费**保证——事件至少投递一次、消费端幂等去重（第 5 篇已埋下伏笔）。

**辨析｜易错点：最终一致 ≠ 弱一致。** 「最终」是一句有分量的承诺：它要求停止写入后副本必然收敛，且通常对收敛时延有界。弱一致（weak consistency）不承诺收敛，读到什么全凭运气。一个系统若回答不了「多久收敛」，那它不是「最终一致」，而是「从不一致」——工程上把这两者分清，才能避免把「没设计好的系统」包装成「选了最终一致」。

**事务路径的最终一致**：Saga 的补偿让「失败后系统能回到一致」成为承诺（第 5 篇）。它回答第四个问题的机制是**对账（reconciliation）**：定期扫描「订单状态 = 处理中 且 超过 N 分钟」的孤例，触发补偿或人工介入。<span class="marginnote">对账是分布式系统的「兜底数学」：因为任何协议都可能漏消息，最终一致系统的完整性往往靠「周期性全量核对 + 差异修复」来封底。这与数据库的定期校验、备份验证是同一个思想——把「可信」建立在「定期核对」而非「一次性信任」之上。</span>

**对账的周期与粒度也是一门工程**：订单对账若每小时跑一次全量，需承受「最多一小时的不一致窗口」；把它拆成「每五分钟扫增量 + 每小时全量」，就能在不显著增加成本的前提下把不一致窗口压到分钟级。工程常态是高频小范围对账抓增量、低频全量对账兜底。

## 6 一致性选择：一张决策地图

一致性不是「技术选型」，而是「业务需求 + 代价」的平衡。工程决策地图：

1. **数据有共享可变状态且并发写入激烈、冲突后果严重**（账户余额、库存扣减）——优先**强一致边界**：把数据收进单个服务/单个数据库，用本地事务保证；必要时接受 quorum 的存储成本。
2. **读多写少、写入后短暂读到旧数据可容忍**（商品详情、报表、搜索）——**CQRS + 事件同步**，读模型最终一致，收益远大于成本。
3. **跨服务业务操作、需要整体回滚语义**——**Saga 补偿**，接受中间状态可见。
4. **任何「最终一致」都必须配套**：幂等消费、冲突消解、对账与告警。

举例：库存若拆成「库存服务（写）+ 详情页读模型（读）」，下单扣减写入库存服务的本地事务，详情页读模型经事件异步同步——写入后的头几百毫秒，详情页可能仍显示旧库存，这在「库存不必精确到个位」的 C 端场景可容忍；但对「超卖就亏钱」的内部对账，必须回到强一致边界。**一致性选择永远要问一句：这一份数据，用错误的旧值后果有多重？**<span class="marginnote">「后果有多重」是决策的真正分水岭：余额算错要赔钱、库存多卖要亏钱，这类数据优先强一致；而商品描述、评分、浏览计数这类读多写少的展示数据，最终一致几乎总是更划算。</span>

这张地图还有一个隐藏前提：**同一份数据在系统的不同位置，允许有不同的一致性级别。** 账户余额的「权威账本」要强一致，而它的「展示快照」可以最终一致——把数据按用途分层、分别决定一致性级别，是成熟系统最常见的做法，也是这张「决策地图」真正落地的样子。

## 7 术语速查：把「一致」的词汇表对号入座

| 术语 | 一句话定义 | 记忆锚点 |
| --- | --- | --- |
| 线性一致性 | 全局只有一个时序，读到的必是最新 | 串行 + 最新 |
| 顺序一致性 | 各进程看到的操作顺序一致，可交错 | 顺序在，时序可漂 |
| 因果一致性 | 有因果的操作保持相对顺序 | 因在前、果在后 |
| 最终一致性 | 停止写入后各副本收敛到一致 | 收敛承诺 |
| 读己之写 | 会话内「自己刚写的立刻读得到」 | 会话保证 |
| 单调读 | 已读到的新值不回退到旧值 | 只进不退 |
| 会话一致性 | 同一会话内保证「读己之写 + 单调读」 | 会话内承诺 |
| 对账 | 周期性全量核对 + 差异修复 | 兜底数学 |

## 8 小结

- **CAP**：分区时在 C 与 A 之间选一；**P 是物理现实不可回避**，不存在「又强一致又可用」的系统。
- CAP 只在分区瞬间生效，且这里的 C 与 ACID 的 C **不是同一个词**。
- 强一致 = 串行化 = 高账单（quorum、锁、协调），这正是微服务普遍选最终一致的原因。
- **一致性是光谱**：线性 → 顺序 → 因果 → 最终；工程上要回答「多久收敛、多旧可见、冲突怎么消解、不一致怎么发现」。
- 落地两条典型路径：**CQRS 读写同步（事件+幂等）**与 **Saga 补偿（+对账封底）**。
