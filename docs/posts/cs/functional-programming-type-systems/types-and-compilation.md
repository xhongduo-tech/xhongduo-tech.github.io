## 为什么从类型与编译器开始

前面十篇，类型系统一直作为「语言的约束」出现。但类型还有另一副面孔：**它是编译器手里的金矿**。同一段代码，有了类型信息，编译器可以做出截然不同的优化决策——拆箱、特化、内联、去函数化，全都仰仗类型。这一节把镜头调转：**不是「类型约束程序」，而是「类型解放编译」**。<span class="marginnote">Pierce 的 TAPL 第25章讲 System F 的 ML 实现，里面就包含了类型擦除的核心思想；本章另一条主线「类型引导的优化」则是 GHC、OCaml、Rust、Swift 编译器性能的秘密武器。</span>

从课程结构看，这一节是「类型理论的工程侧」：把前几篇的抽象结论（多态、擦除、类型安全）接回真实的编译流水线，回答三个具体问题——类型什么时候消失、类型怎么帮优化、优化之后如何保证仍然正确。

这与「从极限到大模型」主线的连接也很自然：**优化器之于编译器，正如自动微分之于深度学习**——都是「把工程师的推导外包给机器」，而类型就是优化器手里的「先验」。读懂这一节，你就理解了为什么同样的算法，Haskell 写的编译器（GHC）与 C 写的编译器可以比拼性能。

## 1 编译流水线里的类型

一条典型编译管线长这样：

```
源代码 → 语法分析 → 类型检查/推断 → (中间表示 IR) → 代码生成 → 机器码
              ↑ 类型在这里使用       ↑ 类型在这里被擦除     ↑ 类型信息大多消失
```

类型检查发生在**前端**：它验证程序合法，并把「类型标注」记录成编译器可用的元数据。走到**后端**（代码生成）时，大部分类型已经被**擦除**——机器码里没有 `Vec Int 3`，只有寄存器、栈与指令。<span class="marginnote">「擦除（erasure）」是类型与运行的接缝：类型只在编译期存在，运行期的程序是一份「脱去类型外衣」的骨架。这份骨架怎么保证还是安全的？——这正是擦除定理要回答的。</span>

关键洞见：**类型是「免费」的**——类型检查不引入运行时开销（检查完即擦除），却为后端优化提供依据。类型系统越丰富，前端约束越强，后端可用的优化信息越多。

以 Rust 的一个小函数为例看类型如何在管线里流动：

```rust
fn double(x: u32) -> u32 { x * 2 }
```

`double` 的签名让编译器在**前端**就确定：无别名（所有权保证）、参数是标量（可拆箱）、可内联（小且纯）。于是**后端**直接把 `double` 编译成一条 `shl`（左移）指令——类型信息全程没有进入机器码，却决定了机器码长什么样。**类型在运行期看不见，但它的影响无处不在**。

## 2 公式解析：System F 的擦除翻译

**「多态类型怎么从运行程序里消失」是擦除理论的核心问题。** 定义擦除翻译 $| \cdot |$，把类型化的项映射回无类型的项：

$$|\Lambda X.\; t| = |t|, \qquad |t\;[T]| = |t|$$

拆解这条翻译：

- **第一步，类型抽象被擦掉**：$\Lambda X. t$ 的运行时行为与 $|t|$ 完全相同——类型参数 $X$ 在运行期没有任何表示，直接丢弃；
- **第二步，类型应用被擦掉**：$t\;[T]$ 只是「把类型喂给模板」，运行时什么也不做，也直接丢弃；
- **第三步，擦除与求值交换**：擦除定理（erasure theorem）说——**先求值再擦除，与先擦除再求值，结果一致**。即「类型检查保证的行为」在擦除后的程序里原样保留；
- **第四步，直觉**：`map` 的多态版本运行时就是「同一份代码」，无论实例化成 `[Int]` 还是 `[Bool]`——**类型只存在于编译期，运行期只有一份共享代码**。这为「类型不引入开销」提供了严格的定理保证。

**辨析｜易错点：**擦除 ≠ 丢弃信息。类型信息在**前端**已被用于检查与优化，擦除只是发生在**后端**、把运行期不需要的部分脱掉。Rust 里 `T` 的静态分派（monomorphization）恰恰相反——它**保留**每个实例化版本换取零开销，是「擦除」的另一极（见第 4 节）。

用一个具体的「多态恒等函数」把擦除走一遍：

```
源代码：  id = ΛX. λx:X. x
类型检查：id : ∀X. X → X          （前端，类型完整）
擦除后：  id = λx. x              （后端，无类型）
运行期：  λx. x                    （机器码，只有这份共享函数）
```

`id [Bool]` 与 `id [Nat]` 在擦除后**是同一个 `λx. x`**——多态的运行时代价是零。这行简单的例子，是「类型不引入开销」这个承诺的最小证明。

## 3 类型引导的优化（type-directed optimization）

擦除只是开始。更精彩的是**用类型信息指导优化决策**：

- **拆箱（unboxing）**：类型说「这是 `Int`」而非「指向盒子的指针」，编译器就能直接放进寄存器——Swift、OCaml 的数值优化全靠它；
- **特化（specialization）**：`map` 实例化为 `map_Int` 与 `map_String`，各自动态分派消失——Rust 的 monomorphization 走的就是这条「反擦除」路线；
- **内联（inlining）**：类型确定、无递归的小函数直接展开——GHC 的 `INLINE`、Rust 的 `#[inline]` 让编译器放心展开而不膨胀；
- **去函数化（defunctionalization）**：把高阶函数「函数作为数据」翻译成「带标签的枚举 + match」，让底层可以用 C 语言实现高阶语言——Reynolds 1972 年提出，LMS 生成式编程里仍在用。<span class="marginnote">GHC 的优化管线里，类型信息像「放大镜」一样逐条启用这些优化；没有类型，很多优化要么不成立、要么无法证明安全。这正是「类型是编译器金矿」的完整含义。</span>

这些优化能成立，全都依赖同一件事：**类型告诉我们「值长什么样、能不能共享、要不要装箱」**——没有类型的运行时模型，优化器只能瞎猜。

把「类型如何指导每种优化」摊成一张表，便于一次看清：

| 优化 | 类型提供的信息 | 效果 | 代表实现 |
| --- | --- | --- | --- |
| 拆箱 | 值的基本形状 | 免堆分配 | Swift、OCaml |
| 特化 | 泛型的具体实例化 | 免动态分派 | Rust monomorphization |
| 内联 | 函数的规模与纯度 | 免调用开销 | GHC `INLINE` |
| 去函数化 | 高阶参数的可能形状 | 转成枚举+match | Reynolds 1972、LMS |

值得注意的是，这些优化在动态语言（Python、Ruby）里**大多不成立**——运行时类型未知，拆不了箱、特化不了。**「静态类型换可优化性」，是类型系统给工程界的又一份长期回报**。

## 4 保类型编译：让类型一路走到机器码

比「类型引导优化」更激进的是**保类型编译（type-preserving compilation）**：不让类型在 IR 阶段消失，而是让中间表示**每一层都有类型**，最终的类型化汇编语言里仍带着类型标注。它的价值：

- **端到端安全**：只要类型系统是健全的，且每步编译保持类型，那么「编译过的代码」自动继承「源程序的类型安全」；
- **可验证优化**：每个优化步骤变成一个「保持类型的转换」，可以机械验证——这正是 Coq 里 `CompCert` 编译器（验证的 C 编译器）的做法；
- **分层语言（staged languages）**：LMS（Lightweight Modular Staging，Odersky 的 Scala 团队）让「生成代码的程序」也带类型，类型系统保障生成的代码也正确。

**保类型编译**把类型从「编译前的一道工序」升级为「贯穿编译全程的不变量」——类型第一次不仅仅约束源程序，还约束编译器的每一步动作。

再往前一步的设想是**在编译器内部也使用依赖类型**：把「这个优化是正确的」编码成类型，编译器对优化本身进行验证。Coq 的 `CompCert` 与 `CakeML`（验证的 ML 编译器）已经做到「每一步编译都被机器证明保持语义」——**它们的正确性不是测试出来的，是证出来的**。<span class="marginnote">`CakeML` 的优雅之处在于：它用自己编译自己的方法验证，其 HOL4 逻辑里的证明覆盖整个编译链。这类工作证明了「保类型编译」不是学院派空想，而是可运行的工程。</span>

对普通工程师，保类型编译最大的启发是**心态**：与其「写完再测」，不如把「不可违反的约束」前置成类型——编译器替你检查，正如借用检查器替你检查内存。**把越多的不变量写进类型，就越少需要运行时救火**。<span class="marginnote">这与《依赖类型》一篇形成闭环：依赖类型让「程序的性质」成为类型；保类型编译让「编译过程的性质」也成为类型。两者共享同一信仰——<strong>把正确性写进类型，机器就能替你守住</strong>。</span>

## 5 小结

- 类型在编译管线中**前端使用、后端擦除**——类型检查本身不引入运行时开销。
- **擦除翻译** $|\Lambda X.t| = |t|$、$|t[T]| = |t|$ 保证多态在运行期零成本，擦除定理保证「先擦除再求值」与「先求值再擦除」一致。
- 类型在运行期看不见，但它的影响无处不在——`double(x) = x*2` 被编译成单条指令。
- **类型引导的优化**：拆箱、特化、内联、去函数化，全靠类型信息指导。
- Rust 的 monomorphization 与 Haskell 的擦除是「保留实例」与「共享代码」的两极。
- **保类型编译**让类型贯穿 IR 直到机器码，优化即「保持类型的转换」——`CompCert` 是旗舰范例。
- 把越多不变量写进类型，就越少需要运行时救火——这是本专题贯穿始终的工程心法。
- 类型的两副面孔统一了：**约束程序的是它，解放编译器的也是它**。
- 动态语言无法享受拆箱/特化，因为运行时类型未知——「静态类型换可优化性」是长期回报。

在下一节，我们将用最后一篇把整个专题的结论接到真实世界：**现代语言实践**——Haskell、OCaml、Scala、Rust、Swift 各自在「推断力 × 表达力 × 安全性」上如何取点，它们的设计选择如何构成一部「类型系统选型史」。
