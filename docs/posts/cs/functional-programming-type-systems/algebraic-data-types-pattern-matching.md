## 为什么从代数数据类型开始

前面四篇我们都在处理「函数」：从 λ 演算到类型、到多态、到推断。但程序由两半组成——**处理数据的函数**与**被处理的数据**。这一节补齐后一半：**代数数据类型（algebraic data type, ADT）**，它是 Haskell、OCaml、Rust、Swift 枚举与结构体的共同理论底座，也是「一切皆表达式」的纯函数世界里描述数据形态的标准化语言。<span class="marginnote">「代数」二字不是噱头：类型之间确实可以做「加法」「乘法」，它们的元素个数遵循真正的代数定律（$|A+B| = |A|+|B|$）。这一点我们在第 2 节会严格展开——理解它，就理解了为什么叫「代数」数据类型。</span>

从课程结构看，这一篇也是承上启下：前面「多态写不出来」的缺口已经被 System F 补上，而 ADT 是「在简单类型之上再加两种类型构造子」的最自然扩展——Harper 的 PFPL 正按这个顺序排（第10章积类型、第11章和类型）。

「代数数据类型」这个名字本身还有一层值得细品的含义：**数据结构的形状决定了你能对它做什么**。`Maybe a` 的形状告诉你「可能没有值」，于是消费它就必须处理「没有」的情形——类型把这个「未完成的分支」提前摆到了桌面上，逼你面对它。

## 1 两种基本组合：积与和

要构造复杂数据，只需要两种「拼装」方式：

**积类型（product type）**：$T_1 \times T_2$——同时容纳 $T_1$ 的一个值与 $T_2$ 的一个值，写作有序对 $(t_1, t_2)$。这就是元组、记录、C 结构体、Rust `struct` 的理论化身。**「积」字来自「同时满足」**：元素个数相乘。

**和类型（sum type）**：$T_1 + T_2$——容纳 $T_1$ 的一个值**或** $T_2$ 的一个值，但必须用标签（tag）区分是哪一边，写作 $\mathrm{inl}(t_1)$（left）或 $\mathrm{inr}(t_2)$（right）。这就是枚举、Rust `enum`、Haskell `data` 变体的理论化身。**「和」字来自「二者择一」**：元素个数相加。<span class="marginnote">「和类型」在 C 系语言里长期缺失，程序员只能拿「一个整型标志位 + 一堆互斥字段」手搓——这正是无数 bug 的来源。Rust 的 `enum`、Swift 的 `enum`、TypeScript 的 discriminated union 都是和类型迟到的主流化。</span>

这两个构造子还有一层逻辑投影：**积类型对应「且」（AND）**——要构造 $A\times B$，你必须同时给一个 $A$ 和一个 $B$；**和类型对应「或」（OR）**——要构造 $A + B$，你只需给出其中一边。这正是《依赖类型》一篇里「类型即命题」的出发点：数据构造规则读起来就是逻辑推理规则。

## 2 公式解析：为什么叫「代数」数据类型

**类型为什么可以做算术？因为类型的「大小」（元素个数）满足代数的加法与乘法。** 设 $|T|$ 表示类型 $T$ 的元素个数，则：

$$|A \times B| = |A| \times |B|, \qquad |A + B| = |A| + |B|$$

拆解这两条等式：

- **第一步，积的直觉**：构造 $A \times B$ 的一个元素，等于从 $A$ 选一个、从 $B$ 选一个，共 $|A| \cdot |B|$ 种组合——正是乘法原理。例：`Bool × Bool` 有 $2 \times 2 = 4$ 个元素。
- **第二步，和的直觉**：构造 $A + B$ 的一个元素，要么选 $A$（$|A|$ 种）、要么选 $B$（$|B|$ 种），共 $|A|+|B|$ 种——正是加法原理。例：`Bool + Bool` 有 $2+2=4$ 个元素，但结构不同（每个元素带「来自哪一边」的标签）。
- **第三步，单位元**：空积类型（只有「无字段」的单元）恰有 1 个元素，对应算术里的 $1$；空和类型（没有任何值）有 0 个元素，对应算术里的 $0$。
- **第四步，推导红利**：于是合法恒等式如 $(A+B)\times C = A\times C + B\times C$（分配律）**自动成立**——优化器可以把 $A\times C + B\times C$ 重排成 $(A+B)\times C$ 而不改变任何行为，这就是「代数」给编译器工程师的免费定理。

**辨析｜易错点：**和类型不是「把字段堆在同一个结构里」。C 的 `union` 共享同一块内存、类型不安全；而和类型**每个构造子都是独立的**，用标签区分，类型系统保证「取到的一定是写进去的那一边」——这是 Rust `enum` 安全、C `union` 不安全的根源。

再补一个数字对照，让「代数」的直觉落地：设 $|A|=3$、$|B|=5$，则 $A\times B$ 恰有 15 个元素、$A+B$ 恰有 8 个元素。把类型当成「容器容量」，积与和就分别是「笛卡尔积」与「不相交并集」——**这正是集合论与类型理论共享的骨架**。

## 3 模式匹配：解构的另一半

构造数据用构造子（`inl`、`inr`、`Just`、`Nil`），消费数据则用**模式匹配（pattern matching）**——它是解构数据、按标签分派的正规武器。Rust 里一个典型的匹配：

```rust
fn describe(x: Option<i32>) -> String {
    match x {
        Some(v) => format!("值是 {}", v),
        None    => format!("空"),
    }
}
```

模式匹配天然带来两件好事。第一，**穷尽性检查（exhaustiveness check）**：编译器核对你的分支覆盖了和类型的全部构造子，漏掉 `None` 分支会编译报错——把「少写一种情况」从运行时 bug 变成编译期错误。<span class="marginnote">Rust、Haskell、OCaml 的匹配器都做穷尽性检查；更妙的是 Rust 的 `_` 通配分支与 `if let` 只是穷尽性检查的两个语法糖。</span>第二，**不可变解构**：匹配把元组、结构体拆开成绑定，不修改原值——这与纯函数式世界观完全一致。

模式匹配还能**嵌套**使用：模式里可以再写模式。给二叉树求深度只需一行漂亮的递归：

```haskell
depth :: Tree a -> Int
depth Leaf = 0
depth (Node _ l r) = 1 + max (depth l) (depth r)
```

第一个等式匹配 `Leaf`，第二个等式把 `Node` 的三个字段直接解构出来绑定到 `_`、`l`、`r`——**「解构 + 递归」在模式匹配里是无缝一体的**，这正是处理递归数据结构的标准姿势。

## 4 递归类型：List 与树

积与和组合起来，再加一个「类型可以递归地指自己」，就能造出几乎所有数据结构。Haskell 风格的列表定义是一个经典方程：

$$\mathrm{List}\;A \approx 1 + A \times \mathrm{List}\;A$$

意思是「一个 `List A`，要么是空（`Nil`，占 1 个元素），要么是一个 `A` 加上一个 `List A`（`Cons`）」。「空列表」是单元类型（1 个元素），所以整条方程在元素个数上恰好对应 $1 + |A|\cdot|\mathrm{List}A|$——一种把「无穷结构」写进有限定义的方式。<span class="marginnote">把递归方程看成「无限展开」：$\mathrm{List}\,A = 1 + A(1 + A(1 + \cdots))$。这种「用方程定义无穷对象」的思路，与《惰性求值》一篇里无限数据结构的哲学一脉相承。</span>二叉树、`Maybe`、`Either` 全都是同一套「和 + 积 + 递归」的产物。

二叉树的 Haskell 定义把三种要素一次用尽：

```haskell
data Tree a = Leaf              -- 和类型的第一支（空叶子）
            | Node a (Tree a) (Tree a)   -- 和类型的第二支，含积与递归
```

`Node` 构造子同时用了「积」（三个字段）与「递归」（两个子树），`Leaf` 用了「和」（第二种情况）。于是 `Tree a` 的元素个数满足 $T(a) = 1 + a\cdot T(a)^2$——**数据结构的规模方程，和它的类型定义一一对应**。

## 5 三种语言的同一颗内核

代数数据类型是「一套理论、三种方言」的绝佳样本：

| 概念 | Haskell | OCaml | Rust |
| --- | --- | --- | --- |
| 积类型 | `data P = P Int Bool` | `type p = int * bool` | `struct P { a: i32, b: bool }` |
| 和类型 | `data S = A \| B` | `type s = A \| B` | `enum S { A, B }` |
| 模式匹配 | `case e of ...` | `match e with ...` | `match e { ... }` |
| 递归列表 | `[a]` | `'a list` | `Vec<T>`（堆分配） |

差异在表层（语法、布局、内存表示），内核完全同构——**这就是为什么学过 PFPL 第10–11章，三门语言的数据定义都能一眼看懂**。<span class="marginnote">Rust 的 `enum` 与 Haskell 的 `data` 在语义上几乎一一对应，差异只在布局：Rust 允许 `#[repr(C)]` 指定内存排布、允许判别值优化，而 Haskell 的惰性表示完全是另一套。详情见《现代语言实践》。</span>

ADT 的现代演化还值得一提：**GADT（广义代数数据类型）**允许每个构造子「指定自己的返回类型」，把「积 + 和 + 递归」升级成可以表达「类型层面的约束」。例如 `data Term a where ...` 可以规定某些构造子只产出 `Term Int`。GADT 是「类型即命题」在数据类型层面的先锋，也为《依赖类型》一篇的「索引类型」埋下伏笔。

## 6 小结

- 数据形态由**两种基本组合**拼装：**积类型**（同时容纳）与**和类型**（二者择一）。
- 「代数」名副其实：$|A\times B| = |A|\cdot|B|$、$|A+B| = |A|+|B|$，分配律等恒等式对类型自动成立。
- **模式匹配**是解构数据、按标签分派的武器，自带**穷尽性检查**把「漏分支」变成编译错误。
- 递归的「和 + 积 + 自指」同时给出数据结构的类型定义与规模方程。
- **递归类型**用「和 + 积 + 自指」定义 `List`、树等一切数据结构。
- 和类型与 C `union` 的本质区别：标签保证「取到的一定是写进去的那一边」。
- Haskell/OCaml/Rust 的数据定义共享同一颗 ADT 内核，只是语法方言不同。
- 积/和类型对应逻辑的且/或，是《依赖类型》「类型即命题」的第一块拼图。

在下一节，我们将从「描述数据」上升到「抽象数据之上的统一操作模式」：**函子、应用函子与单子**——让「把函数应用到结构上」这件事本身成为一等公民。
