## 为什么从效应系统开始

前一篇的结论把我们逼到墙角：**惰性求值要求语言是纯的，可真实程序总要读键盘、写屏幕、访问数据库**——这些操作有副作用、有顺序、不可重算。两者如何共存？这一节给出类型系统史上最漂亮的答案之一：**不消除副作用，而是把副作用「放进类型」**，让类型系统精确地知道——并隔离——一个程序执行了什么效应。

这句「不消除、而是隔离」很值得先停下来品一品：它不是要消灭 `print`，而是要消灭「`print` 悄无声息地发生」这件事。**目标是让每个副作用都留下类型指纹**，于是「这段代码会不会碰网络」成为一个可以在编译期回答的问题。<span class="marginnote">「效应（effect）」指程序对环境造成的一切可观察改变：I/O、状态、异常、非确定性。把效应显式化在类型里的系统，统称<strong>效应系统（effect system）</strong>；Haskell 的 `IO` 单子是最著名的一个实例。</span>

从课程结构看，这一节是「纯度哲学」的收官：λ 演算给了计算模型，类型给了形状，单子给了结构操作，现在**效应系统把「世界」也请进了类型**。它也直接通向《线性类型》一篇——Rust 的「所有权」本质上是一种精细的效应（资源消耗）管理。对读者而言，掌握「效应可见性」这一心智，比背下任何具体语法都更重要。

## 1 纯函数与世界的矛盾

**纯函数**的定义是「无副作用、同样输入必得同样输出」。读文件不是纯函数——读同一路径，结果可能不同；打印不是纯函数——它改变了屏幕。若把整个世界都当成不允许的「脏操作」，纯函数式语言就退化成计算器，什么也干不了。

命令式语言的处理方式是**放行**：任何函数随时可以做任何副作用，类型系统不闻不问。函数式语言反其道而行——**「不纯」不是隐藏的罪过，而是必须被类型标注出来的事实**。于是问题变成：如何让「不纯」显式、可控、可组合？<span class="marginnote">这里的关键转变：把「副作用」从「函数的隐秘行为」变成「类型的公开签名」。类型 `IO ()` 明明白白告诉调用者「这个动作会与世界交互」——与 C 里一个 `void f()` 可能偷偷打印、改全局、fork 进程相比，可见性天差地别。</span>

用一个对比把「放行 vs 标注」的差别钉死。设我们要写「读取配置、打印问候」：

- **命令式**（Python）：`def greet(): cfg = read_config(); print("你好")`——类型签名 `-> None` 什么也没说，这个函数可能在改全局、可能抛异常、可能联网；
- **函数式**（Haskell）：`greet :: IO ()`——类型签名明说「这是一个与世界交互的动作」，且它**只能是** `IO` 动作，纯代码里无法调用它，纯代码与脏代码的边界由编译器强制执行。

「边界由类型强制执行」这句话，是整节最值得记住的一句——**它把工程纪律上升为编译期事实**。

## 2 IO 单子：把世界当作一个参数

Haskell 的解法带着一个天才的直觉：**把「世界」当作一个值，显式地传来传去**。每个有副作用的动作，都接收「当前世界」、返回「新世界」加结果：

$$IO\;a \quad\approx\quad \texttt{World} \to (a, \texttt{World})$$

读文件是「接受世界、归还世界与文件内容」；写屏幕是「接受世界、归还世界与单元」。于是**副作用被还原成纯函数**——它仍然「同样输入（同一世界）必得同样输出」，只是输入输出里多了一个「世界」。<span class="marginnote">严格说，现实实现里 `IO` 不是真把整个世界复制，而是用底层的 `RealWorld` token 保证顺序、并在编译期擦除——「世界作为值」是解释器里的心智模型，编译后它变成真实系统调用。关于擦除，见《类型系统与编译器》。</span>

问题：世界被传来传去，谁保证顺序正确？答案是类型。`IO a` 与 `IO b` 无法直接串联，必须通过 `bind`：

$$(\ggg) :: IO\;a \to (a \to IO\;b) \to IO\;b$$

`>>=` 保证：先执行左边动作拿到世界，再把结果喂给右边——**顺序被钉死在类型里，不可能写错**。这正是《高阶抽象》一篇单子的实战应用。

## 3 公式解析：为什么 bind 能保证顺序

**「IO 单子靠什么保证副作用严格有序？」答案是 bind 的类型。** 拆解 `(>>=) :: IO a -> (a -> IO b) -> IO b`：

- **第一步，动作是一个「世界函数」**：`IO a` 本质是「`World -> (a, World)`」。执行一个动作 = 把它应用到当前世界上。
- **第二步，bind 串联**：`m >>= f` 先执行 `m`，得到 `(a, world1)`；把 `a` 喂给 `f`，得到「又一个世界函数」`f a :: IO b`；再把 `world1` 应用上去，得到 `(b, world2)`。
- **第三步，顺序锁定**：因为 `f a` 拿到的世界是 `m` 产出的 `world1`，**后一个动作一定看到前一个动作的结果**——读、写、读的顺序被类型强制，编译器不可能调换。
- **第四步，直觉**：「世界」像一个接力棒，`>>=` 是唯一的传递通道；**没有它，你根本无法把两个副作用动作接起来**。这就是「效果被类型隔离」的精确含义。

与此相对，命令式语言用「程序计数器」天然保证顺序，却也放弃了对「这行代码到底做了什么」的静态可见性。**类型换可见性，就是效应系统的交易本质**。

## 4 从 IO 单子到一般效应系统

`IO` 单子把所有副作用一刀切地装进一个大袋子。但「读数据库」与「抛异常」其实是两种不同的效应，混在 `IO` 里让类型信息变粗。更精细的做法是**标记每种效应**：

- **类型与效应（type-and-effect）**：类型签名写 `fn f() -> int reads rw, throws E`——像 Java 的 checked exception 的加强版，但更系统（PFPL 第24章之后的行为类型是雏形）；
- **代数效应（algebraic effects）**：Koka、Eff、OCaml 5 的 `effect`——效应作为一等公民，可组合、可被 handler 捕获，是「do-notation 的运行时化」；
- **能力（capabilities）**：把「能不能执行某效应」当成一个权限值传入——Rust 的 `unsafe` 块、Koka 的 `with` 都是能力思想的体现。<span class="marginnote">「效应系统」并不只有 Haskell 一条路：Java 的 checked exception、Rust 的 `Result`、Kotlin 的 coroutine 上下文，都是「把效应写进类型」的半成品或变体。它们共享同一个信念：<strong>副作用必须可见，才能被管理</strong>。</span>

Harper 的 PFPL 从另一个角度逼近同一问题：它把**可赋值引用（assignable reference）**与「不可变性由类型强制」当作语言设计的基本问题（第34–35章），说明「可变即效应」的思想早已是类型理论的公共财产。效应系统，本质上是这个思想的**类型化完成**。

**辨析｜易错点：**`IO` 单子不等于「把命令式风格搬进 Haskell」。do 记法读起来像命令式，但它的**语义**仍是纯函数的——`IO` 动作是一个不可分割的「世界函数」，不能中途插入、不能被拆解、不能被并行重排。所谓「IO 让 Haskell 变成命令式」，是对纯度模型的误解：**不是语言变命令式了，是副作用被钉在了类型墙外**。

真实的 Haskell 程序往往不止 `IO` 一种效应，于是有**单子变换器（monad transformer）**：`StateT`、`ReaderT`、`ExceptT`、`WriterT` 各自负责一种效应，再叠到 `IO` 上组成「全能单子」：

```haskell
type App = ReaderT Config (StateT Cache IO)
```

`ReaderT` 提供只读配置、`StateT` 提供可写缓存、`IO` 兜底真正的 I/O——**每一种效应都有它自己的类型槽位**。这就是「效应系统」组合性的工程形态：不是一个大袋子，而是一摞分工明确的抽屉。<span class="marginnote">Rust 侧的对应物是「分层错误处理」：`Result<T, E>` 里 `E` 用 `?` 自动向上传播，配合 `thiserror`/`anyhow` 组合错误类型——与 ExceptT 想解决的是同一个问题。</span>

## 5 效应系统的价值：可测试性、并发、正确性

把效应放进类型，回报是可验证的工程收益：

- **可测试性**：一个「读配置」的动作可以替换成「返回假配置」——因为接口是纯的类型签名，测试替身无须侵入；
- **并发安全**：若类型说明「此函数只读共享状态、不改写」，编译器就能安全并行——`read` 型效应可并发，`write` 型效应须串行；
- **错误可见**：`Result`/`Either` 型错误让「会失败」成为签名的一部分，强制调用者处理，这正是 Rust 的 `?` 操作符与 Haskell 的 `ExceptT` 共享的设计。

这三条回报在真实项目里可感可触：Haskell 的大型代码库（如 GHC、Cardano）能维持极高的重构安全度，依赖的正是「类型说它做什么、它就只能做什么」；Rust 社区对「错误必须显式」的执着，让 `unwrap()` 成为被反复审查的 code smell。**效应的可见性，直接兑换成维护成本的下限**。

把几种「效应处理方案」摊在一张表上，便于对照：

| 方案 | 效应如何标注 | 组合性 | 典型语言 |
| --- | --- | --- | --- |
| `IO` 单子 | 一律进 `IO a` | 单子变换器堆叠 | Haskell |
| 检查异常 | `throws E` | 类型会污染签名 | Java |
| `Result`/`Either` | 返回值即结果或错误 | `?` / do-notation | Rust、Kotlin |
| 代数效应 | `effect` 一等公民 | handler 捕获 | Koka、OCaml 5 |

没有哪个方案「最好」——`IO` 单子严格但笨重，代数效应灵活但语义深，`Result` 直观但嵌套多了啰嗦。**选哪种，取决于你要严格性还是灵活性**。

把这条线拉到本专题的收束处看：**类型系统的演进，就是把「哪些不可见的行为」一个个变成「可见的类型」**——从数据类型、到函数类型、到多态、到效应、到所有权。每一站，都让「程序做了什么」更早、更可靠地被机器知道。

而这个「越来越强、越来越细的类型约束」的趋势，会在《线性类型》《依赖类型》两篇里走到极致：前者把「资源被用几次」写进类型（Rust），后者把「结果等于什么」写进类型（Agda）。**效应系统不是终点，而是这条路上的一个里程碑**。

## 6 小结

- **效应**是程序对环境的一切可观察改变；**效应系统**把它们显式化在类型里。
- `IO` 动作 = 世界函数：同一个输入（世界）必得同一输出，副作用由此被还原为纯函数。
- **IO 单子**把世界当作参数传来传去：$IO\,a \approx \texttt{World} \to (a, \texttt{World})$，副作用被还原成纯函数。
- **bind 的类型**保证副作用顺序不可写错——顺序被钉死在类型里。
- 精细化的路径：**类型与效应**、**代数效应**（Koka、OCaml 5）、**能力**（Rust `unsafe`）。
- 「效应可见性」兑换成可测试性、并发安全与维护成本——类型说它做什么，它就只能做什么。
- 效应系统换来可测试性、并发安全、错误可见三大回报。
- 类型系统的历史 = 把不可见行为逐步变成可见类型的历史。
- 效应系统的目标不是消灭副作用，而是让每个副作用都留下类型指纹。

在下一节，我们将从「描述计算会做什么」跃升到「描述计算是什么」：**依赖类型**——让类型携带数据、让类型即命题，把 Agda/Idris 里「证明即编程」的王国打开。
