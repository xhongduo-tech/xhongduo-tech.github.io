## 为什么从惰性求值开始

回看《λ 演算》一篇的正则序归约：它总是**先归约最外层 redex**——即使实参根本用不到，也不先算它。这条在 1936 年写下的策略，1980 年代在 Haskell 里成长为完整的语言哲学，这就是**惰性求值（lazy evaluation）**，又叫**按需调用（call-by-need）**。<span class="marginnote">Haskell 是本专题三本对标教材里唯一把惰性作为语言默认的语言；Bird 的书把惰性求值当作核心卖点（其「Efficiency」与「Infinite lists」章节专讲此事）。理解惰性，就理解了 Haskell 的一半灵魂。</span>

这段历史的谱系值得一记：1976 年 Wadsworth 给出「惰性」的图重写语义，David Turner 1970 年代末把它用于 SASL、Miranda 语言，1987 年一群语言学家（含 Simon Peyton Jones）联名提出 Haskell，把惰性定为语言默认。**惰性不是某个天才的灵光，而是「正则序 + 共享」几十年工程打磨的结果**。

这一节在课程中的位置很特别：它讲的是**求值时机**，而非**类型形状**。但两者深度纠缠——惰性要求语言是**纯的**（无副作用），因为只有表达式可重算、无顺序依赖时，「不先算」才安全。这正是类型系统与求值策略的第一次正面交汇。

## 1 三种求值策略

「先算实参」还是「用时再算」，有三种经典策略：

- **按值调用（call-by-value）**：先算实参，再传入函数——C、Java、Python 的默认；直观但浪费。
- **按名调用（call-by-name）**：实参**原样**传给函数，用到才展开——不浪费但**可能重复计算**（每用一次算一遍）。
- **按需调用（call-by-need）**：实参用到才算，且**只算一次、之后共享结果**——不浪费也不重复，这就是惰性求值。<span class="marginnote">「只算一次」靠的是<strong>共享（sharing）</strong>：被惰性求值的表达式变成一个「thunk」（未求值闭包），第一次被逼出结果后，把结果写回、后续直接复用。命令式世界的记忆化（memoization）在语言层面自动实现了。</span>

举个例子说明「用到才算」的力量。`head (map expensive [1..1000000])`——`head` 只要第一个元素，于是惰性语言里 `map` 只被迫求值第一个元素，剩下 999999 个昂贵的计算**根本没发生**。按值调用语言则会先把整个一百万长度列表算完。

再对比一个更微妙的例子。设 `f x = 100`——函数 `f` 根本不使用参数 `x`。惰性语言里 `f (puke())` 完全安全，`puke()` 从不执行；而 Python 里必须先调用 `puke()` 再传入。**「参数会不会被用到」这件事，惰性语言里由被调用者决定，调用者永远不必提前付出代价**——这是惰性对「延迟决策」的终极表达。

## 2 无限数据结构

惰性最令人惊叹的副产品，是**无限数据结构**。因为元素「用到才造」，一个「无限长」的列表可以是合法的值：

```haskell
nats = 0 : map (+1) nats        -- 0, 1, 2, 3, ... 无穷无尽
take 5 nats                     -- [0,1,2,3,4]，只造需要的 5 个
```

`nats` 这个「无限列表」并不真实存在——它是一个**生成器**，按需吐出下一个元素。只要你不 `length nats` 或者 `foldl (+) 0 nats`（这才会要求无穷个元素），它就永远温和。<span class="marginnote">无限结构与惰性是同生共死的一对：严格语言里写 `nats` 会立即爆栈或死循环；惰性语言里它是日常。Bird 书中第 9 章「Infinite lists」正展示如何用无限列表优雅地处理流式问题（如筛法求质数、系统事件流）。</span>流式处理、反应式编程、大模型生成 token 的「按需产出」逻辑，与这里的心智模型完全相同。

无限列表的另一个经典应用是**埃拉托色尼筛法**：

```haskell
primes = sieve [2..]
  where sieve (p:xs) = p : sieve (filter (/= 0) (map (\x -> if x `rem` p == 0 then 0 else x) xs))
```

这个定义里，`primes` 是「无限个质数的列表」，它由「无限自然数列表」不断筛出。惰性保证：要第 10 个质数，只推进筛子到第 10 个——**无穷的候选集，按需产出有限的答案**。这正是流式数据处理在函数式世界的标准形态。

## 3 公式解析：斐波那契的无限定义

**惰性让「自引用」的优雅定义成为可能。** 下面这个定义在严格语言里必然死循环，在 Haskell 里却给出完整的斐波那契数列：

$$\mathrm{fibs} = 0 : 1 : \mathrm{zipWith}\,(+)\;\mathrm{fibs}\;(\mathrm{tail}\;\mathrm{fibs})$$

逐步拆解：

- **第一步，读懂结构**：`0 : 1 : rest`——前两个元素写死，`rest` 才是递归来源。`zipWith (+) xs ys` 把两条列表逐元素相加。
- **第二步，看递归**：`fibs` 的第 3 个元素 = `0 + 1 = 1`；第 4 个 = `1 + 1 = 2`；第 5 个 = `1 + 2 = 3`……每算出一个新元素，就自动供给后续计算。**计算进度与被消费进度同步**——惰性保证「没有死循环」。
- **第三步，为何不爆**：求第 $n$ 个元素时，只创建到第 $n$ 个节点为止；之前的结果被共享（`fibs` 与 `tail fibs` 指向同一个已算前缀），所以总复杂度是线性而非指数。若用共享缺失的按名调用，同一个定义会退化回指数级——**共享是「优雅」能否成立的关键**。
- **第四步，直觉**：无限列表 = 「自我生产的流」。`fibs` 的定义**同时**是算法与数据——这种「定义即计算」的美感，是惰性求值送的最贵重的礼物。

## 4 WHNF 与强制求值

惰性求值到底「求到多细」？答案是一个浅层标准：**弱头范式（WHNF，weak head normal form）**——只要求一个表达式求到「外层构造子」为止，内部字段仍可保持未求值。`Just (expensive 10)` 处于 WHNF：外层是 `Just`，里面那个 `expensive 10` 还是 thunk。<span class="marginnote">`5 + 3` 不是 WHNF（最外层是运算）；`5` 是 WHNF；`(5+3, expensive 2)` 是 WHNF（外层是元组，字段未求值）。判断「是否 WHNF」只看最外层构造——这是理解空间行为的钥匙。</span>

「强制求值」就是用 `seq` 或 `BangPatterns` 把一个表达式推进到 WHNF：

```haskell
seq a b   -- 先对 a 求值到 WHNF，再返回 b
```

`foldl'` 内部正是每步 `seq` 累加器，从而打破 thunk 堆积。**WHNF 的「浅」是刻意的**：只求到足够深，恰好避免空间泄漏，又尽量保留惰性的好处——这是惰性语言工程的核心手艺。

用一张表把「求值深度」的层级钉清楚：

| 表达式 | 是否 WHNF | 原因 |
| --- | --- | --- |
| `1 + 1` | 否 | 最外层是运算，不是构造子 |
| `Just (1+1)` | 是 | 最外层是 `Just`，内部字段未求值 |
| `(1+1, 2)` | 是 | 最外层是元组 |
| `\x -> x + 1` | 是 | 函数即值 |

WHNF 只关心「最外层是什么」——这正是它能兼顾「避免泄漏」与「保持惰性」的原因。

## 5 惰性的代价：空间泄漏与严格性

惰性不是免费的午餐。它的主要代价有二：

**空间泄漏（space leak）**：未被消费的 thunk 在内存里堆积——「计算没发生，但待计算的承诺堆着」。经典反例是 `foldl (+) 0 [1..10^7]`：惰性版本在累加器上堆积上千万个 thunk，内存爆掉；而严格版本 `foldl'` 一步一算、常数内存。<span class="marginnote">`foldl'` 用 `seq` 强制每一步先求值累加器再继续——「强制求值」是惰性语言里程序员手动取回控制权的工具。</span>

泄漏的机制值得看穿：`foldl (+) 0 [1,2,3]` 在惰性下展开成 `((0+1)+2)+3` 的**未求值骨架**，每个 `+` 都是待算的 thunk。只有到最外层需要结果时，整条链才「啪」地连锁求值——于是链有多长，临时内存就有多高。`foldl'` 每步先算、再把结果传给下一步，把「链」压成「常数」。**同一算法、同一条式子，一个逗号（`'`）之差，内存复杂度从 $O(n)$ 变 $O(1)$**——这就是惰性语言里最著名的一课。

**严格性分析（strictness analysis）**：编译器静态判断「这个参数反正会被用到、也安全提前求值」，于是把惰性悄悄降级为严格，换回性能。Haskell 的 GHC 拥有相当强的严格性分析器——**语言是惰性的，但编译器替你把不必要的惰性消掉**，这正是「惰性 + 优化器」配合的典范。

**辨析｜易错点：**「惰性」不等于「运行慢」。对多数程序，惰性的收益（只算需要的）与成本（thunk 开销）大致抵消；它的真正价值在**表达力**——无限结构、定义即算法、组合子库。把「惰性」与「性能差」划等号，是对它最大的误读。真实世界里，用 Haskell 写的高性能编译器（GHC 自身）就是「惰性语言可以很快」的最好证据。

有趣的是，现代严格语言都在**偷师**惰性：Python 的 generator、Rust 的 `Iterator`（惰性链、`collect()` 才求值）、Java 的 `Stream`、C++20 的 `views`——它们把「按需计算」作为一种显式 API 提供，却因为语言不纯，无法享受「无限列表」那样的全自动红利。<span class="marginnote">对比两者：严格语言的惰性 API 是「工具」，用完要手动 `collect`；Haskell 的惰性是「世界观」，处处默认、处处生效。差别不在语法，在纯度。</span>

## 6 惰性与纯度：共生关系

惰性求值能成立，前提是**表达式没有副作用**。若 `x = log("读到了x")` 会打日志，而 `x` 可能永不被求值——日志该不该打？顺序该怎样？这类问题在副作用语言里无解，于是惰性语言要求**纯函数**：同一个表达式多次求值必须得到同一结果，求值与否不产生可观察差异。<span class="marginnote">这就把话题引回《效应系统》一篇：Haskell 用 `IO` 单子把副作用隔离在类型里，纯函数部分保持可重排、可共享、可惰性——纯度与惰性互相成全，缺一不可。</span>反过来，这也是 Rust、Swift 等语言「惰性求值」只存在于流式 API（iterator、`lazy`）而不作默认的原因：它们舍不得放弃副作用。

从「从极限到大模型」的视角看，惰性与纯度还是一对优雅的理论呼应：**纯度让表达式可以任意重排与共享，正像极限让函数可以任意逼近；而效应系统为「不纯」划出边界，正像收敛条件为「无穷」划出边界**。本专题的下一节，正是这场「边界」的系统化。

## 7 小结

- **惰性求值 = 按需调用 + 共享**：用到才算、只算一次，靠 thunk 实现。
- 三种策略：**按值、按名、按需**；按需兼得「不浪费」与「不重复」。
- **无限数据结构**是惰性的直接红利：`nats`、`fibs`、`primes` 都是自我生产的流。
- **WHNF** 定义「求到多浅算够」：外层构造子到位即可，内层保持 thunk。
- 惰性的代价：**空间泄漏**（thunk 堆积）与严格性分析的补救（`seq`、`foldl'`）。
- 惰性**要求纯度**，纯度**成全**惰性——二者互相绑定。
- `head (map f xs)` 只求一个元素，是惰性「只算需要的」最直观的注脚。

在下一节，我们将追问惰性铺垫出的那个问题：**如果函数都是纯的、没有副作用，程序又该如何与外界交互？** 答案是**效应系统**——把副作用放进类型，用 `IO` 单子把世界接进纯函数宇宙。
