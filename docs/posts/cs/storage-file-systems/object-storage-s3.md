## 为什么从对象存储开始

过去十三篇，我们从文件接口一路走到分布式文件系统。但今天的存储版图上，最大的一块地盘被一个「不像文件系统」的存储占着：**对象存储**。大模型训练集、备份、媒体资产、网盘——都以「对象」的形态躺在 S3、Ceph、MinIO 里。<span class="marginnote">Tanenbaum §12 与 Silberschatz 的存储章节都指向同一个事实：现代数据中心把存储分成块、文件、对象三种范式，对象存储承载最大体量的非结构化数据。</span>

对象存储的「不像文件系统」，恰恰是它成功的原因——**放弃 POSIX，换来规模、成本与简单性**。这也是本专题的收官之篇：它把前六篇的一切主题——寻道、RAID、校验和、副本、一致性、接口设计——重新组装成一个面向海量数据的最终形态。

## 1 对象模型：桶、键、元数据

对象存储的世界里只有三个概念：

**桶（bucket）**：命名空间容器，类似「顶层目录」。
- **对象（object）**：由 **键（key，名字）+ 数据 + 元数据（用户自定义标签）** 构成，数据不可修改，只能整体替换或删除。
- **元数据**：比文件系统丰富得多——可自定义任意标签，用于搜索、策略、生命周期管理。

命名空间是**扁平的**：S3 的「目录」只是键名里的 `/` 前缀，`ListObjects` 按前缀模拟目录浏览，底层根本没有目录结构。<span class="marginnote">「S3 没有目录」是对象存储最反直觉的一点：`aws s3 cp` 的 `--recursive` 底层是把「前缀匹配」伪装成目录遍历。理解这点，就不会惊讶于「移动目录」在对象存储里是逐个复制再删除。</span>

扁平键 + 前缀还有一个隐藏红利：**按前缀范围扫描**（`ListObjects` 带 `prefix` 参数）天然高效，并行数据扫描任务（如 Spark 分区读取）就靠「把前缀切碎」打满带宽。与文件系统的目录树相比，这是一种**为并行扫描而生的命名法**。<span class="marginnote">传统文件系统里「一个目录一个热点」，对象存储里「一组前缀一个扫描单元」——命名空间的形态，直接决定了并行度怎么分配。</span>

接口是 **HTTP/REST**：`PUT /bucket/key`、`GET /bucket/key`、`DELETE`、`ListObjects`。一个对象一个 HTTP 请求，天然跨平台、天然可缓存、天然能被任意语言调用——这正是数据湖能建在对象存储上的原因之一。

对象的**元数据**与**版本**是对象存储的两个隐藏引擎：版本化（versioning）让每次覆盖都留下历史版本，覆盖删除变「存档」而非「销毁」——数据保护、误删找回、审计都靠它；用户自定义标签（tag）则可以驱动生命周期策略，如「30 天前的日志自动转归档、90 天后删除」。<span class="marginnote">「不可变对象 + 版本化」合起来，就是对象存储能在勒索软件面前自称「不可变存储」的底气——想删旧版本，得先等策略或权限放行，这比文件系统的可覆盖写安全得多。</span>

S3 还有一层「意外之喜」：因为接口是 HTTP、命名空间是键，它天生就能当**静态网站托管**——把 HTML/CSS/JS 当对象上传，配好 bucket 策略就是一个小型 CDN 源头。**「文件系统做不到的事，对象存储因为接口简单反而顺手做了」**，这是接口选择反哺产品形态的绝佳例子。

## 2 无 POSIX 语义：为什么这反而是优点

对象存储主动放弃文件系统三大件：**就地更新、目录层级、POSIX 锁与一致性**。这不是缺陷，而是为规模让路：

**对象不可变**：写新版本就换 key（或版本化），省去「读改写」的锁与一致性协议——并发写者的冲突被彻底简化。
- **扁平命名 + 哈希分布**：数据可以无差别地撒到成千上万节点上，不存在「一个目录下的热文件」这种不均匀热点。
- **最终一致性**：S3 历史上对覆盖/删除最终一致，对新建对象则提供 read-after-write 强一致——够用即可，省下的正是第 13 篇讲的高昂代价。<span class="marginnote">对象存储与 GFS 的「defined」一脉相承：负载是「写完读、不回改」，为这种负载裁剪一致性，换来吞吐与可用性。第 13 篇的「分层取舍」在这里落地成产品默认值。</span>

**辨析｜易错点：** 不要试图把文件系统语义硬塞进对象存储。「改一个字节」在 S3 上要整个对象重传——这不是 S3 的 bug，而是它「对象不可变」的根本设计。选型时问清楚负载是「读多写少、追加为主」还是「频繁随机改写」，后者应该找块存储/数据库。

S3 的一致性语义其实在演进：早期「新对象 read-after-write 强一致、覆盖/删除最终一致」，2017 年起覆盖与删除也升级为强一致。但「强一致」在对象存储里意味着**元数据与数据两面的提交协议更重**——S3 选择「默认强一致 + 极简 API」，Ceph RGW 则允许按需配置，两者都在「够用即可」上做文章。<span class="marginnote">一致性升级不是免费的：越强的一致，越依赖中心化裁决。S3 的元数据索引服务正是为此存在——它用「元数据集中、数据分散」换取强一致与扁平路由。</span>

## 3 架构：元数据与数据分离

对象存储的分布式架构延续 GFS 的智慧，但走得更远：

**S3**：数据对象分散在存储节点，元数据（桶、键、版本、ACL、对象位置）集中在**独立的元数据索引服务**里，负责路由「这个键在哪」。
- **Ceph RGW**：把 S3 兼容 API 架在上一节的 **RADOS** 之上——每个对象被切成若干 RADOS 对象（4 MB 粒度）存放，桶索引（bucket index）与元数据存在 RADOS 的 pool/OMAP 里，底层复用 CRUSH 的分布式放置与多副本/纠删码冗余。<span class="marginnote">Ceph RGW 是「对象存储可以建在通用分布式存储之上」的证明：一套 RADOS 同时支撑块（RBD）、文件（CephFS）、对象（RGW）三种接口——第 5 篇 VFS 的「多实现共享一层抽象」在存储集群里再次上演。</span>

写一个对象时，数据先按纠删码或副本冗余散到多个 OSD，元数据再更新——**数据面与元数据面分离**，任何一面都可独立扩展，这正是对象存储能到 EB 级的架构原因。

对象存储的另一项工程成就是**近乎无限的水平扩展**：由于元数据与数据分离、命名空间扁平，新增节点不需要重排既有对象（哈希分布只影响新增数据），数据再均衡在后台悄悄进行。这就是为什么「对象存储的容量上限以 EB 计」——**扩展瓶颈被架构拆掉了，剩下的只是钱**。

S3 内部并不为每个 key 维护一个「权威节点」——它把桶按 key 哈希**分片（shard）**到大量元数据分区，每个分片由一组服务器服务并自动复制。写入走「主分区」、其他分区异步跟随，读可能短暂读到旧版本——这正是「最终一致」的物理来源，也是 2020 年后改为强一致时内部要动大手术的原因。**一致性从弱到强，从来不是改一行配置，而是重构整条提交链路**。

## 4 公式解析：纠删码的容量账本

对象存储的第二个大创新是用**纠删码（erasure coding）**代替纯副本降成本。参数记为 $(k, m)$：

$$
\text{存储开销倍率} = \frac{k+m}{k}, \qquad \text{可容忍失效节点数} = m
$$

分三步拆解：

- **第一步，$(k,m)$ 是什么**：一个对象切成 $k$ 个数据块，算出 $m$ 个校验块，共 $(k+m)$ 块散到不同节点。读出时只需任意 $k$ 块即可重建全部——校验块是「全体数据的冗余投影」。
- **第二步，为什么比副本省**：3 副本的开销倍率是 3；$(4,2)$ 纠删码开销倍率是 $1.5$，同样能抗任意 2 块失效——**容量省一半，可靠性与 3 副本同级**。这就是对象存储能比传统 NAS 便宜得多的核心。
- **第三步，代价在哪**：读时要凑 $k$ 块（网络访问翻倍）、损坏时重建要算（CPU 与带宽），所以**冷数据用纠删码、热数据用副本**——Ceph 允许按 pool 配置，S3 智能分层自动切换。<span class="marginnote">纠删码与第 6 篇 RAID-5 的奇偶校验是同族思想：RAID-5 是「逐条带 $(k,1)$」，纠删码是把它推广到任意 $m$ 并在集群级实施。从磁盘阵列到对象存储，冗余的数学一直没变。</span>

**数值算例：** 假设一个 1 GB 对象。3 副本要占 3 GB 容量；改用 $(6,3)$ 纠删码只占 $1.5$ GB，且仍能容忍任意 3 块同时失效——同一份数据的「保险成本」从 3 倍降到 1.5 倍。$m$ 越大、容错越强，但读写时凑齐 $k$ 块的数据块也越多，网络与 CPU 开销同步上涨。**可靠性不是白送的，纠删码只是把「花的钱」换成「算的功夫」**。

副本与纠删码的差异不止在容量：**读路径也不同**。3 副本读时只需就近取一份；$(4,2)$ 纠删码读时必须凑齐 $k=4$ 块再算回原数据——每次读都是网络扇出 + 计算。所以热数据用副本（读快）、冷数据用纠删码（省容量），**「按热度选择冗余」是对象存储成本优化的核心旋钮**。

## 5 核心要点：三种存储范式对照

| 维度 | 块存储 | 文件存储 | 对象存储 |
| --- | --- | --- | --- |
| 访问单位 | 块 | 字节流 | 对象（整读整写） |
| 命名 | 卷/分区 | 层级路径 | 扁平键 |
| 接口 | SCSI/NVMe | POSIX 系统调用 | HTTP/REST |
| 语义 | 覆盖写 | 就地更新、锁 | 对象不可变 |
| 一致性 | 强 | 强 | 最终一致为主 |
| 典型容量 | GB–TB | TB | PB–EB |
| 典型负载 | 数据库、虚拟机 | 共享目录、代码 | 数据湖、备份、媒体 |
| 代表 | SSD/云盘 | NFS、ext4 | S3、Ceph RGW、MinIO |

选型可以浓缩成一个三问测试：**要不要就地改写？** 要 → 块/文件；不要 → 对象。**数据量是 GB 还是 PB？** GB 级文件系统绰绰有余，PB 级几乎只能对象存储。**要给谁用？** 数据库/虚拟机吃块，人共享吃文件，训练集/备份/媒体吃对象。三个问题问完，存储选型基本不再纠结——**存储的答案，永远由负载先定**。

## 6 自建生态：MinIO 与 S3 兼容

对象存储的另一半世界是**自建**。以 **MinIO** 为代表的 S3 兼容服务，让企业不用上云也能拥有 S3 语义：同一套 API、同样的扁平键模型、同样的纠删码冗余，部署在自家机房或边缘节点。<span class="marginnote">MinIO 走「S3 兼容」路线而非另立标准，是个教科书级的生态策略：应用只要写好 S3 API，就能在云端与自建间无缝迁移——标准化的价值，比任何一家独大的协议都大。</span>

自建对象存储的冗余默认走纠删码：MinIO 默认 $(4,2)$ 起步、可配到 $(16,14)$，用若干普通服务器即可拼出「任一节点失效不丢数据」的集群——**对象存储把 RAID 从一块盘复制到了整个机架**，这是它取代传统 NAS 的技术底气。

**辨析｜易错点：** 「对象存储 = 便宜的文件系统」是最大的误会。它便宜的前提是接受「对象不可变 + 整读整写 + 按需一致性」；硬把文件语义塞进来（频繁小对象改写、目录重命名、POSIX 锁），要么性能崩盘，要么成本暴涨——**省下来的钱，是用「语义降级」换来的，别指望两头都占**。

## 7 术语速查表

| 术语 | 含义 |
| --- | --- |
| bucket / 桶 | 对象的命名空间容器 |
| object / 对象 | 键 + 数据 + 元数据的不可变单元 |
| key / 键 | 对象的扁平名字，可用 `/` 模拟层级 |
| 版本化 | 覆盖/删除保留历史版本，防误删 |
| 生命周期策略 | 按标签/时间自动转档或删除 |
| 分片上传（multipart） | 大对象切片并行上传、断点续传 |

| RADOS | Ceph 的底层对象存储层 |
| RGW | Ceph 的 S3 兼容对象网关 |
| 纠删码 $(k,m)$ | $k$ 数据 + $m$ 校验，开销 $1+m/k$ |
| 智能分层 | 热/温/冷数据自动切换冗余与介质 |

## 8 小结

- 对象存储以**桶 + 键 + 元数据**组织海量非结构化数据，接口是 HTTP/REST，命名空间扁平。
- 放弃 POSIX 换来**规模、成本与简单性**：对象不可变、无目录热点、一致性按需裁剪。
- 架构核心是**数据面与元数据面分离**；Ceph RGW 把对象存储架在 RADOS 之上。
- **纠删码 $(k,m)$** 以 $1+m/k$ 的开销换 $m$ 节点容错，容量比副本省一半。
- 对象存储的**版本化 + 生命周期策略**是隐藏的工程底座：防误删、自动转档、安全「不可变」。
- 块、文件、对象三种范式各归其位，选型看负载：**改不改、小不小、要不要 POSIX**。

至此，「存储与文件系统」专题完结。从磁头的寻道，到 inode 的档案，到崩溃时的日志，再到 EB 级的数据湖——你已拥有理解现代存储体系的完整地图。回顾这六篇：块存储给你最底层的读写单元，文件系统给你人用语义，对象存储给你海量与廉价——**三者不是替代关系，而是同一批数据在不同尺度下的三种投影**。下一步，沿着《分布式系统》与《数据库》专题，把「一致性」与「事务」继续推向工程深处。
