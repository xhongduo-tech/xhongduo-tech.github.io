## 为什么从实现开始

上一节我们站在接口层：「文件是字节流，目录是文件名到文件控制块的映射」。但「映射」二字是抽象的，磁盘上到底长什么样？这一节回答三个问题：**目录项里的那个号码（inode 号）是什么、数据块怎么组织、空闲空间怎么记账**。<span class="marginnote">Silberschatz §14 的核心是把文件系统的磁盘布局讲清楚：引导块、超级块、inode 区、数据区，以及它们如何在内存中镜像。</span>

这个视角一旦建立，你就能看懂 `df`、`du`、`mkfs` 在干什么，也才能在下一节理解日志文件系统（LFS）为什么要「把随机小写变成顺序大写」。

具体到操作系统课程，这一节对应 Silberschatz §14 的核心：磁盘布局、文件的分配方式、空闲空间管理、目录实现、以及内存中的镜像结构。把这些机制串起来看，你会发现文件系统其实是一套**「块记账」系统**——所有复杂度都在回答一个问题：每个数据块现在被谁用着、下一次该写到哪里。

## 1 磁盘布局：一张磁盘的五块地盘

一个格式化好的文件系统，磁盘被划分成若干区域，典型布局（UNIX 风格）是：

| 区域 | 内容 | 作用 |
| --- | --- | --- |
| 引导块（boot block） | 自举程序 | 开机时最先读入 |
| 超级块（superblock） | 文件系统总量、块数、inode 表位置 | 全局元数据 |
| inode 表（inode table） | 所有文件的索引节点 | 存放每个文件的元数据 |
| 数据区（data blocks） | 文件内容与目录内容 | 实际数据 |
| 空闲空间记账 | 位图或自由链表 | 记录哪块空闲 |

**重点：** inode（index node，索引节点）是文件系统的枢纽——**每个文件有一个 inode，inode 里装着文件的元数据（属主、权限、大小、时间戳）和指向数据块的指针，目录里只存「名字 → inode 号」**。<span class="marginnote">inode 不是磁盘上文件的内容，而是「关于文件的档案」。文件内容=数据块；文件档案=inode。这一区分是理解整个实现的钥匙。</span>

超级块是「文件系统的根档案」：它告诉你 inode 表在哪、数据区从哪开始、块大小是多少。没有超级块，磁盘上的一块数据就无从解释——这就是「格式化」的本质：**mkfs 干的第一件事就是写超级块**。

## 2 数据块的组织：从连续到多级索引

文件的数据块怎么找到？历史上主要有三种方案：

**连续分配（contiguous allocation）**：文件占用连续的磁盘块。随机访问快（直接算偏移），但碎片严重、难以增长——外部碎片是它被淘汰的主因。
- **链表分配（linked allocation）**：每块末尾存指向下一块的指针。无外部碎片，但**随机访问要逐块链走**，且指针占空间、坏块断链即丢数据。
- **索引分配（indexed allocation）**：inode 里放一张「数据块指针表」，要第 $k$ 块就直接查表。现代文件系统的基石。

**索引分配**的代价是指针表要占空间。对一个大文件，一张表可能放不下，于是出现**多级索引**：inode 里放若干直接指针 + 一个间接指针 + 一个双重间接指针……<span class="marginnote">经典 UNIX 的 inode 用 12 个直接块指针 + 单重 + 双重 + 三重间接指针：小文件靠直接指针几乎零开销，大文件靠间接指针无限扩展——「小文件快，大文件能长大」正是它长盛不衰的原因。</span>ext2/3/4、Linux 的 block 指针结构都继承这套设计；而 ext4 更进一步支持 **extent**（连续块区间描述），把「一串指针」压缩成「起点+长度」。

三种分配方式的取舍可以总结成一张表：

| 分配方式 | 随机访问 | 碎片 | 文件增长 | 关键缺点 |
| --- | --- | --- | --- | --- |
| 连续分配 | 最快（直接算偏移） | 外部碎片严重 | 难 | 碎片 + 难扩容 |
| 链表分配 | 最慢（逐块链走） | 无 | 容易 | 随机访问 O(n) |
| 索引分配 | 快（查表） | 内部碎片小 | 容易 | 指针表占空间 |

现代文件系统几乎清一色选索引分配，再叠加 extent 与预留（preallocation）弥补它的短板——这条「先选结构、再优化常数」的路线，是整个存储设计反复出现的模式。

## 3 空闲空间记账：位图与分配算法

磁盘哪些块空着？最通用的是**位图（bitmap / bit vector）**：每个块对应一个比特，1 表示占用，0 表示空闲。<span class="marginnote">位图的优点是空间省（一块盘一个比特）且查找可批量；缺点是分配时可能扫描很长的 0 串。ext 系列与大多数现代文件系统都用位图或类似结构。</span>

分配算法追求两件事：**就近分配**（尽量靠近上次分配的块，减少寻道）与**预分配**（一次预留多个块，减少反复分配）。这正是「数据局部性」在磁盘层面的体现——下一节讲日志结构时，「把相关数据顺序写在一起」会变成第一原则。

位图只是一个记账结构，真正的学问在「分配时怎么选块」。ext4 用**块组（block group）+ 每组独立的位图**，把分配局部化到某个组内；XFS 用**空闲空间 B+ 树**，支持「一次找一个连续 extent」。这些细节决定了磁盘写入的碎片程度与后续读取的顺序性——「哪块盘被你写满了」和「你够不够碎片」，答案都藏在分配器里。

## 4 目录的实现：一次两次查找

目录本身也是文件，它的数据块里存的是目录项。目录项有两种主流格式：

**旧式固定长度项**：名字（如 14 字节）+ inode 号。名字短、浪费。
- **变长项**：名字长度 + 名字 + inode 号。现代文件系统（ext4、XFS）都用变长项，长文件名不再受限。

**重点：** 打开 `/var/log/syslog` 的过程就是沿着目录树逐级查找：查根目录的 inode → 读根目录内容找 `var` 的 inode → 读 `var` 的内容找 `log` 的 inode → 读 `log` 内容找 `syslog` 的 inode → 最后读 `syslog` 的 inode 拿到数据块指针。路径越长，中间读取越多——这是**路径解析（path resolution）**的成本模型，也是目录项缓存（dcache）存在的理由。

大目录里逐项线性扫描同样昂贵：一个包含十万个文件的目录，每次查找都要从头线性找名字。现代文件系统为此给目录加了 **hash 树或 B 树索引**（ext4 的 htree、XFS 的 B+ 树目录），把「找名字」从 O(n) 降到 O(log n)——文件系统里的「数据库化」随处可见。

**辨析｜易错点：** inode 号不是磁盘偏移，而是 inode 表内的索引。磁盘偏移 = inode 表起始位置 + inode 号 × inode 大小。很多初学者把「inode 号」当成「块号」，一错就是整个布局的理解崩塌。

## 5 内存中的镜像：文件系统的高层框架

磁盘上是静态布局，运行时要动态缓存。文件系统在内存中维护：**in-memory inode 表**（打开文件的 inode 副本）、**目录缓存**、**打开文件表**、**数据块缓存（page cache）**。<span class="marginnote">读文件先在 page cache 命中则免去磁盘 IO；写文件先落 cache、延迟刷盘——这是性能与崩溃一致性的矛盾起点，正是本专题第 4 篇《崩溃一致性与 journaling》要正面处理的难题。</span>「磁盘结构 + 内存镜像」的两层模型，也是下一节 VFS 能让多种文件系统共存的基础框架。

写缓存尤其值得留意：`write()` 返回不等于数据已落盘，而是已进 page cache——真正的落盘由 **回写（write-back）机制**按策略延迟执行（Linux 的 `dirty` 页在超时、水线或 `sync` 时刷出）。这个「先缓后落」的窗口正是崩溃一致性问题（第 4 篇）的温床，也是 `fsync`、`O_SYNC` 这类「强制落盘」接口存在的全部理由。

## 6 公式解析：多级索引到底能表示多大的文件

多级索引的威力要用数字说话。设块大小 $S = 4\,\text{KB}$，指针大小 $p = 4\,\text{B}$，则一个指针块能装下 $K = S/p = 1024$ 个指针。经典 UNIX inode 用 12 个直接指针 + 单重 + 双重 + 三重间接：

$$
\text{最大文件大小} = 12S + KS + K^2 S + K^3 S
$$

分三步拆解：

- **第一步，直接指针**：$12$ 个直接指针各指一块，覆盖 $12 \times 4\,\text{KB} = 48\,\text{KB}$——绝大多数小文件到这里就结束了，inode 不需要额外表。
- **第二步，间接层**：单重间接 = $K$ 个块 = $1024 \times 4\,\text{KB} = 4\,\text{MB}$；双重间接 = $K^2$ 个块 = $4\,\text{GB}$；三重间接 = $K^3$ 个块 = $4\,\text{TB}$。
- **第三步，总量**：加起来约 $4\,\text{TB}$。**每个数量级对应一级间接**，这就是「地址空间按幂次扩展」的代价——访问深层的块要多读几次指针块，但换来的是近乎无限的容量。

**辨析｜易错点：** 很多人以为「间接层越多越好」。恰恰相反——每多一层间接，随机访问一个深层块就要多读一层指针块。设计追求的是**小文件零额外开销、大文件按需扩展**的平衡：ext4 用 extent 压缩指针开销、XFS 用 B+ 树替代多级间接，本质都是在「指针查得少」与「能装得下」之间重新取点。

## 7 术语速查表

| 术语 | 含义 |
| --- | --- |
| 引导块（boot block） | 开机自举程序，最先读入的块 |
| 超级块（superblock） | 文件系统的「根档案」：总量、块数、inode 表位置 |
| inode（index node） | 每个文件的元数据档案：属主、权限、大小、数据块指针 |
| 位图（bitmap） | 每块一个比特的空闲空间记账 |
| 多级索引 | 直接 + 间接 + 双重/三重间接指针，按幂次扩展容量 |
| extent | 用「起点 + 长度」描述一段连续块的区间 |
| dcache（目录项缓存） | 缓存「路径分量 → inode」解析结果 |
| htree / B+ 树目录 | 大目录的名字索引，把查找从 O(n) 降到 O(log n) |

## 8 小结

- 磁盘布局五块地盘：**引导块、超级块、inode 表、数据区、空闲记账**；超级块是根档案。
- **inode** 是每个文件的档案，含元数据与数据块指针；目录只存「名字 → inode 号」。
- 数据块组织从连续 → 链表 → **索引分配**；多级间接指针让文件「小则快、大则长」，extent 是其现代演进。
- 空闲空间用**位图**记账，分配追求**就近 + 预分配**的局部性。
- 路径解析是**逐级 inode 查找**，目录项缓存是它的性能救星；inode 号 ≠ 块号。

在下一节，我们离开磁盘上的静态结构，看一种把「局部性」贯彻到极致的设计——**日志结构文件系统（LFS）**：让「写磁盘」像「写日志」一样只做顺序追加。
