## 为什么从分布式文件系统开始

NFS 把文件搬上了网络，但服务器还是**一台**。当数据从 TB 涨到 PB，搜索引擎的网页库、大模型的训练语料动辄几个 PB——**单台机器连存储接口都插不下**。2003 年，Google 在 SOSP 发表的 GFS 论文给出了工业级答案：把文件切成大块，散到成千上万台廉价机器上，同时默认「机器会坏」来设计。HDFS 与 Ceph 是这条路的开源延伸。<span class="marginnote">Tanenbaum §11 把 GFS/HDFS 归入「对等/大规模分布式文件系统」；GFS 是 BigTable、MapReduce、整个大数据时代存储层的鼻祖，也是理解「为应用裁剪一致性」的教科书案例。</span>

这一篇不是「另一个文件系统」，而是文件系统设计范式的转型：**从「让单个系统更强」转向「让系统组在失效中保持可用」**——下一个主题「一致性模型」的所有争论都源于这个转向。

## 1 架构：单主节点 + 分块存储

GFS 的架构一句话：**一个主节点管元数据，一群块服务器管数据，客户端绕过主节点直接读数据**。

**主节点（master）**：只存元数据——命名空间、文件到块的映射、块到服务器的映射。元数据全在内存，启动时从操作日志 + 检查点恢复。
- **块服务器（chunkserver）**：存数据，默认把每个 64 MB 的大块复制 3 份放到不同机器。
- **客户端（client）**：向主节点要「块句柄 + 位置」，然后**直接与块服务器通信**传输数据。

**重点：** 数据通路与控制通路分离——主节点只回答「块在哪」，不搬运数据。这是 GFS 让单点元数据服务器不至于成为吞吐瓶颈的第一招。<span class="marginnote">为什么块要 64 MB 这么大？GFS 的负载是「大文件、追加为主」：大块让客户端一次拿到的位置信息管很久，元数据量也按比例缩小——设计服从负载。</span>

## 2 写入路径：租约、主副本与流水线复制

往 GFS 追加一个块，主节点先选出**主副本（primary）**并授予**租约（lease）**——租约期间主副本说了算。写入流程：

1. 客户端向主节点请求「谁是这个块的主副本」，主节点返回主副本与其余副本位置。
2. 客户端把数据推给最近的副本，副本之间**流水线接力**传给下一台。
3. 所有副本收齐数据后，客户端命令**主副本**执行写入并确定偏移。
4. 主副本写好后通知各副本写，全部确认后向客户端应答成功。

**辨析｜易错点：** 副本之间是「先缓存、后提交」的两阶段：数据先流到所有副本，主副本才统一决定顺序。这保证了一次写入在各副本上顺序一致，但**并发写者的相对顺序由主副本串行裁决**——于是有了 GFS 著名的「记录追加（record append）」与「一致性稍弱（defined）」的折中。别把 GFS 的语义当成 POSIX 的「每次读都看到最新值」，它追求的是「大家看到同一个顺序，个别副本可能暂时旧」。

## 3 公式解析：副本数如何把数据丢失打成极小

副本是分布式系统对抗「机器会坏」的武器。设**单个块在一年内的失效概率**为 $p$（考虑一台机器上的硬件、断电、网络隔离），副本数 $r$，则该块的丢失概率近似：

$$
P(\text{丢失一个块}) \approx p^{r}
$$

分三步拆解：

- **第一步，为什么是 $p^r$**：每个副本独立地「不坏」；要丢数据，必须**所有 $r$ 个副本同时失效**——独立事件相乘。
- **第二步，代入数字**：若 $p = 1\%$（单副本年失效率 1%，对旧机器并不夸张），$r=3$ 时丢失概率约为 $10^{-6}$——百万分之一。一个 100 万块的文件系统，期望约 1 块/年受损，再靠快速重建兜底。$r=2$ 则是 $10^{-4}$，高出两个数量级。
- **第三步，关键前提**：$r$ 个副本必须**真正独立**——不同的机架、不同的电源、不同的磁盘批次。同机架同时断电、同批次盘同时返修，都会把 $p^r$ 变回 $p$。**「看起来有三份」不等于「三份互相独立」**，这是分布式存储可靠性的第一条暗坑。

## 4 HDFS：GFS 的开源化身

Hadoop 生态的 **HDFS** 是 GFS 的忠实复刻：NameNode 对应 master，DataNode 对应 chunkserver，默认块 128 MB、副本 3，**机架感知放置（rack-aware placement）**——同一块的副本默认放不同机架，兼顾「抗整架故障」与「读带宽」<span class="marginnote">HDFS 副本放置默认「第一个本机、第二个同机架另一机、第三个异机架」，正是上节公式里「副本要独立」的工程落地。</span>。NameNode 也是单点，靠 Secondary NameNode/Edit Log 提供恢复。

HDFS 面向**一次写入、多次读取、以追加为主**的批处理负载——训练集、日志、中间结果都在这个模式里。它不提供 POSIX 的文件锁与随机改写，这不是缺陷，而是对负载的诚实。

## 5 Ceph：去中心化元数据

GFS/HDFS 的单主节点迟早是瓶颈。**Ceph** 走另一条路：核心是 **RADOS** 对象存储层 + **CRUSH** 算法——**不靠中心映射表，而靠哈希与伪随机计算，直接算出「块 → OSD（对象存储设备）」的放置位置**。<span class="marginnote">CRUSH 把「位置查找」从「查表」变成「计算」：任何节点都能独立算出某块数据在哪，元数据不再需要单点权威——这是对 GFS 单主架构的根本性解构。第 14 篇 Ceph RGW 对象网关就是架在 RADOS 之上的。</span> 它的文件系统接口 CephFS 由一组 MDS（元数据服务器）动态分片子树提供，追求接近 POSIX 的语义与无单点。

## 6 核心要点：三大系统对照

| 维度 | GFS | HDFS | Ceph |
| --- | --- | --- | --- |
| 元数据 | 单 master | 单 NameNode | 分布式（CRUSH） |
| 块大小 | 64 MB | 128 MB | 4 MB 对象 |
| 副本/冗余 | 3 副本 | 3 副本 | 多副本或纠删码 |
| 一致性 | relaxed（defined） | 与 GFS 同源 | 较强（多副本同步） |
| 接口 | 专用 API | 类 POSIX/HTTP | POSIX / 对象 / 块 |
| 出处 | 工业论文（2003） | 开源（2006） | 开源（UCSC） |

## 7 小结

- 分布式文件系统把数据**切分 + 复制**到多台机器，设计前提是「**失效是常态**」。
- **单主 + 分块**：主节点管元数据、块服务器管数据、客户端绕过主节点直连——数据/控制通路分离。
- 写入靠**租约选主副本 + 流水线复制**；一致性是「同一顺序、可能暂时旧」的折中。
- 丢失概率 $\approx p^{r}$：**副本必须真正独立**，机架感知放置让公式成立。
- HDFS 忠实复刻 GFS；**Ceph** 用 CRUSH 去中心化元数据，是对单点瓶颈的根治。

在下一节，我们把「可能暂时旧」这种措辞变成精确的数学语言——**一致性模型（CAP 与线性一致性）**。
