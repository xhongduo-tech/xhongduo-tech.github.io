## 为什么从 NFS 开始

上一节 VFS 让我们看到：文件系统的实现可以五花八门，接口可以统一。那么更进一步——**文件根本不在本机，而是在网络对面的另一台机器上**，这层抽象还撑得住吗？NFS 用三十多年的事实回答：撑得住，而且撑出了整个分布式存储的雏形。<span class="marginnote">Tanenbaum §10.4 把 NFS 放在「分布式文件系统」章节，与 Sun 1985 年发布、现已是 POSIX 分布式文件系统事实标准的历史对应。今天每个 Linux 集群的 `/home` 几乎都挂 NFS。</span>

理解 NFS，等于理解分布式存储的两个核心矛盾：**无状态与性能**（崩溃恢复 vs 缓存一致性）的权衡、**客户端缓存**（怎么让远端数据读得快又读得对）。下一节的 GFS/HDFS 就是针对 NFS 的不足重新设计的「平行宇宙」。

## 1 架构：客户端-服务器 + RPC + VFS

NFS 采用经典的**客户端-服务器架构**：数据在服务器磁盘上，客户端通过 **RPC（远程过程调用）** 把 `read`、`write` 变成网络请求。<span class="marginnote">RPC 让「远端函数调用」看起来像本地调用——这正是「远程文件服务」与「远程访问」（FTP 下载文件、HTTP 拉网页）的差别：NFS 保留文件的字节流语义与随机访问能力，应用无需先下载整个文件。</span>

关键点在于，NFS 客户端就是一个**特殊的 VFS 文件系统**：它的 `file_operations` 里没有磁盘寻道，只有「组包 → 发 RPC → 等应答 → 解包」。上一节的 VFS 图里，把 NFS 那块换成「NFS 客户端 + 网络」，你就有了 NFS 的完整分层。

**文件句柄（file handle）**是 NFS 的身份凭证：由（文件系统 ID，inode 号，generation 号）构成——generation 号用于识别「同一 inode 号是否已被复用」。句柄在客户端一打开文件就取得，之后每个读写请求都带着它，服务器据此找到对应的文件。

## 2 无状态 vs 有状态：v2/v3 与 v4 的哲学分野

NFS v2/v3 的设计核心是**无状态服务器（stateless server）**：**服务器不保存任何「哪个客户端打开了哪个文件」的记录**。每个请求都自包含——文件句柄 + 偏移 + 长度——服务器像处理临时快递一样处理每个请求。

无状态带来两个惊人收益：

**崩溃恢复极简**：服务器崩了重启，没有任何「打开状态」需要恢复，客户端重发请求即可。
- **故障隔离**：客户端崩了也不会在服务器上留下悬挂状态。

代价也很明确：**做不了可靠的文件锁**（锁是有状态的东西），**客户端缓存的一致性难以保证**——这正是 v4 要解决的问题。<span class="marginnote">NFS 的「无状态换简单恢复」与数据库的「持久状态换强一致性」形成鲜明对照：前者把可靠性压到协议重试层，后者把可靠性做进日志层。第 13 篇讲 CAP 时你会再次看到这种「状态放哪」的抉择。</span>

v2/v3 与 v4 的对比：

| 维度 | v2/v3 | v4 |
| --- | --- | --- |
| 服务器状态 | 无状态 | 有状态（会话 + 委托） |
| 文件大小 | v2 受限 32 位 | 64 位 |
| 锁 | 需外置 lock 协议 | 内建文件锁 |
| 复合操作 | 多个 RPC | compound 一次封装多个操作 |
| 客户端缓存 | 超时猜测 | 委托（delegation）显式管理 |
| 挂载 | mount 协议 | 路径式，内置安全协商 |

**辨析｜易错点：** 无状态 ≠ 不缓存。v2/v3 的客户端照样缓存目录与数据，只是「缓存是否有效」要靠超时猜；v4 的委托则让服务器**主动通知**客户端缓存失效。一个是被动猜，一个是主动管——这是理解「为什么 v4 更强一致性」的关键分水岭。

## 3 客户端缓存与一致性：委托与租约

远端读每次都要走网络，太慢。于是客户端缓存目录属性与数据块。但缓存引入脏读风险：两台客户端各缓存一份，A 改了数据，B 还在读旧版。

**v3 的办法**：给缓存设**超时**（如属性 3 秒、数据 30 秒），到期再问服务器。简单，但要么延迟旧数据、要么多打 RPC。
- **v4 的办法**：**委托（delegation）**——服务器把文件的控制权暂时「委托」给某个客户端，该客户端在自己缓存里随便改；其他客户端要碰这个文件时，服务器先收回委托、通知持托客户端把改动刷回。<span class="marginnote">委托的收回即「回叫（callback）」机制。它把「谁允许读写」从每个操作升级为「一段时期的独占」，是分布式缓存一致性的成熟形态，也是第 14 篇对象存储里「读缓存一致性」的近亲。</span>

**重点：** NFS 的一致性不是「强一致」，而是**「会话内可见 + 启发式」**——同一客户端的修改自己可见，跨客户端则依赖超时或委托。它追求的是「足够好」，因为强一致（每次读都问服务器）等于放弃缓存，性能不可接受。这个「一致性换性能」的跷跷板，是分布式存储永恒的定价表。

## 4 可靠性设计：幂等与重试

NFS 的可靠性建立在 **RPC 的幂等性**上：`read` 天然幂等（读同样的内容）；`write` 在 v3 引入**异步写**与**稳定写**的区分——`stable write` 要求服务器落盘后才应答，`unstable write` 允许先回应答再刷盘，数据丢失由上层承担。<span class="marginnote">把「应答时机」分成「落盘后答」与「先答后落」，正是数据库 fsync 语义在分布式层的翻版——还记得第 4 篇 journaling 里的提交记录吗？「什么时候算成功」是存储里最深的哲学问题。</span>

**辨析｜易错点：** 「分布式文件系统」不等于「所有节点共享一块盘」。NFS 里只有服务器持有数据，客户端只是远程访问者；真正把数据**切分到多台机器**上的，是下一节 GFS/HDFS 做的事。NFS 解决「远程访问」，GFS 解决「大规模存储」，两者目标不同、架构不同。

## 5 小结

- NFS 是**客户端-服务器 + RPC** 的远程文件服务，客户端以 VFS 文件系统形态接入，用**文件句柄**标识远端文件。
- v2/v3 走**无状态**路线：崩溃恢复简单、性能受限；v4 走**有状态**路线：内建锁、compound、委托。
- 客户端缓存用**超时（v3）或委托（v4）**管理一致性，追求「足够好」而非强一致。
- 可靠性靠 **RPC 幂等 + 稳定写/异步写**的分层语义实现。
- NFS 解决「远程访问」；把数据**切分到多台机器**是 GFS/HDFS 的战场。
