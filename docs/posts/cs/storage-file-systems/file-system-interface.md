## 为什么从文件系统接口开始

程序要长期保存数据，靠的是内存之外的第二级存储——磁盘。可磁盘只是一块「能读写的比特荒地」，谁来把比特组织成「有意义的东西」？这正是文件系统的职责：**文件系统（file system）是操作系统中负责以文件形式存储和检索数据的那一部分**。<span class="marginnote">Silberschatz 将文件系统分为接口（§13）与实现（§14）两层：接口回答「文件长什么样、能做什么操作」，实现回答「这些操作在磁盘上怎么落地」。今天先立住接口，下一节再钻进 inode 看实现。</span>

把接口学清楚，是理解后面一切存储主题的入口：崩溃一致性要讨论「文件系统崩溃后丢什么」，日志文件系统要记录「哪些写操作要记账」，分布式文件系统要把「目录」搬上多台机器。同时，文件接口也是你每天都在用的东西——`cat`、`ls`、`open()`、`read()` 全是它的化身。

## 1 文件：把比特流装进有意义的名字

**文件（file）**：一个被命名的信息单位，是磁盘存储的逻辑单元。<span class="marginnote">「文件」这个词在 1960 年代由 MIT 的 Multics 团队正式化，UNIX 把它推向「一切皆文件」的哲学。</span> 一段数据之所以能被称为「文件」，因为它拥有**属性（attribute）**：名字、标识符、类型、位置、大小、保护信息、时间戳（创建/修改/访问时间）。操作系统不关心文件内容是什么，它只维护这套元数据，并保证「按名字访问」这件最基本的事成立。

**辨析｜易错点：** 文件的内容与文件的属性是两回事。文件的内容是字节序列；属性是文件控制块（FCB）里记录的「关于文件的元数据」。修改文件内容不会改变它的 inode 号，但会更新 mtime 时间戳——这两个概念分不清，后面读 inode 一节就会糊涂。

文件的内容可以有三种组织方式：

**无结构字节流（byte stream）**：一串字节，解释权完全交给应用程序。这是 UNIX/Linux 与 Windows 的做法，最简单也最灵活——文本、图片、可执行文件都是「字节流」。
- **定长记录（fixed-length records）**：文件是若干等长记录的序列，常见于古老的卡片系统与某些数据库的存储层。
- **树状结构（tree）**：文件内部自带层级组织，见于 IBM 早期的大型机文件系统。

现代主流操作系统的选择是**字节流**：把「如何解释内容」推给应用层。你可以把一段 JSON、一张图片、一个 Python 脚本都装进同一个文件——这就是「字节流」最大程度地不做预设。

文件的**类型（type）**如何区分？两类机制并存：靠**扩展名**（`.txt`、`.jpg`）或靠**魔术数字（magic number）**。魔术数字是文件头部的固定字节，例如 JPEG 以 `FF D8 FF` 开头、PDF 以 `%PDF` 开头——`file` 命令就是读魔术数字而非扩展名来判定类型。

## 2 打开文件：从磁盘到内存的协议

**辨析｜易错点：** 很多初学者以为 `read()` 要传文件名。不对。绝大多数系统调用直接操作的是**文件描述符（file descriptor）**——一个整数，是「打开的文件」在进程里的句柄。<span class="marginnote">Win32 用 HANDLE，POSIX 用 int fd。它们本质相同：都指向内核里的一条打开文件记录。</span>

操作系统为「打开文件」维护一组表格：

**进程级打开文件表**：每个进程一张，记录该进程用到的文件描述符。
- **系统级打开文件表（open-file table）**：全系统一张，记录每个打开文件的状态——当前文件偏移量、打开模式（读/写/追加）、引用计数。
- **in-memory inode 表**：把磁盘上文件元数据的高速缓存副本载入内存。

`open()` 要做的事：在目录里找到文件的 FCB 拷入内存、在打开文件表中登记、给进程分配一个文件描述符。`close()` 则释放进程条目，引用计数归零时把 inode 写回磁盘。<span class="marginnote">打开文件的引用计数（open count）正是硬链接计数在文件描述层面的孪生概念——两者都回答了「还有谁在用这份数据」。</span>

与「打开」配套的还有**文件锁（file lock）**：共享锁（shared lock，可多个读者持有）与排他锁（exclusive lock，写者独占）。`flock`、`fcntl` 以及数据库事务的锁管理，都建立在这对概念上。

## 3 访问方式：顺序与随机

打开文件之后，怎么读？两种基本方式：

**顺序访问（sequential access）**：从文件开头按顺序读写，靠自动维护的文件指针推进。磁带时代这是唯一合理的方式，如今读日志、读流式数据仍默认顺序。
- **直接访问（direct access）**：也叫随机访问。给出文件内相对块号，直接跳到任意位置读写。磁盘是可随机寻址的设备，所以现代文件系统普遍支持——数据库的索引查找、`lseek` + `read` 的经典组合就是直接访问。

**重点：** 顺序访问与直接访问不是对立的世界观，而是「能否低成本指定位置」的区别。文件指针（file offset）把「读到哪里」从硬件设备（磁带/磁盘）中抽象出来，应用程序不必关心底层寻道。

## 4 目录：把命名组织成树

文件需要被查找，于是有了**目录（directory）**：一个把「文件名 → 文件控制块」联系起来的映射结构。<span class="marginnote">目录本身也是一种文件——它包含的不是用户数据，而是目录项（name → inode 号）。这正是 UNIX 目录「就是文件」的真相。</span>

目录的进化史是一条由浅入深的结构演化：

| 结构 | 特点 | 缺陷 |
| --- | --- | --- |
| 单层目录 | 所有文件平铺 | 多用户撞名 |
| 双层目录 | 每个用户一个目录 | 用户间无法共享 |
| 树形目录 | 任意深度嵌套 | 无法共享已有文件 |
| 无环图目录 | 允许共享，无环 | 删除需处理引用计数 |
| 一般图目录 | 允许环（符号链接可成环） | 遍历需防循环 |

现代系统停在「树形 + 无环图共享」的组合上，并用两种链接实现共享：

**硬链接（hard link）**：同一 inode 的多个目录项。共享的是数据本身，链接计数随创建/删除增减，不能跨文件系统、不能链接目录。
- **符号链接（symbolic link）**：一个存着「目标路径字符串」的特殊文件，可跨文件系统、可断链（悬空引用）。

**辨析｜易错点：** 删除硬链接与删除符号链接语义完全不同。删硬链接只是引用计数减一，数据还在；删符号链接只是删掉那条路径字符串。`ls -l` 里 inode 号相同的是硬链接，`->` 指向的是符号链接——这是面试常考、也最容易想当然的一对。

## 5 挂载：把树拼接成树

有了目录树，还需要把树拼起来：**挂载（mounting）**——把某个文件系统的根目录，接入当前目录树的某个节点（挂载点）。<span class="marginnote">Windows 用盘符（C:、D:）隐式挂载；UNIX 用 `/mnt`、`/` 这类目录显式挂载。Linux 的 `mount` 命令、macOS 的磁盘自动挂载都是同一机制。</span> 挂载点上的旧内容在挂载期间被遮蔽，卸载后恢复——这层「树套树」的机制，是后面讲 VFS（虚拟文件系统）时「异构文件系统共存」的雏形。

## 6 小结

- **文件**是被命名的信息单位，核心属性是名字、大小、位置、时间戳；现代文件系统内容采用**无结构字节流**。
- 文件操作的核心协议是 **open → 读写/seek → close**，由进程表、系统级打开文件表、inode 表三层维护状态。
- 访问方式分**顺序**与**直接（随机）**两种，靠文件指针抽象设备差异。
- **目录**是「文件名 → 文件控制块」的映射，结构从单层演进到树形与无环图；**硬链接共享数据、符号链接共享路径**，语义务必分清。
- **挂载**把多棵树拼成一棵树，是异构文件系统共存的基础。

在下一节，我们将掀开接口看实现：目录项里的那个 inode 号到底是什么，文件系统怎么在磁盘上组织 inode、数据块与位图——这就是**文件系统实现与 inode**。
