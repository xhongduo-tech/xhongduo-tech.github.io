## 为什么从浏览器架构开始

写前端的第一行代码之前，应该先回答一个问题：**你写的 HTML、CSS、JavaScript，最终是怎样变成屏幕上像素的？** 这条链路叫**渲染管线（rendering pipeline）**，它决定了为什么 `transform` 动画流畅而 `top` 动画卡顿、为什么一次输入要等很久、为什么「渲染进程」有时会整页崩溃。理解了浏览器这座「车间」的结构，后面讲 DOM、事件循环、HTTP、性能优化时才有共同的坐标系。

在本专题的谱系里，浏览器架构是**一切前端问题的物理底座**：它连接着第三级《操作系统》的进程与线程、第四级《GPU 架构与 CUDA》的光栅化硬件，也预演了下一节要讲的 JavaScript 引擎（V8 就是跑在渲染进程主线程上的解释器）。

## 1 多进程模型：一座工厂的车间划分

2008 年 Chrome 发布时带来的最激进决策，就是**多进程架构**：不再让一个浏览器进程包办一切，而是把工作拆给多个进程，每个进程负责一块职责。<span class="marginnote">Firefox 当年走单进程路线，一个标签页崩溃会拖垮整个浏览器；Chrome 用「每个渲染进程都是沙箱」换来了稳定与安全，后来 Firefox 也在 Quantum 时代（2017）转向多进程。</span>

Chrome 至少有以下几类进程：

- **浏览器进程（browser process）**：总管。负责地址栏、书签、网络请求、存储访问、页面进程的创建与调度。
- **渲染进程（renderer process）**：每个标签页（或每个站点）一个。负责 HTML/CSS 解析、布局、绘制，以及执行页面里的 JavaScript。
- **GPU 进程（GPU process）**：把纹理、位图交给 GPU 合成与光栅化。
- **网络进程 / 存储进程 / 工具进程**：把磁盘、网络、沙箱这些危险边界单独隔离。

**站点隔离（Site Isolation）** 是这条思路的极致：从 Chrome 67（2018）起，**不同源（origin）的页面被强制放进不同的渲染进程**，即使它们同在一个标签页。这样做是为了防御 Spectre 类侧信道攻击——进程边界是浏览器最后的隔离墙。<span class="marginnote">渲染进程运行在沙箱里，拿不到操作系统的多数权限；它连文件系统都要通过 IPC 请求浏览器进程代办。这就是「渲染进程里炸了，最多重载这个页面」的原因。</span>

一个渲染进程内部又分多个线程：

- **主线程（main thread）**：执行 JavaScript、布局、绘制，是页面的心脏。
- **合成线程（compositor thread）**：独立于主线程，负责把已光栅化的图块拼成最终画面。
- **IO 线程**：接收浏览器进程经 IPC 传来的输入与消息。

进程间靠 **IPC（进程间通信）** 传递消息，跨进程调用远比同进程函数调用昂贵——这也是性能优化时「尽量别把工作推给主线程」之外的另一个理由。

## 2 渲染管线：从字节到像素的八道工序

浏览器把一次页面渲染拆成一条流水线。理解它，就能解释几乎一切渲染性能问题：

**HTML 解析 → 构建 DOM → 构建 CSSOM → 渲染树（Render Tree）→ 布局（Layout）→ 绘制（Paint）→ 分层与合成（Composite）→ 光栅化（Raster）→ 显示**

逐道展开：

1. **HTML 解析（Parsing）**：渲染进程的主线程把 HTML 字节流解析成 **DOM（文档对象模型）** 树。遇到 `<script>` 会暂停解析去取脚本（除非标记了 `defer` 或 `async`）。
2. **构建 CSSOM**：CSS 被解析成 **CSSOM**，它与 DOM 一起决定元素长什么样。
3. **渲染树**：把 DOM 与 CSSOM 合并，只保留「要画出来的」节点。
4. **布局（Layout / Reflow）**：计算每个元素在视口中的**几何位置**——宽度、高度、坐标。这一步成本随 DOM 规模近似线性增长，是「回流」的代价。
5. **绘制（Paint）**：主线程把每个节点「画」成绘制指令序列（record），像给画布下了一串「先画圆、再画方」的命令。
6. **分层（Layerize）**：页面被拆成若干层（layer），例如 `will-change: transform` 的元素会单独成层。
7. **光栅化（Raster）**：合成线程把每层切成**图块（tile）**，交给光栅线程/GPU 进程画成位图。
8. **合成与显示（Composite）**：合成线程按层序把位图拼接，交给 GPU 上屏。

<span class="marginnote">布局、绘制都在主线程上完成，只有分层之后的合成与光栅化是在合成线程/GPU 上并行做的——这就是「仅合成属性」的动画（`transform`、`opacity`）能稳定 60fps 的根本原因：主线程完全没被占用。</span>

这段流水线里有一个关键约束：**解析是「渲染的起点」，而它会被脚本阻塞**。浏览器碰到 `<script src="...">` 时，会暂停 DOM 解析、去下载并执行脚本，因为脚本可能用 `document.write` 改写 DOM。于是「首屏速度」的第一课就出现了：把关键 CSS 放在 `head`，把阻塞脚本尽量延迟到页面解析完再执行。这条「从收到 HTML 到画出第一帧」的最短路径，业界叫**关键渲染路径（Critical Rendering Path）**，我们在《性能优化》一节会用量化的方式（TTFB、FCP）继续讲。

## 3 合成与光栅化：为什么 transform 比 top 快

同样是把元素从 A 移到 B，`top` 与 `transform: translate()` 的成本天差地别：

- 修改 `top` 会触发**布局 → 绘制 → 合成**整条重走，全部在主线程上排队执行，主线程稍忙就会掉帧。
- 修改 `transform` 只改变**合成阶段**的层变换，主线程完全不参与，动画直接由合成线程驱动。

这正是「**合成（composite）**」与「**光栅化（raster）**」两词的精髓：合成线程只管「几块位图怎么拼」，光栅化只负责「把图块画成位图」。两者都在主线程之外，因而动画可以不被 JavaScript 拖慢。现代 Chrome 还引入了 **Display Compositor（视觉层）** 让 GPU 直接参与，进一步把合成从渲染进程搬到 GPU 进程。

输入事件也有自己的路径：触摸/滚轮事件先到合成线程，合成线程判断是否只涉及滚动；只有需要执行 JS 处理时才转给主线程，否则页面滚动都不经过主线程。

## 4 核心对比表：进程、线程与渲染阶段

| 维度 | 浏览器进程 | 渲染进程（主线程） | 合成线程 | GPU 进程 |
| --- | --- | --- | --- | --- |
| 职责 | 网络、存储、UI、调度 | JS、布局、绘制 | 分层、合成 | 光栅化、上屏 |
| 崩溃影响 | 所有页面 | 单个页面 | 轻微卡顿 | 无页面损失 |
| 是否沙箱 | 否（受信任） | 是 | 是 | 半受信 |
| 可并行任务 | IPC 收发 | 单线程执行 JS | 独立于主线程 | 大规模并行 |

再放一张渲染阶段对照表，把「哪一步改了会重跑多少」说清：

| 改动属性 | 触发阶段 | 是否占用主线程 |
| --- | --- | --- |
| `color` / `background` | 绘制（Paint） | 是 |
| `width` / `height` / `top` | 布局（Layout） | 是 |
| `transform` / `opacity` | 仅合成（Composite） | 否 |
| 滚动 | 仅合成（部分场景） | 否 |

值得注意的是，**「触发布局」与「强制同步布局」是两回事**：前者是属性改变后浏览器等待下一个帧去重排，后者是你在主线程里读取 `offsetWidth`、`getComputedStyle` 等会立刻反映布局结果的属性，浏览器被迫**当场**把排队中的布局跑完。一个常见的性能反模式就是在循环里「先写后读」地交替修改与读取布局，从而触发几十次同步重排。这条规则我们会在讲事件循环与渲染时机时再次遇到。

## 5 从架构到工程

理解架构不只是考试题，它直接决定工程决策：

- **优先用 `transform`/`opacity` 做动画**，把动画从主线程挪走。
- **`will-change` 别滥用**：它提前创建图层，图层太多会让 GPU 内存与合成成本上升。
- **避免长任务**：主线程被一段 200ms 的 JS 占满时，合成线程再快也补不上「用户点击无人响应」的空白。
- **懒加载与节流**：重布局（如读 `offsetTop`）会强制同步重排，能省则省。
- **Web Workers**：把纯计算（JSON 解析、图片处理）丢到 Worker 线程，别堵主线程。
- **DevTools 是架构的透视镜**：Performance 面板的「Main」时间线就是主线程任务的回放，Layers 面板能看分层，Raster 阶段则会在 GPU 进程的统计里出现——这些工具暴露的，正是本节讲的每一道工序。

对团队协作还有一个隐含结论：**「首屏性能」从来不只是 CSS/JS 的优化问题**，它还取决于网络层（资源多少、能否并行下载）、渲染层（主线程忙不忙）、合成层（图层多不多）三层是否同时接近空闲。架构不看清，性能优化就会像在错误的楼层修电梯。

<span class="marginnote">到《性能优化》一节我们会把这些准则量化成 Core Web Vitals 与帧预算；到《DOM 与事件》一节则会看到主线程上的任务队列是如何决定「JS 何时跑、页面何时画」的。</span>

## 6 小结

- 现代浏览器用**多进程**换稳定与安全：浏览器/渲染/GPU/网络各司其职，渲染进程被沙箱隔离。
- 渲染管线 = **解析 → DOM/CSSOM → 渲染树 → 布局 → 绘制 → 分层 → 光栅化 → 合成**。
- **布局与绘制在主线程**，**合成与光栅化在合成线程/GPU**——这是性能差距的根源。
- `transform`/`opacity` 只触发合成，`top`/`width` 会触发布局+绘制，成本完全不同。
- 输入事件先经合成线程，能滚则滚，要执行 JS 才转主线程。
- 关键渲染路径受**阻塞脚本**影响最大，`defer`/`async` 与关键 CSS 前置是首屏优化第一步。

在下一节，我们将钻进渲染进程内部，看驱动这一切的**JavaScript 引擎（V8）**——隐藏类、JIT 分层编译与垃圾回收，究竟是怎么让一段脚本跑起来的。
