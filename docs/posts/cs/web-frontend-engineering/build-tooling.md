## 为什么从构建工程化开始

源码是一套由成百上千个模块组成的工程，而浏览器只想要「尽量少、尽量小、尽量并行」的几份文件。**构建（build）** 就是把两者翻译对接的工序：打包器读取源码，生成浏览器能高效消费的产物。这一节把《HTTP 演进》的「少请求、小体积」落到具体工具，《性能优化》的加载瀑布也在这里定下基调。

## 1 模块系统的谱系：从 IIFE 到 ESM

理解打包器，先理解模块。JavaScript 历史上出现过五代模块方案：

- **IIFE（立即执行函数）**：用闭包隐藏私有变量，靠全局对象手工注册——无依赖管理，容易冲突。
- **CommonJS（CJS）**：Node 的 `require`/`module.exports`。同步加载，天然适配本地磁盘；浏览器无法直接使用，需打包器转换。
- **AMD / UMD**：为浏览器异步加载而生（RequireJS），UMD 是「同时兼容 CJS 与 AMD」的包装层。
- **ES Modules（ESM）**：`import`/`export` 的标准语法，**静态可分析**——依赖关系在代码运行前就已确定。ESM 是浏览器的原生模块标准，也是现代打包器的分析基础。

<span class="marginnote">ESM 的「静态可分析」是整个构建体系的支点：`import { a } from './x'` 在写出来的瞬间就声明了「我要 `a`」，打包器不需要运行代码就能知道整个依赖图长什么样、每个模块导出了什么。这既是 Tree Shaking 的前提，也是 `import()` 动态导入能做代码分割的前提。</span>

打包器要兼容所有历史包袱：一边把 CJS 翻译成可静态分析的 ESM 等价物，一边把 npm 里 `main`/`module` 字段的入口理顺。Flanagan《JavaScript 权威指南》第 10 章对 ESM 的导出/导入、动态导入、模块顶层的执行时机有完整讲解，是本节模块语义的权威依据。

ESM 的**执行时机**还有两个值得记住的性质：**模块只执行一次**（首次 import 后缓存），且**模块顶层代码先于其依赖树中的导出被求值**。这解释了「为什么顺序 import 看似无关紧要」——所有 `import` 都先执行，真正的运行逻辑在模块体里。理解这一层，调试「变量未定义」时就不至于在 import 顺序上瞎猜。

## 2 打包器原理：依赖图 → 合并 → 分块

一个打包器的核心流程几乎都一样：

1. **入口（entry）**：从 `main.js` 出发。
2. **遍历依赖图**：解析每个 `import`/`require`，构建一棵「谁依赖谁」的图。现代工具（esbuild、Rspack）用 Rust/Go 并行扫描，比 JS 打包器快一个量级。
3. **合并**：把所有模块代码包进**运行时**（module registry），给每个模块一个 ID，把 `import` 替换成对运行时注册表的访问。这一步产生一个「所有模块共用一套作用域」的大文件——这叫**打包（bundling）**。
4. **分块（chunking）**：把代码按入口、动态导入、共享依赖切成多份，浏览器按需加载。

关键产物之一是**共享模块提取（code splitting）**：两个页面都用了 `react`，就把 `react` 单独提成 `vendor` chunk，让它在两个页面间被浏览器 HTTP 缓存复用——一个 chunk 只下载一次。这正是《HTTP 演进》缓存语义的应用：**体积小 + 缓存命中率高，才是下载优化的双引擎**。

打包器的运行时还有一个经典包袱——**循环依赖**：`a.js` 与 `b.js` 互相 import。ESM 用「模块先注册、后求值」的语义容忍循环依赖，但求值顺序仍有陷阱；CJS 转 ESM 后尤其容易踩「取到 `undefined`」的坑。构建工程里的这些细节，本质上都是在为「模块间的时序」兜底。

分块策略有一个实用的经验法则：**入口页的分块按「首屏依赖」切**。首屏需要的模块打进 `main` chunk，路由懒加载的部分用 `import()` 拆成独立 chunk，只在一个页面用到的重库（如富文本编辑器、图表库）单独成块、按需加载。判断标准始终是《性能优化》里的那个问题：**哪些字节是用户看到第一屏之前必须的？** 不是的，都该推迟。

## 3 Tree Shaking：把没用的代码摇掉

**Tree Shaking（摇树）**：通过静态分析删除「从未被使用」的导出，只把实际用到的代码打进产物。它依赖两件事：

- **ESM 的静态结构**：`export` 的边界在编译期就清楚，可以判断「这个导出有没有被 import」。
- **`sideEffects` 标记**：`package.json` 里声明 `"sideEffects": false`，告诉打包器「这个包的模块没有副作用（不会在 import 时就修改全局状态），可以放心删掉没用到的部分」。

用 `import { debounce } from 'lodash'` 与 `import _ from 'lodash'` 的区别，就是 Tree Shaking 的第一课：前者让打包器只保留 `debounce`，后者可能把整个库拖进来。正确姿势是从具名导入开始，配合 `sideEffects: false` 与按需入口（如 `lodash-es`）。<span class="marginnote">Tree Shaking 的边界很清晰：<strong>不能删「有副作用的模块」</strong>。`import './style.css'`、顶层执行 `console.log`、给全局挂东西的模块，都无法被安全摇掉——所以组件库、UI 库常因副作用标记不当而「摇不动」，这也是各库文档反复强调 `sideEffects: false` 的原因。</span>

**压缩（minification）** 与 Tree Shaking 是两步：摇树删「没用的代码」，压缩（如 Terser、esbuild）则把「有用的代码」改得更小——删空白、缩短变量名、合并常量。产物还要配 **Source Map**，把压缩后的代码映射回源码，让浏览器 DevTools 能还原调试位置——代价是额外的 `.map` 文件下载，生产环境通常只留错误上报。

Tree Shaking 的实践坑也值得列出来：**它只看「是否被 import」，不看「是否在运行时真的用到」**。`import * as utils from './utils'` 会把整个命名空间视为「用到了」，摇树立刻失效；同理，动态属性访问 `utils[name]()` 也无法静态判断。所以在写工具函数库时，**优先具名导出、避免默认导出大对象、避免运行时动态属性访问**——这三条几乎就是「你的库能不能被摇干净」的开关。

## 4 开发体验：Vite 与 HMR

构建不只服务生产，还服务开发。2010 年代 Webpack 的 dev server 需要「全量重新打包」，大型项目一次热更新要等数秒。**Vite**（2020 起）换了一条思路：

- **开发期不打包**：直接用浏览器原生 ESM，按需请求源码，让 esbuild 只转译被请求的文件——冷启动与热更新都是毫秒级。
- **生产期再打包**：构建时用 Rollup（基于 Rust 的 Rolldown 正在替换它），产出优化过的静态文件。
- **HMR（模块热替换，Hot Module Replacement）**：改一个组件，只把那个模块及其依赖重新执行，页面状态（滚动位置、输入值）保持不变——比整页刷新体验好得多。

HMR 的实现离不开我们《DOM 与事件》一节的模块边界：热更新本质是「运行时的模块重新求值 + 重新渲染受影响的组件」。框架生态为 HMR 提供了专门钩子（如 React Fast Refresh、Vue HMR），它们约定组件模块的「导出入口」必须稳定，否则热更新会失败回退为整页刷新。

开发与生产「同一份源码、两套构建」也带来了一个隐含要求：**HMR 只存在于开发构建，生产构建必须把 HMR 代码彻底摇掉**。打包器通过环境变量（`process.env.NODE_ENV`）在构建期区分两种模式，把开发专用代码从生产产物中剔除——这是「构建期做的决策」比「运行时做的决策」更彻底的一个例证。

## 5 产物交付：内容哈希与缓存版本

打包的最后一公里是「怎么把产物发给浏览器」。这里有一个容易忽略的规则：**文件名必须「内容寻址」**——即用文件内容算出的哈希作为文件名（`app.8f3a2b.js`）。

- **内容变了，哈希就变**：浏览器把新文件名当作新资源下载；
- **内容没变，哈希不变**：浏览器命中 HTTP 缓存（`Cache-Control`），复用旧文件，零下载。

这就是**缓存版本（cache busting）**：用「名字是否变化」自动表达「内容是否变化」。若不用哈希而固定叫 `app.js`，浏览器可能一直用旧缓存，或被迫用 `no-cache` 每次回源验证——两种都浪费。这一节与《HTTP 演进》的缓存语义、《性能优化》的加载瀑布直接挂钩：**构建期的哈希策略，决定了 HTTP 缓存层能命中多少。**

CDN 部署也在此闭环：哈希文件 + 长 `max-age` + CDN 边缘缓存，让「改一个组件」只让那个 chunk 的哈希变化，其余全部命中缓存——这是「构建 → 部署 → 缓存」协同优化的完整链条。

## 6 模块联邦：跨应用的运行时共享

**模块联邦（Module Federation，Webpack 5 起）** 解决一个更激进的问题：**多个独立部署的应用，如何在运行时共享同一个模块**。经典场景是微前端——一个后台系统由三个团队分别构建、分别上线，但共用一套组件库与依赖。

联邦的思路是把每个应用建成**容器（container）**：应用 A 暴露「远程模块」（如共享的按钮库），应用 B 在运行时从 A 加载这些模块，而不是各自打包一份。这样依赖版本只需升级一次，三个应用同步受益。代价是**运行时耦合**：A 挂了，B 加载 A 的远程模块也会失败，需要容错与回退策略。<span class="marginnote">模块联邦的「运行时共享」与《SSR》一节的「流式渲染」、与《跨端技术》的「小程序容器」共享同一个动机：<strong>把「边界」从构建期推到运行期</strong>，让大型系统能拆分、能独立演进，同时避免重复下载。</span>

## 7 核心对比表：主流打包器

| 工具 | 语言 | 定位 | 优势 |
| --- | --- | --- | --- |
| Webpack | JS | 全能打包器 | 生态最全、模块联邦、配置最强 |
| Rollup | JS | 库/ESM 打包 | Tree Shaking 彻底、产物干净 |
| esbuild | Go | 高速转译/打包 | 快一个量级、内置压缩 |
| Vite | JS/Go | 开发服务器 + 打包 | 原生 ESM 冷启动 + Rollup 生产构建 |
| Rspack | Rust | Webpack 兼容 | 高吞吐、贴近 Webpack 配置 |

## 8 小结

- 模块系统从 **IIFE → CJS/AMD → ESM** 演进，ESM 的**静态可分析**是打包、摇树、分割的共同前提。
- 打包器 = **依赖图 → 合并 → 分块**；代码分割 + 共享 chunk 让缓存复用最大化。
- **Tree Shaking** 依赖 ESM 静态结构与 `sideEffects: false`，只能删「无副作用的未用代码」。
- **压缩**删空白改短名，**Source Map** 还原源码供调试。
- **Vite** 开发期用原生 ESM + esbuild 快启动，生产期用 Rollup；**HMR** 让更新保持页面状态。
- **模块联邦**把共享从构建期推到运行期，是微前端的基础设施。
- **内容哈希文件名** + 长缓存 + CDN，让「改一个组件只更新那个 chunk」。
- 具名导出、避免动态属性访问，是让你的库「能被摇干净」的硬规则。
- 构建是《HTTP 演进》与《性能优化》之间的翻译层：少请求、小体积、高命中全在这里落定。
- 构建工程不是「配置个 webpack」那么简单，而是一整套「模块语义 + 缓存策略 + 产物形态」的系统设计。
- 下一节我们将用指标反推构建策略：Core Web Vitals 正是检验「打包打包得好不好」的裁判。
- 记住一句话：**构建的终点不是产物文件，而是浏览器里的首屏体验**。
