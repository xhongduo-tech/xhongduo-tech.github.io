## 为什么从 HTTP 演进开始

一个页面要渲染，浏览器先得把 HTML、CSS、JS、图片从服务器「搬」到本地。这条搬运管道的协议叫 **HTTP（超文本传输协议）**。它的每一次换代，几乎都是为了一件事：**让资源更快、更可靠、更省地到达**。从 1991 年的 HTTP/0.9 到 2022 年成为正式的 HTTP/3，协议演进史就是一份「网络如何拖慢 Web、工程师如何反击」的档案。

本节把上一节《浏览器架构》里「网络进程负责拿资源」的幕后拆开，也直接为后面《构建工程化》里「为什么要打包、为什么拆 chunk」、《性能优化》里「加载瀑布（loading waterfall）」提供网络层的解释。

## 1 从 0.9 到 1.1：一个协议长成 Web 的骨架

- **HTTP/0.9（1991）**：只有 `GET` 一个方法，只传纯 HTML 正文，没有头部、没有状态码，请求完就断开连接。
- **HTTP/1.0（1996，RFC 1945）**：加入请求头、响应头、状态码（如 `200`、`404`）、`POST` 等方法；但**每个请求都要新建一条 TCP 连接**，建立连接的三次握手成本压在每次请求头上。
- **HTTP/1.1（1997，RFC 2616，后更新为 RFC 7230–7235）**：一次大飞跃。引入**持久连接（keep-alive）**——同一连接可复用，省去反复握手；引入**管线化（pipelining）**、**分块传输编码（chunked）**、`Host` 头（让一台服务器能挂多个虚拟主机）以及现代缓存指令（`Cache-Control`、`ETag`）。

<span class="marginnote">管线化在纸面上很美：客户端连发多个请求不必等响应。但它要求服务器<strong>按请求顺序</strong>逐个返回响应，队头那个慢响应会卡住后面全部；加上各实现兼容性糟糕，浏览器最终几乎都关掉了它。管线化的失败直接催生了 HTTP/2。</span>

HTTP/1.1 还有一个关键现实：**浏览器对同一源（origin）最多开约 6 条 TCP 连接**。这意味着一个页面若有 30 个资源，就要在 6 条连接上排队吞吐。为了绕过这个限制，工程上出现了「域名分片（domain sharding）」——把一个站点拆到多个子域（`a.example.com`、`b.example.com`）以增加并行连接数，代价是 DNS 查询、连接握手、TLS 握手的整体上升。这套「跟协议较劲」的奇技，正是后来 HTTP/2 想根治的问题。

HTTP/1.1 同时确立了现代**缓存语义**，它们沿用至今：`Cache-Control` 用 `max-age`、`no-cache`、`no-store` 等指令告诉客户端/代理「缓存多久、能否复用」；`ETag` 是资源的指纹，配合 `If-None-Match` 做**条件请求**——资源没变时服务器只回一个 `304 Not Modified` 头，正文不再重传。这套语义被 HTTP/2、HTTP/3 原样继承，是《性能优化》一节里「第二次访问为何快」的核心。

## 2 队头阻塞：1.1 时代的两座大山

**队头阻塞（Head-of-Line Blocking）** 是 HTTP 演进史上的头号反派，它分两个层面：

**HTTP 层的队头阻塞**：同一连接上，响应必须严格按请求顺序返回。若第一个请求要下载 10 MB 的视频，排在其后的 CSS、JS 就都得等它传输完——即使网络空闲、其他响应早已就绪。

**TCP 层的队头阻塞**：TCP 保证「按序可靠交付」。当一个数据段（segment）丢失，接收方必须等重传，后续已到达的数据段只能排在缓冲区里等待。于是**一次丢包就会让整条 TCP 连接「暂时冻结」**，无论这条连接里跑的是哪几个请求。HTTP/2 解决了第一座山，却绕不过第二座山——这正是 QUIC 出场的原因。

一个具体的瀑布（waterfall）就能说明问题：首屏加载一个 HTML 和它引用的 3 张关键图片。1.1 时代若第一个资源是 2 MB 的大图，其后的 CSS、JS 全部排在它后面；把大图改为懒加载、把 JS 标成 `async`、把关键 CSS 内联——这些《性能优化》一节的标准动作，本质都是在「绕过队头阻塞」这一现实约束下挤出来的优化空间。

## 3 公式解析：带宽延迟积——为什么「一条连接」那么成问题

要理解「连接越多越快」与「一条连接复用」各自的逻辑，需要一条 TCP 的核心公式：

$$
\text{带宽延迟积（BDP）} = \text{带宽（bandwidth）} \times \text{往返时间（RTT）}
$$

- **带宽（bandwidth）**：链路每秒能传输的比特数，如 100 Mbps。
- **往返时间（RTT）**：一个数据包从发送到收到确认（ACK）所花的时间，通常几十到几百毫秒。
- **带宽延迟积**：链路「在途容量」——单位时间内能塞在管道里、还没来得及确认的数据总量。

TCP 有一个「在途数据上限 = 发送窗口（window）」。要让吞吐量接近带宽，窗口必须不小于 BDP：

$$
\text{理论吞吐量} \approx \frac{\text{窗口大小}}{\text{RTT}}
$$

拆三步理解：

- **第一步**：RTT 大（如跨国 200ms），确认回得慢，窗口就得开得很大才能占满带宽。若窗口只够 1 MB，吞吐就被锁死在 $1\text{MB} / 0.2\text{s} = 5\text{Mbps}$，与带宽无关。
- **第二步**：HTTP/1.1 的 6 条连接，本质是「用 6 个独立窗口拼带宽」。但每条连接各有握手与拥塞控制慢启动，资源竞争且开销翻倍。
- **第三步**：HTTP/2 把 6 条连接合成 1 条，**在单条连接的窗口内复用**——只要窗口够大、丢包少，单连接多路复用反而比多连接更高效。可一旦丢包触发 TCP 冻结，1 条连接比 6 条更容易整体停摆。

<span class="marginnote">这就是「为什么 HTTP/2 在强网（低丢包、高带宽）上完胜 1.1、在弱网（高丢包）上有时还不如 1.1」的数学解释：多路复用省了握手与慢启动，但把全部鸡蛋放进了 TCP 这一只篮子里。</span>

## 4 HTTP/2：二进制分帧、多路复用与 HPACK

HTTP/2（2015，RFC 7540）是对 HTTP 传输机制的一次彻底重写，而**上层语义（方法、头、状态码）保持兼容**——所以服务器和浏览器能无感升级。

- **二进制分帧层（binary framing layer）**：把原来的文本报文拆成二进制**帧（frame）**——`HEADERS` 帧、`DATA` 帧、`SETTINGS` 帧等。帧是传输的最小单元。
- **多路复用（multiplexing）**：多个请求/响应被切成一帧帧，**交错**地跑在同一条 TCP 连接上，接收方按「流 ID」重组。响应的顺序不再被强制串行——这就是对 HTTP 层队头阻塞的根治。
- **流（stream）**：一次请求-响应全程是一条流，带优先级与依赖关系。服务器可据此先推关键资源。
- **HPACK 头压缩**：HTTP 头以明文重复传输极浪费（Cookie 动辄几百字节）。HPACK 用**静态表 + 动态表 + 哈夫曼编码**把重复头压到个位数倍率。
- **服务器推送（server push）**：服务器猜测客户端马上要 CSS/JS，主动 `PUSH_PROMISE` 推过去，省去一次请求往返。

多路复用还带来两个配套机制：**流优先级与依赖（stream priority）**——前端可以把首屏关键 CSS 所在流标记为最高优先级，让服务器先发；**流量控制（flow control）**——用 `WINDOW_UPDATE` 帧按流粒度控制发送速率，避免一条流吃光整条连接的带宽。这些机制让「单连接」不仅没有退化成瓶颈，反而成为可以精细调度的「高速公路」。

<span class="marginnote">服务器推送听起来很美，却常被滥用：推送的资源若客户端本有缓存，等于白白占用连接带宽；浏览器后来默认禁用推送，转而推荐 `<link rel="preload">`——主动声明而非猜测。这为《性能优化》一节的资源提示（preload/prefetch/preconnect）埋下伏笔。</span>

## 5 HTTP/3 与 QUIC：终结 TCP 队头阻塞

HTTP/2 解决了 HTTP 层队头阻塞，但 TCP 层的队头阻塞还在：一条连接里只要有一个段丢失，后续全排队。HTTP/3（2022，RFC 9114）把传输层从 TCP 换成 **QUIC**（RFC 9000，基于 UDP），做对了两件事：

1. **流级隔离**：QUIC 里的每条流独立拥塞控制，一条流丢包只影响它自己，不再冻结同连接的其他流——TCP 层队头阻塞被终结。
2. **连接建立更快**：QUIC 把传输握手与 TLS 1.3 握手合并，首次连接 1-RTT，**复用连接 0-RTT** 即可发数据；连接迁移（如 Wi-Fi 换 4G）靠连接 ID 而不换 IP 语义，不断连。

配套的 **QPACK** 在头压缩上另起炉灶（因为 QUIC 流不保证全局有序，动态表同步需要专门的指令），`Alt-Svc` 让服务器宣布「我支持 HTTP/3」。如今主流 CDN 与浏览器的 HTTP/3 占比早已过半，但对长尾网络（老旧代理、受限 UDP）的降级路径仍然重要。

对前端工程师来说，HTTP/3 的落地是「透明」的：浏览器与 CDN 协商好就自动升级，代码无需改动。但理解它仍有实际价值——当你在弱网（丢包率高、移动网络切换频繁）上报页面「莫名其妙慢」，很可能就是 TCP 层队头阻塞在作祟，而 HTTP/3 恰恰是针对这类场景设计的。

## 6 核心对比表：三代 HTTP

| 维度 | HTTP/1.1 | HTTP/2 | HTTP/3 |
| --- | --- | --- | --- |
| 传输层 | TCP（每源约 6 条） | TCP（单条连接） | QUIC（UDP） |
| 多路复用 | 无（按序排队） | 流内多路复用 | 流内多路复用 |
| HTTP 层队头阻塞 | 存在 | 解决 | 解决 |
| TCP 层队头阻塞 | 存在 | 存在 | 解决（流级隔离） |
| 握手成本 | 新连 3 次握手 | 复用连接；首次+握手 | 首次 1-RTT，复用 0-RTT |
| 头压缩 | 无 | HPACK | QPACK |
| 关键特性 | 持久连接 | 二进制分帧/推送 | 连接迁移/流级隔离 |

## 7 小结

- HTTP/1.1 靠**持久连接**解决握手开销，但**管线化失败**，留下 HTTP 层与 TCP 层双重队头阻塞。
- **带宽延迟积（BDP）= 带宽 × RTT** 决定单连接吞吐上限，解释了多连接时代的取舍。
- HTTP/2 用**二进制分帧 + 多路复用**根治 HTTP 层队头阻塞，用 **HPACK** 压头，用**服务器推送**省往返。
- HTTP/3 用 **QUIC（UDP）** 实现流级隔离，终结 TCP 队头阻塞，并提供 0-RTT 与连接迁移。
- 工程启示：**能少一个请求就少一个**，但更要理解「为什么」——协议层的每一次换代都在为页面提速铺路。
- 缓存语义（`Cache-Control`/`ETag`/`304`）跨版本沿用，是「第二次访问快」的根基。
- 协议演进是不破不立的历史：管线化失败催生 HTTP/2，TCP 队头阻塞催生 QUIC。
