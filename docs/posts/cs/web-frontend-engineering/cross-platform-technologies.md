## 为什么从跨端技术开始

「写一次，处处运行」是 Web 的原生承诺，但「处处」不止浏览器：手机桌面、离线环境、重计算场景、以及微信这类超级 App 的封闭容器。**跨端技术**就是回答「Web 能力如何在不同环境里延续」的一组答案：PWA 让网页可安装可离线，WebAssembly 让浏览器能跑重计算，小程序容器让 Web 代码在受限沙箱里安全运行。

本节把《浏览器架构》的渲染进程、《JavaScript 引擎》的 JIT/内存模型、《Web 安全》的信任边界，投影到这三个新环境中去。

## 1 PWA：让网页像一个 App

**PWA（渐进式 Web 应用，Progressive Web App）** 的核心理念是「增强式」：一个普通网页，随着能力被支持，逐步变成可安装、可离线、可推送的「App 级」体验。它由三块基石组成：

- **Manifest（Web 应用清单）**：`manifest.json` 描述应用名称、图标、主题色、启动方式，让浏览器把它当「可安装应用」展示，用户可「添加到主屏幕」。
- **Service Worker**：一个**独立于页面的脚本**，充当网络代理——所有页面请求都先经过它。它是 PWA 的心脏，支撑离线与缓存。
- **HTTPS**：Service Worker 是「可信能力」，只在 HTTPS 下注册（`localhost` 除外）。

浏览器对「可安装」有硬性门槛：**页面必须已注册 Service Worker，且满足基本的交互参与度**（如用户访问过一段时间）。这样设计是为了防止垃圾站点靠「一键安装」骚扰用户。被拒绝时，问题几乎总是「Service Worker 没注册成功」或「访问信号不足」。

**Service Worker 生命周期**只有三个事件：`install`（安装，预缓存关键资源）、`activate`（激活，清理旧缓存）、`fetch`（拦截请求，按缓存策略响应）。缓存策略按场景选择：

- **Cache-first（缓存优先）**：有缓存直接用，适合版本化静态资源——与《构建工程化》的「内容哈希」天然契合。
- **Network-first（网络优先）**：先走网络，失败回退缓存，适合实时数据。
- **Stale-while-revalidate**：显示缓存的同时后台更新——老朋友了，《HTTP 演进》与《状态管理》里都见过它。

<span class="marginnote">Service Worker 与页面的关系值得厘清：它在<strong>另一个线程</strong>运行，受浏览器独立管理（可被杀掉重启），<strong>不直接操作 DOM</strong>，只通过 `fetch` 事件介入网络、通过 `postMessage` 与页面通信。它相当于给页面加了一层「离线的 HTTP 层」——这是《HTTP 演进》在应用侧的延伸。</span>

PWA 的离线能力直接改善《性能优化》的体验：`web.dev` 的经典评估中，「可离线」与「首屏秒开」是 PWA 审计的核心项。iOS 从 Safari 11 起逐步支持、Chrome/Edge 完整支持，「添加到主屏幕」后 PWA 甚至可以全屏运行——**它不是「另一个 App」，而是「Web 原生的 App 化」**。

PWA 还常与**推送通知（Web Push）** 搭配：通过 `Push API` + 服务端推送，让网页具备「唤醒用户」的能力。但推送权限与 App 一样敏感，滥用会被用户关掉、被平台限制。对产品而言，PWA 的价值是**免审核分发**：链接即安装，不经过应用商店——对更新频繁、地域受限的场景尤其重要。它与小程序「宿主内分发」形成了两种截然不同的分发哲学。

## 2 WebAssembly：让浏览器跑重计算

**WebAssembly（Wasm）** 是一种**低层字节码格式**：C/C++、Rust、Go 等语言编译成 `.wasm` 后，浏览器可以直接运行，性能接近原生。它不是取代 JavaScript，而是**补足 JavaScript 做不了或做不好的重计算**。

核心事实：

- **线性内存**：Wasm 模块拥有一块连续内存，用 32 位偏移访问；JavaScript 侧通过 `ArrayBuffer`/`WebAssembly.Memory` 共享这块内存，数据交换走「共享内存 + 拷贝」。
- **类型有限**：只有 `i32`/`i64`/`f32`/`f64` 四种数值类型与函数类型——没有字符串、没有对象，一切高层数据结构都要由宿主（JS 或 Rust 的 `wasm-bindgen`）编解码。
- **流式编译**：`WebAssembly.instantiateStreaming` 边下载边编译，进一步压 TTFB 到「可执行」的间隔。

典型战场：视频编解码（`<video>` 之外的自定义编解码器）、图像处理（WebP/AVIF 解码）、3D 渲染计算、加密、以及**把 C/C++ 老代码库搬到 Web**（如 Emscripten 编译 ffmpeg）。浏览器图形栈背后，WebGPU 着色器也可经 Wasm 分发——这条线直接通向《浏览器架构》的 GPU 进程。

一个具体例子：浏览器原生只解码常见的图片格式，遇到小众格式（如 TIFF、多帧 GIF、RAW）就无能为力——用 Emscripten 把 libvips 或 OpenCV 编译成 Wasm，浏览器就获得了「新编解码器」，无需等待厂商支持。**Wasm 给了浏览器「装新轮子」的自由**，这也是 Google Earth、Figma 这类重应用敢上 Web 的原因之一。

Wasm 的多线程也有讲究：`WebAssembly.Threads` 引入共享内存（`SharedArrayBuffer`）与原子指令，让 Wasm 可以真正并行——但共享内存触发了浏览器更强的安全约束（需要跨源隔离，即 `COOP`/`COEP` 头）。这又回到了《Web 安全》的主题：**能力越大，浏览器的信任要求越高**。对大多数前端来说，单线程 Wasm 已够用，多线程是锦上添花的进阶选项。

<span class="marginnote">Wasm 与《JavaScript 引擎》的对比最能说明问题：<strong>V8 用 JIT「猜」类型来提速，Wasm 则把类型信息在编译期就写死</strong>——所以 Wasm 不需要隐藏类、不需要类型反馈、也不需要去优化，性能可预测。代价是开发体验：你得用 Rust/C++ 写代码，还得管内存。它不是「更好的 JavaScript」，而是「JavaScript 之外的另一种轮子」。</span>

## 3 小程序容器：受限沙箱里的 Web

**小程序**（WeChat 小程序、支付宝小程序、抖音小程序）是一个「超级 App 内部的封闭应用体系」。它们长得像 Web，却运行在一套**受限运行时**里：

- **无 DOM 访问**：小程序没有传统 DOM API，页面用自定义 DSL（微信的 WXML/WXSS、支付宝的 AXML）描述，由**渲染层**负责渲染。
- **双线程模型**：逻辑层（运行 JS，用 V8/JSCore 之类的引擎）与渲染层（WebView/自渲染）分离，通过**桥（bridge）** 通信。数据更新走 `setData`，桥接一次的成本不小——这解释了小程序性能优化的经典命题「减少 `setData` 调用与数据量」。
- **封闭能力**：`wx.login`、`getUserProfile`、支付等能力只通过宿主暴露的 API 获得，且受严格权限控制——**沙箱既是安全边界，也是能力边界**。

双线程模型还有一层安全动机：**逻辑层不直接接触 DOM，恶意代码即便跑起来，也拿不到页面渲染树**。这比浏览器「渲染进程沙箱 + SOP」的防护更硬——代价是开发自由度。实践中 `setData` 有一个隐性成本：**每次调用都要把数据序列化后跨线程拷贝**，数据量大（如长列表）时尤其明显，所以「分页拉取、局部更新」是小程序性能优化的基本功，这又与《性能优化》的「少、小、精准」完全同构。

<span class="marginnote">小程序容器对前端工程师意味着「浏览器机制的缺失项要自己补」：没有 DOM → 模板编译（对应 Vue/Svelte 的编译器）；没有标准事件循环依赖 → 桥接异步（对应《DOM 与事件》的时序）；没有 CORS 概念 → 一切请求由宿主代理（对应《Web 安全》的信任模型）。学会小程序，本质是把本专题前几节的知识<strong>重新装配到一个缺部件的环境里</strong>。</span>

小程序容器还催生了「跨端框架」：**uni-app**、**Taro** 把 React/Vue 源码编译成多端可运行的小程序代码，思路与《构建工程化》的编译时框架一脉相承——**用编译器抹平运行时差异**。这与 Wasm「抹平语言差异」、PWA「抹平平台差异」一起，构成了跨端技术的三种「抹平」方式。

## 4 邻近方案：RN、Flutter 与「桥接跨端」

提到跨端，绕不开另一族方案——**把 Web 技术栈映射到原生 UI**：

- **React Native**：用 React 写 UI，但渲染的是**原生组件**（`<View>` → UIView），JS 与原生通过**桥（bridge）** 通信。它保留 React 心智（Hooks、组件树），换掉「渲染到 DOM」为「渲染到原生」——是《现代框架》与《浏览器架构》在原生世界的投影。
- **Flutter**：不用 Web 技术栈，用 Dart + 自绘引擎（Skia/Impeller）自己画 UI，性能稳定、跨端一致，但与 Web 生态割裂。
- **Tauri/Electron**：用 Web 前端包桌面应用——Electron 内置 Chromium + Node，Tauri 用系统 WebView + Rust 后端，体积小得多。

这族方案的共同点是「**多一层桥**」：JS/Dart ↔ 原生双向通信，桥的性能与数据拷贝直接决定流畅度——它和《小程序容器》的 `setData`、和《WebAssembly》的共享内存，是同一个「跨环境数据交换」问题的三种解法。**选型本质是选「你要多 Web 生态，还是要多原生性能」**。

桥的性能瓶颈是经典工程话题：React Native 早期因「JS 每帧都要过桥」而卡顿，后来引入 Fabric + 并发特性、把高频操作下沉到原生；Flutter 则干脆「少桥多自绘」。**所有跨端方案的历史，几乎都是「把桥的次数与数据量压下来」的历史**——这与《DOM 与事件》里「减少主线程往返」、与《性能优化》里「减少长任务」是同一条纪律的三种方言。

## 5 核心对比表：三大跨端技术

| 维度 | PWA | WebAssembly | 小程序容器 |
| --- | --- | --- | --- |
| 本质 | Web 能力的增强 | 浏览器内的低层字节码 | 超级 App 内的受限运行时 |
| 运行时 | 浏览器（Service Worker） | 引擎内 Wasm 虚拟机 | 宿主隔离沙箱 |
| 离线 | 支持（Service Worker 缓存） | 无特殊支持 | 受限（受宿主策略） |
| 性能 | 一般 | 接近原生 | 一般（桥接有开销） |
| 安全边界 | SOP + HTTPS | 线性内存隔离 | 宿主严格沙箱 |
| 典型场景 | 可安装 Web App | 重计算、老代码迁移 | 微信生态应用 |

## 6 小结

- **PWA** = Manifest + Service Worker + HTTPS：缓存策略（cache-first/network-first/stale-while-revalidate）让网页可离线、可安装。
- **WebAssembly** 用编译期定死的类型换取可预测的性能，擅长重计算与 C/C++/Rust 迁移，不是 JS 的替代品。
- **小程序容器**在受限沙箱里运行 Web 形态代码：无 DOM、双线程桥接、`setData` 是性能关键。
- 三种跨端思路殊途同归：**PWA 增强 Web、Wasm 扩展计算、小程序容器重定义 Web 的运行环境**。
- 跨端框架（uni-app/Taro）用编译器抹平运行时差异，是编译时思想在跨端的重演。
- 小程序性能的核心命题是「**少 `setData`、小数据量、局部更新**」——与 Web 性能的「少、小、精准」完全同构。
- 小程序容器强调「能力边界由宿主定」：能做什么由宿主 API 说了算——这是与开放 Web 最本质的差异。
- 无论端如何变，本专题的底层知识（渲染、事件、安全、构建）都原样适用——**它们是跨端的公共底座**。
- RN/Flutter/Electron 靠「桥」映射原生 UI，桥的成本与数据拷贝决定流畅度。
- PWA 补能力、Wasm 补计算、容器补生态、原生映射补性能——跨端是「多工具凑一场戏」。
- 分发哲学之别：PWA 免审核链接分发，小程序走宿主内生态分发，原生 App 走应用商店审核。
- 一个前端工程师的跨端素养，是能在这三套环境里「翻译」本专题的所有机制。
- 跨端选型口诀：**要分发免审核选 PWA，要重计算选 Wasm，要宿主生态选小程序，要原生手感选 RN/Flutter**。
- 跨端技术的终点不是「端」，而是「同一个心智模型在不同运行时上的复用」。
