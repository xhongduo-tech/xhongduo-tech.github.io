## 为什么从 DOM 与事件开始

浏览器把 HTML 变成一棵可编程的树——**DOM（文档对象模型，Document Object Model）**；用户点击、滚动、键盘输入则通过**事件**涌进页面。而连接「用户操作」与「页面更新」的，是那个决定一切执行顺序的**事件循环（event loop）**。可以说：**看懂事件循环，就看懂了 JavaScript 在浏览器里的全部时序。**

本节承接《浏览器架构》的渲染管线（任务排队发生在主线程），并为《现代框架》的 React/Vue「为什么需要虚拟 DOM、为什么批量更新」、《性能优化》的「为什么长任务可怕」提供直接的机制基础。

## 1 DOM：页面的文档对象模型

**DOM（Document Object Model）**：浏览器把 HTML 文档解析后生成的、可编程访问的对象树。树的根是 `document`，往下是 `html`、`body`、各元素节点，叶子是文本节点与属性。

节点类型主要有几种：

- **元素节点（Element）**：如 `<div>`、`<p>`，承载标签名、属性、子节点。
- **文本节点（Text）**：元素内的字符串内容。
- **注释节点、文档节点**：前者对应 `<!-- -->`，后者即 `document` 本身。

JavaScript 通过 `document.querySelector`、`document.getElementById` 等 API 在这棵树上「读取」与「修改」。关键事实：**DOM 不是 JavaScript 的私有物，而是浏览器用 C++ 实现、通过接口暴露给脚本的独立世界**。每次访问 DOM 都有跨语言的边界成本——这解释了为什么「先批量改内存里的 JS 数据，再一次写 DOM」比「逐次写 DOM」快得多，也是 React 的 `setState` 合并、Vue 的响应式批量的底层动机。<span class="marginnote">DOM 的「快与慢」可以量化为：读 `offsetWidth` 会强制同步重排（见《浏览器架构》「强制同步布局」），而 `innerHTML` 整体替换会重建整棵子树。现代前端几乎都不直接操作 DOM，而是交给框架——但框架的每一项优化，都是在对这些真实成本做回避。</span>

## 2 事件循环：单线程上的调度器

JavaScript 在浏览器里**单线程**运行：同一时刻只有一段脚本在主线程上执行。那异步（定时器、网络回调、点击处理）怎么排进这唯一一条车道？答案是**事件循环（event loop）**。

事件循环的核心是**任务队列**：主线程空闲时，从队列取出一个任务执行，执行完再取下一个，如此循环。任务（task）包括：

- 执行整个 `<script>` 脚本；
- 事件回调（点击、键盘、网络就绪）；
- `setTimeout` / `setInterval` 到期的回调；
- 微任务队列的**清空**（见下节）。

**Event Loop 的标准一轮（iteration）是：取出一个任务 → 执行它 → 清空整个微任务队列 → （若需要）执行渲染 → 回到取任务。** 注意「取一个任务」与「清空全部微任务」的差别——这一多一少，决定了无数异步代码的执行顺序。

## 3 微任务与宏任务：优先级的两级台阶

任务并非一视同仁，而是分**宏任务（macrotask，即上文的任务）**与**微任务（microtask）**两级：

- **宏任务**：`setTimeout`、`setInterval`、`I/O` 回调、事件回调。每个宏任务之间，浏览器有机会插入渲染。
- **微任务**：`Promise.then/catch/finally`、`async/await` 的续体、`queueMicrotask`、`MutationObserver` 回调。微任务在**每个宏任务结束后、渲染之前**被一次性清空。

这带来一个极易踩坑的结论：**`Promise.resolve().then(...)` 一定先于 `setTimeout(..., 0)` 执行**，哪怕定时器超时时间设为 0。因为 `setTimeout` 的回调是宏任务，要等当前宏任务 + 微任务清空后、下一次循环才轮到。

```javascript
Promise.resolve().then(() => console.log("微任务先"));
setTimeout(() => console.log("宏任务后"), 0);
// 输出顺序：微任务先 → 宏任务后
```

<span class="marginnote">为什么要有微任务？为了保证「同一个数据变更触发的后续回调在同一轮完成、中间不被渲染打断」。若微任务与宏任务同级，`Promise` 链就会被定时器或渲染插队，一致性会被撕裂。微任务的「连续性」正是 `await` 语义能成立的前提。</span>

危险同样藏在微任务里：**微任务可以无限产生微任务**，导致宏任务与渲染永远轮不到，页面「假死」。经典的死循环 `while(true) { await Promise.resolve() }` 或 `Promise` 递归自调用，都会制造这种饥饿——这与《状态管理》里「大状态树导致的重渲染风暴」是同一类问题。

## 4 渲染时机：任务、微任务与绘制的先后

事件循环不只调度 JS，还调度**渲染**。浏览器在每个宏任务之后、下一宏任务之前，检查是否需要绘制（通常是 60fps，即每 16.67ms 一帧）。关键时序是：

**宏任务 → 清空微任务 → requestAnimationFrame 回调 → 样式计算与布局 → 绘制 → 下一个宏任务**

两点值得牢记：

- **`requestAnimationFrame（rAF）` 在绘制前运行**，所以它适合做「下一帧动画的更新」——在它里面修改样式，本帧就能绘制出去，不会白改。
- **`setTimeout` 不保证与帧对齐**：它只保证「至少等这么久」，可能落在帧中间、可能一次等了两帧。做动画用 `rAF`、做「延迟后做某事」用定时器，是性能纪律的起点。

<span class="marginnote">把「读布局」「写布局」分开，让一次帧循环内浏览器只在渲染阶段重排一次，避免读写交错造成的多次强制同步布局——这条来自《浏览器架构》的规则，在这里有了精确的执行序：写操作尽量集中在 rAF 回调里，读操作放在宏任务里。</span>

渲染时机还引出一条性能红线：**长任务（long task）**。一段超过 50ms 的宏任务会挤掉本应插入的渲染帧，用户就会感到「卡一下」。`PerformanceObserver` 的 `longtask` 条目能直接统计这类任务；《性能优化》一节里 INP（交互到下一次绘制）指标的恶化，多半就是长任务在作祟。事件循环不是玄学，而是可以用工具逐帧观测的调度表。

## 5 事件传播：捕获、目标与冒泡

事件不只是「点到谁就触发谁」，它沿着 DOM 树走完三个阶段：

1. **捕获阶段（capturing）**：从 `window` 一路向下，经过各祖先元素，到达目标元素。此阶段可拦截事件。
2. **目标阶段（target）**：在目标元素上触发。
3. **冒泡阶段（bubbling）**：从目标元素一路向上返回 `window`。

`addEventListener("click", handler, { capture: true })` 让处理函数在捕获阶段执行；默认（`capture: false`）则在冒泡阶段执行。`stopPropagation()` 阻止事件继续传播；`preventDefault()` 则阻止浏览器默认行为（如链接跳转、表单提交）——两者常被混用，语义完全不同。

冒泡带来前端最重要的委派技巧——**事件委托（event delegation）**：与其给成千上万个列表项各绑一个监听器，不如只在父容器绑一个，用 `event.target` 判断点击落在哪个 `data-id` 上。这样新增列表项无需重新绑定，内存占用从 O(N) 降到 O(1)。<span class="marginnote">React 的合成事件系统（SyntheticEvent）把监听器集中挂在根节点、用事件委托 + 事件池来管理，正是把这个浏览器机制工业化了——本专题《现代框架》一节会展开讲。</span>

## 6 核心对比表：宏任务、微任务与渲染

| 队列 | 代表来源 | 执行时机 | 是否可插渲染 |
| --- | --- | --- | --- |
| 宏任务（task） | `setTimeout`、事件回调、`I/O` | 每次循环取一个 | 是（任务之间） |
| 微任务（microtask） | `Promise`、`queueMicrotask`、`MutationObserver` | 每个宏任务后全部清空 | 否（渲染前清空） |
| rAF 回调 | `requestAnimationFrame` | 绘制前统一执行 | 本身即渲染的一部分 |

再放一张「三大 API 该何时用」的对照：

| 场景 | 应选 API | 原因 |
| --- | --- | --- |
| 下一帧动画 | `requestAnimationFrame` | 与渲染对齐，本帧可见 |
| 延迟后执行（不在意帧） | `setTimeout` | 语义是「至少等」，非帧对齐 |
| 状态变更后立刻续做 | `queueMicrotask` | 渲染前完成，保证连续性 |

## 7 小结

- **DOM** 是浏览器用 C++ 实现的文档对象树，访问它有跨语言边界成本，批量更新更划算。
- **事件循环**单线程调度一切：**取一个宏任务 → 清空全部微任务 → （必要时）渲染 → 再取**。
- **微任务优先于宏任务**，`Promise.then` 一定先于 `setTimeout(..., 0)`；微任务无限递归会让渲染饿死。
- **rAF 在绘制前执行**，动画用它；`setTimeout` 只保证延迟下限，不做帧对齐。
- 事件走**捕获→目标→冒泡**三阶段，`stopPropagation` 与 `preventDefault` 语义不同；**事件委托**把监听器成本压到 O(1)。
- 长于 **50ms** 的任务就是长任务，会挤掉渲染帧——这是 INP 恶化的首要来源。
