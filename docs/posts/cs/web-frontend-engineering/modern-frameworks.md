## 为什么从现代框架开始

上一节我们看到操作 DOM 有真实成本：跨语言边界、同步重排、事件循环的时序约束。**现代框架**的价值，就是把这些成本藏进一套「声明式」的抽象里：你描述「UI 应当是什么样」，框架负责「怎么把它变成 DOM」。这是本专题从「浏览器机制」走向「工程实践」的转折点，也是后面《状态管理》《构建工程化》《SSR》几节的共同地基。

先厘清一个时间坐标系：前端框架不是新发明。Backbone（2010）、AngularJS（2010）、React（2013）、Vue（2014）、Svelte（2016）各领风骚十年，核心命题始终是同一个——**在「直接操作 DOM 的命令式」与「描述目标状态的声明式」之间，找到一个开发者体验与运行时效率的平衡点**。看懂这三个框架，你就拿到了前端二十年的浓缩答案。

## 1 声明式与虚拟 DOM：React 的核心命题

React 的出发点极其朴素：**UI = f(state)**。开发者描述 state 变化后 UI 应该长什么样，React 负责把差异落到真实 DOM。为此 React 维护一棵与真实 DOM 对应的 **虚拟 DOM（virtual DOM）** 树，每次状态更新时：

1. 用新的 state 重新渲染出新的虚拟 DOM 树；
2. 与上一棵虚拟 DOM 做**调和（reconciliation）**，算出差异（diff）；
3. 把差异批量、最小化地提交到真实 DOM。

「先算差异、再一次提交」正好规避了我们在《DOM 与事件》里看到的「逐次写 DOM」的高成本——**多次状态更新合并成一次提交**，还避开了脚本执行中途的强制同步布局。<span class="marginnote">虚拟 DOM 不是「快」的代名词，而是「把 DOM 操作降频、批量、可预测」的调度层：真正的性能来源是 diff 后的最小 DOM 变更 + 批量提交，而不是「多一层虚拟树」本身。Svelte 就认为这一步可以完全去掉。</span>

React 的组件模型对应 Osmani 书里的经典结构模式：**类组件用「类 + 继承」组织，函数组件 + Hooks（React 16.8，2019）则把「状态、副作用、上下文」拆成可组合的原子**——Hooks 是「行为复用」对「继承复用」的替代，也正是《设计模式》里组合优于继承这一原则在组件层的落地。

调和算法的细节直接决定性能：React 靠**列表的 `key`** 来识别「哪个元素是哪个」，`key` 稳定，diff 就能高效复用旧节点；`key` 用数组下标，增删时就会误认元素，产生「复用错节点」的经典 bug。深层语义是：**虚拟 DOM 的 diff 不是一个通用算法，而是一组基于「相同位置、相同类型、稳定 key」的启发式假设**——框架的快，建立在「开发者遵守约定的数据形态」之上。

## 2 并发模型：让渲染可以被中断

React 17 引入、React 18（2022）默认开启的**并发特性（Concurrent Features）**，把「渲染」从「不可中断的整块工作」变成「可分片、可暂停、可放弃的工作」：

- **可中断渲染**：一个耗时的更新可以拆成多片，让位给更紧急的更新（如输入框的每一次敲击）。
- **优先级调度**：紧急更新（用户输入）插队，非紧急更新（后台数据到达）让路。
- **`useTransition` 与 `useDeferredValue`**：把「非紧急更新」显式降级，界面保持响应。

实现这一切的是 **Fiber 架构**（React 16，2017）：React 把渲染工作拆成一个个 fiber 节点，构成可暂停/恢复/重排的工作链表，由调度器（scheduler）在事件循环的空隙里推进——这正是上一节「宏任务之间插渲染」机制的工程化利用。<span class="marginnote">可中断渲染的代价是「一次渲染可能被废弃重来」：React 用「把旧 UI 保持到新 UI 完全就绪再一次性切换」来兜底，避免用户看到半成品。这种「让出主线程、分片工作」的思路，与《性能优化》里「把长任务拆成短任务」的纪律同源。</span>

并发模型还支撑起 **Suspense**：让组件「声明自己在等待数据」，React 在数据就绪前展示回退 UI，数据到位后再无缝切换。配合 **React Server Components（RSC）**，组件可以在服务器端直接访问数据库、读取文件，客户端只接收渲染好的树——把「数据获取」从客户端瀑布（先 HTML 后 JS 再数据）里解放出来。这两项是 React 从「客户端渲染库」迈向「全栈框架」的关键，也直接关联本专题《SSR/SSG/ISR》一节的流式渲染。

## 3 Vue 的响应式：观察者模式的现代演绎

Vue 走了另一条路：不靠「重跑整个组件再 diff」，而是**精确追踪哪些数据被哪些视图依赖**。Vue 3 用 ES6 的 **Proxy** 重写了响应式系统：

- 访问响应式对象的属性时，**收集**依赖（当前正在渲染的组件）；
- 修改属性时，**触发**依赖的更新；
- 只有「用到了被改数据」的组件才会重新渲染——**粒度是组件级，而非整棵树**。

这套机制在 Osmani 的分类里正是 **观察者模式（Observer）/ 发布-订阅（Publish/Subscribe）**：数据是被观察者（subject），组件是观察者（observer），响应式系统是中间的依赖收集器。Vue 的「模板编译 + 组件级依赖追踪 + 批量更新」同时提供了确定性：`computed` 缓存派生值，`watch` 监听副作用，模板在编译期就被解析成高效的更新函数。

Vue 与 React 的取舍浓缩成一句话：**React 把「计算差异」交给运行时，Vue 把「知道谁依赖谁」做在数据层**——前者更通用，后者更精确。两者共享同一个底层信念：批量化、最小化地触碰 DOM。

Vue 的**模板编译器**也值得一提：模板里的 `v-if`、`v-for`、`{{ 插值 }}` 在编译期被翻译成渲染函数，并打上「动态节点」标记。到了运行时，**同构渲染**（模板 + 渲染函数）能让 Vue 对「哪里会变」有先验知识，连 diff 都比 React 更省——这被称为「带编译信息的虚拟 DOM」。它证明了一个趋势：**把能提前做的判断放到编译期**，运行时只做必须运行时才知道的事。

## 4 编译时框架：Svelte 与信号（Signal）

**Svelte**（2016 起）质疑了虚拟 DOM 的必要性：既然框架在编译期就能看到全部组件代码，为什么不直接把组件**编译成手写级的原生 JavaScript**？

- **无虚拟 DOM**：编译产物直接生成精准的 DOM 更新代码，运行时几乎为零——框架的「开销」被前移到编译期。
- **编译器分析**：它知道 `count += 1` 会改到哪个变量、这个变量被哪几处模板引用，于是只生成「更新这几处」的代码。
- **Svelte 5 的信号机制**：用细粒度信号（signal）追踪依赖，连「组件级更新」都省了，直接精确到「哪个绑定」。

Svelte 的声明式写法在编译器眼里是一份「要做什么」的说明书：

```svelte
<script>
  let count = 0;
</script>
<button onclick={() => count++}>点了 {count} 次</button>
```

编译后，这段代码只生成「更新按钮文本」的语句，没有协调器、没有 diff、没有运行时调度。代价是**更新逻辑由编译器固化**：一旦需要在运行期动态决定「更新什么」（如运行时拼接模板），编译时路线就力不从心——这也是 Svelte 直到今天仍被评价为「极客的工具，但生态回报明确」的原因。

**信号（signals）** 成为 2020 年代前端的热词：Solid.js 把它做到极致（真·细粒度、无虚拟 DOM），Angular 从 v16 起引入，React 团队也在实验。信号的核心是把「值 + 依赖订阅」打包成一个原子对象，读时收集、写时触发——可以看成 **Vue 响应式的「无框架化」与 Svelte 编译时思路的合流**。<span class="marginnote">设计模式视角下，信号就是观察者模式的「值版本」：`const count = signal(0)` 返回的可写信号自带订阅表。把它与 Osmani 书中 Singleton/Observer 的例子对照，会发现现代框架并没有发明新的模式语言，只是把旧模式工程化、类型化、可组合化。</span>

## 5 框架与设计模式：MV\* 的遗产

用 Osmani 的《Learning JavaScript Design Patterns》回看框架史，会发现今天的一切都是设计模式的工程化沉淀：

- **MVC 与 MV\* 谱系**：Backbone 是经典 MVC，AngularJS 引入 MVVM（Model-View-ViewModel），Vue 的 `data` + `methods` + 模板即 MVVM 的轻量版。ViewModel 负责「把模型的变化翻译成视图的更新」——这正是 Vue 响应式做的事。
- **观察者/发布-订阅**：Vue 响应式、React 的 store 通知、Angular 的 RxJS 事件流，都是发布-订阅的不同方言。
- **单例（Singleton）**：全局唯一的 store（Redux store、Vuex store）就是单例模式的现代形态——我们下一节《状态管理》会专门展开。
- **中介者（Mediator）**：事件总线、框架的调度中心，把「谁跟谁直接通信」变成「都找我转达」，降低耦合。

框架没有抛弃模式，只是把它们升级成了带类型、带编译优化、带并发调度的「模式运行时」。读懂设计模式，等于拿到了阅读任何框架的通用词汇表。

## 6 核心对比表：三大框架的思想路线

| 维度 | React | Vue | Svelte |
| --- | --- | --- | --- |
| 范式 | 函数式（f(state)→UI） | 响应式 + 模板 | 编译时 + 信号 |
| DOM 更新 | 虚拟 DOM + diff | 组件级依赖追踪 | 编译期生成精准更新 |
| 运行时大小 | 较大（约 40 KB 内核） | 中等（约 30 KB） | 极小（接近零） |
| 并发 | Fiber 可中断渲染 | 无（依赖同步批处理） | 无（编译期已就绪） |
| 对应设计模式 | Hooks（组合优于继承） | Observer / MVVM | 编译期优化（无模式运行时） |
| 上手曲线 | 中（需理解并发） | 低（模板直观） | 中（需理解编译期） |

## 7 小结

- **React** 用**虚拟 DOM + 调和**把 DOM 操作批量化；**Fiber + 并发特性**让渲染可中断、可分级。
- **Vue** 用 **Proxy 响应式**精确追踪依赖，是**观察者模式**的现代工程实现，粒度到组件。
- **Svelte** 把工作前移到**编译期**，去掉虚拟 DOM 与大部分运行时，Svelte 5 全面转向**信号**。
- **信号（signals）** 是当前各框架收敛的方向：值 + 依赖订阅打包，读写即收集/触发。
- 三大框架共享同一底层约束：**少碰 DOM、批量碰 DOM**——这正是《DOM 与事件》一节的机制结论。
- 从 Osmani 视角看，框架是设计模式的**工程化、类型化、并发化**升级：MV\*、观察者、单例、中介者一个不少。
- 选型不是「谁快用谁」，而是「谁的心智模型与你的问题匹配」——React 适合复杂交互的确定性，Vue 适合模板驱动的渐进增强，Svelte 适合运行时预算极紧的场合。
- 框架是「把机制成本藏起来」的工程：藏得越深，你要懂的底层就越多——而本专题前四节正是这些底层的钥匙。
