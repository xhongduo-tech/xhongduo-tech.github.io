## 为什么从渲染策略开始

同样一份 React/Vue 代码，可以在浏览器里渲染（CSR）、可以在服务器上渲染（SSR）、可以在构建时渲染成静态文件（SSG）、也可以「构建时生成 + 按需再更新」（ISR）。这四种不是四种「技术」，而是**同一套代码在不同时机执行**的四种选择。选哪种，取决于你对「首屏速度、内容新鲜度、服务器成本」三者的权衡。

本节把《性能优化》的指标当作天平，把《状态管理》的「谁是真相」延伸到「谁在渲染」，最终给出一个可操作的决策框架。

## 1 光谱的起点：CSR 与 SSR

**CSR（客户端渲染，Client-Side Rendering）**：服务器只返回一个空壳 HTML 与一个 JS 包，浏览器下载并执行 JS 后，才把内容渲染出来。这是 SPA（单页应用）的默认形态。优点是交互体验一致、一次加载后导航无刷新；缺点是**首屏依赖 JS 下载与执行**——LCP 被拖后，且爬虫看到的是空壳（SEO 差，虽然现代爬虫能执行 JS，但成本与不确定性仍在）。

**SSR（服务端渲染，Server-Side Rendering）**：服务器把组件渲染成完整 HTML 直接返回，浏览器「拿到就能看」。首屏 TTFB 里的内容立即可见，SEO 友好。但它引入了**水合（hydration）**：浏览器拿到的是「静态的 HTML 骨架」，还需要加载同一份 JS、在客户端把事件处理器挂回那棵已经存在的 DOM 树——否则页面能看不能点。

CSR 与 SSR 背后还有一层**架构之别**：**SPA（单页应用）** 用一份 HTML + 路由在前端切换页面，导航无刷新但首屏重；**MPA（多页应用）** 每页独立 HTML，首屏快但导航要整页刷新。SSR/SSG 通常配合 MPA（Next.js 虽是「一个应用」，但每个路由可静态/动态生成），CSR 通常配合 SPA（Vite + React Router 的典型形态）。「框架是 SPA 还是 MPA 的心智」决定了你选哪种渲染策略时顺不顺手。

<span class="marginnote">水合是 SSR 的成本核心：服务器渲染一次、浏览器再渲染一次，「同一棵树被渲染两遍」。Flanagan 第 16 章讲的 Node 服务端能力（流、HTTP 响应、模板）正是 SSR 的工程底座——服务器端不只是「返回字符串」，而是真的在跑组件代码。这也解释了为什么 SSR 要单独维护服务器运行时。</span>

水合有一个著名陷阱：**水合不匹配（hydration mismatch）**。服务器与客户端各自跑一遍组件，若两边的输出不一致（例如组件里用了 `Date.now()`、`Math.random()`、或读取了客户端才有 `window`），浏览器会在水合时「对不上账」，轻则警告、重则整个树重建。规避手段是让「初始渲染」不依赖运行时随机性：把客户端特有逻辑放进 `useEffect`（客户端专用副作用）或 `client-only` 组件。**这条规则是 SSR 时代的常识，却常被新手踩中**。

## 2 SSG 与 ISR：把渲染前移到构建期

**SSG（静态站点生成，Static Site Generation）**：在**构建时**把页面渲染成静态 HTML，部署到 CDN。浏览器请求时 CDN 直接返回现成文件——TTFB 极小、可全球就近、无服务器成本、抗高并发。代价是内容「生下来就是死的」：要更新必须重新构建部署。

**ISR（增量静态再生，Incremental Static Regeneration，Next.js 提出）**：在 SSG 之上加一层**按需失效**。页面构建时静态生成，同时配置 `revalidate` 间隔；到期后第一次请求会触发后台重新生成，新版本生成前用户看到的仍是旧版本（stale-while-revalidate 的页面级版本）。它回答的问题是：**「既想要静态的速度，又不想内容永远不变」怎么办？**

ISR 与《状态管理》里 TanStack Query 的缓存哲学如出一辙：**前端/边缘缓存一份带过期策略的视图，后台按需刷新**。区别只在层级——前者是页面级（HTTP 缓存 + CDN），后者是数据级（应用内缓存）。两层可以叠加：ISR 生成页面、页面内的数据用声明式缓存，形成「页面静态 + 数据新鲜」的组合。

实现层面，Next.js 用 `revalidate`（页面级，秒级）与 `unstable_cache`/`revalidatePath`（数据级、按需手动失效）两条腿走路；静态参数列表由 `generateStaticParams` 在构建时枚举。理解了 ISR，就理解了现代框架的默认姿态：**默认静态、按需动态、显式失效**——能提前渲染的绝不运行时渲染，能在边缘解决的绝不回源。

SSG 也有隐藏成本：**构建时长随页面数线性增长**。一个十万页的站点，每次全量重新生成都耗时数分钟——于是出现「按需生成」（生成到即渲染，首访才生成）、`generateStaticParams` 分批、以及 ISR 的「构建时只生成热门页，冷门页首访再生成」等折中。**静态不是「永远免费」，而是「把成本从每次请求挪到构建时」**——预算视角下，它赌的是「构建频率 < 请求频率」。

## 3 流式 SSR：不等全部，先发关键部分

传统 SSR 有一个隐藏瓶颈：**服务器必须把整页渲染完，才发第一个字节**。某个慢接口拖住整页，用户就只能盯着空白等待。**流式 SSR（Streaming SSR）** 改变这个顺序：

- 服务器把 HTML **分块流式**发送：先发能立刻渲染的骨架（外壳、标题、导航），再逐个发每个异步区域（用 `Suspense` 挂起的那部分数据）。
- 浏览器**边收边渲染**，不必等完整响应。
- React 的 `renderToPipeableStream`（React 18）就是为此而生，配合 `<Suspense>` 描述「哪块先出、哪块后出」。

`<Suspense>` 的边界就是「流的边界」：被 `Suspense` 包裹的异步组件，在其数据就绪前会在流里占一个「加载占位」，数据一到就补发该段 HTML。这相当于把《状态管理》里「加载/成功/失败三态」从数据层搬到了响应层——**页面本身就是分阶段的**。对首屏而言，这常常是把 LCP 从「2 秒整页」压到「600ms 骨架 + 后续渐进」的关键。

这本质上把《HTTP 演进》的「分块传输编码」用在了 HTML 上：**响应不再是「全部或空白」，而是「先到的先用」**。它对 LCP 的改善立竿见影——用户看到框架的速度从「整页渲染完」提前到「第一个 chunk 到达」。

<span class="marginnote">流式 SSR 的代价是工程复杂度：流里 HTML 的顺序与 `Suspense` 边界绑定，客户端水合要等对应流段到齐，错误处理也变复杂（流一旦发出就难以整体回滚）。框架把大部分复杂度藏起来了，但「它为什么快、哪些情况不适用」你仍要心中有数——不是所有页面都需要流式。</span>

流式还与「渐进水合」咬合：浏览器**收到哪一段 HTML，就水合哪一段**，不必等整个流结束——这被称为「流式水合」。于是「服务器分片发送」与「客户端分片接管」形成了一条同步的流水线，理想情况下用户看到骨架时手指已经开始交互。这条「边到边水合」的调度，本质是《DOM 与事件》事件循环在 SSR 语境下的又一次复用：**每一段 HTML 到达都是一个可插渲染的任务边界**。

## 4 岛屿架构：只水合需要的部分

**岛屿架构（Islands Architecture，Astro 提出）** 是对「整页水合」的反叛：与其把整页 JS 都下载并水合一遍，不如**只对页面里真正需要交互的「岛屿」水合**，其余部分保持静态 HTML。

- 页面默认是**纯静态 HTML**（零 JS），速度接近纯静态站；
- 交互组件（评论、搜索、计数器）被标记为岛屿，**只有它们加载并水合自己的 JS**；
- 岛屿之间互相独立，一个岛屿的 JS 不影响另一个。

它和流式 SSR 互补：流式解决「服务器发多快」，岛屿解决「客户端收多少」。两者合并后的终极形态是「HTML 快出、JS 极少、交互刚好够用」——这正是《性能优化》渲染预算的完美状态。

岛屿架构还顺带回答了 SEO 的疑问：**静态 HTML 直接给爬虫，无需执行 JS**——这对内容型站点是「SSG 的速度 + 可交互组件」的最佳组合。Astro 正是靠「默认零 JS + 按需岛屿」在内容站、文档站里崛起；代价是需要刻意区分「静态部分」与「交互部分」，心智模型与纯 SPA 相反，组件复用也受边界约束。

## 5 边缘渲染：把服务器推到离用户最近

SSR 的服务器在「某地」，而用户分布全球。**边缘渲染（Edge Rendering）** 把渲染函数部署到 CDN 的边缘节点（如 Cloudflare Workers、Vercel Edge），让「渲染」发生在距离用户最近的节点：

- **TTFB 从跨洲的几百毫秒，降到同城的几十毫秒**——直接作用在《性能优化》的 TTFB 指标上。
- 边缘节点是**有限运行时**（如 V8 isolates），不能跑全部 Node API，所以边缘渲染与「轻量 SSR」绑定：能静态的尽量静态，必须动态的交给边缘上的轻函数。
- 边缘渲染让 **ISR 的「按需再生」也能发生在边缘**，而不是每次都回源到主服务器。

它本质是「渲染策略 + 部署拓扑」的组合：**CSR/SSR/SSG/ISR 决定代码何时执行，CDN/边缘/服务器决定代码在哪执行**。把两轴叠起来看，整个渲染工程就变成了一张可调矩阵。

还有一个必须提及的约束：**边缘运行时 ≠ Node 完整运行时**。边缘节点提供的是受限的 Web 标准 API（`fetch`、`crypto`、`Request/Response`），没有完整文件系统、没有部分 Node 内置模块。所以「边缘化」不是免费迁移——**你的 SSR 代码越「重」（依赖 Node 特定 API），越难上边缘**。这也是为什么「边缘友好」成了新框架（以及 Flanagan 第 16 章强调的 Node 服务端能力）之外的第二条标准：服务端代码要在「全量 Node」与「受限边缘」之间保持可移植。

## 6 核心对比表：渲染策略谱系

| 维度 | CSR | SSR | SSG | ISR |
| --- | --- | --- | --- | --- |
| 渲染时机 | 浏览器运行时 | 每次请求在服务器 | 构建时一次 | 构建时 + 按需再生 |
| 首屏 TTFB | 空壳快、内容慢 | 内容随首字节 | 极快（CDN） | 极快（CDN，stale 期间） |
| 内容新鲜度 | 最新 | 最新 | 固定 | 按 `revalidate` 更新 |
| SEO | 差（依赖爬虫执行 JS） | 好 | 好 | 好 |
| 服务器成本 | 低 | 高（每请求渲染） | 零（静态托管） | 低（只按需再生） |
| 典型用途 | 后台管理、重度交互 App | 个性化页面、登录态内容 | 博客、文档、营销页 | 电商、新闻、半动态页 |

## 7 小结

- 渲染策略是「**何时执行同一份代码**」的四种选择：浏览器（CSR）、服务器每请求（SSR）、构建时（SSG）、构建时+按需（ISR）。
- **水合**是 SSR 的成本：同一棵树渲染两遍，交互才可用。
- **流式 SSR** 分块发送 HTML，用 `<Suspense>` 描述「先出哪块」，把 LCP 提前到第一个 chunk。
- **岛屿架构**只水合交互「岛屿」，其余保持静态 HTML，让「零 JS 优先、交互够用」成为可能。
- 选型公式：**内容个性化程度高 → SSR；内容静态为主 → SSG；内容会变但可容忍短暂旧 → ISR**。
- 所有策略都服务同一目标：在《性能优化》的天平上，用最小成本换取「快」与「新」的平衡。
- **边缘渲染**把执行地点推到离用户最近的节点，与「何时执行」的渲染策略正交，共同构成可调矩阵。
- **水合不匹配**是 SSR 的常见雷区：初始渲染避免 `Date.now()`/`Math.random()`/读 `window`，客户端逻辑进 `useEffect`。
- 现代框架默认姿态：**默认静态、按需动态、显式失效**——能提前渲染的绝不运行时渲染。
- 工具生态一句话：Next.js 全家桶（SSR/SSG/ISR/边缘），Astro 走岛屿架构，Remix 强调「按数据边界流式」。
- 决策框架最终可以收成两个问题：**内容多久变一次？用户多久来一次？**——前者定「何时渲染」，后者定「在哪渲染」。
- 记住：静态把成本挪到构建时，SSR 把成本摊到每次请求，边缘把成本推到最近处——没有免费午餐，只有预算转移。
- 至此，渲染层与数据层的策略已对齐：页面级 ISR 对应数据级 stale-while-revalidate，两层叠加是现代全栈的默认姿势。
- 一句话总览：渲染策略 = 「何时执行」×「在哪执行」×「水合多少」的三维选择。
- 实际项目常混合使用：营销页 SSG、详情页 ISR、登录态页 SSR——先分类，再逐个定策。
- 本节与《状态管理》的呼应提醒我们：渲染策略和数据策略必须同一次设计，否则会出现「页面旧、数据新」或反之的割裂。
