## 为什么从状态管理开始

上一节我们看到了框架如何把 state 渲染成 UI。但 state 从哪来、怎么变、谁能改、多个组件之间怎么共享——这些问题的答案，就是**状态管理**。它决定了应用的「真相来源（source of truth）」在哪里，也是大型前端项目从「能跑」走向「能维护」的分水岭。

本节与《现代框架》一脉相承，又为《构建工程化》《SSR》提供数据层的视角：当同一个状态既存在于服务器又存在于客户端时，谁说了算？

## 1 客户端状态：单向数据流的纪律

先看最经典的客户端状态模型——**Flux**（Facebook，2014）与它的现代形态 **Redux**（2015）。Flux 针对的是当时 MVC 大型应用「状态散落、谁都能改、难以追踪」的痛点，其答案是**单向数据流**：

**Action（动作）→ Dispatcher / Reducer → Store（唯一状态树）→ View（视图）→（再次派发 Action）**

- **Action**：一个普通对象，描述「发生了什么」，如 `{ type: "INCREMENT" }`。
- **Reducer**：一个**纯函数**，`(state, action) => newState`。它不改旧状态，而是返回新状态——这让每一步状态变化都可重放、可测试、可时间旅行。
- **Store**：唯一的状态容器，全局单例（对应设计模式里的**单例 Singleton**）。
- **View**：通过 `store.subscribe` 订阅更新（对应**观察者 Observer**），把状态渲染成 UI。

核心约束有三条：**状态只进 Store；改状态只能派发 Action；Reducer 必须是纯函数**。这三条把「状态改了」这件事变得完全可预测——这是对《现代框架》里「UI = f(state)」的彻底贯彻。Redux 的中介角色（dispatcher/action 总线）就是 Osmani 书里的**中介者模式（Mediator）**：组件不直接通信，都经过 store 中转。<span class="marginnote">Redux 的代价是样板代码：一个功能要写 action 类型、action creator、reducer、selector 四件套。社区因此用 Redux Toolkit 收窄 API、用 Zustand 走「直接改一个发布-订阅 store」的轻量路线——但无论 API 多轻，「状态流向单一、变更经过明确入口」这条纪律没变。</span>

Redux 的**不可变性（immutability）**带来一个副产品：因为 reducer 从不改旧状态、只返回新对象，store 的每一次快照都被保留下来。于是 **Redux DevTools 可以「时间旅行」**——回放每一个 action，逐帧观察 UI 如何变化，甚至跳到任意历史点调试。这是纯函数 reducers 的红利：**可预测性（确定性）换来了可调试性**。相比之下，直接原地改状态的库（mutable store）更快但无法回溯，这是一条真实存在的取舍。

## 2 状态就近原则：不是所有状态都该全局化

过度全局化是新手最常见的问题：把一切塞进一个全局 store，结果是任何一次更新都触发大面积订阅、重渲染风暴。现代共识是**状态就近存放（state colocation）**：

- **组件局部状态**（表单输入、展开/收起）：留在组件里，别进全局 store。
- **派生状态**（基于已有状态算出来的）：用 `computed`/`useMemo` 即时算出，不要复制一份存在 store 里——存了副本，就会产生「两个真相」，同步逻辑无穷无尽。
- **跨组件的共享状态**（用户、主题、购物车）：才进全局 store 或 Context。

React 的 `Context + useReducer`、Vue 的 `provide/inject + reactive` 提供了「局部共享」的中间地带，适合中小范围共享；真正的全局状态才动用 Redux/Zustand。判断标准一句话：**这个状态是「这个子树的」还是「整个应用的」？**

全局 store 的另一面是**订阅范围**：store 每次变化都通知所有订阅者。若几十个组件订阅同一个 store，一次微小的更新就会触发一场重渲染风暴——这正是《现代框架》里「组件级更新 vs 细粒度更新」之争在数据层的镜像。Redux 用 **selector + 记忆化（memoization）** 让组件只订阅「自己关心的切片」；Zustand 也要求用 selector 收窄。**选什么样的 store，决定了你能承受多大的重渲染**——这是一条性能与架构的交界线。

## 3 服务端状态：客户端无权拥有真相

进入真实产品，绝大多数状态其实**不属于客户端**：用户资料、订单、评论都存储在服务器数据库里。它们是**服务端状态（server state）**，与客户端状态有本质差异：

- **异步**：只能通过网络异步获取，永远有「加载中/成功/失败」三态。
- **服务器是真相**：客户端只是一份缓存，随时可能过期。
- **其他用户也在改**：你的缓存视图会与服务器不一致。

如果把服务端状态当普通客户端状态塞进 Redux，你会陷入「手动管理 loading、error、缓存、过期、重试」的无底洞。于是有了专门的工具：**TanStack Query（React Query）**、**SWR**。它们的核心抽象是**把「获取」变成声明式缓存**：

1. **缓存与去重**：同一 key 的请求并发时只发一次，结果进缓存。
2. **stale-while-revalidate**：显示旧数据的同时后台刷新，界面不空白。
3. **失效与重取**：增删改成功后在 `queryKey` 上标失效，自动重取相关数据。
4. **乐观更新**：先按预期改 UI，请求失败再回滚。

举一个乐观更新的具体例子：用户点了「点赞」，你**立刻**把按钮置为已赞并 +1，同时后台发请求；请求失败再回滚为原状。这把「等待网络的 300ms 空白」从用户感知里删掉了。乐观更新的代价是**一致性风险**：如果服务器判断权限不足、返回拒绝，你就要处理回滚与提示。这也是为什么「乐观」只适合低风险、可逆的操作——它是《性能优化》里「感知性能」的一次典型实践。

<span class="marginnote">SWR 一词来自 HTTP 缓存语义（RFC 5861），React Query 与它共享这一哲学：<strong>前端持有的服务端数据，本质是一层「带过期策略的缓存」，而不是第二份真相</strong>。这直接呼应《HTTP 演进》里的 `Cache-Control`/`ETag`——缓存语义从协议层一路延伸到了应用层。</span>

## 4 客户端状态与服务端状态的分界：一份决策清单

实践中用一张清单来分界：

- 数据**必须**从网络获取、可能过期、会被别人修改 → **服务端状态**，交给 TanStack Query/SWR。
- 数据是纯客户端临时的（输入框、开关、草稿）→ **客户端状态**，留在组件或轻量 store。
- 数据**同时**存在（如已保存的草稿，本地缓存 + 服务器同步）→ 客户端一份 + 服务端一份，通过「失效重取」对齐，绝不双向手写同步。

这三条把「状态管理」从「选哪个库」变成了「分清哪种真相」。混为一谈时会出现最经典的 bug：本地改了数据 A 却没告诉服务器，另一个页面刷出旧值，「两个真相」打架。

理解「缓存失效」还要回到 HTTP 层的比喻：`Cache-Control: max-age=60` 说「这个资源 60 秒内可以用」，服务端状态管理里的 `staleTime`/`gcTime` 干的是同一件事——**声明这份数据的生命周期**。区别只在于：HTTP 缓存由协议字段驱动，应用层缓存由你的 `queryKey` 和过期配置驱动。把这两层想通，《状态管理》就与《HTTP 演进》连成了一条线。

## 5 核心对比表：客户端 vs 服务端状态

| 维度 | 客户端状态 | 服务端状态 |
| --- | --- | --- |
| 真相归属 | 客户端（组件/store） | 服务器（数据库） |
| 获取方式 | 同步（本地） | 异步（网络，三态） |
| 是否可能过期 | 否 | 是 |
| 管理工具 | Redux/Zustand/Context | TanStack Query/SWR |
| 更新方式 | 派发 action 改 store | 服务端写库 + 缓存失效重取 |
| 对应设计模式 | Singleton/Mediator/Observer | 缓存 + 过期策略（Cache-Control 语义） |

再放一张状态管理工具的对照：

| 工具 | 范式 | 适用场景 |
| --- | --- | --- |
| 组件 state | 局部 | 单组件内临时状态 |
| Context/Provider | 局部共享 | 跨少量组件（主题、会话） |
| Redux | 单向数据流 | 大型复杂全局状态 |
| Zustand | 发布-订阅 | 轻量全局状态 |
| TanStack Query/SWR | 声明式缓存 | 一切服务端数据 |

## 6 小结

- **单向数据流**（Action→Reducer→Store→View）让状态变化可预测、可重放；Store 是**单例**、订阅是**观察者**、分发是**中介者**。
- **状态就近存放**：局部状态留组件，派生状态即时计算，全局状态才进 store。
- **服务端状态不属于客户端**：它是缓存不是真相，交给 TanStack Query/SWR 的**声明式缓存 + 失效重取**。
- 分界清单：**异步可过期 → 服务端状态；纯本地临时 → 客户端状态；两处都有 → 失效重取对齐**。
- 状态管理的本质是**管理真相**：谁是 source of truth，谁就拥有这份数据的生命周期。
- 不可变性 + 纯函数 reducers 带来**时间旅行调试**；原地改状态更快，却失去可回溯性。
- 全局 store 订阅范围决定重渲染成本，**selector + 记忆化**是必备的收窄手段。
- 乐观更新删除「等待网络的空白」，但只适合低风险可逆操作。
- 先分清「哪种真相」，再选工具——库只是真相的容器，不是真相本身。
- 状态管理的成熟标志，是团队能对「这个状态该放哪」给出唯一答案。
- 单向数据流 + 缓存语义（stale-while-revalidate）共同构成现代前端「状态」的两根支柱。
- 学完本节，你已经能把「状态」翻译成三种东西：本地临时值、全局事实、服务器缓存。
- 下一步把这些状态送进浏览器之前，先想想它们如何在构建期被合并、精简、分包。

在下一节，我们把视角从运行时拉到**构建工程化**——打包器如何把成百上千个模块合并成几个文件，Tree Shaking 如何删掉没用的代码，模块联邦又如何让多个应用共享运行时的模块。这条线从《HTTP 演进》的「少请求、小体积」一路延续：构建的一切优化，最终都服务于「让浏览器少下载、快执行」。

> 补充：Flux/Redux 语义以 Redux 官方文档为准；TanStack Query 与 SWR 的缓存/失效语义以各自官方文档为准；设计模式归因参照 Osmani《Learning JavaScript Design Patterns》第 7 章。SWR 的 RFC 5861 出处为 HTTP Cache-Control 的 stale-while-revalidate 扩展。
