## 为什么从 JavaScript 引擎开始

上一节我们看到了渲染进程的主线程：HTML、CSS、JavaScript 都在这里排队执行。但「执行 JavaScript」到底意味着什么？一段 `for` 循环的代码，怎么就被翻译成了 CPU 能跑的机器指令？答案是渲染进程里那颗心脏——**JavaScript 引擎**。Chrome 用的是 Google 自研的 **V8**，Node.js 与 Deno 也用 V8；Firefox 的 SpiderMonkey、Safari 的 JavaScriptCore（Nitro）原理相通。

理解引擎，你就理解了为什么「对象属性访问的顺序」会影响性能、为什么热循环会被编译、为什么内存会像潮水一样被回收。这是从「会写 JS」到「知道 JS 为什么快/慢」的转折点。

## 1 从源码到字节码：解释器的舞台

V8 的执行流水线是一条**多级编译链**，每一级都在「启动快」与「跑得快」之间做取舍：

**源码 → Parser 解析成 AST → Ignition 解释器生成字节码 → 逐条执行字节码 → 收集类型反馈**

- **Parser**：把源码解析成抽象语法树（AST）。V8 的 parser 分「预备解析（pre-parse）」与「完全解析（full parse）」：外层函数先浅扫一遍，函数体内的代码等真正调用时才全量解析，用来省启动时间。
- **代码缓存（code cache）**：V8 会把编译好的字节码存进磁盘缓存，第二次加载同一脚本时跳过重复解析与编译，直接复用。这是浏览器「刷新第二次明显变快」的幕后推手之一，也是 CDN 静态资源能否命中缓存策略的重要考量。
- **Ignition 解释器**：把 AST 编译成**字节码（bytecode）**并直接解释执行。字节码是紧凑的中间表示，比如 `LdaNamedProperty a0, [0]` 这样的指令。解释执行启动快、内存占用低，但速度不如原生机器码。
- **类型反馈（type feedback）**：这是整条链的燃料。每次属性访问、函数调用，Ignition 都会在调用点（call site）记录**实际出现的类型**，供后面的优化编译器使用。<span class="marginnote">「动态类型」之所以能被优化，正是因为引擎在运行时观察到了「这个变量实际总是整数」「这个对象的形状总是同一个」这类规律——优化编译器赌的就是规律会延续。</span>

字节码的出现让「启动快」与「可优化」解耦：不解释执行源码，而是解释执行字节码，同时把类型信息喂给下一级。这就像一个熟手工人，先用手工慢做保证交付，同时记录每道工序的习惯，为后续自动化铺路。

V8 走到今天花了近二十年：2008 年随 Chrome 一同发布时，首版用全量代码生成器（Full-codegen）直接编译到机器码，快但启动慢、内存高；2010 年引入 Crankshaft 做轻量优化；2017 年大重构为「Ignition + TurboFan」架构——解释器与优化编译器彻底分工，并沿用至今；2021 年加 Sparkplug，2023 年加 Maglev。这条演进主线正是本节讲的分层思想的来龙去脉，也解释了为什么「V8 很快」并非一句口号，而是一代代架构取舍的累积。

## 2 JIT 分层编译：Sparkplug 与 TurboFan

如果只有解释器，JavaScript 会慢得无法支撑今日的 Web。于是 V8 引入了**即时编译（Just-In-Time，JIT）**：在运行中把热代码编译成机器码。

现代 V8 的分层如下：

1. **Ignition（解释器）**：所有函数先到这里，快速启动。
2. **Sparkplug（基线编译器，V8 9.4，2021 引入）**：把字节码一次性翻译成机器码。不做优化、不加类型假设，但比解释执行快一个量级，用来垫掉从「解释」到「深度优化」之间的漫长过渡。
3. **TurboFan（优化编译器）**：针对**热点函数**（被反复调用的函数）做深度优化。它利用类型反馈做**推测性编译（speculative optimization）**：假设 `x + y` 里两个变量总是整数，就生成整数加法指令。

**去优化（deoptimization）** 是这套体系里最重要的纠错机制：一旦运行中出现了与假设不符的类型（比如某个参数突然变成了字符串），TurboFan 编译的机器码必须**回退**到解释器/基线版本，从当前状态继续执行。<span class="marginnote">去优化代价高昂，所以工程师的「性能直觉」大多围绕「让类型和对象形状稳定」展开：避免一会儿传整数一会儿传字符串、避免在循环里给对象增减属性——这些都是在保护 TurboFan 的假设不被打破。</span>

这条「先解释、再基线、后深度优化、错了回退」的链，正是 **JIT 分层编译**的全貌。V8 还有 **Maglev（中层优化编译器，V8 11.3，2023）** 夹在 Sparkplug 与 TurboFan 之间，专门优化中等热度的函数，避免直接上重型 TurboFan。

TurboFan 的深度优化里最值钱的一招是**函数内联（inlining）**：把被频繁调用的小函数直接展开进调用方，省去调用开销，并让后续优化（如常数折叠、逃逸分析）有更大的可见范围。它的极限形态是**逃逸分析（escape analysis）**：TurboFan 发现一个临时对象从头到尾没有逃出函数作用域，就直接在寄存器/栈上分配它，甚至完全消除分配——GC 的压力也随之变小。这些优化与《性能优化》一节里「让函数保持小巧、让热路径类型稳定」的建议一一对应。

## 3 隐藏类（Hidden Classes）：让属性访问变成偏移量

JavaScript 的对象是「动态字典」：随时可以增删属性。若每次都拿属性名去做哈希查找，属性访问会慢一个量级。V8 的办法是 **隐藏类（hidden class，内部叫 Map）**：

**同一形状的对象共享同一个隐藏类，属性在对象里的存储偏移量被缓存，访问变成一次「偏移量取数」而非常规哈希查找。**

来看例子。执行：

```javascript
function Point(x, y) { this.x = x; this.y = y; }
const p1 = new Point(1, 2);
```

`p1` 被创建时，V8 会为它建立隐藏类 C0，添加 `x` 后过渡到 C1，添加 `y` 后过渡到 C2。若再 `new Point(3, 4)`，`p2` 会沿着**同一条过渡链**走到 C2——于是 `p1` 与 `p2` 共享隐藏类 C2，两者访问 `x` 的偏移量相同，TurboFan 就能据此生成高效的机器码。<span class="marginnote">反例同样经典：如果两个对象以不同顺序添加属性，或某个对象多删一个属性，它们就会走上不同的隐藏类分支，变成「形状不同」的两个对象——共享、缓存、优化全部失效。这就是「构造对象时尽量让属性顺序一致、别动态增删」这条经验的底层原理。</span>

**内联缓存（Inline Caches，IC）** 与隐藏类配套工作：每个「读属性」的调用点都带一个缓存，记录「上次看到的是哪个隐藏类、属性在哪个偏移量」。同一调用点反复见到同一个隐藏类，就直接命中缓存，跳过隐藏类查找。一旦出现新隐藏类，缓存失效、重新学习——这是 JIT 的「运行时自适应」心脏。

V8 的对象布局让这个体系落地：属性被分成「**对象内属性（in-object properties）**」与「**属性表（properties backing store）**」两层。前几个常用属性直接存在对象体里，随对象指针一次取到；更多的属性落入一个独立数组，隐藏类记录数组的偏移。**频繁访问的属性放在构造顺序最前**，就能保证它们落在 in-object 区域，让 IC 命中后是真正的一次指针访问。

这张「隐藏类 + IC + 分层对象布局」的组合拳，也是 JavaScript 与 C++ 在「类」语义上最根本的差别所在：C++ 的类在编译期就已定死布局，而 JavaScript 的「形状」要到运行期才被观察与固化——这正是《DOM 与事件》一节里框架们费尽心机批量、一致地更新 DOM 节点的底层原因之一。

## 4 垃圾回收（GC）：谁在管理你不再需要的对象

JavaScript 没有手动 `free`，内存由引擎的 **GC（垃圾回收器）** 自动管理。V8 的堆按「代龄」划分，基本原则是：**绝大多数对象活得很短，只有少数能活到「老」。**

- **新生代（Young Generation）**：新分配的对象住在这里，容量小、GC 频繁。V8 用 **Scavenger（半区复制）** 算法：把新生代一分为二，`from-space` 与 `to-space`；GC 时把存活对象复制到 `to-space`，然后交换角色。复制只遍历存活对象，代价正比于存活量而非对象总数，所以新生代 GC 极快。
- **晋升（Promotion）**：对象在一次新生代 GC 中存活（或两次），就被**晋升**到老年代——因为「活得久」往往意味着「还会活更久」。
- **老年代（Old Generation）**：用**标记-清除（Mark-Sweep）/ 标记-整理（Mark-Compact）** 算法。先标记所有可达对象（从 GC 根出发遍历），再清除不可达对象，必要时整理碎片。
- **三色标记 + 增量 + 并发**：现代 V8 用三色标记（白=未访问、灰=待处理、黑=已处理）做**增量标记**，把大停顿拆碎，还引入写屏障与并发标记/清除，让 GC 尽量与主线程并行，减少「全局暂停（stop-the-world）」的卡顿。

<span class="marginnote">GC 对前端的实际影响是「内存越规整、停顿越少」。创建大量短期对象（如每次渲染都 `new Array`）会让新生代 GC 频繁运行；持有不再需要的闭包引用、忘记解绑事件监听器，则会把对象「留」在老年代，慢慢堆出内存泄漏——这正是 Node 端 `--trace-gc`、Chrome DevTools Memory 面板存在的原因。</span>

GC 还催生了一个语言级技巧：**弱引用（WeakRef）与 `FinalizationRegistry`**。普通引用会「拽住」对象不让它被回收，而弱引用允许对象在无人使用时被回收。前端用它实现缓存、按需销毁订阅时，要格外小心：不能假设弱引用对象「还在」，每次使用都要判空。这与《跨端技术》一节里小程序容器的内存治理、以及第三级《操作系统》讲的内存管理是同一套思维——只是在这里，管理者换成了引擎。

## 5 核心对比表：V8 各层编译器

| 层级 | 产物 | 优化强度 | 典型用途 |
| --- | --- | --- | --- |
| Ignition | 字节码 | 无（解释执行） | 所有函数首次执行，快启动 |
| Sparkplug | 机器码（无假设） | 低 | 垫平解释到优化的过渡 |
| Maglev | 机器码（轻优化） | 中 | 中等热度的函数 |
| TurboFan | 高度优化机器码 | 高（推测性） | 热点函数，赌类型假设 |

再放一张隐藏类相关的行为对照表：

| 行为 | 对隐藏类/缓存的影响 | 后果 |
| --- | --- | --- |
| 按一致顺序构造对象 | 共享同一过渡链 | 属性访问被缓存为偏移量，快 |
| 增删属性、乱序添加 | 产生新分支 | 缓存失效，触发去优化，慢 |
| 参数类型保持稳定 | 类型反馈稳定 | TurboFan 放心优化 |
| 参数类型漂移 | 假设被打破 | 去优化回退，代价高 |

## 6 小结

- V8 的执行链是 **Parser → Ignition 字节码 → Sparkplug 基线 → Maglev/TurboFan 优化**，靠运行时类型反馈驱动。
- **推测性编译**让动态语言逼近静态速度，代价是假设被打破时的**去优化**。
- **隐藏类（Map）+ 内联缓存（IC）** 把属性访问从哈希查找变成偏移量访问；对象形状一致是性能前提。
- **GC 分代**：新生代用半区复制、晋升老年代，老年代用标记-清除/整理，靠增量与并发标记减少停顿。
- 对前端而言，**类型稳定 + 形状稳定 + 少造短期对象**就是给引擎的三份「友好信号」。
- 引擎的分层、优化与回收都不是玄学，而是可观测的：DevTools Performance、`--trace-gc`、`--trace-ic` 都是照进 V8 内部的手电筒。
- 同一套 JIT/GC 思维适用于所有现代引擎（SpiderMonkey 的 Baseline/Warp、JavaScriptCore 的 FTL），V8 只是最常用的样板。
- 引擎既是性能瓶颈，也是性能杠杆：能读懂 V8 的人，写出的代码天然更「快」。
- 记住一句话：引擎不是魔法，而是「解释、观察、编译、回收」四件事的工程化。
