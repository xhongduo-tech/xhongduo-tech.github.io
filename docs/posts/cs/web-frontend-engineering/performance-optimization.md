## 为什么从性能优化开始

前面七节我们拆开了浏览器的每个零件。现在把它们装回去，面对一个总问题：**这个页面，到底快不快？** 「快」不能靠感觉，要有**指标**。性能优化这门手艺的成熟，就体现在它把「感觉流畅」翻译成了几个可以测量、可以设预算、可以进 CI 的数字——**Core Web Vitals**。

本节站在整个专题的顶点：它复用《浏览器架构》的渲染管线、《HTTP 演进》的网络层、《构建工程化》的产物策略，把它们汇成一条可执行的优化路线。

## 1 指标：先定义「快」

**Core Web Vitals** 是谷歌定义的三个「关乎用户体验核心」的指标，各有**良好（good）**阈值：

- **LCP（最大内容绘制，Largest Contentful Paint）**：首屏「最大可见元素」（图片、标题块）出现的时刻，衡量**加载**体验。良好：≤ 2.5 秒。
- **INP（交互到下一次绘制，Interaction to Next Paint）**：从用户点击/按键到界面响应的最差延迟，衡量**交互**体验，2024 年起取代 FID（首次输入延迟）。良好：≤ 200 毫秒。
- **CLS（累积布局偏移，Cumulative Layout Shift）**：加载过程中「元素意外移动」的总量，衡量**视觉稳定**。良好：≤ 0.1。

再补两个辅助指标：**FCP（首次内容绘制）** 记录第一块内容出现的时间；**TTFB（首字节时间）** 记录服务器响应到第一个字节的时间。三者串起来，正好对应一条加载链路：**网络 → 渲染 → 交互**。<span class="marginnote">为什么是这三个？因为它们分别回答了用户最在意的三件事：「页面多久能用」「点下去响应多快」「有没有突然乱跳」。谷歌做过海量实证：这三个指标与转化率、跳出率显著相关——它们不是工程师的自嗨，而是商业指标的技术代理。</span>

指标必须在**真实环境**测量，因为实验室（Lighthouse 在模拟机上跑）测不出真实网络与设备分布。**RUM（真实用户监控，Real User Monitoring）** 从线上用户浏览器采集，才代表真实体验；Lighthouse 适合回归测试与找瓶颈。两者互补：**实验室定位问题，RUM 衡量效果**。

有指标就能设**性能预算（performance budget）**：给体积、请求数、LCP、CLS 定上限，写进 CI——每次构建超预算就报警，防止「这周加的功能把首屏拖慢了」悄悄上线。预算的粒度可以是「初始 JS ≤ 200KB」「LCP ≤ 2.5s」「CLS ≤ 0.1」。**性能退化从此被挡在合并之前**，这是 Web 团队从「事后救火」转向「事前防病」的机制保障。

## 2 加载瀑布：从 TTFB 到 LCP

**加载瀑布（loading waterfall）** 把一次页面加载画成时间线，逐段标注每个阶段耗时：

**TTFB → 解析 HTML → 发现资源 → 并行下载 → FCP → LCP**

每一段都对应前面几节的机制：

- **TTFB 长**：网络层问题。可能是 DNS、TCP/TLS 握手、服务器慢、无 CDN。对策是 CDN 就近、HTTP/2/3、服务器端优化。
- **解析被阻塞**：渲染层问题。阻塞脚本拖慢解析（见《浏览器架构》关键渲染路径）。对策是 `defer`/`async`、把脚本移到 `body` 尾部。
- **关键资源下载慢**：体积与请求数问题（见《构建工程化》）。对策是代码分割、Tree Shaking、压缩。
- **LCP 晚**：最大元素本身出现得晚。对策是让 LCP 元素更早渲染、图片更早加载、避免被 JS 推迟。

**LCP 尤其值得单列**：它往往被一张大图或一个被 JS 延迟渲染的块拖住。对策是 `preload` 关键图片、为 LCP 元素预留尺寸（也顺带护住 CLS）、用响应式图片只下载需要的尺寸。一句口诀：**首屏只让「必要的」东西先到，其余全部让路**。

实验室指标里还有一个与 INP 相关的聚合量：**TBT（总阻塞时间，Total Blocking Time）**——LCP 之后、页面可交互之前，所有长任务超过 50ms 部分的累加。它是 Lighthouse 在**合成环境**下对「交互卡顿」的近似度量：真实 INP 由 RUM 采集，TBT 则是没有真实用户的实验室替代品。这套「实验室用近似量、线上用真实量」的双轨制，贯穿了 Web Vitals 的整个方法论。

## 3 公式解析：60fps 的帧预算

交互流畅的底线是「屏幕每 16.67ms 刷新一帧」。这个数字来自一条简单公式：

$$
\text{帧预算（frame budget）} = \frac{1000\text{ms}}{帧率} = \frac{1000}{60} \approx 16.67\text{ms}
$$

- **分子 1000ms**：一秒的时间。
- **分母 60fps**：主流屏幕的刷新率（120Hz 屏则分母是 120，预算只有 8.3ms）。
- **16.67ms**：**一帧的全部时间预算**——脚本、样式、布局、绘制、合成、光栅化都要塞进这 16.67ms，超了就掉帧。

拆三步理解：

- **第一步**：16.67ms 不是「给 JS 的」，而是给**整条渲染管线**的。经验法则是 JS 工作占其中约 10ms，剩下留给布局、绘制与合成。
- **第二步**：一段 50ms 的长任务会吃掉三帧的预算。所以「把长任务拆成 ≤ 50ms 的短任务」（见《DOM 与事件》）就是「给渲染让出帧」的直接手段。
- **第三步**：60fps 的另一面是**渲染预算（rendering budget）**——像财务预算一样，给每帧的每类工作设上限，超了就报警。Lighthouse 的「Long tasks」、DevTools 的帧统计就是这台「会计」。

DevTools Performance 面板把帧预算画成可视的时间线：每一帧是一条水平条，绿色是脚本、紫色是样式/布局、黄色是绘制，超过 16.67ms 的帧会被标红。**读帧时间线是性能调优的显微镜**：你一眼能看出「是脚本太长，还是布局太贵，还是绘制太重」，然后对症下药——这正是《浏览器架构》渲染管线的实战回归。

<span class="marginnote">为什么用 60fps 而非「越快越好」？因为 16.67ms 是感知的临界点：超过它用户能察觉卡顿，低于它用户感觉不到更快。优化到「每帧 10ms JS」和「每帧 3ms JS」在体验上几乎无差，但前者多花的时间可能用在别处更值——<strong>性能优化是预算管理，不是无限压榨</strong>。</span>

## 4 资源提示：让网络先人一步

HTML 里有一族「资源提示」，让浏览器提前知道「马上要用什么」：

- **`<link rel="preload">`**：立刻以最高优先级下载，用于首屏关键资源（LCP 图片、字体）。它是「主动声明」，比《HTTP 演进》里被禁用的 HTTP/2 服务器推送更可控。
- **`<link rel="preconnect">`**：提前建立与目标源的连接（DNS + TCP + TLS），省下关键请求前的握手时间。
- **`<link rel="dns-prefetch">`**：只提前解析 DNS，比 preconnect 更轻，用于「可能用但不确定」的源。
- **`<link rel="prefetch">`**：空闲时下载**下一跳**页面需要的资源，用于导航预感（如 hover 到链接时）。

原则是**克制**：preload 太多反而挤占首屏带宽。优先给 LCP 资源 preload，给第三方源 preconnect，给下一跳 prefetch——这是「把有限的预取预算花在最值的地方」。

图片优化单独成章：用 `srcset`/`sizes` 按视口下发不同尺寸，用 AVIF/WebP 减体积，用 `loading="lazy"` 让视口外图片延迟加载，并**给图片写死 `width`/`height`**——这是 CLS 的护城河，浏览器据此预留占位，不再在图片加载完成时把布局「顶一下」。

字体是 CLS 的第二大来源：`font-display: swap` 允许先渲染回退字体、字体就绪后再替换，避免「空白闪烁（FOIT）」，但替换瞬间可能引起小幅布局偏移。更稳的做法是 `size-adjust` 等字体度量对齐技术（Google Fonts 的 API 已内建），让替换前后布局几乎不跳。**性能优化的很多功夫，就花在「视觉上无感」这五个字上。**

## 5 核心对比表：Core Web Vitals 一览

| 指标 | 衡量的体验 | 良好阈值 | 常见瓶颈 | 首要对策 |
| --- | --- | --- | --- | --- |
| LCP | 加载 | ≤ 2.5s | 大图、阻塞 JS | preload LCP 图、分割代码 |
| INP | 交互 | ≤ 200ms | 长任务、大重渲染 | 拆长任务、减少重渲染 |
| CLS | 视觉稳定 | ≤ 0.1 | 无尺寸图片、字体切换 | 预留尺寸、`font-display` |
| FCP | 首次内容 | ≤ 1.8s | 阻塞渲染资源 | 内联关键 CSS、`defer` JS |
| TTFB | 网络往返 | ≤ 0.8s | 无 CDN、服务器慢 | CDN、HTTP/3、缓存 |

## 6 小结

- **指标先行**：LCP 管加载、INP 管交互、CLS 管稳定；实验室测瓶颈，RUM 测真实。
- **加载瀑布** = TTFB → 解析 → 下载 → FCP → LCP，每段都有对应的网络/渲染/构建对策。
- **帧预算 = 1000 / 60 ≈ 16.67ms**，是渲染预算与长任务拆分的数学根基。
- **资源提示**（preload/preconnect/prefetch）与图片优化（srcset/AVIF/懒加载/预留尺寸）是下载与稳定性的两手。
- 性能优化是**预算管理**：不是无限压榨，而是把有限预算花在最值的地方。
- 它把前七节的机制全部收拢成一条可度量、可设预算、可进 CI 的工程红线。
- 优化的终点不是「分更高」，而是「真实用户变快」——所以 RUM 数据才是最终裁判。
- 一条经验总结：**先测，再改，改完再测**；没有数据的优化都是玄学。
- 资源提示克制使用：LCP 图 preload、第三方 preconnect、下一跳 prefetch。
- `font-display: swap` 防 FOIT，`size-adjust` 对齐字体度量，是 CLS 的第二道防线。
- 性能预算 + CI 拦截，让「性能退化」在合并前就被挡下。
- 本专题第一篇的「渲染管线」到这一节完成闭环：机制解释一切，指标量化一切。
- 帧预算公式（1000/60 ≈ 16.67ms）值得背下来——它是所有渲染优化的换算单位。
- 记住顺序：网络（TTFB）→ 解析（FCP）→ 下载（LCP）→ 交互（INP）→ 稳定（CLS）。

在下一节，我们开始回答「渲染策略」的谱系问题——**SSR/SSG/ISR**：同样一份 React/Vue 代码，为什么有的在服务器渲染、有的构建时生成、有的按需更新？流式 SSR 与岛屿架构又是如何补上各自短板的。性能这架天平的两端——「首屏多快」与「动态多新」——将首次被放在同一张表上权衡。

> 补充：Core Web Vitals 阈值（LCP 2.5s、INP 200ms、CLS 0.1、FCP 1.8s、TTFB 0.8s）以 web.dev 官方文档为准；INP 于 2024 年 3 月正式取代 FID，为官方确认事实。帧预算与长任务定义（50ms）同样以 web.dev 的 Web Performance 指南为准。`srcset`、`loading="lazy"`、`font-display` 等属性语义均以 HTML/CSS 规范为准。
