## 为什么从幻影问题开始

第 13 章的幻读（phantom）在这一节得到「锁语义」的严格处理：**只锁已存在的行，防不住「新插入的行」**——这就是**幻影现象（phantom phenomenon）**。为什么行锁防不住幻影？因为要防幻影，锁的不是「行」，而是「满足某谓词的行**集合**」——这引出了**谓词锁（predicate lock）**与更可行的**索引锁（index lock）**方案。这一节是锁协议的「最后一课」，也是理解 MySQL 间隙锁（gap lock）与可串行化实现的钥匙。

## 1 幻影现象的本质

**幻影（phantom）**：事务 $T$ 执行 $T$，第一次返回 5 行；并发事务插入一行 $T$ 并提交；$T$ 重查同条件返回 6 行——**多出的行就是幻影**。

**为什么行锁防不住**：$T$ 只锁了「已存在的 5 行」。新插入的行**从未被锁过**——它在 $T$ 的锁集之外诞生。

**核心要点：幻影是「数据集合」层面的冲突，不是「单行」层面的冲突。** 行锁管的是「具体行」，幻影涉及「整个谓词范围」——需要锁「范围」而非「行」。

## 2 谓词锁

**谓词锁（predicate lock）**：锁「满足某个谓词的所有行」的逻辑集合——包括当前存在的、以及**未来将插入的**。

**优点**：精确——锁住整个查询谓词，插入满足谓词的行会被阻塞。

**缺点**：**开销巨大**。谓词锁的数量随谓词复杂度增长，锁管理器要维护谓词索引、做蕴含判断（新插入行是否命中某谓词锁）——**实现复杂且昂贵**。纯谓词锁在真实系统几乎不可行。

**辨析｜易错点：** 谓词锁「锁集合」的理想是完美的，但工程代价太高——数据库用一个**近似**：**索引锁（index lock）**。它锁的不是任意谓词，而是**索引键值范围**。

## 3 索引锁：用键值范围近似谓词

**索引锁（index lock）**：当查询的谓词对应索引的范围（如 \`WHERE salary > 50000\` 命中 **salary** 索引），就对**索引键的范围**加锁——不仅锁现有键，还锁**键之间的间隙（gap）**。

**间隙锁（gap lock）**：锁住「两个相邻键值之间的空隙」——**阻止向该间隙插入新键**。

**核心要点：间隙锁让「未来插入」也无处可逃。** 事务对 **\`WHERE salary > 50000\`** 加范围锁时，锁住索引中该范围的键**及间隙**——并发事务想插入 **\`salary = 75000\` 的新行**（落在锁定的间隙）会被阻塞。幻影被从「出生地」堵死。<span class="marginnote">MySQL InnoDB 的可重复读就是靠 <strong>next-key lock（键 + 间隙）</strong>实现「防幻读」的：它锁的不只是行，还有行之间的间隙——这让 RR 级别在 InnoDB 下达到近似可串行化的防幻读效果。</span>

**公式解析：索引锁的覆盖**

设查询范围 $R = [low, high]$，索引键序列 $\dots < k_i < k_{i+1} < \dots$：

$$
\text{锁住} = \{ k \mid k \in R \} \;\cup\; \{ (k_i, k_{i+1}) \mid \text{间隙与 } R \text{ 相交} \}
$$

- **第一步，锁现有键**：$R$ 内的所有索引键（阻止更新/删除）。
- **第二步，锁间隙**：$R$ 覆盖到的相邻键之间的空档（阻止插入）。
- **第三步，效果**：任何「满足 $R$ 的新行」都落在被锁键或其间隙——插入被阻塞。
- **第四步，条件**：**前提是谓词命中索引**。若查询条件无索引可用（全表扫），索引锁无从谈起——数据库退化为表锁或更高成本方案。

## 4 索引锁与可串行化

**可串行化的锁实现** = **2PL + 索引锁（含间隙）**：

- 所有读/写按 2PL 加锁。
- 范围查询对索引范围加锁（含间隙）。
- 结果：新插入无法进入被锁范围——幻影被防住，调度可串行化。

**对比快照隔离**：

| 维度 | 2PL + 索引锁 | 快照隔离 |
| --- | --- | --- |
| 防幻读 | ✅（间隙锁） | ✅（快照固定行集） |
| 防写偏斜 | ✅（范围锁） | ❌（需 SSI） |
| 读写互斥 | 有 | 无 |
| 死锁 | 有 | 无 |
| 代表 | MySQL InnoDB（RR 用 next-key） | PostgreSQL（MVCC） |

**核心要点：锁与 MVCC 都能防幻影，但路径不同。** 锁靠「间隙锁堵住未来插入」，MVCC 靠「快照固定过去行集」——**一个防「将来」，一个防「变化」**。各自的弱点（死锁 vs 写偏斜）也因此不同。

## 5 幻影场景速查与索引锁的数值算例

**用一个具体的并发场景，把幻影和索引锁完整走一遍。** 设 `salary` 上有 B+ 树索引，事务 T1 执行 `SELECT * FROM emp WHERE salary > 50000`，事务 T2 要插入 `salary=75000` 的新员工。

- **T1 加锁**：在 2PL + 索引锁下，T1 对 salary 索引中「> 50000」的键及间隙加锁——含键 52000、70000 及它们之间的空档。
- **T2 尝试插入**：新键 75000 落在 T1 锁住的键值范围（70000 之后的下一个间隙）——T2 被阻塞。
- **T2 提交前**：T1 重查同条件，结果集不变（无幻影）——间隙锁把「未来插入」堵死在出生地。
- **T1 提交后**：T2 继续执行，插入成功——间隙锁只在 T1 存活期生效。

**数值算例：无索引时的退化** 若 `salary` 没有索引，T1 的范围谓词无法映射到键值区间：

- 索引锁无从谈起——数据库只能退化为**表锁**（锁整张 emp 表），并发度骤降。
- 或者用谓词锁的简化实现（代价高）。
- 现实教训：**范围查询的谓词尽量命中索引**——不仅查询快，连并发控制也受益。这是「索引设计」同时服务「查询性能」与「隔离性」的双重理由。

**辨析｜易错点：** 间隙锁不能只锁「现有行之间的间隙」，还要锁**边界外的开放区间**（如 `salary > 100000` 的下方无界间隙）。漏锁边界，幻影仍可能从「范围末尾」钻进来——MySQL 的 next-key lock 正是把键与间隙一起锁住来覆盖边界。

<span class="marginnote">间隙锁的代价是「<strong>范围被扩大锁定</strong>」：T1 只想读 `> 50000`，间隙锁却把 `70000` 之后尚未存在的区间也占住——插入性并发请求被无辜阻塞。这是「防幻影」与「并发度」的经典冲突，也是为什么 MVCC（快照隔离）会成为 PostgreSQL 默认的原因之一。</span>

### 术语速查

| 术语 | 含义 |
| --- | --- |
| 幻影 | 并发插入使同条件查询结果变多 |
| 谓词锁 | 锁满足谓词的行集合（含未来行） |
| 索引锁 | 锁索引键值范围近似谓词 |
| 间隙锁 | 锁两个相邻键之间的空档 |
| next-key lock | 键 + 间隙一起锁（InnoDB RR） |
| 表锁 | 无索引时退化的整表锁定 |

## 6 小结

- **幻影** = 数据集合级冲突：行锁锁不住「未来插入的行」。
- **谓词锁**锁整个谓词集合，理想但开销巨大，工程不可行。
- **索引锁**用键值范围近似谓词，**间隙锁**堵住插入——工程方案。
- 索引锁**前提是命中索引**；无索引时退化为表锁。
- 可串行化 = **2PL + 索引锁**；MVCC 用快照固定行集防幻影——两种路径，各有取舍。
- 间隙锁覆盖边界外开放区间，漏锁边界则幻影仍会钻进来。
- 范围谓词尽量命中索引：无索引时退化为表锁，并发度骤降。
