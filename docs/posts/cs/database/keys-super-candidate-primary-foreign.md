## 为什么从码开始

上一节确立了模式与实例之分。但实例是**元组的集合**——集合不区分重复，可现实里的「两个同名同姓的教师」怎么办？数据库必须有一套机制，让系统**在任何时刻都能唯一指认某一行**，并且让**不同表之间的行彼此能对上号**。这套机制就是**码（key）**。

码是关系模型的「身份系统」。它同时服务两个目的：对内，**唯一标识**一个元组；对外，**关联**两个关系。前者衍生出超码、候选码、主码，后者衍生出外码与引用完整性约束。<span class="marginnote">码的思想在数据库之外无处不在：身份证号、学号、快递单号、Git 的 commit hash……凡是要在现实世界里「唯一指认一个东西」的场合，都在用一个「超码」。</span> 它也与第一级逻辑学里的**同一律**「A 是 A」呼应——没有身份，任何关于「哪个对象」的断言都无法书写。

## 1 超码：够用即可的唯一标识

**超码（superkey）**：关系模式 $R$ 的一个属性集合 $K$，若满足——在同一实例中**不存在两个不同元组在 $K$ 的所有属性上取值完全相同**——则 $K$ 是 $R$ 的一个超码。

直觉上，超码是「一组足以区分所有行的属性」。比如 instructor 关系：

$\{ID\}$ 是超码（工号唯一）。
$\{name\}$ 不是超码（可能有重名）。
$\{name, dept\_name\}$ 可能是、也可能不是超码（取决于现实里「同系同名」是否存在）。
**全体属性 $\{ID, name, dept\_name, salary\}$ 一定是超码**：把全部列拼起来，两个不同元组必然在某处不同。

注意「超码」只要求**唯一区分**，不要求**精简**——往超码里塞再多属性，它仍是超码。判断超码不是纯粹的逻辑问题，而要依赖现实世界的约束（「工号必然唯一」是应用层承诺，不是数学定理）。

## 2 候选码：最精简的超码

超码可以很大、很冗余。我们真正关心的是**最小的超码**。

**候选码（candidate key）**：若 $K$ 是超码，且 $K$ 的**任何真子集都不再是超码**，则 $K$ 是候选码。候选码也叫**最小超码（minimal superkey）**。<span class="marginnote">「最小」指属性个数意义上的极小：去掉任何一个属性都会破坏唯一性。注意「极小」不等于「唯一」——一个关系可以有多个候选码，比如学生表里 $\{学号\}$ 与 $\{身份证号\}$ 都是候选码。</span>

以 $\{ID\}$ 为例，若 $\{ID\}$ 唯一，则它是候选码；而 $\{ID, name\}$ 是超码但**不是候选码**，因为去掉 $\{ID, name\}$ 后 $\{ID\}$ 仍是超码。**所有超码都包含至少一个候选码**——这条性质是后续函数依赖理论（第8章）的出发点之一。

「逐子集排除」的过程值得走一遍。假设现实约束是「工号唯一、姓名可重」，逐个判断：

| 属性集合 | 唯一吗 | 是最小超码吗 |
| --- | --- | --- |
| $\{ID\}$ | 是 | 是 → 候选码 |
| $\{name\}$ | 否（有重名） | 否 |
| $\{ID, name\}$ | 是 | 否（$\{ID\}$ 已唯一） |
| $\{name, dept\_name\}$ | 未知，取决于现实 | 需检查真子集 $\{name\}$、$\{dept\_name\}$ 后才知道 |

关键在最后一行：即便 $\{name, dept\_name\}$ 碰巧唯一，也要确认它的两个真子集都不唯一，才能晋级为候选码。**候选码的判定永远依赖现实约束，而现实约束要靠对业务的理解去发现，数据库不会替你猜到。**

**辨析｜易错点：** 候选码强调的是「不可再删」。$\{name, dept\_name\}$ 若恰好唯一，还要检查它的真子集 $\{name\}$、$\{dept\_name\}$ 是否也唯一——只有两者都不唯一时，它才是候选码。考试与面试最爱考这个「逐子集排除」的过程。

## 3 主码与备用码

多个候选码中，由设计者**选定一个**作为主码。

**主码（primary key）**：被选中的、用于唯一标识元组的候选码。其余的候选码称为**备用码（alternate key）**。主码在模式图中用**下划线**标注：

$$instructor(\underline{ID},\ name,\ dept\_name,\ salary)$$

**重点：主码的选取是设计决策，不是数学推导。** 稳定（工号比姓名稳）、精简（列越少越好）、非空（下一节的码设计原则）是选主码的常见标准。为什么必须指定一个「正主」？因为外码引用需要**唯一的、稳定的锚点**——系统不可能去引用「某个候选码」，只能引用「被大家约定好的那个」。

选主码的几条实用标准：

- **稳定性**：值一旦确定就不再改。姓名、手机号都可能变，工号几乎不变——所以「自然标识」里优先选不变的。
- **精简性**：列越少越好。复合主码（多列拼成）会增加外码的列数，让引用与索引都变重。
- **简洁性**：与业务无关的**代理码（surrogate key）**（如自增整数、UUID）常优于自然码——它不随业务波动而变，是工程上的常见选择。

这些标准不是定理，而是权衡。数据库不强迫你用工号还是自增 ID，但它会确保：**你指定的主码，系统就严格保证其唯一且非空。**

## 4 外码与引用完整性

数据库不是一张孤立的表。instructor 里的 dept_name 指向 department 里的 dept_name——这种「指向另一张表的主码」的列，就是**外码（foreign key）**。

**外码（foreign key）**：设关系模式 $R_1$ 中的属性集合 $\alpha$，其值域与关系模式 $R_2$ 的主码 $K$ 相匹配，则 $\alpha$ 是 $R_1$ 的**引用 $R_2$ 的外码**。这里 $R_1$ 叫**引用关系（referencing relation）**，$R_2$ 叫**被引用关系（referenced relation）**。

```sql
CREATE TABLE instructor (
    ID        varchar(5),
    name      varchar(20) NOT NULL,
    dept_name varchar(20),
    PRIMARY KEY (ID),
    FOREIGN KEY (dept_name) REFERENCES department
);
```

外码带来一条硬约束——**引用完整性约束（referential integrity constraint）**：instructor 中任何元组的 dept_name 取值，**要么是 NULL，要么必须真实出现在 department 里**。系统禁止「挂靠一个不存在的系」。这条约束保证了两张表之间的引用永远「指得着」，不会出现悬空的指向。

## 5 公式解析：超码的形式定义

超码的定义可以用一条带量词的公式精确写出。设 $K$ 是 $R$ 的一个属性集合，$t[K]$ 表示元组 $t$ 在 $K$ 上各属性取值的「投影」（见上一节 $t[A_i]$ 的推广），则「$K$ 是超码」等价于：

$$\forall\, t_1, t_2 \in r:\quad t_1 \neq t_2 \;\Longrightarrow\; t_1[K] \neq t_2[K]$$

逐步拆解：

- **第一步，认识 $\forall$**：这个断言对所有元组对 $(t_1, t_2)$ 成立，没有例外。「唯一」从来都是全称判断。
- **第二步，认识 $t[K]$**：它把「元组在若干属性上的取值」打包成一个整体。$t_1[K] \neq t_2[K]$ 的意思是：这两个元组在 $K$ 的**至少一个属性上**取值不同。
- **第三步，认识 $\Longrightarrow$**：整句读作「只要 $t_1 \ne t_2$，就必有 $t_1[K] \ne t_2[K]$」。它等价于反过来说：**若 $t_1[K] = t_2[K]$，则 $t_1 = t_2$**（同一值只能对应同一行）——这正是「由码的值能唯一确定一行」的严格表述。

有了这条定义，候选码就能用一句话收束：**候选码 = 超码 − 冗余**，即满足上面公式、且任何真子集都不再满足的属性集合。

## 6 易错辨析：码的四层坑

- **超码与候选码混淆**：超码允许冗余，候选码要求最简。$\{ID, name\}$ 是超码，却不是候选码。
- **主码的「主」字无数学含义**：主码只是候选码里的一个「指定代表」；备用码在唯一性上与主码完全等价。
- **外码不要求同名**：instructor 的 dept_name 指向 department 的 dept_name 只是恰好同名。外码「值域匹配」即可，名字是设计者的自由。
- **外码值可以为 NULL**：引用完整性允许外码为空——「这名教师还没分配系」是合法状态；但主码**不允许**为 NULL，否则「唯一指认」就失效了。<span class="marginnote">主码非空（NOT NULL）是关系模型与 SQL 的默认约定；而「空」的三值逻辑要到第3章《空值与三值逻辑》才系统展开——这里先记住「主码非空、外码可空」这个不对称。</span>

## 7 小结

- **超码（superkey）**：能唯一区分所有元组的属性集合；允许冗余，全体属性必是超码。
- **候选码（candidate key）**：超码中「去掉任一属性即失去唯一性」的最小超码；一个关系可有多个。
- **主码（primary key）**：被选定的候选码，模式图中下划线标注，不允许为 NULL。
- **外码（foreign key）**：引用另一关系主码的属性集合，由**引用完整性约束**保证指向有效。
- 码的形式定义：$\forall t_1 \ne t_2:\ t_1[K] \ne t_2[K]$；候选码 = 满足该式的最简属性集。
