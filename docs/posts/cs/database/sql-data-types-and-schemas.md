## 为什么从数据类型与模式开始

前面几节我们写表、写查询，默认数据不是字符串就是整数。但真实数据远不止这两种：工资要精确到分、时间要精确到秒、论文全文可能有几十 MB、两个值之间的差值需要单独表达。**数据类型（data type）决定了一个值能存什么、占多大、怎么比较**——选错类型，轻则浪费空间，重则精度丢失、比较出错。

同时还有一个被忽略的问题：一个大学数据库里有几百张表、几十个用户，大家都叫 `student` 怎么办？**模式（schema）与目录（catalog）** 就是数据库用来组织这些名字的「命名空间」，它和第 2 章讲的「关系模式」不同——那是表的结构，这里是**名字的归属与隔离**。这一节把类型与命名空间两条线讲清楚，它们共同回答「数据怎么存、名字怎么管」。

## 1 内置类型：字符串、数值、日期时间

SQL 提供一整套内置数据类型，最常用的分三类：

**字符串类型**

- `CHAR(n)`：**定长**字符串，固定占 $n$ 个字符，不足部分以空格补齐。
- `VARCHAR(n)`：**变长**字符串，最多 $n$ 个字符，按实际长度存储。
- `TEXT` 之类：标准外的长文本类型，各数据库方言不一。

**数值类型**

| 类型 | 含义 |
| --- | --- |
| `INT` / `SMALLINT` / `BIGINT` | 整数，范围依次增大 |
| `NUMERIC(p, d)` | 定点数：共 $p$ 位有效数字，其中 $d$ 位在小数点后 |
| `REAL` / `DOUBLE PRECISION` | 浮点数，精度为机器相关 |
| `FLOAT(n)` | 浮点数，至少 $n$ 位有效数字 |

**日期时间类型**

- `DATE`：日历日期，如 `'2005-07-27'`。
- `TIME(p)`：时刻，如 `'09:00:30'`，`TIME(2)` 表示带两位小数秒 `'09:00:30.75'`。
- `TIMESTAMP(p)`：日期 + 时刻，如 `'2005-07-27 09:00:30.75'`。
- `INTERVAL`：两个日期/时刻之差，如 `INTERVAL '1' DAY`。

日期时间类型的字面量写法很严格：`DATE '2005-07-27'`、`TIME '09:00:30'`，用单引号包裹，顺序固定。<span class="marginnote">日期时间的字符串格式在不同数据库之间并不完全统一（如 MySQL 的 `'2005-07-27'` 可直接当日期用），但标准要求显式加类型前缀。数据迁移时「日期字符串格式不一致」是最常见的坑之一。</span>

## 2 定长与变长：CHAR 与 VARCHAR 的隐蔽陷阱

`CHAR(5)` 存 `'Amy'`，实际存储是 `'Amy  '`（补两个空格）；`VARCHAR(5)` 存 `'Amy'` 就是 `'Amy'`。差别不止在空间，更在**比较与拼接**：

- **比较**：SQL 标准规定 `CHAR` 与 `VARCHAR` 比较时，系统会为 `CHAR` 补空格到等长再比，所以 `'Amy'`（CHAR(5)）与 `'Amy'`（VARCHAR(5)）通常相等——但不同数据库实现细节不同。
- **拼接**：`'Amy' || 'Li'` 在定长下可能带出中间空格，结果变成 `'Amy  Li'`，与直觉不符。

**辨析｜易错点：** 存**长度固定**的标识（学号、身份证号、课程号）用 `CHAR`，存**长度可变**的文本（姓名、地址、简介）用 `VARCHAR`。反过来用会出问题：姓名用 `CHAR(10)`，查询结果里每行都拖着尾随空格，`WHERE name = '张伟'` 都可能对不上。<span class="marginnote">业界普遍经验：几乎总是优先 `VARCHAR`，因为定长补空格带来的比较与拼接麻烦，往往超过它省下的那点存储——现代数据库大多按实际内容压缩或对齐，CHAR 的「定长优势」已被弱化。</span>

## 3 默认值、大对象与用户自定义类型

### 默认值

建表时可给列指定默认值，插入时缺省则自动填充：

```sql
CREATE TABLE student (
    ID       CHAR(5) PRIMARY KEY,
    tot_cred INT DEFAULT 0,             -- 数值默认
    enr_date DATE DEFAULT CURRENT_DATE  -- 当前日期默认
);
```

`DEFAULT` 是声明式的：规则在数据库侧，应用代码可以不关心「没填怎么办」。

### 大对象：BLOB 与 CLOB

文档、图片、音视频这类巨型数据，用**大对象类型**存储：`BLOB`（二进制大对象）与 `CLOB`（字符大对象）。它们通常**不直接存在表的行内**，而是存一个引用（locator），实际内容放在单独存储区——否则一个几 MB 的图片会把整张表拖垮。<span class="marginnote">「行内只放引用、正文放外面」是数据库应对大值的通用策略，与文件系统、对象存储的思路一致。查询时要按 locator 把内容取回来，而不是直接在 WHERE 里和 BLOB 比较。</span>

### 用户自定义类型与域

SQL 允许把内置类型「取个有业务含义的名字」。有两种机制：

```sql
CREATE TYPE Dollars AS NUMERIC(12, 2) FINAL;   -- 自定义类型
CREATE DOMAIN Dollars AS NUMERIC(12, 2) NOT NULL;  -- 域
```

两者都能让 `salary` 声明为 `Dollars`，使类型语义自解释。区别在于：**`CREATE TYPE` 定义的是一种可互换的新类型，不带约束**；而 **`CREATE DOMAIN` 定义的域可以附带约束与默认值**（如上面带了 `NOT NULL`）。<span class="marginnote">域上还可以加 CHECK，例如 `CREATE DOMAIN Over18 AS INTEGER CHECK (VALUE >= 18);`——把「成年」这个业务规则直接钉在类型上，任何用它建表的列自动继承该规则。</span>

**辨析｜易错点：** `CHAR(n)` 的 $n$ 在标准里是**字符数**而非字节数——存中文时一个汉字算一个字符，但实际字节数翻倍，这直接影响字段长度的选择。另外，浮点类型（REAL/DOUBLE）**不保证精确**，金额类数据永远用 `NUMERIC` 而非 `FLOAT`——第 2 章我们讲过关系是数学集合，浮点误差会让「相等比较」变得不可靠。

## 4 模式、目录与环境：名字的命名空间

数据库里有两处叫「模式」的概念，容易混淆：第 2 章的**关系模式（relation schema）**描述一张表的属性结构；本节的**模式（schema）**是**一批相关对象的集合**——表、视图、约束、域都归属在某个 schema 名下。

SQL 标准的命名层级是：**环境（environment）> 目录（catalog）> 模式（schema）> 对象**。

- **目录（catalog）**：一组模式的命名集合，一个环境可含多个目录。
- **模式（schema）**：一组相关数据库对象（表、视图、约束等）的命名集合，可用 `CREATE SCHEMA <名字>;` 创建。
- 引用对象时可用**全限定名**逐级定位：`catalog.schema.table`。省略则使用**默认模式**。

```sql
CREATE SCHEMA university;
CREATE TABLE university.course (
    course_id VARCHAR(8) PRIMARY KEY
);
```

这套命名空间解决的核心问题是**隔离与共享**：不同模式里可以各有一张 `course` 表，互不干扰；两个应用团队可以各占一个 schema，再通过授权（下一节）控制谁能访问谁。<span class="marginnote">工程里常见的做法是「一个数据库实例，多个 schema 隔离多个业务」——比开多个实例省资源，又比全挤在默认 schema 里干净。这套「名字空间 = 隔离边界」的思想，在文件系统目录、编程语言的包/命名空间里反复出现。</span>

## 5 索引：CREATE INDEX

数据一旦多了，`WHERE ID = '12345'` 若还要逐行扫描整张表，速度会惨不忍睹。数据库用**索引（index）**解决：为某个属性建一个额外的数据结构，让系统能直接定位到满足条件的行，而不必扫描全表。

```sql
CREATE INDEX studentID_index ON student (ID);
```

**索引（index）**：基于一个或多个属性建立的辅助数据结构，用于快速查找指定取值对应的元组。<span class="marginnote">索引是物理存储层的东西，属于第 10 章《索引与哈希》的主角；这里只需知道：它牺牲写入/存储开销，换取查询速度。索引不会被查询优化器「忽略」，恰恰相反——优化器会用它来评估哪条执行计划更便宜，见第 11、12 章。</span>

**辨析｜易错点：** 索引不是越多越好。每建一个索引，INSERT/UPDATE/DELETE 都要额外维护它，写放大随之而来。**索引是对「读」的投资，要向「写」收税**——只给高频过滤条件建索引，是数据库调优的基本功。

## 6 公式解析：NUMERIC(p, d) 到底能存多大

定点数 `NUMERIC(p, d)` 的语义值得精确拆解，因为它直接决定金额类的表示能力：

$$
\text{NUMERIC}(p, d):\quad
\text{共 } p \text{ 位有效数字，其中 } d \text{ 位在小数点后};
\qquad
\text{最小刻度} = 10^{-d},\quad
\text{最大绝对值} = 10^{\,p-d} - 10^{-d}
$$

以 `NUMERIC(12, 2)` 为例逐步拆：

- **第一步，读 $p$ 与 $d$**：$p=12$ 是**总的有效数字位数**，$d=2$ 是其中**小数点后的位数**。于是整数部分最多 $p-d = 10$ 位。
- **第二步，看最小刻度 $10^{-d} = 10^{-2} = 0.01$**：这个类型能精确表示到「分」，任何值都是 0.01 的整数倍。**这不是精度「约等于两位小数」，而是「固定 0.01 的步长」**——存 `3.141` 会被舍入到 `3.14`，存 `0.005` 会舍入到 `0.01`。
- **第三步，看最大绝对值 $10^{10} - 10^{-2}$**：即 `9,999,999,999.99`，整数部分最多 10 位 9。超范围的值要么报错、要么被拒，而不会「偷偷变大」。
- **第四步，对比浮点**：`REAL`/`DOUBLE` 是**按 2 的幂近似**存储的，`0.1` 在二进制下是无限循环小数，存进去就是一个近似值；`NUMERIC(p,d)` 则是**按十进制位精确**存储，适合金额、税率、重量等「差一分钱都不行」的数据。**这就是为什么 `balance NUMERIC(12,2)` 而不是 `FLOAT`。**

把这条公式和上一节完整性约束连起来：`NUMERIC(12,2)` 声明了「刻度与范围」，CHECK 声明了「取值不能为负」——**类型管「长什么样」，约束管「合不合规」**，两者叠加才构成对一个字段的完整定义。

## 7 小结

- **内置类型**分字符串（CHAR/VARCHAR）、数值（INT/NUMERIC/REAL/FLOAT）、日期时间（DATE/TIME/TIMESTAMP/INTERVAL）三类。
- **CHAR 定长、VARCHAR 变长**；定长补空格会在比较与拼接时埋坑，姓名等变长文本优先 VARCHAR。
- **BLOB/CLOB** 存大对象，行内只存引用；**DEFAULT** 声明缺省值；**CREATE TYPE** 定义新类型，**CREATE DOMAIN** 定义可带约束与默认值的域。
- **环境 > 目录 > 模式 > 对象** 构成名字的命名空间，`catalog.schema.table` 全限定名逐级定位。
- **CREATE INDEX** 建索引换查询速度，但向写操作收税，不可滥用。
- **NUMERIC(p,d)** 共 $p$ 位有效数字、$d$ 位小数，步长 $10^{-d}$，最大绝对值 $10^{p-d}-10^{-d}$；金额类必须用定点数而非浮点。

在下一节，我们将回答「谁有权看到、修改什么」——**授权**：权限、角色与收回，把数据库的大门装上锁。
