## 为什么从物化视图开始

优化器再聪明，也改变不了一个事实：**有些查询天生贵**（跨表聚合、深连接）。与其每次重新算，不如**把结果预存起来**——这就是**物化视图（materialized view）**。它是查询优化的「第二层防线」：在优化器的运行时改进之外，用**预计算**绕开昂贵查询。这一节讲物化视图的定义、**增量维护**（incremental maintenance）与**查询改写**（query rewriting），并顺带讲查询结果缓存——OLTP 里更轻量的同一思想。

## 1 物化视图 vs 普通视图

**视图（view）**：只存查询定义，每次查询都重新执行（第 4 章）。

**物化视图（materialized view）**：把视图的**查询结果**物理存成一张表。

| 维度 | 普通视图 | 物化视图 |
| --- | --- | --- |
| 存储 | 只存定义 | **存结果** |
| 查询 | 每次执行 | 直接读结果（快） |
| 新鲜度 | 永远最新 | 依赖刷新策略 |
| 维护 | 无 | **需要刷新** |
| 空间 | 无 | 占存储 |

**核心要点：物化视图用「空间 + 新鲜度管理」换「查询速度」。** 它是数据库内建的「反规范化/汇总表」，比应用层缓存更可靠——优化器能自动识别并改写查询到物化视图上。

## 2 增量维护

**维护（maintenance）**：基表更新后，物化视图如何保持同步。三种策略：

1. **完全重算（full refresh）**：重新执行视图定义——简单但贵，适合低频更新。
2. **增量维护（incremental maintenance）**：只更新受影响的视图行——快，但要记录基表的变更（delta）。
3. **惰性维护（lazy）**：查询时检查过期并刷新——按需计算。

**公式解析：增量维护的收益**

设基表变更 $\Delta$ 行、物化视图规模 $M$ 行：

$$
T_{\text{incr}} = O(\text{处理 } \Delta \text{ 的能力}), \qquad
T_{\text{full}} = O(\text{重算全部})
$$

- **第一步，增量代价**：只处理变更 $\Delta$，与视图规模无关。
- **第二步，全量代价**：重新执行整个查询，随基表增长而增长。
- **第三步，收益条件**：$\Delta \ll M$ 时增量远快于全量——**变更小、视图大**的场景收益最大。
- **第四步，工程代价**：增量维护要维护「基表 → 视图」的变更传播逻辑（物化日志、触发器），实现复杂——多数数据库支持完全刷新 + 手动增量，全自动增量维护（如 Oracle MV）是高级能力。

## 3 查询改写：自动利用物化视图

**查询改写（query rewriting）**：优化器把用户查询**重写为对物化视图的访问**，若两者语义等价且视图更新鲜。

**例子**：有物化视图 `mv_sales_summary (region, month, total)`，用户查询：

```sql
SELECT region, SUM(amount) FROM sales WHERE month = 202601 GROUP BY region;
```

若 `mv_sales_summary` 已按 region+month 聚合，优化器可改写为直接查 `mv_sales_summary`——省掉整次聚合。

**核心要点：改写是「优化器自动匹配预计算」。** 匹配条件是：**物化视图包含查询所需的所有信息，且粒度不粗于查询**。粒度匹配失败（视图按年、查询按月）则无法改写。

**辨析｜易错点：** 物化视图不是「缓存」（cache）——**缓存过期自动失效，物化视图过期仍返回旧数据**。新鲜度由维护策略决定：`REFRESH MATERIALIZED VIEW` 手动刷、或定时自动刷。**查物化视图得到的是「快照」，不是实时数据**——业务上要能容忍这个延迟。

## 4 查询结果缓存

OLTP 里还有更轻量的**结果缓存（query result cache）**：

- 缓存「查询文本 → 结果」的映射（如 MySQL Query Cache、Redis 应用缓存）。
- 命中直接返回，零计算。
- 基表变更即失效（Query Cache 因维护成本高在 MySQL 8 被移除）。

**对比物化视图**：

| 维度 | 结果缓存 | 物化视图 |
| --- | --- | --- |
| 缓存粒度 | 精确查询文本 | 可被改写匹配 |
| 失效粒度 | 整表变更即失效 | 增量维护 |
| 优化器感知 | 否 | **是（可改写）** |
| 典型场景 | OLTP 重复查询 | OLAP 昂贵聚合 |

**核心要点：结果缓存适合「相同查询反复执行」的 OLTP**（如仪表盘、热点页）；物化视图适合「查询多样但都需大聚合」的 OLAP。两者都是「以存储换计算」——与第 8 章反规范化是同一哲学。<span class="marginnote">注意「缓存失效」的语义差异：结果缓存<strong>不保证新鲜</strong>（可能返回旧结果），物化视图的新鲜度也由刷新决定。对一致性敏感的读，不能依赖这两者——这正是第 13 章事务要解决的「读什么算一致」的问题。</span>

## 5 物化视图的最佳实践

- **识别昂贵且重复的查询**：`pg_stat_statements` 找高频高耗时查询，建对应物化视图。
- **与数据仓库配合**：第 20 章数据仓库的「汇总表」就是物化视图思想的工程化。
- **刷新窗口**：选业务低谷刷新（夜间 batch）。
- **空间预算**：物化视图也占存储——别过度物化。

## 6 小结

- **物化视图**预存查询结果，用空间 + 刷新成本换查询速度。
- 维护三策：**完全重算、增量维护、惰性**；增量收益 $\propto$ 变更小/视图大。
- **查询改写**让优化器自动匹配物化视图——粒度要匹配。
- 物化视图是**快照**，不是实时数据；新鲜度由刷新策略决定。
- 结果缓存是 OLTP 的轻量版，失效粒度更粗、优化器不感知。
