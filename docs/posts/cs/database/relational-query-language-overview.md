## 为什么从查询语言概览开始

前几节我们解决了「数据如何组织、如何标识、如何设计」，但还缺最后一块拼图：**数据存进去之后，怎么问问题？** 查询语言（query language）就是人与数据库之间的协议。理解查询语言，不是记几条 SQL 语法，而是先建立一幅地图：**世界上有哪些查询语言，它们各自「想问题」的方式有何不同。**

本节给你这幅地图：一类是**过程式（procedural）**的关系代数——告诉数据库「按什么步骤算」；一类是**声明式（declarative）**的关系演算——只告诉数据库「我想要什么」。SQL 则站在两者肩上，是面向实际系统的商业语言。<span class="marginnote">这幅「要什么 vs 怎么做」的二分，远不止数据库：命令式编程 vs 函数式/声明式编程、手写循环 vs 聚合函数、以及「向大模型描述目标而非逐步指令人工操作」，都是同一个思想的两极。本站主线「从极限到大模型」会反复回到这条分界线。</span>

## 1 查询语言的类别

**查询语言（query language）**：用户用来从数据库中请求信息的语言。按「由谁决定怎么做」可分为两大类：

- **过程式语言（procedural language）**：用户给出**操作序列**，系统依序执行。用户不仅说「要什么」，还说「先做这个、再做那个」。
- **非过程式 / 声明式语言（declarative language）**：用户只描述**期望的结果**，系统自行决定如何计算。用户说「要什么」，不问「怎么做」。

关系模型恰好在两个极端各有一门**纯理论语言**：关系代数（过程式）与关系演算（声明式）。它们是理解 SQL 的两个数学锚点，也是第6章《形式化关系查询语言》与第12章《查询优化》的地基。

## 2 关系代数：过程式的核心

**关系代数（relational algebra）**：一门以**关系为操作对象、以关系为操作结果**的代数。每个运算吃进一个或两个关系，吐出一个新关系——因为结果仍是关系，所以表达式可以**嵌套复合**，构成任意复杂的查询。它共六个**基本运算**：

| 运算 | 记号 | 作用 |
| --- | --- | --- |
| 选择 | $\sigma_p(r)$ | 挑出满足谓词 $p$ 的**行** |
| 投影 | $\Pi_{A_1,\dots,A_k}(r)$ | 只保留指定**列** |
| 并 | $r \cup s$ | 两关系的行取并集 |
| 集合差 | $r - s$ | 在 $r$ 中但不在 $s$ 中的行 |
| 笛卡儿积 | $r \times s$ | 两关系的行两两配对 |
| 更名 | $\rho_S(r)$ | 给关系换名（便于自连接） |

**重点：这六个运算全部承袭自第一级《集合》的运算。** $\cup$、$-$、$\times$ 就是集合论里的同名运算；$\sigma$ 与 $\Pi$ 是从集合中「筛选子集」「提取分量」的数据库专用形态。<span class="marginnote">数学的集合论在数据库里「复活」了：集合、笛卡儿积、子集、交并差，全部原样上阵。第一级学集合时以为在学纯数学，其实在预习关系代数。</span> 其余常用运算（连接、交、除法等）都可以由这六种**定义**出来，留到下一节《关系代数：基本运算》。

## 3 关系演算：声明式的另一极

**关系演算（relational calculus）**：一门**声明式**语言——用户写一个「描述结果的谓词」即可。又分两支：

- **元组关系演算（tuple relational calculus）**：写法 $\{t \mid P(t)\}$，意为「所有满足谓词 $P$ 的元组 $t$」。例如「找所有 CS 系教师」写作 $\{t \mid t \in instructor \wedge t[\text{dept\_name}] = \text{'CS'}\}$。
- **域关系演算（domain relational calculus）**：以属性取值为变量而非整个元组，写法形如 $\{\langle x, y \rangle \mid \dots\}$。

关系演算的关键特质是**不描述步骤**：它是一条「筛选规则」，而不是一份「操作清单」。至于系统如何按规则去找元组，用户不管。

同一个查询「找 CS 系教师」，两种语言的写法对照一眼就能看出风格差异：

| 语言 | 表达 |
| --- | --- |
| 关系代数（过程式） | $\sigma_{dept\_name = \text{'CS'}}(instructor)$——先选行，再（若要投影就）选列，步骤明确 |
| 元组演算（声明式） | $\{t \mid t \in instructor \wedge t[\text{dept\_name}] = \text{'CS'}\}$——只写「哪些元组合格」，没有任何步骤 |

代数写的是「操作管道」，演算写的是「合格标准」。这正是维特根斯坦那句话的数据库注脚：**语言的不同形态，决定了你能以多高的抽象层思考问题**——声明式把「怎么做」整个外包给了系统。

**辨析｜易错点：** 关系代数与关系演算**表达能力等价**——任何关系代数表达式能表达的东西，关系演算也能表达，反之亦然（第6章给出严格结论）。差别不在「能问什么」，而在「用什么方式问」：一个是逐步操作，一个是结果描述。

## 4 公式解析：代数表达式的逐步求值

用关系代数问一个问题：「找出 CS 系教师的姓名与工资。」对应表达式为

$$\Pi_{name,\ salary}\Big(\sigma_{dept\_name = \text{'CS'}}(instructor)\Big)$$

逐步拆解这条表达式：

- **第一步，从内层开始**：$\sigma_{dept\_name = \text{'CS'}}(instructor)$ 是选择运算——把 `instructor` 中 `dept_name = 'CS'` 的**行**全部挑出。谓词是逐行判断的布尔条件。得到一张「只含 CS 教师」的临时关系。
- **第二步，向外一层**：$\Pi_{name,\ salary}(\cdots)$ 是投影运算——在上一步的结果上，**只保留 `name` 与 `salary` 两列**，其余列（`ID`、`dept_name`）丢弃。得到「CS 教师的名 + 薪」表。
- **第三步，认识复合**：整个表达式是一个嵌套结构，**内层输出是外层输入**。这正是「代数」二字的含义——像 $f(g(x))$ 一样复合。括号的取舍顺序就是求值顺序。

运算结果的属性由投影列出、元组由行给出，因此**任何子表达式的结果仍是一个关系**。这条「封闭性」是关系代数能够无限复合的根基，也是第11章「物化 / 流水线」求值策略讨论的对象。

## 5 SQL：站在两者肩上的商业语言

关系代数与关系演算都是**纯理论语言**，现实中没有人直接用它们写查询。实际使用的商业语言是 **SQL（Structured Query Language）**。SQL 的定位是「关系语言」：它的 `SELECT ... FROM ... WHERE ...` 结构同时吸收了关系代数（投影、选择、连接）与关系演算（声明式）的基因。<span class="marginnote">SQL 名字里的 Structured 容易误导人——它既不「结构化」到过程式，也不纯声明式到关系演算，而是二者混合的实用折中。这也是为什么面试常说「SQL 是声明式的」这句话需要打补丁：它的查询部分是声明式的，但它还有过程式的存储过程。</span>

把同一查询写成 SQL：

```sql
SELECT name, salary
FROM   instructor
WHERE  dept_name = 'CS';
```

对照第4节的代数表达式，两者几乎逐词对应：`SELECT name, salary` ↔ $\Pi_{name,\ salary}$，`WHERE dept_name = 'CS'` ↔ $\sigma_{dept\_name = \text{'CS'}}$，`FROM instructor` 指定了操作对象。**理解关系代数，就等于拿到了阅读任何 SQL 查询的底层语法图。** 逐词映射可以扩成一张速查表，后面第3章还会反复用到：

| SQL 片段 | 关系代数 | 语义 |
| --- | --- | --- |
| `FROM instructor` | — | 指定输入关系 |
| `WHERE <条件>` | $\sigma_{<条件>}$ | 选行 |
| `SELECT <列清单>` | $\Pi_{<列清单>}$ | 选列 |
| `UNION` | $\cup$ | 并 |
| `EXCEPT` | $-$ | 差 |
| `ORDER BY` | 代数中没有（集合无序） | 排序是 SQL 的附加特性 |

这张表的最后一格值得记住：**排序不在关系代数里**，因为关系是集合、天生无序；`ORDER BY` 是 SQL 为了人机交互增加的「出口」，并不改变关系本身的语义。

## 6 易错辨析：三条常见的坑

- **SELECT 不是「选择」**：SQL 的 `SELECT` 同时对应代数里的投影 $\Pi$（列）与选择 $\sigma$（行）两个概念——`SELECT` 的列清单是投影，`WHERE` 才是选择。初学者把两者都叫「选」，结果分不清行筛选与列筛选。
- **代数结果无重复，SQL 结果可能有重复**：纯关系代数基于**集合**语义，结果天然去重；SQL 基于**多重集（bag/multiset）**语义，默认保留重复行，需要 `SELECT DISTINCT` 才去重。<span class="marginnote">「SQL 的笛卡儿积、并集都按 bag 处理」这件事，会在第3章《集合运算》与单关系查询里反复制造差异——记住「关系代数 = 集合，SQL = 多重集」这条分界线，能避开大量困惑。</span>
- **笛卡儿积不加条件会爆炸**：$r \times s$ 把每行都配一遍，行数等于两表行数之积。第3章讲多关系查询时你会看到，几乎所有 `FROM a, b WHERE a.x = b.x` 都是「先积后选」——理解这层才能理解为什么要用连接（join）而不是盲目叉积。

## 7 小结

- 查询语言分**过程式**（关系代数）与**声明式**（关系演算）两类；SQL 是两者之上的商业折中。
- 关系代数有六种基本运算：$\sigma$ 选行、$\Pi$ 选列、$\cup$、$-$、$\times$、$\rho$；结果仍是关系，可无限复合。
- 关系演算只写「结果谓词」：$\{t \mid P(t)\}$；与代数表达能力等价，只是风格相反。
- SQL 的 `SELECT / FROM / WHERE` 与 $\Pi / \sigma$ 逐词对应；理解代数即理解 SQL 的底层语法图。
- **关系代数 = 集合语义，SQL = 多重集语义**，这是两者最根本的分界线。

在下一节，我们将正式进入关系代数的**基本运算**，逐个吃透选择、投影、并、差、笛卡儿积与更名——并用它们拼出真正的查询。
