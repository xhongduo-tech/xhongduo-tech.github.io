## 为什么从行/列存储开始

前面讲的表都是**行式存储（row-oriented）**：一个块存「多行完整记录」。但有一类系统完全反过来——**列式存储（column-oriented）**：一个块存「一列的全部值」。这个选择不是风格差异，而是**工作负载的镜像**：行存服务「取整行」的 OLTP，列存服务「聚合一列」的 OLAP。这一节对比两种组织方式的结构、I/O 特性与适用场景，为第 20 章 OLAP 与列存数据库打地基。**你会在第 20 章看到，列存的优势远不止 I/O**。

## 1 两种存储方式的结构

**行式存储（row store）**：记录连续存放。块内是「行1的A,B,C | 行2的A,B,C | …」。

**列式存储（column store）**：每列独立存放。块的划分是「列 A 的所有值 | 列 B 的所有值 | …」。

例如账户表 account(branch_name, account_number, balance)：行存把每条记录的三个字段连续放进一个块；列存则把 balance 列的所有值放一组块、branch_name 列的所有值放另一组块，彼此独立。

**核心要点：存储方式决定「读一块能回答什么问题」。** 行存读一块 = 拿到几行完整记录；列存读一块 = 拿到一列的几个值。查询只关心某几列时，列存只读那几列的文件——**行存却必须把整行读出来再扔掉用不到的列**。

## 2 I/O 特性的对比

用「SELECT SUM(balance) FROM account WHERE branch='主楼'」这类聚合查询看差异。设表有 100 列、每行 1KB、共 100 万行（1GB），查询只用 2 列。

**行式**：必须扫描全部 1GB——每块的整行都读进内存，只取其中 2 列。**读放大 50 倍**。

**列式**：只读 branch_name 列与 balance 列两个文件，约 20MB。**只读用到的数据**。

**公式解析：列存的 I/O 优势**

$$
\frac{\text{I/O}_{\text{row}}}{\text{I/O}_{\text{column}}} = \frac{N_{\text{columns}}}{N_{\text{used}}}
$$

- **第一步，行存 I/O**：扫描整个表，读全列，I/O 正比于列总数 $N_{\text{columns}}$。
- **第二步，列存 I/O**：只读被查询引用的列，I/O 正比于用到的列数 $N_{\text{used}}$。
- **第三步，比值**：列越多、查询用列越少，列存优势越大——100 列用 2 列，快 50 倍。
- **第四步，但要看清场景**：若查询用「全部列」（如 SELECT *），两者 I/O 相同——列存此时还有重组行的开销，反而更慢。**列存不是更快，是「对窄查询更快」**。

## 3 压缩与延迟物化

**列存让压缩更高效**：同一列的值类型相同、往往取值相似，可以用**列级压缩**：

- **字典编码**：把重复值替换成短码。
- **游程编码（RLE）**：连续相同值存成 (值, 次数)。
- **位图**：为每个取值存位图。

**延迟物化（late materialization）**：列存执行时，**先在各列上做过滤/聚合，最后才组装完整行**——避免提前拼行浪费带宽。例如先对 branch_name 列做过滤，再投影 balance，最后才拼结果行。<span class="marginnote">延迟物化是列存执行器的灵魂：行存是「边读边拼行」，列存是「各列独立算、最后拼」。它配合向量化执行（第 20 章）能最大化 CPU 利用率——因为每列的值在内存里连续排布，天然适合 SIMD。</span>

## 4 适用场景对照

| 维度 | 行式存储 | 列式存储 |
| --- | --- | --- |
| 典型负载 | OLTP（点查、事务） | OLAP（聚合、扫描） |
| 读单位 | 整行 | 整列 |
| 点查（按码取一行） | 快 | 慢（要拼多列） |
| 聚合（SUM/AVG） | 慢（读放大） | 快（只读相关列） |
| 插入 | 快（追加行） | 慢（要写多列文件） |
| 更新单行 | 快 | 慢（改写多列） |
| 压缩率 | 低 | **高** |
| 代表 | PostgreSQL、MySQL | ClickHouse、DuckDB、SQL Server 列存 |

**辨析｜易错点：** 列存**不适合** OLTP 点查——点查（如 SELECT * FROM account WHERE account_number = 'A-101'）在列存里要读「所有列文件中 id=123 的位置」再拼成行，比行存的一行读取慢得多。**列存与行存不是谁取代谁，而是负载决定的选择**；「HTAP」试图两者兼得（第 20 章末）。

## 5 从文件组织到数据库家族的延伸

行/列存储的选择把数据库分成两大阵营：

- **行存系**：PostgreSQL、MySQL、Oracle——OLTP 主力。
- **列存系**：ClickHouse、DuckDB、Vertica、SQL Server 列存索引——OLAP 主力。

**连接点：** 第 20 章会把列存讲透——压缩编码的细节、向量化执行、物化列、以及 ClickHouse/DuckDB 的工程实现。今天的 I/O 直觉，是理解「为什么数据仓库用列存、为什么列存能向量化」的第一层。而「行存点查快、列存聚合快」的权衡，也是 HTAP（同时服务两种负载）要解决的终极问题。

## 6 小结

- 行存：块含多行整记录，点查快、聚合读放大；列存：块含一列多值，聚合快、点查需拼行。
- 列存 I/O 优势 $= N_{columns}/N_{used}$，列越多优势越大，查询用全部列时则无优势。
- 列存利于**列级压缩**（字典、RLE、位图）与**延迟物化**。
- 负载决定存储：OLTP 用行存，OLAP 用列存；HTAP 试图兼得。
