## 为什么从 NoSQL 开始

关系数据库统治了四十年，但 Web 2.0 时代的三大需求——**海量数据、高并发写、灵活模式**——让关系模型的「严格模式 + 强事务」成为负担。**NoSQL（Not Only SQL）**由此兴起：放弃关系模型的某些约束，换取**水平扩展、高可用、灵活模式**。这一节讲 NoSQL 兴起的背景、四大数据模型分类（键值、文档、宽列、图），以及「NoSQL 不是什么」。理解 NoSQL 的「放弃与获得」，才能理解为什么它和关系数据库共存而非取代。

## 1 NoSQL 兴起的背景

**关系数据库的三大痛点**：

1. **扩展难**：单机垂直扩展有上限，分库分表要改应用、跨节点事务复杂（第 17 章）。
2. **模式僵化**：\`ALTER TABLE\` 加列要锁表——互联网业务的**快速迭代**等不起。
3. **强一致代价高**：分布式强事务（2PC）慢且阻塞——**高并发写**扛不住。

**NoSQL 的对应选择**：

- **水平扩展**：天然分布式，分片 + 复制内建（第 17 章）。
- **无模式/灵活模式**：文档想加字段就加。
- **弱一致性**：用最终一致换可用性（第 18 章）。

**核心要点：NoSQL 是「在一致性/关系语义上做减法，在规模/灵活性上做加法」。** 它不是「更好的数据库」，而是**为不同负载设计的数据库**——「NoSQL」不是「No SQL」（其实很多支持 SQL），而是 **Not Only SQL**。

## 2 四大数据模型

**NoSQL 按数据模型分四大类**：

| 类别 | 数据模型 | 查询方式 | 代表 |
| --- | --- | --- | --- |
| 键值存储 | Key → Value | 按键查值 | Redis、Memcached、DynamoDB |
| 文档数据库 | 文档（JSON） | 文档内查询、索引 | MongoDB、CouchDB |
| 宽列存储 | 行 + 动态列族 | 按行键 + 列查询 | BigTable、Cassandra、HBase |
| 图数据库 | 节点 + 边 | 图遍历、路径查询 | Neo4j、JanusGraph |

**核心要点：数据模型决定「查询能怎么走」。** 键值只能按键查、文档能查字段、宽列能按行键+列族扫、图能遍历关系——**选 NoSQL = 选数据模型与查询的匹配**。

## 3 键值存储与文档数据库

**键值存储（key-value store）**：最简单——**GET / PUT / DELETE**。值是不透明的字节串（或简单对象）。

- **优势**：极快（哈希/内存）、极简、易扩展。
- **局限**：只能按主键查——无二级索引、无范围查询（除非有序键）。

**文档数据库（document store）**：值是**半结构化的文档**（JSON/BSON/XML），可嵌套。

- **优势**：灵活模式（字段可增）、**二级索引**、类 SQL 查询、聚合。
- **关系表达**：文档内嵌（嵌套子文档）或引用（存文档 ID）——**没有外键约束，一致性靠应用**。

**辨析｜易错点：** **文档数据库不是「存 JSON 的关系库」**——它没有 schema 约束、没有跨文档事务（除非单文档原子性）、没有 JOIN（要应用层做）。MongoDB 的「文档 = 一行」的心智模型，与关系模型的「行 + 外键」完全不同。

## 4 宽列存储与图数据库

**宽列存储（wide-column store）**：行有**行键**，列被组织成**列族（column family）**，每行的列可以**动态变化**——「稀疏表」。

- **行键定位**：按行键范围扫（BigTable）或按哈希（Cassandra）。
- **优势**：海量数据、写吞吐高、列族优化读。
- **代表**：BigTable、HBase、Cassandra——**第 19 章后文专讲**。

**图数据库（graph database）**：数据是**节点（vertex）+ 边（edge）+ 属性**，查询是**遍历（traversal）**。

- **优势**：关系查询（「朋友的朋友」「最短路径」「影响链」）**天然高效**——关系库要多次 JOIN，图库沿边走。
- **代表**：Neo4j、JanusGraph——**第 19 章后文专讲**。

**公式解析：关系 vs 图的「多跳查询」**

查「A 的 3 度关系」（A→…→…→X）：

$$
T_{\text{关系库}} = O(k \cdot \text{JOIN 代价}), \qquad
T_{\text{图数据库}} = O(\text{沿边遍历的度数})
$$

- **第一步，关系库多跳 = 多次 JOIN**：每个跳一次连接，代价随深度线性（且连接昂贵）。
- **第二步，图库多跳 = 沿边遍历**：每跳访问「邻居集合」，本地索引快。
- **第三步，深度 3、扇出 100**：关系库 3 次大 JOIN；图库访问 $100^3$ 个节点但每次 O(1)——**图的优势在「关系密集型」查询**。
- **第四步，反之**：关系库的「按属性批量过滤」图库不一定快——**图数据库是「关系优先」的专用工具**。

## 5 NoSQL 的边界与选择

**NoSQL 不是什么**：

- 不是「抛弃 SQL」——很多 NoSQL 加了 SQL（Cassandra CQL、DynamoDB PartiQL）。
- 不是「没有一致性」——只是默认弱一致、可调。
- 不是「取代关系库」——OLTP 强事务仍是关系库主场。

**选型决策**：

| 负载 | 推荐 | 理由 |
| --- | --- | --- |
| 通用 OLTP + 强事务 | 关系库 | ACID、SQL、成熟 |
| 缓存/会话 | 键值 | 极快、简单 |
| 灵活模式的内容/目录 | 文档 | 无模式、二级索引 |
| 海量时序/事件写 | 宽列 | 写吞吐、水平扩展 |
| 关系密集型查询 | 图 | 遍历高效 |

**核心要点：NoSQL 与关系库是「负载匹配」关系，不是「优劣」关系。** 真正的「既要关系语义又要水平扩展」——就是下一节起的 **NewSQL**。

## 6 小结

- NoSQL 兴起：**水平扩展、灵活模式、弱一致**换规模与迭代速度。
- 四大模型：**键值、文档、宽列、图**——数据模型决定查询能力。
- 键值极简但只按主键；文档灵活但无 JOIN/外键。
- 宽列适合海量写；图适合关系遍历。
- NoSQL ≠ No SQL；与关系库**共存互补**；「既要又要」是 NewSQL。
- 选型核心是「数据模型 × 查询负载」匹配，而非「哪个更好」——先想清查询模式，再选数据库形态。
