## 为什么从图数据库开始

关系数据库用表 + JOIN 表达关系，但「关系密集型」查询（朋友的朋友、最短路径、影响传播）在多跳 JOIN 面前力不从心。**图数据库（graph database）**把「节点 + 边」作为一等公民，让**遍历**成为核心查询——沿边走、逐跳扩展，复杂关系查询在图上高效。这一节讲图的属性图模型、Cypher 查询语言、与关系库的 JOIN 对比、以及图数据库的适用边界。图数据库是「关系即数据」的极致体现。

## 1 属性图模型

**属性图（property graph）**由三要素组成：

- **节点（vertex）**：实体，带标签（如 `Person`）与属性（如 `name`）。
- **边（edge）**：关系，带类型（如 `FRIEND_OF`）、方向、属性。
- **遍历（traversal）**：从某个节点出发，沿边访问邻居——图查询的基本操作。

**核心要点：边的属性让「关系本身」携带信息。** 关系库把「关系」表达为外键 + 连接表（关系数据散落在多表）；图库把「关系」表达为**实体的边**——关系是数据，直接可查。

**对比关系模型**：

| 维度 | 关系数据库 | 图数据库 |
| --- | --- | --- |
| 关系表达 | 外键 + JOIN | **边（first-class）** |
| 多跳查询 | 多次 JOIN | **沿边遍历** |
| 模式 | 固定 schema | 灵活（节点/边可带任意属性） |
| 优化器 | 基于代价（连接顺序） | 基于遍历（索引邻接表） |

## 2 Cypher：声明式图查询

**Cypher**（Neo4j 的查询语言）用 ASCII 图形语法描述模式：

```cypher
MATCH (a:Person)-[:FRIEND_OF]->(b:Person)-[:FRIEND_OF]->(c:Person)
WHERE a.name = 'Alice'
RETURN c.name
```

- `(a:Person)`：节点变量 a，标签 Person。
- `-[:FRIEND_OF]->`：有向边，类型 FRIEND_OF。
- `MATCH ... WHERE ... RETURN`：模式匹配 + 过滤 + 返回——**与 SQL 的 SELECT-FROM-WHERE 同构**。

**核心要点：Cypher 用「模式（pattern）」描述要匹配的子图。** `MATCH` 声明「要找到这样的结构」，数据库用遍历/索引完成匹配——**声明式（要什么）而非过程式（怎么走）**，与 SQL 的哲学一致。

**公式解析：模式匹配 = 子图同构搜索**

`MATCH` 匹配「图中与模式同构的子图」：

$$
\text{匹配数} = \#\{ \text{子图 } S \subseteq G \mid S \cong \text{模式} \}
$$

- **第一步，同构**：$S$ 与模式的结构一致（节点标签、边类型、属性匹配）。
- **第二步，搜索**：从锚定节点出发做**回溯搜索**（backtracking）——图库用邻接表索引加速。
- **第三步，代价**：一般图子图同构是 NP 难——图库靠「起点锚定 + 剪枝」控制规模。
- **第四步，工程**：真实查询大多从**少量起点**（按属性找到锚节点）出发遍历，规模可控——**图查询快不快，取决于遍历深度与扇出**。

## 3 图查询 vs SQL JOIN

**「朋友的朋友」**：查 Alice 的 2 度好友。

**SQL（关系库）**：

```sql
SELECT c.name
FROM person a
JOIN friend f1 ON a.id = f1.a_id AND a.name = 'Alice'
JOIN friend f2 ON f1.b_id = f2.a_id
JOIN person c ON f2.b_id = c.id;
```

- 两跳 = 两次 JOIN；三跳三次 JOIN——**深度增加 = JOIN 数线性增加，且连接代价昂贵**。

**Cypher（图库）**：

```cypher
MATCH (a:Person {name:'Alice'})-[:FRIEND_OF*2]->(c:Person) RETURN c.name
```

- 两跳 = 一次模式匹配——**深度变化不改查询形态，遍历沿边走**。

**公式解析：多跳查询的代价比**

设扇出 $d$、深度 $k$：

$$
T_{\text{SQL}} \approx O(k \cdot \text{JOIN}), \qquad
T_{\text{Graph}} \approx O(d^k) \text{ 但每步本地邻接表索引}
$$

- **第一步，SQL 每次 JOIN**：连接是全局操作（排序/哈希），随深度线性加贵。
- **第二步，图遍历**：每跳访问当前节点的邻居（本地索引 $O(d)$），总 $d^k$ 但每步极快。
- **第三步，深度 3、$d=100$**：SQL 3 次大 JOIN；图访问 $10^6$ 节点但每步微秒——**图在「关系密集型、深度遍历」上显著更快**。
- **第四步，反之**：图的**按属性批量过滤**（「找所有 30 岁的人」）不一定比关系库快——**图是「关系查询」的专用工具，不是通用替代**。

## 4 图数据库的适用边界

**适合**：

- 社交网络（好友链、推荐）、欺诈检测（资金流环）、知识图谱（实体关系）、推荐系统（用户-物品-偏好路径）。

**不适合**：

- 纯点查/事务型 OLTP（关系库更好）。
- 海量聚合/报表（列存更好）。
- 简单的两表连接（关系库足够）。

**辨析｜易错点：** **图数据库 ≠ 分布式图处理（如 Pregel）**。图数据库是**在线查询**（交互式遍历）；Pregel/GraphX 是**离线批量图计算**（PageRank、连通分量）。两者底层都用图，但一个服务查询、一个服务计算。

**核心要点：图数据库的价值在「关系密集型在线查询」。** 选择图库的标准是「你的查询是否以『沿关系遍历』为主」——若是，图库省掉 JOIN 的指数成本；否则，关系库/列存更合适。

## 5 小结

- **属性图**：节点 + 边 + 属性；遍历是核心操作——关系是数据。
- **Cypher**：`MATCH` 模式匹配，声明式——与 SQL 哲学同构。
- 图库把多跳查询从「多次 JOIN」变成「沿边遍历」——**深度遍历显著更快**。
- 图查询是子图同构搜索——靠锚定起点 + 剪枝控制规模。
- 图库适合关系密集型在线查询；通用 OLTP/聚合还是关系库/列存。
