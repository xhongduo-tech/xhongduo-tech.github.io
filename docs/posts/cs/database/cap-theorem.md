## 为什么从 CAP 开始

前面每一章都在「一致性与可用性/性能」之间做取舍——复制要容忍滞后、2PC 要阻塞、Saga 要补偿。**CAP 定理**把这些取舍上升为一条「守恒律」：**网络分区（partition）发生时，系统只能在「一致性（Consistency）」与「可用性（Availability）」之间选一个**。这一节讲 CAP 的准确含义、它的证明直觉、以及流传最广的误解——**CAP 不是「三选二」，而是「分区时的二选一」**。CAP 是第 18 章全部一致性模型的「取舍地图」。

## 1 CAP 的准确定义

**CAP** 三个性质：

- **一致性（Consistency）**：**线性一致性**——读请求返回**最近一次写**的结果（所有节点看到相同的、最新的值）。
- **可用性（Availability）**：每个请求都**得到响应**（非故障节点必须应答，不能无限等待）。
- **分区容错（Partition tolerance）**：网络分区（节点间消息丢失/延迟）时，系统仍能运行。

**CAP 定理（Brewer, 2000；Gilbert & Lynch 证明）**：在**异步网络**下，当网络分区发生时，**一致性**与**可用性****不可兼得**——系统必须放弃其一。

**核心要点：CAP 只在「分区发生时」做出取舍。** 无分区时，系统可以既一致又可用（复制同步、等待协调都可行）——CAP 管的是「分区这种故障场景下怎么办」。

## 2 定理的证明直觉

**为什么分区时二选一**：

设网络把系统分成两部分 $G_1, G_2$，两者无法通信。客户端向 $G_1$ 写值 $v_1$、向 $G_2$ 读：

- **选一致性（CP）**：$G_2$ 的读必须返回「最新写 $v_1$」——但 $G_2$ 无法联系 $G_1$，得不到 $v_1$——只能**拒绝响应**（放弃可用）。
- **选可用性（AP）**：$G_2$ 必须响应——但拿不到 $v_1$，只能返回旧值 $v_0$（放弃一致性）。

**公式解析：分区的两难**

设分区两侧 $G_1, G_2$，$G_1$ 接受写 $v$，$G_2$ 收到读：

$$
\text{响应}(G_2) = 
\begin{cases}
v \text{（需联系 } G_1\text{）} \Rightarrow \text{不可用（等 } G_1\text{）} \\
v_0 \text{（本地旧值）} \Rightarrow \text{不一致（非最新）} \\
\text{无响应} \Rightarrow \text{不可用}
\end{cases}
$$

- **第一步，响应必须来自本地**：分区时 $G_2$ 无法从 $G_1$ 取最新值。
- **第二步，要一致就要等**：等 $G_1$ = 阻塞 = 不可用。
- **第三步，要可用就给旧值**：给旧值 = 不一致。
- **第四步，结论**：分区下无解——**CP 或 AP，必选其一**。

## 3 常见误解

**误解 1：「CAP 三选二」**。以为系统在 C、A、P 中任选两个。**错**——P 不是可选项，**分区容错是分布式系统的必选项**（网络分区必然会发生）。系统只在「分区时」于 C 与 A 之间选——无分区时两者都可。

**误解 2：CP = 强一致、AP = 弱一致**。CP 不保证「永远一致」——分区恢复后它要**恢复一致性**（分区期间拒绝写或拒绝读）。AP 也不等于「没有一致性」——它提供**最终一致**等弱保证。

**误解 3：CAP 决定数据库选型**。真实系统**不是非 C 即 A**——它们提供**一致性谱系**（第 18 章后文），在 C 与 A 之间**连续地**取舍（如多数派读、可用性优先的最终一致）。**CAP 是「分区的极端情况」的边界，不是日常设计的全部**。

**辨析｜易错点：** **CAP 的「C」是线性一致性（linearizability）**，不是泛指「一致性」——因果一致、最终一致等弱模型**不在 CAP 的 C 里**。所以「选 AP 的系统也有因果一致」不违反 CAP——**CAP 只约束线性一致性**。

## 4 CAP 与前面章节的呼应

**CAP 把第 16、17 章的所有取舍统一起来：**

| 系统选择 | 分区时行为 | 对应机制 |
| --- | --- | --- |
| CP（一致优先） | 拒绝部分请求/等待 | 2PC、Raft 多数派 |
| AP（可用优先） | 返回旧值、异步修复 | 主从异步复制、多主、Saga |
| 「中间态」 | 多数派读、读修复 | 可调一致性（第 18 章） |

**核心要点：CAP 是「一致性谱系」的理论边界。** 它告诉你「极端分区时二选一」，而第 18 章后面的线性一致、顺序一致、因果一致、最终一致，就是「二选一之外的中间地带」——**如何在不必二选一时尽量两全**。

**连接点：** 第 16 章 Raft 选「CP」（分区时多数派可用、少数派不可用）；第 17 章 Saga 选「AP」（分区时照常执行、事后补偿）；第 19 章 Spanner 用「TrueTime + Paxos」试图「分区时也接近 CP」。**CAP 给了读这些系统的一把尺子**。

## 5 CAP 的数值算例与选型速查

**用一个具体系统把 CP/AP 的行为演示清楚。** 设某社交系统三个副本，网络把 A 与 B、C 断开（分区）。

- **CP 系统（如多数派共识）**：A 是少数派——A 拒绝写入（quorum 不满足），返回「暂时不可用」。用户写入被拒，但读到的永远是最新一致数据。分区恢复后 A 自动追上。
- **AP 系统（如多主异步复制）**：A 照常接受写入，返回成功；B、C 分区恢复后同步 A 的写入——期间读到旧值（不一致），最终收敛。
- **真实权衡**：多数派读（read quorum）是「中间态」——A 分区时多数派仍可用，少数派拒绝——系统「大部分时候 CP、局部 AP」。

**数值算例：CP 的分区可用性** 设 5 副本、多数派 3。

- 分区成 3+2：3 侧可写（满足多数派），2 侧被拒——**分区时可用性 3/5**。
- 分区成 2+2+1：没有一侧达多数派——**全部拒绝写，系统写不可用**。
- **结论**：CP 系统的分区可用性取决于「多数派是否在同侧」——设计时要避免「把可能一起分区的节点凑成多数派」。

**辨析｜易错点：** 「CP 更安全、AP 更可用」的二分是误导——**现实中多数系统是「分级一致性」**：同一系统里，有的数据用强一致（账务）、有的用最终一致（计数）。CAP 是「极端分区的理论边界」，不是「系统的全部设计约束」。

<span class="marginnote">CAP 与第 16 章复制滞后、第 18 章一致性谱系的关系：<strong>CAP 定义了「分区时二选一」的边界，复制滞后描述「无分区时的暂时不一致」，一致性谱系提供「边界内的连续选择」</strong>——三者合起来才是分布式一致性的完整图景。</span>

### 术语速查

| 术语 | 含义 |
| --- | --- |
| 线性一致 | 读返回最近一次写的结果 |
| 可用性 | 每个请求都得到响应 |
| 分区容错 | 网络分区时仍能运行 |
| CP | 分区时优先一致（可能拒绝） |
| AP | 分区时优先可用（可能旧值） |
| 可调一致 | 按请求调整一致性强度 |

## 6 小结

- **CAP**：线性一致性、可用性、分区容错——**分区时 C 与 A 不可兼得**。
- 定理直觉：分区时 $G_2$ 无法取最新值——要一致就得等（不可用），要可用就得给旧值（不一致）。
- **误解**：不是「三选二」；P 是必选项；CAP 的 C 仅指**线性一致**。
- CP 与 AP 是「分区时的极端选择」；真实系统用**一致性谱系**连续取舍。
- CAP 是第 16-19 章所有分布式取舍的**理论框架**。
