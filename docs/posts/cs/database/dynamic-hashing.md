## 为什么从动态哈希开始

静态哈希的致命伤是「桶数固定」：数据涨了，溢出链拖垮性能；数据少了，空间浪费。**动态哈希（dynamic hashing）**让桶数随数据量自动伸缩，且**不打断在线服务**。这一节讲两种主流方案：**可扩展哈希（extendable hashing）**用「桶目录 + 分裂」按需扩桶；**线性哈希（linear hashing）**用「轮转分裂」让所有桶渐次翻倍。理解两者的「扩桶时机」与「查找代价」，是看懂现代数据库哈希索引（如 MySQL Adaptive Hash Index 的思路源头）的钥匙。

## 1 可扩展哈希：目录与全局深度

**可扩展哈希（extendable hashing）**的结构：

- **桶目录（bucket directory）**：一个指针数组，指向实际桶。目录大小 $2^d$（$d$ = **全局深度 global depth**）。
- **每个桶有自己的局部深度 $d_i$**：桶内记录共享哈希值的前 $d_i$ 位。
- **查找**：算哈希取前 $d$ 位 → 目录下标 → 桶。

**桶溢出时的分裂**：

1. 局部深度 $d_i < d$：**只分裂该桶**，目录不动。桶的 $d_i$ 位地址被「细化」成 $d_i+1$ 位，一分为二，目录里对应项指向新桶。
2. 局部深度 $d_i = d$：**目录翻倍**（$d \to d+1$），再分裂。

**核心要点：可扩展哈希是「按需扩容」。** 只有满桶才分裂，且多数时候只需局部处理；目录翻倍是稀有事件（仅在桶深度达到全局深度时）。

## 2 可扩展哈希的代价分析

**公式解析：可扩展哈希的查找与空间**

$$
T_{\text{lookup}} = 1 \text{ 次 I/O}, \qquad
\text{空间} = 2^d \cdot \text{指针} + \sum_i \text{桶大小}
$$

- **第一步，查找恒为 1**：算哈希取 $d$ 位定位目录项，读对应桶——**无论数据多少，等值查找都是 1 次 I/O**。
- **第二步，目录空间**：目录 $2^d$ 项随数据增长指数变大——数据量大时目录本身可能很占内存（但目录在内存，不算 I/O）。
- **第三步，桶空间**：一个桶 $d_i < d$ 时被多个目录项共享，共享减少存储；但「一个桶对应多个目录项」意味着部分桶实际很小、利用率不高。
- **第四步，权衡**：可扩展哈希的优点（查找恒定 1 I/O）用「目录可能很大 + 桶利用率不均衡」换取。数据分布偏斜时，某些桶频繁分裂、目录虚胖。

## 3 线性哈希：轮转分裂

**线性哈希（linear hashing）**不维护目录，而是**按顺序分裂桶**：

- 初始 $n$ 个桶，哈希函数 $h_0(K) = K \bmod n$。
- 用一个**轮转指针**按桶号从 0 到 $n-1$ 依次分裂：分裂到 $i$ 时，把第 $i$ 个桶的记录用 $h_1(K) = K \bmod 2n$ 重新分布到 $i$ 与 $i+n$ 两个桶。
- 分裂一个桶后指针 +1；全部桶分裂完一轮，$n$ 翻倍，$h_0$ 升级为 $h_1$。

**查找**：先试 $h_0$，若桶号 < 轮转指针（已分裂），用 $h_1$ 再定位。<span class="marginnote">线性哈希的妙处是<strong>分裂不依赖「哪个桶满了」</strong>，而是按固定顺序推进——实现简单、无需目录、最坏情况可预测。代价是<strong>分裂与溢出不绑定</strong>：满的桶可能还没轮到分裂，仍要溢出链顶着。</span>

## 4 两种动态哈希的对比

| 维度 | 可扩展哈希 | 线性哈希 |
| --- | --- | --- |
| 扩桶时机 | 桶满即分裂 | **按固定顺序轮转** |
| 目录 | 有（$2^d$ 项） | 无 |
| 查找 I/O | 恒定 1 | 1-2（取决于分裂轮次） |
| 空间利用 | 可能不均衡 | 渐进均衡 |
| 实现复杂度 | 目录管理复杂 | 简单 |
| 数据偏斜应对 | 差（目录虚胖） | 尚可（轮转摊平） |

**辨析｜易错点：** 可扩展哈希的「分裂」是**局部触发**（满桶才裂），线性哈希是**全局轮转**（与溢出无关）。所以线性哈希的桶「该裂的未必裂、不该裂的也裂」——这不是缺陷，是用「可预测的渐进扩容」换「实现简单」。

## 5 动态哈希的现代归宿

教科书里的可扩展/线性哈希是「磁盘哈希文件」的经典方案。现代工程里，哈希索引以更丰富的形态存在：

- **MySQL Adaptive Hash Index（AHI）**：InnoDB 为热点页自动建的哈希索引——查热点免走 B+ 树。
- **内存哈希表**：缓冲池、连接哈希（第 11 章哈希连接）用内存哈希，无磁盘桶概念。
- **一致性哈希**：分布式存储把「哈希」用于分片路由（第 17 章）——动态扩容的现代主角。

**核心要点：动态哈希的思想（按需扩容、避免全量重哈希）延续到了分布式系统。** 一致性哈希是「可扩展哈希」在集群维度上的继承者——第 17 章会看到它如何解决「增删节点只影响少量数据」。

## 6 动态哈希的数值算例与术语速查

**把一个可扩展哈希的扩桶过程走一遍，数字直观。** 设哈希值 6 位，初始全局深度 $d=1$，目录 2 项，指向桶 A（$d_A=1$）。

- **桶 A 满**：需分裂。$d_A = d = 1$，所以**目录翻倍**到 4 项（$d \to 2$），A 的地址从「0*」细化成「00*」与「01*」两个桶，目录 00、01 指向它们，10、11 指向未分裂的桶 B。
- **桶 B 满**：$d_B = 1 < d = 2$，**只需局部分裂**——目录不动，B 细化成「10*」与「11*」两个桶，目录 10、11 分别指向它们。
- **查找**：任何时刻，算哈希取 $d$ 位定位目录项，读对应桶——**恒为 1 次 I/O**。

**数值算例：线性哈希的轮转分裂** 设初始 $n=4$ 个桶，哈希 $h_0(K)=K \bmod 4$，轮转指针 $i=0$。

- 当负载超过阈值，分裂桶 0：把桶 0 的记录用 $h_1(K)=K \bmod 8$ 重分布到桶 0 与桶 4。
- 指针移到 1，下次分裂桶 1（到桶 5）……一轮后 $n=8$，$h_0$ 升级为 $h_1$。
- 查找一个键：先试 $h_0$，若桶号 < 指针则已分裂，改用 $h_1$ 定位——**1-2 次 I/O**。

**辨析｜易错点：** 可扩展哈希的「目录翻倍」与线性哈希的「轮转分裂」触发条件完全不同：前者因**单桶满 + 深度到顶**，后者因**全局负载阈值**。别把「满桶分裂」套到线性哈希上——线性哈希的桶分裂与「满不满」无关。

<span class="marginnote">动态哈希与 B+ 树在「扩容」上是两种哲学：B+ 树<strong>分裂发生在写路径上、当场分裂</strong>；动态哈希（尤其线性哈希）<strong>把扩容摊到后台/按轮次渐进完成</strong>——后者在分布式场景更吃香，因为「一次性全量重哈希」的成本被摊平了。这正是一致性哈希的动机。</span>

### 术语速查

| 术语 | 含义 |
| --- | --- |
| 全局深度 d | 目录指针数组的位数 |
| 局部深度 d_i | 桶内共享哈希前缀位数 |
| 桶目录 | 可扩展哈希的指针数组 |
| 轮转指针 | 线性哈希的下一个分裂桶号 |
| 分裂 | 桶记录重分布到两个新桶 |
| 一致性哈希 | 分布式场景的动态哈希继承者 |

## 7 小结

- **可扩展哈希**：目录 + 桶，满桶分裂，全局深度/局部深度管理，查找恒定 1 I/O。
- **线性哈希**：轮转指针顺序分裂，无目录，实现简单、扩容可预测。
- 动态哈希让桶数**随数据生长**，避免静态哈希的溢出退化。
- 可扩展哈希贵在目录空间、线性哈希贵在溢出未及时处理。
- 现代形态：AHI、内存哈希、**一致性哈希**（分布式维度）。
