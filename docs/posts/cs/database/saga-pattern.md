## 为什么从 Saga 开始

TCC 需要每个参与者实现 Try/Confirm/Cancel 三个操作，业务侵入大。**Saga 模式**走另一条路：**把长事务拆成一串本地事务**，每步有对应的**补偿事务（compensating transaction）**——正向执行到某步失败时，**逆序执行补偿**回到起点。Saga 不需要「预留」，只用「本地事务 + 补偿」，业务侵入更小。这一节讲 Saga 的两种编排方式——**编排式（orchestration）**与**协同式（choreography）**——以及 Saga 的隔离性弱点。Saga 是微服务长事务的主流模式。

## 1 Saga 的基本结构

**Saga**：一组本地事务 $T_1, T_2, \dots, T_n$ 顺序执行，每个 $T_i$ 配补偿 $C_i$：

- **正向**：$T_1 \to T_2 \to \dots \to T_n$——全部成功则 Saga 完成。
- **回滚**：若 $T_k$ 失败，执行 $C_{k-1} \to \dots \to C_1$——**逆序补偿**已成功的事务。

**核心要点：Saga 用「本地事务 + 补偿」代替「分布式原子提交」。** 每一步都是独立的本地事务（有自己的 ACID），但**整个 Saga 不是原子的**——中间步骤的提交对外可见，失败时靠补偿「业务上回滚」。

**对比 TCC**：

| 维度 | TCC | Saga |
| --- | --- | --- |
| 资源处理 | **Try 预留** | 直接执行本地事务 |
| 回滚方式 | Cancel（释放预留） | **补偿事务 C_i** |
| 隔离性 | 预留提供弱隔离 | **无隔离**（需业务容忍） |
| 业务侵入 | 每个操作拆三份 | 每个操作 + 一个补偿 |

**辨析｜易错点：** **补偿 ≠ 回滚**。数据库回滚恢复旧值；Saga 的补偿是**新的业务操作**（如「取消订单」补偿「创建订单」）——它让业务状态「逻辑上回到起点」，但不保证「物理旧值」。补偿必须**幂等**（重试安全）。

## 2 编排式 Saga（Orchestration）

**编排式（orchestration）**：一个**中央编排器（orchestrator）**负责调度所有步骤：

```
编排器（Orchestrator）
  ├─ 调用「订单服务」创建订单（T1）
  ├─ 调用「扣款服务」扣款（T2）
  ├─ 调用「通知服务」发送确认（T3）
  └─ 任一步失败 → 逆序触发补偿 C_{i-1} … C_1，回到起点
```

**优点**：

- **流程集中**：编排器一目了然，便于管理与监控。
- **故障处理集中**：补偿逻辑在编排器，各服务无需知道 Saga 全局。
- **依赖清晰**：服务间无直接依赖（都听编排器）。

**缺点**：

- **编排器是单点**：编排器故障 = 流程停摆（需编排器高可用 + 持久化状态）。
- **中心化耦合**：新增步骤要改编排器。

**核心要点：编排式 = 中央指挥。** 它把 Saga 的控制流集中在一个角色上——简单可控，但编排器成为关键路径。

## 3 协同式 Saga（Choreography）

**协同式（choreography）**：**没有中央编排器**——每个服务完成本地事务后，**发布事件**，下一个服务**订阅事件**继续执行：

```
订单服务  ──发布「订单已创建」──▶  扣款服务  ──发布「已扣款」──▶  通知服务
  (T1)                              (T2)                          (T3)
  失败则发「订单创建失败」事件，由前序服务自行补偿
```

**优点**：

- **无单点**：没有编排器，无中心瓶颈。
- **解耦**：服务只关心「自己负责的事件」，新增服务无需改他人。
- **天然异步**：事件驱动，吞吐高。

**缺点**：

- **流程不透明**：整个 Saga 的流程分散在事件链里，**难以追踪**。
- **补偿难编排**：跨服务的补偿顺序隐含在事件里，出错难排查。
- **循环依赖风险**：事件链可能形成循环。

**公式解析：两种模式的依赖结构**

$$
\text{编排式：依赖图} = \text{星型（所有服务 → 编排器）}, \qquad
\text{协同式：依赖图} = \text{链型（服务 → 服务 → 服务）}
$$

- **第一步，编排式星型**：所有调用经编排器——中心依赖，控制集中。
- **第二步，协同式链型**：事件按顺序流转——无中心，但链路长。
- **第三步，故障影响**：星型故障在中心（编排器）；链型故障在断点（某服务）。
- **第四步，选择**：流程简单、要可观测 → 编排式；服务多、要解耦 → 协同式。

## 4 Saga 的隔离性问题

**Saga 没有隔离性**（无数据库级隔离保证）——中间步骤的提交对其他事务可见。后果：

- **脏读**：Saga 进行中，外部看到「部分完成」的状态。
- **丢失更新**：补偿与并发操作竞争，可能覆盖。

**缓解手段**：

- **语义锁（semantic lock）**：业务状态机加「进行中」标记，其他操作等待/拒绝。
- **补偿时校验**：补偿前检查「状态是否仍可补偿」。
- **幂等保证**：所有操作与补偿幂等，重试安全。

**核心要点：Saga 的隔离性要靠**业务设计**补偿。** 它放弃了数据库级隔离，换取「不持锁、可扩展」——业务要能容忍中间状态，并用「语义锁 + 幂等」自我保护。

**连接点：** Saga 与第 18 章「最终一致性」直接对应——Saga 是最终一致性的**应用层实现**。它放弃「线性一致/原子提交」，换取「不阻塞 + 可用」，正是 CAP 取舍在事务层面的体现（第 18 章会系统化这个谱系）。

## 5 小结

- Saga：**本地事务链 + 逆序补偿**；非原子，靠业务补偿达最终一致。
- **编排式**：中央编排器调度，流程集中、故障集中，但编排器是单点。
- **协同式**：事件链驱动，无中心、解耦，但流程不透明、难追踪。
- 补偿 ≠ 回滚：补偿是新业务操作，必须**幂等**。
- Saga 无隔离性——靠**语义锁 + 幂等 + 补偿校验**弥补。
