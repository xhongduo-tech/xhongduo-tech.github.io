## 为什么从数据字典开始

数据库怎么知道「有哪些表、每张表有哪些列、谁有权限读哪张表」？——这些**关于数据的数据**，就是**元数据（metadata）**，存放在**数据字典 / 系统目录（system catalog）**里。系统目录是数据库的「自我意识」：优化器靠它选计划，权限系统靠它做授权，查询处理器靠它展开列名。这一节把系统目录的内容、存储方式与常见实现讲透——**它是连接「用户表」与「数据库内部机制」的桥梁**。

## 1 什么是系统目录

**系统目录（system catalog）**：DBMS 维护的元数据集合，记录关于数据库本身的信息。对用户而言，它是一组**只读的系统表**；对 DBMS 而言，它是自身运转的「配置中心」。

**核心要点：系统目录本身也是表。** 它用和普通表一样的文件与块组织存储，但由系统维护、只读暴露。因此——**目录也要能被索引、被缓存、被权限控制**，就像一个「特殊用户表」。这就构成了自指：用表管理表。

<span class="marginnote">SQL 标准提供 INFORMATION_SCHEMA 视图来查询目录，如 TABLES、COLUMNS；PostgreSQL 还有 pg_catalog（pg_tables），MySQL 有 SHOW TABLES。你会发现「查询元数据」的语法与普通查询完全一致——因为目录就是表。</span>

## 2 系统目录存什么

系统目录记录的信息可分为几类：

| 类别 | 内容 | 示例 |
| --- | --- | --- |
| 关系信息 | 表名、创建者、创建时间 | `(student, alice, 2026-08-07)` |
| 属性信息 | 列名、类型、长度、顺序、默认值 | `student(s_id, varchar(20), 非空, 默认 NULL)` |
| 约束信息 | 主码、外码、唯一、CHECK | `PRIMARY KEY (s_id)` |
| 索引信息 | 索引名、索引列、唯一性 | `idx_sname ON student(s_name)` |
| 视图信息 | 视图名、视图定义 | `v_honors AS SELECT * FROM student WHERE ...` |
| 权限信息 | 用户对对象的授权 | `GRANT SELECT ON student TO alice` |
| 统计信息 | 表行数、列基数、直方图 | `nrows=10000, n_distinct(s_name)=...` |

**统计信息**尤其关键：第 12 章代价优化器用表行数、列基数、直方图估算选择率——这些数据正是从系统目录读取的。**没有统计信息，基于代价的优化就无从谈起**。

## 3 数据字典的历史与两种实现

**数据字典（data dictionary）**的概念早于关系数据库：它最初是独立的「数据管理系统」——记录企业全部数据资产的元数据，独立于具体 DBMS。演化出两种定位：

- **被动数据字典**：由 DBA 手工维护，只做文档，不参与系统运行（已基本被淘汰）。
- **主动系统目录**：DBMS 自动维护、自动更新，是系统运行的一部分——**现代数据库全是主动式**。

**辨析｜易错点：** 「数据字典」与「系统目录」在日常语境常混用，但严格说：系统目录是 DBMS 内部的元数据表，数据字典更偏向「企业级数据管理文档」。在《数据库系统概念》里两者指同一件事，就是系统目录。

## 4 公式解析：目录中表的自描述

系统目录的信息量有一个有趣的**闭合性**：目录本身描述所有表，包括目录自身。

$$
\text{Catalog} \ni \text{tables} \ni (\text{columns}) \ni \cdots \ni \text{Catalog}
$$

- **第一步，目录记录所有表**：记录表的 TABLES 表里也有一行描述 TABLES 自己。
- **第二步，列信息记录所有列**：COLUMNS 表描述每张表的列，包括 COLUMNS 表的列。
- **第三步，自指闭合**：这种「描述自身的表」结构是元数据系统必然的自指性——就像编译器要能编译自己（可参考第三级《编译原理》里的自举）。
- **第四步，工程意义**：因为目录自包含，DBA 可以只靠目录查询就了解整个库的结构，无需外挂文档。

## 5 系统目录的实际使用

在真实数据库里，系统目录支撑着最日常的操作：

每条 SQL 从解析到执行都要查目录多次——它是查询的「字典」。

**工程要点：**

- **优化器**：读统计信息决定扫描还是走索引、连接顺序如何排。
- **权限系统**：读授权表判断当前用户能否执行某操作。
- **DDL 实现**：CREATE TABLE 实际是「往系统目录插一行」。
- **查询处理器**：执行时查询目录展开列名。

**连接点：** 系统目录是第 12 章查询优化的「情报来源」。优化器选计划前要读行数、基数、直方图——**没有准确的统计信息，再聪明的优化算法也是瞎猜**。统计信息的采集与更新策略（何时 ANALYZE、采样多少），是数据库性能调优的日常。

## 6 目录查询与统计信息的数值算例

**看看系统目录如何被日常查询与优化器使用。** 一条 `SELECT * FROM student WHERE s_name = '张三'` 的执行背后：

- **解析阶段**：查询处理器查目录——student 表存在吗？s_name 列存在吗？类型是什么？（2-3 次目录读）
- **优化阶段**：查统计信息——student 有多少行？s_name 的基数是多少？有无索引？（2-3 次目录读）
- **执行阶段**：按优化器选择的计划扫描或走索引；若目录里有 `s_name` 索引记录，用索引。
- **合计**：一条简单查询至少查目录 5-6 次——**目录访问是查询代价的固定底数**，所以目录本身也必须被缓存。

**数值算例：统计信息过期导致的次优计划** 设 `student` 表实际有 1 亿行，但目录里 `nrows=10000`（过期）。

- 优化器以为表只有 1 万行，选择全表扫描而非索引——实际扫 1 亿行，查询慢上千倍。
- 根本原因：统计信息是「某时刻快照」，与真实数据脱节——需要周期性 ANALYZE（第 12 章）。
- 教训：**目录的准确性直接决定优化器智商**。这就是为什么 DBA 的例行工作里有「更新统计信息」。

**辨析｜易错点：** 系统目录里的统计信息是**近似快照**，不是实时值。查询目录拿到 `nrows` 时，它可能已是几小时前的数字。**统计信息「够新」比「精确」更重要**——采样 + 定期刷新是常态做法。

<span class="marginnote">目录的自指性有一个工程后果：<strong>目录表也要建索引、也参与缓存替换</strong>（第 9 章缓冲区管理）。PostgreSQL 把系统表当普通表管理，因此「查 pg_class 很慢」在极端场景也会成为性能问题——元数据本身也需要性能优化，这是数据库「自我管理」的趣味所在。</span>

### 术语速查

| 术语 | 含义 |
| --- | --- |
| 元数据 | 关于数据的数据 |
| 系统目录 | DBMS 维护的元数据表集合 |
| 数据字典 | 企业级元数据文档（广义） |
| INFORMATION_SCHEMA | SQL 标准目录视图 |
| 统计信息 | 行数、基数、直方图 |
| 主动/被动 | 自动维护 / 手工维护 |

**连接点：** 目录是第 12 章优化器的「情报来源」，也是第 3 章 DDL（CREATE TABLE 即插目录）的实现基础。读到这里，你已把「数据库如何认识自己」串起来了。

## 7 小结

- **系统目录**是数据库的元数据中枢：表、列、约束、索引、权限、统计全在此。
- 目录**本身也是表**，用普通文件组织存储，只读暴露，支撑自指结构。
- SQL 通过 INFORMATION_SCHEMA 等标准视图查询目录。
- 两类实现：被动数据字典（手工，已淘汰）与**主动系统目录**（自动维护，现代标配）。
- 目录的**统计信息**是代价优化器的输入——没有它优化无从谈起。
