## 为什么从关系数据库开始

上一节讲了数据库语言的 DDL 与 DML。但语言总要落在一种**数据模型**上，今天占统治地位的就是**关系模型**——把一切数据组织成"表"。1970 年科德在一篇里程碑论文中提出它，当时连作者自己也说不准能否工程实现；半个多世纪后，MySQL、PostgreSQL、Oracle、SQL Server 几乎全是关系数据库。这一节把"关系数据库"五个字拆开：**表**承载数据，**DML** 操作数据，**数据库设计**决定数据如何组织得既正确又不冗余。

## 1 关系：把数据装进表

**关系（relation）**：一张二维表。**元组（tuple）**：表中的一行。**属性（attribute）**：表中的一列。

例如教师关系：

| ID | name | dept_name | salary |
| --- | --- | --- | --- |
| 10101 | Srinivasan | CS | 65000 |
| 12121 | Wu | Finance | 90000 |
| 15151 | Mozart | Music | 40000 |

这里每一列都有**定义域（domain）**：`ID` 是定长字符串，`salary` 是数值。每个元组在各属性上的取值，必须落在各定义域的笛卡儿积里——这正是上一篇那个公式的现实版。<span class="marginnote">术语混用提醒：教科书说"关系/元组/属性"，日常口语说"表/行/列"，说的是同一事物。写严谨的论文时用前者。</span>

一个数据库里通常有多张表，表与表靠取值相同的属性"勾连"。比如再建一张系别表：

| dept_name | building | budget |
| --- | --- | --- |
| CS | Taylor | 100000 |
| Finance | Painter | 120000 |

`instructor` 的 `dept_name` 与 `department` 的 `dept_name` 取值来自同一个域，于是两条关系的元组可以按系名对上——这是"教师属于某个系"的存储表达，也正是第 2 章**外码（foreign key）** 概念的前身。

**关系是元组的集合，不是多重集**：一张关系里不允许出现两行完全相同的元组，行的先后顺序也无关紧要。这与第一级《集合》的"互异性、无序性"完全一致。但 SQL 为了实用允许重复行、允许排序，这造成理论与 SQL 的一处著名差异，第 2 章《关系模型》会专门辨析。

## 2 数据操纵：在关系上做运算

关系数据库的 DML 遵循**关系运算**：一个操作吃进一个或几个关系，吐出一个新关系。这保证"查询的结果仍是关系"，可以继续参与下一次运算——这叫**关系的闭包性（closure）**。<span class="marginnote">闭包性是关系代数的命根子：正因为"运算的结果还是关系"，才能把简单查询嵌套成复杂查询。它与第一级数学里"整数集对加法封闭"是同一个词、同一个思想。</span>

最基本的两个关系运算是**选择（selection）** 与**投影（projection）**：前者选行，后者选列。用 SQL 表达：

```sql
-- 选出 CS 系的教师（选行）
SELECT * FROM instructor WHERE dept_name = 'CS';
-- 只看 name 和 salary 两列（选列）
SELECT name, salary FROM instructor;
```

关系代数（第 2 章）把这套运算严格化，而 SQL 是它的"用户友好语法"。理解了"查询 = 关系运算"，就抓住了关系数据库的灵魂。

查询之外，DML 还要能改数据。SQL 的三种修改操作也都作用在"关系"上：

```sql
-- 插入：向关系中加入新元组
INSERT INTO instructor VALUES ('32343', 'El Said', 'History', 60000);
-- 修改：按条件更新若干元组的属性值
UPDATE instructor SET salary = salary * 1.05 WHERE dept_name = 'CS';
-- 删除：按条件移除若干元组
DELETE FROM instructor WHERE ID = '12121';
```

注意它们都带一个共同特征：**修改以元组集合为对象**。`UPDATE ... WHERE ...` 可以同时更新任意多条满足条件的记录，而不是"逐行手动改"——这正体现了"关系"作为操作单元的思路。

## 3 数据库设计：先画蓝图，再建表

**数据库设计（database design）**：决定数据库**逻辑结构**的过程——建哪些关系、每个关系有哪些属性、如何避免冗余。设计过程一般分四步：

1. **需求分析**：弄清用户需要什么数据、什么操作。
2. **概念设计**：用**实体-联系（ER）模型**画出高层蓝图：有哪些实体（如"教师""系"）、它们如何联系（如"教师属于某个系"）。<span class="marginnote">ER 模型是"设计师的草图"：不关心怎么存，只关心现实世界的结构。本专题第二篇《数据库设计》会系统展开 ER 图符号与转换规则。</span>
3. **逻辑设计**：把 ER 图翻译成关系模式，得到具体的表结构。
4. **物理设计**：决定索引、文件组织等物理细节。

为什么设计如此重要？因为设计不好会带来**冗余（redundancy）** 与随之而来的**异常（anomaly）**。看一张把所有信息硬塞进一行的坏表：

| ID | name | dept_name | dept_building |
| --- | --- | --- | --- |
| 10101 | Srinivasan | CS | Taylor |
| 12121 | Wu | Finance | Painter |

`dept_building` 被冗余存储：如果 Finance 系搬进新楼，得去更新每一行 Finance 系教师的记录；漏改一行，数据库就**不一致**了。

**辨析｜易错点：** 初学者常以为"信息放同一张表最省事"，恰恰相反——冗余会引发三个典型异常：**更新异常**（改一处漏一处，数据不一致）、**插入异常**（没有学生就无法记录某课程的信息）、**删除异常**（删除最后一位学生连带删掉课程信息）。第 8 章《规范化理论》会教我们通过"分解"消除这些异常，那是数据库设计最核心的技巧。

## 4 公式解析：选择运算 σ

关系代数以集合为对象，把"选行"写成一个严格的数学定义。设 $r$ 是一个关系，$P$ 是作用于元组的谓词（条件），**选择运算**定义为：

$$\sigma_{P}(r) = \{ t \mid t \in r \wedge P(t) \}$$

拆成三步理解：

- **第一步，读集合构造式**：$\{ t \mid t \in r \wedge P(t) \}$ 表示"从 $r$ 中挑出所有元组 $t$，要求『$t$ 属于 $r$』且『$P(t)$ 为真』"。这正是第一级《集合》里描述法 $\{x \mid x \text{ 满足某性质}\}$ 的翻版。
- **第二步，看懂 $\wedge$**：它是逻辑"且"。$t \in r$ 保证我们只在 $r$ 内部挑，$P(t)$ 保证挑出来的必符合条件，两者缺一不可。若去掉 $t \in r$，表达式可能捡到"不存在的元组"。
- **第三步，对应到 SQL**：$\sigma_{\mathrm{dept\_name} = 'CS'}(instructor)$ 就是 `SELECT * FROM instructor WHERE dept_name = 'CS'`。WHERE 子句正是谓词 $P$ 的 SQL 语法糖。

关系的闭包性在这个定义里一目了然：$\sigma_P(r)$ 的结果本身仍是一个关系（元组的集合），所以可以对它继续做 $\sigma$、做投影、做连接——运算可以无限嵌套，直到得到想要的答案。

与选择"选行"相对，**投影（projection）** 是"选列"。它从每个元组里抽出一部分属性，并去重：

$$\Pi_{A_1, A_2, \dots, A_k}(r)$$

这里 $A_1, \dots, A_k$ 是要保留的属性名。投影是"抽出子元组后去重"：因为关系是集合，重复的投影结果只保留一份。`SELECT DISTINCT dept_name FROM instructor` 就是投影的 SQL 形态。把选择与投影组合起来——先 $\sigma$ 选行、再 $\Pi$ 选列——就能用两个小运算拼出绝大多数简单查询，这正是第 2 章关系代数"基本运算"的开端。

## 5 小结

- **关系 = 表，元组 = 行，属性 = 列**；关系是元组的**集合**，无重复、无序。
- 关系数据库的 DML 基于**关系运算**，具有**闭包性**：运算结果仍是关系。
- 数据库设计四步：**需求分析 → 概念设计（ER）→ 逻辑设计 → 物理设计**；设计不佳带来**冗余与更新/插入/删除异常**。
- 选择运算 $\sigma_{P}(r) = \{ t \mid t \in r \wedge P(t) \}$ 是"选行"，对应 SQL 的 WHERE。
