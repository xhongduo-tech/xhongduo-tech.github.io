## 为什么从历史开始

前面几节讲完了「数据库是什么」，这一节回答「数据库从哪里来」。历史不是背年份的负担，而是理解现状的捷径：**关系模型为什么赢了？NoSQL 为什么出现？为什么今天云数据库、向量数据库这么火？** 这些问题只有回到历史语境里才有答案。更重要的是，数据库的发展史与硬件成本、与「数据规模爆炸」这两条曲线紧密纠缠——理解了这条脉络，你就知道数据库不是一劳永逸的发明，而是不断被新需求推着演化的系统。

这条历史线还能把你带到「从极限到大模型」主线的最近端：**大模型时代的数据基建，正是数据库历史的最新一章**——向量数据库、数据湖仓、RAG 检索管线，都在延续「数据变多→存储与查询方式必须跟着变」的老剧本。<span class="marginnote">把数据库历史压缩成一句话就是：<strong>每次「数据形态或规模发生质变」，就会催生新一代存储与查询范式</strong>。从层次模型到关系模型、从关系到 NoSQL、从 NoSQL 到向量检索，莫不如此。</span>

## 1 前关系时代：文件与第一代 DBMS

数据库的起点不是数据库，而是**文件**。1950–1960 年代，数据以文件形式存放在磁盘上，每个应用程序自己读写文件、自己管理格式。文件方式的问题我们在第一课《从文件系统到 DBMS》已经讲过：冗余、不一致、数据孤立、程序与数据强耦合。

**1960 年代，第一代 DBMS 诞生**，标志是两种「导航式」数据模型：

- **层次模型（hierarchical model）**：用**树**组织数据。IBM 的 IMS（1968 年发布）是代表，最初为美国阿波罗计划的物料清单设计。<span class="marginnote">IMS 的「树」意味着一个节点只能有一个父节点——描述「一个学生选多门课、一门课被多个学生选」这样的多对多关系时，层次模型要笨拙地复制数据。这个「表达力缺口」是关系模型最好的切入点。</span>
- **网状模型（network model）**：用**图**组织数据。CODASYL 的 DBTG 规范（1971）是代表，记录之间可以用任意「系」（set）相连，表达能力比层次模型强，但操作要靠程序员手动「导航」指针，极其繁琐。

这两个模型并非纸面构想，而是实实在在的商业系统：除了 IBM 的 IMS，还有 IDMS、TOTAL 等网状模型产品在金融、航空、制造领域广泛应用。它们能跑起来，靠的是**应用开发者的高度纪律**——每个查询都要手工设计遍历路径，数据结构一改，全部导航代码跟着重写。这种「数据被锁在程序里」的状态，正是后来关系模型要打破的东西。<span class="marginnote">今天你很难见到还在用 IMS 的新系统，但它没有完全消失——不少银行核心系统至今仍跑着基于层次模型思想的旧系统。学习历史的意义之一，就是看懂这些「活化石」为什么还能存在。</span>

**辨析｜易错点：第一代模型不是「不会做」，而是「用起来太重」。** 层次与网状模型表达能力并不弱，它们的失败在于**数据操作负担全压在用户身上**：查询要写「沿哪条路径走」的导航代码，改数据要手动维护指针。这个「把复杂度留给用户」的缺陷，正是关系模型革命要解决的核心矛盾。

## 2 关系革命：1970 年代

**1970 年，埃德加 · 科德（E. F. Codd）发表《大型共享数据银行的关系模型》（A Relational Model of Data for Large Shared Data Banks）**，提出用一张张**表**（关系）组织数据，用**关系代数**与**关系演算**做查询。这个想法在当时近乎激进：用集合论把数据操作变成「声明要什么」，而不是「导航怎么做」。

科德的论文之所以是「革命」而非「改进」，在于它换了一个层面解决问题：第一代模型在「怎么遍历」上做文章，科德则在「声明结果是什么」上做文章——至于「怎么算出结果」，交给系统去优化。**「把困难从用户身上转移到系统身上」，这是关系模型最深远的方法论遗产**，也是后面查询优化（第 12 章）的哲学前提。

关系模型的胜利不是一蹴而就的。1970 年代是它的「孵化期」，两个关键原型验证了可行性：

- **System R**（IBM，1974–1979）：第一个完整的关系 DBMS 原型，发明了 **SQL**、事务、锁与查询优化——今天我们用的 SQL 和事务理论，源头都在这里。
- **Ingres**（加州大学伯克利，1974–）：另一个重要原型，强调查询语言与视图，其团队后来衍生出 PostgreSQL。

为什么关系模型用了整整十年才从论文变成产品？答案藏在硬件里，见第 5 节的公式解析。<span class="marginnote">科德因此获得 1981 年图灵奖。有意思的是，他晚年对关系模型的「革命不够彻底」颇有微词，主张更多依赖逻辑语言——但历史已证明，关系模型和 SQL 的简单实用赢得了市场。</span>

## 3 商业化与普及：1980–1990 年代

1980 年代，关系数据库走出实验室，进入商业市场：

- **1980 年代初**：Oracle、IBM DB2、SQL Server 相继商用。关系模型靠「易用、标准、有数学基础」横扫市场，层次与网状模型黯然退场。
- **1986 年**：SQL 成为 ANSI 标准（SQL-86），此后历经 SQL-92、SQL:1999、SQL:2003……语言的标准化是关系数据库「一统江湖」的关键——应用不必为每个厂商重写。
- **1990 年代**：数据库进入「应用深化」期。**决策支持（decision support）** 兴起，数据仓库、OLAP（联机分析处理）成为热点；WWW 的爆发让三层架构成为主流，数据库从「企业内部系统」变成「每台 Web 服务器背后的引擎」。

这个时期也有一支插曲：1980 年代末面向对象数据库（OODBMS）试图用「对象」取代「关系」，最终市场证明它无法撼动关系模型——但对象思想没有消失，而是以**对象-关系数据库**（如 PostgreSQL 的自定义类型）的形式融入了主流。<span class="marginnote">PostgreSQL 的名字已经预告了它的身世：Post-Ingres，即 Ingres 项目的后继者。它后来以「最先进的开源关系数据库」著称，自定义类型、JSONB 等能力都带着对象-关系时代的基因。</span>

为什么关系模型能「兼容并吞」对象思想，而反过来不行？因为**关系模型的抽象更接近「数据本身」，对象的抽象更接近「程序的实现」**。数据是长期共享的资产，而程序会不断重写——用「程序视角」定义数据，等于让数据绑定在特定语言上。这个判断，到今天仍是选择数据模型时最值得记住的一条。

## 4 互联网与大数据的爆发：2000 年代至今

2000 年之后，数据库史进入了「加速爆炸」阶段，几乎每几年就出现一次范式跃迁：

| 年代 | 关键事件 | 解决什么问题 |
| --- | --- | --- |
| 2000 年代 | XML 数据库、Web 应用普及 | 半结构化数据、互联网流量 |
| 2004–2008 | Google MapReduce、BigTable 论文；Hadoop 开源 | 海量数据的批处理与扩展 |
| 2009 年起 | NoSQL 运动：MongoDB、Cassandra、Redis | 高并发、灵活模式、水平扩展 |
| 2012 年 | Google Spanner 论文；NewSQL 兴起 | 分布式下的事务一致性 |
| 2013 年起 | 云数据库：Amazon Aurora、云厂商托管数据库 | 按需付费、免运维 |
| 2015 年起 | 列存数据库：ClickHouse、DuckDB；数据湖仓 | 海量数据的分析查询 |
| 2017 年起 | 向量数据库：Milvus、pgvector | 大模型嵌入向量的相似检索 |

**辨析｜易错点：NoSQL 不是「取代关系数据库」，而是「为它顾不上的场景补位」。** NoSQL 放弃事务与严格模式，换来的是水平扩展与灵活——它适合社交信息流、推荐、缓存这类「可以容忍最终一致」的场景；而银行转账、订单库存这类强一致场景，关系数据库至今无可替代。**NewSQL 的野心正是「既要关系模型的事务，又要 NoSQL 的扩展」**，Google Spanner 是这一路线的代表作。<span class="marginnote">数据库历史最深刻的教训：<strong>没有银弹</strong>。每一次新范式都在「一致性、可用性、扩展性」三角中重新取舍，而不是全都要。第四篇《事务》、第五篇《分布式数据库》会把这个取舍讲透。</span>

同一时期，分析型负载与事务型负载也彻底分家。**OLTP（联机事务处理）** 要的是「快而准地处理每一笔交易」；**OLAP（联机分析处理）** 要的是「在海量历史数据上做聚合分析」。前者沿用行式存储的关系数据库，后者催生了**数据仓库（data warehouse）**、列式存储与各种分析引擎。<span class="marginnote">「行存 vs 列存」是数据库史上第二次大的「物理存储革命」——第一次是从文件到表，第二次是从行到列。同一个 `SELECT SUM(salary) FROM instructor`，列存可能比行存快一个数量级，原因在第 20 章《列存与 OLAP》揭晓。</span>今天的数据湖仓（lakehouse）试图把「数据仓库的治理」与「数据湖的廉价存储」统一起来，正是这条分析主线的延续。

把视线拉回最近十年，**大模型把数据库带入了新的章节**：向量数据库为嵌入向量提供相似性检索，成为 RAG 检索管线的底层存储；云数据库让「开一个数据库」从买硬件变成发一条命令。**数据库的每一次演化，都是对「数据形态与规模变化」的回应**——这一规律从 1960 年代到今天从未改变。你甚至可以做一个大胆预测：**下一个十年的数据库史，大概率就写在「大模型如何重塑存储与检索」这一章里**——这也正是本专题第五篇《NoSQL 与 NewSQL》、第六篇《列存与 OLAP》要抵达的地方。

## 5 理论主线：一门学科的四根支柱

历史课还有一个任务：把散落的年代串成学科的骨架。今天的数据库课程，无论哪本教材，都围绕**四根支柱**展开，它们恰好都孕育于 1970 年代那场关系革命：

- **完整性约束（integrity constraints）**：如何保证数据「说得通」——主码唯一、外码引用存在、工资不能为负。关系模型 1970 年就明确提出这一需求，对应本专题第 8 章《规范化理论》。
- **查询语言与查询处理（query processing）**：如何「声明要什么」并被高效执行。SQL 与关系代数诞生于 System R 与 Ingres 的研究，对应第 2 章与第三篇《查询引擎》。
- **事务与并发控制（transactions & concurrency）**：多个用户同时读写时，如何保证结果与「逐个执行」等价。对应第四篇第 13–14 章。
- **故障恢复（recovery）**：系统崩溃后，如何把数据库还原到一致状态。对应第 15 章《恢复系统》。

这四根支柱的诞生有一个共同背景：**数据从「单个程序的私有财产」变成「许多程序共享的企业资产」**——一旦共享，就必须约束、必须优化、必须并发、必须可恢复。<span class="marginnote">今天分布式数据库的所有难题——分布式事务、全局一致性、复制——都是这四根支柱在「多台机器」上的延伸。学完本专题第二、三、四篇，你会认出：<strong>单机上的每根支柱，在分布式里都有一座更陡的山</strong>。</span>

**辨析｜易错点：数据库史 ≠ SQL 语法史。** 学历史时，别把注意力全放在「哪年发布了哪个标准」上。标准只是「表」，真正重要的是四根支柱的**演化逻辑**——为什么约束先于优化被提出、为什么并发问题直到关系模型普及才成为显学、为什么「共享数据」是这一切的共同起因。抓主线，比背年份有用得多。

## 6 公式解析：摩尔定律与关系模型的「时差」

关系模型 1970 年提出，却在 1980 年代才商用——为什么滞后十年？答案不在理论，而在硬件。科德的关系模型需要**大量内存与 CPU**：一次连接、一次排序都要把数据搬进内存计算，这在 1970 年代初的硬件上是难以接受的奢侈。

**摩尔定律（Moore's law）**：集成电路上可容纳的晶体管数目，大约每 18–24 个月翻一番：

$$N(t) = N_0 \cdot 2^{t/T}$$

拆成三步理解：

- **第一步，看懂公式**：$N_0$ 是初始时刻的晶体管数，$T$ 是翻倍周期（约 18–24 个月），$t$ 是经过的时间，$N(t)$ 是 $t$ 时刻的晶体管数。每过一个 $T$，指数部分 $2^{t/T}$ 就翻一番，于是 $N(t)$ 翻倍。
- **第二步，代入估算**：若 1970 年一块芯片约含 2000 个晶体管（$N_0 = 2000$），取 $T = 2$ 年，那么 10 年后（$t = 10$）：$$N(10) = 2000 \times 2^{5} = 2000 \times 32 = 64000$$ 也就是 1980 年的芯片集成度约为 1970 年的 32 倍——内存与 CPU 性能的同步增长，恰好把关系模型的「计算成本」降到了可接受的范围。
- **第三步，读结论**：**理论先于硬件，是技术史上最平常的事。** 关系模型 1970 年就绪，却在 1980 年代才普及，因为要等摩尔定律把硬件「喂饱」。这个「时差」今天仍在重演——大模型 2017 年提出 Transformer 架构，真正大规模应用却要等 GPU 与数据的爆发。<span class="marginnote">同一规律也解释了为什么列存数据库、向量数据库都「起了大早、赶了晚集」：存储与查询范式的创新，永远受制于当时的硬件价格曲线。</span>

摩尔定律还解释了另一个现象：**为什么数据库功能越来越多、价格越来越便宜**。硬件每 18 个月翻倍，意味着同样价格能买到两倍性能——于是数据库敢于承担更重的查询优化、更细粒度的并发控制，把「系统复杂度」内化，把「用户使用复杂度」降低。这个「硬件换易用」的交换，是数据库史最隐蔽的主线。

## 7 小结

- 第一代 DBMS：**层次模型（IMS）与网状模型（CODASYL）**，导航式操作、复杂度留给用户。
- **1970 年科德提出关系模型**，System R 与 Ingres 在 1970 年代验证了 SQL 与事务的可行性。
- **1980–1990 年代**关系数据库商业化、SQL 标准化，数据库进入数据仓库与 Web 时代。
- **2000 年代至今**：NoSQL、NewSQL、云数据库、列存、向量数据库接连登场——每次数据形态质变都催生新范式。
- 数据库学科的四根支柱：**完整性约束、查询处理、事务并发、故障恢复**，都源于「数据成为共享资产」。
- **OLTP 与 OLAP 分家**催生了数据仓库与列存；对象思想最终以**对象-关系数据库**形式融入关系模型。
- **摩尔定律** $N(t) = N_0 \cdot 2^{t/T}$ 解释了关系模型「理论先行十年、硬件跟上才普及」的时差。
