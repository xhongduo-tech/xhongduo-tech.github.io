## 为什么从嵌套循环开始

连接（join）是关系查询最贵的运算，也是查询优化最大的战场。数据库有三大类连接算法：**嵌套循环（nested-loop）、归并连接（merge join）、哈希连接（hash join）**。这一节讲嵌套循环家族的两种形态——**朴素嵌套循环（nested-loop join, NLJ）**与**块嵌套循环（block nested-loop join, BNLJ）**。朴素版本是「理解起点」但工程几乎不用；块嵌套循环通过**块级缓存**大幅降低 I/O，是 OLTP 小表连接的主力。理解 NLJ 的代价爆炸，你就明白为什么数据库要在连接算法上绞尽脑汁。

## 1 朴素嵌套循环连接

**嵌套循环连接（nested-loop join）**：对外层关系 $r$ 的每条记录，扫描内层关系 $s$ 全部记录找匹配。

```
for each 元组 t_r in 关系 r:
    for each 元组 t_s in 关系 s:
        if t_r 与 t_s 满足连接条件:
            把 (t_r, t_s) 加入结果
```

**代价分析**：设 $r$ 为外层、$s$ 为内层，$b_r, b_s$ 为块数，$n_r, n_s$ 为记录数：

$$
T_{NLJ} = n_r \cdot b_s + b_r
$$

- 外层每扫一条记录，内层整表读一遍 $b_s$ 块——**共 $n_r b_s$ 次块读**，天文数字。

**辨析｜易错点：** $n_r = 10^6$、$b_s = 10^4$ 时，$T = 10^{10}$ 次 I/O——不可能执行。**朴素嵌套循环只适合「内层在内存」或「外层极小」**。数据库绝不直接用这个版本。

## 2 块嵌套循环连接（BNLJ）

**块嵌套循环连接（block nested-loop join）**：把外层**按块**读入缓冲区，对整块记录一起扫描内层。

```
for each 块 B_r in 关系 r:
    for each 块 B_s in 关系 s:
        for each 元组 t_r in B_r:
            for each 元组 t_s in B_s:
                if t_r 与 t_s 满足连接条件:
                    把 (t_r, t_s) 加入结果
```

**代价分析**：外层按块读，每块一次 I/O 即可扫描整块记录的匹配：

$$
T_{BNLJ} = b_r \cdot b_s + b_r
$$

**核心要点：块嵌套循环比朴素版快 $f_r$ 倍。** 朴素版每外层记录扫一遍内层表；块版每外层**块**扫一遍内层表——块含 $f_r$ 条记录，I/O 就除以 $f_r$。$b_r = 10^4$、$b_s = 10^4$ 时 $T = 10^8$ 次——仍大，但已可用（配合索引进一步降）。

**公式解析：为什么「小表做外层」**

$$
T_{BNLJ} = b_r b_s + b_r \quad \Longrightarrow \quad \text{选 } b_r \le b_s \text{ 的表做外层}
$$

- **第一步，代价看外层块数**：$b_r b_s$ 是主导项，与内外顺序无关（对称）。
- **第二步，但 $+b_r$ 项不对称**：外层多一次自己的读盘（$b_r$），内层读盘已含在 $b_r b_s$ 里。
- **第三步，结论**：外层选块数少的表——总代价略低，且**外层块的缓存复用率**更高。
- **第四步，工程实践**：优化器把**小表放外层**，配合内层索引时效果最好（下一节）。

## 3 块嵌套循环的变体

- **缓存多块外层**：若缓冲区能装 $M$ 块外层，则内层每读一次可匹配 $M$ 块外层——代价降为 $b_s \cdot \lceil b_r/M \rceil + b_r$。**内存越多越划算**。
- **索引嵌套循环**：内层改用索引查找而非全扫（下一节）。
- **内存嵌套循环**：两个表都能进内存，直接内存哈希/索引匹配。

**核心要点：BNLJ 是「内存换 I/O」的典型。** 把更多外层块缓存进缓冲池，内层表就能少读几遍——这正是缓冲池容量 $M$ 直接影响连接代价的体现。

## 4 适用场景对比

| 场景 | NLJ | BNLJ | 说明 |
| --- | --- | --- | --- |
| 内层小 | ✅ | ✅ | 内层整表常驻内存 |
| 外层极小 | ✅ | ✅ | 外层记录少 |
| 无索引大表 | ❌ | 勉强 | $b_r b_s$ 仍大 |
| 有索引内层 | 用索引版 | 用索引版 | 下一节 |
| OLTP 点查连接 | — | ✅ | 小表 + 索引 |

**辨析｜易错点：** 教科书常把「嵌套循环」与「索引嵌套循环」分开讲。**NLJ/BNLJ 是「无索引」版本**；下一节的「索引嵌套循环」用索引把内层 $b_s$ 全扫降为每次查找 $O(\log)$——那是 OLTP 的主力。命名接近、机制完全不同，别混淆。

## 5 嵌套循环的数值算例与术语速查

**把 NLJ 与 BNLJ 的代价代入真实数字。** 设 orders 100 万行（$b_r = 2$ 万块，每块 50 行）、customers 10 万行（$b_s = 2000$ 块）。

- **NLJ（orders 外层）**：$n_r b_s + b_r = 100万 \times 2000 + 2万 = 20$ 亿次块 I/O——约 55 小时，**不可执行**。
- **BNLJ（orders 外层）**：$b_r b_s + b_r = 2万 \times 2000 + 2万 = 4000$ 万次——约 11 小时，仍慢。
- **BNLJ（customers 外层）**：$2000 \times 2万 + 2000 = 4000$ 万次——**块数对称，主导项不变**，只有 $+b_r$ 项小了一点。
- **关键改进**：内层加索引（索引嵌套循环）或缓存 $M$ 块外层——见下一节。

**数值算例：缓存 $M$ 块外层的收益** 设缓冲区能装 $M = 100$ 块外层。

- BNLJ 代价降为 $b_s \cdot \lceil b_r/M \rceil + b_r = 2000 \times 200 + 2万 = 42$ 万次——**从 4000 万降到 42 万，快 95 倍**。
- **结论**：嵌套循环的性能几乎完全由「缓冲池容量 $M$」决定——**内存越多，嵌套循环越强**。
- 这也是为什么 OLTP（小表 + 大缓冲池）喜欢嵌套循环——它在「能装进内存」的场景最划算。

**辨析｜易错点：** 嵌套循环的「小表做外层」只在「**内层无索引**」时成立；一旦内层有索引（索引嵌套循环，下节），规则反转——**内层应是被驱动的大表（用索引定位），外层是任意表**。别把「无索引版的规则」套到「有索引版」上。

<span class="marginnote">嵌套循环是「<strong>内存友好型</strong>」算法的代表：它把 I/O 成本押在缓冲池上，缓存够大就快。对比哈希连接（下节）是「内存敏感型」——建哈希表必须进内存，进不去就分区。理解这个差别，是选连接算法的第一层判断。</span>

### 术语速查

| 术语 | 含义 |
| --- | --- |
| NLJ | 外层逐记录 × 内层全扫 |
| BNLJ | 外层按块缓冲 × 内层全扫 |
| 外层/内层 | 连接的两张表 |
| 块因子 | 一块能放的记录数 |
| 缓冲区 M | 外层可缓存块数 |
| 索引嵌套循环 | 内层用索引定位 |

## 6 小结

- NLJ：外层逐记录 × 内层全扫，代价 $n_r b_s + b_r$，**工程不可用**。
- BNLJ：外层**按块**缓冲 × 内层全扫，代价 $b_r b_s + b_r$，快 $f_r$ 倍。
- 小表做外层、加大缓存 $M$ 降低内层重扫次数。
- NLJ/BNLJ 是**无索引**版本；有索引内层用索引嵌套循环（下节）。
- 连接算法三大家：嵌套循环、归并、哈希——按负载选。
