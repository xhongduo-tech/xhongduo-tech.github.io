## 为什么从 MVCC 开始

基于锁的并发控制在「读读并行」处就停了——**读者与写者互斥**。但现实里读多写少，若读写都阻塞，并发度大打折扣。**多版本并发控制（MVCC, Multi-Version Concurrency Control）**换个思路：**数据存多个版本，读者读「自己事务开始时」的快照，写者写新版本**——读写互不阻塞。**快照隔离（snapshot isolation, SI）**是 MVCC 实现的典型隔离级别，也是 PostgreSQL、MySQL InnoDB、Oracle 的并发控制核心。这一节讲 MVCC 的版本管理、快照可见性规则与快照隔离的语义。

## 1 MVCC 的核心思想

**MVCC**：每个数据项维护**多个版本**，每个版本带创建/失效的**时间戳（事务号）**。

- **读者**：读取「对当前事务可见」的版本——通常是事务开始时（或最早提交）的快照。
- **写者**：创建新版本，不覆盖旧版本——**写不阻塞读，读也不阻塞写**。

**核心要点：MVCC 把「读写冲突」转化为「版本选择」。** 锁协议让读写排队；MVCC 让读写各看各的版本——**读永远看到一致快照，写永远不阻塞读者**。

<span class="marginnote">版本存储：行内多版本（PostgreSQL 在行上留版本链）、或独立版本区（Oracle 的 undo、MySQL 的 undo log）。<strong>版本数越多，读取越老快照越容易，但清理（vacuum/回收）越难</strong>——长事务是 MVCC 的敌人（它钉住旧版本）。</span>

## 2 快照隔离：读快照 + 写冲突检测

**快照隔离（snapshot isolation, SI）**是 MVCC 最常见的隔离级别，规则：

1. **读快照**：事务在**开始时刻**取得一个全库快照，所有读都从这个快照取——**读不阻塞、且总是读一致快照**。
2. **写新版本**：写操作创建新版本，**提交时才可见**。
3. **写冲突检测**：两个事务若**写了同一数据项**（并且都提交），后提交者**中止**（first-committer-wins）。

**快照隔离防住的异常**：

| 异常 | 是否防住 | 原因 |
| --- | --- | --- |
| 脏读 | ✅ | 只读已提交版本 |
| 不可重复读 | ✅ | 固定快照 |
| 幻读 | ✅ | 快照含固定行集 |
| 丢失更新 | ✅ | 写冲突检测 |

**核心要点：快照隔离防住了 SQL 标准里的「三大读异常」。** 这是它成为主流的原因——性能好（读写不互斥）且直观（每个事务看到一致快照）。

## 3 快照可见性规则

MVCC 判断「版本 $v$ 对事务 $T$ 是否可见」的规则：

**可见 ⇔ 版本创建者已提交，且版本未在 $T$ 开始前被更新覆盖。**

**公式解析：快照隔离的可见性条件**

设事务 $T$ 开始时间戳 $TS(T)$，版本 $v$ 由事务 $W$ 创建、创建时时间戳 $TS(v)$，下一个版本创建时间戳 $TS(v')$：

$$
\text{可见}(v) \iff TS(v) < TS(T) \;\land\; \text{W 已提交} \;\land\; TS(v') > TS(T)
$$

- **第一步，$TS(v) < TS(T)$**：版本在 $T$ 开始前创建。
- **第二步，W 已提交**：版本来自已提交事务（防脏读）。
- **第三步，$TS(v') > TS(T)$**：$T$ 开始后没有被更新覆盖——保证「读到的是 $T$ 开始时刻的最新值」。
- **第四步，三个条件合取**：同时满足则 $T$ 看到版本 $v$——**快照 = 「T 开始前最后提交的版本」**。

## 4 快照隔离与可串行化的差异

**快照隔离 ≠ 可串行化**——它允许**写偏斜（write skew）**（下一节专讲）。但快照隔离在**不并发写同一数据**时与可串行化等价；只有「并发读-写重叠」时才可能偏离。

| 维度 | 快照隔离 | 可串行化 |
| --- | --- | --- |
| 读写互斥 | 不阻塞 | 锁定时互斥 |
| 读异常 | 全防 | 全防 |
| 写偏斜 | ❌ 允许 | ✅ 防 |
| 实现成本 | 低（版本 + 冲突检测） | 高（谓词锁/串行化验证） |
| 并发度 | 高 | 低 |

**辨析｜易错点：** 很多数据库标称「REPEATABLE READ」实现为快照隔离（PostgreSQL），而 SQL 标准的 RR 仍允许幻读——**名字与语义的错位**在第 13 章已强调。快照隔离防幻读却允许写偏斜，**两者都不是标准语义的简单对应**。

## 5 MVCC 的数值算例与术语速查

**把快照可见性规则套到具体版本上。** 设数据项 X 的版本历史：T1(ts=1) 创建 v1，T2(ts=2) 创建 v2，T3(ts=3) 创建 v3。事务 T 开始于 ts=5。

- **T 读 X**：版本 v3 由 T3 创建（ts=3 < 5），T3 已提交，且 ts=5 后无新版本覆盖 → **T 读到 v3**。
- **若 T3 未提交**：v3 不可见，T 回退到 v2（T2 已提交）——**读到「已提交的最新版本」**。
- **若 T 开始于 ts=2.5**（在 T3 提交之前开始）：v3 的创建时间戳 3 > 2.5 → 不可见，T 读到 v2——**T 的一致性快照固定**。

**数值算例：写冲突检测（first-committer-wins）** 设 T1、T2 同时读余额=1000，各自尝试写入 800 与 1200。

- T1 先提交（创建新版本，成功）。
- T2 提交时发现「它读的版本已被更新」——写冲突 → **T2 中止**。
- 结果：余额=800，T2 重试——**丢失更新被防住**。
- **代价**：T2 可能白做一堆工作后被中止（事务可能重试）——这是快照隔离「不阻塞」换来的「提交时中止」风险。

**辨析｜易错点：** 快照隔离防「写-写冲突」（同一数据项），但防不住**写偏斜**（不同数据项的并发写-读重叠）——下一节专讲。**「快照隔离是弱化的可串行化」这种说法不精确**：它防住大部分异常、漏掉写偏斜，是「实用主义」的一致性，不是「标准语义」的严格子集。

<span class="marginnote">MVCC 的「版本」思想在分布式数据库里被复用：<strong>第 19 章 Spanner 用「提交时间戳 + 版本」实现外部一致性，TiDB 用 MVCC 支持分布式事务</strong>。单机 MVCC 的「版本可见性」规则，是分布式「快照隔离」的直接前身——把「事务号」换成「全局时间戳」即可。</span>

### 术语速查

| 术语 | 含义 |
| --- | --- |
| 版本 | 数据项的一个历史值 |
| 快照 | 事务开始时刻的全库状态 |
| 先提交者胜 | 写冲突时后提交者中止 |
| 版本链 | 行内/undo log 中的版本序列 |
| 可见性 | 版本对事务是否可读的判据 |
| 写偏斜 | 快照隔离漏掉的异常（下节） |

## 6 小结

- MVCC：**数据多版本，读者读快照、写者写新版本**——读写互不阻塞。
- **快照隔离**：读开始时刻快照 + 写冲突检测（先提交者胜）。
- 快照隔离防住**脏读、不可重复读、幻读、丢失更新**。
- 可见性三条件：创建于开始前、创建者已提交、开始后未被覆盖。
- SI ≠ 可串行化——**允许写偏斜**（下一节）；名字与标准语义有错位。
