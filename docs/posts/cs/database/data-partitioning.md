## 为什么从数据分区开始

复制让多台机器存**同一份**数据（扩展读），但数据总量与写吞吐仍受单机限制。**分区（partitioning / sharding）**把数据**切分成不相交的子集**，分布到不同节点——每台只存一部分、只处理一部分写。这一节讲分区的动机与三种主要策略：**范围分片、哈希分片、一致性哈希**——它们的优劣、热点问题与适用场景。分区是分布式数据库的「水平扩展」骨架，第 17 章后面的再平衡、分布式事务都在这个骨架上展开。

## 1 分区的动机

**分区（partitioning）**：把一张大数据表按某个键切分成多个**分区（partition / shard）**，分布到不同节点。

**动机**：

- **扩展存储**：单机磁盘装不下——每节点只存一部分。
- **扩展写吞吐**：写请求分摊到多个节点——各分区独立写。
- **并行查询**：查询按分区并行执行，减少单点扫描。

**核心要点：分区是「数据水平切分」。** 复制让每台存全量副本；分区让每台存一部分数据——**复制是「垂直维度」（多副本），分区是「水平维度」（分块）**。两者正交，真实系统同时用（每个分区再复制多份）。

## 2 范围分片

**范围分片（range partitioning）**：按分区键的值**范围**切分——如按时间、按 ID 区间。

```sql
-- 按时间范围分区（PostgreSQL 声明式分区）
CREATE TABLE events (
  id      BIGINT,
  ts      TIMESTAMPTZ,
  payload JSONB
) PARTITION BY RANGE (ts);

CREATE TABLE events_2024 PARTITION OF events
  FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');
CREATE TABLE events_2025 PARTITION OF events
  FOR VALUES FROM ('2025-01-01') TO ('2026-01-01');
```

**优点**：

- **范围查询高效**：优化器只访问相关分区。
- **按时间归档**：旧分区可整体移动/删除。

**缺点**：

- **热点问题**：当前时间片（如今天）的写全打在一个分区——**写热点**。
- **数据偏斜**：分区大小不均衡（某区间数据特别多）。

**核心要点：范围分片适合「按时间/有序键访问」的场景，但天然有写热点。** 时间序列数据用范围分片最自然，但「今天」的写入全落同一个分区，写吞吐受限。

## 3 哈希分片

**哈希分片（hash partitioning）**：对分区键哈希，按哈希值取模/映射到分区。

```sql
-- MySQL 哈希分区：按 id 的哈希值取模分配到 8 个分区
CREATE TABLE users (
  id   BIGINT,
  name VARCHAR(64)
) PARTITION BY HASH (id) PARTITIONS 8;
```

**优点**：

- **均匀分布**：哈希打散数据，各分区负载均衡——**无热点**。
- **写扩展好**：写分摊到所有分区。

**缺点**：

- **范围查询失效**：范围查询要扫所有分区——**哈希后有序性丢失**。
- **增删分区要重排**：取模法在分区数变化时，几乎全部数据要重新映射（再平衡问题，下一节）。

**公式解析：取模哈希的重分布代价**

设 $N$ 个分区、取模哈希 $h(k) = k \bmod N$。从 $N$ 变到 $N+1$：

$$
\text{需迁移的数据比例} = 1 - \frac{N}{N+1} \approx 1 - \frac{1}{1+1/N} \approx \frac{1}{N+1} \text{……仍几乎全部}
$$

- **第一步，取模映射**：$k \bmod N$ 与 $k \bmod (N+1)$ 对大多数 $k$ 结果不同。
- **第二步，迁移量**：约 $1/(N+1)$ 的数据留在原地？——不，实际约 $\frac{N}{N+1}$ 的数据需要迁移（新桶号变了）。
- **第三步，问题**：加一个节点要迁移几乎全部数据——**再平衡代价爆炸**。
- **第四步，对策**：一致性哈希（下节）把迁移量降到「只影响附近节点」。

## 4 一致性哈希

**一致性哈希（consistent hashing）**：把哈希空间看成一个**环（ring）**，节点与数据键都哈希到环上；每个数据键归「顺时针遇到的第一个节点」。

**优点**：

- **增删节点只影响少量数据**：加节点只把「落在新节点与前一节点之间」的数据迁移过来——**迁移量约 1/n**。
- **虚拟节点**：每个物理节点对应环上多个虚拟位置，均衡负载、平滑增减。

**公式解析：一致性哈希的迁移量**

设 $n$ 个节点均匀分布在环上，加入一个节点：

$$
\text{迁移比例} \approx \frac{1}{n+1} \quad \text{（只影响新节点的顺时针区间）}
$$

- **第一步，环分布**：$n$ 个节点把环分成 $n$ 段。
- **第二步，加节点**：插入一段的中点，拆成两段——只有「被拆的那一段」的数据迁移。
- **第三步，迁移量**：约 $1/(n+1)$——**与 $n$ 成反比，节点越多迁移越少**。
- **第四步，对比取模**：取模迁移约全部，一致性哈希迁移约 $1/n$——**差一个数量级**。

**核心要点：一致性哈希解决了「再平衡」的根本矛盾。** 它是 Redis Cluster、Cassandra、Memcached 等分布式缓存的标配分区策略——**用「环 + 虚拟节点」让增删节点几乎无痛**。

## 5 三种分片策略对比

| 维度 | 范围分片 | 哈希分片 | 一致性哈希 |
| --- | --- | --- | --- |
| 范围查询 | ✅ 高效 | ❌ 失效 | ❌ 失效 |
| 热点 | 有（时间/有序键） | 无（均匀） | 无（虚拟节点均衡） |
| 增删节点迁移 | 部分（需重切） | **几乎全部** | **约 1/n** |
| 负载均衡 | 依赖数据分布 | 均匀 | 均匀（虚拟节点） |
| 代表 | PostgreSQL 分区、TiDB Range | MySQL 分库分表 | Redis Cluster、Cassandra |

**辨析｜易错点：** **范围分片与哈希分片不是二选一的排他选择**——真实系统常结合：外层按业务（如用户 ID 哈希）分区，内层按时间（范围）再分。TiDB 用 Range 分片（支持范围查询），Cassandra 用一致性哈希（写均匀）——**分片策略是「查询模式」的镜像**，与索引选择同理。

## 6 小结

- 分区**水平切分**数据，扩展存储与写吞吐；与复制正交（分区×副本）。
- **范围分片**：范围查询高效，但有写热点与偏斜。
- **哈希分片**：均匀无热点，但范围查询失效、增删节点几乎全迁移。
- **一致性哈希**：环 + 虚拟节点，增删只迁移约 $1/n$——分布式缓存标配。
- 分片策略是查询模式的镜像；真实系统常「哈希 + 范围」组合。
