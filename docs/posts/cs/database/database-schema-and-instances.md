## 为什么从模式与实例开始

上一节我们认识了**关系（relation）**、**元组（tuple）**与**属性（attribute）**，把「一张表」翻译成了数学对象。但只认识「表长什么样」还不够：数据库里存在两个天然不同的层次——**表的结构**与**表的内容**。结构几乎一成不变，内容却每分每秒都在变。本节要确立的正是这对概念：**数据库模式（database schema）**与**关系实例（relation instance）**。

这个区分是整个数据库领域的「地基中的地基」。它贯穿全书：物理层与逻辑层的分离、DDL 与 DML 的分工、数据库迁移（migration）时「改结构」与「改数据」的本质差异，全都从这里发源。<span class="marginnote">这个「类型/值」的两层结构你在编程里早就见过：类是蓝图，对象是实例；Python 里「类定义」与「对象」、TypeScript 里「type」与「运行时值」都是同一种思想。数据库把这种思想搬到了「数据集」的尺度上。</span> 它同样呼应第一级《集合》里的**内涵与外延**：模式是「用什么规则定义数据」，实例是「满足规则的那些数据本身」。

## 1 关系模式：关系的「类型」

**关系模式（relation schema）**：用属性名与属性所在的域（domain）来描述一个关系的结构。设关系有 $n$ 个属性 $A_1, A_2, \dots, A_n$，每个属性 $A_i$ 取值于某个**域** $D_i$（如字符串、整数、日期），则这个关系模式记为

$$R(A_1, A_2, \dots, A_n)$$

例如教师关系：

$$instructor(\underline{ID},\ name,\ dept\_name,\ salary)$$

它规定了这张表「应该有哪些列、每列是什么类型」，但**不含任何具体数据**。关系模式的几个名称要熟悉：属性的个数 $n$ 称为关系的**度（degree）**或**元数（arity）**；只有 1 个属性称为一元关系，2 个称为二元关系，$n$ 个称为 $n$ 元关系。<span class="marginnote">degree 与 arithmetic 里的「次数」无关，纯粹指「列数」。一个度数为 2 的「二元关系」在集合论里就是「序偶的集合」，这与第一级集合论里「$A\times B$ 的子集」的定义完全接上了。</span>

**辨析｜易错点：** 关系模式里属性的顺序有约定（通常按设计时列出的顺序），但**模式本身是集合式的结构**，顺序只是书写方便；真正不可乱的是「属性名 ↔ 域」的对应。有些教材把带下划线的属性（如 $\underline{ID}$）标为主码，那是下一节《码》的内容，这里先知道记号即可。

## 2 关系实例：关系的「内容」

**关系实例（relation instance）**：某一时刻满足关系模式的**元组集合**，记作 $r(R)$，读作「关系模式 $R$ 的一个实例 $r$」。实例是**随时间变化的**：插入一行、删除一行、改一个工资，实例就变了。

```text
r(instructor) = { (10101, 'Srinivasan', 'CS',      65000),
                  (12121, 'Wu',         'Finance',  90000),
                  (15151, 'Mozart',     'Music',    40000) }
```

关系实例的**基数（cardinality）**就是元组的个数，即「当前表里有多少行」。注意实例里元组的**顺序无关紧要**——关系是集合，不是列表；数据库对查询结果的排序由 ORDER BY 单独指定，而不是关系本身固有的性质。<span class="marginnote">「元组无顺序」常让新手不适，因为文件、数组都有序。但正是「集合无顺序」保证了对关系做交换律、结合律式的等价变换不会改变结果——这是第12章查询优化敢于自由调整执行顺序的根本前提。</span>

把「实例」落到实处，比如上一节 instructor 关系此刻的实例 $r(instructor)$ 可以是：

| ID | name | dept_name | salary |
| --- | --- | --- | --- |
| 10101 | Srinivasan | CS | 65000 |
| 12121 | Wu | Finance | 90000 |
| 15151 | Mozart | Music | 40000 |
| 22222 | Einstein | Physics | 95000 |

这张表里每一行是一个元组 $t$，四个分量分别来自对应属性的域（ID 是定长字符串、salary 是定点数）。**现在这四行是当前实例；明天删掉 Mozart、再插入一位新教师，实例就变了，而模式纹丝不动。**

**重点：模式与实例的关系，就是「类型与值」的关系。** 模式回答「这张表长什么样」，实例回答「此刻这张表里有什么」。一个模式在任意时刻有且仅有一个「当前实例」，但可以先后有很多个不同的实例。

## 3 数据库模式与数据库实例

一个数据库通常包含多个关系（比如 instructor、student、department）。把它们的模式合起来：

**数据库模式（database schema）**：数据库中全部关系模式的集合。**数据库实例（database instance）**：某一时刻这些关系所有实例的集合。二者是「集合的集合」意义上的整体与部分关系。

概念对照表：

| 层次 | 结构（不变） | 内容（变化） |
| --- | --- | --- |
| 单个关系 | 关系模式 $R(A_1,\dots,A_n)$ | 关系实例 $r(R)$ |
| 整个数据库 | 数据库模式 | 数据库实例 |
| SQL 视角 | CREATE TABLE / ALTER TABLE（DDL） | INSERT / UPDATE / DELETE（DML） |

模式的变更远比数据变更罕见且重大：改一列的名字可能让所有引用它的应用崩掉，因此 DDL 往往需要版本管理、需要迁移脚本，而 DML 是日常操作。把「结构」与「数据」分离管理，正是数据库能长期演进而数据不丢的机制之一。

举个具体的演化例子：某电商系统上线时 orders 表没有「优惠券」列；后来产品要发券，DBA 执行 `ALTER TABLE orders ADD COLUMN coupon VARCHAR(20)`——这是**一次模式变更**，需要评估索引、存量数据回填、下游应用兼容，往往要排期上线。而 INSERT 一条新订单是**实例变更**，每秒发生成千上万次，完全无感。**一条 SQL 属于「改结构」还是「改数据」，决定了它的风险等级与审批流程**——这个判断力从今天就该建立。

## 4 公式解析：关系是笛卡儿积的子集

关系模型最漂亮的地方在于：**一个关系实例，就是一个数学上精确的对象**——它是各属性域之笛卡儿积的一个子集。

$$r(R) \subseteq D_1 \times D_2 \times \cdots \times D_n$$

把这个式子拆成三步：

- **第一步，理解 $\times$**：$D_1 \times D_2 \times \cdots \times D_n$ 是全部 $n$ 元组 $t = (v_1, v_2, \dots, v_n)$（其中 $v_i \in D_i$）的集合，即所有「合法列组合」的穷举。这是第一级集合论里笛卡儿积的直接移植。
- **第二步，理解 $\subseteq$**：不是所有组合都真实存在。比如 $v_1$ 是教师工号、$v_2$ 是姓名，但「工号 99999 叫某某」的组合可能根本没登记。**关系实例只保留现实中真实出现的那些元组**，所以它是子集，而不是全积。
- **第三步，理解元组与属性取值**：对实例 $r$ 中任意元组 $t$，用 $t[A_i]$ 表示 $t$ 在属性 $A_i$ 上的取值。例如 $t[\text{ID}] = \text{'10101'}$。这个「分量取值」记号是下一节定义**码**时反复使用的原子操作。

用一个极小的例子把「子集」看清楚。设 $D_1 = \{a, b\}$、$D_2 = \{1, 2, 3\}$，则 $D_1 \times D_2$ 共有 $2 \times 3 = 6$ 个二元组：$(a,1),(a,2),(a,3),(b,1),(b,2),(b,3)$。一个关系实例可以只取其中一部分，例如

$$r = \{(a,1),\ (a,3),\ (b,2)\} \subset D_1 \times D_2$$

它合法吗？合法——因为每个元组的第一个分量都来自 $D_1$、第二个都来自 $D_2$，且 $r$ 是 $D_1 \times D_2$ 的子集。**「合法性」只要求元组分量落在各自的域内，并不要求把全部组合都占满**——空出来的组合（如 $(b,3)$）只是「现实中不存在这条记录」而已。

这条式子第一次把「数据库」放进了严格的数学框架：关系 = 集合，元组 = 有序分量组合，查询 = 对集合做运算。理解了它，后面关系代数的全部运算都不过是「在集合上定义的一批操作」罢了。

## 5 空关系与「零数据」的语义

关系实例允许是**空集**——一张有模式、没数据的表。空关系（cardinality 为 0）是合法的，它回答「系统刚上线还没有任何数据」的状态。<span class="marginnote">空集在数据库里同样扮演「什么都没有」的精确表达：它与「有数据但查询不到」是两回事——前者是关系本身为空，后者是查询结果为空。区分「空关系」与「查询结果为空集」是理解后续 SQL 聚合、COUNT 语义的伏笔。</span>

**辨析｜易错点：** 空关系 ≠ 关系不存在。关系的**模式**仍然存在（列还在），只是当前实例没有元组。这与第一级数学里**空集 $\emptyset$** 与「集合不存在」的区别如出一辙——模式是「容器的形状」，实例为空只是「容器里暂时没东西」。

## 6 小结

- **关系模式** $R(A_1,\dots,A_n)$ 描述结构：属性名 + 域；度 = 属性个数。
- **关系实例** $r(R)$ 是某一时刻满足模式的元组集合，**随时间变化**；基数 = 元组个数。
- **数据库模式 / 数据库实例** 是「集合的集合」意义上的整体与部分。
- 关系实例是 $D_1 \times \cdots \times D_n$ 的**子集**；元组 $t$ 在属性 $A_i$ 上的取值记 $t[A_i]$。
- 实例中元组**无顺序**；空关系合法，但模式仍存在。
- 结构用 DDL 管理（罕见、重大），数据用 DML 管理（频繁、日常）。

在下一节，我们将回答一个尖锐的问题：同一张表里可能有成千上万行，**凭什么区分它们？** 靠的是属性组合的「唯一性」——这就是**码**。
