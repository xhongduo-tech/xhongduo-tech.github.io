## 为什么从视图与授权的递归开始

前面两节我们分别讲了**视图**（一个查询的别名）与**授权**（谁能在哪个关系上做什么）。它们各有一个「递归」的问题没有展开：视图能不能在定义里引用自己？权限能不能沿着授权链递归地传递下去？这一节把两条线收拢——**递归视图**与**递归授权**，它们是视图与授权话题的收官，也是通往第5章《递归查询》的桥梁。

在关系模型里，「递归」几乎总意味着**传递闭包**：经理的经理、课程的先修的先修、好友的好友。这类问题用普通 SQL 表达极其笨拙，却几乎每个数据库都会遇到。理解它，需要一点**不动点**的直觉——而这正是把 SQL 从「查询语言」升级为「能算图算法」的关键一步。

## 1 视图的递归：一个视图能引用自己吗

**递归视图（recursive view）**：定义中直接或间接引用了自身的视图。直观的例子是「祖先」关系。

假设有关系 `emp_supervisor(employee, supervisor)`，表示「supervisor 是 employee 的直接上级」。现在要回答：**谁是谁的祖先（任意层级）**？普通视图做不到，因为「祖先」的定义是自我参照的：

$$
\text{ancestor}(x, y) \;\Longleftrightarrow\; \text{supervisor}(x, y) \;\lor\; \exists z\,(\text{supervisor}(x, z) \land \text{ancestor}(z, y))
$$

意思是：$y$ 是 $x$ 的祖先，当且仅当 $y$ 直接管理 $x$，或者存在一个 $z$——$z$ 直接管理 $x$，而 $y$ 是 $z$ 的祖先。这里 $\text{ancestor}$ 在等号两边都出现了，这就是**递归定义**。

**辨析｜易错点：** 如果把上面的定义原样写成一个普通视图，数据库会立刻陷入**无限展开**：查询一个递归视图时，系统把视图名替换成定义，定义里又出现视图名，再替换……永不停止。<span class="marginnote">普通视图的展开是一次性的文本替换；递归视图的展开会无限嵌套，所以它必须改用「先迭代、后取结果」的方式执行，而不是展开。</span>因此，递归视图不是普通 `CREATE VIEW` 的语法变体，它需要专门的构造。

## 2 WITH RECURSIVE：把递归写进 SQL

SQL 标准用 `WITH RECURSIVE` 表达递归查询，它由一个**基例（base case）**与一个**递归步（recursive step）**组成，两者取并集：

```sql
WITH RECURSIVE rec_ancestor(employee, ancestor) AS (
    -- 基例：直接上级
    SELECT employee, supervisor
    FROM emp_supervisor
  UNION
    -- 递归步：再往上一级
    SELECT rec_ancestor.employee, emp_supervisor.supervisor
    FROM rec_ancestor, emp_supervisor
    WHERE rec_ancestor.ancestor = emp_supervisor.employee
)
SELECT * FROM rec_ancestor;
```

逐行读这个查询：**基例**先给出「直接管理关系」；**递归步**说「如果我已经知道 $x$ 的祖先是 $y$，而 $y$ 的上级是 $z$，那么 $z$ 也是 $x$ 的祖先」——每次迭代把链条向上延伸一级。<span class="marginnote">「基例 + 递归步」与数学归纳法、函数式编程里的递归结构完全同构：基例是递归出口，递归步把问题化小。第二级《离散数学》里的归纳证明与这里是一套思想。</span>

递归步还必须满足一个关键约束：它只能引用 `WITH RECURSIVE` 定义的临时关系 `rec_ancestor` 一次（而且不能把它放在「非递归」一侧的运算符里）。这条限制不是吹毛求疵，而是**保证递归可计算**的技术前提——它确保每次迭代只向结果**添加**元组，绝不删除，于是迭代必然单调增长。

## 3 递归的语义：最小不动点

递归查询真正执行时，数据库用的不是「展开」，而是**迭代求值**：从基例出发，反复应用递归步，直到结果不再变化为止。这个收敛结果在数学上有一个漂亮的名字——**最小不动点（least fixed point）**。

把整个递归查询看成一个算子 $F$：输入是当前已知的 `rec_ancestor`，输出是「基例 ∪ 再往上走一级后的结果」。则：

$$
R^{(0)} = \emptyset, \qquad R^{(i+1)} = F(R^{(i)}) = T \cup (T \circ R^{(i)})
$$

其中 $T$ 是直接管理关系，$T \circ R^{(i)}$ 是「先走一步 $T$、再沿已有祖先关系 $R^{(i)}$ 走到底」的复合关系。迭代从空集出发：第一轮得到直接上级，第二轮得到上级的上级，第三轮再往上一级……直到某轮 $R^{(k+1)} = R^{(k)}$，收敛，$R^{(k)}$ 就是**传递闭包**。<span class="marginnote">复合关系 $T \circ R$ 即关系代数里的连接运算：$T \circ R = \{(x,z) \mid \exists y, T(x,y) \land R(y,z)\}$。这个记号在第2章《关系代数》里见过，现在它成了递归的燃料。</span>

**辨析｜易错点：** 迭代一定收敛吗？不一定。若底层关系存在**环**（比如两个人互为上司这种不合法的数据），迭代仍会收敛，因为环只是让某些祖先元组被重复发现——而 `UNION` 自动去重，重复发现不会增加新元组。真正危险的是**自相矛盾的定义**，比如在递归步里用了 `NOT EXISTS` 或聚集函数来「否定」已有结果——那会破坏单调性，导致结果不收敛或语义无定义。<span class="marginnote">对含 `NOT` / 聚集的递归查询，需要更精密的「分层否定」理论（分层逻辑程序）才有良定义的最小不动点。这部分在数据库理论课里属于 Datalog 的范畴。</span>

## 4 授权的递归：权限沿着授权图流动

现在把镜头转向授权的「递归」。第4章《授权》里我们建立了**授权图**：节点是用户，边 $u \to v$ 表示「$u$ 把权限 $p$ 授给 $v$（含 grant option）」。权限的拥有是**沿边递归推导**出来的：

$$
v \text{ 拥有 } p \;\Longleftrightarrow\; \text{存在授权链 } u_0 \to u_1 \to \cdots \to u_n = v,\ \text{且链上每步都承载 } p
$$

这条递归链有三个推论：

- **递归撤销**：`REVOKE p FROM u CASCADE` 不只是删掉 $u$ 这一条边，而是删除以这条边为根、递归可达的**整棵授权子树**——$u$ 授给过的、以及那些继续转授出去的，全部一并撤销。<span class="marginnote">CASCADE 的「连坐」本质就是在授权图上做一次递归的深度优先删除；而 RESTRICT 则是「先检查这次删除是否需要递归，需要就拒绝」。上一节的两个关键词，翻译过来就是「要不要递归」。</span>
- **间接可见**：视图让授权产生「数据递归」——用户 A 对基表有权限并创建了视图 V，A 把 `SELECT ON V` 授给 B，则 B 能读到经 V 裁剪过的数据，却始终没有触碰基表的权限。数据经由「视图之眼」层层递进，这是授权的另一种递归。
- **权限不沿视图自动传递**：B 从 V 里读到的行，属于 V 所引用的基表；但 B 对基表仍没有任何权限。**「能查视图」不等于「能查底层表」**，这个上一节强调过的结论，在递归语境下依然成立——视图只是透镜，不是护照。

**辨析｜易错点：** 递归授权最容易踩的坑是**授权环**：A 授给 B，B 又授给 A。此时撤销哪一条边都可能让对方「绕路」继续持有权限，所以在做 `REVOKE` 前必须想清楚整条链路。数据库的 CASCADE 会替你递归清理，但若两处授权相互独立，撤销一条未必能真正剥夺权限——**权限的剥夺要追根溯源，看的是整张图而不是一条边**。

## 5 公式解析：传递闭包的递归方程

把第3节的迭代收敛写成一条等式，就是递归查询的**灵魂公式**：

$$
R = T \cup (T \circ R)
$$

逐项拆解：

- **$T$（直接关系）**：基例，代表「一步可达」。在祖先问题里是直接上下级；在先修问题里是直接先修关系。
- **$T \circ R$（复合关系）**：递归步，代表「先走一步 $T$，再沿 $R$ 走任意多步」——即「多走一步」。
- **$R$（传递闭包）**：等号左边是我们要的答案，右边却含有 $R$ 自己。这不是循环定义的死结，而是一个**不动点方程**：我们要找的是那个满足「$R = $ 一步关系 $\cup$ 多走一步仍在内」的关系 $R$。
- **最小不动点**：不动点方程可能有很多解，比如「全集关系」总满足它（因为 $T \cup (T \circ U) = U$）。数据库要的是**最小**的那个——从空集出发迭代得到的解，恰好就是「恰好等于传递闭包」的那个。

$$
R^{\star} = \bigcup_{i \ge 0} F^{(i)}(\emptyset) = T \cup T \circ T \cup T \circ T \circ T \cup \cdots
$$

这个展开式把递归翻译成了**无限并**：一步可达、两步可达、三步可达……所有有限步可达关系的并集，正是传递闭包。这就是为什么递归查询能表达「多深的层级都能找到」——它把「任意深度」化成了「有限步的每一步」。

从计算角度看，这恰好也是数据库执行递归查询的方式：第 $i$ 轮迭代只处理第 $i$ 层新增的元组（这叫**半朴素求值**），避免了每轮都重算全部结果。理解了这条等式，就理解了 SQL 递归的语义、终止性与实现，也提前预演了第5章《递归查询》与第12章查询优化的一个重要落点。

## 6 小结

- **递归视图 / 递归查询**：定义中引用自身的查询，用 `WITH RECURSIVE` 表达，由**基例 + 递归步**构成。
- **递归视图不能靠展开执行**，而要**迭代求值**：反复应用递归步直到结果不再变化（不动点）。
- **最小不动点** $R = T \cup (T \circ R)$ 是递归查询的语义：从空集迭代，恰好得到传递闭包。
- **递归步的约束**：不能含否定与聚集，以保证单调收敛；关系里的环不会破坏收敛，因为 `UNION` 去重。
- **授权的递归**：权限沿授权图递归推导；`REVOKE ... CASCADE` 是对授权子树做递归删除，`RESTRICT` 拒绝需要递归的撤销。
- **视图授权的递归**：通过视图授出的只是「透镜」，数据递归可见，权限并不递归自动传递。
