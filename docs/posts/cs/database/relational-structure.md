## 为什么从关系的结构开始

历史课告诉我们，关系模型靠「一张表打天下」征服了数据库世界。但「表」这个日常词太模糊了：电子表格是表，报表是表，关系模型里的「关系」到底严格指什么？这一节把「一张表」拆成四个精确的术语——**关系（relation）、元组（tuple）、属性（attribute）、域（domain）**——并回答一个在数学上很干净的问题：**关系在集合论里到底是什么？**

这四个术语是本专题往后几十篇的「母语」。后面讲关系代数、讲 SQL、讲范式，全都建立在这套词汇上。更重要的是，把「表」升级成「关系」是一次思维跃迁：从「我看得见的样子」跳到「它在数学上是什么」——有了这层严格定义，才能谈「为什么查询结果是集合」「为什么不能有两行完全相同的记录」这类看似平凡、实则深奥的问题。<span class="marginnote">关系模型的革命性恰恰在于「严格」：它把「表」这个工程直觉翻译成了集合论的精确对象，于是可以用逻辑与代数对查询做推理。这就是第一级《集合》与数据库的连接点——你当年学的子集、笛卡儿积，今天在数据库里全部派上用场。</span>

## 1 关系、元组与属性：一张表的三个名字

**关系（relation）**：关系模型里的基本对象，直观上就是一张**二维表**。**元组（tuple）**：表中的**一行**。**属性（attribute）**：表中的**一列**，也就是表头那行里的每个名字。三者是「同一张表」的三个正交切面。

![关系、属性与元组：instructor 关系的一个实例](/images/database/relational-structure-1.svg)

用图里的 **instructor** 表说话：这张表整体是一个关系；表头的 **ID、name、dept_name、salary** 是四个属性；每一行，比如 **（10101, 王芳, CS, 80000）**，是一个元组。**关系名加属性名，合起来定义这张表的「形状」；元组则是「形状」里实实在在的内容。**

这里有一个初学者最容易踩的坑，先记住结论：

**辨析｜易错点：「关系」是数学概念，「表」是用户界面。** 关系是「一组元组的集合」，严格遵循集合的规则（无重复、无序）；而我们日常说的「表」常常带着电子表格的印象——允许多余的重复行、行有先后顺序。SQL 里的表在细节上允许重复行（更像是多重集），这是 SQL 与纯关系模型的一个微妙出入，第 4 节会展开。**现在先把「关系 = 元组的集合」刻在脑子里，这是最干净的定义。**

## 2 域（domain）与属性的原子性

**域（domain）**：属性取值所来自的**集合**。**instructor** 表的 **dept_name** 列，其域可以是「该校所有系名的集合」；**ID** 列的域可以是「5 位字符串的全体」。每个属性都从自己的域里取一个值，所以关系的一个严格定义可以写成：**一个属性 $A_i$ 的值必须来自它的域 $\mathrm{dom}(A_i)$**。

域还有一个约束，叫**原子性（atomicity）**：**关系的每个属性都必须是原子的——不能再拆分成更小的部分。** 例如 **name** 是原子字符串，但「**phone** 列同时存办公电话与手机号」就不原子，因为它可以再拆。<span class="marginnote">原子性不是绝对的，而是「对应用而言不可再分」：对教务系统，「地址」可以是一个字符串（原子）；对地理应用，「地址」又要拆成省、市、街道。是否原子取决于业务需要——这是第 8 章《规范化》讨论第一范式（1NF）的伏笔。</span>

原子性带来一个直接后果：**关系模型不喜欢「复合值」与「集合值」塞进一个属性里。** 想在 **instructor** 里记录一个教师的多部电话，正确的做法不是在一个单元格里塞多个号码，而是另建一张 **phone（电话）** 表（一教师多电话，是多对多关系的一角）。这个「拆表」的习惯，正是后面《规范化理论》与《ER 模型》反复训练的核心动作。

## 3 关系模式与关系实例

把前面两个术语组装起来，就得到关系模型的两个核心概念：

**关系模式（relation schema）**：关系名加属性名，即 $R(A_1, A_2, \dots, A_n)$。它描述关系的「形状」或「骨架」。**instructor(ID, name, dept_name, salary)** 就是一个关系模式。<span class="marginnote">关系模式是「类型」，关系实例是「值」——这个类比与第一级《集合》里「模式 vs 实例」完全一致。模式的英文 schema 与实例 instance，我们在数据视图那一节已经见过，这里是它在关系层面的具体化。</span>

**关系实例（relation instance）**：某个时刻关系里的**实际元组集合**，记作 $r(R)$。同一模式可以有不同的实例——今天 **instructor** 里有 3 行，明天可能变成 5 行，但模式不变。

还有两个描述大小的术语，它们常被混淆：

**度（degree）**：属性的个数，也叫**元数（arity）**。**instructor** 的度是 4。
**基数（cardinality）**：元组的个数。图里 **instructor** 实例的基数是 3。

**辨析｜易错点：度的单位是「列数」，基数的单位是「行数」。** 「这张表的度是 3、基数是 2」意思是「3 个属性、2 个元组」。把两者说反是最常见的小错误，面试里也常被用来试探基础是否扎实。

## 4 空值：NULL 与未知

现实世界总有「不知道」：新入职的教师工资还没定、某学生的电话号码没登记。为了表达「值未知」的状态，关系模型与 SQL 引入**空值 NULL**——它**不是数字 0，也不是空字符串 ''，而是「当前不知道是什么」的占位符**。

空值在关系模型里是一个「刺头」，因为它与「关系是集合」的干净定义产生张力：如果一个元组里某属性取 NULL，这个元组还算「取自域」吗？数据库的应对是务实的——允许 NULL，但给它三条明确的规则：

NULL 参与比较时，结果不是真也不是假，而是**未知（unknown）**——这催生了三值逻辑，第 3 章《SQL》会专节展开。
NULL 参与算术时，结果仍是 NULL：**salary + 1000** 若 **salary** 是 NULL，结果还是 NULL。
聚合函数（**SUM、AVG** 等）**忽略 NULL**：一组数据里有一个 NULL，**AVG** 只对非 NULL 值求平均。

用建表语句看 NULL 的声明：

```sql
CREATE TABLE instructor (
    ID        CHAR(5) PRIMARY KEY,
    name      VARCHAR(20) NOT NULL,
    dept_name VARCHAR(20),
    salary    NUMERIC(8, 2)
);
```

**NOT NULL** 表示该列不允许空值（**该列的值**必须有）；**PRIMARY KEY** 隐含了非空与唯一；**dept_name 与 salary** 没有约束，意味着它们允许 NULL——「还没分配系」或「工资还没定」都可以合法地存进去。<span class="marginnote"><strong>NULL</strong>` 与 <strong>0</strong>`、与 <strong>''</strong>（空字符串）是三个完全不同的东西：0 是一个具体的数，'' 是一个具体的字符串，NULL 是「没有值」。这是 SQL 新手最容易踩的坑之一，第 3 章《空值与三值逻辑》会专门把它讲透。</span>

**辨析｜易错点：主码不能为 NULL。** 主码（PRIMARY KEY）的作用是「唯一标识一行」，因此它隐含 **NOT NULL（非空）**。往主码列插入 NULL，数据库会直接报错——这是「主码」与「允许 NULL 的列」之间不可逾越的边界，也是后续讲完整性约束时的第一课。

## 5 关系 vs 表：集合与多重集的分歧

关系是元组的**集合**，而集合的三个特征——**确定性、互异性、无序性**——会在数据库里一一投射：

**互异性**：一个关系里**不允许出现两个完全相同的元组**。因为集合的元素互不相同，重复出现的元组只算一个。
**无序性**：关系的元组**没有内在顺序**。**任意元组** 排在第一行还是最后一行，不影响这个关系。
**确定性**：任意一个元组，都能明确判断它在不在关系里。

但 SQL 的实现与纯关系模型有一个**著名出入**：SQL 里的「表」允许出现重复行（除非查询显式写 **DISTINCT**）。这意味着 **SQL 的表更接近多重集（multiset），而非严格集合**：

```sql
SELECT dept_name FROM instructor;           -- 可能返回重复的系名
SELECT DISTINCT dept_name FROM instructor;  -- 保证返回不重复的系名
```

第一条语句可能返回 **重复的系名**（有重复），第二条保证返回 **不重复的系名**。<span class="marginnote">为什么 SQL 允许重复？因为「去重」是有代价的——排序或哈希才能判断两行是否相同。为了性能，SQL 把「去重」的开关交给了用户（<strong>DISTINCT</strong>），这是「数学纯洁性」向「工程效率」的一次让步。你会看到，代价估算（第 12 章）里处理重复也占了一席之地。</span>

**辨析｜易错点：「查询结果是一张表」不等于「关系里允许重复元组」。** 关系（作为存储对象）本身无重复；查询**结果**在 SQL 里可能重复，因为它是「经过投影/选择后的一次性输出」，不是持久化的关系。理解这个差别，你就能看懂为什么 **关系（表）** 和 **查询结果** 的重复行为不同。

## 6 公式解析：一个关系模式上有多少种可能的关系

有了「关系是笛卡儿积的子集」这一定义，就能回答一个漂亮的计数问题：**给定一个关系模式，理论上可能有多少种不同的关系实例？**

回顾数据视图那一节的精确定义：设关系模式 $R = (A_1, \dots, A_n)$，则一个实例是笛卡儿积的子集：

$$r(R) \subseteq \mathrm{dom}(A_1) \times \mathrm{dom}(A_2) \times \cdots \times \mathrm{dom}(A_n)$$

现在推导「可能的关系个数」，拆成三步：

- **第一步，数笛卡儿积的大小**：设 $|\mathrm{dom}(A_i)|$ 是第 $i$ 个域的规模，则笛卡儿积的元组总数为各域规模之积：
  $$|\mathrm{dom}(A_1) \times \cdots \times \mathrm{dom}(A_n)| = |\mathrm{dom}(A_1)| \times \cdots \times |\mathrm{dom}(A_n)|$$
- **第二步，数子集的个数**：一个关系是「从这些候选元组中挑出若干元组」——每个元组都有「在」与「不在」两种选择，互不影响。于是可能关系的总数是 $2$ 的「候选元组数」次方：
  $$\#\{\text{可能的关系}\} = 2^{|\mathrm{dom}(A_1)| \times \cdots \times |\mathrm{dom}(A_n)|}$$
- **第三步，代入一个可手算的例子**：设 $R = (A, B)$，$\mathrm{dom}(A)$ 有 3 个值、$\mathrm{dom}(B)$ 有 4 个值，则候选元组有 $3 \times 4 = 12$ 个，可能的关系共有 $2^{12} = 4096$ 种。**「集合的子集个数 = $2^{\text{元素个数}}$」**——这个公式在第一级《集合》里就学过，今天在数据库里第一次「复用」。

这个推导的价值不在 4096 这个数，而在它揭示的**指数爆炸**：候选元组数每加 1，可能的关系数就翻一倍。这正是为什么数据库的**统计信息**（第 12 章）如此重要——真实数据库里可能的关系数量大到不可枚举，优化器只能靠采样与直方图去**估计**，而不是去**数**。

## 7 小结

- 一张表有三个名字：整体叫**关系**，行叫**元组**，列叫**属性**。
- 每个属性取之于一个**域**（$\mathrm{dom}(A_i)$），且取值必须**原子**（不可再分）。
- **关系模式** $R(A_1, \dots, A_n)$ 是「骨架」，**关系实例** $r(R)$ 是「血肉」；**度 = 属性个数，基数 = 元组个数**。
- **空值 NULL** 表示「值未知」，不是 0 也不是 ''；主码隐含 **NOT NULL**。
- 关系是元组的**集合**：无重复、无序；SQL 的表更接近**多重集**，重复与否由 **DISTINCT** 决定。
- 可能关系的个数是 $2^{|\mathrm{dom}(A_1)| \times \cdots \times |\mathrm{dom}(A_n)|}$——指数爆炸决定了优化器只能「估计」而非「穷举」。
