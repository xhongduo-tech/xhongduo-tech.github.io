## 为什么从 ER 图开始

前面几节讲了 ER 模型的全部构件，但它们散落在文字里。**ER 图（ER diagram）**把这套构件固化成一套图形语言：矩形、菱形、椭圆、连线——一眼看清整个数据库的概念结构。对设计者，它是沟通工具；对后续工作，它是逻辑设计（转表）的输入。这一节把符号系统完整过一遍，再用一个完整的「大学选课系统」示例把知识串起来。读完这节，你能读懂任何一张 ER 图，也能把自己的需求画成一张。

## 1 标准符号总览

ER 图的基本记号：

| 符号 | 含义 | 说明 |
| --- | --- | --- |
| 矩形 | 实体集 | 名称写在框内 |
| 菱形 | 联系集 | 连接参与的实体集 |
| 椭圆 | 属性 | 连到所属实体或联系 |
| 下划线椭圆 | 主码属性 | 唯一标识 |
| 双椭圆 | 多值属性 | 如多个电话 |
| 虚线椭圆 | 派生属性 | 如年龄 |
| 双矩形 | 弱实体集 | 依赖宿主 |
| 双菱形 | 标识联系 | 弱实体与宿主 |
| 波浪下划线 | 部分码 | 弱实体的部分码 |
| 粗/双线 | 总量参与 | 每个实体必须参与 |
| 箭头（无符号） | 一 | 指向「一」侧 |
| 边上的 1 / n | 映射基数 | 数量标注 |

## 2 一个完整的 ER 图示例

用「大学选课系统」把全部符号串起来。实体集：**学生**（学号、姓名、电话多值）、**课程**（课程号、学分）、**教师**（工号、姓名）、**系**（系名、办公楼）。联系集：**选修**（学生 m:n 课程，带成绩属性）、**授课**（教师 1:n 课程）、**属于**（教师 n:1 系，总量参与）。

读图三步法：

1. **看实体与码**：每个矩形是实体集，下划线属性是主码——学生主码学号，课程主码课程号。
2. **看联系与基数**：菱形连接谁、边上的 1 和 n 怎么标——学生与课程之间 m:n，因此将来要建连接表。
3. **看约束**：粗线表示总量参与——教师到「属于」是粗线，说明每个教师必须属于一个系；教师到「授课」是细线，允许不授课的教师。

**核心要点：ER 图是「一个设计文档」，不是「一张表结构图」。** 它描述业务语义，不描述索引、不描述存储——这正是第 7 章开头强调「概念设计独立于实现」的图形化落地。

## 3 常见错误与辨析

**辨析｜易错点 1：联系属性放错位置。** 「选修」联系带成绩，成绩椭圆必须连在**菱形**上，不能连在学生或课程矩形上——否则语义变成「学生的成绩」或「课程的成绩」，无法表达「某学生某门课的成绩」。

**辨析｜易错点 2：基数标注方向反。** 学生-课程 m:n，边上写「n」的是学生侧还是课程侧取决于读法约定：**「一个学生可选 n 门课」→ 学生侧标 n**；「一门课被 m 个学生选」→ 课程侧标 m。读图时必须先确认「站在哪一侧看对面」。

**辨析｜易错点 3：双线（总量参与）滥用。** 把所有联系都画成双线是新手常态——但业务上「教师可以暂时不授课」就是部分参与。**双线意味着数据库必须拒绝「无联系实体」的插入**，画错了等于把宽松业务做成了强制约束。

## 4 公式解析：ER 图到后续设计的输入

ER 图虽然不直接算数，但它承载了一个可度量的信息量：

$$
\text{relations} = \#\{\text{实体集}\} + \#\{\text{多值属性}\} + \#\{\text{m:n 联系集}\}
$$

- **第一步，每个实体集 → 一张表**：学生、课程、教师、系各成一张表。
- **第二步，每个多值属性 → 一张子表**：学生电话单独成表。
- **第三步，每个 m:n 联系 → 一张连接表**：选修成连接表。
- **第四步，1:n 与 1:1 联系不新增表**：外键并入「多」侧即可——属于、授课都是外键，不建新表。

这个粗略公式预告了下一节「从 ER 图到关系模式」的转换规则：**ER 图里「数的清的东西」决定了关系模式里「有几张表」**。概念设计的粒度直接决定逻辑设计的表数量，这是两层设计之间的换算枢纽。

## 5 小结

- ER 图符号系统：矩形=实体、菱形=联系、椭圆=属性，**双线/双框/虚线**分别表示总量参与、弱实体、派生属性。
- 读图三步：看实体与码 → 看联系与基数 → 看约束（粗线）。
- 联系属性连**菱形**，基数标注先确认视角，双线不可滥用。
- 表数量 ≈ 实体集数 + 多值属性数 + m:n 联系数——ER 图是关系模式的**蓝图输入**。
