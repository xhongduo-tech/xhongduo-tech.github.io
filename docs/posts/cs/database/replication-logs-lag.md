## 为什么从复制日志与滞后开始

复制的数据流靠**复制日志（replication log）**承载，而异步复制的核心问题是对**复制滞后（replication lag）**的管理——从节点落后主节点多久、读到滞后数据会出什么问题、如何缓解。这一节讲复制日志的四种实现（语句、WAL、逻辑日志、触发器），以及滞后导致的三种异常：**读己之写、单调读、前缀一致读**。读己之写是分布式应用最常见的 bug 来源——本节会给出对应的缓解手段。

## 1 复制日志的实现

**复制日志（replication log）**是把主节点的写传给从节点的载体。四种实现：

1. **语句复制（statement-based）**：把 SQL 语句发给从节点重放。简单，但**非确定性语句**（`NOW()`、`RAND()`、自增）在从节点产生不同结果。
2. **WAL 传输（WAL shipping）**：传输主节点的**预写式日志**（第 15 章）——从节点应用同一条日志。确定性强，但**日志与存储格式耦合**（版本升级困难）。
3. **逻辑日志（logical log）**：传输**行级变更**（如 MySQL binlog row 格式）——「插入了 id=5 的行，值...」。与存储解耦，是主流。
4. **触发器（trigger-based）**：应用层触发器捕获变更并转发。灵活但**开销大、易出错**。

**核心要点：逻辑日志（行级变更）是现代复制的主流。** 它与存储引擎解耦，支持异构复制、数据管道、CDC（变更数据捕获）——大数据与流处理依赖它。

## 2 复制滞后

**复制滞后（replication lag）**：从节点落后主节点的延迟——主节点写完之后，从节点要过多久才应用。

- **滞后来源**：日志传输延迟、从节点应用排队、从节点负载。
- **常态**：异步复制下，滞后**不是 0**——从节点读到的可能不是最新数据。

**核心要点：读从库 = 接受「读到旧数据」的可能。** 这是读扩展的代价（第 16 章动机）。问题不在滞后本身，而在「应用对滞后的敏感度」。

## 3 滞后导致的三种异常

**异常 1：读己之写（read-your-writes）**。用户写完立刻读——**写走主、读走从**，从节点还没同步，用户「读不到自己刚写的数据」。

**异常 2：单调读（monotonic read）**。用户多次刷新——**第一次读到新值（从已同步副本读），第二次读到旧值（从落后副本读）**——时间倒流。

**异常 3：前缀一致读（consistent prefix read）**。用户读到**乱序的因果关系**——先读到「B 回复 A」的评论，后读到「A 的发言」（因为副本复制顺序不同）。

**公式解析：读己之写的缓解**

读己之写可用「**读己写保证**」（read-your-writes consistency）缓解：

$$
\text{保证}：\forall \text{ 写 } w \in \text{用户自己的写}: \text{ 该用户后续读 } r \Rightarrow r \text{ 包含 } w \text{ 的效果}
$$

- **第一步，识别「自己的写」**：按用户/会话维度跟踪。
- **第二步，路由规则**：用户读自己刚写过的数据时，**强制路由到主节点**（或已同步副本）。
- **第三步，实现**：会话级「read-your-writes」——写入后一段时间内，该用户的读走主节点。
- **第四步，代价**：牺牲「读从库」的负载均衡——只在「刚写完」的窗口内。

## 4 缓解滞后的工程手段

- **读写路由**：敏感读走主，非敏感读走从（按数据/时间分）。
- **带时间戳的路由**：读请求带「要求 ≥ 某时间戳」——路由到已同步到该时间戳的副本。
- **单调读绑定副本**：同一用户会话**固定读同一个副本**——避免「时间倒流」。
- **前缀读绑定**：因果相关的读写路由到同一分区/副本。

**核心要点：缓解滞后 = 把「一致读」的需求路由到「能满足的地方」。** 要么读主、要么读「足够新的从」、要么固定副本——**都是「按需路由」的思想**。彻底消灭滞后需要同步复制（牺牲可用性）或共识（第 16 章后文）。

**辨析｜易错点：** **读己之写不是「弱一致」的错，而是「读写不对称路由」的错**。如果所有读都走主节点，绝无读己之写——问题是读从库优化。**滞后异常的本质是「路由不当」**，不是「复制失败」。

## 5 小结

- 复制日志四种：**语句、WAL、逻辑日志（主流）、触发器**。
- **复制滞后**是异步复制的常态——从节点读到旧数据。
- 三种滞后异常：**读己之写、单调读、前缀一致读**。
- 缓解 = 按需路由：敏感读走主、会话固定副本、带时间戳路由。
- 滞后异常的本质是**路由不当**；彻底消除需同步复制或共识。
