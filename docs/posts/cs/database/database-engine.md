## 为什么从数据库引擎开始

前面几节我们都在"外面"看数据库：用户看到视图，用 DDL 定义模式，用 DML 操作关系。现在掀开引擎盖——**数据库引擎（database engine）** 由三大子系统构成：**存储管理器**负责把数据落盘，**查询处理器**负责把 SQL 变成可执行计划，**事务管理器**负责保证并发与故障下的正确性。理解这三个子系统，就理解了 DBMS 的骨架，也为第三篇《数据存储与查询引擎》、第四篇《事务与故障恢复》埋下地图。

这三大子系统不是三块并列的积木，而是一条配合默契的流水线：查询处理器在前台接单（SQL），存储管理器在后台出库（磁盘 I/O），事务管理器在中间记账（保证正确性）。把这条流水线拆开看，正是整门数据库课程的骨架图。

## 1 存储管理器

**存储管理器（storage manager）**：数据库系统中负责"数据怎么存、怎么取、怎么管元数据"的组件。

它由若干部件协同工作：

- **权限及完整性管理器（authorization and integrity manager）**：检查访问权限，保证完整性约束不被破坏。
- **事务管理器（transaction manager）**：保证即使系统崩溃数据库也处于一致状态；并发访问时保证事务互不干扰。
- **文件管理器（file manager）**：管理磁盘上数据文件的分配与回收。
- **缓冲区管理器（buffer manager）**：负责把磁盘块读入内存、决定何时写回、替换哪些块。<span class="marginnote">缓冲区管理器本质上是数据库自己的"虚拟内存"：在内存与磁盘之间搬运块并处理替换策略。这与第三级《操作系统》里的页置换如出一辙——LRU、Clock 那些算法会在数据库缓冲区替换中以类似面貌重演。</span>

存储管理器还维护**数据文件（data files）**、**数据字典（data dictionary）** 与**索引（indices）**。索引是加速查询的关键设施，第 10 章《索引与哈希》会专门讲 B+ 树与哈希索引。

存储管理器面对的是整个**存储层次（storage hierarchy）**。从上到下，容量越来越大、速度越来越慢、单位成本越来越低：

| 层级 | 典型容量 | 访问速度 | 持久性 |
| --- | --- | --- | --- |
| 主存（RAM） | 数十 GB | ~100 ns | 断电即失 |
| 闪存（SSD） | 数百 GB 至数 TB | ~10–100 µs | 持久 |
| 磁盘（HDD） | 数 TB | ~10 ms | 持久 |
| 磁带 / 归档 | 数十 TB 以上 | 秒级 | 持久 |

数据库的数据主体在磁盘或闪存上，但"热数据"要尽量留在内存里。缓冲区管理器就是这套搬运的调度员：它把被访问的块读进缓冲池，按某种替换策略决定哪些块该被换出。<span class="marginnote">整个存储层次的"快慢差"与代价模型，会在第 9 章《数据存储与文件组织》里用更细的数量级展开；而第 4 节先给你一个核心数量级：磁盘一次 I/O 约 10 ms。</span>

**辨析｜易错点：数据库 ≠ 一堆数据文件。** 初学者容易把"数据库"理解成磁盘上那张表对应的文件。实际上数据文件只是存储管理器管理的一类对象；数据字典、索引、日志（第 15 章）同样由存储管理器维护。用户眼中的"表"是逻辑层概念，磁盘上的字节是物理层概念——中间隔着整套存储管理器。

还有一个容易忽略的点：**数据字典与索引也是存储管理器维护的对象**。数据字典是"表的表"，索引是"为查询服务的辅助结构"，它们和数据文件一起，构成存储管理器视野里的全部家当。用户建表、建索引的 DDL，最终都转化为存储管理器对这些物理对象的一次次读与写。

## 2 查询处理器

**查询处理器（query processor）**：把用户的 SQL 变成高效执行的计划。

它包含三个部分：

**DDL 解释器（DDL interpreter）**：解释 DDL 语句，把模式定义写进数据字典。
**DML 编译器（DML compiler）**：把查询语句翻译成底层可执行指令——先把 SQL 转成语义等价的关系代数表达式，再交给优化器生成**查询执行计划（query execution plan）**。<span class="marginnote">SQL → 关系代数 → 执行计划，这条流水线解释了为什么要先学关系代数（第 2 章）再学查询优化（第 12 章）：优化器正是在关系代数层面做等价变换。</span>
**查询评估引擎（query evaluation engine）**：真正执行低级指令，逐条扫描、连接、排序，返回结果。

一次查询的旅程大致是：SQL 进来 → 语法解析 → 转关系代数 → 优化器从众多候选计划里挑代价最低的 → 评估引擎执行并返回。**用户写"要什么"，优化器决定"怎么做"**——这正是声明式语言背后的引擎故事，也是"性能"二字在数据库里的落点。

举个最小的例子。查询 `SELECT name FROM instructor WHERE dept_name = 'CS'` 经 DML 编译器翻译后，等价的关系代数表达式是 $\Pi_{\text{name}}(\sigma_{\text{dept\_name} = 'CS'}(\text{instructor}))$。优化器可能给出两种物理计划：**全表扫描**（从头到尾扫一遍，逐行判断系名）或**索引扫描**（先沿 `dept_name` 的索引定位到 CS 系的记录，再回表取 `name`）。两种计划返回同样的结果，代价却可能相差几个数量级——评估引擎只负责把选定的计划执行完。<span class="marginnote">"全表扫描 vs 索引扫描"这组对照，是第 11 章《选择运算的算法》的第一课；代价怎么估、计划怎么选，则是第 12 章的主题。</span>

一条查询最终的执行计划，在真实数据库里可以用 `EXPLAIN` 查看。下面是索引扫描计划的示意输出——从下往上看，数据先被索引定位，再被投影：

```
Index Scan using idx_dept_name on instructor
  Index Cond: (dept_name = 'CS')
  ->  Project: name
```

注意执行计划是**一棵树**，叶子是表扫描、内部节点是运算（投影、连接、排序）。优化器要做的，就是在这棵树的巨大候选空间里挑出一棵代价最小的——这是第 12 章《查询优化》的主题。

## 3 事务管理器与 ACID

存储管理器里的**事务管理器**是 DBMS 正确性的守门员。它保证**事务（transaction）**——数据库操作的原子执行单元——满足四条性质，合称 **ACID**：

**原子性（Atomicity）**：事务要么全做、要么全不做。
**一致性（Consistency）**：事务执行前后，数据库都满足完整性约束。
**隔离性（Isolation）**：并发执行的事务相互不可见，如同串行执行。
**持久性（Durability）**：事务提交后，其结果对系统故障免疫。

事务管理器配合**恢复管理器（recovery manager）**，在系统故障后把数据库恢复到某个一致状态。<span class="marginnote">ACID 是本专题第四篇《事务》的整篇主题。现在只需记住一个画面：崩溃发生时，要么事务没提交（撤销），要么已提交但数据没来得及写盘（重做）。</span>

看一个经典例子理解 ACID 为什么重要。银行转账：从 A 账户扣 100 元，再往 B 账户加 100 元。这两步要么都发生、要么都不发生——原子性保证不会出现"扣了没加"的中间状态。若两步之间系统崩溃，恢复管理器根据日志把已扣的钱退回（撤销）或把未加的补上（重做），从而回到一致状态。并发时两个事务同时读写同一账户，隔离性保证它们互不看到对方的中间结果。

在 SQL 里，这两步被显式包进一个事务：

```sql
BEGIN;
UPDATE account SET balance = balance - 100 WHERE account_id = 'A';
UPDATE account SET balance = balance + 100 WHERE account_id = 'B';
COMMIT;
```

`BEGIN` 开事务、两条 `UPDATE` 是事务体、`COMMIT` 提交。任何一个环节出问题，都可以 `ROLLBACK` 整体撤销。数据库保证：要么 `COMMIT` 成功后两步全部生效，要么什么都没发生——这就是原子性的 SQL 形态。

## 4 公式解析：磁盘存取的代价

理解存储管理器，先要理解"磁盘到底有多慢"。一次磁盘存取的总时间可写成三项之和：

$$T_{\text{access}} = t_{\text{seek}} + t_{\text{rotational}} + t_{\text{transfer}}$$

逐项拆解：

- **寻道时间 $t_{\text{seek}}$**：把磁头臂移动到目标磁道的时间。这是最大头，典型值约 $4$–$10\,\mathrm{ms}$。
- **旋转延迟 $t_{\text{rotational}}$**：盘片转半圈、让目标扇区转到磁头下的平均时间。对 $7200$ 转/分的磁盘，$t_{\text{rotational}} = \dfrac{1}{2} \cdot \dfrac{60}{7200}\,\mathrm{s} \approx 4.17\,\mathrm{ms}$。
- **传输时间 $t_{\text{transfer}}$**：真正读写数据块的时间，取决于块大小与带宽，典型一块 $4$–$16\,\mathrm{KB}$ 只需零点几毫秒。

代入典型值得：

$$T_{\text{access}} \approx 5\,\mathrm{ms} + 4.17\,\mathrm{ms} + 0.2\,\mathrm{ms} \approx 9.4\,\mathrm{ms}$$

**一个直观结论**：一次磁盘 I/O 大约花 $10\,\mathrm{ms}$，而主存访问约 $100\,\mathrm{ns}$——磁盘比内存慢了约 10 万倍。因此数据库的一切性能技巧，本质都是"**少做随机 I/O、多做顺序 I/O、尽量把热数据留在内存**"。这个数量级直觉，是理解第 9–12 章全部索引与查询优化算法的前提。<span class="marginnote">$10\,\mathrm{ms}$ 有多慢？一台 3 GHz 的 CPU 在这段时间里能执行约三千万条指令。B+ 树把"一次查询"设计成几次磁盘访问，就是在拼命省这 10 ms。</span>

再进一步，**顺序 I/O 与随机 I/O 的差距**。一次随机读要付完整的寻道加旋转延迟（约 $9\,\mathrm{ms}$）；而一次顺序读，把磁头停在一条磁道上连续读多个块，每块只付传输时间（零点几毫秒）。所以"把随机访问改成顺序访问"常常能带来上百倍的提速——外部归并排序（第 11 章）、批量写日志（第 15 章）的设计动机，都藏在这一个数字对比里。

## 5 小结

- 数据库引擎三大子系统：**存储管理器、查询处理器、事务管理器**。
- 存储管理器含权限与完整性/事务/文件/缓冲区管理器，维护数据文件、数据字典与索引。
- 查询处理器流水线：**SQL → 关系代数 → 执行计划 → 评估引擎**。
- 事务管理器保证 **ACID**（原子性、一致性、隔离性、持久性）。
- 磁盘存取代价 $T = t_{\text{seek}} + t_{\text{rotational}} + t_{\text{transfer}} \approx 10\,\mathrm{ms}$，比内存慢约 10 万倍——一切优化都在为省磁盘 I/O。
