## 为什么从触发器开始

上一节的函数与过程有一个共同点：**必须被显式调用**——应用发一条 CALL 语句，数据库才执行。但现实里很多逻辑希望在**数据变化的那一刻自动执行**：删除教师前先审计是谁删的、插入选课记录后自动累加学分、工资表更新后立刻同步到备份表。这就是**触发器（trigger）**——它不等人来调用，而是被**事件**触发。

触发器把数据库从「被动响应查询」的系统，升级为「主动感知变化」的系统——学术界称之为**主动数据库（active database）**。它的核心是一句 **ECA 规则**：**事件（Event）发生 → 检查条件（Condition）→ 执行动作（Action）**。这一节把触发器的定义语法、行级与语句级的区别、以及它容易引发的「连锁反应」讲透。

## 1 ECA 模型：事件、条件、动作

**触发器（trigger）**：当特定数据库事件（插入 / 修改 / 删除）发生在特定关系上时，自动执行的程序。任何触发器都由三要素构成：

- **事件（Event）**：INSERT、UPDATE、DELETE，可限定在某张表，甚至某几列。
- **条件（Condition）**：WHEN 子句，事件发生后先检查它，为真才执行动作。
- **动作（Action）**：要执行的语句块，可以是一条 SQL，也可以是一段过程。

三个词合起来就是触发器的完整语义。**「事件」是触发开关，「条件」是闸门，「动作」是被执行的工作**。<span class="marginnote">ECA 模型不只是数据库的：规则引擎、事件驱动架构、甚至「If This Then That」这类自动化服务都是同一个三件套。理解触发器，等于理解了一整类反应式系统。</span>

## 2 CREATE TRIGGER：语法与实例

创建触发器的标准语法是：

```sql
CREATE TRIGGER timeslot_check1
BEFORE INSERT OF time_slot_id ON section
REFERENCING NEW ROW AS nrow
FOR EACH ROW
WHEN (nrow.time_slot_id NOT IN (SELECT time_slot_id FROM timeslot))
RAISE EXCEPTION 'Invalid time slot ID';
```

这个例子来自 Silberschatz：在 section 表插入前检查时间槽是否合法，非法就抛异常、拒绝插入。关键关键字逐个解读：

**BEFORE / AFTER**：动作在事件之前还是之后执行。
**FOR EACH ROW**：对受影响**每一行**执行一次动作。
**NEW**：指代「新插入 / 更新后」的那一行。<span class="marginnote">NEW 与 OLD 是行级触发器里最关键的两个伪元组：NEW 只有 INSERT，OLD 只有 DELETE，UPDATE 两者都有（NEW 是改后值，OLD 是改前值）。</span>

一个更实用的例子——记录谁改过工资表：

```sql
CREATE TRIGGER salary_audit
AFTER UPDATE OF salary ON instructor
REFERENCING NEW ROW AS nrow, OLD ROW AS orow
FOR EACH ROW
INSERT INTO audit_log (who, old_salary, new_salary)
VALUES (USER, orow.salary, nrow.salary);
```

每次工资被改，审计表自动多一行。**审计（audit）是触发器最经典的应用**：改动本身不产生日志，但触发器保证「每次改动都有记录」。

## 3 行级与语句级：触发粒度的语义

FOR EACH ROW 是**行级触发器**——每影响一行执行一次。与之相对的是**语句级触发器** FOR EACH STATEMENT——整条语句只执行一次，不管它影响了多少行。

这两者的差异在批量更新时极其明显。执行 UPDATE 更新了 1000 行：

行级触发器：动作执行 **1000 次**，每次能看到这一行的 NEW / OLD。
语句级触发器：动作执行 **1 次**，不关心具体哪一行，适合「这条语句改了多少行」这类聚合语义。

**辨析｜易错点：** 该用哪种粒度取决于「动作是否需要逐行数据」。**要做逐行审计，用行级；要做语句级统计或权限检查，用语句级。** 把逐行逻辑写进语句级触发器（没有 NEW / OLD 可用），或把 1000 次无关的重复动作塞进行级触发器，都是常见错误。<span class="marginnote">行级触发器在批量写时开销线性放大；对「更新 100 万行」的操作，一个没必要的行级触发器足以把一条秒级语句拖成分钟级。性能调优时第一个要查的就是触发器。</span>

现代数据库（如 PostgreSQL）还提供**过渡表（transition table）**：把一条语句涉及的所有旧行 / 新行装进临时表，让语句级触发器也能访问行的集合——它缓解了「行级 vs 语句级」的二选一。

## 4 触发器的危险：连锁反应与不可预测

触发器最迷人的地方，也是最危险的地方：**触发器的动作里又可以触发别的触发器**，形成连锁。考虑：

1. 触发器 $T_1$ 在 A 的 UPDATE 后更新 B；
2. B 表上又有个 UPDATE 触发器 $T_2$，它会再去改 A；
3. 改 A 又触发 $T_1$……

这就形成了**触发器环（trigger cascade）**。数据库对此的态度各不相同：有的（如 PostgreSQL）默认**不递归**——同一条语句的连锁触发器只触发一轮；有的会一直递归，直到某处主动终止或检测到无限循环而报错。<span class="marginnote">触发器环是生产事故的高发区：一次普通的 UPDATE 像多米诺一样带崩整库。排查时要能「按触发器链条逐环回放」，这也是触发器代码必须写得像普通程序一样有注释、有边界的原因。</span>

**辨析｜易错点：** 触发器动作**与触发它的语句共享事务**：语句失败，触发器动作一起回滚；触发器抛异常，整个语句也失败。很多人误以为「触发器是额外的、可有可无的补充」，实则它是事务的一部分——**触发器的失败 = 原操作的失败**。所以别在触发器里放「最好失败但别影响主流程」的代码，它会拖垮主流程。

## 5 公式解析：触发器如何维护派生数据

触发器最常见的实用场景是**维护派生数据**：一行被插入或删除，某个汇总值要同步更新。以选课为例，学生每通过一门课，总学分要增加；删除记录，则要扣回。

设 takes 记录选课，student 表维护 tot_cred。插入一门课（学分 $c$）与删除一门课，对 tot_cred 的影响可以写成：

$$
\Delta = \text{sgn} \times c, \qquad
\text{sgn} =
\begin{cases}
+1, & \text{INSERT}\\
-1, & \text{DELETE}\\
0, & \text{UPDATE 不改学分}
\end{cases}
$$

于是触发器做的事是：

$$
\text{tot\_cred}_{\text{new}} = \text{tot\_cred}_{\text{old}} + \Delta
$$

逐项拆解这条「增量维护」公式：

- **增量而非全量**：如果不用触发器，每次查询时从头**聚合（SUM）**所有选课记录也能得到总学分——但那要扫描整张 takes 表。触发器把计算**平摊到每次写入**：插入一行，只做一个 O(1) 增量加法。<span class="marginnote">「写时增量、读时零成本」是派生数据维护的两条路线之一；另一条是「读时现算」。触发器的增量维护换取了读快，代价是写变慢且逻辑分散——这正是后面数据存储与查询权衡反复出现的主题。</span>
- **$\text{sgn}$ 决定方向**：INSERT 加、DELETE 减、UPDATE 视情况——一个触发器需要覆盖所有可能的事件，否则会出现「删了课学分没扣」的不一致。
- **与事务的耦合**：这段加法在事务里执行，如果事务后来回滚，学分修改一并回滚——派生数据与源数据**永远一致**，这是触发器维护派生数据相对「定时重算」的巨大优势。

触发器不是维护派生数据的唯一手段，但它是「即时、一致、自动」三者兼备的那个。把 ECA 语义想清楚，触发器就能成为可靠的自动机制，而不是失控的连锁反应。

## 6 小结

- **触发器（trigger）**：事件发生时自动执行的程序，三要素为**事件（Event）、条件（Condition）、动作（Action）**。
- **语法**：CREATE TRIGGER + BEFORE / AFTER + FOR EACH ROW / FOR EACH STATEMENT + WHEN 条件。
- **NEW / OLD**：行级触发器里的伪元组，NEW 只有 INSERT，OLD 只有 DELETE，UPDATE 两者都有。
- **行级 vs 语句级**：行级逐行执行、可访问 NEW/OLD；语句级整条语句执行一次，适合聚合语义。
- **触发器与事务同生共死**：触发器失败 = 原语句失败；触发器动作随事务一起提交或回滚。
- **触发器环**是连锁事故源：动作里触发触发器会级联，生产环境要警惕环并限制递归深度。
- 触发器的经典应用：审计日志、完整性检查、派生数据（汇总值）的增量维护。
