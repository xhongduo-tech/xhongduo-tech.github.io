## 为什么从 TCC 开始

2PC/3PC 是「数据库层」的强一致方案，但现实里大量分布式事务发生在**应用与微服务**之间——没有共享数据库，也付不起 2PC 的锁与阻塞代价。**TCC（Try-Confirm-Cancel）**是应用层的补偿式分布式事务：把每个业务操作拆成 Try（预留）、Confirm（确认）、Cancel（取消）三个子操作，**用「业务补偿」代替「数据库锁」**。这一节讲 TCC 的三阶段、它与 2PC 的本质区别、以及落地时的工程要点。TCC 是阿里 Seata、微服务分布式事务的主流方案——**它回答「不用 2PC，分布式事务还能怎么做」**。

## 1 TCC 的三个阶段

**TCC（Try-Confirm-Cancel）**：每个参与者（微服务）把业务操作实现为三个子操作：

- **Try（预留）**：检查并**预留**资源，**不真正提交**。如转账时「冻结」账户金额——账户余额减少但被冻结，不可用。
- **Confirm（确认）**：真正完成业务——把「预留」变成「实际扣款」。Try 成功后**必然可 Confirm**（资源已预留）。
- **Cancel（取消）**：回滚——把「预留」的资源释放。Try 失败或全局中止时调用。

**全局流程**：主事务协调者（事务管理器）：

1. **Try 阶段**：调用所有参与者的 Try——全部成功则进入 Confirm；任一失败则进入 Cancel。
2. **Confirm 阶段**：调用所有参与者的 Confirm——最终完成。
3. **Cancel 阶段**：任一 Try 失败时，调用**已 Try 成功**的参与者的 Cancel——补偿回滚。

**核心要点：TCC 把「锁」换成「预留」。** Try 不持有数据库锁（冻结是业务状态），Confirm/Cancel 是**应用逻辑**——不阻塞、不占用长事务资源。

## 2 TCC 与 2PC 的本质区别

| 维度 | 2PC | TCC |
| --- | --- | --- |
| 层 | 数据库/资源层 | **应用/业务层** |
| 资源占用 | 数据库锁（全程） | **业务预留**（无 DB 锁） |
| 实现 | 数据库内置（XA） | **业务代码实现** |
| 隔离性 | 强（锁保证） | **无隔离保证**（业务自管） |
| 一致性 | 强一致（原子提交） | 最终一致（补偿） |
| 性能 | 慢（锁 + fsync） | 快（无锁） |
| 依赖 | 数据库支持 XA | 任何存储 |

**核心要点：TCC 用「业务补偿」替代「数据库原子性」。** 它**不保证瞬时原子**——Try 成功的参与者在 Confirm 前，其「预留」状态对外可见（隔离性弱）；最终通过「全 Confirm 或全 Cancel」达到**最终一致**。<span class="marginnote">TCC 的「预留」让 Confirm 阶段<strong>必定成功</strong>（资源已锁定），这是它与朴素补偿（先做后撤）的关键区别——Confirm/Cancel 不依赖业务条件，只执行预定的资源流转，因此<strong>幂等可重试</strong>。</span>

## 3 公式解析：TCC 的一致性窗口

设参与者 $P_1, \dots, P_n$，Try 阶段 $P_i$ 成功、$P_j$ 失败（$i < j$）：

$$
\text{最终状态} = \bigcup_{k \le i} \text{Cancel}(P_k) \quad \text{（已 Try 成功的全部取消）}
$$

- **第一步，$P_j$ Try 失败**：全局决定 Cancel。
- **第二步，已成功的 $P_i$ 取消**：$P_1 \dots P_i$ 各执行 Cancel——资源释放。
- **第三步，最终一致**：所有参与者的业务状态回到「事务前」——**但中间态（预留期）对外可见**。
- **第四步，窗口**：从「$P_i$ Try 成功」到「$P_i$ Cancel 完成」之间，外部可能看到「资源被冻结」的中间状态——**隔离性由业务约定**。

## 4 TCC 的工程要点

**幂等性**：Confirm/Cancel 可能**重复调用**（重试、协调者恢复）——必须**幂等**（重复执行结果不变）。

**空回滚**：Cancel 可能被调用到「Try 从未执行过」的参与者——要能安全跳过（空回滚）。

**悬挂**：Try 被延迟执行时，Cancel 已先到——**不能出现「Cancel 后再 Try」的悬挂**。

**确认与取消的可靠性**：Confirm/Cancel 也要**记录日志 + 重试**——TCC 的协调者需要自己的持久化与重试机制。

**核心要点：TCC 的正确性靠「幂等 + 空回滚 + 悬挂处理」三条纪律。** 这三条是 TCC 落地最容易踩的坑——补偿逻辑写得不幂等，重试就会造成重复扣款。

**辨析｜易错点：** **TCC 不是「不用日志」**——它只是把「数据库事务日志」换成「应用级补偿 + 重试记录」。Confirm/Cancel 的调用记录、Try 的状态，都需要持久化，否则协调者崩溃后无法恢复全局状态。**TCC 的可靠性从「数据库保证」转移到了「应用框架保证」**。

## 5 小结

- TCC：**Try（预留）→ Confirm（确认）→ Cancel（取消）**——业务补偿代替数据库锁。
- 与 2PC 区别：应用层 vs 数据库层、业务预留 vs 数据库锁、最终一致 vs 强一致。
- Confirm/Cancel 是**幂等**业务操作——Try 成功后 Confirm 必然成功。
- 一致性窗口：Try 成功到 Cancel 完成之间的「预留」状态对外可见。
- 工程纪律：**幂等、空回滚、防悬挂**；协调者需持久化与重试。
