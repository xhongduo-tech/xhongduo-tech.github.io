## 为什么从键值与文档开始

NoSQL 四大模型里，**键值存储**与**文档数据库**是「把数据看作单条记录」的两个代表——区别在「值」的结构化程度：键值的值是不透明的，文档的值是可查询的 JSON。这一节把两者的内部机制（索引、分区、复制）、适用场景与局限讲透——以 Redis 与 MongoDB 为具体参照。理解「键值 vs 文档」的差别，就理解了 NoSQL「灵活度与能力」的光谱起点。

## 1 键值存储：极简到极致

**键值存储（key-value store）**：数据模型 = `key → value`，核心操作 `GET` / `PUT` / `DELETE`。

**内部机制（以 Redis 为例）**：

- **内存为主**：Redis 数据驻内存，读写微秒级；持久化靠 RDB 快照 + AOF 日志。
- **数据结构**：value 不只是字符串，还有 List、Hash、Set、Sorted Set——**有序集合（ZSET）**用跳跃表实现范围/排名查询。
- **分区**：Redis Cluster 用**一致性哈希槽**（16384 个 slot）水平扩展。
- **复制**：主从 + 哨兵/Raft 选主。

**核心要点：键值存储的「快」来自「简单」——没有二级索引、没有 JOIN、没有复杂查询。** 它的价值在于**把「按主键取数据」这条路径做到极致**——缓存、会话、计数器、分布式锁（`SETNX`）都是它的主场。

**公式解析：Redis 为何快**

一次 Redis 操作的时间组成：

$$
T_{\text{redis}} \approx T_{\text{内存访问}} + T_{\text{网络}} \approx 0.1\mu s + 0.1ms
$$

- **第一步，内存访问**：数据在内存哈希表，~100ns。
- **第二步，网络**：RTT 主导（0.1-1ms）。
- **第三步，单线程**：Redis 单线程事件循环，避免锁竞争——吞吐高（十万级 QPS）。
- **第四步，代价**：单线程 = 单命令原子，但**大 key/慢命令阻塞所有请求**——「不要用 Redis 跑慢查询」。

## 2 文档数据库：可查询的 JSON

**文档数据库（document store）**：值 = **文档（JSON/BSON）**，可嵌套、可索引、可查询字段。

**内部机制（以 MongoDB 为例）**：

- **文档模型**：一条记录 = 一个文档，字段可动态增删——**无固定 schema**。
- **二级索引**：可对任意字段建索引（B+ 树）。
- **查询语言**：类 JSON 的查询（`{age: {$gt: 18}}`）+ 聚合管道（`$match`/`$group`/`$lookup`）。
- **分区**：按分片键（shard key）范围/哈希分区。
- **复制**：副本集（replica set），主从 + 多数派选主。

**核心要点：文档数据库 = 「灵活模式 + 二级索引 + 类 SQL 查询」。** 它比键值强在「能按字段查」，比关系库弱在「无 JOIN、无跨文档事务（除单文档原子性）」。

## 3 键值 vs 文档：对比

| 维度 | 键值存储 | 文档数据库 |
| --- | --- | --- |
| 值 | 不透明字节/简单对象 | **结构化 JSON，可查询** |
| 二级索引 | ❌ | ✅ |
| 范围/排名 | 有序键/有序集合可 | ✅ |
| 复杂查询 | ❌ | ✅（聚合管道） |
| 事务 | 单键原子 | **单文档原子** |
| 典型场景 | 缓存、会话、计数 | 内容、目录、用户资料 |
| 代表 | Redis、DynamoDB | MongoDB、CouchDB |

**辨析｜易错点：** **DynamoDB 是键值还是文档？** ——它是**两者都有**的「混合」：按键值 API 提供 `get/put`，也支持 JSON 文档与二级索引。**「键值 vs 文档」不是排他分类，而是「值的结构化程度」的光谱**——Redis 的 Hash、DynamoDB 的文档、MongoDB 的文档，是光谱上的不同点。

## 4 文档数据库的建模：内嵌 vs 引用

文档数据库用两种方式表达「关系」：

- **内嵌（embedding）**：把相关数据嵌进文档——订单内嵌商品列表。**单文档原子性**（一次读全），但数据冗余（商品改名要改所有订单）。
- **引用（referencing）**：文档里存**对方 ID**——需应用层二次查询（类似 JOIN）。不冗余，但查询要多跳。

**公式解析：内嵌 vs 引用的取舍**

设「一对多」关系（订单 → 商品），内嵌 vs 引用的读代价：

$$
T_{\text{内嵌}} = 1 \text{ 次读}（整文档带子数据）, \qquad
T_{\text{引用}} = 1 + k \text{ 次读}（父 + k 个子文档）
$$

- **第一步，内嵌**：一次读拿到订单 + 全部商品——快，但子数据**随父文档复制**。
- **第二步，引用**：先读订单、再逐个读商品——$k+1$ 次读，但商品数据**单点存储**。
- **第三步，取舍**：**内嵌适合「子数据随父读、变化少」**（订单快照）；**引用适合「子数据独立变化、被多父共享」**（商品信息）。
- **第四步，与关系库对照**：内嵌 ≈ 反规范化（冗余换速度），引用 ≈ 外键（规范 + 连接）——**NoSQL 建模的「内嵌/引用」就是关系建模的「反规范/规范」**。

## 5 小结

- **键值存储**：`key→value` 极简，主键操作极致快——缓存/会话/锁的主场。
- Redis 快在**内存 + 单线程 + 简单**；持久化靠 RDB/AOF。
- **文档数据库**：JSON 文档 + 二级索引 + 聚合查询——灵活模式，无 JOIN/无跨文档事务。
- 键值 vs 文档是「值的结构化程度」的光谱，不是排他分类。
- 文档建模：**内嵌**（冗余换单读）vs **引用**（规范换多读）——与关系建模同构。
