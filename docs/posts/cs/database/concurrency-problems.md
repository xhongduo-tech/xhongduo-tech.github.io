## 为什么从并发问题开始

为什么不让事务「一个接一个」串行执行？——那样绝对正确，但太慢：一个事务等待时，CPU、磁盘都闲着。**并发执行（concurrent execution）**让多个事务交错进行，提升吞吐与响应。但并发带来四种经典异常：**丢失更新、脏读、不可重复读、幻读**。这一节讲清「为什么必须并发」以及「并发会出什么乱子」——这些异常是下一节「可串行化」要消灭的目标，也是第 13 章隔离级别的划分依据。

## 1 并发执行的必要性

**并发执行的必要性**有三条：

1. **吞吐量（throughput）**：单位时间处理的事务数——并发让 CPU、I/O 都忙起来。
2. **平均响应时间**：短事务不必等长事务完成——多个事务并行推进。
3. **资源利用率**：一个事务等待 I/O 时，另一个事务用 CPU——硬件不空转。

**核心要点：并发是性能的必然要求，代价是正确性风险。** 数据库的并发控制（第 14 章）就是要「既要并发的好处，又要串行的正确性」——这正是「可串行化」标准的由来。

## 2 四种经典异常

**异常 1：丢失更新（lost update）**

两个事务同时读同一值，各自修改后写回，后写覆盖先写：

```text
T1: 读 A = 100
T2: 读 A = 100
T1: 写 A = 50
T2: 写 A = 80      ← 基于过期的 100 计算，覆盖 T1 的 50
最终 A = 80，T1 的更新丢失
```

**异常 2：脏读（dirty read）**

一个事务读到另一个**未提交事务**的修改：

```text
T1: 写 A = 200   （未提交）
T2: 读 A = 200    ← 脏读：读到未提交的修改
T1: 回滚，A 恢复为 100
T2 基于已消失的 200 继续执行
```

**异常 3：不可重复读（non-repeatable read）**

同一事务内两次读同一行，结果不同（被并发事务修改并提交）：

```text
T1: 读 A = 100
T2: 写 A = 200 并提交
T1: 再读 A = 200   ← 同一事务两次读，结果不同
```

**异常 4：幻读（phantom read）**

同一事务两次查询同一范围，第二次多出/少掉行（被并发插入/删除）：

```text
T1: 查询 salary > 50000  → 返回 5 行
T2: 插入 salary = 60000 的新行并提交
T1: 重查 salary > 50000  → 返回 6 行  ← 多出的行就是幻影
```

**辨析｜易错点：** 四种异常是**递进关系**：脏读（未提交可见）→ 不可重复读（已提交更新可见）→ 幻读（已提交插入/删除可见）。**隔离级别正是按「允许哪些异常」划分的**——这一节的异常清单是下一节隔离级别的直接输入。

## 3 公式解析：并发问题的统一视角

四种异常都可以用一个统一框架理解——**调度（schedule）**：

$$
\text{调度} = \text{多个事务操作的某种交错顺序}
$$

- **第一步，操作序列**：把多个事务的操作排成一个全局顺序（调度）。每个事务内部保持顺序，事务之间可交错。
- **第二步，串行调度**：无交错——事务一个接一个，绝对正确。
- **第三步，等价性**：若某个并发调度的结果等价于某个串行调度，则并发正确。
- **第四步，异常 = 不等价**：丢失更新、脏读等都是「并发调度的结果无法对应任何串行调度」的具体表现——**消灭异常 = 让调度等价于串行**。

## 4 并发控制的必要性总结

**核心要点：并发控制的目标是「让并发调度的效果等价于某串行调度」。** 这个目标就是下一节的「可串行化」——数据库用锁、时间戳、多版本等手段，把并发调度「约束」到可串行化的范围内。

| 异常 | 本质 | 防住它的隔离级别 |
| --- | --- | --- |
| 丢失更新 | 写-写冲突 | 需要锁（任何写互斥） |
| 脏读 | 读-未提交写 | 读已提交 |
| 不可重复读 | 读-已提交写 | 可重复读 |
| 幻读 | 读-插入/删除 | 可串行化 |

**连接点：** 这一节的异常清单贯穿第 13、14 章——隔离级别按「防哪些异常」划分，锁协议按「防哪类冲突」设计，MVCC 用「版本快照」同时防多种异常。**带着这四种异常的名单读后两章，每个协议都在回答「它防住了哪一个」**。

## 5 并发异常的数值算例与术语速查

**把四种异常放到一个银行转账场景里，看它们怎么连环出现。** 设账户 A 余额 1000，T1 给 B 转账 200、T2 给 A 存 100。

- **丢失更新**：T1、T2 都读 A=1000，T1 写 A=800、T2 写 A=1100——后写覆盖先写，**T1 的转账效果丢失**。
- **脏读**：T1 写 A=800（未提交），T2 读 A=800——T1 回滚，T2 的后续决策基于已消失的值。
- **不可重复读**：T2 先读 A=1000，T1 提交转账后 T2 再读 A=800——同事务两次读不同。
- **幻读**：T2 查「余额 > 500 的账户」返回 2 行，T1 插入新账户后 T2 重查返回 3 行。

**数值算例：并发的吞吐收益** 设每个事务耗时 20ms，其中 15ms 是 I/O 等待。

- 串行：每秒最多 50 个事务——CPU 在等 I/O 时空转。
- 4 路并发：I/O 等待被其他事务的计算填补，吞吐约 4 倍——**并发把「等待时间」变成「他人干活的时间」**。
- **代价**：并发越多，异常发生概率越高——**并发控制（第 14 章）正是在「并发收益」与「异常风险」之间找平衡**。

**辨析｜易错点：** 「丢失更新」常被误当成「不可重复读」——两者不同：丢失更新是**写-写**冲突（两事务都写、后者覆盖），不可重复读是**读-写**冲突（一事务读、另一事务写后提交）。**「谁在写」决定它是哪种异常**——写-写要锁，读-写靠隔离级别。

<span class="marginnote">把四种异常与第 14 章协议对照：<strong>丢失更新靠「写互斥」（锁）、脏读靠「读已提交」、不可重复读靠「可重复读」、幻读靠「谓词锁/间隙锁或快照」</strong>——每种异常对应一种「防它的机制」。先记住异常清单，后面每个协议都是在「回答防住哪一个」。</span>

### 术语速查

| 术语 | 含义 |
| --- | --- |
| 丢失更新 | 写-写冲突，后者覆盖前者 |
| 脏读 | 读到未提交修改 |
| 不可重复读 | 同事务两次读不同 |
| 幻读 | 同条件结果集变多 |
| 调度 | 事务操作的交错顺序 |
| 串行调度 | 无交错的绝对正确调度 |

## 6 小结

- 并发执行提升**吞吐、响应、资源利用**，代价是正确性风险。
- 四种异常：**丢失更新、脏读、不可重复读、幻读**——递进关系。
- 统一视角：并发调度要**等价于某串行调度**，异常 = 不等价。
- 并发控制目标 = 可串行化：用锁/MVCC 把调度约束到正确范围。
- 隔离级别按「允许哪些异常」划分——异常清单是隔离级别的输入。
