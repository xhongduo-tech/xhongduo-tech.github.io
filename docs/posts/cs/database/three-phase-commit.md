## 为什么从 3PC 开始

2PC 的硬伤是「协调者崩溃时参与者无限阻塞」。**三阶段提交（Three-Phase Commit, 3PC）**在 2PC 的「准备」与「提交」之间插入一个「**预提交（pre-commit）**」阶段，让参与者**在没有协调者时也能安全地自行决定**——从而在**无故障延迟假设下**消除阻塞。这一节讲 3PC 的三个阶段、它如何缩小阻塞窗口、以及它的两个致命局限（「假定网络可靠」与「协议复杂」，且**不能完全消灭阻塞**）。3PC 是理论课上「2PC 的改进」，但工程上几乎不用——**它的局限解释了为什么现实用 2PC + 共识，而非 3PC**。

## 1 三阶段流程

3PC 三个阶段：

**阶段 1（准备，Vote）**：同 2PC——协调者问参与者能否提交，参与者投票。

**阶段 2（预提交，Pre-Commit）**：若全票 Yes，协调者广播 `Pre-Commit`——参与者**进入「预提交」状态**（锁仍持有，但已确认「将提交」）。

**阶段 3（决定，Commit）**：协调者广播 `Commit`，参与者提交。

**核心要点：预提交阶段是「提交的预告」。** 参与者收到 `Pre-Commit` 就知道「全局倾向提交」——即使协调者此时崩溃，参与者也可以**相互协商**（只要超时未收到最终决定、且多数参与者已收到 Pre-Commit）**自行提交**。

## 2 为什么能减少阻塞

**3PC 的关键洞察**：参与者从「准备就绪」推进到「预提交」后，**不再需要协调者也能决定**。

- 若参与者已收到 `Pre-Commit`（全局倾向提交）→ 协调者崩溃 → **主动提交**（因为全局已无中止可能，全票 Yes 且已预提交）。
- 若参与者**未收到** `Pre-Commit`（还停在准备就绪）→ 协调者崩溃 → **主动中止**（全局可能还没决定提交）。

**公式解析：3PC 的「无协调者决定」规则**

设参与者 $P_i$ 超时未收到协调者决定：

$$
P_i \text{ 决定} = 
\begin{cases}
\text{提交}, & P_i \text{ 已收到 } Pre\text{-}Commit \text{（全局倾向提交）} \\
\text{中止}, & P_i \text{ 只投了 } Yes \text{ 未收到 } Pre\text{-}Commit
\end{cases}
$$

- **第一步，收到 Pre-Commit 则提交**：多数参与者都进入预提交 → 协调者必会发 Commit（或有别的参与者推进）——**提交是安全选择**。
- **第二步，未收到则中止**：全局可能还没到提交阶段 → 中止安全。
- **第三步，阻塞窗口缩小**：协调者崩溃时，参与者**基于自身状态**就能决定——不再无限等待。
- **第四步，代价**：每个参与者要能**相互协商**（知道「多数派的状态」）——协议复杂度大增。

## 3 3PC 的两个致命局限

**局限 1：假定网络可靠（partially synchronous 的乐观）。** 3PC 的「无协调者自行决定」依赖「参与者能相互通信」。若发生**网络分区**——一部分参与者收到 Pre-Commit、另一部分没收到——两部分会**做出相反决定**（一边提交一边中止）——**一致性被破坏**。<span class="marginnote">3PC 只解决「协调者崩溃」，不解决「网络分区」。而现实里网络分区（节点间的「脑裂」）与崩溃同样常见——3PC 在分区下会分裂。<strong>这就是「2PC 阻塞但安全、3PC 不阻塞但不安全」的取舍根源</strong>。</span>

**局限 2：不能完全消灭阻塞。** 在「协调者崩溃 + 网络分区」同时发生时，参与者无法知道其他参与者的状态——仍可能阻塞。**3PC 只是把阻塞的「概率窗口」缩小，不能根除**（上一节已证：非阻塞原子提交在有故障时不存在）。

**核心要点：3PC 用「假定部分同步」换「减少阻塞」，但网络分区让它不安全。** 工程上「安全」永远优先于「不阻塞」——所以现实系统宁可用「阻塞但安全的 2PC」或「共识化协调者」。

## 4 为什么工程不用 3PC

| 维度 | 2PC | 3PC |
| --- | --- | --- |
| 阻塞 | 有（协调者崩溃） | 减少（但分区下不安全） |
| 网络分区 | 安全（阻塞等待） | **不安全（可能分裂）** |
| 复杂度 | 中 | 高（预提交 + 相互协商） |
| 工程使用 | **广泛（XA、分布式事务）** | 几乎不用 |
| 现实替代 | 2PC + Raft | — |

**辨析｜易错点：** **3PC 不是「更好的 2PC」**——它在「减少阻塞」上改进，却在「分区安全」上退步。工程实践的正确路线是：**2PC 处理「原子提交」，Raft 处理「协调者高可用」**（Spanner、TiDB 的做法）——两者组合既安全又不阻塞在协调者单点上。**3PC 是理论上的中间解，工程上的弃儿**。

## 5 小结

- 3PC = 2PC + **预提交阶段**：参与者超时后**基于自身状态自行决定**。
- 收到 Pre-Commit → 提交；只投 Yes → 中止——**缩小阻塞窗口**。
- 致命局限：**网络分区下两部分参与者可能做出相反决定**（不一致）。
- 3PC 不能根除阻塞（与原子提交不可能性一致）。
- 工程不用 3PC；用 **2PC + Raft**（共识化协调者）保安全与可用。
