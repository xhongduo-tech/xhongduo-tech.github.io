## 为什么从星型模式开始

数据仓库的建模不是 OLTP 的第三范式——它用**维度建模（dimensional modeling）**：**事实表（fact table）**存「发生了什么」（交易、订单），**维度表（dimension table）**存「描述角度」（时间、地点、产品）。星型模式与雪花模式是两种经典的维度建模布局。这一节把两种模式的结构、查询方式、优劣讲透——**它是「数据仓库怎么建表」的标准答案**，也是 BI 报表（第 5 章 CUBE/ROLLUP）的建模基础。

## 1 事实表与维度表

**维度建模的两个基本构件**：

- **事实表（fact table）**：存**度量值**（金额、数量、时长）+ **外键**指向各维度。每行是一次「业务事件」——如一次销售。
- **维度表（dimension table）**：存**描述属性**（时间、地区、产品、客户）。每行是一个「分析角度」——如一个日期、一个地区。

**核心要点：事实表是「数值 + 外键」，维度表是「描述」。** 查询「按地区统计销售额」= 事实表 JOIN 维度表（地区）+ 按维度属性分组聚合。

**公式解析：事实表的粒度**

事实表的**粒度（grain）** = 一行代表什么：

$$
\text{粒度} = \text{「一次销售」} \Rightarrow \text{每行: } (时间FK, 地区FK, 产品FK, 金额, 数量)
$$

- **第一步，确定粒度**：先定「一行是什么」——销售明细、日汇总、还是分钟级。
- **第二步，粒度决定外键**：粒度越细，维度外键越多、事实行越多。
- **第三步，粒度与聚合**：细粒度可聚合出粗粒度（SUM 日汇总）——**粗粒度无法下钻到细**。
- **第四步，工程**：粒度是维度建模的第一步，错了全盘皆错。

## 2 星型模式

**星型模式（star schema）**：**一张事实表在中心，多张维度表围绕它**（像星星）。维度表**不规范化**（直接冗余描述属性）。

```
              ┌── 时间维度 ──┐
              │              │
   产品维度 ──┤  事实表(销售)  ├── 地区维度
              │              │
              └── 客户维度 ──┘
```

**查询**：`SELECT 地区, SUM(金额) FROM 事实 JOIN 地区维度 GROUP BY 地区`——**事实 JOIN 一个维度 + 聚合**。

**优点**：

- **查询简单**：每维一次连接（最多一次 JOIN 一层）。
- **查询快**：维度表小、少规范化，连接少。
- **直观**：分析师好理解。

**缺点**：

- **维度冗余**：维度表反规范化，数据重复（如「产品类别」在每行重复）。
- **维度更新**：改维度属性要改多行。

## 3 雪花模式

**雪花模式（snowflake schema）**：维度表**进一步规范化**——维度属性拆成多级表（如「产品维度」拆成「产品表 + 类别表」），维度表呈雪花状展开。

```
  产品表 ── 类别表 ── 部门表
  事实表（销售）
```

**优点**：

- **省空间**：维度规范化，去冗余。
- **一致性**：维度属性单点存储，改一处。

**缺点**：

- **查询连接多**：维度每级一次 JOIN——雪花查询比星型多连接。
- **复杂**：分析师难以理解多层结构。

**公式解析：星型 vs 雪花的连接代价**

设维度拆成 $d$ 层，一次维度查询：

$$
T_{\text{星型}} = 1 \text{ 次维度 JOIN}, \qquad
T_{\text{雪花}} = d \text{ 次维度 JOIN}
$$

- **第一步，星型**：维度表单层，JOIN 一次。
- **第二步，雪花**：维度拆 $d$ 层，逐级 JOIN $d$ 次。
- **第三步，列存补偿**：列存下雪花的多 JOIN 代价被压缩与向量化缓解——但仍是额外开销。
- **第四步，取舍**：**星型「连接少换冗余」，雪花「省空间换连接」**——现代数据仓库默认星型。

## 4 星型 vs 雪花：怎么选

**核心要点：现代数据仓库几乎都用星型模式。**

| 维度 | 星型 | 雪花 |
| --- | --- | --- |
| 规范化 | 维度不规范化 | 维度规范化 |
| JOIN 次数 | 每维 1 次 | 每维多层 |
| 查询性能 | 快 | 慢（多连接） |
| 存储 | 冗余多 | 省空间 |
| 可理解性 | 直观 | 复杂 |
| 维护 | 简单 | 复杂 |
| 现代倾向 | **默认** | 较少 |

**辨析｜易错点：** **星型的「冗余」在现代列存仓库里不是大问题**——列存压缩率高（第 20 章）、存储便宜，冗余的空间代价远小于「雪花多连接」的查询代价。**「维度冗余换查询简单」是星型胜出的核心**——金博尔维度建模的标准形态就是星型。

**连接点：** 星型模式是第 5 章 `CUBE`/`ROLLUP`（多维聚合）的建模基础——事实表 + 维度表正是「数据立方体的轴与度量」。**「星型 + CUBE」= 数据仓库多维分析的完整链路**。

## 5 小结

- **事实表**：度量 + 维度外键，粒度定义「一行代表什么」。
- **维度表**：描述属性，分析角度。
- **星型模式**：单事实表 + 反规范化维度——连接少、直观、默认选择。
- **雪花模式**：规范化维度——省空间但多连接、复杂。
- 现代仓库默认星型（列存压缩抵消冗余代价）；星型是 CUBE 分析的建模基础。
