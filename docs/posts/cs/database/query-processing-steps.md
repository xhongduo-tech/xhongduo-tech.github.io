## 为什么从查询处理开始

前八章讲「怎么写 SQL、怎么设计表」，但 SQL 是声明式的——你说「要什么」，数据库得自己决定「怎么算」。**查询处理（query processing）**就是数据库执行一条 SQL 的完整流水线：从文本解析，到逻辑重写，到物理优化，再到执行算子。这一节建立整条流水线的**地图**，讲清每一步的输入输出，并解释最核心的概念——**执行计划（execution plan）**。后续各节逐个深入「选择、排序、连接」的物理算法，都是在这张地图上展开的。

## 1 查询处理的四个阶段

一条查询的生命周期：

1. **解析与翻译（parsing & translation）**：SQL 文本 → 语法树 → 关系代数表达式。检查语法错误、表/列是否存在。
2. **优化（optimization）**：关系代数表达式 → 执行计划。找出代价最小的求值方案。
3. **执行（execution）**：执行计划 → 结果。由执行引擎逐算子运行。
4. **结果返回**：结果集返回客户端（可能流式分页）。

**核心要点：SQL 的声明式给了优化空间。** 同一个查询有无数等价执行方式，优化器的职责就是从中选出代价最小的——这是第 12 章的主题。

**解析与翻译的产物**是**关系代数表达式树**：叶子是表（或索引扫描），内部节点是运算符（选择、投影、连接、聚集）。这棵树再经优化器重排，变成**执行计划**。<span class="marginnote">解析→代数树的翻译依赖第 6 章的等价性——SQL 的 `WHERE` 翻译成选择运算、`JOIN` 翻译成连接运算。学过的关系代数在这里真正派上用场。</span>

## 2 执行计划：算子树

**执行计划（execution plan / query plan）**：一棵**算子树（operator tree）**，每个节点是一个执行算子，数据从叶子流到根。

- **叶子算子**：表扫描（`seq scan`）、索引扫描（`index scan`）。
- **内部算子**：选择（`filter`）、投影（`project`）、连接（`nested-loop join` / `merge join` / `hash join`）、聚集（`aggregate`）、排序（`sort`）。
- **数据流**：子节点的输出作为父节点的输入，根节点输出结果。

一个例子：

```sql
SELECT name, course_id
FROM instructor, teaches
WHERE instructor.ID = teaches.ID
  AND dept_name = 'CS';
```

可能的执行计划：

```text
→ Project (name, course_id)
  → Hash Join (instructor.ID = teaches.ID)
    → Seq Scan on instructor, filter: dept_name = 'CS'
    → Hash
      → Seq Scan on teaches
```

**关键概念：同一个查询有多个候选计划。** 上面可以用 Nested Loop 而非 Hash Join、可以先过滤再连接……优化器要枚举候选并选优（第 12 章）。

## 3 查询代价与 I/O 度量

优化器怎么比较两个计划谁更优？靠**代价模型（cost model）**。基本度量单位是**磁盘块访问次数**（第 9 章介质背景）。

**公式解析：查询总代价的构成**

$$
\text{Cost}(E) = \text{Cost}_{I/O}(E) + \text{Cost}_{CPU}(E) + \text{Cost}_{mem}(E)
$$

- **第一步，I/O 代价**：读取的磁盘块数 × 每次访问代价——通常是主导项。
- **第二步，CPU 代价**：比较、运算的指令数。
- **第三步，内存代价**：缓冲池占用量。
- **第四步，优化器的近似**：因为 I/O 主导（第 9 章差 $10^5$），教科书优化器几乎只计 I/O：$\text{Cost} \approx b_r \cdot t_T + s \cdot t_S$（$b_r$ 为读的块数，$t_T$ 传输、$t_S$ 寻道）。**块数越少，计划越优**。

## 4 执行计划的度量指标

除了绝对代价，还有三个指标描述计划执行时的资源特征：

- **流水线（pipelining）**：算子的输出能否**边产边传**给父节点，无需物化整份中间结果——流水线省内存、省磁盘临时文件。
- **物化（materialization）**：中间结果落盘/落内存，供父节点多次读取——牺牲延迟换复用。
- **中间结果大小**：影响内存与临时文件占用。

**辨析｜易错点：** 执行计划是**物理计划**（指定了扫描方式、连接算法、排序方式），不是逻辑表达式。`EXPLAIN` 看到的就是物理计划——它告诉你数据库**实际打算怎么做**，而不只是「要什么」。读懂 `EXPLAIN` 输出是数据库调优的第一技能。

## 5 查询处理的数值算例与术语速查

**把一个查询的执行计划走一遍，把概念落到具体算子。** 设 instructor 表 1 万行、teaches 表 5 万行，查询「CS 系的教师教了哪些课」。

- **解析**：SQL 转成关系代数树——选择(dept='CS')、连接(ID=ID)、投影(name, course_id)。
- **逻辑优化**：把 `dept_name='CS'` 下推到 instructor 叶子——先过滤（只剩约 200 行）再连接，中间结果大幅缩小。
- **物理优化**：估算——instructor 过滤后 200 行、teaches 5 万行。选「小表驱动」的嵌套循环（外层 200 行 × 内层索引查）或哈希连接，比较代价取小者。
- **执行**：按计划逐算子流式执行——先 Seq Scan + Filter 得到 200 行，再对每行走 teaches 的索引找匹配，最后投影输出。
- **EXPLAIN**：上述每一步都反映在 `EXPLAIN` 输出里——**调优的第一步是读懂它**。

**数值算例：选择下推的收益** 设连接前不过滤：instructor 1 万 × teaches 5 万 = 5 亿次比较。

- 下推后：先过滤 instructor 到 200 行，再 200 × 5 万 = 1000 万次比较——**快 50 倍**。
- 若 teaches 也用过滤（如只查本年度）——中间结果再缩小，收益叠加。
- 教训：**谓词下推是逻辑优化里收益最稳定、最普适的一条规则**（第 12 章专讲）。

**辨析｜易错点：** 解析阶段的「关系代数树」与执行阶段的「算子树」是**两棵树**——前者是逻辑层（算子：选择/投影/连接），后者是物理层（算子：Seq Scan/Hash Join/Sort）。**别把「逻辑树」当「物理计划」**：`EXPLAIN` 显示的是物理计划，逻辑树在优化器内部。

<span class="marginnote">把查询处理四阶段与「编译原理」对照：解析 ≈ 词法/语法分析，优化 ≈ 中间代码优化，执行 ≈ 目标代码生成与运行。<strong>SQL 是「面向结果的 DSL」，查询处理器就是它的「编译器 + 虚拟机」</strong>——这也是为什么第三级《编译原理》与数据库查询引擎如此同构。</span>

### 术语速查

| 术语 | 含义 |
| --- | --- |
| 解析 | SQL 文本 → 关系代数树 |
| 优化 | 代数树 → 物理执行计划 |
| 执行计划 | 算子树，从叶子到根流式执行 |
| 代价模型 | 以磁盘块访问为核心的估价 |
| 流水线 | 边产边传，省中间物化 |
| EXPLAIN | 显示物理执行计划的命令 |

## 6 小结

- 查询处理四阶段：**解析 → 优化 → 执行 → 返回**。
- 解析产物是**关系代数树**；优化产物是**物理执行计划**（算子树）。
- 计划从叶子（扫描）到根（输出）**流式执行**，算子包括扫描、过滤、连接、聚集、排序。
- 代价模型以**磁盘块访问**为核心（I/O 主导），兼顾 CPU 与内存。
- 同一查询多计划，优化器选代价最小者；`EXPLAIN` 展示实际计划。
