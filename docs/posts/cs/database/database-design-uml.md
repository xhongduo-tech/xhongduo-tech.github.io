## 为什么从设计问题与 UML 开始

ER 图能画数据库结构，但真实项目里还需要回答更多问题：设计文档给谁看？软件工程里的类图与数据库的 ER 图是什么关系？如何让「代码里的对象」与「数据库里的表」协同？这一节把 ER 模型放回软件工程的语境：看看概念设计的补充问题（设计文档、工具、与应用的衔接），以及 **UML（统一建模语言）**如何用另一种记号体系描述同一件事。UML 类图与 ER 图的对照，是理解「面向对象设计」与「关系设计」差异的钥匙。

## 1 ER 模型没回答的问题

ER 模型专注「数据是什么、怎么关联」，但完整的数据设计还要处理：

- **与应用层的关系**：表结构如何映射成编程语言里的对象？（ORM 的诞生背景）
- **与时序/流程的关系**：数据状态怎么流转？（一个订单从「待付款」到「已发货」）
- **与安全/审计的关系**：谁能看哪些数据、谁改了什么？（第 4 章授权与审计日志）
- **与可演化性的关系**：需求变了，表结构怎么平滑迁移？（模式演进与版本化）

<span class="marginnote">ER 模型是<strong>静态</strong>的：它描述「某一时刻」数据的结构。而真实系统是动态的——订单状态机、审批流、事件日志，这些「随时间变化」的建模需要状态图、活动图等 ER 之外的记号。数据库设计不能只靠一张 ER 图包打天下。</span>

## 2 UML 与 ER：两种建模语言的对照

**UML（Unified Modeling Language）**是软件工程的统一建模语言，其中 **UML 类图（class diagram）**与 ER 图角色相近：都描述「静态结构」。对照如下：

| 维度 | ER 图 | UML 类图 |
| --- | --- | --- |
| 基本元素 | 实体集、联系集、属性 | 类、关联、属性、方法 |
| 属性 | 椭圆，主码下划线 | 类框内列表，主码标注 |
| 联系 | 菱形 + 基数 1/n | 关联线 + 多重性 1..* |
| 继承 | ISA 三角形 | 空心三角箭头 |
| 组合 | 弱实体双矩形 | 实心菱形（组合） |
| 用途 | 数据库概念设计 | 面向对象软件设计 |

**核心要点：ER 面向「数据」，UML 面向「对象」。** 一张 UML 类图除了数据属性，还含**方法**（行为）；而 ER 图纯粹描述数据。当项目用面向对象语言写应用时，常用 UML 类图做主设计，再把类图「降级」成 ER 图或直接转关系模式——两个模型必须保持一致，否则代码与数据库会脱节。

## 3 ORM：对象与表的鸿沟

**对象-关系映射（Object-Relational Mapping, ORM）**（如 Hibernate、Django ORM、SQLAlchemy）试图弥合「对象模型」与「关系模型」的鸿沟，即所谓的**阻抗失配（impedance mismatch）**：

| 对象模型 | 关系模型 | 冲突 |
| --- | --- | --- |
| 对象有身份与引用 | 行靠主码关联 | 引用的粒度不同 |
| 继承体系 | 表/外码 | 继承难以直接表达 |
| 对象图可循环 | 关系需无环外码 | 建模约束不同 |
| 方法/行为 | 纯数据 | 行为无处安放 |

ORM 用「类 ↔ 表、属性 ↔ 列、对象引用 ↔ 外码」的映射消除大部分摩擦，但它**不能消除**所有摩擦——N+1 查询、继承映射策略、延迟加载，都是阻抗失配的余波。<span class="marginnote">「ORM 是银弹吗？」答案是否定的：<strong>对象关系差异是本质性的</strong>——对象强调导航与封装，关系强调集合与声明式查询。ORM 只是把它藏到框架里，工程师仍然需要懂 ER、懂关系模型，才能真正写好 ORM 映射。</span>

**辨析｜易错点：** 用 ORM 不等于懂数据库设计。ORM 生成的表结构默认方案未必满足范式（第 8 章）与查询效率（第 12 章）。成熟的工程实践是「先设计 ER/关系模式，再配置 ORM 映射」，而不是「让 ORM 自动建表听天由命」。

## 4 公式解析：从类图到关系模式的继承映射

UML 类图的继承在关系模型里的映射，与 ER 特化/泛化的转换同构。设有父类 $P$ 与子类 $S_1, \dots, S_k$，三种策略：

$$
\text{Strategy} \in \{\, \text{SingleTable},\; \text{ClassPerTable},\; \text{ConcreteClassPerTable} \,\}
$$

- **第一步，SingleTable**：全部子类并入一张表，用 `type`（判别）列标识类型。查询快、无连接，但大量列为空、约束难写——对应 ER 的「单表策略 A」。
- **第二步，ClassPerTable**：父类一张表 + 每个子类一张表，子类主码 = 父类主码（外码）。数据无冗余、扩展性好，但查子类需要连接——对应 ER 的「策略 B」。
- **第三步，ConcreteClassPerTable**：每个子类独立完整建表。子类各自完整，但无法统一查父类、父类属性重复——对应 ER 的「策略 C」。
- **第四步，选择依据**：三者权衡「查询速度 / 存储冗余 / 模式演化」。ORM 里常用 SingleTable 或 ClassPerTable；没有放之四海皆准的答案，只有负载决定的取舍。

## 5 设计文档与团队协作

概念设计的产物最终要成为**团队共享的设计文档**。好的数据库设计文档包含：

- **ER 图 / 类图**：整体结构一目了然。
- **关系模式清单**：每张表的列、类型、主外码、约束。
- **数据字典**：每个字段的业务含义、取值范围、默认值。
- **设计决策记录（ADR）**：为什么这样设计——「takes 用组合主码而非代理主码」的来龙去脉。

**核心要点：设计文档是「活文档」。** 它随需求演进持续更新，ADR 记录决策动机，让后来的维护者知道「当时为什么这么选」，而不是只看到结果。这与软件工程的文档实践一脉相承——可参考第三级《软件工程》中关于设计文档与可维护性的部分。

## 6 小结

- ER 模型是**静态**数据视图，动态流程与安全审计需要其他建模手段补充。
- **UML 类图**与 ER 图角色对应，但含方法与行为，面向对象；ER 面向纯数据。
- **阻抗失配**是对象模型与关系模型的本质差异，ORM 只是缓解而非消除。
- 继承映射三种策略（SingleTable / ClassPerTable / ConcreteClassPerTable）按负载取舍。
- 设计文档（ER 图 + 模式清单 + 数据字典 + ADR）是团队协作的共享基础。
