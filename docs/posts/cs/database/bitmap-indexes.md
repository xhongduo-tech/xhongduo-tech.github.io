## 为什么从位图索引开始

B+ 树与哈希适合「高基数」列（每行取值不同，如 ID）。但有一类列**基数很低**——性别（2 个值）、状态（几个值）、国家（百个值）。对这种列建 B+ 树索引，每个键都指向海量记录，收益有限。**位图索引（bitmap index）**为低基数列而生：每个取值存一个**位图**（每行一个 bit），等值查询、多条件组合（AND/OR）都用**位运算**解决——极快且省空间。这一节讲位图索引的原理、位图运算与适用场景，顺带浏览其他辅助索引（函数索引、覆盖索引、倒排索引）。

## 1 位图索引的结构

对列 $A$（取值集合 $v_1, \dots, v_k$），位图索引为每个取值 $v_j$ 存一个**位图（bitmap）**：长度为行数 $n$ 的位数组，第 $i$ 位为 1 当且仅当第 $i$ 行的 $A = v_j$。

例如「性别」列，假设 4 行：男、女、男、女。

```
行号：  1  2  3  4
男：    1  0  1  0
女：    0  1  0  1
```

**查找**：\`SELECT * FROM 员工 WHERE 性别 = '男'\` → 直接取「男」位图，第 1、3 位为 1 → 第 1、3 行。<span class="marginnote">位图是<strong>列的压缩表示</strong>：4 行只要 4 bit 而非 4 个完整的值。行数越大、取值越少，位图越省空间——这正是低基数列的完美匹配。</span>

## 2 位图运算：AND、OR、NOT

位图索引最强的能力是**多条件组合**：

- 条件「都满足」（AND） → **位图 AND**（两图逐位与）。
- 条件「任一满足」（OR） → **位图 OR**。
- 条件「取反」（NOT） → **位图 NOT**（逐位取反）。

**核心要点：组合条件的代价 = 几次位运算，与行数无关。** CPU 的位运算按字（64 位）并行，处理百万行位图只需几万次字操作——比「逐行判断两个条件」快几个数量级。这是数据仓库大量使用位图索引的原因（第 20 章列存 + 位图是标配）。

**公式解析：位图 AND 的成本**

设行数 $n$，字长 $w = 64$：

$$
T_{\text{AND}} = \frac{n}{w} \text{ 次字操作}
$$

- **第一步，按字处理**：两个位图逐字 AND，每字 64 位一次运算。
- **第二步，总次数**：$n$ 位需要 $n/w$ 个字。
- **第三步，$n = 10^8$ 时**：约 156 万次字操作，毫秒级完成——**比走 B+ 树聚簇位图匹配都快**。
- **第四步，结果仍是位图**：AND 结果可继续与第三个条件 AND，多条件叠加不增行数扫描。

## 3 位图的适用与局限

**适用场景：**

| 条件 | 说明 |
| --- | --- |
| 低基数列 | 取值少（性别、状态、布尔） |
| 只读/分析负载 | 数据仓库、OLAP |
| 组合条件多 | 多维度过滤 |
| 大表 | 行数越大收益越明显 |

**局限与辨析：**

- **高基数列退化**：取值 100 万个的列，位图 100 万个 × 行数位，空间爆炸——高基数列用 B+ 树。
- **写代价高**：插入一行要更新**所有位图**（该列每个取值对应的位图都要加一位）——**位图索引不适合写密集 OLTP**。
- **需要位图运算支持**：普通 MySQL/PostgreSQL 默认不用位图索引；Oracle、PostgreSQL（varbit）支持，列存（DuckDB、ClickHouse）内部常用。

**辨析｜易错点：** 位图索引和「位图」（bitmap）文件组织不是一回事。位图索引是**索引结构**；「位图」作为列存储的压缩编码（第 20 章）是**数据表示**。两者思想同源（用 bit 表示布尔），但一个加速查询、一个压缩存储。

## 4 其他辅助索引

数据库里还有一批针对特殊需求的辅助索引：

- **函数索引（functional index）**：对表达式建索引，如 \`LOWER(name)\`——加速 \`WHERE LOWER(name) = 'smith'\` 这类无法直接走普通 B+ 树的查询。
- **覆盖索引（covering index）**：索引包含查询所需的全部列，查询**免回表**（index-only scan）。
- **部分索引（partial index）**：只对满足条件的行建索引（PostgreSQL 支持），缩小索引体积。
- **倒排索引（inverted index）**：词 → 文档列表，全文检索与搜索引擎的核心（第 11 章「信息检索」专题有专篇）。
- **复合索引（composite index）**：多列联合索引，按**最左前缀**匹配。

**核心要点：索引是「查询模式」的镜像。** 每种特殊索引都对应一类查询模式：函数索引对应「表达式过滤」，覆盖索引对应「只取几列」，倒排索引对应「包含词」。**设计索引 = 先收集查询模式，再选结构**。

## 5 小结

- **位图索引**：每个取值一个位图，每行一位，等值与组合查询用**位运算**完成。
- 位运算成本 $= n/w$ 次字操作，与行数弱相关，组合条件极快。
- 适用**低基数列 + 分析负载**；高基数列空间爆炸、写密集场景更新昂贵。
- 其他辅助索引：**函数索引、覆盖索引、部分索引、倒排索引、复合索引**。
- 索引是查询模式的镜像——**先收集查询，再选结构**。
