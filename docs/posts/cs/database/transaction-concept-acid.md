## 为什么从事务开始

数据库的价值不只是「存数据、查得快」，更在于**多个操作的原子性**。从账户 A 转账到 B：扣 A 的钱、加 B 的钱，两步之间若断电，钱就「消失」了。**事务（transaction）**把多个操作打包成一个不可分割的单元，并用 **ACID** 四个性质保证正确性。这一节是第四篇「事务与故障恢复」的开篇：讲清事务的定义、ACID 四性、以及它们分别由哪些机制保证。后续第 14 章（并发控制）与第 15 章（恢复系统）就是 ACID 的工程实现。

## 1 什么是事务

**事务（transaction）**：数据库操作的一个**原子执行单元**——要么全部执行成功提交（commit），要么全部不生效回滚（abort/rollback）。

一个转账事务：

```sql
BEGIN;
UPDATE account SET balance = balance - 100
  WHERE account_no = 'A-101';
UPDATE account SET balance = balance + 100
  WHERE account_no = 'A-201';
COMMIT;
```

**核心要点：事务是「读 + 写」序列的打包。** 它把多个 SQL 包装成一个「要么全成、要么全败」的整体，把「中途失败」的状态对用户隐藏。<span class="marginnote">事务的核心动机是<strong>部分失败</strong>：现实中任何一步都可能失败（断电、死锁、约束冲突）。事务的存在让应用层不必处理「扣了钱没加到账」这种中间状态——失败就整体回滚。</span>

## 2 ACID：四个性质

**ACID** 是事务正确性的四支柱：

- **原子性（Atomicity）**：事务的所有操作**要么全部完成、要么全部不生效**。转账要么两笔都成功，要么都回滚。
- **一致性（Consistency）**：事务执行前后，数据库都满足**完整性约束**。转账前后总余额不变。
- **隔离性（Isolation）**：并发事务的执行结果，**等价于**它们串行执行。两个并发转账互不干扰。
- **持久性（Durability）**：事务提交后，其修改**永久保存**，即使系统崩溃也不丢失。

**辨析｜易错点：** **一致性是「应用层的责任」**——数据库只保证「约束不被破坏」，但「余额不能为负」这种业务规则要靠应用写 `CHECK` 约束或业务逻辑。数据库保证的是「事务前后约束一致」，不是「业务语义正确」。ACID 里 A、I、D 是数据库的机制承诺，C 是 A+I 的推论 + 约束强制。

## 3 公式解析：ACID 的机制归属

ACID 四性分别由哪套机制保证？可以画一张对应表：

$$
\begin{aligned}
\text{Atomicity} &\leftarrow \text{恢复系统（Undo/回滚，第15章）} \\
\text{Consistency} &\leftarrow \text{完整性约束（第4章）+ AID} \\
\text{Isolation} &\leftarrow \text{并发控制（锁/MVCC，第14章）} \\
\text{Durability} &\leftarrow \text{恢复系统（Redo/日志，第15章）}
\end{aligned}
$$

- **第一步，原子性 → 回滚**：事务失败时撤销已做的修改，靠日志里的 Undo 信息。
- **第二步，一致性 → 约束 + 原子隔离**：约束在写时检查；A 与 I 保证并发下的约束不被破坏。
- **第三步，隔离性 → 并发控制**：锁、时间戳、多版本，保证并发调度等价于串行。
- **第四步，持久性 → 重做日志**：提交时把修改记入持久日志，崩溃后重放。

**核心要点：ACID 不是抽象口号，而是三套具体机制的契约。** 后续三章就是这三套机制的详解——这是整个第四篇的「导航图」。

## 4 事务的正确性直觉

**为什么需要隔离性？** 看两个并发转账互相干扰的例子：两个事务同时把账户 B 的余额读出来，各自加 100，再写回——**两次更新只生效一次**，丢失更新（lost update）。

**ACID 的保证**：如果并发事务的效果等价于「某个串行顺序」，就不会有丢失更新、脏读、幻读等问题——**隔离性把并发问题消灭在「等价于串行」这个标准上**。

**辨析｜易错点：** ACID 是「理想目标」，工程上为性能会**放宽隔离**（第 13 章隔离级别、第 14 章快照隔离）。「可串行化」是最高隔离级别，但日常用「读已提交」就够——**了解 ACID 的理想，才知道放宽了什么**。

## 5 事务与 ACID 的数值算例与术语速查

**把一个转账事务的 ACID 四性落到具体执行上。** 设 A 转 100 给 B，A 余额 1000、B 余额 500。

- **原子性**：若第二步（加 B）失败，第一步（扣 A）必须回滚——数据库用日志的 Undo 信息撤销「已扣的 100」——最终 A=1000、B=500，像没发生过。
- **一致性**：事务前后「总余额 1500」不变；若业务规则「余额不能为负」是 CHECK 约束，转账前检查 A≥100。
- **隔离性**：并发两个转账同时改 A、B——数据库用锁/MVCC 让它们的效果等价于串行执行，互不干扰。
- **持久性**：COMMIT 后，A=900、B=600 被记入持久日志——即使立刻断电，重启后重放日志仍恢复到这两个值。

**数值算例：隔离性放宽的代价** 设默认用「读已提交」（比可串行化弱）。

- 读已提交：两个只读报表事务可能看到「转账前」与「转账后」的混合状态——**报表偶尔不一致**。
- 可串行化：报表永远看到一致快照，但并发度低、吞吐降。
- **工程权衡**：绝大多数业务用「读已提交」，报表类用「可重复读」——**知道 ACID 的理想，才清楚放宽了什么**（第 13 章隔离级别详述）。

**辨析｜易错点：** ACID 的「C（一致性）」常被误当成「数据库保证业务正确」——**数据库只保证「约束」不被破坏，不保证「业务逻辑对」**。转账多转了 100 块、账目不平，数据库不会拦——那是应用逻辑的责任。**「ACID 里 A/I/D 是数据库承诺，C 是 A+I 的推论 + 应用写约束的结果」**——把这个记牢，就不会对一致性产生错误期待。

<span class="marginnote">把 ACID 与第 15 章恢复系统、第 14 章并发控制对接：<strong>A、D 由「日志 + 恢复」实现，I 由「锁/MVCC」实现</strong>——本专题后三章就是 ACID 的「实现篇」。先立住 ACID 的目标，再看实现，是「需求 → 机制」的标准读法。</span>

### 术语速查

| 术语 | 含义 |
| --- | --- |
| 事务 | 原子执行单元 |
| 原子性 | 全部成功或全部回滚 |
| 一致性 | 约束在事务前后成立 |
| 隔离性 | 并发等价于串行 |
| 持久性 | 提交后永久保存 |
| 提交/回滚 | COMMIT / ROLLBACK |

## 6 小结

- **事务** = 原子执行单元：**要么 `COMMIT` 要么 `ROLLBACK`**，全部成功或全部回滚。
- **ACID**：原子性、一致性、隔离性、持久性。
- 一致性是**应用 + 约束**的责任；A/I/D 是数据库机制的承诺。
- 机制归属：原子性→回滚，隔离性→并发控制，持久性→重做日志。
- 隔离性把并发问题归结为「等价于串行」——工程上可按需放宽。
- 事务的核心动机是**部分失败**——现实里任何一步都可能断电、死锁、约束冲突。
- 转账多转了 100、账目不平，数据库不会拦——那是应用逻辑的责任。
- 读已提交防脏读、可重复读防不可重复读——隔离级别按需放宽 ACID 理想。
- A、D 由「日志 + 恢复」实现，I 由「锁/MVCC」实现——后三章是 ACID 的实现篇。
- ACID 是理想目标，工程上为性能放宽隔离——知道理想，才清楚放宽了什么。
