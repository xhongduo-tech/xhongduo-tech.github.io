## 为什么从 ClickHouse 与 DuckDB 开始

第 20 章的原理（列存、压缩、向量化、延迟物化）需要落到真实系统。这一节看两个代表性的列存数据库：**ClickHouse**——分布式列存，为海量日志/事件分析而生；**DuckDB**——嵌入式单机列存，为「笔记本上跑分析」而生。它们把「列存三件套」以不同的工程取向实现——ClickHouse 强调**吞吐与分布式**，DuckDB 强调**易用与单机极速**。读懂两个系统，等于看完了列存工程的全部要点。

## 1 ClickHouse：分布式列存 OLAP

**ClickHouse** 是开源的**分布式列存数据库**，为海量数据分析而生。

**核心特性**：

- **列式存储 + 向量化执行**：MergeTree 引擎，列存 + 批量 SIMD 执行。
- **MergeTree 表引擎**：数据按主键（排序键）有序分区，后台 merge——**写追加 + 读有序**（LSM 思想）。
- **稀疏索引**：每 8192 行一个索引（`index_granularity`）——主键不存全量，只存「每块的第一个值」。
- **压缩**：列级编码（LZ4、ZSTD、字典、Delta）。
- **分布式**：分片 + 副本（ReplicatedMergeTree 用 ZooKeeper 协调）。

**公式解析：ClickHouse 的稀疏索引**

主键 $K$，每 $g$ 行存一个索引条目：

$$
\text{索引条目} = \frac{n}{g}, \qquad
\text{点查 I/O} = O(\log \frac{n}{g} + \text{块内扫})
$$

- **第一步，稀疏**：索引只覆盖每 $g$ 行的第一个值——比 B+ 树索引小 $g$ 倍。
- **第二步，定位块**：二分索引找目标块，块内顺序扫。
- **第三步，收益**：索引极小（可全驻内存）、插入无需维护索引（追加即可）。
- **第四步，代价**：范围查询要扫整个块（不能精确定位到行）——**ClickHouse 为「聚合大表」优化，不为「点查单行」优化**。

**核心要点：ClickHouse 是「为分析聚合而生的分布式列存」。** 它的设计处处为「扫描 + 聚合」服务——稀疏索引、列存、向量化、压缩、分布式——**OLAP 工作负载的极致优化**。

## 2 DuckDB：嵌入式单机列存

**DuckDB** 是**嵌入式（in-process）列存数据库**——像 SQLite 一样嵌入应用，但用列存 + 向量化。

**核心特性**：

- **列式存储 + 向量化执行**：完整实现「列存三件套」。
- **嵌入式**：无服务器、无配置，`import duckdb` 即用。
- **分析 SQL**：完整 SQL（窗口函数、CUBE、复杂连接）。
- **零拷贝接口**：直接查 Parquet、CSV、Pandas DataFrame——**数据不导入也能查**。
- **优化器**：现代 CBO（第 12 章），连接顺序动态规划。

**公式解析：DuckDB 的零拷贝查询**

查外部 Parquet 文件：

$$
T_{\text{DuckDB 查 Parquet}} \approx T_{\text{读列文件}} \quad \text{（无需导入）}
$$

- **第一步，直接读列**：Parquet 是列存格式——DuckDB 按查询需要的列读。
- **第二步，谓词下推**：Parquet 的统计信息（min/max）帮 DuckDB 跳过无关块。
- **第三步，零拷贝**：数据不复制进 DuckDB 自己的存储——**即查即用**。
- **第四步，价值**：数据分析师「在笔记本上分析 TB 级数据」——**单机 + 列存 + 向量化 = 够用且快**。

**核心要点：DuckDB 是「列存引擎的极简形态」——单机、嵌入式、极速。** 它证明「列存三件套」不一定要分布式才有价值——**单机上，向量化列存已经比行存快一两个数量级**。

## 3 两个系统的对比

| 维度 | ClickHouse | DuckDB |
| --- | --- | --- |
| 定位 | 分布式 OLAP 服务器 | 嵌入式单机分析 |
| 架构 | 分片 + 副本 | 单进程嵌入 |
| 数据规模 | PB 级 | 单机内存/磁盘 |
| 执行 | 向量化 + 分布式并行 | 向量化 |
| 引擎 | MergeTree + 稀疏索引 | 列存 + CBO |
| 部署 | 集群 | `import` 即用 |
| 典型场景 | 日志分析、时序、事件 | 数据分析、数据科学、ETL |
| 学习门槛 | 中 | 低 |

**辨析｜易错点：** **ClickHouse 与 DuckDB 不是竞争关系，而是不同定位**——ClickHouse 是「集群部署的 OLAP 服务」，DuckDB 是「嵌入应用的 OLAP 库」。**选型的本质是「你的分析数据在哪种规模、哪种部署形态」**——海量集群用 ClickHouse，单机快速分析用 DuckDB。

## 4 从两个实践回看第 20 章原理

**两个系统把第 20 章的原理都落地了：**

| 原理（第 20 章） | ClickHouse | DuckDB |
| --- | --- | --- |
| 列式存储 | ✅ MergeTree 列存 | ✅ |
| 列级压缩 | ✅ LZ4/ZSTD/字典 | ✅ |
| 向量化执行 | ✅ SIMD 批量 | ✅ |
| 延迟物化 | ✅ | ✅ |
| 稀疏索引 | ✅（每 8192 行） | Parquet 统计下推 |

**核心要点：两个系统证明「列存三件套」是成熟工程。** 差异只在「规模与部署」——原理完全一致。**读第 20 章的原理，再看 ClickHouse/DuckDB 的文档，你就能理解它们「为什么这么设计」**——这就是「原理 → 系统」的完整闭环。

## 5 小结

- **ClickHouse**：分布式列存 OLAP——MergeTree + 稀疏索引 + 向量化，为海量聚合而生。
- **DuckDB**：嵌入式单机列存——向量化 + 零拷贝查 Parquet，笔记本上极速分析。
- 稀疏索引：每 $g$ 行一个条目——小索引 + 大块扫，适合聚合不适合点查。
- 两者把「列存三件套」落地为成熟工程——规模与部署不同、原理一致。
- 选型：海量集群用 ClickHouse，单机快速分析用 DuckDB。
