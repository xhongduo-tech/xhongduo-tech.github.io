## 为什么从数据视图开始

上一节《数据库系统的目标》回答了"为什么需要 DBMS"：它把应用程序员从文件系统的细节中解放出来。可紧接着的问题就是：用户"看到"的数据库到底是什么？答案不止一个。物理磁盘上的字节是一种看法，逻辑上的表结构是另一种看法，特定应用关心的局部又是第三种看法。这一节要讲的**数据抽象（data abstraction）**，正是数据库"多副面孔"背后的理论框架；而**数据模型（data model）** 是描述这些面孔的通用语言。可以说，理解数据视图，是理解数据库的第一块透视镜。

先举一个贯穿全节的例子：大学数据库里有一张教师表，里面存着每位教师的编号、姓名、所属系和工资。同一个数据库，在三个不同的人眼里长得完全不同——这正是下一节要展开的三层抽象。

这三副面孔并不是同一事物的三个别名，而是同一数据在不同抽象层次上的三种合法表示。用户只需要与其中一层打交道，却往往不知道其余两层存在——这种"被保护的无知"，恰恰是抽象设计成功的标志。下面把这三层逐一展开。

## 1 数据抽象的层次

为了让不同角色各取所需、又不必关心与己无关的细节，数据库系统把数据组织成三个抽象层次：

- **物理层（physical level）**：描述数据"实际上"怎么存储。比如一张 \`instructor\` 表被顺序放在磁盘的哪些块上、有没有建 B+ 树索引、采用哪种压缩算法。物理层只有数据库实现者才关心。
- **逻辑层（logical level）**：描述"存了哪些数据、数据之间是什么关系"。它不关心存储细节，只关心模式与数据本身。<span class="marginnote">逻辑层是 DBA 与大多数应用打交道的地方：你写 SQL 时面对的就是逻辑层，而根本不用管某一行到底落在哪个磁盘块上。</span>
**视图层（view level）**：描述数据库的一个特定局部。图书管理里读者只查图书、采编员才能改书目，各自面对一张"裁剪过的表"。

拿我们的教师表举例：物理层看到的是"第 1024 号磁盘块起连续存放 3 条记录，每条 64 字节"；逻辑层看到的是"一张四列的表 \`instructor (ID, name, dept_name, salary)\`"；而一位普通教师看到的是视图层——"只能看到自己的工资，看不到别人的"。同一个数据库，三层三副面孔。把三层的"关注点"与"使用者"放到一张表里，脉络更清楚：

| 抽象层次 | 描述什么 | 谁在使用 |
| --- | --- | --- |
| 物理层 | 数据怎么存储（块、索引、压缩） | 存储引擎实现者 |
| 逻辑层 | 数据是什么、彼此如何关联（模式） | DBA、应用开发者 |
| 视图层 | 数据的局部裁剪 | 终端用户、特定应用 |

视图层存在两个理由：一是**简化**——用户只接触与自己相关的一小片数据，不必面对整个数据库；二是**安全**——让不该看到的数据对用户不可见。<span class="marginnote">视图是数据库"最小权限"安全的第一步。第三级《中级 SQL》会讲如何用 SQL 的 CREATE VIEW 真正实现视图层，届时这些抽象会落到语法上。</span>

**数据抽象的核心：每一层都向上层隐藏实现细节，只暴露稳定接口。** 这与程序设计里"接口与实现分离"是同一个原则，只是数据库把它贯彻到了系统级。因为这套分层，应用程序员可以在不修改逻辑层接口的前提下，随意更换底层的物理存储——这引出"数据独立性"。

## 2 实例与模式

两个术语必须一次分清，它们贯穿全书：

**模式（schema）**：数据库的**整体逻辑结构**，是"骨架"。它相对稳定，很少改动。
**实例（instance）**：某个**时刻**数据库里的**实际内容**，是"血肉"。它随每次插入、删除、更新而改变。

举个例子。\`instructor\` 表的模式是"有 ID、name、dept_name、salary 四个属性，ID 是主码，salary 是八位小数位的数值"；而 2026 年 8 月 7 日这天表里实际存着哪几位教师、每人工资多少，则是实例。<span class="marginnote">程序员的类比：模式好比类的定义（class），实例好比创建出来的对象（object）。类只有一个，对象可以有成千上万个。这个类比在第三级《面向对象程序设计》里还会深化。</span>

模式与实例的区别有一个实际后果：**改模式是"大手术"，改实例是"日常操作"**。DML 只动实例，随时可以发生；而 DDL 动的是模式，需要谨慎评估——所有依赖这张表的应用都会受影响。这正是分层抽象保护用户的方式：应用建立在模式之上，模式不变，底层存储随你折腾。

再看一个会随时间变化的例子。学校决定把教师的职称也纳入管理。若采用"加一列"方案，模式从 $(ID, name, dept\_name, salary)$ 变成 $(ID, name, dept\_name, title, salary)$——这是**模式变更**，涉及数据字典的修改，属于 DDL。而之后某位教师从副教授晋升为正教授，只是把某一行 \`title\` 属性改掉——这是**实例变更**，属于 DML。**一条经验法则：能被事前预见的、结构性的调整才动模式；一次性的、针对具体记录的修改交给 DML。** 这个 DDL 与 DML 的分工，下一节《数据库语言》会正式展开。用 SQL 把两种变更摆在一起，一眼可辨：

```sql
-- 模式变更（DDL）：加一列
ALTER TABLE instructor ADD COLUMN title VARCHAR(20);

-- 实例变更（DML）：某教师晋升，改一行
UPDATE instructor SET title = '正教授' WHERE name = '王芳';
```

数据库系统内部还区分**物理模式（physical schema）** 与**逻辑模式（logical schema）**：前者描述数据怎么存储，后者描述数据的逻辑结构。二者之间、以及逻辑层与视图层之间的相对独立，叫作**数据独立性（data independence）**——它是数据库能"换存储不换应用"的根本保证。

数据独立性还分两层：**逻辑数据独立性**指逻辑模式改变时视图层不变；**物理数据独立性**指物理存储改变时逻辑模式不变。后者多数数据库已经做到（换个磁盘、改个文件组织，应用无感知）；前者更难，因为应用往往直接依赖逻辑模式。理解这两层独立性，就能解释数据库发展史上"视图为何能屏蔽表结构调整"这类设计问题。

## 3 数据模型

**数据模型（data model）**：用于描述数据、数据之间的联系、数据的语义以及一致性约束的一组工具。它是数据库世界的"语法书"，决定了我们用什么样的词汇谈论数据。

主要的模型家族有四支：

**关系模型（relational model）**：用二维表组织数据。1970 年由 E. F. Codd 提出，凭其简单与数学基础成为今天绝对的主流，也是本专题接下来几十篇的主角。<span class="marginnote">关系模型的"简单"本身就是优势：只用一种结构（表）表达一切，学习成本低，且能用集合论严格推理。</span>
**实体-联系模型（entity-relationship model）**：面向**设计阶段**的图形化模型，用"实体""联系"描述现实世界，通常作为关系模型设计的前置步骤。本专题第二篇《数据库设计》将系统展开。
**基于对象的模型（object-based model）**：把面向对象的思想（对象、封装、继承）引入数据库，适合与面向对象程序直接对接。
**半结构化数据模型（semistructured data model）**：数据不必有严格预定义的模式，典型的如 XML 与 JSON。<span class="marginnote">半结构化数据"模式与数据混在一起"的特点，与关系模型"模式先行"形成鲜明对比——这也是 JSON 在互联网接口中大行其道的原因之一。第五篇《NoSQL 与 NewSQL》会重点讨论。</span>

在关系模型流行之前，还有两种**历史模型**：**网状模型（network model）** 用"记录 + 系"组织数据，**层次模型（hierarchical model）** 用树形结构组织数据（IBM 的 IMS 是其代表）。它们表达能力不弱，但操作繁琐、缺乏数学基础，如今已基本被关系模型取代。<span class="marginnote">了解历史模型不是为了复古，而是理解"关系模型为什么胜利"：它把数据操作的复杂度从用户端转移到了系统端，用户只需要用集合论语言声明意图。</span>

不同的数据模型带来不同的"思考方式"。关系模型逼你把一切抽象成"表 + 属性"，半结构化模型允许你保留嵌套与顺序，面向对象模型让你把方法与数据捆绑。选择哪种模型，本质是在"表达能力"与"严格约束"之间取平衡：约束越强，系统能替你做的保证越多（比如一致性）；约束越弱，建模越自由，但代价与责任都留给应用层。这个权衡会一直延续到第五篇 NoSQL 的讨论里。

以同一份"教师信息"为例，半结构化模型里它长这样——没有预定义的列，每个记录可以有不同的字段：

```json
[
  { "id": "10101", "name": "王芳", "dept_name": "CS" },
  { "id": "10102", "name": "李雷", "title": "副教授" }
]
```

第一条有 \`dept_name\` 没有 \`title\`，第二条恰好相反——模式与数据混在一起，这就是"半结构化"。换成关系模型，这种"每行字段不同"是不允许的：所有元组必须共享同一组属性。**模型的选择决定了你能容忍怎样的不规整。**

**辨析｜易错点：数据模型 ≠ 数据模式。** 数据模型是"描述手段的总称"（用什么语言描述），数据模式是"对某个具体数据库的描述结果"（描述出来的具体样子）。关系模型是一种数据模型；而 \`instructor (ID, name, dept_name, salary)\` 是某个具体数据库的模式。两者是"语法 vs 一句话"的关系，初学者最容易混。

## 4 公式解析：关系模型的一个实例是什么

关系模型把"实例"定义得异常精确，这正是它能成为数学良基的原因。设一个关系模式为 $R = (A_1, A_2, \dots, A_n)$，每个属性 $A_i$ 都取自一个定义域 $\mathrm{dom}(A_i)$，那么关系的一个**实例 $r$** 定义为：

$$r(R) \subseteq \mathrm{dom}(A_1) \times \mathrm{dom}(A_2) \times \cdots \times \mathrm{dom}(A_n)$$

拆成三步理解：

- **第一步，看懂笛卡儿积**：$X = \mathrm{dom}(A_1) \times \cdots \times \mathrm{dom}(A_n)$ 是所有可能元组的全体，规模为 $|\mathrm{dom}(A_1)| \times \cdots \times |\mathrm{dom}(A_n)|$。它代表"理论上可能出现的所有行"。
- **第二步，看懂子集**：实例 $r$ 只是 $X$ 的**一个子集**——从所有可能的行里挑出实际存在的那些。这与第一级《集合》里的子集 $A \subseteq B$ 是同一个概念，只是对象换成了元组。
- **第三步，为什么用集合**：集合天然"无重复、无序"。关系模型由此承诺：一张表里没有两行完全相同，行的排列顺序无关紧要。这是第一级数学中集合"互异性、无序性"在数据库里的直接投影。

套到具体例子上：设 $R = (ID, name)$，$\mathrm{dom}(ID)$ 是五位字符串的全体、$\mathrm{dom}(name)$ 是姓名的全体，那么笛卡儿积 $X$ 是"所有可能的 (编号, 姓名) 对"，而我们的实例 $r$ 只是其中真实存在的三对，如 $\{(10101, \text{Srinivasan}), (12121, \text{Wu}), (15151, \text{Mozart})\}$。**模式是 $R$ 本身，实例是 $r$ 这个子集**——一句话把整节的三个概念连成了闭环。

这个定义还有一个常被忽略的推论：**实例可以为空**。$r(R) = \emptyset$ 是合法的关系实例——一张没有任何元组的表依然存在，它的模式完好无损。这与第一级数学里空集 $\emptyset$ 的地位一致：空关系也是关系，模式照常定义。许多 SQL 新手在"查询没结果"与"表不存在"之间犯迷糊，区分它们的正是模式（结构存在）与实例（内容为空）之别。

## 5 小结

- 数据抽象分**物理层、逻辑层、视图层**三层，逐层隐藏细节、提供接口。
- **模式**是数据库的骨架（结构），**实例**是某一时刻的血肉（内容）；模式与实例之别贯穿全书。
- 数据模型是描述数据的工具，四大族系：**关系、实体-联系、面向对象、半结构化**；历史上还有网状与层次模型。
- 关系模型的一个实例是属性定义域笛卡儿积的**子集**：$r(R) \subseteq \mathrm{dom}(A_1) \times \cdots \times \mathrm{dom}(A_n)$。
- 数据独立性分**逻辑独立性**与**物理独立性**，是数据库"换存储不换应用"的根本保证。
