## 为什么从域关系演算开始

上一节的元组关系演算把「一行」当成基本单位，元组变量遍历整行。这一节换一个更细的视角：**把每一个属性值（域值）当成变量**。域关系演算（domain relational calculus, DRC）用形如 $\{ \langle x_1, x_2, \dots, x_n \rangle \mid P(x_1, \dots, x_n) \}$ 的公式描述结果，变量就是输出列上的值。它看起来更像「拼一行答案」，也与 QBE（Query-by-Example）这类表格化查询语言直接相关。<span class="marginnote">QBE 是 1970 年代 IBM 开发的图形化查询语言，用户直接在表格模板里填例子值，系统自动生成查询——域关系演算正是它的形式化基础。Excel 的高级筛选、低代码平台的「表格查询」都沿袭这个思路。</span>

## 1 域变量的基本形式

域关系演算的查询形式：

$$
\{ \langle x_1, x_2, \dots, x_n \rangle \mid P(x_1, x_2, \dots, x_n) \}
$$

其中 $x_1, \dots, x_n$ 是**域变量**，各取值于某个属性的域；$\langle \dots \rangle$ 表示输出元组的形状；$P$ 是谓词。例如「找出薪资超过 80000 的教师的名字、系别与薪资」：

$$
\{ \langle n, d, s \rangle \mid \exists\, i \in instructor \; ( i[{\text{name}}] = n \land i[{\text{dept\_name}}] = d \land i[{\text{salary}}] = s \land s > 80000 ) \}
$$

与 TRC 的最大区别：**输出元组是各自由变量值拼成的**，而不是整行。变量 $n, d, s$ 分别绑定到元组的三个属性，谓词负责「存在一行教师记录，其值等于这些变量」。

## 2 与元组关系演算的对照

**TRC 的变量绑定「整行」，DRC 的变量绑定「单元格」。** 同一个查询，两种写法：

| 维度 | 元组关系演算（TRC） | 域关系演算（DRC） |
| --- | --- | --- |
| 变量单位 | 元组（整行） | 属性值（单元格） |
| 基本形式 | $\{t \mid P(t)\}$ | $\{ \langle x_1,\dots,x_n \rangle \mid P \}$ |
| 绑定方式 | $t \in r$ | $\exists\, x \; (r[A] = x)$ |
| 属性引用 | $t[A]$ | 变量 $x$ 直接对应 $A$ |
| 直观对应 | SQL `FROM r` | QBE 表格模板 |

**辨析｜易错点：** DRC 中变量与属性的绑定靠「属性取值等于变量」的原子公式完成，变量**没有**显式声明域，只能从谓词的比较中推断。若公式里某个变量既不与关系属性比较、也不与常量比较，它就没有类型，查询会退化成无穷域上的遍历——这正是 DRC 对安全性的要求比 TRC 更敏感的原因。

## 3 用域关系演算写查询

DRC 处理复杂查询的方式与 TRC 平行，只是变量更细。看一个带否定的例子——「找出所有不在计算机系且薪资低于 80000 的教师的名字」：

$$
\{ \langle n \rangle \mid \exists\, d, s \; ( \exists\, i \in instructor \; ( i[{\text{name}}] = n \land i[{\text{dept\_name}}] = d \land i[{\text{salary}}] = s \land d \ne \text{'Comp. Sci.'} \land s < 80000 ) ) \}
$$

注意这里 $n$ 是唯一自由变量，$d, s$ 被 $\exists$ 约束为内部辅助变量。<span class="marginnote">「辅助变量」是 DRC 里最需要适应的地方：谓词内部为拼装一行而临时引入的变量，全部要用 $\exists$ 或 $\forall$ 约束掉，只留要输出的变量自由。</span>

再写出「找到薪水最高的教师」这类极值查询，DRC 用全称量词刻画「没有更高的」：

$$
\{ \langle n \rangle \mid \exists\, s \; ( \exists\, i \in instructor \, ( i[{\text{name}}] = n \land i[{\text{salary}}] = s ) \land \forall\, j \in instructor \, ( j[{\text{salary}}] \le s ) ) \}
$$

内层 $\forall$ 断言「所有教师的薪资都不超过 $s$」，于是 $s$ 就是最大值。

## 4 公式解析：安全约束与无穷域问题

DRC 最微妙的点是**安全性（safety）**。考虑这样一个公式：

$$
\{ \langle n \rangle \mid \neg ( \exists\, i \in instructor \, ( i[{\text{name}}] = n ) ) \}
$$

它声称「找出所有**不是**教师名字的值」——可 $n$ 的取值范围是整个姓名域（可以是任何字符串），结果**无穷大**，数据库无法返回。

- **第一步，看清问题**：$\neg$ 让查询的范围溢出到数据库之外。域变量没有显式声明范围，否定词会把取值范围扩到「域的全部可能值」。
- **第二步，定义安全**：DRC 查询 $\{ \langle x_1,\dots,x_n \rangle \mid P \}$ 是安全的，当且仅当 $P$ 中出现的每个值都出现在某个关系的某个属性中，且 $n$ 个输出变量的域可被数据库内容界定。
- **第三步，约束量词**：安全的做法是让每个 $\forall$、$\neg$ 都限定在关系范围内——即只讨论「数据库里实际存在的元组」，而不是「所有可能的元组」。
- **第四步，对照 SQL**：SQL 的 `WHERE NOT EXISTS` 之所以总是安全，是因为每个子查询都绑定在具体关系上——数据库语言通过**关系范围**天然规避了无穷域。

**核心要点（对比表）：**

| 语言 | 变量范围来源 | 无穷结果风险 | 实际使用 |
| --- | --- | --- | --- |
| 关系代数 | 显式的关系操作 | 无（操作闭合） | 查询执行内部表示 |
| 元组关系演算 | 元组变量绑定关系 | 低（$\forall/\neg$ 需安全） | 研究性语言 |
| 域关系演算 | 变量从比较中推断 | 高（否定易逃逸） | QBE、教学 |
| SQL | 关系范围 + 子查询 | 极低 | 工业标准 |

## 5 小结

- 域关系演算以**单元格（域值）**为变量单位，输出由自由变量拼成 $\langle x_1, \dots, x_n \rangle$。
- DRC 与 TRC 表达力相同，但变量绑定方式更细、更接近 QBE 的表格模板思想。
- 辅助变量必须用量词约束，只留输出变量自由。
- **安全性**是 DRC 的核心约束：否定与全称量词可能让查询溢出到无穷域，必须限定在关系范围内。
