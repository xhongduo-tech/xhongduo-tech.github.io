## 为什么从查询重写开始

上一节讲了等价变换的「规则库」，这一节看优化器**实际怎么用**这些规则——**查询重写（query rewriting）**把 SQL 转换成更适合优化的形式。两大重写目标贯穿始终：**谓词下推**（让过滤最早发生）与**连接顺序**（让中间结果最小）。这一节结合真实 SQL，演示重写如何把「写得很差但语义正确」的查询改写成「执行得飞快」的形式——这是数据库「自动调优」的第一层，也是 DBA 手动改写 SQL 的理论依据。

## 1 谓词下推：过滤最早发生

**谓词下推（predicate pushdown）**：把 WHERE 里的条件尽可能下推到扫描/索引层。

一个例子：

```sql
SELECT s.name
FROM student s, takes t
WHERE s.ID = t.ID AND t.course_id = 'CS-101';
```

**重写前**：先连接两个大表，再过滤 course_id = 'CS-101'——连接输入巨大。

**重写后**：先对 takes 过滤 course_id = 'CS-101'（走索引），再连接——连接输入只剩选课数。

**核心要点：谓词下推的价值随「选择率」放大。** 条件过滤掉越多行，下推收益越大——谓词若只命中 1% 的行，连接输入缩小 100 倍。<span class="marginnote">这正是「<strong>先过滤，后连接</strong>」的工程直觉。手写 SQL 时也应遵循：把选择性高的条件写进 WHERE 而非连接后再过滤——优化器多半会替你下推，但写对了更好。</span>

## 2 谓词下推的边界

谓词下推**不是无条件**的：

- **外连接**：LEFT OUTER JOIN 时，左表的过滤条件可下推到左表，但右表的过滤条件**不能**下推到右表——否则会把「右表无匹配的行」也过滤掉，改变外连接语义（保留左表行）。
- **视图/子查询**：下推要穿透视图，但含 ORDER BY、聚合、UNION 的视图不能随便下推（会改变语义）。
- **分布式**：下推到存储层（第 19 章 TiDB 的算子下推）要确保存储层能执行该算子。

**辨析｜易错点：** 外连接场景的谓词下推是经典错误源。LEFT OUTER JOIN 的右表过滤条件若写在 WHERE，会**悄悄把外连接变成内连接**（NULL 行被过滤）。正确写法是把过滤放进 ON 子句。

## 3 连接顺序：中间结果最小化

**连接顺序优化**：决定「先连哪两个表」，目标是**中间结果最小**。

一个三表连接例子：

```sql
SELECT s.name, c.title
FROM student s, takes t, course c
WHERE s.ID = t.ID AND t.course_id = c.course_id;
```

- **顺序 A**：先连 (student ⋈ takes) 再连 course——若 student 很大，中间结果爆炸。
- **顺序 B**：先连 (takes ⋈ course) 再连 student——若 course 很小，总代价低。

**核心要点：连接顺序的决定性因素是「中间结果大小」。** 而中间结果大小取决于连接条件的选择性——高选择性的连接先做，能「掐掉」大量无用配对。

**公式解析：选择连接顺序的启发式**

设 $r, s$ 连接的结果大小估计：

$$
n_{r \bowtie s} \approx \frac{n_r \cdot n_s}{V(A, r \text{ 或 } s)}
$$

- **第一步，基数影响**：连接结果行数 ≈ 两表行数乘积 / 连接属性基数（$V(A)$ 大则结果小）。
- **第二步，先连小结果**：估算各对连接的中间结果，先做「结果最小」的连接。
- **第三步，级联最小化**：多表时用动态规划，从最小的子集连接逐步扩展。
- **第四步，工程直觉**：**先连「能大幅缩小数据集」的表对**——选择性高的连接优先。

## 4 完整的重写流程

一条 SQL 的典型重写序列：

1. **解析**成代数树。
2. **视图展开**：把视图引用替换成其定义。
3. **谓词下推**：选择下推到叶子。
4. **投影下推**：列瘦身。
5. **连接重排**：选择中间结果最小的顺序。
6. **合并步骤**：相邻选择/投影合并。
7. **转物理计划**：选扫描与连接算法（第 11 章）。

**连接点：** 重写是「逻辑优化」的工程形态——它把等价变换规则组织成一个**流水线**。重写后的代数树再交给物理优化（代价估算 + 动态规划）。所以一条慢查询的排查往往从「看**执行计划**（EXPLAIN）里谓词有没有下推、连接顺序对不对」开始。

## 5 查询重写的数值算例与术语速查

**把谓词下推的收益算到具体数字。** 设 orders 1 亿行、customers 1000 万行，连接条件 `o.cid = c.cid`，谓词 `o.date > '2026-01-01'`（选择率 10%）。

- **不下推**：先连接 1 亿 × 1000 万 = 1 万亿次配对，再过滤——连接输入巨大，中间结果接近全量。
- **下推**：先过滤 orders 到 1000 万行，再连接 1000 万 × 1000 万 = 1 万亿次配对——**连接规模不变，但中间结果（连接后的行）缩小 10 倍**；若谓词还能走索引，过滤本身也快。
- **下推 + 选择率高**：`o.status='已取消'`（选择率 1%）——过滤后 100 万行——中间结果再缩 10 倍。
- **结论**：**下推的收益 = 选择率的倒数**——条件越狠，收益越大。

**数值算例：连接顺序的中间结果** 设三表 student(1000 万)、takes(5000 万)、course(10 万)。

- 先连 (student ⋈ takes)：中间结果 ≈ 5000 万行（每选课匹配一个学生）。
- 先连 (takes ⋈ course)：course 小、基数大，中间结果 ≈ 5000 万行但**每行更窄**（只留连接列）——传输与内存更省。
- **再优化**：先对 takes 过滤（如只查本学期），中间结果骤降——**过滤先行 + 小表先行**是两个最有效的顺序启发式。

**辨析｜易错点：** 谓词下推的收益不是「自动免费」的——**优化器能否下推取决于代数树的形状与统计信息**。若统计信息过期（第 12 章基数估计），优化器低估/高估选择率，可能「错误地下推或不下推」。**「重写规则正确」与「规则用得对不对」是两回事**——后者依赖统计质量。

<span class="marginnote">查询重写与第 3 章「写出好 SQL」的经验呼应：<strong>手写 SQL 时把选择性最高的条件放前面、避免在连接后过滤、避免 SELECT *</strong>——优化器多数能替你重写，但「写得好」能让优化器更省力，也让执行计划更可预测。</span>

### 术语速查

| 术语 | 含义 |
| --- | --- |
| 谓词下推 | 把过滤下推到叶子 |
| 投影下推 | 连接前只留所需列 |
| 连接顺序 | 先连中间结果最小的表对 |
| 视图展开 | 把视图替换为定义 |
| 选择率 | 满足条件的行占比 |
| 中间结果 | 算子之间传递的数据量 |

## 6 小结

- **谓词下推**：把过滤最早发生，收益随选择率放大；外连接与视图下推有语义边界。
- **连接顺序**：以中间结果最小为目标，高选择性连接先做。
- 重写流水线：解析 → 视图展开 → 谓词/投影下推 → 连接重排 → 物理化。
- 外连接右表过滤写在 WHERE 会把外连接变内连接——下推边界的经典陷阱。
- 排查慢查询：先看**执行计划**的谓词位置与连接顺序。
