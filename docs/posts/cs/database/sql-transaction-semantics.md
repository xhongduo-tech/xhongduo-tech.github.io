# 事务的 SQL 语义

## 为什么从事务开始

想想银行转账：从账户 A 转 100 元到账户 B，至少要执行两条语句——A 减 100，B 加 100。麻烦在于，**这两条语句必须「生死与共」**：如果第二条失败了而第一条成功，钱就从系统里凭空消失；反过来第一条失败第二条成功，钱就凭空冒出来。数据库必须保证「两条一起成、或一起不成」，这个保证就叫**原子性（atomicity）**。

SQL 把「一组必须共同成败的语句」包装成一个整体，这个整体就是**事务（transaction）**。它是数据库并发与故障恢复两大主题的最小单元——后续第 13 章的事务、第 14 章的并发控制、第 15 章的恢复系统，全都围绕「如何把事务做对、做快、做成」展开。今天这一节，先讲清 SQL 层面对事务的**直接语法**：怎么声明提交、怎么声明回滚，以及数据库在故障面前靠什么机制兑现「全部或全不」。

## 1 事务：一个「全部或全不」的工作单元

**事务（transaction）**：由一条或多条 SQL 语句构成的、作为整体执行的工作单元。下面的转账就是最经典的例子<span class="marginnote">account 表存账户余额，account_number 是主码。这条事务由两条 UPDATE 组成：先扣减 A，再增加 B。</span>：

```sql
UPDATE account SET balance = balance - 100
WHERE account_number = 'A-101';
UPDATE account SET balance = balance + 100
WHERE account_number = 'A-102';
COMMIT;
```

这段 SQL 由一条语句触发、可能由用户显式结束。它带给数据库一个必须兑现的承诺：**要么两条更新都永久写入数据库，要么一条都不留痕迹**。任何「只做了一半」的状态都是系统不可接受的。

围绕这个承诺，数据库教材总结出事务的**四个特性**，合称 **ACID**：原子性（Atomicity）、一致性（Consistency）、隔离性（Isolation）、持久性（Durability）。<span class="marginnote">「隔离性」指的是多个事务并发执行时，互相看起来像是在串行执行。这四个特性的严格定义与实现机制，是第 13 章《事务》与第 14 章《并发控制》的正式主题，这里先给你直觉。</span>SQL 层面的语法主要服务原子性与持久性——即本节的主角：提交与回滚。

## 2 提交与回滚：COMMIT 与 ROLLBACK

**提交（commit）**：把事务中所有更新的结果**永久**写入数据库。**回滚（rollback）**：撤销事务中所有更新，把数据库恢复到该事务开始前的状态。SQL 中的两条语句是：

```sql
COMMIT;
ROLLBACK;
```

WORK 关键字是可选的，COMMIT WORK 与 COMMIT 完全等价。关键语义在于**事务的开始时机**：SQL 标准并不规定「开启事务」的专门语句，**事务在第一条 SQL 语句执行时隐式开始**，在下一次 COMMIT 或 ROLLBACK 时结束。

**辨析｜易错点：** 有人以为 COMMIT 是「把数据存盘」、ROLLBACK 是「撤销最后一条语句」。都不对。COMMIT/ROLLBACK 的边界是**整段事务**，不是单条语句；事务内的所有更新是一个整体。另外，某些数据库（如早期的 MySQL 默认）把每条语句当作独立事务自动提交，这种模式下根本没有跨语句的原子性——要转账这种多语句事务，必须先显式关闭自动提交。**工程经验：转账、下单这类「多步必须同成败」的操作，永远要包在显式事务里，并检查每条语句的返回状态。**

一旦事务中途出错，数据库的行为取决于系统：有的系统自动回滚整个事务；有的只回滚出错的那条语句并允许事务继续。为稳妥起见，应用层应在关键步骤后主动检查错误，必要时显式 ROLLBACK。

## 3 事务还能声明什么：SET TRANSACTION

除了提交与回滚，SQL 还允许应用声明事务的**访问模式**与**隔离级别**：

```sql
SET TRANSACTION READ ONLY;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

**只读事务**向系统承诺「本事务绝不写数据」。这个声明对数据库意义重大：系统可以据此省略加锁或采用更廉价的一致性方案，因此**性能更好、约束也更严格**——只读事务里执行任何 INSERT/UPDATE/DELETE 都会被拒绝。

**隔离级别**从低到高依次是 READ UNCOMMITTED、READ COMMITTED、REPEATABLE READ、SERIALIZABLE（可串行化）。它决定事务并发执行时能「看到」多少别人的未提交数据。<span class="marginnote">SERIALIZABLE 保证并发事务的执行结果等价于某种串行顺序，是标准里最严格的一档；代价是并发度下降。各档级别允许哪些异常（脏读、不可重复读、幻读），是第 13 章隔离级别一节的主题。</span>注意：**声明隔离级别，是应用向数据库下订单，不是数据库给应用的承诺**——如果数据库实现没提供对应级别，可能悄悄降级为更弱的实现，这在分布式系统里尤其常见。

## 4 公式解析：转账事务的原子性条件

把转账事务记为 $T$，它由两条更新 $u_1, u_2$ 组成。**原子性**用「执行结果只可能是两种极端」来定义：

$$
\text{Result}(T) \;=\;
\begin{cases}
\text{提交态：} u_1 \text{ 与 } u_2 \text{ 的更新都永久生效}, & T \text{ 以 } \text{COMMIT} \text{ 结束}\\[2pt]
\text{回滚态：} u_1 \text{ 与 } u_2 \text{ 的更新都完全撤销}, & T \text{ 以 } \text{ROLLBACK} \text{ 结束}
\end{cases}
$$

逐项拆解这条定义的三层含义：

- **第一层：更新是成对出现、成对生效的。** 原子性禁止「$u_1$ 生效而 $u_2$ 未生效」这种中间态进入最终数据库状态。数据库靠**日志（log）**在后台记录每个更新的旧值，一旦决定回滚，就用旧值把被改动的数据逐个「擦回原样」——这是第 15 章恢复系统的工作，但语义上你现在就该理解：回滚不是「时光倒流」，而是「按日志补偿还原」。
- **第二层：一致性约束是原子性存在的理由。** 转账必须保持账户总余额不变，记作不变量：

$$
\text{balance}(A) + \text{balance}(B) = \text{常量}
$$

在事务 $T$ 独立执行的假设下，这条不变量在 $T$ 前后都成立。若 $u_2$ 失败而 $u_1$ 生效，等式左边少 100，数据库就从「一致状态」跌入「不一致状态」——这正是必须靠原子性把 $u_1$ 也撤销掉的原因。
- **第三层：持久性是提交的兑现。** 提交态还要求「永久生效」：即使紧接着系统断电、进程崩溃，已提交的更新也不能丢。这一点单靠内存做不到，必须把更新记录写入**非易失存储**后才能宣告提交——所以「提交」在物理上是「先写日志、再回确认」的，代价不低。**这也是为什么真实系统里「提交」比「执行一条语句」慢得多。**

把这三点连起来读：原子性规定**结果只能二选一**，一致性规定**两个结果都必须是好状态**，持久性规定**提交的那个好状态要扛住故障**——SQL 的 COMMIT/ROLLBACK 只是把这三件事浓缩成两个动词。

## 5 各数据库的事务语法与工程习惯

标准给的是「隐式开始 + 显式提交/回滚」，但具体数据库的方言略有出入，动手前务必确认：

| 数据库 | 显式开启事务 | 提交 / 回滚 |
| --- | --- | --- |
| PostgreSQL | BEGIN | COMMIT / ROLLBACK |
| MySQL (InnoDB) | START TRANSACTION | COMMIT / ROLLBACK |
| SQL Server | BEGIN TRANSACTION | COMMIT / ROLLBACK |
| Oracle | 隐式开始 | COMMIT / ROLLBACK（无显式 begin 语句） |

事务与 DDL 的交互也值得留意：不少数据库在处理 CREATE TABLE、DROP TABLE 这类 DDL 语句时会**隐式提交当前事务**——MySQL、Oracle 皆有此行为，意味着 DDL 之前事务里已经执行的更新会被悄悄固化，ROLLBACK 再也覆盖不到；而 PostgreSQL 的 DDL 是可回滚的（事务性）。写迁移脚本前先弄清所用数据库的 DDL 是否隐式提交，是避免「回滚失灵」的最稳做法。反过来，若数据库支持事务性 DDL，把整段迁移包进一个显式事务，失败时整体回滚，正是数据库迁移工具的常见策略。

**辨析｜易错点：** MySQL 的 MyISAM 引擎不支持事务，换了引擎代码就「看起来成功、实际无原子性」；SQL Server 里 ROLLBACK 若省略名字可能匹配到外层事务。**两条工程铁律：其一，事务要短**——长事务长期持锁，拖累所有并发事务，第 14 章会从锁的角度解释「连接要趁早、提交要果断」；**其二，把失败路径想清楚**——出错的语句不检查返回码、直接往下跑，是事务被破坏的第一大来源。

最后把眼光放远一点：本节的事务只是**单机、单个数据库**内的原子性。当数据被复制到多台机器、或一个操作横跨多个数据库时，「全部或全不」的难度剧增，演化出两阶段提交（2PC）、Saga、TCC 等分布式事务方案——那是本专题第五篇《分布式数据库》的战场。

## 6 小结

- **事务**：一组共同成败的 SQL 语句，是原子性、并发控制与故障恢复的最小单元。
- **原子性**：要么全部更新生效，要么全部撤销；SQL 用 COMMIT 与 ROLLBACK 两个动词表达。
- **事务开始时机**：SQL 标准下事务在第一条语句执行时**隐式开始**，到 COMMIT/ROLLBACK 结束。
- **SET TRANSACTION** 可声明只读事务与隔离级别；只读声明能带来性能收益，但级别声明可能被数据库静默降级。
- **原子性的物理基础**是日志与恢复系统；**持久性**要求提交前把更新写入非易失存储，因此提交有真实成本。
- **DDL 与事务的交互**：MySQL/Oracle 的 DDL 会隐式提交当前事务，PostgreSQL 的 DDL 可回滚；写迁移脚本前先确认所用数据库的行为。
- 具体数据库的事务语法有方言差异，MySQL MyISAM 等引擎甚至不支持事务，动手前先确认。
