## 为什么从修改策略开始

基于日志的恢复有两种更新策略，区别在「数据页何时被真正修改」：**延迟修改（deferred modification）**——修改先记日志，**数据页到提交后才动**；**立即修改（immediate modification）**——**日志落盘后立刻改数据页**（但未提交前不刷盘）。这个区别决定了恢复算法的复杂度：延迟修改**不需要 Undo**（未提交事务根本没改过数据页），立即修改**必须 Undo**（未提交的修改可能已落到磁盘）。这一节把两种策略与各自的恢复算法讲透——它们是最初的日志恢复方案，也是理解 ARIES 的前提。

## 1 延迟修改

**延迟修改（deferred modification）**：

- 事务的每次修改，只把**新值**写进日志（**不写旧值**——因为不需要 Undo）。
- 数据页的**实际修改推迟到事务提交之后**才执行。

**为什么不需要 Undo**：未提交事务从未碰过数据页——回滚只需**丢弃日志记录**，数据页无需撤销任何修改。

**恢复算法**（崩溃后）：

1. 扫描日志，找出所有**已提交**的事务。
2. 对每个已提交事务，**重做**其全部修改（用日志中的新值）。
3. 未提交事务的修改**不重做**（数据页本来就没改）——**无 Undo**。

**核心要点：延迟修改让恢复只剩 Redo。** 这是它简洁之处，但代价是：**提交前修改不落数据页**——若数据页在提交前被其他事务读？不允许（无 Undo 意味着未提交修改不可见）。**缓存失效与长事务**让延迟修改的实际并发度受限。

## 2 立即修改

**立即修改（immediate modification）**：

- 修改操作：**先写日志（含旧值+新值），日志落盘后立即修改缓冲池中的数据页**。
- 数据页可能在**事务提交前**被刷到磁盘（STEAL 策略）。

**为什么需要 Undo**：未提交事务的修改**可能已落盘**——崩溃时磁盘含未提交的修改，必须撤销。

**恢复算法**（崩溃后）：

1. 扫描日志，找出已提交与未提交事务。
2. **Redo**：重做已提交事务的所有修改（含可能已落盘的部分——**重做是幂等的**，重复执行无妨）。
3. **Undo**：撤销未提交事务的修改（用日志中的旧值恢复）。

**公式解析：立即修改的恢复复杂度**

设日志长度 $L$，崩溃时未提交事务集合 $U$：

$$
T_{\text{恢复}} = \underbrace{O(L)}_{\text{扫描日志}} + \underbrace{O(L)}_{\text{Redo 已提交}} + \underbrace{O(|U| \cdot \text{修改数})}_{\text{Undo 未提交}}
$$

- **第一步，扫描**：遍历日志一遍，识别事务状态。
- **第二步，Redo**：重放所有已提交事务的修改记录。
- **第三步，Undo**：撤销未提交事务的修改——**从后往前**回滚（后修改的先撤销）。
- **第四步，对比延迟**：立即修改多一个 Undo 阶段，但**修改可以更早落盘**（STEAL），缓冲池压力小、事务能处理更大数据集。

## 3 两种策略的对比

| 维度 | 延迟修改 | 立即修改 |
| --- | --- | --- |
| 日志记录 | 只有新值 | 旧值 + 新值 |
| 数据页修改时机 | 提交后 | 日志落盘后 |
| 崩溃恢复 | 仅 Redo | **Redo + Undo** |
| 未提交修改可见 | 否 | 可能已落盘 |
| 缓冲池压力 | 大（提交前不落盘） | 小（可 STEAL） |
| 大事务支持 | 差 | 好 |
| 现代使用 | 较少 | **ARIES 的基础** |

**辨析｜易错点：** **「立即修改」不等于「立即落盘」**——它只保证「日志落盘后立刻改缓冲池中的数据页」，数据页是否刷到磁盘由缓冲策略（STEAL）决定。立即修改 + STEAL 才导致「未提交修改在磁盘」、才需要 Undo。

## 4 从两种策略到 ARIES

**核心要点：立即修改 + STEAL + NO-FORCE 是现代恢复系统的标准组合。** 这套组合：

- **STEAL**：未提交事务的页可提前刷盘（缓冲池压力小）。
- **NO-FORCE**：已提交事务的页不必立即刷盘（提交快）。
- **后果**：崩溃时磁盘既有未提交修改（需 Undo）又有已提交修改（可能需 Redo）——**恢复必须做 Undo + Redo 两件事**。

ARIES 算法（第 15 章后文）就是为这套组合设计的工业级恢复算法：**先分析、再 Redo、最后 Undo**，用日志序列号（LSN）精确控制重做/撤销的范围。

## 5 两种修改策略的数值算例与术语速查

**把同一个崩溃场景分别用两种策略恢复一遍。** 设事务 T1 提交、T2 未提交，都改过数据页 P。

- **延迟修改（崩溃）**：T1、T2 的数据页修改都未发生（延迟到提交后）——扫描日志，Redo T1 的全部修改（P 用 T1 新值）；T2 未提交、数据页没改过——**直接丢弃 T2 的日志记录，无需 Undo**。
- **立即修改 + STEAL（崩溃）**：T1、T2 的修改可能都已落盘——Redo T1（幂等重放），**Undo T2**（P 用 T2 的旧值恢复）——恢复要做两件事。
- **差异本质**：延迟修改「未提交 = 没改过」，立即修改「未提交 = 可能已落盘」——**前者只需 Redo，后者必须 Redo + Undo**。

**数值算例：缓冲池压力的对比** 设事务修改 1 万个页，缓冲池 10 万块。

- **延迟修改**：未提交期间 1 万页钉在缓冲池（不能刷盘）——若多个大事务并发，缓冲池被未提交页占满，其他事务无法运行。
- **立即修改（STEAL）**：未提交页可提前刷盘——缓冲池压力小，大事务也能并发。
- **结论**：延迟修改「恢复简单」换「缓冲池受限」；立即修改「恢复复杂」换「缓冲池灵活」——**现代系统选后者**（ARIES 的组合）。

**辨析｜易错点：** 「延迟修改」不是「没有日志」——它仍有日志（记录新值用于 Redo），只是**不写旧值**（因为不需要 Undo）。「不写旧值」是它日志更紧凑的来源，也是它「无法回滚已落盘的修改」的原因——**两种策略的日志记录内容与恢复能力严格对应**。

<span class="marginnote">延迟修改与立即修改的选择，与第 15 章 STEAL/NO-FORCE 是同一枚硬币：<strong>「什么时候动数据页」与「什么时候允许刷盘」两个决策共同决定恢复复杂度</strong>。现代 ARIES 把两者统一到「STEAL + NO-FORCE + 立即修改」——恢复算法因此要做全：分析、Redo、Undo。</span>

### 术语速查

| 术语 | 含义 |
| --- | --- |
| 延迟修改 | 提交后才改数据页 |
| 立即修改 | 日志落盘后即改数据页 |
| 无 Undo | 延迟修改的恢复特征 |
| Redo + Undo | 立即修改的恢复特征 |
| 旧值/新值 | 日志携带的回滚/重做信息 |
| STEAL | 未提交脏页可提前刷盘 |

## 6 小结

- **延迟修改**：只写新值日志，提交后才改数据页——恢复**仅 Redo**。
- **立即修改**：写旧值+新值日志，日志落盘后即改数据页——恢复**Redo + Undo**。
- 立即修改 + STEAL 让未提交修改可能落盘，Undo 成为必需。
- 延迟修改简洁但缓冲压力大、大事务支持差。
- 现代标准 = **立即修改 + STEAL + NO-FORCE**，ARIES 是它的工业实现。
