## 为什么从完整性约束开始

上一节我们学会了把多条语句打包成事务，保证「要错一起错、要对一起对」。但事务只解决**执行过程**的问题，不解决**数据本身**的问题——如果应用写进来的余额是负数、外码指向一个不存在的系、或者课程成绩的总学分对不上账，事务照样「成功提交」。数据库如何拒绝这类**语义上就是错**的数据？

答案是**完整性约束（integrity constraint）**：一种**声明式的守卫**——应用在建表时把规则写进数据库，此后每一次插入、修改、删除都由数据库自动校验，违规即拒绝。<span class="marginnote">「声明式」是重点：约束说的是「数据必须满足什么条件」，而不是「检查时怎么一步步写代码」。把校验逻辑交给数据库而非应用代码，所有应用（包括未来的新应用）自动共享同一套守则。</span>这是数据库把「正确性」从应用层上收到数据层的关键一步，也是后续第 8 章规范化理论「好模式为什么好」的语义根基。

## 1 完整性约束：把规则写进数据库

**完整性约束（integrity constraint）**：数据库必须始终满足的一组条件，任何导致条件失效的数据修改都会被拒绝。它的价值在于**从源头拦截**：与其等应用层写一堆校验代码，不如在建表时一次性声明，让数据库成为唯一的裁判。

约束可以按「作用范围」分层：

**单关系内**：约束只涉及一张表的若干列，如某列不许为空、某列取值必须大于 0。
**跨关系**：约束涉及多张表之间的对应关系，如外码必须指向存在的行。
**全局断言**：约束描述数据库整体状态，如「学生的已获学分必须等于其选课记录之和」。

这三层对应的 SQL 机制分别是 NOT NULL/UNIQUE/CHECK、外码声明、以及断言（assertion）。下面逐层展开。

## 2 单关系约束：NOT NULL、UNIQUE 与 CHECK

### NOT NULL

某个属性**不允许为 NULL**。例如教师的名字必须存在：

```sql
CREATE TABLE instructor (
    ID        VARCHAR(5) PRIMARY KEY,
    name      VARCHAR(20) NOT NULL,
    dept_name VARCHAR(20),
    salary    NUMERIC(8, 2)
);
```

### UNIQUE

某个属性（或属性组）的取值**在表中必须互不相同**，作为候选码的约束表达：

```sql
CREATE TABLE student (
    ID    VARCHAR(5),
    email VARCHAR(50) UNIQUE
);
```

### CHECK

用任意谓词约束一列的取值域，语义上最丰富：

```sql
CREATE TABLE account (
    account_no VARCHAR(10) PRIMARY KEY,
    balance    NUMERIC(10, 2) CHECK (balance >= 0)
);
```

CHECK 在**每次插入或修改**时被求值，谓词为假则整条操作被拒绝。<span class="marginnote">注意 CHECK 只在「数据写入」时拦截，已经存在的老数据若先违反了约束，建约束时可能会失败或需要显式迁移——约束是从建立时刻起向后生效的。</span>

**主码（PRIMARY KEY）** 其实是上述约束的组合：**主码 = NOT NULL + UNIQUE**。SQL 规定主码隐含这两条性质，所以写 PRIMARY KEY 就等于同时声明了「非空」和「唯一」——第 2 章《码》里我们把主码定义为「选定的候选码」，这里则看到它在 SQL 中的具体落实。

**辨析｜易错点：** UNIQUE 允许一个 NULL，而主码不允许任何 NULL——因为主码还要承担「定位一行」的职责，值为 NULL 的行无法被可靠定位。所以「UNIQUE 与主码差不多」是不准确的，差就差在**对 NULL 的容忍度**。

## 3 参照完整性：外码与违约动作

**参照完整性（referential integrity）**：外码属性上的每个取值，要么是 NULL，要么必须等于被参照表主码上的某个取值。声明方式：

```sql
CREATE TABLE takes (
    student_id VARCHAR(5) REFERENCES student(ID),
    course_id  VARCHAR(8) REFERENCES course(course_id)
);
```

更标准的写法是把外码单独列出，以便声明**违约时的动作**：

```sql
CREATE TABLE takes (
    student_id VARCHAR(5),
    course_id  VARCHAR(8),
    PRIMARY KEY (student_id, course_id),
    FOREIGN KEY (student_id) REFERENCES student(ID) ON DELETE CASCADE,
    FOREIGN KEY (course_id)  REFERENCES course(course_id) ON DELETE CASCADE
);
```

ON DELETE / ON UPDATE 指定**当被参照的行被删除或主码被修改时**，系统对该外码的处理方式：

**CASCADE**：连带删除/修改引用它的所有行（级联）。
**SET NULL**：把外码置为 NULL。
**SET DEFAULT**：把外码置为默认值。
**RESTRICT / NO ACTION**：拒绝删除或修改（默认行为）。

**辨析｜易错点：** 用错违约动作会造成「连锁误伤」。删除一个系时，CASCADE 会把该系所有课程、所有教师一并删掉——若你只想删系名，这是灾难；而 SET NULL 会把教师的外码清空，使教师变成「无系属」，若该列又声明了 NOT NULL，系统会直接拒绝删除。**选动作前先想清楚：被参照行消失后，引用它的行该怎么处置？** 没有任何动作能同时保证「删得掉」又「数据无损」，这是设计时要权衡的。

## 4 断言：把约束写进数据库整体

CHECK 与外码都只能约束「有限范围」内的条件。若约束涉及**跨表汇总**——比如「学生的已获学分必须等于他所有选课记录学分之和」——就需要**断言（assertion）**：

```sql
CREATE ASSERTION tot_cred_check CHECK (
    NOT EXISTS (
        SELECT s.ID
        FROM student s
        WHERE s.tot_cred <> (
            SELECT COALESCE(SUM(c.credits), 0)
            FROM takes t JOIN course c ON t.course_id = c.course_id
            WHERE t.student_id = s.ID
        )
    )
);
```

断言的语义是：**该谓词在任意时刻都必须为真**。数据库在每次可能影响它的修改后都要重新校验，因此**代价极其高昂**——这也是为什么绝大多数商业数据库（如 PostgreSQL、MySQL）并不真正支持断言，而要求应用用触发器（第 5 章）或应用层逻辑来实现同等效果。<span class="marginnote">断言与 CHECK 的区别正在于「作用域」：CHECK 看一行或一列，断言看整个数据库。作用域越大，校验成本越高，这解释了为什么标准里有它、工程里却很少用。</span>

**辨析｜易错点：** 不要用「触发器」和「断言」互相替代而不看语义差异。断言是**声明式**的——数据库保证它永远成立；触发器是**过程式**的——你在特定事件上挂一段代码，代码没覆盖到的路径就漏了。能用声明式约束解决的问题，优先用声明式。

## 5 公式解析：参照完整性的包含条件

把参照完整性写成一条精确的条件。设参照关系（外码所在表）为 $r$，外码属性组为 $A = (A_1, \ldots, A_n)$，被参照关系为 $s$，其主码为 $K$。则数据库满足参照完整性，当且仅当：

$$
\forall\, t \in r:\qquad
t[A] = \text{NULL} \quad\text{或}\quad t[A] \in \Pi_{K}(s)
$$

逐项拆解这条定义：

- **第一步，读懂 $\forall t \in r$**：条件要对 $r$ 中**每一个元组**成立。外码不是「大多数字典值都能对上」就行，而是**一个都不能失联**——这正是「参照」二字的强度所在。
- **第二步，读懂 $t[A]$ 与 $\Pi_K(s)$**：$t[A]$ 是元组 $t$ 在外码属性组上的取值（一个组合值）；$\Pi_K(s)$ 是把 $s$ 投影到主码 $K$ 上得到的**主码取值集合**（第 2 章的关系代数投影）。于是「$t[A] \in \Pi_K(s)$」就是在说：这个外码值**必须出现在被参照表的主码里**。
- **第三步，读懂那个「或 NULL」**：外码允许为 NULL，此时该元组「尚未归属」，不要求对应任何被参照行。这与你直觉一致：一个还没分到系的教师，dept_name 为 NULL 是合法的。**注意主码里的属性不能为 NULL，但作为外码的属性可以**——主码的「非空」约束并不自动传给外码列。
- **第四步，看违约动作**：当外码值 $t[A]$ 指向的 $s$ 中某行被删除或主码被改，$t[A] \in \Pi_K(s)$ 就可能从真变假。CASCADE 采取的行动是「把 $t$ 也删掉」，从而让条件重新成立；RESTRICT 则干脆拒绝引发违约的删除。**四种违约动作，本质上是「用四种不同方式让这条包含条件重新恢复为真」**。

把这条公式和第 2 章的关系结构连起来看：外码本质上是**两个关系之间的一种包含断言**——它把「表与表之间的语义联系」翻译成了「一个投影集合包含另一个取值」这种纯集合语言。这也解释了为什么第 8 章讲分解时，参照完整性是必须保住的硬指标：**一旦丢失参照完整性，跨表查询（连接）就可能在语义上拼接出「幽灵数据」**。

## 6 小结

- **完整性约束**：数据库始终必须满足的条件，任何违规修改都会被拒绝，是「把正确性收进数据库」的机制。
- **单关系约束**：NOT NULL、UNIQUE、CHECK；**主码 = NOT NULL + UNIQUE**，而 UNIQUE 允许一个 NULL、主码不允许。
- **参照完整性**：外码值要么为 NULL，要么出现在被参照表主码中；ON DELETE / ON UPDATE 的 CASCADE、SET NULL、SET DEFAULT、RESTRICT 是四种「让包含条件重新成立」的违约处置。
- **断言**：CREATE ASSERTION 声明跨表的全局条件，语义强但校验代价极高，多数数据库不支持。
- **声明式优于过程式**：能用约束、断言表达的规则，尽量不落到触发器或应用代码里。
- 参照完整性是第 8 章规范化的硬约束，也是关系代数「连接」语义正确性的前提。
