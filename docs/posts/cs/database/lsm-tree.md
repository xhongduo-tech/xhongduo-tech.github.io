## 为什么从 LSM 树开始

B+ 树的痛点是**写放大**：每次插入都要维护索引结构，随机写落在磁盘各处。**LSM 树（Log-Structured Merge Tree）**换了一条路：写操作只追加到**内存表（memtable）**，满了就**顺序刷盘**成不可变的 SSTable 文件，后台再用 **Compaction** 合并整理。所有写都是顺序写——这在 HDD 时代快了百倍，在 SSD 时代也大幅减少擦写。LSM 树是 LevelDB、RocksDB、Cassandra、HBase、TiKV 的存储引擎核心，也是第 19 章 NoSQL 存储的物理基础。

## 1 LSM 树的层次结构

LSM 树由多层组成：

1. **Memtable（内存表）**：写操作先写入的有序结构（通常用跳表）。在内存里，读写都极快。
2. **WAL（预写日志）**：写入 memtable 前先追加日志，崩溃时能恢复 memtable。
3. **SSTable（有序字符串表）**：memtable 满后**顺序刷盘**生成的不可变有序文件。
4. **层级结构**：SSTable 分层存放（L0, L1, L2, …），下层容量比上层大数倍。

**核心要点：LSM 树把「随机写」转化成「顺序写」+「批量合并」。** 内存累积 + 顺序刷盘 + 后台合并，三步把写性能从 B+ 树的随机 I/O 中解放出来。<span class="marginnote">WAL 与第 15 章恢复系统的「预写式日志」是同一思想：<strong>先把日志顺序落盘，再改数据</strong>。LSM 树天生把 WAL 融入架构——写 memtable 之前先写日志，这是它「崩溃可恢复」的保证。</span>

## 2 读取路径：多层查找

读一条记录 $K$：

1. 先查 **memtable**。
2. 再查 **L0 的各 SSTable**（L0 之间可能有重叠）。
3. 逐层向下查 L1, L2, …（同层 SSTable 键范围不重叠，二分定位到单表）。
4. 命中即返回；**要维护墓碑（tombstone）**——被删除的键以「删除标记」存在，读到墓碑则视为不存在。

**辨析｜易错点：** LSM 的**删除也是写**——插入一个删除标记，而不是物理删除。所以旧版本的键在多层都有副本，必须读到最旧才确定状态。**读一条可能要多层查找**，这是 LSM 树「写快读慢」的根源。

## 3 Compaction：后台的合并

**Compaction（压缩合并）**把多层 SSTable 合并整理，两个目的：

- **去重**：同一键的多版本、删除标记在合并时清除。
- **降层**：把上层小文件合并成下层大文件，控制文件数量。

常见策略：

- **Size-Tiered Compaction**（Cassandra 用）：先把同层小文件堆到一定大小再合并——写友好，但读要查多文件。
- **Leveled Compaction**（LevelDB/RocksDB 用）：严格分层，每层键范围不重叠——读稳定，但写放大更高。

**公式解析：读写放大**

**写放大（write amplification）**：实际写入物理介质的字节 / 应用写入的字节。一次 Compaction 反复重写数据，是放大的来源。

$$
\text{写放大} \approx \frac{\text{各层合并重写量}}{\text{原始写入量}} \approx O(T)
$$

- **第一步，$T$ 是层间大小比**：每层容量约为上一层 $T$ 倍（如 10 倍）。
- **第二步，Leveled Compaction 的写放大**：一个键从 L0 一路合并到最深层，被重写约「层数」次，约 $O(T)$ 量级。
- **第三步，读放大的反作用**：层数越少、$T$ 越大，读时查的层越少（读放大小）但合并重写多（写放大高）——**读写放大此消彼长**。
- **第四步，工程调参**：RocksDB 的写放大通常在 10-30 之间，读放大在个位数。调大 $T$ 省读、调小省写，是 LSM 引擎最重要的旋钮。

## 4 LSM 树 vs B+ 树

| 维度 | B+ 树 | LSM 树 |
| --- | --- | --- |
| 写入 | 随机 I/O，原地更新 | **顺序写 + 后台合并** |
| 读点查 | 快（树高 ~4） | 慢（多层查找） |
| 范围扫描 | 叶子链顺序 | 各层 SSTable 归并 |
| 写放大 | 低 | **高（Compaction 重写）** |
| 读放大 | 低 | 高（多文件查找） |
| 空间放大 | 低 | 中（多版本暂存） |
| 代表 | PostgreSQL、MySQL | RocksDB、Cassandra、TiKV |

**核心要点：LSM 是「写优化」、B+ 树是「读优化」的索引。** 写多读少、写吞吐关键的负载（日志、时序、KV 存储）用 LSM；读多写少、要求低延迟点查的负载用 B+ 树。<span class="marginnote">有趣的是很多系统「两条腿走路」：<strong>WAL 日志用顺序追加（LSM 思想），数据主索引用 B+ 树</strong>。而像 TiKV 这样的 NewSQL 则把全部数据放 LSM——架构选择取决于「哪个瓶颈更痛」。</span>

## 5 LSM 的数值算例与术语速查

**把读写放大算一遍，数字会揭示设计的取舍。** 设数据库每秒写入 10 万条 100B 记录（10 MB/s 应用写），层间大小比 $T=10$。

- **应用写**：10 MB/s 追加到 memtable，顺序刷盘——**磁盘实际接受的是顺序写**。
- **Leveled Compaction 写放大 ~10**：磁盘实际写约 100 MB/s——其中 90 MB/s 来自 Compaction 的反复重写。
- **对比 B+ 树**：B+ 树随机写放大较低，但随机 I/O 使同样 10 MB/s 应用写的磁盘压力大得多（随机 vs 顺序的寻道成本差距可达百倍）。
- **读放大**：读一个键最多查 memtable + 每层 1 个 SSTable = 约 6 次文件访问——比 B+ 树的约 4 次块读稍多，但在磁盘上仍可接受。

**数值算例：写放大对 SSD 寿命的影响** SSD 写入次数有限（擦写寿命），写放大 10 意味着实际擦写量是应用的 10 倍。

- 若应用日写 1 TB，放大 10 后 SSD 日擦写 10 TB。
- 消费级 SSD 寿命约 300-3000 次全盘擦写，1 TB 容量下约 300 TBW——**高速写入下很快就耗完一块**。
- 因此**写放大量级是 SSD 存储引擎选型的第一参数**——这也是为什么 RocksDB 提供 Write Stall、Compaction 限流等控制手段。

**辨析｜易错点：** LSM 的「写快」不是「免维护」——Compaction 在后台持续消耗 CPU 与 I/O，**峰值写入时若 Compaction 跟不上，写入会被 Stall（停顿）**。LSM 的写性能是「平均快」，峰值抖动需要工程兜底（限流、分层合并策略）。

<span class="marginnote">LSM 树与第 11 章外部归并排序是「表亲」：都靠「分块 + 后台归并」驯服超内存/超 I/O 数据。SSTable 合并、归并连接的排序合并，本质都是<strong>同一个多路归并框架</strong>——理解了归并，就理解了 LSM 的一半。</span>

### 术语速查

| 术语 | 含义 |
| --- | --- |
| Memtable | 内存有序表，写先落这里 |
| WAL | 预写日志，崩溃可恢复 |
| SSTable | 有序字符串表，不可变 |
| Compaction | 后台合并去重降层 |
| 写放大 | 物理写 / 应用写 |
| 读放大 | 一次读访问的文件数 |

## 6 小结

- LSM 树：**memtable 累积 → 顺序刷盘成 SSTable → 后台 Compaction 合并**。
- 写路径全是**顺序写**，配 WAL 保证崩溃可恢复；删除用**墓碑标记**。
- 读取要**多层查找**（memtable → L0 → 逐层向下），读点查慢于 B+ 树。
- Compaction 去重降层；**写放大与读放大此消彼长**，层间大小比 $T$ 是关键旋钮。
- LSM = 写优化、B+ 树 = 读优化；写多读少用 LSM，读多写少用 B+ 树。
