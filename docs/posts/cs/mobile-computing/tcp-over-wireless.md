## 为什么从 TCP over wireless 讲起

移动 IP 把数据包送到了移动节点，但互联网上的绝大多数应用跑在 TCP 之上——文件下载、网页、视频、即时消息都依赖 TCP 的可靠传输。问题是，**TCP 的整个设计都建立在「丢包 = 网络拥塞」这条假设上**，而有线链路确实大体如此：丢包极少，丢了就说明中间路由器排队爆了。无线链路却完全不同——瑞利衰落、随机干扰、切换中断都会丢包，而这些都与拥塞无关。<span class="marginnote">这一篇是移动计算里「错位」最典型的地方：上层协议带着「有线时代的直觉」跑在「无线时代的物理信道」上，性能因此急剧劣化。理解这种错位，比背下几条优化协议更有价值。</span>这一篇先回顾 TCP 的拥塞控制，再解剖无线信道如何「欺骗」它，最后给出三类优化思路。

## 1 TCP 拥塞控制：为有线世界而生

TCP 的核心目标是在**未知共享网络**上公平高效地利用带宽。它通过一个滑动窗口控制发送速率，窗口大小的增长由拥塞控制算法决定：

**慢启动（slow start）**：连接建立后，拥塞窗口从 1 个报文段开始，每收到一个 ACK 窗口翻倍（指数增长），快速探测可用带宽；遇到阈值后转入拥塞避免。
**拥塞避免（congestion avoidance）**：窗口每往返时延（RTT）只增加 1 个报文段（线性增长），缓慢逼近网络容量。
**快速重传 / 快速恢复（fast retransmit / recovery）**：收到三个重复 ACK 即判定报文段丢失，立即重传并减半窗口，而不是傻等超时。

这套算法的**隐含假设**有三条：丢包源于拥塞、丢包率极低（有线介质）、RTT 相对稳定。<span class="marginnote">TCP 用一个简单的信号——丢包——同时推断「网络有没有拥塞」和「该发多快」。它不区分丢包的原因，因为设计者相信：在有线网络里，丢包的原因只有一个。这个「信号语义的朴素性」正是它后来在无线里吃亏的根源。</span>

拥塞控制遵循**加性增、乘性减（AIMD）**的经典纪律：慢启动阶段指数探路，拥塞避免阶段线性增长，每次丢包就把窗口砍半。这套「激进增长、保守后退」的策略，保证了共享链路上多个 TCP 流之间的**公平性**——但公平的对象是「相互竞争的有线流」，一旦其中一条是无线链路，公平就变成了「无线流给有线流让路」。<span class="marginnote">AIMD 的另一个深层代价是「锯齿」：窗口永远在「涨满—砍半」的循环里摆动，平均利用率只能达到可用带宽的一部分。无线丢包只是让这个锯齿更密、更低——性能差的不只是峰值，更是平均。</span>

## 2 无线信道如何「欺骗」TCP

无线链路的四个特性逐一击穿 TCP 的假设：

**随机丢包被误判为拥塞**：无线信道因衰落、干扰产生的丢包率常在 1%–10% 量级，远超有线的 10⁻⁶。TCP 一看到丢包就减半窗口、进入拥塞避免——明明带宽充足，吞吐却被白白压下来。

**带宽时延积巨大导致慢启动过低**：长距离链路的带宽时延积很大，慢启动的指数增长需要很多 RTT 才能把窗口涨满；若途中遭遇无线丢包，窗口再次被砍，**长期徘徊在远低于可用带宽的水平**。

**时延抖动与 RTO 误判**：切换、调度造成的时延波动可能让 ACK 迟迟不来，TCP 把「慢」误判为「丢」，触发不必要的超时重传，甚至雪崩式地重启慢启动。

**带宽不对称**：移动链路常是「下行宽、上行窄」（如卫星/蜂窝），ACK 在上行方向挤成一团，被延迟或丢弃，反过来拖慢下行发送。<span class="marginnote">ACK 压缩问题至今仍是 TCP 在不对称链路（卫星、蜂窝上行）上的重要瓶颈。改进思路要么给 ACK 更高的优先级，要么在网关做 ACK 过滤/合包——一个看似「只有几十字节」的 ACK，能决定几百 Kbit 的吞吐。</span>

还有一个常被忽略的因素：**无线链路层自带的 ARQ 重传**。3G/4G/5G 的无线链路协议（RLC）在物理层之上做本地重传，这本身是好事——但重传会引入**额外且可变的时延**：分组在无线侧被反复重传，TCP 看到的是「RTT 突然变大」，同样会被误判为拥塞。**链路层重传与传输层超时之间存在「跨层耦合」**，协调不好时，两层都在做重复的重传，白白浪费无线资源。

把四个因素合起来看，它们的共同点是：**TCP 从丢包信号里读出的结论，在无线环境下几乎总是错的**——要么把噪声当拥塞，要么把变慢当丢失。错误的信号 × 错误的反应 = 反复的性能惩罚。下一节用一条公式量化这种惩罚到底有多重。

## 3 公式解析：吞吐与丢包率的关系

TCP 的吞吐上限与丢包率之间有一个著名的近似关系——**Mathis 公式**：

$$R \leq \frac{MSS}{RTT \cdot \sqrt{p}}$$

- **第一步，认出变量**：$R$ 是 TCP 长期平均吞吐（bit/s），$MSS$ 是最大报文段大小，$RTT$ 是往返时延，$p$ 是丢包率。
- **第二步，理解根号**：吞吐与 $\sqrt{p}$ 成反比——丢包率翻 100 倍（从 10⁻⁶ 到 10⁻⁴），吞吐只降到 1/10；但若丢包率从 10⁻⁴ 升到 10⁻²（无线常见的量级），吞吐骤降 10 倍。
- **第三步，代入数字感受**：设 $MSS = 1460\ \text{B}$、$RTT = 100\ \text{ms}$，则丢包率 $10^{-4}$ 时 $R \approx \frac{1460 \times 8}{0.1 \times 0.01} \approx 11.7\ \text{Mbit/s}$；丢包率升到 $10^{-2}$ 时只剩约 1.2 Mbit/s。**一个百分点的随机丢包，就把 10 Mbit/s 压成 1 Mbit/s。**
- **第四步，直觉**：根号里的 $p$ 揭示了无线丢包的杀伤力——TCP 用「丢包」作为唯一的降速信号，而无线把无关拥塞的噪声喂给了这个信号。**公式不是要你背，是要你看见：为什么无线优化必须处理丢包语义。**

**辨析｜易错点：** Mathis 公式假设丢包是随机的、TCP 工作在稳态、无 SACK 等高级机制，且忽略慢启动与超时。它给出的是**上限**估计，实际吞吐还会更低；但它量化了「丢包率对吞吐的平方根级伤害」这一最重要的定性结论，在工程估算里足够实用。

## 4 三类优化思路：本地修复、连接分裂、端到端改造

无线 TCP 优化的全部方案，可以归入三条路线。理解路线之间的取舍，比记住某个协议更重要。

**路线一：本地修复（link-layer / snoop）**。在无线链路的网关处缓存报文段并本地重传，把无线丢包**在无线侧就地解决**，不让它传导到 TCP。代表是 **Snoop 协议**：网关监听经过的 TCP 流，缓存未确认报文段；检测到无线丢包时在本地重传并抑制重复 ACK。<span class="marginnote">Snoop 的思路是「把问题拦在最后一公里」：TCP 发送端（有线侧）完全无感，只管正常收发。它保持了端到端语义，是三类方案里最「透明」的——代价是网关要有状态、要理解 TCP 语义，且对加密流量（TCP 载荷不可见）无能为力。</span>

**路线二：连接分裂（split connection）**。把端到端 TCP 连接在基站处**拆成两段**：有线段用标准 TCP，无线段用一套对无线友好的传输协议（如 M-TCP、I-TCP 用本地重传与快速恢复）。<span class="marginnote">分裂让「无线的那段」可以自由定制，不必迁就有线端的 TCP 假设；但代价是破坏了 TCP 的端到端语义——中间节点成为连接的一部分，丢包、重启都会影响两端的一致性，也让加密端到端安全更难实施。</span>

**路线三：端到端改造（TCP variants）**。不改变 TCP 的端到端结构，而是改进算法本身：**TCP Vegas** 用时延而不是丢包作为拥塞信号；**TCP Westwood** 用带宽估计自适应设置慢启动阈值；**TCP Cubic** 用三次函数让窗口增长对丢包更「钝感」，已成为 Linux 默认。这些方案从「减少对丢包信号的依赖」入手，让 TCP 在无线里更稳健。

## 5 对比表：三类无线 TCP 优化方案

**纯概念主题，以核心对比表替代公式解析。**

| 维度 | 本地修复（Snoop） | 连接分裂（M-TCP） | 端到端改造（Vegas） |
| --- | --- | --- | --- |
| 修改位置 | 无线网关 | 网关 + 两端 | 发送端/接收端 |
| 端到端语义 | 保留 | 破坏 | 保留 |
| 对 TCP 透明 | 基本透明 | 需要两端配合 | 需要两端部署 |
| 对加密流量 | 失效（看不到载荷） | 受影响 | 无影响 |
| 部署难度 | 低 | 中 | 中高（需推广新算法） |
| 典型代表 | Snoop | M-TCP、I-TCP | Vegas、Westwood、Cubic |

一条经验总结：**想「不打扰两端」就用本地修复，想「彻底定制无线段」就分裂连接，想「长期演进」就改造算法**。现实网络往往混用：蜂窝网在无线侧用 RLC 层重传（路线一），同时主机部署 Cubic（路线三），两层配合。

在带宽时延积极大的**卫星链路**上，还有一类更激进的方案——**TCP spoofing（欺骗）**：卫星网关向发送端「假扮」接收端，提前发送 ACK，让发送端以为链路畅通、全速发送；真正的数据再在卫星段按卫星协议可靠投递。它与连接分裂同理，但连 ACK 的语义都代为处理了。<span class="marginnote">欺骗方案把 TCP 的确认流彻底架空，代价是端到端语义完全由网关承担，一旦网关故障，两端状态就错乱了。它是最「不透明」也最能榨干长肥管道的方案——说明在极端链路上，TCP 假设被突破到什么程度都需要接受。</span>

## 6 新一代传输：QUIC 与移动友好设计

进入移动互联网时代，传输层优化迎来了一位新主角：**QUIC**。QUIC 是建立在 UDP 之上的新一代传输协议（已被 HTTP/3 采用），它对移动环境的改善是结构性的：

**连接迁移（connection migration）**：连接不再绑定「IP 地址 + 端口」，而由 64 位连接 ID 标识。手机从 Wi-Fi 切到蜂窝、IP 变了，连接 ID 不变，**连接可以继续，无需重建**——这是对「切换重启慢启动」问题的釜底抽薪。<span class="marginnote">连接迁移把 TCP 的「地址即身份」改成了「ID 即身份」——你会在《移动 IP》里看到同样的话题。区别在于：移动 IP 在<strong>网络层</strong>解耦身份与位置，QUIC 在<strong>传输层</strong>解耦。两层殊途同归，都是「身份可携带」思想的不同落点。</span>
- **独立字节流（multistreaming）**：一次连接里多个流互相独立，一个流的丢包不阻塞其他流——避免「队头阻塞」在无线丢包下放大。
- **内建 TLS 与更快的握手**：握手与密钥协商合一，减少往返；对频繁切换的移动端，少一个 RTT 就是实打实的体感提升。

**辨析｜易错点：** QUIC 并不「解决」无线丢包——随机丢包依然存在，拥塞控制依然要处理它。QUIC 的贡献是**让连接对网络变化更健壮**：切换不重建、单流不拖累全局、握手更少往返。它没有推翻 Mathis 公式，而是改变了「一次切换付出多大代价」的计算方式。

QUIC 的拥塞控制还继承并放大了「用更丰富信号代替丢包」的趋势：QUIC 可以携带**显式拥塞通知（ECN）**与更细的 RTT 测量，让发送端在丢包发生之前就感知拥塞。配合连接迁移，移动端的传输层终于有了「感知网络变化、快速重配路径」的能力——这是 3G 时代 TCP over wireless 的各类补丁从未达到的完备度。

## 7 易错辨析：无线 TCP 理解的三个误区

**辨析｜易错点：** 集中澄清三个高频误解。

- **「无线丢包和拥塞丢包对 TCP 的伤害一样，所以只要加大重传就行」**：不止。拥塞丢包时该**降速**，无线丢包时该**尽快补发**——两者对发送端的正确反应相反。盲目加大重传会加剧拥塞，盲目降速则浪费带宽。区分丢包原因是所有优化的核心，也正是难点所在。
- **「Snoop 缓存会破坏端到端语义」**：恰恰相反，Snoop 的设计目标就是**保持**端到端语义——它在无线侧重传，但不接管连接；破坏语义的是连接分裂。
- **「切换丢包只是暂时性掉线，TCP 会自动恢复」**：切换引起的暂停常达数百毫秒，足以让 TCP 判定超时并重启慢启动——每次切换都付一次「从头再来」的代价。频繁切换下，吞吐损失是持续的，不是一次性的。

## 8 小结

- TCP 的拥塞控制把「丢包」当作唯一的降速信号，这条假设在有线成立、在无线失效。
- 无线四害：随机丢包误判、慢启动过低、时延抖动、带宽不对称。
- Mathis 公式 $R \leq \frac{MSS}{RTT\sqrt{p}}$：吞吐与 $\sqrt{p}$
