## 为什么从类与接口的设计讲起

学会了 `class`、`interface` 的语法，你也许能写出「能跑」的类。但「能跑」与「值得发布」之间隔着一条深沟：一个设计糟糕的类，一旦被别的代码使用，它的缺陷就成了永久的公共债务——改它破坏调用方，不改它憋屈自己。Effective Java 第 4 章（第 15–25 条）讲的正是**类和接口的「公序良俗」**：如何最小化可访问性、如何设计接口与继承、为什么优先组合而非继承。<span class="marginnote">Java 的「Javadoc 注释」不只是文档，它与你写的类同构：公开成员都能被任何人调用，所以每个公开成员都值得一句「它承诺什么、参数是什么、什么时候抛异常」。把 API 文档当<strong>承诺</strong>来写，是这一章的第一课。</span>这一篇把设计规范归纳成四条主线：可见性、不可变、接口设计、组合优于继承。

## 1 最小化可访问性：信息隐藏

Effective Java 第 15 条：**最小化类和成员的可访问性**——能 `private` 就不 `protected`，能包私有就不 `public`。

**为什么？** 公开 API 是「不可撤销的承诺」。你公开了一个字段，调用方就会依赖它；想改内部实现？调用方的代码在等你。访问面越小，你能自由修改的内部细节就越多——**这是「信息隐藏（information hiding）」的工程价值**：封装让「改内部」的成本趋近于零。

**三个实战建议：**

- **实例字段不要 `public`**：公开字段意味着「任何调用方都能把它改成任意值」，你的不变量瞬间失守。要暴露就暴露访问方法（getter/setter），把校验握在自己手里。
- **公开类不要公开可变字段**：连 `public static final` 数组都是危险的——`public static final Thing[] VALUES = {...}` 看起来是「只读常量」，调用方却可以 `VALUES[0] = evil`。真正的只读做法是返回 `Collections.unmodifiableList(Arrays.asList(...))` 或直接返回防御性拷贝。
- **把「会不会被用到」当作访问级别唯一标准**：不要「反正没人用就 private，也许以后用再放开」。公开是沉重的，`private` 是自由的。

**辨析｜易错点：`protected` 是「半公开」。** `protected` 意味着「所有子类都能调用」——而子类你无法控制。它比 `private` 暴露面大得多，只有「真的要为子类扩展留口子」时才用。

## 2 使可变性最小化：不可变类的艺术

Effective Java 第 17 条：**使类和成员的可变性最小化**——尽量把类设计成**不可变（immutable）**。

**不可变对象**一旦创建，内部状态永不改变。`String`、`BigDecimal`、`LocalDate`、包装类都是不可变的。不可变的好处：

- **天然线程安全**：多个线程共享同一个不可变对象，无需任何同步。
- **可自由共享、缓存、复用**：反正内容不变，引用随便传。
- **失败原子性**：操作过程中抛异常，对象也不会被「改一半」——因为改不了。

**设计不可变类的五个要点：**

1. 不要提供任何「修改对象状态」的方法（setter）。
2. 所有字段 `final` 且 `private`。
3. 类不要被继承——`final` 修饰类，或把构造器设为 `private` 用静态工厂。
4. 若字段是可变对象引用，不要泄露出去：getter 返回拷贝，构造时做防御性拷贝。
5. 需要「修改」时，返回**新对象**：`"abc".toUpperCase()` 返回新的 `"ABC"`。

**重点结论：不可变是「免费的并发安全」，可变是「需要付费的灵活性」。** 在「值对象」上（金额、坐标、日期、颜色）优先不可变——它们没有「状态演变」的语义，可变反而危险。只在对象**确实有状态生命周期**（如 `StringBuilder`、`ArrayList`）时才做可变。

**权衡**：不可变对象每次「修改」都新建对象，少量时开销可忽略，大量拼接才有成本（所以有 `StringBuilder`）。**先写不可变，性能瓶颈出现时再局部可变**——这个顺序比反着来稳得多。<span class="marginnote">JDK 里的 `String`、`BigDecimal`、`LocalDate` 都是不可变的活教材：它们没有 setter、字段 `final`、类 `final`。需要「修改」就返回新对象——`"abc".replace('a','b')` 返回新字符串，原字符串不动。</span>

## 3 接口设计：小而专一

接口是「能力契约」。设计接口的两条铁律：

**第一，接口要「专一」**——一个接口表达一种能力，别塞进无关方法。`Comparable` 只管「可比较」，`Runnable` 只管「可运行」。接口大而全，实现类就被迫实现一堆用不上的方法（Effective Java 第 21 条警告「别为未来设计接口」）。

**第二，接口应「描述能做什么，而非怎么做」**——接口里只有方法签名，实现细节交给实现类。

**接口的合理粒度**：如果某个「能力」被多种类型共享，就抽成接口；如果只是某个类内部的细节，别抽。判断标准：**「这个接口，我会愿意为它写第二个实现吗？」**——不愿意，它就不该是接口。

**「标记接口（marker interface）」的取舍**：`Serializable` 这类没有方法的接口是「类型标记」。它比注解的优势是**类型安全**——`instanceof Serializable` 在编译期就合法；而注解要在运行期反射检查、写错名也不报错。不过现代实践更偏爱注解（可携带参数），见《枚举类型与注解》。

**接口 vs 抽象类的再次确认**：接口是「can-do」、可多实现、能配合 lambda；抽象类是「is-a」、可共享字段与构造器。设计时**优先接口**——它给使用方最大的自由（实现、代理、lambda 都能上）。

## 4 组合优于继承

Effective Java 第 18 条：**优先考虑组合而非继承。** 这里的「继承」指「跨类实现的继承」，它有一个根本缺陷：

**继承破坏了封装。** 子类依赖父类的实现细节，父类一个看似无关的改动（改个方法实现、换个内部结构）就可能悄悄破坏子类。经典案例：`HashSet` 的子类想统计「一共加了多少元素」——重写 `add` 和 `addAll` 计数，结果 `addAll` 内部调用的是父类的 `add`，导致计数翻倍。

```java
// 反例：继承导致的「双重计数」陷阱
class CountingSet extends HashSet<String> {
    private int count = 0;
    public boolean add(String s) { count++; return super.add(s); }
    public boolean addAll(Collection<? extends String> c) {
        count += c.size();               // 计数一次
        return super.addAll(c);          // 父类内部又调 add()，又计数一次！
    }
}
```

**组合（composition）**的做法：把一个类「装进去」，通过转发（delegation）暴露需要的接口：

```java
class CountingSet implements Set<String> {       // 实现接口，而不是继承实现
    private final Set<String> inner = new HashSet<>();   // 组合：内嵌一个真实实现
    private int count = 0;
    public boolean add(String s) { count++; return inner.add(s); }
    public boolean addAll(Collection<? extends String> c) {
        count += c.size();
        return inner.addAll(c);
    }
    // 其余方法转发给 inner……
}
```

组合暴露的是「接口」，不是「父类的所有行为」——你可以决定暴露哪些、如何暴露，`addAll` 想怎么计数都行，不会被动撞上父类内部行为。

**重点结论：继承适合「子类是父类的一种」且「父类的行为就是子类要的行为」；否则组合。** 判断标准（Effective Java 第 18 条）：**「B 真的 is-a A 吗？」** 若 B 只是「要用 A 的功能」，那就是 has-a，该组合。继承不是代码复用的首选工具——**组合 + 接口**是更安全的复用方式。

## 5 核心对比表：继承与组合

纯概念主题用**核心对比表**替代公式解析，把两种复用方式并排比一比：

| 维度 | 继承 | 组合 |
| --- | --- | --- |
| 关系 | is-a（B 是 A 的一种） | has-a（B 拥有一个 A） |
| 关键字 | `extends` | 字段 + 转发方法 |
| 封装 | 依赖父类实现细节 | 只依赖对方公开 API |
| 运行时多态 | 有（父类引用指向子类） | 靠接口实现 |
| 父类改动影响 | 可能悄悄破坏子类 | 不影响 |
| 复用粒度 | 整棵继承树 | 单个对象，灵活 |

**重点结论：组合是「白盒复用」的天敌、`public` 继承是「黑盒复用」。** Effective Java 第 18 条并不否定继承——「子类确实是父类的一种」时继承完全正当（`ArrayList` is-a `List`）。它反对的是「为了复用方法而继承」。顺序应是：**优先组合 + 接口 → 必要时才继承**。这条设计纪律与 Spring 的「组合优于继承」、函数式编程的「对象组合」一脉相承，是 Java 生态里最被低估的架构智慧。

## 6 小结

- **最小化可访问性**：公开 API 是永久承诺，能 `private` 就不 `public`。
- **使可变性最小化**：值对象优先不可变，换来免费的线程安全与失败原子性。
- **接口小而专一**：一种能力一个接口，描述「能做什么」而非「怎么做」。
- **组合优于继承**：继承破坏封装，`addAll` 双重计数是经典案例；has-a 用组合。
- 设计类时先问「这个公开成员会被谁依赖」——把承诺写清楚，是最高级的封装。
