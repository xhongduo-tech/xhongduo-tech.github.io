# 并发编程最佳实践

<div class="epigraph">

## 为什么从并发最佳实践开始

前两章讲了并发的「武器」：`synchronized`、并发集合、线程池、`CompletableFuture`。这一章讲「**纪律**」——Effective Java 第 11 章把并发编程从「能用」推向「可靠」。核心问题始终是那一个：**共享可变状态**。它是竞态、死锁、内存不一致的万恶之源。应对之道不是「更小心地加锁」，而是**减少共享、隔离可变、把同步声明清楚**。这一篇提炼出五条可操作的原则，覆盖同步的边界、线程安全的文档化、延迟初始化的陷阱，以及「别依赖线程调度器」的告诫。

## 1 同步访问共享的可变数据

Effective Java 第 78 条：**同步访问共享的可变数据。** 上一章的 `volatile` 已讲过「可见性」，这一条再补一个更隐蔽的坑——**读线程也需要同步**，不只是写线程。

```java
// 反例：只有写加了同步，读没加——读可能看到旧值
private int count;
public synchronized void increment() { count++; }
public int getCount() { return count; }     // 没同步！可能读到过期的 count
```

**为什么读也要同步？** Java 内存模型允许线程把变量缓存进寄存器/CPU 缓存；只有**进入/退出同步块**才会刷新缓存。读方法不进入同步块，就读不到写线程的最新值——即使写那边加了锁。

**重点结论：要么所有访问都同步，要么根本不共享。** 同步必须**对称**：一个字段若在多线程间共享，它的每一次读、每一次写都要在同步的约束下进行，漏掉任何一侧，同步就名存实亡。<span class="marginnote">这条原则与 `volatile` 的规则互为表里：`volatile` 正是「每次读都刷新、每次写都立即可见」的轻量同步。而「一个线程写、其他线程读」的计数器，用 `AtomicInteger` 或 `synchronized` 更稳。</span>

**最佳实践：不可变对象 + 线程安全对象**。让共享数据**不可变**（改了返回新对象，天然线程安全），或让共享对象是**已线程安全**的（`ConcurrentHashMap`、`AtomicInteger`），就能绕开「手写同步」这个高风险环节。

## 2 避免过度同步与死锁

**过度同步（excessive synchronization）**（Effective Java 第 79 条）：把不该放进临界区的代码也锁住——比如在持有锁时做慢操作（IO、网络、`Thread.sleep`）。后果不只是「慢」，还可能**死锁**：一个线程拿着锁 A 等锁 B，另一个线程拿着锁 B 等锁 A，两个都等不到。

**死锁（deadlock）的四个必要条件**，任一不满足就能避免：

| 条件 | 含义 | 破解手段 |
| --- | --- | --- |
| 互斥 | 锁只能被一个线程持有 | 用不可变/无锁数据结构 |
| 持有并等待 | 拿着 A 等 B | 一次性申请所有锁 |
| 不可剥夺 | 锁不能强抢 | 用 `tryLock` 带超时 |
| 循环等待 | A 等 B，B 等 A | **锁排序**：所有人按同一顺序加锁 |

**重点结论：锁排序是工程上最实用的死锁预防**——多个锁总是按**固定的全局顺序**获取（比如先锁 id 小的）。两个线程都「先拿小的、再拿大的」，循环等待就不成立，死锁从结构上被消除。

**保护不被锁内调用**：**绝不要在持有锁时调用「外部方法」**——那个方法可能是你的、也可能是个可重写的钩子，它若又去拿另一把锁，死锁概率大增。把临界区压缩到「只碰共享数据」，外部调用挪到锁外。

## 3 线程安全的文档化与层次

Effective Java 第 82 条：**文档化线程安全属性。** 类按线程安全强度可分为四个层次，API 应该**写明自己是哪一层**：

| 层次 | 含义 | 例子 |
| --- | --- | --- |
| **不可变** | 实例不可变，天然线程安全 | `String`、`Integer`、`BigDecimal` |
| **无条件线程安全** | 所有公开操作都已同步 | `ConcurrentHashMap`、`StringBuffer` |
| **有条件线程安全** | 多数操作安全，个别需要外部同步 | `Collections.synchronizedMap`（遍历需外部锁） |
| **非线程安全** | 不提供任何同步保证 | `HashMap`、`ArrayList` |

**辨析｜易错点：调用方最怕「有条件线程安全」却不被告知条件。** 比如 `synchronizedMap` 的迭代器**不是**线程安全的——遍历时必须手动在 `synchronized(map)` 里做，而文档若不写明，调用方在并发遍历时就会撞 `ConcurrentModificationException`。**写类时用 javadoc 声明线程安全级别，读类时先看声明再用**。

**私有锁对象技巧**：想让类的内部同步不暴露给外部，用私有锁对象而非 `this` 作为锁——调用方拿不到锁，就无法用你的对象做「外部同步」引发连锁死锁。<span class="marginnote">`this` 作为锁的隐患：调用方如果也写 `synchronized(instance)`，就能用你的对象锁「串门」——锁的用途越公开，被误用导致死锁的概率越高。私有锁把锁的用途锁进类内部。</span>

## 4 公式解析：延迟初始化的双重检查与问题

**延迟初始化（lazy initialization）**是「首次用到时才创建字段」的优化，但**它在多线程下是个陷阱**。经典的「双重检查锁（double-checked locking）」写法看似聪明，实际有内存可见性缺陷：

$$

\text{if (field == null)} \to \text{synchronized 块内再判一次} \to \text{创建}

$$

对这条公式做三步拆解：

- **第一步，快速判空**：字段为 null 才进同步块——绝大多数调用在锁外就返回，性能好。
- **第二步，锁内二次判空**：进入同步块后**再判一次**，防止「两个线程同时看到 null，先后创建两个实例」。
- **第三步，创建**：在锁内真正 `new` 出实例。

**陷阱：不写 `volatile` 的双重检查锁是错的。** 不加 `volatile` 时，「创建对象」不是原子的——`new Singleton()` 在字节码层面是「分配内存 → 调构造器 → 把引用赋给字段」，其中「赋引用」可能被指令重排到「调构造器」**之前**。于是另一个线程在锁外读到「不为 null 但还没构造完」的半成品实例，直接使用就崩了。

**正解一：字段加 `volatile`**——`private volatile Singleton instance;`。`volatile` 禁止重排，保证「构造完成」在「赋引用」之前可见，双重检查锁才成立。

**正解二（更推荐）：静态内部类持有者（initialization-on-demand holder）**：

```java
public class Singleton {
    private Singleton() { }
    private static class Holder {
        static final Singleton INSTANCE = new Singleton();   // 类加载时才初始化
    }
    public static Singleton getInstance() { return Holder.INSTANCE; }
}
```

**为什么正解二更优雅**：JVM 保证「类的初始化（`<clinit>`）由 JVM 加锁」，`Holder` 只有在 `getInstance()` 第一次被调用时才被加载——既延迟初始化、又线程安全、还零锁竞争。**Effective Java 第 83 条「明智地使用延迟初始化」正是此意：延迟初始化是优化手段，非必要不用；要用就选最安全的形态。**

## 5 核心对比表：并发的三层防身术

纯概念主题用**核心对比表**替代公式解析的展开，把「并发可靠性」的三层防线收拢：

| 层 | 手段 | 解决的问题 | 代价 |
| --- | --- | --- | --- |
| 结构层 | 不可变对象、线程安全对象 | 源头消除共享可变 | 设计约束 |
| 同步层 | `synchronized`、`volatile` | 原子性、可见性 | 锁竞争、死锁风险 |
| 文档层 | 线程安全级别声明 | 让调用方用对 | 文档义务 |

**重点结论：并发可靠性是「结构优先、同步兜底、文档闭环」。** 最佳实践的顺序永远一样：**先让共享变少（不可变、线程安全对象），再让剩下的共享被同步保护（对称加锁），最后把「每个类属于哪个线程安全层次」写进 javadoc。** 三层配合，才是 Effective Java 第 11 章「并发」的全部要义——它教你的不是更多锁，而是**更少的共享与更清楚的同步**。

## 6 小结

- **同步必须对称**：读、写都进锁，漏掉任何一侧同步就失效。
- 避免过度同步：锁内不做慢操作、不调外部方法；死锁四条件逐一击破，**锁排序**最实用。
- 文档化线程安全层次：不可变 / 无条件 / 有条件 / 非线程安全，写清楚。
- 延迟初始化用**静态内部类持有者**或 `volatile` 双重检查锁，别裸写。
- 并发的要诀不是「更小心」，而是「更少的共享 + 更显眼的同步」。
