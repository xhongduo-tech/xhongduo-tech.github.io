## 为什么从通用编程规范开始

前几章讲的是「设计」，这一章回到「**日常**」——每天写局部变量、循环、字符串拼接、数值计算时，那些最不起眼却最容易错的地方。Effective Java 第 9 章是「编程常识的成文版」：局部变量作用域要小、循环用 for-each、**别用浮点数算钱**、优先使用基本类型、别用字符串冒充类型、字符串拼接用 `StringBuilder`、命名要清晰。这些规则单个看都「不高级」，但它们决定了一段代码是「能跑」还是「能维护、算得准、不被坑」。

## 1 最小化局部变量的作用域

**局部变量的作用域应该最小化**——在使用它的地方才声明，声明时就要初始化。这是 Effective Java 第 57 条，也是最容易被忽视的「代码卫生」：

- **在首次使用处声明**，不要提前到方法开头堆一摞变量——每提前一步，读者就要多记一个「这变量是干嘛的」直到它被用到。
- **声明时初始化**：`int count;` 这种「先声明、后赋值」的悬空变量，让读者无法确定「此刻它是未初始化还是有意为之」。
- **循环变量作用域收进循环**：`for (int i = 0; ...)` 的 `i` 只在循环内可见——这正是 `for` 比 `while` 干净的地方；用 `while` 时循环变量会泄漏到循环外。
- **优先用 `for-each` 而不是下标循环**（第 58 条）：`for (Employee e : staff)` 没有下标、没有越界风险、没有「手写迭代器」的样板代码。<span class="marginnote">什么时候必须用下标循环？需要同时访问多个集合的对应位置、需要跳过或倒序遍历、需要修改元素——这些场景才退回到传统 `for`。For-each 是默认，下标是特例。</span>

**辨析｜易错点：「一次声明，多处复用」是坏味道。** 一个变量被复用来装两种含义不同的东西，第一次读代码的人没法判断它的真实意图——这是「变量作用域过大」的典型症状，拆成两个小作用域的变量即可。

## 2 数值的真相：浮点数的精度陷阱

**重点结论：不要用 `float`/`double` 表示金钱或其他需要精确十进制的地方。** 看这条经典代码：

```java
System.out.println(1.0 - 0.9);   // 输出 0.09999999999999998，而不是 0.1
```

为什么？`double` 是**二进制浮点数**，它能精确表示的只是「二进制小数」，而 `0.1` 在二进制里是无限循环小数——就像 `1/3` 在十进制里写不尽。于是 `1.0 - 0.9` 落进一个最接近的二进制近似，误差就冒出来了。

**公式解析：浮点数为何「算不精确」**：

$$

0.1_{(10)} = 0.000110011001100\ldots_{(2)} \quad \text{（二进制无限循环小数）}

$$

对这条公式做三步拆解：

- **第一步，十进制 0.1 想写成二进制**：$0.1 \times 2 = 0.2$ 取整数位 0，$0.2 \times 2 = 0.4$ 取 0，$0.4 \times 2 = 0.8$ 取 0，$0.8 \times 2 = 1.6$ 取 1……不断乘 2 取整，得到 `0.000110011...`。
- **第二步，它是无限循环的**：就像 $1/3 = 0.333\ldots$ 在十进制写不尽，$0.1$ 在二进制也是无限循环小数——`double` 只有 53 位有效位，只能**截断**成近似值。
- **第三步，误差累积**：单次截断误差极小，但加减乘除一次次累积，就出现了 `1.0 - 0.9 = 0.09999999999999998`。**不是 Java 的 bug，是「二进制浮点数的固有属性」**——C、Python、JavaScript 全都一样。

**什么时候误差会咬人**：**金钱与十进制精确计算**。`0.1 + 0.2 == 0.3` 在二进制里是 `false`；记账差一分钱，审计就过不了。

**正解一：`BigDecimal`**——以十进制字符串为精确表示：

```java
BigDecimal a = new BigDecimal("0.1");       // 用字符串构造，不用 0.1（那是二进制近似）
BigDecimal b = new BigDecimal("0.2");
BigDecimal sum = a.add(b);                    // 精确的 0.3
```

注意：**构造 `BigDecimal` 用字符串**——`new BigDecimal(0.1)` 会先把 0.1 转成二进制近似再「还原」，反而不精确。

**正解二：以分为单位用整数**——钱先换算成最小单位（分），全程 `long` 整数运算，最后再格式化。性能好、也精确。<span class="marginnote">「以最小单位存整数」是金融系统里更主流的做法：分、厘、毫甚至纳，用 `long` 表示。它既没有浮点误差、又比 `BigDecimal` 快一个量级；代价是格式化与显示要自己补位。电商计价、支付网关大多走这条路。</span>

## 3 字符串拼接：别在循环里用 `+`

Effective Java 第 63 条：**性能敏感的字符串拼接用 `StringBuilder`，别用 `+`。** 看这条循环：

```java
// 反例：每次 + 都创建一个新 String
String result = "";
for (int i = 0; i < 10000; i++) {
    result += i + ",";      // 10000 次拼接 = 10000 个中间 String
}
```

`String` 不可变，`result += ...` 每次都要**新建一个 String、拷贝旧内容、追加新内容**——总成本是 $O(n^2)$ 的（第一次拷贝 1 个字符，第二次拷贝 2 个……）。10000 次拼接，要拷贝约 5000 万字符。

```java
// 正例：StringBuilder 原地追加
StringBuilder sb = new StringBuilder();
for (int i = 0; i < 10000; i++) {
    sb.append(i).append(",");     // 原地修改缓冲区
}
String result = sb.toString();
```

**重点结论：`String` 不可变、拼接用 `StringBuilder`。** 一条 `StringBuilder` 链把 `$O(n^2)$` 压回 `$O(n)$`。这与你学过的「数组扩容」是同一个思想：**可变缓冲区 + 按需扩容**，避免反复复制。固定数量的拼接（两三个字符串）编译器会自动优化，不用担心；**担心的是循环里、动态拼接。**

## 4 别用字符串冒充类型：数值与类型的正确姿势

Effective Java 第 62 条：**别用字符串表示基本类型以外的值。** 「字符串万能论」是常见坏味道：

```java
// 反例：用字符串装数字与类型
String count = "42";
String status = "PAID";
// 需要运算、比较、校验时，全得手写解析与判断

// 正例：用对的类型
int count = 42;
enum Status { PENDING, PAID }   // 状态用枚举，见《枚举类型与注解》
```

**为什么「字符串冒充」是坑**：字符串没有类型约束——`"PAID"` 与 `"paid"` 不相等、`"42"` 不能直接加 1、拼写错误编译器不拦。**能用数字就用数字，能用枚举就用枚举，能用类就用类**——类型是编译器给你的免费校验。

**数值的另一条铁律（Effective Java 第 60 条）：优先基本类型，避免无意识的装箱。** `Integer` 与 `int`：在循环、集合操作里，自动装箱/拆箱有对象分配与判空开销，还可能踩 `Integer` 的缓存与相等性坑（`Integer a = 100, b = 100; a == b` 为 true，但 `a = 200, b = 200` 时 `==` 为 false——因为缓存只到 127）。**能用 `int` 就别用 `Integer`，需要对象语义时才装箱。**

## 5 小结

- **局部变量**：作用域最小化、声明即初始化、优先 for-each。
- **别用 `float`/`double` 算钱**：`BigDecimal`（字符串构造）或以分为单位的整数。
- 循环里拼接字符串用 **`StringBuilder`**，把 `$O(n^2)$` 压回 `$O(n)$`。
- 别用字符串冒充数字/枚举/类型；优先基本类型、避免无意识装箱。
- 这些规则单看都不「高级」，却是「能跑」与「可靠」的分水岭。
