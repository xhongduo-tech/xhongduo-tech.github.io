## 为什么从系统级 I/O 与网络开始

程序与外界交换数据的每一扇门——读键盘、写屏幕、读写文件、收发网络包——在 Linux 上都收敛到同一套概念：**文件描述符**与 **Unix I/O**。而网络编程，恰恰就是「用读写文件的同一套函数，去读写另一台机器上的数据」。<span class="marginnote">这是 Unix 最深刻的设计决定：把设备、文件、网络连接统统抽象成「一个描述符上的字节流」。`read`/`write` 学会一次，键盘、磁盘、socket 全都会了。McIlroy「像花园水管一样把程序接起来」的哲学，正是靠这套统一抽象落地。</span>

上一章《异常控制流》讲了进程与系统调用，本章的 `read`、`write`、`open` 就是这些系统调用的具体面孔；《存储器层次结构》里的页面缓存，也在这里与文件读写相遇。写一个能跑的 HTTP 客户端/服务器，是这一章的毕业设计——它同时把《计算机网络的《计算机网络》专题与《操作系统》专题串了起来。

## 1 Unix I/O：一切皆文件描述符

Linux 里打开的文件、设备、socket，都用一个小整数标识——**文件描述符（file descriptor）**。进程启动时自动打开三个：0 是标准输入，1 是标准输出，2 是标准错误。核心函数就四个：<span class="marginnote">描述符表（descriptor table）是每个进程私有的：一个从 0 起的整数数组，每项指向内核打开文件表的一项。`open` 返回「数组中第一个空闲位置」的下标；`close` 把该项标记为可用。</span>

`open(path, flags, mode)`：打开文件，返回描述符；
- `read(fd, buf, n)`：读至多 n 字节；
- `write(fd, buf, n)`：写 n 字节；
- `close(fd)`：关闭。

**重点：** `read`/`write` 返回的是**实际传输的字节数**，不一定等于你要求的 `n`——这叫**短计数（short count）**。读文件时，只有读到文件末尾才可能返回 0；读写 socket 时短计数是家常便饭，因为对方可能一次只发来一半数据。**永远用返回值判断传输了多少，而不是假设「一次读完」**——这是新手与老手之间肉眼可见的分水岭。

## 2 标准 I/O 与 Unix I/O：一层缓冲之隔

C 库提供的 `stdio`（`fopen`/`fread`/`fwrite`/`fgets`/`printf`）在 Unix I/O 之上加了一层**用户空间缓冲**：数据先攒进缓冲区，够一大块或刷出时才真正调用 `read`/`write`。这样做的好处是系统调用次数从「每字节一次」降到「每 4KB 一次」——`getchar` 能跑得飞快，全靠这层缓冲。<span class="marginnote">缓冲有三态：全缓冲（`fopen` 文件默认）、行缓冲（终端上的 `stdout`）、无缓冲（`stderr`）。为什么 `printf` 后要 `fflush` 才能立刻看到输出？因为行缓冲只在遇到换行或写满时才刷——这一层「看不见的攒货」，是无数「为什么我的输出没出现」谜题的答案。</span>

**辨析｜易错点：** 标准 I/O 与 Unix I/O **不能混着用**：`stdin` 底层缓冲里可能还躺着数据，`read(0, ...)` 却跳过缓冲直接读内核，两边的「读位置」会打架。唯一的例外是 `stdio` 提供的 `fopen` 之后的 `fdopen`/`fileno` 桥接——但混用前务必三思。CS:APP 用「在同一描述符上混用 `read` 与 `fgets`」为例，演示了这类 bug 的典型发病过程。

## 3 网络：从主机到端口

网络编程把「文件」抽象换成「连接」。一台主机用 **IP 地址**标识，一台机器上的某个服务用 **端口号** 标识；「IP:端口」共同确定一个通信端点。<span class="marginnote">IP 找机器，端口找进程。为什么端口是 0–65535 的 16 位整数？因为 TCP/UDP 报文头里只有 16 位给端口。常见端口：HTTP 用 80、HTTPS 用 443、SSH 用 22——约定俗成，方便记忆与默认行为。</span>

**客户端-服务器（client-server）模型**是网络应用的基本骨架：服务器被动监听，等待连接；客户端主动发起连接。一次网络应用的全部意义，可以浓缩成一句：**客户端把「请求」写成字节流写进 socket，服务器从 socket 读出请求、处理、把「响应」写回去**。

「谁主动」是这套模型里最容易被低估的语义：服务器只能监听、等待，永远不能主动连客户；客户端只能主动发起，且必须有确定的服务器地址与端口。这决定了 NAT、防火墙、P2P 等技术为什么那么难做——它们都是在与「谁先开口」的固有不对称作斗争。现代 Web 的 WebSocket、P2P 的打洞，都是把这条不对称补上的工程尝试。

标识的分层速查：

| 层 | 标识 | 例子 |
| --- | --- | --- |
| 应用 | 主机名 | `example.com` |
| 网络 | IP 地址 | `93.184.216.34`（IPv4）、`2606:2800:220:1::1`（IPv6） |
| 传输 | IP:端口 | `93.184.216.34:80` |

## 4 套接字接口：socket 的六步舞

**套接字（socket）**是「文件描述符的网络化身」。建立一个 TCP 连接的完整流程，双方各走各的舞步：

**服务器端：**
1. `socket(domain, type, protocol)` 创建一个 socket 文件描述符；
2. `bind(fd, addr, len)` 把 socket 绑定到自己的 IP 与端口；
3. `listen(fd, backlog)` 开始监听，等待连接；
4. `accept(fd, ...)` 接受一个连接，返回**新的**描述符（此后与这个客户端通话用它）。

**客户端端：**
1. `socket(...)` 创建 socket；
2. `connect(fd, addr, len)` 向服务器地址发起连接。

连接建立后，双方就用普通 `read`/`write` 在这对描述符上通信——**客户端描述符与服务器 `accept` 返回的描述符，就是这条连接的两端**。<span class="marginnote">`accept` 返回「新描述符」而不是复用监听描述符，是个容易忽略但很关键的设计：监听描述符永远只负责「接客」，每个具体客户用自己专属的描述符通信——于是服务器可以用上一章的多进程/下一章的多线程，为每个客户各开一条控制流。</span>

六个核心函数一张表：

| 函数 | 客户端 | 服务器 | 作用 |
| --- | --- | --- | --- |
| `socket` | ✓ | ✓ | 创建 socket 描述符 |
| `bind` | — | ✓ | 绑定本地地址与端口 |
| `listen` | — | ✓ | 转为被动监听 |
| `connect` | ✓ | — | 主动发起连接 |
| `accept` | — | ✓ | 接受连接，返回新描述符 |
| `close` | ✓ | ✓ | 关闭连接 |

**辨析｜易错点：** `connect` 前必须确认端口与地址写进了 socket 地址结构，而地址结构（`sockaddr_in`）的**字节序必须用网络序（大端）**——`htonl`/`htons` 函数就是干这个的。在小端 x86 上忘记字节序转换，端口 80 会被读成 20480，连接必然失败。地址的转换、主机的解析都藏在 `getaddrinfo` 里——它是现代网络编程的正确入口。

在 C 里，地址被塞进一个「类型混杂」的结构：`struct sockaddr` 是通用版本，`struct sockaddr_in`（IPv4）与 `struct sockaddr_in6`（IPv6）是具体版本，用法是「定义具体结构、填充、再强转成 `struct sockaddr*` 传给 socket 函数」。`getaddrinfo` 自动替你填好这一切，所以现代代码里几乎见不到手工构造地址结构——它把「主机名 → IP → 端口 → sockaddr」整条链封装成一次调用。它内部会去 DNS 查域名、查 `/etc/services` 把「http」翻译成端口 80，并按照 `hints` 决定协议族；解析出的每个地址都要试着 `connect`——因为主机可能同时有 IPv4 与 IPv6，一个不行就试下一个，这是健壮客户端的标准态度。

## 5 一个完整的 echo 服务器

把上述舞步拼起来，就是 CS:APP 的经典 `echo` 服务器骨架：`open_listenfd`（socket + bind + listen）之后，`accept` 循环里为每个新连接 `echo` 收到的每一行。客户端则 `open_clientfd`（socket + connect）后写一行、读一行。

**重点：** 这里能看清三个系统级细节：其一，**连接是字节流，不是消息**——TCP 不保证一次 `read` 就拿到一整个「请求」，服务器必须自己按协议「组装」字节（比如读到换行符才算一行）；其二，`accept` 返回的描述符用毕要 `close`，否则连接数耗尽；其三，**循环只服务一个客户端，其他请求在监听队列里排队**——这正是下一章《并发编程》要解决「同时服务多客户端」问题的入口。<span class="marginnote">echo 服务器是「hello world 之后的第一个网络程序」，但它已经包含了网络编程的全部要素：地址、连接、字节流、循环、关闭。给它加上多线程，就是现代 Web 服务器的雏形。</span>

回看 echo 服务器，它暴露了单线程循环的致命伤：`accept` 返回后，若前一个客户端一直不发数据，服务器就卡在 `read` 上，后续连接全部在监听队列里排队。解法有三条路线：**多进程**（每连接 fork 一个子进程）、**多线程**（每连接开一个线程）、**I/O 多路复用**（单线程同时盯多个描述符）。三者是《并发编程》一章的主线，也是现代 Web 服务器架构的岔路口。

把「echo 服务器」读成一份解剖图：`open_listenfd` 负责 socket+bind+listen，`accept` 循环负责接客，`echo` 函数负责读一行回一行。它缺的正是错误处理与并发——生产代码里，`accept` 失败要 `close` 后重试、每个连接要限制读入长度、`EINTR` 要重新发起系统调用。从玩具到生产，差的从来不是「功能」，而是「面对每一种失败都不崩溃」。

## 6 从 echo 到 HTTP

HTTP 不过是 echo 换了个协议：客户端发一个 `GET / HTTP/1.1` 请求行，服务器解析后回一个 `HTTP/1.1 200 OK` 状态行 + 响应体。<span class="marginnote">写一个 HTTP 客户端 = 建立 TCP 连接 + 按 HTTP 文本协议格式化请求 + 读响应。写一个 HTTP 服务器 = accept + 解析请求行 + 返回状态行与文件内容。CS:APP 的 Web 服务器小项目正是这么一步步长起来的——网络协议的表层，几乎全是文本与字节流的拼装。</span>

**重点：** 到这一步，本书「系统的所有层次终于打通」：信息表示（响应字节的编码）→ 机器级表示（处理请求的代码）→ 存储层次（被服务的文件）→ 链接与进程（服务器程序本身）→ 异常控制流（每个请求的 fork/线程）→ 系统级 I/O（socket 上的读写）。你写的每行代码，都同时是这六层约定的一次兑现。

HTTP 协议的请求格式其实非常简单：一行请求行（方法 + 路径 + 版本）、若干请求头（每行一个「键: 值」）、一个空行、然后是可选的消息体。解析它就是「按行读、按冒号切」——`readline` 加字符串处理的活。CS:APP 的 Web 服务器作业正是这样从零拼出响应头 `HTTP/1.1 200 OK` + `Content-Length` + 空行 + 文件内容。

还有一个容易被忽略的工程细节：HTTP/1.0 每次请求都开一条新 TCP 连接，握手开销巨大；HTTP/1.1 默认 **keep-alive**，在同一连接上复用多个请求——代价是服务器必须按 `Content-Length` 或 chunked 编码区分「一个响应的边界」，否则数据会粘连。这个「复用连接却要自己划边界」的矛盾，正是字节流与消息之间的永恒张力。

**TCP 的建立与拆除**：三次握手——客户端发 SYN，服务器回 SYN+ACK，客户端再回 ACK——之后双方才各自就绪；四次挥手——主动方发 FIN，对端回 ACK，对端再发 FIN，主动方回 ACK——之后连接关闭。这些握手都在 `connect`/`accept`/`close` 内部自动完成，程序看到的只是「函数返回成功」。**易错点：** `close` 只是「我想关了」，对端可能还在发数据；半关闭用 `shutdown(fd, SHUT_WR)` 才能精确控制「我不再写了但仍可读」——HTTP/1.1 服务器告诉客户端「请求体发完了」正靠它。若服务器 `close` 前忘了读走未处理的数据，客户端可能收到 `RST`，连接被硬生生掐断。

在《并发编程》之前，先认识一个更轻量的并发形态：**I/O 多路复用（multiplexing）**。`select`/`poll` 让一个线程同时监视多个描述符，哪个可读就处理哪个——不需要为每个连接 fork 或开线程。它的上限是「同时监视的描述符数」，且每次都要重新把集合传给内核，连接数到几千后开销可观；Linux 的 `epoll` 把「注册」与「等待」分开，`epoll_wait` 只返回就绪的那几个，复杂度从 O(n) 降到 O(就绪数)——这正是「C10K 问题」的经典答案之一，也是 Node.js 事件循环与 Nginx 高性能的底层逻辑。

## 7 小结

- Unix 用**文件描述符**统一了设备、文件与网络；四个核心函数 `open`/`read`/`write`/`close`。
- **短计数**是 I/O 的常态：永远用返回值判断实际传输量，别假设一次读完。
- 标准 I/O 在 Unix I/O 之上加**缓冲**，换来系统调用锐减；缓冲态分全缓冲/行缓冲/无缓冲，且两者不可混用。
- 网络 = IP 找主机 + 端口找进程；客户端-服务器模型是网络应用的骨架。
- 套接字六步舞：服务器 `socket→bind→listen→accept`，客户端 `socket→connect`；字节序必须网络序。
- TCP 是字节流不是消息，服务器要按协议自行组包；echo 到 HTTP 之间只差一层文本协议。
- 网络编程把前六章的系统知识全部串成一条线——而「同时服务多客户端」这道题，就留给下一章《并发编程》。

在下一节，我们将让服务器「分身」——**并发编程**：线程、共享变量、竞态与信号量，看操作系统如何在多份控制流之间维持秩序。
