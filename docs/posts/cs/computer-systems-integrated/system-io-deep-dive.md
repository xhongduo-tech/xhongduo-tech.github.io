## 为什么要把系统级 I/O 单拎出来

第八篇《系统级 I/O 与网络编程》搭好了 I/O 的骨架——描述符、四个核心函数、socket。但「会用 read 和 write」和「懂 I/O」之间，还隔着一层没人替你讲透的机制：为什么两个文件描述符可以「共享同一个文件位置」？`dup2` 凭什么一句命令就实现重定向？`printf` 的数据到底攒在哪儿、又什么时候才真正写出去？这一篇，就是把这些「看不见的管道与阀门」逐个拧开。<span class="marginnote">McIlroy 的「花园水管」意象精准得可怕：重定向是接水管，管道是把 A 的输出接到 B 的输入，`dup2` 是换一个水龙头。Unix I/O 的全部高级技艺，都是「让字节流按你想要的方式流动」。</span>

它同时是全书 I/O 线的收尾：上一章《虚拟内存》的 `mmap` 在这里与文件读写面对面，第八章《异常控制流》的系统调用在这里有了具体的字节流形态，而第七篇的网络 socket 在本篇的「描述符共享」机制上获得更深的含义——`fork` 后父子进程共享打开文件，正是并发服务器能工作的基石。

## 1 文件描述符不是「文件」，是指针

**文件描述符（fd）**是打开文件在内核里的「句柄」：`open` 返回一个 0 起的整数，它指向内核**打开文件表**中的一项。每项记录着**文件位置（file position，偏移量）**、引用计数、以及指向**v-node 表**（文件的元数据与磁盘信息）的指针。<span class="marginnote">进程里的每个描述符，只是「打开文件表项」的一个引用。理解这三张表——进程的描述符表、内核的打开文件表、v-node 表——是理解文件共享、重定向与关闭语义的唯一钥匙。</span>

**重点：** `read`/`write` 会**更新文件位置**：读 10 字节，位置前进 10，下次接着读。文件位置是打开文件表项的属性，而不是进程或文件的属性——这句话是理解「两个描述符怎么共享偏移」的入口。

把文件位置的操作单列出来：`lseek(fd, offset, whence)` 只移动位置、不碰数据，`whence` 可选 `SEEK_SET`（从头）、`SEEK_CUR`（当前位置）、`SEEK_END`（从尾）。`tail -n 1`、`od -j`、随机访问数据库都靠它「跳到某处再读」。**易错点：** 对管道、socket、终端调 `lseek` 会失败——它们的「位置」概念不存在，这正是流（stream）与文件（file）的分界。

`read`/`write` 返回 `-1` 表示出错，具体原因查 `errno`：`EINTR`（被信号打断）、`EAGAIN`（非阻塞下暂时没数据）、`EBADF`（描述符非法）。系统级程序员写 I/O 时几乎都会习惯性地 `if (n < 0) perror("...")`——把错误分层，是「面向系统编程」区别于「玩具代码」的起点。

## 2 文件共享：同一文件的两种打开方式

两个进程 `open` 同一个文件，各自会得到**独立的打开文件表项**：各有一个文件位置。它们写同一个文件，会互相覆盖——因为各自从自己的位置写起。<span class="marginnote">这在 shell 里太常见了：`echo a > f; echo b > f` 两个命令各自 open，第二个命令把第一个的成果整个覆盖。但如果用 `>>` 追加模式（`O_APPEND`），内核保证每次写前都把位置移到文件末尾——原子追加，两个写者就能安全地「排队」写同一个文件。</span>

**fork 之后**：子进程复制了父进程的**整个描述符表**，于是父子进程共享**同一个打开文件表项**——**文件位置也共享**。`fork` 后父子各自 `write`，会像「两个人共用一个光标」一样接着写，而不是各自从 0 开始。<span class="marginnote">这正是并发服务器的原理：服务器 `fork` 后，父子都持有 `accept` 返回的连接描述符——共享同一打开文件表项，即共享同一条 socket 连接。谁 close 自己那份，连接的另一端依然有效，因为内核打开文件表项的引用计数还没归零。</span>

**辨析｜易错点：** 「文件位置是共享的」只在「多个描述符指向同一打开文件表项」时成立；两个独立的 `open` 各自为政。判断共享与否，就看**是否经由同一内核打开文件表项**——描述符表的复制（fork）与显式 `dup` 都会共享，独立 `open` 不会。

再强调一次引用计数的作用：`close` 只是把描述符表里那一项标成空闲，真正的「关闭文件」发生在打开文件表项的引用计数归零时。父子进程共享同一打开文件表项，`fork` 后如果各自都 `close`，该表项计数减到 0，文件才真正关闭——这也解释了为什么服务器常「fork 后立刻在父进程 close 连接描述符」：父进程不再需要它，但子进程那份还开着，连接不会断。

**文件位置的移动与原子性**：`O_APPEND` 保证「把位置移到末尾再写」是一条原子操作（内核语义保证），因此日志可以用追加模式安全地多进程并发写；而普通 `O_WRONLY` 下「先 `lseek` 到末尾再 `write`」是两条调用，两个写者之间可能插入别人的写——这正是「追加模式被日志系统广泛使用」的机制原因。

## 3 重定向：dup2 的魔力

`dup2(oldfd, newfd)` 是重定向的原子：它让 `newfd` 指向 `oldfd` 所指向的**同一个打开文件表项**，并关闭 `newfd` 原本指向的那一项。<span class="marginnote">`dup2(fd, 1)` 让「标准输出」指向 `fd` 所指向的文件——从此所有往 stdout 的 `printf` 都写进那个文件。shell 里的 `ls > out.txt`，本质就是 fork 出一个子进程、在里面执行这条 `dup2`、再 exec `ls`。重定向不是魔法，是几行描述符操作。</span>

**重点：** 借助文件位置共享的语义，`dup2` 能实现**镜像重定向**：`dup2(1, 2)` 让 stderr 与 stdout 指向同一个文件表项——两者共享文件位置，输出不会互相踩踏，是「日志同时写给屏幕和文件」的标准做法。<span class="marginnote">Linux 的 `2>&1` 语法，翻译成系统调用就是 `dup2(1, 2)`。而 `1 > file 2> file` 用两个独立 open 则各自持有位置，互相覆盖——这正是「`>` 与 `2>&1` 的区别」这一千古名坑的机制答案。</span>

## 4 短计数与 RIO：健壮 I/O

我们反复强调：`read`/`write` 返回的是**实际传输的字节数**，可能少于请求——**短计数（short count）**。对本地普通文件，短计数极少（到文件末尾才出现）；但读 socket、管道、终端时，短计数是常态，因为数据是「流式」到达的，永远不知道对方下一批会发多少。<span class="marginnote">新手最常见的 I/O bug：`read(fd, buf, MAX)` 一次读就假设拿到了全部数据，于是解析 buf 时访问越界或解析到垃圾。服务端程序里这类 bug 的后果通常是「偶发协议错误」——最难排查的那一类。</span>

CS:APP 的 **RIO（Robust I/O）**包，就是「跟短计数硬碰硬」的教科书解法：`rio_readn`/`rio_writen` 用循环把 `read`/`write` 包到「要么传输完、要么出错」为止；`rio_readlineb` 则带缓冲地按行读。**辨析｜易错点：** RIO 的「n」类函数对**普通文件**可以放心用，但对**网络 socket** 必须与缓冲版配合——因为服务端要按「消息边界」而不是「字节数」解析数据，而 socket 只是字节流，消息边界得靠协议自己约定（比如读到 `\r\n` 才算一行）。这是上一章「TCP 是字节流不是消息」在本章的延续。

短计数的应对还分「阻塞」与「非阻塞」两条路。默认 `read` 是阻塞的：没数据就挂起。若把描述符设为非阻塞（`fcntl` 的 `O_NONBLOCK`），`read` 没有数据时立即返回 `-1` 与 `EWOULDBLOCK`——配合 `select`/`poll`/`epoll`，就是事件驱动、单线程并发服务器的地基。RIO 的循环只解决「一次读不够」，而「什么时候读、读完做什么」是更高层的调度问题，留给《并发编程》与网络专题。

## 5 标准 I/O 的缓冲：看不见的仓库

`stdio`（`printf`/`fgets`/`fopen`）在 Unix I/O 上加了一层**用户空间缓冲**：数据先攒进缓冲区，满一大块、遇到换行、或显式 `fflush` 时才真正调用 `read`/`write`。缓冲有三种模式：**全缓冲**（文件，攒 4KB）、**行缓冲**（终端上的 stdout，遇换行刷出）、**无缓冲**（stderr）。<span class="marginnote">为什么调试时 `printf` 不出东西、加个 `\n` 或 `fflush` 就出来了？因为管道里 stdout 是全缓冲——数据全在仓库里躺着，没到 4KB 不发货。这个「看不见的仓库」是系统级 I/O 里最反直觉、也最常被忽视的一层。</span>

缓冲三态速查：

| 模式 | 何时刷出 | 典型场景 |
| --- | --- | --- |
| 全缓冲 | 缓冲区满（约 4KB）或 `fflush` | 普通文件、管道 |
| 行缓冲 | 遇换行符或 `fflush` | 终端上的 stdout |
| 无缓冲 | 立即 | stderr |

一个经典的「看不见的仓库」事故：`printf` 之后 `fork`，若 `printf` 的输出还躺在行缓冲里，`fork` 会把这份缓冲连同进程一起复制——于是父子进程各自把同一段文本写了一遍，屏幕出现两遍输出。这正是「先 `fflush` 再 fork」这条铁律的来源：**缓冲是进程地址空间的一部分，它随 fork 复制，也随 execve 清空**。

**重点：** 标准 I/O 与 Unix I/O **不能混用**：`stdio` 的缓冲区里可能还有未落地的数据，此时直接 `read(fd, ...)` 会绕过缓冲读内核，两边的文件位置与数据错位。混用的唯一正确姿势是先 `fflush`，或在两者之间用 `fileno`/`fdopen` 桥接——但 CS:APP 的建议更干脆：**在套接字上永远用 Unix I/O 或 RIO，不要用 `stdio`**，因为 socket 没有文件末尾（EOF 语义不同），`feof` 与真实连接关闭之间极易产生误判。<span class="marginnote">一句话版本：文件用 stdio（方便、带缓冲），socket 用 RIO/Unix I/O（可控、无缓冲陷阱）。把两者对调，就是教科书级别的「偶尔正常、经常抽风」。</span>

缓冲行为不是天生定死的：`setvbuf` 可以手工切换缓冲模式，`fflush` 强制刷出。日志系统的「实时落盘」、交互终端的「按行回显」，全是对默认缓冲策略的有意改写——理解默认值，才知道何时该打破它。而**描述符跨 `execve` 存活**的机制也在这里汇合：`execve` 用新程序替换进程映像，但打开的描述符默认保留，shell 的 `cat < in.txt` 重定向正是靠「fork 后 `dup2` 再 exec」实现的；若想 exec 时自动关掉某些描述符，用 `fcntl` 的 `FD_CLOEXEC` 标记。

## 6 元数据、目录与 /proc

`read`/`write` 只搬数据，要问「这个文件多大、谁拥有、何时改过」，得用 **`stat`**——它填一张 `struct stat`，包含文件类型、权限、大小、时间戳等元数据。<span class="marginnote">`stat` 是命令行的老朋友：`ls -l` 的每一列都来自一次 stat 调用。文件大小与「文件里有多少可读字节」是两回事——后者由文件位置决定，这正是 `tail`、`lseek` 等工具能随意跳读的机制基础。</span>

**目录**本身也是文件：它的「内容」是一个个 `dirent` 结构（文件名 + inode 号）。`ls` 无非是 `opendir`/`readdir` 循环读目录条目，再对每个条目 stat 出细节。**辨析｜易错点：** 「目录里有什么」由目录条目决定，与文件系统如何存储这些条目无关——`readdir` 返回的顺序不保证排序，`ls` 之所以看起来有序，是它自己 sort 过。

自己写一个 `ls` 的思路，就能把「目录是流」落到实处：`opendir` 得到目录流，循环 `readdir` 读出每个 `dirent`（名字 + inode 号），再对每个名字 `stat` 拼出权限、大小、时间。任何「目录有多大」的问题都答不上来——**目录没有「大小」，只有「条目流」**，这正是目录与普通文件在语义上最大的不同。

**`/proc`** 是 Linux 的「虚拟文件系统」：它不是磁盘上的真实文件，而是内核数据的窗口。`/proc/self/maps` 显示进程的地址空间映射，`/proc/cpuinfo` 是 CPU 详情，`/proc/<pid>/...` 是每个进程的状态。<span class="marginnote">`/proc` 把「内核内部状态」伪装成普通文件，让上一章讲的虚拟内存、第七章的链接段、甚至系统调用的计数都可以用 `cat`、`grep` 直接查看——它是「一切皆文件」哲学的终极形态，也是调试系统问题时的第一侦察兵。</span>

## 7 两张对照表：把 I/O 的层次钉死

**Unix I/O 与标准 I/O 的对照：**

| 层面 | Unix I/O | 标准 I/O |
| --- | --- | --- |
| 打开 | `open` | `fopen` |
| 读 | `read` | `fread` |
| 写 | `write` | `fwrite` |
| 缓冲 | 无（直接系统调用） | 有（全/行/无） |
| 适用 | socket、精确控制 | 普通文件、格式化输出 |
| 与描述符 | 直接拿 fd | 用 FILE\*，内部包着 fd |

**三张内核表的层级：**

| 表 | 归属 | 内容 | 共享与否 |
| --- | --- | --- | --- |
| 描述符表 | 每个进程 | fd → 打开文件表项 | fork 时复制 |
| 打开文件表 | 内核全局 | 文件位置、引用计数 → v-node | 共享（dup/fork） |
| v-node 表 | 内核全局 | 文件类型、大小、磁盘块 | 同文件共享 |

**重点：** 这两张表就是本节全部内容的索引——判断「两个描述符是否共享文件位置」看第二张表；判断「该用哪个 I/O 接口」看第一张表。把机制钉在表格里，比背十条经验法则可靠得多。

把这两张表记牢，I/O 的机制地图就画完了；剩下的是把它们拼进具体程序时，对每一处错误路径保持敬畏——`EINTR` 要重试、`EWOULDBLOCK` 要等待、`EBADF` 要关闭后重新打开。系统级编程的成熟，一半是机制知识，一半是「每种失败都写进代码」的习惯。

## 8 小结

- 描述符是「指针」不是「文件」：进程描述符表 → 内核打开文件表（存文件位置）→ v-node 表。
- **文件位置**是打开文件表项的属性：独立 `open` 各自为政，`fork`/`dup` 则共享同一个文件位置。
- **`dup2`** 是重定向的原子操作：shell 的 `>`、`2>&1` 都是它的包装；共享位置让镜像重定向互不踩踏。
- **短计数**是流式 I/O 的常态：`rio_readn`/`rio_writen`/`rio_readlineb` 用循环与缓冲对付它。
- **标准 I/O 有三态缓冲**（全/行/无），与 Unix I/O 混用必须 `fflush`；socket 上别用 `stdio`。
- `stat` 给元数据，目录是 `dirent` 的流，`/proc` 把内核状态伪装成文件。
- 两张表（接口对照、内核表层级）是本章一切结论的索引。

至此，从位模式到字节流，从单条指令到并发服务器，从虚拟地址到文件共享——CS:APP 视角下的计算机系统全景已经走完一遍。下一站，无论你转向《操作系统》专题去深挖调度与文件系统，还是转向《并发并行程序设计》去实战多线程与分布式，这里的每一条机制都会成为你脚下的地基。
