## 为什么从链接开始

写完 `main.c`，敲下 `gcc main.c`，一个 `a.out` 凭空出现，双击就能跑。这中间发生了什么？多数程序员的答案是「编译」，但更准确的答案是——编译只占了前一半，**链接（linking）**完成了「把分散的目标文件拼成完整程序」的后一半。<span class="marginnote">链接是 CS:APP 里公认「最被低估」的机制：它几乎不产生你「看得见」的成果，却决定了符号冲突、库版本、启动速度、甚至攻击面。斯波尔斯基说的「有漏洞的抽象」，链接绝对名列前茅——因为直到出错之前，你都意识不到它的存在。</span>

链接在 C 程序里的典型表现：`undefined reference to 'foo'`、重复定义、以及「为什么我改了头文件还要重编」——这些报错的根源全部在这章。它与《编译原理》专题的分工是：编译器负责把 C 变成汇编与目标文件，链接器负责把目标文件变成进程。上一章的存储器层次结构则告诉我们，链接器的产出会被加载器读进内存、映射成进程。

## 1 链接器做的事：符号解析与重定位

链接器只有两件大事：

**符号解析（symbol resolution）**：把程序里的每个全局符号（函数名、全局变量）关联到它的定义。编译器产出目标文件时，只能保证「本文件内的引用」有着落；跨文件的引用——`call printf` 里的 `printf`——必须由链接器在「所有目标文件 + 库」里找到那个定义。<span class="marginnote">你在 `a.c` 里调用了 `b.c` 定义的函数，编译 `a.o` 时编译器只能生成「未解析引用」的占位，真正的地址要等链接阶段才知道。这就是为什么单独 `gcc -c a.c` 不会报「未定义」，而 `gcc a.c` 才可能报。</span>

**重定位（relocation）**：链接器把符号解析的结果写成最终地址——把占位的「虚拟地址」换成真实的内存地址，并逐条修正机器指令中的引用。

**辨析｜易错点：** 链接是「把符号变成地址」的过程，而不是「把代码复制粘贴」的过程。链接失败报的 `undefined reference`、`multiple definition` 都发生在符号解析阶段——这两个错误占了 C 初学者链接报错的大半。

## 2 目标文件：ELF 的三种形态

Linux 的目标文件遵循 **ELF（Executable and Linkable Format）** 格式，由文件头、各 section 与节表组成。三种主要形态：<span class="marginnote">ELF 的三个「文件头 + 节表」结构，把「信息」与「布局」分离：`readelf -h` 看头、`readelf -S` 看节、`objdump -d` 反汇编。调试器、反汇编器、加载器都在读这张同一张表。</span>

**可重定位目标文件（`.o`）**：编译器的直接产物，代码节 `.text`、已初始化数据节 `.data`、未初始化数据节 `.bss`，以及最重要的 **`.symtab`（符号表）** 与 **`.rela.text`（重定位节）**——后者记录了「哪些指令里的哪个位置需要被修正」。<span class="marginnote">`.bss` 有个有趣的特质：它不占文件空间，只是「声明将来要多少未初始化内存」。所以 `char buf[100000]` 的全局数组几乎不增加可执行文件大小——初始化过的数据才真的写进文件。</span>
**可执行目标文件**：链接器的最终产出，多了程序头表（告诉加载器每段放哪、权限如何），并把代码与数据**合并**到连续的虚拟地址上。
- **共享目标文件（`.so`）**：可被多个进程加载的库，静态与动态链接都靠它，见第 5 节。

**重点：** ELF 里的「节（section）」是编译期概念，而加载进内存后的「段（segment）」是运行期概念——同一个 `.o` 的多个节会按权限合并成 `.text`（只读可执行）、`.data`（读写）等少数几个段。这层「节 → 段」的合并不是细节，它是下一章虚拟内存里「按段设置权限」的前提。

## 3 符号解析的规则：强符号与弱符号

每个全局符号有两种强度：**强符号（strong）**是函数或已初始化的全局变量；**弱符号（weak）**是未初始化的全局变量（C 里写作普通 `int x;` 而非 `int x = 0;`）。<span class="marginnote">C 的历史包袱：为了让一个未初始化的全局变量在多个文件里「共享」而不会连环报错，标准把这类符号定为弱符号——代价是「多重定义不报错」的怪规则，也正是无数诡异 bug 的源头。</span>

符号解析的铁律只有三条：

1. **同名的多个强符号 = 链接错误**（`multiple definition`）。
2. **一个强符号 + 多个弱符号 = 取强符号**。
3. **多个弱符号 = 任选其一**（通常是第一个出现的）。<span class="marginnote">规则 3 最坑：如果两个 `.c` 文件各声明了一个未初始化的同名全局变量 `int flag;`，链接器静默地只保留一个——而你的直觉是「应该报错」。等到两个文件对 `flag` 的语义不一致，排查半天也想不到是链接器替你「选」了。最稳妥的做法：跨文件共享状态用 `extern` + 唯一定义。</span>

**辨析｜易错点：** 规则 1 的常见误区——把 `int x;` 写在头文件里且每个 `.c` 都 `#include` 它。头文件保护只防「一个文件内重复包含」，防不了「多个 `.c` 各声明一份」——于是弱符号相安无事，`int x = 0;` 的强符号版本则直接引爆多重定义错误。全局变量的定义永远只该写在一个 `.c` 里。

## 4 重定位：把符号换成语义地址

符号解析确定了「每个引用指向谁」，重定位则负责「把地址写进指令」。链接器逐条扫描重定位节 `.rela.text`，对每个重定位条目套用公式。以 x86-64 的 PC 相对引用为例，设符号 $s$ 定义在目标地址 $ADDR(s)$，重定位条目在节内的偏移为 $r.offset$：

$$
\text{refaddr} = ADDR(s) + r.offset, \qquad
\text{写入值} = ADDR(r.symbol) + r.addend - \text{refaddr}
$$

分四步拆解：

- **第一步，refaddr**：这条指令在最终可执行文件里的地址 = 所在节被放置的基址 $ADDR(s)$ 加节内偏移。
- **第二步，目标的绝对地址**：$ADDR(r.symbol)$ 是被引用符号最终落定的地址，$r.addend$ 是编译器预先留好的「小修正」。
- **第三步，为什么要减去 refaddr**：x86 的跳转与数据引用大多用**PC 相对**寻址——指令里存放的是「从本条指令末尾到目标的距离」，而不是目标的绝对地址。于是写入值 = 目标地址 − 本条指令地址。
- **第四步，为什么 PC 相对**：代码段被加载到不同基址时（ASLR），绝对地址会全部失效；而「相对距离」在代码段内部保持不变——这就是动态加载与地址随机化都能安心工作的机制根源。<span class="marginnote">PC 相对引用是「位置无关代码（PIC）」的基础：共享库里的函数调用用相对地址，库被加载到任何地址都能跑，无需重写指令。这是现代安全（ASLR 随机化加载基址）与共享库能共存的唯一方式——第三章讲 `%rip` 相对寻址时埋下的伏笔，在这里揭晓。</span>

## 5 静态链接与动态链接：PLT 与 GOT

**静态链接**把库的代码直接拷进可执行文件——程序自包含、启动快，但每个程序都带一份 `printf`，文件巨大，且库升级必须重编程序。<span class="marginnote">静态链接是「把所有菜谱抄进菜谱本」；动态链接是「菜谱本里只记一句『看《家常菜》第 3 页』」——省纸，但书必须始终在书架上。</span>

**动态链接**用两个小节实现「运行时才接上」：

**PLT（过程链接表）**：每个动态库函数在代码里有一段跳板，第一次调用时把控制交给动态链接器去解析，之后直接跳转。
- **GOT（全局偏移表）**：保存被引用数据的实际地址，由链接器或加载器填写。<span class="marginnote">「延迟绑定（lazy binding）」让大多数动态库函数第一次调用时才解析——启动时不必解析几千个符号，快很多。代价是第一次调用慢一拍，以及两个表给攻击者留下了「劫持 GOT 条目」的著名攻击面——安全专题会回来。</span>

**辨析｜易错点：** 「动态链接的程序是不是运行时必须有那个 `.so`？」——是的。把可执行文件拷到别的机器而忘了 `.so`，就会得到经典的 `error while loading shared libraries`。静态链接以体积换独立，动态链接以独立换体积，没有免费午餐。

## 6 加载：execve 与进程的诞生

链接器交出可执行文件后，**加载器（loader）**接管：`execve` 系统调用把程序读进内存，建立新的进程地址空间——正文段、数据段、栈、堆各就各位，然后把控制交给入口点 `_start`。<span class="marginnote">加载并不是「整个文件塞进内存」，而是按程序头表<strong>按需映射</strong>：代码段映射为只读可执行，数据段映射为可读写，未用到的部分等到真正访问才调入——这正是第九章《虚拟内存》与按需调页的舞台。链接器的输出，是虚拟内存的第一份客户名单。</span>

**重点：** 链接与加载的边界：链接器处理的是「文件之间的符号」，加载器处理的是「文件到内存的映射」。前者在编译后、运行前完成；后者发生在进程诞生的瞬间。本章标题里的「加载」，就是从链接器交棒到加载器的那一步。

## 7 小结

- 链接器做两件事：**符号解析**（引用 → 定义）与**重定位**（符号 → 地址）。
- ELF 有三种形态：可重定位 `.o`、可执行、共享库 `.so`；节（section）是编译期概念，段（segment）是运行期概念。
- 符号有强/弱之分；强强冲突报错，一强多弱取强，多弱任选——**全局变量的定义只能写在一个 `.c` 里**。
- PC 相对重定位让代码与加载地址无关（PIC），这是动态库与 ASLR 共存的机制基础。
- 静态链接以体积换自包含，动态链接用 PLT/GOT 以运行时解析换体积。
- 加载器把可执行文件映射成进程，链接与加载由此交棒——下一章《异常控制流》将解释进程如何被创建与控制。

在下一节，我们进入操作系统的地盘——**异常控制流**：中断、陷阱、故障与终止，以及建立在它们之上的进程、信号与上下文切换。链接为我们准备好了进程的「皮」，异常控制流则给它装上了「心脏」。
