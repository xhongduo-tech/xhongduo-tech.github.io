## 为什么从处理器体系结构开始

上一章我们看到一条条汇编指令的语义；这一章要回答一个更硬的问题：**这些指令在物理上是怎么被「执行」的？** 答案的骨架是一条流水线（pipeline），而流水线的生命线是「不断处理冒险」——这条主线会一直延续到下一章的性能优化。<span class="marginnote">CS:APP 用一个自研的教学指令集 Y86-64 来解剖处理器——它足够简单、又足够真实：有取指、译码、执行、访存、写回五级，也有转发与分支预测。看懂 Y86-64，就看懂了真实 CPU 的骨架。</span>

学完本章，你会理解三个相互纠缠的问题：为什么「指令的顺序执行」注定慢；为什么把执行拆成流水线就能快 $k$ 倍；又为什么冒险（hazard）会把这份「快」打回原形。本章在知识树上与《计算机组成原理》《计算机体系结构》专题衔接，也为《优化程序性能》提供理论的根。

## 1 指令集与微体系结构：把「做什么」与「怎么做」分开

**指令集体系结构（ISA）**定义的是「对程序员可见的约定」：有哪些指令、寄存器、内存寻址方式，是 C 编译器面向的契约；**微体系结构（microarchitecture）**则是 ISA 之下的具体实现：用几条流水线级、几个 ALU、几级缓存去兑现这份契约。<span class="marginnote">ISA 是接口，微体系结构是实现。同一个 x86-64 ISA，Intel 与 AMD 的实现完全不同，性能天差地别，但都跑同一份编译产物——这是计算机系统「接口与实现分离」的教科书级例子。</span>

CS:APP 的教学 CPU 是 **Y86-64**：一个极简的 x86-64 变体，只有几种整数指令（`rrmovq`、`irmovq`、`addq`、`call`、`ret`、条件跳转等），字长 64 位。它足够小，可以把「顺序实现（SEQ）」与「流水线实现（PIPE）」两种硬件设计都完整画出来。

**硬件设计语言 HCL**：CS:APP 用 HCL（Hardware Control Language）描述处理器各部件之间的信号流动——它的核心是**组合逻辑**（现在算出来）与**时序单元**（下一周期才生效）的区分。<span class="marginnote">这个区分是所有硬件正确性的关键：寄存器在时钟上升沿才采样新值，因此同一周期内可以放心地让信号「乱窜」而不会互相覆盖——顺序读（先读旧值）后写（再写新值）由时钟节拍保证。</span>

## 2 顺序实现 SEQ：正确但慢

顺序实现（SEQ）在一个时钟周期里让指令依次经历**取指（IF）→ 译码（ID）→ 执行（EX）→ 访存（MEM）→ 写回（WB）**五个阶段，然后进入下一条指令。<span class="marginnote">取指从内存取指令字节并解码出操作数；译码读寄存器；执行做算术或计算地址；访存读写内存数据；写回把结果写回寄存器。一条指令的周期 = 五阶段耗时之和。</span>

顺序实现是「语义正确」的黄金标准：每条指令严格按程序次序完成，永远没有冒险——因为根本没有并发。但它的代价一目了然：**整个周期的长度由最慢的阶段决定，而一个周期只完成一条指令**。假如 EX 需要 300ps、访存需要 250ps、其余每级 100ps，则一条指令要 850ps，吞吐就是每 850ps 一条。

**重点：** 顺序实现的教训是——把「一次只做一件事」换成本质上「五件事同时在五条指令上做」，是提速的钥匙。但这把钥匙会打开潘多拉盒子：冒险。

五个阶段各自做什么，一句话一张表：

| 阶段 | 缩写 | 做的事 |
| --- | --- | --- |
| 取指 | IF | 从内存读指令字节，拆出操作码与操作数说明 |
| 译码 | ID | 读寄存器文件，准备立即数与操作数 |
| 执行 | EX | ALU 做算术或算有效地址，更新条件码 |
| 访存 | MEM | 读写数据内存 |
| 写回 | WB | 把结果写回寄存器文件 |

## 3 流水线 PIPE：吞吐优先

流水线把五个阶段拆开，让指令像工厂流水线一样前后脚流动：第 1 拍 I1 在 IF，第 2 拍 I1 在 ID 而 I2 进入 IF，第 3 拍 I1 在 EX、I2 在 ID、I3 在 IF……<span class="marginnote">流水线不缩短单条指令的延迟（latency），它缩短的是相邻两条指令的间隔——吞吐（throughput）。就像洗衣服：单件衣物要 30 分钟（延迟），但流水线上每 10 分钟就洗完一件（吞吐）。</span>

下图是四条例入流水线的时序：红框标出 I1 与 I2 之间的数据冒险，红线是转发路径。

![五级流水线时序：数据冒险与转发](/images/computer-systems-integrated/processor-architecture-pipeline.svg)

**重点：** 流水线的周期由最慢一级决定：$T_{clk} = \max_i t_i$。只要把最慢阶段再拆细（比如把访存拆成两段），周期就能继续缩短——这是「让常见情况快」原则的第一次落地。理想情况下 $k$ 级流水线让吞吐提升约 $k$ 倍，但它带来了三类**冒险（hazard）**，让实际吞吐永远够不到理想值。

把抽象数字落到具体，设五级延迟分别为 IF=100ps、ID=120ps、EX=150ps、MEM=200ps、WB=100ps：

- 顺序实现：一条指令 $T_{seq} = 670$ps，吞吐 1/670ps；
- 流水线实现：$T_{pipe} = 200$ps + 锁存器约 20ps ≈ 220ps，吞吐 ≈ 1/220ps——快了约 3 倍；
- 把最慢的 MEM 拆成两段（各 100ps），$T_{pipe}$ 降到 150 + 20 = 170ps，又快了约 30%。

顺序实现与流水线实现的对账：

| 维度 | 顺序实现 SEQ | 流水线实现 PIPE |
| --- | --- | --- |
| 一周期完成 | 一条指令 | 一条指令的一个阶段 |
| 周期长度 | 五级延迟之和 | 最慢一级 + 锁存器 |
| 冒险 | 无 | 有（数据/控制/结构） |
| 理想吞吐 | 每周期 0.2 条 | 每周期 1 条 |

## 4 冒险：数据、控制、结构

**结构冒险（structural hazard）**：两个阶段要同时用同一份硬件。比如取指要读指令内存、访存要读写数据内存——若两者共用一块内存，IF 与 MEM 就会打架。解决：指令内存与数据内存分开（哈佛式）或用缓存分开。<span class="marginnote">在真实 CPU 里，L1 指令缓存与 L1 数据缓存分离正是为了消除结构冒险——这也是为什么《存储器层次结构》一章里「统一缓存」会成为特例。</span>

**数据冒险（data hazard）**：下一条指令要用上一条指令还没写回的结果。看图：I1 `addq %rax,%rbx` 在 t3 的 EX 才算出结果，I2 `subq %rbx,%rcx` 在 t4 的 EX 就要读 `%rbx`——按顺序执行本该「等 I1 写完」——结果晚了一个节拍。

**控制冒险（control hazard）**：遇到 `jmp`、`call`、条件跳转时，处理器在取指阶段并不知道该取哪条指令，只能猜。猜错了，已经取进来的几条指令全部作废（冲刷 pipeline），白费几个周期。

**辨析｜易错点：** 三类冒险的「受害者」不同：结构冒险浪费的是硬件空闲，数据冒险浪费的是数据就绪前的等待，控制冒险浪费的是「猜错」的惩罚。三者的共同解药都指向同一件事——**尽量不让流水线停**。

## 5 转发与分支预测：让流水线不停

**转发（forwarding）**是数据冒险的主要解药：I1 的 EX 结果虽然要等 t5 才写回寄存器文件，但结果在 t3 末就已算好——硬件加一条「旁路」，把 EX 的输出直接送到下一条指令的 EX 输入，于是 I2 在 t4 就能拿到 `%rbx`，流水线照常流动。<span class="marginnote">转发的本质是把「等数据写回再读」改成「结果一算出来就用」。它是硬件里最划算的投资：几条连线 + 一点比较逻辑，换来流水线近乎无损。</span>

但有转发也覆盖不到的情形：**加载-使用（load-use）冒险**。`movq (%rax),%rbx` 的结果要等访存（MEM）结束才有，而紧接着的 `addq %rbx,%rcx` 在下一拍就要用——此时必须**停顿（stall）**一拍，插入气泡。<span class="marginnote">转发只能从「已经算出来」的地方取数据，而加载的值在访存结束前根本不存在——「不能转发还没发生的事」。load-use 停顿因此是流水线里最经典、也最贵的一拍。</span>

**分支预测（branch prediction）**对付控制冒险：处理器用历史记录猜测跳转是否发生、往哪跳。猜对了零成本，猜错了要冲刷流水线并重新取指，代价等于流水线深度。<span class="marginnote">「让常见情况快」在这里变成「让经常发生的跳转被猜中」。现代 CPU 的分支预测器命中率普遍超过 95%，是你能跑得飞快而几乎不察觉的隐形引擎。</span>

**重点：** 预测错误的惩罚正是下一章《优化程序性能》里「让循环体尽量简短、避免分支交织」的硬件根源——程序员改一行 `if`，硬件里可能就是一次冲刷新旧预算的重新分配。

流水线里还藏着一个哲学问题：**异常该由谁处理**？一条指令在 t1 已算出结果、t5 才写回，若它随后引发缺页，后面的指令可能已经污染了寄存器。Y86-64 的约定是：**流水线阶段结束时才处理异常，异常由「最靠近写回端的那条指令」负责**——排在前面的指令被冲刷掉，寄存器只写回正常结果。这保证异常处理的顺序与程序语义一致，是「接口正确性」在硬件里的体现。

把预测错误的代价换算成数字：五级流水线猜错一次，大约赔 5 个周期。这就是为什么越深的流水线越依赖预测器——现代 CPU 用两级自适应预测器把命中率提到 95% 以上，把「赔 5 个周期」的发生概率压到不足 5%。

## 6 公式解析：流水线周期与理想加速比

设一条指令在顺序实现里要经历 $k$ 级，各级延迟为 $t_1, t_2, \dots, t_k$，流水线寄存器（两级之间的锁存器）延迟为 $d$。则：

$$
T_{seq} = \sum_{i=1}^{k} t_i, \qquad
T_{pipe} = \max_{1 \le i \le k} t_i + d, \qquad
S = \frac{T_{seq}}{T_{pipe}}
$$

分四步拆解：

- **第一步，顺序实现的延迟**：$T_{seq}$ 是各级延迟的**和**——一条指令完整走完的时间，也就是 SEQ 的周期。
- **第二步，流水线的周期**：$T_{pipe}$ 是各级延迟的**最大值**加上锁存器开销 $d$。慢的一级决定整条线的节拍，$d$ 是拆分带来的固定税。
- **第三步，理想加速比**：$S$ 是两者之比。若各级均匀，$S \approx k$——$k$ 级流水线理想提速 $k$ 倍。这正是「吞吐优先」的量化表达。
- **第四步，为什么达不到 $k$ 倍**：三级原因——最慢一级拖后腿（均衡问题）、$d$ 是不可消除的开销、以及冒险造成的停顿与冲刷。于是实际吞吐 = 理想吞吐 ×（1 − 冒险损失率），而减少损失率正是转发、预测、乱序执行的全部意义。

## 7 小结

- **ISA 是接口，微体系结构是实现**；Y86-64 把两者拆开讲透。
- 顺序实现正确但慢：周期 = 五阶段之和，一周期一条指令。
- 流水线以吞吐换延迟：周期 = 最慢一级 + 锁存器开销，理想提速 $k$ 倍。
- 三类冒险：**结构**（硬件争用）、**数据**（结果未就绪）、**控制**（取指猜错）。
- 转发消除大部分数据冒险；load-use 必须停顿；分支预测靠「猜」来避免冲刷。
- 常见情形优先（make the common case fast）是这一切设计的总原则。
