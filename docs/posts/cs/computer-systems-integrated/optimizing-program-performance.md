## 为什么从优化程序性能开始

前两章我们看了汇编，又看了流水线。这一章要把这两样换算成**性能**：同样的循环，为什么编译器换个优化级别就能快五倍？为什么我手写的「优化」反而更慢？答案藏在一条主线上——**程序的行为由「数据流」决定，而速度由「数据依赖的链条」与「硬件的执行单元数」共同决定**。<span class="marginnote">Knuth 这句话常被误解为「别优化」。它真正的意思是：不要在一开始就为了省几个周期牺牲清晰；但当性能是硬需求时，理解优化的机制就是职业素养，而不是炫技。</span>

本章既承接上一章的流水线与转发，也提前用上第六章《存储器层次结构》里的结论——性能优化的两大敌人，一个是**数据依赖链**，一个是**内存访问**。本专题之外的《数据结构》与《编译原理》专题，也会在这里找到它们的「为什么」。

## 1 编译器优化的边界：语义必须不变

首先要认清现实：**编译器绝不会为了快而改变程序的可观察行为**。它所有的优化都必须满足一个前提——优化前后的程序，对任何合法输入产生完全相同的可观察结果。<span class="marginnote">这里的「可观察行为」含金量很高：浮点运算的顺序改变会改变舍入，所以编译器默认不重排浮点表达式；函数调用可能有副作用，所以编译器通常不跨调用移动代码。开发者常常骂编译器「太保守」，其实是在骂它「守规矩」。</span>

最常用的优化级别是 **GCC 的 `-O2`**：它开启循环展开、内联、寄存器分配等大量转换，是大多数项目的默认选择。`-O0` 不做任何优化——调试时逐行对应源代码；`-O3` 更进一步，但可能引入更激进的假设（比如「无符号加法不溢出」），从而删掉程序员写的溢出检查。<span class="marginnote">一个血淋淋的案例：`for (i = 0; i < n; i++) v = v + a[i];` 这类累加，`-O3` 可以把它向量化——用 SIMD 一次算四个数。但前提是编译器能证明循环次数、别名关系都没问题。证明不了，它就老实排队算。</span>

**重点：** 所以优化的第一课不是「教编译器」，而是「理解它为什么不能」。剩下的功课，是要认出哪些优化编译器不会替你做的、只能由程序员的双手完成的转换。

GCC 的优化级别速查：

| 级别 | 开启的优化 | 典型用途 |
| --- | --- | --- |
| `-O0` | 无 | 调试：汇编与源码逐行对应 |
| `-O1` | 基础局部优化 | 快速编译、可读性尚可 |
| `-O2` | 保守的完整优化 + 内联 + 循环变换 | 大多数项目的默认档 |
| `-O3` | `-O2` 全部 + 向量化等激进变换 | 数值计算、热循环 |
| `-Os` | 以体积为目标的优化 | 嵌入式、体积敏感场景 |

## 2 程序不变量：循环外提、强度削减、无效代码消除

编译器最擅长的三类变换，都是同一个思想——**把每轮重复的工作挪到只需要做一次的地方**：

**循环外提（loop hoisting）**：把循环体内与迭代无关的表达式搬到循环外。`for (...) { y += 2 * i; }` 里的 `2*i` 依赖 `i`，但像 `4 * sizeof(int)` 这种常量表达式，编译器会算一次存下来。<span class="marginnote">程序员版的外提是「把 strlen(s) 存进循环前变量」——这是每个 C 程序员的入门优化，而编译器对纯常量才会替你做，因为它无法证明 strlen 没副作用。</span>

**强度削减（strength reduction）**：把「贵」的运算换成「便宜」的。用移位代替乘 2 的幂、用增量代替乘法：`for (i = 0; i < n; i++) { p = i * 4; ... }` 被编译成每轮 `p += 4`。**寻址的乘法在硬件里就是一次 `lea`**——这正是第三章讲 `lea` 时的伏笔。<span class="marginnote">强度削减在硬件层面还有一个更激进的版本：编译器把循环变量改写成「乘法变加法」的归纳变量，省下每轮一次的乘法。它说明汇编里看到的 `lea`、`add`，常常已经是编译器优化过一轮的结果——读汇编时要带着「它可能不是源代码的直译」的警惕。</span>

强度削减也有翻车的一面：把 `x / 8` 改成 `x >> 3` 只在「x 非负且整除」时严格等价——负数算术右移向负无穷取整，而 C 的整数除法向零取整。编译器只在能证明非负时才敢做这个替换，这正是第一章「右移不等于整除」在优化器里的再次印证。

**无效代码消除（dead code elimination）**：把结果永远不会被使用的赋值删掉。这是优化器对「写了不用」的惩罚，也是为什么 `-O2` 下未使用的全局变量看起来「凭空消失」了。

## 3 循环展开与指令级并行

现在进入本章的深水区。假设我们在累加一个数组的元素：`for (i = 0; i < n; i++) sum += a[i];`。每条 `add` 之间隔着一条数据依赖：`sum` 的新值要等旧值。**这条依赖链决定了程序的延迟界**——你没法快过「链上每条运算的延迟之和」。

**循环展开（loop unrolling）**有两条腿：一是**每轮多处理几个元素**，减少循环控制（比较、跳转）的开销；二是**使用多个独立累加变量**，把一条依赖链拆成几条并行的链。比如把 `sum` 拆成 `sum0` 与 `sum1` 两个累加器，一轮处理两个元素，最后再合并：<span class="marginnote">拆累加器利用了硬件的多执行单元：现代 CPU 有 3–4 个整数 ALU，可以同时执行互不依赖的加法。依赖链只有一条时，多余的执行单元全在空转——拆分累加器就是把它们唤醒。</span>

```c
for (i = 0; i + 1 < n; i += 2) {   /* 一轮两个元素 */
    sum0 += a[i];
    sum1 += a[i + 1];
}
sum = sum0 + sum1;
```

**辨析｜易错点：** 展开必须与「尾元素处理」配合。当 `n` 是奇数时，循环退出后还剩一个元素没算——所以要么保证 `n` 为偶数，要么循环后补一段 `while (i < n) sum += a[i++]`。忘记收尾的展开，是 90% 的「我展开后结果就错了」事故的来源。<span class="marginnote">顺便说：`i + 1 < n` 里的 `i + 1` 可能被编译器做掉，但 `sum0 + sum1` 的最终合并引入了一次加法延迟——比起展开省下的，微不足道。</span>

展开到什么程度合适？经验上 2–4 次即可：展开 2 次省掉一半循环控制开销，展开 4 次再省一半但收益递减——因为控制开销占比越来越小，而代码体积与寄存器压力越来越大。展开 8 次以上常常开始变慢，寄存器溢出把省下的周期又还了回去。

## 4 限制性因素：内存别名与过程调用

两类障碍让上面的技巧失灵，而且都很隐蔽：

**内存别名（memory aliasing）**：当两个指针可能指向同一块内存时，编译器不敢重新排列读写顺序。经典的受害者是：

```c
void add(long *dst, long *src, long n) {
    for (i = 0; i < n; i++) dst[i] += src[i];
}
```

若 `dst` 与 `src` 重叠（比如 `src = dst + 1`），一次读会影响下一次读的结果——编译器无法证明它们不重叠，于是**每一轮都严格按顺序读写**，循环展开的收益全被别名假设吃光。<span class="marginnote">C 里承诺不重叠的关键字是 `restrict`：`long *restrict dst` 告诉编译器「我保证没有别名」，它才敢大胆重排。系统程序员对性能敏感的函数，常常就是差这一个修饰符。想了解 C 语言自身的这类语义陷阱，可参照《编程语言》与《编译原理》专题。</span>

**过程调用（procedure calls）**：编译器不知道被调函数内部做了什么，通常不会把它内联到循环里——每轮一次调用，寄存器保存、栈帧分配全是开销。解决：**内联（inlining）**。要么手动把函数体写进循环，要么用 `static inline` 让编译器替你展开。<span class="marginnote">`inline` 是「建议」而非「命令」，真正的决定权在编译器的成本模型。但它的存在，把「函数调用是否有开销」这个问题从程序员的心里搬到了编译器的桌上。</span>

## 5 性能剖析：先测量，再优化

Knuth 那句话的正面翻译是：**优化之前先测量**。否则你很可能在「90% 时间根本没被跑到」的代码上挥霍。

**剖析（profiling）**靠的是上一章讲的硬件设施：周期计数器（如 x86 的 `rdtsc`）与性能计数器（PMU），配合 `gprof`、`perf` 这样的工具，告诉你每个函数、每行代码花了多少时间。<span class="marginnote">`perf` 之所以能给出硬件级数据（缓存未命中率、分支预测失败率），是因为现代 CPU 内置了一组可编程的性能计数器——这又是「硬件为软件服务」的一个实例。</span>

**辨析｜易错点：** 用「猜」代替测量是性能工程的头号错误。你以为的瓶颈（某段循环）往往不是真正的瓶颈；真正的瓶颈常常是缓存未命中——这恰恰是下一章《存储器层次结构》的主角。**性能优化的正确顺序永远是：测量 → 假设 → 验证 → 再测。**

## 6 公式解析：延迟界与吞吐界的 CPE 模型

CS:APP 用 **CPE（Cycles Per Element）** 来量化循环性能：处理一个数组元素的平均周期数。设一段内循环体执行 $n$ 个元素共用 $T$ 个周期，则：

$$
CPE \approx \frac{T}{n}, \qquad
T(n) = n \cdot CPE + K
$$

其中 $K$ 是与元素个数无关的开销（循环控制、结尾处理）。分四步拆解：

- **第一步，定义 CPE**：它剔除掉「与 $n$ 无关」的固定开销，只保留「每个元素分摊多少周期」，是公平比较不同实现的核心指标。
- **第二步，读线性模型**：$T(n) = n \cdot CPE + K$ 表明时间是元素数的线性函数，CPE 是斜率，$K$ 是截距。画成图，谁更陡谁更慢。
- **第三步，两个物理界**：**延迟界**——由数据依赖链决定，每条运算的延迟（如整数加法 ~1 周期）是链上每一环的下限；**吞吐界**——由执行单元数量决定，比如只有 3 个加法器，每周期至多发起 3 次加法。实际 CPE 至少是两者的较大者。<span class="marginnote">把这两个界念在嘴里：延迟界惩罚「串行依赖」，吞吐界惩罚「依赖太少、并行度不够」。循环展开 + 多累加器，正是同时打击两界——缩短链长、喂饱执行单元。</span>
- **第四步，行动清单**：先确认瓶颈是哪一界——用独立累加器把链拆短（打延迟界）、用更多并行变量让执行单元忙起来（打吞吐界）、用 `restrict` 解除别名（解编译器的束缚），然后用 `perf` 验证每一步。

套一个具体数字感受两界的差别：整数加法延迟约 1 周期，整数除法约 20 周期。若一段循环里每个元素做一次整数除法，CPE 至少是 20（延迟界）；把除法改成查表或「乘倒数」的乘法加移位，CPE 可能降到 1 左右——一次改动快 20 倍，正是「瓶颈在哪一界」的威力。

## 7 小结

- 编译器优化必须**保持可观察语义不变**；`-O2` 是默认档位，`-O3` 更激进也可能更「傲慢」。
- 程序不变量优化：**循环外提、强度削减、无效代码消除**——能做的编译器都做了，别自己重写。
- **循环展开**与**多个累加器**是程序员的两把武器：一个砍循环控制开销，一个把依赖链拆成并行链。
- 两大障碍：**内存别名**（用 `restrict` 解开）与**过程调用**（用内联消除）。
- 性能工作必须**先测量后优化**：CPE 是斜率，延迟界与吞吐界是两个物理极限。
- 硬件级剖析（`perf`/PMU）能直达缓存未命中与分支预测失败——它们把我们引向下一章。
