## 为什么从并发编程开始

单核 CPU 的主频爬了十几年，终于在 2005 年前后撞上功耗墙——从那以后，「更快」不再来自时钟频率，而是来自**更多核**。萨特说「免费午餐结束」，意思是：想让程序变快，程序员必须亲手把工作拆成可以并行执行的份。这一章就是给那顿「不免费的午餐」买单的入门课。<span class="marginnote">上一章 echo 服务器「一次只服务一个客户端」的瓶颈、多核 CPU 的空转、大模型训练时的分布式数据并行——它们指向同一门手艺：<strong>并发</strong>。学会控制并发，是系统程序员与只会写顺序代码的程序员的分界线。</span>

本章承接《异常控制流》的进程与《系统级 I/O》的 socket：进程是并发的第一种形态，线程是更轻量、更适合并行的第二种形态。它与《操作系统》专题的分工是：本章站在「程序员写代码」的一侧，系统专题站在「内核如何调度」的一侧。

## 1 线程：同一进程内的并发

**线程（thread）**是「一个进程内的多条执行流」。多个线程**共享同一份虚拟地址空间**（所以访问全局变量零成本），同时各自拥有**独立的栈**与寄存器上下文。<span class="marginnote">线程与进程的核心差别就在「共享」：进程之间地址空间彼此隔离，线程之间共享一切——共享意味着高效，也意味着「我的变量被它改了」的噩梦。这也是为什么并发 bug 几乎都长在共享变量上。</span>

线程的控制函数（POSIX）：`pthread_create` 创建、`pthread_join` 等待、`pthread_exit` 退出。创建线程时传入一个「线程例程」，它在线程自己的控制流里运行：

```c
pthread_t tid;
pthread_create(&tid, NULL, thread_routine, arg);  /* 开一条新控制流 */
pthread_join(tid, NULL);                          /* 等它结束 */
```

**重点：** 线程调度是**非确定**的——两个线程谁先跑、一次跑多久，由内核决定，程序员无法预知。这不是设计缺陷，而是「共享 CPU」的必然代价：**只要两个线程可能同时执行，你的代码就必须假设它们会同时执行**。这条假设，是后面所有同步工具存在的理由。

## 2 共享变量与竞态

**共享变量（shared variable）**是「多个线程都能访问的全局或堆变量」。当两个线程**同时读写同一个共享变量**，而读写顺序又影响结果时，就产生了**竞态（race condition）**——结果取决于「谁恰好先到」，往往不可复现。<span class="marginnote">经典事故：两个线程各自执行 `counter++`。这句 C 代码在机器层是三条指令——读 `counter`、加 1、写回。两个线程交错执行时，可能出现「两次都读同一个旧值、两次都写同一个新值」，于是两次自增只生效一次。硬件乱序与缓存让这种交错更加随机。</span>

**辨析｜易错点：** 竞态 bug 最大的杀伤力在于**不可复现**——在单核调试器里跑一万次都没事，上多核生产环境就偶发崩溃。所以并发调试的第一原则不是「跑一跑看看」，而是**代码审查时就去寻找每个共享变量的每次访问，问一句：这一步是不是原子操作？** 不是，就需要加锁。<span class="marginnote">「原子（atomic）」指「不可被中途打断」：对程序员来说，一条 C 语句几乎都不是原子的——`counter++` 是三步，`x += y` 也是三步。只有少数「读-改写」类指令在硬件上才可能有原子版本。判断原子性，是并发编程的核心直觉。</span>

## 3 互斥锁：把临界区圈起来

**互斥锁（mutex，mutual exclusion）**是最基本的同步工具：它保证**同一时刻只有一个线程能进入被它保护的代码区**（临界区，critical section）。

```c
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
pthread_mutex_lock(&m);      /* 若已被占用，则阻塞等待 */
/* 临界区：对共享变量的操作 */
pthread_mutex_unlock(&m);    /* 释放，唤醒等待者 */
```

**重点：** 锁的正确使用是「圈住**所有**对该共享变量的访问」。漏锁一处，锁就形同虚设——这就是并发 bug 常常「加锁了还是坏」的原因：不是锁坏了，是没锁全。<span class="marginnote">锁的粒度是权衡的艺术：锁得太大（整个函数加锁）会串行化所有线程，性能回到单线程；锁得太小（只锁一条语句）又防不住更长的临界区交错。生产代码里「锁多大」之争，本质是「正确性与并行度」之争。</span>

## 4 信号量：一个计数器的三种用法

**信号量（semaphore）**由迪杰斯特拉在 1965 年提出，是一个带非负整数的对象，只允许两个操作：

**P（wait）**：若计数器 > 0 则减 1；否则阻塞等待。
- **V（signal）**：计数器加 1，并唤醒一个等待者。<span class="marginnote">P 来自荷兰语「proberen」（试探），V 来自「verhogen」（增加）——迪杰斯特拉是荷兰人，这两个字母的典故至今活在每本操作系统教材里。信号量的优雅在于：<strong>一个计数器，就能模拟锁、限制并发数、并调度生产者与消费者</strong>。</span>

把计数器初始化为 1，信号量就是一把**互斥锁**（二值信号量）；初始化为 N，它限制「最多 N 个线程同时进入临界区」；把它当作「可用资源计数」，它就能协调**生产者-消费者**：缓冲区有空格时生产者才能放，有数据时消费者才能取。

**辨析｜易错点：** P 与 V 的调用顺序错了会**死锁**——比如消费者先对「空格」做 P、再对「数据」做 P，而生产者恰好相反，双方就可能互相等待对方释放的资源。死锁的四个必要条件（互斥、持有并等待、不可抢占、循环等待）是《操作系统》专题的系统话题，但「两个信号量的顺序必须全局一致」这条经验法则，现在就该背下来。

## 5 生产者-消费者：并发协调的教科书

**生产者-消费者（producer-consumer）**是并发里最重要的协同模式：生产者线程往缓冲区放，消费者线程从缓冲区取。它们共享一个固定大小的缓冲区，于是需要三个信号量：

$$
\text{mutex} = 1, \quad \text{slots} = n, \quad \text{items} = 0
$$

生产者每次放之前 `P(slots)`（占一个空位），放之后 `V(items)`（多一件货）；消费者恰好相反。而 `mutex` 把「读写缓冲区」这个临界区锁起来。<span class="marginnote">这个模式几乎可以原样翻译成 Web 服务器：主线程 accept 连接后，把描述符放进任务队列（生产者），一组工作线程从队列取任务处理（消费者）——「线程池」的全部思想就是它。</span>

**重点：** 信号量方案天然**安全**（不会出现两个线程同时改缓冲区）也天然**有界**（`slots` 与 `items` 之和永远 ≤ n，见第 7 节公式解析）。它比「忙等轮询」强在：消费者没货时**睡**在 `P(items)` 上，不烧 CPU——这正是上一章上下文切换与调度机制的意义所在。

## 6 线程安全、可重入与并发服务器

把并发知识拼回上一章的 echo 服务器：给 `accept` 后的每个连接开一个线程，就得到一个**并发服务器**——主线程只负责接客，工作线程各管一个客户端。<span class="marginnote">并发服务器的几种流派：进程派（fork，隔离强但重）、线程派（pthread，轻但共享易错）、事件派（I/O 多路复用 `select`/`epoll`，单线程高并发）——三者对应《并发并行程序设计》专题的不同章节，这里只立下「多份控制流各自服务一个连接」的心法。</span>

**线程安全（thread safety）**指「函数对并发调用安全」。判断一个函数是否线程安全，看它是否满足：不访问共享可变状态，或访问时全程加锁。**可重入（reentrant）**是更强也更难的属性——它只依赖参数与局部变量，连锁都不需要，因为可重入函数根本不动共享状态。<span class="marginnote">两者的关系：可重入 ⇒ 线程安全，但反之不然。`rand` 线程不安全（改了全局种子），`strtok` 线程不安全（用了静态缓冲）——这正是 `rand_r`、`strtok_r` 这些 `_r` 后缀函数存在的理由：把共享状态移进调用方提供的参数。</span>

**辨析｜易错点：** 线程安全与「加锁」不是一回事。加锁的函数是「线程安全」，但它仍然可能不可重入（比如锁内又调用了同一个会加锁的函数 → 死锁）。**可重入函数才是并发世界的纯净水**——设计库接口时优先做可重入，是系统编程的长期主义。

## 7 公式解析：信号量方案的不变式

生产者-消费者三个信号量的关系，可以写成一条始终成立的不变式：

$$
0 \le \text{slots} + \text{items} \le n
$$

分四步拆解：

- **第一步，slots 与 items 之和**：缓冲区里「空位」与「货物」加起来，永远等于缓冲区总大小 $n$——一件货被放进来，就从 slots 挪到 items；被取走，就从 items 挪回 slots。
- **第二步，为什么永不越界**：生产者放之前必须 `P(slots)`（保证 slots ≥ 1），消费者取之前必须 `P(items)`（保证 items ≥ 1）。信号量 P 的语义（为 0 则阻塞）天然压住了两端。
- **第三步，为什么不会互踩**：`mutex` 把「读写缓冲区」变成临界区，两个线程不可能同时修改同一个槽位。
- **第四步，这条不变式意味着什么**：它是一次性的「正确性证明」——只要方案满足不变式，就不会越界、不会空取、不会互踩。**用不变式证明并发正确性**，比跑一万次测试可靠得多；这是迪杰斯特拉留给我们的、对付非确定性的唯一武器。

## 8 小结

- **线程**是共享地址空间内的多条执行流；调度非确定，代码必须假设「会同时执行」。
- **共享变量**上的交错访问产生**竞态**——一条 C 语句往往不是原子的，这是 bug 的温床。
- **互斥锁**圈住临界区；漏锁一处等于没锁，锁的粒度是并行度与安全性的权衡。
- **信号量**是迪杰斯特拉的统一工具：一个计数器 + P/V 两个操作，能模拟锁、限流、协调生产者与消费者。
- **生产者-消费者**模式是线程池与并发服务器的心法；`slots + items = n` 的不变式保证正确性。
- **可重入**是最强的线程安全属性；设计共享状态尽量移进参数，库接口优先做可重入。
- 并发服务器 = accept 主线程 + 每连接一个工作线程，把 I/O 与并发两章真正焊在一起。
