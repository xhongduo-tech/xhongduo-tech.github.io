## 为什么从测量开始

上一篇定下了「测什么」（指标），这一篇回答「**怎么测**」。机器不会主动把性能报告递到你手上，需要一套工具链去窥探它。而窥探本身会扰动被窥探的对象——加探针改代码、采样占 CPU、记录日志占磁盘，**测量动作本身就是一种负载**。这是测量技术的第一性约束，也是本篇反复出现的主题。<span class="marginnote">观察者效应在性能测量里不是哲学问题，而是工程问题：一个每秒记一次日志的 profiler，可能让被测服务的延迟升高几个百分点。设计的核心就是让扰动尽量小、结果尽量可信。</span>

测量工具按原理分三大类：**计数器（counters）、剖析器（profilers）、追踪器（tracers）**。它们回答不同的问题、侵入程度不同、适用场景也截然不同。

## 1 测量的层级

性能数据可以来自不同层级，层级越深，越接近硬件真相，也越难使用：

**硬件层**：CPU 内置的性能计数器直接统计缓存命中率、分支预测、CPI（每指令周期数）等微架构事件，精度最高、开销几乎为零。<span class="marginnote">CPI 与缓存命中率这类硬件指标，正是《计算机组成原理》里流水线与存储层次两章的量化接口；两者在此汇合。</span>

**操作系统层**：`vmstat`、`top`、`iostat` 等工具报告 CPU 利用率、内存换页、磁盘队列、网络丢包——宏观、易得，但粒度粗。

**应用层**：在应用代码里埋点，记录某次事务的耗时、某个接口的调用次数，直接对准业务指标，但需要改代码。

测量的**目标**也决定手段。Jain 把测量目标分为四类：比较两个系统、理解系统行为、调优某个参数、预测未来负载下的表现。目标不同，测量方法、负载选取、统计处理全都不同——**动手前先用一句话写清目标**，否则很容易测出一堆正确而无用的数字。

**辨析｜易错点：** 新手常拿着操作系统层的数据去解释应用层的问题。CPU 空闲 90% 却响应很慢？瓶颈可能在锁等待、I/O 或网络——**先确认数据的层级与问题的层级一致**，再开始调优。

## 2 计数器：最便宜的真相

**计数器（counter）**：由硬件或操作系统维护的累加数值，记录某个事件发生了多少次，如「缓存未命中次数」「网卡收到的包数」。读取计数器不改变系统行为，是扰动最小的测量方式。

现代 CPU 提供一组**性能计数器（hardware performance counters）**，配合 `perf`、`vtune` 等工具，可以回答「这段代码的缓存未命中率是多少」。这类指标对理解**算法与微架构的匹配度**至关重要：一个理论上 $O(n \log n)$
