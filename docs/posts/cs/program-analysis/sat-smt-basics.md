## 为什么程序分析需要求解器

前几节的约束系统（第 17 节）用的是专用迭代求解。但有一类更强大、更通用的约束——布尔可满足性（SAT）与一阶理论可满足性（SMT）——需要通用的**求解器（solver）**。符号执行（下一节）把「程序路径」翻译成路径条件，交给 SMT 求解器问「有没有输入能走到这条路径」；验证工具问「有没有反例能违反这条断言」。**求解器是现代程序分析/验证引擎的心脏。**<span class="marginnote">SAT 求解器的性能革命发生在 2000 年代：DPLL 回溯 + 子句学习（CDCL）+ 启发式变量选择，让求解器处理百万变量级实例。这不是理论突破，而是工程突破——所以本节既要讲 DPLL 算法，也要讲工程配方。</span>

**SAT 问题（boolean satisfiability）**：给定布尔公式（合取范式 CNF），判断是否存在使公式为真的变量赋值。**SMT 问题（satisfiability modulo theories）**：给定含特定理论符号（算术、位向量、数组、未解释函数）的一阶公式，判断其在相应理论下是否可满足。

## 1 SAT：从 DPLL 到 CDCL

**SAT 问题**是第一个被证明为 NP 完全的经典问题（Cook-Levin 定理）。求解它的现代算法基线是 **DPLL**（Davis-Putnam-Logemann-Loveland）回溯搜索：

1. **单元传播（unit propagation）**：若某子句只有一个未赋值文字（单元子句），它的文字必须取真——否则子句为假。
2. **纯文字消除**：某文字在所有子句中只以一种极性出现，赋真不损失可满足性。
3. **分裂（splitting）**：无可传播时，选一个变量试赋真/假，递归搜索。

DPLL 是「系统地猜 + 立即传播」：每次分裂沿一棵搜索树走下去，遇到冲突就回溯换一边。

**CDCL（conflict-driven clause learning，冲突驱动子句学习）** 在 DPLL 上加了三个工程引擎：

**冲突分析**：遇到冲突（某子句所有文字都为假），从冲突出发沿蕴含图（implication graph）回溯，找出一组「导致冲突的赋值」，学出一条新子句。**子句学习**：把新子句加入子句集——它编码「这组赋值不能再来」的教训，剪掉整棵等价的搜索子树。**回溯跳跃（backjumping）**：冲突学到的子句决定回溯到「刚好避开冲突」的决策层，而不是只回溯一层。<span class="marginnote">CDCL 的三件套：冲突分析（蕴含图）、子句学习（学教训）、回溯跳跃（跳着退）。再加上 VSIDS 启发式（按冲突频率选变量）、重启（restart，周期性重开搜索但保留学到子句）、惰性删除子句（控制内存）——这些工程配方合起来，把 SAT 求解从「指数级碰运气」变成了「对绝大多数实例多项式级实用」。</span>

**易错点：** SAT 求解器只回答「可满足/不可满足」，不直接给「最优」。要找最优（如最多满足多少子句），要在 SAT 外面再套一层搜索（MaxSAT 或二分）。程序分析里常把「是否存在反例」编码成 SAT——回答存在性就够了。

## 2 SMT：把理论搬进 SAT

**SMT** 把 SAT 从布尔世界推广到一阶理论世界。问题：判定公式在**理论 T** 下是否可满足。例如：

$$
x > 0 \ \land\ y = x + 1 \ \land\ y \le 0
$$

在**线性算术理论（linear arithmetic, LIA/LRA）**下，这个公式不可满足——由 $x > 0$ 与 $y = x+1$ 得 $y > 1$，与 $y \le 0$ 矛盾。

**SMT 的标准架构：DPLL(T)**——把 SAT 求解器与**理论求解器（theory solver）** 嫁接：

1. **抽象**：把原子命题（如 $x > 0$）抽象成布尔变量，交给 SAT 求解器。
2. **找模型**：SAT 给出布尔赋值，理论求解器检查它是否与理论一致（如 $x>0 \land x \le 0$ 冲突）。
3. **学习冲突**：理论不一致时，把矛盾的原因作为**新子句（theory lemma）** 交给 SAT——如「$x > 0 \land x \le 0$ 不同时成立」这条理论引理。
4. **循环**：SAT 带着新引理继续搜索，直到找到一致模型或穷尽。

**理论求解器**每个理论一个：线性算术用 **单纯形法（simplex）** 或差分级联，位向量用位爆破（bit-blasting）转 SAT，数组用等值推理，未解释函数用同余闭包（congruence closure）。<span class="marginnote">SMT 与程序分析最经典的配对：<strong>差分逻辑（difference logic）</strong>——只含 $x - y \le c$ 形式的约束——用图上的最短路（Bellman-Ford）求解，线性时间，是时序验证的主力；<strong>线性算术</strong>用单纯形，是符号执行的主力。选理论 = 选表达力与求解代价的平衡。</span>

## 3 求解器在程序分析中的三个角色

**路径条件求解（符号执行）**：下一节的主角。程序每走一条路径，累积一个路径条件——用 SMT 求解器问「存在满足此条件的输入吗」。可满足 => 路径可达，还能反解出一个具体输入；不可满足 => 路径不可达，剪枝。

**验证的反例生成**：验证工具证明「断言 P 在程序点 q 成立」时，构造「走到 q 且 P 为假」的公式，交 SMT 求解器。可满足 => 找到反例（真实 bug）；不可满足 => 断言被证明。

**依赖与冲突检测**：类型检查、模型检测（第三级《形式化方法》）里，把「状态转换条件」编码成 SAT/SMT，问可达性。<span class="marginnote">这里的求解器用法延续第三级《形式化方法》的模型检测：把「坏状态是否可达」编码成可满足性问题。区别在于：模型检测通常用 BDD/显式状态，程序分析更常用 SMT 做「路径级」的验证。</span>

**易错点：** 求解器是**不可判定的边界**。纯 SAT 可判定（但 NP 完全）；一阶理论的 SMT 部分可判定（如含量词消去的 LIA），部分不可判定（如含非线性算术与量词的组合）。**工程上对不可判定片段用启发式 + 超时**：求解器跑不过超时阈值就报「unknown」——分析器必须把「unknown」当作「无法确定」而不是「不可满足」，否则会得出错误的验证结论。

### 增量求解：程序分析的性能命脉

程序分析调用求解器的模式非常特殊：**一路上要问成百上千个高度相关的问题**——符号执行里每条路径问一次「PC 可满足吗」，前后 PC 只差一个分支条件。每次从头求解是巨大的浪费。**增量求解（incremental solving）** 专门优化这种场景：

**增量加约束（push/pop）**：SMT 求解器支持「在栈上压入一组断言、求解、再弹出」。符号执行沿一条路径时不断 `push` 新的分支条件；探索完回溯时 `pop` 掉。求解器维护学习到的引理，跨 `push/pop` 复用——新路径的约束与已学引理叠加，求解往往瞬间完成。

**增量重求解**：约束集变化不大时，求解器不必重跑 DPLL，而是保留决策栈，从「离冲突最近的位置」继续。

**为什么关键**：符号执行/验证工具里，求解占 90% 时间；增量求解能把总时间降一个数量级。**学习引理的复用，是增量求解的隐藏红利**——CDCL 学到的子句不只对当前公式有用，对「几乎相同」的后续公式同样有效。<span class="marginnote">Z3 等现代求解器的「增量模式」是程序分析工具的标配接口：`solver.push()`、`solver.assert()`、`solver.pop()`。理解「求解器是有状态的、可以复用的」，是写高效分析引擎的重要心法——把求解器当「数据库」而非「一次性计算器」。</span>

### 不可满足核心：当验证失败时给出证据

当 SMT 回答「不可满足」时，程序分析有时需要的不只是「否」，而是**为什么**。**不可满足核心（unsat core）** 是一个**不可满足的约束子集**——一组尽量小的断言，去掉任何一个就可满足。

**用途**：

**反例精简**：验证失败（公式不可满足）时，给出最小冲突集——程序员一眼看到「哪几个条件凑在一起导致了矛盾」，比看到整个公式好调试得多。

**抽象提炼（CEGAR）**：在「抽象-验证-反例-精化」循环（第三级《形式化方法》的 CEGAR）里，不可满足核心告诉分析器「哪条抽象路径是死路」，从而只精化相关部分。

**MaxSAT 与诊断**：找「最少放弃哪些约束才能可满足」，是软件配置、规划、排错的常见问题。

**易错点：** 不可满足核心不唯一。同一个不可满足公式可能有多个不同的最小冲突集，求解器给出的只是「它发现的那一个」。**依赖「最小」作精确定位时要多取几个核心交叉验证**，单核心可能遗漏真正的根因。

### 选择求解器的实践：Z3 与它的伙伴们

程序分析工程里「选哪个求解器」是一个现实问题。当前生态的默认选择与理由：

**Z3（微软）**：功能最全的 SMT 求解器，支持线性算术、位向量、数组、未解释函数、量词，还带模型生成与不可满足核心提取。它是符号执行与验证工具的事实标准——KLEE、angr、SymCC 都默认用它。**理由**：理论覆盖广、增量接口完善（push/pop）、API 友好（Python/C++/Rust 绑定）。

**CVC5**：SMT-COMP 竞赛的常客，尤其擅长位向量与算术的某几类问题，与 Z3 互补。**什么时候用**：Z3 卡住（超时）时换 CVC5 重试，或作交叉验证——两个求解器对同一公式结论一致时，可信度大增。

**MiniSat / CaDiCaL**：纯 SAT 求解器，只处理布尔 CNF。**什么时候用**：问题天然是布尔（如硬件验证、位爆破后的 SAT），或需要自研 DPLL(T) 外壳时的底层引擎。

**选型要点**：先看问题片段（线性？位向量？量词？），再看接口需求（增量？模型？核心？），最后看规模。**「先 Z3、卡住换 CVC5、布尔问题上 CaDiCaL」是绝大多数分析工程的默认配方。**

## 4 公式解析：DPLL(T) 的一次循环

把 DPLL(T) 的抽象-求解-学习循环写成精确形式。设 $F$ 是待判定的一阶公式，$\mathrm{abs}(F)$ 是它的布尔抽象，$M$ 是 SAT 求解器找到的布尔模型：

$$
\text{若 } M \vDash \mathrm{abs}(F) \text{ 且 } \mathrm{Th}(M) \text{ 一致，则 } F \text{ 可满足；否则学习引理 } \eta \text{ 并继续}
$$

对这条式子做三步拆解：

- **第一步，看布尔层**：$M \vDash \mathrm{abs}(F)$ 表示 SAT 求解器给每个原子命题赋了真假，使布尔骨架成立。$M$ 是「候选解释」。
- **第二步，看理论层**：$\mathrm{Th}(M)$ 一致表示「候选解释没有违反理论」。如 $M$ 说「$x>0$ 真且 $x\le 0$ 真」，理论求解器拒绝——不一致。
- **第三步，看学习**：不一致时学出引理 $\eta$（如「$x>0$ 与 $x\le 0$ 不同真」），把它加进 $\mathrm{abs}(F)$
