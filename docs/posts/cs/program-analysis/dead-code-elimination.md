## 为什么死代码值得单独一节

上一节的传播优化「照出」了冗余，这一节负责「删除」。**死代码消除（dead code elimination, DCE）** 大概是编译器里最直观、又最容易被低估的优化：它不加速任何一条指令，却让代码变小、让后续分析变快、让生成的二进制更干净。更重要的是，它展示了程序分析里一个微妙的主题——**什么算「死」**。<span class="marginnote">死代码的判据比表面看起来微妙：一条语句「没用」并不等于「没执行」。赋值 $x := 1$ 若 $x$ 之后从不被读，删除它不改变可观察行为；而 `print(x)` 即使其结果没人用，也绝不能删——它有可观察的副作用。副作用是 DCE 的分界线。</span>

**死代码（dead code）**：不改变任何可观察程序行为的语句或基本块。**死代码消除（DCE）**：识别并删除这类代码的优化。判断「可观察」的关键是**副作用（side effect）**：I/O、内存写、异常、外部可见状态——有副作用的语句永不视为死。

## 1 什么算死：三种「无用」

死代码有三种形态，对应三种判据：

**结果无用**：定义了一个变量，但它的值从来不被读取。`x := 1` 之后 `x` 没有任何使用，这条赋值是死的。判据：**定义无使用**。

**运算无效**：运算的结果本身不会被读取，且运算无副作用。`t := a + b` 若 $t$ 从不被用，整个加法是死的。判据：**定义无使用 + 无副作用**。

**执行无用（不可达）**：某个基本块根本不可能被执行——从入口不可达。例如 `if (true) S1 else S2` 中的 `S2`，或死循环之后的代码。判据：**从入口不可达**。

**易错点：** 第一、二种是「值死」，第三种是「路死」。值死靠活跃变量（或 SSA 的 use-def）判定，路死靠可达性（或常量折叠后）判定。两者方法不同，却都叫「死代码消除」——现代编译器里它们是两个不同的遍，只是常常合在一个 pass 里跑。

## 2 值死：SSA 上的「逆向活络」

SSA 形式让「值死」的判定变得局部。在 SSA 里每个变量恰好定义一次，一条定义是死的，当且仅当**它的定义没有任何使用**（除了可能被 $\phi$ 引用）。于是 DCE 变成：

1. 标记所有「有副作用」的语句为**活（live）**：输出、存储、调用、返回、无法证明无副作用的运算。
2. 从活的语句出发，**逆着 SSA 依赖边**标记它们的输入定义也为活。
3. 未被标记的定义就是死的，删除之；删除后可能连带使其输入定义变死，继续传播。

这是一个**可达性/闭包**计算：活集合从副作用根出发沿依赖反向扩散，像病毒传染。用数据结构课的术语说，就是对 use-def 图做一次逆向遍历。<span class="marginnote">注意它和活跃变量分析的关系：传统（非 SSA）的 DCE 用活跃变量分析先找「哪些变量的值还活着」，再删对应定义；SSA 的 DCE 更直接——一个定义没有使用点就是死，不需要整函数的迭代。这就是 SSA 让分析变「稀疏」的一个实例。</span>

**副作用根的清单**是 DCE 的正确性核心：漏标一个副作用根，就可能删除一条「实际上有影响」的语句。保守原则：**拿不准有没有副作用，就当作有**——宁可少删，不可错删。

### 值死的一个完整例子

把 SSA 版 DCE 在一条短程序上完整走一遍。设 SSA 代码：

```
1:  a = 1
2:  b = a + 2
3:  c = b * 3
4:  print(c)
```

SSA 化后每个变量定义一次，使用点直接可见。副作用根只有一个：语句 4 `print(c)`——它做 I/O，必活。反向传播：

- 从 `print(c)` 出发，`c` 的定义（语句 3）变为活。
- 语句 3 使用 `b`，`b` 的定义（语句 2）变为活。
- 语句 2 使用 `a`，`a` 的定义（语句 1）变为活。

四条语句全活，DCE 无事可做——这是对的，它们构成一条完整的依赖链，`print(c)` 确实需要全部。

改一个版本：把 `c` 的用途删掉——程序变成：

```
1:  a = 1
2:  b = a + 2
3:  c = b * 3
4:  print(b)      // 不再用 c
```

副作用根仍是语句 4。反向传播：`b` 的定义（语句 2）活；语句 2 用 `a`，`a` 的定义（语句 1）活。**语句 3 `c = b * 3` 没有被任何活语句使用——它是死的，删除。** 删除后程序为三条语句，行为完全不变（`c` 从不被读）。

再进一步，若 `b` 也只被语句 4 用、而语句 4 换成 `print(1)`，则 1、2、3 全死，程序塌缩成 `print(1)`。**「活」像潮水从副作用根倒流，够不着的岸就是死地。**

### 过程间 DCE：为什么调用是分界线

跨函数时，「活」的判断要过过程间这一关。设：

```
void helper(int x) { g = x; }   // g 是全局
int main() { helper(5); ... }
```

若 `helper` 只写全局 `g` 而 `g` 从不被读，`helper` 体内 `g = x` 是死的吗？**不能轻易删**——`helper` 可能被其他函数调用，那些调用可能读 `g`；更微妙的是，`helper` 的调用本身可能有「被观察」的语义（如调试器、插件、动态链接）。**过程间 DCE 的判断要沿着调用图检查被调函数的副作用与全局使用**，通常比过程内保守得多。

**易错点：** 有调用者不可见的副作用时，删调用是危险的。C 里无副作用的纯函数调用可以被删，但编译器默认「调用可能有副作用」——只有通过 `pure`/`const` 属性或过程间分析证明后，才敢删。**「拿不准就当有副作用」在过程间被放大成「拿不准就当整个调用有副作用」。**

## 3 路死：不可达基本块的消除

「路死」针对控制流。一个基本块若从入口不可达，它里面的语句执行不到，可以整块删除，包括它的副作用——因为副作用只在「被执行」时才算可观察，永不执行等于无副作用。

**不可达块从哪里来**：常量折叠把 `if (1) ...` 折叠成无条件跳转，`else` 分支变成不可达；异常处理代码在特定路径下不可达；死循环之后的代码不可达；还有人为的调试代码、被条件编译残留的代码。

**消除算法**：从入口做一次可达性遍历（BFS/DFS），标记所有可达块；未标记的块删除，同时删除指向它们的边。删除后可能使某些边变为悬空，需要一并清理。

**易错点：** 「死循环之后的代码」是路死的一个经典陷阱。`while(true){}; S;` 中 $S$ 不可达，但**死循环本身不是死代码**——它虽然永不返回，却有「卡住执行」的可观察行为。严格地说，把死循环优化成空程序需要「能证明循环终止」或「能证明循环体无副作用且退出后无观察者」，这超出了普通 DCE 的能力。**普通 DCE 只删不可达块，不删死循环。**

## 4 公式解析：DCE 的活集合闭包

把 SSA 版 DCE 的核心写成不动点形式。设 $Live$ 是被标记为活的**定义**集合，$SideEffect$ 是有副作用的语句集合，$Use(x)$ 是定义 $x$ 的所有使用点：

$$
Live = \text{lfp}_{\ \subseteq}\ \Big( SideEffect \ \cup\ \big\{ d \mid d \in \mathrm{Def}(u),\ u \in Use(d) \cap Live \big\} \Big)
$$

对这条式子做三步拆解：

- **第一步，看基底**：$Live$ 至少包含 $SideEffect$——一切副作用语句天生是活的，这是正确性的底线。
- **第二步，看传染规则**：若定义 $d$ 的某个使用点 $u$ 已经在 $Live$ 里，则 $d$ 也进 $Live$——活使用反向要求它的输入定义活着。
