## 为什么类型是一种程序分析

类型系统也许是人类最熟悉的一种程序分析：编译器在运行前检查每个表达式是否「类型匹配」。它也是程序分析里唯一被大规模强制部署的技术。**类型系统（type system）** 用静态规则保证程序不会发生「类型错误」；**效应系统（effect system）** 把它推广到更细的行为性质——这个函数会不会写全局状态？会不会抛异常？会不会执行 I/O？<span class="marginnote">类型系统与前面数据流分析的连接点：类型推导本质上是基于约束的分析（第 17 节），Hindley-Milner 的类型变量 + 合一就是约束求解。类型系统是「程序分析已成功工业化」的最好证据——每个编译器都在跑它。</span>

**类型系统（type system）**：一套静态规则，为每个表达式推导一个类型，并证明「良类型程序不会发生类型错误」的某个安全性质。**效应系统（effect system）**：类型系统的推广，为每个表达式推导一个**效应（effect）**——描述它在计算过程中可能进行的可观察操作（读写、异常、I/O、分配）。

## 1 类型：程序的「形状承诺」

**类型（type）** 是一个值的形状约定：`int`、`bool`、`List<int>`、`A → B`（函数类型）。类型系统的推导规则形如「若前提成立，则结论成立」：

$$
\frac{\Gamma \vdash e_1 : \tau_1 \quad \Gamma \vdash e_2 : \tau_2 \quad \tau_1 = \tau_2}{\Gamma \vdash e_1 + e_2 : \mathrm{int}}
$$

读作：「若在环境 $\Gamma$ 下 $e_1$ 有类型 $\tau_1$、$e_2$ 有类型 $\tau_2$，且 $\tau_1 = \tau_2 = \mathrm{int}$，则 $e_1 + e_2$ 有类型 $\mathrm{int}$」。$\Gamma$ 是类型环境——把自由变量映射到类型的表。

**类型安全（type safety）**：类型系统证明的性质。经典表述是「良类型程序不会 stuck」：只要程序还有一步可执行，类型就不会出错。它由两个引理支撑：

**进展性（progress）**：良类型的表达式要么是值，要么能再走一步。**保持性（preservation）**：良类型表达式走一步后仍是良类型。

这两条合起来，就是「类型保证程序不崩」的严格表述。<span class="marginnote">进展性 + 保持性（progress + preservation）是莱特（Wright）与费勒（Felleisen）在 1994 年给出的类型安全证明范式，至今是 PLT 教材的标准框架，与第三级《程序设计语言理论》的 ML 类型系统一脉相承。</span>

**类型与程序分析的关系**：类型是**可判定的、全自动的**静态性质，但它的表达力是「预定义抽象」——类型抽象了值，抽象不了「值之间的运行时关系」。这就是为什么数据流、抽象解释还要存在：它们提供类型系统给不了的更细性质。

## 2 从类型到效应：类型只管值，效应管行为

类型系统的局限在于它**只抽象值，不抽象行为**。一个函数 `f: int → int` 的类型告诉我们它返回整数，却不告诉我们它在过程中是否 `print` 了、是否改了全局、是否抛异常。**效应系统（effect system）** 补齐这个缺环。

**效应（effect）**：程序行为的一个静态描述。典型效应集合 $\Phi$ 含：

**读写（read/write）**：读取或修改某变量/存储。
**异常（exception）**：可能抛出异常。
- **I/O**：执行输入输出。
- **分配（alloc）**：分配内存（在关注资源分析时）。

函数类型带上效应标注：$A \xrightarrow{\phi} B$ 表示「输入 $A$、输出 $B$、计算过程中可能发生效应 $\phi$」。于是 `print` 函数是 $\mathrm{string} \xrightarrow{\{\mathrm{io}\}} \mathrm{unit}$——类型说返回值是 unit，效应说它做 I/O。<span class="marginnote">效应系统的历史：吉福（Gifford）与卢奇科（Lucassen）在 1980 年代提出，用于编译器的严格求值（strictness）分析；其后被用于异常分析、区域推断（region inference，ML 的 Typed Regions）、资源使用分析。它把「类型推导」的机械流程推广到了「效应推导」。</span>

**效应推导规则**与类型推导同构。顺序复合的效应是两部分的并：若 $e_1$ 有效应 $\phi_1$、$e_2$ 有效应 $\phi_2$，则 $e_1; e_2$ 有效应 $\phi_1 \cup \phi_2$。条件分支取并集：`if b then e1 else e2` 的效应是 $\phi_{e_1} \cup \phi_{e_2}$（两条分支都可能执行）。**效应推导 = 类型推导的「值换效应」版本**——同一个推理骨架，抽象的对象从「值」换成「行为」。

## 3 效应系统能干什么

效应系统的用途横跨编译优化与程序验证：

**纯度分析（purity analysis）**：函数无效应（纯函数）才能安全地缓存、重排、并行。Java 世界的 `@Pure`、Dart 的 `pure` 注解，编译器都可以用效应分析验证。

**异常分析**：推导「这个函数可能抛什么异常」，让 `catch` 的匹配、异常路径的数据流更精确——异常控制流是过程内分析的大坑，效应标注显式化后，分析器可以只沿「可能的异常路径」传播。

**区域与资源分析（region / resource analysis）**：推断内存分配、文件句柄、锁的获取与释放模式，为「保证释放」「保证成对」提供静态证据。Rust 的借用检查可以看作一种极其成功的效应/借用系统——它静态地保证「没有悬垂引用、没有数据竞争」。<span class="marginnote">Rust 是效应思想在工业界最响亮的胜利：借用检查器用「所有权 + 借用」的静态规则，在编译期消除整类内存错误——它本质上是把「可变借用」作为一种受限的写效应来静态管理。从程序分析视角看，Rust 的类型系统是一种高度工程化的效应系统。</span>

**调度与并行**：若函数被证明无写效应，可以安全地在多线程间并行或重排调用。数据依赖分析（第四篇《程序切片与依赖分析》）与之互补：效应给出「会不会读写」，依赖给出「读写之间是否有依赖」。

**易错点：** 效应系统的「并」不总是安全。若两个分支都有效应，取并集是保守的——但**效应并集会掩盖「效应之间的交互」**：读效应与写效应并起来，看不出「读到的是不是写过的」。所以更精细的系统用「读集/写集」成对记录，而不是单层效应集合——这是从「一阶效应」到「读写依赖」的精度升级。

### 效应多态与高阶函数

函数式程序里函数作为参数传递，「被传入的函数会做什么」也要静态知道。设：

```
apply_twice(f, x) = f(f(x))
```

`apply_twice` 的效应是什么？它本身不直接做 I/O，但它**调用**了 $f$——若 $f$ 有 I/O 效应，`apply_twice` 就有 I/O 效应。这就需要**效应多态（effect polymorphism）**：`apply_twice` 的效应是「参数 $f$ 的效应」——用一个效应变量 $\varepsilon$ 表示：

$$
\mathrm{apply\_twice} : \forall \varepsilon.\ (A \xrightarrow{\varepsilon} A) \times A \xrightarrow{\varepsilon} A
$$

读作：「对任意效应 $\varepsilon$，若 $f$ 有效应 $\varepsilon$，则 `apply_twice(f, x)` 也有效应 $\varepsilon$」。**效应像类型一样被量化、被实例化**——调用 `apply_twice(print_fn, 5)` 时 $\varepsilon$ 实例化为 `{io}`，调用 `apply_twice(pure_fn, 5)` 时 $\varepsilon$ 实例化为 `{}`。<span class="marginnote">效应多态把「高阶函数的行为」纳入静态掌握，是效应系统从「一阶语言」走向「函数式语言」的关键一步。它与类型系统里的「多态（polymorphism）」完全平行：类型多态量化「值」，效应多态量化「行为」。ML 的 MLKit 用区域推断（region inference）实现了这套思想的实用版。</span>

**易错点：** 效应多态不是免费的。高阶效应需要「效应变量 + 实例化」，推导算法比一阶效应复杂；且效应多态与「副作用内联」交互时，实例化点可能漏标。**工程系统常对高阶部分退化为「保守标全效应」**——纯度分析只对「无高阶调用的纯函数」给 `{}`，其余标满，牺牲精度换稳健。

### 与数据流分析的关系：效应是「轻量级」分析

最后把效应系统放回程序分析的大坐标系。效应系统与数据流分析处理同类问题（「程序会做什么」），但走的是**不同路线**：

- **数据流分析**：面向 IR，逐程序点传播，精度高、开销大，可处理任意性质（活跃、定值、可用表达式）。
- **效应系统**：面向类型推导，逐表达式组合推导，精度中等、开销低，擅长「结构化行为」（读写、异常、纯度）。

**它们的互补关系**：类型检查器在编译早期用效应系统快速过滤明显违规（如纯函数里调了 I/O）；更精确的验证在优化阶段用数据流/抽象解释细查。**效应系统是「静态分析的先遣队」，数据流分析是「精算师」**——前者便宜快，后者贵准，两者在同一代码上先后工作，各取所长。

### 效应系统的边界：它测什么，不测什么

把效应系统的「能力边界」说清楚，避免期望过高。效应系统**能**静态保证：

- **纯度**：函数不做 I/O、不改全局——可安全缓存、重排、并行。
- **异常**：函数可能抛什么异常——`catch` 匹配与异常路径分析。
- **读写范围**：函数读/写哪些存储——副作用局部化，利于缓存与依赖分析。
- **资源配对**：获取/释放的模式——文件句柄、锁的成对性。

效应系统**不能**保证（要靠其他分析）：

- **值之间的关系**：`x < y` 这种运行时关系，效应系统不建模（那是抽象解释）。
- **路径敏感的行为**：效应是「全路径的并集」，无法区分「这条路径抛异常那条不抛」。
- **时序/并发安全**：效应系统说「这个函数写全局 g」，但不自动判断「两个线程并发写 g 是否竞争」——那是并发分析的领域。

**易错点：** 效应系统的结论是「可能行为」而非「必然行为」。`f` 标有效应「可能写 g」，不代表 `f` 每次执行都写 g——只代表「存在路径会写」。**优化器利用的是「效应集合为空」的强结论（纯函数），而不是「效应集合非空」的弱结论。**这与数据流「可能/必然」的二分完全一致——程序分析的语言里，「不可能」永远比「可能」值钱。

## 4 公式解析：效应推导规则

把效应推导写成一个与类型推导平行的规则。设 $\Phi(e)$ 是表达式 $e$ 的效应，条件表达式与顺序复合的规则：

$$
\frac{\Gamma \vdash b : \mathrm{bool} \quad \Gamma \vdash e_1 : \tau, \Phi_1 \quad \Gamma \vdash e_2 : \tau, \Phi_2}{\Gamma \vdash \mathrm{if}\ b\ \mathrm{then}\ e_1\ \mathrm{else}\ e_2\ :\ \tau,\ \Phi_1 \cup \Phi_2}
$$

对这条式子做三步拆解：

- **第一步，看前提**：$e_1$ 与 $e_2$ 都必须良类型（都是 $\tau$），各自带效应 $\Phi_1$、$\Phi_2$。分支的效应先各自推导。
- **第二步，看结论的效应**：条件表达式的效应是 $\Phi_1 \cup \Phi_2$——**两条分支都可能执行，效应必须取并集**。这是「效应是可能行为的集合」的直接推论。
- **第三步，看结论的类型**：条件表达式的结果类型是 $\tau$——两个分支类型一致，整体类型才良定义。**类型要求分支「值一致」，效应要求分支「行为并集」——两套推导并行、互不干扰，却共享同一个证明结构。**

## 5 小结

- **类型系统**静态推导表达式的类型，用进展性 + 保持性证明类型安全；它是已工业化的最成功分析。
- **效应系统**把推导对象从「值」推广到「行为」，函数类型带效应标注 $A \xrightarrow{\phi} B$
