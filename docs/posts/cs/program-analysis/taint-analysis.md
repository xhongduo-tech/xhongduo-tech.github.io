## 为什么污点分析是安全的「数据流」

这一节把第二篇的数据流框架用到安全上。**污点分析（taint analysis）** 回答一个直击安全要害的问题：**不可信的数据（污点源）是否可能流入敏感的位置（污点汇）？** 它的学名是「信息流分析（information flow analysis）」的安全子集，与软件安全、Web 应用漏洞（SQL 注入、XSS、命令注入）绑定在一起。<span class="marginnote">信息流分析的正统学术形态（Denning 1976）研究「机密信息如何泄露」（保密性）与「不可信信息如何破坏完整性」（完整性）；污点分析是它在工程上的实用化：不追求全部信息流，只追「源→汇」的数据依赖。第三级《系统安全》的漏洞章节与此直接衔接。</span>

**污点源（source）**：不可信数据的入口——用户输入、网络请求、环境变量、数据库查询结果。**污点汇（sink）**：敏感操作的位置——SQL 查询拼接、HTML 输出、`exec()` 命令执行、内存拷贝。**污点分析（taint analysis）**：静态或动态地追踪「污点从源到汇的数据流」，报告「可能到达汇」的路径（即潜在漏洞）。

## 1 三要素：源、汇与传播规则

污点分析把数据流框架实例化成一套「污点标记」逻辑：

**源（source）**：给来自这些位置的数据打上污点标记 $T$。在数据流框架里，源语句的传递函数**生成**污点：`input()` 的输出标记为污点。

**汇（sink）**：检查到达汇的数据是否带污点。`execute(cmd)` 若 `cmd` 带污点，就是「命令注入」漏洞候选。

**传播规则（propagation）**：污点如何沿数据流移动。核心规则是「数据依赖传播」：

赋值 $x = y$：若 $y$ 带污点，$x$ 也带污点。
运算 $x = y \ \mathrm{op}\ z$：$y$ 或 $z$ 任一带污点，$x$ 就带污点（污点的**保守**传播：不确定就标记）。
- 函数调用 $x = f(y)$：$y$ 的污点是否流到 $x$，取决于调用图与函数摘要——**过程间污点传播**是污点分析的精髓（复用第 18 节）。<span class="marginnote">污点传播与抽象解释的格论对应：污点集合就是一个抽象域——元素是「数据对象」，join 是并集，传递函数按数据依赖生成/保留污点。所以污点分析 = 抽象解释 + 特定源汇配置，框架完全复用。</span>

**易错点：** 污点传播必须区分**显式流（explicit flow）** 与**隐式流（implicit flow）**。显式流是数据依赖（`x = y`），隐式流是控制依赖（`if (secret) leak = 1;`——秘密通过分支结构泄露）。**大多数实用污点分析只追显式流**：隐式流需要「标记 + 条件」的联合建模，代价高，误报多。这是「保密性信息流」与「完整性污点」的精度取舍。

## 2 静态污点分析：沿数据流找漏洞

静态污点分析在源码或 IR 上做数据流分析。把它塞进第二篇的框架：

**信息域**：每个程序点的「污点集合」——带污点的对象清单。
**传递函数**：按传播规则生成/保留污点；汇点处检查污点并报告。
- **汇合**：并集——任一路径带污点，汇合点就带污点。
- **方向**：正向（从源出发）或逆向（从汇回溯）；逆向常更快——从每个汇回溯找源，只算相关路径。

**污点路径（taint path）** 是分析报告的核心：一条从源到汇的数据依赖链。工程师拿到报告，重点看这条链上的**净化器（sanitizer）**：若链上有可信的净化（如对 SQL 参数做转义、对 HTML 做编码），则漏洞被缓解；若没有，则确认漏洞。<span class="marginnote">净化器（sanitizer）是污点分析的「终结者」：`sanitize(x)` 若被信任，它的输出不带污点——传递函数在这里「杀死」污点。净化的可信度是静态污点分析最脆弱的假设：转义不彻底、编码有洞，就会漏报。所以工业工具（如 CodeQL、Semgrep）把净化器清单做成可配置、可审计的。</span>

**工业实践**：GitHub CodeQL 把「源—汇—净化」建模成 query（污点查询），在大型代码库上跑过程间污点分析；Semgrep 用模式匹配做轻量污点；商业工具如 Checkmarx、Fortify 走全程序污点。**静态污点分析的瓶颈在精度**：过程间 + 字段敏感 + 别名感知才够准，而这三样都贵。

**易错点：** 静态污点分析是「可能流」而非「必然流」。报告「污点可能到达汇」是**误报候选**——实际运行时也许永远没有那条路径。工程师要人工判断或动态验证。**「可能」是静态分析的本性，不是工具的缺陷。**

### 一个 SQL 注入的污点路径例子

把三要素在一段真实风格的代码上走一遍。设 Web 应用的登录代码：

```php
$user = $_POST['username'];          // 源：不可信用户输入
$sql  = "SELECT * FROM users WHERE "
      . "name = '" . $user . "'";     // 拼接 SQL
$result = mysql_query($sql);          // 汇：SQL 执行
```

**源**：`$_POST['username']`——HTTP 请求参数，不可信。污点标记 `T`。

**传播**：`$user` 带 `T`；字符串拼接 `"..." . $user . "..."` 的输出也带 `T`（污点沿数据依赖传播）；`$sql` 带 `T`。

**汇**：`mysql_query($sql)` 若 `$sql` 带 `T`——报告「SQL 注入」。攻击者输入 `' OR '1'='1` 之类，就改变查询语义，绕过认证。

**净化器**：若代码在拼接前做了转义——`$user = mysql_real_escape_string($_POST['username'])`——净化器的输出不带 `T`，报告被抑制。**但这依赖净化器真的完备**：转义少一个字符、少一种上下文（如数值上下文）就可能仍有洞。

**污点分析器的工作**：自动标出「源 → 汇」的路径，报告「`$user` 从 `$_POST` 到 `mysql_query` 未经净化」。工程师只需确认「这条链上有没有可信净化」——**污点分析把「找漏洞」从全文审计变成「审报告」**。

### 隐式流：为什么大多数工具不追它

上一节提到隐式流，这里展开它的代价。隐式流（implicit flow / control dependency）的经典泄露：

```c
int secret = ...;   // 机密
int leak = 0;
if (secret == 42) leak = 1;   // leak 泄露了 secret 是否为 42
```

`leak` 的值由控制流决定，没有「数据依赖」——显式流污点分析看不到这条泄露。要捕获它，分析必须追踪「控制依赖 + 数据依赖」的联合：进入 `if` 时，分支条件里的污点要「传染」给分支体里的所有写操作。

**为什么大多数工具不追**：代价三重。

**精度崩溃**：`if (secret)` 的整个分支体所有写都被标记，污点泛滥成灾。
**路径爆炸**：控制依赖沿路径传递，分析与路径敏感结合，复杂度过高。
- **实际收益低**：真实漏洞（注入、XSS）几乎都是显式流；隐式流主要出现在「信息泄露」的保密性分析里。

**易错点：** 「不追隐式流」不是「不知道隐式流」，而是**有意的精度-代价取舍**。需要完整信息流保证（如军工、金融的保密性认证）时，工具会开启隐式流追踪（如 JOANA、FlowDroid 的高精度模式），接受其开销。**隐式流的开与关，是污点分析「工程妥协」的最好缩影。**

## 3 动态污点分析：运行时跟踪

与静态版相对，**动态污点分析（dynamic taint analysis）** 在程序运行时追踪数据传播：

**插桩**：在读写点插桩，当带污点的数据被读入某个变量时，该变量被标记；当污点数据参与运算、流入存储、传参时，标记随之传播。现代实现靠 **DFI（data-flow instrumentation）** 或硬件辅助（Intel PT、ARM CoreSight）。

**优点**：精确——只报真实到达的路径，几乎无误报；能捕捉「静态分析看不见」的复杂传播（反射、动态分发、间接调用）。**缺点**：只覆盖被执行的路径——未执行的代码是盲区；运行时开销大（插桩普遍 2-10 倍减速）。

**典型应用**：浏览器漏洞利用检测、恶意软件行为分析（沙箱里的污点追踪）、协议模糊测试的导向（DTA-guided fuzzing）。<span class="marginnote">DTA-guided fuzzing 是污点分析与 fuzzing 联姻的亮点：fuzzer 跑出覆盖后，用动态污点找出「哪个输入字节影响了哪个分支条件」，把变异集中在相关字节——比盲目变异高效得多（如 Redqueen、VUzzer 等）。这是「动态污点 + 搜索」的现代结合。</span>

**易错点：** 动态污点分析也会被**隐式流与过度污点**困扰：污点标记沿数据依赖传播，遇到「基于污点数据的控制流」时，要么漏（不标隐式流）要么爆（连控制依赖也标，污点泛滥）。**标记粒度（byte/bit）与传播策略，是动态污点分析调参的核心。**

## 4 公式解析：污点传播的传递函数

把污点分析的静态版本写成数据流方程。设 $\mathrm{Taint}(n)$ 是程序点 $n$ 的污点集合，语句 $S$ 的传播规则为「若输入对象带污点，输出对象就带污点」：

$$
\mathrm{Taint}(out) = \bigcup_{in \in \mathrm{Defs}(S)} \big\{ t \mid t \in \mathrm{Taint}(in) \lor t = \mathrm{src}(S) \big\}
$$

对这条式子做三步拆解：

- **第一步，看右侧的并**：遍历语句 $S$ 涉及的所有输入定义，收集它们的污点；若 $S$ 本身是源（$\mathrm{src}(S)$），把 $S$ 产生的污点也加进去。
- **第二步，看传播语义**：输出污点 = 「输入污点的并」 + 「本语句新产生的污点」。赋值/运算/调用的输出都按这条规则标记——**数据依赖是污点传播的唯一通道**（显式流）。
- **第三步，看汇检**：在汇点 $S'$ 检查 $\mathrm{Taint}(in) \cap \mathrm{SinkTaint}(S') \ne \emptyset$
