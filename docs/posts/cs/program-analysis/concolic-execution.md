## 为什么「光符号」不够

上一节的纯符号执行有个顽固的软肋：**外部世界**。文件内容、网络包、系统调用返回值——这些很难符号化，纯符号执行往往卡死或退化成具体。而**动态符号执行（concolic execution）** 给出的方案非常务实：**一边用具体值真实地跑，一边用符号值平行地记录约束**。「concolic」是 concrete + symbolic 的合成词。<span class="marginnote">DART（Directed Automated Random Testing，戈德弗莱等人，2005）首次提出「具体+符号并行执行」：具体执行负责与真实环境交互，符号执行负责追踪路径约束。随后 KLEE 的姊妹系统与各类 fuzzer 把它发扬光大，成为现代漏洞挖掘的主流技术路线。</span>

**动态符号执行 / concolic 执行（concolic execution）**：同时维护具体状态与符号状态，用具体值执行程序（解决外部世界），用符号约束追踪路径（解决覆盖引导），并通过**符号化取反（negation）** 系统性探索未走过的分支。

## 1 双状态执行：具体与符号并行

concolic 执行的核心是**两条平行线**：

**具体状态**：变量绑定到真实值，照常执行——调用真实 API、读写真实文件。
**符号状态**：变量绑定到符号表达式，记录「具体值是从哪条输入约束演化来的」。

执行每条语句时，两条线同时推进：具体求值得到真值，符号求值得到表达式。关键在分支处：`if (cond)` 在具体执行里只走一边，但符号层把 `cond` 的符号表达式记下来——它是「这条路径的约束」的一部分。

于是 concolic 执行避开了纯符号执行的最大坑：**程序可以自由调用外部世界**，因为具体执行真的在跑；符号层只是「旁观记录」，从不向外部世界要符号值。<span class="marginnote">这个「具体跑 + 符号记」的设计，让 concolic 执行对真实程序（含系统调用、第三方库）的适应力远超纯符号执行。代价是：具体路径只有一条——覆盖面要靠「反复换输入重跑」来扩展，这引出下一节的路径探索。</span>

**易错点：** 具体状态与符号状态必须**保持同步**。若符号表达式里的某个变量在具体执行中被外部调用（非符号化）污染，符号层必须把该变量的符号值「具体化」——用当前具体值替换符号表达式，否则符号约束就失真了。**具体化的时机是 concolic 实现最重要的正确性细节。**

## 2 路径探索：符号化取反

concolic 执行一次只跑一条具体路径，但它可以**系统地改变下一次运行**。这靠**符号化取反（symbolic negation）** 实现：

1. 跑一遍，收集沿路径的所有分支条件 $c_1, c_2, \dots, c_k$（符号表达式）。
2. 从后往前，依次尝试「取反某个分支条件」：构造新路径条件
$$
PC' = c_1 \land c_2 \land \dots \land \neg c_i
$$
（前 $i-1$ 个分支保持原方向，第 $i$ 个取反）。
3. 用 SMT 求解 $PC'$：可满足 ⟹ 得到一组新输入，重跑程序就会走一条「没走过的路径」。
4. 对每个 $i$ 都试一遍，得到一族新输入，覆盖相邻路径。

这个「从后往前取反」的策略，保证每次新输入至少与当前路径共享前 $i-1$ 个分支、但在第 $i$ 个分支掉头——**新的路径是当前路径的「邻居」**，覆盖从当前路径逐步铺开。

**易错点：** 求解 $PC'$ 不一定总成功——$PC'$ 可能不可满足（取反的分支被前面的约束蕴含掉了）。工业实现会跳过不可满足的取反点，继续试更靠前的分支；若全部取反点都不可满足，说明该路径的「邻居」都被剪枝，换一条路径再试。**路径探索是启发式的，不是穷举的**——它是「尽可能多地覆盖」，不是「覆盖所有」。

### magic bytes 问题：concolic 的招牌胜利

concolic 执行最有说服力的场景是破解 **magic bytes 检查**——程序检查输入是否等于某个魔数：

```c
int check(const char *buf, int len) {
    if (len >= 4) {
        if (buf[0] == 0xDE && buf[1] == 0xAD
         && buf[2] == 0xBE && buf[3] == 0xEF) {
            vulnerable(buf);   // 只有魔数才能走到这
        }
    }
    return 0;
}
```

**随机测试的困境**：随机输入命中的概率是 $2^{-32}$——几乎不可能。即使 fuzzer 覆盖引导，也只会把变异花在「已有覆盖」的字节上，这 4 字节的精确匹配对它也是天堑。

**concolic 的解**：用符号执行追踪 `buf[0]` 到 `buf[3]` 的约束。第一轮具体执行（随机输入）会卡在 `buf[0] == 0xDE` 上；符号化取反后，PC' =「`buf[0] == 0xDE` 且其他分支条件保留」，求解器给出满足的输入——$buf[0] = 0xDE$。下一轮再取反下一个字节，依此类推，**四轮求解就能生成完整魔数 `DE AD BE EF`，让 `vulnerable(buf)` 被触发**。

这个例子概括了 concolic 的全部价值：**它把「猜出魔数」这种概率几乎为零的事，变成「求解 4 条线性约束」这种确定的事**。现代漏洞挖掘里，凡遇「格式检查墙」，concolic 就是破墙的锤子。

### 覆盖率反馈：fuzzer 与 concolic 的分工

把 concolic 放进更大的 fuzzing 生态，看清分工。现代 fuzzer（如 AFL、libFuzzer）是**灰盒覆盖引导**：

- 插桩收集「这次执行覆盖了哪些边」。
- 保留「带来新覆盖」的输入，丢弃重复覆盖。
- 在保留的输入上随机变异，继续跑。

它的优势是**便宜**——每次执行开销极小，每秒数万次；劣势是**过不了 magic bytes 这类精确检查**。concolic 正好相反：**贵**（求解耗秒级）但**能过精确检查**。

于是工业标准分工成型：**fuzzer 铺广度（快速覆盖大量普通代码），concolic 解深度（定向突破格式检查）**。Driller（2016）把这个分工流水线化：fuzzer 跑到瓶颈（覆盖停滞），把「卡住的输入」交给 concolic 求解突破，突破后再交回 fuzzer 继续铺。**「广度保底 + 深度攻坚」是今天漏洞挖掘的标准配方。**<span class="marginnote">这个分工也是程序分析「静态/动态」长期争论的一个建设性答案：不是谁替代谁，而是各干各擅长的活。concolic 是「动中有静」——运行时收集约束、静态求解突破；fuzzer 是「动中带引」——运行时反馈引导变异。两者叠加，覆盖了彼此盲区。</span>

## 3 从 DART 到主流 fuzzing

concolic 执行的技术谱系，从源头到今天的 fuzzing 生态：

**DART（2005）**：最早提出「具体+符号并行 + 取反探索」的三件套，目标是单元测试自动化。

**KLEE / EXE（2008）**：符号执行引擎的巅峰之作。它对「符号化一切」做了极致——把文件、网络、环境变量都建模成符号，用启发式（如按「新覆盖」「危险操作」优先）选路径。KLEE 用在小程序（如 GNU coreutils 的工具）上，一次能找到几十个真实 bug。<span class="marginnote">KLEE 的成功证明了符号执行在「有界小程序的深度探索」上远胜随机测试。它把搜索策略做成可插拔组件，研究者可以换启发式来比较效果——这使它也成为符号执行研究的实验台。</span>

**选择性符号执行（selective symbolic execution）**：全程序符号化代价太高，于是「只对感兴趣的代码段符号化，其余具体化」。SAGE（微软）用它把「大程序的某个模块」深度验证，是白盒 fuzzing 的代表。

**今天的 fuzzing 生态**：纯随机的灰盒 fuzzer（如 AFL）用覆盖反馈快速铺开；concolic 与其互补——「concolic 解复杂约束，fuzzer 铺覆盖」。两者混合（如 Driller、SymCC）成为现代漏洞挖掘的标准配方。<span class="marginnote">「混合 = fuzzer 铺广度 + concolic 解深度」是过去十年漏洞挖掘最重要的工程结论：AFL 这类覆盖引导 fuzzer 对简单约束极快，但一遇「magic bytes」（如 `if (input == 0xdeadbeef)`）就卡住——concolic 正好用约束求解跳过这种「检查墙」。Driller（2016）把这个分工做成了清晰的流水线。</span>

## 4 公式解析：取反生成新路径

把符号化取反生成新输入写成一个精确流程。设第 $r$ 次执行走过的分支条件序列为 $c_1^{(r)}, \dots, c_k^{(r)}$（$c_i$ 是第 $i$ 个分支处为真时走的方向），取反第 $j$ 个分支生成第 $r+1$ 次的输入 $\vec x^{(r+1)}$：

$$
\vec x^{(r+1)} = \mathrm{SMT}\Big( c_1^{(r)} \land \dots \land c_{j-1}^{(r)} \land \neg c_j^{(r)} \Big)
$$

对这条式子做三步拆解：

- **第一步，看前缀保持**：$c_1^{(r)} \land \dots \land c_{j-1}^{(r)}$ 是「前 $j-1$ 个分支维持原方向」——新路径与旧路径在前缀上一致，这是「邻居」的定义。
- **第二步，看取反点**：$\neg c_j^{(r)}$ 是第 $j$ 个分支掉头——**唯一改变的约束**。它保证新输入触发与旧路径不同的分支决策。
- **第三步，看求解**：SMT 求解这条公式，返回满足的输入 $\vec x^{(r+1)}$
