# 过程间分析：调用字符串与环境

<div class="epigraph">

## 为什么单函数分析不够

前几节的分析都默认作用在单个函数上：函数入口给定初始信息，函数出口得到结果。但真实程序是函数调用构成的网络——`foo()` 调用 `bar()`，`bar()` 又调用 `baz()`。**过程内分析（intraprocedural analysis）** 把每个函数当成独立世界，调用点被粗暴地当作「生成/杀死」的抽象；**过程间分析（interprocedural analysis）** 沿调用图分析跨函数的控制流。<span class="marginnote">不做过程间分析，跨函数的常量、指针、副作用全部丢失——而现代大型程序里大量逻辑在函数调用之间流动。过程间分析是「让机器理解真实程序」的分水岭，也是第三级《软件工程》里依赖分析、第四级形式化验证的基石。</span>

**调用图（call graph）**：以函数为节点、以「$f$ 调用 $g$」为边的有向图。**过程间分析（interprocedural analysis）**：沿调用图把被调函数的信息并入调用点的分析。**上下文敏感（context-sensitive）**：区分「同一函数在不同调用点/调用路径下的不同行为」。

## 1 调用图与调用约定：过程间分析的地图

过程间分析的第一件事，是建**调用图**。对静态派发（C、Java 的非虚方法），调用边直接确定：`foo()` 里 `bar(x)` 就是一条 `foo → bar` 边。对动态派发（C++ 虚函数、Java 接口、JavaScript），调用目标要分析才知道——这就形成「分析依赖调用图、调用图又依赖分析」的循环，需要不动点求解（通常在类层级分析或指针分析之后做一轮）。

过程间分析需要给每个调用点建模**调用约定**——参数怎么传、返回值怎么回、全局与内存怎么共享：

**参数传递**：调用点把实参信息绑定到形参；被调函数返回时，返回值信息流回调用点。**引用与指针**：形参若是指针，实参指向的对象可能被被调函数修改——这是别名分析（下一节）与过程间分析的交叉点。**全局状态**：被调函数可能读写全局变量，调用点的全局信息要先「传进去」再「收回来」。<span class="marginnote">在 IR 层面，这些约定被展开成显式的拷贝：实参赋值给形参、返回值赋值给接收者。于是过程间分析可以复用过程内的数据流框架——只要把「调用语句」的传递函数替换成「被调函数摘要 + 绑定」的组合。</span>

## 2 两种精度策略：流敏感与上下文敏感

过程间分析的精度，由两个「敏感」维度决定：

**流敏感（flow-sensitive）**：区分函数内不同程序点的信息。上一节已述。**上下文敏感（context-sensitive）**：区分「函数在不同调用环境下的行为」。对同一个被调函数 `add(a, b)`，若在 `foo` 里实参是 `(1, 2)`、在 `bar` 里实参是 `(x, y)`，上下文不敏感的分析会把两种调用**混在一起**，得出「$a$ 可能是 1 也可能是 $x$」的粗糙结论；上下文敏感的分析分别记录，各自精确。

上下文敏感的两种标准实现：

**调用字符串（call strings）**：为每个「调用点序列」单独记录信息。信息带上「从入口到现在经过的调用点清单」，同一函数的不同调用字符串视为不同「程序点」。精度与字符串长度成正比，代价随长度指数增长。<span class="marginnote">调用字符串的直觉：给每次「函数之旅」贴一个路径标签。有限长度 $k$ 的调用字符串（$k$ 层上下文）是工业标准——$k=1$ 就是「一层调用上下文」，已能显著提升精度。无限长度理论上最精确，但通常不可终止，需用加宽式的截断。</span>

**函数摘要（summaries）**：为每个函数预先计算「输入 → 输出」的行为摘要（如「给定输入区间 $[0,10]$，输出区间 $[1,11]$」），调用点只需查摘要、按实参实例化。摘要可复用——同一函数被调用 100 次，摘要只算一次。<span class="marginnote">摘要与调用字符串是互补的：调用字符串精确但重复计算（每个上下文重跑函数），摘要复用但要做「摘要组合」（嵌套调用的摘要如何合并）。现代分析器往往混用：热点函数用摘要，深路径用有界调用字符串。</span>

## 3 求解过程间不动点

有了调用图与上下文策略，过程间分析照例收敛到不动点。以一个**朴素但正确**的迭代版本说明流程：

1. 初始化：每个函数入口信息为 $\bot$，调用点信息为 $\bot$。
2. 反复：对每个调用点 $f(x)$，用当前实参信息实例化被调函数入口；沿被调函数传播；把返回信息并回调用点。
3. 直到所有信息不再变化。

这个迭代的终止由格有限高 + 单调保证（若上下文策略有界）。但**过程间不动点的「规模」比过程内大得多**——每个「函数 × 上下文」都占用一份信息，上下文敏感分析的内存随上下文数增长。

**易错点：** 递归调用（直接或间接）制造调用图中的环，也制造「函数信息依赖自己」的循环。递归的摘要不能简单「算一次」，必须迭代到不动点；且递归 + 无限上下文敏感（调用字符串无限长）可能不终止——**有界上下文是终止性的前提**。<span class="marginnote">尾递归优化的分析版：若递归调用的信息只沿「返回路径」传播，可以展平成循环来分析；但一般递归没有这个性质。工业界对递归函数的上下文深度通常设上限（如 2-3 层），超过即退化到上下文不敏感。</span>

### 一个跨函数常量传播的完整例子

用「上下文敏感」与「上下文不敏感」对比，看精度差异。设程序：

```
int add(int a, int b) { return a + b; }
int main() {
    int x = add(1, 2);      // 调用点 1：实参 (1,2)
    int y = add(x, 100);    // 调用点 2：实参 (x,100)
    return y;
}
```

**上下文不敏感**：`add` 只有一份「入口信息」——它汇合了两个调用点的实参。调用点 1 传 $a=1,b=2$，调用点 2 传 $a=x,b=100$。合并后 $a$ 的抽象值「可能是 1 也可能是 $x$」，$b$「可能是 2 也可能是 100」。返回信息同样合并：`add` 的返回值「可能是 $3$ 也可能是 $x+100$」。于是 `y` 的值为「可能是 $3$ 也可能是 $x+100$」，常量传播被破坏——`y` 非常量。

**一层上下文敏感（1-CFA / 1 层调用字符串）**：`add` 按调用点分裂成两个实例。调用点 1 的 `add`：$a=1, b=2$，返回 3，`x = 3`——`x` 是常量。调用点 2 的 `add`：$a=3, b=100$，返回 103，`y = 103`——**`y` 也是常量，`return y` 变成 `return 103`**。

这个例子展示了过程间分析的黄金收益：**跨函数的常量可以精确传播**。代价是 `add` 被分析两次（两个上下文），调用点越多越贵——这就是上下文敏感的「指数墙」。

### 过程间分析的典型框架

现代过程间分析器的标准装配，是一套「三明治」：

**第一层，构建调用图**：先做一轮粗分析（类层级分析、指针分析）确定调用目标，建出调用图。动态派发多时这层就要迭代。

**第二层，选择上下文策略**：决定「每个函数保留几份上下文」。工业默认是「有界调用字符串（2-3 层）+ 热点函数用摘要」，配合「按需上下文」——只在精度敏感处增加上下文深度。

**第三层，求解**：在调用图上跑不动点迭代，用工作表 + 摘要缓存加速。递归调用用「摘要不动点」处理。

**工程教训**：过程间分析的复杂度几乎全在「上下文」的管理上——上下文太多内存爆炸，太少精度不足。**「按需上下文」（demand-driven context）**是近年主流：先做廉价的粗分析，只在「某个结论会被下游用到且粗结论不够用」时，才为那条路径增加上下文深度。它把「全量精算」变成「按需精算」，是精度与规模之争的最佳实践。

### 过程间分析的复杂度权衡

把过程间分析的代价模型量化，看清「上下文」的账单。设程序有 $F$ 个函数、每个函数平均 $N$ 个程序点、平均 $C$ 个调用点，各档策略的复杂度：

**上下文不敏感**：每个函数一份信息，总工作量 $O(F \cdot N)$——几乎与过程内分析同级，快，但精度差（所有调用互相污染）。

**1 层调用字符串**：每个函数按「直接调用者」分裂，总状态数 $O(F \cdot C)$——函数数 × 调用点数，中等；但调用点多的程序（如库代码）会膨胀。

**k 层调用字符串**：$O(F \cdot C^k)$——指数增长。这也是为什么 k 很少超过 3：**每次加深一层上下文，内存就乘以调用点平均出度。**

**按需上下文**：大部分路径只跑不敏感版本，只在「关键结论」处加深。实际开销介于「不敏感」与「1 层」之间，但精度接近「1-2 层」——**这是「付出少、收获多」的典型工程设计**，也是过程间分析在现代大型代码库上跑得动的根本原因。

**易错点：** 别用「上下文越多越准」一刀切。上下文敏感**对某些性质无效**——若一个函数的行为不依赖调用者（如纯函数、无全局依赖），加深上下文只会白花钱。**上下文深度的选择要「按性质驱动」**：先问「这个结论需要区分调用者吗」，再决定加深与否。

## 4 公式解析：调用点的信息流

把过程间分析的核心——调用点信息流——写成公式。设调用点 $c$ 调用函数 $g$，$IN_{c}$ 是调用点入口信息，$arg$ 把实参信息绑定为形参环境，$ret$ 从返回信息中提取返回值：

$$
IN_{g}(\alpha(c)) = \mathrm{env}(\alpha(c),\ IN_c), \qquad OUT_c \ \supseteq\ \mathrm{ret}\big( OUT_g(\alpha(c)) \big)
$$

对这条式子做三步拆解：

- **第一步，看第一式**：$IN_g(\alpha(c))$ 是「被调函数 $g$ 在上下文 $\alpha(c)$ 下的入口信息」——由调用点入口信息 $IN_c$ 经实参绑定 $\mathrm{env}$ 得到。$\alpha(c)$ 是调用字符串：同一函数 $g$ 在不同调用点 $c$ 下被当作不同对象分析。
- **第二步，看第二式**：$OUT_c \supseteq \mathrm{ret}(OUT_g(\alpha(c)))$ 是「返回信息流回调用点」——$g$ 在该上下文下的出口信息，经返回值提取，并回调用点出口。$\supseteq$ 表示「至少并入这些」，多个调用路径的信息在此汇合。
- **第三步，看上下文**：$\alpha(c)$ 是这一切的核心——**没有它，$g$ 只有一个入口信息、一个出口信息，所有调用互相污染；有了它，$g$ 按上下文分裂成多个分析实例，各自精确。**

## 5 小结

- **过程间分析**沿调用图跨函数分析；先建调用图（动态派发需不动点求解）。
- 精度由**流敏感 × 上下文敏感**两个维度决定；上下文敏感区分同一函数在不同调用下的行为。
- **调用字符串**贴路径标签、精确但重复计算；**函数摘要**按输入输出复用、省算但需组合。
- 递归制造信息环，**有界上下文**是过程间迭代终止的前提。
- 调用点信息流公式：$IN_g(\alpha(c)) = \mathrm{env}(IN_c)$，$OUT_c \supseteq \mathrm{ret}(OUT_g(\alpha(c)))$——上下文 $\alpha(c)$ 是精度的灵魂。
- **复杂度权衡**：不敏感 $O(F \cdot N)$，k 层调用字符串 $O(F \cdot C^k)$；**按需上下文**在成本与精度之间取最优，是大型代码库上跑得动的根本原因。
