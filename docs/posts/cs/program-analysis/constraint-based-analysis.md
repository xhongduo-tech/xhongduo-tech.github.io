## 为什么把分析写成「约束」

前几节的分析都是「沿控制流图传播信息」——数据流传播。但有一类分析（尤其是**指针分析、类型推导、部分求值**）不容易组织成「图上的传播」，它们更适合**约束**的观点：为每个程序点建立一组关于信息的方程，再求解这组方程。<span class="marginnote">「沿图传播」与「建方程求解」其实是同一枚硬币的两面——数据流方程就是一种约束系统。区别在视角：传播强调「信息的流向」，约束强调「信息之间的关系」。基于约束的分析把关系显式写成约束，交给统一求解器。</span>

**约束系统（constraint system）**：一组形如 $x \supseteq \dots$ 或 $x = f(y_1, \dots, y_k)$ 的式子，其中 $x, y_i$ 是「每个程序点/变量的抽象信息」。**基于约束的分析（constraint-based analysis）**：把分析问题翻译成约束系统，再求其最小解（通常是不动点）。

## 1 把分析翻译成约束

以**流不敏感的指针分析**（别名分析的一类）为例，看约束翻译是怎么做的。流不敏感分析不区分执行顺序，把整个函数当作一个约束网络：每个变量的「可能指向集合」用 $\mathrm{pts}(x)$ 表示（$x$ 可能指向的分配点集合），每条语句翻译成一条约束。

三类基本语句的约束：

分配 $x = \mathrm{new}()$：$\mathrm{pts}(x) \supseteq \{\mathrm{new}\}$——$x$ 至少指向这个分配点。
复制 $x = y$：$\mathrm{pts}(x) \supseteq \mathrm{pts}(y)$——$x$ 继承 $y$ 的一切可能指向。
- 读取字段 $x = y.f$：$\mathrm{pts}(x) \supseteq \bigcup \{ \mathrm{pts}(z).f \mid z \in \mathrm{pts}(y) \}$——$y$ 可能指向的每个对象 $z$，其字段 $f$ 的可能指向都算进 $x$。

**约束全是「⊇」形式**：左边是「至少包含」——分析从最小的可能指向集合出发，逐步把必须包含的信息加进去，直到满足所有约束。**这正是求最小解**：最小解是最精密的解，不包含任何「不必要」的指向关系。<span class="marginnote">「最小解 = 最精确解」不是偶然：约束 $\supseteq$ 的方向编码了「信息越少越精确」的格约定（第三节）。解空间里最小的那个，恰好是信息最少的、也就是最可信的——不含多余猜测。</span>

**易错点：** 复制语句的约束方向容易写反。$x = y$ 应该给 $\mathrm{pts}(x) \supseteq \mathrm{pts}(y)$，不是 $\subseteq$。方向错了，求解出来的就不是「最小闭包」而是「最大退化」——分析彻底失去意义。**约束的方向由「信息流动的方向」决定：赋值把 $y$ 的信息流向 $x$，所以 $x$ 的约束从 $y$ 收取。**

## 2 求解约束：从不动点到图上闭包

约束系统的求解，本质还是不动点迭代。设约束为 $x_i \supseteq f_i(x_{j_1}, \dots, x_{j_m})$，整体写成向量方程：

$$
\vec x \ \supseteq\ F(\vec x)
$$

其中 $F$ 是把所有约束右侧「并起来」的单调函数。**约束系统的解 = $F$ 的前不动点；最小解 = $F$ 的最小不动点 $\text{lfp}(F)$**。计算它仍是第三节的迭代：从 $\bot$ 出发，反复应用 $F$ 直到稳定。

但对具体约束系统，有个更图论的看法：把「约束依赖」画成图——节点是程序点/变量，边 $y \to x$ 表示「$x$ 的约束从 $y$ 收取信息」。求解就变成**图上沿依赖边的闭包计算**：

- 若依赖图无环：按拓扑序一趟传播即可。
- 若依赖图有环（指针分析几乎必有环，如 `x = y; y = x`）：迭代到不动点。

指针分析的经典求解器（如 Andersen 的算法）正是这样：用「向量的集合并」模拟图上传播，每个变量一个位向量，一条复制语句就是一次「把 $y$ 的位集并入 $x$」的位或运算。<span class="marginnote">Andersen（1994）与 Steensgaard（1996）的指针分析是两种精度的代表：Andersen 逐条约束并、精度高；Steensgaard 合并约束图、近乎线性但精度低。它们一个是我们说的「精确但慢」，一个是「快但粗」——精度-代价光谱在指针分析里同样上演。</span>

**易错点：** 字段敏感（field-sensitive）分析要区分 `x.f` 与 `x.g`，每个对象每个字段单独记 pts 集；流敏感分析则要区分不同程序点。**约束系统只定义了「怎么算」，不定义「算多细」**——粒度由你建模的字段、流、路径敏感性决定。

## 3 类型推导：约束分析的另一个主场

基于约束的分析不止用于指针，**类型推导（type inference）** 是它的经典主场。以 Hindley–Milner 类型推导（ML、Haskell 的类型系统）为例：

每个表达式引入一个类型变量 $\tau$。
语言规则翻译成类型约束。函数应用 `f x`：$\tau_f = \tau_x \to \tau_{fx}$（$f$ 的类型是「参数类型到结果类型」）。加法 `a + b`：$\tau_a = \tau_b = \mathrm{int}$。
- 求解约束系统：用**合一（unification）** 算法逐步替换类型变量，直到所有约束满足。

**合一**是类型约束求解的核心：方程 $\tau_1 = \tau_2$ 把两个类型统一——若都是类型变量，就替换一个；若都是构造类型（如 `List`），则递归统一各成分；若矛盾（`int = bool`），类型推导失败。<span class="marginnote">这里与第三级《程序设计语言理论》的 ML 类型系统直接呼应：Hindley-Milner 的多态类型推导，本质就是把「程序良类型」翻译成一组可满足的约束方程。类型系统的「静态性质」在基于约束的观点下，就是「约束可满足」。</span>

**区别**：指针分析的约束是「⊇ 单调」，类型推导的约束是「= 等式」。前者用不动点迭代，后者用合一替换。两者都是「建约束 → 求解」，但代数结构不同——这也解释了为什么它们分属 Nielson 教材的不同章节。

### 约束系统与数据流框架的统一

敏锐的读者会发现：数据流框架（第 5 节）与基于约束的分析（本节）惊人地相似。它们其实是**同一枚硬币的两面**：

**数据流方程也是约束系统**。回忆向前数据流方程：

$$
OUT[n] = f_n(IN[n]), \qquad IN[n] = \bigsqcup_{p \in \mathrm{pred}(n)} OUT[p]
$$

把它展开成「每个程序点一个变量、每条更新一条等式」的约束系统，求解就是同一套不动点迭代。**区别只在于组织方式**：

- 数据流框架强调**图结构**：信息沿 CFG 的边流动，汇合点在节点上。
- 约束系统强调**关系**：每个变量的信息由「它依赖谁」的约束决定，不关心物理的「流」。

**何时用哪个视角**：当分析的依赖结构恰好与 CFG 重合（活跃变量、到达定值），数据流视角更直观；当依赖结构偏离 CFG（指针的字段图、类型变量之间的等式），约束视角更自然。**很多分析（尤其过程间分析）用数据流框架建模会别扭，换成约束系统就清晰了**——这就是为什么现代分析框架（如 Doop、JSA）以约束/Datalog 风格为主。

**易错点：** 别被「约束系统」的名字误导以为它不能处理循环。约束可以互相引用（$x \supseteq y$ 且 $y \supseteq x$），形成环——求解仍用不动点迭代，环只会让迭代多转几轮，不会让求解失效。**约束的图有环，正是它建模循环/递归的渠道。**

### Datalog：把约束分析变成数据库查询

基于约束的分析有一个极致的工程化形态：**Datalog**。Datalog 是一种逻辑编程语言（Prolog 的子集），每条规则形如「若前提全真则结论真」，语义就是「求最小不动点」。

指针分析用 Datalog 写，是把约束规则翻译成 Datalog 规则：

```
pts(X, N) :- assign(X, Y), pts(Y, N).   // 复制
pts(X, N) :- new(X, N).                  // 分配
```

求解器（如 Soufflé、bddbddb）把 Datalog 程序编译成高效的数据库查询（关系代数、半朴素求值），能处理百万级变量的指针分析。<span class="marginnote">Datalog 指针分析的代表是 Doop（耶鲁大学 Bravenboer & Smaragdakis，2009）：把 Java 指针分析写成几十条 Datalog 规则，靠 Soufflé 引擎获得「可声明、可复用、性能可接受」的分析器。它把「分析即约束」推进到「分析即数据库查询」——这是程序分析工业化的一条重要路线。</span>

**Datalog 的价值**：分析规则与求解引擎彻底解耦——换规则就是换分析，引擎不变；规则可以组合、演进，支持增量维护。**代价**：表达力受限（Datalog 的递归受限、不支持某些高阶构造），且数据库引擎的开销可能高于手工位向量实现。

## 4 公式解析：约束系统的最小解

把约束分析的求解写成统一形式。设变量集合 $X$，约束系统为每个 $x_i$ 一条下界约束，整体是前不动点方程：

$$
\vec x = \text{lfp}\left( \lambda \vec x .\ \Big( f_1(\vec x), f_2(\vec x), \dots, f_n(\vec x) \Big) \right)
$$

对这条式子做三步拆解：

- **第一步，看右侧**：$\lambda \vec x . (f_1, \dots, f_n)$ 是「把信息向量整体映射成新向量」的函数，第 $i$ 分量按约束 $x_i \supseteq f_i$ 计算。因为右侧是各约束的并，它是单调的。
- **第二步，看 lfp**：最小不动点 = 「从 $\bot$ 迭代、取最小满足所有约束的向量」。由于约束是「⊇」（下界），最小解恰好是「信息最少 = 最精确」的解——不多装任何没被约束要求的指向。
- **第三步，看正确性**：任何满足约束的实际信息 $S$ 都满足 $F(S) \subseteq S$（前不动点），而最小不动点满足 $\text{lfp}(F) \subseteq S$——**分析的最小解被所有合法信息包含，是最保守的结论**。
