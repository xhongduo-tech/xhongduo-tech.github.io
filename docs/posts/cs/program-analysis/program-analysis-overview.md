## 为什么从「让机器理解程序」开始

从前几级的学习里，我们已经熟悉了编译器如何把高级语言翻译成机器码：词法、语法、语义分析，再到代码生成。但编译器为什么要长成那样？答案藏在**程序分析（program analysis）**里——编译器要做优化，必须先知道程序的性质；安全工具要找出漏洞，也必须先知道程序的性质。<span class="marginnote">这条线索从第三级《编译原理》延伸而来：编译器的中间表示、优化遍（pass）就是程序分析最早的工业应用；而到第四级，抽象解释与符号执行又会与形式化方法汇流，成为验证大模型推理链路的前提。</span>

**程序分析（program analysis）**：在程序源码或其中间表示上，自动化地推断程序性质（property）的一整套理论、方法与工具的总称。它回答的问题是「这个程序在**所有**可能的执行下表现如何」——注意是「所有」，这正是它与普通测试最本质的区别。

本章是这门学科的入口。我们先看清程序分析要解决什么、分成哪些流派、用在哪些地方，再在后续章节逐个把工具——格论、数据流、抽象解释、符号执行——装进工具箱。

## 1 目标：不可判定性阴影下的三座灯塔

程序分析面临一个根本的坏消息：**程序的所有非平凡性质都是不可判定的**。这是莱斯定理（Rice's Theorem）的结论——任何关于程序语义的非常识性质，都不存在对一切程序都停机且正确的判定算法。<span class="marginnote">莱斯定理是停机问题的推论：若存在算法能判断「程序 $P$ 是否具有性质 $\Phi$」，就能用它判断停机，矛盾。所以「完全精确的程序分析」在理论上就不存在。</span>

既然完美做不到，程序分析就退而求其次，瞄准三种可计算的近似，构成它的三座灯塔：

**完备但可能误报（soundness-first）**：分析只报告「确定会发生」的问题，宁可漏报（false negative），绝不误报（false positive）。编译器优化走这条路线——把一个真的会被执行的赋值删错是灾难，而漏删一个可删的赋值只是少了一次优化。

**可靠但可能漏报（completeness-first）**：分析保证不漏掉任何真问题，宁可多报（误报），绝不漏报。安全漏洞扫描走这条路线——一个真实漏洞被漏掉是安全事故，而多几个假警报只是让工程师多花时间人工甄别。

**工程折中**：在两者的张力之间，用精度换速度、用启发式换可判定性，找到一个「够用」的平衡点。

**易错点：** 「sound」与「complete」的中文翻译容易打架。**sound（健全/可靠）**指的是「凡报告的皆真实」，**complete（完备）**指的是「凡真实的皆报告」。静态分析工具宣传「零漏报」是谈完备性，「零误报」才是谈健全性，两者不可兼得。

## 2 分类：一条沿着精度轴的地图

程序分析不是单一技术，而是一族在「精度—效率—自动化」三维空间里各占位置的方法。沿着分析对象与分析方式，可以画出两条主要分界线。

### 按分析对象：源码 / 中间表示 / 二进制

分析可以直接作用在源码上（如许多 lint 工具）、作用在编译器的中间表示上（如 LLVM IR、Java 字节码），也可以作用在二进制上（如逆向工程的僵尸扫描）。对象越底层，信息越具体，但结构性信息越少。<span class="marginnote">二进制分析属于第三级《逆向工程与二进制分析》的地盘，但程序分析的思想一以贯之：不过把控制流图从源码级换成了指令级。</span>

### 按分析方式：静态 / 动态 / 混合

**静态分析（static analysis）**：不运行程序，直接在程序文本上做推理。它覆盖所有执行路径，但代价是必须用抽象近似不可判定性。

**动态分析（dynamic analysis）**：实际运行程序，观察真实的执行轨迹。它精确但只覆盖被跑到的路径——未执行的代码对它而言是黑箱。

**混合方法**：动态符号执行（concolic execution）、插桩采样等方法试图兼取两者之长。<span class="marginnote">一条贯穿课程的主线：静态与动态不是敌人，而是同一问题轴上的两端。第四篇《动态符号执行》会展示它们如何融合。</span>

### 按分析粒度：流不敏感 / 流敏感 / 路径敏感

这是精度轴上最常用的一把尺子：

**流不敏感（flow-insensitive）**：无视语句的执行顺序，把所有信息当作一个全局集合来算。快，但粗糙。

**流敏感（flow-sensitive）**：考虑语句顺序，为每个程序点维护独立的信息。数据流分析即此类。

**路径敏感（path-sensitive）**：进一步区分不同控制流路径，能回答「这条分支下变量是什么」。符号执行即此类。

| 维度 | 流不敏感 | 流敏感 | 路径敏感 |
| --- | --- | --- | --- |
| 是否区分执行顺序 | 否 | 是 | 是 |
| 是否区分不同路径 | 否 | 否 | 是 |
| 典型代表 | 指针分析的别名集合 | 活跃变量、到达定值 | 符号执行 |
| 复杂度 | 最低 | 中 | 最高 |

## 3 应用：从优化到安全验证

程序分析的应用横跨三个战场，值得在入门时看清全貌：

**编译器优化**：活跃变量分析决定哪些寄存器可以被释放，到达定值分析支撑常量传播，可用表达式分析支撑公共子表达式消除。这是程序分析最成熟的工业阵地，也是第二篇的主体。

**软件验证与安全**：抽象解释被用来证明数组越界不会发生（如法国的 Astree 工具验证航空控制软件），符号执行与污点分析被用来在开源代码里自动寻找漏洞（如可执行文件的模糊测试）。这是第三、四篇的主体。

**程序理解与重构**：程序切片把「影响某个变量的代码」从整个程序里剥出来，依赖分析帮助工程师安全地重构与并行化。这些技术贯穿全专题。

### 从工具看全景：三款代表性分析器

抽象的分类容易空泛，看三个具体工具，全景立即落地：

**GCC 的 `-fanalyzer`**：编译器内建的静态分析器，走「过程间 + 路径敏感」路线。它在源码上做符号执行式的探索，报告越界、空指针、内存泄漏。它的意义在于：**分析从「优化器的附庸」变成了「编译器自带的安检」**——不装任何外部工具就能跑。

**Clang Static Analyzer**：LLVM 生态的路径敏感分析器，按「bug 模式」组织——每个模式（`alpha.security.*` 等）是一组源-汇规则，底层是符号执行引擎 + 约束求解。它展示了程序分析的**模块化**：分析框架与 bug 模式解耦，新增一种漏洞只需写一套规则。

**GitHub CodeQL**：把整个代码库建成可查询的数据库，用类似 SQL 的 QL 语言写「污点查询」找漏洞。它把程序分析变成了**声明式查询**——分析器是数据库，分析是查询。大型代码库上的安全扫描大多用它。

三款工具横跨「编译期内建」「IDE 分析」「代码扫描平台」，正好对应程序分析的三条产业化路径：**与编译器融合、与开发流程融合、与供应链安全融合**。

### 学完本章你该带走什么

在进入后续章节之前，把这一节的「地图」浓缩成三个可带走的心智模型：

**第一，程序分析是「在不可判定里做安全近似」**。莱斯定理决定完美不可得，于是健全/完备的二选一是分析设计的起点。每当你看到「分析结果」，先问它是「sound（凡报告的皆真）」还是「complete（凡真的都报）」。

**第二，分析的精度是一个三维坐标**：流敏感（区分顺序）、路径敏感（区分路径）、上下文敏感（区分调用环境）。任何分析工具都可以用这三个维度定位，也都可以沿任一维度加深来提高精度。

**第三，分析服务于三种消费者**：编译器要「敢优化的依据」，安全工具要「不敢保证的提醒」，程序员要「理解程序的捷径」。同一个技术，服务的消费者不同，精度与代价的取舍就不同。

这三条将贯穿本专题的每一篇——格论给它数学，数据流给它算法，抽象解释给它理论，符号执行给它实践。

一个帮助记忆的定位：**程序分析 = 在「不可判定」的墙上挖「够用的窗」**。编译器要的窗是「我敢据此优化」，安全工具要的窗是「我不敢说这里绝对安全」。窗的大小由下面的近似方法决定，而这正是整门学科的工作。

## 4 公式解析：近似分析的不动点观

程序分析在数学上可以统一地写成**不动点**的语言。设分析对象是程序点集合上的一个信息集合，用一个偏序集 $L$ 描述（信息越靠上越精确，见《格论基础》），程序中的每条语句对应一个传递函数 $f: L \to L$，它描述「执行这条语句后，已知信息如何演化」。

程序执行的语义就变成一个函数方程：程序入口的信息 $x_0$ 经各条语句逐步传播，最终稳定在满足下式的点 $x^*$：

$$
x^* = F(x^*), \qquad F = f_1 \circ f_2 \circ \cdots \circ f_n
$$

这里 $F$ 是把所有语句的传递函数按控制流复合起来的整体函数。**程序分析算法，本质上就是求解这个不动点方程 $x^* = F(x^*)$ 的迭代过程**。对这条式子做三步拆解：

- **第一步，读懂 $F$ 的复合**：$f_1 \circ f_2$ 表示先执行语句 1 再执行语句 2 的信息演化；$F$ 把整个程序压缩成一个函数，把「程序」变成了「函数」。
- **第二步，理解不动点**：$x^* = F(x^*)$ 说「信息传播到 $x^*$ 后不再改变」。这是分析的终止条件——迭代到信息稳定，就是分析收敛。
- **第三步，明白为什么可行**：当 $L$ 是完备格、$F$ 是单调函数时，塔斯基不动点定理保证不动点存在且可迭代逼近。这就是为什么下一章必须先把格论讲透——**格论不是程序分析的装饰，而是它的数学地基**。

## 5 小结

- **程序分析**在不可判定性（莱斯定理）的约束下工作，必须选择**健全性**或**完备性**之一作为近似策略。
- 按分析方式分为**静态、动态、混合**；按精度分为**流不敏感、流敏感、路径敏感**。
- 应用横跨**编译器优化、软件验证与安全、程序理解与重构**三个战场。
- 分析的数学本质是**不动点方程** $x^* = F(x^*)$
