## 为什么从反汇编开始

上一节我们在调试器里看程序逐条执行，但调试器展示的汇编是从哪来的？答案藏在反汇编（disassembly）里：把机器码字节翻译成人类可读的汇编指令。看似只是「查字典」，实际上是个暗藏陷阱的工程——x86 的指令是变长的，同一个字节序列从不同位置开始读，会得到完全不同的指令流。<span class="marginnote">迪杰斯特拉痛恨无节制的 goto，恰恰是因为控制流跳转让程序难以读懂；而逆向工程的第一场硬仗，正是把「到处乱跳」的机器码还原成可以读懂的控制流——某种意义上，我们是在和迪杰斯特拉做相反的工作。</span>

这一节也是后面所有动态技术的地基：脱壳要定位 OEP，模糊测试要理解崩溃地址，符号执行要构建路径条件，全都建立在「先恢复控制流」之上。

## 1 从机器码到汇编：x86 指令的形态

一条 x86 指令由若干字节组成，大致结构是：**操作码（opcode）+ 操作数字段（modrm、sib、立即数、位移）**。`89 e5` 是 `mov ebp, esp`，`83 c4 08` 是 `add esp, 8`。问题在于操作码的边界不是对齐的——`c4 08` 单独读是 `les` 指令的操作码，而放在 `83 c4 08` 里是 `add` 的立即数。**同样的字节，起点差一个，语义天差地别**——这就是反汇编器最大的敌人：它不知道指令从哪儿开始。<span class="marginnote">反汇编是「把二进制翻成汇编」；而本专题后面《加壳、脱壳与混淆》里的花指令（junk code），就是恶意地利用这个歧义，往真实指令流里塞进一些永远不会被执行、但会带歪反汇编器的字节。</span>

## 2 两种反汇编策略：线性扫描与递归下降

### 2.1 线性扫描（Linear Sweep）

从段起始地址开始，**逐字节顺序解码**：读一条指令，按长度跳到下一条，直到段尾。`objdump` 就是这种。它快、无脑，但**一旦数据混在指令里（常见于跳转表和字符串），后续对齐全错**，一错到底。

### 2.2 递归下降（Recursive Descent）

只在**确定是代码入口**的位置开始反汇编，遇到分支指令时**顺着每个目标地址继续**，遇到不改变控制流的指令则顺序跟进。<span class="marginnote">IDA Pro 默认采用递归下降，这也是它「识别函数」的方式：函数入口 + 可达的每个分支，共同拼出函数边界。被带偏的对齐错误，在递归下降里是局部而非全局的。</span>代价是：间接跳转（`jmp [table+rax*4]`）的目标在运行时才知道，递归下降无法静态跟进，只能停下来等人工处理或等动态信息补充。

## 3 控制流图：把跳转画成图

反汇编得到的裸指令序列仍然难读，真正的「控制流恢复」是把指令组织成**控制流图（CFG，Control Flow Graph）**。节点是**基本块（basic block）**——一段「只有一个入口、一个出口、内部无跳转」的连续指令；边是块与块之间的跳转关系。

以一段典型的条件判断为例（对应右图）：<span class="marginnote">基本块判定的口诀：指令序列里，前一条是跳转/调用、或后一条是跳转/调用目标，就切一刀。反汇编器、编译器优化、符号执行全都在和基本块打交道。</span>

```
0x401000:  mov eax, [rsp+8]
0x401004:  test eax, eax        ; 比较，置标志
0x401006:  jz  0x401020         ; ZF=1 则跳走（条件分支）
0x401008:  add eax, 1           ; 顺序执行（fallthrough）
0x40100b:  mov [rsp+8], eax
0x40100e:  jmp 0x401025         ; 无条件跳转
0x401020:  mov eax, 0           ; 另一个分支的入口
0x401025:  ret
```

这 8 条指令会被切成 4 个基本块：`0x401000`（到 `jz` 前为止）、`0x401008`（顺序执行到 `jmp`）、`0x401020`（分支目标）、`0x401025`（`ret` 结尾）。边就是 `jz` 的两个目标：一个是 fallthrough 的 `0x401008`，一个是 `0x401020`。**CFG 一画出来，程序的骨架就现形了**：条件分支在图上分叉成两个出口，循环在图上呈现为回到头部的回边，函数调用则连接两个不同的图。

### 3.1 工具里的三种 CFG 形态

同一个 CFG，在不同工具里以三种粒度呈现，逆向时要会切换：

**函数级 CFG**：IDA 的 Graph View 把每个函数画成一张图，条件分支分叉、循环成环——读一个函数先看它的「图长得像什么」：线性函数一眼看穿，嵌套判断一望便知复杂度；<span class="marginnote">IDA Graph View 是「图脑」的入口：花几十秒浏览整图结构，胜过逐行读几百条指令。图里「大片方块中间一个小菱形」= 一个简单的 if；「稠密回边」= 循环；「一个方块连出十几条线」= switch 跳转表。</span>
- **调用图（call graph）**：把函数当节点、调用当边，俯瞰整个程序的分工；恶意代码的调用图往往有「明星节点」（被四处调用的函数），那通常是解密器或编码器；
- **支配树（dominator tree）**：CFG 的代数化——`d 支配 b` 意味着「任何到 b 的路径都必经 d」。支配关系是编译器优化的地基，也是分析「哪段代码必然先于另一段执行」的数学工具，在符号执行（本专题最后一节）里它直接指导路径搜索的优先级。

## 4 公式解析：相对跳转的目标地址

条件跳转指令（如 `jz`）的机器码里存的是一个**有符号相对位移**，目标地址这样算：

$$
\text{target} = \text{next\_addr} + \text{disp8}
$$

其中 `next_addr` 是**跳转指令下一条指令的地址**，`disp8` 是紧随操作码的 1 字节有符号偏移量。分三步拆解：

- **第一步，理解 next_addr**：CPU 取完指令后，`rip`（x86-64）已经指向下一条指令。相对跳转的基准是「下一条指令」而非「跳转指令本身」，这是初学者最容易算错的点。
- **第二步，看 disp8 的正负**：`disp8` 是补码表示的有符号数，正数向前跳（往高地址），负数向后跳（往低地址）——循环体里往回跳的 `jz` 就是负数。
- **第三步，翻译到 CFG**：这条式子给出的 `target`，正是上节 CFG 里「分支边」指向的另一个基本块入口。反汇编器对每条跳转指令做一次这个计算，就得到全部边。

反汇编器与调试器在每一处跳转上都重复这个「基准 + 偏移」的计算，把指令流变成图——**控制流恢复的本质，就是把这个算术做对、并正确决定哪些地址算作基本块入口**。

## 5 反汇编的失败模式与应对

**辨析｜易错点：** 反汇编不是万能的，三种情况会让它失效：

- **数据与代码混合**：跳转表、内嵌字符串被线性扫描误读成指令，整段错位。应对：递归下降 + 人工标注数据。
- **间接跳转**：`jmp [table+idx*4]` 静态无目标。应对：靠运行期观察（动态调试）或约束求解（符号执行）补充。
- **自修改代码与多态**：程序运行期改写自身指令，磁盘上的字节根本不是执行时的字节。应对：动态调试、在内存里反汇编（本专题《加壳、脱壳与混淆》《二进制插桩与符号执行》分别给出两种路线）。

还有一层更隐蔽的失败：**反汇编正确 ≠ 语义正确**。还原出 `mov eax, 0x8040000` 很容易，但要知道这是个字符串地址、还是段基址、还是被拆开的立即数，需要符号信息——这正是下一步（符号表、重定位、调试信息）的作用，也是《ELF/PE 文件格式解析》要补的功课。

## 6 小结

- **反汇编 = 把机器码翻成汇编**；x86 变长指令导致「从哪儿开始读」成为核心难题。
- 两种策略：**线性扫描**（顺序解码，遇数据易错位）与**递归下降**（跟随分支目标，IDA 默认）。
- **控制流图 CFG**：基本块为节点、跳转为边；基本块的切分标准是「一个入口一个出口」。
- **相对跳转** $\text{target} = \text{next\_addr} + \text{disp8}$，基准是下一条指令，偏移是补码。
- 三种失败模式：数据/代码混合、间接跳转、自修改代码；应对分别靠人工标注、动态观察、内存反汇编。

在下一节，我们从「指令流」回到「文件本身」——把 ELF 与 PE 这两种可执行文件格式从字节层面彻底解剖，因为一切控制流、导入表、节区的认识最终都要落回文件格式上。
