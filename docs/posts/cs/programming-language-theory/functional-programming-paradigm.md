## 为什么从函数式范式开始

巴科斯在 1977 年图灵奖演讲里向「冯·诺依曼风格」——逐条指令、靠赋值改变状态——发起挑战，为一条更古老也更抽象的路辩护：**把计算当作函数求值**。这条路的源头正是本专题第一课的 λ 演算，而它的现代化身（Lisp、ML、Haskell、Scala、F#、Kotlin 的柯里化与 `map/filter/reduce`）已深深渗入所有主流语言。Sebesta《程序设计语言概念》第 15 章把「函数式语言范式」当作一种独立的思考方式来讲：**纯函数、引用透明、高阶函数、惰性求值**。理解它，就理解了「数据不可变」为何成为现代系统设计的关键词。

## 1 范式：计算是函数的求值

**函数式范式（functional paradigm）**：程序由**纯函数**（给定输入、返回输出、无任何副作用）与**函数应用**构成，计算即对函数表达式的求值。它从 λ 演算继承了核心承诺——**引用透明（referential transparency）**：表达式可以随时被它的值替换而不改变程序行为。`2 + 3` 在任何上下文里都是 `5`；`length xs` 只要 `xs` 不变就永远是同一个数。

**辨析｜易错点：** 引用透明与「命令式」的冲突点在于**赋值**。命令式程序 `x = x + 1` 是非透明的——同一个 `x` 在赋值前后值不同，表达式 `x` 无法被一个固定值替换。<span class="marginnote">「不可变」是这个范式的肌肉记忆：函数式语言里变量一经绑定不再改变（Haskell 根本没有赋值，ML 里 `val` 只绑一次）。这正是《操作语义》里提到的「可换性」的实现形态，也是编译器与 CPU 能放心并行/缓存的前提。</span>巴科斯把这种风格叫作「代数式」：程序像代数表达式一样可以化简、可以证明相等。

## 2 一等函数与高阶函数

函数式语言的引擎是**一等函数（first-class function）**：函数像数值一样可被传递、返回、存进数据结构。由此派生出**高阶函数（higher-order function）**——接受函数为参数或返回函数。列表处理三件套是它的名片：

$$\texttt{map}\,f\,[x_1, \dots, x_n] = [f\,x_1, \dots, f\,x_n]$$
$$\texttt{filter}\,p\,xs = \text{保留 } xs \text{ 中满足 } p \text{ 的元素}$$
$$\texttt{foldl}\,(\oplus)\,z\,[x_1, \dots, x_n] = ((z \oplus x_1) \oplus x_2) \cdots \oplus x_n$$

**重点：** `map`/`filter`/`fold` 把「对列表做遍历」这个通用骨架固定下来，程序员只提供「每步干什么」的函数——**把循环的控制流抽象成数据**。这是「循环」在函数式世界的继承者：`fold` 一族承载了几乎所有遍历算法，而 `map`/`filter` 是 `fold` 的著名特化。<span class="marginnote">Python 的 `map/filter/reduce`、Java 的 `Stream`、Kotlin 的 `map/fold` 都是这套三件套的移植。区别只在：函数式语言里「函数即值」是默认，而命令式语言需要 `lambda`/`函数指针` 显式抬一手。</span>配合第一课的柯里化与《参数传递与作用域》的闭包，一个函数式程序可以像搭积木一样由高阶函数组装而成——这正是「组合优于继承」的源头。

## 3 递归、模式匹配与惰性求值

循环的另一个继承者是**递归**。链表求和、树的遍历、`fold` 本身，都用递归定义——函数式语言的编译器会做**尾调用优化（tail-call optimization）**，把「尾位置的递归」编译成跳转，避免栈溢出，于是递归在性能上不输迭代。搭配**模式匹配**，数据结构被「按形状」解构：空表怎么处理、非空表怎么处理，写在一处，清晰如数学归纳法。

**惰性求值（lazy evaluation）**是 Haskell 的招牌：表达式只在被需要时求值，且至多一次（这就是《参数传递与作用域》的 by-need 传递在范式层面的放大）。它带来了两个惊喜：**无限数据结构**——`fibs = 0 : 1 : zipWith (+) fibs (tail fibs)` 定义了斐波那契的无限流，用到哪算到哪；以及**分离「构造」与「消费」**——程序可以先生成无穷的候选、再让消费者按需取用，不必事先想清楚边界。<span class="marginnote">惰性的代价是求值顺序难以预测，实时交互（I/O）需要专门的机制。Haskell 用 <strong>Monad</strong>（单子）把「有副作用的计算」做成显式的、带类型的管道——I/O 动作是普通值，可以被组合、被传递，但副作用只在动作被「执行」时发生。这让 Haskell 保持纯函数内核，又拥有真实 I/O 能力，是「纯函数 + 显式副作用」设计哲学的极致。</span>

## 4 函数式 vs 命令式：一张对照表

| 维度 | 函数式 | 命令式 |
| --- | --- | --- |
| 计算的本质 | 函数求值 | 语句改变状态 |
| 状态 | 不可变绑定 | 可赋值变量 |
| 引用透明 | 始终成立 | 赋值处破坏 |
| 循环 | 递归 / fold | for / while |
| 错误处理 | 类型 + 显式结果（`Maybe`/`Result`） | 异常 |
| 并行安全 | 天然无数据竞争 | 需锁 |
| 理论根基 | λ 演算 | 图灵机 / 状态机 |

**重点：** 函数式的优势来自「状态越少、越不容易错」：无共享可变状态，就无数据竞争；引用透明，就可在意何处并行、何处缓存、何处证明正确性。代价是学习曲线与 I/O 复杂度——所以现代语言普遍取「混合」路线：用不可变与高阶函数写核心逻辑，把可变状态围在边界。<span class="marginnote">回到《对象与封装》：对象与函数式看似对立，实则互补——对象封装可变状态，函数式消灭可变状态；现代语言（Java 记录 + Stream、Kotlin data class + 函数 API）正是两者的合流。所谓范式，不是「只能用一个」，而是「知道每个的边界在哪」。</span>

## 5 公式解析：fold 拆开循环的骨架

以 `foldr`（右折叠）为例，把「循环」翻译成代数：

$$
\texttt{foldr}\,(\oplus)\,z\,[x_1, x_2, \dots, x_n] = x_1 \oplus (x_2 \oplus (\cdots (x_n \oplus z)\cdots))
$$

- **二元运算 $\oplus$**：用户提供的「每步」——这是循环体里真正有变化的部分。
- **初值 $z$**：折叠的「起点」，对应循环变量的初值；空表时 `foldr (⊕) z [] = z`——**base case 决定了对空表的处理**。
- **右结合结构**：`foldr` 先把列表**最右端**的 $x_n$ 与 $z$ 结合，再向左套——它能处理无限列表（因为 $x_1 \oplus (\dots)$ 只要求惰性地知道右侧）；`foldl` 则是从左往左结合、依赖整个列表，且更贴合命令式累加。
- **直觉**：`foldr` 是「把列表中的 `:` 全部换成 $\oplus$、把 `[]` 换成 $z$」——**列表的构造器被替换成运算，折叠是对列表结构的「同态映射」**。这个视角让 `fold` 不再神秘：它不过是把「数据怎么建」原样翻译成「数据怎么算」。

## 6 小结

- **函数式范式**以纯函数与函数应用为中心，核心承诺是**引用透明**——表达式可被其值替换。
- **一等函数与高阶函数**让 `map`/`filter`/`fold` 把循环骨架抽象成数据；柯里化与闭包来自第一课与《参数传递与作用域》。
- 递归 + **尾调用优化**取代循环；**惰性求值**支持无限结构，Haskell 用 **Monad** 把 I/O 做成显式带类型的管道。
- 函数式 vs 命令式的分野在「状态」：不可变绑定消灭数据竞争，代价是学习曲线。
- 现代语言普遍混合二者：不可变核心 + 边界可变状态。

在下一节，我们把「计算 = 求值」换成另一个大胆的视角——计算 = 证明，程序 = 逻辑前提，这就是**逻辑编程范式 Prolog**。
