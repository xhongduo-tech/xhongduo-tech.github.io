## 为什么从递归类型开始

上一课《对象与封装》留了一道悬案：方法要引用「自己」，就得有能指回自身的类型。可类型怎么长得像自己？答案是一个让类型拥有「自我引用」能力的构造：**递归类型（recursive type）**。它远不止服务对象——链表、树、流、JSON 值、Haskell 的 `data`、Rust 的枚举，底层全是它。皮尔斯在《类型与程序设计语言》§20 用一个希腊字母 $\mu$ 给了它最经济的形式：$\mu X.\,T$ 读作「满足 $X = T$ 的 $X$」。本课讲 $\mu$ 类型的形式规则、折叠与展开，以及等递归与异构递归的两种实现哲学。

## 1 递归类型：让类型指回自己

考虑「自然数链表」：一个链表要么是空，要么是一个「自然数 + 一条链表」。直觉上它的类型应写成 $X = \langle \texttt{nil}: \texttt{Unit},\; \texttt{cons}: \{\texttt{Nat}, X\} \rangle$——可 $X$ 出现在等号两边，这正是**递归定义**。把它记作：

$$\texttt{NatList} = \mu X.\,\langle \texttt{nil}: \texttt{Unit},\; \texttt{cons}: \{\texttt{Nat}, X\} \rangle$$

**递归类型（recursive type）**：形如 $\mu X.\,T$ 的类型，它表示「满足『把自己展开成 $T$』的那个类型」。$X$ 在 $T$ 中自由出现的位置，就是「再递归一层」的位置。链表的直觉验证：$\texttt{NatList}$ 的展开 $T[\texttt{NatList}/X]$ 正是「要么 nil，要么 (Nat, NatList)」——和我们的直觉完全吻合。<span class="marginnote">$\mu$ 是「最小不动点」符号（来自域论）。类型层面的 $\mu$ 与第一课 λ 演算的 Y 组合子（值层面的不动点）是孪生兄弟：Y 造「递归函数」，$\mu$ 造「递归类型」，合起来让「数据结构 + 递归算法」都有了形式基础。</span>

**递归类型回答的问题**：普通类型（$\texttt{Nat}$、$\texttt{Bool}$、$\texttt{Nat}\to\texttt{Bool}$）都不含「自指」，而链表、树天然需要「一个结点里还能放同类结点」。λ 演算用 Y 组合子在**值层面**造递归函数，类型层面则需要自己的 Y——$\mu$ 就是这个「类型的 Y 组合子」。值得记下这个对应：**值层面的递归靠不动点组合子，类型层面的递归靠 $\mu$ 类型**，两者共享同一个「自我指涉」的骨架。

## 2 折叠与展开：递归类型的开关

$\mu X.\,T$ 与它的展开 $T[\mu X.\,T / X]$ 可以互相转换，转换工具是两个操作符：

- **折叠（fold）**：$\texttt{fold}[X]\,(t)$——把「一层展开」的项 $t: T[\mu X.\,T/X]$ 包装成类型 $\mu X.\,T$ 的项。
- **展开（unfold）**：$\texttt{unfold}[X]\,(t)$——把 $\mu X.\,T$ 类型的项 $t$ 拆回它的一层展开 $T[\mu X.\,T / X]$。

**用 fold 造、用 unfold 拆**：要建一个 cons 单元，先折叠；要用一个 cons 单元，先展开拿到 `{Nat, NatList}` 再取字段。这组操作让递归类型成为一个「有界的开关」——**任何使用都必须先 unfold 一层，任何构造都必须 fold 一层**，递归由此受控地进行，不会无限展开。C 里要手动写链表指针、OCaml 里用 `Cons (1, l)` 这种构造子、Haskell 里写 `data NatList = Nil | Cons Nat NatList`——这些语法糖的背后都是同一对 fold/unfold。

**一个具体的构造与消费链**：造链表 `[1, 2]`，先造内层对 `{1, Cons(2, Nil)}`，`fold` 一次得到 `NatList`；要读第一个元素，`unfold` 一层取出 `head = 1` 与 `tail`，对 `tail` 再 `unfold` 继续前进。整个过程里，「造一层」对应一次 `fold`、「走一层」对应一次 `unfold`——递归的每一次进出都显式地发生在这两扇门之间，这也解释了为什么遍历链表总写成「unfold、取字段、对 tail 递归」的三步循环：三个动作恰好对应三条规则。

## 3 两个例子：自然数与流

递归类型能编码的不只是有限结构。自然数本身：

$$\texttt{Nat} = \mu X.\,\langle \texttt{zero}: \texttt{Unit},\; \texttt{succ}: X \rangle$$

「3」就被编码为 `succ(succ(succ(zero)))`——**自然数 = 要么零，要么一个自然数的后继**，这是皮亚诺公理在类型里的投影。更妙的是**流（stream）**：

$$\texttt{Stream} = \mu X.\,\langle \texttt{head}: \texttt{Nat},\; \texttt{tail}: X \rangle$$

$\texttt{tail}$ 返回的还是 $\texttt{Stream}$，于是流可以无限地展开——`1, 2, 3, 4, …` 不用事先建完，用到哪展开到哪。<span class="marginnote">这暴露了递归类型的两个世界：<strong>归纳型（inductive）</strong>以「最小不动点」为准——链表必须有尽头，递归必须向 base case 收敛；<strong>余归纳型（coinductive）</strong>以「最大不动点」为准——流可以永远展开下去。皮尔斯在 §20 用 fold/unfold 把两者统一处理，但两者的编程约定（终止 vs 持续产出）截然不同。</span>Haskell 惰性求值能表示无限列表，正是因为它把递归类型当余归纳型来用。

**三种语言里的同一件事**：OCaml 的 `type nat = Zero | Succ of nat` 里，`Succ(Succ Zero)` 的每一次 `Succ` 都是一次 fold（构造子就是 fold 的语法糖），`match` 解构则自动完成 unfold；Haskell 的 `data Nat = Zero | Succ Nat` 同理，且惰性让它可以把 `Nat` 当无限对象用；Rust 的 `enum List { Nil, Cons(i32, Box<List>) }` 里 `Box` 显式声明「这一层递归放在堆上」——否则编译器会因为类型大小无限而拒绝编译。**构造子 = fold，模式匹配 = unfold，这个对应关系在每种语言里都成立**。

## 4 等递归与异构递归

同一个 $\mu X.\,T$，不同语言选择不同的折叠策略：

- **等递归类型（equirecursive types）**：$\mu X.\,T$ 与它的展开 $T[\mu X.\,T/X]$ 被当作**同一个类型**——类型系统把递归类型看作「无限展开的树」，fold/unfold 只是换了个记号，类型相等判定需要处理无限结构。实现复杂，但书写自由。
- **异构递归类型（isorecursive types）**：$\mu X.\,T$ 与展开是**两个不同类型**，靠显式的 fold/unfold（或构造子）在两个世界之间切换。实现简单、规则整洁，是 OCaml、Haskell、Rust 等主流语言的路线。

**辨析｜易错点：** 多数现代语言是**异构递归**：类型上 `Nat` 与 `Zero|Succ` 并不字面相等，必须通过构造子显式「折叠」。所以「把 $\mu X.\,T$ 直接当 $T[\mu X.\,T/X]$ 用」在等递归系统里合法，在异构系统里就是类型错误——写 Haskell 时 `Nil` 和 `NatList` 的关系是构造子（fold），不是相等关系。**判定一个系统是等递归还是异构递归，只需问：`unfold` 是否需要显式写出？**

两条路线在一张表里对照：

| 维度 | 等递归（equirecursive） | 异构递归（isorecursive） |
| --- | --- | --- |
| μX.T 与它的展开 | 视为同一个类型 | 视为两种类型 |
| 是否需显式 fold/unfold | 不需要（只是记号） | 必须显式切换 |
| 类型相等判定 | 需处理无限树，复杂 | 常规递归判定，简单 |
| 元理论（正规化等） | 困难，需强化论证 | 相对容易 |
| 代表语言 | 部分理论系统与原型 | OCaml、Haskell、Rust、Java |
| 书写体验 | 自由、不用打 fold | 啰嗦但规则干净 |

**工程结论**：主流语言几乎都选异构递归——因为「类型能否相等判定」是可判定类型检查的前提，而等递归的无限树相等判定成本太高。代价是程序员要显式写构造子（fold）；回报是类型检查简单、元理论证明干净。这也解释了为什么「数据结构要靠构造子包一层」成为所有强类型语言的习惯。

## 5 递归类型不是免费午餐

**重点：** 递归类型是有代价的——**不是每个 $\mu X.\,T$ 都「良性」**。形如 $\mu X.\,X \to \texttt{Bool}$ 的「负递归」类型会让类型检查陷入怪圈，甚至与「终止性」「正常形唯一性」冲突。皮尔斯在 §20 末明确：**等递归类型给类型系统的元理论（如进展与保持引理、正规化）带来实质困难**，必须用「无类型展开」的强化论证才能恢复证明——这也是等递归类型虽优雅却少见的原因。工程上，编译器对递归类型都要求「递归发生在构造子位置（正位置）」或做展开深度限制，防止无限循环。

负递归的具体危害：类型 $\mu X.\, X \to \texttt{Bool}$ 展开后是「吃一个自己的函数」，要让一个值既是「函数」又是「参数」，类型论里会与正常形、强正规化冲突；$\mu X.\, X \times X$ 则声称「某类型与自身的笛卡尔积同构」，这在许多语义里与「空类型必须非空」矛盾。编译器通常直接禁止「递归出现在箭头左侧（负位置）」，或要求递归通过 `Box` 等指针间接层——Rust 的 `Box`、OCaml 的 `-rectypes` 开关（默认关闭）、Java 的类间递归，正是这类约束的三种形态。

## 6 公式解析：fold/unfold 两个方向一条线

$$
\frac{\Gamma \vdash t : [X \mapsto \mu X.\,T]\,T}{\Gamma \vdash \texttt{fold}[X](t) : \mu X.\,T}
\qquad
\frac{\Gamma \vdash t : \mu X.\,T}{\Gamma \vdash \texttt{unfold}[X](t) : [X \mapsto \mu X.\,T]\,T}
$$

- **方向一（fold）**：前提里的项 $t$ 已经有一层展开的类型 $T[\mu X.\,T/X]$——它是一个「单层」结构，如 `{Nat, NatList}` 对；结论把它折叠成递归类型 $\mu X.\,T$（即 `NatList`）。**从外层看，fold 是「构造」**：把一个零件组装进递归结构。
- **方向二（unfold）**：反过来，前提里的项 $t$ 是递归类型 $\mu X.\,T$，结论把它展开回一层——**unfold 是「消费」**：先拆掉外壳，才能拿到里面的字段继续前进。
- **替换 $[X \mapsto \mu X.\,T]$**：两处都做了「把 $X$ 换成递归类型本身」——这正是递归的类型学签名：**$\mu X.\,T$ 在它自己的展开里再次出现**，自我指涉由此闭环。
- **用在哪**：链表遍历就是「unfold 到 nil 为止，否则取出 `head`、把 `tail` 递归下去」的循环；流的读取则是「unfold 一次、取 `head`、把新的 `tail` 留在那里」。fold/unfold 是这套循环的全部词汇。

fold/unfold 这组规则的对称性值得记住：fold 的前提在「展开世界」、结论在「递归世界」；unfold 正好相反。**两扇门方向相反、对象互补**——这正是递归类型的代数结构（初始代数 / 终结余代数）在规则层面的投影，也是《范畴论》专题可以接续的接口。

## 7 术语速查

| 术语 | 含义 | 一句话直觉 |
| --- | --- | --- |
| 递归类型 | $\mu X.\,T$，类型能指回自身 | 类型的自我指涉 |
| fold | 把一层展开收进 μ 类型 | 造一层 |
| unfold | 把 μ 类型拆回一层展开 | 走一层 |
| 归纳型 | 最小不动点，递归向 base 收敛 | 有尽头的结构 |
| 余归纳型 | 最大不动点，可无限展开 | 无穷的流 |
| 等递归 | μX.T 与其展开是同一类型 | 不用显式开关 |
| 异构递归 | μX.T 与其展开是两种类型 | 必须显式 fold/unfold |
| 正位置 / 负位置 | 递归出现在构造子 / 箭头左侧 | 良性与病态的界 |

**记忆锚点**：递归类型 = 「类型的 Y 组合子」；fold/unfold = 「进出门的两扇开关」；等递归与异构递归 = 「开关要不要显式按」——三句话串起本课全部内容。

## 8 小结

- **递归类型** $\mu X.\,T$ 让类型指回自身，链表、树、自然数、流全是它的实例。
- **fold / unfold** 是递归类型的两扇门：fold 构造一层，unfold 消费一层，递归由此受控。
- 归纳型（链表、最小不动点）与**余归纳型**（流、最大不动点）是递归类型的两个世界。
- **等递归**（展开即相等）与**异构递归**（显式 fold/unfold）是两种实现路线，主流语言多为异构。
- 负递归与等递归会给元理论带来困难——递归类型不是免费午餐。
- 递归类型是对象 self、递归数据结构、递归算法的共同地基，也是类型推导（下一课）要处理的现实类型之一。
