# 对象与封装

## 为什么从对象开始

Smalltalk、Java、C++ 把「对象」变成了每个程序员都离不开的词，但「对象到底是什么、它和我们已经建好的类型理论什么关系」反而常被工程习惯掩盖。皮尔斯在《类型与程序设计语言》第 18 章做了一件极有说服力的事：**用前面学过的记录、递归类型、存在类型，把对象完整地构造出来**——证明对象不是魔法，而是一个可组合的组合物。本课主题：**封装（encapsulation）**——对象把状态藏起来、只暴露行为，以及支撑这个「藏」的类型学机制（递归类型 + 存在类型）。

## 1 对象：状态 + 方法，藏着状态

**对象（object）**：一个把**状态（state）**与操作该状态的一组**方法（methods）**绑定在一起的值。它的核心承诺是**封装**：外部只能通过公开方法访问状态，状态的具体表示（representation）对用户不可见。Alan Kay 提醒我们把目光放在「消息传递」而非字段上——对象间的交互是发消息（调用方法），不是直接翻别人的口袋。

一个简单的计数器对象，拥有内部状态 `n` 与两个方法 `get`、`inc`。从类型上看，它长的样子是：

$$c : \exists \texttt{Rep}.\; \{ \texttt{get}: \texttt{Rep} \to \texttt{Nat},\; \texttt{inc}: \texttt{Rep} \to \texttt{Nat} \}$$

**重点：** 类型里那个 $\exists \texttt{Rep}$ 正是封装的形式化——**存在一个内部表示类型 Rep，但外部世界被蒙在鼓里**。<span class="marginnote">对象内部的状态「藏」住了，可只要方法签名暴露，状态是什么样（`Int`、`Float`、自增还是自减）都随实现者换——这正是「面向接口编程」的源头：用户只依赖类型，实现可以替换。</span>对象可以在不同时刻拥有不同的具体 Rep（先藏 `Nat`，后藏 `Float`），只要方法行为不变，用户程序不动。

**一个更有真实感的对象：银行账户**。`BankAccount` 藏着余额 `bal` 与两个方法 `deposit`、`getBalance`，它的存在类型长这样：$\exists \texttt{Rep}.\,\{\texttt{deposit}: \texttt{Rep}\to\texttt{Nat}\to\texttt{Rep},\; \texttt{getBalance}: \texttt{Rep}\to\texttt{Nat}\}$。外部只知道「存在一个 Rep 存着余额」，既不知道它是 `Int` 还是 `Float`，也不知道余额如何编码——只要方法行为不变，实现者可以把 `Nat` 换成任意结构，用户程序一行不改。**「藏住表示、暴露签名」是封装的全部意义，也是依赖倒置、接口隔离这些工程原则的类型学根源**。

**消息传递与「鸭子类型」**：Alan Kay 强调「真正的大想法是消息传递」，指对象之间只通过「发消息」交互、不关心对方是什么类——只要响应同样的消息就能互相替换。这成了动态语言里「鸭子类型」（duck typing）的哲学源头：Python、Ruby 里「叫起来像鸭子」的对象就能当鸭子用，而静态语言则用子类型（上一课）给这份自由加上可检查的边界。

## 2 用记录建模对象：状态被方法闭包捕获

没有 `class` 关键字，对象也能搭出来。回顾《参数传递与作用域》的**闭包**：函数可以捕获定义它的环境。把状态放进环境，方法放进记录，一个极简对象就诞生了（用一个不可变计数器示例）：

$$c = \texttt{let } n = 0 \texttt{ in } \{ \texttt{get} = \lambda \_.\, n,\; \texttt{inc} = \lambda \_.\, \texttt{let } n = n+1 \texttt{ in } \dots \}$$

这里的每个方法都是闭包，它们共享同一个捕获环境里的 `n`——**对象的状态正是多个方法共同捕获的那份环境**。这一观察把对象还原成了我们已掌握的机制：记录（方法表）+ 闭包（状态）。真正的语言把这份共享变成显式的 `self`/`this`：每次方法调用把「这个对象」作为隐藏参数传入，方法由此读写同一份可变状态。

**辨析｜易错点：** 不要把「封装」与「抽象」画等号。**抽象（abstraction）**是「隐藏实现细节、只留接口」，**封装（encapsulation）**是「把状态与方法绑定在一起并强制访问受控」——抽象偏语义，封装偏结构。C 语言的 `FILE*` 是抽象（你不看内部），但它不封装（没有把操作绑定为对象）；Java 的对象两者兼备。

三种「把数据打包」的构造值得并列：

| 构造 | 隐藏什么 | 是否含方法 | 类型 | 代表 |
| --- | --- | --- | --- | --- |
| 记录（record） | 什么都不隐藏 | 否（仅字段） | 结构类型 | C `struct`、OCaml record |
| 对象（object） | 隐藏状态表示 | 是（方法挂在实例） | 存在 / 递归类型 | Java、Smalltalk |
| 抽象数据类型（ADT） | 隐藏实现，仅暴露操作集 | 是（操作集中） | 存在类型 + 闭包 | OCaml module、ML |

**对象偏「每个值自带方法」（数据驱动），ADT 偏「一类值共享一组操作」（操作驱动）**——C 的 `FILE*` 是 ADT（操作集中在一组函数），Java 的 `FileInputStream` 是对象（方法挂在实例上）。**语言如何把「藏」落成语法**：Java 用 `private` 字段 + `public` 方法，C++ 用 `private:` 与 `friend`（friend 是「特定外部函数也可以进」的例外），Smalltalk 干脆「一切消息皆方法、一切字段皆私有」。这些关键词的本质，都是把「存在类型里的 Rep 不可见」翻译成编译器能强制执行的访问规则——**关键词会变，但「对外只暴露签名」的约束不变**。

## 3 自引用：对象需要一个「我」

闭包建模的对象有个缺口：方法之间要互相调用，就得能引用「这个对象自己」。在 λ 演算里没有名字，「自己」如何表达？答案是**递归类型（recursive types）**——下一课《递归类型》的主角。皮尔斯用不动点与递归类型处理 `self`：对象类型被写成递归类型，方法在调用前先把「自身」解包出来：

$$\texttt{type } Obj = \mu X.\; \{ \texttt{get}: \texttt{Nat},\; \texttt{inc}: \texttt{Unit} \to X \}$$

读作：「$Obj$ 是这样一个递归类型——它的一层展开是『有个 get 字段给自然数、inc 字段给一个返回另一个 $Obj$ 的函数』的记录」。一个方法若要调用 `self.inc`，就要用到递归类型自指的展开。**自引用 = 递归类型**，这是本课要留给下一课的桥：没有递归类型，对象就无法像自己调用自己那样引用自己。<span class="marginnote">现实语言用名字躲开了这道难题——`this` 是一个隐式形参，在方法体里当作绑定变量直接用；λ 演算没有内置名字，只能显式地把「自己」作为参数传入，或用不动点组合子把自引用编码出来。</span>

**语言里的自引用长什么样**：Java 里 `this.deposit(amount)` 的 `this` 是隐式形参，编译器在每个实例方法前塞一个「指向当前对象的指针」；Smalltalk 里 `self` 是一个真正的表达式，方法体内写 `self` 就像写一个普通变量。皮尔斯这里的「递归类型」版本，则是把「self 作为方法传入的第一个参数」显式化——`inc : Rep -> Rep` 里的 `Rep` 既是状态也是「自指的载体」。**三种写法只是同一件事的三副面孔：方法需要知道自己属于哪个对象**。

## 4 存在类型与隐藏的正式化

对象类型里的 $\exists \texttt{Rep}$ 不是装饰，它是**存在类型（existential type）**——皮尔斯第 24 章的形式系统，这里先借它的核心规则一用。存在类型的两个操作是：

**打包（pack）**：$t = \texttt{pack } \{T, v\} \text{ as } \exists X.\,\sigma$ ——把具体的实现类型 $T$ 与实现值 $v$ 封起来，对外只宣称「存在某个 $X$」。
- **解包（open）**：使用者不能直接拿到 $T$，只能用 `open` 语句在类型 $T$ 与实现 $v$ 上做受控计算，且结果类型 $\sigma$ 不能提及 $T$。

打包是「藏」，解包是「受控地看」。**重点：** 解包规则的结论类型 $\sigma$ 不许自由出现被隐藏的类型 $X$——这一条「不得泄露」约束，让「藏」成为不可绕过的：无论怎么解包，那个具体 Rep 都传不出使用边界，封装在类型层面是铁板一块。

**pack/open 的一次完整往返**：实现者写 `pack {Nat, {bal = 0, deposit = ..., getBalance = ...}} as ∃Rep. σ`，把「Rep 是 Nat」藏进包；使用者写 `open c as {Rep, body} in body.getBalance(...)`，在 open 块里 Rep 暂时可见、用完即隐。**pack 是「封口」，open 是「受控开箱」**——开箱的窗口一旦关闭，Rep 的真实身份再次不可见，这正是「实现细节只能在包内被依赖」的机制化表达。

## 5 开放递归与封闭递归

对象系统还有一个设计维度：方法里的 `self` 绑定到谁。若 `self` 绑定到「构造时那个对象」，称为**封闭递归（closed recursion）**——父类方法里的 `self` 永远是父类实例；若 `self` 在每次方法调用时重新绑定到「当前被调用的对象」，称为**开放递归（open recursion）**——父类方法调用 `self.xxx` 时，若子类重写了 `xxx`，会动态分派到子类版本。Java 的 `this` 是开放递归，因此父类构造器里调虚方法可能调到子类实现（著名的构造器陷阱即源于此）。**开放递归让方法组合更灵活，也把「方法分派」与「继承」耦合得更深**——这正是下一课子类型与对象如何共存时要处理的复杂性。<span class="marginnote">皮尔斯用「不可变对象 + 递归类型」的编码证明：对象行为无需运行时魔法即可在纯类型化 λ 演算里成立；真正需要专门类型构造的是可变状态与开放递归的组合，这正是现代语言类型系统仍在演进的地方。</span>

构造器陷阱的具体场景：父类构造器里调用 `this.render()`，若 `render` 是虚方法且被子类重写，那么子类字段尚未初始化时就会调用到子类版本——C++ 在基类构造期间把虚函数解析到基类版本（先建父、再建子），Java 则解析到子类版本但字段仍是默认值（可能读到 0 或 null）。**开放递归的灵活性，正是「时机不当」这类 bug 的根源**：`self` 每次调用都重绑，也就无法保证「调用发生时对象已经构造完毕」。

## 6 公式解析：解包规则把「藏」写成了约束

$$
\frac{\Gamma \vdash t_1 : \exists X. T_1 \quad \Gamma, X, x: T_1 \vdash t_2 : T_2}{\Gamma \vdash \texttt{let }\{X, x\} = t_1 \texttt{ in } t_2 : T_2}
\quad (X \notin FV(T_2))
$$

- **前提一 $t_1 : \exists X. T_1$**：$t_1$ 是一个打包好的对象——外界只知道「存在内部类型 $X$，内部结构是 $T_1$」。
- **前提二 $\Gamma, X, x: T_1 \vdash t_2 : T_2$**：解包之后，使用代码 $t_2$ 可以暂时把「具体类型」当作 $X$、把「实现」当作 $x$ 来写——**在解包块内部，$X$ 与 $x$ 是合法的**。
- **旁注 $X \notin FV(T_2)$**：结论类型 $T_2$ 中不得出现 $X$。这条「抽象边界条件」是全部精髓：你的程序可以\*用\*内部实现，却**写不出任何依赖内部表示类型的类型**——一离开解包块，那个具体的 Rep 就再也说不出口。
- **直觉**：这就像银行的保险柜——你可以在柜台（解包块）里存取，但绝不允许把「柜子结构图」（$X$ 本身）带出营业厅。

解包规则为什么是「安全」的？因为 $X \notin FV(T_2)$ 保证：无论使用者在 open 块里怎么折腾，他写出的任何类型都「说不出 $X$」——这就像银行只让你在柜台存取，却绝不让你把保险柜图纸带出门。**类型系统用一条「自由变量限制」就把封装钉死**，这是本课最漂亮的一处设计，也是后续《类型推导》里「出现检查」的近亲。

## 7 术语速查

| 术语 | 含义 | 一句话直觉 |
| --- | --- | --- |
| 对象（object） | 状态 + 绑定其上的方法 | 自带方法的记录 |
| 封装（encapsulation） | 状态表示对外不可见 | 藏住 Rep |
| 抽象（abstraction） | 隐藏实现、只留接口 | 不关心怎么做的 |
| 存在类型 $\exists X$ | 存在某个类型但说不出口 | 实现者的保密承诺 |
| pack / open | 打包（藏）/ 解包（受控看） | 封口 / 开箱 |
| 递归类型 $\mu X$ | 让对象能引用自己 | 方法间的 self |
| 开放递归 | self 每次调用重绑 | 支持动态分派 |
| 封闭递归 | self 构造时固定 | 父类方法永是父类 |
| 鸭子类型 | 响应同样消息即可互相替换 | 叫起来像鸭子 |

**记忆锚点**：对象 = 记录 + 闭包 + 递归类型；封装 = 存在类型 + 「结论类型不得提及 X」；self = 递归类型把「自己」指回来——三个词盖住全章。

## 8 小结

- **对象** = 状态 + 方法，核心是**封装**：状态表示对外不可见，行为通过消息（方法调用）暴露。
- 对象可用**记录 + 闭包**建模：方法共享同一份捕获的环境，那就是对象的状态。
- 方法间的自引用需要**递归类型**（self/this），这是下一课的桥。
- **存在类型**把「隐藏」写成规则：pack 藏、open 受控地看，且结论类型不得引用被隐藏类型。
- 递归分**开放**（每次调用重新绑定 self，支持动态分派）与**封闭**（构造时固定 self）；Java `this` 是开放递归。

在下一节，我们正面展开「自引用」的形式机制——让类型可以指回自己，这是链表、树、流与对象自指共同的基石：**递归类型**。
