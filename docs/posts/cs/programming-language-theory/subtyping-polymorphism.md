# 子类型与多态

<div class="epigraph">
<p>若对类型 S 的每个对象 o₁，都存在类型 T 的对象 o₂，使得以 T 定义的所有程序 P 在把 o₂ 替换成 o₁ 后行为不变，则 S 是 T 的子类型。</p>

## 为什么从子类型开始

类型系统目前是一张严格的名册：$\lambda x: \texttt{Nat}.\,\dots$ 只接受 $\texttt{Nat}$。但真实世界充满「更大与更小」：一个 `Dog` 能不能放进只要求 `Animal` 的槽位？真实语言里这个「能顶替」的关系就是**子类型（subtyping）**，记作 $S <: T$，读作「$S$ 是 $T$ 的子类型」。它是里氏替换原则（Liskov substitution principle）的类型学表达，也是面向对象类型系统（《对象与封装》一课）的地基。本课覆盖皮尔斯第 15 章：子类型关系的形式规则，以及它如何与多态共存。

## 1 子类型关系与包容规则

**子类型关系（subtype relation）**$S <: T$ 的定义可以非常朴素：**凡是 $T$ 合法的上下文，$S$ 都合法**。要把这条语义落成规则，需要两条结构性公理：

- **自反性（reflexivity）**：$S <: S$，任何类型是自己的子类型。
- **传递性（transitivity）**：$S <: U$ 且 $U <: T$ 推出 $S <: T$，子类型关系沿链传递。

以及一条连接子类型与类型判定的核心规则——**包容规则（subsumption rule）**：

$$
\frac{\Gamma \vdash t : S \quad S <: T}{\Gamma \vdash t : T}
$$

它说：**如果一个项有类型 $S$，而 $S$ 是 $T$ 的子类型，那么这个项也「有」类型 $T$**。正是这一条规则让 `Dog` 能被当作 `Animal` 使用——类型检查器在需要一个 `Animal` 时，接受任何 `S <: Animal` 的项。**辨析｜易错点：** 注意 $S <: T$ 的箭头方向：**子类型在左，父类型在右，读作「S 是 T 的子类型」**。初学者常写成 $T <: S$；把它想成「$S$ 能顶替 $T$ 的岗位」，方向就自然了。

**一个隐藏操作：最小公共超类型（LUB）**。类型检查器常常需要「两个类型的公共上界」——比如 `if (b) then 1 else 2.0` 的结果类型应是「同时包住 $\texttt{Nat}$ 与 $\texttt{Float}$ 的最小类型」。这要求子类型关系构成一种**偏序**，且任意一对类型都有**最小上界（least upper bound）**。并非所有子类型系统都有干净的 LUB：Java 里 `Number` 与 `String` 的 LUB 只能借道接口，这也解释了为什么「条件表达式的公共类型」在某些语言里会直接报错——类型检查器找不到「够小的公共上界」，只能拒绝。

## 2 记录子类型：宽度、深度与传递

子类型最有价值的实例是**记录（record）**——即命名字段的结构类型，是「对象」的雏形。设 $R_1 = \{x: \texttt{Nat}\}$，$R_2 = \{x: \texttt{Nat},\, y: \texttt{Bool}\}$，那么 $R_2 <: R_1$：**字段更多的记录，可以顶替字段更少的记录**，因为多出来的字段不会被注意到。这称为**宽度子类型（width subtyping）**。此外还有**深度子类型（depth subtyping）**：字段本身的类型也随子类型关系变，$\{x: \texttt{Bool}\} <: \{x: \texttt{Nat}\}$ 当 $\texttt{Bool} <: \texttt{Nat}$ 时成立。<span class="marginnote">宽度子类型就是「面向接口编程」的类型学形态：父类对使用方承诺更少（字段更少），子类在此基础上多承诺——于是父类的使用方永远安全。Go 的隐式接口、TypeScript 的结构类型都按这条规则工作。</span>

**宽度规则**（加字段）、**深度规则**（字段类型可换）、**传递性规则**（沿链走）三者合起来，记录的子类型判定就有了完整的规则集。**重点：** 深度规则的合法性要由被包含字段类型的子类型关系来证明——「外层的更大」最终必须化归为「内层的更大」，这是所有结构性子类型规则的共同模式。

**一个带实例的组合**：设 $R_1 = \{x:\texttt{Nat},\, y:\texttt{Bool}\}$，$R_3 = \{x:\texttt{PosInt},\, y:\texttt{Bool}\}$，且 $\texttt{PosInt} <: \texttt{Nat}$。则 $R_3 <: R_1$ 不靠「加字段」（宽度）而靠「字段类型更具体」（深度）成立——外层记录的更小，最终化归为内层字段的更小。两条规则叠加使用，子类型判定就有了完整的推导能力：**先问有没有多出的字段（宽度），再问每个共同字段是否顺着子类型方向（深度）**。

记录子类型为什么无处不在：它正是「结构类型 + 开放世界」的化身。Go 的接口是隐式结构子类型——一个类型只要实现了接口声明的全部方法就算实现该接口，无需显式声明；TypeScript 的对象字面量类型同样按结构判定。而 Java/C# 用名义子类型，需要显式 `extends`/`implements`。**结构子类型轻量灵活，名义子类型可读可控**，两种哲学至今并行，皮尔斯这里的记录子类型是纯结构的一极。

## 3 函数子类型：输入逆变，输出协变

函数类型的子类型关系是全书最重要的一个结果。考虑两个函数类型 $T_1 \to T_2$ 与 $S_1 \to S_2$，什么时候 $S_1 \to S_2$ 能顶替 $T_1 \to T_2$？直觉实验：上下文按「吃 $T_1$、吐 $T_2$」来使用这个替身，因此替身必须**吃得了所有可能出现的 $T_1$ 实参**——这要求替身的输入 $S_1$ 是 $T_1$ 的超类型（$T_1 <: S_1$）；同时替身给出的每一个 $S_2$ 结果都必须被接受为 $T_2$——这要求 $S_2 <: T_2$。写成规则：

$$
\frac{T_1 <: S_1 \quad S_2 <: T_2}{S_1 \to S_2 \;<:\; T_1 \to T_2}
$$

即：**函数子类型中，参数类型逆变（contravariant）、结果类型协变（covariant）——子类型关系在输入位置上被翻转，在输出位置上保持方向**。

**辨析｜易错点：** 这是全专题最著名的反直觉结论。直觉上「子类型越小越具体」，可函数参数却「越大越好」——因为函数需要能应付\*更多\*的输入。Java 数组是协变的（`Dog[]` 是 `Animal[]` 的子类型），而泛型 `List<Dog>` 不是 `List<Animal>` 的子类型（不可变型，invariant），这是历史妥协与正确设计的经典对比。<span class="marginnote">Java 数组协变是 1970 年代为通用容器 API 做的历史妥协（2005 年 JDK 官方文档直言这是「在类型系统上凿的一个洞」），泛型则守住不可变型。现代语言把方差声明权交还给程序员：Kotlin 用 `out`/`in`、C# 用 `out`/`in` 注解，方差从「隐式规则」变成「显式契约」。</span>**判定函数子类型时，先问「谁吃谁」：输入要装得下全部实参（参数越大越好），输出要全都被接受（结果越小越好）**。

方差不仅存在于函数，也存在于一切「参数化构造子」：`List<Dog>` 与 `List<Animal>` 的关系取决于 `List` 的方差。皮尔斯给出的一般判定法：**看类型变量出现在哪个位置**——只出现在「输出」位置（读操作）则为协变，只出现在「输入」位置（写操作）则为逆变，两处都出现则为不可变。C# 的 `IEnumerable<out T>`（只读、协变）与 `IList<T>`（可读可写、不可变）正是这条规则的工业版；Java 的 `List<? extends T>` 通配符则用「使用点标注」在调用处临时声明方差——读 `List<? extends Animal>` 安全，写它则被拒绝。**方差不是玄学，它只是「类型变量出现位置」的记账**。

## 4 名义 vs 结构；子类型与多态的四种颜色

子类型关系有两种确立方式：**名义子类型（nominal subtyping）**由程序员显式声明（Java 的 `extends`、C# 的 `:`），**结构子类型（structural subtyping）**由类型形状自动推出（记录、Go 接口、TypeScript）。前者可读性强、适合大工程，后者自由、支持鸭子类型；皮尔斯的记录子类型是纯结构的。

再把视野拉开，多态（polymorphism）按来源分四类，子类型只是其中之一：

- **特定多态（ad-hoc）**：重载、运算符重载——同一名字多个无关实现。
- **强制多态（coercion）**：隐式类型转换——`int` 自动变 `double`。
- **子类型多态（subtype/inclusion polymorphism）**：本课主题，`Dog` 顶替 `Animal`。
- **参数多态（parametric polymorphism）**：`List<T>` 对所有 `T` 一视同仁——本专题《System F 参数化多态》的主题。

子类型多态看的是「类型之间的关系」，参数多态看的是「对类型变量的全称量化」，二者互补且可结合（皮尔斯第 26 章有界量化 $\forall X <: T$ 即是两者的合一）。

**有界量化的日常形态**：Java 的 `T extends Comparable<T>` 要求类型参数同时「满足 $T <: \texttt{Comparable}$」又「具体类型任意」——既限制了「必须是可比较的」，又保留了多态的自由。这就是 $\forall X <: T$ 在泛型 API 里的投影：**边界让函数知道「$X$ 至少会什么」，多态让函数不关心「$X$ 具体是什么」**。两股力量合起来，才支撑起 `sort`、`max` 这类既能约束又通用的库函数。

**里氏替换的日常含义**：能接受 `Animal` 的代码，必须也能接受任何 `Dog`。违反它会发生什么？经典反例：让 `Square` 继承 `Rectangle` 并把 `setWidth` 重写为「同时改两边」——于是「只关心宽、改完再读高」的 Rectangle 客户端在传入 Square 时会得到意外的结果。**子类型关系的正确性，最终要由「行为是否真的可替换」来检验**；类型规则只是把这个承诺尽量前移到编译期。

## 5 公式解析：函数子类型规则的可读方式

$$
\frac{T_1 <: S_1 \quad S_2 <: T_2}{S_1 \to S_2 \;<:\; T_1 \to T_2}
$$

- **结论 $S_1 \to S_2 <: T_1 \to T_2$**：要判定的目标——「类型 $S_1\to S_2$ 的替身能否顶替 $T_1\to T_2$」。
- **前提一 $T_1 <: S_1$，注意关系被翻转**：替身的输入 $S_1$ 必须是原输入 $T_1$ 的**超类型**。为什么？原上下文可能抛出\*任何\* $T_1$ 实参，替身要接得住全部，于是 $S_1$ 必须更大——这就是**逆变**：子类型关系在输入位置被翻转。
- **前提二 $S_2 <: T_2$，方向保持**：替身的每个输出都是 $S_2$，都必须被当成 $T_2$ 接受，于是 $S_2$ 必须更具体——**协变**。
- **验证实例**：设 $\texttt{Dog} <: \texttt{Animal}$，则 $\texttt{Animal} \to \texttt{Dog} <: \texttt{Dog} \to \texttt{Animal}$ 成立——前提一要求 $\texttt{Dog} <: \texttt{Animal}$（逆变 ✓），前提二要求 $\texttt{Dog} <: \texttt{Animal}$（协变 ✓）；而反向的 $\texttt{Dog} \to \texttt{Animal} <: \texttt{Animal} \to \texttt{Dog}$ 不成立——它要求 $\texttt{Animal} <: \texttt{Dog}$，假。

这套规则回答了最实际的问题：「我的类型替身合不合法？」——把目标类型拆成「输入位置」与「输出位置」，逐一核对方向即可。**方差思维（输入看大、输出看小）是理解一切泛型 API 设计（`out`/`in`、`? extends`）的钥匙**，也是本课留给《System F 参数化多态》一课的伏笔。

## 6 术语速查

| 术语 | 含义 | 一句话直觉 |
| --- | --- | --- |
| 子类型 $S <: T$ | S 能顶替 T | 更小的顶替更大的 |
| 包容规则 | 子类型项可直接用于父类型上下文 | 有 S 就算有 T |
| 宽度子类型 | 字段更多 ⇒ 更小 | 多承诺的是子类 |
| 深度子类型 | 字段类型可顺着子类型换 | 外层更小化归为内层更小 |
| 协变（covariant） | 输出位置，方向保持 | 结果越小越好 |
| 逆变（contravariant） | 输入位置，方向翻转 | 参数越大越好 |
| 名义 / 结构子类型 | 显式声明 / 按形状自动 | Java extends / Go 接口 |
| 有界量化 $\forall X <: T$ | 子类型 + 参数多态合一 | 有边界地任意 |
| 最小上界（LUB） | 一对类型的公共超类型之最小者 | 条件表达式的公共类型 |
| 里氏替换 | 子类必须能安全替换父类 | 行为真的可替换 |

**记忆锚点**：子类型是「偏序 + 包容」；记录看宽度与深度；函数看输入逆变、输出协变——三句口诀即可复现整章规则。

## 7 小结

- **子类型** $S <: T$ 意味「$S$ 能顶替 $T$」，由自反、传递与**包容规则**支撑，后者让子类型项可直接用于父类型上下文。
- 记录子类型有**宽度**（加字段）与**深度**（字段类型可换）两种来源。
- 函数子类型**参数逆变、结果协变**——最反直觉也最重要的规则。
- 子类型有**名义**与**结构**两种确立方式；多态四色中，子类型多态与参数多态构成两大主线。
- 里氏替换原则把「能顶替」的语义落实为「行为不变」的承诺，是子类型的工程意义。
