## 为什么从渲染管线开始

上一篇我们用主循环把「一帧」框了出来，其中第三步就是 `render()`。这一步到底做了什么？答案就是**实时渲染管线（real-time rendering pipeline）**：一条从「场景中的三维网格」到「屏幕上的像素颜色」的工业化流水线。它之所以值得单独成篇，是因为它是引擎里**吞吐量最大、性能瓶颈最常出现**的地方——一个 60 FPS 的游戏，每帧只有约 16.7 ms 完成全部绘制，而其中任何一段慢了，玩家看到的都是卡顿。理解管线，等于拿到了读懂「为什么这游戏这么吃显卡」的钥匙。<span class="marginnote">渲染管线的完整数学与光栅化细节属于第三级《计算机图形学》（GAMES101/虎书）的正职，本篇站在引擎视角讲「调度与工程形态」：哪部分在 CPU、哪部分在 GPU、两者如何交接。</span>

## 1 从场景到像素：四阶段流水线总览

传统 GPU 渲染管线可分成四大阶段，前两阶段主要在 CPU 上准备，后两阶段主要在 GPU 上执行：

**应用阶段（application stage）**：CPU 端。剔除不可见物体、准备渲染命令、更新变换矩阵，把「要画什么、用什么材质、在哪个位置」打包成 GPU 能消费的形式——**draw call**。<span class="marginnote">「剔除」是应用阶段的第一个性能杠杆：场景里 10000 个物体，对相机可见的可能只有 2000 个。怎么快速知道哪些不可见，是本专题《场景管理与空间数据结构》一篇的核心。</span>

**几何阶段（geometry stage）**：GPU 端。对每个顶点执行**顶点着色器（vertex shader）**，做坐标变换与光照计算，把顶点从模型空间一路搬到屏幕附近；随后执行**裁剪（clipping）**与**屏幕映射（screen mapping）**，把图元规整到像素坐标。

**光栅化阶段（rasterization stage）**：GPU 端。把三角形**离散成像素**：判断三角形覆盖了哪些像素，并插值出每个像素所需的属性（深度、颜色、UV、法线）。

**片元阶段（fragment stage）**：GPU 端。对每个被覆盖的像素运行**片元着色器（fragment shader）**，采样纹理、算光照、做测试（深度测试、模板测试），最终把颜色写进**帧缓冲（framebuffer）**。

用一张图把整条流水线串起来：

![实时渲染管线总览：CPU 应用阶段打包 draw call，GPU 依次执行顶点处理、裁剪、光栅化、片元着色，最终写入帧缓冲](/images/game-development/real-time-rendering-pipeline-1.svg)

**实时渲染的秘诀，在于它是一条真正意义上「流动」的管线**：GPU 处理第 $n$ 帧的顶点时，CPU 已在准备第 $n+1$ 帧的命令，两者像传送带上下游一样并行——这被称作**双 CPU-GPU 并行（double buffering of work）**。

把四个阶段的主权归属与代价理清，是读后续一切渲染文章的基础：

| 阶段 | 执行者 | 主要输入 | 主要输出 | 复杂度来源 |
| --- | --- | --- | --- | --- |
| 应用 | CPU | 场景/相机/光源 | draw call 列表 | 物体数量、剔除效率 |
| 几何 | GPU | 顶点数据 | 屏幕坐标三角形 | 顶点数量、蒙皮 |
| 光栅化 | GPU | 三角形 | 片元（含插值属性） | 覆盖像素数 |
| 片元 | GPU | 片元 | 帧缓冲颜色 | 像素数、光照/纹理 |

## 2 顶点阶段：坐标系的四次搬家

一个顶点在建模软件里定义时，用的是**模型空间（model space）**，以物体自身中心为原点。而场景里的每个物体都有自己的位置、朝向与缩放，于是顶点要依次穿过四个坐标系：

1. **模型空间 → 世界空间（world space）**：乘上**模型矩阵 $\mathbf{M}$**，完成平移/旋转/缩放，让物体落在场景的正确位置。
2. **世界空间 → 视图空间（view space）**：乘上**视图矩阵 $\mathbf{V}$**，以相机为原点重建坐标——相机往前看，世界就往后退。
3. **视图空间 → 裁剪空间（clip space）**：乘上**投影矩阵 $\mathbf{P}$**，把视锥（frustum）压成标准立方体，为透视除法做准备。
4. **裁剪空间 → 标准化设备坐标（NDC）**：做**透视除法**（各分量除以 $w$），把坐标归一化到 $[-1,1]^3$，再经**视口变换（viewport transform）**映射到像素坐标。

其中第 1、2、3 步常被合并成一个矩阵，称为 **MVP 矩阵**：$\mathbf{MVP} = \mathbf{P}\mathbf{V}\mathbf{M}$。顶点着色器通常只需做一次矩阵乘，就把一个局部坐标顶点送到了裁剪空间。

## 3 公式解析：MVP 变换把顶点送到裁剪空间

核心公式是顶点着色器里的那条矩阵乘：

$$
\mathbf{p}_{\text{clip}} = \mathbf{P}\,\mathbf{V}\,\mathbf{M}\;\mathbf{p}_{\text{local}}
$$

- **第一步，读 $\mathbf{p}_{\text{local}}$**：它是模型空间里的一个齐次坐标 $(x,y,z,1)^{\mathsf{T}}$。齐次坐标多出的第 4 个分量 $w$ 让平移也能写成矩阵乘法——这是向量 $\begin{bmatrix}x&y&z\end{bmatrix}^{\mathsf{T}}$ 无法直接做到的事。<span class="marginnote">为什么平移需要齐次坐标？因为平移是加法，矩阵乘天然是线性变换只含乘与加；把 3 维点抬到 4 维齐次空间后，平移退化为一次矩阵乘。这一笔在第三级《线性代数》与第二级《向量与张量》里有更严格的背景。</span>
**第二步，读 $\mathbf{M}$、$\mathbf{V}$、$\mathbf{P}$ 的次序**：矩阵乘法是右乘优先的。$\mathbf{P}\mathbf{V}\mathbf{M}\;\mathbf{p}$ 的意思是「先对 $\mathbf{p}$ 应用 $\mathbf{M}$，再应用 $\mathbf{V}$，最后应用 $\mathbf{P}$」。次序绝不能换：若先把相机变换乘进去再旋转物体，物体就会绕相机转而不是绕自己转。**矩阵的书写次序，就是变换的执行次序**——这是全篇最容易踩的坑。
- **第三步，读 $\mathbf{P}$ 的两种形态**：**透视投影（perspective）**用 $w$ 分量携带「深度倒数」，使远处的物体在屏幕上更小，符合人眼；**正交投影（orthographic）**则不做这种压缩，工程图纸、2D 游戏、阴影贴图常用。$\mathbf{P}$ 矩阵的具体元素（视场角 $fov$、宽高比、近远裁剪面）决定了「看多大、看多深」。
- **第四步，理解裁剪空间之后**：裁剪空间里的坐标还带着 $w$，GPU 随后把每个分量除以 $w$ 得到 NDC——这一步叫**透视除法**。所有在视锥外的三角形都在此之前被裁剪掉，避免给屏幕外的几何白付着色成本。

**辨析｜易错点：** 初学者常以为「模型矩阵把物体放好」就结束了。其实视角不同，同一场景要重算 $\mathbf{V}$ 与 $\mathbf{P}$；物体动了，只变它的 $\mathbf{M}$。把「哪些矩阵是每帧重算、哪些是每物体重算」理清，是调试「物体飞向错误位置」的第一把尺子——若角色绕相机转，多半是变换次序写反了；若角色原地不动，多半是 $\mathbf{M}$ 忘了更新。

## 4 光栅化：从三角形到片元

几何阶段把三角形送到了屏幕附近，光栅化阶段要回答的问题是：**这个三角形覆盖了哪些像素？** 光栅化器逐个三角形工作：先算出它在屏幕上的包围范围，再判断范围内每个像素是否落在三角形内，对每个被覆盖的像素生成一个**片元（fragment）**，并沿三角形**插值**出深度、UV、颜色、法线等属性。

**插值是光栅化的灵魂**：三角形的三个顶点各带一份属性，覆盖区内的每个片元按**重心坐标（barycentric coordinates）**把三份顶点属性按距离混合成自己的那份。逐像素的平滑渐变全靠这一步——它是「顶点数据 → 像素数据」的桥梁，也是第三级《计算机图形学》里重心坐标的主场。<span class="marginnote">重心坐标用三个系数 $(\alpha,\beta,\gamma)$ 描述「片元在三角形里有多靠近三个顶点」，且 $\alpha+\beta+\gamma=1$。它对纹理采样尤其关键：直接把 UV 线性插值，透视下会歪，必须先按深度倒数插值——这被称为<strong>透视校正插值（perspective-correct interpolation）</strong>。</span>

**深度测试（depth test）**：每个片元都要跟**深度缓冲（Z-buffer）**里的旧深度比一比，更近的覆盖、更远的丢弃。这一条简单的规则，让几十万个三角形能正确叠出前后遮挡——它是光栅化正确性的第一保障。<span class="marginnote">深度缓冲的精度是经典坑：近平面附近精度高、远处精度低，远处会出现抖动的深度冲突（z-fighting）。解法是<strong>反向 Z（reversed-Z）</strong>——把深度映射倒过来，让远处也分到足够精度——现代图形 API 已普遍默认。</span>

从成本模型看，管线的后两段「吃」的其实是不同的资源：**几何阶段吃顶点数、光栅化吃像素数、片元阶段吃像素数与着色复杂度**。一个「多边形很多但很小」的场景瓶颈在光栅化；一个「多边形少但贴着大屏幕」的场景瓶颈在片元。**先判断瓶颈在哪一端，再谈优化**，是渲染调优的第一课——这与物理、AI 里的「预算优先」是同一个思维。

## 5 片元着色：纹理、光照与透明

对每个通过深度测试的片元，引擎运行**片元着色器（fragment shader）**，决定它最终是什么颜色。三项主要工作：

**纹理采样**：用片元的 UV 坐标到**纹理（texture）**里查颜色。一张 512×512 的纹理有 26 万多个纹素，采样的关键是**过滤（filtering）**——最近邻出马赛克，双线性过滤在四个相邻纹素间插值让边缘平滑；远处的三角形一个像素盖住十几个纹素，还要用 **mipmap**（预先缩小的纹理层级）避免闪动的摩尔纹。<span class="marginnote">mipmap 的直觉：把纹理预先缩成一半、四分之一……每一级都变小，采样时按「一个像素盖住多少纹素」选合适的一级。它多花约 33% 的纹理内存，换掉的是远处物体表面剧烈的闪烁——「预计算换运行期稳定」，与《场景管理》里的静态烘焙是同一哲学。</span>

**逐片元光照**：用插值出的法线、位置与材质参数，按光照模型（如 Phong、PBR）逐像素算颜色。逐片元光照比逐顶点光照平滑得多，代价是计算量随像素数线性增长——于是引擎把最贵的光照拆成多遍，并在可选项上做该不该算的裁剪。

**透明混合（alpha blending）**：片元带透明度时不能直接覆盖，而是按 $\alpha$ 与已有颜色**混合**：`color = src·alpha + dst·(1−alpha)`。透明物体必须先画远的再画近的，否则混合顺序出错——这正是《场景管理与空间数据结构》里「渲染队列排序」的由来。

## 6 渲染路径与后处理

管线怎么组织，还分不同**渲染路径（rendering path）**。两条主流：

**前向渲染（forward rendering）**：对每个片元直接累加所有光源的光照。实现简单、MSAA 好做，但光源一多，每个片元要算的光照翻倍——适合光源少、或移动端场景。

**延迟渲染（deferred rendering）**：先只记「几何信息」（颜色、法线、位置、材质）进**几何缓冲（G-buffer）**，第二遍再逐像素算光照。光源再多也只需一遍 G-buffer 采样——适合光源成百上千的场景。代价是 MSAA 难做、带宽吃紧、透明物体要另走一遍前向。<span class="marginnote">延迟渲染的「先攒几何、后统一算光照」，与数据库里「先收集、后批处理」、以及《场景管理》里「先剔除、后渲染」是同族思想：<strong>把昂贵计算与几何处理解耦，让贵的部分只在必要时发生</strong>。</span>

**后处理（post-processing）**：画面全部画完后，整帧再做一遍特效——色调映射（HDR 到 LDR）、泛光（bloom）、景深、动态模糊、色彩分级。后处理是「一张纹理进、一张纹理出」的链式滤镜，每一环都是一次全屏像素操作，所以它是「按像素」开销的大户，也是游戏画面质感的重要来源。

## 7 渲染的工程形态：draw call 与并行

管线讲完了，还要回答「怎么让几亿次运算在 16.7 ms 里跑完」。渲染的工程形态有三根支柱：

**draw call 合并**：CPU 每发一次「画这个物体」的命令就是一次 **draw call**，每次提交都有固定开销。场景有 10000 个物体，若画 10000 次，CPU 先被拖垮。于是引擎把「同材质、同着色器」的物体**合并成一次绘制**——合并纹理（texture atlas）、合并网格（static batching）。**draw call 数量是渲染性能的第一指标**。<span class="marginnote">合并 draw call 的代价是灵活性降低（合并后不能单独隐藏其中一块），所以引擎用 <strong>GPU 实例化（instancing）</strong>在「同网格、同材质」时一次提交多份实例，既保住性能又保住灵活性——「按需选合并粒度」是渲染性能调优的主线。</span>

**状态排序（state sorting）**：GPU 换着色器、换纹理、换混合模式都要花时间。引擎把渲染命令按「状态」排序，先排好同状态的 draw call，把状态切换压到最低——与 CPU 缓存局部性是同一个思想。

**CPU-GPU 并行**：CPU 准备第 $n+1$ 帧时 GPU 在画第 $n$ 帧，命令**提前排进命令缓冲**，GPU 异步消费。命令缓冲满时 CPU 被「反压」等待——这是「GPU 成为瓶颈」的信号。并行深度的设计，是渲染调度的心脏。<span class="marginnote">「CPU 提交、GPU 异步执行、缓冲反压」与《操作系统》里的生产者—消费者模型、网络篇的发送缓冲是同构的：<strong>两边速度不匹配，就用队列吸收，队列满就反压</strong>。渲染的并行调度，本质是一道经典的流水线设计题。</span>

**辨析｜易错点：**「这张卡这么强，怎么帧率还上不去？」一大半原因是 **CPU 成了瓶颈**——draw call 提交、状态切换、剔除全在 CPU 上，GPU 再强，喂不饱也没用。优化渲染的第一步永远不是调 GPU 参数，而是先用剖析器确认瓶颈在 CPU 还是 GPU，再对症下药。

## 8 小结

- 实时渲染管线四阶段：**应用（CPU）→ 几何 → 光栅化 → 片元（GPU）**，是一条「流动」的流水线。
- 顶点经 **MVP 矩阵**（$\mathbf{p}_{\text{clip}}=\mathbf{P}\mathbf{V}\mathbf{M}\,\mathbf{p}_{\text{local}}$）搬过四套坐标系，透视除法后在 NDC 落定。
- **光栅化**用重心坐标把三角形插值成片元，**深度测试**决定谁可见；片元着色做纹理采样、逐片元光照与透明混合。
- 渲染路径两条：**前向**（简单、光源少）与**延迟**（G-buffer 解耦几何与光照，光源多）；后处理是链式全屏滤镜。
- 性能三支柱：**draw call 合并**、**状态排序**、**CPU-GPU 并行**（命令缓冲 + 反压）；先判瓶颈在 CPU 还是 GPU 再优化。

在下一节，我们要给这条流水线装上「计算语言」——把位置、朝向、速度装进向量、矩阵与四元数，这就是**游戏数学**。
