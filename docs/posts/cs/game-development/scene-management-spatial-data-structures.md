## 为什么从场景管理开始

一个开放世界可能有十万个物体，但玩家一眼望去、一帧之内真正要处理的，通常只有几百个。**场景管理（scene management）**回答一个朴素却极难的问题：**如何在不遍历整个世界的前提下，快速找到「我关心的那一小部分」**——哪几个物体在相机视锥内、哪几对物体可能相撞、射线穿过了哪些物体、NPC 附近有哪些掩体。它不是一个独立子系统，而是一组**空间数据结构（spatial data structures）**：把「世界」组织成可按空间快速检索的形式。渲染、物理、AI、音频——前面所有子系统的查询，最终都落到这里。<span class="marginnote">「用空间索引换检索速度」的思想远不止游戏：第三级《数据库》的 B+ 树、空间索引（R 树）、以及《数据结构》的二叉搜索树，都是同一个母题——<strong>把线性扫描变成树/哈希上的对数或常数查询</strong>。</span>

## 1 场景图：变换的层级

先分清两个常被混为一谈的概念：**场景图（scene graph）**与**空间分区（spatial partition）**。

**场景图**管的是「**变换的父子关系**」，不是「位置」。它是上一篇《游戏数学》里 Transform 嵌套的正式化：角色手里的剑是角色手骨骼的子节点，角色移动，剑跟着移动；整条「角色 → 手 → 剑」链条共享一次世界矩阵更新。场景图的每一次遍历，产出的是「每个节点的世界变换矩阵」。

**空间分区**管的是「**空间上的邻近关系**」，回答「谁在哪儿附近」。场景图是树（按父子），空间分区也是树（按空间），但两者的**建树依据完全不同**——场景图按「谁挂在谁下面」，空间分区按「谁在哪个区域里」。<span class="marginnote">一个经典误区：把场景图的父子关系当成空间包含关系。父节点在左边，子节点完全可以在右边（隔着半张地图）——它们只共享变换，不共享位置。空间上的「包含」要找空间分区，而不是沿场景图往上走。</span>

现代引擎往往**两者并用**：场景图管理变换层级与可见性标记，空间分区提供「按位置检索」的索引。

场景图的一次遍历，在每帧里是这么嵌进主循环的：更新阶段，从根节点深度优先走一遍，把每个节点的世界矩阵算出来（用父节点的世界矩阵 × 自己的局部矩阵），顺路做「本节点是否可见、是否要提交渲染」的标记；渲染阶段，再把可见节点交给空间分区做真正的裁剪与排序。**「场景图算矩阵，空间分区做裁剪」**——两棵树各管一件事，配合得严丝合缝。<span class="marginnote">场景图的遍历顺序还与渲染的「由远及近」排序有关：透明物体要先画远的再画近的，否则混合（alpha blending）会出错。引擎常在场景图遍历后做一次<strong>渲染队列排序</strong>，这正是《实时渲染管线》里「Render Pass 组织」的前置一步。</span>

## 2 空间分区：把世界切成可搜索的块

空间分区的家族成员，按「怎么切」分成几类：

**均匀网格（uniform grid）**：把世界切成等大的格子，每个格子记一份物体列表。查询「谁在以点 P 为中心半径 r 的范围内」只需查覆盖范围内的格子。实现极简、动态物体友好（移动物体只需换格子），但格子大小难选——物体大小悬殊时（一座山 vs 一粒弹壳），均匀网格会很不均匀。

**四叉树 / 八叉树（quadtree / octree）**：递归地把空间切四（二维）或八（三维）份，物体大的待在高层大格子、物体小的沉到低层小格子。它自动适配物体尺寸，是三维世界最经典的选择之一。<span class="marginnote">八叉树的「自适应细分」与<strong>网格 LOD（多级细节）</strong>、以及图像处理里的<strong>金字塔</strong>都是「递归细分」家族的亲戚。对静止地形这类数据，八叉树几乎完美；对高速移动的物体，更新代价是它最大的软肋。</span>

**包围盒层次（BVH, Bounding Volume Hierarchy）**：不是按空间切，而是按**物体集合切**——把物体递归地分到「空间上相近」的组里，每个节点用一个包围盒包住整组。查询时自上而下用「盒-盒相交」快速排除整棵子树。BVH 对动态场景友好（物体移动只影响其祖先节点），是游戏里实时渲染与物理碰撞的**默认选择**。<span class="marginnote">BVH 与八叉树的关键差别：八叉树的分区是<strong>空间固定</strong>的（物体跨界就换格子），BVH 的分区是<strong>随物体</strong>的（盒跟着物体变）。前者查得爽但维护累，后者维护便宜但盒会重叠。选择它们，就是在「查询速度」与「更新成本」之间选位置。</span>

**空间哈希（spatial hash）**：把空间坐标哈希到数组下标，用哈希表代替树。查询快、实现简单，适合**动态、大量、物体大小相近**的场合——布娃娃碎片、弹壳、粒子都爱用它。代价是「附近」的定义粗糙，跨界物体要哈希进多个格子。

| 结构 | 动态友好 | 查询速度 | 实现难度 | 典型用途 |
| --- | --- | --- | --- | --- |
| 均匀网格 | 高 | 中 | 低 | 大量同类动态物体 |
| 四叉/八叉树 | 低 | 高 | 中 | 静态地形、大世界 |
| BVH | 中 | 高 | 中 | 渲染/物理碰撞默认 |
| 空间哈希 | 高 | 中 | 低 | 粒子、碎片、海量小物体 |

无论选哪种，它们的查询套路都长得一样——**从根开始，能用包围盒排除就排除，不能排除就递归**。以 BVH 的「射线求交」为例：

```text
function intersect(node, ray):
    if not boxHit(node.bounds, ray): return null   # 盒没被射线击中 → 整棵子树排除
    if node.isLeaf:
        return testTriangles(node.triangles, ray)  # 叶节点 → 精确测试
    return min(intersect(node.left, ray),          # 递归，取更近的交点
               intersect(node.right, ray))
```

这个「**先盒后精、能挡就挡**」的骨架，就是所有空间索引查询的通用形态——树的高度决定排除的效率，包围盒的质量决定误判的比例。

从复杂度看，四类结构的对比非常清晰：均匀网格与空间哈希的查询近似 **O(覆盖格子数)**，与物体总数无关；四叉/八叉树与 BVH 的查询最坏是 **O(N)**，但配合好的包围盒与启发式，实际平均远低于线性——**它们赌的是「空间上相近的物体在树上也相邻」这个事实**。空间局部性（locality）是这一切成立的根本前提，也是《计算机组成原理》里 cache 局部性在更高维度上的同构。

## 3 公式解析：八叉树节点与空间哈希

空间结构的好坏，可以用**一条查询要触碰多少节点**来度量。以八叉树为例，一个查询「哪些物体在半径 $r$ 的球内」的成本，正比于被该球触碰的节点数——它可以用节点的空间尺寸来估算。最简洁的落点其实是**空间哈希的下标公式**：

$$
\text{index} = \left( \lfloor \tfrac{x}{\text{cell}} \rfloor,\ \lfloor \tfrac{y}{\text{cell}} \rfloor,\ \lfloor \tfrac{z}{\text{cell}} \rfloor \right) \xrightarrow{\ \text{hash}\ } \text{bucket}
$$

- **第一步，读 $\lfloor x/\text{cell} \rfloor$**：把世界坐标除以格子尺寸后向下取整，得到「这个点在哪个格子里」。除以 cell 是缩放，向下取整是量化——连续坐标变成了离散格标。
- **第二步，读 hash**：三个格标 $(i,j,k)$ 通过哈希函数压缩成一个桶下标。好的哈希让空间上相近的格子**尽量散开**，避免「一个桶塞满整片区域」。
- **第三步，读桶（bucket）**：每个桶挂一个物体链表。插入：算一次哈希、挂链；查询：把范围覆盖的所有格子算出来、查它们的桶。**「几何查询」就这样变成了「数组下标 + 链表遍历」**——这就是空间索引的全部秘密：把几何问题变成内存问题。
- **第四步，读代价**：空间哈希的查询成本近似正比于**覆盖格子数 × 每格平均物体数**。格子太大，每格物体多、查询慢；格子太小，覆盖格子数爆炸。cell 的选择是「黄金尺寸」，通常取「场景里最常见物体的平均半径」量级——**结构选型永远在赌「你的场景长什么样」**。

同样读一下八叉树的节点分裂，体会「递归细分」的优雅与代价：一个节点开始时包住整块立方体区域，当它容纳的物体超过阈值（如 8 个）且深度未到上限，就平均切成 8 个子立方体，把物体按「中心落在哪个子立方体」分下去。查询时从根向下，只在「与查询范围相交」的节点里继续——**每深入一层，搜索空间缩小八分之一**。但若物体分布极不均匀（一栋楼挤在一格角），树会退化成「瘦高」结构，查询不再高效，因此八叉树常设**最大深度**兜底，过深就「认了，多放几个」。

## 4 裁剪：看不见的就不画

空间分区的头号应用是**裁剪（culling）**——把不会被玩家看到的物体拦在渲染之前。主要有三层：

**视锥剔除（frustum culling）**：把相机的可视区域建成一个**视锥体**，用「视锥 vs 包围盒」的相交测试，把完全在视锥外的物体剔掉。视锥测试一次约几十次比较，配合 BVH/八叉树能一次排除整棵子树。<span class="marginnote">视锥剔除的数量级很惊人：十万物体的世界，视锥测试通常能砍掉 90% 以上。它是「渲染管线第一篇」里应用阶段剔除的正式实现——那里我们说过「渲染前先删掉看不见的」，这里补上了「怎么删得这么快」。</span>

视锥测试的数学很简单：视锥由 6 个平面（近、远、左、右、上、下）围成，判断一个包围盒是否在视锥内，就是对 6 个平面各做一次「点在平面内侧」的检验，任何一个平面能证明盒子完全在它外侧，就剔除。**这里用的是「或」的短路逻辑**：只要有一个平面挡住，就整棵排除——这也是为什么空间结构树越深，剔除越高效。

**遮挡剔除（occlusion culling）**：物体在视锥内但被一堵墙完全挡住，画了也是白画。粗暴做法是把相机与物体连线做射线检测，但更常用的是**遮挡查询**（把物体包围盒画进一个超低分辨率深度缓冲，看有没有像素通过）与**预计算遮挡数据**。遮挡剔除比视锥剔除贵得多，往往只在重要物体上启用。

**距离裁剪（distance culling）与 LOD**：太远的物体不画或画简化版。**细节层次（LOD）**提供同一物体的多个精度网格，按距离切换——它与「裁剪」是表亲：裁剪是「删掉」，LOD 是「降级」。<span class="marginnote">LOD 的选择策略（按距离、按屏幕面积、按重要性）与「预算优先」哲学一脉相承。游戏里「远处山体的轮廓还在，细节没了」就是 LOD 在起作用——它把渲染预算让给了玩家真正盯着看的东西。</span>

**辨析｜易错点：** 裁剪的收益要用「被剔除的物体 vs 剔除本身的成本」衡量。裁剪测试本身也要花 CPU——如果场景里只有几十个物体，花在视锥测试上的钱可能比直接画还贵。**「先问场景规模，再决定要不要裁」**，是裁剪工程里最常被忽略的一课。

还有一层**空间查询**是前面各子系统都在悄悄用的：音频要「以听者为中心找 64 个声源」、AI 要「找 20 米内的敌人与掩体」、物理要「找可能碰上的物体对」——它们全都调用同一个空间索引，只是查询半径与过滤器不同。**把空间结构做成全引擎共享的基础设施（而不是渲染私有），是场景管理成熟的标志**——这也在提醒我们，场景管理是「横切」的，它服务于引擎的每一个子系统。

## 5 动态与静态：空间结构的维护策略

空间结构最大的工程分岔在**动静之分**：

**静态场景**（地形、建筑、家具）几乎不变，可以用最贵但最快的结构（预烘焙八叉树、预计算遮挡数据、流场寻路的速度场），因为构建成本摊在加载期。<span class="marginnote">「加载期多花几秒，运行期每秒省几毫秒」——这是静态数据的投资逻辑。它解释了为什么大型游戏的加载时间越来越长：那是一次性购买运行期性能的「首付」。</span>**动态物体**（角色、载具、飞行的弹丸）每帧在动，插入/删除/移动的频率极高，必须选更新成本低的结构。

于是现代引擎普遍**分层**：一张静态 BVH/八叉树管静态世界，一张动态结构（空间哈希或增量更新的 BVH）管动态物体，查询时两棵都查再合并。物理引擎更进一步——宽阶段碰撞检测直接用 **AABB 动态 BVH**（也叫 **Box2D/btBroadphase 的 dynamic AABB tree**），物体的 AABB 每帧更新，树靠**增量调整**维持平衡，把「每帧全量重建」的 O(N log N) 变成「只改局部」的 O(log N)。<span class="marginnote">「静态建好、动态增改」的二分法，在第三级《数据库》里几乎是同款剧本：<strong>索引的「维护成本」与「查询收益」之间永远要权衡</strong>，成熟的系统从来是「区分冷热数据、分而治之」。</span>

**辨析｜易错点：** 空间结构的「增量更新」有个经典陷阱——**AABB 的胖盒（fat AABB）**。动态物体的包围盒若每次都精确缩到当前尺寸，物体一动就频繁换叶、树抖个不停；于是引擎给每个物体留一点「余量」，把包围盒做得比物体略大，让小幅移动不触发结构调整。这个「**牺牲一点查询精度、换来稳定维护**」的余量设计，是动态 BVH 工程里最不显眼却最关键的一笔。<span class="marginnote">胖盒的思路在别处也常见：CPU cache 的「缓存行」、内存分配器的「池」、网络包的「MTU 余量」——<strong>给边界留缓冲，换来高频操作的稳定</strong>，是一条跨领域的工程通则。</span>

## 6 小结

如果把本专题前八篇比作「引擎的器官」，那场景管理就是把它们串起来的**循环系统**——渲染、物理、AI、音频的每一次空间查询，都从这套索引里取数据。理解它，也就理解了引擎里「查询」这件事为什么总是这么快。

**场景图**管变换父子关系，**空间分区**管空间邻近关系，两者并存且不可混淆。
- 空间分区四大件：**均匀网格**、**四叉/八叉树**、**BVH**、**空间哈希**——选择 = 在「查询速度」与「更新成本」之间定位。
- 空间哈希把几何查询变成 **$\lfloor x/\text{cell}\rfloor$
