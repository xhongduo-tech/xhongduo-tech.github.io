# 资源系统与资产管线

<div class="epigraph">
<p>一个游戏不是代码写出来的，而是资产堆出来的——引擎的职责，是让这堆资产能被高效地吃进运行期。</p>

## 为什么从资源系统开始

一篇 3A 游戏的体量里，代码通常只占很小一部分，剩下的是**纹理、网格、动画、音频、关卡、配置文件**——统称**资产（asset）**。而引擎里所有子系统消费的，都是资产经过转换后的**资源（resource）**。**资源系统（resource system）**就是这条「从磁盘上的资产到内存里的资源」的搬运工与仓库管理员：它负责导入、转换、加载、缓存、释放，以及最重要的——**在有限的 GPU/CPU 内存里，把几千个资产按需、按序、不卡顿地喂给运行期**。<span class="marginnote">资源系统是引擎里最「操作系统」的子系统：内存管理、缓存、并发加载、引用计数——第三级《操作系统》的虚拟内存、页面缓存、文件系统在这里全部有了用武之地。读这篇时，请带着「OS 里那套缓存与替换策略」的眼光。</span>

## 1 资产与资源：两套数据的边界

先立住一对关键区分：**资产（asset）**与**资源（resource）**不是一回事。

**资产**是**创作态**的数据——美术在 Maya/Photoshop/Blender 里做的 `.fbx`、`.psd`、`.blend` 文件。它们体积巨大、结构复杂、充满冗余（PSD 里存着几十个图层），**不适合运行期直接加载**。

常见的资产类型与它们进引擎后的资源形态，值得先铺一张表：

| 资产（创作态） | 资源（运行态） | 转换做了什么 |
| --- | --- | --- |
| `.psd` / `.tga` | 压缩纹理（BC/DXT） | 合并图层、生成 mipmap、压缩 |
| `.fbx` / `.gltf` 网格 | 顶点缓冲 + 索引缓冲 | 坐标轴转换、剔除冗余顶点、合并材质 |
| `.fbx` 动画 | 压缩动画资源 | 通道量化、剔除常数通道 |
| `.wav` / `.flac` | ADPCM/Vorbis 音频 | 重采样、压缩、预计算衰减参数 |
| 关卡编辑文件 | 场景资源 + 空间索引 | 烘焙光照、生成导航网格 |

这张表也暗示了资源系统的规模：**一个中型项目有几千到几万个资源实例**，每一个都要被追踪、去重、按需加载。所以资源管理器的「账本」通常本身就是一套数据库。

**资源**是**运行态**的数据——引擎直接吃进内存的、针对目标平台优化过的格式（压缩纹理、蒙皮网格、预计算好的数据）。资产到资源的转换，就是**资产管线（asset pipeline）**的主业。

为什么不能直接加载资产？三个理由：**体积**（运行时纹理不需要 PSD 的图层）、**性能**（顶点、纹理必须按 GPU 喜欢的布局排列）、**平台**（不同 GPU 的纹理格式、不同 CPU 的对齐要求不同）。**「一次创作，多端消费」——资产是创作的事实源（source of truth），资源是各平台的分发物**。<span class="marginnote">「创作态与运行态分离」是数据工程里的通用原则：源码与编译产物、设计稿与切图、数据库的逻辑模型与物理存储，都是同一个「事实源 → 派生物」结构。第三级《软件工程》里的「单一事实源（single source of truth）」正是它的哲学基础。</span>

## 2 资产管线：从 DCC 到运行时的流水线

**资产管线（asset pipeline）**是资产到资源的转化链，通常由引擎的**离线工具**执行：

**DCC 导出**：美术在 DCC 软件里做好模型/动画/材质，通过导出器（exporter）保存成中间格式（FBX/glTF 是常见的开放中间格式）。导出器同时负责前面《动画系统》提到的**坐标轴转换**、单位换算、骨骼层级校验。

**导入与转换**：引擎的**导入器（importer）**读入中间格式，做裁剪与优化——剔除不可见顶点、合并材质、把纹理压缩成目标格式（如 DXT/BC 系列）、把动画数据量化压缩。<span class="marginnote">导入器是「一次写、处处受惠」的典型：一个模型从 FBX 导入后，后续所有加载都吃转换后的资源，再也不用碰原始文件。这也是为什么引擎项目的『首次导入很慢』——那是在为每一次启动预缴性能。</span>

**烘焙与预处理**：有些资源还需要**离线烘焙**——光照贴图（把静态光照预先算进纹理）、导航网格、空间结构、流场速度场。这些「运行期太贵、加载期算」的数据，是资源管线里最重的一环，也正是《场景管理》里「静态预烘焙」的出处。

转换结果被写进引擎自己的**资源格式**（`.uasset`、`.pak` 之类），连同元数据（GUID、版本、依赖关系）一起入库。**资源之间还有依赖图**——一个角色资源引用它的骨骼、蒙皮、动画、材质，材质又引用纹理。依赖图是资源系统正确性的骨架。

## 3 资源管理器：加载、缓存与引用计数

运行期负责资源生命周期的，是**资源管理器（resource manager）**。它有三个核心职责：

**加载（loading）**：把资源从磁盘读进内存并**解码**（解压纹理、解析网格）。加载可能很慢（一个高质量纹理几十 MB），所以绝不能同步阻塞在主线程——现代引擎用**异步加载**：发出请求、后台线程读盘解码、完成后回调通知。<span class="marginnote">异步加载与主循环的配合是「帧不卡」的基石：关卡加载时画面仍在流动（转场动画、进度条），靠的就是「不阻塞主线程的加载」。这与《操作系统》里「异步 I/O、中断驱动」的思想直接同源。</span>

**缓存（caching）**：同一个资源可能被多个对象同时引用（10 个敌人共用同一个网格），资源管理器保证**每个资源在内存中只有一份实例**，所有消费者共享——这叫**资源去重（deduplication）**。查找靠 **GUID 或资源路径**的哈希表，加载过的资源进缓存，下次命中直接返回已有实例。<span class="marginnote">「一次加载、多处共享」正是第三级《操作系统》里「共享库/写时复制」、以及《数据库》里「缓冲池」的同款策略——<strong>用一次 I/O 换取所有消费者的命中</strong>。资源去重同时也是内存节省的大头：一个有 100 个重复树模型的地图，去重后只占一份内存。</span>

资源管理器对外暴露的接口，通常是「借还」式而非「拿建」式，一套典型的接口长这样：

```cpp
Handle acquire(const AssetId& id);   // 取引用：refCount+1，未加载则异步加载
void    release(Handle h);           // 还引用：refCount-1，归零则考虑卸载
Resource* resolve(Handle h);         // 句柄 → 内存实例（可能仍在加载中）
```

**句柄（handle）**在这里是「资源的间接指针」——它不直接指向内存地址，而是指向资源表里的一个条目。这样做的好处是：资源被卸载、重载后，旧句柄不会变成悬垂指针，而是统一解析到新实例（或「仍在加载」的占位）。**「用间接层换安全性」**，与《操作系统》里「文件描述符」「虚拟地址」是同一种设计——它也是第三级《操作系统》里「地址空间」思想的迷你版。

**释放（release）**：资源何时能卸载？直接「不用就删」很危险——另一个对象可能还在用。标准答案是**引用计数（reference counting）**。

## 4 公式解析：引用计数与内存预算

引用计数的规则是一对简单的账，但值得逐条看清：

$$
\text{refCount} = \#\{\text{持有该资源的消费者}\},\qquad
\text{refCount} \xrightarrow{\text{acquire}} \text{refCount}+1,\quad
\text{refCount} \xrightarrow{\text{release}} \text{refCount}-1
$$

把这三行账逐条看清：

- **第一步，读 refCount 的含义**：一个资源被多少个消费者持有，就计几。每个 `acquire` 加一、每个 `release` 减一，归零意味着「没人再用」——这时卸载是安全的。**「谁借了就必须还」**是引用计数的铁律，谁破坏它，谁就制造泄漏或悬垂。
- **第二步，读循环引用的坑**：两个资源互相引用时（材质引用纹理、纹理的调试信息引用材质），两者的 refCount 都永远 ≥1，永远不卸载——这是引用计数的经典死结。引擎的解法要么引入**弱引用（weak reference）**（不计数的引用，只用来「查」、不拿来「持有」），要么定期做垃圾回收式的清扫。
- **第三步，读「计数」与「预算」的配合**：引用计数回答了「能不能卸」，内存预算回答了「该不该卸」。当总内存逼近预算时，资源管理器会优先卸载「refCount 低 + 最近没用过」的资源——**引用计数管正确性，LRU 管淘汰策略**，两者一横一纵，构成资源生命周期的完整棋盘。<span class="marginnote">「引用计数 + 最近最少使用（LRU）」正是第三级《操作系统》里页面置换思想的资源版：计数保证没人用时能释放，LRU 保证预算紧张时牺牲最不重要的。OS 的虚拟内存、数据库的缓冲池，与资源管理器是同一门课。</span>
- **第四步，读异步与计数的纠缠**：异步加载下，同一个资源可能同时被多个线程 acquire/release，计数必须用原子操作或加锁；更麻烦的是「正在解码中」的资源——release 把计数减到 0 时，是取消解码还是等它解完再卸？成熟引擎用「引用计数 + 状态机」双重保险，把**加载中 / 就绪 / 卸载中**显式建模。

**辨析｜易错点：** 引用计数解决不了「我把资源忘了放」——`acquire` 了却不 `release`，计数一直不减，泄漏发生在「看不见的地方」，比悬垂更阴险。所以大引擎普遍加一层**泄漏检测**：关闭时把所有计数归零，报出「还有哪些资源没被释放」，当作构建检查的一部分。

## 5 流送、关卡加载与热更新

静态地「加载-缓存-卸载」还不够，现代引擎要应付的是「一边玩一边变」的世界：

**流送（streaming）**：开放世界的关卡地图巨大，不可能一次全载入。**流送**把资源按需、按区域加载：玩家走进一片新区域，后台预加载那里的纹理与网格，离开后逐渐卸载。流送与《场景管理》里「静态 / 动态分层」一拍即合——空间索引告诉你「该预载哪块」，资源管理器负责「把它喂进来」。<span class="marginnote">流送的调度通常按「距离 + 方向」预判：玩家朝北走，就先预载北边。提前量要够，否则「走到面前才加载」就会卡顿——这是「预加载换顺滑」的又一个实例。</span>

**关卡加载（level loading）**：切换关卡是最重的加载瞬间，处理不好就是长长的黑屏。引擎用三招缓解：**异步加载**（主线程继续渲染，加载在后台跑）、**转场画面**（加载时放剧情或转场动画遮住等待）、以及**增量加载**（先载入「能玩」的最小集，其余在玩的过程中补）。这三招的底层，全是「不阻塞主循环」这一条。

**热更新（hot patch / DLC）**：游戏上线后还要改。**资源热更新**让客户端只下载「变了的资源」而非整个游戏——按 GUID 与版本比对，只拉差异。它依赖资源系统的「GUID + 版本 + 依赖图」这套元数据：没有依赖图，就不知道「改了一个模型，哪些关卡要跟着重下」。<span class="marginnote">热更新与《多人游戏网络同步架构》的「增量同步」是同一思想的两个战场：网络同步传「变化的游戏状态」，热更新传「变化的资源文件」。两者的共同点都是「只传增量 + 版本对齐」。</span>

**资源审计（asset audit）**：项目规模大了，最大的敌人是「没人记得有哪些资源、谁在用它们」。成熟引擎会做**资源引用分析**：从每个关卡出发，沿依赖图扫一遍，找出「没被任何关卡引用的孤儿资源」与「被错误引用的大资源」——这正是第三级《数据库》里「引用完整性」检查的镜像。审计不是写一次就完，而是作为**构建流程的固定一环**，每次构建都跑。

**辨析｜易错点：** 流送不是「把加载变快」，而是「把加载分散」——总数据量没变，只是把一次大的卡顿拆成许多次小的、不引人注意的加载。所以流送调优的目标不是「加载更快」，而是「加载峰值更低、提前量更足」：宁可提前多载一点（多占点内存），也别让玩家在转角处撞上卡顿。

## 6 打包与平台分发

资源最终要装进安装包、发到各个平台。这一步看似是最后一公里，却藏着资源系统最硬的约束。

**打包（packaging）**：把资源、关卡、脚本、引擎本体按平台装配成最终产物（`.pak`、安装包）。打包的核心是**依赖图遍历**——从一个入口（主菜单、第一关）沿引用关系把所有需要的资源收集齐，一个都不能漏，漏了就「发布版在某个角落崩溃」。这也是为什么资源审计要在打包前跑：孤儿资源浪费体积，漏引用的资源直接是事故。<span class="marginnote">打包的「从入口沿依赖图收资源」，与图论里的「可达性分析」、以及《数据库》里「从根表出发做引用完整性检查」是同一个遍历问题。引擎里处处是图，打包只是其中之一。</span>

**平台适配（platform targeting）**：同一个资源在 PC、主机、移动端长得不一样——纹理格式不同（PC 用 BC、移动端用 ASTC）、内存预算不同、对齐要求不同。资源系统用**平台变体（platform variants）**管理：一份资产可以有多份目标格式，打包时按平台挑对应变体。这正是「一次创作、多端消费」在分发端的落实。

**构建与增量（build & incremental）**：大型项目的打包要持续数小时，所以构建系统会缓存「没变的资源」——只有被修改的资产才重新导入、重新打包，其余直接复用上一次的产物。增量构建依赖资源的「哈希 + 版本」：变了就是变了，没变就是没变，绝不含糊。这与第三级《软件工程》里的「增量编译」是同一策略。

## 7 小结

- **资产**是创作态、**资源**是运行态；资产管线负责「一次创作、多端消费」的转换。
- 资源管理器三职责：**异步加载**、**去重缓存**（GUID 哈希）、**引用计数释放**。
- 引用计数保证「没人用就安全卸」，LRU 保证「预算紧张时牺牲谁」——一管正确性、一管淘汰。
- **流送**按区域预加载开放世界，**关卡加载**靠异步 + 转场 + 增量躲开卡顿，**热更新**只拉资源差异。
- **打包**沿依赖图收齐资源，**平台变体**应对多端差异，**增量构建**复用未变产物。

在下一节，我们将站到引擎与游戏的交界处——看玩法规则如何通过脚本表达、又怎样与引擎握手，这就是**脚本系统与游戏逻辑**。
