## 为什么从动画系统开始

一张静态的角色网格不会走路，是**动画系统（animation system）**让角色活了起来。<span class="marginnote">动画系统的读者不必是美术师，但最好有一张「蒙皮数据是从哪来的」的直觉：它源自 DCC 软件里的骨骼绑定，经由《资源系统与资产管线》导入引擎——本篇讲运行期，管线篇讲导入期。</span>游戏动画与电影动画最大的不同是**实时与交互**：电影可以离线渲染每一帧，游戏却必须在玩家按下方向键的同一帧内，把「走路」「转身」「攻击」这些动作顺滑地衔接起来。动画系统要回答的问题因此格外具体：**如何用一套可复用的「姿势」数据，在任意时刻给出一帧漂亮的姿势，并在动作切换时不突兀。** 本篇沿「骨架 → 蒙皮 → 采样 → 混合」的链条展开，其中蒙皮矩阵与混合权重是本篇的两条公式主线。<span class="marginnote">动画系统坐在上一篇物理与下一篇音频之间，但它真正的邻居是渲染管线：动画算出的是一组变换矩阵，渲染管线用它们把网格顶点变形——「动画输出矩阵，渲染消费矩阵」，这是引擎里最典型的接口耦合。</span>

## 1 骨架与蒙皮：骨骼如何带动网格

**骨骼动画（skeletal animation）**的关键洞察是：**别让艺术家直接摆几万个顶点，而是让艺术家摆几十根「骨头」**。模型内部有一棵**骨架（skeleton）**，由**骨骼（bone/joint）**组成层级树——骨盆是根，脊椎是它的子，头是脊椎的子，左右腿各自分叉。<span class="marginnote">骨架的层级正是上一篇《游戏数学》里「父子变换嵌套」的实例：每一根骨头在自己的局部空间里定义变换，乘上父骨的变换就得到世界姿势。场景图（scene graph）与此是同构结构。</span>

每根骨头只关心两件事：**它相对父骨的偏移（bind pose 里的静态关系）**，以及**它当前该转成什么姿势（动画姿态）**。而角色表面那几万顶点，被**蒙皮（skinning）**绑定到若干根骨头上——每个顶点记录「它由哪些骨头影响、各自权重多少」，典型的权重数是 4（影响最多四根骨头）。

于是动画的每一帧都要做一件核心计算：**用骨骼当前姿势，把网格顶点从「绑定时的样子」变形到「当前姿势的样子」**。

这一篇还会反复出现一个思想：**动画是一个「由数据驱动、由参数调节」的系统**——同样的走路剪辑，改一下播放速度、混合权重、IK 目标，就能表达出慌张、悠闲、受伤等完全不同的状态。把「动作」从「代码」中解放出来，正是游戏动画与程序化动画（procedural animation）分道扬镳的起点。

在进入公式前，先理清动画系统的**运行时结构**——它不是一坨数据，而是一条有组织的管线：

| 环节 | 输入 | 输出 | 主舞台 |
| --- | --- | --- | --- |
| 采样 | 剪辑 + local time | 每根骨头的局部变换 | CPU |
| 姿势计算 | 局部变换 | 世界姿势（层级连乘） | CPU |
| 混合 | 多个姿势 + 权重 | 融合后的姿势 | CPU |
| 蒙皮 | 姿势 + 顶点数据 | 变形后的顶点 | GPU（或 CPU 软蒙皮） |
| 渲染 | 变形顶点 | 屏幕像素 | 渲染管线 |

这条管线的每一环都对应着本篇后续的一节——采样在 §3，混合在 §4，蒙皮是 §2 的公式，渲染交给上一篇《实时渲染管线》。

## 2 公式解析：蒙皮矩阵与绑定姿势逆

顶点变形的核心公式是蒙皮矩阵：

$$
\mathbf{p}_{\text{skinned}} = \sum_{i} w_i\;\big(\mathbf{M}_{\text{bone}_i}^{\text{anim}}\cdot \mathbf{M}_{\text{bone}_i}^{\text{bind}^{-1}}\big)\;\mathbf{p}_{\text{bind}}
$$

- **第一步，读懂 $\mathbf{p}_{\text{bind}}$**：它是在建模软件里、角色摆着「绑定姿势（bind pose，通常 T-pose）」时导出的顶点坐标。这个姿势是网格与骨架对齐的「基准态」。
- **第二步，读懂 $\mathbf{M}_{\text{bone}}^{\text{bind}^{-1}}$**：绑定姿势逆矩阵，作用是把顶点从「模型空间」挪进「该骨头的局部空间」——相当于问「在绑定姿势下，这个顶点相对这根骨头在哪儿」。它是**静态的**，建模导出时就定死，运行期只读。
- **第三步，读懂 $\mathbf{M}_{\text{bone}}^{\text{anim}}$**：当前动画姿势下，该骨头在模型空间的世界变换（由骨架层级从根一路乘下来）。它每帧随动画改变。
- **第四步，读懂求和**：一个顶点受最多 4 根骨头影响，$w_i$ 是权重且 $\sum w_i = 1$。每根骨头先把它「从绑定空间搬到骨头局部，再搬回当前姿势下的模型空间」，四根骨头的贡献按权重加权——**骨头动，顶点跟着动，且被多根骨头拉扯出平滑的曲面**（肩部、肘部尤其需要多根骨头）。<span class="marginnote">$\mathbf{M}^{\text{anim}}\cdot\mathbf{M}^{\text{bind}^{-1}}$ 这个组合常被预计算成<strong>蒙皮矩阵（skin matrix）</strong>数组，逐顶点应用时只是一个矩阵乘。GPU 里用「蒙皮矩阵数组 + 顶点权重」并行处理，正是第三级《计算机图形学》里 GPU 并行的标准示范。</span>

**辨析｜易错点：** 最常见的新手错误是只乘 $\mathbf{M}^{\text{anim}}$，忘了乘绑定姿势逆——结果是顶点飞到骨架的坐标系里，角色「爆炸」成一团。记住口诀：**先逆着绑定姿势把顶点送进骨头，再顺着动画姿势把它带回来**。

还有一个细节值得展开：**顶点到底绑到哪几根骨头，是导出的资产数据**。美术在 DCC 软件里用「权重笔刷」画出来的肩部顶点，可能 40% 归上臂、40% 归锁骨、20% 归躯干——引擎不重新决定这个分配，只忠实执行。蒙皮数据因此属于**资源管线**的一部分：导出时权重必须归一化、骨骼必须带正确的层级与命名，否则运行期蒙皮会错位。这也是为什么《资源系统与资产管线》一篇总把「蒙皮数据校验」列为导入器的重要职责。<span class="marginnote">若一个顶点完全没被任何骨头绑定，它的 $\sum w_i=0$，蒙皮后顶点留在绑定姿势原点——「模型上一撮顶点纹丝不动」往往是权重漏刷的资产问题，而不是引擎 bug。</span>

## 3 动画剪辑与采样：从关键帧到姿势

蒙皮公式里的 $\mathbf{M}^{\text{anim}}$ 从哪来？来自**动画剪辑（animation clip）**。一份剪辑（比如「走路」）由若干**通道（channel）**组成，每根骨头一条；每个通道存一串**关键帧（keyframe）**——在时间点 $t_i$ 上该骨头的局部平移、旋转（四元数）、缩放。

运行时对每根骨头做**采样（sampling）**：找到当前动画时间 $t$ 落在哪两个关键帧之间，用 **slerp**（对四元数）与 **lerp**（对平移/缩放）插值出当前姿势。上一节《游戏数学》里 slerp 的「沿大圆弧匀速插值」，在这里就是每个关节每帧都在跑的东西。<span class="marginnote">动画时间不是直接等于现实时间：引擎用一个 <strong>local time</strong> 游标在剪辑里前进，速度可调（走路快慢、攻击加速），并可被「时间缩放」控制——慢动作特效就是这么做的。</span>

采样出的局部变换，还要沿骨架层级逐层组合成世界姿势：`worldPose[bone] = worldPose[parent] × localPose[bone]`。这一步叫**姿势计算（pose evaluation）**，是每帧每根骨头都要做的层级矩阵连乘。对于几十根骨头、上百个角色，这是一笔可观的 CPU 开销，因此引擎常把「静态部分」（不受动画影响的根节点）缓存起来。

一次完整的采样-姿势循环，用伪代码看并不复杂：

```text
function evaluate(clip, t, skeleton):
    for bone in skeleton:
        local[bone] = sample(clip, bone, t)   # 在两关键帧之间插值
    for bone in skeleton.preorder():          # 从根到叶
        world[bone] = world[bone.parent] × local[bone]
    return world
```

复杂度来自规模：一个 30 FPS 的游戏，每个角色每帧都要为全部骨骼跑一遍这两层循环。于是动画数据会走**压缩（compression）**：关键帧的平移/旋转被量化、降采样，骨骼间常数通道被剔除——一段走路动画从几百 KB 压到几 KB，是「数据规模 vs 精度」的又一次权衡。<span class="marginnote">动画压缩与上一篇《资源系统与资产管线》里纹理压缩是同一类工程：<strong>在可感知损失很小的情况下，把资产的存储与带宽压到十分之一</strong>。判断压缩好坏的标准永远是「肉眼（耳）能否察觉」，而不是数值误差。</span>

## 4 动画混合：让动作平滑过渡

单段动画的采样解决不了「从走到跑」的衔接问题——如果直接硬切，角色会瞬间从走路姿势弹到跑步姿势，像被电击。**动画混合（animation blending）**让两个（或多个）姿势按权重融合：

**线性混合（crossfade / lerp）**：过渡期内，两段动画同时采样，姿势按权重 $\alpha$ 从 0→1 线性融合：

$$
\mathbf{p}_{\text{blend}} = (1-\alpha)\,\mathbf{p}_A + \alpha\,\mathbf{p}_B
$$

$\alpha$ 随时间从 0 走到 1，角色便从走路「融化」进跑步。由于姿势里旋转是四元数，混合时对每根骨头的旋转做 **nlerp/slerp**，对平移/缩放做 lerp——**「姿势混合」本质是「每根骨头的变换混合」**。<span class="marginnote">这里的 $\alpha$ 又是一个「时间参数」，但它由「过渡时长」驱动而不是由帧率驱动——与主循环里固定步长思想一致：<strong>过渡进度按累计时间算，而非按帧数算</strong>，这样在不同帧率下过渡时间恒定。</span>

**辨析｜易错点：** 混合权重必须满足 $\sum \alpha_i = 1$。若两层权重加起来小于 1，角色会「缩水」（姿势向零位偏移）；大于 1 则「膨胀」。引擎通常在混合节点出口做一次**权重归一化**。另一个常见坑是**对平移直接 lerp**——角色绕世界原点旋转时，平移插值会让角色走一条直线切过去而不是弧线；正确处理是把根骨骼的位移放进「根运动（root motion）」单独管理。

**混合树（blend tree / blend space）**更进一步：不只是一对一过渡，而是把多个姿势放在一个参数空间里（比如「速度」参数从 0 到 1 对应站→走→跑），由参数实时选取并加权融合。角色的移动动画几乎都用混合树：一个参数「水平速度」就同时驱动腿部步频与身体前倾。

**分层混合（layered blending）**：把动画叠在多个层上——下层播「走路」，上层单独播「上半身开枪」，两层按骨骼分区（掩码）融合。于是角色可以「边走路边挥手」，两段动画互不干扰。

### 状态机：动画之间如何「被决定」

混合回答了「姿势之间怎么过渡」，还要回答「何时该过渡到哪段动画」——这由**动画状态机（animation state machine）**接管。每个动画（或动画组）是一个**状态**（idle、walk、run、jump、attack），状态之间用**转移（transition）**连接，转移由**条件**触发（速度大于阈值 → walk→run，按下攻击键 → 任意→attack）。<span class="marginnote">状态机不止在动画里：本专题《游戏 AI》一篇的「状态机 AI」与《脚本系统》里的「行为驱动」都复用同一套思想——<strong>把离散的世界状态建模成节点，把事件建模成边</strong>。动画状态机是其中最简单也最成熟的一例。</span>

现代引擎在此基础上做了两种演进：**动画层混合**（上文）让同一状态内还能叠加细节；而更新的**运动匹配（motion matching）**干脆放弃手工状态机，改从一段**庞大的动作数据库**里实时检索「与当前姿势 + 目标速度最匹配的片段」再无缝衔接。前者是「设计好的规则」，后者是「数据驱动的搜索」——正如我们在 AI 系统里会看到的模式之争。运动匹配的效果更自然，代价是内存与搜索开销，以及难以解释的决策。

## 5 逆向运动学与动画后处理

采样与混合解决的是「按预设播放」，还有一类问题要按**目标**反推姿势——**逆向运动学（inverse kinematics, IK）**。正向运动学是从关节角度求末端位置（手在哪），IK 是从末端目标反求关节角度（要让手摸到杯子，肘该弯多少）。<span class="marginnote">IK 与物理引擎的「约束求解」是亲戚：两者都是在「末端条件」与「关节自由度」之间做约束满足。攀爬时手要精准抓握扶手、脚要踩准台阶，都靠 IK 在动画上做修正。</span>

IK 之后还有一层**动画后处理**：动画数据本身可能和物理世界冲突（角色脚穿进地面），引擎会做「脚部 IK 修正」让脚贴地、做「布料模拟」让裙摆飘动、做「物理交互动画」让身体被击退时自然前倾。**动画系统的最后一公里，几乎都是「让预设动画与动态世界握手言和」的修修补补**。

一个典型的处理顺序：先采样并混合出「理想姿势」，再做「物理/IK 修正」得到「真实姿势」，最后才把真实姿势喂给蒙皮与渲染。这样预设动画保证艺术表现，修正层保证物理合理，两者互不污染——**「先理想后修正」的分层思想**，在引擎的很多子系统里都能看到。
