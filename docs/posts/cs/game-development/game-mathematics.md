## 为什么从游戏数学开始

上一篇的 MVP 矩阵、本篇的四元数、以及后续物理引擎里的所有力与冲量，靠的都是同一套数学语言——**向量（vector）、矩阵（matrix）与四元数（quaternion）**。如果说主循环是引擎的心跳、渲染管线是引擎的肌肉，那这套数学就是引擎的**骨骼系统**：它把「物体在哪儿、朝哪转、怎么移动」这些世界里的基本事实，压缩成几个数，再靠一套统一的运算把它们推导出下一帧的状态。<span class="marginnote">本篇是第三级《线性代数》与第二级《向量与张量》在引擎里的「工作语言版」：那里的定理与性质，在这里全部变成了每天跑几百万次的运算。建议把线代当作先修，但本篇会自成闭环。</span>

## 1 向量：引擎的原子

引擎里最基础的量是 **向量（vector）**：一个既有大小又有方向的量。它有三个几乎无处不在的用途：

**位置（position）**：把向量当成「从原点出发的位移」，一个 $(x,y,z)$ 就标定了一个点——严格说这时的它叫**位置向量（position vector）**。整个世界的物体坐标都是这么存的。

**方向与朝向（direction）**：归一化后的**单位向量（unit vector）**只保留方向，是「朝哪看」「往哪走」「面朝哪」的标准表达。<span class="marginnote">单位向量的「大小是 1」不是可选项而是纪律：很多公式（点积求余弦、法线光照）默认向量已归一化，传一个非单位向量进去，结果会悄悄偏掉——这是新手 Debug 时最隐蔽的误差源之一。</span>

**位移与速度（delta & velocity）**：两位置向量相减得位移，位移除以时间得速度。运动学全部建立在「向量可加减、可数乘」之上。

向量的两个乘法是引擎里真正的引擎：

**点积（dot product）** $\mathbf{a}\cdot\mathbf{b}=\lVert\mathbf{a}\rVert\lVert\mathbf{b}\rVert\cos\theta$：结果是一个标量。当两个向量都是单位向量时，点积就是夹角余弦——于是「敌人在我前方多少度」变成一次点积；点积正负还能判断前后关系（背对时点积为负）。
**叉积（cross product）** $\mathbf{a}\times\mathbf{b}$：结果是**垂直于两者**的新向量，大小等于两向量围成平行四边形的面积。它的方向由**右手定则**决定，用途包括：由两个切向量算出法线、判定旋转方向、构造正交基。<span class="marginnote">叉积对次序极其敏感：$\mathbf{a}\times\mathbf{b}=-(\mathbf{b}\times\mathbf{a})$。在左手坐标系与右手坐标系之间迁移引擎代码时，叉积方向会反转——这是移植到另一套坐标约定时最经典的「神秘 bug」来源。</span>

**辨析｜易错点：** 点积结果还能用来做「分量投影」：向量 $\mathbf{a}$ 在单位向量 $\hat{\mathbf{b}}$ 上的投影长度正是 $\mathbf{a}\cdot\hat{\mathbf{b}}$。这一条看似简单，却是「把一个速度分解成沿路径方向与垂直方向」「把力分解成法向与切向」等一切分解运算的基础——物理引擎里法向冲量与切向摩擦的分家，就是从这里开始的。

### 坐标系约定：容易被忽视的「第一事实」

在进入矩阵之前，必须先把坐标系这个前提说清，因为它是引擎数学里**最先被写下、也最常被默认**的设定。三维引擎通常用**右手系**（Z 轴向观察者，$\mathbf{x}\times\mathbf{y}=\mathbf{z}$），DirectX 传统上用左手系，而美术软件（Maya 用 Y 轴向上、Z 轴指向屏幕外）与引擎（常 Y 向上）之间还隔着一次坐标轴交换。向量与矩阵的公式在两个约定下**含义不变，但具体矩阵元素与叉积方向会镜像**。

**辨析｜易错点：** 模型从 Maya 导入引擎后「整个反转了」，90% 的原因不是导入工具坏了，而是坐标约定不一致：一边 Y-up 一边 Z-up。每个成熟的资产管线都在导入阶段做一次显式的**轴转换（axis conversion）**，这也是本专题《资源系统与资产管线》一篇里 DCC 与引擎接口的核心议题。<span class="marginnote">判断一个坐标系是左手还是右手：把大拇指、食指、中指依次指向 X、Y、Z 轴，若与右手一致则是右手系。跨引擎移植代码时，把「坐标约定」写进接口注释，能省下无数个「为什么模型反了」的夜晚。</span>

## 2 矩阵：变换的组合器

如果说向量是「名词」，矩阵就是「动词」——它把向量变成另一个向量。**旋转、缩放、平移**都能写成矩阵，引擎里统一用 $4\times 4$ 齐次矩阵（含平移）表达。

矩阵最了不起的性质是**组合性**：连续施加多个变换，等价于先乘一个变换矩阵。上一篇的 **MVP** 就是活例。但矩阵不是没有代价的：旋转矩阵存 9 个元素（齐次下更多），插值困难（矩阵插值通常不保持正交性，会引入拉伸），还容易出现数值漂移——旋转矩阵相乘久了，会逐渐退化成「不纯的旋转」，需要反复正交化修复。

于是引擎在「旋转」这个领域另寻了一种更优美的表示——**四元数（quaternion）**。

### 变换的两种存储风格

矩阵的世界里还有一场「组织之争」，值得提前标注。**行主序（row-major）**与**列主序（column-major）**决定了两件事：数组里第 4 个元素是平移量还是第 13 个是，以及向量与矩阵相乘是写成 $\mathbf{v}\mathbf{M}$ 还是 $\mathbf{M}\mathbf{v}$。这纯粹是**存储与书写的约定**，但混用时后果是灾难性的——矩阵会以转置后的方式相乘，表现成「物体绕着错的方向转」。引擎与图形库之间（如与 DirectXMath、glm、Eigen 的互操作）第一件事就是对齐主序约定。<span class="marginnote">一个实用的自检法：用矩阵把一个点沿 +X 平移 1 单位，若结果没动，多半是主序或乘序写反了。数学上「$\mathbf{M}\mathbf{v}$ 对列向量」与「$\mathbf{v}\mathbf{M}$ 对行向量」完全等价，只是书中写法不同——引擎代码里统一约定即可。</span>

## 3 欧拉角的问题：为什么引擎弃用它

先看看引擎为什么不用直觉上最亲切的 **欧拉角（Euler angles）**（绕 X 轴俯仰 pitch、绕 Y 轴偏航 yaw、绕 Z 轴翻滚 roll）。三个数确实好懂，但它有两个硬伤：

**万向锁（gimbal lock）**：当两个旋转轴在某个角度重合时，系统丢失一个自由度。典型场景：俯仰拉到 ±90°，偏航与翻滚变成同一个动作，无法独立表达。<span class="marginnote">《游戏引擎架构》里有个著名的演示：用欧拉角做相机旋转时，一旦 pitch 到正上或正下，相机的 yaw 与 roll 就「打架」——画面开始不可控地旋转。航天与动画工业也为此吃过苦头。</span>

**插值不自然**：对三个欧拉角分别做线性插值，角度在途中不会沿「最短路径」走，会出现诡异的甩头。

**四元数把「旋转」改写成「四维单位球上的点」**：既没有万向锁，插值又有优雅的数学解。它是引擎旋转事实上的标准。

## 4 公式解析：四元数旋转与球面插值

四元数可看作 $q=(w,\ x,\ y,\ z)$，其中 $\mathbf{v}=(x,y,z)$ 是虚部向量，$w$ 是实部，并满足 $\lVert q\rVert=1$（单位四元数）。用它对三维向量 $\mathbf{p}$ 做旋转的公式是：

$$
\mathbf{p}' = q\,\mathbf{p}\,q^{-1}
$$

- **第一步，理解 $q$ 与轴角的关系**：单位四元数直接编码了「绕轴 $\mathbf{u}$ 转 $\theta$ 角」：$q=\left(\cos\frac{\theta}{2},\ \mathbf{u}\sin\frac{\theta}{2}\right)$。**半角**是这个公式的灵魂：为什么是 $\frac{\theta}{2}$ 而不是 $\theta$？因为公式要乘两次 $q$（先左乘再右乘 $q^{-1}$），两个半角叠加正好凑成一次完整的 $\theta$ 旋转。
- **第二步，理解 $q^{-1}$**：单位四元数的逆就是共轭：$q^{-1}=(\overline{w},\ -\overline{\mathbf{v}})$。对单位四元数，它等于「反向旋转同样角度」。$q\,\mathbf{p}\,q^{-1}$ 读作「先转 $\frac{\theta}{2}$，再转 $\frac{\theta}{2}$」——两个半程合起来，中间的冗余维度被 $q^{-1}$ 消掉，只留下绕 $\mathbf{u}$ 的净旋转。
- **第三步，理解它的代价**：这条公式比矩阵乘法复杂。所以实际引擎常把单位四元数**先转成旋转矩阵**再批量乘顶点——每帧只转换一次，换得后面每顶点一次的廉价矩阵乘。**「换表示来换成本」是引擎数学的常态**。
- **第四步，看插值为什么优雅**：两个单位四元数 $q_1,q_2$ 之间的**球面插值（slerp）**定义为

$$
\operatorname{slerp}(q_1,q_2,t)=\frac{\sin\big((1-t)\Omega\big)}{\sin\Omega}\,q_1 + \frac{\sin(t\Omega)}{\sin\Omega}\,q_2
$$

其中 $\cos\Omega=q_1\cdot q_2$。它的直觉是：在四维单位球上沿**大圆弧**匀速插值，角速度恒定，且不偏离球面——这正是「骨骼动画从走路过渡到跑步」时每一帧关节角度需要的东西。若直接对矩阵或欧拉角做线性插值，姿态会在中途「飘」出合理范围。<span class="marginnote">注意 $\Omega\to 0$ 时 slerp 分母趋零，引擎会退化为普通线性插值避免除零；同时要处理 $q_1\cdot q_2\lt 0$ 时取负（走短弧），否则动画会绕远路。这些「数值卫生」细节是动画系统里天天在踩的坑。</span>

## 5 游戏数学的应用地图

把这套语言放到引擎各处，会看到同一套工具反复登场：

| 场景 | 向量 | 矩阵 | 四元数 |
| --- | --- | --- | --- |
| 角色移动 | 位移/速度向量 | 模型矩阵 | 转身四元数 |
| 相机控制 | 视线方向 | 视图矩阵 MVP | 相机朝向插值 |
| 物理碰撞 | 法线/冲量 | 惯性张量 | 刚体姿态 |
| 骨骼动画 | 骨偏移向量 | 蒙皮矩阵 | 关节旋转插值 |
| 寻路 | 路径点 | 格子变换 | 朝向平滑 |

**Transform（变换组件）** 几乎总被实现为「位置向量 + 旋转四元数 + 缩放向量」，而不是一堆矩阵——因为前三个量可读、可插值、无冗余；矩阵只在最终渲染或物理结算时才被临时组装出来。这套「**以向量/四元数为存储、以矩阵为计算**」的分工，是引擎数学最大的设计品味。

用一份极简的结构体把这个惯例钉死：

```cpp
struct Transform {
    Vec3    position = {0, 0, 0};   // 平移：向量
    Quat    rotation = Quat::identity(); // 旋转：四元数
    Vec3    scale    = {1, 1, 1};   // 缩放：向量
    Mat4x4  toMatrix() const;       // 需要时再组装成 4x4 矩阵
};
```

从 `Transform` 到渲染，只差一次 `toMatrix()` 的调用——父节点相乘得到世界矩阵，再乘上视图/投影矩阵，就接上了上一篇 MVP 的末尾。**父子的变换相乘**还会引出「局部空间与父空间」的嵌套，它是场景图（scene graph）的基础，我们留到《场景管理与空间数据结构》一篇正式展开。<span class="marginnote">注意组合次序：通常「先缩放，再旋转，最后平移」——先旋转再缩放会得到斜切的假缩放。四元数里的顺序也是「先本地旋转，再叠加父旋转」。这些细节正是第三级《线性代数》里「矩阵乘法不可交换」在引擎中的血肉化。</span>

## 6 小结

- **向量**表达位置、方向与速度；**点积**算夹角与前后，**叉积**算法线与面积，两者是引擎运算的原子。
- **矩阵**负责变换与组合（MVP）；代价是存储冗余、插值困难、数值漂移。
- **欧拉角**直观但有**万向锁**与插值不自然的硬伤，引擎旋转事实标准是**四元数**。
- 单位四元数 $q\,\mathbf{p}\,q^{-1}$ 编码「绕轴 $\mathbf{u}$ 转 $\theta$」，半角公式是它的灵魂；**slerp** 沿大圆弧匀速插值，是动画过渡的标准工具。
- Transform 的存储惯例：**位置向量 + 旋转四元数 + 缩放向量**，需要时才组装矩阵——「以向量 / 四元数为存储、以矩阵为计算」。
- 齐次坐标用第 4 个分量 $w$ 让平移也能写成矩阵乘，而 $w$ 还参与透视除法——MVP 公式里它一人分饰两角。

在下一节，我们将把这套数学推入运动的世界——看力、冲量与碰撞如何被积分进每一帧，这就是**物理引擎与碰撞检测**。
