## 为什么从文件系统开始

上一篇停在分区层：我们拿到了整块盘和它的镜像，但镜像里是一片连续的字节，还读不出「哪个文件是谁写的」。**文件系统（file system）**就是搭在块设备之上、把字节组织成文件的那一层——它维护「文件名 → 数据块位置」的映射，以及每个文件的时间、大小、权限等**元数据（metadata）**。对取证师而言，文件系统是双重的宝贝：一方面它是提取文件内容的高速通道，另一方面**元数据本身记录了文件的「前世今生」**——什么时候创建、什么时候修改、什么时候被访问、什么时候被删。<span class="marginnote">Carrier 的整本《File System Forensic Analysis》都在做一件事：把文件系统的每一个数据结构翻译成「这条记录能证明什么」。读文件系统，要像读案卷一样读它的字节。</span>本篇以 NTFS、ext4、APFS 三大代表为主线——它们分别来自 Windows、Linux、macOS，正是 Casey 教材第 17–19 章「三大操作系统取证」的底层支撑。

## 1 从扇区到文件：文件系统的职责

想象磁盘是一片巨大的字节海，文件系统要做三件最基本的事：**分配**（决定文件数据放在哪些块）、**命名**（维护目录结构把名字映射到元数据）、**记录**（保存元数据与日志）。不同文件系统的差异，全在这三件事的具体实现上。

**块（block）/簇（cluster）**是文件系统的分配单位。NTFS 称 **cluster**，ext4 称 **block**，大小由格式化时决定（常见 4096 字节）。文件数据按块存放，一个块内的碎片浪费称为**内部碎片**。<span class="marginnote">簇大小与取证关系密切：簇越小，slack space（文件尾到簇尾的空隙）越小，能藏的数据越少；簇越大，碎片更少但 slack 更多。取证报告中「该磁盘簇大小 4096」这类参数，直接决定你能否判断某个文件是否「完整删净」。</span>

**元数据与目录项分离**是几乎所有现代文件系统的共同设计：目录项（directory entry）只存「文件名 + 元数据编号」，真正的时间、大小、数据块指针存在**inode**（Unix 系）或 **MFT 记录**（NTFS）里。这个分离给了取证一个巨大便利：**删除文件往往只删目录项，inode/MFT 记录还在**——只要元数据没被复用，被删文件的名字、时间、甚至内容位置都能找回来。

从取证的角度，文件系统还有一层「经济账」要算：**未分配空间与元数据碎片**。一块盘上有三种「数据」——已分配文件、未分配簇（被删文件的残留）、以及元数据自身（MFT 记录、inode、目录项、日志）。其中未分配簇与元数据碎片占据了「证据密度」最高的区域：它们不在任何目录里出现，却可能藏着被删文件的全部内容或至少是时间戳。所以**文件系统取证 = 已分配文件的提取 + 未分配空间的挖掘 + 元数据碎片的解读**三线并进，缺一不可。

## 2 公式解析：簇号到字节偏移

文件系统分析的所有「把抽象文件还原到磁盘位置」的操作，最终都归结到同一个换算：**簇号 → 字节偏移**。设某卷的起始字节偏移为 $V_{\text{start}}$，簇大小为 $C$（字节），某文件数据块所在簇号为 $n$，则该簇数据的字节偏移为：

$$
\text{offset} = V_{\text{start}} + n \times C
$$

三步拆解：

- **第一步，分清坐标系**：$n$ 是「卷内簇号」，从 0 开始；而卷本身的字节偏移 $V_{\text{start}}$ 来自上一篇的分区表（如 GPT 记录的起始 LBA × 扇区大小）。绝不要把「卷内簇号」直接当「磁盘簇号」用——差一个卷起点，一切全错。
- **第二步，乘法即定位**：$n \times C$ 把「第几个簇」翻译成「距卷头多少字节」。例如簇大小 4096、卷起点 1 MiB、目标文件数据在第 100 簇，则绝对偏移是 $1{,}048{,}576 + 100 \times 4096 = 1{,}458{,}176$ 字节。
- **第三步，工具化**：The Sleuth Kit 里 `fsstat` 报告簇大小，`istat` 列出 inode/MFT 记录的每个数据块地址，`icat` 按记录提取内容——三条命令配合，上面这条公式就变成「先 `istat` 拿簇号，再按公式换算，或直接让 `icat` 代劳」。<span class="marginnote">理解公式的价值在「调试」：当 `icat` 提取出的文件是乱码，取证师要能手动算出该簇的偏移、用十六进制编辑器核对数据是否真的在那里——这往往是找出「分区表起点错了」还是「元数据被篡改」的唯一手段。</span>

**重点**：这条公式不仅用于提取，还用于**验证**。如果 MFT/inode 声称的簇号换算出的偏移处，字节内容与文件头签名不符，只有两种可能——元数据被篡改，或该块已被重新分配。这两种情况，都是必须写进报告的发现。

**实操里还要常驻一个「扇区大小」的警惕**：`$Boot`（NTFS 引导扇区）里记录的是**每扇区字节数**与**每簇扇区数**，两者相乘才是簇大小。许多被删分区重建时，`$Boot` 与 MFT 记录的簇大小读出来不一致，这时候要以哪边为准？——Carrier 的建议是**先怀疑「最后被修改的那一边」**，因为恶意篡改往往只改了分区表或引导扇区之一，而 MFT 记录是「天然难改」的一方。这类「哪个字段更可信」的判断，正建立在对手工换算的熟练上。

## 3 NTFS 的取证视图

NTFS 是 Windows 的默认文件系统，其取证核心是 **$MFT（Master File Table）**：一个为每个文件保留一条 1024 字节记录的数组，记录里按**属性（attribute）**组织信息。最重要的两个属性：**$STANDARD_INFORMATION（SI）**与 **$FILE_NAME（FN）**，各自携带一套时间戳。<span class="marginnote">两个属性的时间戳可以互相印证：篡改者改了 SI 的时间，FN 的往往没改；反之亦然。两份时间不一致，本身就是「时间被动手脚」的红旗——这是 NTFS 取证最著名的交叉验证技巧。</span>

NTFS 的时间戳称 **MACB 四时间**：**M**odified（内容修改）、**A**ccessed（访问）、**C**hanged（MFT 记录变化，即元数据修改）、**B**irth（创建）。取证工具输出 `MACB` 列正是这四个时间。每个时间戳都是 64 位整数，以 100 纳秒为单位自 1601-01-01 起计。<span class="marginnote">1601 年的原点常让新手困惑——那是公历可逆的四百年周期起点，Windows 选它纯属历史包袱。换算时记得「+1601」，或用 `date` 类工具自动处理。</span>

删除与隐藏：NTFS 删除文件把 MFT 记录标记为「未使用」，SI/FN 属性往往残留——这正是「被删文件可恢复」的机制。此外两个「日志」极具取证价值：**$LogFile** 记录文件系统事务，**USN 日志（$Extend\$UsnJrnl）**记录每次文件变更的流水账，堪称「文件操作的时间胶囊」。

NTFS 还有一个隐蔽的藏身处——**备用数据流（Alternate Data Streams, ADS）**。文件可以携带 `主流` 之外的命名数据流（如 `file.txt:secret`），普通资源管理器与 `dir` 都看不见，却能被程序读写。<span class="marginnote">经典攻击：把恶意可执行文件藏进一个正常文档的 ADS，`file.txt:hidden.exe`——Windows 探针多数扫不到。取证时用 `dir /r`、`streams`（Sysinternals）或 The Sleuth Kit 的 `istat` 检查所有数据流，是 NTFS 分析的标准动作。</span>分析 ADS 时注意：流的时间戳、大小独立记录，删掉主流不等于删掉所有流——「删除文件」的语义在 NTFS 上比想象中更微妙。<span class="marginnote">USN 日志能回答「这个文件是何时被创建/改名/删除的」，即使目录项已被清空。它随系统默认开启，是 Windows 取证里被严重低估的金矿。</span>

## 4 ext4 的取证视图

ext4 是 Linux 的主流文件系统，取证核心是 **inode**：每个文件一块 256 字节的 inode，存时间、大小、权限与数据块指针。ext4 用**区段（extent）**记录连续块范围，大文件只需少数几个 extent 就能覆盖全部数据。时间戳有 **atime/mtime/ctime** 三套——注意 **ctime 不是「创建时间」，是「状态变更时间」**，改权限、改属主都会刷新 ctime，这是新手最容易搞错的一点。<span class="marginnote">没有「创建时间」是 Unix 系文件系统的老传统：inode 里根本没存 btime。所以 Linux 取证里「文件是什么时候创建的」往往要靠目录项时间、日志或 USN 的对应物（如 journal）来间接推断——这正是时间线分析要干的事。</span>

删除与恢复：ext4 删除文件会清掉 inode 里的块指针并把 inode 标记为空闲，但 inode 数据本身不归零；只要该 inode 未被新文件复用，取证师可以用 `fls` 找 deleted 项、`istat` 看 inode、`icat` 提取——即使目录项已经没了。恢复的关键参数是 **inode 号与块组**：inode 按块组分布，`fls -d` 只扫标记删除的项，`fls -D` 还能列出「inode 空闲但目录项已删」的深度候选，配合「同块组的未分配 inode 全表扫描」能捞回更多内容。<span class="marginnote">ext4 目录项里还藏着「被删名字」：删除目录项时文件名会被标记删除但保留在原地，`fls` 会以 `*` 前缀列出这类已删除项——有时文件名本身（如一份加密 ZIP 的命名）就透露了内容。</span>ext4 的 journal 与 `fsync` 相关记录也能佐证文件何时被写。整体上，ext4 的取证思路与 NTFS 同构：**先找元数据，再按元数据定位数据块，最后验证内容**。

## 5 APFS 的取证视图

APFS 是 2017 年起 macOS 与 iOS 的默认文件系统，为 SSD 与加密而设计。它给取证带来的三个新课题：**快照（snapshot）**、**写时复制（copy-on-write）**、**原生加密**。<span class="marginnote">写时复制意味着「旧版本数据不会立即被覆盖」：修改一个文件时，新数据写入新块、旧块仍保留——这在取证上是天大的好消息，等于给「被覆盖即丢失」的定律开了一道口子。但代价是快照与克隆会制造大量「看似存在其实重复」的数据，分析时要靠 inode 引用计数去重。</span>

APFS 的时间戳是 **64 位纳秒级**，自 1970-01-01 起计，精度远超 NTFS 与 ext4，足以区分亚毫秒级的写入顺序——在「到底先打开文件还是先登录」这类时间竞赛里，APFS 的纳秒时间戳几乎是降维打击。APFS 的容器（container）内含多个卷，彼此共享空间，取证分析要小心「卷边界」。此外 APFS 的加密默认开启于 iOS，macOS 可选；加密卷的镜像分析会遇到「读得出来但都是密文」的困境，这时内存取证（找密钥）就派上用场——这是后话。<span class="marginnote">APFS 的快照由 Time Machine 与系统自动产生，一个 iPhone 上可能躺着几十个历史快照。它们是天然的「历史数据备份」，但也可能是反取证者刻意制造的「假历史」——快照越多，时间线越要小心甄别。</span>

## 6 时间线分析

把各类元数据里的时间戳**按时间排序**，就得到**时间线（timeline）**——它是把零散的文件证据织成故事的核心手段。Carrier 教材的「超级时间线（super timeline）」做法是：把 MFT/inode 记录、目录项、日志、系统日志里所有时间戳统一收集、归一化、排序，生成一张「什么时刻发生了什么」的总表。<span class="marginnote">超级时间线的价值在<strong>交叉印证</strong>：仅凭文件时间戳，嫌疑人大可说「文件是别人放的」；但如果文件创建时间、登录日志、浏览器历史三者指向同一分钟，故事就圆上了。时间线让孤证连成链条。</span>

时间线分析的要领有三条：**一是多源**——文件时间、日志、网络时间、附件元数据（如 JPEG 的 EXIF）全都要采；**二是归一化**——把不同时区、不同格式的时间统一到同一坐标系（建议 UTC 存储、展示本地时区）；**三是质疑**——任何时间戳都可能被篡改，重要结论必须由多个独立时间源交叉验证。<span class="marginnote">「伪造时间」是反取证的经典手段（见第九篇）：改系统时钟、用 `touch` 改时间戳、故意制造时间漂移。时间线分析的全部功力，就在于把这份「可能被涂改的时间」与其他独立源对照，找出破绽。</span>

**工具层面**，The Sleuth Kit 自带的 `mactime` 把 `fls`、`istat` 输出的时间戳整理成按秒排序的时间线；Autopsy 在图形界面里渲染同一张时间线；更现代的 **Plaso（log2timeline）** 能吞进上百种日志格式（事件日志、注册表、浏览器历史、系统日志）统一输出超大规模时间线。工具在变，方法不变：**多源采集 → 归一化 → 排序 → 交叉印证**。

## 7 核心对比表：三大文件系统的取证要点

把三种文件系统放在一张表里，取证视角的差异一目了然：

| 维度 | NTFS (Windows) | ext4 (Linux) | APFS (macOS/iOS) |
| --- | --- | --- | --- |
| 元数据载体 | MFT 记录（属性式） | inode（256 字节） | inode + 快照 |
| 时间戳 | MACB 四时间，100ns 自 1601 | atime/mtime/ctime | 纳秒级自 1970 |
| 时间戳交叉验证 | SI 与 FN 双份 | 无创建时间，靠间接 | 快照提供历史版本 |
| 删除恢复 | MFT 记录残留 | inode 残留 | 写时复制 + 快照 |
| 特色金矿 | $LogFile、USN 日志 | extent、目录项残名 | 快照、纳秒时间戳 |
| 主要障碍 | 属性碎片、ADS | inode 复用 | 原生加密 |

**辨析｜易错点：**很多人以为「时间戳越精确越好」，其实 APFS 纳秒级时间戳反而可能暴露反取证：`touch` 这类工具通常只改到秒或微秒精度，若一个文件的时间戳恰好「干净到纳秒」，反而值得怀疑——「太完美的时间戳」本身就是异常信号。

三个文件系统之外，还有一个绕不开的**UFS（Unix 文件系统，BSD/macOS 旧版）**。Carrier 教材第 15–16 章专讲 UFS1/UFS2——它们的取证思路是 inode 系的老传统：柱面组（cylinder group）布局、`fsdb`/`clri` 一类的底层工具。如今主流是 APFS，但旧式 FreeBSD 服务器、老款 macOS 设备仍是现实世界的一部分，取证师至少要能认出 UFS 的结构并调用 The Sleuth Kit 的对应解析器。<span class="marginnote">这张表的统一结论是：无论哪种文件系统，取证师的第一动作永远是「<strong>先保全元数据，再读内容</strong>」——内容可以被伪造，但元数据里残留的痕迹（USN 日志、快照、残留 inode）往往比内容更诚实。</span>

## 8 走读：从文件系统重建一段案发经过

把这一篇的知识放进一个具体案子，最能体会「元数据即证据」。假设一起职务侵占案，嫌疑人声称涉案文件「从未在自己电脑上打开过」。取证师在镜像上做的第一件事就是**给关键文件建立时间档案**：

第一步，`istat` 读出该文件的 **MFT 记录 / inode 的全部时间戳**——NTFS 上就是 SI 与 FN 两组 MACB 四时间，先看两组是否一致。若 FN 的创建时间比 SI 的早几毫秒，通常正常（先建名字后建属性）；若两组时间差以「小时」计，就要怀疑有人改过 SI。<span class="marginnote">这是 NTFS 交叉验证的直接应用：<strong>两组时间戳「对不上」本身就是一个需要解释的发现</strong>，而不是「数据错误」——写报告时它往往比「时间吻合」更有力。</span>

第二步，查 **USN 日志**：该文件在 `$UsnJrnl` 里应有「创建/写入/改名」的记录，给出精确到系统级的事件序列；同时比对 `$LogFile` 里的事务时间，确认文件系统层没有「事后插入」的痕迹。

第三步，**跨源印证**：把文件时间与 Windows 事件日志（登录时间）、浏览器历史（同一时刻访问了哪个站点）、以及相邻文件的时间戳放在一起——若文件创建时间与一次登录、一次访问都落在同一分钟，嫌疑人的「从未打开过」就很难自圆其说。

第四步，**反证检查**：主动寻找「时间被改」的证据——`touch` 改过的文件常会留下 SI/FN 时间不一致、USN 缺失、或日志记录与文件时间矛盾这三类破绽。找不到破绽，结论才敢写「该时间戳可信」。

这一套「时间档案」流程把文件系统取证从「找文件」推进到了「讲故事」。Carrier 教材的终极观点正在于此：**文件系统的价值不在文件，而在文件身上的时间**——它是唯一能同时回答「何时」「何人可能」「证据如何」三问的系统化数据源。下一篇将离开文件系统，进入操作系统层，看注册表、事件日志与各种痕迹如何补全这张证据图景。

## M 小结

- 文件系统做三件事：**分配、命名、记录**；目录项与元数据分离让「删名字不删数据」成为常态。
- **簇号 → 字节偏移**的公式 $\text{offset}=V_{\text{start}}+n\times C$ 是一切文件系统提取与验证的基础。
- NTFS 看 **MFT 的 SI/FN 双时间戳**交叉验证 + **$LogFile/USN 日志**；ext4 看 **inode 残留 + extent**，注意 ctime 是状态变更时间而非创建时间。
- APFS 的**写时复制与快照**天然保留历史数据，**纳秒时间戳**精度最高但「太完美」反而可疑。
- **时间线分析**把多源时间戳归一化排序，用交叉印证把孤证连成链条。
- 无论哪种文件系统：**先保全元数据，再读内容**；对时间戳保持「可以相信，但必须交叉验证」的态度。
- 时间档案是**跨源印证**的产物：MFT 时间 + USN 日志 + 事件日志 + 浏览器历史四方对齐，孤证才有分量。
- 时间被篡改往往留下破绽：SI/FN 不一致、USN 缺失、日志与文件时间矛盾——**找不到破绽才敢下「可信」的结论**。
- NTFS 的 ADS、ext4 的 inode 残留、APFS 的快照是三大「藏数据/救数据」的特色战场，分析时按表逐项检查。

在下一节，我们从「文件是怎么存的」上升到「操作系统留下了哪些脚印」：**Windows 注册表/事件日志、Linux/macOS 痕迹**——文件系统之外，还有一整座日志与配置的证据库在等着我们。
