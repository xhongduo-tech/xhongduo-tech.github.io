## 为什么从网络开始

前六篇都在「一台机器内部」打转：磁盘、文件系统、操作系统、内存。但真实案件极少只涉及一台机器——恶意软件要连 C2 服务器，诈骗资金要经过网关，嫌疑人要登录远方的邮箱。**网络取证（network forensics）**把这些机器之间的「对话」纳入证据范围：流量从哪来、到哪去、说了什么。Casey 教材第五部分（第 21–25 章）按 OSI 分层逐一展开——网络基础、网络上的数字证据、因特网、物理/链路层、网络/传输层——把「网络取证」讲成一套自底向上的完整技术栈。<span class="marginnote">网络取证与内存取证天然互补：内存告诉我们「这台机器正在连谁」，网络告诉我们「这些连接实际传了什么」。前一篇 `netscan` 发现的 C2 地址，到这一篇就要靠流量与日志来落实。</span>

网络取证有一个前六篇都没有的**先天难题**：磁盘与内存是「事后可挖」，网络流量却是**如果不预先抓取，事后就永远拿不到**。抓包工具必须在流量经过的那一刻就记录，错过了就是永别——这正是网络取证「既要有预案、又要会分析」的双重性格。

## 1 网络取证的两个视角

网络取证大体分两条路线，对应不同的证据来源：

**流量取证（traffic forensics）**：直接捕获并分析网络报文——`tcpdump`/Wireshark 抓下的 `.pcap`/`.pcapng` 文件、以及交换机 SPAN 端口或网络 TAP 镜像过来的原始流量。它回答「**线路上实际流过什么**」，证据粒度最细、最不可抵赖，但只覆盖「被捕获的那段时间」。

**日志取证（log forensics）**：分析各设备自己记下的日志——防火墙、入侵检测/防御系统（IDS/IPS）、代理服务器、DNS 服务器、邮件服务器、Web 服务器。它回答「**系统记录了什么**」，覆盖面广、存续时间长，但粒度和可信度都打折扣——日志是「各设备自己的版本」，可能缺失、可能被篡改。<span class="marginnote">两条路线的证据价值排序有讲究：<strong>流量 &gt; 日志 &gt; 传闻</strong>。一条会话若能同时被防火墙日志（记录了连接）、IDS 告警（标记了异常）和抓包（还原了内容）三方印证，其证明力远高于任何单一来源。</span>

Casey 给出的方法论是先问「证据能存多久」：**交换机的 ARP 缓存、路由器的转发表、活动的 TCP 连接**是分钟级的易失证据，要先取；**防火墙连接表、IDS 告警库**能存几天到几周；**DNS 查询日志、邮件日志**可存数月；**代理与 Web 访问日志**最长。这条「网络版的易失性清单」，正是第一篇原则在网络层的翻版。

## 2 流量捕获：在正确的点、用正确的方法

抓包的成败一半取决于**抓在哪**。理想位置是「嫌疑人机器到外部网络之间的唯一咽喉」——例如网关、核心交换机镜像口、或内部 DMZ 的入口。常见的部署方式：

**SPAN/RSPAN（交换机端口镜像）**：把指定端口或 VLAN 的流量复制一份到监控端口，不改动业务路径。<span class="marginnote">SPAN 是「旁路」抓包：原始流量照常流动，监控端收到的是副本，所以对业务零影响——但它也意味着如果交换机本来就只镜像了入站方向，你只会拿到一半的故事。部署前先确认镜像方向与覆盖范围。</span>
**网络 TAP（Test Access Point）**：物理串接在链路中间的无源分光器，流量必须经过它，抓到的就是「全双工、无丢弃」的完整拷贝。
**内网主机抓包**：在特定主机上直接 `tcpdump`/`Wireshark`，适合小范围、目标明确的场景。

抓包格式与工具有讲究：`tcpdump` 用命令行做长时后台抓包（`tcpdump -i eth0 -s 0 -w capture.pcap` 全字节、不打折扣）；Wireshark 适合交互式分析；NetworkMiner、Xplico 则擅长把 pcap 自动还原成文件、邮件、图片——**从原始流量到「人类可读的证据物」**。

还有一个常被忽视的抓包来源：**目标主机自己**。一台被入侵的机器上，`netstat` 的快照、系统日志里的连接记录、甚至杀软的流量记录，都是「现场第一手」的网络证据——它们虽不如 SPAN 的 pcap 完整，却带有时机优势：机器还活着，数据还在。取证师的网络技能包里，「主机侧取证」与「链路侧取证」缺一不可，二者互补才不会被单点失效卡死。<span class="marginnote">`-s 0` 意味着「抓满每个包的全部字节」——默认的 snaplen 可能只抓包头、丢掉负载，那样就永远看不到文件内容了。取证抓包永远用 `-s 0`，这是新手最容易踩的坑。</span>pcap 文件本身也是需要哈希保全的证据，与镜像同等待遇。

## 3 公式解析：TCP 的「字节账本」

网络取证要做**流重组（flow reassembly）**——把上千个 IP 分片拼回完整的 TCP 流，才能读出 HTTP 请求、邮件正文、文件内容。重组全靠 TCP 序列号：TCP 为每个连接维护字节流的序号，接受方用「下一个期待序号」应答。二者关系是核心公式：

$$
\text{ACK} = \text{SEQ}_{\text{prev}} + \text{LEN}_{\text{payload}}
$$

三步拆解：

- **第一步，读语义**：$\text{SEQ}_{\text{prev}}$ 是对方上一个数据段携带数据的起始序号，$\text{LEN}_{\text{payload}}$ 是该段的负载字节数（不含 TCP/IP 头）。两者相加，就是「这段数据结束后的下一个字节序号」。
- **第二步，理解应答**：接收方把「已收到的最后一个字节 + 1」写进 ACK 字段发给对方，意思就是「我确认到这儿了，下一个给我这个序号」——所以 $\text{ACK} = \text{SEQ} + \text{LEN}$ 恰好是「账目对上」的数学表达。核对每一段的 ACK 是否等于上一段的 SEQ+LEN，能立刻发现丢包、重传与乱序。
- **第三步，用于重组**：把同一连接的所有段按 SEQ 排序、按 LEN 拼接，就得到连续的数据流；Wireshark 的「Follow TCP Stream」与 `tcpslice`/`editcap` 的重组功能，底层都是这一套账本逻辑。<span class="marginnote">TCP 还有一个容易被忽略的证据含义：<strong>重传与乱序反映网络路径</strong>。多次重传通常意味着链路拥塞或被干扰；大量乱序可能暗示走了多条路径（或被人为分片注入）。在「邮件是不是被篡改后重发」这类问题上，序列号模式常能给出线索。</span>

**重点**：TCP 序号是无符号 32 位，约 4 GiB 回绕一次。高速链路上长连接会多次回绕，重组工具必须处理回绕，否则高序号段的排序会错——这是流重组里最常见也最隐蔽的实现坑。

## 4 协议还原与应用层证据

抓下流量只是开始，**还原**才是产出：把原始字节翻译成「某人某时刻下载了某个文件、发了某封邮件、访问了某个网址」。可还原的应用层证据包括：

**HTTP 会话**：请求行、响应头、URI、Referer、Cookie——完整还原「浏览了什么、上传了什么、下载了什么」。<span class="marginnote">HTTP 取证的一个经典推论：<strong>URI 本身就在叙事</strong>。`/download/tool_erase.exe` 或 `/search?q=xxx` 这样的请求串，即使没有文件内容，也足以佐证「某人检索/下载了什么」。</span>
**邮件（SMTP/POP3/IMAP）**：发件人、收件人、主题、正文、附件——整封邮件的完整重建。
**FTP/文件传输**：文件名、目录、传输方向与字节数。
**DNS 查询**：域名解析记录——「这台机器解析过哪些域名」是定位 C2、定位访问目标的金矿。
**VoIP/即时消息**：协议还原后可恢复会话内容（在未加密或密钥可得的场景）。<span class="marginnote">现代即时消息多走 TLS，内容还原受限；但<strong>元数据仍在</strong>——会话建立时间、对端 IP、连接时长、数据量。Casey 强调「拿不到内容，就拿元数据；元数据也是证据」，这条原则贯穿整个加密时代。</span>

还原工具链上，Xplico 与 NetworkMiner 会自动把 pcap 拆成「文件+图片+邮件」的分类物证；Wireshark 的协议解码器覆盖数百种协议；对 TLS 流量，若能在内存取证或密钥交换点拿到会话密钥（如 SSLKEYLOGFILE），也能解密还原——这又把网络取证与《内存取证》连了起来。

## 5 日志关联分析

日志取证的功夫在**关联**：把不同设备各自记录的片段，按时间与五元组（源 IP、源端口、目的 IP、目的端口、协议）对齐，拼成一条完整的事故链。一个典型场景——内网主机外联 C2：

防火墙日志显示「内网 IP 192.168.1.50 持续向 45.77.x.x 的 443 端口建立连接」；IDS 告警标记「该主机有 shellcode 特征」；DNS 日志显示「该主机反复解析 `cdn-update.pw`」；代理日志显示「同一主机访问过可疑更新脚本」。四条日志指向同一 IP、同一时间段——**单一来源都可能被解释成「误报」，四条对齐后几乎无法抵赖**。<span class="marginnote">关联分析的两个工程前提：<strong>统一时间基准</strong>（所有设备用 NTP 同步，否则跨设备时间对比全是错的）与<strong>统一日志格式</strong>（把 syslog、厂商私有格式、Windows 事件日志归一化到同一 schema）。这两件事不做，再好的关联工具也白搭。</span>

工具层面，SIEM（如 Splunk、ELK、Arkime/Zeek 生态）承担「收集 → 归一化 → 检索 → 关联」的重任；Zeek（原 Bro）则偏「协议分析 + 日志生成」，把流量流变成结构化事件。Casey 教材第 22–25 章的建议始终一致：**先定好「要回答什么问题」，再选日志与流量来源**——否则只会淹没在海量告警里。

关联分析还要记得「反向看」：**攻击者同样在看着日志**。清除防火墙记录、篡改系统日志时间、用加密隧道掩盖通信，是网络反取证的常规动作。此时，`tcpdump` 抓下的原始 pcap 因不在受害者控制之外往往安然无恙，成了「日志被清洗后」最后的凭证——这再次印证「流量 > 日志」的排序不是教条，而是实战规律。

## 6 核心对比表：流量取证 vs 日志取证

把两条路线并排对比，各自的能力边界一目了然：

| 维度 | 流量取证 | 日志取证 |
| --- | --- | --- |
| 证据来源 | 抓包文件（pcap/pcapng） | 各设备日志（防火墙/IDS/DNS…） |
| 回答的问题 | 线路上实际传了什么 | 系统记录了什么 |
| 时效 | 只在抓包期间有效 | 可存续数天到数月 |
| 粒度 | 字节级，含内容 | 事件级，多无内容 |
| 不可抵赖性 | 高（原始流量） | 中（各设备自述） |
| 分析重点 | 流重组、协议还原 | 时间对齐、五元组关联 |
| 代表工具 | Wireshark、Xplico、Zeek | SIEM、防火墙日志检索 |

**辨析｜易错点：**「抓了包就等于有证据」是最大误区。pcap 只是原始素材——**不经过流重组与协议还原，它只是一堆十六进制**；而还原过程的每一步（工具、版本、过滤条件）都要记录，因为「你是怎么得到这个文件内容的」与「文件内容本身」同等重要。<span class="marginnote">网络取证的报告纪律因此格外严格：还原出的文件要单独哈希、单独保全，与 pcap 一并移交——这正是第一篇证据链原则在网络层的延续。</span>

## 7 网络取证的挑战与应对

网络取证有四个绕不开的对手：

**加密**：TLS 让内容取证失去抓手，只能靠会话密钥、TLS 元数据与「解密前置的合规部署」（如企业代理解密）。这是当前网络取证最大的现实课题。
**规模**：万兆链路的抓包每小时可达数十 GB，存储与检索压力巨大——所以才有「只抓告警关联的会话」「用 Zeek 只记元数据」这类折中设计。<span class="marginnote">规模问题的务实解法是<strong>分级取证</strong>：默认只留元数据与关键会话，出问题时再回溯到「完整抓包」的特定时段。预先想好「什么值得全留」，是网络取证架构师的核心职责。</span>
**易失**：ARP 缓存、活动连接、路由表，分钟级消失；网络设备重启即失。应对靠「先取易失」清单与持续监控。
**反取证**：恶意流量可用加密隧道、域前置（domain fronting）、匿名网络（Tor/I2P）伪装，日志可能被清、时间可能被改——应对靠跨源关联与「伪装本身是线索」的研判。

**重点**：网络取证的方法论一句话——**抓全、留痕、关联、还原**。抓全是部署问题，留痕是证据纪律，关联是分析艺术，还原是产出能力。四者缺一不可；而它的终极价值在于把前面六篇的「单机故事」连成「跨机行动」——这也正是本专题从「机器内部」迈向「机器之间」的最后一跳，为《移动设备取证》《恶意软件分析与反取证》铺好了「数据从哪来、到哪去」的坐标系。

## M 小结

- 网络取证分**流量取证**（pcap 原始报文）与**日志取证**（各设备日志）两条路线，流量 > 日志 > 传闻。
- 抓包位置决定成败：**SPAN 镜像、网络 TAP、主机抓包**三选一，`tcpdump` 永远用 `-s 0` 全字节抓取。
- 流重组靠 TCP 序号账本：**ACK = SEQ + LEN**；32 位序号会回绕，重组工具必须处理。
- 协议还原产出**HTTP/邮件/文件/DNS/VoIP**等应用层证据；拿不到内容就拿元数据，元数据也是证据。
- 日志关联的核心是**统一时间基准 + 统一格式**，按五元组把多源日志拼成完整事故链。
- 四大挑战：**加密、规模、易失、反取证**；方法论是抓全、留痕、关联、还原。
- 主机侧与链路侧取证**互补**；日志可能被清洗，而链路侧的 pcap 往往是最后的凭证。
