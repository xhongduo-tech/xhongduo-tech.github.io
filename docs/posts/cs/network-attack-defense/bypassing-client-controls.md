## 为什么从绕过客户端控件开始

上一节我们用 Burp 建立了「能看到并修改每条 HTTP 请求」的能力——这一节就用它来做第一件具体的事：**绕过客户端控件（bypassing client-side controls）**。WAHH 第 5 章指出一个 Web 安全里最朴素的真理：**所有运行在浏览器里的防御都不可信**。

开发者为了省事，常把校验逻辑放在 JavaScript 里（前端校验）、把关键数据藏在隐藏字段里、甚至用混淆 JS 加密关键流程——但这些「防线」全在攻击者眼皮底下运行，而攻击者只需把请求交给 Burp，就能完全绕过它们。

本节拆解三类经典客户端控件的绕过手法，它也是整个 Web 渗透系列里「最入门、却最反映攻防思维」的一课。

<span class="marginnote">客户端控件的本质：<strong>它在客户端（浏览器）运行，客户端又完全受攻击者控制</strong>——所以任何只在客户端实现的「安全」都是形式安全。服务器必须假定「一切输入都不可信」并自行校验。这是 WAHH 的核心立场，也是本专题反复强调的「输入与信任」主题。</span>

## 1 前端校验：改了浏览器就改了规则

**客户端校验（client-side validation）**最常见的形式是**用 JavaScript 在表单提交前检查输入**——长度限制、格式校验（邮箱/手机号）、必填项。它设计的初衷是「提升用户体验、减少无效请求」，却被开发者错误地当成了「安全措施」。

**绕过手法**：前端校验只拦截「浏览器里的合法表单」——攻击者直接**用 Burp Repeater 构造一个不经过 JS 的 HTTP 请求**，绕开一切前端检查。比如前端限制密码长度 ≤8，攻击者直接提交 20 字符的口令测试注入，服务器只要没做后端校验就照单全收。

**核心要点｜为什么前端校验拦不住攻击者：** 校验代码在浏览器里运行，而浏览器是攻击者的地盘——开发者「信任」了一个被对方完全控制的环境。**正确做法**：前端校验只做体验优化，**后端必须重复全部校验**（服务端校验是不可省略的安全底线）。

<span class="marginnote">前端校验在 CTF Web 题里几乎是一道「送分题」：题目用 JS 限制输入、或把正确口令写在前端 JS 里，直接看源码或改请求即可。它也是「信任客户端」这一大类漏洞的入门款——后面隐藏字段、Cookie 篡改都是同一主题的变体。</span>

## 2 隐藏字段与参数篡改：别信页面告诉你的

**隐藏字段（hidden field）**：HTML 表单里 `<input type="hidden" value="...">` 字段——它在页面上不可见，但**随表单一起提交**。开发者常把「不该让用户改」的数据放在这里：商品价格、用户 ID、角色权限、折扣码。

攻击者只需改请求里的隐藏字段值，就能篡改服务器收到的数据。

**经典案例｜价格篡改**：电商表单里 `<input type="hidden" name="price" value="100">`——攻击者把 `value` 改成 `1` 再提交，服务器若直接用该字段计价，攻击者就以 1 元买到 100 元商品。

这属于**参数篡改（parameter tampering）**，是隐藏字段漏洞的最典型形态。

**辨析｜易错点：** 隐藏字段「隐藏」的只是**视觉效果**，不是安全——它在 HTTP 请求里完全可见、可改。

同样的错误还出现在：把用户身份放进**可篡改的 Cookie**（如 `role=user` 改 `role=admin`）、把路径或文件名交给客户端构造（如 `file=doc1.pdf` 改成 `file=../../etc/passwd`）。

凡是「客户端提交的关键数据」，服务器都必须在后端重新验证其可信性。

**核心要点｜客户端提供的「可信数据」清单：**

| 数据形态 | 常见字段 | 攻击 |
| --- | --- | --- |
| 隐藏字段 | price、role、uid | 参数篡改 |
| Cookie | 身份、角色 | 篡改提权 |
| 参数 | 文件名、路径 | 路径穿越 |
| 下拉/单选 | 预设值 | 改值越权 |

## 3 JS 混淆与前端加密：伪装成安全的把戏

当开发者发现「隐藏字段能改」之后，下一招是**用 JavaScript 把逻辑藏起来**——**JS 混淆（obfuscation）**、前端加密、甚至自定义编码，试图让攻击者「看不懂」而放弃。

**混淆的本质**：把 JS 源码变得难以阅读（变量名压缩、字符串编码、逻辑扁平化），但**代码仍在浏览器里执行**——攻击者可以用 **开发者工具（F12）的断点调试**、**反混淆工具（如 de4js）**、甚至直接替换代码把混淆层剥掉。混淆提高的是**攻击成本**，不是**安全性**。

**前端加密的错误用法**：有些应用在登录时先用 JS 加密口令再发送（如先做一次 `md5`/`SHA1` 哈希）。这看似安全，实际有两个致命问题——**加密密钥在前端代码里**（攻击者看源码即得）；**服务器收到的仍是「可重放」的密文**（攻击者重放同样的密文即可登录）。

前端加密不能替代 HTTPS 与后端安全。

<span class="marginnote">「客户端防御 → 被剥掉」是一条不断升级的军备竞赛：开发者把逻辑藏进混淆 JS，攻击者用浏览器调试器在 `debugger` 断点逐行看它执行。WAHH 的立场很直白——<strong>任何必须在客户端保密的「秘密」本质上无法保密</strong>，真正的安全必须放在攻击者控制不了的服务器侧。</span>

**核心对比表｜三类客户端控件与绕过：**

| 控件 | 假设 | 绕过手段 | 正解 |
| --- | --- | --- | --- |
| JS 校验 | 攻击者用表单 | 直接发 HTTP | 后端校验 |
| 隐藏字段 | 用户改不了 | 改请求参数 | 后端信任自己的数据 |
| JS 混淆 | 攻击者读不懂 | 调试/反混淆 | 安全不放在客户端 |

## 4 从绕过到防御：服务端校验的正确姿势

真正的防御只有一个答案：**服务端校验（server-side validation）**。客户端的一切数据——表单输入、隐藏字段、Cookie、请求头——在服务端都必须被重新验证。前端校验只负责「用户体验」，服务端校验才负责「安全边界」。

**服务端校验的正确做法**：其一，对输入做**白名单校验**——明确「什么格式是允许的」，而不是「什么是不允许的」（黑名单永远有遗漏）；其二，对「价格、角色、用户 ID」这类业务数据，**不要信任客户端提交的值**，而要从会话与数据库重新读取；其三，尽量用框架级校验机制（ORM 参数绑定、表单验证器），避免手写遗漏。

**实战清单｜一次标准的绕过测试：**

- **枚举客户端控件**：检查所有表单的隐藏字段、下拉框、按钮绑定的 JS 校验。
- **改值提交**：用 Burp 修改隐藏字段与参数，逐个尝试「越界值」（价格改 0、ID 改别人的）。
- **观察服务端反应**：若服务端照单全收，说明缺少服务端校验，漏洞确认。
- **回归验证**：确认漏洞后，写进报告时要附上「服务端应如何校验」的修复建议。

**核心对比表｜客户端控件 vs 正确防御：**

| 环节 | 错误做法 | 正确做法 |
| --- | --- | --- |
| 输入校验 | 只在前端 JS | 服务端重复校验 |
| 敏感数据 | 放隐藏字段 | 服务端会话持有 |
| 安全逻辑 | 客户端混淆 | 服务端强制执行 |

<span class="marginnote">「信任但验证」是 Web 安全的第一课，也是 WAHH 全书的基调：<strong>一切客户端输入都不可信</strong>。它同样适用于文件上传（校验在服务端做）、接口鉴权（角色在服务端判定）——凡是安全边界，都必须落在攻击者控制不了的服务器侧。本专题后续的认证、会话、越权各篇，全是这个原则的具体展开。</span>

## 5 小结

- **客户端控件**包括前端校验、隐藏字段、JS 混淆——它们的共同问题是「运行在攻击者完全控制的浏览器里」。
- **前端校验**用 JS 限制输入，绕过 = 直接用 Burp 构造不经过 JS 的请求。
- **隐藏字段**把价格、角色、ID 等「可信数据」放在表单里，绕过 = 参数篡改。
- **JS 混淆**只提高攻击成本，不提供安全性——调试器与反混淆工具可剥掉任何混淆。
- **前端加密**的密钥在前端代码里，无法替代 HTTPS 与后端防护。
- 铁律：**服务器必须假定一切输入不可信，并在后端重复全部校验**。

**动手练习｜想一想：**

1. 打开一个你常用的网站，用浏览器「检查元素」找出它的隐藏字段与前端 JS 校验逻辑——想想哪些数据其实能被篡改。

2. 在不登录任何系统的前提下，用 Burp 的 Repeater 对站点的搜索/查询接口手工改一个参数，观察服务端是否做了后端校验。

这套「找字段 → 改值 → 看反应」的练习，就是绕过客户端控件的完整方法论。
