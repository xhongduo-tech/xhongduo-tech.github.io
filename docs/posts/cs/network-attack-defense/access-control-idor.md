## 为什么从访问控制继续

上一节我们守住了「会话」这张身份证。但**登录成功 ≠ 什么都能做**——系统还要决定每个身份能访问哪些资源、执行哪些操作，这就是**访问控制（access control，AuthZ）**。

WAHH 第 8 章的主题——**越权（unauthorized access）**——是 Web 应用里最普遍、也最容易被忽视的一类漏洞：开发者认真做了登录，却忘了在「登录之后的每个资源访问」上做权限校验。结果是：一个普通用户能看别人的订单、改别人的资料、甚至执行管理员操作。

本节拆解越权的三种形态：**IDOR、水平越权、垂直越权**，它们是 Web 渗透测试里「改一个数字就能攻破」的经典代表。

<span class="marginnote">回忆第9篇的「AuthN vs AuthZ」：认证（AuthN）决定「你是谁」，授权（AuthZ）决定「你能做什么」。<strong>越权是 AuthZ 的失败——认证通过，但权限校验缺失</strong>。这一组对照是 Web 安全最基础也最重要的概念对，WAHH 第6–8章正是按「认证→会话→授权」的顺序递进。</span>

## 1 越权的本质：漏掉的那次权限检查

**访问控制**要实现的是：**每个资源访问、每个操作执行前，都确认「当前用户是否有权」**。越权就是这条检查被漏掉或做错的结果。

最典型的原因是**「前端隐藏」被当成了「后端限制」**：开发者把「管理员按钮」藏起来不给普通用户看，却忘了在服务器端校验「这个操作只能管理员执行」——攻击者绕过前端，直接调用管理员接口即可越权（呼应第8篇：隐藏 ≠ 安全）。

**越权的两大分类**：

**水平越权（horizontal privilege escalation）**：**同等级**用户之间的越权——普通用户 A 访问普通用户 B 的资源。比如改 URL 里的 `id` 参数看别人的订单、改 `userid` 改别人的资料。

**垂直越权（vertical privilege escalation）**：**不同等级**之间的越权——低权限用户执行高权限操作。比如普通用户调用管理员删除接口、访问 `/admin` 页面。

<span class="marginnote">为什么越权如此普遍？因为它不是「某种技术的坑」，而是<strong>开发流程的坑</strong>——只要开发者在某个接口上「忘记」加权限检查，越权就存在。这正是它难以被扫描器发现（第5篇）的原因：扫描器无法理解「这个操作应该属于谁」。所以越权主要靠人工测试与代码审计发现。</span>

**核心要点｜越权分类：**

| 类型 | 越权对象 | 例子 |
| --- | --- | --- |
| 水平越权 | 同级其他用户 | 看别人的订单/资料 |
| 垂直越权 | 更高权限角色 | 普通用户调管理员接口 |

## 2 IDOR：改个数字就是别人的数据

**IDOR（Insecure Direct Object Reference，不安全的直接对象引用）**是水平越权最常见、最直观的形态：**应用直接用用户可控的 ID 去数据库取对象，却不校验「这个对象属于当前用户吗」**。

**典型场景**：订单查看接口 `GET /order?id=1001`——服务器拿到 `id` 直接查 `orders` 表返回订单。普通用户把 `id` 改成 `1002`，如果没校验归属，就看到了别人的订单——**IDOR 达成**。

类似地：`/profile?userid=5`、`/download?file=invoice_7.pdf`、`/api/cart?cart_id=xxx` 都是 IDOR 的温床。

**公式解析｜IDOR 的判定条件：**
$$
\text{IDOR 成立} \iff (\text{对象引用来自客户端可控输入}) \land (\text{缺少对象归属校验})
$$
两个条件缺一不可：**输入可控**（ID 在 URL/参数里，可改）+ **无校验**（服务器直接取数据，不查归属）。判断一次渗透测试「是否发现 IDOR」就看这两条同时成立没有。

防御就是把第二个条件补上：**服务端必须校验「当前用户是否有权访问该对象」**，且永远不要信任客户端传来的 ID 属于谁。

<span class="marginnote">IDOR 与越权的关系：IDOR 是水平越权的一种实现方式（用「对象 ID 直接可引用」达成）。OWASP 2021 Top 10 把「Broken Access Control」列为第一大风险类别——IDOR 正是其中最常见的形态。CTF Web 题里「改 id 拿 flag」就是 IDOR 的教学版本。</span>

## 3 垂直越权与功能级访问控制

**垂直越权**对应的是**功能级访问控制（function-level access control）**的缺失：不同角色的功能权限没有在服务端执行。

**典型场景**：应用把「删除用户」功能做成 `POST /admin/users/delete`，但只有管理员页面有入口——普通用户**直接构造这个请求**，服务器若只检查「是否登录」而不检查「是否管理员」，普通用户就能执行管理员操作。

**为什么常见？** 权限控制常被做成「前端菜单/按钮的显示控制」，而非「后端接口的调用校验」——开发者认为「菜单不显示 = 无法访问」，忽略了攻击者根本不看菜单，直接发 HTTP 请求（呼应第7篇「信任但验证」）。

**核心要点｜正确 vs 错误的访问控制：**

| 层次 | 错误做法 | 正确做法 |
| --- | --- | --- |
| 前端 | 隐藏按钮/菜单 | 仅为体验，不设防 |
| 后端 | 只查「是否登录」 | 每个操作查「是否有权限」 |
| 数据层 | 直接按 ID 取数据 | 校验对象归属 |

**辨析｜易错点：** 越权经常与「会话劫持」纠缠：劫持管理员会话再访问资源，看起来像垂直越权，但本质是 AuthN 被破（冒充了管理员本人）；垂直越权则是**用自己（低权限）的身份执行高权限操作**——两者攻击路径不同，防御也不同：前者防令牌泄露，后者防权限校验缺失。

<span class="marginnote">越权的系统化测试方法：登录两个账号（A 与 B），用 A 的会话去访问 B 的资源与高权限接口——逐个对比「应该拒绝却放行」的请求。这个「双账号交叉测试」是 WAHH 第8章给出的标准流程，也是渗透测试报告里越权发现的来源。蓝队对应加固：给每个接口做基于角色的访问控制（RBAC），并定期做权限审计。</span>

## 4 如何发现与修复越权

**发现越权**的三条路：**手工双账号测试**（上面说的 A/B 交叉）；**ID 遍历**（改 `id`/`userid` 等参数看响应变化，配合 Burp Intruder 批量）；**API 枚举**（抓包看前端调了哪些接口，逐个用低权限会话试）。

**修复越权**的三条原则：**服务端校验**——所有接口都在后端做「当前用户是否有权」检查；**最小权限**——每个角色只给够用的权限；**统一授权框架**——用框架级权限中间件，避免每个接口手写、漏写。

**核心要点｜越权的生命周期：**

| 阶段 | 动作 | 工具/方法 |
| --- | --- | --- |
| 发现 | 双账号交叉测试 | Burp、手工 |
| 验证 | 遍历 ID 确认越权 | Intruder |
| 评估 | 判定影响范围 | 数据敏感度分析 |
| 修复 | 服务端 RBAC 校验 | 权限中间件 |
| 复测 | 回归确认已修 | 重新测试 |

<span class="marginnote">越权与「从极限到大模型」课程体系的连接：它在第三级《数据库原理》的「数据对象访问」、第三级《软件工程》的「授权设计」、以及第五级《安全工程》的「访问控制模型（RBAC/ABAC）」里都有对应的理论底座。攻防视角的越权，正是这些理论「缺位时会发生什么」的实证。</span>

## 5 越权的典型真实案例

越权不是理论概念，而是真实世界反复上演的数据泄露事故。

**典型案例**：某电商平台曾因订单接口的 **IDOR** 漏洞——订单查看接口直接按用户可控的订单号返回数据且不校验归属——导致大量用户的订单信息（姓名、地址、电话）可被遍历抓取。攻击者只需要写一个脚本循环请求 `order?id=1,2,3...` 就能批量拖走数据。

**教训**：这类事故的根因几乎都是同一句话——**「功能上线了，权限校验没跟上」**。而修复同样直接：在接口层统一加「对象归属校验」即可。**越权是「实现层面」的漏洞，靠统一权限框架可以系统性消灭**。

**核心要点｜越权的危害评估：**

| 危害维度 | 说明 |
| --- | --- |
| 数据泄露 | 批量拖取他人隐私 |
| 账号接管 | 改他人资料/密码 |
| 业务破坏 | 越权执行关键操作 |

<span class="marginnote">越权在 OWASP Top 10 里长期霸榜（2021 版「Broken Access Control」列第一位），但它在静态扫描与常规测试里却最容易被漏掉——因为它不是「某个函数的问题」，而是「每个接口都可能有的遗漏」。所以<strong>越权测试必须「全覆盖」：每个接口、每个角色、每条数据路径</strong>，这正是渗透测试里最考验耐心与系统性的环节。</span>

## 6 小结

- **访问控制（AuthZ）**决定「你能做什么」，越权是它的校验缺失——**登录通过 ≠ 权限到位**。
- 越权分**水平**（同级用户之间）与**垂直**（低权限提权到高权限）两大类。
- **IDOR** 是水平越权最典型形态：对象引用来自可控 ID + 缺少归属校验，改个数字就看别人的数据。
- **垂直越权**源于功能级访问控制的缺失：前端隐藏菜单 ≠ 后端限制调用，攻击者直接发请求。
- 发现越权靠**双账号交叉测试**与 **ID 遍历**；修复靠**服务端 RBAC 校验 + 最小权限**。
- 越权难以被扫描器发现，是人工测试与代码审计的重点对象。
