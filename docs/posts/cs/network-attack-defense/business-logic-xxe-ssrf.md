## 为什么从业务逻辑继续

SQL 注入、XSS 这类漏洞是「技术性」的——它们源于代码实现缺陷，扫描器能发现、模式可复现。但 Web 应用还有另一大类漏洞，**与代码无关、与业务规则有关**：兑换码能重复使用、订单可以负数量、密码找回流程可以被社工。这类**业务逻辑漏洞（business logic vulnerability）**是 WAHH 第10章的主题，也是最难自动化、最考验人脑的部分——因为「什么行为是越权的」，只有理解业务才能判断。第11章则转向**后端组件攻击**：文件上传、XXE、SSRF 这些利用服务器端组件处理逻辑的漏洞。本节把两类合并呈现：先讲业务逻辑漏洞的思维方式，再拆解文件上传、XXE、SSRF 三种典型后端攻击。<span class="marginnote">业务逻辑漏洞为什么难：它不违反「技术规则」（输入合法、请求正常），只违反「业务规则」（这样操作不合常理）。扫描器按技术规则工作，自然抓不到它。这解释了为什么 Web 渗透的终极能力不是会用多少工具，而是<strong>理解业务</strong>——WAHH 反复强调，逻辑测试是渗透测试者真正的价值所在。</span>

## 1 业务逻辑漏洞：信任假设的裂缝

**业务逻辑漏洞（business logic vulnerability）**：攻击者通过**以合法方式使用应用功能**，触发应用设计时未预料的业务后果。它不靠恶意 payload，靠的是**操作顺序、参数组合、状态绕行**的异常。

理解它最好的方式是看经典案例：

**流程绕过（workflow bypass）**。多步流程（注册→验证→付款→发货）本应顺序执行，攻击者直接跳到第 4 步的 URL，或跳过验证步骤——服务器未检查「前置步骤是否完成」。

**数量与金额操纵**。订单数量传负数、折扣叠加、价格字段改 1 分——服务器未校验业务数值的合理范围。

**重复操作**。兑换码、优惠券、抽奖可重复使用；同一请求重复提交多次均被接受。

**边界与状态异常**。并发提交两个请求（竞态条件，race condition）；一个操作未完成就触发下一个；账户状态（禁用/过期）被绕过。<span class="marginnote">竞态条件是业务逻辑漏洞里的「硬核题」：两个请求几乎同时到达，服务器按「先查后写」的顺序处理，但两次「查」都发生在「写」之前——于是余额扣两次都通过了检查。防御靠数据库事务与原子操作，这在《数据库》篇的事务并发控制里有系统的论述。</span>

**核心要点｜业务逻辑漏洞的分类：**

| 类别 | 例子 | 攻击者的「合法操作」 |
| --- | --- | --- |
| 流程绕过 | 跳过验证步骤 | 直达后续 URL |
| 数值操纵 | 负数量、改价格 | 提交超范围数值 |
| 重复利用 | 兑换码复用 | 重复提交同一请求 |
| 竞态条件 | 余额双扣 | 并发提交 |
| 状态绕行 | 禁用账户继续操作 | 复用旧会话 |

**辨析｜易错点：** 业务逻辑漏洞的**测试没有清单可循**——每个业务的规则不同，攻击面不同。方法论是：**先彻底理解业务流程（正常用户怎么走完一次完整操作），再问「哪一步可以被跳过/重复/逆序/篡改」**。WAHH 称之为「对每个功能追问攻击者的视角」，这也正是渗透测试报告里「高危逻辑缺陷」总是最值钱部分的原因。

## 2 文件上传：从图片到 WebShell

**文件上传漏洞**：应用允许用户上传文件（头像、附件、导入），但**未对上传内容做充分校验**，攻击者上传恶意文件并在服务器上执行。最典型的攻击链是**上传 WebShell**——一个包含服务端代码（PHP/JSP/ASP）的文件，访问它即可在服务器上执行任意命令。

**WebShell**：如 `shell.php` 内容为 `<?php system($_GET['cmd']); ?>`——访问 `shell.php?cmd=whoami` 就执行 `whoami` 命令。攻击者借此获得命令执行权限，进而提权、横向（见第3篇内网渗透）。

上传漏洞的校验绕过是核心战场：

**类型校验绕过**：只查 `Content-Type` 头（可改包）；只查扩展名黑名单（`.php` 禁了改 `.php5`、`.phtml`）；只查 MIME（改文件头字节伪装成图片）。
**内容校验绕过**：图片头 + PHP 代码拼合（图片马）；依赖解析差异（`shell.php.jpg` 在某些服务器上被当 PHP 解析）。
- **路径与存储绕过**：上传路径可控（`../../shell.php` 写到任意目录）、文件名可控（写进可执行目录）。

**核心要点｜文件上传攻防对照：**

| 攻击手段 | 绕过对象 | 防御手段 |
| --- | --- | --- |
| 改扩展名 | 黑名单 | 白名单扩展名 |
| 改 Content-Type | 头校验 | 服务端校验文件真实类型 |
| 图片马 | 魔数校验 | 重新编码图像/校验完整 |
| 路径穿越 | 路径校验 | 服务端固定存储路径 |

**辨析｜易错点：** 只做**扩展名黑名单**是教科书式的错误——`.php` 禁了还有 `.php3`、`.php5`、`.phtml`、`.pht`，以及大小写变体。正确做法是**白名单**（只允许图片扩展名）+ **内容校验**（读取文件真实类型）+ **不可执行存储目录**（上传目录禁用脚本执行）+ **随机文件名**（防路径可控）。「最小化存储目录的执行权限」是关键兜底。

## 3 XXE：XML 解析器的信任危机

**XXE（XML External Entity，XML 外部实体注入）**：应用解析 XML 时，XML 解析器默认允许「外部实体」引用，攻击者在 XML 里声明外部实体，让解析器**读取服务器本地文件**或**发起网络请求**。

XML 实体（entity）是 XML 里的「宏」——定义一个名字，在文档中引用时展开。攻击者的恶意 XML：

```xml
<?xml version="1.0"?>
<!DOCTYPE foo [ <!ENTITY xxe SYSTEM "file:///etc/passwd"> ]>
<foo>&xxe;</foo>
```

解析器遇到 `&xxe;` 时，按声明去读 `file:///etc/passwd`，把文件内容插入文档——应用若把解析结果显示在页面/报错里，**服务器本地文件就被读出来了**。SSRF 变体则是让实体指向内网地址（`http://169.254.169.254/` 云元数据），**以服务器身份访问内网**。

**核心要点｜XXE 的攻击面：**

| 利用方向 | 实体目标 | 效果 |
| --- | --- | --- |
| 文件读取 | `file:///etc/passwd` | 读服务器文件 |
| SSRF | `http://内网IP/` | 以服务器身份扫内网 |
| 拒绝服务 | 实体嵌套（Billion Laughs） | 解析爆炸拖垮服务 |

**防御**：**禁用外部实体**（`XXE` 防护在解析器配置里通常是「禁用 DOCTYPE/外部实体」一个开关）。现代解析器默认较安全，但老框架、手动配置的解析器常开着。<span class="marginnote">XXE 的教训与 SQL 注入同构：解析器「信任」了文档里的声明，把输入当指令。防御同样是「默认拒绝外部实体」。安全领域的规律反复出现——<strong>解析一切输入时，默认关闭「输入即指令」的能力</strong>，只在显式需要时开启并严格限制。</span>

## 4 SSRF：让服务器当攻击者的跳板

**SSRF（Server-Side Request Forgery，服务端请求伪造）**：应用存在「根据用户输入发起服务端请求」的功能（图片代理、URL 预览、Webhook 回调），但**未限制请求目标**——攻击者让服务器去请求攻击者指定的地址，服务器成了攻击者的「代理」。

SSRF 的典型危害：

**访问内网**：服务器在内网，攻击者让它请求 `http://192.168.1.10:3306` 扫描内网数据库端口——**攻击者本来到不了内网，SSRF 给了他一条隧道**。
**读云元数据**：请求 `http://169.254.169.254/latest/meta-data/` 读取云服务器的 IAM 临时凭证——**直接通向云上全部资源**。
- **绕防火墙**：外网到内网的访问被防火墙拦截，但服务器发出的内网请求不在拦截范围内。

**核心要点｜SSRF 的防御：**

| 层面 | 防御手段 |
| --- | --- |
| 输入 | 白名单允许的 URL 协议与域名 |
| 解析 | 解析 DNS 后校验 IP 非内网地址 |
| 网络 | 服务器出站流量经代理/防火墙管控 |
| 功能 | 最小化「URL 提交」类功能，移除不必要的重定向跟随 |

**辨析｜易错点：** SSRF 防御里「只校验域名、不校验 IP」是常见漏洞——`example.com` 解析到 `192.168.1.1`（域名解析后是内网 IP）就能绕过。正确做法是**解析后再校验 IP 是否在内网段**，同时防范 DNS 重绑定（TOCTOU：校验时解析一次、请求时解析到另一个 IP）。<span class="marginnote">云元数据地址 `169.254.169.254` 是 SSRF 攻击的「圣杯」：它内网可达、无需凭据、直接返回云主机角色凭证。AWS/阿里云等厂商近年为它加了防护（如 IMDSv2 强制令牌），但老配置仍大量暴露。SSRF 从「边缘漏洞」升级为「云上瘫痪级漏洞」的转折，正由此而来。</span>

## 5 小结

- **业务逻辑漏洞**不靠 payload，靠以合法方式触发未预料的业务后果——流程绕过、数值操纵、重复利用、竞态。
- **文件上传**漏洞的终点是上传 WebShell 获得命令执行；防御靠白名单扩展名 + 内容校验 + 不可执行目录。
- **XXE** 利用 XML 外部实体读取服务器文件/发起 SSRF；根治是禁用外部实体。
- **SSRF** 让服务器代发请求，可扫内网、读云元数据、绕防火墙；防御要解析后校验 IP。
- 共同母题：**解析一切输入时，默认拒绝「输入即指令」**——与 SQL 注入的防御哲学完全一致。
