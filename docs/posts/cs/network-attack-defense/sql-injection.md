## 为什么从 SQL 注入继续

如果只能选一个 Web 漏洞来讲，业界十有八九会选 **SQL 注入（SQL Injection，SQLi）**。它是 Web 安全史上影响最深远、名气最大的漏洞：1998 年首次被公开讨论，二十多年过去仍常年占据 OWASP Top 10 榜首梯队。原因很简单——**它把攻击者的输入变成了数据库的查询命令**，直接命中 Web 应用最值钱的东西：数据。SQL 注入的根源是**输入与命令没有分离**：开发者把用户输入直接拼接进 SQL 语句，数据库分不清「哪部分是数据、哪部分是命令」，于是输入被当作命令执行。本节讲透 SQL 注入的三种主流形态——**联合注入、盲注、堆叠注入**——并给出参数化查询等根治方案。本主题含「代码层面的公式解析」，我们将像拆数学公式一样，把一条注入 payload 拆解到底。<span class="marginnote">SQL 注入的思想能推广到一切「拼接」场景：操作系统命令注入（拼 shell 命令）、LDAP 注入、XPath 注入、模板注入。理解 SQLi，等于理解了「输入即代码」这一类漏洞的母题——见本专题业务逻辑篇的 XXE/SSRF，它们同根同源。</span>

## 1 注入的根源：字符串拼接

看一个经典的脆弱代码：

```sql
SELECT * FROM users WHERE username = '$username' AND password = '$password'
```

如果应用把用户输入直接填入 `$username` 与 `$password`，而攻击者提交的用户名是：

```
admin' OR '1'='1' --
```

拼接后，SQL 变成：

```sql
SELECT * FROM users WHERE username = 'admin' OR '1'='1' --' AND password = '...'
```

**拆解这条 payload 的四个部件**（这也是本主题的「公式解析」核心）：

**`admin'`**：闭合掉应用原有的字符串引号——`username = '` 已经开了一个引号，`admin'` 用单引号把它**闭合**，使后续内容脱离「字符串」身份，成为 **SQL 语法的一部分**。
**` OR '1'='1'`**：注入一个恒真条件。`'1'='1'` 永远成立，`OR` 让整个 WHERE 条件无论用户名密码如何都成立——于是查询返回表中所有行。
**`--`**：SQL 的行注释符。它把后面应用拼上的 `' AND password = '...'` **整段注释掉**，避免残留代码造成语法错误。
**` `（空格）**：`--` 后面必须跟空格（或注释尾随控制符），否则某些数据库不识别注释。

**核心要点｜SQL 注入的本质**：数据库同时收到「数据」与「命令」两种信息，且无法区分。注入 payload 干的事就是：**用引号/注释符操纵 SQL 语法边界，把攻击者代码拼进查询命令**。防御就是让输入永远只当「数据」——参数化查询（见第4节）。<span class="marginnote">`OR '1'='1'` 是 SQLi 的「hello world」，任何教材都会先讲它。但它的意义远不止「绕过登录」——它演示了注入的<strong>语法机理</strong>：闭合引号、注入逻辑、注释尾部。理解机理，才能推导出后面所有变体。</span>

## 2 联合注入：让查询「多返回一列」

**联合注入（UNION-based injection）**利用 SQL 的 `UNION` 运算符：把两条查询的结果**合并**成一张表返回。攻击者的目标是**让数据库执行两条查询**——第一条是应用原本的查询，第二条是攻击者构造的、能从数据库中拖数据的查询。

`UNION` 有严格限制：**两条查询的列数必须相同、对应列类型兼容**。所以联合注入的第一步是**确定列数**——经典方法是用 `ORDER BY`：

```sql
' ORDER BY 1--   -- 不报错
' ORDER BY 2--   -- 不报错
' ORDER BY 3--   -- 报错，说明原查询只有 2 列
```

确定列数后，用 `UNION SELECT` 指定每列的值，其中一列用来**回显数据库数据**：

```sql
' UNION SELECT username, password FROM users--
```

如果应用把查询结果的第 2 列显示在页面上，攻击者就通过这一列看到 `users` 表的用户名与口令。**报错信息是关键情报**：`ORDER BY` 报错会提示列数超界，`SELECT` 报错会提示列类型——开发者留下的报错细节，成了注入攻击的地图。

**核心要点｜联合注入流程：**

1. **确认注入点**：输入 `'` 看是否报错/异常。
2. **确定列数**：`ORDER BY N` 逐次递增，找到报错边界。
3. **定位回显列**：`UNION SELECT 1,2,3`，看哪个数字显示在页面。
4. **拖取数据**：在回显列位置填目标查询，如 `UNION SELECT username,password FROM users`。
5. **查库结构**：先拖 `information_schema`（元数据库）拿表名/列名，再拖目标数据。

**辨析｜易错点：** `UNION SELECT 1,2,3` 里用**数字**探列，是因为数字与任何列类型都兼容；而拖数据时要保证**对应列的类型**匹配（字符串列放字符串）。此外 `UNION` 要求两个 SELECT 列数严格相等——多一列、少一列都会报错，这正是「确定列数」必须先行一步的原因。

## 3 盲注：看不到回显时怎么偷数据

**盲注（blind SQL injection）**：页面**不直接回显**查询结果——注入成功与否，只能通过**应用行为差异**来观察。盲注有两种主流形态：

**布尔盲注（boolean-based blind）**。注入条件式，根据**页面是否正常返回**来推断真伪：

```sql
' AND (SELECT substring(database(),1,1))='a'--
```

如果数据库名第一个字符是 `a`，条件为真，页面正常；否则异常。逐个字符二分猜测，就能**逐字符拼出整个数据库名**——慢，但有效。用时间盲注可提速，但逐字符推断的本质不变。

**时间盲注（time-based blind）**。注入会让数据库**延迟响应**的函数，以「响应时间」作为真伪信号：

```sql
' AND IF(1=1, SLEEP(5), 0)--
```

条件为真则睡 5 秒、为假立即返回。攻击者用「睡多久」当布尔信号，适用于**布尔信号不可区分**（页面无论真假都一致）的场景。<span class="marginnote">盲注是「边信道」的经典：不直接看结果，而看「反应差异」——页面长短、响应时间、HTTP 状态码。这类技术把「一次查询能带回一屏数据」降级成「一次查询只能带 1 bit 信息」，但<strong>只要能观察差异，数据就藏不住</strong>。自动化工具（sqlmap）正是把这种逐位推断跑成脚本。</span>

**核心要点｜盲注的三种信号：**

| 盲注类型 | 信号 | 判断方式 |
| --- | --- | --- |
| 布尔盲注 | 页面正常/异常 | 条件真 → 正常 |
| 时间盲注 | 响应延时 | 条件真 → `SLEEP()` |
| 报错盲注 | 报错信息 | 用报错函数带出数据 |

## 4 堆叠注入与数据存储攻击的扩展

**堆叠注入（stacked queries）**：SQL 支持用分号 `;` 分隔多条语句，攻击者注入第二条独立语句：

```sql
'; DROP TABLE users; --
```

如果数据库驱动允许执行多条语句（部分驱动默认禁止），堆叠注入可以执行**任意后续语句**——增删改、建表、写文件，远超 `SELECT` 的读取范围。**辨析｜易错点：** 联合注入受「只能 SELECT」与「列数相等」约束，堆叠注入则能执行任何语句——但很多数据库连接驱动（如 JDBC 默认）禁止多语句执行，所以堆叠注入不是总能成立，需逐目标探测。

**数据存储攻击**是注入在「存储层」的扩展形态：**NoSQL 注入**（MongoDB 的 `$ne`（不等于）、`$gt`（大于）、`$regex`（正则）等操作符被注入进查询条件，实现「绕过认证」与「拖库」）。NoSQL 不像 SQL 有严格的语句结构，攻击者通过操纵 JSON/操作符字段，让查询逻辑失真。**XXE 与 SSRF**（本专题业务逻辑篇）则是「数据存储/数据获取」环节的另一类攻击。**辨析｜易错点：** 参数化查询只能防 SQL 注入，防不了 NoSQL 注入（因为 NoSQL 查询是结构化对象而非字符串拼接）——NoSQL 注入的防御靠**白名单操作符、类型校验与输入结构校验**。

## 5 防御：让输入永远只是数据

SQL 注入的防御是 Web 安全「输入处理」的最佳示范，层层递进：

**第一道：参数化查询（Prepared Statement）**。用占位符 `?` 绑定参数，数据库把输入**当作数据**而非命令处理——**从根本上消灭拼接**。这是根治 SQL 注入的首选方案，几乎所有现代框架（JDBC `PreparedStatement`、PHP PDO、Python 的 `execute`）都原生支持。

**第二道：输入校验与白名单**。对输入做类型、长度、格式校验；对「用户 ID」「排序字段」等用白名单限制取值，让非法输入在进入查询前就被拦截。

**第三道：最小权限与纵深防御**。数据库账户最小权限（不用 root 连应用）、错误信息不泄露 SQL 细节（关 `display_errors`）、WAF 拦截明显注入特征（`' OR 1=1`、`UNION SELECT`）。

**核心要点｜三层防御对比：**

| 层次 | 手段 | 对抗什么 |
| --- | --- | --- |
| 参数化 | 预编译占位符 | 一切拼接型注入 |
| 输入校验 | 类型/白名单 | 畸形输入 |
| 纵深 | 最小权限、WAF | 绕过尝试 |

**为什么「过滤特殊字符」不是好方案？** 黑名单过滤（屏蔽 `'`、`--`、`SELECT`）看似简单，实则**永远有遗漏**——编码绕过（`%27`）、大小写绕过（`SeLeCt`）、注释符变体，而且容易误伤正常输入（用户名字里带 `'` 怎么办？）。**白名单参数化远优于黑名单过滤**——这个「白名单优于黑名单」的教训，也适用于 XSS（第14篇）与命令注入（第16篇）的防御。

## 6 小结

- **SQL 注入**把用户输入拼进查询命令，根源是**输入与命令未分离**，常年位居 OWASP Top 10 榜首。
- 三种主流形态：**联合注入**（UNION 多返回一列拖库）、**盲注**（布尔/时间边信道逐位推断）、**堆叠注入**（分号执行任意语句）。
- 联合注入流程：**确认注入点 → ORDER BY 定列数 → 定位回显列 → 拖数据**。
- 盲注是**边信道**的经典：用「页面差异/响应延迟」当信号，一次只能带 1 bit。
- **NoSQL 注入**用操作符字段使查询失真，参数化查询防不了它——要白名单与类型校验。
- 防御首选**参数化查询**（白名单优于黑名单），辅以输入校验与最小权限。
