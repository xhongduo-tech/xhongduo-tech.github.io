## 为什么从 XSS 与 CSRF 开始

Web 渗透前六篇（第7–12篇）攻击的都是「服务器」——注入、越权、会话，目标都在后端。而 **XSS 与 CSRF** 换了一个完全不同的战场：**攻击目标不再是服务器，而是用户（浏览器）**。

**XSS（Cross-Site Scripting，跨站脚本攻击）**：攻击者把恶意脚本注入到网页中，当其他用户浏览该页面时，脚本在**受害者的浏览器里**以受害者身份执行。

**CSRF（Cross-Site Request Forgery，跨站请求伪造）**：攻击者诱导受害者的浏览器**以受害者的身份**发起攻击者想要的请求。WAHH 第 12 章把这两类统称为**基于浏览器的攻击**——它们的共同点是**受害者浏览器成了攻击者的跳板**，而服务器往往「浑然不知」。

本节拆解 XSS 的三类形态与 CSRF 的利用链，这是从「打服务器」到「打用户」的视角转折。

<span class="marginnote">为什么攻击「用户」也属于渗透测试？因为 Web 应用的<strong>数据与操作都挂在使用者身上</strong>：偷走管理员的会话（XSS 窃 Cookie）等于进后台，让已登录用户执行转账（CSRF）等于打钱。攻「人」的漏洞，最终打到的还是「系统」——这也是为什么 XSS 常年稳居 OWASP Top 10。</span>

## 1 XSS 的原理：把脚本塞进别人的页面

**XSS 的本质**：应用**把用户的输入当成了代码**输出到页面里。当用户提交的内容含 `<script>` 等 HTML/JS 代码，而服务器**未过滤直接回显**时，浏览器会把这段内容当作脚本执行——**输入与代码未分离**，这正是本专题反复出现的母题（SQL 注入篇同源）。

**XSS 的利用目标**：**会话窃取**（读 Cookie）、**钓鱼**（伪造登录框）、**键盘记录**、**页面篡改**、**CSRF 跳板**（借受害者浏览器发请求）。一句话：**能在受害者浏览器里执行任意 JS = 能在受害者会话里做任何事**。

**核心要点｜XSS 的杀伤链条：**
$$
\text{XSS} \rightarrow \text{JS 执行} \rightarrow \text{窃取会话/操作数据} \rightarrow \text{冒充用户}
$$
关键在于「JS 在受害者浏览器里以受害者身份运行」——服务器收到的请求看起来完全合法。

<span class="marginnote">回忆第10篇会话管理的 `HttpOnly`：它正是为对抗 XSS 窃取 Cookie 而生——打了 `HttpOnly` 后 `document.cookie` 读不到会话令牌，XSS 的杀伤力骤降。这就是「防御成体系」的实例：<strong>单个漏洞（XSS）的后果，被另一层防御（HttpOnly）大幅削弱</strong>。</span>

## 2 XSS 的三种形态

按「脚本落在哪、何时执行」，XSS 分三类：

**存储型 XSS（stored / persistent）**：恶意脚本**持久保存**在服务器上（评论、留言、个人资料），任何用户打开该页面都会触发。**危害最大**——攻击一次，中招所有人。

典型场景：论坛评论里写 `<script>alert(document.cookie)</script>`，管理员一打开管理后台就看到这条评论，脚本即执行。

**反射型 XSS（reflected）**：脚本**不落库**，而是随请求「弹回」——攻击者构造含恶意参数的链接，诱导受害者点击；服务器把参数值反射进响应，浏览器执行。典型场景：搜索框回显 `GET /search?q=<script>...</script>`。

需要受害者点击恶意链接，通常配合钓鱼。

**DOM 型 XSS（DOM-based）**：漏洞在**前端 JS 逻辑**里——脚本从 URL 的 `location.hash`/`document.referrer` 取数据写入 DOM，不经过服务器响应。防御最容易被忽略，因为**后端扫描不到**，只能靠前端代码审计发现。

**核心对比表｜三种 XSS：**

| 类型 | 脚本存在处 | 触发方式 | 危害 |
| --- | --- | --- | --- |
| 存储型 | 服务器数据库 | 任意用户打开页面 | 最大 |
| 反射型 | 响应即弹回 | 受害者点恶意链接 | 中 |
| DOM 型 | 前端 JS/DOM | 前端逻辑执行 | 中 |

<span class="marginnote">反射型 XSS 的利用要「两头欺骗」：既要让服务器把恶意参数反射出来，又要骗受害者点这个链接——所以它常与短链接、邮件钓鱼组合。而 DOM 型 XSS 躲过了「服务器过滤」这一标准防线，只能靠前端「不把不可信数据写进 `innerHTML`」来防——这正好呼应第三级《Web 前端开发》里的 DOM 安全实践。</span>

## 3 CSRF：让受害者的浏览器替你发请求

**CSRF（跨站请求伪造）**不注入任何脚本，而是**利用「浏览器会自动携带 Cookie」**这一机制：用户在已登录的站点 A，攻击者构造一个指向 A 的恶意请求（放在自己的站点 B 或邮件里），受害者浏览器访问 B 时**自动带上 A 的会话 Cookie 发起请求**——服务器看到「带合法 Cookie 的请求」，以为是用户本人操作。

**攻击流程**：受害者已登录 A（有会话 Cookie）→ 访问攻击者的 B → B 里有一张 `img`/`form`/`script` 指向 A 的操作接口（如 `POST /transfer`）→ 浏览器带着 A 的 Cookie 执行了转账 → 服务器放行。**受害者全程无感知**。

**CSRF 的成立条件**：目标接口**只靠 Cookie 认证**（不校验来源）+ 请求**可被跨站构造**（GET 用 img/script，POST 用表单）。

**核心对比表｜XSS vs CSRF：**

| 维度 | XSS | CSRF |
| --- | --- | --- |
| 攻击目标 | 在受害者浏览器执行 JS | 让受害者浏览器发请求 |
| 是否需要脚本执行 | 需要 | 不需要 |
| 被攻击对象 | 受害者浏览器+会话 | 服务器接口 |
| 核心防御 | 输入过滤/输出编码 | CSRF Token、SameSite |

**辨析｜易错点：** XSS 与 CSRF 常被搞混。**XSS 是先执行攻击者的 JS，再干坏事**（主动权在攻击者脚本）；**CSRF 是直接借受害者浏览器的合法 Cookie 发请求**（根本不需要 JS）。

两者也常组合：XSS 用来绕过 CSRF 防护（JS 能读到 token）——所以「先 XSS 再 CSRF」是一套经典连招。

<span class="marginnote">CSRF 的防御三板斧：<strong>CSRF Token</strong>（表单里带随机 token，服务器校验来源）、<strong>SameSite Cookie</strong>（浏览器跨站请求不带 Cookie，直接阻断）、<strong>验证来源</strong>（检查 `Origin`/`Referer`）。其中 SameSite=Lax 在现代浏览器里已是默认，CSRF 的现实空间被大幅压缩——但老系统与 API 仍是重灾区。</span>

## 4 XSS 与 CSRF 的测试与防御实践

理解了原理，还要能「测出来」与「防得住」——这两件事各有标准做法。

**测试方法**：反射型与存储型 XSS 用手工 payload 验证（`<script>alert(1)</script>`、`<img src=x onerror=alert(1)>`），配合 Burp 的 `Repeater` 观察响应是否原样回显；CSRF 用「不带 token 重放请求」验证——如果请求被接受，说明缺少 CSRF 防护。自动化扫描器（Burp Scanner、Acunetix）能兜底常规点，但**绕过滤器的变体（编码、标签白名单绕过）必须人工验证**。

**防御方法**：XSS 靠**输出编码**（按上下文转义 HTML/JS/URL）、**CSP（内容安全策略）**限制可执行脚本来源、`HttpOnly` 保护会话 Cookie；CSRF 靠 **CSRF Token**（随表单下发、服务端校验）、**SameSite Cookie**（现代浏览器默认 `Lax` 已挡住多数跨站携带）、校验 `Origin`/`Referer`。

**核心对比表｜漏洞与防御机制：**

| 漏洞 | 防御机制 | 作用层 |
| --- | --- | --- |
| 存储型 XSS | 输出编码 + CSP | 服务端/浏览器 |
| 反射型 XSS | 输入校验 + 输出编码 | 服务端 |
| DOM XSS | 安全 DOM 操作 | 前端 |
| CSRF | Token + SameSite | 服务端/浏览器 |

<span class="marginnote">防御要「配套成体系」：CSP 能拦住「外部脚本执行」但拦不住「内联事件」，所以 CSP + 输出编码要一起上；CSRF Token 防住了跨站请求，但防不住「同站 XSS 发起的请求」——所以 XSS 永远是 CSRF 之上的第一优先级。<strong>一层漏洞，往往需要多层防御；一层防御，往往对抗多类漏洞</strong>。</span>

## 5 小结

- **XSS 与 CSRF** 都是**基于浏览器的攻击**，目标从「打服务器」转向「打用户」。
- **XSS** 把输入当代码回显，在受害者浏览器执行任意 JS——按位置分**存储型、反射型、DOM 型**，存储型危害最大。
- XSS 的杀伤链：**脚本执行 → 窃取会话 → 冒充用户**；`HttpOnly` 是关键的会话防线。
- **CSRF** 利用浏览器自动携带 Cookie，诱导受害者的浏览器发请求——**不需要脚本**。
- 防御：XSS 靠**输入过滤 + 输出编码 + 安全 DOM 操作**；CSRF 靠 **Token + SameSite + 来源校验**。
- XSS 可绕过 CSRF 防护，两者常组合成连招——攻防始终在「组合」里升级。

**动手练习｜想一想：**

用 Burp 拦截一个登录后的请求，把它原样重放给服务器——如果服务器照常接受，说明这个接口很可能缺少 CSRF 防护。
