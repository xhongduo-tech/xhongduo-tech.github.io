## 为什么从 RTC 开始

VOD 可以缓冲三秒再播，视频通话不行——**延迟超过 400 ms 就打断对话节奏**。RTC 面对的问题和 HLS 完全不同：没有播放列表、没有大缓冲，只有「在丢包、抖动、带宽起伏的网络上，把每一帧尽量按时送到」。WebRTC 把浏览器变成实时通信终端，GCC 拥塞控制在毫秒级窗口内调节码率，NACK/FEC/降级构成弱网对抗的完整武器库。它是音视频工程里最难也最迷人的一环。

## 1 WebRTC 架构：浏览器内置的 RTC 栈

**WebRTC**（W3C API + IETF 协议，RFC 8825 起）是浏览器原生支持、点对点优先的实时音视频框架，四大块：

- **`getUserMedia`**：采集麦克风/摄像头；
- **`RTCPeerConnection`**：承载媒体传输——RTP/RTCP、SRTP 加密、DTLS 密钥协商；
- **信令（signaling）**：WebRTC 不规定信令协议，用 SDP 交换媒体参数，通常走 WebSocket；
- **网络穿越**：**ICE** 用 STUN 发现公网地址、TURN 中继穿透 NAT/对称 NAT。

媒体默认是 **Opus + VP8/VP9/AV1**：Opus 的低延迟与丢包韧性、VP9 的高压缩率、AV1 的开放生态，让浏览器之间无需插件即可互连。<span class="marginnote">WebRTC 走 UDP + SRTP：RTP 承载媒体，RTCP 承载反馈（丢包统计、接收端带宽估计）。UDP 没有 TCP 的拥塞控制，所以 RTC 必须**自己实现**拥塞控制——这正是 GCC 的舞台。</span>

## 2 GCC 拥塞控制：在毫秒级找到安全码率

**GCC（Google Congestion Control）** 是 WebRTC 的拥塞控制算法（draft-ietf-rmcat-gcc，接收端反馈进入 RFC 8888），由两条链路合成：

- **基于丢包（loss-based）**：用 RTCP RR 的丢包率判断——丢包超过阈值（如 2%），按乘性因子降码率；低于阈值可缓慢试探升码率。
- **基于延迟（delay-based）**：观察**到达间隔延迟（inter-arrival delay）**的梯度。排队时延上升 = 链路快饱和，即便还没有丢包也要提前降速。

两条链路的输出取**更保守者**作为发送码率上界，编码器据此实时调整（降帧率、降分辨率、调 QP）。<span class="marginnote">GCC 的延迟梯度用卡尔曼滤波（或简化线性趋势）平滑：$\hat{m}(t) = \beta \hat{m}(t-1) + (1-\beta)m(t)$，其中 $m(t)$ 是当前排队时延梯度。趋势为正且持续上升即判定「拥塞前兆」。</span>

## 3 弱网对抗：NACK、FEC 与降级

即使有拥塞控制，丢包仍会发生。RTC 的对抗手段分三层：

- **NACK（重传）**：接收端报告丢失包序号，发送端重传关键包。对音频/关键帧非常有效，但重传引入额外延迟，只能用于「还来得及」的包。
- **FEC（前向纠错）**：发送冗余数据（如 1/3 冗余度），接收端丢包可本地恢复，无需等重传——代价是固定带宽开销，通常与丢包率联动开启。
- **编码层降级**：丢包严重时主动降分辨率/帧率，把码率让给 RTP 头部保护与 FEC；**PLI（图片丢失指示）** 让解码端请求关键帧（I 帧），快速恢复参考链断裂。

工程上的核心权衡是**延迟 vs 恢复**：重传快但占往返时间，FEC 快但常驻带宽。高质量 RTC 栈用**丢包估计器**动态分配两者比例。<span class="marginnote">语音与视频的韧性不同：Opus 的 PLC（丢包隐藏）可以靠前帧预测补一帧，而视频参考链断了只能等下一个关键帧——所以会议系统普遍用「快速 PLI + 分层帧（SVC）」。AV1 在 WebRTC 里通常走 SVC 分层，低层丢失不影响高层恢复。</span>

## 4 公式解析：时延梯度的拥塞前兆

GCC 延迟链的核心信号是**到达间隔时延梯度**。接收端每帧记录到达时间，发送端/接收端算：

$$m(t) = \big(t_a(i) - t_a(i-1)\big) - \big(t_s(i) - t_s(i-1)\big)$$

- **$t_s(i)$、$t_a(i)$**：第 $i$ 帧的发送时间与到达时间。
- **$m(t)$**：到达间隔相对发送间隔的**增量**，即「网络里多攒了多少」。

三步拆解：

- **第一步，读出直觉**：链路空闲时，到达间隔 ≈ 发送间隔，$m(t)\approx 0$；链路饱和时帧在缓冲队列里越排越久，到达间隔被拉长，$m(t)>0$。
- **第二步，理解「梯度」**：$m(t)$ 的**斜率**比绝对值更重要——持续上升说明队列在堆积、即将丢包；这就是「提前于丢包」预警的关键。
- **第三步，连回控制**：GCC 用平滑后的 $\hat{m}(t)$ 对目标码率做加减法：$\hat{m}(t)$ 正且增长 → 乘性降码率（如 ×0.85）；稳定 → 可尝试线性上升。**一句话：队列开始排队的那一刻，就是降速的最早时机。**

## 5 核心对比表：RTC 与分片流媒体

| 维度 | WebRTC | HLS/DASH |
| --- | --- | --- |
| 延迟 | 100–500 ms | 6 s 级（LL 可至 ~1 s） |
| 传输 | UDP + SRTP | HTTP(S) + TCP |
| 缓冲 | 极小（抖动缓冲） | 大缓冲平滑带宽 |
| 拥塞控制 | GCC（自实现） | 靠 TCP + ABR |
| 典型场景 | 会议、直播连麦、云游戏 | VOD、传统直播 |

## 6 小结

- **WebRTC** 用 getUserMedia + RTCPeerConnection + ICE/STUN/TURN 把浏览器变成实时终端。
- **GCC 拥塞控制** = 丢包链 + 延迟链，取更保守者为码率上界。
- **时延梯度** $m(t)$ 是「提前于丢包」的拥塞前兆信号，靠滤波平滑后驱动加减码率。
- 弱网对抗三件套：**NACK、FEC、编码降级 + PLI**，核心权衡是延迟 vs 恢复带宽。
- RTC 与分片流媒体的差异本质是**缓冲换延迟**：RTC 几乎不缓冲，所以一切都要主动反馈。
