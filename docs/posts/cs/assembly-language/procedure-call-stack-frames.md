## 为什么从过程调用开始

从这一节起，我们从「单条指令」跃升到「整个函数」。C 里每次函数调用——无论多深、多嵌套、多递归——都必须回答三个问题：调用结束后**回到哪**？被调函数的数据**放哪**？调用者/被调用者的寄存器怎么**交接**？三个答案都指向同一个数据结构：**栈**。

过程调用是计算机科学里「封装与抽象」在机器层的化身：一个函数执行时仿佛拥有自己的小宇宙，退出后世界复原。理解栈帧，你就理解了递归为什么「深了会爆栈」、为什么局部变量不能返回给调用者、为什么编译器优化时要维护对齐——这些在 C 层只能死记的规矩，在汇编层全部是**因果**。<span class="marginnote">栈是「后进先出」的天然递归结构：函数 A 调 B，B 调 C，C 返回后 B 继续、再返回后 A 继续——每条路径都要求「后调用先返回」，栈恰好满足。这也是为什么栈几乎出现在一切语言运行时里（Python、JVM 的调用栈同理）。</span>

## 1 栈：向下生长的内存

x86-64 的**栈（stack）**是一段向**低地址**生长的内存，栈顶由专用寄存器 `%rsp` 指向。关键规则：

`pushq S`：先把 `%rsp` 减 8，再把 S 写到新栈顶——**先减后写**。
- `popq D`：先读栈顶 8 字节到 D，再把 `%rsp` 加 8——**先读后加**。

于是「栈顶」始终是**最低地址**，栈里越晚压入的数据越靠近 `%rsp`。`pushq`/`popq` 之外还有 `callq`/`retq` 两个成员：`callq Label` 把**返回地址**（`call` 的下一条指令地址）压栈后跳转；`retq` 从栈顶弹出返回地址并跳回。<span class="marginnote">栈向下生长、堆向上生长，两者在进程地址空间里相向而行；`%rsp` 越界撞上堆（或碰到只读区）就是经典的栈溢出。递归层数一深，`%rsp` 无路可退，程序段错误退出——「爆栈」这个词在机器层就是字面意思。</span>

## 2 一个函数的地盘：栈帧

每次函数调用，栈上都铺开一块专属区域叫**栈帧（stack frame）**。典型布局如图：

![函数调用栈帧的布局](/images/assembly-language/procedure-call-stack-frames-1.svg)

从上到下（高地址到低地址）依次是：**调用者的栈帧**（第 7 个及以后的参数也在这里）→ **返回地址**（`callq` 压入）→ **保存的 `%rbp`** → **局部变量区** → **参数构造区**（调用前写入实参）。`%rbp` 是**帧指针**，`%rsp` 是**栈指针**：

局部变量用 `%rbp` 的**负偏移**访问：`-8(%rbp)`、`-16(%rbp)`；
- 传给子过程的参数写进参数构造区，子过程用 `%rbp` 的**正偏移**访问：`16(%rbp)`、`24(%rbp)`；
- `%rsp` 在函数执行中随 push/pop 上下浮动，所以编译器偏爱用固定不动的 `%rbp` 来引用局部变量。

现代编译器在优化级别较高时会**省略帧指针**，直接用 `%rsp` 加固定偏移访问全部局部量——省一个寄存器、少两条维护指令。

## 3 经典的入口与出口

一个用帧指针的标准函数骨架长这样：

```
  pushq %rbp          # 保存调用者的帧指针
  movq  %rsp, %rbp    # 建立自己的帧指针
  subq  $24, %rsp     # 为局部变量留出 24 字节
  ...                 # 函数体
  movq  %rbp, %rsp    # 撤销局部变量区（等效 leave 的第一半）
  popq  %rbp          # 恢复调用者的帧指针
  retq                # 弹出返回地址并跳回
```

前三行是**入口序（prologue）**，后三行是**出口尾（epilogue）**。`leave` 指令一条顶最后两步（`movq %rbp, %rsp` + `popq %rbp`），所以优化代码里常写成 `leave` 加 `ret`。<span class="marginnote">入口序的关键纪律：<strong>谁用谁还</strong>。调用者之前可能正用着 `%rbx`、`%r12`，被调函数若要碰它们，必须压栈保存、退出前弹回——这正是《x86-64 调用约定与 ABI》篇里「被调用方保存寄存器」的由来。</span>

## 4 公式解析：16 字节对齐为何是硬约束

栈上有个看不见的规矩：**x86-64 ABI 要求每次 `call` 执行前 `%rsp` 都是 16 字节对齐的**（即 `%rsp ≡ 0 (mod 16)`）。为什么？

`callq` 会压入 8 字节返回地址，于是被调函数一进门 `%rsp ≡ 8 (mod 16)`；
- 而许多指令（SSE 的 `movaps` 等）要求操作数 16 字节对齐，`%rsp` 不对齐会导致**未定义行为/段错误**；
- 于是被调函数必须把自己的栈帧总大小设计成 **16 的倍数**：`subq $24, %rsp` 是为了让 24+8（返回地址）= 32，保持 `%rsp ≡ 8 (mod 16)` 不变。

拆解：

- **第一步**：记录进门时刻 $R[\text{rsp}]\bmod 16 = 8$；
- **第二步**：局部量总字节数 $L$ 满足 $L \bmod 16 = 0$；
- **第三步**：`subq $L, %rsp` 后 $R[\text{rsp}]\bmod 16 = 8$，再次 `call` 时满足「调用前 16 对齐」。

这条公式解释了为什么编译器总和 16 较劲地填空字节——那不是洁癖，是 ABI 的硬约束。手写汇编若破坏对齐，在特定指令上会以极其诡异的方式崩溃。

## 5 递归：每个调用一个帧

递归无非是「自己调用自己」，而每次调用都会**重新压一块独立栈帧**。阶乘 `fact(n)` 的递归调用链里，每一层都有自己独立的局部变量与返回地址，互不干扰：

```
fact:                      # 参数 n 在 %rdi
  pushq %rbp
  movq  %rsp, %rbp
  cmpq  $1, %rdi           # n <= 1 ?
  jle   .Lbase             # 递归基
  leaq  -1(%rdi), %rax     # n - 1
  movq  %rax, %rdi
  call  fact               # fact(n-1)：压新帧
  imulq %rax, %rdi         # 回来时 %rax = fact(n-1)
  movq  %rdi, %rax         #   × n，存进返回值
  jmp   .Ldone
.Lbase:
  movq  $1, %rax
.Ldone:
  leave
  ret
```

每层 `call fact` 都压入新的返回地址和帧，返回时依次弹回——「后调用先返回」的栈语义保证了递归的正确性。<span class="marginnote">深递归慢、易爆栈，根因正是每层都要分配和释放栈帧。尾调用优化（TCO）就是编译器发现「返回前不再需要本帧」时直接复用当前帧、去掉 `call`，把递归变成循环——这正是我们在《过程调用》的机器层能亲眼看到的优化动机。</span>

## 6 栈帧偏移速查

把「帧指针正负偏移」的语义钉死，一张表足够：

| 内容 | 相对 %rbp 偏移 |
| --- | --- |
| 保存的 %rbp | 0(%rbp) |
| 返回地址 | 8(%rbp) |
| 调用者的帧指针 | 16(%rbp) |
| 第 7 个参数 | 24(%rbp) |
| 第 8 个参数 | 32(%rbp) |
| 局部变量 | -8(%rbp)、-16(%rbp)… |

正偏移往上走（进入调用者帧），负偏移往下（本帧内部）。`%rbp` 上方先隔一个返回地址（8 字节），再隔保存的 `%rbp` 才是调用者的参数——所以栈参数从 16(%rbp) 起，而不是 8(%rbp)。<span class="marginnote">若函数省略帧指针（`-fomit-frame-pointer`，`-O2` 默认），就没有 `%rbp` 这回事，局部量与参数全部改用 `%rsp` 加固定编译期偏移访问——帧内偏移是「编译期常数」，比 `%rbp` 追着跑更省寄存器。</span>读反汇编时，一张表在手，栈布局不再有歧义。

## 7 小结

- **栈**向低地址生长，`%rsp` 指向栈顶；`pushq` 先减后写、`popq` 先读后加。
- **callq** 压入返回地址后跳转，**retq** 弹出返回地址跳回。
- **栈帧** = 返回地址 + 保存的 `%rbp` + 局部变量区 + 参数构造区；`%rbp` 负偏移管局部量、正偏移访问参数。
- 入口序 `push %rbp; mov %rsp,%rbp; sub`，出口尾 `leave; ret`。
- **易错点｜调用前 `%rsp` 必须 16 字节对齐，栈帧总大小取 16 的倍数**。
- 递归靠「每次调用压新帧」实现，层数深了会**爆栈**；尾调用优化把递归变循环。
