## 为什么从 CSRF 开始

XSS 是在可信页面里执行脚本，而 **CSRF（Cross-Site Request Forgery，跨站请求伪造）** 是另一类攻击：**让受害者的浏览器向可信站点发「伪造的请求」**——受害者已经登录（浏览器带着会话 Cookie），攻击者借这个身份执行转账、改密码、发帖等操作。它不需要偷 Cookie、不需要执行脚本，只需要受害者「访问了一个恶意页面」。理解 CSRF 是理解「浏览器身份模型」弱点的关键一课。<span class="marginnote">CSRF 与 XSS 的本质区别：<strong>XSS 利用「站点信任输入」，CSRF 利用「站点信任浏览器」</strong>——CSRF 不注入代码，只是让浏览器「替攻击者发请求」，而站点误以为「带 Cookie 的请求 = 用户本人」。Cookie 的「自动携带」是 CSRF 的物理基础。</span>

## 1 攻击机制：借 Cookie 发请求

CSRF 的完整链条：

1. **受害者登录**目标站点（如银行），浏览器持有会话 Cookie。
2. 受害者**访问了恶意页面**（攻击者控制的网站/邮件里的图片）。
3. 恶意页面里有一个「对目标站点的请求」——例如：

```html
<!-- 攻击者的页面里藏着一个「转账」图片 -->
<img src="https://bank.com/transfer?to=attacker&amount=10000">
```

4. 浏览器请求图片 URL 时，**自动带上 bank.com 的 Cookie**（同源策略允许发请求，只是不允许读响应）。
5. 银行服务器看到「带合法 Cookie 的转账请求」——**以为是用户本人**，执行转账。

**攻击成功的三个前提**：受害者已登录、目标站点用 Cookie 认证、目标请求是「幂等的副作用操作」（转账/改密/发帖）。这三个前提可以做成一张「排查表」——凡是满足其中两条以上的业务请求，都值得先问一句「这里要不要防 CSRF」：

| 前提 | 含义 | 典型反面案例 |
| --- | --- | --- |
| 受害者已登录 | 浏览器持有效会话，请求会被当作本人 | 游客可访问的公开操作（如站内搜索）无需防 CSRF |
| 站点用 Cookie 认证 | 身份凭证由浏览器自动携带 | 用 `Authorization` 头 + Bearer Token 认证的 API 天然免疫 |
| 副作用操作 | 请求改变服务器状态 | 只读的 `GET` 查询本身无害，但「GET 触发转账」就该警惕 |

值得注意的是，现代 API 越来越倾向「不用 Cookie、用显式请求头带凭证」，这恰好从根上拿掉了 CSRF 的物理基础——<span class="marginnote">这也是为什么 SPA + 纯 Token 认证架构在讨论「是否还需要 CSRF 防护」时常有争议：<strong>Token 若放在 `Authorization` 头里就不会被浏览器自动携带，CSRF 自然失效；但如果 Token 存进 Cookie 以便自动续期，CSRF 风险又会回来</strong>——安全设计的每个选择都有代价。</span>

## 2 为什么浏览器会「听话」：Cookie 的自动携带

CSRF 能成立，源于浏览器的两个行为：

**Cookie 自动携带**：浏览器向某域名发请求时，自动带上该域名的 Cookie（无论请求来自哪个页面）。
**同源策略的「不对称」**：浏览器**允许跨域发送请求**（`GET`、`POST`、`HEAD` 的简单请求），只是**禁止读取跨域响应**——「发请求」的门是开的，「读响应」的门是关的。

所以恶意页面能**触发**请求、但读不到响应——CSRF 要的只是「请求被执行」，不需要读响应。**「能发不能读」的不对称，正是 CSRF 的土壤**。<span class="marginnote">同源策略的一个精确认知：<strong>它限制「读取」跨域资源，不限制「发送」跨域请求</strong>——跨域发送请求完全合法。CSRF 就是利用「发送不受限 + 自动带 Cookie」的组合，让「用户的浏览器」替攻击者干活。</span>

## 3 防御：三件套

CSRF 的防御思路是「让伪造的请求无法通过」：

**① CSRF Token（同步令牌）**：服务器在表单/页面里放一个**随机 token**，随会话绑定；请求必须带 token，服务器比对——攻击者无法预知 token。

**② SameSite Cookie**：设置 `SameSite=Strict/Lax`——浏览器只在「同站请求」或「顶级导航」时带 Cookie；跨站 `POST`/AJAX 请求**不带 Cookie**。现代浏览器的默认（Lax）已阻断大部分 CSRF。

**③ 自定义请求头**：要求 AJAX 带自定义头（如 `X-Requested-With`）——跨域简单请求**不允许**自定义头，攻击者难以伪造。

**现代默认**：SameSite=Lax 已成浏览器默认，CSRF 的威胁面大幅缩小——但**高风险操作仍要 CSRF Token**（SameSite 有边界情况，如顶级导航 GET 请求）。<span class="marginnote">防御的层次：<strong>SameSite 是「浏览器层兜底」，CSRF Token 是「应用层根治」</strong>——Token 校验直接拒绝「不带有效 Token 的请求」，无论 Cookie 怎么带。生产建议是两者并用：SameSite 默认、敏感操作加 Token。</span>

把三种手段放在同一张表里，能看清各自的「防线位置」与「失效场景」：

| 手段 | 作用层 | 机制 | 失效场景 |
| --- | --- | --- | --- |
| CSRF Token | 应用层 | 服务器验证随表单携带的随机令牌 | 站点存在 XSS，攻击者能读 Token |
| SameSite Cookie | 浏览器层 | 跨站请求不再自动带 Cookie | 顶级导航 `GET`（如图片跳转）、旧浏览器不支持 |
| 自定义请求头 | 应用层 | 跨域简单请求不能带自定义头 | 站点接受 `CORS` 预检通过的自定义头 |

## 4 公式解析：CSRF Token 的校验

$$
\text{表单里的 token} \in \text{会话存储的 token 集} \Rightarrow \text{请求来自本站点}
$$

三步拆解这条「Token 校验」：

- **第一步，发 token**：服务器渲染表单时，插入一个与用户会话绑定的随机 token（并存入会话）。
- **第二步，带 token**：表单提交/ AJAX 请求带上这个 token。
- **第三步，验 token**：服务器比对「请求里的 token」与「会话里的 token」——一致才接受。攻击者的恶意页面**不知道 token**（跨域读不到），伪造的请求缺 token 或 token 错——被拒。

拿「转账 10000 元」写一个带数值的完整推演，体会 Token 为什么拦得住：

1. 受害者在银行站点会话里存入一个随机会话 id `sid = a1f2…`，服务器在会话中记下 `csrf_token = 8f3k9m…`。
2. 银行渲染转账表单时，把 token 写进隐藏域 `<input type="hidden" name="_token" value="8f3k9m…">`，表单提交时一并 POST 过去。
3. 攻击者的恶意页面向 `/transfer` 发一个 POST，但它**不知道** `8f3k9m…` 这个值——浏览器不会把另一个域名的页面内容暴露给它，同源策略在此起作用。
4. 服务器收到请求，比对「请求里的 `_token`」与「会话里的 token」：一个是空/乱填、一个是真实值，不匹配——请求被 400 拒绝，转账未发生。

关键在于：**Token 的保密性来自「跨域不可读」，而 CSRF 恰恰是一个「只能发、不能读」的攻击**——攻击者造不出一个它读不到的随机值。

## 5 CSRF 与其他攻击的关系

- **与 XSS 的关系**：**XSS 可以绕过 CSRF 防御**——如果攻击者能执行脚本，就能读 token（Token 存在 DOM 里）。所以 CSRF Token 的强度依赖「站点没有 XSS」。
- **与登录 CSRF**：攻击者让受害者在**攻击者控制的账号**登录——之后受害者的操作都记在攻击者账号上（配合钓鱼）。
- **与 CORS**：CORS 配置错误可能把「不能读」的边界打开——CSRF 升级为可读取。

**统一认知**：CSRF 是「浏览器身份模型 + 服务器信任」的漏洞——防御靠「让伪造请求无法通过」+「减少 Cookie 自动携带」+「消除 XSS 让攻击者拿不到 Token」三者闭环。<span class="marginnote">一个完整的安全心智：<strong>Web 应用的安全边界 = 输入编码（防 XSS/SQLi）+ 请求验证（防 CSRF）+ 权限控制（防越权）</strong>——CSRF 只是其中「请求验证」这一环。把每一环都守住，才谈得上「可信的 Web 应用」。</span>

这里顺带辨析三个「缩写很像、机理完全不同」的漏洞，避免在面试与代码评审里张冠李戴：

- **CSRF**：攻击者借**受害者的浏览器身份**，向可信站点发请求——受害者的浏览器是「帮凶」。
- **XSS**：攻击者把脚本注入**可信站点的页面**，脚本在受害者浏览器里执行——可信站点是「受害者」。
- **SSRF**：攻击者诱导**服务器**去请求攻击者指定的内网地址——服务器是「跳板」。

一句话记忆：<span class="marginnote"><strong>CSRF 是「借浏览器骗服务器」，XSS 是「借页面骗浏览器」，SSRF 是「借服务器逛内网」</strong>——三者分别落在「身份层、脚本层、网络层」，防护手段也天然分属请求验证、输出编码、访问控制。</span>CSRF 是三者里唯一「不读响应也能成事」的——这既是它的特征，也是它容易在防御时被低估的原因。

## 6 小结

- **CSRF**：借受害者已登录的浏览器身份，向可信站点发伪造请求——转账、改密、发帖。
- **根因**：Cookie 自动携带 + 同源策略「能发不能读」的不对称。
- **防御三件套**：CSRF Token（应用层根治）+ SameSite Cookie（浏览器层兜底）+ 自定义头。
- **与 XSS 联动**：XSS 能读 Token 绕过 CSRF——「没有 XSS」是 Token 有效的前提。
- **认知**：Web 安全 = 输入编码 + 请求验证 + 权限控制——CSRF 是「请求验证」一环。
