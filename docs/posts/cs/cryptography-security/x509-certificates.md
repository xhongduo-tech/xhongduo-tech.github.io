## 为什么从公钥证书开始

公钥密码解决了「不需要共享密钥」，却引入了新问题：**攻击者可以把自己的公钥冒充成你的**。Eve 生成一对密钥，把公钥塞给 Bob 说「这是 Alice 的公钥」——Bob 用它加密，Eve 就能解密。解决这个问题需要**公钥认证**：把「公钥 ↔ 持有者身份」绑定起来，由可信机构签名担保。这个绑定的载体就是**公钥证书**，其标准格式是 **X.509**。HTTPS 的每一把锁、代码签名、电子邮件加密，全都建立在 X.509 证书上。<span class="marginnote">「公钥绑架」（man-in-the-middle）的要害：<strong>公钥本身无法证明「它是谁的」</strong>——公钥只是一串数字。X.509 证书就是给这串数字加一张「身份证」，由第三方（CA）签字担保「这串数字属于这个人/这台机器」。</span>

## 1 证书是什么：一张签名担保的公钥身份证

**X.509 证书**是「公钥 + 身份信息 + 有效期 + CA 签名」的绑定文件。一个典型证书（如 HTTPS 服务器证书）包含：

- **主体（Subject）**：公钥持有者（域名、组织、国家）。
- **主体公钥**：真正的公钥（如 RSA-2048 或 ECDSA 公钥）。
- **有效期**：生效与过期时间（证书必须定期更换）。
- **签发者（Issuer）**：签发这张证书的 CA。
- **CA 的签名**：用 CA 私钥对以上内容签名——**这是证书可信的核心**。
- **扩展字段**：用途（服务器认证、客户端认证、代码签名）、密钥用法、CRL 地址等。

**证书的信任链**：CA 用自己的私钥签名，任何人都能用 CA 的公钥验证证书「确实是 CA 签发的、内容没被改」。所以信任证书 = 信任 CA。<span class="marginnote">X.509 是 ITU-T 定义的「公钥证书目录标准」，1988 年第一版，1996 年 v3 加入扩展字段。今天的证书几乎都是 X.509 v3。<strong>「X.509」指证书格式，「PKI」指签发/验证/吊销这套完整体系</strong>——证书是 PKI 的「公民」，CA 是「户籍机构」。</span>

## 2 证书的信任链条：从 CA 到服务器

HTTPS 浏览器验证证书的过程，沿一条**证书链（certificate chain）**向上追溯：

1. 服务器送来「服务器证书」+ 可能还有「中间 CA 证书」。
2. 浏览器用「中间 CA 的公钥」验证服务器证书的签名——通过则服务器证书可信。
3. 浏览器再用「根 CA 的公钥」验证中间 CA 证书——通过则中间 CA 可信。
4. 根 CA 证书在浏览器的**信任库**里（预装）——**信任根**。

**信任的锚点**：浏览器预装了一批「根 CA 证书」（约 100 多个机构），它们是信任链的尽头。整条链只要有一个环节签名不匹配，浏览器就报「证书无效」。<span class="marginnote">一个关键认知：<strong>信任是「锚定在根」的</strong>——浏览器不预装你的服务器证书，只预装根 CA。你的证书必须能「通过某条链追溯到预装的根」，否则不被信任。这就是为什么「自签证书」在浏览器里总是红锁——它不指向任何预装根。</span>

## 3 公式解析：证书签名验证

$$
\text{Cert}_{CA} = \text{subject} \| \text{公钥} \| \text{有效期} \| \sigma_{CA}, \qquad \text{Verify}_{pk_{CA}}(\text{Cert}) = \text{接受}
$$

三步拆解这条「证书可信判定」：

- **第一步，CA 签发**：CA 用私钥对证书内容签名 $\sigma_{CA}$（内容是 subject、公钥、有效期等）。
- **第二步，验证者校验**：任何拿到证书的人，用 CA 的公钥验签——$\sigma_{CA}$ 合法 ⟹ 证书内容确为 CA 所签、未被篡改。
- **第三步，信任迁移**：验证者信任 CA ⟹ 信任「CA 所担保的公钥 ↔ 主体绑定」。**证书把「对 CA 的信任」迁移到「对公钥的信任」**——这是 PKI 的全部秘密。

## 4 证书的字段与生命周期

X.509 v3 证书的关键字段与生命周期管理：

**字段**：
- `version`、`serialNumber`（序列号，CA 全局唯一，吊销时用）。
- `signatureAlgorithm`（签名算法，如 SHA256-RSA）。
- `issuer`、`validity`（notBefore/notAfter）、`subject`、`subjectPublicKeyInfo`。
- `extensions`：`keyUsage`（用途限制）、`extendedKeyUsage`（服务器/客户端认证）、`subjectAltName`（SAN，含域名）。

**生命周期**：
- **签发**：CA 验证主体身份后签发。
- **使用**：客户端在有效期内验证链 + 用途。
- **续期**：到期前重新签发（ACME 自动续期）。
- **吊销**：私钥泄露、域名变更时提前作废（CRL/OCSP，后文）。

**证书的「用途限制」很重要**：一张证书被签发为「服务器认证」，就不能用于「代码签名」——扩展字段把证书的适用范围框死，防止一张证书被乱用。<span class="marginnote">一个值得注意的实现细节：<strong>现代证书的域名校验靠 SAN 字段而非 Common Name</strong>——浏览器 2017 年起忽略 CN 只看 SAN。签发证书时 SAN 必须准确包含全部域名，漏一个就可能导致覆盖不全或「域名不匹配」错误。</span>

## 5 从证书到 PKI 的完整图景

证书不是孤立的文件，它活在完整的 **PKI（公钥基础设施）** 里：

| 组件 | 角色 |
| --- | --- |
| CA（证书颁发机构） | 签发、管理证书 |
| RA（注册机构） | 审核证书申请者的身份 |
| 证书库 | 公开发布证书（LDAP、DNS CAA） |
| CRL / OCSP | 吊销信息的发布与查询 |
| 信任库 | 客户端预装的根 CA 集合 |

理解 X.509 证书，等于拿到了进入 PKI 的门票——下一节的证书链、CA 信任模型，以及再下一节的 CRL/OCSP 吊销，都是在这张「证书」的骨架上搭建的。<span class="marginnote">一个贯穿全书的连接：<strong>证书 = 「公钥 + 身份 + 签名」的组合</strong>——它把第八篇的签名（CA 签名）、第六篇的公钥（主体公钥）、以及认证协议（验证链）三块知识焊在了一起。PKI 是公钥密码的「社会工程」层面。</span>

## 6 小结

- **X.509 证书**：主体 + 公钥 + 有效期 + 签发者 + CA 签名——「公钥的身份证」。
- **信任链**：服务器证书 ← 中间 CA ← 根 CA（预装信任库）——信任锚定在根。
- **验证**：用 CA 公钥验签，签名合法 ⟹ 证书可信；信任从 CA 迁移到公钥。
- **生命周期**：签发 → 使用 → 续期 → 吊销；用途扩展字段框定适用范围。
- PKI 组件：CA、RA、证书库、CRL/OCSP、信任库——证书是 PKI 的核心公民。
