## 为什么从反序列化与命令注入开始

软件系统到处是「转换」：把对象序列化成字节流（存储/传输）、把字符串拼进系统命令（调用工具）。这两类「转换」若处理不可信输入，就成了两个高危漏洞：**反序列化漏洞**（字节流被还原成恶意对象 → 代码执行）与**命令注入**（输入拼进 shell 命令 → 任意命令执行）。它们都是「数据当指令」的注入家族成员，但目标分别是「对象模型」与「操作系统」——危害等级常是 RCE（远程代码执行）。<span class="marginnote">一个威胁定位：<strong>反序列化与命令注入的常见后果是 RCE（远程代码执行）</strong>——攻击者直接获得在目标机器上执行命令的能力，是漏洞世界「最严重」的那一档。Java（ObjectInputStream）、PHP（unserialize）、Python（pickle）都曾是反序列化攻击的重灾区。</span>

## 1 反序列化漏洞：字节流变代码

**序列化**：把内存对象转成字节流（存文件/传网络）。**反序列化**：把字节流还原成对象。

**漏洞机制**：很多语言的**反序列化会触发对象的方法**（构造、析构、魔术方法），攻击者精心构造「恶意对象图」，反序列化时链式触发危险方法——**无需任何代码注入，一条字节流就能执行命令**。

**经典案例——Java 的 ysoserial**：攻击者构造一个「HashMap → 触发 hashCode → … → Runtime.exec」的对象链，一条序列化字节流在反序列化时执行系统命令。PHP 的 `unserialize` 同样可通过 `__wakeup`/`__destruct` 魔法方法触发（如 phpggc 的 gadget 链）。

**危害**：**RCE、DoS、任意文件操作**——Java、PHP、Python、Ruby 的反序列化都出过致命 CVE（如 2015 年 Apache Commons Collections 引发的 Java 反序列化大潮）。<span class="marginnote">「Gadget 链」是反序列化攻击的核心：<strong>攻击者不必注入代码，只需把「程序里已有的类和方法」按特定顺序串成一条执行链</strong>——就像 ROP 用已有指令拼功能，反序列化用已有类拼出 `exec`。一次安全的 `readObject` 调用，可能因为「类路径里有某个有副作用的类」而变成 RCE。</span>

## 2 命令注入：字符串变系统命令

**命令注入（command injection）**：用户输入被拼进系统命令字符串。

```php
system("ping " . $_GET['host']);   // 危险！
```

如果 `host` 是 `127.0.0.1; rm -rf /` 或 `$(cat /etc/passwd)`，shell 会执行**分号后的第二条命令**——任意命令执行。

**能做什么**：读取任意文件、反弹 shell、植入后门、横向移动——服务器权限有多大，攻击者就有多大。

**与 SQL 注入的同构**：都是「不可信数据拼进一种语言（shell/SQL）」，只是语言不同。<span class="marginnote">命令注入的关键符号：<strong>`;`（顺序执行）、`&&`/`||`（条件执行）、`` `cmd` ``/`$(cmd)`（命令替换）、`|`（管道）</strong>——它们让攻击者「在合法命令之后追加自己的命令」。防御的根本是「不让输入进入 shell 的语法空间」。</span>

## 3 公式解析：命令注入的追加

$$
\text{ping } \underbrace{127.0.0.1; \text{cat } /etc/passwd}_{\text{用户输入}} \;\; \Rightarrow \;\; \text{先 ping 再执行 cat}
$$

三步拆解这条「命令追加注入」：

- **第一步，闭合上下文**：输入里的 `;` 结束 `ping` 命令的参数。
- **第二步，追加命令**：分号后的 `cat /etc/passwd` 是**第二条命令**——shell 按顺序执行。
- **第三步，读取结果**：若应用把命令输出回显给用户，`/etc/passwd` 的内容直接出现在页面里——信息泄露。

## 4 防御：白名单、参数化与「不拼命令」

命令注入的防御分三层：

- **首选：不拼命令**——用语言的**进程 API 直接传参数**（Python 的 `subprocess.run(["ping", host])`），参数不进 shell 语法——**从根上消灭注入**。
- **次选：白名单校验**——`host` 只允许 IP/域名格式（正则白名单），非法输入直接拒绝。
- **兜底：转义**——转义 shell 特殊字符（容易出错、不推荐作主防线）。

反序列化的防御：

- **不反序列化不可信数据**：只对可信来源做反序列化。
- **白名单类**（Java 的 `ObjectInputFilter`、PHP 的 `allowed_classes`）：反序列化时**禁止加载不信任的类**。
- **用安全的格式**：JSON 等纯数据格式（不触发魔术方法）。
- **签名/加密**：序列化数据加 MAC——防篡改伪造。<span class="marginnote">一句话记忆：<strong>「不拼命令用参数、不反序列化用 JSON、一定要反序列化就白名单类 + 签名」</strong>——三个「不」把两类 RCE 堵在门外。命令注入与反序列化的防御哲学一致：减少「不可信数据触达指令解释器」的路径。</span>

## 5 从两类漏洞看「数据-指令边界」

反序列化与命令注入，连同前面的 SQL 注入、XSS、模板注入，构成一个完整的「注入家族」。它们唯一的共同教训：

**任何「不可信数据进入指令解释器（SQL、shell、模板、序列化器、HTML）」的路径，都是潜在的 RCE/数据泄露点**。

**统一的防御原则**：

- **参数化**（SQL 预编译、进程参数数组）——让数据只当数据。
- **白名单**（输入格式、可加载类）——把「允许的」显式列出。
- **最小权限**（数据库账号、进程权限）——即使注入成功也封顶危害。
- **输出编码**（HTML/JS 上下文）——让注入无法成为可执行代码。<span class="marginnote">把全书串起来的视角：<strong>信息安全的所有经典漏洞，几乎都是「边界混淆」</strong>——数据被当成代码（注入）、信任被错误迁移（MITM）、错误反馈被利用（Padding Oracle）。「清晰地划分数据与指令的边界」是贯穿密码学与软件安全的第一原则。</span>

## 6 小结

- **反序列化漏洞**：字节流还原对象时触发危险方法（gadget 链）——Java/PHP/Python 的 RCE 重灾区。
- **命令注入**：输入拼进 shell 命令——`;`、`$( )` 追加任意命令。
- **注入同构**：SQL/shell/模板/HTML/序列化——都是「数据当指令」。
- **防御**：不拼命令用参数、不反序列化用 JSON、白名单 + 签名 + 最小权限。
- **统一原则**：减少「不可信数据触达指令解释器」——边界清晰是安全第一原则。
