## 为什么从流式模式开始

上一节的 CBC 有一个硬伤：**加密必须串行**——每个分组的加密都依赖前一个密文，无法并行。在高吞吐场景（磁盘加密、网络加密、硬件加速）里，这个瓶颈不可接受。这一节讲三个把分组密码「流式化」的模式：**CFB、OFB、CTR**。它们的共同思路是：先用分组密码生成**密钥流**，再与明文异或——这等于把 AES 变成了「伪随机数生成器」。CTR 模式因此成为现代高速加密的事实标准，也是下一节认证加密 GCM 的底座。<span class="marginnote">一个贯穿性观察：CFB/OFB/CTR 三种模式本质上是「用 AES 造流密码」——它们和第四篇真正的流密码（RC4、ChaCha20）共享同一套思想：<strong>密钥流 + 异或</strong>。区别只在密钥流怎么生成。</span>

## 1 CFB：把密文反馈回密钥流

**密码反馈模式（Cipher Feedback, CFB）**：把前一个**密文分组**加密，作为当前密钥流块，再与明文异或：

$$
C_i = P_i \oplus E_K(C_{i-1}), \qquad C_0 = P_0 \oplus E_K(IV)
$$

CFB 的关键性质：

- 解密不用 $D_K$，**只用到 $E_K$**——加密器与解密器是同一函数，硬件实现简单。
- 错误传播与 CBC 类似：$C_i$ 的一位翻转损坏 $P_i$ 与 $P_{i+1}$ 的对应位。
- 加密仍是**链式串行**：生成密钥流需要前一个密文，无法预先生成。

CFB 的一个重要变体是 **CFB-1**（一次只反馈 1 位），用于极低带宽的逐比特场景——但现代系统几乎都用整分组的 CFB 或直接改用 CTR。<span class="marginnote">CFB 提醒我们一个微妙的对称性：<strong>CBC 与 CFB 都依赖「前一个密文」，所以都串行、都有两分组错误传播</strong>；差别只在异或发生在加密前（CBC）还是加密后（CFB）。这两个模式是一对「表兄弟」。</span>

## 2 OFB：密钥流与密文脱钩

**输出反馈模式（Output Feedback, OFB）**：把前一个**密钥流块**（而不是密文）加密，作为当前密钥流块：

$$
S_i = E_K(S_{i-1}), \qquad C_i = P_i \oplus S_i, \qquad S_0 = IV
$$

OFB 与 CFB 的关键区别：**密钥流只依赖 IV 与密钥，完全不依赖密文**。这带来两个重要性质：

- **可以预先生成密钥流**：离线把 $S_0, S_1, \ldots$ 全部算好，加密时只需异或——适合实时性要求高、但明文后到先到不确定的场景（如卫星链路）。
- **错误传播为零**：密文一位翻转只影响对应明文一位，不扩散——但这**不**意味着安全：攻击者翻转一个密文位，等价于翻转一个明文位，可被用于可预测地篡改。

OFB 的隐患是**周期**：$S$ 的序列本质上是一个 $2^{128}$ 状态空间的随机游走，若 IV 选择不当可能进入短周期。现代实践中 OFB 的地位被 CTR 取代，但它的思想（密钥流与密文解耦）在认证加密里仍有回响。<span class="marginnote">OFB 的「密钥流可预生成」在历史上很诱人，但它的<strong>无错误传播</strong>同时也是弱点：攻击者能精确地翻转明文的任意位而不被察觉。现代 AEAD 模式（GCM）用「加密+认证」组合，同时解决了可预生成与防篡改两个需求。</span>

## 3 CTR：用计数器做密钥流，现代默认

**计数器模式（Counter, CTR）**：用一个**不断递增的计数器**作为分组密码输入，生成密钥流：

$$
C_i = P_i \oplus E_K(\text{Nonce} \mathbin{\|} i), \qquad i = 0, 1, 2, \ldots
$$

其中 Nonce 是一个**唯一的、随机的**初始值，$i$ 是分组序号（通常用 64 位 nonce + 64 位计数器）。

CTR 的优势是压倒性的：

- **可并行**：每个分组的密钥流只依赖 (Nonce, $i$)，互不依赖——加密解密都可以多核并行、GPU 加速。
- **可随机访问**：想解密第 5 个分组，直接算 $E_K(\text{Nonce}\|5)$ 即可，不需要解密前 4 个——磁盘加密、数据库加密的关键能力。
- **预生成密钥流**：与 OFB 一样，可以离线算好。
- **无错误传播**：单比特翻转只影响对应位。

CTR 的安全性前提：**Nonce 绝不能重复**。Nonce 重复 → 两段密钥流相同 → $C_1 \oplus C_2 = P_1 \oplus P_2$，明文差异直接泄露（与一次一密重用密钥是同一个灾难）。<span class="marginnote">Nonce 管理的教训是 CTR 唯一的坑：<strong>随机生成要防碰撞，计数器生成要防复位</strong>。TLS 1.3 用「每连接独立随机 IV」、磁盘加密用「每扇区计数器」，本质都是「保证 nonce 唯一」的工程化方案。</span>

## 4 公式解析：CTR 如何做到可并行与可随机访问

$$
C_i = P_i \oplus E_K(\text{Nonce} \| i)
$$

三步拆解这个「现代默认模式」：

- **第一步，看密钥流来源**：$E_K$ 的输入是 $\text{Nonce}\|i$——一个不重复的初始值拼上分组序号。密钥流 $S_i = E_K(\text{Nonce}\|i)$ 与明文、与之前的分组都无关。
- **第二步，看加密**：$C_i = P_i \oplus S_i$。加密 = 生成密钥流 + 异或，仅此而已——不需要 $D_K$。
- **第三步，看性质来源**：因为 $S_i$ 独立于其他分组，任意分组的密钥流可**独立计算**——这就是可并行、可随机访问、可预生成的数学根源。

## 5 数值算例：4 位玩具密码走一遍 CTR

用一个「玩具分组密码」$E_K(x) = (x + 3) \bmod 16$（4 位块，当作 AES 的替身）把 CTR 的机制落到数字上。取 Nonce $= 0$，明文三个分组 $P_0 = 1101$、$P_1 = 0010$、$P_2 = 0111$。

**生成密钥流**：

- $S_0 = E_K(0) = 3$，$C_0 = 1101 \oplus 0011 = 1110$。
- $S_1 = E_K(1) = 4$，$C_1 = 0010 \oplus 0100 = 0110$。
- $S_2 = E_K(2) = 5$，$C_2 = 0111 \oplus 0101 = 0010$。

**随机访问解密 $C_1$**：只需算 $S_1 = E_K(1) = 4$，$P_1 = 0110 \oplus 0100 = 0010$——**完全不需要 $C_0$ 或 $S_0$**。这就是磁盘加密「想解哪块解哪块」的机制来源。

**Nonce 重用的灾难**：若用同一 Nonce 加密第二条消息 $P'$，则 $C_1' = P_1' \oplus S_1$，攻击者算 $C_1 \oplus C_1' = P_1 \oplus P_1'$——密钥流被消掉，与一次一密重用密钥是同一个灾难（对照《一次一密》一节的算例）。<span class="marginnote">这个 4 位例子把 CTR 的「三可」与「一前提」全部演示了：<strong>可并行（$S_i$ 互不依赖）、可随机访问（只算 $S_1$）、可预生成（$S_i$ 与明文无关）、Nonce 唯一（重复即崩）</strong>。真实 AES-CTR 只是把 $(x+3)\bmod 16$ 换成 128 位上的真加密函数——结构完全相同。</span>

## 6 三个流式模式的对比

| 模式 | 密钥流来源 | 加密能否并行 | 错误传播 | 主要用途 |
| --- | --- | --- | --- | --- |
| CFB | 前一个密文 | 否 | 两分组 | 历史遗留，逐比特变体 |
| OFB | 前一个密钥流块 | 否 | 零 | 卫星链路等预生成场景 |
| CTR | Nonce + 计数器 | **是** | 零 | 现代高速加密、磁盘、GCM |

CTR 在「可并行」「可随机访问」「预生成」三维全胜，代价只有一个（Nonce 唯一性），因此成为现代密码引擎的默认选择。它也是下一节 **GCM** 的核心——GCM = CTR 加密 + GHASH 认证，把「加密」与「认证」合并成一个高效模式。<span class="marginnote">记忆锚点：<strong>CFB/OFB 靠「反馈」生成密钥流，CTR 靠「计数器」生成</strong>。反馈系（CBC/CFB/OFB）是串行的旧世界，计数器系（CTR/GCM）是并行的新世界——分界线就是「密钥流是否依赖密文」。</span>

## 7 选型与现实：流式模式在协议里的足迹

这些模式不是纸面理论，它们刻在真实协议里：

- **SSH**：历史版本用 CBC（OpenSSH 长期默认），现代 SSH 用 **AES-CTR** 或 **ChaCha20-Poly1305**——因为 CTR 可并行、抗错误扩散。
- **TLS 1.2**：常用 **AES-GCM**（= CTR + 认证）；1.3 更进一步，只保留 AEAD（GCM/ChaCha20-Poly1305）。
- **磁盘加密**：BitLocker、LUKS 用 **XTS**（CTR 的变体，带两把密钥）——因为磁盘需要随机访问且密文不能扩散。
- **5G/无线**：SNOW3G、ZUC 是专用流密码，本质也是「密钥流 + 异或」。

**选型心法**：需要并行/随机访问/预生成 → CTR 系；需要逐比特（极低带宽）→ CFB-1；需要离线预生成且不在乎可并行 → OFB。但 2026 年的现实是：**新系统几乎一律选 AEAD（GCM/ChaCha20-Poly1305）**，裸 CTR 只用于「加密但无需认证」的角落。<span class="marginnote">一个连接第四篇《流密码》的观察：<strong>ChaCha20 是「原生流密码」，AES-CTR 是「分组密码造出的流密码」</strong>——两者在协议里互为替代。2020 年代后，移动端与软件场景越来越多地选 ChaCha20（无 AES 硬件加速时更快），服务器端仍以 AES-GCM 为主。模式选型背后是「硬件加速 vs 纯软件性能」的权衡。</span>

## 8 小结

- **CFB**：$C_i = P_i \oplus E_K(C_{i-1})$，解密只用 $E_K$；串行、两分组错误传播。
- **OFB**：$S_i = E_K(S_{i-1})$，密钥流与密文解耦，可预生成；无错误传播（也是弱点）。
- **CTR**：$C_i = P_i \oplus E_K(\text{Nonce}\|i)$，可并行、可随机访问、可预生成；**Nonce 绝不重复**是唯一前提。
- **算例**：玩具密码 $(x+3)\bmod16$ + Nonce=0 得密钥流 $3,4,5$；随机访问只算 $S_1$。
- 三者本质都是「用分组密码造流密码」：密钥流 + 异或。
- 现实：SSH/TLS/磁盘加密的足迹——现代一律 AEAD（GCM/ChaCha20-Poly1305）。

在下一节，我们把加密与认证合二为一——**认证加密模式 GCM 与 CCM**，看它们如何用 CTR 的并行性同时解决机密性与完整性。
