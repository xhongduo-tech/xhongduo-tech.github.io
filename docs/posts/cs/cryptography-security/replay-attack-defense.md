## 为什么从重放攻击开始

上一节的挑战-响应用「新鲜挑战」防重放，这一节把防重放**系统化**。**重放攻击（replay attack）**是最朴素也最有效的攻击之一：攻击者截获一段合法消息（登录请求、交易、命令），不破解任何密码，只是**原样重发**——系统无法区分「第一次」与「重发」。防护的三种标准手段——**随机数（nonce）、时间戳（timestamp）、序列号（sequence number）**——是现代协议（TLS、Kerberos、IPsec）防重放的基石。理解三者的取舍，是理解协议新鲜性设计的核心。<span class="marginnote">重放攻击的可怕在于它的「零成本」：<strong>不需要破解加密、不需要伪造签名——只是复制粘贴</strong>。历史上银行转账重放、传感器命令重放、甚至登录会话重放都造成过真实损失。防重放因此是认证协议的头号需求。</span>

## 1 重放攻击的形态

重放攻击有三种典型形态：

- **简单重放**：把整条截获的合法消息原样重发——系统再次执行（转账两遍、登录两次）。
- **跨会话重放**：把上次会话的消息用到这次会话（凭据跨会话复用）。
- **反射攻击**：攻击者把消息「反射」回发送者或转发到另一方（Needham-Schroeder 等协议曾被这类攻击困扰）。

**攻击成功的前提**：接收方**无法判断消息的新鲜性**。所以防重放的全部思路，就是给消息绑定「新鲜性证据」。

## 2 三种新鲜性证据：nonce、时间戳、序列号

**随机数（nonce）**：接收方先发一个随机挑战，发送方把它编进响应——响应只在「挑战对应」时有效。优点：无需同步时钟；缺点：需要一次额外的交互往返。

**时间戳（timestamp）**：消息里带发送方时钟的时间，接收方拒绝「太旧」的消息。优点：无额外交互；缺点：**需要时钟同步**，且「多久算太旧」有窗口——窗口内仍可重放，窗口外又可能误杀正常消息。

**序列号（sequence number）**：消息带一个递增计数，接收方只接受「比上次大的号」。优点：精确、无时钟；缺点：**需要维护会话状态**（双方都要记「当前号」）。

| 机制 | 额外交互 | 时钟依赖 | 状态维护 | 适用 |
| --- | --- | --- | --- | --- |
| nonce | 有 | 无 | 无 | 认证握手、挑战-响应 |
| 时间戳 | 无 | 有 | 无 | 票据、状态无关协议 |
| 序列号 | 无 | 无 | 有 | 长连接、IPsec、TLS 记录层 |

**现代协议往往组合使用**：握手用 nonce（如 TLS 的 random），会话内用序列号（如 TLS 记录层的 seq），凭证用时间戳（如 Kerberos 票据）。<span class="marginnote">一个经典组合：<strong>TLS 握手用随机数（握手新鲜性）+ 记录层用隐式序列号（消息新鲜性）</strong>——不同层解决不同粒度的重放。理解「在哪个层级防什么重放」，是协议设计的精细之处。</span>

## 3 时间戳的窗口困境

时间戳看似简单，实则处处是坑：

- **窗口太大**：重放窗口大（比如 5 分钟），攻击者在窗口内重放仍有效。
- **窗口太小**：网络延迟稍高，合法消息被误拒。
- **时钟不同步**：接收方时钟快/慢，产生误判。
- **重放窗口内的「去重」**：同一时间戳的消息多次到达——接收方还要记录「最近见过的消息」去重，否则窗口内重放仍成功。

**实践**：时间戳通常配合「滑动窗口 + 最近消息缓存」使用——既允许一定延迟，又拒绝重复。Kerberos 的票据时间戳 + 防重放缓存就是这种设计的代表。<span class="marginnote">一个易被忽略的点：<strong>时间戳防重放的前提是「记录已见过的消息」</strong>——只检查时间不够，还要检查「这个时间戳/标识是否见过」。否则攻击者在时间窗口内重放同样有效。去重缓存的大小与持久化，是时间戳方案的隐藏复杂度。</span>

## 4 公式解析：序列号的防重放判定

$$
\text{接受 } M_i \iff i > \text{last\_accepted}, \quad \text{然后 } \text{last\_accepted} \leftarrow i
$$

三步拆解这条「序列号判定」：

- **第一步，单调性**：序列号 $i$ 必须严格大于上次接受的号——任何重复、乱序的旧消息被拒。
- **第二步，状态更新**：接受后更新 `last_accepted`——状态在两端维护。
- **第三步，边界**：序列号空间耗尽（2^64 次后）需要「重协商」；乱序到达（UDP）需要滑动窗口——序列号方案在可靠传输（TCP/TLS）里最自然，在乱序信道里要加复杂度。

## 5 防重放的工程清单

设计一个防重放的认证/通信系统，检查清单：

- **握手层**：用 nonce 绑定每次会话——TLS 的 client_random/server_random。
- **消息层**：用序列号或时间戳绑定每条消息——TLS 记录层、IPsec 的 ESP 序列号。
- **凭证层**：票据/令牌带时间戳与生命周期——Kerberos、JWT 的 `exp`。
- **去重**：任何时间戳/序号方案都要「记录已见」，防窗口内重放。
- **统一**：防重放必须与完整性绑定——防重放字段要参与 MAC/签名，否则攻击者能改字段。

**核心铁律**：**新鲜性字段必须被认证**（纳入 MAC/签名）——否则攻击者改掉时间戳就能绕过检查。<span class="marginnote">一个常见漏洞：<strong>系统检查时间戳，但时间戳不在 MAC 里</strong>——攻击者把「过期消息」的时间戳改回「当前时间」再重放，MAC 仍然通过（因为 MAC 只保护了别的字段）。防重放字段必须与消息一起被认证，这是排第一位的设计约束。</span>

## 6 小结

- **重放攻击**：原样重发合法消息，零成本、防不胜防。
- **三种新鲜性证据**：nonce（交互换新鲜）、时间戳（时钟换新鲜）、序列号（状态换新鲜）。
- **取舍**：nonce 无状态有往返、时间戳有窗口无状态、序列号精确要状态。
- **时间戳陷阱**：窗口权衡、时钟同步、窗口内去重缓存。
- **铁律**：新鲜性字段必须参与 MAC/签名——否则攻击者能「改字段绕过」。
