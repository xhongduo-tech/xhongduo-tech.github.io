## 为什么从沙箱开始

上一节的最小特权需要「载体」——**沙箱（sandbox）** 就是那个载体：把不可信代码限制在一个隔离环境里，即使它恶意，也「看不见、摸不到、够不着」外面的世界。从古老的 **chroot** 到现代容器（**命名空间 + cgroups**）再到系统调用过滤（**seccomp**），沙箱机制是「隔离」思想的层层深化。浏览器渲染网页、运行未知二进制、隔离容器——都靠沙箱。<span class="marginnote">一个定义：<strong>沙箱 = 限制「能看到的资源 + 能执行的操作」的隔离环境</strong>——chroot 管「文件视野」，命名空间管「系统视图」，seccomp 管「系统调用面」。三者叠加 = 现代容器的隔离栈。</span>

## 1 chroot：改变「根」的假监狱

**chroot** 改变进程看到的「根目录」——把根 `/` 换成一个子目录：

```bash
chroot /srv/jail /bin/sh    # 进程的 / 变成 /srv/jail
```

- 进程只能看到 `/srv/jail` 之下的文件——`/etc/passwd`、`/bin` 都变成「假根」里的版本。
- 常用于 DNS（BIND）、FTP、Web 服务隔离——「就算被攻破，看到的文件系统是假的」。

**chroot 的局限（它不是真正的沙箱）**：

- **root 可逃逸**：有 root 权限的进程可以通过 `chroot` 逃逸（需要 `CAP_SYS_CHROOT` 与特定技巧）。
- **只限制文件系统**：不限制网络、进程、系统调用——进程仍能访问网络、杀别的进程。
- 它是「视野隔离」而非「权限隔离」。

**结论**：chroot 是沙箱的「祖辈」，现代系统用**命名空间**替代它。<span class="marginnote">chroot 逃逸的现实警示：<strong>「改了根 ≠ 关了门」</strong>——chroot 只是让进程「看不见」外面的路径，但文件描述符、挂载点、root 能力都可能成为逃逸通道。所以现代隔离不再单独依赖 chroot，而是用命名空间 + seccomp 组合。</span>

## 2 命名空间：让进程看到「假系统」

**Linux 命名空间（namespaces）** 让一组进程看到「独立的系统视图」——它们以为自己在「自己的机器」上。关键命名空间：

- **Mount（mnt）**：独立的文件系统挂载视图。
- **PID**：进程看到的进程号从 1 开始（看不到宿主的其他进程）。
- **Network（net）**：独立的网络栈（自己的 IP、端口、路由）。
- **User**：独立的用户 ID 空间——容器里的 root 映射为宿主非特权用户。
- **UTS、IPC、cgroup**：主机名、进程间通信、资源控制的隔离。

**容器 = 命名空间 + cgroups + 镜像**：Docker/containerd 用命名空间隔离视图、cgroups 限制资源、镜像提供根文件系统——「看似独立的小系统」。

**关键安全点**：容器共享**宿主的操作系统内核**——命名空间是「视图隔离」，不是「内核隔离」。这既是容器高效的原因，也是容器逃逸（突破命名空间）风险的根源。<span class="marginnote">容器 vs 虚拟机的本质区别：<strong>虚拟机有独立内核（硬隔离），容器共享宿主内核（视图隔离）</strong>——容器快、轻，但「一个内核漏洞 = 所有容器可能受影响」。所以容器安全的关键是「命名空间 + seccomp + 非 root 运行」叠满，而不是「容器天生安全」。</span>

## 3 seccomp：过滤系统调用

**seccomp（secure computing mode）** 是 Linux 的**系统调用过滤器**——限制进程能调用的系统调用及参数：

- 允许白名单：进程只能用指定的系统调用（如 `read`、`write`、`mmap`），其余（如 `execve`、`ptrace`、`mount`）直接拒绝。
- 参数过滤：用 BPF 规则检查系统调用的参数。

**seccomp 的价值**：攻击者即使拿到代码执行（RCE），也被限制在「白名单系统调用」里——不能 `execve` 启动 shell、不能 `ptrace` 调试、不能 `mount`。**它把「代码执行」降级为「只能做有限的事」**。

Chrome 的渲染进程、Docker 的默认 profile（只允许约 300 个系统调用里的子集）、gVisor 的拦截层都依赖 seccomp。<span class="marginnote">seccomp 与最小特权的呼应：<strong>seccomp 是「系统调用层的最小特权」</strong>——进程不需要的 syscall 一律不给。一个 PDF 渲染器只需要文件读写与内存映射，不需要 `execve`——seccomp 就把这扇门关死，让「渲染恶意 PDF」无法变成「执行 shell」。</span>

## 4 公式解析：三层沙箱的叠加

$$
\text{隔离深度} = \underbrace{\text{chroot/命名空间}}_{\text{看不见}} + \underbrace{\text{seccomp}}_{\text{做不到}} + \underbrace{\text{capabilities 丢弃}}_{\text{没资格}}
$$

三步拆解这条「现代沙箱公式」：

- **第一步，看不见（视图隔离）**：命名空间/chroot 让进程看不到宿主文件、进程、网络。
- **第二步，做不到（操作隔离）**：seccomp 让进程不能调危险系统调用——即使「看到」也「做不了」。
- **第三步，没资格（权限隔离）**：capabilities 丢弃让进程没有特权能力——即使「能做」也「没资格」。三层叠加，任何单层被绕过还有后两层兜底。

## 5 沙箱的现实应用与逃逸

**沙箱的应用**：

- **浏览器**：Chrome 的每个渲染进程一个沙箱（隔离网页 JS 与插件）。
- **容器**：Docker/K8s 的运行时隔离（命名空间 + seccomp + cgroups）。
- **移动应用**：iOS/Android 每个 App 一个沙箱（UID 隔离 + 权限）。
- **云函数/无服务器**：每函数一个隔离环境。

**沙箱逃逸（sandbox escape）**：突破隔离拿到宿主权限——是沙箱安全的核心对抗。逃逸路径常来自：

- **内核漏洞**（命名空间/系统调用的 bug）。
- **共享内核资源的越权**（IPC、网络、挂载）。
- **配置错误**（特权容器、漏挂 hostPath、seccomp 放太宽）。

**结论**：沙箱是「概率性」防御——它大幅提高攻击成本，但「共享内核」意味着不可能绝对隔离。纵深（多层沙箱 + 最小特权 + 更新内核）才是现实策略。<span class="marginnote">一个行业趋势——<strong>「更强隔离」正在成为云安全的方向</strong>：gVisor（用户态内核拦截系统调用）、Kata Containers（轻量虚拟机）、Firecracker（微虚拟机）——它们用「用户态内核」或「微型 VM」替代「纯命名空间」，牺牲一点性能换更强的隔离。沙箱的历史，就是「隔离越来越硬」的历史。</span>

## 6 小结

- **chroot**：改根目录的「视野隔离」——祖辈沙箱，root 可逃逸。
- **命名空间**：独立系统视图（mount/PID/net/user）——容器隔离的基础。
- **seccomp**：系统调用白名单过滤——把「代码执行」降级为「做不了事」。
- **三层叠加**：看不见（视图）+ 做不到（syscall）+ 没资格（capabilities）——纵深。
- **现实**：浏览器/容器/移动沙箱；逃逸靠内核漏洞与配置错误——隔离越硬越安全（gVisor/Kata）。
