## 为什么从填充预言攻击开始

上一节反复强调「验签失败就拒绝」是铁律，这一节讲一个把这条铁律反过来利用的著名攻击——**填充预言攻击（Padding Oracle Attack）**。它由塞尔日 · 沃德勒在 2002 年提出，是「侧信道」的教科书案例：攻击者不需要破解 AES，只需要一个能回答「**这段密文的填充合法吗？**」的预言（比如服务器解密失败时返回的错误码差异），就能逐步还原明文、甚至**伪造合法密文**。理解它，是理解「错误处理也是攻击面」这一信息安全核心原则的第一课。<span class="marginnote">Padding Oracle 的著名实战是 2014 年的 <strong>POODLE</strong> 攻击（攻破 SSL 3.0）与一系列 ASP.NET / Java 加密漏洞。它们共同教训：<strong>填充校验、错误消息、计时差异——一切可观测的行为都可能成为预言</strong>。</span>

## 1 填充方案：解密前必须回答「合法吗」

分组密码要求明文是分组长度的整数倍，所以加密前要填充。PKCS#7 的规则是：缺 $k$ 个字节就补 $k$ 个值为 $k$ 的字节（$1 \le k \le 16$）。解密时，程序必须**验证填充是否合法**：

看最后一个字节 $v$（$1 \le v \le 16$），检查最后 $v$ 个字节是否全是 $v$。
合法 → 去掉填充，返回明文。
非法 → 报错「填充错误」或直接拒绝。

「填充是否合法」这个**二元判断**本身看似无害，但它泄露了关于明文最后分组的信息——这正是攻击者要的预言。关键前提是：**同一个密钥、同一套填充校验，攻击者可以反复提交自己构造的密文并观察结果**。<span class="marginnote">这个预言的强度在于它<strong>独立于密钥</strong>：填充校验发生在解密后的明文上，攻击者不需要知道密钥，只需要一个能给出「是/否」的黑盒。任何把「填充错误」与「其他错误」区分开来的错误信息、状态码、甚至响应时间的差异，都构成了预言。</span>

用一个具体的填充例子看明白规则。假设分组 8 字节，明文只有 5 字节：

| 明文长度 | 缺字节数 | 填充内容 | 解密后末字节 |
| --- | --- | --- | --- |
| 8 | 0 | 补满 8 个 `0x08` | 8 |
| 5 | 3 | `0x03 0x03 0x03` | 3 |
| 1 | 7 | 7 个 `0x07` | 7 |
| 7 | 1 | `0x01` | 1 |

注意最后一行：即使明文恰好是 7 字节，也**必须补 1 个 `0x01`**——因为解密端无法区分「8 字节明文」与「7 字节明文 + 无填充」。所以 PKCS#7 规定：**填充永不省略，最短填 1 字节**。这是容易漏掉的细节，却正是某些实现出错的根源。

填充校验的存在本身没有错，问题出在「校验失败时的反馈」上。真实系统里这种反馈随处可见：Web 框架的「Bad Padding」异常、数据库驱动的「decryption failed」状态码、甚至只是**响应时长的微小差异**（合法填充走完了解密流程，非法填充提前返回）。Lucky13 攻击正是利用后者——通过测量 TLS 记录处理的时间差来还原明文。

## 2 攻破 CBC：逐步解密最后一个分组

攻击对象是 **CBC 模式**（未认证的经典场景）。回忆 CBC 解密：$P_i = D_K(C_i) \oplus C_{i-1}$。攻击者拿到一串密文，想恢复明文 $P_n$（最后一个分组）。

核心观察：**$D_K(C_n)$ 是固定的未知量，而 $C_{n-1}$ 是攻击者可控的**。篡改 $C_{n-1}$ 的最后一个字节 $C_{n-1}[15]$，就会**精确地**改变 $P_n[15]$（异或一个可预测的值），而不影响其他字节——CBC 的一位翻转只影响对应位。

攻击流程（对最后一个字节）：

尝试 256 个可能的字节值 $g$，构造 $C'_{n-1}[15] = C_{n-1}[15] \oplus g \oplus \text{0x01}$，提交完整密文给预言。
当 $g$ 恰好等于 $P_n[15]$ 时，$P'_n[15] = \text{0x01}$——填充合法（最后 1 字节是 0x01），预言回答「合法」。
**在 256 次尝试中，合法的那一次就确定了 $P_n[15] = g$**。<span class="marginnote">细节：如果最后两字节恰好天然是 0x02 0x02 也可能返回「合法」——这叫<strong>偶然命中</strong>。处理办法是只把「最后 1 字节填充合法」当成命中信号，或重复两次排除偶然。这类实现细节正是真实攻击脚本最容易翻车的地方。</span>

为什么攻击者能「反复试探」而不会被察觉？因为这是**正常的解密流程**：服务器每天要处理海量密文，出现非法填充的请求并不罕见。攻击者只需把成千上万条构造好的密文伪装成普通请求发送，服务器照常响应——**攻击在协议层面完全「合规」**，这也是它难以被网络层检测的原因。

## 3 从最后一个字节到整块明文

## 3 从最后一个字节到整块明文

拿到最后一个字节后，往前推进：现在想恢复 $P_n[14]$。把填充改成 2 字节（0x02 0x02），固定已经恢复的 $P_n[15]$，让 $P'_n[15] = \text{0x02}$（把 $C'_{n-1}[15]$ 设为 $C_{n-1}[15] \oplus P_n[15] \oplus \text{0x02}$），再对 $P_n[14]$ 尝试 256 个值，找「填充合法」的那一个。

如此逐字节推进：恢复 $P_n[15], P_n[14], \ldots, P_n[0]$，恰好 16 个字节。每个字节最多 256 次尝试，**整个分组最多 $256 \times 16 = 4096$ 次预言查询**。然后对 $C_n$ 的上一分组 $C_{n-1}$ 重复同样流程（它作为密文分组继续被解密），直到整个消息还原。

攻击的代价是**预言查询次数**，与密钥长度无关：AES-256 在这个攻击面前与 AES-128 一样脆弱。真正的防线是**认证加密**——填充错误根本不会被反馈，因为先验标签、验签失败就直接丢弃。<span class="marginnote">一句话量化：<strong>Padding Oracle 把「不可破解的 AES」变成「平均每个分组 2048 次查询就能解出的密文」</strong>。这不是破解 AES，而是绕过 AES——攻击打在「模式 + 错误处理」这一层，而非算法本身。</span>

**辨析｜易错点：** 有人误以为「预言的判定越细，攻击越强」。其实恰恰相反——**攻击者只需要一个粗糙的「合法/非法」判定**。更细的错误分类（比如「填充错误 #1」「填充错误 #2」）反而给攻击者更多信息；更统一的错误响应（一律「认证失败」）才是防御方向。信息越少，攻击越难。

## 4 公式解析：预言查询如何逼近一个明文字节

$$
\text{如果 } P'_n[15] = \text{0x01} \quad \text{则} \quad g = P_n[15]
$$

三步拆解这个「命中判定」：

- **第一步，构造篡改**：令 $C'_{n-1}[15] = C_{n-1}[15] \oplus g \oplus \text{0x01}$。因为 $P'_n[15] = D_K(C_n)[15] \oplus C'_{n-1}[15]$，代入得 $P'_n[15] = P_n[15] \oplus g \oplus \text{0x01}$。
- **第二步，命中条件**：当 $g = P_n[15]$ 时，$P'_n[15] = \text{0x01}$——最后 1 个字节填充合法，预言返回「合法」。当 $g \neq P_n[15]$ 时，$P'_n[15] \neq \text{0x01}$，若也不是其他合法填充，则返回「非法」。
- **第三步，读出结果**：攻击者遍历 256 个 $g$，预言唯一回答「合法」的那个 $g$ 就是 $P_n[15]$。明文的一个字节到手。

再补一层直觉：整个攻击本质是**「用 256 次试探换 1 字节明文」的拍卖**。每试探一次，攻击者就把「$P_n[15]$ 是不是这个值」的概率全部押上——而预言像一台测谎仪，只在猜对时亮绿灯。256 次试探的期望成本对应「一字节 = 8 比特信息」的下界，这就是为什么它能无条件还原出全部明文。

## 5 防御：为什么认证加密一劳永逸

Padding Oracle 的全部威力来自「攻击者能**反复试探**且**得到区分性反馈**」。认证加密（GCM/CCM）正好同时断掉这两条：

- **先验标签**：接收方先重算 MAC 并比对，不通过就拒绝——根本不会执行填充校验，错误反馈为零。
- **一次认证**：篡改任意一个密文位都会导致标签不匹配，攻击者无法「逐字节试探」——任何试探都只会得到统一的「认证失败」。

其他防御手段包括：**统一错误信息**（填充错误与 MAC 错误返回同一个错误）、**恒定时间比较**、**先 MAC 后解密**。但最干净的做法只有一个：**用 AEAD，别自己拼加密与填充**。<span class="marginnote">这条经验可以推广成信息安全的一般原则：<strong>错误信息与行为差异也是信息</strong>。一个「悄悄失败」的系统通常比一个「响亮失败」的系统更安全——因为攻击者无法从失败模式里读取线索。最小化可观测差异，是现代安全设计的一门必修课。</span>

历史教训遍地都是：2010 年前后的 **ASP.NET 填充预言漏洞**可让攻击者还原 ViewState 里的敏感数据；**Java 的 CBC 实现**多次出现同类问题；**POODLE**（2014）利用 SSL 3.0 的 CBC 填充直接绕过加密读明文。这些都不是新理论，而是同一个 2002 年的攻击在十多年里反复上演——**因为总有人在「手动拼」加密、填充与错误处理**。用现成的 AEAD 库，是写给未来的自己最便宜的保险。

## 6 术语速查

| 术语 | 含义 |
| --- | --- |
| 填充（padding） | 把明文补到分组长度整数倍的字节方案 |
| PKCS#7 | 缺 $k$ 字节补 $k$ 个值为 $k$ 的字节；最短填 1 |
| 填充预言 | 能回答「填充是否合法」的黑盒（错误码/时序） |
| CBC 位翻转 | 篡改 $C_{i-1}$ 一个字节只影响 $P_i$ 对应字节 |
| 偶然命中 | 最后一字节恰为 0x02 0x02 等导致的误判 |
| AEAD | 认证加密，先验标签、失败即拒，从根上封死预言 |

## 7 小结

- **填充方案**：PKCS#7 缺 $k$ 补 $k$ 个 $k$；解密时校验填充合法性；填充永不省略。
- **填充预言**：服务器对「填充合法/非法」的反馈差异，就是可被利用的预言。
- **攻击流程**：篡改 $C_{i-1}$ 末字节 → 遍历 256 个值 → 命中「0x01 合法」即还原一个明文字节；逐字节推进，每分组 ≤ 4096 次查询。
- 攻击打的是 **CBC + 错误处理**，与密钥长度无关；AES-256 同样脆弱。
- 错误响应越统一越好——「悄悄失败」比「响亮失败」更安全。
- **防御正解**：认证加密（先验标签、失败即拒），加上统一错误信息、恒定时间比较。
- 攻击在协议层面完全「合规」——伪装成普通请求，网络层难以检测，只能靠协议层封死。
- 推论：任何「自己拼 分组密码 + 填充 + 错误处理」的做法都是重造轮子，用 AEAD 是唯一省心的答案。

- 填充方案细节：填充永不省略（最短 1 字节），否则无法区分「恰好整块」与「有填充」。
- 一个自查问题：你的系统把「填充错误」与「认证失败」区分开了吗？如果是，它可能就是一个预言。
