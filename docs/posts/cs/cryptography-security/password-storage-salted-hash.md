## 为什么从口令存储开始

上一节说口令是最普及的认证因子——这引出最关键的工程问题：**服务器怎么存口令？** 存明文是灾难（泄露即沦陷）；存裸哈希也不够（GPU 秒破、彩虹表、撞库）。正确的答案是**加盐 + 慢哈希**：让每个用户的哈希都不一样（盐）、让每次猜测都昂贵（慢）。PBKDF2、bcrypt、Argon2 是三代标准实现。这一节讲清「为什么裸哈希不够」与「盐和慢到底解决了什么」。<span class="marginnote">一个令人震惊的历史数字：2012 年 LinkedIn 泄露 1.6 亿口令——<strong>只做了 SHA-1 哈希、没加盐</strong>，绝大多数在几小时内被彩虹表与字典攻击还原。这次事故是「加盐哈希」从最佳实践变成强制标准的转折点。</span>

## 1 为什么裸哈希不够：三个致命问题

如果服务器只存裸哈希（如 SHA-256），有三个致命弱点：

**彩虹表（rainbow table）**：攻击者预先算好「常见口令 → 哈希」的大表，拿到哈希直接查表还原——对常见口令几乎秒破。
**GPU 暴力**：SHA-256 在 GPU 上每秒可算数十亿次——8 位以下的随机口令几分钟就能穷举。
**相同口令相同哈希**：两个用户用同一口令，哈希相同——攻击者一次破解，两个账号同时沦陷（还能发现「谁用了弱口令」）。

**辨析｜易错点：** 「用 SHA-256 存口令」常被误当成「安全」。SHA-256 是**快速**哈希，它的设计目标就是「算得快」——而口令验证恰恰需要「算得慢」。用快速哈希存口令，等于把攻击者的穷举速度也拉到最快。这提醒我们：**密码学工具没有绝对的好坏，只有「是否适合场景」**。SHA-256 适合校验完整性，慢哈希才适合口令。

## 2 盐（Salt）：让相同口令产生不同哈希

**盐（salt）**：给每个用户生成一个**随机盐**，存明文，并把盐与哈希一起存储。

**盐是公开的**（不保密），它的作用是**随机化**：每个用户盐不同 → 相同口令的哈希不同 → 彩虹表失效、跨用户破解不共享。
盐必须**足够长且唯一**（通常 16 字节），每个口令独立生成。

**盐解决了什么**：彩虹表攻击（表针对固定哈希，盐让每个哈希都是「新问题」）与跨用户关联（同口令不同哈希）。**盐不解决**「慢」的问题——它不增加单次猜测的成本。<span class="marginnote">一个常见误解：<strong>盐不是秘密，是「去重剂」</strong>。它让每个哈希都独一无二，迫使攻击者「一对一」地猜，而不是「一次算好、处处可用」。把盐保密（当作 pepper）是额外加固，但盐的本职是公开的随机化。</span>

用数字体会盐的威力：假设攻击者有一张覆盖 $10^{10}$ 条常见口令的彩虹表。对裸哈希，一次查表就还原口令；对加盐哈希，每个用户都要重新算一遍 $10^{10}$ 次——**彩虹表的「预计算」优势被完全抹平**，攻击者退回到「每个哈希单独暴力」的起点。

## 3 慢哈希：让每次猜测都昂贵

**慢哈希（slow hash / KDF）**：把口令哈希的代价**人为拉高**——单次验证慢（如 100ms），攻击者的穷举也慢（每猜一个口令都要 100ms）。这是「时间换安全」：合法用户登录一次无感，攻击者穷举百万口令要几小时。

**三个标准**：

**PBKDF2**：反复应用 HMAC 指定次数（如 600,000 次迭代）。可调迭代数、基于 HMAC（通用）。**弱点是抗 GPU 一般**（迭代次数可被并行）。
**bcrypt**：基于 Blowfish 的密钥调度，内置**内存成本**。抗 GPU 更好（有内存依赖），是 2000–2010 年代的默认选择。
**Argon2**：2015 年密码哈希竞赛冠军，可调**时间、内存、并行度**三参数——抗 GPU 与 ASIC 最强，是现代推荐（Argon2id 变体）。

**关键**：不是「用 SHA-256 多跑几轮」就行——慢哈希要**设计上抗并行**（内存硬依赖），否则 GPU 并行直接抵消「慢」的努力。<span class="marginnote">记忆锚点：<strong>PBKDF2 用「迭代次数」制造慢，bcrypt 用「内存」制造慢，Argon2 用「内存 + 时间 + 并行度」制造慢</strong>。抗专用硬件（GPU/ASIC）的关键是「内存硬」——让并行的每个核都要大内存，而内存带宽是稀缺资源。</span>

**辨析｜易错点：** 「迭代次数越多越好」是个片面结论。PBKDF2 的迭代次数再多，也只消耗 CPU/GPU 的**计算**资源——专用 ASIC 可以堆大量并行核来分摊，因为每次迭代只用一个寄存器的状态。而 Argon2 的「内存硬」让**每个并行核都需要独立的大块内存**，内存带宽成为瓶颈，ASIC 的并行优势被抹掉。所以选择慢哈希时，「内存成本」比「迭代次数」更关键。

## 4 公式解析：加盐慢哈希的存储格式

| 算法 | 慢的来源 | 抗 GPU/ASIC | 现状 |
| --- | --- | --- | --- |
| PBKDF2 | 迭代次数 | 一般 | 兼容首选，需高迭代 |
| bcrypt | 内置内存 | 较好 | 2000–2010 默认 |
| Argon2id | 内存+时间+并行 | 最强 | 现代推荐 |

## 4 公式解析：加盐慢哈希的存储格式

$$
\text{store} = \text{format} \| \text{params} \| \text{salt} \| H(\text{password}, \text{salt}, \text{params})
$$

三步拆解这条「口令存储记录」：

- **第一步，盐**：16 字节随机盐，每次注册生成——保证同口令不同哈希。
- **第二步，参数**：慢哈希的强度参数（迭代次数/内存/并行度）——让验证与攻击成本都明确可调。
- **第三步，哈希**：$H$ 是慢哈希（PBKDF2/bcrypt/Argon2id），输出嵌入盐与参数——验证时用存的盐与参数重算，比对结果。

例如 Argon2id 存储串：`$argon2id$v=19$m=65536,t=3,p=4$c29tZXNhbHQ$RdescudvJCsgt3ub+b+dWRWJTmaaJObG`——全部信息都在，验证者可复算。

**重点：存储串自包含（self-contained）。** 格式、参数、盐、哈希全在一个字符串里——验证程序只需这一个串就能重算比对，也方便未来升级参数（改存新的参数再重哈希）。这是现代口令库的标准做法，避免了「参数存在别处、升级要迁移」的麻烦。

## 5 验证流程与升级路径

**登录验证**：

1. 从数据库取出该用户的盐、参数与哈希。
2. 用同样的参数重算哈希。
3. 恒定时间比对，一致则通过。

**口令升级**：用户下次登录时，若存的参数过旧（迭代太少），用新参数重哈希并更新——渐进式加固。

**防爆破**：慢哈希之外，还要**速率限制**（同账号/同 IP 失败次数限制）与**账号锁定/审计**——慢哈希解决「离线拖库」，速率限制解决「在线爆破」——两者互补。<span class="marginnote">一个完整的口令安全栈：<strong>加盐（防彩虹表）+ 慢哈希（防 GPU）+ 速率限制（防在线爆破）+ 恒定时间比较（防侧信道）</strong>——每一层防一种攻击，缺一不可。现代框架（如 Django、Rails）默认内置这套栈，但历史系统常缺其中几层。</span>

**辨析｜易错点：** 登录失败时，不要立刻返回「口令错误」——那会泄露「用户名是否存在」（用户名枚举）。正确的做法是：无论用户名是否存在都返回「用户名或口令错误」，并执行同等代价的口令哈希计算——让攻击者无法通过响应差异探测有效用户名。

## 6 术语速查

| 术语 | 含义 |
| --- | --- |
| 裸哈希 | 只用快速哈希（如 SHA-256）存口令，不安全 |
| 彩虹表 | 预计算的「常见口令→哈希」查表 |
| 盐（salt） | 每个用户唯一的随机值，让同口令不同哈希 |
| 慢哈希/KDF | 故意拉高计算成本的哈希（PBKDF2/bcrypt/Argon2） |
| 内存硬 | 需要大内存的哈希，抗 GPU/ASIC 并行 |
| 恒定时间比较 | 长度固定、不随内容变化的比对，防计时攻击 |
| pepper | 附加的全局保密盐（可选加固） |

## 7 小结

- **裸哈希不够**：彩虹表、GPU 暴力、同口令同哈希——三个致命弱点。
- **盐**：随机、公开、每用户唯一——让同口令不同哈希，彩虹表与跨用户关联失效。
- **慢哈希**：拉高单次验证成本——PBKDF2（迭代）、bcrypt（内存）、Argon2（内存+时间+并行）。
- **存储格式**：参数‖盐‖哈希——验证可复算、参数可升级、存储串自包含。
- 完整栈：加盐 + 慢哈希 + 速率限制 + 恒定时间比较——现代框架默认，历史系统常缺。
- 口令安全的顺序：先防「离线拖库」（慢哈希），再防「在线爆破」（速率限制），缺一不可。
- 一条铁律：存口令用「慢哈希」，校验完整性才用「快速哈希」——工具要匹配场景。
- 选型建议：新系统默认 Argon2id；兼容老系统用 PBKDF2 并设高迭代；绝不自己发明口令哈希。
- 迁移技巧：加盐哈希无法「原地解密」旧库，用「下次登录重哈希」渐进升级最省事。
- 一句话总结：存口令 = 加盐 + 慢哈希 + 自包含存储串；验证 = 复算 + 恒定时间比对。

- 最后一个提醒：口令存储做对了，也不等于认证安全——下一节开始讲「传输与验证」环节的协议层防护。
