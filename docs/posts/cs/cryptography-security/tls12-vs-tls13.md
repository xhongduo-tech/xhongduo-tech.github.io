# TLS 1.2 与 TLS 1.3 的差异

## 为什么从 TLS 1.2 与 1.3 的差异开始

TLS 1.2（2008）统治互联网十年，TLS 1.3（2018）则是一次「从复杂到简洁」的重写。理解两者的差异，不只是背几个版本号——它揭示了安全协议设计的一个根本转向：**从「给足选项让使用者配置」到「砍掉选项让默认安全」**。这一节用一张对比表 + 逐项拆解，把两代的握手、密码套件、记录层、性能差异讲透。<span class="marginnote">一个数字锚点：TLS 1.2 的标准密码套件有几十个，TLS 1.3 只有 5 个。<strong>「少即是多」在安全里尤其成立——每个多余的套件都是一个潜在的弱点面</strong>。</span>

## 1 核心差异总览

| 维度 | TLS 1.2 | TLS 1.3 |
| --- | --- | --- |
| 密钥交换 | RSA / DH / ECDH（可选） | **仅 (EC)DHE** |
| 密码套件 | 可组合（密钥交换+认证+AEAD） | **只有 AEAD**（套件=AEAD+哈希） |
| 记录层 | CBC 模式（可协商） | **仅 AEAD**（GCM/ChaCha20） |
| 前向保密 | 需正确配置 ECDHE | **强制**（默认即安全） |
| 握手往返 | 完整 2-RTT | 1-RTT，恢复 0-RTT |
| 版本协商 | 客户端明文声明 | 加降级保护（转录签名） |
| 会话恢复 | Session ID / Ticket | PSK（预共享密钥） |
| 压缩 | 支持（CRIME 漏洞） | 移除 |
| 认证器 | 独立 CertificateVerify | 签名覆盖完整转录 |

## 2 密码套件的简化：从「组合」到「套餐」

**TLS 1.2 的套件**是**组合式**的：`TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256`——密钥交换（ECDHE）+ 认证（RSA）+ 加密（AES-GCM）+ 哈希（SHA256）各自独立可换。几十个组合给了攻击者「诱导降级到弱组合」的空间（如 RSA 密钥交换无前向保密、CBC 套件可被 POODLE 攻击）。

**TLS 1.3 的套件**是**套餐式**的：`TLS_AES_128_GCM_SHA256`——加密与哈希二选一，密钥交换（ECDHE）与认证（证书签名）是**固定结构**。套件名称短了，安全边界却清晰了：**只要用 1.3，就默认有前向保密 + AEAD**，不存在「配错」的窗口。<span class="marginnote">一个设计洞察：<strong>TLS 1.2 把「安全」当可选配置，TLS 1.3 把「安全」当协议不变量</strong>——密码套件不再能选择「弱模式」，因为弱模式根本不存在了。这消灭了一整类「配置失误导致的漏洞」。</span>

## 3 握手与性能：从 2-RTT 到 1-RTT 再到 0-RTT

**TLS 1.2 完整握手**（2-RTT）：ClientHello → ServerHello + 证书（1 个 RTT）→ 客户端发密钥交换+Finished（1 个 RTT）→ 服务器 Finished → 才开始数据。加上 TCP 的 1-RTT，首次连接共 3-RTT。

**TLS 1.3 完整握手**（1-RTT）：ClientHello 直接带客户端 ECDHE 公钥 → 服务器一条消息返回 ServerHello + 服务器 ECDHE + 证书 + 签名 + Finished → 客户端发 Finished + 第一条数据。**密钥交换提前到第一条消息**，省掉一个完整往返。

**TLS 1.3 恢复**（0-RTT）：客户端用上次的 PSK，在第一条消息就带应用数据——**零往返**。代价是可重放，只限幂等请求。

**性能差距**：对 API 密集应用，0-RTT 可省数十毫秒到数百毫秒——这是 TLS 1.3 被 CDN 与移动应用广泛采用的直接动力。<span class="marginnote">为什么 1.3 能「提前带公钥」：因为密钥交换（ECDHE）不依赖服务器身份——客户端可以先把「我这边的一半 DH 值」发出去，等服务器身份认证后再补签名验证。<strong>「先协商密钥、后认证身份」的次序，用 1-RTT 换来了安全（身份绑定在 transcript 里）</strong>。</span>

## 4 公式解析：TLS 1.3 的 transcript 签名

$$
\sigma_{server} = \text{Sign}_{sk}\big(H(\text{ClientHello} \| \text{ServerHello} \| \text{证书} \| \cdots)\big)
$$

三步拆解这条「转录签名」为什么同时防篡改与防降级：

- **第一步，累积**：握手每一层消息的哈希持续累积成 transcript——一个「完整会话指纹」。
- **第二步，签名覆盖**：服务器的 CertificateVerify 签名覆盖 transcript——任何消息被改/重排，转录变，签名失。
- **第三步，防降级**：若攻击者诱导客户端「声明低版本」，ServerHello 会写入「降级标记」，该标记进入转录——客户端验证签名时发现标记与版本不符即中止。**版本协商被钉进签名**。

## 5 迁移的现实：兼容性与中间件

TLS 1.2 → 1.3 的迁移不是一蹴而就：

- **服务器**：需支持 TLS 1.3（现代 OpenSSL/nginx/Cloudflare 皆已支持）。
- **客户端**：现代浏览器全部支持；老客户端（2016 年前）只到 1.2。
- **中间件**：老式代理、负载均衡器、防火墙可能不识别 1.3 的握手指纹——需升级。
- **兼容策略**：服务端同时支持 1.2 与 1.3，让客户端协商到最高共同版本。

**现状（2026）**：主流 Web 流量已以 TLS 1.3 为主，1.2 作为兼容层仍在服务老旧系统。<span class="marginnote">迁移的工程规律：<strong>安全协议升级的阻力不在协议本身，而在「不升级就没事」的中间件生态</strong>——负载均衡、WAF、监控系统不认识新协议握手，就不敢开。TLS 1.3 从标准到普及花了 5 年+，靠的是「向后兼容 + 生态压力」双重驱动。</span>

## 6 小结

- **核心差异**：TLS 1.3 强制 (EC)DHE + AEAD、砍掉 RSA 交换与 CBC、套件从「组合」变「套餐」。
- **前向保密**：1.2 需配置、1.3 默认——「安全是默认」的量化体现。
- **性能**：完整握手 2-RTT → 1-RTT，恢复 0-RTT——密钥交换提前到第一条消息。
- **防降级**：转录签名 + 降级标记——版本协商被钉进认证。
- **迁移**：兼容策略「双版本共存」，中间件生态是主要阻力；主流已转向 1.3。
