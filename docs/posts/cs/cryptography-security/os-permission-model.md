## 为什么从操作系统权限模型开始

第十三篇的漏洞攻击「应用」，这一节进入「系统安全」：操作系统如何决定「谁能访问什么」。**权限模型**是系统的第一道防线——用户、组、权限位、访问控制表（ACL）构成 Unix/Windows 的授权骨架。理解权限模型，等于理解「提权攻击在打什么」「为什么最小特权如此重要」。<span class="marginnote">一个概念定位：<strong>认证（authentication）回答「你是谁」，授权（authorization）回答「你能做什么」</strong>——前面讲了大量认证，这一节讲授权。系统安全 = 认证 + 授权 + 隔离 + 审计 四根支柱。</span>

## 1 主体与客体：权限的语法

**主体（subject）**：发起访问的实体——用户、进程。

**客体（object）**：被访问的资源——文件、设备、进程、内存。

**权限（permission）**：主体对客体能做的操作——读、写、执行、删除、发送信号……

权限模型回答三个问题：

1. **主体是谁**（身份）。
2. **客体是什么**（资源）。
3. **允许什么操作**（权限集）。

**Unix 的经典模型**：每个文件有三个「身份类别」——owner（属主）、group（属组）、other（其他人），每类三个权限——r（读）、w（写）、x（执行）。例如 `rwxr-xr--` 表示：属主 rwx、属组 r-x、其他人 r--。<span class="marginnote">Unix 权限的读写执行：<strong>r=读内容、w=改内容、x=当程序执行</strong>。对目录来说语义不同：r=列出文件名、w=增删文件、x=进入目录。这套「三三制」简单到极致，但也因此不够精细——ACL 与 SELinux 是对它的扩展。</span>

## 2 从权限位到 ACL：更细的粒度

**权限位**（rwx）只能表达「三档」（owner/group/other），粒度太粗。**ACL（访问控制表，Access Control List）** 把每个客体的权限变成「主体 → 权限」的列表：

```
$ getfacl report.txt
user::rw-
user:alice:rw-
group::r--
group:finance:r--
mask::rw-
other::---
```

每条 ACL 项指定「某个用户/组对某文件有什么权限」。
比 rwx 精细——能表达「Alice 可写、Bob 只读、其他组不可访问」。

**Unix ACL**（POSIX ACL / NFSv4 ACL）与 **Windows ACL**（NTFS 的 DACL）是现代系统的标准。ACL 是「DAC」的核心实现（下一节讲 DAC 与 MAC）。<span class="marginnote">ACL 的直观意义：<strong>权限位是「三格抽屉」，ACL 是「一张完整的授权表」</strong>——企业里「财务组能读报表、只有审计员能改」这类需求，权限位表达不了，ACL 正好。</span>

## 3 超级用户与特权：权限的「顶点」

Unix 有 **root（超级用户）**，Windows 有 **Administrator/System**——它们的权限是「全有」，能绕过一切 ACL 检查。

**特权的双刃剑**：

**必要**：系统管理（装驱动、改配置、管用户）需要最高权限。
**危险**：被攻破的 root 进程 = 攻击者拥有整台机器——**提权（privilege escalation）** 是系统攻击的核心目标。

**现代趋势——特权最小化**：

**capabilities（Linux 能力）**：把 root 的「全能」拆成几十个独立能力（`CAP_NET_BIND_SERVICE`、`CAP_SYS_ADMIN`）——进程只需「绑定 80 端口」的能力，不必是 root。
**降权运行**：服务以普通用户运行，不 root。
**权限分离**：需要特权的操作拆到独立小进程（如 OpenSSH 的 privilege separation）。

**理解 root 的风险，是理解一切系统攻击的钥匙**——「拿到 root = 拿到机器」是攻击者的终极目标，防御者的一切努力都是「让拿到 root 变难」。<span class="marginnote">Linux capabilities 的哲学：<strong>把「全能 root」拆成「按需授权的能力位」</strong>——一个只想绑定 80 端口的服务，只需 `CAP_NET_BIND_SERVICE`，其余能力一概不给。这比「root/非 root」二元模型精细得多，也是容器（Docker 默认丢弃大量能力）安全性的基础。</span>

## 4 公式解析：Unix 权限的检查流程

$$
\text{允许访问} \iff \exists \text{ ACL 项} (\text{主体} \in \text{项的主体}, \text{所需操作} \in \text{项的权限})
$$

三步拆解这条「权限检查」：

- **第一步，定位主体**：进程的用户 ID（UID）与组 ID（GID）确定「我是谁」。
- **第二步，查 ACL**：内核在客体的 ACL 里找「匹配 UID/GID 的项」——按顺序匹配第一条。
- **第三步，判定**：所需操作（读/写/执行）在匹配项的权限集里才允许——否则返回 `EACCES`（权限拒绝）。

## 5 权限模型的现实问题

权限模型在实践中不断暴露新问题：

- **过度授权**：默认「给太多」（开发图省事给 777、root 跑服务）——攻击面扩大。
- **共享账户/组**：多人共用一个账户，无法审计「谁干的」。
- **ACL 复杂化**：ACL 越精细越难管理——权限漂移（权限只加不减）。
- **提权漏洞**：内核/驱动的权限检查 bug（脏牛 Dirty COW 等）——权限模型再完善，实现漏洞仍可绕过。

**趋势**：向「最小特权 + 可审计 + 动态授权」演进——零信任架构里的「每请求授权」、云 IAM 的「角色而非账户」。<span class="marginnote">把权限模型与前面的内容连起来：<strong>「最小特权原则」贯穿一切安全设计</strong>——数据库账号只给必要权限（防 SQL 注入拖库）、进程用非 root 运行（防 RCE 直达 root）、服务降权（防被攻破后横向扩散）。权限模型是「最小特权」落到操作系统的载体。</span>

## 6 小结

- **主体/客体/权限**：权限模型的三个要素——谁、对什么、能做什么。
- **Unix rwx**：owner/group/other × r/w/x 的「三三制」——简单但粗粒度。
- **ACL**：主体→权限的列表——细粒度授权（DAC 的实现）。
- **超级用户与特权**：root 全能、提权是核心目标；现代用 **capabilities** 拆分特权。
- **现实问题**：过度授权、权限漂移、提权漏洞——趋势是最小特权 + 可审计。
