# HMAC 的构造与安全性

<div class="epigraph">
<p>HMAC 用一个简单的夹心结构，把哈希函数变成了一个带密钥的 MAC——它的优雅在于，安全建立在哈希的「最小假设」之上。</p>

## 为什么从 HMAC 开始

上一节说 MAC 有两条构造路线，其中哈希型的事实标准就是 **HMAC**。1996 年 Bellare 等人提出，1997 年进入 RFC 2104，此后成为 TLS、SSH、IPsec、JWT、API 签名的事实认证原语。HMAC 的特别之处在于：它**不要求**哈希函数有多强的性质——只要底层哈希是「弱伪随机的」，HMAC 就是安全的。这给了它近乎普适的适用性。这一节拆开 HMAC 的构造、正确性与安全性。<span class="marginnote">HMAC 的诞生背景：1996 年前，人们用各种「把密钥接进哈希」的土办法（secret-prefix、secret-suffix），全都被长度扩展攻击或穷举攻击打穿。HMAC 是第一个把「密钥混入哈希」做对的标准化构造。</span>

## 1 构造：ipad 与 opad 的夹心

HMAC 的公式（RFC 2104）：

$$
\text{HMAC}_K(m) = H\big((K' \oplus \text{opad}) \| H((K' \oplus \text{ipad}) \| m)\big)
$$

其中：

- $K'$：若 $K$ 比哈希块长，先哈希压缩成块长；否则直接补零到块长。
- $\text{ipad} = 0x36$ 重复到块长，$\text{opad} = 0x5c$ 重复到块长。
- 外层用 opad、内层用 ipad，两层哈希夹住「密钥+消息」。

**为什么两层**：外层哈希把内层结果「锁」住，防止从 $H(m)$ 直接推出 $H(m\|x)$（长度扩展的防护正是靠外层 opad 的密钥遮蔽）。

## 2 公式解析：HMAC 的两次哈希

$$
\text{HMAC}_K(m) = H(\underbrace{K' \oplus \text{opad}}_{\text{外层密钥}} \| \underbrace{H(K' \oplus \text{ipad} \| m)}_{\text{内层摘要}})
$$

三步拆解这条「夹心公式」：

- **第一步，内层**：先算 $H(K' \oplus \text{ipad} \| m)$——把密钥与消息混在一起哈希。ipad 让内层密钥块与外层不同。
- **第二步，外层**：把内层摘要接到「opad 密钥」后面再哈希一次——外层把内层结果封装，同时让「密钥」最终仍参与最后一步。
- **第三步，为什么安全**：即使攻击者知道内层摘要，他也**不知道 $K' \oplus \text{opad}$**（密钥被 opad 二次隐藏），无法继续「接消息」——长度扩展攻击被外层阻断。

## 3 为什么 HMAC 不要求哈希抗碰撞

直觉上，MAC 应该需要哈希抗碰撞。但 HMAC 的安全性证明给出一个更强的结论：**只要底层哈希是伪随机的（PRF），HMAC 就是安全的 MAC**——甚至不需要哈希抗碰撞。

原因：HMAC 把密钥藏在 ipad/opad 里，攻击者面对的是一个「带密钥的黑盒」，而不是「无密钥的公开函数」。碰撞攻击需要攻击者能自由选择输入并观察输出；但 HMAC 里攻击者不知道密钥，无法构造「对 HMAC 的两个输入」来碰运气。所以：

- 即使某天 SHA-1 的碰撞被进一步实用化，**HMAC-SHA1 至今仍未**被攻破（SHA-1 的碰撞攻击不能直接迁移到 HMAC）。
- HMAC 的安全性绑定在「哈希作为 PRF」这个弱得多的假设上——这是它「普适」的根源。<span class="marginnote">一个耐人寻味的事实：<strong>HMAC-SHA1 至今安全，而裸 SHA-1 已被碰撞攻破</strong>。密钥的存在把「公开碰撞攻击」挡在门外。这提醒我们：一个组件的「安全属性」高度依赖它被使用的「上下文」——同一哈希，裸用被攻破，套进 HMAC 就安全。</span>

## 4 HMAC 家族与用途

HMAC 与不同哈希组合覆盖各种场景：

**HMAC-SHA256**：现代默认，TLS 1.2 记录层、JWT、API 签名。
**HMAC-SHA1**：老系统仍在用（如老 TLS、OAuth 1.0），至今安全但新系统不推荐。
**HMAC-SHA3**：新建系统的选项。

**工程用途**：
**API 认证**：把请求体哈希成签名，防篡改与伪造。
**HKDF（密钥派生）**：用 HMAC 做「提取-扩展」，把共享秘密派生成会话密钥（TLS 1.3 的 KDF 基石）。
**TOTP（一次性口令）**：HMAC 加时间计数器生成动态验证码。
**带状态验证**：cookie 签名、JWT 的 HMAC 变体。

## 5 使用 HMAC 的纪律

HMAC 正确用，几条纪律必须遵守：

**密钥长度**：至少等于哈希输出长度（HMAC-SHA256 用 ≥ 32 字节密钥）；短密钥浪费安全性。
**密钥独立**：HMAC 密钥与加密密钥分离（密钥派生、不用同一个）。
**恒定时间比较**：比对标签必须用恒定时间比较函数（如 Python 的 `hmac.compare_digest`），否则计时侧信道泄露「第几个字节不同」，逐字节猜出标签——**这是 API 签名验证最常见的漏洞**。
**消息编码**：HMAC 的输入必须明确界定边界（防「拼接歧义」），通常用长度前缀或规范编码。<span class="marginnote">「恒定时间比较」是一条易被忽略的红线：<strong>用 `==` 或 `memcmp` 比较标签，攻击者就能按「比较耗时」推断「前缀匹配了几位」</strong>——逐位猜出合法标签。几乎所有语言的标准库都提供恒定时间比较（如 Python 的 `hmac.compare_digest`），必须用它。</span>

## 6 小结

- **HMAC**：$\text{HMAC}_K(m) = H((K'\oplus\text{opad}) \| H((K'\oplus\text{ipad}) \| m))$——两层夹心。
- 外层 opad 阻断**长度扩展攻击**；密钥藏在 ipad/opad 里。
- 安全基于「哈希是 PRF」的弱假设——**不要求哈希抗碰撞**（HMAC-SHA1 至今安全）。
- 用途：API 签名、HKDF、TOTP、TLS 1.2——现代认证原语。
- 纪律：密钥够长、密钥独立、**恒定时间比较**、消息边界明确。
