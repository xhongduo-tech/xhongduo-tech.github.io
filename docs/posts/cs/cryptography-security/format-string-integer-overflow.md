## 为什么从格式化字符串与整数溢出开始

缓冲区溢出是「写太多」，而这一节的两个漏洞是「读太多」与「算错数」：**格式化字符串漏洞**把用户输入当格式串，泄露/改写任意内存；**整数溢出**让「看似安全的长度检查」在算术上被绕过。它们与缓冲区溢出一样根源于 C 语言的「信任程序员」哲学，且经常**配合**使用（整数溢出绕过长度检查 → 触发栈溢出）。理解它们是掌握「编程错误 → 安全漏洞」映射的重要一环。<span class="marginnote">一个连接点：<strong>格式化字符串漏洞常被用来「泄漏 ASLR 地址与 canary」</strong>——它把上一节的「信息泄漏」能力变成现成工具。而整数溢出常是「绕过长度检查」的第一步，为后续溢出铺路。三类漏洞是「漏洞链」的常客。</span>

## 1 格式化字符串漏洞：printf 的格式串

C 的 `printf` 系列函数接受**格式字符串**，用 `%d`、`%s`、`%x` 等占位符读取**可变参数**：

```c
printf(user_input);   // 危险！
printf("%s", user_input);  // 安全
```

**漏洞**：当用户输入被直接当作格式串时，攻击者可放入 `%x %x %x...`（读栈上的任意值）、`%n`（**写入**内存）。这就是**格式化字符串漏洞（format string vulnerability）**。

**能做什么**：

- **读内存**：`%x`/`%p` 把栈上的值当作参数打印——泄漏地址、canary、甚至栈上的其他数据。
- **写内存**：`%n` 把「已打印的字符数」写入指定地址——配合 `%hhn` 可逐字节改写任意内存（如返回地址、函数指针）。

它是「读+写任意内存」的万能漏洞——利用难度低、危害极大。<span class="marginnote">`%n` 的威力：<strong>printf 家族支持「把输出长度写进内存」——这让格式化字符串从「泄露信息」升级成「任意写」</strong>。攻击者用地址作 `%n` 的目标，用填充控制写入的值，就能改写返回地址或 GOT 表项，实现代码执行。这是「一个格式串 = 任意读 + 任意写」的可怕来源。</span>

## 2 公式解析：格式化字符串的读写

$$
\%n: \text{ 把已打印字符数写入地址}, \qquad \%hhn: \text{ 写单字节}
$$

三步拆解这条「格式化字符串利用」：

- **第一步，定位栈参数**：`printf("%p%p%p%p%p")` 会打印栈上前 5 个「参数位置」的值——攻击者数出「我的输入在栈上第几个参数」。
- **第二步，用地址覆盖**：在输入里放一个目标地址（如返回地址），再用 `%<n>`hhn` 指定「把值写到第 n 个参数所指的地址」。
- **第三步，逐字节改写**：`%hhn` 每次写 1 字节，配合控制「已打印字符数」，逐字节把目标地址改成攻击代码/ROP 的地址。

## 3 整数溢出：算术的边界陷阱

**整数溢出（integer overflow）** 是「整数运算结果超过类型上限」导致的回绕。C 的类型有固定宽度：

```c
uint16_t len = strlen(input);   // 假设 = 65535
char buf[256];
if (len < sizeof(buf)) {        // 检查通过？
    memcpy(buf, input, len);    // 但 len 被截断/回绕……
}
```

**两种经典形态**：

- **回绕（wrap-around）**：`unsigned` 溢出回绕到 0——`0 - 1 = 0xFFFFFFFF`（极大值），长度检查被绕过。
- **截断（truncation）**：大类型赋给小类型丢失高位——`65536 → 0`，检查通过但实际长度远大于缓冲区。

**利用模式**：**「整数溢出 → 长度检查绕过 → 缓冲区溢出」** 是经典漏洞链。攻击者构造一个「检查时看似很小、memcpy 时实际很大」的长度值。<span class="marginnote">整数溢出的本质：<strong>「符号位与宽度是算术的隐藏假设」</strong>——C 里 `-1 > 0` 为真（因为 `-1` 转成无符号是最大数），`65536` 赋给 `uint16_t` 变 `0`。任何「用整数做安全边界」的代码都必须警惕这些算术陷阱。</span>

## 4 公式解析：回绕绕过长度检查

$$
\underbrace{\text{len}}_{\text{无符号回绕后极小}} \;\; \text{通过检查} \;\; \Rightarrow \;\; \underbrace{\text{memcpy 实际拷贝}}_{\text{巨大}} \;\; \text{溢出}
$$

三步拆解这条「回绕攻击」：

- **第一步，构造输入**：`len = 0x100000000 - k`（一个「回绕后很小」的巨大数）。
- **第二步，检查通过**：`len < 256` 因为回绕后 `len = -k mod 2^32` 恰好是「小值」——检查被骗。
- **第三步，实际溢出**：`memcpy` 用**原值**（巨大）拷贝——缓冲区被远超预期地写满，触发栈/堆溢出。

## 5 现实中的漏洞与修复

**真实案例**：

- **格式化字符串**：Linux 内核的历史 CVE、Apache 的 mod_ssl 漏洞、大量 daemon——`%n` 任意写曾是 2000 年代远程利用主流。
- **整数溢出**：OpenSSH、浏览器（如 2014 年的 ImageMagick）、游戏服务端——配合溢出成为 RCE 链条。

**修复与防御**：

- 格式化字符串：**永远用 `printf("%s", x)`**；编译器 `-Wformat-security` 警告；glibc 的 `FORTIFY_SOURCE` 检测。
- 整数溢出：用**无符号/有符号一致的比较**、`-fwrapv` 语义谨慎处理、运行时检查工具（ASan/UBSan）、用 `size_t` 与明确宽度。
- 语言层面：Rust 的溢出检查（debug 下 panic）、类型安全——再次指向「内存安全语言根治」。

**通用教训**：C 的「隐式转换 + 无边界检查」是这两类漏洞的共同土壤——**「看似无害的语言便利」累积成攻击面**。<span class="marginnote">一个编译器时代的防御：<strong>`FORTIFY_SOURCE` 与 `_FORTIFY_SOURCE=2` 能在编译期/运行期拦截「格式串非常量」的 printf 调用与常见溢出</strong>——现代 Linux 发行版默认开启。但它不是银弹：只覆盖「可静态判断」的情况，复杂的运行时构造仍需人工审查与语言迁移。</span>

## 6 小结

- **格式化字符串漏洞**：用户输入直接当格式串——`%x` 任意读、`%n` 任意写。
- **`%n` 的威力**：把「打印长度」写进内存——从信息泄漏升级为任意写。
- **整数溢出**：回绕 + 截断——「看似安全的长度检查」可被算术绕过。
- **漏洞链**：整数溢出绕过检查 → 栈溢出；格式化字符串泄漏 canary/ASLR → 配合 ROP。
- 修复：正确用 printf、警告选项、ASan/UBSan、类型安全语言——C 的便利是漏洞土壤。
