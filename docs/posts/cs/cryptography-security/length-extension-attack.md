## 为什么从长度扩展攻击开始

上一节强调 HMAC 用外层 opad 阻断长度扩展攻击——本节点破这个攻击本身。**长度扩展攻击（length extension attack）**是 Merkle-Damgård 结构（MD5、SHA-1、SHA-2）的固有弱点：给定 $H(m)$ 与 $m$ 的长度，攻击者**不需要知道 $m$ 的内容**，就能算出 $H(m \| \text{pad} \| x)$。这听起来像魔法，其实是链式压缩的直接后果。它让「secret-prefix MAC」（$H(K\|m)$）彻底失效，也是现代哈希转向海绵结构（SHA-3）的动力之一。<span class="marginnote">长度扩展攻击的最著名实战是 2009 年的 <strong>Flickr API 签名绕过</strong>：Flickr 用 $H(\text{secret}\|m)$ 当签名，攻击者据此给任意 API 调用伪造合法签名。<strong>「用户能控制的输入接在密钥后面」是长度扩展攻击的经典触发场景</strong>。</span>

## 1 前提：MD 结构的「可续算」性质

回忆 Merkle-Damgård 链式压缩：

$$
h_0 = IV, \qquad h_i = f(h_{i-1}, m_i), \qquad H(m) = h_k
$$

**关键观察**：摘要 $H(m) = h_k$ **就是**「算完所有块之后的状态」。攻击者拿到 $H(m)$，等于拿到了压缩函数的**中间状态**。他只要：

1. 把这个状态当作新的 $IV$。
2. 把「想要追加的内容 $x$」当作下一个块（前面补上正确的填充）。
3. 继续跑压缩函数。

就能得到 $H(m \| \text{pad}(m) \| x)$——**全程不需要知道 $m$**。

## 2 攻击流程：三步追加

假设受害系统用 $\text{MAC} = H(K \| m)$（secret-prefix），攻击者截获了 $(m, \text{tag})$：

- **第一步，恢复内部状态**：$\text{tag} = H(K\|m)$ 就是压缩函数处理完 $K\|m$（含填充）后的状态。这个状态直接可用。
- **第二步，伪造延长输入**：攻击者不知道 $K$，但知道 $K$ 的长度 $|K|$（可猜测或推断）。他构造「延长消息」$\bar m = (K \| m \| \text{pad} \| x)$——其中 $\text{pad}$ 是根据 $|K| + |m|$ 算出的合法填充，$x$ 是他想追加的内容。
- **第三步，续算标签**：从状态 $\text{tag}$ 出发，对 $\text{pad}\|x$ 继续压缩，得到 $\text{tag}' = H(\bar m)$——一个**合法的** MAC 标签。

攻击者现在有了「一个合法消息 + 一个合法标签」，而这条消息是他自己构造的、末尾多了 $x$。<span class="marginnote">攻击的前提细节：攻击者必须知道密钥长度 $|K|$。实践中 $|K|$ 常可推断（固定长度密钥、或从协议文档得知）。若不确定，可以<strong>对每个可能的 $|K|$ 都试一遍</strong>——每个长度算一次延长，总有一次能命中。</span>

用一个具体的 SHA-256 例子验证「续算」的确可行（示意，非完整实现）。设密钥 $K$ 长 16 字节、消息 $m$ 长 8 字节：

1. 攻击者拿到 $(m, \text{tag} = H(K\|m))$，$\text{tag}$ 是 32 字节的 SHA-256 输出。
2. 他算出「$K\|m$ 已处理的长度」为 $16 + 8 = 24$ 字节，据此构造 MD 填充 $\text{pad}$（补 0x80、补 0、补 24 字节的比特数 192）。
3. 他选追加内容 $x = \text{"/delete"}$，把 $\text{tag}$ 当作压缩函数的初始状态，对 $\text{pad}\|x$ 继续压缩，得到 $\text{tag}'$。
4. 他提交消息 $m' = (K\|m\|\text{pad}\|x)$——但注意他不知道 $K$，**他只提交「$(m\|\text{pad}\|x, \text{tag}')$ 给服务器验证，而服务器自己会在前面拼上 $K$」**——于是服务器算 $H(K\|m\|\text{pad}\|x)$，恰好等于攻击者算的 $\text{tag}'$——通过。

关键的最后一环是：**服务器只验证「标签是否匹配」，不检查「消息是否由服务器签发」**——这正是 secret-prefix MAC 方案的致命盲区。

## 3 公式解析：为什么「不知道 m 也能续算」

$$
H(m) = h_k, \qquad H(m \| \text{pad} \| x) = \text{compress}(h_k, \text{pad} \| x)
$$

三步拆解这条「续算魔法」：

- **第一步，状态即钥匙**：$H(m)$ 输出的不是「某种抽象摘要」，而是压缩函数的**最后一个状态** $h_k$。状态本身携带了 $m$ 的全部压缩信息。
- **第二步，填充可复制**：MD 填充（补 1、补 0、补长度）只依赖**输入长度**，而攻击者知道 $|K| + |m|$——他算得出合法填充 $\text{pad}$，让延长后的消息「看起来」是完全合法的输入。
- **第三步，续算即合法**：从 $h_k$ 出发继续压缩 $\text{pad}\|x$，得到的结果与「真实计算 $H(K\|m\|\text{pad}\|x)$」完全一致——因为压缩链每一步都是确定性的。

## 4 受影响的构造与不受影响者

**受影响**（都是 MD 结构 + 密钥位置错误）：

- **Secret-prefix MAC**：$\text{MAC} = H(K\|m)$——直接可延长攻击。
- **基于 $H(K\|m)$ 的签名、cookie 认证、URL 签名**——Flickr、各种框架的历史漏洞。
- 任何「把用户可控数据接在密钥后面再哈希」的方案。

**不受影响**：

- **HMAC**：外层 opad 把结果再封装，密钥不在「可续算」的终点。
- **SHA-3（海绵结构）**：挤压阶段的输出不是压缩终态，容量不可见——从结构上免疫。
- **Secret-suffix MAC**（$H(m\|K)$）：密钥在末尾，延长攻击追不到密钥后……但它有其他问题（前缀碰撞），也不推荐。

**正确做法**：**MAC 一律用 HMAC**，不要自创「哈希+密钥」方案。<span class="marginnote">一句实用的判定口诀：<strong>「密钥在前、内容在后，且用 MD 哈希」= 长度扩展攻击的温床</strong>。任何「$H(\text{secret} + \text{user_input})$」模式都要换成 HMAC、KMAC 或 SHA-3。这是安全审查里频率极高的发现项。</span>

把「受影响 / 不受影响」的判定标准汇总成一张速查表，做代码评审时直接对照：

| 构造 | 是否受影响 | 原因 |
| --- | --- | --- |
| $H(K \| m)$（secret-prefix） | 受影响 | 密钥在可续算的终点之前 |
| $H(m \| K)$（secret-suffix） | 否（但有前缀碰撞问题） | 密钥在末尾 |
| HMAC | 否 | 外层 opad 封装 |
| SHA-3 / KMAC | 否 | 海绵结构，输出非压缩终态 |

**判别准则一句话**：只要「用户可控数据」接在「密钥或未知前缀」后面、且用 MD 家族哈希，就默认它可被长度扩展攻击，除非有显式防护。

## 5 从长度扩展到协议设计

长度扩展攻击的教训超越 MAC 本身：

**结构决定安全边界**：MD 结构把「摘要」与「内部状态」耦合，暴露了续算能力；海绵结构把两者解耦。**设计密码时，「输出」与「内部状态」的边界必须清晰**。
**密钥与数据的拼接顺序**：密钥在前（secret-prefix）触发长度扩展；密钥在后（secret-suffix）触发前缀碰撞——**任何「手动拼密钥+哈希」都危险**，用标准化构造。
**对协议的影响**：很多历史协议（如老版 Flickr API、WordPress cookie）都因这个攻击被修复。现代协议（TLS 1.3、JWT）全部改用 HMAC 或 AEAD。<span class="marginnote">跨书连接：长度扩展攻击是「结构耦合」的又一例证——与 Padding Oracle 的「错误反馈耦合」、CTR 的「nonce 唯一性耦合」一样，<strong>安全漏洞往往出现在「组件接口的隐式约定」上</strong>。设计的接口越少隐式约定，越安全。</span>

**修复的通用形态**：凡是「把长度扩展漏洞堵上」的标准做法，本质上都在做同一件事——**让「输出的摘要」不再是「可续算的内部状态」**：

- HMAC 用外层 opad 重新封装，输出与内部状态解耦。
- KMAC（SHA-3 专用）用容量位把输入定界，从结构上消灭续算。
- SHA-3 海绵结构挤压阶段输出，状态不可见。

记住这个统一视角：**「输出 = 状态」是漏洞的根源，「输出 ≠ 状态」是修复的方向**。判断任何新哈希构造是否抗长度扩展，就检查这一条。

## 6 小结

- **长度扩展攻击**：给定 $H(m)$ 与 $|m|$，不需知道 $m$ 即可算 $H(m\|\text{pad}\|x)$——MD 结构的固有弱点。
- 根因：摘要 = 压缩终态，状态可续算；填充只依赖长度。
- **Secret-prefix MAC（$H(K\|m)$）被一击打穿**；HMAC 与 SHA-3 结构性免疫。
- 影响：cookie/URL/API 签名的历史漏洞（Flickr 2009）。
- 铁律：**MAC 一律用 HMAC/KMAC**，绝不手拼「密钥+哈希」。
- 记忆锚点：**「输出 ≠ 状态」才是安全的哈希接口**——凡是「摘要 = 压缩终态」的构造，都要警惕续算能力。
