# 权能（Capability）与最小特权原则

<div class="epigraph">

## 为什么从权能与最小特权开始

前两节讲了 DAC 与 MAC，这一节讲渗透所有安全设计的**第一原则**——**最小特权（least privilege）**：每个进程/用户/服务只应拥有完成任务**所必需的最小权限**。它的执行载体是**权能（capability）**——把「能力」作为可传递的令牌，替代「全有或全无」的超级用户。Linux capabilities、Android 权限、OAuth scope、AWS IAM 策略全是这一思想的实现。理解最小特权，等于理解「为什么 root 跑服务是坏实践」「为什么容器默认丢能力」。<span class="marginnote">最小特权的出处：<strong>Saltzer 与 Schroeder 1975 年在《计算机系统保护机制》里提出八条设计原则，「最小特权」是第一条</strong>。它被反复引用为安全设计的第一铁律——因为它同时降低「误操作风险」与「攻击影响」。</span>

## 1 最小特权：为什么「少给」更安全

**最小特权原则**：主体应只拥有完成其**合法任务**所需的最小权限。

它的安全价值有两条：

**限制误操作**：权限少，不小心删库/改配置的概率小。
**限制攻击影响**：进程被攻破时，攻击者继承的权限就是「这个进程的最小权限」——权限越小，损失越小。

**反面教材**：

用 root 跑 Web 服务——被攻破 = 攻击者直接是 root。
数据库账号用 DBA 权限——SQL 注入 = 整库为所欲为。
应用共享一个「管理员组」——一个成员被攻破，全组权限沦陷。

**最小特权不是「少给一点」，而是「精确到任务」**——每个服务一个账号、每个账号只有必要权限、权限用完即回收。<span class="marginnote">一个量化的直觉：<strong>攻击的「爆炸半径」= 被攻破进程的权限范围</strong>——root 的爆炸半径是整台机器，非 root 服务是它的数据目录，容器里是容器的沙箱。最小特权的每一层「降权」，都在缩小爆炸半径。</span>

## 2 权能：从「全能 root」到「按需能力」

**权能（capability）** 模型把「特权」从「一个全能身份」变成「一组可单独授予的能力令牌」。

**Linux capabilities**：把 root 的全能拆成几十种能力，如：

`CAP_NET_BIND_SERVICE`：绑定 1024 以下端口。
`CAP_DAC_READ_SEARCH`：绕过文件读权限检查。
`CAP_SYS_ADMIN`：挂载、网络配置等系统管理。

一个「只想绑定 80 端口的服务」只需 `CAP_NET_BIND_SERVICE`——不需要 root，也不需要其他 39 种能力。

**权能的传递性**：权能是「可携带的凭证」——持有权能的进程可以在其范围内操作，权能可被赋予/撤销/限制（Linux 还有 bounding set、ambient capabilities 等机制精细控制）。

**关键对比**：

| 模型 | 权限形态 | 粒度 |
| --- | --- | --- |
| 超级用户 | 全有或全无 | 粗（root/非root） |
| Linux capabilities | 独立能力位 | 细（几十种） |
| 能力安全（学术） | 不透明令牌 | 最细（对象级） |

**Linux capabilities 让「非 root 也能干特定特权事」成为可能**——这是容器与降权服务的安全基础。<span class="marginnote">capabilities 与 DAC 的区别：<strong>DAC 是「对象上的权限表」（文件属于谁），capability 是「主体持有的令牌」（进程有什么能力）</strong>。capability 跟着进程走、可精细授予、默认拒绝——它更接近「最小特权」的理想形态。Android 的权限、OAuth 的 scope 都是 capability 思想的跨领域孪生。</span>

## 3 公式解析：权能检查

$$
\text{允许操作} \iff \text{cap}(process) \cap \text{required}(\text{操作}) \neq \emptyset
$$

三步拆解这条「权能判定」：

- **第一步，进程的权能集**：$\text{cap}(process)$ 是进程当前持有的能力位集合（如 `{CAP_NET_BIND_SERVICE, CAP_NET_RAW}`）。
- **第二步，操作的要求**：每个特权操作声明「需要哪些能力」——如绑定 1024 以下端口需要 `CAP_NET_BIND_SERVICE`。
- **第三步，交集判定**：进程能力集与操作所需能力有交集才允许——**默认拒绝，除非明确持有**。

## 4 最小特权的落地全景

最小特权在系统各处落地：

- **进程**：服务用非 root 专用账号运行；Linux 上 `setcap` 给特定可执行文件授权特定能力。
- **容器**：Docker 默认**丢弃全部 capabilities**，只按需 `--cap-add` 添加——容器内 root 也缺能力。
- **数据库**：应用账号只给 `SELECT`、`INSERT`、`UPDATE`，不给 `DELETE`、`DROP`。
- **云 IAM**：AWS 策略「Allow 最小集合」、角色而非长期密钥。
- **Web 权限**：OAuth scope 只请求所需权限、Android 只申请所需权限。
- **文件**：按需挂载只读、最小暴露。

**统一逻辑**：「默认拒绝 + 按需授予 + 定期审查」——最小特权是一个**过程**（持续收敛），不是一次性配置。<span class="marginnote">最小特权的「过程观」：<strong>权限会「漂移」——团队为了省事不断加权限，几年后最小特权变成了「最大特权」</strong>。所以它要求「定期审查 + 按需回收」：权限只加不减的系统，最终必然违背最小特权。安全审计的本质，就是「检查权限有没有漂移」。</span>

## 5 最小特权与其他原则

最小特权不是孤立原则，它与其他安全概念互为表里：

**权限分离（separation of duties）**：关键操作拆成多步，不同主体负责不同步——「一个人不能既发起转账又批准转账」。
**纵深防御**：最小特权是其中一层——即使上层（认证、注入防御）被绕过，权限限制仍在兜底。
**默认安全**：最小特权 = 默认拒绝的授权——与 TLS 1.3「默认安全」、SELinux「默认拒绝」同一哲学。
**防御性编程**：程序按最小权限运行，即使有 bug 也难被利用。

**一句话**：最小特权是「授权领域」的默认安全——它不追求「防住一切」，而是「把每个环节的损失降到最低」。<span class="marginnote">把全书串起来：<strong>最小特权与「边界清晰」是安全的两条总纲</strong>——前者管「授权边界」（谁能做什么），后者管「数据-指令边界」（什么算代码）。密码学、系统安全、软件安全的几乎所有实践，都落在这两条总纲之下。</span>

## 6 小结

- **最小特权**：只给完成任务所需的最小权限——减少误操作 + 缩小攻击爆炸半径。
- **权能**：从「全能 root」到「按需能力位」——Linux capabilities 是代表。
- **能力检查**：进程能力集 ∩ 操作所需能力 ≠ 空才允许——默认拒绝。
- **落地**：非 root 服务、容器丢能力、IAM 最小策略、OAuth scope。
- **过程观**：默认拒绝 + 按需授予 + 定期审查——防止权限漂移。
