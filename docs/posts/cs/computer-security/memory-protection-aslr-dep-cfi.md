## 为什么从内存防护开始

上一篇拆解了缓冲区溢出「怎么把数据变成代码」——但现代系统并不会乖乖就范：**操作系统与编译器筑起一道道防护，让「有漏洞」与「能利用」之间隔着巨大的鸿沟**。<span class="marginnote">这是安全里最重要的区分之一：<strong>「有漏洞」不等于「可被利用」</strong>——一个无法被稳定利用的漏洞，威胁等级远低于一个几行代码就能打穿的漏洞。内存防护机制的目标，就是把「可利用」的难度从「几行脚本」抬升到「国家级攻击者的科研项目」。</span>本篇讲三类核心机制——**ASLR、DEP/NX、CFI**——并解释它们为什么会让经典的 shellcode 攻击失效，以及攻击者如何进化出绕过手段。

## 1 攻击者的经典剧本：shellcode 与地址固定

先回顾上一篇的「对手模型」：经典栈溢出攻击要成功，攻击者需要两样东西——**要执行的代码（shellcode）** 与 **shellcode 所在的地址**。

在没有任何防护的旧系统上，这两样都很容易满足：**shellcode** 可以放进缓冲区本身（栈上）；**地址**可以直接写死——因为每个进程每次启动，内存布局都一样，栈地址是「可预测的常量」。于是攻击者把「返回地址 = 固定栈地址」写进 payload，一打一个准。<span class="marginnote">早期漏洞利用的「轻松」就在于<strong>地址固定</strong>：攻击者可以在自己的机器上调试出精确的栈地址，然后把这个地址直接写进攻击载荷——因为目标机器的布局和自己的机器一样。整个利用过程不需要任何「信息泄露」，纯靠猜测即可命中。</span>

**重点：这个剧本有两个关键假设——「代码可执行」与「地址可预测」**。内存防护机制正是逐条打破这两个假设：DEP 打破「代码可执行」，ASLR 打破「地址可预测」，CFI 连「控制流可被劫持」本身都要管。

## 2 DEP/NX：让栈上的数据不能当代码

**DEP（Data Execution Prevention）/ NX（No-eXecute）**：把内存页标记为「不可执行」——数据所在的页（栈、堆）不允许当作指令执行。<span class="marginnote">DEP 是硬件级机制：CPU 的 NX 位（AMD）/ XD 位（Intel）为每个内存页提供「可执行」标记。操作系统把栈、堆、数据段标记为不可执行——<strong>shellcode 就算被成功注入到栈上，CPU 也拒绝执行它</strong>。Windows 自 2004 年 XP SP2 起默认开启，Linux 的 NX 由内核 <code>mmap</code> 保护实现。</span>

**DEP 的效果**：经典「把 shellcode 放栈上执行」的攻击被直接封死——这是 2000 年代中期的一次重大安全转折，让「注入并执行」变成「注入但不让执行」。

**攻击者的绕过**：既然不能执行**新代码**，就复用**系统已有的代码**——**ROP（Return-Oriented Programming，面向返回的编程）**。攻击者不再注入 shellcode，而是在程序已有的库（如 libc）里找到一系列以 `ret` 结尾的指令片段（**gadget**），把它们串成一条「代码链」，让控制流沿着这些 gadget 一路「滑」到攻击者想要的效果。<span class="marginnote">ROP 是 2007 年后漏洞利用的主流技术：<strong>它不注入任何新代码，只操纵返回地址栈，让已有的指令序列被「借」来执行</strong>——完美绕过了「数据不可执行」的限制。Ropchain 的长度可以很长，功能足以拼出任意系统调用（调用 <code>execve</code> 起 shell）。DEP 由此从「绝对防御」降级为「迫使攻击者更麻烦」。</span>

## 3 公式解析：ASLR 打破地址可预测

**ASLR（Address Space Layout Randomization，地址空间布局随机化）**：每次进程启动，把**栈、堆、共享库、可执行映像的基址随机化**到不同位置——攻击者无法再写死地址。

$$
\text{栈地址} = \text{随机基址} + \text{偏移}
$$

- **随机基址**：进程每次启动时由内核从一个随机源生成，Linux 的栈随机化熵通常在 20–30 位级别。
- **偏移**：同一进程内相对位置是确定的（局部变量相对栈顶的偏移不变），但**绝对地址**因随机基址而每次不同。
- **效果**：攻击者把「返回地址 = 固定栈地址」写进 payload，命中概率从「几乎必中」跌到「$2^{-20}$ 量级」——暴力尝试成功的期望次数是百万级，几乎不可行。

**为什么 ROP 也难了**：ROP 需要知道 libc 的地址（才能指向 gadget），而 ASLR 让 libc 基址每次随机——攻击者必须**先泄露一个地址**才能推算其余，这正是「信息泄露 + 利用」两步走的由来。<span class="marginnote">「<strong>先泄露、再利用</strong>」是 2010 年代漏洞利用的标准流程：先找一个能读出内存内容的漏洞（如越界读、格式化串），泄露出 libc 或栈的某个真实地址，从而<strong>推算 ASLR 的随机化</strong>，再精确构造攻击。这就是为什么浏览器、内核的漏洞报告里「信息泄露漏洞」常常与「任意代码执行」成对出现——前者是为后者「开路的」。</span>

## 4 栈保护（canary）与编译期防护

在 DEP/ASLR 之外，编译器还提供一层「先手防御」——**栈保护（stack canary）**：

**Canary**：在函数的局部变量与返回地址之间插入一个**随机哨兵值（canary）**。函数返回前先检查 canary 是否被覆盖——如果被覆盖（说明发生了溢出），立即终止程序而非跳到攻击者代码。<span class="marginnote">Canary 的名字来自煤矿里的「金丝雀」——矿工用金丝雀检测有毒气体，金丝雀死了人就撤。这里 canary 被篡改 = 缓冲区发生了越界写 = 程序「有毒」，立即中止。GCC 的 <code>-fstack-protector</code>、MSVC 的 <code>/GS</code> 都自动插入 canary，对「覆盖返回地址」的经典攻击几乎零成本免疫。</span>

**为什么 canary 防不住所有溢出**：它只能检测「从缓冲区**向下/向上**连续覆盖到 canary 的写」——如果溢出不经过 canary（如堆溢出、格式化串直接改写返回地址）、或攻击者先用越界读**泄露 canary 值**再原样写回（保持 canary 不变），canary 就形同虚设。<span class="marginnote">canary 与 ASLR/DEP 的对抗组合，是「<strong>每一道防护都改变攻击的面貌</strong>」的又一例证：canary 挡「盲目的连续覆盖」，逼攻击者先读后写；而读的能力来自另一个漏洞——于是「一个漏洞不够，要一串漏洞」成为现代利用的现实。</span>

## 5 CFI：连控制流本身都要验证

前面几道防护都围绕「地址」与「可执行」，但攻击者仍有最后一张牌：**哪怕不能注入新代码，只要能把控制流**劫持**到已有代码的任意位置，就可能造成危害**。**CFI（Control-Flow Integrity，控制流完整性）** 直接对这个问题下手：

**CFI 的思想**：程序的控制流是「有规矩」的——函数调用只能跳到函数入口、`ret` 只能回到调用点。**CFI 在编译期标注所有「合法的转移目标」，运行时校验每次跳转是否合法**——不合法的跳转（被劫持的控制流）立即终止。<span class="marginnote">CFI 分「粗粒度」与「细粒度」：<strong>粗粒度 CFI</strong> 只校验「跳转目标在合法集合内」（代价小但可被 ROP 利用同一集合内的 gadget）；<strong>细粒度 CFI</strong> 精确到「每个调用点只能跳到一个确定的合法目标」（防御性强但开销大）。Intel CET（Control-flow Enforcement Technology）在硬件层面实现了 <code>shadow stack</code> 与 IBT，2020 年后逐步进入主流 CPU。</span>

**重点：防护的完整光谱**——canary 防「覆盖返回地址」、DEP 防「执行注入代码」、ASLR 防「预测地址」、CFI 防「劫持控制流」。**四者叠加，才构成现代内存防护的完整纵深**：单独任何一道都能被绕过，合起来让利用成本指数级上升。

## 6 防护机制的协同与局限

四道防护不是孤立存在的，它们互相配合，也各有代价：

**协同**：ASLR 让 ROP 需要地址泄露；CFI 让「即便泄露了地址、劫持了控制流」也难以下手；canary 在返回地址层面做第一道哨兵——**每一道防护都把攻击者的「信息收集」与「控制流操作」成本推高一步**。<span class="marginnote">现代攻击几乎都是「<strong>漏洞链（exploit chain）</strong>」：一个越界读泄露地址（破 ASLR）+ 一个越界写劫持控制流（破 canary/CFI）+ 一个 ROP 链完成执行。单漏洞「一把梭」的时代已经过去——这也是为什么漏洞奖励计划里「可利用性」与「需要几步」直接决定赏金高低。</span>

**代价与局限**：ASLR 需要地址空间布局支持（32 位下熵不足、部分系统关闭）；CFI 有性能开销；canary 有被泄露的风险。且所有机制都是**「概率性/机制性」而非「数学性」**的防御——它们把「几乎必中」变成「非常难」，但没有消除漏洞本身。

## 7 公式解析：为什么 ROP 需要精确地址

ROP 之所以在 ASLR 之后仍能存活，靠的是「一个泄露的地址推算出全部布局」。用公式理解这一推算：

$$
\text{libc\_base} = \text{leaked\_addr} - \text{offset}
$$

- **leaked_addr**：攻击者通过漏洞读出的某个真实地址（如某个函数地址）。
- **offset**：该函数在 libc 内的固定偏移——**库文件在编译时就固定了内部的相对偏移**，攻击者从自己的 libc 副本就能查到。
- **libc_base**：一旦算出基址，攻击者就能推出 libc 里**任意 gadget 的绝对地址**——整个 ROP 链的位置全部确定。

**重点：ASLR 的安全性依赖于「随机基址不被泄露」**——一旦有任何渠道泄露一个地址，随机化就被这一条减法公式**逆转**。这解释了安全界为什么反复强调「信息泄露漏洞也要当高危对待」——它是把「随机化防御」重新变回「可预测」的那把钥匙。

## 8 防护与绕过的时间线：一次攻防演化史

把各机制按时间排开，能看到一条清晰的「攻防升级」主线：

**1990s**：无防护时代——固定地址、栈可执行，攻击者一把梭。**2004**：Windows XP SP2 默认开启 DEP/NX——注入 shellcode 失效，ROP 登场。**2007**：主流系统开启 ASLR——地址预测失效，「先泄露再利用」成为标配。<span class="marginnote">注意 ASLR 与 DEP 的「<strong>接力</strong>」：DEP 先落地，攻击者转向 ROP；ROP 需要地址，ASLR 再补上「地址随机化」——<strong>每一步攻击者进化都催生新的防御</strong>。这就是为什么安全永远在「升级-绕过-再升级」的循环里，而不是一劳永逸。</span>

**2010s**：CFI 研究成熟、CET 等硬件方案提出；攻击者转向「信息泄露 + 堆利用 + 漏洞链」的组合拳。**2020s**：内存安全语言（Rust）大范围落地、CHERI 等能力硬件原型、影子栈（shadow stack）进 CPU——防线的重心从「给 C 语言打补丁」转向「换一种更安全的内存模型」。

**重点：内存防护的历史，就是「攻击者与防御者共同把软件安全推向更高标准」的历史**——每一个曾「够用」的机制，都在下一代攻击面前暴露局限。这也解释了为什么「彻底的内存安全」最终要靠「语言/架构层面」解决，而不是「在 C 语言上打补丁」。

## 9 工程实操：检查你的防护是否开启

防护机制写了文章里不算数，要「真的开着」才算数。工程上三个快速检查点：

**检查可执行文件**：Linux 用 `checksec` 或 `readelf` 看二进制的防护属性——`NX`（栈不可执行）、`RELRO`（重定位表只读，防 GOT 覆写）、`PIE`（位置无关可执行，ASLR 生效的前提）、`canary`（栈保护）。**检查系统级**：`sysctl kernel.randomize_va_space`（Linux ASLR 开关，2 为全开）、Windows 的「强制地址空间布局随机化」组策略。<span class="marginnote"><strong>RELRO/GOT 覆写</strong>是绕开栈保护的另一条路：动态链接的跳转表（GOT）若可写，攻击者改写函数指针即可劫持调用，不碰返回地址——所以现代加固把 GOT 设为只读（Full RELRO）。检查防护是否齐全，要看的远比「有没有 ASLR」多。</span>

**辨析｜易错点：** **PIE 与 ASLR 是两个东西**——PIE 决定「可执行映像本身能否被随机化」，ASLR 决定「地址空间是否随机」。Linux 上只开 ASLR 不开 PIE，主程序基址仍是固定的，攻击者只需绕过库的随机化。**「开了 ASLR 就安全」是常见误区**——要「PIE + ASLR + NX + canary + Full RELRO」全部到位，才是完整的内存防护基线。

## 10 小结

- **对手模型**：经典攻击需要「可执行的 shellcode + 可预测的地址」——防护机制逐条打破这两点。
- **DEP/NX**：数据页不可执行，封死「栈上放 shellcode」；攻击者用 ROP 复用已有代码绕过。
- **ASLR**：栈/堆/库基址每次随机，写死地址失效；攻击者需「先泄露再利用」两步走。
- **Canary**：返回地址前的随机哨兵，溢出覆盖即终止；但可被泄露绕过。
- **CFI**：校验跳转目标合法性，连控制流劫持都要管；Intel CET 提供硬件级实现。
- **纵深哲学**：单道防护可绕过，四者叠加让利用成本指数级上升——「有漏洞」与「可利用」之间被拉开巨大鸿沟。
- **漏洞链是常态**：越界读（破 ASLR）+ 越界写（破 canary/CFI）+ ROP 链，现代利用几乎都是多步组合。
- **ASLR 的关键假设**：随机基址不被泄露——一个地址泄露即可用 `base = leaked − offset` 逆转随机化。
- **攻防时间线**：无防护→DEP→ASLR→CFI/CET→内存安全语言，每步防御都催生更高级的绕过——「彻底安全」最终要靠语言/架构层面。
- **防护是概率性/机制性**而非数学性：把「几乎必中」降为「非常难」，但漏洞本身仍在——修复漏洞仍是最根本的防线。
- **工程基线是「全都要」**：PIE + ASLR + NX + canary + Full RELRO 齐备才算完整；PIE ≠ ASLR，「开了 ASLR 就安全」是常见误区。

在下一节，我们从「程序层面」上升到「系统层面」——**操作系统安全加固**：前面的防护是「代码怎么防」，加固是「整个系统怎么配置、怎么补丁、怎么最小化」。
