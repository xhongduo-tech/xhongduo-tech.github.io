## 为什么从数据库与云安全开始

前面几篇防的是「系统被攻破」，但攻击者真正想要的是**数据**——而数据绝大多数存在**数据库**里，如今越来越多地放在**云端**。数据库与云是数据安全的「最后堡垒」：攻击者绕过了认证、突破了加固，最终目的是把数据库里的客户信息、交易记录、训练数据搬走。<span class="marginnote">Stallings 第5章把数据库安全与云安全放在一起讲，因为它们共享同一逻辑：<strong>数据在哪里，安全就要守到哪里</strong>——数据库是「数据的家」，云端是「越来越多数据的家」。理解数据库与云的安全，是理解「数据真正值钱在哪」的关键。</span>本篇建立四件事：数据库特有的安全威胁、数据库访问控制与加密、SQL 注入、以及云安全的责任共担模型。

## 1 数据库安全：与传统安全的不同

数据库安全有其特殊性，不能照搬「文件安全」的思路：

**细粒度访问控制**：数据库的客体是**行、列、单元格**，而非整个文件——「员工张三可看本部门的工资列，但看不到全公司」需要行级/列级授权。**数据完整性**：除了防篡改，还要保证**语义完整性**——约束（外键、唯一性、CHECK）防止「逻辑上不可能」的数据。

**推理攻击（inference）**：数据库安全特有的威胁——攻击者不直接读敏感数据，而是通过**聚合与统计查询**推理出单个记录的信息。<span class="marginnote"><strong>推理攻击</strong>是数据库独有的：比如「平均工资」查询本身不泄露个人数据，但若「部门中只有一个人的工资明显偏高/偏低」，或多次查询取交集，就能反推出那个人的精确工资。统计数据库的防护手段是「禁止过小粒度的查询」「结果加入随机扰动」——这是在「可用性」与「隐私」之间做权衡。</span>

**聚合攻击（aggregation）**：多个低敏感数据聚合后反而敏感——单独看「客户 A 的订单」不敏感，汇总「所有客户的购买记录」就是商业机密。

## 2 数据库的访问控制与加密

数据库访问控制的实现，延续访问控制篇的概念但更细：

**基于角色的权限**：数据库用角色管理权限（DBA、开发、只读用户），与 RBAC 一脉相承。**行级安全（row-level security）**：按用户属性（部门、地区）自动过滤可见行——实现「同一张表，不同人看到不同数据」。<span class="marginnote"><strong>行级安全</strong>是现代数据库（PostgreSQL RLS、Oracle VPD、SQL Server 行级权限）的杀手锏：策略写在数据库里，应用层不用操心「谁该看到哪行」——权限判断从「应用代码」下沉到「数据库引擎」，更可靠、更统一。</span>

**数据库加密**：**透明数据加密（TDE）**——数据库自动对落盘的数据库文件加密，应用无需改动，防「直接偷数据库文件」的攻击；**字段级加密**——对敏感列（身份证、银行卡）单独加密，即使整个库被拖走，关键字段仍不可读。<span class="marginnote">TDE 防的是「<strong>物理偷库</strong>」：攻击者绕过一切访问控制，直接把数据库文件拷贝走。TDE 在存储层加密，文件拿走了也读不出内容。但要注意：<strong>TDE 不防「通过应用正常查询偷数据」</strong>——所以它要与访问控制、审计配合，而不是替代它们。</span>

**审计**：记录谁在何时对哪些数据做了什么操作——数据泄露后的溯源（谁查过这张表）靠它。

## 3 公式解析：SQL 注入——数据库的头号威胁

**SQL 注入（SQL injection）**：攻击者把恶意 SQL 拼进应用查询，让数据库执行非预期的命令。它是 Web 应用的头号数据库威胁。原理是**「用户输入被当作 SQL 代码执行」**：

$$
\text{查询} = \text{SELECT * FROM users WHERE name = '} + \underbrace{\text{用户输入}}_{\text{被拼接进 SQL}} + \text{'}
$$

攻击者把输入设为 `' OR '1'='1`，拼出的完整查询变成：

$$
\text{SELECT * FROM users WHERE name = '' OR '1'='1'}
$$

- **用户的 `'`**：闭合了字符串的引号，让后续内容不再是「字符串值」而是「SQL 语法」。
- **`OR '1'='1'`**：一个恒真的条件——于是整张表被查出，登录验证被绕过。
- **本质**：**输入与代码没有区分**——用户输入被「拼接」成了程序代码的一部分。

**为什么危险**：SQL 注入可以绕过认证（如上）、读取任意数据（`UNION SELECT` 拼出其他表的查询）、篡改数据、甚至**执行存储过程/系统命令**（如 `xp_cmdshell`）。<span class="marginnote"><strong>防御的根本是「参数化查询（prepared statement）」</strong>：SQL 的结构与参数分开传递，用户输入永远作为「数据」而非「代码」被处理——数据库引擎知道「这里是值，不是语法」，注入自然失效。这是 SQL 注入最彻底、最标准的解法；输入校验（白名单）是第二道防线。凡是用字符串拼接 SQL 的代码，都是注入的候选——这也是代码审计的高优先级检查点。</span>

## 4 云安全：责任共担模型

云改变了安全的边界——物理安全、主机安全、数据安全，谁负责？答案是**责任共担模型（shared responsibility model）**：

**云服务商（CSP）负责「云的安全」（security of the cloud）**：物理数据中心、硬件、虚拟化层、基础网络。**客户负责「云中的安全」（security in the cloud）**：自己的数据、应用、账户、访问策略、虚拟机配置。<span class="marginnote"><strong>责任共担的分界线取决于服务模式</strong>：IaaS（虚拟机）客户负责从操作系统往上的一切；PaaS（平台）客户负责应用与数据；SaaS（软件）客户基本只负责数据与配置。<strong>最常见的云安全事故，恰恰是「客户误以为云厂商什么都管了」</strong>——比如「桶权限设成公开」「云数据库没设密码」，这不是云的锅，是客户的责任区没守住。</span>

**云的三种服务模式与责任划分**：

| 模式 | 客户负责 | 云商负责 |
| --- | --- | --- |
| IaaS（VM） | OS、应用、数据、访问策略 | 物理、虚拟化、网络 |
| PaaS（平台） | 应用、数据、配置 | + 运行环境、中间件 |
| SaaS（软件） | 数据、用户配置 | + 应用本身、平台 |

## 5 云安全的核心威胁与防护

云的常见安全威胁与应对：

**错误配置**：存储桶公开可读、安全组放行过宽、数据库公网暴露——**云上第一大事故源**。<span class="marginnote">「<strong>云上最大的敌人是误配置</strong>」几乎成了安全界的共识：AWS S3 桶设为公开、安全组 <code>0.0.0.0/0</code> 全放行、云数据库绑定公网——这类「一个开关设错」的事故造成了大量知名数据泄露。防护靠「<strong>配置审查 + 扫描工具</strong>」（如 AWS Config、CloudSploit）与「默认私有」的架构习惯。</span>

**身份与访问管理（IAM）**：云的权限管理核心——最小权限、角色分离、密钥管理（Access Key 泄露是云攻破的常见入口）。**多租户隔离**：虚拟化层的隔离漏洞（如 CPU 侧信道 Meltdown/Spectre 曾跨越租户边界）。**数据加密**：存储加密（KMS 托管密钥）+ 传输加密（TLS）+ 密钥管理。

**供应链与 API**：云 API 的攻击面、第三方服务的信任——「最薄弱的环节往往在依赖链上」。

## 6 数据库攻击的其他形态：命令注入与越权

SQL 注入之外，数据库攻击还有几个高频形态，值得一并看清：

**命令注入（OS command injection）**：用户输入被拼进系统命令（`system()`/`exec()`），执行任意命令——与 SQL 注入同源的「输入当代码」问题，只是拼接目标从 SQL 变成了 shell。防御同样靠「参数化 + 白名单」：**绝不把用户输入直接拼进 shell 命令**。

**越权访问（IDOR/水平越权）**：攻击者直接修改请求里的资源 ID（如 `order/1234` → `order/1235`）访问他人数据——**这是数据库层面的授权漏洞**：查询执行了，但没有校验「这个用户有权看这条记录」。防御靠服务端校验对象归属，而非信任 URL 参数。<span class="marginnote"><strong>水平越权（访问同级用户的数据）与垂直越权（访问管理员功能）</strong>是 Web 应用漏洞清单里的常客。它们的共同根因是「<strong>只验了身份，没验权限</strong>」——登录了不代表能访问每一条记录。行级安全（第2节）在数据库层从源头防止这种越权：策略是「只能看到属于自己部门/自己的行」，应用层再粗心也越不过去。</span>

**数据备份与恢复安全**：备份是攻击者的「第二目标」——若备份未加密、未受访问控制保护，攻击者直接偷走备份就等于偷走整个库。备份也要**加密存储 + 最小权限访问 + 定期恢复演练**。

## 7 云安全的落地：从配置到治理

把云安全从「概念」落到「行动」，几个关键实践：

**云安全姿态管理（CSPM）**：自动扫描云配置、发现「公开桶/过宽权限/未加密存储」等风险——把「误配置」变成「可自动发现的告警」。**云工作负载保护（CWPP）**：对云里的服务器/容器做加固、漏洞扫描、运行时防护。**云访问安全代理（CASB）**：夹在用户与云服务之间的安全网关——监控数据外传、防泄露（DLP）。<span class="marginnote">云安全的产品矩阵（CSPM/CWPP/CASB）本质上对应本专题的既有概念：<strong>CSPM ≈ 配置加固 + 风险评估，CWPP ≈ 系统加固 + 恶意软件防护，CASB ≈ 边界防护 + 数据防泄露</strong>——云的复杂性只是让「同样的安全逻辑」以新工具形态出现。理解底层原理，新工具上手就不难。</span>

**多云与合规**：企业往往用多家云（AWS/Azure/阿里云）——统一的安全基线、统一的密钥管理、跨云的可视化，成为治理的关键。**云上的数据主权**：数据存储位置涉及法规（GDPR、数据本地化要求）——「数据在哪」本身就是合规问题（见《隐私保护与数据合规》一篇）。

## 8 数据库审计与合规

数据库保存着最敏感的数据，因此也是合规监管（见《安全法规、伦理与责任》一篇）的核心对象：

**数据库审计（database auditing）**：记录并审查「谁对什么数据做了什么」——登录、查询、导出、权限变更都要留痕。**审计的两种方式**：数据库内置审计（记录到日志）与**数据库防火墙/代理审计**（在应用与数据库之间拦截记录）。<span class="marginnote">审计与加密是「一体两面」：<strong>加密保证「读不懂」，审计保证「读得明白是谁读的」</strong>——加密防外部偷，审计防内部滥用与追责。合规框架（GDPR、PCI-DSS、等级保护）几乎都要求「敏感数据的访问可审计」——「能证明你没碰过」与「你确实没碰过」同样重要。</span>

**数据库安全与威胁建模的联系**：回到《攻击面与威胁建模》——数据库是绝大多数系统里「价值最高、最怕被碰」的资产，理应是威胁建模里优先级最高的客体。**把数据库当「皇冠上的宝石」来保护**——外层是网络防护、中间是访问控制与注入防护、核心是加密与审计，这就是数据库安全的纵深。

## 9 小结

- **数据库安全的特殊性**：细粒度（行/列级）授权、语义完整性、**推理/聚合攻击**——不是文件安全的照搬。
- **数据库防护**：基于角色的权限 + 行级安全 + **TDE/字段加密** + 审计；TDE 防「偷库」，不防「合法查询偷数据」。
- **SQL 注入** = 用户输入被拼成 SQL 代码执行；防御的根本是**参数化查询**（输入当数据不当代码）。
- **云的责任共担**：云商管「云的安全」，客户管「云中的安全」；分界线随 IaaS/PaaS/SaaS 移动。
- **云第一大事故源是错误配置**：公开桶、过宽安全组、公网数据库——配置审查 + 默认私有是关键。
- **云安全核心**：IAM 最小权限、多租户隔离、KMS 加密、供应链与 API 防护。
- **命令注入**与 SQL 注入同源（输入当代码）；**越权访问**是「只验身份没验权限」；行级安全从数据库层根治越权。
- **云安全工具**：CSPM（配置扫描）、CWPP（工作负载保护）、CASB（数据网关）——本质仍是加固/检测/防泄露的逻辑。
- **数据在哪，安全就要守到哪**：数据库是数据的家、云端是越来越多的家——本专题的访问控制/加密/加固，全部要延伸到数据层。
- **备份也要安全**：备份是攻击者的第二目标，需加密存储 + 最小权限访问 + 定期恢复演练。
- **数据主权与合规**：数据存储位置本身就是合规问题（GDPR、本地化），与《隐私保护与数据合规》一篇衔接。
- **数据库审计与合规**：加密防「读不懂」，审计防「读了没人知道」；合规框架普遍要求敏感数据访问可审计。

在下一节，我们从「数据安全」转向「服务的可用性被攻击」——**拒绝服务攻击与防护**：数据库与云是攻击者的「猎物」，而 DoS 是让猎物「从所有人眼前消失」的攻击。
