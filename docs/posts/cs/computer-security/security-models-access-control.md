## 为什么从访问控制开始

前两篇回答了「安全要什么」「威胁从哪进」，但还缺一环：**进了系统之后，能做什么？** 即使攻击者突破了网络边界，如果访问控制得当，他仍无法接触高价值资产。**访问控制（access control）** 就是回答「谁对什么能做什么」的机制——它是攻击面之后、数据安全之前的第二道闸门。<span class="marginnote">访问控制与认证的分工：<strong>认证（authentication）回答「你是谁」，访问控制（authorization）回答「你能做什么」</strong>。上一篇《认证》讲了入口，本篇讲入口之后的权限。Stallings 第4章把访问控制称为「安全体系的核心机制」，因为它把「抽象的 CIA」落到「具体的能/不能」。</span>本篇建立四件事：访问控制的基本模型、三种主流策略（DAC/MAC/RBAC）、正式安全模型，以及它们在现实系统里的样子。

## 1 访问控制的基本要素

访问控制的三要素，构成它的语法基础：

**主体（subject）**：发起访问的实体——用户、进程、服务。**客体（object）**：被访问的资源——文件、数据库记录、设备、内存区域。**访问操作（access operation）**：主体对客体可以执行的动作——读、写、执行、删除、创建。<span class="marginnote">一个反直觉但重要的点：<strong>进程（process）既是主体也是客体</strong>——它作为「发起访问者」是主体，作为「可被杀、可被挂起」的资源又是客体。主体与客体的角色随上下文切换，这是设计访问控制时容易忽略的细节。</span>

**访问控制的三步**：**识别（identification）**——声明身份；**认证（authentication）**——验证身份；**授权（authorization）**——决定权限并执行。前两步是认证篇的内容，本篇聚焦第三步。

## 2 访问控制的实现：访问矩阵

访问控制策略的经典表达是**访问控制矩阵（access control matrix）**——行是主体、列是客体、格子是「主体对客体允许的操作」：

|  | 文件 A | 文件 B | 打印机 | 数据库 |
| --- | --- | --- | --- | --- |
| Alice | 读/写 | 读 | 打印 | 读 |
| Bob | 读 | 读/写 | — | 写 |
| 进程 P | 读 | — | — | — |

**重点：矩阵是「理论模型」，实际实现要压缩它——因为矩阵太稀疏、太大，无法直接存储。** 由此产生两种经典的物理表示：

**访问控制表（ACL, Access Control List）**：按**客体**组织——每个客体列出「哪些主体可对其做什么」。对应矩阵的「列」。**能力表（capability list）**：按**主体**组织——每个主体列出「可访问哪些客体」。对应矩阵的「行」。<span class="marginnote"><strong>ACL 与能力表的差别是「查询视角」的差别</strong>：ACL 便于「查某文件谁能访问」（面向管理），能力表便于「查某用户能访问什么」（面向执行）。Unix 文件权限、Windows 的 NTFS 权限是 ACL 的典型；而「能力令牌」「凭据票据」是能力表的现代化身。两种组织方式也带来不同的权限撤销难度——ACL 撤销某用户的权限只需改一个条目，能力表却要找到并作废所有相关能力。</span>

## 3 自主访问控制（DAC）

**自主访问控制（DAC, Discretionary Access Control）**：资源的**所有者**有权自行决定谁能访问、给什么权限——「自主」即「所有权说了算」。

典型实现：Unix 的 rwx 权限、Windows 文件属性、数据库的对象级权限。<span class="marginnote">Unix 的经典三位权限 <code>rwx</code> 分属 owner / group / others——所有者可用 <code>chmod</code> 自行授权。Windows 的 NTFS 权限更细（可指定用户/组、可继承、可设多个权限项），但本质都是「所有者授予」的 DAC。</span>

**DAC 的弱点**：权限由用户自主决定，可能被滥用（所有者把敏感文件共享给不该看的人）；且**不能防止「木马问题」**——用户运行一个恶意程序，程序继承用户权限，就能访问用户能访问的一切，而用户不知情。<span class="marginnote">「<strong>木马继承用户权限</strong>」是 DAC 的结构性缺陷：你运行了一个带病毒的文档宏，病毒就以你的权限行动——读你的文件、删你的数据，而你毫无察觉。因为访问控制的判定依据是「进程以谁的身份运行」，而运行恶意程序的你「自愿」给了它这个身份。这正是 MAC 与最小权限要解决的问题。</span>

## 4 强制访问控制（MAC）

**强制访问控制（MAC, Mandatory Access Control）**：由**系统强制**执行的安全策略，主体与客体都有**安全标签**（如密级），访问由系统按既定规则裁决，**不由所有者或用户决定**。

典型实现：**多级安全（multilevel security）**——主体有安全许可（clearance），客体有安全等级（classification），如「机密 / 秘密 / 公开」。系统依据标签关系决定读、写权限。<span class="marginnote">MAC 的最典型场景是军事与政府系统：一份「机密」文件，只有「机密」级以上许可的人才能读；这种决策不能由普通用户或文件所有者自定，必须由系统按标签强制裁决——这就是「强制」的含义。Linux 的 SELinux、AppArmor 把 MAC 概念带进了通用操作系统。</span>

**MAC 与 DAC 的根本差别**：DAC 是「所有权自主」，MAC 是「标签强制」。MAC 能防木马——因为恶意程序继承用户标签后，仍受标签规则的约束，不能读到标签之上的数据。<span class="marginnote">一句话记忆：<strong>DAC 问「谁拥有它」，MAC 问「它被标成什么密级」</strong>。DAC 灵活但松，MAC 严格但僵——现实系统（如 Android 应用沙箱、容器安全）常两者并用：DAC 管日常，MAC 管高价值边界。</span>

## 5 基于角色的访问控制（RBAC）与 ABAC

大型组织里，按「人」给权限难以管理，于是有了按「角色」给权限的思路：

**RBAC（基于角色的访问控制）**：权限授予**角色**而非个人，用户通过「担任角色」获得权限——一个用户可以是「财务专员」，另一个是「审计员」，角色的权限集合由管理员统一配置。<span class="marginnote">RBAC 的管理学价值：<strong>把「给用户授权」变成「给角色配置」</strong>——新员工入职，只需分配角色，不必逐项配权限；员工离职，撤销角色即可。角色数量远小于用户数量，权限管理从「每个用户」降到「每类角色」，这是 RBAC 在大企业普遍采用的原因。</span>

**RBAC 的模型**：**用户-角色关联**、**角色-权限关联**、**角色层级**（高角色继承低角色权限）、**约束**（职责分离——同一角色不能同时拥有「发起」与「审批」权限，防舞弊）。<span class="marginnote"><strong>职责分离（SoD, Separation of Duties）</strong>是 RBAC 里的治理关键：比如「提交报销」与「审批报销」必须是不同角色——一个人若同时拥有两者，就能自己给自己批钱。SoD 把「最小权限」升级成「互相制衡」，是防内部舞弊的第一机制。</span>

**ABAC（基于属性的访问控制）**：权限依据**属性**动态判定——主体属性（部门、职位）、客体属性（敏感度）、环境属性（时间、地点、设备）。ABAC 比 RBAC 更灵活，能表达「财务部员工在办公时间可查看财务报表」这类细粒度规则，是现代云平台（AWS IAM、零信任）的主流。

## 6 公式解析：Bell–LaPadula 安全模型

正式安全模型把访问控制数学化，最经典的是 **Bell–LaPadula（BLP）模型**——它是 MAC 多级安全的形式化，核心目标：**防止机密信息从高密级流向低密级**（防泄露）。

设主体 $S$ 的密级为 $\text{sl}(S)$，客体 $O$ 的密级为 $\text{sl}(O)$，BLP 的两条性质：

$$
\text{不向上读（No read up）: } S \text{ 可读 } O \iff \text{sl}(S) \ge \text{sl}(O)
$$

$$
\text{不向下写（No write down）: } S \text{ 可写 } O \iff \text{sl}(S) \le \text{sl}(O)
$$

- **$\text{sl}(S) \ge \text{sl}(O)$ 才能读**：密级高的人可以读同级或更低密级——「机密」用户可以读「秘密」「公开」文件，但不能读「绝密」。
- **$\text{sl}(S) \le \text{sl}(O)$ 才能写**：密级低的人不能向更低密级写——防止高密级信息被「写进」低密级文件而泄露。
- **两条性质合起来的直觉**：信息只能向上流（从低密级写到高密级、从高密级读到……等等）——整体约束是**信息不许向下流**，从而保证「低密级的人永远拿不到高密级的信息」。

**重点：BLP 是「防泄露」模型，但它不管完整性。** 其孪生模型 **Biba** 正好相反——目标是防篡改，规则是「不向上写、不向下读」：高完整性主体不能读低完整性数据（避免被低质量数据污染）。**BLP 护机密，Biba 护完整**——一个完整的安全系统往往需要两者的权衡。Stallings 第4章强调：理解这些正式模型，是理解「为什么访问控制要这样设计」的理论基础。

## 7 访问控制在现实系统里的样子

理论模型最终要在具体系统落地，几个代表性实现值得对照：

| 系统 | 机制 | 类型 | 特点 |
| --- | --- | --- | --- |
| Unix/Linux | `rwx` + `chmod` | DAC | 简单经典，三位权限 |
| Windows NTFS | ACL + 继承 | DAC+ | 权限可继承、可枚举 |
| Linux SELinux | 标签 + 策略 | MAC | 强制、粒度细、难配置 |
| Android | 应用沙箱 + 权限声明 | MAC+ | 每个应用独立 UID |
| 数据库 | 对象权限 + 角色 | DAC/RBAC | 行级、列级权限 |

**重点：现实中几乎都是「混合模式」**——用 RBAC 管用户角色、用 ACL 管文件、用 MAC 管高价值边界、用 ABAC 管动态策略。理解各模型的定位，才能理解为什么一个系统会「同时有好几套访问控制」。

**辨析｜易错点：** 「装了访问控制 = 安全」是常见误区。访问控制的强度取决于**判定依据的可靠性**——如果认证脆弱（弱口令），再严的授权也被绕过（用别人的身份进入）；如果授权逻辑有漏洞（越权，如 IDOR——直接改 URL 里的资源 ID），访问控制形同虚设。**访问控制的价值上限，由认证质量与授权实现的正确性共同决定**。

## 8 访问控制与威胁建模、最小权限的联系

把访问控制放回本专题的脉络里看，它的位置十分清晰：

**承接威胁建模**：威胁建模产出的「资产与入口清单」，正是访问控制要保护的客体与要限制的入口——「谁对什么能做什么」的每个决策，都来自「这个资产怕什么、这个入口该怎么守」的威胁分析。<span class="marginnote">访问控制是威胁建模的「<strong>落地执行者</strong>」：威胁建模说「数据库怕被越权读取」，访问控制就用「数据库只对授权角色开放 + 参数校验防 IDOR」来执行这个决策。没有访问控制，威胁模型只是一纸空谈。</span>

**落实最小权限**：上一篇概述里的「最小权限」原则，在访问控制里得到最直接的实现——每个主体只获得完成任务所需的最小权限。RBAC 的角色划分、ABAC 的属性判定，本质上都是在「精确地实现最小权限」。

**延伸**：访问控制还牵动「审计」——谁能访问、何时访问、访问了什么，是审计（第4篇《风险评估与审计》）的基础输入。**可问责性依赖访问记录，访问记录来自访问控制。**

## 9 小结

- **访问控制三要素**：主体、客体、访问操作；三步流程：识别→认证→授权。
- **访问矩阵**是理论模型，物理实现分两种：**ACL**（按客体列「谁能访问」）与**能力表**（按主体列「能访问什么」）。
- **DAC**：所有权自主授权，灵活但防不了木马继承权限；**MAC**：标签强制，严格但僵。
- **RBAC**：权限授予角色、用户担任角色，便于规模化与职责分离；**ABAC** 按属性动态判定，更灵活。
- **Bell–LaPadula**：不向上读、不向下写，防机密泄露；**Biba** 不向上写、不向下读，防完整性破坏。
- **正式模型是「为什么这样设计」的理论**——理解模型，才理解现实访问控制的内在逻辑。
- **现实是混合模式**：RBAC 管角色、ACL 管文件、MAC 管边界、ABAC 管动态；访问控制强度上限由认证质量与授权正确性决定。
- **访问控制是威胁建模的落地执行者**，也是最直接的「最小权限」实现；访问记录为审计提供输入。

在下一节，我们进入安全的「入口防线」——**身份认证机制：口令、生物识别与 MFA**：访问控制假定「主体已被认证」，而认证正是回答「你到底是谁」的第一步。
