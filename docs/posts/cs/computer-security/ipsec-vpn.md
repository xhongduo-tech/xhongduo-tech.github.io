## 为什么从 IPsec 开始

TLS 一篇解决了「一个连接怎么安全」，但它有个局限：**TLS 只能保护单个应用连接，且需要应用主动启用**。当你要保护的是「两个网络之间的全部流量」（总部与分支互连、远程员工访问内网），逐应用套 TLS 既不现实也不彻底——这正是 **IPsec** 登场的场景。<span class="marginnote">IPsec 与 TLS 的分工是<strong>「保护连接 vs 保护网络」</strong>：TLS 在传输层之上、逐应用启用；IPsec 在网络层、对上层应用完全透明——应用无需任何改动，所有 TCP/UDP 流量自动被保护。这个「透明性」正是 IPsec 用于 VPN 的根本优势。</span>本篇建立三件事：IPsec 要解决什么、它的两大协议（AH/ESP）与两种模式、以及它如何支撑 VPN。

## 1 IPsec 的设计动机与两个核心问题

IP 协议本身没有任何安全机制——数据包在网络上裸奔，任何人都能窃听、篡改、伪造。**IPsec（IP Security）** 在网络层为 IP 包提供安全服务，回答两个核心问题：

**问题一：这个包的内容机密吗？**（加密——防窃听）**问题二：这个包真的是发送方发的、且没被篡改吗？**（认证与完整性——防伪造防篡改）<span class="marginnote">IPsec 的核心价值在于「<strong>透明地保护所有 IP 流量</strong>」：无论上层跑的是 HTTP、数据库协议还是自定义应用，IPsec 在网络层统一加密与认证——应用无需感知。对「保护整段网络」的场景（VPN），这是唯一现实的方案。它的代价是要在通信双方/两端网关之间先建立「安全关联」（下一节）。</span>

**重点：IPsec 是「一次配置、处处保护」**——不像 TLS 每个应用都要单独集成，IPsec 在网络层为所有流量提供统一的安全边界。

## 2 安全关联（SA）：IPsec 的会话

IPsec 在两个通信实体（主机或网关）之间建立**安全关联（SA, Security Association）**——一条「我们之间用什么算法、什么密钥、怎么保护」的约定：

**SA 的内容**：使用的安全协议（AH 或 ESP）、加密与认证算法、密钥、SPI（Security Parameter Index，标识这条 SA 的编号）。<span class="marginnote"><strong>SPI</strong> 是 IPsec 包的「身份证」：接收方看到 SPI 就知道该用哪条 SA 的算法与密钥来解。SA 是<strong>单向</strong>的——双向通信需要一对 SA（A→B 一条、B→A 一条）。这与 TLS 的「一个会话双方向」不同，是 IPsec 的底层细节之一。</span>

**SA 的建立**：手工配置（小规模）或通过 **IKE（Internet Key Exchange）** 自动协商——IKE 负责双方认证与密钥交换（类似 TLS 握手，但服务于网络层）。**SA 的撤销**：SA 有生命周期，过期需重新协商。

## 3 ESP 与 AH：IPsec 的两大协议

IPsec 用两个协议实现安全服务：

**AH（Authentication Header，认证头）**：只提供**认证与完整性**（不加密）——验证「包是发送方发的、没被篡改」。**ESP（Encapsulating Security Payload，封装安全载荷）**：提供**加密 + 认证 + 完整性**——既保密又可信。<span class="marginnote">AH 与 ESP 的选择：<strong>AH 提供认证但不加密，ESP 加密且认证</strong>。现实中几乎都用 ESP——因为「只认证不加密」的场景（AH）很少，而 ESP 一个协议就覆盖全部。AH 还有个问题：它认证整个 IP 包（含源/目的地址），与 NAT 冲突（NAT 会改写地址导致 AH 认证失败），这也让 AH 逐渐边缘化。ESP 在隧道模式下只认证「内层包」+ 部分外层头，能与 NAT 共存。</span>

| 特性 | AH | ESP |
| --- | --- | --- |
| 加密 | 否 | 是 |
| 认证/完整性 | 是 | 是 |
| 抗重放 | 是 | 是 |
| 与 NAT 兼容 | 差 | 较好 |
| 实际使用 | 少 | 主流 |

## 4 传输模式与隧道模式

IPsec 的两种操作模式，决定「保护什么」：

**传输模式（transport mode）**：只保护**上层数据**（TCP/UDP 段），IP 头保持原样——用于「主机到主机」的直接通信。<span class="marginnote"><strong>传输模式</strong>的典型场景是「两台主机直接加密通信」：IP 头（源/目的地址）不动，只把 TCP 段包进 ESP——这样网络路由照常工作（地址可路由），只是内容被保护。适合单机对单机。</span>

**隧道模式（tunnel mode）**：把**整个 IP 包**（含原 IP 头）封装进一个新的 IP 包——新的外层 IP 头是隧道的两端（通常是两个 VPN 网关）。<span class="marginnote"><strong>隧道模式是 VPN 的核心</strong>：内网主机的原始 IP 包（源地址是内网私有地址）整个被加密封装，外层 IP 头是「网关 A → 网关 B」。这样内网地址被隐藏、内网包被保护，两个内网就像连成一片——「隧道」的名字正是「把包封进管道里送过去」的意思。</span>

**公式解析：隧道模式下的封装**

$$
\text{外层} = [\text{新IP头(网关A→网关B)}] \; [\text{ESP头}] \; [\text{原IP包(主机1→主机2)}] \; [\text{ESP尾+认证}]_{加密区}
$$

- **新 IP 头**：隧道的两端（两个网关），保证包能在公网上路由。
- **原 IP 包**：内网主机的完整包——整个被加密，公网上的观察者只能看到「网关 A 到网关 B 的加密流量」。
- **加密区**：ESP 头、原 IP 包、ESP 尾是加密 + 认证的——内容、内网地址全部保密。

**重点：隧道模式让「两个内网互通且全程加密」成为可能**——这正是站点间 VPN 的标准形态。

## 5 VPN 的类型与部署

IPsec 支撑的 **VPN（Virtual Private Network，虚拟专用网络）**，按场景分两类：

**站点间 VPN（site-to-site VPN）**：总部与分支的网关之间建立 IPsec 隧道——两个内网像连在一起，分支员工访问总部资源如同在本地。**远程访问 VPN（remote-access VPN）**：单个员工（笔记本）通过 IPsec 客户端连回公司网关——远程办公访问内网。<span class="marginnote">「<strong>虚拟专用网络</strong>」名字的含义：物理上数据走在公共互联网上，但加密 + 隧道让它「像一条专用网络」一样安全与私有。2020 年代远程办公普及后，VPN 成为企业标配；但经典 VPN 的「一次认证、全程信任」模型逐渐被零信任（SP 800-207）补充——见《认证》篇的零信任讨论。</span>

**VPN 的取舍**：**加密隧道带来安全，也带来开销**——IPsec 加密与封装增加延迟与带宽消耗；隧道的「一旦建立就信任」模型与现代零信任「每个请求都验证」的理念有张力。**SSL/TLS VPN** 是另一流派（用 TLS 而非 IPsec 实现远程访问，无需客户端软件，浏览器即可）——两种流派各有拥趸。

## 6 IKE：自动化地协商安全关联

SA 不能全靠手工配置——大型 VPN 需要**自动协商**。**IKE（Internet Key Exchange，互联网密钥交换协议）** 就是「IPsec 的握手协议」：

**IKE 的工作**：在双方之间先建立一条安全的「协商信道」，再在这条信道上协商 SA 的算法与密钥。<span class="marginnote">IKE 分两阶段：<strong>阶段 1 建立 ISAKMP SA</strong>（一条保护协商过程的加密信道，双方先互相认证、协商出「用于协商的密钥」）；<strong>阶段 2 建立 IPSec SA</strong>（在阶段 1 的保护下，协商真正保护数据的 ESP/AH SA）。这个「先保护协商，再协商保护」的分层设计，让复杂的协商过程本身也安全——类似 TLS 握手先做密钥交换再做数据加密的逻辑。</span>

**IKE 的认证方式**：预共享密钥（PSK，简单但扩展性差）、数字证书（PKI 篇的信任链，适合大规模）。**IKEv2**：现代版本，简化握手、内建 NAT 穿越、更强的安全默认——主流 VPN 部署的标配。

**重点：IKE 是把「IPsec 的安全」从「手工配置」变成「自动且可扩展」的关键**——没有 IKE，站点间 VPN 在规模稍大时就难以为继。

## 7 IPsec 面临的攻击

IPsec 提供了强保护，但并非免疫一切攻击：

**IKE 攻击**：暴力破解预共享密钥、中间人攻击协商过程（IKEv1 的 aggressive mode 曾有漏洞）。**加密弱化攻击**：攻击者尝试把协商拉到弱算法（降级攻击）——所以 IPsec 配置要禁用弱算法、强制强套件。<span class="marginnote">IPsec 的安全性有一个容易被忽视的边界：<strong>它保护「数据在途」，不保护「数据在端」</strong>——VPN 两端的机器本身被攻破、或 VPN 网关配置了弱密钥，IPsec 再强也没用。这也是为什么「VPN + 端点防护」总是搭配出现——IPsec 是网络层的盾，端点加固是终端上的盾。</span>

**针对隧道的 DoS**：攻击者向 VPN 网关发海量 IKE 请求，耗尽协商资源。**重放攻击**：IPsec 的抗重放机制（滑动窗口计数器）需要正确实现与足够大的窗口，否则可被绕过。

## 8 核心对比：IPsec 与 TLS 的取舍

两个「保护传输」的协议经常被并列比较，用一张表收束：

| 维度 | IPsec | TLS |
| --- | --- | --- |
| 所在层 | 网络层（IP 包） | 传输层（TCP 之上） |
| 保护对象 | 整段网络流量 | 单个应用连接 |
| 应用透明性 | 完全透明 | 需应用启用 |
| 部署位置 | 网关/主机 | 应用/库 |
| 典型场景 | 站点间 VPN、远程访问 | HTTPS、邮件、API |
| 客户端 | 需客户端/网关 | 浏览器内建 |

**重点：选型取决于「保护什么」**——两个数据中心之间要全程加密互连，用 IPsec VPN；一个 Web 应用要安全，用 TLS。两者共享同一套密码学地基（加密、认证、密钥交换、证书），只是把保护点放在协议栈的不同高度——这正是《网络安全基础》「分层安全」的又一次印证。

## 9 小结

- **IPsec 的网络层安全**：透明地保护所有 IP 流量，无需应用配合——与 TLS 的「保护单个连接」互补。
- **SA 是 IPsec 的会话**：约定算法、密钥与 SPI；单向、可经 IKE 自动协商。
- **AH 只认证、ESP 加密+认证**：现实几乎都用 ESP；AH 因 NAT 不兼容而边缘化。
- **传输模式**保护上层数据（主机到主机）；**隧道模式**封装整个 IP 包（网关到网关，VPN 核心）。
- **VPN 两类**：站点间（网关隧道）与远程访问（客户端连网关）；加密隧道带来安全也带来开销与信任模型张力。
- **IPsec 与 TLS 的分工**：TLS 逐应用、IPsec 逐网络——「保护连接」还是「保护一段网络」，看你要什么。
- **IKE 是自动化的握手**：先保护协商、再协商保护；IKEv2 简化握手、内建 NAT 穿越，是主流 VPN 标配。
- **IPsec 防「在途」不防「在端」**：端点被攻破或弱密钥，IPsec 再强也没用——VPN 需与端点防护搭配。

在下一节，我们转向「看不见的链路」——**无线网络安全**：无线信道比有线更易窃听，IPsec 与 TLS 都挡不住「空中的窃听者」。
