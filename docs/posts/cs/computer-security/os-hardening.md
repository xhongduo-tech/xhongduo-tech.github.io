## 为什么从系统加固开始

前几篇的防护集中在「代码层面」——缓冲区溢出怎么防、内存怎么保护。但攻击者真正进入系统后，面对的不是代码，而是**整个操作系统：默认服务、默认端口、默认口令、宽松的文件权限、没打补丁的软件**。**系统加固（hardening）** 就是把「开箱即用的默认系统」变成「经过最小化、收紧、监控的坚固系统」的过程。<span class="marginnote">Stallings 第4章与 NIST 的加固基线（如 CIS Benchmarks、NIST 800-123）都把加固定义为「<strong>最小化攻击面 + 收紧权限 + 持续监控</strong>」——它不是装个安全软件，而是「把系统该关的关掉、该锁的锁上」。大多数真实入侵利用的正是「没加固的默认配置」，而不是「未公开的零日漏洞」。</span>本篇建立三件事：加固的基本原则、加固的具体清单、以及加固之后如何保持。

## 1 加固的基本原则

系统加固的指导思想，与概述篇的安全原则一脉相承：

**最小化（minimalism）**：只安装必需的软件、只开放必需的服务、只保留必需的账户——**系统越小，攻击面越小**。<span class="marginnote">「<strong>默认安装一刀切</strong>」是许多服务器的通病：服务器上跑着图形界面、开发工具、不用的服务，攻击面被无谓地放大。加固的第一步永远是「问每个组件：真的需要吗？」——不需要就删掉或禁用。每个被移除的组件，都是一个不会被打穿的漏洞。</span>

**默认拒绝（default deny）**：防火墙默认拒绝、服务默认关闭、权限默认无——显式放行才开放。

**纵深防御（defense in depth）**：单点加固不够，账户、权限、防火墙、监控层层设防。**最小权限（least privilege）**：账户与进程只拥有完成任务所需的最小权限——这与访问控制篇的 RBAC 一脉相承。

## 2 账户与口令的加固

系统安全的第一道闸是「谁能登录」——账户与口令的管理是加固的重头：

**删除与禁用不必要的账户**：默认账户（`guest`、`admin`）、无人使用的离职账户、共享账户——每个残留账户都是一个潜在入口。<span class="marginnote"><strong>默认账户</strong>是最常被忽视的入口：许多设备出厂自带 <code>admin/admin</code> 或 <code>root/空口令</code>，管理员「懒得改」，攻击者「第一个试」。Mirai 僵尸网络正是靠默认口令批量攻破物联网设备。账户清理 = 关闭「明知道有人会试」的后门。</span>

**口令策略**：强制复杂度与长度、禁止弱口令、启用口令过期与历史。**MFA**：高权限账户强制多因素认证。**账户锁定与审计**：登录失败锁定、口令变更留痕。

**服务账户最小化**：服务以非 root 专用账户运行（如 Nginx 用 `www-data`），即使服务被攻破，攻击者也拿不到管理员权限。

## 3 服务与端口的加固

攻击者从「开放的端口」进入——服务与端口的最小化直接决定网络攻击面的大小：

**只运行必要的服务**：每个运行的服务都要有「存在理由」，多余服务（打印服务、蓝牙、Telnet、FTP 明文）一律关闭。**只监听必要的端口**：用端口扫描工具（`ss -tlnp`、`nmap localhost`）清点监听端口，关闭与业务无关的端口。<span class="marginnote">「<strong>先清点，再收敛</strong>」是服务加固的标准动作：先列出系统当前监听的所有端口（清点），再逐一判断「这个端口/服务必要吗」——不必要就关（收敛）。清点步骤容易跳过，但「不知道有什么在跑」恰恰是很多系统被入侵后仍不自知的原因。</span>

**禁用不安全协议**：用 SSH 取代 Telnet（Telnet 明文传输口令）、用 SFTP/SCP 取代 FTP、禁用明文 HTTP 而用 HTTPS。**SSH 加固**：禁用 root 直接登录（`PermitRootLogin no`）、启用密钥登录、限制可登录用户、修改默认端口以降低被扫描概率。

## 4 补丁管理：修复已知漏洞

**重点：补丁管理是加固里「最无聊却最重要」的一环**——大量真实入侵利用的是**早已公开、有补丁的已知漏洞**（而不是零日）。补丁管理就是「把已知漏洞的入口封死」：

**补丁的生命周期**：发现漏洞（CVE）→ 厂商发布补丁 → 管理员测试 → 分批部署 → 验证。**补丁的优先级**：按漏洞严重性（CVSS 评分）、受影响资产的重要程度、暴露程度（是否对外可达）决定先补谁。<span class="marginnote"><strong>CVSS（通用漏洞评分系统）</strong>是补丁排队的标尺：评分 9.0 以上（Critical）优先紧急处理，7.0–8.9（High）尽快处理。但「评分高 ≠ 优先打」——一个评分 9.0 但只在局域网内部、无互联网暴露的漏洞，优先级可能低于一个评分 8.0 但直接暴露公网的漏洞。<strong>补丁优先级 = 漏洞严重性 × 资产价值 × 暴露程度</strong>。</span>

**补丁的挑战**：补丁可能引入新问题（需测试）；「老系统无法打新补丁」（如停止支持的 Windows XP/老 Linux 发行版）是常见困境——对策是隔离、迁移或加外围防护（WAF、防火墙规则）。**自动补丁 vs 人工补丁**：自动省时但有风险（补丁坏兼容），关键系统宜人工分批。

## 5 文件权限与系统监控

**文件系统加固**：敏感目录与文件设置最小权限——`/etc`、日志、配置文件的属主与权限收紧；使用文件完整性监控工具（**Tripwire、AIDE**）记录关键文件的哈希，定期比对——文件被篡改立刻发现。<span class="marginnote"><strong>文件完整性监控（FIM）</strong>的价值在于「检测被篡改」：恶意软件或入侵者往往会改写系统文件（植入后门、替换登录程序）。FIM 在系统干净时先记录基线哈希，之后任何文件变化都会触发告警——它是「系统是否被篡改」的哨兵，也是事件响应（《事件响应》一篇）的重要取证来源。</span>

**日志与审计**：开启系统日志（`syslog`/`journald`）、命令审计（`auditd`）、登录日志——日志是「攻击者来过」的证据与「攻击进行中」的告警来源。**日志集中与不可篡改**：日志要集中存储、防止本地篡改（「攻击者删日志灭迹」是常见对抗手段）。

**系统监控**：资源监控（异常 CPU/网络可能是挖矿或外联）、进程监控（可疑进程）、文件变化监控——把「被入侵」从「事后才知道」变成「过程中发现」。

## 6 公式解析：加固的优先级怎么算

加固工作千头万绪，如何排序？可以用一个「风险驱动」的简化公式：

$$
\text{加固优先级} = \text{资产价值} \times \text{漏洞严重性} \times \text{暴露程度}
$$

- **资产价值**：该系统对业务的重要程度（越重要越优先）。
- **漏洞严重性**：CVSS 评分（漏洞越严重越优先）。
- **暴露程度**：系统对外暴露的程度（暴露越广越优先）。

**为什么三者相乘**：三个因子**任何一个为 0，整体为 0**——一个不重要的系统、或一个不严重的漏洞、或一个不暴露的系统，加固优先级都低。反之三者都高（核心系统 + 严重漏洞 + 公网暴露）必须立即处理。<span class="marginnote">这个公式与《风险评估与审计》篇的「风险 = 威胁 × 漏洞 × 影响」是同一个思想的两种表达——<strong>加固不是「把所有事情都做」，而是「把高风险的事优先做」</strong>。用数字排序，才能避免「把时间花在不重要系统上、漏掉真正致命的风险」。</span>

**重点：加固是风险管理在系统层面的落地**——用有限的人力与时间，优先加固「价值高、漏洞重、暴露广」的系统。

## 7 加固基线：CIS Benchmarks 与安全模板

手工一项项加固既慢又容易遗漏——于是业界把「一套经过验证的加固清单」固化成**加固基线（baseline）**：

**CIS Benchmarks（互联网安全中心基准）**：最权威的加固清单——为 Windows、Linux（Ubuntu/CentOS 等）、macOS、数据库、云平台等提供分项加固建议，每项都标注「检查方法 + 整改方法 + 影响」。**NIST 加固指南**：NIST SP 800-123（通用服务器安全指南）、800-44（服务器安全）、800-70（安全配置管理）。**发行版自带模板**：Linux 的 `lynis` 审计工具、SELinux/AppArmor 策略、Windows 的安全配置基准（组策略模板）。<span class="marginnote"><strong>CIS 基准是「加固的检查清单」</strong>：它把「什么样的系统算加固到位」具体化——比如「SSH 禁用 root 登录」「密码最大年龄 90 天」「审计日志开启」等数百条。安全团队按清单逐项检查打分，未达标项就是待整改清单。这也让「加固」从「凭经验」变成「可度量的合规过程」——CIS 合规度成为企业安全审计的常见指标。</span>

**重点：加固基线让「加固到位」变得可度量、可审计、可复现**——新系统上线前按基线加固，定期对照基线复核，就是系统安全质量的持续保证。

## 8 加固的生命周期：从上线到退役

加固不是「部署时做一次」的时点动作，而是贯穿系统生命周期的持续过程：

**上线前（pre-deployment）**：按基线加固、打补丁、配置监控与日志、做一次安全基线扫描。**运行期（operation）**：定期补丁、配置复核（防止「配置漂移」——有人手动改了配置导致加固失效）、监控告警、基线重评估。<span class="marginnote"><strong>配置漂移（configuration drift）</strong>是加固的头号敌人：系统刚上线时加固到位，运行一段时间后，有人为了「方便调试」关了防火墙、改了 SSH 配置、加了共享账户——加固就悄悄失效了。对策是把加固做成「代码」（如 Ansible、Chef、基础设施即代码 IaC），让「系统配置」可审查、可回滚、可重新套用——这正是 2020 年代「安全左移 + 配置即代码」的核心理念。</span>

**退役时（decommissioning）**：数据安全销毁、账户清理、系统从网络下线——退役阶段最容易被忽略，却常是数据泄露的来源。

**重点：加固是「过程」不是「状态」**——一次加固的成果会随时间漂移、随补丁失效、随系统演化而变旧。只有「基线 + 定期复核 + 配置即代码」的闭环，才能让加固长期有效。

## 9 一次最小化的加固演练：Linux Web 服务器

把前面的原则落到一个具体场景——加固一台 Linux Web 服务器，标准动作大致是：

**第一步，最小化**：最小化安装（无图形界面、无多余软件）；关闭不用的服务（打印、蓝牙、CUPS）；禁用 `root` 直接 SSH 登录；删除 `guest` 等默认账户。**第二步，收紧**：防火墙（`ufw`/`iptables`）默认拒绝、只放行 80/443/22；SSH 改用密钥登录并限制用户；数据库绑定内网而非公网。<span class="marginnote">「<strong>数据库绑定内网</strong>」是常见的加固遗漏：应用要连数据库，就顺手把数据库端口对外开放——结果数据库成了公网可访问的目标（被扫描、被暴力破解）。正确做法是数据库只监听内网/本机，应用通过内网访问。任何「业务不需要对外的服务」都应当「不对外」——这就是最小暴露原则的日常应用。</span>

**第三步，监控**：开启审计日志（`auditd`）、文件完整性监控（`aide`）、系统日志集中；配置异常登录告警（多次失败即告警）。**第四步，基线复核**：对照 CIS 基准跑一遍 `lynis` 审计，把未达标项逐条整改。

**重点：这套「最小化 → 收紧 → 监控 → 复核」四步，几乎适用于任何服务器**——无论 Linux、Windows 还是云主机，方法论一致，只是命令与基线不同。

## 10 小结

- **加固的本质**：最小化攻击面 + 收紧权限 + 持续监控——把「开箱即用」变成「坚固可用」。
- **四大原则**：最小化、默认拒绝、纵深防御、最小权限。
- **账户加固**：清理默认/闲置/共享账户、口令策略 + MFA、服务用专用低权限账户。
- **服务加固**：只跑必要服务、只监听必要端口、禁用明文协议、SSH 禁用 root 登录。
- **补丁管理**：补丁优先级 = 漏洞严重性 × 资产价值 × 暴露程度；「有补丁却没人打」是最大短板。
- **监控加固**：文件完整性监控（Tripwire/AIDE）、日志集中与防篡改、资源与进程异常监控。
- **加固优先级** = 资产价值 × 漏洞严重性 × 暴露程度——把有限资源优先投给高风险系统。
- **加固基线**：CIS Benchmarks、NIST 指南把「加固到位」具体化成可度量清单，让加固可审计、可复现。
- **加固是过程不是状态**：配置漂移会悄悄让加固失效；「基线 + 定期复核 + 配置即代码」才能长期有效。
- **默认配置是最大短板**：攻击者利用的常是「没加固的默认配置」而非零日——加固是把「默认」变成「最小化 + 收紧」。
- **补丁管理是「最无聊却最重要」的一环**：大量入侵用的是已公开、有补丁的漏洞——「有补丁却没人打」是最大短板。

在下一节，我们把加固的视野从「一台机器」扩展到「数据与云端」——**数据库与云安全**：系统加固保护「主机」，数据库与云安全保护「数据」。
