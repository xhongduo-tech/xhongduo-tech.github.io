## 为什么从引用与借用开始

上一课的所有权有个尴尬：函数想**读**一个值，却必须把所有权拿走，用完再还回来，代码写得像在打乒乓球。引用与借用解决了这个问题——**引用（reference）让你在不拥有数据的情况下访问数据**，而「通过引用访问数据」这一动作在 Rust 里叫**借用（borrowing）**，语义上正是「借来看看，不带走」。

这一章的内容是借用检查器的全部核心规则，也是 Rust 编译器报错最集中的地方。把这套规则内化成直觉，后面所有章节的代码都会顺很多。

## 1 引用：`&` 与 `&mut`

### 不可变引用 `&`

让函数只读借用参数：

```rust
fn calculate_length(s: &String) -> usize {
    s.len()
} // 这里 s 被 drop，但因为它只是引用，不释放 String 本体

fn main() {
    let s = String::from("hello");
    let len = calculate_length(&s);  // 借用 s，而不是移动
    println!("{} 的长度是 {len}", s);  // s 仍然可用
}
```

`&s` 创建对 `s` 的**不可变引用**。传引用进去，函数只能读不能写，数据仍归 `main` 所有。借用结束后引用失效，但 `s` 毫发无损。<span class="marginnote">「借用不转移所有权」是这一课的地基：`&String` 表示「这段数据的访问权被临时借出，数据主人不变」。这在语义上呼应了日常的「借」——借出去的东西，主人还是你，还回来时东西还得在。</span>

引用不拥有数据，所以 `&s` 这个引用离开作用域时不会释放堆内存——它只是「看着」那块内存的指针。这正解决了所有权「传来传去」的笨拙。

### 可变引用 `&mut`

要允许函数修改借用的数据，用**可变引用**：

```rust
fn change(s: &mut String) {
    s.push_str(", world");
}

let mut s = String::from("hello");
change(&mut s);   // s 必须本身可写（mut），才能借出 &mut
```

可变引用的出现有严格限制，这是 Rust 防止数据竞争的关键：

**限制一：同一时刻只能有一个可变引用**。写一个 `&mut` 后，在它失效前不能再创建第二个可变引用指向同一数据：

```rust
let mut s = String::from("hello");
let r1 = &mut s;
let r2 = &mut s;   // 编译错误：不能同时有两个可变借用
```

**限制二：可变引用与不可变引用不能共存**。数据一旦被可变借用，不可变借用也不能同时存在：

```rust
let r1 = &s;        // 不可变借用
let r2 = &mut s;    // 错误：已有不可变借用时不能创建可变借用
```

**限制三：引用的作用域在「最后一次使用」处结束**。Rust 引用的有效性（lifetime）不是到代码块结尾，而是到**最后一次使用它**的地方。这允许「先借用用完，再申请新的借用」：

```rust
let r1 = &s;             // 不可变借用
println!("{r1}");        // 最后一次使用 r1，r1 在此失效
let r2 = &mut s;         // 合法：r1 已不再被使用
```

**为什么「一写不能多写、读写不能并存」**：这正是数据竞争（data race）的定义——多个线程同时读写同一内存，且至少一个是写。Rust 把「数据竞争」从运行期竞争条件变成了编译期类型错误，因为你根本写不出同时两个 `&mut` 的代码。<span class="marginnote">数据竞争是并发 bug 的头号来源：C/C++ 里两个线程同时写同一个变量是未定义行为，排查极难。Rust 的「同刻唯一可变借用」在编译期就排除了它——这是第16篇《线程与消息传递》能那么轻松的前提。</span>

## 2 悬空引用（dangling reference）：编译器如何抓住它

悬空引用指向已释放的内存。Rust 在编译期就拒绝返回悬空引用：

```rust
fn dangle() -> &String {
    let s = String::from("hello");
    &s          // 错误：返回局部变量的引用
}               // s 在这里被 drop，引用指向已释放的内存
```

`dangle` 返回 `&s`，但 `s` 在函数结束时被 drop——返回的引用就成了悬空引用。编译器报错「`missing lifetime specifier`」并明确提示：返回的引用引用了函数内部的局部数据，数据已被清理。<span class="marginnote">悬空引用在 C 里是著名的未定义行为来源：函数返回局部变量的地址，调用者拿到野指针，运行期崩溃或静默出错。Rust 借用检查器把这种 bug 从「运行期之谜」变成了「编译期一行报错」。</span>

正确的做法是返回 `s` 本身（转移所有权）：

```rust
fn no_dangle() -> String {
    let s = String::from("hello");
    s           // 所有权返回给调用者
}
```

## 3 借用规则与 `&str` 之谜

把 Rust 的借用规则整理成一张总表，它是整个借用检查器的纲领：

| 规则 | 说明 |
| --- | --- |
| 可以同时有多个 `&`（不可变借用） | 只读共享是安全的，人人可读 |
| 同一时刻最多一个 `&mut` | 写必须独占，防止竞争 |
| `&` 与 `&mut` 不能同时存在 | 读写互斥 |
| 引用必须始终有效 | 生命周期内数据不可被 drop（见第10篇） |
| 引用只是借用，不拥有数据 | 引用失效不会释放数据 |

### 字符串字面量为什么是 `&str`

现在可以解释上一课遗留的问题：字符串字面量 `"hello"` 的类型为什么是 `&str` 而不是 `String`。字面量**编译期就写死在二进制里**（程序的数据段），程序运行时它已经存在，不需要堆分配、也没有谁「拥有」它——所以把它当作一段被借用的只读文本 `&str` 最自然。它借用的是程序静态数据区的内存，永远有效，不需要释放。<span class="marginnote">`&str` 与 `String` 的关系是 Rust 最常见的类型配对：`&str` 是「借用的不可变文本视图」，`String` 是「拥有的可增长文本」。函数参数默认用 `&str`（谁都能传），需要修改时才收 `String` 或 `&mut String`。</span>

这也解释了为什么猜数游戏里 `guess.trim().parse()` 是安全的：`trim()` 返回 `&str`（借用 `guess`），`parse()` 解析出一个新值，整个过程中 `guess` 的数据从未被移动。

## 4 公式解析：借用规则的集合表述

借用规则可以用「访问权限的集合」表达得很精确。设内存中有数据 $D$，记：

$$
R(D) = \{\text{当前有效的不可变借用数}\}, \quad W(D) = \{\text{当前有效的可变借用数}\}
$$

借用检查器的约束是：

$$
R(D) \ge 0, \quad W(D) \in \{0, 1\}, \quad R(D) + W(D) \le 1
$$

拆解三步：

- **第一步，读第一条 $W(D) \le 1$**：可变借用最多一个，这是「写独占」——多个写者同时改数据就是竞争。
- **第二步，读第二条 $R(D) + W(D) \le 1$**：不可变借用与可变借用不能并存。若有一个 `&mut`，则 $W=1$，要求 $R=0$；若全是 `&`，则 $W=0$，$R$ 可以任意大。
- **第三步，为什么「多个读」允许**：只读不写，数据不变，所有读者看到的是一致的快照，没有竞争。允许 $R$
