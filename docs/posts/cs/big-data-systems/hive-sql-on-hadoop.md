## 为什么从 Hive 开始

HDFS 把数据存好了，MapReduce / Spark 能算了，YARN 能调度了——但一个现实问题立刻浮出水面：**让每个分析师去写 MapReduce 代码，几乎不可能。** 绝大部分数据需求是"从一张大表里按条件筛、按维度聚、出报表"，这正是 SQL 的强项。Hive 诞生于 Facebook 2008 年前后，目标朴素而深远：**把 HDFS 上的文件翻译成一张张"表"，让 SQL 语句自动编译成 MapReduce / Spark 作业。**<span class="marginnote">Hive 是"SQL-on-Hadoop"的开山之作，此后 Presto、Impala、Spark SQL 都沿着"声明式 SQL + 大数据引擎"这条路继续走，但 Hive 定义了表、分区、分桶这些今天仍在用的数据仓库原语。</span>它与你学过的第二级《数据库》关系模型、《SQL 查询优化》直接对接——只是把执行引擎从单机换成了分布式集群。

## 1 从关系数据库到 Hive 的映射

Hive 把 HDFS 上的文件组织成关系模型的表结构，映射关系如下：

| 关系数据库 | Hive 对应物 |
| --- | --- |
| 数据库 | HDFS 上一个目录 |
| 表 | 一个目录下的若干文件（文本 / Parquet / ORC） |
| 行 | 文件里的每一条记录 |
| 列 | 记录被 schema 解析出的字段 |
| 索引 | 分区（partition）、分桶（bucket）、统计信息 |

**重点：Hive 的表不是"实体"，而是"HDFS 文件 + 一份元数据解释"。** 文件里存什么、怎么解释成行，由存在 MySQL/derby 里的元数据（schema、分区、存储格式）决定。这也是 Hive 被称为"数据仓库"而非"数据库"的原因：它的读写吞吐极高，但单条查询延迟以秒计——为分析而生，不为事务而生。

## 2 分区与分桶：让查询只扫该扫的

数据仓库里最贵的资源是"扫描"。Hive 用两层手段缩小扫描范围：

**分区（partition）**：按某列的离散值（通常是日期）把表拆成子目录，如 `orders/dt=2026-08-11/`。查询带 `WHERE dt = '2026-08-11'` 时，Hive **只读该子目录**，其余分区直接跳过——这叫**分区裁剪（partition pruning）**。<span class="marginnote">分区本质上是把"按值过滤"翻译成了"按目录跳过"：过滤条件在读取文件<strong>之前</strong>就被应用掉了。这与 Parquet/ORC 的谓词下推是同一思路的两层——一层在文件目录粒度，一层在文件内部。</span>

**分桶（bucket）**：在分区内部再按某列的哈希把文件切成固定数量的小文件，如 `bucket 0,1,2,...,n-1`。分桶的价值在于**抽样**与**分桶连接**——两边按同一列同桶数分桶后，join 时只需匹配对应的桶，而不是全表笛卡尔式比较。

**辨析｜易错点：** 分区列选错了代价巨大。选**基数低且查询高频**的列（如日期、地域）做分区，能砍掉大量扫描；选基数高的列（如订单 ID）做分区，会切出成千上万个小目录，元数据膨胀、文件数爆炸，反而拖垮性能——**分区是"用目录数量换扫描量"，方向要选对**。

分区、分桶、文件格式三层手段的正确组合顺序，是数仓性能调优的第一课：

| 手段 | 作用粒度 | 削减的对象 | 适用列 |
| --- | --- | --- | --- |
| 分区 | 目录级 | 扫描的目录数 | 低基数、查询高频（日期/地域） |
| 分桶 | 文件级 | 文件数与 join 匹配量 | 中基数、join 与抽样键 |
| 列式格式 | 文件内部 | 读取的列数与压缩量 | 宽表分析查询 |
| 行组索引（ORC） | 行组级 | 文件内跳过的行组 | 有范围条件的过滤列 |

**一条实战准则**：先用分区把"范围"缩到目录级，再用列式格式 + 索引把"文件内"的扫描最小化，最后才考虑分桶优化 join——**三层优化叠加后，一次查询的 IO 可以比初始全表扫描低三个数量级**，这是"数仓优化性价比"由高到低的正确顺序。

## 3 HiveQL 的一次编译旅程

一条 `SELECT` 语句从写下来到结果返回，经历了完整的翻译流水线：

1. **解析**：SQL 文本 → 语法树（AST）。
2. **语义分析**：查元数据，解析表、列、类型，生成逻辑计划（运算符树）。
3. **逻辑优化**：谓词下推、列裁剪、分区裁剪——与 Spark Catalyst 的逻辑优化同一套手法。
4. **生成执行计划**：把逻辑计划翻译成 MapReduce / Spark 作业（一个 join 可以是一个 reduce 阶段；多阶段作业串成 DAG）。
5. **执行**：交给 YARN 上的 MapReduce / Spark 引擎运行。

**这就是"SQL-on-Hadoop"的字面含义：Hive 本身不计算，它把 SQL 翻译成引擎的作业。** 所以"换引擎不用改 SQL"——从 MapReduce 换到 Spark（Hive on Spark）或 Tez，分析代码一行不改，只是跑得快了。

## 4 数仓建模的三种表

做数据仓库绕不开星型 / 雪花型建模，Hive 里对应三类表，分工明确：

- **事实表（fact）**：记录业务事件本身，行多、列宽，如订单表。可增长、不可随意覆盖。
- **维度表（dimension）**：描述业务对象的属性，如用户、商品、地域。行少、常更新。
- **宽表 / 汇总表（aggregate）**：预先聚合的结果（如"每日分城市销售汇总"），把高频查询的聚合成本提前付掉。

**重点：数据仓库的核心方法论是"**预处理**"——把昂贵的聚合在数据进入时算好，让查询变得极简。** 这就是为什么 Hive 大量使用分区、分桶、预聚合：**查询可以慢在第一天，但不能慢在每一天。**这与 Lambda 架构里"批层产出预计算视图"是同一个思想——一次算好，多次读取。

## 5 公式解析：分区裁剪到底省了多少扫描

设表 $T$ 共有 $N_p$ 个分区，某查询只命中其中 $k$ 个，每个分区大小近似 $S$。无裁剪时全表扫描：

$$
C_{\text{full}} = N_p \cdot S
$$

有裁剪时只扫命中分区：

$$
C_{\text{prune}} = k \cdot S, \qquad \frac{C_{\text{prune}}}{C_{\text{full}}} = \frac{k}{N_p}
$$

- **$N_p$（总分区数）**：如按天分区存两年的表，$N_p = 730$。
- **$k$（命中的分区数）**：查"昨天"只命中 $k=1$。
- **节省比**：$\frac{1}{730} \approx 0.14\%$——**这就是"加一个日期条件，查询快几百倍"的数字来源**。配合 Parquet 列裁剪（只读所需列）与 ORC 行组索引，三者叠加，一次查询的 IO 可以比"全表全列扫描"低三个数量级。

**数字算例**：假设订单表按 `dt` 分 730 个天分区，每分区约 4 GB 列式数据。查"昨日分城市销售额"（只取 4 列、命中 1 个分区），列式裁剪后实际读取约 $4\ \mathrm{GB} \times \frac{4}{20\ \text{列}} = 0.8\ \mathrm{GB}$；而全表全列扫描要读 $730 \times 4 = 2.92\ \mathrm{TB}$。**一次查询的 IO 从 TB 级降到 GB 级，快三个数量级的说法由此而来**——这也是数仓团队"每加一个分区键都要反复掂量"的原因。

**辨析｜易错点：** 分区列不是越多越好。两个以上分区列会生成**嵌套目录**，文件数按笛卡尔积爆炸（如按 天×小时 分区，一年就产生 8760 个目录）。**高基数列做分区、低基数列做桶、筛选频繁的高基数列留给 ORC 行组索引**，是更稳的组合。

## 6 术语速查表

| 术语 | 英文 | 一句话解释 |
| --- | --- | --- |
| 分区 | partition | 按列值切目录，查询时可跳过无关目录 |
| 分桶 | bucket | 分区内按哈希切固定数量的小文件 |
| 分区裁剪 | partition pruning | 过滤条件翻译成"只读命中目录" |
| 元数据 | metastore | 存于 Derby/MySQL，解释文件如何映射成表 |
| 事实表 | fact table | 记录业务事件，行多列宽 |
| 维度表 | dimension table | 描述业务对象的属性，行少常更新 |
| 汇总表 | aggregate table | 预聚合结果，把聚合成本提前付掉 |
| 谓词下推 | predicate pushdown | 把过滤下推到文件读取层 |

## 7 小结

- Hive 是 **SQL-on-Hadoop**：把 HDFS 文件 + 元数据组织成表，SQL 自动编译成 MapReduce / Spark 作业。
- 表 ≈ 目录 + 文件 + schema 解释；**分区裁剪**与**分桶连接**是缩小扫描范围的两大手段。
- 查询流水线：解析 → 语义分析 → 逻辑优化 → 生成作业 → 执行；引擎可替换而 SQL 不变。
- 数仓三类表：**事实表 / 维度表 / 汇总表**，核心方法论是**预处理**（一次算好、多次读取）。
- 分区裁剪收益可量化：扫描量从 $N_p S$ 降到 $kS$，数量级可差 1000 倍。
