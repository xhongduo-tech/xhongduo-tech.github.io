## 为什么从序列化与存储格式开始

前几节讲的 MapReduce、HDFS、YARN 解决了"算、存、调"，但忽略了一个每时每刻都在发生、却容易被忽视的环节：**数据从内存到磁盘、从这台机器到那台机器，是以什么字节序列存在的？** 一个 Python 对象没法直接塞进网络包；一个表也没法原样存进 HDFS。把这些对象、记录变成可存储可传输的字节流，叫**序列化（serialization）**；反过来叫反序列化。而**列式存储**则是让"只读其中几列"的分析查询快一个数量级的存储布局。<span class="marginnote">序列化与存储格式直接决定你的作业 IO 有多大、能压缩多少、schema 能不能演进——大数据系统里最便宜的优化，往往不在算法，而在格式。</span>它与第三级《计算机组成原理》里的内存布局、第二级《数据库》里的存储引擎是同一知识的不同切片。

## 1 为什么要序列化：对象离开内存之后

在单机上，两个模块通过函数调用传参；在分布式系统里，模块散落在不同机器上，参数只能变成**字节流**跨网络传输。序列化要解决四个问题：

**互操作**：不同语言（Java、Python、C++）写的系统之间能互相读懂数据。
- **紧凑**：同样的信息，占的字节越少，网络与磁盘开销越低。
- **快速**：序列化 / 反序列化的 CPU 成本要低。
- **schema 演进**：数据定义（加了字段、删了字段）之后，新旧版本还能互相兼容。

**重点：大数据系统的序列化选型，本质上是在"紧凑性、速度、可读性、演进能力"之间找平衡。** Java 原生的 `Serializable` 又慢又膨胀；JSON 可读但冗余；于是有了面向大数据专门设计的二进制格式。

**一个直观的规模感**：同一份"用户信息"记录，Java 原生序列化约需 300+ 字节（它把完整的类结构也写进字节流），JSON 约 120 字节，而 Avro 二进制只需约 50 字节。<span class="marginnote">这些数字是量级参考而非精确值：自描述文本（JSON）比紧凑二进制（Avro）通常大 2–3 倍，Java 原生序列化则因携带类元信息而更臃肿。方向比精确值更重要——"格式决定 IO 的量级"。</span>当同一批数据要经过十万条记录的传输与落盘，体积差就直接换算成网络与磁盘的耗时差，甚至差出一个数量级。这解释了为什么大数据作业的"最便宜优化"往往在格式而非算法。

## 2 Avro：自描述、支持 schema 演进的序列化格式

**Avro** 是 Hadoop 生态官方钦定的序列化格式，核心设计有两条：

**第一，schema 用 JSON 书写，随数据一起保存或通过 RPC 传递。** 数据文件头部直接携带 schema，读取端无需事先约定——这解决了"数据自描述"问题。

```
{"type": "record", "name": "User",
 "fields": [{"name": "name", "type": "string"},
            {"name": "age",  "type": "int"}]}
```

**第二，schema 演进有明确规则**：加字段必须给默认值（旧数据读新 schema 时填默认值），删字段则旧 reader 自动忽略多余字段。这让"给用户表加一列"不再需要重写历史数据。**这是"向后兼容 + 向前兼容"的分工**：新 reader 读旧数据（向后）靠默认值兜底，旧 reader 读新数据（向前）靠忽略未知字段——两条规则合起来，才让跨版本的读写不会崩。<span class="marginnote">Avro 的哲学是"<strong>先有 schema，后有数据</strong>"：数据本身只是紧凑的裸字节，schema 才是解释这些字节的地图。相比 JSON 每个字段都带名字，Avro 只需按 schema 里的顺序与类型解码，所以体积小得多。</span>

## 3 列式存储：Parquet 与 ORC

行式存储把一条记录的所有字段挨在一起写；**列式存储（columnar）把同一列的所有值挨在一起写**。这一布局改变对"分析型查询"（OLAP）是革命性的：

- **只读所需列**：查 `SELECT AVG(age)` 只需读 age 那一列的数据，不必读整行——IO 减少一个数量级。
- **同列类型一致，压缩率极高**：同一列的值类型相同、常高度相似（如年龄大多是两位数），能压到行式的几分之一。
- **天然适配谓词下推**：先读某列做过滤，命中才取其他列。

**Parquet** 与 **ORC** 是两大主流实现，都基于 Google 的 Dremel 论文里提出的"列族嵌套编码"。它们把文件切成若干行组（row group），行组内再按列独立存储，使得"一列一块"既好压缩又好并行读。ORC 更进一步，为每列内建**索引**（min/max、布隆过滤器），让"只扫需要的行组"成为可能。

**一个具体的行组剪枝例子**：一张订单表按 `order_date` 排序落盘，Parquet 会在每列末尾记下该列的 min/max 统计。当查询是 `WHERE order_date > '2026-01-01'` 时，引擎先只读 `order_date` 列的统计信息，发现某些行组的最大值早于该日期——**整个行组直接跳过，数据根本没进内存就被排除**。ORC 的布隆过滤器则擅长另一类过滤：判断"某个 `user_id` 是否出现在某行组"，用极小的内存代价挡掉绝大多数不命中的块。**列式 + 索引，让"全表扫描"这个说法在许多分析查询里名存实亡**——这正是数据仓库能在亿行表上做秒级聚合的底气。

**辨析｜易错点：** 列式存储不是万能的。它**极不适合点查与高频更新**：插入一行要分别写所有列文件，更新一条记录的代价更高。这就是为什么在线交易（OLTP）仍用行式数据库，而分析（OLAP）用列式——两种布局是**为两种查询模式分别优化**的，不存在谁取代谁。这个区分在第二级《数据库》的"行存储 vs 列存储"里是考点，在大数据里是选型依据。

**写入视角的补充**：列式对"高频小写入"尤其不友好——每写一行要触碰所有列文件，且压缩块越大、部分更新越贵。于是生产上常见"**行式接收、列式分析**"的管道：OLTP 端用行式库承接交易，通过 ETL 把数据落到 Parquet / ORC 供分析引擎查询。**存储格式的选择从来不只是技术问题，而是由"数据如何被写入、如何被读取"共同决定的**——读多写少走列式，写多读少走行式。

**一个常见误区**：以为"用了列式存储就会自动变快"。实际上列式只对"需要少数列的分析查询"生效；对 `SELECT *` 式的全列读取，列式与行式 IO 相当，甚至因需要拼装各列而更慢。**选型要对着真实查询画像来选，而不是对着潮流来选**——先问你的查询读几列，再决定要不要列式。

三大格式各有所长，选型对照如下：

| 维度 | Avro | Parquet | ORC |
| --- | --- | --- | --- |
| 布局 | 行式 | 列式 | 列式 |
| 适用 | RPC / 事件 / Kafka 消息 | 数据湖通用分析格式 | Hive / Spark 数仓 |
| schema 演进 | 原生支持（字段增删） | 支持（较繁琐） | 支持 |
| 压缩率 | 好 | 极好 | 极好 |
| 内置索引 | 无 | 统计信息 | min/max + 布隆过滤器 |
| 写入性能 | 快（追加友好） | 中 | 中 |

**一句话选型**：要"跨系统传输与演进"选 Avro；要"大表分析查询"优先 Parquet（生态最广）或 ORC（Hive 深度优化）。它们并不互斥——同一份数据可以 Avro 负责接入、Parquet/ORC 负责分析，各取所长。**现代数据湖的常见配置正是如此**：Kafka 里的事件用 Avro 承载，落湖时转成 Parquet，由 Iceberg / Hudi / Delta Lake 负责事务与演进——格式之间是接力，不是竞争。

## 4 公式解析：列式存储省下的 IO 到底有多少

设一张表有 $C$ 列、$N$ 行，分析查询只需要其中 $K$ 列。行式读取需读整表，列式只需读 $K$ 列，IO 之比：

$$
\frac{\text{列式 IO}}{\text{行式 IO}} = \frac{K \cdot N \cdot s}{C \cdot N \cdot s} = \frac{K}{C}
$$

分三步拆解：

- **$C$（总列数）**：表的宽度。数据仓库里 $C$ 常达几十上百列。
- **$K$（查询需要的列数）**：分析查询往往只要 3–5 列（维度和度量）。
- **$\frac{K}{C}$（IO 节省比）**：当 $K=5,\ C=100$ 时，列式只需读 5% 的数据——**这正是"列式快一个数量级"这句话的出处**。

再叠加压缩：列式对同列值压缩，压缩比通常再省 3–10 倍。**列式存储把"数据量大"从性能问题变成了几乎可以忽略的问题**，这是所有分析型大数据系统（Hive、Spark SQL、Presto、ClickHouse）都建立在列式文件上的根本原因。**一句直觉**：列式压缩率高的根源，是同列值类型一致、取值分布集中（年龄多为 20–60、日期多为同年份），冗余天然大；行式混装不同类型与取值，压缩无从下手。**一句话总结本节**：行式把"读整行"优化到极致，列式把"读几列"优化到极致——大数据分析大多是后者，所以列式成了分析型系统的默认选择。

## 5 术语速查表

| 术语 | 英文 | 一句话解释 |
| --- | --- | --- |
| 序列化 | serialization | 把内存对象变成可存储、可传输的字节流 |
| 反序列化 | deserialization | 从字节流还原出内存对象 |
| schema | schema | 数据的字段名与类型定义 |
| schema 演进 | schema evolution | 数据定义变更后新旧版本仍可互读 |
| 行式存储 | row-oriented | 一条记录的所有字段连续存放 |
| 列式存储 | columnar | 同一列的所有值连续存放 |
| 行组 | row group | 列式文件内可独立扫描与剪枝的块 |
| 谓词下推 | predicate pushdown | 先做过滤再取其他列，减少 IO |
| 布隆过滤器 | bloom filter | 用少量内存判断"元素是否在集合中" |
| 自描述 | self-describing | 数据自身携带如何解读它的 schema |
| 压缩比 | compression ratio | 压缩后大小与原始大小的比值 |

## 6 小结

- **序列化**把内存对象变成可存储、可传输的字节流，选型要在紧凑、速度、互操作、演进之间权衡。
- **Avro**：schema 用 JSON 自描述，支持增删字段的 schema 演进，适合 RPC 与事件数据。
- **Parquet / ORC**：列式布局 + 列内压缩 + 索引，专为分析查询（OLAP）设计。
- 核心公式：列式 IO 是行式的 $\frac{K}{C}$，只读需要的列。
- **行式适交易、列式适分析**，两者不是替代关系而是分工。
- 一句选型：**传输演进用 Avro，分析查大表用 Parquet / ORC**，它们可在一份数据上分工共存。
- **min/max 与布隆过滤器是不同武器**：前者回答"范围过滤"，后者回答"存在性过滤"，两者配合覆盖了绝大多数谓词下推场景。
