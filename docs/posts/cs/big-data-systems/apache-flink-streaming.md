## 为什么从 Flink 开始

Structured Streaming 那条路把"流切成微批"来获得低延迟，但微批的延迟下界在数百毫秒，而且"批"的语义在事件时间、精确一次这些细节上总有种"补丁"感。**Flink 走的是另一条路：从第一天起就把"流"当作一等公民，让每条记录到达即被处理——事件级、毫秒级、真·流式。**<span class="marginnote">Flink 起源于 2010 年的柏林工业大学研究项目，2014 年进入 Apache 孵化。它的口号是"Stateful stream processing for accurate, low-latency, high-throughput"——有状态、准确、低延迟、高吞吐，四个词句句都有对应的工程实现。</span>如果说 Spark 是"把批做快"，Flink 就是"把流做真"；两者共同撑起了今天"批流一体"的两大阵营。它与本专题的 Structured Streaming、Kafka、ZooKeeper 环环相扣。

## 1 Flink 的流式世界观

Flink 认为：**一切计算都可以建模为流**。批处理只是"流恰好结束"的特例（有界流），真正的核心是**无界流上的持续计算**。这一世界观带来三个推论：

**处理单位是"事件"**：每条记录到达后立即进入算子流水线，不像微批要等一批攒齐。
- **一切算子有状态**：聚合、去重、窗口都需要记住"之前的输入"，这个**状态**是流计算与"无状态 map"的本质区别。
- **数据进来就不回头**：一旦某条事件被消费，后续对它的重访只能靠重放，无法原地重算。

**重点：Flink 与微批的本质差异，不在"快了多少毫秒"，而在"状态与容错的对象不同"——Flink 管的是"每条事件 + 每个算子的状态"，微批管的是"一批又一批的作业"。** 这决定了 Flink 能在窗口、事件时间、精确一次这些语义上做到系统级的一致。

## 2 状态与 Checkpoint：让"记住"变得可靠

流计算的核心资产是**状态（state）**——算子在处理过程中记住的一切（聚合的累计值、窗口的内容、去重集合）。状态出了错，结果全错。Flink 用 **Checkpoint（检查点）** 机制让状态可靠：

1. 每隔固定间隔（如 10 秒），JobManager 在数据流中注入一个**屏障（barrier）**标记。
2. barrier 顺着数据流穿越每个算子；每个算子遇到 barrier，就把它**当前的状态快照**到持久化存储（HDFS、S3）。
3. 当所有算子的快照对齐完成，本次 checkpoint 完成——**那一刻系统的完整状态就有了一个一致快照**。
4. 崩溃恢复时，Flink 从最近完成的 checkpoint **回滚**：状态载回快照，数据从 barrier 位置**重放**，重新算到当前点。

<span class="marginnote">Checkpoint 的思想与数据库的<strong>预写日志（WAL）+ 快照</strong>几乎同构：定期落一致快照，增量靠日志重放。你在第二级《数据库》学的"原子性靠日志"，在这里被扩展成了跨整个数据流拓扑的分布式快照——Chandy-Lamport 分布式快照算法（1985）正是其理论源头。</span>

## 3 精确一次语义（Exactly-once）

消息系统里一个反复出现的承诺是 **at-least-once / at-most-once / exactly-once**：

- **at-least-once（至少一次）**：可能重复，但不会丢——多数系统的默认。
- **at-most-once（至多一次）**：可能丢，但不重复——适合可容忍丢的指标。
- **exactly-once（精确一次）**：既无重复也不丢——最理想也最难。

Flink 通过"**Checkpoint 回滚 + 事务输出**"实现端到端精确一次：计算内部靠 barrier 对齐保证状态不重不漏；对外的输出（写 Kafka、写数据库）用**两阶段提交**——先写"预提交"，checkpoint 完成才"正式提交"。整套机制让结果看起来像是"每条记录恰好被处理一次"。

**辨析｜易错点：** "精确一次"是一个**端到端**承诺，不是单靠计算引擎就能兑现的。Flink 只保证引擎内部精确一次；到下游接收器（数据库、文件系统）这一步，还必须接收器支持幂等或事务。**任何一处不支持，端到端就退回 at-least-once。** 这也是工程上最常见的高估点。

## 4 窗口：流式聚合的时空切片

流是无限的，聚合必须"切窗口"。Flink 支持四类窗口：

- **滚动窗口（tumbling）**：固定长度、不重叠，如每 5 分钟。
- **滑动窗口（sliding）**：固定长度、可重叠，如每 5 分钟、每 1 分钟滑一次。
- **会话窗口（session）**：按不活动的间隔切开，如"用户连续操作直到静默 10 分钟"。
- **全局窗口**：整个流一个窗口（需自定义触发）。

窗口可基于**处理时间**（到达时间，快但不准）或**事件时间**（数据自带时间戳，准但需处理乱序）。事件时间窗口依赖**水位线（watermark）**推进与触发——与 Structured Streaming 一脉相承，但 Flink 对乱序、迟到数据的处理更细粒度（可设允许迟到时间、延迟数据单独触发）。

四类窗口各自适用于不同业务形态，选型对照：

| 窗口类型 | 定义 | 典型场景 |
| --- | --- | --- |
| 滚动 tumbling | 固定长度、不重叠 | 每 5 分钟统计一次实时交易额 |
| 滑动 sliding | 固定长度、重叠滑动 | 每 1 分钟看"过去 5 分钟"在线人数 |
| 会话 session | 按静默间隔切分 | 用户在站操作一次"会话"的时长统计 |
| 全局 global | 整个流一个窗口 | 全量去重、全量统计（需自定义触发） |

**重点：事件时间 + 窗口 + 水位线，三者合起来回答的是同一个问题——"数据在物理上到达的顺序，并不等于业务上发生的顺序"。** 处理乱序的标准姿势是三层防线：watermark 决定"窗口何时关闭"，`allowedLateness` 决定"关闭后还能容忍迟到多久"，side output 接收"彻底迟到的数据"。**把窗口算对，比把窗口算快难得多**——这也是流处理工程师与批处理工程师最显著的能力分界。

## 5 公式解析：一次 Checkpoint 的代价

Checkpoint 频繁与否，直接决定吞吐与恢复时长的权衡。设：

- $D$：每秒到达的数据量（事件/秒）
- $C_{\text{int}}$：Checkpoint 间隔（秒）
- $V_s$：单算子平均状态快照大小（字节/事件）

每个 checkpoint 快照的存储量：

$$
S_{\text{ckpt}} = D \cdot C_{\text{int}} \cdot V_s
$$

- **$C_{\text{int}}$（间隔）**：Flink 默认 60 秒（`env.enableCheckpointing(60000)`）。
- **$S_{\text{ckpt}}$（单次快照量）**：间隔越长、状态越大，快照越重，对吞吐的扰动（屏障在途、快照 IO）越大。
- **权衡**：间隔太短 → 频繁快照拖慢吞吐；间隔太长 → 崩溃时需重放的数据越多，**恢复时间（recovery time）**越久。
- **实践准则**：恢复时间目标除以 $D$，估算可接受的最大间隔；一般把恢复时间控制在秒级，即可推出 $C_{\text{int}}$ 的上限——**"快照频率"是吞吐与恢复之间最直接的调节旋钮**。

**数字算例**：设业务峰值 $D = 200$ 万事件/秒、$C_{\text{int}} = 60$ 秒、单算子平均状态 $V_s = 200$ 字节/事件，则单次快照量
$$
S_{\text{ckpt}} = 2\times10^6 \times 60 \times 200 = 2.4\times10^{10}\ \mathrm{B} \approx 24\ \mathrm{GB}
$$
如果每 10 秒做一次 checkpoint，快照降到约 4 GB，但频率上去了；若把间隔放宽到 120 秒，快照又翻倍到约 48 GB，崩溃时需重放的数据同样翻倍。**这套数字把"快照频率"拧成了可量化的取舍**——内存、磁盘、恢复时间三项成本都能按公式先估出来。

## 6 术语速查表

| 术语 | 英文 | 一句话解释 |
| --- | --- | --- |
| 事件 | event | 流里的一条记录，到达即被处理 |
| 状态 | state | 算子在处理中记住的一切（累计值、窗口、去重集合） |
| 检查点 | checkpoint | 定期对全拓扑做一致快照，崩溃回滚的基准 |
| 屏障 | barrier | 注入数据流、标记快照边界的特殊记录 |
| 两阶段提交 | two-phase commit | 先预提交、checkpoint 完成后才正式提交的输出协议 |
| 水位线 | watermark | 声明"事件时间早于它就不会再来"的边界 |
| 允许迟到时间 | allowedLateness | 窗口关闭后仍能容忍的迟到时长 |
| 旁路输出 | side output | 接收彻底迟到数据的附属输出流 |
| 精确一次 | exactly-once | 每条记录恰好被处理一次、不重不丢 |

## 7 小结

- Flink 是**真流式引擎**：事件级处理、毫秒延迟，一切计算都可建模为流（批是有界流的特例）。
- 状态是流计算的核心资产，**Checkpoint**（barrier 对齐 + 分布式快照 + 重放）让状态可靠。
- **exactly-once** 靠"checkpoint 回滚 + 两阶段提交输出"，但必须是端到端各环节共同承诺。
- 四类窗口（滚动 / 滑动 / 会话 / 全局）+ 事件时间 + 水位线，支撑流式聚合的时空语义。
- Checkpoint 频率是吞吐与恢复的旋钮：$S_{\text{ckpt}} = D \cdot C_{\text{int}} \cdot V_s$。
