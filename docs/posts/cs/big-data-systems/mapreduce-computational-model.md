## 为什么从 MapReduce 开始

2026 年谈大模型，很少有人直接想起 MapReduce——但今天的整个大数据体系，几乎都从 2004 年 Google 那篇著名的论文出发。**MapReduce 不是一种具体的软件，而是一种看待"大规模计算"的方式**：与其让一台机器吃力地处理全部数据，不如把数据切开，交给一千台廉价机器并行算，再让框架替你收拾残局。<span class="marginnote">MapReduce 论文当年一发表就改变了世界：Hadoop 就是照着它开源的实现。此后 Hive、Pig、Spark 等一大批系统，本质都在回答"怎么让 MapReduce 更好写、更快跑"。</span>这个"并行 + 容错 + 隐藏复杂度"的思想，是后面讲 HDFS、YARN、Spark 的共同前提——它是本专题真正的第一块基石。

## 1 从函数式编程的两条原语说起

MapReduce 的名字暴露了它的出身：**map 与 reduce（在 Lisp 里叫 fold）是函数式编程的两条原语**，在第一级《函数》与第二级《函数式编程范式》里你已经见过它们。

**map（映射）**：把函数 $f$ 逐个施加到列表的每个元素上，得到一个等长的结果列表。它体现的是"每个元素独立地、彼此无关地变换"。
- **reduce / fold（归约）**：把列表用某个二元运算折叠成一个值，如求和 $\mathrm{sum}([1,2,3]) = 1+2+3 = 6$。它体现的是"把一堆东西合并成一个"。

<span class="marginnote">注意两个原语的内在并行性差异：map 天然可并行——一万个元素各算各的，互不打扰；而 reduce 必须把<strong>所有</strong>元素先收集到一处才能合并。这一差别正是 MapReduce 里"shuffle"阶段存在的根本原因。</span>

MapReduce 的伟大之处在于一个洞察：**现实世界里大量计算，都能拆成"先各自算，再归并"两个阶段**。词频统计、倒排索引、PageRank 的迭代、矩阵乘法……都能用这两条原语搭出来。

## 2 MapReduce 计算模型

MapReduce 把一次分布式计算抽象成两个用户自定义的函数，外加框架负责的中间过程：

**Map**：输入一个键值对，输出一组键值对。
$$
\mathrm{map}:\ (k_1, v_1) \rightarrow \mathrm{list}(k_2, v_2)
$$

**Reduce**：输入一个键和它对应的所有值的列表，输出一组新值。
$$
\mathrm{reduce}:\ (k_2, \mathrm{list}(v_2)) \rightarrow \mathrm{list}(v_2)
$$

中间的键值对，由**框架**负责按键分组（group by key），把同一个 key 的所有值收集给同一个 reduce——这一步叫 **shuffle（洗牌）**，是整个模型里框架替你做的、最耗性能也最关键的部分。

**重点：用户只需要写两个纯函数（map 和 reduce），"分发、排序、分组、容错、负载均衡"全由框架包办。** 用户不写任何网络、进程、锁代码，这正是 MapReduce 想让普通程序员也能用上分布式算力的设计初衷。

## 3 一个完整的例子：词频统计

词频统计（WordCount）是 MapReduce 世界的"Hello World"。给定若干文档，统计每个单词出现多少次。

**Map 阶段**：每个文档拆成单词，对每个单词发射 `(word, 1)`。

```
map(key=文件名, value=文档内容):
    for word in tokenize(value):
        emit(word, 1)
```

**Reduce 阶段**：框架已经把同一个 word 的所有 `1` 收集到一起，reduce 把它们加起来。

```
reduce(key=word, values=[1,1,1,...]):
    emit(word, sum(values))
```

看到没有：**map 只负责"打散"，reduce 只负责"聚合"**，单词的分组、排序、传输全部透明。换一批完全不同的数据，这两段函数的骨架几乎不变。<span class="marginnote">一个常见误解是"reduce 必须先排序才能分组"。实际上分组（group by key）不必依赖排序，但排序能让"相同 key 相邻"从而只需顺序扫描一遍；Hadoop 框架用排序实现分组，这也是为什么 shuffle 里有一轮排序。</span>

## 4 Shuffle 与 Sort：框架偷偷替你做的部分

map 输出与 reduce 输入之间那一段，是整个作业最贵的部分。框架做的动作依次是：

1. **分区（partition）**：把 map 的输出按键哈希，分成 R 份，每份对应一个 reduce 任务，例如 $\mathrm{hash}(k) \bmod R$。
2. **排序**：每份内部按键排序，使相同 key 相邻。
3. **合并与归并**：多个 map 任务输出到同一个 reduce 的中间文件，先合并（combine），再归并（merge）。
4. **拉取（fetch）**：reduce 任务从各 map 节点拉取自己那部分数据。

<span class="marginnote">中间结果会<strong>落盘</strong>：map 输出先写到本地磁盘，reduce 再从远端拉取。这一步是 Hadoop MapReduce 慢的根源之一，也是 Spark 用内存缓存解决的核心问题——后面《Spark RDD 与 DAG》会专门对比。</span>

**辨析｜易错点：** map 数不是越多越好，reduce 数也不是。map 任务数与输入分片数相等，分片过小会导致启动与调度的固定开销（每任务约毫秒到秒级）压过计算收益；reduce 数决定最终输出文件的个数，设为集群 slot 数的整数倍是常见经验，但若 key 分布严重偏斜（data skew），个别 reduce 会独揽大量数据成为瓶颈——这是分布式计算中最著名的坑之一。

## 5 容错：失败是常态，而不是例外

在大规模集群上，**某个节点随时可能宕机**——几千台机器的集群，平均故障间隔常常只有数小时。MapReduce 的容错哲学是"**重新执行（re-execute）**"：

- **map 任务失败**：在另一台机器上重新跑同一个分片。
- **reduce 任务失败**：重新跑，并且重跑前先重新拉取它的输入（map 输出还在磁盘上，按需重新读取）。
- **推测执行（speculative execution）**：当某台机器明显拖慢（straggler）时，框架在另一台机器上同时启动该任务的副本，谁先完成用谁的。

关键在于：**由于 map 输出写入了磁盘（持久化），失败后无需重算全部上游，只需重跑受影响的部分**。这是"写磁盘换来容错"的经典权衡。

## 6 公式解析：为什么它真能扛住超大规模数据

MapReduce 并行度的根基，是一个简单的除法。设输入数据总量为 $N$（字节），每个分片的大小为 $B$（字节），则 map 任务数：

$$
M = \left\lceil \frac{N}{B} \right\rceil
$$

拆成三步理解：

- **$N$（输入总量）**：整个作业要处理的原始数据大小。它决定了问题的规模。
- **$B$（分片大小）**：每个 map 任务分到的数据量。Hadoop 里默认约等于 HDFS 的一个 block（128 MB），目的有二：让分片尽量落在本地节点上（数据本地性），并让任务粒度大到"调度开销可忽略"。
- **$M$（map 任务数）**：并行任务的个数。集群若有 $C$ 个可用计算槽，理想情况下吞吐提升倍数约 $\min(M, C)$——这就是"一台机器做不完的事，一千台机器摊着做"的数量化表达。

于是整个模型的自洽性一目了然：**分片让数据可并行，磁盘让结果可恢复，按键分组让结果可归并**。三个机制合起来，构成了一个"只管写两个函数，剩下的交给规模"的计算范式。

一个常被追问的工程细节：分片大小 $B$ 与 HDFS 块大小（默认 128 MB）的关系。**分片默认取"一个块"**，让 map 任务的输入正好落在本地节点上——"数据本地性"由此而来；若分片跨越多个块，任务就要从远端拉数据，本地性受损。实践中据此有两条经验：

- **输入文件被切成 128 MB 一块，则每个块天然是一个 map 任务的输入**，文件数 ≈ map 任务数。
- **想让 map 任务更多（提高并行度）或更少（减少调度开销），靠调整分片/块大小，而不是改业务代码。**

**辨析｜易错点：** "map 越多越好"是初学者的直觉陷阱。每个 map 任务有固定的启动与调度开销（毫秒到秒级），把 1 GB 文件切成十万个 10 KB 分片，光任务调度就会淹没实际计算——**任务粒度应与"单任务计算量 ≥ 其固定开销"保持平衡**，这也是 $B$ 不设得太小的原因。

## 7 小结

- MapReduce 把大规模计算抽象成 **map（打散）与 reduce（聚合）** 两个纯函数，中间过程由框架负责。
- 形式化：$\mathrm{map}:(k_1,v_1)\rightarrow \mathrm{list}(k_2,v_2)$；$\mathrm{reduce}:(k_2,\mathrm{list}(v_2))\rightarrow \mathrm{list}(v_2)$。
- **shuffle 负责按键分组**，实现为分区 + 排序 + 拉取；它是开销与复杂度最集中的部分。
- 容错靠**重新执行**与中间结果落盘，失败是常态而不是异常。
- 并行度来自**分片**：$M = \lceil N/B \rceil$，分片数决定 map 任务数。
