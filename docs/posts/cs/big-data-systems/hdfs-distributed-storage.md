## 为什么从 HDFS 开始

上一节的 MapReduce 告诉我们"怎么算"，却还没回答一个更基本的问题：**海量数据到底存在哪里、怎么读？** 单台机器的磁盘装不下、也喂不饱上千台机器的计算。HDFS（Hadoop Distributed File System，Hadoop 分布式文件系统）就是 Hadoop 体系的数据底座：把一份大文件切成块，分散存放在集群里，再通过冗余副本保证"硬盘坏了数据不丢"。<span class="marginnote">Google 的 GFS（Google File System）论文发表于 2003 年，比 MapReduce 还早一年——先解决"数据住哪"，才能谈"数据怎么算"。</span>理解了 HDFS，MapReduce 的"数据本地性"、Spark 的"缓存"、Hive 的"表文件"，才能统统落到实地。

## 1 设计目标与前提假设

HDFS 为超大规模数据的**批式顺序读取**而设计。要理解它的每个设计，先记住四个前提：

**数据写一次、读很多次**：文件一经写入基本不再修改（append 是仅有的例外），没有随机写需求。
- **移动计算比移动数据便宜**：把计算程序送到数据所在节点，远比把 TB 级数据搬到计算节点划算。
- **硬件故障是常态**：几千台普通服务器，每天都有磁盘或节点损坏。
- **追求高吞吐，不追求低延迟**：顺序读一个大文件，HDFS 比任何传统文件系统都快；但随机读一个字节，它反而更慢。

**重点：HDFS 是"为大规模顺序读优化"的文件系统，它主动放弃了随机写和低延迟随机读——不是缺陷，而是取舍。** 这一取舍几乎决定了后面所有组件的设计立场。

## 2 架构：NameNode 与 DataNode

HDFS 采用**主从（master-slave）架构**，两种节点各司其职：

**NameNode（名字节点）**：整个系统的"大脑"，只保存**元数据（metadata）**——目录树（命名空间）、文件被切成哪些块、每个块存在哪些节点上。它不保存任何用户数据。<span class="marginnote">文件系统最重要的设计原则之一：把"数据在哪"和"数据是什么"分开。NameNode 管前者，DataNode 管后者；元数据小而热，数据大而冷，分管才能各自优化。</span>

**DataNode（数据节点）**：真正存数据的"肌肉"，负责读写本地磁盘上的数据块、向 NameNode 周期性发送**心跳（heartbeat）**与块报告（block report）。

读写流程的分工极其清晰：**客户端先找 NameNode 要"块的位置"，拿到地址后直接与 DataNode 并行传数据**——元数据路径与数据路径分离，数据不经过 NameNode，否则它早就成为瓶颈。

## 3 数据块与副本机制

HDFS 把大文件切成固定大小的**数据块（block）**，默认 128 MB，每个块默认保存 **3 个副本**，分布在**不同**的 DataNode 上。

$$
\text{副本数 } R = 3,\quad \text{块大小 } B = 128\ \mathrm{MB}
$$

副本带来三重收益：**容错**（一块坏了两块仍在，NameNode 自动安排复制补齐）、**带宽**（读文件时多个副本可并行、就近选取）、**负载均衡**（热点文件分散在多节点）。<span class="marginnote">块的概念让"文件"在分布式世界里退居次要：HDFS 的最小存储与容错单元是块，不是文件。一个 2 GB 文件 = 16 个块 = 48 份副本，分布在整片集群上——你在任何一台机器上"找不到"这个文件，但整个集群把它完整存着。</span>

## 4 文件写入与读取流程

**写入流程**（以写一个文件为例）：

1. 客户端请求 NameNode **创建文件**并拿到块分配方案（DataNode 列表）。
2. 客户端把数据流式地发给第一个 DataNode，第一个边存边转发给第二个，第二个转发给第三个——形成**流水线（pipeline）**。
3. 每写完一个块，客户端请求下一批 DataNode 继续写下一个块。
4. 全部写完，客户端通知 NameNode **关闭文件**，元数据落盘。

**读取流程**：

1. 客户端请求 NameNode：这个文件在哪些块、块在哪些节点？
2. 客户端从就近的副本开始，按块顺序读取并校验。

**辨析｜易错点：** 把副本数降到 1 省一半存储？可以，但那等于放弃容错——一块磁盘损坏就丢一块数据。副本不是"性能增强"而是"可靠性预算"：它对应公式 $1 - (1 - p)^R$（单块故障率 $p$ 下，$R$ 个副本全部损坏的概率）。副本数降到 2 甚至 1 在测试环境常见，生产环境通常保持默认。

## 5 数据可靠性：均衡、机架感知与回收站

- **机架感知（rack awareness）**：默认副本策略是"同机架两块、跨机架一块"，兼顾故障隔离（整个机架断电不丢数据）与写入带宽（同机架内复制快）。
- **块均衡器（balancer）**：定期把块在节点间挪动，消除磁盘使用不均。
- **回收站（trash）**：删除的文件先进回收站，默认保留一段时间再彻底清除，防手滑误删。
- **块校验**：每个块存 CRC 校验码，读取时校验，发现损坏自动从副本恢复。

实践中最常踩的坑，集中在 HDFS 的三处"不擅长"上，提前认清能省大量排障时间：

| 场景 | HDFS 的表现 | 正确姿势 |
| --- | --- | --- |
| 大量小文件 | 每个文件都要 NameNode 一条元数据记录，内存与 RPC 开销爆炸 | 合并成 SequenceFile / ORC，或用 HBase 等列族存储 |
| 随机写 / 追加频繁 | 几乎不支持随机写，追加也有限制 | 换 Kafka / HBase 等专为追加而生的系统 |
| 低延迟随机读 | 单字节随机读比本地文件系统慢得多 | 用缓存层（如 Alluxio）或改用内存数据库 |

**辨析｜易错点：** "HDFS 很慢"是个常见的笼统说法。准确地说，**HDFS 对"大文件顺序读"极快，对"小文件随机访问"极慢**——它慢在随机、慢在元数据压力，不慢在吞吐。拿 HDFS 的短板去和 RDBMS 的长处比，得到的结论只能误导选型。

## 6 公式解析：副本到底换来了多少可靠性

设单块在某时段内的故障概率为 $p$（很小），副本数为 $R$，则"所有副本同时损坏"导致数据丢失的概率：

$$
P_{\text{loss}} = p^R
$$

分三步拆解：

- **$p$（单副本故障率）**：一块硬盘一年的故障概率，常见量级约 $10^{-2} \sim 10^{-3}$。
- **$R$（副本数）**：故障必须**同时且独立**发生在全部 $R$ 个副本上才丢数据。$R=3$ 时，$P_{\text{loss}} \approx 10^{-6} \sim 10^{-9}$——比单盘损坏的概率低了 3 个数量级。
- **为什么"同时"是关键**：HDFS 的修复机制（检测到块坏就复制补齐）让坏块"存活"时间很短，进一步压缩了同时损坏的时间窗口。**副本是"用空间换可靠性"，这也是分布式系统里最常见的可靠性等式之一**，与第二级《概率论》里独立事件的交运算一脉相承。

## 7 小结

- HDFS 是**主从架构**：NameNode 管元数据，DataNode 管数据块，数据流不经过 NameNode。
- 文件被切成 **128 MB 的块**，默认 **3 副本**、跨节点分布，容错靠冗余。
- 写入走**流水线**，读取就近取副本；**移动计算而非移动数据**。
- 可靠性来自副本：$P_{\text{loss}} = p^R$，用空间换可靠性。
