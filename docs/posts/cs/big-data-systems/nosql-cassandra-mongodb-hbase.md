## 为什么从 NoSQL 开始

本专题最后一节，回到一个根本问题：前面讨论的表（Hive）、日志（Kafka）、键值流（Flink 状态）都绕开了关系模型，而现实中真有人用关系数据库存了二十年数据。**为什么大数据时代需要"关系数据库之外"的存储？NoSQL（Not Only SQL，不只是 SQL）不是否定关系数据库，而是承认：有些负载，关系模型并非最优解。**<span class="marginnote">NoSQL 这个标签最早是 1998 年 Carlo Strozzi 的数据库名，真正流行起来是 2009 年，指称一批"不用传统关系模型"的存储：键值、文档、列族、图。它们的共同特征是大规模水平扩展 + 宽松的一致性 + 灵活的 schema。</span>这一节以 HBase（列族）、MongoDB（文档）、Cassandra（宽列 / 分布式）为代表，把 NoSQL 的三条主线讲透。它与第二级《数据库》的关系模型、第三级《分布式系统》的 CAP 定理直接对接。

## 1 关系模型的三大"不够用"

关系数据库统治了互联网上半场，但在超大负载下暴露三个短板：

**扩展是垂直的**：加并发要换更大的机器（scale-up），横向分库分表则要业务层改造，代价高昂。
- **schema 是僵硬的**：加一列要 `ALTER TABLE` 迁移全表，而互联网产品的字段（埋点、属性）变化极快。
- **一致性是昂贵的**：事务保证在多副本、多机房下成本陡增，而很多场景并不真的需要全局强一致。

**NoSQL 的共同回应是：放弃一部分关系模型的能力（join、强事务、固定 schema），换取水平扩展（scale-out）与灵活性。** 这不是技术倒退，而是把"能省的成本省掉"——正如本专题反复出现的主题，**一切系统都是权衡的艺术**。

## 2 理论基础：CAP 定理

理解 NoSQL，绕不开 **CAP 定理**（Eric Brewer, 2000；Gilbert & Lynch 证明，2002）：分布式系统在分区（Partition，网络隔离）发生时，**一致性（Consistency）与可用性（Availability）不可兼得**。三选二：

- **C（强一致）**：任何时刻所有节点看到同一份最新数据。
- **A（高可用）**：任何请求都有响应，哪怕可能是旧数据。
- **P（分区容忍）**：网络分裂时系统仍能继续运行。

**重点：P 是必然存在的**——网络迟早会分裂，所以真正可选的是 **CP（牺牲可用性保一致，宁可停服不给错答案）**与 **AP（牺牲一致性保可用，给旧答案但不停服）**。本专题前面已见两例：ZooKeeper 是 CP，Kafka 的分区 ISR 机制也是 CP 风格；而绝大多数 NoSQL 数据库是 AP。<span class="marginnote">CAP 里的"一致性"与事务里的 ACID 一致性要分清：CAP 讲的是<strong>多副本对同一份数据的看法</strong>是否一致（线性一致性），ACID 讲的是<strong>事务内多条操作</strong>是否遵守约束。它们经常被混为一谈——这是分布式课程里最高频的混淆点之一。</span>

## 3 HBase：列族存储，Hadoop 上的实时读

**HBase** 是运行在 HDFS 之上的**列族（column-family）**数据库，专为"超大规模、低延迟随机读写"设计——它补上了 HDFS"只适合顺序读"的空缺。

**行键（row key）**：每行一个唯一键，数据按行键**排序存储**，读一行 = 一次定位。行键设计几乎决定了 HBase 的全部性能。
- **列族（column family）**：若干列的逻辑分组，同族内的列物理上存一起；族内列可以动态增加（`cf:qualifier`），schema 高度灵活。
- **架构**：一个 HMaster 管元数据与分区，无数 RegionServer 管数据；每个**region（表的一段）**自动分裂、分布到不同服务器，实现水平扩展。
- **存储层**：写入先落**内存（MemStore）+ 日志（WAL）**，再定期刷成 HFile 落 HDFS；读时先查内存再查文件。

**辨析｜易错点：** HBase 更新是"**逻辑覆盖、物理追加**"：同一行键反复写，旧版本仍留在 HFile 里，直到合并（compaction）才真正清除。所以 HBase 的行数与"物理存储"可能差异巨大，**row key 设计不当（如随机 ID 直接做行键）会造成热点**——单一 region 被集中读写，集群其他地方却闲置。

## 4 MongoDB：文档模型，开发者友好

**MongoDB** 是**文档（document）**数据库：每条记录是一份 JSON 风格的文档，字段结构自由。

```json
{ "_id": "u1001", "name": "李雷", "orders": [{"id": "o1", "amt": 99}] }
```

- **字段自由**：不同文档可以有不同的字段，产品迭代无需迁移表。
- **内嵌 vs 引用**：关联数据可**内嵌**（一条文档全放下）或用 **$lookup** 引用查询。内嵌换来"一次读全"，换来的是更新嵌套数组的麻烦。
- **分片（sharding）**：按 shard key 把集合切分到多台服务器，实现水平扩展。
- **一致性与分布式事务**：单文档操作是原子的（跨文档事务 4.0 后支持但成本高）；副本集默认读主副本（强一致读），也可配读从副本（更快但可能读到旧数据）。

<span class="marginnote">MongoDB 的成功证明：对"schema 频繁变化 + 嵌套自然表达 + 开发者效率优先"的应用，文档模型的体验远超关系模型。但它也牺牲了 join 与跨文档事务的表达力——"用 document 还是 table"，本质是"表达力 vs 约束"的取舍。</span>

## 5 Cassandra：无主架构，AP 的极致

三种 NoSQL 的定位差异，用一张表总结最清楚：

| 维度 | HBase | MongoDB | Cassandra |
| --- | --- | --- | --- |
| 数据模型 | 列族（宽表） | 文档（JSON） | 宽列（Dynamo 风格） |
| 架构 | 主从（HMaster + RegionServer） | 分片（可配主从） | 无主（对等） |
| 强一致倾向 | CP（读主副本） | 默认 CP，可配 | AP（一致性级别可调） |
| 存储底座 | HDFS（也可独立文件系统） | 本地磁盘 + WiredTiger | 本地磁盘（自管副本） |
| 典型定位 | 实时读超大数据量 | 开发者友好的通用存储 | 跨机房高可用写密集 |

**Cassandra** 是**宽列（wide-column）**数据库，源于 Amazon Dynamo 论文 + Bigtable 的数据模型，把"可用性"推到极致：

- **无主（peer-to-peer）**：所有节点地位平等，任何节点都能读写，无单点、无 master。
- **一致性级别（consistency level）**：读写时可指定"需要多少副本确认才返回"，如 `QUORUM`（多数派）、`ONE`（一个）、`ALL`。调它就是在 CAP 上拨动旋钮——**用一次 API 调用显式选择 C 与 A**。
- **对等分片**：数据按分区键一致性哈希分布，天然跨机房、跨区域复制。
- **最终一致**：多副本异步收敛，读修复（read repair）与反熵（anti-entropy）保证最终一致。

## 6 公式解析：Quorum 读写的乘法一致

Cassandra 的一致性通过调节读写级别实现。设副本总数为 $R$（数据存 $R$ 份），写确认数 $W$、读确认数 $w$……更准确地：写级别 $W$、读级别 $R_d$。要保证"读到的至少包含最新写入"，只需

$$
W + R_d > N
$$

- **$N$（副本总数）**：一份数据复制到几个节点。
- **$W$（写级别）**：几个副本确认写入成功才返回。$W$ 越大越安全越慢。
- **$R_d$（读级别）**：读取时至少要读几个副本。若 $W + R_d > N$，则"写覆盖的副本"与"读触及的副本"**必然有交集**，读端能通过版本号挑出最新值。
- **经典配置**：$N=3,\ W=2,\ R_d=2$ 时 $2+2>3$，读多写多，**在"无主"架构下依然能读到最新数据**——这就是无主系统"用多数派数学替代单主"的原理。它与 ZooKeeper 的 $2f+1$ 是同一个数学根源：**让任何两次决策必然有公共见证者**。

## 7 小结

- **NoSQL = 不止 SQL**：关系模型在超大规模、schema 多变、开发者效率上不够用，NoSQL 以"放弃 join / 强事务 / 固定 schema"换取水平扩展。
- 理论底座是 **CAP 定理**：网络分区必然存在，真正可选的是 **CP**（ZooKeeper、HBase 主写）与 **AP**（Cassandra 无主）。
- **HBase**：列族 + 行键排序 + HDFS，补 HDFS 的实时读写短板，row key 设计决定命运。
- **MongoDB**：文档模型 + 分片，开发者友好，牺牲 join 与跨文档事务。
- **Cassandra**：无主 + 一致性级别拨盘，AP 极致；$W + R_d > N$ 的多数派数学与 ZooKeeper 同源。

这是本专题的最后一篇。回望这 13 篇：从 MapReduce 的"算"、HDFS 的"存"、YARN 的"调"，到 Spark 的内存计算与声明式 SQL，再到 Kafka、ZooKeeper、Flink、Hive 与 NoSQL——**每一个系统，都是"存储 / 计算 / 一致性"三角权衡的一次具体切片**。带着这套世界观，你在第三级《分布式系统》与第四级《大规模机器学习系统》里遇到的每一个设计，都会显得无比眼熟，因为它们讨论的，正是同一批权衡的更精细版本。
