# 安全模型与访问控制

## 为什么从访问控制开始

加密解决的是「数据在传输或存储时被偷看」的问题，但它对已授权的人毫无约束——Alice 能读文件，不等于 Alice 可以删文件；root 能装驱动，不等于任何进程都该有 root 权限。**访问控制（access control）**回答的是另一类更朴素的问题：**在系统内部，谁、能对什么、做什么。** 它是信息安全的「第一道门」，也是我们整篇《系统安全》的第一个话题：先立住「主体—客体—权限」这个三角，后面讲的认证、沙箱、加固全部是在为它服务。<span class="marginnote">访问控制与认证不同：认证（authentication）回答「你是谁」，访问控制回答「你能做什么」。先认证、后授权，这个顺序本身就是一条安全原则。密码学专题里的口令与多因子认证见《身份认证机制》一篇。</span>

## 1 主体、客体与访问权：访问矩阵

系统的保护状态可以用一张表来精确描述——这就是 **Lampson 访问矩阵（access matrix）**，由巴特勒 · 兰普森（Butler Lampson）在 1971 年提出。

把系统中的一切对象分成两类角色：

**主体（subject）**：主动发起操作的实体，通常是进程，其背后是用户。
**客体（object）**：被访问的被动资源，包括文件、目录、内存段、设备、套接字等。

访问矩阵 $M$ 的每一行对应一个主体，每一列对应一个客体，单元格 $M[S, O]$ 就是**主体 $S$ 对客体 $O$ 拥有的权限集合**：

$$M[S, O] \subseteq R, \qquad R = \{ \text{read}, \text{write}, \text{execute}, \text{append}, \text{delete}, \text{own}, \ldots \}$$

例如 $M[\text{alice}, \text{/tmp/report}] = \{\text{read}, \text{write}\}$，表示 Alice 对这份报告只有读写权，没有删除权。

访问矩阵只是理论模型，实际系统从不存一整张 $M$，而是按行或按列拆开：

- **按列存**，得到**访问控制列表（ACL）**：每个客体挂一张「谁可以动我」的清单。文件系统权限就是典型的 ACL 实现。
- **按行存**，得到**能力列表（capability list）**：每个主体握着一串「我可以动谁」的凭证。<span class="marginnote">ACL 是「客体视角」：好查、好审计，但想知道某个用户所有权限要扫全表；能力列表是「主体视角」：进程可直接出示能力，但能力一旦泄漏就成了「捡到钥匙就能开门」。两种视角各有代价，Linux 的 file capabilities、Windows 的句柄都暗含能力思想。</span>

## 2 自主访问控制 DAC 与强制访问控制 MAC

按「谁有权改权限」来分，访问控制有两大家族。

**自主访问控制（DAC，Discretionary Access Control）**：客体的属主可以自行决定谁有权限——Linux 里 `chmod`、Windows 里修改文件 ACL，都属于 DAC。它的关键词是「自主」：属主说了算。

**强制访问控制（MAC，Mandatory Access Control）**：权限由系统统一的安全策略决定，属主也无权更改。每个主体与客体都打上**安全标签（label）**，是否允许访问只由标签的偏序关系决定。<span class="marginnote">军事背景下的「秘密 / 机密 / 绝密」就是安全标签，签发密级的是系统策略而非文件属主——这正是 MAC 与 DAC 的本质差别。<strong>DAC 防不住属主自己泄密，MAC 才能表达「即使属主同意，低密级者也不能读」。</strong></span>

MAC 最著名的两个模型都来自上世纪 70 年代：

**Bell–LaPadula 模型（简称 BLP）**面向**机密性**：谁都不许把秘密往上或往下流。其核心是「不向上读、不向下写」——低密级者不许读高密级文件，高密级主体也不许把高密级内容写进低密级文件（否则秘密就被「降级」泄露出去了）。下一节专门拆解它的两条性质。

**Biba 模型**面向**完整性**，规则恰好相反：「不向上写、不向下读」。低完整性数据不许写入高完整性客体，以免污染；这也解释了为什么「只读的干净数据」不可信——完整性关注的是「数据会不会被改坏」，而非「机密会不会被偷」。

## 3 基于角色的访问控制 RBAC

BLP 的标签模型适合机密系统，但对普通企业来说太僵硬：把「会计」「医生」「客服」按角色管理，才符合组织现实。**RBAC（Role-Based Access Control）**因此成为企业中应用最广的模型，由美国国家标准 NIST（Ferraiolo & Kuhn，1992；Sandhu 等人的 RBAC96 体系）规范。

RBAC 的核心思想：**权限不直接授予用户，而是授予角色，用户只拥有角色。** 用户与权限之间多了一层「角色」间接层：

$$(U \to R) \qquad (R \to P) \qquad \Longrightarrow \qquad U \text{ 经角色继承 } P$$

角色带来两个重要能力：

- **职责分离（Separation of Duties，SoD）**：让「发起付款」与「审批付款」分属不同角色，防止单人作案。
- **权限随角色变化**：员工调岗只改角色，不用逐条改权限——权限管理从「逐人」变成「逐角色」，复杂度骤降。<span class="marginnote">RBAC 还有一个变体叫 ABAC（属性访问控制），用「用户属性 + 客体属性 + 环境属性」的布尔规则（如「工作时间 9:00—18:00 且部门=财务」）来做细粒度判断，云厂商 IAM 的 Policy 就是 ABAC 语言。</span>

三种模型的取舍可以用一张表概括：

| 模型 | 谁定权限 | 粒度 | 典型场景 | 核心短板 |
| --- | --- | --- | --- | --- |
| DAC | 客体属主 | 用户级 | Linux 文件权限、Windows ACL | 防不住属主泄密 |
| MAC | 系统策略（标签） | 标签级 | 军事/政府机密系统 | 僵硬、难适配组织分工 |
| RBAC | 角色 | 角色级 | 企业 ERP、云 IAM | 角色爆炸、静态绑定 |

**重点：** 三者的本质差别不在「有没有权限表」，而在「**谁拥有修改权限的权力**」——DAC 交给属主，MAC 收归系统，RBAC 委托给角色管理员。选型时先回答「这个系统的保护对象是机密、完整性还是组织合规」，再决定用哪套模型。

## 4 公式解析：Bell–LaPadula 的两条安全性质

BLP 用两个公式把「保密」变成可判定的规则。设主体的安全级别为 $C(s)$，客体的安全级别为 $C(o)$，且级别之间存在全序（如公开 < 秘密 < 机密 < 绝密）：

$$
\text{read 允许 } \iff C(s) \ge C(o) \qquad \text{（简单安全性质：不向上读）}
$$

$$
\text{write 允许 } \iff C(o) \ge C(s) \qquad \text{（*-性质：不向下写）}
$$

- **第一步，读规则**：主体要能读客体，其级别必须**不低于**客体级别。这就是「不向上读」——低密级的人读不了高密级文件。
- **第二步，写规则**：主体要能写客体，客体级别必须**不低于**主体级别。高密级主体只能写同密级或更高密级的文件，禁止把绝密内容写进公开目录——这就是「不向下写」。
- **第三步，合起来看**：两条规则互成镜像，共同保证**信息只在高处流、不在低处流**，即**无干扰（noninterference）**。注意两条规则的蕴含方向相反，初学者常把方向记反：读向下兼容，写向上兼容，中间用「主体级别必须落在客体级别的哪一侧」来判断。

**辨析｜易错点：** BLP 防的是**机密泄漏**，不防**完整性破坏**——一个高密级主体可以合法地把高密级文件内容覆盖进高密级文件里的垃圾数据，BLP 对此毫无意见。Biba 模型才管这件事，二者是同一枚硬币的两面。

## 5 从模型到系统：Linux 与 Windows 里的落地

模型的最终价值在于落地：

- **Linux 的经典权限**是 DAC：文件记录属主（owner）、属组（group）、其他（other）三类身份，每类有读 r、写 w、执行 x 三位。这正是一张压缩到极致的 ACL。
- **Linux 的能力模型（capabilities）**把 root 的超级权限拆成约 40 项细粒度能力（`CAP_NET_BIND_SERVICE`、`CAP_DAC_OVERRIDE` 等），容器与 systemd 用它实现最小权限。
- **SELinux / AppArmor** 在 Linux 之上实现 MAC：每个进程与文件带类型标签，策略文件规定标签间能否访问——这是「Bell–LaPadula 思想」的现代工程化。<span class="marginnote">这些机制在《操作系统》专题有更底层的展开：访问矩阵与权限位见 os/access-matrix 与 os/os-permission-model；MAC/DAC 的经典论文式辨析见密码学专题的 dac-mac 一篇。</span>
- **Windows** 用安全标识符 SID 与 ACL 记录权限，并用**完整性级别（integrity levels）** 实现类 MAC 的分层：普通进程（低完整性）无法写高完整性进程的内存。

**重点：** 安全模型提供的不是某一招，而是一套思考框架——先问「谁是主体、谁是客体」，再问「用什么策略决定权限」，最后问「策略在哪里强制、失败时默认拒绝还是默认放行」。把这三问刻进习惯，就抓住了系统安全的骨架。

常见术语速查：

| 术语 | 含义 |
| --- | --- |
| 主体 / 客体 | 主动发起操作者 / 被访问的资源 |
| ACL | 按客体挂权限清单（客体视角） |
| Capability | 主体持有的权限凭证（主体视角） |
| label | 主体或客体上的安全标签 |
| SoD | 职责分离：关键操作拆给不同角色 |
| 最小权限 | 只授予完成工作必需的最小权限 |

## 6 小结

- 访问控制是**系统内部**的第一道防线，与「你是谁」的认证相对、互补。
- **访问矩阵** $M[S,O]$ 是理论基石，工程上被拆成 **ACL**（按客体）与**能力列表**（按主体）。
- **DAC** 由属主决定权限；**MAC** 由系统策略决定，属主无权更改。
- **BLP** 管机密性（不向上读、不向下写），**Biba** 管完整性（规则相反），二者共同构成 MAC 的经典双子。
- **RBAC** 用「角色」间接层把权限管理从逐人变为逐角色，并支持职责分离。
- Linux、Windows、容器、云 IAM 都是这些模型的工程变体——最小权限原则贯穿始终。

在下一节，我们将回答「主体是谁」：口令、生物特征与多因子认证如何把用户的身份可靠地绑定到进程上——这就是**身份认证机制**。
