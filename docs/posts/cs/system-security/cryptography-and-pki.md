## 为什么从密码学开始

系统安全的四道防线是**防偷听、防篡改、防伪造、防抵赖**，而密码学是唯一能同时提供这四者的数学工具。<span class="marginnote">密码学的系统知识（从古典密码到后量子）在密码学与信息安全专题完整展开；这里只做「系统安全够用」的横向综述：加密、哈希、签名三大件，以及把公钥绑到人身上的 PKI。</span>在《系统安全》这一篇，我们不重复算法的内部构造，而是看它们如何组装进系统：TLS 握手里谁加密谁签名？SSH 凭什么信任主机？证书过期后浏览器凭什么弹红屏？答案都指向同一块基石——**PKI**。

## 1 三大密码学原语：加密、哈希、签名

系统安全只依赖三个「零件」：

**对称加密**：AES 等。同一把密钥加密解密，快，用于批量数据。混淆与扩散保证「改变一个明文字节，密文面目全非」。
- **非对称加密**：RSA、ECC 等。公私钥成对，公钥公开、私钥私有。慢，用于密钥交换与签名。
- **哈希**：SHA-256 等。任意长度输入 → 定长摘要，单向、抗碰撞。「文件指纹」与「口令存储」全靠它。
- **数字签名**：私钥签名、公钥验签。签名是对哈希摘要的非对称运算，保证**完整性与不可抵赖性**。<span class="marginnote">关键区分：加密保护机密性，签名保护完整性与真实性。<strong>加密 + 签名是两个正交操作，缺一不可</strong>——只加密不签名，中间人可以替换密文；只签名不加密，任何人都能读到内容。TLS、PGP、JWT 的构造差异很大程度来自「谁加密、谁签名、顺序如何」。</span>

四个原语各自回答一种安全目标，对照如下：

| 原语 | 保护目标 | 是否保密 | 速度 | 密钥形态 |
| --- | --- | --- | --- | --- |
| 对称加密（AES） | 机密性 | 是 | 快 | 单把共享密钥 |
| 公钥加密（RSA/ECC） | 密钥分发 | 是 | 慢 | 公私钥对 |
| 哈希（SHA-256） | 完整性 | 否 | 快 | 无密钥 |
| 数字签名 | 真实性、不可抵赖 | 否 | 慢 | 私钥签、公钥验 |

**辨析｜易错点：** 哈希不是「加密」——加密可逆（有密钥就能解密），哈希单向不可逆；把口令哈希说成「加密口令」是常见口误，会误导人相信它可被解密还原。

## 2 混合加密：为什么 TLS 两者都用

非对称加密虽安全，但比对称慢几个数量级；对称加密虽快，但密钥怎么在公网上分发？工程答案是**混合加密（hybrid encryption）**：

$$
\text{会话密钥 } K_{sym} \xleftarrow{\text{随机}} \quad \text{用 } K_{sym} \text{ 对称加密数据},\quad \text{用公钥非对称加密 } K_{sym}
$$

- **第一步，生成会话密钥**：客户端随机生成一把对称密钥 $K_{sym}$。
- **第二步，加密数据**：消息用 $K_{sym}$ 做 AES 加密——又快又密。
- **第三步，护送密钥**：$K_{sym}$ 本身用服务器公钥加密后随密文一起发送——只有持私钥的服务器能解开。
- **第四步，看意义**：对称加密的性能 + 非对称加密的密钥分发，各取所长。这正是 TLS 握手「密钥交换 + 记录加密」两个阶段的本质分工。

**重点：** 混合加密的关键前提是「客户端真的知道服务器公钥」——这一步若被偷换（中间人伪装服务器），后面一切加密都白搭。**公钥本身的可信度**，正是 PKI 要解决的问题。

## 3 PKI：把公钥绑到真实身份上

公钥加密暴露了一个悖论：公钥人人可见，但「这把公钥属于你声称的那个人吗」？伪造者可以生成自己的公私钥对，然后把假公钥当「官方公钥」塞给你——**中间人攻击（MITM）**由此而生。

**公钥基础设施（PKI，Public Key Infrastructure）**就是「公钥确权」的工程体系，核心是**数字证书（certificate）**：一个受信任的**证书颁发机构（CA）**用自己的私钥，对「公钥 + 持有者身份信息 + 有效期」签名，形成证书：

$$
\text{cert} = ( \text{subject}, \text{subjectPublicKey}, \text{CA}, \text{有效期}, \text{extensions} ) + \text{CA 私钥签名}
$$

验证一条证书链时，浏览器逐级向上：证书上的签名由上级 CA 的公钥验，上级证书又由更上级验……直到内置的**根证书**（root CA）。这个「证书 → CA → 根证书」的链条就是**信任锚（trust anchor）**。<span class="marginnote">X.509 是证书的标准格式，v3 的扩展字段承载用途限制（密钥用途、扩展密钥用途、SAN 域名）。CRL 与 OCSP 负责吊销：证书可能因私钥泄露提前作废，浏览器查询 CRL/OCSP 判断「这张证书现在是否仍有效」。这些细节在密码学专题 certificate-chains-ca 与 certificate-revocation-crl-ocsp 两篇展开。</span>

## 4 公式解析：CA 的签名与验签

把「证书是真的」翻译成数学，就一句话：

$$
\sigma = \text{Sign}_{sk_{CA}}(H(\text{公钥}\|\text{身份信息}\|\text{有效期}))
$$

- **第一步，摘要**：把证书的核心字段（公钥、身份、有效期）拼起来，算哈希 $H(\cdot)$，得到一个定长摘要——签名不是对整份证书签，是对摘要签，省算力且足够。
- **第二步，签名**：CA 用其私钥 $sk_{CA}$ 对摘要做签名运算（RSA 或 ECDSA），得到签名值 $\sigma$，连同公钥一起写进证书。
- **第三步，验签**：任何人拿到证书，先用证书里的公钥字段算同一摘要，再用 CA 的公钥验证 $\sigma$ 是否对应该摘要。验签成功 ⟹ 证书内容未被篡改、且确实由该 CA 签发。
- **第四步，看信任链条**：验签只能证明「CA 签过这张证书」，CA 的可信度来自其内置于操作系统/浏览器中的根证书。**信任不是数学给出的，而是社会安排的**——PKI 把「我信谁」从数学问题变成了「我信哪个根 CA」的社会问题，这正是 CA 被攻破（如 DigiNotar 事件）时整个体系的软肋。

## 5 PKI 的工程形态与常见坑

- **Web/TLS**：证书绑域名，浏览器校验域名（SAN）、有效期、吊销状态、签发链。HTTPS 三件套：加密、完整性、认证，缺一不可。
- **代码签名**：软件发布者对二进制签名，杀毒软件与系统校验「这份软件真的来自该开发者且未被篡改」。
- **SSH**：第一次连接时提示信任主机密钥（TOFU，信任首次使用）；更严谨的用 SSHFP 或证书签主机密钥。
- **邮件（PGP/S/MIME）**：Web of Trust 与 CA 两种不同哲学，前者「人人可认证」，后者「集中权威」。

**辨析｜易错点：** 证书有效 ≠ 连接安全。以下任何一个都会让 HTTPS 形同虚设：证书域名不匹配（SAN 不含目标域名）、CA 被攻破后签发伪造证书、用户点击「继续访问」绕过警告、私钥泄露却未及时吊销。**PKI 的强度是「最弱一环」的强度**——证书体系再严密，也架不住用户点掉红屏。

以访问 `https://example.com` 为例，把「证书链」完整走一遍：

1. 服务器送来自己的叶子证书（公钥 + 域名 + 有效期 + 签名）。
2. 浏览器发现签名的签发者是某中间 CA，去查中间 CA 证书。
3. 中间 CA 的证书又由根 CA 签发，根 CA 已在浏览器信任库里——链条闭合。
4. 逐级验签 + 检查 SAN 含 `example.com` + 查 OCSP 确认未吊销，全过才显示小锁。

**重点：** 一旦某个中间 CA 的私钥泄露（如 2011 年 DigiNotar 事件，攻击者用它签发了 `.google.com` 的假证书），浏览器信任库会把该 CA 整个拉黑——**信任是「可撤销的」**，这正是 PKI 与「永久信任」的 Web of Trust 不同的地方。

## 6 小结

- 系统安全的密码学底座是三件套：**对称加密、哈希、数字签名**，再加**公钥加密**做密钥分发。
- **混合加密**用非对称护送会话密钥、对称加密数据，是 TLS 等协议的共同结构。
- **PKI** 用 CA 签名把「公钥 ↔ 身份」绑定成**数字证书**，信任锚是内置根证书。
- 证书验证链路 = **验签 + 查有效期 + 查吊销 + 核对域名**；任一环失守，加密归零。
- 信任的最终归属是社会安排（根 CA），而非纯数学——这是 PKI 的力量与软肋。
- 工程形态有 **TLS/代码签名/SSH/PGP** 四种落地，各自对「谁可信」做出不同的取舍。

一个直观的数值例：2048 位 RSA 签名约需毫秒级，而 AES 加密同样数据只需其千分之一的时间——所以混合加密用「RSA 护送 256 位 AES 会话密钥」，把昂贵运算限制在密钥交换这一小步上，这是性能与安全平衡的典范。

术语速查：

| 术语 | 含义 |
| --- | --- |
| 对称 / 非对称加密 | 同一密钥 / 公私钥成对 |
| 混合加密 | 非对称护送会话密钥 + 对称加密数据 |
| 哈希 | 任意长输入 → 定长单向摘要 |
| 数字签名 | 私钥签名、公钥验签 |
| 数字证书 | 公钥 + 身份 + CA 签名的绑定 |
| 信任锚（根证书） | 浏览器/系统内置的可信 CA |
| CRL / OCSP | 证书吊销清单 / 在线吊销查询 |
