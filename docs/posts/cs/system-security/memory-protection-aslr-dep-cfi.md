## 为什么从内存保护开始

上一节我们看到了经典的栈溢出四步走：**算偏移、猜地址、跳 shellcode、夺执行流**。这一节的主题就一句话——**让这四步每一步都变难**。<span class="marginnote">这里讲的机制都是「基于编译器 + 操作系统」的系统级防护，与上节的漏洞原理、与后面《漏洞利用与缓解技术》的绕过手法是一体的三幕剧：攻、防、再攻。</span>**内存保护机制**是现代系统安全最重要的前沿防线：它不消灭漏洞，而是让「有漏洞 ≠ 可利用」。ASLR、DEP（NX）、栈金丝雀、CFI——每个名字都对应一次「攻击者下一步被堵死」。

## 1 栈金丝雀：把返回地址埋上雷

**栈金丝雀（stack canary）**由 Crispin Cowan 于 1998 年提出（StackGuard），是现代编译器（GCC `-fstack-protector`、MSVC `/GS`）的内置防线。

原理极简：函数入口在返回地址**下方**放一个**随机哨兵值（canary）**，函数返回前校验它是否被改动：

```
[局部变量 buf][金丝雀][帧指针][返回地址]      ← 金丝雀挡在溢出路径上
```

溢出要覆盖返回地址，**必须先从金丝雀身上踩过去**。
- 金丝雀值随机且含 `\0`，攻击者无法预知也无法在字符串载荷里嵌入——`strcpy` 一遇到 `\0` 就停，天然绕不开它。
- 一旦金丝雀被改，函数在返回前**检测到并中止**（abort），返回地址根本不会被取出。

**辨析｜易错点：** 金丝雀防的是「连续越界覆盖返回地址」，不是「一切溢出」——它拦不住堆溢出、拦不住「精确在返回地址前停手」的二次写、也拦不住攻击者先**读取**金丝雀值（信息泄漏漏洞能把它偷走）。它的价值是让「计算偏移」变成「还得先过随机雷区」。<span class="marginnote">金丝雀得名于煤矿里的金丝雀：矿工带它下井，瓦斯泄漏时鸟先死，人来得及逃。<strong>栈金丝雀就是程序里那只「先死的鸟」</strong>——它被踩坏时，程序还没执行到返回地址。</span>

## 2 DEP / NX：让数据不能当代码

经典 shellcode 放在数据里（栈上），等 CPU 跳进去执行。**DEP（Data Execution Prevention）/ NX（No-eXecute）**直接釜底抽薪：**标记「不可执行」的内存，CPU 拒绝在其中取指。**

硬件层：AMD 2003 年引入 NX 位（Intel 的 XD），页表里加一个「可执行」位。
- 操作系统层：Windows 从 XP SP2（2004）起默认开 DEP，Linux 的 `W^X` 策略（写与执行互斥）同此思想——**内存要么可写、要么可执行，不能两者兼得**。
- 栈、堆、数据段默认**不可执行**，shellcode 放在栈上也没人敢跳——一跳就是非法指令（segfault）。

**重点：** DEP 直接杀死了「栈上放 shellcode」这种最朴素的利用，逼着攻击者转向「代码重用」（复用程序里已有代码，见下一节 ROP）——**DEP 是一次性改变攻防版图的机制**。<span class="marginnote">JIT（即时编译）是 NX 与性能的经典矛盾：JIT 缓冲区需要「可写（生成代码）又可执行（运行代码）」。<strong>「可写可执行」的 JIT 区域恰好是攻击者最爱的着陆点</strong>——现代 JIT 用「写保护 + 刷缓存」尽量缩小这个窗口。</span>

## 3 ASLR：让地址变成随机数

**ASLR（Address Space Layout Randomization）**把每个进程的**布局随机化**：栈基址、堆基址、共享库加载地址、甚至程序自身（PIE）每次启动都在不同位置。攻击者上一节要「猜地址」——ASLR 让地址**不可猜**。

Linux 自 2001 年起（PaX/OpenBSD 率先部署，主流的 exec-shield/PIE 演进），Windows 自 Vista（2007）起默认开启。打开一次进程，栈从哪开始、`libc` 落在哪，都是当次启动掷骰子的结果。

**组合的意义：** 单看金丝雀是「踩雷」，单看 NX 是「不让跑」——两者靠地址确定性配合（shellcode 在栈上的固定位置）才能被绕过；ASLR 打掉的是**确定性本身**。防护因此形成纵深：

金丝雀：让**覆盖返回地址**变难（要猜雷）。
- DEP：让**数据当代码**变难（栈不可执行）。
- ASLR：让**定位目标**变难（地址每次随机）。<span class="marginnote">ASLR 的敌人是「信息泄漏」：一个能读内存的 bug 就把随机化归零。<strong>攻击者先泄漏地址、再精心构造利用，是 2010 年代漏洞利用的标准剧本</strong>——这也是「纵深防御」为什么总强调多个独立机制的原因。</span>

## 4 CFI：约束程序只能去它该去的地方

前面的机制挡「shellcode」，但挡不住「代码重用」。**CFI（Control-Flow Integrity）**由 Abadi 等人于 2005 年提出，是防代码重用的理论方案：**程序的合法控制流图（CFG）在编译期确定，运行期所有间接跳转（jump/call/ret）都必须落在合法目标集合内。**

- **粗粒度 CFI**：把间接跳转的目标按「同类型」分组（如「所有合法函数入口」），检查目标是否在组内。
- **细粒度 CFI**：为每条边维护精确目标集，安全性更强但开销更大。
- 工程上的代表作是 **Shadow Stack（影子栈）**：另存一份「真正的返回地址栈」，函数返回时与影子栈比对，不一致即报——这是对「覆盖 ret」的直接封杀，已被 Intel CET 硬件化。

CFI 的实际价值与局限都在「粒度」：粒度越细越安全、开销越大；实现常妥协在「能挡常见利用、放掉部分边」。**CFI 不是银弹，而是把「任意跳」降级为「只能跳到很接近合法目标的地方」**。

## 5 公式解析：金丝雀校验的一次快进

把「金丝雀挡攻击」压缩成一条判定式。设 $c$ 为函数入口写入的金丝雀，$c'$ 为返回前读回的值，$\text{overwrite}(p)$ 表示输入 $p$ 触碰到了返回地址（必然先改写 $c$）：

$$
\text{return 正常执行} \iff (c' = c) \wedge \text{canary 未被触碰}
$$

$$
\text{overwrite}(p) \text{ 成功} \iff \text{攻击者事先得知 } c, \text{ 且在载荷 } p \text{ 中写回原值 } c
$$

- **第一步，看第一行**：返回值前程序取 $c'$ 与入口值 $c$ 比较，不等则立即中止。金丝雀夹在缓冲区和返回地址之间，任何「一路写上去」的溢出必然先改 $c$——于是 $c' \neq c$，函数在取到返回地址前就死了。
- **第二步，看第二行**：唯一的绕过是攻击者**预知 $c$ 并在载荷中精确复写**。而 $c$ 每进程随机、含 `\0`、通常从操作系统熵源取样——预知它需要一次信息泄漏漏洞。
- **第三步，看整条逻辑**：金丝雀把一个「确定性的偏移问题」升级成「还要先破解随机数」的问题。叠加 NX（数据不可执行）、ASLR（地址不可知）、CFI（跳转被约束），攻击者每一步都必须「先泄漏、再绕过、还要精确」，纵深由此形成。

## 6 小结

- **金丝雀**：随机哨兵挡在缓冲区与返回地址之间，覆盖必被察觉。
- **DEP/NX（W^X）**：数据段不可执行，shellcode 无处安放，逼攻击者转向代码重用。
- **ASLR**：栈/堆/库地址每次启动随机化，让「猜地址」失效，是最强的「信息」防御。
- **CFI + 影子栈**：约束间接跳转目标，Intel CET 已把影子栈硬件化。
- 四个机制**彼此独立、互为纵深**：任一被单独绕过，都还有下一道。攻防由此进入「信息泄漏」的军备竞赛。

在下一节，我们将穿上攻击者的手套，看这些防护如何被绕过：**漏洞利用与缓解技术**——ret2libc、ROP、堆利用是如何在「不可执行、不可预知、不可任意跳」的世界里继续找到出路。
