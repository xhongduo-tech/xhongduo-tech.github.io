## 为什么从协议开始

上一节我们把「你是谁」的证据体系讲透了，但证据要在**不可信的网络上**传递：口令不能明文发送，凭证不能到处复制，第三方应用不该看到你的主口令。**认证与授权协议**就是把上一节的证据，编码成能在网络中安全流动的**票据、令牌与断言**。<span class="marginnote">同一枚「信任」的三种工程形态：Kerberos 属于企业内部网络的对称密钥体系；OAuth 是「委托授权」的语言；SAML 是「断言传递」的 XML 语言。它们的战场不同——理解「在什么场景用哪个」，比记住每个字段更重要。</span>

## 1 Kerberos：企业内网的单点登录

Kerberos 源自 MIT 雅典娜计划，核心是**可信第三方**模型：客户端、服务、密钥分发中心（KDC）三方，两两之间只共享会话密钥，从不共享长期口令之外的多余秘密。KDC 拆成两级：

**AS（认证服务器）**：验证用户身份，颁发**票据授权票据（TGT）**——「我是谁」的长期通行证。
- **TGS（票据授权服务器）**：用 TGT 换取**服务票据（ST）**——「我能用哪个服务」的短期凭证。

一次完整流程：用户口令派生密钥 → AS 验证并发 TGT（带时间戳与生命周期）→ 用户向 TGS 出示 TGT 换 ST → 用 ST 访问服务。此后访问其他服务只需再换 ST，无需重新输口令——这就是**单点登录（SSO）**。时间戳与生命周期使票据**防重放**：30 秒前的 TGT 过期作废。<span class="marginnote">Kerberos 的密码学细节（Needham-Schroeder 的后继、票据内容、跨域票据）在密码学专题 kerberos 一篇有逐步拆解；Windows Active Directory 与 macOS 企业登录都在用它。</span>

**辨析｜易错点：** Kerberos 是**对称密钥**体系——密钥由一个 KDC 统一掌管，因此 KDC 就是信任的「单点」：KDC 被攻破 = 整个域的凭证失控。这就是它与 OAuth「去中心化证书」路线的本质差别。

## 2 OAuth 2.0：把授权交给第三方应用的「代客泊车」

你在网页上「用 Google 账号登录」某第三方网站时，用的就是 **OAuth 2.0（RFC 6749）**。它的设计目标不是认证，而是**委托授权（delegation）**：让第三方应用**不接触你的口令**，也能获得访问你资源的**限定权限**。

四个角色：

**资源所有者（resource owner）**：也就是你。
- **客户端（client）**：想访问你资源的第三方应用。
- **授权服务器（authorization server）**：负责认证你、颁发令牌，如 Google、GitHub。
- **资源服务器（resource server）**：持有你的数据，按令牌放行。

核心流程（授权码模式）：

1. 客户端把用户重定向到授权服务器，附上重定向地址与申请的权限范围（scope）。
2. 用户在授权服务器登录、同意授权。
3. 授权服务器把用户带回客户端，附上**授权码（authorization code）**。
4. 客户端用授权码 + 自己的密钥，在后台换取**访问令牌（access token）**。
5. 之后客户端凭令牌访问资源服务器；令牌过期后用**刷新令牌（refresh token）**续期。

**重点：** 访问令牌是**限定范围、限定时长**的委托凭证——它不等于「你是你」，只等于「你授权了某个应用在限定范围内代表你」。这正是 OAuth 与 Kerberos 最大的理念差异：Kerberos 证明「你是你」，OAuth 证明「你授权了这个应用」。<span class="marginnote">OAuth 2.0 本身不做认证，于是出现了在令牌之上叠加身份声明的 OpenID Connect（OIDC）：令牌里携带 id_token（JWT），「这是谁」和「授权了什么」同时可验证。JWT 是三段式（头部.载荷.签名）的 JSON 令牌，见密码学专题与 Web 安全各篇。</span>

## 3 SAML：企业级身份断言的 XML 语言

**SAML（Security Assertion Markup Language，安全断言标记语言）**是 OASIS 标准，解决同一类问题，但面向企业单点登录（IdP—SP 架构）：

**IdP（身份提供者）**：企业内的统一身份源，如 Okta、AD FS。
- **SP（服务提供者）**：用户要使用的各类云服务、应用。

用户访问 SP 时，被重定向到 IdP 登录，IdP 签署一条 **SAML 断言（assertion）**，声明「Alice 已认证、属于财务组、拥有某些属性」，浏览器把断言带回 SP 完成登录。<span class="marginnote">SAML 断言本身是个签名 XML，兼容企业已有的 AD/LDAP 体系，因此成为大企业 SSO 的主流；但它与 OAuth 的最大差别在方向：SAML 是「身份单向传递」，OAuth 是「权限委托且令牌可作废」。</span>

## 4 公式解析：Kerberos 的两次票据交换

Kerberos 的安全核心可以压缩成两条交换公式。设 $K_{C}$ 为客户端口令派生密钥，$K_{C,T}$ 为客户端与 TGS 的会话密钥，$K_{T,S}$ 为 TGS 与服务间的会话密钥：

$$
\text{AS 阶段：} C \to C_s: T_{C,T} = E_{K_C}(K_{C,T}, T_C), \quad \text{TGS 票据用 } K_{C,T} \text{ 签名}
$$

$$
\text{TGS 阶段：} C \to S: T_{C,S} = E_{K_{C,T}}(K_{C,S}, T_C), \quad \text{服务票据用 } K_{T,S} \text{ 加密}
$$

- **第一步，看 AS 阶段**：客户端用自己的口令密钥 $K_C$ 解开第一层，得到与 TGS 的会话密钥 $K_{C,T}$。$T_C$ 是时间戳，保证票据新鲜。
- **第二步，看 TGS 阶段**：客户端用 $K_{C,T}$ 换取服务票据，票据最终由 $K_{T,S}$ 加密——只有 TGS 与服务知道这把密钥，客户端拿到手也只是「递送员」。
- **第三步，看安全属性**：时间戳 $T_C$ 让**重放攻击**失效；每步的密钥分层让**任何单一密钥泄露都只影响一段链路**；客户端自始至终没把口令交给任何服务。三层防护叠在一起，正是「对称密钥 + 可信第三方」能达到的工程上限。

## 5 三种协议的选型对照

| 维度 | Kerberos | OAuth 2.0 | SAML 2.0 |
| --- | --- | --- | --- |
| 目标 | 企业内网单点登录 | 第三方应用的委托授权 | 企业 SSO 的身份断言 |
| 密钥体系 | 对称密钥 + KDC | 对称令牌 + 非对称签名（JWT） | 非对称签名 XML |
| 认证主体 | 用户在域内 | 授权服务器（OIDC 才携带身份） | IdP 统一认证 |
| 典型场景 | Windows AD、HDFS、SSH | 微信/Google 登录、API 授权 | 企业云应用 SSO |
| 最大风险 | KDC 单点被攻破 | 令牌泄漏 / 误授权 scope | 断言伪造 / IdP 钓鱼 |

**辨析｜易错点：** 别把「OAuth 登录按钮」误认为认证——OAuth 本身只授权、不认证；别把「SAML 断言」当长期凭证——断言应限时并用 HTTPS 传递；别把 Kerberos 口令复用扩展到互联网——KDC 的对称单点模型不适合公网。三者都在回答「信任如何传递」，但信任的方向、粒度与生命周期各不相同。

## 6 小结

- **Kerberos**：KDC 两级颁发票据，时间戳防重放，实现企业内网 SSO，对称密钥单点信任。
- **OAuth 2.0**：委托授权语言，第三方应用凭授权码换限定范围的访问令牌，不接触用户口令。
- **OIDC** 在 OAuth 之上加身份断言（JWT id_token），补齐了「认证」一块。
- **SAML**：IdP 向 SP 签署身份断言，企业级 SSO 的主流 XML 语言。
- 选型三问：**在什么网络里？信任谁？要认证还是要授权？**——三者的答案决定了用哪个协议。

在下一节，我们将离开「谁是主体」与「能做什么」，回到这些协议共同依赖的数学底座：对称与非对称加密、哈希、数字签名，以及把签名绑到人身上的**公钥基础设施 PKI**。
