## 为什么从缓冲区溢出开始

1988 年，Morris 蠕虫用一段缓冲区溢出让当时的互联网大面积瘫痪；2001 年，Code Red 借助 IIS 的缓冲区溢出一天感染 25 万台机器；2003 年，SQL Slammer 用同样的招数让全球互联网骨干抖动。**缓冲区溢出（buffer overflow）**是计算机安全史上被利用最久、影响最广的一类漏洞——它之所以长盛不衰，是因为它直指一个最朴素的事实：**C 语言不检查边界，程序员必须自己记得「写入的数据是否超出缓冲区」**。<span class="marginnote">缓冲区溢出不是语言语法错误，而是<strong>「信任输入会遵守边界」的错误假设</strong>——调用方承诺数据长度不超过 N，`strcpy` 选择相信。这是所有「越界写」漏洞的共同祖先，也解释了为什么内存安全语言（Rust、Go）能在根上消灭它。</span>

## 1 栈：函数调用的记账簿

要理解栈破坏，先看函数调用时**栈（stack）**上发生了什么。x86 的栈向**低地址方向增长**，每次函数调用压入一个**栈帧（stack frame）**，包含：

**局部变量**：函数自己的缓冲区，如 `char buf[64]`。
- **保存的帧指针（EBP）**：调用者的栈帧基址，用于函数返回后恢复现场。
- **返回地址（ret）**：`call` 指令压入的「下一条指令地址」，`ret` 指令执行时把它弹回指令指针——**程序下一步去哪儿，由它决定**。

栈帧布局与溢出后果如图所示：

![x86 栈帧在缓冲区溢出前后的对比](/images/system-security/buffer-overflow-stack-corruption-stack.svg)

**重点：** 栈向低地址长、`buf` 向高地址写——x86 上局部变量的数组从低地址向高地址填充，而返回地址恰好**躺在更高的地址**上。于是「向 `buf` 多写几字节」，就能一路写穿帧指针、直达返回地址。<span class="marginnote">栈向低地址长、数组向高地址写，两个方向相撞，这正是溢出能覆盖返回地址的几何原因。<strong>如果栈向高地址长（某些架构、某些编译器布局），溢出可能先破坏别的区域</strong>——漏洞的面貌完全由内存布局决定。</span>

## 2 一次经典溢出：从 strcpy 到劫持执行流

下面这段代码是教科书级的漏洞，出自 Wenliang Du 的经典实验：

```c
int vuln(char *input) {
    char buf[64];
    strcpy(buf, input);        /* 危险：不检查 input 长度 */
    return 0;
}
```

攻击流程分四步：

1. **定位偏移**：算出 `buf` 起始地址到返回地址之间差多少字节（这里是 64 字节局部变量 + 4 字节帧指针 = 68，即 0x44 字节）。这一步在真实攻防中靠「把 `AAAA…` 填入看崩溃地址」的**模式法（pattern）**确定。
2. **构造载荷**：前 68 字节填任意数据，第 69–72 字节填**攻击者指定的返回地址**。
3. **放置 shellcode**：把一段机器码（shellcode，通常是「启动一个 shell」）放进溢出数据里，返回地址指向它。
4. **触发**：函数 `return` 时 `ret` 指令取出被覆盖的返回地址，CPU 跳进 shellcode——**攻击者获得一次代码执行**。

**辨析｜易错点：** 溢出本身≠任意代码执行。溢出造成的是**越界写**，后果取决于覆盖到了什么：覆盖返回地址 → 代码执行；覆盖堆上的对象指针 → 任意写；只覆盖局部数据 → 也许只是崩溃。**判断威胁等级，先看「被覆盖的是什么」，而不是「溢出了多少字节」。**

## 3 不止栈：堆溢出、格式字符串与整数溢出

栈溢出只是「越界写」的旗舰。同一病根还有多个变体：

**堆溢出（heap overflow）**：`malloc` 的堆块上溢，覆盖相邻堆块的元数据或用户对象。glibc 的堆利用技术（unlink、fastbin dup）一度是 CTF 与真实攻击的常客。它比栈溢出难：没有固定的返回地址可覆盖，得想办法让覆盖变成「任意写」。

**格式字符串漏洞（format string）**：`printf(user_input)` 把输入当格式串解析——`%x` 泄漏栈上数据、`%n` 往指定地址写值。一条 `%n` 就是一次「任意写原语」，「任意写」叠加「任意读」就能一步步攻破。<span class="marginnote">格式字符串漏洞是「类型误用」的绝佳样本：<strong>输入被当作「代码（格式串）」而不是「数据」解析</strong>。这个「把数据当代码」的根因，后来在 Web 世界以 SQL 注入、XSS 的形式全面重演——见《Web 安全》一篇。</span>

**整数溢出（integer overflow）**：`len + 1` 溢出成负数，被当作超大长度导致后续拷贝越界。它常作为其他溢出的「引信」出现。

## 4 公式解析：漏洞偏移量的计算

定位「返回地址在数据中的偏移」是溢出的核心数学。设：

$$
\text{offset} = N + \underbrace{p}_{帧指针大小} + \underbrace{r}_{返回地址大小}
$$

- **第一步，分清三项**：$N$ 是缓冲区大小（如 64），$p$ 是保存的帧指针宽度（32 位 4 字节、64 位 8 字节），$r$ 是返回地址宽度。
- **第二步，代入数字**：32 位下 `char buf[64]` 的返回地址偏移为 $64 + 4 + 4 = 72$ 字节；64 位下为 $64 + 8 + 8 = 80$ 字节。编译器可能加栈对齐与金丝雀（见《内存保护机制》一篇），实际偏移要做实验确认——公式给出的是**无防护下的理论值**。
- **第三步，看 shellcode 的落点**：返回地址指向的 shellcode 可以放在溢出缓冲区里（需要栈地址可预测，被 ASLR 打击），也可以放在环境变量、全局数据等**固定地址区域**（牺牲栈空间换取稳定）。
- **第四步，看公式的意义**：$N$ 每大一分，偏移就线性大一分——**缓冲区越大，攻击者越从容**；而防护（金丝雀）的价值正在于让「计算偏移」这一步变成「还得先猜随机值」。

## 5 从漏洞到修复：教训与方向

缓冲区溢出的教训，是理解现代系统安全的钥匙：

**开发层面**：换内存安全语言（Rust/Go/Java），或用安全函数族（`strlcpy`、`snprintf`），或加边界检查。**最高效的修复在语言层面**——这也是为什么新系统全面转向 Rust。
**编译/运行时层面**：金丝雀（StackGuard）、DEP/NX、ASLR、CFI——让「即使有漏洞，也难以利用」。这些是下一节《内存保护机制》的主角。
**运维层面**：及时打补丁、纵深防御、限制权限——让「即使被利用，损失也有限」。

**重点：** 缓冲区溢出没有「银弹」，只有「层层加码」：语言防根子、编译防利用、系统防扩散。理解这一点，就理解了整个系统安全的哲学——**不是消灭漏洞，而是让漏洞的代价高到攻击者买不起**。

## 6 小结

- 缓冲区溢出源于**信任输入会遵守边界**，C 语言不检查边界使其成为历史主流漏洞。
- x86 栈向低地址长、数组向高地址写，**返回地址恰好在溢出路径上**——「多写几字节」即可劫持执行流。
- 经典攻击四步：**定位偏移 → 构造载荷 → 放置 shellcode → 触发跳转**。
- 同根变体：**堆溢出、格式字符串、整数溢出**——都是「越界写」与「数据当代码」的不同面孔。
- 修复是立体战：**语言层防根子、编译层防利用、系统层防扩散**。

在下一节，我们将站到攻击者的对立面，看现代编译器与操作系统如何为内存装上天罗地网：**ASLR、DEP 与 CFI** 凭什么让「算偏移、猜地址、跳 shellcode」每一步都变难。
