## 为什么从硬件安全开始

前面所有防御都建立在同一个假设上：**操作系统是可信的**。可如果 bootloader 被换了、内核被改了、甚至固件被植入了后门，那么操作系统之上的一切防线（ASLR、SELinux、审计）都只是「在对方的地盘上站岗」。<span class="marginnote">「在什么之上建立信任」正是可信计算的核心问题。Dieter Gollmann《Computer Security》第 12 章把它从软件推到硬件：<strong>当软件层无法自证清白时，把信任锚钉在一颗不可篡改的芯片上</strong>——这就是 TPM。</span>**可信计算（Trusted Computing）**回答的终极问题是：**这台机器能不能向自己、也向别人证明「我处于未被篡改的状态」？**

## 1 TPM：一颗独立于 CPU 的可信芯片

**TPM（Trusted Platform Module，可信平台模块）**是焊在主板上的一颗**独立安全芯片**，它把「信任」从软件层锚定到硬件：CPU、操作系统都可能被替换，但 TPM 是**物理上、逻辑上都独立**的信任点。TPM 的核心能力：

**受保护的密钥存储**：私钥只存在于 TPM 内部，永不导出——即使系统被完全控制，攻击者也拿不到 TPM 里的私钥。
- **平台配置寄存器（PCR，Platform Configuration Register）**：记录「系统启动到现在的每一层状态」，且只能**扩展（extend）**不能覆盖。

PCR 的「只能 extend」是它最精妙的设计。扩展操作定义为：新值 = 哈希(旧值 ‖ 新度量)。一旦某一层的度量被记录，**任何后续度量都会改变 PCR 值**——攻击者无法「抹掉」被篡改的痕迹，只能让它变得「可见地不正确」。<span class="marginnote">TPM 的完整操作模型（PCR、EK/AK 密钥、quote 远程证明）在密码学专题 tpm-trusted-boot 一篇有逐步拆解。<strong>一句话记住 TPM：它是「什么都信不过的软件世界」里那个「什么都信得过」的硬件起点</strong>。</span>

## 2 信任链：安全启动与度量启动

「TPM 可信」还得先回答「怎么保证 TPM 之外的第一步也是可信的」。答案是**链式信任**：

**安全启动（Secure Boot，UEFI）**：UEFI 固件验证 bootloader 的签名 → 验证通过才执行。bootloader 再验证内核签名。**每一层只信任「已被上一层验证过的下一层」**——签名验证把「非法代码」挡在启动链之外。

**度量启动（Measured Boot）**：不阻止，但把每一层的度量值（哈希）**记录进 PCR**。这样「系统确实启动到了某状态」成为**可验证的事实**，而不仅是「看起来正常」。

把两者结合，就是完整的信任链：

$$
\underbrace{\text{固件（信任根）}}_{\text{硬件上电}} \to \underbrace{\text{bootloader}}_{\text{验签名}} \to \underbrace{\text{内核}}_{\text{验签名}} \to \underbrace{\text{用户态}}_{\text{测度量}}
$$

- **第一步，定锚**：信任根是固件与 TPM 的硬件绑定——它上电即可信，不需要任何软件背书。
- **第二步，验签**：UEFI Secure Boot 保证「能启动的代码」都在签名白名单内——被篡改的 bootloader 根本进不了执行流。
- **第三步，度量**：同时把各层哈希扩展进 PCR——即使签名被绕过，启动状态仍会被「如实记录」。
- **第四步，证明**：远程一方用 TPM 的 `quote`（对 PCR 的签名响应）验证「这台机器当前 PCR 值确实如此」——**远程证明（remote attestation）**由此成立。

## 3 远程证明与隔离执行：可信计算的两副面孔

**远程证明（remote attestation）**是可信计算的对外输出：客户端/服务端向远方的验证者证明「我运行在预期的、未被篡改的软件栈上」。典型流程：验证者发 challenge → 机器返回 `quote`（PCR 值 + TPM 用 AIK 私钥签名）→ 验证者比对已知「好」的 PCR 参考值。PCR 值对不对，由 TPM 这个硬件担保签名，**软件无法伪造**。

**隔离执行（TEE，Trusted Execution Environment）**是可信计算的对内输出：**即使操作系统被攻破，也能在受保护的 enclave 里安全运行关键代码与数据**。两大阵营：

- **Intel SGX**：在普通内存里划出「飞地（enclave）」，内容加密且只能在 CPU 内部解密——操作系统看不见 enclave 内部，连系统管理员也无法读取。
- **ARM TrustZone**：把系统物理划分为「安全世界」与「普通世界」，安全世界跑可信 OS 与支付/密钥等敏感服务，普通世界（Android、iOS 的用户空间）无法访问。<span class="marginnote">TEE 的边界在于：<strong>它保护「可信 CPU 内核」之外的秘密，但保护不了 CPU 本身</strong>。2018 年的 Spectre/Meltdown 从 CPU 预测执行里读出内核内存——这正是「硬件层的信任根」自身的裂缝，业界至今仍在用「缓存清理 + 序列化指令」做折中修复。</span>

## 4 公式解析：PCR 的扩展与「不可逆」证明

PCR 扩展是把「状态不可篡改」变成数学性质的关键。设 PCR 当前值为 $v$，新度量值为 $m$，则扩展后的值为：

$$
v' = H(v \,\|\, m)
$$

- **第一步，看运算**：不是覆盖（`v' = m`），而是把旧值 $v$ 与新度量 $m$ **拼接后哈希**。因此 $v'$ 同时依赖**历史全部状态**与**当前新状态**。
- **第二步，看不可逆**：$H$ 是抗碰撞哈希——给定 $v'$，攻击者无法「找出」一个 $m'$ 让 $H(v\|m') = v'$（那需要破解哈希）；也无法把 $v$ 「恢复」成旧状态。**PCR 只能前进，不能后退**。
- **第三步，看篡改痕迹**：如果 bootloader 被换，它的哈希 $m$ 就不是预期值，扩展进 PCR 后的 $v'$ 与「干净启动」的参考值不符——**篡改必然留下 PCR 层面的「指纹」**。
- **第四步，看证明闭环**：验证者只要拿到「PCR 引用值（期望）」，就能用 TPM 的签名 quote 判定「这台机器是否按干净链条启动」。**信任从「目测」变成了「数学验证」**——这就是可信计算「可证明」的精髓。

## 5 硬件安全的另一面：侧信道与供应链

可信计算的芯片本身也不是铁板一块：

**侧信道攻击（side-channel）**：不攻击密码学算法，而攻击**物理泄露**——执行时间（时间侧信道）、功耗（功耗分析）、缓存命中（Cache 侧信道）。2018 年的 **Spectre/Meltdown** 是教科书级案例：CPU 的**推测执行**（提前执行可能用到的指令）让「不该读的内存」被带进缓存，攻击者再通过缓存时间差异读出它们——**CPU 以「性能优先」为名，泄露了内存保护承诺**。

**硬件供应链风险**：芯片制造、固件更新、第三方硬件的植入（如 2018 年曝出的服务器主板芯片上发现隐蔽硬件后门）——「信任根」如果一开始就被污染，一切证明都失效。

**辨析｜易错点：** 可信计算不等于「绝对安全」。它提供的是**可验证性**（attestation）与**隔离**（TEE），不防侧信道、不防被攻破的硬件本身、也解决不了「参考 PCR 值被泄露/被替换」的管理问题。**信任锚是可信的起点，不是安全的全集。**

## 6 小结

- **TPM** 是独立于 CPU 的硬件信任锚：受保护存储 + 只能扩展的 **PCR**。
- **信任链** = 固件信任根 → UEFI 验签 → 内核验签 → 用户态度量；**安全启动**挡篡改，**度量启动**留证据。
- **远程证明**用 TPM 签名 quote 让「当前状态」可对外验证；**TEE（SGX/TrustZone）**让敏感代码在隔离环境里运行。
- **PCR 扩展** $v' = H(v \,\|\, m)$ 使状态不可逆、篡改必留指纹——信任变成数学事实。
- 硬件安全仍受**侧信道与供应链**威胁；可信计算提供的是「可验证」，不是「绝对安全」。

到这里，我们走完了《系统安全》从「信任模型」到「硬件信任根」的完整闭环：模型定规则、认证定身份、密码学定保密、攻防定边界、加固定配置、硬件定锚点——**安全不是单一机制，而是一条从芯片到浏览器的信任链，每一环都在回答「我凭什么信它」。**
