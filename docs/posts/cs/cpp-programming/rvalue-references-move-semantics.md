## 为什么从右值引用开始

第13章拷贝控制里已经出现了「移动构造」——它能把临时对象的资源「偷」过来，而不是深拷贝一份。但要理解移动为什么可能、什么时候发生，必须回到第4章那个被我们一笔带过的二分法：**左值与右值**。C++11 引入 **右值引用（rvalue reference）** `T&&`，专门绑定「即将销毁的临时对象」；配合 **`std::move`** 与 **`std::forward`**，让「移动而非拷贝」成为一种可以被程序员显式请求、被编译器自动识别的语言机制。这一节是 C++11 最重大的语言特性之一：它让 `std::vector`、`std::string` 的按值返回几乎零拷贝，也让 `unique_ptr`、`thread` 这类「移动唯一类型」成为可能。<span class="marginnote">在 C++11 之前，「把 vector 从函数里返回出来」要么靠指针、要么忍受一次深拷贝（然后靠 RVO 优化掉）。移动语义出现后，「按值返回 + 编译器自动移动」成为最自然也最快的写法——这改变了 C++ 程序员十年来养成的传参习惯。</span>

## 1 左值与右值的价值类别

**左值（lvalue）**：有名字、能取地址、代表**一个对象**的表达式——变量、`v[i]`、`*p`。**右值（rvalue）**：代表**一个即将消失的临时值**的表达式——字面量 `42`、表达式 `a + b` 的结果、`std::move(x)`。<span class="marginnote">C++11 把值类别扩成五类：lvalue、rvalue、xvalue（即将消亡的值，如 `std::move(x)` 的结果）、glvalue（广义左值 = lvalue ∪ xvalue）、prvalue（纯右值 = rvalue − xvalue）。日常只需记住两分法：<strong>左值「会留下」，右值「马上走」</strong>——右值既然马上走，谁拷贝它就蠢，谁能接管它就赚。</span>

**右值引用（rvalue reference）** `T&&` 只能绑定到右值上，作用是「明确声明：我要接管这个即将销毁的对象的资源」：

```cpp
int &&rr = 42;                 // 右值引用绑定字面量（延长临时生命周期）
// int &&x = i;                // 错误：i 是左值，右值引用不能绑定左值
```

## 2 移动构造与移动赋值

**移动构造（move constructor）**把「接管」翻译成代码：不深拷贝，只搬走指针、把源对象置空。以 `HasPtr` 为例（承接第13章）：

```cpp
HasPtr(HasPtr &&rhs) noexcept
    : ps(rhs.ps), i(rhs.i) {   // 直接接管 rhs.ps 指向的堆对象
    rhs.ps = nullptr;          // 置空源：析构时不会误删被接管的资源
}
```

**重点：** 移动后**必须把源对象置回「合法但未指定」的状态**——`rhs.ps = nullptr` 保证源对象的析构函数不会 `delete` 掉已经被接管的内存。<span class="marginnote">标准术语是「valid but unspecified state」：移动后的源对象可以继续析构、可以重新赋值，但不能依赖它的具体值。这就是为什么移动操作里「把源置空」这一步不可或缺——否则析构时双重释放再次上门。</span>

移动发生的情形：**初始化/赋值右侧是右值**（临时对象、`std::move` 结果）。而**具名的左值不会自动被移动**——`HasPtr b = a;` 里 `a` 是左值，走的永远是拷贝；想让它走移动，必须显式 `std::move(a)`。

## 3 std::move：把左值「标记」成右值

**`std::move`** 是一个**类型转换函数**（本质 `static_cast<T&&>`），作用只有一个：把左值**当作右值**对待，从而触发移动而不是拷贝。

```cpp
std::vector<int> v1{1, 2, 3};
std::vector<int> v2 = std::move(v1);   // 接管 v1 的堆缓冲
// 此后 v1 是空壳，v2 拥有那三块数据
```

**辨析｜易错点：** `std::move` **什么也不移动**——它只把参数标记成右值，真正的搬运发生在**移动构造函数/移动赋值**里。还有三条纪律：

- **move 之后别再用源对象**（它的状态未指定）。
- 对 `const` 对象 `std::move` 无效：`std::move(constObj)` 会落到**拷贝构造**上（const 右值引用不会绑定到移动构造）。
- 该不该 move 要想清楚：move 不是「免费拷贝」，它转移所有权——用在「真不需要源对象」的地方。<span class="marginnote">Scott Meyers 有一条著名警告：<strong>「没谱就别 move」</strong>——对一个你可能还会用的对象执行 `std::move`，等于把它的内脏掏空后继续用，是未定义行为的温床。`std::move` 的英文名其实有误导性，它本该叫 `rvalue_cast` 之类更中性的名字。</span>

## 4 std::forward 与完美转发

**完美转发（perfect forwarding）**解决的是模板问题：一个模板函数把参数**原样**转交给另一个函数，且**保持左值/右值属性不变**——左值到左值、右值到右值。

```cpp
template <typename T>
void wrapper(T &&arg) {          // 转发引用（引用折叠的产物）
    target(std::forward<T>(arg)); // forward 按 T 决定是左值还是右值转发
}
```

这里的 `T&&` 不是「右值引用」，而是**转发引用（forwarding reference）**：实参是左值时 `T` 推导为 `T&`、实参是右值时 `T` 推导为 `T`，再经**引用折叠**统一成一个 `&&`。**`std::forward<T>`** 负责「把被折叠掉的值类别还原」——这正是完美转发的钥匙。<span class="marginnote">`std::move` 与 `std::forward` 的区别一句话：<strong>move 是无条件转成右值，forward 是条件性地还原原来的值类别</strong>。在模板里写 `std::forward<T>(arg)`，让 target 既能接收左值、也能接收右值——`make_unique`、`emplace_back` 这些工厂函数全靠它工作。</span>

## 5 移动语义带来的连锁效应

移动语义不只是「快一点」，它改变了类型设计规则：

- **移动唯一类型（move-only）**：`unique_ptr`、`thread`、`future`、`fstream` 都不可拷贝、只能移动。它们「天然唯一」地占有资源。
- **容器的按值返回**：`std::vector<Widget> build() { ... return v; }`——C++11 后返回 `v`（具名左值）会自动尝试移动而非拷贝，配合 RVO 几乎零开销。
- **`emplace_back`**：在容器内**原地构造**元素，省去「构造临时对象 + 移动/拷贝进容器」两步。

**核心对比表：** 拷贝 vs 移动

| 维度 | 拷贝构造/赋值 | 移动构造/赋值 |
| --- | --- | --- |
| 源对象 | 保持原样 | **被掏空（置空/未指定）** |
| 对堆资源 | 深拷贝一份 | 接管指针，$O(1)$ |
| 大对象开销 | 随大小增长 | 恒定（几个指针） |
| 触发条件 | 源是左值 | 源是右值 |
| noexcept | 可选 | 推荐（vector 扩容才敢用） |

**易错点：** 移动构造函数/赋值**通常应该标 `noexcept`**——否则 `std::vector` 扩容时「怕移动抛异常」会选择拷贝，移动的收益就白白浪费在扩容路径上了。<span class="marginnote">为什么 vector 要保证「移动不抛」才敢用移动？因为扩容是先搬元素、再释放旧缓冲——如果搬到一半抛异常，旧缓冲已部分破坏、无法回滚。C++ 社区因此有一条约定：<strong>移动操作能做到不抛就声明 noexcept</strong>，让容器放心大胆地移动。</span>

**move 与 noexcept 的工程组合**：移动构造/移动赋值/swap 标 `noexcept` 之后，`std::vector` 扩容、`std::sort` 的交换、异常安全里的提交步骤（第4篇条款29）都能放心走「移动」而非「拷贝」。一个容易被忽略的细节是**移动会「掏空」源**——把 `std::vector` move 进另一个之后，源 vector 处于合法但未指定的状态（`size()` 可能为 0，`empty()` 为 true），可以直接复用但不能假设它仍持有旧数据。**判断「该不该 move」的实践**：只在「源对象之后绝不再用」时 move；「只是不想拷贝」但之后还要用源，用拷贝或引用，别 move。<span class="marginnote">完美转发 + move 在「工厂函数」里最见功力：<strong>`std::make_unique<T>(args...)` 内部用 `std::forward<Args>(args)...` 把参数原样转给 `T` 的构造函数</strong>——左值走拷贝、右值走移动，构造函数省一次临时拷贝。写「转发构造函数」时别忘 `std::forward`，否则右值会被当作左值退化成拷贝。</span>

**引用折叠的一张完整推导表**（模板里 `T&&` 遇到不同实参的折叠结果）：

| 实参类型 | `T` 推导 | 折叠后形参 | 效果 |
| --- | --- | --- | --- |
| 左值 `X&` | `X&` | `X& && → X&` | 绑定左值，走拷贝 |
| 左值 `const X&` | `const X&` | `const X&` | 绑定 const 左值，走拷贝 |
| 右值 `X` | `X` | `X&&` | 绑定右值，走移动 |
| 右值 `X&&` | `X` | `X&&` | 绑定右值，走移动 |

这张表是「完美转发」的全部秘密：**`T` 推导成 `T&` 时，`std::forward<T>` 还原为左值；推导成 `T` 时还原为右值**——于是同一个 `wrapper` 既能转发左值、也能转发右值，且值类别一毫不差。

**工程提醒：别滥用 std::move**——`std::move` 不是性能魔法，它把对象「标记为可偷」；对 `int`、`double` 这类「拷贝就是复制寄存器」的类型，move 没有任何收益；对「之后还要用」的对象 move，是搬起石头砸自己的脚。<span class="marginnote">判断要不要 move 的一条经验：<strong>「这个对象我之后还读吗？」「读 → 别 move；只用于转移所有权（如塞进容器/返回）→ move」</strong>。移动语义解决的是「对象大、拷贝贵、用完即弃」的场景——字符串、容器、智能指针、IO 对象是它的主场，内置类型不是。</span>

**一个自查清单**：① 右值引用 `T&&` 与转发引用 `T&&` 在模板内外的区别？② `std::move` 真的移动了吗？③ move 后源对象是什么状态？④ 为什么移动构造要 `noexcept`？四问答清，移动语义一章便过关。

## 6 小结

- **右值引用 `T&&`** 只绑定临时对象；值类别二分法（左值会留下、右值马上走）是移动语义的地基。
- **移动构造/赋值**接管资源、把源置空；移动后源对象是「合法但未指定」状态。
- **`std::move`** 只是把左值标记成右值，不搬运任何东西；对 const 对象无效、move 后别用源。
- **`std::forward<T>`** 在模板里还原值类别，是**完美转发**与工厂函数（`emplace_back`、`make_unique`）的钥匙。
- **移动唯一类型**（unique_ptr、thread、fstream）不可拷贝、只能移动，天然独占资源。
- 移动操作标 **`noexcept`**，vector 扩容才敢用移动而非拷贝。一句话收束：移动语义让 C++ 从「拷贝一切」走向「能搬则搬」，而右值引用是这场变革的语法地基——它让「临时对象的资源」能被廉价接管，也让 `unique_ptr`、`thread` 这类「只搬不拷」的类型成为可能。
