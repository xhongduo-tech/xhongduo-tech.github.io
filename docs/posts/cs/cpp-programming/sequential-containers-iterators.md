## 为什么从顺序容器开始

第3章的 `std::vector` 只是惊鸿一瞥，第9章才把「容器」当作一个**家族**来展开：`vector`、`deque`、`list`、`forward_list`、`array`、`string`。它们都保存「有序的元素序列」，却因为底层存储结构不同，在「插入、删除、随机访问、空间开销」上各有优劣。这一章同时引入**迭代器（iterator）**——一组统一的「指针式」访问接口，让算法不必关心容器内部结构。<span class="marginnote">「选对容器」是 C++ 性能实践的第一课：在 vector 头部频繁插入是灾难，改用 deque 或 list 就顺畅。C++ Primer 第9章开篇就把六个顺序容器列成一张表，让读者先建立「按访问模式选容器」的直觉。</span>

## 1 六个顺序容器速览

**顺序容器（sequential container）**：保存相同类型元素、且**元素之间有先后顺序**的容器。六个成员各怀绝技：

| 容器 | 底层 | 随机访问 | 头部插入 | 尾部插入 | 中间插入 |
| --- | --- | --- | --- | --- | --- |
| `vector` | 连续数组 | $O(1)$ | $O(n)$ | $O(1)$ 均摊 | $O(n)$ |
| `string` | 连续数组（char） | $O(1)$ | $O(n)$ | $O(1)$ 均摊 | $O(n)$ |
| `deque` | 分块连续 | $O(1)$ | $O(1)$ | $O(1)$ | $O(n)$ |
| `list` | 双向链表 | $O(n)$ | $O(1)$ | $O(1)$ | $O(1)$ 已知位置 |
| `forward_list` | 单向链表 | $O(n)$ | $O(1)$ | — | $O(1)$ 已知位置 |
| `array` | 定长数组（C++11） | $O(1)$ | — | — | — |

**直觉速记**：`vector`/`string` 是「能随机访问的连续块」，尾插快、头插慢；`list`/`forward_list` 是「能任意插删的链」，但随机访问要挨个走；`deque` 居中——头尾都快、随机访问也不差；`array` 是「定长的 vector」，编译期定大小。<span class="marginnote">为什么 `vector` 中间插入是 $O(n)$？因为元素必须保持连续且有序——插入一个，后面的每个都要挪一格。而 `list` 中间插入只需改两个邻居的指针，$O(1)$。这是「数据结构决定复杂度」的经典教科书例子，与第2级《数据结构与算法》里的链表/数组对比完全同构。</span>

## 2 迭代器：容器与算法之间的接口

**迭代器（iterator）**：一种**行为像指针**的对象——支持 `*it`（解引用）、`it->member`、`++it`、`it1 == it2`，用来「走到容器里某个元素」并移动。所有标准容器都提供 `begin()`（指向首元素）与 `end()`（指向**尾后位置**，不指向任何元素）：

```cpp
std::vector<int> v{1, 2, 3, 4, 5};
for (auto it = v.begin(); it != v.end(); ++it)
    std::cout << *it << ' ';
```

**重点：** `end()` 是**尾后迭代器（off-the-end iterator）**——它不指向任何元素，只作为「遍历结束」的哨兵，**绝不能对它解引用**。`v.empty()` 就等价于 `v.begin() == v.end()`。范围 for 之所以能一行遍历容器，正是因为它在底层做了「`begin` 到 `end` 的迭代器循环」。<span class="marginnote">`cbegin()`/`cend()` 返回 <strong>const 迭代器</strong>，只读不改；`rbegin()`/`rend()` 是反向迭代器，`++` 往前走（指向末尾往头移动）。这套命名法在整个标准库通用——看名字就知道「只读还是可写、正向还是反向」。</span>

## 3 迭代器失效与容器操作

**迭代器失效（iterator invalidation）**是顺序容器最大的坑：对 vector/string，**任何改变容量或尺寸的操作**（`push_back` 扩容、`insert`、`erase`、`resize`）都可能让已持有的迭代器、指针、下标**指向被移动或删除的元素**，继续使用是未定义行为。<span class="marginnote">list/forward_list 的迭代器更「皮实」：插入删除只失效被删除的那个，其余仍有效；vector 则「一次扩容，全部作废」。C++ Primer 第9章给每条容器操作都标注了迭代器是否失效——写循环删除元素时，务必用「保存下一迭代器」或 `erase` 的返回值更新。</span>

**vector 的 size 与 capacity**：`size()` 是**当前元素个数**，`capacity()` 是**已分配内存能容纳的个数**。`reserve(n)` 预分配内存避免反复扩容；`shrink_to_fit()` 把多余内存还给系统。

```cpp
std::vector<int> v;
v.reserve(1000);       // 一次分配 1000 个 int 的空间
for (int i = 0; i < 1000; ++i)
    v.push_back(i);    // 全程不扩容，零拷贝搬迁
```

## 4 公式解析：vector 的均摊 O(1) 扩容

`push_back` 声称是 $O(1)$，但扩容时要整体搬一次家，为什么还能算 $O(1)$？答案在**均摊分析（amortized analysis）**。假设 vector 按**加倍**策略扩容：容量依次为 $1, 2, 4, 8, \dots$。

- **第一步，数搬家次数**：向容量 $2^k$ 的 vector 里再塞一个元素，要申请 $2^{k+1}$ 的空间并**拷贝已有 $2^k$ 个元素**。
- **第二步，累加总拷贝量**：往一个最终装下 $n$ 个元素的 vector 里依次 `push_back`，扩容拷贝的总元素数是
  $$1 + 2 + 4 + \cdots + 2^{\lfloor \log_2 n \rfloor} < 2n$$
- **第三步，取平均**：$n$ 次 `push_back` 的总代价 < $2n$ 次拷贝 + $n$ 次写入，于是**每次 push_back 的均摊代价是 $O(1)$**。

$$T(n) = \frac{n \text{ 次写入} + <2n \text{ 次拷贝}}{n} = O(1)$$

关键在「< $2n$」：几何级数求和收敛到 $2n$ 以内，所以把昂贵的搬家摊到每次廉价操作上，平均仍是常数。这就是教科书上「**vector 尾部插入均摊 O(1)**」的完整来历。<span class="marginnote">如果扩容倍率是 1.5 而不是 2，总拷贝量约 3n，仍是 O(1) 均摊，但<strong>峰值内存更小</strong>——不少实现（如 MSVC）用 1.5 倍，正是为了在「均摊复杂度」与「峰值空间」之间取平衡。这也是为什么 `reserve` 重要：已知规模时预分配，把「摊掉的」成本也省掉。</span>

## 5 insert 与 erase 的正确姿势

删除「所有值为 3 的元素」是迭代器陷阱的经典现场。list 用 `remove` 一行解决；vector 用「erase-remove 惯用法」：

```cpp
// vector：erase-remove 惯用法
v.erase(std::remove(v.begin(), v.end(), 3), v.end());

// list：成员 remove 更优
lst.remove(3);
```

`std::remove`（第10章算法）把「要留的元素」挪到前面、返回新的逻辑尾；`erase` 再把从逻辑尾到 end 的尾巴删掉。**不能**用「`for` 里边遍历边 `erase`」的朴素写法——`erase` 会让当前迭代器失效。<span class="marginnote">为什么 list 有成员 `remove` 而 vector 没有？因为 list 的节点删除本身 $O(1)$，专有实现更直接；vector 的删除必须配合算法挪动。这体现标准库的设计观：<strong>容器提供「自己的数据形态」最擅长的操作</strong>，通用形态交给算法。</span>

**emplace_back：原地构造**：`push_back(x)` 把现成对象**拷贝/移动**进容器；而 `emplace_back(args...)` 直接在容器**预留的内存里构造**对象，连「构造临时对象 + 搬入」都省了：

```cpp
struct Point { Point(int x_, int y_) : x(x_), y(y_) {} int x, y; };
std::vector<Point> pts;
pts.emplace_back(1, 2);      // 直接构造 Point(1,2)，一次构造
pts.push_back(Point(3, 4));  // 构造临时 + 移动进容器（编译器可能优化掉）
```

对「构造昂贵」的类型，`emplace_back` 是实打实的性能收益；对内置类型两者几乎无差。它是「移动语义（第13章）+ 完美转发（第16章）」在容器接口上的合体。

**迭代器类别一览**：迭代器按「能力」分五级，容器按「能提供哪一级」分档——`vector` 提供**随机访问迭代器**（能 `it + 5`、能 `it2 - it1`），`list` 只提供**双向迭代器**（只能 `++`/`--`），`forward_list` 只有**前向迭代器**。这解释了为什么「给 list 用 `std::sort` 会编译报错」——它需要随机访问迭代器。选容器时，「我要对迭代器做什么操作」决定容器的下限。<span class="marginnote">五级迭代器从强到弱：<strong>随机访问 > 双向 > 前向 > 输入 > 输出</strong>。算法在头文件里声明「我只要求前向迭代器」就能同时服务 list 与 vector；要求随机访问的算法（如 sort）则只服务 vector 这类。这是「算法与容器解耦」的精细刻度——<strong>接口的强度就是泛化的范围</strong>。</span>

**capacity 与 size 的数值直觉**：`capacity() - size()` 是「还能免费塞几个」——`push_back` 只有越过 capacity 才触发扩容搬迁。所以「预知规模」的程序可以先 `v.reserve(n)`，让全程零搬迁；`shrink_to_fit()` 把 capacity 压回 size，但它是「请求」而非保证，且可能触发一次搬迁。**读代码时**，`capacity()` 大而 `size()` 小的 vector 是「预留空间尚未用完」的信号，别误以为「元素很多」。<span class="marginnote">`std::array`（C++11）补齐了「定长、带 size、可赋值」的需求：<strong>`std::array<int, 5>` 大小固定、有 `size()`、可整体赋值、可按 `at()` 越界检查</strong>——它是「内置数组的正规替代」，「定长但要用现代容器接口」时选它。它没有 `push_back`（定长嘛），也没有动态分配。</span>

**一个选型决策示例**：实现「编辑器撤销栈」——需要「尾部压入、从尾部撤销」，数据量大、随机访问不必要：`std::vector` 是最优（尾插尾删均摊 O(1)、缓存友好）。实现「任务调度队列」——既要头删又要尾加：`std::deque` 最合适（两头 O(1)）。实现「LRU 缓存」——要按访问顺序移动元素、要中间插入删除：`std::list` 配 `unordered_map`。**先想操作、再选容器**，是这一章落到实践的唯一结论。

**补充：容器的比较与赋值**：所有顺序容器都支持「整容器比较」（`v1 == v2`，逐元素比较）与「整容器赋值」（`v1 = v2`，拷贝全部元素）。`assign` 系列还能用「迭代器区间」或「重复值」重建容器：`v.assign(beg, end)`、`v.assign(10, 7)`。这些「整容器操作」让容器可以作为「值」参与拷贝与交换，是「值语义容器」区别于裸数组的重要特性。

**一个「按需选容器」的速查流程**：先问「要不要随机访问？」——要，`vector`/`deque`；不要，`list`/`forward_list`。再问「要不要在头部频繁插入？」——要，`deque` 或 `list`。再问「大小运行时才知道吗？」——是，`vector`；否，`array`。最后问「数据是否有序按键？」——是，去第11章关联容器。四问下来，容器选型基本尘埃落定；若仍拿不准，`std::vector` 永远是「先跑起来」的安全默认。等性能剖析证明它是热点，再针对性换成 `deque` 或 `list`。<span class="marginnote">这条流程的底层是「访问模式决定数据结构」——第2级《数据结构与算法》里「数组 vs 链表」的全部权衡，在这里浓缩成四个问题。选错容器的代价不是「慢一点」，而是「从 O(1) 掉到 O(n)」的数量级落差。</span>

**一张「本专题容器地图」的预告**：顺序容器（第9章）管「有位置的序列」，关联容器（第11章）管「按键的映射」，二者配合「算法」（第10章）与「迭代器」形成标准库的四大支柱——本章的六个顺序容器是这条主线的起点。

## 6 小结

- **六个顺序容器**按「随机访问、头尾插删、中间插删」三个维度选型；`vector` 是默认选择。
- **迭代器**是「行为像指针的通用访问接口」；`begin()`/`end()`，`end()` 是**不可解引用的尾后哨兵**。
- **迭代器失效**是 vector 的头号坑：改变容量/尺寸后旧迭代器作废；list 更皮实。
- `size()` vs `capacity()`：`reserve` 预分配可消除扩容搬迁；`shrink_to_fit` 归还空间。
- **均摊分析**解释了 `push_back` 为何是 O(1)：几何级数总拷贝量 < 2n。
- 删除元素的惯用法：list 用 `remove`，vector 用 **erase-remove**。

在下一节，我们把「容器上的通用操作」抽出来——**泛型算法与 lambda 表达式**：find、sort、count 如何只依赖迭代器工作，lambda 如何作为「内联函数对象」喂给算法。

> 补充一句：如果你把本章「选容器四问」与「迭代器五级」两条主线都记住了，那么标准库的任何容器、任何算法对你而言就不再是黑盒——它们只是「数据结构 × 访问接口」的组合。
