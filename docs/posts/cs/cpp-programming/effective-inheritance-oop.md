## 为什么从继承设计开始

第15章我们讲了继承的机制（虚函数、构造顺序），第6章（条款32–40）回答继承的**设计**问题：什么时候该用继承、什么时候该用组合、public/private/protected 继承各自意味着什么。九条里最核心的是：**public 继承必须是 is-a**（32）、**名字隐藏**的规则（33）、**接口继承与实现继承的分野**（34）、**虚函数的替代方案**（35）、**别重定义非虚函数与默认参数**（36–37）、**composition 即 has-a**（38）、**private 继承要明智**（39）、**多重继承要审慎**（40）。<span class="marginnote">这一章的底色是「继承不是免费午餐」：<strong>一旦使用继承，你就把基类的每一条规则都强加给了派生类</strong>——所以「该不该继承」比「怎么继承」更值得先想。Meyers 的态度很鲜明：组合（composition）往往是比继承更稳的选择。</span>

## 1 条款32：确定你的 public 继承塑模出 is-a 关系

**重点：** `public` 继承意味着「**派生类是一种基类**」（is-a）：凡是能对基类做的事，必须也能对派生类做——否则继承就塑造错了关系。

```cpp
class Bird { virtual void fly() {} };        // 鸟会飞？
class Penguin : public Bird {};              // 企鹅是鸟，但企鹅不会飞！
```

**易错点：** 企鹅「is-a」鸟，却不会飞——`Penguin : public Bird` 强迫企鹅继承 `fly`。这种「is-a 但有个体差异」的建模错误，根源是把「基类能力」当成了「所有子类的共性」。**对策**：把 `fly` 从 Bird 挪到「会飞的鸟」中间层（`FlyingBird : public Bird`），或干脆不放进 Bird。**判断 is-a 的测试**：把派生类当基类用，会不会在语义上出问题？会，说明继承关系选错了。<span class="marginnote">is-a 的判断利器是「Liskov 替换原则」：<strong>凡能接受基类对象的地方，替换成派生类对象不应破坏程序行为</strong>。`Square` 继承 `Rectangle` 是教科书级的反例：把 `Rectangle` 的 `setWidth` 用到 `Square` 上会破坏「宽高相等」不变量——is-a 成立，但「可替换」不成立，继承仍错。</span>

## 2 条款33：避免遮掩继承而来的名称

**易错点：** 派生类里声明一个名字（哪怕形参完全不同），就会**隐藏**基类的同名成员——C++ 作用域规则是「内层作用域的名字遮蔽外层」，与重载无关：

```cpp
class Base {
public:
    void mf1(); void mf1(int);
    virtual void mf2();
};
class Derived : public Base {
public:
    void mf1();          // 隐藏了 Base 的两个 mf1！
};
Derived d;
d.mf1();      // 派生版本
d.mf1(42);    // 编译错误：基类 mf1(int) 被藏起来了
```

**对策**：想「继承同名一族」，用 **`using` 声明**把基类版本引入派生类作用域：

```cpp
class Derived : public Base {
public:
    using Base::mf1;     // 把 Base::mf1 的两个版本都请回来
    void mf1();          // 再叠加自己的版本
};
```

**重点：** 名字隐藏的规则是「**按名字**」而非「按签名」——`mf1` 一出现，基类的 `mf1` 全部被藏。这与第6章函数重载的「签名匹配」是两套作用域规则，不可混淆。<span class="marginnote">隐藏规则有个「聪明反被聪明误」的变体：派生类想「隐藏虚函数、不重定义」，结果只是名字隐藏、虚函数链反而断了。<strong>隐藏与 override 是两回事</strong>——override 需要签名匹配，隐藏只要同名。写 `virtual` 函数时用 `override` 关键字，编译器能立刻帮你抓出「本想覆盖、实际隐藏」的错误。</span>

## 3 条款34：区分接口继承和实现继承

**重点：** 继承传递的不只是代码，而是**三类东西**，设计时要想清楚「这一句继承要的是哪一类」。下表是核心对比表：

| 你写的 | 派生类得到 | 含义 |
| --- | --- | --- |
| 纯虚函数 `= 0` | **只继承接口** | 派生类必须自己实现，基类不给实现 |
| 虚函数（带实现） | **接口 + 缺省实现** | 派生类可选覆盖，也可直接用基类实现 |
| 非虚函数 | **接口 + 强制实现** | 派生类**不得**重定义 |

- **纯虚函数** = 「你必须会做这件事」（接口契约）。
- **带实现的虚函数** = 「你必须能做，但如果你愿意，就用我的默认做法」（缺省实现）。
- **非虚函数** = 「你不需要改，也**不该**改」——非虚函数在 C++ 里是「永不变化的行为」的标记（条款36）。

**易错点：** 「虚函数 + 缺省实现」有个陷阱——派生类继承缺省实现时，**默认行为可能不适合它**（比如企鹅继承 `fly` 的默认实现）。对策是「缺省实现不要做成虚函数体，而是做成 protected 的非虚辅助函数」——这就是 **NVI（non-virtual interface）** 的前身。<span class="marginnote">这三类继承的分野是第15章「接口继承 vs 实现继承」的精确化：<strong>纯虚 = 接口；虚 = 接口+可覆写的实现；非虚 = 不可覆写的实现</strong>。想清楚「我要给派生类什么」，比「能不能继承」重要得多——Meyers 的建议是「宁可多给接口、少给可覆写实现」。</span>

## 4 条款35、36、37：虚函数的替代、别重定义非虚与默认参数

**条款35——考虑虚函数以外的其他选择**：虚函数不是实现「多态行为」的唯一办法。替代方案：

- **NVI 惯用法**：public 非虚函数调 private/protected 虚函数——「公共接口固定、钩子可覆写」。
- **函数指针 / `std::function` 数据成员**：把「行为」作为可注入的对象，运行期替换。
- **Strategy 模式**：行为委托给另一个类（组合优于继承）。
- **模板 + 编译期多态**：第16章的模板在编译期实现同样的「按类型分发」。

**易错点：** 「虚函数是万能的」是 C++ 新手最常见的预设——其实「行为可变」至少还有上述四条路，且**它们都比「改虚函数继承树」更容易测试、更容易组合**。选型标准：行为的**变体数量**与**变化频率**。

**条款36——绝不重新定义继承而来的非虚函数**：

```cpp
Base *b = &d;   Derived *pd = &d;
b->mf();        // 调用 Base::mf（静态绑定）
pd->mf();       // 调用 Derived::mf（若被重定义）
```

非虚函数**静态绑定**：同一对象，经基类指针调与经派生类指针调，结果可能**不同**——「同一个东西、行为不一致」，违背直觉。所以非虚函数就是「不该被重定义」的承诺，重定义它等于打破契约。

**条款37——绝不重新定义继承而来的默认参数值**：虚函数**函数体动态绑定、默认参数静态绑定**（第15章讲过）——派生类重定义默认参数，会出现「调用派生类函数体、却用了基类默认参数」的分裂。**对策**：永远不重定义默认参数，只在基类里定一次。<span class="marginnote">条款36+37 是「继承契约」的最后一环：<strong>非虚函数与默认参数都是「静态绑定」的东西，重定义它们会让「静态看」与「动态跑」撕裂</strong>。一句话概括三条：接口继承（纯虚）随意覆写，实现继承（虚）谨慎覆写，非虚与默认参数绝不覆写。</span>

## 5 条款38、39、40：组合、私有继承与多重继承

**条款38——通过复合塑模出 has-a 或 is-implemented-in-terms-of**：**组合（composition）**让一个类持有另一个类的对象——表示「有一个」（has-a）或「用另一个类来实现自己」（is-implemented-in-terms-of）。组合是**最安全的复用手段**：没有继承的名字隐藏、没有虚函数链、没有「is-a 的语义负担」。

**条款39——明智而审慎地使用 private 继承**：private 继承表示「**is-implemented-in-terms-of**」——它不产生「是」的关系，只复用实现，且基类的 public/protected 成员在派生类里全变 private。**凡能用组合表达的，就别用 private 继承**；private 继承只在「需要 protected 成员 / 需要重定义虚函数」等组合做不到时才上场。

**条款40——明智而审慎地使用多重继承**：多继承（第18章）带来菱形问题与二义性，但也有正当用途——**纯接口组合**（每个基类都只有纯虚函数，无状态冲突）。<span class="marginnote">这三条的排序本身就是一份建议：<strong>组合（38）优先于 private 继承（39）优先于多重继承（40）</strong>。Meyers 给多继承开的「安全处方」：所有基类都是「接口类」（只有纯虚函数 + 虚析构），继承它们只有接口、没有实现与状态——菱形问题的两大麻烦（状态重复、初始化顺序）就都不存在了。</span>

**一条实践判断**：拿不准「该用继承还是组合」时，问两个问题——「派生类真的**是一种**基类吗？把它当基类用会不会破坏语义？」（是 → public 继承）；「我只是想**复用**基类的实现吗？」（是 → 组合或 private 继承）。大多数「为了省代码」的继承，改成组合后代码更直白、耦合更低。

## 6 小结

- **条款32**：`public` 继承 = **is-a**；企鹅不会飞就该有中间层，is-a 用 Liskov 可替换性检验。
- **条款33**：派生类名字**按名遮蔽**基类同名字族；用 `using 声明` 请回基类版本。
- **条款34**：纯虚 = 接口、虚 = 接口+缺省实现、非虚 = 强制实现——想清楚「给什么」。
- **条款35–37**：行为可变有 NVI/函数指针/Strategy 等替代；**非虚函数与默认参数绝不重定义**。
- **条款38–40**：组合 > private 继承 > 多重继承；多继承只用于纯接口组合。
- 本章主线：**继承是契约，不是便利**——用得越少越安全，组合总是优先的备选。
