## 为什么从实现细节开始

前几章谈接口，第5章（条款26–31）落回**函数体里怎么写**——这些「实现细节」恰恰是线上性能与正确性事故的高发地：**变量定义放哪**（26）、**怎么最小化转型**（27）、**别返回内部句柄**（28）、**怎么写异常安全代码**（29）、**inline 的真相**（30）、**怎么最小化编译依赖**（31）。这一章的独特价值在于「正确性 + 性能 + 可维护性」三线并进：每一条都同时教你「别踩坑」和「为什么」。<span class="marginnote">第5章的气质与前几章不同：前面是「接口语义」、这章是「实现功夫」。Meyers 自己说，第5章是「把正确的代码写出来」——<strong>正确性不是「恰好能跑」，而是「无论异常、优化还是重构，都依然正确」</strong>。</span>

## 1 条款26：尽可能延后变量定义式的出现时间

**易错点：** 在函数开头定义一堆变量，结果某些分支根本用不到它们——每次定义都付出**构造 + 析构**成本，白花了：

```cpp
std::string encrypt(const std::string &password) {
    std::string encrypted;          // 构造了，但可能下面直接 return
    if (password.length() < 8) return "too short";
    encrypted = password;           // 赋值而非初始化——又付一次默认构造
    return encrypted;
}
```

**对策：** 把定义挪到「真正需要它」的地方，并且**用值初始化而非「先默认构造再赋值」**：

```cpp
if (password.length() < 8) return "too short";
std::string encrypted(password);    // 需要时才构造，且直接初始化到位
```

**重点：** 这条不仅省开销，更让「这个变量负责什么」一目了然——变量只在它的用途附近活着，读代码的人不必来回跳。<span class="marginnote">延后定义在循环里尤其值得想：<strong>「每轮循环都构造临时对象」vs「循环外定义、循环内赋值」</strong>——前者每次构造+析构，后者只在首轮构造、但「赋值比初始化慢」且容易误保留旧值。Meyers 的结论是：除非赋值比构造+析构便宜得多，否则倾向「在循环内定义」——可读性优先。</span>

## 2 条款27：尽量少做转型动作

**易错点：** 转型是「让编译器把类型 A 当类型 B 看」——它能掩盖真实问题，且每种转型都有代价与陷阱：

```cpp
int x = static_cast<int>(3.14);          // 明确截断：OK
const_cast<char*>(...);                  // 去掉 const：只在「原始对象非 const」时安全
reinterpret_cast<int*>(...);             // 位级重解释：完全依赖平台
Base *b = dynamic_cast<Base*>(&derived); // 多态转型：运行期检查，有开销
```

**重点：** 转型最危险的坑在**继承下的地址调整**——C++ 里「指向派生类的基类指针」与「指向派生类对象的指针」**数值上可能不同**（多继承时尤甚），`static_cast` 会做偏移修正；而 `reinterpret_cast` **不做修正**，把它当「位拷贝」用会得到错误的地址。**对策**：能不用转型就不用；必须用时先问「是不是设计在逼我转型」——用虚函数或模板通常能免掉一半转型。<span class="marginnote">Meyers 的名言：「转型常常会打乱类型系统」（casts subvert the type system）。一条实用反例：<strong>构造/析构期间用 dynamic_cast 转型自己</strong>，返回的不是派生类版本而是当前层——因为构造期的动态类型就是当前构造层。想「构造期多态」，用「派生类把需要的参数传给基类」的常规手法，而不是转型。</span>

## 3 条款28：避免返回指向对象内部成分的句柄

**易错点：** 返回 `operator[]`、`getData()` 等暴露内部数据的**引用/指针**，会让外部绕过封装直接改内部状态，且**悬垂**风险极高：

```cpp
class Rect {
    Point &upperLeft() { return ul_; }   // 返回内部成员的引用
};
const Rect r;                             // const 对象
r.upperLeft();                            // 编译错误（非 const 版本被拒绝）——还算幸运
```

更隐蔽的是**悬垂句柄**：成员函数返回「指向容器元素的引用」，调用方持有它、容器随后 `push_back` 扩容——引用指向已失效内存。**对策**：数据藏深（pimpl）、返回**值或 const 引用**、或干脆不返回内部句柄。<span class="marginnote">返回 const 引用比返回非 const 引用安全一大截，但还有隐患：<strong>const 引用仍会「悬垂」</strong>——返回的临时对象离开表达式就销毁，引用随即失效。真正稳的规则：<strong>优先返回值</strong>（小对象靠 RVO 零开销）、返回引用只用于「调用方明确知道生命周期」的场合。</span>

## 4 条款29：为「异常安全」而努力

**异常安全（exception safety）**分三个保证等级，你的函数至少要达到一个：

- **基本保证（basic）**：抛出异常后，对象处于**合法但状态未指定**——不泄漏、不崩溃，但数据可能变了一半。
- **强保证（strong）**：抛出异常后，对象状态**完全回滚**，像没执行过一样——靠「先拷贝一份、成功后 swap」实现。
- **不抛保证（nothrow）**：**绝不抛异常**——内置操作、`swap` 常走这一级。

```cpp
void PrettyMenu::changeBackground(std::istream &imgSrc) {
    Lock ml(&mutex);                    // RAII：锁一定释放（基本保证的下限）
    Bitmap *newBmp = new Bitmap(imgSrc);  // 先做「可能失败」的部分
    delete bgImage;                     // 再动「既有的状态」
    bgImage = newBmp;                   // 最后才提交
    ++changeCount;
}
```

**重点：** 异常安全的核心手法是 **copy-and-swap**——先在一个**副本**上操作，全部成功后用不抛异常的 `swap` 一次性替换，从而把「失败」挡在提交之前。配合 RAII（锁、智能指针），「不泄漏」是底线、「不强保证」是目标。<span class="marginnote">copy-and-swap 与第2章条款11（自赋值）同源：<strong>「先制造一个必然成功的状态，再一次性切换」</strong>。它同时解决自赋值与异常安全——这是 C++ 里少见的「一个技巧两处收益」。对「修改容器内部多个成员」的操作，先整块拷贝、再 swap，是达成强保证的标准姿势。</span>

## 5 条款30 与 31：inline 的真相、最小化编译依赖

**条款30——透彻了解 inline 的里里外外**：`inline` 是**对编译器的请求**，不是命令——它让「函数调用」在调用点展开。**能 inline 的前提是函数体必须可见**（通常得在头文件里）。但 inline 不是免费的：

- **代码膨胀**：调用点内联多次，二进制变大、指令缓存命中率下降——「小且热」的函数才值得。
- **虚函数几乎不能 inline**：目标要到运行期才确定（vtable 间接调用）。
- **调试困难**：inline 展开后，断点与调用栈都变糊——**发布版才开 inline 优化**。

**对策**：把 inline 留给**真正小**的访问器/工具函数；`= default` 的构造/析构在编译器内联的候选里，别手动强加。

**条款31——将文件间的编译依存关系降至最低**：头文件一改，所有 include 它的 `.cpp` 全部重编——这是大型项目「改一行、编译十分钟」的根源。对策是「**头文件只依赖声明，不依赖定义**」：

- **Pimpl idiom（指针指向实现）**：头文件只放「指向实现类的指针成员」，实现细节全部藏进 `.cpp`。
- 尽量用**指针/引用成员**（前向声明即可）而非「按值持有需要完整定义的类」。
- 用接口基类 + 工厂函数，让客户代码只依赖抽象。<span class="marginnote">Pimpl 的代价值得权衡：每次访问成员都要多一层指针解引用、多一次间接；但它换来的「编译依赖隔离」在大型代码库是巨大的工程收益。<strong>头文件是接口的合同，合同越薄、改动越少人受影响</strong>——这正是第4章条款22「数据私有」的工程版。</span>

**一组对照：三种异常安全级别在「登录函数」上的差别**——基本保证：密码验证失败时，会话计数器可能已经 +1（但对象仍合法）；强保证：先在整个副本上验证、成功才 swap 提交，失败则计数器原样；不抛保证：`swap` 会话指针、`noexcept` 的锁定操作。写实现时「先定级别，再写代码」比「写完再补安全」可靠得多。

**补充一条「延迟计算」的加分项**：条款26的延伸是「**需要时才计算**」——把「昂贵且可能用不到」的计算推迟到第一次真正访问时（lazy initialization）。例如 `bool firstUsed() const { if (!initialized_) { compute(); } return initialized_; }`。它与「延后变量定义」是同一哲学在不同尺度上的体现：**不提前付代价，用到才付**。

**回看全局**：条款26–31 把「实现」从「把逻辑写对」升级为「在异常、优化、重构三重压力下依然写对」——延迟定义省开销、少转型守类型、藏句柄保封装、copy-and-swap 求安全、inline 慎用、Pimpl 隔离依赖。它们是一套「实现层次的最小美德」，彼此正交、缺一不可。

**核心对比表：异常安全三级**（条款29）——

| 级别 | 抛出后状态 | 实现手法 | 典型 |
| --- | --- | --- | --- |
| 基本保证 | 合法但状态未指定 | RAII 不泄漏 | 多数函数 |
| 强保证 | 完全回滚 | copy-and-swap | 提交型操作 |
| 不抛保证 | 绝不抛出 | noexcept / 纯内置操作 | swap、move |

## 6 小结

- **条款26**：变量**用到才定义**、直接初始化而非先构造再赋值。
- **条款27**：**少转型**；多继承下指针地址会修正，`reinterpret_cast` 不修正——能免则免。
- **条款28**：**别返回内部句柄**；优先返回值、次选 const 引用，警惕悬垂。
- **条款29**：异常安全三级（基本/强/不抛）；**copy-and-swap** 同时达成自赋值安全与强保证。
- **条款30**：inline 是请求非命令，虚函数难内联、代码膨胀是代价——只 inline 小而热的函数。
- **条款31**：**Pimpl + 前向声明**隔离编译依赖，让「改实现不触发全项目重编」。
