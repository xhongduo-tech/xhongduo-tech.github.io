## 为什么从 HTTPS 开始

上一篇把 TLS 讲透了：握手协商、记录加密、会话恢复。但 TLS 只是一台「加密引擎」——**它要真正改变世界，必须被接进应用**。而 Web 正是它最大的应用场景：今天你访问的任何正经网站，地址栏前缀都是 `https://`。

**HTTPS 就是 HTTP over TLS**：把原本明文传输的 HTTP 请求/响应，整个塞进 TLS 记录协议里加密封装。对用户，它是地址栏那把锁；对攻击者，它是窃听、篡改、会话劫持的全面屏障。理解 HTTPS，等于理解「TLS 这台引擎如何被装配进人类最大的公共基础设施——Web」。<span class="marginnote">HTTPS 与 TLS 的关系是「应用套壳」：TLS 本身与 HTTP 无关，任何应用协议（HTTP、SMTP、FTP）都能套。HTTP 套上 TLS 就变成 HTTPS，这是应用层安全最成功的一次嫁接。</span>

HTTPS 的历史也是 Web 安全演进的缩影：网景 1994 年发明 SSL 就是为了保护在线支付，从此「加密 + 身份验证」就成了 Web 的商业底线。本篇从威胁出发，讲清 HTTPS 到底保护了什么、证书链如何建立信任、以及 Web 会话安全里那些藏在细节里的坑。

## 1 Web 安全的威胁全景

Web 的安全威胁可以从两个视角切开：**威胁的位置**（客户端侧还是服务器侧）与**攻击的主动性**（被动还是主动）。

**被动攻击（passive attacks）**：攻击者只「听」不「动」——监听网络上传输的明文数据，读取敏感信息。HTTP 时代这几乎是免费的午餐：咖啡店公共 Wi-Fi 上，同一网段的人用 Wireshark 就能抓到你提交的账号密码。**HTTPS 的加密正是为对抗被动攻击而生。**

**主动攻击（active attacks）**：攻击者直接动手——篡改传输中的数据、冒充服务器钓鱼、向客户端注入恶意内容。主动攻击的目标不止服务器，**客户端同样是被攻击对象**：恶意网页利用浏览器漏洞植入木马，这引出了 Web 安全的另一半战线——客户端安全。<span class="marginnote">客户端安全是 Web 独有、却常被低估的一环：TLS 保护「传输途中」，但恶意网页、钓鱼站、浏览器漏洞攻击的是「浏览器本身」。纵深防御在这里表现为「传输加密 + 浏览器加固 + 用户警觉」三层。</span>

斯托林斯把 Web 威胁归纳为四个对象维度：**服务器上的数据、服务器与客户端之间传输的数据、服务器本身、客户端本身**。一张表看清：

| 威胁对象 | 典型攻击 | 对策 |
| --- | --- | --- |
| 传输中的数据 | 窃听、篡改、会话劫持 | TLS/HTTPS 加密与认证 |
| 服务器数据 | SQL 注入、目录遍历 | 服务端输入校验、访问控制 |
| 服务器本身 | 漏洞利用、DDoS | 加固、补丁、WAF |
| 客户端 | 恶意代码、钓鱼 | 浏览器沙箱、用户教育 |

## 2 HTTPS：HTTP 套上 TLS

**核心概念：HTTPS**：在标准 HTTP 之下插入一个 TLS 层，使所有 HTTP 报文在发出前先经 TLS 加密封装。默认端口是 **443**（HTTP 是 80）。它的协议栈从下到上是：TCP → TLS 记录协议 → TLS 握手协议与 HTTP——HTTP 本身**一行不改**，全靠下面垫着的 TLS 提供安全服务。

浏览器访问一个 HTTPS 网站时，做的事情是上一篇 TLS 握手的完整重演：

1. 浏览器与服务器完成 TCP 三次握手；
2. TLS 握手：协商密码套件、交换密钥、验证服务器证书；
3. 握手完成，双方开始用会话密钥加密传输 HTTP 报文。

**重点：HTTPS 一次同时拿到了机密性、完整性、真实性三件套**。机密性靠对称加密，完整性靠 MAC（TLS 1.3 用 AEAD），真实性靠服务器证书——而其中「真实性」正是 HTTP 时代最被忽视、却最致命的一环。没有它，中间人可以在你和网站之间放一个假服务器，把你的流量全部照单收走。<span class="marginnote">「中间人攻击」是 HTTPS 要根治的头号威胁：攻击者冒充网站、骗取你的请求，再替你转发给真网站——你看到的是「加密」的假连接，隐私照样泄露。证书存在的意义，就是让中间人无处遁形。</span>

**辨析｜易错点：** 不要以为「https:// 的网站就安全」。HTTPS 保护的是**传输管道**，不保护**管道两头**：一个恶意网站同样可以申请 HTTPS 证书，把钓鱼页面加密得漂漂亮亮。HTTPS 证明「这个域名是真的、通信是加密的」，但**不证明这个网站值得信任**——这要靠安全策略与用户的判断。

## 3 证书链：浏览器如何相信服务器

浏览器第一次访问 `https://example.com`，凭什么相信拿到的证书是真的？答案是**证书链（certificate chain）**——一条从「你的浏览器」追到「根证书」的信任路径。

验证分三层：

**第一层，检查证书本身**：证书是否在有效期内、域名是否与请求的网站一致、证书是否已被吊销（用 OCSP 或 CRL 查询）；
**第二层，检查签发者**：这张证书是谁签发的？浏览器用「签发者的公钥」验证证书上的签名；
**第三层，回溯到根**：签发者本身也是证书（中间 CA），继续往上查它的签发者……直到遇到**根 CA**——根证书预装在浏览器/操作系统的信任库里，是这条链的终点。**链上的每一环都有效，信任才成立。**

这个「回溯到根」的机制，正是 PKI 篇里讲的证书体系在 Web 上的实战：浏览器无需认识每一个网站，只需预装几十个根 CA 的证书，就能验证全世界的 HTTPS 网站。<span class="marginnote">「预装根证书」是信任的起点，也是攻击面：如果某个根 CA 被攻破，它就能为任意域名签发证书——2011 年 DigiNotar 事件中，被攻破的荷兰 CA 曾为 Google 等域名签发伪造证书，最终导致整个 CA 被浏览器厂商踢出信任库。</span>

**重点：证书链的本质是「代际信任」**——根 CA 信任中间 CA，中间 CA 信任网站。链越长，信任传递的环节越多，验证开销越大，但也让「信任管理」得以集中：你只需管理根，剩下的交给层级。

## 4 Web 会话与 Cookie 安全

HTTPS 解决了「传输」，但 Web 应用的安全远不止传输——**会话（session）与 Cookie** 是另一个主战场。

HTTP 是无状态协议，服务器记不住「你是谁」；为了维持登录状态，服务器签发一个**会话标识**，浏览器用 **Cookie** 把它存下来，每次请求带上。问题来了：**如果攻击者偷到了你的会话 Cookie，就能冒充你登录**——这叫**会话劫持（session hijacking）**。

现代浏览器给 Cookie 提供了三道安全护栏：

**Secure 属性**：Cookie 只在 HTTPS 连接上传输，杜绝明文网络上的窃取；
**HttpOnly 属性**：脚本（JavaScript）无法读取该 Cookie，堵死 XSS 攻击窃取会话的路径；
**SameSite 属性**：限制 Cookie 随跨站请求发送，缓解 **CSRF（跨站请求伪造）**——攻击者在恶意网站诱导你发起对目标站的请求，若无 SameSite 限制，你的浏览器会「乖乖带上」目标站的会话 Cookie。

**重点：Web 安全是「传输 + 应用」的合力**。HTTPS 把传输管道封死，Cookie 的 Secure/HttpOnly/SameSite 把应用层会话管住，两者缺一不可——只加密不设防，会话照样能被偷。<span class="marginnote">XSS（跨站脚本）是「偷会话」的经典入口：攻击者把恶意脚本注入页面，脚本读取 `<strong>HttpOnly 之外的</strong> Cookie 并外传。HttpOnly 让脚本「有权限执行、却读不到会话」，是把攻击者的手从最值钱的筹码上挪开。</span>

## 5 HSTS 与 HTTPS 的降级陷阱

HTTPS 有一个隐蔽的软肋：**用户是主动输入 `http://` 还是被引导到 HTTPS，取决于网站**。如果用户在地址栏输入 `example.com`，浏览器默认先走 HTTP（明文），网站再 302 重定向到 HTTPS——**这个「先 HTTP 后重定向」的窗口，正是中间人劫持的机会**：攻击者在你发出 HTTP 请求时抢先应答，把连接引向钓鱼站。

对策是 **HSTS（HTTP Strict Transport Security）**：网站通过一个响应头告知浏览器「**未来一段时间内，只允许用 HTTPS 访问本站**」。浏览器记住这条指令后，任何 `http://` 请求都会被**自动改写为 `https://`**，中间人失去劫持窗口。HSTS 是「把安全选择权从用户手里交给协议」的典型设计——用户不需要理解，浏览器自动保护。

**辨析｜易错点：** HSTS 依赖「第一次访问必须是安全的」——浏览器第一次访问时若已被劫持，HSTS 指令本身都可能被抹掉。这就是著名的 **HSTS 预加载（HSTS preload）** 解决的问题：浏览器把一批知名网站（如 Google、PayPal）的 HSTS 指令**内置进浏览器**，第一次访问就直接走 HTTPS，彻底封死降级攻击。<span class="marginnote">HSTS preload 与 PKI 的根证书异曲同工：都是「在浏览器里预置信任」。区别是预加载名单由浏览器厂商维护，网站需申请加入。安全总是「少信任用户的选择，多信任内置的规则」。</span>

## 6 核心对比表：HTTP vs HTTPS

> 本篇为纯概念主题，按编辑章程以核心对比表替代公式解析。

HTTP 与 HTTPS 的差异，浓缩成一张表：

| 维度 | HTTP | HTTPS |
| --- | --- | --- |
| 底层协议 | 明文 TCP | TCP + TLS |
| 默认端口 | 80 | 443 |
| 机密性 | 无（明文传输） | 有（对称加密） |
| 完整性 | 无 | 有（AEAD/MAC） |
| 服务器认证 | 无 | 有（证书链验证） |
| 性能开销 | 低 | 多一次握手，开销可优化（会话恢复/1-RTT） |
| 典型状态 | 已基本淘汰 | 现行标准，浏览器强制推广 |

**重点：HTTPS 不是「HTTP 的增强版」，而是「换了地基」**。它解决的不只是加密，而是把「可信身份」也装了进去——服务器必须证明「我是我」，用户才敢把凭据交给它。这正是从「加密通信」走向「可信通信」的关键一步。

现代 Web 的另一个趋势是 **TLS 1.3** 带来的性能革命：握手从 TLS 1.2 的两次往返（2-RTT）压缩到一次往返（1-RTT），复用会话时甚至 **0-RTT**——安全性提升的同时，连接更快。加密不再是「贵的代价」，而是「默认的底线」。

## 7 小结

- **HTTPS = HTTP + TLS**，默认 443 端口，一次拿到机密性、完整性、真实性三件套。
- HTTPS 保护**传输管道**，不保护管道两头的恶意网站——加密不等于可信。
- 证书链验证通过「预装根证书 → 回溯到根」建立信任，根 CA 是信任的锚点。
- 会话安全靠 **Cookie 的 Secure / HttpOnly / SameSite** 三属性联防会话劫持与 CSRF。
- **HSTS** 强制浏览器只走 HTTPS，封死「先 HTTP 再重定向」的降级攻击窗口。
- 现代 Web 全面走向 HTTPS，TLS 1.3 让加密更快、更省往返。
