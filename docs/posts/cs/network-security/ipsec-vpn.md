## 为什么从 IPSec 开始

TLS 保护了 HTTP，却保护不了「IP 层以下的一切」——源目 IP、TCP 端口、路由信息统统裸露。如果一台主机与另一台主机之间想加密**所有**流量（不限于某个应用），或者两个子网之间想建立一条「安全管道」，TLS 就无能为力了。这正是 **IPSec** 登场的理由：**它在 IP 层工作，为每一个 IP 数据报提供安全服务，对上层应用完全透明。**<span class="marginnote">IPSec 与 TLS 的分工是层次问题：TLS 在传输层之上管「应用数据」，IPSec 在网络层管「整个 IP 数据报」。企业远程接入、分支机构互联普遍用 IPSec 而非 TLS，就是因为要保护的是「所有流量」，而不只是某个应用。</span>

IPSec 的实际载体是 **VPN（虚拟专用网络）**：在公共网络上「虚拟」出一条专用加密通道。本篇先讲 IPSec 的架构与两种协议（AH/ESP），再讲它们如何组装成 VPN。

## 1 IPSec 能做什么：六大服务

IPSec 协议族为 IP 流量提供六种安全服务，可以理解为一张能力清单：

**访问控制**：只有持有合法密钥与 SA 的实体能通信；
**无连接完整性**：数据报在途未被篡改；
**数据源认证**：确认数据报确实来自声称的源地址；
**防重放（anti-replay）**：拒绝重放的旧数据报；
- **机密性**：载荷加密，中间人不可读；
- **有限流量流机密性**：通过隧道封装，连「谁在和谁通信」都难以观察。

**重点：六项服务不总是同时启用，由 SA 与策略决定组合**。有的场景只要完整性与认证（AH），有的要机密性（ESP），有的全要。理解 IPSec 的关键，是先理解它是「按安全关联工作的框架」，而不是单一算法。

IPSec 的落地载体也值得一提：它既可以**端到端**部署（两台主机），也可以**网关到网关**部署（两台防火墙/路由器），还可以**端到网关**（远程用户到企业网关）。部署位置决定安全边界——网关模式让内部主机「无感获得安全」，但端点间（网关内部）的流量不在保护范围内。

VPN 的典型形态有三种：**远程访问 VPN**（单个用户拨入企业网）、**站点到站点 VPN**（两个分支机构之间）、**内联网/外联网 VPN**（企业与伙伴之间）。三种形态共享同一套 IPSec 内核，只是端点与规模不同。<span class="marginnote">「VPN」一词常被滥用：凡是加密隧道都叫 VPN。但实现有 TLS-VPN、IPSec-VPN、WireGuard 之别；本专题聚焦 IPSec，它是历史最久、标准最全的 VPN 体系。</span>

## 2 安全关联 SA：IPSec 的「连接」

**核心概念：安全关联（Security Association, SA）**：两个通信实体之间为 IPSec 会话建立的一个单向逻辑连接，规定了使用哪个协议（AH 还是 ESP）、什么算法、什么密钥、什么 SPI（安全参数索引）。**SA 是单向的**——双向通信需要两个 SA，各自方向一个。

IPSec 端点用两个数据库管理 SA：

**安全关联数据库（SAD）**：存放已建立的 SA 及其实例化参数（密钥、算法、SPI、序号）；
**安全策略数据库（SPD）**：存放「什么流量该用哪种安全处理」的规则表。

**重点：SPD 决定「做什么」，SAD 决定「怎么做」**。每个出站数据报先查 SPD 匹配策略（丢弃 / 绕过 / 应用 IPSec），再查 SAD 取对应的 SA 执行处理；入站数据报则凭 SPI 在 SAD 里找到匹配的 SA 进行验证与解密。<span class="marginnote">SPD/SAD 的「先策略、后执行」结构，与上一篇 NAC 的 PDP/PEP 分离异曲同工——策略与状态解耦，是网络安全架构里反复出现的同一模式。</span>

SA 不是永生的，它有**生存期（lifetime）**：按时间或按处理字节数到期后，SA 必须重新协商。原因还是那一句「一次一密」——同一个密钥用得太久，暴露面随字节数累积，泄密损失也随之放大。**密钥的定期轮换，是 SA 机制里最不起眼却最关键的安全习惯。**

## 3 传输模式与隧道模式

IPSec 有两种封装方式，决定「保护到什么程度」：

**传输模式（transport mode）**：只保护 IP 载荷，不改动原 IP 头。典型用于端到端通信（两台主机直连），开销小。
**隧道模式（tunnel mode）**：把**整个原始 IP 数据报**封装进一个新的 IP 数据报，新外层头由隧道端点使用。典型用于 VPN 网关之间——两边的内部地址对新外层头完全不可见，连拓扑都被隐藏。

**重点：隧道模式是 VPN 的本质**。远程用户的数据报被整体加密后装进新信封，公共网络上看到的只有「网关到网关」的流量；进入企业网后解封装，内部地址重新可见。这就是「虚拟专用」四个字的物理含义。

两种模式的应用场景随之分明：**远程访问 VPN** 几乎总用隧道模式（用户网关是隧道端点，内部网络整体被保护）；**主机间直连**才用传输模式。判断口诀是——**只要有一方是「网络」（网关/子网），就选隧道模式；只有两边都是「主机」，才考虑传输模式。**<span class="marginnote">类比快递：传输模式是「给包裹贴封条」，隧道模式是「把包裹装进一只不透明的集装袋，再贴一张全新的快递单」。后者连包裹外形都看不到，隐私层级更高。</span>

## 4 AH 与 ESP：两个安全协议

IPSec 用两个协议承载上面的服务，方向互补：

| 协议 | 全称 | 机密性 | 完整性 + 认证 | 防重放 | 适用场景 |
| --- | --- | --- | --- | --- | --- |
| AH | 认证头 | 无 | 有（覆盖到部分 IP 头） | 有 | 纯认证、无加密需求 |
| ESP | 封装安全载荷 | 有 | 有（不覆盖外层 IP 头） | 有 | 绝大多数现代部署 |

**AH（Authentication Header）** 为数据报提供完整性、数据源认证与防重放，但**不加密**。它甚至认证 IP 头里的「不可变字段」（版本、源目地址、协议等），防止地址被篡改——代价是 NAT 兼容性差（NAT 要改写地址，会破坏 AH 的认证）。

**ESP（Encapsulating Security Payload）** 是绝对主力：既加密又认证，一个协议搞定机密性 + 完整性 + 防重放。NAT 兼容性比 AH 好，因为认证范围不含外层 IP 头。<span class="marginnote">AH 与 ESP 可以嵌套使用（先 AH 再 ESP），但实践中极少这样做——ESP 单挑就够了。IPv6 原生支持 AH/ESP，IPv4 则要靠 IPsec 实现追加。</span>

**辨析｜易错点：** 「AH 认证 IP 头、ESP 不认证 IP 头」看似 AH 更安全，但 AH 的完整性与 ESP 的完整性是**不同覆盖范围**：AH 认 IP 头，ESP 不认。实际选择几乎总是一边倒——**能用 ESP 就用 ESP**，因为它同时给了机密性，而机密性往往比「认证 IP 头」更值钱。

## 5 公式解析：ESP 的加密与认证装配

以**传输模式 ESP** 为例看数据报如何被处理。设原始载荷为 $P$，会话密钥 $K_e$ 与认证密钥 $K_a$，则加密与认证两步：

$$
C = E_{K_e}(P \| \text{pad} \| \text{pad_len} \| \text{next_hdr})
$$

$$
\text{ICV} = \text{HMAC}_{K_a}\big(\text{ESP 头} \;\|\; C\big)
$$

- **第一步，加密**：载荷 $P$ 补齐（pad）后连同「下一协议」字段一起用 $K_e$ 加密成密文 $C$——密钥、算法都由 SA 指定。
- **第二步，认证**：对「ESP 头 + 密文」计算完整性校验值 ICV，覆盖范围从 ESP 头到密文末尾，但**不含外层 IP 头**——这正是 NAT 兼容的原因。
- **第三步，装配**：最终数据报 = 外层 IP 头 + ESP 头 + $C$ + ICV。接收方先验 ICV（防篡改），再解密还原 $P$，恢复原始载荷。

这条流水线揭示了一个反直觉的事实：**ESP 的「加密」与「认证」是分开算的**——加密管「别人看不懂」，ICV 管「别人改不动」，两个密钥 $K_e$、$K_a$ 各司其职。攻击者既算不出 $K_e$（读不懂密文），也算不出 $K_a$（伪造不了 ICV），两者缺一不可。

## 6 密钥管理：IKE 如何建立 SA

SA 里的密钥不是凭空来的，IPSec 需要一个机制安全地协商它们——这就是 **IKE（Internet Key Exchange，互联网密钥交换）**。它在**建立 SA 之前**先做两件事：

**认证双方身份**：确认「我正在和谁建立 SA」——IKE 用预共享密钥或证书完成双向认证，防止攻击者冒充对端骗取 SA；
**协商算法与密钥**：通过 **Diffie-Hellman 密钥交换**（见本专题第2篇）在公开频道上协商出共享密钥——窃听者看得到交换过程，却算不出最终的共享秘密。<span class="marginnote">IKE 的架构与 TLS 握手异曲同工：都是「先认证、再协商密钥」的两阶段协议。事实上 IKE 早期版本曾直接借用 TLS 的思路，如今它自身就是一套完整的加密协议——加密自身、认证自身、防重放自身。</span>

IKE 还有两个版本值得留意：**IKEv1** 是经典版本，分「主模式 / 野蛮模式」两个阶段，流程冗长；**IKEv2** 精简了握手，把「建立 SA 的 SA」收敛进一次交换，可靠性、抗 DoS 能力都更强。现代部署几乎都转向 IKEv2。

**重点：IPSec 的完整生命周期是「IKE 协商 SA → ESP/AH 用 SA 保护流量 → SA 到期重协商」**。SA 不是一次性的，而是有生存期的动态对象——到期即换新密钥，这再次呼应了贯穿全篇的「一次一密」原则：**密钥用得越久，暴露面越大，定期轮换是 IPSec 的生命线。**

**辨析｜易错点：** 有人把「IPSec」与「IKE」混为一谈——**IPSec 是「数据面」协议（AH/ESP 保护数据），IKE 是「控制面」协议（协商数据面的密钥与 SA）**。没有 IKE，SA 无从建立，ESP 拿到密钥也无从谈起；没有 ESP，IKE 协商出的密钥没有用武之地。两者是「总装车间」与「装配工」的关系。

现代部署中，IKEv2 与 ESP 的配合已是标准组合：IKEv2 建 SA 时把 ESP 的加密算法、认证算法、密钥一起谈妥，之后 ESP 直接「拿着钥匙干活」。控制面与数据面的这种「一次谈妥、长期执行」分工，让 IPSec 既可靠又高效——这也解释了为什么 ESP（而非 AH）几乎总是数据面的选择：它一次搞定加密与认证，IKE 只需为一套算法谈判。

## 7 小结

- **IPSec** 在 IP 层工作，为每一个 IP 数据报提供访问控制、完整性、认证、防重放、机密性等安全服务。
- **SA 是单向逻辑连接**，由 **SAD**（怎么做）与 **SPD**（做什么）两个数据库管理，有生存期、需定期轮换。
- **传输模式**保护载荷，**隧道模式**封装整个原始数据报——隧道模式是 VPN 的本质。
- **AH 只认证不加密**，**ESP 加密 + 认证**是绝对主力；ESP 的认证范围不含外层 IP 头，因此 NAT 兼容性更好。
- 密钥由 **IKE**（认证身份 + DH 协商密钥）建立，IKEv2 是现行主力。
- 理解 IPSec 的关键是抓住主线：**IKE 协商 SA → ESP/AH 用 SA 保护流量 → SA 到期重协商**。
