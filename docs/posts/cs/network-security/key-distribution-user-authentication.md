## 为什么从密钥分发开始

前面的篇章解决了「算法设计」：我们有了一把把好锁（AES、RSA、签名）。但从今天起，问题转到「锁的钥匙怎么管理」——在实战里，**钥匙的配送与管理远比锁本身更脆弱**。你的 AES 密钥怎么送到对方手里？对方登录时，怎么确认他就是本人而不是偷了密码的人？

这一篇把两件事一起讲：**密钥分发**（把密钥安全送到该去的地方）与**用户认证**（确认对方的真实身份）。它们共享同一个底层难题——在没有预先信任的两个实体之间，如何建立信任。

先给一个全篇的航拍图：**密钥分发**解决「钥匙怎么送」，**用户认证**解决「对方是不是本人」，而把两者串起来的关键角色是**可信第三方（TTP）**——它要么保管并中转密钥（KDC/Kerberos），要么背书公钥（CA）。记住「可信第三方」这根主线，后面所有协议都顺着它展开。<span class="marginnote">本专题前四篇建好了密码学工具箱，本篇开始把工具组装进「协议」；下一篇《TLS/SSL》就是这套组装逻辑在互联网上最大规模的一次实战。</span>

## 1 对称密钥分发的四条路

对称加密的前提是双方共享密钥，但这条密钥从哪来？斯托林斯给出四种基本方案：

1. 由一方产生密钥，**物理地**（如专人递送）交给另一方；
2. 由**可信第三方（TTP）** 产生并物理分发给双方；
3. 若双方此前用过旧密钥，用旧密钥加密新密钥传输（但旧密钥被破则全盘皆输）；
4. 通过第三方连接双方，第三方用各自的密钥为其**中转会话密钥**——这是 KDC 模式的雏形。

**核心概念：密钥分发中心（Key Distribution Center, KDC）**：一个可信第三方，维护着与每个用户的长期密钥。当用户 A 想与 B 通信，A 向 KDC 申请会话密钥，KDC 生成一把临时密钥 $K_s$，分别用 A、B 的长期密钥加密后发给双方。这样**双方永远不用交换长期密钥**，只交换由 KDC 担保的临时会话密钥。<span class="marginnote">会话密钥用后即弃，是「密钥管理」里最核心的取舍：即使某次会话密钥泄露，也只损失这一次通信，长期密钥安然无恙。密钥的生命周期设计，决定了损失的爆炸半径。</span>

方案 4 看似完美，却引出一个新问题：**KDC 怎么知道「申请者真是 A」？** 伪装者也可以向 KDC 申请。这就必须叠加用户认证——也就是本篇的下半场。

顺带一提，方案 1、2 的「物理分发」今天仍以另一种形态存在：**离线预置**。云服务的根密钥、手机的 TOTP 种子、硬件的出厂证书，都是出厂时在可信环境里预置的。物理手段没有消失，只是被移到了供应链的最上游。

## 2 公钥 + 对称：混合体制

有了公钥密码，密钥分发有了第五条路：**用公钥加密来安全传递对称密钥**。发送方用接收方的公钥加密对称密钥 $K_s$ 发送，接收方用私钥解密得到 $K_s$，之后大数据流量用对称加密承载。

这种**混合体制（hybrid cryptosystem）** 兼顾了公钥的「免分发」与对称的「高性能」：公钥慢、只用来加密一个小密钥；对称快、用来加密海量数据。TLS、PGP、SSH 全部遵循这个模式。<span class="marginnote">这就是「混合」二字的分工智慧：昂贵的公钥运算只做一次「开门」，昂贵的对称运算负责「搬运」。凡是大流量的安全协议，几乎必然是这个结构。</span>

**辨析｜易错点：** 用公钥加密分发对称密钥，解决了**机密性**（只有对方能解），但若没有验证对方公钥的真实性，就会招来**中间人攻击**——你加密的对象可能是伪装者。这正是上一篇 PKI 存在的意义：**公钥本身要先被认证**。密钥分发与公钥认证是两件事，缺一不可。

## 3 Kerberos：票据式认证

**Kerberos** 是 MIT 开发的经典认证协议，其血缘可追溯到 1978 年的 **倪德翰—施罗特（Needham-Schroeder）** 协议——后者最早提出「由可信第三方分发会话密钥」的蓝图，却有一个著名的软肋：**旧会话密钥可被重放**。攻击者截获并保存一次旧通信后，日后可冒充合法用户重放旧票据。Kerberos 的改进是用**时间戳 + 有效期**让一切票据与认证子都「过时不候」，把这个漏洞补上。

Kerberos 把「认证」与「授权」拆成三个服务器：

**认证服务器（AS）**：验证用户口令，签发**票据授予票据（TGT）**；
**票据授予服务器（TGS）**：凭 TGT 为用户签发访问具体服务的**服务票据**；
- **服务服务器（SS）**：提供目标服务，验证服务票据。

一次典型登录走六步：

1. 客户端 → AS：申请 TGT；
2. AS → 客户端：用**用户口令派生的密钥**加密返回 TGT 与会话密钥（用户解不开口令就进不来）；
3. 客户端 → TGS：出示 TGT + **认证子（authenticator）**，申请服务票据；
4. TGS → 客户端：签发服务票据；
5. 客户端 → SS：出示服务票据 + 新认证子；
6. SS 验证后放行，并可回发一个认证子完成**双向认证**。

**重点：票据（ticket）是「身份证明」，认证子（authenticator）是「我在场证明」**。票据里含用户身份与有效期，用 TGS/SS 的密钥加密，他人无法伪造；认证子含用户 ID 与时间戳，证明「持票者此刻就在线」，时间戳同时封死了**重放攻击**——旧认证子一过期即作废。<span class="marginnote">Kerberos 的票据设计有一个优雅之处：AS 与 TGS 不用各自维护每用户的会话状态，凭「票据 + 时间戳」即可无状态验证。后来的 JWT（JSON Web Token）继承的正是这套「自包含票据」思想。</span>

Kerberos 还引入了**领域（realm）** 概念：一个管理域内的所有主体共享一套 KDC。跨领域访问时，两个 KDC 互相颁发交叉票据——信任由此在管理域之间传播。Windows 域认证、企业单点登录（SSO）至今仍以 Kerberos 为底。

## 4 公式解析：一次性口令 HOTP 与 TOTP

口令重放是认证的老大难：密码一旦被窃听就永远失效。**一次性口令（OTP）** 让每个口令只使用一次，窃听者拿到的口令瞬间作废。主流实现是 **HMAC 类 OTP**，分计数器版与时间版两种。

**HOTP（基于计数器）** 以计数器 $C$ 为输入：

$$
\text{HOTP}(K, C) = \text{Truncate}\big(\text{HMAC-SHA-1}(K, C)\big)
$$

- **$K$**：客户端与服务器共享的种子密钥；
- **$C$**：一个随使用次数递增的计数器，双方各自维护；
- **HMAC-SHA-1**：上一节的带密钥哈希，保证输出不可预测；
- **Truncate**：从 20 字节的 HMAC 输出里动态截取一段，转成 6–8 位数字。

**TOTP（基于时间）** 把计数器换成时间步：

$$
\text{TOTP}(K, T) = \text{HOTP}\big(K, \lfloor (T - T_0)/X \rfloor\big)
$$

$T$ 是当前 Unix 时间，$T_0$ 是起始时间（约定为 0），$X$ 是时间步长（通常 30 秒）。双方时钟在 30 秒内一致，就能算出同一个口令；超过步长，口令自动作废。<span class="marginnote">你手机上的谷歌身份验证器、各大银行动态令牌，用的就是 TOTP。它把「一次性」从「计次」变成「计时」，兼顾了安全（每 30 秒换一个）与便利（无需服务端计数同步）。</span>
