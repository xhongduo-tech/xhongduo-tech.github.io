## 为什么从网络访问控制开始

前面的 HTTPS 篇解决的是「应用的安全」，但这里有一个更靠前的问题：**在设备接入网络的那一刻，它是否可信？** 一台带着病毒、缺了补丁、来历不明的笔记本，一旦连进内网，就成了攻击者最爱的跳板——它绕过了防火墙、骗过了 IDS，因为**它合法地进入了网络内部**。

**网络访问控制（Network Access Control, NAC）** 要回答的正是这个问题：**在设备获准接入网络之前，先验证「你是谁、你干净吗」**。它与「先认证后入网」的思想一脉相承，是无线篇里 802.1X 那套逻辑的规模化升级。<span class="marginnote">NAC 的核心理念「先验证、再接入」，在网络安全史上反复出现：802.1X 端口认证、企业 Wi-Fi 的准入控制、云上的安全组，都是同一个思想的不同载体。本篇把它讲透，往后看任何「准入」类设计都会豁然开朗。</span>

本篇的后半场转向**云安全**：当「网络」被搬到云上，边界消失了、控制权转移了、威胁模型也变了。NAC 管「进门前」，云安全管「进门后」，两者合起来，是「网络访问」这条主线的完整闭环。

## 1 NAC 解决什么问题

传统网络的准入逻辑是「插上就能用」：设备连上交换机端口，就能访问内网资源。这种「物理接入即信任」的模式早已被打破——一台被攻陷的笔记本、一台蹭网的手机、一位访客的电脑，都能直接进入内网。

NAC 在「接入」之前强制完成两件事：

**身份认证（authentication）**：你是谁？凭据（账号口令、证书、设备指纹）能否证明你的身份；
**健康状态检查（posture assessment）**：你干净吗？杀毒软件是否更新、系统补丁是否齐全、是否被植入了恶意软件——不达标的设备，拒绝入网或只能进入「隔离网络」。

**重点：NAC 把「接入网络」从一个动作变成了一次「检查」。** 它是「先认证后入网」思想在企业网里的规模化落地：不合格的设备不是「进不来」，而是「进得来也被隔离」，防止它把风险传染给整个内网。<span class="marginnote">「健康状态检查」是 NAC 区别于一般认证的关键：它检查的不是「你是谁」而是「你身上干不干净」。访客、自带设备（BYOD）、外包人员的机器，正是 NAC 重点关照的对象——它们的身份没问题，但健康状态往往不可控。</span>

健康状态检查的**检查项**也很具体：杀毒软件是否安装且病毒库是否最新、操作系统补丁是否打齐、是否运行了被禁止的软件、是否启用防火墙。每一项都对应一个「合规基线」——设备达标才放行，不达标则引导到**补救网段（remediation network）**：那里只提供升级补丁、安装杀毒的通道，把设备「修好」了才能再申请入网。这种「不合格即隔离、修好再放行」的闭环，是 NAC 相对「拒绝/允许」二分法的精细之处。

## 2 NAC 的架构：PDP 与 PEP

NAC 的架构在产业界有多个实现（思科的 TrustSec、微软的 NAP），但骨架是同一个**三组件模型**：

**策略决策点（Policy Decision Point, PDP）**：NAC 的「大脑」，集中评估接入请求、查阅安全策略、做出「允许 / 拒绝 / 隔离」的决策；
**策略执行点（Policy Enforcement Point, PEP）**：NAC 的「手脚」，串在流量路径上（交换机端口、无线接入点、网关），执行 PDP 的决策——放行、阻断或隔离；
**接入请求者（Access Requestor, AR）**：申请接入网络的设备，与 PEP 交互，向 PDP 提供身份与健康状态信息。

**重点：PDP 与 PEP 的分离，是 NAC 架构的灵魂**——决策与执行解耦：PDP 集中管策略、好维护；PEP 分布在各处、只管执行。这个「先决策、后执行」的结构，你在本专题已多次见到：IPSec 的 SPD/SAD、802.1X 的认证流程，都是同一模式。<span class="marginnote">「决策与执行分离」是网络安全架构里反复出现的母题：策略集中、执行分布，让「改一条策略」不需要碰每一台设备。云上的「集中策略 + 边缘执行」、SDN 的「控制器 + 交换机」，都是这一思想的不同投影。</span>

## 3 NAC 的接入流程：四步放行

一次标准的 NAC 接入，走四步：

1. **设备发起接入**：设备连上 PEP（交换机端口 / Wi-Fi 接入点），此时端口处于「未认证」状态，只放行认证相关流量；
2. **PEP 转发请求**：PEP 把设备信息转发给 PDP，询问「这个设备能不能进」；
3. **PDP 评估**：PDP 核实身份（认证服务器 / 目录服务）、检查健康状态（杀毒状态、补丁等级），对照策略做出决策；
4. **PEP 执行**：PEP 按决策执行——放行（端口全开）、隔离（只进隔离网段）、拒绝（端口封锁）。

**重点：NAC 的每一步都发生在「接入」之前**。认证通过前，设备除了「申请接入」什么也做不了——这是它区别于防火墙的关键：防火墙管「进出边界」的流量，NAC 管「准入边界」的身份与健康。<span class="marginnote">「准入前管控」与「准入后管控」是 NAC 的两个时代：早期 NAC 只看「进门那一刻」，现代 NAC 强调持续评估——设备在网期间的合规状态也要持续监视，发现异常随时降权。安全从「一次检查」变成了「持续盯防」。</span>

NAC 面对的真实场景远不止「办公电脑进内网」——**访客与自带设备（BYOD）**是最典型的考验：访客的笔记本、员工的私人手机，身份未必可疑，健康状态却完全不可控。NAC 的标准解法是给它们划一条**访客 VLAN / 隔离网段**：能上网、能办公所需的最小服务，但进不了内网核心资源。信任程度分档、隔离可落地，正是 NAC 相对「一刀切」认证的价值所在。

**辨析｜易错点：** 常有人把 NAC 与 802.1X 划等号——不对。**802.1X 是 NAC 的一种实现载体**（企业 Wi-Fi 和有线端口的准入协议），NAC 是更宏观的框架：它还要做健康评估、访问策略、持续监视。802.1X 是 NAC 家族的成员，不是全部。

## 4 云安全：边界消失后的新威胁

当企业把网络搬到云端，「网络边界」这个安全前提发生了根本变化：

**传统边界：防火墙以内即内网**，物理隔离提供信任边界；
**云上环境：没有「内网」**，租户资源共享在云端基础设施上，边界退化成「虚拟网络 + 安全组」的配置项。

云安全的威胁也随之上了一个台阶。斯托林斯强调几个关键维度：

**多租户隔离**：多个客户共享同一套云基础设施，如何保证「你的虚拟机访问不到我的数据」——隔离失效是最严重的云事故；
**数据安全**：静态数据（存储）与动态数据（传输）的加密，密钥由谁托管；
**访问控制**：云账号的凭据管理、最小权限、防止密钥泄露；
**共享责任**：云厂商负责「云的安全」（物理设施、虚拟化、网络），客户负责「云中的安全」（应用、数据、账号、配置）——**责任边界不清，是云安全事故最常见的根因**。<span class="marginnote">「共享责任模型」是云安全的第一课：AWS、Azure 都明确画出「厂商负责到哪一层、客户负责到哪一层」。最常见的云事故——S3 存储桶权限配错导致数据公开——就是典型的「客户责任区内」的错误，不是云厂商的问题。</span>

**重点：云安全的本质，是把「边界防御」替换成「配置与身份治理」**。没有物理防火墙可依赖，安全完全取决于虚拟网络划分（VPC/安全组）、密钥管理、身份与访问管理（IAM）是否做对。**云上没有「买了就安全」的边界，只有「配置对才安全」的治理。**

## 5 核心对比表：传统边界 vs 云上安全

> 本篇为纯概念主题，按编辑章程以核心对比表替代公式解析。

两种环境的攻防差异，浓缩成一张表：

| 维度 | 传统网络（本地） | 云上环境 |
| --- | --- | --- |
| 边界 | 物理防火墙，内外分明 | 虚拟网络 + 安全组，边界是配置 |
| 信任模型 | 内网默认可信 | 零信任：任何访问都要验证 |
| 安全重心 | 边界防御设备 | 身份治理 + 密钥管理 + 配置 |
| 责任归属 | 企业自管全部 | 共享责任：厂商管「云」，客户管「云中」 |
| 审计日志 | 本地 SIEM | 云日志 + 云审计（如 AWS CloudTrail） |
| 威胁重点 | 边界突破 | 配置错误、凭据泄露、多租户隔离 |

**重点：云的兴起正在把安全范式从「边界防御」推向「零信任」**——不再相信「内网 = 安全」，而是对每一次访问、每一个请求都验证身份与授权。这与 NAC 的「先验证、再接入」是同一思想的彻底化：当边界无处不在，验证就必须无处不在。<span class="marginnote">「零信任」的三大原则——永不信任、持续验证、最小权限——正是 NAC 思想在云时代的极致展开。本专题从 802.1X 到 NAC 再到云安全，其实都在讲同一件事：把「信任」从「位置」里剥离出来，交还给「验证」。</span>

## 6 云上安全的工程抓手

云安全不是一句口号，它有五个落到实处的工程抓手，也是审计云环境的常见清单：

**身份与访问管理（IAM）**：一切访问先从身份说起——云账号、角色、服务身份的凭据管理，配合**最小权限**原则：只给「完成任务所需的最小权限」，宁可缺、不可滥。历史上大量云事故都源于「一个被过度授权的密钥」；
**密钥管理（KMS）**：静态数据加密的密钥统一由云厂商的密钥管理服务托管，支持自动轮换、定期更新——加密不难，**密钥的托管与轮换才是云加密的命门**；
**网络分段**：用虚拟网络（VPC）与安全组把不同信任等级的资源隔开，公网暴露面收敛到负载均衡一层——这是「DMZ 思想」在云上的重现；
**日志与监控**：开启云审计日志（如 AWS CloudTrail），任何管理操作都留下痕迹——**没有日志，云事故复盘无从谈起**；
**配置即代码**：用基础设施即代码（IaC）管理网络与安全配置，让「安全配置」可版本化、可审查、可回滚——手动在控制台点出来的安全组，往往就是事故源头。<span class="marginnote">云安全事故的最大单一根因是<strong>错误配置</strong>（公开的存储桶、敞开的端口、过宽的权限），而不是「云不安全」。这正是「共享责任」的残酷面：厂商保证「云本身安全」，可「你配置出来的那朵云」是否安全，完全取决于你。</span>

**重点：云安全的抓手可以浓缩成一句话——「配置对、权限小、密钥管好、日志全」**。它与传统边界防御的最大差别在于：传统安全靠「买设备」，云安全靠「管配置」。设备买错了会坏，配置配错了会漏——后者更隐蔽、更致命。

## 7 小结

- **NAC** 在设备接入前完成「身份认证 + 健康检查」，不合格者拒绝或隔离入网。
- 架构上 **PDP 决策、PEP 执行、AR 申请**三者分离——「决策与执行解耦」是反复出现的母题。
- 接入流程四步：**发起 → 转发 → 评估 → 执行**，全部发生在「接入之前」。
- 802.1X 是 NAC 的一种实现载体，不是 NAC 本身。
- **云安全**把「边界防御」换成「配置与身份治理」：多租户隔离、密钥管理、共享责任是三大命门。
- 云时代的安全范式正从「边界防御」走向**零信任**——信任交给验证，而非位置。
- 健康状态检查的合规基线 + **补救网段**闭环，让「不合格」设备修好再放行，而非一刀切拒绝。
- 共享责任模型下，**云事故的最大根因是错误配置**而非云厂商——配置对、权限小、密钥管好、日志全，是云安全的四条铁律。
- 从 802.1X 到 NAC 再到云安全，「**先验证、再接入**」「**决策与执行分离**」是贯穿始终的同一思想。
