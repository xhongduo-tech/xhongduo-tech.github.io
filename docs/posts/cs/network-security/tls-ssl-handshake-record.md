## 为什么从 TLS 开始

前面五篇把密码学零件攒齐了：对称加密、公钥、哈希、签名、证书、密钥分发。但零件堆在仓库里不叫产品——**TLS（传输层安全）就是把这些零件装配成互联网安全地基的那套总装线**。浏览器地址栏的小锁、HTTPS 的加密、几乎一切 API 调用的安全传输，背后都是 TLS。

TLS 前身是网景的 **SSL（Secure Sockets Layer）**。SSL 2.0 因安全缺陷迅速被 3.0 取代，随后由 IETF 标准化为 **TLS 1.0**（SSL 3.0 的直系后代），再到 TLS 1.2（2018 年前的主流）、TLS 1.3（2018 年，现行标准）。**术语上「SSL」已退役，但口语里「SSL 证书」「SSL 握手」仍在使用，指的就是 TLS。**

TLS 的名字点明了它的位置：**传输层安全**。它坐在 TCP 之上、应用之下，因此对上层应用几乎透明——HTTP、SMTP、FTP 都能不改变自身协议就套上一层 TLS（分别变成 HTTPS、SMTPS、FTPS）。这种「给应用免费加安全」的通用性，正是它成为互联网地基的原因。同时它也决定了保护边界：TLS 只管自己这条连接的数据，管不到路由、管不到源目 IP——那些要交给网络层的安全机制。<span class="marginnote">本专题第2、3、4篇建立的公钥、哈希、签名、PKI 概念，将在这篇全部登场；下一节《HTTPS 与 Web 传输安全》则是 TLS 在 Web 场景的应用延伸。</span>

## 1 两层架构：面向连接，层层封装

TLS 不是单个协议，而是一组协议的分层栈，位于传输层（TCP）之上、应用层之下：

**TLS 记录协议（Record Protocol）**：最底层，负责把上层数据切成块、压缩、加 MAC、加密、封装帧头——所有数据的「运输舱」；
**TLS 握手协议（Handshake Protocol）**：建立连接时协商算法与密钥；
**TLS 更改密码规格协议（Change Cipher Spec）**：通知对端「从现在起切换新密钥」；
**TLS 告警协议（Alert Protocol）**：报告错误与终止，告警分**致命（fatal）**与**警告（warning）**两级——致命告警立刻终止连接，例如证书无效、MAC 失败、握手超时等。

**重点：握手先谈，记录后运**。连接建立之初走握手协议，谈妥参数、生成密钥后，握手本身也通过记录协议封装传输；之后应用数据全部走记录协议。这种「先谈判、后运输」的分工，是整个 TLS 的心脏。

`ChangeCipherSpec` 则是一道精确的「开关」：在握手进行到密钥已派生完毕的那一刻，一方发出这条消息，通知对端**「从下一条记录起，改用新协商好的密钥」**。开关只允许打开一次、不能退回——这保证了双方在同一时刻切换，不会出现「我用了新密钥、你还拿旧密钥解」的错位。<span class="marginnote">理解分层的关键是「协议复用」：握手、告警、应用数据统统是记录协议的载荷，只是内容类型字段不同。抓包时看到 TLS 记录层里套着 Handshake/Application Data，就是这个设计。</span>

## 2 握手协议：四步谈出一把会话密钥

TLS 握手的任务，是在双方**零预先共享秘密**的情况下，协商出加密算法与共享密钥。TLS 1.2 的经典握手分四个阶段：

**第一阶段：Hello 互通**。客户端发 `ClientHello`（支持的协议版本、密码套件列表、客户端随机数 $r_C$）；服务器回 `ServerHello`（选定版本、密码套件、服务器随机数 $r_S$），并附带证书。

**第二阶段：服务器认证与密钥协商**。客户端验证服务器证书（PKI 那一套），随后双方通过**密钥交换**生成**预备主密钥（pre-master secret）**——经典做法是客户端用服务器公钥加密一个随机数发过去，现代做法是 ECDHE 双方各出一个临时公私钥，算出共享秘密。

**第三阶段：客户端认证（可选）**。一般只验证服务器；若需双向认证，客户端也出示自己的证书。

**第四阶段：收尾**。双方各自从预备主密钥派生出**主密钥（master secret）**与工作密钥，客户端发 `ChangeCipherSpec`，互发 `Finished` 消息确认握手完成。<span class="marginnote">`Finished` 是握手的安全闸门：它是对「到目前为止全部握手消息」的 MAC，任何一方若在中途被篡改或替换，`Finished` 校验必然失败——中间人在这里现出原形。</span>

握手的昂贵之处在于**每开一条 TCP 连接都要重走一遍**。为省去重复开销，TLS 引入了**会话（session）与连接（connection）的区分**：会话是双方共享的安全参数（主密钥等），连接是一次具体的数据传输。客户端可以把**会话 ID** 或会话票据缓存下来，下次建连时直接复用主密钥、跳过完整握手——这叫**会话恢复（session resumption）**。体验上就是刷新网页不再转圈，安全上则要求恢复的会话也必须重新协商随机数，避免长期复用同一密钥。

## 3 公式解析：PRF 与主密钥派生

握手谈出预备主密钥后，真正的会话密钥由**伪随机函数（PRF）** 派生。TLS 1.2 的 PRF 定义：

$$
P_{\text{hash}}(\text{secret}, \text{seed}) = \text{HMAC}_{\text{hash}}(\text{secret}, A(1) \| \text{seed}) \; \| \; \text{HMAC}_{\text{hash}}(\text{secret}, A(2) \| \text{seed}) \; \| \; \cdots
$$

其中 $A(0) = \text{seed}$，且 $A(i) = \text{HMAC}_{\text{hash}}(\text{secret}, A(i-1))$——一个自我迭代的 HMAC 链，输出不够长就继续拼下一块。主密钥由此导出：

$$
\text{master secret} = \text{PRF}(\text{pre-master}, \text{``master secret''}, r_C \| r_S)
$$

逐项拆解：

- **secret（种子链）**：预备主密钥，只有双方知道；$A(i)$ 迭代让输出成为不可预测的伪随机流。
- **label（标签）**：ASCII 字符串如 `"master secret"`，把「同一种子用于不同用途」的产物彼此隔开——这是**域分离（domain separation）**，防止跨用途复用。
- **$r_C \| r_S$（双方随机数）**：把两次握手的随机性都揉进去，保证**每次连接的密钥都不同**——即使同一会话重连，也得不到相同密钥。
- **最终工作密钥**：再由主密钥经同类 PRF 派生出一组「客户端写密钥、服务器写密钥、双方 MAC 密钥、IV」等，分别用于加密与认证。<span class="marginnote">「一次握手，一把密钥」就是<strong>前向保密</strong>的种子：即使日后长期私钥泄露，历史会话的密钥也已随握手的临时随机数作废。TLS 1.3 把前向保密设为强制，正是对这一原则的彻底贯彻。</span>

## 4 记录协议：加密、认证、防重放

谈妥之后，应用数据进入记录协议流水线，六步加工：

1. **分片**：把应用数据切成不超过 $2^{14} = 16384$ 字节的记录块；
2. **压缩（可选）**：对分片做无损压缩，减小传输量（现代版本几乎不使用，因有压缩侧信道攻击的风险）；
3. **加 MAC**：为分片计算完整性校验值并附加（TLS 1.3 起改为 AEAD 的认证标签）；
4. **加密**：用会话密钥对「分片 + MAC」整体加密；
5. **加记录头**：在密文前附上记录头（内容类型、版本、长度），组成一条完整记录；
6. **传输**：交给 TCP 发送。

**重点：记录协议每一步都环环相扣，最后变成一条「密文 + MAC + 头」的完整帧**。接收方反向处理：验头 → 解密 → 验 MAC → 解压 → 重组。MAC 失败立刻报致命告警并终止连接——**任何一帧被篡改都会被发现，这是 TLS 完整性的落地形态。**<span class="marginnote">记录头的「内容类型」字段决定了 TSL 的协议复用：握手、告警、应用数据都封装成同一种记录，只是类型不同——抓包时看到 TLS 记录层里套着 Handshake 或 Application Data，就是这个字段在起作用。</span>

记录协议还承担**防重放**：每条记录带单调递增的序号（隐式维护），序号重复即视为重放攻击、直接拒绝。再加上「每一帧都带 MAC」的认证，TLS 记录层一次提供了**机密性 + 完整性 + 防重放**三件套。

## 5 TLS 1.3：更少往返，更强安全

TLS 1.2 是 2018 年以前的主流，TLS 1.3（2018 年发布）则是一次结构性革新，关键变化有三：

**精简握手**：1.2 的经典握手需要**两次往返（2-RTT）**；1.3 把密钥协商与证书交换合并，通常**一次往返（1-RTT）**即可，会话恢复时甚至做到 **0-RTT**——网页加载因此明显变快；
**前向保密强制**：1.3 移除了不支持前向保密的密钥交换（如静态 RSA），默认只用 ECDHE——即使服务器长期私钥泄露，历史会话密钥也不受影响；
**砍掉旧算法**：1.3 删除 CBC、RC4、SHA-1 等老旧的加密与哈希组合，密码套件大幅精简，配置错误的空间随之缩小。<span class="marginnote">TLS 1.3 的设计哲学是「少即是安全」：可选项越少，可被配错的坑就越少。它的握手消息也是加密的——证书、参数不再明文暴露，抓包者只能看到一团密文。</span>

**辨析｜易错点：** 别把「TLS 1.3」与「HTTPS」画等号——HTTPS 是协议应用，TLS 是底层引擎；TLS 1.2 与 1.3 都是合法的 HTTPS 底层。浏览器显示「连接安全」不代表用的是 1.3，要看安全详情里的协议版本。**版本新旧影响安全强度，但「是不是 HTTPS」只取决于有没有 TLS。**

## 6 密码套件：TLS 的「算法契约」

TLS 的握手第一件事是**协商密码套件（cipher suite）**——它把 TLS 需要的一整套算法打包成一份「算法契约」。一个经典套件 `TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256` 拆开是四段：

| 字段 | 内容 | 作用 |
| --- | --- | --- |
| ECDHE | 椭圆曲线 DH 密钥交换 | 协商会话密钥（前向保密） |
| RSA | 证书签名算法 | 认证服务器身份 |
| AES_128_GCM | 对称加密 + AEAD | 加密数据并附带认证标签 |
| SHA256 | 哈希函数 | 作为 PRF 与 MAC 的基础 |

**重点：套件的一字之差，安全强度天壤之别**。`ECDHE` 提供了前向保密，而旧套件里的静态 RSA 密钥交换没有——私钥泄露历史会话全废；`GCM` 是 AEAD 模式，一次拿到加密 + 认证，而旧套件里「CBC 加密 + 单独 MAC」的组合曾爆发过多轮填充预言攻击。**看懂密码套件，是判断「这条 TLS 连接到底安不安全」的第一现场。**<span class="marginnote">协议协商永远遵循「就低原则」：如果客户端与服务器都支持强套件，但某一方配置里还留着弱套件，攻击者可能通过协议降级把连接逼到弱套件。现代最佳实践是「只配置强套件，一个弱项都不留」——这是 TLS 配置安全的第一条戒律。</span>

协商顺序也值得注意：客户端把自己的套件列表按偏好排序发给服务器，服务器从中选一个**它自己也支持**的——最终套件由服务器决定，但选择范围被客户端限定。任何一方都不能单方面定死算法，这是「协商」而非「指派」的意义。

## 7 小结

- **TLS 是分层协议栈**：握手协议「谈」参数与密钥，记录协议「运」加密数据，ChangeCipherSpec 与告警协议各司其职。
- 经典握手四阶段：**Hello 互通 → 密钥交换 → 认证 → 收尾**，谈出前向保密的会话密钥。
- 会话密钥由 **PRF** 从预备主密钥 + 双方随机数派生，随机数保证每次连接密钥不同。
- 记录协议六步流水线：**分片 → 压缩 → 加 MAC → 加密 → 加头 → 传输**，一帧被篡改即被发现。
- **会话恢复**复用主密钥、跳过完整握手，刷新页面不再转圈。
- **TLS 1.3** 把握手压到 1-RTT（复用 0-RTT），强制前向保密，砍掉老旧算法。

在下一节，我们将看到 TLS 在 Web 场景的应用延伸——浏览器地址栏的锁、证书链的验证、Cookie 的守卫，都将是**HTTPS 与 Web 传输安全**的主角。
