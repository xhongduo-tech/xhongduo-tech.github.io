## 为什么从「可靠性工程」开始

前面八篇把机柜的每一个子系统都立起来了，但一个残酷的事实是：**一个 120 kW、27 个托盘、几百颗器件的系统，任何一刻都有某个部件在「走向故障」**。风扇轴承在磨损、HBM 的比特在软错、连接器触点在氧化、冷却液在劣化——可靠性工程要回答的是：**在这些故障必然发生的前提下，怎么让系统「看起来一直没事」**。在从极限到大模型的主线上，这是「Scale-Up 的代价」最集中的一章：第 1 篇说过，72 块 GPU 共享一个训练作业，任何一块坏了都可能拖住全柜——**算力越集中，可靠性越不是可选项，而是与性能同等级的硬指标。**

先算一笔吓人的账：假设单颗 GPU 的年失效率是 1%（对 1,000 W 级芯片来说并不算保守），那么 72 颗 GPU 的机柜每年至少有一颗失效的概率约 $1 - 0.99^{72} \approx 51\%$——**也就是说，一台 NVL72 有超过一半的概率在一年内碰到 GPU 故障**。这不是「可能坏」，而是「必然坏」。可靠性工程的全部工作，就是让这个「必然坏」变得「无感」。

## 1 RAS：可靠性、可用性、可服务性

**核心概念：RAS**：Reliability（可靠性）——系统不出故障的概率；Availability（可用性）——系统「可用时间」占全部时间的比例；Serviceability（可服务性）——故障后多快能修好、多容易修。

三个词是三个不同的工程目标：**可靠性**靠设计（好材料、好电路、留裕量），**可用性**靠冗余与容错（坏一个不影响整体），**可服务性**靠结构（模块化、热插拔、好日志）。一个机柜可以「可靠性一般但可用性很高」——因为它用冗余把故障「掩盖」掉了；也可以「可靠性很高但可服务性差」——因为它从不坏，但一坏就要停机三天修。<span class="marginnote">业界有个金句：<strong>「可靠性是让故障不发生，可用性是让故障不重要。」</strong> 整柜工程的重点几乎都押在后者——因为前者（让故障不发生）在物理上做不到。</span>

**可靠性还有一个时间维度：浴盆曲线（bathtub curve）**。器件的失效率随时间呈「先高、中平、后高」：早期失效（出厂瑕疵）在前三个月集中爆发，随后进入漫长的平稳期，最后是磨损期（老化）。可靠性工程据此安排两件事：**出厂老化筛选**（burn-in，把早期失效提前在工厂里烧出来）和**预防性更换**（在磨损期到来前主动换件）——**「故障不是随机的」是可靠性工程的第一个信念，它让「防患于未然」成为可能。**

NVL72 的 RAS 设计贯穿整柜：电源 N+N 冗余、风扇与泵冗余、CDU N+1、NVLink 链路有备份路径、GPU 内存有 ECC 纠错——每一个「万一」都有人兜底。**整柜的 RAS 不是一项技术，而是一张「故障→对策」的完整表格。**

这张「故障→对策」表值得摊开看几行：**风扇失效** → 冗余风扇顶上 + 遥测告警；**电源抽屉失效** → N+N 另一侧兜住 + 告警；**冷却液泄漏** → 支路隔离 + 降载；**HBM 软错** → ECC 纠正 + 计数告警；**NVLink 断链** → 多路径重路由；**BMC 失联** → 双机接管。**每一个故障模式都有明确的「检测手段 + 应对动作 + 通知对象」**——可靠性工程成熟与否，就看成这表格有没有写满、有没有真的执行。

## 2 公式解析：可用性 = MTBF / (MTBF + MTTR)

可靠性的核心算术是**可用性公式**：

$$
A = \frac{\text{MTBF}}{\text{MTBF} + \text{MTTR}}
$$

拆开看：**MTBF（Mean Time Between Failures，平均故障间隔时间）**是系统「平均多久坏一次」，**MTTR（Mean Time To Repair，平均修复时间）**是「平均修一次多久」。$A$ 就是「可用时间占比」，习惯上写成几个 9：99.9%（三个 9）、99.99%（四个 9）。<span class="marginnote">一个九的差距是数量级的：99.9% 每年允许宕机 8.76 小时，99.99% 只有 52.6 分钟，99.999% 只剩 5.26 分钟。数据中心谈判「几个九」时，谈的就是每年能接受停机几分钟。</span>

这个公式给出两条提升可用性的路：**拉长 MTBF**（让系统更少坏）和 **缩短 MTTR**（让系统更快修好）。在 GPU 机柜场景里，MTBF 的增长靠 ECC、冗余、降额设计；而 MTTR 的缩短靠**热插拔**——坏一个托盘，几分钟换掉，不用停机。**对整柜来说，把 MTTR 从「小时」压到「分钟」，比把 MTBF 翻倍更快地提升可用性。**

公式还提示了一个系统级的陷阱：**对串联的子系统，总可用性是各子系统可用性相乘**。假设电源、冷却、互连、计算四块的可用性各为 99.99%，整柜可用性就是 $0.9999^4 \approx 99.96\%$——**每一块都「几乎完美」，合起来却掉了一个档位**。所以整柜的可用性设计必须是「四块一起抓」，任何一块拖后腿，整柜就跟着遭殃——这解释了为什么 NVL72 把冗余做进每一个子系统，而不是只盯着 GPU。

套一个数：假设某整柜 MTBF = 2,000 小时、MTTR = 6 小时，则可用性 $A = 2000/2006 \approx 99.7\%$——一年宕机约 26 小时，很难看。若靠热插拔把 MTTR 压到 0.1 小时（6 分钟），$A = 2000/2000.1 \approx 99.995\%$，一年只停 26 分钟——**同样的故障率，仅仅把「修得快」提升 60 倍，可用性就从三个九跳到四个九**。这组数字就是「热插拔值多少钱」的直接答案。

## 3 故障域隔离：把坏的影响圈起来

**核心概念：故障域（fault domain）**：一个故障发生时会波及的最大范围。设计的核心思想是**「让一次故障的影响面尽量小」**。

**可靠性设计有个标准流程叫 FMEA（Failure Mode and Effects Analysis，失效模式与影响分析）**：把系统的每个部件、每种可能的失效模式、失效后的影响逐条列出来，再针对「影响大 + 概率高」的模式加冗余与检测。NVL72 这种整柜系统的可靠性设计，本质上就是一张大 FMEA 表格的落地——先穷举「会怎么坏」，再回答「怎么办」。带着这个框架读下面的故障域分层，会格外清晰。

NVL72 的故障域按「资源」切成几层：

- **电源域**：电源抽屉 N+N，一个抽屉坏了，另一侧兜住，机柜不断电；托盘上的 e-fuse 让单个托盘短路不至于拖垮母排。
- **冷却域**：CDU N+1、液冷支路独立关断，一个支路漏液，只隔离那一路，其余托盘照常散热。
- **计算域**：单个 GPU 或托盘的故障，通过 NVLink 域内的重路由与调度，把负载挪到健康 GPU 上；NVLink 本身有多条路径，一条断了走另一条。<span class="marginnote">还记得第 2 篇说的「任何两 GPU 之间有 18 条路径」吗？那就是计算域隔离的物理基础：<strong>全互连拓扑天然是冗余的</strong>，一条链路挂了，数据绕另一条走，训练不停。</span>

故障域的大小还要「算得清楚」：一个域太大（比如整个机柜是一个域），一次故障影响面就大；域太小（每颗 GPU 一个域），冗余成本就高。**故障域的设计是「影响面」与「成本」的权衡**——NVL72 的粒度选择是「托盘」：托盘是热插拔的最小单元、有独立 e-fuse 与液冷支路，恰好是「影响可控、成本可接受」的甜点区。

**重点：故障域隔离的终极目标是「坏掉一个部件，作业不中断」。** 整柜设计从电源、冷却到互连，每一层的冗余都是为了让「故障」停留在「可以容忍」的层次——这就是 Barroso 在《The Datacenter as a Computer》里反复强调的：**数据中心用「冗余 + 容错」把不可靠的组件拼成可靠的系统。**

故障域还有一个关键前提：**故障必须能被「看见」**。一个坏了的 GPU 若不被及时发现，它会在域里拖慢所有与它通信的 GPU——「坏」的伤害远小于「坏而不自知」。所以故障域隔离的完整链条是「**检测 → 隔离 → 告警 → 修复**」四步，第 8 篇的遥测负责「检测」，本篇的隔离与热插拔负责「隔离与修复」。**没有遥测的冗余是「无效冗余」——冗余设备只有在故障被发现时才真正起作用。**

**GPU 的故障模式值得单独认识**：GPU 最常见的不是「整体坏掉」，而是「部分劣化」——HBM 出现可纠正的软错（靠 ECC 纠正，但错误计数在爬升）、某个 SM（流式多处理器）单元失效、NVLink 链路误码率升高。这些「亚健康」状态必须被第 8 篇的遥测持续监控，因为**「部分劣化」比「彻底坏掉」更危险——它不报错，却在悄悄拉低整柜性能**。ECC 的纠错能力、错误计数的阈值告警，就是拦截「悄悄劣化」的第一道网。

## 4 GPU 热插拔：换一块 GPU 不关机

**核心概念：热插拔（hot plug）**：在系统运行状态下带电更换部件，无需停机。

普通服务器热插拔硬盘早已司空见惯，但 **GPU 热插拔要难得多**：GPU 不仅带电，还在 NVLink 域里与 71 个邻居保持全速通信，还压着液冷冷板，还吃几百瓦的功率。要热拔一颗 GPU，必须同时做到：

- **软件解耦**：先把该 GPU 上的计算任务迁移或暂停，再让 NVLink 路由绕开它，然后才允许断电。
- **功率安全**：拔掉瞬间该托盘功耗骤降，母排与 PSU 要能承受这个瞬态，不能引起电压跳变波及邻居。
- **液冷解耦**：拔托盘要断开液冷接头且不漏液——这就是第 6 篇说的盲插快接的用武之地。<span class="marginnote">GPU 热插拔是「机械 + 电气 + 液冷 + 软件」四线协同的活：机械给精度、电气给隔离、液冷给安全、软件给编排。任何一线拉胯，热插拔就从「便利」变成「灾难」。</span>

还有一个常被低估的细节：**120 kW 机柜的热插拔要处理「功率突降的连锁反应」**。拔掉一个 5.4 kW 的托盘，母排电流瞬间掉一截；插回新托盘，电流又瞬间跳升——如果供电链路的瞬态响应不过关，电压波动会波及相邻托盘，甚至触发别的 GPU 误降频。所以热插拔的电气设计要**控制功率变化的斜率（slew rate）**，让「换托盘」像「轻轻加减油门」而不是「急刹车再急加速」。

热插拔不是「设计出来就算数」，它要在工厂和现场反复**验证**：拔插几千次测接头寿命、模拟拔到一半断电、测试新 GPU 入域后的 NVLink 训练稳定性。**可靠性工程里最贵的不是设计，是「证明它可靠」的测试成本**——整柜可靠性说到底是测出来的，不是算出来的。

一次标准的 GPU 热插拔流程是这样：调度器先把该托盘的任务迁走 → BMC 收到「允许下电」信号 → 逐级切断该托盘的供电（先核心后外围）→ 断开 NVLink 参与（域内路由重算）→ 液冷接头自动封液 → 运维拔出托盘、换上新的 → 反向流程逐级恢复 → 新 GPU 通过 NVLink 训练与健康检查后重新入域。**每一步都有「失败检查点」：任何一步没完成，流程就回滚，绝不硬拔。**

**辨析｜易错点：** 「热插拔」不等于「热拔插」——不是「想拔就拔、插上就用」。真正支撑热插拔的是一整套**权力交接协议**：软件先交权（停任务）、电源先断电（避免拉弧）、液冷先封液（避免喷水）、网络先退域（避免路由黑洞）。**热插拔是把「断电换件」这件事做得足够精细，让它看起来像「随手一拔」**——背后的复杂性恰恰是整柜工程最见功力之处。

## 5 降频降级：宁可慢，不能停

当故障无法避免、热插拔又来不及时，最后的防线是**降频降级（degradation）**。

**核心概念：降频降级**：在硬件异常（过热、供电不足、个别单元失效）时，系统主动降低运行强度继续工作，而不是直接崩溃。

NVL72 的降级是**分级**的：先是单颗 GPU 降频（比如从全速降到 80%），散热或供电仍不足，再降级到「用更少的显存、跑更小的 batch」；某个 GPU 彻底失效，域内把它的工作分摊给邻居，训练速度下降但**不中断**。<span class="marginnote">分级降级的哲学：<strong>永远保留「还能算」的最低状态</strong>。对训练集群来说，从 100% 降到 90% 是「慢一点」，从 90% 掉到 0 是「灾难」——降级要做的就是把后者变成前者。</span>

举个例子更直观：某次训练中，一颗 GPU 的 HBM 温度持续超标，BMC 先把它降频到 90%；温度仍降不下来，系统把它的数据并行分片调走 1/4，该 GPU 承担更少的工作；最后温度稳定在安全区，训练以 85% 的吞吐继续跑——**从头到尾，作业没停，只是慢了一点点**。这就是降频降级追求的「优雅降级」：宁可牺牲吞吐，绝不让「一卡故障」变成「全柜停摆」。

降级的判断依据全部来自第 8 篇的遥测：温度、功耗、错误计数。BMC 与调度器联动，把「这颗 GPU 要降级」提前告诉上层，让训练框架重新规划并行方案——**可靠性的最后一道防线，是「系统对自己状态的诚实汇报 + 上层的敏捷响应」。**

**降级还有一个兄弟概念：功率封顶（power capping）**。数据中心的电力供应是有限的，当整排机柜同时满负荷、总功率要超配电上限时，管理平台会给每个机柜设「功率上限」，机柜内部再按优先级分配——GPU 降频、托盘点亮顺序调整，把总功率压回预算内。**降频降级服务于「硬件保护」，功率封顶服务于「配电安全」，两者共享同一套执行机制（调频、调流），却由不同的触发器驱动。**

与降级配套的还有**数据保护**：训练中断时，最近的**检查点（checkpoint）**决定了要回滚多少工作。NVL72 的 Grace CPU 与 NVMe 缓存盘就是为「快速写检查点」而设的——故障时先把权重存到本地 NVMe，再慢慢同步到远端存储。**可靠性的最后一层不是「不坏」，而是「坏了之后，损失的工作量最少」**——检查点策略直接决定 MTTR 里「恢复」那一段的长短。

## 6 小结

- **RAS** 三要素分工明确：可靠性靠设计、可用性靠冗余、可服务性靠结构；**「可靠性让故障不发生，可用性让故障不重要」。**
- 可用性公式 $A = \text{MTBF}/(\text{MTBF}+\text{MTTR})$：提升可用性可以拉长 MTBF 或缩短 MTTR，**整柜把宝押在「热插拔把 MTTR 压到分钟级」**。
- 浴盆曲线说明**故障有规律**：出厂老化筛选（burn-in）消灭早期失效，预防性更换应对磨损期。
- **故障域隔离**按电源、冷却、计算三域各做冗余：e-fuse、CDU N+1、液冷支路关断、NVLink 多路径，目标都是「坏一个部件，作业不中断」；且「检测 → 隔离 → 告警 → 修复」四步缺一不可。
- **GPU 热插拔**是机械、电气、液冷、软件四线协同；盲插液冷接头与 NVLink 重路由是物理前提，功率突降的斜率要受控。
- GPU 故障多半是「部分劣化」而非「整体坏掉」：ECC 纠错 + 错误计数告警拦截「悄悄劣化」。
- **降频降级**分级进行：单 GPU 降频 → 缩规模 → 任务分摊，永远保留「还能算」的最低状态；检查点策略决定「坏了之后损失多少工作」。
- 降级（硬件保护）与功率封顶（配电安全）共享同一套调频调流机制，由不同触发器驱动。
- 串联系统的可用性是各子系统可用性相乘：**每一块都 99.99%，四块相乘就掉档**，冗余必须做进每个子系统。
- 可靠性设计流程是 **FMEA**：先穷举「会怎么坏」，再针对「影响大 + 概率高」的模式加冗余与检测；可靠性最终是测出来的，不是算出来的。
- 单颗 GPU 年失效率 1% 时，72 GPU 机柜一年内至少坏一颗的概率约 51%——**故障不是「可能」而是「必然」，可靠性的目标是让「必然坏」变得「无感」。**
- Barroso 的核心思想贯穿全篇：**用冗余与容错，把不可靠的组件拼成可靠的系统。**

在下一节，我们将把视角从「自家的机柜」抬到「整个行业」：为什么一台机柜的接口要公开给全行业、为什么开放标准能养活一整条供应链——**OCP 开放计算（ORV3/DC-MHS 规范、供应链开放生态）**。可靠性设计了一张「故障→对策」表，而开放生态要回答的问题是：这张表由谁来做、给谁用。
