## 为什么从存储系统开始

前面七篇从 GPU 一直讲到检查点，但检查点「写到哪里」还没回答——这就是**存储系统**。训练对存储的需求远比想象中重：每个 epoch 要读一遍训练数据，每 15 分钟要写一次检查点，还要存放模型产出、日志与调试数据。

**把存储放回层次图**：第一篇的「多园区」行提到数据副本，第七篇的「检查点」需要写盘——存储是这两者的物理底座。它在全专题里的角色是「既接计算又接持久化」：计算侧的带宽墙（检查点）与数据侧的吞吐（数据集加载）都压在存储上，所以存储架构的每一分优化，都直接变成训练的吞吐与稳定。<span class="marginnote">Barroso Ch.3.4 把存储分为非结构化（对象/文件）与结构化（数据库/表）两类，并指出数据中心存储要回答的核心问题不是「用什么介质」，而是「怎么在规模下提供一致的带宽」。GPU 集群把这个问题推到了极限：万卡同时写检查点的聚合带宽需求以 GB/s 计。</span>本篇讲清三件事：**检查点带宽墙**到底是什么墙、**并行文件系统（Lustre/GPFS）**怎么拆墙、以及训练数据（对象存储）与检查点（文件系统）为何必须分工。

## 1 检查点带宽墙：万卡同时写盘

上一篇算过：1750 亿参数模型 + Adam 状态 ≈ 1.4 TB，每 15 分钟全量检查点一次，需要持续约 1.5 GB/s 写带宽。但这不是全部——**所有 rank 是同时写盘的**。万卡集群里，2048 个 rank 各自写自己的分片，聚合写带宽需求是「单 rank 写速率 × rank 数」。<span class="marginnote">把数字放进去：2048 rank、每 rank 每 15 分钟写 0.7 GB，聚合写带宽 ≈ 2048×0.7 GB / 900 s ≈ 1.6 GB/s 只是「平均」；检查点瞬间是「突发」——15 分钟攒一次，一次要快速排空，实际需要的瞬时带宽可能是平均值的 10 倍以上。</span>

**「带宽墙」的准确含义**：不是「盘不够快」，而是「单块盘/单套阵列的带宽不够」。一块 NVMe SSD 顺序写约 3–7 GB/s，一套传统 NAS 阵列也就 10–20 GB/s，而万卡检查点的瞬时需求可能冲到 50+ GB/s——**必须把数据同时写到成百上千块盘上，才能攒出这个聚合带宽**。这就引出并行文件系统。

**为什么不用「多套独立盘」而要用「一套并行文件系统」**：如果每台训练节点只写自己的本地盘，那检查点就「锁死在节点上」——节点坏了，检查点跟着没了，容错篇的所有设计归零。**并行文件系统给的是「任何节点可访问的共享持久化」**，这才是容错的前提：检查点写在共享存储上，谁都能恢复。

**一个形象的类比**：检查点就像「全校学生同时冲进食堂打饭」。单个打饭窗口再快也扛不住 2000 人同时到，解决办法不是换一个更快的窗口，而是**开 200 个窗口并行打饭**——并行文件系统就是「开 200 个打饭窗口」的机制：条带化把一个大文件拆到 200 块盘，每块盘同时写自己的那一段，聚合起来就是 200 倍的带宽。

## 2 并行文件系统：把「一个文件」拆到「千块盘」

**并行文件系统（parallel file system）**的核心思想：一个逻辑文件不再放在一块盘上，而是**切成条带（stripe），同时分布到多个存储节点**。客户端并发读写时，各节点并行工作，聚合带宽 = 存储节点数 × 单节点带宽。这个「把一个大对象切碎并行处理」的思路，与第三级《操作系统》里的文件系统、以及《数据结构》里的分块/分片完全同构——**只是把「单机文件系统」的尺度放大到了「集群文件系统」**。<span class="marginnote">Lustre 是最主流的开源并行文件系统（超算 TOP500 份额过半），GPFS（现 IBM Spectrum Scale）是商业版代表作，另外还有 BeeGFS、CephFS、WEKA 等。它们的共同点都是「数据条带化 + 分布式元数据」。</span>

**以 Lustre 为例拆它的三件套**：

- **MGT/MDT（元数据目标）**：管「文件名 → 数据在哪」的映射，用高可用的小集群（如 MDT 成对冗余）。
- **OST（对象存储目标）**：真正存数据的节点，每个 OST 挂一批盘，文件被条带切分到多个 OST。
- **客户端（client）**：挂在训练节点上，让训练程序以普通文件路径访问这个「逻辑大磁盘」。

**关键数字**：条带宽度 $S$（文件被分到几个 OST）与 OST 数量 $N_\text{OST}$ 共同决定聚合带宽。文件条带越多、跨的 OST 越多，聚合带宽越高——但也越依赖所有 OST 同时在线，单 OST 故障会拖累整条带。

**条带化不是免费的**：文件被切成 1 MB–4 MB 的条带单元（stripe size）分布到各 OST，带来的代价是「元数据更复杂」与「小文件反而变慢」——小文件条带化后，每次读都要向多个 OST 发请求，延迟反而上升。所以 Lustre 实践中「大文件高条带、小文件单 OST」是铁律：**检查点这种大文件开足条带，日志这种小文件走默认单条带**。<span class="marginnote">Lustre 的 `lfs setstripe -c N` 命令就是干这个的：按文件类型设置条带宽度与条带大小。训练平台把检查点目录、数据集目录、日志目录分别设不同的条带策略，是存储优化的第一课。</span>

## 3 从块设备到文件：训练怎么用并行文件系统

训练场景把并行文件系统用在两条路径上：

- **检查点路径**：所有 rank 同时写自己的分片文件，Lustre 把写流量分摊到全部 OST 上，瞬时带宽可破 50 GB/s。
- **数据加载路径**：训练数据的「预读 + 混洗」也走文件系统，但通常先用 `tar` 打包 + 预热缓存，把随机读变成顺序读——因为并行文件系统的顺序读远快于随机读。

**检查点怎么「异步化」以绕过带宽墙**：生产级训练常用「异步检查点」——rank 把检查点数据先写到本地 NVMe（快），后台线程再异步刷到并行文件系统（慢但稳）。这样训练几乎不停顿，带宽墙被「本地缓冲 + 后台排空」化解。<span class="marginnote">异步检查点的风险点是「崩溃时本地 NVMe 上的未刷数据会丢」——所以它要配合「周期性强制刷盘」与容错篇的「双写」策略。把「快但易失」与「慢但持久」两层存储组合，是检查点架构的标准答案。</span>

**GPFS 与 Lustre 的定位差异**：Lustre 极致追求「聚合写带宽」，是超算/训练的事实标准；GPFS（Spectrum Scale）更强调「统一命名空间 + 企业级可靠性与配额」，适合「既跑训练又跑业务」的混合负载。

**实测经验谈**：Lustre 的经典「三高」是「高并发写、高带宽、低成本」，它的短板在小文件随机访问与元数据热点——文件太多太小时，MDT 会成为瓶颈。所以训练平台常做「分层」：热数据放 Lustre、冷数据归档到对象存储、小文件合并成 `tar` 包再放 Lustre。<span class="marginnote">这也回应了 Barroso Ch.3.4 的「系统平衡」思想：存储层次的选择本质是「延迟、带宽、容量」三者之间的平衡。训练数据几百 TB 放 Lustre 太贵，放对象存储读不快，于是「分层 + 缓存」成为标准答案。</span><span class="marginnote">GPFS 的看家本领是共享磁盘集群架构：多个节点同时读写同一套底层块设备，配合原子写与分布式锁保证一致性。它在「元数据性能」与「小文件场景」上比 Lustre 稳健，代价是配置复杂度高。</span>

## 4 训练数据：对象存储与数据集流水线

检查点需要「块级大带宽」，训练数据则适合**对象存储（object storage）**——把数据当「键值对象」而不是「目录树文件」管理，天然水平扩展、成本低。主流做法是对象存储（S3/Ceph）存原始数据，训练前用数据加载库（如 NVIDIA DALI、WebDataset）流式拉取。

**数据集预热具体怎么做**：训练开始前，把「对象存储 → 本地/共享缓存」的路径先跑一遍，让热数据进入 SSD 或内存缓存；训练中数据加载只打缓存、不打对象存储。<span class="marginnote">DALI 与 WebDataset 的「流式读取」是这套思路的软件化：把数据打包成顺序可读的 `tar`/`shard` 文件，边读边解码边喂 GPU，全程不把整个数据集载入内存。流式读取把「数据加载」从「等磁盘」变成「流水线」，是万卡训练数据侧的标准解法。</span>预热的时间成本通常一次付清，换取整个训练期的数据加载稳定。<span class="marginnote">对象存储与文件系统的分工：对象存储 = 海量数据集（写入一次、反复读），文件系统 = 高频读写（检查点、中间产物）。两者在训练平台里通常并存，中间用「预取/缓存层」衔接——这也是为什么训练框架都有「数据集预热」这一步。</span>

**训练数据与检查点在存储上的「冷热」分工**：数据集是「温」的（写好之后反复读）、检查点是「热」的（15 分钟一写）、日志是「冷」的（偶尔查）。把存储按温度分层——热放 NVMe/内存缓存、温放并行文件系统、冷归档对象存储——是成本与性能的最佳平衡。

**数据加载的优化套路**：

- **预取（prefetch）**：下一批数据在本批训练时就提前载入显存，隐藏 I/O 延迟。
- **打乱（shuffle）**：跨节点随机采样，用分片索引避免「每个 epoch 重复同一个随机序列」。
- **压缩/解码卸载**：让 GPU 或专用卡做 JPEG/`tar` 解码，避免 CPU 成为数据管线瓶颈。

**「读得快」和「写得快」是两种工程**：读路径优化追求「流水线」——预取、缓存、解码并行，让 GPU 永远有数据可算；写路径优化追求「排空」——检查点要尽快把缓冲区写走，别让训练停顿。**读是隐藏延迟，写是消灭突发**，两者的存储配置策略也因此不同（读吃缓存/条带，写吃聚合带宽/快速排空）。

## 5 公式解析：检查点需要多少聚合带宽

把「检查点带宽墙」用公式写清楚，它是存储架构的第一算术：

$$
B_\text{ckpt} = \frac{M_\text{total}}{T_\text{间隔}}
$$

其中 $M_\text{total}$ 是「模型 + 优化器状态」总字节数，$T_\text{间隔}$ 是检查点间隔。分三步拆解：

- **第一步**：$M_\text{total}$ 不只算权重——Adam 的动量与方差通常再占两份权重大小，1750 亿参数 fp16 权重 350 GB，加优化器约 1.4 TB。
- **第二步**：$T_\text{间隔}$ 是容错篇定的频率，通常 5–15 分钟。取 15 分钟（900 s）：$B_\text{ckpt} = 1.4\,\text{TB}/900\,\text{s} \approx 1.6$ GB/s（平均）。
- **第三步**：再考虑「突发」——检查点是周期性的，瞬时排空需要 $B_\text{瞬时} \approx B_\text{ckpt} \times (\text{检查点持续时间的倒数占比})$。**设计存储时按「瞬时峰值」而非「平均」定规格**，否则检查点期间训练会停顿。

**对比单盘**：一块 NVMe 3–7 GB/s 看似够平均需求，但扛不住瞬时峰值与「万卡同时」的并发——所以需要 $N_\text{OST} = B_\text{瞬时}/B_\text{单OST}$ 个存储节点并行。这就是并行文件系统存在的全部理由。

**再算一版万卡实例**：假设检查点瞬时要 50 GB/s，单 OST（一台双路 CPU + 12 块 NVMe）能供 5 GB/s，则需要 $N_\text{OST}=10$ 个存储节点。再把 RAID 与冗余算进去（每个 OST 用 RAID-10，效率约 50%），实际要 20 个节点。<span class="marginnote">RAID-10 是并行文件系统的标配：条带 + 镜像，既保带宽又保单盘故障不丢数据。它在「写放大」上的代价（镜像双写）正是「冗余 × 带宽」这对永恒的工程权衡在存储层的体现——与本专题第十一篇的 2N 冗余思想同源。</span>

## 7 小结

**读表时的心法**：不要纠结「该用哪个系统」，而要问「这个数据生命周期是写一次读一次（对象存储），还是高频读写（文件系统）」——**数据访问模式决定存储选型**，而不是品牌偏好。训练平台里两者共存、由缓存层衔接，是唯一的正确答案。

- **检查点带宽墙**：万卡同时写盘的聚合带宽需求（瞬时可达 50+ GB/s）远超单盘/单阵列，逼出并行文件系统。
- **并行文件系统**把文件条带化到多个存储节点（Lustre 的 OST/MDT/Client 三件套），聚合带宽随节点线性扩展。
- **Lustre** 极致追求写带宽，是超算/训练事实标准；**GPFS** 重企业级可靠性与统一命名空间。
- **对象存储**管训练数据集（写入一次、反复读），与文件系统分工，靠预取/缓存层衔接。
- 核心公式 $B_\text{ckpt} = M_\text{total}/T_\text{间隔}$：按「瞬时峰值」而非「平均」定存储规格。
- 存储是「容错篇的兑现」：检查点方案再好，写不进去就等于没有。
- **异步检查点**（本地 NVMe 快写 + 后台刷并行文件系统）是绕过带宽墙的实战答案。

**存储篇与全专题的接口**：带宽墙来自容错篇的检查点，条带思想与拓扑篇的「并行」同源，分层缓存又与数据并行「分片」互为表里。**存储不是独立模块，它是「带宽」这一主题在持久化侧的延伸**。
