## 为什么从制冷基础设施开始

上一篇算过：配电链损耗的 12.5% 变成热，而服务器本身的电几乎全部变成热——一个 40 kW 机柜就是一台「40 kW 电暖气」。**制冷的任务**：把这台「电暖气」的热量排到室外，同时保证 GPU 温度在安全区间（通常核心 <85°C，HBM <95°C）。

**能量守恒是制冷的第一定律**：服务器消耗多少电，就必须排走多少热——电力全部变成热量（含配电损耗）。所以「制冷的规模」直接等于「计算的规模」：12 MW 的算力集群，就是一台 12 MW 的电暖气。这个「能量既不会凭空产生也不会凭空消失」的前提，是第二级《物理学》热学章已经建立的第一原理，制冷工程只是它的工程化应用。<span class="marginnote">这条守恒律把前一篇与这一篇焊在一起：供电篇算「多少电进来」，制冷篇算「多少热出去」，中间隔着 IT 设备的转换效率。对 GPU 集群，这个「电→热」的账本几乎就是 1:1——这也是为什么制冷在 PUE 里占比那么重。</span><span class="marginnote">Barroso Ch.4.5 详细分析了数据中心制冷系统：CRAC（机房空调）、冷水机组（chiller）、冷却塔（cooling tower）、自然冷却（free cooling），以及风冷/液冷的分层演进。Ch.5.1 则定义了 PUE 指标——制冷是 PUE 里最大的「非 IT 消耗」部分，通常占非 IT 能耗的 30%–50%。</span>本篇回答三件事：为什么 GPU 时代必须上液冷、制冷系统怎么工作、以及 PUE/WUE 这两个指标到底在衡量什么。

## 1 热从哪来：功率密度是制冷的判据

制冷的难度不取决于「总热量」，而取决于「热量密度」——同样 1 MW 的热，摊在 500 平方米里好办，挤在 20 个机柜里就难办。**功率密度的单位是 kW/柜，GPU 集群把它推到了风冷的极限**。<span class="marginnote">风冷的工程极限：传统风冷机柜上限约 10–15 kW/柜；高密度风冷（冷热通道封闭 + 机房级空调强化）可到 20–30 kW/柜；而 DGX H100 机柜要 40–120 kW/柜——这是风冷物理上做不到的，必须液冷。</span>

**几组密度数字**帮我们建立尺度感：

- 传统 CPU 机柜：5–10 kW/柜。
- 高密度风冷机柜：15–30 kW/柜。
- DGX H100 机柜（风冷勉强可）：40 kW/柜。
- 液冷机柜：60–120 kW/柜。

**从功耗算密度**：一台 DGX H100（10.2 kW）在 42U 机柜里放 3 台（3×10.2 ≈ 31 kW），再算上 ToR 交换机的 2–3 kW，一个「GPU 机柜」的实际密度约 34–40 kW/柜。<span class="marginnote">这个数字正好落在风冷极限附近：用强风冷勉强能做，但「勉强」意味着机柜排风温度高、机房热点多、且散热效率差。NVIDIA 官方的 DGX H100 集群更推荐液冷机柜方案，把密度推到 80–120 kW/柜，一个机柜装 4 台甚至更多。</span>「密度决定制冷」的判据就落在这里：能不能风冷，先看柜密度过不过 30–40 kW。

**核心判断**：当功率密度超过约 30–40 kW/柜时，风冷「空气带不走那么多热」，液冷是唯一解。这就是「GPU 集群必然液冷」的物理原因——不是潮流，是热力学。

**GPU 温度阈值背后的可靠性逻辑**：高温不只是「性能降频」的问题——长期高温会加速 HBM 焊点老化与晶体管漏电，把第七篇讲的「故障预测」里的 ECC 错误率推高。<span class="marginnote">运营经验：GPU 核心温度每升高约 10°C，电子元器件失效率约翻倍（阿伦尼乌斯方程的经验近似）。所以「把温度压住」不只是性能优化，更是可靠性投资——这与第七篇「容忍故障」形成闭环：宁可多花制冷钱，也别让温度推高故障率。</span>制冷的终极理由，是「让 GPU 活着且稳定」。

## 2 风冷与液冷：两条排热路径

**风冷（air cooling）**：机房空调吹冷风，经过机柜热通道排出。它的排热路径是「GPU → 散热鳍片 → 机柜气流 → 机房空调 → 冷水机组/冷却塔 → 室外」。<span class="marginnote">风冷的看家本领是「便宜 + 通用」：所有 x86 服务器、网卡、交换机都能直接放进风冷机房。风冷的极限是「空气的比热太低」——1 立方米空气升温 1°C 只能带走约 1.2 kJ，而 1 升水升温 1°C 带走约 4.2 kJ，<strong>水的比热是空气的约 3500 倍</strong>（按体积）。</span>

**液冷（liquid cooling）**：用冷却液（去离子水或介电液）直接贴近发热源。主流形态：

- **冷板式（cold plate）**：GPU 上方贴冷板，冷却液流经带走热量，服务器其余部件仍风冷——最成熟、主流。
- **浸没式（immersion）**：整台服务器泡进介电液里，换热最彻底，但维护与成本高。
- **后门热交换（rear-door）**：机柜后门换热器把排风热量交给水，折中方案。

**液冷的两大收益**：功率密度上限从 30 kW/柜跳到 100+ kW/柜；PUE 更低（液冷省掉大量空调风机能耗）。**液冷的两大代价**：漏水风险（一次泄漏毁一柜服务器）与维护复杂度（液体管路、防漏设计、冗余泵）。

**液冷回路的工程细节**：冷板液冷通常用「二次侧回路」——一次侧是机房冷源（冷却塔/冷水机组），二次侧是去离子水回路，两侧经板式换热器换热。这样的好处是「GPU 侧的水」与「室外侧的水」隔离，机房内用去离子水避免腐蚀，泵与换热器都做冗余。<span class="marginnote">液冷的「漏水防护」是整套设计的一部分：快速接头（dripless coupling）、机柜级漏水检测带、以及「先断电再处理」的应急流程。NVIDIA 官方推荐液冷机柜的冷却液温度高达 35–40°C（温水液冷），因为这能大幅延长自然冷却时长——液冷与自然冷却的协同，是把 PUE 打到 1.1 以下的关键。</span>

## 3 制冷系统链路：热量最终去哪

无论风冷液冷，数据中心最终都要把热量排到室外。制冷系统有三级能量转移：<span class="marginnote">制冷系统的能量链：IT 设备 → 冷媒/水 → 冷水机组（chiller）或冷却塔 → 室外大气。冷水机组用压缩机做功「把热量从冷侧搬到热侧」（类似家用空调），冷却塔利用水的蒸发散热（把水喷到塔里蒸发带走热量），自然冷却（free cooling）则直接在室外温度低时跳过冷水机组、直接用室外冷空气/冷水。</span>

- **冷水机组（chiller）**：压缩机把 7–12°C 的冷冻水送到机房，吸热后回到机组被冷却。功耗大但能适应任何室外温度。
- **冷却塔**：把机组的热量通过水蒸发散到大气。水蒸发带走热量是「免费的物理」，成本只有水泵与风机。
- **自然冷却（free cooling）**：室外温度低于阈值（如 <15°C）时，直接用室外冷空气或冷却塔冷水给机房降温，关闭冷水机组——这是 PUE 能到 1.1 以下的利器。

**自然冷却的量化收益**：冷水机组的 COP（能效比）约 3–5（每 1 单位电搬走 3–5 单位热），而冷却塔蒸发散热的「电费」只有水泵+风机，约是冷水机组的 1/3–1/5。<span class="marginnote">COP 的概念：制冷机组消耗 1 kW 电，能搬走几 kW 热。COP=4 的机组，制冷 100 kW 只需 25 kW 电。自然冷却相当于「COP 趋近无穷」——因为它根本不用压缩机做功，直接用室外冷源。所以「自然冷却时长」直接决定了机房的全年平均 PUE。</span>一个城市的全年自然冷却小时数，是选址与 PUE 预估的第一输入。

**自然冷却的地区差异**：纬度越高、气候越冷，自然冷却时长越长。北欧数据中心 PUE 常年 1.1 上下，热带地区靠液冷 + 高 COP 机组补偿。**制冷的本质是把「电→热」的热量送回自然界**，选在哪排、怎么排，就是制冷架构的全部内容。

**冷热通道（hot/cold aisle）是机房级的排热纪律**：机柜面对面排（冷通道面对冷风），背对背排（热通道排热），配合封闭冷/热通道，避免冷热空气混合。<span class="marginnote">封闭冷通道 + 精确送风可以把风冷机房的密度再推高一截，但它的边际收益随密度上升而递减——40 kW 以上，再密闭也救不了「空气带不走」的物理瓶颈。这也是为什么「机房级优化」到顶后必须转「设备级液冷」。</span>它告诉我们：制冷的工程优化是分层的——先机房（气流），再机柜（通道），最后设备（液冷）。

## 4 PUE 与 WUE：两个度量衡

**PUE（Power Usage Effectiveness，电能使用效率）**是最重要的数据中心能效指标：

$$
\text{PUE} = \frac{\text{总进线功率}}{\text{IT 设备功率}}
$$

分三步拆解：

- **第一步**：分子是「整座数据中心从电网拉的电」，含 IT + 制冷 + 配电损耗 + 照明等一切。
- **第二步**：分母是「真正用于计算的电」（服务器、GPU、存储、网络设备）。
- **第三步**：理想 PUE = 1.0（所有电都用于计算）。普通风冷机房 1.3–1.5，液冷 + 自然冷却可到 1.1 以下。<span class="marginnote">Barroso Ch.5.1 对 PUE 有一个重要的批评：PUE 衡量的是「设施效率」而非「计算效率」——一个用旧 GPU 跑同样任务的机房，PUE 再低也在浪费电。所以 PUE 要与「每瓦算力」配合看，这也是第十二篇《绿色算力》的核心视角。</span>

**WUE（Water Usage Effectiveness，水利用效率）**是配套指标：$\text{WUE} = \text{总用水量}/\text{IT 设备能耗}$（单位 L/kWh）。冷却塔蒸发大量耗水，缺水地区 WUE 与 PUE 一样重要——**PUE 管电、WUE 管水**，两个指标合起来才是完整的资源效率。

**一组 WUE 参考值**：传统冷却塔机房 WUE 约 1.5–3 L/kWh（一座 1.65 MW 集群一年耗水可达数万吨）；液冷（温水回路 + 干冷器）可把 WUE 降到 0.5 以下，甚至「零水（dry）方案」用风冷换热器完全不用蒸发水。**「省电」与「省水」在制冷里经常是同一个选择**——这直接联系到第十二篇绿色算力的水碳视角。

**PUE 的数值例子**：一座机房 IT 负载 1.65 MW，制冷 0.3 MW，配电损耗 0.2 MW，照明等 0.05 MW——总进线 2.2 MW，PUE = 2.2/1.65 ≈ 1.33。<span class="marginnote">这个例子揭示了 PUE 的构成：1.33 里，制冷贡献了 0.18（0.3/1.65），配电贡献了 0.12。<strong>看 PUE 要看结构</strong>——PUE 高，先分清楚是制冷耗电多还是配电耗电多，优化方向完全不同（前者上液冷/自然冷却，后者提高配电效率）。</span>

**辨析｜易错点：** PUE 是「比值」不是「功率」——它无单位，1.3 表示「每 1 kW 计算电要 1.3 kW 总电」。把 PUE 当成「机房的用电量」是常见误读。它回答「效率」，不回答「多少电」。

**PUE 的行业演进**值得看一组历史数字：2007 年美国数据中心平均 PUE 约 1.9，2020 年大型云厂商普遍降到 1.1–1.2，头部新机房做到 1.05–1.1。<span class="marginnote">这个「从 1.9 到 1.1」的进步，一半来自制冷技术（自然冷却、液冷、气流优化），一半来自测量与运维（PUE 变成可追踪的实时指标）。Barroso 在 Ch.5.1 提醒：PUE 公布值往往只算「最佳负载时」，真实年度平均要看全年——「报表 PUE」与「实际 PUE」之间的落差，是行业普遍存在的真实情况。</span>读任何 PUE 数字，先问它是「峰值」「平均」还是「年度累计」。

## 6 小结

**读表时的心法**：风冷与液冷不是「二选一」，而是「同一排热任务在不同密度下的不同解法」。现实机房大量采用**混合方案**——CPU 部分风冷、GPU 部分液冷；冷板液冷机柜与风冷机柜共存于同一机房。**先算每排机柜的密度，再决定这一排用风还是用水**。

- 制冷难度由**功率密度**决定：GPU 集群 40–120 kW/柜，超过风冷物理极限，必须液冷。
- **液冷三形态**：冷板（主流）、浸没（彻底）、后门热交换（折中）；收益是密度 + 低 PUE，代价是漏水风险。
- 温水液冷（35–40°C）延长自然冷却时长，是 PUE<1.1 的关键协同。
- 制冷链路：**IT → 冷水机组/冷却塔 → 室外**，自然冷却是 PUE<1.1 的利器。
- **PUE = 总进线 / IT 功率**：管电；**WUE = 总用水 / IT 能耗**：管水；两者合起来才是资源效率。
- 核心判断：PUE 是比值不是功率，要配合「每瓦算力」一起读。
- 液冷不是潮流而是热力学结论：GPU 时代的排热只能靠水。

**制冷的冗余**也要提一句：泵、冷水机组、冷却塔都做 N+1，避免「制冷故障等于停机」——但制冷冗余比供电冗余便宜得多（停一会儿不会烧设备，只会热停）。**制冷与供电的容错哲学不同**：供电要「不中断」，制冷要「不超温」，这决定了它们各自的冗余设计。<span class="marginnote">这也是为什么第十一篇的 Tier 分级里，制冷的冗余要求（N+1 足够）总是低于供电（常需 2N）——制冷可以「短时降级」，供电不能。这个「不同系统不同容错标准」的思想贯穿整个机房设计。</span>

**制冷与全专题的接口**：第一篇的机柜功耗密度决定制冷方案，第九篇的配电损耗决定制冷负荷，第十二篇的绿色算力则把 PUE 与碳足迹挂钩。**制冷是「能量」这条主线在机房里的大头**——讲清它，才讲得清整座机房为什么是这个样子。

在下一节，我们把「怎么设计」上升到「怎么承诺」——**数据中心等级与可靠性**：Tier 分级、2N 冗余与可用性数学。
