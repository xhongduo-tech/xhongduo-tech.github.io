## 为什么从作业调度开始

前五篇把「单任务怎么跑得快」讲完了：网络、拓扑、集合通信。但一座万卡集群不是只跑一个任务——它要同时服务十几个团队、几十个模型、数百个并行度各不相同的作业。**作业调度**负责回答三个问题：哪个作业先跑、占用哪些节点、按什么顺序排队。看似平凡的「安排座次」，在 GPU 集群里因为两个特性而变得艰难：**作业是「成组」的（一个训练作业要同时占几百个节点，缺一个就跑不动），节点是「异构分层的」（NVLink 域、机柜、轨，放错位置性能暴跌）**。

**调度是「从极限到大模型」主线里第一次把「人的管理问题」引入工程**：前几篇优化的是「硬件与算法」，这一篇优化的是「资源的经济学」——集群一年几千万元的电费与折旧，调度得不好就浪费一半。Barroso 在 Ch.1 就点明：规模带来的第一大挑战不是造出来，而是**用起来**。调度器就是「用起来」这层软件的核心。<span class="marginnote">Barroso Ch.2.3 把调度器归为集群级基础设施软件（cluster-level infrastructure software），与资源管理、集群监控并列——它是「把硬件变成服务」的那一层。GPU 时代它的地位进一步提升，因为拓扑感知直接决定训练性能。</span>

## 1 调度问题的本质：资源碎片化

先把调度抽象成最简单的形式：集群有 $N$ 个节点，每个作业申请 $k$ 个节点。**关键约束**是作业必须整组获得资源才能启动（Gang），因此一次最多并行 $N/k$ 个作业，剩余 $N \bmod k$ 个节点闲置。

**Gang 约束为什么存在**：以 1024 卡数据并行作业为例，它需要 128 个节点同时就位。若调度器只给 100 个节点，作业启动后 NCCL 初始化就失败——**缺一张卡，整个作业白启动**。所以「要么全给、要么不给」不是设计偏好，而是分布式训练协议的硬约束。<span class="marginnote">这也是为什么「GPU 利用率」不能只看「节点满了没」：128 个节点里 127 个满、1 个空，对一个 128 节点作业来说仍然是 0% 可用。Gang 约束让「碎片」这个本来只影响效率的问题，变成影响「可用性」的问题。</span><span class="marginnote">Gang Scheduling（成组调度）来自 IBM LoadLeveler 时代：一组进程必须同时全部启动，否则先启动的进程空等——分布式训练尤其如此，因为 NCCL 需要全体 rank 在线才能做 AllReduce。Kubernetes 里的 Coscheduling、Volcano 插件都是 Gang 思想的现代实现。</span>

**资源碎片化（fragmentation）**是调度的头号敌人：作业按不同的 $k$ 申请，节点被「切剩」的零头越积越多。公式上，利用率是 $\lfloor N/k\rfloor \cdot k / N$，碎片让利用率永远低于 100%。**调度器的一切优化，本质上都在跟这个碎片做斗争**。

**碎片有两种形态**，值得分开对待：**时间碎片**是「某个时刻有空节点但不够组一个作业」，靠回填（让短作业插空）解决；**空间碎片**是「节点分散在不同机柜/不同轨，凑不齐拓扑正确的整块」，靠拓扑感知打分解决。**先分清是哪种碎片，再谈优化手段**——这是调度排障的第一原则。

## 2 拓扑感知调度：放对位置比放满更重要

普通调度只关心「有没有空节点」，GPU 集群调度还必须关心「空节点在不在正确的位置」。**拓扑感知调度（topology-aware scheduling）**把第一篇到第四篇的层次知识变成调度约束：<span class="marginnote">调度器的拓扑信息来自资源报告：每个节点的 NVLink 域归属、机柜位置、轨编号。调度时把这些当成「软约束」打分，而不是硬性拒绝——在资源紧张时允许降级放置，但要记录性能损失。</span>

- **同域优先**：TP 并行要求 8 卡同机，调度器把 TP 组锁定在同一节点的 NVLink 域内。
- **同柜优先**：数据并行要求通信越短越好，调度器尽量把 DP 组放在同一机柜、同一条轨内。
- **避免碎片**：宁愿把一个大作业放到一整片连续节点上，也不把它拆散塞进不同机柜。

**辨析｜易错点：**「拓扑感知」不是「强制拓扑」。它是软约束打分制——当集群满负荷时，调度器可以退而求其次（例如把 TP 拆到两台机器），但会记录性能损失并优先调度「位置正确」的作业。**把拓扑感知当成硬性要求，会让集群在资源紧张时严重利用率不足**；当成纯建议，又会让性能随机波动。权衡的火候就是调度器调参的核心。

**调度策略的两种极端**也有必要分清：**最优适配（best-fit）**把作业塞进「刚好够大的碎片」里，最大化利用率但加剧拓扑分裂；**最大适配（worst-fit）**把作业放在「最大的连续整块」里，保住拓扑但浪费碎片。**GPU 集群调度器的艺术，就是在「利用率」与「拓扑完整性」之间滑动**——这也是为什么大厂调度器都提供可配置的评分函数。

## 3 Slurm：HPC 世界的调度正统

**Slurm（Simple Linux Utility for Resource Management）**是超算与 GPU 集群最主流的调度器，从上世纪 90 年代的 LoadLeveler 体系一路演化而来，托管全球大半 Top500 超算。<span class="marginnote">Slurm 的三段式：`scontrol` 管理配置、`sbatch` 提交作业、`squeue` 查看队列；资源由 `slurmctld` 守护进程统一仲裁。它把「分区（partition）」当作调度的最小资源池，分区可按机柜/轨/机型划分。</span>Slurm 的关键能力：

- **成组资源申请**：`#SBATCH --nodes=128 --gres=gpu:8` 一次性占满 128 个节点、每节点 8 卡。
- **拓扑感知插件**：`--contiguous`、`--distribution=block` 等约束让节点连续放置。
- **回填（backfill）**：让「小作业插进大作业的空档」，是抗碎片的第一利器。
- **抢占与优先级**：`Priority`/`Preempt` 机制允许高优作业挤掉低优作业，配合检查点（下一篇）实现「让位不丢进度」。

**Slurm 的架构值得记一句话**：它是「中央裁决 + 节点代理」模式——`slurmctld` 在管理节点裁决队列，`slurmd` 在每个计算节点执行启动/回收。这种集中式模型在万卡规模下成为瓶颈（队列裁决延迟），所以超算界出现了 Slurm-ng 等分布式调度研究——**调度器本身也要面对规模难题**。

**Slurm 的一次完整作业生命周期**：`sbatch` 把脚本交给 `slurmctld` → 进入队列等待资源 → 资源就绪后 `slurmd` 在各节点拉起 `srun` 任务 → 完成后回收资源并记录计费。这个流程里的每一步都有对应的 `sacct`/`sstat` 可查——**学会看作业账本（accounting），是排障的第一步**。

**给 GPU 作业的一条常用模板**：`srun --nodes=128 --ntasks-per-node=8 --gpus-per-node=8 python train.py`——`--nodes` 定并行度、`--ntasks-per-node` 定每节点 rank 数、`--gpus-per-node` 定卡数。三者对齐是训练作业正确提交的前提，错一个数字，NCCL 的 rank 映射就会错位、性能随机劣化。

**Slurm 的局限**是「单集群、命令式」——它把一个集群当作一台大机器，作业通过脚本提交，不擅长容器化与微服务化的多云编排。

## 4 Kubernetes：云原生的调度哲学

**Kubernetes（K8s）**把调度从「HPC 命令」变成「声明式 API」：用户提交一个 `Pod`（请求 GPU 的容器），调度器（kube-scheduler）把它放到合适的节点上，失败自动重启、漂移自动迁移。<span class="marginnote">K8s 在 GPU 集群的演化路线：原生只认 `nvidia.com/gpu` 这种「整数个 GPU」资源；要调度「成组 + 拓扑」需要扩展——Volcano、Kueue、NVIDIA K8s Device Plugin 都是为此而生。K8s 的生态优势是容器化、弹性、可观测性一体化。</span>

- **设备插件（Device Plugin）**：把 GPU 注册为可调度资源，`nvidia.com/gpu`。
- **Gang 调度扩展**：Volcano / Kueue 实现「全部 Pod 就绪才启动」的成组语义。
- **拓扑约束**：`nodeAffinity`、`podAffinity` 把「同机柜」「同域」表达为亲和要求。

**K8s 与 Slurm 的资源表述差异**也直接影响调度：Slurm 里 GPU 是「节点的属性」，K8s 里 GPU 是「可独立请求的资源量」——前者适合「整卡/整机申请」的批处理，后者适合「按 GPU 粒度共享」的微服务。**从「按机器调度」到「按 GPU 调度」的转变，是云原生调度器最深刻的改进**，也是它更适合推理弹性的原因。

**辨析：Slurm 还是 K8s？** 这是 GPU 集群架构里的经典选择题。大型单体训练（万卡单作业）更接近 Slurm 的模型；多租户、多模型、弹性推理的云原生平台更接近 K8s。现实方案往往是**混合**：Slurm 管「重作业」，K8s 管「服务化与推理」——这也是 NVIDIA 在 SuperPOD 上同时提供两种接口的原因。

**云原生的另一大优势是「弹性」**：推理服务的负载随时波动，K8s 的 HPA（水平自动伸缩）能让 GPU 副本随流量增减；而 Slurm 的批处理模型天然没有「缩容」概念。**选择标准一句话：作业生命周期是「小时/天」用 Slurm，是「秒/分钟」用 K8s**——生命周期尺度决定调度范式。

**给混合方案的落地方案**：底层 Slurm 管物理资源池，上层 K8s 通过 Slurm Operator 把「Pod 申请」翻译成「Slurm 作业」，推理服务还能用虚拟 kubelet 无缝伸缩。**两条生态不是二选一，而是互补**——大型训练用 Slurm 的确定性，在线服务用 K8s 的弹性。

## 6 公式解析：碎片化的代价有多贵

用第一小节的公式把碎片量化，它是调度优化所有工作的「靶子」：

$$
U = \left\lfloor \frac{N}{k} \right\rfloor \cdot \frac{k}{N}
$$

分三步拆解：

- **第一步**：$\lfloor N/k \rfloor$ 是同时能跑的作业数，$k$ 是每个作业的节点数，两者相乘是「被占用的节点数」。
- **第二步**：除以总节点 $N$，得到利用率 $U$——理想是 1，现实永远小于 1，差出来的就是碎片。
- **第三步**：代入数字——$N=2048$、$k=300$：$\lfloor 2048/300\rfloor = 6$，$6\times300=1800$，$U = 1800/2048 \approx 88\%$。**248 个节点闲置，既不能跑任何 300 节点作业，也难凑成一个整作业**。

**降低碎片的三条路**：把作业按 $k$ 对齐（让 $N/k$ 除尽）、用回填把碎片填满、或允许作业缩放到「整片可用的最大块」。「调度优化」百分之八十是在做这三件事的排列组合。

**再考虑时间维度**：作业会结束，碎片随时间流动。调度的完整目标函数其实是「在时间窗口 $T$ 内，让累计完成作业数（makespan/throughput）最大」——这已经是一个带约束的优化问题，也是回填（backfill）在数学上的定位：**用「可预知的未来」去填补「现在」的空隙**。<span class="marginnote">回填的经典算法：按优先级排序待跑作业，允许低优作业「插入」大作业等待期的空档，条件是不延迟大作业的开始时间。这让平均作业完成时间（mean response time）大幅改善，是每个调度器默认开启的优化。</span>

## 7 小结

- 调度回答三问：**谁先跑、占哪些节点、怎么排队**；GPU 集群因 Gang 与拓扑两层约束而变难。
- **Gang Scheduling** 要求作业整组同时启动，否则 NCCL 全体 rank 无法就位。
- **资源碎片化**是头号敌人，利用率公式 $U=\lfloor N/k\rfloor\cdot k/N$ 永不等于 1。
- **拓扑感知调度**把 NVLink 域/机柜/轨变成软约束打分，防止「放对位置」被资源紧张牺牲。
- **Slurm** 管大型单体训练，**Kubernetes** 管云原生多租户；现实多为混合编排。
- **调度的尺度句**：作业生命周期以小时/天计用 Slurm，以秒/分钟计用 K8s；调度器本身也有规模瓶颈。
- 抗碎片三招：对齐作业尺寸、回填（backfill）、允许缩放到整片可用块。

**调度与容错的接口**：调度器会「驱逐」作业（抢占低优、节点维护、故障迁移），而驱逐必须有「可恢复」的前提——这就是下一篇检查点的作用。**调度与容错是同一枚硬币的两面：调度让资源流动，容错让流动不丢进度**。

在下一节，我们面对训练里最不想面对的事——**故障**：怎么检查点、怎么预测故障、怎么让训练在节点坏了以后继续——这就是 **训练容错**。
