# 语义网与知识图谱

## 为什么需要一张「机器可读的网」

上一篇的 KR 在单个知识库内解决「如何表示与推理」；本篇把问题放大到**互联网规模**：全世界几十亿条知识，如何让机器彼此共享、查询与推理？蒂姆·伯纳斯-李（万维网发明者）在 1998 年给出愿景——**语义网（Semantic Web）**：给网页里的信息附加**机器可读的语义**，让程序像人一样「读懂」网上内容。它的工程落地，就是 2012 年谷歌推出的**知识图谱（Knowledge Graph）**。

从「从极限到大模型」的视角看，知识图谱是**符号主义的互联网级实现**，而大模型是**联结主义的数据级实现**。理解知识图谱，等于理解符号派在「数据海量」时代如何存活——它没有死，而是换了一套工程语言（三元组、本体、图查询）继续生长，并反过来成为今天大模型可靠性的重要拐杖。

## 1 三元组：知识的原子单位

语义网的基石是**RDF（资源描述框架）**。它规定知识的最小单位是一条**三元组（triple）**：

**主语（subject）— 谓语（predicate）— 宾语（object）**

「北京是中国的首都」写成三元组：`北京 — 首都(是…的首都) — 中国`。这里的谓语其实是一条「有方向的边」，因此三元组天然构成一张**有向图**：主语是起点，宾语是终点，谓语是边上的标签。<span class="marginnote">关键设计：一切事物（人、城市、概念甚至抽象关系）都被统一称为「资源」，用 URI（统一资源标识符）命名。「北京」和「中国的首都」指向同一个 URI，机器才能判断它们说的是同一件事——这就是「语义」的起点：<strong>名字与身份的绑定</strong>。</span>

三元组的威力在于**极简而通用**：任何陈述都能拆成三元组。但极简也有代价——表达「所有鸟都会飞，除了企鹅」这种**带例外的全称命题**，单纯三元组做不到，需要上一层的本体语言来补充语义。

## 2 本体与 OWL：给图加上逻辑

RDF 图是「数据层」，**本体（ontology）**是「模式层」——它规定这张图里**可以出现哪些类型、哪些关系、哪些约束**。「人」是一种类，「城市是一种地方」「首都关系只能连接城市与国家」「每个人恰好有一个出生日期」——这些是本体层的声明。本体用 **OWL**（Web Ontology Language）书写，其逻辑底座正是上一篇的**描述逻辑**。

有了本体，知识图谱就有了三重能力：**一致性检查**（图里不会出现「这个人是城市」之类的错误）、**自动蕴含**（声明「城市⊆地方」后，系统自动知道北京是地方）、**增量演化**（加新类型不必重构整张图）。<span class="marginnote">本体就是现实世界的「数据库模式 + 完整性约束 + 推理规则」三合一。它把「这堆数据是什么含义」从程序员脑中搬到机器可读的声明里——这正是语义网「让机器理解」的关键一步。</span>

## 3 SPARQL 与图查询

数据用三元组存了，本体约束了，接下来是**查询**。语义网的标准查询语言是 **SPARQL**，它像「SQL 的图版本」：用「模式匹配」找图里所有满足条件的子图。查询「列出所有人口超过一千万、且是首都的城市」，SPARQL 会写成带变量占位符的三元组模式，在图中做模式匹配。

**辨析｜易错点：** SPARQL 是**精确查询**，不是「搜索」。查询 `?c 首都 ?x` 返回的是图里**字面上存在**的边；而「北京是不是中国的首都」这类**需要推理**的问题（图里只有「北京 位于 中国」），要依赖 OWL 蕴含或额外规则层，不是 SPARQL 一句能答的。**「查」与「推」是两层操作**——这决定了知识图谱系统里查询引擎与推理引擎的明确分工。

## 4 知识图谱：从理论到十亿实体

语义网的早期梦想（网页全部 RDF 化）没有完全实现——给网页写本体太贵。但它的技术栈以另一种形态爆发：**知识图谱**。2012 年谷歌发布 Knowledge Graph，把搜索从「匹配关键词」升级为「识别实体与关系」：搜索「北京」，搜索引擎知道它是个城市、是首都、有邻省、有地标，于是右侧的信息卡片自动生成。<span class="marginnote">知识图谱与语义网的关系可以这样记：语义网是「愿景 + 标准栈」（RDF/OWL/SPARQL），知识图谱是「工程实现 + 规模」，二者共享三元组与本体技术。今天百亿级实体的图谱，靠的是从维基百科、数据库、网页文本里<strong>自动抽取</strong>，而非手工编写。</span>

工业知识图谱带来两个关键能力。**实体消歧（entity disambiguation）**：「苹果」在「苹果发布新机」与「吃苹果有益健康」里指两个不同的实体——图谱把「苹果（公司）」与「苹果（水果）」做成两个节点，上下文自动选边。**关系补全（link prediction）**：图谱已知「北京—是首都—中国」，能推断「中国—有首都—北京」这种对称关系，甚至推测缺失的边。

## 5 公式解析：TransE——把三元组翻译成向量

知识图谱是符号结构，但深度学习要处理向量。**TransE**（2013）给出一个至今影响深远的桥：把每个实体和关系嵌入低维向量空间，并要求**「主语向量 + 关系向量 ≈ 宾语向量」**：

$$
\mathbf{h} + \mathbf{r} \approx \mathbf{t}
$$

- **第一步，认符号**：$\mathbf{h}$ 是主语实体的嵌入向量，$\mathbf{t}$ 是宾语实体的嵌入向量，$\mathbf{r}$ 是关系的嵌入向量——三者维度相同，都在同一个向量空间里。
- **第二步，读几何**：等式要求「北京向量 + 首都向量」落在「中国向量」附近。于是**关系的语义被编码成向量空间里的平移**：「首都」对所有首都-国家对，都是同一个平移步长。
- **第三步，看推理能力**：一旦学成，系统可以完成类比推理：如果「北京 + 首都 ≈ 中国」且「巴黎 + 首都 ≈ 法国」，那么「北京 - 中国 + 法国 ≈ 巴黎」——向量算术直接给出跨国类比。这正是「知识图谱 + 深度学习」的第一次亲密接触：符号关系被压进连续几何。
- **第四步，连主线**：TransE 与词嵌入（word2vec 的「国王 - 男人 + 女人 ≈ 女王」）数学同源，都是「关系 = 向量平移」。而大模型时代，把知识图谱喂给 Transformer 做**图增强预训练**（把三元组当作句子加入训练语料），已经成了缓解大模型幻觉的常规手段——知识图谱从「符号遗物」变成了「大模型的助记本」。

<span class="marginnote">TransE 的局限同样值得记下：它默认「每类关系是同一个平移」，无法表达「对称」「传递」等复杂关系的多样语义；后续 TransR、RotatE 等模型用不同几何（反射、旋转）补足。这条「把关系装进几何」的路，至今仍是知识图谱表示学习的主线。</span>

## 6 知识图谱 × 认知计算 × 大模型

三者今天正深度融合。对认知计算，知识图谱是**可解释知识**的现成载体：医疗图谱把「症状—疾病—药物」编成显式网络，推理结论可以回溯到具体边。对大模型，知识图谱是**事实锚点**：RAG 系统先在图谱里检索相关事实，再把事实塞进提示词，让模型「照着写」而不是「凭记忆编」。<span class="marginnote">这形成了认知计算特有的「双通道」答案：一条通道来自图谱的精确事实，一条通道来自大模型的流畅语言，最后由一个验证器裁决、并生成解释。可解释性不是事后解释，而是从一开始就把「证据链」显式建模。</span>

## 7 案例拆解：从零搭一张「人物—公司」小图谱

把图谱工程的手感建立起来，最好的办法是亲手搭一张小图谱。假设我们要建一张关于「科技公司高管」的知识图谱，覆盖「谁在哪个公司任什么职、哪些公司被谁收购」。从零开始有五步。

**第一步，确定本体（schema）**：先画类型与关系——类型：`人物`、`公司`；关系：`人物—任职于→公司`、`人物—职务→职务名`、`公司—被收购于→公司`。再定约束：「任职于」只能连接人物与公司、「被收购」只能连接公司对公司。这一步看似简单，却决定了整张图能答什么、不能答什么。

**第二步，抽取（extraction）**：从新闻与维基百科文本里用 NER 抽实体、用关系抽取抽三元组。「马斯克于 2022 年收购 Twitter」→ `马斯克—收购—Twitter`。抽取的文本是「源文本」，三元组是「断言」——**要保留源引用，这是可审计性的起点**。

**第三步，实体消歧（disambiguation）**：文本里的「Twitter」可能指公司、产品或事件。用上下文 + 图谱既有实体投票，把「Twitter」指到公司节点。这是整条流水线错误率最高的一步，也是《自然语言理解》的语义角色标注的直接应用。

**第四步，对齐与融合（alignment & fusion）**：两份不同来源对同一事实可能有冲突——「A 公司收购 B 公司」与「B 公司被 A 公司并购」。需要置信度打分与冲突消解：时间新的、来源权威的胜出。融合让图谱从「一堆三元组」变成「一份可信的知识」。

**第五步，存储与查询**：把图谱存进三元组库或图数据库，用 SPARQL 或图查询语言检索。同样一条「列出马斯克收购的所有公司」，在 SPARQL 里是一个带变量的三元组模式；在向量检索（TransE 嵌入）里是一段向量的最近邻搜索。**符号查询与向量检索并存，是现代图谱的标准姿势**。

把这五步连同「每步的输入输出」压成一张流水线表：

| 步骤 | 输入 | 输出 | 关键技术 |
| --- | --- | --- | --- |
| 定本体 | 领域需求 | 类型 + 关系 + 约束 | 描述逻辑 |
| 抽取 | 非结构化文本 | 候选三元组 + 源引用 | NER / 关系抽取 |
| 消歧 | 候选三元组 | 指向唯一实体的三元组 | 上下文消歧 |
| 融合 | 多源三元组 | 置信度标注的一致图谱 | 证据打分 |
| 存储查询 | 一致图谱 | 可检索的图 + 嵌入 | SPARQL / TransE |

**辨析｜易错点：** 这五步里最容易被低估的是**第三步的消歧与第五步的双检索**。新手常以为「图谱 = 一堆三元组」，于是直接跳过本体与消歧——结果建出来一张「同名实体互相打架、约束全无」的伪图谱：查「苹果」既返回水果也返回公司，怎么答都错。**图谱的价值不在于「图」，在于「图上的每个节点身份明确、每条边语义明确」**——身份与语义，正是第一步本体与第三步消歧赋予的。<span class="marginnote">这条「先定 schema 再做数据」的纪律，与《知识表示与推理》里「表达力先于数据」一脉相承。工业界血泪教训：跳过本体的「快速图谱」，规模越大越难修，因为错误的身份假设会随着融合一层层放大——数据量不是解药，结构正确才是。</span>

这张小图谱搭完，你手里就有了一台微型的「语义网」：有本体、有三元组、有消歧、有融合、有双查询。把它放大百万倍，就是谷歌、医学、金融里的工业知识图谱；把它接上大模型，就是《认知计算与深度学习》里「图谱做事实锚点」的 RAG 架构。图谱的每一块砖，本专题都给了出处。

最后，把知识图谱与「向量数据库」这对当代最容易混淆的技术区分清楚——因为 RAG 时代两者常被并列提起，但它们的知识观完全不同：

- **知识图谱存「关系」，向量库存「相似度」**：图谱回答「A 与 B 有什么关系」（精确、可推理）；向量库回答「谁和谁长得像」（模糊、可排序）。
- **图谱可追溯，向量库不可**：图谱的每条结论都能回溯到具体边与本体约束；向量库的相似性没有「证据」，只有「距离」。
- **图谱要 schema，向量库不要**：建图谱必须先定本体（费人力、但有结构）；建向量库只需嵌入（省事、但黑箱）。
- **两者互补而非替代**：RAG 的先进做法是「图谱检索事实 → 向量检索相似文本 → 两者合流进大模型」——图谱给「确凿」，向量库给「丰富」。

这个区分对认知计算尤其关键：知识图谱是「可解释的符号层」的载体，向量库只是「高维相似度」的索引。把知识图谱降格成「一种向量库」来用，等于把认知计算的骨架扔掉、只留肌肉——这正是许多「图谱项目」失败的根源。认知系统的正确姿势是**双轨**：图谱管「确凿的事实与规则」，向量库管「灵活的联想与补充」，各归其位。

最后给知识图谱一个「时代坐标」式的收尾：它在 2000 年代以「语义网」的名义起步，2012 年以「知识图谱」的名字复兴，2020 年代又以「RAG 的事实锚点」焕发第二春——**技术名字换了三次，内核（三元组 + 本体 + 可查询）从未改变**。读懂这个内核，你就不会被任何一个「新概念」迷惑：凡是「把知识变成可查询、可推理、可回溯的结构」的技术，骨子里都是知识图谱。这也是认知计算坚持「图谱给事实、模型给语言」的根本原因。

最后，把知识图谱与「信任」的关系点破：认知系统要被人信任，前提是「它的知识能被人查验」——而知识图谱正是「可查验知识」最成熟的载体。一个靠图谱给出事实、靠大模型给出语言的系统，可以这样回答质疑：「这个答案的依据是图谱里这条边，来源是这份文档，置信度是 0.87」——每一个字都可回溯。**知识图谱给认知计算的不只是「知识」，更是「知识的凭证」**——这份凭证，是所有高风险认知应用的信任基石。

## 8 小结

- **RDF 三元组**（主语—谓语—宾语）是语义网与知识图谱的原子单位，天然构成有向图。
- **本体 / OWL** 提供模式层：类型、约束与蕴含规则，让图「自洽且可推理」。
- **SPARQL** 做精确模式匹配查询；「查」与「推」是分离的两层。
- **知识图谱**是语义网的工程落地：实体消歧、关系补全让它成为互联网级的符号知识库。
- **TransE**（$\mathbf{h} + \mathbf{r} \approx \mathbf{t}$）把符号关系嵌入向量空间，开启知识图谱 × 深度学习的融合。
- 知识图谱今天是大模型的**事实锚点与助记本**，也是认知计算**可解释推理**的公共底座。
