## 为什么档案与数据库是数字人文的底座

前四节我们从单篇文本走到了语料库。但数字人文的许多研究，对象不是「文本库」，而是**分散的档案**：数千张战地照片、一部门档案里的十万件呈文、一座教堂三百年间的婚姻登记。要把它们组织成可检索、可关联、可长期存续的资产，需要两类基础设施——**数字档案**负责「保真与保存」，**数据库**负责「组织与查询」。本节是「第一篇 数字人文基础」的收束：它把前四节的单点技术汇合成一套完整的**数据底座**，也为后面「第二篇 方法与工具」的所有分析提供对象。理解这层底座，你才知道一份分析结果背后站着怎样的数据组织决策。

## 1 两种组织逻辑：档案与数据库

「档案」与「数据库」在日常语里常被混用，在数字人文里分工明确：

- **数字档案（digital archive）**：以**原始凭证**为核心的集合，强调**出处（provenance）与保真**——每件材料是谁、何时、如何入藏的，都要记录。它回答「这个对象存在过、长什么样」。
- **数据库（database）**：以**结构化记录**为核心的容器，强调**可查询与可关联**——把档案里的信息抽成字段与关系。它回答「哪些对象满足什么条件」。

一条典型流水线是：**档案保存原件（图像/全文 PDF），数据库承载抽出的结构化信息（人物表、事件表、关系表），两者用标识符互相挂接**。原件与结构化数据分离，是避免「为了建库而损毁档案原貌」的纪律。<span class="marginnote">这个「原件/数据分离」原则对应第三级《数据库》的「逻辑独立性」思想，也对应档案学的「原件主义」：数据模型再完美，也必须随时能回溯到原件核对——这是数字人文区别于纯数据科学的伦理底线。</span>

## 2 元数据：让档案可以被发现与信任

数据库存「内容」，元数据存「关于内容的信息」。人文档案的元数据有两套经典标准：

- **描述性元数据**：Dublin Core 的 15 个核心字段（标题、创作者、日期、语种、覆盖范围…），跨库互操作的「最小公约数」。MARC 则用于图书馆书目，字段更细。
- **结构性元数据**：EAD（编码档案描述）描述档案的层级结构——全宗 → 系列 → 案卷 → 件，保留档案原始的**登记层级**。

元数据不只是检索的钥匙，还是信任的凭证：**一个数字化对象缺失「来源」「拍摄日期」「处理管线」，就无法被学术引用。** 好的元数据记录的是「决策史」——谁选的版本、谁做的 OCR、谁校的稿，全部留痕。

两类元数据的典型字段对照如下：

| 元数据族 | 标准 | 典型字段 | 用途 |
| --- | --- | --- | --- |
| 描述性 | Dublin Core | 标题、创作者、日期、语种 | 跨库互操作与发现 |
| 描述性 | MARC | 编目标目、主题词、索书号 | 图书馆书目著录 |
| 结构性 | EAD | 全宗→系列→案卷→件 | 档案层级导航 |

一套完整的档案库通常三者都配：Dublin Core 供外部检索，MARC 供图书馆系统交换，EAD 保档案原始层级——三者各司其职，缺一不可。<span class="marginnote">这里与第七级《图书情报与档案管理》深度交叉：数字人文与 LIS 共享「知识组织」的核心问题，只是数字人文更强调把元数据变成可计算的分析输入，而不只是检索工具。</span>

## 3 核心对比：三种人文数据模型

数据库的「形状」决定分析能问什么问题。人文数据按关系复杂度在三种模型间选型：

| 数据模型 | 基本单元 | 擅长问题 | 短板 | 适用场景 |
| --- | --- | --- | --- | --- |
| 关系型（SQL） | 表 + 行 + 外键 | 精确字段查询、聚合统计 | 关系深、模式灵活时僵硬 | 书目、登记表、结构化事件 |
| 文档型（JSON/XML） | 嵌套文档 | 保留原文层级、半结构化 | 跨文档关联弱 | TEI 文本、档案原文 |
| 图模型 | 节点 + 边 | 关系路径、中心性、网络演化 | 数值聚合弱 | 人物—机构—作品网络 |

选型判据一句话：**数据的关系「是固定的」用关系型，关系的形状「要探索」用图模型**。现实中人文库几乎都是混合体——TEI 文档库 + 关系型索引 + 图模型分析层，各取所长。

再补充一个常被忽略的维度——**时间**：人文数据几乎都有时间戳（作品作于何年、人物生卒、事件发生于何时），因此建模时要么把时间建成字段，要么建成时间属性边。没有时间维度的人文数据库，等于把历史压平成一个截面；而带上时间的库，才能支持「某年的作者网络」「某十年的词频曲线」这类历时分析。时间字段的粒度也要预先定好（年？月？精确到日？），粒度不同，能回答的问题范围就不同。

## 4 查询思维：从 SQL 到「问题翻译」

数据模型的下一步是查询。数据库的价值最终落在「把研究问题翻译成查询语言」：

- 关系型用 SQL：`SELECT dynasty, COUNT(*) FROM authors GROUP BY dynasty`——「历代作者数量分布」。
- 图模型用查询或遍历：找「与李白相隔不超过两跳的唐代诗人」，在 SQL 里要递归自连接，在图中是一步邻居扩展。
- 全文检索用索引：倒排索引把「哪些文献提到『吐蕃』」从全库扫描变成 O(词频) 的查找。<span class="marginnote">倒排索引正是第三级《信息检索》的核心数据结构；到《数字人文与知识图谱》一节，我们会看到全文检索如何与实体链接叠加成「语义检索」。</span>

**一条黄金法则：先定义研究问题，再选数据模型与查询方式，而不是反过来。** 很多数字人文项目失败于「先把所有数据塞进一张大表」，等到想研究关系网络时才发现模型不支持。

## 5 长期保存与 FAIR 原则

数据库会过期，档案要传世。数字人文的数据底座必须应对技术过时的威胁——格式会死、软件会停产、存储介质会老化。为此有两套支柱性规范：

- **OAIS 参考模型**（开放档案信息系统）：把保存拆成摄取、存储、存取、分发等功能实体，明确「提交包/存档包/分发包」三种数据形态，并强制做**格式迁移与容灾复制**。
- **FAIR 原则**：让数据**可发现（Findable）、可访问（Accessible）、可互操作（Interoperable）、可复用（Reusable）**——每件数据有全局唯一标识符（DOI/ARK）、有可机读元数据、用开放格式（TIFF/XML/CSV 而非专有格式）、写清许可证。

这两个规范把「保存」从玄学变成工程：保存不是把硬盘放好，而是**承诺在 N 年后仍能让后人读到、理解、复算这批数据**。存档级格式的共性：开放、文档化、广泛支持、无损——这也是为什么 TIFF 胜过 JPEG、XML 胜过 Word、UTF-8 胜过本地编码。

## 6 案例：一座「抗战书信档案库」的数据模型

把三种数据模型与两种元数据标准串成一个完整案例。假设要建「抗战士兵家书档案库」，目标既支持「按写信人检索」又支持「研究书信网络」：

| 需求 | 数据形态 | 落点 |
| --- | --- | --- |
| 保存原始书信影像与全文 | TIFF + TEI/XML 文档 | 文档型存储原件 |
| 按写信人、收信人、日期、部队检索 | 关系型表（书信表、人物表） | SQL 查询 |
| 研究「谁给谁写信」的网络 | 人物—书信图模型 | 图分析层 |
| 记录来源与处理管线 | Dublin Core + 处理史字段 | 元数据层 |

关键设计决策是「三层的标识符一致」：同一封书信，在 XML 文档、SQL 表、图模型里用同一个 ID 指称，三处随时可互相跳转——原件在文档库，结构化信息在关系库，关系在图库，研究者在三者之间自由往返。

这个案例展示了一条通则：**人文数据库不是「选一种模型」，而是「按用途分层，用标识符缝合」**。档案馆最怕的不是数据少，而是「原件、结构化数据、分析结果」三者之间断了线。

最后补一句档案伦理：家书涉及隐私与情感，公开边界必须谨慎——原件可限制访问，结构化字段脱敏后才可公开。**数据库设计的第一课不是技术，而是「谁有权读、读到什么程度」**——这与《数字人文批评与伦理》的关怀一脉相承。

### 一个查询练习：把研究问题翻译成 SQL

把「翻译问题 → 写查询」的能力练熟，最有效的办法是拿真实问题练手。下面三个练习覆盖三种典型人文查询：

1. **单表聚合**：`SELECT dynasty, COUNT(*) FROM authors GROUP BY dynasty ORDER BY COUNT(*) DESC`——「历代作者数量排名」。
2. **跨表连接**：`SELECT p.name, w.title FROM persons p JOIN works w ON p.id = w.author_id WHERE p.birth_year BETWEEN 700 AND 800`——「八世纪作者及其作品」。
3. **时间窗口**：`SELECT year, COUNT(*) FROM events WHERE event_type = '战事' GROUP BY year`——「战事的年度分布」。

练习的收获不仅是 SQL 语法，更是**把「模糊的人文问题」切成「可查的精确条件」的能力**——这种能力在数据库之外同样成立，是数字人文研究者最通用的基本功。

### 数据库的未来：语义网

数据库技术还在演进，人文方向尤其值得关注**语义网（Semantic Web）**的落地：

- **链接开放数据（LOD）**：让不同机构的数据库通过共享标识符互相链接，人文学者的查询可以跨库漫游；
- **推理与约束**：本体逻辑自动检查矛盾（某人卒年早于生年）；
- **可生长性**：新史料不断以三元组形式汇入，库随研究成长。

**从关系表到语义网，数据库的演进方向始终是同一个：让「存」更靠近「知」**——人文数据库的终极形态，是一张持续生长的知识之网。

## 7 小结

- 数字档案管**保真与出处**，数据库管**组织与查询**；「原件/结构化数据分离」是纪律。
- 元数据双轨：Dublin Core 描述内容，EAD 描述档案层级；元数据记录的是「决策史」。
- 三种数据模型——关系型、文档型、图模型——按**关系是否固定**选型，现实项目常混合使用。
- 查询思维从「研究问题」出发：SQL 问字段、图遍历问路径、倒排索引问全文。
- 长期保存靠 **OAIS + FAIR**：唯一标识符、开放格式、格式迁移；保存是「对后人的承诺」而非「存硬盘」。
