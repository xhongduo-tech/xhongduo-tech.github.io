## 为什么从数据隐私开始

数据治理管「数据可信」，这一篇管「数据安全」。**数据隐私与安全**是数据科学的另一条高压线：数据集里藏着真实的个人（姓名、行踪、健康记录、支付信息），处理不当既是法律风险，也是道德失守。<span class="marginnote">隐私与安全是两件事但常被混说：<strong>安全</strong>管「数据不被偷、不被破坏」（技术防御），<strong>隐私</strong>管「个人信息被正当使用」（合规与伦理）。类比：安全是「门锁够不够结实」，隐私是「别人是否有权进这扇门」。数据科学家的每次取数与建模，都同时触碰这两件事。</span>从第3篇《数据获取》到第23篇《数据治理》，隐私是贯穿始终的约束线。

## 1 个人数据与法律框架

数据隐私保护的对象是**个人信息（personal data）**：能直接或间接识别到特定自然人的信息。姓名、身份证号、手机号、精确位置、浏览记录、健康数据——都属于个人信息。

全球法律框架以两部为代表：

**GDPR（欧盟《通用数据保护条例》）**：最严格、影响最广。核心权利包括**知情权、访问权、删除权（被遗忘权）、可携权**；违规罚款可达全球营业额的 4%。它管辖「处理欧盟居民数据的任何组织」，无论组织在哪。
**中国《个人信息保护法》（PIPL）**：与 GDPR 类似，强调**告知-同意**、目的限制、最小必要原则，并对重要数据的出境有专门限制。

**重点：无论法律在哪，数据科学家都该默记三条底线——告知同意、目的限制、最小必要。** 告知同意：收集前说明用途并取得同意；目的限制：数据只用于告知过的目的；最小必要：只收集完成任务所必需的最少数据。<span class="marginnote">「最小必要」是数据科学里最反直觉的一条：数据科学家本能想「能拿的全拿」，法律却要求「够用就好」。实践中，这条原则会逼你把「某个字段是否真的需要」想清楚——这恰好也是好的特征工程（第16篇）的纪律。合规与质量在这里殊途同归。</span>

## 2 安全的技术面：加密、脱敏与访问控制

隐私的合规最终要靠技术落地，三类技术手段构成地基：

**加密（encryption）**：数据在传输中（TLS）与存储中（静态加密）都加密。密钥管理是加密的命门——密钥泄露，加密等于没加密。

**脱敏（masking）**：把敏感字段替换为不可识别形式，用于开发、测试、分析环境。常见手段：

**假名化（pseudonymization）**：把「张三」替换为随机 ID，但仍可关联回原人。
**匿名化（anonymization）**：彻底去除可识别信息，**不可再关联回个人**——匿名化后的数据一般不再受个人数据法律的严格管辖。

**访问控制（access control）**：按角色控制谁能看什么数据。原则是**最小权限**：分析师能看脱敏数据，不能看原始身份证号；权限按需申请、按需撤销。<span class="marginnote">脱敏与匿名的区别常被忽略：<strong>假名化是「可逆的伪装」，匿名化是「不可逆的摧毁」</strong>。假名化数据仍属个人信息（有密钥就能还原），法律要求照旧；匿名化数据则退出个人信息范畴。做分析时用假名化就够了，做对外公开数据集才需要匿名化。别把「换了个 ID」当「匿名」。</span>

## 3 差分隐私：让统计结果不泄露个体

脱敏保护的是「存储中的字段」，但还有一个隐蔽的泄露通道：**统计结果本身**。看似安全的聚合数字，可能反推出个体信息——比如「某病发病率 50%」加上「班里只有 2 个人」这样的背景知识，就能猜出某人是否患病。这个攻击叫**重识别（re-identification）**，最著名的案例是 Netflix 竞赛：研究者用「观影记录 + 公开 IMDb 数据」反推出了用户身份。

**差分隐私（differential privacy）** 是应对这类攻击的数学框架：**在查询结果里注入受控噪声，让「包含某个体」与「不包含某个体」的查询结果统计上不可区分**。<span class="marginnote">差分隐私的核心思想是「保证个体的加入对输出几乎无影响」：设计一个随机化机制，无论数据集中是否包含某个人的数据，输出的分布都极其接近。这样攻击者即便用背景知识，也无法确认某个体是否在数据中。代价是统计结果带噪声、精度下降——隐私与精度是一对权衡，参数 ε 控制这个权衡。</span>

**公式解析：拉普拉斯机制。** 最简单的差分隐私机制是在真实答案 $f(D)$ 上加上**拉普拉斯噪声**：

$$
\tilde{f}(D) = f(D) + \text{Lap}\!\left(\frac{\Delta f}{\varepsilon}\right)
$$

- **第一步，$\Delta f$（敏感度）**：删除任意单个个体的数据，查询结果最大变化多少。计数查询的敏感度是 1——多一个人，计数最多变 1。
- **第二步，$\varepsilon$（隐私预算）**：越小越隐私。$\varepsilon \to 0$ 时噪声无穷大，结果完全无用；$\varepsilon$ 越大，噪声越小、隐私保障越弱。<span class="marginnote">ε 的直觉：它衡量「输出结果对单个人的加入有多敏感」。ε 小 = 机制更随机 = 更隐私但更不准；ε 大 = 更接近真实答案但更容易被反推出个体。实际系统（如苹果、Google 的隐私统计）会为不同的 ε 预算做分配与累计管理——每次查询都消耗隐私预算，预算耗尽就该停止查询。</span>
**第三步，$\text{Lap}(\cdot)$**：拉普拉斯分布，长尾分布，能产生「偶尔很大的噪声」，正是掩盖个体差异所需要的。

**重点：差分隐私保证的是「单个个体的加入与否，几乎不影响任何人看到的输出」。** 它把「隐私保护」从「技术承诺」变成「可证明的数学性质」，也因此成为隐私保护的标准学术框架。

## 4 隐私与数据科学：不是对立的，而是约束

很多数据科学家把隐私法规当成「阻碍创新的麻烦」。更健康的视角是：**隐私是一组硬约束，数据科学在这个约束下设计解法**——就像预算、算力一样。三个实用姿态：

1. **默认隐私（privacy by design）**：在新项目设计阶段就考虑隐私，而不是事后补救。
2. **数据分级**：把数据按敏感度分级（公开/内部/敏感/机密），不同级别适用不同的存储与访问策略——把「一刀切」变成「分级管控」。<span class="marginnote">数据分级是隐私治理的实用抓手：把「脱敏数据可以自由分析、原始敏感数据要审批、核心机密数据仅限指定人员」写成策略，落到访问控制上，让「最小权限」可执行。分级工作通常与第23篇的数据目录一起做——目录里给每个数据集标上敏感级别。</span>
3. **技术替代**：能不用原始敏感数据就别用——用脱敏数据、聚合数据、合成数据（synthetic data）替代原始数据训练与分析。

**辨析｜易错点：** 一个危险的误区是「我脱敏了，就可以随便用」。脱敏（假名化）后的数据**仍可能被重识别**——结合外部数据，脱敏 ID 也能被反推回个人。**脱敏降低风险，不等于消除风险**；真正的保护需要「脱敏 + 访问控制 + 差分隐私 + 用途审查」的组合拳。

## 5 数据科学家的隐私自查清单

把隐私与安全的要求变成一份「开工前」清单，让合规从「担心」变成「可操作」：

**取数阶段**：

- [ ] 我申请的数据权限是否**最小够用**（只要我分析需要的列，不整表全拉）？
- [ ] 我是否知道每列是原始字段还是脱敏字段？敏感字段（身份证、手机号、精确位置）是否已脱敏？
- [ ] 数据使用目的是否在**授权范围内**（申请时说「分析流失」，就不能拿去做营销）？

**建模阶段**：

- [ ] 是否避免使用「可间接识别个体」的原始字段（如精确生日、邮编 + 姓氏组合）？
- [ ] 模型输出是否会暴露个体信息（生成模型的「记忆」、反推训练样本）？
- [ ] 差分隐私或聚合手段是否必要、是否已用？

**发布与协作阶段**：

- [ ] 对外发布的统计是否经过**重识别风险评估**（第3节的组合攻击）？
- [ ] 密钥、token 是否已从代码和文档中清理（第3篇的 API Key 纪律）？
- [ ] 分析结果是否有「数据来自脱敏副本、勿外传」的标注？

**辨析｜易错点：** 清单不是「打勾了就安全」。真正的风险常在**边界情况**：你申请了脱敏数据，却在一个 SQL 里 join 回原始表；你发布了「年龄段 × 地域」的统计，看似聚合，却被「小格子重识别」（一个格子只有 1 个人，隐私全暴露）。**「看起来安全」不等于「经得起重识别攻击」**——把这份清单当「最低底线」，真正的安全要靠第4节的「组合拳」意识。

**重点：隐私是数据科学家的职业伦理，不是合规部门的专属。** 每一次你决定「要不要多拿一列、要不要发布这个统计」，都是一次隐私判断。这份清单的意义是让这些判断**变得可审查、可传授**——当隐私意识内化成习惯，你写出的每一个取数查询、每一份报告，都自动站在了「尊重个体」这一边。

### 多法域合规的现实：数据没有国界，法律有

数据科学项目常常跨法域运行——服务器在 A 国、用户在欧洲、研发团队在 C 国。多法域合规不是「选一个最宽松的遵循」，而是「最严格的约束同时生效」。

一个典型的场景：你的公司在中国，服务器在新加坡，产品有欧盟用户。这时**三套法律同时压过来**：

- **中国《个人信息保护法》（PIPL）**：数据出境要评估、重要数据出境要申报——数据从境内服务器出境就有约束。
- **GDPR**：只要处理欧盟居民数据，无论服务器在哪，都要遵守「告知-同意」「被遗忘权」等规则。
- **本地数据法**（新加坡 PDPA）：同样有独立的通知、同意与跨境传输要求。

**合规的现实策略是「就高不就低」**：设计数据流程时，直接按最严格的法域标准做（通常 GDPR 最严），再核对本地要求的差异——**按最严标准设计，能同时满足所有法域，代价是「过严」而非「违规」**。

**辨析｜易错点：** 一个隐蔽的合规盲区是「**云服务商的地域切换**」。你今天把数据放在欧洲区、明天工程师图方便切到美国区——这本身就是一次「数据跨境传输」，可能触发申报义务。**数据存储的地域是合规状态的一部分**，工程上的「方便」不能绕过「地域」这条红线。

**重点：隐私合规是「工程约束」，不是「法务提醒」。** 它应该被设计进数据架构（存哪个 region、脱敏在哪一层做、权限怎么管），而不是事后被发现。数据科学家在架构选型、取数设计时就把「数据会去哪、谁能看」想清楚——这份「地域与权限意识」，是第23篇数据治理在现代合规环境下的延伸。

## 6 小结

- **安全**管「防偷防坏」，**隐私**管「正当使用」；二者是数据科学的合规高压线。
- 法律底线三条：**告知同意、目的限制、最小必要**；GDPR 与 PIPL 是最重要的两个框架。
- 技术三件套：**加密、脱敏（假名/匿名）、访问控制（最小权限）**；假名化可逆、匿名化不可逆。
- 统计结果也会泄露个体（**重识别**），**差分隐私**用注入噪声让个体「不可区分」，ε 是隐私-精度的权衡旋钮。
- 隐私是**设计约束**而非阻碍：默认隐私、数据分级、技术替代。
