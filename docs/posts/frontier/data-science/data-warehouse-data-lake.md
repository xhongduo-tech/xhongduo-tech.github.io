## 为什么从仓库与湖开始

关系数据库适合支撑业务系统（下单、登录），但不适合大规模分析：分析要跨表聚合全量历史，事务数据库扛不住这种查询压力。于是数据世界分化出两类大规模存储：**数据仓库**与**数据湖**。<span class="marginnote">二者的根本区别一句话：<strong>仓库存「处理好的、为分析优化的」数据，湖存「原样的、还没想好怎么用的」数据</strong>。理解这个区别，就能理解企业数据架构里「哪里该放什么」。它与第三级《数据库》的知识衔接：仓库和湖的底层最终还是要落到文件存储或列存引擎。</span>

## 1 数据仓库：为查询和分析优化的数据库

**数据仓库（data warehouse）** 是一个面向分析的、集成化的、时间稳定的数据集合。它把来自多个业务系统的数据**抽取、清洗、转换后集中存放**，让分析师用一个统一模型查全公司的数据。

仓库的三大特征：

**面向主题（subject-oriented）**：按「客户」「订单」「商品」等业务主题组织，而非按业务系统组织。
**集成（integrated）**：统一命名、单位、编码——财务系统里的「cust」与 CRM 里的「customer」在仓库里合并成一个「customer」。
**时间稳定（non-volatile）**：仓库数据按历史快照留存，支持回溯分析。

技术上的关键设计是**列式存储**：按列而非按行存数据。分析查询常只扫少数几列（如全表只取 `region` 和 `amount` 两列），列存能跳过无关列，压缩率也远高于行存。<span class="marginnote">列式存储的直觉：如果按行存，想算「全国各区域总销售额」就得把每行的所有字段都读出来再丢弃；按列存，只需读 `region` 与 `amount` 两列的文件。行存适合「一次取一整行」（事务），列存适合「一次扫一整列」（分析）——这个分野也解释了为什么分析型数据库（ClickHouse、Snowflake、BigQuery）清一色列存。</span>

## 2 数据湖：把一切原样存下来

**数据湖（data lake）** 是「先把所有原始数据都存下来，以后再说」的存储哲学：把结构化的表、半结构化的日志、非结构化的图片视频，**以原始格式**全部放进廉价的分布式对象存储（如 S3），不预先定义 schema。

湖的三大优势：

**低成本**：对象存储远比数据库便宜，海量原始数据堆得起。
**schema-on-read**：存的时候不强制结构，读的时候再按需解析——灵活应对未知用途。
**全量保留**：原始数据不丢，未来想换一种清洗方式、重建特征，随时可以从源头重来。

**辨析｜易错点：** 数据湖最有名的陷阱叫「**数据沼泽（data swamp）**」——只管往里存、不做元数据管理，最终数据堆成没人知道内容、没人敢用的烂泥塘。**数据湖的成败不在存储，而在治理**：谁来写、谁能读、数据的血缘与质量如何追踪。没有治理的湖，很快会变成沼泽。

## 3 数据仓库与数据湖的对照

用一张核心对比表把二者的分工钉清楚：

| 维度 | 数据仓库 | 数据湖 |
| --- | --- | --- |
| 数据结构 | 预先定义 schema（schema-on-write） | 读时解析（schema-on-read） |
| 数据类型 | 以结构化为主 | 结构化 + 半/非结构化 |
| 数据质量 | 清洗、集成后入库 | 保留原始形态 |
| 存储成本 | 较高 | 低 |
| 典型用户 | 分析师、BI、决策者 | 数据科学家、数据工程师 |
| 典型用途 | 固定报表、指标、BI 看板 | 探索性分析、机器学习原始数据 |
| 代表技术 | Snowflake、BigQuery、Redshift | S3 + Hudi/Iceberg/Delta Lake |

**重点：仓库与湖不是二选一，而是互补。** 现代数据架构的主流是「**湖仓一体**」（lakehouse）：以低成本湖存原始数据，再用一套表格式（Delta Lake、Iceberg）在湖上提供仓库级的 ACID 事务与查询优化——「湖的存储 + 仓的体验」。<span class="marginnote">湖仓一体的技术核心是「表格式」（table format）：它在廉价对象存储之上叠加一层「表的元数据与事务日志」，让原来只适合批量读的湖变成可事务化读写的「湖表」。这层抽象同时解决了「仓库贵、湖脏」两个老问题，是当前数据架构演进的主线。</span>

## 4 从数据科学家的视角选型

数据科学家在具体项目里，应该用哪种存储？一个实用的决策思路：

1. **要快速出报表、看固定指标** → 数据仓库。schema 清晰、查询快、语义统一。
2. **要探索新数据源、训模型要原始数据** → 数据湖。别让「先建 schema」拦住探索。
3. **模型要的特征是一份「宽表」** → 往往是从仓库或湖加工后落到一张分析表/特征表，供训练时批量读取。

**辨析｜易错点：** 一个常见误区是「数据湖 = 大数据，所以更好」。湖与仓是**分工不同**，不是**等级不同**。把需要高可用、高一致性的业务数据放进无人治理的湖，和把原始日志强行建模进仓库，都是选型错误。选型的判断标准永远是「这个数据要支撑什么用途」。

## 5 仓库里的模型设计：星型与雪花

数据仓库「按主题组织」具体怎么组织？答案藏在**维度建模（dimensional modeling）**里，它用两个概念搭建分析的地图：

**事实表（fact table）**：存放「发生了什么」的数值度量与关联键。如订单事实表，每行一笔订单，含金额、数量，以及指向各维度的外键。
**维度表（dimension table）**：存放「谁、何时、何地、何种商品」的描述性属性。如用户维度表、时间维度表、商品维度表。

**星型模型（star schema）**：中心一张事实表，四周放射状连接若干维度表。它像一颗星，查询时从中心事实表出发，JOIN 少量维度表即可——**结构简单、查询快，是分析场景的主流**。

**雪花模型（snowflake schema）**：维度表再进一步规范化（时间维度拆成「年-月-日」层级表），像雪花一样分叉。**更省存储，但 JOIN 层数多、查询慢**。

**重点：星型 vs 雪花的选择，本质是「查询速度」与「存储冗余」的权衡。** 现代仓库存储越来越便宜、查询越来越被优化，**星型几乎总是赢家**——它牺牲一点冗余，换来了「分析师一眼看懂 + 查询少 JOIN」。维度建模的意义在于：**把「一堆表」变成「一套分析师能共同理解的分析地图」**，这正是第23篇「指标口径统一」在结构层面的保障。<span class="marginnote">维度建模是数据仓库的「通用语言」：无论底层是 Snowflake、BigQuery 还是 Redshift，分析师都按「事实 + 维度」的框架写查询。如果你接手一个仓库，第一步就是找「哪张是事实表、哪些是维度表」——这张地图决定了你对整个数据资产的理解效率。</span>

**辨析｜易错点：** 新手常把「业务库的表」直接搬进仓库当维度表用。业务表会更新（用户改地址就覆盖旧值），而分析需要「历史快照」——**维度建模要求维度表按「渐变维度」处理（保留历史版本），事实表「只追加、不改写」**。把「会变的业务表」当「稳定的分析维度」用，是仓库里最经典的数据质量事故源头。

### 现代数据栈：把仓库与湖的抽象落地

理解了仓库、湖与湖仓一体，再补一张「现代数据栈」的拼图——它告诉你数据架构的每一层由什么工具承担。一个典型现代数据栈的分层：

| 层级 | 职责 | 代表工具 |
| --- | --- | --- |
| 数据接入 | 把各系统数据搬进来 | Fivetran、Airbyte、Debezium |
| 存储 | 原始与处理后的数据 | S3、Snowflake、BigQuery |
| 湖表格式 | 在对象存储上提供事务 | Delta Lake、Iceberg、Hudi |
| 计算引擎 | 大规模 SQL 与批流处理 | Spark、Trino、Flink |
| 调度编排 | 管理流水线依赖 | Airflow、Dagster |
| 数据目录与质量 | 元数据、血缘、质量监控 | DataHub、Great Expectations |
| BI 与分析 | 报表与自助分析 | Looker、Metabase |

**重点：现代数据栈的核心理念是「用最佳组件拼装，而非全家桶」。** 每一层可以独立选型、独立演进——这正是仓库与湖之争在 2020 年代后的答案：**不必在「仓库还是湖」二选一，而是用「湖存储 + 湖表格式 + 灵活计算」的组合，同时获得两者的优点**。理解这张分层图，你就能看懂任何一家公司的数据架构图在讲什么。

**辨析｜易错点：** 面对现代数据栈，最常见的误区是「工具越多越好」。每多接一个工具，就多一层运维与数据漂移风险。**选型的判断标准是「这个工具解决的是不是我现在最痛的问题」**——初创团队直接用云仓库 + 调度 + BI 三件套就够，不必急着上全套湖仓组件。数据架构的成熟度，是用「需要」而非「时髦」衡量的。

### 仓库的建模流程：从需求到星型

理解了星型模型，再看它怎么「造」出来，仓库就有了一张施工图。流程分五步：

1. **梳理业务过程**：先列「公司发生了哪些可度量的事件」——下单、支付、发货、退款，每个是一个事实表候选。
2. **确定事实**：对每个业务过程，选「可加的数值度量」——订单金额、商品数量。度量要「可加」：能按任意维度求和才有分析价值。
3. **确定维度**：围绕事实确定「从哪些角度切」——时间、用户、商品、渠道、地域。每个角度是一张维度表。
4. **建模**：事实表放度量 + 维度外键，维度表放描述属性——星型模型成型。
5. **加载与验证**：写 ETL 把数据填进去，用质量检查（第20篇）验证「订单数与业务系统对得上」。

**重点：建模的顺序是「先事实、后维度」，思考的顺序是「先问『要分析什么』，再反推『要建什么』」。** 仓库不是为了「存数据」而建，是为了「回答分析问题」而建——**从问题出发反推建模**，才不会建成「存了一堆没人用的表」的仓库。这一步，是第23篇「指标口径统一」在结构层的落实。

**辨析｜易错点：** 新手建仓库最常见的错误是「把业务库的表原样搬来」——业务库是「事务型」设计（避免冗余、保证更新），仓库是「分析型」设计（方便聚合、容忍冗余）。**直接搬表，等于用「防更新」的结构去服务「狂查询」的需求**——维度建模正是为了纠正这个错位而存在。

## 6 小结

- **数据仓库**：面向分析、集成化、时间稳定的存储，按主题组织，**schema-on-write**，用**列存**优化分析查询。
- **数据湖**：原样存一切原始数据的廉价存储，**schema-on-read**，灵活但易变「数据沼泽」——成败在治理。
- 仓库 vs 湖：**结构 vs 原始、贵 vs 便宜、报表 vs 探索**，不是替代而是互补。
- **湖仓一体**（lakehouse）用表格式在湖上提供仓库级体验，是现代架构主线。
- 选型看**用途**：固定报表进仓，探索与模型原始数据进湖。

在下一节，数据量真的大到单机装不下时，分布式计算引擎登场——这就是**大数据技术（Hadoop/Spark）**。
