## 为什么从流程开始

上一篇确立了数据科学的定义与认识论底线。但定义是静止的，数据科学却是**动作**：一个问题进来，一份报告或一个模型出去，中间经过若干明确的环节。<span class="marginnote">这里的「流程」观念与软件工程的软件生命周期、第四级《机器学习》里的建模流程一脉相承——都是把不可预测的创造性工作拆成可管理、可复检、可迭代的阶段。</span>如果只记得「清洗 → 建模 → 出结果」这种三句话版流程，你会漏掉数据科学里最容易翻车的两个环节：问题定义与部署监控。

## 1 流程全景：CRISP-DM 与它的现代变体

数据科学流程最经典的框架叫 **CRISP-DM（Cross-Industry Standard Process for Data Mining，跨行业数据挖掘标准流程）**，它把工作拆成六个阶段：

1. **业务理解（Business Understanding）**：把模糊的业务诉求翻译成可分析的问题。
2. **数据理解（Data Understanding）**：收集并初步探索数据，验证数据能否回答问题。
3. **数据准备（Data Preparation）**：清洗、变换、构造特征，得到建模用的数据集。
4. **建模（Modeling）**：选择并训练模型，反复调参。
5. **评估（Evaluation）**：在业务标准下检验模型是否达标。
6. **部署（Deployment）**：把模型接入生产系统，持续监控。

现代工业界常用一个更简洁的八步表述：**问题定义 → 数据获取 → 数据清洗 → 探索性分析（EDA）→ 特征工程 → 建模 → 评估 → 部署与监控**。<span class="marginnote">你会在本专题后续章节一一对应：第3篇《数据获取》、第4篇《数据清洗》、第5篇《探索性数据分析》、第14篇《机器学习工作流衔接》、第15篇《模型评估与选择》。流程不是一张地图，而是本专题的目录。</span>

**重点：CRISP-DM 不是线性的，而是环形的。** 评估阶段发现数据不足，会回到数据准备；部署后监控发现性能衰减，会回到建模甚至业务理解。真实的项目里，这个环往往要转很多圈。

## 2 最容易被跳过的环节：业务理解

几乎所有数据科学项目的失败，都能追溯到第一步没做好。业务理解的交付物是**把「模糊诉求」翻译成「可分析问题」**。

举个例子，运营部门说「用户流失太严重，帮我们分析分析」。这个诉求没法直接分析。数据科学家要追问：

谁是「用户」？注册未付费算不算？超过 30 天未登录算不算？
「流失」的判定标准是什么？阈值取几天？
分析目标是什么：解释原因，还是预测谁会流失，还是给出挽留建议？三种目标对应完全不同的方法。

把这些追问的结果写下来，就得到一份**问题定义文档**。它至少包含三要素：

**目标（Objective）**：用一句话说明要解决什么问题。
**成功标准（Success Criteria）**：怎么判断做成了？是预测准确率，还是挽留率提升，还是成本下降？
**约束（Constraints）**：数据时限、隐私边界、算力与预算、合规要求。

**辨析｜易错点：** 初学者最常犯的错，是把「有了数据就开始建模」当成流程起点。**没有清晰问题定义的建模，产出的是「答案」，而不是「对问题的答案」。** 如果你做的模型连「成功」都无法定义，你就无法知道自己是否成功——这比模型精度低更致命。

## 3 流程中的数据产物：每次迭代都要有交付物

流程不是走形式，每一环都要有**可检验的交付物**。一个成熟的团队，会用下面的清单管理进程：

| 环节 | 典型交付物 | 检验问题 |
| --- | --- | --- |
| 业务理解 | 问题定义文档 | 目标、成功标准、约束是否齐备？ |
| 数据理解 | 数据清单与质量报告 | 各字段缺失率、取值范围、来源是否记录？ |
| 数据准备 | 干净的数据集 + 处理日志 | 清洗规则可复现吗？换了环境结果一样吗？ |
| 建模 | 模型文件 + 训练日志 | 超参数与随机种子是否固定？ |
| 评估 | 评估报告 | 在**留出集**上的指标是多少？是否过拟合？ |
| 部署 | 接口文档 + 监控面板 | 延迟、吞吐、数据漂移指标是否可观测？ |

**可复现性（reproducibility）** 是这些交付物背后的共同底线：任何一次清洗、任何一次训练，都应该能被原样重跑一遍。<span class="marginnote">可复现性的具体技术手段包括：固定随机种子、记录依赖版本、把处理流程写成脚本而非手工点击、用版本管理保存数据与代码。数据科学里的「科学」二字，一半体现在可复现上——不能复现的结论等于没有结论。</span>

## 4 循环中的反馈：流程为什么会回头

CRISP-DM 的环形本质，来自数据科学工作的**不确定性**：你事先并不知道数据能否回答你的问题。因此真实过程是一个「假设-检验-修正」的循环，下面两种回头最常见：

- **数据理解 → 回业务理解**：探索数据后发现，现有数据根本无法度量「流失」，必须重新定义问题或补充数据源。
- **评估 → 回数据准备**：模型在测试集上表现不佳，分析后发现是训练/测试划分泄漏（data leakage），或特征构造引入了未来信息，需要回到特征工程修正。

**重点：流程回头的次数，往往与项目成败正相关。** 一次都不回头直接上线，要么是问题过于简单，要么是评估做得太马虎。数据科学不奖励「一次走完」，奖励「走得稳、回头快」。

## 5 从 CRISP-DM 到 MLOps：流程的现代形态

数据科学流程在上规模后，演变成了一个更完整的体系——**MLOps（机器学习运维）**。它不是对 CRISP-DM 的否定，而是把「部署与监控」这一环从项目收尾提升为持续运营。

MLOps 补上了传统流程缺的三块：

1. **实验追踪**：每次建模的参数、数据版本、结果都要记录（工具如 MLflow、Weights & Biases）。没有它，三个月后你根本说不清「那个 AUC 0.92 是拿哪份数据、哪组参数跑出来的」。
2. **模型版本与回滚**：模型像软件一样有版本。新模型上线前做 A/B 对比，效果不如旧模型就回滚——第29篇《数据驱动的决策》里「错误代价决定自动化程度」在此落地。
3. **持续监控与再训练**：模型上线只是开始。数据分布漂移、业务规则变化会让模型性能衰减，监控发现后触发再训练——第21篇《流数据处理》里的「概念漂移」正是监控的对象。

**辨析｜易错点：** MLOps 常被误解为「更高级的 DevOps」。两者的差别在「数据也在变」：软件代码不变、行为不变，模型却在数据漂移时悄悄退化。**MLOps 的核心是「把『模型会过期』这个事实管起来」**，而不是简单地把训练脚本打包成 CI/CD。理解了这一点，你就不会把 MLOps 做成「定时跑脚本」这么浅。

**重点：流程的成熟度，从「一人跑通」到「团队可持续运营」。** CRISP-DM 教会你「怎么走完一次」，MLOps 教会你「怎么让这条流水线一年 365 天可靠地转」。数据科学家的职业进阶，就是从前者走向后者——这也是第31篇《案例实践》上线环节要展开的内容。

### 团队角色：数据工程师、分析师与科学家

流程要运转，靠的是团队分工。三个角色的边界值得说清——因为很多项目卡在「职责不清」而不是「方法不行」：

- **数据工程师（Data Engineer）**：负责「数据能可靠到达」——搭建仓库/湖、写 ETL/流管线、保证质量与性能（第17-24篇的主场）。交付物是「可靠的数据管道」。
- **数据分析师（Data Analyst）**：负责「数据在回答什么」——做报表、下钻、诊断、把结果讲给业务听（第25篇的「描述 + 诊断」层）。交付物是「洞见与报告」。
- **数据科学家（Data Scientist）**：负责「数据能预测什么、该做什么」——建模、实验、把预测与建议落地（第9-16篇 + 第29篇）。交付物是「模型与决策支持」。

**重点：三者不是「高低级」，而是「不同工位」。** 数据科学家不能没有工程师的管道与分析师的口径——模型的质量上限由数据管道决定；分析师不能没有科学家的预测——诊断到瓶颈后要靠模型给出前瞻。**一个成熟的数据团队，是「工程师保证数据对，分析师保证看得清，科学家保证看得远」的三段接力。**

**辨析｜易错点：** 最常见的团队问题是「角色错配」——让科学家去修管道（浪费建模能力），或让工程师去解释业务洞见（浪费领域判断）。小团队里身兼数职是常态，但**要清楚「此刻自己在哪个工位、按哪个工位的标准验收」**。你自己也要想清楚：你正在培养的能力，是更偏工程、分析还是建模？本专题四个部分正是这三条能力的完整图谱——哪里弱，就回哪一篇补。

### 流程中的文档与汇报

流程的最后一个隐性环节是**文档与汇报**——它常被忽略，却决定分析能否落地。三条经验：

1. **过程文档比结论文档更难写，也更有价值**：记录「数据从哪来、清洗做了什么、模型怎么选、为什么放弃某个方案」——这份「过程账」是团队复盘的依据，也是后来者接手的基础。
2. **结论文档要「一个人读得懂」**：假设读者只有 5 分钟——标题即结论、一张关键图、一个行动建议。细节放附录。
3. **汇报时备好「三问」**：这结论有多可靠？（不确定性）在什么条件下会失效？（边界）如果要更多人相信，还需要什么？（下一步）

**重点：数据科学项目的交付物，不只是「模型或报告」，还有「让过程可理解」。** 一个只交付结论的项目，三个月后就变成「不知道当初为什么这么做」的黑历史；一个有完整文档的项目，是团队的资产。**把「写文档」当成流程的一部分（而非事后补），是数据科学专业性的分水岭。**

## 6 小结

- 数据科学流程的经典框架是 **CRISP-DM**：业务理解 → 数据理解 → 数据准备 → 建模 → 评估 → 部署。
- 现代变体是八步表述，本专题的章节划分与它一一对应。
- **业务理解**是最关键也最容易被跳过的环节，交付物是含目标、成功标准、约束的问题定义文档。
- 每一环都要有**可检验的交付物**，可复现性是共同底线。
- 流程本质是**环形迭代**，评估与数据理解阶段最常见的回头是流程的正常组成部分。
