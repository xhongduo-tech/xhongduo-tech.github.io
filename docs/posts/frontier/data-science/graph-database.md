## 为什么从图数据库开始

关系数据库用「表 + 外键」表达关系，但有些问题的核心就是「关系本身」：谁是谁的朋友、哪两件商品常被一起买、欺诈团伙怎么连成网络。这类问题用「表」表达别扭，用**图**表达却天然顺畅。<span class="marginnote">图数据库与第22篇《大数据技术》里 Spark 的 GraphX、第四级《图神经网络》一脉相承：底层是「点 + 边」的数学结构，来自第一级《集合》与第二级《离散数学》里的图论。图数据库的独特之处在于<strong>把「边的查询」做成第一公民</strong>——查「好友的好友」在表模型里要多次 JOIN，在图里只是一次「跳两步」。</span>图数据库就是为这类「关系密集」的数据设计的存储与查询引擎。

## 1 图数据模型：顶点、边与属性

图数据库以**属性图（property graph）** 为基本模型，三个概念：

**顶点（vertex/node）**：实体，如一个用户、一部电影。可带属性（姓名、年龄）。
**边（edge/relationship）**：实体间的关系，如「A 关注了 B」。边**有方向**（A→B）、**有类型**（follows、purchased），也可带属性（关注时间）。
**标签（label）**：给顶点/边打类别，如「用户」「商品」。

**重点：图模型把「关系」本身存储为实体，而不是像表模型那样靠 JOIN 现算。** 这意味着「跨多跳的关系查询」（A 买了商品，该商品被哪些 B 也买过，这些 B 还买过什么）不需要昂贵的多表连接，而是一次沿着边的遍历。<span class="marginnote">对比表模型：查「用户 A 的二度好友」在 SQL 里要写两次自连接，每加一跳多一次 JOIN；在图中就是「从 A 的邻居出发再走一步」，复杂度与「实际涉及的节点数」成正比，而非与全表大小成正比。这个「按边遍历」与「全表连接」的差别，是图数据库在关系密集场景胜出的根本。</span>

## 2 查询语言：Cypher 与图遍历

图数据库的查询语言以遍历为核心。Neo4j 的 **Cypher** 是最流行的一种，语法直观到接近自然语言。找「A 的好友中 25 岁以上的人」：

```cypher
MATCH (a:User {name: "A"})-[:FOLLOWS]->(b:User)
WHERE b.age > 25
RETURN b.name
```

拆解语法：

`(a:User {name: "A"})`：匹配一个带标签与属性的顶点，变量名 `a`。
`-[:FOLLOWS]->`：匹配一条有方向的边，类型 `FOLLOWS`。
`(b:User)`：边的另一端顶点，要求是用户。
`WHERE b.age > 25` 过滤，`RETURN b.name` 输出——整体就是在图里「走一步」。

多跳遍历只需延长路径模式：

```cypher
MATCH (a:User {name: "A"})-[:FOLLOWS]->(:User)-[:FOLLOWS]->(c:User)
RETURN DISTINCT c.name
```

这就是「二度好友」——一条路径模式，替代了 SQL 里的两次自连接。<span class="marginnote">Cypher 的 `MATCH` 路径模式本质上是在图上做<strong>模式匹配</strong>：声明「我要找什么样的子图」，引擎在图中高效地寻找匹配。可变长路径 `*1..3` 甚至能表达「走 1 到 3 跳」。这套「图模式即查询」的思想，与正则表达式之于字符串、SQL 之于表，是同一种「声明式」哲学。</span>

## 3 图分析算法：不只存储，还能计算

图数据库的价值不只在查询，还在**图上跑算法**。几个数据科学常用的图算法：

**最短路径**：社交网络中「你通过几个人能认识某人」，物流中「两点间最优路线」。
**中心性（centrality）**：谁是这个网络的枢纽？**度中心性**数邻居数，**介数中心性**看「有多少最短路径经过该点」——用于找意见领袖、关键中转节点。<span class="marginnote">介数中心性的直觉：想象所有节点对之间都在传消息，某个节点的「介数」就是它被当作中间人的次数。通信网络里介数高的节点一旦失效，网络就瘫痪——所以介数中心性常用于找「单点故障」与反欺诈里的「中转账户」。</span>
**社区发现**：把图分成联系紧密的簇——用于用户分群、相似商品簇。Louvain 算法是最常用实现。
**PageRank**：节点重要性排序，源自 Google 的网页排序，也可用于「谁是社交网络里最有影响力的人」。

**重点：图算法的通用思想是「信息沿边传播」**——无论是 PageRank 的投票迭代，还是标签传播的邻居多数表决，都是让每个节点的值逐步被邻居影响，直到收敛。这个「迭代传播」的思路，也是第四级《图神经网络》里消息传递机制的直接前身。

## 4 图数据库 vs 关系数据库 vs 图计算引擎

用一张表厘清「什么时候该用图」：

| 维度 | 关系数据库 | 图数据库 | 图计算引擎（如 Neo4j/Spark GraphX） |
| --- | --- | --- | --- |
| 数据模型 | 表 + 外键 | 顶点 + 边 | 顶点 + 边（批量） |
| 擅长 | 事务、报表、聚合 | 多跳关系查询 | 全图迭代算法 |
| 多跳查询 | 多次 JOIN，慢 | 原生遍历，快 | 批量计算，不适合交互查询 |
| 典型场景 | 订单、账务 | 社交、欺诈、推荐关系 | PageRank、社区发现 |
| 与数据科学的关系 | 数据源 | 关系型特征与查询 | 图特征计算 |

**辨析｜易错点：** 图数据库不是万能的。**如果你要的是「按列聚合统计」（本月各区域销售额），图数据库既慢又别扭**——那是仓库与 OLAP 的领地。图数据库的适用判据是「**查询的核心动作是沿着关系跳转**」：社交关系、权限路径、供应链溯源、反欺诈团伙识别。问一句「我的核心查询是『跳』还是『算』」，就能判断要不要图。

## 5 图数据科学：从图到特征

数据科学家用图数据库的典型姿势，是**把图分析的结果落成特征**：给每个用户算出「其社交圈的密度、它的 PageRank、所在社区的规模」，作为普通表格特征喂给下游模型（第26篇《推荐与用户行为》就是典型）。<span class="marginnote">「图特征」的价值在于它编码了「关系结构」：两个「好友数量相同」的用户，一个的朋友彼此也是好友（高聚类系数），另一个的朋友互不相识——聚类系数这一个特征就区分了这两种完全不同的社交角色。这类结构特征在表格里造不出来，只能从图里算。</span>

图特征之后，更近一步是让模型直接在图上学习——**图神经网络（GNN）** 把「沿边传播」变成了可学习的层，这是第四级《图神经网络》的主场；图数据库则为它提供高质量的图数据与子图采样。

## 6 图数据科学的工具生态

把「图上做数据科学」的工具铺开，你会发现它不是单点，而是一个生态：

- **图数据库**：Neo4j——最主流的属性图数据库，Cypher 查询 + 内置图算法（最短路径、中心性、社区发现、PageRank），适合交互式关系查询与关系特征提取。
- **图计算引擎**：Spark GraphX、GraphFrames——批处理全图算法，适合「对整张图跑 PageRank」这类批量计算（第19篇 Spark 的图扩展）。
- **图学习库**：PyTorch Geometric、DGL——图神经网络（GNN）的训练框架，负责「沿边传播」的可学习版本（第四级《图神经网络》）。
- **图可视化**：Gephi、vis.js——把图渲染成可交互的网络图，让「关系结构」被人眼看见。

**选型的简单判据**：

| 需求 | 工具 |
| --- | --- |
| 在线回答「A 与 B 几跳关系」 | 图数据库（Neo4j） |
| 离线算「全网 PageRank/社区」 | 图计算引擎（GraphX） |
| 训练「图上的预测模型」 | 图学习库（PyG/DGL） |
| 让人看懂网络结构 | 图可视化（Gephi） |

**辨析｜易错点：** 工具选型最常见的错是「**把图数据库当图计算引擎用**」——在 Neo4j 里跑全图 PageRank、期望秒级出结果。图数据库擅长「沿边的小范围遍历」，对全图迭代算法并不快；反之用 GraphX 做在线「好友的好友」查询也慢。**先想清楚「在线遍历」还是「离线全图」，再选工具**，与第4节的「跳 vs 算」判据是同一枚硬币。

**重点：图工具生态的共同语言是「点 + 边」。** 无论数据存哪、算法在哪跑，图的建模都是「顶点 + 边 + 属性」。先学会「把问题画成图」，再选工具——**建模正确比工具熟练更根本**。这张「图思维」的地图，也是通往第四级《图神经网络》的入口。

### 图查询与表查询：什么时候图更快

对「什么时候该用图数据库」再补一个直观的复杂度视角。多跳查询在两种模型下的成本：

- **表模型（关系数据库）**：查「A 的三度好友」要做 3 次自连接，每次连接的代价与「全表大小 × 参与行数」相关——**成本随「跳数」线性增加，且每跳都扫全表**。
- **图模型（图数据库）**：从 A 出发沿边遍历 3 跳，代价与「实际涉及的邻居数」相关——**成本随「该点的局部密度」增长，与全图大小基本无关**。

在「社交网络」这类**稠密、多跳、局部查询多**的场景，图模型快出几个数量级；而在「按列聚合、报表」场景，图模型毫无优势。

**一个实用的决策速查：**

- 查询是「**沿关系跳**」（好友链、路径、子图）→ 图数据库。
- 查询是「**沿列算**」（求和、分组、聚合）→ 关系库/仓库。
- 查询两者都有 → 混合：关系库存明细，图库存关系，按查询类型路由。

**重点：图数据库不是「更好的数据库」，而是「另一种形状的数据库」。** 它的快，来自「把关系做成索引、按局部遍历」；它的慢，来自「全表聚合不是它的设计目标」。**选型的第一问永远是「我的查询形状是什么」**——形状对了，性能与表达自然都对。

## 7 小结

- 图数据库以**属性图**建模：顶点、边、标签；**关系被存储为一等公民**。
- 查询语言 **Cypher** 以路径模式为核心，一条 `MATCH` 即可一步遍历，多跳关系远快于表模型 JOIN。
- 图分析算法：**最短路径、中心性、社区发现、PageRank**；共同思想是**信息沿边迭代传播**。
- 选型判据：核心查询是**「跳」**（沿关系遍历）就用图；是**「算」**（列聚合）就用仓库。
- 数据科学用法：把图算法结果**落成结构特征**，再喂给下游模型；更进一步是 GNN。
