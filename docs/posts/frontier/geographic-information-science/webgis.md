## 为什么从 WebGIS 开始

1990 年代之前，地图躺在 GIS 专家的电脑里。如今，任何人在浏览器里随手就能拖动地球——**WebGIS** 把地理信息从「专家工具」变成了「公共服务」。本专题《GIS 系统架构》讲了系统的骨架，这一篇讲它如何通过互联网被千万人使用。<span class="marginnote">WebGIS 是「分布式系统」思想在 GIS 的完整落地：服务器渲染地图、浏览器交互、标准接口通信、缓存加速。它与《计算机网络》《Web 开发》共享几乎全部底层技术，只是传输的内容带上了「空间」的语义。</span>

## 1 WebGIS 的架构：瘦客户端模式

WebGIS 的经典架构是**服务器—浏览器（B/S）**模式：

1. **服务器端**：空间数据库（PostGIS）存储数据，地图服务器（GeoServer）把数据渲染成可发送的格式，应用服务器执行业务逻辑。
2. **客户端**：浏览器接收地图并渲染，用户交互（拖拽、缩放、点选）通过请求-响应与服务器通信。
3. **中间协议**：客户端与服务器用标准接口对话——OGC 的 WMS、WFS、WMTS 就是这套「对话语法」。

**核心概念：WebGIS 的成败取决于「传输什么、传输多少」。** 一张完整地图可能几十 MB，直接发给浏览器会卡死。于是 WebGIS 发展出两大核心技术：**瓦片地图**（只传当前可视范围、当前缩放级的图块）与**矢量服务**（只传几何与属性、由浏览器自己画）。<span class="marginnote">这套「按需传输」与《数据库》的「索引 + 按需读页」、《分布式系统》的「缓存」异曲同工。Web 地图的每一次缩放，都在背后做一次「范围 → 瓦片集合 → 缓存命中」的检索——空间索引（R 树）与 HTTP 缓存在这里并肩作战。</span>

## 2 瓦片地图：把世界切成小方块

**瓦片地图（tile map）**把地球按**金字塔（pyramid）**组织：缩放级 $z$ 越高，细节越细，全球被切成 $2^z \times 2^z$ 张方块瓦片。拖动地图时，浏览器只请求「当前视口覆盖的几张瓦片」，其余不动——体验顺滑，服务器压力小。

**公式解析（Slippy Map 瓦片编号）：** 以 Google/OSM 采用的 **Web 墨卡托（Slippy Map）** 瓦片方案为例。给定经纬度 $(\lambda, \varphi)$ 与缩放级 $z$，瓦片列号 $x$ 与行号 $y$ 为：

$$
x = \left\lfloor \frac{\lambda + 180}{360} \cdot 2^z \right\rfloor, \qquad
y = \left\lfloor \left(1 - \frac{\ln\big[\tan(\varphi \cdot \pi/180) + \sec(\varphi \cdot \pi/180)\big]}{\pi}\right) \cdot 2^{z-1} \right\rfloor
$$

分三步拆解：

- **第一步，列号 $x$**：经度 $\lambda \in [-180, 180]$ 线性映射到 $[0, 2^z)$——加 180 归一化、乘 $2^z$、取整。**列号是经度的均匀切分**，与第1篇第4条墨卡托的 $x = R\lambda$ 一脉相承。
- **第二步，行号 $y$**：纬度的映射**不是线性**的——因为墨卡托在高纬度要拉伸（见 `k = \sec\varphi`），行号公式里那个 $\ln[\tan + \sec]$ 正是墨卡托的纵坐标函数，用它把「球面纬度」映射到「平面 y」，再均匀切分。**同一个公式，既是投影变换，又是瓦片编号。**
- **第三步，实际意义**：任意经纬度在任意缩放级都能算出唯一的 $(z,x,y)$，浏览器据此拼装瓦片 URL、按需拉取。**「世界如何被切成编号的小块」由这条公式一锤定音。**<span class="marginnote">这套方案叫 Slippy Map（源自它的「滑动」交互），几乎成了 Web 地图的事实标准：Leaflet、Mapbox 都遵循 $z/x/y$ 编号。瓦片金字塔 = 多尺度表达（第1篇第5条）的工程实现——每一级 $z$ 就是一套分辨率。</span>

## 3 OGC 网络服务：让地图可互操作

不同厂商的 GIS 要能互相对话，靠的是 **OGC（开放地理空间联盟）** 的网络服务标准：

| 服务 | 全称 | 返回内容 | 用途 |
| --- | --- | --- | --- |
| WMS | Web Map Service | 渲染好的图片（PNG/JPEG） | 把地图「画出来」给别人看 |
| WMTS | Web Map Tile Service | 预渲染的瓦片图片 | 高性能瓦片分发 |
| WFS | Web Feature Service | 矢量要素（GML/GeoJSON） | 让用户拿到**数据**本身 |
| WCS | Web Coverage Service | 栅格/场数据 | 拿原始栅格做分析 |

**辨析｜易错点：** **WMS 给「图」，WFS 给「数据」**——这层区别很关键。用 WMS 叠加分析不可行（你拿到的只是图片像素），要拿真实坐标与属性必须用 WFS。**「能在地图上看到」不等于「能拿数据」**——这两个能力对应不同的服务。<span class="marginnote">这套「图片服务 / 要素服务」的划分，与《Web 开发》里「渲染 HTML vs 返回 JSON」的分工同构：一个面向人眼，一个面向程序。SDI（空间数据基础设施）的互操作性，正是靠这些标准服务实现的（见《GIS 系统架构》）。</span>

## 4 矢量瓦片与轻量格式：把画图交给浏览器

传统瓦片是**预渲染图片**：服务器画好、浏览器贴图。**矢量瓦片（vector tiles）**换了一种思路：服务器只发**几何数据（MVT，Mapbox Vector Tile）**，浏览器用 WebGL 自己渲染——于是**样式（颜色、线宽）可以在客户端动态改，缩放平滑无锯齿**，数据量还小。

轻量交换格式方面，**GeoJSON** 是事实标准：用 JSON 表达点线面，浏览器原生解析，是 Web 前端与 GIS 之间最亲民的「通用语」。全球开放数据的代表作 **OpenStreetMap（OSM）**以 GeoJSON/矢量瓦片为骨，把「人人可编辑的地图」变成了现实。<span class="marginnote">矢量瓦片把《数据可视化》的「渲染在客户端做」推向极致：数据与表现彻底分离——同一份 MVT，换套样式就是换张主题图。这与「CSS 让结构与表现分离」是同一个架构哲学。</span>

## 5 WebGIS 的社会意义：共享、开放与实时

WebGIS 的深层影响不是技术而是**访问模式**的转变：

**开放数据**：OSM、政府公开数据让空间数据从「机构资产」变成「公共资源」。
**众包更新**：任何人可以报错、补充、编辑地图——数据的生产从「专业测绘」走向「社会共创」。
- **实时共享**：公交位置、灾害态势、疫情分布以流式推送给所有人，地图成为「活的仪表盘」。
- **移动化**：手机定位让每个人既是地图用户又是数据生产者——LBS（位置服务）重塑了出行、外卖、社交。<span class="marginnote">这与第4篇《地理信息的社会、组织与个体视角》直接相连：WebGIS 不只是技术架构，更是地理信息的「公共化」进程。它让「位置」成为互联网的第一公民——而这也带来了隐私、准确性与信息操纵的新问题。</span>

## 6 移动 GIS 与位置服务：地图进入口袋

WebGIS 的最后一公里是**移动端**。智能手机集成了定位（GNSS + 基站/Wi-Fi 辅助）、相机、陀螺仪与触屏，把地图从「浏览器里的页面」变成「随身携带的传感器平台」。

**位置服务（LBS，Location-Based Services）**基于一个简单的循环：**定位 → 匹配 → 服务 → 反馈**。用户点一下「附近的餐厅」，手机定位 → 地图服务器匹配到所在区域 → 返回周边 POI → 用户选择后评价反馈。外卖、打车、导航、社交打卡全是这个循环的变体。<span class="marginnote">LBS 把 WebGIS 从「看地图」升级为「围绕位置的服务」。它的两个技术底座是<strong>室内外无缝定位</strong>（GPS 在室内失效，靠 Wi-Fi 指纹、蓝牙信标补位）与<strong>实时推送</strong>（基于位置的触发式通知）。这也让「位置隐私」（见《地理信息的社会、组织与个体视角》）从学术议题变成每天发生在手机里的现实。</span>

移动 GIS 还带来两种新的数据形态：

- **众包轨迹**：每个开着导航的手机都是路况传感器——聚合轨迹反推实时路况，这是高德/Google 路况的本质。
- **现场采集（field collection）**：巡检员用 App 现场拍照、定位、填表，数据实时回传——**数据生产从「室内数字化」变成「现场录入」**，显著缩短了「现实 → 数据库」的时延。

**辨析｜易错点：** 移动数据的坐标质量参差：室内 GPS 漂移可达几十米、基站定位精度只有街区级。**用移动数据做精细空间分析前，先评估定位方式与精度**——「手机定位」不是单一精度，而是一个从米级到百米级的连续谱。

## 7 延伸阅读与自测

### 自测题

**1. WebGIS 的成败为什么取决于「传输什么、传输多少」？两大核心技术是什么？**
提示：整图传输会卡死浏览器；瓦片地图（只传可视范围图块）与矢量服务（只传几何由浏览器画）。

**2. Slippy Map 的行号公式里为什么有墨卡托纵坐标函数？**
提示：因为墨卡托在高纬度拉伸（k=secφ），纬度的瓦片切分必须用投影后的 y 均匀切分——同一公式既是投影又是编号。

**3. WMS 与 WFS 的本质区别是什么？「看到地图」等于「拿到数据」吗？**
提示：WMS 给渲染图片、WFS 给矢量数据本身；不等于——要真实坐标与属性必须用 WFS。

**4. 矢量瓦片相比图片瓦片有什么优势？**
提示：样式可客户端动态改、缩放平滑无锯齿、数据量小——数据与表现彻底分离。

**5. 为什么说移动 GIS 让「人人既是用户又是数据生产者」？**
提示：手机定位产生众包轨迹与现场采集数据，LBS 基于「定位→匹配→服务→反馈」循环持续产出。

### 关键术语快速检查

| 术语 | 一句话定义 |
| --- | --- |
| 瓦片地图 | 按金字塔把全球切成 2^z×2^z 张瓦片的组织方式 |
| WMS | Web 地图服务，返回渲染好的图片 |
| WFS | Web 要素服务，返回矢量数据本身 |
| 矢量瓦片 | 只传几何与属性、由浏览器渲染的瓦片 |

### 一句话总结

WebGIS 用「按需传输」把地图装进每个浏览器——瓦片管效率、标准管互操作、开放管共享，位置从此成为互联网的第一公民。

## 8 小结

- **WebGIS = 服务器 + 标准服务 + 浏览器客户端**，瘦客户端架构让地图走进任何浏览器。
- **瓦片金字塔**把世界切成 $z/x/y$
