## 为什么从消息交换标准讲起

上一章解决了「语义怎么定」（受控术语），这一章解决「消息怎么传」——**数据从 A 系统到 B 系统，以什么格式、什么结构打包**。医院里每天发生海量的系统间通信：检验结果从 LIS 传回 HIS、医嘱从 HIS 传到药房、住院事件从登记系统传到病案系统。**HL7（Health Level Seven，健康水平七级）** 就是医疗领域最著名的消息交换标准家族——它的名字取自 OSI 七层模型中「应用层（第七层）」，寓意「只约定应用层怎么沟通」。这一章剖析 HL7 v2 与 v3，下一章再看它的继任者 FHIR。<span class="marginnote">对主线：消息标准是「接口协议」的医学特化——像 HTTP 之于 Web，HL7 之于医院系统。理解「消息结构、字段语义、握手确认」，就理解了系统集成的基本功。</span>

## 1 为什么医院需要「消息」

医院系统是「异构的群岛」：HIS、LIS、PACS、药房系统往往来自不同厂商、用不同数据库、跑不同操作系统。要让它们协作，必须有一套「通用接口语言」——**消息（message）**。

**消息（message）**：一段结构化的数据包，表达「一个事件或一份数据」——比如「患者入院了」「检验结果出来了」「医嘱开出了」。系统间通过**发送/接收消息**来交换信息。

**HL7 的定位**：定义「消息长什么样、字段是什么含义、如何确认收到」——让任何两家遵循 HL7 的系统都能互发互读。它是医疗互操作历史最悠久、部署最广的标准家族。<span class="marginnote">HL7 组织成立于 1987 年，总部在美国；「Level Seven」指 OSI 模型的第七层（应用层）——HL7 不管传输层怎么走（TCP/IP、文件、消息队列都行），只规定「应用层消息的语义与结构」。这份「不管底层、只管语义」的定位，是它长盛不衰的原因。</span>

**消息与「一次事件」的关系**：消息不是「数据库的整库快照」，而是「**一次事件的通知**」——患者入院发一条 ADT、检验出结果发一条 ORU。接收方在自己的系统里「按消息更新本地数据」——**消息是「增量事件的载体」，而非「数据的全部」**。理解了这一点，就理解了为什么医疗集成是「事件驱动」的：每个系统保留自己的数据，靠消息保持「同步更新」。

## 2 HL7 v2：务实的分段消息

**HL7 v2**（1980 年代末发布）是医疗互操作的事实标准——它把一条消息拆成若干**段（segment）**，段内用竖线 `|` 分隔**字段（field）**，构成一个「扁平、可读、好解析」的文本消息。一条典型的 v2 消息长这样：

```
MSH|^~\&|LIS|HOSPITAL|HIS|HOSPITAL|202607140930||ORU^R01|202607140930001|P|2.3
PID|1||123456||张三^ZHANG SAN|19650101|M
OBX|1|NM|1558-6^Fasting glucose^LN||7.1|mmol/L|3.9-6.1|H|||F
```

这条消息在说：`MSH`（消息头）声明「从 LIS 发给 HIS、消息类型 ORU^R01（检验结果）、HL7 版本 2.3」；`PID`（患者信息）声明患者标识与人口学；`OBX`（观察结果）声明「血糖 7.1 mmol/L，超出正常范围」——**LIS 把化验结果用一段这样的消息推给 HIS**。<span class="marginnote">v2 的经典特征：<strong>竖线分隔、段即业务单元、消息类型约定</strong>。它不强迫统一建模，允许厂商在标准段外扩展（Z 段）——这份「灵活」让它极易落地，也埋下了「各自扩展、语义不一」的隐患。</span>

**怎么「读」一条 v2 消息**：解析 v2 依赖「**段名 + 字段位置**」的约定——看到 `OBX|1|NM|...`，就知道「这是第一条观察结果（OBX）、数据类型是数值（NM）」；看到第 5 个字段（`7.1`）就是数值、第 6 个字段（`mmol/L`）就是单位。**「位置即语义」** 是 v2 的读取规则——这也解释了为什么 v2 的字段顺序错了、接收方就会读错：它的语义藏在「约定好的位置」里，而不是「自描述的标签」里。

**常用的 v2 消息类型**：`ADT`（入院/出院/转科事件）、`ORU`（检验/观察结果）、`ORM`（医嘱请求）、`BAR`（账单）。医院里最常见的集成，就是「HIS 收 ADT、LIS 发 ORU」这条消息链。

**确认（acknowledgment）与可靠性**：消息不能「发了就算完」——接收方要回一个**确认（ACK）**：「收到且处理成功」或「收到但处理失败」。发送方据此决定重发或报警。这个「请求—确认」机制（类似 TCP 的 ACK）让「检验结果有没有传到 HIS」有据可查——**没有确认机制的消息系统，等于「把信扔进邮筒却不知道对方收到没有」**。<span class="marginnote">医疗消息的可靠性还有「事务性」的一面：一条 ADT「患者入院」如果丢了，后续所有关联数据都会错位——所以集成实践中常用「消息队列 + 失败重试 + 日志对账」来兜底。「消息可靠到达」是医疗集成的基础设施需求。</span>

## 3 v2 的成功与软肋

v2 为什么统治了医疗集成三十年，又为什么被诟病？

**成功之处**：**务实、易实现、兼容老系统**——厂商改造成本低，医生/医院立刻受益；竖线文本人类可读，排错容易。<span class="marginnote">v2 的现实地位：今天的医院里，v2 仍是「在役主力」——检验结果、挂号事件、医嘱传输大多还是 v2。它的「继续服役」本身说明了标准的「粘性」：改标准要动存量系统，成本极高。</span>

**「老而不死」的标准经济学**：为什么 v2 三十年还在？因为**互操作标准的成本在「存量」**——每家医院都有几十条基于 v2 的消息流在跑，升级意味着所有接口、所有厂商、所有测试要重来一遍。标准经济学告诉我们：**换标准的边际成本，远比新标准的理论优势更重**——所以 v2 与 FHIR 会长久并存，靠「桥接」过渡，而非「革命」替换。

**软肋所在**：**语义弱**——v2 没有强制的参考模型，同一种消息在不同厂商实现里字段含义可能不同；Z 段扩展让「扩展多了就各说各话」。它「能传数据，但传的数据含义未必一致」。

**重点：** v2 的成败是一体两面——**「好落地」与「弱语义」源于同一个设计选择**。理解 v2，就理解了「为什么互操作既有工程问题，更有语义问题」。

**集成引擎（integration engine）**：医院要管理几十条系统间消息流，于是有了专门的「消息中转站」——**集成引擎**。它负责「接收 A 系统的消息 → 按规则转换/映射 → 转发给 B 系统」，并把「谁传了、传成没成」记录下来。医院里「LIS 结果回 HIS、HIS 医嘱给药房」这些跨系统流转，大多由集成引擎统一调度——它是「医院消息的总调度室」。<span class="marginnote">集成引擎的常见形态：Mirth Connect（开源）、Rhapsody、Cloverleaf 等。它把「点对点接口」变成「中心化总线」——新增一个系统，只需接上总线，不必与每个老系统各拉一条线。「星型集成」比「网状集成」好维护得多。</span>

## 4 HL7 v3 与 RIM：一次「严谨」的实验

针对 v2 的「语义松散」，HL7 在 1990 年代启动了 v3——试图用**严格模型**根治语义问题：

**RIM（Reference Information Model，参考信息模型）**：v3 的核心——一个覆盖医疗全部业务对象的**统一信息模型**，用「类、属性、关系」定义一切（如「用药」是「Act（行为）」的一个子类）。<span class="marginnote">RIM 的雄心是「一个模型统一宇宙」：所有业务都建模成 Act/Entity/Role 三大类的组合。理论上，严格按 RIM 建模的系统间「语义天然一致」——这是 v3 对 v2「语义随缘」的正面回应。</span>

**「统一模型」的代价**：RIM 的问题在于「抽象层次太高」——「开医嘱」要表达成「行为（Act）由医生（Role）对患者（Entity）执行」的通用骨架，实际落地时每个具体场景都要再「雕出」专属约束，建模工作量惊人。**「表达一切」的模型，反而让「表达任何具体事」都变难**——这是 v3 留给后人的经典悖论，也是 FHIR「资源化、按场景建模」的直接原因。

**消息基于 RIM**：v3 消息不再是「扁平竖线文本」，而是**基于 RIM 的 XML 文档**——字段位置、取值由 RIM 类与约束决定，语义有严格出处。

**CDA（Clinical Document Architecture，临床文档架构）**：v3 家族里最成功的成员——用结构化 XML 表示**临床文档**（出院小结、转诊单），既保留人类可读文本，又带机器可读的语义标签，成为「文档级互操作」的标准。

**v3 的结局与教训**：v3 试图「一步到位」的严谨，换来了「建模复杂、实现困难、厂商抵触」——大规模部署远少于 v2。**它的遗产是深刻的：RIM 的建模思想沉淀进后续标准，而「重建模轻落地」的教训，直接催生了 FHIR 的「轻量化」哲学**（下一章展开）。<span class="marginnote">v3 是互操作史最著名的「理想主义实验」：模型无懈可击，落地寸步难行。「标准要有理想，更要有现实感」——这是 v3 用十年代价换来的最贵教训，也是 FHIR 诞生的直接背景。</span>

**CDA 的文档级互操作**：在「消息」之外，医疗还要共享「整份文档」——出院小结、转诊单、影像报告。**CDA（临床文档架构）** 规定这类文档的标准结构：XML 里既有人类可读的文本（医生直接看），又有机器可读的语义标签（系统能解析）。「跨院共享一份出院小结」正是 CDA 的典型场景——它让「文档」成为独立于「消息」的另一条互操作通道。<span class="marginnote">CDA 的成熟产物是「CDA 文档 + 文档注册」的组合：文档存起来、在区域注册表里登记，别的医院按需查询调阅——这套「文档级共享」机制是区域卫生信息化的常用组件（呼应第2篇区域平台）。</span>

## 5 核心对比表：v2 vs v3 vs 文档级标准

纯概念主题用核心对比表替代公式解析——把 HL7 家族的主要成员摆开：

| 标准 | 载体 | 建模 | 优点 | 缺点 | 地位 |
| --- | --- | --- | --- | --- | --- |
| HL7 v2 | 竖线分隔文本 | 无强模型 | 易实现、好落地 | 语义弱、扩展乱 | 在役主力 |
| HL7 v3 | XML（基于 RIM） | 严格统一模型 | 语义严谨 | 复杂难落地 | 部署有限 |
| CDA | XML 临床文档 | 基于 RIM | 文档级共享 | 文档粒度偏粗 | 文档互操作标准 |
| FHIR | JSON/XML 资源 | 模块化资源 | 现代、开发者友好 | 语义深度靠 profile | 未来方向 |

这张表的关键：**HL7 家族在「落地容易」与「语义严谨」之间摆荡**——v2 选了前者、v3 选了后者、FHIR 试图兼得。理解这条摆动曲线，就看懂了医疗互操作三十年的演化逻辑。<span class="marginnote">现实中各标准「长期共存」：v2 管存量消息、CDA 管文档共享、FHIR 管新建系统与生态——「标准之间要桥接」（如把 v2 消息转成 FHIR 资源）是集成工程师的日常。</span>

### 常见疑问

**问：消息交换和「调 API」是一回事吗？**
答：思路相似、时代不同。v2 是「推送式消息」——A 系统主动把消息推给 B（如 LIS 推结果给 HIS）；FHIR 是「请求式 API」——调用方按需向服务器取数据（如 App 查患者档案）。两者还共存，但新系统越来越偏 API——这正是下一章 FHIR 的主题。

**问：HL7 只在美国用吗？**
答：不是。HL7 是全球性的标准组织，v2 在世界各地医院广泛部署（中国医院系统集成也大量使用 HL7 v2 及类似的消息模式）；只是不同国家会结合本地术语与格式做「国家化适配」（呼应上一章中文术语的多码并存）。

**问：消息丢了、发重复了怎么办？**
答：这正是消息系统的工程问题——靠「**消息编号 + 幂等处理 + 对账**」解决：每条消息带唯一编号，接收方按编号识别「重复」并丢弃；集成引擎记录收发日志，定期「对账」发现遗漏重发。**医疗集成把「网络不可靠」当作默认假设来设计**，而不是期待网络永不丢包。

**关联阅读**：消息里的字段语义靠受控术语承载（见《医学受控术语》）；消息的现代替代见《互操作框架与 FHIR 标准》；文档级共享见《卫生信息交换（HIE）与数据共享网络》；消息交换的安全见《健康信息安全、隐私与 HIPAA》。

## 6 小结

- **消息**是系统间通信的「数据包」：医院异构系统靠消息协作，HL7 是其中最著名的标准家族。
- **HL7 v2**：竖线分隔的分段消息——**务实、易落地、在役主力**，但语义弱、Z 段易乱。
- 常用消息类型：**ADT（出入院）、ORU（结果）、ORM（医嘱）**——检验回传、事件通知都是消息。
- **HL7 v3 / RIM**：严格统一模型——**语义严谨但复杂难落地**，CDA 是其最成功的成员。
- 教训：**「标准要有理想，更要有现实感」**——v3 的失败直接催生了 FHIR 的轻量化哲学。
- 可靠性机制：**消息确认（ACK）+ 集成引擎 + 失败重试**——「发了不算数，收到确认才算」。
- **CDA** 是文档级互操作的桥梁：人类可读 + 机器可解析的「双面文档」。
- 换标准的成本在「存量」：**v2 与 FHIR 会长期并存，靠「桥接」过渡而非「革命」替换**。
- 「表达一切」的统一模型反而让「表达任何具体事」变难——v3 留给后人的经典悖论。
- 消息是「增量事件的载体」：**每个系统保留本地数据，靠消息保持同步**——医疗集成是事件驱动的。
- HL7 家族的历史是一部「摆荡史」：**在「落地容易」与「语义严谨」之间找平衡**——这正是下一章 FHIR 的登场背景。
- 读 HL7 的钥匙：**「位置即语义」（v2）、「模型即语义」（v3）**——两代对「语义从哪来」给出了不同答案。

在下一节，我们将顺着这条演化线，看那个「试图兼得 v2 之快与 v3 之稳」的新标准——**互操作框架与 FHIR 标准**。
