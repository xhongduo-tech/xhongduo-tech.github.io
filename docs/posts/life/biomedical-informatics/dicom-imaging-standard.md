## 为什么从 DICOM 讲起

上一章的 PACS 是「影像的系统」，这一章深挖影像的「底层语言」——**DICOM**。CT、MRI、DR、超声、内镜、病理切片……不同厂商的影像设备输出的图像格式五花八门；如果每家医院的设备只认自家格式，影像就永远无法共享、无法归档、无法被 AI 分析。**DICOM（Digital Imaging and Communications in Medicine，医学数字影像与通信）** 就是全球医学影像的「世界语」——它规定了「一张医学图像在计算机里长什么样、怎么传输、怎么附带患者与检查信息」。它是 PACS 运转的基石，也是第4篇影像 AI 的数据前提。<span class="marginnote">对主线：DICOM 是「医学图像的标准格式」——像 JPEG 之于照片、DICOM 之于医学影像。理解「一幅图不只是像素，还带着一串元数据」，是理解影像数据与影像 AI 的第一步。</span>

## 1 一幅「DICOM 图像」里装着什么

一张 DICOM 文件，远不止「一张图」——它是「**像素 + 元数据**」的复合体：

**像素数据（Pixel Data）**：图像本体——CT 的每个像素是一个「CT 值」（反映组织密度，单位 HU）、MRI 每个像素是信号强度。CT 图像的像素通常 12–16 位深，所以它「含的信息量」远超普通照片的 8 位 JPEG。

**CT 值（Hounsfield 单位）与诊断**：CT 的像素不是「亮度」而是「密度」——水的 CT 值是 0 HU、空气约 -1000 HU、骨骼可达 +1000 HU 以上。诊断时医生用「窗宽窗位」把感兴趣的范围映射成可分辨的灰度（看肺用肺窗、看骨用骨窗）。**DICOM 保住了这份「密度的真值」**，机器才能在后处理与 AI 里做定量分析——这是它与「照片格式」最本质的区别。

**元数据（Metadata）**：附着在图像上的「画像」——患者姓名/ID、检查日期、设备类型、扫描参数（层厚、管电压）、体位、序列号、医院信息。**DICOM 把「图像」和「它是谁的、怎么拍的」绑在一起**。<span class="marginnote">「图 + 元数据」的一体化是 DICOM 的核心设计：拿到一张 DICOM 图，就同时知道「这位患者、这份检查、这个参数」——不必另建一张表来对应。「病历头 + 图像体」合在一个文件里，是它与普通图片格式的本质区别。</span>

**一个 DICOM 文件的「解剖」**：DICOM 用**数据元素（Data Element）** 组织信息——每个元素有一个标签（如 `(0010,0010)` 表示患者姓名、`(0028,0010)` 表示图像行数）和值。整份文件就是「一串带标签的数据元素 + 末尾的像素数据」。**「标签即语义」**——机器靠标签读懂「这个字段是患者的什么信息」。

## 2 DICOM 的体系：对象、服务与唯一标识

DICOM 不只是一种文件格式，而是一整套「对象 + 服务」的协议体系：

**信息对象（IOD, Information Object Definition）**：定义「一类影像对象长什么样」——CT 图像对象、MR 图像对象、放疗计划对象……每种对象规定「必须有哪些元素、可选哪些元素」。<span class="marginnote">IOD 是 DICOM 的「对象模板」：规定了「一份 CT 检查记录应包含哪些数据元素」。医生在 PACS 里看到的「一份检查」，在 DICOM 里是「由多个 IOD 实例组成」的——图像、报告、放疗计划各自是独立对象。</span>

**服务类（Service Class）**：定义「对对象能做什么操作」——**存储（Store）**（把图像存进 PACS）、**查询/检索（Query/Retrieve）**（按患者/检查条件查询并取回图像）、**打印（Print）**、**工作列表（Modality Worklist）**（设备从 RIS 拉取「今天要检查的患者列表」）。

**唯一标识符（UID, Unique Identifier）**：每个对象、每个实例都有全局唯一的 UID——保证「全世界不会有两份图像撞号」。跨院共享时，靠 UID 追踪「同一份检查」。

**服务对象对（SOP Class）**：IOD + 服务类的组合，定义一个「完整的 DICOM 交互」——如「CT 图像的存储（SOP）」=「CT IOD + Store 服务」。

**一段 DICOM 的「出生史」**：DICOM 的前身是 1983 年成立的 ACR-NEMA 委员会（美国放射学会 + 美国电器制造商协会）制定的影像格式标准。当时 CT/MRI 刚普及，各厂商格式互不兼容，「跨厂商看片」是天方夜谭。DICOM 标准于 1993 年发布 3.0 版并沿用至今——**「三十多年一版没换过主版本」，本身就是它生命力的证明**：它设计的「对象 + 服务 + 标签」架构，撑过了从胶片、光盘到云端的所有技术变迁。

## 3 核心对比表：DICOM 与 HL7 的分工

纯概念主题用核心对比表替代公式解析——把影像与消息的两套标准摆开：

| 维度 | DICOM | HL7 |
| --- | --- | --- |
| 管什么 | 影像对象与传输 | 临床消息与流程 |
| 载体 | 图像 + 元数据 | 竖线消息/XML |
| 典型交互 | Store、Query/Retrieve | ADT、ORU、ORM |
| 场景 | 设备→PACS、PACS 间共享 | HIS↔LIS、HIS↔药房 |
| 并存的结合点 | RIS 用 HL7 收检查单、DICOM 收图像 | — |

这张表的关键：**影像科同时用两套标准**——HL7 管「流程消息」（登记、报告），DICOM 管「图像本身」（存储、检索）。「RIS 用 HL7 知道该做谁、PACS 用 DICOM 收图像」——两套标准各管一层，构成影像信息化的完整协议栈。<span class="marginnote">这提醒我们：医疗互操作不是「一个标准通吃」，而是「多个标准分工协作」——HL7/FHIR 管临床数据与流程、DICOM 管影像对象、术语标准管语义。理解「谁管哪一层」，比背标准名称更有用。</span>

## 4 DICOM 与 PACS 的日常协作

DICOM 在 PACS 的每个环节都在出场：

**采集**：CT 设备按 DICOM 标准输出图像，采集工作站用 **DICOM Store** 接收。

**归档**：PACS 按 DICOM 格式存储图像（含元数据），用 UID 索引。

**调阅**：医生工作站用 **DICOM Query/Retrieve** 按「患者/检查」条件查询并取回图像——这就是上一章「一键调阅」背后的协议。

**工作列表**：设备启动时从 RIS 拉取 DICOM Worklist，得到「今天 9:00 张三做胸部 CT」——避免重复录入患者信息。<span class="marginnote">Worklist 是个「省事」设计：技师不用在设备上重新敲患者信息，设备自动从 RIS 拿到「检查申请列表」，技师勾选即开始检查——「流程消息（HL7/RIS）与图像服务（DICOM/PACS）」在这里无缝衔接。</span>

**打印与胶片**：即使数字化时代，部分场景仍要胶片——DICOM Print 服务让「电子图像 → 胶片打印」标准化。

**多帧与动态影像**：DICOM 不只支持「单张静态图」——**多帧图像（Multi-frame）** 可承载 CT 的数百层「序列」、超声的连续动态视频、甚至心脏 CTA 的电影回放。一份「多帧 DICOM」就是一个「可播放、可逐层翻阅」的影像对象——这让 DICOM 从「照片」扩展为「视频/体数据」的统一容器。

## 5 DICOM 的互操作挑战

DICOM 让「机器能互相读」，但「读出来对不对」还有难题：

**厂商实现的「方言」**：DICOM 标准给了选项空间，不同厂商实现不同——「私有元素」（厂商自定义标签）大量存在，跨厂商调阅时可能「读得到图像、读不全语义」。**标准之外还有方言，是 DICOM 互操作的第一现实**。<span class="marginnote">「DICOM 一致性声明（Conformance Statement）」是厂商必须提供的「说明书」：声明「支持哪些服务、哪些 SOP、哪些私有元素」。集成工程师靠读一致性声明判断「两家设备能不能配起来」——它是 DICOM 互操作的「接口文档」。</span>

**影像去标识化（de-identification）**：共享/科研前要抹掉 DICOM 元数据里的患者标识（姓名、ID、出生日期）——DICOM 定义了「去标识化」的标准方法，但仍要小心「图像里嵌入的信息」（如刻在图像上的名字）会泄露。这与第4篇临床 NLP 的去标识化呼应。

**DICOM 灰阶显示函数（GSDF）**：前面 PACS 章节提到「阅片显示器要校准」——校准的标准正是 DICOM 的 **GSDF（灰阶标准显示函数）**：它定义「显示器灰度值 → 感知亮度」的标准曲线，保证「同一张 CT 在任何校准过的显示器上呈现同样的灰度观感」。**「图像数据统一 + 显示标准统一」双管齐下，才是完整的影像一致性**。

**版本与扩展**：DICOM 持续演进（如 DICOMweb，用 REST/JSON 传输影像，让 Web 与云端能用它）——新协议与老设备并存，过渡靠「桥接」。

## 6 从 DICOM 到影像 AI

DICOM 是影像 AI 的「数据入口」：AI 模型读的「那张 CT」，通常是 DICOM 解析出来的像素 + 元数据（扫描参数、序列）。影像 AI 的价值高度依赖「DICOM 数据是否规范」——扫描参数不一致、元数据缺失，模型的输入就「脏」。<span class="marginnote">影像 AI 的现实瓶颈之一正是「数据异构」：不同设备、不同序列、不同参数扫出的图，「长得一样、内涵不同」——模型要鲁棒，就要在大规模、多中心的规范 DICOM 数据上训练与验证。DICOM 的规范程度，直接决定影像 AI 的天花板（呼应第4篇医疗数据分析）。</span>

**重点：** DICOM 不是「过时的格式」，而是「仍在进化的基础设施」——从胶片时代到云端时代，它一直是「让医学图像在全世界流动」的底层语言。

### 常见疑问

**问：DICOM 图像能直接用普通看图软件打开吗？**
答：多数不行——因为 DICOM 是「带元数据 + 深位深像素」的专有结构，普通看图软件只能显示成「黑乎乎或异常」的图。要正确显示，需要支持 DICOM 的阅片软件（PACS 工作站、DICOM 浏览器）做「窗宽窗位」映射（把 12–16 位的像素值映射到屏幕可显示的 8 位灰度）。**「能打开 DICOM」本身就是一项软件能力**。

**问：手机上看影像（移动阅片）是怎么办到的？**
答：靠 **DICOMweb**——把 DICOM 图像通过 REST/JSON 转成 Web 可用的格式（JPEG 2000 等），浏览器/App 直接拉取。它让「应急会诊在手机上打开 CT」成为可能，也让云 PACS、跨院远程阅片有了标准通道——这是 DICOM 在 Web 时代的自我进化。

**问：为什么说「DICOM 数据干净，AI 才干净」？**
答：因为影像 AI 的输入是「像素 + 元数据」——扫描参数（层厚、重建算法）不同，同一器官在图像里的「长相」就不同。元数据残缺或参数混乱的数据，会让模型学到「设备差异」而非「病灶差异」。「数据规范 + 多中心」是影像 AI 验证的基本功，也是第4篇医疗数据质量的影像侧体现。

## 7 小结

- **DICOM 文件 = 像素 + 元数据**：图 + 「它是谁的、怎么拍的」绑在一起，靠「标签即语义」组织。
- 体系三件套：**信息对象（IOD）、服务类（Store/Query/Retrieve）、唯一标识（UID）**。
- 与 HL7 分工：**HL7 管流程消息、DICOM 管影像对象**——影像科两套标准并行。
- 在 PACS 的日常：**采集、归档、调阅、工作列表、打印**处处是 DICOM。
- 互操作三挑战：**厂商方言、去标识化、版本演进（DICOMweb）**。
- DICOM 是影像 AI 的数据入口：**数据规范程度决定 AI 的天花板**。
- DICOM 3.0 自 1993 年沿用至今——**「对象 + 服务 + 标签」的架构撑过了从胶片到云端**。
- 移动阅片靠 **DICOMweb**（REST/JSON 化）：DICOM 在 Web 时代的自我进化。
- 多帧 DICOM 承载序列与动态影像：**DICOM 从「照片」扩展为「视频/体数据」的容器**。
