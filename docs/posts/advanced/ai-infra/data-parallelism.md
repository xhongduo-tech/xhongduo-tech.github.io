## 为什么从数据并行开始

第二篇我们把 AllReduce 的每一笔账都算清楚了：Ring 算法、带宽最优性、NCCL 的通道与协议。但一个关键问题始终悬而未决——**这些通信原语到底被谁调用、多久调用一次、代价有多大**。数据并行（Data Parallelism，DP）就是那个答案的第一页：它是所有并行策略里最简单、也最普遍的一种，几乎所有大模型训练的第一站都是它。

DP 的思想一句话就能说清：**把训练数据切成 N 份，让 N 张卡各自持有一份完整的模型副本，算完本地梯度后再把所有梯度同步平均**。你不需要理解复杂的切分规则，只需要会数一张卡能装下多大的模型。但正因为它「简单」，它把全部成本都压在了那个每步都要执行的梯度同步上——这正是阿姆达尔的定律登场的地方：**只要同步占用的时间不是零，加速比就永远追不上卡的数量**。<span class="marginnote">这一课与第三级《分布式系统》的「单写多读副本」「一致性协议」遥相呼应：数据并行本质上是<strong>每步做一次全量同步的复制式计算</strong>。同步开销、失效模型、扩展性曲线，这些分布式系统的老话题，在 GPU 集群上换了个名字重新上演。</span>

## 1 数据并行的思想：一份模型，N 份数据

把训练循环拆开看。单卡训练的一步是这样的：取一个 batch，前向算损失，反向算梯度，用优化器更新参数。数据并行把这一套复制到 $P$ 张卡上，只改一个地方——**每张卡只吃整个 batch 的 $1/P$**。

**数据并行（data parallelism，DP）**：让 $P$ 个 worker 各自持有一份完整的模型副本与优化器状态，把全局 batch 均分为 $P$ 个分片 $B_1, B_2, \dots, B_P$，每个 worker 在 $B_i$ 上独立计算局部梯度，然后通过集合通信把 $P$ 份梯度同步为平均值，再各自用这个平均梯度更新自己的参数副本。

为什么这样做是正确的？因为**求梯度的算子对数据是线性的**：把损失函数对一个小 batch 求梯度，再对 $P$ 个小 batch 的平均梯度求和取平均，恰好等于在「这些小 batch 的并集」上求梯度。我们后面会在公式解析里严格推一遍。先记住直觉：**平均梯度 ≈ 在全部数据上的梯度，等价于把全局 batch 一次算完**——只是算力被拆到了 $P$ 张卡上。<span class="marginnote">这里有一个容易被忽略的前提：<strong>全局 batch 必须是各分片的并集，且每个样本恰好属于一个分片</strong>。若两份数据重叠，平均梯度就悄悄变成了「带权梯度」，训练轨迹会偏离原计划——这也是数据预处理里去重（第八篇）如此重要的原因之一。</span>

实现上还有一条重要分叉：同步（synchronous）与异步（asynchronous）。**同步数据并行**：所有 worker 算完梯度后互相等待，同步达成平均再一起更新——每步的模型状态完全一致，等价于一个更大的单机训练。**异步数据并行**：worker 不等别人，算完就更新——吞吐高，但 worker 之间看到的是不同版本的参数，梯度可能过期，收敛轨迹会偏移。工业级大模型训练几乎清一色选同步，异步更多出现在推荐系统这类稀疏场景。

## 2 梯度同步：从参数服务器到 AllReduce

「把 $P$ 份梯度平均并传回所有人」这个操作，历史上先后有两条实现路线。

**参数服务器（Parameter Server，PS）**：一组专门的服务器节点持有参数的权威副本。每个 worker 把本地梯度「推」（push）给服务器，服务器聚合后把新参数「拉」（pull）回给 worker。这套架构天然支持异步、天然适配稀疏模型——推荐系统的 embedding 只有一部分参数活跃，每次只同步那部分即可。<span class="marginnote">PS 是 2010 年代大规模机器学习的主流（DistBelief、Distributed Paddle 等），但它在稠密大模型上有个死穴：<strong>服务器是通信汇聚点，会变成瓶颈</strong>；而且「推梯度 + 拉参数」每步要传两趟全量数据。</span>

**AllReduce 路线**：不设服务器，$P$ 个 worker 直接用集合通信把 $P$ 份梯度归约为一份平均值，分发给所有人——这正是第二篇 Ring AllReduce 的用武之地。每步通信量约 $2(P{-}1)/P \cdot M$（$M$ 为模型字节数），全部流量均匀摊到所有节点上，没有单点瓶颈。Horovod、PyTorch DDP、Megatron 的 DP 组，底层都是它。

对比一下两种路线的每步账单（模型大小 $M$ 字节，$P$ 个 worker）：

| 架构 | 每 worker 每步通信量 | 同步性 | 瓶颈 | 适用场景 |
| --- | --- | --- | --- | --- |
| 参数服务器 | 推梯度 $M$ + 拉参数 $M$ = $2M$ | 常为异步 | 服务器带宽与 CPU | 稀疏模型、推荐系统 |
| AllReduce（Ring） | $2(P{-}1)/P \cdot M \approx 2M$ | 同步 | 无单点，受网络总带宽限制 | 稠密模型、LLM 训练 |

两边的通信量同量级，差别在**拓扑**与**同步语义**。AllReduce 把流量打散到全网，而 PS 把所有流量灌向服务器。大模型训练选 AllReduce，不是因为它更省流量，而是因为它更不容易被一个点卡死。

## 3 公式解析：同步 SGD 的梯度平均

把同步数据并行的一步写成数学，只有一个式子：

$$
\theta_{t+1} = \theta_t - \eta \cdot \frac{1}{P} \sum_{i=1}^{P} g_i(\theta_t;\, B_i), \qquad g_i(\theta_t; B_i) = \frac{1}{|B_i|} \sum_{x \in B_i} \nabla_\theta \ell(x; \theta_t)
$$

对它做三步拆解：

- **第一步，看 $g_i$ 是什么**：$g_i$ 是第 $i$ 个 worker 在分片 $B_i$ 上算出的局部梯度——它就是普通的单卡梯度，只是数据少到原来的 $1/P$。$|B_i| = B/P$，所以局部梯度是用 $B/P$ 个样本平均出来的。
- **第二步，看 $\frac{1}{P}\sum_i g_i$ 是什么**：把 $P$ 个局部梯度求平均。因为梯度算子对「损失求和再求梯度」是线性的，所以
  $$
  \frac{1}{P}\sum_{i=1}^{P} g_i = \nabla_\theta \left( \frac{1}{P}\sum_{i=1}^{P} \frac{1}{|B_i|} \sum_{x \in B_i} \ell(x;\theta_t) \right) = \nabla_\theta \mathcal{L}_{\text{batch}}(\theta_t)
  $$
  右边正是「把 $P$ 个分片拼成全局 batch 后」的梯度。**平均梯度就是全局梯度**，一个字节都不差——这是数据并行正确性的数学根基。
- **第三步，看更新**：$\theta_{t+1} = \theta_t - \eta \cdot \nabla_\theta \mathcal{L}_{\text{batch}}(\theta_t)$，和单卡 SGD 一模一样，只是梯度来自 $P$ 张卡。**数据并行没有改变优化算法，只改变了梯度的计算方式**——这正是它能与任何优化器、任何网络结构无缝组合的原因。

**重点：数据并行把「有效 batch size」放大了 $P$ 倍。** 全局 batch 从 $B$ 变成 $P \cdot B$，而学习率 $\eta$ 通常需要随 batch 放大而调整（线性缩放法则）——所以大模型训练普遍要配 warmup 与学习率调度，这是 DP 带来的第一个隐藏成本。

## 4 开销分析：每个 step 都要 AllReduce

数据并行最容易被低估的一点是同步的**频率**。很多人以为「训练结束同步一次」，实际上**每一个优化器 step 都要做一次全量梯度 AllReduce**。训练一次 7B 模型、跑一百万步，就要做一百万次 14 GB 级的全量同步。

设模型参数量为 $N_p$、以 BF16 存梯度（每参数 2 字节），则每个 step 的通信量约为：

$$
V_{\text{comm}} \approx \frac{2(P-1)}{P} \cdot 2 N_p \ \text{字节}
$$

代入 7B 模型：$N_p = 7\times 10^9$，梯度 $= 14$ GB，一次 AllReduce 每节点大约搬 $28$ GB。若走 NVLink（约 25 GB/s 单链路），通信时间 $\approx 1.1$ s；若走单根 400 Gbps 网卡（50 GB/s），也要约 0.56 s。<span class="marginnote">对比一下计算时间：一张 A100 约 312 TFLOPS（BF16），7B 模型、全局 batch 4096、每卡 32 个样本，一个 step 的 FLOPs 约 6·N_p·B ≈ 1.7×10^14，摊到每卡约 2×10^12 FLOPs，算力时间仅毫秒级。<strong>通信时间远大于计算时间——这就是「通信墙」</strong>，也是训练框架要不惜代价把通信与反向计算重叠的原因。</span>

用公式量化「加卡能赚多少」。设单卡一步耗时 $T_1 = T_{\text{calc}}$，$P$ 卡理想加速比是 $P$，实际加速比被通信拖累：

$$
E(P) = \frac{T_1}{P \cdot T_P} = \frac{1}{1 + T_{\text{comm}}/T_{\text{calc}}}
$$

$T_{\text{comm}}/T_{\text{calc}}$ 越大，扩展效率 $E$ 越低。这个比值大体正比于 **模型大小 /（单卡 batch × 单卡算力）**：模型越大、每卡分的 batch 越小，通信占比越高。**大模型 + 小 batch 是数据并行的天然死穴**——这直接引出了后面张量并行与流水线并行的动机：不是 DP 不够好，而是模型大到单卡连一份副本都装不下、或通信占比高到加卡无益时，必须换玩法。

## 5 压缩与重叠：让同步更便宜

既然通信躲不掉，工程上就有三条路降低它的实际代价。

- **通信计算重叠（overlap）**：不等整轮反向算完再同步，而是把梯度切成多个 bucket，**每个 bucket 一算出来就立刻 AllReduce**，与剩余的反向计算并行。DDP 默认就干这件事——第二篇《通信计算重叠》分析过它的机制，这里只需记住：重叠能把通信「藏」进计算时间，让 $T_{\text{comm}}$ 几乎不额外增加。
- **梯度累积（gradient accumulation）**：每张卡连续算 $k$ 个 mini-batch，累加梯度后再同步一次。等效于把每步 batch 放大 $k$ 倍、同步频率降为 $1/k$，直接抬高 $T_{\text{calc}}/T_{\text{comm}}$。代价是显存中要多存一份梯度累加器，且全局 batch 变得很大——又一个必须配学习率调度的原因。
- **梯度压缩（gradient compression）**：量化（FP32→FP16/FP8）、Top-$k$ 稀疏化（只传最大的 $k$ 个元素）。对稠密 Transformer，Top-$k$ 会破坏收敛，收益有限；真正吃这口红利的是稀疏的推荐系统 embedding。**压缩的通用原则是「先压误差有界的部分，再谈省带宽」**——把通信量当账算，但不能把收敛性当赌注。

```python
# 数据并行训练循环（伪代码，示意 DDP 的语义）
for step in range(num_steps):
    x, y = next_loader()                 # 本 worker 拿到的分片（全局 batch 的 1/P）
    loss = model(x, y).mean()            # 前向 + 损失
    loss.backward()                      # 反向：每算出一个梯度 bucket 就排队 AllReduce
    optimizer.step()                     # 用「全 P 份的平均梯度」更新本地副本
    optimizer.zero_grad()
```

这三条路并不互斥：DDP 同时做「分桶重叠」与「梯度累积」，分布式训练框架则在编译层再叠一层「通信调度」。它们的目标都一样——**让 $T_{\text{comm}}$ 从「每步的显性开销」变成「被计算藏住的影子开销」**。

## 6 辨析｜易错点

- **「数据并行能增加模型容量」**——错。DP 复制模型，不切分模型；**模型必须完整装进单卡显存**，否则 DP 无法启动。单卡装不下、需要切分模型时，要转向张量并行 / 流水线并行 / ZeRO。
- **「AllReduce 只在训练结束后同步一次」**——错。**每个优化器 step 都要做一次全量梯度 AllReduce**，训练百万步就是百万次全量同步。
- **「平均梯度 = 平均参数」**——差很远。DP 是「同一份 $\theta$ 下各算各的梯度、再平均梯度、再更新」；「平均参数」是另一类操作（联邦学习、模型融合），若各 worker 已各自更新多步，平均参数会破坏训练轨迹。二者不可混用。
- **「异步一定比同步快」**——不一定。异步去掉了等待，但引入了**梯度过期**：worker 用的是旧参数算的梯度，可能让损失震荡甚至发散。稠密大模型训练宁可等，也不赌过期梯度。
- **「PS 一定比 AllReduce 慢」**——看场景。稀疏 embedding 训练里 PS 的异步 + 稀疏同步反而占优；稠密 LLM 训练里 PS 的服务器汇聚点才是瓶颈。选型要看**稀疏度**，不是看名字。
- **「卡越多一定越快」**——被阿姆达尔定律否决。当 $T_{\text{comm}}/T_{\text{calc}}$ 显著时，扩展效率 $E(P) = 1/(1 + T_{\text{comm}}/T_{\text{calc}})$ 随 $P$ 增大而下降，加卡收益递减甚至为负。**扩展性是要算的，不是许愿来的**。

## 7 小结

- **数据并行**：$P$ 个 worker 各持一份完整模型副本，均分 batch，同步平均梯度后各自更新。
- **正确性根基**：梯度算子的线性性——$\frac{1}{P}\sum_i g_i$ 精确等于全局 batch 的梯度，DP 不改变优化算法，只改变梯度的生产方式。
- **实现两路线**：参数服务器（异步、稀疏友好、有汇聚瓶颈）vs AllReduce（同步、稠密友好、无单点）——大模型训练选后者。
- **每步都同步**：7B 模型每步 AllReduce 约 28 GB/节点，通信时间常超计算时间，形成「通信墙」；扩展效率 $E = 1/(1 + T_{\text{comm}}/T_{\text{calc}})$。
- **降本三招**：分桶重叠（藏通信进计算）、梯度累积（降同步频率）、梯度压缩（省带宽，但稠密模型谨慎）。
- **边界**：DP 不解决「单卡装不下」；模型大到放不下一份副本时，DP 失效——正是下一篇张量并行登场的理由。

在下一节，我们将从「复制模型」转向「切分模型」：**张量并行**——把矩阵乘按行、按列切开，让多个 GPU 共同扛住一个装不下的层。
