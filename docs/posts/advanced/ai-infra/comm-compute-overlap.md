## 为什么从 overlap 开始

前三节我们认识了通信的「路」（RDMA、InfiniBand、RoCE v2），但通信再快，它也**占用时间**。在数据并行训练里，每一步都要做一次全局梯度 AllReduce——一个 7B 模型的梯度就有几百 MB，即便走 400 Gb/s 的 NDR 网卡，也要传几毫秒。而 GPU 的求导计算是另一段可观的毫秒级时间。**如果这两段时间是「先算完、再通信、再算」，那么每一步的有效吞吐就要打对折；如果能边算边传，通信的时间就被「藏」进计算里，几乎是免费的。** 这个「把通信藏进计算」的技术，就是**通信计算重叠（communication-computation overlap）**。它是分布式训练性能优化里性价比最高的一招，也是 PyTorch DDP、Megatron、DeepSpeed 等框架共同的核心机制。<span class="marginnote">一个直觉：AllReduce 不是「开始-阻塞-结束」的黑盒，而是一串可以按块切分的传输。只要把梯度切成很多块，第一块算完就能先传，后面边算边传——像工厂流水线，而不是「所有人干完活才一起搬货」。</span>

## 1 通信为什么拖慢训练：先算后传的串行时间

在没有任何重叠的朴素实现里，一步训练的墙钟时间是「计算」与「通信」的简单相加：<span class="marginnote">「通信占比」在 GPU 上可以用 `nsys` 直接读出来：把 AllReduce 相关 kernel 的总时长除以一步总时长，就是 $T_{\text{comm}}/(T_{\text{comp}}+T_{\text{comm}})$。</span>

$$T_{\text{serial}} = T_{\text{comp}} + T_{\text{comm}}$$

- $T_{\text{comp}}$：一个 iteration 的前向 + 反向计算时间；
- $T_{\text{comm}}$：梯度 AllReduce 等通信时间。

若 $T_{\text{comm}}$ 占 $T_{\text{serial}}$ 的 30%，即使计算部分再优化，**墙钟时间最多也只能省 70%**——通信像一块石头卡在流水线正中间。**数据并行扩到几百张卡时，通信占比随规模上升**：因为每个 rank 的 $T_{\text{comp}}$ 随数据切分而缩小，而 AllReduce 的数据量（完整梯度）不随数据并行缩小（除非用 ZeRO 之类做梯度切分）。这就是为什么「通信重叠」在越大规模下越关键。

**代入一个具体数字**。设一个 10B 参数的模型，梯度全量约 40 GB（BF16），单卡一次反向耗时 $T_{\text{comp}} = 100$ ms。跨 512 卡用 ring AllReduce，通信时间约 $T_{\text{comm}} = 2 \times \frac{P-1}{P} \times \frac{40\ \text{GB}}{400\ \text{Gb/s}} \approx 1.6$ s——注意这里通信已远超计算！把它切成 128 块流水后，理想情况每步总时间从 1.7 s 压到 $\max(0.1, 1.6) \approx 1.6$ s，看起来只省 6%；但如果模型更小、卡数更少，使 $T_{\text{comm}} < T_{\text{comp}}$，重叠就能把通信几乎全额隐藏。**重叠的收益上限由「慢的那一方」决定，这一步是全文最重要的直觉。**

## 2 重叠的本质：把通信切成块，边算边传

**重叠的核心手段是「切块 + 流水」：把一整块通信拆成很多小片，第一片计算一结束就立刻发出去，后续各片在计算进行的同时完成。** 设计算总量为 $C$、通信总量为 $M$，把它们各切成 $n$ 块，每块的计算时间与通信时间分别约为 $C/n$ 与 $M/n$，则流水线化的总时间为：

$$T_{\text{overlap}}(n) = \frac{C}{n} + (n-1) \cdot \max\!\left(\frac{C}{n}, \frac{M}{n}\right) + \frac{M}{n}$$

先用数字建立直觉。设 $C = 40$ ms、$M = 8$ ms（通信较快）：完全不切块（$n=1$）是 $C + M = 48$ ms；切成 $n=4$ 块，由下文公式得 $T = C + M/4 = 42$ ms；切成 $n=64$ 块，$T = 40.125$ ms——**通信几乎完全消失**。反过来若 $C = 8$ ms、$M = 40$ ms（通信慢），任何 $n$ 都收敛到 $M = 40$ ms，重叠无济于事。**先判断「谁慢」，再决定要不要花力气做重叠。**

工程上 $n$ 不是越大越好：每块太小会让通信协议头占比上升、网卡批处理（coalescing）失效，且每块都要独立的显存缓冲。典型取值在**几十到几百块**之间，把「块数 × 块大小」落在网卡的最佳报文区间附近。

## 3 公式解析：为什么分块越多，隐藏得越干净

对上面的式子做三步拆解，就能看清重叠的全部机制：

- **第一步，读时间线**：第 1 块先算，花 $C/n$；此后每多一块，流水线以「算一块、传一块」的节奏前进，每步耗时由较慢者决定，即 $\max(C/n, M/n)$；收尾时最后一块的通信 $M/n$ 要等它算完。
- **第二步，考虑常见情形 $M \le C$（通信比计算快）**：此时 $\max(C/n, M/n) = C/n$，代入得：

$$T_{\text{overlap}}(n) = \frac{C}{n} + (n-1)\frac{C}{n} + \frac{M}{n} = C + \frac{M}{n}$$

当 $n \to \infty$，$T_{\text{overlap}} \to C$。**通信完全被藏进计算，额外开销 $M/n$ 随分块数反比缩小——这就是「分块越多越好」的数学根源。** 实际里 $n$ 受「每块太小则通信效率下降」约束，存在一个甜点。

- **第三步，反向情形 $M > C$（通信比计算慢）**：此时 $T_{\text{overlap}} \to M$，通信时间成为新的下界，藏不掉的暴露时间为 $M - C$。这说明**重叠不能消灭通信，只能让慢的那一方成为瓶颈**——所以优化通信本身（RDMA、无损网络）与重叠是互补的。

## 4 三种实现机制

理论上讲清楚了，工程上怎么落地？主流框架用了三种机制，层层递进。

**机制一：独立 CUDA 流（stream）承载异步通信。** NCCL 的集合通信本身是异步的——`ncclAllReduce` 只是把一个 kernel 排进 CUDA 流就返回。把它放进**专门的通信流**，就能与主流里的计算 kernel 并发执行：

```python
# PyTorch：把 AllReduce 放到独立 CUDA 流，与反向传播重叠（示意）
comm_stream = torch.cuda.Stream()
bucket = [g.contiguous() for g in grads]        # 一批就绪的梯度
with torch.cuda.stream(comm_stream):
    for g in bucket:
        dist.all_reduce(g, op=dist.ReduceOp.SUM)  # NCCL 异步执行
# 主流继续算下一层，通信在 comm_stream 上并行推进
compute_next_layer()
torch.cuda.current_stream().wait_stream(comm_stream)  # 用结果前同步
```

GPU 上**多个流是真实并行的**：SM 有富余时，通信 kernel 与计算 kernel 可以在不同 SM 上同时执行；NVLink/网卡的 DMA 引擎更是不占用 SM。<span class="marginnote">这里的关键是 `wait_stream` 的位置：只在「真正需要通信结果」的那条指令之前同步，而不是在函数开头就 `synchronize`——过早同步等于把异步打成串行。</span>

需要补充的是，**即使不写任何代码，NCCL 自己也会在内部做一层「隐性重叠」**：ring AllReduce 天然把数据切成 $P$ 块逐段传输，环形流水线上「第 2 段的归约」与「第 1 段的下传」本来就在并行。应用层的切块重叠，是在这层之上再叠加「通信与计算」的并行，两者互补。

**机制二：PyTorch DDP 的梯度分桶（bucket）。** 这是最经典的教科书级重叠。反向传播是一层层算梯度的，**早算完的梯度不必等全部算完**。DDP 按参数顺序把梯度装进若干 **bucket**，每个 bucket 的梯度一就绪，就在**独立流**上立刻发起该 bucket 的 AllReduce——于是「后几层的 AllReduce」与「前几层的反向计算」在时间上重叠。这正是上一节公式里 $n$ 取「bucket 个数」的实例。<span class="marginnote">DDP 默认把参数按注册顺序连续排列（`flat_param`），`bucket_cap_mb` 控制每个 bucket 的大小：桶越小、块越多、重叠越细，但通信报文变小、协议开销上升。`bucket_cap_mb=25` 左右是常见起点。</span>

**机制三：张量切分的局部通信（算子内 overlap）。** 在张量并行/序列并行里，一个算子的 AllReduce 可以**先算一部分、传一部分、再算一部分**。例如 Megatron 对 LayerNorm、dropout 这类「算一行、同步一行」的算子做切分：算完前一半就发前一半的 AllReduce，同时算后一半——把通信藏进算子内部。这比机制二更精细，也常与**选择性激活重计算**配合，是 3D 并行里压榨性能的最后几招之一。

三种机制不是互斥的，而是**层层嵌套**：DDP 的分桶重叠发生在「层与层之间」，算子的切分重叠发生在「算子内部」，两者之上都跑在独立 CUDA 流上。一个成熟框架（如 Megatron 的 `sequence_parallel` + DDP/FSDP）往往把三层同时用上。工程判断的顺序是：**先看有没有重叠（机制二是否默认开启），再看重叠是否够细（机制三），最后看流的编排是否合理（机制一）。**

以 DDP 为例，`bucket_cap_mb` 调小的收益要在「重叠更细」与「报文更碎」之间权衡：小桶让 AllReduce 更早启动（重叠更多），但每桶的协议头与调度开销占比上升。实测曲线通常是先降后升的 U 形——**调参的目标是找到谷底，而不是盲目取最小桶**。这部分与《PyTorch DDP 内部机制》一节的实现细节相互印证。

## 5 前提条件与易错点

重叠不是免费的，它有前提，也有一堆坑：

**前提一：依赖关系允许。** AllReduce 必须「晚于梯度就绪」，这是自然的；但通信结果是否被后续计算**立即**使用，决定了能不能随便重叠。数据并行里，梯度 AllReduce 结果只用于优化器更新，与后续反向计算无关，所以可以放心重叠；张量并行里 AllReduce 结果要被下一层计算消费，就必须切块、做到「这一块不依赖，那一块依赖」的精细编排。

**辨析｜易错点：** 几个最常见的「重叠失效」写法：

- **过早 `torch.cuda.synchronize()`**：一同步，所有异步通信全部排空，重叠归零。
- **在默认流上直接发 NCCL 调用**：NCCL 默认在当前流执行，与计算流没有并行关系，等于串行。
- **多个通信流互相竞争**：多个流同时灌满 NVLink/网卡时，NCCL 需要 `ncclConfig` 里的 `maxCTAs` 等参数避免 SM 抢占；通信 kernel 也吃 SM，可能挤掉计算。
- **每步都新建 stream**：stream 创建/销毁有开销，应该常驻复用。

**容易忽视的另一面：重叠需要「把依赖显式化」。** 异步通信的代价是程序员必须自己用 CUDA event 把「通信结果被谁消费」讲清楚。漏掉 `wait_stream` 会读到未就绪的数据（隐性 bug），多加一个又会打断重叠。成熟的框架把这件事封装成 `comm_ready_event` 之类的句柄，避免使用者在每个调用点手写同步。

**前提二：硬件有余量。** 通信 kernel 同样占用 SM 与显存带宽。如果计算已把 SM 占满（高 occupancy 且无空闲），通信 kernel 只能排队，重叠名存实亡。这也是为什么**给通信留一点 SM（如 `ncclMaxThreads`、`NCCL_MAX_NTHREADS` 调低）**、或把通信 kernel 归到低优先级流，反而能提升整体吞吐。反之，如果链路带宽（NVLink/网卡）是瓶颈而 SM 有富余，则通信 kernel 可以多占 SM 去推满链路——**重叠的最优配置取决于哪一方更紧张**，没有银弹。

## 6 如何验证重叠真的生效

重叠的效果必须「用眼睛看」，不能靠感觉。标准做法是 **Nsight Systems 时间线**：在时间线上，如果 AllReduce kernel 的紫色条与反向计算的条**并排出现**（时间轴重叠），说明重叠成功；如果它们首尾相接、互不重叠，就是串行。<span class="marginnote">量化指标是「重叠率」：$\text{overlap\_ratio} = \frac{T_{\text{serial}} - T_{\text{overlap}}}{T_{\text{serial}}}$。若 overlap 后总时间接近 $\max(T_{\text{comp}}, T_{\text{comm}})$，重叠率接近上限。交叉引用《NCCL 通信的观测与重叠验证》一节。</span>

更细的验证包括：用 `torch.profiler` 看每个 kernel 的 stream 归属，用 `nsys stats` 统计通信 kernel 的总活跃时长，对比「单独计时通信」与「重叠后总步长」之差。一个实用技巧是**「双步对照」**：先记录第 $k$ 步的纯计算耗时，再记录第 $k+1$ 步加通信后的总耗时；若两步之差远小于通信裸耗时，说明重叠充分；若恰好等于通信耗时，说明完全没有重叠。这种对照无需任何剖析工具，几行日志就能做。

## 7 小结

- 串行训练时间 $T = T_{\text{comp}} + T_{\text{comm}}$；重叠的目标是把时间压到 $\max(T_{\text{comp}}, T_{\text{comm}})$。
- 重叠的本质是**切块 + 流水**：$T(n) = C + M/n$（通信快于计算时），分块越多隐藏越干净。
- 三种机制：**独立 CUDA 流**、**DDP 梯度分桶**、**算子内张量切分**。
- 前提是**依赖关系允许**与**硬件有余量**；坑在过早同步、默认流、stream 竞争。
- 用 **Nsight Systems** 时间线验证重叠，用重叠率量化收益。
- 先判断「谁慢」：$T_{\text{comm}} < T_{\text{comp}}$ 时重叠收益最大，反之先优化通信本身。
