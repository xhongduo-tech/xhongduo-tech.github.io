# Roofline 模型：判断 kernel 是计算瓶颈还是访存瓶颈

<div class="epigraph">
<p>我们提出 Roofline，一种有洞见力的可视化性能模型：它把浮点峰值、内存带宽与计算强度画进同一张图，用来分析这三者之间的固有取舍。</p>

## 为什么从 Roofline 模型开始

前面十几课我们逐个学习了合并访存、Shared Memory、occupancy、算子融合……每一个都是「怎么改得更快」的招式。但招式的选择取决于一个前置问题：**这个 kernel 到底是被算力卡住的，还是被内存卡住的？** 用错了方向的优化，比如给一个访存瓶颈的 kernel 疯狂加算力、精简指令，等于给堵车的马路换更快的引擎——白费。

Roofline 模型把这个问题变成一张图：横轴是算术强度，纵轴是可达性能，一条「L 形」天花板把 kernel 分成**计算瓶颈**与**内存瓶颈**两大类。它给上一篇《GPU 内存层次》里的公式 $\max(W/P,\ B/\beta)$ 配上了一个坐标系，从此「卡在哪」不是感觉，而是读数。这张图也是本专题后半程的公共坐标系：FlashAttention、激活重计算、MFU（第十二篇《成本工程》）都要在这张图上定位自己。<span class="marginnote">Roofline 诞生于 2009 年，为多核 CPU 设计（第三级《计算机系统结构》会以 CPU 视角再见它）；如今它成为 GPU 性能工程的入门必修，正是因为<strong>GPU 的算力膨胀远快于带宽膨胀</strong>——张量核让峰值翻了几十倍，ridge point 一路右移，越来越多的算子被推入内存瓶颈区。理解这条曲线，就是理解现代 AI 计算为什么「卡在搬东西」。</span>

## 1 一条天花板曲线：把 kernel 画进坐标系

任何 kernel 能达到的性能，都逃不过两道物理上限：

- **算力上限**：浮点峰值 $P_{\text{peak}}$。再聪明也快不过硬件允许的每秒浮点运算次数，画成一条**水平线**。
- **带宽上限**：每搬运 1 字节，至多能支撑多少运算。设内存带宽为 $\beta_{\text{peak}}$，则可达性能 $\le \beta_{\text{peak}} \times I$，画成一条**过原点的斜线**，斜率就是带宽。

真实可达性能是两者中较小的那个，于是画出来就是一条 L 形的天花板——这就是 Roofline 名字的由来：你只能在这条「屋顶」之下运行。

![Roofline 模型示意图](/images/ai-infra/roofline-model-1.svg)

斜线与水平线的交点叫作 **ridge point（山脊点）**，它的横坐标是算力与带宽的比值。交点左侧，斜线更低，kernel 被带宽按在斜线上，属于**内存瓶颈（memory-bound）**；交点右侧，水平线更低，kernel 被算力按在水平线上，属于**计算瓶颈（compute-bound）**。判断一个 kernel 属于哪一边，只需比较它的算术强度与 ridge point 的大小。

注意两个轴都用**对数刻度**，这是 Roofline 的关键设定：在 log-log 坐标系里，斜线变成一条直线，横跨四个数量级的算子（$I=0.25$ 的逐元素与 $I=2731$ 的矩阵乘）才能画进同一张图。若用线性刻度，慢的算子会缩成紧贴坐标轴的一个点，图就失去诊断价值——**对数把「从 0.1 到 10000」的跨度摊开，让内存瓶颈区与计算瓶颈区在视觉上同样可读**。

## 2 公式解析：Roofline 的数学形式

Roofline 的完整表达式是一条两段函数：

$$
\text{Attainable}(I) = \min\left(P_{\text{peak}},\ \beta_{\text{peak}} \cdot I\right), \qquad I = \frac{W}{B}
$$

其中 $W$ 是 kernel 的总浮点运算量（FLOPs），$B$ 是它搬运的总字节数，$I = W/B$ 就是**算术强度（arithmetic intensity）**——每搬 1 字节、干多少活。对这条式子做三步拆解：

- **第一步，读 $I = W/B$**：算术强度是 Roofline 的「入场券」。同一个算子，实现方式不同 $B$ 就不同：tiling 复用、合并访存、混合精度降字节，全都在提高 $I$。所以 Roofline 不是算子固有的性质，而是**某种实现**的性质。
- **第二步，读 $\min(\cdot)$**：两个上限取较小者。当 $I$ 很小时，$\beta_{\text{peak}} I$ 那一项小，性能被带宽卡住，落在斜线上；当 $I$ 很大时，$P_{\text{peak}}$ 那一项小，性能被算力卡住，落在水平线上。
- **第三步，求交点**：令 $\beta_{\text{peak}} I = P_{\text{peak}}$，解得 **ridge point** $I_{\text{ridge}} = P_{\text{peak}} / \beta_{\text{peak}}$。$I < I_{\text{ridge}}$ 时内存瓶颈，$I > I_{\text{ridge}}$ 时计算瓶颈。

把 H100 的数代进去感受一下。FP16 张量核峰值约 $989$ TFLOPS，HBM3 带宽约 $3.35$ TB/s：

$$
I_{\text{ridge}} = \frac{989 \times 10^{12}}{3.35 \times 10^{12}} \approx 295\ \text{FLOPs/byte}
$$

这个数意味着：**只有每搬 1 字节、至少干 295 次浮点运算的 kernel，才配被称为「计算瓶颈」**。绝大多数深度学习算子远远够不到这个门槛。<span class="marginnote">ridge point 不是常数，它随精度与指令路径变化。同一张 H100，FP32 CUDA Core 峰值约 67 TFLOPS，对应的 ridge 降到约 20；TF32 张量核又在两者之间。<strong>画 Roofline 时必须选与 kernel 匹配的那条屋顶</strong>，这是最常被忽略的细节。</span>

## 3 把三个典型 kernel 放到图上

纸上谈兵结束，放三个真实的深度学习算子进坐标系。

**逐元素算子（elementwise）**，如 $I \approx 0.25$、$= 3.35 \times 0.25 \approx 0.84$：读 4 字节、算 1 次、写 4 字节，$I \approx 0.25$ FLOPs/byte，远低于 295。可达性能 $= 3.35 \times 0.25 \approx 0.84$ TFLOP/s——**用满 989 的 0.1%**。这就是前面反复说「逐元素算子内存瓶颈」的图面证据：它在图的最左下角，离天花板上的算力段差着三个数量级。

**标准注意力的 $\mathbf{S} = \mathbf{Q}\mathbf{K}^\top$**：序列长 $N$、头维度 $d$，运算量 $2N^2d$，搬运量约为 $2N^2$（写回 $N\times N$ 的 $\mathbf{S}$ 占大头），于是 $I \approx d$。对常用的 $d = 128$，$I = 128 < 295$——**注意力核心算子也是内存瓶颈**，即便旁边就躺着 989 的峰值算力也够不着。这是下一课 FlashAttention 的整个动机：不是要算得更快，而是要少搬东西。

**大矩阵乘** $\mathbf{C} = \mathbf{A}\mathbf{B}$（三块 $N\times N$，FP16）：$W = 2N^3$，$B = 6N^2$ 字节，$I = N/3$。当 $N = 8192$ 时 $I \approx 2731 > 295$——**终于落在计算瓶颈区**，可达性能贴着 989 的峰值。这就是为什么大矩阵乘要用 Tensor Core、要调 instruction 调度：它配得上那些算力优化。<span class="marginnote">三条曲线的结论可以一句话收束：<strong>逐元素与注意力是「搬得慢」，矩阵乘是「算得满」</strong>。于是优化的分工也清楚了——矩阵乘抠算力利用率，其他算子抠搬运字节数。这正是后面算子融合、FlashAttention、激活重计算各司其职的原因。</span>

## 4 用 Roofline 做优化决策

把 kernel 定位到图上之后，优化方向就不再是玄学：

- **内存瓶颈（左侧）**：任何「让运算更快」的改动都无效——换更快的执行单元、改指令调度，都是在斜线下方打转。唯一有效的路径是**减小 $B$、抬高 $I$**：合并访存、tiling 复用、算子融合（上一篇《kernel 启动开销与 kernel fusion》）、混合精度降字节、FlashAttention 式的不落盘。它们的共同点：不是让 GPU 算得更快，而是让 GPU 少搬。
- **计算瓶颈（右侧）**：此时减 $B$ 无意义，带宽绰绰有余。该做的是**减小 $W$**：更优的算法、稀疏化、低精度张量核。例如把 FP16 换成 FP8，峰值翻倍，ridge 点右移，更多 kernel 落入计算区。
- **瓶颈在两者边界（ridge 附近）**：两个方向都要试。边界附近的 kernel 往往最「敏感」，微调 $I$ 就能跨过 ridge，从被带宽按着变成被算力按着——这是性能工程师最爱的位置。

Roofline 也是**预算工具**：先画出目标硬件（型号、精度、带宽）的屋顶，再把候选优化手段折算成 $I$ 的提升量，就能在动手写 kernel 之前估算收益上界。省下的是无数个「写了半天才发现方向错了」的日夜。

## 5 一个实战：把矩阵乘从内存瓶颈搬回计算瓶颈

Roofline 最有价值的地方，是它能指导「先优化什么」。以矩阵乘为例，看 naive 实现与 tiling 实现把同一个算子的 $I$ 抬高了几个量级。

**naive 实现**：每个输出元素 $C_{ij}$ 都要重新读一遍 $A$ 的第 $i$ 行与 $B$ 的第 $j$ 列。于是 $W = 2N^3$，而 $B \approx 4N^3$ 字节（每个输出读 $2N$ 个元素、写 1 个），算术强度只有

$$
I_{\text{naive}} = \frac{2N^3}{4N^3} \approx 0.5\ \text{FLOPs/byte}
$$

**0.5，比 ridge 小三个数量级**——naive 矩阵乘是彻头彻尾的内存瓶颈。这解释了为什么「教科书式三重循环」在 GPU 上跑不快：它每搬 1 字节只干 0.5 次运算，被带宽死死按在斜线底部。优化指令、换更快的调度器，都只是在斜线下面打转。

**tiling 实现**：把 $A, B$ 切成 $T\times T$ 的块，每块读进 Shared Memory 复用 $N/T$ 次（这正是第一篇《矩阵乘法 kernel 优化实战》的核心）。搬运量降为约 $6N^2$ 字节（三个矩阵各读/写一遍），于是

$$
I_{\text{tiled}} = \frac{2N^3}{6N^2} = \frac{N}{3}
$$

对 $N = 8192$，$I \approx 2731$，**越过 295 的 ridge point，跨进计算瓶颈区**。同一个算子、两种实现，在 Roofline 图上一个在左下角、一个贴住天花板——tiling 的收益被画得一清二楚：**不是让 GPU 算得更快，而是把 $I$ 从 0.5 抬到 $N/3$**。

再看硬件趋势：FP8 张量核让 H100 峰值再翻一倍（约 1979 TFLOPS），ridge point 右移到约 590——**更多算子的 $I$ 落进斜线区，优化天平进一步向「减 $B$」倾斜**。算力越强，数据搬运越贵，Roofline 上的点就越往右下方沉。

## 6 辨析｜易错点

- **「Roofline 能精确预测运行时间」**——不能。它给出的是性能**上界**，是诊断工具不是模拟器；缓存命中、通信重叠、调度不均都只会让实际更低。图上的点低于天花板是常态，高于天花板则说明你算错了 $W$ 或 $B$。
- **「峰值随便拿一个数」**——必须与 kernel 的精度和指令路径匹配。用 FP16 张量核的 989 去评一个 CUDA Core 逐元素算子，会得出「严重计算瓶颈」的错误结论，误导优化方向。逐元素算子该参照 67 那根屋顶。
- **「算术强度是算子的固有属性」**——不是，它是**实现**的属性。同一个矩阵乘，naive 逐元素实现 $I \approx 0.5$，tiling 后 $I$ 提高几十倍。Roofline 图上的点，画的是「当前这个 kernel 的实现」。
- **「ridge point 是固定常量」**——它随算力与带宽的比值漂移。张量核让 $P_{\text{peak}}$ 暴涨，ridge 右移，把更多原本「还算计算瓶颈」的算子推进内存瓶颈区。Roofline 不是一张静态地图，硬件升级就要重画。
- **「一张图覆盖所有精度」**——一张 Roofline 通常只画一条精度/指令路径的屋顶。FP16 与 FP8 的峰值不同、屋顶不同、ridge 不同；混合精度场景要画多条天花板，并拿更保守的那条做决策，否则会误判瓶颈。

## 7 小结

- Roofline 把 kernel 画进「算术强度—可达性能」坐标系：可达性能 $= \min(P_{\text{peak}},\ \beta_{\text{peak}} I)$，是一条 L 形天花板。
- **ridge point** $= P_{\text{peak}} / \beta_{\text{peak}}$，左侧内存瓶颈、右侧计算瓶颈；H100 FP16 张量核下约 295 FLOPs/byte。
- 三个典型定位：逐元素 $I\approx0.25$、标准注意力 $I\approx d=128$、大矩阵乘 $I=N/3$——前两个内存瓶颈，只有大矩阵乘是计算瓶颈。
- 优化决策由区域决定：**内存瓶颈减 $B$，计算瓶颈减 $W$**，方向用反了等于给堵车换引擎。
- 峰值必须选与 kernel 匹配的精度/指令路径；ridge point 随硬件漂移，需按硬件重画。
- Roofline 是上界诊断，不是精确预测；它把「凭感觉猜瓶颈」升级成「看图读数」。
- 工程用法一条龙：**画屋顶 → 定位 kernel → 判断减 $B$ 还是减 $W$ → 预算优化收益**，先看图再动手写 kernel。

在下一节，我们将把这张图用到最著名的案例上：**标准注意力**被 Roofline 判定为内存瓶颈，FlashAttention 却用「IO 感知」的设计把它从斜线底下捞了出来——它究竟是怎么做到的？
