## 为什么从推理与训练的差异开始

前八篇几乎都在讲训练。但大模型的真正价值在「用」——推理。而**推理不是「训练跑一遍」**：它没有梯度、不做反向、目标不是吞吐而是延迟，还有训练里根本不存在的 **KV Cache**。把训练优化思路照搬到推理上，往往适得其反。

本篇是推理基础设施的总纲：把「推理与训练的本质差异」讲透——目标不同、计算模式不同、显存结构不同、批处理方式不同。理解这些差异，后面几篇的每一个推理优化（continuous batching、PD 分离、显存带宽选型）才有立论基础。

## 1 目标差异：延迟敏感 vs 吞吐优先

训练与推理的第一性差异是**优化目标**：

- **训练**：吞吐优先。一个 batch 晚 1 秒无所谓，关键是「每小时算多少 token」。用满算力、最大化 MFU。
- **推理**：延迟敏感。用户等着回答，TTFT（首 token 延迟）与 TPOT（每 token 间隔）直接决定体验。单个请求快，比「整体吞吐」更优先。

于是推理系统要做的第一件事是**满足延迟约束下的吞吐最大化**——不是「无脑打满算力」，而是在「每个请求都够快」的前提下尽量多接请求。<span class="marginnote">这个「延迟约束下的吞吐」是推理调优的总纲：单纯打满 GPU（高吞吐）可能让每个请求都慢到不可用；单纯追低延迟又浪费算力。连续批处理、投机解码、PD 分离等技术，本质都是在「快」与「多」之间找最优解。</span>

## 2 计算模式差异：无梯度、只前向

训练的计算是「前向 + 后向」，后向约占 2/3 的计算量。推理**只有前向**：

没有梯度，不做反向，算力需求降为训练的 1/3 左右。
权重固定，可量化、可融合、可静态优化——**推理的优化空间比训练大得多**。
计算是「串行的自回归」：一个 token 一个 token 生成，后一个依赖前一个——**无法像训练那样并行处理整条序列**。

「自回归串行」是推理计算模式的灵魂：推理的本质是一个**循环**（每步生成一个 token 并把它拼进输入），这决定了它的延迟下限与批处理方式。<span class="marginnote">自回归的串行性意味着「延迟」有硬下限：生成 $N$ 个 token 至少要 $N$ 次串行前向，无法靠并行压缩。这是推理与训练的又一分野——训练可以「序列并行」，推理的序列是「因果依赖」的，必须逐步走。</span>

## 3 KV Cache：推理特有的显存结构

推理与训练最大的工程差异是 **KV Cache**：在生成过程中，每个已生成 token 的 Key 与 Value 被**缓存下来**，避免每步重算整个历史的 attention。

显存开销：KV Cache 大小 = $2 \times \text{layers} \times \text{heads} \times \text{head\_dim} \times \text{seq\_len} \times \text{batch} \times 2\text{字节}$。
随序列长度与并发数**线性/平方增长**——长上下文 + 高并发 = 显存爆炸。
KV Cache 是推理显存的**大头**，也是「推理的 GPU 选型要看显存带宽」的原因（后文详述）。<span class="marginnote">KV Cache 与训练的激活是「同类不同命」：两者都是「中间结果」，但训练里可重算（activation checkpointing），推理里 KV Cache <strong>不可重算</strong>（生成过的不回头）。所以推理优化的核心战场就是「KV Cache 怎么省、怎么管理」——量化 KV、PagedAttention、缓存共享都是围绕它展开的。</span>

## 4 批处理差异：变长、动态、持续到达

训练的 batch 是「定长、固定形状、整批推进」；推理的请求是「变长、持续到达、各自独立」：

**长度不同**：请求 A 问 10 token，请求 B 问 200 token——无法对齐成固定形状。
**到达不同时**：请求像流水一样不断进来，不是「攒一批再算」。
**完成不同时**：每个请求生成完就退出，batch 持续在变。

于是推理的批处理必须**动态**——这正是 **continuous batching（连续批处理）** 存在的理由（本专题专门一篇）。训练的「静态批处理」在这里不适用。<span class="marginnote">「静态 vs 动态批」是推理系统设计的起点：训练一次迭代 batch 固定，推理每一刻的 batch 都在变。把「batch 视作持续流动的池子」而非「固定的块」，就是 vLLM 等系统与传统 batch 的根本区别——它直接影响显存分配（PagedAttention）与调度策略。</span>

## 5 公式解析：推理的成本结构

推理一次请求的成本可以分解为两个阶段（本专题专门一篇讲 prefill/decode）。一次生成 $S$ 个 token 的请求，总计算量近似：

$$\text{FLOPs} \approx 2N \cdot (P + S)$$

其中 $N$ 是参数量，$P$ 是输入（prompt）长度。而显存侧：

$$\text{Mem} \approx \underbrace{2N}_{\text{权重}} + \underbrace{2 \cdot L \cdot H \cdot d_h \cdot (P + S) \cdot b}_{\text{KV Cache}}$$

- **$2N(P+S)$（计算量）**：与「总 token 数」成正比，$N$ 越大、上下文越长，计算越重。
- **$2N$（权重显存）**：固定，与并发无关。
- **$2L H d_h (P+S) b$（KV Cache 显存）**：与「序列长度 × 并发数」成正比——**并发越高、上下文越长，KV Cache 越大**，这是推理显存的伸缩项。

**关键洞察**：训练的成本由「参数量 × 训练 token」决定，推理的成本由「参数量 × 上下文 token」决定。**当上下文很长、并发很高时，KV Cache 显存超过权重显存**——这是推理系统设计的核心约束。<span class="marginnote">这个成本结构解释了推理的一切设计选择：为什么量化权重（省 $2N$）、为什么管理 KV Cache（省伸缩项）、为什么 PD 分离（prefill 吃算力、decode 吃带宽）——都是围绕「计算 $2N(P+S)$ 与显存 $2N + KV$」这两条成本线做文章。</span>

## 6 辨析｜易错点：推理优化的常见误区

**辨析｜易错点：**
- **「训练优化思路直接套推理」是错的方向**：无梯度、自回归串行、KV Cache 让推理的优化点与训练完全不同。
- **「打满 GPU 利用率就是好推理」忽略延迟**：推理先满足延迟，再谈吞吐；利用率只是手段不是目标。
- **「KV Cache 可以不省」是错觉**：长上下文 + 高并发下 KV Cache 超过权重成为第一大头，必须量化/分页管理。
- **「推理不需要批处理优化」**：变长、动态到达的请求必须用 continuous batching，静态 batch 浪费严重。
- **别把「推理延迟」当单一指标**：TTFT（首 token）与 TPOT（每 token）是不同阶段的两个指标，优化手段不同。

## 7 小结

- **目标差异**：训练吞吐优先、推理延迟敏感——「延迟约束下的吞吐」是推理总纲。
- **计算差异**：无梯度、只前向，且自回归串行，延迟有硬下限。
- **显存差异**：KV Cache 是推理特有的大头，随上下文与并发增长，常超权重显存。
- **批处理差异**：变长、持续到达、动态完成，必须 continuous batching。
- **成本结构**：计算 $2N(P+S)$、显存 $2N + KV$，推理优化的两条主线。

## 8 进阶与延伸

**动手跑一次「训练 vs 推理」对比**：同一个模型，分别跑一次训练 step 和一次推理生成——对比 GPU 利用率、显存占用、计算模式。你会直观看到「训练打满算力、推理的算力闲置 + KV Cache 增长」两个世界。

**几个值得进一步挖的方向**：

- **「无梯度」带来的优化空间**：推理不需要反向，所以权重可以量化、算子可以融合、图可以静态编译——「优化空间比训练大」具体指哪些手段？
- **KV Cache 的「不可重算」**：训练激活可重算（checkpointing），推理 KV 不可重算——为什么？「生成过的不回头」这句话在工程上意味着「KV 省显存只能靠压缩/管理，不能靠重算」。
- **延迟的分解**：一次请求的总延迟 = TTFT + S × TPOT——哪个优化手段影响哪一项？把「优化手段 → 延迟项」的映射画出来。

**自测题**：为什么「打满 GPU 利用率」不是推理的目标？如果你能说清「推理先满足延迟、再谈吞吐」，就理解了推理与训练的目标分野。
