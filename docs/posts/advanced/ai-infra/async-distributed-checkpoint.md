## 为什么从异步分布式 checkpoint 开始

上一节的断点续训讲了「存什么、多久存、怎么保证一致」。但在真实集群上，还有两个工程问题没解决：**同步存档会让训练停顿**（一次全模型写盘可能几十秒，全集群干等），以及**分布式存档的一致性与效率**（几千张卡怎么协调存同一份逻辑状态）。这就是**异步 checkpoint** 与**分布式 checkpoint** 的用武之地。

异步 checkpoint 的梦想一句话：**让存档在后台进行，训练不暂停**。分布式 checkpoint 的梦想另一句话：**让几千张卡各存各的分片，恢复时拼成完整模型**。本篇把这两个梦想的工程实现讲透。

## 1 同步存档为什么慢：全集群的 IO 停顿

朴素实现：训练步走到 `save` 时，各 rank 把状态写盘，写完后才继续下一步。问题：

- **写盘是慢速 IO**：一个 70B 模型，参数 + 优化器状态共约 200GB，按 2GB/s 写盘要 100 秒——**每存档一次，全集群停 100 秒**。
- **多 rank 同时写**：若所有 rank 同时写同一个存储，还会互相争抢带宽，更慢。
- **停顿不可重叠**：同步模型下，IO 与计算严格串行。

对数千卡的集群，一次同步存档可能让**全集群**停几分钟——这是巨大的吞吐浪费。<span class="marginnote">「同步存档停顿」在千卡集群上尤其肉疼：存档间隔 30 分钟、每次停 2 分钟，等于 6% 的算力永远浪费在等待写盘上。异步化把这 6% 直接还给了训练——这是异步 checkpoint 最大的经济价值。</span>

## 2 异步 checkpoint 的核心：拷贝 + 后台写盘

异步的思路是「**先拷贝，再慢慢写**」：

1. **快照拷贝**：训练步结束时，把要存的张量**快速拷贝**到一块「暂存内存」（或另一块显存）。这个拷贝是内存到内存，很快（几十毫秒）。
2. **立即继续训练**：训练循环不被阻塞——它继续算下一步，用到的仍是「正在训练的权重」。
3. **后台写盘**：一个后台线程把「快照」从暂存区慢慢写盘。由于快照与正在训练的权重**已经分离**，写盘多久都不影响训练。

**关键前提**：拷贝必须「一步内完成」，且拷贝后训练对该权重继续更新，而快照停留在「拷贝那一刻的值」。这需要 **copy-on-write 或双缓冲**：训练权重更新时不改动快照区。<span class="marginnote">工程实现常用「CPU 暂存区」：GPU 张量 `cudaMemcpy`（D2H）到 CPU 内存——D2H 很快且不占显存，再由 CPU 线程慢慢写盘。这个「GPU→CPU 快、CPU→磁盘慢」的两段式，是异步存档的标准结构。</span>

## 3 分布式 checkpoint：各存各的分片

训练是分布式的，存档也应该是分布式的。**分布式 checkpoint（distributed checkpoint）** 的原则：

- **每 rank 只存自己的分片**：TP 切分的权重存它那份、ZeRO/FSDP 分片的存它的 shard。不复制全量。
- **一份元数据描述全局**：一个小的元数据文件记录「模型逻辑结构 + 各分片在哪个文件」。
- **恢复时按元数据重组**：各 rank 读自己的分片，必要时跨 rank 重组（如 TP 需要拼接完整权重才能转成 HuggingFace 格式）。

收益：总写入量 = 模型全量（不冗余），每 rank 写自己那份，写盘时间被 rank 数摊薄。<span class="marginnote">Megatron 的 checkpoint 就是这个模型：`model_parallel_checkpoint` 下每个 rank 存 `model_00-rank-XX.pt`，恢复时按 rank 读回。而 HuggingFace 格式的转换要「拼回全量权重」，这是分布式存档之后常见的二次操作。</span>

## 4 一致性的分布式难题：集体提交

异步 + 分布式，一致性挑战升级：

- **各 rank 的存档步数必须一致**：一个 rank 存了第 5000 步、另一个存了第 5001 步，恢复就散架。
- **异步的「快照」可能错位**：rank A 的快照在 step 5000 拷贝，rank B 因调度偏差在 step 5001 拷贝——两份快照不一致。

对策是**全局屏障（barrier）+ 两阶段提交**：

1. **第一阶（阶段）**：所有 rank 到达同一 step，各自把快照拷贝到暂存区，然后**屏障等待**。
2. **第二阶（提交）**：全部就绪后，各自把暂存区写盘，元数据文件记录同一个 step。
3. 恢复时校验元数据里的 step 一致性，不一致则整体回退。

**「集体提交」是把分布式一致性引入 checkpoint 的关键**——它牺牲一点异步性（屏障仍要等最慢的 rank），换取「恢复后训练严格连续」的保证。<span class="marginnote">「屏障」与「异步」看似矛盾，实际上业界做法是「异步的写盘 + 同步的提交点」：拷贝与写盘异步化，但「这次存档对应哪个 step」的判定是同步的。折中让 90% 的存档时间被隐藏，同时保证一致性——这是工程上最成熟的形态。</span>

## 5 公式解析：异步存档的收益

设存档数据量 $D$，内存拷贝带宽 $B_{\text{mem}}$，磁盘写带宽 $B_{\text{disk}}$，训练步耗时 $T_{\text{step}}$。

**同步存档**每步停顿时间：$T_{\text{sync}} = \frac{D}{B_{\text{disk}}}$

**异步存档**每步停顿时间：$T_{\text{async}} = \underbrace{\frac{D}{B_{\text{mem}}}}_{\text{拷贝，快}} + \underbrace{\max\left(0, \frac{D}{B_{\text{disk}}} - T_{\text{step}} \cdot \text{存档间隔}\right)}_{\text{写盘，被训练掩盖}}$

- **$\frac{D}{B_{\text{mem}}}$（拷贝时间）**：D2H 拷贝，$B_{\text{mem}} \approx 20$–$60$GB/s，远快于磁盘。
- **$\frac{D}{B_{\text{disk}}}$（写盘时间）**：若在两次存档之间写完，则完全被训练掩盖（第二项为 0）。
- **对比**：$B_{\text{disk}} \approx 1$–$3$GB/s 而 $B_{\text{mem}} \approx 30$GB/s，**异步把停顿从「磁盘级」降为「内存级」，快一个数量级**。<span class="marginnote">用数字说话：200GB 存档，磁盘写要 100 秒，内存拷贝只要 ~7 秒。异步化把每 30 分钟的停顿从 100 秒压到 7 秒，吞吐损失从 ~5% 降到 ~0.4%——这就是为什么现代训练框架都把异步存档当默认。</span>

## 6 辨析｜易错点：异步分布式 checkpoint 的常见误区

**辨析｜易错点：**
- **「异步存档永不阻塞」是错觉**：快照拷贝仍会短暂占用 GPU/内存，且「提交屏障」要等最慢 rank——异步省的是写盘，不是一致性成本。
- **「每 rank 各存各的就不用协调」是错觉**：步数一致性与元数据仍需全局协调，否则恢复散架。
- **「拷贝到 CPU 就万事大吉」不准确**：CPU 内存若被训练的其他部分占用（如数据预取），拷贝也会变慢。
- **「恢复时直接读分片就行」忽略了格式转换**：从分片存档转成 HuggingFace/发布格式需要拼权重，要预留这个步骤。
- **别忽略「存档后权重被更新」的竞态**：异步存档必须在「拷贝那一刻」冻结快照，否则存出个不伦不类的中间态。

## 7 小结

- **同步存档的痛**：全集群写盘停顿，千卡规模下浪费 5%–6% 算力。
- **异步化**：先内存快照（快）、后台写盘（慢但被训练掩盖），停顿降一个数量级。
- **分布式存档**：各 rank 存自己分片 + 元数据描述全局，写入量不冗余、写盘时间被 rank 摊薄。
- **一致性**：全局屏障 + 两阶段提交，保证「恢复后严格连续」。
- **工程形态**：异步写盘 + 同步提交点，是当前最成熟的折中。

## 8 进阶与延伸

**动手设计一次异步存档**：给你的训练加一个「每 100 步把权重 `cudaMemcpy` 到 CPU、再后台写盘」的异步存档——对比同步存档，你会看到每步停顿从「磁盘级」降为「内存级」，吞吐损失大幅收窄。

**几个值得进一步挖的方向**：

- **「快照冻结」的实现**：异步存档要求在拷贝那一刻冻结权重——「double buffering（双缓冲）」或「copy-on-write」怎么选？训练权重更新与快照拷贝的竞态怎么处理？
- **元数据文件的设计**：分布式存档的「全局状态」存哪——一个小的元数据 JSON 记录「step、shard 列表、各 rank 文件路径」；恢复时先读元数据再决定读哪些分片。
- **与弹性训练的结合**：world size 变化后，旧的分片布局失效——「re-shard + 重存」是弹性 checkpoint 的核心。TorchElastic 的 `torch.distributed.checkpoint` 怎么处理 re-shard？

**自测题**：异步存档的「提交屏障」为什么牺牲了一点异步性？如果你能说清「所有 rank 必须一致地提交同一个 step」，就理解了「一致性 vs 异步」的取舍。

## 9 动手实践清单

- 实现「每 100 步把权重 `cudaMemcpy` 到 CPU、后台写盘」的异步存档。
- 对比同步与异步存档的「每步停顿」与吞吐。
- 为分布式存档设计「元数据 JSON」（step、shard 列表、文件路径）。
- 实现「提交屏障」：所有 rank 就位才集体提交。
- 验证「恢复后各 rank 步数一致」的集体提交正确性。
- 试 world size 变化后的 re-shard 恢复。
- 用「异步写盘 + 同步提交点」评估你的存档停顿。
- 验证「快照冻结」在训练权重更新时的一致性。
