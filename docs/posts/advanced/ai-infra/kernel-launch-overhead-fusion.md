## 为什么从「启动开销」开始

上一课我们学会了用事件精确计时，于是第一次能诚实地回答：**一个 kernel 到底值不值得单独跑一遍？** 这一课要直面一个常常被忽视的成本项——**kernel 启动开销（launch overhead）**。对长 kernel 它无足轻重，对短 kernel 它能把 GPU 利用率打到地板。而应对它最优雅的手段，是 **kernel fusion（算子融合）**：把多个 kernel 合成一个，既省启动、又省全局内存往返。这是后面矩阵乘优化、FlashAttention、以及 PyTorch 的 `torch.compile` 全部共享的一条主线。<span class="marginnote">上一课用事件计时，本课讲「启动本身值多少钱」——两课合起来就是完整的「GPU 时间去哪了」：<strong>执行时间 + 启动时间 + 等待同步的时间</strong>。这三项构成了后续一切剖析（第十篇《监控与性能剖析》）的记账科目。</span>

## 1 一次 kernel 启动究竟花掉什么

一次 `kernel<<<...>>>()` 在 CPU 侧并非「一条指令」，而是一串动作：参数打包与校验、内核对象查找、向 GPU 命令队列写入启动指令、必要时触发驱动层的上下文切换。这些动作叠加起来，量级大约在 **3–8 微秒（µs）**——放在 GPU 的纳秒时钟下，这已经是一段相当长的「CPU 时间」。

关键在对比：一个训练模型里的**主计算 kernel**（如矩阵乘）动辄跑几百微秒，3µs 的启动成本只占 1%；但一个**逐元素 kernel**（`x + b`、`relu`、`scale`）可能只跑 5µs，启动开销与执行时间相当，GPU 有一半时间在空转等指令。<span class="marginnote">启动开销的本质是「命令从 CPU 到 GPU 的飞行时间 + 驱动软件的搬运成本」，它几乎与 kernel 本身的规模无关——<strong>所以越小的 kernel，被它压得越狠</strong>。CUDA Graph 能把一串启动固化成一次图捕获，把多次启动摊成一次，是本主题的进阶解法。</span>

更隐蔽的是：如果 host 侧提交命令的速度跟不上 GPU 消费命令的速度，GPU 还会进入「饿肚子（idle）」状态。启动开销真正伤人的场景，不是单次几百微秒的 kernel，而是**几千个微秒级 kernel 排队执行**——累计的启动等待可以轻松吞掉总时间的 30% 以上。

缓解启动开销的工程手段首推 **CUDA Graphs**：把一长串 kernel 启动固化成一张图（graph），一次捕获、多次重放，CPU 侧只需提交一个图对象，启动开销被摊到整张图上。对启动密集的小算子流水，CUDA Graphs 常能带来可观的整体加速，是生产级推理/训练框架（TensorRT、vLLM 等）的标配优化。

## 2 启动开销的数字感觉：与执行时间赛跑

用上一课的事件计时，我们可以直接量出「启动 + 执行」的合计。假设启动开销 $\ell$、kernel 执行时间 $t$，则 GPU 的**有效利用率（efficiency）**为：

$$
\text{效率} = \frac{t}{\ell + t}
$$

一个 $t = 5\,\mu s$ 的 kernel，按 $\ell = 5\,\mu s$ 算，效率只有 50%——**每个 kernel 有一半时间在等启动**。这也是为什么「一个操作一个 kernel」的朴素写法在 GPU 上是反模式：它把本可以合起来的执行时间，拆成了多次启动排队。

量级上记住三个数字：启动开销 $\approx 3\text{–}8\,\mu s$；逐元素短 kernel 执行时间 $\approx 5\text{–}20\,\mu s$；一个训练 batch 里可能串着几十到几百个算子。三行放一起，结论自然浮现：**短 kernel 是启动开销的受害者，而把短 kernel 合并成少而长的 kernel，是立竿见影的优化**。

做一个具体的估算感受它。设一个训练 step 有 200 个 kernel，平均执行 8 µs、启动 4 µs，未融合总时间 $\approx 200 \times 12 = 2400\,\mu s$，其中**启动占了整整 800 µs（三分之一）**。若用融合把 200 个 kernel 压成 40 个（每个平均执行 40 µs），总时间 $\approx 40 \times 44 = 1760\,\mu s$，直接省约 27%。**启动开销是按「kernel 个数」收税的——kernel 越少，税率越低**，这就是融合能当饭吃的原因。

## 3 Kernel Fusion：把多个 kernel 合成一个

**Kernel fusion（算子融合）**：把多个算子合并进同一个 kernel，让一份数据在寄存器 / 片上完成全部变换，中间结果不再回全局内存。<span class="marginnote">融合的收益不是「省几条指令」，而是<strong>砍掉了中间结果在全局内存的整轮读写</strong>。对算术强度极低的逐元素链，这是把「访存瓶颈」直接翻倍、翻三倍吞吐的杠杆——它的思想与第一篇《GPU 内存层次》的合并访存一脉相承：尽量少碰全局内存。</span>

以经典的三段式 `y = sigmoid(x·w + b)` 为例：

```python
# 未融合：三个 kernel，两个中间结果 t1, t2 写全局内存
t1 = x * w
t2 = t1 + b
y = torch.sigmoid(t2)

# 融合：一个 kernel，x 只读一次、y 只写一次，中间值留在寄存器
# （torch.compile 或 Triton 编译后，等价于下方的手写 CUDA kernel）
```

手写融合 kernel 的骨架长这样：

```cpp
// 每个线程处理若干连续元素，一次读完、一次算完、一次写完
__global__ void fused_linear_sigmoid(const float* x, const float* w,
                                     const float* b, float* y, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        float t = x[i] * w[i];      // 中间量只在寄存器里
        t = t + b[i];
        y[i] = 1.0f / (1.0f + expf(-t));
    }
}
```

编译器有时会自动做这类融合，但跨 kernel 的融合（尤其涉及复杂数据流时）它常无能为力——这就是 `torch.compile` / Triton / 手写 kernel 存在的意义。而**融合思想的最强代言人是 FlashAttention**：它把「读 Q、K、V → 算注意力 → softmax → 输出」整条链在一个 kernel 内分块完成，成为 IO 感知优化的教科书。<span class="marginnote">FlashAttention 的细节留到本主题收尾篇《FlashAttention 的 IO 感知设计思想解析》；今天你只需抓住它最核心的一句话：<strong>融合 = 让数据在片上多待一会儿，少去全局内存跑一趟</strong>。</span>

融合还带来一个常被忽略的间接收益：**L2 缓存的局部性**。未融合时，中间结果写全局内存后，下一个 kernel 再读，中间隔了一次 kernel 启动，数据很可能已被挤出 L2；融合后中间值留在寄存器或片上，L2 压力骤减。对访存密集的算子链，这层收益有时比省启动本身还大。

## 4 公式解析：融合省下的全局内存流量

设一条**逐元素算子链**有 $k$ 个算子，输入数组 $a_0$，输出数组 $a_k$，中间产生 $k-1$ 个临时数组。

**未融合**时，每个算子一个 kernel：第 $j$ 个算子读 $a_{j-1}$、写 $a_j$。全部数组访问次数为

$$
\text{访问}_{\text{未融合}} = \underbrace{k}_{\text{读}} + \underbrace{k}_{\text{写}} = 2k
$$

**融合后**，一个 kernel 读一次 $a_0$、写一次 $a_k$：

$$
\text{访问}_{\text{融合}} = 2
$$

做三步拆解：

- **第一步，数读**：$a_0$ 读一次；$k-1$ 个中间数组 $a_1,\dots,a_{k-1}$ 各读一次，合计 $k$ 次读。
- **第二步，数写**：$k$ 个数组 $a_1,\dots,a_k$ 各写一次，合计 $k$ 次写；读写相加得 $2k$。
- **第三步，作比**：融合后只有 1 读 1 写，全局访存流量降为 $\frac{2}{2k} = \frac{1}{k}$，**省下了 $k$ 倍的访存量**。

对 $k=3$（乘、加、sigmoid），流量直接除以 3。又因为逐元素算子的算术强度极低（约 0.25 flops/byte，远低于 A100 的 ridge point，见本篇《矩阵乘法 kernel 优化》的定量讨论），它是**访存瓶颈**——访存量除以 3，运行时间也近似除以 3。这就是融合「免费午餐」的来源：**它没让 GPU 算得更快，只是让 GPU 少搬了东西**。

## 5 辨析｜易错点

- **「融合永远更快」**——错。融合会增大单个 kernel 的寄存器压力与 shared 用量，可能降低 occupancy（占用率）；当多个小 kernel 在资源上本可良好并行、融合反而把串行依赖拉长时，融合可能更慢。逐元素链是融合的甜区，不是所有算子都是。
- **「编译器会替我融合」**——不保证。`-O3` 只做有限的单 kernel 内优化；跨 kernel 融合依赖 `torch.compile`、Triton 或手写。性能敏感路径默认当它不会自动融合。
- **「融合不改变结果」**——浮点上会。合并运算改变了中间值的舍入顺序，结果可能有 1 ULP 级的微小差异；对数值稳定性要求苛刻的场景需验证。
- **「`torch.compile` 融合了所有算子」**——只融合它能静态分析、且符合图模式的算子；含动态控制流、原地修改、视图依赖的算子常常无法融合，落在 fallback 路径。

## 6 小结

- **kernel 启动开销约 3–8 µs**，与 kernel 规模无关，对短 kernel 是致命开销。
- 效率公式 $\text{效率} = t/(\ell + t)$：kernel 越短，启动占比越高。
- **kernel fusion** 把多个算子合成一个 kernel，同时省下启动开销与中间结果的全局内存往返。
- 对 $k$ 个逐元素算子的链，融合把全局访存流量除以 $k$——因为这类 kernel 是访存瓶颈，时间也近似除以 $k$。
- 融合不是无条件免费的：寄存器/occupancy 代价、浮点舍入变化、编译器不保证自动融合。
- 快速诊断法：用事件分别量「单个 kernel」与「一批 kernel 串行」的总耗时，前者若远超单 kernel 执行时间，说明启动/排队在主导，该融合了。

在下一节，我们把这套「少搬数据」的哲学用到矩阵乘法上，从最朴素的写法一路优化到 tiling——**用算术强度这把尺子，把访存瓶颈打成计算瓶颈**。
