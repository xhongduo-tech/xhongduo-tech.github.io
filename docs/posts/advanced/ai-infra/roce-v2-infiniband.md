## 为什么从无损网络开始

上一节我们认识了 RDMA 的三板斧——内核旁路、零拷贝、网卡卸载。但 RDMA 只定义了「数据怎么在网卡与内存之间移动」，**没有定义「数据在网络上会不会丢」**。RDMA 的假设是：网络不丢包。为什么？因为 RDMA 网卡把「重传」这类协议杂务卸载到了硬件，硬件重传非常昂贵，且 one-sided 语义下接收端 CPU 根本不参与，根本没有软件层可以兜底重传。于是问题变成：**怎样才能让网络不丢包？** 这就是「无损网络」的命题。本文拆开两条路线：InfiniBand 靠**链路级信用流控**天然无损，RoCE v2 站在有损的以太网上，被迫用 **PFC** 补无损、用 **DCQCN** 补拥塞控制。<span class="marginnote">一句话记住主线：InfiniBand 是无损的「原生 RDMA 网络」，RoCE v2 是把 RDMA 硬塞进「会丢包的以太网」，后者的一切复杂性（PFC、ECN、DCQCN）都是在为这个「基因错配」买单。</span>

## 1 InfiniBand：为 RDMA 而生的无损网络

InfiniBand（IB）从设计第一天就是 RDMA 的原生网络，它的无损是「刻在基因里」的，靠两层机制保证：

- **链路级信用流控（link-level credit-based flow control）**：IB 的每一条物理链路，接收端都会给发送端**预先发放信用（credit）**，发送端每发一包就消耗一份信用，信用耗尽就必须停发。数据永远不会把接收端缓冲冲爆，因为发送端早就知道对方能收多少。这是**逐跳（hop-by-hop）**的无损保证——每条链路独立确保不丢，与整网拥塞无关。
- **子网管理器（Subnet Manager，SM）**：IB 子网里有一个 SM 负责给每个端口分配 **LID**（16 位局部标识符）、计算转发路径（类似最短路径优先）、发现拓扑。也就是说 IB 交换机的转发表**不是靠协议自学习**，而是由 SM 集中计算好再下发——这让 IB 的拥塞避免可以从「拓扑层面」就做文章，比如自适应路由。<span class="marginnote">SM 的集中式管理是 IB 与以太网的根本气质差异：以太网「分布式、尽力而为、丢了就丢」，IB「集中式、精确可控、发了必达」。大模型训练要的就是后者。</span>

IB 的带宽按「代」演进，每代再按**并行 lane 数**打包成端口，最常见的是 4x 端口：

| 世代 | 每 lane 标称速率 | 4x 端口速率 | 备注 |
| --- | --- | --- | --- |
| SDR | 2.5 Gb/s | 10 Gb/s | 第一代 |
| QDR | 10 Gb/s | 40 Gb/s | 早期 HPC 常见 |
| FDR | ~14 Gb/s | ~56 Gb/s | |
| EDR | 25 Gb/s | 100 Gb/s | |
| HDR | 50 Gb/s | 200 Gb/s | 当前主流 |
| NDR | 100 Gb/s | 400 Gb/s | 高端新簇 |

表中是每方向每端口的标称速率，全双工。注意实际数据速率要扣除编码开销（如 64b/66b），表中为行业惯用叫法。**大模型训练里说的「200G HDR」「400G NDR」指的就是这类 4x 端口速率。**

## 2 RoCE v2：把 RDMA 塞进以太网

以太网的成本只有 IB 硬件的几分之一，生态也更开放，于是有了 **RoCE**（RDMA over Converged Ethernet，以太网上的 RDMA）：

- **RoCE v1**：把 RDMA 报文直接封装进以太网帧（EtherType `0x8915`），工作在**二层**，只能在同一个广播域内通信，无法路由。几乎无人使用。
- **RoCE v2**：把 RDMA 报文再包一层 **UDP/IP**（目的 UDP 端口固定为 `4791`），工作在**三层**，可以跨路由。**今天的「RoCE」几乎都指 RoCE v2。**

RoCE v2 的报文是「三层嵌套」：外层以太网帧 → 中间 IP + UDP 头 → 内层 IB 的 BTH（Base Transport Header）与数据。UDP 头不是用来传输语义的，而是提供**四元组熵**，让交换机可以做更细粒度的负载均衡（ECMP 哈希）。<span class="marginnote">RoCE v2 用 UDP 端口 4791，也被戏称为「UDP 上跑 IB」。之所以选 UDP 而不是 TCP，是因为 TCP 的滑动窗口与重传正是 RDMA 想卸载掉的「协议杂务」——RDMA 要的是「传输被硬件接管」，TCP 的软件状态机反而碍事。</span>

**RoCE v2 最大的问题：以太网会丢包。** 传统以太网交换机在缓冲溢出时直接丢包（丢给 TCP 的拥塞控制去处理），而 RDMA 没有 TCP 式的软件重传兜底。要让 RDMA 跑在以太网上，必须先把以太网改造成「**无损网络**」。改造的第一步就是 PFC。

## 3 PFC：优先级流控与它的代价

**PFC（Priority-based Flow Control，基于优先级的流控，IEEE 802.1Qbb）** 是给以太网补「无损」的补丁。以太网帧的 VLAN 头里有 3 位 802.1p 优先级，共 **8 个优先级**。PFC 按优先级分别流控：

- 交换机的某个端口的**某个优先级**的队列长度超过阈值时，端口向**上游**发一个 **PFC PAUSE 帧**，请求上游**暂停发送该优先级**一段时间（pause duration）。
- 上游收到后，在暂停期间只停发该优先级，其他优先级不受影响——这就是「按优先级」的意义。
- 这种**逐跳背压（hop-by-hop backpressure）**逐级向上传导，一直压到数据源。

**辨析｜易错点：PFC 不是拥塞控制，它只是「不许丢」。** PFC 只是把「丢包」变成了「停发」，拥堵并没有消失，而是被**堵在链路里**、沿反向逐跳传递。它带来三个著名的副作用：

- **队头阻塞（head-of-line blocking）**：一个优先级被 PFC 暂停，会堵住这条链路上**所有**走该优先级的流——哪怕只有一条流拥塞，其它无辜流也被殃及。
- **暂停风暴（pause storm）与死锁**：如果链路 A 暂停 B、B 又暂停 A，且暂停帧互相等待，就形成**链路级死锁**。在环形拓扑或路由不当的拓扑里，PFC 死锁是真实事故。
- **反应慢**：PFC 每跳都要等缓冲越过阈值再传暂停帧，反应时间是「RTT 量级 + 多跳累积」。在突然的通信尖峰（比如梯度同步瞬间）面前，PFC 往往来不及。

所以业界结论是：**PFC 是 RoCE 的「安全网」，不是「油门」**——它保证不丢，但真正的拥塞响应要靠端到端的拥塞控制，也就是 ECN + DCQCN。

**PFC 的实际部署要点**。生产里通常把 RoCE 流量单独放进**一个专用优先级**（例如 802.1p priority 3），让它的丢包行为与普通 TCP 流量隔离；网卡上还要把 **PFC 缓冲与无损队列**打开，并且 `pause_time`（暂停时长）、缓冲阈值（`xoff`/`xon` 上下阈值）都要按「最大包长 + 链路速率」仔细核算。阈值设太小，PFC 频繁触发、吞吐抖动；设太大，延迟飙升。**PFC 参数调优本质上是「在延迟与吞吐之间选点」**，这也是 RoCE 集群运维最常踩坑的地方。

## 4 公式解析：PFC 需要多少缓冲

要让「缓冲不溢出」成立，交换机必须能吸收**从决定暂停到上游真正停下**这段时间里涌进来的所有数据。设链路速率为 $\text{BW}$，这段时间约为一条链路的往返时间 $\text{RTT}_{\text{link}}$，则每个 PFC 优先级需要的缓冲约为**带宽延迟积（BDP）**：

$$B_{\text{pfc}} \approx \text{BW} \times \text{RTT}_{\text{link}}$$

拆成三步看：

- **第一步，理解「暂停要花多久」**：发送端不是瞬间停下的。上游网卡从「收到 PAUSE 帧」到「最后在途的那一比特落地」，要经过 PAUSE 帧的传播延迟、上游自身的处理延迟、以及**已经在线上飞着的数据**。这一段总时间近似为链路往返 $\text{RTT}_{\text{link}}$。
- **第二步，算这段时间里流进来多少**：在这 $\text{RTT}_{\text{link}}$ 内，上游仍以速率 $\text{BW}$ 全速发送，流进缓冲的数据量就是 $\text{BW} \times \text{RTT}_{\text{link}}$——**带宽 × 延迟积**。缓冲少于这个数，就会溢出丢包，无损承诺破功。
- **第三步，代入数字**：25 Gb/s 的链路、约 1 µs 的链路往返，需要约 $\text{BW} \cdot \text{RTT} = 25\times10^9 \times 10^{-6} = 2.5\times10^4$ 比特 ≈ **3 KB**；到 400 Gb/s、同样延迟则要 **50 KB**。交换机端口众多、优先级众多，加总起来是相当可观的片上 SRAM——**无损是有物理成本的**。

**DCQCN 的速率更新**。PFC 保证不丢之后，RoCE 还需要「尽快把速率压下来」以避免长时间排队。DCQCN（Data Center Quantized Congestion Notification，微软 SIGCOMM 2015）是目前最主流的方案，核心是 **ECN + 速率控制**：

- **ECN 打标**：交换机队列超过阈值 $K$ 时，把数据包头部标记为 **CE（Congestion Experienced）**，不改包内容、不丢包。
- **接收端反射**：收到 CE 包的一端生成 **CNP（Congestion Notification Packet）** 发回发送端。
- **发送端降速**：发送端每收到一个 CNP 就执行：

$$R \leftarrow R \times \left(1 - \frac{\alpha}{2}\right), \qquad \alpha \leftarrow \alpha \times (1 - 2^{-11})$$

$R$ 是当前发送速率，$\alpha$ 是降速因子（初值 1）。CNP 来得越密集，$\alpha$ 因第二式逐次向 0 衰减，降速越「温和」——先狠后柔，避免一次性砍太狠引起网络空转。**当一段时间内没有 CNP 到来**，发送端每过一个定时周期（默认 15 µs）做一次**加法增加** $R \leftarrow R + R_{AI}$，缓慢试探恢复带宽。<span class="marginnote">对比一下两代思路：PFC 是「堵」——用缓冲把数据憋住不丢；DCQCN 是「疏」——用 ECN 让源端立刻降速，从根上减少数据。生产集群通常两者配合：DCQCN 负责快反应，PFC 负责兜底极端突发。</span>

## 5 训练集群里的取舍：IB 还是 RoCE

到这一步，两条路线的取舍已经清晰。需要注意，**IB 与 RoCE 的差距不是「能不能跑」而是「跑得多稳」**：两者在理想工况下都能喂满网卡带宽，差别在链路拥塞、偶发丢包、长尾延迟这些「脏场景」里被拉开的——IB 靠信用流控与 SM 兜底，RoCE 则把一切押在 PFC/DCQCN 的参数是否调对了。

| 维度 | InfiniBand | RoCE v2 |
| --- | --- | --- |
| 无损机制 | 链路级信用流控（原生） | PFC（补丁式） |
| 拥塞控制 | SM 集中式 + 自适应路由等 | DCQCN（ECN + 速率控制） |
| 成本 | 专用硬件，贵 | 以太网硬件，便宜 |
| 生态 | 闭源、单一厂商 | 开放、多厂商 |
| 路由 | 子网内 LID，需 SM | 标准 IP 路由 + ECMP |
| 部署复杂度 | 低（开箱无损） | 高（要调 PFC 阈值、ECN 阈值、DCQCN 参数） |

**生产结论**：追求极致的稳定与性能（前沿训练集群）选 IB，它们买的就是「不用伺候流控参数」的省心；追求成本与供应链灵活（云厂商、中小集群）选 RoCE v2，但要做好与「PFC 风暴」「DCQCN 参数调优」长期共存的准备。<span class="marginnote">NCCL 对两者一视同仁：只要走 Verbs 接口，IB 与 RoCE 在 NCCL 看来都是「RDMA 网卡」。真正拉开差距的是实际训练中的丢包率与拥塞行为——这也是为什么有团队专门为 RoCE 调 NCCL 的超时与协议参数，见《NCCL 调优》一节。</span>

## 6 小结

- **InfiniBand 天然无损**：链路级信用流控逐跳保证不丢，SM 集中管理转发，代价是专用硬件贵。
- **RoCE v2 = RDMA 跑在以太网上**：UDP/IP 封装（端口 4791），可路由、成本低，但以太网本身会丢包。
- **PFC 把「丢包」变成「停发」**：按优先级逐跳背压，需要 $\text{BW} \times \text{RTT}$ 的缓冲兜底，并带来队头阻塞、暂停风暴等副作用——它是安全网，不是油门。
- **DCQCN 用 ECN + 速率控制治拥塞**：交换机打标、接收端反射 CNP、发送端按 $R(1-\alpha/2)$ 降速、无 CNP 时加法增加试探恢复。
- **选型**：前沿训练求稳选 IB，成本敏感选 RoCE v2 并接受调参成本。
