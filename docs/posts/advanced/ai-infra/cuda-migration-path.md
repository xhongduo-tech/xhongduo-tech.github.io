## 为什么从迁移路径开始

前面几篇讲了「为什么难迁」（护城河），这一篇讲「怎么迁」。真实工程里，把一套 PyTorch + CUDA 的训练/推理栈迁到国产芯片，有几种路径可选，各有权衡；而迁移路上的坑点，往往比想象的多——**「改一行 import 就能跑」只是宣传，真实迁移是一次工程战役**。

本篇把迁移的四种路径、常见坑点、以及「性能调优的差异」讲透。读完你就能为自己的代码选一条合适的迁移路线，并预判路上的坑。

## 1 四种迁移路径

按「改动量」从少到多：

- **路径 A：框架适配层**（如 `import torch_npu`）——代码几乎不改，只换设备名。适合「标准 PyTorch 模型」。
- **路径 B：兼容运行时**（如寒武纪 CNRT、海光类 CUDA 层）——把 CUDA 调用映射到国产硬件。适合「用了 CUDA API 的代码」。
- **路径 C：ONNX/中间表示**——模型导出 ONNX，用目标平台的推理引擎（MagicMind 等）转换。适合「推理部署」。
- **路径 D：算子改写**——不支持的算子用目标平台的原生算子/自定义算子重写。适合「深度优化」或「框架不支持的模型」。

**选型原则**：能走 A 走 A（改动最小），A 不行走 B/C，最后才 D——**迁移成本与优化深度成反比**。<span class="marginnote">四种路径对应「信任哪一层」：A 信任框架适配层、B 信任兼容运行时、C 信任中间表示、D 只信任自己写的算子。路径越浅，改动越少但「黑盒」越多；路径越深，可控性越高但工作量越大——这是迁移的核心权衡。</span>

## 2 路径 A 的真相：import 之后还有三步

以 `import torch_npu` 为例，真实迁移流程比「改一行」长得多：

1. **能跑**：换设备（`to('npu')`）、换分布式初始化——先跑通。
2. **调对**：逐算子验证精度——发现不支持的算子，改用原生算子或绕道实现。
3. **调快**：性能剖析（用国产 profiler），针对瓶颈算子优化。
4. **稳定**：长训练验证、容错、checkpoint 兼容性。

**「能跑」到「稳定」之间，隔着一整套工程**。而每一步都可能发现新的坑：精度不一致、算子缺失、分布式库不兼容。<span class="marginnote">「三步走」（能跑 → 调对 → 调快）是迁移的基本方法论：别在第一步就追求性能，也别在性能没起来时就宣布「迁移完成」。每一步都有独立的验收标准——跑通看「无报错」，调对看「loss 曲线对齐」，调快看「MFU/延迟达标」。</span>

## 3 常见坑点清单

迁移路上反复出现的坑：

- **精度不一致**：算子实现不同，同一模型 loss 曲线偏离——需要逐算子比对。
- **算子缺失**：最新模型（MoE、GQA、长上下文算子）在国产算子库里没实现——卡住。
- **分布式库不兼容**：DDP/FSDP/通信库的国产实现不完整，多卡跑不起来或性能差。
- **torch.compile 不兼容**：编译图在国产栈上不可用或退化。
- **内存管理差异**：caching allocator 行为不同，显存峰值/碎片表现不同。
- **随机性差异**：RNG 行为不同，复现实验失败。
- **工具链缺失**：profiler、调试器、可视化不如 CUDA 生态成熟。

**坑点的共性**：都发生在「CUDA 生态默认提供、国产栈刚补齐」的地方——越新、越复杂的功能，坑越深。<span class="marginnote">「精度不一致」是最隐蔽的坑：它不是报错，而是「loss 慢慢偏离」——可能几十步后才被发现。对策是「分算子比对」：跑一遍 reference 模型，逐层对比激活的误差。国产栈的算子实现、融合方式不同，浮点顺序差异会让 loss 曲线不完美重合——要判断「可接受」而非「必须相等」。</span>

## 4 性能调优的差异：别拿 CUDA 经验硬套

即使迁「通」了，性能调优也不能照搬 CUDA 经验：

- **瓶颈位置不同**：国产卡的算力/带宽比、缓存结构不同——同一算子可能是「访存瓶颈」而非「计算瓶颈」。
- **融合策略不同**：图优化（CANN/MagicMind）的融合方式与 cuDNN/TensorRT 不同——算子组合要重新设计。
- **分布式调优不同**：NCCL 的调参经验（环境变量、算法选择）不能直接套到国产通信库。
- **量化行为不同**：量化算法的硬件支持不同，量化模型的精度表现不同。

**核心原则**：用「剖析数据」而非「CUDA 经验」指导调优——**重新剖析、重新定位、重新优化**。<span class="marginnote">「经验不可迁移」是国产迁移最反直觉的点：你在 CUDA 上积累的「这个算子慢就换那个」的直觉，在国产栈上可能完全相反。正确姿势是「忘记经验、只看剖析」——用目标平台的 profiler 重新画时间线、重新找瓶颈。工程师要做的不是「套经验」，而是「重新学习目标平台的性能模型」。</span>

## 5 公式解析：迁移工作量的估算

迁移一个模型的总工作量，按「路径成本」分解：

$$W = \underbrace{\sum_{op \in \text{unsupported}} w_{op}}_{\text{算子改写}} + \underbrace{w_{\text{env}}}_{\text{环境/分布式}} + \underbrace{w_{\text{tune}}}_{\text{性能调优}} + \underbrace{w_{\text{verify}}}_{\text{验证/回归}}$$

- **$\sum w_{op}$（不支持的算子）**：核心工作量，按「时间加权」的不支持算子逐个改（见 Ascend 篇的 Coverage 公式）。
- **$w_{\text{env}}$（环境适配）**：分布式库、数据管线、工具链的适配。
- **$w_{\text{tune}}$（性能调优）**：重新剖析、重新优化——**常被低估的最大头**。
- **$w_{\text{verify}}$（验证）**：精度对齐、长训练稳定性、回归测试。

**经验分配**：一个「import 就能跑」的模型，迁移总工作量里「调优 + 验证」通常占 70%+——**「能跑」只是开始，真正的成本在「跑好」**。<span class="marginnote">这个分解解释了为什么「算子覆盖率高 ≠ 迁移成本低」：不支持的算子可能只占工作量的 20%，而「调优 + 验证」占 70%。很多团队做完「能跑」就宣布成功，结果上线后发现性能只有 CUDA 的 60%——因为调优环节根本没做。<strong>迁移的验收标准是「性能达标」，不是「能跑」</strong>。</span>

## 6 辨析｜易错点：迁移的常见误区

**辨析｜易错点：**
- **「改 import 就算迁移完成」**：那只是「能跑」；「调对 + 调快 + 稳定」才是迁移的全部。
- **「算子覆盖率高就放心」**：覆盖率按「算子数」算会骗人，要看「时间加权」与「不支持的算子有多贵」。
- **「CUDA 调优经验直接套」**：硬件与软件栈不同，必须重新剖析、重新优化。
- **「先跑通再谈性能」要留性能预算**：如果「调快」阶段才发现架构不兼容，可能推翻重来——迁移要提前评估性能风险。
- **别忽略「长期维护」**：新 PyTorch 版本、新模型、新算子都要持续适配——迁移是「开始」不是「结束」。

## 7 小结

- **四种路径**：框架适配层（A）→ 兼容运行时（B）→ 中间表示（C）→ 算子改写（D），改动量与优化深度成正比。
- **三步走**：能跑 → 调对 → 调快，各有验收标准。
- **坑点共性**：精度不一致、算子缺失、分布式不兼容、compile 不可用——都在「CUDA 默认、国产刚补」的地方。
- **调优差异**：瓶颈位置、融合策略、分布式调参都与 CUDA 不同——用剖析数据代替经验。
- **成本公式**：迁移工作量 = 算子改写 + 环境 + 调优 + 验证，调优验证占 70%+。

## 8 进阶与延伸

**动手做一次「迁移演练」**：挑一个你熟悉的小模型，按「路径 A（改 import）→ 跑通 → 精度对比 → 性能剖析」走一遍迁移流程——记录每一步遇到的问题。你会得到一份「这个模型迁到国产卡要多久」的第一手数据。

**几个值得进一步挖的方向**：

- **精度对齐的「可接受标准」**：迁移后 loss 曲线与 CUDA 基线「不完全重合」——差多少算可接受？「相对误差 < 1%」够不够？这与任务对精度的敏感度有关。
- **「调快」的国产工具链**：昇腾的 `msprof`、寒武纪的 profiler——它们的成熟度与 nsys/ncu 差多少？工具链缺失对「调快」环节的制约。
- **迁移的「回归测试」**：迁移完成后，怎么持续验证「新模型、新算子、新 PyTorch 版本」不破坏迁移？——CI 里加「跨平台精度回归」。

**自测题**：为什么「迁移的验收标准是性能达标、不是能跑」？如果你能说清「能跑只是开始、调优验证占 70% 工作量」，就理解了迁移的真实成本结构。

## 9 动手实践清单

- 挑一个小模型走一遍「路径 A：改 import → 跑通 → 精度对比 → 剖析」。
- 记录「不支持的算子」清单，算「时间加权覆盖率」。
- 用国产 profiler 重新剖析，对比 CUDA 的瓶颈定位。
- 制定「精度对齐」的可接受标准（相对误差阈值）。
- 评估「调快」环节的工具链成熟度。
- 为迁移设计「回归测试」：CI 加跨平台精度检查。
- 估算「迁移总工作量」的分解：能跑 / 调对 / 调快 / 验证。
