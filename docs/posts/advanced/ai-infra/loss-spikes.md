## 为什么从损失尖刺开始

训练日志里最吓人的瞬间：loss 稳步下降到第几千步，突然从 2.0 一条直线蹦到 20+，又或者停在 50 不回来。这就是**损失尖刺（loss spike）**——大规模训练的头号「灵异事件」。它不报错、不崩溃，只是静默地把你几小时的算力毁掉。

GPT-3 论文专门用一节讨论 spikes，OPT 训练时经历并复盘过 spikes。**训练稳定性**的第一课就是：尖刺从哪来、怎么识别、怎么救。本篇聚焦**现象与成因**，把尖刺的几大来源分类讲清——下一节再讲应对。

## 1 现象：尖刺长什么样

典型的 loss spike 有以下特征：

- **突发性**：loss 在一步之内跳升几个数量级（2.0 → 50）。
- **可恢复性不同**：有的尖刺很快回落（一次性坏 batch），有的持续抬升（模型被破坏）。
- **伴随信号**：通常同时出现梯度范数爆炸、loss scale 骤降、或某些层的输出出现 NaN/Inf。
- **不完全可复现**：同一个 checkpoint 恢复重跑，尖刺不一定复现——因为分布式下随机性很多。<span class="marginnote">「不完全可复现」是尖刺最令人头痛的特征：如果它每次都复现，那就是确定性 bug；如果随机，就指向数据顺序、硬件错误、或分布式非确定性。排查的第一步就是「复现实验」——复现得了走代码路径，复现不了走基础设施路径。</span>

## 2 成因一：数值层——梯度爆炸与 loss scaling 失效

最经典的成因在数值：**某个大步出现极大梯度，把模型权重推出「正常盆地」**。链条如下：

1. 某些异常样本产生异常大的梯度（norm 突增）。
2. Adam 的更新量 $\eta \cdot \hat{m}/\sqrt{\hat{v}}$ 被二阶矩撑住，但权重仍被推向危险区。
3. 后续层输出进入饱和/极端区，梯度进一步放大——**恶性循环**。

混合精度下还有一条特殊路径：**loss scaling 失效**。若梯度整体溢出（FP16 下超过 65504），loss scale 减半、跳过该步——但若频繁溢出或 scale 降得过低，梯度精度恶化，loss 波动加剧。<span class="marginnote">数值尖刺的「导火索」常是梯度范数监控：正常训练梯度范数在 1–10 量级平稳波动，尖刺前往往先看到范数冲到 100+。这就是为什么训练框架都默认记录 `grad_norm`——它是尖刺的早期预警信号。</span>

## 3 成因二：数据层——坏样本与坏 batch

数据管线是尖刺的「富矿」：

- **损坏样本**：一个被截断的 token 序列、一个标签错位的 pair，可能产生「有违常态」的巨大梯度。
- **重复样本**：数据 shuffle 出问题，同一批高 loss 样本反复出现，强化尖刺。
- **tokenizer 异常**：超长序列、非法字符导致极端 token 组合。
- **数据加载竞态**：`num_workers` 或预取器出错，把错位数据喂给模型。

数据导致的尖刺通常**单次发生、随机分布、一次性**——坏样本进模型，产生一次大梯度，然后恢复。<span class="marginnote">数据尖刺的排查线索：它在「换数据 loader」「加缓存」「换 shuffle 种子」后行为变化；而且常出现在「恰好处理到某个特定 shard」的步数附近。用「跳过该 batch 继续训练」的应对（下一节）能直接验证是否数据问题。</span>

## 4 成因三：优化器与超参

超参不当也会制造尖刺：

- **学习率过大**：前向的权重更新步长太大，翻出盆地。
- **warmup 不足**：冷启动直接大步更新，早期梯度还没稳定就冲过头。
- **batch 突然变化**：梯度累积步数、batch size 中途调整，破坏 loss 的平稳性。
- **Adam 的二阶矩估计失稳**：罕见大梯度让 $\hat{v}$ 瞬间膨胀，更新量骤降（这是 Adam 的自我保护，但也会让 loss 卡住）。

超参尖刺的典型模式：**与训练步数强相关**（总在某个 LR 阶段切换点附近）、**与数据无关**（换数据仍复现）。<span class="marginnote">学习率调度的「尖峰点」尤其危险：cosine decay 中途、或 LR 突然重启（warmup restart）时，权重更新尺度剧变，容易诱发尖刺。工程上在 LR 变化点附近会临时把梯度裁剪阈值调低、甚至降 LR 试探。</span>

## 5 成因四：基础设施层——静默错误

最棘手的尖刺来自「看起来没报错」的硬件/系统问题：

- **静默数据损坏（SDC）**：GPU 计算单元出错，产出错误的梯度但不崩溃（第十篇专门讲）。
- **NCCL 通信错误**：某次 AllReduce 结果不对，一个 rank 拿到坏梯度。
- **checkpoint 恢复错位**：参数、优化器状态、数据位置没对齐恢复。
- **CPU/GPU 内存位翻转**：ECC 未覆盖区域的偶发错误。

这类尖刺**难以复现、难以定位**，只能靠冗余计算、checksum、多卡交叉验证来检测——它是大规模训练稳定性的「深海区」。<span class="marginnote">区分「数据尖刺」与「硬件尖刺」的一个实用技巧：在<strong>同一 checkpoint</strong> 上用<strong>不同随机种子</strong>重跑同样的几百步。数据尖刺往往不重现（数据顺序变了），硬件尖刺可能重现也可能不重现；再用「多卡比对中间梯度 checksum」进一步锁定——若多卡梯度一致而 loss 仍尖，则是数据/超参；若多卡梯度不一致，则是硬件。</span>

## 6 公式解析：梯度范数与尖刺的关系

尖刺最直接的定量信号是**梯度范数（gradient norm）**。设模型参数为 $\theta$，一步的梯度向量 $g = \nabla_\theta \mathcal{L}$，其范数为：

$$\|g\|_2 = \sqrt{\sum_i g_i^2}$$

- **$g_i$（第 i 个参数的梯度分量）**：正常训练中大部分分量小而平稳。
- **$\|g\|_2$（全局范数）**：监控对象。正常波动在「个位数到十位数」，尖刺前常冲到 $10^2$–$10^3$。
- **裁剪判据**：若 $\|g\|_2 > \text{clip\_norm}$（如 1.0），将梯度整体缩放为 $\frac{\text{clip\_norm}}{\|g\|_2}$ 倍。

**尖刺的量化画像**：尖刺步的梯度范数通常是常态的 10–100 倍。所以训练框架默认每步打印 `grad_norm`，并设告警阈值——**「梯度范数异常放大」是所有尖刺的共同前兆**，无论根源在数据、数值还是硬件。<span class="marginnote">梯度裁剪是数值尖刺的「防火墙」：它把每一步的梯度范数钳在阈值内，从根上防止「一步冲出盆地」。代价是裁剪会引入偏差（梯度方向被改），但经验上大模型训练里裁剪利远大于弊——GPT-3 等普遍用 clip 1.0 左右。</span>

## 7 辨析｜易错点：尖刺排查的常见误区

**辨析｜易错点：**
- **「loss 尖了就是过拟合/学习率问题」是错觉**：先按「数据 → 数值 → 超参 → 硬件」四类排查，别上来就调 LR。
- **「跳过一次就完事」掩盖根因**：跳过能救这一步，但若根因是 SDC，尖刺会不断复发。
- **「复现不了就是随机噪声」是错觉**：分布式非确定性让很多确定性 bug 也不可复现，要主动做多卡梯度比对。
- **「grad norm 没用」是错觉**：它是尖刺的最早信号，没监控等于盲飞。
- **别把「一次尖刺」与「持续发散」混**：一次尖刺常可自愈，持续发散说明模型已被破坏，需回滚。

## 8 小结

- **尖刺画像**：突发、可复现性差、伴随梯度范数爆炸与 loss scale 骤降。
- **四大成因**：数值（梯度爆炸/loss scaling 失效）、数据（坏样本/bad batch）、超参（LR/warmup）、基础设施（SDC/通信错误）。
- **共同前兆**：梯度范数异常放大，是尖刺的早期预警。
- **排查思路**：先分类（复现性 + 时机），再定位（数据对比 / 多卡梯度比对）。
- **定位**：训练稳定性课题的入口，理解成因才谈得上应对。

## 9 进阶与延伸

**动手搭一套尖刺告警**：给训练日志加一个「梯度范数监控」——每步打印 `grad_norm`，并设一个「超过历史均值 10 倍」的告警。训练 100 步后回看：有几次告警？对应步的 loss 有什么异常？这套告警就是尖刺的「早期预警系统」。

**几个值得进一步挖的方向**：

- **loss scale 与尖刺的联动**：FP16 训练里，尖刺前 loss scale 常骤降——「loss scale 下降」是比「loss 升高」更早的信号，怎么把它加进监控？
- **尖刺的「事后取证」**：尖刺发生后，除了 loss/grad_norm，还要记什么现场？（batch id、loss scale、各层梯度范数、是否复现）——为「根因排查」留证据。
- **确定性复现实验**：给训练设固定种子，尖刺能否复现？「可复现 → 代码/数据 bug」「不可复现 → 硬件/非确定性」——这个二分怎么实操。

**自测题**：为什么「同一个 checkpoint、换随机种子重跑」能区分数据尖刺与硬件尖刺？如果你能说清「数据顺序变了 vs 硬件错误与顺序无关」，你就掌握了尖刺排查的第一招。

## 10 动手实践清单

- 给训练加「每步打印 grad_norm」，观察正常训练的波动区间。
- 设「梯度范数超历史 10 倍」告警，回看告警步的 loss。
- 记录尖刺现场：batch id、loss scale、各层梯度范数。
- 用「换随机种子重跑」区分数据尖刺与硬件尖刺。
- 检查 dmesg 与 XID，排除硬件错误。
- 对比「跳过该 batch」后尖刺是否复现，验证数据根因。
- 把「grad_norm 曲线」与「loss 曲线」叠在一起找相关性。
