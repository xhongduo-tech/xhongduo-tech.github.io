## 为什么从 warp 调度与分支分化开始

前三课我们已经备齐了全部零件：SM 里有 4 个 warp 调度器，warp 是锁步执行的 32 线程单位，程序员通过 Grid/Block/Thread 组织线程。现在问题来了：**调度器凭什么在每一拍决定执行哪个 warp？当一个 warp 里的 32 个线程「意见不一致」时，硬件会怎么做、要付出多少代价？** 前者是 warp 调度策略，后者是分支分化（divergence）——两者合起来，是 GPU 上「为什么有的 kernel 快、有的 kernel 慢」最常被忽视的一层。

这一课是理解后续一切性能工作的钥匙：共享内存编程、Occupancy 调优、FlashAttention 的 kernel 设计，乃至通信内核里避开条件分支的技巧，都和「让 warp 尽量一致地走同一条路」有关。<span class="marginnote">在第三级《计算机体系结构》里，CPU 对付分支靠的是<strong>分支预测 + 乱序执行</strong>——预测对了就当无事发生；GPU 不做预测，而是「两条路都走一遍、用掩码屏蔽」。两种策略的取舍是本章反复出现的对照主题。</span>

## 1 warp 调度器如何工作

回顾 SM 的结构：每个 SM 有 4 个 warp 调度器，最多驻留 64 个 warp，因此每个调度器管辖约 16 个 warp。每个时钟周期，每个调度器独立地做一次「发射」（issue）决策：

1. 从自己管辖的 warp 中找出**就绪**的（下一条指令的源操作数都齐了、没有未决依赖、执行单元有空位）；
2. 按某种策略**挑一个**；
3. 发射它的下一条指令到对应的执行单元（FP32/INT32/Tensor Core/LD·ST…）。

「挑哪个就绪 warp」的策略有讲究。简单硬件用**轮转（round-robin）**：轮流让每个就绪 warp 各发一条，公平且实现便宜。更复杂的调度器会做**贪心/最老优先**：优先发射等待最久的 warp，以降低个别 warp 的极端延迟。NVIDIA 没有公开各代的完整调度策略，但有一点是明确的——**调度器在「就绪」的前提下挑选，绝不为某个 warp 等待**。<span class="marginnote">这正好呼应上一课《SIMT 与 warp》的结论：SM 只有 64 个 warp 的容量，4 个调度器每周期合计最多发射 4 条指令。调度器的工作不是「让某条指令尽快完成」，而是「让流水线每个周期都有活干」——吞吐优先在这里又一次兑现。</span>

两个容易混淆的点要先厘清：

**辨析｜易错点一：「每周期发射一条指令」≠「每周期只做一个线程的事」。** 一条 warp 指令发射后，32 个 lane 同时执行它——一次发射推动 32 个线程前进。所以 4 个调度器 × 每周期 1 条指令 = 每周期推动最多 128 个线程。GPU 的「宽」来自两条乘法：SM 个数 × 每 SM 的 warp 并行度。

**辨析｜易错点二：调度是「warp 粒度」的，不是「线程粒度」的。** 调度器挑的是一个 warp、发射的是这个 warp 的下一条指令。线程没有独立的调度资格（Volta 之后的独立线程调度改进了执行语义，但调度与吞吐的计量单位仍是 warp）。这意味着 warp 内任何不一致，都会在「一次发射」这个粒度上被放大——这就是分支分化的根源。

## 2 分支分化：一个 warp 里意见不一致

设想 warp 里的 32 个线程执行到一条条件分支：

```cuda
if (data[threadIdx.x] > 0) {
    // 路径 A：对正数做昂贵处理
    result[threadIdx.x] = expensive(data[threadIdx.x]);
} else {
    // 路径 B：对非正数做便宜处理
    result[threadIdx.x] = cheap(data[threadIdx.x]);
}
```

如果 32 个数据里既有正数又有非正数，那么**同一个 warp 里同时存在要走路径 A 的线程和要走路径 B 的线程**——这就是**分支分化（branch divergence）**。

硬件没法「让一条指令一半 lane 做 A、另一半做 B」，因为 SIMT 的核心约束是**同一时刻所有活跃 lane 执行同一条指令**。于是硬件采用**掩码执行（masked execution）**：先用谓词掩码（predicate mask）标记每个 lane 走哪条路，然后**串行地执行两条路径**——执行路径 A 时把要走 B 的 lane 掩掉（它们空转），执行路径 B 时把要走 A 的 lane 掩掉。<span class="marginnote">每个线程的「方向」由一个 32 位的活跃掩码记录，置 0 的 lane 在整条指令执行期间不写回寄存器、不产生副作用，但仍在流水线上「占坑」。这种「两边都跑一遍」与 CPU 的<strong>分支预测</strong>截然不同：CPU 猜对就赚、猜错就付出 20 个周期代价；GPU 不猜，直接把所有可能路径都走完，代价是确定性的。</span>

于是关键结论浮现：**一个 warp 的分化，让两段本来互斥的代码被顺序执行；warp 的执行时间从「两条路径之一」变成「两条路径之和」。** 而且这个过程对单个线程毫无正确性影响——每个 lane 最终只拿到它那一路的结果，代价纯粹是性能上的。

## 3 公式解析：分化的代价到底有多大

把上一节的定性描述定量化。设一个 warp 内有 $k$ 个线程走路径 A（耗时 $t_A$），$32 - k$ 个线程走路径 B（耗时 $t_B$）：

- **理想情况（warp 一致）**：全部 32 个线程走同一条路，耗时取较长那条路径：

$$
t_{\text{uniform}} = \max(t_A, t_B)
$$

- **实际（分化后串行执行）**：两条路径都被完整执行：

$$
t_{\text{diverged}} = t_A + t_B
$$

- **分化的额外开销（被浪费的周期占比）**：

$$
\text{waste} = \frac{\min(t_A, t_B)}{t_A + t_B}
$$

对这条式子做三步拆解：

- **第一步，读符号**：$t_A, t_B$ 是路径 A/B 整条执行完的耗时；$\min$ 是较短路径的耗时——这部分在「理想情况」下本来可以省掉，现在被白白执行了一遍。$t_A + t_B$ 是实际总耗时。
- **第二步，代入极端情形**：若 $t_A = t_B$（两条路径一样长），则 `waste = 1/2`，即**一半的指令周期被浪费**；若 $t_A \gg t_B$（一条路径明显更长），则 `waste ≈ 0`，分化代价可忽略——这说明「分化贵在两条路径都长」。
- **第三步，推广到最坏情况**：如果条件分支不是二选一，而是每个 lane 各走各的（例如 `switch` 有 32 个分支），理论上可能被串行执行 32 遍，即**最坏 32 倍慢**。真实场景里编译器与硬件（重汇聚）会缓解，但量级感是：**分化可以把一个 warp 的吞吐打掉一半甚至一个数量级**。

一个更工程化的解读：把「分化」想成**吞吐税**。只要一个 warp 里有任何一个 lane 要走另一条路，整条 warp 就得为这条路付费。**「为少数 lane 付全 warp 的价」是 SIMT 模型的根本经济规律**——这也是为什么「加快常见情形」这条设计原则在 GPU 上要翻译成「让 warp 内绝大多数线程走同一条路」。

## 4 编译器与硬件如何救场（以及局限）

分化这么贵，编译器与硬件自然不会坐视。三道防线，层层都有局限：

**防线一：谓词化（predication / if-conversion）。** 对**很短**的条件分支，编译器把 `if/else` 改写成「两条指令都执行，再用谓词选结果」，用「多算」换「不分叉」：

```cuda
// 源码
r = (cond) ? a : b;
// 编译后（示意）
r_a = a;        // 无条件执行
r_b = b;        // 无条件执行
r   = (cond) ? r_a : r_b;   // 按谓词选择
```

谓词化的前提是两条路径都便宜（几个周期内能算完）；若路径体很长，无条件执行两条的代价反而超过串行执行，编译器会放弃谓词化。<span class="marginnote">CPU 的指令集也有条件传送（CMOV）等谓词思想，但 CPU 有分支预测可以「赌」，GPU 没有——所以 GPU 编译器把谓词化用得更彻底，这是「无分支预测」架构的补偿机制。</span>

**防线二：重汇聚（reconvergence）。** 硬件在执行完一条路径后，自动在分支的**汇聚点**（两条路径重新汇合的地方）恢复全部 lane。现代 GPU（尤其 Volta 之后）用收敛屏障（convergence barrier）管理这件事，尽量让分化只发生在「分叉点到汇聚点」这段区间，而不是整段 kernel。

**防线三：独立线程调度（ITS，Volta+）。** 每个线程有自己的程序计数器，理论上可以更灵活地推进；但**性能经济学没有改变**——warp 的吞吐仍以「整 warp 一致」为最优，ITS 更多是提升了正确性与编程模型（如允许不同线程在复杂控制流下独立等待）。

**辨析｜易错点：** 很多资料说「Volta 之后分支分化没有代价了」，这是错的。ITS 改变的是**执行语义**（线程能各自推进、能正确地在汇聚点汇合），不是**吞吐结构**——分化路径仍然要串行执行、掩码空转仍然存在。你在性能剖析器（nsight-compute）里依然会看到 divergence 指标，它就是冲着这个代价来的。

## 5 程序员的应对：让 warp 一致

既然分化是吞吐税，程序员能做的就是**别让一个 warp 里的线程意见分歧**。几条实战规则：

**规则一：让条件依赖 warp 统一的量，而不是 threadIdx。** `if (blockIdx.x % 2 == 0)` 在一个 block 内所有线程一致，整 block 的所有 warp 都走同一条路，零分化；`if (threadIdx.x % 2 == 0)` 让每个 warp 内一半线程走 A 一半走 B，必分化。**能挂靠 `blockIdx` 就别挂靠 `threadIdx`**。

**规则二：按「路径」重排数据，而不是在数据上分支。** 比如处理正数/负数时，先把数据**按符号分区**（partition），再让每个 block 处理同一类数据——warp 一致，且还能顺带改善合并访存。<span class="marginnote">「先重排数据、再整块处理」是 GPU 上通用的模式：一次重排的 O(n) 成本，换来后续每个 warp 都走同一条路。这也是很多排序/规约/直方图 kernel 快的原因。</span>

**规则三：block 大小取 32 的倍数。** 上一课的结论在这里多了一个理由：不满的尾部 warp 本身就是一种「结构性分化」——28 个 lane 空转。

**规则四：用算术代替分支。** 能用位运算、`min/max`、查表表达的逻辑，别用 `if`。分支在 GPU 上不是「免费的控制流」，而是「要么谓词化多算、要么分化串行」的二选一。

**规则五：警惕 `__syncthreads()` 出现在分化代码里。** `__syncthreads()` 要求 block 内**所有**线程到达该点；若它被放在只有部分线程能走到的分支里，另一部分线程永远等不到——**死锁**。CUDA 规范规定这是非法用法，后果未定义，实战中常表现为 kernel 挂死或超时。<span class="marginnote">这是最隐蔽的 GPU bug 之一：在 `if (threadIdx.x < 32)` 里放 `__syncthreads()`，表面看没错，实际整个 block 卡死。诊断手段是先怀疑同步与分化的组合——这也是《Nsight 性能剖析》一课会教你怎么看 divergence 与阻塞的直接原因。</span>

## 6 小结

- **warp 调度器**：每 SM 4 个，各管辖约 16 个 warp；每周期挑一个就绪 warp 发射一条指令，绝不等待——延迟靠换 warp 隐藏。
- **分支分化**：warp 内线程走不同路径时，硬件用掩码**串行执行所有路径**，正确性无损、性能有税。
- **代价公式**：$t_{\text{diverged}} = t_A + t_B$，`waste = min(t_A, t_B)/(t_A + t_B)`；两条路径等长时浪费一半，最坏 32 路分化可达一个数量级。
- **三道防线及其局限**：谓词化（只对短路径）、重汇聚、独立线程调度（改语义不改吞吐经济学）。
- **应对**：条件挂靠 blockIdx、数据分区重排、block 取 32 倍数、用算术替代分支、绝不在分化代码里放 `__syncthreads()`。
