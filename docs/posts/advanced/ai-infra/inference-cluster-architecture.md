## 为什么从推理集群架构开始

前两篇讲的是「一块 GPU 上的推理」。但线上推理服务是「一个集群的推理」：成千上万个用户同时请求，请求要路由到合适的实例，流量波动要自动扩缩容。这是典型的**在线服务架构**问题，只是「算力单位」从 CPU 变成了昂贵的 GPU。

推理集群的架构分层清晰：**网关/路由层 → 调度层 → 推理实例层 → 存储层**。本篇把每一层的作用、以及「如何扩缩容」这个在线服务的灵魂讲透。理解它，就理解了「把大模型变成可靠在线服务」的工程全貌。

## 1 推理集群的分层架构

一个生产级推理集群通常有四层：

| 层 | 职责 | 关键技术 |
| --- | --- | --- |
| 网关/路由层 | 接受请求、鉴权、路由到实例 | 负载均衡、连接管理 |
| 调度层 | 任务排队、实例选择、扩缩容 | 队列、autoscaler |
| 推理实例层 | 真正跑模型推理 | vLLM/TensorRT-LLM 引擎 |
| 存储层 | 模型权重、KV 缓存、日志 | 对象存储、分布式缓存 |

**核心设计原则**：网关层「无状态」（不记住请求上下文），把状态放在存储层；实例层「可水平扩展」（加实例就加吞吐）。这套「无状态入口 + 有状态存储 + 可扩实例」是云原生在线服务的地基。<span class="marginnote">「无状态网关 + 有状态后端」让推理集群能水平扩展：任何请求可以路由到任何实例，因为上下文（KV Cache、会话状态）在别处或请求自带。这是在线服务的经典解耦——一旦网关有状态，扩缩容就处处受制。</span>

## 2 路由层：请求怎么找到对的实例

路由层解决「请求从哪进、进哪个实例」。几个关键决策：

- **负载均衡**：Round-robin、最少连接、或「按实例负载」加权——把请求均匀撒到实例。
- **亲和性**：同一用户的连续请求尽量路由到同一实例（利用 KV Cache 的会话复用）。
- **降级路由**：实例过载时，把请求路由到其他实例或排队。
- **多模型路由**：一个网关背后多个模型，按路径/请求头分发。

**路由的粒度**：可以是「请求级」（每个请求独立路由），也可以是「会话级」（保持亲和）。推理场景的亲和性很重要——**同一个会话的 KV Cache 可以复用**，换实例就要重算。<span class="marginnote">「会话亲和」是推理路由与普通 Web 路由的差别：普通服务无状态随便路由；推理服务若把同一对话的请求路由到不同实例，KV Cache 不共享，prefill 要重算整个历史——浪费算力、增加延迟。所以推理网关要「粘住」会话。</span>

## 3 推理实例层：引擎与副本

推理实例层是「跑模型的 GPU 进程」：

- **引擎**：vLLM、TensorRT-LLM、SGLang 等推理引擎，负责模型加载、continuous batching、KV Cache 管理。
- **副本（replica）**：一个模型可以有多个 GPU 副本，每个副本独立处理请求——**副本数 = 吞吐的线性杠杆**。
- **实例内调度**：引擎内部的请求队列与批处理策略，决定「一个副本能同时服务多少请求」。

**引擎选型的关键**：吞吐（每 GPU 每秒 token）、延迟（TTFT/TPOT）、显存管理（PagedAttention 等）。不同引擎在同一 GPU 上的吞吐可能差 2–3 倍——这是推理成本的最大差距来源。<span class="marginnote">「多副本 + 每副本高效引擎」是推理集群的算力模型：总吞吐 ≈ 副本数 × 单副本吞吐。扩缩容的本质就是「调副本数」——加副本提升吞吐、减副本节省成本，而单副本内的效率由引擎决定。两条杠杆缺一不可。</span>

## 4 扩缩容策略：应付流量的潮汐

在线流量的特征是有潮汐：白天高峰、深夜低谷、活动突增。推理集群的扩缩容策略分几档：

- **HPA（水平自动扩缩）**：按指标（QPS、GPU 利用率、排队深度）自动加减副本。指标选错会「过冲」或「滞后」。
- **预制容量**：为可预期的峰值（如活动）预置副本，峰值过了再缩。
- **弹性队列**：流量突增时，请求先进队列「排队」，队列深度作为扩缩信号。
- **慢启动**：新副本要加载模型（几十秒到几分钟），扩容要提前量——**GPU 推理副本的启动比普通服务慢得多**。

**推理扩缩容的难点**：模型加载慢 + GPU 贵，扩缩容是「提前量」与「成本」的博弈——扩早了烧钱、扩晚了掉体验。<span class="marginnote">推理副本的冷启动是扩缩容的「时间炸弹」：加载 70B 权重可能 1–2 分钟，加上预热，一个副本从「决定加」到「能接请求」要好几分钟。所以生产系统用「预热池」：保持少量空闲副本「热着」，流量涨时秒级接管，流量跌时再销毁——用「常驻成本」换「响应速度」。</span>

## 5 公式解析：容量规划

设目标 QPS（每秒请求数）$Q$、单请求平均输出长度 $S$、单 GPU 的 decode 吞吐 $D$（token/s/GPU）、目标排队延迟 $W$。

**所需副本数**：

$$\text{Replicas} \ge \frac{Q \cdot S}{D}$$

- **$Q \cdot S$（每秒输出 token 需求）**：QPS × 每请求长度 = 集群每秒要产出的 token 总数。
- **$D$（单副本吞吐）**：一个 GPU 副本每秒能生成的 token 数。
- **排队约束**：副本数不够时，请求排队；排队延迟 $W \approx \frac{\text{队列长度}}{D}$，要控制在 SLA 内。

代入数字：$Q=100$、$S=500$、$D=2000$ → 需要 $\frac{100 \times 500}{2000} = 25$ 个副本。**这个公式是推理容量规划的起点**——它把「业务指标（QPS、长度）」直接翻译成「GPU 数量」。<span class="marginnote">容量规划的另一个视角是「并行度放大」：prefill 阶段每请求的算力需求随 prompt 长度涨，decode 随输出长度涨。如果 prompt 很长（RAG 场景几百 token），prefill 的算力需求会改变副本数的平衡——容量规划要同时算 prefill 与 decode 两笔账，而不是只看输出 token。</span>

## 6 辨析｜易错点：推理集群的常见误区

**辨析｜易错点：**
- **「加副本 = 线性加速」不完全**：副本间要共享网络/存储/网关，且流量倾斜时部分副本空闲——线性有上限。
- **「QPS 是唯一容量指标」不完整**：还要看平均输出长度与 prompt 长度，QPS 相同但长度翻倍，需求翻倍。
- **「缩容可以很激进」有风险**：缩太快会让排队深度暴涨、延迟超标；缩容也要平滑。
- **「路由层随便做」**：会话亲和、降级路由做不好，用户直接感受到「上下文丢失」或「超时」。
- **别忽略「慢启动」**：模型加载慢导致扩容滞后，预先「预热」比事后追补重要。

## 7 小结

- **四层架构**：网关（无状态路由）、调度（排队 + 扩缩容）、推理实例（引擎副本）、存储（权重/日志）。
- **路由关键**：会话亲和利用 KV Cache 复用；负载均衡按实例负载加权。
- **实例层**：总吞吐 ≈ 副本数 × 单副本引擎吞吐，两条杠杆。
- **扩缩容**：HPA + 预热池 + 弹性队列，模型加载慢让扩缩容必须「提前」。
- **容量公式**：副本数 ≥ Q·S/D，把业务指标翻译成 GPU 数量。

## 8 进阶与延伸

**动手画一张推理集群图**：给你的推理服务画「网关 → 调度 → 推理实例 → 存储」四层图，标出「会话亲和」「扩缩容信号」「预热池」的位置——画完你会看到「无状态网关 + 有状态后端」这套云原生骨架长什么样。

**几个值得进一步挖的方向**：

- **会话亲和与 KV 复用**：同一对话的请求路由到持有 KV Cache 的实例——亲和性怎么实现（会话 hash 路由）？路由错了的代价是「prefill 重算整个历史」。
- **扩缩容的「预热池」**：保持少量空闲副本「热着」，流量涨时秒级接管——「常驻成本」与「响应速度」的权衡怎么量化？
- **多模型共享集群**：一个集群跑多个模型，怎么按「模型 × 负载」分配副本？「专用池 vs 共享池」的隔离与效率之争。

**自测题**：为什么「副本数 ≥ Q·S/D」是容量规划的起点？如果你能说清「每秒输出 token 需求 ÷ 单副本吞吐」，就掌握了推理容量规划的核心公式。
