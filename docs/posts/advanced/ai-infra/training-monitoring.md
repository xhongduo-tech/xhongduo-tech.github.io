## 为什么从监控开始

前九篇讲了一整套训练与推理系统，但「系统跑起来」之后第一件事是**看它跑得怎么样**。没有监控，训练就是盲飞：GPU 是忙是闲、显存还够不够、网络有没有卡、功耗有没有异常——全靠猜。而所有性能优化的起点，都是「从监控数据里定位瓶颈」。

监控不是「看几个数」，而是一套**指标体系 + 采集工具链 + 告警机制**。本篇讲透训练监控的四大类核心指标（算力、显存、网络、功耗）、常见工具链、以及「怎么从监控数据里读出问题」。

## 1 监控什么：四类核心指标

训练任务的监控围绕四类资源：

| 类别 | 关键指标 | 异常信号 |
| --- | --- | --- |
| 算力 | GPU 利用率、SM 占用、Tensor Core 利用率 | 利用率低（数据/通信瓶颈） |
| 显存 | 已用/预留、带宽占用 | 逼近上限（OOM 前兆） |
| 网络 | 吞吐、重传、队列 | 吞吐低（通信瓶颈） |
| 功耗/温度 | 功耗、温度、降频 | 降频（过热） |

**核心原则**：监控的是「资源利用率」，而「利用率低」通常不是资源问题，而是「上游喂不饱」——**低利用率是症状，病因在别处**（数据、通信、调度）。<span class="marginnote">「利用率低 ≠ 资源闲置」是监控解读的第一课：GPU 利用率 50% 往往不是「还有一半算力没用」，而是「数据没喂到或通信在等」。诊断时要顺着「算力利用率 → 显存/网络 → 数据管线」这条链往下找，而不是盯着利用率本身。</span>

## 2 GPU 利用率：几个容易混的数字

监控里 GPU 利用率有几个不同含义，极易混淆：

**nvidia-smi 的 GPU-Util**：采样周期内「有多少时间 SM 上有 warp 在跑」。它**不反映算力打得多满**——SM 上只要有一个 warp 就算「忙」。
**SM 占用率（achieved occupancy）**：活跃 warp 与最大 warp 之比，反映并行度是否拉满。
**Tensor Core 利用率（NVTX/DCGM）**：真正做矩阵乘的占比——训练的核心算力指标。

**关键陷阱**：GPU-Util 显示 90% 可能其实算力利用只有 30%——因为 kernel 很小、并行度低，但 SM「没闲着」。要判断「算力是否真打满」，看 **achieved occupancy 与 Tensor Core 利用率**，而不是 GPU-Util。<span class="marginnote">「GPU-Util 高但训练还是慢」是常见困惑：小 kernel 也能把 GPU-Util 拉高，但计算量小、吞吐低。真正的性能要看「每秒处理的 token / FLOPs 利用率」，而不是 SM 忙不忙。这也是为什么监控要比 GPU-Util 更深的指标（DCGM 的 SM 占用、Tensor Core 利用率）。</span>

## 3 显存、网络与功耗监控

**显存监控**：

`torch.cuda.memory_allocated()`（真占用）vs `torch.cuda.memory_reserved()`（含缓存）——判断是否泄露/碎片。
显存带宽占用——判断是否「显存带宽瓶颈」（某些算子是带宽密集的）。
峰值水位——OOM 前兆。

**网络监控**：集合通信是训练的关键路径，要看每卡网卡吞吐、NCCL 的时间占比、重传率。**网络吞吐低 + GPU 利用率低** = 通信瓶颈。

**功耗/温度监控**：功耗曲线异常（该高不高、该低不低）、降频（throttling）会直接拉低吞吐。**降频是最隐蔽的性能杀手**——GPU 为了不烧坏而降频，算力悄悄打折。<span class="marginnote">降频的典型场景：夏天机房温度高、或者多卡堆叠散热差，GPU 温度逼近上限，频率被硬件自动压低——算力下降但「没有报错」。监控里看到「功耗低 + 温度高 + 频率低」三连，就是降频；对策是改善散热或降功耗墙。</span>

## 4 工具链：DCGM 与 Prometheus/Grafana

现代训练监控的标配工具链：

**DCGM（Data Center GPU Manager）**：NVIDIA 官方 GPU 监控框架，采集 GPU 利用、显存、温度、功耗、NVLink 带宽、SM 占用等 100+ 指标。
**Prometheus + node-exporter + dcgm-exporter**：采集层——DCGM 数据进 Prometheus 时序库。
**Grafana**：可视化面板——GPU 利用率、显存、网络、功耗一目了然。
**告警**：Prometheus Alertmanager + 自定义规则（利用率低、显存高水位、温度高）。

**监控分层**：集群级（看整体资源）、任务级（看单个训练）、节点级（看单卡细节）。**先有集群级大盘，再钻到任务级定位**——这是监控使用的标准路径。<span class="marginnote">监控体系的价值在「时间维度」：不只有「现在」，还有「历史曲线」。训练从「正常」到「变慢」的转折点，往往能从曲线里找出来——比如某步开始网络吞吐骤降、或某节点温度爬升。<strong>曲线是性能问题的「案发现场」</strong>。</span>

## 5 公式解析：从监控数据算真实利用率

设训练某 step 用时 $T_{\text{step}}$，其中 GPU 计算时间 $T_{\text{compute}}$、通信时间 $T_{\text{comm}}$、数据等待 $T_{\text{data}}$。

**真实算力利用率（区别于 GPU-Util）**：

$$U_{\text{real}} = \frac{\text{实际 FLOPs}}{\text{峰值 FLOPs}} = \frac{T_{\text{compute}} \cdot U_{\text{peak}}}{T_{\text{step}}}$$

- **$T_{\text{compute}} / T_{\text{step}}$（计算占比）**：一步里真正在算的时间占比。通信/数据等待越多，这个占比越低。
- **$U_{\text{peak}}$（纯计算时的算力利用）**：kernel 是否把算力打满（Tensor Core 利用率）。
- **乘积 $U_{\text{real}}$**：真实的「算力 × 时间」利用率——训练优化的终极指标（MFU 的雏形，见成本工程篇）。

**从监控读数定位瓶颈**：若 $T_{\text{comm}}$ 占比高 → 通信瓶颈（优化并行/重叠）；若 $T_{\text{data}}$ 占比高 → 数据瓶颈（优化数据管线）；若 $U_{\text{peak}}$ 低 → kernel 效率低（优化算子）。<span class="marginnote">这个「把一步时间拆成 compute/comm/data」的分析，是性能剖析的起点（第十篇后面几节会细讲）。监控给的是「读数」，剖析给的是「时间分解」——两者结合，才能定位「时间花在哪」。监控是「体检」，剖析是「活检」。</span>

## 6 辨析｜易错点：监控的常见误区

**辨析｜易错点：**
- **「GPU-Util 高 = 性能好」是错觉**：它只反映 SM「忙」，不反映算力「用满」；要看 Tensor Core 利用率与真实 FLOPs。
- **「监控指标越多越好」**：指标要可行动——每个监控项都要能回答「高了/低了说明什么、该动哪个旋钮」。
- **「看监控就够了，不用剖析」**：监控定位「哪类资源有问题」，剖析定位「哪个算子/哪个阶段」——两层都要。
- **「利用率必须 100%」是错误目标**：通信/数据天然占时间，目标是把「非计算占比」压到合理范围，不是消灭它们。
- **忽略「历史基线」**：没有基线，单点的「利用率 60%」无从判断好坏——监控要存历史、设基线。

## 7 小结

- **四大类指标**：算力（SM/Tensor Core）、显存（分配/带宽）、网络（吞吐/重传）、功耗（温度/降频）。
- **GPU-Util 的陷阱**：它 ≠ 算力利用率，判断性能要看 achieved occupancy 与 Tensor Core 利用率。
- **降频最隐蔽**：温度高 + 功耗低 + 频率低 = 降频，算力悄悄打折。
- **工具链**：DCGM 采集 → Prometheus 存储 → Grafana 可视化 → Alertmanager 告警。
- **真实利用率**：$U_{\text{real}}$ = 计算占比 × 纯计算利用，一步时间拆成 compute/comm/data 三份来定位瓶颈。

## 8 进阶与延伸

**动手搭一块监控面板**：给一个训练任务配 dcgm-exporter + Prometheus + Grafana，画「GPU 利用率、显存、温度、功耗」四张图——训练 30 分钟，回看曲线：有没有利用率低谷？低谷对应的时段发生了什么？

**几个值得进一步挖的方向**：

- **「利用率低」的归因**：GPU 利用率低时，怎么从监控数据判断是「数据、通信、还是 kernel」？——看 CPU 利用率（数据）、网卡吞吐（通信）、kernel 时间占比（算子）三个伴随指标。
- **降频的监控**：nvidia-smi 里的「Power / Temp / Clocks」三列——频率低于基准就是降频。怎么把「降频告警」加进监控规则？
- **监控的「基线与阈值」**：一个任务的「正常利用率曲线」是什么样的？设「利用率低于基线 20% 且持续 10 分钟」告警——基线怎么用历史数据自动生成？

**自测题**：为什么「GPU-Util 高 ≠ 算力利用高」？如果你能说清「SM 上有一个 warp 就算忙」，就理解了为什么监控要比 GPU-Util 更深一层。
