## 为什么从合并访存与 bank conflict 开始

上一课我们建立了内存层次与内存瓶颈判据：多数深度学习算子注定是内存瓶颈，唯一的出路是「少搬字节」与「把字节搬得更高效」。这一课回答后一半的机制问题：**同一个全局内存，为什么访问模式不同，实际带宽能差出一个数量级？** 答案是一个名字很唬人、原理很朴素的机制——**合并访存（coalescing）**，以及它在上上一层 Shared Memory 里的孪生兄弟——**bank conflict**。

这一课的价值在于：它是 CUDA 性能优化的**第一性原理**。矩阵转置、图像卷积、词向量查表、FlashAttention 的访存设计……几乎每个「快 kernel」的底层都写着同一句话：**让一个 warp 的 32 次访问尽量挤进少数几个事务里**。<span class="marginnote">这个概念不是 GPU 独有的。CPU 上的「空间局部性」、数据库里的「顺序 IO 快于随机 IO」、甚至大模型训练里<strong>「连续 batch 的数据排布影响吞吐」</strong>，都是同一条规律的化身。理解合并访存，等于拿到一把能读遍整个性能世界的钥匙。</span>

## 1 一次 warp 访存，硬件在搬什么

当一个 warp 执行一条读全局内存的指令（例如 `float x = arr[i]`），32 个线程同时发出 32 个内存请求。硬件不是让每个请求单独跑一趟，而是先看**这 32 个地址落在哪里**：

- 现代 NVIDIA GPU 把全局内存切成 **32 字节的扇区（sector）**，L1 缓存行是 **128 字节**（4 个扇区）。
- 内存子系统会把落在**同一扇区 / 同一缓存行**内的请求**合并（coalesce）**成一次事务（transaction）来搬运。

于是极端情况一目了然：如果 32 个线程访问的恰好是**连续**的 128 字节，硬件一次事务就全部搞定；如果 32 个地址散布在 32 条不同的缓存行里，硬件就要发 **32 次（甚至更多）**事务，把每条缓存行里用不到的字节也一并搬回来——**搬了 32 份，只用 1 份**。

关键点：**合并访存不是某个开关，而是访问模式的天然结果。** 你不需要「开启」它，你只需要不破坏它。

用事务数感受一下量级：一个 warp 读 32 个连续 `float`，地址恰好铺满一条缓存行，硬件发 **1 次事务**，搬 128B、用 128B。同样一个 warp 若按步长 8 读 `float`，32 个地址散布在 1KB 区间里，跨过约 8 条缓存行，硬件发 **约 8 次事务**，搬 1KB、用 128B——**搬了 8 倍的数据，只为用到其中一份**。若访问完全随机（间接寻址），最坏情况是 32 次事务、搬 4KB、用 128B。这就是「差一个数量级」的出处。<span class="marginnote">「缓存行 128B」意味着：一个 warp 读 32 个 `float`（4 字节 × 32 = 128B）恰好是整整一条缓存行——<strong>所以「连续线程访问连续 float」被设计成硬件的最优情形，这不是巧合，是架构刻意对齐的结果</strong>。</span>

## 2 理想模式与三种破坏它的写法

**理想模式（stride 1）**：线程 `t` 访问 `arr[base + t]`。32 个线程恰好铺满 128 字节 = 一条缓存行 = 一次事务，利用率 100%。

三种常见的「破坏性」写法：

**写法一：跨步访问（strided）。** 线程 `t` 访问 `arr[base + t * stride]`。步长越大，32 个地址铺得越开，跨过的缓存行越多，利用率按 `1/stride` 掉。<span class="marginnote">处理「结构体数组 / 数组结构体」时最常踩这个坑：对每个线程只取结构体里的一个字段（SoA vs AoS 问题），就等于让 warp 跨大步访问。</span>

**写法二：转置 / 按列访问。** 行主序的二维数组 `mat[t][j]` 里，固定列号 `j` 让线程 `t` 访问第 `t` 行——地址的步长就是行长（可能几百字节），一个 warp 立刻跨过几十条缓存行。

**写法三：间接寻址（gather）。** `arr[idx[t]]`，索引来自数据本身（例如查表、稀疏采样）。这是最坏情形：地址完全随机，每条缓存行都可能只被用到一个字节。

对比两种写法的实际吞吐，差距是数量级的：

```cpp
// 合并访存：连续线程访问连续地址，一个 warp 一次事务
__global__ void scale_coalesced(float* out, const float* in, float s) {
    int t = blockIdx.x * blockDim.x + threadIdx.x;
    out[t] = in[t] * s;          // 线程 t 访问 in[t]，相邻线程相邻地址
}

// 跨步访问：每个线程跨 stride 个元素，利用率 ≈ 1/stride
__global__ void scale_strided(float* out, const float* in, float s, int stride) {
    int t = blockIdx.x * blockDim.x + threadIdx.x;
    out[t] = in[t * stride] * s; // 32 个线程散布在 stride×128B 的区间里
}
```

工程上的三条保命法则：**连续线程访问连续地址**；数据排布能用「数组结构体（SoA）」就别用「结构体数组（AoS）」；访问密集、可对齐的小块时，用 `float4` 之类**向量化读取**让每个线程一次搬 16 字节——warp 仍是连续铺满，但指令数和事务数都降到四分之一。

「SoA 还是 AoS」值得一个具体例子。要处理 $N$ 个粒子的位置与速度，若存成「结构体数组」：

```cpp
struct Particle { float x, y, z, vx, vy, vz; };
Particle* p;                       // AoS：第 t 个线程读 p[t].x
```

线程 `t` 读 `p[t].x`，地址步长是一个结构体 24 字节——一个 warp 铺满 $32 \times 24 = 768$ 字节、跨 6 条缓存行，只用到每条行里 4 字节。改成「数组结构体」`float xs[N]; float ys[N]; ...` 后，线程 `t` 读 `xs[t]`，步长 4 字节、一条缓存行搞定。**同一个数据，两种排布，带宽利用率差 6 倍**——这就是为什么 SoA 在 GPU 上是铁律。

## 3 Shared Memory 的 bank 结构与 bank conflict

全局内存的孪生问题出在 Shared Memory 内部。Shared Memory 被硬件组织成 **32 个 bank**，每个 bank 宽 **4 字节**；一个时钟周期里，硬件最多同时服务 32 个地址——恰好每个 bank 一个。

**bank conflict** 的定义：一个 warp 访问 Shared Memory 时，如果**两个或更多线程访问了同一个 bank 的不同地址**，它们就被迫**串行**，硬件把这次访问拆成多次「通过（pass）」。一次冲突都没有，叫 **conflict-free**，一拍完成；最坏情况是 32 个线程挤进同一个 bank——**32 路冲突，32 拍**。

判定公式很简单：设线程 `t` 访问的**字地址**（以 4 字节为单位）为 $w_t$，则它命中的 bank 是 $w_t \bmod 32$。一个例外：如果所有线程读的是**同一个地址**（例如 `smem[0]`），硬件做**广播**，一拍完成，不算冲突。<span class="marginnote">这解释了为什么「归约（reduction）让所有线程读同一个累加变量」在 Shared Memory 里不但不慢，反而最快——<strong>广播是硬件特意支持的「全体读同一地址」优化</strong>。我们在《Shared Memory 编程》一课会再次见到它。</span>

经典的冲突场景是**按列访问行主序矩阵**：行长恰好是 32 的倍数时，线程 `t` 访问第 `t` 行的同一列，字地址是 `t * 32 + j`，对 32 取模恒等于 `j`——**32 个线程全挤在 bank `j` 上，32 路冲突**。修法朴素而经典：**padding**——把行长从 `32` 加宽到 `33`，让字地址变成 `t * 33 + j`，而 `33 ≡ 1 (mod 32)`，于是 bank 变成 `(t + j) mod 32`，32 个线程落进 32 个不同 bank，冲突瞬间归零。

## 4 公式解析：合并度与冲突次数

两条公式分别量化全局内存的「浪费」与 Shared Memory 的「串行」。

**全局内存——合并利用率。** 设一个 warp 的 32 个线程访问 `float`，步长为 $s$ 个元素，则 32 个地址铺满约 $128s$ 字节，即跨过约 $s$ 条 128B 缓存行；实际被搬回的是这 $s$ 条缓存行（约 $128s$ 字节），真正用到的只有 $128$ 字节：

$$
U = \frac{\text{用到的字节}}{\text{搬运的字节}} = \frac{128}{128\,s} = \frac{1}{s}
$$

三步拆解：

- **第一步，算跨度**：线程 $t$ 的字节地址是 `base + t·s·4`，32 个线程从 $0$ 到 $31$，总跨度约 $31 \cdot 4s + 4 \le 128s$ 字节。
- **第二步，数缓存行**：跨度除以 128 再向上取整，就是被触碰的缓存行数 $s$（精确地说 $s' = \lceil \frac{128s}{128}\rceil = s$）。
- **第三步，得利用率**：真正用到 1 条行、搬了 $s$ 条行，$U = 1/s$。步长 1 → 100%；步长 2 → 50%；步长 8 → 12.5%。**这就是「跨步访问的代价随步长线性增长」的定量版本。**

**Shared Memory——冲突通过数。** 设一个 warp 里线程 $t$ 访问字地址 $w_t$，命中的 bank 是 $w_t \bmod 32$，则这次访问需要通过的次数等于「最拥挤的 bank 上挤了多少个线程」：

$$
p = \max_{b \in \{0,\dots,31\}} \#\{t : w_t \bmod 32 = b\}
$$

对这条式子做两步拆解：

- **第一步，逐个 bank 数人头**：把 32 个线程按 `w_t mod 32` 分组，每组是「命中同一个 bank 的线程们」。
- **第二步，取最大组**：最大的那一组有多大，这次访问就要串行通过多少拍。conflict-free 要求 $p = 1$；若某 bank 挤了 8 个线程，$p = 8$，一拍变八拍。

举例：线程 $t$ 访问字地址 $8t$（步长 8 个 float），$8t \bmod 32$ 只在 $\{0, 8, 16, 24\}$ 四个 bank 间循环，每组 8 个线程，$p = 8$——**步长 8 的 Shared Memory 访问是 8 路冲突**。这就是为什么 2 的幂步长在 Shared Memory 里尤其危险，也解释了 padding 为什么永远有效：把步长换成「与 32 互质的数」，冲突自然消散。

## 5 辨析｜易错点

- **「bank conflict 发生在全局内存」**——错。bank 是 Shared Memory 内部的硬件结构；全局内存对应的概念是**未合并 / 未对齐**。两者的诊断指标、工具（Nsight Compute 里的 `Memory` 页）都不相同。
- **「所有线程读同一地址是灾难」**——恰恰相反。全局内存里 32 个线程读同一地址，硬件当作 1 次事务；Shared Memory 里硬件直接广播，1 拍完成。真正怕的是「同一 bank、不同地址」。
- **「只要步长是 2 的幂就危险」**——对 Shared Memory 尤其成立（容易映射到同一批 bank）；对全局内存，危险与否取决于**跨过多少缓存行**，而非步长是否为 2 的幂。
- **「合并访存是旧架构才需要关心的」**——现代架构只是多了 32B 扇区粒度，让「部分合并」不至于全盘皆输，但「跨步吞掉 8 倍带宽」的物理没有变。算子库（cuBLAS、cuDNN、FlashAttention）恰恰是**最执着**于合并访存的地方。

## 6 小结

- **合并访存** = 让一个 warp 的 32 个地址尽量落在少数几个 128B 缓存行 / 32B 扇区内；硬件自动合并，你的**访问模式**决定一切。
- 理想模式：**连续线程访问连续地址**，一个 warp 恰好一条缓存行 = 一次事务；跨步、转置、间接寻址是三大破坏模式。
- 全局内存利用率公式：$U = 1/s$（$s$ 为步长），跨步访问的代价**随步长线性增长**。
- Shared Memory 分 **32 个 4B bank**，一拍最多服务每 bank 一个地址；同 bank 不同地址 → **bank conflict**，按最拥挤 bank 的线程数拆成多次通过：$p = \max_b \#\{t: w_t \bmod 32 = b\}$。
- **padding（加宽一列）** 是把「2 的幂步长」错开、消 conflict 的经典手法；广播（全体读同一地址）不算冲突，反而是最快情形。
