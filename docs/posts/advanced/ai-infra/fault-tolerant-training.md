## 为什么从容错训练开始

集群规模一大，「故障」就不是 if 而是 when：千卡集群上，GPU 平均无故障间隔可能只有几天，一次训练要跑几周——**几乎必然遇到节点故障**。没有容错机制，训练就只能「全靠运气」；有了它，故障只是「一次自动重来」。

容错训练的三部曲：**检测（发现故障）→ 诊断（定位故障）→ 恢复（自动续训）**。本篇把每一步的工程做法讲透，并介绍工业界的弹性训练思路——训练系统如何从「崩溃即失败」进化到「故障即自愈」。

## 1 检测：怎么发现节点挂了

训练进程本身不报错时，故障靠**外部信号**检测。常用手段：

- **心跳（heartbeat）**：每个 rank 定期向协调者报告「我还活着」。超时未报 → 判为故障。
- **集合通信超时**：AllReduce 卡住超过阈值 → 某个 rank 掉线（NCCL 有 `NCCL_TIMEOUT`）。
- **硬件监控**：GPU XID 错误（`NVRM Xid`）、温度、功耗异常。
- **watchdog**：训练进程崩溃/挂起时，由外部进程重启它。

关键设计：**检测要快而准**——太快误杀（一次网络抖动就重启全集群），太慢损失大。工业实践常用「多级超时」：短超时告警、长超时判定死亡。<span class="marginnote">「挂起」比「崩溃」更棘手：崩溃至少留下退出码，挂起则一切静默（进程在、就是不动）。挂起检测靠「心跳超时」或「watchdog 检查进度文件是否更新」——训练死锁、IO 卡死、GPU 计算挂起都会表现为挂起。</span>

## 2 诊断：故障出在哪、什么类型

检测到故障后要分类定位，因为不同类型的处理方式完全不同：

| 故障类型 | 特征 | 处理 |
| --- | --- | --- |
| 节点故障 | 进程崩溃、机器掉线 | 换节点重启 |
| 网络故障 | NCCL 超时、连接重置 | 重启通信域 |
| GPU 故障 | XID 错误、ECC 报错 | 隔离该 GPU |
| 挂起/死锁 | 进程在但无进度 | 杀进程重启 |
| 数据问题 | IO 读不到、损坏 | 检查存储 |

**「哪块坏了」比「坏没坏」更重要**——定位后可以「只重启受影响部分」而不是全集群。<span class="marginnote">诊断的信息来源：训练日志（最后一条正常的日志是哪步）、系统日志（dmesg 里有没有 GPU 错误）、监控面板（哪个节点心跳断）。工业集群把这些信息汇总到「故障追溯」，自动给出「node X, GPU Y, 原因 Z」的结论，供调度器决策。</span>

## 3 恢复一：手动重启与检查点回滚

最朴素但最可靠的恢复：**发现故障 → 从最近 checkpoint 重启**。

1. 故障告警，暂停集群。
2. 运维确认故障节点，隔离/替换。
3. 从最近健康 checkpoint 启动新训练进程。
4. 数据位置恢复到 checkpoint 记录的步。

这套流程的可靠性依赖前两篇的 checkpoint 体系（六项状态 + 一致性）。**缺点**：需要人工介入，恢复时间 = 人处理故障的时间（分钟到小时）。<span class="marginnote">手动恢复的「人工环节」是大规模训练的隐性成本：一次深夜故障可能让训练停 2 小时，而其中大部分时间在等人。这让「自动恢复」成为刚需——不是更快，而是「不用等人」。</span>

## 4 恢复二：弹性训练与自动重启

**弹性训练（elastic training）** 让恢复自动化：训练系统感知节点数量变化，自动调整并行配置并继续训练。

- **TorchElastic**：`torch.distributed.elastic` 提供「agent 管理 + 容错重启」：检测到 rank 死亡，自动从 checkpoint 重启，且**允许节点数变化**（新节点加入、坏节点剔除，动态 re-shard）。
- **RDZV（rendezvous）**：节点重聚机制——重启后各 rank 重新「会合」，协商新的 world size 与 rank 分配。
- **动态 checkpoint**：重启时从最近 checkpoint 恢复，若节点数变化则 re-shard 并重新保存。

弹性训练把「故障恢复」从「运维操作」变成「系统能力」——故障时集群自动缩容继续训，修复后自动扩容回去。<span class="marginnote">弹性训练的精髓是「world size 可变」：传统分布式假设 rank 数固定，一坏就整个训练死掉；弹性假设「节点数是可以协商的」，坏几个就先用剩下的继续训。代价是 re-shard 要重新切分数据与模型（有开销），且 TP/PP 维度不能随便变（它们对 rank 数敏感），弹性主要作用在 DP 维。</span>

## 5 公式解析：容错的收益建模

设训练总时长 $T_{\text{compute}}$，故障率 $\lambda$（单位时间的故障期望次数），单次故障的「检测 + 重启 + 回退」开销 $C_{\text{recover}}$。

**无容错**：一次故障即训练失败，期望投入全部浪费（重来）。**有容错**：期望总耗时为：

$$\mathbb{E}[T] \approx \frac{T_{\text{compute}}}{1 - \lambda \cdot C_{\text{recover}} / T_{\text{compute}}} \quad\approx\quad T_{\text{compute}} + \lambda \cdot C_{\text{recover}}$$

- **$\lambda \cdot C_{\text{recover}}$（期望恢复开销）**：故障次数 × 每次恢复成本。这就是「容错的税」。
- **降低成本的两条路**：减少 $C_{\text{recover}}$（更快检测、更近的 checkpoint、自动重启）——这是弹性训练的着力点。
- **阈值**：当 $\lambda \cdot C_{\text{recover}}$ 超过重训成本时，容错反而亏——但现实中 $C_{\text{recover}}$ 远小于重训，容错几乎总划算。

**一句话**：容错训练买的是「把故障税压到最低」——检测越快、回滚越近、重启越自动，税率越低。<span class="marginnote">用数字感受：千卡集群若 5 天一次故障，一次恢复开销 30 分钟，则「故障税」≈ 0.4%；若没有容错，一次故障 = 全部训练重来 = 100% 损失。这就是为什么「容错是必需品而非可选项」——它把灾难变成小费。</span>

## 6 辨析｜易错点：容错训练的常见误区

**辨析｜易错点：**
- **「挂起进程会自己恢复」是错觉**：多数挂起是死锁/IO 卡死，等多久都不会好，必须杀进程重启。
- **「检测越快越好」不成立**：网络瞬时抖动也会触发超时，太敏感会频繁误重启，反而拖慢训练。
- **「弹性训练是万能的」不准确**：TP/PP 维度对 rank 数敏感，弹性主要作用在 DP 维；且 re-shard 有开销，频繁变化更糟。
- **「从 checkpoint 重启一定成功」不保证**：checkpoint 本身可能损坏（要校验），或数据位置错位导致恢复偏差。
- **别把「硬件故障」当「代码 bug」反复调参**：先查 dmesg/XID/监控确认是硬件问题，再谈重启。

## 7 小结

- **容错三部曲**：检测（心跳/超时/XID）→ 诊断（类型 + 位置）→ 恢复（重启/回滚/弹性）。
- **挂起最棘手**：进程在但无进度，靠心跳超时与 watchdog 检测。
- **手动恢复**：可靠但靠人，恢复时间分钟到小时。
- **弹性训练**：TorchElastic + rendezvous，节点数可变、自动缩扩容、re-shard 续训。
- **收益模型**：容错把「一次故障 = 全部重来」变成「故障税」≈ λ·C，把灾难变成小费。

## 8 进阶与延伸

**动手做一次「故障演练」**：在训练中途手动 kill 一个 rank 的进程，观察你的系统怎么反应——是有 watchdog 自动重启，还是整个训练崩掉？通过演练暴露容错体系的缺口，比等真故障来得划算。

**几个值得进一步挖的方向**：

- **挂起的诊断三板斧**：进程「活着但不动」时，先查「dmesg 有无 GPU 错误」→「`py-spy dump` 看 Python 栈卡在哪」→「看监控里该 rank 的 GPU 利用率」——三步定位是挂起还是死锁。
- **NCCL 超时的配置**：`NCCL_TIMEOUT` 设多久合适？太短误杀（网络抖动）、太长等死——结合你的网络状况找一个平衡值。
- **TorchElastic 的 min/max 配置**：`max_restarts`、`min_size` 怎么定？弹性区间越宽越稳、但 re-shard 越频繁——「稳定性 × 成本」的权衡。

**自测题**：为什么「弹性主要在 DP 维」？如果你能说清「TP/PP 的通信图对 rank 数固定」，就理解了弹性训练与并行策略的边界。
