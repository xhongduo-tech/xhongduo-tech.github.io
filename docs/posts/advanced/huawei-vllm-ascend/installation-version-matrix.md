## 为什么从版本匹配开始

上一篇我们夸下海口：昇腾路线「代码不用改」。这句承诺的前提是一个苛刻但冷酷的事实——**CANN、PyTorch、torch_npu 三者的版本必须精确匹配**。CUDA 生态里，PyTorch 和驱动各玩各的，版本错配通常只是「装不上」；昇腾生态里，torch_npu 直接编译进 CANN 的接口约定里，版本错配会以**运行时崩溃、算子报错、莫名其妙的精度问题**等形式出现，而且查起来极其痛苦。这一篇把「装环境」从「玄学」变成「按表操作」，是昇腾部署最值得花时间的一步。

## 1 三角依赖：为什么版本必须成套

要装的东西不是一个，而是一个**互相锁定的三角**：

**CANN（Compute Architecture for Neural Networks）**：昇腾的软件栈（第 1 篇《昇腾 NPU 硬件与软件栈》）。它提供 AscendCL 运行时、算子库、图引擎。版本以「CANN 8.x」这类命名。

**PyTorch**：上层框架。昇腾官方发布的 torch_npu 只适配特定几个 PyTorch 版本（如 2.1.0、2.3.1 等），**不是「最新 PyTorch 都能配」**。

**torch_npu**：连接 PyTorch 与 CANN 的插件。它**编译时锁死**了 PyTorch 的 ABI 与 CANN 的接口版本——这是整个三角锁定的根本原因。

<span class="marginnote">为什么不能「各自最新」？因为 torch_npu 的二进制是在<strong>特定 PyTorch 版本上编译的</strong>：PyTorch 的算子分发表、Tensor 布局在不同小版本间会变，torch_npu 若不对应就会段错误。<strong>这就像插头与插座：每个 torch_npu 插头只认它对应的那排 PyTorch 插座</strong>。</span>

**核心要点**：CANN 定「算力接口」，PyTorch 定「框架接口」，torch_npu 是夹在中间、把两者翻译到一块的固件——**只要有一环换版本，整个三角必须成套换**。

## 2 安装前的三查

动手 `pip install` 之前，先把环境查清楚，可以省掉一整晚的排错：

**查操作系统**：昇腾官方对操作系统有明确支持范围（openEuler、Ubuntu 等）。用 `uname -a` 与 `/etc/os-release` 确认。

**查硬件型号**：`npu-smi info` 能看到昇腾芯片型号（910B3、310P 等）与驱动状态。驱动没起来，后面全白搭。

**查已有版本**：`python -c "import torch; print(torch.__version__)"` 与 `pip show torch_npu` 看是否已有残留。**残留的旧版本是升级时最常见的坑**——新旧 torch_npu 混在一起，运行时行为不可预测。

**辨析｜易错点：** 昇腾的「驱动、固件、CANN」是三个独立安装件，很多人只装了 CANN 忘了驱动，报「设备不存在」。`npu-smi info` 能列出设备，驱动才正常；列不出，先查驱动与固件，别急着怀疑 CANN。

## 3 安装步骤：一条主路径

昇腾社区推荐的主路径，大致是「装 CANN → 装 PyTorch → 装 torch_npu → 装 vllm-ascend」四步：

**第一步，装 CANN**：从昇腾社区或官方仓库下载与硬件匹配的 CANN 安装包，按文档完成安装与 `source /usr/local/Ascend/ascend-toolkit/set_env.sh` 之类的环境变量注入。

**第二步，装 PyTorch**：用 pip 安装**与 torch_npu 对应的那个 PyTorch 版本**——这一步的关键不是「最新」，而是「torch_npu 要求的那个版本」。

**第三步，装 torch_npu**：`pip install torch-npu`（或从官方 wheel 装），安装后跑一条冒烟测试验证「torch 能驱动 npu」：

```python
import torch, torch_npu
x = torch.randn(2, 2).npu()
print(x + x)  # 能算出来，三角就通了
```

**第四步，装 vllm-ascend**：`pip install vllm-ascend`，然后 `vllm serve --help` 确认 CLI 可用。

<span class="marginnote">冒烟测试是这条链路上<strong>性价比最高的一步</strong>：在跑任何模型之前，先用一行代码确认「PyTorch 能真的在 npu 上算」。三角没通，后面的模型加载错误全是二次污染的假象。</span>

## 4 版本匹配的验证：装完怎么确认没装错

装完不等于装对。三个快速验证命令，各管一个环节：

**`npu-smi info`**：确认硬件驱动正常，能看到芯片型号与显存。

**冒烟测试**（上面那条）：确认 torch_npu 与 PyTorch 配对成功。

**`vllm serve --model <小模型>` 跑通**：确认 vllm-ascend 与 CANN 算子库对接成功。小模型（如 0.5B 级）加载快、出错快，是最便宜的端到端验证。

**核心要点**：环境验证的次序是「硬件 → 张量 → 推理」逐层递进。**任何一层失败，先在本层解决，不要跳过**——跳过一层去查下一层，只会让错误信息变得更难懂。

### 一套组合长什么样

昇腾社区的版本兼容表通常给出「CANN × torch_npu × PyTorch」的映射关系。实际部署时，最稳妥的做法是**选官方验证过的「黄金组合」**，而不是自己拼版本：

- 官方版本兼容表里标注「推荐」的那一组，通常兼顾了性能与稳定性；
- 想要新特性，可能需要升级到更高版本的组合——但稳定性优先时，选「验证过的旧组合」更省心；
- 每次升级，先在小规模环境验证一遍冒烟测试，再推广到生产集群。

**这样做的原因很简单**：版本组合是「多对多」的关系，自己拼出来的组合也许「碰巧能用」，但一旦遇到冷门路径，就会撞上没人踩过的坑。**跟着官方推荐的组合走，你踩的每一个坑都有人替你踩过。**

## 5 核心对比表：常见版本错配的症状

这一篇是工程主题，用一张「症状表」把版本错配的典型表现钉出来：

| 症状 | 最可能的根因 | 排查方向 |
| --- | --- | --- |
| 启动即段错误 / core dump | torch_npu 与 PyTorch 版本不匹配 | 核对 torch_npu 要求的 PyTorch 版本 |
| 报 `No module named torch_npu` | torch_npu 未装或装错环境 | 检查 pip 装到了哪个 Python |
| 算子报 `NotImplementedError` | CANN 版本过旧，缺算子实现 | 升级 CANN 到支持的版本 |
| 设备不可见 / `no NPU device` | 驱动、固件未装或未加载 | `npu-smi info` 先确认设备 |
| 跑起来精度离谱 | CANN 与 torch_npu 版本混搭 | 全链路版本对齐后重测 |
| 性能远低于预期 | 环境变量（如算力档位）未设 | 核对启动文档中的环境变量 |

**辨析｜易错点：** 版本错配的症状**经常伪装成别的错误**——比如「算子不存在」其实是「CANN 太旧缺算子」，「显存报错」其实是「驱动未就绪导致初始化失败」。所以排查的第一原则永远是：**先确认为什么层级出错，再对症下药**，不要对着表面错误文字打补丁。

## 6 版本匹配的总原则

把整个三角关系压缩成三条铁律，装环境时贴在脑门上：

**铁律一，以官方文档的「版本兼容表」为准**：vllm-ascend 的 Installation 文档会列出「vllm-ascend 版本 → CANN 版本 → torch_npu 版本」的组合。**你不是去发明组合，而是去查组合**。

**铁律二，成套升级，不拆件升级**：升级任何一个组件，其余组件一起升级到配套版本。只升级 torch_npu 而留着旧 CANN，是「半配」状态，比不升级还危险。

**铁律三，环境隔离**：用 conda/venv/容器把昇腾环境与日常开发环境隔离。**昇腾环境「娇气」，最怕被其它环境的依赖污染**——一个隔离的环境，是版本匹配的第一道保险。

**核心要点**：版本匹配不是「懂原理就能推导」的问题，而是「查表」的问题——**你的工作不是判断组合，而是找到官方那份组合表并照着做**。原理告诉你「为什么要匹配」，表格告诉你「匹配成什么样」。

## 7 小结

- **三角锁定**：CANN、PyTorch、torch_npu 三者版本必须成套匹配，torch_npu 是锁死的翻译层。
- **安装次序**：CANN → PyTorch（torch_npu 对应的版本）→ torch_npu → vllm-ascend，逐层推进。
- **验证次序**：`npu-smi info`（硬件）→ 冒烟测试（张量）→ 小模型跑通（推理），逐层递进。
- **症状会伪装**：段错误、算子报错、设备不可见，根因常是版本错配或驱动缺失，先定位层级再处理。
- **三条铁律**：查官方版本表、成套升级、环境隔离——三条做到，版本问题基本绝迹。

在下一节，环境就绪，我们终于可以动手了：**vllm serve 快速启动与在线推理**——一条命令把模型拉起来，看它开口说话。
