## 为什么从容器化开始

上一节我们花了整篇讲版本匹配——CANN、PyTorch、torch_npu 一个都不能错。这个「一个都不能错」恰恰是容器化存在的理由：**把一整套锁死的环境烘焙进镜像，团队任何成员 pull 下来就是同样的环境，不再有「在我机器上是好的」**。昇腾的 Docker 部署还有一个特殊性：NPU 不是普通外设，容器要能「看见」它，必须做**设备映射**。这一篇讲清昇腾镜像的构成、NPU 容器化的关键动作，以及多形态部署的取舍。

## 1 为什么要容器化昇腾环境

昇腾环境「娇气」，恰恰是容器化最大的受益者：

**版本可复现**：CANN/torch_npu/PyTorch 三件套锁进镜像，团队、CI、生产三处环境一致，告别「版本漂移」。

**环境隔离**：不同项目可能需要不同 CANN 版本，容器互不干扰——**不必为了一个项目的升级，污染另一个项目。**

**快速交付**：模型服务以镜像为单位分发，扩容时「拉镜像 → 起容器」即完成，无需逐台机器配环境。

**辨析｜易错点：** 容器化昇腾环境有一个经典误区：**把「容器」当成「虚拟机」**。容器共享宿主内核，NPU 设备要显式挂进去（下节讲）；不是「起了容器就自动有 NPU」。

## 2 昇腾镜像的构成：三层烘焙

一个可用的 vllm-ascend 推理镜像，大致是三层叠加：

**底层：操作系统**。昇腾官方镜像多以 **openEuler**（华为自研 Linux 发行版）或 Ubuntu 为基础，因为 CANN 的官方支持范围覆盖这些系统。

**中层：CANN 运行时**。镜像里内置 AscendCL 运行时、算子库与驱动相关的用户态组件。**注意区分「驱动」与「CANN」**：驱动通常装在宿主机（含内核模块），容器里装的是 CANN 的用户态软件。

**上层：Python 推理环境**。PyTorch + torch_npu + vllm-ascend 及依赖，锁死版本。

<span class="marginnote">为什么驱动在宿主机、CANN 在容器里？因为驱动含<strong>内核模块</strong>，而容器共享宿主内核——内核模块天然在宿主机。<strong>所以「镜像里要不要装驱动」取决于部署方式</strong>：以昇腾官方提供的「带驱动镜像」为基础时驱动已内置；自己拼镜像时通常让容器只装 CANN 用户态，驱动由宿主承担。</span>

### 一个 Dockerfile 的骨架

把「三层烘焙」落到一个 Dockerfile 的骨架（示意，具体以官方镜像为准）：

```dockerfile
FROM quay.io/ascend/cann:8.x        # 底层：CANN 运行时基础镜像
RUN pip install torch torch_npu     # 中层：与 CANN 配套的 PyTorch + torch_npu
RUN pip install vllm vllm-ascend    # 上层：推理引擎与昇腾后端
CMD ["vllm", "serve", "Qwen/Qwen2.5-7B-Instruct"]
```

启动时再通过运行参数挂载设备：

```bash
docker run --device /dev/davinci0 \
  -v /usr/local/Ascend/driver:/usr/local/Ascend/driver \
  -e ASCEND_RT_VISIBLE_DEVICES=0 \
  vllm-ascend:v1
```

**核心要点**：镜像负责「环境」，运行参数负责「挂设备」——**一个管静态，一个管动态**。生产镜像应把环境变量、默认命令固化进镜像，运行侧只留「挂哪张卡」这个最少的动态决策。

## 3 NPU 设备映射：让容器「看见」NPU

容器与 NPU 之间，隔着三道「看见」的关：

**第一关，设备文件**：昇腾通过 `/dev/davinci*`（NPU 设备）与 `/dev/davinci_manager`（管理设备）等设备节点暴露硬件。容器要挂载这些设备文件。

**第二关，驱动组件**：`/usr/local/Ascend/driver` 等驱动相关目录需要挂进容器，用户态程序才能与驱动通信。

**第三关，环境变量与系统库**：`ASCEND_RT_VISIBLE_DEVICES`（指定容器可见的 NPU 编号，类比 CUDA 的 `CUDA_VISIBLE_DEVICES`）、`LD_LIBRARY_PATH` 指向 CANN 库路径，还有 `/etc/ascend_install.info` 之类的配置。

**核心要点**：昇腾容器化的本质，是**「在隔离的文件系统里，显式地重建 NPU 的可见性」**。这三关缺一不可——少挂设备文件，容器里就「没有设备」；少了驱动目录，就「设备不可用」。

## 4 多形态部署：三种典型场景

Docker 化的昇腾推理，落到不同场景有不同形态：

**单机单卡 / 单机多卡**：最常用形态。Atlas 800T A2（8 卡 910B）宿主机上，一个容器占一卡，或多个容器各占一卡，靠 `ASCEND_RT_VISIBLE_DEVICES` 隔离。**一容器一卡**是隔离与易运维的默认选择。

**边缘推理（310P）**：310P 以推理卡形态出现在边缘或一体机，镜像更小、部署更轻，常配 openEuler 精简基础镜像，追求「镜像小、启动快」。

**多机集群**：跨机部署时容器负责「单机环境」，跨机通信走 RoCE 网络。容器编排（如 K8s）负责 NPU 调度——昇腾的 device plugin 把 NPU 作为可调度资源暴露给编排系统。

<span class="marginnote"><strong>容器粒度是架构决策</strong>：一容器一卡，隔离好、故障面小，但卡间通信要走容器间网络；一容器多卡，通信走容器内 HCCS，性能好，但故障影响面大。<strong>多卡并行（张量并行）场景通常用一容器多卡</strong>，让 HCCS 高速互连在容器内生效——这是第 4 篇《张量并行与多卡推理》的性能基础。</span>

## 5 核心对比表：裸机与容器化部署

把两种交付方式摆在同一张表里，取舍一目了然：

| 维度 | 裸机部署 | 容器化部署 |
| --- | --- | --- |
| 环境一致性 | 靠脚本/文档，易漂移 | 镜像锁定，天然一致 |
| 版本冲突 | 难以隔离 | 容器隔离，多版本共存 |
| 环境变量管理 | 手工 export | 镜像内固化 |
| 多卡并行性能 | 原生最优 | 一容器多卡可保持 |
| 交付与扩容 | 逐台配置 | 拉镜像即部署 |
| 排障难度 | 依赖机器状态 | 环境可重建、可复现 |

**核心要点**：容器化的代价是**多一层抽象**（镜像管理、设备映射、网络配置），换来的是**环境可控性与交付一致性**。对「一个版本跑很久」的生产推理服务，这笔交易几乎总是划算——**它把「环境玄学」关进了镜像里。**

### 从镜像到集群：编排的那一步

单机用 `docker run` 足够，多机就轮到编排系统接手：

- 编排系统通过昇腾设备插件把 NPU 暴露为「可调度资源」，容器调度时自动绑定空闲卡；
- 环境变量（`ASCEND_RT_VISIBLE_DEVICES`）由调度器在创建容器时注入，应用无感；
- 多机张量并行时，编排还要保证「同一模型的各卡容器」落在同一拓扑内（同机优先），让 HCCS 生效。

**辨析｜易错点：** 编排层最常见的坑是**「调度到了卡，但没调度好拓扑」**——两卡并行却落在两台机器上，HCCL 跨机通信把并行性能拖垮。多卡并行场景，先确认编排的拓扑亲和（affinity）配置，再谈扩容。

## 6 小结

- **为什么容器化**：昇腾环境版本锁死、易漂移，镜像把「三件套 + 版本」一起锁定交付。
- **镜像三层**：openEuler 底 + CANN 中层 + Python 推理环境上层，层层烘焙。
- **NPU 可见性**：设备文件、驱动目录、环境变量三关，缺一不可——容器要「看见」NPU 是显式动作。
- **多形态**：单卡/多卡用 `ASCEND_RT_VISIBLE_DEVICES` 隔离；310P 边缘形态要轻；多机靠编排调度 NPU。
- **镜像管环境、参数管设备**：Dockerfile 固化静态环境，运行参数挂载动态设备。
- **容器粒度**：一容器一卡隔离好、一容器多卡并行好，多卡并行场景选择后者。
- **编排要管拓扑**：多机并行先确认拓扑亲和，否则跨机通信拖垮性能。
