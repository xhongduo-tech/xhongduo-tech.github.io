## 为什么从概览开始

「从极限到大模型」这条线走到这里，我们已经见过 CUDA 生态里完整的推理引擎：vLLM 在高性能 GPU 上如何把连续批处理、PagedAttention、投机解码织成一台高吞吐的机器。

但大模型的算力从来不止 NVIDIA 一家。**华为昇腾（Ascend）NPU 是国产算力里部署最广的路线之一**，而要在昇腾上跑 vLLM，靠的不是「魔法」，而是一层名字就叫 `vllm-ascend` 的适配。

这一篇是整个专题的地图：先回答「这是什么、解决了什么、能干什么、在哪查」，再往下每一篇才各自展开一块砖。**先看全貌，再抠细节**——这是学习任何一套新栈的第一步。

## 1 vllm-ascend 是什么

**vllm-ascend**：vLLM 的**官方昇腾后端（Ascend backend）**，由 vllm-project 与华为昇腾社区共同维护，托管在 github.com/vllm-project/vllm-ascend。它的使命可以一句话概括：**让「同一份 vLLM 代码」在昇腾 NPU 上也能以接近原生 CUDA 的质量运行**。

理解它的定位，要先分清三层：

**vLLM 本体**：与硬件无关的推理引擎——调度器、KV Cache 管理器、连续批处理、HTTP 服务、OpenAI 兼容接口。这些代码关心「算法与调度」，不关心「在什么芯片上算」。

**torch_npu**：PyTorch 的昇腾设备插件（我们在《昇腾 NPU 硬件与软件栈》里讲过）。它把 `torch.Tensor` 接到昇腾设备上，让「张量能在 npu 上算」成为可能。

**vllm-ascend**：站在 vLLM 与 torch_npu 中间，补齐 vLLM 特有的**昇腾算力缺口**——分页注意力内核、融合算子、算子注册、图编译适配。它把 vLLM 的「我要一个 PagedAttention 内核」翻译成「昇腾上这个算子怎么实现」。

<span class="marginnote">一个常见误解：以为 vllm-ascend 是「重写了一个 vLLM」。恰恰相反，它<strong>几乎不碰 vLLM 的调度逻辑</strong>，只替换「在 NPU 上怎么执行」这一层。<strong>调度的成熟度继承自 vLLM，硬件适配度由 vllm-ascend 提供</strong>——这正是「可插拔后端」架构的价值，也是第 2 篇《vLLM 硬件可插拔架构与 Ascend 后端》要展开的主题。</span>

## 2 核心特性：原生之外的能力

vllm-ascend 提供的不是「降级版 vLLM」，而是一套在昇腾上完整的推理能力。与 CUDA 后端对齐的核心特性包括：

**PagedAttention 昇腾实现**：KV Cache 分页管理在昇腾上的落地，块表驻留 L2、分页取数配合 AI Core 搬运（第 2 篇《PagedAttention 在昇腾上的实现》）。

**连续批处理与调度**：调度器逻辑复用 vLLM 本体，昇腾端保证算子与内核支持动态批次。

**前缀缓存、Chunked Prefill、投机解码**：三大推理特性在昇腾上都有对应实现（第 3 篇逐一展开），只是底层内核换成昇腾版。

**量化与精度策略**：BF16 主推、INT8 量化支持，配合昇腾的整数算力档位（第 3 篇《FP16/BF16 与 INT8 量化精度策略》）。

**多模态与 Embedding**：视觉塔算子覆盖与 `/embeddings` 向量化接口（第 3 篇《多模态大模型与 Embedding 模型推理支持》）。

<span class="marginnote"><strong>读版本说明的姿势</strong>：vllm-ascend 的特性覆盖是<strong>随版本滚动扩大的</strong>——同一特性不同版本支持程度可能不同。看文档时认准「你装的那个版本」对应的支持矩阵，别拿最新版文档描述旧版行为。</span>

## 3 支持矩阵：先查表再动手

**支持矩阵（support matrix）**：vllm-ascend 官方文档里一张随版本维护的表，列明三件事——**支持哪些模型、支持哪些精度、支持哪些特性**。动手之前先查它，是昇腾部署的第一条纪律。

模型维度：以主流开源系列为主（Qwen、Llama、DeepSeek、ChatGLM、Mixtral 等）。每个系列的支持程度受算子覆盖影响：模型里某个算子昇腾没有实现，整模型就退回「不支持」。

精度维度：BF16/FP16 为基础档，INT8 等量化方式随版本与模型而变。昇腾 910B 没有 FP8 计算单元，所以文档里的精度矩阵不会出现 FP8——这是硬件决定的边界。

特性维度：PagedAttention、前缀缓存、张量并行等是否可用，常与模型、精度绑定（如「某模型支持 TP=8，另一模型只支持 TP=2」）。

**核心要点**：支持矩阵不是「最好能看」的参考，而是**部署前必查的约束**。选模型先查矩阵，再查显存，再动手——顺序错了，最典型的失败就是「模型加载成功，跑起来某个算子报不支持」。

## 4 核心对比表：vllm-ascend 与 CUDA 后端

这一篇是纯概念主题，用一张对比表把「昇腾后端 vs 原生 CUDA 后端」的差异钉清楚：

| 维度 | CUDA 后端 | vllm-ascend 后端 |
| --- | --- | --- |
| 设备插件 | 无（原生支持） | torch_npu |
| 底层运行库 | CUDA Runtime / cuDNN / NCCL | AscendCL / CANN 算子库 / HCCL |
| 内核来源 | vLLM 自带 CUDA 内核 | vllm-ascend 的 `csrc/` 昇腾内核 |
| 集合通信 | NCCL | HCCL |
| 图编译 | 轻量 JIT | CANN ATC/GE（首启编译时间更长） |
| 代码改动 | 无 | 仅 `pip install vllm-ascend` |
| 性能天花板 | 由 NVIDIA 硬件决定 | 由昇腾 AI Core 决定 |

**辨析｜易错点：** 这张表里最容易误读的是「代码改动=无」。**你的推理代码确实不用改**，但「不用改代码」不等于「不用管环境」——CANN、torch_npu、PyTorch 三者版本必须严格匹配（下一篇就讲）。改代码的负担换成了配环境的负担，这是昇腾路线与 CUDA 路线的本质差别。

## 5 运行路径：从安装到一次推理

把整个专题的脉络放进一张运行路径图，你就知道每一篇在整条链路的哪一环：

```
pip install vllm-ascend（第1篇：环境安装与版本匹配）
        ↓
vllm serve 启动（第1篇：快速启动与在线推理）
        ↓ 检查模型是否在支持矩阵里
模型加载 → 图编译 → KV Cache 初始化 → 调度器上线 → HTTP 服务
（第1篇 支持矩阵）（第2篇 ATC）（第2篇 PagedAttention）（第3篇 连续批处理）
        ↓
一次请求：连续批处理 + 前缀缓存 + Chunked Prefill + 投机解码（第3篇）
        ↓
吞吐不达标：张量并行 / 专家并行 / 显存优化 / msprof 剖析（第4篇）
```

**这条路径就是本专题的目录**。第 1 篇解决「怎么装、怎么跑通」，第 2 篇解决「昇腾上算子与编译是怎么工作的」，第 3 篇解决「推理特性在昇腾上怎么用」，第 4 篇解决「多卡与性能怎么调」。

### 一窥全豹：最小启动示例

纸上谈兵不如跑一次。在环境就绪的昇腾机器上，最小启动只需要两条命令：

```bash
pip install vllm-ascend
vllm serve Qwen/Qwen2.5-7B-Instruct --dtype bfloat16
```

第二条命令敲下去的瞬间，本专题后面所有内容——算子、调度、显存、并行——就已经全部悄悄启动了。**把这当作本专题的「全览触发器」**：读到任何一篇想不起它是干嘛的，就回看这条命令里它被藏在哪一环。

**读完这一篇，你手里的地图已经成形，剩下的每一篇都是往地图里填细节。**

## 6 小结

- **定位**：vllm-ascend 是 vLLM 的官方昇腾后端，负责「在 NPU 上怎么执行」，调度逻辑继承 vLLM 本体。
- **分工**：vLLM 管算法与调度、torch_npu 管张量设备、vllm-ascend 管昇腾算子与内核——三者各司其职。
- **特性**：PagedAttention、连续批处理、前缀缓存、量化、投机解码、多模态等在昇腾上都有对应实现。
- **支持矩阵**：模型、精度、特性三个维度随版本滚动维护，部署前必查。
- **与 CUDA 对比**：代码不改、环境要配——CANN/torch_npu/PyTorch 版本匹配是昇腾路线的第一道门槛。

在下一节，我们将扎进这道门槛本身：**环境安装与版本匹配**——CANN、PyTorch、torch_npu 三者怎么配对，装错了会踩哪些坑。
