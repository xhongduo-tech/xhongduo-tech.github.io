## 为什么从硬件开始

上一篇我们站在「插件使用者」的视角看了 vllm-ascend：装一个包、起一个服务，代码不变。但一个推理引擎的性能天花板，从来不是由框架代码决定的，而是由**芯片的算力、存储层次与数据通路**决定的。vLLM 的 PagedAttention 为什么在昇腾上要重写？FlashAttention 为什么能快几个量级？答案都要回到 AI Core 的结构里找。这一篇把昇腾硬件与软件栈的骨架立起来，之后每一篇提到「AI Core」「L2 Cache」「HCCL」「CANN」时，你都有清晰的地图。

## 1 达芬奇架构与 AI Core

昇腾 NPU 的芯片微架构统称**达芬奇（Da Vinci）架构**，其最小计算单元是 **AI Core（AI 计算核心）**。与 CPU 的「通用但偏科」、GPU 的「大规模 SIMT」都不同，昇腾的 AI Core 是一个**异构三单元**设计：

**立方单元（Cube Unit）**：专做矩阵乘加（MMA）。一次指令可完成一个 $16 \times 16 \times 16$ 的矩阵乘累加，是 GEMM（通用矩阵乘法）的主力，对应 GPU 的张量核。矩阵乘是大模型推理里算力消耗的绝对主体，所以立方单元的设计直接决定算力峰值。

**向量单元（Vector Unit）**：逐元素/逐向量运算，负责激活函数（ReLU、GELU）、归一化（RMSNorm）、逐元素加乘等。它的运算位宽比立方单元宽，适合「算得不多但每步都要碰」的算子。

**标量单元（Scalar Unit）**：处理地址计算、循环控制、标量运算，相当于核内的「CPU」，负责协调前面两个单元的取数与运算节奏。

三个单元共享一套**存储层次**：每个 AI Core 内有紧贴运算单元的 L0 缓冲（L0A/L0B/L0C 分别服务立方单元的 A/B/C 矩阵）与统一缓冲（Unified Buffer，服务向量单元）；多个 AI Core 共享芯片级的 **L2 Cache**；最外层是大容量 **HBM 高带宽内存**。<span class="marginnote">把 Cube / Vector / Scalar 三个单元想象成流水线上的三台机器：Scalar 负责发号施令与搬运，Cube 负责最重的矩阵活，Vector 负责轻量的逐元素活。算子性能好坏，很大程度上取决于「数据是否喂得饱 Cube」——这就是后面 FlashAttention 优化要反复处理的主题。</span>

## 2 产品形态：910 系列与 310 系列

芯片与「你能买到的卡」是两回事。昇腾通过**产品化封装**把芯片变成服务器里的加速单元，vllm-ascend 主要面对两条产品线：

### 910 系列：训练/推理一体

910B 是当前大规模推理部署的主力。以公开信息为准，910B 的常见规格如下：

**910B3** 单卡约 **313 TFLOPS FP16/BF16**、**64 GB HBM2e**、实测带宽约 1.5 TB/s，采用 7nm 制程，典型形态是 Atlas 800T A2 服务器——机箱里 8 张 910B 通过 **HCCS 高速互连** 全互联成一张「八卡网」，跨机再走 RoCE 网络。<span class="marginnote">910B 家族内部有 B1/B2/B3/B4 等市场俗称，算力与显存梯度不同（B4 为 32 GB、约 280 TFLOPS；B1/B2 为 64 GB、约 376–414 TFLOPS）。这些并非华为官方命名，选购时要以具体配置单为准。另一个要点：910B 没有 FP8 计算单元，高精度部署更吃显存。</span>

### 310 系列：推理专用

310P 面向纯推理场景，显存分 8 / 16 / 24 GB 等多档，功耗与体积远小于 910，常以推理加速卡形态出现在边缘或专用推理服务器上。它的算力规模小，但推理吞吐/功耗比好——回答「小模型高频请求」这类问题时，310P 往往比 910B 更划算。

**辨析｜易错点：** 显存 64 GB 是「卡上能放多少模型权重与 KV Cache」的上限，但不是「模型服务并发上限」。同一个 7B 模型，同样的 64 GB 显存，用连续批处理 + PagedAttention 可能扛住几百路并发，用朴素的一次性预分配可能只够几十路——**显存管理方式决定了同样硬件的实际吞吐**，这正是第 3 篇的重点。

## 3 CANN：昇腾的计算架构

芯片之上是软件。**CANN（Compute Architecture for Neural Networks）** 是昇腾的软件栈总称，对标 NVIDIA 的 CUDA，从下到上大致四层：

**AscendCL（ACL）**：运行时抽象层，负责设备管理、显存分配、流（stream）同步、内核启动——对应 CUDA Runtime 的角色。

**算子库**：预编译的高性能算子集合（对标 cuBLAS / cuDNN），包含 GEMM、卷积、FlashAttention 融合算子等，应用层多数时候不必手写算子。

**图引擎与编译器（GE / ATC）**：把计算图做算子融合、格式转换、内存规划后编译为离线模型（`.om`）。第 2 篇《ATC 图编译与算子图优化》会专门展开。

**算子开发框架（Ascend C / TBE）**：让开发者用类 C++ 的 **Ascend C** 语言编写自定义算子，编译到 AI Core 上运行——vllm-ascend 的自定义融合算子正是这样写的。

<span class="marginnote">一句话记住 CANN 的分层：<strong>AscendCL 管「怎么启动」、算子库管「现成的活」、GE/ATC 管「图怎么优化」、Ascend C 管「没有的活自己写」</strong>。这四层与 CUDA Runtime、cuBLAS、nvcc/JIT、CUDA C 一一对应。</span>

### HCCS 互联与多卡拓扑

910B 多卡部署的物理基础，是片间互联 **HCCS（Huawei Cache Coherence System）**。与 GPU 平台常见「PCIe 交换 + NVLink」的组合不同，910B 的 8 卡通过 HCCS 实现机内全互联，片间带宽与延迟都显著优于 PCIe 层级。这带来三个直接后果：

**张量并行友好**：机内 8 卡做张量并行时，每层的 AllReduce 通信走 HCCS，带宽充足，通信占比可控（第 4 篇《张量并行与多卡推理》会量化这一点）。

**拓扑简单**：8 卡全互联意味着「任意两卡通信路径等价」，不像某些平台要区分「同交换机 / 跨交换机」，调度与负载均衡更省心。

**跨机是分水岭**：HCCS 是机内的；跨机通信走 RoCE 网络，延迟与带宽都差一个量级。所以「机内用 HCCS 亲密并行，跨机用数据并行 / 专家并行」是昇腾多机部署的默认分层。

### 310P 与推理场景的取舍

310P 是推理专用卡：显存分 8 / 16 / 24 GB 档位，算力远小于 910B，但功耗与成本也低。它的典型画像：

- **小模型高并发**：Embedding、7B 级对话模型，单卡即可支撑，靠连续批处理吃满吞吐。
- **边缘与私有化**：体积小、功耗低，适合机房边缘或一体机形态。

选型时算的账很简单：**目标模型的权重 + 目标上下文的 KV Cache 能否塞进一张 310P**。塞得进就用 310P（省钱省电），塞不进就上 910B。这条线就是「容量规划」的起点，第 4 篇《显存优化与长序列推理内存管理》会给出完整的预算公式。

## 4 torch_npu：PyTorch 与昇腾之间的桥

有了 CANN，为什么还需要 `torch_npu`？因为 PyTorch 的应用层代码只认 `torch.Tensor` 与算子分发机制，并不认识 AscendCL。`torch_npu` 就是那个**把 PyTorch 接到 CANN 上的设备插件**：

**设备注册**：向 PyTorch 注册一种新的设备类型 `npu`，于是 `tensor.npu()`、`tensor.to('npu')` 合法可用。

**算子分发**：PyTorch 的每个 ATen 算子（`add`、`matmul`、`layer_norm`）都通过 dispatch 机制选择实现。`torch_npu` 为 `npu` 设备提供这些算子的实现，内部调用 CANN 算子库或手写内核，用户无感。

**集合通信**：多卡场景下 `torch_npu` 封装 **HCCL（Huawei Collective Communication Library）**，提供 `all_reduce`、`all_gather` 等接口，对应 CUDA 生态里的 NCCL。

vllm-ascend 就构建在这座桥上：**它假定 `torch_npu` 已把「张量能在 npu 上算」这件事做好，自己专注补 vLLM 特有的算力缺口**（PagedAttention 内核、量化内核等）。

## 5 公式解析：计算强度与存储墙

硬件结构决定算法设计，而「为什么算子要重新设计」可以用一条公式说清。定义一个算子的**计算强度（arithmetic intensity）**：

$$
I = \frac{\text{计算量（FLOPs）}}{\text{访存量（字节）}}
$$

对一次 $M \times N \times K$ 的矩阵乘，计算量约 $2MNK$，访存量约 $MN + MK + KN$ 字节（读 A、读 B、写 C），于是：

$$
I_{\text{GEMM}} \approx \frac{2MNK}{MN + MK + KN}
$$

当 $M, N, K$ 都很大时，$I_{\text{GEMM}} \approx K$——计算强度近似等于「每个输出元素对应的乘加次数」。对 910B 这类 AI Core，立方单元峰值算力固定，于是产生两个判读分支：

**访存受限**：当 $I$ 小于「算力峰值 ÷ 带宽」这个**机器平衡点（ridge point）**时，计算在等数据，利用率上不去——这类算子该融合、该优化搬运（FlashAttention 正是干这个的，见第 2 篇）。

**算力受限**：当 $I$ 大于平衡点时，数据喂得饱，算力是瓶颈——这类算子靠库算子与张量指令优化即可，不必大改。

**为什么 PagedAttention 要重写**：分页访问让 KV 取数变得「不连续、有额外查表」，直接拉低有效计算强度，把本可算力受限的注意力拖进访存受限区。昇腾版内核做的，正是把这段被分页「浪费掉」的计算强度抢回来——**这就是「硬件结构决定算法设计」在本专题的第一个实例**。

## 6 小结

- **AI Core 三单元**：Cube（矩阵乘）、Vector（逐元素）、Scalar（协调），共享 L0/UB/L2/HBM 存储层次。
- **两条产品线**：910B（训练/推理一体、大显存）与 310P（推理专用、低功耗），按容量规划选择。
- **CANN 四层**：AscendCL（怎么启动）、算子库（现成的活）、GE/ATC（图优化）、Ascend C（自己写）。
- **HCCS 机内、RoCE 跨机**：机内亲密并行、跨机数据并行/专家并行，是昇腾多机部署的默认分层。
- **计算强度**：$I = \text{FLOPs} / \text{字节}$，低于平衡点即访存受限——算子重写的第一性原理。

在下一节，我们将离开硬件与栈的「骨架」，进入动手前的最后一环：**环境安装与版本匹配**——把 CANN、PyTorch、torch_npu 这套三角组合装对、装稳。
