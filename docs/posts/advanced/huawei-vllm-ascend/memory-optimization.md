## 为什么从显存优化开始

推理服务的并发上限，几乎总是**由显存决定**，而不是由算力决定。64 GB 的卡，放完模型权重后剩多少给 KV Cache，直接决定能同时服务多少序列。这一篇把显存账单算清楚：**每一块显存花在哪、哪些能省、长序列场景怎么撑**。理解了显存，你就理解了为什么「同样的卡，有人服务 30 并发，有人服务 300 并发」。

## 1 显存花在哪：一张账单

一块 64 GB 的昇腾 NPU 显存，运行一个 7B 模型时大致这样分配：

**模型权重**：BF16 的 7B 模型约 14 GB，加上优化器不需要（推理无梯度），权重是**固定开销**。

**KV Cache**：随并发与序列长度动态增长，是**最大的可变开销**（第 2 篇算过：单序列每 token 几十 KiB，几千 token 就几百 MiB）。

**激活值（activation）**：单次前向的中间张量，与批大小、序列长度相关，通常在 GB 级但远小于 KV Cache。

**运行时开销**：CANN 上下文、算子缓冲、HCCL 通信缓冲等，几十到几百 MiB 不等。

**核心要点**：**权重是「买定离手」，KV Cache 才是「日常开销」**。显存优化的大头几乎都花在 KV Cache 上——它既是最大的可变项，也是最有优化空间的一项。

## 2 KV Cache 优化三板斧

针对 KV Cache，有三个从「调度」到「数值」的优化手段：

**第一板斧，分页（PagedAttention）**：消除预留浪费，让 KV 按需分配。这是**结构性**优化，收益是数量级的，已在第 2 篇展开。

**第二板斧，KV Cache 量化**：把 KV 用 INT8 存（甚至更低），每 token 的 KV 字节数直接减半。代价是注意力计算的数值精度下降，需要评估。这是**数值**优化，收益接近减半。

**第三板斧，KV 复用（前缀缓存）**：共享前缀的 KV 不重复存、不重复算。这是**语义**优化，靠请求模式获利。<span class="marginnote">三板斧的叠加效果接近「相乘」：分页消除浪费、量化砍一半字节、复用砍掉重复——三者同时上，同样的显存能撑的并发可以翻好几倍。<strong>先上结构性的分页，再谈量化和复用</strong>，顺序别反。</span>

## 3 长序列推理的显存策略

当序列越来越长（几万 token），KV Cache 按 $O(L)$ 增长，会迅速吃光显存。长序列场景需要额外的策略：

**滑动窗口注意力（sliding window attention）**：每个位置只关注最近 $W$ 个位置，KV Cache 只保留窗口内的部分，**显存从 $O(L)$ 变成 $O(W)$**（常数级）。代价是模型看不到窗口外的历史——但许多模型的注意力天然偏重近邻。

**上下文压缩**：把已生成的历史压缩成摘要 token 再继续，相当于「记忆压缩」。实现复杂，但能把「无限长」对话压进有限显存。

**选择性保留**：结合稀疏注意力，只保留关键位置的 KV，丢弃次要位置。需要判断「哪些位置值得留」。

**辨析｜易错点：** 滑动窗口**不是免费**的。它牺牲的是「长程依赖」——如果你的任务需要模型反复引用几千 token 前的信息（如长文档问答），窗口太小会明显掉质量。**用窗口换显存前，先确认任务的注意力距离**，别把「显存优化」变成「质量滑坡」。

## 4 公式解析：显存预算分解

把显存优化数字化。设卡上可用显存为 $M_{\text{total}}$，权重占用 $M_w$，运行时开销 $M_{\text{rt}}$，则留给 KV Cache 的预算：

$$
M_{\text{kv}} = M_{\text{total}} - M_w - M_{\text{rt}}
$$

单个序列占用的 KV 由序列长度 $L$ 与每 token KV 字节 $b$ 决定（第 2 篇的公式）：

$$
M_{\text{seq}} = L \times b
$$

于是理论并发上限：

$$
C_{\max} \approx \frac{M_{\text{kv}}}{M_{\text{seq}}} = \frac{M_{\text{total}} - M_w - M_{\text{rt}}}{L \cdot b}
$$

**直觉**：想提高并发，四条路——**增大总显存（换卡）、减小权重（量化权重）、减小每 token KV（KV 量化）、减小序列长度预算（窗口/压缩）**。任何一条路的收益都能沿公式直接估算。<span class="marginnote">用这条公式做「容量规划」比拍脑袋可靠得多：<strong>知道模型和卡，就能先估出理论并发上限</strong>，再决定要不要上 KV 量化、要不要开窗口。公式给出的上限是「天花板」，实际还要扣掉分页碎片与调度余量，但作为决策起点已经足够。</span>

## 5 昇腾上的实践要点与易错点

**显存水位监控**：昇腾上用 `npu-smi` 查看显存占用。压测时盯水位，识别「是不是显存先于算力耗尽」。

**`gpu-memory-utilization` 的边界**：这个参数控制引擎「最多用多少」，但留太少的余量会导致运行时（HCCL 缓冲、算子临时空间）分配失败。常规留 5%–10% 余量。

**易错点一，忽略激活峰值**：长序列 + 大批下，激活值可能瞬时暴涨，与 KV 抢显存。出现「显存明明有预算却 OOM」时，查激活峰值，而不是怀疑 KV 管理。

**易错点二，量化的精度陷阱**：KV Cache 量化后，**长序列的误差会累积**——越长的上下文，量化误差越可能显现。长序列部署 KV 量化前，务必做长上下文质量评测。

**易错点三，把「显存大」当「无限」**：64 GB 不是免死金牌，长上下文 + 高并发组合下显存依旧会爆。**容量规划是部署前必做的一步**，公式算完再定服务规格。

### 从 30 并发到 300 并发：一个优化叙事

把本节的工具串成一个完整故事。假设一块 64 GB 卡跑 7B 模型，一开始用「每序列预留整段显存」的朴素方式，KV Cache 预留按最大长度算，实际并发可能只有 30 上下。

**第一步，分页**：换成 PagedAttention，预留浪费消失，KV 按实际长度分配，并发直接跳到 80–100。

**第二步，KV 量化**：把 KV 从 BF16 压到 INT8，每 token 字节减半，同样的 KV 预算能服务近两倍的序列，并发跳到 150–200。

**第三步，前缀缓存**：如果请求共享系统提示，前缀 KV 不再重复存，多轮与共享场景的显存压力骤降，并发再上一个台阶，逼近 300。

这条叙事不是虚构的「魔法」，每一步都能用第 2 篇与本节预算公式算出来：**`并发 ≈ (总显存 − 权重 − 运行时) / (每 token KV × 平均序列长)`**。每一次优化，都是在缩小分母或放大分子。**记不住细节没关系，记住「显存优化的终点是让公式里的分母变小」就够了。**

### 一张图记住显存决策链

把本节的显存决策压缩成一条「看到问题 → 选手段」的链：

```
显存不够 / 并发太低？
  ├─ 权重占太多 → 权重量化 / 换更大显存的卡
  ├─ KV Cache 占太多 → 分页（结构性）→ KV 量化（数值性）→ 前缀复用（语义性）
  ├─ 序列太长 → 滑动窗口 / 上下文压缩
  └─ 激活峰值 → 降批大小 / 降最大序列长
```

**核心要点**：显存问题先**定位是「哪一块」超标**（权重、KV、序列长度、激活），再选对应手段——**不要一上来就全面量化**。大多数场景，KV Cache 才是最大头，优先级是「分页 → 量化 KV → 复用」。

## 6 小结

- **显存账单**：权重固定、KV Cache 最大且可变、激活与运行时小但存在——优化大头在 KV Cache。
- **三板斧**：分页（结构性）、KV 量化（数值性）、前缀复用（语义性），叠加收益近相乘。
- **长序列策略**：滑动窗口把 KV 从 $O(L)$ 压到 $O(W)$，窗口内上下文仍是主流手段。
- **定位先行**：先看清「哪一块超标」再优化，别一上来就全面量化——KV 才是最大头。
