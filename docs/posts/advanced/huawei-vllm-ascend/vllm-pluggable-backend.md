## 为什么从可插拔架构开始

昇腾能跑 vLLM，最表层的原因是「有人写了 vllm-ascend」；最深层的原因是 vLLM 设计了一个**硬件可插拔（pluggable hardware backend）**的架构，让第三方硬件不必 fork 整个 vLLM 就能接入。这不是一个「要不要」的加分设计，而是 vLLM 从单硬件走向多硬件生态的**分水岭**。这一篇讲清可插拔架构的几个抽象——平台、设备能力、算子分发、执行器——以及昇腾后端如何利用它们「插」进去。

## 1 动机：为什么要可插拔

在可插拔架构之前，vLLM 里到处是 `if torch.cuda.is_available()` 之类的硬编码，硬件适配散落在核心代码各处——每次接一块新硬件都要改核心、fork 主仓库，下游维护成本爆炸。

可插拔的动机是三个「别」：

**别改核心**：接新硬件不动 vLLM 的调度与内存管理核心，只新增「这块硬件怎么执行」的实现。

**别 fork**：硬件厂商不必维护自己的 vLLM 分支——主仓库更新，硬件适配依然跟着走。

**别散落**：把散落在各处的 `if cuda` 分支收敛成统一抽象，核心代码只面对抽象接口。

**核心要点**：可插拔架构的价值是**「接缝」**——把「与硬件无关」与「与硬件相关」切开，前者进核心、后者进插件，中间用抽象接口缝起来。

## 2 平台抽象：认识你的硬件

可插拔架构的第一个抽象是**平台（Platform）**：一块硬件在 vLLM 眼中的「身份卡」，回答「我是谁、我能做什么」。

每个平台对象携带硬件的基本信息：设备类型、设备数量、显存规模、算力能力。核心调度器通过平台接口询问「这个张量在哪、能不能合并」之类的问题，而不是自己判断。

**设备能力（DeviceCapability）**：平台携带的一张「能力清单」——支持哪些精度（BF16？FP16？）、支持哪种图编译方式、是否支持某些特性。**调度器与图编译据此决定「能不能开某个特性」**。

昇腾的 `AscendPlatform` 就实现这套接口：上报「这是 npu 设备、支持 BF16、图编译走 CANN」，核心据此调度。

<span class="marginnote"><strong>为什么能力要问而不是猜</strong>：调度器要决定「这个模型能不能用 INT8 量化」，直接问平台的 DeviceCapability 比写死 `if 厂商==NVIDIA` 干净得多。<strong>平台抽象把「硬件知识」从核心代码里抽出来，装进插件</strong>——核心只问，不猜。</span>

## 3 算子分发：运行时选择实现

平台解决了「认识硬件」，**算子分发（operator dispatch）**解决「在硬件上怎么算」——同一个算子，在不同硬件上跑不同的实现。

PyTorch 本身有 dispatch 机制：`torch.add` 会根据设备类型选择 `add_cpu`、`add_cuda` 等实现。vLLM 在其之上再抽象一层**自定义算子层**：vLLM 里那些为推理特制的算子（PagedAttention、融合归一化等）同样按设备分发。

昇腾后端的做法是：**注册 `npu` 设备对应的算子实现**。vLLM 前向跑到 PagedAttention 时，分发机制把它导向昇腾的 Ascend C 内核（第 2 篇《PagedAttention 在昇腾上的实现》），上层代码无感。

**核心要点**：算子分发让「同一份模型代码在不同硬件上跑不同内核」成为可能——**模型的图结构不变，变的只是每个节点背后的实现**。

## 4 执行器：硬件如何执行一桶 token

第三个抽象是**执行器（executor）**：vLLM 把「一次调度决策」交给执行器落地——这一批序列、这些 token，在硬件上怎么并行、怎么跑完。

**单卡执行器**：一块设备上，把模型前向按批次跑起来。昇腾单卡执行器把图喂给 CANN，跑昇腾算子。

**多卡执行器**：张量并行/专家并行的实现载体。TP 的执行器负责「切分 + 集合通信」，昇腾端走 HCCL（第 4 篇《张量并行与多卡推理》）。

执行器是硬件最「重」的接缝——并行策略、图编译、集合通信都在这里落地。可插拔架构让每块硬件提供自己的执行器，核心调度器只发「命令」不关心「执行细节」。

<span class="marginnote">把几个抽象串起来记：<strong>Platform 回答「硬件是谁」、算子分发回答「每个算子怎么算」、Executor 回答「一批 token 怎么跑完」</strong>。<strong>核心调度器站在三者之上，只做与硬件无关的决策</strong>——这就是「可插拔」三个字的全部含义。</span>

## 5 插件机制：装包即插即用

抽象定好了，最后的问题是「昇腾后端怎么被 vLLM 发现」。答案在 **Python 插件机制**（vLLM 的可插拔后端通过插件注册表实现）：

**装包即注册**：`pip install vllm-ascend` 后，它通过 Python 包入口把 `AscendPlatform` 注册进 vLLM 的插件系统。

**启动时发现**：vLLM 启动时扫描注册表，遇到 `npu` 设备就实例化昇腾平台、挂载昇腾算子与执行器。

**用户无感**：用户侧只多了一句「装了个包」，其余一切自动。

**辨析｜易错点：** 「装包即插即用」是昇腾路线的体验，但别忘了它有个前提——**vllm-ascend 的版本必须与 vLLM 主版本兼容**（第 1 篇《环境安装与版本匹配》）。插件机制解决「怎么被发现」，不解决「版本对不对」。

### 一次注册的代码视角

昇腾后端「装包即注册」落到代码上，是一个很小的入口（示意）：

```python
# vllm-ascend 的插件入口（示意）
def _register_ascend_platform():
    vllm.platforms.register("npu", AscendPlatform)
    register_npu_ops()   # 挂载昇腾算子实现
    register_ascend_executor()   # 挂载昇腾执行器
```

vLLM 启动时检测到 `npu` 设备，就调用这个入口，把平台、算子、执行器一次性接进引擎。**这个入口虽小，却是整个可插拔架构的「插头」**——昇腾后端与 vLLM 的全部对接，就浓缩在这一段注册里。

## 6 核心对比表：可插拔前后

用一张表对比「可插拔」给硬件适配带来的变化：

| 维度 | 硬编码时代 | 可插拔时代 |
| --- | --- | --- |
| 接新硬件 | 改核心代码、fork 主仓库 | 写插件、装包即用 |
| 硬件知识 | 散落在 `if cuda` 各处 | 收敛进 Platform/DeviceCapability |
| 算子实现 | 核心里堆判断 | 按设备分发，各插各的实现 |
| 并行策略 | 核心硬编码 | Executor 提供，核心只调度 |
| 上游更新 | fork 后难跟随 | 插件跟着主仓库走 |
| 厂商维护 | 高成本 | 低成本的「插件模式」 |

**核心要点**：可插拔架构把「接一块硬件」从**改造工程**变成**插件工程**——**不是「改 vLLM 支持昇腾」，而是「写一个昇腾插件塞进 vLLM」**。这既让 vLLM 生态更广，也让昇腾后端更轻。

## 7 小结

- **动机**：别改核心、别 fork、别散落——用抽象接缝切开「硬件无关」与「硬件相关」。
- **Platform / DeviceCapability**：硬件身份卡与能力清单，核心只问不猜。
- **算子分发**：同一个算子按设备选实现，模型图不变、实现变。
- **Executor**：一桶 token 在硬件上怎么并行跑完，多卡并行在此落地。
- **插件机制**：装包即注册，vLLM 启动时自动发现昇腾后端——用户侧只多一句安装。
- **版本前提**：插件机制解决「怎么被发现」，不解决「版本对不对」——版本兼容仍是前提。
- **本质**：可插拔让「接硬件」从改造工程变成插件工程，这是昇腾能轻松接入 vLLM 的架构原因。

在下一节，我们钻进那个「插件」的肚子里：**vllm_ascend 包结构**——平台层、算子层、执行器在代码里到底是什么样的。那里你将会看到，可插拔架构的三个抽象如何落成真实目录。
