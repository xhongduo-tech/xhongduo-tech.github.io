## 为什么从包结构开始

上一篇我们讲了可插拔架构的抽象——平台、算子分发、执行器。这些抽象是「图纸」，而 `vllm_ascend` 包里的目录结构是「实物」。**读懂一个开源项目最快的方式，就是读懂它的目录怎么切**——目录的划分，就是作者对「这个后端由哪几块拼成」的回答。这一篇把 `vllm_ascend/` 包拆开：每一层放什么、跟 vLLM 哪个抽象对应、为什么这样放。

## 1 包的三层骨架

`vllm_ascend` 包整体是一个三层结构，与可插拔架构的三个抽象一一对应：

**平台层**：回答「昇腾是什么硬件」。实现 `AscendPlatform`，注册 npu 设备、上报能力、接管设备初始化。对应上一节的「Platform / DeviceCapability」。

**算子层**：回答「昇腾上每个算子怎么算」。把 PagedAttention、融合算子、量化内核等昇腾实现注册进 vLLM 的算子分发。对应「算子分发」。

**执行与编译层**：回答「一批 token 在昇腾上怎么跑完」。实现昇腾的图编译路径、执行器与集合通信适配。对应「Executor」。

**核心要点**：包的目录划分**不是随意的功能堆放**，而是「可插拔抽象」在代码里的落地——**看到每一层，就知道它对应 vLLM 的哪个接缝**。

### 一张目录树

vllm_ascend 包的目录大致长这样（示意，随版本演化）：

```
vllm_ascend/
├── platform/        # 平台层：AscendPlatform、设备注册
├── ops/             # 算子层：PagedAttention、融合、量化内核
├── executor/        # 执行层：单卡/多卡执行、HCCL 通信
├── compilation/     # 编译层：图编译与 ATC 适配
├── csrc/            # 原生内核源码（Ascend C / C++）
└── _C/              # 编译产物（Python 扩展）
```

**这张树就是上一节「可插拔抽象」的落点**——每个目录名都对应一个抽象职责，读到目录名就知道它在 vLLM 里扮演什么。

## 2 平台层：设备身份与初始化

平台层是包的最顶层，负责「让 vLLM 认出昇腾」：

**设备注册**：向 vLLM 声明「这里有一种设备叫 npu」，让 `torch.npu`、`ASCEND_RT_VISIBLE_DEVICES` 等被正确理解。

**能力上报**：实现 DeviceCapability——支持哪些精度、图编译走哪条路、支持哪些特性，供调度器查询。

**环境初始化**：设备上下文创建、环境变量校验、CANN 运行时启动，是「启动时发生什么」的第一步。

<span class="marginnote">平台层在包里的体量通常<strong>很小、但很关键</strong>——它决定「vLLM 认不认昇腾」。<strong>这一层的代码往往是最「薄」的，因为它做的是「宣告身份」而不是「干活」</strong>；真正干活的是算子层与执行层。</span>

## 3 算子层：昇腾算力的注册表

算子层是包性能的心脏，管「昇腾上怎么算」：

**PagedAttention 内核**：分页注意力在昇腾的实现，块表访问 + AI Core 搬运（第 2 篇《PagedAttention 在昇腾上的实现》）。

**融合算子**：残差 + RMSNorm + 激活这类融合内核（第 2 篇《自定义融合算子与 Ascend C 内核开发》）。

**量化内核**：INT8 等量化推理所需的整数算子（第 3 篇《FP16/BF16 与 INT8 量化精度策略》）。

**注册机制**：每个内核通过 vLLM 的算子抽象注册进去，覆盖默认实现。**vLLM 调度到该算子时，走昇腾实现。**

**核心要点**：算子层是「昇腾后端性能」的载体——**可插拔架构决定了「算子能插」，算子层决定了「插进来的算子快不快」**。模型能不能跑、跑多快，很大程度上取决于这一层的内核质量。

## 4 执行与编译层：图与并行

第三层负责「执行」的落地：

**图编译适配**：把 vLLM 的模型前向接到 CANN 的图优化/编译路径（第 2 篇《ATC 图编译与算子图优化》），处理首启编译。

**执行器**：单卡/多卡的执行逻辑，张量并行的切分与集合通信走 HCCL（第 4 篇《张量并行与多卡推理》）。

**量化/精度执行**：精度转换、量化权重的加载与运行路径。

<span class="marginnote">三层的边界不是死的：有些功能会横跨多层。比如<strong>张量并行既在算子层（通信算子）也在执行层（切分逻辑）</strong>。<strong>读包时先按「平台/算子/执行」给每个目录贴标签，再接受少量跨界</strong>——比按目录名硬背高效得多。</span>

## 5 配套目录：csrc/ 与编译产物

`vllm_ascend` 包之外，仓库里还有一块不能忽略的配套——**`csrc/`**（C/C++ 源码）：

**为什么需要 csrc/**：算子是性能敏感代码，Python 层只做「注册与调度」，真正的内核用 Ascend C / C++ 写在 `csrc/` 里，编译成 Python 扩展。

**编译流程**：`setup.py` 一类脚本把 `csrc/` 的 Ascend C 源码编译进 `vllm_ascend` 扩展。**这一层是「版本匹配」的又一个落点**——CANN 头文件与库的版本变了，`csrc/` 的编译产物就要重新构建。

**Python 与 csrc 的分工**：Python 管「注册、参数组织、错误处理」，csrc 管「内核本体、搬运、tiling」。

**核心要点**：`csrc/` 的存在回答了「为什么昇腾后端这么轻却能很快」——**重活全在编译好的原生内核里，Python 只是「司机」**。这也是昇腾自定义算子（Ascend C）开发要独立的 csrc 目录的原因。

## 6 核心对比表：包的每一层 vs vLLM 抽象

把包的骨架与可插拔抽象对照成一张表，结构就彻底清晰了：

| 包内层次 | 职责 | 对应 vLLM 抽象 | 关键实现 |
| --- | --- | --- | --- |
| 平台层 | 设备身份、能力上报 | Platform / DeviceCapability | AscendPlatform |
| 算子层 | 昇腾算子与内核 | 算子分发 | PagedAttention、融合、量化内核 |
| 执行层 | 图编译、并行执行 | Executor | 图适配、HCCL、TP/EP |
| csrc/ | 原生内核本体 | （被算子层引用） | Ascend C 内核、tiling |

**辨析｜易错点：** 很多新人读包时盯着算子层看性能，却忽略了平台层的「版本与能力」问题——**平台层的版本校验不通过，算子层写得再好也白搭**。读包的顺序应该是「平台 → 执行 → 算子」，先把「能不能跑」搞清楚，再看「快不快」。

## 7 小结

- **三层骨架**：平台层（硬件身份）、算子层（怎么算）、执行层（怎么跑完）——与可插拔抽象一一对应。
- **平台层薄而关键**：宣告「vLLM 认不认昇腾」，决定启动成败。
- **算子层是性能心脏**：PagedAttention、融合、量化内核的质量决定模型跑多快。
- **执行层管图与并行**：图编译走 CANN、并行走 HCCL，是「多卡」的落点。
- **csrc/ 管重活**：原生内核在 C/C++ 侧，Python 只做司机——这就是轻而快的原因。
- **读包顺序**：平台 → 执行 → 算子，先搞清「能不能跑」，再看「快不快」。
