## 为什么从 FAQ 开始

本专题一路走到这里，从硬件架构到算子内核，从单卡到多卡，从安装到剖析——你已经掌握了昇腾 vLLM 推理的「正确姿势」。但生产环境的残酷在于：**大部分时间花在「错误姿势」上**。这一篇是整个专题的收尾，也是实战的起点：把昇腾部署路上最高频的问题按「启动、显存、算子、精度、性能」五类排成一张排查表。**记住：每个坑的解法都在「先定位层级，再对症下药」这个总原则之下。**

## 1 启动类问题：服务起不来

**现象一，`No module named torch_npu` 或 `ImportError`**。根因通常是：torch_npu 没装，或装到了另一个 Python 环境。排查：确认 `pip show torch_npu` 在**当前环境**可见；用 conda/venv 隔离环境时，检查激活的是哪个环境。

**现象二，报「设备不存在 / no NPU device」**。根因通常是驱动/固件未就绪，或 `ASCEND_RT_VISIBLE_DEVICES` 指向了不存在的设备。排查：`npu-smi info` 看设备是否列出；核对容器里的设备映射（第 1 篇《Docker 镜像与多形态部署》）。

**现象三，启动即段错误（Segmentation fault）**。这是昇腾最著名的「版本错配指纹」——torch_npu 与 PyTorch 版本不匹配。排查：核对 torch_npu 要求的 PyTorch 版本，全套对齐（第 1 篇《环境安装与版本匹配》）。

**核心要点**：启动失败先问「哪个层级」——环境层（模块缺失）、设备层（驱动/映射）、版本层（ABI 错配）。**三层按序查，不要直接重装系统。**

### 一次排查演练：启动段错误

把「先定位层级」演示一遍。假设你敲下 `vllm serve` 立即段错误，按层级推进：

**第一层，环境层**：`pip show torch_npu torch` 确认装齐了；`python -c "import torch, torch_npu"` 看能不能 import。import 就崩 → 版本层问题（torch_npu 与 PyTorch 不匹配）。

**第二层，版本层**：核对 torch_npu 官方要求的 PyTorch 版本与实际装的版本。对不上 → 装对版本，重测。

**第三层，设备层**：`npu-smi info` 看设备是否就绪。设备没列出来 → 查驱动与固件。

**第四层，推理层**：import 通、设备在，还崩 → 用最小模型跑，二分定位到具体环节。

**核心要点**：这次演练的每一步都是「先证伪一个层级」——**把「段错误」这个模糊症状，一步步缩成「哪一层的问题」**。层级没定位就重装，是浪费时间的最大来源。

## 2 显存类问题：OOM 与并发上不去

**现象一，模型加载 OOM**。根因通常是：权重 + 预分配的超预算。排查：确认 `--gpu-memory-utilization` 没给到 1.0（留余量给运行时）；换更小的 `--max-model-len`；加大张量并行把权重切分到多卡。

**现象二，并发上不去，报 KV Cache 不足**。根因：KV Cache 预算被挤占或 `--max-num-seqs` 设太高。排查：核对 `--max-model-len` 与 KV Cache 预算（第 2 篇《PagedAttention 在昇腾上的实现》的显存公式）；确认没被前缀缓存/投机解码的草稿模型挤占（第 3 篇《Prefix Caching》《投机解码》）。

**现象三，长序列推理中途 OOM**。根因：序列长度波动超出预算，或 KV 增长异常。排查：用 `--max-model-len` 给足上界；开分块/分页按需分配；检查是否有未回收的显存块。

<span class="marginnote"><strong>显存问题的总钥匙</strong>是第 2 篇那张 KV 预算公式：`Bytes_per_token = 2×L×H_kv×D×s`。<strong>显存不够，先沿这条公式查「哪里吃得多」</strong>——层数、KV 头数、精度、上下文长度，四个变量各有对策，别一上来就换机器。</span>

## 3 算子与编译类问题

**现象一，编译期报「算子不支持 / op not found」**。根因：模型用了昇腾算子库没覆盖的算子。排查：查支持矩阵与版本（第 1 篇《支持模型矩阵》）；升级 CANN 到更新版本；若算子确实缺失且必要，考虑自定义算子（第 2 篇《自定义融合算子与 Ascend C 内核开发》）。

**现象二，首次启动编译特别慢**。根因：CANN 图编译在进程启动时执行（第 2 篇《ATC 图编译与算子图优化》）。排查：**这不是故障**；生产用长驻进程、预热、或缓存编译产物规避，而不是反复重启。

**现象三，运行到某个特殊输入才报错**。根因：冷门路径未验证，或形状/长度越界。排查：缩小输入复现最小样例；对照支持矩阵确认「验证过」的负载范围。

**核心要点**：算子类问题的本质是**「覆盖」问题**——昇腾算子库覆盖不到的算子，决定模型能不能跑。**先确认「是不是覆盖问题」，再决定「换模型」还是「写算子」。**

## 4 精度类问题：能跑但结果不对

**现象一，输出乱码或明显错误**。根因排查顺序：先查精度档位（`--dtype` 与权重是否匹配，BF16 vs FP16 vs INT8）；再查量化（INT8 的 scale/校准是否正确，见第 3 篇《FP16/BF16 与 INT8 量化精度策略》）；最后查模型权重完整性。

**现象二，与 CUDA 端结果略有差异**。根因：不同硬件/内核的浮点舍入顺序不同（第 2 篇《FlashAttention 昇腾实现》讨论过在线 softmax 的数值差异）。**这是正常的，不是 bug**——用容差对拍而非逐位比对。

**现象三，多卡结果与单卡不一致**。根因：张量并行切分引入的数值差异，或通信未正确同步（第 4 篇《张量并行与多卡推理》）。排查：先用单卡验证基线，再对照多卡。

**辨析｜易错点：** 精度问题最容易**误判为算子 bug**。实际中「精度差一点」往往来自浮点差异，「精度完全错」才要怀疑算子或权重。**先用一个已知正确的模型 + 已知正确输入跑基线**，再谈别的。

## 5 性能类问题：能跑但慢

**现象一，吞吐远低于预期**。排查路径：先显存预算（KV 预算够不够）→ 批大小（`--max-num-seqs` 是否到平台期）→ 特性开关（该开的前缀缓存/分块预填充开了没）→ 算子层（用 msprof 找热点，第 4 篇《msprof 性能剖析》）。**顺序就是「先结构、后细节」。**

**现象二，首字延迟（TTFT）高**。排查：长 prefill 是否堵住了流水线（开 Chunked Prefill，第 3 篇）；前缀缓存是否命中（共享前缀场景开 `--enable-prefix-caching`）。

**现象三，单请求慢但吞吐可以**。根因：批太大压低了单序列速度（第 3 篇《连续批处理》的吞吐公式）。**这是吞吐与延迟的固有权衡**——按 SLA 取舍，不是 bug。<span class="marginnote">「单请求慢但吞吐可以」是生产里最常被误解的「问题」——<strong>它往往不是故障，而是吞吐与延迟权衡的正常结果</strong>。先问 SLA 要求哪个，再决定要不要调。</span>

**核心要点**：性能问题的排查顺序是**「预算 → 调度 → 特性 → 算子」**——先确认资源没白给，再确认调度没空转，再确认特性没漏开，最后才回到算子层抠细节。

## 6 核心对比表：五类问题的速查

把整个专题的「坑」浓缩成一张速查表：

| 问题类别 | 典型现象 | 首要排查 | 对应章节 |
| --- | --- | --- | --- |
| 启动 | 段错误 / 模块缺失 / 无设备 | 版本对齐、设备映射 | 第1篇 |
| 显存 | 加载 OOM / 并发上不去 | KV 预算公式、utilization | 第2、4篇 |
| 算子编译 | 算子不支持 / 首启慢 | 支持矩阵、CANN 版本 | 第1、2篇 |
| 精度 | 乱码 / 与 CUDA 有差 | 精度档位、量化、浮点差异 | 第2、3篇 |
| 性能 | 吞吐低 / TTFT 高 | 预算→调度→特性→算子 | 第3、4篇 |

**核心要点**：这张表是**排查的出发顺序，不是终点**——每个「首要排查」之后，都要沿对应章节的机制继续追。**把问题分类，是最快的排障手段**——先知道是哪一类，才知道去哪里找答案。

### 排查的总流程

把「先定位层级」操作化成一套固定流程，任何问题都能套用：

1. **复现**：用固定输入/负载稳定复现问题，避免在偶发现象里猜；
2. **分类**：把问题归入「启动/显存/算子/精度/性能」五类之一；
3. **定位**：沿对应章节的机制链追根因，而不是对表面文字打补丁；
4. **修复**：每次只改一处，记录改动；
5. **验证**：用与复现时相同的负载回归，确认修复有效且无副作用。

**这五步把「排查」从碰运气变成工程**——每一步都有明确产出，不会原地打转。遇到棘手问题，按这五步走一遍，多数情况在第 2、3 步就锁定答案了。

## 7 小结

- **启动类**：先分层——环境、设备、版本三层按序查，段错误九成是版本错配。
- **显存类**：沿 KV 预算公式找「哪里吃得多」，别一上来就换机器。
- **算子类**：本质是覆盖问题——先确认「缺算子」，再决定换模型还是写算子。
- **精度类**：先跑已知基线，区分「浮点差异」与「真错误」。
- **性能类**：预算 → 调度 → 特性 → 算子，先结构后细节。
- **先复现再排查**：用固定负载复现问题，避免在偶发问题里猜。
- **分类先行**：把问题归入五类之一，再去对应章节找答案。
- **最小改动修复**：每次只改一处，改完用相同负载回归验证。
- **总原则**：先定位层级，再对症下药——这六个字贯穿整个专题的每一个坑。
