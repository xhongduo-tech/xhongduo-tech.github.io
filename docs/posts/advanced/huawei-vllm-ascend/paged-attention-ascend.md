## 为什么从 PagedAttention 开始

vLLM 之所以能成为吞吐标杆，PagedAttention 是第一个理由。它的灵感直接来自操作系统的**虚拟内存分页**：让 KV Cache 像用户进程的地址空间一样，按页分配、按页换入换出，从而把显存浪费降到最低。这一篇先讲清「为什么必须存 KV」「朴素实现浪费在哪」，再落到昇腾上：**分页的 KV Cache 在 AI Core 上怎么访问、块表怎么组织**。理解了它，后面所有推理特性（连续批处理、前缀缓存）都有了地基。

## 1 为什么要存 KV Cache

Decoder-only 模型生成 token 时，每生成一个新 token，都要让所有注意力头「回顾」之前的所有 token。回顾的方式是计算查询与历史键值的注意力分数：

$$
\text{Attention}(Q, K, V) = \text{softmax}\left(\frac{QK^\top}{\sqrt{d_k}}\right) V
$$

每一步都要用到**此前所有位置的 K 和 V**。如果不缓存，就得把历史输入重新前向一遍——每出一个 token 就重算一次全量，代价是 $O(n^2)$ 的累积开销。于是引擎选择**把每一步算出的 K、V 缓存下来**，后续步骤直接读取。这个缓存就是 **KV Cache**。

KV Cache 有多大？对每个序列的每个 token，要为每一层、每一组 KV 头各存一份 K 和 V。一个 7B 级模型，单序列的 KV Cache 就可能达到**每 token 几十 KiB**，撑满几千 token 的上下文就是几百 MiB。<span class="marginnote">KV Cache 的规模与模型深度、KV 头数线性相关，与上下文长度线性相关，因此<strong>长上下文推理的显存压力主要来自 KV Cache 而非权重</strong>——这是贯穿整个专题的一条主线。</span>

## 2 朴素实现的浪费：连续预留

最朴素的做法，是给每个序列**预留一整段连续显存**，长度按最大可能序列（`max-model-len`）分配。问题有两个：

**内部碎片**：一个序列实际只生成了 100 token，却为它预留了 8192 token 的空间——中间全是空洞。

**无法共享**：即使两个序列有完全相同的 token 前缀，各自也存了一份重复的 KV。

这两种浪费加起来，能让同 64 GB 显存下的并发量差一个数量级。PagedAttention 的解法，是把显存当成**页**来管理。

## 3 PagedAttention 的思想：把 KV Cache 切成页

PagedAttention 的核心是**分页**：把 KV Cache 按固定大小的**块（block）**组织，每个块装固定数量 token 的 KV（如 16 或 32 个 token）。于是：

**逻辑块**：序列视角下连续的「第 0 块、第 1 块、……」，按 token 顺序编号，序列永远像在访问连续内存。

**物理块**：显存里实际分配的块，编号是物理位置；**逻辑上连续的块，物理上可以分散在显存任何位置**。

**块表（block table）**：维护「逻辑块号 → 物理块号」的映射，类似操作系统里页表的作用。

Attention 计算时，对每个 token 位置的注意力，都要**通过块表把逻辑地址翻译成物理地址去取 K、V**。这就是「分页注意力」名字的由来——注意力内核必须理解分页，而不能假设内存连续。<span class="marginnote">把 vLLM 的 KV 块表与第四级《操作系统》的页表对比着学：逻辑地址→物理地址的翻译、按需分配、缺页……<strong>虚拟内存的全部概念在 KV Cache 里重演了一遍</strong>，只不过一页从「4 KiB」变成了「16 个 token 的 K/V」。</span>

## 4 昇腾上的实现：把分页访问落到 AI Core

在昇腾上实现 PagedAttention，难点不在「分页」本身，而在**分页访问与 AI Core 的存储结构如何配合**。昇腾内核面临三个约束：

**约束一，取数要走块表**：每次计算注意力都要先查块表拿物理地址，再取 K/V。块表常驻 **L2 Cache**，避免每次都回 HBM 查表。

**约束二，数据布局**：昇腾的 Cube 单元擅长「连续、对齐」的矩阵搬运。分页后的 KV 在显存里不连续，搬运时要把每个物理块的 KV 先搬进片上缓冲（L0/UB），凑成 Cube 能吃的形状再算。

**约束三，tiling 切分**：一个 batch 里每个序列的上下文长度不同，块数不同，需要按「每序列的块列表」做 tiling，让不同长度的序列共享同一批执行而互不干扰。<span class="marginnote">一个常被忽略的点：<strong>块大小不是越大越好</strong>。块大，块表项少、搬运连续，但内部碎片多；块小，碎片少，但查表与搬运开销大。昇腾后端要按目标负载选块大小，本质是「碎片 vs 开销」的折中。</span>

**核心要点**：昇腾版 PagedAttention 就是「分页管理 + AI Core 搬运」的结合——Python 层管理逻辑/物理块的映射，`csrc/` 里 Ascend C 内核负责「查块表、搬 KV、算注意力」三步。

## 5 公式解析：KV Cache 显存到底怎么算

用一条公式把「分页管理」的收益量化。单个序列存一个 token 的 KV 所需字节数：

$$
\text{Bytes}_{\text{per token}} = 2 \times L \times H_{kv} \times D \times s
$$

其中 $L$ 是层数，$H_{kv}$ 是 KV 头数（GQA 下远小于查询头数），$D$ 是每个头的维度，$s$ 是每元素字节数（BF16 为 2），前面的因子 2 来自 K 和 V 各一份。

代入一个具体模型（28 层、4 个 KV 头、`head_dim=128`、BF16）：

$$
\text{Bytes}_{\text{per token}} = 2 \times 28 \times 4 \times 128 \times 2 = 57344 \ \text{B} \approx 56 \ \text{KiB}
$$

于是 8192 token 的单序列 KV Cache 约 $56 \times 8192 \approx 448$ MiB。假设权重占 16 GiB、可用 64 GiB 显存，理论可容纳的并发序列数：

$$
\text{并发上限} \approx \frac{(64 - 16)\ \text{GiB}}{448\ \text{MiB}} \approx 107
$$

**分页的意义在于让这个上限接近「按需分配」的真实值**：无分页时每个序列按最大长度预留，100 个并发序列可能只有三分之一真正写到那——分页后，多少 token 占多少页，上限就顶到哪儿。<span class="marginnote">这个数字链是后面所有显存决策的<strong>标尺</strong>：换模型（层数/KV 头变）、换精度（`s` 变）、换上下文长度，都能沿这条公式重新估算，不必每换一次配置都靠猜。</span>

### 块大小：一个具体的权衡

第 4 节提到块大小是「碎片 vs 开销」的折中，这里把数字摆出来。设块大小为 $B$（每个块装 $B$ 个 token 的 KV），序列平均生成长度为 $\bar{L}$：

**碎片代价**：每个序列的最后一个块平均浪费 $\frac{B}{2}$ 个 token 的空间，总碎片率约 $\frac{B}{2\bar{L}}$。块越大，碎片越多。

**开销代价**：块表项数约 $\frac{\bar{L}}{B}$，每项要查一次表；块越小，查表与搬运开销越频繁。

**一个直觉的折中**：若平均序列长 512 token，块取 16，则块表约 32 项、碎片率约 1.6%；块取 64，则块表约 8 项、碎片率约 6%。**短序列场景小块的碎片优势明显，长序列场景大块的搬运优势明显**——这就是为什么「块大小」要按负载调，而不是写死一个值。

### 与 GPU 端实现的差异

昇腾版 PagedAttention 与 GPU 版思想一致，但落地细节不同，值得对比：

- **块表驻留**：GPU 端常把块表放全局内存靠缓存命中；昇腾端更强调把块表放进 L2 Cache，减少每次取 K/V 的查表延迟。
- **搬运单元**：GPU 的线程块天然承担「一页」的搬运；昇腾的 DMA 搬运以对齐块为单位，物理块的布局要匹配 DMA 的对齐要求。
- **融合程度**：昇腾版常把「查表 + 搬运 + 注意力」融成一个内核，减少内核启动与中间张量（这与《FlashAttention 昇腾实现》的融合路径一致）。

**核心要点**：思想是「虚拟内存」，落地是「对齐与驻留」。**看懂昇腾版 PagedAttention，就是看懂「分页思想如何适配一块以对齐为美德的硬件」**。

### 一句话总结分页的价值

**PagedAttention 的全部价值，是让「显存按需分配」成为可能——而「按需」两个字，决定了引擎的并发天花板。** 它把 KV Cache 从「预留一整段」变成「用多少页分配多少页」，配合连续批处理与显存优化，让同样的显存服务更多的并发。分页是 vLLM 一切吞吐神话的地基，也是昇腾后端性能代码里最值得读的一段。
