## 为什么从自定义算子开始

vLLM 的算子里，有一类在 CANN 算子库里找不到现成实现，比如**分页的 KV Cache 访问**、**逐层融合的归一化**。这些算子不是没人写过，而是「通用库不会为一个推理引擎的私有数据结构写」。于是 vllm-ascend 必须在 `csrc/` 里用昇腾的算子开发语言自己写。这一篇讲清 Ascend C 编程模型的骨架、一个算子从设计到上板的完整生命周期，以及「为什么融合算子值得写」。

## 1 为什么需要自定义算子

两个动机，一个「有和无」，一个「快和慢」。

**有与无**：PagedAttention 的块表访问、投机解码里的特殊采样，这类逻辑是 vLLM 私有的，CANN 算子库不会提供——**没有现成算子，就必须自己写**。

**快与慢**：即使某个功能 CANN 有算子，把多个小算子串起来调用也未必高效。每调用一个算子，都要经历「启动内核 → 读回中间结果 → 再启动下一个」的往返，中间结果在显存里反复搬家。**融合算子把多个步骤并成一个内核，中间结果留在片上缓冲不落显存**，访存开销大幅下降。

**核心要点**：判断一个算子值不值得手写，看两点——**库有没有**，以及**它是不是访存受限**。访存受限的算子序列，融合收益最大；算力受限的算子（如大 GEMM），库算子已经够好，不必重写。

## 2 Ascend C 编程模型：核函数的三件套

Ascend C 是昇腾的算子开发语言，面向 AI Core 的异构三单元。写一个 Ascend C 内核，核心是理解它的**执行模型**：

**核函数（Kernel）**：一个内核对应一次在 AI Core 上执行的程序。它像 CUDA kernel 一样被「调度」到核上运行，但内部是显式的多线程（多核）模型。

**Tiling（切分）**：把大数据切成适合片上缓冲处理的小块。因为 AI Core 的片上存储（L0/UB）远小于要处理的数据，内核必须按「片上一次能装多少」切分计算，循环搬运。**Tiling 策略是算子性能的第一决定因素。**

**Queue 与 Buffer 抽象**：Ascend C 提供队列化的数据搬运抽象——数据从全局内存（HBM）经 DMA 进入片上缓冲，计算单元消费缓冲，结果再写回。开发者显式控制「取数 → 计算 → 存回」的流水，而不是依赖隐式的线程调度。

<span class="marginnote">把 Ascend C 与 CUDA 对比着记：CUDA 是「隐式大量线程 + 显式少量控制」，Ascend C 更接近「显式搬运 + 显式切分 + 显式多核」。<strong>上手第一关是接受「搬运要自己管」</strong>——CUDA 里编译器替你做的数据搬移，在 Ascend C 里是代码的一部分。</span>

## 3 一个算子的生命周期

写一个自定义算子，从设计到被 vLLM 调用，是一条完整流水线：

**第一步，定义算子接口**：声明算子的输入、输出、属性与形状约束。在 vllm-ascend 里通常以「Python 侧的 torch 函数 + C++ 侧的注册」形式出现。

**第二步，写 Ascend C 内核**：在 `csrc/` 里实现核函数，包含 tiling 逻辑与计算主体。

**第三步，编译进库**：通过编译脚本把 Ascend C 源码编译为算子的二进制实现，链接进 `vllm_ascend` 的 Python 扩展。

**第四步，注册覆盖**：在 Python 层用 vLLM 的算子抽象把自己实现注册进去，覆盖默认（CUDA）实现。

**第五步，调用验证**：前向跑到该算子时，vLLM 走昇腾实现；用数值对拍（昇腾结果 vs 参考结果）验证正确性，再做性能对拍。

**辨析｜易错点：** 最容易出错的是**数值精度与数据布局**。昇腾 Cube 对矩阵有特定的对齐要求（如按 16 字节/特定倍数对齐），按普通内存布局写出的内核可能「能编译但算不对」。所以新算子第一步永远是**小规模数值对拍**，而不是直接上大模型。

## 4 核心对比表：CUDA 内核与 Ascend C 内核

把两个生态的算子开发放在同一张表里对照，差异一目了然：

| 维度 | CUDA 内核 | Ascend C 内核 |
| --- | --- | --- |
| 最小执行单位 | 大量隐式线程（thread） | 显式多核 + 显式队列 |
| 数据搬运 | 编译器/访存模型部分接管 | 开发者显式控制 DMA 与缓冲 |
| 存储层次 | 寄存器/SMEM/全局内存 | L0/L1/UB/L2/HBM |
| 切分策略 | grid/block/thread 隐式 | tiling 显式，性能关键 |
| 开发语言 | CUDA C++ | Ascend C（类 C++ DSL） |
| 调试手段 | cuda-gdb / nsight | msprof / 昇腾调试工具 |
| 应用场景 | 通用 GPU 算子 | 昇腾 NPU 算子 |

<span class="marginnote">这张表的本质区别是<strong>「编译器替我扛多少」</strong>：CUDA 的线程抽象替你扛了大量调度细节，Ascend C 把搬运与切分交还给你。<strong>对熟悉 CUDA 的人，Ascend C 的第一感觉是「更底层、更啰嗦」——但这也意味着对性能有更强的掌控力。</strong></span>

## 5 融合算子的价值：一次搬运用到底

融合算子的核心收益可以用「中间结果不落地」一句话概括。以一个典型融合为例：`残差 + RMSNorm + 激活 + 上投影`。未融合时：

```
读 x、读残差 → 算加法 → 中间结果写显存
→ 读中间结果 → 算 RMSNorm → 写显存
→ 读 → 算激活 → 写显存
→ 读 → 算 GEMM → 写输出
```

每两步之间都是一次「写显存 + 读显存」。融合后，除最后一步 GEMM 外，中间的加、归一、激活全部在片上缓冲完成：

```
读 x、读残差 → 片上依次算 加法→RMSNorm→激活 → 直接喂给 GEMM → 写输出
```

**对访存受限的算子，融合的收益往往是数量级的**——省掉的是每次往返的 HBM 带宽，而带宽正是昇腾这类加速器的稀缺资源。<span class="marginnote">融合算子的另一个隐藏收益是<strong>降低内核启动开销</strong>：每个内核启动都有固定成本，少启动一个内核就少付一次。算子多了之后，启动开销会从「忽略不计」变成「吞吐瓶颈」。</span>
