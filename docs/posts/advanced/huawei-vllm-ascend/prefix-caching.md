## 为什么从前缀缓存开始

真实世界的模型请求，很少是「每条 prompt 都完全不同」。同一套系统提示、同一份被反复检索的文档、同一个多轮对话的上下文——**大量请求共享同一段前缀**。如果每次都重新对这段前缀做 prefill（处理输入并计算 KV），就是在反复支付同一笔计算账。前缀缓存（prefix caching）把「算过一次的 KV」存下来，后续请求直接复用，把 prefill 成本从「每次都付」变成「只付一次」。

## 1 重复计算的浪费在哪里

先看 prefill 的成本构成。一个请求进来，处理输入 prompt 的代价约等于对 prompt 长度做一次全量前向，并生成 KV Cache。而**很多请求的 prompt 高度雷同**：

**共享系统提示**：公司级服务通常在每条请求前拼同一段长长的「人设 + 工具说明 + 安全规范」，几千 token 全是重复的。

**RAG 文档前缀**：不同用户问不同问题，但都先塞进同一份被检索的文档段落，前缀命中率高得惊人。

**多轮对话**：第 $k$ 轮的 prompt 天然包含前 $k-1$ 轮的完整历史，轮轮累积、轮轮重复。

这三类场景下，**prefill 的大部分计算都是重复劳动**。前缀缓存的目标，就是把这些重复劳动从每个请求里抠掉。

**核心要点**：前缀缓存的收益条件是**「共享前缀 + 前缀够长」**。前缀越长、共享请求越多，收益越大；如果每条请求的 prompt 前缀都不同，缓存就是白占显存。

## 2 核心机制：哈希匹配与 KV 复用

前缀缓存怎么知道「这段前缀之前算过」？vLLM 的做法基于一个朴素的思路：**给 KV Cache 的块打指纹**。

**块级哈希**：KV Cache 被分成块（同 PagedAttention 的块），每块对应一段 token。vLLM 维护「token 块 → 哈希值」的映射。新请求的 prompt 逐块计算哈希，与缓存中的块哈希比对。

**哈希命中即复用**：如果请求的前若干块的哈希与缓存中某序列的对应块一致，就认为这段前缀是「见过」的，直接把缓存的物理块挂到新序列的块表上——**不用重新计算 KV，也不用重新分配显存**。

**分块比对的优点**：按块（如每块 16 个 token）做哈希比对，比按整段前缀比对更精细——两个请求共享前 64 个 token、后面分叉，也能复用这 64 个 token 的 4 个块。<span class="marginnote">按块复用的实现细节很妙：复用的物理块被<strong>多个序列同时引用</strong>（类似操作系统的共享内存页），块表里用引用计数管理——最后一个引用者退出时块才回收到空闲池。这就是「多序列共享 KV 块」的机制基础。</span>

## 3 自动前缀缓存：无需改代码

前缀缓存的优雅之处在于它对上层**几乎透明**。开启 `--enable-prefix-caching` 后：

- 用户照常发请求，不需要手工标注「哪些是共享前缀」；
- 引擎在运行时自动对 prompt 做块哈希，能复用就复用；
- 缓存有容量上限，超出后按策略淘汰（类似 LRU 的近似）。

对比「手工 KV 拼接」的方案（需要应用层把共享上下文单独算一次再拼进每条请求），自动前缀缓存**不改变接口、不改变请求语义**，纯靠引擎内部机制获利。<span class="marginnote">前缀缓存与 RAG 的关系很顺：<strong>RAG 每次把同一份文档段落塞进 prompt，前缀缓存恰好把这些「常客」的 KV 存了下来</strong>——两者搭配，检索增强的重复计算成本会显著下降。</span>

**辨析｜易错点：** 前缀缓存会**额外占用显存**来存放可复用的 KV。如果你的场景前缀命中率很低，缓存就是「占了显存却很少命中」，反而可能挤占 KV Cache 预算、压低并发。所以它**不是无脑开关**——高共享前缀场景开，低命中场景关，用基准测试说话。

## 4 公式解析：缓存命中省了多少计算

把收益量化。设一个请求的 prompt 长度是 $P$，其中前缀缓存命中了 $k$ 个 token（$0 \le k \le P$）。若不命中，prefill 计算量约正比于 $P$；命中后，只需计算未命中的 $P - k$ 个 token：

$$
\text{计算节省} = \frac{k}{P}
$$

再考虑多请求场景。若有 $N$ 条请求共享一段长 $k$ 的相同前缀，朴素实现总 prefill 计算量约：

$$
C_{\text{朴素}} = N \times P
$$

有前缀缓存后，前缀只算一次，总计算量约：

$$
C_{\text{缓存}} = k + N \times (P - k)
$$

当 $P - k \ll P$（前缀占 prompt 的大部分）时，$C_{\text{缓存}} \approx k + N(P-k)$ 相比 $NP$ 的节省接近 $\frac{k}{P}$——**缓存命中省掉的正是「被命中的那段前缀」的 prefill 计算**。前缀越长、命中率越高，收益越接近「免费」。

### 一个命中的直观例子

把公式落到一个具体场景。假设你的服务每请求都拼一段 2048 token 的系统提示，其余 prompt 平均 256 token：

- 单请求 prefill 长度 $P = 2048 + 256 = 2304$；
- 若前缀缓存命中前 2048 token，未命中部分只有 256 token；
- 单请求 prefill 计算量从「全量 2304」降到「增量 256」——**省了约 89% 的 prefill 计算**。

再看多请求：100 个请求共享同一段系统提示，朴素实现要算 100 × 2048 的系统提示 prefill；有缓存只需算 1 次。**这就是为什么「长共享前缀」场景前缀缓存收益巨大**——它的收益与共享请求数成正比。

**一句话总结**：前缀缓存是「把重复的 prefill 变成一次 + 无数次挂载」——挂载几乎免费，prefill 很贵，所以共享前缀场景它几乎总是划算。

## 5 昇腾上的实现与易错点

前缀缓存在昇腾后端落地，几个工程要点：

**显存预算的权衡**：缓存要占显存存放可复用的 KV。昇腾上显存本来就紧张（第 2 篇《PagedAttention 在昇腾上的实现》），缓存占比要监控——缓存命中率高时值回票价，命中率低时是纯开销。

**块粒度与哈希成本**：块级哈希要算 token 的哈希值，有 CPU 成本。块太大哈希粒度粗，块太小哈希开销大——昇腾后端按负载调块大小，与 PagedAttention 的块大小选择联动。

**与连续批处理的协同**：缓存命中的物理块被多个序列共享，引用计数管理（第 2 节讲过）要正确——释放时机错了，会「误杀」还在用的块。

**辨析｜易错点：** 前缀缓存**不是显存优化的手段**，它是「用显存换 prefill 计算」的手段——**它以占用显存为代价省计算**。显存本身不够时，开前缀缓存可能反而挤占 KV 预算、压低并发。**先确认显存有富余，再谈开不开前缀缓存。**

## 6 核心对比表：前缀缓存 vs 其它复用手段

前缀缓存不是唯一的「避免重复计算」手段，把它与同类手段对比：

| 手段 | 复用什么 | 是否改代码 | 适用场景 |
| --- | --- | --- | --- |
| 前缀缓存 | 前缀的 KV | 否（自动） | 共享系统提示、RAG、多轮对话 |
| 手工 KV 拼接 | 共享上下文的 KV | 是 | 极少数高度固定的场景 |
| 请求模板缓存 | 请求模板 | 是 | 缓存级别更粗的兜底 |

**核心要点**：前缀缓存是「自动、不改代码、按 token 块粒度复用」的通用手段——多数共享前缀场景用它就够。手工方案只在极端场景才值得。

## 7 小结

- **浪费来源**：共享系统提示、RAG 文档前缀、多轮对话——大量 prefill 是重复劳动。
- **核心机制**：KV 块哈希 + 块表挂载，命中的物理块被多序列共享、引用计数管理。
- **透明开关**：`--enable-prefix-caching` 无需改代码，运行时自动复用。
- **收益公式**：节省约等于被命中前缀的占比 $\frac{k}{P}$——前缀越长、命中越多越赚。
- **显存代价**：缓存占显存，命中率低时是纯开销——先确认显存富余再开。
- **不是显存优化**：它是「用显存换计算」，别把它当成省显存的手段。
- **判断开关**：共享前缀占比高则开、命中率低则关，用基准测试说话。
