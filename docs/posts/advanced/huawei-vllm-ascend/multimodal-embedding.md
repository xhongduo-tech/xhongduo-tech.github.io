## 为什么从多模态与 Embedding 开始

到目前为止，我们谈的都是「纯文本对话模型」。但生产环境里，模型服务的形态远不止这一种：**输入可以是图文混合**（多模态大模型），**输出可以是向量**（Embedding 模型，供检索使用）。这两种形态在昇腾上的加载与算子需求各不相同，支持程度也不一样。这一篇把两种形态的服务逻辑、昇腾适配要点一次讲清，补齐支持矩阵的最后两块拼图。

## 1 多模态大模型：输入不只是文本

多模态大模型（如视觉-语言模型 VL）的能力是「看图说话」。它的内部结构通常是三段式：

**视觉编码器（vision encoder）**：把图像切成 patch 并编码为视觉 token 序列（如 ViT 结构）。

**投影层（projector）**：把视觉 token 映射到文本 token 的嵌入空间，让 LLM 能「读懂」图像。

**语言模型主体（LLM）**：把文本 token 与视觉 token 拼成同一个序列，走标准的自回归生成。

服务端的呈现方式很自然：用户在 prompt 里插入一张图，引擎把图像编码成视觉 token，与文本一起送入模型。**对引擎而言，多模态模型的特殊之处在于「输入预处理」**——图像要经过视觉塔，而视觉塔的算子（卷积、patch embedding、位置编码）在昇腾上也需要支持。<span class="marginnote">视觉 token 的数量通常远多于文本 token（一张图可能编码出几百上千个视觉 token），所以<strong>多模态请求往往天然是「长上下文」请求</strong>——KV Cache 压力大，前缀缓存与分块预填充在多模态场景的收益也更显著。</span>

## 2 Embedding 模型：输出不是文字

Embedding 模型做的是「把一段文本变成一个向量」。它服务的不是对话，而是**检索**：RAG 系统里，文档被切成块、每块向量化存库；查询时把用户问题向量化，在库里找最相似的块。

vLLM 通过 `/v1/embeddings` 端点暴露这个能力：传入文本，返回 `embedding` 向量（如 1024 维的浮点数组）。关键实现点：

**用最后一层隐藏状态，而非语言模型头**：Embedding 服务不生成 token，它取模型对输入序列编码后的**最后一层表示**（通常是最后一个 token 或池化结果）作为向量。

**批量与缓存**：大量文档块要快速向量化，连续批处理同样适用；文档向量可以缓存，重复请求零成本。

**与 RAG 的关系**：Embedding 是检索增强生成的第一环——先向量化，再检索，再生成。它不产出「回答」，产出的是「检索的钥匙」。

## 3 昇腾上的加载与算子需求

两种形态落到昇腾后端，各自的适配重点不同：

**多模态的算子增量**：视觉塔的算子（如卷积、多层感知机、图像位置编码）需要昇腾算子层支持。若某个视觉算子没有对应实现，整个模型会退回「不支持」。支持矩阵里「多模态支持范围随版本扩大」说的正是这层算子覆盖。

**Embedding 的轻量适配**：Embedding 模型的算子与文本模型几乎一致（同一套 LLM 架构），差异主要在「取哪层输出」——昇腾端的适配重点在**输出提取与池化**的路径正确，而不在新算子。

**显存画像**：多模态模型通常更大（视觉塔 + 投影 + LLM），Embedding 模型往往较小（检索场景偏好轻量模型以支撑高并发）。<span class="marginnote"><strong>服务形态决定性能画像</strong>：多模态模型是「重前向、少并发」——一次请求要编一张图；Embedding 是「轻前向、高并发」——一段文本向量化很快，靠大批量撑吞吐。调优时先认清自己属于哪类，再去调批大小与显存预算。</span>

## 4 核心对比表：三种服务形态

把「对话模型 / 多模态模型 / Embedding 模型」放在一起对比，差异一目了然：

| 维度 | 文本对话模型 | 多模态模型 | Embedding 模型 |
| --- | --- | --- | --- |
| 输入 | 文本 | 文本 + 图像 | 文本 |
| 输出 | 生成的 token | 生成的 token | 一个向量 |
| 核心算子 | LLM 主体 | 视觉塔 + LLM | LLM 编码器 |
| 主要接口 | `/chat/completions` | `/chat/completions`（带图像） | `/embeddings` |
| 并发画像 | 中 | 低（长上下文） | 高（轻前向） |
| 显存压力 | KV Cache | 视觉 token 的 KV | 偏小 |

<span class="marginnote"><strong>部署上的现实建议</strong>：三种形态对资源的诉求差异大，<strong>别挤在同一张卡上混跑</strong>。多模态长请求会吃掉大量 KV 预算，把 Embedding 的高并发拖垮；反之亦然。生产上按形态分卡、分实例，是比「一个大实例全包」更稳的架构。</span>

## 5 易错点与最佳实践

**易错点一，接口张冠李戴**：把 Embedding 请求发到对话接口（或反之），会得到错误格式的返回。先确认端点与参数，再谈性能。

**易错点二，多模态支持不等于「所有视觉模型都支持」**：每个视觉架构（不同的视觉塔、不同的投影设计）都要有对应的算子与模型实现。开跑前查支持矩阵，别拿一个冷门视觉模型直接上线。

**易错点三，Embedding 的向量质量**：向量化质量取决于池化策略（用哪个位置的隐藏状态）。不同模型约定不同，换模型后检索效果可能大变，这属于「模型侧」问题，不是引擎故障。

**最佳实践**：多模态先小图验证（降低视觉 token 数）确认链路通，再上大图；Embedding 用批量请求压吞吐，并配合向量库做端到端检索评估。
