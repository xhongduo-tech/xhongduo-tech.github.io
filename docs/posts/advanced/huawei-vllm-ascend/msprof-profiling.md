## 为什么从剖析开始

前面几篇我们讲了大量优化手段：连续批处理、量化、并行、融合算子……每一个都号称「更快」。但真正的问题是：**你的服务慢，到底慢在哪？** 是算子没喂饱 AI Core？是通信在等？是显存换页在卡？**没有数据，一切优化都是猜。** `msprof` 是昇腾的官方性能剖析工具，专门回答「慢在哪」。这一篇讲清 msprof 采集什么、关键指标怎么看、以及「从指标到瓶颈」的定位路径。

## 1 剖析为什么难：黑盒里的时间去哪了

推理服务的一次请求，时间分散在极多环节：CPU 上的调度决策、PyTorch 的算子派发、AscendCL 的内核启动、AI Core 上的计算、HBM 的搬运、HCCL 的通信、甚至显存的换页……**这些环节在「墙上的时间」里是无法区分的**——你只知道「慢」，不知道「谁在耗」。

剖析工具做的事，就是**给每段执行贴上标签**：把墙钟时间拆成「哪段在哪个设备上跑哪个算子」，让黑盒变成透明的流水账。

**核心要点**：剖析的第一价值不是「提速」，而是**「归因」**——把「慢」定位到具体环节。定位错了，再多的优化都是打在错误的位置上。

## 2 msprof 是什么：采集一次剖面

**msprof**：CANN 提供的**性能剖析工具**，通过 AscendCL 的 profiling 接口采集设备侧执行数据。一次典型的使用流程：

**第一步，采集**：对目标进程启用 profiling，运行一段负载（或压测脚本），msprof 在后台记录设备侧的算子执行、内核耗时、带宽占用等数据。

```bash
# 示意：对运行中的 vLLM 服务启用 profiling 并采集
msprof --application="<启动命令>" --output=./prof_result
```

**第二步，落盘**：采集结果写进输出目录，包含算子执行时间线、AI Core 利用率、通信时长等结构化数据。

**第三步，分析**：用 msprof 的解析/可视化能力，或直接查看生成的报告，定位热点。

<span class="marginnote"><strong>采集的代价要记住</strong>：profiling 本身会拖慢运行（记录开销、同步点），所以<strong>生产环境不要常开 profiling</strong>，只在「定位问题」时临时采集。<strong>先复现、再采集、再优化</strong>——用固定负载采集一次剖面，比在线上长期开着划算得多。</span>

## 3 关键指标：先看什么

一次 msprof 采集会产出大量数据，新手容易淹没在数据里。**先看四个指标**，足够定位绝大多数瓶颈：

**AI Core 利用率**：计算单元被喂得多饱。利用率低，说明「计算在等数据」——访存/通信瓶颈。

**算子耗时占比**：哪个算子占总时间最多。Top-1 算子就是你的「热点算子」。

**Host 侧 vs 设备侧时间**：CPU 派发与设备执行的失衡——如果 Host 侧主导，瓶颈在调度/派发而非算力。

**带宽与通信**：HBM 带宽占用、HCCL 通信时长——通信占比高，考虑并行策略问题。

**核心要点**：这四个指标的判读有一个总原则——**「算力没喂饱」看利用率，「时间被谁吃掉」看算子占比，「CPU 在等设备还是设备在等 CPU」看 Host/设备时间比**。先看这四个，再决定要不要深挖。

## 4 公式解析：AI Core 利用率与瓶颈判读

把「利用率」这条最有信息量的指标量化。定义一次执行窗口内 AI Core 的利用率：

$$
\text{利用率} = \frac{\text{AI Core 有效计算时间}}{\text{窗口总时间}}
$$

窗口总时间大致可拆成三部分：

$$
T_{\text{总}} = T_{\text{计算}} + T_{\text{访存等待}} + T_{\text{通信/同步}}
$$

于是：

$$
\text{利用率} = \frac{T_{\text{计算}}}{T_{\text{计算}} + T_{\text{访存等待}} + T_{\text{通信/同步}}}
$$

**判读直觉**：利用率低，说明分母里的「等待」占比大——**慢的不是「算」，而是「等」**。等谁？看 `T_{\text{访存等待}}` 与 `T_{\text{通信/同步}}` 谁大：访存等待主导 → 算子访存受限（该融合/优化搬运，见《FlashAttention 昇腾实现》）；通信同步主导 → 并行/通信问题（见《张量并行与多卡推理》）。

<span class="marginnote">这条公式是剖析的<strong>总纲</strong>：一切瓶颈都逃不出「计算、访存、通信」三个桶。<strong>看到低利用率，先问「时间在等什么」，而不是「为什么不够快」</strong>——前者指向正确的优化方向，后者只会让人乱试参数。</span>

## 5 从指标到优化：一条定位路径

拿到剖面数据后，优化走一条「自顶向下」的路径：

**第一步，看 Host/设备时间比**。若 Host 侧主导，先查 CPU 侧：调度器开销、Python 热点、同步等待——这类问题换算子没用，要改调度与派发。

**第二步，看算子耗时 Top-N**。找出热点算子，问三个问题：它访存受限还是算力受限？有没有现成融合路径？能不能换实现（库算子 vs 自定义内核）？

**第三步，看带宽与通信**。若通信占比高，查并行度与通信拓扑：TP 切分是否合理、HCCL 路径是否最优、是否需要换并行策略。

**第四步，回炉优化再对拍**。改完一处，用**相同负载**再采一次剖面，看热点是否转移、指标是否改善。**优化是「测量 → 改动 → 再测量」的循环，不是一次性动作。**

**辨析｜易错点：** 最常见的错误是**「按时间占比直接优化，不看因果」**——某个算子占比高，可能是另一个瓶颈的「受害者」（比如通信慢导致算子等数据，时间都记在算子上）。所以定位要**沿着「等待链」追**，而不是对 Top-1 无脑下手。

## 6 核心对比表：msprof 与 CUDA 剖析生态

昇腾的剖析工具与 CUDA 生态的工具对应关系，对照着记最快：

| 能力 | CUDA 生态 | 昇腾生态 |
| --- | --- | --- |
| 设备侧剖析 | Nsight Compute / Systems | msprof |
| 算子耗时统计 | nsys 的 profiler | msprof 算子报告 |
| AI Core 利用率 | SM 利用率 | msprof 利用率指标 |
| 通信剖析 | Nsight Systems（NCCL） | msprof（HCCL 通信数据） |
| 命令行采集 | nsys profile | msprof |
| 数据落盘 | .nsys-rep / .sqlite | msprof 输出目录 |

**核心要点**：msprof 在昇腾生态的位置，就是 Nsight 在 CUDA 生态的位置——**「看懂一张剖面图」的方法论是通用的，只是工具名不同**。你在 CUDA 下练就的「先归因再优化」思路，换到昇腾上直接可用，只需把工具换成 msprof。

## 7 小结

- **剖析的价值是归因**：把「慢」定位到具体环节，避免在错误位置打补丁。
- **msprof 采集流程**：启用 profiling → 跑固定负载 → 落盘 → 分析报告，生产环境只在定位时采集。
- **先看四指标**：AI Core 利用率、算子耗时占比、Host/设备时间比、带宽与通信。
- **利用率总纲**：低利用率 = 在等，看「计算/访存/通信」三桶谁占主导，决定优化方向。
- **定位路径**：Host/设备比 → 算子 Top-N → 通信 → 回炉对拍，循环优化。
