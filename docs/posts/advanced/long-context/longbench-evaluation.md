## 为什么从 LongBench 开始

本专题从 $O(n^2)$ 的复杂度一路讲到了 GQA 的缓存共享——每一种优化都宣称自己「支持长上下文」。可怎么知道它们是真的？**长上下文评测（long-context evaluation）是整个优化链条的收尾，也是被误解最多的环节**：有人拿困惑度说话，有人拿「大海捞针」说话，而它们往往测的不是同一件事。

LongBench（Bai et al., 2023）是第一个系统化的中英双语长上下文基准：21 个任务、6 大类，平均长度数千到上万 token，覆盖检索、综合、总结、代码等真实需求。它最重要的贡献是厘清了一件事：**「能读完长文」与「会用长文」是两种能力，评测必须把两者分开测**。这一节讲 LongBench 的设计逻辑、它的关键发现，以及评测长上下文时最常踩的坑。

## 1 一个悖论：为什么评测长上下文这么难

直觉上，「能不能处理长上下文」似乎一测便知——把文档加长，看模型表现下降多少。但真正的难点是**模型的退化可能来自任何一环**：注意力头看不到远处（信息可达性）、位置编码失灵（外推）、缓存显存不够（工程）、或者**干脆不读上下文**（能力缺失但捷径可用）。

**核心概念：** 评测的黄金标准是看模型**有没有真的利用上下文**。于是产生了两类测试：

- **检索型测试**：把一条事实藏在长文中，问「它说了什么？」——测「找得到吗」。代表是**大海捞针（Needle-in-a-Haystack）**测试。
- **综合型任务**：让模型基于全文总结、跨文档推理、多跳问答——测「找得到且用得起来」。LongBench 的主体是这一类。

**评测与本专题的耦合**：LongBench 的 21 个任务恰好能反过来「体检」本专题的各节优化——检索型任务考窗口与全局 token 是否给了直达通路，多跳任务考位置编码是否读得懂长程相对位置，长摘要考 FlashAttention 之后显存是否撑得住，缓存密集型推理考 KV Cache 优化是否到位。**评测既是优化链条的终点，也是下一轮优化的起点。**

**评测设计的两难**：任务太可控（合成），结论清晰但离真实远；任务太真实（真人问答），长度与难度纠缠、噪音大。LongBench 用「真实文档 + 分层控制 + 双指标」破局：真实保证外部效度，分层暴露退化曲线，EM 与 F1 双指标平衡严格与宽松。理解了这对张力，你就能读懂任何一个评测基准的取舍。

**为什么不能沿用短上下文基准**：把 512 长度的任务直接拉长，难度、噪音、长度效应一起变，短基准的分数对新旧模型毫无区分力。长上下文需要自己的基准，就像耐力跑不能拿百米冲刺的计时表来卡。**评测的「计量单位」**：任务长度以 token 计，但中英 token 的含义不同——同样 8k token，中文可能只有英文一半的「信息单位」。LongBench 按语言分别报告，正是为了不把这两把尺子混用。

**辨析｜易错点：** 大海捞针成绩好 ≠ 长上下文能力强。检索只需要模型「注意到一个位置」，而多文档问答需要把分散在几处、甚至互相矛盾的信息**整合**起来。<span class="marginnote">实测中不少模型大海捞针满分、LongBench 综合任务却垫底——因为捞针只测「眼球扫到」，不测「脑子想通」。评测长上下文，不能只看捞针曲线。</span>

## 2 LongBench 的任务地图

LongBench 选了 21 个任务，按能力需求分成 6 类：

| 类别 | 代表任务 | 测什么 | 平均长度 |
| --- | --- | --- | --- |
| 单文档问答 | NarrativeQA、Qasper、MultiFieldQA | 读懂一篇长文后回答细节 | 约 5k–15k |
| 多文档问答 | HotpotQA、2WikiMultihopQA、DuReader、MuSiQue | **跨文档整合与多跳推理** | 约 5k–15k |
| 摘要 | GovReport、QMSum、MultiNews、VCSUM | 全局综合与信息压缩 | 约 5k–10k |
| Few-shot 学习 | TREC、TriviaQA、SAMSum | 从长示例中学习格式与模式 | 约 5k |
| 合成任务 | PassageRetrieval、PassageCount | 可控的检索与计数压力测试 | 约 15k–30k |
| 代码补全 | LCC、RepoBench-P | 仓库级代码理解与生成 | 数千行 |

合成任务的构造尤其值得一提：**PassageRetrieval** 把一句话「缝」进一篇长文档里，问模型「那句话是否出现在文中」，直接测最朴素的检索；**PassageCount** 问「文中提到了几个不同的组织名」，测精确计数。两者都是「答案明确、无法靠语言模型惯性蒙对」的探针——它们的存在，就是为了把「检索」和「计数」这两种最容易退化的能力单拎出来体检。

中文与英文任务各半，长度从几千到 30k 以上。数据怎么来？中文任务从 DuReader、VCSUM 等中文数据集采样，英文任务从 NarrativeQA、HotpotQA 等采样；样本按长度分层，保证每个长度区间都有覆盖。它刻意把「长度」做成一个变量——报告结果时按 0–4k、4k–8k、8k+ 分段汇报，让读者能看出「长度涨到哪一档，模型开始掉」。**任务构造还有一个细节**：每个任务都取「完整文档」而非截断段落——截断会破坏真实的篇章结构，让评测偏容易。这一取舍让 LongBench 的分数更贴近真实部署，也让它迅速成为长上下文模型的标配基准。**长度分层的用意**：按长度分段报告，等于把「模型性能 vs 上下文长度」画成一条曲线——这恰好呼应本专题第一节那张「复杂度 vs n」的曲线：一侧是代价随 n 怎么涨，一侧是能力随 n 怎么掉。两条曲线同读，才看得见优化的全貌。

**为什么 21 个任务而不是 3 个**：单一任务测不出「长上下文能力」——检索好可能整合差，总结好可能计数差。21 个任务覆盖六类能力，平均分才有意义，同时各分项分数能画出能力雷达。**评测的粒度，决定了结论的可信度。**<span class="marginnote">选样的原则是「真实场景优先」：既有从真实语料采样的文档任务，也有可控的合成任务——真实任务保外部效度，合成任务保压力强度，两者互补。这是评测设计里「自然与可控」平衡的范例。</span>

**评测指标**按任务类型不同：问答类用 EM / F1，摘要类用 ROUGE-L，Few-shot 与合成类用 F1 / 准确率，代码类用 Edit Similarity——每种指标只度量它该度量的那一种「对」。以代码类为例：LCC 用 Edit Similarity，把模型补全与参考答案做最小编辑距离归一化，得分反映「改几个字符就能对上」。它比词序型指标更适合代码——代码的正确性不是「词序相近」，而是「字符级接近」。代码任务的存在也提醒我们，长上下文的「文档」不只是自然语言，还有仓库级的程序文本。Edit Similarity 的计算是 $1 - \frac{\text{编辑距离}}{|X| + |Y|}$——它不像 F1 那样对词序宽容，也不像 EM 那样苛刻，是代码任务的地板指标。

拿一个具体任务看评测长什么样。以**多文档问答**的 HotpotQA 子集为例：模型收到一段约 10k token 的拼接文档（由若干支持性段落拼成），要回答一个需要**跨段落整合**的问题，比如「甲国某条约的签署时间，与乙国同类条约相比哪个更早」。答案是「检索到两处事实 + 比较推理」的产物——单点检索做不出来，这正是它区别于大海捞针的地方。<span class="marginnote">LongBench 的任务构造原则是「真实文档 + 真实问题」：不用人工编造的假长文，而是从现有数据集取整篇文档，只在必要时拼接。这样评测的复杂度才贴近真实部署。</span>

## 3 公式解析：F1 与 ROUGE-L 到底在算什么

拿问答的 token 级 F1 与摘要的 ROUGE-L 拆开看，评测「好」的定义就清楚了。

$$
F1 = \frac{2 \cdot \text{Precision} \cdot \text{Recall}}{\text{Precision} + \text{Recall}}, \qquad
\text{Precision} = \frac{|G \cap P|}{|P|},\ \text{Recall} = \frac{|G \cap P|}{|G|}
$$

- **$G$（gold answer）**：参考答案的 token 集合；**$P$（prediction）**：模型回答的 token 集合。交集的个数 = 模型答对了多少个词。
- **Precision** 惩罚「胡说」：预测里无关的词越多，越低；**Recall** 惩罚「漏答」：参考答案里没覆盖的词越多，越低；F1 取调和平均，**两项都不偏袒**。
- **Exact Match（EM）**是更严格的「对」：要求预测与参考答案完全一致（归一化后），答对半个词也不算。EM 与 F1 总是成对出现——EM 看「多少次一击即中」，F1 看「平均命中率」，一个偏严格、一个偏宽松，合起来才是完整的画像。
- **分数的标尺随任务而变**：F1 与 ROUGE-L 都在 0–1 之间，但「0.3」在问答里意味着答错一半、在摘要里意味着要点缺失但结构尚在——跨任务横向比绝对值是常见误读。**先看任务类型，再读分数。**

ROUGE-L 换了一种「对」的定义——最长公共子序列（LCS）。设参考答案为 $X$、预测为 $Y$，LCS 长度记为 $L(X, Y)$：

$$
R_{\text{lcs}} = \frac{L(X, Y)}{|X|}, \quad P_{\text{lcs}} = \frac{L(X, Y)}{|Y|}, \quad \text{ROUGE-L} = \frac{2 R_{\text{lcs}} P_{\text{lcs}}}{R_{\text{lcs}} + P_{\text{lcs}}}
$$

**核心要点：** LCS 保留**语序**——「模型先归纳再举例」的顺序对了才算对，这是摘要评测与问答评测的关键差异。摘要只求「要点齐全、顺序合理」，不要求逐字命中，所以用 LCS 这类序列级指标；问答要求「答案精确」，所以用集合级 F1。**摘要指标的另一面**：ROUGE-L 天然偏好「说得更全」的摘要——LCS 越长分数越高，于是长摘要容易虚高。LongBench 会在计算前做长度归一化与冗余处理，避免「抄原文」刷分——**指标与它的防护机制，是评测设计里一对不可分的组合**。<span class="marginnote">选指标就是在定义「好」：F1 把「好」定义为词袋重叠，ROUGE-L 把「好」定义为顺序保留。评测报告数字之前，先想清楚指标在定义哪种「好」。</span>

## 4 关键发现：长上下文模型的「真实画像」

LongBench 在 2023 年用当时的主流长上下文模型（GPT-3.5、Claude 等）跑出了一幅清醒的画像：

**其一，「支持长上下文」不等于「长上下文用得好」**。多个宣称 32k/128k 的模型，在平均长度 10k 左右的综合任务上，得分反而低于更小但短上下文更强的模型——长窗口是**可选项**，模型未必学会用。**一个反直觉的榜首现象**：LongBench 发布时的最优模型并不是「窗口最大的模型」——16k 窗口的 GPT-3.5 常常击败宣称 32k 甚至 128k 的竞品。窗口大只代表「装得下」，任务分高分毫取决于「用得起来」。**其二，合成任务全线垫底**：PassageCount、PassageRetrieval 这类「必须精确数清/找全」的任务，几乎所有模型都大幅下降——长上下文模型的计数与精确检索能力普遍不足。**为什么合成任务这么难**：精确计数与定位要求注意力把权重集中到「正确的那一个位置」上，而训练出来的注意力往往倾向分散——合成任务像一面照妖镜，把「注意力分散」这个通用弱点照得清清楚楚。**其三，长度与质量并非单调关系**：部分模型在中等长度反而最强，超过某阈值急转直下——位置编码外推的缺陷在此现形。把结果按「长度分档」画成曲线（0–4k、4k–8k、8k+ 三档），能清楚看出哪些模型是「稳健外推」（曲线平缓），哪些是「硬撑窗口」（曲线在 8k 处跳水）——**这正是我们上一节讲位置编码时反复强调的「报梯度而非单点」在评测侧的实现**。把 21 个任务按平均长度重排，退化模式更是各异：有的 8k 内平稳、8k 后跳水（外推断裂），有的全程缓慢下滑（信息遗忘），有的在中等长度反而最好（注意力分布偏向）。每一条退化曲线，都是架构问题的一张 X 光片。<span class="marginnote">与大海捞针测试对照：捞针测「找到一处」，LongBench 测「整合多处」——后者是真实长文档工作的日常，也是优化者真正该盯的指标。</span>

还有一个著名的「位置效应」值得记住：**Lost in the Middle**（Liu et al., 2023）发现，当相关信息位于文档**中部**时，模型的利用能力显著下降——注意力把重心压在开头与结尾，中间成了「盲区」。这解释了为什么长上下文模型对「信息出现在哪里」极度敏感，也为滑动窗口、全局 token 等设计提供了实证支撑。<span class="marginnote">该现象在 LongBench 里同样被复现：把证据从文档开头移到中部，多数模型的问答 F1 掉 10–20 个点。设计长上下文应用时，「把重要信息放开头或结尾」是一条朴素但有效的工程建议。</span>

值得注意的是，LongBench 当年的头部模型（GPT-3.5-Turbo-16k、Claude 系列）在 21 个任务上的平均分并不高——即便是最好的模型，平均分也只到六七成。**中英任务的分野**同样值得注意：LongBench 特意做到中英各半，因为中文长文档（长文摘要、阅读理解）的句法结构与检索路径与英文不同；实测多数模型在中文长任务上普遍低约 10 个点——「长上下文能力」存在语言依赖，只用单语评测会得出误导性结论。这给后来的研究留出了巨大的空间，也直接催生了评测本身的迭代：LongBench-v2（2024）把长度拉到 8k–128k 并引入「真实任务过滤」，RULER 用可编程模板把检索、多跳、聚合等能力**分项**测度，∞Bench 则把中文长文档与代码理解放进更大规模。<span class="marginnote">评测基准本身也在内卷：从「测能不能读完」进化到「测用得有多好」。读长上下文评测文献时，先看它的任务长度与真实度，再看它报的数字。</span><span class="marginnote">Lost in the Middle 与注意力分布的软注意力偏移有关，也与位置编码的退化有关——它把本专题的位置编码、注意力结构、评测三块内容串成了一条线。</span>

## 5 评测的纪律：几条避坑守则

**其一，困惑度（perplexity）不是长上下文能力的证据**。PPL 测的是「文本分布学得有多好」，而长文档问答需要的是「给定的信息用没用上」——两者几乎无关。曾有模型在 128k 外推后 PPL 依旧漂亮，LongBench 综合分却垫底：**PPL 看的是「写得顺不顺」，任务分看的是「答得对不对」**，这两件事被同一块 PPL 数字掩盖时最危险。**其二，固定 prompt 与一次抽样不可信**：长上下文评测对 prompt 措辞、解码温度极度敏感，方差远大于短任务。LongBench 官方建议同一任务跑多次取均值、并固定解码配置——这既是公平性要求，也是统计常识：被测对象（语言模型）本身是随机的。

**榜单的阅读纪律**：LongBench 有公开榜单，但读榜单要先看三样东西——用的版本（是否过滤了训练集泄漏）、报的分档（单点还是梯度）、以及 prompt 与解码是否公平。基准数字会过时，评测方法论不会：理解了「任务 × 长度 × 指标」的三维结构，任何新基准你都能快速判断它的说服力。**可复现性**同样关键：LongBench 对每个任务规定统一的 prompt 模板与解码配置并公开评测脚本——这不是吹毛求疵，而是长上下文评测方差太大的必然要求。跑同一个模型，换一种 prompt 措辞，分数可能差 5–10 个点；没有固定协议，任何榜单对比都不可信。

**旗舰模型的共性**：榜单前列的模型大多不是窗口最大的，而是「检索 + 整合 + 鲁棒性」综合最强的；它们也几乎都是同时部署了本专题前几节整套优化（FlashAttention + GQA + RoPE 长基频）的模型。架构清单写在配置文件里，分数写在榜单上——当两者对上，说明优化确实兑现成了能力。

**评测的开放性问题**：上下文还在不断变长，但评测方法论没有同步跟上——128k 时代的正确评测，可能不只是「更长的 LongBench」，还包括信息密度、干扰物比例、多任务并发等新维度。这个开放问题，正是下一轮长上下文研究的起跑线。

**评估一个长上下文模型的最低套餐**：一份「长长度 × 多任务 × 双语言 × 分档报告」的基准结果、一条随长度变化的退化曲线、加上对位置外推与检索能力的专项检查——有了这套最低套餐，长上下文能力的全貌才不至于被单点分数掩盖。**其三，要报告「梯度」而非「单点」**：只报「32k 表现」而不报「4k / 8k / 16k / 32k 全程」，无法区分「稳健外推」与「恰好撑住」。**其四，警惕「长度与难度的混同」**：LongBench 里 8k 的检索任务可能比 20k 的总结更容易——任务要按「长度 + 能力类型」双维划分才有意义。评估一个长上下文模型，与其只问「支持多长」，不如问「在什么长度上、什么类型的任务还能及格」。说到底，**评测是优化闭环的验收员**：本专题每一节的技术，最终都要回到 LongBench 这类基准上兑现——一个优化在 PPL 上好看、在 LongBench 上无效，等于没优化；反之亦然。评测纪律，就是优化者的诚实底线。<span class="marginnote">这条纪律也是评测设计的通用原则：好的评测要给出「随长度变化的退化曲线」，而不是一个孤立的数字——本专题前面各节反复出现的「复杂度随 $n$ 的变化」，在评测侧就是「性能随 $n$ 的变化」。</span>

## 6 小结

- 长上下文评测的难点：**退化原因多样**，必须区分「读得完」与「用得起来」。
- **大海捞针**只测检索，**LongBench** 的 21 个综合任务测「检索 + 整合」。
- 六类任务：单/多文档问答、摘要、Few-shot、合成、代码补全；中英双语、长度数千到 30k+。
- 指标各有所指：问答用 token 级 F1，摘要用 LCS 型 ROUGE-L——指标在定义「好」。
- 关键发现：长窗口 ≠ 用得好；合成任务全线偏弱；Lost in the Middle 揭示中部信息利用不足。
- 评测纪律：PPL 不作数、多长度报梯度、固定 prompt 反复抽样；榜单阅读看版本、分档与公平性。
- 最低套餐：多任务 × 双语言 × 分档报告 + 退化曲线 + 外推与检索专项检查。
- 评测是优化闭环的验收员：PPL 好看不算数，LongBench 及格才算优化兑现。
- LongBench 与后续 LongBench-v2、RULER、∞Bench 一脉相承：从「测能不能读完」进化到「测用得有多好」。
- 作为 2023 年的基准，它的绝对数字已被超越，但「任务 × 长度 × 指标」的三维结构成了长上下文评测的语法。

到这里，本专题从「$O(n^2)$ 从哪来」走到「怎么测长上下文真的有用」，走完了一条完整的闭环：**复杂度 → 稀疏化 → 线性化 → IO 优化 → 分块 → 窗口 → 位置外推 → 缓存共享 → 评测**。在下一专题，我们将把这些能力放进**检索增强（RAG）**的框架，回答「当上下文太长装不下时，怎么选着读」。
