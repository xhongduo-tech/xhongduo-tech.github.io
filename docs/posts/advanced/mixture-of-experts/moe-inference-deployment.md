## 为什么从推理部署讲起

MoE 的招牌是「万亿参数」，但**万亿参数怎么跑起来**才是真正的战场。训练可以用几千块 GPU 堆，推理不行——服务的延迟、单机显存、吞吐成本都要精打细算。好消息是：MoE 的稀疏性在推理时反而成了资产——**每次推理只激活 $K$ 个专家，其余 $E-K$ 个专家这一轮根本用不到**。既然用不到，为什么要让它们占着 GPU 显存？

这就是 **专家卸载（expert offloading）** 的核心思路：把不常用的专家放到显存之外（CPU 内存甚至 NVMe），GPU 只保留「本轮活跃」的专家。Rajbhandari 等人在《DeepSpeed-MoE: Advancing Mixture-of-Experts Inference and Training to Power Next-Generation AI Scale》（ICML 2022）里把它做成了系统级方案。<span class="marginnote">DeepSpeed-MoE 的口号是「让 MoE 推理在单个 GPU 上跑起来」：用显存卸载 + 负载优化，把原本需要多卡的 MoE 推理压进单卡。对一个「万亿参数」架构来说，这是「能落地」与「只能看」的分水岭。</span>这一节我们算清推理的显存账，讲卸载的三种路由策略（PR-MoE 等），再讨论 MoE 推理与稠密推理的本质差别。

## 1 推理的显存账：为什么 MoE「看起来装不下」

设模型总参数 $P$，其中专家参数占 $P_{exp}$，单 token 激活参数 $P_{act}$。推理时 GPU 需要驻留多少参数？

$$\mathrm{GPU}_{\mathrm{mem}} \gtrsim P_{exp} + P_{\mathrm{other}} + \mathrm{activations} \approx P + \mathrm{activations}$$

- 若不做卸载，**全部专家参数 $P_{exp}$ 都要常驻显存**——236B 总参的 DeepSeek-V2 就要 236B × 2 字节 ≈ 472GB，远超出单张 H100（80GB）。
- 但**每次推理只用到其中约 $K/E$ 的专家**：DeepSeek-V2 激活约 21B 参数，只占总参的 ~9%。
- 于是矛盾浮现：**模型要装 236B 才能「随时用」，但每次真用的只有 21B**——其余 215B 是为了「可能用到」而付费。

卸载要解决的就是这「可能用到」的 215B：不常驻 GPU，只在被路由到时**临时调入**。<span class="marginnote">这本质上是「以带宽换显存」：GPU 显存贵、CPU 内存便宜、NVMe 更便宜；把参数放在慢但大的层级，用的时候搬上来。它和操作系统把不常用页换到磁盘、浏览器把后台标签页冻结，是同一个「冷热分层」思想——只是换成了 GPU 的语境。</span>

## 2 卸载的架构：热层、温层、冷层

DeepSpeed-MoE 的推理按「活跃度」给参数分三层：

**热层（GPU 显存）**：注意力、路由器、以及**被高频激活的专家**——这一层要零延迟。
- **温层（CPU 内存）**：**其余专家**的权重常驻 CPU 内存，被路由到时才通过 PCIe/NVLink 异步搬运到 GPU。
- **冷层（NVMe/磁盘）**：最不常用的专家可以进一步下放到 NVMe，用到时再读入 CPU 再进 GPU（两级搬运）。

一次推理的流程是：路由决定本轮需要哪些专家 → 若不在 GPU 就**异步预取**（prefetch）→ 等搬运完成再执行专家计算。为了不让搬运阻塞生成，系统用**流水线重叠**：当前 token 在算的时候，下一个 token 需要的专家已经在路上。**隐藏搬运延迟，是卸载能跑通的关键工程点。**<span class="marginnote">「预取 + 重叠」和 CPU 里的 cache prefetch 是同一个模式：预测你马上要什么，提前搬。MoE 的好处是<strong>路由给了预取一个天然的预测器</strong>——路由器几乎免费地告诉你「下一批 token 要去哪个专家」。</span>

## 3 卸载的核心决策：哪些专家常驻 GPU

显存放不下所有专家，那**把谁留在 GPU** 就成了一个组合优化问题。DeepSpeed-MoE 对比了三种策略：

**随机（Random）**：随机选一批常驻——最差，路由命中率低，频繁搬运。
- **Top-K（按使用频率）**：统计训练/历史推理里每个专家的被选中次数，把**最高频的 $M$ 个**留在 GPU。直观有效，但「频率」与「实时」脱节——某些低频专家在特定输入下照样被需要，还是会搬运。
- **PR-MoE（Profiled routing, 画像路由）**：用路由器的**打分分布**而不是简单的频次来画像——对每类输入，预测它最可能路由到哪些专家，动态决定常驻集合。在 DeepSpeed-MoE 的实验里，PR-MoE 的命中率最高、搬运最少。<span class="marginnote">PR-MoE 与上一节的「平滑路由」直接挂钩：只有路由是平滑、可预测的，才能用画像去预测「这类输入会找哪个专家」。训练稳定性又一次在推理端兑现——两条线在这里收拢了。</span>

## 4 公式解析：卸载的命中率与搬运成本

设 GPU 常驻专家数 $M$、专家总数 $E$，单专家参数 $p$，推理的总搬运字节数近似为：

$$\mathrm{Bytes}_{\mathrm{transfer}} \approx p \cdot \sum_{\mathrm{layers}} \mathbb{E}\Big[ \#\{\text{本轮路由到非驻留专家}\} \Big]$$

- **驻留率 $M/E$**：GPU 能留的比例。$M$ 越大，命中率越高、搬运越少，但显存占用越大——**显存与搬运带宽的权衡**。
- **命中率（hit rate）**：$H = \frac{\text{路由到驻留专家的 token 数}}{\text{总路由数}}$。PR-MoE 的目标就是最大化 $H$，把 `Bytes_transfer` 压到最低。
- **搬运成本模型**：每次「专家不在 GPU」就多付一次 `CPU→GPU` 搬运（PCIe 带宽约 32 GB/s，远低于 GPU 显存带宽）。如果 $H$ 不足，搬运时间反而超过省下的计算时间——**卸载不是无条件赢，是命中率够高才赢**。

一个经验数字：当每 token 激活专家数 $K$ 很小、且高频专家高度集中时（现实中正是如此——少数专家承担大部分路由），$M/E$ 可以做得很小（比如常驻 20% 的专家），命中率仍能超过 95%。**推理时 MoE 的负载分布比训练时更「尖」**——因为推理输入往往集中在少数领域，而预训练让模型学会了「专才」分工。<span class="marginnote">这解释了为什么「训练时最头疼的负载失衡（退化一节）」在推理时反而成了帮凶之外的好事：训练要均衡是怕饿死专家，推理要集中是因为高频专家真的就那么几个——卸载正是把「少数专家承担大部分工作」这条规律拿来变现。</span>

## 5 MoE 推理 vs 稠密推理：不止是显存

卸载之外，MoE 推理还有两个与稠密模型根本不同的工程问题：

**动态计算图**：稠密模型的张量形状是编译期固定的；MoE 的 token 流向哪个专家是**运行时才知道**的，形状动态、分桶动态。这要求推理引擎支持**动态 batch** 与**在线聚合（grouped GEMM）**，不能用传统「静态编译」的方式跑。
- **batch 管理**：稠密推理用静态 batch 很高效；MoE 里不同 token 去不同专家，batch 必须在「按专家分桶」后重排，还得处理「桶装不下」的溢出——上一节容量因子的讨论在推理时同样适用。

DeepSpeed-MoE 的系统报告给出了定量的收益：相比朴素部署，卸载 + 优化后**推理吞吐提升数倍、单卡即可承载原本需多卡的模型**。它的整套「冷热分层 + 预取重叠 + PR-MoE 画像」后来被 vLLM、SGLang 等推理引擎继承为 MoE 支持的标准件。<span class="marginnote">至此本专题的线索全部收拢：训练端（路由/均衡/稳定）与推理端（卸载/预取/画像）共用同一套「稀疏性」——训练把稀疏性练出来，推理把稀疏性变现。MoE 不是一个模型结构，而是一整套「以稀疏为中心」的系统工程。</span>

### 一个具体例子：单卡跑「装不下」的模型

把整条流水线串成一个数字例子。设模型 100B 参数（其中专家占 90B），单张 A100 显存 80GB：

- **不卸载**：90B 专家 × 2 字节 ≈ 180GB，远超 80GB——**单卡根本装不下**，只能靠张量并行把 90B 切成多卡；
- **卸载（Top-K 常驻）**：统计路由，发现 80% 的推理流量只经过约 20% 的高频专家——于是只把 18B 高频专家 + 注意力层常驻 GPU（约 40GB，能放下），其余 72B 专家放 CPU 内存（DDR 很便宜）；
- **运行时**：路由命中高频专家的概率约 90%+，命中时零搬运；未命中时触发「CPU→GPU」预取，用下一轮的生成时间把搬运隐藏掉。

结果：**单卡跑起了原需 3 卡的模型，代价是平均每 token 多几毫秒的搬运时间**——对离线批量推理这是很划算的交易。这个例子也说明卸载的适用范围：**流量越集中（命中率越高）、生成越长（越能隐藏搬运），卸载越划算**。

### 卸载与训练端负载均衡的「反向」关系

一个容易误会的点值得专门辨析：**训练时我们要负载均衡，推理时我们反而要「负载集中」**。

- 训练：均衡是目标——防止专家饿死、防止 all-to-all 桶失衡（退化与并行两节）；
- 推理：高频专家高度集中在少数几个，是卸载能成立的前提——**越集中，GPU 常驻集合越小，搬运越少**。

这不是矛盾，而是两个阶段目标不同：训练用「均衡」换「模型健康」，推理用「集中」换「部署经济」。**同一个 MoE，训练要它分散，推理要它聚拢**——理解这层「反向」，才能真正理解为什么 DeepSpeed-MoE 要把「画像路由」做成训练与推理的桥梁：它把训练阶段学到的「每个 token 大概找谁」在推理时兑现成部署决策。

### 与主流推理引擎的关系：vLLM、SGLang 的 MoE 支持

DeepSpeed-MoE 的「卸载 + 预取 + 画像」后来沉淀成了推理引擎的标配功能：

- **vLLM** 把「动态 batch + 分组 GEMM」做成默认：MoE 层的 token 按专家分桶，用 grouped GEMM 一次算多个小专家的批量乘法，避免逐个专家串行启动；
- **SGLang** 进一步做「结构化调度 + 连续批（continuous batching）」，把稀疏路由与请求调度结合，让每个专家的桶保持「大而整齐」；
- **业界共识**：MoE 推理的性能瓶颈不再是「算力」而是「把动态的、稀疏的计算流组织成硬件友好的批量」——这恰恰是本节的「动态计算图 + 分桶」问题的工程化。

所以「MoE 推理部署」与「稠密推理部署」是两套系统：前者多了路由、分桶、动态形状、专家搬运四个维度。理解了本节，你就理解了现代 LLM 推理引擎里「MoE 支持」到底在解决什么。

### 什么时候不该用卸载

卸载不是万能药，它有三个明确的「不适用」场景：

- **批量小、延迟敏感**：单次请求只有几个 token、且路由分散时，命中率低、预取来不及，搬运延迟直接暴露——在线对话这类场景要慎用大范围卸载；
- **专家负载太分散**：如果模型训练得「雨露均沾」太彻底（负载均衡过度），高频专家不集中，常驻集合要覆盖的专家太多，卸载省不下显存；
- **带宽极低**：PCIe 3.0 与 NVLink 的搬运速度差一个数量级，低带宽设备上「搬」比「算」还慢。

判断口诀：**命中率高 + 生成长 + 带宽够，才值得卸载**。反之，老老实实多卡张量并行更省心。

## 6 小结

- **推理显存账**：总参 236B 装不下、激活只要 21B——卸载把「可能用到」的专家搬出 GPU，以带宽换显存。
- **三层冷热分层**：GPU（高频专家）/ CPU（其余专家）/ NVMe（冷门专家），异步预取 + 流水线重叠隐藏搬运延迟。
- **常驻选择**：随机 < Top-K（按频次）< PR-MoE（按路由画像）——命中率决定卸载是否划算。
- **卸载成立的前提**：路由集中且可预测；训练稳定性（上一节）是「可预测」的来源——两条线在推理端收拢。
- **系统性差异**：动态计算图、分组 GEMM、动态 batch，让 MoE 推理引擎与稠密推理引擎是两种工程。

至此，我们从 Shazeer 2017 的稀疏门控一路走到 DeepSpeed 2022 的卸载部署：**MoE 的全部秘密，就是「让网络足够大、让每次计算足够小」这一句话的层层兑现**。从 KeepTopK 的稀疏门控，到 top-1 的简化，到负载均衡与容量因子的软硬兼施，再到专家并行与细粒度切分的规模化，最后在推理端把稀疏性变现成显存与吞吐——每一层都在回答同一个问题的不同侧面。
