## 为什么从专家容量因子讲起

前两节我们一直在问「专家怎么选」：路由打分、负载均衡、防退化。但 MoE 还有个被低估的工程问题：**就算路由是均匀的，专家也装不下**。想象一个 batch 有 4096 个 token、64 个专家，理想情况下每个专家分到 64 个 token。但路由是离散决策，batch 里 token 分布难免有起伏——某个专家可能一下子收到 120 个 token。它该收吗？不收的话那些 token 怎么办？

**专家容量因子（expert capacity factor, CF）** 就是回答这个问题的开关。它由 GShard 提出、在 Switch Transformer 里被系统研究，决定了「每个专家最多能接待多少 token」以及「装不下的 token 何去何从」。它直接控制 MoE 的**计算效率与模型质量的第一个直接矛盾**，也是 Switch 论文里被反复权衡的核心旋钮。<span class="marginnote">容量因子是「先有负载均衡损失、再有容量上限」的原因：aux loss 让路由尽量均匀，容量上限则是「万一不均匀时的最后防线」。两者是 MoE 的刹车与保险带。</span>

## 1 容量公式：一个 batch 一个「硬预算」

设 batch 内 token 总数为 $N$，专家数为 $E$，容量因子为 $C$，则每个专家的容量是：

$$\mathrm{Cap}_j = \left\lceil \frac{C \cdot N}{E} \right\rceil$$

逐项看：$N/E$ 是「完全均匀时的每专家 token 数」；$C \ge 1$ 是这个理论值的**放宽倍数**。$C=1$ 表示「每个专家最多只接理论均摊量的 token」，$C=1.5$、$2$ 则是「允许偶尔波动到 1.5、2 倍」。GShard 用 $C=2$（配合 top-2 路由），Switch 用 $C=1$ 起步（配合 top-1 与 aux loss）。<span class="marginnote">`ceil` 向上取整不是细枝末节：它保证极端情况下（$E > N$，专家比 token 还多）每个专家至少能收到 1 个 token，否则会出现「容量为 0」的荒谬专家。工程细节里全是这类角落。</span>

**为什么需要这个硬预算？** 因为分布式下每个专家被放在某台设备上，它的计算是**同步批处理**的。设备要为每个专家预分配一块固定形状的显存张量来存放这 $E$ 个专家的输入——如果 token 数无上限，显存就无法预分配，也无法做批量矩阵乘法。容量上限把「每个专家最多几个 token」变成一个编译期可知的常数，硬件效率才有保证。

## 2 装不下怎么办：丢弃 token

这是容量因子最受争议、也最说明权衡的部分。当路由把超过 $\mathrm{Cap}_j$ 个 token 发给专家 $j$ 时，超出部分的 token 被 **丢弃（drop）**：

被丢弃的 token **不经过该专家的 FFN**，这一层的输出直接走**残差（residual）旁路**——即输出等于输入，等于「这一层没发生任何变换」。
- 训练时丢弃是**有意的正则**：它惩罚了路由器的过度集中（把 token 送进一个塞不下的专家 = 自毁质量），相当于给「负载均衡损失」加了一道**硬约束的牙**。<span class="marginnote">这里有个漂亮的耦合：aux loss 是软惩罚「路由偏心」，容量上限是硬惩罚「路由溢出」。软的先劝，硬的直接断（丢弃 token）。Switch 论文里，辅助损失把丢弃率压到接近 0，让两者在训练中配合默契。</span>
推理时丢弃意味着**信息丢失**：token 在这一层没有获得任何非线性的语义变换，直接原样前传——如果丢弃率高，模型质量肉眼可见地下降。

**辨析｜易错点：** 不要把「丢弃 token」误解为「丢弃训练样本」。被丢弃的 token 仍然存在于 batch 里、仍然参与前后层的梯度，只是**在这一个 MoE 层没有经过专家变换**。丢弃的是「这一层对它的改造」，不是它本身。

## 3 容量因子与质量的权衡曲线

Switch 论文做了系统的消融，画出的是一条经典的权衡曲线：**容量因子 $C$ 越大，丢弃越少、质量越好，但计算量越大、稀疏性收益越小**。

- $C = 1.0$：计算最省，但 batch 路由波动时丢弃率上升，质量损失最大。Switch 在配合 aux loss 后，实践中 $C=1.0$ 足够——aux loss 把路由按得足够均匀，丢弃率被压得很低。
- $C = 1.5, 2.0$：给路由更多余量，丢弃几乎消失，质量逼近「永不丢弃」的理想值，但专家计算量按 $C$ 倍放大——专家空闲时也在吃算力。
- $C \to \infty$：等于没有容量上限，退化回「每个专家都全量计算」，稀疏性红利清零——MoE 名存实亡。

一个常被引用的经验数字：**在 Switch 的设定下，aux loss + $C=1$ 的效果 ≈ 无 aux loss + 大容量**，但前者快得多。这就是为什么「负载均衡损失」和「容量因子」必须成对出现——**负载均衡损失让容量可以取小，容量因子让负载均衡的失败不至于灾难化**。<span class="marginnote">这条「用软约束换小容量、小容量保效率」的思路，是 MoE 工程哲学的一个缩影：能用正则解决的问题，就不付结构上的成本。后文《MoE 训练稳定性》里 z-loss 也是同一哲学。</span>

## 4 公式解析：被丢弃的 token 如何流经网络

把整个机制串成一张「token 命运图」：

$$y_t = \underbrace{x_t}_{\text{残差旁路}} + \underbrace{\mathbb{1}\{t \in \mathcal{A}_j\} \cdot p_{i^*}(x_t) \cdot \mathrm{FFN}_{i^*}(x_t)}_{\text{专家路径，可能被丢弃}}$$

- **$\mathcal{A}_j$**：专家 $j$ 本 batch 实际「收下」的 token 集合，容量 $|\mathcal{A}_j| \le \lceil CN/E \rceil$。路由来的 token 按到达顺序（或按门控概率排序）填坑，坑满即拒。
- **指示函数 $\mathbb{1}\{t \in \mathcal{A}_j\}$**：token 是否真的被接走。为 0 时，专家路径整项消失，$y_t = x_t$——token 原样穿过本层。
- **$p_{i^*}(x_t) \cdot \mathrm{FFN}_{i^*}(x_t)$**：正常情况下的专家输出（top-1 情形），乘门控权重后叠加到残差上。

三个量共同决定 token 的结局：**路由概率（谁来）**、**容量预算（收不收）**、**填充顺序（谁先来）**。一个隐蔽但重要的细节：Switch 里被丢弃的 token **不进路由器损失的分母**——丢弃率太低时，aux loss 会失去「发现负载失衡」的观察窗口，这是训练时监控丢弃率（一般应 < 1%）的原因。

## 5 容量因子的现代演化

容量因子没有停留在 2020 年的样子，它在后续工作里被反复修改：

- **DeepSeek-MoE / DeepSeek-V2**：放弃「丢弃」，改为**更激进的负载均衡 + 更小的容量**——用共享专家与 sigmoid 路由（上一节）把负载压得足够均匀后，容量可以取得更小而不担心丢弃，单位算力内塞进更多专家。
- **Mixtral**：把 MoE 训练转为「负载均衡损失权重可调」，容量设为充足值，把丢弃压到 0——推理时用「无丢弃」保证每 token 都经过两个专家，服务质量稳定。
- **DeepSpeed-MoE**：把「丢弃」反向利用——既然某些 token 本来就会丢，不如显式地让「低置信度 token」走更便宜的路径，把算力预算化。<span class="marginnote">这条线索在本专题最后的《推理部署》一节会再出现：容量因子本质上是在「效率」与「保真」之间做预算分配，推理部署的专家卸载也是同一类「预算思维」。</span>

### 一个具体例子：容量是怎么「装不下」的

设 batch 有 $N = 2048$ 个 token、$E = 64$ 个专家、容量因子 $C = 1$。则 $\mathrm{Cap}_j = \lceil 2048/64 \rceil = 32$，每个专家最多接 32 个 token。若路由把 41 个 token 分给了专家 7，就有 9 个 token 被丢弃、走残差旁路：

- 这 9 个 token 在本层没有经过任何非线性变换，输出就是输入；
- 它们的梯度仍会传回**前面的层**（注意力、前一层），只是**这一层的专家路径**对它们没有贡献；
- 如果 batch 里同时有 5 个专家「超员」，丢弃的 token 总数就是这几个溢出的和——训练日志里应监控「丢弃率 = 被丢弃 token 数 / 总 token 数」。

**辨析｜易错点：** 丢弃率与 aux loss 是两个不同的观测。aux loss 低（路由看起来均匀）不代表丢弃率一定低——因为「均匀」是平均意义，batch 内的随机起伏仍可能让个别专家瞬间超员。所以容量因子与 aux loss 要一起看：**aux loss 管长期偏心，丢弃率管瞬时溢出**。

### 容量因子如何与专家并行耦合

容量因子最初是 GShard 为分布式场景设计的，它的工程意义在《专家并行》一节会彻底展开，这里先给直觉：当专家分布在不同设备上，每台设备必须**预先分配**一块形状固定的显存来接收「路由过来的 token 块」。容量上限让这块显存的大小是编译期常数——`Cap_j × d` 的张量，写死。**没有容量因子，设备就无法预分配显存、无法做批量的专家 GEMM，专家并行的「可预分配」红利就全部落空**。所以容量因子既是质量旋钮，也是并行系统的「形状约定」——这个双重身份，是它常常被误以为是「纯正则」的原因。

### 一个容易混淆的量：容量因子 vs 专家数

「容量因子」这个名字容易让人误以为是「专家数」。两者完全不同：

- **专家数 $E$**：层里共有多少个专家——决定参数量与「分工粒度」；
- **容量因子 $C$**：每个专家在一个 batch 里最多接多少 token 的放宽倍数——决定「溢出如何处理」与计算量。

一个 MoE 层同时有 $E$ 和 $C$ 两个旋钮，却经常被混为一谈。一个有用的记忆：**$E$ 管「雇多少专家」，$C$ 管「每个专家允许有多忙」**——一个管结构，一个管负载。调参时先定 $E$（结构），再定 $C$（效率）。

### Switch 论文里的容量实验

Switch 论文对容量因子做了系统的消融，几个关键发现值得记住：

- **$C=1.0$ + aux loss 是「甜点」**：在标准配置下，$C=1.0$ 配合负载均衡损失，质量与「容量无穷」几乎持平——因为 aux loss 把路由按得足够均匀，溢出极少；
- **$C=1.5$、$2.0$ 提升有限**：放宽容量只带来极小质量增益，却让专家计算量线性上涨——**在「质量-效率」曲线上，$C=1.0$ 已经在拐点附近**；
- **$C$ 过小的代价是丢弃率**：$C=0.5$ 时丢弃率陡增，质量明显下降——容量因子有个「不能低于 1」的隐含下限。

这条实验曲线是「负载均衡损失 + 容量因子」这对组合最好的注脚：**前者让后者可以取得很小而不伤质量，后者让前者的失效不至于灾难化**——一对完美互补的软硬约束。

### 与《负载均衡损失》的回扣

本节的「软硬约束互补」在负载均衡损失一节已埋下伏笔，这里正式收口：**aux loss 是软约束（惩罚偏心但不强制），容量上限是硬约束（装不下就丢弃）**。理解这对组合，是理解 MoE 一切工程决策的钥匙——几乎所有「正则 + 上限」的搭配（如 KV 缓存上限、max tokens per request）都是同一个模式：先让软约束尽量把行为按向理想，再用硬上限兜底。

补充一个实用视角：**容量因子是最容易「先改后验」的超参数**——改大改小都能立刻从丢弃率、吞吐、loss 三个指标上看出反应，是调试 MoE 时最先该动的旋钮之一。

## 6 小结

- **容量公式**：$\mathrm{Cap}_j = \lceil CN/E \rceil$，$C$ 是理论均摊量的放宽倍数；它让每个专家的显存与计算可预分配，是分布式效率的前提。
- **丢弃机制**：容量满员后 token 被丢弃，该层输出走残差旁路 $y_t = x_t$；丢弃的是「本层的变换」，不是 token 本身。
- **权衡曲线**：$C$ 大 → 少丢弃、质量好、但算力浪费；$C$ 小 → 省算力、要 aux loss 兜底。Switch 的结论：aux loss + $C=1$ 又快又不丢质量。
- **软硬配合**：aux loss 是软约束、容量上限是硬约束；负载均衡损失让容量可以取小，容量因子让均衡失败不至于灾难化。
- **演化**：现代 MoE（DeepSeek、Mixtral）倾向于把容量设得足够、用结构手段压负载，丢弃率趋近 0。

在下一节，我们从「单个 MoE 层内部的预算」跳到「多个设备之间的布局」：**专家并行（Expert Parallelism）**——专家放在不同 GPU 上时，token 怎么被搬运、通信量怎么算、GShard 又是怎么把这一切在 6 000 亿参数上跑通的。
