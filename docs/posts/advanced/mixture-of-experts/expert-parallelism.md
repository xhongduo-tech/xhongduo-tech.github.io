## 为什么从专家并行讲起

前五节我们都在「单个 MoE 层」内部打转：怎么选专家、怎么均衡、怎么限流。但 MoE 之所以能撑起万亿参数，还差最后一块拼图——**这些专家物理上放在哪、token 怎么在设备间搬家**。答案就是 **专家并行（Expert Parallelism, EP）**：把 $E$ 个专家分散到不同设备上，每台设备只装一部分专家，路由把 token 送去对应的设备计算。

它是 GShard（Lepikhin et al., 2020）的原创贡献之一。GShard 把 MoE 装进 Transformer 机器翻译，在 2048 块 TPU v3 上训练出 6 000 亿参数的模型——这是「MoE + 大规模并行」的第一次工业级合体。<span class="marginnote">6 000 亿参数不是靠「一台设备塞不下」，而是靠「专家的容量增长不再受单卡显存约束」。参数总量可以无限涨，只要专家足够多、设备足够多。这为后文的万亿参数铺了路。</span>这一节我们回答：专家并行与其他并行范式的关系、token 如何在设备间流动（all-to-all 通信）、以及通信量为什么是 EP 的第一成本。

## 1 三种并行范式：数据并行、模型并行、专家并行

大模型训练把「切」这个词玩出了三种形态：

**数据并行（data parallelism, DP）**：每台设备放**完整模型**，各吃一部分数据，梯度 AllReduce 汇总。模型得装得进单卡。
- **模型并行（model parallelism, MP / tensor parallelism, TP）**：把**同一个层/张量**切到多卡上，卡间频繁同步。解决「一层装不下」。
- **专家并行（expert parallelism, EP）**：把 **$E$ 个专家**按「层内切分」放到不同设备上，每台设备持有部分专家；token 经路由**被发送到**持有对应专家的设备上计算，再送回。

一句话区分：**DP 切数据、MP 切张量、EP 切专家**。<span class="marginnote">EP 和 MP 常被混用，但机制完全不同：MP 里每台设备算的是同一层的一小片，每次前向都要同步；EP 里每台设备持有的是<strong>独立的、完整的专家</strong>，token 分流过去、算完回来，设备之间不需要持续的梯度同步——只有路由导致的数据搬运。</span>GShard 的布局其实是三者叠加：在设备网格上，注意力等非 MoE 层用 **MP/DP**（每个设备副本独立算），FFN 专家层用 **EP**（专家切到不同设备，token 按路由搬家）。

## 2 All-to-All：token 的「分拣与搬家」

专家并行里的核心原语是 **all-to-all 通信**。设 $D$ 台设备，每台设备先收到一批 token（比如该设备上注意力层输出的那部分 token），路由决定每个 token 要去哪个专家，于是：

1. **本地分拣**：本设备把 token 按「目标专家所在的设备」分桶，桶 $k$ = 要发往设备 $k$ 的 token 集合。
2. **全交换（all-to-all）**：每个设备把自己各桶发给对应设备，同时收到其他设备发来的桶——最终每台设备持有「属于本设备专家」的 token 块。
3. **批量专家计算**：设备对自己持有的专家做批量前馈。
4. **反向 all-to-all**：把计算结果按 token 原籍送回，并在原设备上按门控权重加权求和。

整个过程是通信与计算交替的流水线。通信量是 EP 的命门：**每次专家前馈，都要经历「送出去—算—收回来」两轮全交换**，通信开销与路由选择的专家数成正比。

## 3 公式解析：为什么 top-1 通信量是 top-2 的一半

设 batch 共 $N$ 个 token、每 token 维度 $d$，每个 token 被路由到 $k$ 个专家，则每层专家前馈的**通信字节数**约为：

$$\mathrm{Comm} \approx 2 \cdot k \cdot N \cdot d \cdot (4\ \text{bytes})$$

- **$k \cdot N \cdot d$**：每个 token 被复制成 $k$ 份（要送 $k$ 个专家），一次全交换搬运 $kNd$ 个值；`4 bytes` 是 bf16/fp32 的常见宽度。
- **因子 2**：去程（dispatch）与回程（combine）各搬一趟。
- **不随 $E$ 增长**：通信只取决于「实际路由到几个专家」，与专家总数无关——这正是「专家可以无限多、通信却可控」的数学基础。

代入数字：$N = 4096$、$d = 2048$、$k = 2$，一层通信 ≈ $2 \times 2 \times 4096 \times 2048 \times 4 \approx 134$ MB。**这是每一层、每一个 batch 都要付的钱**。于是 top-1 相对 top-2 的通信减半（上一节 Switch 的论点在这里兑现）：$k$ 从 2 降到 1，通信直降一半。<span class="marginnote">通信量随 $k$ 线性增长、而专家数增长不增加通信——这是 MoE 能「加专家不加通信」的根本原因，也是「以通信换容量」之外的另一层解耦。理解这个比例关系，就理解了为什么工业界那么执着于压 $k$。</span>

GShard 还做了两个通信优化：**分组调度（group dispatch）**——把路由结果中「去同一设备」的 token 打包成一个块（group）再发，避免细碎小包；以及**容量上限内打包**——容量因子保证每设备的 token 数可预分配，通信张量的形状是编译期常量。

## 4 负载均衡损失的工程角色

把前三节的线索收拢：**专家并行让「负载均衡」从学术概念变成通信硬指标**。在 EP 里，一个设备持有多个专家，如果负载失衡，某台设备收的 token 块巨大、其他设备几乎空转：

通信的**桶大小**失去平衡 → all-to-all 慢的桶拖慢整个同步步进（阿姆达尔定律显灵：串行的全交换成为瓶颈）。
- 设备算力闲置 → 整体吞吐下降。

所以 GShard 的 aux loss、容量上限、随机第二专家，并不只是「防止专家退化」——它们**直接保护 all-to-all 的均衡性**，把通信调平。<span class="marginnote">这是 MoE 里「正则目标」与「系统目标」罕见地对齐的时刻：让路由均匀，既提升模型质量，也提升系统吞吐。也正因如此，负载均衡损失在 EP 部署里是不可砍的。</span>

## 5 专家并行的边界：通信瓶颈与规模化

专家并行也不是免费的。它的主要代价有三：

- **通信延迟**：all-to-all 是同步屏障，设备越多、网络越慢，瓶颈越明显。GShard 用 TPU 的片上互联（速度远超普通以太网）才把 600B 模型跑起来。
- **显存碎片**：每设备持有多个专家，专家间显存复用需要专门的分配策略。
- **路由开销**：打分、分桶、排序都要算力与内存；top-1 的路由比 top-2 便宜一半。

一个经常被引用的经验法则：**当专家参数量远大于模型其他部分时，EP 的收益最大**——因为专家占大头，切出去最能缓解单卡压力；而当通信带宽受限时，k 小、EP 张量形状固定、分组打包就格外重要。现代 DeepSeek、Mixtral 的推理部署，本质上都继承了 GShard 的 EP 骨架，只是把「TPU 全交换」换成了「GPU + NVLink/InfiniBand」的变体——这条线索我们留到本专题最后一节《推理部署与专家卸载》。

### 一个具体例子：GShard 的网格布局

GShard 在 2048 块 TPU v3 上把设备排成一个网格：非 MoE 的注意力层用「张量并行 + 数据并行」切成若干副本，每份副本独立处理一部分 batch；MoE 的 FFN 专家层则按「专家并行」把 2048 个专家（每层约 2048 个）切到不同设备——更精确地说，是把专家按「组」分布，每组设备持有若干专家，token 经 all-to-all 在组内交换。

- 注意力等层：**每个设备副本完整持有**（用张量并行切分，属于「切张量」）；
- 专家 FFN：**设备持有的是不同的专家**（属于「切专家」）。

一次前向里，token 先在自己设备的副本里走注意力，到 MoE 层时被路由器「分拣」成去往不同设备的桶，经 all-to-all 全交换搬去算、再搬回。**两个层面的并行用「token 在设备间流动」这个动作缝合起来**——这正是 MoE 与纯稠密模型并行的本质差异。

### 通信量与「批次组合」的权衡

专家并行还有一个隐蔽但重要的设计点：**单设备 batch 太小会让 all-to-all 效率骤降**。每个专家收到的 token 数约等于「本设备 batch 的 token 数 × 路由概率」，若每设备 batch 很小，每个专家只收到零星几个 token，批量矩阵乘法发挥不出硬件算力，通信占比却不变——这就是 Shazeer 论文里「收缩批量」问题在分布式下的放大。解决思路是**批次组合（batch combination）**：把多个设备、多个微步的 token 先攒在一起，再统一做一次全交换，用「更大的桶」摊薄通信固定开销。**专家并行的吞吐优化，本质上是在「桶越大越省通信」与「延迟越高」之间找平衡**——这一权衡在最后的推理部署一节（动态 batch）还会以更尖锐的形态出现。

### 一个具体例子：通信与计算的时间账

把「通信是 EP 第一成本」量化。设每层专家 FFN 的计算时间 $T_{\mathrm{calc}}$ 与 all-to-all 通信时间 $T_{\mathrm{comm}}$：

- 若 $T_{\mathrm{comm}} \ll T_{\mathrm{calc}}$（如 TPU 片上互联），通信被计算天然掩盖，EP 几乎免费——GShard 在 TPU 上成立的原因；
- 若 $T_{\mathrm{comm}} \approx T_{\mathrm{calc}}$（如普通数据中心用 PCIe/Ethernet），则每层专家前馈的墙钟时间约翻倍——**EP 的红利被通信吃掉一半**。

实践中用「计算-通信比（compute-to-communication ratio）」评估：比值越大，EP 越划算。提高比值的手段就两条：**让桶更大**（批次组合、加大单设备 batch）或**让包更少**（分组调度，把去同一设备的 token 打包成大块发送）。这也是为什么 MoE 部署几乎总是绑定高速互联（NVLink、InfiniBand）——EP 的效率上限由互联决定。

### 从 TPU 到 GPU：EP 的工程迁移

GShard 的 EP 是给 TPU（片上互联、同步执行模型）量身定做的；今天的 GPU 集群（NVLink + InfiniBand、异步流式执行）在做同样的东西，但有两个额外考量：一是**多卡负载平衡**要在「路由 + 容量」之外再叠加「动态批调度」；二是 GPU 的显存小、PCIe 慢，专家搬上搬下的成本更高——这正是下一节《推理部署与专家卸载》的出发点：**训练时的 EP 是「token 去找专家」，推理时的卸载是「专家来找 token」**，一个主动搬运 token、一个被动搬运参数，是同一个「设备间流动」思想的两种方向。

### 与《大模型训练基础设施》的衔接

专家并行并不是孤立的技术，它是分布式训练「并行策略」家族的一员——张量并行（TP）、流水线并行（PP）、数据并行（DP）、专家并行（EP）在第四级《大模型训练基础设施》里会被系统化。这里只需记住一点：**EP 与前三者的本质区别在于「切分的对象」**——TP 切张量、PP 切层、DP 切数据、EP 切「决策单元」。现代万亿参数训练几乎都是「四者叠加」，而叠加的难点就在「各层通信模式不同」：EP 的 all-to-all 与 TP 的 all-reduce 在同一批数据上交叉出现，调度稍有不慎就互相阻塞。

一个最后的提醒：**EP 的价值是「专家足够多」时才成立**。若 $E$ 小到「每设备一个专家都不到」，EP 退化成普通的模型并行，还要白白背负 all-to-all 的通信——这就是为什么 EP 几乎只出现在「专家成百上千」的巨型 MoE 里。判断该不该用 EP，先看专家数与设备数的比值是否远大于 1；若两者同数量级，先把专家数放大或把设备数缩小，再谈 EP。

一句话记忆：**EP 是「token 搬家」的并行**——专家的容量不受单卡显存约束，代价是 all-to-all 通信与负载均衡的复杂性。

再提醒一句：学完本节，你已具备看懂 GShard 全图的能力——它就是「DP/MP 管注意力、EP 管专家、aux loss 管负载」三行话的总和。

## 6 小结

- **专家并行（EP）**：把 $E$ 个专家切到 $D$ 台设备，token 经 all-to-all 送去目标设备计算再收回；与 DP（切数据）、MP（切张量）形成三维互补。
- **All-to-all 原语**：本地分桶 → 全交换 → 批量专家计算 → 反向交换；通信量 $\approx 2kNd$ 字节。
- **通信不随 $E$ 增长、只随 $k$ 线性增长**——所以 top-1 通信是 top-2 的一半，「加专家不加通信」。
- **负载均衡是 EP 的硬指标**：桶不平衡会拖慢同步屏障，aux loss 在此同时服务质量与吞吐。
- **代价**：通信延迟、显存碎片、路由开销；EP 在「专家占比大 + 互联快」时收益最大。
