## 为什么从「GPU 对」开始

前面讲 NVLink 域，我们把 72 颗 GPU 当成一个整体；讲机架布局，我们把 18 个计算托架当成单元。但**构成 NVL72 的最小「积木」既不是单颗 GPU，也不是整个域，而是两两成对的 GPU**——每个 GB200 超级芯片里，两颗 B200 与一颗 Grace CPU 被封装在一起。这个「2 GPU + 1 CPU」的组合，NVIDIA 称它为 **GPU 对（GPU Pair）**，是整个机架级 Scale-up 架构的原子单位。<span class="marginnote">「Scale-up」指把多颗 GPU 合成一台更大的机器（靠 NVLink），与「Scale-out」（靠网络把多台机器连成集群）相对。NVL72 的 Scale-up 不是「把 72 张卡插进一个箱子」，而是「以 GPU 对为积木，层层搭出一个域」——积木的形态决定了整个架构的性格。</span>

在「从极限到大模型」的坐标里，GPU 对回答的是「系统的最小组织单位」：极限告诉我们单点能做到多小，而 GPU 对告诉我们<strong>把多强的算力焊在一起才算「一个节点」</strong>。从「1 GPU 一个节点」到「2 GPU + 1 CPU 一个节点」，这个「节点」定义的迁移，正是机架级系统对软件栈最深刻的影响之一。这一节回答三个问题：GPU 对是什么、为什么是「对」、以及软件怎么用它。

## 1 GPU 对：超级芯片里的「铁三角」

拆开一块 GB200 超级芯片，三个成员以固定的方式排列：

**两颗 B200 GPU**：它们各自拥有 18 条 NVLink5 链路连向交换层（每颗 1.8 TB/s），与域内任何其他 GPU 的通信带宽完全一致——没有「私有专线」，但共享同一位「家长」。
**一颗 Grace CPU**：通过两条 NVLink-C2C 分别连接两颗 GPU，每颗 GPU 独享 900 GB/s 的 CPU 直连带宽。
- **共享的「家庭账户」**：三者通过 C2C 的一致性机制共享内存地址空间、Grace 的 480 GB 内存与网卡出口，对外看像一个整体。

在物理上，这三颗芯片与各自配套的 HBM 堆栈躺在同一块封装基板上——两颗 B200 各带 8 个 HBM3e 堆栈，Grace 带 8 个 LPDDR5X 颗粒，全部经先进封装连成一体。<span class="marginnote">「铁三角」这个词在半导体里是形象说法：三颗 Die 在同一块基板上互连，尺寸、功耗、散热都要在封装阶段统一设计。这也是超级芯片「贵」的来源——先进封装不便宜，但换来的是片间带宽的数量级提升。</span>

**GPU 对**特指这「两颗 GPU」的配对关系。它的物理纽带是那颗 Grace CPU 与两条 C2C——CPU 是「家长」，两颗 GPU 是「双胞胎」，没有彼此专线，但共享同一份「家庭账户」：内存、网卡、地址空间。<span class="marginnote">这个结构也回答了第 1 篇的疑问：为什么是 1 颗 CPU 配 2 颗 GPU？因为 Grace 的约 1 TB/s 内存带宽恰好够同时喂饱两颗 B200 的 C2C 入口，而两颗 GPU 之间的通信交给 NVSwitch——CPU 管「喂」，交换机管「连」，各司其职。</span>

## 2 为什么是「成对」，而不是「成单」或「成组」

「成对」不是巧合，它处在「单颗」与「更大组」之间的甜点位置：

**对比「单颗」**：单颗 B200 单独插进机架，它到 Grace、到其他 GPU 都要走独立的长路径，管理分散。两颗配对后，**它们共享同一颗 Grace 的 480 GB 内存、网卡与 C2C 通道**——「喂数据」这件事由同一位家长统一负责，数据搬运与通信出口被集中起来。<span class="marginnote">在训练里，把「通常放在同一节点的两层」分配给同一对的 GPU，可以让它们共享 Grace 内存里就近存放的公共张量（如 embedding、中间缓冲），减少跨节点搬运——这是 GPU 对在软件层最实际的收益。</span>

**对比「更大组」**：为什么不是 4 颗、8 颗一组？因为组越大，共享同一颗 CPU 的 GPU 越多，CPU 内存带宽与 C2C 入口会被摊薄，管理复杂度上升而收益递减；而 2 颗一组，恰好让 Grace 的约 1 TB/s 内存带宽配比均衡。**「对」是「CPU 带宽配比」与「封装成本」的最优交点**。

于是 NVL72 的 Scale-up 树形结构清晰了：**GPU 对（1 Grace + 2 B200）→ 超级芯片 → 计算托架（2 个超级芯片）→ 机架（18 个托架 = 36 个 GPU 对 = 72 颗 GPU）**。每一层都是上一层的「放大的积木」。

把「Scale-up 积木」放在历代 NVIDIA 平台上并排，能清楚看到「积木」本身在变大：

| 平台 | Scale-up 积木 | GPU 数 | CPU 配比 | 域内带宽 |
| --- | --- | --- | --- | --- |
| DGX A100 / H100 | 8 卡节点 | 8 | 2 路 x86 | 600 / 900 GB/s |
| GB200 超级芯片 | GPU 对 | 2 | 1 颗 Grace | 1.8 TB/s |
| GB200 NVL72 | 整个 NVLink 域 | 72 | 36 颗 Grace | 129.6 TB/s |

从「8 卡节点」到「72 卡域」，积木的粒度放大了近一个量级——**软件眼里「一台机器」的规模，从 8 颗 GPU 变成 72 颗 GPU**。这正是「机架级 Scale-up」最本质的变化。

## 3 机架级 Scale-up：把 36 个「对」焊成一个域

有了 GPU 对这块积木，机架级 Scale-up 就是「把 36 个对全部互联」的工程。它的关键决策是：

**域内全部互连，域外只剩网络**。36 个 GPU 对（72 颗 GPU）通过 18 颗 NVSwitch 组成单 NVLink 域，任何两颗 GPU——无论同对、同托架、还是跨托架——都以 1.8 TB/s 的域内带宽通信。<span class="marginnote">「同对的两颗 GPU 与跨对的两颗 GPU，带宽都是 1.8 TB/s」——域内带宽对通信对象不敏感。这正是第 6 篇「无阻塞」的直接收益：无论模型怎么切，域内通信的带宽待遇完全一致。</span>「对」内与「对」外的差别不在 GPU 间带宽，而在 CPU 侧：同对 GPU 共享同一颗 Grace，访问其内存时延迟更低、无需跨节点；跨对 GPU 访问彼此的 Grace 内存则要经交换机，多一次转发。

Scale-up 的软件意义也随之浮现：**36 个 GPU 对是「调度的最小单元」**。训练框架可以把一个模型并行组「恰好」分配给整数个 GPU 对，让组内通信尽量落在对内与域内；跨对的通信由 NVSwitch 无阻塞转发。整个机架在软件里呈现为一台「有 36 个双核-单管的对称多处理器」式的巨型机。

这个类比值得展开：在经典对称多处理器（SMP）里，每个 CPU 核都看到同一块内存；在 NVL72 里，每个 GPU 对都看到同一块「域内内存」（13.5 TB 显存 + 17 TB Grace 内存）。<span class="marginnote">SMP 的「对称」指所有核地位平等、共享统一地址空间；NVL72 的 36 个 GPU 对也共享统一的 NVLink 域地址空间——除了「访存速度因远近而异」（NUMA），语义上完全对称。把 NVL72 理解成「一个巨大的 SMP」，就抓住了它的编程模型本质。</span>调度器只关心「哪几个 GPU 对干活」，而不关心它们之间的通信细节——通信已经被硬件域吞掉了。

GPU 对同时也是一个**故障域**：一颗 B200 的故障通常意味着整个超级芯片（连同那颗 Grace）要一起下架——因为三者焊在同一块基板上，无法单独替换。<span class="marginnote">「故障域」是可靠性的基本概念：一次故障影响的最小范围。GPU 对的故障域是「一个超级芯片」= 2 GPU + 1 CPU；整架 36 个对中坏一个，影响 72 颗 GPU 中的 2 颗。这个粒度决定了冗余设计怎么铺，详见本专题《系统可靠性、冗余与 OOB 管理》。</span>这也解释了为什么机架采用「热插拔托架 + 快速接头」——既然换就得换整块，那就让换的动作尽量快。

举一个具体的映射例子：训练一个 70B 模型，最直观的切法是**流水线并行**——把模型的 80 个 Transformer 层切成 36 段，每段恰好放在一个 GPU 对上。每对内的 2 颗 GPU 再各自处理半个段（张量并行），Grace 负责缓存该段的高频中间张量。<span class="marginnote">「一层段 ↔ 一个 GPU 对」的映射，让流水线的气泡、通信与显存分配都规整化：每段显存预算确定、每段通信只在段边界发生、每段的 Grace 缓存独立。这是 GPU 对作为「调度单元」最自然的一次应用。</span>「积木对齐」让模型并行变得像拼积木一样直白。

## 4 公式解析：Scale-up 与 Scale-out 的带宽账

「Scale-up 到底划不划算」可以量化。设域内聚合带宽为 $B_{\mathrm{up}}$，域外聚合带宽为 $B_{\mathrm{out}}$，二者的比值刻画了「机架这台机器」的通信倾向：

$$
\frac{B_{\mathrm{up}}}{B_{\mathrm{out}}} \approx \frac{72 \times 1.8\ \mathrm{TB/s}}{72 \times 50\ \mathrm{GB/s}} \approx \frac{129.6\ \mathrm{TB/s}}{3.6\ \mathrm{TB/s}} \approx 36
$$

- **$72 \times 1.8\ \mathrm{TB/s}$**：72 颗 GPU 各自的 NVLink5 带宽，组成 129.6 TB/s 的域内聚合。
- **$72 \times 50\ \mathrm{GB/s}$**：72 颗 GPU 各分摊一个 400G（约 50 GB/s）的 Scale-out 出口，聚合约 3.6 TB/s。
- **比值 36**：域内带宽是域外带宽的 **36 倍**。

如果把 C2C 也算进来，每颗 GPU 的「总入口带宽」其实是 **1.8 TB/s（NVLink5）+ 0.9 TB/s（C2C）= 2.7 TB/s**——CPU 侧还有近一半的额外带宽。这解释了为什么 GPU 对在「喂数据」上比「单 GPU + PCIe」架构强一个量级：**单卡的入口带宽从 128 GB/s（PCIe）涨到 2.7 TB/s，20 倍以上**。GPU 对把「喂」与「连」两条带宽通道都拉满了。

这个 36 倍就是「为什么高通信并行度必须留在域内」的数字证据。<span class="marginnote">如果某类通信需要频繁跨域，它就会撞上只有域内 1/36 的带宽——训练速度立刻被拉回「网络时代」。设计并行策略时，先用这个比值判断「什么该域内、什么该域外」，比凭感觉切分可靠得多。</span>36 倍也正是第 7 篇里「140 GB 梯度域内 156 ms vs 域外 5.6 s」那个对比的另一种表达——同一件事，两套账本，结论一致。

把 36 倍落到训练上：一个 70B 模型做数据并行，每个 step 要聚合 140 GB 梯度。若把两个 NVL72 域之间的梯度聚合也算进来，每步就要额外搬 140 GB 走只有 1/36 带宽的域外网络——每步多出数秒的通信。这正是「域内装得下就不跨域」最硬的理由：**跨域一次，等于把训练速度砍回网络时代**。

这个账还有一个隐藏推论：**域的规模决定了「多大模型能纯域内训练」**。72 颗 GPU × 13.5 TB 显存，理论上限约 27T 参数（FP4）；超过这个量级，模型就必须跨域，通信成本立刻跳一个台阶。所以「GB300 把域扩到 NVL576」不只是堆更多卡——它是把「纯域内可训」的模型上限再抬高一个量级，我们到第 4 篇《NVL576 机架群与万卡集群扩展》再细算。

## 5 软件怎么「看见」GPU 对

GPU 对不是硬件工程师的自嗨，它在软件栈里处处可见：

**NCCL 的拓扑感知**：NCCL 会把通信图映射到物理拓扑，优先利用域内交换、把跨机架的流量压到最少。GPU 对让 NCCL 可以「就近聚合」——把同对 GPU 的数据先合并，再统一跨域，通信算法的第一步就省下流量。
**框架的节点抽象**：在 Megatron / PyTorch 的视角里，一个 GB200 超级芯片（GPU 对 + Grace）就是一个「节点」——72 颗 GPU 不是 72 个节点，而是 36 个节点，调度粒度变粗、通信模式更规整。<span class="marginnote">「把 2 颗 GPU 捆成一个节点」对软件是纯收益：流水线并行可以把一个 Transformer 层正好放在一个对里，共享同一颗 Grace 的缓存与内存；张量并行的通信则尽量落在域内交换层。并行策略的「对齐」全靠这个积木。</span>
**MoE 的专家放置**：MoE 推理把专家放在 Grace 内存（见第 4 篇），GPU 对内的两颗 GPU 共享同一个 Grace，专家路由天然在本对内的两颗 GPU 间就近完成——负载均衡与通信开销一并改善。

**辨析｜GPU 对 ≠ 硬亲和性（hard affinity）：** 配对并不强制「这两颗 GPU 必须一起干活」。调度器完全可以只把一对中的一颗 GPU 分配给某个任务，另一颗闲下来或跑别的任务——域内带宽对通信对象不敏感，单颗 GPU 也能正常参与任何并行模式。<span class="marginnote">「配对」提供的是一种「优先机会」而非「强制约束」：能共享 Grace 时就共享，不能共享也不影响正确性。这种「软配对」的设计，让 GPU 对既给了软件优化的抓手，又没有牺牲调度的灵活性。</span>真正把「对」当成铁律的，只有物理层面——它们确实焊在同一块基板上。

把各软件层「怎么用 GPU 对」收成一张核心对比表，全篇的结论就一目了然：

| 软件层 | 把 GPU 对当成什么 | 由此得到什么 |
| --- | --- | --- |
| 通信库（NCCL） | 就近聚合单元 | 同对数据先合并再跨域，省流量 |
| 训练框架（Megatron） | 一个「节点」 | 流水线层段 ↔ GPU 对一一映射 |
| 推理引擎（vLLM 等） | 大显存切片 | 专家/嵌入就近放共享 Grace |
| 调度器（Slurm 等） | 一个可分配资源 | 按「对」粒度分配，粒规整 |

每一层都在用自己的语言消费同一个事实：**GPU 对是「算力、内存、通信」三者的最小交汇点**。

- **GPU 对**：1 颗 Grace CPU + 2 颗 B200，各以 900 GB/s C2C 连到 Grace、共享其内存与网卡；GPU 间通信经 NVSwitch 域内交换（各 1.8 TB/s）——NVL72 的原子积木。
- **为什么是「对」**：两颗 GPU 共享同一颗 Grace，CPU 带宽配比均衡、封装经济；组太大则 CPU 带宽被摊薄，「2」是配比与成本的最优交点。
- **Scale-up 树**：GPU 对 → 超级芯片 → 托架（2 个超级芯片）→ 机架（18 托架 = 36 对 = 72 GPU），36 个对焊成一个 NVLink 域。
- **带宽账公式** $B_{\mathrm{up}}/B_{\mathrm{out}} \approx 36$
