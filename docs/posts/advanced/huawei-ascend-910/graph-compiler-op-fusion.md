## 为什么从图编译器开始

上一篇我们建立了 CANN 的地图：五层软件栈，其中 **GE（图引擎）是大脑**。这一篇要钻进去，看这个大脑具体怎么工作。核心问题只有一个，却极其深刻：**一张计算图（几十上百个算子）怎么被编译成昇腾上一组高速执行的指令？** 答案的关键词是**算子融合（operator fusion）**——把多个小算子合并成一个大算子。这是昇腾性能工程里最划算、也最体现编译器智慧的优化之一。<span class="marginnote">为什么「融合」如此重要？回顾第 4 篇的驻留率公式：<strong>中间张量每落一次 HBM 就是一次「过路费」</strong>。融合把中间张量留在片上，直接砍掉了大量过路费——这是「不花钱的性能提升」。</span>

这一篇讲三件事：图编译器处理计算的流程、算子融合为什么省性能、以及融合背后的「代数等价」原则。

## 1 图编译器的三段式流程

昇腾 GE 把「用户计算图 → 可执行指令」的过程分成三个阶段：**构图（Frontend）→ 优化（Optimizer）→ 代码生成（Codegen）**。

### 1.1 构图：把算子调用整理成图

GE 把上层送来的算子调用整理成一张**计算图**：节点是算子，边是张量。这一步「看起来简单」，实则要处理很多细节：算子的输入输出形状、数据类型、数据格式、执行设备（AI Core 还是 CPU）。**构图的质量决定后续优化的空间**——图结构完整、信息准确，优化器才能放开手脚。

### 1.2 优化：所有聪明都发生在这里

优化阶段是 GE 的精华，包含一长串图改写（graph rewrite）操作：

**算子融合**：把多个算子合并成一个（下面专门讲）。
**常量折叠**：编译期能算出来的常量，直接算出结果，省去运行期计算。
- **死代码消除**：删掉结果不被使用的算子。
- **格式与布局优化**：选择最优的数据格式与内存布局。
- **算子下沉与 tiling 决策**：决定每个算子怎么切块、用哪个单元执行。

<span class="marginnote">优化阶段是「编译器智慧」的集中体现：<strong>它做的是「语义不变、性能提升」的图改写</strong>——改写前后计算结果必须完全一致，但执行方式完全不同。这与传统编译器里的「循环展开」「内联」是同一类技术，只是作用对象从「代码」变成了「计算图」。</span>

这里要特别强调「**改写规则的可信度**」问题。图改写器手里握着一堆「模式匹配规则」（比如「矩阵乘后跟逐元素激活 → 融合」），每一条都必须被证明是语义等价的。规则库里任何一条「错误的等价」，都会静默地改变模型行为——比报错更可怕。因此昇腾对融合规则实行「白名单 + 严格验证」：只有被验证过的规则才会上线。**编译器优化有一条铁律：宁可优化不到，不可优化出错**——这在任何编译器工程里都是最高优先级。

### 1.3 代码生成：把优化后的图变成指令

最后，优化后的图被翻译成昇腾的指令序列：为每个算子生成 tiling 方案、安排数据流、插入同步点。这一步在昇腾的「算子编译器」中完成，我们会在《Ascend C 算子编程模型》与《Cube 矩阵乘算子开发实战》里看到具体形态。

代码生成的产物通常有两类：一类是**编译好的 kernel 二进制**（直接可执行），另一类是 **JIT 生成的代码**（运行时按 shape 现编）。GE 会缓存已编译的 kernel，遇到相同 shape 直接复用——这就是上一节「冷启动慢、热运行快」的根源。对 shape 多变的任务（如推理时的动态 batch），JIT 让「每个 shape 都能吃到编译优化」成为可能，但也带来「首次运行慢」的代价。<span class="marginnote">「静态编译 + JIT」双轨是昇腾编译器的标准配置：<strong>静态编译保性能，JIT 保灵活性</strong>。动态 shape 场景下如何平衡两者，是昇腾推理优化的常考题目。</span>

## 2 算子融合：为什么「合」比「分」快

### 2.1 不融合的代价：中间张量的「过路费」

设一段网络：$\mathbf{Z} = \text{GELU}(\mathbf{X}\mathbf{W})$。如果不融合，执行是：

1. 计算 $\mathbf{Y} = \mathbf{X}\mathbf{W}$，把 $\mathbf{Y}$ 写回 HBM；
2. 再从 HBM 读 $\mathbf{Y}$，做 GELU，写回 $\mathbf{Z}$。

第 1 步的「写 $\mathbf{Y}$」与第 2 步的「读 $\mathbf{Y}$」都是多余的——$\mathbf{Y}$ 只是中间结果，用完即弃。**这两次 HBM 往返，就是「过路费」**。对 $\mathbf{Y}$ 为 4096×4096 的张量，一次往返约 64 MB 流量；而整个网络有成千上万个这样的中间张量。<span class="marginnote">用第 4 篇的语言说：不融合时，中间张量的「驻留率」很低——它刚算完就被写回 HBM，根本来不及在片上被复用。<strong>融合的本质，就是提高中间张量的驻留率</strong>。</span>

### 2.2 融合后的执行：中间张量留在片上

融合后，GELU 被「并进」矩阵乘的 kernel：$\mathbf{Y}$ 不再写回 HBM，而是留在 UB/L0C 里直接被 GELU 消费，最后只写一次 $\mathbf{Z}$。**HBM 流量从「两次往返」变成「一次直达」**——省掉的就是过路费。

融合带来的收益不止省流量，还有：

**省同步**：融合后算子数量变少，跨算子同步点减少（回顾第 3 篇）。
**省启动开销**：一个 kernel 的启动开销被摊薄到大算子身上。
- **提高利用率**：融合后的 kernel 通常能更充分地利用 Cube 与 Vector 的流水并行。

还有一个「隐性收益」：**融合降低了「算子粒度太小」带来的调度开销**。昇腾的指令集是「长指令、粗粒度」的（回顾第 3 篇），一个太小的算子连「喂饱一条长指令」都不够，纯粹浪费发射带宽。融合把若干小算子拼成一个大算子，正好把「粒度」抬到长指令的舒适区——**融合既是流量优化，也是指令效率优化**。

## 3 融合的边界：不是所有算子都能合

算子融合不是「想合就合」，它受三大约束约束：

**其一，语义必须等价**。两个算子能否融合，前提是「融合后的计算结果与融合前完全一致」。像 GELU 这种「逐元素」算子，融合到矩阵乘后每个元素的计算顺序不变，语义等价；而像 softmax 这种「需要整行信息」的算子，融合时要特别小心规约顺序带来的数值差异。<span class="marginnote">数值上的「几乎等价」在训练里通常可接受（浮点本身就有误差），但<strong>在推理部署时要警惕：融合可能改变极小概率下的数值行为</strong>——这就是为什么昇腾会为「安全融合」维护一张白名单。</span>

**其二，硬件形态必须支持**。融合后的算子要能映射到昇腾的执行单元。矩阵乘 + 逐元素（GELU、ReLU）融合很自然，因为 Cube 算完、Vector 接着算，数据流顺；但「两个矩阵乘」融合就不行——它们都抢 Cube，没法在一个 kernel 里流水。<span class="marginnote">昇腾融合的「黄金组合」是<strong>「Cube 算子 + 紧随其后的 Vector 算子」</strong>：Cube 的结果留在片上，Vector 就地处理，省一次写回。Transformer 里的注意力几乎整条都能这样融合。</span>

**其三，寄存器/片上空间有限**。融合后中间张量要留在片上，若片上空间不足，融合就无从谈起。这又回到「tile 大小必须塞得进 UB」的约束——**融合与 tiling 是强耦合的**。

这三条约束也解释了为什么融合不是「拍脑袋就能做」的工程：**每条约束背后都是一整套编译器基础设施**。语义等价要依赖严格的形式化验证；硬件形态支持要依赖算子库与指令集的完备描述；片上空间要依赖精确的内存规划。**「融合」看似是编译器的一个动作，实则是整个编译体系成熟度的试金石**——一个连融合都做不好的编译器，其他优化也很难到位。

## 4 公式解析：融合节省的流量

把「融合省了多少」精确量化。设某段计算有 $n$ 个算子，不融合时每个算子都会把中间张量写回 HBM（假设中间张量总字节为 $V_{\text{mid}}$，被写出又读回），则不融合的总流量为：

$$V_{\text{no-fusion}} = V_{\text{in}} + (n-1)\times 2V_{\text{mid}} + V_{\text{out}}$$

融合后，中间张量只留在片上：

$$V_{\text{fusion}} = V_{\text{in}} + V_{\text{mid}} + V_{\text{out}}$$

逐项拆解：

- **第一步，$V_{\text{no-fusion}}$**：输入 $V_{\text{in}}$ 读一次，$n-1$ 个中间张量每个「写一次 + 读一次」（$2V_{\text{mid}}$），输出 $V_{\text{out}}$ 写一次。
- **第二步，$V_{\text{fusion}}$**：融合后中间张量只写一次（被后续算子消费），流量大减。
- **第三步，对比**：省下的流量为 $(n-1)\times V_{\text{mid}}$。**算子越多、中间张量越大，融合越值**。

代入感受：$n=3$（如 MatMul + Add + GELU）、$V_{\text{mid}}=64$ MB，则省下约 $2\times64=128$ MB 的 HBM 流量。**对一个训练 step 有上万个这类「小而碎」的算子序列的大模型，融合省下的累计流量是 TB 级的**——这解释了为什么昇腾把算子融合列为「头号优化」：它不是锦上添花，而是决定大模型能否高效训练的关键。<span class="marginnote">这条公式还揭示了一个判断技巧：<strong>融合的价值与「中间张量的体积」成正比</strong>。中间张量越大（batch 大、序列长），融合越值得做；中间张量很小，融合的收益就有限。</span>

## 5 小结

- 图编译器三段式：**构图 → 优化 → 代码生成**，核心智慧集中在优化阶段。
- **算子融合**把多个算子合并成一个，砍掉中间张量落回 HBM 的「过路费」。
- 融合的收益：**省流量、省同步、省启动开销、提高利用率**。
- 融合的边界：**语义等价、硬件形态支持、片上空间足够**。
- 流量公式：融合省下 $(n-1)\times V_{\text{mid}}$——算子越多、中间张量越大，融合越值。
- **融合的价值与「中间张量的体积」成正比**：batch 大、序列长，融合收益越大。
- **融合的黄金组合是「Cube 算子 + 紧随其后的 Vector 算子」**：Cube 结果留在片上，Vector 就地处理，省一次写回。
- **「静态编译 + JIT」双轨是昇腾编译器标准配置**：静态编译保性能，JIT 保动态 shape 的灵活性。
- **编译器优化铁律：宁可优化不到，不可优化出错**：融合规则白名单 + 严格验证，语义等价是底线。

- **优化阶段是「编译器智慧」的集中体现**：常量折叠、死代码消除、格式布局优化、tiling 决策，全是「语义不变、性能提升」的图改写。
- **图改写规则的可信度决定编译器质量**：任何一条错误的等价都会静默改变模型行为，比报错更可怕。
- **「构图的质量决定后续优化的空间」**：输入输出形状、数据类型、执行设备，信息准确优化器才能放开手脚。
- **GE 缓存已编译 kernel，遇到相同 shape 直接复用**：这是「冷启动慢、热运行快」的根源。
- **融合降低「算子粒度太小」的调度开销**：把粒度抬到长指令的舒适区，既是流量优化也是指令效率优化。
