## 为什么从 Ascend C 开始

前几篇我们反复提到：昇腾把「调度智慧」交给编译期，而编译器优化的对象是**算子**。那么问题来了——**算子从哪来**？常见算子（矩阵乘、卷积）有预置的算子库，但模型里总会有算子库里没有的「新算子」：要么是新论文里的新运算，要么是业务特有的融合逻辑。这时就需要开发者自己写算子。**Ascend C** 就是昇腾的算子开发语言，它让开发者用 C++ 风格的代码描述「一个算子怎么在 AI Core 上执行」，而编译器负责把它变成高效的指令。<span class="marginnote">Ascend C 之于昇腾，类似 CUDA 之于 GPU——<strong>都是「面向硬件的 C-like 语言」</strong>。但两者的心智模型完全不同：CUDA 让你管理「线程」，Ascend C 让你管理「数据流与分块」。这正是本专题反复强调的「线程视角 vs 数据流视角」的又一次体现。</span>

这一篇讲清 Ascend C 的核心编程模型：一个算子长什么样、关键抽象有哪些、以及「写一个算子」与「写一个 CUDA kernel」的根本区别。

## 1 Ascend C 的核心抽象：一个算子 = 一个「分块数据流」

与 CUDA 的「线程块（block/thread）」模型不同，**Ascend C 把「数据」当作一等公民**。写一个 Ascend C 算子，核心是描述：

1. **如何把大张量切成小块（tiling）**——决定每个核、每个阶段处理哪块数据；
2. **每块数据怎么流动**——从 HBM 搬到 L1/UB，被 Cube/Vector 消费，再写回；
3. **每块数据上做什么运算**——调用矩阵乘指令、向量指令，或标量运算。

「把数据当作一等公民」听起来抽象，落到代码上是这样：**你在 Ascend C 里「搬运」是显式写出来的动作，而不是编译器替你猜测的隐式行为**。CUDA 里线程访问全局内存时，硬件会自动决定命中哪级缓存；Ascend C 里你明确地说「把这 16 KB 从 HBM 搬到 UB」——搬不搬、搬多少、何时搬，全由代码决定。**这种「显式」是昇腾性能可控性的来源，也是新手最容易不适应的点**。

<span class="marginnote">打个比方：CUDA 是「<strong>招一万个工人，每人干一小块，靠人多取胜</strong>」；Ascend C 是「<strong>招几个高手，每人领一大块料，沿流水线精心加工</strong>」。工人（AI Core）数量有限，但每个都「一专多能」且节奏被精心编排。</span>

### 1.1 一个算子的代码骨架

一个典型的 Ascend C 算子（以 Vector 算子为例）大致包含：

**数据搬移**：用 `DataCopy` 把输入从 GM（Global Memory，即 HBM）搬到 UB；
**计算**：用 `Add`、`Mul` 等向量指令在 UB 上做运算；
- **写回**：把结果从 UB 搬回 GM。

这套「搬进来 → 算 → 搬出去」的骨架，就是「数据流」的最小单元。Ascend C 的语法让这三步都「显式可见」——**你清楚地看到数据每一刻在哪**，这是它与「黑盒算子库」最大的区别。

初看这个骨架，你会觉得「啰嗦」：明明一个 `Add` 就能表达的运算，为什么要写搬入、计算、搬回三句话？答案是：**这三句话分别对应三条可优化的环节**——搬入可以双缓冲、计算可以流水、搬出可以异步。如果把这些都藏进「一个 `Add`」里，你就失去了优化的抓手。Ascend C 的「啰嗦」是刻意的：**把每个可优化点都暴露给你，让你有能力榨干硬件**。

## 2 Ascend C 的三大关键抽象

### 2.1 Tensor 与数据格式

Ascend C 用 `GlobalTensor`（指向 HBM）与 `LocalTensor`（指向 UB/L1 等片上存储）区分数据所在位置。**位置的显式区分，是 Ascend C 数据流编程的基石**——你不可能把 `GlobalTensor` 直接丢给向量指令，必须先搬到 `LocalTensor`。<span class="marginnote">这与 CUDA 的「全局内存 vs 共享内存」是同一层区分，但 Ascend C 的片上存储层级更多（UB/L1/L0），类型也更细。数据格式（ND、FRACTAL_NZ）同样体现在 Tensor 的类型里——<strong>「数据在哪」与「数据怎么排」都被编码进了类型系统</strong>。</span>

这种「位置编码进类型」的设计带来一个编译期收益：**类型不匹配的错误在编译期就能发现**。你若想把 `GlobalTensor` 直接喂给向量指令，编译器直接报错——它「知道」这个数据不在片上。相比「运行时才发现访存错误」，Ascend C 把一批隐患提前到编译期消除。**「类型即约束」是 Ascend C 从语言层面保护性能正确性的手段**，也是它与「无类型限制」的裸汇编编程的分水岭。

### 2.2 运算指令：直接对应硬件单元

Ascend C 的运算函数直接映射到硬件单元：矩阵乘类指令对应 Cube，向量类指令对应 Vector，标量运算对应 Scalar。**你在代码里写的 `Matmul(...)`，编译器会把它下沉成一条 Cube 长指令**——这种「指令即函数」的设计，让开发者能精确控制「哪个单元干什么」。

「指令即函数」还有一个实际好处：**代码的意图与硬件的行为几乎一一对应**。你在 Ascend C 里写「对这块 UB 数据做向量加」，编译器几乎不会「自作主张」改写它的语义——它把控制权完全交还给开发者。这与高层框架（PyTorch）完全不同：框架帮你决定一切，Ascend C 让你决定一切。**「决定权越大，责任越大」**——写 Ascend C 算子，开发者要对 tiling、流水、同步全权负责。

### 2.3 同步与流水：让三单元协同

Ascend C 提供同步原语（如 `SetFlag` / `WaitFlag`），让开发者控制「Cube 算完，Vector 才能开始」这类依赖。**写 Ascend C 算子时，你不仅要写「算什么」，还要写「什么时候能算什么」**——这正是软件流水的显式表达。

这里的「同步」不是障碍，而是「编排工具」：**主动插入的同步点，是在告诉编译器「这里的依赖关系由我保证」**。好的 Ascend C 代码，同步点又少又准——少到不浪费等待，准到不产生数据竞争。初写者常犯两个错误：一是同步点过多（每个算子都同步，流水被切碎），二是同步点缺失（数据竞争，结果错误）。**「在正确的地方插入恰到好处的同步」是 Ascend C 从「能跑」到「跑得好」的分水岭**。

## 3 从 CUDA 迁移的思维转变

如果你熟悉 CUDA，接触 Ascend C 时最需要完成的转变有三个。但先说一句宽心话：**底层原理是相通的**——访存局部性、并行度、负载均衡，这些「物理规律」在两种硬件上完全一样。变的只是「表达方式」：CUDA 用线程来表达并行，Ascend C 用数据流来表达并行。**掌握了原理，换语言只是换一套「表达语法」**，而不是重新学一门学科。

具体到三个转变：

**第一，从「线程」到「数据块」。** CUDA 的 `threadIdx` 决定每个线程干什么；Ascend C 里没有线程，只有「数据块被切给谁、何时被处理」。性能优化的起点从「调整线程布局」变成「调整 tiling 与数据流」。

**第二，从「共享内存手工同步」到「buffer 显式管理」。** CUDA 里 `__syncthreads()` 同步线程；Ascend C 里同步的是「buffer 的生产者与消费者」（DMA 与 Cube/Vector）。同步的对象从「线程」变成「数据依赖」。

**第三，从「kernel 粒度」到「算子粒度」。** CUDA 的一个 kernel 通常对应「一种运算在一批数据上」；Ascend C 的一个算子可以横跨 Cube 与 Vector，把「矩阵乘 + 激活」写进同一个算子描述。**粒度从「单指令流」放大到「多单元协作」**——这既是昇腾算子融合的编程基础，也是它与 CUDA 心智差异最深的点。

这三条转变合在一起，指向同一个结论：**「优化什么」变了**。CUDA 优化的是「线程的占用率与访存合并」，Ascend C 优化的是「数据流的节奏与 buffer 的利用率」。目标都是「让计算单元忙起来」，但抓手完全不同——从 GPU 迁移到昇腾，最难的不是学语法，而是**换一套性能心智模型**。

## 4 公式解析：tiling 数量与数据流效率

Ascend C 算子性能的关键变量是 **tiling（分块）**。设一个大张量共有 $N$ 个元素，每个 tile 处理 $T$ 个元素，则总 tile 数为：

$$N_{\text{tile}} = \left\lceil \frac{N}{T} \right\rceil$$

每个 tile 的处理时间约为「搬入 + 计算 + 搬出」三者之和。若搬入时间为 $t_{\text{in}}$、计算时间为 $t_{\text{calc}}$，则单 tile 时间下限为 $\max(t_{\text{in}}, t_{\text{calc}})$（搬算重叠后），总时间为：

$$T_{\text{total}} \approx N_{\text{tile}} \times \max(t_{\text{in}}, t_{\text{calc}})$$

逐项拆解：

- **第一步，$N_{\text{tile}}$**：$T$ 越大，tile 越少，循环与同步次数越少；但 $T$ 受限于 UB 容量（回顾第 4 篇「tile 必须塞得进 UB」）。
- **第二步，$\max(t_{\text{in}}, t_{\text{calc}})$**：搬入与计算若能重叠（双缓冲），单 tile 时间由「慢的那一个」决定。若搬入慢，则内存受限；若计算慢，则计算受限。
- **第三步，最优 $T$**：$T$ 越大，tile 越少、固定开销越摊薄；但 $T$ 超过某个值后，双缓冲的成本与 UB 压力上升。**最优 tile 是「让 $t_{\text{in}}$ 与 $t_{\text{calc}}$ 大致平衡」的那个值**——这也是 Ascend C 调优的核心命题。

这条公式告诉写算子的人一件事：**Ascend C 调优的第一件事，是找对 tile 大小**。tile 太大，UB 放不下；tile 太小，循环与同步开销吃掉性能。而「找对」靠的是对「搬入/计算比」的估算与实测——这正是《Cube 矩阵乘算子开发实战》一篇要亲手演示的。<span class="marginnote">一个实用的经验法则：<strong>让每个 tile 的计算时间 ≈ 搬入时间</strong>——这样双缓冲的利用率最高，流水最满。偏离这个平衡，要么 Cube 空等数据，要么 DMA 空等计算。</span>

用一个数字例子感受 tile 的敏感度。设 $N=10^7$ 元素、UB 能装 $T_{\max}=10^5$ 元素，于是 $T$ 只能在 $[0,10^5]$ 内选。取 $T=5\times10^4$，则 $N_{\text{tile}}=200$；若 $T=2.5\times10^4$，$N_{\text{tile}}=400$——tile 减半，循环次数翻倍。若每次循环有固定的同步/发射开销 $t_{\text{oh}}=100$ 周期，则仅循环开销就翻倍。**在 UB 允许的范围内「尽量取大 tile」通常是对的**，但若 tile 大到「搬入时间 ≫ 计算时间」，内存受限又会拖累——所以「平衡」才是关键字。

## 5 小结

- **Ascend C 是昇腾的算子开发语言**：核心抽象是「分块数据流」，而非「线程」。
- 三大关键抽象：**GlobalTensor/LocalTensor（数据位置）、指令即函数（映射硬件单元）、同步原语（显式依赖）**。
- 从 CUDA 迁移的三转变：**线程→数据块、同步线程→管理 buffer、kernel→多单元算子**。
- **换性能心智模型比学语法更难**：优化对象从「线程占用率」变成「数据流节奏」。
- tiling 公式 $T_{\text{total}}\approx N_{\text{tile}}\times\max(t_{\text{in}},t_{\text{calc}})$
