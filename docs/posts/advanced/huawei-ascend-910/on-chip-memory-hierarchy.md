## 为什么从存储层次开始

算力再强，数据喂不进去就是空转。前两篇我们把 AI Core 的三单元与流水线看清楚了，但它们脚下踩着的「土地」——L0、L0C、Unified Buffer、L1、L2、HBM——才是决定「算得快不快」的隐性主角。昇腾在存储上有一个鲜明的设计立场：**不像 CPU/GPU 那样依赖硬件的缓存自动管理，而是提供一组可显式控制的片上 buffer，把「数据何时搬到哪一层」的决定权交给软件**。这一篇把每一层存储的职责、容量量级与数据流讲透，并给出昇腾特有的「多路数据流」图景。

给存储层次找一个日常类比：**把芯片想象成一家餐厅。** HBM 是远处的中央仓库（东西全，但取一趟很久），L2 是后厨的备料台（常用食材集中放），L1 是厨师的取菜窗口（下一道菜提前放好），L0/UB 是厨师手边的工作台（正在切的那块料）。餐厅的营业速度，不取决于厨师手多快，而取决于「从中央仓库到工作台」这条供应链能不能跟上。**芯片设计的本质，和餐厅供应链设计的本质是一样的：让最贵的手（计算单元）一刻不停。** 这个类比会在后文反复帮我们判断「瓶颈出在哪个环节」。

## 1 L0：Cube 的贴身粮仓

**L0 Buffer** 与 **L0C** 是 Cube 单元专用的局部存储，位于 AI Core 内部，容量以 KB 计，是整颗芯片带宽最高、延迟最低的存储：

- **L0 Buffer**：矩阵乘的输入缓冲，分成 A、B 两个区（也可能有更细的分区），存放即将参与乘加的输入 tile。Cube 每个周期都要从 L0 读出 $16\times16$ 的数据喂给乘加阵列——**L0 的带宽必须 ≥ Cube 的消耗速率**，否则 Cube 断粮。
- **L0C**：累加缓冲（accumulator buffer），存放矩阵乘的中间累加结果。由于矩阵乘的中间结果是 FP32 精度的累加，L0C 的宽度通常比输入更宽，避免精度损失。<span class="marginnote">为什么累加要更宽？两个 BF16 相乘得到 FP32 精度的积，累加 4096 次后，若仍用 BF16 存中间和，误差会被放大。L0C 用更高精度保存累加，正是「精度换可靠性」的硬件体现。</span>

L0 由软件显式管理：编译器决定哪个 tile 进 L0 的哪个分区，计算完一批就换下一批。**不存在硬件自动替换**——这是昇腾与 CPU 缓存最大的不同。

L0 的「分区」策略本身就是一个微型优化问题：A、B 两个输入区各占多少容量？权重区要不要单独留一块常驻？这些在编译期由「L0 分配算法」求解。一个典型的策略是：**把 A 区设成「双缓冲」结构，B 区设成「常驻」结构**——因为 B（权重）在一轮计算里反复复用，常驻最省搬运；A（激活）每算一个 tile 就要换新，双缓冲让搬运与计算重叠。<span class="marginnote">这个「A 流式、B 常驻」的分区直觉，是理解昇腾 tiling 的钥匙：<strong>把重用的数据钉在片上，把流式的数据用流水搬</strong>。读者在后面写 Cube 算子时会亲手调这两个参数。</span>

## 2 Unified Buffer 与 L1：向量与预取的中转站

### 2.1 Unified Buffer（统一缓冲）

**Unified Buffer（UB）**：AI Core 内供 Vector 单元使用的工作区，容量数百 KB。向量运算的输入、中间结果、输出都在这里完成读写。之所以叫「统一」，是因为它同时服务多种数据形态：既放 Vector 的输入张量，也放 Cube 累加结果转存过来的数据，还放 DMA 从 L1/L2 搬来的原始数据。

数据在 L0C 与 UB 之间经常发生「转存」：Cube 在 L0C 算完累加，输出 tile 被 DMA 搬到 UB，Vector 在 UB 上做激活、归一化，再写回 L1/L2。**一次 GEMM+GELU，就是 L0→L0C→UB→L1/L2 的一次完整接力**。<span class="marginnote">UB 的设计隐喻着昇腾对「异构数据流」的承认：不同单元消费不同格式的数据，中间必须有可读写的公共空间完成格式转换。CANN 编译器会在算子图里插入显式的搬运/转换节点，管理这些「接棒」。</span>

### 2.2 L1 Buffer

**L1 Buffer**：位于 AI Core 之外、L2 之内的二次数据缓冲，容量数百 KB 到 MB 级。它的角色是「**预取中转站**」：DMA 把 L2/HBM 的数据成块搬进 L1，再由 L1 向 L0/UB 供货。有了 L1，数据搬运可以被流水化——L1 里存的是「下一批」数据，当前批正在 L0/UB 中被消费。<span class="marginnote">L1 的容量设计存在权衡：太小则预取窗口不够，来不及藏住 HBM 延迟；太大则挤压 L2 面积。昇腾在各代型号里调整 L1 容量，正是围绕这个平衡点。</span>

UB 的容量则直接决定**一个向量算子能一次处理多大的 tile**：UB 装得下 $N$ 个元素，向量算子就最多同时处理 $N$ 个元素，多出来的部分要分批。所以「UB 容量」与「tile 大小」之间存在刚性约束——**tile 必须塞得进 UB**。这带来一个在 GPU 上少见的现象：昇腾的算子性能往往对「张量形状」非常敏感，因为形状决定了 tile 怎么切才能塞进 UB 又保持高利用率。工程师调参时，第一个要确认的就是「这个 shape 的 tile 在 UB 里放不放得下、放得下几个」。<span class="marginnote">反直觉的一点：UB 越大，tile 能越大，同步越少，但每个 tile 的搬运粒度也越大、双缓冲成本越高。<strong>「越大越好」并不总是成立</strong>——最优 tile 是算出来的，不是拍脑袋定的。</span>

L1 与 L0/UB 之间也常做双缓冲，形成「两级流水」：L2→L1 搬下一块，同时 L1→L0 搬当前块，Cube 正在算上一块。三级重叠把「等数据」的时间压到几乎为零。这种多级双缓冲与上一节《指令集与流水线设计》里的软件流水是同一思想在不同层级上的复现——<strong>昇腾的性能哲学高度统一：每个层级都在做同一件事——「让数据提前就位，让计算永不等待」</strong>。

## 3 L2 与 HBM：全芯片的共享与主存

**L2 Cache**：全芯片共享的缓存，容量数十 MB，是所有 AI Core 之间交换数据的枢纽。张量在核间并行计算时，一个核的输出往往是另一个核的输入——这份中间张量要么留在 L2 被邻居直接读走（快），要么被迫落回 HBM（慢）。昇腾对 L2 的管理同样偏显式：它既可以被当作「缓存」用（硬件自动管理），也可以被当作「片上暂存」用（软件指定数据留在 L2 供他核复用）。<span class="marginnote">「L2 到底算缓存还是算显存」是昇腾生态里的经典考题：把 L2 当自动缓存，软件简单但命中率不可控；当片上暂存，性能可控但编译器要承担数据生命周期管理。CANN 两者都支持，按算子场景切换。</span>

多核共享还有一个隐性的竞争：**L2 到 HBM 的总带宽是所有核共享的**。一个核「吃得再多」，也不能独享 HBM 的全部带宽；当多个核同时爆发式访问 HBM 时，会出现带宽争抢，每个核实际获得的带宽都低于纸面值。这就是为什么昇腾性能评估要看「多卡/多核协同场景」而不是单核峰值：**单核把带宽用满不难，难的是让所有核同时用满而不互相拖累**。编译器在切分任务时，会在核间错开「HBM 访问高峰」，这又是一层跨核的数据流调度。

**HBM（高带宽内存）**：片外主存，容量数十 GB，通过内存控制器与片内 L2 交换。HBM 的价值在于**在合理的功耗内提供极宽的带宽**——它不是靠提高时钟，而是靠极其宽的数据位宽（数百甚至上千位）+ 大量 bank 交错，把带宽推到 TB/s 量级。昇腾 910B 的 HBM 带宽约 1.6 TB/s，910C 更进一步达到约 3.7 TB/s 量级。<span class="marginnote">HBM 与 GDDR 的区别：GDDR 走「高时钟 + 中位宽」路线（如显卡显存），HBM 走「低时钟 + 超高位宽 + 3D 堆叠」路线。HBM 因为 3D 堆叠在封装上把多颗 DRAM die 叠在一起，位宽可以做到极宽。关于带宽的完整账，见《HBM 高带宽内存与带宽设计》。</span>

L2 与 HBM 之间还有一个工程细节值得注意：**访存粒度**。L2 与 HBM 交换的最小单位是一整个 cache line 大小的大块，而非单字节。这意味着「小张量频繁读写」在昇腾上是低效的——每次搬运都带着整块数据，哪怕只用到其中的一小条。这也是为什么昇腾教程反复建议**把小的、碎片化的算子合并成大算子**：不只是减少同步，更是为了「搬运粒度」达标。**数据在存储层次间流动时，是按块搬的，不是按元素搬的**——记住这一点，很多性能困惑会迎刃而解。

## 4 数据流全景：一条张量的一生

把各层拼起来，看一条张量在昇腾上的「一生」，数据流可以归纳为四种典型路径：

| 数据流 | 路径 | 典型场景 |
| --- | --- | --- |
| 主存直达 Cube | HBM → L2 → L1 → L0 → Cube → L0C | 大 GEMM 的权重与输入 |
| 向量处理链路 | HBM/L2 → L1 → UB → Vector → L2/HBM | 激活、归一化、逐元素算子 |
| 核间接力 | 核 A 的 L2 数据 → 核 B 的 L1/L0 | 张量并行时相邻核交换中间结果 |
| 算子内转存 | L0C → UB（或 L0 ↔ UB） | GEMM 后接逐元素/规约 |

**辨析｜易错点：** 初学者常把昇腾的存储层次等同于 CPU 的缓存层次，于是期待「数据只要在 L2，访问就一定快」。事实上，**L1/L0/UB 的容量有限且需显式管理，数据若不能按时到达 Cube，一切靠缓存直觉的优化都会失效**。昇腾上真正的性能高手，画的第一张图永远是「数据流图」——每个算子的每个 tensor，在哪个时刻位于哪一层，谁生产、谁消费。

数据流图还有一个「多核版」：当算子被切分到多个 AI Core 上并行时，每个核都有一份自己的数据流，而核与核之间通过 L2 交换边界数据。这带来一个新的调度问题——**负载均衡**：若一个核分到的数据块明显偏多，其他核会干等。昇腾的编译器在切分时不仅考虑「每个核的 tile 放不放得下」，还要考虑「各核完成时间是否大致相同」。**单核看数据流，多核看负载均衡**，两套视角共同构成昇腾性能分析的整体框架。

顺着数据流往下看，还会遇到一个「在哪里切」的问题：一个大的矩阵乘，是每个核各算一块独立的输出（切输出），还是每个核各持一部分权重、对同一输出做部分累加（切权重）？两种切法对应不同的数据流形态：切输出让每个核「自给自足」，适合推理；切权重需要核间做部分和归约，适合训练时的张量并行。**切分策略决定了数据流拓扑，而数据流拓扑又反过来决定了要付出多少核间通信代价**——这个话题将在《HCCL 集合通信与多卡并行》中彻底展开。

## 5 数据格式：写在存储里的性能秘密

谈论存储层次时，一个常被忽略的前提是**数据以什么格式存储**。昇腾对矩阵的存放格式有一套自己的约定，最典型的是 **FRACTAL_NZ**（分形 NZ）格式：把一个大矩阵切成 $16\times16$ 的小块，再按特定顺序重新排列，使得 Cube 读取时能连续命中、少做转置。<span class="marginnote">FRACTAL_NZ 的名字拆开看：FRACTAL 指分形/分块重排，N 与 Z 是两种扫描方向的记号。它的本质是<strong>「把矩阵的物理布局对齐到 Cube 的访问模式」</strong>。</span>

为什么要花力气重排格式？因为**布局决定访存效率**。一个按行主序（row-major）存的大矩阵，在 Cube 眼里是「横着来」的；而 Cube 的乘加阵列是按 16×16 块「竖着取」的。若数据不重排，读取时会产生大量跨行跳跃，等效带宽大打折扣。昇腾的编译器会在算子下沉前，自动插入「格式转换」节点，把 ND（普通行主序）转成 FRACTAL_NZ——这个过程对上层用户透明，但它解释了为什么**同一个算子在昇腾上的最优实现往往与 GPU 长得完全不同**。<span class="marginnote">这也是为什么从 GPU 迁移到昇腾时，不能直接「照搬 kernel」：<strong>迁移的不只是代码，更是对数据布局的整套理解</strong>。CANN 生态里的自动转换帮助用户「先跑起来」，但极致性能仍要求开发者理解 FRACTAL_NZ。</span>

由此回看存储层次：**每一层「缓存」存的其实不是「同一份数据的更小副本」，而可能是「同一份逻辑数据的不同物理布局」**——L0 里是 FRACTAL_NZ 的输入块，L2 里是 ND 的原始张量。这个认识，是理解昇腾「数据流」与「格式转换」为什么总是绑定的钥匙。

举一个具体的重排例子。一个 $4\times4$ 的矩阵按行主序存为 $[a_{00},a_{01},a_{02},a_{03},a_{10},\dots,a_{33}]$；若 Cube 要按 $2\times2$ 的块去读，最理想的是把 4 个 $2\times2$ 小块 $[a_{00},a_{01},a_{10},a_{11}]$、$[a_{02},a_{03},a_{12},a_{13}]$……连续摆在一起。FRACTAL_NZ 做的事情正是这种「把块切出来、连续摆放」的重排。**重排看似只是「换个顺序」，但连续的内存访问与跳跃访问的带宽差异可达数倍**——这就是为什么昇腾把格式当成一等公民，而 GPU 生态的 cuBLAS 通常把这类重排藏在库函数内部。

## 6 公式解析：片上数据驻留率与搬运量

存储层次设计的终极目标，是让数据尽量**驻留**在片上（L0~L2），少与 HBM 交换。定义一个算子的**片上驻留率**，用「避免了多少片外流量」来衡量优化效果。设算子总的数据访问字节数为 $V_{\text{total}}$，其中发生在片内各层之间的为 $V_{\text{onchip}}$，则：

$$\text{Residency} = \frac{V_{\text{onchip}}}{V_{\text{total}}}$$

逐项拆解：

- **第一步，$V_{\text{total}}$**：算子执行期间，所有对数据的总访问量（读输入 + 读权重 + 写输出，可能多次往返）。
- **第二步，$V_{\text{onchip}}$**：其中被 L0/L1/L2 消化掉、未触及 HBM 的部分。tiling 做得好，权重会被反复复用，$V_{\text{onchip}}$ 占比极高。
- **第三步，解读**：$\text{Residency}$ 越接近 1，说明芯片越是在「用自己的缓存打天下」，HBM 只负责「一进一出」的大块数据。对单卡训练，高驻留率直接意味着高能效、低延迟。

由此引出昇腾算子的一个黄金法则：**能复用就别重搬，能片上就别下 HBM**。具体手段包括：权重常驻 L2（供整个 epoch 复用）、激活的中间结果就地计算（算子融合省去写回再读入）、以及把多个小算子打包成一个大 kernel 减少「搬出-搬入」边界。<span class="marginnote">算子融合之所以能同时省「算」和「省搬」，正是因为融合砍掉的是中间张量落回 HBM 的那一段路。这一点在 CANN 的《图编译器与算子融合》里会以图改写的形式重现。</span>

算一笔具体账。设一个 MLP 层：线性变换 $\mathbf{Y}=\mathbf{X}\mathbf{W}$（$\mathbf{X}$ 为 $4096\times4096$ 激活，$\mathbf{W}$ 为 $4096\times4096$ 权重），随后接 ReLU。若**不融合**：$\mathbf{Y}$ 写回 HBM（$\approx 32$ MB），再读出来做 ReLU（又 $\approx 32$ MB）——这一来一回多出约 64 MB 的 HBM 流量。若**融合**：ReLU 在 UB 里就地完成，$\mathbf{Y}$ 只存在于片上，HBM 流量省掉 64 MB。对一次训练 step 里成千上万个这样的层，融合省下的累计流量是惊人的——**这也是为什么昇腾生态把「融合」当作性能优化的头号主题**。

## 7 小结

- **存储层次**：L0/L0C（Cube 贴身）→ Unified Buffer（Vector 工作区）→ L1（预取中转）→ L2（全芯片共享）→ HBM（片外主存）。
- **显式管理**：L0/L1/UB 由软件显式控制，硬件不做自动替换——这是昇腾与 CPU 缓存的根本区别。
- **四种数据流**：主存直达 Cube、向量处理链路、核间接力、算子内转存。
- **驻留率公式** $\text{Residency}=V_{\text{onchip}}/V_{\text{total}}$：能复用就别重搬，能片上就别下 HBM。
- **L0「A 流式、B 常驻」的分区直觉**：把重用的权重钉在片上，把流式的激活用流水搬。
- **「L2 是缓存还是显存」是经典考题**：当自动缓存用软件简单但命中率不可控，当片上暂存性能可控但负担重。
- **数据按块搬，不按元素搬**：小的碎片化算子合并成大算子，为的是「搬运粒度」达标。
- **FRACTAL_NZ 把布局对齐到 Cube 访问模式**：迁移不只是换代码，更是换整套数据布局理解。

- **「每一层存的是同一份逻辑数据的不同物理布局」**：L0 里是 FRACTAL_NZ 的输入块，L2 里是 ND 的原始张量。
- **L2 到 HBM 的总带宽是所有核共享的**：多核同时爆发式访问会带宽争抢，单核把带宽用满不难，难的是所有核同时用满。
- **「单核看数据流，多核看负载均衡」**：编译器切分时既考虑 tile 放不放得下，也考虑各核完成时间是否大致相同。
- **重排看似只是「换个顺序」，连续与跳跃访问的带宽差异可达数倍**：这就是昇腾把格式当一等公民的原因。
- **算一笔账**：不融合的 MLP 层多出约 64 MB HBM 流量，一个训练 step 上万个这样的小算子，累计省下的是惊人的。
