## 为什么从指令集与流水线开始

上一篇我们把 AI Core 拆成 Cube、Vector、Scalar 三个单元——它们像三台机器，但机器再好，如果「喂料」与「取件」不同步，整条产线照样空转。**指令集决定机器能听懂什么命令，流水线决定命令如何被不间断地执行**。昇腾的 AI Core 在这两点上都与 CPU/GPU 很不一样：CPU 靠乱序执行与分支预测压榨单线程，GPU 靠成千上万线程掩盖延迟；而昇腾 AI Core 走的是「**多流水线显式并行 + 编译期静态调度**」的路子——硬件尽量简单，把「何时发射什么指令」的智慧前置到编译器。这一篇先看指令长什么样，再看流水线如何组织，最后回答「为什么会断流、怎么避免」。

在动手之前，先把「指令集」与「流水线」两个概念放对位置。**指令集（ISA）是「软件与硬件之间的合同」**：软件承诺只发这些指令，硬件承诺按语义执行；**流水线（pipeline）是「指令在硬件里的生产线」**：取指、译码、发射、执行、写回各司其职。对 AI Core 而言，合同的「粒度」被放大到张量块，生产线的「级数」则让位于「几条并行流水线」。理解这一层，就不会把「指令集」误当成一张单纯的指令表格——它其实是「你能让硬件干什么」的完整表达能力的边界。

顺带说一句：昇腾指令集的表达能力是「**偏科**」的——它在矩阵乘与向量运算上极强，却在通用逻辑（复杂分支、不规则内存访问）上偏弱。这不是缺陷，而是设计取舍：AI 算子的规律性正好落在它的强项区间。写算子时若发现「怎么都优化不动」，先问问自己：**这个算法的控制流是不是太不规则，超出了 AI Core 指令集的舒适区？** 必要时把不规则部分放到 CPU/主机侧，把规则的重活留给 AI Core。

## 1 AI Core 指令集：三类指令，各管一事

AI Core 的指令集可以按消费者分成几类，每一类对应一条独立的流水线，互不抢占：

| 指令类别 | 消费者 | 职责 | 典型指令 |
| --- | --- | --- | --- |
| Cube 指令 | Cube 单元 | 矩阵乘/卷积 | `matrixMul` 类指令，指定 A/B/C 在 L0 中的位置与尺寸 |
| Vector 指令 | Vector 单元 | 逐元素/规约/类型转换 | `vadd`、`vmul`、`vrelu`、`vsoftmax` 类 |
| Scalar 指令 | Scalar 单元 | 标量运算/分支/循环 | `add`、`cmp`、`jump`、`loop` 类 |
| 搬运/同步指令 | DMA 引擎、同步机制 | 数据搬移与核间同步 | `copy`（L2↔L0/L1）、`sync`、`barrier` 类 |

<span class="marginnote">与 CPU 指令集的差别是本质性的：CPU 指令操作「寄存器」，粒度是字；AI Core 指令操作「片上 buffer 中的张量块」，粒度是 KB 甚至 MB。<strong>一条 Cube 指令就完成一整块矩阵乘</strong>，所以指令条数少、但每条指令的「含金量」极高——这就是所谓「长指令、粗粒度」的 AI 专用指令集。</span>

### 1.1 指令携带「形状信息」

一条 Cube 指令并不是简单说「做矩阵乘」，而是要声明**操作数在 L0 Buffer 中的位置、tile 的尺寸、是否转置、累加起始地址**。换句话说，**数据布局是指令的一部分**。这使得编译器在生成指令时必须同时决定数据摆放——「先定布局，再定指令」成为昇腾编译器的铁律。<span class="marginnote">这也是为什么昇腾对「数据格式（format）」特别敏感：同一张矩阵，按行主序（row-major）还是按昇腾偏好的专用分块格式（如 ND、FRACTAL_NZ）存储，生成的指令完全不同，性能可能差出数倍。格式话题我们在《Ascend C 算子编程模型》中还会碰到。</span>

从指令编码的角度看，昇腾的指令是「**立即数丰富、操作数宏大**」的：一条指令里塞进了 tile 尺寸、步长、偏移、精度模式等多个字段，像一个「打包好的工作订单」。与之相对，CPU 指令操作的是「寄存器编号」（几个比特），因为寄存器只有几十个；而昇腾指令操作的是「buffer 地址 + 形状」，信息量大得多。**这条差异的根源是硬件设计意图：CPU 想让一条指令尽快执行完，昇腾想让一条指令干完一大摊活**。指令越「大」，发射开销越被摊薄，这正是长指令路线的立足点。而「形状信息」必须写进指令，也意味着同一段算法的不同输入尺寸，会生成不同的指令序列——所以昇腾的算子往往按「形状（shape）」分派，为常见 shape 预编译好 kernel，运行时按 shape 选 kernel 而不是现编。

## 2 流水线组织：三流并行 + 同步屏障

### 2.1 三条独立流水线

AI Core 内部有**三条计算流水线**（Cube 流水、Vector 流水、Scalar 流水）加**一条搬运/存储流水**。四条流水可以同时前进：一个周期内，Cube 在算第 $i$ 块、Vector 在算第 $i-1$ 块的激活、DMA 在搬第 $i+1$ 块的输入、Scalar 在算地址——这就是上一节提到的软件流水。硬件为此付出的代价是**每个单元都要有独立的指令缓冲与译码逻辑**，换来的是单核内的高并行度。

四条流水线并不是「地位平等」的。**Cube 与 Vector 是生产者，DMA 是搬运工，Scalar 是发令官**——而搬运工永远服务于生产者。设计者最关心的平衡是：**DMA 的搬运带宽能否跟上 Cube/Vector 的消耗速度**。若 DMA 每周期能搬的数据 < 三个计算单元每周期要消费的数据，那么即使指令调度得再好，计算单元也会因「无米下锅」而等待。于是昇腾在硬件层面给了 DMA 足够宽的端口与独立的地址计算单元，让它在「幕后」稳定供血——这条「供血线」的宽窄，往往比某条计算流水线的深度更能决定最终性能。

### 2.2 同步屏障：不让流水「撞车」

并行必然带来依赖问题：Vector 要处理的 L0C 结果，必须等 Cube 写完；Cube 的下一块输入，必须等 DMA 搬完。昇腾用**同步机制（sync/barrier 指令）**在流水线之间建立「会合点」。一条 `sync` 指令的效果是：**让后续的某类指令等待之前的所有同类指令完成**。<span class="marginnote">屏障粒度可以按单元选择：只等 Cube、只等 Vector、只等搬运，或者全部等齐。粒度越细，等待越短，但编译器要做的依赖分析越复杂——这是性能与复杂度的又一次权衡。</span>

**辨析｜易错点：** 不要以为「指令越多并行度越高」。恰恰相反，**过于细碎地发射指令会让同步开销吃掉并行收益**。昇腾的做法是「一次把一整块工作交给一个单元，再集中同步一次」——块越大，同步频率越低，利用率越高。这也解释了为什么昇腾算子开发强调 **tiling（分块）粒度要够大**：把 16×16 的小 tile 逐个同步是灾难，把整个 128×128 甚至更大的 tile 交给 Cube 连续算完再同步才是正确姿势。

换个角度理解同步：它其实是「数据依赖」在时间轴上的投影。Cube 写 L0C、Vector 读 L0C，这是一条依赖；DMA 搬 L0、Cube 读 L0，这是另一条依赖。**每一条依赖都必须被一条同步指令「担保」**，否则就是数据竞争。因此同步指令的条数与算子内部的依赖边数成正比——这也从侧面说明，为什么「算子融合」（减少中间张量）能同时减少同步：**中间张量少了，跨单元的依赖边也少了**。

### 2.3 顺序发射，但不妨碍并行

一个常见的误解是：「昇腾 AI Core 既然三流并行，那它一定像现代 CPU 一样支持乱序执行（out-of-order）」。实际上，昇腾的 AI Core **以顺序发射（in-order issue）为主**：每条流水线上的指令按编译器排定的顺序依次发射，硬件不重排。乱序执行的复杂度（寄存器重命名、重排序缓冲、冒险检测）被昇腾整个省略了——它相信编译器已经在编译期把所有依赖理清，运行期只需要「按部就班」。

这套「顺序发射 + 编译期调度」的组合，本质上是用软件的「离线智能」换取硬件的「在线简单」。它的代价是：**如果一个算子的依赖关系在编译期没有被充分挖掘，运行期也不会得到任何补救**——硬件不会像 GPU 那样用线程切换兜底。因此昇腾上「编译质量」直接决定「执行效率」，这也是 CANN 图编译器在昇腾生态里地位极高的原因。<span class="marginnote">对比 CPU：现代 CPU 花了几十年的晶体管预算去支持乱序、分支预测、投机执行，就是为了「软件写得糙也能跑得快」。昇腾把这个预算还给了 AI Core 的存储与计算单元——<strong>前提是软件栈足够强</strong>。</span>

## 3 公式解析：流水线吞吐与「加速比」

衡量流水线好坏，先看理想情况。设一条流水线有 $S$ 级，单级延迟为 $t$，则处理一个任务需要 $S t$，但**稳态下每个周期流出一个结果**，吞吐为 $1/t$。<span class="marginnote">这就是流水线的基本悖论：<strong>单个任务变慢了（多了填满时间），但整体吞吐不变</strong>——只要任务足够多，流水线就是划算的。</span>

考虑 Cube 流水处理 $N$ 个 tile，理想吞吐为：

$$T_{\text{ideal}} = N \cdot t_{\text{cube}}$$

实际执行时，由于同步屏障、数据未就绪等待、以及流水线填满/排空，实际耗时为：

$$T_{\text{actual}} = N \cdot t_{\text{cube}} + \underbrace{N \cdot t_{\text{stall}}}_{\text{等待}} + \underbrace{t_{\text{fill}} + t_{\text{drain}}}_{\text{填满与排空}}$$

逐项拆解：

- **第一步，$N \cdot t_{\text{cube}}$**：理想情况下每个 tile 花 $t_{\text{cube}}$，全部串起来。
- **第二步，$N\cdot t_{\text{stall}}$**：真实世界每个 tile 平均要等 $t_{\text{stall}}$（数据没到、屏障同步、Vector 没算完），这是最主要的损失项。
- **第三步，$t_{\text{fill}}+t_{\text{drain}}$**：流水线刚启动时是空的，要 $S$ 个周期才能填满；结束时也要排空。任务数 $N$ 越大，这笔固定开销摊得越薄。

由此得到**流水线利用率**：

$$\text{Utilization} = \frac{T_{\text{ideal}}}{T_{\text{actual}}} = \frac{N\cdot t_{\text{cube}}}{N(t_{\text{cube}}+t_{\text{stall}})+t_{\text{fill}}+t_{\text{drain}}}$$

**推论：要逼近 100% 利用率，必须让 $t_{\text{stall}} \to 0$ 且 $N$ 足够大。** 前者靠「数据提前就位」（软件流水 + 双缓冲），后者靠「把算子切成尽量少的、尽量大的块」（减少同步次数）。这两条，正是昇腾算子优化手册里出现频率最高的两条建议。

用一个数字例子感受「等待的代价」。设 $t_{\text{cube}}=100$ 周期、$t_{\text{stall}}=25$ 周期、$t_{\text{fill}}+t_{\text{drain}}=20$ 周期。当 $N=10$ 时，$\text{Utilization}=10\times100/(10\times125+20)\approx 78\%$；当 $N=100$ 时，利用率升至 $\approx 80\%$，而若把 $t_{\text{stall}}$ 压到 0，$N=100$ 时利用率可达 $10000/10020\approx 99.8\%$。**可见：优化 $t_{\text{stall}}$ 比盲目加任务数有效得多**——这也解释了为什么昇腾性能工程师的第一动作永远是「打开 profile，看 Cube/Vector 的空闲比例（stall 占比）」，而不是急着改算法。

## 4 双缓冲与软件流水：把「等待」藏起来

如何把 $t_{\text{stall}}$ 压到接近零？核心技巧是**双缓冲（double buffering）**：为数据准备两套缓冲，一套在算、一套在搬。

- 第 $i$ 块在 L0 Buffer A 里被 Cube 计算时，第 $i+1$ 块正在被 DMA 搬进 L0 Buffer B；
- 算完 A 换 B，DMA 同时开始搬第 $i+2$ 块进 A；
- **只要「搬一块」的时间 ≤「算一块」的时间，Cube 就永远不空等**，$t_{\text{stall}}\approx 0$。

双缓冲的思想还可以向上推广成「多级流水」：不仅 L0 与 L2 之间可以双缓冲，L2 与 HBM 之间、以及相邻 AI Core 之间都可以做类似的搬算重叠。昇腾编译器会在多层同时建立「在算/在搬」的交替节奏，形成一条**从 HBM 一路铺到 Cube 的输送带**。这条输送带的每一级都要满足一个约束：**上一级搬得快于下一级消费，输送带才不会断**。工程上，这体现为「按瓶颈级配缓冲」的调优口诀——先找最慢的那一级，把它的双缓冲做足，其他级不必过度投资。

这套「搬算重叠」在指令上由编译器静态排布，硬件无需像 CPU 那样做动态调度。<span class="marginnote">这也是昇腾与 GPU 最大的哲学分野之一：<strong>GPU 用大量线程「乱序补洞」，昇腾用编译器「提前排雷」</strong>。前者硬件复杂、软件简单；后者硬件简单、软件复杂。到了 CANN 一篇我们会看到，这份「复杂」被昇腾交还给了图编译器与算子库。</span>

双缓冲当然不是免费的午餐，它的代价是**存储容量翻倍**：要两套 L0/UB 缓冲区才能「一边算一边搬」。对面积敏感的芯片来说，这迫使设计者在「缓冲区大小」与「搬运重叠度」之间精打细算。昇腾的实际做法是折中：**不是所有 buffer 都双份，而是让编译器按算子的访存特性决定哪些数据需要双缓冲**。重读率高的权重可以只放一份（它一直在 L0 里），而每轮都要换新的激活输入才值得开双缓冲。这种「按需双缓冲」正是显式数据流架构的灵活之处——换作硬件自动管理的缓存，你根本无法精确控制这种布局。

## 5 小结

- **指令集是粗粒度、长指令、带形状信息**：一条 Cube 指令完成一整块矩阵乘，操作数位置与 tile 尺寸都写进指令。
- **流水线是「三算一搬」四线并行**：Cube、Vector、Scalar、DMA 各走各的流水，靠 `sync`/`barrier` 同步。
- **利用率公式** $\text{Utilization}=T_{\text{ideal}}/T_{\text{actual}}$：损失主要来自同步等待，填满/排空是固定开销。
- **双缓冲 + 软件流水**把搬算重叠，让数据「提前就位」，是压 $t_{\text{stall}}$ 的主力。
- 昇腾哲学：**编译器静态调度，硬件保持简单**——与 GPU 的动态调度路线形成对照。
- **顺序发射**：AI Core 以 in-order issue 为主，把调度智慧全部交给编译器，硬件不做乱序补救。
