## 为什么从 CANN 软件栈开始

前十三篇我们把昇腾从达芬奇架构一路拆到了超节点集群——硅片、缓存、HBM、服务器、互联，一层层物理实体都看过了。但读者心里一直悬着一个问题：**这些硬件凭什么能被 PyTorch/MindSpore 里的一个 `model.train()` 调用起来？** 答案就在软件栈。华为把这套连接「框架」与「芯片」的软件层命名为 **CANN（Compute Architecture for Neural Networks，神经网络计算架构）**。<span class="marginnote">CANN 之于昇腾，正如 CUDA 之于 NVIDIA——<strong>它是「把硬件能力暴露给上层软件」的那层翻译器</strong>。没有它，910B 只是一块不能编程的硅。</span>

这一篇建立 CANN 的**总地图**：它由哪些层组成、每层干什么、层与层怎么协作。把地图先立起来，后面五篇（图编译器、Ascend C、Cube 实战、HCCL、MindSpore 适配）才能各自「对号入座」。本篇是纯概念主题，用**核心对比表**代替公式解析。

在建立地图之前，先回答一个更根本的问题：**为什么 AI 芯片需要一套「自家软件栈」，而不是像 CPU 那样「装个驱动就能用」？** 因为 CPU 的指令集是「通用合同」，任何操作系统都能直接翻译；而昇腾的 AI Core 是「专用单元」——Cube 矩阵乘、Vector 向量流、显式数据流，这些能力没有「通用合同」，必须由一套专门的软件去调度、编译、优化。**「硬件越专用，软件越厚重」**是 AI 芯片时代的铁律：昇腾在硬件上省下的复杂度，全部转移到了 CANN 这套软件栈里。

## 1 软件栈的坐标：框架之下、芯片之上

把昇腾的软件生态从用户视角看，可以排成一条「栈」：

| 层 | 名字 | 干什么 | 类比 |
| --- | --- | --- | --- |
| 最上层 | 深度学习框架 | MindSpore / PyTorch / TensorFlow，用户写模型 | 写菜谱 |
| 上层 | CANN 应用接口 | AscendCL，统一编程接口 | 点菜下单 |
| 中层 | 图引擎 GE | 构图、优化、调度、算子融合 | 厨师长统筹 |
| 下层 | 算子层 | 算子库 + Ascend C / TBE 算子 | 掌勺炒菜 |
| 底层 | 运行时与驱动 | Runtime、Driver，直接驱动硬件 | 端盘上菜 |

<span class="marginnote">这张表的阅读顺序是「<strong>从框架到驱动，一层比一层离硬件更近</strong>」。用户几乎只接触最上层；越往下，越是为「让芯片跑满」服务的工程层。CANN 恰好是中间那三层的统称。</span>

**CANN 的位置**：它从「框架对接层」一路覆盖到「驱动之上的运行时」，把「模型怎么算」翻译成「芯片怎么执行」。理解 CANN，就是理解这条翻译链的每一环。这张栈表会作为后续所有篇章的「坐标系」反复出现——每讲一个新组件，先问「它在栈的哪一层」。

## 2 CANN 的五层地图

把 CANN 内部再细化成五层，是理解它的标准动作。这五层各有各的「客户」与「产出」：

**第一层，AscendCL（Ascend Computing Language）**：给上层框架与应用的统一编程接口。用户（或框架）通过它申请设备、创建流、执行算子、管理内存——它屏蔽了下层所有细节，是「一扇统一的门」。<span class="marginnote">AscendCL 的设计哲学是「<strong>统一接口、多后端实现</strong>」：同一套 API，既可以驱动昇腾，也便于框架接入。PyTorch 适配昇腾，本质就是让 PyTorch 的算子调用落到 AscendCL 上。</span>

**第二层，图引擎 GE（Graph Engine）**：CANN 的「大脑」。它接收框架送来的计算图，做整图优化（算子融合、内存复用、调度、tiling 决策），再交给下层执行。GE 是「编译智慧」的载体——第 15 篇《图编译器与算子融合》会专门钻进去。

**第三层，算子层**：包含预置的**算子库**（MatMul、Conv、Softmax 等常见算子的优化实现）与**算子开发工具**（Ascend C、TBE）。算子库是「即插即用」的成熟实现，算子开发工具是「现写」新算子的手段。第 16~17 篇讲的就是这层。

**第四层，运行时 Runtime**：负责算子的实际执行——加载 kernel、分配设备内存、管理流与事件、维护执行状态。它是「CPU 侧调度 + 芯片侧执行」的交接点。

**第五层，驱动 Driver**：最贴近硬件的软件，直接操作 AI Core 与存储。驱动之上的一切都依赖它把「抽象指令」变成「硬件动作」。

这五层的关系可以压缩成一句话：**AscendCL 定接口，GE 做优化，算子层定执行，Runtime 管运行，Driver 管硬件**。层与层之间通过定义良好的接口协作，上层不必关心下层实现——这种「分层」让每一层可以独立演进，也让排障时责任边界清晰。

## 3 核心对比表：CANN 与 CUDA 的「同构不同名」

把 CANN 与 NVIDIA 的 CUDA 软件栈并排看，能最快建立「它到底是干什么的」的直觉。两者在宏观上是**同构**的——都是「框架 → 计算架构 → 硬件」三段式，只是名字与实现不同：

| 职责 | NVIDIA | 华为昇腾 | 说明 |
| --- | --- | --- | --- |
| 统一计算接口 | CUDA Runtime / Driver API | AscendCL | 给框架与应用的编程入口 |
| 图级优化 | TensorRT / cuDNN 启发 | 图引擎 GE | 整图融合与调度的载体 |
| 算子库 | cuBLAS / cuDNN | 昇腾算子库 | 预置优化算子 |
| 算子开发语言 | CUDA C | Ascend C / TBE | 手写自定义算子 |
| 集合通信库 | NCCL | HCCL | 多卡并行通信 |
| 运行时与驱动 | CUDA Runtime + Driver | CANN Runtime + Driver | 直接驱动硬件 |

<span class="marginnote">这张表最容易误导的地方是「<strong>一一对应</strong>」：读者容易把 GE 当成「昇腾的 TensorRT」。其实 GE 是编译期图优化（跑在训练时），TensorRT 更多是推理期优化——<strong>两者在「何时优化」上并不完全对齐</strong>。对应关系用于建立直觉，细节要逐层单独学。</span>

看懂这张表的真正价值，是理解昇腾「**为什么非要自建软件栈**」：CUDA 生态的护城河太深，昇腾无法「借」，只能「自建一套同构的」。而这套同构软件栈的每一层，都必须在「显式数据流」的硬件哲学下重新设计——这就是为什么昇腾的图编译器、算子语言、通信库都值得单开篇章。**同构是「目标」，重新设计是「现实」**，两者之间的张力，贯穿 CANN 的全部内容。

## 4 一次算子调用的完整旅程

把五层地图「跑一遍」，看一个 `matmul` 算子从框架到芯片的完整旅程：

1. **框架**调用 MindSpore 的 `ops.MatMul`，生成一个计算图节点；
2. **AscendCL** 接到「执行 MatMul」的请求，把它投递给 GE；
3. **GE** 拿到整张图，对 MatMul 做优化：决定 tiling 方案、安排数据流、选择执行单元（Cube）、插入同步点；
4. **算子层**提供 MatMul 的 kernel 实现（若算子库没有，则用 Ascend C 现写并编译）；
5. **Runtime** 把编译好的 kernel 加载到 AI Core，分配设备内存，发起执行；
6. **Driver** 驱动 AI Core 真正完成乘加，结果写回显存。

<span class="marginnote">这条旅程里，<strong>用户（框架）只做第 1 步，其余五步全由 CANN 代劳</strong>。但「代劳」不等于「免费」：每一步都有优化空间，也都可能成为性能瓶颈——这正是后面几篇逐个展开的对象。读到最后你会发现，<strong>昇腾上所有的性能优化，本质上都是在这六步里「找窟窿、堵窟窿」</strong>。</span>

这条旅程还揭示了软件栈设计的「哲学分水岭」：昇腾把「调度与优化」前置到了编译期（第 3 步），而不是像 GPU 那样留给运行期硬件调度器。**「编译期尽可能算清楚，运行期尽可能简单执行」**——这是 CANN 与 CUDA 在架构哲学上的最深差异，也是它把「软件复杂度」背在自己身上的原因。第 15 篇的图编译器，就是这套哲学的集中体现。

## 5 为什么 CANN 值得单独成专题

CANN 在整个「从极限到大模型」课程里的位置，是「**把硬件知识变成生产力**」的那一环。前十三篇建立的是「昇腾长什么样」，从这一篇开始的六篇建立的是「昇腾怎么用」。没有这六篇，前十三篇只是「纸面图鉴」；有了这六篇，前十三篇的每个概念（L0/L1、tiling、算术强度、拓扑）才真正「有了用武之地」。

对读者而言，CANN 的学习价值还在于**可迁移性**：无论未来接触昇腾、寒武纪还是任何国产芯片，都会遇到「自家软件栈」——而 CANN 的「分层地图 + 统一接口 + 编译期优化」几乎是所有国产 AI 软件栈的共同范式。**学会了读 CANN 这张地图，就等于学会了读任何一张 AI 软件栈地图**。这也是为什么本专题把 CANN 单独拉出来讲透，而不只是「顺带提一句」。

## 6 小结

- **CANN** 是昇腾的神经网络计算架构，连接「框架」与「芯片」，是昇腾版的 CUDA。
- 五层地图：**AscendCL（接口）→ GE（图优化）→ 算子层（执行）→ Runtime（运行）→ Driver（硬件）**。
- **硬件越专用，软件越厚重**：昇腾的显式数据流决定了它必须自建一套厚重软件栈。
- 与 CUDA **宏观同构、细节各异**：同名职责（算子库、集合通信）一一对应，但优化时机与哲学不同。
- 一次算子调用要经历六步旅程，**性能优化就是在这六步里找窟窿**。
- **编译期优化 vs 运行期调度**，是 CANN 与 CUDA 的哲学分水岭。
- **层与层通过定义良好的接口协作**：上层不必关心下层实现，每一层可以独立演进，排障责任边界清晰。
- **GE 做整图优化、JIT 保动态 shape**：静态编译保性能，JIT 保灵活性，是昇腾推理优化的常考题目。
- **AscendCL 是「一扇统一的门」**：同一套 API 既可驱动昇腾，也便于 PyTorch 等框架接入。

- **CANN 五层之间通过定义良好的接口协作**：接口清晰是「每一层可以独立演进、排障责任边界清晰」的前提。
- **本专题的软件篇由此开启**：后面五篇（图编译器、Ascend C、Cube 实战、HCCL、MindSpore）都在回答「五层地图里某一层怎么做到极致」。

## 7 动手练习：画出你自己的 CANN 地图

学完这一篇，动手画一张「CANN 分层地图」是巩固理解的最好方式：

1. **画出五层**：AscendCL、GE、算子层、Runtime、Driver，从上到下排好。
2. **给每层标一句「它的客户是谁」**：AscendCL 服务框架与应用，GE 服务 AscendCL，算子层服务 GE……依次标下去。
3. **标出「哪里藏性能」**：在每层旁边写一个「优化点」——AscendCL 接口是否高效、GE 融合做得好不好、算子是否落在算子库。
4. **把前十三篇的知识点钉到层上**：L0/L1 属于硬件（Driver 之下），tiling 属于算子层，算子融合属于 GE——你前面学过的每个概念，都能在这张地图上找到「层地址」。

这张地图完成后，你会发现自己对昇腾的认知从「一串型号参数」变成了「一张分层系统图」——这正是本专题想给你的最后一份礼物：**把零散的知识，织成一张能迁移的地图**。

在下一节，我们将钻进 CANN 的「大脑」——图引擎 GE，看它如何把几十上百个算子编译成昇腾上高速执行的指令，这就是**图编译器与算子融合**。
