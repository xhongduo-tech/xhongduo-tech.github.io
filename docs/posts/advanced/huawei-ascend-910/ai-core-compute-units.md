## 为什么从 AI Core 的三个单元开始

上一篇我们拿到了达芬奇架构的总图：一颗昇腾芯片由几十个 AI Core 组成，每个 AI Core 内部有 Cube、Vector、Scalar 三个单元。现在我们要回答一个更本质的问题：**为什么是这三个单元，而不是一个「全能单元」？** 答案藏在深度学习的计算结构里——它天然分成三种粒度：矩阵、向量、标量。把三种粒度各配一个专用执行单元，就是 AI Core 的「三单元分工」。这一篇拆开看每个单元的内部结构与适用边界，并在最后用一张图把三者的配合关系钉进记忆。

这张图值得你先看三秒再往下读：三块「计算单元」并列排开，脚下踩着各自的局部存储，最下方是 L2 与 HBM。**三个单元谁都不直接访问 L2/HBM**——它们只跟自己的局部存储打交道，跨层的搬运全部交给 DMA 引擎。这个「计算单元-局部存储」的绑定关系，是三单元设计的物理真相：**每个单元身边都有一个「专属粮仓」，搬运由专职搬运工负责**。理解了这张图的绑定结构，后面的 L0/UB/L1 分工、tiling、软件流水就都有了地图。

## 1 Cube 矩阵单元：算力的发动机

**Cube Unit（矩阵计算单元）**：AI Core 中专司矩阵乘（GEMM）的硬件单元，一次可完成 $16 \times 16 \times 16$ 的乘累加阵列运算，是整颗芯片峰值算力的主要来源。

### 1.1 为什么矩阵乘值得「量身定做」

卷积与全连接层的本质是矩阵乘：输入特征 $\mathbf{X} \in \mathbb{R}^{M\times K}$ 与权重 $\mathbf{W}\in\mathbb{R}^{K\times N}$ 相乘得输出 $\mathbf{Y}=\mathbf{X}\mathbf{W}\in\mathbb{R}^{M\times N}$。计算量为 $2MNK$ 次乘加，而其中每个输出元素 $y_{ij}=\sum_{k=1}^{K}x_{ik}w_{kj}$ 都是**一个乘加序列**。若用通用单元逐个乘加，每算一个 $y_{ij}$ 都要反复读写中间结果；Cube 单元则把 $16\times16$ 的输出子块一次性算完——输入的 $16\times16$ 个 $x$ 与 $16\times16$ 个 $w$ 各自进入 L0 Buffer，在乘加阵列里「像一块布一样被织出来」。<span class="marginnote">16×16×16 是昇腾官方的 Cube 基础尺寸：一次取 A 的 16 行、B 的 16 列，做 16 层乘加。更大的矩阵乘被切成无数个 16×16 子块（tile），逐个喂给 Cube。这个分块策略我们会在《Cube 矩阵乘算子开发实战》里写代码验证。</span>

### 1.2 Cube 的两种核心形态

昇腾的 Cube 除了常规 GEMM，还支持 **GEMM 的变形**：卷积可以被改写为矩阵乘（im2col 或 implicit GEMM），矩阵转置、批次矩阵乘（batched GEMM）也在 Cube 的能力范围内。之所以把这么多形态都收敛到「矩阵乘」，是因为**只要收敛成 GEMM，就能吃到 Cube 的专用硬件**——这是昇腾编译器做算子下沉（把算子映射到硬件指令）时的第一原则。

### 1.3 数据复用：Cube 高吞吐的隐形前提

Cube 能维持 4096 次乘加/周期的前提，是**输入数据被高度复用**。在一次 $16\times16\times16$ 乘加中，16 个输出位置共享同一批输入元素——这是矩阵乘天然的「重读」结构。硬件利用这一点，把权重与激活分别留在 L0 的两个分区里反复使用，而不是每算一个输出就去内存重读。**复用程度越高，Cube 越不需要等数据**；而「让数据在 L0 里多待一会儿」正是 tiling 分块要解决的布局问题。可以这么说：**矩阵乘之所以是 AI 计算的王者，一半因为算得快，一半因为数据复用度高到可以喂饱专用硬件**。

## 2 Vector 向量单元：算力的搬运工与加工厂

**Vector Unit（向量计算单元）**：AI Core 中执行逐元素、规约与向量运算的单元，工作区是统一缓冲（Unified Buffer），负责所有「不是矩阵乘」的算术。

为什么矩阵乘之外的运算要单开一个 Vector 单元？因为它们的形状太「碎」：

**逐元素**：激活函数（ReLU、GELU）、残差相加、逐元素乘——每个输出只依赖一个或两个输入元素，算术强度接近 1 FLOP/byte；
**规约**：softmax 的分母求和、LayerNorm 的均值/方差——把一个向量压成一个标量；
- **向量移动与转换**：数据类型转换（FP32→BF16）、内存搬运、拼接。

这些运算若强行交给 Cube 做，16×16 的矩阵阵列会大面积空转——「杀鸡用牛刀」。Vector 单元的设计目标是：**把一次「读一批元素→算→写回」的流式操作做到最高吞吐**，并直接对接 Unified Buffer，让数据在本地完成变换而不必绕道 L1/L2。<span class="marginnote">Transformer 里一个注意力头，<strong>Query×Key 矩阵乘交给 Cube，softmax 与缩放交给 Vector，输出投影再交给 Cube</strong>——一个算子被切分成「Cube 段」与「Vector 段」交替执行，是昇腾上跑 Transformer 的标准节奏。</span>

Vector 单元的另一项被低估的职责是**数据格式转换**。深度学习里同一条数据经常要换精度：训练时梯度用 FP32、前向用 BF16，推理时做 INT8 量化要把浮点压成整数。昇腾让 Vector 单元在「搬」的过程中顺手完成类型转换——**数据从 L2 搬进 UB 的途中，就完成了 FP32→BF16 的降精度**，省下一趟独立的转换算子。这类「搬运即转换」的融合思想，在 CANN 算子融合一篇里会以更系统的形式出现。

**Vector 与 Cube 的职责边界，由算术强度决定**：$I \gg P/\text{BW}$ 的算子归 Cube，$I \approx 1$ 的算子归 Vector。这正是上一篇「算术强度判据」的第一个落地实例。

## 3 Scalar 标量单元：流水线的指挥

**Scalar Unit（标量计算单元）**：AI Core 中执行标量运算、地址计算与程序控制的单元，负责驱动整条流水线的节奏。

标量单元做的事通常不起眼，但缺了它整颗芯片无法运转：

**地址计算**：tiling 之后，下一个数据块在 L1/L2/HBM 里的地址由谁算？Scalar。
**循环控制**：分块循环的计数器、跳转、分支判定——Scalar。
- **少量标量算术**：例如归一化里的 $\sqrt{\text{var}+\epsilon}$、逐元素缩放系数——Scalar。
- **指令发射**：从指令存储中取出指令，分发给 Cube/Vector 各自的流水线——也是 Scalar 单元主导。

可以用一个比喻收束三者关系：**Cube 是工厂里的大冲床（一次压出一整块），Vector 是流水线上的小机床（逐个精加工），Scalar 是车间主任（决定下一块料什么时候送到哪台机器）**。<span class="marginnote">三者并行执行、共享同一片局部存储，由标量单元协调数据到达的时序——这种「一个指挥、多条流水」的结构，是 AI Core 能在单核内达到高利用率的关键，也直接决定了下一节《指令集与流水线设计》要讨论的「数据是否来得及」。</span>

车间主任手里的「排产表」从哪来？来自编译器。昇腾的算子编译流程会把一段 Python/C++ 算子描述展开成一长串标量指令序列：循环边界、tile 步进、地址增量、同步点，全被标量单元逐条执行。这带来一个反直觉的推论：**标量单元的性能（指令发射速率）反而会成为大算子的隐藏瓶颈**。若一个算子的循环体太碎、tile 太小，标量单元可能忙着发指令、而 Cube 在空等下一块数据——这就是「指令发射受限」。优化手段也很直接：**把循环展开、把 tile 加大，减少标量指令的条数**。这条经验在昇腾算子优化的实际案例里反复出现。

## 4 三个单元的配合：一个 GEMM + GELU 的完整旅程

把三者拼起来看一次真实的算子执行，设某层要算 $\mathbf{Y} = \text{GELU}(\mathbf{X}\mathbf{W})$：

| 阶段 | 执行者 | 数据在哪 | 干什么 |
| --- | --- | --- | --- |
| 1. 取数 | Scalar + DMA | L2/HBM → L0 Buffer | 把 $\mathbf{X}$ 的 tile 搬到 L0 Buffer A |
| 2. 取权 | Scalar + DMA | L2 → L0 Buffer B | 把 $\mathbf{W}$ 的 tile 搬到 L0 Buffer B |
| 3. 乘累加 | Cube | L0 Buffer → L0C | 计算 $\mathbf{X}_{tile}\mathbf{W}_{tile}$，结果累积在 L0C |
| 4. 转存 | DMA | L0C → Unified Buffer | 把累加结果搬到向量工作区 |
| 5. 激活 | Vector | Unified Buffer | 对每个元素算 GELU |
| 6. 写回 | DMA | Unified Buffer → L2/HBM | 输出 $\mathbf{Y}$ 的 tile |

**三个阶段（取数、Cube 计算、Vector 处理）可以像流水线一样重叠**：Cube 正在算第 $i$ 块时，Scalar/DMA 已经在搬第 $i+1$ 块，Vector 正在处理第 $i-1$ 块的激活。<span class="marginnote">这就是「软件流水」（software pipelining）：<strong>让每个单元永远有活干，而不是轮流排队</strong>。衡量这份重叠做得好不好的指标叫「流水利用率」，它是《AI Core 指令集与流水线设计》的主角。</span>

要做到这种重叠，硬件只提供一个条件：**三个单元可以互不阻塞地并行前进**。这意味着它们各自拥有独立的指令队列与寄存器文件，互不共享执行资源。而软件则要承担「别让它们撞车」的责任——什么时候 Cube 能读 L0、什么时候 Vector 能写 UB，都由编译器排定，运行期不需要仲裁。**硬件把并行能力给足，软件把并行秩序排好**，是昇腾 AI Core 协作设计的完整表述。

这张旅程表还暴露了一个容易被忽视的点：**一次算子执行里，真正「算」的时间可能只占一半**。取数与写回（阶段 1、2、4、6）都是搬运，只有阶段 3、5 是计算。因此「提高计算占比」成为昇腾算子优化的永恒主题——手段包括加大 tile（摊薄每块的搬运固定开销）、让搬运与计算重叠（软件流水）、以及把多个算子融成一个 kernel（砍掉中间的搬运）。**换句话说：三单元的分工只是起点，「让三个单元同时忙起来」才是性能的真战场**——这个主题贯穿本专题第 3 篇（流水线）与第 15 篇（算子融合）。

## 5 公式解析：单周期乘加吞吐与单元规模

Cube 单元的峰值吞吐可以用一个简单的式子框住。设乘加阵列尺寸为 $a \times a \times k$（昇腾为 $16\times16\times16$），主频为 $f$，则每秒完成的乘加数为：

$$\text{MACs/s} = a^2 \times k \times f$$

逐项拆解：

- **第一步，$a^2 \times k$ 是单周期乘加次数**：$a\times a$ 个输出位置，每个位置做 $k$ 层累加，一次发射完成 $a^2k$ 次乘加。对 $16\times16\times16$ 即 $4096$ 次乘加/周期。
- **第二步，乘 $f$ 得每秒次数**：把单周期吞吐乘上主频，得到每秒乘加数。FLOPs 通常按「乘加 = 2 FLOP」计数，于是 BF16 峰值约为 $2\times4096\times f$。
- **第三步，与整芯片对账**：单核吞吐乘上 AI Core 数量再乘上时钟，就得到芯片峰值。这正是各型号白皮书里 TFLOPS 数字的来历——**它是一条从阵列尺寸出发的乘法链，而不是凭空给的**。

这条式子揭示了两个设计杠杆：**把阵列做大（$a^2k$ 大），或把频率拉高（$f$ 大）**。阵列做大的代价是面积与布线压力，频率拉高的代价是功耗与散热。昇腾选择把阵列定在 $16\times16\times16$、并靠「多个 AI Core 并行」来扩规模，就是在面积、功耗、良率之间取平衡。<span class="marginnote">对比之下，NVIDIA 的 Tensor Core 用更小的子块（4×4 或 8×8）配合更长指令执行周期，达到类似的单指令乘加总量——不同厂商把「单次发射做多少乘加」放在不同的硬件层，思路殊途同归。</span>

用一个具体例子走一遍乘法链。设某昇腾型号主频 $f=1.8$ GHz，则单核 BF16 峰值约为 $2\times 4096\times 1.8\times 10^9 \approx 1.47\times 10^{13}$ FLOP/s。若该芯片含 40 个 AI Core，整卡 BF16 峰值约为 $40\times 1.47\times10^{13}\approx 5.9\times 10^{14}$ FLOP/s——约 590 TFLOPS。**你可以拿任何昇腾白皮书里的峰值数字反推：用「2 × 4096 × 主频 × AI Core 数」这条链，看它是否对得上账。** 对不上时，往往是白皮书采用了不同的计数口径（比如是否含稀疏加速、是否按 FP16 而非 BF16 计）。

## 6 小结

- **AI Core 三单元**：Cube 司矩阵乘（16×16×16/周期）、Vector 司逐元素与规约、Scalar 司地址与流程控制。
- **分工依据是算术强度**：计算受限的算子归 Cube，内存受限的算子归 Vector。
- **三者并行配合**：取数（DMA/Scalar）、矩阵乘（Cube）、向量处理（Vector）形成软件流水，互相重叠。
- **单核吞吐公式** $\text{MACs/s}=a^2kf$
