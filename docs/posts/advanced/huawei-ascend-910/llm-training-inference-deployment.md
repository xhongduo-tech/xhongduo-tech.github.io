## 为什么从部署实践开始

这是本专题的收官之篇。前十九篇，我们从达芬奇架构一路走到 MindSpore，把「硅片 → 软件栈 → 框架」的每一层都摸了一遍。这一篇要把所有知识**串成一个端到端的故事**：一个真实的大模型，怎么在昇腾上完成「数据准备 → 训练 → 调优 → 推理部署 → 上线服务」的完整生命周期。它不引入新概念，而是**把前面学过的每一个知识点放到它「真实该出现的位置」**。<span class="marginnote">如果说前十九篇是「一个一个零件的图鉴」，这一篇就是「把这些零件装成一辆完整的车，再开一圈」——<strong>零件你都会认，但「装起来开起来」才是真正的考验</strong>。</span>

读完后，你应当能回答一个终极问题：**「在昇腾上部署一个大模型，到底要经过哪些步骤、每步会踩什么坑？」**

## 1 端到端总览：从数据到服务

一个昇腾大模型项目，通常走这样一条流水线：

| 阶段 | 主要工作 | 用到的昇腾能力 | 前几篇的对应 |
| --- | --- | --- | --- |
| 1. 数据准备 | 数据清洗、tokenize、样本打包 | CPU/存储为主，AI 卡预处理 | 第 11~12 篇（整机与 PCIe） |
| 2. 模型训练 | 预训练/微调，多卡并行 | MindSpore/PyTorch + CANN + HCCL | 第 14~19 篇 |
| 3. 调优与压缩 | 量化、剪枝、蒸馏 | CANN 推理优化、算子融合 | 第 15 篇 |
| 4. 推理部署 | 导出、加载、服务化 | MindSpore Lite / AscendCL | 第 16 篇 |
| 5. 上线服务 | 高并发、弹性、监控 | 推理服务框架 + 调度 | 第 13 篇 |

<span class="marginnote">这张流水线表是全专题的「索引」：<strong>每一格都能回指到前几篇的某个知识点</strong>。读这张表时，不妨试试「每格能不能说出对应的细节」——能说出来，说明前面学扎实了。</span>

这条流水线还有一个「反复迭代」的特性：它不是一次走完就结束，而是**训练 → 部署 → 反馈 → 再训练**的循环。推理阶段发现的问题（精度不够、延迟超标、某类请求效果差）会反馈回训练阶段，触发「继续预训练」「微调」「重新量化」等新一轮迭代。**真正的昇腾大模型项目，是一个「训练与推理互相喂养」的闭环**——理解这个闭环，就理解了为什么「懂训练」与「懂部署」必须同一个人或同一个团队。

## 2 训练阶段：把模型跑起来的「工程五问」

训练一个模型，不只是「把代码跑起来」，而是一连串工程决策。以昇腾为例，训练前要回答五个问题：

**第一问：用哪个框架？** 新项目追求性能与国产化 → MindSpore；存量代码依赖 PyTorch 生态 → PyTorch 适配。这一问直接决定后面所有工具链的选择。

**第二问：显存装得下吗？** 用第 7 篇的估算公式：模型大小 × 每参数字节（训练约 16）< 可用显存。装不下，就要选并行策略。

**第三问：选什么并行策略？** 模型放不下 → 张量并行（机内）+ 流水并行（机间）；数据量大 → 数据并行。三种并行按第 18 篇的方式混用，并「照顾」第 13 篇的物理拓扑。

**第四问：算子覆盖度够吗？** 用 MindSpore/PyTorch 跑一遍，检查热点算子是否落在算子库（第 19 篇）。覆盖不到的，决定是「组合实现」还是「手写 Ascend C」（第 16~17 篇）。

**第五问：性能达标吗？** 用 MFU 等指标验收（第 17 篇）：MFU 低，先查 tiling、双缓冲、通信重叠（第 3、4、18 篇）。<span class="marginnote">这「五问」是把前面十几篇的知识「压缩」成了一张训练启动检查清单——<strong>每一问背后，都站着前面某篇的一个「公式或原则」</strong>。写进自己项目里，就是一份可复用的昇腾训练 SOP。</span>

这五问的顺序也有讲究：**它是「先模型、后数据、再并行、再算子、最后性能」的自上而下排查**。模型定义错，后面全白费；显存放不下，并行白设计；算子覆盖差，性能白优化。按这个顺序走，每问在上一层「通过」后才进入下一层——**它既是一份检查清单，也是一张故障排除的决策树**。把五问背下来，就掌握了昇腾训练从零到一的全流程骨架。

## 3 推理阶段：从「训练卡」到「服务卡」

训练完的模型要上线服务，这一步与训练有本质区别：**训练追求吞吐，推理追求延迟与成本**。昇腾推理部署的关键步骤：

### 3.1 模型压缩：把「房子」变小

推理部署的第一步通常是**量化**：把模型从 BF16/FP16 压到 INT8/INT4。回顾第 5 篇：推理吞吐 ≈ 带宽 ÷ 模型大小，量化把「模型大小」变小，吞吐直接上升。昇腾支持训练后量化（PTQ）与量化感知训练（QAT），量化后的模型还能在推理引擎里继续做算子融合。<span class="marginnote">量化的「性价比」极高：<strong>INT8 把带宽需求砍半，INT4 砍到四分之一</strong>——对「带宽是命门」的推理，这是第一优先级的优化。但量化有精度代价，需要在「吞吐」与「精度」之间取平衡。</span>

量化的另一个好处常被忽略：**它同时缓解了「显存放不下」**。INT4 把 70B 模型的权重压到约 35 GB，配合 KV Cache 的优化，一张 128 GB 的 910C 就能装下并推理——这直接兑现了第 9 篇「70B 级模型单卡推理」的价值。「压缩」与「容量」是同一枚硬币的两面：**量化既让「喂得饱」变容易，也让「装得下」变容易**——对推理部署，它是双重收益。

### 3.2 推理引擎：让模型「跑得又快又稳」

昇腾的推理引擎（如 MindSpore Lite、vLLM 适配）负责把优化后的模型高效地跑起来。它要做的事包括：静态图优化（合并算子、固定 shape）、KV Cache 管理（第 5 篇）、批处理（多个请求合并成 batch，提高吞吐）、以及「预热」（第 14 篇：编译缓存在首次调用后生效）。

「静态图优化」与「动态 shape」是一对需要平衡的矛盾：固定 shape 能让编译器把优化做到极致（第 15 篇的 JIT 与缓存），但真实推理请求的长度多变。昇腾推理引擎的解法是「**按 shape 分组 + 分组内固定**」：把长度相近的请求归到一组，组内用固定 shape 执行，组间动态切换。这样既吃到「固定 shape 的编译优化」，又兼容「动态请求」——**「在动态世界里制造局部的静态」是推理引擎的经典思路**。

### 3.3 服务化：应对真实流量

上线服务还要考虑：**高并发**（多路请求同时进来，如何排队与批处理）、**弹性**（请求多了怎么扩，少了怎么缩）、**监控**（延迟、吞吐、错误率的可观测性）。这些已经超出「芯片」的范畴，进入「系统工程」——但它们决定了大模型服务「好不好用」。

「监控」还带来一个「反向优化」的机会：**生产数据是再训练的富矿**。真实用户的请求、反馈、失败样本，经过筛选与标注，可以回到训练阶段做「在线微调」——让模型越用越贴合业务。这就是前面说的「训练与推理互相喂养」闭环在数据层面的具体形态。**部署不只是「把模型放上去」，更是「让模型持续变好」的起点**——这是大模型服务与传统软件服务最本质的区别之一。

「批处理」值得单独强调，因为它直接把「芯片的带宽账」与「服务的吞吐账」接上了。自回归生成时，单个请求的 token 生成是串行的，GPU/昇腾的算力大量空闲；把多个请求拼成一个 batch，让它们「并行生成」，就能把算力与带宽同时填满。**「批处理因子 $b$」是推理成本公式里最灵活的旋钮**——$b$ 越大，每 token 摊薄的「读权重」越少，吞吐越高；但 $b$ 太大，单个请求的等待变长，延迟上升。**在「吞吐」与「延迟」之间找到服务等级协议（SLA）允许的最优 $b$，是推理服务工程师的核心手艺**。<span class="marginnote">这也解释了「为什么推理服务的 benchmark 要区分『吞吐』与『延迟』」：<strong>两者由同一个旋钮 $b$ 控制，鱼与熊掌不可兼得</strong>——理解这个权衡，比背任何 benchmark 数字都有用。</span>

## 4 公式解析：端到端的成本账

把整个生命周期「算一笔总账」，用一个端到端成本模型收束全专题。设：

- 训练：模型参数 $N$、训练 token 数 $T$、每 token 每参数训练 FLOPs 约 $6$，集群有效算力 $P_{\text{cluster}}$，则训练时间为：

$$T_{\text{train}} \approx \frac{6 \times N \times T}{P_{\text{cluster}}}$$

- 推理：模型大小 $Np$ 字节（$p$ 为每参数字节）、单卡带宽 $\text{BW}$、批量因子 $b$，则单卡吞吐上限为：

$$\text{tokens/s} \approx \frac{\text{BW} \times b}{N \times p}$$

逐项拆解：

- **第一步，$6NT/P_{\text{cluster}}$**：训练一个 $N$ 参数模型、$T$ 个 token，约需 $6NT$ FLOPs（前向+反向）。除以集群有效算力，得训练时间。**$P_{\text{cluster}}$ 用「有效算力」而非峰值**——因为利用率与通信效率（第 13、18 篇）都折算进去了。
- **第二步，$\text{BW}\times b / (Np)$**：推理每 token 要读一遍权重 $Np$ 字节，带宽除以它就是吞吐上限。$b$（批处理因子）把多个请求合并，摊薄「每 token 读权重」的开销。
- **第三步，两条公式合起来看**：**训练是「算力问题」**（$P_{\text{cluster}}$ 越大越好），**推理是「带宽问题」**（$\text{BW}$ 与 $p$ 决定上限）。同一个昇腾平台，训练要堆算力、推理要压带宽需求——这正是前五篇「算力—带宽」三角在本篇的最终兑现。

代入一组量级感受：$N=70$B、$T=1$T token、$P_{\text{cluster}}=10$ PFLOPS（约 25 张 910C 的有效算力），$T_{\text{train}}\approx 6\times7\times10^{10}\times10^{12}/10^{16}=4.2\times10^7$ 秒 ≈ 486 天——**这解释了为什么大模型训练要以「集群 + 并行」为常态，也解释了为什么「有效算力」比「纸面算力」重要**。<span class="marginnote">这两条公式是全专题的「期末考试题」：<strong>能写出它们、解释每一项、并且用真实量级代入算出感觉</strong>——就是「从极限到大模型」这一路最扎实的收尾。</span>

再看推理侧的量级。70B 模型 INT8（$p=1$）、单卡 $\text{BW}\approx1.6$ TB/s、$b=8$，则单卡吞吐约为 $1.6\times10^{12}\times8/(7\times10^{10}\times1)\approx 183$ tokens/s——**一次量化 + 8 路批处理，把第 5 篇「单卡每秒 11 个 token」的朴素值拉高了 16 倍**。这就是为什么「压缩 + 批处理」是推理部署的黄金组合：它们不改变芯片，却成倍放大了芯片的产出。**「同样的硬件，不同的软件，差出一个数量级的服务能力」**——这句总结，正是整个昇腾软件栈（CANN、编译器、框架、引擎）存在的全部意义。

## 5 小结

- **端到端流水线**：数据准备 → 模型训练 → 调优压缩 → 推理部署 → 上线服务。
- **训练前工程五问**：框架选择、显存估算、并行策略、算子覆盖度、性能验收。
- **训练是算力问题，推理是带宽问题**：同一平台两种优化重心。
- **推理关键动作**：量化压缩（INT8/INT4）、静态图优化、KV Cache 管理、批处理、预热。
- **成本账公式**：训练 $6NT/P_{\text{cluster}}$，推理 $\text{BW}\times b/(Np)$——全专题知识的收束。
- **零件你都会认，装起来开起来才是考验**——学完不是终点，跑起来才是。
- **五问的顺序是自上而下的决策树**：模型 → 显存 → 并行 → 算子 → 性能。
- **批处理因子 $b$ 是推理成本公式里最灵活的旋钮**：$b$ 越大每 token 摊薄的读权重越少，但单请求延迟上升，要在 SLA 允许内取最优。
- **量化既让「喂得饱」变容易，也让「装得下」变容易**：压缩与容量是同一枚硬币的两面，双重收益。
- **「在动态世界里制造局部的静态」**：按 shape 分组 + 分组内固定，既吃编译优化又兼容动态请求。
- **部署是「让模型持续变好」的起点**：生产数据经筛选回填训练，训练与推理互相喂养的闭环。

- **端到端流水线的「反复迭代」特性**：训练 → 部署 → 反馈 → 再训练，训练与推理互相喂养的闭环。
- **训练成本公式的启示**：70B 模型、1T token、10 PFLOPS 集群要训约 486 天——这解释了为什么大模型训练以「集群 + 并行」为常态。
- **推理黄金组合「压缩 + 批处理」**：一次 INT8 量化 + 8 路批处理，把单卡每秒 11 token 的朴素值拉高 16 倍。
- **「监控」是反向优化的富矿**：生产数据经筛选标注回到训练阶段做在线微调，让模型越用越贴合业务。
- **SLA 是批处理因子 $b$ 的边界**：在吞吐与延迟之间找到服务等级协议允许的最优 $b$，是推理服务工程师的核心手艺。
- **「同样的硬件，不同的软件，差出一个数量级的服务能力」**——这就是 CANN、编译器、框架、引擎存在的全部意义。

到这里，本专题二十篇全部走完：从达芬奇架构的硅片，到 CANN 软件栈、再到端到端部署实践，昇腾计算平台「从硅片到算力服务」的完整链路已经收束。你学到的不是一堆型号参数，而是一套能迁移到任何 AI 芯片的思考框架——算力—带宽—显存的三角、算术强度的判据、数据流与编译期调度的方法论。带着这套框架去面对任何一张新芯片参数表，你都能像读体检报告一样读懂它、评判它、用好它。
