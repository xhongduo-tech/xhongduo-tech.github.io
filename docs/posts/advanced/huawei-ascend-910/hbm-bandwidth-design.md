## 为什么从 HBM 开始

前四篇我们一直待在芯片「里面」：算力、流水线、缓存。但大模型的体积早就超出了任何片上缓存——一个 70B 参数的模型，仅权重就要 140 GB（BF16）。这些权重住在哪？住在 **HBM**。训练时每个 token 都要把所有权重读一遍，推理时每生成一个 token 也要把全部权重过一遍——**因此大模型的性能天花板，很多时候不是算力，而是「权重能不能及时喂给算力单元」**。这一篇把 HBM 讲透：它为什么能提供 TB/s 级带宽、昇腾各代怎么配 HBM、以及「带宽是命门」这句判断背后的算术。

在进入技术细节前，先把「带宽焦虑」的来龙去脉讲清楚。人工智能的算力需求由深度学习驱动的这十年里，芯片计算单元（乘法器）的面积和速度都在稳步提升，**但内存的访问速度远远跟不上**——这一现象被称为「内存墙」（memory wall）。对通用处理器，内存墙意味着 CPU 等数据；对 AI 芯片，内存墙意味着**算力再高，数据喂不上来也是空转**。HBM 正是为翻越内存墙而生的技术：它把内存「立」起来堆叠、把通路「拓宽」，在面积与功耗都可接受的前提下，把带宽拉高了一个数量级。理解 HBM，就是理解 AI 硬件如何与内存墙正面交手。

## 1 HBM 是什么：3D 堆叠的内存革命

**HBM（High Bandwidth Memory，高带宽内存）**：一种将多层 DRAM 芯片通过硅通孔（TSV）垂直堆叠、再与逻辑 die 封装在一起的内存技术，以「超高位宽 + 中低时钟」实现远超普通 DDR/GDDR 的带宽。

要理解 HBM，先看传统内存怎么给带宽。内存带宽公式为：

$$\text{BW} = \text{clock} \times \text{bit width} \times \text{transfer rate per clock}$$

普通 DDR 内存位宽通常是 64 bit，想提高带宽只有拉高时钟。而 HBM 换了一条路：**把位宽做到极致**。

这条带宽公式还揭示了一个简单的推论：**带宽 = 位宽 × 时钟，两条路都能走**。GDDR 选了「高时钟 × 中位宽」，HBM 选了「中低时钟 × 超高位宽」。为什么 HBM 不把时钟也拉高？因为高时钟意味着高功耗、强信号串扰，而 HBM 的「超高位宽 + 3D 堆叠」已经在功耗预算内给出了足够的带宽——**这是功耗约束下的理性选择，而不是技术上的退让**。一颗 HBM 堆叠（stack）内部有多个通道（channel），每个通道几百 bit 位宽，一个 stack 的总位宽可达 1024 bit（即 1 Kbit）；通过多个 stack 并行，总位宽可以到数千 bit。<span class="marginnote">HBM 的堆叠结构：底层是逻辑 die（负责接口与控制器），上面叠着若干层 DRAM die，die 之间用数千根 TSV 垂直打穿连接。TSV 短而密，信号传播快，这是「宽而不慢」的物理基础。</span>

于是 HBM 用「**很宽的马路、开不快但车很多**」的方式，把总带宽堆到了 TB/s：例如 HBM2E 的单个 stack 带宽约 460 GB/s，用 3~4 个 stack 就能到 1.6~1.8 TB/s；HBM3 单 stack 更高，配合多 stack 能到 3.7 TB/s 甚至更高。昇腾 910B 与 910C 的带宽差异，主要就来自 HBM 代数与 stack 数量的升级。

### HBM 的代际演进：每一次都「更宽」

HBM 的代际数字（HBM2E、HBM3、HBM4）背后是一条清晰的演进主线：**单 stack 容量与带宽同步增长，同时把「每比特功耗」降下来**。HBM2E 的单 stack 容量约 16 GB、带宽约 460 GB/s；HBM3 把单 stack 容量推到 24 GB、带宽提到约 800 GB/s 以上；HBM3E 更进一步。对 AI 芯片而言，换用新一代 HBM 等于同时获得「更大的房子」和「更宽的门」——这正是昇腾 910 到 910C 显存与带宽双双翻倍的根本来源。<span class="marginnote">HBM 的代际升级并不只发生在颗粒层面，还涉及<strong>封装基板的布线密度、热管理方案、以及与计算 die 的互连方式</strong>。换一代 HBM 往往意味着整套先进封装方案重做——这也是为什么「用第几代 HBM」会成为芯片发布会上的焦点话题。</span>

值得注意的是，HBM 的「宽」不是免费的：超高位宽意味着**成千上万条并行走线**，对封装与良率是巨大考验；3D 堆叠也带来了散热难题——DRAM 层叠在一起，热量更难散出。因此 HBM 总是与「先进封装」绑定出现。**你看到的每个 TB/s 数字背后，都站着一整条先进封装的工艺链**。

还有一个工程现实是**带宽的「保持率」**：芯片在满载、高温下运行，HBM 可能因热降频而达不到纸面带宽。因此白皮书里的「峰值带宽」是理想值，真实场景要看「可持续带宽」——通常打个七到八折。昇腾的性能测试报告、以及用户自测时，都会强调「用真实负载测带宽，而不是读参数表」。**参数表给的是上限，真实系统给的是下限，工程师活在下限与上限之间**。

## 2 昇腾各代的 HBM 配置

| 型号 | HBM 代数 | 容量 | 片内带宽量级 | 说明 |
| --- | --- | --- | --- | --- |
| 昇腾 910 | HBM2E | 32 GB | ~1.2 TB/s | 初代，训练/推理通用 |
| 昇腾 910B（B3 等） | HBM2E | 64 GB | ~1.6 TB/s | 主流训练卡，显存翻倍 |
| 昇腾 910C | HBM3 | 128 GB | ~3.7 TB/s | 双 die 封装，显存与带宽翻倍 |
| 昇腾 950 | HBM 新一代 | 预计更大 | 预计继续提升 | 尚处发布期，以官方白皮书为准 |

<span class="marginnote">表中 910C 与 950 的具体数字以官方白皮书为准——<strong>昇腾的公开规格常常以「报性能区间」而非「报精确值」的方式呈现</strong>。比起背数字，更该掌握的是「容量、带宽、算力三者如何互相锁定」的规律，这正是第 4 节要算的账。</span>

**辨析｜易错点：** 别把「显存容量」和「带宽」混为一谈。容量决定「能装多大模型」，带宽决定「每秒能喂给算力多少数据」。一台 128 GB 显存的卡装得下 70B 模型，但如果带宽只有 500 GB/s，每个 token 读一遍权重就要 140 GB ÷ 0.5 TB/s ≈ 280 ms——每秒只能生成 3 个 token。**容量是「房子」，带宽是「门」：门不够宽，房子再大也吞吐不起来。**

### 910C 的双 die 与 HBM 排布

昇腾 910C 的 HBM 故事尤其值得单独说：910C 采用**双 die 封装**，即把两颗计算 die 放进同一颗封装，每颗 die 各自连接自己的 HBM stack。这种布局让 910C 的显存与带宽几乎是 910B 的两倍——但它也引入了一个新问题：**die 与 die 之间的数据流动（跨 die 访存）比 die 内访存慢得多**。于是软件需要「感知 die 拓扑」：尽量让数据在同一个 die 的 HBM 里被消费，减少跨 die 访问。**「显存翻倍」是硬件给的，「用不用得好」是软件的事**——这再次呼应昇腾「显式数据流」的哲学。<span class="marginnote">关于 910C 双 die 的完整拆解，见《昇腾 910C：双 die 封装与超大显存》一篇。这里只需记住：<strong>大显存的代价是内存访问有了「本 die」与「跨 die」之分</strong>。</span>

## 3 为什么大模型是「带宽敏感」的

训练与推理对带宽的依赖分两种形态：

**训练侧（权重 + 梯度全部流动）**：一次前向要把权重读一遍，反向要再把权重读一遍、梯度写一遍；多卡并行还叠加集合通信。每一步的搬运量 ≈ 数倍模型大小，因此训练步时间高度受带宽约束。

**推理侧（权重只读、逐 token 流动）**：自回归生成时，每生成一个 token，需要把全部权重从 HBM 读入计算单元一次。设模型参数量为 $N$、精度为 $p$ 字节，则每 token 至少读 $Np$ 字节，理论上限为：

$$\text{tokens/s} \leq \frac{\text{BW}}{N \cdot p}$$

这正是「**推理吞吐 ≈ 带宽 ÷ 模型大小**」这条经验的来源。<span class="marginnote">对 70B 模型、BF16（$p=2$）、1.6 TB/s：$\text{tokens/s}\approx 1.6\times10^{12}/(70\times10^{9}\times2)\approx 11$。单卡每秒约 11 个 token——这解释了为什么服务大模型要靠多卡并行、量化（把 $p$ 变小）与 KV Cache 复用（减少重复搬运）。</span>

「权重只读」这个前提有个重要推论：推理时权重可以被**常驻**在高带宽区域甚至被多个请求共享，而真正「流式」的只有每次生成的激活与 KV Cache。于是推理优化的方向非常明确——**把权重读得越少、越快越好**：量化把 $p$ 从 2（BF16）压到 1（INT8）甚至 0.5（INT4），等于把「每 token 读权重」的字节砍半甚至砍到四分之一。这也是为什么昇腾推理卡总是把「支持 INT8/INT4」当作卖点——**它直接买在推理的命门上**。

另一条减负路径是**KV Cache 复用**。生成阶段除了读权重，还要读写不断增长的 KV Cache；上下文越长，KV Cache 越大，对带宽的占用越多。工程师们用「前缀共享」（多个请求共用同一段系统提示词的 KV）、「分页 KV Cache」（按页分配、只搬需要的部分）等技巧，把这条负担降下来。**推理优化的本质，就是一场「减少每 token 搬运字节数」的军备竞赛**——谁把「每 token 的搬运量」压得最低，谁就能在同样的带宽下服务最多的用户。这条主线会在《大模型训练与推理部署实践》里以系统架构的形式重现。

## 4 公式解析：算力-带宽平衡点

把「带宽是命门」这句话精确化。设峰值算力 $P$（FLOP/s）、带宽 $\text{BW}$（byte/s），芯片的**平衡点算术强度**为：

$$I_* = \frac{P}{\text{BW}} \qquad (\text{单位：FLOP/byte})$$

代入昇腾 910B：$P\approx 3.8\times10^{14}$ FLOP/s（BF16），$\text{BW}\approx1.6\times10^{12}$ byte/s，得 $I_*\approx 238$ FLOP/byte。

用实际算子对号入座。一个 $8192\times8192$ 的矩阵乘（相当于大模型里常见的超大 GEMM），$I\approx 2048$ FLOP/byte，落在 $I_*$ 之上——**计算受限，Cube 能跑满**。而一个对同样大小张量的逐元素 GELU，$I\approx 0.5$ FLOP/byte，远低于 $I_*$——**内存受限，算力大面积空转**。同一个芯片，两种算子，一个天堂一个地狱。这正是「为什么算子融合那么重要」的最根本证据：**把两个低 $I$ 的算子融合成一个高 $I$ 的算子，等于把一个内存受限场景改造成计算受限场景**。

拆解其含义：

- **第一步，$I_*$ 是什么**：芯片想要「算满」，每个字节必须支撑 $I_*$ 次计算。如果一个算子每字节只产生 $I \lt  I_*$ 次计算，则它「算得太少、搬得太多」，芯片被带宽卡住——这时再堆算力也白搭。
- **第二步，看趋势**：摩尔定律放缓后，算力（FLOP/s）与带宽（byte/s）的增速开始脱节——算力涨得快，带宽涨得慢，于是 $I_*$ 逐年攀升。这对架构设计的含义是：**未来芯片的瓶颈必然越来越向带宽靠拢**。
- **第三步，昇腾的应对**：提高带宽（上 HBM3/HBM4）、把数据留在片上（L0~L2 复用、算子融合）、以及降低精度 $p$（BF16、FP8、INT8 量化）——三管齐下，把「每字节的算力消耗」降下来，让实际算子在平衡点之上运行。

由此得出一个贯穿本专题的判断：**昇腾（以及所有 AI 芯片）的性能故事，一半写在算力表里，一半写在带宽表里**。看一张白皮书，先问「$I_*$ 是多少、主力算子能不能跑在它之上」，再谈峰值 TFLOPS。

用一个对比感受「带宽墙」的紧迫。假设算力每年增长 2.5 倍、带宽每年增长 1.5 倍，那么平衡点 $I_*$ 每年膨胀约 1.67 倍。三五年后，$I_*$ 就会从「几百 FLOP/byte」涨到「几千 FLOP/byte」——**这意味着越来越多原本「计算受限」的算子，会随着算力跑赢带宽而滑向「内存受限」**。架构师能做的只有两件事：要么把带宽追上去（用新一代 HBM），要么把每字节的算力消耗降下来（低精度、稀疏、算子融合）。昇腾把这两条路都走了，但理解这份「跑不赢的焦虑」，才能真正看懂昇腾为什么如此执着于片上复用与低精度支持。

## 5 从 HBM 到集群：带宽焦虑的扩散

单卡带宽只是第一层。当模型大到单卡装不下，数据开始跨越芯片边界流动——这时「带宽」从 HBM 扩散到**片间互联（如 RoCE、HCCS）与机间网络**。昇腾 910C 的双 die 封装、超节点集群的高速互联，本质上都是在回答同一个问题：**数据搬不动时，怎么让搬动更快**。<span class="marginnote">多卡并行（张量并行、流水并行）对互联带宽的要求极高：张量并行每步都做 all-reduce，通信量近似等于每层的激活量；互联带宽不足，并行效率会直线下滑。这是《HCCL 集合通信与多卡并行》与《超节点集群与机间互联拓扑》的主线。</span>

这里出现了一个容易混淆的概念对：**内存带宽（HBM 带宽）与互联带宽（片间/机间带宽）**。前者是「单颗芯片从自己肚子里取数据的速度」，后者是「数据从一颗芯片搬到另一颗芯片的速度」。对单卡推理，命门是内存带宽；对多卡训练，命门常常变成互联带宽。一张卡再能算，若数据在卡与卡之间挪不动，集群整体效率照样上不去——**「卡内看 HBM，卡间看互联」，是两个不同量级的带宽问题，优化手段也完全不同**。<span class="marginnote">一个常用经验值：张量并行要求片间带宽至少达到单卡内存带宽的几分之一，否则通信会成为新的墙。这也是为什么昇腾超节点要用专用高速互联（而非普通以太网）把卡连在一起——<strong>网卡带宽和内存带宽不是一个量级，不能混为一谈</strong>。</span>

## 6 小结

- **HBM 用 3D 堆叠 + 超高位宽**把带宽推到 TB/s 级，与 GDDR/DDR 的「高时钟」路线截然不同。
- 昇腾代际升级的核心之一就是 HBM：910B（64 GB HBM2E，~1.6 TB/s）→ 910C（128 GB HBM3，~3.7 TB/s）。
- **容量是「房子」，带宽是「门」**：大模型推理吞吐 ≈ 带宽 ÷ 模型大小。
- 平衡点算术强度 $I_*=P/\text{BW}$：算力与带宽的增速脱节，使带宽成为越来越紧的瓶颈。
- 昇腾的三大对策：**上代际 HBM、片上复用与融合、低精度量化**。
- **内存墙**是带宽焦虑的总根源；HBM 用「更宽的马路 + 3D 堆叠」正面翻越它。
- **910C 双 die**让显存带宽翻倍，但引入「本 die/跨 die」访存差异，软件必须感知拓扑。
- **卡内看 HBM，卡间看互联**：两个量级的带宽问题，优化手段完全不同。
- **KV Cache 复用 + 低精度量化**是推理减负的两大路径：本质都是减少「每 token 搬运字节数」。
- **峰值带宽 ≠ 可持续带宽**：热降频与满载会让纸面数字打七到八折，测真实负载为准。
- **带宽公式** $\text{BW}=\text{clock}\times\text{width}$：HBM 走「超高位宽 × 中低时钟」，是功耗约束下的理性选择。
- **算子融合的本质**：把低 $I$ 算子合成高 $I$ 算子，等于把内存受限场景改造成计算受限场景。
- **平衡点 $I_*$ 逐年攀升**：算力涨得快、带宽涨得慢，未来瓶颈必然越来越向带宽靠拢。
- **「容量是房子，带宽是门」**：推理吞吐 ≈ 带宽 ÷ 模型大小，量化与 KV Cache 复用是减负双路径。
- **峰值带宽 ≠ 可持续带宽**：热降频让纸面数字打七到八折，测真实负载为准。

在下一节，我们将把昇腾与 GPU 并排对比，看同一道题两种架构如何给出不同的答案——**昇腾与 GPU 的架构设计哲学对比**。
