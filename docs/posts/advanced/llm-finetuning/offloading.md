## 为什么从卸载开始

并行把显存摊到了多张卡，但总有那么些场景连「多卡」都没有——一张 24GB 的消费卡，想微调 7B 模型。此时优化器状态 56 GB、梯度 14 GB 根本进不了显存。怎么办？答案是**卸载（offload）**：把这些状态搬到 GPU 之外的存储——**CPU 内存（DRAM）或 NVMe 固态盘**——用的时候再搬回来。

卸载是显存优化的「最后一招」：它几乎不改善速度（甚至显著变慢），唯一的价值是**让「显存不够」变成「显存够」**。理解卸载，你就能判断「单卡到底能不能训」「该卸载什么、往哪卸」，而不被各种 offload 开关弄昏头。本节先看「内存金字塔」决定往哪卸，再用一条时间账量化卸载的代价，最后落到分页优化器与选型表。<span class="marginnote">一句话定位：<strong>并行是「把东西摊到更多卡」，卸载是「把东西搬到更便宜的地方」</strong>。前者不牺牲速度（甚至更快），后者为了容量牺牲速度——所以卸载是「最后的防线」，不是默认选择。</span>

## 1 卸载什么、往哪卸：内存金字塔

「往哪卸」取决于你的存储有多便宜、多慢。现代训练机器的存储是分层的，每一层容量更大、带宽更慢：

| 层级 | 典型容量 | 带宽量级 | 相对速度 |
| --- | --- | --- | --- |
| GPU HBM | 24–80 GB | 2–3 TB/s | 1× |
| CPU DRAM | 数百 GB | 50–100 GB/s | 1/30× |
| NVMe SSD | 数 TB | 3–7 GB/s | 1/500× |

**卸载的顺序遵循「先卸最不常用的」**：

1. **优化器状态**（最占、更新频率低）——第一个搬去 CPU；
2. **梯度**（算完即用）——也可搬去 CPU；
3. **参数**（每步前向反向都要用）——搬去 CPU 就变成「CPU 训练」，速度暴跌；
4. **激活值**——一般留在 GPU（重计算更划算）。

ZeRO-Infinity 提出的分层卸载正是沿这个顺序：显存先放不下就卸优化器到 CPU，CPU 还不够就卸到 NVMe。每往下卸一层，容量扩大、速度变慢——「能装下就行，尽量留在快的层级」。

这张「存储金字塔」也是理解整篇显存优化的总地图：混合精度在 GPU 层内做文章，并行在「多卡」维度做文章，卸载在「跨层」维度做文章——所有优化技术都在回答同一句话：**状态放在哪一层最划算**。

<p></p>

注意一个反直觉点：**卸载优化器状态到 CPU 只影响「更新那一下」，不影响前向反向主体**。因为前向反向用的是参数（在 GPU），优化器状态只在每步更新时被用到。这解释了为什么「只卸优化器」是性价比最高的卸载——它把最重的 56 GB 挪走，却只让每步多一次「梯度→CPU、状态→GPU」的搬运。

## 2 公式解析：卸载的时间账——PCIe 带宽是硬约束

卸载最容易被低估的是**搬运时间**。GPU 与 CPU 之间的通道是 PCIe，4.0 ×16 的理论带宽约 32 GB/s——比 GPU 显存带宽慢两个数量级。算一笔账：

$$
t_{\text{transfer}} = \frac{\text{优化器状态字节数}}{\text{PCIe 带宽}} = \frac{12B_{\text{params}}}{32\ \text{GB/s}} = \frac{56\ \text{GB}}{32\ \text{GB/s}} \approx 1.75\ \text{秒}
$$

对 7B 模型，每步要把 56 GB 的优化器状态在 GPU 与 CPU 之间来回搬一次，**单是搬运就要近 2 秒**。而正常的训练一步（前向 + 反向 + 更新）通常不到 1 秒——于是卸载让每步时间翻了数倍。

逐项拆解这条时间账：

- $12B_{\text{params}}$：优化器状态 = FP32 主权重 + 两个动量 = 每参数 12 字节；
- 分子换成梯度（$2B_{\text{params}}$）时，搬运只要约 0.3 秒——所以**卸梯度比卸优化器便宜**，但省下的显存也少；
- **结论**：卸载省显存的代价是「每步多花 1–3 秒的搬运」，且搬运量与参数量成正比——模型越大越慢。

这条账给出三条实践推论：其一，**卸载只能「够用」，别指望「快」**；其二，**卸载配合小 batch / 小学习率能减少每步有效开销**（更新频率不变，但每步的计算更少）；其三，**NVMe 卸载只在「CPU 内存也不够」时才值得**——它比 CPU 又慢一个数量级，是真正的最后手段。<span class="marginnote">工程上常把卸载与「每步搬运一次」解耦：梯度累积可以攒几步再统一搬运，摊薄通信开销。DeepSpeed 的 offload 配置里专门有优化这类调度的选项——调它比纠结「卸多少」更能提升实际吞吐。</span>

## 3 分页优化器：QLoRA 的「防尖峰」设计

卸载之外，还有一个轻量得多的技巧值得单独讲——**分页优化器（paged optimizer）**，它来自 QLoRA 论文（Dettmers et al., 2023）。

**它解决的问题**：即使显存「理论够用」，AdamW 更新时优化器状态会瞬时顶起一个尖峰——比如一次性把所有参数的动量张量从 CPU 拷回 GPU 更新，显存瞬间爆掉，训练 OOM 崩溃。这种「够用但不稳」是单卡微调最磨人的问题。

**它的做法**：利用 CUDA 的统一虚拟内存（Unified Memory）分页机制，把优化器状态放进 CPU 内存，但**由系统按需分页换入换出**——GPU 需要哪一页就自动调入，用完自动换出。程序不用手动管理搬运，系统像管理虚拟内存一样管理这些状态。

**它的本质**：不是省显存，而是**把「显存尖峰」平滑掉**。状态总量没变，但不再需要一次性全量驻留——尖峰时刻多出来的几 GB，由分页机制临时「借」到 CPU。对 QLoRA 这种「显存预算紧巴巴」的训练，分页优化器是防止 OOM 崩溃的关键一环。<span class="marginnote">用一句话区分三者：<strong>CPU offload 是「主动搬家」，NVMe offload 是「搬到更远的地方」，分页优化器是「让系统自动搬家」</strong>。QLoRA 里优化器状态本就放 CPU（因为 4-bit 基座省下的显存仍不够），分页优化器再给这套方案加了「防尖峰」保险。</span>

## 4 工程实践：什么时候卸载、怎么配

判断「该不该卸载」有一条简单准则：**先做显存账本（第一篇），确认「缺多少」**。

只差优化器状态（如单卡 48GB 训 7B 全参）→ **CPU offload 优化器状态**：DeepSpeed 的 `offload_optimizer`（`device: cpu`），或 HF Trainer 的 `fsdp_offload_params` 配置；
连参数都放不下（单卡 24GB 训 7B 全参）→ **全量 offload（参数+梯度+优化器）**，但速度极慢，通常不如直接上 PEFT；
CPU 内存也不够（几十 B 模型）→ **NVMe offload**（ZeRO-Infinity），最后的最后手段；
单卡跑 QLoRA/LoRA 且频繁 OOM → **分页优化器**（`paged_adamw_32bit` / `paged_adamw_8bit`），几乎零成本地防崩溃。

一段 DeepSpeed 的 CPU offload 配置示意：

```yaml
# ds_config.json：把优化器状态卸载到 CPU（ZeRO-2 即可）
zero_optimization:
  stage: 2
  offload_optimizer:
    device: cpu
    pin_memory: true
  offload_param:
    device: none
```

配 offload 时记住：**`pin_memory` 开启**、**梯度累积减少搬运次数**、**batch 别贪大**（显存本来就不够）。卸载是「带着镣铐跳舞」的方案，把镣铐调轻，比幻想解开镣铐更实际。<span class="marginnote">再提醒一次卸载与 PEFT 的关系：对绝大多数「显存不够」的场景，<strong>先想 LoRA/QLoRA（第四篇），再想 offload</strong>——PEFT 从根上减小状态量（从 16 字节/参数降到约 1 字节/参数），而 offload 只是把状态搬远。两者可叠加，但顺序不要搞反。</span>

把三种卸载策略并排对照，选型就清楚了：

| 策略 | 卸载对象 | 每步开销 | 适用场景 | 典型工具 |
| --- | --- | --- | --- | --- |
| CPU offload（优化器） | 优化器状态 → CPU | 约 1–3 秒搬运 | 显存差一档，能接受慢 | DeepSpeed `offload_optimizer` |
| CPU offload（全量） | 参数+梯度+优化器 → CPU | 显著变慢（数倍） | 单卡勉强能跑，验证为主 | ZeRO-3 offload |
| NVMe offload | 一切 → NVMe | 极慢（>10×） | CPU 内存也不够的超大模型 | ZeRO-Infinity |
| 分页优化器 | 状态由系统按需换页 | 几乎无感知 | 显存紧、防 OOM 尖峰 | bitsandbytes `PagedAdamW` |

注意「CPU offload（优化器）」与「分页优化器」的差别：前者是**主动把优化器状态常驻 CPU**（彻底腾出显存），后者是**状态在 CPU、按需换页进 GPU**（防尖峰但不保证腾空间）。前者为「腾显存」，后者为「防崩溃」，目标不同、可叠加使用。

## 5 小结

- **卸载是把状态搬到 GPU 之外**（CPU 内存 → NVMe），牺牲速度换容量，是显存的「最后防线」。
- 卸载顺序：**优化器状态 → 梯度 → 参数**；「只卸优化器」性价比最高，因为前向反向主体仍在 GPU。
- 时间账：7B 优化器状态搬运约 1.75 秒/步（PCIe 32 GB/s），卸载显著变慢——**只求够用，别求快**。
- **分页优化器**用统一虚拟内存平滑显存尖峰，不省总量但防 OOM，是 QLoRA 的标配。
- 判断顺序：**先算账本 → 缺优化器用 CPU offload → 缺参数上 PEFT → 都缺才考虑 NVMe**；分页优化器几乎零成本可常开。
- 卸载与并行可叠加：ZeRO-3 + CPU offload 是最常见的「分片 + 搬远」组合，容量弹性最大。
- 判断口诀：**「显存差一档 → 优化器 offload；差很多 → PEFT；彻底不够 → NVMe」**——先算账本再选路。
