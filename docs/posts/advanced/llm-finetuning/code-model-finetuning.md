## 为什么从代码微调开始

代码是与数学并列的「第二可验证领域」——而它的数据比数学丰富得多：GitHub 上数十亿行开源代码，天然是训练语料。**代码模型微调**（CodeLlama、StarCoder、CodeGemma 等）因此成了领域微调里「数据最充足、验证最自动」的一员。

代码微调有两个标志性的技术点：一是**数据配方**（GitHub 语料的清洗、去重与配比），二是 **Fill-in-the-Middle（FIM，中间填充）**——它把「续写」训练扩展成「填空」训练，让模型不仅会「接着写」，还会「补中间的洞」。理解代码微调，你就理解了「可验证领域 + 海量数据」这条微调路线的最佳实践。<span class="marginnote">代码微调还有一个「战略意义」：<strong>代码是 RLVR（可验证奖励强化学习）的完美训练场</strong>——每个函数都能跑单元测试，正确性可以自动判定。代码模型因此成了「RLVR 技术」最早的受益者与验证者（对应第六篇《RLVR》）。</span>

## 1 代码微调的特殊性：数据丰富、可自动验证

代码领域有三张「好牌」，是其他领域羡慕不来的：

**① 数据极其丰富**。GitHub 开源代码、Stack Overflow、代码竞赛题——动辄数十亿文件。数据量不再是瓶颈，**瓶颈转移到「数据质量」**（哪些代码值得学）。

**② 可以自动验证**。代码的正确性有「客观裁判」——单元测试。这让代码模型的**评测与强化学习都变得「机器可判」**：写对没写对，跑一下就知道。

**③ 结构性强**。代码有明确的语法、缩进、函数边界——比自然语言更「规整」，模型更容易学到「结构化的生成模式」。

但代码也有独特的难点：**代码是「填空式」的**——开发者在函数中间插入一段逻辑、在已有函数间补一个新函数，而不是「从头续写」到底。普通 LM 的「左到右续写」训练，并不直接对应这个「中间插入」的使用场景——这正是 FIM 要解决的问题。

## 2 数据配方：GitHub 语料的清洗与配比

代码模型的数据配方（以 StarCoder 的 The Stack、CodeLlama 的配方为代表）有几个关键步骤：

**① 清洗与去重**：GitHub 语料噪声大——要按扩展名过滤（只要代码文件）、按大小过滤（去掉超长/超短）、按「代码比例」过滤（去掉注释占绝大多数的文件）。**去重是重点**：GitHub 上有海量「复制粘贴」的仓库，不去重会让模型在「重复代码」上过拟合。

**② 许可证过滤**：开源代码有不同许可证（MIT、Apache、GPL 等）——**合规的许可证筛选**是代码语料的前置（GPL 代码的使用有法律限制）。StarCoder 为此专门做了许可证审计。

**③ 配比：代码 + 自然语言**。纯代码训练会让模型「只会写代码、不会说话」——所以配方里要混入自然语言（注释、文档、GitHub issue），让模型同时保持「自然语言理解」能力。经验配比：**代码为主（约 60%–80%），自然语言打底（20%–40%）**——与领域微调方法论里的「领域 + 通用」配比同构。

**④ 语言平衡**：GitHub 上 Python、JavaScript 占大头，但小语言（Rust、Go）也要保有一定比例——**避免「只会热门语言」**。

## 3 Fill-in-the-Middle：从「续写」到「填空」

**FIM（Fill-in-the-Middle，中间填充）** 是代码模型微调最标志性的技术。普通 LM 训练只做「左到右预测下一个 token」；FIM 额外训练「**给定前缀和后缀，预测中间的代码**」。

它的动机是使用场景：开发者在代码里「补一个函数」「填一个条件分支」「修一段逻辑」——这些都不是「接着写」，而是「**在已知开头和结尾之间补全**」。IDE 的代码补全、模型的条件生成，本质都是 FIM。

**FIM 的训练方式**：在训练时，随机把一部分样本改造成「前缀 + 后缀」的形式，让模型预测被「挖掉」的中间部分：

```text
普通样本：  def f(x):       <-- 从左到右续写
FIM 样本：  def f(x): <FILL> return x*2   <-- 预测 <FILL> 处的内容
```

**FIM 的两种变形**（前缀-后缀的摆放顺序）：

- **PSM（Prefix-Suffix-Middle）**：`[前缀, 后缀, <FILL>, 中间]`——先给前缀后缀，再要求补中间；
- **SPM（Suffix-Prefix-Middle）**：`[后缀, 前缀, <FILL>, 中间]`——后缀在前。

两者的差异影响模型对「先看到什么」的偏重——实践中常混合使用（如 CodeLlama 用了 PSM 与 SPM 的变体）。<span class="marginnote">FIM 的「特殊 token」设计是细节关键：<strong>`<FILL>` 必须是一个词表里独占的特殊 token</strong>——模型要能识别「这里该补内容」。这与对话模板的「角色 token」是同一类设计（第二篇《对话模板》），原理互通：给模型一个「可学习的占位标记」。</span>

一个 FIM 数据的构造示意（理解「重排 + 掩码」即可）：

```python
def to_fim(code, fill_token="<FILL>"):
    # 按函数/块把代码切成前缀、中间、后缀
    prefix, middle, suffix = split_code(code)
    # PSM 变形：前缀 + 后缀 + 填充标记 + 中间
    fim_text = prefix + suffix + fill_token + middle
    # 掩码：只有中间部分参与损失
    mask = [0]*len(prefix) + [0]*len(suffix) + [1]*len(fill_token) + [1]*len(middle)
    return fim_text, mask
```

注意掩码 `mask`：**中间与填充标记要算损失，前缀后缀只作上下文**——这与 loss mask（第二篇）是同一个「只对目标位置算损失」的机制，只是「目标位置」从「回答」变成了「中间填充」。FIM 与普通续写混合训练时，两条数据流共享同一套 mask 逻辑。## 4 公式解析：FIM 的训练目标

FIM 的训练目标，本质还是「下一个 token 预测」，只是**顺序被重排**了。设一条样本被切成「前缀 $p$、中间 $m$、后缀 $s$」，FIM 把序列重排为「$p, s, \langle\text{FILL}\rangle, m$」，然后照常做自回归：

$$
\mathcal{L}_{\mathrm{FIM}} = -\sum_{t \in m} \log P_\theta\big(m_t \mid p,\; s,\; \langle\text{FILL}\rangle,\; m_{<t}\big)
$$

逐项拆解：

- $p, s$：前缀与后缀——FIM 模型**同时看到开头与结尾**；
- $\langle\text{FILL}\rangle$：填充标记——模型先「读完全部已知信息」再开始补；
- $m_t$：中间部分的第 $t$ 个 token；
- $P_\theta(m_t \mid p, s, \langle\text{FILL}\rangle, m_{<t})$：给定前缀、后缀与已补的内容，预测下一个中间 token；
- 损失只算在**中间部分**上——前缀与后缀作为「已知上下文」参与预测，但不被预测。

**直觉**：FIM 让模型学会「**根据前后两头的信息，推断中间的内容**」——这比「只会顺着写」多了一个「回看后面」的能力。对代码来说，这个能力对应「补全函数体」「修复中间逻辑」的真实场景。论文报告，FIM 训练能**同时提升「中间补全」与「前缀续写」**——因为它让模型「看全上下文再生成」，整体生成质量都受益。<span class="marginnote">FIM 的训练比例是个超参：<strong>不是所有样本都转成 FIM</strong>——通常按一定概率（如 50%）随机把样本转成 FIM 格式，其余保持普通续写。因为「纯 FIM」会让模型失去「纯续写」的流畅度；「混着训」则两头都稳。这个「按概率混合」的思路，与对话模板里「训练-推理一致」的直觉相反相成——FIM 是「为推理时的中间补全做准备」。</span>

## 5 评测与 RLVR 衔接

代码模型的评测与强化学习，都靠「可执行」：

**评测**：

- **HumanEval / MBPP**：给定函数签名与 docstring，生成函数实现——用 **pass@k** 度量（采样 k 个，只要有一个通过隐藏测试即算过）；
- **pass@k 的意义**：它不是「生成一次的对错」，而是「采样 k 次的成功率」——**反映「模型的能力上限」而非「一次运气」**。

**与 RLVR 的衔接**：

- 代码的正确性「跑测试就知道」——代码模型是 RLVR 的天然对象；
- 流程：模型生成代码 → 跑单元测试 → 通过给 1、否则 0 → 用 GRPO/PPO 优化——**「写代码 → 测试 → 强化」是 RLVR 最标准的落地**（对应第六篇《RLVR》的「代码战场」）。

**一条完整的代码模型流水线**：清洗/去重 GitHub 语料 → 按「代码 + NL」配比 → FIM + 续写混合预训练/微调 → HumanEval/MBPP 评测 →（可选）RLVR 强化——**数据配方解决「会写」，FIM 解决「会补」，RLVR 解决「写对」**。

## 6 小结

- **代码微调的三张好牌**：数据丰富、可自动验证、结构性强——与 RLVR 完美衔接。
- **数据配方**：清洗去重、许可证过滤、**代码+自然语言配比**（60%–80% 代码）、语言平衡——质量胜过数量。
- **FIM（中间填充）**：训练「给定前缀+后缀，补中间」——对应「在代码中间插入/补全」的真实场景。
- **FIM 目标**：重排为「前缀、后缀、`<FILL>`、中间」再自回归，损失只算中间部分——**「看全上下文再生成」**。
- **两种变形**：PSM（前缀后缀在前）与 SPM（后缀在前）——混合使用更稳。
- **评测与 RLVR**：HumanEval/MBPP + pass@k；「生成→测试→强化」是 RLVR 的标准落地。
- 一句话流程：**配方解决「会写」，FIM 解决「会补」，RLVR 解决「写对」**。
