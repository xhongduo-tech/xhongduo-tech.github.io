## 为什么从多轮对话开始

真实的用户不会只问一句就走。「帮我写个大纲」「再扩展第二点」「换个语气重写」——用户会追问、会纠偏、会追加约束。模型要服务的正是这种**有来有回的对话**，而不是孤立的问答。

前几节的指令数据基本都是「单轮」（一个指令、一个回答）。单轮数据教会模型「看到指令就作答」，却教不会「记住前文」「衔接上一句」「不把上一轮说过的又重复一遍」。**多轮对话数据**补的正是这堂课上不了的能力：上下文利用与角色一致性。<span class="marginnote">很多刚接触微调的人以为「多轮 = 多存几轮文本」，其实难点全在组织与掩码：谁的 token 该算损失、系统提示词放哪、角色怎么区分、上下文怎么不串味。构造多轮数据的正确姿势，正是本节的主题。</span>

## 1 单轮与多轮：差的不只是轮数

把单轮数据简单拼接成多轮，并不能让模型学会对话。单轮数据与多轮数据有本质差异：

| 维度 | 单轮指令数据 | 多轮对话数据 |
| --- | --- | --- |
| 目标 | 学会「指令 → 回答」 | 学会「上文 → 合理的下一句」 |
| 上下文 | 指令即全部 | 历史轮次都是上下文，且会累积 |
| 角色 | 一个用户、一个助手 | 多轮交替，角色必须清晰区分 |
| 错误模式 | 答非所问、幻觉 | 还多出「角色错乱」「重复自己」「忘前文」 |
| 评测难度 | 单轮对错可判 | 连续性、一致性难自动评估 |

一句话：**单轮教的是「会答」，多轮教的是「会聊」**。而「会聊」的起点，是让模型在训练时就看到「上一轮我们说了什么」。

## 2 三大来源：真实、合成与人工

多轮对话数据从哪里来？三条路各有优劣。

**真实用户对话**：最具代表性的来源，典型是 ShareGPT——用户分享自己与 ChatGPT 的真实对话，Vicuna 就是用它训练的 70K 多轮数据训练而成。优点是贴近真实使用、轮次自然；缺点是有隐私风险、质量参差（用户可能中途删改、话痨、多语言混杂），需要清洗与脱敏。

**模型自对话（self-chat）**：让强模型分别扮演用户与助手，交替生成对话，代表工作如 **Baize**（用提示词指定人设与主题让两个模型角色互聊）与 **UltraChat**（先定场景/话题，再让模型多轮展开）。优点是成本低、可规模化、场景可控；缺点是容易「自我重复」——模型扮演的用户问的问题总是那几类，需要引入场景与话题池来保多样性。<span class="marginnote">UltraChat 的一个关键设计是给每段对话预设一个「场景 + 参与者描述」：模型不是凭空聊，而是按剧本演。有了剧本约束，对话的主题、语气、轮次才有结构，否则 self-chat 几轮后就滑向寒暄。</span>

**人工编写**：由标注者模拟真实用户与助手对话。质量最高、最可控，但成本也最高，通常只用于补充「真实与合成都覆盖不到」的难场景（如敏感的价值观冲突对话）。

实践中三者常混用：**真实对话打底 + 合成对话扩规模 + 人工编写补难点**。混合比例同样由上一节的「配比」原则决定。

一个值得注意的趋势：随着强模型能力提升，**合成多轮数据的占比越来越高**。原因是真实对话版权与隐私风险大、清洗成本高，而合成对话只要把场景与角色设计好，产量和可控性都远胜。判断合成质量的一个简单信号：看对话里是否有「用户像助手、助手像用户」的趋同——合成对话最容易犯的毛病，就是两个角色说话越来越像。

## 3 组织与掩码：让模型分清谁在说话

多轮数据在训练时的组织，有一个绕不开的核心问题：**哪些 token 算损失？** 答案与单轮一致——**只对助手（assistant）的回答部分算损失**，用户的话、系统提示词、历史轮次的助手回答，都作为上下文存在、但不计入损失（loss mask 掉）。

设一段 $M$ 轮对话，第 $a$ 轮助手回答的 token 位置集合为 $\mathcal{R}_a$，全部助手 token 数为 $N_A = \sum_a |\mathcal{R}_a|$，则多轮 SFT 损失为：

$$
L_{\text{multi}} = -\frac{1}{N_A}\sum_{a=1}^{M}\sum_{t \in \mathcal{R}_a} \log P_\theta\big(y^{(a)}_t \mid h_{\\lt t}\big)
$$

逐项拆解：

- $M$：对话轮数，$a$ 遍历每一轮助手回答；
- $y^{(a)}_t$：第 $a$ 轮回答里的第 $t$ 个 token；
- $h_{\\lt t}$：位置 $t$ 之前的**全部历史**——系统提示词、之前所有轮次的用户与助手文本，都被模型看到；
- $\mathcal{R}_a$：掩码集合，只覆盖助手回答；**用户文本在求和里被跳过**；
- $N_A$：归一化分母。注意用的是**助手 token 总数**而非总 token 数——这样不同轮数、不同长度的对话，损失尺度一致。

**为什么用户 token 不计损失？** 因为模型不该为「预测用户说什么」负责——它要学的是「作为助手，看到这段历史后接一句合理的话」。若把用户 token 也计入损失，模型会同时学「如何当用户」，产出时容易角色错乱。<span class="marginnote">一个常见的实现坑：有人偷懒把整段对话的 token 都算损失，结果模型学会在回答开头复述用户问题、甚至反串用户语气——因为「预测用户下一句」恰恰让模型养成了「替用户说话」的坏习惯。loss mask 的正确性在第四篇《loss mask 细节》还会细讲。</span>

把一段两轮对话摊开看，掩码长这样（**✓** 算损失，**✗** 不算）：

| 角色 | 内容 | 计入损失 |
| --- | --- | --- |
| system | 你是一个乐于助人的助手 | ✗ |
| user | 帮我写一份周报 | ✗ |
| assistant | 好的，这是周报草稿：…… | ✓ |
| user | 再补充第二点的数据 | ✗ |
| assistant | 第二点补充如下：…… | ✓ |

注意两条细节：第一，**每一轮助手回答都算损失**，而不是只算最后一轮——模型每一轮「如何接话」都值得学；第二，**系统提示词永远不计损失**，但它持续参与上下文，模型在训练中会逐步学会「按系统提示词设定的角色行事」。这段「谁说话、谁算损失」的表格，正是后续《对话模板》与《loss mask》两篇的实质内容——本节先立住概念。

## 4 质量控制：多轮数据特有的错误模式

多轮数据的坏样本，除了单轮就有的「答非所问、幻觉」之外，还有四种特有病灶，筛选时要格外盯住：

**角色错乱**：助手回答里混入「作为用户，我想……」「好的，我明白了，那我们换个话题吧」这类用户口吻的句子。成因是数据里用户与助手话语区分不清，或模型在生成时被用户 token 带偏。检测上可让模型判断「这段回答是否保持助手身份」。

**上下文断裂**：回答完全没利用前文信息。比如用户先问「我的代码报错了」，助手回答「请把报错贴出来」，用户给出报错后，助手却开始讲不相干的原理。这类样本训练模型「忽略上文」，是对话体验的隐形杀手。

**首轮泄漏（context leakage）**：第一轮就假设了对话里没出现过的信息——比如用户第一句只是「你好」，助手却回答「根据你的上一条问题……」仿佛有前文。这说明数据构造时把本属后文的上下文错误地提前了。

**重复自己**：助手在后续轮次把前面已经给出的答案又复述一遍。多轮数据里这类样本会训练模型「车轱辘话来回说」，需要按语义相似度去重。<span class="marginnote">检测「重复自己」可以用简单的 n-gram 重叠：助手当前轮回答与其历史轮次回答的 8-gram 重叠率超过阈值，即可标记为可疑。这个启发式便宜有效，是多轮数据清洗里的常用算子。</span>

质量控制的总原则与单轮一致：**先规则清洗（角色标记、长度、语言），再打分筛选（IFD 等），最后人工抽查**。多轮数据额外要过一遍「上下文一致性」检查——这比单轮更依赖模型辅助判断，因为「有没有接住上一句」是语义问题，规则难以穷举。

## 5 分布设计：轮数、长度与结尾

多轮数据还有一个单轮没有的设计自由度：**轮次分布**。要点有三：

- **轮数分布要贴近使用**：真实用户对话大多数只有 1–3 轮，长对话（10 轮以上）稀少。训练数据若全是长对话，模型在短对话上会「过度表演」——还没问到点子上就开始长篇大论；若全是短对话，长对话的上下文利用能力又练不出来。折中是：**1–3 轮为主（约 70%），4–7 轮一档，8 轮以上少量**。
- **结尾轮次可加权**：模型的「第一反应」往往来自最近的对话状态，有些实践对**最后一轮助手回答**提高损失权重，让模型更重视「当前这轮该说什么」，而非平均用力于所有轮次。
- **长度与轮数解耦**：一轮回答可以很短（「好的」）也可以很长（整段代码）。长度分布按上一节的「长度分层」处理，但注意**轮数多≠长度长**——10 轮短句对话与 1 轮长文回答是两种不同的能力，都要覆盖。

一个实用视角：**多轮数据其实是「上下文利用」的天然教材**。用户在前文给过的偏好（「我是素食者」「我用 Python」），模型能否在后续轮次遵守，就是第九篇评估里「对话一致性」的评分项。构造数据时有意埋设这类「跨轮线索」，比随机对话更能锻炼模型的长程记忆。

构造跨轮线索还有一个常见技巧：**在合成对话里显式插入「要求回顾前文」的轮次**。例如第三轮让用户说「你还记得我第一轮问的是哪两个问题吗？」——这类轮次直接逼迫模型在前文中检索信息，是对「上下文利用」最直白的训练。当然要控制占比，否则对话会显得刻意。

这些分布决策共同指向一句话：**多轮数据的「轮数」「长度」「线索密度」都不是越多越好，而是要与目标产品的对话形态对齐**——你打算让用户和模型聊多久，就按那个形态去配数据。

## 6 小结

- **单轮教「会答」，多轮教「会聊」**——多轮数据的核心是上下文利用与角色一致性。
- 三大来源：**真实对话**（ShareGPT，最贴近使用）、**模型自对话**（Baize、UltraChat，可规模化）、**人工编写**（最可控），实践常三者混用。
- 多轮组织的关键是 **loss mask：只对助手回答计算损失**，用户与系统 token 只作上下文。
- 多轮特有错误模式：**角色错乱、上下文断裂、首轮泄漏、重复自己**——需要规则 + 模型辅助双重清洗。
- **轮次分布贴近使用**：1–3 轮为主、少量长对话；结尾轮次可加权；轮数与长度是两个独立维度。
- 多轮数据是「上下文利用」的教材，跨轮埋线索（用户偏好、历史事实）能有效锻炼长程记忆。
