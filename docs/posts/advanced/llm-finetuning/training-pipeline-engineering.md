## 为什么从训练工程化开始

框架实战这一篇，前五节讲的是「怎么把训练跑起来」，本节讲的是「怎么把训练**工程化**」——即从「能跑」升级到「**能重复、能追踪、能止损**」。这三件事对应三根支柱：**数据校验**（训练前挡住坏数据）、**断点续训**（训练中能止损恢复）、**实验跟踪**（训练后可复现可比较）。

微调是「实验密集」的工作——一天跑十几个配置是常态。没有工程化，你的十几个实验就会「分不清哪个配置、丢了哪个 checkpoint、训崩了只能重来」。**工程化不是「锦上添花」，而是「实验效率的根本」**。本节把三根支柱讲透，再加一条「完整流水线的组装」。

## 1 数据校验：训练前把「坏数据」挡在门外

「垃圾进、垃圾出」——数据校验是在「进」之前把垃圾拦下来。一个完整的数据校验，三层：

**① Schema 校验**：字段齐不齐、类型对不对——`instruction` 是不是字符串、`conversations` 是不是数组。**这是「保不崩」的底线**：字段缺失会让训练中途报错，且错误信息常不指明是哪条。

**② 内容校验**：值合不合理——回答是否为空、是否超长、是否含「该被过滤的」内容（污染、重复）。**这是「保不歪」的质量关**。

**③ 统计校验**：数据集整体是否正常——样本数、长度分布、标签分布。**统计能暴露「数据偏斜」**（某个任务占 95%，另一个几乎没有）——这是「保不偏」的体检。

**工程化的关键**：把校验做成「管线的一步」，而不是「一次性动作」——**每道数据工序（清洗、转换、筛选）的输出都过一遍校验**，而不是只在「数据刚下载时」校验一次。**校验脚本要「fail fast」**：发现问题立即报错退出，而不是「带着问题往下跑」。

## 2 断点续训：训练中的「时间机器」

训练动辄几小时到几天，**任何中断（OOM、断电、手动停止）都不该让前面白跑**——这就是断点续训（checkpoint + resume）的价值。

**断点（checkpoint）**：每隔 N 步保存一份「训练状态」——模型权重 + 优化器状态 + 学习率调度器状态 + 当前步数。**关键：只存权重不够**，优化器状态与调度器状态也要存——否则「续训」时优化器「失忆」，等于重新开始。

**续训（resume）**：从最近的 checkpoint 恢复——权重、优化器、调度器、步数全部接上，训练「无缝继续」。

**工程要点**：

- **保存频率要平衡**：太频繁（每步存）浪费磁盘与时间，太稀疏（每 10k 步）丢了 9k 步的进度——**按「可接受的损失」定频率**；
- **「可恢复性」优先**：**checkpoint 不只是备份，是「时间机器」**——训练崩了可以回到「崩之前的正常状态」再调参（呼应第三篇《训练稳定性》的回滚机制）；
- **清理策略**：保留「最近 + 最优」几个 checkpoint，删除旧的——磁盘是有限的。

**与「实验跟踪」联动**：每个 checkpoint 记录「当时的学习率、loss、步数」——**回滚时知道「回到的是哪个状态的哪一步」**。

在 HF Trainer 里，断点续训几乎是「一行配置」：

```python
training_args = TrainingArguments(
    output_dir="./output",
    save_strategy="steps",
    save_steps=500,                   # 每 500 步存一次 checkpoint
    save_total_limit=3,               # 磁盘上最多保留最近 3 份
    load_best_model_at_end=True,      # 训练结束加载最优权重
    metric_for_best_model="eval_loss",
    greater_is_better=False,
    resume_from_checkpoint=True,      # 断点续训
)
```

注意三件事：`save_steps` 定「可接受损失的粒度」（丢 500 步的进度可以接受）；`save_total_limit` 防磁盘爆炸（只留最近几份）；`load_best_model_at_end` 让「训练结束用的是最优权重」而不是「最后一步的权重」——**「最优」与「最后」往往不是同一个**。

## 3 公式解析：实验跟踪——让实验「可复现、可比较」

实验跟踪的目标：**任何一个训练结果，都能回答「这个结果是怎么来的」**。核心是「配置与结果一一对应」：

$$
\text{一次实验} = \underbrace{\{\text{配置: 模型/数据/超参/框架版本/seed}\}}_{\text{输入}} \;\longrightarrow\; \underbrace{\{\text{指标: loss/评测/吞吐}\}}_{\text{输出}}
$$

逐项拆解「可复现」需要什么：

- **配置完整记录**：模型、数据、超参、**框架与库的版本**、**随机种子**——缺一项都复现不了；
- **随机种子固定**：seed 影响数据打乱、模型初始化、采样——**不固定 seed，同一个配置跑两次结果不同**，「比较实验」失去意义；
- **指标统一**：用「同一套评测、同一个解码配置」测不同实验——**指标口径不一致，比较就是错的**；
- **运行目录规范**：每个实验一个目录（如 `run_20260807_lr2e-5_s42`），里面放「配置 + 日志 + checkpoint + 评测结果」——**一个目录 = 一次可追溯的实验**。

**工具**：Weights & Biases / TensorBoard 等——自动记录曲线、对比多次运行。**但工具只是载体**，核心是「记录什么」：**配置（含版本与 seed）+ 曲线（loss/LR/吞吐）+ 产物（checkpoint/评测）**三件套，缺一不可。<span class="marginnote">「可复现」的最大敌人不是「没记录」，而是「<strong>记录不全</strong>」：<strong>忘了记录 seed、忘了记录框架版本、忘了记录数据哈希</strong>——这三样任何一样缺了，别人（或三个月后的你）就无法复现。工程经验：把「配置 + 版本 + seed + 数据指纹」打包成一个 `manifest.json` 放进运行目录，比任何花哨的跟踪工具都实在。</span>

## 4 完整流水线的组装：从数据到迭代

把三根支柱 + 前文的全部内容，组装成一条生产级流水线：

| 阶段 | 内容 | 工程要点 |
| --- | --- | --- |
| ① 数据 | 清洗、校验、切分 | 三层校验 + fail fast |
| ② 配置 | 模型/数据/超参/seed | 记录完整配置 + 版本 |
| ③ 训练 | 跑训练 | 定期 checkpoint + 监控 |
| ④ 评估 | 三层基线评测 | 同一口径 |
| ⑤ 记录 | 归档配置/日志/产物 | 运行目录规范化 |
| ⑥ 迭代 | 按评测调参重跑 | 对比历史实验 |

**流水线的两个关键心智**：

- **「可重复」优于「一次跑通」**：宁可慢一点也要「每一步可复现」——因为「微调 = 反复迭代」，不可复现的实验等于白跑；
- **「止损」优于「硬撑」**：训练异常（loss 起飞、显存不稳）时，**及时停下、回滚、调参重跑**，比「硬撑到结束」省时间——断点续训让「止损」没有代价。

**一条现实的时间线**：早上配好实验 → 训练中断一次 → 断点续训继续 → 晚上跑完 → 评测 + 记录 → 第二天按结果调参——**工程化让这条时间线「不慌」**：中断不怕、结果可查、对比有据。

### 监控与告警：工程化的「仪表盘」

除了「事后可追溯」，工程化还要「事中可感知」——训练跑着的时候，你要能「一眼看出有没有问题」。三块仪表盘：

1. **训练指标**：loss、学习率、梯度范数——**loss 起飞、梯度 NaN** 是「该停了」的信号（第三篇《训练稳定性》）；
2. **资源指标**：GPU 利用率、显存、吞吐（MFU）——**利用率低是「数据或并行有问题」，显存逼近上限是「要 OOM 了」**（第三篇《吞吐》）；
3. **评测抽样**：训练中定期跑一小批评测（而非只在结束跑）——**「训练中能力有没有涨」能提前看到**，不用等到结束。

告警的粒度：**不是「所有异常都报警」，而是「会导致白跑的异常才报警」**——loss 一两次尖峰可以不报（可能自愈），连续数步 NaN 必须报（会污染权重）。**把「该停的阈值」提前设好，让机器替人盯着**——这是工程化的「省心」所在。## 5 小结

- **训练工程化三支柱**：数据校验（挡坏数据）、断点续训（能止损）、实验跟踪（可复现）。
- **数据校验三层**：Schema（保不崩）、内容（保不歪）、统计（保不偏）——做成「每道工序后的例行步骤」，fail fast。
- **断点续训**：保存「权重 + 优化器 + 调度器 + 步数」四件套；checkpoint 是「时间机器」，不是备份。
- **实验跟踪**：配置（含版本与 seed）+ 指标（同一口径）+ 运行目录规范化——「一个目录 = 一次可追溯实验」。
- **完整流水线**：数据 → 配置 → 训练 → 评估 → 记录 → 迭代——「可重复」优于「一次跑通」，「止损」优于「硬撑」。
- **工程化的本质**：让「反复迭代」这件事不慌——中断不怕、结果可查、对比有据。
