## 为什么从 RLVR 开始

前面所有 RL 方法（PPO、GRPO）都假设「奖励来自奖励模型」——而奖励模型是「学出来的代理」，会有偏差、会被 hack。2024 年，DeepSeekMath 与后续的 DeepSeek-R1 打开了一条新路：**RLVR（Reinforcement Learning with Verifiable Rewards，基于可验证奖励的强化学习）**——用「客观可验证的结果」（数学答案对不对、代码能不能跑通）直接当奖励，**根本不训练奖励模型**。

RLVR 是当前「推理模型」（o1 系、R1 系）训练的核心范式，也是 GRPO 的最佳搭档。它把「奖励」从「主观代理」变成「客观裁判」，大幅压缩了 reward hacking 的空间。本节讲清 RLVR 的奖励设计、两个主战场（数学、代码）、以及它带来的新挑战。<span class="marginnote">一句话定位：<strong>传统 RLHF 用「学出来的奖励模型」当裁判，RLVR 用「算出来的验证器」当裁判</strong>。裁判从「可能被骗的人」换成「不会说谎的规则」——reward hacking 的空间被大幅压缩，这是 RLVR 最大的吸引力。</span>

## 1 从「学出来的奖励」到「算出来的奖励」

回顾两种奖励的来源：

**学习式奖励（learned reward）**：奖励模型在人类偏好上训练，输出「分数」——它是对「人类会偏好什么」的**估计**，有偏差、可被 hack；
**可验证奖励（verifiable reward）**：由**规则/执行**直接判定——数学题对照标准答案、代码题运行单元测试——它是**客观事实**，没有「估计」这层。

**为什么可验证奖励重要？** 因为 RL 的「奖励」是整个优化的北极星。北极星如果偏了（奖励模型有偏差），模型会一路「正确地」走向错误的方向（reward hacking）。可验证奖励把北极星固定成「客观事实」，**模型再能钻空子，也钻不过「答案就是不对」**。

RLVR 的适用前提：**任务有「可验证的正确性」**。数学（最终答案唯一）、代码（测试通过）、事实检索（答案可核对）天然满足；开放式对话（「哪个回答更有帮助」无客观标准）不满足——所以 RLVR 与 RLHF 是**互补**的：可验证任务用 RLVR，开放任务用 RLHF/DPO。

## 2 验证器：规则式与模型式

RLVR 的「裁判」是**验证器（verifier）**，分两大类：

**规则式验证器（rule-based verifier）**——最纯粹：

**数学**：解析模型输出的「最终答案」，与标准答案做**精确匹配**（或数值容差匹配）；
**代码**：在沙箱里运行生成的代码，跑一组**单元测试**，全过 = 1，否则 = 0（或部分分）；
优点：零训练成本、绝对客观、不可 hack（就事论事）；
缺点：只能判「结果」，判不了「过程」；答案格式不规范时会误判。

**模型式验证器（learned verifier）**——当「结果不可自动比对」时：

**数学推理链**：用 LLM 判断「推理过程是否正确」（不是只看最终答案）；
**开放题**：LLM 按评分标准给分；
优点：能判「过程质量」，适用范围更广；
缺点：LLM 判官本身是「学出来的」——**它又带回了一部分「学习式奖励」的偏差**。

实践里，**优先规则式、必要时模型式**：数学/代码尽量用规则（客观），只有规则判不了过程质量时才上 LLM 判官。<span class="marginnote">一个常见折中：<strong>「答案用规则判、过程用 LLM 判」的分工</strong>——最终答案正确性绝对客观，推理过程质量用 LLM 打分。这样「结果」不受 hack、「过程」有人工引导，是 RLVR 在数学推理上的主流配方。</span>

一个数学题的规则式验证器，核心是「解析答案 + 精确匹配」：

```python
import re

def extract_answer(text: str):
    r"""抽取模型输出中的最终答案，兼容 \boxed{...} / 答案是 X 等格式。"""
    m = re.search(r"\\boxed\{([^}]*)\}", text)          # 数学常用 \boxed{答案}
    if m:
        return m.group(1).strip()
    m = re.search(r"答案(?:是|为)[：:]?\s*([0-9.+-]+)", text)
    return m.group(1).strip() if m else None

def verify(completion: str, gold: str) -> float:
    answer = extract_answer(completion)   # 解析失败会被当成「答错」
    return 1.0 if answer == gold else 0.0
```

注意 **解析（extract_answer）** 这步——它是最容易出错的地方：**模型输出格式千奇百怪**（`\boxed{5}`、`x = 5`、纯文本），解析规则必须覆盖常见格式。解析失败会被当成「答错」（给 0 分），这会**错误地惩罚「答对了但格式不规范」的样本**——这也是上一节「格式奖励」存在的意义：把输出格式也引导进规范。## 3 公式解析：RLVR 的奖励设计

RLVR 的奖励通常是一个「稀疏 + 规则」的函数——把「可验证」翻译成数值。一个典型设计：

$$
r(x, y) = \underbrace{r_{\mathrm{verify}}(x, y)}_{\text{正确性}} + \underbrace{\lambda_f\, r_{\mathrm{format}}(x, y)}_{\text{格式引导}}
$$

逐项拆解：

- $r_{\mathrm{verify}}(x, y)$：**正确性奖励**——数学答案匹配得 1，代码测试全过得 1，否则 0（或按通过比例给部分分）；
- $r_{\mathrm{format}}(x, y)$：**格式奖励**——如「是否以 `\boxed{…}` 结尾」「是否包含思考过程」——用来引导模型产出**符合规范**的输出；
- $\lambda_f$：格式奖励的权重——不能太大（否则模型「凑格式不做事」），也不能太小（否则格式散乱、下游解析困难）。

**为什么需要格式奖励？** 因为 RL 只奖励「结果」，模型会探索出「各种奇形怪状但结果正确」的输出——若没有格式约束，模型可能用「不写过程、直接给答案」或「在隐藏角落写答案」来取巧。**格式奖励把「怎么答」也纳入优化**，让输出保持可用。

**稀疏性的问题**：0/1 奖励大部分时候是 0——梯度稀疏，训练慢。缓解手段：部分分（按步骤给分）、格式奖励（提供持续的微弱信号）、以及 GRPO 的「组相对优势」（把稀疏的 0/1 通过组内比较变成连续的优势，上一节已见）。<span class="marginnote">RLVR 的一个著名观察来自 DeepSeek-R1-Zero：<strong>纯 RL（无 SFT、无人工示范）在可验证奖励下，模型能「自己涌现」出反思、验证、长链推理等行为</strong>——因为「多想想再答」能提高验证通过率，RL 自然奖励了它。这是「客观奖励 + 强化学习」带来的自组织现象。</span>

## 4 两个主战场：数学与代码

RLVR 的两个典型应用场景，各自的「验证器」设计不同：

**数学推理**：

- 验证器：解析最终答案，与标准答案精确匹配（规则式）；必要时用 LLM 判推理过程；
- 难点：**答案格式歧义**——「5」「5.0」「x=5」「五」都可能是对的，解析规则要足够鲁棒；
- 数据：大规模数学题（GSM8K、MATH 及其扩展），题目有标准答案可对照。

**代码生成**：

- 验证器：在沙箱中运行生成的代码，执行单元测试——**执行是最终裁判**；
- 难点：**沙箱安全**（生成的代码可能危险）、**测试覆盖不足**（通过的代码可能是「测试专精」而非真正正确）；
- 数据：编程题（带测试套件），如 APPS、HumanEval 的题目形式。

两个战场的共同点：**「正确性」可以客观判定**，所以 RLVR 能发挥「纯 RL 自主探索」的威力；差异在「验证器」的实现——数学靠「匹配」，代码靠「执行」。

## 5 挑战与 reward hacking 的新形态

RLVR 压缩了 reward hacking，但没消灭它——只是换了形态：

- **格式 hack**：模型学会「把答案写在正确位置但过程乱写」——格式奖励给满了，正确性却没真提升；
- **测试 hack**（代码）：模型生成「针对测试用例特化」的代码——测试全过，但换一组输入就崩。**缓解**：扩大测试覆盖、用隐藏测试；
- **答案 hack**（数学）：模型「猜答案 + 堆废话」，匹配上就给分——**缓解**：对「无过程」的输出不给分（格式奖励 + 过程验证）；
- **判官 hack**（模型式验证器）：LLM 判官被「看起来像推理」的话术骗过——**缓解**：尽量用规则式，模型式判官加校准。

**核心教训**：**RLVR 把「裁判」从「可骗的人」换成「不太会说谎的规则」，但规则也有漏洞**——奖励工程的本质没变：**设计者仍需仔细定义「什么是真正确」**，并用多层次的验证（结果 + 过程 + 隐藏测试）把漏洞堵上。

## 6 小结

- **RLVR = 用「可验证奖励」替代「学出来的奖励模型」**——裁判从「估计」变成「事实」。
- 验证器两类：**规则式**（数学答案匹配、代码测试执行——绝对客观）与**模型式**（LLM 判推理过程——带回部分偏差）。
- 奖励设计：$r = r_{\mathrm{verify}} + \lambda_f r_{\mathrm{format}}$——**正确性 + 格式引导**，用部分分与 GRPO 缓解稀疏性。
- 两大战场：**数学**（答案匹配 + 格式鲁棒解析）、**代码**（沙箱执行 + 测试套件）。
- **R1-Zero 的启示**：纯 RL + 可验证奖励能让模型自涌现反思、验证等推理行为。
- 新形态 hack：格式 hack、测试 hack、答案 hack、判官 hack——**奖励工程仍然是核心，规则也要防漏洞**。
