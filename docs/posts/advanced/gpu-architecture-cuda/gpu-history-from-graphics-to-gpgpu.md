## 为什么从 GPU 简史开始

从「从极限到大模型」这条主线看，**大模型之所以能诞生，靠的是三件事：算法、数据、算力**。算法与数据在前几级已经讲了很多，而算力的主角正是 GPU。理解大模型预训练、理解分布式训练、理解推理时的 KV 缓存与延迟，最终都要回到同一个问题：**GPU 是怎么被造出来的，它的架构哲学到底是什么。**

本专题对标 Kirk 与 Hwu 的 *Programming Massively Parallel Processors*（第 4 版）、NVIDIA 官方《CUDA C++ Programming Guide》，以及 Hennessy、Patterson 的《计算机体系结构：量化研究方法》（第 6 版 §4 GPU 章）。第一篇不碰指令、不碰寄存器，先讲清楚一件最基本的事：**GPU 从哪里来，为什么它的设计哲学与 CPU 如此不同。** <span class="marginnote">PMPP 第 1 章 "Introduction" 与第 2 章 "Heterogeneous Data Parallel Computing" 用整整两章回答「为什么我们需要异构并行计算」，正是本篇的知识地图；后续各篇将按第 4–6 章（计算与存储架构）、第 20–22 章（流与集群）逐节展开。</span>

## 1 从固定功能到可编程：GPU 的第一次转折

GPU 的历史可以压缩成一句话：**先是把「图形渲染」从 CPU 手里抢过来，再把「通用计算」从 CPU 手里抢过来。**

1999 年，NVIDIA 发布 **GeForce 256**，第一次自称「GPU」（Graphics Processing Unit，图形处理单元）。它的革命性在于把几何变换与光照（Transform & Lighting，T&L）从 CPU 固化成专用硬件：原本要在 CPU 上排队等待的三角形变换，现在由显卡自己完成，游戏画面的帧率因此跃升。此后两年，显卡市场围绕「固定功能管线」竞争——顶点怎么变换、像素怎么着色，都在硬件里写死，程序员只能调参数，不能改流程。

转折发生在 2001 年：NVIDIA 的 **GeForce 3** 引入**可编程着色器（programmable shaders）**。顶点着色器与像素着色器不再是固定的黑盒，而变成一段可以由程序员书写的短程序。<span class="marginnote">着色器（shader）这个词源于 "shade"（着色）：最初它只是给三角形表面计算颜色与光照的小程序，后来演变成「在 GPU 上执行的任意可编程代码段」的代名词——今天 CUDA kernel 的前身。</span>2003 年，DirectX 9 与 OpenGL 2.0 把这项能力标准化，GPU 第一次真正向「可编程处理器」靠拢。这是 GPU 历史上的**第一次转折：从固定功能走向可编程。**

## 2 通用计算的觉醒：GPGPU 与 CUDA

可编程着色器打开了潘多拉魔盒：既然能写程序，为什么只能写图形程序？2003 年前后，斯坦福大学的 Ian Buck 等人提出 **Brook** 语言，把通用科学计算塞进着色器——这就是最早的 **GPGPU（General-Purpose computing on Graphics Processing Units，基于 GPU 的通用计算）**。当时的先驱者把数据伪装成纹理、把计算伪装成「像素着色」，用一套笨拙的拐杖实现流式计算：写一个「像素程序」，把它渲染到一块屏幕大小的离屏画布上，运算结果就藏在画布的像素值里。

真正改变一切的是 2006 年 11 月 NVIDIA 发布的 **G80 架构（GeForce 8800 GTX）** 与随后的 **CUDA**：

- G80 首次把顶点着色器与像素着色器合并成**统一着色器（unified shaders）**——同一批执行单元既能跑图形程序，也能跑通用程序。
- CUDA 让程序员用熟悉的 C/C++ 方言直接写 GPU 程序，把「数据伪装成纹理」的拐杖彻底扔掉。

**CUDA（Compute Unified Device Architecture，计算统一设备架构）** 的名字本身就宣告了方向：图形与计算共用同一套设备、同一套编程模型。<span class="marginnote">同一年代，苹果联合多家厂商推动的 OpenCL 也在 2008 年发布首个规范，试图做成「异构计算界的 USB」，但 CUDA 凭借更成熟的工具链、更深的编译器优化和更丰富的库生态，成为事实上的主流——这一点的细节会在《CUDA 编程模型》一篇展开。</span>2008 年，NVIDIA 推出 Tesla 系列，把 GPU 正式卖向高性能计算市场——GPGPU 从民间黑客玩法变成了正规生意，也奠定了今天「异构计算 = CPU 控制 + GPU 加速」的格局。

## 3 2012 年：GPU 与大模型相遇

GPU 历史上的**第二次转折**由深度学习点燃。2012 年，Alex Krizhevsky 用两块 GTX 580 训练出 **AlexNet**，在 ImageNet 图像分类挑战赛上以压倒性优势夺冠（错误率从 26% 一举降到 15% 级别）。业界突然意识到：GPU 的「数据并行」天性与神经网络的矩阵运算完美契合，**GPU 从此不只是图形卡，而是 AI 的第一引擎。**

此后 GPU 的算力一路狂奔：G80（2006）的 FP32 浮点约 0.5 TFLOPS，到 A100（2020）约 19.5 TFLOPS，H100（2022）约 67 TFLOPS——十六年间提升了约两个数量级，远超同期 CPU 的演进速度。<span class="marginnote">这一数量级跃迁不靠时钟频率（频率早已停滞在 2–3 GHz 附近），而靠晶体管规模与并行执行单元数量的扩张。这正是下一篇《SIMT 执行模型与硬件层次》的主角。</span>今天的「从极限到大模型」主线，也正是踩着这条曲线跑起来的：预训练、推理、KV 缓存、量化，全部构建在这一颗颗吞吐导向的芯片之上。

## 4 核心对比表：CPU 与 GPU 的设计分野

GPU 不是「更强的 CPU」，而是**换了一整套取舍**的处理器。下表是理解本专题全部内容的第一块基石：

| 维度 | CPU | GPU |
| --- | --- | --- |
| 设计哲学 | 延迟导向（latency-oriented） | 吞吐导向（throughput-oriented） |
| 执行单元 | 数十个复杂乱序核心 | 数千个简单有序执行单元 |
| 缓存策略 | 大容量缓存压低延迟 | 小缓存 + 大寄存器堆，靠并行隐藏延迟 |
| 控制逻辑 | 分支预测、乱序发射 | 简单调度，海量线程快速切换 |
| 寄存器/线程 | 每核少量线程 | 每 SM 数千活跃线程 |
| 擅长任务 | 串行、分支密集、单任务延迟敏感 | 数据并行、计算密集、整体吞吐敏感 |
| 典型比喻 | 跑车 | 公交车 |

**关键结论：CPU 为「让单个程序尽快跑完」优化，GPU 为「让一大批程序整体跑完」优化。** 现代大模型训练需要的正是后者——万亿次矩阵乘法中没有任何一个单点需要极低延迟，需要的只是把海量数据并行地碾过去。<span class="marginnote">Hennessy 与 Patterson 在《量化研究方法》第 4 章（Data-Level Parallelism in Vector, SIMD, and GPU Architectures）用「吞吐 vs 延迟」这对矛盾概括 CPU 与 GPU 的分野，并由此引出「领域专用架构」的讨论——本篇表格正是该论点的浓缩。</span>

## 5 两条技术线的分岔：为什么 GPU 选择吞吐

值得停下来看清的是：GPU 的「吞吐导向」并非凭空设计，而是**从图形应用的需求一步步演化而来**。

图形渲染的本质是「对屏幕上几百万个像素做同样的运算」，天生数据并行；而 3D 游戏需要每秒渲染 60 帧，帧率就是吞吐率。于是 GPU 从一开始就选择了「越多越好」的并行路线：与其把一个像素算得飞快，不如同时算几百万个像素。这套取舍沉淀出一批影响至今的硬件习惯：**合并内存访问**（相邻像素读相邻纹理，天生亲和）、**简单调度**（无需乱序发射）、**海量线程**（一个像素一个线程）。

这条路线与 CPU 的「越单越快」路线分道扬镳，并在 2005 年前后因为**功耗墙**而得到印证：CMOS 工艺下时钟频率无法再安全提升，CPU 单核性能增长放缓，多核与数据并行成为唯一出路——GPU 的吞吐哲学反而成了时代的答案。**功耗墙让 GPU 从「图形专用协处理器」升级为「通用并行引擎」。** 这也是第一篇的核心叙事：GPU 的崛起不是偶然，而是「架构取舍 + 时代瓶颈」的共同结果。<span class="marginnote">2005 年前后正是「频率竞赛」终结的节点：Intel 在 2004 年取消 4 GHz 的 NetBurst 计划，AMD、IBM 也相继转向多核。多核时代 = 并行时代，而 GPU 已经为并行准备了十年。</span>

## 6 一张时间线：三十年 GPU 演进

把上面的故事压进一张表，方便回看：

| 年份 | 事件 | 意义 |
| --- | --- | --- |
| 1999 | GeForce 256 | 首次自称 GPU，T&L 硬件化 |
| 2001 | GeForce 3 | 可编程着色器，GPU 开始可编程 |
| 2003 | Brook / DirectX 9 | 通用计算尝试，GPGPU 萌芽 |
| 2006 | G80 + CUDA | 统一着色器，通用编程模型诞生 |
| 2008 | NVIDIA Tesla / OpenCL | GPU 进入高性能计算与异构标准 |
| 2012 | AlexNet 于 GTX 580 | 深度学习引爆 GPU 算力需求 |
| 2017 | Volta + Tensor Core | 为矩阵运算定制专用硬件（见《Tensor Core》一篇） |

从这张表能看到一条清晰的轨迹：**图形专用 → 可编程 → 通用计算 → AI 专用**。GPU 不断拓宽自己的战场，也一路留下「专用化」的遗产——最新的例子就是为矩阵乘法定制的 Tensor Core，以及为光线追踪定制的 RT Core。

读这张表时注意：每一个「转折」都对应一次「专用化程度的跃迁」——GPU 从不专用（固定管线）到半专用（着色器）再到更专用（Tensor/RT Core），而每一次跃迁都让「从极限到大模型」的算力故事更进一步。

## 7 为什么是 CUDA 赢了：生态护城河

通用计算的早期并不只有 CUDA 一个玩家，今天的「CUDA 事实标准」是打出来的，不是设计出来的。把当年的竞争者排在一起，格局一目了然：

| 方案 | 发起者/年代 | 定位 | 命运 |
| --- | --- | --- | --- |
| CUDA | NVIDIA，2006 | 私有但开放的异构编程模型 | 事实标准，生态最厚 |
| OpenCL | Apple/Khronos，2008 | 开放异构计算标准 | 作为兼容层存在，生态趋弱 |
| DirectCompute | Microsoft，2009 | DirectX 内的计算着色器 | 仅 Windows/游戏圈 |
| ATI Stream / ROCm | AMD，2006/2016 | 对标 CUDA 的 AMD 方案 | 兼容 CUDA 编译路径为主 |

把胜负摊开看，赢的原因不在「谁的指令集更好」，而在三件事：

- **cuBLAS / cuFFT / cuDNN（2008–2014）**：NVIDIA 把最常用库写好，矩阵乘法、FFT、卷积开箱即用，性能由专家打磨，用户不必从头写。
- **编译器与工具链成熟**：nvcc、Nsight、CUDA 运行时稳定演进，社区文档与案例极多，学习曲线平坦。
- **框架绑定**：TensorFlow、PyTorch 的原生后端几乎都是 CUDA——**训练框架选型 = 隐式选 CUDA**。

这条生态战争的历史，对「从极限到大模型」主线是重要的一课：**算力之争，从来不只是芯片之争，更是「谁能被最省力地用起来」之争。** 当 PyTorch 用户敲一句 `cuda()` 就能吃到全栈优化时，通用标准在工程便利性面前已经输了。AMD 的 ROCm 近年靠「兼容 CUDA 源」奋起直追，但「生态惯性」仍是 CUDA 最深的护城河——这也是华为昇腾 CANN 全力做算子库与图编译的原因（见《华为 CANN》专题）。

对学习者而言，这条历史同样有方法论意义：**标准不是「设计」出来的，而是「生态」养出来的。** 理解 CUDA 生态的构成（库、编译器、框架绑定），比背诵指令集更能预测 GPU 世界的未来走向——这也为后文《Tensor Core 与矩阵运算》《性能分析与调优》里「为什么直接调库」埋下伏笔。

补充一个细节：CUDA 生态的「软件即护城河」不是口号——cuBLAS 在 2008 年发布时就把矩阵乘法性能做到了当时手写代码的数倍，此后每次架构换代（Volta 张量核心、Hopper WGMMA）都是库先行、开发者零改动吃到新硬件。**生态让「升级硬件」对用户几乎无感，这才是平台真正的粘性**——它解释了为什么「从极限到大模型」的算力故事，一半写在了芯片上，一半写在了库与框架里。

## 8 小结

- GPU 经历两次转折：从**固定功能管线**到**可编程着色器**（2001），再到 **GPGPU/CUDA 通用计算**（2006）。
- 1999 年 GeForce 256 首称 GPU；2001 年 GeForce 3 引入可编程着色器；2006 年 G80 + CUDA 开启通用计算；2012 年 AlexNet 开启 GPU + AI 时代。
- **CPU 延迟导向、GPU 吞吐导向**，这是二者所有差异的总根源。
- 功耗墙（2005 年前后）让吞吐并行从「可选项」变成「必然项」。
- GPU 的演进主线是「图形专用 → 可编程 → 通用 → AI 专用」，本专题后续各篇都是这条主线的具体展开。
