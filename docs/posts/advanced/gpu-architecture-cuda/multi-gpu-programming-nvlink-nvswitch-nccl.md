## 为什么从多 GPU 开始

本专题前十一篇讲的都是单张 GPU。但今天的现实是：**一张卡远远不够**——GPT-4 级别的模型动辄数万亿参数，单卡显存连模型都装不下；即便装得下，单卡的算力也喂不饱训练时长要求。于是问题变成：**如何把多张 GPU 组织成一个「超大 GPU」。**

多 GPU 编程是《流、事件与并发执行》篇的自然延伸：流让「一张卡上」的计算/传输重叠，多 GPU 让「多张卡之间」的计算/传输并行。它也是通往集群训练（《AI 基础设施》专题、分布式训练系列）的桥头堡。<span class="marginnote">PMPP 第 20 章以 CUDA 流讲透「时间重叠」，第 22 章扩展到多 GPU 与异构集群；NCCL 与 NVLink 的权威定义见 NVIDIA 官方文档。与《多 GPU 编程》衔接的集群细节，本博客另有《AI 基础设施》与分布式训练专题展开。</span>

## 1 硬件互联：卡与卡怎么说话

多 GPU 系统的一切性能都取决于**卡间互联带宽**。三种主流连接：

- **PCIe**：通用总线，一代大约每链路翻倍。PCIe 4.0 ×16 双向约 32 GB/s，PCIe 5.0 ×16 约 64 GB/s——够小规模互传，但训练大模型时常成瓶颈。
- **NVLink**：NVIDIA 的点对点高速互联。A100 单卡 NVLink 带宽约 600 GB/s（双向），H100 约 900 GB/s——比 PCIe 高一个数量级，是「多卡像一卡」的硬件基础。
- **NVSwitch**：NVLink 的**交换矩阵**。机架内的多张 GPU 都连到 NVSwitch 上，任意两张卡之间都能以全速互访——DGX 这类机器用 NVSwitch 把 8 张卡连成「一张大卡」。

**关键直觉：多 GPU 程序的下限由互联决定。** 数据在卡间传一次，成本是 NVLink 的纳秒级、PCIe 的微秒级；设计并行方案时，「卡间通信量」和「计算量」的比例，直接决定扩展效率。<span class="marginnote">可以对比一下数量级：H100 的 NVLink 900 GB/s 已经和它自己的显存带宽（3.35 TB/s）同一量级——所以「把数据搬到另一张卡」和「从自己的显存取数」差不多贵。这正是 NVLink 出现后、GPU 集群能「像一台机器」的原因。</span>

这张「互联决定一切」的现实，决定了多 GPU 程序员的第一个问题永远是：我的卡之间带宽是多少？它直接决定该选哪种并行策略、以及扩展效率的天花板在哪——所以读任何多 GPU 白皮书，先看互联带宽表。

## 2 集合通信：NCCL 在做什么

多 GPU 训练里，最频繁、最贵的操作是**集合通信（collective communication）**——所有卡要交换数据，最常见的是 **all-reduce（全归约）**：数据并行训练每步算完梯度后，要把所有卡的梯度**求和**并**广播回**每张卡。

这个「求和并广播」如果让程序员手写，要在卡间搬 $N$ 次数据；而 NVIDIA 的 **NCCL（NVIDIA Collective Communications Library）** 把它优化到接近下限：

- **Ring all-reduce**：把 $N$ 张卡排成环，每张卡只和邻居传数据，总量摊到 $N$ 份，通信量与卡数解耦。
- **NVLink/NVSwitch 感知**：NCCL 知道拓扑，自动选最快的路径，避免流量挤在一条链路上。

**结论：多 GPU 场景永远不要手写梯度同步，直接调 `ncclAllReduce`。** 它不仅是「少写代码」，而是「算法级更优」——手写版本往往会比 NCCL 慢一个数量级。<span class="marginnote">NCCL 的另一个价值是拓扑自发现：它读 GPU 的 NVLink/PCIe 拓扑表，自动决定 ring 怎么排、数据走哪条路径。这在「8 卡机」和「跨机 NVLink/InfiniBand 混合」场景下差距巨大——工程师在集群上做的一切「调拓扑」，NCCL 都在底层替你做了大半。</span>

### NCCL 的 Ring 与 Tree 算法

NCCL 内部不止一种 all-reduce 实现，主流是两类：**Ring（环形）** 与 **Tree（树形）**。

- **Ring all-reduce**：把 N 张卡排成环，每张卡只和左右邻居通信，把数据切成分片逐轮传递。通信总量 ≈ 单份数据的 $2(N-1)/N$ 倍，**与卡数基本无关**——适合「卡多、单份数据大」的规模（如 8 卡以上的训练）。
- **Tree all-reduce**：把数据沿二叉树「从叶到根逐层归约、再广播回去」，延迟随树高（约 $\log N$）增长，**比 Ring 的链式传递延迟更低**——适合「卡少、数据小、延迟敏感」的场景。

NCCL 会根据 GPU 数量、互联拓扑与数据大小**自动选择算法**——大多数时候你不需要指定。真正需要人介入的是「跨机」场景：机内走 NVLink、机间走 InfiniBand，NCCL 会尽量让「机内 Ring + 机间 Tree」分层，把跨机流量降到最低。<span class="marginnote">这条「Ring 管带宽、Tree 管延迟」的权衡，与前面「分块大小」「流数量」是同一套思路：<strong>不同的性能目标（带宽 vs 延迟）对应不同的拓扑选择，没有一种算法通吃。</strong></span>

## 3 公式解析：Amdahl 定律与扩展效率

多 GPU 能带来多大加速？教科书答案是 **Amdahl 定律**：

$$
S(N) = \frac{1}{(1 - f) + \dfrac{f}{N}}
$$

逐项拆解：

- **$N$**：GPU 数量。
- **$f$**：可并行的比例（0 到 1）。剩余 $1 - f$ 是**不可并行**的串行部分（如不可避免的同步点、通信等待、启动开销）。
- **$S(N)$**：相对单卡的加速比。

代入 $f = 0.9,\ N = 8$：$S = 1 / (0.1 + 0.9/8) = 1 / (0.1 + 0.1125) \approx 4.7$——**8 张卡只换来 4.7 倍**，因为 10% 的串行尾巴卡住了上限。$N \to \infty$ 时 $S \to 1/(1-f)$，加速比有天花板，不是卡越多越好。

**扩展效率（parallel efficiency）** 定义为 $E = S(N)/N$：8 卡得 4.7 倍，效率 $= 4.7/8 \approx 59\%$。工程上「加速比除以卡数」是判断「值不值得加卡」的第一指标——效率掉到 40% 以下，往往是通信已经盖过了计算。<span class="marginnote">这里有个和 Roofline 神似的结构：Amdahl 的天花板 $1/(1-f)$ 就是「扩展受限」的屋顶，$f$ 越接近 1，屋顶越高。多 GPU 优化的本质，就是不断压低不可并行的 $1-f$（通信、同步、负载不均）。</span>

再补充一个常被忽略的点：**Amdahl 里的 $1-f$ 不只是通信**，还包括负载不均——GPU 之间若分工不均，快的卡要等慢的卡，这同样是「不可并行」的一部分。把负载调平，往往比单纯压通信更立竿见影。

## 4 三种并行：数据、模型、流水线

多 GPU 到底怎么「分」？三种主流的切分方式：

- **数据并行（data parallel）**：每张卡放一份完整模型，把 batch 切成多份，各算各的梯度，然后 **all-reduce 同步梯度**。最简单、扩展性好，但模型要装得进单卡显存——**这是 90% 场景的默认选择**。
- **模型并行 / 张量并行（model / tensor parallel）**：把模型**权重**切开，每张卡持有一块，矩阵乘法时跨卡协作。适合单卡装不下的巨型模型，但通信频率高，对 NVLink 带宽要求苛刻。
- **流水线并行（pipeline parallel）**：把模型的**层**按顺序分到各卡，卡与卡之间像流水线一样接力。每卡只存一部分层，通信量小（只在相邻卡间传激活值），但存在「气泡（bubble）」——流水线空转的时间。

三者的取舍恰好呼应本专题反复出现的主题：**用带宽换显存、用通信换容量。** 现代大模型训练（如 DeepSeek 系、GPT 系）普遍是三者**混合**：张量并行切权重 + 流水线切层 + 数据并行放大批量。<span class="marginnote">把三者想成三种「切蛋糕」方式：数据并行是「每人一份完整蛋糕图纸，各烤各的再对味道」；张量并行是「一块蛋糕切开，几个人各拿一块同时裱花」；流水线并行是「蛋糕分楼层，每层一个师傅接力」。它们回答同一个问题：模型太大/卡太多时，怎么把活拆开。</span>

补充一个实际判断：**不是所有问题都值得多 GPU**。通信占比超过 30% 的小模型、或每步只跑几毫秒的 kernel，多卡往往得不偿失——固定开销（启动、同步、网络握手）吞掉了并行的好处。**先跑单卡基线，再用 Amdahl 估算上限**，是决定「要不要上多卡」的第一道闸。

## 5 与集群博文衔接：从多卡到数据中心

多 GPU 是「机内」的并行，再往上就是「跨机」的集群。两条线是连续谱：

- **机内**：NVLink + NVSwitch + NCCL，延迟纳秒级，可以像一张卡一样编程。
- **跨机**：InfiniBand / RoCE + RDMA，延迟微秒级，NCCL 同样抽象掉底层（用 `NCCL_P2P` 等控制）。

本博客《AI 基础设施》专题（CUDA、NCCL、并行训练、集群与成本）正是从这里继续展开：MoE 的专家并行、序列并行、分布式注意力、All-to-All 通信、跨机拓扑优化——它们都是「多 GPU 编程」在数据中心尺度上的放大版。<span class="marginnote">记住一条贯穿主线：<strong>单卡是 SIMT，多卡是「SIMT 的 SIMT」</strong>——同一套「并行 + 通信 + 同步」的三段论，从 warp 内部（32 线程）搬到 SM 之间（共享内存/原子），再搬到 GPU 之间（NVLink/NCCL），尺度在变，思想不变。</span>

## 6 数据并行训练的一步：all-reduce 的时间账

把「数据并行训练的一个 step」拆开，看通信时间从哪来——这是多 GPU 优化的主战场。

一个 step 的流程是：**前向（每卡独立）→ 反向（每卡独立算出自己的梯度）→ all-reduce（把 N 卡的梯度求和并广播）→ 更新（每卡独立）**。前向、反向、更新都是「每卡单干」，只有 all-reduce 需要跨卡通信——**训练里唯一无法靠算力加速的部分就是它。**

all-reduce 的数据量是确定性的：每步要同步全部模型参数梯度。设模型有 $P$ 个参数、FP32 存梯度（4 字节），则每步跨卡传输约 $2 \times P \times 4$ 字节（一次 reduce 求和 + 一次 broadcast 下发）。拿 7B 模型算：$2 \times 7\times 10^9 \times 4 \approx 56$ GB——**一个 step 要在卡间搬 56 GB！** 这正是「模型越大，通信占比越高」的数学来源，也是为什么大模型必须转向张量并行/流水线并行的原因：它们把「每步全量同步」拆小，换走部分通信。

**Ring all-reduce 的价值**：朴素做法是「一张卡收齐全部、求总、再下发」，通信量随卡数线性膨胀且受单卡瓶颈；Ring 算法让每张卡只和邻居传「一份分片」，总量固定为「单份数据的 $2(N-1)/N$ 倍」，与卡数基本解耦。**这就是为什么「多卡训练一定要用 NCCL」——它把通信量从「随卡数爆炸」压到「与卡数无关」。**<span class="marginnote">放大到数据中心尺度，这套「如何让通信不随规模爆炸」的思想继续演化：分层 Ring、树状 all-reduce、All-to-All、MoE 的专家并行——本博客《AI 基础设施》专题会逐个展开。多 GPU 篇到这里，只是把「通信是并行系统的第二定律」这一课立住。</span>

**一句话总结：多 GPU 训练的性能，前向/反向看单卡算力，步与步之间看 all-reduce 的通信量。** 想让训练更快，要么用更强的卡（降单步耗时），要么用更好的并行切法（降通信占比）——NCCL 只是把后者的通信实现做到最优，这也是为什么工程团队常把「通信优化」与「并行策略设计」一起排优先级，而不是只盯着单卡算力表看。

补一个视角：**那 56 GB 不是每步都「从零搬」**——NCCL 会做分片流水与梯度打包，把通信藏进计算；真正的杀手锏仍是「把需要同步的参数量变小」（如梯度压缩、低精度通信），这是《AI 基础设施》专题的前沿话题。

（延伸：当你听到「通信计算比（communication-to-computation ratio）」这个词，它其实就是 Amdahl 里 $1-f$ 的工程化身——数值越高，越该用张量并行/流水线并行把通信摊薄，这是集群设计的第一直觉。）

## 7 小结

- 多 GPU 性能上限由**互联**决定：PCIe（约 32–64 GB/s）＜ NVLink（A100 约 600 GB/s、H100 约 900 GB/s）＜ NVSwitch 交换矩阵。
- **NCCL** 提供 all-reduce 等集合通信，Ring 算法 + 拓扑感知，多 GPU 梯度同步必须用它而不是手写。
- Amdahl 定律 $S(N) = 1/((1-f)+f/N)$：串行尾巴 $1-f$ 决定加速比天花板；扩展效率 $E = S/N$ 是加卡值不值的判据。
- 三种并行：**数据并行**（每卡整模型 + all-reduce）、**张量并行**（切权重）、**流水线并行**（切层），现代训练三者混合。
- 从多卡到集群是连续谱：机内 NVLink、跨机 InfiniBand，NCCL 统一抽象。
