## 为什么从内存层次开始

SIMT 教会了我们怎么让 GPU 算得快——但 GPU 上「算」几乎从来不慢，慢的是「取数」。**一个浮点加法几个周期，一次全局内存访问几百个周期。** 谁控制了数据流动，谁就控制了 GPU 性能。

CPU 世界有一条「只要缓存足够大，性能问题都能拖过去」的经验，GPU 世界完全不同：GPU 靠并行隐藏延迟，靠**合并访问**压榨带宽。理解内存层次，是 GPU 优化的核心功课，也是后面占用率、bank conflict、Tensor Core 全部内容的底层逻辑。<span class="marginnote">PMPP 第 5 章 "Memory Architecture and Data Locality" 是本篇的主线；《CUDA C++ Programming Guide》§5 详细列出了每种内存空间的官方规格，下面的数值都以官方文档与 PMPP 为据。</span>

## 1 内存层次总览：五层各有分工

CUDA 编程模型给程序员提供了多个可寻址的内存空间，从快到慢（大致）排列：

| 内存空间 | 位置 | 延迟 | 容量 | 谁用 |
| --- | --- | --- | --- | --- |
| 寄存器 | 片上 SRAM | 1 周期 | 每线程 ≤255 个 | 线程私有 |
| 共享内存 | 片上 SRAM | ~20–30 周期 | 每 SM 可达 100+ KB | block 内共享 |
| 常量内存 | 片上缓存 + DRAM | 命中即快速 | 64 KB | 全体只读、广播 |
| 纹理内存 | 片上缓存 + DRAM | 命中即快速 | 显存容量 | 全体只读、空间局部 |
| 全局内存 | 板载 DRAM（显存） | ~400–800 周期 | 数十 GB | 全体 |

**关键直觉：容量越大越慢，速度越快越小。** GPU 没有把「大而快」的幻想留给程序员，而是逼你学会在正确的层级放正确的数据。<span class="marginnote">注意共享内存与寄存器都是「片上 SRAM」，它们的速度比显存快一个数量级。GPU 的缓存策略与 CPU 相反：CPU 用大缓存自动帮你隐藏，GPU 把一部分「缓存」交给你手动管理（共享内存），用对了是性能放大器，用错了是正确性地雷。</span>

## 2 全局内存与合并访问：GPU 的带宽命脉

**全局内存（global memory）** 是 GPU 的主存，挂在显存 DRAM 上。它的延迟极高（数百周期），但带宽极大——A100 约 1.5–2 TB/s，H100 约 3.35 TB/s。GPU 的全部性能故事，一半是「怎么把这么多带宽用满」。

用满带宽的关键是**合并访问（coalesced access）**：**当一个 warp 的 32 个线程访问地址连续的 32 个元素时，硬件把这些请求合并成最少的几个内存事务（transactions），一次就把一整段数据取回。** 反之，如果线程访问地址分散（跨步、转置），硬件要发很多个事务，带宽利用率急剧下降。

举例：一个 warp 读 `float A[i]`，若 `i` 随 `threadIdx.x` 连续（`A[blockIdx.x*blockDim.x + threadIdx.x]`），则 32 个 `float` = 128 字节恰好是几段缓存行，一次事务搞定；若线程读 `A[i*1024]`，32 个线程访问相距 4 KB 的地址，需要 32 个独立事务，带宽浪费近一个数量级。<span class="marginnote">这就是上一篇「让线程布局匹配数据布局」的硬件原因：`threadIdx.x` 当数据下标、而不是当「第二个维度」时，warp 的访问自动变成合并的。GPU 以 32 字节为最小扇区（sector）粒度读写 DRAM。</span>

## 3 公式解析：需要多少并行度才能喂饱带宽

合并访问解决「一次取多少」，还有一个问题：「要同时在途多少数据」才能让带宽不被延迟拖垮。这里用**利特尔定律（Little's law）**：

$$
\text{Bytes in flight} = \text{Bandwidth} \times \text{Latency}
$$

拆解这条公式：

- **$\text{Bandwidth}$**：显存带宽，如 H100 约 $3.35 \times 10^{12}$ 字节/秒。
- **$\text{Latency}$**：一次全局访问的往返时间。若延迟 800 个周期、GPU 主频 1.5 GHz，则 $\text{Latency} = 800 / (1.5 \times 10^9) \approx 533$ 纳秒 $= 5.33 \times 10^{-7}$ 秒。
- **$\text{Bytes in flight}$**：为了不让 DRAM 空闲，必须「同时在路上」的数据量。

代入 H100 的数值：$3.35 \times 10^{12} \times 5.33 \times 10^{-7} \approx 1.8$ MB。**这意味着要喂饱 H100 的带宽，系统里必须同时有约 1.8 MB 的读请求在途。**

**结论：单个 warp 一次只取 128 字节，远不够。你需要很多很多 warp 同时都在发请求**——这正是「占用率/延迟隐藏」的量化起点（下一篇专题讲）。带宽是河，延迟是桥；要让河满流，桥上必须排满车。

## 4 共享内存：程序员手动管理的缓存

**共享内存（shared memory）** 是每个 SM 上一块片上 SRAM，一个 block 内的线程可以读写它，速度比全局内存快一个数量级，延迟约 20–30 周期。

共享内存的典型用途是**数据复用**：当相邻线程反复读同一个数据块（比如图像卷积的权重窗口、矩阵分块），先把这块数据从慢速全局内存加载进共享内存，再让所有线程从共享内存读——一次全局访问换回几十次快速访问。

```c
__shared__ float tile[TILE_W][TILE_H];   // 声明共享内存数组
// 每个线程协作把全局数据载入 tile，然后 __syncthreads()，再从 tile 读
```

但共享内存不是免费的午餐：它有**容量上限**（每 SM 几十到两百多 KB）、需要 `__syncthreads()` 同步，还有一个著名的坑——**bank conflict**，专门留给《共享内存与 bank conflict、同步原语》一篇深入。<span class="marginnote">共享内存的设计哲学与 CPU L1 缓存完全不同：CPU 的 L1 是硬件自动管理、程序员看不见；GPU 的共享内存是软件显式管理、程序员说了算。这既是灵活性，也是责任。</span>

## 5 常量内存与纹理内存：两个特化缓存

**常量内存（constant memory）**：64 KB，全体线程只读。它最妙的特性是**广播（broadcast）**：当 warp 内所有线程读同一个常量地址时，硬件把值一次广播给全部 32 个线程，成本几乎为零。因此它特别适合存「所有线程都一样的参数」——比如卷积核、物理常量、矩阵的标量系数。PMPP 第 7 章用它做卷积优化，就是这个道理。

**纹理内存（texture memory）**：原本为图形采样设计，通过纹理缓存（texture cache）提供优良的**空间局部性**——处理图像、网格这类「相邻数据一起用」的场景时，命中率极高。它还内置了硬件插值、越界钳制等图形能力，在通用计算里主要用于「2D 空间局部访问」。<span class="marginnote">一句话区分：常量内存适合「warp 内全部线程读同一个值」（广播），纹理内存适合「warp 内线程读相邻的多个值」（空间局部）。两者都用缓存，但命中的访问模式完全不同。</span>

## 6 内存访问模式的体检清单

把上面的原则整理成一份自查清单，写 kernel 时可以逐条过：

- **全局内存**：让 `threadIdx.x` 直接对应连续数据下标，保证合并访问；避免跨步、转置访问。
- **尽量复用**：重复读的数据先进共享内存，而不是反复访问全局内存。
- **只读且全体同值**：放常量内存，吃广播。
- **只读且空间局部**：放纹理内存（或 `__ldg` 走只读数据缓存）。
- **寄存器优先**：单线程循环内的临时量编译器会自动放寄存器，别手动塞进共享内存。

**性能不是玄学，是一笔笔「访问模式」的账。** 掌握了合并访问、复用与广播，就已经解决了 GPU 优化的大部分问题——后面的《性能分析与调优》一篇会用 Roofline 把这些账算得更系统。

## 7 合并访问的量化算例：128 字节 vs 16 KB

把合并访问的收益算成数字，才记得牢。设一个 warp（32 线程）要读 `float` 数组，每线程一个元素：

- **合并访问**：32 个 `float` 恰好 128 字节，落在 1–2 个 128 字节缓存行（或 4 个 32 字节扇区）里——硬件发 **1 批**内存事务就取回全部数据，扇区全部用上。
- **跨步访问（步长 1024）**：32 个线程的地址相距 4 KB，覆盖约 1 MB 的地址空间，却只用了其中 128 字节——硬件要发 **32 批**事务，每批都白白搬了没用到的数据。

把两种访问代入有效带宽公式：

$$
\text{BW}_{\text{eff}} = \frac{\text{实际传输的有用字节}}{\text{总时间}}
$$

- 合并时「有用字节 ≈ 总传输字节」，效率接近 100%。
- 跨步时总传输是「有用字节 × 32」，有效带宽跌到约 3%。

**这就是「合并访问 = 免费的带宽」的量化含义：同样是正确代码，访问模式不同，性能差一个数量级。** 对 GPU 而言，「内存带宽利用率」不是玄学，而是「一个 warp 一次访问覆盖了多少有用数据」的算术题。PMPP 第 5 章给出一组实测表证明这一点：相同逻辑的 kernel，仅因转置或跨步访问，带宽可以从接近峰值掉到个位数百分比。

**结论一句话：把数据按线程访问顺序排好，就是最廉价的优化。** 这不是风格建议，而是从「128 字节 vs 1 MB」这笔账里算出来的——本专题后面《性能分析与调优》篇，还会把「如何判断是不是带宽在卡」做成系统的 Roofline 方法。

## 8 小结

- 内存层次从快到慢：**寄存器 → 共享内存 → 常量/纹理缓存 → 全局内存**；容量越大越慢。
- **合并访问**是 GPU 带宽的命脉：warp 内连续地址访问被合并成最少事务。
- 利特尔定律 $\text{Bytes in flight} = \text{Bandwidth} \times \text{Latency}$：喂饱 H100 需要约 1.8 MB 数据在途，所以需要海量并行。
- 共享内存是**程序员手动管理**的片上缓存，适合数据复用，但有容量与同步限制。
- 常量内存吃「全 warp 同值广播」，纹理内存吃「空间局部」。
