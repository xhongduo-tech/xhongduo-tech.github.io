## 为什么从图形管线开始

本专题从「GPU 简史」开篇，那里提到 GPU 的老本行是图形渲染。到了最后一篇，我们回到图形本身——但它已不是当年的图形：今天的 GPU 把图形管线、通用计算（CUDA）、矩阵运算（Tensor Core）、光线追踪（RT Core）整合在同一颗芯片上。**理解图形管线，是理解这颗芯片完整版图的最后一块拼图。**

这一篇以 Hennessy 与 Patterson《量化研究方法》第 4 章（Data-Level Parallelism in Vector, SIMD, and GPU Architectures）为对标：该章正是从「为什么 GPU 用来做图形」讲起，再延伸到通用计算。理解了图形管线，也就理解了 SIMT 与吞吐哲学最初的服务对象。<span class="marginnote">一个容易被忽略的事实：<strong>没有图形，就没有今天的 CUDA</strong>。GPU 的「数千个执行单元 + 海量线程 + 吞吐导向」，全部为「每秒渲染几百万三角形」而生；GPGPU 只是把这套现成的吞吐机器借给了通用计算。所以图形管线不是「过时话题」，而是 GPU 架构的根。</span>

## 1 图形管线：一幅画面的诞生流水线

把「一个 3D 场景变成屏幕上的一幅画面」拆成流水线，就是**图形管线（graphics pipeline）**，大致四个阶段：

1. **顶点处理（vertex processing）**：对每个三角形顶点做变换——把世界坐标变到屏幕坐标，程序员可编程（顶点着色器）。
2. **光栅化（rasterization）**：把三角形「填」成屏幕上的像素集合（片段，fragment）。这一步由固定硬件完成，速度极快。
3. **片段处理（fragment processing）**：对每个覆盖的像素计算颜色（光照、纹理采样），程序员可编程（片段着色器）。
4. **输出合并（blending）**：把片段颜色与已有帧缓冲合并（深度测试、透明度混合），写入屏幕。

流水线的每个阶段都在处理**大量独立的小任务**——几百万顶点、几亿像素——这正是 SIMT 吞吐架构的完美形状：**一个线程束处理一批三角形/一批像素，天然数据并行。**<span class="marginnote">Hennessy 与 Patterson 在第 4 章用「数据级并行」的框架看图形管线：顶点、像素、纹理采样全都是「对海量同构数据做同一套运算」——这是 GPU 所有并行性的原始来源，也解释了为什么 GPU 的指令集天生适合 SIMT。</span>

## 2 光栅化：从三角形到像素

**光栅化（rasterization）** 是图形管线的心脏：它决定「这个三角形覆盖了哪些像素」。几何上，一个三角形是三个顶点围成的平面区域；屏幕上覆盖它的像素，就是与三角形相交的所有像素中心。

光栅化硬件要做的是：对每个三角形，找到它在屏幕上的包围盒，逐像素判断「这个像素中心在不在三角形内」，在则生成一个**片段**，交给片段着色器算颜色。这个「在不在三角形内」的判断，本质是一组简单的边缘函数（叉积符号）测试——**计算量巨大但彼此完全独立**，于是交给海量执行单元并行。

**关键认知：光栅化是「天生并行」的典范。** 它不需要任何跨像素的共享状态，每个像素算自己的，这就是 GPU 吞吐架构的原始训练场——从光栅化到 SIMT，只有一步之遥。<span class="marginnote">这里可以回看《SIMT 执行模型与硬件层次》：GPU 里「一个线程处理一个像素」「32 个线程一个 warp 覆盖 32 个相邻像素」，最早的 warp 调度就是为这种「像素并行」设计的。CUDA 只是把同一套并行机器借给了别的任务。</span>

（现代 GPU 的光栅化器每周期能处理多个三角形，具体吞吐是硬件常量——你只需记住：**图形管线的每个阶段都在「海量同构任务」上做流水，这就是 GPU 吞吐架构的原始训练场**。）

## 3 公式解析：透视投影的除法

顶点处理里最核心的数学是**透视投影（perspective projection）**：把 3D 点映射到 2D 屏幕，近大远小。它的灵魂是**透视除法**：

$$
x_{\text{ndc}} = \frac{f \cdot x_c}{z_c}, \qquad y_{\text{ndc}} = \frac{f \cdot y_c}{z_c}
$$

逐项拆解：

- **$(x_c, y_c, z_c)$**：顶点在**相机坐标系**里的坐标，相机看向 $-z$ 方向。
- **$f$（焦距）**：与视野角相关的常数——视野越窄，$f$ 越大，物体看起来越大。
- **$x_{\text{ndc}}, y_{\text{ndc}}$**：归一化设备坐标（NDC），$z_c$ 越大的点（离相机越远），$f \cdot x_c / z_c$ 越小——**同一根柱子，远处投在屏幕上的位置更靠中间、更小**，这就是「近大远小」的数学来源。
- **除以 $z_c$**：这是透视除法，把「距离」变成「缩放因子」，是图形学一切透视效果的根。

顶点着色器做的，正是把这条投影公式（与平移旋转矩阵一起）应用到每个顶点上——又一次「对海量同构数据做同一套运算」，SIMT 顺手就把它并行化了。**一条投影公式 + 海量并行执行单元，就是 GPU 图形学的全部起点。**

## 4 隐藏面消除：深度缓冲

画出来的三角形有前后之分：远处的三角形被近处的挡住，不该画出来。GPU 用**深度缓冲（z-buffer）** 解决：每个像素存一个「当前最近深度值」，新的片段只有深度更小（更近）才覆盖，否则丢弃。

深度测试是**像素级并行的**——每个像素独立比较自己的深度——再次完美匹配 SIMT。这套「每像素一个状态 + 独立判断」的硬件，后来也演化出通用计算里的一切「原子操作」思想：z-buffer 就是最早的大规模「读-比较-写」并行原语。<span class="marginnote">值得注意：光栅化 + 深度缓冲这套「确定性」渲染流程，与 CUDA 里「每线程处理一个输出元素 + 越界保护」几乎是同一设计模式的两种表述——你已经在《CUDA 编程模型》篇见过它一次了。</span>

补一个规模感：现代游戏画面动辄 1080p 或 4K——1920×1080 约 207 万像素，4K 约 830 万。每个像素每帧都要做一次深度测试，**这意味着 GPU 每帧都要处理几百万次「比较并决定是否覆盖」的独立判断**。这套「海量同构判断」的规模，正是 SIMT 吞吐架构的天然主场，也解释了 GPU 为何从诞生起就选择了「海量执行单元」路线。

## 5 RT Core：让光线追踪跑进实时

光栅化快，但有天花板：它难以表现镜面反射、软阴影、全局光照这类「光线在场景里弹来弹去」的效果。**光线追踪（ray tracing）** 从原理上更真实——向每个像素射出一条光线，让它与场景所有三角形求交，得到真实的光照——但求交运算量巨大，历史上只能离线渲染电影（皮克斯、工业光魔）。

2018 年，NVIDIA **Turing** 架构引入 **RT Core（光线追踪核心）**：一个专门做「光线-三角形求交」与 **BVH（包围体层次结构）加速遍历** 的硬件单元，把求交从通用执行的数十条指令压缩进专用管线。此后每代增强：Ampere、Hopper 到 Blackwell，配合 Tensor Core 做**降噪（denoising）**——RT Core 负责「算对」，Tensor Core 负责「去噪」，实时光线追踪才成为可能。<span class="marginnote">RT Core 与 Tensor Core 是同一套「领域专用」哲学的两次落地：《Tensor Core 与矩阵运算》篇讲过 GPU 为矩阵乘法长出专用单元；RT Core 就是 GPU 为「光线-三角形求交」长出的专用单元。Hennessy 与 Patterson 在第 4 章讨论 GPU 时，正是把「专用 vs 通用」作为分析框架。</span>

### BVH：让求交不必遍历所有三角形

光线求交的朴素做法是「对每个三角形做一次求交」，场景有上百万三角形时，一条光线要试百万次——不可行。**BVH（Bounding Volume Hierarchy，包围体层次结构）** 把三角形按空间组织成一棵树：每个节点是一个包围盒（长方体或球），叶子是三角形。

求交时从树根开始：光线与某节点包围盒不相交，整棵子树直接跳过；相交则进入孩子继续试。**平均把「每条光线要测的三角形」从百万级压到几十个**——这是实时光线追踪可行的关键，也是 RT Core 在硬件上加速的那件事：它把「光线 vs 包围盒」与「光线 vs 三角形」做成专用管线，比通用指令快一个数量级。

**辨析｜易错点：** BVH 是「数据结构」不是「硬件」——它由驱动程序或引擎构建（每次场景变化要重建），RT Core 加速的是「在已建好的 BVH 上遍历求交」。所以「光线追踪快不快」取决于两件事：BVH 建得好不好 + RT Core 用得好不好，前者仍是一门软件学问，与《性能分析与调优》篇「先测量、再对症」的思路完全一致。

（如果你好奇「光栅化与光线追踪谁会赢」：二者正在共存——光栅化渲染场景主体、RT Core 补反射/阴影/全局光照的「混合渲染」已成主流，这正是图形管线「硬件专用化」继续演进的当下形态。）

## 6 图形与计算的统一：一颗芯片的完整版图

把本专题的全部内容拼起来，一颗现代 GPU 的完整版图是这样的：

- **CUDA 核心（SM）**：通用吞吐计算，跑 CUDA 程序、顶点/片段着色器。
- **Tensor Core**：矩阵乘法专用，喂大模型训练与推理。
- **RT Core**：光线求交专用，喂实时图形与物理模拟。
- **光栅化硬件 + 纹理单元**：图形管线的固定功能部件。

而它们共享同一套 SIMT 基础、同一片显存、同一批 SM。**图形与计算在硬件上已经不分家**——这也是为什么「GPU 简史」里 G80 的统一着色器是决定性的一步：它让「画图」和「计算」共用执行单元，才有了后来的 CUDA、Tensor Core 与 RT Core。<span class="marginnote">对「从极限到大模型」主线，这条版图的意义是：大模型训练用 Tensor Core，推理降噪可能用 RT Core 的思路，而控制这一切的仍是 SIMT 通用计算。GPU 是「通用 + 专用」混合的集大成者——本专题十二篇，讲的就是这一颗芯片的完整故事。</span>

## 7 纹理单元与采样器：图形的另一块专用硬件

光栅化与 RT Core 之外，GPU 还有一块历史悠久的专用硬件——**纹理单元（texture unit）**。它服务图形里最频繁的操作：**纹理采样**——把一张图片（纹理贴图）按 UV 坐标取颜色。

纹理单元做三件通用执行单元不擅长的事：

- **双线性插值**：UV 坐标几乎从不对齐像素中心，纹理单元用硬件算「周围 4 个纹素加权平均」，一次完成；用通用代码写，要好几条乘加指令。
- **Mipmap 自动选层**：远处的表面纹理细节应当变小，纹理单元按「纹理缩小的程度」自动选合适的分辨率层级（mipmap），避免远处的闪烁（混叠）——图形算法被固化成硬件。
- **越界处理**：纹理坐标可能超出图像范围，硬件按「钳制 / 重复 / 镜像」等模式自动处理。

**对通用计算的意义**：纹理内存（见《内存层次》篇）正是借了纹理单元与它的缓存——那篇讲的「空间局部性优秀」，根源就是纹理单元为「相邻像素采相邻纹素」这一图形负载而设计。所以「纹理内存适合图像、网格类数据」不是巧合，而是图形硬件遗产的直接继承。

**辨析｜易错点：** 现代 CUDA 里「走纹理单元」与「走通用只读缓存（`__ldg`）」各有适用场景——`__ldg` 让只读数据走缓存而不必动用纹理坐标系；纹理的插值 / 越界能力对「网格重采样」这类任务仍是杀手锏。**判断标准还是那句老话：数据访问的模式像不像「图像采样」。** 对通用计算而言，纹理单元就是「图形硬件送给 CUDA 的一份礼物」——它提醒我们，GPU 的每一次性能红利，往往都来自一块为图形而生的专用硬件。

（至此，本专题十二篇走完了 GPU 的完整旅程：从图形管线的吞吐基因，到 SIMT、CUDA 编程模型、内存层次、占用率、共享内存、Tensor Core、流、统一内存、性能调优、多 GPU，再回到图形——一条从「图形专用」出发又回到「图形专用硬件」的闭环。）

## 8 小结（全专题收束）

- 图形管线四阶段：**顶点处理 → 光栅化 → 片段处理 → 输出合并**，每阶段都是海量独立小任务的 SIMT 并行。
- **光栅化**把三角形变成像素，是「天生并行」的典范；**深度缓冲**用像素级并行解决隐藏面。
- **透视投影**的灵魂是透视除法 $x_{ndc} = f x_c / z_c$——近大远小的数学根。
- **RT Core** 是光线-三角形求交的专用硬件，让实时光线追踪成为可能；配合 Tensor Core 降噪。
- 现代 GPU = **SM 通用计算 + Tensor Core 矩阵 + RT Core 求交 + 光栅化硬件**，共享 SIMT 基础与显存。
