## 为什么从 SIMT 开始

上一篇讲清了 GPU 的「吞吐导向」哲学：为整体吞吐优化，而不是为单点延迟优化。但这套哲学落到硬件上，具体长什么样？**SIMT 就是答案。** 它是 GPU 执行模型的核心，决定了「一行 `kernel` 代码到底是怎么被几万个线程跑起来的」。

理解 SIMT，是理解后面一切——CUDA 编程模型、内存层次、占用率、bank conflict——的前提。它是 GPU 世界的「牛顿定律」：你在编程模型里看到的线程、块、栅栏，最终都要翻译成 SIMT 硬件上的一次次 warp 执行。<span class="marginnote">PMPP 第 4 章 "Compute Architecture and Scheduling" 专门讲解 GPU 的计算架构与调度机制，本篇是其主线浓缩；NVIDIA《CUDA C++ Programming Guide》§4.1 的 "SIMT Architecture" 一节给出官方定义。</span>

## 1 SIMT：单指令，多线程

**SIMT（Single Instruction, Multiple Threads，单指令多线程）** 是 GPU 的基本执行模型。它的名字与经典的 **SIMD（Single Instruction, Multiple Data，单指令多数据）** 只差一个字母，却有关键差别。

回忆经典的 SIMD：CPU 一次把一条指令施加到一批数据上，比如一条 `addps` 指令同时计算四个单精度浮点的加法，数据放在向量寄存器里，程序员（或编译器）负责把数据凑齐。SIMD 的问题是**僵硬**：四个通道必须一起动，遇到分支要么全部执行要么全部跳过。

SIMT 换了个思路：**让一个「线程束」共享一条指令流，但每个线程拥有自己独立的寄存器、独立的程序计数器（在支持独立线程调度后）与独立的执行路径掩码。** 于是 GPU 程序员写的是「单个线程的逻辑」，而硬件把这个逻辑复制到一群线程上同时跑——**并行是硬件替你做的，不是你在代码里显式操控的。**<span class="marginnote">一句话记忆：SIMD 是「数据并行、指令级锁步」；SIMT 是「线程并行、指令级共享」。你写一个线程的行为，硬件替你跑一堆线程——这正是 CUDA「写一个、跑一万个」的根源。</span>

## 2 硬件层次：从 thread 到 SM

SIMT 的思想落实在一整套硬件层次上。从最底层的执行单元往上看：

- **线程（thread）**：编程模型里最小的执行单位，拥有自己的寄存器与局部状态。
- **warp（线程束）**：硬件实际调度的最小单位，固定 **32 个线程**。
- **线程块（block / CTA）**：程序员组织线程的分组，一个块在同一个 **SM** 上执行。
- **SM（Streaming Multiprocessor，流式多处理器）**：GPU 的核心计算单元，负责调度与执行 warp。一个 GPU 上有几十到上百个 SM。
- **grid（网格）**：一次 kernel 启动的全体线程，分布在所有 SM 上。

现代 NVIDIA GPU（如 A100、H100）的每个 SM 内部又分成 **4 个处理子分区（processing block / sub-partition）**，每个子分区拥有自己独立的 **warp 调度器** 与执行管线。<span class="marginnote">A100 的每个 SM 有 4 个子分区，每个子分区一套调度器 + 执行单元；所以一个 SM 可以同时从多个 warp 取指令。子分区内部还共享寄存器堆（A100 每 SM 65536 个 32 位寄存器）与共享内存。</span>

**关键点：硬件按 warp 执行，但程序员按 thread 思考。** 这一层「翻译」由调度器完成——这就是 SIMT 模型存在的意义。

## 3 warp 调度：如何填满执行单元

如果只把 SIMT 理解为「一堆线程共享指令」，还远远不够。真正的难点在于**调度**：SM 上同时有成千上万个活跃线程，它们分属不同的 warp，而执行单元只有那么几套。warp 调度器做的事，就是**在每一拍挑一个「准备好」的 warp 发射一条指令**。

这里的「准备好」很关键。一个 warp 在等待数据（比如等显存返回）时，就是「没准备好」；调度器此刻直接转向另一个没在等待的 warp，发射它的指令。<span class="marginnote">这就是 GPU 隐藏延迟的经典机制：<strong>不是把延迟变短，而是用其他 warp 的运算把等待时间填满</strong>。 下一篇讲内存层次、再下一篇讲占用率时，这个「用并行填等待」的思想会反复出现。</span>

调度器的效率直接决定执行单元的利用率。假设一个子分区每周期能发射 1 条指令，SM 上若只有 4 个 warp 可调度，一旦其中一个在等内存，调度器可能无指令可发，执行单元就空转了。**活跃 warp 数量越足，调度器越能一直发射，吞吐越高**——这正是后文「占用率」要量化的东西。

## 4 公式解析：warp 的 SIMD 效率

当一个 warp 执行一条指令时，并非每个线程都一定有用。**当 warp 内出现分歧（divergence，分支分岔），部分线程走 A 路径、部分线程走 B 路径，硬件只能先执行 A 路径（B 路径线程被掩码禁掉），再执行 B 路径（A 路径线程被掩码禁掉）**——两条路径串行化，浪费了等待的那一半通道。

我们定义 warp 的**指令效率（SIMD efficiency）** 为：

$$
E = \frac{N_{\text{active}}}{N_{\text{warp}}} = \frac{\text{实际参与执行的线程数}}{32}
$$

拆解这条公式：

- **$N_{\text{warp}}$**：warp 的固定规模，32 个线程。这是硬件定死的，一个 warp 永远 32 条通道。
- **$N_{\text{active}}$**：这条指令执行时实际处于激活状态的线程数。无分歧时 $N_{\text{active}} = 32$，效率 100%。
- **分歧最坏情况**：两个线程各走一路，则 $E = 2/32 = 6.25\%$——两条指令各只用了 1/32 的通道，指令资源被极大浪费。

**结论：分支越均匀地切碎 warp，SIMD 效率越低。** 理想的写法是让 warp 内线程尽量走同一路径——比如把分支放在块边界而不是 warp 内部，这正是 PMPP 第 4 章反复强调的「让分歧发生在 warp 之间，而不是 warp 之内」。<span class="marginnote">注意：现代 GPU（Volta 及以后）支持独立线程调度，部分收敛了分歧的代价，但「串行化执行分岔路径」的基本模型仍然成立，只是开销与调度细节更复杂——初学阶段按经典 SIMT 模型理解即可。</span>

## 5 分歧、掩码与收敛

理解了 SIMD 效率，就能理解 GPU 上两个著名的概念：**掩码（mask）** 与**收敛（convergence）**。

每个 warp 在硬件上都带一个 **激活掩码**，32 位，每一位代表一个线程是否在当前路径上。执行分支指令时，调度器更新掩码：走 A 路径的线程位置 1，其余置 0，然后发射 A 路径指令；再翻转让 B 路径线程激活，发射 B 路径指令。<span class="marginnote">掩码机制解释了为什么「在 GPU 上写 `if (threadIdx.x % 2 == 0)` 会比在 CPU 上贵很多」：CPU 的分支预测是「猜一次」，GPU 的分支是「把两条路径都执行一遍」。</span>

这带来一个实用的编程铁律：**让 warp 内的线程数据访问与分支尽量一致。** 例如处理数组时，让 `threadIdx.x` 与数组下标对齐，而不是做转置式访问；把「少数特殊情况」放到独立的 kernel 或独立的块里处理。这些建议不是风格偏好，而是 SIMT 硬件效率的直接推论。

## 6 从 SIMT 到 CUDA 编程模型

SIMT 是硬件的语言，CUDA 是程序员的语言。二者之间靠一条精心设计的「翻译桥」相连：**grid → 一系列块 → 一系列 warp → 32 个线程。** 程序员声明 grid 与 block 的大小，编译器与运行时把它切分成 warp，再交给调度器。

这套层次带来的第一个实用结论是：**block 大小最好选成 32 的倍数**（如 128、256），这样 block 被切分时不会产生「尾部不满 32 线程」的残缺 warp；每多一个残缺 warp，就多一份 SIMD 效率损失。<span class="marginnote">实操中 blockDim 常见取值 128 / 256 / 512：太小则每个 SM 调度负担重，太大则占用率受限——量化的权衡留到《占用率与延迟隐藏》一篇。</span>理解了 SIMT，下一篇走进 CUDA 编程模型时，你看到的 grid/block/thread 就不再是三个名词，而是一套被硬件逼出来的组织方式。

## 7 warp 内通信：shuffle 原语

「warp 内线程通信」是 SIMT 里一个特别的特权：warp 的 32 个线程本来就同时执行，硬件天然知道它们之间的关系，所以它们之间交换数据不必经过共享内存或显存，而可以用专门的 **shuffle（洗牌）指令**。

`__shfl_sync(mask, var, srcLane)` 让每个线程取到「编号 srcLane 的那个线程的 var 值」：

```c
float v = value[threadIdx.x];
float w = __shfl_sync(0xffffffff, v, (threadIdx.x + 1) % 32);  // 拿到下一个线程的值
```

这套指令能干什么？三个最常见用途：

- **warp 内归约**：用 `__shfl_down_sync` 逐轮折叠，一个 warp 的 32 个线程在几条指令内完成求和——不占共享内存、没有 bank conflict、无需块级同步。
- **`__ballot_sync`**：把 32 个线程的谓词打包成一个 32 位整数，是「全 warp 有多少线程满足条件」的最快问法。
- **`__syncwarp()`**：只同步一个 warp（比 `__syncthreads()` 轻得多），配合 shuffle 使用。

<strong>辨析｜易错点：</strong> shuffle 只在「同一个 warp 内」有效——`srcLane` 是 warp 内相对编号（0–31），不是全局线程号；跨 warp 换数据仍要走共享内存或显存。**mask 参数**（`0xffffffff` = 32 位全 1）必须包含全部参与线程，否则行为未定义。<span class="marginnote">shuffle 是「协作组」思想在硬件层的化身（见《统一内存与新特性》篇）：它把「线程间通信」从「写内存 + 同步」升级为「一条指令」，是 PMPP 第 10 章归约优化的硬件基础。</span>

为什么值得单独一提？因为它再次说明了 SIMT 的本质：**warp 不只是「并行的 32 个线程」，更是「同步前进的 32 个伙伴」**——硬件给了它们低成本通信的特权。会用这条特权（shuffle、ballot）的代码，往往比「先写共享内存再同步」的实现又快又省，也是现代归约、扫描、排序库（CUB、Thrust）的内部武器。

### Volta 后的独立线程调度

经典 SIMT 模型里，一个 warp 共享一个程序计数器，分歧路径靠掩码串行——这是本专题一直沿用的模型。Volta 架构（2017）起，GPU 引入了**独立线程调度（independent thread scheduling）**：每个线程拥有自己的程序计数与调度状态，分歧路径可以「分别前进、自动收敛」，不再强制整束锁步。

它的意义：让 warp 内线程在遇到分支后能独立推进，减少「等兄弟路径」的空转；代价是调度逻辑更复杂、对编译器要求更高。**初学阶段继续按经典 SIMT 模型理解即可**——独立线程调度是「掩码串行」的硬件改良，不是替换；本专题关于分歧、收敛、掩码的所有结论，在大方向上依然成立。

## 8 小结

- **SIMT**：单指令多线程，硬件把一条指令流复制给 32 线程的 warp，各线程独立寄存器、独立掩码。
- 硬件层次：**thread → warp（32）→ block（CTA）→ SM → grid**；调度的最小单位是 **warp**。
- 每个 SM 内分成若干子分区，各配 warp 调度器，**用「切走等待中的 warp」来隐藏延迟**。
- warp 出现分歧时两条路径**串行执行**，SIMD 效率 $E = N_{active}/32$ 随之下降。
- 掩码机制是分歧代价的硬件根源；**让 warp 内线程路径一致、block 取 32 的倍数**是两条实用铁律。
