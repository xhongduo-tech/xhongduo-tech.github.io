## 为什么从占用率开始

上一篇文章用利特尔定律算了一笔账：要喂饱 H100 的显存带宽，需要约 1.8 MB 数据同时「在途」。而单个 warp 一次只能发 128 字节的请求——**答案只能是：让海量 warp 同时都在等数据、同时都在发请求。**

「海量 warp」这个词，量化出来就是**占用率（occupancy）**。它是 GPU 性能分析里最重要的单一指标：不高，延迟藏不住；太高，又往往伴随资源浪费。理解占用率，是把前两篇（SIMT、内存层次）连成一条性能链的最后一环。<span class="marginnote">PMPP 第 6 章 "Performance Considerations" 用一整章讲并行度、占用率与性能的关系，并给出「每个 SM 能容纳多少活跃线程」的量化框架；官方数值见《CUDA C++ Programming Guide》§19 Occupancy。</span>

## 1 延迟隐藏：GPU 用并行对抗延迟

CPU 对抗延迟靠**猜**（分支预测、乱序执行）和**缓存**（把常用数据放近处）；GPU 对抗延迟靠**换**——**当一个 warp 在等内存时，调度器立刻切到另一个不等的 warp。**

这就是**延迟隐藏（latency hiding）**：延迟本身没有变短，但「等待」不再浪费执行单元。它的前提是**现场里必须备着足够多「可调度」的 warp**。如果 SM 上只有 1 个 warp 在跑，它一等内存，执行单元就空转几百个周期；如果有 48 个 warp 轮流登场，执行单元几乎永远有指令可发。<span class="marginnote">一个直观类比：餐厅只有 1 张桌子时，一桌人等菜、其余全空；有 48 张桌子时，厨房永远在出菜。GPU 用「桌位（warp 槽位）」换「厨房（执行单元）不歇火」。</span>

## 2 占用率的定义

**占用率（occupancy）** 定义为：**SM 上实际运行的活跃 warp 数占 SM 最大可容纳 warp 数的比例。**

$$
\text{Occupancy} = \frac{\text{活跃 warp 数}}{\text{SM 最大 warp 数}}
$$

- 对大多数现代 NVIDIA GPU（包括 A100、H100），**每个 SM 最多 2048 个线程 = 64 个 warp**，即 $\text{maxWarps} = 64$。
- 因此，若某个 kernel 在每 SM 上同时运行 32 个 warp，占用率就是 $32/64 = 50\%$；若能挤进 64 个 warp，占用率 100%。

**占用率 100% 意味着延迟隐藏的潜力最大**——无论哪个 warp 在等数据，调度器都还有 63 个候补。但注意是「潜力」：具体能不能藏住延迟，还取决于内存访问频率与计算强度，这是后面《性能分析与调优》篇 Roofline 的战场。

## 3 公式解析：谁在限制占用率

占用率不是程序员直接设置的，而是被四种资源「掐」出来的。SM 上活跃线程数 = 每种资源分别能容纳的线程数的最小值：

$$
\text{activeThreads} = \min\left(
\frac{R_{\text{SM}}}{r_{\text{thread}}},\,
\frac{S_{\text{SM}}}{s_{\text{block}}},\,
\frac{B_{\text{SM}}}{1},\,
\frac{W_{\text{SM}} \times 32}{32}
\right) \times \text{blockDim}
$$

逐项拆解：

- **$\frac{R_{\text{SM}}}{r_{\text{thread}}}$（寄存器）**：$R_{SM}$ 是每 SM 寄存器总数（A100 为 65536 个 32 位寄存器），$r_{thread}$ 是每线程占用寄存器数。线程用寄存器越多，能驻留的线程越少。
- **$\frac{S_{\text{SM}}}{s_{\text{block}}}$（共享内存）**：$S_{SM}$ 是每 SM 共享内存（可配置到 164 KB 级别），$s_{block}$ 是每个 block 声明占用的共享内存。
- **$\frac{B_{\text{SM}}}{1}$（block 数上限）**：每 SM 最多驻留的 block 数有硬上限（如 32 或 16）。block 太大反而让上限先到。
- **$\frac{W_{\text{SM}} \times 32}{32}$（线程数上限）**：$W_{SM}=64$ warp 即 2048 线程，这是天花板。

**占用的逻辑是短板效应：四个瓶子，最矮的决定了水位。** 想提高占用率，就要找到当前最矮的那块板。

## 4 一个完整算例：寄存器怎么掐住占用率

假设 block 大小 256 线程，编译器给每个线程分配 40 个寄存器，A100 每 SM 65536 寄存器：

- 每 block 需要 $256 \times 40 = 10240$ 个寄存器。
- 每 SM 最多 $\lfloor 65536 / 10240 \rfloor = 6$ 个 block。
- 总活跃线程 $= 6 \times 256 = 1536$，占用率 $= 1536 / 2048 = 75\%$。

如果编译器只压到 32 个寄存器/线程：

- 每 block 需要 $256 \times 32 = 8192$ 个寄存器。
- 每 SM 最多 $\lfloor 65536 / 8192 \rfloor = 8$ 个 block。
- 总活跃线程 $= 8 \times 256 = 2048$，占用率 100%。

**同样是正确代码，占用率从 75% 提到 100%**——手段往往是 `__launch_bounds__(256, 8)` 之类的指令告诉编译器「8 个 block 是我的目标，寄存器别用超」，编译器会做寄存器重分配甚至溢出到局部内存。<span class="marginnote">⚠️ 辨析｜易错点：压寄存器不是白拿。压得太狠会让线程把临时数据「溢出」到局部内存（local memory，实际落在显存），用慢速访问换占用率，反而更慢。「占用率提升」与「单线程性能下降」之间有一个最佳点，必须用分析器实测，不能盲目压。</span>

## 5 占用率不是越高越好

这是新手最容易误解的一点。占用率 100% 不等于性能最好，原因有三：

- **尾部效应**：如果总线程数不是 SM 容量的整数倍，最后一批 block 只占了一半 SM，平均占用率掉下来——这时调整 block 大小让「整除」更顺，往往比盲目堆线程更有效。
- **资源换效率**：占用率高的代码往往把寄存器、共享内存压得很紧，单线程吞吐可能下降（见上面的溢出教训）。
- **计算受限时无所谓**：如果 kernel 是纯计算（计算强度高），执行单元本来就满载，此时多藏几个 warp 毫无收益——**内存受限时占用率是关键，计算受限时它不是瓶颈**，这个判定在《性能分析与调优》篇会给出正式工具（Roofline）。

**正确的用法：用占用率做第一轮筛子，再用实际吞吐做最终裁判。** NVIDIA 的 Nsight Compute 会把「占用率瓶颈」与「实际吞吐瓶颈」分开报告，正是为了让你别在非瓶颈上过度优化。

## 6 block 大小的选择：为什么没有银弹

「用多大 block 最合适」是新手问得最多的问题。诚实的答案：**没有固定最优，但有清晰的思考框架。**

先看硬件约束：block 大小必须是 warp（32）的倍数才不浪费——`blockDim = 100` 会产生 4 个 warp 中最后 1 个只有 4 个线程的残缺 warp，SIMD 效率打折扣。所以常见取值是 64、128、256、512。

再看三个方向的权衡：

- **block 太小（如 32–64）**：每 SM 能驻留的 block 数有上限（如 32 个），block 太小会撞「block 数上限」这块板，占用率上不去。
- **block 太大（如 1024）**：每 SM 线程数上限（2048）下只能装 2 个 block，若再叠加「每 block 用太多共享内存/寄存器」，会直接撞资源上限。
- **负载均衡**：block 是调度的最小单元，一个 block 跑完才让出 SM 上的「槽位」——block 太大时，若尾部若干 block 数据稀疏，尾部浪费更明显。

还有一个高级技巧叫 **grid-stride loop（网格跨步循环）**：让一个线程循环处理多个数据块，而不是「一个线程一个元素」。它的好处是解耦「问题规模」与「网格大小」——无论数据有多少，都能固定用一个「装满但不溢出」的网格，避免「网格太大导致每 SM 只剩几个线程」的尴尬，也让「改问题规模」不必重调网格。<span class="marginnote">实战经验：先从 256 起步（8 个 warp、4 个完整 warp 组，调度友好），再用 Nsight Compute 的 Occupancy 面板看「哪块板最矮」，按《性能分析与调优》篇的流程改——多数 kernel 在 128–512 之间能找到最佳点，盲目追求 100% 占用率往往适得其反。</span>

**一句话总结：block 大小是「资源短板」的函数，不是玄学。** 把占用率公式里那四块短板都算一遍，你就能预测哪个 block 大小会撞哪块板——剩下的交给 Nsight 验证，这正是本专题一贯的「先算账，再实测」作风。

### 一个实操工具：让硬件替你算短板

手推占用率公式容易出错。CUDA 提供 `cudaOccupancyMaxActiveBlocksPerMultiprocessor`：给定 block 大小与每线程资源占用，它直接返回「每 SM 最多几个 block」。用它做「block 大小扫描」（如 64/128/256/512 逐个查询），比手推快得多，也避免了「以为自己算对了」的错误。

另一个经验是：**不同 kernel 的最优 block 不同**——访存密集的 kernel 偏好更大 block（更多并行度藏延迟），计算密集的反而可能小 block 更好。所以「某个 block 大小好」只在特定 kernel 内成立，别跨 kernel 照搬。

## 7 小结

- **延迟隐藏**：warp 等内存时调度器切换，执行单元不空转；前提是 SM 上有足够多活跃 warp。
- **占用率** $= \frac{\text{活跃 warp 数}}{64}$（A100/H100 每 SM 上限 64 warp），反映延迟隐藏潜力。
- 占用率被**寄存器、共享内存、block 上限、线程上限**四块短板共同决定，取最小值。
- 提高占用率的常用手段是 `__launch_bounds__` 等编译器约束，但要警惕寄存器溢出换来的虚假提升。
- **占用率只是潜力的度量，不是性能本身**：计算受限场景、非整除的尾部效应都会让它「失真」，必须用 Nsight/Roofline 实测。
