## 为什么从共享内存开始

《内存层次》一篇把共享内存称为「程序员手动管理的缓存」——它快（比全局内存快一个数量级），但有容量、有同步、还有一个著名的陷阱：**bank conflict**。这一篇把这三件事讲透。

共享内存几乎是所有 GPU 优化手段的枢纽：卷积、矩阵乘法、归约、直方图，全都围绕它展开。而 **bank conflict** 是它最隐蔽的性能杀手——代码明明正确，性能却凭空慢几倍。学会它，等于拿到了 GPU 优化的「第二层钥匙」。<span class="marginnote">PMPP 第 5 章讲共享内存的硬件组织，第 9 章讲直方图时把「私有化 + 原子操作」玩到了极致；《CUDA C++ Programming Guide》§5.2.4 专门讲 bank conflict。本篇把两处知识合并。</span>

## 1 为什么需要共享内存：先解决「算得快」

回顾一下性能链条：全局内存延迟几百周期，靠并行隐藏；但很多算法里**同一个数据要被相邻线程反复读**——比如卷积核窗口、矩阵分块、归约的中间结果。每次都去全局内存读，就是一次次浪费几百周期。

共享内存的解法是**换**：一次把整块数据从全局内存读进共享内存（一次高延迟），然后所有线程从共享内存反复读（每次低延迟）。这就是「数据复用（data reuse）」。代价是**协作**：谁来读、谁在等、谁先写完，都要协调——于是同步原语登场。

## 2 硬件结构：32 个 bank

为什么共享内存能被 32 个线程「同时」访问？因为它的物理结构按 **bank（存储体）** 划分：**一个 warp 的 32 个线程，正好对应 32 个 bank，每个 bank 每次能供一个 4 字节访问。** 当 32 个线程同时访问共享内存时，硬件把它们对齐到 32 个 bank 上，理想情况下一个周期就能完成全部 32 个访问——这就是共享内存的「并行读写」。

地址到 bank 的映射简单而机械：**地址按 4 字节对齐，`bank = (地址 / 4) % 32`。** 换句话说，连续 32 个 4 字节地址恰好落在 32 个不同的 bank 上。<span class="marginnote">直觉：把 32 个 bank 想成 32 个独立的小抽屉，一次访问就是每个线程伸进一个抽屉取 4 字节。只要 32 个线程伸进的是 32 个不同的抽屉，这一拍就全完成了——这就是共享内存「宽带宽」的来源。</span>

## 3 bank conflict：撞了抽屉就要排队

**bank conflict（存储体冲突）** 的定义：**当一个 warp 内有两个或更多线程访问同一个 bank 的不同地址时，这些访问必须串行化——每个 bank 每拍只能服务一个地址。** 于是本来 1 拍完成的访问，变成 2 拍、3 拍……直到最拥挤的 bank 的线程数那么多拍。

看两个极端例子：

- **无冲突**：线程 i 访问 `s[i]`（连续 4 字节元素），32 个线程访问 32 个不同 bank，1 拍完成。
- **二路冲突**：线程 i 访问 `s[i * 2]`，`s[0]` 与 `s[32]` 都在 bank 0，`s[2]` 与 `s[34]` 都在 bank 1……每个 bank 被两个线程挤到，需要 2 拍。

**特别注意：所有线程读同一个地址（如 `s[5]`）不算冲突**——硬件会广播同一个字，一拍完成。<span class="marginnote">易错点辨析：bank conflict 指的是「同一 bank 的<strong>不同地址</strong>」。「同地址」是广播（免费），「不同 bank」是并行（免费），只有「同 bank 不同地址」才排队——三种情况要分清楚。</span>

## 4 公式解析：一次访问要几拍

把 bank conflict 量化成一个公式，用于估算共享内存访问的开销：

$$
T_{\text{access}} = \max_{b \in \{0,\ldots,31\}} \left( \text{访问 bank } b \text{ 的线程数} \right)
$$

拆解这条公式：

- **$b$**：bank 编号，0 到 31，由地址映射 $b = (\text{addr} / 4) \bmod 32$ 决定。
- **访问 bank $b$ 的线程数**：一个 warp 里恰好落入该 bank 的线程数。
- **取最大值**：所有 bank 并行服务，但最挤的那个 bank 决定总拍数——**短板效应**，与《占用率》篇的「四块短板」逻辑一脉相承。

代入例子：无冲突时每个 bank 至多 1 个线程，$T = 1$；二路冲突每个 bank 恰好 2 个，$T = 2$。**最坏情况 32 路冲突（所有线程挤同一 bank 的不同地址）$T = 32$，一次访问慢 32 倍。**

**结论：共享内存访问的开销 = 同一 bank 上最拥挤的线程数。** 优化的目标就是让这个最大值尽量回到 1。

## 5 经典技巧：填洞（padding）

bank conflict 最经典的解法是**填洞（padding）**。当行长度恰好是 32 的倍数时，二维数组的**同列相邻行**会映射到同一个 bank：

- `s[row][col]`，行宽 32 个 `float`：`s[0][7]` 与 `s[1][7]` 的地址差 `32 * 4 = 128` 字节，$128/4 \bmod 32 = 0$，**同 bank**！如果线程按列访问（跨行读同一列），就 32 路冲突。

解法是把每行多垫一个元素：`s[ROWS][33]`。这样行宽变成 33 个元素，行间地址差 $33 \times 4 = 132$ 字节，$132/4 \bmod 32 = 1$——**相邻行错开 1 个 bank，列访问瞬间无冲突。**

```c
__shared__ float s[ROWS][33];   // 33 = 32 + 1，垫一列
float v = s[row][col];          // 按列访问不再冲突
```

**代价只是每行浪费 1 个元素的容量，换来最多 32 倍的访问加速**——这笔账绝大多数时候划算。<span class="marginnote">其他常用手段还有：把数据重新排列成「线程访问步长为 1」的布局、用 `float4` 向量化访问、在归约/直方图场景里让每线程私有化一份再合并。核心永远只有一句话：<strong>让一个 warp 的 32 个访问散到 32 个不同 bank</strong>。</span>

## 6 同步原语：让协作变得正确

共享内存是「共享」的，共享就必然有**数据竞争**。CUDA 提供两组同步原语：

**第一组：块内屏障（barrier）**。`__syncthreads()` 让 block 内所有线程**等在同一个点**，全部到达后才放行。典型用法是「先协作写共享内存，同步，再读」：

```c
__shared__ float tile[32];
tile[threadIdx.x] = input[i];   // 各自写一块
__syncthreads();                // 全部写完再往下走
float v = tile[31 - threadIdx.x]; // 现在读别人写的数据是安全的
```

**没有 `__syncthreads()` 就去读别人刚写的共享内存，就是未定义行为**——比死锁更隐蔽，因为它偶尔能跑对。<span class="marginnote">⚠️ 辨析｜易错点：`__syncthreads()` 必须被 block 内<strong>所有线程</strong>执行到。如果它被放在 `if (threadIdx.x < 8)` 这种分支里，只有部分线程到达，其余线程永远不返回——程序直接挂死。所以 `__syncthreads()` 严禁放进会切分 warp 的分支。</span>

**第二组：原子操作（atomic）**。当多个线程要更新同一个全局/共享内存变量（如直方图计数 `count[bin]++`），普通赋值会丢更新。原子操作保证「读-改-写」不可分割：`atomicAdd(&count[bin], 1)` 让每个线程的累加都生效。PMPP 第 9 章的直方图正是「原子操作 + 私有化」的教科书：每线程先算自己的私有直方图（无竞争），最后再原子合并（竞争大大减少）。

## 7 把共享内存放进更大的画面

现在可以串起本专题的完整图景了：**SIMT 提供并行，内存层次决定去哪取数，共享内存让取数变快，同步原语保证取数正确，占用率保证藏延迟有资源。** 而这一切的量化工具（bank 拍数、占用率、有效带宽）最终都会汇入《性能分析与调优》篇的 Roofline，成为一张统一的性能地图。

值得记住的是：共享内存不是「缓存」，而是「程序员写进代码的协作契约」。它给你最快的片上带宽，代价是你必须自己管理布局、同步与冲突——这正是 CUDA 与「开箱即用」的 CPU 缓存最本质的区别。

## 8 归约：共享内存与同步的完整实践

把本篇的武器（共享内存 + bank 意识 + `__syncthreads`）串成一个经典例子——**归约（reduction）**，即把 $N$ 个数求和成一个数。朴素写法是让一个线程累加全部，O(N) 串行；GPU 版用「树形归约」把每块的开销降到 O(log N)：

```c
__shared__ float sdata[256];
sdata[threadIdx.x] = input[blockIdx.x * 256 + threadIdx.x]; // 载入共享内存
__syncthreads();                                            // 全部载完再往下
for (int s = 128; s > 0; s >>= 1) {                         // 树形折叠
    if (threadIdx.x < s) sdata[threadIdx.x] += sdata[threadIdx.x + s];
    __syncthreads();                                        // 每轮都要同步
}
if (threadIdx.x == 0) output[blockIdx.x] = sdata[0];        // 每块一个部分和
```

读这段代码，注意三个要点：

- **每轮折叠只让前一半线程工作**：`if (threadIdx.x < s)` 让后半线程闲置，但这正是「每轮同步需要所有线程到达」的原因——所以 `__syncthreads()` 在循环里每轮都要放，缺一轮就是未定义行为。
- **步长选 `s/2` 还是相邻（`sdata[i] + sdata[i+1]`）**：相邻版本首轮无 bank conflict、后半轮有；`s/2` 版本反之。这是 bank 意识在真实算法里的经典权衡。
- **`output[blockIdx.x]` 只是每块的部分和**：跨块还要再做一层归约（或原子操作），这正是 PMPP 第 10 章「最小化分歧」要处理的问题。

**归约是「共享内存 + 同步 + bank 意识」的毕业设计**：代码短、处处是坑、优化空间极大。能把它写对且写快，说明本篇三个主题你都接住了——也说明「先跑对、再调 bank、后看 Nsight」这套流程你已经有感觉了。

## 9 小结

- 共享内存按 **32 个 bank** 组织，一次 warp 访问理想情况下 1 拍完成。
- **bank conflict** = 同一 warp 内多线程访问同一 bank 的不同地址，按最挤 bank 的线程数串行化，最坏慢 32 倍。
- 访问拍数公式 $T = \max_b(\text{访问 bank } b 的线程数)$，无冲突 $T=1$。
- **填洞（padding）**：行宽从 32 垫到 33，让列访问错开 bank，是最常用解法。
- 同步原语两组：`__syncthreads()` 块内屏障（严禁放进切分 warp 的分支）、原子操作（读-改-写不可分割）。
- 共享内存 = 带宽与协作的契约，代价是自己管理布局与冲突。
