## 为什么从编码 Agent 讲起

在所有智能体应用中，**编码（coding）是被验证得最充分、也是商业上最成功的场景**。
原因很朴素：代码有「客观对错」——编译过不过、测试通不通、能不能跑出预期结果，
都不可争辩。
这让编码 Agent 拥有了最可靠的反馈信号，
也让它成了检验「智能体范式」最好的试验场。
<span class="marginnote">回望第 5 篇《反思与自我修正》的三种对错信号：编码场景把「环境反馈」用到了极致——编译器、测试用例、运行结果就是天然的验证器。
这也解释了为什么编码 Agent 比「自由对话 Agent」更容易做到可靠：它的反馈是<strong>确定性</strong>的，
不像文本任务那样依赖主观评判。
</span>

这一节我们看编码 Agent 从「自动补全」到「自主修 Bug」的三级跳，
以及它背后的循环架构。

## 1 三级跳：从补全到自主编程

编码 AI 的能力演进，
可以清晰地分成三个台阶：

**第一级：自动补全（completion）**：模型根据光标前的代码，
  续写下一段。
  没有循环、没有工具，
  本质是「高条件概率的文本生成」。
  这是 2021 年 Copilot 初版的形态——它很强，
  但只是「打字加速器」，
  不改变程序员的思维负担。
**第二级：对话式编程（chat）**：程序员在 IDE 里与 AI 对话，
  「帮我写个排序函数」「这个报错是什么意思」。
  模型能理解上下文、生成代码块，
  但**代码是否放进文件、能否跑通，
  仍由人负责**。
  这是 2023 年 Copilot Chat 的形态。
**第三级：自主编码（agent）**：给智能体一个任务（如「修复这个 issue」），
  它自己读代码库、定位问题、改代码、跑测试、根据失败再改，
  直到测试通过。**人从「写代码的人」变成「验收的人」。** 这是 Copilot Agent Mode 与 Claude Code、Devin 等工具的形态。
  <span class="marginnote">三级跳的本质是「控制权转移」：第一级 AI 控制「词的生成」，
  第二级控制「代码的生成」，
  第三级控制「代码的<strong>生命周期</strong>」——定位、修改、验证、迭代。
  每一级多交出一部分控制权，
  都需要更可靠的循环来承接。
  </span>

**重点：编码 Agent 不是「更会写代码的补全器」，
而是「能验证自己代码的执行者」。** 补全器只负责「写」，
Agent 还要负责「写对」——这个「对」由测试与环境判定。

## 2 编码 Agent 的循环架构

一个典型的自主编码 Agent，
循环由四个环节构成：

1. **仓库理解（repo understanding）**：把整个代码库「装进脑子」。
   工程上靠**仓库索引**：解析文件树、提取符号表（函数、类、引用关系）、建立向量索引，
   让智能体能在海量代码里快速定位。
   这就是第 4 篇「检索」在代码领域的实例化。
   <span class="marginnote">仓库索引与第三级《编译原理》的「符号表」同构：编译器需要「哪个标识符在哪、类型是什么」，
   编码 Agent 需要「哪个函数在哪、被谁调用」。
   区别是编译器的符号表是精确的，
   Agent 的索引是<strong>语义近似</strong>的——这也决定了 Agent 定位代码是「检索 + 推断」而非「精确查表」。
   </span>
2. **问题定位（localization）**：从任务描述（issue 文本、报错信息）出发，
   找到「哪个文件、哪个函数出了问题」。
   定位是编码 Agent 最难的环节之一——「改哪儿」比「怎么改」更容易错。
3. **修改生成（edit）**：在定位处生成代码修改。
   形式可以是整块重写、补丁（diff）、或结构化编辑。
   生成的修改要符合仓库既有风格与接口约定。
4. **验证迭代（verify-iterate）**：跑测试、跑编译、读运行结果。
   失败就回到定位或修改环节，
   带着错误信息重试。**验证信号的质量直接决定 Agent 的收敛速度**——这就是为什么 SWE-bench 等基准都用「测试是否通过」作为终极判据。

**辨析｜易错点：** 编码 Agent 最常见的失败不是「代码写得不对」，
而是「改错地方」或「没有验证就宣称完成」。**一个只写代码、不跑测试的编码 Agent，
等于一个从不复查的工程师**——它的输出再漂亮，
可信度也要打问号。

## 3 工具与环境的武器库

编码 Agent 的「手脚」是它拥有的工具集，
核心工具几乎成为标准配置：

**代码搜索**：`grep` / `rg` 全文检索、按符号名跳转、语义向量检索。
**文件操作**：读文件、写文件、创建/删除、生成补丁。
**命令执行**：跑测试、跑构建、跑目标程序。
  命令执行是编码 Agent 的「最强工具」——它让 Agent 能**自己验证**，
  而不是靠猜。
**版本控制**：查看 git 历史、diff、branch。
  理解「改动从哪来、影响什么」，
  是大型代码库协作的前提。
  <span class="marginnote">git 工具让 Agent 具备「时间维度的视野」：不仅能看当前代码，
  还能看「这次改动动了什么、上次提交为什么失败」。
  这在第三级《软件工程》的「版本控制」专题里有完整背景——编码 Agent 把这门课程里的操作变成了可调用的工具。
  </span>

**重点：工具越多，
责任越大。** 能执行命令的 Agent 也具备「误删文件、跑坏环境」的破坏力。
因此编码 Agent 框架普遍内置**沙箱隔离**：Agent 在隔离容器里执行命令，
用户确认后才应用到真实仓库。
自主性越高，
安全闸越不能省——这一主题在第 16 篇会系统展开。

## 4 公式解析：编码任务的成功信号

为什么编码场景的智能体能做得更可靠？
因为它有一个**可计算的成功判据**。
设仓库代码为 $C$，
任务为 $t$（如修复某个 bug），
Agent 产出修改后的代码 $C'$，
则任务成功定义为：

$$
\text{Success}(t, C') = \mathbb{1}\big[\underbrace{\text{new\_tests}(C')}_{\text{新增测试}} \wedge \underbrace{\text{old\_tests}(C')}_{\text{回归测试}} \wedge \underbrace{\text{hidden\_tests}(C')}_{\text{隐藏测试}}\big]
$$

逐项拆解：

- **$\text{new\_tests}(C')$ 是新增测试**：验证「目标功能真的被修好/实现」。
  没有它，
  改得再花哨也可能是「改了个寂寞」。
- **$\text{old\_tests}(C')$ 是回归测试**：验证「原有功能没被改坏」。
  编码 Agent 最隐蔽的坑——修好了 A，
  弄坏了 B。
  回归测试是防「按下葫芦浮起瓢」的闸门。
- **$\text{hidden\_tests}(C')$ 是隐藏测试**：基准里不公开、用于评测的测试。
  它防止 Agent「过拟合」到可见测试上——SWE-bench 正是靠 hidden tests 保证评测的公平性。
  <span class="marginnote">「可见测试 vs 隐藏测试」的区分，
  对应第二级《概率论与数理统计》的「训练集 vs 测试集」：可见测试是训练信号，
  隐藏测试是泛化信号。
  Agent 在可见测试上全过、隐藏测试上翻车，
  就是「过拟合」——这正是第 15 篇《Agent 评测基准》要专门防的问题。
  </span>
- **$\mathbb{1}[\cdot]$ 是布尔判定**：三个条件必须同时满足，
  才算成功。**这就是编码 Agent 比文本 Agent 可靠的结构性原因——成功与否是一个可计算的谓词，
  而不是一个模糊的主观印象。**

## 5 核心对比：三级编码 AI 的能力边界

| 层级 | 控制范围 | 验证能力 | 人参与度 | 典型产品 |
| --- | --- | --- | --- | --- |
| 补全 | 词级生成 | 无 | 人负责一切 | Copilot（2021 初版） |
| 对话 | 代码块生成 | 人验证 | 人负责落地 | Copilot Chat |
| 编码 Agent | 代码生命周期 | 自验证循环 | 人负责验收 | Copilot Agent / Claude Code |

## 6 小结

- 编码 AI 三级跳：**补全 → 对话 → 自主 Agent**，
  每级交出更多控制权，
  也需要更可靠的循环承接。
- 编码 Agent 循环四环节：**仓库理解 → 问题定位 → 修改生成 → 验证迭代**，
  验证信号决定收敛速度。
- 核心工具集：**代码搜索、文件操作、命令执行、版本控制**；
  能执行命令的 Agent 需要沙箱隔离。
- 编码任务的成功是可计算谓词：**新增测试 + 回归测试 + 隐藏测试**三者同时通过，
  这让编码 Agent 天生比文本 Agent 可靠。
