## 为什么从协议讲起

上一节我们讲了多智能体「组团队」，
但团队协作有一个前提：**成员之间得能听懂彼此的话。** 人类的协作靠语言与礼节，
智能体的协作靠协议——一套双方都遵守的消息格式与交互规则。
<span class="marginnote">把视角抬高一点：人类社会的协作之所以能规模化，
靠的是语言、法律、货币这些「共同协议」；
互联网的协作靠 TCP/IP 与 HTTP；
智能体的协作正在经历同样的「协议化」过程。
没有协议，
每个智能体都自说自话，
团队协作无从谈起——这正如第三级《计算机网络》里「没有 TCP/IP 就没有互联网」。
</span>

这一节我们要回答三个问题：智能体之间传输什么、用什么格式、谁负责协调。

## 1 消息：智能体间的最小通信单元

智能体之间传递的是**消息（message）**——一个带「元信息」的结构化数据块。
一条典型消息包含：

- **消息头**：发送者、接收者、消息 ID、时间戳、类型。
  类似 HTTP 的 header，
  供路由与追溯用。
- **载荷（payload）**：实际内容。
  可能是自然语言指令、结构化数据（JSON）、工具调用请求、或一个代码块。
- **上下文（context）**：与这条消息相关的背景信息，
  如引用哪条旧消息、当前任务编号、信任凭证。
  <span class="marginnote">「引用旧消息」很关键：消息如果不带引用，
  接收者就不知道「你说的『它』指什么」。
  这在工程上对应<strong>消息溯源（provenance）</strong>——与第三级《数据库》里的事务日志、第四级《分布式系统》里的因果一致性是同一个「可追溯」诉求。
  </span>

消息格式的选择直接影响通信质量。**自然语言**最灵活，
但歧义多；**结构化 JSON**最精确，
但表达力有限；**工具调用格式**（如 `` `<tool_call>` `` 包裹的函数名 + 参数）介于两者之间——足够机器可解析，
又保留语义。
现代系统普遍采用「自然语言 + 结构化字段」混合的消息体。

## 2 通信模式：请求-响应与发布-订阅

消息如何流动，
构成通信的两大模式：

- **请求-响应（request-response）**：一个智能体发起请求，
  另一个响应。
  同步、一对一，
  像 HTTP。
  适合「管理者派活，
  工人回报」这类明确分工。
- **发布-订阅（publish-subscribe）**：智能体向主题发布消息，
  订阅者按兴趣接收。
  异步、一对多，
  解耦发送方与接收方。
  适合「状态广播、事件通知」这类松散协作。
  <span class="marginnote">发布-订阅在第三级《计算机网络》里对应消息队列/事件总线（如 Kafka、MQTT）；
  在第四级《分布式系统》里对应事件驱动架构。
  智能体系统的通信层，
  本质上是在复用分布式系统几十年积累的成熟中间件。
  </span>

**重点：通信模式决定协作拓扑。** 请求-响应适合「有主从」的协作（第 8 篇的管理者-工人式），
发布-订阅适合「无中心」的协作（黑板式）。
选错模式，
就像用「打电话」做广播——能工作，
但别扭且昂贵。

## 3 协议栈：从工具到智能体的三层协议

「智能体协议」不是一个协议，
而是一组分层协议。
今天业界正快速成型三层栈：

- **工具协议（tool protocol）**：连接「模型 ↔ 工具」。
  代表是 **MCP（Model Context Protocol，
  模型上下文协议）**——Anthropic 于 2024 年底推出，
  定义了「模型如何发现、调用工具、读写资源」的标准接口。
  MCP 让「一个智能体连接任意 MCP 兼容工具」成为可能，
  类似 USB 让「一个接口连接任意外设」。
- **智能体间协议（agent-to-agent protocol）**：连接「智能体 ↔ 智能体」。
  代表是 **A2A（Agent2Agent，
  2025）** 与 ACP（Agent Communication Protocol）。
  A2A 定义了能力发现、任务协商、消息路由的标准，
  让不同厂商的智能体能互相对话。
- **协作编排协议（orchestration protocol）**：连接「编排层 ↔ 智能体」。
  管理任务分派、状态回传、重规划指令，
  通常由框架内定（AutoGen、LangGraph），
  尚未形成统一标准。
  <span class="marginnote">这层协议栈与第三级《计算机网络》的 OSI 分层惊人地同构：<strong>每一层只关心自己的职责，
  下层对上层透明</strong>。
  工具协议管「怎么操作世界」，
  智能体协议管「怎么对话」，
  编排协议管「怎么分工」。
  分层让各层独立演进——这正是网络协议栈教会我们的最大一课。
  </span>

**辨析｜易错点：** 不要把「工具调用」与「智能体通信」混为一谈。
工具调用是「智能体 → 函数」的单向操作，
返回的是数据；
智能体通信是「智能体 ↔ 智能体」的双向对话，
交换的是意图与承诺。
一个用 MCP 连工具的系统，
并不自动具备「智能体间协作」能力——那是 A2A 那一层的事。

## 4 公式解析：协议的开销与收益

协议不是免费的。
引入一套协议层，
用「接口收益」与「协商开销」的对比来理解它的存在理由。
设系统有 $n$ 个组件（工具或智能体），
组件间通信需要「标准化 vs 点对点定制」两种方案：

$$
\text{Cost}_{\text{点对点}} \approx \binom{n}{2} \cdot c_{\text{custom}} \;,\qquad \text{Cost}_{\text{协议化}} \approx n \cdot c_{\text{adapter}} + C_{\text{标准}}
$$

逐项拆解：

- **$\binom{n}{2} \cdot c_{\text{custom}}$ 是点对点成本**：$n$ 个组件两两对接，
  需要 $\binom{n}{2} = \frac{n(n-1)}{2}$ 份「定制适配」。
  每加一个新组件，
  就要为它写 $n$ 份新适配器——成本随 $n$ 平方增长，
  这是「无协议」的恐怖账单。
- **$n \cdot c_{\text{adapter}}$ 是协议化成本**：每个组件只需要实现一份「协议适配器」，
  接入标准接口即可。
  新组件只要会讲协议语言，
  就能与所有组件通信——成本随 $n$ **线性**增长。
- **$C_{\text{标准}}$ 是标准本身的一次性成本**：设计协议、写规范、维护 SDK。
  这笔钱前期投入大，
  但摊到大量组件上就越来越划算。
  <span class="marginnote">这是「标准之争」的经济学解释：为什么大家愿意为 TCP/IP、为 USB、为 JSON Schema 付前期成本？
  因为当组件数量 $n$ 很大时，
  线性增长远小于平方增长。
  MCP 与 A2A 的流行，
  本质上是「$n$ 足够大了，
  协议化的拐点已经到来」。
  </span>
- **临界点 $n^*$**：当 $n$ 超过某个临界值，
  协议化成本反超点对点。**今天智能体生态的组件数已经远超临界点**——这就是为什么各大厂商抢着推协议标准。

## 5 核心对比：三种协议的职责分工

| 协议 | 连接两端 | 核心职责 | 类比 OSI 层 |
| --- | --- | --- | --- |
| MCP | 智能体 ↔ 工具/资源 | 工具发现、调用、数据读写 | 会话层 + 表示层 |
| A2A / ACP | 智能体 ↔ 智能体 | 能力发现、任务协商、消息路由 | 传输层 + 应用层 |
| 编排协议 | 编排器 ↔ 智能体 | 任务分派、状态回传、重规划 | 会话层 |

**重点：协议的价值在于「让陌生组件无需定制即可协作」。** 协议标准化越彻底，
智能体生态越像「可插拔乐高」，
而非「彼此手焊的定制线」。

## 6 小结

- 智能体通信的最小单元是**消息**，
  含头部、载荷、上下文；
  格式在「自然语言 ↔ 结构化」之间取混合。
- 通信两大模式：**请求-响应**（有主从）与**发布-订阅**（无中心），
  选型取决于协作拓扑。
- 智能体协议分三层：**工具协议（MCP）、智能体协议（A2A/ACP）、编排协议**，
  与 OSI 分层思想同构。
- 协议化的收益是「线性 vs 平方」的通信成本：**组件规模越过临界点后，
  协议化是必然选择**。
