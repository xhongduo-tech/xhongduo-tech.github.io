## 为什么从工具讲起

上一节的 PPA 循环里，
「行动」环节对纯语言模型来说是空的——它只能输出文本，
改变不了任何环境。**工具（tool）就是给大模型装上「手脚」的接口**：让模型可以查网页、跑代码、调数据库、发邮件。
没有工具，
智能体是「会想不会做」的脑内幽灵；
有了工具，
它才真正进入世界。
<span class="marginnote">这正好呼应本专题第一篇《智能体的定义与能力》：工具是智能体的「执行器扩展」。
没有工具的循环是思考游戏，
有了工具的循环才闭合到环境。
第四级《大模型部署》里的 API 网关、函数计算，
本质都是给智能体的工具提供承载。
</span>

工具使用的核心工程形态是**函数调用（function calling）**：让大模型输出一个结构化的调用请求，
系统去执行真正的函数，
再把结果返回给模型。
这一节我们把它拆开：工具是什么、函数调用怎么实现、为什么 Toolformer 能自己学会用工具。

## 1 工具的本质：把世界封装成接口

工具（tool）在不同语境下有不同的外壳，
但内核一致：**一组「输入 → 执行 → 输出」的接口，
把外部世界的一个操作封装成语义明确的函数**。
常见形态有：

- **API 调用**：天气预报、股票行情、地图导航。
  输入是参数，
  输出是 JSON。
- **代码解释器**：执行 Python/JavaScript，
  返回 stdout 与错误。
  这是最强的工具之一——它等于给了模型一个「万能计算器」。
- **结构化数据查询**：SQL 查询、数据库检索、向量库召回。
- **系统操作**：读写文件、执行命令、发送邮件、操作浏览器。

**重点：工具的价值不在于实现，
而在于语义。** 工具的定义（tool definition）必须让模型理解三个问题：这个工具是干什么的？
需要什么参数？
什么时候该用它？
一个语义模糊的工具，
模型要么不敢用，
要么乱用。
<span class="marginnote">这里的「工具定义」在工程上就是一份 JSON Schema：包含工具名、描述、参数列表。
它相当于给模型的「工具手册」——模型读到这份手册才知道世界有哪些可操作入口。
对比第三级《编译原理》里的符号表：编译器也靠一张「函数签名表」决定如何生成调用代码，
两者思路一脉相承。
</span>

## 2 函数调用：把「想调用」翻译成「真调用」

函数调用（function calling）把一个循环拆成清晰的四个环节，
每一步都是今天智能体框架的标准件：

1. **定义工具**：开发者把工具注册进系统的工具表，
   每个工具有名称、描述、参数 Schema。
2. **模型选工具**：把工具表（连同对话历史）拼进提示词，
   让模型决定「要不要调用、调哪个、传什么参数」。
   现代模型输出一个特殊标记，
   比如 `` `<tool_call>` ``，
   后跟工具名与 JSON 参数。
3. **系统执行**：框架拦截模型输出，
   校验参数，
   调用真实函数，
   拿到返回值。
4. **结果回填**：把返回值作为新消息放回上下文，
   模型读到结果后继续推理——循环闭合。

**辨析｜易错点：** 初学者常把「模型输出 JSON」误当成「模型执行了函数」。
其实模型从未执行任何东西——它只是**生成了一段调用描述**，
真正的执行者是框架。
这个区分极其重要：模型不知道执行结果（除非结果被回填），
而执行者也无需「理解」工具，
它只是忠实运行。**「理解」与「执行」被函数调用协议清晰地切开了。**

## 3 公式解析：工具选择的概率模型

模型如何决定该不该用工具、用哪个工具？
把这个问题形式化，
就能看清函数调用背后的数学结构。
设模型 $M$ 的上下文为 $c$（对话历史 + 工具定义表），
则它在每一步选择一个输出 $y$ 的概率为：

$$
P(y \mid c) = P(y_{\text{text}} \mid c) + P(y_{\text{tool}} \mid c)
$$

其中 $y_{\text{tool}}$ 表示「这一轮输出一个工具调用」，
$y_{\text{text}}$ 表示「这一轮输出普通文本」。
更细地看，
一次工具调用可分解为三个子决策：

$$
\underbrace{P(\text{tool} = t \mid c)}_{\text{选哪个工具}} \;\cdot\; \underbrace{P(\text{args} = \theta \mid c, t)}_{\text{传什么参数}} \;\cdot\; \underbrace{P(\text{该调用} \mid c)}_{\text{要不要调用}}
$$

逐项拆解：

- **$P(\text{tool} = t \mid c)$**：上下文里塞进了工具表，
  模型在候选工具里做一次「分类」——本质上和一个文本分类器别无二致，
  只是类别变成了工具名。
- **$P(\text{args} = \theta \mid c, t)$**：选定工具后，
  再生成参数。
  这一步要求模型**严格按 Schema 输出**，
  所以工程上常用约束解码（如 JSON 语法约束）来保证参数合法——这正是第三级《编译原理》里语法分析的下推自动机思想的现代翻版。
- **$P(\text{该调用} \mid c)$**：模型还可能决定「不需要工具，
  直接回答」。
  这是隐式的门控，
  让模型学会在「知道答案」时闭嘴、在「不知道」时求助。
  <span class="marginnote">「学会闭嘴」比「学会调用」更难。
  GPT 系列早期常出现「明明知道答案也要搜一下」的过度调用；
  后来的模型通过训练数据里混合「该调/不该调」的样本，
  学会了何时用、何时不用。
  这提醒我们：给模型配工具的同时，
  也要教它不用的分寸。
  </span>

## 4 Toolformer：让模型自己学会用工具

函数调用的工程协议解决了「怎么调」，
但还留着一个更根本的问题：**模型怎么知道某个工具什么时候有用？** 早期的做法是人工标注，
成本极高。
Toolformer（Schick et al., 2023）给出了一个优雅的答案：**让模型自己用「自监督」学会调用工具**。

思路分四步，
每一步都呼应我们在第二级《机器学习》里学过的经典套路：

1. **采样候选**：给定一段文本，
   让模型自己采样出「这里该调工具」的位置与参数。
2. **执行验证**：调用工具拿到结果。
3. **判断增益**：比较「带工具结果的文本」与「不带工具结果的文本」的损失——如果带工具结果的损失更低，
   说明这次调用有帮助；
   否则丢弃。
4. **构造训练集**：把有帮助的调用保留，
   重新训练模型。

**重点：判断标准是「损失是否下降」，
即调用工具是否真的让模型更擅长预测后续文本。** 这让工具选择从「人教」变成「模型自己权衡」——工具不再是被硬编码的插件，
而成了模型世界模型的一部分。
<span class="marginnote">这套「采候选 → 执行 → 判增益 → 重训」与第三级《机器学习》的期望最大化（EM）精神相通：先用当前模型猜，
再用数据反馈修正。
Toolformer 之后，
同类思路演化出「工具即语言」的统一范式，
本专题第 11 篇《AutoGPT 与通用 Agent 框架》会看到它的工程化版本。
</span>

## 5 小结

- **工具的本质**是把外部世界的操作封装成语义明确的接口；
  工具的价值在于语义定义，
  而不在于实现。
- **函数调用**的四环节：定义工具 → 模型选工具（输出结构化调用）→ 系统执行 → 结果回填。**理解与执行被协议切开**。
- 工具选择的数学本质是**在候选工具上的条件概率分解**：选工具、定参数、决定是否调用。
- **Toolformer** 用「损失下降」作为自监督信号，
  让模型自己学会何时调用工具，
  开启了「工具即数据」的路线。
