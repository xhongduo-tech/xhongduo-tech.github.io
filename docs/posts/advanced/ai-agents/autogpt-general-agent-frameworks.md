## 为什么从 AutoGPT 讲起

2023 年春，
AutoGPT 一夜爆红——一个「你给它目标，
它自己规划、拆解、执行、验证」的开源项目，
让普通用户第一次亲眼看见「会自己干活的 AI」。
它引爆了智能体热，
也很快暴露了「通用自主智能体」的种种问题。
<span class="marginnote">回望本专题的范式之旅：ReAct 给了「交替循环」，
Plan-and-Execute 给了「先规划后执行」，
多智能体给了「分工协作」。
AutoGPT 的贡献不是某个新算法，
而是把这些范式<strong>封装成一套人人可运行的软件</strong>——它把「学术范式」变成了「工程产品」，
也第一次让大众尝到「自主智能体失控」的滋味。
</span>

这一节我们解剖通用 Agent 框架：它们由哪些模块构成、主流框架各有什么设计取向、以及 AutoGPT 教给行业的教训。

## 1 通用 Agent 框架的四件套

所谓「通用 Agent 框架」，
就是把本专题前面学的所有机制**做成一盒即插即用的积木**。
一个典型的框架包含四件套：

**智能体循环（agent loop）**：最外层的控制器，
  负责「目标 → 规划 → 行动 → 观察 → 再规划」的驱动。
  它是框架的骨架，
  决定循环怎么转、何时停。
**工具注册表（tool registry）**：工具的有序目录，
  含名称、描述、Schema、执行函数。
  智能体按描述选择工具，
  框架按 Schema 校验参数。
  这就是第 3 篇函数调用的工程化封装。
**记忆存储（memory store）**：短期上下文 + 长期向量库 + 技能库的统一接口。
  框架把「记忆」抽象成可插拔组件，
  允许开发者换不同的实现（内存、向量库、文件系统）。
  <span class="marginnote">「可插拔记忆」是框架与自制脚本的最大区别：脚本的记忆写死在代码里，
  框架的记忆是<strong>依赖注入</strong>的组件——换一种记忆后端，
  不改一行智能体逻辑。
  这对应第三级《软件工程》的依赖倒置原则，
  也是框架「通用性」的工程根基。
  </span>
**可观测层（observability）**：日志、追踪、状态快照。
  负责记录「智能体每一步想了什么、调了什么、结果如何」——这是调试自主系统的生命线。
  AutoGPT 早期最大的工程短板之一，
  就是用户完全看不清它在干什么。

**重点：框架的价值不在「模型」，
而在「控制」。** 模型是插在框架里的大脑，
框架管的是「大脑如何接上世界」：循环、工具、记忆、观测。
框架设计的好坏，
直接决定智能体是「可控的助手」还是「脱缰的野马」。

## 2 主流框架的设计取向

今天的框架百花齐放，
但按「对开发者开放的控制粒度」可以分成三种取向：

**低代码智能体（low-code agents）**：如 OpenAI 的 Assistants API、字节的 Coze。
  开发者配置角色、工具、知识库即可，
  循环由平台托管。**优点**：上手极快、免运维；**缺点**：控制粒度粗，
  无法深度定制循环。
  适合业务人员做自动化助理。
**图编排框架（graph orchestration）**：如 LangGraph、AutoGen 的图模式。
  把智能体循环建模成**状态机/有向图**，
  节点是「步骤」，
  边是「转移条件」。**优点**：循环可设计、可调试、可加分支与回环；**缺点**：学习曲线陡，
  本质是在写「行为图」。
  <span class="marginnote">把智能体循环画成状态图，
  等于把「第 2 篇的状态递推 $s_{t+1} = \text{Env}(s_t, a_t)$」可视化成了节点与边。
  这与第三级《数字逻辑》的有限状态机、<strong>第四级《自动机理论》</strong>的转移图是同一套「状态-转移」语言——图编排框架的底层就是一台广义状态机。
  </span>
**纯代码智能体（code-first agents）**：如老牌 LangChain Agent、自定义脚手架。
  开发者用代码直接控制每一步循环。**优点**：最灵活、无抽象泄漏；**缺点**：一切自己搭，
  成本高。

**辨析｜易错点：** 不要以为「用了框架」就等于「有智能体」。
框架只提供循环骨架；**智能体是否智能，
取决于模型质量 + 工具设计 + 记忆策略的组合**。
一个装进 LangGraph 的弱模型 + 混乱工具集，
产出的还是笨系统。
框架降低的是「搭建成本」，
不是「智能下限」。

## 3 AutoGPT 的教训：自主智能体的失控

AutoGPT 带来了兴奋，
也带来了行业最早的一课。
它暴露的问题至今仍是通用智能体的核心挑战：

**循环失控（runaway loop）**：AutoGPT 常陷入「反复尝试同一个失败动作」的死循环，
  直到耗尽 API 额度。
  原因：没有强力的终止条件与失败识别。
  第 5 篇的反思和「最大轮数 + 早停」在 AutoGPT 初版里是缺位的。
**成本黑洞**：通用任务的每一步都要调模型、传上下文，
  token 消耗随循环呈线性甚至超线性增长。
  一次「自主完成」任务的账单可能远超预期。
  <span class="marginnote">成本问题的数学根源在 ReAct 篇已埋下伏笔：上下文随轮次<strong>线性累加</strong>，
  每一轮都重新处理全部历史。
  AutoGPT 的教训催生了「压缩上下文」「子代理隔离上下文」「规划后减少轮次」等工程对策——今天框架的「省钱设计」大多从这次教训来。
  </span>
- **缺乏验证与回滚**：AutoGPT 会自信地宣称「完成」，
  但没人验证结果是否正确。
  没有验证器（第 5 篇的外部验证），
  自主执行与「自主幻觉」只有一线之隔。
- **安全边界缺失**：赋予智能体「执行命令、写文件、上网」的能力后，
  一旦目标理解出错，
  可能做出破坏性操作。**自主性的另一面是破坏力**——第 16 篇《Agent 安全与可靠性》会系统处理这个问题。

**重点：AutoGPT 的意义不是「一个成功的产品」，
而是「一次全员免费的实验」**——它让行业用最短时间看清了「通用自主智能体」的甜与苦，
把研究焦点从「怎么自主」转向「怎么可靠地自主」。

## 4 公式解析：自主系统的期望成本

通用框架的「自由」是有代价的，
用期望成本把「自主」的账算清楚。
设任务目标为 $g$，
智能体需要 $T$ 轮循环完成，
每轮期望成本 $\bar{c}$，
成功概率 $p$，
失败重试次数 $R$：

$$
\mathbb{E}[\text{Cost}] = \underbrace{T \cdot \bar{c}}_{\text{正常执行}} + \underbrace{(1-p)\cdot R \cdot \bar{c}}_{\text{失败重试}} + \underbrace{(1-p)\cdot L}_{\text{失败损失}}
$$

逐项拆解：

- **$T \cdot \bar{c}$ 是正常执行成本**：轮数 × 每轮成本。
  轮数取决于任务的复杂度与框架的循环设计——规划得越好，
  $T$ 越小。
- **$(1-p)\cdot R \cdot \bar{c}$ 是重试成本**：失败概率 $(1-p)$ 越高、重试次数 $R$ 越多，
  额外花费越大。
  AutoGPT 的成本黑洞就集中在这一项——它的 $R$ 常常不受控。
- **$(1-p)\cdot L$ 是失败损失**：失败不仅浪费 token，
  还可能造成真实损失 $L$（删了文件、下了错误订单）。
  自主性越高、$L$ 越大，
  就越需要「安全闸」。
- **设计启示**：好的框架不是「更自主」，
  而是**在保证成功率 $p$ 与压低损失 $L$ 的前提下，
  适度自主**。
  <span class="marginnote">这个期望成本的分解，
  其实呼应第二级《概率论与数理统计》里「随机变量的期望 = 各种可能结果 × 其概率求和」——把「自主执行」当成一次随机试验，
  期望成本就是它的「风险度量」。
  工程上所有「自主性开关」「人工审批点」，
  都是在调整这个期望成本中的 $p$ 与 $L$。
  </span>

## 5 小结

- 通用 Agent 框架的四件套：**智能体循环、工具注册表、记忆存储、可观测层**；
  框架管的是「控制」而非「模型」。
- 三种设计取向：**低代码**（平台托管，
  快但粗）、**图编排**（状态机建模，
  可控）、**纯代码**（最灵活，
  最贵）。
- AutoGPT 的教训：**循环失控、成本黑洞、缺乏验证、安全边界缺失**——把研究焦点推向「可靠地自主」。
- 自主系统的期望成本 = 执行 + 重试 + 失败损失，**好框架是「在保成功、控损失前提下适度自主」**。
