## 为什么从工作流讲起

商业世界运行在「流程」上：客户下单 → 库存核对 → 开票 → 发货 → 通知。
传统自动化把这些流程写成**固定脚本**——每一步做什么都事先规定。
但真实流程总有意外：库存不足、格式出错、条款例外。**Agent 进场的意义，
是把「流程中的意外处理」交给智能体。**<span class="marginnote">回望第 1 篇《智能体的定义与能力》的判别标准：「决策是否根据环境反馈动态调整」。
这条标准恰好划出了「工作流」与「智能体」的界线——工作流的每一步是预设的，
智能体的每一步是临场决定的。
本篇把这条界线放到企业场景里放大看，
也会看到二者如何融合。
</span>

这一节我们讲：工作流与智能体怎么区分、RPA 与 Agent 是什么关系、以及「确定性流程 + 智能决策点」的融合架构。

## 1 工作流与智能体：确定性与应变性

**工作流（workflow）**：一组**预设步骤**，
按固定顺序或条件分支执行。
它是确定性的——同样的输入，
必然走同样的路径。
优点是可预测、可审计、出错面小；
缺点是僵硬——遇到「规则没覆盖的情况」就停摆。

**智能体（agent）**：一个**动态决策**的执行者。
面对意外能「想出新办法」，
但代价是行为不可完全预测。

两者不是竞争关系，
而是**互补的两端**：

- 流程**稳定、高频、规则清晰**的部分 → 用工作流。
  省、快、稳。
- 流程**变化多、需要判断、异常频发**的部分 → 用智能体。
  灵活、会应变。

**重点：好系统不是「全用 Agent」或「全用工作流」，
而是「把确定性交给脚本，
把不确定性交给智能体」。** 这就是「Agentic Workflow」（智能体工作流）的核心思想——用编排层把「确定步骤 + 智能决策点」拼成一个整体。
<span class="marginnote">「确定步骤 + 智能决策点」的融合，
对应第三级《软件工程》的「程序 + 异常处理」：正常路径是直线代码，
异常路径进 handler。
工作流里，
正常路径是预设 DAG，
异常与判断路径进智能体。
工程上这叫「<strong>把智能体当函数的异常分支</strong>」——智能体不是替代流程，
而是补足流程的「判断死角」。
</span>

## 2 RPA 与 Agent：上一代自动化 vs 新一代

讲工作流自动化，
绕不开**RPA（机器人流程自动化，
Robotic Process Automation）**——上一代自动化技术的代表。
它用「录制人类操作」的方式让软件自动点击、填表、搬运数据。

| 维度 | RPA | Agent 自动化 |
| --- | --- | --- |
| 操作对象 | 界面元素（录制好的点击路径） | 界面 + 语义理解 |
| 应变能力 | 无——路径变了就失效 | 有——理解变化并调整 |
| 维护成本 | 高——界面一改就得重录 | 低——语义理解对布局变化鲁棒 |
| 适用 | 稳定、高频、重复操作 | 变化、低频、需要判断的操作 |

**辨析｜易错点：** Agent 会「替代 RPA」吗？
更准确的说法是**互补**：RPA 擅长「高精度重复执行」（每天同一张报表），
Agent 擅长「理解与判断」（报表格式变了，
Agent 能识别并调整）。**现实中大量「RPA + Agent」的混合系统**——RPA 负责机械执行，
Agent 负责兜底「RPA 跑不下去的意外」。
<span class="marginnote">RPA 与 Agent 的分工，
像第三级《操作系统》里「中断处理 + 轮询」的分工：确定性的轮询负责常规，
中断负责异常。
RPA 是「预设的轮询」，
Agent 是「会判断的中断处理器」——一个管常态，
一个管异常，
各司其职。
</span>

## 3 融合架构：把智能体装进流程

一个生产级的「Agent 工作流」架构，
通常由三层组成：

- **编排层（orchestration）**：定义流程的「骨架」——哪些步骤是确定的、哪些节点是「智能决策点」。
  编排层用 DAG / 状态机描述，
  决定流程何时走脚本、何时唤 Agent。
  这层就是第 11 篇图编排框架的企业落地。
- **执行层（execution）**：跑确定性步骤（调用 API、读写数据库、生成文件）与智能决策（调用 Agent）。
  执行层要有**重试、超时、幂等**保障——自动化系统的可靠性 80% 靠执行层兜住。
- **监控与治理层（observability & governance）**：记录每条流程的执行轨迹、每个决策点的判断依据、每笔自动化操作的审计日志。**自动化越深，
  审计越重要**——出了事要能「回溯到决策的那一步」。
  <span class="marginnote">审计与第 16 篇《Agent 安全与可靠性》的监督层一脉相承：不可逆操作要有人工卡点，
  卡点记录要留痕。
  企业自动化里的「治理」不是技术洁癖，
  而是合规刚需——「这笔钱是 Agent 自动付的」必须有完整的决策日志支撑。
  这对应第三级《数据库》的「审计日志」与《软件工程》的「配置管理」。
  </span>

**重点：融合架构的灵魂是「把智能体的判断关在预先设定的范围内」。** 智能体只在「决策点」上被召唤，
只被授予「该决策点的权限」，
决策完回到确定性流程。
这样既拿到灵活，
又保住可控。

## 4 公式解析：自动化流程的可靠性与吞吐

自动化系统的设计，
可以用「吞吐 × 可靠性」的权衡来描述。
设一条流程有 $n$ 个环节，
每个环节的成功率 $p_i$（确定性环节接近 1，
Agent 决策环节较低），
则整条流程的成功率：

$$
P_{\text{flow}} = \prod_{i=1}^{n} p_i
$$

逐项拆解：

- **$\prod$ 是连乘**：整条流程的成功率是所有环节成功率的乘积。
  这是「流程可靠性」的残酷真相——**环节越多，
  整体越脆**。
  一个 10 环节的流程，
  即使每环节 99% 可靠，
  整体也只有 $0.99^{10} \approx 0.90$。
  <span class="marginnote">连乘结构与第 13 篇 GUI 的 $p^n$ 是同一个数学：<strong>链条越长，
  错误累积越致命</strong>。
  这就是为什么自动化架构强调「环节尽量少、每个环节尽量可靠、关键环节可回滚」——每多加一个环节，
  都在给整体成功率「打折扣」。
  </span>
- **$p_i$ 的差异**：确定性环节（脚本、API）的 $p_i$ 接近 1；
  Agent 决策环节的 $p_i$ 较低（模型会判断错）。**插入一个 Agent 决策点，
  等于给流程成功率「引入一个短板」**——所以设计时要把 Agent 用在该用处，
  而不是到处撒。
- **重试与补偿**：工程上用「失败重试」（提高有效 $p_i$）与「补偿事务」（失败时回滚）把连乘的损失追回来——这对应第 16 篇的「验证 + 回滚」。
- **吞吐与可靠性互换**：追求高吞吐（并行、快跑）与高可靠（串行、多验）之间存在取舍。**设计准则是「按环节的价值密度分配可靠性预算」**——关键环节加倍验证，
  非关键环节放开跑。

## 5 核心对比：工作流自动化的三种形态

| 形态 | 决策来源 | 应变能力 | 适用场景 | 可靠性与成本 |
| --- | --- | --- | --- | --- |
| 纯工作流 | 预设规则 | 无 | 稳定高频流程 | 高可靠、低成本 |
| RPA | 录制路径 | 极弱 | 界面重复操作 | 中可靠、维护贵 |
| Agentic Workflow | 预设 + 智能决策 | 强 | 有意外、需判断的流程 | 中可靠、按需投入 |

## 6 小结

- **工作流**（确定性脚本）与**智能体**（动态决策）是互补两端：稳定部分交给脚本，
  意外部分交给智能体。
- RPA 与 Agent **互补而非替代**：RPA 管高精度重复，
  Agent 管理解与应变。
- 融合架构三层：**编排层**（骨架 + 决策点）、**执行层**（重试幂等）、**监控治理层**（审计留痕）。
- 流程可靠性是连乘 $\prod p_i$：**环节越少越可靠、Agent 决策点是短板、关键环节要加倍验证**。
