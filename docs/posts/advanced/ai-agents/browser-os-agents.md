## 为什么从浏览器与操作系统讲起

编码 Agent 已经能让 AI「操作文件与命令」，
但世界上还有大量软件**没有命令行接口**——网页、桌面应用、手机 App。
要操作它们，
智能体必须学会人类的方式：**看屏幕、点按钮、填表单、拖窗口**。
<span class="marginnote">这是「智能体接口」的一次革命：编码 Agent 走的是「为机器设计的接口」（API、CLI），
浏览器/操作系统 Agent 走的是「为人类设计的接口」（GUI）。
后者覆盖面大得多——所有人类能用的软件它都能用——但代价是信号更难解析：从像素还原语义，
比从 JSON 还原语义难一个量级。
</span>

这一节我们看浏览器 Agent 与操作系统 Agent 的架构、它们如何「看懂」界面、以及这个方向的核心难点。

## 1 从 DOM 到像素：浏览器 Agent 的感知方式

浏览器 Agent 要「操作网页」，
先要「看懂网页」。
它有两条感知路线，
代表了两种工程哲学：

**DOM 路线（结构化感知）**：直接读取页面的 DOM 树——每个按钮、链接、输入框在 DOM 里都是带标签的节点。
  Agent 把 DOM 精简成「可操作元素清单」，
  在清单里选目标、做动作。**优点**：信号精确，
  元素可定位、可点击；**缺点**：长页面 DOM 极长（数千节点），
  需要压缩与截断；
  对纯 canvas 渲染的页面无能为力。
  <span class="marginnote">把 DOM 精简成操作清单，
  类似第三级《编译原理》的「中间表示」：不直接处理源文本，
  先转成结构化表示再处理。
  浏览器 Agent 的「可访问性树（accessibility tree）」正是为此设计——它只保留「人能感知和操作」的元素，
  剔除了纯布局节点，
  是 DOM 的<strong>语义投影</strong>。
  </span>
**视觉路线（像素感知）**：把截图喂给多模态模型，
  让模型「看图」识别元素位置（如「右上角的蓝色按钮」）。**优点**：能处理任意渲染方式，
  包括 canvas、视频、图表；**缺点**：像素级定位误差大、推理成本高、依赖多模态模型能力。
  <span class="marginnote">视觉路线依赖的多模态理解，
  正是第 18 篇《多模态 Agent》的核心能力——让模型同时理解「图上的元素」与「文字指令」。
  两个方向在此交汇：视觉 Agent 是「多模态 + 行动」的产物。
  </span>

**重点：主流工程采用「DOM 为主、视觉为辅」的混合路线**——结构信号用于精确定位，
视觉信号用于兜底「DOM 拿不到的」。
纯视觉路线（如 Claude Computer Use）是更通用但更难的形态，
它面向「任意软件」，
代价是必须承担像素理解的误差。

## 2 操作系统 Agent：把桌面当环境

把浏览器 Agent 的思路再放大一层，
就是**操作系统 Agent（computer-use agent）**——把整个桌面操作系统当作环境。
它不再只操作网页，
而是操作：文件系统、命令行终端、桌面应用、系统设置。

操作系统的「传感器」与「执行器」都更复杂：

**传感器**：屏幕截图（视觉）、可访问性接口（结构）、剪贴板、进程列表、系统日志。
**执行器**：鼠标点击/拖拽、键盘输入、运行命令、读写文件、启动应用。

Claude Computer Use（2024）是这一路线的代表：模型接收截图，
输出「鼠标移到坐标、点击、输入文本」等动作，
由沙箱环境执行。
<span class="marginnote">「把坐标当动作接口」听起来原始，
但却是<strong>通用性</strong>的极致——任何能在屏幕上呈现的软件都能被这套接口操作，
就像人类使用电脑一样。
这比给每个软件写 API 要通用得多，
代价是精度与速度。
这个「通用性 vs 精度」的取舍贯穿整个 GUI Agent 领域。
</span>

**辨析｜易错点：** 操作系统 Agent ≠ 「能跑命令的 Agent」。
能跑命令的 Agent（如编码 Agent）操作的是「命令行环境」；
操作系统 Agent 操作的是「图形环境」——它要理解屏幕布局、窗口层级、按钮状态。
命令行的环境是文本流，
图形环境是**空间布局**，
两者对模型的感知要求完全不同。

## 3 行动空间与轨迹：GUI 任务的挑战

GUI Agent 看起来「只是点一点」，
实际上充满了隐蔽的难点：

**长时程任务（long-horizon）**：一次真实任务（「订一张下周五的机票」）可能需要 30–80 步：打开网站、登录、搜索、筛选、比价、填表、支付。
  步骤越长，
  越容易中途迷失、累积错误。
  <span class="marginnote">长时程任务对「记忆」提出苛刻要求：第 4 篇的三层记忆在这里全都要用上——工作记忆装当前页面的操作上下文，
  情景记忆记「上次这个网站这么操作成功了」，
  语义记忆存「订票的一般流程」。
  这也解释了为什么 GUI Agent 是长期记忆系统最好的试验场。
  </span>
- **状态稀疏与反馈延迟**：GUI 操作的反馈常常滞后——点完「提交」要等页面跳转，
  判断对错要等好几步之后。
  这比编码 Agent「跑个测试几秒钟出结果」困难得多。
- **视觉歧义**：页面上的「确定」按钮可能有好几个，
  「关闭」可能是 × 也可能是「右上角叉」。
  像素识别 + 语义推断的误差会随步数累积。

**重点：GUI Agent 的第一性难点是「反馈的稀疏与延迟」**——它不像编码有即时可验证的测试，
很多时候要等几步才知道「走错了」。
这要求 Agent 具备更强的规划能力与试探能力，
也正是第 7 篇 Plan-and-Execute 与第 5 篇反思的价值所在。

## 4 公式解析：轨迹成功率与步数

GUI 任务的成功率随步数「雪崩式」下降，
用概率把这个现象写清楚。
设单步操作的正确率为 $p$（例如 0.98），
任务需要 $n$ 步，
假设各步独立，
则整条轨迹成功的概率为：

$$
P_{\text{success}} = p^{\,n}
$$

逐项拆解：

- **$p$ 是单步正确率**：0.98 已经很高——意味着 100 次操作里错 2 次。
  对编码来说这可能无伤大雅，
  但对 GUI 来说，
  一步错就可能让整个任务偏离轨道。
- **$n$ 是步数**：一次真实 GUI 任务 30–80 步是常态。
  代入计算：$0.98^{50} \approx 0.36$——**即使单步正确率高达 98%，
  50 步的任务成功率只有约 36%**。
  <span class="marginnote">这就是「错误累积」的数学真相：$p^n$ 随 $n$ 指数衰减。
  它揭示了 GUI Agent 的两条出路——要么把 $p$ 提得极高（更强的单步模型），
  要么把 $n$ 压下来（更好的规划，
  少走弯路）。
  所有 GUI Agent 的架构设计，
  本质上都是在同时优化这两个变量。
  </span>
- **从 $p^n$ 得到的工程启示**：① 用验证与回滚把「错一步」变成「错一步且能爬回来」，
  等价于提升有效 $p$；
  ② 用规划压缩 $n$，
  避免无意义的试探步；
  ③ 必要时引入人类确认点，
  在关键步骤「止损」。
- **对比编码 Agent**：编码 Agent 有即时测试反馈，
  等价于「每步之后都能修正」，
  实际成功率远高于 $p^n$ 的裸算。**GUI Agent 因为反馈稀疏，
  最接近「裸 $p^n$」的困境**——这就是它比编码 Agent 更难做的结构性原因。

## 5 核心对比：浏览器 vs 操作系统 Agent

| 维度 | 浏览器 Agent | 操作系统 Agent |
| --- | --- | --- |
| 环境 | 网页（DOM + 截图） | 整个桌面（文件、应用、终端） |
| 主感知 | DOM 树 / 可访问性树 | 截图 / 可访问性接口 |
| 主执行 | 元素点击、填表、导航 | 鼠标、键盘、命令、文件 |
| 典型任务 | 订票、查信息、填表单 | 装软件、改配置、跨应用协作 |
| 代表基准 | WebArena / Mind2Web | OSWorld |

## 6 小结

- 浏览器 Agent 的两条感知路线：**DOM 结构化路线**（精确、可定位）与**视觉像素路线**（通用、有误差），
  主流是「DOM 为主、视觉为辅」。
- **操作系统 Agent**把整个桌面当环境，
  用「坐标动作」实现人类级通用性，
  代价是精度与速度。
- GUI 任务的核心难点是**反馈稀疏延迟**与**长时程轨迹**，
  比编码场景更难可靠。
- 成功率模型 $P = p^n$ 揭示：**错误随步数指数累积**，
  出路在于提升单步正确率与压缩步数。
