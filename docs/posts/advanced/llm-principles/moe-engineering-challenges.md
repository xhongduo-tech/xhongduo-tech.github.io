## 为什么 MoE 的工程比算法更难

MoE 的算法思想（稀疏激活）很简单，但把它**真正部署到生产**——跨卡并行、显存调度、推理引擎——是另一座山。它的困难根源在于：**「按需激活」打破了稠密模型的静态计算图**——token 要动态地跨卡流动（all-to-all），专家要分片、要缓存、要负载感知。这篇把 MoE 工程的三大战场讲透：**通信、显存、推理**。<span class="marginnote">稠密模型的工程是「确定性」的：每层算完传给下一层，流水线清晰。MoE 模型多了「路由器 → 分发 → 专家 → 聚合」的动态过程，像在确定的流水线上加了一个「动态分拣系统」——分拣效率直接决定整体吞吐。vLLM、SGLang 等引擎为 MoE 做了大量专用优化，正是因为这个原因。</span>

## 1 通信开销：all-to-all 的双刃剑

MoE 前向中，token 经过路由后被送到不同专家——**跨设备的专家分布意味着 token 要跨卡搬运**。这就是 **all-to-all 通信**：每张卡要把「属于自己的 token」发给「托管对应专家的卡」，同时接收「路由到自己这里」的 token。

**为什么 all-to-all 贵**：

稠密模型是「每层一次同步」；MoE 在**每个 MoE 层**都要做一次 all-to-all，层数多则通信次数多。
通信量与「token 的分布」有关——负载不均时，某些卡收到的 token 爆多，通信热区形成。
all-to-all 是「全对全」的，卡越多，通信量增长越快（$O(P^2)$ 级别的最坏情况）。

**缓解手段**：

**专家并行（expert parallelism）**：专家分布到多卡，注意力部分用张量并行，MoE 部分用专家并行——两种并行混用。
**设备受限路由**：限制 token 只路由到「本设备组内」的专家，牺牲一点路由自由度换取通信减少（DeepSeekMoE 的做法）。
**通信计算重叠**：把 all-to-all 与专家计算流水化，通信期间算别的层。
**减少 MoE 层数**：不是每层都 MoE，稀疏地插入 MoE 层（如「每 2 层 MoE 一次」）平衡质量与通信。<span class="marginnote">一个直观的数据：DeepSeek 报告里，通信优化前后 MoE 部分的吞吐可以差 2–3 倍。MoE 的「稀疏计算」红利，很容易被「稠密通信」吃光——<strong>工程上把通信压下去，MoE 才算真正快起来</strong>。</span>

## 2 显存：权重按总参数算，激活按专家算

MoE 的显存是「矛盾」的：

**权重显存**：按**总参数**算——所有专家都要驻留显存（或存储）。Mixtral 8×7B 总参数约 47B，FP16 权重约 94 GB——即使单 token 只激活 2 个专家，部署时 94 GB 一分不能少。

**激活显存**：按**激活的专家**算——只有被路由的专家才产生中间激活，激活显存与「激活参数」成正比。

**后果**：

MoE 的「便宜」是**算力**便宜，不是**显存**便宜。
单卡装不下时，专家必须分片到多卡（专家并行），否则只能用小 batch。
KV Cache 仍按「每 token」算（与专家数无关），但在大 batch 下与专家权重抢显存。

**显存优化手段**：专家权重量化（每个专家独立量化）、专家卸载（不常用的专家放 CPU/磁盘，按需加载）、权重共享压缩（共享专家的复用）。<span class="marginnote">「权重全驻留 + 激活稀疏」意味着 MoE 特别适合「容量敏感、算力敏感」的云端场景，而不适合「显存受限」的边缘端。这也是为什么 MoE 大模型主要在数据中心推理，而手机端几乎不用 MoE。</span>

## 3 推理部署：批处理与负载感知

MoE 推理的特殊挑战在于 **batch 内的「token-专家」动态匹配**：

- **动态计算量**：不同 token 路由到不同专家，专家收到的 token 数不均——GPU 利用率天然不齐。
- **批处理（batching）**：把多个请求拼成一个 batch，让「路由到同一专家的 token」尽量多，提高每个专家的「批量效率」。batch 越大，专家的利用率越高——**MoE 对 batch 大小更敏感**。
- **负载感知调度**：推理引擎需要知道「每个专家当前多忙」，把 token 调度到空闲专家——这与「纯路由质量」冲突，需要权衡。

**vLLM 的 MoE 支持**：

- 统一的专家分片 + PagedAttention 管理 KV；
- 对不同专家的「批内分组」优化，减少动态形状开销；
- 支持「推测解码」的 MoE 变体（小模型代跑，减少 MoE 的重复计算）。

## 4 公式解析：MoE 的训练算力账

把 MoE 的「理论红利」算清楚。设稠密模型参数 $P_d$、训练 token 数 $T$、FLOPs/token 为 $6P_d$（经验系数）；MoE 总参数 $P_m = E \cdot P_e$（$P_e$ 每专家），激活参数 $P_a = k \cdot P_e$：

$$
\text{FLOPs}_{\text{dense}} \approx 6 P_d T, \qquad
\text{FLOPs}_{\text{MoE}} \approx 6 P_a T = 6 k P_e T
$$

对这两条式子做三步拆解：

- **第一步，读懂 $6P$ 系数**：训练一个 token 大约需要 $6 \times$ 参数量 的 FLOPs（前向 2P + 反向 4P）。这是缩放定律里的「计算系数」。
- **第二步，读懂 MoE 的替换**：MoE 用「激活参数 $P_a$」替代「总参数 $P_d$」进入 FLOPs——因为只有激活的专家产生计算。
- **第三步，读出缩放含义**：相同 FLOPs 下，MoE 的「知识容量」可以做到 $E/k$ 倍于稠密——**参数涨、算力不涨**。这就是「以参数换知识，不以算力换知识」的定量表达。

**辨析｜易错点：** FLOPs 只是「理论计算量」，不含通信与内存。MoE 的**实际**训练/推理成本 = 计算 + 通信 + 内存搬运。在小 batch 或小设备数下，通信开销可能抹平稀疏红利——所以「MoE 一定快」是错误认知，**「MoE 在规模上快」才准确**。

## 5 MoE 的部署决策清单

| 场景 | MoE 是否合适 | 理由 |
| --- | --- | --- |
| 云端大模型、大 batch | ✅ | 稀疏红利被批处理放大 |
| 低延迟单请求 | ⚠️ | 通信/调度开销占比大 |
| 显存受限（边缘端） | ❌ | 权重全量驻留 |
| 长上下文 + 高并发 | ✅ | KV 与算力双优化 |
| 训练算力紧张 | ✅ | 同样算力更大容量 |

## 7 数值算例：稀疏红利 vs 通信开销

以 Mixtral 8×7B（总参 47B、激活 13B）为例：

- **单 token 计算**：$6 \times 13\text{B} \approx 78$ GFLOPs（只算激活专家）。
- **若换稠密 47B**：$6 \times 47\text{B} \approx 282$ GFLOPs——理论省约 3.6 倍计算。

但每次 MoE 前向都要做 all-to-all：每个 token 的 4096 维 hidden 状态要在卡间传输。**在小 batch（如 1 个请求）下，通信开销可能占 30–50% 的时间**——稀疏红利被通信吃掉大半；在大 batch（如 256 请求）下，通信被摊薄、专家利用率拉满，MoE 才真正「快」。

**辨析｜易错点：** 「MoE 省算力」是「相对稠密同参数」而言的。实际系统里「端到端快不快」取决于 batch 大小、设备数、通信带宽——**「省了 FLOPs」不等于「省了时间」**。评估 MoE 部署，要看端到端吞吐与延迟，而不是纸面的 FLOPs 对比。

## 8 稠密 vs MoE 部署对照

| 维度 | 稠密 | MoE |
| --- | --- | --- |
| 权重显存 | 按总参 | 按总参（全驻留） |
| 激活显存 | 按总参 | 按激活参 |
| 单 token 计算 | 全量 | 稀疏 |
| 通信开销 | 少 | 多（all-to-all） |
| batch 敏感度 | 低 | 高 |
| 适合场景 | 边缘端、低并发 | 云端、大 batch |

**一句话选型**：MoE 的「稀疏计算」红利要用「大 batch + 强互联 + 通信优化」去兑现。算力敏感、网络好、batch 大的云端是它的主场；显存受限、低并发的边缘端是它的禁区。

## 9 小结

- **通信**：all-to-all 是 MoE 的头号开销，靠专家并行、设备受限路由、计算通信重叠缓解。
- **显存**：权重按**总参数**算（全驻留）、激活按**激活参数**算——省算力不省显存。
- **推理**：动态 token-专家匹配让批处理更敏感，需负载感知调度。
- 训练算力：$\text{FLOPs} \approx 6 P_a T$——**参数涨、算力不涨**。
- 判断标准：**MoE 在规模上快，不在单请求上快**。
