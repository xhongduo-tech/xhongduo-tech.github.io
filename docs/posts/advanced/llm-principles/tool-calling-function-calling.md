## 为什么「工具调用」要有「协议」

Agent 要「调用工具」，首先得让模型「知道有什么工具、怎么调用」。**Function Calling（函数调用）** 是一套「协议」：**把工具的「名字、参数、说明」告诉模型，模型输出「调用哪个工具、传什么参数」，系统解析并执行，返回结果**。这套协议让「模型的意图」与「系统的执行」无缝衔接——它是 Agent 工程的基础设施。<span class="marginnote">Function Calling 的「协议化」意义：<strong>把「工具调用」从「自由文本」（ReAct 的 `search[...]`）升级为「结构化输出」（JSON）</strong>——结构化让「解析可靠、执行安全、多工具统一」。OpenAI 在 2023 年把它标准化，各家的 Agent 框架（LangChain、LlamaIndex）都围绕它构建。MCP（下一节）是这套协议的「再标准化」。</span>

## 1 Function Calling 的完整流程

一次工具调用的生命周期：

1. **工具声明**：把工具「注册」给模型——「名字、描述、参数 schema（JSON Schema）」。
2. **模型决策**：模型看到「用户请求 + 工具清单」，判断「要不要调用工具、调用哪个、传什么参数」。
3. **结构化输出**：模型输出一个「函数调用」的结构化对象（如 JSON）——`{"name": "search", "arguments": {"query": "北京天气"}}`。
4. **系统执行**：框架解析 JSON，调用「真实的工具函数」，拿到结果。
5. **结果回传**：把工具结果作为「新的消息」回给模型。
6. **模型生成**：模型基于「工具结果」生成最终回答（或再次调用工具）。

**工具声明示例**（JSON Schema）：

```json
{
  "name": "search",
  "description": "在知识库中搜索信息",
  "parameters": {
    "type": "object",
    "properties": {
      "query": {"type": "string", "description": "搜索关键词"}
    },
    "required": ["query"]
  }
}
```

**关键**：**描述要「清晰」**——模型靠「描述」决定「何时用这个工具」。描述含糊，模型「不知道什么时候该用」。<span class="marginnote">工具描述的「提示工程」本质：<strong>模型是通过「描述」来「理解」工具的——描述写得好，模型「会用」；写得差，模型「乱用或不用」</strong>。所以工具描述要写清「何时用（触发条件）」「怎么用（参数含义）」「别滥用（边界）」——它是一段「给模型的说明书」。</span>

## 2 模型怎么「学会」工具调用

模型输出「结构化函数调用」——这个能力从哪来？两种来源：

**① 训练（SFT/工具微调）**：用「含工具调用的数据」微调模型——「问题 + 工具清单 → 函数调用」——模型学会「识别需要工具的场景、输出正确的调用」。

**② 上下文学习（prompt）**：不训练，把工具清单放进 prompt——模型「按格式」输出调用（ReAct 式）。

**两种方式的对比**：

| 维度 | 训练（SFT） | 上下文学习（prompt） |
| --- | --- | --- |
| 可靠性 | 高（内化为能力） | 中（靠格式引导） |
| 可扩展性 | 加工具要重训 | 加工具只需改 prompt |
| 成本 | 训练成本 | 零 |

**现代 Agent 的趋势**：**基础模型内置 Function Calling 能力**（通过 SFT 训练），框架层用 prompt 注册「具体工具」——「通用能力（会调用）+ 具体工具（注册清单）」——兼顾可靠与灵活。<span class="marginnote">「会调用工具」与「会用某个工具」是两层能力：<strong>「会调用」是模型的通用能力（能输出结构化调用），「会用某个工具」是「看说明书」（理解描述）</strong>——所以「模型内置调用能力 + 工具用描述注册」是最佳组合：模型「天生会伸手」，具体「抓什么」看清单。</span>

## 3 工具调用的鲁棒性挑战

真实环境里工具调用「没那么顺」，几个经典问题：

**① 参数幻觉**：模型「编造参数」——调 `search` 传了个「不存在的 query」。
- 缓解：参数 schema 约束 + 工具返回「参数错误」反馈。

**② 工具选择错误**：模型「选错工具」——该用 `calculator` 却用了 `search`。
- 缓解：工具描述更清晰 + 模型微调。

**③ 无限循环**：模型「反复调用同一个工具」停不下来。
- 缓解：最大调用次数限制、循环检测、超时。

**④ 错误观察**：工具返回「错误/异常」，模型「被误导」。
- 缓解：错误信息「结构化回传」（`error: ...`），模型学会「识别错误、换方案」。

**⑤ 多工具协作**：任务需要「先查、再算、再查」——模型要「记住中间状态」。
- 缓解：上下文保留历史 + 迭代循环。

## 4 公式解析：工具调用的「决策」本质

工具调用是模型的一次「决策」——选择「调用哪个工具」还是「直接回答」。设工具集 $\mathcal{T}$，模型对用户请求 $u$ 的决策：

$$
\text{decision}(u) = \begin{cases} \text{answer}(u) & \text{不需要工具} \\ \arg\max_{t \in \mathcal{T}} p_\theta(t \mid u, \text{描述}) & \text{调用工具 } t \end{cases}
$$

对这条式子做三步拆解：

- **第一步，读懂分支**：模型先判断「要不要工具」——不需要就直接答（简单请求）；需要就「选工具」。
- **第二步，读懂选择**：$\arg\max_{t} p_\theta(t \mid u, \text{描述})$——从工具集里选「概率最高的」——**工具选择是「基于描述的判别」**——模型「读描述、对需求、选最匹配」。
- **第三步，读出关键因素**：决策质量取决于「$p_\theta$ 的判别能力」（模型够不够强）与「描述的信息量」（描述够不够清）——**「模型 × 描述」共同决定「工具调用好不好」**。

**辨析｜易错点：** 工具调用的输出是「意图」，不是「执行」——模型「说」要调 `search`，系统才「真调」——**「模型的输出」与「系统的执行」是分离的**。这带来「安全边界」：模型「提议」，系统「授权」——**执行层要有权限控制**（哪些工具允许、哪些参数合法）。

## 5 工具调用的工程实践

1. **工具注册**：统一的工具描述格式（JSON Schema）——「名字 + 描述 + 参数」。
2. **解析与校验**：解析模型的 JSON 输出，校验参数合法性——「不合法就拒绝 + 反馈」。
3. **执行与回传**：执行真实函数，结果「结构化」回传——「成功/错误/数据」。
4. **循环控制**：最大轮数、超时、去重——防止失控。
5. **权限**：敏感工具（数据库写、邮件、支付）要「人工确认」或「权限分级」。

## 6 小结

- **Function Calling**：工具注册 + 模型决策 + 结构化输出 + 系统执行——「意图到执行的协议」。
- 工具描述是「给模型的说明书」——「何时用、怎么用、别滥用」。
- 能力来源：**SFT 训练（内化）+ prompt 注册（灵活）**。
- 鲁棒性：参数幻觉、选错工具、死循环、错误观察——各有缓解。
- 安全边界：**模型「提议」、系统「授权」**——执行层要有权限控制。
