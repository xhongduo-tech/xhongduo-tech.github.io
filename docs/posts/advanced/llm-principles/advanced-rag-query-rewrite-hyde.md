## 为什么「直接检索」不够

基础 RAG 是「问题 → 检索 → 生成」——但直接检索有三个盲区：**问题表述不清晰**（「那个东西怎么弄」——检索器不知道「那个东西」是什么）、**query 与文档的「表述鸿沟」**（query 口语、文档书面）、**一次检索不够**（答案需要「多次查找 + 组合」）。**高级 RAG** 针对这些盲区做「预处理」与「多轮化」——查询改写、HyDE、迭代检索是三个代表性技术。<span class="marginnote">「高级 RAG」不是一个「技术」，而是一族「检索前/后处理技巧」——<strong>核心思想：把「直接检索」升级为「策略性检索」</strong>——先「想清楚怎么问」（改写），再「用假设缩小距离」（HyDE），最后「分步查」（迭代）。这些技巧让 RAG 从「玩具」走向「生产」。</span>

## 1 查询改写：让「问题」更适合检索

**查询改写（query rewriting）** 在检索前「优化问题」：

**① 澄清与扩展**：

把「模糊表述」改写成「清晰 query」——「那个东西」→「那个红色的文件夹」。
把「口语」翻译成「检索友好」的表述——「怎么退」→「退货流程」。

**② 多查询分解**：

复杂问题拆成「多个子查询」——「比较 A 和 B 的价格与性能」→ 「A 的价格」+「A 的性能」+「B 的价格」+「B 的性能」。
每个子查询分别检索，再合并结果——**多路召回**。

**③ 用 LLM 做改写**：让 LLM「把问题改写成更适合检索的形式」——「用几个检索词表达这个问题的核心」。

**为什么改写有效**：检索器「匹配的是词面/向量」，而用户的原始问法「未必是最优匹配形式」——改写让 query「更接近文档的表达」，检索「更容易命中」。

## 2 HyDE：用「假设答案」缩小语义鸿沟

**HyDE（Hypothetical Document Embeddings）** 解决「query 与文档的表述鸿沟」——**让 LLM 先「假设一个答案」，用「假设答案」的向量去检索**，而不是用「问题」的向量：

1. **生成假设文档**：让 LLM 对问题「写一个可能的答案」（不要求正确，只要「相关主题的文本」）。
2. **向量化假设文档**：把「假设答案」embedding。
3. **用假设答案检索**：在文档库中找「与假设答案最像的文档」。

**为什么有效**：

**query 与文档「不对称」**：问题（短、口语）与文档（长、书面）的向量「分布不同」——直接用问题向量检索「匹配不准」。
**假设答案「填补鸿沟」**：假设答案是「文档形态」的文本——它的向量「更接近文档空间」——**用「文档形态」去匹配「文档」**。<span class="marginnote">HyDE 的直觉：<strong>与其用「问题」问「文档」，不如先「写出像文档的回答」，再用它去找「真文档」</strong>——因为「答案的样子」比「问题的样子」更接近「文档的样子」。这是「检索侧的思维链」：先用 LLM「假设」、再检索「验证」。代价是「假设答案」要额外一次 LLM 生成。</span>

## 3 迭代式检索：边检索边决定「下一步查什么」

基础 RAG「一次检索」——但复杂问题的答案「分散在多个文档」「需要逐步缩小」。**迭代式检索（iterative retrieval）** 把检索变成「多轮」：

**① 检索-评估-再检索**：

- 第一轮检索 → LLM 看结果 → 「还缺什么」→ 用「新 query」再检索。
- 像「人查资料」：先查一遍，发现不够，换关键词再查。

**② 多跳检索（multi-hop）**：

- 第一跳：查「问题」→ 找到「实体 A」。
- 第二跳：查「实体 A 相关的」→ 找到「答案」。
- 「查一步、看一步」——答案需要「链条式」检索。

**③ 与 Agent 结合**：迭代检索升级为「Agent 检索」——LLM 决定「查什么、查几次、要不要换方向」——**「检索」成为「工具调用」**（第十五篇 Agent 详述）。

**迭代检索的代价**：多轮 = 多倍检索 + 多倍 LLM 调用——「慢但全」——适合「高价值」问题，不适合「实时」场景。

## 4 公式解析：检索的「组合拳」效果

高级 RAG 的收益来自「多个技巧的叠加」。以「查询改写 + HyDE + 迭代」的组合为例，每步都在「提升召回」：

$$
P(\text{答案被找到}) = 1 - \prod_{i} \left(1 - P_i\right)
$$

其中 $P_i$ 是「第 $i$ 次检索找到答案的概率」。

对这条式子做三步拆解：

- **第一步，读懂 $1 - P_i$**：第 $i$ 次检索「没找到」的概率。
- **第二步，读懂连乘**：假设各次独立，「都没找到」的概率是连乘——「至少一次找到」= 1 - 连乘。
- **第三步，读出叠加效应**：改写（$P_1$ 提升）+ HyDE（$P_2$ 提升）+ 迭代（多轮 $P_i$）——**每个技巧单独提升一点「单次命中率」，叠加后「总命中率」大幅提升**。这就是「高级 RAG 的组合拳」：**每个技巧是「一块拼图」，合起来「把漏网降到最低」**。

**辨析｜易错点：** 高级 RAG 的「技巧」不是「越多越好」——每个技巧加「一次 LLM/检索调用」（延迟与成本）。**「技巧的收益」与「延迟的代价」要平衡**：简单查询用基础 RAG，复杂查询用高级 RAG——「按需升级」。

## 5 高级 RAG 的工程配方

| 场景 | 技巧 |
| --- | --- |
| query 模糊 | 查询改写（澄清/扩展） |
| query 与文档表述鸿沟 | HyDE |
| 复杂问题多子题 | 多查询分解 |
| 答案需多文档组合 | 迭代/多跳检索 |
| 全都要（生产） | 改写 + 混合检索 + Rerank + 迭代 |

**一个生产级 RAG 的完整管线**：查询改写 → 混合检索（BM25 + 稠密）→ Rerank → （可选）迭代再检索 → 生成（带引用）。

## 6 小结

- 基础 RAG 的盲区：**query 表述不清、表述鸿沟、一次检索不够**。
- **查询改写**：澄清/扩展/分解——让 query「更适合检索」。
- **HyDE**：用「假设答案」检索——「文档形态匹配文档」。
- **迭代检索**：多轮/多跳——「边查边决定下一步」。
- 组合拳：**每个技巧提升「单次命中」，叠加后「总命中大幅提升」**——但要注意延迟代价。
