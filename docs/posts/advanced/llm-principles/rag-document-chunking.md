## 为什么「切块」是 RAG 的第一道坎

RAG 检索的粒度是「块」（chunk）——但「一块该多大」「怎么切」直接影响检索质量。**切太大**：块里混着无关内容，检索「不精准」；**切太小**：块里信息不完整，检索到「半句话」；**切太随意**：把「语义完整的段落」劈成两半，检索到「残缺信息」。切分策略的本质：**让「每个块」恰好是「一个完整的信息单元」**——既能被检索器「精准匹配」，又能给 LLM「完整上下文」。<span class="marginnote">切分的「粒度悖论」：<strong>「检索要精准」（块小）与「上下文要完整」（块大）互相拉扯</strong>——切分就是在这个拉锯里找平衡。没有「普适的最优切法」——文档类型（论文/对话/代码/合同）不同，最优切法不同。这篇讲三种主流策略与「怎么选」。</span>

## 1 固定窗口切分：最简单、最常用的基线

**固定窗口切分（fixed-size chunking）**：按「固定长度」切——每 $n$ 个 token（或字符）一块，可加「重叠」：

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=512,    # 每块长度（token）
    chunk_overlap=50,  # 相邻块重叠（token）
)
chunks = splitter.split_text(document)
```

**chunk_size**：每块长度（如 512 token）。
**overlap**：相邻块的重叠（如 50 token）——避免「切断语义」在「切口」附近。

**为什么用重叠**：固定切分「不管语义」，会在「句子中间」切断——重叠让「切口附近的信息」在「相邻两块」里都出现，检索时「切口处的信息」也能被找到。

**优点**：简单、可控、可预测（块数固定）。
**缺点**：**不管语义**——一个块可能「从上一段的结尾切到下一段的开头」，语义不完整。**对「段落/句子」结构强的文档，固定切分是「浪费」**。

**适用**：通用场景、无法预知结构的文档、作为「基线」对比。

## 2 语义切分：让「语义完整」决定切点

**语义切分（semantic chunking）** 的直觉：**在「语义边界」处切**——句子结束、段落结束、话题转换处。

**实现方式**：

**① 结构启发式**：

按「句子/段落」切：以「换行符」「句号」为边界。
按「标题/章节」切：用文档结构（Markdown 的 `#` 标题、PDF 的段落）做边界。
简单、免费——「标点与空行」就是「语义边界」的近似。

**② 嵌入相似度切分**：

把文本切成「小段」（如句子），对相邻小段算「嵌入相似度」。
相似度「断崖式下降」处 = 「话题转换」= 切点。
更「语义化」——能抓住「话题转换」这种「结构启发式抓不到的边界」。

**语义切分的优点**：块「语义完整」——检索到的块「是一个完整话题」，LLM 用起来「上下文连贯」。
**缺点**：比固定切分「贵」（要算嵌入）、块大小「不可预测」（语义块长短不一）。

## 3 结构感知切分：尊重文档的「骨架」

**结构感知切分（structure-aware chunking）** 针对「有结构」的文档（代码、Markdown、HTML、合同、论文）：

**按文档结构切**：Markdown 按「标题层级」切、代码按「函数/类」切、HTML 按「标签块」切。
**保留结构信息**：把「标题/上下文」附在块上（如「块的开头加所属章节标题」）——检索时「块自带语境」。
**父子块（parent-child chunking）**：**子块**（小、精准）用于检索，命中后返回**父块**（大、完整）给 LLM——「检索用小的、生成用大的」。
**元数据**：给块加「来源、标题、时间」等标签——「可追溯」与「过滤」的基础。

**为什么结构感知重要**：代码的「函数」是「天然的信息单元」——按函数切，检索到「一个完整函数」，LLM 能直接「读懂」；按固定长度切，函数被「劈开」，检索到「半个函数」，LLM「看不懂」。**「结构的完整性」对「语义的完整性」至关重要**。<span class="marginnote">「父子块」是结构感知的经典技巧：<strong>「检索的粒度」与「生成的粒度」可以不同</strong>——子块小（检索准）、父块大（上下文全）。命中子块后「向上取父块」，既「找到准确位置」又「给足上下文」。这是「检索精准」与「上下文完整」矛盾的「两全解法」。</span>

## 4 公式解析：切分的「检索-召回」权衡

切分策略的核心是「块大小」对「检索效果」的影响。设文档被切成 $C$ 块，每块大小 $s$（token），命中某信息需「该信息所在的块被检索到」。召回率近似：

$$
\text{Recall} \approx \frac{\text{命中块的信息覆盖}}{\text{总信息}} \propto \frac{s \cdot k}{L} \quad \text{（k 为检索块数，L 为文档长）}
$$

对这条式子做三步拆解：

- **第一步，读懂分子 $s \cdot k$**：检索到的「总内容」= 每块大小 × 检索块数。**块越大（$s$ 大）或检索越多（$k$ 大），覆盖信息越多**。
- **第二步，读懂矛盾**：块大 → 召回信息多，但**精准度下降**（块里混着无关内容，匹配「不聚焦」）；块小 → 精准但召回可能不足（信息被切碎，命中难度上升）。**「召回（多）」与「精准（准）」的权衡由 $s$ 决定**。
- **第三步，读出「最优块」**：理想块 = 「尽可能小但信息完整」——**「小而完整」是切分的目标**。语义切分/结构感知正是在逼近「小而完整」：让每块「恰好是一个完整信息单元」。

**辨析｜易错点：** 切分不是「越大越好」也不是「越小越好」——它取决于「查询的粒度」。**「问答型查询」（要精准答案）适合小块；「摘要/综述型查询」（要完整话题）适合大块**。切分策略要与「下游任务」匹配——没有「万能切法」。

## 5 工程实践清单

1. **先看文档类型**：代码用结构感知、论文用章节、对话用轮次、通用用固定窗口。
2. **块大小经验值**：300–800 token 是常用区间（太短信息碎、太长检索钝）。
3. **重叠 10–20%**：缓解「切口切断语义」。
4. **父子块**：检索子块、返回父块——「两全」。
5. **元数据**：块带「来源、章节、时间」——「可追溯 + 可过滤」。
6. **评测**：用「检索召回率」与「下游 QA」评估切分方案——「数据说话」。

## 7 数值算例：块大小与召回覆盖

设 100k token 文档、检索 top-5 块：

| 块大小 | 块数 | 检索覆盖 | 特点 |
| --- | --- | --- | --- |
| 512 | 195 | 约 2560 token | 精准、聚焦 |
| 1000 | 100 | 约 5000 token | 折中 |
| 2000 | 50 | 约 10000 token | 完整、但混噪声 |

**读这张表**：块越大、检索覆盖越全，但块内「无关内容」越多、匹配越钝。**「精准」与「完整」的拉锯，就是块大小的本质权衡**——实践中 300–800 token 是「精准度与完整性」的常用平衡区。

**辨析｜易错点：** 块大小「不是全局统一最优」——同一文档里「不同部分的信息密度」不同（引言密度低、结论密度高）。**更精细的做法是「自适应切分」**：信息密度高的部分切小、密度低的部分切大——但这需要额外计算，是否值得按任务决定。

## 8 文档类型 → 切分策略速查

| 文档类型 | 推荐切法 | 理由 |
| --- | --- | --- |
| 代码 | 结构感知（按函数/类） | 函数是天然单元 |
| 论文/报告 | 结构感知（按章节） | 章节语义完整 |
| 对话 | 按轮次 | 一轮是一个话题 |
| 通用网页 | 固定窗口 + 重叠 | 无固定结构 |
| 长话题文 | 语义切分 | 话题边界清晰 |

**选切法的第一原则**：**看文档有没有「天然结构」**——有结构用结构感知，没结构用固定/语义。切分不是「一套打天下」，而是「按文档类型定制」。

## 9 小结

- 切分的本质：**让每块「小而完整」**——检索精准与上下文完整的权衡。
- **固定窗口**：简单基线，用「重叠」缓解切口问题。
- **语义切分**：句子/话题边界切——语义完整但较贵。
- **结构感知**：按文档骨架切 + 父子块——「检索小、生成大」。
- 最佳实践：**先看文档类型，再选切法；用「召回率 + QA」评测**。
