## 为什么分词不只是"切一下"

分词是模型的**第一层感知**，而任何感知都会带来偏置。数字被切碎导致数学能力弱，代码缩进被空格记号污染导致代码质量差，甚至攻击者可以**故意构造 token 序列来绕过安全护栏**。这些都不是「分词算法好不好」的问题，而是**表示层固有的副作用**——理解它们，才能解释模型很多「莫名其妙」的行为，也是设计 tokenizer 时绕不开的权衡清单。<span class="marginnote">一个经典现象：大模型在「加减大数」上频频翻车，很多人归因于模型笨，但根源常常在分词——`13579` 可能被切成 `1` `357` `9` 三个 token，模型根本没把数字当作整体看。</span>

## 1 数字切分：数学能力的隐形天花板

BPE 按频率合并，而数字的分布极其零散：`13579` 几乎不会连续出现第二次。于是数字被切成**单数字或小段数字**，模型看到的不是一个数，而是一串孤立的记号。

后果很直接：

- **位数比较失效**：`99` 与 `100` 的 token 数不同，模型可能误判大小。
- **加减乘除退化为模式匹配**：模型记的不是「计算」，而是「见过类似 token 串的答案」。
- **大数灾难**：超过常见范围的数字（如身份证号、长账号）完全不可靠。

一些缓解手段：

- **数字整词保留**：在训练数据或分词规则中，把一定长度内的数字串整体入词表。LLaMA 就保留了数字模式的合并。
- **逐位数字化**：某些研究直接按「单数字 token」建模，牺牲压缩率换取每位数字可独立参与计算。
- **频率加权**：在 BPE 统计时给数字对加权，让数字更早合并。<span class="marginnote">这也是为什么很多模型在「数学题」上表现差、在「带格式的日期/金额」上表现好——前者数字无规律，后者数字有固定模式，能被 tokenizer 记住。理解了分词，就理解了模型的一半「偏见」。</span>

## 2 代码与空白：缩进和命名之争

代码对分词有两个特殊要求：**缩进敏感**与**符号密度高**。

- **空格被符号化**：SentencePiece 把空格编码为 `▁`。Python 里缩进是语义（4 空格 vs 8 空格），若 `▁` 与缩进混合切分，模型要把「缩进级别」从 token 串里重新推断出来——这是**额外负担**。
- **标识符过长**：`get_user_profile_data` 这样的蛇形命名会变成一长串 token，模型难以整体把握。研究者发现，把 snake_case/camelCase 的拼接点在分词阶段拆开（如 `get_user_profile_data` → `get` + `_user` + `_profile` + `_data`）能显著提升代码模型表现。
- **符号序列**：`->`、`::`、`=>` 等组合符号能否被合并成单 token，直接影响语法学习效率。<span class="marginnote">代码语料的分词质量可以用「括号配对数」「缩进还原率」来量化。Starcoder、CodeLlama 在词表里专门为代码加了高频符号 token，就是针对这一副作用。</span>

## 3 拼写与形态：拼写敏感性的丧失

子词分词的一个隐性代价是**拼写能力下降**：模型见过 `un`、`##happi`、`##ness` 组合，但未必见过完整拼写 `unhappiness`。

- **拼写错误容忍**：`accidential` 可能被切得面目全非，模型把「错拼」当成「新词」。
- **字符级信息丢失**：需要逐字符判断的任务（如回文、字母计数、首字母缩写）在子词层做得稀烂。
- **对抗性拼写**：`str!ke`、`wh1te` 这类「混淆拼写」可以绕过词级过滤——因为分词后的 token 串在词表里是干净的。<span class="marginnote">这带来一个有趣的应用：<strong>鲁棒性训练</strong>。故意把训练文本中的词替换为「子词层面接近」的变体，让模型学会在噪声拼写下保持语义——类似计算机视觉里的数据增强。</span>

## 4 安全问题：分词即攻击面

分词层不只是「性能问题」，更是**安全攻击面**。两个主要方向：

**方向一：token 走私（token smuggling）。** 安全过滤器通常在文本层检查恶意内容（如「如何制造炸弹」）。攻击者把敏感词拆成 `如何 制 造 炸 弹`，文本层看似无害，但模型分词后拼出的 token 序列依然携带恶意语义。**文本层的过滤与模型实际看到的 token 不一致，就是漏洞。**

**方向二：对抗性 token 注入。** 精心构造的字符序列（如 Unicode 变体、全角/半角混淆）可以让分词结果「意外」接近有害模式，或者让安全对齐的负样本绕过。<span class="marginnote">相关研究（如「Token-level adversarial attacks」）发现：替换一两个字符使 token 切分漂移，就可能把「安全」句变成「有害」句——因为模型的 SFT 数据里只见过「安全切分」形态的样本。</span>

**缓解思路**：

- **字节级净化**：在字节层面归一化（统一大小写、转义、去除不可见字符），让攻击者难以用变体绕过分词。
- **对齐训练时的多样性**：在安全数据里刻意加入「被奇怪切分」的有害样本，让模型学会在 token 层面也识别有害意图。
- **双层检查**：输入侧按「模型实际分词后的序列」做安全检测，而不是只查原始文本。

## 5 公式解析：分词把「文本距离」变成「token 距离」

分词副作用的一个统一视角：它把原始文本嵌入到一个**记号空间**，文本间的相似性被重新定义。设两条文本 $A$、$B$ 分词后为 $T_A$、$T_B$，定义记号层的编辑距离：

$$
d_{\text{token}}(A, B) = \text{EditDist}(T_A, T_B)
$$

对这条式子做三步拆解：

- **第一步，读懂 $\text{EditDist}$**：它是把 $T_A$ 变成 $T_B$ 所需的最少编辑操作数（替换/插入/删除）。在字符层面这是经典编辑距离；在 token 层面，一次「替换」替换的是整个子词。
- **第二步，理解粒度迁移**：字符层相似的词（`cat` vs `cut`，差 1 字符）在 token 层可能距离很大（如果 `cat` 是一个 token、`cut` 是另一个 token，替换代价是 1 个 token）；而语义相近的词（`run` vs `running`）因为共享子词，token 距离反而小。
- **第三步，读出副作用**：**任何基于文本的相似性、聚类、检索与安全判断，在分词后都会被重新度量。** 攻击者利用的正是「字符层距离大、token 层距离小」或反之的错位。安全与鲁棒性的本质工作，就是让模型「看到」的 token 距离与我们「想要」的语义距离对齐。

**辨析｜易错点：** 不要把「分词副作用」都归咎于 BPE 实现。副作用是**表示层固有的**：只要用子词表示文本，数字切分、拼写漂移、token 走私就都存在。换算法（Unigram/WordPiece）只能改变副作用的分布，不能消除它们。

## 6 小结

- **数字切分**让模型对数字「只见树木不见森林」，是数学能力的天花板之一；缓解靠整词保留或逐位建模。
- **代码**对空格、缩进、长标识符敏感，词表需为符号与拼接点专门优化。
- **子词分词牺牲拼写能力**，错拼与对抗拼写可绕过字面过滤。
- 分词是**安全攻击面**：token 走私与对抗性 token 注入利用「文本层与 token 层的不一致」。
- 统一视角：分词把文本相似性重定义为 **token 距离**，安全工作的本质是让两者对齐。
