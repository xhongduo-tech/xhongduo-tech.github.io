## 为什么工具需要「统一接口」

每家公司的工具都不一样——数据库、API、文件系统、浏览器。如果 Agent 要「接 N 个工具」，就要「写 N 个适配器」——**每个工具一套自定义协议，成本爆炸**。**MCP（Model Context Protocol，模型上下文协议）** 是一个「开放标准」——**把「模型 ↔ 工具」的接口统一起来**：任何工具只要「实现 MCP」，任何模型/Agent 框架就能「即插即用」——像「USB 接口」之于「外设」。<span class="marginnote">MCP 由 Anthropic 在 2024 年提出，迅速成为「模型-工具接口」的事实标准。它的定位类比：<strong>「MCP 之于 AI 工具，如 USB 之于外设、HTTP 之于 Web」</strong>——统一协议让「生态」成为可能：工具写一次，处处可用。它的核心是「把工具调用、资源读取、上下文管理」标准化。</span>

## 1 MCP 解决什么问题

没有 MCP 之前，Agent 接工具的痛点：

- **每个工具一套协议**：A 公司工具用 REST、B 公司用 SDK、C 公司用专用格式——Agent 要为每个写适配器。
- **上下文不统一**：工具返回的数据格式各异——Agent 要「解析各种格式」。
- **集成成本高**：新工具接入 = 重新开发——「生态」难生长。

**MCP 的标准化**：

- **统一接口**：所有工具通过「同一个协议」暴露能力——「工具发现、调用、返回」标准化。
- **统一上下文**：工具结果、资源、提示都通过「标准化的上下文」传递给模型。
- **即插即用**：工具实现 MCP → 任何 MCP 客户端（Agent 框架）直接使用。

**类比**：MCP 之前的 Agent 是「每个工具一个充电口」；MCP 之后是「统一的 USB-C」。

## 2 MCP 的核心架构

MCP 采用「客户端-服务器」架构：

```
模型/Agent（MCP 客户端）
    │  MCP 协议（JSON-RPC over stdio/HTTP）
    ├── MCP 服务器（工具 A：数据库）
    ├── MCP 服务器（工具 B：文件系统）
    └── MCP 服务器（工具 C：API）
```

- **MCP 客户端**：Agent 框架（Claude、LangChain 等）——发起请求、接收结果。
- **MCP 服务器**：工具提供方——把工具「包装」成 MCP 协议——暴露「工具/资源/提示」。

**MCP 的三类「原语」**：

1. **工具（Tools）**：可调用的函数——「搜索、计算、执行」——Agent 主动调用。
2. **资源（Resources）**：可读取的数据——「文档、配置、数据库内容」——模型需要时读取。
3. **提示（Prompts）**：可复用的提示模板——「预定义的指令」——帮助模型「用对工具」。

**一次 MCP 交互**：

1. Agent（客户端）向服务器「发现可用工具」。
2. 用户请求 → Agent 决定调用「工具 A」。
3. 客户端向「服务器 A」发「工具调用」请求（JSON-RPC）。
4. 服务器执行、返回「结构化结果」。
5. Agent 把结果给模型，模型生成回答。

## 3 MCP 与 Function Calling 的关系

MCP 与「Function Calling」（上一节）不是「竞争」而是「分工」：

| 维度 | Function Calling | MCP |
| --- | --- | --- |
| 层次 | 模型「如何输出调用」（协议内） | 工具「如何暴露」（系统间） |
| 范围 | 单模型 + 单框架 | 跨模型、跨框架、跨工具 |
| 目的 | 让模型「会调用」 | 让工具「可接入」 |
| 类比 | 「语言的语法」 | 「设备的接口」 |

**关系**：Function Calling 是「模型层的调用协议」，MCP 是「工具层的互操作协议」——**MCP 把「工具接入」标准化，Function Calling 把「模型输出」标准化**——两者结合：模型用 Function Calling 表达意图，MCP 把意图路由到「任意实现 MCP 的工具」。

**为什么要「再标准化一层」**：Function Calling 各家 API 的「工具声明格式」仍有差异（OpenAI/Anthropic/Google 各有细微不同）；MCP 让「工具声明」与「调用」在「工具侧」统一——**工具写一次，适配所有模型**。<span class="marginnote">MCP 的「生态价值」在于「一次实现、处处可用」：<strong>工具开发者只写一个 MCP 服务器，就同时被 Claude、LangChain、各种 Agent 框架使用</strong>——工具的「市场」被打开了。这也推动了「工具生态」的爆发——GitHub、Slack、各种 SaaS 都在发布 MCP 服务器。</span>

## 4 公式解析：MCP 的「接口成本」收益

MCP 的价值可以用「接口的复杂度」来量化。设工具数 $T$、框架数 $F$：

**无 MCP**：每对「工具-框架」要写适配器——总适配器数：

$$
\text{Adapters}_{\text{无 MCP}} = T \times F
$$

**有 MCP**：每个工具实现一次 MCP、每个框架实现一次客户端——总实现数：

$$
\text{Adapters}_{\text{MCP}} = T + F
$$

对这两条式子做三步拆解：

- **第一步，读无 MCP**：$T \times F$——「每对组合都写适配器」——工具与框架数量增长，成本「乘积爆炸」。
- **第二步，读有 MCP**：$T + F$——「每个工具写一次 + 每个框架写一次」——成本「线性增长」。
- **第三步，读出标准化的价值**：**$T \times F$ vs $T + F$**——工具/框架越多，MCP 的节省越巨大（10 工具 × 5 框架 = 50 vs 15）。**这就是「协议」的经济学：标准化把「组合成本」变成「线性成本」**。

**辨析｜易错点：** MCP 不是「唯一的工具标准」——也有「OpenAPI」「function-calling 直连」等替代。**MCP 的取舍**：标准化带来「互操作」，但「协议的抽象」可能「不完全适配某些特殊工具」——「标准 vs 灵活」的经典权衡。选型看「生态」——MCP 生态在快速扩张，是当前的主流趋势。

## 5 MCP 的工程实践

- **服务器开发**：用 SDK（Python/TS）把工具包成 MCP 服务器——「写一次，处处用」。
- **客户端集成**：Agent 框架内置 MCP 客户端——「发现工具、路由调用」。
- **安全边界**：MCP 服务器的权限控制——「工具能做什么、不能做什么」（敏感操作分级）。
- **生态现状**：官方 MCP 服务器（文件、Git、浏览器）+ 第三方（数据库、SaaS）——「工具市场」成型。

## 6 小结

- **MCP**：标准化的「模型-工具接口」——「工具的 USB-C」。
- 解决「每工具一套协议」的碎片化——「写一次，处处可用」。
- 架构：**客户端-服务器**——工具（调用）+ 资源（读取）+ 提示（模板）。
- 与 Function Calling 分工：**模型层（会调用）+ 工具层（可接入）**。
- 价值：$T \times F$ → $T + F$——**标准化把「组合成本」变「线性成本」**。
