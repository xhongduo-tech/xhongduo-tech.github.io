## 为什么"模型越大越贵"可以被打破

直觉上，参数量决定计算量。MoE（Mixture of Experts，混合专家）打破了这条铁律：**参数很多，但每个 token 只激活其中一小部分**。它把 FFN 复制成 $E$ 份「专家」，由路由器为每个 token 挑选 top-k 个专家计算——于是模型参数量可以到万亿级，而**单 token 的前向计算量只相当于一个几十 B 的稠密模型**。<span class="marginnote">MoE 的思想最早可以追溯到 1991 年 Jacobs 等人的「混合专家」，2017 年 Shazeer 把它用稀疏门控引入深度学习。真正让它进入大模型主流的是 Switch Transformer（2021）与 DeepSeekMoE、Mixtral——「稠密模型的容量 + 稀疏模型的计算」。</span>这篇先立住 MoE 最核心的两个概念：**稀疏激活**与**条件计算**。

## 1 条件计算：专家只在需要时被调用

**条件计算（conditional computation）**：网络中的不同部分根据输入决定是否被激活——不是所有参数都参与每个样本的前向。

对比两种模型：

- **稠密模型**：每个 token 前向时，**所有参数都被调用**。参数越多，计算越贵。
- **MoE 模型**：每个 token 前向时，**只有被路由器选中的少数专家被调用**。参数多 ≠ 计算贵。

把 FFN 替换成 MoE-FFN：

$$
\text{FFN}_{\text{MoE}}(x) = \sum_{i \in \mathcal{T}(x)} w_i \cdot \text{Expert}_i(x)
$$

其中 $\mathcal{T}(x)$ 是路由器为 token $x$ 选中的专家集合（大小 $k$，通常 1 或 2）。**只有 $k$ 个专家参与计算，其余 $E - k$ 个专家「在却不动」**——这就是条件计算：参数总量与计算量解耦。<span class="marginnote">类比一个巨型医院：全部科室都配备齐全（参数多），但一个病人只看 1-2 个科（激活少）。「科室数量」决定医院的「总容量」，「单病人看科数」决定「单次服务成本」。MoE 的『参数/计算比』就对应『科室数/就诊科室数』——这是它「便宜大碗」的本质。</span>

## 2 稀疏激活：top-k 路由

**稀疏激活（sparse activation）** 指：每一层的专家中，只有极少数被「点亮」。路由器（router / gate）为每个 token 计算对 $E$ 个专家的「匹配分数」，然后取 **top-k** 个：

$$
w_i = \text{softmax}(W_r x)_i, \qquad \mathcal{T}(x) = \text{top-k}(w)
$$

- 路由分数 $w_i$：token 与专家 $i$ 的亲和度（通常一个线性层 + softmax）。
- top-k：只保留分数最高的 $k$ 个专家（$k \ll E$）。
- 输出：选中的专家输出按权重加权求和。

**为什么稀疏能工作**：路由让「每个专家专精一类模式」。训练中，相似的 token 倾向于路由到相同的专家——专家自动分化，像「词性专家」「代码专家」「数学专家」自发涌现。<span class="marginnote">直观例证：Mixtral 8×7B（8 个专家、每 token 激活 2 个）实测中，不同专家对「代码」「数学」「自然语言」有明显偏好。稀疏路由是「分工」的机制——没有分工，就没有 MoE 的收益。</span>

## 3 为什么 MoE 能"以少算多"：参数-计算解耦

MoE 最反直觉的地方是「参数多但不算」：

| 维度 | 稠密模型 | MoE 模型 |
| --- | --- | --- |
| 总参数 | $P$ | $E \cdot P_{\text{expert}}$（很大） |
| 单 token 计算 | $O(P)$ | $O(k \cdot P_{\text{expert}})$（很小） |
| 激活参数比 | 100% | $k/E$（如 2/8 = 25%） |
| 显存（权重） | $P$ | $E \cdot P_{\text{expert}}$（全量加载） |
| 推理速度 | 慢（全算） | 快（只算选中的） |

以 Mixtral 8×7B 为例：总参数约 47B（8 个 7B 级专家 + 共享组件），但每个 token 只激活 2 个专家——**有效计算量只相当于 ~13B 的稠密模型**。这就是「47B 的容量、13B 的计算成本」。

**关键提醒**：MoE 省的是**计算**，不省**显存**——所有权重都要加载到显存（或磁盘）。所以 MoE 的「便宜」体现在**推理算力/训练算力**，不体现在「显存占用」。部署 MoE 时，显存还是按总参数算——这是工程上最常踩的坑。<span class="marginnote">换个说法：MoE 把「容量」和「算力」分开卖——容量贵（显存/存储），算力便宜（每次只用一小块）。对「容量需求大、单次推理预算有限」的场景（如巨量知识、多语言、长尾任务），MoE 尤其划算。对显存紧张的场景，MoE 反而不友好。</span>

## 4 公式解析：MoE 层的前向

一个 MoE 层的完整前向：

$$
y = \sum_{i=1}^{k} \underbrace{\frac{e^{w_i}}{\sum_{j \in \mathcal{T}} e^{w_j}}}_{\text{归一化权重}} \cdot \text{Expert}_i(x), \qquad w = \text{top-k}\big(\text{softmax}(x W_r)\big)
$$

对这条式子做四步拆解：

- **第一步，读懂路由器**：$x W_r$ 是 token 对每个专家的打分（$W_r \in \mathbb{R}^{d \times E}$），softmax 变成「概率」。top-k 选出 $k$ 个，$\mathcal{T}$ 是它们的集合。
- **第二步，读懂归一化**：权重 $e^{w_i}/\sum_{j \in \mathcal{T}} e^{w_j}$ 是在**选中的 $k$ 个专家之间**重新归一化（不是对全部 $E$ 个）。这保证输出是「选中专家的加权混合」，权重和为 1。
- **第三步，理解专家计算**：$\text{Expert}_i(x)$ 是第 $i$ 个专家的 FFN 前向——**只有 $k$ 个专家执行了 FLOPs**，其余 $E-k$ 个专家零计算。
- **第四步，读出稀疏性**：计算量 $O(k \cdot P_{\text{expert}})$，与 $E$（总专家数）无关——**只要 $k$ 固定，专家再多也不加计算量**。这就是「参数随 $E$ 涨、计算不随 $E$ 涨」的数学表达。

**辨析｜易错点：** 稀疏激活 ≠ 剪枝。剪枝是「删掉不重要参数」，MoE 是「参数都在，只是某次前向不调用」——被跳过的专家下次可能被用到。MoE 的稀疏是「运行时按需」，不是「永久删除」。另外，注意力部分仍是稠密的——MoE 只替换 FFN，不替换注意力。

## 5 MoE 的收益与代价清单

**收益**：

- 用相同算力换更大的模型容量（知识、多语言、长尾覆盖）。
- 训练更省算力（同样质量下训练 FLOPs 更低）。
- 推理可扩展（token 按需分配，批内异构负载友好）。

**代价**：

- 显存/存储按总参数算（比稠密同计算量大）。
- 路由有额外开销（路由器本身 + top-k 计算）。
- 训练易失衡（专家负载不均、专家坍塌）——需要负载均衡技术。
- 推理工程复杂（专家分片、通信、缓存管理）。

## 7 数值算例：专家数与激活比

固定 $k=2$，专家数 $E$ 变化时「激活参数比」：

| 专家数 $E$ | 激活比 $k/E$ |
| --- | --- |
| 8 | 25% |
| 32 | 6.25% |
| 64 | 3.1% |
| 256 | 0.8% |

**读这张表**：专家越多、激活比越低——**「容量」与「计算」的解耦程度随 $E$ 放大**。DeepSeek-V3 用 256 个路由专家、激活 37B/671B ≈ 5.5%，正是「以 0.8%–5% 的激活参数承载全部知识」的极致形态。**MoE 的吸引力随专家数增长**——但通信与负载的工程代价也随之增长。

**辨析｜易错点：** 「激活比」不是「越压越低越好」——专家太细、路由太碎会让「每个 token 分到的知识太少」，且通信开销上升。**$k$ 与 $E$ 是「容量-效率-通信」的三方权衡**，不是单目标最小化。

## 8 MoE 收益随阶段的分布

| 阶段 | MoE 的收益 |
| --- | --- |
| 训练 | 同样算力、更大容量 |
| 推理 decode | 单 token 算得少、快 |
| 显存占用 | 无收益（权重全加载） |
| 边缘端部署 | 负面（显存受限） |

**读这张表**：MoE 的「便宜」集中在「算力」维度，在「显存」维度没有优势甚至吃亏。**选型时要分清「我缺算力还是缺显存」**——缺算力（云端大模型）选 MoE，缺显存（边缘端）选稠密小模型。

## 9 小结

- MoE = **稀疏激活 + 条件计算**：专家全加载、按 token 选 top-k 激活。
- 核心收益：**参数容量与计算量解耦**——「总参数大、单次算得少」。
- Mixtral 8×7B：47B 容量、~13B 计算量，是「以少算多」的典型。
- 省计算不省显存——部署时显存按总参数算。
- 代价：负载失衡、路由开销、推理工程复杂度。
