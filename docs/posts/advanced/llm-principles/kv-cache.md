## 为什么 KV Cache 是推理的「分水岭」

在第七篇我们从「显存瓶颈」角度认识了 KV Cache。这一篇从**推理机制**本身讲透：自回归生成每一步都要「重新看历史」，如果不缓存，每一步都要重算全部历史的注意力——总代价 $O(L^2)$；缓存后，每步只算新 token，总代价降到 $O(L)$。**KV Cache 是「用显存换时间」的经典工程**，也是理解 prefill/decoding 两阶段、长上下文成本、批量调度的核心。<span class="marginnote">KV Cache 不是「可选优化」，而是「推理引擎的默认基础设施」——vLLM、TensorRT-LLM、HF 的 $O(L^2)$ 都在管理它。没有它，自回归推理慢到不可用。理解 KV Cache，是理解「为什么推理贵」「为什么长文本更贵」「为什么并发受限」的总钥匙。</span>

## 1 自回归推理的两阶段：Prefill 与 Decoding

一次生成请求分成两个阶段：

**Prefill（预填充）**：

输入完整提示（如用户问题），一次性前向，计算所有位置的 Q/K/V。
把 K/V **写入 KV Cache**。
特点是「一次算很多」——计算密集，吞吐高。

**Decoding（解码）**：

逐 token 生成：每步只输入「最后一个 token」，前向时**从 KV Cache 读取历史 K/V**，只算新位置的 Q/K/V。
新位置的 K/V 追加进缓存。
特点是「每步算一点」——内存带宽受限，慢且串行。

**为什么 Prefill 快、Decoding 慢**：Prefill 是「大矩阵乘」（算得多但吞吐高）；Decoding 每步只有「一个 token 的计算量」（算得少但每步都要读全部历史 KV）——**Decoding 是「内存带宽瓶颈」**，吞吐上不去。

## 2 KV Cache 的读与写

KV Cache 的组织：形状 `[2, B, H_kv, L, d_h]`（2 表示 K 和 V），即「K 一份、V 一份」的两份张量，各自形状为 `[batch, num_kv_heads, seq_len, head_dim]`。

**写入**：每生成一个新 token，把它各层的 K、V 追加到缓存末尾。

**读取**：第 $t$ 步，注意力计算用「全部缓存的 K/V」（长度 $t$）与「当前 Q」（长度 1）。

**关键：KV Cache 只缓存「历史」**，而历史 Q 不需要缓存（前文已说明）。所以缓存体积随序列长度线性增长，与「已生成的 token 数」直接相关。

**PagedAttention（vLLM）** 进一步把 KV Cache 按「页」管理——像操作系统的虚拟内存：不同请求的动态长度不再造成「连续分配的碎片」，而是按页分配、按需增长，利用率从 ~60% 提到 ~95%。<span class="marginnote">PagedAttention 是 KV Cache 工程化的重要一步：它把「显存碎片」问题变成「页表管理」问题——系统里的「块表」记录每个请求的 KV 在哪些页。这让「动态长度」的高并发成为可能，也是 vLLM 吞吐大幅领先的原因之一。</span>

## 3 为什么 KV Cache 决定「并发上限」

推理服务的「并发请求数」直接受 KV Cache 显存约束：

$$
\text{可并发请求数} \approx \frac{\text{可用显存}}{\text{平均每请求 KV 大小}}
$$

每请求 KV = $2 \times \text{层数} \times \text{KV 头数} \times \text{头维} \times \text{序列长} \times \text{字节}$。序列越长，每请求越贵，并发越少。

**这解释了三个现象**：

- 短文本快、长文本慢——长文本的 KV Cache 占满显存，只能服务更少并发。
- 批量推理是「显存游戏」——batch 越大吞吐越高，但 KV 显存线性吃紧。
- GQA/MLA/KV 量化（第七篇讲的）是「提高并发上限」的直接手段——**压缩 KV = 塞更多请求**。

## 4 公式解析：缓存与不缓存的复杂度对比

设序列总长 $L$，注意力层数 $N$，头维 $d_k$，KV 头数 $H_{kv}$。**不缓存**时，第 $t$ 步要重算前 $t-1$ 个位置的 K/V：

$$
\text{FLOPs}_{\text{no-cache}} = \sum_{t=1}^{L} O(t) = O(L^2)
$$

**缓存**时，第 $t$ 步只算新 token 的 K/V 与注意力：

$$
\text{FLOPs}_{\text{cache}} = O(L), \qquad \text{Mem}_{\text{cache}} = 2 \cdot L \cdot N \cdot H_{kv} \cdot d_k \cdot \text{bytes}
$$

对这三条式子做三步拆解：

- **第一步，读懂不缓存的 $O(L^2)$**：第 $t$ 步要重算 $t$ 个位置的 K/V，总计算是 $\sum t = O(L^2)$——**序列越长，重复计算越多**。
- **第二步，读懂缓存的 $O(L)$**：每步只算新 token 的 K/V（$O(1)$ 个位置），总 $O(L)$——**线性**。KV Cache 正是把「平方」降成「线性」的关键。
- **第三步，读出显存换时间的本质**：$O(L^2) \to O(L)$ 省的是**计算**，$2LNH_{kv}d_k$ 花的是**显存**——**「算得少」与「存得多」是一对交易**。长上下文时代，这笔交易越来越值得，因为「算」比「存」贵。

**辨析｜易错点：** KV Cache 的「缓存」是「每层一份」，不是「全模型一份」——每层注意力有自己的 K/V 缓存（因为每层的 K/V 不同）。所以 KV Cache 大小 = 层数 × 每层大小。这也是「层数越多、KV 越贵」的原因——GQA 压缩的正是「每层的 KV 头数」。

## 5 KV Cache 的工程优化全景

| 手段 | 原理 | 效果 |
| --- | --- | --- |
| GQA/MQA | 减少 KV 头 | 缓存缩数倍 |
| MLA | 低秩压缩 | 缓存缩数十倍 |
| KV 量化（INT8/INT4） | 少字节存储 | 缓存减半/减四分之三 |
| KV 驱逐 | 只留关键 token | 长上下文有界 |
| PagedAttention | 页式管理 | 利用率提升 |
| 前缀缓存 | 共享相同前缀的 KV | 多请求复用 |

这些手段共同支撑「长上下文 + 高并发」——**KV Cache 是推理优化的主战场**（大模型部署专题会系统展开）。

## 6 小结

- 推理两阶段：**Prefill（一次算完写缓存）+ Decoding（逐 token 读缓存）**。
- KV Cache 让复杂度从 $O(L^2)$ 降到 $O(L)$——**用显存换时间**。
- Decoding 是**内存带宽瓶颈**：每步读全部历史 KV，算得少搬得多。
- **并发上限由 KV 显存决定**——长文本贵、batch 受显存约束。
- 工程优化：GQA/MLA/KV 量化/PagedAttention/前缀缓存。
