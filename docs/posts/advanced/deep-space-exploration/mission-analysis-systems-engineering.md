## 为什么从系统工程开始

上一篇《任务案例总览》回答的是「人类去过哪里、为了什么」。
但「想去火星」和「火星任务成功」之间隔着一条极长的链条：目标怎么变成指标、指标怎么分给子系统、每个子系统怎么留裕度、失败怎么兜底。
这条链条上的方法论，就是**系统工程（systems engineering）**。
<span class="marginnote">系统工程不是航天独有——第一级《算法》、第三级《软件工程》里都有「把大问题拆成小问题、再装配回去」的思维；
航天只是把它逼到了极致：没有人能在发射后上门维修，一切错误都必须在发射前暴露。
</span>深空任务动辄十亿美元、周期十年，容不得「差不多」，所以本专题第二篇必须先立住这套工程语法，后面 11 篇的所有子系统设计都要用它来叙述。

## 1 任务生命周期：从想法到归档

航天工程用**阶段（phase）**管理一个任务的一生，NASA 的标准划分是：

| 阶段 | 名称 | 核心产出 |
| --- | --- | --- |
| Phase A | 概念研究 | 任务概念、备选方案、初步成本 |
| Phase B | 初步设计 | 初步设计评审（PDR）、基线确定 |
| Phase C | 详细设计 | 关键设计评审（CDR）、图纸冻结 |
| Phase D | 建造与试验 | 总装、环境试验、发射、在轨测试 |
| Phase E | 运行 | 科学运行、长期维护 |
| Phase F | 退役 | 处置（烧毁、封存、撞月） |

**关键认识：错误发现得越晚，代价越高。
** Phase A 改一个数字几乎免费，Phase D 改一个设计可能要重新做热真空试验、推翻几个月的进度。
<span class="marginnote">这对应工程上著名的「1-10-100 法则」：设计阶段发现并修正问题的成本是 1，集成测试阶段是 10，在轨运行阶段是 100。
与第三级《软件工程》里「缺陷越晚发现越贵」是同一句话。
</span>所以系统工程的核心动作全部发生在早期：在纸面上穷尽问题，而不是在轨道上。

生命周期里最容易被新人低估的是 Phase A 的「方案空间」：一个好的概念阶段要产出一组**相互竞争的备选方案**（不同轨道、不同推进、不同载荷组合），而不是一个。
真正的工程智慧往往出现在「把看似不可能的方案排除掉」的过程中——排除的理由比选中的理由更值钱。
例如火星采样返回曾被论证为「飞掠采样、着陆采样、轨交对接采样」三条路，最终轨交对接方案靠「质量与成本最低」胜出，但其余两条的排除过程本身产出了宝贵的工程数据。

## 2 从任务目标到需求分解

系统工程的起点是一句话的**任务目标（mission objective）**，终点是一堆可验证的**需求（requirements）**。分解的链条是：

**任务目标 → 顶层需求 → 子系统需求 → 部件需求 → 试验验证项**

例如目标「研究火星古代水的痕迹」会被翻译成：环绕器携带光谱仪（质量 ≤60 kg、功耗 ≤90 W、光谱范围 0.4–3 μm）→ 光谱仪的光学系统指标 → 光学镜面的面形误差公差 → 振动试验中镜面必须经受的载荷。
<span class="marginnote">每一步翻译都要求「可验证」：写「光谱仪要好」不行，写「信噪比 ≥ 100 @ 2.5 μm」才行。
需求的验证性（verifiability）是评审会上第一个被攻击的弱点。
</span>

**辨析｜易错点：** 需求必须区分「功能需求」与「约束」。
功能需求回答「必须做什么」，约束回答「在什么条件下做」——质量上限、功率上限、工作温度范围、辐射剂量承受能力都是约束。
把约束误当功能，或把功能写成无法测量的话，是需求评审里最常见的问题。

需求管理还要配套一套**验证矩阵（verification matrix）**：每条需求对应至少一项验证方法（分析、试验、演示、检查），并写明「在哪一阶段、由谁验证」。
需求与验证方法一一对应，是评审时最常被要求补全的文件——**无法验证的需求等于不存在**。

## 3 指标与预算：质量、功率、Δv、成本

上一篇说的四条预算，在这里进入形式化。每笔预算都有一套**分配表（budget allocation）**：总值、各子系统占比、已用值、剩余值、增长裕度。

以质量预算为例，典型分配是：结构与机构约 20–25%、推进约 15–20%、电源约 20–25%、姿控与导航约 10%、热控约 5%、C&DH 约 10%、载荷约 15–20%——比例随任务类型变化，但「总额固定、彼此争抢」的格局不变。

功率预算与质量预算同构：每个子系统的功耗（工作态 / 待机态 / 峰值态）逐项列表，加总后对比电源系统的供电能力（第 8 篇），再留增长裕度。
深空任务特别要注意「工况」：同一个子系统在巡航、进入、着陆阶段的功耗完全不同——预算表其实是「多张工况表」而非一张。
<span class="marginnote">SMAD 的一个经典洞见：<strong>质量、功率、成本近似正相关</strong>——更重往往更贵，因为运载、结构、推进都要放大。
所以工程决策常常先在「干重」上做减法，而不是先问价格。
</span>成本一般用**参数估算**：拿历史任务的干重、功率、继承性（heritage）套经验公式，而不是逐项精算。

**辨析｜易错点：** 预算表里必须区分**干质量（dry mass，不含推进剂）**与**湿质量（wet mass，含推进剂）**。
推进剂质量不能拍脑袋，它由 Δv 和比冲用火箭方程反解（第 6 篇）；
把推进剂算进干质量、或忘了配管路残液，都是导致超重的经典事故。

## 4 权衡分析与设计裕度

有了预算表，决策就有了解题场。
**权衡分析（trade study）**把备选方案放到同一张打分表上：每个方案按性能、质量、成本、风险、进度逐项打分，加权重后取最优。
看似死板的打分表，作用是把「我喜欢这个方案」这种隐性偏好逼到台面上，让每个人看到分数是怎么来的。

设计上还要给不确定性留后路，这就是**裕度（margin）**。
SMAD 的指导原则是：设计越不成熟，初期的增长裕度越大——全新设计（new design）质量裕度常取 20–30%，成熟设计 10–15%，到 CDR 前裕度逐渐被消耗到接近零。
<span class="marginnote">裕度不是「留了余量就好」这么简单：裕度过大会让系统超重、方案被否，裕度过小会在集成期处处捉襟见肘。
管理裕度是在「过设计」与「欠设计」之间走钢丝。
</span>还有一类裕度是**性能裕度**：天线比要求大 1 dB、电源比要求多 10%，这换来的是后期改动的自由度。

裕度还有一种「时间维」的表达：越接近发射，设计冻结的部分越多，能改的越少。
所以进度表本身就是一份「裕度消耗表」——每过一道评审，就在某些参数上把裕度「花掉」一点、把承诺钉死一点。
成熟的系统工程管理，本质是**在正确的时间点把正确的裕度换成确定性**。

## 5 公式解析：质量增长怎么算

裕度在预算里如何落地？一条最常用的算式是质量分配与增长：

$$
M_{\mathrm{alloc}} = M_{\mathrm{est}} \times \left(1 + \frac{g_{\mathrm{allow}}}{100}\right), \qquad
M_{\mathrm{final}} = M_{\mathrm{est}} \times (1 + g_{\mathrm{actual}})
$$

- **第一步，读符号**：$M_{\mathrm{est}}$ 是某个子系统当前最可能的估计质量，$g_{\mathrm{allow}}$ 是分配给它的增长百分比裕度，$M_{\mathrm{alloc}}$ 是它在预算表中被批准占用的配额。
- **第二步，看用途**：$M_{\mathrm{alloc}}$ 出现在预算表里，告诉系统工程师「你最多能用这么多」；设计方用 $M_{\mathrm{est}}$ 开发，若 $M_{\mathrm{est}}$ 逼近 $M_{\mathrm{alloc}}$ 就触发设计变更。
- **第三步，看实际**：$g_{\mathrm{actual}}$ 是发射前实际发生的质量增长。对全新设计，历史上实际增长常达到 20–30%——所以 $g_{\mathrm{allow}}$ 必须大于预测误差，否则到集成期必然爆表。

**辨析｜易错点：** 增长裕度不是「误差项」，而是**承诺的预算**。
一个常见失败模式是：设计团队为压低总重而虚报乐观的估计质量，结果裕度被「吃掉」，到 Phase D 结构、线缆、涂层逐项加回，总质量超限，只能砍科学仪器——这就是「质量增长吞噬科学回报」的经典路径。

## 6 里程碑评审与接口管理

生命周期里真正把「各说各话」变成「一个系统」的机制，是**里程碑评审（review gate）**。每一道评审是一道关卡，不通过就不得进入下一阶段：

- **SRR（系统需求评审）**：需求基线冻结，确认「做对了事」。
- **PDR（初步设计评审）**：各子系统方案定型，预算与接口初步锁定。
- **CDR（关键设计评审）**：图纸冻结，验证「把事做对」。
- **QR / FRR（合格 / 飞行就绪评审）**：发射前的最后放行。

评审的核心对象之一是**接口控制文件（ICD）**：A 子系统给 B 子系统的每一个电气、机械、热、数据接口都要写清、签字、版本化。
接口是系统工程的「接缝」，九成集成问题的根源都在接缝上，而不在部件内部——正如第三级《软件工程》里「模块接口的错误比模块内部更致命」。

**重点**：评审的价值不在「通过」而在「暴露」。
CDR 之前，项目负责人的唯一任务是让评审专家**尽量多地找到问题**——评审组里故意安排「唱反调的人」（red team），用最坏假设攻击设计。
这与第三级《软件工程》的代码评审、第四级《安全工程》的红队演练是同一套思想：**把错误留在纸面，是系统工程最便宜的保险。
**

系统工程还要管理**风险**：每项关键风险都登记在风险表上，标注「概率 × 影响」，制定缓解措施并定期复查。
深空任务常把风险分为「设计风险」（可通过冗余、试验缓解）与「残余风险」（环境未知、知识不足，只能接受并预留退路）。
**工程不是消灭所有风险，而是把风险装进可管理的盒子里。
**

## 7 小结

- 任务生命周期分 **Phase A–F**，错误发现越晚代价越高，系统工程的重心放在早期纸上设计。
- 需求按**目标 → 顶层 → 子系统 → 部件 → 试验**逐级分解，每一步都必须**可验证**。
- 四条预算（质量、功率、Δv、成本）靠**分配表**管理，质量、功率、成本三者近似正相关。
- 决策用**权衡分析**打分表显性化，不确定性用**裕度**承接；全新设计初期质量裕度取 20–30%。
- 质量增长是深空任务的常客：$M_{\mathrm{alloc}} = M_{\mathrm{est}}(1 + g_{\mathrm{allow}}/100)$，虚报估计必然在集成期爆表。
