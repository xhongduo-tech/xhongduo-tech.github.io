## 为什么从线程块簇讲起

在 CUDA 的经典模型里，**线程块（thread block）是一座孤岛**：块内线程可以共享内存、可以 `__syncthreads()` 同步；但不同块之间，只能通过全局内存 + 原子操作 + 内存栅栏（fence）通信——慢、还要小心内存一致性的坑。TMA 解决了「块内数据搬运」的异步化，但**块与块之间的协作**依然笨重。Hopper 的新答案是 **线程块簇（thread block clusters）** 与 **分布式共享内存（DSMEM）**：让相邻的 2–8 个块组成一个「簇」，簇内任意块可以直接访问另一个块的共享内存。这是 CUDA 诞生以来第一次，跨块通信不必绕道全局内存。<span class="marginnote">从「从极限到大模型」主线的视角：我们学过的并发模型（线程、进程、消息）一直在处理「协作的成本」。GPU 的块间协作同样在权衡「同步粒度 vs 通信成本」——簇是把粒度从「块」提到「簇」、把成本从「全局内存」降到「共享内存」的一次精调。</span>

## 1 块的孤岛困境

先看清问题。两个线程块要交换数据，传统做法只有一条路：

```
块 A 写数据到全局内存
  → __threadfence()（保证写可见）
  → 块 B 原子操作/轮询，确认后读取全局内存
```

这条路有三个痛点：

**延迟高**：全局内存的往返要几百个周期，加上栅栏与原子操作，通信延迟远超共享内存（约 30 周期）。
**要「轮询」**：块 B 不知道块 A 何时写完，只能忙等或依赖原子计数——软件同步复杂且易错。
**一致性包袱**：跨块访问依赖「写后读」的全局内存一致性，程序员要小心处理可见性。

大模型 kernel 里，这类「块间协作」恰恰很多：分布式 GEMM 的分块归约、FlashAttention 的分块 softmax 汇总、卷积的 tile 边界处理。传统方式让这些协作又慢又难写——Hopper 用「簇」来解决。

## 2 线程块簇：给块一个「邻居圈」

**线程块簇（thread block cluster）**：一个由 2–8 个线程块组成的执行单元，簇内各块可以被调度到同一 GPC（图形处理簇）内、共享一组同步与内存设施。

CUDA 里声明一个簇很简单，启动 kernel 时指定簇维度：

```cuda
cudaLaunchConfig_t cfg = {};
cfg.clusterDimX = 2;          // 簇在 X 方向含 2 个块
cfg.clusterDimY = 2;          // 簇在 Y 方向含 2 个块
// 共 4 个块组成一个簇
```

- 簇的维度可以是 1D/2D/3D，各维乘积 ≤ 8（Hopper 支持一个簇最多 8 个块）；
- 簇内的块**必须同时驻留**（co-resident）——调度器保证它们在同一时刻占住 SM；
- 簇内用 `cluster.sync()` 做轻量级同步（比 grid 级同步轻得多）。

为什么「必须同时驻留」很重要？因为簇内协作依赖「我的邻居在物理上就在旁边」——只有同时驻留，共享内存的直接访问才成立。这也是簇与「任意两块间通信」的本质区别：**簇牺牲了「随便谁和谁通信」的自由，换来了「邻居间极速通信」的能力**。<span class="marginnote">对比 CPU 世界的 NUMA：簇有点像「把某些线程固定在同一个 NUMA 节点上」——牺牲调度自由度，换取局部性带来的速度。GPU 的簇把这个思路变成了头等的编程原语，而不是底层细节。</span>

## 3 分布式共享内存：敲敲墙就能说话

簇的真正价值在 **DSMEM（distributed shared memory，分布式共享内存）**：

**DSMEM**：一个簇内所有块的共享内存，构成一个逻辑上的「分布式共享内存空间」。簇内每个块，可以通过特殊的地址映射，**直接读写另一个块的共享内存**。

实现机制是两条新的 PTX 指令：

**mapa（map to address）**：把「簇内某个成员块的共享内存」映射进本地地址空间，让本地线程能直接访问。
**mapc（map to cluster）**：把「整个簇的共享内存」统一映射到本地，形成一个连续的分布式地址视图。

有了 DSMEM，块 A 把结果写进「自己的共享内存」，块 B 通过 mapa 直接读走——**不再经过全局内存，不再需要栅栏与轮询**。配合上一节的 TMA，还可以一条指令完成「共享内存 → 共享内存」的搬运（TMA 支持 DSMEM 到 DSMEM 的 bulk 拷贝）。

**辨析｜易错点：** 有人把 DSMEM 理解成「跨 GPU 的共享内存」——这是错的。DSMEM 的共享范围是**一颗 GPU 内的簇（最多 8 个块）**，不是跨 GPU。跨 GPU 的共享内存并不存在；跨 GPU 通信仍要靠 NVLink 或网络。DSMEM 解决的是「同一颗 GPU 内、相邻块之间」的通信提速。

还有一个细节值得留意：**簇内的块必须来自同一个 grid**——簇不是「随便挑几个块编组」，而是「一个 kernel 的 grid 在启动时就被划分成若干个簇」。程序员通过簇维度（cluster dims）声明「每几个块算一个簇」，硬件按此把块的调度限制在同一个 GPC 内。这意味着簇的「邻居圈」是启动时定好的、静态的——它牺牲了灵活性，换来了可预测的驻留与极低的通信开销。

## 4 核心对比表：块间协作的三种方式

把「块与块怎么协作」的几种方案放在一张表里：

| 协作方式 | 范围 | 延迟量级 | 同步方式 | Hopper 现状 |
| --- | --- | --- | --- | --- |
| 全局内存 + fence | 任意块 | 数百周期 | 手动/原子 | 通用但慢 |
| grid 级同步 | 整个 grid | 很重 | cooperative groups | 开销大、全 grid 停顿 |
| 簇 + DSMEM | 簇内（≤8 块） | 共享内存级 | cluster.sync() | 新增、轻量 |
| TMA DSMEM 搬运 | 簇内 | 异步 | mbarrier | 新增、流水化 |

读这张表的核心洞察：**Hopper 在「块内（快但小）」与「grid（大但慢）」之间，插入了一个「簇（中等大小、快）」的档位**。它不是替代全局内存通信，而是给「本就需要频繁协作的一小组块」提供一条快车道。

## 5 公式解析：簇的带宽优势

为什么 DSMEM 快？用「数据访问距离」来量化。设簇内有 $C$ 个块，块间要交换一块大小为 $S$ 的数据：

通过全局内存：$S$ 字节要先写回 L2/HBM 再读回，往返延迟 $L_{\text{global}} \approx 200$–300 周期；
通过 DSMEM：$S$ 字节留在片上共享内存，访问延迟 $L_{\text{dsmem}} \approx 30$ 周期量级。

加速比：

$$
\frac{L_{\text{global}}}{L_{\text{dsmem}}} \approx \frac{250}{30} \approx 8
$$

三步拆解：

- **第一步，定延迟**：共享内存的片上访问（约 30 周期）比全局内存（数百周期）快一个数量级。
- **第二步，省往返**：DSMEM 省掉了「写全局 → 栅栏 → 读全局」的两跳，只剩「写邻居共享内存 → 读」一跳。
- **第三步，看吞吐**：带宽上，共享内存的聚合带宽远高于 HBM，块间高频小数据交换不再占用宝贵的 HBM 带宽。

这条式子解释了为什么 FlashAttention-2 的块间归约、分布式 GEMM 的累加，在 Hopper 上都能用簇重写并加速——**高频、小块的通信，正是 DSMEM 的主场**。

## 6 小结

- 经典 CUDA 里**线程块是孤岛**：跨块通信只能走全局内存 + fence + 原子，慢且难写。
- **线程块簇**：2–8 个块组成簇，必须同时驻留，`cluster.sync()` 轻量同步。
- **DSMEM**：簇内各块的共享内存构成分布式共享空间，用 **mapa/mapc** 指令直接访问邻居块的共享内存。
- **辨析**：DSMEM 是「一颗 GPU 内、簇内」的机制，不是跨 GPU 共享内存。
- 块间协作三档：**全局内存（通用但慢）、grid 同步（大而重）、簇 DSMEM（小而快）**。
- 簇的划分是**启动时静态声明的**（cluster dims），块必须同 grid、同驻留——用灵活性换可预测性。
- **搭配 TMA**，DSMEM 可以一条指令完成「共享内存 → 共享内存」的簇内 bulk 搬运，与 wgmma 组成完整的异步协作闭环。
- 共享内存延迟约 30 周期 vs 全局内存数百周期，**簇把块间高频通信提速近一个数量级**。
