## 为什么从线程层次讲起

前 12 节我们把 H100 的硬件从外到内看了一遍：系统、内存、互连、SM、Tensor Core、TMA、簇、warpgroup。但**硬件只是舞台，戏还得靠程序来演**。CUDA 是 H100 的编程语言，而理解 CUDA 的第一把钥匙就是它的**线程层次（thread hierarchy）**——程序如何把「海量并行任务」组织成硬件能高效执行的形态。本节从 grid、block、warp 三个层次讲起，把「软件线程模型」与前面学的「硬件 SM 结构」一一对应起来。<span class="marginnote">CPU 编程时，线程是「稀缺资源」，要小心管理；GPU 编程时，线程是「廉价资源」，用成千上万个线程来压满硬件。这种「以量取胜」的模型叫<strong>SIMT</strong>（单指令多线程），是整个 CUDA 执行模型的基石。</span>

## 1 三级层次：grid → block → thread

CUDA 程序以 **kernel（内核函数）** 为单位执行。启动一个 kernel 时，程序员声明两个维度：

$$
\text{gridDim} \times \text{blockDim} = \text{线程总数}
$$

**grid（网格）**：kernel 的完整线程集合，由若干**线程块（block）**组成。

**block（线程块）**：一组可以协作的线程（共享内存 + 同步），最多 1024 个线程（H100）。

**thread（线程）**：最小的执行单元，每个线程独立执行 kernel 代码、持有自己的寄存器与程序计数器。

以「向量加法 $y = a x + b$」为例，一份朴素 kernel 的启动是：

```cuda
int N = 1 << 20;
int blockSize = 256;
int gridSize = N / blockSize;        // 4096 个块
vecAdd<<<gridSize, blockSize>>>(y, x, a, b, N);
```

4096 个块 × 256 线程 = 1,048,576 个线程，一次启动全部铺满 GPU。每个线程通过内置变量找到自己的身份：`blockIdx.x`（块号）、`threadIdx.x`（块内线程号）、`blockDim.x`（块大小），从而确定自己负责的数组元素下标：

```cuda
int i = blockIdx.x * blockDim.x + threadIdx.x;
if (i < N) y[i] = a * x[i] + b;
```

这段代码背后的模型是：**线程不知道彼此，只知道自己是谁、自己在哪**——协作是隐式的，靠「下标分工」完成。<span class="marginnote">这个「下标分工」模式是 GPU 编程的母题：几乎所有 kernel 的第一步都是「算出我的全局编号 i」，然后「我只处理第 i 份数据」。它把「并行任务」翻译成了「每个线程一个职责」，与函数式编程的 map 思想同源。</span>

## 2 warp：硬件真正执行的单位

线程层次里还有一个隐藏的第四级——**warp（线程束）**，它是硬件真正调度执行的单位。

**warp**：32 个连续线程组成的执行组。GPU 以 warp 为单位发射指令：**一个 warp 里的 32 个线程在同一时刻执行同一条指令**（SIMT）。

这带来几个重要的推论：

**最小粒度**：即使 block 里只有 1 个线程，硬件也会给它分配整整一个 warp（其余 31 个线程闲置）。
**线程数最好是 32 的倍数**：block 尺寸取 64、128、256、512 这类 32 的倍数，可以避免「浪费半个 warp」。
- **warp 内分歧（divergence）**：若 warp 内线程走不同分支（`if (tid % 2) ... else ...`），GPU 会**串行执行两个分支**——先执行 if 分支的线程，再执行 else 分支的线程。分支分歧是 GPU 性能的大敌。

H100 的调度器以 warp 为对象（前面 SM 微架构讲过：4 调度器 + 双发射），一个 SM 最多驻留 64 个 warp（2048 线程）。**程序写的 thread 是「逻辑的」，硬件看到的 warp 是「物理的」**——这个映射关系决定了线程如何被高效地安排。<span class="marginnote">warp 分歧的代价可以很夸张：一个 `if/else` 让 warp 的执行时间翻倍，嵌套分支会让时间指数级增长。因此 GPU 编程的最佳实践是「让 warp 内线程走同一条路」——用整块掩码（掩码操作）而不是细粒度分支来表达条件。</span>

## 3 从线程层次看 H100 的硬件映射

线程层次不是纯软件概念，它与前面学的硬件结构精确对应：

| 软件层次 | 硬件对应 | 关键资源 |
| --- | --- | --- |
| thread | CUDA 核心上的一个执行槽 | 寄存器（每线程 ≤255 个） |
| warp（32 线程） | 调度器的一个调度单位 | 一个 warp 一条指令 |
| block（≤1024 线程） | 一个 SM（或 SM 的一部分） | 共享内存、同步 |
| warpgroup（128 线程） | SM 内一个处理块的协作单位 | wgmma、mbarrier |
| grid | 整个 GPU（多个 SM） | 全局同步需核间协作 |

这张映射表是「软硬件对应」的心智模型。它解释了很多工程现象：

为什么 block 太大不好：超过 SM 能容纳的线程数（2048），块会被排队，利用率下降；
为什么 block 太小也不好：一个 32 线程的块只占 SM 一小部分，无法用满 64 个 warp 的驻留空间来隐藏延迟；
- 为什么寄存器太多会降低占用率：每线程寄存器用得多，SM 能驻留的线程就少。

**占用率（occupancy）**：SM 中实际驻留线程数与最大线程数的比值。它直接决定隐藏延迟的能力——而它由 block 大小、寄存器用量、共享内存用量三者共同决定。<span class="marginnote">用「餐厅」类比：SM 是餐厅，线程是顾客，寄存器/共享内存是座位与餐桌。座位太挤（寄存器用太多）会减少能同时接待的顾客数，顾客太少（低占用率）则高峰期吞吐上不去。调优就是在「每个顾客占用的资源」与「同时接待的顾客数」之间找平衡。</span>

## 4 公式解析：block 与 grid 的尺寸选择

block/grid 尺寸选择是新手的第一道坎，背后是一条算术链。设：

- 总工作量 $N$（数组长度、像素数等）；
- 每块线程数 $B$（blockDim）；
- 需要块数 $G = \lceil N / B \rceil$（gridDim）。

以 H100 为参考，取 block 大小的一个常用法则是「让每个 SM 有 4–8 个块驻留」：SM 最多 64 个 warp = 2048 线程。若每块 $B = 256$（8 warp），则每 SM 可驻留 $2048 / 256 = 8$ 个块，恰好在「块数足够多、粒度足够细」的甜点区：

$$
\text{每 SM 常驻块数} = \left\lfloor \frac{2048}{B} \right\rfloor, \qquad \text{块内 warp 数} = \frac{B}{32}
$$

- **第一步，算块内 warp 数**：$B = 256$ → 8 warp，是 32 的倍数，无浪费。
- **第二步，算每 SM 常驻块数**：$2048 / 256 = 8$ 块，同时有 8 个块竞争调度，延迟隐藏充足。
- **第三步，算总块数**：$G = \lceil N/256 \rceil$
