## 为什么从 CUDA Graphs 讲起

前面的章节都在追求「把每个 kernel 跑得更快」。但很多真实程序的问题不在 kernel 内部，而在 kernel 之间：**一次 kernel 启动，CPU 要花几微秒做参数校验、分配、下发**。当你的程序是「一千个小 kernel 顺序执行」，这 5–10 微秒的启动开销会累积成毫秒级的纯浪费——尤其推理场景，延迟就是生命。**CUDA Graphs** 的解法很直接：把一串 kernel 的启动一次性「拍成照片」（捕获），然后**一次启动整张图**，让 GPU 自己调度，省掉中间的每一跳 CPU。Hopper 让这套机制更成熟，也让它成为推理引擎（如 TensorRT、Triton）的标准优化。<span class="marginnote">启动开销的典故：NVIDIA 在 GTC 上反复演示「同样的工作量，图启动比流启动快一个数量级」。对小 kernel 密集的程序（推理、图神经网络、强化学习），这个差距直接变成端到端的延迟收益。CUDA Graphs 是「别让 CPU 成为 GPU 的瓶颈」这一原则的官方武器。</span>

## 1 问题：CPU 启动开销正在吃掉 GPU

先量化「启动开销」。一次 kernel 启动，CPU 侧要做的事包括：

- 检查 kernel 参数与合法性（参数校验）；
- 在驱动层构造启动请求并排队（驱动交互）；
- 把启动指令下发给 GPU（总线传输）；
- GPU 端解析并开始调度（解析开销）。

这些加起来约 **5–10 微秒**。单独看微不足道，但放进真实程序就失控了：

- 推理时一个 Transformer 层拆成几十个 kernel，几十层下来就是数百次启动——**启动开销与计算相当甚至超过**；
- 小规模计算（单个小矩阵、逐元素算子）的计算时间本身才几微秒，启动开销直接「翻倍成本」；
- 依赖链（kernel A 完了才启动 kernel B）让 CPU 与 GPU 反复「握手」，GPU 频繁空转等 CPU。

**关键事实：启动开销与 kernel 的计算量无关，只与「启动了几次」有关。** 把「启动次数」降下来，就是 CUDA Graphs 的全部意义。<span class="marginnote">这个「固定开销 vs 可变开销」的思路在计算机系统里处处可见：系统调用、HTTP 请求、数据库事务都有「每连接固定开销」。优化思路也一致——<strong>批量化、预编排、减少握手次数</strong>。</span>

## 2 CUDA Graphs 的三步工作流

**CUDA Graphs**：把一系列 GPU 操作（kernel、memcpy、memset 等）组织成一张**有向无环图（DAG）**，一次性提交给 GPU 执行。工作流分三步：

**第一步，捕获（capture）**：在 `cudaStreamBeginCapture()` 与 `cudaStreamEndCapture()` 之间，正常调用那些 kernel/API——它们不会被真正执行，而是被「录」进一张图。捕获期间用的参数会被「冻结」成图节点的参数。

**第二步，实例化（instantiate）**：`cudaGraphInstantiate()` 把捕获的图编译成可直接执行的版本，分配好执行所需的资源。实例化通常只做一次，之后反复执行。

**第三步，启动（launch）**：`cudaGraphLaunch()` 一次启动整张图。CPU 只需提交一个图启动请求，GPU 端自行完成图上所有节点的调度与执行。

之后可以反复 `cudaGraphLaunch()` 同一张图（同一模型推理的每步都重放同一张图）——**把「每次重新启动」变成「每次重放一张编排好的图」**。

**辨析｜易错点：** 捕获是「录制」，不是「执行」。捕获期间 kernel 不会被真正运行，所以捕获代码里若依赖「运行时数据」（如某 kernel 的输出决定下一个 kernel 的形状），需要特别处理（动态形状要用图更新或分图）。**图的参数是捕获时冻结的**，这是初学者最容易踩的坑。<span class="marginnote">对照深度学习框架：PyTorch 的 <code>torch.cuda.graphs</code> 与 CUDA Graphs 的 capture 机制是同一回事，vLLM、TensorRT 的图捕获路径也基于它。框架层把它包装成「把推理模型拍成一张图」，就是因为它能同时降低启动开销与 CPU 参与度。</span>

## 3 程序化依赖：把「先后」显式化

图中的节点如何排序？有两种依赖来源：

**隐式依赖（流内顺序）**：捕获时在同一流里先后调用的操作，天然按流顺序排列。
**程序化依赖（programmatic dependencies）**：通过 `cudaGraphAddDependencies()` 显式声明「节点 A 必须在节点 B 之前」——即使它们来自不同的流。

程序化依赖的价值在于**并行调度**：传统流模型里，不同流之间的同步靠事件（event）「握手」，繁琐且粒度粗；图模型里可以直接声明依赖关系，让 GPU 调度器看清全局，把**没有依赖关系的节点并行执行**。

常见节点类型：kernel 节点、memcpy 节点、memset 节点、空节点（占位）、子图节点（把一张图嵌进另一张图）。节点类型越丰富，能「拍进图」的工作就越多——比如把「数据拷贝」也拍进去，省掉一次 CPU 发起的 memcpy 往返。

动态形状是图执行要处理的难点：模型每步的序列长度、批次大小会变，而图节点的参数是捕获时冻结的。CUDA 提供 `cudaGraphExecUpdate` 做**原地更新**——不重建整张图，只替换变化的节点参数，省掉重新实例化的开销。配合「按常见形状拍几张图、按需切换」的惯例，动态推理也能吃到图启动的红利。

## 4 核心对比表：流执行 vs 图执行

把传统「流式启动」与「图启动」放在一起对比（本节核心对比表）：

| 维度 | 流执行（streams） | 图执行（CUDA Graphs） |
| --- | --- | --- |
| CPU 参与 | 每 kernel 一次启动 | 一次启动整张图 |
| 启动开销 | 每 kernel 5–10 μs | 分摊到一次图启动 |
| 依赖表达 | 事件握手 | 显式 DAG 依赖 |
| 并行调度 | 依赖程序员手工组织流 | 调度器全局编排 |
| 适用场景 | 大 kernel、动态逻辑 | 小 kernel 密集、推理重放 |
| 心智模型 | 每一步发指令 | 拍好照片，一次放映 |

读这张表的结论：**流执行适合「大而少」的 kernel（启动开销占比小）；图执行适合「小而多」的 kernel（启动开销占比大）**。现代推理引擎（TensorRT、vLLM）几乎都用图执行，正是因为推理恰好是「小 kernel 密集」的典型场景。

## 5 公式解析：图启动省了多少

用一条公式量化「省多少」。设程序有 $N$ 个 kernel，每个 kernel 计算时间 $c$，每次启动开销 $h$：

流式执行的总时间：

$$
T_{\text{stream}} = N \times (c + h)
$$

图执行（一次图启动，GPU 端 $N$ 个 kernel 顺次执行）的总时间：

$$
T_{\text{graph}} = N \times c + h
$$

加速比：

$$
\frac{T_{\text{stream}}}{T_{\text{graph}}} = \frac{N(c + h)}{Nc + h}
$$

三步拆解：

- **第一步，看分子**：流式每 kernel 都付一次启动税 $h$，$N$ 个 kernel 共付 $N \times h$。
- **第二步，看分母**：图启动只付一次 $h$，$N$ 个 kernel 的启动税被**压缩成一份**。
- **第三步，看极限**：$N$ 很大时，加速比趋于 $(c+h)/c$；若 $h \approx c$（启动与计算相当），加速比接近 2；若 $h \ll c$，图收益有限——**所以图优化的收益恰好集中在「小 kernel」上**。

这条式子解释了为什么 CUDA Graphs 是「推理场景的神器」而「大训练 kernel 收益小」——它是一个「按启动次数收税」的模型，图启动把税从 $N$ 份降成 1 份。

## 6 小结

- **启动开销**每次 5–10 μs，与计算量无关，只与启动次数有关——小 kernel 密集程序被它拖垮。
- **CUDA Graphs 三步**：捕获（capture）→ 实例化（instantiate）→ 启动（launch），一次启动整张 DAG。
- **程序化依赖**（`cudaGraphAddDependencies`）显式声明先后，让无依赖节点并行执行。
- 流执行适合大 kernel，**图执行适合小 kernel 密集的推理**——TensorRT、vLLM 都在用。
- 动态形状用 **`cudaGraphExecUpdate` 原地更新**，或按常见形状拍多张图按需切换。
- **辨析**：图捕获是「录制」不是「执行」，参数在捕获时冻结——依赖运行时数据的形状要特别处理。
- 图启动把「$N$ 份启动税」压成「1 份」，加速比 $(c+h)/c$，小 kernel 收益最大。
