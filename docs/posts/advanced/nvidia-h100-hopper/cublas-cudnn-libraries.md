## 为什么从性能库讲起

前面十几节教的是「自己写 kernel 时怎么把 H100 用满」。但绝大多数人并不会直接写 kernel——他们用 **PyTorch、TensorFlow**，而这些框架底层调用的是 NVIDIA 的**性能库（libraries）**：cuBLAS（线性代数）、cuDNN（深度网络）。可以说，**你写的 AI 代码最终跑在 cuBLAS/cuDNN 的 kernel 上**。理解这两个库，你就理解了「为什么框架里的同一个算子，在 A100 上和在 H100 上会快这么多」——因为性能库会针对每一代新硬件重写内核。本节讲清楚它们各自管什么、如何在 Hopper 上把 TMA/wgmma/FP8 吃到极致。<span class="marginnote">性能库在软件栈中的位置：应用（PyTorch）→ 框架算子层（ATen）→ 厂商库（cuBLAS/cuDNN/cuBLASLt）→ CUDA 驱动 → 硬件。框架层的优化（算子融合）与厂商库的优化（kernel 选择）相互配合，共同决定端到端性能。</span>

## 1 为什么矩阵乘不能自己写

理论上，一个 $M \times N \times K$ 的矩阵乘用三循环就能写：

```cuda
for (i = 0; i < M; i++)
  for (j = 0; j < N; j++)
    for (k = 0; k < K; k++)
      C[i][j] += A[i][k] * B[k][j];
```

但这段代码在 GPU 上会慢得离谱——它完全没利用共享内存的分块复用、没利用 TMA 的异步搬运、没利用 wgmma 的矩阵级指令。**一个「能用」的 GEMM kernel 和一个「吃满 Tensor Core」的 GEMM kernel，性能差距可达 10–50 倍。**

一个工业级 GEMM 要考虑的维度包括：

**分块（tiling）**：把矩阵切成能装进共享内存/寄存器的小块，最大化数据复用；
**流水线**：TMA 预取下一块，wgmma 算当前块，重叠搬运与计算；
- **精度**：FP8/FP16/TF32 的缩放与累积策略；
- **形状启发式**：不同的 $M/N/K$ 与不同的 SM 数对应不同的最优分块；
- **尾块处理**：矩阵维度不是分块倍数时的边界逻辑。

这些优化互相纠缠，且随硬件换代而失效。**性能库的价值就是把这份复杂性封装起来，并用海量自动化测试保证「任意形状下都接近最优」。** 自己写 GEMM 很容易写成「能用但慢一半」——而这在千卡集群上意味着白白浪费几千万的电费与机时。

值得一提的还有性能库的**自动调优（autotuning）**：库在首次使用时会对你的形状做一次「试跑」，在几十个 kernel 变体里实测出最快的一个并缓存下来。这个「跑分选最优」的机制，让库既保持「通用」又逼近「专用」——**你不需要懂每个 kernel 变体的细节，库用实测替你选了**。<span class="marginnote">NVIDIA 在 Hopper 上把 cuBLAS 的 FP8 GEMM 用 TMA + wgmma + 双缓冲流水线重写，相对「Ampere 风格」的实现有数倍提升——这就是为什么「换 GPU 后库也要升级」。新硬件的能力，通常要等库更新才真正落地到你的模型。</span>

## 2 cuBLAS：线性代数的事实标准

**cuBLAS（CUDA Basic Linear Algebra Subroutines）**：NVIDIA 的 GPU 线性代数库，实现 BLAS 规范，核心是矩阵乘 GEMM 与一系列分解、求解、向量操作。

对 AI 最关键的是它的 **cuBLASLt（lightweight）** 变体——专门针对「一次配置、反复执行」的 GEMM 场景做了轻量化设计：

**plan 机制**：把「选择算法 + 分配 workspace」放在 plan 阶段，运行时反复执行同一 plan，避免重复决策开销；
- **算法启发式**：对给定形状，在数十种 kernel 变体（不同分块、不同流水线深度）里自动选优；
- **split-k**：当 $K$ 维过大时，把 $K$ 切成多段并行算，再归约——用小批量换取更多并行度。

在 H100 上，cuBLAS 支持 FP8 GEMM（配 Transformer Engine 的缩放）、TF32、以及面向 Hopper 的 wgmma 路径。框架里一个 `torch.matmul` 落到 FP16 GEMM 时，背后就是 cuBLASLt 在几十个候选 kernel 里挑最快的一个。

**辨析｜易错点：** 很多人以为「调 cuBLAS 就是调个参数」，其实它的性能高度依赖**批次形状**。矩阵太小（如 $M = 8$ 的逐样本 GEMM）时，吞吐被「每个 kernel 一次小矩阵」浪费；矩阵太大（如 $M = 10000$）时，需要 split-k 或更多分块。**同一个库、同样的代码，形状不同性能可以差几十倍**——性能库不是「魔法」，它是在「给你几十种 kernel 变体」中挑最快的一个，而「哪个最快」取决于你的形状。

## 3 cuDNN：深度网络的「积木库」

**cuDNN（CUDA Deep Neural Network library）**：NVIDIA 的深度网络算子库，覆盖卷积（CNN）、RNN、归一化、激活、池化等深度学习的全部基础算子。

与 cuBLAS 的定位区别要分清：

**cuBLAS 是「线性代数」库**：管 GEMM、分解、求解，偏「数学运算」。
**cuDNN 是「神经网络」库**：管卷积、注意力、归一化、激活，偏「网络结构」。

两者在 Transformer 里分工明确：**线性层与注意力投影用 cuBLAS 的 GEMM，LayerNorm、激活、softmax 用 cuDNN，卷积类模型（ViT 的 patch embed、CNN 骨架）用 cuDNN 的卷积算子**。一个 PyTorch transformer 前向，背后就是 cuBLAS 与 cuDNN 的交替调用。

cuDNN 对 H100 最重要的适配是**支持 FP8**：卷积与注意力算子都能跑 FP8，配合 Transformer Engine 的缩放。对推理场景，cuDNN 还提供 **cudnn_frontend** 的图级 API，可以把整个网络拍成一张图执行（呼应《CUDA Graphs》一节的图执行思路）。

cuDNN 在 Hopper 上还接住了 **FlashAttention 家族**：从 FlashAttention-2 到 FlashAttention-3，其分块注意力内核被收录进 cuDNN 的注意力 API，让框架用户无需手写内核就能用上「分块 + 在线 softmax」的优化。**这体现了一个趋势：越来越多「曾经要手写」的算法，正被性能库「收编」**——性能工程师把最佳实践固化成库，普通开发者直接调用。<span class="marginnote">卷积是「滑动窗口 + 局部共享」，GEMM 是「全连接 + 分块复用」——两者数学结构不同，但都被 NVIDIIA 的库优化到了「针对每代硬件重写」的程度。学深度学习框架时看到「算子」这个词，心里可以默认它是「cuBLAS/cuDNN 的一个 API 调用」。</span>

## 4 核心对比表：cuBLAS vs cuDNN

把两个库并排看（本节核心对比表）：

| 维度 | cuBLAS | cuDNN |
| --- | --- | --- |
| 定位 | 线性代数库 | 深度网络算子库 |
| 核心算子 | GEMM、分解、求解 | 卷积、注意力、归一化、激活 |
| Transformer 角色 | 线性层、注意力投影 | LayerNorm、softmax、激活、卷积 |
| H100 重点 | FP8 GEMM、wgmma 路径 | FP8 卷积/注意力、图执行 |
| 上层调用方 | PyTorch 的 matmul/linear | PyTorch 的 conv/attention/norm |

读这张表的要点：**框架里 80% 的计算时间花在「GEMM 类」算子上（cuBLAS），剩下 20% 花在「网络结构」算子上（cuDNN）**——所以优化先盯 GEMM，但也不能忽略 cuDNN 的归一化与激活（它们在 memory-bound 上同样可以优化）。

## 5 公式解析：为什么「库更新」比「自己调优」更快

性能库的价值可以用「调优成本」来量化。设你要在 H100 上写一个 FP8 GEMM，需要手工调优的参数空间：

$$
N_{\text{configs}} = \text{分块方案} \times \text{流水深度} \times \text{精度组合} \times \text{尾块处理}
$$

代入量级：分块 10 种 × 流水 4 种 × 精度 3 种 × 尾块 3 种 ≈ 360 种配置。

- **第一步，看组合爆炸**：360 种配置 × 每种要测数十种形状 = 上万次实验——个人开发者根本做不完。
- **第二步，看硬件换代**：A100 的最优配置在 H100 上往往不是最优——每代硬件都要重调。
- **第三步，看库的规模效应**：NVIDIA 用自动化测试矩阵（成千上万种形状 × 版本）找出每个形状的最优配置，并在驱动更新时自动重调——**这份「调优成本」被库摊销到了所有用户头上**。

这条式子是「为什么用性能库」的最终理由：**性能库 = 把「每人都要付的调优成本」变成「一次投入、万人受益」的公共品**。自己写 GEMM 不是不能更快，而是「更快所需的成本」在单个项目里几乎永远收不回来。

**辨析｜易错点：** 还有人以为「性能库已经是天花板，不需要再优化」。实际上，性能库的最优是针对「它见过的形状」——如果你的形状组合很特殊（如极小的 $M$、非标准的对齐、批量矩阵乘），性能库未必找到全局最优。**先测库的表现，再决定要不要手写**——绝大多数情况库够用，少数极端形状值得手工 kernel 补上。

## 6 小结

- 你写的 AI 代码最终跑在 **cuBLAS/cuDNN 的 kernel 上**——性能库是框架与硬件之间的桥梁。
- **cuBLAS（线性代数/GEMM）** 与 **cuDNN（深度网络算子）** 分工明确，Transformer 两者交替调用。
- 性能库的价值：**封装「分块 + 流水线 + 精度 + 形状启发式」的复杂性，用自动化测试保证任意形状接近最优**。
- cuBLASLt 的 **plan 机制**把「选算法 + 分配」放在 plan 阶段，运行时反复执行同一 plan。
- H100 上 cuBLAS/cuDNN 全面拥抱 **FP8 + TMA + wgmma + 图执行**——新硬件能力要靠库更新才落地。
- 性能库的**自动调优**在首次使用时对形状「试跑选最优」，既保持通用又逼近专用。
- 性能库 = **「每人要付的调优成本」变成「一次投入、万人受益」**；形状决定「哪个 kernel 最快」。
- **辨析**：cuBLASLt 与 cuBLAS 的差别在「轻量 plan + 反复执行」——一次配置、多次运行的 GEMM 场景（训练循环）选 cuBLASLt。
- **辨析**：性能库最优是「对见过的形状」——极端形状下先测库、再决定要不要手写 kernel。
- FlashAttention 等「曾要手写」的算法正被性能库**收编**：最佳实践固化成库，开发者直接调用。
- **实操建议**：先用库、再测瓶颈、极端形状才手写——「性能库够用」是默认假设，「手写更快」需要实测证据。
