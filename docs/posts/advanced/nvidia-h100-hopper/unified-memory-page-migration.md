## 为什么从统一内存讲起

传统 GPU 编程有一道令人烦躁的工序：`cudaMemcpy`——把数据从主机搬到设备、算完再搬回来，程序员要手工追踪「这块数据现在在 CPU 还是 GPU」。**统一内存（Unified Memory，UVM）** 的目标是消灭这道工序：CPU 和 GPU 共享**同一个虚拟地址空间**，你只管 `cudaMallocManaged` 分配，硬件按需把数据搬到需要它的地方。对 H100 与 AI 工作负载，UVM 还有一个更实用的价值——**超卖（oversubscription）**：模型比显存大时，不写显存管理代码也能跑，因为页面会按需迁进迁出。本节讲清 UVM 的机制、页迁移的成本，以及 H100 在这条路上的进展。<span class="marginnote">UVM 的思想与操作系统里的「虚拟内存 + 缺页换页」如出一辙：操作系统把磁盘当内存用，UVM 把「CPU 内存」与「GPU 显存」统一成一个可换页的地址空间。学过《操作系统》的同学，会在这里看到完整的翻版——只是换页的双方从「内存/磁盘」变成了「CPU 内存/GPU 显存」。</span>

## 1 统一内存：消灭 cudaMemcpy

传统流程是「显式拷贝」：

```cuda
cudaMalloc(&d_x, N * sizeof(float));
cudaMemcpy(d_x, h_x, N * sizeof(float), cudaMemcpyHostToDevice);
// ... 算完
cudaMemcpy(h_x, d_x, N * sizeof(float), cudaMemcpyDeviceToHost);
```

程序员要回答三个问题：数据在谁那边？什么时候该搬？搬多少？错一个就「悄悄慢」或「直接错」。

统一内存的写法简洁得多：

```cuda
float *x;
cudaMallocManaged(&x, N * sizeof(float));
// CPU 可以用 x，GPU 也可以用 x——同一个指针
```

背后的机制是**按需页迁移**：CPU 或 GPU 访问一个页面时，如果该页面不在当前设备的内存里，硬件触发**缺页（page fault）**，把页面从另一侧搬过来再继续执行。从 Volta（V100）开始，NVIDIA 用**硬件加速页迁移引擎**实现缺页处理，不必停下来等软件。

**核心好处：可移植的指针**——一段既被 CPU 读、又被 GPU 算的代码，可以只写一遍，运行时自动换页。<span class="marginnote">UVM 不是新概念：2014 年的 Kepler 就有第一代 UVM，但当时缺页由软件模拟、慢得不能用于性能敏感代码。V100 引入硬件缺页引擎，A100 增强，H100 继续改进——它从「教学玩具」变成了「大模型跑不跑得动」的现实工具。</span>

## 2 页迁移的成本：免费是没有的

UVM 的「方便」不是免费的，它的成本藏在两个地方：

**缺页迁移延迟高**：一次缺页要 CPU 参与页表处理、搬 64 KB–2 MB 的页面、再恢复执行——延迟是微秒到百微秒量级，比显存访问（几百纳秒）慢几个数量级。频繁缺页的程序会「卡」。
**页面粒度粗**：迁移以页为单位（默认 2 MB 大页），一个 2 MB 的页面里哪怕只用到 1 KB，整页都要搬——空间效率不理想。

所以正确的用法不是「依赖按需迁移」，而是**预取（prefetch）**：

```cuda
cudaMemPrefetchAsync(x, N * sizeof(float), deviceId, stream);
```

在计算开始前，主动把页面搬到目标设备，把「运行时缺页」变成「启动时搬好」。**经验法则：UVM 可以偷懒，但不能依赖偷懒——热数据必须显式预取**，否则按需迁移的延迟会吃掉全部收益。<span class="marginnote">这个「按需 vs 预取」的取舍也出现在 CPU 世界：操作系统的按需分页 vs 显式 mmap + 预读。两条路线的共同规律是——<strong>按需处理保证正确，显式预取保证性能</strong>。GPU 端 H100 的 page migration 引擎更聪明（支持异步、多页流水），但这条规律不变。</span>

## 3 H100 的进展：更聪明的迁移

H100（以及配合的 CUDA 12 驱动）在 UVM 上做的主要改进：

**更强的异步迁移**：`cudaMemPrefetchAsync` 与迁移操作可以在流里异步执行，与计算重叠，迁移不再是「同步卡点」；
**更好的超卖体验**：模型占用超过 GPU 显存时，按需换页让「大模型跑在小显存」成为可能——虽然慢，但能跑；
**Grace-Hopper 的质变**：在 Grace Hopper 超级芯片上，CPU 与 GPU 通过 **NVLink-C2C** 以 900 GB/s 的相干互连相连，CPU 内存与 GPU 显存形成**统一的内存池**——迁移不再是「慢速 PCIe 搬运」，而是「几乎像本地访问」。这是 UVM 从「应急方案」迈向「第一公民」的转折点。

**辨析｜易错点：** 很多人以为「UVM = 自动优化」，这是误会。**UVM 保证的是「正确性」与「便捷」，不保证「性能」**。数据访问模式不好（频繁跨设备随机访问）时，UVM 的迁移开销会远超手工 `cudaMemcpy` 的优化拷贝。大模型训练里，权重与激活通常是「明确的流式访问」，手工管理（先搬好、算完不搬回）仍然是最优解；UVM 更适合「稀疏、偶发、跨设备」的访问。

为了帮助「该预取什么」，硬件还提供**访问计数器（access counters）**：硬件统计每一页被哪个设备访问、访问了多少次，驱动据此判断「这页是不是该长期留在 GPU」。你可以用 `cudaMemAdvise` 显式给出提示（如「这页以后主要给 GPU 用」），让迁移策略更准。**UVM 不是「魔法」，而是一套「提示 + 统计 + 换页」的可调系统**——用好它的关键，是理解它的策略并给出正确的提示。<span class="marginnote">业界实践：训练框架（Megatron、DeepSpeed）大多仍然用显式管理，因为权重生命周期清晰、手动分片最省心；而推理服务（如长上下文场景）常借用 UVM 超卖把「放不下的 KV Cache」溢出到 CPU 内存。用途不同，选择不同。</span>

## 4 核心对比表：内存管理的三种范式

把 GPU 内存管理的三种范式放在一起对比（本节核心对比表）：

| 范式 | 数据位置 | 搬运方式 | 程序员负担 | 性能上限 |
| --- | --- | --- | --- | --- |
| 显式拷贝 | 程序员手工管理 | cudaMemcpy 显式 | 高 | 最高（最优编排） |
| 统一内存 | 一个地址空间 | 按需缺页迁移 | 低 | 依赖预取质量 |
| 超卖 + UVM | 超过显存容量 | 换页溢出 | 低 | 低于显存内运行 |

读这张表的结论：**显式拷贝「最高效但最累」，UVM「最省心但依赖预取」，超卖「能跑但慢」**。没有免费的午餐——三者的取舍，正是内存管理这门「工程学」的全部内容。

## 5 公式解析：缺页迁移的代价模型

用一条公式看清「什么时候该用 UVM」。设数据块大小 $S$，缺页迁移单位 $P$（页大小），迁移速率 $B_{\text{mig}}$（带宽），一次缺页固定开销 $h$：

按需访问全部 $S$ 字节数据的迁移总时间：

$$
T_{\text{mig}} = \frac{S}{P} \times h + \frac{S}{B_{\text{mig}}}
$$

两步拆解：

- **第一步，看缺页次数**：$S/P$ 次缺页，每次付固定开销 $h$——**页越小，缺页次数越多，固定开销越重**。
- **第二步，看迁移吞吐**：$S/B_{\text{mig}}$ 是数据本身的搬运时间。若迁移走 NVLink-C2C（900 GB/s），这部分接近「本地带宽」；若走 PCIe（约 30–60 GB/s），就是明显的瓶颈。

代入一个例子：4 GB 数据、2 MB 页、缺页固定开销约 10 μs、PCIe 迁移 50 GB/s：

$$
T_{\text{mig}} = \frac{4 \times 10^9}{2 \times 10^6} \times 10\ \mu s + \frac{4\ \mathrm{GB}}{50\ \mathrm{GB/s}} \approx 2048 \times 10\ \mu s + 80\ \mathrm{ms} \approx 100\ \mathrm{ms}
$$

其中缺页固定开销占约 20 ms、搬运占 80 ms——**两者都不可忽略**。这解释了为什么「能预取就别靠缺页」：预取把缺页固定开销省掉，只剩下吞吐那一项。

## 6 小结

- **统一内存（UVM）**：CPU 与 GPU 共享一个虚拟地址空间，`cudaMallocManaged` 分配、按需缺页迁移。
- **按需迁移**从 Volta 起由硬件引擎实现，但**缺页延迟高、粒度粗**——「能偷懒，别依赖偷懒」。
- 正确的姿势是 **`cudaMemPrefetchAsync` 显式预取**热数据，把运行时缺页变成启动时搬好。
- **H100 的进展**：异步迁移更成熟；Grace-Hopper 用 NVLink-C2C 把 UVM 提升为「统一内存池」。
- **辨析**：UVM 保证正确与便捷，不保证性能；训练用显式管理，推理可借超卖。
- **访问计数器 + `cudaMemAdvise` 提示**是 UVM 的可调旋钮：给出「谁用、怎么用」的提示，迁移策略更准。
- 迁移代价 $T_{\text{mig}} = (S/P)h + S/B_{\text{mig}}$，缺页次数与吞吐都不可忽略。
- **经验法则**：训练用显式管理、推理可借超卖、Grace-Hopper 上 UVM 接近本地访问——选型看「数据是流式的还是稀疏的」。
- **辨析**：UVM 的「统一」是地址空间统一，不是「性能统一」——该预取不预取，缺页延迟照样卡死 kernel。
