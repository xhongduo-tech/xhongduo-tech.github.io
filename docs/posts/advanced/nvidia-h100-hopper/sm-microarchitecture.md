## 为什么从 SM 讲起

前面几节我们站在「芯片外面」看 H100：规格、封装、内存、互连。从本节开始，我们走进芯片内部——**流式多处理器（SM）**就是 GPU 的计算心脏。整个 H100 就是 132 个 SM 的集合，而 CUDA 程序最终也落实到「SM 怎么执行线程」。理解了 SM，你就理解了 GPU 性能的一切来源；不理解 SM，后面所有性能优化（TMA、分布式共享内存、FlashAttention）都无从谈起。<span class="marginnote">SM = Streaming Multiprocessor，流式多处理器。这个名字里的「多处理器」暗示了它的本质：每个 SM 本身就是一个微型的、高度并行化的多核处理器，GPU 是「很多个 SM」的集合。这也与第二级《计算机组成原理》中 SIMD 架构的思想一脉相承。</span>

## 1 SM 的整体结构：一个微型处理器

H100 的 SM 可以被看作一台「小而密的并行处理器」。它由四个**处理块（processing block）**组成，每个处理块包含一组计算单元、一级缓存与一个调度器。整个 SM 的资源配置如下：

| 资源 | H100 SM 配置 | 说明 |
| --- | --- | --- |
| FP32 核心 | 128 | 单精度浮点/整数通用计算 |
| INT32 核心 | 64 | 独立整数运算单元 |
| 第四代 Tensor Core | 4 | 矩阵乘专用硬件 |
| 调度器 | 4 | 每个处理块一个，支持双发射 |
| 寄存器文件 | 64K × 32-bit（256 KB） | 每线程最多 255 个寄存器 |
| 共享内存/L1 | 256 KB | 可配置划分 |
| 最大线程数 | 2048 | 同时驻留的线程上限 |
| 最大线程块数 | 32 | 常驻块数上限 |

先抓结构主干：**每个 SM 内有四个处理块，每个处理块有 32 个 FP32 核心、16 个 INT32 核心、1 个 Tensor Core 和 1 个调度器。** 四个处理块并行工作，这就是 SM 内部的第一层并行。

把 H100 的 SM 与 A100 的 SM 并排比一比，代际差异一目了然：

| 资源（每 SM） | A100 SM | H100 SM | 变化 |
| --- | --- | --- | --- |
| FP32 核心 | 64 | 128 | ×2 |
| INT32 核心 | 64（与 FP32 共享） | 64（独立） | 独立流水线 |
| Tensor Core | 3（第三代） | 4（第四代） | 换代 |
| 调度器 | 4（单发射） | 4（双发射） | 每周期指令×2 |
| 寄存器文件 | 256 KB | 256 KB | 不变 |
| 共享内存/L1 | 192 KB | 256 KB | +33% |
| 最大驻留线程 | 2048 | 2048 | 不变 |

这张表的重点在**结构变化而非数量翻倍**：INT32 独立成流水线、Tensor Core 换代、调度器双发射——H100 的 SM 不是「A100 SM 的加强版」，而是「重新设计过的并行引擎」。A100 的整数与浮点抢同一组流水线，H100 让它们各走各路，这正是大模型 kernel 里大量「算下标」的整数操作不再拖累浮点吞吐的原因。

## 2 计算单元的三种「人格」

SM 里的计算单元不是一种，而是分工明确的三种，理解它们的分工是优化性能的前提：

**FP32 核心（CUDA core）**：负责标量单精度浮点运算（加、乘、融合乘加）。深度学习里的逐元素操作、激活函数、归一化都跑在这里。H100 每个 SM 128 个，全芯片 132 × 128 = 16,896 个。
**INT32 核心**：负责整数运算，与 FP32 核心**并行独立**。地址计算、循环计数、索引运算等整数活不会占用浮点流水线——这是 H100 相对 A100 的重要改进，A100 的整数与浮点是共享流水的。<span class="marginnote">这一点对性能影响很大：深度学习 kernel 里有大量「算下标、算偏移」的整数操作。A100 时代整数与浮点抢同一条流水线，H100 让它们各走各的，浮点吞吐不受整数干扰。</span>
**第四代 Tensor Core**：矩阵乘专用硬件，一次能算一整块矩阵乘。它才是 H100 大模型算力的真正来源——FP16 算力 989 TFLOPS 里，FP32 核心只贡献了微不足道的部分，绝大部分来自 Tensor Core。<span class="marginnote">Tensor Core 是我们专栏的高频词：它在 V100（Volta）首次登场，在 A100 定型，在 H100 升级为第四代。深度学习=矩阵运算，矩阵运算=Tensor Core 的主场，这就是「AI 芯片」的由来。</span>

三种单元的数量比例很说明问题：**128 个 FP32 核心 vs 4 个 Tensor Core**。按「个数」看 FP32 完胜，但按「算力」看 Tensor Core 是绝对主力——因为每个 Tensor Core 每周期完成的 FLOP 是单个 FP32 核心的几百倍。**判断一个 SM 的「AI 算力」，别数 CUDA 核心，要看 Tensor Core**；判断它的「通用算力」，才看 FP32/INT32。这个「看什么数」的习惯，会直接影响你读规格表时的判断。

H100 相对 A100 还有一个常被忽略的改动：**FP64 单元被大幅削减**。A100 有 64 个 FP64 核心/SM（双精度强），H100 降到 2 个/SM（FP64 算力只有 34 TFLOPS，且靠独立单元）。这是「AI 专用化」的又一证据——NVIDIA 明摆着把芯片面积让给了 Tensor Core 与 FP32，而不是照顾 HPC 客户的双精度需求。对科学计算用户，这是「从通用加速器到 AI 专用器」的分水岭信号。

## 3 两级调度：让指令喂饱流水线

SM 性能的另一个关键是**调度**——怎么让计算单元一直有活干。H100 的调度分两级：

**第一级：warp 调度。** GPU 以 **warp（线程束，32 个线程一组）**为最小调度单位。SM 内每个处理块有一个调度器，每周期从「就绪的 warp 池」里选一个 warp 发射指令。H100 每个 SM 有 4 个调度器，分别管自己的处理块。

**第二级：双发射（dual-issue）。** Hopper 新增强化：每个调度器**每周期最多发射两条指令**。因此 H100 的 SM 每周期最高可从 4 个调度器发出 8 条 warp 指令——这是 A100（每调度器单发射）的 2 倍。<span class="marginnote">双发射的价值在于隐藏延迟：一条长延迟指令（如访存）发出后，调度器立刻可以发另一条无关指令填满流水线，而不是干等。这与 CPU 的乱序执行异曲同工，但 GPU 用「更多线程」而非「乱序窗口」来藏延迟。</span>

为什么要这么多线程？因为 GPU 用**线程并行**隐藏访存延迟：当一个 warp 在等内存数据时，调度器切换到另一个就绪的 warp，让计算单元不停歇。每个 SM 最多驻留 2048 个线程 = 64 个 warp，为的就是「总有 warp 处于就绪状态」。这个概念叫**占用率（occupancy）**——驻留线程越多，越能藏住延迟。

用数字感受一下这个「切换」：一次 HBM 访存的延迟约 400–600 周期，而一条算术指令只要几个周期。若只有一个 warp，等数据期间计算单元全程空闲——利用率不足 10%。当 SM 里驻留 64 个 warp、调度器双发射时，一个 warp 等数据，立刻切到别的 warp，计算单元几乎不停。**「驻留线程数」就是把「访存延迟」折算成「可隐藏的等待」的转换器**——这也是为什么 GPU 编程要让 kernel 尽量跑满占用率。

**辨析｜易错点：** 很多人以为「占用率越高越好」，其实有例外。当 kernel 的计算密度极高（算术强度大、访存很少）时，延迟本来就不是瓶颈，盲目堆线程反而会让每个线程分到的寄存器变少、指令级并行变差。**占用率是「访存密集时的重要指标」，不是「所有场景的灵丹妙药」**——判断它是否重要，先看 kernel 是计算受限还是带宽受限（第 4 篇的 Roofline 会系统讲）。

## 4 公式解析：SM 是怎么拼出整颗芯片的

H100 的宏观规格都能从「SM × 每 SM 资源」推导出来。核心公式：

$$
N_{\text{核心}} = N_{\text{SM}} \times C_{\text{per SM}}
$$

代入 FP32 核心数：$132 \times 128 = 16{,}896$，与官方规格完全一致。再代入寄存器：

$$
R_{\text{总寄存器}} = 132 \times 64K \times 32\ \mathrm{bit} = 132 \times 256\ \mathrm{KB} \approx 33\ \mathrm{MB}
$$

三步拆解这条式子：

- **第一步，看清单位**：64K × 32-bit 是每个 SM 的寄存器文件，256 KB/SM；每线程最多 255 个寄存器，正是为了让更多线程驻留而设。
- **第二步，乘 SM 数**：132 SM × 256 KB ≈ 33 MB——整颗 H100 的寄存器总量，相当于一个「微型的片上主存」。
- **第三步，看背后的权衡**：寄存器越多、每线程分到的越少，能驻留的线程就越多（占用率越高）——**寄存器用量是占用率的第一调校旋钮**，我们会在第 3 篇《CUDA 线程层次》里正式展开。

这条「每 SM × 数 = 全芯片」的推导法还有一个用处：**验证官方数字的对错**。NVIDIA 官方给出 FP32 总核心 16896，你算 $132 \times 128 = 16896$ 完全一致；如果你读到的某张「规格表」对不上这条乘法，大概率是表格抄错了。养成「用每 SM 规格回推整芯片」的习惯，能帮你快速筛掉市面上大量不准确的信息。

## 5 四层并行：从线程到 SM

把 H100 的并行结构从下到上串起来，正好是四层：

**线程（thread）**：最小的执行单元，跑在 FP32/INT32 核心上，持有自己的寄存器。
**warp（32 线程）**：调度单位，一个 warp 同时执行同一条指令（SIMT）。
**处理块（processing block）**：32 个 FP32 + 16 个 INT32 + 1 个 Tensor Core + 1 调度器，是 SM 内的并行子结构。
**SM（132 个）**：4 个处理块 + 共享的 L1/共享内存 + 寄存器文件，是整个 GPU 的计算单元。

这四层是理解「H100 为什么快」的骨架：**每一层都在「并行」，上层给下层喂活，下层用并行把活消化掉。** 你写 kernel 时看到的 block/thread 是软件的影子，硬件实际执行的是 warp 与处理块——这个「软件逻辑 / 硬件物理」的双轨视图，是后面所有性能分析的基础。<span class="marginnote">对照「从极限到大模型」主线：这里每一层的并行，都是「用并行换吞吐、用吞吐补延迟」这一思想的硬件具象化。CPU 靠乱序执行与分支预测藏延迟，GPU 靠「海量线程 + 逐层并行」藏延迟——路径不同，目的相同。</span>

## 6 小结

- H100 的 SM 是**四个处理块**的组合：每块 32 FP32 + 16 INT32 + 1 Tensor Core + 1 调度器。
- 三种计算单元分工明确：**FP32（标量浮点）、INT32（独立整数）、Tensor Core（矩阵乘）**。
- 两级调度：**warp 调度 + 双发射**，每 SM 每周期最高 8 条 warp 指令。
- 占用率 = 驻留线程 / 最大线程，靠「更多线程」隐藏访存延迟；寄存器用量是最关键的调校旋钮。
- 四层并行结构：**线程 → warp → 处理块 → SM**，每层都在「并行」，软件逻辑与硬件物理构成双轨视图。
- **辨析**：占用率越高越好有例外——计算密集 kernel 里延迟不是瓶颈，盲目堆线程反而降寄存器、损指令级并行。
- 判断「看什么数」：**AI 算力看 Tensor Core，通用算力看 FP32/INT32**——别用 CUDA 核心数衡量大模型算力。
