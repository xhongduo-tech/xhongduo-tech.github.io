## 为什么从校验闭环开始

上一节讲了「用 schema 约束生成」，但约束只是防线的第一层——
结构合法不等于内容正确。这一节补上**校验闭环（validation closed loop）**：
**生成 → 校验 → 反馈 → 重生成**，把 LLM 的输出从「候选」升级为
「事实」。校验分四层：**语法、schema、语义、图谱一致性**——
一层比一层深，一层比一层贵。理解校验闭环，
你就掌握了 LLM 时代知识系统的「质检闸门」：
不是所有 LLM 输出都能进库，只有通过全部校验的才算数。

## 1 四层校验：由浅入深的防线

LLM 输出的校验不是一次检查，而是分层过滤：

| 层 | 检查什么 | 工具 | 成本 |
| --- | --- | --- | --- |
| 语法 | 能否解析？ | JSON 解析器 | 极低 |
| schema | 字段/类型/必填对吗？ | JSON Schema | 低 |
| 语义 | 值是否合理（枚举、范围、引用）？ | 规则/LLM-judge | 中 |
| 图谱一致性 | 与既有知识冲突吗？实体存在吗？ | SHACL/图谱约束 | 高 |

- **语法层**：JSON 能 parse 吗？——结构损坏直接打回。
- **schema 层**：字段、类型、必填满足吗？——上一节的
  约束解码已保证，但对非约束输出仍要查。
- **语义层**：值合法但不合理；引用
  非法——需要领域规则或模型判断。
- **图谱层**：新三元组与既有图谱冲突吗？链接的实体存在吗？
  ——最贵但最关乎「知识质量」。

**重点：四层是「金字塔」，越往上越贵、越接近真知识。**
前两层是「机器便宜查」，后两层是「语义贵把关」。
**工程上按成本分配**：高频低质输出只过前两层，
关键数据必须过完四层。<span class="marginnote">四层校验对照第六篇的 SHACL 分层：
语法/schema ≈ SHACL 的「形状约束」（形状对不对），
图谱一致性 ≈ SHACL + 推理机的「约束与蕴含」（与本体合不合）。
<strong>LLM 校验闭环，是把第六篇的质检机制搬进了生成管道</strong>——规则没变，
只是「待检物」从人工数据换成了模型生成。</span>

## 2 公式解析：校验闭环的一次执行

一个 LLM 生成的知识三元组走完闭环：

1. **生成**：LLM 输出 `{ "subject": "谷歌", "relation": "总部位于", "object": "美国" }`。
2. **语法校验**：JSON 解析成功。
3. **schema 校验**：`subject` 为 string、`relation` 在枚举
   `["总部位于", "收购", "worksFor"]` 内——通过。
4. **图谱一致性校验**：
「谷歌」实体在库里存在吗？不存在 → 标记「待链接或拒收」。
库里已有「张三 worksFor 微软」？与新三元组冲突 → 冲突标记。
5. **反馈**：把错误信息（「tail 实体不存在」「与既有事实冲突」）
   喂回 LLM，要求修正或给出证据。
6. **重生成**：LLM 修正输出，重新进入第 2 步——直到通过或放弃。

**重点：闭环的灵魂是「反馈驱动的重生成」。**
校验不是「判死刑」，而是「给反馈、求修正」——LLM 看到错误
信息后重试，往往能自我纠正。**「一次生成一次通过」是理想，
「生成—校验—纠错」是现实**；闭环让系统把「模型会错」
变成「错能自愈」。<span class="marginnote">「反馈—重生成」让人想起第四篇的
TMS（真值维护系统）：发现矛盾，回溯原因，修正信念。LLM 校验
闭环是 TMS 的「概率版」——符号版靠逻辑回溯，LLM 版靠
「把错误喂回模型让它改」。<strong>两种「自我修复」，
一个精确一个模糊，但骨架相同：发现 → 反馈 → 修正</strong>。</span>

## 3 LLM 作为校验器：自校验与判官

除规则校验外，LLM 还能当「校验器」：

**LLM-as-judge**：让一个 LLM（或同模型的另一次调用）判断
  输出「是否合理、是否忠于原文」。适合语义层的开放判断
  （规则写不尽的「合不合理」）。
**自一致性（self-consistency）**：同一问题生成多次，
  取多数答案——「一致的多半对」。
**自我验证（self-verification）**：让模型回头检查自己的输出
  是否与证据相符（证据来自抽取的原文片段）。

**重点：LLM-judge 是「把规则的盲区交给模型判断」。**
规则校验擅长「精确的错」（缺字段、超范围），
LLM-judge 擅长「模糊的错」（「这段抽取与原文矛盾吗」）。
**两者互补：规则管「硬约束」，模型管「软判断」。**<span class="marginnote">LLM-as-judge 的
哲学位置很微妙：它既是「被校验者」又是「校验者」——用一个
模型的「共识」压住另一个模型的「幻觉」。这种「以模型制模型」
的做法有争议（同一模型可能同错），但工程上「更强的模型判
更弱的模型」效果显著——<strong>「判官」通常选更大/更强的模型</strong>。</span>

## 4 校验闭环的工程实践

把闭环落地成系统，还需要三件事：

**人工回环（human-in-the-loop）**：低置信/校验失败的数据
  进入「人工审核队列」——人是闭环的最后一道闸。
**置信度标注**：给每条输出附模型置信度/证据强度，
  指导「哪条该人工看」。
**监控与指标**：统计各层校验的通过率、重生成次数——
  「校验指标就是生成质量的仪表盘」。

**重点：校验闭环不是「加一道检查」，而是「重排整个管道」。**
它让系统「信任但验证」——LLM 快速产出，校验层严格把关，
人工兜底关键。**「自动生成 × 自动校验 × 人工抽查」是
LLM 知识系统的标准治理结构**，缺了任何一环都会出事。<span class="marginnote">把治理结构
对照第七篇「本体即代码」：本体提交要过 CI（推理机一致性检查），
LLM 生成要过校验闭环——<strong>两者的共同点是把「质量保证」自动化、
持续化</strong>。校验闭环就是 LLM 时代的「本体 CI」：每次生成
都是「一次提交」，每次校验都是「一次 CI 运行」。</span>

## 5 小结

- **校验闭环**：生成 → 校验 → 反馈 → 重生成，把候选变成事实。
- 四层校验：**语法、schema、语义、图谱一致性**——由浅入深、由便宜到贵。
- **反馈驱动重生成**：错误信息喂回模型，让它自愈。
- **LLM-judge** 处理规则写不尽的「软判断」；自一致性/自验证辅助。
- 工程三件套：**人工回环、置信度标注、监控指标**。
- 治理结构：**自动生成 × 自动校验 × 人工抽查**。
- 定位：校验闭环是 LLM 时代的「本体 CI」——生成即提交，校验即构建。

在下一节，我们将从「单次生成」走向「长期运行」——**Agent 的世界模型**：
知识图谱如何成为智能体的长期记忆，让 Agent 在多步任务里不迷路。
