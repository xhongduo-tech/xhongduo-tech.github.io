# 能力问题（competency questions）：用问题界定范围

## 为什么从能力问题开始

上一节我们看到 METHONTOLOGY 把「能力问题」当作规格阶段的交付物。
这一节把它放到聚光灯下：**能力问题（competency questions, CQ）**——
「本体必须能回答的问题」——是整个本体工程最锋利的工具。
它同时扮演三副角色：**需求分析**（界定范围）、**验收标准**（检验成果）、
**沟通媒介**（让领域专家与工程师对齐）。格吕宁格与福克斯提出它时，
只是 TOVE 方法论的一个步骤；如今它已是本体工程的事实标准起点。
理解能力问题，你就掌握了「本体该建多大、建完算不算好」的判定依据。

## 1 什么是能力问题：一个定义，三重角色

**能力问题（competency question）**：本体在其应用场景中必须能够回答的
一组自然语言问题。它回答「这个本体凭什么存在」——如果本体答不上
任何能力问题，它就是无用。

三重角色：

- **范围界定**：能力问题划出本体的边界——「问不到的问题不在范围内」。
- **需求捕获**：把模糊的领域需求变成具体的、可检验的问题。
- **验收标准**：本体建完后，逐条对照 CQ 验证——答得上才算合格。

TOVE 企业本体的一组经典 CQ 是：「某产品当前库存量是多少？」
「某订单能否在当前库存下完成？」——每一个问题都锚定一个
**具体的查询需求**。<span class="marginnote">能力问题的哲学力量在于它把
「本体好不好」从「主观评价」变成「客观测试」：就像软件验收
看「测试用例过不过」，本体验收看「能力问题答不答得上」。
需求从「形容词」（用户友好）变成「动词」（能回答什么）。</span>

## 2 怎么写好能力问题：五条准则

好的 CQ 与坏的一线之隔。工程实践总结出五条准则：

**具体**：不是「关于库存的问题」，而是「某产品当前库存是多少？」
**可测试**：每个问题都能翻译成可执行的查询（SPARQL/SQL）。
**粒度恰当**：问「类」还是「个体」要想清楚——「有哪些子类」与
  「张三的父亲是谁」是不同粒度的 CQ。
**覆盖关键决策**：优先写「会改变业务决策」的问题。
**可追溯到用途**：每个 CQ 都应能回答「谁会在什么场景问它」。

**易错点｜把「功能描述」当成 CQ**：「系统应能管理库存」不是能力问题，
它不可测试。真正的 CQ 是**能给出答案的提问**：「某产品库存低于
安全线时，系统应能列出所有受影响的订单吗？」——这句话可以
被翻译成查询并验证。<span class="marginnote">判断 CQ 好坏的一句话：
「把问题扔给一个没有本体的数据库，它能答吗？」若能，说明问题
太浅（不需要本体）；若不能，说明 CQ 真正压住了本体的价值。
CQ 应该问「本体才答得出」的问题——蕴含、分类、跨域关联。</span>

## 3 从能力问题到查询：模式化翻译

CQ 的威力在于它可以**形式化**——每条 CQ 都能翻译成一个查询模板。
任等人（Ren et al., 2014）系统化了一批**能力问题模式（CQ patterns）**：

| CQ 模式 | 自然语言例 | SPARQL 骨架 |
| --- | --- | --- |
| 实例查询 | 张三的父亲是谁？ | `SELECT ?f WHERE { :zhangsan :father ?f }` |
| 类成员查询 | 谁是医生？ | `SELECT ?x WHERE { ?x a :Doctor }` |
| 关系查询 | 谁拥有这只宠物？ | `SELECT ?o WHERE { ?o :hasPet :huahua }` |
| 子类查询 | 动物有哪些子类？ | `SELECT ?c WHERE { ?c rdfs:subClassOf :Animal }` |
| 传递查询 | 张三的所有祖先？ | `SELECT ?a WHERE { :zhangsan :ancestor+ ?a }` |
| 聚合查询 | 每个城市有多少人？ | `SELECT ?city (COUNT(?p) AS ?n) WHERE { ?p :livesIn ?city } GROUP BY ?city` |

**重点：CQ 模式让「需求」与「查询」之间有了桥梁。**
写 CQ 时，你就已经在构思查询骨架；而查询骨架决定了本体需要
哪些类、属性与推理能力。**CQ → 查询 → 建模需求**，这条链路
把需求工程与本体设计缝合在一起。<span class="marginnote">「CQ 模式」的有趣之处：
它暗示许多领域的 CQ 其实高度相似（「谁的 X 是什么」「哪些 Y 属于 Z」）。
识别出模式，就能复用对应的建模方案——这正是「本体设计模式」
（后续一节）的源头：<strong>问题有类型，解法就有模式</strong>。</span>

## 4 能力问题在工程中的位置

CQ 贯穿本体工程的多个阶段：

**需求阶段**：CQ 是规格文档的核心。
**概念化阶段**：CQ 反推需要的概念与关系。
**评估阶段**：CQ 是验收清单——逐条「本体能答吗」。
**部署之后**：CQ 是回归测试——领域变化后，再跑一遍 CQ。

在**敏捷式本体工程**里，CQ 还充当「用户故事」：每个迭代
「选几条 CQ → 建对应模型 → 验证 CQ 可答」，本体随迭代增量生长。
**CQ 让本体开发从「一次成型」变成「增量交付」**——这比
METHONTOLOGY 的瀑布式更贴合现实节奏。<span class="marginnote">CQ 驱动开发（CQDD）
是近年来流行的轻量实践：把 CQ 写进 Git 仓库、每个 PR 附带
「本 PR 让哪些 CQ 变得可答」、CI 里跑对应的 SPARQL 验证。
本体从「文档」变成「可测试的代码」——CQ 正是这份可测试性的载体。</span>

## 5 局限与对策

CQ 不是万能的需求工具，它有三个已知短板：

- **非功能需求表达不了**：性能、隐私、可用性——「查询应在 1 秒内返回」
  不是 CQ 能承载的。
- **问题写不全**：需求可能以陈述句（「库存必须精确」）而非问题形式存在。
- **静态视角**：CQ 抓「查询」，抓不住「推理任务的动态变化」。

对策：

- 用**附加需求清单**补 CQ（性能指标、约束、非功能需求）。
- 把陈述句需求**改写**成可检验问题（「库存必须精确」→「系统能发现
  库存不一致吗」）。
- 定期**回访 CQ**，随领域演化增删——CQ 不是一次性的，是活文档。

**重点：CQ 是需求工具中最强的一把，但不是唯一的一把。**
成熟的工程把 CQ 与用例、非功能需求、约束清单**组合使用**——
CQ 管「能回答什么」，其余工具管「答得多快、多安全、多合规」。

## 6 小结

- **能力问题**：本体必须能回答的问题，兼具需求、验收、沟通三重角色。
- 写 CQ 五准则：**具体、可测试、粒度恰当、覆盖关键决策、可追溯**。
- **CQ 模式**把自然语言问题翻译成 SPARQL 骨架，连接需求与建模。
- CQ 贯穿**需求、概念化、评估、部署后回归**全流程。
- 敏捷实践中 CQ 充当**用户故事**，驱动增量式本体开发。
- 局限：**表达不了非功能需求、问题写不全、视角偏静态**——需组合其他工具。
- 定位：CQ 是需求工具中的**最强单兵**，不是**唯一兵器**。
