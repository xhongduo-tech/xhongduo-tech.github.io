# 从文本到图：LLM 驱动的知识抽取流水线

## 为什么从 LLM 抽取开始

第八篇的构建流水线（NER → RE → 融合）费时费力，是知识图谱
最大的成本瓶颈。LLM 的降临让「自动建图」第一次真正可行：
一段提示词，LLM 就能从文本里抽出实体、关系、事件。
这一节讲**LLM 驱动的知识抽取流水线**——从语料库到知识图谱的
完整路径：分块 → 提示抽取 → 结构化输出 → 实体链接与去重 →
溯源与校验 → 入库。理解这条流水线，你就掌握了 GraphRAG
（上一节）的前置工序，也看清了 LLM 时代知识图谱
「自底向上」构建的新形态。

## 1 流水线全景：从语料到图谱

LLM 驱动的抽取流水线大致六步：

1. **分块**：语料切成 chunk（控制提示长度与抽取粒度）。
2. **提示抽取**：用 LLM 从每个 chunk 抽实体、关系（+ 事件）。
3. **结构化输出**：LLM 输出 JSON（实体列表、关系三元组）。
4. **实体链接**：把抽取的实体名链接到既有图谱/标准实体
   （「Google Inc.」→ 库里的「谷歌」节点）。
5. **去重与消解**：合并跨 chunk 的重复实体（第八篇实体消解）。
6. **校验与入库**：SHACL/规则校验（第 5 节），通过后加载存储。

**重点：LLM 抽取只是「第一道粗加工」——真正的功夫在后续。**
LLM 抽出的三元组是「候选」，要经链接、去重、校验才能成为
「事实」。**「抽取 10% 的功夫，后处理 90%」是 LLM 建图的真相**——
模型负责「说」，管道负责「确认」。<span class="marginnote">把这条流水线与第八篇的
传统管线对照：NER/RE 是「训练专用模型」，LLM 是「提示通用模型」。
省掉的不是「后处理」，而是「标注数据与模型训练」——LLM 把
「特征学习」外包给了预训练，把「抽取执行」留在提示里。
<strong>工具变了，但「抽取 → 清理 → 校验」的骨架没变</strong>。</span>

## 2 提示设计与 schema 约束

LLM 抽取的效果，一半由提示词决定：

**给 schema**：告诉 LLM 实体类型与关系类型
  （「实体只能是 Person/Company/Location，关系只能是 worksFor/
  locatedIn」）——这就是**用本体约束生成**（下一节专讲）。
**要结构化**：指令「输出 JSON 数组，每个元素含
  entity/type/mention」——让模型产出可解析的结构。
**示例**：给 1-2 个 few-shot 示例，质量立涨。
**证据要求**：指令「每个三元组附原文片段」——为溯源留证据。

```json
{
  "entities": [
    { "entity": "张三", "type": "Person" },
    { "entity": "谷歌", "type": "Company" }
  ],
  "relations": [
    { "head": "张三", "relation": "worksFor", "tail": "谷歌",
      "evidence": "张三在 2020 年加入谷歌" }
  ]
}
```

**重点：schema 约束 + 结构化输出是 LLM 抽取的「纪律」。**
没有 schema，模型自由发挥（抽出一堆未定义类型）；没有结构化，
输出没法程序化消费。**「给模型规则，模型还你整洁」**——LLM 的
生成能力需要被约束才能变成工程资产。<span class="marginnote">这段 JSON 恰好演示了
「本体约束的生成」的价值：schema 就是第七篇的本体/TBox，
LLM 的输出必须落在 schema 定义的类型里——<strong>LLM 在扮演
「受约束的 ABox 填充器」</strong>。下一节会把这条「约束生成」
单独放大。</span>

## 3 抽取后的清理：链接、去重、溯源

LLM 抽取产出的「脏」主要有四类，各有对策：

| 问题 | 现象 | 对策 |
| --- | --- | --- |
| 实体名不一致 | 「谷歌」「Google」「Google Inc.」 | 实体链接 + 消解 |
| 关系幻觉 | 抽出原文不存在的关系 | 证据校验 + 规则过滤 |
| 跨 chunk 重复 | 同一实体抽了 N 次 | 图谱级去重（MERGE） |
| 类型漂移 | 实体类型随上下文变 | schema 约束 + 二次校验 |

**重点：实体链接是 LLM 建图的关键环节**——LLM 抽出的「名字」
不是「实体」，链接到图谱的标准节点后才是。**「Google Inc.」
只有被链接到库里的「谷歌」节点，才能共享它的全部属性和关系**。
溯源（evidence）则是「幻觉过滤器」——要求每个三元组带原文证据，
没有证据的一律可疑。<span class="marginnote">「名字 → 实体」的链接，正是第八篇
实体消解的延续：LLM 时代它多了一个来源（模型的抽取），
但「同一性判定」的算法本质没变。<strong>图谱的「同一性」问题，
从福尔摩斯（第三篇）一路走到 LLM 抽取，始终是知识工程的核心</strong>。</span>

## 4 公式解析：一个 chunk 的抽取走查

用一个句子走一遍流水线。原文：「张三在 2020 年加入谷歌，担任工程师。」

**第一步，schema 设定**：实体类型 Person/Company/Location；
  关系类型 worksFor/locatedIn。
**第二步，LLM 抽取**（带 schema 的提示）：
实体：张三（Person）、谷歌（Company）、工程师（类型存疑）。
关系：worksFor(张三, 谷歌)、joinedAt(张三, 2020)、
    hasRole(张三, 工程师)。
**第三步，链接去重**：若库里已有「谷歌」节点，把抽取的
  「谷歌」链接过去，不新建。
**第四步，校验**：SHACL 检查——worksFor 的宾语必须是 Company
  （满足）；joinedAt 的宾语必须是 date 类型（"2020" 转成 2020-01-01？存疑，标记待修）。
**第五步，入库**：通过校验的三元组写入图谱，附 evidence 与来源。

**重点：走查暴露了 LLM 抽取的典型坑——「2020」的类型不完整。**
LLM 给的是裸字符串，schema 校验抓住它，标记待修。**这正是
「生成 + 校验」闭环的价值**：LLM 负责提取信息，规则负责
抓住缺陷——**模型说「有」，规则说「对不对」**。<span class="marginnote">「2020」的类型问题
是 LLM 抽取与真实本体之间「粒度鸿沟」的缩影：模型给出自然语言
的粗糙值，本体要求精确的类型与格式。<strong>「翻译 + 校验」是
跨越这条鸿沟的必经桥</strong>——第 5 节的结构化输出验证，
就是这座桥的正式化。</span>

## 5 与监督管线的对比

| 维度 | 监督管线（第八篇） | LLM 抽取 |
| --- | --- | --- |
| 模型 | 专用 NER/RE 模型 | 通用 LLM |
| 数据需求 | 大量标注 | 少量示例/零样本 |
| 精度 | 高（受限领域） | 中高（易幻觉） |
| 领域迁移 | 要重训 | 换提示即可 |
| 成本 | 训练高、推理低 | 推理高 |
| 输出 | 标签/分类 | 自由结构（需约束） |

**重点：LLM 抽取不是「免费升级」，而是「换了一个成本结构」**
——把「标注 + 训练」的一次性高成本，换成了「提示 + 推理」的
持续运行成本。**它让「小团队建大图谱」成为可能**，但把
「质量保障」的责任转移到了管道后处理上。**选哪种，取决于
你的规模、领域与精度要求**——固定领域高精度要监督模型，
开放领域快起步要 LLM。

## 6 小结

- **LLM 抽取流水线**：分块 → 提示抽取 → 结构化输出 → 链接去重 →
  校验 → 入库。
- **提示设计的核心**：给 schema、要 JSON、给示例、要证据。
- 抽取后的四类脏：**名字不一、关系幻觉、跨块重复、类型漂移**，各有对策。
- **实体链接**是「名字 → 实体」的关键一跳；**证据**是幻觉过滤器。
- **「生成 + 校验」闭环**：LLM 说「有」，规则说「对不对」。
- 与监督管线对比：**换成本结构而非免费升级**——质量责任移到后处理。
- 一句话：**LLM 让建图快 100 倍，也让「垃圾进垃圾出」快 100 倍——
  后处理比抽取更关键**。
