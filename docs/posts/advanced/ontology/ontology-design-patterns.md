# 本体设计模式（ODP）：可复用的建模方案

<div class="epigraph">

## 为什么从 ODP 开始

NeOn 把「复用」列为默认姿势，但复用什么、怎么复用，还需要具体抓手。
**本体设计模式（Ontology Design Pattern, ODP）**就是那个抓手——
它是「被反复验证、可复用的建模方案」，类比于软件工程里
GoF 的设计模式。建模者常遇到的难题（「这个关系是一对多，怎么建模？」
「这个值到底是类还是实例？」）几乎都有现成的 ODP 答案。
理解 ODP，你就从「每个本体都从零发明建模」升级到
「站在前人方案的肩膀上组装」——这是本体工程走向成熟的重要标志。

## 1 ODP 的类型谱系

ODP 不是一种东西，而是一族。按用途分：

| 类型 | 解决什么 | 例子 |
| --- | --- | --- |
| 逻辑模式 | 常见的逻辑结构难题 | n-ary 关系、值分区 |
| 内容模式（CP） | 重复出现的领域建模问题 | 参与、角色、时间区间 |
| 结构模式 | 架构组织方式 | 模块化、分层 |
| 推理模式 | 需要特定推理支持 | 默认推理、传递闭包 |
| 表现模式 | 怎么命名与注释 | 命名约定、注释规范 |
| 词法句法模式 | 从文本中识别概念 | 名词短语 → 类 |

**重点：最常用的是「逻辑模式」与「内容模式」**——前者解决
「结构上怎么搭」，后者解决「这个领域问题怎么建模」。
其余类型更多是工程规范。理解 ODP，重点是掌握这两类中最经典的几个。 <span class="marginnote">ODP 与软件设计模式的
类比值得压紧：GoF 的「观察者」「工厂」是代码层面的解决方案，
ODP 的「n-ary 关系」「值分区」是本体层面的解决方案。两者的共同点是
「<strong>问题有类型，解法就有模式</strong>」——不重复发明轮子，是工程师的本能。</span>

## 2 逻辑模式一：n-ary 关系（关系重化）

**问题**：RDF/OWL 的属性是**二元**的（`hasTeacher`），但现实里很多关系
是 **n 元**的——「张三于 2020 年教李四微积分」有**三个**参与者
（教师、学生、课程），再加时间。怎么建模？

**n-ary 关系模式（n-ary relation pattern）**：把关系本身**重化（reify）**
成一个「关系个体」：

```turtle
:教学 x a :教学关系 ;
       :教师 :张三 ;
       :学生 :李四 ;
       :课程 :微积分 ;
       :时间 2020 .
```

**重点：把关系变成个体，n 元信息各归其位。** 教学关系成了一个类，
教师、学生、课程、时间都成了它的属性。代价是查询变绕
（要先找到关系个体），收益是**不丢失任何信息**——三元组的世界
装不下四元，重化是唯一干净的出路。<span class="marginnote">重化的哲学对应
在第四篇：把「关系」变成「对象」，正是语义网络「弧可以变成节点」
的极端化——也是描述逻辑里「角色可以角色化（rolification）」的
同构操作。关系与对象的界限，在本体工程里是流动的。</span>

## 3 逻辑模式二：值分区（类还是实例）

**问题**：「红色」「蓝色」到底是**类**还是**实例**？`:红色 a :颜色`
（实例）还是 `:红色 rdfs:subClassOf :颜色`（子类）？建模者常纠结。

**值分区模式（value partition pattern）**：当值的集合是**封闭且有限**
（如颜色、性别、状态）时，把它们建模成**互不相交的子类**：

```turtle
:颜色 a rdfs:Class .
:红色 rdfs:subClassOf :颜色 .
:蓝色 rdfs:subClassOf :颜色 .
:红色 owl:disjointWith :蓝色 .
```

**重点：值分区的准则是「这个值集会不会扩展」。** 颜色、性别、订单状态
是封闭的——用互斥子类，推理机能自动检查「一个东西不能同时是红色
和蓝色」。但「人名」「地名」是开放的——必须用实例。**判据一句话：
封闭有限 → 子类；开放无限 → 实例。**<span class="marginnote">值分区与第五篇的
「不相交」直接挂钩：`disjointWith` 让「颜色不能既是红又是蓝」变成
可检测的约束。它也是 SHACL 的 `sh:in`（枚举）的替代方案——
用类层级表达枚举，比用约束列表表达枚举更「可推理」。</span>

## 4 内容模式：描述情境模式

内容模式（CP）针对「重复出现的领域问题」。最经典的是
**描述情境模式（description and situation, D&S）**：

**问题**：如何表达「某个物体在某个情境下扮演某个角色」——
「张三在急诊科担任主治医师」，「这座楼在这次地震中被判定为危房」。
对象与角色分开建模：

```turtle
:张三 a :人 .
:急诊科 a :科室 .
:主治医师 x a :角色 ;
          :由 :张三 扮演 ;
          :在 :急诊科 .
```

**重点：D&S 模式把「持续的实体」与「情境性的角色」分离。**
张三一直是「人」，但他「担任主治医师」只在这段情境里成立——
把角色独立成个体，就能表达「同一个人在不同情境扮演不同角色」、
「同一个物体在不同评估里得到不同判定」。**这个模式是医疗、司法、
工程评估等领域的建模基石。**<span class="marginnote">D&S 模式的哲学根子
在第三篇「时间中的存在」：endurantism（持续存在）把张三当成
四维中持续的个体，角色只是他在某时段的「状态」——本体工程
用「角色个体」实现了哲学上「本质 vs 偶性」的区分。</span>

## 5 怎么用 ODP：工作流与门户

使用 ODP 不是「套模板」，而是「匹配问题 → 定制方案」：

1. **识别问题**：你的建模难点属于哪类？（n 元关系？枚举值？角色？）
2. **检索模式**：在 `ontologydesignpatterns.org` 按问题类型检索 CP。
3. **理解语义**：读模式的文档与示例，理解它的类、属性与约束。
4. **定制适配**：把模式中的类映射到你的领域（`教学关系` → `雇佣关系`）。
5. **集成验证**：并入本体，跑推理机验证与既有公理一致。

**重点：ODP 是「起点」不是「终点」**——它给你一个经过验证的骨架，
你往里填领域细节。**直接照抄不思考，会引入不匹配；完全不用，
则重复发明轮子。** 成熟团队把常用 ODP 整理成本地模式库，随取随用。<span class="marginnote">ODP 门户的价值
不只是「模式本身」，还有<strong>模式的「已知陷阱」文档</strong>——每个模式都
附注「何时不该用它」。这份「反模式」知识，常常比模式本身更值钱。
工程经验的传承，一半是「怎么做」，一半是「千万别怎么做」。</span>

## 6 ODP 的价值与边界

**价值：**

- **质量**：模式经过验证，用它们少踩建模坑。
- **可互操作**：共享模式 = 共享结构，不同系统容易对齐。
- **速度**：不重复发明，建模快一个数量级。

**边界：**

- **过度使用**：为了用模式而用，引入不必要的复杂度。
- **模式不匹配**：强行套用不适合领域的模式，比不用更糟。
- **维护成本**：模式会演化，追踪版本需要投入。

**重点：ODP 的定位是「脚手架」，不是「囚笼」。** 它加速但不替你思考——
真正的建模判断（这个值集封不封闭、这个角色持不持久）永远在你手里。
**模式是知识的压缩，不是思考的替代。**

## 7 小结

- **ODP** 是可复用的建模方案，类比软件设计模式，分逻辑/内容/结构等六类。
- **n-ary 关系模式**：把 n 元关系重化为「关系个体」，各元信息各归其位。
- **值分区模式**：封闭有限的值集建模成互斥子类；判据「封闭 → 子类，开放 → 实例」。
- **描述情境模式（D&S）**：把「持续的实体」与「情境性角色」分离。
- 用 ODP 四步：**识别问题 → 检索模式 → 理解语义 → 定制集成**。
- 价值：**质量、可互操作、速度**；边界：**过度使用、不匹配、维护成本**。
- 定位：ODP 是**脚手架**，加速但不替代你的建模判断。
