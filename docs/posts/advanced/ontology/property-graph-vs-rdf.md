# 属性图 vs RDF：两种范式的对比与互操作

<div class="epigraph">

## 为什么从范式之争开始

连续两节我们分别看了属性图（Neo4j + Cypher）与 RDF（三元组存储 + SPARQL），
现在让两个阵营正面交锋。**属性图（property graph）**以「节点/关系/属性」
为模型、遍历优先；**RDF** 以「三元组/IRI/语义」为模型、推理优先。
这场争论不是学术意气——**它决定了你的知识图谱长成什么样**：
能推理还是跑得快、开放互连还是应用内嵌、有标准还是灵活。
理解这场范式之争，你就不再是「选个数据库」，而是**选一个世界观**；
也理解了两者在工程里如何互操作、如何混合共存。

## 1 六大差异维度

| 维度 | 属性图 | RDF |
| --- | --- | --- |
| 身份 | 局部 ID | 全局 IRI |
| 语义 | 无标准形式语义 | 模型论语义 + 推理 |
| schema | 标签 + 约束 | RDFS/OWL |
| 关系属性 | 原生支持 | 需重化（reification） |
| 空白节点 | 无 | 有 |
| 查询 | Cypher/Gremlin（无标准） | SPARQL（W3C 标准） |
| 推理 | 无原生 | 原生蕴含 |
| 互操作 | 靠转换 | 天然链接数据 |

**重点：差异的根子在「语义」与「身份」两件事。** RDF 用全局 IRI
（每个资源世界唯一）+ 形式语义（可推理、可链接）；
属性图用局部 ID + 工程约束（快、灵活、无推理负担）。
**RDF 是「为开放语义而生」，属性图是「为应用性能而生」**——
它们不是同一目标的两个版本，而是两个目标的各自最优解。<span class="marginnote">「全局 IRI vs 局部 ID」
是两派最根本的分歧：RDF 相信「同一资源该有同一名字」（链接数据
四原则），属性图相信「我的应用里一个 ID 就够了」。前者换取
跨系统互操作，后者换取实现简单——<strong>这又是一个「共享 vs 效率」的
永恒权衡</strong>。</span>

## 2 各自的优势场景

**RDF 的「主场」：**

- **开放数据互连**：DBpedia、Wikidata——数据要被人引用、合并、链接。
- **跨组织集成**：多个系统共享一套本体语义。
- **需要推理**：医学、法规——蕴含查询是刚需。
- **标准化**：W3C 全套标准，长期兼容有保障。

**属性图的「主场」：**

- **高并发遍历**：社交网络、风控——多跳查询要毫秒级。
- **应用内嵌**：单团队掌控、schema 快速演进。
- **关系属性密集**：交易、雇佣、评分——「边的属性」要原生。
- **开发效率**：Cypher 直观、团队上手快。

**重点：选范式先看「你的图谱开放吗、要推理吗」**——开放 + 推理
选 RDF；封闭 + 性能选属性图。**多数企业内部图谱选属性图
（不开放、要速度），多机构共享图谱选 RDF（要互操作、要语义）。**<span class="marginnote">把两派的主场
放回本书坐标：RDF 是「本体论语义派」的存储（第五、六篇一路下来），
属性图是「工程遍历派」的存储（第四篇语义网络直觉的工业版）。
<strong>范式之争实为本书两条工程路线的存储层摊牌</strong>——它们的哲学
分歧可以一直追溯到「语义是否先于实现」这个本体论问题。</span>

## 3 互操作：RDF ↔ 属性图的转换

两个范式可以互转，转换规则值得写清：

| RDF 概念 | 属性图对应 |
| --- | --- |
| IRI（个体） | 节点 ID |
| `rdf:type` | 节点标签 |
| 字面量属性 | 节点属性 |
| 关系三元组 | 关系 + 类型 |
| 重化的 n 元关系 | 关系属性（天然） |
| 空白节点 | 匿名节点（映射成自动 ID） |
| `subClassOf` 等公理 | 丢失（需外部本体层） |

**重点：转换是「有损」的——方向不同，损失不同。**
RDF → 属性图：语义公理（`subClassOf`、推理）丢失，重化可简化为
关系属性；属性图 → RDF：局部 ID 要生成 IRI，关系属性要重化。
**工具（rdf2neo、Neosemantics）能做转换，但「语义无损」
需要额外维护本体层**——这正指向下一节的混合架构。<span class="marginnote">互操作的哲学
注脚：转换的「有损」暴露了两种模型的<strong>表达力不对等</strong>——
RDF 能表达「类的层级与推理」，属性图不能；属性图能原生表达
「关系的属性」，RDF 要绕路重化。<strong>没有谁完全包含谁</strong>——
这正是它们能共存、也必须要映射的原因。</span>

## 4 混合架构：两全其美的工程答案

现实中，成熟团队很少「非此即彼」。常见混合方案：

- **双库并行**：RDF 存储管语义（本体、推理、开放数据），
  属性图管性能（遍历、推荐、风控），用管道同步。
- **属性图 + 本体层**：Neo4j 存数据，外部用 OWL 本体 + SHACL
  管语义与校验——「图库负责跑，本体负责义」。
- **RDF + 物化视图**：三元组存储做推理物化，把结果同步到
  属性图供快速查询。

**重点：混合架构把「语义」与「性能」分给两个引擎各司其职。**
这正是第六篇「OWL 管推理、SHACL 管校验」双引擎思想的存储版——
**一个知识系统可以有多个引擎，只要每个引擎做自己最擅长的事。**<span class="marginnote">混合架构的
管理成本不容小觑：数据同步、语义一致性、双份存储的运维。
工程现实是：<strong>小团队先用一种范式撑到极限，再为特定查询加第二个
引擎</strong>——「先单库、后混合」的渐进路线，比「上来就双库」务实得多。</span>

## 5 公式解析：一条选型判据

把选型压成「三个问题」：

1. **数据要开放共享吗？** 是 → 倾向 RDF（全局 IRI、可链接）。
2. **需要推理/蕴含查询吗？** 是 → RDF（或属性图 + 本体层）。
3. **查询以多跳遍历为主吗？** 是 → 属性图（index-free adjacency）。

**逐项拆解判据的组合：**

- **（是, 是, 是）**：开放 + 推理 + 遍历 → 混合（RDF 底座 + 属性图加速）。
- **（否, 是, 是）**：封闭 + 推理 + 遍历 → 属性图 + 本体层。
- **（否, 否, 是）**：纯应用图谱 → 属性图，够用且快。
- **（是, 是, 否）**：开放知识库 → RDF 三元组存储。

**重点：选型是「三维打分」，不是「站队」。** 大多数系统在
某个维度上是混合的。**把「选属性图还是 RDF」换成「我的三个
答案是什么」，争论就变成了工程决策。**<span class="marginnote">这个三维判据
也是第九篇 GraphRAG 选型的钥匙：RAG 的图底座要「检索快」
（属性图或三元组皆可）又要「语义准」（靠本体约束），
于是 GraphRAG 常常「两者都要」——范式之争在 LLM 时代
没有终结，只是换了个场地继续。</span>

## 6 小结

- 属性图与 RDF 是**两个问题的各自最优解**：应用性能 vs 开放语义。
- 六大差异：**身份（局部 ID vs 全局 IRI）、语义、schema、关系属性、
  空白节点、推理与标准**。
- RDF 主场：**开放互连、跨组织集成、推理、标准化**。
- 属性图主场：**高并发遍历、应用内嵌、关系属性、开发效率**。
- 互转**有损**：语义公理 vs 关系属性，方向不同损失不同。
- **混合架构**是主流：语义与性能分给两个引擎，各司其职。
- 选型三问：**开放吗？要推理吗？遍历多吗？**——三维打分，而非站队。
