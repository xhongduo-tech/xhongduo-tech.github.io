# 知识融合：实体对齐与实体消解

<div class="epigraph">

## 为什么从知识融合开始

抽取产出了大量三元组，但它们来自**不同来源**——同一个「谷歌」在
A 源叫「Google」、在 B 源叫「谷歌公司」、在 C 源还有个旧名「Google Inc.」。
不合并，图谱里就躺着三个「谷歌」，查询与统计全部失真。**知识融合
（knowledge fusion）**就是处理这团乱麻的工序：**实体对齐**（跨图谱
找同一实体）与**实体消解**（库内去重/指代消解）。它是知识图谱
「多源合一」的枢纽，也是第四篇「虚构对象的同一性」那个哲学问题
的工程总爆发——**「两个名字是不是一个东西」，在这里变成算法问题**。

## 1 任务与术语：一物多名，一名多物

先理清一族的相似术语：

- **实体消解（entity resolution）**：判断两个记录是否指向同一真实实体
  （最通用术语）。
- **记录链接（record linkage）**：数据库领域对同一任务的称呼。
- **去重（deduplication）**：同一数据源内部找重复。
- **实体对齐（entity alignment）**：两个知识图谱之间找同一实体。
- **指代消解（coreference resolution）**：文本内「他」「谷歌」指向同一实体。

**重点：这些术语是同一个问题的不同场景。** 共同的核心是——
**给定两个实体描述，判断「同一」与否**。难度在于：**同名可能是
不同实体**（叫「张三」的有几百万人），**不同名可能是同一实体**
（「北京」与「Beijing」）。「同一性」从来不是字符串的事。<span class="marginnote">这个
问题在第三篇《虚构对象的本体论地位》已经埋过伏笔：福尔摩斯
「两个版本是不是同一个」——工程上，实体消解就是给所有实体
（包括福尔摩斯）发明同一性判据。哲学讨论的「同一性标准」，
在工程里变成了「相似度阈值 + 合并规则」。</span>

## 2 流水线第一站：阻塞与候选生成

直接「两两比较」所有实体是不可行的——$n$ 个实体就是 $O(n^2)$ 对，
亿级实体完全跑不动。**阻塞（blocking）**先把候选对压缩：

**阻塞键（blocking key）**：用「首字母」「年份」「国家」等粗特征
  把实体分桶，只比较同桶内的对。
**排序邻域（sorted neighborhood）**：按排序键滑动窗口，
  只比较窗口内的记录。
**LSH（局部敏感哈希）**：把相似实体哈希到同一桶，兼顾召回与效率。

**重点：阻塞是「用粗筛换效率」**——它宁可漏掉一些「表面不像、
实际相同」的对（损失召回），也要把比较空间压到可计算。
**阻塞质量决定整个流水线的上限**：阻塞键设计不好，
真正的匹配对根本不进候选集，后面再精确也白搭。<span class="marginnote">阻塞与
第五篇 Tableau 的「吸收优化」异曲同工：都是「先用廉价规则砍掉
大部分不可能，再对剩下的做精确判定」。大规模计算里，
「先粗筛再精判」是通用的性能法则——从数据库 join 到
知识图谱对齐皆然。</span>

## 3 相似度计算：属性级与结构级

候选对进入精确比较，计算「同一个」的证据。证据分两级：

| 层级 | 方法 | 依据 |
| --- | --- | --- |
| 属性级 | 编辑距离、Jaccard | 名字/标签的字符串相似 |
| 属性级 | 词嵌入相似（SBERT 等） | 语义相似（「汽车」≈「轿车」） |
| 属性级 | 字段比对 | 出生日期、坐标、国籍 |
| 结构级 | 邻居图相似 | 共享邻居越多越可能是同一实体 |
| 结构级 | 嵌入对齐（TransE/GCN） | 把实体映射到同一向量空间比相似 |

**重点：没有单一证据能定「同一」——成熟系统把多级证据加权。**
名字像 + 生日同 + 邻居重叠多 → 高分。**「同一性」是证据的
加权综合**，与第七篇本体匹配的融合公式同构——匹配对齐的是
「类」，实体对齐对齐的是「个体」，方法同源。<span class="marginnote">结构级相似
（共享邻居）尤其有趣：它对应第四篇「语义网络」的联想直觉——
「朋友多的人大概率是同一个人的朋友」。现代嵌入方法
（TransE/GCN 对齐）把「邻居结构」学成向量，让「结构相似」
变成「向量相近」——这正是第八篇最后一节「知识表示学习」的前奏。</span>

## 4 公式解析：从相似度到合并

得到相似度之后，还要决定「合不合并、怎么合并」。这一步是决策：

**阈值法**：$s \geq \theta$ 则合并。简单，但阈值难调。
**分类器**：把「相似度向量」喂给二分类器，学出「是否同一」的决策面。
**聚类**：对候选图做「连通分量」聚类——同簇合并、跨簇保留。
**传递闭包**：A≈B 且 B≈C → 推 A≈C（用 `≈` 的传递性）。

**逐项拆解「传递闭包合并」的逻辑：**

**前提一**：$A$ 与 $B$ 判定为同一（$B$）。
**前提二**：$B$ 与 $C$ 判定为同一（$B \approx C$）。
**结论**：由 $\approx$ 的传递性，$A$ 与 $C$ 也应合并。
**风险**：传递闭包会「放大错误」——一次误判沿着闭包传染成一片。

**重点：合并不是终点，合并后的**一致性**才是考验。**
合并实体的属性可能冲突（A 源说出生于北京，B 源说出生于上海）——
需要**冲突消解策略**（多数投票、按源可信度、保留全部）。
**知识融合的最后一公里，是「怎么把合并结果收拾得自洽」。**<span class="marginnote">等价关系 `≈` 的
传递性是双刃剑：它让「A≈B、B≈C 则 A≈C」自动化（省力），
也让「一个错误链接传染全簇」（危险）。现代图谱因此给 `≈` 链接
加<strong>上下文限制</strong>，或用「加权合并」而非「纯传递」——
工程上对「全传递」保持警惕，正是对逻辑天真的清醒。</span>

## 5 跨图谱实体对齐与 LLM 时代

**跨图谱实体对齐（cross-KG alignment）** 是知识融合的前沿形态：

**嵌入对齐**：用 TransE/GCN 把两个图谱的实体嵌入同一向量空间，
  用「种子对齐」训练映射，再靠向量相似找新对齐（MTransE、GCN-Align）。
**LLM 对齐**：用大模型判断两个实体描述是否同一——
  「Google Inc. 与 谷歌公司 是同一实体吗？」，零样本即可，效果强大。

**重点：LLM 让「同一性判断」从「特征工程」走向「语义理解」。**
「北京大学 vs 北大」「苹果公司 vs Apple Inc.」这类需要背景知识的
对齐，传统特征很难处理，LLM 却几乎零成本。**代价是稳定性与成本**——
LLM 判断需要校验，且不适合处理上亿候选（先靠阻塞压缩，再用 LLM 精判）。<span class="marginnote">LLM 对齐的
工程姿势是「<strong>阻塞压缩 + LLM 精判 + 规则兜底</strong>」：阻塞把亿级压到
千级，LLM 把千级判完，规则兜住「完全相同」的确定性案例。
这不是「让 LLM 接管」，而是「让 LLM 在人类设计的管道里当精确部件」——
第九篇的神经—符号融合，正是这种分工的系统化。</span>

## 6 小结

- **知识融合**处理「多源同一」：实体消解、记录链接、去重、跨图谱对齐、指代消解。
- 难度根源：**同名不同物、异名同物**——同一性不是字符串问题。
- 流水线三步：**阻塞（候选生成）→ 相似度计算 → 分类/聚类/合并**。
- **阻塞**用粗键压缩比较空间，决定流水线的召回上限。
- 相似度证据分**属性级**（字符串/嵌入）与**结构级**（邻居/嵌入对齐）。
- 合并后的**冲突消解**与**传递闭包放大风险**是最后一公里的考验。
- LLM 时代：**阻塞压缩 + LLM 精判 + 规则兜底**，分工制胜。
