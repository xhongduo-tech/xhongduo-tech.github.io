## 为什么从图数据库开始

构建流水线产出了知识，接下来是**存储**。知识图谱的存储有两条主流：
**图数据库**（Neo4j 为代表，用**属性图模型**）与 **RDF 三元组存储**
（Jena、Virtuoso，下一节）。这一节聚焦图数据库与属性图模型——
这是工业界知识图谱**最常用的工程形态**：节点、关系、属性三件套，
配合 `index-free adjacency` 的遍历引擎，让「关系的多跳查询」
快到极致。理解属性图，你就理解了「工程派」知识图谱的
存储底座——也看清了它与 RDF「语义派」的分野（再下一节对比）。

## 1 属性图模型：三件套

**属性图（property graph）**用三类构件表示知识：

- **节点（node）**：实体。可带**标签（label）**（相当于类）与
  **属性（property）**（键值对）。
- **关系（relationship）**：两个节点之间的边。有**类型（type）**、
  **方向**，且**可以自带属性**（关系上的键值对）。
- **属性（property）**：节点或关系上的「键 → 值」。

```cypher
(:Person {name: "张三"})
  -[:WORKS_FOR {since: 2018}]-> (:Company {name: "谷歌"})
```

**重点：属性图最独特的点，是「关系也能带属性」。**
`:WORKS_FOR` 这条边自带 `{since: 2018}`——「从 2018 年起在谷歌工作」。
这在 RDF 里要用「重化」（把关系变个体）才能表达，
属性图却是一等公民。**属性图的建模哲学：关系不是连接，
关系本身就是数据。**<span class="marginnote">「关系带属性」让属性图特别适合
「关系的属性」密集的领域：雇佣关系（入职时间）、交易（金额、时间）、
评论（评分）。这也是它在金融、社交、风控领域大受欢迎的原因——
这些领域的「边」和「点」一样信息丰富。</span>

## 2 Neo4j 的引擎：index-free adjacency

Neo4j 性能的核心是 **index-free adjacency（免索引邻接）**：

每个节点物理上「记住」它的邻居（指针直接相连）；
遍历「张三 → WORKS_FOR → 谷歌 → 位于 → 美国」时，
  每一步都是**指针跳转**，不需要查索引；
查询成本与「走过的路径长度」成正比，与**全图大小无关**。

**重点：这是图数据库与关系数据库的根本差异。** 关系数据库做
多跳 join，每次 join 都要查索引/哈希；图数据库做遍历，
直接沿指针走。**当你的查询是「多跳关系模式」时，图数据库
在常数图上可能快几个数量级。**「多跳」正是社交网络、风控
反欺诈（「张三离洗钱者几步远」）这类查询的本质。<span class="marginnote">index-free adjacency
的哲学是「用物理结构换算法复杂度」——把「关系」存成物理指针，
遍历就从「搜索」变成「行走」。这让人想起第四篇语义网络
「沿链行走」的直觉：图数据库把语义网络的行走直觉，
变成了工业级的物理实现。</span>

## 3 用 Neo4j 建模一个知识图谱

属性图的建模步骤，与本体工程有对应也有差异：

1. **定标签**：实体类别 → `:Person`、`:Company`（对应类的粗粒度版本）。
2. **定关系类型**：`:WORKS_FOR`、`:FOUNDED_BY`（对应关系的粗粒度版本）。
3. **定属性**：节点属性（`name`、`birthDate`）、关系属性（`since`）。
4. **加约束**：Neo4j 支持唯一性约束与存在性约束（类似 SHACL 的封闭校验）。

**重点：属性图的「schema」比 RDF 轻**——标签与关系类型是
「松散的类型」，没有 OWL 那套公理语义。**Neo4j 的世界观是
「够用的结构 + 极致的遍历」**，而不是「严格的语义 + 推理」。
这也解释了为什么企业图谱常常「Neo4j 存数据、OWL 管语义」
双轨并用。<span class="marginnote">属性图建模与第五篇 TBox 的差异值得记住：
标签（`:Person`）没有 `rdfs:subClassOf` 语义、关系类型没有 domain/range
约束——除非你额外加规则。<strong>Neo4j 的 schema 是「工程约定」，
不是「逻辑公理」</strong>；要逻辑语义，得靠 RDF/OWL 那一路（下一节）。
这是两种存储范式最根本的分水岭。</span>

## 4 公式解析：多跳查询为何快

把「找张三的同事」翻译成图遍历，看 index-free adjacency 如何发威：

```cypher
MATCH (:Person {name: "张三"})-[:WORKS_FOR]->(:Company)<-[:WORKS_FOR]-(colleague:Person)
RETURN colleague.name
```

**第一步**：从张三出发，沿 `:WORKS_FOR` 指针走到谷歌——$O(1)$ 指针跳。
**第二步**：从谷歌出发，反向沿所有 `:WORKS_FOR` 指针找其他员工
  ——只访问「谷歌的入边」，不扫全图。
**总成本**：与「张三的邻居 + 谷歌的员工数」成正比，
  与全图百万/亿节点**无关**。

**逐项拆解这条路径的成本：**

**访问局部性**：每步只碰「路径上」的节点，碰不到图的其他部分。
**无全图扫描**：不查索引、不排序、不 join 全表。
**深度受控**：多跳 = 多次指针跳，成本随「深度」而非「规模」。

**重点：图遍历的复杂度是「路径长度」，关系数据库的 join 是
「表规模」。** 这是「多跳查询」场景上图数据库碾压的数学根源——
你的查询越「图样」（多跳、多模式），图数据库越占优。<span class="marginnote">把复杂度公式
写清楚：一次 $k$ 跳遍历 ≈ $O(k \cdot \bar{d})$（$\bar{d}$ 为平均度），
而关系数据库的 $k$ 次 join ≈ $O(n^k)$（$n$ 为表规模）。<strong>当 $n$ 是
亿级而 $k$ 是 3 时，差距是「毫秒 vs 小时」</strong>。这就是图数据库
存在的全部理由。</span>

## 5 图数据库 vs 关系数据库：一张对照表

| 维度 | 图数据库（Neo4j） | 关系数据库 |
| --- | --- | --- |
| 数据模型 | 节点/关系/属性 | 表/行/列 |
| 关系查询 | 遍历（沿指针） | join（索引/哈希） |
| 多跳成本 | 随深度 | 随表规模 |
| schema | 松散标签 + 约束 | 严格 schema |
| 查询语言 | Cypher（无统一标准） | SQL（全球标准） |
| 擅长 | 关系模式查询 | 聚合、事务、报表 |
| 扩展 | 单机强、分片难 | 成熟分布式 |

**易错点｜「图数据库更快」不是普适真理**：图数据库只在「关系模式
查询」上快；做「全表聚合」（按城市统计人数）图数据库反而不如
SQL。**选型看查询画像**：多跳关系型查询多 → 图库；
聚合报表型查询多 → 关系库。没有「更好的数据库」，
只有「更配的查询」。

## 6 图数据库的适用与边界

**适用场景：**

**风控/反欺诈**：多跳路径检测（洗钱网络、团伙识别）。
**社交网络**：好友推荐、影响力传播（多跳遍历）。
**知识图谱**：企业图谱、数据血缘（依赖链查询）。
**推荐**：用户—物品的多关系路径。

**边界：**

**分片难**：图切到多台机器后，跨片遍历昂贵——图数据库
  大规模水平扩展是公认难题。
**无统一标准**：Cypher、Gremlin、GSQL 三家各说各话。
**无推理语义**：属性图不承诺 OWL 式推理，要靠上层补。

**重点：图数据库是知识图谱的「速度引擎」，不是「语义引擎」。**
它让「沿关系行走」极快，但「行走的含义」要靠你额外的规则/
本体层保证。**工程派图谱的完整形态，通常是「图库存数据 +
规则/本体管语义 + 校验保质量」。**<span class="marginnote">把属性图放回本书坐标系：
它是第四篇「语义网络」的工业直系后裔——节点、弧、沿链行走，
一模一样，只是加上了工程化（索引、事务、查询语言）。语义网络
缺的「语义」，属性图依然缺——那正是 RDF/OWL 那一路要补的。
两种存储范式，实为「工程派 vs 语义派」的知识图谱路线之争。</span>

## 7 小结

- **属性图模型**：节点 + 标签 + 属性，关系 + 类型 + 方向 + 属性。
- 属性图的招牌：**关系也能带属性**——边本身就是数据。
- **index-free adjacency**：节点物理记住邻居，遍历沿指针走，
  成本随深度而非规模。
- 多跳查询复杂度：**图遍历 $O(k \cdot \bar{d})$ vs 关系 join $O(n^k)$**。
- 图数据库强在**关系模式查询**，弱在聚合、分片与标准。
- 选型看查询画像：**多跳关系型 → 图库，聚合报表型 → 关系库**。
- 定位：图数据库是**速度引擎**，语义推理要靠 RDF/OWL 那一路上层补。
