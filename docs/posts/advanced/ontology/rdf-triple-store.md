## 为什么从三元组存储开始

上一节图数据库是「工程派」的存储，这一节看「语义派」的仓库——
**RDF 三元组存储（triple store）**：专门存 RDF 三元组、跑 SPARQL、
支持推理的数据库。如果说属性图把「遍历」做到极致，
三元组存储把「语义」做到原生：IRI 全局寻址、推理机内置、
SPARQL 标准查询。DBpedia、Wikidata 这些开放大图谱，
就跑在 Virtuoso 这类三元组存储上。理解三元组存储，
你就看到了知识图谱「语义派」的存储底座——以及它在性能与
功能间的取舍。

## 1 存储引擎：从三元组表到六路索引

三元组存储的核心是「怎么把亿级三元组存得又快又省」。经典设计：

- **词典编码（dictionary encoding）**：把 IRI/字面量映射成整数 ID，
  存储只碰整数，省空间且比较快。
- **六路索引**：三元组表 `(s, p, o)` 上建 6 种排列索引
  （spo、sop、pso、pos、osp、ops），任何「固定某些列的查询」
  都能走对应索引，避免全表扫描。
- **属性表/垂直分区**：把同一谓词的三元组分到一张表
  （`:拥有宠物(张三, 花花)` 存进 `拥有宠物` 表），
  让「按谓词扫描」变快——Virtuoso 的列式存储即此。

**重点：六路索引的本质是「为所有可能的查询方向预排序」。**
RDF 查询的变量可以出现在任意位置（`?s :p ?o`、`:s ?p ?o`、
`?s ?p :o`），每种形态都有一路索引兜底。**「空间换时间」
的极致：六份索引，换来任何方向的 $O(\log n)$ 定位。**<span class="marginnote">六路索引与
数据库的「复合索引」同理，只是 RDF 的 schema-free 逼它把
所有排列都建上。这份「六路冗余」是三元组存储「什么都能查、
但更新变贵」的根源——写一次三元组要维护六份索引。</span>

## 2 三大代表：Jena、Virtuoso、GraphDB

| 存储 | 出身 | 特点 | 典型角色 |
| --- | --- | --- | --- |
| Apache Jena | 开源（Apache） | Java 全家桶：TDB 存储 + ARQ 查询 + 推理器 | 研究、嵌入式、定制 |
| Virtuoso | OpenLink | 列式、极高性能，SPARQL 端点标准实现 | DBpedia、Wikidata 后端 |
| GraphDB | Ontotext | 企业级，规则推理强，支持 GeoSPARQL | 企业知识图谱、语义搜索 |

- **Jena**：最「学术全能」——存储、查询、推理、规则（Jena Rules）
  全在 Java 生态里，可嵌入可定制。
- **Virtuoso**：最「性能」——DBpedia 和 Wikidata 的官方端点
  都跑它，证明它在亿级开放数据上的吞吐能力。
- **GraphDB**：最「企业推理」——内置强大规则推理，适合
  「图谱 + 推理」型业务。

**重点：三个代表对应三种需求——嵌入定制（Jena）、开放大数据
（Virtuoso）、企业推理（GraphDB）。** 没有「最好」，只有
「你的场景最配哪个」。<span class="marginnote">三个存储的名字常被混提，
但它们性格迥异：Jena 是「工具箱」，Virtuoso 是「引擎」，
GraphDB 是「推理机」。选型时先问自己：我是要嵌入一个库、
托管一个开放端点，还是跑企业级语义推理？</span>

## 3 推理：三元组存储的增值服务

三元组存储区别于普通数据库的杀手锏是**内置推理**：

- **RDFS/OWL 子集推理**：加载时/查询时自动推 `subClassOf`、
  domain/range 的蕴含。
- **规则推理**：GraphDB 的 RDF4J 规则、Jena 的规则引擎——
  用户可写自定义规则（第四篇的产生式思想）。
- **物化（materialization）**：把推理结果预先算好存起来，
  查询直接读「闭包图」；代价是更新时重算。

**重点：推理能力把「查询」升级为「语义查询」。**
在支持推理的存储里，`SELECT ?x WHERE { ?x a :宠物 }` 能返回
所有**被蕴含为宠物**的个体，而不仅是显式声明的。
**「查推出来的知识」是三元组存储对比属性图的根本差异**——这是
「语义派」路线的立身之本。<span class="marginnote">物化与增量推理的权衡
（第五篇提过）在存储层变成实打实的设计决策：全物化快查但慢更新，
运行时推理省更新但慢查。GraphDB 支持两者，Virtuoso 偏物化，
Jena 偏运行时——<strong>「推多少、存多少」是三元组存储的调优主轴</strong>。</span>

## 4 公式解析：一次 SPARQL 查询如何被存储执行

一条 SPARQL 查询在六路索引存储上的执行路径：

```sparql
SELECT ?公司 WHERE { :张三 :就职于 ?公司 . ?公司 a :科技公司 }
```

- **第一步，模式拆分**：查询有两个三元组模式：
  `(:张三, :就职于, ?公司)` 与 `(?公司, rdf:type, :科技公司)`。
- **第二步，索引选择**：第一个模式 `s` 固定，走 `spo` 索引
  （主排序是 s）定位张三的 `就职于` 全部宾语；第二个模式
  `o` 固定，走 `osp` 索引定位所有 `科技公司` 的实例。
- **第三步，连接**：两个中间结果按 `?公司` 做哈希连接，
  输出交集。
- **第四步，返回**：投影出 `?公司`。

**逐项拆解关键点：**

- **索引选择**：每个模式挑「固定列最多的索引」，把扫描范围压最小。
- **连接策略**：存储把图模式当作「小表 join」，用哈希/归并连接。
- **推理介入**：若开了推理，`rdf:type` 的匹配还要并入
  `subClassOf` 推导出的实例。

**重点：SPARQL 执行本质是「索引驱动的多路连接 + 可选推理展开」。**
把 RDF 当「一张大宽表」的朴素实现会很慢；**六路索引 + 连接优化**
才是亿级数据能跑的真相。<span class="marginnote">三元组存储的查询优化器
与关系数据库同源：都是「代价估算 + 连接顺序 + 索引选择」。
区别只在「表」变成了「三元组模式」、「schema」变成了「无」。
学懂数据库执行计划的人，学三元组存储几乎是平移——只是
「表结构」换成了「六路索引」。</span>

## 5 选型与趋势

**选型对照：**

| 维度 | Jena | Virtuoso | GraphDB |
| --- | --- | --- | --- |
| 部署 | 嵌入式/服务器 | 服务器 | 服务器 |
| 性能 | 中 | 高 | 高 |
| 推理 | RDFS + 规则 | RDFS/OWL 子集 | 强规则推理 |
| 扩展 | 单机 | 集群 | 单机/集群 |
| 特色 | 可定制 | 开放数据托管 | 企业语义应用 |

**趋势：混合架构成为主流**——现代知识图谱常「三元组存储管语义层、
属性图管性能层」双库并存，或「RDF 存储 + 物化 + 图数据库」级联。
**「语义派」与「工程派」的分野（下一节正面交锋）正在被
混合架构弥合**：既要 SPARQL 的语义查询，也要 Cypher 的遍历性能。

## 6 小结

- **三元组存储**：为 RDF + SPARQL + 推理而生的数据库。
- 引擎核心：**词典编码 + 六路索引**，任何查询方向都有索引兜底。
- 三大代表：**Jena（嵌入式工具箱）、Virtuoso（开放大数据引擎）、
  GraphDB（企业推理机）**。
- 杀手锏是**内置推理**：查「推出来的知识」，把查询升级为语义查询。
- 执行本质：**索引驱动的多路连接 + 推理展开**。
- 选型看**部署、性能、推理、扩展**四维。
- 趋势：**混合架构**——三元组管语义、属性图管性能，双库级联。
