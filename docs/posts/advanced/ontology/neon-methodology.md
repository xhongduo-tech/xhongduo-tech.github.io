# NeOn 方法论：场景驱动的本体网络开发

<div class="epigraph">

## 为什么从 NeOn 开始

METHONTOLOGY 是「从零建一个本体」的瀑布；但 2010 年代的现实是：
**本体的世界早就不是单个文件，而是互相引用、共同演化的本体网络**
（医学本体链、跨领域本体的映射、复用上层本体的项目群）。
NeOn 方法论直面这个现实，做出两项关键革新：**以「本体网络」为
开发单位**，以及用**九个可组合场景**取代「固定流程」。
理解 NeOn，你就从「建本体」升级到「建设本体的生态」——
这是从单体到微服务在知识表示领域的翻版。

## 1 本体网络：开发单位变了

**本体网络（ontology network）**：一组本体及其之间的映射关系构成的
结构——本体间通过 `owl:imports`（模块引用）、等价映射、对齐关系彼此相连。

在 NeOn 的视野里，你要开发的不是一个本体，而是一个**网络**：

- 顶层是**上层本体**（BFO、DOLCE、SUMO），提供共享概念；
- 中间是**领域本体**（医学、金融），提供领域概念；
- 底层是**应用本体**，面向具体任务；
- 各层之间通过**映射**连接，形成一个互相约束的网。

**重点：网络思维改变了一个根本问题——「从零建」变成「接入」。**
新项目不再是「造一个新本体」，而是「在既有网络里定位自己」：
imports 哪些、对齐哪些、复用哪些。**本体的价值，越来越多地
取决于它「连上了谁」而非「装了什么」。**<span class="marginnote">网络思维与
第七篇「上层本体的意义」直接呼应：上层本体之所以重要，正因为
它是网络里的「公共协议」——两个领域本体都 import 同一个上层本体，
它们就有了对齐的共同底座。没有网络，就没有「共享顶层」的必要。</span>

## 2 九个场景：按需组合而非固定流程

NeOn 最著名的产出是**九个开发场景（scenarios）**——每种场景描述
一类常见的「起点与目标」组合，方法论不再规定「必须走哪几步」，
而是让你**从九个场景里挑选、组合**你的开发路径：

| 场景 | 起点 → 目标 | 何时用 |
| --- | --- | --- |
| 1 | 规格 → 实现 | 全新领域、无复用 |
| 2 | 非本体资源 → 本体 | 从数据库/文本/词典建本体 |
| 3 | 复用本体资源 | 复用设计模式、模块 |
| 4 | 复用并重构本体资源 | 复用旧本体并改造 |
| 5 | 复用并合并 | 合并多个既有本体 |
| 6 | 复用、重构、合并 | 复杂重组 |
| 7 | 复用本体设计模式 | 用 ODP 加速建模 |
| 8 | 重构 | 重排既有本体结构 |
| 9 | 本地化 | 翻译/适配到新语言文化 |

**重点：场景是可组合的积木。** 一个真实项目可能同时用场景 2（从数据库
建）、场景 7（用设计模式）与场景 5（合并两个旧本体）。**NeOn
不告诉你「怎么做」，它给你「九种常见做法」让你自选**——这是
方法论从「规定」走向「服务」的关键一步。<span class="marginnote">九个场景的
哲学：承认「现实没有标准起点」。不同团队、不同资源、不同遗产，
起点千差万别。方法论的价值不是「标准流程」，而是「把已知路径
分类、并说明每种路径的注意事项」——这更像「路书」而非「铁轨」。</span>

## 3 复用为中心：NeOn 的核心立场

NeOn 把**复用**从「加分项」升格为「默认项」。它复用的对象分三类：

**本体资源**：完整本体、本体模块、本体设计模式（ODP）。
**非本体资源（NORs）**：数据库 schema、术语表、分类法、词典——
  通过「再工程（re-engineering）」转换成本体。
**知识内容**：既有的注释、映射、版本。

**重点：NeOn 的「复用」不是「拷过来」，而是「再工程」。**
场景 2 的精华是把「关系数据库 schema」改造成本体——不是自动翻译，
而是**人工判断哪些表该变类、哪些列该变属性、哪些约束该变公理**。
再工程是「有意识的转化」，比「从零」快，但比「照抄」稳。<span class="marginnote">NeOn 的
复用立场与第九篇 LLM 时代有奇妙的呼应：LLM 自动抽取生成的本体草稿
（第八、九篇），本质上就是「非本体资源（文本）→ 本体的再工程」——
只是执行者从人换成了模型。NeOn 为「再工程」积累的方法，恰好是
LLM 驱动建本体最需要的框架。</span>

## 4 配套方法：从规格到演化的工具箱

NeOn 不只给场景，还给**每个生命周期阶段配套了方法**：

**规格**：能力问题 + 本体网络的需求说明（描述网络层级与依赖）。
**概念化**：术语表、概念图、模块划分。
**形式化/实现**：选择语言与工具，建立网络映射。
**评估**：对照 CQ，加上**网络一致性**检查（映射是否冲突）。
**演化**：版本管理、变更传播（改一个本体如何影响网络里其他本体）。
**协作**：多人分布式开发（NeOn 支持多组织共建本体网络）。

**重点：网络带来的新任务是「映射管理」与「变更传播」。**
单本体没有「映射」这回事；本体网络里，一个类的定义变了，
引用它的所有映射都要重审。**NeOn 把「网络级的一致性」当成
一等公民**——这是它超越单本体方法论的最大新增量。<span class="marginnote">「变更传播」的
复杂度在 LLM 时代被放大：自动生成的本体持续在变，手工维护映射
跟不上。这就是为什么现代图谱用「对齐服务 + 校验管道」来管理映射
（第八篇），以及为什么「schema 约束生成」（第九篇）要强制
LLM 输出服从网络约束——NeOn 早就划出了这些任务的形状。</span>

## 5 批判与遗产

NeOn 的批评者指出：**九个场景 + 全套方法仍是「重量级」**——
小团队、快迭代的现实里，很少有人能完整执行。但它留下了
三个影响深远的遗产：

**本体网络**取代「单个本体」成为开发单位——改变了整个领域的问题表述。
**场景驱动**取代「固定流程」——方法论走向「按需组装」。
**复用/再工程**成为默认姿势——「从零建本体」被视为反模式。

**重点：NeOn 的最大贡献是「重新定义了问题」——从「如何建一个
本体」变成「如何在既有本体生态里定位、复用与演化」。**
这个视角转移，比它的任何具体方法都重要。<span class="marginnote">软件工程史的对照很清晰：
METHONTOLOGY 是「瀑布」，NeOn 是「微服务 + 治理」——它承认系统
是模块网络，承认复用是默认，承认演化和治理是长期主旋律。
第九篇「知识图谱 × 大模型」里「图谱作为 Agent 记忆」的架构，
本质就是 NeOn 式本体网络在 Agent 时代的重演。</span>

## 6 小结

- NeOn 以**本体网络**为开发单位——本体是互相映射、共同演化的网。
- **九个场景**是「可组合的积木」，取代固定瀑布流程。
- **复用/再工程**是默认立场：本体资源、非本体资源（数据库、文本）、
  设计模式都是复用对象。
- 新增能力：**映射管理与变更传播**——网络级一致性的维护。
- 生命周期配套方法：规格（网络化 CQ）、概念化、形式化、评估、演化、协作。
- 批判：**重量级**；遗产：**网络思维、场景驱动、复用优先**。
- 现代回响：LLM 生成本体 = 文本再工程；Agent 记忆图谱 = 本体网络重演。

可复用的建模方案如何让「造本体」从手工作坊走向组件化。
