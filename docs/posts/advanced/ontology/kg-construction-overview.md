# 知识图谱构建总览：自顶向下与自底向上

<div class="epigraph">
<p>建知识图谱只有两条路：先定 schema 再填数据，或先有数据再归纳 schema——以及最重要的，第三条路：两者交替进行。</p>
<footer>—— 海克·保尔海姆（Heiko Paulheim），《知识图谱反思》(2017)</footer>
</div>

<div class="article-byline">
<p>第四级 · 本体论 ｜ Hogan et al.《知识图谱》(ACM Computing Surveys, 2021)；Paulheim《知识图谱反思》(2017) ｜ 2026-08-07</p>

## 为什么从构建总览开始

上一节我们搞清了知识图谱「从哪里来」，这一节回答「怎么建起来」。
知识图谱构建有两个经典策略，像软件工程里的「自顶向下设计」与
「自底向上生长」：**自顶向下**先定义 schema（本体）再填实例，
**自底向上**先抽取事实再归纳 schema。理解这两条路线及其融合，
你就拿到了知识图谱工程的「总指挥图」——后面每一节（实体抽取、
关系抽取、知识融合、存储）都是这张总图上的一个工序。

## 1 自顶向下：先 schema，后数据

**自顶向下（top-down）**：先由专家设计本体（类、属性、约束），
再向其中填充实例数据。Freebase 早期的众包编辑、企业内部的
「主数据管理」多走这条路。

**优点：**

- **质量可控**：schema 严谨，数据必须符合约束。
- **一致性高**：同类实体共享同一套属性定义。
- **可推理**：schema 即 TBox，可直接跑 OWL 推理。

**缺点：**

- **扩展慢**：新领域要先设计 schema，跟不上数据增长。
- **成本高**：专家设计 schema 昂贵，瓶颈在「人」。
- **覆盖有限**：schema 没定义的概念，数据进不来。

**重点：自顶向下是「设计驱动」**——它把「先想清楚世界长什么样」
当成前置条件。这与第七篇的 METHONTOLOGY 一脉相承，
是本体工程传统在知识图谱里的延续。<span class="marginnote">自顶向下的哲学对应
「柏拉图式的建模」：先有理念（schema），再有具体事物（实例）。
它的风险也像柏拉图——理念若不能涵盖现实，现实就被拒之门外
（数据进不来）。「schema 先行」既是它的纪律，也是它的天花板。</span>

## 2 自底向上：先数据，后 schema

**自底向上（bottom-up）**：先从文本、网页、数据库抽取大量事实，
再通过统计与归纳形成/修正 schema。DBpedia、以及今天大部分
LLM 驱动的知识抽取，走这条路。

**优点：**

**扩展快**：跟着数据走，爬多快建多快。
**覆盖广**：schema 从数据里长出来，不会被预设框死。
**成本低**：自动抽取为主，人力做后校验。

**缺点：**

**噪声大**：抽取错误、不一致、重复实体层出不穷。
**schema 松散**：归纳出的类与属性往往粗糙、互相冲突。
**难推理**：数据驱动 schema 常缺严谨公理，推理价值打折。

**重点：自底向上是「数据驱动」**——它把「先有数据，再想结构」
当成默认姿势。DBpedia 的 schema 是从维基百科的信息框模板
「涌现」出来的，而不是先设计的。<span class="marginnote">自底向上的哲学对应
「经验主义」：知识从观察（数据）中来，结构是归纳的产物。
它的风险也像经验主义——归纳出的规律可能以偏概全。
「让 schema 从数据里长出来」的代价，是 schema 的「不纯」。</span>

## 3 混合路线：schema 与数据共同演化

现实中极少纯用一条路线。主流是**混合**：

**粗 schema 先行**：先定一个粗粒度的核心 schema（人、地点、组织），
  保证最基本的骨架。
**数据驱动扩展**：新实体与关系进来，暴露 schema 缺口，再补 schema。
**schema 与数据交替演化**：schema 约束数据、数据反哺 schema，
  形成迭代循环。

**重点：混合路线的关键是「schema 的粗粒度起步」**——不要一开始就
追求完美的 TBox，先用「够用」的骨架让数据流进来，再随数据
不断精化。**这与第七篇的「能力问题驱动 + 迭代开发」完全同构**：
schema 是活的，不是一次定死的。<span class="marginnote">混合路线的工程形态，
正是「本体（schema 层）与图谱（数据层）分而治之」：schema 层
慢变、严格、可推理；数据层快变、宽容、海量。第六篇 SHACL 的
「校验 + 推理双引擎」、第八篇「物化 + 规则」架构，都是这套
分层的具体实现。</span>

## 4 构建流水线：一张总指挥图

无论哪条路线，知识图谱构建都跑在一条流水线上：

| 工序 | 任务 | 对应章节 |
| --- | --- | --- |
| 数据接入 | 收集网页、文本、数据库 | — |
| 实体抽取 | 识别命名实体（NER） | 下一节 |
| 关系抽取 | 提取实体间关系 | 下下节 |
| 指代消解 | 把「他」「谷歌」指到同一实体 | 融合 |
| 实体对齐 | 跨源合并同一实体 | 知识融合 |
| 知识融合 | 冲突消解、去重 | 知识融合 |
| 校验 | 一致性检查、约束验证 | SHACL/推理机 |
| 存储 | 图数据库 / 三元组存储 | 存储两节 |

**重点：流水线是「循环」不是「直线」。** 校验阶段发现的问题
会倒流回抽取与融合——低质量的抽取产出低质量的图，
质量必须在每一道工序设闸。**「构建」是一个持续运行的管道，
不是一次性工程**：新数据不断进来，旧数据不断修订。<span class="marginnote">把流水线
与第四篇的「识别—行动循环」对照：知识图谱构建本质是一个
<strong>大规模的信息处理管道</strong>——每一道工序都是「从原始数据到结构知识」
的一步压缩。理解流水线，你就知道每个「坑」（抽取噪声、对齐失误）
出在哪一段，也就能按图索骥去堵。</span>

## 5 构建的挑战与 LLM 时代的转向

知识图谱构建的永恒挑战：

**质量 vs 覆盖**：抽得全就噪声多，抽得准就覆盖少。
**schema 的刚性**：预设 schema 框不住新数据。
**新鲜度**：数据在变，图谱要持续更新。
**人工瓶颈**：纯人工校验不可扩展，纯自动又不可信。

**LLM 时代的转向**（第九篇详述）：

LLM 让「文本 → 实体/关系」的抽取质量大幅跃升，
  「自底向上」变得空前可行。
「schema 约束的生成」把「自顶向下」的纪律重新引入——
  用 schema 约束 LLM 输出，兼顾两派优点。
知识图谱与 LLM 形成**双向增强**：图谱锚定 LLM 的事实，
  LLM 反哺图谱的构建与更新。

**重点：LLM 没有终结「自顶向下 vs 自底向上」之争，而是把
「混合」推到了新高度**——schema 约束生成 = 顶向下，
自由抽取 = 底向上，两者的张力变成「生成 + 校验」的工程闭环。<span class="marginnote">一个
冷静的提醒：LLM 让构建更快，也让「垃圾进垃圾出」更隐蔽——
模型生成的错误关系很难被肉眼发现。<strong>LLM 时代的构建，校验环节
比抽取环节更关键</strong>：第五篇的 OWA、第六篇的 SHACL、第七篇的
推理机，在 LLM 管道里全部重新上岗。</span>

## 6 小结

- 两条路线：**自顶向下**（先 schema 后数据）与**自底向上**（先数据后 schema）。
- 自顶向下：**质量高、扩展慢、成本高**——设计驱动。
- 自底向上：**扩展快、噪声大、schema 松**——数据驱动。
- 主流是**混合路线**：粗 schema 起步，schema 与数据共同演化。
- 构建流水线：**接入 → 实体抽取 → 关系抽取 → 消解 → 融合 → 校验 → 存储**。
- 流水线是**循环**：质量必须在每道工序设闸。
- LLM 时代：**「生成 + 校验」闭环**让混合路线空前强大，校验更关键。
