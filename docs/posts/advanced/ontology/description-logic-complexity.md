## 为什么从复杂度开始

前面几节我们说「SROIQ 最坏情况指数级」——但到底「指数」到哪一档？
这一节把账算清。描述逻辑的复杂度研究，回答一个工程生死问题：
**我选的语言，在最坏情况下要花多少时间才能判一个「可满足」？**
答案从 EL 的多项式时间（PTIME）一路爬到 SROIQ 的双指数（N2EXPTIME）——
七个数量级的差距，决定了医学本体敢用 EL、而完整 OWL 2 推理机
只能在小规模本体上逞强。理解这张复杂度地图，你选语言时
就不再是「凭感觉」，而是「看预算」。

## 1 复杂度类速览：五个档位

先给不熟悉计算复杂度理论的读者一张快速地图（详见第二级
《计算复杂性理论》）：

| 复杂度类 | 直觉含义 | 类比 |
| --- | --- | --- |
| PTIME | 多项式时间 | 快：数据翻倍，时间翻几倍 |
| PSPACE | 多项式空间 | 时间可指数，但空间省 |
| EXPTIME | 指数时间 | 慢：数据翻倍，时间指数涨 |
| NEXPTIME | 非确定指数时间 | 更慢（且难证下界） |
| N2EXPTIME | 双重指数时间 | 最慢：$2^{2^n}$ 级 |

**重点：复杂度类说的是「最坏情况」**——它给出「无论输入多刁钻，
算法都必须在这个时间/空间内完成」的保证。日常数据也许跑得快，
但**复杂度上界决定你能否放心地声明「一定会停」**。DL 可判定的
「含金量」，正体现在它能给出精确的最坏情况界。

## 2 DL 家族的复杂度地图

不同语言的「可满足性判定」复杂度如下（这是 DL 学界几十年的核心成果）：

| 语言 | 关键特性 | 可满足性复杂度 |
| --- | --- | --- |
| EL | 无否定、无全称 | PTIME-complete |
| ALC（空 ABox） | 有否定 | PSPACE-complete |
| ALC（含一般 TBox） | 加 GCI | EXPTIME-complete |
| SHOIN（OWL DL） | 传递+逆+名义+数限制 | NEXPTIME-complete |
| SROIQ（OWL 2 DL） | 全部 + 角色链 | N2EXPTIME-complete |

**重点：每加一类构造子，复杂度跳一档。** EL 加否定 → 从 PTIME 跳到 PSPACE；
加一般包含公理 → 跳到 EXPTIME；加名义与数限制 → 跳到 NEXPTIME；
再加角色链 → 双指数。**这条阶梯不是巧合，而是表达力的「定价表」**——
你能表达「恰好有两个女儿」（Q）或「指着花花」（O），就要为这份能力
付复杂度的账。<span class="marginnote">注意一个微妙的点：ALC 空 ABox 是 PSPACE，
但<strong>不是</strong> EXPTIME——因为此时模型可以很小（「树模型性质」：若可满足，
必有大小以概念规模为指数的树模型，且可用多项式空间逐枝搜索）。
加了 GCI 之后模型可能指数大，才升到 EXPTIME。复杂度研究经常给出
这种「没想到」的精确边界。</span>

## 3 公式解析：为什么 ALC 能「省空间」

一个反直觉的事实是：ALC 的可满足性虽可能需指数时间，却只需**多项式空间**。
秘密在 Tableau 的**树模型性质（tree model property）**：

- 若概念 $C$ 可满足，必存在一个**树形**模型，其大小以 $|C|$ 为底的指数为界；
- Tableau 的搜索可以**深度优先**：不需要把整棵树都存在内存里，
  只需记住当前分支的路径；
- 于是空间只随「树的深度」线性增长——深度由概念规模限制，多项式即可。

**逐项拆解这条推理链：**

- **树模型性质**：把「存在模型」限制成「存在树模型」——可满足性不变。
- **深度优先**：一次只探索一个分支，空间 = 路径长度。
- **路径长度有界**：由概念结构决定的有限深度，多项式空间装得下。

**重点：复杂度分析不是理论游戏，它直接刻画了 Tableau 在 ALC 上
能跑得多省。** 这也是为什么早期 DL 推理机在「中等规模」本体上
就能大显身手——它们跑的是 PSPACE 级的 ALC，而不是 N2EXPTIME 级的 SROIQ。<span class="marginnote">「树模型性质」是
模态逻辑与描述逻辑共享的深层结构：它来自「沿角色边走一步」的受限语法。
这个性质让 DL 与「图性质不可判定的逻辑」（如完整的一阶逻辑）
划清界线——你会在第三篇模态逻辑那里再见到它。</span>

## 4 复杂度如何指导工程：OWL 2 Profiles 的诞生

复杂度研究最直接的工程产物，是 **OWL 2 Profiles**——三个牺牲表达力、
换低复杂度的子语言：

| Profile | 设计目标 | 复杂度 | 典型场景 |
| --- | --- | --- | --- |
| OWL 2 EL | 大规模分类 | PTIME | 医学本体（SNOMED CT） |
| OWL 2 QL | 与数据库集成 | PTIME（可归约为 SQL） | 数据访问层 |
| OWL 2 RL | 规则式推理 | PTIME（可归约为 Datalog） | 图数据库推理 |

**重点：三个 Profiles 都把推理压到 PTIME，靠的是「只保留能高效处理的构子」**
——EL 去掉否定，QL 限定为「查询视图」，RL 限定为「规则闭包」。
它们的共同哲学是：**与其追求「什么都能表达」，不如承诺「常用场景
永远跑得动」**。医学本体几百万个概念，若不是 EL 的多项式分类，
SROIQ 的双指数最坏情况会让推理机直接失守。<span class="marginnote">这张表是第七篇
「本体工程」里「选型」一节的伏笔：真正的本体项目从不上来就用
OWL 2 Full，而是先问「我的推理任务是分类、查询还是规则闭包」，
再选 EL、QL 还是 RL。复杂度地图，就是选型的地图。</span>

**易错点｜「更简单的语言 = 更弱」不全对**：EL 虽然不能表达否定，
却能表达医学分类几乎全部需要的「子类 + 存在限制 + 角色层级」。
对「SNOMED 这类本体」，EL 不是「降级」，而是「刚好够用且跑得动」。
**选语言的关键不是「最强」，而是「你的问题需要什么表达力、能容忍什么复杂度」。**

## 5 小结

- 复杂度类地图：**PTIME → PSPACE → EXPTIME → NEXPTIME → N2EXPTIME**。
- EL 是 PTIME，ALC（空 ABox）是 PSPACE，ALC（含 GCI）是 EXPTIME，
  SHOIN 是 NEXPTIME，SROIQ 是 N2EXPTIME。
- **每加一类构造子，复杂度跳一档**——表达力按复杂度定价。
- **树模型性质 + 深度优先**解释 ALC 为何「时间可能指数、空间仍多项式」。
- **OWL 2 Profiles**（EL/QL/RL）把复杂度压到 PTIME，靠牺牲部分表达力。
- 复杂度研究直接指导**语言选型**：先定推理任务，再选语言。
- 工程铁律：**不选「最强」，选「够用且跑得动」**。
