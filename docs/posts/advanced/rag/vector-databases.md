## 为什么从向量数据库开始

前 10 篇把「向量从哪来」讲完了，剩下的问题是「向量放哪里、怎么被查」。理论上，把向量存进内存、写个暴力扫描循环也能跑——但生产系统还需要**持久化、动态增删、元数据过滤、并发查询、扩缩容与高可用**。这些是一个「数据库」的职责，而不是一个「相似度算法」的职责。向量数据库（vector database）把这套职责与第 2 篇的 ANN 算法打包成产品。这一篇以 FAISS（Facebook AI Research, 2017）为算法内核的起点，再讲 Milvus / Pinecone 等系统如何在 FAISS 之上做工程化，并拆开乘积量化（PQ）的数学。

## 1 从 FAISS 到向量数据库：差在哪一层

**FAISS**（Facebook AI Similarity Search）是一个高性能相似度搜索**库**：提供索引数据结构与 GPU 加速，解决「给定查询向量，快速返回 Top-k」。<span class="marginnote">关键认知：FAISS 不是数据库。它不保证持久化、不管理事务、不处理故障恢复——索引在内存里，进程一退出就没了。RAG 论文与多数实验用 FAISS 就够了，但生产系统通常需要包一层「数据库」能力。</span>

向量数据库在 FAISS 这类内核之上补齐了四件事：**写入落盘与持久化、向量与元数据的联合查询（如「在 2024 年之后发布的文档里查」）、并发与高可用、水平扩展**。这正是数据库领域经典的「内核算法 vs 系统能力」分工。

## 2 索引家族：Flat / IVF / HNSW / PQ

FAISS 的索引名就像「菜谱」，按精度与速度排序：

**IndexFlatIP / IndexFlatL2**：暴力精确扫描，内存换精度，小数据、追求参照时用。
- **IndexIVFFlat**：先 k-means 聚类成倒排列表，查询只进最近的几个簇（nprobe 控制），换取数量级提速、召回略降。
- **IndexHNSW**：第 2 篇的多层小世界图，搜索路径 $\sim O(\log N)$，是现代高并发默认；代价是内存占用大（图结构本身要存）。
- **IndexIVFPQ**：IVF + 乘积量化，把向量压成短码，换取**10–100 倍内存节省**，代价是量化误差。<span class="marginnote">选索引本质是选「精度—速度—内存」的三角折点：Flat 三费其一（快/准/省内存只能选两样），IVFPQ 用压缩换省内存，HNSW 用图换快——所有向量数据库的配置界面，都是这三角的滑杆。</span>

FAISS 还支持 **GPU** 并行：把批量查询分到多块 GPU 上，是「亿级向量 + 毫秒级响应」的关键武器。

**一个「索引怎么配」的经验**：小数据（百万级以内）用 IndexFlat 最稳，精确无误差；中等规模用 HNSW 默认参数；超大规模（亿级）才轮到 IVFPQ——先用 HNSW 顶着，等内存吃紧再切 PQ。配索引的起点是「先测出内存上限」，再反推用哪种折点，而不是直接上最花哨的。

## 3 产品化的系统：Milvus / Pinecone 等

围绕 FAISS 思想，产品化向量数据库分两大阵营：

**开源可自托管**：Milvus（架构分「查询、索引、存储」三层，支持标量过滤与向量检索混合查询）、Qdrant、Weaviate、Chroma——适合数据主权与可控成本。
- **托管云服务**：Pinecone 等——免运维、开箱即用、按量计费，适合快速验证与无运维团队场景。<span class="marginnote">选「自建 FAISS」还是「向量数据库」，判断标准不是数据量，而是<strong>非检索需求</strong>：要不要元数据过滤、要不要多租户、要不要跨地域容灾。这些系统能力才是「数据库」三个字的含义所在。</span>

现代向量数据库的标配能力已经超出「查相似」：**元数据过滤（预过滤 / 后过滤）、混合检索（向量 + 稀疏/BM25，见第 14 篇）、批量写入、动态 schema**。

**一个「开源 vs 托管」的决策例子**：数据量千万级、且需要多租户隔离与自定义过滤逻辑，选自托管 Milvus / Qdrant，能完全掌控索引参数与扩缩容节奏；数据量小、团队无运维人力、希望一周内上线，选 Pinecone 类托管服务，把「调索引」的精力省下来留给业务。判断基准不是「谁更先进」，而是「你愿意为哪种能力付维护成本」。

## 4 公式解析：乘积量化 PQ 的内存魔法

PQ 让「把 $10^9$ 个 768 维向量塞进内存」成为可能。核心是把向量**切碎后用码本压缩**：

$$
p = [p^{(1)}, p^{(2)}, \ldots, p^{(m)}], \qquad \hat{p} = [c_{1}(p^{(1)}), c_{2}(p^{(2)}), \ldots, c_{m}(p^{(m)})]
$$

- **第一步，切子向量**：把 768 维向量均分成 $m$ 段（如 $m=96$），每段 8 维。
- **第二步，逐段建码本**：对每一段的所有取值做 k-means 聚类（如 256 个质心），得到 $m$ 个码本。
- **第三步，量化表示**：每一段用「离它最近的质心编号」表示，一个 8 维浮点子向量被压成一个 8 bit 的码。整向量从 768×4 字节 ≈ 3 KB 压到 $96 \times 1$ 字节 = 96 B，**压缩约 30 倍**。<span class="marginnote">这就是「乘积」二字的来源：把高维向量拆成若干低维子空间，每个子空间独立量化，复杂度从「码本大小随维度指数爆炸」降到「按段线性增长」。数学上是近似，工程上是数量级的存储红利。</span>
**第四步，近似距离**：查询时把查询也切段，与每段的码本质心查表算距离，求和即近似距离。精度损失可控，换来内存与带宽的大幅下降。

**把 PQ 的压缩账再算细一点**：以 1000 万向量、768 维为例，float32 原始存储约 30 GB；PQ 到 96 B/向量后约 0.96 GB，内存占用缩到 3% 量级。检索时的距离计算也从「768 次浮点乘加」变成「96 次查表 + 加法」——时间与空间同时省，这就是 PQ 作为「大索引标配」的原因。

## 5 选型权衡与正确姿势

向量数据库选型，最实用的一张决策表：

| 场景 | 推荐 | 理由 |
| --- | --- | --- |
| 实验 / 原型 | FAISS + 内存 | 零运维、最快跑通 |
| 中等规模、要过滤 | Milvus / Qdrant | 向量 + 元数据联合查询 |
| 云上托管、免运维 | Pinecone | 按量付费、自动扩缩容 |
| 亿级 + GPU | FAISS-GPU / Milvus GPU | 并行查询吞吐 |
| 高并发 / 生产级 | Milvus / Qdrant 或托管 | 副本、读写分离、故障转移 |

**辨析｜易错点：** 向量数据库之间「谁更快」的对比很容易被营销带偏——同一套 HNSW 参数下性能差距往往很小，真正的差异在**过滤语义、一致性保证与运维复杂度**。先想清楚「要查什么样的数据」，再选系统。<span class="marginnote">与第三级《数据库系统》的呼应：向量数据库不是来「替代」传统数据库的，而是补上「非结构化数据的相似性查询」这一格；事务、严格一致性仍由传统数据库承担。</span>

## 6 写入、过滤与一致性：数据库的三道基本功

「相似度算法」与「数据库」的分水岭，藏在三个容易忽略的环节里：

**写入路径**：向量数据库要把「新增段落 → 嵌入 → 落盘 → 入索引」做成原子操作。增量写入若与已有索引冲突（如 HNSW 图结构被频繁改动），可能引入索引碎片、拉低检索质量；生产上常见「写新索引 + 双写 + 切换」的滚动更新策略。<span class="marginnote">对比 FAISS：它是纯内存库，向量一次性装载、查询极快，但「动态增删」不是它的本职。要不要包一层数据库能力，第一条判断线就是「你的向量会变吗」。</span>
- **过滤**：现代系统普遍支持「标量过滤 + 向量检索」联合查询。过滤有两种执行策略：预过滤（先按标签缩候选，再算向量相似度）与后过滤（先检索再剔除不符标签的）。前者快但可能漏掉「标签未命中但内容相关」的段落，后者全但慢——与第 14 篇混合检索的「先粗滤再细滤」同源。
- **一致性**：向量索引的更新不是即时生效的——删除一条向量，HNSW 图里可能还留着它的边。数据库要在「读到旧数据」与「付出重排代价」之间给出一致性承诺（最终一致是常见默认）。
- **并发与高可用**：生产环境常有多个查询并发涌入，向量库要用读写分离、副本与故障转移保证不丢查询。小团队的第一道门槛往往不是算法，而是「上线后扛不扛得住并发」——这也是自托管与托管的又一个分岔点。

三道基本功做完，才配叫「数据库」；缺了它们，就是「一个带 ANN 的键值存储」。

## 7 术语速查表：向量库工程关键词

| 术语 | 英文 | 一句话定义 |
| --- | --- | --- |
| 相似度搜索库 | similarity search library | 只负责「查相似」的算法库（如 FAISS） |
| 向量数据库 | vector database | 封装持久化、过滤、并发等能力的系统 |
| 倒排文件 | IVF | 用聚类建倒排表加速检索 |
| 乘积量化 | PQ | 切段 + 码本压缩向量 |
| 图索引 | HNSW | 多层小世界图，$O(\log N)$ 搜索 |
| 元数据过滤 | metadata filtering | 用标签约束候选集 |
| 预过滤 / 后过滤 | pre/post filtering | 过滤发生在检索前 / 后 |
| 最终一致 | eventual consistency | 允许短暂读到旧数据的折中 |
| 滚动更新 | rolling update | 写新索引 + 双写 + 切换的无损升级 |
| 高可用 | high availability | 用副本与故障转移保证服务不中断 |

这张表把第 2 篇的 ANN 算法（LSH / IVF / HNSW）与本节的产品化能力（持久化、过滤、一致性）对齐：算法负责「快」，系统负责「稳」。二者缺一不可——只有算法没有系统，向量只能在内存里活一瞬；只有系统没有算法，亿级检索就慢到没法用。

## 8 小结

- **FAISS 是库不是数据库**：只负责「查相似」，持久化、过滤、并发、扩缩容要由向量数据库补上。
- 索引家族是「**精度—速度—内存**」三角的滑杆：Flat（精确）、IVF（聚类加速）、HNSW（图加速）、IVFPQ（量化省内存）。
- **乘积量化**把向量切段、逐段用码本压缩，约 30 倍内存节省，代价是可控的量化误差。
- 选型看场景：**实验用 FAISS，要过滤用 Milvus/Qdrant，要托管用 Pinecone**；真正的差异在系统能力而非算法速度。
- 数据库三道基本功：**写入路径、标量过滤（预过滤 / 后过滤）、一致性**；缺了它们就只是「带 ANN 的键值存储」。
- PQ 压缩账：**1000 万向量、768 维从约 30 GB 压到约 0.96 GB**，距离计算同步减到 96 次查表加加法。
- 并发与高可用是生产门槛：**读写分离、副本、故障转移**，也是自托管与托管的又一分岔。
- 标配能力在扩展：**动态 schema、批量写入、混合检索**——向量数据库正从「专用索引」走向「通用数据平台」。
- 算法与系统互补：**算法负责「快」，系统负责「稳」**，缺了任何一边向量库都立不起来。

到这里，向量从「选模型」（第 10 篇）到「放哪、怎么查」（本篇）的存储链路完整了：算法负责快，系统负责稳。在下一节，我们把目光从「怎么存」转回「怎么用」：检索结果拿到手之后，生成器怎么把多路证据融合进答案？——这就是**生成融合与 RAG-Fusion**。
