## 为什么「窗口长」不等于「会用长窗口」

2023 年起，模型的上下文窗口被一路拉长：4k、32k、128k、甚至百万 token。直觉上「窗口越长越强」，但评测立刻戳破了这个幻觉：**窗口只定义了「能塞进多少」，没有定义「塞进去之后能不能用」**。模型可能在短上下文中检索精准，一旦塞进十万 token，就彻底「迷失」在信息的汪洋里。长上下文评测，就是专门度量「长到能装下之后，模型还剩多少真本事」的尺子。

本篇聚焦两件代表工具：**LongBench**（Bai 等人，2023）——系统化测「长上下文里的任务能力」；**NEEDLE**（Li 等人，2024）——用极端压力测试暴露「检索的死角」。<span class="marginnote">Bai, Y. 等，「LongBench: A Bilingual, Multitask Benchmark for Long Context Understanding」，2023；Li, M. 等，「NEEdle in a Haystack: Single Needle In A Haystack」，2024。前者问「长文任务做得好不好」，后者问「长文里的信息找不找得到」。</span>

## 1 LongBench：把长上下文拆成六类任务

LongBench 是第一套**中英双语**的长上下文基准，包含 **21 个数据集、6 类任务**：

| 任务类别 | 例子 | 判分 |
| --- | --- | --- |
| 单文档问答 | 对一篇长文提问 | F1 |
| 多文档问答 | 横跨多篇文档找答案 | F1 |
| 摘要 | 压缩一篇长文 | ROUGE |
| 少样本学习 | 从长示例里学格式 | 任务自定义 |
| 代码补全 | 补全长代码库中的函数 | 精确匹配 |
| 合成任务 | 在长序列里定位信息 | 精确匹配 |

平均上下文长度 5k–15k token，个别任务可达 60k+。评测协议强调**逐任务报告**——因为不同任务对「长上下文能力」的要求截然不同：多文档问答考「跨文档整合」，合成任务考「定位」，摘要考「去冗存精」。

LongBench 的早期结论令人清醒：**几乎所有模型在更长上下文上成绩下滑**，且下滑幅度因任务而异——检索类任务最脆，摘要相对坚挺。<span class="marginnote">「越慢越长越差」颠覆了「窗口越长越强」的直觉，也解释了为什么厂商广告里「支持 128k」与用户实测「只记得开头和结尾」的落差如此之大——支持窗口与利用窗口是两码事。</span>

## 2 NEEDLE：一根针埋进干草垛

LongBench 测「任务做得好不好」，NEEDLE 则把问题逼到最极端：**在超长上下文的某个位置埋一根「针」——一句独一无二的关键事实——然后问模型一个只有这根针能回答的问题**。针被埋在「不同深度」（相对位置）、上下文被拉到「不同长度」，于是得到一张「干草垛网格」（haystack grid）：

![NEEDLE 干草垛网格](/images/llm-evaluation/needle-haystack.svg)

每个格子的颜色表示「这个长度 × 这个深度下，模型能否检索出那根针」。一张理想的网格应该全是浅色；而真实的网格往往在**中间地带出现一条深色带**——**模型记得开头、记得结尾，却唯独记不住中间**。这就是著名的**「迷失在中间（lost in the middle）」**现象：长上下文里，信息被放在开头或结尾时检索成功率显著高于中间位置。<span class="marginnote">「迷失在中间」由 Liu 等人 2023 年在多文档问答中首次系统量化；技术根源之一与注意力机制对首 token 的强偏置（所谓 attention sink）有关——这是《Transformer 原理》专题与《大模型原理》专题的交汇点。</span>

**重点：NEEDLE 的价值不在「测出哪家强」，而在「把长上下文的缺陷可视化成一个可复现的网格」。** 它让「长上下文能力」从厂商宣传词变成了一张可以贴进论文、逐格对比的实测图。

## 3 从「找得到」到「用得了」

长上下文评测正在经历一次升级：**单纯检索（针找得到）远远不够，还要测推理（找到之后能否多步利用）**。

- **检索层**：NEEDLE 测「信息定位」，是底线能力；
- **推理层**：LongBench 的多文档问答测「跨片段整合推理」——把针找出来后，还要比较、推断、综合；
- **对话层**：LongBench-Chat、RULER 等后续工作，把长上下文评测推进到多轮对话与更复杂的指令场景。

**辨析｜易错点：** 不要把「检索成功」当作「长上下文能力强」的充分证据。一根针的检索本质是**模式匹配**——模型记住了「那句话出现过」；而真正的长上下文能力，是**从几千 token 里抽取信息、跨多段做推理、抵抗位置与噪声的干扰**。检索高分但推理低分，是长上下文模型最常见的「偏科」。

## 4 公式解析：干草垛网格的检索准确率

NEEDLE 的核心指标是对每个「（上下文长度 $l$，针深度 $d$）」组合计算检索准确率：

$$
\text{Retrieval}(l, d) = \frac{1}{N}\sum_{i=1}^{N} \mathbb{1}\!\left[\text{模型在第 } i \text{ 次试验中答出了针的内容}\right]
$$

拆成四步理解：

- **第一步，固定 $l$ 与 $d$**：$l$ 是上下文总长度（如 4k、128k），$d$ 是针的相对深度（如 10%、50%、90%）。每个组合做 $N$ 次独立试验（针的内容、噪声文本各随机）。
- **第二步，逐试验判定**：模型回答只要命中了针里的关键事实，$\mathbb{1}[\cdot]$ 记 1——这是**二元判定**，不是打分。
- **第三步，取平均**：得到该格子的检索成功率，填进网格。全部组合的成功率就构成一张 $L \times D$ 的彩色网格。
- **第四步，读网格**：横看长度效应（越长越难？），纵看深度效应（中间是否塌陷？）。**「迷失在中间」在公式层面的表现，就是中间深度 $d$ 组合的 $\text{Retrieval}$ 显著低于两端。**

由此还能构造一个「硬核」指标：**模型在 128k 长度、50% 深度的成功率**——一个广告宣称 128k 的模型若在这里失败，它的「长上下文支持」就只是窗口意义上的，而非能力意义上的。

## 5 局限与小结

长上下文评测仍不成熟：合成任务（埋针）与真实使用（长文档精读）存在差距；「针」与「噪声」的构造方式不同会改变结论；上下文窗口与评测任务本身的耦合也让结果难跨模型比较。但方向是清晰的——**从「能装多长」到「能用多长」，从「找得到」到「用得了」**。

## 6 小结

- **LongBench** 以 21 个中英双语数据集、6 类任务，系统测「长上下文中的任务能力」。
- **NEEDLE** 用「干草垛网格」把「单针检索」变成可视化压力测试，暴露**「迷失在中间」**。
- 检索能力 ≠ 长上下文能力；评测正从**检索层升级到推理层**。
- 网格检索准确率 $\text{Retrieval}(l,d)$ 逐格判定，中间深度的塌陷就是迷失现象。
- 结论：支持窗口是必要条件，能利用窗口才是充分条件。

至此，我们从「评什么」（MMLU、BigBench）走到「怎么量」（HELM 七指标），从「谁来判」（MT-Bench、LLM-as-a-Judge、HumanEval 的编译器）走到「测哪些新战场」（幻觉、多语言、智能体、安全、污染、长上下文）——**大模型评测的十三块拼图已经拼齐**。当你能为一个模型同时回答「它知道什么、推理多稳、对话多好、有多安全、分数有没有注水、长文里还剩几成本事」时，你就真正掌握了用尺子审视这个时代最复杂人造物的方法。下一步，不妨走向《大模型对齐》《大模型部署》与《提示工程》——评测出短板，正是这些专题的起点。
