## 为什么从「效率局限」开始

大语言模型的统治性范式，是**自回归的下一 token 预测（next-token prediction）**：给定前文，模型输出下一个 token，把这个 token 接回输入，再输出下一个。GPT、Llama、DeepSeek 无一例外。这套范式带来了语言建模的辉煌，也埋下了两个越来越疼的效率问题——**推理时一次只算一个 token，训练时一个数据样本只用一次**。<span class="marginnote">下一 token 预测的损失函数本质是对整个序列做<strong>乘积分解</strong>：$P(x_1,\dots,x_T) = \prod_t P(x_t \mid x_{<t})$。这个分解在「逐字生成」的同时，也把「一次只走一步」刻进了范式里，详见第2篇《MTP 与单 Token 预测的本质差异》。</span>

多 Token 预测（Multi-Token Prediction, MTP）要回答的问题正是：能否让模型**一次预测未来的 K 个 token**，同时换来训练样本复用与推理加速？而一切改进的起点，是先看清单 Token 范式到底「慢」在哪里。

## 1 自回归生成的「逐字」困境

训练好的大模型在推理时，就是一台**逐字印刷机**。以生成「北京是中国的首都」为例，模型先读完整句前缀，算出下一个词 `北京`，把 `北京` 拼回去，再算 `是`，如此反复。每一步都要**重新读一遍全部权重**，才能算出一小步。

<span class="marginnote">这里的关键是「访存量」而非「计算量」：无论这一步只预测一个 token 还是十个 token，模型都必须把全部参数从显存搬到计算单元，权重访存与生成长度<strong>无关</strong>，而只与模型大小有关。</span>

由此引出推理阶段的第一个观察：**解码是访存瓶颈（memory-bound）而非算力瓶颈（compute-bound）**。一个 7B 模型每生成一个 token，要搬运约 14 GB 权重；而 H100 每秒能搬运数 TB 显存带宽，但生成一个 token 的数学运算只用掉了其中极小一部分。于是 GPU 空等内存，利用率长期徘徊在个位数百分比。**不是算不快，而是「喂不快」。**

## 2 推理阶段：显存带宽是真正的瓶颈

把一次解码「搬运的数据量」写清楚，就能解释几乎所有加速技术的动机。<span class="marginnote">KV Cache 是逐 token 变长的部分：上下文越长，要重读的 KV 越多，这就是「长上下文越跑越慢」的来源，见第三级《长上下文与注意力优化》专题。</span>

**单步解码需要搬运两类数据**：

- **权重**：每一层 Transformer 的矩阵 $W$ 都要从显存读入，规模约为模型参数量的两倍（fp16 下）。
- **KV Cache**：为当前 token 计算的注意力键值对会被缓存，供后续 token 复用；每步新增的量正比于序列长度与层数。

设模型参数量为 $N$，权重以 b 字节每参数存储，单步解码的访存量近似为

$$M_{\text{decode}} \approx b \cdot N + \underbrace{2 \cdot n_{\text{layers}} \cdot d \cdot L}_{\text{KV 增量}}$$

其中 $L$ 是当前序列长度，$d$ 是每个头的维度。**瓶颈关系**是：当 $L$ 还短时，第一项 $bN$ 占绝对主导——于是「小模型 + 大上下文」与「大模型 + 短上下文」各自遇到不同的访存墙。**所有投机解码、量化、MTP 推理复用，本质都是想减少单位 token 的访存量。**

## 3 训练阶段：下一个 token 只用一次

推理的「慢」显而易见，训练侧的「浪费」则更隐蔽。标准的预训练目标只预测**下一个** token：

$$\mathcal{L} = -\frac{1}{T}\sum_{t=1}^{T} \log P_\theta(x_t \mid x_{<t})$$

对序列里的每一个位置 $t$，模型只在一个目标 token $x_t$ 上得到监督信号。**「预测正确」意味着什么？** 一个 token 被正确预测，可能只是因为它是高频词；而真正需要长期规划的「结构」（函数体的结尾、论证的结论）在样本里出现频率低，下一 token 目标给它的梯度很稀疏。

<span class="marginnote">Gloeckle 等人 2024 年的论文里有一个直观类比：下一 token 预测迫使模型把大部分容量花在「短程」的局部统计上，而多步预测则强制模型在表示里编码「下一步、下下步要发生什么」，相当于给同一个输入配了 K 份监督。</span>

更直接的浪费是**样本利用率**：一段长 $T$ 的文本，在标准目标下产生 $T$ 个「输入-输出」对，但**每个输入只看一个输出**。若改成同时预测后续 K 个 token，同样的输入文本就能产生 $K$ 份监督信号——**训练信号的密度直接翻 K 倍**。这正是 MTP 在训练侧的红利来源。

## 4 公式解析：单步解码的耗时模型

**推理耗时 = 访存量 ÷ 访存带宽**，这是理解一切解码加速的第一条公式：

$$
t_{\text{step}} = \max\left(\frac{M_{\text{decode}}}{B_{\text{mem}}},\; \frac{C_{\text{step}}}{F_{\text{compute}}}\right)
$$

- **第一步，认符号**：$t_{\text{step}}$ 是生成一个 token 的平均耗时，$M_{\text{decode}}$ 是上节算出的访存量，$B_{\text{mem}}$ 是显存带宽（如 H100 约 3.35 TB/s），$C_{\text{step}}$ 是这一步的浮点运算量，$F_{\text{compute}}$ 是算力（如 H100 约 989 TFLOPS）。
- **第二步，比两项**：哪个大，哪个就是瓶颈。对大模型自回归解码，几乎总是 $\frac{M_{\text{decode}}}{B_{\text{mem}}} \gg \frac{C_{\text{step}}}{F_{\text{compute}}}$——**算力远过剩，内存拖后腿**。
- **第三步，看结论**：想让 $t_{\text{step}}$ 下降，最有效的办法不是加算力，而是**减少访存量**或**让一个 token 的访存摊到多个输出上**。MTP 推理复用、投机解码正是后一条路——模型多算几步的成本几乎免费（算力闲着），省下的却是整段访存。

## 5 数值算例：一个 7B 模型到底慢在哪

把两条公式合起来，算一笔具体的账。设模型为 7B 参数、fp16 存储（每参数 2 字节），则每步权重访存为 $7\times10^9 \times 2 = 14$ GB。

在 H100（显存带宽约 3.35 TB/s）上，单是搬运权重就需要 $14 \div 3350 \approx 4.2$ 毫秒。而这一步的浮点运算量只有约 $2 \times 7\times10^9 = 1.4\times10^{10}$ FLOPs，H100 的算力约 989 TFLOPS，纯计算只需 $1.4\times10^{10} \div 9.89\times10^{14} \approx 0.014$ 毫秒。

两个数字放在一起，**访存耗时是计算耗时的约 300 倍**——GPU 的算力几乎全程闲置在等待内存。若上下文为 4096、单层 KV 128 维、48 层，KV 增量项 $2\times48\times128\times4096 \approx 50$ MB，与 14 GB 权重相比仍是零头——**短上下文里权重访存是绝对主导**。<span class="marginnote">这个算例给出了「解码慢」的精确分工：短上下文靠权重访存，长上下文靠 KV 增量。两者的缓解手段也各不同——权重侧靠量化与投机解码摊薄，KV 侧靠缓存压缩（如 DeepSeek 的 MLA）——但 MTP 的「一步多 token」对两侧都有效。</span>

这个算例还解释了为什么「加算力」救不了解码慢：瓶颈在带宽，不在 FLOPs。要让单步产出多个 token，只有**复用一次访存、多算几步**这一条路——这正是 MTP 推理复用与投机解码共同的出发点，也是第3篇《MTP 驱动的投机解码机制》的核心。

## 6 两道效率墙的对照表

把推理与训练两侧的问题并排看，能更清楚地看到 MTP 的落点：

| 维度 | 推理侧 | 训练侧 |
| --- | --- | --- |
| 瓶颈 | 显存带宽（访存瓶颈） | 样本利用率（监督稀疏） |
| 症状 | 每步重读全部权重，GPU 空等 | 每个输入只看一个输出 |
| 关键量 | 单位 token 访存量 $M_{\text{decode}}$ | 每位置监督信号数 |
| 缓解方向 | 减少访存 / 一步多 token | 一份输入配 K 份监督 |
| MTP 的作用 | 推理复用 MTP 头做投机解码 | K 个预测头同时给监督 |

**单 Token 范式的两道墙，恰好是 MTP 两大红利（推理加速 + 样本效率）的瞄准点**——这是本专题后续所有设计的第一性原理。

## 7 术语速查表

| 术语 | 含义 | 在本节的作用 |
| --- | --- | --- |
| 自回归（autoregressive） | 一次生成一个 token，把输出接回输入 | 单 Token 范式的基本形态 |
| 访存瓶颈（memory-bound） | 耗时受显存带宽限制而非算力 | 解码慢的根源 |
| KV Cache | 缓存的注意力键值对 | 上下文重读更省，但变长后线性增长 |
| 预填充（prefill） | 处理输入上下文的一次前向 | 首 token 延迟的来源，见第3篇 |
| 样本利用率 | 每个输入位置产生的监督信号数 | 训练侧「一次只用一次」的浪费所在 |

## 8 延伸：单 Token 局限的两面性

必须澄清一个常见误会：**「单 Token 范式有局限」不等于「它该被抛弃」**。直到今天，绝大多数生产级大模型仍以 next-token prediction 为主损失——MTP 是它的**叠加项**而非替代品（第1篇《MTP 训练目标与损失函数设计》的 $\mathcal{L} = \mathcal{L}_{\text{CE}} + \lambda \mathcal{L}_{\text{MTP}}$ 正说明了这一点）。

单 Token 局限的真正价值，在于标出了**效率改进的空间**：

| 局限 | 表现 | 对应的改进方向 |
| --- | --- | --- |
| 推理访存浪费 | 每步重读全部权重 | 投机解码、量化 |
| 训练样本只用一次 | 每个输入只配 1 个输出 | MTP 的 K 份监督 |
| 长上下文 KV 膨胀 | 上下文越长越慢 | KV 压缩（MLA） |

这三个方向在后续篇章逐一展开——**理解「单 Token 慢在哪」，就是理解大模型效率优化的全部出发点**。

## 9 小结

- 自回归解码**逐字生成**，每一步都要**重读全部权重**，因而**解码是访存瓶颈**。
- 单步耗时 = 访存量 ÷ 带宽：权重项 $bN$ 主导短上下文，KV 增量 $2 \cdot n_{\text{layers}} \cdot d \cdot L$ 随序列长度线性增长。
- 数值算例：7B 模型每步权重访存 14 GB，访存耗时约为计算耗时的 300 倍——**算力远过剩，内存拖后腿**。
- 训练侧每个输入只看一个输出，**样本利用率低**；MTP 把目标数从 1 扩到 K，训练信号密度翻 K 倍。
- 一切解码加速的共性目标是**减少单位 token 的访存量**：投机解码、量化、MTP 复用都是这条路。

在下一节，我们把「单 Token 慢在哪、废在哪」的诊断接到正面答案上：**多 Token 预测如何定义、它的核心思想是什么**。
