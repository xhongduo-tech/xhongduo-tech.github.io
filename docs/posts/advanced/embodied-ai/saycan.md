# SayCan：语言模型可供性（Affordance）落地

## 为什么从 SayCan 开始

大语言模型（LLM）知道「怎么做番茄炒蛋」，
但它**不知道机器人会不会做**——LLM 活在语言里，
机器人活在物理里。**SayCan**（2022，
谷歌）第一次系统回答了这个「语言落不到现实」的问题：**把 LLM 的「任务概率」与机器人价值函数的「可行概率」相乘**，
让 LLM 说「想做什么」、让机器人说「能做做什么」，
二者都认可才执行。
这是「LLM 当高层 + 低层技能落地」的开山范式<span class="marginnote">SayCan 的名字是个双关：LLM 能「Say」（说），
机器人能「Can」（做），
合起来「SayCan」——说得出来又做得到才动手。
它的公式 $p(\text{step}) = p_{LLM}(\text{step}) \times p_{value}(\text{step})$ 成了「语言-动作落地」的标准模板，
后来的 LLM 具身工作几乎都引用它。
</span>。

## 1 问题：LLM 知道但做不到

LLM 的局限在具身场景里暴露无遗：

- LLM 能写出「把可乐从冰箱拿出来」的步骤，
但**不知道冰箱在哪、可乐在不在、机器人能不能打开冰箱**；
- LLM 的「规划」是**语言合理**，
不是**物理可行**——「先拿杯子再倒水」听起来对，
但杯子可能在隔壁房间；
- 没有「可行性」的概念，
LLM 会规划出「机器人做不到」的步骤。

**SayCan 的洞察**：把「可行性」交给**机器人自己的价值函数**——价值函数（RL 学出来的）知道「在当前位置、当前场景下，
这个技能有多可能成功」。**LLM 负责「想做什么」，价值函数负责「做得到吗」**。

## 2 方法：两个概率相乘

SayCan 的每一步选技能：

1. **LLM 打分**：给定任务目标与历史步骤，
LLM 给出「下一步该做什么」的**任务概率** $p_{LLM}(\text{step})$（语言上合理吗）；
2. **价值函数打分**：对每个候选技能，
机器人价值函数给出**可行概率** $p_{value}(\text{step})$（当前场景做得到吗）；
3. **综合**：选「两者乘积最大」的技能执行：

$$
\text{step}^* = \arg\max_{\text{step}}\; p_{LLM}(\text{step}) \cdot p_{value}(\text{step})
$$

执行后更新场景，
再让 LLM 规划下一步——**闭环逐步推进**，
直到 LLM 认为任务完成（输出「完成」）。

## 3 为什么乘积是对的

- **$p_{LLM}$ 高、$p_{value}$ 低**：LLM 想做的机器人做不到——乘积低，
不选（「说得出来但做不了」）；
- **$p_{LLM}$ 低、$p_{value}$ 高**：机器人能做的但不是任务需要的——乘积低，
不选（「做得了但不该做」）；
- **两者都高**：既符合任务又可行——才执行。

**乘积 = 「既合理又可行」的双重门**。
它防止 LLM「空想」、也防止机器人「瞎忙」。

## 4 系统与技能

SayCan 部署在**移动操作机器人**上（厨房场景），
技能库包括「拿可乐」「开抽屉」「把物品给人类」等——**每个技能是一个 RL 学出来的策略**，
价值函数能给出「当前成功概率」。
整体架构是标准的**分层**（上一节）：LLM 当高层选技能，
RL 策略当低层执行。

**效果**：SayCan 在长任务（101 个指令）上成功率显著高于纯 LLM 规划（LLM 不知道可行性的会「卡在不可行步骤」）——**「知道能做」让长任务真正执行下去**。
<span class="marginnote">SayCan 的工程启示：<strong>LLM 的价值不在「自己规划得多好」，
而在「给机器人提供任务语义 + 让机器人用价值函数兜可行性」</strong>。
很多「LLM 机器人」项目失败的根源，
就是让 LLM 直接出动作、没有任何可行性门控——SayCan 的「乘积门」是第一道也是最重要的一道。
</span>

## 5 公式解析：SayCan 的综合打分

$$
\text{step}^* = \arg\max_{\text{step}}\; \underbrace{p_{LLM}(\text{step})}_{\text{任务合理性}} \cdot \underbrace{p_{value}(\text{step})}_{\text{物理可行性}}
$$

- **第一步，看 $p_{LLM}$**：LLM 在「任务目标 + 已完成步骤」下，
判断每个候选「是不是合理的下一步」——**语义层**的合理性；
- **第二步，看 $p_{value}$**：价值函数对每个技能给「当前场景下的成功概率」——**物理层**的可行性；
- **第三步，看乘积的语义**：取 log 变成「合理性 + 可行性」的相加——**两个维度都要好，整体才好**
  任何一个塌掉，
整体塌掉；
- **第四步，看滚动执行**：每步选完、执行、更新场景、LLM 再规划下一步——**「走一步、看一步」的闭环**，
让 LLM 的规划永远基于「当前真实状态」而非「语言想象」。

## 6 辨析｜SayCan vs 纯 LLM；可供性与可行性

**辨析｜易错点一：SayCan 不是「让 LLM 更聪明」，是「给 LLM 装上可行性」。** 纯 LLM 规划在语义上可能完美，
但**不落地**；
SayCan 用价值函数门控，
让「语义合理」与「物理可行」必须同时满足。
<span class="marginnote">实务判断：<strong>「LLM 只出高层、可行性交给机器人」是 LLM 具身的黄金法则</strong>。
SayCan 之后几乎所有 LLM 具身系统（VoxPoser、Code as Policies 等）都沿用了这个「语言定方向、机器人定可行」的分工。
</span>

**辨析｜易错点二：可供性（affordance）不是「可行性」的同义词。** 可供性是「环境允许什么行为」（杯子可以抓、门可以开）——是**环境的属性**；
可行性是「当前机器人成功概率」——是**机器人+环境的联合属性**。
SayCan 的 $p_{value}$ 是「可行性」，
它隐式包含可供性（环境不允许，
价值函数自然给低分）。**理解可供性（环境），是理解可行性（机器人）的前提**。

**再辨析｜SayCan 的局限**：技能库需要预先定义（每个技能都要 RL 训练）；
LLM 只在「技能选择」层起作用，**技能内部没有语言参与**。
后续工作（Code as Policies、VoxPoser）把语言推进到「技能内部」（用语言生成代码/价值图）——但「高层语言 + 低层落地」的骨架是 SayCan 立的。

## 7 小结

- **SayCan** = LLM（任务概率）× 价值函数（可行概率），
双重门选技能。
- **问题**：LLM 知道但做不到——可行性必须来自机器人的价值函数。
- **公式**：$\text{step}^*=\arg\max p_{LLM}\cdot p_{value}$，
乘积 = 既合理又可行。
- **系统**：移动操作 + 技能库（RL 策略），
LLM 当高层选技能、滚动闭环执行。
- 「语言定方向、机器人定可行」是 LLM 具身的黄金法则；
SayCan 立了骨架。
