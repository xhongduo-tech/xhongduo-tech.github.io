## 为什么从 Code as Policies 开始

SayCan 让 LLM 选技能；**Code as Policies（CaP）** 再进一步：**让 LLM 直接写机器人策略的代码**。
LLM 不输出「文字动作」，
而是输出**可执行的 Python 程序**——程序调用机器人 API、做几何计算、写条件逻辑，
最终算出动作。**代码比语言精确、可组合、可测试**，
还能借助 numpy 等库做复杂的几何与约束推理——这是「LLM 控制机器人」在表达力上的一次跃迁<span class="marginnote">CaP 的洞察：<strong>LLM 训练时就见过海量代码，
它「写程序」的能力比「写动作序列」的能力强得多</strong>——因为代码是精确的、可验证的。
与其让 LLM 输出「把物体放到障碍物上方 10 厘米」这样含糊的语言，
不如让它输出一行 `pos = obstacle_pos + [0, 0, 0.1]` 的代码。
</span>。

## 1 从「语言动作」到「代码动作」

传统 LLM 具身让 LLM 输出**文本**（动作描述或技能名）——**含糊**：把物体放到「旁边」到底是哪？
CaP 让 LLM 输出**代码**——**精确**：

```python
# LLM 生成的代码
def pick_and_place(obj, target):
    obj_pose = get_pose(obj)          # 查询物体位姿（API）
    target_pose = get_pose(target)
    above = obj_pose + [0, 0, 0.15]   # 抬到物体上方 15 cm
    move_to(above)                    # 移到上方
    grasp(obj)                        # 抓取
    lift(obj)
    move_to(target_pose + [0, 0, 0.15])
    release()
```

**API 层**：机器人平台暴露一组「感知/运动 API」（`get_pose`、`move_to`、`grasp`）——LLM 在提示里见过这些 API，
就会**用它们拼出策略**。**LLM 是「程序员」，API 是「工具箱」，代码是「程序」**。
## 2 为什么代码比语言强

四个理由：

- **精确**：代码是确定性描述，
没有「旁边」「差不多」这类含糊；
- **几何计算**：LLM 写的代码可以调用 numpy 做向量运算、坐标变换——「把杯子放到桌子中心」这类**空间推理**用代码三行搞定；
- **逻辑控制**：`if-else`、`for` 循环、约束检查——「如果夹爪没抓到就重试」这类**条件逻辑**语言描述不了，
代码天生支持；
- **可测试与可组合**：代码能跑、能 debug、能复用——**代码策略可以调用其他代码策略**（分层），
形成策略库。

## 3 约束与避障：用代码写「不该做什么」

CaP 的杀手锏是**把约束写进代码**。
LLM 写策略时，
可以生成**约束检查**：

```python
def pick_avoiding(obj, obstacle):
    # 采样候选抓取点，排除与障碍物碰撞的
    candidates = sample_grasps(obj)
    for g in candidates:
        if not collides(g, obstacle):   # 避障约束
            return g
    return None  # 无可行抓取
```

LLM 用「代码思维」处理「避开什么、在哪个区域、多高多低」——**约束被编译成可执行的检查**，
而不是靠模型「猜」。
这让 CaP 在**需要精确几何与明确约束**的任务上远超「语言直接出动作」。

## 4 分层：代码策略套代码策略

CaP 天然支持**递归分层**：LLM 生成的高层策略可以**调用**它生成（或人类写好的）的低层代码策略：

- 高层：`plan_kitchen_task()` 里调用 `pick(obj)`、`place(obj, loc)`；
- 低层：`pick()` 是另一个（LLM 或预写的）代码函数。

**这比 SayCan 的「选技能」更灵活**——技能不是预先定义的离散集合，
而是**按需生成的代码**。
「技能库」从「静态列表」变成「动态生成」，
组合能力指数增长。
<span class="marginnote">CaP 的分层是「代码的函数调用」：<strong>高层代码策略把低层代码策略当函数调用，
低层策略处理细节</strong>。
这让「零样本组合」成为可能——LLM 写一个新高层策略时，
可以用「之前见过的低层函数」——比「固定技能库」的表达力高一个数量级。
</span>

## 5 公式解析：代码策略的生成与执行

$$
\pi_\theta(a \mid o, \text{API}) \;\equiv\; \text{LLM}\big(\text{prompt} + \text{API 文档}\big) \to \text{Python}(o) \to a
$$

- **第一步，看提示设计**：给 LLM 的任务描述 + **API 文档**（函数签名、示例用法）——LLM 从这些「已知工具」里拼策略，**提示里的 API 就是 LLM 的「工具箱」**；
- **第二步，看代码生成**：LLM 输出 Python 函数，
输入观测 $o$、输出动作 $a$——**策略被「编译」成代码**；
- **第三步，看执行**：机器人运行代码，
调用 API、做几何计算、执行动作——**确定性执行，没有「概率采样」**（这是与 learned policy 的本质区别）；
- **第四步，看失败处理**：代码能捕获异常、检查返回值、条件重试——**错误处理也被「写进程序」**，
比概率策略更可控。

## 6 辨析｜CaP vs SayCan；代码 vs 学出来的策略

**辨析｜易错点一：CaP 与 SayCan 是「代码生成」与「技能选择」的分野。** SayCan 从**固定技能库**里选；
CaP **现场生成**策略代码。
<span class="marginnote">选型判断：<strong>任务需要精确几何、约束、逻辑 → CaP（代码表达力强）；
任务需要「泛化到没写过的情况」→ 学习的策略（神经网络，
从数据学）</strong>。
CaP 的代码「精确但死板」——它只能做「提示里 API 能表达的」；
学出来的策略能「涌现」，
但不可解释。
</span>

**辨析｜易错点二：CaP 的代码 ≠ 端到端学出来的策略。** CaP 是「LLM 生成程序 + 程序执行」，**没有学习**（LLM 是预训练的，
策略本身不是训练出来的）；
学出来的策略是「参数化的函数」。**CaP 的可靠性来自「代码确定性」，上限来自「API 表达力」**——API 没有的（如「判断物体软硬」）代码做不了。

**再辨析｜API 设计决定 CaP 的成败**。
LLM 只能调用「提示里出现的 API」——**API 设计得好不好，直接决定 LLM 能写出什么策略**。
API 太底层（关节角），
LLM 写不出高层任务；
太高层（只有「完成做饭」），
LLM 没得拼。**「粒度合适的 API + 清晰的文档 + 好示例」是 CaP 系统的真正工程**。

## 7 小结

- **Code as Policies**：LLM 生成可执行 Python，
调用机器人 API，
算出动作。
- **代码的优势**：精确、几何计算、条件逻辑、可测试可组合。
- **约束写进代码**：避障、抓取候选过滤——「不该做什么」编译成可执行检查。
- **分层**：代码策略调用代码策略，
技能库从「静态」变「动态生成」。
- CaP 可靠来自代码确定性、上限来自 API 表达力；
API 设计是成败关键。
