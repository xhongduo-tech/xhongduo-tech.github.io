## 为什么从"分布式"开始

前两篇我们都在回答同一个问题：怎么用一台机器的有限内存，把索引造出来？BSBI 与 SPIMI 都是**单机策略**——内存不够就分块、排序、归并，把磁盘当作第二级内存。但当文集大到千万、上亿篇文档（想想整个维基百科、整个 Web 快照），单机的 CPU、磁盘 IO 与网络带宽都会成为瓶颈：**索引构建不是"造不造得出来"的问题，而是"造完时数据是否已过时"的问题。**

**MapReduce** 是谷歌在 2004 年提出的分布式编程模型，把"大规模并行"抽象成两个极其简单的原语——map（映射）与 reduce（归约）。索引构建恰好是它的经典应用场景之一：倒排索引的形成，天然是一个"先按词项打散、再按词项聚合"的过程，与 MapReduce 的"映射-归约"两步几乎一一对应。<span class="marginnote">MapReduce 这个名字取自函数式编程里的 map（映射）与 reduce（归约）。它最大的贡献不是新算法，而是<strong>把"并行"从程序员手里接管过来</strong>：你只需写两个纯函数，调度、容错、数据搬运全部交给框架。分布式索引不过是它的第一个名场面。</span>

## 1 索引构建为什么天然适合并行

倒排索引构建的总工作量是**读取全部文档并解析出所有词项**——这摊工作有一个美妙的性质：**按文档切分后互不干扰**。

- 文档 $d_1$ 里出现"brutus"，不需要知道文档 $d_2$ 里有什么。
- 唯一需要"跨文档"协作的点是：同一个词项在无数文档里出现，最后要把它们**汇总到同一张倒排表**。

于是整个任务被切成两半：**第一步，各干各的（把文档解析成"词项 → 文档编号"）**；**第二步，合起来干（按词项把所有文档编号聚拢）**。前者是 **map（映射）**，后者是 **reduce（归约）**。这正是 BSBI / SPIMI 在单机里反复做的"分块 + 归并"，只不过被抽象成了统一接口，交给集群去跑。

**重点：分布式的核心不是"更多 CPU"，而是"把数据流切开"。** 每台机器只处理自己分到的那片文档，只产出一部分中间结果；框架负责把中间结果按词项路由到正确的归约机器上。

## 2 MapReduce 的两个原语

一个 MapReduce 作业由两个用户自定义函数驱动：

- **map 函数**：输入是"文档编号 + 文档内容"，输出是若干"词项 → 文档编号（或词项频率）"对。例如对文档 3 里出现的每个词 $t$，emit 一个 $\langle t, 3 \rangle$。
- **reduce 函数**：框架把**同一个 intermediate_key（即同一个词项）的所有值**聚集在一起，交给 reduce 函数。对索引构建，reduce 只需把文档编号列表排序（或合并），即得到该词项的完整倒排表。

**辨析｜易错点：map 的输出是"键值对"，不是"写盘文件"。** 中间键值对会按键被框架分组（shuffle）后送给 reducer——"分组"这一步由框架完成，你不用写任何聚合逻辑。你写的 reduce 收到的已经是一个"键 + 该键下所有值的迭代器"。

举一个具体的索引作业：整个文集被切成 $M$ 份，分给 $M$ 个 map 任务并行解析；map 输出按词项哈希分成 $R$ 个桶，每个桶由一个 reduce 任务归并。最终产生 $R$ 份"部分倒排索引"，每份覆盖一部分词项——**词项被划到哪个桶，它的倒排表就在哪个 reduce 任务的输出里**。

## 3 词项划分：哈希桶与按字母序桶

上一节里的 $R$ 个桶不是随便分的。reduce 任务的数量与**分桶方式**直接决定两件事：负载是否均衡、最终索引是否方便查询。

两种常见分桶策略：

- **哈希分桶**：$t$ 落入桶 $\text{hash}(t) \bmod R$。优点：词项均匀散开，负载均衡好。缺点：桶与桶之间无顺序关系，若后续要"按字典序合并成单一词典"，还得再排一趟。
- **按字母序分桶**：如"a–c"一个桶、"d–f"一个桶。优点：桶之间天然有序，后续按词项二分定位时能先锁桶；缺点：词项按字母分布不均（英文里 s、c 开头的词远多于 x、z），易出现热点桶。

**重点：分桶粒度决定查询代价。** 一个词项的倒排表只在一个桶里，查询某个词项时只需访问一个 reduce 的输出——这是"按词项划分"（term partitioning）的雏形。我们在《分布式检索》一篇还会见到"按文档划分"（document partitioning）的另一派做法，两者在在线查询时的通信模式截然不同。

## 4 公式解析：索引构建的 shuffle 开销

MapReduce 真正的成本不在计算，而在**中间数据搬运**。设文集有 $N$ 篇文档、共 $T$ 个词项实例，每个中间键值对约 $B$ 字节，则 map 阶段产出的中间数据总量是：

$$\text{Data}_{\text{shuffle}} = T \times B$$

三步拆解：

- **第一步，读清 $T$**：$T$ 是"所有文档里词项出现的总次数"（约等于倒排表条目数），不是词典大小 $V$。每个词项实例都对应一个中间键值对。
- **第二步，看 $B$**：$B$ 是"词项 + 文档编号 + 元数据"序列化后的字节数。词项短则几字节，加上框架的键值包装，常到几十字节。
- **第三步，理解代价**：这 $T \times B$ 字节要**通过网络**从 map 机器搬到 reduce 机器。对比一下：单机 BSBI 的"归并"是磁盘顺序读，分布式却是跨机器网络 IO——**网络是分布式索引最贵的资源**。

所以工程上的优化方向清晰了：**尽量在 map 端就地聚合**。如果 map 函数在发出中间键值对之前，先在本地把同一文档里重复出现的词项合并成 $\langle t, \text{tf}_{t,d} \rangle$，中间数据量就从"词项实例数"降到"文档-词项对数"，往往能省下几个数量级的网络流量。<span class="marginnote">这正是 SPIMI 与 MapReduce 的结合点：<strong>map 端用哈希累积本机倒排表（SPIMI 的做法），reduce 端做跨机归并</strong>。每台 map 机器先当一次 SPIMI 跑，再交出精炼后的中间结果——把两篇的思想缝成一套流水线。</span>

## 5 容错与延迟：分布式索引的工程底色

分布式系统逃不开一个事实：**机器会挂**。MapReduce 的容错设计因此成为它得以大规模部署的关键：

**任务重试**：某台机器失败，框架把它的 map / reduce 任务重新调度到别的机器上重跑。map 输出可重建（源数据还在），reduce 输出持久化后只需处理未完成部分。
**数据本地性**：map 任务尽量调度到"存有该文档分片"的机器上，让"读数据"走本地磁盘而非网络——这就是"移动计算而非移动数据"的原则。<span class="marginnote">数据本地性是海量数据处理的第一定律：<strong>网络带宽远比磁盘带宽稀缺，把代码派过去，而不是把数据搬过来。</strong> 这条直觉从 MapReduce 一路传承到 Spark、Flink，是分布式系统的元认知。</span>

但分布式不是免费的午餐。它引入了单机没有的两类成本：**调度延迟**（任务排队、启动开销）与**倾斜问题**（个别词项如"the"的倒排表极大，让承载它的 reducer 成为木桶短板）。对付倾斜的经典办法是**二次切分**：把超级词项按文档编号切成子区间，分给多个 reducer 并行归并，最后再拼。

## 6 小结

- **MapReduce** 用 map 与 reduce 两个原语把"解析文档"与"按词聚合"分开，索引构建是它的天然场景。
- **中间数据搬运是最大成本**：$T \times B$ 字节走网络；map 端就地聚合是首要优化。
- **分桶决定负载与查询结构**：哈希桶均衡但无序，字母序桶有序但可能倾斜。
- **容错靠重试与数据本地性**；倾斜靠对超级词项二次切分。
- **与单机策略的关系**：SPIMI / BSBI 是"一台机器上的 MapReduce"，MapReduce 是"集群上的 SPIMI / BSBI"——思想同源，规模不同。

在下一节，我们将回到单机视角，回答索引的生命周期问题——文档不断新增、更新、删除，索引该如何随之演化，这就是**动态索引：辅助索引与即时合并策略**。
