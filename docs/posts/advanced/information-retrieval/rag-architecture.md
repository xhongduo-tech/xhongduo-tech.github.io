## 为什么从"骨架"开始

上一篇立住了 RAG 的动机与思想，但没把"机器"拆开看。这一篇把 RAG 的骨架立起来：**检索器（retriever）+ 生成器（generator）两大模块，以及它们之间的"上下文组织"环节**。理解了这个骨架，RAG 的每个组件（切分、检索、重排、生成、评测）都能在骨架上找到位置。

RAG 的完整流水线是：

1. **索引（离线）**：把知识库文档切分成段落、编码成向量、建索引。
2. **检索（在线）**：用户问题 → 编码 → 检索 Top-K 段落。
3. **重排/过滤（可选）**：对 Top-K 段落精排、去噪。
4. **生成（在线）**：把问题 + Top-K 段落组装成 prompt，交给 LLM 生成答案。

**重点：RAG = 检索器决定"答案的依据"，生成器决定"答案的表达"——中间的上下文组织决定"依据怎么喂给表达"。**<span class="marginnote">RAG 的架构在 2020 年原始论文里是"检索器（双塔）+ 生成器（BART）"联合微调——检索与生成一起训练。今天工业 RAG 通常是"检索器与生成器分开"（检索器用现成的稠密检索，生成器用现成 LLM），组装成流水线。<strong>这个"从联合训练到组件拼装"的演变，说明 RAG 已经工程化了——像搜索引擎一样，成了可插拔组件的流水线</strong>。</span>

## 1 检索器：答案的依据从哪来

**核心概念：检索器（retriever）**：从知识库中检索与问题相关的段落，输出 Top-K 个候选。

检索器在本系列里已经完整学过：

**索引**：知识库文档切段 → 向量化 → ANN 索引（第八篇）。
**检索**：问题编码 → ANN 召回 Top-K（第八篇）。
**进阶**：混合检索（BM25 + 嵌入，第八篇）、查询改写（第九篇）、重排（第八篇）。

**重点：RAG 的检索器就是前十二篇的完整检索系统——它的质量直接决定答案质量。** 检索器召回的相关段落里若有正确答案，生成器就能答对；若没有，生成器只能编（幻觉）。**检索器是 RAG 的第一瓶颈**。<span class="marginnote">RAG 检索器的一个特殊点：<strong>它检索的对象是"段落/切片"而不是"文档"</strong>——因为 LLM 上下文窗口有限，不能把整篇文档塞进去。这就引出下一篇的"切分（chunking）"：怎么把文档切成适合检索与生成的小段。切分粒度直接影响检索质量（段太大检索粗，段太小上下文碎片化）——这是 RAG 检索器独有的设计维度，传统搜索没有。</span>

## 2 生成器：答案怎么写出来

**核心概念：生成器（generator）**：基于"问题 + 检索到的段落"，生成最终答案的 LLM。

生成器的作用：

**理解问题**：从问题的语义出发，组织答案结构。
**整合证据**：把多个检索段落的证据综合成一段连贯答案——**不是复述段落，而是"读段落、写答案"**。
**表达限制**：答案要"基于提供的段落"——**生成的约束条件是"只使用检索到的内容"**。

**重点：生成器是"有据的表达者"——它被要求"只基于证据回答"，这是 RAG 压幻觉的关键设计。** prompt 里的指令（"请仅根据以下文档回答，不要使用外部知识"）就是把这个约束显式化。<span class="marginnote">生成器的"约束强度"是一个可调旋钮：<strong>严格约束（只准用检索内容）减少幻觉但可能答不全；宽松约束（可用模型知识补充）答得更全但幻觉风险高</strong>。工程上按场景调：法律/医疗场景严格约束（正确优先），通用问答宽松一些（流畅优先）。这个"约束 vs 自由"的旋钮，与检索的"召回 vs 精确"权衡一样，是 RAG 调优的主轴。</span>

## 3 上下文组织：检索结果怎么喂给 LLM

检索器与生成器之间，还有一个常被忽略但极其关键的一环：**上下文组织（context assembly）**——把 Top-K 段落变成 LLM 能有效使用的 prompt。

上下文组织的决策点：

**选哪些段落**：Top-K 取多少（K=3 还是 K=10）——太多塞不进上下文/稀释注意力，太少漏信息。
**怎么排序**：段落按相关度排序，最相关的放最前——LLM 对"上下文开头"的注意力最强。
**怎么截断**：段落太长要截断（塞不进上下文），截哪里、留哪段——**截断策略影响信息完整性**。
**怎么组织 prompt**：问题放哪、段落怎么标注、指令怎么写——prompt 结构影响答案质量。<span class="marginnote">上下文组织有一个反直觉的经验：<strong>"Top-K 越多越好"是错的——段落太多，LLM 注意力被稀释，答案反而变差</strong>。工业经验 K 通常在 3–10 之间，且"相关度最高的放在 prompt 最前"。另一个细节：段落里"与问题无关的噪声"（切分带进来的无关句）会误导生成器——所以"检索后过滤/重排"（只留真正相关的段落）对答案质量的影响，往往比"提高召回"更大。上下文组织是 RAG 里"性价比最高"的优化点——不花训练成本，只调 prompt 结构。</span>

**重点：上下文组织是 RAG 的"隐形第三模块"——它决定"检索到的信息能否被生成器有效使用"。** 检索质量高但上下文组织差，答案照样差；检索一般但组织好，答案可能不错。

## 4 公式解析：上下文窗口的约束

RAG 的上下文组织受一个硬约束：**LLM 的上下文窗口长度**。设问题 token 数 $L_q$、每个段落 token 数 $L_p$、取 $K$ 段，则：

$$L_q + K \times L_p + L_{\text{指令}} \le L_{\text{窗口}}$$

三步拆解：

- **第一步，读预算**：问题 + K 段 + prompt 指令的 token 总和，必须小于上下文窗口——**窗口是硬上限**。
- **第二步，看 K 与段落长度的权衡**：$K$ 越大或 $L_p$ 越长，越逼近上限——**K 和段落长度是"窗口预算"的分配**。
- **第三步，看矛盾**：窗口有限（如 8K–128K token），但知识库无限——**"装进窗口的信息"必然小于"全部相关信息"**，检索器的任务就是在有限窗口里装"最相关的信息"。

**核心结论：RAG 的一切设计（切分粒度、K 值、截断）都受"上下文窗口"约束——RAG 是"在窗口预算内装最多有效信息"的优化问题。**<span class="marginnote">上下文窗口的扩展（从 2K 到 128K 甚至更长）正在改变 RAG 的形态：<strong>窗口大了，可以塞进更多段落、甚至整篇文档——切分与 K 值的压力变小</strong>。但窗口不是无限大，且"窗口内信息太多"会让 LLM 注意力分散（lost in the middle 现象：中间位置的段落容易被忽略）。所以 RAG 的"信息组织"永远不会消失——窗口越大，"怎么在窗口里组织信息"越重要。</span>

## 5 RAG 架构的变体

RAG 的基本架构（检索 → 生成）之上，有各种变体：

**重排增强 RAG**：检索 → 重排（交叉编码器）→ 生成——用重排提升"喂给生成器的段落质量"。
**多路检索 RAG**：BM25 + 嵌入双路检索 + 融合——提升召回覆盖（第八篇的混合检索）。
**迭代检索 RAG**：先生成初步答案，用答案再检索，再生成——**"生成-检索-再生成"的迭代闭环**（Agentic RAG 的前奏）。
**self-RAG**：LLM 自己判断"要不要检索、检索结果可不可信、答案是否忠实于证据"——**生成器自己管理检索**。<span class="marginnote">这些变体的共同趋势：<strong>RAG 从"一次检索一次生成"的直线，走向"检索-生成-反思-再检索"的循环</strong>——检索与生成从"串行"变成"交互"。这个趋势的终点是 Agentic RAG（最后一篇）：检索变成"可规划的智能行为"，生成器变成"会判断、会决策的智能体"。理解基本架构，是理解这些变体的起点。</span>

**辨析｜易错点：RAG 的"检索器"与"生成器"不是固定的一套，是可插拔的。** 检索器可以是 BM25、双塔、混合；生成器可以是任何 LLM。**"换检索器"与"换生成器"是 RAG 优化的两个独立杠杆**——检索器决定"看到什么依据"，生成器决定"把依据写成什么"。优化 RAG 时先分清"是检索问题还是生成问题"——检索差就换检索，生成差就换 prompt/模型，别混在一起调。

## 6 数值算例：一次上下文组织的预算分配

把"上下文窗口是硬约束"演算成一次 prompt 组装。设窗口 4096 token，问题 50 token、指令 100 token、段落平均 400 token：

| 方案 | K（段落数） | 总 token | 是否超窗 |
| --- | --- | --- | --- |
| K=8 | $50 + 8\times400 + 100 = 3350$ | 3350 | 不超，但接近上限 |
| K=10 | $50 + 10\times400 + 100 = 4150$ | 4150 | **超窗，塞不下** |
| K=5 | $50 + 5\times400 + 100 = 2150$ | 2150 | 充裕，但可能信息不足 |

三步读这张表：

- **看 K=10 的硬约束**：4150 > 4096——**塞不下就是塞不下，窗口是硬上限**。
- **看 K=8 的临界**：3350 勉强装下，但"中间段落"可能被 LLM 忽略（lost in the middle）——**装得下 ≠ 用得好**。
- **看 K=5 的保守**：2150 充裕但只 5 段——若正确答案在第 6 段，就被漏掉了——**信息完整性 vs 窗口容量的权衡**。

这个例子是"RAG 是窗口预算内装最多有效信息"的实证：**K 值不是越大越好，也不是越小越好，而是"窗口能装下的最大有效段落数"**。工程上 K 与段落长度（切分粒度）是一对协同变量——段落切短些就能多放几段，段落切长些每段信息更完整——**K、切分粒度、窗口三者的联合调优，是 RAG 上下文的日常工程**。

**辨析｜易错点：RAG 的"检索质量"与"生成质量"不能只看检索的 Recall@K，要看"喂进 prompt 后的答案质量"。** 检索召回 100 段、生成只用了 5 段——**真正影响答案的是"进 prompt 的那 5 段"**。评测 RAG 要"端到端"：检索质量 + 上下文组织 + 生成质量一起看，单看任何一环都会误判瓶颈（第十三篇的因果链会详细展开）。"检索到"≠"喂进 prompt"≠"答得好"——三层差距，是 RAG 评测的层层关卡。

## 8 小结

- **RAG 骨架**：索引（离线）→ 检索 → 重排/过滤 → 上下文组织 → 生成（在线）。
- **检索器**：前十二篇的完整检索系统——检索段落而非文档，质量是答案的第一瓶颈。
- **生成器**：基于证据表达的 LLM——"只使用检索内容"是压幻觉的关键约束。
- **上下文组织**：隐形第三模块——选段、排序、截断、prompt 结构，决定"依据能否被有效使用"。
- **窗口约束**：$L_q + K L_p + L_{\text{指令}} \le L_{\text{窗口}}$——RAG 是"窗口预算内装最多有效信息"的优化。
- **架构变体**：重排增强、多路检索、迭代检索、self-RAG——从"直线"走向"循环"。

在下一节，我们处理 RAG 的第一个工程细节——文档怎么切成适合检索与生成的片段，这就是 **RAG 中的文档切分（Chunking）策略**。
