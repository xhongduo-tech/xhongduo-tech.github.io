# 索引压缩的意义与词典压缩技术

## 为什么从"压缩"开始

到此为止，我们建立了一套完整的索引世界：倒排索引的两段结构、构建时的单机与分布式方案、数据流入时的动态更新。但有一个问题被一路搁置了：**索引到底占多大空间？**

直觉是"文档有多大，索引就差不多多大"。真实数字会推翻这个直觉。IIR 里引用的经验是：倒排索引约占原始文本体积的 **25%–35%**，甚至更小。也就是说，**索引比被索引的文档还小一个量级**——这听起来反直觉，却是压缩技术一分一厘省出来的结果。更关键的是，索引是要**常驻内存或按需读入内存**的：内存比磁盘贵，磁盘比文档多。索引每小一分，能放进内存的文档就多一分，查询就能少访问一分磁盘——**压缩不只是省钱，是直接换查询速度**。<span class="marginnote">搜索引擎把"能塞进内存的索引越多，查询越快"当作第一工程法则。谷歌早年有一句流传的话：<strong>内存是新的磁盘，磁盘是新的磁带。</strong> 压缩的本质是把你想要的东西压小，让它在更贵的存储层里装得下。</span>

压缩分两个战场：**词典压缩**（这篇）与**倒排表压缩**（下一篇）。它们压缩的对象、手段、收益完全不同——一个压"词项名字"，一个压"文档编号"。

## 1 压缩的三个收益

在动手压之前，先算清楚压缩到底买到了什么。IIR 把压缩的收益归纳为三点：

**节省磁盘空间**：直接降低存储成本，也减少合并、备份等操作的重写量。
**提高内存利用率**：更多索引条目能常驻内存。词典通常要全部进内存，压缩词典直接等于"内存里能装更大的词典"。
**加快数据读取**：从磁盘读入的数据变少，IO 时间缩短；代价是额外的 CPU 解码开销。**当"省下的 IO"大于"多花的 CPU"时，压缩净赚速度**——这是压缩悖论（compression paradox）的正面。

**重点：压缩的终极目标是速度，不是空间。** 磁盘是检索系统最慢的部件，任何"以 CPU 换 IO"的操作，只要 CPU 开销小于 IO 节省，就是净收益。<span class="marginnote">压缩悖论：压缩数据看似多做了解码工作，但因为 IO 瓶颈远大于 CPU 瓶颈，<strong>读"压缩数据 + 解压"常常比读"未压缩数据"更快</strong>。现代存储引擎广泛依赖这条反直觉经验。</span>

## 2 词典为什么需要单独压缩

回忆词典的结构：每个词项条目要存三样东西——**词项本身**、**文档频率 df**、**倒排表指针**。词典的体量来自词项字符串本身：一个 $V$ 词项的词典，若平均词长 $L$ 字节，光是字符串就要 $V \times L$ 字节。

词典通常必须**全部常驻内存**（查询要先在词典里定位词项，再去磁盘读倒排表）。而词项之间有一个极其可利用的结构：**共享前缀**。英文里 automate, automatic, automation, automobile 共享 auto 前缀——字典序排列下，相邻词项前缀重合得越多。这个结构是词典压缩的主战场。<span class="marginnote">对比倒排表：倒排表是数字列表，数字之间没有"共享前缀"这种结构，它的压缩靠"差值小"（下一篇的主角）。<strong>两种结构、两套压缩——词典压字符串，倒排表压整数。</strong></span>

## 3 词项级压缩：按块存储与前端编码

**核心概念：前端编码（front coding / prefix encoding）**：按字典序排列词项后，每个词项不存完整字符串，而存"与上一个词项的共享前缀长度 + 剩余后缀"。

例如 transmit → transmitted → transpire：

| 词项 | 存储形式 |
| --- | --- |
| transmit | 完整存储（无前缀可比） |
| transmitted | (8, ted)：共享前缀 8 字符，后缀 ted |
| transpire | (5, pire)：与上一个共享 5 字符，后缀 pire |

当词项按字典序排列时，共享前缀普遍较长，平均每个词项可省下大量字符。**字典序排列是前端编码的前提**——所以我们在《分布式索引》里看到"按字母序分桶"的副产品（词项有序）在这里再次派上用场。<span class="marginnote">前端编码的极端形态是<strong>字典树（trie）</strong>：把整本词典表示成前缀树，所有共享前缀只存一次。它在查询时按前缀逐层下降，与哈希表形成了"空间换时间 / 时间换空间"的对照——下一节《词典的数据结构》会细讲。</span>

**按块存储（blocking）**则是不分词项的粗粒度方案：把词典按每 $k$ 个词项分块，块首词项存完整字符串，块内其余词项只存"共享前缀长度 + 后缀"。查询时先二分到块首（块首完整可比较），再在块内顺序比较。它牺牲一点查询速度（块内要顺序扫），换回显著的词典缩小。

**辨析｜易错点：压缩后的词典"不能直接二分"。** 前端编码让词典不再是"定长记录数组"，无法从下标直接定位到第 $i$ 个词项。要么用"块首索引"（每个块一个指针）辅助二分，要么退回顺序扫描。**压缩与随机访问是一对矛盾，工程上永远在两者间取平衡。**

## 4 公式解析：词典压缩的收益度量

用数字看看前端编码能省多少。设词典有 $V$ 个词项，平均词长 $L$ 字符，平均共享前缀长度 $P$，前缀长度字段占 $S$ 字节，则压缩前后词典的字符串区大小：

$$S_{\text{raw}} = V \times L, \qquad S_{\text{comp}} = V \times (L - P + S)$$

三步拆解：

- **第一步，读 $S_{\text{raw}}$**：未压缩时每个词项存完整 $L$ 字符。
- **第二步，读 $S_{\text{comp}}$**：压缩后每个词项只存"非共享后缀 $L - P$"加上记录前缀长度的字段 $S$（通常 1–2 字节）。
- **第三步，算压缩比**：$\frac{S_{\text{comp}}}{S_{\text{raw}}} \approx \frac{L - P + S}{L}$。IIR 给过一个量级：英文文本里 $P$ 常占 $L$ 的 40% 以上，压缩比可到 50%–60%——**词典字符串区直接砍掉近一半**。

注意这里的细节：**前缀长度字段本身也要空间**。当共享前缀极短时（$L - P$ 接近 $L$），前端编码反而可能不划算——但字典序下共享前缀普遍长，所以整体仍是大赚。

## 5 压缩的工程约束

词典压缩不是"压得越狠越好"，三个约束决定压缩策略的选择：

- **查询速度**：压缩引入了"先解压再比较"的开销。对位于查询热路径的词典，极端压缩（如前端编码+块存储叠加）可能让每次词项查找都慢一截。**热度越高的索引，越倾向轻压缩。**
- **更新频率**：动态索引频繁合并，压缩数据每次合并都要重新编码。压缩比越高，重编码越贵——动态场景常选择"适度压缩"。<span class="marginnote">这是压缩策略与《动态索引》一篇的联动：<strong>高压缩比 = 高写放大</strong>。动态系统在压缩与更新成本之间另有一层权衡。</span>
- **硬件时代**：当内存便宜、磁盘是 SSD 时，"压缩省内存"的收益下降；但"压缩减 IO"的收益在磁盘访问更贵时上升。压缩策略是跟着硬件成本走的活参数。

## 6 小结

- **压缩的终极目标是速度**：以 CPU 换 IO，压缩悖论让它常常净赚。
- **词典压字符串**：利用字典序下的**共享前缀**，前端编码按块存储是主力手段。
- **压缩与随机访问矛盾**：压缩后词典不能直接二分，需块首索引辅助。
- **压缩比量级**：英文词典字符串区可压缩至原来的一半左右，$S_{\text{comp}}/S_{\text{raw}} \approx (L-P+S)/L$。
- **工程约束**：查询热度、更新频率、硬件成本共同决定压缩深度。

在下一节，我们转战索引的另一半——倒排表是几十亿个整数的长列表，压缩它的手段与词典完全不同，这就是**倒排表压缩：可变字节编码与 γ 编码**。
