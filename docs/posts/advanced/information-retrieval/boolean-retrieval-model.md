## 为什么从布尔检索开始

上一篇《倒排索引的一个例子》已经带你逛过莎士比亚文集的倒排索引：**"Brutus" 对应一张文档编号表，查 "Brutus AND Caesar" 就是把两张表求交集**。但那时我们只看了数据，还没把它上升成"模型"。这一篇要补上这层抽象——**检索模型（retrieval model）**，也就是系统凭什么判定"这篇文档满足你的查询"。

为什么偏偏从布尔模型讲起？因为它是历史上第一个、也是最简单的检索模型：把"检索"还原成**逻辑运算**。它虽然老了，却从没退出过舞台——今天的数据库 SQL 查询、电商后台的精确筛选、甚至 Lucene 的底层 query API，骨子里都还是布尔检索。<span class="marginnote">Lucene 的 BooleanQuery 允许把词项用 MUST / SHOULD / MUST_NOT 组合，正是布尔模型在现代引擎里的直接后裔。学懂这一篇，你在 Lucene 里写复杂查询时会突然明白它"为什么长这样"。</span>更重要的是，布尔模型暴露了"模型"的两个核心问题——**文档如何表示**、**相关性如何判定**——而这两问将贯穿我们后面所有的检索模型。它还隐含着一条贯穿本博客的暗线：把"一篇文章是否相关"压扁成"词项是否属于文档"的二值判断，正是第一级《集合》里"元素与集合的属于关系"在工业场景的第一次实战——当年学的集合语言，今天开始派上用场。

## 1 文档表示：词项-文档关联矩阵

布尔模型把每篇文档看成**一组词项的集合**：它不关心词出现了几次，只关心"有没有出现"。于是整本文集可以被写成一张 0/1 矩阵——**词项-文档关联矩阵（term-document incidence matrix）**：

$$M[t][d] = \begin{cases} 1 & \text{词项 } t \text{ 出现在文档 } d \text{ 中} \\ 0 & \text{否则} \end{cases}$$

矩阵的行是**词项（term）**，列是**文档（document）**，格子 $M[t][d]$ 非 0 即 1。例如前面那部莎翁全集，取其中几篇与几个词项：

| 词项 | 文档1 | 文档2 | 文档3 | 文档4 |
| --- | --- | --- | --- | --- |
| Brutus | 1 | 1 | 0 | 1 |
| Caesar | 1 | 1 | 0 | 1 |
| Calpurnia | 0 | 1 | 0 | 1 |
| mercy | 0 | 0 | 1 | 0 |

这个例子藏着两个重要观察。其一，**矩阵极度稀疏**：一篇真实文档只含数万个词项，而词典常有百万级词项，绝大多数格子是 0；存储整张矩阵的代价是灾难性的。其二，**每一行其实都是一张"文档编号表"**——把行里所有 1 所在的列号收集起来，就得到了词项对应的倒排表。这两点正是下一篇《倒排索引的结构》要解决的：倒排索引就是"只存 1，不存 0"的稀疏矩阵压缩存储。

## 2 布尔查询：把用户需求翻译成逻辑式

布尔模型把**查询（query）**定义为词项用三种逻辑运算符组合而成的表达式：

- **AND（与）**：文档必须同时包含两侧词项。例如 Brutus AND Caesar。
- **OR（或）**：文档至少包含一侧词项。例如 Brutus OR Caesar。
- **NOT（非）**：文档不得包含该词项。例如 NOT Caesar。

**核心概念：布尔模型（Boolean model）**：文档要么**满足**查询（返回），要么**不满足**查询（不返回），没有中间地带——结果集 $S$ 就是文档集合 $D$ 中"使查询为真"的那个子集。

$$S = \{ d \in D \mid \text{查询 } q \text{ 在 } d \text{ 上取值为真} \}$$

**重点：布尔模型是"集合运算"，不是"打分排序"。** 它把相关性当成一个二值谓词——一篇文档相关还是不相关，由逻辑式判定，系统不做任何程度上的比较。这既是它简单可靠的原因，也是它最大局限的根源（见第 5 节）。

**辨析｜易错点：NOT 的语义随实现而变。** 数学上 Brutus AND NOT Caesar 是"包含 Brutus 且不含 Caesar 的文档"，但工程上常把 NOT 实现为"从全集里排除"——在分布式检索中，这需要额外的集合差运算，代价高昂；而不同引擎对 NOT Caesar 单独出现（不带 AND）的处理也不一致。写查询时务必查清你所用引擎的约定，别想当然。

## 3 查询处理：把逻辑式翻译成算法

有了倒排表，查询处理就变成了**对若干有序链表的集合运算**。以 Brutus AND Caesar 为例：先取出两行倒排表，再求交集。

用上一篇文章的数据：$L_{\text{Brutus}} = [1, 2, 4, 11, 31, 45, 173, 174]$，$L_{\text{Caesar}} = [1, 2, 4, 5, 6, 16, 57, 132]$，交集为 $[1, 2, 4]$。<span class="marginnote">这两串数字是 IIR 教材第一章的经典例子——Brutus 出现在 8 篇文档、Caesar 出现在 8 篇文档，而同时出现的只有 3 篇。教材用整整一章来演示：看似简单的交集，做对了就能支撑整个布尔检索。</span>

两个有序链表求交集，用**双指针合并（merge）**即可，只扫描一遍：

```python
def intersect(L1, L2):
    i = j = 0
    result = []
    while i < len(L1) and j < len(L2):
        if L1[i] == L2[j]:
            result.append(L1[i]); i += 1; j += 1
        elif L1[i] < L2[j]:
            i += 1
        else:
            j += 1
    return result

intersect([1, 2, 4, 11, 31, 45, 173, 174],
          [1, 2, 4, 5, 6, 16, 57, 132])   # [1, 2, 4]
```

每次循环都把指针指向编号较小的那条链表前进一位：两指针相遇处就是共同文档，编号较小的那个"追不上"时往前赶。**因为两条链表都按文档编号升序，这个算法绝不会漏掉任何交集元素，也不会重复扫描任何元素。**

用具体的一步一步来看指针如何前进（$L_1$ 指 Brutus，$L_2$ 指 Caesar，加粗为当前指针所指）：

| 轮次 | 指针1 | 指针2 | 比较 | 动作 |
| --- | --- | --- | --- | --- |
| 1 | **1** | **1** | 相等 | 收入结果，双双前移 |
| 2 | **2** | **2** | 相等 | 收入结果，双双前移 |
| 3 | **4** | **4** | 相等 | 收入结果，双双前移 |
| 4 | **11** | **5** | $11 > 5$ | 指针2 前移 |
| 5 | **11** | **6** | $11 > 6$ | 指针2 前移 |
| 6 | **11** | **16** | $11 < 16$ | 指针1 前移 |
| 7 | **31** | **16** | $31 > 16$ | 指针2 前移 |
| 8 | **31** | **57** | $31 < 57$ | 指针1 前移，直至 $L_1$ 耗尽 |

每次比较，编号较小的指针一定前进，于是两指针的总前进步数**恰好等于两表长度之和**——这正是下一节公式 $O(|L_a| + |L_b|)$ 的直觉来源。

OR 运算更简单——求并集同样是双指针合并，只是逻辑改为"把较小者直接写入结果"。NOT 则借助集合差实现：A AND NOT B 可以先求出全集与 $B$ 的差集，再与 $A$ 相交。

## 4 公式解析：AND 合并为什么是 O(x + y)

把上面的算法抽象成一个代价公式，这是本模型最值得记住的一条：

$$C_{\text{intersect}}(L_a, L_b) = O\bigl(|L_a| + |L_b|\bigr)$$

三步拆解这个式子：

- **第一步，读懂 $|L_a|$ 与 $|L_b|$**：它们分别是词项 $a$、$b$ 的倒排表长度，即包含 $a$ 的文档数（文档频率 $df_a$）与包含 $b$ 的文档数（$df_b$）。在矩阵语言里，就是两行里 1 的个数。
- **第二步，为什么是"加"而不是"乘"**：朴素的集合交集（把 $L_a$ 的每个元素都去 $L_b$ 里查一遍）代价是 $O(|L_a| \cdot |L_b|)$——乘起来。而双指针合并利用"两表都有序"，每步只让一个指针前进，总共最多走 $|L_a| + |L_b|$ 步，于是从乘法塌缩成加法。**排序带来的有序性，把交集从 $O(nm)$ 降到了 $O(n+m)$，这是整个倒排检索的算力根基。**
- **第三步，解释系数**：公式里没有常数因子，因为每个元素至多被比较几次。真实系统中链表长度往往很不均衡（比如高频词"the"的倒排表有百万级长度），此时一个工程技巧是**按表长从小到大依次合并**（先并短的，把中间结果尽量压小），这也是后续查询优化里"查最小倒排表优先"策略的来源。

**辨析｜易错点：O(x + y) 是指针步数，不是内存比较次数意义上的"快"。** 在内存里跑，它确实快；但每条链表可能跨多个磁盘页，实际 I/O 才是瓶颈。工业实现里会给倒排表加**跳表指针（skip pointers）**以跳过不必要的位置——那是第二篇《倒排索引的结构》与后面《跳表与跳表指针》会展开的优化，你现在只需记住：算法的步数是上界，物理世界的页命中率才是真实边界。

## 5 布尔模型的局限

模型简单，代价是把"相关性"这个大问题压扁成了二值判断。IIR 教材用一句话点破它的尴尬：查询 Romeo AND Juliet 返回的文档不保证质量，而用户真正想问的往往是"我要一篇**关于**罗密欧与朱丽叶的文章"——这是一个**程度**问题，不是**有无**问题。布尔模型的三个硬伤：

- **不支持排序（ranking）**：结果集里所有文档地位平等，无法回答"哪篇最相关"。这对 Web 搜索是致命的——用户几乎不会逐页翻看未排序的结果。
- **丢失词频信息**：矩阵里只有 0 和 1，词在文档中出现几次、出现在标题还是正文，全被抹掉。而这些恰恰是相关性的强信号，要到第四篇《TF-IDF 权重机制》才被捡回来。
- **查询表达不友好**：普通用户写不出 (Caesar AND Brutus) OR (Romeo AND Juliet) 这种布尔式；即使会写，漏掉一个同义词就漏掉一片相关文档。

**辨析｜易错点：布尔模型"没有相关性程度"不等于"没有用"。** 恰恰相反，当查询**意图明确、词项精确**时（人名、产品型号、法规条文、数据库主键），布尔检索又快又准，零幻觉、零排序开销。理解它"在哪些场景是王者、在哪些场景是青铜"，比单纯背诵局限更重要——这也是为什么今天的搜索系统普遍采用"布尔召回 + 排序模型精排"的两级架构。

**辨析｜易错点：运算符优先级在系统间并不统一。** 数学与多数教科书约定 AND 的优先级高于 OR（Romeo AND Juliet OR Tybalt 读作 Romeo AND (Juliet OR Tybalt)），但不同检索系统对此的处理各不相同——有的规定一律从左到右，有的要求用户显式加括号。真实世界里的教训：**查询表达式里的括号是免费的，多写括号省去一切歧义。** 这也是为什么绝大多数搜索 API 推荐用嵌套对象（如 `{"bool": {"must": [{"term": {"text": "romeo"}}, {"term": {"text": "juliet"}}]}}`）而不是裸字符串来表达布尔逻辑。

## 6 小结

- **检索模型**回答两个问题：文档如何表示、相关性如何判定；布尔模型是第一代答案。
- **文档表示**是词项-文档关联矩阵：0/1 稀疏矩阵，行是词项、列是文档。
- **查询**是布尔表达式，结果集是使查询为真的文档集合；**相关性是二值谓词，不产生排序**。
- **查询处理** = 对有序倒排表做集合运算；AND 用双指针合并，代价 $O(|L_a|+|L_b|)$，有序性把 $O(nm)$ 降为 $O(n+m)$。
- **局限**：无排序、丢词频、查询难写；但在意图明确的高精度场景（数据库、电商筛选）它依然是不可替代的基石。
