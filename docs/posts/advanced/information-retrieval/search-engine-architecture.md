## 为什么从"全景"开始

到此为止，我们已经掌握了检索的每一块积木：倒排索引、排序模型、语义向量、查询理解、重排……但积木不等于建筑。**搜索引擎是一个"离线 + 在线"双体系统**：离线部分负责"把整个文档集读进来、处理、建成索引"（慢，小时级），在线部分负责"收到查询、毫秒级返回结果"（快，毫秒级）。这两半有不同的时间尺度、不同的资源约束、不同的失败模式——**理解它们的边界与协作，是理解搜索系统的第一步**。

这篇用一张全景图把十篇的内容串起来：**文档从哪来、怎么进索引、索引怎么服务查询、查询怎么走完一条链路**。<span class="marginnote">搜索系统架构的两条铁律，贯穿本系列全部工程主题：<strong>一是"离线做重、在线做轻"</strong>——能离线算好的（索引、向量、模型特征）绝不放在线算；<strong>二是"延迟是硬约束"</strong>——在线查询的每一步都要在几十毫秒预算内完成。理解了这两条铁律，搜索引擎的每个组件选择都变得可解释。</span>

## 1 离线与在线的分工

搜索引擎分成两个时间尺度完全不同的世界：

| 维度 | 离线（offline） | 在线（online） |
| --- | --- | --- |
| 任务 | 爬取、处理、建索引、训练模型 | 查询处理、检索、排序、返回 |
| 时间尺度 | 分钟到小时 | 毫秒 |
| 数据量 | 全量文档 | 单条查询 |
| 资源 | 大批量、可重试 | 低延迟、不可重试 |
| 失败代价 | 低（重建即可） | 高（用户流失） |

**重点：离线与在线的边界，由"什么可以预先算好"决定。** 倒排索引是离线建好的（词项 → 文档的映射）；文档向量是离线算好的；排序模型是离线训练好的。**在线只做"查预先算好的东西 + 轻量计算"——绝不在查询路径上做重活**。<span class="marginnote">这个分工的深层原因，是<strong>延迟的非对称性</strong>：离线花 10 分钟建索引没问题（没有人等着），在线花 100 毫秒排序就是灾难（用户在等）。所以"能预先算的都预先算"成为铁律——甚至"预先算好"的范围还在不断扩大（离线预计算更多特征、离线预生成更多结果变体）。</span>

## 2 离线的完整流水线

文档从"原始状态"到"可检索状态"，经过一条完整流水线：

1. **爬取/采集（crawling）**：抓取网页、接收文档源——把世界上的文本搬进来。
2. **解析与清洗（parsing）**：提取正文、去 HTML 标签、去噪、编码归一。
3. **分析与索引（analysis & indexing）**：分词、去停用词、词干化/规范化、建倒排索引（含压缩与跳表）。
4. **向量化（embedding）**：文档编码成稠密向量，建 ANN 索引。
5. **辅助结构**：正排索引（文档内容存储）、文档元数据（时间、权威性）、特征库（排序特征离线算好）。
6. **模型训练**：学习排序模型、重排模型、查询理解模型——离线训练、在线推理。<span class="marginnote">离线流水线有一个关键工程点：<strong>它必须能"增量更新"</strong>（新文档进来不能全量重建）。这就是第二篇《动态索引》讲的辅助索引与合并策略——离线不是"一次建好"，而是"持续维护"。"爬取 → 解析 → 索引 → 合并"是一个不断转动的环，而不是一条结束的线。</span>

**重点：离线的产出不是"一份索引"，而是"一整套预先算好的可查询资产"——倒排索引、ANN 索引、正排存储、特征库、模型。** 在线系统站在这些资产上，才能毫秒级响应。

## 3 在线查询的完整链路

在线侧，一条查询从"用户输入"到"结果返回"走过整条链路：

1. **查询理解**：纠错、分词、意图分类、改写（第九篇）——把原始输入变成"可检索的查询"。
2. **召回（retrieval）**：走倒排索引（BM25）与 ANN 索引（嵌入）双路召回候选——几百万文档 → 几百个候选。
3. **融合（fusion）**：RRF 等策略合并两路召回（第八篇）。
4. **粗排/精排（ranking）**：级联排序——轻量模型粗排几百个，交叉编码器精排前几十个（第八篇、第十篇后续）。
5. **后处理（post-processing）**：去重、过滤（时效、安全）、多样性调整、摘要生成。
6. **返回**：拼装结果页。<span class="marginnote">这条链路的每一步都有延迟预算：查询理解 5ms、召回 10ms、融合 2ms、粗排 5ms、精排 20ms、后处理 3ms——加起来约 45ms。<strong>"预算分解"是搜索系统工程的核心方法：给每步设预算，谁超了优化谁</strong>。这条链路每一步都在本系列里展开过——现在你看到的是一次"全景串联"。</span>

**重点：在线链路的本质是"逐步缩小"——理解后是"查询"、召回后是"候选"、精排后是"答案"。** 每一步的输入是上一步的输出，每一步都在"更精、更少"的方向收敛。

## 4 公式解析：延迟预算的分配

用公式看延迟预算如何决定系统设计。设总延迟预算为 $T_{\text{budget}}$，链路有 $n$ 步，每步延迟为 $t_i$：

$$T_{\text{total}} = \sum_{i=1}^{n} t_i \le T_{\text{budget}}$$

三步拆解：

- **第一步，读约束**：总延迟是各步延迟之和，必须小于预算（如 50ms）——**预算是硬约束，超出即失败**。
- **第二步，看分配**：每一步的 $t_i$ 由"组件选型"决定——ANN 索引的 efSearch 设多宽（召回延迟）、精排模型用多大（精排延迟）、查询改写用不用 LLM（理解延迟）。**预算分配 = 组件选型的决策结果**。
- **第三步，看取舍**：预算有限，某步多花另一步就得少花——**"召回宽一点（多花）还是精排贵一点（多花）"是这个公式的日常博弈**。

**核心结论：搜索系统的所有组件选型，最终都受制于"延迟预算的分配"。** 没有预算约束的组件选型是不存在的——**每个"更快但更粗"与"更准但更慢"的选择，都是在分同一笔预算**。<span class="marginnote">一个工业实践：<strong>延迟预算不是静态的，而是按"查询价值"浮动的</strong>——高频导航查询预算紧（快为主），长尾复杂查询预算松（准为主）。系统用"查询性能预测 + 意图分类"（第九篇）动态决定预算分配。这就是为什么我们花两篇讲 QPP 与意图分类——它们不只是"理解查询"，还直接参与"资源调度"。</span>

## 5 搜索引擎架构的现代演进

经典架构（倒排索引 + 检索 + 排序）之上，现代搜索系统加了三层：

**语义层**：双塔检索、向量索引、重排模型——把"词面匹配"升级为"语义匹配"（第八篇）。
**知识层**：知识图谱、实体识别、结构化数据——把"文档检索"升级为"答案检索"（实体卡、知识面板）。
**生成层**：LLM 问答（RAG，第十三篇）、AI 搜索产品——把"结果列表"升级为"生成式回答"（第十四篇）。<span class="marginnote">这三层不是替代经典架构，而是叠加在它之上：<strong>经典索引与排序仍是地基，语义/知识/生成层在地基上提供更丰富的检索能力</strong>。现代搜索引擎是"经典检索 + 语义检索 + 知识 + 生成"的混合体——本系列每一篇都在为这张全景图添砖加瓦，第十篇（本篇起）就是把这砖瓦砌成建筑的施工图。</span>

**辨析｜易错点：搜索引擎 ≠ 一个算法，而是一个系统。** 很多人以为"搜索 = BM25"或"搜索 = 嵌入"——实际上搜索引擎是几十个组件的协同：理解、召回、融合、粗排、精排、后处理、缓存、调度。**任何单一组件都不是搜索引擎，组件的编排才是。** 本篇（及后续几篇）讲的就是这个"编排"。

## 6 数值算例：一条查询的延迟预算账单

把"延迟预算是硬约束"演算成一次链路预算。设一条查询的延迟预算 50ms，各环节的分配：

| 环节 | 预算 | 实际 | 超支？ |
| --- | --- | --- | --- |
| 查询理解（纠错/分词/改写） | 5ms | 6ms | 超 1ms |
| 双路召回（BM25 + ANN） | 12ms | 10ms | 省 2ms |
| 融合（RRF） | 2ms | 1ms | 省 1ms |
| 粗排（轻量模型） | 8ms | 7ms | 省 1ms |
| 精排（交叉编码器） | 20ms | 25ms | 超 5ms |
| 后处理（去重/过滤） | 3ms | 2ms | 省 1ms |
| 合计 | 50ms | 51ms | **超 1ms** |

三步读这张表：

- **看总账**：总延迟 51ms 超出预算 1ms——**预算超出即失败**（无论只超 1ms）。
- **看超支环节**：精排超 5ms 是最大超支项——**优化目标明确：压缩精排（模型更小、候选更少）**。
- **看"总预算 = 组件选型的映射"**：每个环节的实际耗时由选型决定（ANN 的 efSearch、精排模型大小、改写用不用 LLM）——**预算分解把"系统设计"翻译成"各环节的选型约束"**。

这个例子是"组件选型是预算分配的结果"的实证：**先定总预算，再分到各环节，每个环节的选型都要"在预算内做到最好"**。工程上超预算时，先压最大项（本例的精排），而不是平均砍——**"找最大项、消最大项"是延迟优化的第一原则**。

**辨析｜易错点：延迟预算是"端到端"的，不能只看核心检索。** 真实延迟包含"网络传输、网关、日志、渲染"等外围环节——核心检索只占一半。**预算分解要算上整个用户请求链路，否则"检索 30ms 达标"但"端到端 300ms"的真相会被掩盖**。工程上"端到端监控 + 环节级剖析"并用，才能看清延迟花在哪。

## 8 小结

- **双体系统**：离线（读世界、建索引、训练模型，小时级）+ 在线（收查询、毫秒返回，毫秒级）。
- **两条铁律**：离线做重、在线做轻；延迟是硬约束。
- **离线流水线**：爬取 → 解析 → 索引（倒排 + ANN + 正排）→ 特征 → 模型——一套可查询资产。
- **在线链路**：查询理解 → 双路召回 → 融合 → 级联排序 → 后处理——逐步缩小，收敛到答案。
- **延迟预算**：$T = \sum t_i \le T_{\text{budget}}$——组件选型是预算分配的决策结果。
- **现代演进**：语义层、知识层、生成层叠加在经典架构之上。

在下一节，我们聚焦离线流水线的"索引构建"环节——文档怎么变成索引，每一步做什么，这就是**索引构建流水线：文档处理、分词与索引更新**。
