## 为什么需要"块"

上一篇我们给出了内存式构建的完美方案：抽取二元组、全局排序、归并倒排表，代价 $O(T \log T)$。但它有一个我们反复强调的软肋——**排序的工作集必须装进内存**。当文集的词项实例数 $T$ 冲到十亿级，仅二元组就要 8 TB 内存时，全局排序连同它那 $O(T \log T)$ 的比较，会在物理上破产。

**基于块排序的索引构建（Blocked Sort-Based Indexing，BSBI）**是 IIR 第 4 章给出的第一个规模化方案。它的核心思想朴素到令人惊讶：**既然一口气排不完，那就切成能一口气排完的小块，各排各的，再把排好的小块归并起来。** 这是"分而治之"在索引构建里最标准的落地，也是数据库外排序（external sort）思想在信息检索里的直接应用。<span class="marginnote">BSBI 与数据库的"归并排序外排"（external merge sort）几乎是同一套流程：分块、块内排序、写盘、多路归并。你在数据库课程里学到的外排技巧，换一层皮就是 BSBI。这也是为什么我们建议把第三级《数据库》的外排序与这里对照着学。</span>

## 1 问题的规模：从"一趟"到"多趟"

先精确描述"装不下"这件事。内存式构建要把 $T$ 个二元组整体排序，需要 $O(T)$ 的存储；假设可用内存能装下约 $M$ 个二元组（更严格地说是排序中间态的工作集），那么**装得下的条件**是 $T \le cM$（$c$ 是排序临时缓冲的系数，工程上常取 1.5 左右）。

当 $T > cM$ 时，两条路摆在你面前：

- **换用外排序**：把全局排序交给磁盘感知的外排实现。可行，但通用外排不利用"我们的记录是 (termID, docID) 二元组"这一结构信息，显得笨重。
- **自定义分块流程**：利用索引构建的结构，把排序拆成"块内排序 + 块间归并"，并让每一块的产物直接就是"部分倒排索引"，方便后续合并。**BSBI 走的就是这条路。**

**重点：BSBI 的洞见在于，把"一次全局排序"换成"若干次块内排序 + 一次归并"，总比较次数不变（仍是 $O(T \log T)$），但单次内存占用从 $O(T)$ 降到了 $O(M)$。** 用可控的磁盘 I/O，换来了内存从"装不下"到"装得下"，这是规模化索引构建的第一桶金。

**辨析｜易错点：块（block）的大小由"内存"决定，不是由"文档"决定。** 初学者常把块理解成"文档的自然分组"（比如 1000 篇一组）。不对——块的大小上限是"这组二元组排序后放得进内存"，也就是约 $M$ 个二元组。**块是内存的切片，不是语料的切片。** 一篇超长文档甚至可能横跨多个块。

把数字填进去感受一下规模。设文集有 $T = 10^{11}$ 个词项实例（约 1 亿篇 × 每篇 1000 词），构建机内存预算 $M = 10^8$ 个二元组（约 0.8 GB 排序工作集）。于是块数 $b \approx T / M = 1000$，也就是说：内存式构建那"装不下的 800 GB 排序"被切成了 1000 块、每块 0.8 GB，分别排序后写 1000 个临时文件，最后用一次 1000 路归并收成全局索引。**1000 个文件句柄对一个现代操作系统是可管理的（可通过多趟归并进一步压低），而这正是"单个 800 GB 排序任务"与"1000 个 0.8 GB 小任务"在内存层面上的天壤之别。**

## 2 BSBI 算法：分块、排序、写盘、归并

BSBI 的主流程可以写成四步。设可用内存能容纳 $M$ 个二元组：

1. **分块读入**：把文档流切成若干块，每块大致对应 $M$ 个二元组，逐块读入内存。
2. **块内排序**：对当前块的二元组按 (termID, docID) 排序，并归并出该块内部的"部分倒排索引"（每词项一张有序倒排表）。
3. **写盘**：把这块的部分索引写入磁盘上的临时文件 `block_i`。
4. **归并**：全部块写完后，把 $b$ 个块的部分索引多路归并（k-way merge）成一份全局倒排索引，并在此过程中把词项统一映射进最终词典。

IIR 教材给 BSBI 的伪代码大致是这样：

```text
BSBI(collection, M):
    blocks = []
    while collection 未读完:
        读入约 M 个 (termID, docID) 二元组          # 1. 分块
        按 (termID, docID) 排序                     # 2. 块内排序
        归并成块内部分倒排索引，写入 block_i         # 3. 写盘
        blocks.append(block_i)
    return merge_blocks(blocks)                    # 4. 归并
```

以 $b$ 个块、每块内存 $M$ 为例，块内排序的总代价是 $b \cdot O(M \log M)$，而归并阶段把 $b$ 个有序流合成一个，代价约 $O(T)$（严格说是 $O(T \log b)$，见第 3 节）。总时间仍是 $O(T \log T)$，但**单次排序的内存从 $O(T)$ 降为 $O(M)$**——这就是"分块"的全部意义。<span class="marginnote">归并时若块数 $b$ 太大，单趟归并要同时打开 $b$ 个文件句柄，会碰系统文件描述符上限。工业实现通常做<strong>多趟归并</strong>（先把 $b$ 块并成 $\sqrt{b}$ 个，再并一轮），这也与数据库外排的做法一致。</span>

用一个具体的两块例子把"归并"看穿。假设两块部分索引里，"brutus" 的倒排表分别是：

```
块1：brutus → [(1,1), (2,3), (4,5), (11,1)]
块2：brutus → [(4,2), (31,1), (45,1), (173,1), (174,1)]
```

机械地把 docID 排序拼接，会得到 $[1, 2, 4, 4, 11, 31, 45, 173, 174]$——等等，$4$ 出现了两次？这正是归并必须做的第二件事：**当同一个 docID 在多个块里重复出现时（说明该文档的二元组跨了块边界），要把词频相加并合并成一个倒排项**。真正归并出来的结果是：

```
brutus → [(1,1), (2,3), (4,7), (11,1), (31,1), (45,1), (173,1), (174,1)]
```

**辨析｜易错点：归并"合并部分索引"不是"拼接倒排表"，也不是"机械合并 docID"。** 两个块的部分索引里，同一个词项各自有一张有序倒排表；归并是**把这两个有序表合并成一张更大的有序表**（真正的 k-way merge），并且**对跨块重复的 docID 做词频累加**——这是索引构建与普通排序最大的不同。前者保持有序、累加词频，后者若直接拼接会破坏有序性、并丢失词频信息，摧毁后续一切排序模型。**"归并 = 合并有序流 + 词频累加"，这是整个外部构建里最容易被写错的一步。**

## 3 公式解析：BSBI 的时空代价

把 BSBI 的代价完整写出来，和内存式对比着看：

$$T_{\text{BSBI}} = \underbrace{b \cdot O(M \log M)}_{\text{块内排序}} + \underbrace{O(T)}_{\text{归并}} = O(T \log T), \qquad S_{\text{内存}} = O(M)$$

四步拆解：

- **第一步，块数 $b$ 是什么**：$b \approx T / M$，即二元组总数除以每块能容纳的二元组数。它决定了要写多少个临时文件，也决定归并时要开多少个输入流。
- **第二步，块内排序的代价**：每个块做 $O(M \log M)$ 的比较，$b$ 个块合计 $b \cdot M \log M = (T/M) \cdot M \log M = T \log M$。
- **第三步，归并的代价**：把 $b$ 个有序流合成一个，每个元素进出堆一次，代价 $O(b \cdot T)$？不——归并时用堆选最小，每个元素比较 $O(\log b)$ 次，所以严格说是 $O(T \log b)$；但若采用"多趟归并"控制 $b$，工程上常近似为 $O(T)$。**无论哪种，归并都低于或等于块内排序的量级。**
- **第四步，时间与内存的平衡**：总时间 $O(T \log T)$ 与内存式完全相同，**没有为规模付出时间代价**；换来的是峰值内存从 $O(T)$ 降到 $O(M)$。这正是"用外存换内存"的典型收益结构——时间不涨，内存可控。

把上一步的数值代进去，还会看到一个反直觉的小红利：BSBI 的块内排序是 $T \log M$，而内存式全局排序是 $T \log T$；因为 $M < T$，所以**分块排序的总比较次数其实略少于一次性全局排序**——用上一节 $T = 10^{11}$、$M = 10^8$ 的数算，$\log_{10}$ 下 $T\log M$ 约为 $1.1 \times 10^{12}$，$T \log T$ 约为 $1.3 \times 10^{12}$，省了约 15% 的比较。当然，这点省下的 CPU 通常会被磁盘 I/O 的代价完全吞掉——但理解"分块不增时、反略减时"这一事实，能帮你破除"外部算法一定更慢"的直觉偏见。

**辨析｜易错点：$O(T \log T)$ 是"比较次数"的代价，不是"I/O 代价"。** BSBI 的真正成本增量在磁盘：每个块要写一次、归并时要读 $b$ 次。当 $T$ 巨大时，**磁盘 I/O 往往才是真正的瓶颈**，而不是 CPU 比较。教材里的复杂度刻画的是算法逻辑，工程上估算 BSBI 耗时，要按"每块写 $O(M)$、归并读 $O(T)$"的 I/O 字节数来算。

## 4 BSBI 的权衡与局限

BSBI 是教科书级的正确算法，但工业界仍会为两个问题皱眉：

- **归并的词项重排问题**：每个块在排序时都各自维护一份"词项 → termID"的局部映射；归并时，不同块里同一个词项可能顶着不同的 termID，需要统一。IIR 教材明确指出，BSBI 需要**在归并后做一次全局的词项重排**，这一步要额外扫描词典——这正是它相比下一篇 SPIMI 显得"重"的原因之一。
- **I/O 放大**：全流程"读文档 → 写块 → 读块 → 写最终索引"，加上归并时反复读，磁盘流量是数据本身的数倍。对单机 SSD 尚可接受，一旦索引规模需要分布式，BSBI 的"两趟式"就会被**基于 MapReduce 的索引构建**（后面《分布式索引构建》一篇）取代——在那里，块的排序和归并天然对应用 Map 与 Reduce 两个阶段。

关于第一个问题"词项重排"，看一个具体场景：块 1 遇到 `brutus` 时给它分配 termID = 5，块 2 遇到 `brutus` 时可能分配 termID = 7（因为各块独立扫描、独立分配）。归并时，两张 "brutus" 的倒排表在编号上对不上，必须查一份**全局词项表**把 5 与 7 统一成同一个 ID。IIR 教材明确指出，这一步"重排"需要在归并完成后额外扫描一遍词典，并重写所有倒排表中的 termID——**这是一次额外但线性的开销**，也正是 BSBI 相比 SPIMI 显得"重"的结构性原因。

**重点：BSBI 的价值不在"最佳"，而在"分水岭"。** 它是第一个让我们看清"外部构建长什么样"的算法：分块排序 + 归并，是后面 SPIMI、MapReduce 方案共同的主干。读懂了 BSBI 的块与归并，后面所有大规模构建算法都是在它的骨架上做"省一趟 I/O"或"省一张词项表"的优化。

**辨析｜易错点：BSBI 是"离线一次性"算法，与动态索引无关。** 它假设文集是静态的、索引从零构建。真实搜索引擎的索引天天有新文档加入，用的是**动态索引**（辅助索引 + 合并，见《动态索引》一篇）。两者解决的是不同问题：BSBI 解决"初始全量构建的内存不足"，动态索引解决"持续增量更新的即时性"——别把"构建"与"更新"混为一谈。

所以"什么时候用 BSBI"的答案也很清晰：**当你要给一个静态的大文集做初始索引、而单机内存装不下全局排序时**——典型如学术语料库的一次性建库、离线文档库的批量索引、搜索引擎新抓取数据集的首次全量构建。它不需要分布式集群，一台配了大内存的机器加若干临时磁盘空间就能完成；等规模大到单机都吃力，才轮到后面的 MapReduce 方案登场。

## 5 小结

- **BSBI 的流程**：分块读入 → 块内排序 → 写盘 → 多路归并；把"一次全局排序"拆成"块内排序 + 块间归并"。
- **代价**：时间仍为 $O(T \log T)$，峰值内存从 $O(T)$ 降到 $O(M)$——用磁盘 I/O 换内存可控。
- **块的大小由内存决定**，是"内存的切片"而非"语料的切片"；块数 $b \approx T/M$。
- **归并是合并有序流**，不是拼接倒排表；需要处理跨块的 termID 重排。
- **真正的瓶颈在磁盘 I/O** 而不在比较次数；它是分布式构建（MapReduce）与前一篇内存式构建之间的分水岭。
- **词项重排**：归并后须按全局词项表统一各块的 termID，是 BSBI 相比 SPIMI 多出的结构性开销。
- **适用场景**：静态大文集的初始全量构建——单机内存装不下全局排序时，"一台大内存机器 + 临时磁盘"即可完成。
- **与 SPIMI 的衔接**：BSBI 用排序换内存可控，SPIMI 用哈希换"少一趟词项重排"，两者互为镜像——下一篇见分晓。

在下一节，我们将看到 BSBI 的"表亲"——**基于哈希的单遍内存扫描构建（SPIMI）**：它不排序、只哈希，省掉词项映射与归并重排，为内存受限的流式索引带来新的可能性。
