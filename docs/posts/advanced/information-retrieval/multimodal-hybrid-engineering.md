## 为什么从"工程"开始

前三篇分别讲了多模态检索的概述、CLIP 表示、图像检索、视频检索——它们是零件。但真实的检索产品不是"一个模型"，而是"把多模态组件装进一个可服务的系统"。这一篇回答工程问题：**怎么把文本检索、图像检索、视频检索整合进一个统一系统？多模态查询（图 + 文）怎么处理？融合与评测怎么做？**

多模态混合检索系统的工程实践，本质是把本系列的架构智慧（两级、混合、级联、缓存、评测）与多模态组件（CLIP 编码、ANN 索引、跨模态重排）组合成"一个可扩展、可维护、可评测的真实系统"。<span class="marginnote">多模态检索系统的工程复杂度，比单模态高一个维度：<strong>它要管理"多种模态的索引"（文本索引 + 图像索引 + 视频索引）、"多种查询形态"（纯文本、纯图像、图文混合）、"多种匹配逻辑"（文本-文本、文本-图像、图像-图像）</strong>。好的系统设计，是用"统一的表示空间 + 统一的检索框架"把这些复杂性"规范化"——让多种模态共享一套索引与检索管道，而不是每种模态一套独立系统。</span>

## 1 统一表示空间：多种模态一个空间

多模态混合系统的第一设计决策：**所有模态（文本、图像、视频）都映射到同一个向量空间**。

用 CLIP 家族的模型：文本 → 文本向量、图像 → 图像向量、视频关键帧 → 图像向量——**都进同一个 $d$ 维空间**。于是：

文搜图 = 文本向量 × 图像向量。
图搜文 = 图像向量 × 文本向量。
图搜图 = 图像向量 × 图像向量。

**重点：统一表示空间让"跨模态检索"变成"同一空间里的向量匹配"——一个空间，所有检索形态。** 这是多模态混合系统的"规范化核心"：多样性来自"怎么编码"，统一性来自"一个空间 + 一套检索"。<span class="marginnote">统一表示空间的工程收益巨大：<strong>一个 ANN 索引可以同时索引图像与文本（混合索引），一个检索管道服务所有查询形态，一个缓存策略覆盖所有检索</strong>——基础设施一套，多模态复用。这个"统一空间 + 统一基建"的设计，让多模态系统从"多个系统的拼接"变成"一个系统的多面"。</span>

## 2 多模态查询：图文混合怎么处理

用户的多模态查询有两种形态，各有处理方式：

**纯文本/纯图像**：单一模态查询——直接编码对应模态，走统一检索。
**图文混合查询**："一张沙发的照片 + 想要红色的"——**多模态信息怎么融合进一个查询表示？**

图文混合查询的处理方式：

1. **跨模态融合模型**：把图 + 文一起喂给多模态编码器（如多模态 Transformer），生成"融合查询向量"。
2. **多路检索融合**：图像路检索 + 文本路检索，各自结果用 RRF 融合（第八篇）。
3. **加权查询**：查询 = 文本向量 + $\alpha$ × 图像向量，在统一空间里直接匹配。

**重点：图文混合查询 = "多模态信息合成一个查询" 或 "多路检索后融合"——前者靠融合模型，后者靠融合策略。** 两条路各有取舍：融合模型端到端更强但更贵，多路融合简单可解释但丢交互。<span class="marginnote">图文混合查询是"多模态检索"比"单模态检索"独特的地方：<strong>查询本身是多模态的——用户给一张图 + 一句修改（"这个款式，换成红色"）</strong>。工业上这个需求在电商搜索很常见（拍同款 + 改颜色）。现代解法倾向"多模态大模型"：直接把图和文一起交给大模型，让它生成"标准查询"或直接做匹配——多模态检索与多模态大模型的结合，是当前的前沿（与第十三篇的 RAG 汇合）。</span>

## 3 多路召回与融合

多模态系统的召回，天然是多路的：

**文本路**：查询的文本部分走文本索引（BM25 / 文本向量）。
**图像路**：查询的图像部分走图像 ANN 索引。
**视频路**：查询走视频索引（时序表示）。
**元数据路**：标签、类目、标题走结构化检索。

多路召回的结果用 **RRF**（第八篇）或加权融合合并——**每路召回一个子集，融合成一个候选池，再统一精排**。

**重点：多模态系统的召回是"多路并行"的——每路管一种模态的匹配，融合策略决定"各路怎么合成"。** RRF 的"只认排名"特性在这里尤其合适：文本分、图像分、视频分的量纲完全不同，只有排名可比。<span class="marginnote">多路召回与 RRF 的结合，是第八篇"混合检索"在多模态的扩展：<strong>第八篇混合的是"稀疏 + 稠密"（两路文本），这里混合的是"文本 + 图像 + 视频"（多路模态）</strong>——框架不变（多路召回 + RRF 融合），路数变多。理解了 RRF 的普适性，你就理解了为什么它是现代检索融合的事实标准——它几乎不挑"路"的性质。</span>

## 4 公式解析：多模态系统的架构账本

多模态混合系统的架构设计，可以用一个"总成本"账本看清楚。设 $M$ 种模态、每种模态 $N_m$ 个对象，统一向量维度 $d$：

$$\text{总索引} = \sum_{m=1}^{M} N_m \times d \times \text{字节}, \qquad \text{查询成本} = \underbrace{\text{查询编码}}_{\text{多模态}} + \underbrace{\text{ANN 检索}}_{M \text{ 路}} + \underbrace{\text{融合 + 精排}}_{\text{跨模态}}$$

三步拆解：

- **第一步，读索引规模**：每种模态的对象都进索引，总量是各模态之和——**统一空间让索引合并（一个 ANN 索引装所有模态），省掉"每模态一个索引"的重复基建**。
- **第二步，读查询编码**：图文混合查询要编码多个模态——**查询侧的编码成本随"查询模态数"上升**。
- **第三步，读检索成本**：$M$ 路召回 + 融合 + 跨模态精排——**每加一种模态，召回多一路、精排多一点**，但共享的 ANN 基建把增量压到最小。

**核心结论：统一表示空间让"多模态"的边际成本降到"只加一种编码器 + 一路召回"——基建共享是多模态系统可扩展的关键。**<span class="marginnote">这个"边际成本"视角指导架构决策：<strong>要不要加一种新模态，看"索引增量 + 一路召回 + 一路精排"的边际成本</strong>——如果共享基建做得好（统一空间 + 统一 ANN），加模态的边际成本很低；如果每种模态一套独立系统，加模态就是翻倍成本。工程上"统一基建"与"独立模态系统"的选择，本质上是在比"共享的节省"与"隔离的灵活"。</span>

## 5 评测与运营

多模态混合系统的评测与运营，有几个工程要点：

**分模态评测**：文本检索、图像检索、视频检索各自评测（Recall@K、NDCG）——**不要用一个总指标掩盖某个模态的短板**。
**跨模态评测**：混合查询（图文）的端到端评测——标注图文混合查询的相关性，贵且难。
**在线监控**：分模态的延迟、吞吐、缓存命中率、检索质量——**多模态系统的运营，是"每种模态一张仪表盘"**。
**持续更新**：不同模态的更新频率不同（文本快、图像中、视频慢）——索引更新策略要按模态差异化。<span class="marginnote">多模态系统的"分模态监控"是工程纪律：<strong>一个多模态系统出了质量问题，第一件事是"定位到哪个模态"</strong>——是图像路召回崩了，还是文本路精排慢了，还是视频路索引过期了？分模态的指标、日志、报警，是快速定位的前提。没有分模态监控的多模态系统，出问题时就像"在黑箱里找一根断了的线"。</span>

**辨析｜易错点：多模态 ≠ 多模型堆叠，系统要"统一编排"。** 一个常见的反模式是把文本检索、图像检索、视频检索各建一套独立系统，再用一个网关"转发"——**这不是多模态检索系统，是三个单模态系统拼在一起**。真正的多模态系统，是"统一表示空间 + 统一检索框架 + 多模态编码器插拔"——**模态的多样性被"表示层"吸收，检索与工程层保持统一**。理解这个"表示统一、工程复用"的设计哲学，是多模态系统架构的钥匙。

## 6 小结

- **统一表示空间**：所有模态进同一个向量空间——"一个空间，所有检索形态"，基建一套多模态复用。
- **多模态查询**：纯模态直接编码；图文混合 = 跨模态融合模型（端到端）或 多路检索融合（可解释）。
- **多路召回融合**：文本/图像/视频/元数据多路并行，RRF 融合——框架与第八篇混合检索同构，路数变多。
- **架构账本**：统一空间让"加模态"的边际成本 = 编码器 + 一路召回——基建共享是可扩展关键。
- **评测与运营**：分模态评测与监控；统一编排而非多系统拼接。
