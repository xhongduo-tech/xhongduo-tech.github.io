## 为什么从"流水线"开始

上一篇把搜索引擎切成"离线 + 在线"两半。在线链路的性能，完全建立在离线产出的索引质量之上——**索引里有什么，在线就只能搜到什么**。而索引不是"一次建成"的：文档每天都在新增、更新、删除，索引必须持续演进。这条"把文档持续变成索引"的流水线，就是搜索系统最底层的工程——**它决定了"能搜到什么"这个搜索系统的第一性问题**。

本篇把索引构建流水线拆开：**文档处理（清洗与解析）→ 文本分析（分词与规范化）→ 索引构建（倒排 + 向量）→ 索引更新（增量与合并）**。每一环都影响最终能搜到什么、搜得多好。<span class="marginnote">索引构建流水线的定位，是前面多篇技术的"装配线"：<strong>第二篇的 SPIMI/BSBI（怎么建索引）、中文检索的分词（怎么切词）、第四篇的权重（怎么算词权重）、第八篇的向量化（怎么算文档向量）——全部在这里汇集成一条自动化的流水线</strong>。理解流水线，等于把这些散落的技术"装"进了真实的系统。</span>

## 1 文档处理：从原始文本到干净正文

流水线的第一站是"让文档变得可分析"。原始文档是脏的：

**HTML/PDF/Word** 等格式带标签、带排版噪声——要去标签、提取正文。
**编码问题**：字符编码不一致（GBK/UTF-8）、乱码——要归一。
**噪声内容**：导航栏、广告、评论、模板文本——要识别并剥离，否则它们会污染索引（搜到一堆"登录""注册"）。

**重点：文档清洗的质量，直接决定"索引里有没有垃圾"。** 一个没洗干净的任务，会让"导航栏的常见词"占据倒排表的头部——**清洗是索引质量的第一道闸门**。<span class="marginnote">工业上"正文提取"是一门精细活：<strong>网页正文提取算法（如 Readability、Boilerpipe）用 DOM 结构与文本密度判断"哪部分是正文"</strong>。模板检测（template detection）专门对付"整个网站的页脚都是同一段话"这类问题——因为模板内容会污染统计信号（IDF、词频）。清洗得越干净，后面的排序模型看到的数据越真实。</span>

## 2 文本分析：分词、停用词与规范化

干净文本进入**分析器（analyzer）**，决定"文档被切成哪些词项、哪些词项进索引"。关键步骤：

**分词（tokenization）**：把文本切成词项——英文按空格/标点，中文按分词器（第三篇）。
**规范化（normalization）**：大小写统一、全角半角、连字符处理、词干化/词形还原（"running" → "run"）——让"同一语义的不同形式"映射到同一词项。
**停用词（stop words）**：过滤 "的""了" 等无区分度词——减少索引体积、降低噪声。

**辨析｜易错点：规范化是"检索质量 vs 信息保留"的权衡。** 词干化让 "connect" 与 "connection" 共享词项（召回好），但可能让 "university" 与 "universe" 也被错误合并（精确受损）。**现代系统对规范化越来越克制**——用轻量规范化（大小写）保证基本召回，用"原形保留 + 同义扩展"处理变体，避免过度词干化损害精确性。<span class="marginnote">分词与规范化的"一致性"问题（中文检索篇强调过）在这里以工程形态出现：<strong>索引侧分析器与查询侧分析器必须用同一套配置</strong>——Lucene/Elasticsearch 用"同一分析器处理索引与查询"保证词项对齐。这个"同源分析"是检索召回一致性的地基。</span>

## 3 索引构建：倒排、正排与向量

分析完的词项，进入三路索引构建：

**倒排索引**：词项 → 文档列表（含词频、位置）——用 SPIMI/BSBI 构建，用压缩与跳表优化（第二篇）。
**正排索引**：文档 ID → 文档内容（标题、摘要、字段）——用于结果展示与字段检索。
**向量索引**：文档 → 稠密向量（嵌入模型离线编码）→ ANN 索引（IVF/HNSW）——语义召回的基础（第八篇）。

**重点：三路索引是"同一文档的不同视图"——倒排管词面匹配、正排管内容取用、向量管语义匹配。** 一次文档处理，产出三种索引，在线查询按需取用。<span class="marginnote">三路索引的构建顺序有讲究：<strong>先做文本分析（分词/规范化），再做倒排（词项级）；正排是"原样存储 + 轻量处理"；向量最贵（深度模型编码），常单独一条流水线、独立更新</strong>。工业上倒排与正排同步构建（一次扫描两用），向量异步构建（模型更新要重新编码全量文档）。</span>

## 4 索引更新：增量、合并与新鲜度

文档不断涌入，索引不能每次全量重建。更新策略是流水线的最后一环（也是动态索引篇的工程形态）：

**增量索引（incremental）**：新文档先进辅助索引（内存/小索引），查询时主辅合并——新文档"即时可搜"。
**合并（merge）**：辅助索引长到阈值，与主索引合并（对数/分层合并）——控制写放大。
**删除与更新**：删除走"删除列表"，更新 = 删旧 + 加新。

**重点：索引更新是"新鲜度"与"成本"的持续博弈——更新越频繁，新文档越早可搜，但合并成本越高。** 工业系统的目标不是"绝对新鲜"，而是"按业务需求的新鲜度"——新闻搜索秒级，商品搜索分钟级。<span class="marginnote">索引新鲜度在工程上有一个专门的度量：<strong>"文档可搜延迟"（indexing latency）——从文档被采集到它出现在搜索结果里的时间</strong>。流式处理框架（如 Kafka + 在线索引）可以把这个延迟压到秒级：文档被发布 → 进入消息队列 → 流式消费 → 进辅助索引 → 立即可搜。理解"新鲜度是一种可调的工程指标"，你就理解了索引更新的本质。</span>

## 5 公式解析：流水线的吞吐与延迟

索引流水线是一个"持续处理"系统，两个核心指标：**吞吐（throughput）**与**延迟（latency）**。

$$\text{吞吐} = \frac{\text{处理的文档数}}{\text{时间}}, \qquad \text{延迟} = t_{\text{采集}} + t_{\text{分析}} + t_{\text{建索引}} + t_{\text{合并}}$$

三步拆解：

- **第一步，看吞吐**：每分钟能处理多少篇文档——由分析速度、索引构建速度、机器数共同决定。**吞吐决定"能不能跟上内容增长速度"。**
- **第二步，看延迟**：从采集到可搜的总时间——每环都在贡献延迟。**延迟决定"内容多快可搜"。**
- **第三步，看两者权衡**：吞吐高不保证延迟低（批量处理吞吐高但延迟大）；延迟低不保证吞吐高（流式单篇处理延迟小但吞吐受限）。**流水线设计是"吞吐 × 延迟"的双目标优化——批量与流式混合、并行与顺序搭配**。<span class="marginnote">工业上的典型混合方案：<strong>批量处理管"历史全量"（高吞吐，吞吐优先），流式处理管"实时增量"（低延迟，延迟优先）</strong>——全量建索引用 MapReduce 批量跑，增量更新用 Kafka 流式推。两条线合并成最终索引。这个"批量打底 + 流式补新"的混合，与《分布式索引》与《动态索引》两篇的技术在系统层面汇合。</span>

**辨析｜易错点：索引流水线的质量指标，不只是"延迟与吞吐"，还有"一致性"。** 文档更新时，旧的倒排项与新的内容可能短暂共存——查询结果可能"看见旧版本"。**最终一致性（eventually consistent）是索引更新的默认标准**——大多数搜索产品接受"更新后几秒内新旧可见"，少数要求严格一致（金融、法律检索）需要额外机制。

## 6 小结

- **索引流水线**：文档处理 → 文本分析 → 三路索引构建 → 增量更新——"持续把文档变成可查询资产"。
- **文档处理**：清洗（去标签、去噪声、编码归一）决定"索引里有没有垃圾"。
- **文本分析**：分词、规范化、停用词——索引侧与查询侧必须"同源分析"。
- **三路索引**：倒排（词面）、正排（内容）、向量（语义）——同一文档的三个视图。
- **索引更新**：增量 + 合并 + 删除列表——"新鲜度 vs 成本"的持续博弈，新鲜度是可调指标。
- **吞吐与延迟**：批量打底 + 流式补新；最终一致性是默认标准。
