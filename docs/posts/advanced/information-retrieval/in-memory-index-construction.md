## 为什么把"构建"单独成篇

前两篇我们研究了倒排索引的**静态结构**：词典是什么、倒排表长什么样。但一个严肃的问题是：**这份结构是从哪来的？** 给定一个文档集合，从原始文本到词典与倒排表，中间要经过怎样的加工？这正是索引构建（index construction）的任务。

为什么值得单独讲？因为**规模决定难度**：在莎士比亚全集（37 部剧本，约 90 万个词项实例）上，任何笨办法都行；但到了千万级网页的规模，一个词的草率实现就会让构建变成天文时间。IIR 第 4 章正是研究"如何在给定的内存预算下，最快地造出倒排索引"——而它的第一条路，就是我们这篇的**内存式构建流程**。它也是后面一切外部索引算法（BSBI、SPIMI、MapReduce 方案）的基准与前提。<span class="marginnote">索引构建是"离线大数据处理"的经典案例：输入是一次性的文档全集，输出是一次性建好的索引，期间无用户查询。因此构建算法可以尽情做排序、做重排，只要能接受一次性的代价——这与在线查询对延迟的苛刻要求完全不同。</span>

## 1 构建的输入与输出

先界定两端的形状。

**输入**：一个文档集合，每篇文档有唯一编号（docID）与文本正文。例如 `{"doc1": "to be or not to be", "doc2": "i came i saw i conquered", ...}`。

**输出**：一篇完整的倒排索引——词典（词项 → df → 指针）加倒排表（每项 $(d, \text{tf}_{t,d})$）。关键在"倒排"二字：输入是**按文档组织**的（一篇文档的所有词挨在一起），输出是**按词项组织**的（一个词项的所有文档挨在一起）。**构建的本质，就是把按文档组织的数据，重排成按词项组织的数据。** 这道重排，就是构建算法的主线。

**重点：构建流程可以总结成一句"三步走"——抽取词项、全局排序、归并倒排表。** 全篇记住这条主线，后面的每个算法都只是在这三步上做内存与磁盘的权衡。

## 2 三步流程：抽取 → 排序 → 归并

第一步，**抽取词项对**。逐篇扫描文档，把每篇文档里的每个词项与它的文档编号组成一个二元组 $(\text{termID}, \text{docID})$。词项要先用上一篇文章讲的规范化处理，再映射成整数 ID（termID），因为整数排序远比字符串排序快。<span class="marginnote">把词项映射成 termID 的过程依赖一个"词项 → ID"的对照表。这个对照表本身也是一份词典雏形——构建流程里它可能常驻内存，也可能分块落盘，这是不同算法（BSBI 与 SPIMI）的重要分歧点。</span>

以两篇小文档为例，得到的二元组序列：

```
(to, 1), (be, 1), (or, 1), (not, 1), (to, 1), (be, 1),
(i, 2), (came, 2), (i, 2), (saw, 2), (i, 2), (conquered, 2)
```

第二步，**全局排序**。按 termID 为第一关键字、docID 为第二关键字，把所有二元组排序。排序后，同一个词项的所有文档编号会**聚拢在一起**：

```
(be, 1), (be, 1), (came, 2), (conquered, 2), (i, 2), (i, 2),
(i, 2), (not, 1), (or, 1), (saw, 2), (to, 1), (to, 1)
```

第三步，**归并成倒排表**。从左到右扫描排序后的序列，把 termID 相同的连续段收拢成该词项的倒排表；同时统计每段长度（得 $df$）与每个 (termID, docID) 的重复次数（得 $\text{tf}_{t,d}$）。这一步得到的结果，恰好就是我们需要的"按词项组织"的结构。

```python
def in_memory_construction(docs):
    pairs = []
    for docID, text in docs.items():
        for term in tokenize(text):
            termID = term_to_id(term)
            pairs.append((termID, docID))   # 第一步：抽取
    pairs.sort()                            # 第二步：排序
    index = defaultdict(list)
    for termID, docID in pairs:             # 第三步：归并
        postings = index[termID]
        if postings and postings[-1][0] == docID:
            postings[-1] = (docID, postings[-1][1] + 1)  # 累计 tf
        else:
            postings.append((docID, 1))
    return index
```

**辨析｜易错点：排序是"构建"的核心，不是可有可无的优化。** 有人会想：既然最终要按词项归并，为什么不直接用哈希表，扫一遍就装好？能，但哈希表的代价是**词项顺序完全随机**——倒排表就失去了"按文档编号有序"这一关键性质（想想上一篇的合并算法）。排序构建一举两得：既完成分组，又天然产出有序倒排表。**"用排序换有序"，是这个算法的灵魂。** 哈希方案并非没有价值，它正是下一篇 SPIMI 的思想前身，但那是为"单遍处理、内存紧凑"而生的变体。

## 3 公式解析：为什么排序构建是 O(T log T)

设文集中词项实例的总数为 $T$（每个词项出现一次就贡献一个二元组），构建的代价可以这样分解：

$$C_{\text{build}} = \underbrace{O(T)}_{\text{抽取}} + \underbrace{O(T \log T)}_{\text{排序}} + \underbrace{O(T)}_{\text{归并}} = O(T \log T)$$

三步拆解：

- **第一步，$T$ 从哪来**：$T = \sum_{d \in D} n_d$，其中 $n_d$ 是文档 $d$ 的词项实例数。整个流程的输入规模就是 $T$ 个二元组，没有更小的线性下界——任何方案至少要把每个词项看一眼。
- **第二步，排序为什么是瓶颈**：对 $T$ 个元素排序的下界是 $O(T \log T)$。当 $T$ 到十亿量级时，$\log T \approx 30$，排序大约要 300 亿次比较——这通常是整个构建里唯一"超线性"的环节，也是所有构建算法都想绕开或分摊的部分。
- **第三步，抽取与归并都是线性的**：扫描文档产二元组是 $O(T)$；归并阶段从排序后的序列走一遍也是 $O(T)$。两者加起来不超过排序的零头。**所以"构建快不快"，基本等于"排序快不快"。**

由此得到一个重要的工程结论：**内存式构建能吃下的规模，上限是"排序一趟装得下"。** 当 $T$ 对应的二元组超出可用内存时，标准排序就要用外排序（external sort），代价陡增——这正是下一篇《基于块排序的索引构建（BSBI）》要专门解决的场景。

**辨析｜易错点：$T$ 是"词项实例数"，不是"词典大小 $V$"，更不是"文档数 $N$"。** 一篇 1000 词的网页贡献 $T$ 中约 1000 个二元组，但词典里可能只增加几十个新词项。构建算法的开销由 $T$ 主导，而索引的"瘦身"目标却是减少 $V$ 与倒排表长度。**把 $T$、$V$、$N$ 三者混为一谈，会在估算内存与磁盘时差出几个数量级。**

## 4 内存的墙：什么时候该换算法

内存式构建很优雅，但它有一个硬前提：**所有二元组（至少是排序中间态）要放得进内存。** 以 Web 规模为例，假设 10 亿网页、平均每页 1000 个词项实例，则 $T \approx 10^{12}$；每个二元组（termID + docID，各 4 字节）占 8 字节，仅二元组就要 8 TB——远超单机内存。此时内存式构建直接失效。

退化是渐进的，先看两个台阶：

- **慢速退化**：内存勉强放得下，但排序产生的临时数组频繁触发垃圾回收与交换，构建慢如蜗牛。此时问题在"内存效率"，不在"放不下"。
- **彻底失效**：排序中间态装不下，进程 OOM（out of memory）崩溃。此时必须改变策略——要么**分块排序、落盘归并**（下一篇的 BSBI），要么**单遍哈希、边扫边落盘**（后面的 SPIMI）。

**重点：判断"要不要换算法"，看的是排序的工作集（working set），不是词典大小。** 词典本身（$V$ 个词项）通常远比 $T$ 个二元组小；真正吃内存的是那 $T$ 个待排序记录。工程上常用"排序一趟所需内存 ≈ 1.5 × 8T 字节"来粗估（标准库排序的临时缓冲系数），一旦逼近可用内存，就该为外部算法做准备。

**辨析｜易错点：不要过早为"外部算法"做准备。** 很多教材把 BSBI 与 SPIMI 讲得花团锦簇，初学者容易一上来就用它们。但绝大多数实际语料（一本书、一个语料库、一个小型网站）在单机内存里用朴素排序构建，几分钟就完成了——**简单算法在它成立的范围内，永远是最优的**。外部算法是给"内存装不下"的场合准备的，而不是默认配置。

## 5 小结

- **构建的本质**：把"按文档组织"的输入重排成"按词项组织"的输出，一句话——**抽取词项、全局排序、归并倒排表**。
- **排序是关键**：它同时完成分组与产出有序倒排表；代价 $O(T \log T)$ 主导整个构建，$T$ 是词项实例总数。
- **词频与文档频率**在归并阶段顺势统计，写进倒排表与词典，为后续排序模型预留。
- **内存是硬约束**：排序的工作集约 8T 字节装不下时，内存式构建退化为外排序乃至 OOM，需切换外部算法（BSBI / SPIMI）。
- **用简单的算法处理简单的问题**：单机内存能装下时，朴素排序构建就是最优解。

在下一节，我们将面对"内存装不下"的正式挑战——如何把排序拆成**若干块**，分块在内存里排好、落盘，再**归并**成全局有序的倒排索引，这就是**基于块排序的索引构建（BSBI）**。
