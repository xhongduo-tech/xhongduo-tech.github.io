## 为什么从"检索器"开始

上一篇的查询重写是"外部翻译"——检索器本身不懂对话，靠重写层把对话查询翻译成独立查询再喂给它。这个方案简单有效，但有一个瓶颈：**重写是"有损翻译"——上下文的信息（焦点、约束、意图）在翻译成独立查询时，总有一部分丢失**（重写漏了"预算 5000 以内"这个约束，检索就搜偏了）。

**对话式稠密检索（Conversational Dense Retrieval，CDR）** 换一个思路：**让检索模型本身"理解"对话上下文——不（只）靠外部重写，而是把对话历史直接编码进检索过程**。这相当于"取消翻译层，让检索器学会对话语言"。这篇讲 CDR 的核心：怎么把对话上下文建模进稠密检索的表示与训练。<span class="marginnote">对话式稠密检索的代表工作是 2020–2022 年的 ORCA、CQR、ConvDR 等系列——它们把"对话上下文"与"当前查询"一起编码，训练检索器理解"对话中的查询"。<strong>CDR 与查询重写是"检索器侧"与"查询侧"两种对话理解的落点</strong>——重写在查询侧做（改查询），CDR 在检索器侧做（改表示）。两者不互斥：工业系统常"重写 + 对话感知检索器"并用，一个保底、一个增强。</span>

## 1 重写 vs 对话感知：两种对话理解

对比两条路线的差异，理解 CDR 的定位：

| 维度 | 查询重写（查询侧） | CDR（检索器侧） |
| --- | --- | --- |
| 理解方式 | 把对话查询翻译成独立查询 | 把对话上下文编码进检索表示 |
| 对检索器 | 不改变（检索器照旧） | 改变（检索器要训练） |
| 信息保真 | 有损（翻译丢信息） | 更完整（上下文直接进表示） |
| 工程成本 | 低（加一个重写层） | 高（重训练检索器） |
| 泛化性 | 依赖重写质量 | 依赖训练数据 |

**重点：重写是"无损假设下的有损翻译"，CDR 是"让表示承载更多上下文"。** 重写假设"独立查询能表达完整意图"（但经常表达不全）；CDR 直接让"上下文 + 当前查询"共同决定检索——**信息链更短、损耗更少**。<span class="marginnote">为什么说重写是"有损"的？<strong>重写把一段对话压缩成一个独立查询——压缩必然丢弃信息（语气、否定、未言明的约束）</strong>。CDR 把整个对话上下文喂给检索器（编码进向量），不经过"压缩成查询"这一步——理论上信息保真更高。但 CDR 的代价是"检索器要专门训练"（理解对话上下文不是通用检索器的能力）——工程上是"保真 vs 成本"的选择。</span>

## 2 CDR 的核心：上下文感知的查询编码

CDR 的基本形态，是**上下文感知的双塔检索**：

- **标准双塔**：查询编码器只编码当前查询 $q_t$ → 查询向量。
- **对话感知双塔**：查询编码器编码"当前查询 + 对话上下文" → 对话感知的查询向量：

$$\vec{v}_{q_t} = E_{\text{conv}}(q_t, H_t), \qquad \text{score}(d \mid q_t, H_t) = \cos(\vec{v}_{q_t}, \vec{v}_d)$$

对话感知编码器 $E_{\text{conv}}$ 学会"从当前查询与历史中提取检索意图"——**它内部隐式地做了"焦点消解、约束继承"，不需要外部重写**。<span class="marginnote">对话感知编码器的实现通常是把"对话历史 + 当前查询"拼接后喂给 Transformer 编码器（或用特殊 token 分隔），输出的 $E_{\text{conv}}$ 向量作为"对话感知的查询向量"。<strong>它的训练数据是"对话查询-相关文档"对——让编码器学会"对话中的查询该检索什么"</strong>。对比普通双塔：普通双塔见过的是"独立查询-文档"对，对话感知双塔见过的是"带上下文的查询-文档"对——训练数据的不同，让检索器学会了"理解对话"。</span>

**辨析｜易错点：CDR 不是"把历史拼进查询"那么简单。** 把"历史 + 当前查询"拼起来当普通查询喂给标准双塔，不是 CDR——**标准双塔没学过"对话上下文"的语义**（它分不清"历史里的噪声"与"当前需要的焦点"）。CDR 的关键是"专门训练"：检索器必须被训练成"知道从历史里提取什么、忽略什么"。**训练（而非拼接）是 CDR 的本质。**

## 3 公式解析：CDR 的训练数据

CDR 的训练数据是它的命脉。设对话历史 $H_t$ 与第 $t$ 轮查询 $q_t$，训练样本是"（$q_t, H_t$）→ 相关文档 $d^+$"：

$$\mathcal{L} = -\log \frac{e^{\cos(\vec{v}_{q_t}, \vec{v}_{d^+})/\tau}}{e^{\cos(\vec{v}_{q_t}, \vec{v}_{d^+})/\tau} + \sum_j e^{\cos(\vec{v}_{q_t}, \vec{v}_{d_j^-})/\tau}}$$

其中 $\vec{v}_{q_t} = E_{\text{conv}}(q_t, H_t)$ 是对话感知的查询向量。

三步拆解：

- **第一步，读正对**：$(q_t, H_t)$ 与相关文档 $d^+$——"这轮对话要找的文档"。
- **第二步，读负对**：$d_j^-$ 是不相关文档——"对话中不该返回的"。
- **第三步，读学习内容**：损失驱动编码器学到"从对话上下文里提取检索意图"——**同样一个查询 $q_t$，不同对话历史下应检索不同文档（焦点不同）**。

**核心结论：CDR 的训练让编码器学会"对话上下文决定检索目标"——同一句话在不同对话里指向不同文档，编码器要能区分。** 这是 CDR 相对"独立查询检索"的本质能力。<span class="marginnote">CDR 训练数据的一个难点：<strong>"对话查询-文档"标注很贵</strong>（要标注"这轮对话该检索什么"，比单轮查询标注难得多）。工程解法："改写训练"——用查询重写模型生成"理想独立查询"，用它去检索得到伪标注（distant supervision），再训练 CDR。这个"用重写造数据训练对话感知检索器"的循环，把两个方法连成了闭环：<strong>重写先兜底，造数据；CDR 再学习，超越重写</strong>。</span>

## 4 CDR 与 RAG / LLM 的结合

现代对话式检索，几乎都嵌在 LLM 驱动的对话系统里（RAG 的对话版）：

**LLM 做上下文理解**：LLM 读对话历史 → 生成"对话感知的查询表示"（比专门训练的 CDR 编码器更灵活）。
**CDR 做检索器**：对话感知的查询表示走稠密检索 → 召回文档。
**LLM 做回答生成**：检索文档 + 对话历史 → 生成回答（对话式 RAG）。

**重点：现代对话式搜索里，"LLM 上下文理解 + 稠密检索 + LLM 生成"是标准组合——CDR 的思想（让检索表示承载上下文）被 LLM 以更灵活的方式实现。** 专门训练的 CDR 编码器仍有价值（轻量、可控、专用），但 LLM 的上下文理解能力让"重写 + 检索"常常足够——**"要不要专门训练对话感知检索器"，取决于预算与精度要求**。<span class="marginnote">这个"LLM vs 专门模型"的选择，是对话式检索的工程权衡：<strong>LLM 做上下文理解贵但灵活（能处理任意对话模式），专门 CDR 编码器便宜但受训练数据限制（只懂训练见过的对话模式）</strong>。工业实践：高价值/复杂对话用 LLM 重写 + 标准检索；大规模/简单对话用轻量 CDR 或规则重写。与之前反复出现的"便宜分层 + 昂贵兜底"是同一个决策模式。</span>

**辨析｜易错点：对话式检索 ≠ 对话式生成。** 对话式检索的产出是"文档"（这轮对话该检索什么），对话式生成的产出是"回答"（基于文档写什么）。**检索与生成是对话系统的两个环节**——检索决定"依据"，生成决定"表达"（第十三篇 RAG 的分工）。别把"对话式检索"（找对文档）与"对话式问答"（写出答案）混为一谈——前者是后者的前置。

## 5 对话式检索的评测

对话式检索的评测，比单轮检索多一层：

**单轮检索质量**：每轮的检索结果相关性（Recall@K、NDCG）——"每轮检索对不对"。
**对话整体质量**：整个对话的信息获取效果——"多轮下来，用户的问题解决了吗"。
**上下文利用质量**：系统是否正确利用了上下文（焦点消解对不对、约束继承全不全）——"对话理解对不对"。

**重点：对话式检索的评测是"单轮 × 对话"双层——每轮检索要对，整场对话要连贯。** 一个"每轮都对但整体跑偏"的系统（对话中焦点逐渐偏离）与"偶尔错但整体连贯"的系统，要区分对待——**对话级指标（任务完成、用户满意度）是最终裁判**。<span class="marginnote">对话式检索评测的一个特有难点："焦点评测"——<strong>系统是否正确理解了"当前在谈什么"</strong>。评测方法：给每轮标注"当前焦点实体/主题"，对比系统的理解——焦点理解错了，检索必然偏。这个"焦点级标注"比"文档级标注"更细，也更接近"对话理解"的本质。对话检索的成熟评测，要同时看"焦点理解"与"文档检索"两层。</span>

## 6 数值算例：同一句话，两个对话，两个目标

把"对话上下文决定检索目标"演算成一次 CDR 训练的目标。设同一句查询 "它的价格是多少？"，在两个不同对话里：

| 对话 | 历史 | 当前查询 | CDR 应检索的目标 |
| --- | --- | --- | --- |
| 对话 A | "iPhone 15 有哪些颜色？" | "它的价格是多少？" | iPhone 15 的价格 |
| 对话 B | "这台冰箱的容量多大？" | "它的价格是多少？" | 这台冰箱的价格 |

三步读这张表：

- **看查询完全相同**："它的价格是多少？" 在两场对话里字面一致——**标准双塔会给它们同一个查询向量**。
- **看目标完全不同**：A 要找 iPhone 价格，B 要找冰箱价格——**"它"的指代不同，检索目标天差地别**。
- **看 CDR 的学习**：训练数据让 $E_{\text{conv}}(q, H_A)$ 与 $E_{\text{conv}}(q, H_B)$ 产生不同向量——**编码器学会"从历史里找'它'指代谁"**。

这个例子是 CDR 的本质能力：**同一查询 + 不同上下文 = 不同检索目标**。标准双塔（只编码当前查询）做不到，因为"它"的指代在历史里；CDR 编码器通过"上下文感知"的训练，把"从历史找指代"内化进表示——**这是"让检索器学会对话语言"的具体含义**。

**辨析｜易错点：CDR 的"上下文"要用"检索相关的部分"，不是"全部历史"。** 历史里可能有大量与当前检索无关的闲聊（"好的""谢谢"），全部编码会让查询向量被噪声污染。**"上下文选择/压缩"是 CDR 的前置问题**——只编码"与当前检索相关的历史片段"，而非整段对话。工程上"摘要历史"或"加权历史"是常用缓解，理解这一点，你就知道 CDR 不只是"编码历史"，更是"编码对检索有用的历史"。

## 8 小结

- **CDR**：让检索器本身理解对话上下文——把"历史 + 当前查询"编码进检索表示，而非只靠外部重写。
- **重写 vs CDR**：重写是"查询侧翻译"（有损、低成本），CDR 是"检索器侧理解"（保真、需训练）。
- **核心机制**：对话感知编码器 $E_{\text{conv}}(q_t, H_t)$——训练让编码器学会"对话上下文决定检索目标"。
- **训练数据**：对话查询-文档对（贵），可用"重写造数据"（distant supervision）缓解。
- **LLM 结合**：LLM 上下文理解 + 稠密检索 + LLM 生成——现代对话搜索的标准组合。
- **评测双层**：单轮检索质量 × 对话整体质量 × 上下文利用（焦点理解）。

在下一节，我们处理对话式搜索的一个独特能力——当系统"不确定用户要什么"时，主动问用户，这就是**主动澄清：向用户提问澄清需求**。
