## 为什么从"清理"开始

意图分类告诉我们"用户想干什么"，但查询本身常常是"脏"的：`iphnoe` 拼错了、`基于深度学习的图像识别技术研究进展` 没有分词边界、`微信 小程序 怎么做` 是模糊短语。**如果查询本身是错的，后续所有的检索、排序、理解都是在错误的地基上盖楼。**

**查询纠错（query correction）** 与**查询分词（query segmentation）** 是查询理解的"清理环节"：纠错负责把"错的查询"变"对"，分词负责把"连成串的查询"变"结构化的词序列"。它们处理的不是"语义深意"，而是"文本表面的正确性"——但正因为它们在最上游，它们的错误会被下游放大，它们的价值也最容易被低估。<span class="marginnote">查询纠错的统计事实：<strong>约 10% 的搜索查询包含拼写错误或输入错误</strong>（键盘误触、语音误转、输入法失误）。一个没被纠错的错查询，轻则召回失败，重则给出一页错误结果。工业搜索对查询纠错的重视，与对排序模型的重视几乎相当——因为"把错的查询改对"是零成本的收益，比"把对的查询排得更好"还值钱。</span>

## 1 查询纠错：与文档侧拼写矫正的同与异

我们在第三篇学过**拼写矫正（spelling correction）**——编辑距离、k-gram 重叠、Soundex。查询纠错复用同一套工具，但有它自己的特点：

**相同**：核心算法一样——编辑距离、k-gram 候选生成、加权排序。

**不同**：

- **查询极短**：查询通常 2–5 个词，上下文稀少——矫正的"证据"不足。
- **查询有语义**：纠错要"改完语义通顺"——`pytorch` 错写成 `pytorh`，纠成 `pytorch` 而非 `pytor h`。
- **查询有行为信号**：用户搜索后点击了什么，是纠错对错的天然验证——**行为闭环是查询纠错的独特武器**。<span class="marginnote">查询纠错与文档拼写矫正的最大差别在"信号来源"：<strong>文档矫正看的是词典与统计，查询矫正还能看"用户行为"</strong>。一个查询改错后点击率飙升，说明改对了；改了之后没人点，说明改错了。工业查询纠错用"查询-点击日志"做强化：<strong>把"纠错后的查询是否带来更好点击"当反馈信号，让纠错模型持续进化</strong>——这是文档侧没有的闭环。</span>

**重点：查询纠错的目标不是"把词改对"，而是"把查询改得能召回用户想要的东西"。** 一个拼写"错"的词如果原本就能召回好结果，就不该改——**纠错的评价标准是检索收益，不是拼写正确率**。

## 2 查询纠错的两层结构

工业查询纠错通常分两层：

- **离线词典纠错**：维护一个"错误-正确"映射词典（从点击日志挖掘：`iphnone → iphone`），加上编辑距离/k-gram 生成候选。快、可解释、覆盖高频错误。
- **在线模型纠错**：用神经网络（序列到序列模型）对查询做"错误修复"——能处理词典没覆盖的新错误、多词连写错误，但更贵、更难解释。

**辨析｜易错点：纠错要"保守"，不能把对查询改错。** 一个正确的查询被"纠正"成另一个词，是查询纠错最可怕的失败模式——用户搜 `java`（编程语言）却被改成 `java 岛`，体验灾难。**工业铁律：只在高置信时纠错**——纠错的置信度阈值通常设得很高，且"纠错后若无点击/无更好结果则回退到原查询"（回退机制）。<span class="marginnote">"保守纠错 + 回退机制"是查询纠错工程的核心设计：<strong>宁可漏纠（召回差一点），不可误纠（召回全错）</strong>。工业系统常同时返回"原查询结果 + 纠错提示"（"你是不是想找 iphone？"），让用户自己确认——把纠错的决策权部分交还给用户。</span>

## 3 查询分词：中文查询的切分难题

**查询分词（query segmentation）** 在中文检索里尤其关键。我们在《中文检索的特殊性》讲过文档分词，但查询分词有自己的特点：

- **查询无上下文**：文档有完整句子，查询只有几个词——分词歧义更严重。
- **切分方式影响检索**：`北京大学生` 切 `北京/大学生` 与 `北京大学/生`，召回完全不同——**分词错误直接改变检索结果**。
- **词典 + 统计 + 语义**：查询分词用词典最大匹配打底、用统计模型消歧、用语义（预训练模型）理解长尾。

**重点：查询分词的一致性要求比文档分词更高——查询侧与文档侧必须用同一套分词规则，否则词项对不上，召回断裂。** 我们在中文检索一篇强调的"一致性 > 准确性"，在查询分词上尤其适用。<span class="marginnote">查询分词的经典难题是"细粒度 vs 粗粒度"：<strong>切细了（`深度学习` → `深度` + `学习`）召回宽但噪声大；切粗了（`北京大学生` → `北京大学` + `生`）召回精确但可能漏</strong>。工业查询分词的通行做法是"多粒度并存"——同时保留粗切与细切的结果，粗粒度用于精确匹配，细粒度用于宽召回，两者互补（与"词级索引 + 单字索引"混合是同一思想）。</span>

## 4 公式解析：查询分词的目标函数

查询分词可以模型化为"从所有切分方式里选最优"。设查询 $q$ 的一种切分为 $S = [w_1, w_2, \dots, w_m]$，分词质量由两部分决定：**切分后的词是否"合法"**（词频 $P(w_i)$）与**词间衔接是否自然**（转移概率 $P(w_i \mid w_{i-1})$）：

$$\text{Score}(S) = \sum_{i=1}^{m} \log P(w_i) + \sum_{i=2}^{m} \log P(w_i \mid w_{i-1})$$

三步拆解：

- **第一步，读词频项**：$\log P(w_i)$——切出的词在语料里越常见，越可能是合法词。`大学生` 的词频远高于 `学大`，所以"大学生"更可能是词。
- **第二步，读转移项**：$\log P(w_i \mid w_{i-1})$——前一个词到后一个词的衔接越自然，切分越好。`北京 → 大学生` 的衔接比 `北京 → 大学 → 生` 更自然（统计上）。
- **第三步，看动态规划**：最大化这个分数就是"从所有切分里选总分最高的"——可以用动态规划（Viterbi）高效求解，也可以用神经网络直接预测切分边界。

**核心结论：查询分词是一个"在候选切分里选分数最高"的优化问题，分数由词合法性 + 衔接自然度构成。**<span class="marginnote">分词方法的演进：<strong>词典最大匹配 → 统计（HMM/CRF，学词频与转移）→ 神经网络（序列标注，学上下文语义）</strong>。性能上后者更好，但前者快、可解释、可离线分析。查询侧延迟预算紧，很多系统仍用"词典 + 统计"的轻量方案，把重模型留给离线索引侧——"在线轻、离线重"的分层再次出现。</span>

## 5 纠错与分词的联动

纠错与分词不是独立的两步，它们有先后与联动：

- **先纠错再分词**：`iphnoe` 不纠错，分词会把它切成奇怪片段——**纠错在前，分词在后**是标准流水线。
- **分词辅助纠错**：分词结果能帮助判断"哪里是词错误"——切不出来的片段往往是拼写错误。
- **纠错决策依赖分词**：`python 教程` 与 `pytho n教程`，分词把 `pytho n` 切出怪词，触发纠错——**分词为纠错提供"错误定位"**。<span class="marginnote">两者联动的完整形态是"查询规范化流水线"：<strong>大小写归一 → 全角半角 → 纠错 → 分词 → 词性/实体标注</strong>。每步的输出是下一步的输入，任何一步的错误都会向下游传导。工业查询理解团队维护这样一条流水线，并用"查询日志 + 点击反馈"持续评估每一环的质量——查询理解是一个系统，不是一个算法。</span>

## 6 小结

- **查询纠错**：复用拼写矫正工具，但查询极短、有语义、有行为信号——评价标准是检索收益而非拼写正确率。
- **纠错两层**：离线词典（快、覆盖高频）+ 在线模型（强、覆盖长尾）；高置信才纠、误纠要回退。
- **查询分词**：中文查询无边界，切分方式直接改变检索结果；"一致性 > 准确性"，多粒度并存。
- **分词目标函数**：词合法性 + 衔接自然度，动态规划 / 序列标注求解。
- **联动流水线**：归一化 → 纠错 → 分词 → 标注；每环质量靠查询日志 + 点击反馈持续评估。
