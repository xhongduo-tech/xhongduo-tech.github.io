## 为什么从"建模"开始

对话式搜索的核心难题，是**每一轮查询都依赖上下文**：`那红色的呢？` 如果没有前一轮的 `iphone 15 有哪些颜色`，这句话毫无意义。系统必须"记住并理解"对话走到了哪，才能处理当前这一轮。这个"记住和理解对话历史"的工作，叫**对话上下文建模（conversational context modeling）**；而它最直接的产出，是把"依赖上下文的查询"重写成"独立可检索的查询"——**查询重写（query rewriting）**。

这两个环节是对话式搜索的"翻译层"：**上下文建模负责"读懂对话"，查询重写负责"把读懂的结果翻译成检索器能用的查询"**。它们的质量，直接决定对话式搜索的检索质量——**检索器（前十二篇）不会变，变的是"喂给它的查询"变聪明了**。<span class="marginnote">对话上下文建模在学术上叫"对话状态追踪"（dialogue state tracking）与"上下文表征"（context representation）——早期用于任务型对话系统（订票、导航），现在被对话式搜索继承。<strong>对话式搜索的上下文建模有一个特殊性：它不只要"追踪状态"（对话走到哪），还要"提取检索信号"（当前在找什么）</strong>——建模的输出要能直接指导检索（重写查询、修正排序）。"建模为检索服务"，是它与通用对话系统建模的区别。</span>

## 1 上下文里有什么：三类信息

对话上下文不是"一段历史文本"这么简单，它包含三类对检索有指导意义的信息：

- **焦点（focus）**：当前对话在"谈什么对象"——`那红色的` 的焦点是"iPhone 15"（继承上一轮）。
- **约束（constraints）**：用户已经给出的偏好与限定——"红色"、"512GB"、"预算 5000 以内"。
- **意图（intent）**：用户当前想干什么——比较、购买、了解参数。

**重点：上下文建模的目标，是从对话历史里提取"焦点 + 约束 + 意图"——这三者正是重写查询所需的全部信息。** 重写 `那红色的呢？` = 焦点（iPhone 15）+ 约束（红色）+ 意图（了解/比较）→ `红色 iPhone 15`。<span class="marginnote">"焦点 + 约束 + 意图"的三元组，是对话状态建模的经典抽象：<strong>焦点回答"在谈什么"，约束回答"有哪些限定条件"，意图回答"想干什么"</strong>。对话式检索的重写，本质上就是"把这三者组装成一个检索查询"。这个抽象与"任务型对话"的槽位填充（slot filling）同源——`买 红色的 iphone 15` 的槽位是"动作=买、颜色=红、商品=iphone 15"。理解了"焦点-约束-意图"，你就理解了对话状态的核心结构。</span>

## 2 上下文建模的方法

对话上下文怎么建模？三代方法：

- **窗口拼接（window concatenation）**：把最近几轮的查询与回答直接拼接，作为当前查询的上下文喂给模型。简单，但**没有结构**——模型要从原始文本里自己"找焦点"。
- **结构化的对话状态（structured state）**：显式维护"焦点、约束、意图"的槽位，每轮更新。可解释、可控，但**槽位设计是人工的**、覆盖不了复杂对话。
- **神经上下文编码（neural context encoding）**：把对话历史编码成向量（或让 LLM 直接读对话历史）——**端到端，LLM 隐式理解对话结构**。现代主流。<span class="marginnote">三代方法对应"结构化程度"的下降与"表达能力"的上升：<strong>窗口拼接最笨（没结构）、结构化状态最可控（人工槽位）、神经编码最能表达（但黑盒）</strong>。LLM 时代的对话上下文建模，几乎是"让 LLM 读对话历史"的代名词——LLM 天然理解"焦点、约束、意图"（它的语言理解能力），不需要显式槽位。这个"从人工结构到模型隐式理解"的演进，与第九篇查询改写的"从规则到生成式"是同一个趋势。</span>

**辨析｜易错点：上下文不是"越长越好"。** 对话历史越长，上下文建模的负担越重（噪音越多、焦点越分散）。**"近几轮"比"全部历史"更有用**——工业上常用"滑动窗口"（只看最近 3–5 轮）+ "摘要"（更早的历史压成一段摘要）。上下文建模的质量，取决于"从历史里提取当前相关的那部分"，而不是"记住全部"。

## 3 查询重写：从依赖到独立

**核心概念：对话查询重写（conversational query rewriting）**：把"依赖上下文的当前查询"重写为"脱离上下文也能被正确检索的独立查询"。

重写的典型任务（第十一篇讲过，对话场景更系统）：

- **指代消解**：`它怎么样？` → `[焦点] 怎么样`。
- **省略补全**：`价格呢？` → `[焦点] 价格`。
- **约束继承**：`那 512GB 的呢？` → `[焦点] 512GB 版本`。
- **修正与否定**：`不要这个，要另一个` → 基于上下文的否定性重写。

**重点：重写后的查询是"独立可检索的"——它进入的检索流水线（BM25/嵌入/ANN）与前十三篇完全一样。** 重写是"翻译层"，它让"不会说检索语言"的对话表达，变成"检索器能处理"的独立查询。<span class="marginnote">"重写后查询进入标准检索流水线"是这个设计的工程价值：<strong>对话式搜索不需要改检索器——它只需要在检索前加一个"重写层"</strong>。这与你学的第九篇生成式查询改写是同一技术：LLM 读对话历史 + 当前轮次 → 生成独立查询。工业上"LLM 对话查询重写"是标准做法——便宜、可插拔、不侵入检索核心。</span>

## 4 公式解析：重写的信息来源

对话查询重写的"信息来源"，决定它的能力边界。设第 $t$ 轮查询 $q_t$，对话历史 $H_t$，重写函数 $\psi$ 的输出查询为 $q_t^*$：

$$q_t^* = \psi(q_t, H_t) = \text{Focus}(H_t) \oplus \text{Constraints}(H_t) \oplus \text{Intent}(q_t)$$

三步拆解：

- **第一步，读焦点项**：$\text{Focus}(H_t)$——从历史提取"当前对象"（iPhone 15）——**重写的主要信息来自历史**。
- **第二步，读约束项**：$\text{Constraints}(H_t)$——历史里的限定条件（红色、512GB）——**约束是历史累积的偏好**。
- **第三步，读意图项**：$\text{Intent}(q_t)$——当前轮次的表达（"价格""对比"）——**意图来自当前轮，焦点约束来自历史**。

**核心结论：重写 = "历史提供焦点与约束 + 当前轮提供意图"——重写的能力边界，取决于"从历史提取焦点约束"与"从当前轮提取意图"两者都做得好不好。**<span class="marginnote">这个"历史 × 当前"的信息分解，也解释了重写的失败模式：<strong>焦点提取错（把上一轮的 A 当焦点，其实用户在说 B）、约束漏提（历史里的"红色"被忽略）、意图误读（"不要"被当成"要"）</strong>——每一个错误都直接进入检索，导致检索跑偏。所以对话式搜索的"重写质量"评测，是"重写后的查询是否保留原意"——重写错了，检索再强也是"在错误查询上检索"。</span>

## 5 重写与检索的评测

对话式搜索里，重写与检索是一体的，评测要一起做：

- **重写质量**：重写后的查询是否"保留了用户的真实意图"——人工判断（重写对/错）。
- **检索质量**：重写后的查询检索结果是否相关——Recall@K、NDCG（标准检索指标）。
- **对话级质量**：多轮对话整体的信息获取效果——**最终答案/结果的正确性**（对话级评测，后续专门一篇）。

**重点：重写质量的最终验证，是"重写后的检索结果好不好"——重写是手段，检索（乃至答案）质量才是目的。** 一个重写"语法正确但丢了约束"的系统，检索结果会差——评测必须落在"重写 → 检索"的链条上，而不是只看重写文本本身。<span class="marginnote">工程上有一个实用的评测技巧：<strong>"重写 vs 理想查询"对照——如果人工写出"理想的重写查询"（完整保留用户意图的独立查询），用重写系统的输出与理想查询分别检索，对比检索质量，就能量化"重写的损失"</strong>。这个"理想查询"方法（在对话检索基准如 TREC CAsT 里常用）把"重写质量"翻译成"可度量的检索差距"——重写系统越接近理想查询，检索越好。</span>

**辨析｜易错点：重写 ≠ 上下文理解，重写是"产出"，理解是"过程"。** 上下文建模"读懂"对话（提取焦点约束意图），重写把"读懂的结果"变成查询——**建模是理解，重写是翻译**。一个系统可以不显式建模（直接用 LLM 读历史生成重写），但"理解"仍然发生了（在 LLM 内部）。**别把"重写"当全部——重写的质量上限，由"上下文理解"的质量决定**。

## 6 小结

- **对话上下文建模**：从对话历史提取"焦点 + 约束 + 意图"——"读懂对话"。
- **三类信息**：焦点（在谈什么）、约束（限定条件）、意图（想干什么）——重写的原料。
- **建模方法**：窗口拼接（无结构）→ 结构化状态（人工槽位）→ 神经编码/LLM（端到端）。
- **查询重写**：把"依赖上下文的表达"重写为"独立可检索的查询"——翻译层，不侵入检索核心。
- **信息公式**：$q^* = \text{Focus}(H_t) \oplus \text{Constraints}(H_t) \oplus \text{Intent}(q_t)$——历史 × 当前。
- **评测**：重写质量 → 检索质量 → 对话质量——"理想查询"对照量化重写损失。
