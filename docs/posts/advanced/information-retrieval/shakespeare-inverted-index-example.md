## 为什么从莎士比亚开始

Manning《Introduction to Information Retrieval》全书用同一个例子开宗明义：**拿莎士比亚的四部剧，把「从文本到索引、从索引到答案」的全过程手工走一遍。** 这个例子是信息检索的「hello world」——语料小到可以在纸上摊开，却完整包含了词项—文档矩阵、倒排索引、布尔查询处理这三个日后撑起整个搜索引擎的骨架。

上一篇文章我们已经把「检索系统的基本任务」抽象成了一个概率 $P(R=1 \mid q, d)$；这一篇我们把抽象放回地面，回答一个纯工程问题：**给定一个查询，系统凭什么能在亿万篇文档里毫秒级地找出包含某几个词的文档？** 答案就是**倒排索引（inverted index）**——本专题第二篇的核心，也是整个 IR 大厦的地基。<span class="marginnote">莎士比亚在这个例子里不是主角，而是「最小可运行的文档集」：四部剧足够小，让索引结构一眼看穿；又足够真实，让每一个处理步骤都不像玩具。</span>

## 1 最小的文集：四部剧

把文档集合定成四部剧，并给它们编号：

| 编号 | 文档 | 英文标题 |
| --- | --- | --- |
| Doc1 | 《裘力斯 · 凯撒》 | Julius Caesar |
| Doc2 | 《哈姆雷特》 | Hamlet |
| Doc3 | 《麦克白》 | Macbeth |
| Doc4 | 《罗密欧与朱丽叶》 | Romeo and Juliet |

取四个词项，看每个词项出现在哪些剧里。上一篇文章已经建立过这张 **词项—文档关联矩阵（term-document incidence matrix）**，这里我们直接沿用：行是词项，列是文档，$M_{t,d}=1$ 表示词项 $t$ 出现在文档 $d$ 中。

| 词项 | Doc1 | Doc2 | Doc3 | Doc4 |
| --- | --- | --- | --- | --- |
| Brutus | 1 | 1 | 0 | 0 |
| Caesar | 1 | 1 | 1 | 1 |
| Calpurnia | 0 | 1 | 0 | 0 |
| Cleopatra | 0 | 0 | 0 | 1 |

这张矩阵的致命问题一眼可见：**它是一个「词项 × 文档」的二维结构，而真实语料里 99.9% 的格子是 0。** 有 40 万个词项、上亿篇文档时，这张矩阵的规模是 $4 \times 10^5 \times 10^8 = 4 \times 10^{13}$ 个格子——存不下，也扫不动。

## 2 转置：从「词—文档矩阵」到倒排索引

问题的解法，是把矩阵**转置**：**不再问「这篇文档里有哪几个词」，而是问「这个词出现在哪几篇文档里」。** 这个转置出来的结构，就是倒排索引。

**倒排索引（inverted index）**：为每个词项维护一个**倒排表（postings list）**——按升序存放出现该词项的所有文档编号；所有「词项 → 倒排表」的映射合起来，构成倒排索引。

用 Python 写出来，就是一本普通的字典：

```python
# 词项 → 文档编号列表（编号从 1 开始）
inverted_index = {
    "brutus":    [1, 2],
    "caesar":    [1, 2, 3, 4],
    "calpurnia": [2],
    "cleopatra": [4],
}
```

注意它和「矩阵」的关系：矩阵第 $t$ 行上所有非零格子所在的列，就是词项 $t$ 的倒排表。**矩阵是「以文档为列」的组织方式，倒排索引是「以词项为入口」的组织方式**——入口不同，查询的开销天差地别。用矩阵回答「Brutus 出现在哪几篇」要扫描整行；用倒排索引，一次哈希查找就拿到 $[1, 2]$。

**辨析｜易错点：倒排索引的键是「规范化后的词项」，不是原文里的单词。** 语料里可能出现 `Brutus`、`brutus`、`BRUTUS` 三种写法，它们必须在索引构建前被统一成一个词项（第 6 节），否则查询 `brutus` 永远匹配不到文档里的 `Brutus`。「查询与文档使用同一套规范化规则」这一条铁律，我们在上一篇就立下了，这里就是它的用武之地。

## 3 倒排索引的数据结构：词典 + 倒排表

倒排索引在物理上分两部分：

- **词典（dictionary）**：存放所有出现的词项，以及每个词项的**文档频率（document frequency, df）**——即出现该词项的文档数。词典就是字典的「键」。
- **倒排表（postings）**：每个词项对应的文档编号列表，按**升序**排列。词典中的每个键都指向一条倒排表。

下图把这个结构画出来：左边是词典（含 df），右边是倒排表，箭头表示「词项 → 倒排表」的映射。

![倒排索引结构：词典与倒排表](/images/information-retrieval/shakespeare-inverted-index-example-1.svg)

**倒排表必须按文档编号升序排列**，这一点怎么强调都不过分——它是第 5 节「合并求交集」能在线性时间完成的前提，也是后面跳表（skip pointers）、间隙编码（gap encoding）这些优化技术的共同基础。Manning 在全书中反复回到「倒排表有序」这个不变量。<span class="marginnote">「有序列表 + 双指针合并」，在第三级《数据结构》里就是归并（merge）的标准场景；倒排表相交是归并在检索里的第一次落地。后面第五篇的跳表，则是为这个归并加速。</span>

## 4 公式解析：倒排索引的一个词条

倒排索引里一个词项对应的完整数据，可以写成一条三元式——不，是**一个二元组**：

$$\text{index}[t] = \left( \text{df}_t,\; \langle d_1, d_2, \ldots, d_{\text{df}_t} \rangle \right)$$

逐项拆解，四步：

- **第一步，$t$ 是词典的键。** $\text{index}[t]$ 表示「对词项 $t$ 取它的索引条目」。在实现里就是字典的一次查找：Python 的 `inverted_index["brutus"]`。
- **第二步，$\text{df}_t$ 是文档频率。** 它是「出现词项 $t$ 的文档数量」，和词频（term frequency, tf，一个词在单篇文档里出现多少次）不是一回事。$\text{df}_t$ 的量纲是「篇数」，它衡量的是 $t$ 在**文档层面**有多常见——这是第四篇 IDF 的原料，先在这里记住它。
- **第三步，$\langle d_1, d_2, \ldots, d_{\text{df}_t} \rangle$ 是倒排表。** 尖括号表示**有序序列**：$d_1 < d_2 < \cdots < d_{\text{df}_t}$，列表长度恰好等于 $\text{df}_t$。对照例子：$\text{index}[\text{caesar}] = (4, \langle 1, 2, 3, 4 \rangle)$。
- **第四步，为什么是有序序列而不是无序集合。** 因为查询处理的核心操作是「求两个倒排表的交集 / 并集」，有序序列让双指针扫描得以在线性时间内完成（第 5 节）；而无序集合只能靠哈希或嵌套循环，慢一个量级。**「有序」是这个数据结构一切性能承诺的根源。**<span class="marginnote">把「集合」换成「有序序列」正是工程对数学的第一次让步：为了快，我们放弃元素的交换性，牺牲掉一点概念优雅，换来 $O(x+y)$ 的归并。</span>

## 5 用倒排表处理布尔查询：合并求交集

有了倒排索引，布尔查询「**Brutus AND Caesar**」就变成一条非常干净的算法：把两条倒排表**求交集**。因为两条表都按升序排列，可以用双指针同时扫描，谁小谁前进：

```python
def intersect(p1, p2):
    i = j = 0
    result = []
    while i < len(p1) and j < len(p2):
        if p1[i] == p2[j]:
            result.append(p1[i])
            i += 1
            j += 1
        elif p1[i] < p2[j]:
            i += 1
        else:
            j += 1
    return result

intersect(inverted_index["brutus"], inverted_index["caesar"])
# [1, 2]  —— 两部剧同时出现 Brutus 与 Caesar
```

两条长度分别为 $x$ 与 $y$ 的倒排表求交集，时间复杂度是

$$O(x + y)$$

而不是 $O(x \times y)$。差别是本质性的：在「Brutus 出现于 100 万篇、Caesar 出现于 5 亿篇」的真实场景里，$x+y$ 是百万级，$xy$ 是 $10^{14}$ 级——**排序 + 双指针，把一次布尔查询从「不可行」变成「毫秒级」**。这就是倒排索引的威力所在。<span class="marginnote">OR 查询只是把「谁小谁前进」换成「把两条都收进来」，并集同样 $O(x+y)$；真正昂贵的是 NOT——求补集要遍历全集，所以工程上「NOT 词」通常单独处理、后置过滤，Manning 第 1 章对此有专门讨论。</span>

## 6 预处理：从文本到词项

倒排索引的键是词项，但文档里的原始文本不是词项。从原始文本到词典，要经过一条预处理流水线，Manning 称之为**词项化（tokenization）与规范化（normalization）**：

- **分词（tokenization）**：把连续文本切成一个个词元。英文按空格与标点切即可；中文没有空格，需要专门的分词器——这在本专题第三篇《中文检索的特殊性：分词与单字索引》会展开，也与第四级《自然语言处理》的分词一节直接衔接。
- **大小写折叠（case folding）**：`Brutus`、`brutus`、`BRUTUS` 统一成 `brutus`。
- **去停用词（stop word removal）**：去掉 `the`、`a`、`of` 这类高频但无检索信息的词，能显著压缩索引体积。
- **词干化（stemming）**：`retrieval`、`retrieved`、`retrieving` 归并为词干 `retriev`。

**辨析｜易错点：索引时的预处理，必须与查询时的预处理逐字一致。** 如果文档入库时做了词干化而查询没做，`retrieved` 进了索引，查询 `retrieving` 却查不到——召回率瞬间归零。这条「同一套规范化」的铁律，在 RAG 里同样成立：索引时怎么切块分词，查询时就要怎么切块分词。

## 7 小结

- **关联矩阵 vs 倒排索引**：前者是「词 × 文档」的稀疏矩阵，后者是它的**转置**——「词项 → 文档编号列表」，是搜索引擎的数据地基。
- **结构**：倒排索引 = **词典**（词项 + 文档频率 df）+ **倒排表**（有序的文档编号序列）。
- **核心公式**：$\text{index}[t] = (\text{df}_t,\; \langle d_1, \ldots, d_{\text{df}_t} \rangle)$，倒排表必须**升序**。
- **查询处理**：布尔 AND 是两条有序倒排表的双指针求交集，复杂度 $O(x+y)$，把全库扫描变成只碰相关倒排表。
- **预处理**：分词 → 大小写折叠 → 去停用词 → 词干化；索引与查询必须用同一套规则。

在下一节，我们将暂时离开具体的索引，回到评测这条主线：如何判断一个检索系统到底好不好——这就是**检索评测方法：测试集、查询集与相关性判定**。
