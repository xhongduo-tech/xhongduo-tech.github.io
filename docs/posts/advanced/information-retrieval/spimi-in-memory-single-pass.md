## 为什么从"单次扫描"开始

上一篇我们用**块排序法（BSBI）**证明了"即使内存放不下，索引也能造出来"——它的策略是分块、排序、合并，像归并排序一样把规模硬扛过去。但 BSBI 有一个隐蔽的浪费：**它明明已经能确认每个词项属于哪篇文档，却仍要先排序，再在合并阶段反复处理同一个词项**。排序是为了什么？为了归并时能"按字典序对齐"。可如果我们根本不需要排序就能把倒排表按文档编号排好，那这趟排序就是纯开销。

**基于哈希的内存单次扫描构建（Single-Pass In-Memory Indexing，SPIMI）**正是抓住这一点：用哈希表把每个词项的倒排表直接累积在内存里，词项首次出现时为其分配一块空间，后续出现就追加——文档编号天然按扫描顺序递增，追加即有序，根本不需要排序。这一改，让 SPIMI 比 BSBI 更快、更省内存，成了现代搜索引擎处理海量文档时的主流选择。<span class="marginnote">SPIMI 出自 Manning《IIR》第 4.2 节。它的思想后来演化为开源搜索引擎 Lucene 索引构建的核心——今天你搜索时享受的毫秒级响应，底层很可能就有 SPIMI 的直系后代在跑。</span>

## 1 从 BSBI 到 SPIMI：省掉哪一步

回顾 BSBI 的三步：分块、块内排序、归并。SPIMI 把第二步"块内排序"整个删掉了。它凭什么是正确的？

关键在于倒排表的有序性要求。倒排表要求文档编号**升序**，而文档扫描本身就是从编号 1 开始逐篇递增的。只要我们把"第 $d$ 篇文档里出现的词项"逐个追加进该词项在内存中的倒排表尾部，那么追加进去的文档编号天然严格递增——**扫描顺序就是有序性**。既然有序不需要排序来保证，块内排序这一步就纯粹是多余的了。<span class="marginnote">这里的直觉值得刻进脑子里：<strong>如果数据的到达顺序恰好满足输出要求，就不要排序。</strong> 这跟外部排序里"输入近有序时用插入排序"是同一个道理——算法要贴着数据已有的结构走，而不是机械套模板。</span>

但省掉排序不是没有代价。BSBI 靠"排序"把一个词项的所有出现聚到一起，SPIMI 则要**记住每个词项的倒排表在内存里的位置**——这是哈希表的工作。哈希表给出的是 $O(1)$ 的"词项 → 倒排表指针"定位，用空间（哈希表本身）换时间（免排序）。

**重点：SPIMI 的省，省在"免排序"；它的花，花在"哈希表"。** 当内存紧张到连哈希表都放不下时，SPIMI 的优势会缩小——但实践中，哈希表比排序缓冲区便宜得多，SPIMI 综合胜出。

## 2 SPIMI 的完整流程

把 SPIMI 的每一步拆开看。设文集被切成若干块（每块大小由内存预算决定），对每一块执行：

1. **逐文档扫描**：对当前文档 $d$，逐个读出其中的词项 $t$。
2. **哈希定位**：在词典哈希表中查 $t$。
   - 若 $t$ **首次出现**：向哈希表插入 $t$，并分配一段连续内存作为它的倒排表，把 $d$ 写入（此时倒排表为 `[d]`）。
   - 若 $t$ **已存在**：在它已有的倒排表尾部**追加** $d$。若表尾恰好就是 $d$（同一文档里重复出现），就顺带把词频 $\text{tf}$ 加一——这符合"倒排项里存 $(d, \text{tf})$"的设计。
3. **块内完成**：本块所有文档处理完毕，就把这一块哈希表里积累的倒排表连同词典一起写盘（称为一个**中间块**）。

关键在于第 2 步的**就地追加**：文档编号是递增到达的，所以每张倒排表写完就是有序的，无需任何排序步骤。<span class="marginnote">同一文档里重复出现的词项如何处理？SPIMI 有两种选择：要么在扫描文档时先按词项聚合词频，再一次性追加；要么先追加文档编号，词频在后续合并阶段再统计。IIR 介绍的简化版直接把每篇文档内的重复词项各自追加一次，词频字段留待合并时归并——细节取舍不影响整体思想。</span>

处理完所有块之后，剩下一件事：**把中间块合并成最终的全局索引**。这一步和 BSBI 的归并几乎一样：多路归并时，同一个词项的倒排表跨块出现，要按文档编号拼接起来；若是 $(d, \text{tf})$ 完整版，还要把同一文档的多次出现合并成一个倒排项。

## 3 为什么 SPIMI 更省内存

BSBI 的内存大头是**排序缓冲区**：为了给每个词项排序，得先把"词项 + 文档编号"的记录攒够一大块，再整体排序。排序意味着中间状态的体量远超最终结果——你不可能边读边排，必须等一批。

SPIMI 的内存开销只有两块：**哈希表本身**与**倒排表的累积空间**。倒排表的内容就是最终要写盘的内容，几乎零冗余；哈希表则是唯一"额外"的开销，但它只存词项与指针，体量小得多。IIR 里的关键结论是：

$$M_{\text{SPIMI}} \approx M_{\text{BSBI}} \times \frac{1}{2} \sim \frac{1}{3}$$

也就是说，**同样的内存预算，SPIMI 能处理的块大约是 BSBI 的三倍大**——意味着中间块更少、归并轮数更少、整体 IO 更少。<span class="marginnote">一个数量级感受：BSBI 因为排序，内存里同时堆着"未排序记录"与"排序后结果"两份状态；SPIMI 只有一份。省掉排序不只省时间，还直接省了"存在两份"的那份内存。</span>

此外，SPIMI 还有两个实际层面的优势：其一，词项不必等整块读完才处理，**处理到哪写到哪**，流水线化天然友好；其二，哈希表可以按需增长，不像排序缓冲区需要预先留足整块空间。

## 4 公式解析：为什么"追加即有序"

SPIMI 的正确性不依赖排序，这一点值得用公式语言说透。

设扫描按文档编号顺序处理，已处理的文档为 $1, 2, \dots, d$。词项 $t$ 的倒排表当前为 $L_t = [d_1, d_2, \dots, d_k]$，其中各编号满足：

$$d_1 < d_2 < \cdots < d_k$$

现在读到文档 $d' > d$（严格大于，因为编号唯一且递增）。若 $d'$ 含 $t$，我们把它追加到 $L_t$ 尾部得到 $[d_1, \dots, d_k, d']$。因为 $d_k \le d < d'$，有 $d_k < d'$，故新的倒排表仍严格递增：

$$d_1 < d_2 < \cdots < d_k < d'$$

三步拆解：

- **第一步，读清前提**：$d' > d$ 由"按编号递增扫描"保证，$d_k \le d$ 由"$L_t$ 只包含已扫描文档"保证。
- **第二步，看透传递性**：$d_k \le d < d'$ 推出 $d_k < d'$，于是追加不破坏顺序。
- **第三步，归纳**：从空表出发，每一步追加都保持"严格递增"这一不变量。数学归纳法完成——**有序性是结构保证的，不是排序算出来的**。

这条归纳论证就是 SPIMI 全部正确性的核心：它把"排序保证有序"替换成"扫描顺序保证有序"，代价从 $O(T \log T)$ 降到每词项 $O(1)$ 追加。

## 5 什么时候 SPIMI 不够用

SPIMI 不是银弹，三个场景会让它露出软肋：

- **内存里放不下哈希表**：当词典巨大（如多语种、海量唯一词项）时，哈希表的开销可能超出预算，此时 BSBI 的"排序后按字典序流式写盘"反而更稳——排序天然给词项排了序，后续归并是顺序读。
- **需要全局词项排序的场合**：某些索引结构（如需要前缀压缩的词典，见《词典压缩》）喜欢词项按字典序排列。SPIMI 的哈希表给的是随机序，要转成字典序还得补一趟排序——这时 BSBI 的副产品（排序结果）反而免费。
- **极端分布**：若某个词项出现在几乎每篇文档里（如停用词没过滤），它的倒排表会异常庞大，可能撑爆为它分配的内存块。这提示我们：**索引构建前先做停用词过滤与词项规范化，既减体积又保稳定**。

**辨析｜易错点：SPIMI 不是"不需要磁盘"。** 它只是"块内"免排序、免溢写，块与块之间仍然要写中间块并归并——当总规模远超内存时，归并阶段依然存在。把 SPIMI 理解成"完全内存、零磁盘"是常见误读。**正确的理解是：SPIMI 在单块内省掉了排序，跨块的归并依旧不可避免。**

## 6 小结

- **SPIMI** = 哈希表 + 就地追加：词项首次出现时分配倒排表空间，后续出现即追加。
- **省掉排序的原理**：扫描编号天然递增，追加即有序——有序性是结构保证的，数学归纳可证。
- **更省内存**：无排序缓冲区，内存只有哈希表与倒排表本体，同样预算可处理约 2–3 倍的块。
- **与 BSBI 的分工**：SPIMI 快而省，但产出随机序的词典；BSBI 慢而稳，附带字典序副产品。
- **软肋**：词典巨大、需要全局词项排序、词项分布极端时，SPIMI 未必是最优。

在下一节，我们将回答"单机内存不够、甚至单机算力都不够时怎么办"——把索引构建拆到一群机器上并行做，这就是**分布式索引构建：MapReduce 方案**。
