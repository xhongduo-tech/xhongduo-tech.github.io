## 为什么从"指标"开始

前几篇我们设计了搜索系统的每一部分——架构、流水线、分布式、缓存、级联。但设计得好不好，必须用指标回答：**查询快不快？系统扛不扛得住？新内容搜不搜得到？** 没有指标，架构讨论就是"我觉得快"。**性能指标是搜索系统的"仪表盘"——它告诉你系统现在在哪、优化有没有效果。**

搜索系统的性能指标有三根支柱：**延迟（latency）**——单次查询多快；**吞吐（throughput）**——单位时间能扛多少查询；**索引新鲜度（freshness）**——新内容多久可搜。三者互相关联又互相制约：延迟优化可能伤吞吐，吞吐扩展可能伤新鲜度，新鲜度优先可能伤延迟——**系统优化就是在这三者之间找平衡**。<span class="marginnote">性能指标与《第一篇》的检索质量指标（NDCG、MAP）是两套体系：<strong>质量指标回答"结果好不好"（相关性），性能指标回答"系统快不快"（速度与容量）</strong>。工业系统两个仪表盘都要盯——质量指标指导"模型优化"，性能指标指导"架构优化"，两者可能冲突（更强的模型更慢），最终由产品目标（体验 vs 成本）调和。</span>

## 1 延迟：单次查询的速度

**核心概念：延迟（latency）**：从用户发出查询到收到结果的时间。常用分位数度量，而非平均值。

延迟的三个要点：

**分位数比平均更重要**：平均延迟 50ms 可能是"90% 的查询 10ms、10% 的查询 400ms"——但用户体验由"最慢的那 10%"决定。**工业标准看 P50、P95、P99**——P99 是"最慢的 1% 用户等多久"。
**延迟预算分解**：查询链路每步的延迟加起来要低于预算（前面算过）——**延迟优化是"找最大项，消最大项"**。
**尾部延迟（tail latency）**：P99 的优化比 P50 难得多——尾部由"慢机器、缓存未命中、GC 停顿"等长尾因素主导，需要"重试、冗余请求、慢请求取消"等手段。<span class="marginnote">为什么 P99 比平均值重要？<strong>因为用户感知的是"最慢的那次"</strong>——一个用户发 3 次查询，遇到一次 400ms 的概率取决于 P99 而非平均。工业上有句行话"你的平均值骗了你"：平均延迟被大量快查询拉低，掩盖了慢查询的真实占比。<strong>优化延迟，先看 P99 曲线，再动手</strong>。</span>

**重点：延迟是"分位数"指标，不是"平均"指标——优化目标是压 P95/P99，而不是平均。** 一个把 P99 从 400ms 压到 150ms 的优化，比把平均从 50ms 压到 40ms 的优化有价值得多。

## 2 吞吐：系统的容量

**核心概念：吞吐（throughput）**：单位时间内系统能处理的查询数，常用 QPS（queries per second）衡量。

吞吐的要点：

**延迟与吞吐的权衡**：吞吐提高（并发增大）会推高延迟——系统在"某个延迟阈值下能扛多少 QPS"是有上限的。**工程上定义"延迟约束下的最大吞吐"（如 P99 < 150ms 时最大 QPS）**。
**扩展方式**：垂直扩展（单机更强）与水平扩展（加机器）——检索系统主要靠水平扩展（分片 + 副本，前面讲过）。
**瓶颈定位**：吞吐瓶颈通常在"最贵的环节"——精排模型、向量检索、缓存未命中的全量检索。**优化吞吐 = 找出瓶颈环节，减它的成本或加它的并行度**。<span class="marginnote">吞吐与延迟的经典关系：<strong>系统在低负载时延迟低，负载升高延迟攀升——延迟-吞吐曲线</strong>。曲线的拐点附近，延迟开始急剧恶化——工程上要"在拐点左侧运行"（留余量），并监控"距离拐点多远"。这个"负载-延迟"的动态关系，是容量规划的核心——<strong>给系统留余量，就是在拐点左侧运行</strong>。</span>

**辨析｜易错点：高 QPS ≠ 高性能。** QPS 高但 P99 爆炸，是"用延迟换吞吐"——用户感受很差的"高性能"。**正确的表述是"P99 < X 的前提下，QPS ≥ Y"**——延迟与吞吐永远成对说，分开说都会骗人。

## 3 索引新鲜度：内容的时效

**核心概念：索引新鲜度（index freshness）**：从文档被采集/发布，到它出现在搜索结果里的时间。也常叫"索引延迟"（indexing latency）或"文档可搜延迟"。

新鲜度的三个层次：

**数据新鲜度**：索引里有"多新"的数据——新文档多久进索引。
**处理新鲜度**：文档从"被采集"到"被索引"的处理链路耗时。
**结果新鲜度**：用户实际"看到"的新内容——缓存可能挡住新内容（缓存与新鲜度的权衡，前面讲过）。<span class="marginnote">新鲜度的度量单位：<strong>秒级（新闻、社交、电商——新内容即时可搜）、分钟级（一般搜索）、小时级（学术、归档）</strong>。不同产品的新鲜度需求差三个数量级——"索引延迟压到秒级"对新闻搜索是刚需，对图书搜索是浪费。新鲜度是"按业务需求配置的指标"，不是"越小越好"。</span>

**重点：新鲜度不是"越小越好"，而是"匹配业务需求"——新闻要秒级、学术要小时级。** 强制秒级新鲜度会让索引构建与合并成本暴涨（动态索引篇的"新鲜度 vs 成本"权衡）；强制小时级会让新闻搜索失去意义。**新鲜度指标的设定，是业务需求的工程翻译**。

## 4 公式解析：三者如何互相制约

把延迟、吞吐、新鲜度放进一个关系式，看清它们的纠缠。设查询延迟 $L$，系统 QPS 上限 $Q_{\max}$，索引更新频率 $F$（每秒更新文档数）：

$$Q_{\max} \approx \frac{1}{L \times \text{并发利用率}}, \qquad \text{更新成本} \propto F \times (\text{合并/索引开销})$$

三步拆解：

- **第一步，看延迟 → 吞吐**：延迟越低，单个查询占资源时间越短，单位时间能处理的查询越多——**延迟是吞吐的上限约束**。
- **第二步，看新鲜度 → 延迟**：更新频率 $F$ 越高，索引合并越频繁（动态索引篇），合并期间查询变慢——**新鲜度成本会侵蚀延迟**。
- **第三步，看整体权衡**：三者构成一个"不可能三角"——**同时要"低延迟 + 高吞吐 + 秒级新鲜度"几乎不可能，必须牺牲一个**。新闻搜索牺牲吞吐成本（大集群），学术搜索牺牲新鲜度（小时级）。

**核心结论：延迟、吞吐、新鲜度构成"不可能三角"——工程优化的本质是"明确牺牲哪一个，然后优化另外两个"。**<span class="marginnote">这个"不可能三角"的思维可以泛化到任何系统设计：<strong>任何"又快、又省、又好"的诉求都是不现实的，好的设计明确说出"我在哪个维度妥协"</strong>。搜索系统在这里妥协的是成本（想要三者都好 = 买更多机器）。工业上"性能优化"很少是"把三者都变好"，而是"在指定约束下把某个维度压到极致"——先定约束，再谈优化。</span>

## 5 性能优化的方法论

性能指标不只是"看"，还要指导"做"。搜索系统性能优化的标准流程：

1. **建立基线**：测出当前 P50/P95/P99、QPS、新鲜度。
2. **定位瓶颈**：用 profiling 找出"最贵的一环"——通常是精排模型、向量检索、缓存未命中的全量检索、或合并期间的抖动。
3. **优化瓶颈**：针对性手段——模型蒸馏（精排变快）、ANN 参数调优（向量检索变快）、缓存扩容（命中率提升）、合并调度（避开高峰）。
4. **回归验证**：改完重测，确认 P99 降了、QPS 升了、新鲜度没崩——**指标回归是"优化是否有效"的唯一裁判**。<span class="marginnote">一个常见的性能优化反模式：<strong>在不知道瓶颈在哪的情况下盲目优化"看似慢"的环节</strong>——比如疯狂调 ANN 参数，结果瓶颈在精排模型。正确姿势是"先 profiling、后动手"：用火焰图、分环节计时找到真正的热点。检索系统优化的 80% 收益，来自"找到最大的那一项并消掉它"——其余 20% 才是细节打磨。</span>

**辨析｜易错点：性能指标要在"真实负载"下测。** 单机小流量测试的延迟，与真实并发下的延迟完全不同（资源竞争、排队效应）。**性能测试要在"接近生产的负载"下做**——压测工具模拟真实流量分布，测出的 P99 才可信。低负载下的"快"，骗不了真实用户。

## 6 小结

- **三大支柱**：延迟（单查询速度）、吞吐（系统容量）、新鲜度（内容时效）——互相关联又互相制约。
- **延迟看分位数**：P95/P99 比平均重要——尾部延迟决定用户体验，优化目标压 P99。
- **吞吐配约束**："P99 < X 前提下 QPS ≥ Y"——高 QPS 不等于高性能，延迟吞吐成对说。
- **新鲜度按需求**：新闻秒级、学术小时级——不是越小越好，是匹配业务。
- **不可能三角**：低延迟 + 高吞吐 + 秒级新鲜度不可兼得——明确牺牲哪个，优化另外两个。
- **优化方法论**：建基线 → 定位瓶颈 → 优化瓶颈 → 指标回归；真实负载下测试。
