## 为什么从"预测"开始

前几篇都在改进查询——纠错、分词、扩展、改写、反馈。但有一个更根本的问题一直没问：**这个查询本身，检索会成功吗？** 有的查询一搜就有好结果（"深度学习 定义"），有的查询怎么搜都难（"红葡萄酒 冠心病 长期影响"、极长尾的专名、拼写全错的词）。**"这一搜值不值得、会不会失败"如果在检索前就能预测，系统就能提前调整策略。**

**查询性能预测（query performance prediction，QPP）** 回答的正是这个问题：**在检索之前（或刚检索完）预测"这个查询的检索质量"**。它的价值不亚于查询理解的任何一环——因为它让系统"知道自己不知道"：预测到差查询，可以触发改写、放宽召回、请求澄清、或调整排序置信度。<span class="marginnote">查询性能预测在学术上叫 QPP（Query Performance Prediction），早期也叫"query difficulty estimation"——估计查询的"难度"。<strong>它的应用场景非常实际：预测"差查询" → 触发补救（改写、扩展、对话澄清）；预测"好查询" → 加快响应（跳过昂贵步骤）</strong>。检索系统不是"所有查询一视同仁"，而是"把资源投给值得的查询"——QPP 是这种资源分配的眼睛。</span>

## 1 查询难度从哪来

一个查询为什么难搜？原因可以归为几类：

**歧义**："苹果"、"Java"——一个词多个意思，检索器不知道该给哪一面。
**词汇鸿沟**：查询用的词，文档全用别的词表达——词面匹配注定失败。
**信息不足**："推荐一下"——查询本身信息量太少，没有足够信号区分文档。
**稀有性**：极长尾的专名、新词——文集中几乎没相关文档。

**重点：查询难度不是一个"查询属性"，而是"查询 × 文档集"的关系。** "深度学习"在 AI 文集中好搜，在菜谱文集中难搜——**同样的查询，换个文集难度天差地别**。预测的是"这个查询在这个文集里好不好搜"，不是"这个查询本身难不难"。<span class="marginnote">这个"查询 × 文集"视角很重要：<strong>查询性能预测的输入必须包含"文集侧的信息"</strong>——比如查询词在文集里的文档频率（$df$）分布、检索结果里分数的分布。只靠查询文本本身预测难度，是"盲人摸象"；结合文集统计，才看得准。</span>

## 2 预测信号：检索前与检索后

查询性能预测的信号分两大类：

**检索前信号（pre-retrieval predictors）**——只用查询与文集统计：

查询词的 $df$ 分布（词普遍还是稀有）。
查询长度（太短可能信息不足，太长可能过于具体）。
查询歧义度（词的多义性，从词向量或词库估计）。
查询与文档集的"先验匹配度"。

**检索后信号（post-retrieval predictors）**——用检索结果的分布：

**结果分数的分布**：如果 Top 文档的分数都很低且接近（都"勉强匹配"），说明没找到真正相关的——**分数区分度差 = 结果差**。
**结果间相似度**：如果 Top 文档高度相似（都讲同一件事），可能只覆盖了查询的一个侧面——**结果多样性差 = 可能偏科**。
**结果与查询的重合度**：Top 文档与查询的匹配强弱。<span class="marginnote">检索后信号里最著名的直觉是"清晰度（clarity）"：<strong>如果检索结果的语言模型与"文档集整体语言模型"差异很大（结果很有特色），说明检索找到了"专注的、一致的"内容——查询质量可能高；如果结果的语言模型与背景几乎一样（结果毫无特色），检索多半失败了</strong>。这个"结果是否比背景更聚焦"的度量，是 QPP 里最具解释力的信号之一。</span>

## 3 公式解析：一个经典的检索后预测器

用一个具体的检索后信号——"结果分数分布"——来理解 QPP 的计算。设某查询的 Top-$K$ 检索分数为 $s_1 \ge s_2 \ge \dots \ge s_K$，定义一个"分数区分度"预测器：

$$\text{QPP}(q) = \frac{s_1 - s_K}{\frac{1}{K}\sum_{i=1}^{K} s_i}$$

三步拆解：

- **第一步，读分子**：$s_1 - s_K$ 是最高分与最低分的差距——**差距大说明"有鹤立鸡群的结果"（检索找到了明确的赢家）**。
- **第二步，读分母**：平均分——**归一化，消除不同查询的分数尺度差异**（BM25 分数尺度随查询变化）。
- **第三步，读语义**：$\text{QPP}(q)$ 大 → 结果分数拉开差距 → 检索"有把握"；$\text{QPP}(q)$ 小 → 结果分数挤成一团 → 检索"没把握"。**这个信号可以在检索后立即算出，用来决定"要不要补救"**。

**核心结论：QPP 的通用思路是"用检索结果的内在结构（分数分布、多样性、清晰度）推断检索质量"。** 结果越"聚焦、有区分、有特色"，质量越高。<span class="marginnote">一个重要的提醒：<strong>检索后信号有一个"自证"风险——它看的是"这次检索的结果"，而结果好坏依赖检索器本身</strong>。如果检索器本身差，它的"差结果"可能看起来也"结构良好"。所以 QPP 预测的是"这次检索的质量"，不完全等于"查询的固有难度"——两者有区别，但预测的目的（触发补救）两者都够用。</span>

## 4 QPP 的下游应用：资源分配

查询性能预测的真正价值在下游应用——**它让系统"把资源花在刀刃上"**：

**触发补救**：预测为"差查询" → 触发查询改写、伪相关反馈、放宽召回、对话澄清（第十四篇的主动澄清就是"预测到查询难，直接问用户"）。
**调整排序置信度**：预测为"难查询" → 排序分数压低置信度、结果页提示"无满意结果"。
**资源分级**：预测为"好查询" → 用更快更省的处理；"差查询" → 投入更多计算补救——**性能预测是"查询级资源调度"的决策输入**。<span class="marginnote">这个"资源分级"的应用与生成式改写（上一篇）直接联动：<strong>QPP 预测难查询 → 才舍得用 LLM 改写（贵但值）；QPP 预测好查询 → 走便宜的老路</strong>。工业检索系统里，QPP 是"昂贵组件（LLM、深度精排）该不该上"的守门员——它决定了系统把算力预算花在哪。理解了 QPP，你就理解了"检索系统不是功能堆砌，而是资源调度"。</span>

**辨析｜易错点：QPP 不是"预测排名质量"的精确工具，是"概率性的分诊器"。** QPP 的预测与真实检索质量的相关性通常在 0.3–0.6（相关系数），远不是完美——它只能"大概分诊"，不能"精确诊断"。**把 QPP 当"粗筛"而非"精确测量"，用在"决定是否补救"而非"宣布查询必失败"，是正确的使用姿势。**

## 5 现代 QPP：从统计信号到学习模型

QPP 也在进化：

**统计信号时代**：清晰度、分数分布、多样性等手工信号（本篇前几节的例子）。
**学习时代**：把多个信号作为特征，训练模型预测"检索质量"（以真实相关性标注或用户行为为标签）——**QPP 本身变成一个学习问题**。
**LLM 时代**：让大模型直接评估查询难度、检索结果质量——"这个查询的检索结果可信吗"，LLM 可以给出"有理解力"的判断。<span class="marginnote">LLM 做 QPP 很有意思：<strong>它不需要训练数据，靠"理解"判断"这个查询难不难、这些结果靠不靠谱"</strong>。这比统计信号更"聪明"（能理解语义层面的难度），但贵且慢。工业上的分层：统计信号做"每查询都跑的便宜分诊"，LLM 做"高价值/高风险查询的深度诊断"——又是"便宜分层 + 昂贵兜底"的老配方。</span>

**重点：QPP 的现代形态是"统计信号 + 学习模型 + LLM 分层"的组合——便宜的每查询跑，贵的按需跑。** 它的目的始终如一：**让检索系统知道自己这一搜好不好，从而决定下一步怎么走**。

## 6 小结

- **QPP**：检索前/后预测"这个查询的检索质量"——让系统"知道自己不知道"。
- **难度来源**：歧义、词汇鸿沟、信息不足、稀有性——难度是"查询 × 文集"的关系。
- **两类信号**：检索前（词频、长度、歧义度）+ 检索后（分数分布、结果多样性、清晰度）。
- **经典预测器**：$\text{QPP} = (s_1 - s_K)/\text{mean}(s)$——结果分数区分度大 = 检索有把握。
- **下游应用**：触发补救、调整置信度、资源分级——"把算力花在值得的查询上"。
- **现代形态**：统计信号 + 学习模型 + LLM 分层；预测是概率性分诊，不是精确诊断。
