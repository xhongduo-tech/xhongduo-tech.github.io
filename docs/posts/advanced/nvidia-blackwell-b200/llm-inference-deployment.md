## 为什么从推理部署开始

前面二十篇把 Blackwell 从晶体管讲到了软件栈。这一篇回答最终极的问题：**这套平台拿来做大模型推理，到底怎么部署、能跑多快。** 推理是「AI 工厂」真正挣钱的那个环节——训练训一次，推理跑无数次。而推理的瓶颈不在算力而在**内存带宽与容量**：每生成一个 token，都要把整个模型读一遍。B200 的 192GB 与 8 TB/s，就是冲着这个瓶颈来的。理解推理的内存墙模型，你才算真正理解「为什么 192GB 与 8 TB/s 是 B200 最值钱的两个数字」。

## 1 Prefill 与 Decode：两副面孔的推理

LLM 推理被清晰地切成两个阶段，各自的计算画像完全不同：

- **Prefill（预填充）**：处理整段输入提示（prompt），一次算完所有 token 的注意力。它是**计算密集（compute-bound）**的——矩阵乘大、并行度高，靠张量核心的峰值算力。
- **Decode（解码）**：逐个生成输出 token，每步只算一个新 token。它是**访存密集（memory-bound）**的——每步都要把全部权重从显存读一遍，但只做很小的计算。

**两阶段的最优硬件策略不同**：Prefill 想要高算力（张量核心满载），Decode 想要高带宽（把权重尽快喂进计算单元）。这正是「Prefill/Decode 分离部署（disaggregation）」的动机——用不同配置的机器分别伺候两个阶段。<span class="marginnote">Prefill 与 Decode 的二分，与《大模型部署》专题的「推理性能建模」直接对应：算力与带宽的比例（Roofline 的运算强度）决定了一个负载在哪端受困。大模型部署的很多优化——批处理、投机解码、分离部署——本质上都是在「把 Decode 变成更像 Prefill」。</span>

## 2 内存墙下的解码：为什么 8 TB/s 决定生成速度

Decode 的带宽受限可以用一句话说清：**生成一个 token，必须把模型权重全部读一遍。** 设模型大小 $M$ 字节（存于显存），解码一个 token 需要读完这 $M$ 字节，因此单并发下的最大生成速度：

$$
r_{\text{max}} = \frac{B_{\text{mem}}}{M}
$$

其中 $B_{\text{mem}}$ 是显存带宽。代入数字：一个 70B 参数的模型，FP8 权重约 70 GB，B200 的 8 TB/s 带宽给出：

$$
r_{\text{max}} = \frac{8\times10^{12}\ \text{B/s}}{70\times10^9\ \text{B}} \approx 114\ \text{token/s}
$$

**这是单 GPU、单请求的上限**——不是算力不够，而是「读权重」的时间占了全部。把权重换成 FP4（约 35 GB），上限翻倍到约 228 token/s。<span class="marginnote">这个模型解释了三个现象：其一，<strong>模型越大，单卡生成越慢</strong>——不是因为算力，而是因为每次要读的权重更多；其二，<strong>低精度直接换速度</strong>——FP4 把 $M$ 减半，$r$ 翻倍；其三，<strong>批处理能救 Decode</strong>——多个请求共享一次权重读取，让带宽利用率大幅上升。这就是为什么推理引擎都拼命做批处理。</span>

## 3 TensorRT-LLM 的招数：批处理、KV 缓存与 FP4

NVIDIA 的推理引擎 **TensorRT-LLM** 围绕「榨干带宽与显存」设计，几招值得知道：

**动态批处理（in-flight / continuous batching）**：传统批处理要等整批请求一起结束才换下一批，GPU 在长短请求间空转；动态批处理让**任何时刻都塞满 GPU**——某个请求生成完了，立刻插进新请求，同一张卡永远在干活。对 Decode 的带宽利用是关键提升。

**Paged KV Cache（分页 KV 缓存）**：Decode 要不断读写历史 token 的 KV 向量，KV 缓存是显存大户。分页式管理让 KV 缓存像虚拟内存一样按页分配，**消除碎片、提高显存利用率**，直接增加可并发请求数。<span class="marginnote">KV 缓存的大小可以粗算：每个 token 的 KV 占用约 2 × 层数 × 头维度 × 精度字节。序列越长、并发越高，KV 缓存越大。B200 的 192GB 之所以能支撑「超长上下文 + 高并发」，一半功劳在显存大，一半在 Paged KV 缓存把碎片压住。</span>

**FP4 量化 + 投机解码**：前者把权重减半（带宽翻倍），后者用小模型「猜」下一批 token、大模型只做校验——猜中了就一次多生成几个 token，变相绕过「每 token 读一遍」的内存墙。

## 4 NVL72：万亿参数模型的单机推理

把镜头拉到机柜级：NVL72 的 72 颗 B200、约 13.8 TB HBM3e、130 TB/s NVLink，让「**把 1.8T 参数模型装进一个 NVLink 域**」成为现实。

**容量**：1.8T MoE 模型按 FP8 存约 1.8 TB 权重，72 颗 GPU 分摊绰绰有余；
**通信**：MoE 的专家分布在多卡上，token 按路由跨卡访问专家——全靠 NVLink 域内的低延迟；
- **吞吐**：NVIDIA 宣称 GB200 NVL72 可在单个机柜上以「实时」速度服务万亿参数模型，相对 H100 集群的推理加速高达 **30×**。

**部署形态的谱系**：小模型单卡跑（B200 的 192GB 能装下 70B FP8）；中等模型多卡张量并行；万亿参数 MoE 上 NVL72。**B200 的大显存把「模型要切多细」的选择面大幅拓宽**——很多以前要 8 卡才能跑的模型，现在 1–2 张 B200 就够了。<span class="marginnote">「少卡跑大模型」的价值不只是省钱：跨卡通信越少，服务的延迟越稳定。NVIDIA 官方称 B200 相对 H100 能把「需要 8 卡 H100 的模型」压缩到「2 卡 B200」——这背后的杠杆就是 192GB 容量与 FP4 精度，两个本专题反复强调的数字在此合流。</span>

## 5 公式解析：解码吞吐的带宽模型

解码阶段的性能模型是推理工程最核心的一条公式，值得完整推导一遍：

$$
r = \frac{B_{\text{mem}}}{M_{\text{weights}} + M_{\text{KV}}}
$$

逐项拆解：

- **$B_{\text{mem}}$**：显存带宽（8 TB/s）。Decode 是带宽受限的，算力再多也快不了。
- **$M_{\text{weights}}$**：每读一遍全量权重的字节数。低精度（FP4 vs FP8）直接减半它。
- **$M_{\text{KV}}$**：KV 缓存相关的读取。长上下文时 KV 也参与每步读取，把分母变大。
- **$r$**：单请求最大生成速率（token/s）。

**关键结论：提高推理吞吐的三条杠杆——提带宽（买新卡）、降权重（FP4 量化）、减 KV 开销（分页 + 长上下文优化）——全部指向同一条公式。**<span class="marginnote">对照《大模型部署》专题：「算力决定 Prefill 多快，带宽决定 Decode 多快，显存决定能同时服务多少人」。B200 在这三个轴上都把 H100 大幅拉开——算力约 2.3×（FP8）、带宽 2.4×（3.35→8 TB/s）、容量 2.4×（80→192GB），这就是「推理加速 30×」的底层来源。</span>

## 6 推理成本的工程账：批大小与吞吐

上一节讲了「单请求上限」，但真实服务里没人单请求跑 GPU——**批处理（batching）才是推理吞吐的真正杠杆**。把批处理的账算清楚，是推理成本工程的核心。

**为什么批处理能救 Decode？** Decode 每生成一个 token 要读一遍全部权重。若只服务一个请求，读一遍权重只产生一个 token；若同时服务 B 个请求，**读一遍权重可以产生 B 个 token**——权重读取的「成本」被 B 个请求分摊，有效吞吐近似乘上 B。<span class="marginnote">这正是「连续批处理（in-flight batching）」的底层逻辑：<strong>把带宽从「一请求一用」变成「一读多 token」。</strong>批大小越大，带宽利用率越高，每 token 成本越低。</span>

**但批大小不是越大越好**，它受三方面约束：

| 约束 | 表现 | 后果 |
| --- | --- | --- |
| 显存 | 每请求要存 KV 缓存 | 批太大 → 显存爆 |
| 延迟 | 批太大 → 单请求排队变慢 | 交互体验下降 |
| 算力 | Prefill 阶段算力会先到瓶颈 | 批太大 → 算力受限 |

于是「最优批大小」是**吞吐与延迟的平衡点**：对离线批处理（如大规模生成），可以开大 batch 追求极致吞吐；对在线交互（聊天、助手），必须压小 batch 保证首 token 延迟。<span class="marginnote">这个权衡在《大模型部署》里叫「吞吐-延迟曲线」：<strong>吞吐随 batch 单调上升，延迟随 batch 单调变差，工程就是在这条曲线上选点。</strong></span>

**每 token 成本怎么算？** 把整条链串起来：总成本（硬件 + 电费 + 运维）除以总 token 数，就是每 token 成本。B200 对它的贡献是：**同样的成本买到更多带宽与容量 → 同样 GPU 能同时服务更多请求 → 每 token 成本下降。** 这就是「30× 推理加速」在账单上的含义——不只是在实验室里更快，而是每个 token 更便宜。<span class="marginnote">回到《平台动机》一篇的「AI 工厂」比喻：<strong>工厂的竞争力不是「一次生产多快」，而是「单位成本生产多少」。</strong>批处理、FP4、大显存，全都是为这个「单位成本」服务的。</span>

## 7 小结

- LLM 推理分两阶段：**Prefill 计算密集、Decode 访存密集**，两阶段最优硬件策略不同。
- Decode 的带宽模型：$r = B_{\text{mem}} / M$
