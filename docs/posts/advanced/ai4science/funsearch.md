## 为什么从 FunSearch 开始

定理证明的路线图（前几篇）都是「让 AI 证明一个已知的命题」。但数学和科学真正的圣杯是**发现未知**——新构造、新算法、新规律。2023 年 12 月，DeepMind 在 Nature 上发表的 **FunSearch** 给出了一个令人耳目一新的答案：**不直接搜答案，而是用大语言模型搜索「能产生答案的程序」**。<span class="marginnote">FunSearch 的名字是「functions（函数）+ search（搜索）」的合成。它的意义在于：大模型输出的是<strong>人类可读的 Python 函数</strong>——不像黑箱神经网络那样「给个数值结果」，而是「给一个算法」。这个算法本身可以被数学家读懂、分析、改进。发现是透明的。</span>

这一篇拆解 FunSearch 的机制：它如何把「大模型」与「演化算法」结合成一个「程序搜索器」，它在**cap set 问题**与**在线装箱问题**上发现了什么，以及为什么「搜索程序」是比「搜索答案」更高级的搜索形态。

## 1 从「搜索答案」到「搜索程序」

传统计算发现（如 SAT 求解器、枚举搜索）都是**直接搜答案**：答案是「一个数」「一个集合」。FunSearch 把对象换成了**程序（函数）**——搜索空间是「所有可能的 Python 函数」。

为什么搜程序？三个理由：

1. **可验证**：函数能被**评估器（evaluator）**机械地打分——输入测试用例，看输出质量。这与定理证明的「内核验证」同构，但更简单：不需要形式化证明，只需要「跑起来看结果」。
2. **可复用**：一个发现的函数（如「更好的装箱策略」）是**可移植的算法**，能被任何人拿去用——发现一次，收益无限。
3. **可理解**：函数是人类写的语言（Python），数学家能读懂「它为什么好」，甚至继续改进——**发现不是黑箱，而是透明的算法**。<span class="marginnote">「程序即发现」的传统在数学里源远流长：1976 年四色定理用程序辅助证明，2010 年「开普勒猜想」的 Flyspeck 工程用程序辅助验证。FunSearch 的新意在于——<strong>程序不是人写的，而是 AI 演化出来的</strong>，且它发现的程序超过了人类此前设计的启发式。</span>

**核心概念：FunSearch 要解决的问题**是「给定一个可计算的数学/组合优化目标，找到最大化它的程序」。设函数空间为 $\Pi$，目标函数（适应度）为 $f$，FunSearch 试图找到 $\pi^* = \arg\max_{\pi\in\Pi} f(\pi)$。

## 2 演化循环：LLM 当变异算子，评估器当裁判

FunSearch 是一个**演化搜索（evolutionary search）**流水线，用大模型做「变异/交叉」，用评估器做「选择」。流程如下：

1. **初始种子**：一个人类写的「模板程序」——它实现了问题的基础框架，但留出关键部分待优化（如装箱的「放置策略」函数）。
2. **LLM 提出变体**：把「问题描述 + 模板 + 当前最好的几个程序（含代码与分数）」拼进 prompt，让 LLM 写一个新的改进版本。
3. **评估器打分**：每个被提出的程序在测试集上跑，算适应度（如 cap set 的大小、装箱的比率）。
4. **演化保留**：分数高的程序进入「孤岛数据库（islands）」——按分数分桶保存的最优程序集合。
5. **循环**：下一轮 LLM 的 prompt 里包含这些最佳程序，模型「站在前人的肩膀上」继续改进。<span class="marginnote">注意这里的精巧设计：LLM 每一轮<strong>看到的是「当前最优的一批程序」，而不是整个历史</strong>。这避免了「模型重复提出已试过的低分方案」，同时保持了搜索的多样性——「孤岛」模型把不同演化路线隔离开，防止早熟收敛。</span>

**重点：大模型在这里扮演的是「创意引擎」，不是「答案机」。** 它生成「可能更好的程序」，但好不好由评估器裁决。LLM 的「先验」——见过海量代码——让它提出的变体通常语法正确、结构合理，把搜索空间从「所有函数」压缩到「有希望的函数」；评估器保证每一步都朝目标前进。**两者的结合，是「直觉」与「验证」的分工。**

## 3 公式解析：适应度驱动的程序演化

把 FunSearch 的每一轮写成数学形式。设第 $t$ 轮的「精英库」为 $\mathcal{D}_t$（当前分数最高的程序集合），LLM 用 prompt 从库中抽取若干最佳程序生成新程序：

$$
\pi_{t+1} \sim \mathrm{LLM}\big( \text{problem},\ \pi_{\text{template}},\ \mathrm{sample}(\mathcal{D}_t) \big), \qquad
\mathcal{D}_{t+1} = \mathrm{Top}_k\Big( \mathcal{D}_t \cup \{\pi_{t+1}\},\ f \Big)
$$

- **$\mathrm{LLM}(\cdot)$ 是条件分布**：模型在「问题描述 + 模板 + 抽样出的精英程序」条件下采样一个新程序。**这里的「条件」是演化算法的核心**——精英程序把「当前知识」编码进上下文，让新提案聚焦在改进点而不是从头探索。
- **$f(\pi)$ 是适应度**：评估器对程序 $\pi$ 的打分——例如，cap set 问题里是「构造出的集合大小」，装箱问题里是「启发式的竞争比（或平均浪费）」。
- **$\mathrm{Top}_k$ 是选择算子**：新程序与精英库合并，只保留适应度最高的 $k$ 个。**这保证了单调改进——分数只升不降（在库的层面）。**
- **收敛行为**：随着演化，库中的程序适应度逐步上升；LLM 在「越来越好的模板」基础上变异，形成正反馈。<span class="marginnote">为什么用演化而不用「让 LLM 一次写最优」？因为 LLM 的单次生成受上下文与随机性限制，很难一步到位；演化把「一步一步逼近」变成机械流程，<strong>每步只需「小幅改进」</strong>——而「小幅改进」正是 LLM 最擅长、最稳定的能力。</span>

**辨析｜易错点：** 不要把 FunSearch 误解为「强化学习」——它没有「奖励信号的反向传播」，也没有「策略更新」。它是**进化算法 + LLM 变异算子**：选择压来自适应度排序，多样性来自随机采样。两者的区别在于——RL 优化的是「动作概率」，FunSearch 优化的是「函数库本身」。这决定了它的搜索非常依赖「评估器是否可靠」：评估器错，演化就朝着错的方向跑。

## 4 两个发现：cap set 与在线装箱启发式

FunSearch 论文报告了两个可验证的科学发现，分别来自纯数学与运筹学。

**发现一：cap set 问题的新纪录。** cap set 问题是组合数学的经典难题：在有限域 $\mathbb{F}_3^n$ 中，找最大的「不含三项算术级数」的子集（即任意三点不满足 $x + y = 2z$）。问题的指数增长速度（$\mathbb{F}_3^n$ 中 cap set 的最大尺寸）是多项式方法（帽集定理）的著名研究对象。FunSearch 通过演化程序，**在低维空间（如 $n=8$）构造出比此前已知更大的 cap set**——刷新了公开纪录。<span class="marginnote">为什么这个发现重要？因为它不是「猜一个更大的数」，而是<strong>产出了一个可复现的构造算法</strong>——一个能生成该 cap set 的 Python 程序。数学界可以读懂程序、理解构造的结构、把它推广到更高维。这是「程序即发现」的最直接证据。</span>

**发现二：在线装箱的更好启发式。** 在线装箱问题要求「按到达顺序把物品装进箱子，无法回头」——实用场景覆盖云计算的资源分配、物流装载。人类设计了几十年的启发式（First-Fit 等），FunSearch 演化的策略在基准上**显著优于人类设计的启发式**（更小的浪费/更好的竞争比），并且这个策略是**可解释的策略规则**，不是黑箱。它直接给出了「AI 发现更好的工业算法」的证据。<span class="marginnote">装箱策略的发现还展示了一个重要性质：<strong>发现的策略是「鲁棒的」</strong>——它在未见过的测试分布上仍然表现好，而非过拟合到训练用例。这得益于演化搜索「在验证集上打分」的评估设计——评估器用的是与训练不同的实例。</span>

**重点：两个发现都不是「提升几个百分点」的噱头，而是「可验证、可复现、可理解」的科学贡献。** 这正是 FunSearch 的设计目标——「AI 辅助数学发现」不该是神秘的，而该是可审计的。

## 5 为什么「程序」是好的发现载体

FunSearch 带来的启示超越它自己。把「程序」当作科学发现的对象，有四个结构性优势：

- **验证成本低**：程序的正确性/质量可以机械评估（跑测试），不需要人读证明。
- **发现的粒度合适**：一个函数可以编码「一个构造」「一个策略」「一个筛选规则」——正好是数学与工程里「一个可发表贡献」的粒度。
- **组合性**：发现的程序可以被组合、复用、嵌入更大的系统——发现可以「堆叠」。
- **人机协同**：程序是人类与机器的共同语言——AI 提出、人类理解并改进，形成持续的协同循环。<span class="marginnote">这与《AI 科学家的工作流》一篇的主线呼应：<strong>发现的价值不只在结果，更在「可解释的中间产物」</strong>。FunSearch 输出的不是「一个数」，而是「一套能产数的代码」——这让「AI 的发现」能进入人类科学家的因果链条，而不是停留在「听说 AI 发现了个东西」。</span>

**辨析｜易错点：** FunSearch 不是「通用数学 AI」——它需要**问题本身可编程、可评估**。对「给定目标函数 $f$、能写评估器」的问题（组合优化、启发式设计、构造搜索），它如鱼得水；对「开放性的、连怎么打分都不清楚」的数学探索（如「这个概念重要吗」），它无能为力。**它的适用范围是「可计算目标的程序搜索」，不是「一切数学发现」。**

## 6 进阶辨析：FunSearch 的「评估器设计」与「适用边界」

FunSearch 的成败高度依赖「评估器」与「问题类型」——把这两块讲透，你就知道「什么问题上 FunSearch 会赢、什么问题上会输」。

**评估器设计的三条铁律。** 第一，**评估器必须与训练分布独立**——若评估用的测试用例「与生成程序的训练数据同源」，演化会「过拟合测试分布」（提出「在测试集上好看」的程序）。用「留出的、分布外」的测试用例打分，是评估器设计的底线。第二，**评估器要「稳健」**——单个用例的噪声不能决定一个程序的生死，用「多用例聚合」或「中位数而非均值」抗噪。第三，**评估器要「可区分」**——若大多数候选程序得分相同（评估器分辨不出好坏），演化就失去「选择压」，「孤岛」失去意义。

**适用边界一：问题必须「可编程 + 可评估」。** FunSearch 的前提是「目标函数 $f$ 能被写出来」——「给定候选程序，能机械地算出分数」。对「开放性的、连怎么打分都不清楚」的问题（如「这个概念重要吗」），FunSearch 完全无力。**「可评估」是 FunSearch 的入场券**。

**适用边界二：改进必须是「可叠加的」。** FunSearch 靠「小幅改进的累积」——问题要存在「从好到更好的渐变路径」。若问题的「解空间」是「悬崖式」（要么对要么错、没有中间态），演化会「爬不上坡」。**「有梯度的问题适合 FunSearch，悬崖问题不适合」**——「渐进可改进性」决定演化能否收敛。

**适用边界三：发现的「可验证性」。** FunSearch 输出的是「程序」——但「程序跑出的结果」是否「科学上成立」，需要独立验证（如 cap set 的构造要数学验证、装箱策略要独立测试）。**「演化给候选，验证给结论」**——FunSearch 的价值在「产出值得验证的候选」，不在「替代验证」。

**一个延伸：FunSearch 与「猜想生成」的结合。** FunSearch 的程序搜索可以用于「生成科学假说」——搜索「能产生异常模式的程序」，「异常」本身可能就是「新发现的苗头」。但「异常 → 新规律」的判断仍需人——**「FunSearch 负责『找异常』，人负责『解释异常』」**，这与本专题《人机协同》一章完全一致。

**辨析｜易错点：** 别把「FunSearch 找到的程序」当「最优解」——演化找到的是「演化能到达的局部优」，不是「全局最优」。「程序可读」也不等于「程序可解释」——读懂「它怎么做」容易，理解「它为什么好」仍难。

## 7 小结

- **FunSearch** 用「LLM 变异 + 评估器选择」的演化循环，在**程序空间**（而非答案空间）里搜索科学发现。
- **流程**：模板程序 → LLM 提出变体 → 评估器打分 → 精英库保留 Top-k → 下一轮基于精英库继续演化。
- **演化公式**：$\pi_{t+1} \sim \mathrm{LLM}(\mathrm{problem}, \pi_{\text{template}}, \mathrm{sample}(\mathcal{D}_t))$，$\mathcal{D}_{t+1} = \mathrm{Top}_k(\mathcal{D}_t \cup \{\pi_{t+1}\}, f)$。
- **两个发现**：cap set 的低维新纪录构造（可复现程序）与在线装箱的更好启发式——都是「可读、可验、可复用」的算法。
- **「程序即发现」**：验证成本低、粒度合适、可组合、可人机协同——这是搜索「答案」无法比拟的。
- **边界**：FunSearch 适用于「可编程、可评估」的目标；开放性的数学探索仍需其他范式。

> 一个延伸问题：如果「程序」本身也是「参数」（如可微程序），两者就合一了——「神经架构搜索、可微编程」正在模糊这条边界——「搜索对象的『粒度』从数值走向结构」，是 AutoML 到 AI4Science 的共同趋势。

> **延伸辨析：演化搜索的『停滞与重启』**。演化算法有「早熟收敛」——「LLM 变异算子会逐渐『同质化』（都往相似方向改），搜索停滞」——**「对策：周期性『重置孤岛』、注入随机性、保留多样性」**。「FunSearch 的『孤岛』设计正是为『延缓早熟』——但『停滞检测与重启』仍是工程要点」——「演化搜索要『既会爬山，也会换山』」。

> 「FunSearch 的『孤岛』设计正是为『延缓早熟』——但『停滞检测与重启』仍是工程要点」——「演化搜索要『既会爬山，也会换山』」——「只会爬山会困在局部峰，学会换山才能翻到新峰」。
