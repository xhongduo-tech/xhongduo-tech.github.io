## 为什么从语义解析开始

NLI 只回答「推不推得出」，语义分析还有一个更硬的目标：**把自然语言直接翻译成机器能执行的逻辑形式**——「去年卖得最好的手机型号是什么？」变成一条 SQL 查询，跑在数据库上，返回答案。这个任务叫**语义解析（semantic parsing）**，它的语义是「可执行」的。<span class="marginnote">语义解析是「理解」的最强检验：如果机器能把问句准确翻译成 SQL 并在数据库上查出正确答案，我们就很难说它「不理解」这句话。它也把 NLP 带出「文字游戏」，直接接上数据库、知识库、代码生成等真实系统。</span>

这一篇聚焦其中最成熟、最工业化的形态——**Text-to-SQL**（自然语言 → SQL）。它把语义分析的整个链条（词义、组合、逻辑形式）落到一个可评测、可执行、有大量数据的任务上。

## 1 什么是语义解析

**语义解析（semantic parsing）**：给定自然语言句子，输出一个**逻辑形式（logical form）**——一种机器可解释、可执行的表示。句子「北京的天气怎么样」→ 逻辑形式可以是查询 `SELECT * FROM weather WHERE city = '北京'`，也可以是 API 调用 `getWeather("北京")`。

**与前面语义任务的区别**：

词义消歧、SRL 输出的是**标注**（词义、角色）；
NLI 输出的是**标签**（蕴含/矛盾/中立）；
语义解析输出的是**结构化的可执行程序**——它不满足于「理解」，还要「跑起来」。

**核心设定**：同一个语义内容，自然语言句与逻辑形式是「两种语言」——语义解析本质上是**翻译**：从自然语言翻译到「逻辑语言」。这为第十篇机器翻译的 Seq2Seq 框架埋下了伏笔：语义解析的很多模型就是「机器翻译的变体」。<span class="marginnote">历史上语义解析的目标表示五花八门：λ 演算、谓词逻辑、CCG 组合范畴语法、AMR（抽象语义表示）、SQL。Text-to-SQL 之所以成为主流，是因为 SQL 有<strong>明确的执行语义</strong>和<strong>海量可标注数据</strong>——别的逻辑形式很难大规模评测。</span>

## 2 逻辑形式：SQL、λ 演算与 AMR

- **SQL**：「列出所有比平均价格贵的商品」→ `SELECT * FROM products WHERE price > (SELECT AVG(price) FROM products)`。查询数据库、返回表。
- **λ 演算 / 谓词逻辑**：「每个学生都读过一本书」→ 量词辖域形式。用于严格的逻辑推理（上一篇的形式语义学）。
- **AMR（抽象语义表示）**：把句子画成**单根有向无环图**，节点是概念（词义+实体）、边是语义关系（论元、修饰）。「小明喜欢苹果」→ `(l / like-01 :arg0 (p / person :name "小明") :arg1 (a / apple))` 的图。AMR 不面向执行，面向「语义结构比较」。

**三种表示的哲学差异**：SQL 面向**数据库执行**，λ 演算面向**逻辑推理**，AMR 面向**语义对齐**。Text-to-SQL 走第一条，因为它的「对错」可以用执行结果客观判定。

## 3 公式解析：序列到序列的语义解析

现代 Text-to-SQL 的主流框架是**序列到序列（Seq2Seq）**——把自然语言问题当源序列、把 SQL 当目标序列，用编码器-解码器生成。这与第十篇的机器翻译是同一个骨架。解码器逐 token 生成 SQL：

$$
P(\text{SQL} \mid \text{问题}) = \prod_{t=1}^{m} P(s_t \mid s_{\\lt t}, \text{问题})
$$

逐步拆解：

- **第一步，编码器**：把问题「去年卖得最好的手机是什么」编码成上下文表征（LSTM 或 Transformer），每个 token 一个向量。
- **第二步，自回归解码**：从左到右逐个生成 SQL token——`SELECT`、`FROM`、`WHERE`……每个 token 的条件概率依赖「已生成的部分」与「整个问题」。
- **第三步，$P(s_t \mid s_{\\lt t}, \text{问题})$**：第 $t$ 步的条件分布，由解码器隐状态经 softmax 得到。注意这里要处理**词表问题**：SQL 里既有固定关键字（`SELECT`/`WHERE`），也有**数据库 schema 里的列名、表名**（`products`/`price`）——后者词表来自数据库结构，与自然语言词表不同。<span class="marginnote">schema 词表是 Text-to-SQL 与普通机器翻译的关键差异：目标词表不是固定的，而是「随数据库而变」。模型必须学会「问题里的‘价格’ → 数据库里的列 price」——这个映射叫 <strong>schema linking</strong>，是 Text-to-SQL 最难的部分之一。
<strong>第四步，执行</strong>：生成的 SQL 送去数据库执行，拿到查询结果（或报错）。</span>

**直觉**：Text-to-SQL 模型 = 「学会写 SQL 的翻译器」，它必须同时掌握 SQL 语法、数据库结构、以及自然语言到两者的映射。

## 4 约束解码与语法受限生成

**生成 SQL 比生成普通文本要求更严**：SQL 有硬语法，`SELECT`/`FROM`/`WHERE` 的顺序不能乱，列名必须存在，括号必须配对。裸的 Seq2Seq 会生成「看起来像、跑不了」的 SQL。工程解法是**约束解码（constrained decoding）**：

**语法约束**：解码的每一步只允许「合法的下一个 token」——用 SQL 语法（上下文无关文法，第八篇的 CFG）在解码时动态过滤非法选择。<span class="marginnote">这正是 CFG 从「解析」到「生成」的角色转换：第八篇用 CFG 判断「哪些树合法」，这里用 CFG 限制「哪些 SQL token 合法」。生成与解析是一枚硬币的两面。</span>
**schema 约束**：只允许生成「当前数据库里真实存在的表/列名」，杜绝幻觉列名。
**类型约束**：`>` 这类比较运算符后面应该接数值或数值列，不能接字符串列。

**sketch 方法**（更早的套路）：先预测 SQL 的**骨架**（`SELECT <列> FROM <表> WHERE <条件>`），再逐槽位填充列名、条件值——把「写完整 SQL」拆成「填模板」，大幅降低难度。约束解码与 sketch 殊途同归：**用结构知识给生成上保险**。

## 5 评测：精确匹配与执行准确率

Text-to-SQL 的评测指标有两个层次：

**精确匹配（exact match, EM）**：生成的 SQL 字符串与参考答案**逐 token 相同**才算对。严格但苛刻——两条 SQL 语义相同、写法不同（`SELECT price FROM products` vs `SELECT products.price FROM products`）会误判为错。
**执行准确率（execution accuracy）**：把生成的 SQL 在数据库上执行，**查询结果**与参考答案的执行结果一致就算对。宽松但更「务实」——回答对了用户问题就赢了。<span class="marginnote">Spider 数据集（跨库、组合性强）官方指标同时报两者；WikiSQL 只报执行准确率。实践里执行准确率更贴近「用户视角」，EM 更能暴露「生成是否精确」。</span>

**经典数据集**：

**Spider**：约 1 万问题、200 多个数据库，**跨库**（训练见过的数据库与测试不同）——测试模型的组合泛化能力；
**WikiSQL**：约 8 万问题，单表查询，规模大但简单（无 JOIN、无嵌套）；
**ATIS**（航班查询）与 **GeoQuery**（地理查询）：早期小数据集，语义解析研究的起点。

## 6 挑战：组合性与 schema linking

Text-to-SQL 至今未完全解决，两大顽疾：

**组合泛化（compositional generalization）**：训练里见过「按城市查航班」与「按时间查航班」，测试却问「按城市和时间查航班」——模型必须学会把已学的片段**组合**出新查询。Transformer 在这种「新组合」上仍会崩，是当前研究热点。<span class="marginnote">组合泛化考验的是上一篇的组合性原则能否「外推」：语义组合不只在训练分布内有效，还要能在未见过的新组合里用。Spider 的跨库设计正是为了逼出这个能力。</span>
**schema linking（schema 对齐）**：把问题里的词映射到数据库的列/表。「‘价格’ → price 列」容易，「‘卖的好的’ → 隐含‘按销量排序’ → ORDER BY sales DESC」就需要推理。schema linking 做错，整条 SQL 就错。

此外还有：**值匹配**（问题里的「去年」要变成 SQL 里的具体年份）、**多表 JOIN**、**罕见数据库**的零样本迁移。

## 7 辨析｜易错点：四个常见坑

**辨析｜易错点：**

**EM 与执行准确率不是一回事**：EM 严格到「写法不同就错」，执行准确率宽松到「结果对就行」。报指标时必须说明用哪个、别混着比。<span class="marginnote">实践中常出现的尴尬：EM 只有 60% 但执行准确率 85%——说明模型「答对了题但写法不规范」。两种指标从不同角度刻画质量。</span>
- **词表分两套：SQL 关键字 vs schema 名称**：`SELECT` 这类关键字是固定词表，`products`/`price` 是随数据库变的。把它们混进同一个固定词表，换库就崩。
- **生成 SQL 必须过约束解码**：裸 Seq2Seq 生成「语法正确但 schema 不存在」的 SQL 是常见失败模式。语法 + schema 双重约束不能省。
- **跨库评测≠同库评测**：Spider 的训练/测试数据库不同，模型必须学「通用语义→SQL 映射」而非「背这个库的表名」。用同库数据自测会高估真实能力。

## 8 小结

- **语义解析** = 自然语言 → 可执行的逻辑形式；Text-to-SQL 是最成熟、最工业化的形态。
- 逻辑形式三类：**SQL**（可执行）、**λ 演算**（可推理）、**AMR**（可对齐）。
- **Seq2Seq 框架**：$P(\text{SQL}\mid\text{问题})=\prod_t P(s_t\mid s_{\\lt t},\text{问题})$，与机器翻译同骨架；schema 词表随库而变。
- **约束解码**：CFG 语法 + schema 名称 + 类型三重约束，杜绝非法 SQL；sketch 填模板是更早的套路。
- 评测：**精确匹配（EM）** 与 **执行准确率**；数据集 **Spider**（跨库组合）、**WikiSQL**（大而简单）、ATIS/GeoQuery（早期）。
- 两大顽疾：**组合泛化** 与 **schema linking**。

至此，语义分析这条线走完：词义、论元、资源、组合、推理、解析。在下一篇，我们进入 NLP 的另一大经典领域——**机器翻译**：从发展史与 BLEU 评测开始，一路走到神经机器翻译与 Transformer。
