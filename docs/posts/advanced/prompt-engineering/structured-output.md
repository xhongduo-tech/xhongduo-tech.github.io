## 为什么从结构化输出开始

前面讲的提示，最终产出都是「给人看的文本」。但在真实工程里，语言模型通常是**可编程组件**：它被嵌进工作流、被函数调用、被另一个程序解析。一个「说得漂亮但不合格式」的回答，对下游程序就是一场灾难。这一节讨论如何让模型输出**严格符合 JSON/XML 等结构化格式**——这是大模型进入生产系统的前提条件，也是当前各大 API 内置「JSON 模式」「函数调用」的技术根源。<span class="marginnote">这一节属于工程实践：不依赖某篇特定论文，而是把提示、解码、校验三层的通行做法讲成一套可落地的体系。它同时也是第四级里「RAG / 智能体 / 自动化」等后续专题的共同地基。</span>

## 1 为什么需要结构化

聊天场景里，模型回复「答案是 42」毫无问题；但在程序里，下游代码需要 `{"answer": 42, "unit": "m"}` 这样的键值对才能继续运算。结构化输出带来的四样东西，缺一不可：

1. **可解析**：程序能确定性地把输出变成数据结构，而不是靠正则猜；
2. **可校验**：能用 JSON Schema 之类的工具检查类型、必填项、枚举值；
3. **可组合**：一个模块的输出可以直接作为下一个模块的输入（这正是智能体工作流的基本单元）；
4. **可重试**：格式错误能被精准捕获，带着错误信息重来，而不是整段作废。

一句话：**把「模型输出」从自由文本降级为「受控数据」，程序才敢信任它。**

## 2 提示侧的软约束

最朴素的约束来自提示本身。生产级做法是**把 schema 写进系统消息**，并配一个精确的 few-shot 示例：

> 你是数据抽取器。只输出 JSON，不要任何多余文字，不要代码围栏。
> 输出必须符合以下结构：
> {"name": string, "age": int, "tags": [string] }
> 示例输入：小明 28 岁，喜欢跑步和读书。
> 示例输出：{"name": "小明", "age": 28, "tags": ["跑步", "读书"]}
> 输入：{user_input}

这套「软约束」能解决大部分问题，但远非万无一失。常见的翻车模式包括：

| 失败模式 | 表现 | 对策 |
| --- | --- | --- |
| 前言与后语 | 「好的，这是结果：{...}」 | 提示里声明「只输出 JSON」 |
| 代码围栏 | 输出包在 ` ```json ` 里 | 提示禁围栏，或在解析层剥掉 |
| 类型错位 | 数字写成字符串 `"28"` | schema 里写明类型 + 校验层兜底 |
| 枚举越界 | `tags` 填了 schema 外的值 | 在 schema 里写死 `enum` |
| 字段缺失 | 该有的键没出现 | 校验层捕获，走重试 |
| 自我道歉 | 「抱歉我无法……」 | 系统消息里声明「绝不道歉，直接输出数据」 |

**辨析｜易错点：** 提示里的格式声明是**软约束**——它通过改变条件分布「强烈建议」模型这么写，但模型随时可能违反。真正把格式钉死，要靠下一节的**硬约束**。

## 3 约束解码：把格式写进概率

硬约束的思路是：不让「违反格式的 token」有任何被采样的机会。在解码的每一步，根据当前已生成的前缀与文法规则，计算出**当前合法 token 的集合 $V(s_t)$**，然后在模型概率分布上施加掩码：

$$
P(y_t \mid h_t) \;=\; \frac{\mathbb{1}[\, y_t \in V(s_t)\,] \cdot P_{\text{LLM}}(y_t \mid h_t)}{\sum_{w \in V(s_t)} P_{\text{LLM}}(w \mid h_t)}
$$

- **第一步，看 $V(s_t)$**：$V(s_t)$ 是「在语法上合法」的下一 token 集合。它由 JSON Schema（或 CFG、XML 文法）解析器实时计算：比如刚输出了 `"age": `，此时合法 token 只剩数字、负号、小数点，字符串引号被排除。
- **第二步，看 $\mathbb{1}$ 掩码**：指示函数把不合法 token 的概率直接置零，再对合法集合并归一化（分母是合法集合的概率和）。模型的自由度没有被完全剥夺，只是被**限制在文法允许的范围内**。
- **第三步，看效果**：模型仍然在做「概率续写」，但每一步都保证产物能通过语法解析——**语法正确是 100% 保证的，语义正确仍靠模型本身**。这就是约束解码（constrained decoding），实现它的工具有 outlines、guidance、llama.cpp 的 GBNF 文法、以及各大 API 的「JSON 模式 / 函数调用 / 结构化输出」。

<span class="marginnote">把「文法」从静态字符串变成「解码期实时检查」，是一个漂亮而细微的工程点：它不是事后修格式，而是把格式写进了每一步的概率计算里。可以类比正则表达式匹配：提示约束像「宽松匹配」，约束解码像「严格锚定」。</span>

## 4 校验与修复循环

即便有约束解码，工程上仍要保留最后一道保险：**校验—重试循环**。

1. 解析模型输出；解析失败，进入第 2 步；
2. 把解析错误信息（如「字段 `age` 缺失」「第 3 行不是合法 JSON」）**回灌给模型**；
3. 提示模型「你的输出格式不正确，错误是 {error}，请重新输出」；
4. 重试，最多 $N$ 次（通常 2—3 次）；仍失败则返回降级结果。

这一招的可靠性被广泛验证：模型对「你的答案哪里错了」有很强的自我修正能力，而错误信息就是最精准的提示词。<span class="marginnote">一个直觉解释：模型对「看到错误 → 修正」这一文本模式非常熟悉（就像人类被批改作业后订正），所以把解析器的错误原样送回，比笼统地说「再试一次」有效得多。</span>

**核心要点：生产级结构化输出管线六步**——schema 写进系统消息 → few-shot 给精确样例 → 优先用约束解码/JSON 模式 → 解析输出 → 失败带错误重试 2—3 次 → 仍失败走降级路径。每一步都可以独立存在，但只有串成完整管线才算「可信任的结构化输出」。

## 5 辨析｜软约束与硬约束

| 维度 | 提示软约束 | 约束解码硬约束 |
| --- | --- | --- |
| 机制 | 改变条件分布，引导 | 解码期掩码，强制 |
| 语法正确率 | 高但不保证 | 100% 保证 |
| 是否需额外工具 | 否 | 需要文法解析器/API 支持 |
| 语义质量 | 依赖提示质量 | 依赖模型质量（语法被保证） |
| 适用 | 无解码工具、格式宽容场景 | 下游程序严格消费的场景 |

**辨析｜易错点：** 硬约束保证的是「语法」，不是「语义」。一个 `{"name": "小明", "age": 28}` 可以完全合法却语义错误（比如把年龄 28 错标在名字上）。所以正确姿势是**双保险**：约束解码保语法、提示与校验保语义，两者互为补充而非替代。

## 6 小结

- **结构化输出**把模型输出从自由文本降级为受控数据，是可解析、可校验、可组合、可重试的前提。
- 提示侧用**软约束**：schema + 精确示例 + 系统消息声明，能解决大部分格式问题，但随时可能被违反。
- **约束解码**用 token 级掩码把格式钉死：$P(y_t\mid h_t) \propto \mathbb{1}[y_t\in V(s_t)]\cdot P_{\text{LLM}}(y_t\mid h_t)$，语法 100% 保证、语义仍靠模型。
- 生产管线要串起六步：schema → 示例 → 约束解码 → 解析 → 带错误重试 → 降级。
- 硬约束保语法、软约束与校验保语义，**双保险**才是可信任的结构化输出。

在下一节，我们讨论最后一个、也是最重要的一个话题：提示本身可以被攻击。模型分不清「指令」与「数据」，恶意文本可以劫持它——这就是**提示安全与注入防御**。
