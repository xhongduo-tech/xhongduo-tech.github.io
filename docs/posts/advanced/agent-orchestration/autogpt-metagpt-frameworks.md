## 为什么聊框架

前八篇的理论已经齐了：架构、规划、工具、记忆、协作、环境、评估。但理论要变成能跑的东西，还需要一层**落地件**——把智能体循环、工具注册、记忆存取、多智能体通信封装成可复用代码的「框架」。2023 年 GPT-4 发布后，智能体框架一夜爆发：AutoGPT 让全世界第一次看到「给 AI 一个目标它自己干活」，MetaGPT 则把多智能体流水线做到了软件工程的极致。<span class="marginnote">本专题第 1 篇的架构图里，四大模块是「设计图」；框架就是把这些模块变成真实的循环、消息池与工具总线。设计图决定上限，框架决定能不能够到。</span>本节以 Xi 等人综述 §7 为纲，解剖这两个最有代表性的框架，看看「理论→代码」的桥梁是怎么搭的。

## 1 AutoGPT：单智能体的「自动循环」

AutoGPT 的思路一句话讲完：**给智能体一个目标，让它自己循环执行，直到目标完成或预算耗尽**。它的主循环（goal loop）长这样：

1. **目标设定**：用户给出目标（「帮我调研养老行业并写一份报告」）。
2. **任务分解**：LLM 把目标拆成子任务，维护一个动态任务列表。
3. **工具执行**：对每个子任务调用工具（网页搜索、文件读写、执行代码）。
4. **自我评价**：评估当前进度，决定是继续、调整还是宣布完成。
5. **回到第 2 步**，直到评价判定「完成」。

AutoGPT 的历史意义在于**证明了「自主循环」的可行性**——没有任何人逐条指挥，一个 LLM 就能自主推进一个多步任务。它的工程遗产同样重要：任务列表、工具注册、记忆注入，这些词今天仍是每个智能体框架的标准零件。<span class="marginnote">AutoGPT 是 2023 年开源圈的现象级项目，但也迅速暴露了「循环」的双刃剑：一旦评价器误判「没做完」，智能体就会无限自我驱动，直到 token 账单爆炸。</span>

## 2 MetaGPT：SOP 驱动的多智能体流水线

如果说 AutoGPT 是「一个人身兼数职」，MetaGPT 就是「一家软件公司」。它的洞见来自软件工程的常识——**复杂软件从来不是一个人写出来的，而是靠标准作业流程（SOP）串起不同角色**。MetaGPT 把「写一个软件」拆成一条流水线：

```
产品经理(写 PRD) → 架构师(写设计文档) → 工程师(写代码) → 测试员(写测试)
```

每个角色是**独立的智能体**，只做自己那一环；前一道工序的产出（需求文档、设计文档）成为后一道工序的输入。两条关键设计让流水线不崩：

**文档即接口**：智能体之间不传「聊天记录」，传**结构化文档**——PRD、设计文档、代码、测试用例。文档把模糊需求沉淀成可验证的中间产物，这是与第 6 篇「直接对话」的根本区别。
- **消息池解耦**：所有产出发到公共消息池，角色按订阅关系消费（见第 6 篇的通信协议），新增角色不打断既有流水线。

MetaGPT 的启示是：**多智能体的价值，取决于你给协作定的「接口契约」有多硬**。SOP 就是契约——它规定了每个角色交什么、何时交、交给谁。<span class="marginnote">从数学视角看，AutoGPT 是一条「自反馈序列」，MetaGPT 是一条「前馈流水线 + 文档状态」。前者灵活但难控，后者可控但需要人为设计工序。两者不是取代关系，而是组织哲学的两种极端。</span>

## 3 公式解析：目标条件循环

把 AutoGPT 这类「目标驱动」智能体的循环写下来，它其实就是第 1 篇公式加上了**目标与计划两个变量**：

$$
g \sim \mathrm{User}, \qquad
T_t \sim \pi_\theta\!\left(T_t \mid g,\ h_t\right), \qquad
a_t \sim \pi_\theta\!\left(a_t \mid T_t,\ h_t\right), \qquad
o_t = \mathrm{Exec}(a_t)
$$

四步拆解：

- **$g$（目标）**：整个循环的锚点，由用户给定（或由更高层智能体下发）。它同时是任务分解的起点和「是否该停」的判定基准。
- **$T_t \sim \pi_\theta(T_t \mid g, h_t)$**：模型根据目标与当前轨迹，生成**这一步的任务**（AutoGPT 里的「任务分解」）。注意任务本身是模型生成的——这正是 AutoGPT 跑偏的根源：任务列表可以偏离目标而不自知。
- **$a_t \sim \pi_\theta(a_t \mid T_t, h_t)$**：根据任务与轨迹选择**动作**（调哪个工具）。$T_t$ 起着「把目标翻译成动作」的中介作用，比第 4 篇「直接动作」多了一层缓冲。
- **$o_t = \mathrm{Exec}(a_t)$**：动作落地，观测回写 $h_{t+1}$，循环继续——直到某一步评价器判定 $g$ 已完成。**停止条件也是循环的一部分**，判定错了，循环就不会停。

**为什么 AutoGPT 需要「自我评价」这第五个零件**：因为没有外部裁判，只能靠模型自己判断「目标达成没有」。这暴露了目标驱动循环的共性弱点——**评价与执行共用同一个大脑**，编造进度的冲动会同时污染两者。

## 4 辨析：框架、方法与「假自主」

**辨析｜易错点：** 框架话题里，三处最容易被误导。

- **框架 ≠ 方法**：AutoGPT 的「目标循环」是**工程框架**，ReAct 的「思考—行动交替」是**方法**。框架决定零件怎么装，方法决定智能体怎么想。同一套框架可以套不同方法，反之亦然——分清「骨架」与「思维」。
- **「自主」是有限度的**：AutoGPT 式的自主依赖模型自我评价，而自我评价会漂移。实践中要给循环加**硬护栏**：步数上限、预算上限、工具白名单、人工确认点。所谓「完全自主」在工程上是一种危险的修辞。
- **MetaGPT 不是免费的**：流水线的每一步都要跑一个完整 LLM 调用，一份需求文档可能消耗数万 token；工序越多，端到端延迟与成本越高。流水线换取的是可控性，不是便宜。

## 5 实战：同一个任务，两种框架

用一个具体任务对比两种框架的运转方式：让智能体做一个「汇率查询」命令行工具。AutoGPT 先动手：

```
目标：写一个汇率查询命令行工具。
任务列表：[1. 调研汇率 API；2. 设计 CLI 结构；3. 写代码；4. 自测]
→ 子任务 1 完成，追加子任务：把结果写入 requirements.txt
→ 子任务 2 完成……
循环：自我评价「自测通过，目标完成」→ 停止
```

AutoGPT 的轨迹是**一条自我循环的单线**：目标不变，任务列表动态增减，直到自我评价喊停。它的优点是**一体化**——一个上下文全程跟踪，无需角色间交接；缺点是第 3 节公式里的软肋：**自我评价说「完成」时，可能根本没完成**。

MetaGPT 把同一任务切成工序：

```
PM → PRD（功能 + 验收标准）
架构师 → 设计文档（模块划分、数据源选择）
工程师 → 代码（按设计文档实现）
测试 → 用例（覆盖正常与异常输入）
```

两相对比，选择逻辑浮出水面：

- **任务小、工序未知**：选 AutoGPT 式循环——灵活、少配置、快速起步；
- **任务大、工序可拆、需要多人审计**：选 MetaGPT 式流水线——可控、可追溯；
- **两者之上**：今天的框架生态（LangChain / LangGraph / AutoGen）把这两派抽象成「节点 + 边 + 状态」的图编排——AutoGPT 是自环图，MetaGPT 是链式图，复杂系统则是带分支与合并的混合图。

把两派放到对比表里收个尾：

| 维度 | AutoGPT 式 | MetaGPT 式 |
| --- | --- | --- |
| 智能体数量 | 1 | 多个（按角色） |
| 状态流转 | 单上下文滚动 | 文档 + 消息池 |
| 可控性 | 弱（自我评价） | 强（SOP + 审计） |
| 成本 | 循环深则爆炸 | 工序多则爆炸 |
| 适用 | 探索型、小任务 | 交付型、大任务 |

**理解这两派，等于拿到了读任何框架的钥匙**——今天层出不穷的新框架，无非是在「单环 vs 流水线」之间调参，再加一层状态管理与记忆接入的封装。

## 6 小结

- **AutoGPT**：单智能体目标驱动循环——目标设定 → 任务分解 → 工具执行 → 自我评价 → 循环；证明了「自主干活」可行，也暴露了「自我评价会漂移」。
- **MetaGPT**：SOP 驱动的多智能体流水线——PM → 架构 → 编码 → 测试；**文档即接口、消息池解耦**让流水线可工程化。
- 目标条件循环公式：$T_t \sim \pi_\theta(T_t \mid g, h_t)$，任务由模型生成、评价也由模型做，是可控性的最大弱点。
- 框架 = 零件装配，方法 = 思维方式；两者要分清。
- 易错点：**把框架当方法、「完全自主」是危险修辞、流水线成本不可忽视**。

在下一节，我们把所有能力叠加到极限时，最不该忽略的问题终于浮出水面——**当智能体有手有脚、能调工具、能读网页时，它也是攻击者眼里最完美的跳板**。我们谈智能体的安全与提示注入防御。
