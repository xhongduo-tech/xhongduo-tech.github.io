## 为什么单讲「调用」这一环

上一篇的 Toolformer 让模型学会了「提出请求」，但请求要真正变成对世界的影响，还差一层：**动作必须被安全、可靠地执行，并把结果接回来**。这是智能体工程里最枯燥也最容易翻车的一段——模型输出的动作格式错了、参数越权了、循环卡死了，前面的规划再漂亮也白搭。<span class="marginnote">本篇与上一篇的分工：Toolformer 回答「训练时怎么让模型学会调工具」，ReAct 的动作集回答「推理时怎么把动作安全落地」。前者是能力问题，后者是协议问题。</span>我们以 ReAct 论文的 Wikipedia 环境为标本解剖「动作空间」的设计，再延伸到今天更通用的 API 函数调用。

## 1 动作空间：给模型画一条行动的边界

**动作空间（action space）** 是智能体可以发起的所有动作的集合。ReAct 在 Wikipedia 问答环境里只给了三个动作：

| 动作 | 语义 | 例子 |
| --- | --- | --- |
| `search[实体]` | 检索某实体对应的维基页面 | `search[费马大定理]` |
| `lookup[字符串]` | 在当前页面内定位一段文字 | `lookup[证明思路]` |
| `finish[答案]` | 输出最终答案，结束轨迹 | `finish[3]` |

三个动作构成了一个**最小的闭环**：`search` 打开页面，`lookup` 细读内容，`finish` 收敛答案。动作空间被刻意做得很小——**小动作集 + 格式约束，是让模型输出可解析、可执行的关键**。模型可以自由地写 `Thought`，但 `Action` 必须落入白名单，违反格式的轨迹直接判无效。

设计动作空间有三条经验：**够用**（能完成任务的最小集合）、**可解析**（格式严格，能程序化校验）、**可回滚**（动作要么能撤销，要么副作用可审计）。<span class="marginnote">动作空间的哲学与数据库的 ACID 部分相通：每个动作都是对状态的一次受控变更。到安全篇你会看到，动作空间的边界就是攻击面的边界。</span>

## 2 从受限动作到通用 API 调用

Wikipedia 的三个动作太窄，现实任务需要的动作五花八门：查天气、发邮件、跑代码、操作数据库。今天的智能体实践因此走向**通用函数调用（function calling）**：把每个工具声明成一个带参数 schema 的函数（名称、参数类型、说明），模型在生成时选择函数并填充参数，由框架解析后调用真实 API。

一个典型的函数声明长这样：

```
get_weather(city: str, date: str) -> dict
# 返回指定城市、指定日期的天气。
```

模型的「动作」从字符串变成了结构化调用：`get_weather(city="北京", date="2026-08-11")`。这一步看似小，却解决了三件事：**参数结构由 schema 约束**（不再靠模型自由发挥格式）、**返回值类型可控**（框架可以强校验）、**多工具并存**（每个函数一份声明，模型按需选择）。这本质上是把 ReAct 的「小动作空间」泛化成了「动态注册的大动作空间」。

## 3 公式解析：动作采样与观测回写

把上一篇 ReAct 的公式聚焦到「动作」这一环，写出工具调用的完整数据流：

$$
\mathrm{Th}_t \sim \pi_\theta(\cdot \mid h_t), \qquad a_t = \mathrm{Parse}\!\big(\mathrm{Th}_t\big) \in \mathcal{A}, \qquad o_t = \mathrm{Execute}(a_t)
$$

三步拆解：

- **第一步，生成**：模型以轨迹 $h_t$ 为条件采样这一步的文本 $\mathrm{Th}_t$，其中可能包含一条动作（如 `Action: search[费马大定理]`）。
- **第二步，解析与校验**：$\mathrm{Parse}$ 把文本抽成语义动作 $a_t$，并检查它是否落在动作空间 $\mathcal{A}$ 里。**这一步是关键防线**：格式不对直接重试，不在白名单直接拒绝——模型没有「乱来」的余地。
- **第三步，执行与回写**：$\mathrm{Execute}$ 把 $a_t$ 交给真实环境（调用 API、跑代码），返回观测 $o_t$，写回历史 $h_{t+1} = h_t \oplus (a_t, o_t)$。下一轮的模型就带着真实观测继续。

**为什么「解析—校验」必须在系统层做，而不是让模型自律**：因为生成是概率性的，任何一步都可能偏离格式。把约束放在代码里，而不是期望模型的每一次输出都完美，是智能体工程的第一条纪律。

## 4 易错点：工具调用的三个翻车现场

**辨析｜易错点：** 真实系统里，工具调用失败的九成原因集中在三处。

- **格式漂移**：模型偶尔输出 `search 费马大定理`（少了方括号）或嵌套引号，解析器直接懵。对策是校验失败就带着错误信息重试一次，让模型自纠，而不是崩溃。
- **死循环**：同一个动作反复发起——`search[X]` 得到的观测不满足要求，模型又 `search[X]`。必须加**步数上限与重复检测**：观测相同两次以上就该换策略或终止。
- **上下文膨胀**：每多一次调用，观测文本就往上下文里塞一段，长任务很快撑爆窗口（上文《智能体架构概览》提过：上下文只是工作记忆）。对策是截断、摘要历史观测，或只保留与当前子目标相关的观测。

还有一个更隐蔽的问题：**工具返回的结果本身可能是噪声**。网页搜索返回几十条无关内容，模型必须学会「挑有用信息」而不是把整段观测照抄进答案——这又回到了「观测回写」的质量控制。

## 5 实战：一次函数调用的完整往返

把第 2 节的「通用函数调用」走一遍，看每一步谁在做什么。任务是让智能体回答「北京明天天气适合户外跑步吗」。

**第 1 步，工具注册**：系统向模型声明可用工具与参数 schema：

```
get_weather(city: string, date: string) -> dict
  返回指定城市、日期的天气，字段含 temperature 与 condition。
```

**第 2 步，模型发起调用**：模型在生成回答前，先输出结构化调用：

```
{"name": "get_weather", "arguments": {"city": "北京", "date": "2026-08-12"}}
```

**第 3 步，框架解析执行**：框架解析 JSON、校验参数类型（date 格式对不对、city 是否非空），再调用真实天气 API，拿到返回值 `{"temperature": 31, "condition": "晴"}`。

**第 4 步，观测回写与作答**：返回值作为观测拼进上下文，模型基于真实数据给出「适合，但注意午后防晒」这类结论。

对照第 3 节的公式，这四步正好是「生成 → 解析校验 → 执行 → 观测回写」的完整实例。其中有两点值得停下来想：

**第一，参数校验是第一道安全闸门**。模型若填的是「明天」这种模糊表达，框架必须拒绝并请它重填结构化日期——schema 的存在意义正在于此：它不是文档，是硬约束。

**第二，返回值不保证可信**。天气 API 的返回格式可能变化（字段改名、多套一层、偶尔缺字段），框架要加「结果清洗」，把脏数据转成模型能读的干净文本。第 4 节讲的「观测质量」问题，在真实系统里就落在这层清洗上。

把整个往返画成一张职责表，能看清「谁负责什么」：

| 环节 | 谁负责 | 失败怎么办 |
| --- | --- | --- |
| 格式约束 | schema 声明 | 参数不合法：拒绝并重填 |
| 发起调用 | 模型生成 | 格式漂移：带错误信息重试 |
| 执行调用 | 框架 + API | 超时 / 报错：记录并降级 |
| 结果回写 | 框架清洗 | 脏数据：转义、截断、标不可信 |

这张表值得反复对照：**智能体工程的大部分稳定性，都藏在「解析、校验、清洗」这些不起眼的环节里**。模型负责聪明，框架负责可靠。

## 6 小结

- **动作空间** = 智能体可发起动作的集合；ReAct 的 Wikipedia 三动作 `search / lookup / finish` 是最小的可用闭环。
- 设计三原则：**够用、可解析、可回滚**；小动作集是可控性的前提。
- 通用 API 时代用**函数调用**：每个工具一个参数 schema，模型结构化选择与填参，框架解析执行。
- 动作数据流：**生成 → 解析校验（$\mathrm{Parse}$ 与白名单）→ 执行 → 观测回写**；校验必须在系统层做。
- 三大翻车点：**格式漂移、死循环、上下文膨胀**，各有对应的工程对策。

在下一节，模型已经会规划、会调工具了，但它的「经验」仍然一次性：这次试错的教训，下次开局全忘光。我们要给智能体装上**记忆与反思**——这正是 Reflexion 的名字来源。
