## 为什么单个智能体不够

前五篇打造的单个智能体已经相当能干：会规划、调工具、记住教训。但把它扔进真实项目——写一个网站、维护一套代码库、做一场市场调研——很快会碰到天花板：**一个智能体要同时精通需求分析、架构设计、编码、测试、部署，这超出了单一提示词能承载的分工粒度**。<span class="marginnote">这其实是人类工程的常识：没有一家软件公司让一个人包揽全部角色。把常识搬进智能体，就有了「多智能体协作」——Xi 等人综述 §4 的主题。</span>多智能体系统的核心主张是：**与其造一个无所不能的超级智能体，不如造一群各有所长的专业智能体，再设计好它们怎么说话**。本节按「组织方式 → 通信协议 → 协作公式」展开。

## 1 三种协作组织方式

多智能体怎么配合，主流实践可归成三类。

**角色扮演（role playing）**：给每个智能体分配一个专业身份与专属目标。CAMEL 让「AI 用户」与「AI 助手」结对，一个提需求、一个给方案，通过角色扮演把一段任务对话自动扩展成高质量数据；ChatDev 则让 CEO、程序员、测试员依次接力。<span class="marginnote">角色扮演的威力在于<strong>约束专注</strong>：每个智能体只被提示做自己那一块，输出质量反而更高——这印证了第 1 篇「画像模块」的作用。</span>

**辩论（debate）**：多个智能体对同一问题给出各自答案与理由，互相批评后迭代收敛。辩论能显著稀释单点幻觉——A 编了个事实，B 的常识性反驳会把它拦住。代价是 token 开销与可能的「观点趋同」（互相说服后大家都同意了一个错的答案）。

**流水线（pipeline）**：把任务拆成固定工序，每个智能体只负责一道工序，产出物像传送带一样往下传。MetaGPT 就是流水线的极致形态（见第 9 篇），它模拟一家软件公司的 SOP：产品经理写需求文档 → 架构师写设计文档 → 工程师写代码 → 测试员写测试。

## 2 通信协议：对话、共享黑板与消息池

组织方式只是分工，协作还要靠**通信协议**把分工连起来。三种常见协议：

**直接对话**：智能体两两对话，消息只在两者之间流动。简单直观，但无法广播，人多就乱。
- **共享黑板（blackboard）**：所有智能体读写同一块共享状态（如任务列表、进度表）。适合「大家围着同一个目标干活」的场景，但需要定义清楚「谁来写、写什么」。
- **消息池（message pool）**：所有消息发到一个公共池子里，智能体按需订阅与发布。MetaGPT 用的就是消息池：每个角色发布自己的产出，需要的角色拉取消费。<span class="marginnote">消息池把「谁说话」从通信协议里解耦出来：发布者不需要知道谁会读，订阅者不需要知道谁写的——这是软件工程里「消息队列 / 事件总线」的老朋友。</span>

选择协议的本质是选择**耦合度**：直接对话耦合最紧，消息池最松。松耦合换来的是可扩展与可审计（每条消息都有来源），代价是编排逻辑变复杂。

## 3 公式解析：消息驱动的协作循环

把消息池协议写成公式，看一个协作步发生了什么：

$$
m_t^{i} \sim \pi_i\!\left(\cdot \mid \mathcal{H}_t, \mathrm{Msg}_{\mathrm{in}}^i\right), \qquad
\mathcal{H}_{t+1} = \mathcal{H}_t \cup \{(i, m_t^{i})\}, \qquad
\mathrm{Msg}_{\mathrm{out}}^i = \mathrm{Filter}_j(m_t^i)
$$

四步拆解：

- **第一步，第 $i$ 个智能体的生成**：智能体 $i$ 的策略 $\pi_i$ 以自己的画像、当前任务历史 $\mathcal{H}_t$ 和**收到的消息** $\mathrm{Msg}_{\mathrm{in}}^i$ 为条件，产出消息 $m_t^i$。每个智能体是独立的 LLM 调用，各有各的 system prompt。
- **第二步，写入共享历史**：消息带着发布者编号 $(i, m_t^i)$ 追加进 $\mathcal{H}_t$。$\mathcal{H}_t$ 是全体智能体的公共「黑板」——要么是消息池全文，要么是提炼后的共享状态。
- **第三步，订阅与消费**：$\mathrm{Filter}_j$ 表示智能体 $j$ 只消费与自己相关的消息（订阅条件），把自己不需要的消息挡在窗外。**这一步防止上下文爆炸**——一个工程师不必读全部 100 条消息，只读与自己模块相关的几条。
- **第四步，循环**：任一智能体发布新消息后，满足条件的订阅者触发下一轮生成，协作像消息驱动的事件循环一样推进，直到产出最终交付物。

**公式的要点是「消息即状态」**：多智能体系统里，没有集中的「主智能体」发号施令，全局状态就是一条条消息的累积。谁该干活，由订阅关系决定，而不是由某个调度器点名。

## 4 易错点：协作不是万能药

**辨析｜易错点：** 多智能体并非越多越好，三处常见的翻车点。

- **角色冗余**：两个角色画像重叠（都管代码质量），就会互相抢活或互相推诿。角色之间要**边界清晰**，且每个角色必须有「能独立交付的产出物」。
- **通信成本失控**：N 个智能体两两对话是 O(N²) 的消息量，token 消耗爆炸。实践中用消息池 + 订阅过滤把有效消息压下去，或限制辩论轮数。
- **辩论趋同**：多轮互相说服后，分歧消失、错误共识达成。对策是让辩论方「先各自独立给出答案，再互相批评」，而不是一上来就交互——独立答案保留住多样性。

还有一条容易被忽略：**协作的收益依赖单个智能体的质量**。四个幻觉成堆的智能体协作，产出的是四倍速的错误——协作放大的是能力，不是纠错。

## 5 实战：MetaGPT 流水线上的一天

把第 1、2 节的设计接起来，看消息池上的一次完整协作。任务：写一个「汇率查询」命令行工具。

**PM 角色**发布消息：

```
msg_1 (产品经理): PRD——功能：输入币种对与金额，输出实时汇率换算；
   验收标准：支持 USD/CNY，错误输入给出友好提示。
```

**架构师角色**订阅到 msg_1，产出设计文档：

```
msg_2 (架构师): 设计——模块拆分：CLI 入口 / 汇率服务客户端 / 错误处理；
   汇率数据源用公开 API，失败时走缓存兜底。
```

**工程师角色**订阅 msg_2（不再需要读 msg_1 的全文），产出代码；**测试角色**订阅代码，产出用例。每个角色只消费自己订阅的消息——这正是第 3 节公式里 Filter_j 的实例：无关消息不会全塞进工程师的上下文。

流水线胜在哪里，这个例子说得很清楚：

- **分工专注**：工程师的 prompt 永远只谈编码，不掺需求分析，输出更专业；
- **中间产物可审计**：PRD、设计文档都落盘，哪里出错可精确回溯到哪一道工序；
- **可插拔**：想换测试策略，只改测试角色的 prompt，流水线其他环节纹丝不动。

也要说清它的前提：**流水线适合「工序可预定义」的任务**。如果任务高度开放、工序不确定（「帮我头脑风暴一个创业点子」），强加 SOP 反而扼杀发散——那种场景更适合辩论式协作，而不是流水线。

实战中还有一个常见的规模效应：**消息池里消息一多，订阅者的「信号噪声比」就下降**。角色在大量无关消息里找不到自己要的那条，协作就退化成「各自为政」。成熟的系统会为每条消息打「类型 + 主题」标签，订阅按标签匹配——这相当于给第 3 节的 Filter 函数加了一级索引。

把三种组织方式放到选择表里收个尾：

| 组织方式 | 适用场景 | 主要风险 |
| --- | --- | --- |
| 角色扮演 | 生成式任务、数据扩增 | 角色边界模糊 |
| 辩论 | 事实核查、风险决策 | 趋同、成本高 |
| 流水线 | 工序清晰的复杂任务 | 工序僵化、成本高 |

最后回到消息池的本质：**协作的质量不取决于智能体多不多，而取决于「消息契约」定义得多清楚**。谁发布什么、谁消费什么、何时算完成——这三条定清了，协作就稳；定不清，一百个智能体也只会互相刷屏。

## 6 小结

- **多智能体的动机**：单一提示词承载不了复杂任务的分工粒度，与其造全能智能体，不如让专业智能体协作。
- 三种组织方式：**角色扮演（CAMEL / ChatDev）、辩论（debate）、流水线（MetaGPT 式 SOP）**。
- 三种通信协议：**直接对话、共享黑板、消息池**；耦合度依次降低，消息池最松、最可审计。
- 协作核心公式：$m_t^i \sim \pi_i(\cdot \mid \mathcal{H}_t, \mathrm{Msg}_{\mathrm{in}}^i)$，**消息即状态**，订阅关系决定谁干活。
- 易错点：**角色冗余、O(N²) 通信成本、辩论趋同**；协作放大能力但不纠错。

在下一节，所有协作都发生在「文本世界里」——模型与工具、模型与模型。但真实世界还有一整个维度的交互没有覆盖：**智能体与环境、与物理世界的接触**。我们来谈具身智能。
