## 为什么从模型部署开始

训练好的模型要「用起来」——放进 App、服务、边缘设备——这就是**模型部署（model deployment）**。它要解决两个问题：**互操作性**（PyTorch 模型怎么跑到别处）与**效率**（推理要快、要省显存）。**ONNX（Open Neural Network Exchange）**是「模型交换格式」——把 PyTorch 模型导出成「框架无关的中间表示」，让模型「一次导出、到处运行」；**推理优化**则是「让推理更快」的一系列手段——图优化、量化、TensorRT。

理解模型部署，核心是理解「**训练环境 vs 部署环境的不同**」：训练用「自动微分 + 灵活性」，部署要「固定图 + 极致效率」——所以部署要「转换」（训练模型 → 推理格式）与「优化」（推理格式 → 更快）。本节把「ONNX 导出」「推理优化」（图优化、量化、TensorRT）「部署的工程流程」讲透——它是「从训练到产品」的最后一公里，也是第四级《大模型部署》的深度学习侧入口。<span class="marginnote">「部署的『两个目标』」：<strong>互操作</strong>（模型能在不同框架/硬件跑）——ONNX 解决；<strong>效率</strong>（推理快、省资源）——图优化/量化/TensorRT 解决。「<strong>训练『求对』、部署『求快』</strong>」——「训练与部署的『优化目标』不同，所以要『转换 + 优化』」。</span>

## 1 ONNX：模型的「通用语言」

**ONNX（Open Neural Network Exchange）**是「模型交换的开放格式」——把「框架特定的模型」变成「框架无关的计算图表示」。

**导出流程**（PyTorch → ONNX）：

```python
import torch

dummy_input = torch.randn(1, 3, 224, 224)          # 与输入形状一致的假样本
torch.onnx.export(
    model,                                         # 训练好的模型
    dummy_input,                                   # 示例输入（做一次前向以追踪图）
    "model.onnx",
    opset_version=17,                              # 算子集版本（越新支持的算子越多）
    input_names=["input"], output_names=["output"],
    dynamic_axes={"input": {0: "batch"}, "output": {0: "batch"}},
)
```

**「ONNX 模型 = 计算图（算子 + 张量）」**——它记录「数据怎么流动」，不绑定「某个框架的实现」。

**为什么需要 ONNX？**

1. **互操作**：PyTorch 模型 → ONNX → TensorRT/ONNX Runtime/其他框架——「一次导出，到处运行」。
2. **部署优化**：ONNX 是「推理引擎」的输入——ONNX Runtime、TensorRT 针对它做图优化。
3. **硬件适配**：同一 ONNX 模型可以部署到 CPU、GPU、边缘设备。

**易错点：** ONNX 导出要求「模型算子都支持」——「自定义算子/动态控制流」可能导出失败。**「导出前要确认算子兼容」**（用 `onnx.checker.check_model` 检查、用 ONNX Runtime 验证输出一致）。<span class="marginnote">「导出 ≠ 无条件成功」：模型的「动态控制流」（`if`/`while` 依赖数据）、自定义 autograd 算子、非常规操作——ONNX 可能「不支持」或「导出失败」。「<strong>部署友好的模型要『静态化』</strong>」——「设计模型时就想好『能不能导出』」。「『部署友好』是模型设计的一个考量维度」。</span>

## 2 推理优化：让模型跑得更快

推理优化的目标：「在同样的精度下，更快、更省资源」。主要手段：

**手段一：图优化（graph optimization）**。推理引擎（ONNX Runtime、TensorRT）自动做「图级优化」——算子融合（把 Conv+BN+ReLU 合成一个算子）、常量折叠、死代码消除——「<strong>减少算子数、减少内存访问</strong>」。

**手段二：量化（quantization）**。把权重/激活从 FP32 降到 int8——「<strong>显存省 4 倍、推理快 2–4 倍</strong>」（见《混合精度》的「低精度也够用」）。两种量化：

**训练后量化（PTQ）**：训完直接量化——简单，精度略损。
**量化感知训练（QAT）**：训练时模拟量化——精度好，但要重新训练。

**手段三：专用推理引擎（TensorRT）**。NVIDIA 的 TensorRT 针对 GPU 做「极致优化」——算子融合、内核自动调优、精度校准——「<strong>比 PyTorch 的 eager 推理快 2–5 倍</strong>」。

**「推理优化的层次」**：图优化（通用）→ 量化（精度-速度权衡）→ 专用引擎（硬件极致）——「<strong>由通用到专用、由简单到极致</strong>」。<span class="marginnote">「量化的『精度-速度』权衡」：int8 推理快但精度略降——「<strong>『量化』是『精度换速度』的工程决策</strong>」。「<strong>不是所有模型都适合量化</strong>」（小模型/敏感任务量化后精度掉得多）——「<strong>量化前要评估『精度损失可接受吗』</strong>」。「<strong>量化 = 部署的『最后的大招』，不是默认</strong>」。</span>

**易错点：** 推理优化的「加速」依赖「硬件支持」——TensorRT 要 NVIDIA GPU、int8 要硬件支持——「<strong>优化手段与硬件绑定</strong>」。「先确认部署硬件，再选优化手段」。

## 3 公式解析：推理延迟的组成

把「推理优化的收益」用延迟分析看穿。单次推理的延迟可以分解为「计算 + 内存 + 开销」：

$$
T_{\text{infer}} = T_{\text{compute}} + T_{\text{memory}} + T_{\text{overhead}}
$$

- **第一步，看计算项**：算子本身的计算时间——「图优化（融合）减少算子、TensorRT 优化内核」压它。
- **第二步，看内存项**：数据在内存/显存里的读写时间——「量化（int8）省带宽、融合减少中间张量」压它。
- **第三步，看开销项**：框架的调度开销（Python 解释、张量分配）——「用推理引擎（C++ 实现）、图导出（免 Python）」压它——**「深度模型的推理，『内存/开销』常比『计算』更贵」**——「<strong>优化『内存与开销』往往比优化『计算』更有效</strong>」。<span class="marginnote">「推理的『内存瓶颈』」：深度模型每层的「中间激活」要在显存读写——「<strong>内存带宽常常是推理的瓶颈（不是算力）</strong>」。「算子融合减少中间张量（少读写）、量化省带宽」——「<strong>『省内存访问』是推理优化最有效的方向</strong>」。「<strong>计算快但内存慢 = 推理优化的对象是『内存』</strong>」。</span>

## 4 部署的完整流程

把「模型部署」的工程流程串起来：

1. **导出**：PyTorch → ONNX（确认算子兼容、输出一致）。
2. **验证**：ONNX 输出 vs PyTorch 输出（数值一致）——「转换没出错」。
3. **优化**：图优化 →（可选）量化 →（可选）TensorRT——「推理更快」。
4. **服务**：把优化后的模型封装成服务（REST API、gRPC）——「别人能用」。
5. **监控**：延迟、吞吐、错误率——「上线后要盯」。

**「部署 = 导出 → 验证 → 优化 → 服务 → 监控」**——五个环节，每个都有「防错」点。<span class="marginnote">「部署的『延迟 vs 吞吐』」：<strong>延迟</strong>（单次推理多快——在线服务要低延迟）、<strong>吞吐</strong>（单位时间处理多少——批量要高通量）。「<strong>优化目标不同：在线要低延迟、离线要高通量</strong>」——「batch 推理提吞吐（多个请求一起算）、但增延迟」——「<strong>延迟与吞吐是部署的两个轴</strong>」。理解「服务要哪个」决定「优化方向」。</span>

**易错点：** 部署的「输入预处理」要与「训练时一致」——「<strong>部署时忘记标准化/增强的一致性，模型输出全乱</strong>」（见《数据预处理》的「统计量从训练集来」）。「<strong>部署的预处理 = 训练的预处理（固化）</strong>」——「预处理管线要随模型一起部署」。

## 5 现代部署的演进：从 ONNX 到大模型推理

模型部署在现代的演进：

**传统 CNN**：ONNX + TensorRT——「经典部署」。
**LLM（Transformer）**：专门推理引擎（vLLM、TensorRT-LLM）——「KV cache、连续批处理、投机采样」（见第四级《大模型部署》）。
**边缘部署**：量化 + 剪枝 + 轻量模型——「算力受限的设备」。
**跨平台**：ONNX Runtime（CPU/GPU/移动端）、TFLite、Core ML——「一套模型多端跑」。

**「部署的『共同主线』：导出（互操作）+ 优化（效率）+ 服务（可用）」**——从 CNN 到大模型，这条主线不变，只是「优化手段」随模型/硬件演进。<span class="marginnote">「从『模型部署』到『大模型部署』」：本节是「通用模型部署」（CNN 为主）；大模型（LLM）的部署有「独特的优化」（KV cache、批处理、量化到 4bit）——「<strong>理解通用的『导出-优化-服务』框架，是理解大模型部署的起点</strong>」。「大模型部署的『效率』更是生死攸关」（推理成本直接决定能否商用）——「<strong>部署是大模型『落地』的工程核心</strong>」。</span>

**易错点：** 「部署」不等于「Docker 化」——Docker 是「环境打包」，部署是「模型转换 + 优化 + 服务」。「<strong>『容器化』只是部署的『外壳』，『模型优化』才是部署的『内核』</strong>」。

## 6 小结

- **ONNX**：框架无关的模型交换格式——「一次导出，到处运行」；导出要确认算子兼容。
- **推理优化**：图优化（算子融合）、量化（int8，省 4 倍显存/快 2–4 倍）、TensorRT（GPU 极致）。
- 推理延迟分解：计算 + 内存 + 开销——「深度推理常『内存瓶颈』，优化内存最有效」。
- 部署流程：导出 → 验证 → 优化 → 服务 → 监控——「五个环节，每个有防错点」。
- 延迟 vs 吞吐：在线低延迟、离线高通量——「目标决定优化方向」。
- 现代演进：CNN 用 ONNX/TensorRT，LLM 用 vLLM/TensorRT-LLM——「导出-优化-服务」主线不变。
