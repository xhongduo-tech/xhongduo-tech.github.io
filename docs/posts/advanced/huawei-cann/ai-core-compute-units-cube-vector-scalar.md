## 为什么从三个计算单元开始

上一节我们站在芯片层，看到达芬奇架构的 AI Core 由 **Cube、Vector、Scalar** 三个单元构成。这一节要钻进去：每个单元到底算什么、怎么算、三者如何在一根指令流水线上协作。理解这三个单元，就等于拿到了读 CANN 算子实现（TBE 代码）与性能剖析（msprof 报告）的地图——因为所有算子最终都会被拆成这三类负载，分别派给对应单元。<span class="marginnote">把算子拆成三类的思路，和 CUDA 里「把矩阵乘交给 Tensor Core、其余交给 CUDA Core」异曲同工，只是达芬奇把分工做得更结构化。对照第四级《AI 硬件：NVIDIA H100/Hopper》中 SM 的内部结构阅读，两条路线的「分诊台」设计立刻可见。</span>

## 1 AI Core 的工作方式：一根流水线，三个执行单元

AI Core 本质上是一个**自带指令缓冲与多级片上缓冲的小型处理器**。它执行指令的路径是：

1. **取指**：从指令缓冲（Instruction Buffer）中取出下一条指令；
2. **译码**：识别这条指令该交给哪个单元；
3. **派发**：把指令送入 Cube、Vector 或 Scalar 对应的执行管线；
4. **执行**：三个单元各自从自己的片上缓冲读数据、运算、写回。

关键点在于第 4 步：三个单元是**并行执行**的。一个算子往往同时包含矩阵运算、逐元素运算和控制逻辑，它们被编译成相互独立的指令流，在同一个 AI Core 里流水并行。<span class="marginnote">「一条 AI Core 同时跑三件事」是达芬奇架构能耗比高的核心原因：矩阵乘在 Cube 里算的同时，Vector 已经在算下一个算子的激活，Scalar 则在提前计算循环地址——没有等待，只有流水。</span>

## 2 Cube 单元：为矩阵乘加而生的阵列

**Cube（矩阵计算单元）** 是达芬奇架构的灵魂。它是一块固定尺寸的**乘加（MAC）阵列**，以 16×16 为基本组织单位：每个周期能完成 16×16×16 次乘加运算（即 4096 MAC/周期）。

它的数学模型是矩阵乘加：

$$
C_{16\times16} = A_{16\times16} \cdot B_{16\times16} + C_{16\times16}
$$

一次完整的 GEMM（通用矩阵乘）$C = A \cdot B + C$，会被编译器切分成若干个 16×16 的小块，逐个送入 Cube。切分与搬运由上层控制，Cube 只负责「一块一块地算」——这就是为什么上一节说它「为矩阵而生」。<span class="marginnote">对比参照：NVIDIA Tensor Core 在 Volta 上是 4×4×4、Ampere 上扩展为更大的矩阵块。各家 MAC 阵列尺寸不同，但「用固定阵列做分块矩阵乘」的思路完全一致——这说明矩阵乘已是 AI 硬件设计的共识。</span>

## 3 Vector 单元：逐元素的批处理

**Vector（向量计算单元）** 负责**逐元素（element-wise）** 运算：它一次处理一批（向量化）数据，对每个元素施加同一种运算。

激活函数（ReLU、Sigmoid）、归一化（LayerNorm 中的减均值除方差）、池化的池化核、逐元素加乘——这些算子计算强度低、数据搬运量大，用 Cube 反而浪费。Vector 单元的定位是**高吞吐地流过数据**：把一段连续数据从统一缓冲（Unified Buffer）读入，完成逐元素运算后写回。

Vector 单元支撑的指令集非常丰富：向量加、乘、乘加、比较、逻辑运算，甚至近似激活（用查表或多项式近似算 $\mathrm{exp}$、$\mathrm{tanh}$）。<span class="marginnote">近似激活是工程上的常见做法：硬件不追求数学上完美的指数函数，而是用查表 + 多项式拟合达到足够精度，换取高吞吐。这与 TensorRT 里量化、近似算子的思路同源——精度够用即可，速度优先。</span>

## 4 Scalar 单元：控制流与地址生成

**Scalar（标量计算单元）** 是三兄弟里最不起眼、却最不可或缺的一个。它处理**单个数值**的运算，负责算子里的「胶水逻辑」：

- **循环控制**：矩阵分块的外层循环索引、循环结束判断；
- **地址生成**：为 Cube 与 Vector 计算下一次搬运的数据地址（偏移量、步长）；
- **分支与跳转**：算子内部的 if/else 控制流。

Scalar 单元决定了「下一步往哪搬、搬多少」，而 Cube/Vector 负责「搬来之后怎么算」。可以这样记忆：**Cube 和 Vector 是工人，Scalar 是工头——工人只管埋头算，工头决定算什么、在哪算。**

## 5 公式解析：一次 GEMM 如何被 Cube 消化

把「大矩阵乘」翻译成 Cube 能执行的「小矩阵乘」，是理解达芬奇架构性能的关键一步。设 $A$ 为 $M\times K$、$B$ 为 $K\times N$，则

$$
C[m][n] = \sum_{k=0}^{K-1} A[m][k] \cdot B[k][n], \qquad 0 \le m \lt  M,\ 0 \le n \lt  N
$$

拆成四步：

- **第一步，确定分块尺寸**：Cube 每周期算一块 16×16，于是把 $M\times N$ 的输出切成 $\lceil M/16\rceil \times \lceil N/16\rceil$ 个 16×16 输出块。
- **第二步，确定内层规约**：每个 16×16 输出块需要 $K$ 次「16×16 的乘累加」——即按 $k$ 方向把 $A$ 与 $B$ 的 16 宽切片逐块累加进 $C$。
- **第三步，安排数据流动**：$A$ 的切片放在 Cube 的输入缓冲 L0A，$B$ 的切片放 L0B，累加结果走 L0C；Scalar 单元提前计算这些缓冲的地址偏移。
- **第四步，循环直至完成**：外层循环由 Scalar 驱动，逐个 16×16 块推进，直到整块 $C$ 被累加完、写回统一缓冲或全局内存。

每一步的耗时由「计算」与「搬运」中较慢的一方决定。**当 Cube 的计算速度超过数据供给速度时，系统处于访存受限（memory-bound）状态**——这正是下一节存储层级要解决的核心矛盾，也是 CANN 调优时反复盯住的目标。

## 7 小结

- **AI Core 是自带指令缓冲与片上缓冲的小型处理器**，取指→译码→派发→执行，三个单元并行流水。
- **Cube 单元**：16×16 乘加阵列，负责矩阵乘加，是 GEMM 的主战场；一次 16×16×16 = 4096 MAC/周期。
- **Vector 单元**：逐元素运算的批处理引擎，负责激活、归一化、池化等低计算强度算子。
- **Scalar 单元**：循环控制、地址生成与分支逻辑，是决定「下一步算什么」的工头。
- 大 GEMM 要按 16×16 分块、沿 $K$
