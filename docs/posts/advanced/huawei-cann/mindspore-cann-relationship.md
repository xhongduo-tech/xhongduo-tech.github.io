## 为什么从框架与 CANN 的关系开始

前几篇我们看完了软件栈的骨架，但一个核心问题还没回答：**用昇腾开发，到底该写什么**？答案是：写框架。绝大多数昇腾开发者并不是直接调 AscendCL，而是用 **MindSpore**（华为自研 AI 框架）或 PyTorch（经 torch_npu 适配）写模型，由框架在背后驱动 CANN。这一篇把「框架、CANN、硬件」三者之间的分工边界讲清楚——理解这条边界，你才能判断：模型跑不动时该去框架层找原因，还是该去算子层找原因。<span class="marginnote">MindSpore 是华为开源的 AI 框架（openEuler 生态的姊妹项目），主打「原生支持昇腾」——它在昇腾上的算子覆盖、性能优化最彻底。但昇腾并不锁死 MindSpore：PyTorch 经 torch_npu、TensorFlow 也有对应适配。框架可以换，CANN 是它们共同的底座。</span>

## 1 一条完整的调用链

把一个 MindSpore 训练脚本跑在昇腾上，背后经历这样一条链路：

1. **MindSpore 描述计算**：`nn.Conv2d`、`ops.Softmax` 这类 API 构建计算图。
2. **MindSpore 图模式**：构图后，MindSpore 生成计算图并交给后端；图上的节点是「算子」。
3. **算子映射到 CANN**：MindSpore 的昇腾后端把每个算子映射到算子库（oplib），或经 GE 做图优化。
4. **GE + 运行时执行**：优化后的图交给 GE/运行时，最终由驱动驱动 AI Core 计算。

关键点在第 3 步：**MindSpore 负责「描述」，CANN 负责「执行」**。MindSpore 可以跑在 CPU、GPU、昇腾多种后端上；切后端只需换环境与设备配置，模型代码不变。<span class="marginnote">这与你熟悉的 PyTorch + CUDA 模式完全同构：PyTorch 描述、cuDNN/cuBLAS 执行。MindSpore 的「多后端」是它设计上对标 PyTorch 的体现——同一套模型代码，改一行 device 配置就能在 CPU/GPU/NPU 之间切换。</span>

## 2 MindSpore 特有的「图 + 自定义算子」机制

MindSpore 在昇腾上有一个与其他框架不同的能力：**统一的算子自定义机制**。在 MindSpore 里，要写一个昇腾自定义算子，通常只需要两件事：

**注册算子**：用 MindSpore 的算子注册接口声明算子名、输入输出、属性，让框架认识它。

**提供实现**：实现可以选择 MindSpore 原生算子（跑在框架层）、TBE 算子（跑在 AI Core）、或 Ascend C 算子（更底层的实现）。

这套机制让「框架不认识的新算子」也能无缝接入训练图——这正是大模型时代「模型里出现新算子」场景的关键支撑。**MindSpore 把「算子开发」从框架边缘的脏活，变成了框架内的一等公民**。<span class="marginnote">对照 PyTorch 的 `torch.ops` 注册 + `CustomOp` 扩展机制：MindSpore 的算子注册与其功能等价。区别在于昇腾链路上 MindSpore 原生算子默认就走 TBE/Ascend C，省掉了「PyTorch 自定义 CUDA 算子 + torch_npu 迁移」的额外工作量。</span>

与算子机制配套，MindSpore 还提供**两种运行模式**：**图模式（Graph）** 在构图后把整张图交给后端执行，优化空间大、性能好，是昇腾上的主力模式；**PyNative 模式** 逐算子即时执行，便于调试与逐算子查看。两种模式一键切换——`ms.set_context(mode=ms.GRAPH_MODE)` 与 `ms.PYNATIVE_MODE`。**算子开发的常见节奏是：先在 PyNative 下把数值跑通，再切 Graph 模式验证性能**——这是 MindSpore 独有的「调试与性能两全」设计。

在昇腾上，MindSpore 自定义算子的实现有三条路可选：

- **MindSpore 原生算子**：用框架内置算子组合实现，开发最快，性能受限于组合方式；
- **TBE 算子**：用昇腾算子开发框架实现，可贴合 AI Core 形态，性能上限高；
- **Ascend C 算子**：更底层的 C 语言实现，控制力最强，适合性能敏感的核心算子。

## 3 torch_npu：让 PyTorch 生态在昇腾上跑起来

现实中，大量开发者「习惯了 PyTorch」。昇腾生态没有忽略这一点：**torch_npu** 是华为提供的 PyTorch 昇腾适配层。它的工作原理是：

**算子注册**：torch_npu 把 PyTorch 的算子 dispatch 到昇腾实现，底层调用 CANN 的算子库。

**设备抽象**：PyTorch 的 `device` 参数支持 `npu`，如 `tensor.to('npu')`，与 `cuda` 用法一致。

**分布式支持**：PyTorch 的 DDP 后端可配置为 `hccl`，复用 HCCL 集合通信。

torch_npu 的存在意味着：**你已有的 PyTorch 训练代码，经过很小的改动就能迁移到昇腾**——这是昇腾生态「兼容主流框架」战略的核心一环。<span class="marginnote">「CPU → GPU → NPU」的迁移成本，本质上是「算子实现 + 设备 API」的替换成本。torch_npu 让 PyTorch 程序只改设备名与通信后端即可上昇腾，迁移成本被压到最低。但要注意：<strong>算子的实现细节仍可能影响数值</strong>——迁移后务必重跑精度验证。</span>

从 PyTorch 迁移到 torch_npu，一份最小改动清单是：

- 把 `torch.device('cuda')` 换成 `torch.device('npu')`，`model.cuda()` 换成 `model.npu()`；
- 分布式初始化把 `backend='nccl'` 换成 `backend='hccl'`，`init_method` 指向可达地址；
- 核对每个算子是否被 torch_npu 覆盖，缺失算子查昇腾算子库或走自定义算子；
- 重跑精度验证——迁移后数值可能因算子实现细节有微小差异。

清单之外还有一个心态准备：**迁移不是「换个设备名就万事大吉」，而是「用新底座重跑一次验证」**——Loss 曲线、推理精度、性能基线都要重新采集，与 GPU 时代的结果做对照。

## 4 公式解析：混合框架部署时的「算子覆盖」账

选框架前，先算一笔「算子覆盖」账。设你的模型里有 $T$ 个不同的算子类型，某框架在昇腾后端已原生支持 $S$ 个，则需要自定义算子的比例是

$$
\frac{T - S}{T} \times 100\%
$$

拆三步看：

- **第一步，$T$ 是模型算子类型数**：把模型所有算子按类型去重，得 $T$（如 Conv、MatMul、Softmax、FlashAttention 等）。
- **第二步，$S$ 是原生支持数**：查 MindSpore 或 torch_npu 的昇腾算子支持列表，数出 $S$。
- **第三步，算缺口**：$(T-S)/T$ 是需要写自定义算子的比例。比例接近 0，直接跑；比例明显大于 0，就要评估自定义算子的开发成本。

**这条式子的工程含义是：框架选择不是「喜欢哪个」，而是「算子覆盖谁更全」**。大模型里新算子（如各类注意力变体）多，算子覆盖缺口的判断尤其关键——这是昇腾项目立项时首先要做的调研之一。

**一个数字例子**：假设模型有 12 种算子，torch_npu 原生支持 9 种，则缺口是 $(12-9)/12 \approx 25\%$——四分之一算子需要自定义。若这 3 个缺失算子都是注意力变体、且团队没有算子开发经验，这笔账的结论就非常明确：要么换模型结构，要么先补算子开发能力，再谈上线。**缺口百分比不是「知识题」，而是「行动指南」**。

## 5 昇腾框架选型的最佳实践

把前面四条线收拢，昇腾项目的框架选型可以落到一组可执行的检查清单上：

1. **查算子覆盖**：列出模型全部算子类型，逐一核对 MindSpore 与 torch_npu 在昇腾上的支持情况，算清缺口 $(T-S)/T$。
2. **查存量资产**：团队已有代码是 PyTorch 多还是 MindSpore 多。存量 PyTorch 大，torch_npu 迁移成本最低；新项目，MindSpore 优化更彻底。
3. **查新算子需求**：模型里新算子（FlashAttention 变体、MoE 路由等）多不多。新算子多，选「自定义算子机制更顺手」的那条路。
4. **查多机并行需求**：要大规模多机训练，就查框架对 HCCL 多机通信、参数分片的支持是否成熟。
5. **跑小模型试点**：用 1~2 个代表模型各跑一个训练 epoch，对比 Loss 收敛、每步耗时、显存占用——**纸面调研之后，用数据拍板**。

这套清单的本质是「先量化、再决策」：算子覆盖算得清、存量资产数得清、试点跑得出数据，选型就不会变成「赌运气」。**对大多数团队，答案往往是「torch_npu 先迁移起来，MindSpore 后续做深度优化」**——先把业务跑通，再谈榨干硬件。

**辨析｜易错点：选型不是「非此即彼」**。同一套昇腾集群可以 MindSpore 训一个模型、torch_npu 训另一个模型，两者并存互不干扰——它们共用 CANN 底座与同一批设备。真正该问的不是「选谁」，而是「每个模型哪条路最快上量」。<span class="marginnote">把框架选型类比为「编程语言选型」：语言可以换，但<strong>底层的运行时、内存模型、生态边界是共同的约束</strong>。在昇腾上，CANN 就是那个「共同约束」——无论 MindSpore 还是 torch_npu，最终都落到同一个算子库与同一个 HCCL 上。这也是本专题敢用「CANN 计算架构」统摄全局的原因。</span>

## 6 核心对比表：MindSpore 与 torch_npu 两条路线

选 MindSpore 还是 torch_npu，是昇腾新人的第一个选择题。用一张「核心对比表」摊开：

| 维度 | MindSpore | torch_npu |
| --- | --- | --- |
| 定位 | 华为自研全栈框架 | PyTorch 昇腾适配层 |
| 算子优化 | 原生深度优化，覆盖最全 | 覆盖主流算子，迁移成本低 |
| 语法习惯 | MindSpore 的算子/模型 API | 纯 PyTorch 语法 |
| 生态迁移 | 需重写模型代码 | 改动极小，`npu` 替代 `cuda` |
| 自定义算子 | 框架内统一注册机制 | 需经 torch_npu 的扩展机制 |
| 适合人群 | 新项目 / 深度昇腾优化 | 存量 PyTorch 项目迁移 |

一句话结论：**新项目追求极致昇腾优化选 MindSpore，存量 PyTorch 代码迁移选 torch_npu**。两者底层共用 CANN，所以「选了谁」不改变本专题接下来要学的算子、图、通信知识——它们是共同底座。

## 7 小结

- **MindSpore 是华为自研 AI 框架**，原生深度优化昇腾；PyTorch 经 **torch_npu** 也能上昇腾。
- 调用链是「**框架描述 → 算子映射 → GE/运行时执行 → 硬件计算**」——框架负责描述，CANN 负责执行。
- MindSpore 的**统一算子注册机制**让自定义算子成为框架一等公民；torch_npu 让存量 PyTorch 代码改动极小迁移。
- 选框架先算**算子覆盖缺口** $(T-S)/T$，再谈喜好。
- MindSpore 与 torch_npu **共用 CANN 底座**，本专题后续知识对两者通用。
