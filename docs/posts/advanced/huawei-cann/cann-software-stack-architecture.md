## 为什么从软件栈分层开始

前几篇我们俯视了达芬奇芯片，这一篇要讲软硬件之间那层「看不见的接口层」——**CANN**。CANN 的完整含义是 **Compute Architecture for Neural Networks**，它不是某一个工具，而是一整套软件栈：从应用框架到算子库、从图引擎到运行时、从编译器到驱动。硬件造得再强，软件栈分层不清，开发体验就会淹没在细节里。CANN 的价值在于**用清晰的分层把「硬件形态」封装起来**：应用层只面对框架 API，框架层只面对统一的算子与图接口，真正贴硬件的复杂度被隔离在底层。读懂这张分层图，就拿到了阅读整个昇腾生态的地图。<span class="marginnote">把 CANN 与 CUDA 生态对照：CANN ≈ CUDA Toolkit + cuDNN + TensorRT + 驱动 的合体。两者都是「框架之下、硬件之上」的软件中间层，只是 CANN 把这些能力打包成了一个统一体系。对照第四级《AI 基础设施》的「GPU 软件栈」章节阅读，你会发现每一层都能找到对应物。</span>

## 1 全景：CANN 的六层结构

从顶到底，CANN 软件栈可以画成一条六层链，每层只依赖它下面的一层：

**① 应用层**：客户业务代码——训练脚本、推理服务、数据管线。它只认识框架 API，不接触任何昇腾细节。

**② 框架层**：MindSpore、PyTorch（torch_npu）、TensorFlow 等 AI 框架。框架负责描述模型、反向传播、参数更新，并通过后端适配把算子调用交给昇腾。

**③ 算子与图管理层**：这是 CANN 的核心。包括 **AscendCL**（应用与框架统一接入的 C 语言 API）、**GE（Graph Engine，图引擎）**、**算子库**与算子编译工具（TBE / ATC）。框架的算子调用在这里被翻译成昇腾能执行的形态。

**④ 运行时层**：Runtime（运行环境）、资源管理、内存管理、HCCL 集合通信。它负责「在设备上真正把任务跑起来」。

**⑤ 驱动层**：芯片驱动与固件，让操作系统能访问昇腾设备，也是 `npu-smi` 能看见设备的前提。

**⑥ 硬件层**：昇腾芯片本身。<span class="marginnote">六层各自有明确职责：应用层「要什么」，框架层「怎么算」，算子层「拆成什么算子」，运行时「怎么调度」，驱动「怎么访问硬件」。调试时先问「问题出在哪一层」——这是分层架构给你的第一份礼物。</span>

分层还有一个容易被低估的好处：**版本升级可以按层独立进行**。框架可以换、CANN 可以升、驱动可以单独打补丁——只要各层接口保持稳定。这也是昇腾文档里「CANN 版本与驱动/固件必须配套」的根源：底层变了，上层要在配套约束下重新验证。理解分层，就理解了昇腾生态里大量「版本兼容」规则为什么存在。

## 2 AscendCL：全栈的「统一接口」

六层里，开发者最常直接面对的是 **AscendCL（Ascend Computing Language）**。它是 CANN 对外的编程接口，统一封装了设备管理、上下文、内存、模型加载、算子调用等能力。设计上它有两重身份：

**面向应用开发者**：提供 `aclmdl*` 系列接口做模型加载与推理，`aclrt*` 系列接口做运行时管理，让推理程序不必关心算子怎么实现。

**面向算子/框架开发者**：提供单算子调用接口，供框架后端或自定义算子程序直接驱动设备。

AscendCL 的存在，让「上层只管调 API、下层只管实现」成为可能——**它是 CANN 分层哲学的最直观体现**。<span class="marginnote">AscendCL 的接口分两类命名前缀：`aclrt` 管运行时（Runtime），`aclmdl` 管模型（Model）。看到前缀就知道接口属于哪一层。这一习惯贯穿后续所有章节，记住它能让查文档效率翻倍。</span>

实际开发里，绝大多数「昇腾程序」就是一段 AscendCL 代码 + 一个 `.om` 模型：AscendCL 负责把模型送进设备、把结果取回来。**框架层负责「训练时的复杂」，AscendCL 负责「部署时的简单」**——两种复杂度被分层隔开，各归其位。

## 3 GE 与算子库：把「算子」变成「昇腾算子」

框架层之上是「语义」，之下必须是「可执行」。这一转换由两件事完成：

**GE（Graph Engine，图引擎）**：负责计算图层面的管理——读图、构图、图优化（融合、常量折叠、布局转换）、子图切分，最后把图交给运行时。它的输出是昇腾可执行的图或离线模型（`.om`）。

**算子库（oplib）**：昇腾预置的高性能算子集合——Conv、MatMul、Softmax、LayerNorm 等。框架算子在运行时被映射到算子库中的实现，实现里再拆成 AI Core 的 Cube/Vector/Scalar 负载。算子库覆盖不了的，用 TBE 自定义算子补齐。

一句话概括这条线：**GE 管「图」，算子库管「算子」，两者合起来回答「一张神经网络怎么变成昇腾上可跑的程序」**。<span class="marginnote">把这条线与 CUDA 对照：「算子库 + GE」≈「cuDNN/cuBLAS + TensorRT 的图优化」。昇腾的图引擎与算子库是两层分开的——图层面做全局优化，算子层面做单算子优化，各管一段，边界清晰。</span>

## 4 离线模型与在线执行：两种运行方式

CANN 支持两种把「模型 → 可执行」的路径，是本节最重要的概念分叉：

**在线（Graph 模式）**：框架把算子一个个交给昇腾执行，GE 边构图边执行。灵活，适合调试；但每次运行都要重新构图、优化，开销较大。

**离线（.om 模式）**：先用 **ATC（Ascend Tensor Compiler）** 把模型（ONNX、MindSpore、Caffe、TensorFlow 等）离线编译成 `.om` 文件——融合、布局、量化、算子选择全部在编译期完成。运行期只需加载 `.om` 直接执行，**把最贵的优化提前到「部署前做一次」**。生产推理几乎都用离线模式。<span class="marginnote">离线模式与 TensorRT 的「build engine → deploy」流程同构：都是「编译一次、运行多次」。把优化从运行期挪到编译期，是推理部署性能优化的第一条铁律。后面《ATC 模型转换》会专门展开。</span>

## 5 公式解析：从框架算子到设备算子的「放大镜」

算子从框架到设备，中间要经过一层层映射。设框架层有 $N$ 个算子调用，图引擎经融合后剩 $n$ 个设备算子，且融合比例为 $r = 1 - n/N$，则运行期每步需要启动的算子数为

$$
n = N \times (1 - r)
$$

拆三步看：

- **第一步，$N$ 是框架算子数**：训练脚本里的每个 Conv、每个 ReLU 都是一次框架算子调用。
- **第二步，$r$ 是融合比例**：GE 把可融合的算子（如 Conv+BN+ReLU）合成一个，$r$ 越大、$n$ 越小。
- **第三步，$n$ 决定启动开销**：每次设备算子启动都有固定开销（调度、地址计算、同步），$n$ 越小、运行期越快——**融合比例直接折算成运行期性能**。

这条式子的工程含义是：**看一个昇腾推理程序快不快，先看它实际启动了多少个设备算子**——`msprof` 报告里算子数远小于模型层算子数，说明 GE 的融合优化发挥了作用；反之则要检查融合是否被某处配置挡住了。

## 6 一张图读懂 CANN：从训练到推理的完整旅程

把六层结构连起来，走一遍「一个模型从训练到推理」的完整旅程，CANN 的分工就一目了然：

1. **训练阶段**：框架在前向反向中不断调用算子，GE 在线构图、算子库提供实现、HCCL 做多卡梯度同步——训练是「边跑边优化」。
2. **导出阶段**：训练好的模型导出为 ONNX 或 MindSpore 格式，交给 ATC。
3. **转换阶段**：ATC 调用 GE 做离线优化，产出 `.om`——融合、布局、算子选择在此固化。
4. **部署阶段**：推理程序用 AscendCL 加载 `.om`、执行推理，AIPP 做预处理，结果经运行时返回。
5. **调优阶段**：msprof 剖析运行过程，反馈给算子、图、通信三层做针对性优化。

这条旅程覆盖了本专题全部章节：第 1 篇的架构与软件栈、第 2 篇的 AscendCL 推理、第 3 篇的图与算子、第 4 篇的通信与剖析。**CANN 不是一个「API 集合」，而是一条完整的工作流**——把「训练好的模型」变成「生产环境的算力」。

旅程的每一站都有对应的「验收物」：训练站验 Loss 下降，转换站验 `.om` 加载成功，部署站验推理精度与时延，调优站验剖析报告的指标。**看一个昇腾项目做到哪一步，就看它走到了旅程的哪一站**——这一条比记 API 名字更能帮你建立全局感。<span class="marginnote">把「训练 → 导出 → 转换 → 部署 → 调优」五站记下来，就拿到了昇腾项目的路线图：遇到任何报错，先定位「我现在在旅程的哪一站」，再去对应层的文档找答案——这是分层架构带给你的第一份红利。</span>

## 7 核心要点表：CANN 各层的「对应用户」

本主题是纯概念主题，用一张「核心要点表」替代公式解析收尾：

| 层 | 主要组件 | 使用者 | 一句话职责 |
| --- | --- | --- | --- |
| 应用层 | 业务代码 | 应用开发者 | 描述要什么 |
| 框架层 | MindSpore / torch_npu | 模型开发者 | 描述怎么算 |
| 算子与图管理层 | AscendCL、GE、算子库、ATC/TBE | 平台开发者 | 拆成可执行算子 |
| 运行时层 | Runtime、内存、HCCL | 系统软件 | 调度与执行 |
| 驱动层 | 驱动、固件 | 运维 | 访问硬件 |
| 硬件层 | 昇腾芯片 | — | 实际计算 |

## 8 小结

- **CANN 是昇腾软硬件之间的中间层**：应用 → 框架 → 算子/图 → 运行时 → 驱动 → 硬件，六层各司其职。
- **AscendCL 是统一编程接口**：`aclrt`（运行时）与 `aclmdl`（模型）两类前缀统领全局。
- **GE 管图、算子库管算子**：图层面做融合与布局优化，算子层面拆成 Cube/Vector/Scalar 负载。
- 两种运行方式：**在线构图（灵活）** 与 **离线 `.om`（把优化提前到编译期）**；生产推理用离线。
- 设备算子数 $n = N(1-r)$：**融合比例直接折算成运行期启动开销**。

在下一节，我们将把这张分层图「落地」——从安装部署开始，把驱动、Toolkit、环境变量一步步配好，让这台试验台真正能跑起来。
