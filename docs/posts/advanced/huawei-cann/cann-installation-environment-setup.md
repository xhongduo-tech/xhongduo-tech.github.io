## 为什么从安装部署开始

理论分层再好，跑不起来都是零。昇腾开发环境与普通 CPU 开发最大的不同在于：**它不是装一个 SDK 就完事，而是驱动、固件、工具链、算子库、运行环境层层叠加**，每一层版本还要互相匹配。这一节带你走一遍 CANN 从「裸机」到「能跑第一个样例」的完整路径。学完它，你就有了亲手验证后续所有章节（AscendCL 程序、模型转换、算子开发）的试验台。<span class="marginnote">安装层面的「版本配套」是昇腾生态最有名的坑之一：CANN 版本必须与驱动版本、固件版本、芯片型号严格配套，官方以「版本配套表」约束。这一节给出的路径以官方文档为准，具体版本号请以你手上的昇腾文档为准。</span>

## 1 安装前置：先看清要装什么

CANN 的安装对象可以分为**三个层次**，从下到上：

**驱动（Driver）与固件（Firmware）**：驱动让操作系统能访问昇腾设备，固件是芯片上运行的底层程序。这一层决定了 `npu-smi` 能否看到设备，是一切的前提。<span class="marginnote">可以这样类比：驱动之于昇腾设备，就像显卡驱动之于 GPU——先有驱动，才有后续所有 CUDA/CANN 程序。检查它的命令是 `npu-smi info`，能看到设备型号、健康状态与驱动版本。</span>

**CANN Toolkit**：开发者真正需要的那一层，包含编译运行算子所需的工具链、AscendCL 头文件与库、ATC、TBE 等。安装后路径通常在 `/usr/local/Ascend/ascend-toolkit`。

**可选配套**：MindSpore（华为自研 AI 框架）、torch_npu（PyTorch 昇腾适配）、CANN 的算子包（Ascend-cann-kernels）等，按用途决定装不装。

安装前需要先确认：**芯片型号**（910/310 等）、**操作系统**（Ubuntu/CentOS 等）、**架构**（x86_64/aarch64）、**是否有 root 权限**。这四个参数决定了你下载哪个安装包、用哪种安装方式。

## 2 安装流程：三层依次落下

标准流程是**自底向上**，每一层装完都要验证：

**第一步，装驱动与固件**。下载对应芯片的驱动固件包（`.run` 文件），以 root 执行安装脚本，然后**重启**使驱动生效。重启后运行：

```
npu-smi info
```

看到设备列表、且每张卡的 Health Status 为 OK，说明驱动层就绪。<span class="marginnote">「重启」这一步最容易被人跳过——驱动加载需要进入内核，不重启系统就看不到设备。这也是初学者在昇腾上遇到的第一堵墙：`npu-smi` 报「No device found」时，先检查驱动是否加载、权限是否足够。</span>

**第二步，装 CANN Toolkit**。下载与驱动版本配套的 `Ascend-cann-toolkit_<版本>_linux-<架构>.run`，root 用户安装命令形如：

```
./Ascend-cann-toolkit_8.0.0_linux-x86_64.run --install
```

安装脚本会把工具链释放到 `/usr/local/Ascend/ascend-toolkit/latest`，并生成环境变量脚本。非 root 用户可用 `--install-path` 指定安装到用户目录，但后续某些能力（如算子调优缓存）会受限。

**第三步，配置环境变量**。安装完成后，每次进入开发 shell 前需要加载环境：

```
source /usr/local/Ascend/ascend-toolkit/set_env.sh
```

该脚本设置了 `PATH`、`LD_LIBRARY_PATH`、`PYTHONPATH`、`ASCEND_HOME` 等一系列变量。**忘记 source 是运行期报「找不到 libascendcl.so」这类错误的最常见原因**。

**辨析｜易错点：环境变量是「会话级」的**。`source set_env.sh` 只对当前 shell 生效，换个终端或重启后要重新 source。多版本并存时尤其小心：`latest` 是软链接，指向的版本变了，环境就跟着变。养成「每次进入开发环境先 source、先 `echo` 验证」的习惯，能避开一整个类别的诡异报错。

## 3 环境变量与目录结构

安装完成后，有必要弄清环境里几个关键变量的含义，它们会反复出现在后续所有命令中：

| 环境变量 / 路径 | 作用 |
| --- | --- |
| `ASCEND_HOME` | CANN 安装根目录，一般指向 `/usr/local/Ascend/ascend-toolkit/latest` |
| `LD_LIBRARY_PATH` | 运行时动态库搜索路径，含 `libascendcl.so`、`libruntime.so` 等 |
| `PYTHONPATH` | Python 侧工具链（ATC、精度比对等）的搜索路径 |
| `PATH` | 加入 `ascendc_compile`、`atc` 等可执行文件 |
| `/usr/local/Ascend/driver` | 驱动与工具（`npu-smi` 在此目录的 `tools` 下） |

一个常见的坑：**多版本并存时环境变量指向错误版本**。若同时装了多个 CANN 版本，`latest` 是软链接，`source set_env.sh` 只认当前 `latest` 指向的那个版本——排查问题时先 `echo $ASCEND_HOME` 确认实际生效路径。<span class="marginnote">环境变量是 CANN 运维问题的高发区：版本不配套、路径写死、多个 shell 配置互相覆盖，都表现为「编译通过、运行报错」或「找不到符号」。学会先 `echo` 关键变量，能省掉一半调试时间。</span>

## 4 验证安装：从工具到第一个程序

装完不验证等于没装。按依赖顺序做三件检查：

**检查设备可见**：`npu-smi info` 能看到设备、驱动版本、固件版本。

**检查工具链可用**：运行 `atc --version` 或 `ascendc_compile --help`，确认 ATC 等工具在 `PATH` 中。

**跑一个最小样例**：官方样例包通常自带一个 AscendCL 的 Hello World——申请设备、创建上下文、运行一个最简单的张量运算。它的运行日志会打印设备 ID 与执行成功信息。一个能跑通的最小 AscendCL 程序，意味着环境全链路（驱动 → 运行时 → AscendCL → 设备）已打通。

到这一步，你的「试验台」就绪了：后续学 AscendCL 编程、模型转换、算子开发时，写出的每一段代码都能立刻在这里验证。这也呼应了本章反复强调的分层图——**每一层都被上一节验证过，问题定位就只会在当前层内**。

## 5 核心要点表：三类安装角色与权限

安装方式的选择常让人困惑，本表是该纯概念主题的「核心要点表」，帮你在动手前一次选对：

| 安装角色 | 权限要求 | 适用范围 | 注意点 |
| --- | --- | --- | --- |
| root 全量安装 | 需要 root | 开发机/训练机 | 路径统一在 `/usr/local/Ascend`，环境变量由 `set_env.sh` 提供 |
| 非 root 用户安装 | 不需要 root | 共享集群的个人目录 | 需 `--install-path` 指定目录，部分算子编译缓存功能受限 |
| 容器部署 | 需要镜像内配置 | 云上/容器化训练 | 需透传设备（`--device=/dev/davinci*`），并注意驱动与容器内固件匹配 |

三行各有一个关键词：root 安装的坑是**重启与配套表**，非 root 的坑是**环境变量作用域**（只对当前用户生效），容器的坑是**设备透传**——容器里看不到设备，绝大多数时候不是 CANN 的问题，而是设备没映射进去。

## 6 常见安装问题的排查清单

安装环节的报错几乎都能归到几类「已知剧情」，按频率排一张排查清单：

- **`npu-smi` 看不到设备**：先查驱动是否加载、是否重启过、权限是否足够。
- **找不到 `libascendcl.so`**：多半是没 `source set_env.sh`，或 `LD_LIBRARY_PATH` 被覆盖。
- **`atc` 命令不存在**：Toolkit 没装对，或 `PATH` 没指向 `ascend-toolkit/latest/bin`。
- **版本不配套报错**：CANN 与驱动/固件版本对不上，查官方「版本配套表」对齐。
- **容器里看不到设备**：设备没透传——检查 `--device=/dev/davinci*` 与驱动是否映射进容器。
- **权限不足报错**：非 root 安装后部分功能受限，检查安装目录属主与写权限。

这六类问题的共同点：**都是「版本配套」或「环境配置」问题，而非代码问题**。排查时先确认版本配套表，再逐项核对环境变量——**顺序对了，90% 的安装报错都能自己解决**。<span class="marginnote">安装排查的纪律是「先环境、后代码」：昇腾环境报错时，先把「版本配套、环境变量、设备可见」三项过一遍，再怀疑代码。<strong>绝大多数「编译通过、运行报错」的谜案，最后都落在环境上</strong>——这一条在昇腾生态尤其成立。</span>

## 7 小结

- CANN 安装分**驱动/固件 → Toolkit → 可选配套**三层，自底向上安装、逐层验证。
- 驱动层用 `npu-smi info` 验证，工具链层用 `atc --version` 验证，最后用一个最小 AscendCL 样例打通全链路。
- **版本配套表**是权威约束：CANN、驱动、固件、芯片必须匹配，否则以配套表为准。
- 每个 shell 前 `source set_env.sh`，并先 `echo $ASCEND_HOME` 确认实际生效版本。
- 排查安装问题「先环境、后代码」：版本配套 → 环境变量 → 设备可见，逐项过一遍。
