## 为什么从算子原型开始

上一节我们认识了 TBE，但「写一个算子」的第一步往往不是写计算代码，而是**让系统认识这个算子**。GE 要构图、ATC 要转换、框架要调度——它们都不知道你的新算子长什么样：几个输入？什么形状？什么类型？这些「元信息」由**算子原型（Operator Proto）**来声明。原型定义 + 注册 + 自动生成，构成了昇腾自定义算子的「入场券」：没有这张券，计算实现写得再好也进不了系统。这一节把这张入场券的写法讲透。<span class="marginnote">算子原型之于昇腾 ≈ ONNX 的算子 schema 之于 ONNX：都是「声明算子签名的元数据」。理解原型，你就理解了「系统如何在不看实现的情况下，就敢规划你的算子」——构图、内存规划、形状推导，全靠原型信息。</span>

## 1 原型定义：声明算子的「签名」

算子原型（Proto）用声明式的方式定义算子的接口签名。一份典型原型包含四部分：

**op_type**：算子类型名，系统用它在图里标识这个算子。

**inputs**：输入张量的定义——每个输入的名字、个数（是否可选）、形状推导规则。

**outputs**：输出张量的定义——输出个数、形状如何由输入推出。

**attrs**：算子属性——不是张量、而是标量/枚举参数的配置（如卷积的 stride、pad），在转换与构图时被读取。

**关键认知：原型只声明「接口」，不声明「实现」**。系统靠原型做形状推导、做内存规划、做图优化——但真正算起来，靠的是实现里的计算代码。两者分工，各自独立。<span class="marginnote">「接口与实现分离」是软件工程的通用原则，昇腾算子把这条贯彻到极致：原型管「系统如何规划你」，实现管「实际怎么算」。这带来一个实际好处——原型相同、实现不同（如高精度版、低精度版）的算子可以自由切换，系统只看原型签名。</span>

## 2 形状推导：原型里最核心的「规则」

原型里最重的一块是**形状推导（shape inference）**：给定输入形状，推出输出形状。它是构图期 GE 规划内存的基础。常见推导规则：

**逐元素算子**：输出形状 = 输入形状（`Add`、`ReLU`）。

**规约算子**：输出形状 = 输入去掉规约维（`ReduceSum`）。

**卷积算子**：输出形状由输入、卷积核、stride、pad 共同推出。

推导规则写成「一段逻辑」：输入形状 + 属性 → 输出形状。**形状推导错了，构图期就会报错，或更糟——运行期内存越界**。它是原型里最容易出 bug、也最需要认真写的部分。<span class="marginnote">形状推导出错有两个方向：推得太小，运行期写越界、数据被踩；推得太大，内存浪费。两者都要在「单算子验证」里覆盖——本专题《自定义算子开发与调试验证》会把「先验形状、再验数值」列为第一关，正是防这个坑。</span>

## 3 注册：让系统「找到」你的算子

原型定义好之后，必须**注册（Register）**进系统，系统才能在构图时识别它。注册的完整链条是：

**原型注册**：把算子名与原型信息（输入、输出、属性、推导函数）登记进算子原型库——GE/ATC 转换时在这里查算子签名。

**实现注册**：把算子名与它的实现（TBE/Ascend C 二进制或解释实现）关联起来——运行时在这里找到「怎么算」。

**算子库（oplib）**：注册的落点。CANN 安装目录下的 `oplib` 就是预置算子库，自定义算子注册后同样进入该库体系。

**辨析｜易错点：原型注册与实现注册是两回事**。只注册原型不注册实现，构图能过、执行会报「找不到实现」；只注册实现不注册原型，系统根本不认识你的算子。两者都要注册，且算子名必须一致。<span class="marginnote">「注册是两段式」是昇腾算子新手最常踩的坑：原型和实现分属不同的注册机制。排查「算子找不到」类报错时，先确认两段都注册了、且名字完全一致——大小写、下划线都不能差。这是最容易忽略、也最便宜就能修复的错误。</span>

## 4 自动生成：让工具帮你搭骨架

原型定义与注册有固定模式，手工写既繁琐又易错。CANN 提供了**自动生成（Auto-gen）**能力：根据简单的算子声明，自动生成工程骨架与注册代码。自动生成的产物通常包括：

**算子工程目录**：输入输出定义、原型文件、实现文件、编译脚本的标准布局。

**原型与注册代码**：根据声明生成的输入/输出/属性定义与注册调用。

**测试框架**：单算子验证的脚手架，让你「生成即能跑」。

自动生成的定位是「**搭骨架，不写内容**」：骨架里的形状推导逻辑、计算实现仍需你按语义填写，但接口布局、注册接线、编译配置这类「样板活」被工具包办了。<span class="marginnote">「自动生成骨架 + 手工填语义」是硬件厂商的通行做法：CUDA 的 nsight 模板、Xilinx 的 HLS 模板都这么做。自动生成的收益不只是省打字——它还保证「注册接线」这类样板代码永远正确，把你的精力留给真正的语义。</span>

## 5 公式解析：形状推导的两种写法

形状推导是「输入形状 → 输出形状」的映射。以卷积为例，设输入 $H_{\text{in}} \times W_{\text{in}}$、卷积核 $k$、步长 $s$、补边 $p$，输出尺寸为

$$
H_{\text{out}} = \left\lfloor \frac{H_{\text{in}} + 2p - k}{s} \right\rfloor + 1
$$

拆三步看：

- **第一步，加补边**：$H_{\text{in}} + 2p$ 是补边后的输入尺寸，左右各补 $p$。
- **第二步，减核除步长**：$(H_{\text{in}} + 2p - k)$ 是卷积核能滑动的跨度，除以步长 $s$。
- **第三步，向下取整加一**：$\lfloor \cdot \rfloor$ 处理不能整除的边界，$+1$ 是因为起点位置也算一个输出——**这是形状推导里最经典的取整陷阱**，少写一步结果就差一个像素。

这条式子虽来自卷积，但它揭示的规律普遍适用：**形状推导必须处理整除边界**——逐元素算子的「输出 = 输入」看似简单，一旦涉及分块（本专题 TBE 篇的 $\lceil N/B \rceil$），取整逻辑同样藏坑。

## 6 原型设计的最佳实践

原型写得好不好，直接决定后续开发的顺滑度。几条实战经验：

- **命名清晰**：输入输出名用有语义的名字（`x`、`weight`、`bias`），别用 `input0`、`input1`——错误信息会引用这些名字，清晰的命名让排查少走弯路。
- **形状推导先行**：先把「输出形状怎么推」想清楚再写代码，用纸笔算几个典型例子验证，再落进推导函数。
- **属性有默认值**：属性尽量给默认值，让「不传属性也能跑」——这极大简化单算子验证，也让集成时少踩参数缺失的坑。
- **类型支持尽量宽**：支持的类型（FP16、FP32、INT8…）一次声明全，别等用到才补——补类型往往要重新编译注册。

原型是「系统对算子的第一印象」：印象对了，后面构图、规划、验证一路顺畅；印象错了，错误会以「找不到」「不支持」的形式在系统各处冒出来。**花在原型上的时间，是对后续每一步的复利投资**——它也是本专题《自定义算子开发与调试验证》里「先验形状、再验数值」的第一步的根基。

## 7 核心术语速查表

本节的术语集中在「算子原型与注册」语境，整理如下：

| 术语 | 含义 |
| --- | --- |
| 算子原型 | 声明算子输入输出与属性的接口元数据 |
| op_type | 算子类型名，图内标识 |
| 属性 | 算子的标量/枚举参数（stride、pad 等） |
| 形状推导 | 输入形状到输出形状的推导规则 |

| 自动生成 | 根据声明自动生成工程骨架与注册代码 |

| 单算子验证 | 在最小单元上验证形状与数值正确性 |

## 8 小结

- **算子原型**声明算子的签名：op_type、inputs、outputs、attrs；只声明接口、不声明实现。
- **形状推导**是原型里最核心的规则，卷积公式 $H_{\text{out}} = \lfloor (H_{\text{in}}+2p-k)/s \rfloor + 1$ 要格外小心取整。
- **注册是两段式**：原型注册 + 实现注册，算子名必须完全一致，缺一段都会「找不到算子」。
- **自动生成**搭骨架：工程布局、注册接线、测试脚手架由工具生成，你只填语义。
- 「先让系统认识你」= 原型与注册；「再让系统信任你」= 形状与数值的验证。
