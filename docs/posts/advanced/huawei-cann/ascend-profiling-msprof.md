## 为什么从 Profiling 开始

昇腾上写的程序，「能跑」是及格，「跑得快」才是目标。但性能问题不会自己说话——一个算子慢，到底是 Cube 利用率低、还是数据搬运卡脖子、还是同步等待浪费？这需要**剖析（Profiling）**：用工具记录程序运行的微观过程，量化每个算子的时间与资源占用，再把瓶颈钉死在具体环节。昇腾的剖析工具是 **msprof**（以及配套的可视化分析界面），它是昇腾性能调优的「听诊器」。这一节教你读懂它的报告，把调优从「拍脑袋」变成「看数据」。<span class="marginnote">Profiling 是每个计算平台的标配技能：NVIDIA 用 Nsight Systems/Compute，Intel 用 VTune，昇腾用 msprof。工具不同，但「时间线 + 算子统计 + 资源利用率」的分析框架完全一致。会读 Nsight 的人，看 msprof 报告是「换了套名词」的事。</span>

## 1 msprof 采集什么

msprof 从运行中的昇腾程序采集四类信息，对应四个分析视角：

**算子级统计（Op Statistics）**：每个算子的执行次数、总耗时、平均耗时，按耗时排序——先回答「时间都花在哪个算子」。
**时间线（Timeline）**：Host 与 Device 上任务的起止时间序列，可视化地看算子先后、流间并行、同步等待——回答「任务是怎么排布的」。
- **AI Core 资源利用率**：每个算子在 Cube、Vector 单元的忙闲占比——回答「算子的计算单元是否吃饱」。
- **内存与通信**：设备内存占用峰值、HCCL 通信耗时——回答「内存是否够、通信是否拖后腿」。

采集方式有两种：命令行 `msprof` 直接包住程序运行（最常用），或通过 CANN 的 profiling API 在代码里控制起止。<span class="marginnote">msprof 的采集有开销：开全量剖析会让程序变慢（剖析本身的成本）。工程惯例是先全量采集定位热点算子，再针对热点算子做细粒度剖析——「先看森林，再看树木」，别一上来就钻单个算子。</span>

## 2 读懂报告：三步定位瓶颈

拿到 msprof 报告后，按三步走，从宏观到微观收窄问题：

**第一步：看算子耗时排名**。找耗时 Top 的算子。如果 Top 算子集中、占比极高，说明热点明确；如果耗时分散在几十个算子，说明没有单点瓶颈，问题可能在调度/排布/通信层面。

**第二步：看瓶颈类型**。对热点算子，查它的 Cube 利用率与 Vector 利用率、以及数据搬运时间。对照《昇腾芯片存储层级》的计算强度判据：**Cube 利用率低但搬运时间长 → 访存受限；Cube 利用率接近峰值 → 计算受限且已吃饱**。<span class="marginnote">「利用率高 = 好事」要小心解读：Cube 利用率 90% 说明算得满，但如果它算的是一种本来可以融合掉的冗余计算，那就是「高效地浪费」。利用率要结合「这个算子该不该存在」一起看。</span>

**第三步：看时间线与同步**。用 Timeline 检查流间并行是否真的并行、是否出现大段空闲等待（同步等待、依赖未就绪）。**很多「算子不慢但程序慢」的问题，都藏在时间线的空隙里。**

## 3 常用剖析场景

不同阶段用不同的剖析侧重点：

**推理性能调优**：聚焦单算子耗时与整图执行时间，重点查融合是否生效、排布是否有隐式转换。若报告里出现大量 `TransData` 算子，说明布局优化没做干净。
**训练吞吐优化**：关注每步迭代的总耗时与通信占比。通信占比高 → 检查 HCCL 算法与分层配置；计算占比高 → 深入算子级。
- **内存优化**：看峰值内存与内存复用效果。若峰值内存被某个中间张量顶高，检查融合与复用是否到位。
- **多卡并行分析**：对比各卡的时间线是否负载均衡。某卡明显更慢，多半是通信拓扑或数据切分不均。

每个场景对应一组「先看什么指标」的清单，把这四张清单背下来，剖析报告就不会无从下手。<span class="marginnote">「看数据说话」的纪律很重要：调优之前先采集一次基线报告，改一个参数、再采一次，前后对比。没有基线的调优是碰运气——这也是 msprof 报告里同屏对比多次采集能力如此重要的原因。</span>

## 4 公式解析：AI Core 利用率

剖析报告里的核心指标——**利用率**——本质上是一个比值。设某算子在 Cube 单元上的忙时为 $T_{\text{busy}}$，算子总耗时为 $T_{\text{total}}$，则

$$
\text{Cube 利用率} = \frac{T_{\text{busy}}}{T_{\text{total}}}
$$

拆三步：

- **第一步，忙时 $T_{\text{busy}}$**：Cube 实际执行乘加的时间。它由计算量决定：数据量越大、计算强度越高，忙时越长。
- **第二步，总时 $T_{\text{total}}$**：算子的墙钟时间，包含搬入数据、计算、搬出数据、同步等待的全部。
- **第三步，理解比值**：利用率低 = $T_{\text{busy}}$ 只占 $T_{\text{total}}$ 的一小部分，即**大部分时间 Cube 在闲着**——要么在等数据（访存受限），要么在等同步（调度问题）。

**这条式子的工程含义是：利用率是「症状」，病因藏在 $T_{\text{total}}$**——把分母拆开，看时间到底花在搬入、计算还是等待上，才能对症下药。这也是为什么 msprof 报告要把「利用率」与「耗时构成」放在一起看：单独一个数字没有意义，数字背后的构成才是诊断。

## 5 从报告到行动：一个调优案例

把三步法放进一个真实案例里，报告就不再是「数字罗列」。假设一张推理图的 msprof 报告显示：

- **Top 算子**：`MatMul` 占整图耗时 45%，`TransData` 占 22%，其余散在几十个小算子。
- **瓶颈类型**：MatMul 的 Cube 利用率 82%，但数据搬移时间占总耗时一半——**访存受限**。
- **时间线**：Host 与 Device 之间有大段空闲，说明数据没有提前搬入设备。

对照三步法，行动方案水到渠成：

1. **消灭 TransData**：22% 的耗时是布局转换，说明排布没对齐——先统一 NC1HWC0 排布，消除隐式转换。
2. **压 MatMul 搬运**：访存受限 → 调分块策略提高 L0 命中，或把可融合的逐元素算子并入 MatMul。
3. **提前搬移**：用双流把数据搬移与推理重叠，填掉时间线里的空闲。

这个案例展示的，正是 msprof 的价值：**报告不直接给答案，但它把「猜」变成了「查」**——每个数字都指向一类优化动作，剩下的就是按步骤执行、再采一次基线验证。

## 6 常用剖析命令与数据导出

msprof 的使用不复杂，但有几个「高频操作」值得单独列出：

```
msprof --output=profiling_dir ./your_app      # 全量剖析一次运行
msprof --application="./your_app" --ai-core=on  # 开启 AI Core 剖析
```

剖析结果默认落在输出目录，通常包含时间线数据、算子统计与原始 trace 文件。拿到报告后的常用动作是：

- **看汇总**：先看算子耗时 Top 表，确定热点；
- **看时间线**：在可视化工具里放大到热点算子前后，观察依赖与等待；
- **导出对比**：保留多次剖析目录，用工具做前后对比，验证调优是否生效。

**记住一条纪律：剖析是「对比的艺术」**——单次剖析只有「现状」，两次剖析（调优前后）才有「结论」。工程上习惯给每次剖析命名带时间戳，方便回滚对比。<span class="marginnote">msprof 的剖析开销不可忽视：全量剖析会让程序明显变慢。<strong>生产环境不要常开剖析，定位问题、验证优化时再开</strong>——这正是「先采基线、再采验证」节奏存在的原因。</span>

## 7 核心术语速查表

本节的术语集中在「性能剖析」语境，整理如下：

| 术语 | 含义 |
| --- | --- |
| msprof | 昇腾性能剖析工具 |
| Op Statistics | 算子级统计，按耗时排序 |
| Timeline | 主机与设备任务的时间线 |
| AI Core 利用率 | Cube/Vector 单元的忙闲占比 |
| 瓶颈类型 | 计算受限 vs 访存受限的判断 |
| 计算受限 | 算力不足，计算慢于数据供给 |
| 访存受限 | 带宽不足，数据供给慢于计算 |
| TransData | 数据重排算子，排布未对齐的信号 |
| 基线报告 | 调优前采集的参考性能数据 |
| 双流重叠 | 用两条流让搬移与计算并行 |
| 通信占比 | 多卡场景下通信耗时的比例 |
| 剖析开销 | 采集本身带来的程序变慢 |

## 8 小结

- **msprof 是昇腾的剖析工具**，采集算子统计、时间线、AI Core 利用率、内存与通信四类信息。
- 三步定位法：**看算子耗时排名 → 看瓶颈类型 → 看时间线与同步**，从宏观到微观收窄问题。
- 利用率是「症状」，病因藏在总耗时里：低利用率要么访存受限、要么调度等待。
- 四类剖析场景（推理/训练/内存/多卡）各有「先看什么」的指标清单。
- 调优纪律：**先采基线、改一处、再采、前后对比**——没有基线的调优是碰运气。

在下一节，我们将聚焦调优动作本身——学 **内存复用与算子执行性能优化**，把剖析报告里的「热点」翻译成具体的优化手段。
