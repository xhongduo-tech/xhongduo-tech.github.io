## 为什么从 HCCL 开始

多卡训练是昇腾走向大模型的必经之路，而多卡训练的全部复杂性浓缩在一个词里：**数据交换**。每张卡算完自己的梯度后，必须把结果汇总共享，否则大家「各算各的」就无法收敛。**HCCL（Huawei Collective Communication Library，华为集合通信库）** 正是昇腾多卡通信的答案：它提供 AllReduce、AllGather 等一系列**集合通信原语**，把「多卡之间交换数据」封装成一行调用。理解 HCCL，就理解了昇腾集群训练的数据骨架。<span class="marginnote">HCCL 之于昇腾多卡 ≈ NCCL 之于 NVIDIA 多卡：都是「多 GPU 集合通信库」。对照第四级《AI 基础设施》中「NCCL 与集合通信」章节阅读，两者原语几乎同名、算法同源——这是分布式训练领域的「世界语」。</span>

## 1 为什么需要集合通信

在数据并行训练中，每张卡持有完整模型副本与不同数据分片。每轮迭代的流程是：各卡独立前向反向 → 各自算出一份梯度 → **把梯度求平均（AllReduce）** → 各卡用相同梯度更新参数。

如果没有高效的集合通信，第 3 步会变成一场灾难：梯度张量动辄 GB 级，逐卡搬运既慢又乱。集合通信库把「多卡求平均」封装为一条 `AllReduce`，由库内部选择合适的算法（环、树、分层）与拓扑感知路由——**一行调用，库替你决定数据怎么流**。<span class="marginnote">集合通信的「集合」二字，指「一组设备共同参与的操作」：它不是点对点（device A 发给 device B），而是所有设备按同一模式协作。理解了这个区别，就理解了为什么它需要专门的原语与专门的库。</span>

还有一个容易被忽略的点：**集合通信的开销随规模增长**。单卡训练没有通信，双卡训练通信占比小，千卡训练通信可能占掉每步耗时的三四成——这就是为什么「通信优化」在大模型训练里如此重要，也是本专题后面《多卡训练拓扑》《大模型训练工程实践》的核心动机。

## 2 核心原语

HCCL 提供的一组常用原语，各自的语义可以用一句话说清：

| 原语 | 语义 | 典型用途 |
| --- | --- | --- |
| `AllReduce` | 所有设备的张量规约后分发到所有设备 | 梯度求平均 |
| `Reduce` | 所有设备的张量规约到**一个**设备 | 汇总到主卡 |
| `Broadcast` | 一个设备的张量分发到所有设备 | 广播初始参数 |
| `AllGather` | 每张卡收集所有卡的数据片 | 全量数据汇聚 |
| `ReduceScatter` | 先规约、再按卡分片分发 | 切分后的梯度聚合 |
| `AlltoAll` | 每张卡向所有卡各发一片 | 全对全交换（MoE 等） |

这六个原语基本覆盖了分布式训练的全部数据交换模式。**数据并行训练的主角是 `AllReduce`**；而混合专家模型（MoE）的路由交换则高度依赖 `AlltoAll`——后文《大模型训练在昇腾平台的工程实践》会再见到它们。

HCCL 的 API 以 `Hccl*` 前缀命名，核心调用形如：初始化通信域（`HcclCommInitRootInfo` 等）→ 创建通信域 → 在域内执行原语（如 `HcclAllReduce`）→ 释放通信域。<span class="marginnote">通信域（Communication Group）是 HCCL 的重要概念：一组参与通信的设备构成一个域，域内用 rank（设备编号）寻址。分布式框架（MindSpore 的 HCCL 后端、torch_npu 的 `init_process_group`）在底层维护这些通信域，开发者通常不直接触达。</span>

**原语不是越多越好，而是「按场景选」**：数据并行只要 AllReduce 就够，MoE 要 AlltoAll，参数服务器风格要 ReduceScatter + AllGather。会判断「我的模型需要哪几个原语」，比背全所有原语更值钱——它决定了通信图的结构，也就决定了性能的上限。

## 3 通信算法：环与树

一条 `AllReduce` 在物理上怎么跑？HCCL 依据设备规模与拓扑选择算法，两大主流是：

**环形（Ring）算法**：所有设备连成一个环，数据沿环单向流动。每个设备把自己持有的分片传给下游，同时接收上游分片并做局部规约；经「reduce-scatter」与「all-gather」两阶段完成全量规约。环算法的优势是**带宽利用均衡**，对大规模集群友好。

**树状（Tree）算法**：设备组织成树，叶子向根汇聚、根再向叶子分发。优势是**延迟低**（分层聚合），适合小规模或高延迟敏感的场景。

**辨析｜易错点：算法不是越快越好**。环带宽优但延迟随规模上升，树延迟低但带宽利用不如环。HCCL 的自动选择基于设备数、拓扑与数据量做权衡——手动指定算法（如强制用树）在小规模场景可能更快，但大规模下环往往胜出。<span class="marginnote">算法选择的权衡与 NCCL 的 ring/tree/ 分层实现完全一致：NCCL 也在 ring 与 tree 之间按环境自动切换。理解「带宽 vs 延迟」这条主线，就能读懂 HCCL 环境变量里大量调优项的设计动机。</span>

**辨析｜易错点：ring 的「带宽最优」是对「全量数据」说的**。当数据量很小时，ring 的环上启动与同步开销占比反而高，此时 tree 或 broadcast 的变体可能更快。HCCL 依据数据量动态选择——小数据量、大数据量、混合分桶，各有合适算法，手动指定前先看数据量级。

## 4 公式解析：Ring AllReduce 的通信量

为什么环是「带宽最优」？用通信量公式看清楚。设有 $n$ 个设备，每个设备持有大小为 $S$ 的数据（如梯度张量），一次 Ring AllReduce 中**每个设备实际发送的数据量**为

$$
V = 2 \cdot \frac{n-1}{n} \cdot S
$$

拆三步：

- **第一步，数据量守恒**：全量数据总和是 $nS$，每个设备最终要拿到全部 $nS$ 的规约结果，理论上每个设备至少要「接触」约 $S$ 量级外的数据。
- **第二步，两阶段拆分**：Ring AllReduce 分「reduce-scatter」与「all-gather」两阶段，每阶段每个设备发送 $(n-1)/n \cdot S$，合计 $2(n-1)/n \cdot S$。
- **第三步，看规模效应**：当 $n$ 很大时 $(n-1)/n \to 1$，$V \to 2S$——**每个设备的发送量收敛到数据总量的两倍**，这是把「全规约」拆成两阶段的最小下界，故称带宽最优。

**这条式子的工程含义是：通信量随设备数几乎不增长**（$V \approx 2S$），所以环算法能扩展到成百上千卡而不被通信带宽拖垮——这正是大模型集群选择 Ring 作为主力算法的原因。

**一个数字例子**：设 8 卡、每卡梯度 $S = 1$ GB，则每个设备一次 Ring AllReduce 发送 $2 \times 7/8 \times 1 = 1.75$ GB；而当 $n=1000$ 时收敛到约 2 GB。**通信量随卡数几乎不涨**，这正是 ring 能支撑千卡训练的根本原因——若通信量随卡数线性增长，集群规模早就被带宽卡死了。

## 5 通信与计算的编排：同步与异步通信

集合通信原语只是「动作」，怎么与计算编排才是性能关键。HCCL 提供两种执行方式：

**同步通信**：通信操作阻塞，直到数据交换完成。语义简单，但通信期间设备空闲——大模型梯度同步时，这是主要开销。

**异步通信**：通信与计算重叠——算第 $k$ 层梯度时，同时通信第 $k-1$ 层梯度（分桶 + 流水）。把「通信时间」藏进「计算时间」，是分布式训练提速的经典手法。

工程上还有两个常用技巧：**梯度分桶**（把梯度按层切块，边算边发）与 **通信算子融合**（把多个小通信合并成一次大通信，摊薄启动开销）。

编排的几条口诀：

- **先同步后异步**：第一版用同步通信保证正确，跑通后再改异步重叠；
- **分桶要适中**：桶太碎通信次数多、桶太大重叠度低，按层分组是良好起点；
- **用事件画依赖**：把「梯度就绪 → 通信 → 参数更新」的依赖用同步点显式表达。

**辨析｜易错点：通信与计算的依赖不能乱**。异步通信的前提是「计算只依赖已完成的那部分通信」——分桶后，第 $k$ 层的参数更新必须等到第 $k$ 层梯度通信完成。编排错了，数据竞争会在集群规模扩大时突然爆发。<span class="marginnote">「通信与计算重叠」是分布式训练的核心优化：PyTorch DDP 的梯度钩子、Megatron 的 pipeline bubble 填充，都是这一思想的工程化。<strong>同步通信是「正确的起点」，异步通信是「性能的终点」</strong>——先跑通同步，再逐步改成异步重叠。</span>

## 6 核心术语速查表

本节的术语集中在「集合通信」语境，整理如下：

| 术语 | 含义 |
| --- | --- |
| HCCL | Huawei Collective Communication Library，昇腾集合通信库 |
| 集合通信 | 一组设备共同参与的规约/广播/交换操作 |
| AllReduce | 所有设备的张量规约后分发到所有设备 |
| ReduceScatter | 先规约、再按卡分片分发 |
| AllGather | 收集所有卡的数据片到每张卡 |
| Broadcast | 一个设备的张量分发到所有设备 |
| AlltoAll | 每张卡向所有卡各发一片 |
| 通信域 | 参与通信的一组设备，域内用 rank 寻址 |
| rank | 进程在域内的编号（0 到 N-1） |
| Ring 算法 | 环状单向流动的带宽最优规约算法 |
| Tree 算法 | 树状分层聚合的低延迟规约算法 |
| 通信量 | 每个设备实际发送的数据量，决定扩展性 |

## 7 小结

- **HCCL 是昇腾的集合通信库**，提供 AllReduce、AllGather、ReduceScatter、Broadcast、AlltoAll 等原语。
- 数据并行训练的核心是 **AllReduce（梯度求平均）**，MoE 等场景依赖 **AlltoAll**。
- **通信域**是设备组抽象，域内用 rank 寻址；分布式框架在底层维护通信域。
- 通信算法有**环（带宽优）** 与**树（延迟低）** 两大流派，HCCL 按拓扑自动选择。
- Ring AllReduce 每设备发送量 $V = 2\cdot\frac{n-1}{n}\cdot S$，随设备数收敛到 $2S$——通信量随规模几乎不涨。
- **同步通信是正确起点、异步通信是性能终点**；分桶、融合、事件依赖是编排三件套。
