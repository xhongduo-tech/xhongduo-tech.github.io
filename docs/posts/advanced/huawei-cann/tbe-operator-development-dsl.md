## 为什么从 TBE 开始

昇腾平台的算子库覆盖了大量常见算子，但现实总有无穷的「非标需求」：新的激活函数、特殊融合逻辑、专有算法。这时就需要**算子开发**。CANN 提供的算子开发框架叫 **TBE（Tensor Boost Engine）**，它以 **DSL（领域专用语言）** 的方式，让开发者用相对高层的方式描述「这个算子算什么」，再由编译器生成跑在 AI Core 上的高效代码。这一节讲 TBE 的定位、两种编程风格与一次算子的完整旅程。<span class="marginnote">TBE 之于 AI Core，约等于 CUDA C 之于 GPU——都是「面向特定硬件的核函数语言」。但 TBE 走得更远：它让开发者不必手写每条指令，而是描述计算、由编译器调度。对照第四级《AI 基础设施》里 CUDA 核函数与 Triton 的对比阅读，TBE 的「DSL 化」取向与 Triton 异曲同工。</span>

## 1 什么时候需要写算子

先明确边界：不是所有情况都该写算子。三类场景值得动手：

**算子库缺失**：模型里出现了昇腾算子库（`oplib`）没有的算子，ATC 转换时「算子不支持」报错——这是最常见的触发点。
**融合需求**：GE 的标准融合规则覆盖不了的自定义融合（把多个算子按专有语义合并成一个），可写一个融合算子提升性能。
- **专有算法**：业务特有的计算逻辑，如特殊归一化、定制量化——写在框架层会慢，下沉为算子才快。

反过来，**算子库已有实现时，不要重复造轮子**——写一个「官方算子」的劣化版，是算子开发里最不值得的投入。<span class="marginnote">判断「该不该写算子」的标准：先查算子库（CANN 安装目录的 `oplib` 或官方算子清单），再考虑融合改写，最后才动笔新写。昇腾社区与官方文档都维护了算子支持列表，开发前先查一遍能省下大量时间。</span>

**写算子的三个「先问」**：先问算子库有没有（有就不写）、再问能不能融合（能就不新写）、最后才问怎么写。这三问的顺序，能把「要不要动手」的决策成本降到最低——绝大多数「想写算子」的冲动，在前两问就消解了。

## 2 TBE 的两种开发风格

TBE 提供了两种开发范式，对应不同抽象层级：

**TBE DSL（声明式）**：用计算表达式描述「结果怎么由输入算出来」，不关心数据怎么搬、怎么调度。风格接近 TVM 的 `compute`，编译器负责生成调度。适合相对规整的算子。

**TIK（Tensor Iterator Kernel，命令式）**：以「迭代器」为核心，开发者显式控制**数据搬移、片上缓冲、循环分块**，更像在写「为 AI Core 定制的高级汇编」。TIK 给开发者最大的控制力，也要求开发者最懂硬件。

两种风格的取舍是**抽象与控制的权衡**：DSL 上手快、难失控，但性能上限受编译器调度能力限制；TIK 灵活、可榨干硬件，但开发难度高、易出错。官方路线逐步以 TIK（及其后的 C/C++ 风格 Ascend C）为主，因为算子性能越来越依赖对数据流的手工掌控。<span class="marginnote">这条「从声明式到命令式」的演化路径，与 GPU 生态惊人一致：TVM 的 compute/schedule 声明式写算子，Triton 强调 tile 级控制，CUDA C 则完全命令式。昇腾的 TIK 就是「CUDA C 的昇腾版」——抽象往回收，性能往高走。</span>

**辨析｜易错点：DSL 与 TIK 不是「非此即彼」**。一个算子可以先 DSL 快速验证语义，再对热点用 TIK 重写；甚至同一算子的不同部分用不同风格。成熟的算子开发团队，通常「DSL 起步、TIK 收尾」——先对、再快。

还有一条「风格之外的维度」是**数据流显式化**：TIK/Ascend C 都要开发者显式描述数据搬移（哪个缓冲进、哪个缓冲出），这正是昇腾与 GPU 差异最大的地方——GPU 的 cache 是硬件自动的，昇腾的搬移要软件显式排布。**意识到「搬移是你的职责」，是昇腾算子开发最重要的一次认知升级**。

## 3 一次 TBE 算子开发的完整旅程

无论 DSL 还是 TIK，一次算子开发都要走通以下五个阶段：

1. **原型定义（Proto）**：声明算子的输入、输出、属性与推导规则，让 GE 认识这个算子（下一节专门展开）。
2. **计算实现（Compute/Kernel）**：用 DSL 或 TIK 写出算子的计算逻辑。
3. **注册与编译**：调用注册接口把算子登记进算子库，并编译生成 AI Core 可执行代码。
4. **调试验证**：在昇腾设备上运行，用官方工具（如精度比对、`msopst` 系列工具）对比算子输出与标准结果。
5. **集成调用**：通过 AscendCL 或框架调用自定义算子，接入实际模型。

其中阶段 2 是「写算子」的核心，其余阶段是工程骨架。**一个能用的算子，需要五步全通；一个高性能的算子，重点在阶段 2 与 4 的反复打磨。**

**阶段 4（调试验证）被新手跳过的代价最大**。直接上模型集成，一旦报错，错误可能来自形状、实现、注册、调用任何一个环节——而单算子验证把这个排查空间压到「一个算子」。**跳过验证省下的时间，会在排查里加倍还回去**。

## 4 公式解析：TIK 里的分块与迭代

理解 TIK 的钥匙是「分块（tiling） + 迭代（iteration）」。设要对长度为 $N$ 的一维向量做逐元素运算，AI Core 的片上缓冲一次能容纳 $B$ 个元素，则循环次数为

$$
\text{iterations} = \left\lceil \frac{N}{B} \right\rceil
$$

拆三步：

- **第一步，定块大小 $B$**：$B$ 由片上缓冲容量（如统一缓冲 UB 的大小）决定——一次搬入 $B$ 个元素，算完写回，再搬下一块。
- **第二步，算迭代次数**：$\lceil N/B \rceil$ 表示「向上取整」——末尾不足一块时按一块处理，多出的循环里需处理边界。
- **第三步，理解角色分工**：TIK 程序里，「外层迭代」驱动搬移循环（数据搬进搬出缓冲），「内层计算」在缓冲内逐块完成运算。**分块把「搬不动的大数据」切成「搬得动的小块」**——这是所有 AI 算子都要面对的核心工程问题。

这条式子虽简单，却是 TIK 开发里最先要算清的数：$B$ 选大了，缓冲区放不下或浪费；$B$ 选小了，搬移次数增多、带宽被浪费。**分块尺寸就是算子性能的第一个调优旋钮**，与《昇腾芯片存储层级》里 L0/UB 容量约束直接挂钩。

**辨析｜易错点：$B$ 是「片上缓冲能装多少」的上限，不是「越大越好」的甜点**。$B$ 取满 UB 容量看似最优，但还要给「搬下一块」留缓冲、给计算留余量——工程上常取缓冲容量的 1/2 到 3/4。**块大小是「命中率」与「搬移次数」的平衡点**，用剖析报告微调它，是 TIK 调优的第一课。

## 5 从 TBE 到 Ascend C：算子开发的演进

昇腾的算子开发语言在持续演进，理解这条线能帮你「入对门」：

**TBE DSL（声明式）**：最早的开发方式，用计算表达式描述算子，编译器负责调度。适合规整算子，上手快。

**TIK（命令式）**：以迭代器为核心的编程方式，显式控制搬移与循环，性能上限高但开发难。

**Ascend C（C/C++ 风格）**：当前主推的算子编程语言，用标准 C++ 语法 + 昇腾扩展，把「分块、搬移、计算」结构化表达。它在保留 TIK 控制力的同时，让代码更接近通用 C++，可读性与可维护性更好。

**一句话：演进的方向是「保留控制力、降低开发门槛」**——从声明式到命令式再到 C++ 化，抽象不是无限走高，而是在「够用的抽象」上稳定下来。<span class="marginnote">这条演进与 GPU 生态的轨迹惊人相似：从 CUDA 的手写 kernel，到 Triton 的 tile 级抽象，再到编译器自动调度——硬件厂商都在寻找「控制力与开发效率」的最佳平衡点。<strong>底层能力不变，变的是「写起来多顺手」</strong>。</span>

对初学者，入门的建议是：**从 TBE DSL 起步理解「算子 = 数据流 + 计算」，再学 TIK 掌握「搬移与循环」，最后看 Ascend C 的现代写法**。三个台阶各解决一个问题：语义、性能、可维护。

## 6 核心术语速查表

本节的术语集中在「算子开发」语境，整理如下：

| 术语 | 含义 |
| --- | --- |
| TBE | Tensor Boost Engine，昇腾算子开发框架 |
| DSL | 领域专用语言，用高层描述「算子算什么」 |
| 声明式 | 只描述计算，不关心调度，由编译器生成 |
| 命令式 | 显式控制数据搬移与循环，最大控制力 |
| 算子库 | 昇腾预置算子集合，优先查它再决定是否新写 |
| 融合算子 | 把多个相邻算子合成一个，减少中间搬运 |
| 原型定义 | 声明算子输入输出与推导规则的接口规范 |
| 注册 | 把算子名与原型信息登记进算子库 |
| 分块 | 把大数据切成片上缓冲能装下的小块 |
| 迭代 | 外层循环驱动分块数据的搬移与计算 |
| 编译 | 把 DSL/TIK 代码生成 AI Core 可执行二进制 |
| 验证 | 用单算子测试与精度比对确认数值正确 |

## 7 小结

- **TBE 是昇腾的算子开发框架**，以 DSL 方式描述算子，编译器生成 AI Core 代码。
- 三类场景值得写算子：**算子库缺失、自定义融合、专有算法**；已有实现时不要重复造轮子。
- 两种风格：**TBE DSL（声明式，编译器调度）** 与 **TIK（命令式，显式控制数据流）**——抽象与控制成反比。
- 一次开发走五步：**原型定义 → 计算实现 → 注册编译 → 调试验证 → 集成调用**。
- 分块迭代是 TIK 的核心模型：$\lceil N/B \rceil$ 次迭代，块大小 $B$ 是命中率与搬移次数的平衡点。
- 演进路线：**TBE DSL → TIK → Ascend C**，保留控制力、降低门槛；搬移要软件显式排布是昇腾算子开发的认知升级。
