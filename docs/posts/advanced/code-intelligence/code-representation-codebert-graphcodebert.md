## 为什么从表示学习开始

上一篇我们画出了代码智能的任务地图，但所有任务共享同一个地基：**模型必须先把代码变成一个稠密向量**。这段「代码 → 向量」的映射就是**代码的表示学习（representation learning）**。为什么不能像处理普通文本一样处理代码？因为代码和自然语言有本质差别——**代码的语义由结构承载**：`a + b` 与 `b + a` 的语义不同，但把 token 顺序打乱后统计 n-gram 却几乎分不出来。要在向量空间里真正「抓住代码的意思」，必须让表示学习显式或隐式地编码**语法树与数据依赖**。

这一篇也天然衔接本专题的脉络：CodeBERT 的「双模态」思路来自 NLP 的预训练，GraphCodeBERT 的「图结构」思路来自程序分析——**代码智能的每一步，都是 NLP 方法 × 软件工程知识的杂交**。读懂这篇，你就拿到了解读后续所有代码模型的钥匙。

这一篇我们沿着两条技术路线走：**CodeBERT** 回答「怎么用预训练让 BERT 理解代码」，**GraphCodeBERT** 回答「怎么把代码的结构画成一张图塞进模型」。它们解决的是同一个问题：让 `pass@k` 跑得动、让代码检索排得准，前提都是表示空间里的坐标有意义。<span class="marginnote">表示学习是整个代码智能的「入口」。你会在后续所有文章里反复看到同一个句式：「把代码/issue/补丁编码成向量，然后……」。CodeBERT 与 GraphCodeBERT 定义的，正是这个「然后」之前的部分。</span>

表示质量怎么度量？最终要看「下游任务表现」——检索准不准、补全对不对。但中间可以拆成两个代理：**结构保真**（语义相近的代码，向量距离近吗）与**区分度**（语义不同的代码，向量距离远吗）。后面第 4 篇的对比学习公式，正是把这两个代理落成可优化的损失函数。

## 1 为什么通用的 BERT 在代码上不够用

2018 年 BERT 横扫自然语言处理，把它直接搬到代码上会立刻撞上**三个错位**：

**词表错位。** BERT 的词表是英文单词与子词，而代码的 token 形态完全不同：`snake_case`、`CamelCase`、`->`、`::`、`#include`。即便是同一个标识符，`foo` 在代码里可能同时是函数名、变量名、类名——**含义由位置与上下文决定**，而普通 BERT 的 MLM 并不区分这些角色。<span class="marginnote">标识符重载是代码表示的经典难题：`length` 在 `list.length` 与 `def length():` 中语义完全不同。文本 BERT 会把它们当成同一个词，代码预训练则希望通过上下文把两种表示推开。</span>

**结构错位。** 文本的线性序列几乎就是全部信息；代码在线性序列之下还有一棵**抽象语法树（AST）**和一张**控制流/数据流图**。`return a + b` 在 token 层只有四个符号，在 AST 层却包含「返回语句 → 二元运算 → 两个标识符引用」的层级。线性 Transformer 天然看不见这棵树。

AST 并不只是「给模型多一个输入」那么简单：一棵 500 行的 AST 有上千个节点，怎么把树结构喂给只能吃序列的 Transformer，本身就是研究方向——早期做法是把 AST 序列化拼进 token 序列，GraphCodeBERT 则选择了更轻量的数据流图。**结构信息能不能用、怎么用，决定了模型到底「看见」了多少代码语义**。

**语义错位。** 两段完全不同的文本可能执行完全相同的程序（`x = 1` 与 `x = 0x1`、`/* 注释 */`）。反过来，两段几乎相同的文本可能语义天差地别（`x == y` 与 `x = y`）。文本相似 ≠ 语义相似，而表示学习的目标恰恰是**语义相似**。

「语义等价」在代码里有一个自然语言没有的权威裁判：**执行**。`x = 1` 与 `x = 0x1` 执行结果完全相同，`a+b` 与 `b+a` 对大多数运算也相同。如果表示学习能利用「执行等价」作为监督信号（等价则拉近、不等价则推远），就抓住了代码语义的硬核——这是代码对比学习里最诱人、也最贵的一条路。

这三重错位说明：代码表示学习不是「换个语料重新跑一遍 BERT」，而是要在预训练目标里**把代码特有的信号（结构、数据依赖）注入进来**。CodeBERT 走出第一步，GraphCodeBERT 走出第二步。

这三重错位还解释了另一个现象：**为什么通用大模型（如 GPT-3）也能写代码**。通用模型虽然没显式编码结构，但靠海量代码语料 + 自回归目标，隐式学到了大量结构规律。代码表示学习与通用大模型的差别，在于**是否把结构信号显式注入**——显式注入的样本效率更高，隐式学习的泛化边界更宽，两者不是非此即彼。

## 2 CodeBERT：双模态预训练 + 替换词检测

CodeBERT 是第一个专门面向代码-文本对的预训练模型，架构上采用与 RoBERTa 相同的**单编码器**（base 12 层、768 维）。它的关键贡献是把预训练语料组织成**双模态（bimodal）**：每个训练样本是一个 `<code, 自然语言文档>` 配对，同时混入纯代码与纯文本的单模态数据。

喂给 CodeBERT 的 token 也不是普通英文子词：它使用针对代码的 BPE 词表，把 `snake_case`、`CamelCase`、运算符（`->`、`::`）切分成子词。**代码词表与文本词表的差异**（标识符密度、运算符比例）直接影响模型「分得细不细」——这是被很多人忽略、却实打实影响表示质量的前置步骤。

这里的 `<s>` 与 `</s>` 是特殊 token，`<sep>` 是分隔符——它们把「代码」与「文档」两个模态在一条序列里隔开，让模型既能看单模态（只喂代码），也能看双模态（代码 + 文档）。**模态的拼装方式，决定了预训练任务能不能在两种模态间迁移知识**。

**目标一：遮蔽语言建模（MLM）。** 与 BERT 相同，随机遮蔽输入中的 15% token，让模型根据双向上下文预测被遮住的 token。只不过这里被遮的既可能是代码 token，也可能是文档 token。

**目标二：替换词检测（RTD，来自 ELECTRA）。** 这是 CodeBERT 与 BERT 最实质的区别。训练时用一个**生成器**把一部分 token 换成「看起来像、但其实是假的」候选项（例如把 `length` 换成 `count`），然后让 CodeBERT 这个**判别器**逐 token 判断「这个位置是原文还是被换过」。<span class="marginnote">RTD 的直觉：MLM 只要求模型「能补全」，RTD 要求模型「能区分真假」——后者更接近「真正理解上下文」。ELECTRA 在文本上靠这个目标把样本效率提升了数倍，CodeBERT 把它原样搬到代码-文本对上。</span>

训练完成后，CodeBERT 在下游任务上微调，代表作是**代码检索（code search）**：给定一段自然语言描述，从代码库里找出最匹配的函数。微调目标就是下一节的对比学习公式。

RTD 的生成器与判别器是**联合训练**的：生成器不断把假 token 造得更像真的，判别器则越来越擅长识破——这个「对抗式」的博弈让判别器学到的是「上下文语义」，而不只是「词频统计」。代码场景下，RTD 尤其擅长捕捉「标识符用错」这类错误，因为一个放错位置的 `len` 与 `count` 对不懂语义的模型来说难以区分。

**辨析｜易错点：** 很多人以为 CodeBERT 输出的是「一个代码向量」。实际上对于 `code-search` 这类任务，模型对（代码，描述）这对输入各自编码，取 `[CLS]` 位置的向量（也就是 `<s>` 位置）做相似度。**向量不是某个 token 的，而是整个序列的池化结果**；换池化方式（`[CLS]` vs mean-pooling）会显著改变检索效果，这是做工程时最容易被忽略的细节。

代码检索的微调还有一层讲究：**检索器要在一整个代码库里挑答案，而不是在 batch 里挑**。训练时用 batch 内负样本只是近似，推理时的候选集是整个索引。因此很多系统在微调后还会加一层**检索专用 head**或做「双塔 + 重排序」——这与第 7 篇检索增强的系统设计一脉相承。

## 3 GraphCodeBERT：把数据流图塞进 Transformer

CodeBERT 仍把代码当**线性文本**，结构错位只解决了一半。GraphCodeBERT 的出发点是：**代码里最该被显式编码的不是语法树，而是数据流**——变量从哪来、被谁使用、谁依赖谁。它把代码与**数据流图（data-flow graph, DFG）**一起喂给模型，并用**结构感知注意力（structure-aware attention）**让每个变量 token 只看「与它有数据关系的邻居」。

数据流图不是免费得来的：它需要先解析出 AST，再在 AST 上做「定义-使用」分析，把每个变量名映射到「它被定义的位置」与「它被引用的位置」。这个过程对语法不完整、或跨文件的代码会失败——**DFG 的质量取决于解析器的覆盖度**，这也是 GraphCodeBERT 主要针对「完整函数」评测的原因。

GraphCodeBERT 设计了三个预训练目标：

**目标一：遮蔽语言建模（MLM）。** 与 CodeBERT 相同，遮蔽代码 token 预测原文。

**目标二：节点对齐（node alignment）。** 代码文本里的变量名 token 与 DFG 里的变量节点是一一对应的（同一个 `x` 在文本里出现 5 次，在 DFG 里是同一个节点）。目标：让模型判断「文本里的这个 token，对应 DFG 里的哪个节点」——**这强制模型学会把分散的变量引用聚合到同一个语义实体上**。

**目标三：边预测（edge prediction）。** 随机隐藏 DFG 中的一部分边，让模型预测「这两个变量之间是否有数据依赖边」。这是让模型学到**变量间传播关系**的直接监督信号。<span class="marginnote">边预测的物理意义：`y = x + 1` 中，`y` 依赖 `x`，于是 DFG 里有一条 `x → y` 的边。模型学会预测这条边，就学会了「理解数据从哪流向哪」——这是缺陷检测、程序修复等任务最需要的信号。</span>

在 CodeSearchNet 等基准上，GraphCodeBERT 显著超过 CodeBERT，尤其在**需要跨位置追踪变量**的任务上拉开差距。它证明了代码智能里的一个硬道理：**给模型喂结构信息（DFG），比单纯堆参数更有效**——这也启发了后来的 CodeT5 用 AST、以及 DeepSeek-Coder 用仓库级依赖做长上下文。

GraphCodeBERT 也留下了可讨论的空间：数据流图只捕捉「变量级」依赖，对「函数间」甚至「文件间」的依赖无能为力——这需要第 6 篇的仓库级建模来补。它的意义更多在于**证明了「显式结构信号」这条路走得通**：从此「要不要给模型画图」从疑问句变成了「画什么图」的选择题。

## 4 公式解析：代码检索的对比学习目标

代码检索把「表示学得好不好」落到一个可优化的目标上。设一批（batch）里共有 $N$ 个「代码-描述」配对，第 $i$ 对的代码编码为 $\mathbf{c}_i$、描述编码为 $\mathbf{n}_i$。对比学习的目标是：

$$
\mathcal{L} = -\frac{1}{N}\sum_{i=1}^{N} \log \frac{\exp\left(\mathrm{sim}(\mathbf{c}_i,\mathbf{n}_i)/\tau\right)}{\sum_{j=1}^{N} \exp\left(\mathrm{sim}(\mathbf{c}_i,\mathbf{n}_j)/\tau\right)}
$$

对这条公式做四步拆解：

- **第一步，看懂 $\mathrm{sim}(\mathbf{c}_i, \mathbf{n}_i)$**：这是代码向量与**它自己**的描述向量之间的相似度，通常用**余弦相似度** $\mathrm{sim}(\mathbf{u},\mathbf{v}) = \frac{\mathbf{u}\cdot\mathbf{v}}{\|\mathbf{u}\|\|\mathbf{v}\|}$。它是「正样本对」的得分，代表「这行代码确实配这段描述」。
- **第二步，看懂分母的 $\sum_{j=1}^{N}$**：对固定的第 $i$ 个代码，把**批内所有 $N$ 个描述**都拿来算一遍相似度。其中 $j=i$ 是正样本，其余 $N-1$ 个是「负样本」——别的代码的描述与这段代码并不匹配。
- **第三步，看懂 $\tau$（温度）**：温度系数，控制相似度分布的尖锐程度。$\tau$ 越小，softmax 越「两极分化」，模型越用力把正样本对推高、负样本对压低；$\tau$ 太大则梯度太平滑、学不进去。
- **第四步，看懂整体**：对数里是一个 softmax，它衡量「在这 $N$ 个候选中，模型把正确描述排在多前面」。对整批取平均再取负号，最小化 $\mathcal{L}$
