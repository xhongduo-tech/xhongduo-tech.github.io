## 为什么从代码审查、缺陷检测与安全审计讲起

第 8 篇我们让模型「修 bug」，但修 bug 的前提是**先找到 bug**。代码智能在「写」与「改」之外，还有一大块「**评**」的能力：**代码审查（code review）** 像工程师一样给代码提改进意见，**缺陷检测（defect detection）** 判断代码有没有 bug，**安全审计（security audit）** 专门找安全漏洞。这三件事共同构成代码智能的「质检层」，也是第 10 篇 Agent 化编程里「审阅者」角色的技术基础。

这一篇把三件事放在一起讲，因为它们的**任务形态**高度互补：缺陷检测是**分类**（有没有 bug），代码审查是**生成**（给什么意见），安全审计是**分类 + 生成**（有没有漏洞、属于哪类 CWE、怎么修）。搞清三者的共性与差异，你就拥有了阅读整个「代码质量智能」文献的地图。<span class="marginnote">这三件事在真实工程里的位置也不同：缺陷检测跑在 CI 里（提交时自动拦截），代码审查发生在合并请求（PR）的讨论区，安全审计则常作为上线前的强制关卡。它们在代码生命周期的不同节点把关，但共享同一个技术底座。</span>

## 1 三类任务的分工与共性

先看清三件事的分工：

**缺陷检测（defect detection）**：输入一段代码，输出「有 bug / 无 bug」。本质是**二分类**。它关注的是**功能性错误**——逻辑写错、边界忘处理、空指针没判。代表数据集有 **Devign**（C/C++ 漏洞函数）与 **Big-Vul**（C/C++ 漏洞）。
**代码审查（code review）**：输入一段新提交的代码（diff），输出**评审意见**：代码哪里可以改进、风格是否一致、有没有潜在问题。本质是**文本生成**。代表工作是 **CodeReviewer** 模型——它把「审查评论生成」当成翻译任务来做。
**安全审计（security audit）**：输入代码，输出「**是否存在安全漏洞 + 漏洞类型（CWE）**」。它比缺陷检测更进一步——不只关心「代码对不对」，更关心「代码能不能被攻击者利用」。代表数据集覆盖 SQL 注入、XSS、命令注入等 CWE 类别。

三件事共享同一个技术底座：**编码器 + 任务头**。缺陷检测用分类头，代码审查用生成头，安全审计则两者都要——同一个预训练编码器（第 2 篇的 CodeBERT 及其后继）可以挂不同的任务头，这就是「预训练 + 微调」范式在代码质检上的复现。理解了这一点，你就能把「质检三件事」统一成「一个底座、三个出口」的心智模型。

**辨析｜易错点：** 缺陷检测与安全审计**不是一回事**：缺陷是「程序自己跑错」，漏洞是「攻击者可以让程序跑出不该有的行为」。`list` 越界是缺陷，SQL 拼接用户输入是漏洞——前者影响稳定性，后者影响安全边界。把两者混为一谈，会既误报又漏报。

## 2 缺陷检测：不平衡分类问题

缺陷检测的建模通常是：把函数编码成向量，过一个分类头，输出「有 bug」的概率。但真正难的不是建模，而是**数据的不平衡**：真实仓库里绝大多数函数是没 bug 的，有 bug 的只占百分之几。直接训练，模型会学会「永远说没 bug」——准确率 95%，但一个 bug 也找不出来。<span class="marginnote">这就是分类问题的「<strong>准确率陷阱</strong>」：在不平衡数据上，准确率是没用的指标。缺陷检测报告分数必须用 F1、精确率、召回率，或者干脆按「真实 bug 检出率」来衡量——这也是下一节公式解析要算的账。</span>

解决不平衡的思路有三条：

**重采样**：对「有 bug」类过采样、对「无 bug」类欠采样，把分布扳平。
**代价敏感**：在损失里给「漏报 bug」更高的惩罚（漏报一个 bug 的代价远大于误报一次）。
**用检测信号而非标签**：不直接预测「有没有 bug」，而是预测「哪几行可疑」——把分类问题改成**定位问题**，粒度更细、信息更多。

**辨析｜易错点：** 缺陷检测的**假阳性代价**也不低：如果模型天天喊「这里有 bug」而实际没有，工程师很快就会无视它的输出——「狼来了」效应让检测系统形同虚设。所以缺陷检测产品的目标不是「最大化检出」，而是「**在可接受的假阳性率下最大化检出**」——这个权衡在下一节的成本公式里会精确化。

缺陷检测的**粒度**也在从「函数级」走向「行级」：只报告「这个函数有 bug」太粗糙，工程师要的是「第 12 行可疑」。行级定位本质是把「二分类」细化为「序列标注」——对每一行打「可疑/正常」标签，再配合测试栈或数据流给出定位依据。粒度越细，检测结果越可直接投喂给第 8 篇的 APR 去修复。

## 3 代码审查：生成式评审意见

代码审查是人类软件工程里最耗时的环节之一：一个 PR 可能要等好几个 reviewer 逐行看。**代码审查生成**想让模型当那个「永远在线、第一个给意见的 reviewer」。

**CodeReviewer** 是这条线的代表：它把「代码 → 评审意见」建模成一个序列生成任务，输入是 diff（新增/删除的行），输出是自然语言的审查评论。关键设计有三点：

- **diff 专用编码**：diff 里 `+` 与 `-` 行有完全不同的语义，CodeReviewer 用特殊的标记（如 `<ADD>`、`<DEL>`）把增删信息显式编码进输入——这一点比把 diff 当普通文本喂模型强得多。<span class="marginnote">reviewer 与补全模型的一个关键区别：补全看的是<strong>光标附近</strong>，reviewer 看的是<strong>整个 diff 的结构</strong>——新增行与删除行的对应关系（`-` 后紧跟 `+` 往往意味着「改动」而非「新增」）是评审判断的重要线索，必须显式编码。</span>
**多轮评审**：真实 review 是多轮的（作者改完 reviewer 再看）。CodeReviewer 同时支持「给第一轮意见」与「给修订后意见」，让它更像一个参与对话的 reviewer。
**意见分级**：输出不只是「一段话」，而是带定位（哪一行）、带严重度（阻塞/建议）的结构化意见，便于工程集成。

评审意见的质量评测也有讲究：常用**人工分级**（意见是否有用、是否具体、是否会导致真实改动），以及**自动对齐**（模型意见与人工 review 意见的覆盖度）。和补全的接受率一样，审查意见的「**采纳率**」——工程师按着意见改了多少——是最终裁判。一套「生成 → 建议 → 工程师采纳」的闭环，让审查模型可以用真实反馈持续迭代。

**辨析｜易错点：** 审查生成最大的风险是**泛泛而谈**——模型输出「请补充测试」「请处理边界情况」这类放之四海而皆准的空话。好的评审意见必须**锚定具体代码**（引用行号、指出具体变量、给出具体风险场景）。评测审查模型时，「意见是否具体」比「措辞是否流畅」重要得多。

## 4 安全审计：找漏洞与分类 CWE

安全审计把缺陷检测推向对抗场景：不是「代码会不会自己错」，而是「攻击者能不能利用」。它的两个核心子任务：

**漏洞检测**：判断代码片段是否包含可利用的漏洞。比普通缺陷检测更强调**污点分析（taint analysis）**——敏感数据（用户输入）如何流入危险操作（SQL 查询、命令执行）。模型需要识别「不可信输入 → 未净化 → 危险 sink」这条链路。<span class="marginnote">污点分析是安全审计的独特信号：普通缺陷检测看「逻辑错没错」，安全审计看「不可信的数据有没有被干净地处理」。模型若能学会追踪数据流（这恰好是 GraphCodeBERT 边预测训练的能力），就能在「输入未净化」处发出警报。</span>

**漏洞分类（CWE）**：把漏洞归到 MITRE 维护的 CWE（Common Weakness Enumeration）类别，如 CWE-89（SQL 注入）、CWE-79（XSS）、CWE-78（命令注入）。分类不只是贴标签——不同 CWE 有不同的修复策略与威胁模型，分类准确才能给出对口的修复建议。

与传统的**静态应用安全测试（SAST）**工具相比，LLM 安全审计的优势在于**语义理解**：SAST 靠规则与模式匹配（能抓「明显的危险调用」），LLM 能理解跨函数的数据流与上下文（能抓「间接的污点传播」）。局限则是**幻觉与不可靠**——模型可能漏报也可能误报，且给出「看起来很有道理但错」的修复建议。因此 LLM 审计的落地形态普遍是「**人机协同**」：模型先筛出候选，人工或更严格的工具复核。

**辨析｜易错点：** 安全审计的**漏报代价**远高于误报：误报浪费一次人工复核，漏报可能造成一次真实入侵。因此安全审计产品普遍**偏向召回**（宁可多报、不可漏报），再靠人工与上下文去重。这与普通缺陷检测「平衡精确与召回」的取向不同——**任务的代价结构决定了模型的目标函数**，这是贯穿本节的核心判断。

## 5 公式解析：不平衡数据下的 F1 与成本

缺陷检测与安全审计都是**不平衡分类**，核心指标不能看准确率，要看 F1 与成本。先定义四个基本量：**TP**（真阳性，有 bug 且判有）、**FP**（假阳性，无 bug 误判有）、**FN**（假阴性，有 bug 漏判）、**TN**（真阴性，无 bug 判无）。于是：

$$
F_1 = \frac{2 \cdot \mathrm{Precision} \cdot \mathrm{Recall}}{\mathrm{Precision} + \mathrm{Recall}}, \qquad \mathrm{Precision} = \frac{TP}{TP+FP}, \qquad \mathrm{Recall} = \frac{TP}{TP+FN}
$$

对这条公式做四步拆解：

- **第一步，看懂 Precision**：在模型「说有 bug」的结果里，有多少是真的？它惩罚**误报**——FP 太多时精确率掉。它回答「模型的话值不值得信」。
- **第二步，看懂 Recall**：在真正的 bug 里，模型抓到了多少？它惩罚**漏报**——FN 太多时召回率掉。它回答「模型有没有漏掉该抓的」。
- **第三步，看懂 F1 的调和平均**：F1 是精确率与召回率的**调和平均**（不是算术平均）。调和平均对「一方极低」极其敏感：精确率 0.9、召回率 0.1 的 F1 只有约 0.18，而算术平均是 0.5。**它逼着模型不能「偏科」**——这对不平衡检测至关重要，因为「全说没 bug」可以拿到 0.95 的准确率，但召回率为 0，F1 也是 0。
- **第四步，看懂成本视角**：F1 把精确与召回**等权**对待，但安全审计里两者的代价不对称：漏报一个漏洞的损失（数据泄露、入侵）通常远大于误报一次（浪费人工复核）。于是工程上会**加权**：$\text{Cost} = c_{FP} \cdot FP + c_{FN} \cdot FN$，按业务定 $c_{FP}$ 与 $c_{FN}$，再调分类阈值。**F1 是通用基准，成本函数才是产品决策**。

**辨析｜易错点：** 别只看 F1 而忽略**阈值**。同一个模型，把「有 bug」的判定阈值从 0.5 降到 0.3，Recall 上升而 Precision 下降，F1 可能不变但**错误结构完全不同**。报告评测时务必写明阈值与代价假设——这与第 5 篇「报告分数必须写明采样配置」是同一条纪律。

## 6 核心对比表：三类质检任务的差异

| 维度 | 缺陷检测 | 代码审查 | 安全审计 |
| --- | --- | --- | --- |
| 任务形态 | 二分类 | 文本生成 | 分类 + 生成 |
| 输入 | 函数/代码片段 | 代码 diff | 代码片段 |
| 输出 | 有/无 bug | 评审意见 | 漏洞类别 + 修复建议 |
| 核心信号 | 逻辑正确性 | diff 结构与风格一致性 | 污点分析、CWE 类别 |
| 指标 | F1、召回率 | 意见质量（人工评分） | 召回优先、CWE 分类准确率 |
| 代表数据/模型 | Devign、Big-Vul | CodeReviewer | Big-Vul、CWE 数据集 |
| 代价结构 | 误报与漏报较均衡 | 泛泛而谈 = 无用 | 漏报远重于误报 |

读这张表要抓住**纵轴**：三类任务从「判有无」到「提意见」再到「定威胁」，**难度与责任逐级上升**——缺陷检测报错了顶多误报，安全审计漏报了就是事故。任务定位不同，技术选择（信号、指标、模型形态）也随之分化。

## 7 小结

- 代码质量智能三件事：**缺陷检测**（二分类）、**代码审查**（生成意见）、**安全审计**（分类 + 生成）；它们在 CI、PR、上线前三个节点把关。
- 缺陷检测是不平衡分类：**准确率是陷阱**，要报 F1 / 精确率 / 召回率；用重采样、代价敏感、定位式建模应对。
- 代码审查的核心是**生成锚定具体代码的意见**；CodeReviewer 用 diff 专用编码 + 多轮评审 + 结构化意见。
- 安全审计强调**污点分析**与 **CWE 分类**；其漏报代价远重于误报，目标函数要偏向召回。
- F1 是调和平均，对「偏科」敏感；产品决策用**成本函数** $c_{FP} \cdot FP + c_{FN} \cdot FN$
