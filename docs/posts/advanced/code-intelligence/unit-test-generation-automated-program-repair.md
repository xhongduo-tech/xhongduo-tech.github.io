## 为什么从测试生成与程序修复讲起

前七篇的模型都在「生成代码」，但真实工程里更常见的是**审视与修补已有代码**：新写一个函数要配测试，CI 亮红灯要修 bug。代码智能在「写」之外的另一半战场，是**测试生成（unit test generation）**与**自动化程序修复（automated program repair, APR）**——前者给代码配上「考官」，后者让模型当「修理工」。

这两件事为什么放同一篇？因为它们共享同一个引擎：**生成-验证（generate-and-validate）循环**。测试生成是「生成验证代码的程序」，程序修复是「生成被验证的程序」，两者的质量都要靠「真正跑一遍」来裁决——这正是第 5 篇执行式评测哲学的延续。<span class="marginnote">测试生成与程序修复构成了代码智能的「质量控制层」：生成负责「写」，测试负责「把关」，修复负责「兜底」。没有这一层，代码生成再强也只是一台「敢写但不敢保证对」的机器。</span>

## 1 单元测试生成：为代码写「考官」

单元测试（unit test）是最小粒度的自动化验证：给定一个函数，构造输入，断言输出符合预期。**测试生成**的任务，就是自动为已有代码写出这样的测试。

模型怎么做？主流方法是**行为引导生成**：把被测函数与它的文档喂给模型，让模型产出 `assert` 形式的测试。评测测试质量有两个层次：

**覆盖率（coverage）**：测试执行到了多少代码——行覆盖、分支覆盖。覆盖越全，说明测到了越多角落。
**变异杀伤（mutation killing）**：把一个 bug「故意埋进」代码（变异体），看测试能不能抓住它。抓住得越多，测试越「毒辣」。这是比覆盖率更硬的指标——覆盖率只说明「测到了」，变异杀伤才说明「测出了」。

**辨析｜易错点：** 覆盖率是**手段指标**，不是**目的指标**。一个测试可以覆盖 100% 的代码行，却只断言「程序没崩」——这测不出逻辑错误。**现代测试生成的评测必须配合变异分析**，否则「高分覆盖、零分质量」的测试会轻松骗过只看覆盖率的团队。<span class="marginnote">有一个经典误区值得记住：<strong>测试生成 ≠ 测试质量</strong>。模型可以轻易生成几百个「能跑但什么都没验证」的测试（全部 `assert True`），覆盖率瞬间拉满，但对找 bug 毫无贡献。评测端用变异杀伤率把这类「水测试」筛掉。</span>

## 2 覆盖率的数学：测多少算够

测试生成的目标经常被表述成「提高覆盖率」，但「覆盖率」其实是一族指标，背后有明确的数学定义。设被测程序有行集合 $L$，一个测试 $t$ 执行到的行集合记为 $\text{exec}(t) \subseteq L$：

**行覆盖率（line coverage）** = 至少被一个测试执行到的行数 ÷ 总行数：

$$
\text{LineCov} = \frac{\left|\bigcup_{t \in T} \text{exec}(t)\right|}{|L|}
$$

行覆盖率只看「行有没有被跑到」，看不见分支：`if x > 0` 这一行，无论 `x` 取正取负都「被执行了」，但两个分支里只有一个被真正测到。于是有了**分支覆盖率（branch coverage）**：把每个条件判断的两个出口都当成「可覆盖点」，统计「出口被走到了多少」。

**辨析｜易错点：** 行覆盖与分支覆盖**不是等价**的——行覆盖高而分支覆盖低，说明测试「在代码上滑过但没真正考验它」。实践中看覆盖率要问三个问题：**测的是行还是分支？测试用例有没有断言？目标程序是不是被 mock 掉的？** 三个问题答不清，覆盖率数字就没有意义。

还有一类更硬的指标叫**变异杀伤率（mutation score）**：对源程序做一组小的「变异」（如把 `+` 改成 `-`、删掉一行），看测试套件能杀掉多少变异体。它把「测试测到了什么」升级成「测试发现了什么」——是对覆盖率最有力的补充，也是测试生成评测里的黄金标准。

## 3 自动化程序修复：生成-验证循环

**自动化程序修复（APR）**的任务是：给定一段有 bug 的代码和一条**失败的测试**（回归测试，`FAIL → PASS` 的要求），自动生成一个**补丁**让测试通过。传统 APR 走两条路线：

- **基于修复模板（template-based）**：把常见的 bug 模式映射到修复模板（如「改比较运算符」「加空指针检查」），在可疑位置套模板。快、可解释，但只能修「模板见过的 bug」。
- **基于搜索（search-based）**：在程序变换空间里暴力搜索（如基因编程），用测试结果做适应度。覆盖面广，但搜索空间巨大、效率低。

**LLM 时代的 APR** 把这两条路统一成「**生成-验证**」循环：

1. **定位**：先用缺陷检测（第 9 篇）或测试堆栈找到可疑代码行。
2. **生成**：把「可疑代码 + 失败测试 + 周围上下文」喂给模型，让它产出候选补丁（一次多个）。
3. **验证**：逐个跑测试——必须**通过全部已有测试**（不能引入回归）且**通过失败测试**（bug 被真正修掉）。
4. **迭代**：若都失败，把失败信息反馈回模型，再次生成。

**辨析｜易错点：** APR 最容易踩的坑是「**过度修复（overfitting）**」：补丁通过了现有测试，但只是「特判」了测试输入，真实场景里 bug 还在。评判补丁质量必须用**保留的测试**（训练时没见过的 hidden test）——这与第 5 篇 HumanEval 用隐藏测试是一个道理。**能过给定测试 ≠ 修好了 bug**，这个区别贯穿整个 APR 领域。

补丁的**表示方式**也影响修复效果：直接输出「新的完整函数」会让模型偏离原风格，输出「统一 diff 格式」则贴近工程师习惯、也便于审查与回滚。现代 APR 系统普遍让模型生成 diff 而非整段重写——**补丁粒度越细，越容易验证与合并**。

## 4 公式解析：覆盖率的两种定义

第 2 节把行覆盖率写成了集合公式，这里把它和分支覆盖率放在一起，拆清楚「测多少算够」的数学结构。

**行覆盖率**（测试至少执行到一次的行占比）：

$$
\text{LineCov} = \frac{\left|\bigcup_{t \in T} \text{exec}(t)\right|}{|L|}
$$

**分支覆盖率**（条件判断的每个出口至少走到一次的比例）：

$$
\text{BranchCov} = \frac{\left|\bigcup_{t \in T} \text{branch}(t)\right|}{|B|}
$$

对这两条公式做四步拆解：

- **第一步，看懂 $\bigcup_{t \in T} \text{exec}(t)$**：把所有测试执行到的行**取并集**。用并集而不是求和，是因为同一行被多个测试执行只算一次——覆盖率问的是「整个测试套件覆盖了多少」，不是「总共执行了多少次」。
- **第二步，看懂 $|L|$ 与 $|B|$**：$L$ 是行集合，$B$ 是分支出口集合。分支出口把 `if`/`while`/`ternary` 的每个出口都当成独立单元，所以 $|B|$ 通常大于「条件行数」。
- **第三步，看懂分子分母之比**：覆盖率是一个 $[0,1]$ 之间的数——1 表示「全部行/分支都被测到」，0 表示「一个都没测到」。它不是「覆盖率越高测试越好」，而是「覆盖率越高，没被考验的角落越少」；两个测试可能覆盖率相同，但一个断言充分、另一个只是「跑过」，价值天差地别。
- **第四步，看懂并集的意义**：并集 $\bigcup$ 强调覆盖率是「测试套件整体的覆盖」，不是「单个测试的覆盖之和」。它隐含着一个设计选择——**覆盖率衡量的是「探索了多少」，变异杀伤率衡量的是「发现了什么」**，后者才是测试质量的真指标。

举一个具体例子：某函数有 10 行代码、4 个分支出口，一个测试跑了其中 8 行、3 个出口——行覆盖率 80%、分支覆盖率 75%。若第二个测试把剩余 2 行也跑到，行覆盖变 100%，但分支出口若仍只走到 3 个，分支覆盖还是 75%——**「多跑几行」和「多考验几个分支」是两件事**，这正是两类覆盖率不能互相替代的原因。

## 5 核心对比表：测试生成与程序修复

| 维度 | 测试生成 | 自动化程序修复（APR） |
| --- | --- | --- |
| 目标 | 为代码写验证 | 为失败测试写补丁 |
| 输入 | 函数 + 文档 | 可疑代码 + 失败测试 |
| 输出 | 断言形式的测试 | 统一 diff 补丁 |
| 关键指标 | 覆盖率、变异杀伤率 | FAIL→PASS 且不破坏已有测试 |
| 核心风险 | 「水测试」（assert True） | 过度修复（特判测试） |
| 与评测的关系 | 生成评测的「考官」 | 复用评测的执行环境 |

读这张表要抓住一个对称性：**测试生成与程序修复是「考官」与「考生」的关系**——测试生成给代码配考官，程序修复给失败的测试补答案；而两者的质量都要由「真正跑一遍」来裁决。这正是第 5 篇执行式评测哲学在质量层的复现：**能跑，是一切代码智能质量的底线**。

变异分析的具体做法是把源程序做一组小扰动（把 `+` 改成 `-`、删掉一行、反转条件），每个扰动是一个「变异体」；测试套件能杀掉多少变异体，变异杀伤率就是多少。它比覆盖率「硬」的地方在于：**覆盖率只证明「这段代码被执行了」，变异杀伤率证明「执行之后，测试真的发现了问题」**——后者才是「给代码把关」的真本领。

## 6 小结

- **测试生成**为已有代码写断言，质量看两层：**覆盖率**（测到多少）与**变异杀伤率**（测出多少），后者是黄金标准。
- 覆盖率是手段指标不是目的指标：100% 行覆盖 + 没有断言 = 零价值；报告覆盖率必须说明「行还是分支、有无断言、是否 mock」。
- **自动化程序修复（APR）** 用「生成-验证」循环：定位 → 生成候选补丁 → 跑测试 → 迭代；输出统一 diff 格式便于审查与回滚。
- APR 的头号陷阱是**过度修复**：补丁通过现有测试但只是特判，评判必须用保留的隐藏测试——「能过给定测试 ≠ 修好了 bug」贯穿整个领域。
- 行覆盖率与分支覆盖率的数学结构：$\text{LineCov} = |\bigcup_t \text{exec}(t)|/|L|$，$\text{BranchCov} = |\bigcup_t \text{branch}(t)|/|B|$，并集强调「套件整体覆盖」。
- LLM 时代的 APR 把模板修复与搜索修复统一成「生成-验证」，用测试结果而非人类偏好做裁决信号。
- 测试生成评测常见「水测试」防线：能跑但只 assert True 的测试拉满覆盖率却毫无贡献，变异杀伤率把它们筛掉。
- 行为引导生成的测试要能「真正执行」：mock 掉网络与文件系统，保证测试在 CI 里可复现、可并行。

测试生成与程序修复把代码智能的「可靠性」补上了最后一块拼图：**模型不仅能写出代码，还能为代码把关、替代码治病**。这一层的成熟，是第 10 篇 Agent 能「自己跑测试、自己改代码」的前提——没有质量层，Agent 的自主闭环根本无从谈起。

在下一节，我们将从「修代码」进一步到「评代码」：**代码审查、缺陷检测与安全审计**——缺陷检测把「修」的起点自动化，代码审查与安全审计把「质量关」从测试扩展到人类工程的全部环节。
