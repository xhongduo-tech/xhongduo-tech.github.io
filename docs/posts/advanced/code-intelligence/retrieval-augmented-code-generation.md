## 为什么从检索增强讲起

上一篇我们撞上了长上下文的两难：**窗口太长，算力爆炸且注意力稀释；窗口太短，装不下仓库的关键依赖**。检索增强（retrieval-augmented generation, RAG）提供了第三条路：**不把整个仓库塞进模型，而是先检索出「与当前任务最相关」的代码片段，再让模型基于这些片段生成**。

这套思想从自然语言的 RAG（Lewis et al., 2020）移植到代码后，立刻成了仓库级代码智能的标配：Copilot 从仓库里检索相似函数、Agent 从仓库里检索相关文件、代码搜索引擎从「关键词匹配」升级为「语义检索」。这一篇讲清检索增强的四个问题：**为什么要检索、检索什么、怎么检索、检索结果怎么喂给生成器**。<span class="marginnote">RAG 的核心心智模型是「<strong>开卷考试</strong>」：不要求模型记住所有知识（记不住、还会记错），而是允许它「翻书」——把翻到的相关材料直接放进上下文。对代码而言，「书」就是仓库本身，答案常常就藏在某个相似的函数里。</span>

## 1 为什么要检索：长上下文的两难

先看一个具体场景：模型要在 Django 仓库里实现一个「用户注册后发送欢迎邮件」的函数。它需要知道 `User` 模型长什么样、项目里现成的邮件工具叫什么、以及团队习惯的错误处理风格。如果只给函数签名，模型「盲猜」——大概率猜错；如果给整个仓库，模型「淹没」——100k token 里关键信息只有几百个。

检索增强把这个问题拆成两步：**先缩小范围，再专注生成**。第一步用检索器把「整个仓库」缩成「top-k 个相关片段」（通常 5–20 个，几千 token）；第二步让生成器只看这些片段。**它同时解决了算力（输入变短）与准确性（信息更聚焦）两个问题**，还带来一个额外红利——**可解释性**：模型引用了哪段代码，是可以查证与审计的。

但检索增强也有明确的**不适用场景**：当任务「自包含」时（HumanEval 式的单函数题、写一个不依赖外部代码的算法），检索纯属浪费——不仅增加延迟，还可能把无关代码带进来干扰生成。**判断「该不该检索」本身就是一种能力**，成熟的系统会按任务的上下文相关性动态开关检索。<span class="marginnote">检索增强还有一个常被低估的工程价值：<strong>模型更新与知识更新解耦</strong>。仓库里加了一个新函数，不需要重训模型，只需把新函数索引进检索库——检索库是「可插拔的知识」，这让系统能跟上快速演进的代码库。</span>

**辨析｜易错点：** 检索增强不是「免费的午餐」，它引入了**检索失败的风险**：如果检索器没找到关键片段，模型就会在「缺少必要上下文」的情况下生成——结果可能比不检索更糟（自信地错）。因此**检索覆盖率（recall）比检索精确率（precision）更重要**：宁可多给几个无关片段（模型能忽略），不可漏掉关键片段（模型会跑偏）。

检索增强与长上下文不是二选一，而是互补：

| 方案 | 输入规模 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 全仓库长上下文 | 100k+ token | 信息完整、无需检索 | 算力爆炸、注意力稀释 |
| 纯检索增强 | top-k 片段（几 k token） | 聚焦、省钱、可解释 | 有漏检风险 |
| 检索 + 长上下文混合 | 相关片段 + 部分全局 | 兼顾全局与聚焦 | 系统复杂度高 |

读这张表，结论很清晰：**检索增强不是长上下文的替代品，而是它的互补品**。仓库级系统通常「先检索关键片段、再配合适度长上下文」，把两种方案的优点都拿到——这也是第 6 篇与本文合起来要传达的完整方法论。

## 2 检索什么：从函数库到代码块

检索的「文档单元」粒度，直接决定系统效果。常见的四种粒度：

**整文件（file）**：粒度最粗，上下文冗余多，但保留完整上下文。
**函数/类（function/class）**：最常见的粒度——按函数切块，检索「相似函数」。
**代码块（code chunk）**：按语句块或逻辑段切分，粒度细、检索准，但可能切断函数内依赖。
- **多模态单元（code + doc + commit）**：把函数、它的注释、相关 commit 消息绑成一个检索单元，让模型同时看到「实现 + 意图 + 变更历史」。

**辨析｜易错点：** 切块方式要**尊重语法边界**。按「固定 token 数」硬切会把一个函数拦腰截断，检索回来的片段残缺不全，生成器根本没法用。成熟系统普遍用**AST 感知切块**：先解析出函数/类边界，再在其内部按需细分。切块质量决定了检索质量的下限。

检索库的**构建与更新**也有讲究：代码库每天都在变，索引需要增量更新；删除的函数要从索引里移除，新函数要及时加入。索引的陈旧会让检索「看到已经不存在的东西」，生成器据此生成注定过时的代码。**索引的新鲜度，是检索系统长期运行最大的隐性成本**。

## 3 怎么检索：BM25、稠密检索与混合检索

检索器把「查询」（当前要补全的代码片段或需求描述）与「候选单元」逐一打分排序。代码检索有三代技术：

**第一代：BM25 关键词匹配。** 基于词频与逆文档频率打分，快、可解释、零训练成本。对代码很有效——因为代码里的标识符（`get_user`、`send_email`）本身就是高度区分性的「关键词」。但 BM25 不懂语义：`fetch_user` 与 `get_user` 是不同 token，BM25 认为它们毫无关系。

**第二代：稠密检索（dense retrieval）。** 用嵌入模型把「查询」与「候选」都编码成向量，按余弦相似度打分。代表是 CodeBERT、UniXCoder 训练的代码检索器。它弥补了 BM25 的语义盲区——语义相近的函数即使 token 完全不同也能被匹配。代价是需要训练、需要向量索引（如 FAISS）、对 OOV 标识符敏感。<span class="marginnote">稠密检索对代码有个独特挑战：<strong>标识符是「稀疏但极重要」的信号</strong>。`def compute_average(numbers)` 与 `def mean(values)` 语义相同但词汇完全不同，稠密模型靠「见过足够多相似代码」才能学到这种对应——这正是第 2 篇表示学习打下的地基。</span>

**第三代：混合检索（hybrid retrieval）。** 把 BM25 与稠密检索的分数**加权融合**（如 RRF 排序融合），再做一个重排序器（reranker）精排 top-k。工程实践基本收敛到「混合检索 + 重排序」——BM25 保证召回，稠密保证语义，重排序保证最终 top-k 里不混入噪声。

重排序器本身也可以是一个小的编码器模型：对「查询-候选」对打分，在 top-100 的宽召回上精排到 top-10。它比稠密检索更准（因为输入是「配对」而非「单独编码」），但也要多跑一次推理——**重排序的延迟与精度的权衡，是检索系统设计的日常**。

选择嵌入模型时，通用文本嵌入与代码专用嵌入（如 CodeBERT 检索器）差距明显：代码嵌入更擅长处理标识符与语法结构。**用领域匹配的嵌入模型，是稠密检索上线的第一课**。此外，向量索引（如 FAISS）需要按批更新、支持近似最近邻（ANN）以在百万级片段上毫秒返回——检索系统的延迟预算与生成器一样严格。

**辨析｜易错点：** 别在「稠密 vs 稀疏」上二选一。代码场景里两者的失败模式互补：BM25 漏掉「语义相同但词汇不同」，稠密检索漏掉「罕见但精确匹配」。**混合检索的收益几乎总是超过单用任一者**，代价只是多维护一个索引。

## 4 公式解析：RAG 的边缘化目标

RAG 的生成目标不是「只看输入生成」，而是「**先选上下文，再基于所选上下文生成**」。形式化地说，模型对输出 $y$ 的概率要对所有可能的检索结果 $z$ 求边缘化：

$$
p(y \mid x) = \sum_{z \in \text{top-}k(x)} p_\eta(z \mid x) \prod_{i} p_\theta(y_i \mid x, z, y_{<i})
$$

对这条公式做四步拆解：

- **第一步，看懂 $\text{top-}k(x)$**：给定查询 $x$（当前代码），检索器返回**概率最高的 $k$ 个候选片段**组成的集合。边缘化只在 $k$ 个候选中进行——这是「开卷但只翻到 top-k 页」的数学化。
- **第二步，看懂 $p_\eta(z \mid x)$**：这是**检索器**的分布——它认为候选 $z$ 与查询 $x$ 有多相关。在经典 RAG 里，$\eta$ 是检索器参数（BM25 分数或稠密检索相似度都可以被归一化成这个概率）。
- **第三步，看懂连乘 $\prod_{i} p_\theta(y_i \mid x, z, y_{<i})$**：这是**生成器**在「给定查询 $x$ 与检索片段 $z$」下，逐个 token 生成 $y$ 的概率——与第 3 篇的因果语言模型目标完全同构，只是上下文从「只有 $x$」扩展为「$x + z$」。
- **第四步，看懂整体**：对每个候选 $z$ 算「检索权重 × 生成概率」，再把 $k$ 个候选的结果**加起来**。求和意味着「只要有一个候选提供了正确上下文，整体概率就高」——这量化了 RAG 的直觉：**检索不一定要命中「最好」的那一条，命中的多条里有一条是对的就行**。

**辨析｜易错点：** 实际工程中很少严格做这个边缘化（$k$ 个候选各自生成一遍，算力×k），而是简化为「**top-1 或 top-k 拼接**」：把检索到的候选直接拼进提示词，让生成器一次生成。这种「检索增强」不严格等于 RAG 的边缘化目标，但效果好、成本低——**论文里的 $p(y|x)$ 是理论理想，工程里拼上下文是务实折衷**。

从公式还能读出一个设计权衡：**$k$ 的大小是检索增强的核心超参数**。$k$ 太小（如 $k=1$），漏检风险高，且边缘化几乎退化成「只看一条」；$k$ 太大（如 $k=50$），提示词被无关片段稀释，回到长上下文的两难。多数系统取 $k \in [5, 20]$，并配合「相关片段在前、无关在后」的排序来摆放上下文。

## 5 典型系统：RepoCoder 与 RACE 的检索-生成闭环

检索增强代码生成的代表性系统，展示了「检索」与「生成」如何咬合成闭环。

**RepoCoder** 是典型的「迭代检索生成」：它先生成第一版代码，把「已生成的代码」当作新的查询去检索仓库里的相似代码，再基于检索结果重写——**生成到一半的代码本身也是检索查询**。这种「生成即查询」的设计，让检索逐步逼近项目里真正可复用的实现。评测表明，RepoCoder 在仓库级补全上显著超过「一次性检索生成」，因为它利用了「越写越像本仓库」的一致性信号。<span class="marginnote">RepoCoder 的洞见可以概括为：<strong>检索查询不是一次定死的</strong>。随着模型逐渐生成符合仓库风格的代码，这些「半成品」本身就成了更好的检索种子——检索与生成互相促进，形成正反馈。</span>

**RACE**（检索增强的代码编辑）则展示了**跨任务迁移**：把检索到的相似代码块与要编辑的代码块配对，让模型学习「把这块代码改成目标形式」。检索在这里不只是「提供上下文」，而是「提供编辑范例」——模型看到「相似的输入输出对」，从而推断出「我要做的编辑」应该长什么样。

这两个系统的共同模式是：**检索器决定「看什么」，生成器决定「怎么写」，两者通过「查询构造」互相咬合**。检索增强不是「拼一段代码进提示词」这么简单，而是一套「检索-生成」的策略设计。

评估检索增强系统，要把**检索质量与生成质量分开测**：检索用 Recall@k（top-k 里是否包含关键片段）与 MRR；生成用 pass@k。两者要一起看——检索准但生成差，是生成器问题；检索差但生成好，是「盲猫碰到死老鼠」。分开测才能定位瓶颈，也才能回答「瓶颈在检索还是在生成」这个最常被问的问题。

## 6 小结

- 检索增强解决长上下文的两难：**先检索 top-k 相关片段，再专注生成**，同时改善算力与准确性。
- 检索单元分**整文件、函数、代码块、多模态单元**四档；AST 感知切块是检索质量的下限。
- 检索技术分三代：**BM25 关键词、稠密检索、混合检索 + 重排序**；两者的失败模式互补，混合几乎总是更优。
- RAG 的边缘化目标 $p(y|x) = \sum_z p_\eta(z|x) \prod_i p_\theta(y_i|x,z,y_{<i})$ 是理论理想；工程上常用「top-k 拼接」务实折衷。
- 检索覆盖率比精确率更重要：宁可多给无关片段，不可漏掉关键片段。
- RepoCoder 与 RACE 展示了「**生成即查询**」的迭代检索与「**检索即范例**」的跨任务迁移，是检索-生成闭环的两种范式。
- 检索库是「可插拔的知识」：模型更新与知识更新解耦，这是 RAG 在快速演进代码库中的工程红利。
- $k$ 的大小是检索增强的核心超参数：太小漏检风险高，太大提示词被无关片段稀释，多数系统取 $k \in [5, 20]$。
- 评估检索增强系统要把**检索质量与生成质量分开测**：检索用 Recall@k / MRR，生成用 pass@k，分开测才能定位瓶颈。
- 检索增强与长上下文是**互补而非替代**：仓库级系统通常「先检索关键片段、再配合适度长上下文」。
- 混合检索（BM25 + 稠密 + 重排序）几乎总是优于单用任一者，代价只是多维护一个索引。
- 重排序器对「查询-候选」配对打分，在宽召回上精排，是混合检索的最后一道闸门。

检索增强把代码智能从「背下所有知识」的强求中解放出来——模型不必记住仓库的每个细节，只需要知道**去哪翻、翻到什么、怎么用翻到的东西**。
- 检索器上线第一课：用代码专用嵌入（如 CodeBERT 训练的检索器）而非通用文本嵌入——标识符与语法结构只有领域嵌入才「看得懂」。这套「开卷考试」的哲学，贯穿了第 6 篇的仓库理解、本篇的检索，也将延续到第 10 篇的 Agent：Agent 每走一步都要检索，本质上是把「翻书」做成了循环。

在下一节，我们将把「生成 + 验证」的循环用到质量层：**单元测试生成与自动化程序修复**——检索负责找到弹药，测试与修复负责保证「改对了」。
