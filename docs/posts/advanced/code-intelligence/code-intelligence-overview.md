## 为什么从代码智能概览开始

这个网站叫「从极限到大模型」：从微积分的第一道极限，一路走到当代大模型。中间有一条容易被忽略却举足轻重的暗线——**代码**。大模型是被代码训练出来的：它读的语料里，代码占了近两成；它解决的问题里，「写代码、改代码、查代码」是最高频也最赚钱的场景之一。**代码智能（code intelligence）**，就是「让语言模型理解、生成、检索、修复程序」这一整片领域，它是「从极限到大模型」主线里连接「会写程序」与「大模型时代」的那座桥。<span class="marginnote">本专题在课程里属于第四级。它依赖第三级《机器学习》《深度学习》的 Transformer 基础，也为第五级《大模型》提供「模型如何作用于真实工程」的样板——学完这一级，你手里就多了一把「把大模型变成工程师」的钥匙。</span>

为什么要在第一课先看「全景」？因为代码智能不是一两个模型，而是**一整套任务谱系**——生成、理解、检索、修复、审查、测试，各有各的数据、模型与评测。不先在地图上找到自己的位置，后面每一篇都会「只见树木不见森林」。这一篇我们做三件事：把任务谱系画出来，把评测格局讲清楚，把本专题 12 篇的路线图摊开——然后从第 2 篇起，一篇一篇把每个格子填满。

一个学习姿态上的建议：本专题的对标教材是 2024 年的两份综述与 Codex 论文——它们不是「教科书」，而是「地图」与「路标」。读代码智能文献时，先看它属于哪个家族、用的是哪代评测，再看具体数字；不要被论文标题里的「最强」「SOTA」带偏，先对着谱系图对号入座。

## 1 代码智能的任务谱系：写、读、查、修

把代码智能的全部任务放进一张谱系图，可以归成**四个家族**。区分它们的依据是「模型对代码做了什么」：

**写（生成，generation）。** 模型产出新代码：给定注释生成函数、给定光标前后文补全、把 Python 翻译成 Go、根据需求生成单元测试。这是「生成式代码智能」的主战场，也是 Codex、Code LLaMA、DeepSeek-Coder 这批模型的看家本领。判断生成好不好，最后要靠「跑不跑得对」——这引出了执行式评测（第 5 篇）。

**读（理解，understanding / representation）。** 模型把代码变成「含义」：给一段函数写自然语言摘要、根据自然语言问题检索代码片段、判断代码的分类或话题。理解家族的核心问题只有一个——**怎么把代码编码成一个有意义的向量**（第 2 篇的 CodeBERT 与 GraphCodeBERT），它是一切其他任务的地基。

**查（检索，retrieval）。** 在代码库里找「与当前需求最相关的片段」。它不是独立于生成的任务，而是生成的「弹药供给」：仓库级补全、Agent 定位文件，都要靠检索（第 7 篇专门展开）。

**修（修复与质检，repair & quality）。** 模型审视已有代码：测试生成、缺陷检测、自动修复、代码审查、安全审计。这一族把「敢写」升级成「敢保证对」——质量层（第 8、9 篇）。

四个家族之外，还有一个**横切家族**——**Agent 化编程**（第 10 篇）：让模型自己把「读 → 查 → 修 → 测」串成一个多步闭环。它不生产某一种代码能力，而是把上面四种能力编排起来，像一位工程师一样干活。<span class="marginnote">2024 年的两篇权威综述为这张谱系画了边界：Ziyin Zhang 等人的综述统计了 70+ 模型、40+ 评测任务与 180+ 数据集；另一篇 Quanjun Zhang 等人的综述则把 LLM 的 SE 研究归纳为 62 个代码模型、15 类预训练目标与 16 类下游任务。我们这里的「写读查修」四家族，是对它们分类的通俗化。</span>

把这四张图记在心里，本专题的每篇文章都是往这四张图上填一个格子：第 2 篇填「读」的地基，第 3 篇填「写」的引擎，第 4 篇把「写」装进 IDE，第 5 篇给「写」配尺子，第 6、7 篇把「读与查」升级到仓库级，第 8、9 篇填「修」，第 10、11 篇把一切编排成 Agent 与真实工程，第 12 篇讨论落地时的法律与安全。

谱系不是静止的：2021 年的代码智能以「读与写」为主，2023 年开源模型把它推向「写」的规模化，2024 年 Agent 与 SWE-bench 又把重心推向「修」与「编排」。每过一两年，谱系的重心就向右移动一格——读懂了重心在哪，就读懂了当下这波进展在历史里的位置。

## 2 评测格局：从「像不像」到「能不能用」

代码智能的评测走过**三代**，每一代都在回答「什么样的模型算好」这个问题上更进一层。

**第一代：文本相似度（text similarity）。** 用 BLEU、Rouge 这类「翻译」指标，把模型输出与参考答案比较，看「像不像」。它在 2019–2021 年的代码生成早期评测里很常见。问题是**代码不像文本**：两段语义完全相同的代码可以长得完全不同（`x = x + 1` 与 `x += 1`），而一字不差的两段代码可以天差地别（`==` 与 `=`）。「像不像」测不出「对不对」。

**第二代：执行式评测（execution-based）。** 让模型生成代码，**真的跑测试**，通过才算对。HumanEval（164 题）与 MBPP（974 题）是这个时代的代表，指标是 `pass@k`（第 5 篇详讲）。它把「像不像」彻底换成「能不能用」，是代码智能的分水岭——从此，模型的分数靠「行为」说话，不靠「文本」说话。

**第三代：任务式评测（task-based）。** 不再给「写一个函数」的干净题面，而是给**真实工程的完整任务**：SWE-bench 从 12 个真实 Python 仓库挖出 2294 个真实 GitHub issue，模型要自己定位、修改、过测试（第 11 篇）。评测对象从「函数」变成「仓库里的一个 issue」，模型从「会写」变成「会干活」。<span class="marginnote">三代的演进不是「旧的无用」而是「能力够格才用更难的」：第一代还在用，是因为它快且可解释，适合做开发期的粗筛；第二代是主流报告的基线；第三代是 2024 年以来的 Agent 竞赛场。读论文时先问一句「这是什么代的评测」，再读分数才不会被误导。</span>

评测还有一个贯穿始终的敌人——**污染（contamination）**：评测题若混进训练语料，模型就是「背题」而非「做题」。所以负责任的数据管线都会显式剔除评测基准的重复片段（DeepSeek-Coder 就是这么做的），HumanEval 则靠「人工新写」来规避。**分数可信的前提，是评测与训练的数据隔离**——这句话本专题会反复出现。

评测与产品之间还隔着一层：**基准分数是「能力下限」，产品指标是「真实价值」**。模型在 HumanEval 上 pass@1 达到 90%，不代表 IDE 补全接受率就有 90%——后者还受延迟、建议长度、触发策略的影响（第 4 篇详讲）。读论文分数时记住这个落差，就不会被「刷新 SOTA」的标题误导。

## 3 核心对比表：代码智能的四大家族

（纯概念主题，用核心对比表替代公式解析。）

| 家族 | 模型对代码做什么 | 代表任务 | 代表模型/方法 | 代表数据集 | 篇章 |
| --- | --- | --- | --- | --- | --- |
| 写（生成） | 产出新代码 | 补全、代码翻译、测试生成 | Codex、Code LLaMA、DeepSeek-Coder | HumanEval、MBPP | 第 3–5 篇 |
| 读（理解） | 把代码变成含义 | 摘要、检索、分类 | CodeBERT、GraphCodeBERT | CodeSearchNet、CodeXGLUE | 第 2 篇 |
| 查（检索） | 找相关片段 | 语义检索、仓库检索 | BM25、稠密检索、RepoCoder | CodeSearchNet | 第 7 篇 |
| 修（修复质检） | 审视与修补 | 缺陷检测、修复、审查、审计 | CodeReviewer、APR 系统 | Devign、Big-Vul | 第 8–9 篇 |
| 横切（Agent） | 编排四族能力 | 仓库 issue 修复 | SWE-agent、ReAct | SWE-bench | 第 10–11 篇 |

读这张表要抓住一个规律：**横着看，四个家族层层递进——先会读，才会写；会写了，才知道怎么查；能查能写了，才谈得上修；四者齐了，才能当 Agent**。本专题的篇章顺序正是照着这条递进链排的：地基（读）→ 引擎（写）→ 工具（IDE）→ 尺子（评测）→ 放大（仓库与检索）→ 质检（修）→ 编排（Agent）→ 落地（法律与安全）。

这张表也是你未来检索知识的索引：当你在真实工程里遇到「模型不听话」的问题，先对号入座——是「读」没读懂（表示学习）、「查」没查到（检索）、还是「修」没修对（质量层）？定位家族，就找到了对应的章节与方法。

## 4 数据集地图：训练与评测的弹药库

代码智能的每个任务都有对应的高频数据集，先在地图上认个脸：

- **CodeSearchNet**：约 200 万个「代码-文档」对，覆盖 Python、JavaScript、Go、Ruby、Java 等语言，是代码检索训练的标准语料，CodeBERT 用它训练检索器。
- **CodeXGLUE**：微软整理的 13 项任务的合集（代码补全、翻译、摘要、缺陷检测……），把「一个任务一个数据集」的散乱局面收拢成了统一测试场。
- **HumanEval / MBPP**：执行式评测的起点，前者 164 道手写难题，后者 974 道基础题，合起来是「一难一多」的能力画像。
- **SWE-bench**：2294 个真实 GitHub issue + 人类修复补丁，2024 年以来的任务式评测标准。
- **Devign / Big-Vul**：C/C++ 漏洞函数数据集，缺陷检测与安全审计的主战场（第 9 篇）。
- **LongCode / RepoBench / CrossCodeEval**：长代码、跨文件评测，面向第 6 篇的仓库级理解。
- 第一代评测也没完全退役：CodeXGLUE 之外，**CodeBLEU** 等指标仍用于「译文质量」类任务与开发期粗筛。

这些数据集各有个性：有的重在「广」（CodeSearchNet 的量）、有的重在「真」（SWE-bench 的实）、有的重在「严」（Big-Vul 的对抗性）。**选数据集要看任务，更要看评测的代际**——拿一代的尺子量三代的模型，结论必然失真。

使用数据集地图有一条纪律：**训练数据与评测数据必须隔离**。CodeSearchNet 既能训练检索器，也常被当作评测集——两者混用就是污染。负责任的做法是：训练只用训练划分，评测只用官方评测划分，并在论文里写明版本号与划分方式。<span class="marginnote">数据集的「生命周期」也值得记一笔：HumanEval 在头部模型 pass@1 突破 90% 后趋于饱和，社区于是造出 HumanEval+（补更严的边界测试）与 LiveCodeBench（周期性更新新题防污染）。评测基准不是墓碑，而是不断换代的活动靶。</span>

## 5 代码智能的三道难关

第一关：**结构。** 代码的语义由结构承载，而 Transformer 天然只看线性文本。第 2 篇的 CodeBERT 用双模态、GraphCodeBERT 用数据流图，都是在补「结构」这一课——而仓库级结构（第 6 篇）至今仍是开放问题。

第二关：**真实。** HumanEval 的函数题与真实 issue 之间隔着「上下文、长尾、多文件」三座山。SWE-bench 把评测推到真实仓库，但解决率刚过三成——「会写」与「会干活」之间的鸿沟，是整个领域 2026 年最核心的未解之谜。

第三关：**可信。** 模型生成的代码可能正确也可能错误，甚至带着安全漏洞。测试生成（第 8 篇）、缺陷检测与安全审计（第 9 篇）、许可证与安全治理（第 12 篇），都在回答同一个问题——「AI 写的代码，我们能放心用吗？」。

这三道难关对应着本专题三条技术主线：**结构（表示学习）→ 真实（仓库与评测）→ 可信（质量与治理）**。后面 11 篇的每一篇，都是在为这三道难关里的一道添砖加瓦。

## 7 小结

- 代码智能的任务谱系可以归为**写、读、查、修**四个家族，外加一个**横切的 Agent 家族**；本专题 12 篇按「读→写→查→修→编排→落地」的递进链排列。
- 评测走过三代：**文本相似度 → 执行式（HumanEval/MBPP + pass@k）→ 任务式（SWE-bench）**；「能不能用」压倒了「像不像」。
- **污染**是评测的头号敌人，评测与训练的数据隔离是不可动摇的底线。
- 核心数据集地图：CodeSearchNet（检索语料）、CodeXGLUE（任务合集）、HumanEval/MBPP（执行式）、SWE-bench（任务式）、Devign/Big-Vul（安全）。
- 代码智能是「从极限到大模型」主线里连接**编程**与**大模型**的桥：它以 Transformer 为底座，以真实工程为出口。
- 本专题的对标教材是 2024 年的两份综述与 Codex 论文：它们是「地图与路标」而非「教科书」，阅读时先对谱系、再对代际，最后才读数字。

在下一节，我们将回答谱系里「读」家族的地基问题：**怎么把代码编码成一个有意义的向量**——这就是《代码的表示学习：CodeBERT 与 GraphCodeBERT》。
