## 为什么从 IDE 集成讲起

第 3 篇造出了「会写代码」的引擎（Codex、Code LLaMA、DeepSeek-Coder），但引擎放进跑车，才算有了产品。**IDE 集成的工程实践**，就是代码生成大模型从「论文里的分数」变成「工程师每天点几万次的幽灵文本」的那一步。GitHub Copilot 在 2021 年 6 月以技术预览发布，是第一个把「代码补全」做成主流产品的系统——它背后的工程问题，比「训练一个模型」复杂得多：补全必须**快**（几百毫秒内响应）、**省**（每天数十亿次请求）、**懂上下文**（只看光标附近是不够的）、还要**知道什么时候闭嘴**（别在无关场景乱补）。

这一篇我们抛开「模型有多强」，只问一个纯工程问题：**把一个会补全的模型装进 IDE，需要解决哪些问题？**它是本专题里最「产品化」的一篇——第 3 篇的模型、第 5 篇的评测指标、第 7 篇的检索，都在这一篇的工程拼图里汇合。

为什么把这一篇放在评测（第 5 篇）之前？因为 IDE 集成是「模型能力」与「评测指标」之间的真实战场——没有编辑器这个载体，HumanEval 的分数只是纸面成绩；而工程师在编辑器里的每一次按 Tab，都在给第 5 篇的评测补充「产品视角」的判据。先懂产品，再懂指标，顺序不能反。<span class="marginnote">IDE 补全与「论文里的生成」有三个本质差别：<strong>延迟敏感</strong>（论文可以等，工程师不能等）、<strong>上下文由编辑器实时决定</strong>（不是给定的固定题面）、<strong>有即时反馈</strong>（工程师按不按 Tab，就是最好的标注数据）。这三条决定了 IDE 补全自成一套工程方法论。</span>

## 1 补全的用户时刻：光标、幽灵文本与接受率

IDE 补全的「用户时刻」非常具体：程序员在某处敲了几行代码，光标停住，模型基于「光标之前与之后的内容」推测「他想写什么」，在光标处浮现一段**幽灵文本（ghost text / inline suggestion）**。工程师满意就按 Tab 接受，不满意就继续打字，模型再给出新的建议。

这个交互定义了 IDE 补全的**核心指标——接受率（acceptance rate）**：被接受的建议数 ÷ 建议总数。它直接反映「建议对工程师有没有用」，也是补全系统自我迭代的信号：接受的建议是正样本，跳过的建议是负样本，两者都可以回流成训练或排序数据。<span class="marginnote">接受率不是「模型越强就越高」：<strong>什么时候弹建议、弹多长、弹几条</strong>，都直接影响接受率。给一条 100 行的巨型建议，八成会因「太长不靠谱」被跳过；在注释里或配置里乱弹，则会被直接关掉。工程上「建议策略」与「模型能力」各占一半。</span>

补全的触发（trigger）策略也值得单说：是「每次停顿就弹」，还是「只有检测到特定上下文才弹」？太激进会烦人，太保守会漏掉时机。成熟的系统普遍采用**多级触发**——行首、函数签名后、括号内等位置优先，再配合延迟调优。这个「何时出手」的决策，往往是产品口碑的分水岭。

还有一层：**多候选（multi-candidate）**。一次返回 top-k 个建议（如 Copilot 允许循环查看最多 10 个候选），让工程师「不满意就翻下一个」。多候选的本质是第 5 篇 `pass@k` 思想的产品化——单个建议不对，候选池里也许藏着对的。但候选也要排序展示，于是引入了「轻量排序模型」对 top-k 再排一次（下文第 4 节会算它的延迟账）。

**建议长度与分段。** 建议太长容易被整段跳过，太短又没有价值。成熟系统按「光标上下文」动态调长度：函数刚开头给「骨架」，函数内部给「一行」。还有「分段滚动」式建议——把长建议切成几段，工程师先接受第一段，系统再续出后续段，兼顾「长度」与「可接受」。

## 2 上下文装配：把编辑器塞进模型

IDE 补全与论文评测最大的差别在**上下文**：评测时题面固定（签名 + 文档字符串），IDE 里模型要自己判断「该看哪些代码」。而现实是——**能快速推理的模型，上下文窗口都有限**（Copilot 早期为延迟优先选用的模型，上下文大约只有几千字符的量级）。编辑器里有成百上千行代码、几十个打开的文件，全塞进去既不现实也没必要。

于是有了**上下文装配（context assembly）**这一整块工程：把「编辑器状态」压缩成「给模型的提示词」。GitHub 公布的实践包括三个关键手段：

**FIM 拼装（fill-in-the-middle）。** 光标不是永远在文本末尾——真实场景里光标常常在**中间**，前后都有代码。早期 Copilot 只把「光标之前的代码」当上下文，效果有限；引入 FIM 后把「前缀 + 后缀」一起喂给模型，建议接受率**相对提升约 10%**。FIM 的具体机制在第 3 篇讲过训练侧，这里强调的是**推理侧**：模型见到的不是「从头续写」，而是「补中间」，提示词按「前缀 + 后缀」拼装，模型用特殊的 FIM token 识别任务。

**相邻标签页（neighboring tabs）。** 只给当前文件还不够——正在调的函数可能定义在另一个打开的文件里。把 IDE 里所有打开的标签页纳入候选上下文，进一步带来约 **5% 的相对接受率提升**。这也印证了第 6 篇的主题：代码的依赖是跨文件的，补全亦然。

**压缩与优先级。** 编辑器状态动辄几 MB，但模型提示词只有几千 token。工程做法是用 Tree-sitter 解析 AST，只保留**与光标最相关**的片段——当前函数体、当前签名、import 行、就近的相似代码——并按「越相关越靠前」排序，最早的片段最先被截断。GitHub 的报告显示这类压缩能把提示词缩小约 80%，而语义几乎无损。<span class="marginnote">上下文装配有一条反直觉的经验：<strong>一个不太相关的片段，也比完全没有片段好</strong>——模型看到「这个文件在用某库的某种写法」，就能校准自己的输出风格。宁可多给，不要少给，是装配的默认策略。</span>

「该给什么」之后是「怎么给」：提示词的结构顺序（系统指令、当前文件、相关文件、光标标记）本身影响质量。GitHub 把这一整套称为「提示词库」（prompt library）——针对不同语言、不同场景维护不同的装配模板，实时组合。**IDE 补全的提示工程，是独立于模型训练的、每天都在打磨的活手艺**。

装配还有一层**排序**：不是「把相关文件都塞进去」就完事——提示词里代码出现的顺序、与光标的距离，都影响模型对「当前意图」的判断。实践上通常按「当前文件 > 相邻标签页 > 最近打开的文件 > 仓库检索命中」的优先级装配，最相关的放最前。

## 3 公式解析：FIM 的训练目标

FIM 在 IDE 补全里如此重要，值得把它的目标函数看透。设一段代码被切成三段：前缀 $P$、中间段 $M$、后缀 $S$。普通因果语言建模按原顺序 $P, M, S$ 训练；FIM 把它重排成「前缀 + 后缀 + 中间段」，中间段被移到序列末尾，训练目标仍是最大化「在已见前缀下预测下一 token」的对数概率：

$$
\mathcal{L}_{\text{FIM}} = -\sum_{t=1}^{T} \log p_\theta(x_t \mid x_{<t}^{\text{FIM}}), \qquad x^{\text{FIM}} = [P,\ \text{\texttt{<fim>}},\ S,\ \text{\texttt{<end>}},\ M]
$$

对这条公式做四步拆解：

- **第一步，看懂序列 $x^{\text{FIM}}$**：模型看到的顺序是「前缀 $P$ → 特殊标记 `<fim>` → 后缀 $S$ → 结束标记 `<end>` → 中间段 $M$」。推理时模型读到 `<fim>` 就知道「该补中间了」，读到 `<end>` 就知道「补完了」。
- **第二步，看懂目标没变**：$\mathcal{L}_{\text{FIM}}$ 与第 3 篇的因果语言模型目标**形式完全一样**——仍是「预测下一个 token」。变的只是**数据顺序**：FIM 把「补中间」这个 IDE 里的高频场景，改写成模型最熟悉的「从左往右续写」。这就是为什么 FIM 不需要改架构、不需要改损失，只需改数据拼装。
- **第三步，看懂为什么有效**：对后缀 $S$ 的建模让模型学会「根据后面要发生什么来生成中间」——而真实补全正是「既看前文又看后文」的双向推断。FIM 让模型在自回归框架里**近似获得双向信息**，这是它比纯前缀补全强 10% 接受率的机制原因。
- **第四步，看懂比例是超参数**：FIM 不是越多越好——训练数据里 FIM 样本占比过高会削弱「按自然顺序生成长代码」的能力。DeepSeek-Coder 等模型把 FIM 比例控制在约三成，其余保留普通续写。**FIM 是一种数据增广，配比是调参的核心旋钮**。

## 4 延迟预算：补全必须「感觉不到等」

IDE 补全的第二个硬约束是**延迟**。工程师的手指不会为补全等待——行业经验是**端到端延迟须在约 200 毫秒以内**：超过 400 毫秒，开发者会感觉「卡」并逐渐禁用补全；低于 80 毫秒但建议质量差，同样失去信任。延迟与质量是「短跑运动员」式的双重约束——**模型必须在「快到感觉不到」的同时「对到能接受」**。

延迟从哪来？拆开一次补全请求：**上下文装配**（把编辑器状态压缩成提示词，约 25–40 毫秒）、**模型推理**（生成首个 token，视模型大小与量化配置而定）、**多候选排序**（对 top-k 跑一次轻量排序模型）、**网络传输**（若走云端）。其中模型推理占比最大，于是工程上用三招压缩它：

**模型级联（cascade）。** 用一个小模型（1B–7B 量级）覆盖绝大多数请求，只在需要高质量或高置信时调用大模型。实践中约九成的请求可以交给小模型，大小模型的分工把成本与延迟同时降下来。<span class="marginnote">模型级联的哲学是「<strong>把算力花在刀刃上</strong>」：小模型负责快，大模型负责难。这与第 7 篇检索系统里「粗召回 + 重排序」的分层思路同构——系统设计里，分层几乎总是优于「一个全能模型干到底」。</span>

**缓存（caching）。** 连续按键时，相邻两次请求的上下文高度重合。精确匹配缓存命中率约四成，前缀-后缀缓存（配合 Bloom 过滤器）可达六成以上，语义缓存（对上下文前缀做嵌入）则把命中率推到八成——缓存是「补全系统里最大的一块延迟杠杆」，把常用的文件级上下文预计算好，一次请求可省 60–90 毫秒。

**KV 缓存与流式输出。** 首 token 出来后，后续 token 逐个流式吐回编辑器——工程师看到第一个字符就开始评估，感知延迟远小于总生成时间。配合前缀缓存（复用相同上下文的键值缓存），重复请求的推理成本大幅下降。

延迟还与**部署形态**绑定：云端部署（Copilot）把算力外包给数据中心，隐私与离线是短板；本地部署（第 3 篇的量化模型 + vLLM）让补全完全离线，隐私场景受益，但受限于消费级 GPU。**云与本地不是二选一，而是按隐私预算与延迟预算分别部署**——这为第 12 篇的许可证与安全风险埋下了伏笔。

延迟的另一个维度是**场景分层**：不是所有请求都发生在「用户正在打字」的瞬间。批量离线场景（整文件补全、测试生成）可以容忍秒级延迟，用更大的模型、更多的候选；只有「按键即补全」的交互场景才必须 200 毫秒内。**把延迟预算按场景分层，能显著提升算力的使用效率**。

## 5 质量闭环：从接受到迭代

IDE 补全的第三个工程特征是**反馈闭环**：接受率是实时、海量、免费的标注信号。每一次「按 Tab / 跳过」都在告诉系统「这条建议好不好」，由此形成一个持续的迭代环：

**第一环：排序层迭代。** 多候选的排序模型直接以「接受/跳过」为训练信号，持续优化「把最可能的建议排在前面」。这比重新训练生成模型便宜得多，收益却立竿见影。

**第二环：触发策略迭代。** 分析「哪些场景建议被接受、哪些被跳过」，调整弹建议的时机与长度。跳过高发场景（注释、字符串、模板）主动减少打扰。

**第三环：生成模型迭代。** 把大量「被接受的补全」回流为监督微调数据（注意：需清洗与去重，避免教坏模型），周期性升级生成模型。

这三环合起来构成 IDE 补全的**「数据飞轮」**：产品用得越多，数据越多，数据越多，模型越好，模型越好，产品越多人用。<span class="marginnote">数据飞轮是 IDE 类产品的护城河，也带来一个隐蔽问题：<strong>选择偏差</strong>——飞轮里的数据是「工程师接受了的建议」，而工程师往往只接受「不太长、看起来安全」的建议，这会让模型越来越「保守」。对抗选择偏差，是飞轮模式长期运行的必修课。</span>

评测 IDE 补全的质量，不能只看论文里的 `pass@k`：补全场景还强调**线上指标**（接受率、每个建议节省的按键数）与**离线可复现的代理指标**（在真实编辑会话里回放历史，看模型能否补出工程师真正打出的下一段）。第 5 篇的 `pass@k` 测的是「能力上限」，接受率测的是「产品价值」——两者是「这个模型能多强」与「这个工具多好用」的区别。

## 6 补全之外的形态：内联、聊天与 Agent

「光标处弹幽灵文本」只是代码智能进 IDE 的第一形态。2024 年之后，IDE 集成迅速扩展到三个新形态：

**内联重构与编辑（inline edit）。** 不是「补完一句话」，而是「选中一段代码，让模型改」：把选中区域当作 FIM 的中间段，模型输出改写后的整段。`Cmd/Ctrl+K` 式的内联编辑成了 Copilot、Cursor 的标配。

**侧边聊天（chat）。** 把「会话」带进 IDE：模型能「看到」当前文件、选中区域、甚至整个工作区，回答「这个函数哪里超时了」这类问题。聊天把补全的「单点建议」升级为「持续对话」，也把第 7 篇的检索、第 9 篇的缺陷检测接进了交互层。

**Agent 模式（agent）。** 让模型自己「读文件 → 改代码 → 跑测试」多步循环，直到完成一个任务——这正是第 10 篇的 Agent 化编程在产品里的落地。Cursor 的 Agent 模式、Copilot 的 Workspace 功能，都是「把 SWE-agent 装进 IDE」的尝试。

三个形态的技术底座是同一个：**上下文装配 + FIM + 反馈循环**。内联编辑复用 FIM，聊天复用检索与长上下文，Agent 复用工具与验证。**IDE 集成的演进，就是代码智能能力层在产品层的逐层释放**——第 10 篇的 Agent 在本篇已经显出了原型。

## 7 小结

- IDE 补全的「用户时刻」是**幽灵文本 + 按 Tab**；核心指标是**接受率**，它同时是产品信号与训练数据。
- **上下文装配**是 IDE 补全的第一门手艺：FIM 拼装（+约 10% 接受率）、相邻标签页（+约 5%）、AST 压缩（提示词缩小约 80%）。
- **FIM 的训练目标**与普通因果 LM 同构，只是把数据重排成「前缀 + 后缀 + 中间」，让模型在自回归框架里近似获得双向信息；FIM 比例是调参旋钮。
- 补全的硬约束是**延迟**（端到端约 200 毫秒内）：靠**模型级联、多级缓存、KV 缓存与流式输出**压出来。
- IDE 补全靠**接受率数据飞轮**持续迭代：排序层、触发策略、生成模型三层闭环。
- 评测补全产品要把**离线 `pass@k` 能力**与**线上接受率价值**分开看，两者互为补充。
- 上下文装配的排序原则：「当前文件 > 相邻标签页 > 最近文件 > 检索命中」，最相关的放最前。
- IDE 集成从补全扩展到内联编辑、侧边聊天与 Agent 模式，技术底座仍是上下文装配 + FIM + 反馈。

在下一节，我们将给「补全能有多强」配一把精确的尺子：**评测基准：HumanEval、MBPP 与 pass@k 估计**——IDE 里每个接受率的背后，都站着这些基准定义的「一次说对」能力。
