## 为什么从 AI Core 微架构开始

上一节俯瞰了整颗 τ 芯片的 SoC，现在我们要俯冲到底，钻进**一个 AI Core** 的内部。这是整个架构的「原子核」：所有的大算力、高带宽、好能效，最终都要在最小尺度上兑现。AI Core 微架构的核心是三单元分工——**Cube、Vector、Scalar**——它们的名字在前文反复出现，本节把它们彻底讲透：各自长什么样、各自吃什么数据、三者如何配合。

<span class="marginnote">读本节时请带着一个对比：通用 CPU 用「一条指令处理一组数据」（SIMD）来加速；τ 的 AI Core 把这种思想推到极致——<strong>Cube 用一条指令处理一个矩阵</strong>。专用化的每一步，都以「只服务特定形状的数据」为代价，换取数量级的能效。</span>

## 1 Cube：矩阵单元的脉动式数据复用

**Cube 单元（矩阵单元）**：AI Core 中专司矩阵乘累加的执行单元，是 τ 算力密度的来源。

Cube 的物理结构是一张**脉动阵列（Systolic Array）**：大量乘累加单元（MAC，Multiply-Accumulate）按网格排布，每个 MAC 只与相邻单元通信。数据像波浪一样「脉动」着流过阵列——**一次读入的数据，在阵列里被沿途的每个 MAC 复用**。这正是矩阵乘的精髓：

设我们要算 $C = A \times B$，$A$ 是 $M \times K$ 矩阵，$B$ 是 $K \times N$ 矩阵。传统方法把 $A$ 的每行、$B$ 的每列各读一遍；脉动阵列则让 $A$ 的一行与 $B$ 的一列同时「流」过阵列，中间结果被阵列内每个 MAC 依次累加——**数据从内存读一次，却在片内被用了 K 次甚至更多**。这就是「数据复用」的物理实现。

<div class="marginnote">脉动阵列的灵感来自 1980 年代孔祥重（H. T. Kung）等人的经典研究。它之所以在 AI 时代复兴，正是因为矩阵乘的每个输出元 $C[i][j] = \sum_k A[i][k]B[k][j]$ 天然是「累加链」——<strong>把累加链放进硬件，就省掉了反复搬运中间结果的开销</strong>。</div>

τ 的 Cube 在传统脉动阵列之上做了两点强化：

**可组合分块**：大矩阵切成小分块，依次送入阵列；分块大小可调，让不同形状的算子都能把阵列「填满」，避免细长矩阵造成阵列利用率滑坡。
**精度可配**：Cube 内的 MAC 支持 FP16 / BF16 / INT8 等不同精度，精度越低，单位时间完成的运算越多（详见第 8 篇低精度计算）。

## 2 Vector：激活与逐元素运算

**Vector 单元（向量单元）**：AI Core 中执行逐元素运算的执行单元，处理激活函数、归一化、逐元素加减乘除等「非矩阵」运算。

为什么矩阵单元之外还需要向量单元？因为神经网络的算子不全是矩阵乘：ReLU、GELU、LayerNorm、Softmax、逐元素乘（attention 里的 scale）等，都是对张量的逐元素或归约操作。这些操作若也塞进矩阵阵列，会浪费宝贵的 MAC 资源；单独设立向量单元，让它们用「一条指令处理一个向量」的方式并行执行。

Vector 单元与 Cube 的配合有一个**吞吐匹配**的要求：矩阵乘的输出要经过激活、归一化才能进入下一层，如果向量单元太慢，流水线就会在这里卡住。τ 的设计让向量单元的吞吐与 Cube 的输出速率对齐，使「矩阵算完 → 向量接着处理」能够无缝衔接。

<div class="marginnote">可以把 Cube 比作「炼钢炉」（大量产出矩阵结果），把 Vector 比作「精加工车间」（对结果逐项处理）。炼钢炉再快，精加工跟不上，整个工厂的产出也被卡住——<strong>架构里最贵的不是最快的单元，而是最平衡的流水线</strong>。</div>

## 3 Scalar：指令与地址的指挥官

**Scalar 单元（标量单元）**：AI Core 中执行标量运算的控制型单元，负责地址计算、循环计数、分支跳转与指令解码，是 Cube 与 Vector 的「指挥官」。

一个 AI Core 要持续工作，需要不断回答三个问题：**下一步做什么指令？数据在哪里？循环到第几轮了？** Scalar 单元就是回答这三个问题的角色：

- **指令解码**：从指令流中取出一条条指令，解码后分发给 Cube 或 Vector。
- **地址计算**：根据循环变量计算数据在 L0/L1 中的地址，为数据搬运生成访问序列。
- **循环与分支控制**：管理嵌套循环的计数与退出，处理条件分支（如动态 Shape 时的填充逻辑）。

在通用 CPU 里，标量逻辑无处不在；在 AI Core 里，Scalar 被刻意「做小」——它不需要做复杂的乱序执行与分支预测，只需要规律、可预期地编排大规模并行计算。**牺牲单个任务的智能，换取整体吞吐的稳定**，这正是专用架构与通用架构的分野。

**辨析｜易错点：** 三单元的名字容易让人误以为「三者平等、各管一摊」，其实它们的地位完全不对称——**Cube 是主角，Vector 是配角，Scalar 是导演**。设计的重心永远是让 Cube 吃饱，Vector 与 Scalar 的存在是为了「不让 Cube 停下来」。另一个易错点是拿「标量单元」与 CPU 核心类比：Scalar 不做操作系统调度、不跑通用程序，它只服务「固定的算子编排」；试图把通用控制逻辑塞进 Scalar，反而会拖慢整个数据流。**把 Scalar 想成「专用控制器」，而不是「通用 CPU 的缩小版」**，才能正确理解它的职责边界。

<span class="marginnote">一个关键设计取向：AI 芯片的 Scalar 与 CPU 的标量核不同，它面向的是「<strong>规则的数据流</strong>」——循环都是规则嵌套、地址都是可预测的等差序列。因此它无需分支预测器、无需重排序缓冲，把面积省下来给了 Cube。</span>

## 4 三单元如何协同：一条算子的执行流水

把三个单元放在一起，看一条典型算子在 AI Core 里如何走完全程。以「线性层 + GELU 激活」为例：

- **第一阶段（Scalar 编排）**：Scalar 单元解析指令，算出循环边界与数据地址，生成数据搬运请求。
- **第二阶段（数据进 L0）**：A 与 B 的分块经 L1/NoC 搬运进 L0 缓冲，等待 Cube 取用。
- **第三阶段（Cube 计算）**：Cube 用脉动阵列完成 $C = A \times B$，结果写入统一缓冲区。
- **第四阶段（Vector 处理）**：Vector 从统一缓冲区读 $C$，逐元素施加 GELU，得到激活输出。
- **第五阶段（写回）**：结果经统一缓冲区写回 L1/HBM，进入下一算子的输入。

整条流水线与冯·诺依曼的「取指—执行」范式一脉相承，但每一步都被专门化：地址由 Scalar 算、矩阵由 Cube 算、激活由 Vector 算、数据停靠在专属缓冲区。**每个单元只做一件事，但把这件事做到极致。**

这条流水线最值得玩味的地方，是「搬运」几乎出现在每个阶段之间：数据要从 L1 进 L0、结果要在统一缓冲区与 Vector 之间交接、最终要写回 HBM。**AI Core 里真正「干活」的时间往往只占一小半，剩下时间都在搬数据**——这正是为什么数据复用与搬运编排（第 13 篇）比计算本身更值得优化。看一个 AI Core 的性能，先看它的数据通路堵不堵，而不是只看 Cube 有多快。

不同算子在这条流水线上的「瓶颈阶段」各不相同，识别瓶颈是调优的第一课：

- **矩阵乘类算子**：Cube 计算阶段占大头，搬运是配角——算力受限。
- **激活类算子**：Vector 计算与数据搬运并重——带宽与算力双重受限。
- **逐元素类算子**：搬运占绝对大头，计算几乎瞬时——强带宽受限。
- **归约类算子（Softmax、LayerNorm）**：先沿序列归约、再广播，跨行数据依赖多——延迟敏感。
- **动态形状算子**：Scalar 的循环与分支成为额外开销——控制受限。

识别了瓶颈在哪一阶段，优化手段就清楚了：算力受限就调分块、带宽受限就加复用、延迟敏感就减同步点。

<div class="marginnote">这条五阶段流水是后面所有性能讨论的「底盘」。第 7 篇会把它放大看矩阵乘的微观数据流；第 10 篇会讨论如何用指令控制这条流水；第 16 篇会讨论编译器如何把这五步融合成更少的指令。</div>

## 5 公式解析：矩阵乘要花多少 FLOPs

理解 Cube 的威力，先理解矩阵乘的运算量。设 $C = A \times B$，其中 $A \in \mathbb{R}^{M \times K}$、$B \in \mathbb{R}^{K \times N}$、$C \in \mathbb{R}^{M \times N}$，则总浮点运算次数为：

$$
\text{FLOPs} = 2 \cdot M \cdot N \cdot K
$$

三步拆解这条公式：

- **第一步，看单个输出元**：每个输出元 $C[i][j]$ 需要 $K$ 次乘加，即 $K$ 次乘法 + $K$ 次加法 = $2K$ 次浮点运算。
- **第二步，看输出矩阵规模**：输出矩阵有 $M \times N$ 个元素，每个元素 $2K$ 次运算，合计 $2MNK$。
- **第三步，理解 Cube 的意义**：这 $2MNK$ 次运算在脉动阵列里几乎**同时发生**（阵列并行），而数据只需读一次。所以 Cube 的每秒吞吐 = 阵列单元数 × 主频，远高于「逐元素搬运」所能支撑的速度。

再算一个具体的 FLOPs 例子，把抽象的数落到实感：对 LLaMA 类模型的 FFN 层，常取 $M = 4096$（batch × 序列长度）、$N = 11008$（隐藏维扩展）、$K = 4096$，则 $\text{FLOPs} = 2 \times 4096 \times 11008 \times 4096 \approx 3.7 \times 10^{14}$，即约 370 TFLOPs。一次前向要执行几十个这样的线性层——把各层 FLOPs 累加，就是第 18 篇「$6ND$ 账单」里每一项的来源。**记住这个「一次 FFN ≈ 数百 TFLOPs」的量级感，读任何算力规格表都会更有底气。**

<div class="marginnote">量级感：对一个大模型的 FFN 层，取 $M=N=8192,\ K=8192$，则 $\text{FLOPs} = 2 \times 8192^3 \approx 1.1 \times 10^{12}$，即约 1.1 TFLOPs。这样的矩阵乘在单次前向中要执行几百次——这就是为什么算力永远是「第一支柱」。</div>

## 6 小结

- **Cube（矩阵单元）**用**脉动阵列**实现矩阵乘，数据读一次、复用多次，是算力密度的来源。
- **Vector（向量单元）**处理激活与逐元素运算，吞吐须与 Cube 对齐，避免流水线卡壳。
- **Scalar（标量单元）**负责指令解码、地址计算与循环控制，是 Cube 与 Vector 的指挥官。
- 一条算子的五阶段流水：**编排 → 搬运 → 矩阵 → 向量 → 写回**，每步各司其职。
- 公式：矩阵乘 $\text{FLOPs} = 2MNK$——脉动阵列让这 $2MNK$ 次运算一拍一拍并行完成。
- 瓶颈识别：矩阵乘算力受限、激活带宽受限、逐元素强带宽受限、归约延迟敏感、动态形状控制受限——**先判方向，再调优化**。
- 关键事实：AI Core 里真正「干活」的时间往往只占一小半，剩下时间都在搬数据——数据通路比 Cube 更值得盯。
- 三单元的面积排序：**Cube 占的面积与功耗最大、Vector 次之、Scalar 最小**——面积分配本身就是价值排序的物理化。
- 一句记忆：**Cube 是主角、Vector 是配角、Scalar 是导演**——设计的重心永远是让 Cube 吃饱。
- 与 CPU 的分野：Scalar 不做乱序执行与分支预测，只服务「规则的数据流」，把省下的面积留给 Cube。

把三单元的分工再往「成本」上想一层：Cube 占的面积与功耗最大，Vector 次之，Scalar 最小。**面积分配本身就是价值排序的物理化**——把最多的硅片给最频繁的运算，正是专用架构的朴素逻辑。而「让 Cube 吃饱」这条设计原则，还会在后面每一篇里以不同面目出现：矩阵乘篇讲分块怎么喂饱阵列，低精度篇讲精度怎么让 Cube 翻倍，指令篇讲怎么调度才能让 Cube 不停拍。**AI Core 的三单元，是整个专题的一粒种子。** 在下一节，我们将放大其中最大的一格——矩阵乘与张量运算单元，看 Cube 内部如何让数据流起来。
