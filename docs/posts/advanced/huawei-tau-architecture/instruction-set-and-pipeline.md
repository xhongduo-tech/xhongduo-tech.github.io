## 为什么从指令集开始

前几节讲的缓存、矩阵阵列、精度格式，都是「硬件有什么」。但从「硬件有什么」到「软件能用上什么」，中间隔着一道关键的翻译层——**指令集（ISA）**。编译器生成的指令流，是软件唯一能指挥硬件的方式；指令集设计得好不好，直接决定编译器能不能把硬件的每一分算力榨干。本节讲 τ 的指令分类与流水线，看一台 AI 处理器如何「听懂」上层送来的程序。

<span class="marginnote">把指令集比作「乐高积木的接口规格」：积木再多、再漂亮，没有标准的接口，就拼不出城堡。<strong>指令集就是那套接口规格</strong>——它规定了积木能怎么连接、能组合出哪些结构。</span>

## 1 指令集：硬件与软件的契约

**指令集体系（ISA，Instruction Set Architecture）**：处理器硬件与上层软件之间约定的「接口层」，规定了一条指令能做什么、如何编码、如何访问数据。它屏蔽了电路细节，让软件只需对着 ISA 编程。

τ 的 ISA 与通用 CPU 的 ISA 有本质差异，这个差异值得先立住：

**通用 CPU（如 x86/ARM）**：指令面向「一次处理一个/一组数据」，指令集讲究通用、向后兼容，硬件里有复杂的乱序执行与分支预测来「猜」程序的意图。
**τ 的指令集**：面向「张量运算的确定性流水」，指令集追求**可预期、可融合**。硬件不需要猜，因为程序的意图（矩阵乘、搬运、激活）在指令里写得很清楚；硬件把功夫花在「让指令以最高吞吐执行」上。

<div class="marginnote">一句话对比：通用 CPU 的指令集是「<strong>给聪明硬件的模糊指令</strong>」（硬件自己想办法优化），τ 的指令集是「<strong>给老实硬件的明确指令</strong>」（编译器提前把一切安排好）。前者适合负载不可预测，后者适合大模型的规则计算。</div>

## 2 τ 指令的分类：标量、向量、矩阵、搬运

τ 的指令集按作用对象可分为四大类，每一类对应 AI Core 的一个子系统：

**标量指令（Scalar Instructions）**：由 Scalar 单元执行，负责地址计算、循环控制、比较跳转。它们是「指挥棒」，本身不产生大量计算，但决定后续向量与矩阵指令的执行路径。

**向量指令（Vector Instructions）**：由 Vector 单元执行，一条指令作用于一个向量的所有元素——比如对整段激活做 ReLU、做逐元素乘。向量指令带「长度参数」，允许处理不定长的向量。

**矩阵指令（Matrix Instructions）**：由 Cube 执行，一条指令完成一次矩阵乘累加。这是 τ 指令集中「信息密度最高」的指令——一条矩阵指令背后是 $P^2$ 个 MAC 同时工作若干拍。矩阵指令还编码了**精度**（FP16/BF16/INT8）与**分块形状**，让硬件按需配置阵列。

**数据搬运指令（Data Movement Instructions）**：负责在 L0、L1、L2、HBM 之间搬张量。τ 把搬运显式化为指令，是它与「隐式缓存」架构最大的区别之一——编译器精确控制「什么数据、何时、搬到哪」，消除缓存失效的不可预期性。

四类指令在一条指令流里通常是「你方唱罢我登场」的编排：几条标量指令算地址、一条搬运指令拉数据、一条矩阵指令做乘累加、几条向量指令做激活，再一条搬运指令写回——如此循环往复。**读一条 τ 的指令流，几乎能「看见」数据在片上走的路**：这正是显式数据流架构的独特体验。对比之下，通用 CPU 的指令流只有「算数、跳转、访存」三类，数据走哪条路完全由硬件决定，程序员看不见也管不着。

<span class="marginnote">矩阵指令是 τ 的「大招」，但也是最需要小心的：一条矩阵指令会让 Cube 忙几百拍。若编译器在此刻让 Vector 闲着，就是浪费；反之若数据还没搬到位就发矩阵指令，Cube 只能空等。<strong>指令调度的艺术，就是让四类指令像四重奏一样错开而互补。</strong></span>

## 3 指令流水线与发射

一条指令在 AI Core 里要穿过**取指 → 译码 → 发射 → 执行 → 写回**五个阶段，这就是**指令流水线（pipeline）**。τ 的流水线设计与通用 CPU 有显著不同：

**第一，多单元并行发射。** τ 的核心在一个时钟周期内可以同时发射**多条不同类型**的指令给不同单元——一条矩阵指令给 Cube、一条向量指令给 Vector、一条搬运指令给数据通路，三者互不阻塞。这种「每条指令只管自己单元」的设计，避免了通用 CPU 里为「乱序执行」付出的巨大复杂度。

一条指令在 τ 流水线里走过的五阶段，各自的职责可以逐项看清：

**取指（Fetch）**：从指令缓存取出下一条指令。τ 的指令流是编译器排好的序列，取指几乎不出现「猜错」。
**译码（Decode）**：解析指令的操作码与操作数，确定发给哪个执行单元。
- **发射（Issue）**：把指令分发给对应的执行单元，同时检查依赖（是否要等前一条完成）。
- **执行（Execute）**：Cube/Vector/Scalar 实际执行运算或搬运。
- **写回（Writeback）**：把结果写进目标寄存器或缓冲，触发依赖它的指令继续。

五阶段的每一级都由硬件「老实执行」，复杂度全部前置到编译期——这是 τ 与通用 CPU 流水线的根本分野。

**第二，流水线深度浅而确定。** 通用 CPU 追求高主频而把流水线做得很深（十几级），依赖分支预测填补气泡；τ 的指令基本没有分支（循环由 Scalar 计数），流水线可以做得浅而稳，每条指令的执行时间可预期。

**第三，同步由显式指令管理。** 当一条矩阵指令依赖前一条搬运指令的数据，编译器会显式插入**同步指令（barrier）**，而不是靠硬件乱序执行去「猜」依赖。显式同步的代价是编译器的责任更重，收益是运行时的行为完全确定。

**辨析｜易错点：** 谈到 AI 芯片的流水线，人们常套用通用 CPU 的「深流水线 + 高主频」思路，这是理解 τ 的典型错位。通用 CPU 靠深流水线（十几级）冲主频，用分支预测填气泡；τ 的指令以矩阵/张量指令为主，几乎没有分支，深流水线带来的「分支猜错代价」是纯损失，所以 τ 的流水线浅而宽——**宁可每个周期发射更多不同类型的指令，也不为堆主频把流水线挖深**。另一个易错点是以为「IPC 越高越好」：对 τ 而言，指标的关键不是「每周期执行了多少条指令」，而是「每周期各单元是否都在做有用的事」——空转的指令不计入有效吞吐。

<div class="marginnote">τ 的调度哲学是「<strong>把复杂度从运行时搬到编译时</strong>」：硬件不再做乱序执行、动态调度，只忠实地按序执行；一切调度的智慧（指令怎么排、数据怎么搬）都前置到编译器。这意味着同一个模型，编译器越好，硬件利用率越高——软件栈因此成为 τ 性能的一半。</div>

## 4 核心对比表：四类指令的分工

本节是纯概念主题，以核心对比表替代公式解析。

| 指令类别 | 执行单元 | 单条指令的作用 | 执行耗时 |
| --- | --- | --- | --- |
| 标量指令 | Scalar | 地址计算、循环控制 | 1 拍量级 |
| 向量指令 | Vector | 对向量逐元素运算 | 数十拍 |
| 矩阵指令 | Cube | 一次矩阵乘累加 | 数百拍 |
| 搬运指令 | 数据通路 | 张量在缓存层级间移动 | 数十—数百拍 |

<span class="marginnote">读表注意「执行耗时」一列：一条矩阵指令的执行时间是标量指令的几百倍。<strong>调度器的核心任务就是在这几百拍里，用标量、向量、搬运指令把其他单元填满</strong>，别让 Cube 独奏、全场喝彩、Vector 发呆。</span>

## 5 公式解析：流水线的吞吐与 IPC

量化指令流水线的能力，用**每周期指令数（IPC）**与总执行时间的关系。设一个 AI Core 同时可向 $W$ 个单元发射指令（多发射宽度），运行频率 $f$，共需执行 $I$ 条指令，则理想执行时间为：

$$
T_{\text{ideal}} = \frac{I}{W \cdot f} \quad (\text{秒})
$$

但实际执行还要考虑指令间的依赖等待与资源冲突，记一个**效率因子 $\eta \le 1$**：

$$
T_{\text{actual}} = \frac{I}{W \cdot f \cdot \eta}
$$

三步拆解：

- **第一步，看多发射宽度 $W$**：$W$ 越大，同一拍能发射的指令越多，执行越快。但 $W$ 受「各单元是否能同时忙碌」限制——若只有 Cube 有活干，$W=4$ 也白搭。
- **第二步，看效率因子 $\eta$**：$\eta$ 由指令依赖、数据等待、同步开销共同决定。显式同步虽然让行为确定，也引入等待——这是「确定性」的价格。
- **第三步，理解 τ 的优化目标**：编译器的一切努力（指令重排、数据预取、融合）都可以理解为**提高 $\eta$**。硬件把 $W$ 与 $f$ 定死，剩下的胜负手在软件。

用一个对比体会「效率因子」的分量：同一段计算，若编译器把矩阵指令与搬运指令交替排列（让 Cube 忙的时候数据也在路上），$\eta$ 可能到 0.9；若编译器把搬运指令一股脑排在前面（先搬完再算），Cube 会长时间空等，$\eta$ 掉到 0.4。两者差了一倍多——**不是硬件变了，只是指令排队的顺序变了**。这也解释了为什么 τ 的编译器团队和硬件团队必须一起工作：指令集的每一条设计，都是在为编译器的调度「铺路」。

<div class="marginnote">量级感：假设 $I=10^6$ 条指令、$W=4$、$f=1.5\ \text{GHz}$，理想耗时约 0.17 ms；若效率因子只有 0.5，则实际约 0.33 ms。<strong>同一份硬件，编译器差 30%，延迟就差 30%</strong>——这就是为什么 τ 把 CANN 编译器当「架构的一部分」来打磨。</div>

## 6 小结

- **指令集（ISA）**是硬件与软件的契约；τ 的 ISA 追求**可预期、可融合**，与通用 CPU 的「聪明硬件 + 模糊指令」路线不同。
- 四类指令：**标量、向量、矩阵、搬运**，各归各的执行单元，矩阵指令是信息密度最高的一种。
- 流水线特点：**多单元并行发射、流水线浅而确定、同步显式管理**——把复杂度从运行时搬到编译时。
- 核心公式：$T = \dfrac{I}{W \cdot f \cdot \eta}$，编译器的一切努力都在提高效率因子 $\eta$。
- 记住：τ 的性能一半在硬件（$W$、$f$），一半在编译器（$\eta$
