## 为什么从 Cache-aware 路由开始

上一节我们讲了 RadixAttention：同一个推理引擎内部，用前缀树把多条请求共享的 KV Cache 合并存储。但一个生产集群有几十上百个推理实例，请求该发给谁，是**路由器（router）**说了算的。如果路由不看缓存，请求落到一个「前缀完全不认识」的实例上，RadixAttention 再聪明也是白搭——前缀树只有命中才有价值。**Cache-aware 路由（缓存感知路由）**把「请求的公共前缀」和「每个实例缓存了什么」匹配起来，让缓存命中率成为路由决策的第一优先级；而**负载感知（load-aware）**调度则保证高命中不变成「一个实例忙死、其余实例闲着」。两者合起来，才是 SGLang Router 在集群层面做的调度。<span class="marginnote">本专题《服务化》一篇还会讲通用的负载均衡策略；这里讲的是<strong>面向缓存命中</strong>的路由，是 SGLang 区别于普通 Nginx/Envoy 网关的核心。</span>

## 1 为什么路由会影响缓存命中

RadixAttention 的前缀树是**实例内共享**的：树长在每个 worker 进程里，跨实例不共享。<span class="marginnote">这是理解本篇的<strong>第一关键点</strong>：前缀树不是全局的，每个 GPU 进程各有一棵。请求到了别的实例，等于一切从零开始，又要重新做 prefill。</span>因此同一个「公共前缀」的缓存，在物理上被复制到了所有服务过该前缀的实例上。路由的目标就是让新的请求尽量落在**已经缓存了它前缀**的那个实例。

考虑多轮对话的典型形态：用户 A 的系统提示词（system prompt）加历史对话占据了上千 token 的公共前缀，用户每次追问只新增几十个 token。如果 A 的第 5 轮请求被路由到一台新实例，这上千 token 全部要重新 prefill；而如果路由到之前服务过 A 的实例，RadixAttention 直接复用缓存，TTFT 可以降一个数量级。

**路由器必须回答两个问题**：每个请求的「公共前缀」是什么？每个实例当前缓存了哪些前缀？前者来自请求自身（token 化后的前缀），后者来自实例的缓存统计。SGLang 的 Router 正是通过维护每个实例的「缓存中前缀哈希」来完成匹配。

## 2 缓存感知路由的决策过程

SGLang 集群中，每个推理实例（runtime）会周期性地上报自己的缓存状态——其前缀树中每条路径的哈希值，连同对应的前缀长度。Router 维护一张「前缀哈希 → 实例」的索引表。<span class="marginnote">上报是<strong>周期 + 异步</strong>的：缓存状态有延迟，Router 对缓存的认知是「近似」的。工程上常通过估算（例如请求约消耗多少 token、前缀树节点计数）来降低上报频率与网络开销。</span>

当一个新请求到达时，路由决策的骨架如下：

- **第一步，抽取公共前缀**：把请求 prompt 哈希，与索引表里的前缀哈希做最长匹配，找出「命中前缀长度」。
- **第二步，候选实例排序**：按命中长度从大到小给实例排序，命中最长的实例排第一。
- **第三步，负载过滤**：命中很长的实例如果已经满载（例如排队中的 token 数超过阈值），就退而求其次，选命中次长但负载更轻的实例。这步就是**负载感知（load-aware）**。

**命中长度优先、负载兜底**，两者必须合在一起看：只看命中，缓存命中率漂亮但尾部延迟爆炸；只看负载，集群均匀但缓存全部浪费。SGLang Router 的目标函数可以粗略理解为「最小化期望的重新计算量 + 保持队列均衡」。

**路由决策的执行粒度也要想清楚**：Router 的决策发生在「请求进入引擎之前」，一旦把请求派给某个实例，实例内部还有自己的调度器（RadixAttention 的树内共享、内存池分配）。所以 Cache-aware 路由解决的是「实例之间的前缀复用」，实例内部的复用仍靠 RadixAttention——**两层各管一段，别混为一谈**。

## 3 负载感知的度量：CPU 排队 vs GPU 排队

负载感知听起来简单，难在「负载」用什么度量。几个候选：

- **连接数 / 正在处理的请求数**：最便宜，但完全看不出「一个请求是 1 个 token 还是 10 万 token」。
- **GPU 显存中 KV Cache 的占用比例**：直接反映该实例的批大小上限快到了没有，是 SGLang 实际使用的核心指标之一。
- **排队中的 token 总量**：vLLM 等引擎用 waiting/running 队列中的 token 数估计排队深度，比请求数精确得多。
- **预估的 prefill 负载**：新请求自身要 prefill 的 token 数，加上它期望复用的命中部分被剔除后的净新增量。

**请求在 CPU 上排队不等价于 GPU 忙**。GPU 是流式处理器：一个 batch 正在 decode 的时候，prefill 请求还在 CPU 侧做 tokenization 与调度决策。Router 若只看请求数，会把「已经在 GPU 上跑了大 batch」的实例当作空闲，导致它被塞进更多请求、decode 变慢。所以现代调度器用的是「批内 token 总量 + 显存占用」这类更贴近 GPU 工作量的度量。

**一个常被低估的度量：实例的「可命中前缀集合」本身也是负载**。缓存不是免费的——前缀树占显存、树节点计数要维护。实例缓存的前缀越长越多，其显存占用越高、可容纳的批越小。因此负载评估里的「KV 显存占用」一项，其实同时编码了「请求负载」与「缓存负担」两层信息。

## 4 公式解析：净新增计算量的估算

路由选择的效果，可以用一个简单模型量化。设请求的 prompt 总长度为 $L$，某实例已缓存了其中长度为 $h$ 的前缀，则该实例需要重新 prefill 的长度为：

$$L_{\text{net}} = L - h$$

整个集群上，一次请求引发的「净重新计算量」是所有候选中最优路径的 $L_{\text{net}}$。做一个三步拆解：

- **第一步，理解 $h$ 的取值**：$h$ 是「最长公共前缀命中长度」。当 $h = L$ 时 $L_{\text{net}} = 0$，请求零 prefill、直接进入 decode，这是缓存命中的理想情形（常见于同一多轮对话的续问）。
- **第二步，为什么用 $L_{\text{net}}$ 而不是命中率**：命中率是「比例」指标，$L_{\text{net}}$ 是「绝对量」指标。两个实例命中率相同，一个缓存了 1000 中 900、另一个缓存了 100 中 90，$L_{\text{net}}$ 分别是 100 和 10，后者远好于前者。**比例会骗人，绝对量不会**。
- **第三步，把它放进成本函数**：设每 token 的 prefill 计算成本为 $c_p$、decode 为 $c_d$，路由目标近似为

$$\min_{i \in \text{instances}} \; c_p \cdot L_{\text{net},i} + c_d \cdot W_i$$

其中 $W_i$ 是实例 $i$ 当前的排队工作量。这个式子把「缓存命中带来的收益」和「负载均衡的收益」放在同一个量纲下比较，正是 Cache-aware + Load-aware 联合调度的数学骨架。

这个式子也解释了「为什么 Router 要异步上报」：$W_i$（排队工作量）与 $L_{\text{net},i}$（净新增）都在快速变化，Router 拿到的永远是一份「稍旧的快照」。**只要上报频率远高于请求到达率，快照误差对决策的影响就可忽略**；反之则会把请求派到「上报时空闲、此刻已满」的实例。

## 5 实现层面的细节与取舍

SGLang Router 在实现上有几个值得注意的点：

- **前缀哈希的粒度**：缓存索引按「哈希 → 实例」组织，需要让每个实例缓存路径的哈希与请求前缀的哈希算法一致，才能做最长匹配。工程上常用滚桶哈希（如先按 token 分块、再对块哈希），支持 $O(\log)$ 或 $O(1)$ 的前缀匹配。
- **过期与一致性**：实例会驱逐（evict）缓存节点，Router 索引里的旧哈希会失配。因此命中结果要回源校验——Router 说「命中」，最终要以实例实际返回的缓存命中信息为准。
- **请求粘性（affinity）的代价**：把同一用户的请求尽量路由到同一实例，能最大化多轮缓存命中，但也意味着单个实例故障时，该用户的所有前缀缓存随之失效。生产上常配合「定期把热门前缀预热到多台实例」来缓解单点风险。

**辨析｜易错点：缓存感知路由 ≠ 会话粘性。** 会话粘性（sticky session）是「同一个 session 一定去同一台机器」，实现简单但粗暴；Cache-aware 路由是「谁缓存了最长前缀就去谁那」，可能把同一用户的不同轮次分到不同实例（例如前缀已被热迁移）。前者是网络层的惯用做法，后者才是面向 LLM 缓存的正确姿势。

## 6 数值算例：Cache-aware 路由的收益

把「命中 vs 不命中」算成具体数字。设系统提示词 + 历史对话构成 2k 前缀、每轮追问新增 0.1k、$c_p$（每 token prefill）是 $c_d$（decode）的 10 倍：

| 路由策略 | 第 5 轮追问的 prefill | 说明 |
| --- | --- | --- |
| 不看缓存（随机路由） | 2.1k token 全 prefill | 前缀可能落在无缓存的实例 |
| Cache-aware（命中） | 0.1k token | 2k 前缀命中，只算新增 |
| 命中 + 负载兜底 | 0.1k（或略多） | 命中优先，满载时退而求其次 |

**读这张表**：Cache-aware 路由把「每轮追问的 prefill」从 2.1k 降到 0.1k——**TTFT 可以降一个数量级**。多轮对话轮次越深、前缀越长，收益越大。这就是「为什么 SGLang 的 Router 值得为缓存做路由」的量化理由。<span class="marginnote">这张表的另一面：<strong>首轮（冷缓存）必须全 prefill</strong>，且命中收益的上限由「前缀复用率 × 实例缓存容量」决定——Router 的缓存索引只是「把请求送到能命中的地方」，命中本身还要看实例缓存装不装得下。</span>

**一个权衡提醒**：命中优先会把「同一用户的请求」都压到少数实例，负载不均——**「负载兜底」的阈值（满载就放弃命中）决定了平衡点**。命中收益 vs 负载不均的账，正是第四节的成本函数在算。

**另一个值得算的账是「路由要多大才值得」**：缓存路由需要 Router 维护前缀索引、实例周期上报，这些本身有成本。若请求大多是「一次性查询」（无共享前缀、无多轮），命中率趋近于 0，Cache-aware 路由退化为普通负载均衡——此时纯随机/轮询路由反而更省。**缓存路由的收益门槛在「共享前缀 + 多轮/同模板请求」的占比上**：两者任一趋近 0，收益就趋近 0。

## 7 实现细节与工程落地

把 Cache-aware 路由从「决策框架」落到工程，几个要点：

**前缀哈希索引**：Router 维护「前缀哈希 → 实例」的索引表，请求前缀用同一哈希算法做最长匹配——**哈希算法两侧必须一致**，否则匹配不上。

**周期异步上报**：实例周期上报缓存状态（路径哈希 + 前缀长度）——**有延迟，Router 对缓存的认知是「近似」的**。命中结果要回源校验，以实例实际返回为准。

**会话粘性 ≠ Cache-aware**：粘性是「同 session 必去同一实例」（粗暴）；Cache-aware 是「谁缓存最长前缀去哪」（动态）。前者实现简单但僵化，后者是面向 LLM 缓存的正确姿势。

**辨析｜易错点：别把「命中率」当唯一指标。** 命中率是比例，$L_{\text{net}}$ 是绝对量——**两个实例命中率相同，一个缓存了 1000 中 900、另一个缓存了 100 中 90，后者好得多**。路由优化的目标函数要用「净重新计算量」（绝对量），不是命中率（比例）。

**Cache-aware 路由收尾一句**：它是「把请求送到能复用缓存的实例」的调度艺术——**命中优先 + 负载兜底，用「最小化净重新计算量」统一两个目标**。理解它，就理解了 SGLang 集群级调度的心脏。

## 8 小结

- **缓存命中是实例私有的**：前缀树只在单实例内共享，跨实例必须靠路由把请求送到「对的人」手里。
- **路由决策 = 最长前缀命中优先 + 负载兜底**：两个目标统一进「最小化净重新计算量 + 均衡队列」的成本函数。
- **负载度量要用 GPU 视角**：请求数、连接数都失真，KV Cache 占用与批内 token 总量才是贴近 GPU 工作量的指标。
- **实现要点**：前缀哈希索引、周期异步上报、回源校验命中、注意会话粘性与缓存命中的差别。
- **命中收益乘轮次**：多轮追问的 prefill 从全量降到新增，TTFT 降一个数量级；别用命中率、用净重新计算量。
