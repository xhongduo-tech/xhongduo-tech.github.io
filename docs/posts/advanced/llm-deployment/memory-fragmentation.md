## 为什么从显存排查开始

「显存不够了」是推理部署最常见的故障——但很多「OOM」其实不是「真的不够」，而是**显存被碎片化**：总空闲显存够大，却没有一块连续的地址够分配。理解显存怎么被占用、为什么碎、怎么诊断，是推理服务的必修课。<span class="marginnote">本专题《模型加载与权重显存布局》算过「需要多少显存」；本篇讲<strong>显存到了之后怎么管理、为什么碎片、怎么排查</strong>——是「有了预算」之后的「把预算用好」。</span>

本篇讲推理显存的四块构成、碎片化的根源、以及诊断显存问题的工具与方法。

## 1 推理显存的四块构成

一张 GPU 上的显存被四类东西占用：

1. **权重**：模型参数（FP16/INT4/FP8）。固定大小，加载后常驻。
2. **KV Cache**：按「最大序列数 × 最大序列长度」预分配（vLLM 的显存池），随并发与上下文增长，**是动态波动最大的部分**。
3. **激活**：单步前向的中间张量。prefill 时峰值大（大矩阵），decode 时小。
4. **CUDA context / 框架开销**：CUDA 初始化、cuBLAS workspace、PyTorch 缓存分配器等。<span class="marginnote">PyTorch 的缓存分配器（<code>torch.cuda.caching_allocator</code>）会「囤」显存：<strong>释放的张量内存先留在池里复用，而不是立刻还给驱动</strong>——这让「空闲显存」的读数很迷惑人。</span>

**利用率的核心度量**：显存利用率 = 实际使用 / 总量。但「使用」里要区分「有效使用」（权重 + 真在用的 KV）与「浪费」（碎片、预分配但没用的余量）。**高占用率 ≠ 高利用率**——预分配了 max KV 但并发低时，占用高、利用低。

## 2 碎片化的根源

显存碎片（fragmentation）分两类：

**内部碎片**：分配的块比实际需要的大。典型：KV Cache 按固定块（block）分配，一个只用了 1 个 token 的块也占满整个块——**块内的浪费是内部碎片**。<span class="marginnote">vLLM 的页式分配（PagedAttention）已经把 KV 切小，但块大小（默认 16 个 token 一块）仍是内部碎片的下界。<strong>块越小内部碎片越小，但块表与索引开销越大</strong>。</span>
**外部碎片**：多次分配/释放后，空闲显存被切成很多小片，没有连续大块。典型：长序列请求反复分配/释放大块 KV，留下「瑞士奶酪」般的空洞。

碎片化的后果：**空闲显存总量充足，但大分配（如一个大 prefill 的激活）失败 → OOM**。这也是为什么「`nvidia-smi` 显示还有 20 GB 空闲，vLLM 却报 OOM」的真相。

## 3 诊断显存问题的工具链

排查显存问题的工具，从粗到细：

**`nvidia-smi`**：看显存总量、占用、进程。第一层快筛——「是不是别的进程占了」「显存是不是被打满」。
**vLLM 引擎的显存日志**：启动时打印「KV cache 预分配了多少、可用显存多少」。**看 KV 预留是否过大/过小**——预留过大挤压激活，过小则并发上不去。
**PyTorch 显存快照（`torch.cuda.memory_snapshot()`）**：生成内存分配的完整画像——**每个张量多大、何时分配、哪块是碎片**。这是「碎片到底碎在哪」的终极答案。<span class="marginnote">显存快照是排查碎片的标准工具：<strong>它会显示每个分配的「地址、大小、占用的堆栈」</strong>，一眼看出「大块被切成了多少小块」「哪块分配后一直没释放」。</span>
- **引擎的内存池统计**：vLLM 的 `vllm_gpu_cache_usage_perc`（KV 缓存使用率）指标与日志里的 block 使用率，看 KV 池的实际利用率——**利用率低说明预分配过大，利用率高说明接近上限**。

**排查流程**：先 `nvidia-smi` 排除外部占用 → 看引擎日志的 KV 预留 → 若 OOM 频繁且显存有空闲 → 用快照查碎片 → 针对碎片调整（见下节）。

## 4 公式解析：显存预算与碎片的数学

vLLM 的显存分配核心是「KV 池预留」。设可用显存 $M$，权重 $W$，KV 预留 $K$，激活余量 $A$：

$$M = W + K + A$$

- **第一步，读分配逻辑**：vLLM 用 `gpu_memory_utilization`（默认 0.9）控制：$W + K \le 0.9 M$，其余 10% 留给激活与 CUDA 开销。**KV 预留 $K$ 由「最大序列数 × 最大序列长度 × 每 token KV 字节」决定**——并发生成参数直接改变预留量。
- **第二步，读碎片的影响**：外部碎片意味着「逻辑上可用、物理上不连续」。设碎片率 $\rho$（不可用字节 / 总空闲），则实际可分配 $= (1-\rho) \times \text{空闲}$。**$\rho$ 大时，即使空闲多也会 OOM**。
- **第三步，读缓解手段**：降低碎片的方法——**统一 KV 块大小**（vLLM 的块分配天然抗外部碎片）、**提前分配**（权重与 KV 池一次性分配，避免反复分配释放）、**按需增长**（激活用完即还，配合内存池复用）。碎片的终极解是「预分配 + 池化」，这正是 vLLM 的 KV 池设计初衷。

## 5 小结

- **显存四块构成**：权重、KV Cache（预分配、动态）、激活（prefill 峰值）、框架开销；高占用率 ≠ 高利用率。
- **两类碎片**：内部碎片（块内浪费）与外部碎片（空闲被切碎），后者让「有空闲却 OOM」。
- **诊断工具链**：`nvidia-smi` 快筛 → 引擎 KV 日志 → PyTorch 显存快照定位碎片 → 内存池统计。
- **KV 预留是显存预算的核心**：由 max-num-seqs × max-model-len 决定，`gpu_memory_utilization` 控制分配比例。
- **碎片缓解**：统一块大小、预分配池化、激活即用即还——预分配 + 池化是终极解。
