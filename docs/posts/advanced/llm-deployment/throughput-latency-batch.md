# 推理吞吐、延迟与批大小的基本关系

## 为什么把吞吐与延迟放在一起算账

《访存瓶颈》一节我们算过单流生成的上限：LLaMA-3 8B 在 A100 上约每秒 125 个 token，并且预告「批处理是解药」。这一节把这张药方真正开出来，并且回答一个更关键的问题：**批处理到底给服务带来了什么，又拿走了什么？**

答案是一对拆不散的量：**吞吐（throughput）**和**延迟（latency）**。批处理让吞吐几乎线性增长，却同时推高每个请求的延迟——这是推理服务最核心的一对矛盾，也是 vLLM、SGLang、TensorRT-LLM 所有调度技巧都在反复权衡的天平。这一节先把这两个指标定义清楚，再推导「批大小如何同时拨动它们」，最后用 Little's Law 把服务指标翻译成硬件上的并发需求。

## 1 两个指标、三条时间线

服务层的指标比单次前向复杂，因为一次「请求」是**一长串 token 的生成**，而不是一个 token。常用的指标有三个：

- **吞吐量（throughput）**：单位时间产出的 token 总数（token/s），或完成的请求数（req/s）。它衡量「这台机器整体能干活多快」，是容量规划的总闸。
- **首 token 延迟（TTFT，Time To First Token）**：从请求到达引擎，到吐出第一个 token 的时间。用户感知里「它开始说话了」的那一瞬。
- **单 token 间隔（TPOT，Time Per Output Token）**：相邻两个输出 token 之间的时间间隔，也叫 inter-token latency。它衡量「说话有多连贯」。

三者拼成端到端响应时间：

$$T_{\text{e2e}} = T_{\text{TTFT}} + (n_{\text{out}} - 1) \times T_{\text{TPOT}}$$

<span class="marginnote">不同产品的天平完全不同：聊天机器人盯着 TTFT（首字快不快），长文写作盯着 TPOT（是不是一字一字地蹦），离线批量任务只关心吞吐（一晚上能跑完多少篇）。设计服务时先想清楚你的用户盯着哪条时间线，再决定优化哪个指标。</span>

关键认知：**这三个指标不是同一件事，甚至经常相互打架**。一个吞吐极高的服务，可能每个请求都慢得让人抓狂；一个单请求飞快的服务，可能整体吞吐低得没法用。搞清它们各自被什么决定，是理解引擎设计的第一步。

## 2 批大小如何同时拉动吞吐与延迟

先回顾《访存瓶颈》的关键结论：Decode 每步都要完整读一遍权重，而**权重在同一个批次的所有序列之间是共享的**。于是把 $B$ 个序列拼成一轮前向，读一遍权重，喂给 $B$ 个 token 同时算——吞吐几乎翻 $B$ 倍。

更反直觉的是：**在访存受限区间，批大小变大几乎不拖慢每一步**。因为每步的墙钟时间由「搬权重」主导（约 8 ms），而这个搬运量与批大小无关——批大只是让同一批字节被更多 token 复用。所以：

- 批大小从 1 涨到 100，**每步时间几乎不变**，吞吐近似线性增长；
- 单个请求的 TPOT 在批内也几乎不变——它每步照样约 8 ms 出自己那个 token。

这是「批处理为什么几乎是白赚的」的根源：**它填满了原本被浪费的访存带宽，而不增加每步的搬运量**。<span class="marginnote">把访存受限的 Decode 想成一辆每天按固定路线跑的货车：运费由「跑一趟」决定，与货箱装多少无关。空车跑一趟和装满跑一趟同样贵，所以当然要装满——批处理就是往这辆注定要跑的车里尽量塞货。</span>

但批处理并非没有代价，代价分两处。第一，**吞吐不会无限涨**：当批大到每步的计算量追上算力，Decode 就从访存受限翻转为计算受限，每步时间开始随 $B$ 线性上升，吞吐封顶。第二，**延迟会被推高**：调度器要攒够一批才开工，批越大，新请求排队等批位的时间越长（TTFT 上升）；同一批里最长序列还会拖慢整批（同步屏障）。这条曲线是第 3、4 节的主角。

## 3 公式解析：批处理的收益曲线

把上面的直觉写成可计算的公式。记 $N$ 为参数量、$b$ 为每参数字节、$\beta$ 为显存带宽、$\pi$ 为算力、$B$ 为批大小。每步的墙钟时间近似取两项里慢的那个：

$$t_{\text{step}}(B) = \max\left(\frac{Nb}{\beta},\ \frac{2NB}{\pi}\right), \qquad \text{TP}(B) = \frac{B}{t_{\text{step}}(B)}$$

逐步拆解：

- **第一步，写访存项 $Nb/\beta$**：每步把 $Nb$ 字节权重搬一遍所需时间，**与 $B$ 无关**——批再大，读的还是同一份权重。这是曲线「平坦段」的来源。
- **第二步，写计算项 $2NB/\pi$**：每步要算 $2NB$ 次浮点运算（$B$ 个序列各做一个 token 的前向），除以算力 $\pi$。它**随 $B$ 线性增长**。
- **第三步，取 max**：瓶颈是慢的那一项，它决定了每步时间。
- **第四步，吞吐 = $B/t_{\text{step}}$**：每步同时产出 $B$ 个 token，除以每步耗时，就是每秒吞吐。

代入 LLaMA-3 8B + A100（$N=8\times10^9$，$b=2$，$\beta=2\times10^{12}$ B/s，$\pi=312\times10^{12}$）：

$$t_{\text{mem}} = \frac{16\times10^9}{2\times10^{12}} = 8\ \text{ms}, \qquad t_{\text{compute}}(B) = \frac{2\times8\times10^9 B}{312\times10^{12}} \approx 0.051\,B\ \text{ms}$$

两式相等处是曲线的**拐点**：$0.051B = 8 \Rightarrow B \approx 156$。于是吞吐曲线分成两段：

$$B < 156:\ \text{TP} = \frac{B}{8\ \text{ms}} = 125\,B\ \ \text{token/s}; \qquad B \ge 156:\ \text{TP} = \frac{1}{0.051\ \text{ms}} \approx 19{,}500\ \text{token/s}$$

在拐点之前，**每增加 1 个并发，吞吐就多 125 token/s**，且单请求 TPOT 不变（约 8 ms）；过了拐点，吞吐封顶在约 19,500 token/s，TPOT 开始随批大小恶化。

**但工程现实是：绝大多数服务根本走不到这个拐点。** 上一节算过，A100 + 8B FP16 + 4K 上下文，KV 显存只允许约 88 个并发——**88 远小于 156**。也就是说，在这个配置下你永远停在「访存受限」的平坦段，吞吐上限由显存而不是算力决定：

$$\text{TP}_{\text{实际上限}} \approx S_{\max} \times 125 \approx 88 \times 125 \approx 11{,}000\ \text{token/s}$$

这解释了为什么引擎层拼命压 KV 显存（分页、量化、GQA）：**把 $S_{\max}$ 推上去，就是在平坦段把吞吐推上去**。真实部署还要打 60%–80% 的折扣（kernel 到不了满带宽、调度与采样有开销），所以 vLLM 上 8B 模型常见的几千 token/s 就是这个道理。

## 4 延迟从哪里漏进来：排队与同步屏障

吞吐曲线讲清楚了，但延迟的故事还没完。批大小推高延迟，除了「攒批要等」之外，还有一条更隐蔽的路径——**同步屏障（synchronization barrier）**。

Decode 的每一轮，同一批的 $B$ 个序列是**同步推进**的：所有序列都算完，才一起进入下一轮。于是**每步的墙钟时间被批里最慢的那个序列主导**。在纯访存受限区间，每个序列每步的耗时几乎相同（都约 8 ms），屏障代价很低；但一旦某些序列的上下文特别长、注意力特别重，它们就会成为「拖后腿」的那个，把整批的速度拉向自己。<span class="marginnote">这就是为什么超长上下文的请求是「吞吞吐的怪兽」：它每步的 KV 读取量远超普通请求，却让同批的所有序列陪着它一起等。SGLang 的 cache-aware 调度、vLLM 的抢占换出，一大半功夫都在对付这类请求（见第三、四篇）。</span>

另一条延迟路径是**排队**。批大小 $B$ 越大，调度器为了填满批而等待的时间越长，新请求的 TTFT 里「等批位」的部分就越长。这构成了引擎调度器最经典的取舍：**填满批次（吞吐）vs 尽快开工（TTFT）**。Continuous Batching（第三篇）的全部技巧，就是在这对矛盾里反复找平衡——不满批就开跑，但要保证批不至于太小而浪费带宽。

所以延迟的完整来源有三段：**排队等批位 + Prefill 处理 prompt + 逐 token 生成**。吞吐优化的本质，是把前两段压到最小、让第三段尽量保持在平坦段。

## 5 Little's Law：把服务指标翻译成并发预算

吞吐与延迟的账算完，还剩一个工程问题：**给定一个服务目标，到底需要多大的并发（批）容量？** 这里用到排队论的基石——Little's Law：

$$C = \lambda \times W$$

- $C$：**同时在途（in-flight）的请求数**，即硬件需要同时容纳的并发量；
- $\lambda$：请求**到达率**（req/s）；
- $W$：每个请求的平均**服务时间**（s）。

逐步拆解：

- **第一步，理解三量的单位**：$\lambda$ 是「每秒进来几个」，$W$ 是「每个待多久」，相乘得「此刻有几个在系统里」——量纲上 $(\text{req/s}) \times (s) = \text{req}$，正是 $C$。
- **第二步，为什么成立**：稳定系统里，单位时间完成数等于到达数。任取一段长窗口，把每个请求在系统里的逗留时间累加，等价于按在途数逐时刻求和——这就是「平均在途数 = 到达率 × 平均逗留时间」的直观证明。它不依赖任何到达分布，是排队论里少数无条件成立的公式。
- **第三步，如何用它做容量规划**：设好延迟预算（即 $W$），结合到达率 $\lambda$，解出必须的并发 $C$，再和上一节（以及第一篇）的 $S_{\max}$ 对比——**硬件给的并发上限，必须盖过业务算出的并发需求**。

一个具体例子。设服务目标是：TPOT = 20 ms，平均输出 200 token。则单请求生成时间 $W \approx 200 \times 0.02 = 4$ s（暂忽略 TTFT）。若业务到达率 $\lambda = 1000$ req/min ≈ 16.7 req/s：

$$C = 16.7 \times 4 \approx 67\ \text{个在途请求}$$

对照上一节：A100 + 8B FP16 + 4K 上下文给到约 88 个并发——**勉强够，但余量不大**。若平均输出涨到 400 token（$W = 8$ s），则 $C \approx 133$，**超过 88**——单卡 A100 已无法满足，要么换更大的卡、要么砍精度释放 KV、要么上张量并行（第八篇）。Little's Law 的价值就在这：它把「用户体验指标」翻译成「硬件容量需求」，让容量问题在买卡之前就能回答。

**辨析｜易错点：**

**误区一：把 TPOT 当吞吐。** TPOT 是单个请求的节奏，吞吐是整台机器的产出。TPOT 20 ms 意味着每个用户每秒 50 个 token，但 100 个并发用户的服务每秒要产出 5000 个 token——两个指标差了 100 倍，别混用。

**误区二：以为批越大越好。** 在平坦段批越大吞吐越高，但代价是 TTFT 变长、长尾被拖慢。吞吐与延迟是跷跷板，压测报告里「吞吐涨了」与「TTFT 变长」往往同时出现（第十篇会把这条曲线实测给你看）。

**误区三：用峰值 $\lambda$ 当平均。** Little's Law 用的是长期平均。突发请求潮会让在途数瞬间越过 $S_{\max}$，排队爆炸、尾延迟失控——这正是为什么服务要限流、要监控 P99 而不是 P50（第九、十篇）。

## 6 小结

- **三条时间线**：吞吐量、TTFT、TPOT；端到端响应 = TTFT + (输出长度 − 1) × TPOT，三者诉求常互相冲突。
- **批处理收益**：访存受限区间每步时间与批大小无关（$t_{\text{step}} \approx Nb/\beta$），吞吐近似线性增长、TPOT 几乎不变——「填满注定要跑的车」。
- **收益曲线**：$t_{\text{step}}(B) = \max(Nb/\beta,\ 2NB/\pi)$，拐点 $B \approx 156$（8B/A100）；但 KV 显存把并发限在约 88，**实际永远停在访存受限段**，吞吐上限由显存决定。
- **延迟两处漏**：攒批排队（TTFT 变长）与同步屏障（最慢序列拖累整批）。
- **Little's Law**：$C = \lambda W$ 把服务目标翻译成并发需求，与硬件 $S_{\max}$ 对表，容量够不够在买卡前就能算清。
