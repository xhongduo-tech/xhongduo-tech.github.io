## 为什么从多 LoRA 服务开始

微调（第四级《大模型微调》专题）告诉我们一件事：**把一个大模型变成「懂 SQL 的助手」「懂公司文档的助手」「懂法律文书的助手」，不必为每个任务重新训练一个完整模型。** LoRA（Low-Rank Adaptation）只训练一小撮参数，就能把基座模型掰向特定任务。于是真实系统里出现了一种奇观：**同一个基座，背着一大排适配器（adapter）**——一个客户一个，一个业务一个，甚至一个 Prompt 模板一个。

部署的难题随之而来。如果每来一个新适配器就重新部署一份完整模型，那 7B 基座 + 30 个适配器就是 31 份 14 GB 的权重，显存先破产。<span class="marginnote">本章前面讲 KV Cache 时反复强调「显存是推理的第一稀缺资源」。多 LoRA 服务的全部动机，就是不让适配器的个数乘以基座的体积。重量级权重只放一份，轻量级差异随取随用。</span>

**多 LoRA 服务（Multi-LoRA Serving）**：在一个推理进程中只加载一份基座模型权重，同时挂载多个 LoRA 适配器，让不同请求在运行时各选各的适配器，共用同一份显存里的权重与 KV 管理机制。它是「微调普惠化」在部署侧的必然配套——本文以 vLLM 的实现为主线，把这套机制拆开看。

## 1 LoRA 的数学：低秩分解到底改了什么

先回到 LoRA 本身。设某线性层权重为 $W \in \mathbb{R}^{d \times k}$，输入 $x \in \mathbb{R}^{k}$，输出 $y = Wx$。LoRA 不修改 $W$，而是在旁边挂两条**低秩**矩阵：

$$
\Delta W = B A, \qquad A \in \mathbb{R}^{r \times k},\; B \in \mathbb{R}^{d \times r}
$$

其中秩 $r \ll \min(d, k)$。于是新的前向变成：

$$
y = W x + \frac{\alpha}{r}\, B A x
$$

**核心概念：低秩（low rank）**：$BA$ 的秩最多是 $r$，而 $\Delta W = BA$ 想表达的「权重增量」被限制在一个 $r$ 维子空间里。训练时只更新 $A, B$ 里的 $r(d+k)$ 个参数，$W$ 完全冻结。对 7B 模型的全连接层，$d, k$ 都在数千量级，而 $r$ 常取 8–64——**可训练参数占比通常不到 1%**，这就是 LoRA 省显存省算力的根源。<span class="marginnote">$\alpha$ 是 LoRA 论文里的缩放常数，常取与 $r$ 同量级；$\alpha/r$ 这个缩放因子可以预先乘进 $B$（peft 库就是这么做的：保存时把 $B$ 缩放好），推理时就不用再单独乘一次。想复习低秩与矩阵分解，见第二级《线性代数》的矩阵分解一节。</span>

这个公式对服务有两条直接推论，一条省算力，一条省显存：

**省算力**：$BAx$ 按结合顺序算成 $B(Ax)$，先做 $Ax \in \mathbb{R}^{r}$，再做 $B \cdot (Ax) \in \mathbb{R}^{d}$，每 token 计算量是 $O(rk + dr)$；若先算 $BA$ 再乘 $x$，则是 $O(dk)$。因为 $r \ll d, k$，前者比后者少一个数量级以上——**低秩只有按「从右往左」结合才便宜**。
**省显存**：$A, B$ 加起来只有 $r(d+k)$ 个参数。7B 模型上训练全套线性层的 rank-16 LoRA，权重文件通常只有几百 MB，是基座的 1/10 到 1/50。这让「一个进程里常驻几十个适配器」在显存上变得可行。

## 2 多 LoRA 服务的本质：一份基座、N 份适配器

把上面的数学翻译成部署架构，就是三个「共享」与三个「不变」：

**三个共享**：

**权重共享**：基座 $W$ 在所有线性层只存一份。N 个适配器共享这份权重，各自只带自己的 $A, B$。
**KV 机制共享**：多 LoRA 不改变 KV Cache 的任何机制——页式分配、块表、Prefix Caching 全部照常工作。<span class="marginnote">注意这里的「共享」指<strong>结构</strong>共享：每个请求依然有自己的 KV 缓存（缓存内容由「基座 + 该请求所选适配器」共同决定的 QKV 投影算出），跨适配器不会共享 KV 内容，但同一适配器的共享前缀依旧能命中 Prefix Caching。</span>
- **调度共享**：批处理器一视同仁地看待不同适配器的请求，连续批处理照常运行——前提是调度器能知道「这条请求用哪个适配器」。

**三个不变**：

- **注意力不变**：注意力分数只由 Q、K 的点积决定，而 Q、K 已经由带适配器的投影算好；**注意力本身不需要为适配器做任何特殊处理**。
- **采样不变**：softmax、温度、top-p 都在 logits 上进行，适配器只影响 logits 的来源，不影响采样逻辑。
- **解码循环不变**：逐 token 自回归、停止条件、流式输出，全部与单模型一致。

**重点：多 LoRA 把「权重」这个本来随任务倍增的维度，压缩成了「一行选择」。** 请求进来，先认领适配器，再走一条与普通推理几乎完全相同的流水线。这也是为什么 vLLM 敢说「多 LoRA 对基座服务只有约 10% 的吞吐损失」。

## 3 公式解析：y = Wx + (α/r)·B(Ax) 与结合顺序

把多 LoRA 最核心的一条前向公式逐项拆开：

$$
y = \underbrace{W x}_{\text{基座贡献}} + \underbrace{\frac{\alpha}{r} B (A x)}_{\text{适配器贡献}}
$$

- **第一步，认基座贡献 $Wx$**：$W$ 是冻结的基座权重，$d \times k$ 的稠密矩阵。它在所有请求间共享，显存里只放一份。
- **第二步，认适配器贡献 $\frac{\alpha}{r} B (A x)$**：$A$ 先把 $k$ 维输入压到 $r$ 维（$Ax$），$B$ 再把它撑回 $d$ 维。两条矩阵合起来是 $d \times k$ 的「低秩补丁」，但真正要存的是 $r(k+d)$ 个参数，不是 $dk$ 个。
- **第三步，看结合顺序 $B(Ax)$ 而非 $(BA)x$**：$BA$ 在数学上等于 $dk$ 阶稠密矩阵，先算它等于把低秩优势全丢了；先算 $Ax$ 得到 $r$ 维中间量，乘法量级从 $O(dk)$ 降到 $O(r(k+d))$。**这条结合顺序是 LoRA 推理一切性能优化的出发点。**
- **第四步，看缩放因子 $\alpha/r$**：$r$ 越大，每条矩阵的「单位强度」越小，需要 $\alpha$ 补偿。工程上通常把缩放吸收进 $B$：$\tilde{B} = (\alpha/r) B$，前向变成 $y = Wx + \tilde{B}(Ax)$，省一次运行时乘法。

以 7B 模型、$d = 4096, k = 4096, r = 16$ 为例：直接算 $BAx$ 每 token 约 $4096 \times 4096 \approx 1.68 \times 10^7$ 次乘加；按 $B(Ax)$ 算则是 $16 \times 4096 \times 2 = 1.31 \times 10^5$ 次——**差两个数量级**。这也解释了为什么多 LoRA 服务的吞吐损失能压到 10% 以内：适配器的增量计算在数学上被设计得足够便宜。

## 4 vLLM 里怎么组织多 LoRA

vLLM 对多 LoRA 的支持分成「静态声明」与「运行时认领」两层。

**静态声明**：启动服务时用 `--enable-lora` 打开开关，用 `--lora-modules` 一次性声明一批适配器：

```bash
# 静态声明：打开 LoRA 开关，启动时声明两个适配器
vllm serve meta-llama/Llama-3.1-8B-Instruct \
    --enable-lora \
    --lora-modules sql=./lora/sql-adapter doc=./lora/doc-adapter \
    --max-lora-rank 64 \
    --max-cpu-loras 8 \
    --max-loras 4
```

- `max_loras`：**最多能同时「活跃」在 GPU 上的适配器数**。请求与适配器是一对多的——同一适配器的请求可以并行处理，只要总活跃数不超上限。
- `max_cpu_loras`：允许有多少适配器**暂存在 CPU（显存外）**，需要时换入 GPU。这相当于给适配器也做了一层「换入换出」，与第二章调度器的抢占换出思路一脉相承。
- `max_lora_rank`：服务端接受的最大秩 $r$，用来预分配适配器权重所需的缓冲。

**运行时认领**：客户端在请求里带上「我要用哪个适配器」。vLLM 的 OpenAI 兼容接口用 `"lora"` 字段指定（`{"lora_name": "sql"}`）；Python 离线接口则显式构造 `LoRARequest`：

```python
from vllm import LLM, SamplingParams
from vllm.lora.request import LoRARequest

llm = LLM(model="meta-llama/Llama-3.1-8B-Instruct",
          enable_lora=True, max_loras=4, max_lora_rank=64)
outputs = llm.generate(
    ["SELECT * FROM users WHERE id = ?;"],
    sampling_params=SamplingParams(temperature=0, max_tokens=64),
    lora_request=LoRARequest(name="sql", lora_int_id=1, path="./lora/sql-adapter"),
)
```

注意 `LoRARequest` 的三个字段：**名字（name）、全局唯一 ID、适配器路径（path）**。调度器靠这个三元组去查「这个适配器加载了没、在 GPU 上还是 CPU 上」。

**动态装载**：适配器不必启动时全部声明。设置环境变量 `VLLM_ALLOW_RUNTIME_LORA_UPDATING` 后，可以运行时通过 `/v1/load_lora_adapter` 上传新适配器（payload 里给 `lora_name` 与 `lora_path`），或用 `/v1/unload_lora_adapter` 卸载。<span class="marginnote">这给「多租户平台」提供了完整拼图：租户可以自己注册 LoRA，平台按请求粒度路由。代价是安全风险——vLLM 官方明确警告运行时加载功能只应在隔离、可信环境里开启，生产公开服务需谨慎。</span>

## 5 装载缓存与批量计算的工程细节

多 LoRA 服务真正难的不是数学，而是**「一个 batch 里同时有十种适配器」时怎么高效算**。

**装载缓存（LoRA Cache）**：每个适配器的 $A, B$ 权重按 `lora_id` 缓存。首次用某适配器要把它从磁盘读入、可能要从 CPU 换入 GPU——这笔开销约 20–30 ms，**缓存命中后消失**。活跃适配器按 LRU 管理：GPU 上适配器太多时，把最久没用的挪回 CPU 腾位。这块逻辑在 vLLM 里集中在 `LoRAModelManager` 的 `LRUCache` 缓存结构。

**批量低秩计算**：一个 batch 里 $x_1$ 属于适配器 A、$x_2$ 属于适配器 B、$x_3$ 属于适配器 A……如果对每个请求单独跑一遍 $B(Ax)$，GPU 并行度被撕碎。vLLM 的做法是**按适配器分组、对组内做批量矩阵乘**：同一适配器的请求合并成一个小 batch 一起算 $B(Ax)$，不同适配器之间再串行。这就是业界常说的 SGMV（Sparse Gather Matrix-Vector）这类算子的用武之地——把「按请求取权重」翻译成「按组批量取权重再算」的 gather 操作。<span class="marginnote">吞吐损失主要来自这里：适配器个数越多、每个适配器的请求越稀疏，批量形状越碎，GPU 利用率越低。这就是「约 10% 吞吐损失」的工程来源——不是数学贵，是调度形状碎了。</span>

**权重内存布局**：适配器权重通常以低精度（FP16/BF16）常驻，按层索引组织；前向时只把「当前 batch 用到的那些层、那些适配器」的权重搬进计算缓冲。显存成本粗略按「每个活跃适配器 200–400 MB」量级估算（取决于模型大小与秩），几十个适配器在 80 GB 的 A100 上是常态。

## 6 什么时候用多 LoRA：收益与易错辨析

多 LoRA 不是银弹，它的适用边界很清晰：

- **适配器多、且每个适配器都有稳定流量** → 收益最大：一份基座服务 N 个业务。
- **适配器之间是「异构任务」而非「同任务不同口味」** → 合适：SQL 助手、文档问答、法律文书，任务差异大，LoRA 各司其职。
- **适配器个数少、基座也小** → 直接多份部署可能更简单，别为 2 个适配器引入复杂度。

**辨析｜易错点：**

- **误区一：以为多 LoRA 会把 KV Cache 也「按适配器共享」。** 不会。KV 由「基座 + 适配器」的投影算出，每条请求的 KV 都是自己的；共享的是**权重**与**管理机制**。跨适配器复用 KV 是另一回事（且一般不该复用）。
- **误区二：以为适配器只改 FFN。** LoRA 可以挂在任何线性层——注意力的 Q/K/V/O 投影、FFN 的两个全连接、甚至 embedding。挂在 QKV 投影上时，K、V 会随适配器变化，KV 内容自然跟着变。
- **误区三：以为 `max_loras` 是「适配器总数上限」。** 它是**同时活跃**上限；总数由 `max_cpu_loras` + 动态装载决定，超出活跃上限的适配器在 CPU 侧排队等换入。
- **误区四：把「动态加载 LoRA」当默认安全。** 官方默认关闭（需要显式环境变量），因为它引入了任意代码/权重注入面。生产环境务必评估隔离与鉴权。
- **误区五：以为多 LoRA 与量化冲突。** 不冲突：基座可以 FP8 量化，适配器权重独立存放。两者叠加时注意适配器精度与基座精度的对齐（通常适配器保持 BF16，激活里各自反量化）。

## 7 小结

- **LoRA 数学**：$\Delta W = BA$，$r \ll \min(d,k)$，前向 $y = Wx + \frac{\alpha}{r}B(Ax)$；**按 $B(Ax)$ 结合**才能拿到低秩带来的算力红利。
- **多 LoRA 本质**：权重共享、KV 机制共享、调度共享；注意力、采样、解码循环三不变。
- **vLLM 三件套**：`--enable-lora` 开关 + `--lora-modules` 静态声明 + `lora_name`/`lora_request` 字段运行时认领。
- **动态装载**：`/v1/load_lora_adapter` 支持运行时上载适配器；`max_loras` 管活跃数、`max_cpu_loras` 管 CPU 侧暂存。
- **工程开销**：装载缓存命中后约 20–30 ms 消失；批量形状碎片化带来约 10% 吞吐损失；每活跃适配器约 200–400 MB 显存。
- **适用边界**：适配器多、异构任务、流量稳定时收益最大；2 个适配器的小场景直接多份部署更省事。
