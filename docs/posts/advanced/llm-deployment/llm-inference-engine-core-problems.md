## 为什么需要一个「引擎」层

前三篇我们已经把推理的底层账算清了：自回归逐 token 生成、Prefill 计算密集而 Decode 访存密集、KV Cache 的动态显存、权重与并发之间的容量博弈。这些知识是「材料」，但材料不会自动变成服务。**把「模型权重 + GPU」变成「一个能并发服务几十上百用户、首字快、吐字稳、显存不爆的 API」，中间那一层，就是推理引擎。**

为什么不能直接用 PyTorch 写个 for 循环来服务？单请求当然可以，但请回想第二篇的 Little's Law：2000 个在线用户、每个等 4 秒，意味着 130+ 个请求同时在途。一个朴素循环会逐个处理、其余全部排队——延迟爆炸、显存碎片、批利用率极低。**推理引擎把「服务一个请求」这件简单事，规模化成了「稳定服务一千个请求」这件难事**。它要解决的问题，正是这一节的主题。

## 1 从模型权重到 API 之间，发生了什么

站在用户视角，推理引擎是「喂进 prompt，流出 token」的黑盒。但黑盒里其实是**一条流水线**，每一段都在解决一类独立的问题：

- **加载与布局**：把权重读进显存、安排好 KV 与激活的地盘（第一篇）。
- **计算内核**：把 Prefill 的 GEMM 和 Decode 的注意力跑得尽量接近硬件极限（FlashAttention 等）。
- **显存管理**：KV 随上下文动态增长，怎么分、怎么回收、怎么不碎片化。
- **调度与批处理**：请求随机到达、长度各不相同，怎么拼成高效的批次、满了怎么办。
- **采样与后处理**：温度、top-p、logit bias、停止条件、流式输出——保证「生成」不只是一堆 logits。
- **服务接口**：对外暴露 OpenAI 兼容 API，支撑流式 SSE、鉴权、限流、监控。

引擎 = 这六段流水线的**调度中枢与基础设施**。各家引擎的差异，不在「会不会做其中某一段」，而在「每段怎么做、段与段怎么衔接」。

## 2 五类核心问题：算得对、算得快、装得下、调度得动、服务得稳

把流水线归纳成五个问题族，每个问题族对应引擎的一类核心机制：

**问题一：算得对（正确性）。** 生成不是「算完 logits 就完事」，还要采样：温度、top-p、随机种子、logit 偏置、停止词、结构化输出约束。难在服务要保证「单跑与并发跑结果一致、种子可复现」。<span class="marginnote">「可复现性」是正确性里最容易被忽略的一条：同样的 prompt 与种子，本地单跑和服务器并发跑出的 token 序列应该一致。引擎必须把 CUDA 内核、并行批处理对浮点求和的扰动控制在可接受范围，否则调试「为什么线上和本地输出不一样」会变成噩梦。</span>

**问题二：算得快（性能）。** 把内核逼近硬件上限：注意力用 FlashAttention 系列，GEMM 用 cutlass 级调优，访存带宽榨干。第一篇算过，7B 模型单流在 A100 上约 143 token/s——**引擎的目标是把这条「搬运带宽」真正跑满**，而不是让 CPU 调度开销吃掉大半。

**问题三：装得下（显存）。** 权重常住 + KV 动态增长 + 碎片管理。vLLM 的 PagedAttention 把 KV 切成页、按需分配，把显存利用率从 20%–38% 提到 90%+——这是「装得下更多并发」的物理基础。

**问题四：调度得动（动态性）。** 请求**随机到达**、长度**各不相同**，这是引擎独有的难题。怎么在「填满批次」与「尽快开工」之间权衡？批次满了新请求怎么办（排队、抢占、丢弃）？长输入怎么切（Chunked Prefill）？公共前缀怎么复用（Prefix Caching）？**调度是引擎最核心、也是各家差异最大的战场**，它与第三级《操作系统》的进程调度共享同一套哲学——资源怎么分、谁先谁后、满了怎么办。

**问题五：服务得稳（服务化）。** 对外提供标准接口、流式返回、鉴权限流、监控告警（流式传输的 HTTP 长连接与 SSE 语义，见第三级《计算机网络》）。用户看到的不是「算得快」，而是「稳定、规范、可观测」。

五个问题族与后面各篇的对应关系，先立一张表：

| 问题族 | 引擎的核心机制 | 本博客章节 |
| --- | --- | --- |
| 算得对 | 采样器、约束解码、停止条件 | 第三、四篇 |
| 算得快 | FlashAttention、kernel 融合、投机解码 | 第七篇 |
| 装得下 | PagedAttention、块表、KV 量化 | 第三、六篇 |
| 调度得动 | Continuous Batching、Chunked Prefill、抢占 | 第三篇 |
| 服务得稳 | OpenAI 兼容 API、SSE、负载均衡 | 第九篇 |

## 3 请求的生命周期：引擎的骨架

五个问题族不是五个独立模块，而是串在一条**请求生命周期**上。一个请求从进门到出门，经过：

1. **入队**：请求到达，进入调度器的等待队列（问题四）。
2. **分配 KV 块**：调度器为它划出 KV Cache 的地盘（问题三）。
3. **Prefill**：一次前向把整个 prompt 处理完，产出第一个 token 的 logits（问题二）。<span class="marginnote">Prefill 与 Decode 在生命周期里是<strong>不对称</strong>的：Prefill 只发生一次、计算密集（成本随 prompt 长度涨），Decode 反复执行几千次、访存密集（逐 token 串行）。把两者从调度上拆开、各自放到合适的机器上优化，正是第八篇 PD 分离的动机。</span>
4. **Decode 循环**：逐 token 生成，每步与同批序列同步推进（问题四）。
5. **采样与停止**：从 logits 采样出 token，检查 EOS 与长度上限（问题一）。
6. **流式返回**：每个新 token 立即经 SSE 推给客户端（问题五）。

引擎的所有子系统都能挂在这条生命线上。判断一个引擎设计的好坏，最有效的办法就是**把一个请求从头到尾走一遍，看它每步调用了谁、谁在等谁**。这也是第三篇 vLLM 调度器源码分析的读法。

## 4 公式解析：端到端延迟从哪来

用公式把生命周期翻译成时间，会立刻看出引擎的每个子系统在「优化哪一项」。一个请求的端到端延迟是：

$$T_{\text{e2e}} = T_{\text{queue}} + T_{\text{prefill}} + (n_{\text{out}} - 1) \cdot T_{\text{decode}}$$

逐步拆解：

- **第一步，认排队项 $T_{\text{queue}}$**：请求在队列里等批位的时间。它由「到达率 vs 批容量」的供需决定（第二篇 Little's Law），是**最不可控**的一项，也是 SLO 里最难保证的——突发请求潮一来，它最先爆。
- **第二步，认预填充项 $T_{\text{prefill}}$**：处理整个 prompt 的一次前向，**计算密集**。Prompt 越长越贵：8B 模型在 A100 上，512 token 的 prompt 约 26 ms，4096 token 约 210 ms——它是 $P$ 个 token 一起算，随 prompt 长度近似线性涨。
- **第三步，认生成项 $(n_{\text{out}}-1) \cdot T_{\text{decode}}$**：逐 token 串行，**访存密集**（第一篇）。8B 在 A100 上每 token 约 8 ms，256 个输出 token 就是约 2 秒。它**不可并行**，是长输出请求延迟的大头。
- **第四步，把每项挂到子系统**：$T_{\text{queue}}$ 归调度器，$T_{\text{prefill}}$ 归内核与 Chunked Prefill，$T_{\text{decode}}$ 归注意力内核与批处理效率。**引擎的一切优化，都是在砍这个分解式的某一项**——连续批处理砍 $T_{\text{queue}}$，FlashAttention 砍 $T_{\text{decode}}$，PD 分离（第八篇）把 Prefill 与 Decode 拆到不同机器上分别优化。

代入具体数字看得更清楚：prompt 512 token、输出 256 token、8B FP16 单卡，$T_{\text{prefill}} \approx 26$ ms、$T_{\text{decode}} \approx 8$ ms，则理想情况下：

$$T_{\text{e2e}} \approx T_{\text{queue}} + 26\ \text{ms} + 255 \times 8\ \text{ms} \approx T_{\text{queue}} + 2.07\ \text{s}$$

**生成项占了约 98%**。这解释了为什么长输出场景把宝都押在 $T_{\text{decode}}$ 上：投机解码、KV 量化、FlashDecoding，全是冲着这一项去的。

## 5 为什么训练框架不能直接拿来推理

既然引擎也是「前向计算」，为什么不把 PyTorch、DeepSpeed 直接拿来服务？两者追求的目标差得很远：

| 维度 | 训练框架 | 推理引擎 |
| --- | --- | --- |
| 首要目标 | 吞吐（把数据喂饱，快算梯度） | 延迟与吞吐的平衡（用户体验） |
| 时间敏感度 | 不敏感，慢一点无所谓 | 极度敏感，TTFT/TPOT 是 SLO |
| 请求形态 | 均匀的大 batch，固定形状 | 随机到达、长短不一、动态进出 |
| 显存大头 | 激活（反向传播要存中间值） | KV Cache（逐 token 动态增长） |
| 并发模型 | 数据并行训练，无「服务」概念 | 多用户并发，有排队与抢占 |

一句话概括：**训练是「批处理作业」，推理是「交互式批处理」。** 训练可以等 32 个样本凑齐再算，推理不能等；训练只关心整体吞吐，推理还要保证每个请求不超时；训练显存被激活占满，推理显存被 KV 蚕食。这些差别决定了引擎必须自建调度器、自管 KV、自写流式接口——训练框架给不了这些。这张表的逐条展开，是下一节《推理框架与训练框架的本质区别》的主题。

**辨析｜易错点：**

**误区一：以为推理引擎只是「加速推理的 kernel 库」。** Kernel 只是「算得快」一环；调度、显存、服务化是更核心也更难的部分。vLLM 之所以火，不是因为 kernel 多快，而是 PagedAttention 与调度器把「装得下、调度得动」做到了极致。

**误区二：以为批越大越好。** 第二篇已算过：吞吐随批涨、TTFT 随批涨，天平由业务指标决定。无脑把 batch size 调大，换来的常常是首字变慢、尾延迟失控（第十篇）。

**误区三：把 Prefill 与 Decode 当成同一种优化对象。** Prefill 计算密集、随 prompt 长度线性涨；Decode 访存密集、逐 token 串行。优化两者的手段几乎不重叠——前者靠 GEMM 与切分（Chunked Prefill），后者靠注意力内核与 KV 优化（FlashDecoding、KV 量化）。

## 6 小结

- **引擎 = 流水线**：加载布局、计算内核、显存管理、调度批处理、采样后处理、服务接口六段，各自解决独立问题。
- **五类核心问题**：算得对、算得快、装得下、调度得动、服务得稳——分别对应采样器、FlashAttention、PagedAttention、Continuous Batching、OpenAI 兼容 API。
- **生命周期是骨架**：入队 → 分 KV 块 → Prefill → Decode 循环 → 采样停止 → 流式返回；判断引擎好坏就沿着这条线走一遍。
- **延迟分解**：$T_{\text{e2e}} = T_{\text{queue}} + T_{\text{prefill}} + (n_{\text{out}}-1)T_{\text{decode}}$；长输出下生成项占约 98%，一切优化都是在砍某一项。
- **训练 ≠ 推理**：训练是吞吐优先的批处理作业，推理是延迟敏感的交互式批处理；显存大头从激活换成 KV，随之而来的是调度、排队、流式这些训练框架没有的需求。

在下一节，我们把 vLLM、SGLang、TensorRT-LLM、TGI 四家主流引擎摆上桌：**它们各自针对「五类核心问题」选了哪条技术路线、凭什么站住了脚**——这是「主流引擎对比」的完整图谱。
