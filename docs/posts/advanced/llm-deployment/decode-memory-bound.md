## 为什么把访存瓶颈单独算一笔账

前两节我们已经断言：Decode 是访存受限（memory-bound），算术强度只有约 1 FLOP/byte。但「访存受限」到底意味着什么？它意味着**每生成一个 token，你都在为「把权重搬一遍」付账**，而不是为「计算」付账。这一节我们把这笔账算到毫秒级，得到两个能直接指导部署的结论：单流一个 token 要多少毫秒、批处理为什么是 Decode 的解药。

Roofline 给了上限公式，这一节把公式落成数字。它会反复用到《AI基础设施》的 GPU 指标：A100 的 HBM 带宽约 2 TB/s，H100 约 3.35 TB/s；以及第一级概率论里「平均时间 = 总量 / 速率」这个朴素但核心的模型。

## 1 一次 Decode 前向的「运输清单」

生成第 $t$ 个 token 时，模型要做一次完整前向。为这次前向，数据必须从 HBM 搬到计算单元的东西主要有三样：

- **全部权重**：$N$ 个参数、每个 $b$ 字节，共 $Nb$ 字节。这是大头，而且**必须完整读一遍**——理由见第 3 节。
- **该 token 的激活**：Q、K、V 投影的中间结果，相对权重而言很小。
- **已有的 KV Cache**：注意力要拿新 query 与全部历史位置的 K、V 做点积，所以要把缓存里已有的 K、V 也读出来。短上下文时它比权重小得多，长上下文时会反超——这是第 5 节的伏笔。

三者的体量顺序通常是：**权重 ≫ 激活 > KV（短上下文时）**。长上下文时 KV 反超激活、甚至逼近权重——从「权重受限」到「KV 受限」的转折，就是第 5 节要展开的故事。

以 LLaMA-2 7B、FP16 为例，权重一项就是 $7\times10^9 \times 2 = 14$ GB。<span class="marginnote">对 14 GB 的体量有个直观参照：一张 A100 的 HBM 总容量 80 GB，带宽 2 TB/s——理论上 1 秒能从显存里搬出 2 TB，也就是约 140 个「7B 模型」的权重。可生成速度远没到每秒 140 个 token，见下节的浪费发生在哪里。</span>

## 2 算一算：一个 token 要多少毫秒

Decode 每步的耗时，在访存受限的前提下近似等于「搬完这批字节所需的时间」：

$$t_{\text{token}} \approx \frac{Nb}{\beta}$$

代入数字。**A100 + LLaMA-2 7B（FP16）**：

$$t_{\text{token}} = \frac{14\ \text{GB}}{2\ \text{TB/s}} = \frac{14\times10^9}{2\times10^{12}}\ \text{s} = 7\ \text{ms}$$

换算成速度，每秒 $\approx 1000/7 \approx 143$ 个 token。**H100** 带宽 3.35 TB/s：

$$t_{\text{token}} = \frac{14\ \text{GB}}{3.35\ \text{TB/s}} \approx 4.2\ \text{ms} \approx 239\ \text{token/s}$$

这就是「单流生成」的理论上限。实测往往只能到上限的 60%–80%——真实 kernel 达不到满带宽，还有调度、采样、启动开销——但数量级是稳的：**7B 模型在 A100 上单流大约每秒百来字，这就是 Memory-Bound 的直接后果。**

**辨析｜易错点：** 这里算的是「每步读一遍权重」的搬运时间，不是「整次前向的墙钟时间」。在访存受限区间，两者几乎相等；但如果你只盯着 FLOPs，会觉得 14 GFLOPs 在 A100 上 0.045 ms 就能算完——**计算时间与访存时间差了约 150 倍**，这个倍数正是下一节公式解析的主角。

把不同模型放进同一台 A100，单流的上限一表看清：

| 模型 | FP16 权重 | 单流每 token 时间（A100） | 理论 token/s |
| --- | --- | --- | --- |
| LLaMA-2 7B | 14 GB | ≈ 7 ms | ≈ 143 |
| LLaMA-3 8B | 16 GB | ≈ 8 ms | ≈ 125 |
| LLaMA-2 13B | 26 GB | ≈ 13 ms | ≈ 77 |
| LLaMA-2 70B（张量并行 2 卡） | 140 GB（每卡 70 GB） | ≈ 35 ms | ≈ 29 |

注意 70B 这一行：140 GB 权重放不进单张 80 GB 的卡，必须张量并行（第八篇）拆到两张卡上。每卡各读各的 70 GB，于是每 token 时间由「单卡带宽读单卡权重」决定——**并行没有让单流变快多少，它主要解决的是「放不下」，而不是「读得慢」**。这个区分在选卡与规划集群时极为重要。

## 3 为什么权重必须被完整读一遍

直觉上会问：明明每个权重都被「上一轮」用过，为什么不能留在寄存器里？答案藏在那句「每步只算 1 个 token」里。

Decode 每步的输入宽度是 1 个 token 的隐状态向量，参与一个形状大约为 $[1, d] \times [d, 4d]$ 的 GEMM。**每个权重元素只被这一个向量乘一次**，没有第二个数据点来复用它——数据依赖决定了它读完即用、用完即弃。对比 Prefill，宽度是 $P$，同一个权重被 $P$ 个位置复用 $P$ 次，于是能住在片上缓存里反复取用。

这就是 Memory-Bound 的根源：**权重总量不变，但 Decode 让「每个字节被使用的次数」降到了 1**。你可以把它想成一家只卖单件的仓库：每次取货都要把整座仓库搬一遍，哪怕只取一件。想摊薄成本，只有两个办法——把取货量变大（批处理，第 5 节），或者让仓库变轻（量化，第六篇）。

## 4 公式解析：访存时间为什么是计算时间的 150 倍

把「Memory-Bound」从形容词变成可计算的比例。记算力为 $\pi$（A100 约 312 TFLOPS），带宽为 $\beta$（约 2 TB/s）。

**第一步，写计算时间**：每 token 运算量 $\approx 2N$，所以：

$$t_{\text{compute}} = \frac{2N}{\pi}$$

**第二步，写访存时间**：每 token 搬运 $Nb$ 字节，所以：

$$t_{\text{memory}} = \frac{Nb}{\beta}$$

**第三步，作比**：两式相除，$N$ 约掉：

$$\frac{t_{\text{memory}}}{t_{\text{compute}}} = \frac{Nb/\beta}{2N/\pi} = \frac{b\pi}{2\beta}$$

**第四步，代入 A100（FP16，$b=2$）**：

$$\frac{b\pi}{2\beta} = \frac{2 \times 312\times10^{12}}{2 \times 2\times10^{12}} = 156$$

也就是说：**在 A100 上，Decode 每步花在「搬权重」上的时间，约是「算权重」的 156 倍**。所谓 Memory-Bound，就是这 156 倍的失衡。若换成 INT8（$b=1$），比值降到 78——字节减半，失衡减半，这正是量化加速 Decode 的全部秘密。

用 H100 再验算一次：$b\pi/(2\beta) = 2\times989\times10^{12}/(2\times3.35\times10^{12}) \approx 295$。**新一代硬件把「Memory-Bound」推得更深**——算力涨得比带宽快，失衡倍数不减反增，这让量化与 KV 优化的价值在新卡上更加显著。<span class="marginnote">观察公式 $b\pi/(2\beta)$：它不是固定常数，而是 $\pi/\beta$（机器平衡）与 $b$（精度）的乘积。这也解释了为什么「机器平衡」$M=\pi/\beta$ 是计算机体系结构教科书里的核心概念——<strong>一台机器的算力越强而带宽不变，访存受限的计算就越吃亏</strong>。</span>

## 5 批处理：如何把权重复用摊薄

单流 Decode 每秒百来 token，对一个大模型服务显然不够。出路是把多个请求**拼成一个批次（batch）**：同一轮前向，$B$ 个序列的 token 一起算。

关键洞察：**权重是共享的。** 无论批里有 1 个还是 32 个序列，每步都要读同样的 14 GB 权重；读一次，喂给 32 个序列的 32 个 token 同时算。于是每步总吞吐几乎翻到 $B$ 倍，每个序列的等效每-token 成本几乎降到 $1/B$：

$$\text{Throughput} \approx B \times \frac{\beta}{Nb} \ \ \text{token/s}$$

$B=32$ 时，理论上限从约 143 涨到约 $32 \times 143 \approx 4600$ token/s——**批处理把「读一遍权重」的固定成本摊到了更多序列头上**，这就是 Continuous Batching（第三篇）的原始动机。当然它不会无限涨：当批足够大，每步要算的 FLOPs 追上算力屋顶，Decode 就从访存受限翻转为计算受限，吞吐曲线从此封顶——这条曲线的形状，正是第十篇压测要测量的东西。

批处理不是白赚的：同一批里的序列要等最慢的一个算完才能一起前进，**单条序列的延迟会随批大小上升**。吞吐与延迟这对此消彼长的矛盾，是推理服务最核心的权衡——压测报告里「吞吐涨了」和「TTFT 变长了」往往同时出现，第十篇会专门把这条曲线测给你看。

翻转到计算受限的批大小可以直接解出来：令每步运算量等于算力，$2NB = \pi$，即 $B = \pi/(2N)$。对 7B 与 A100：$B \approx 312\times10^{12}/(14\times10^9) \approx 2.2$ 万。<span class="marginnote">这个 $B\approx2.2$ 万是「纯 Decode 也要把算力吃满」的理论批大小——但工程上远在此之前就撞上别的墙：KV Cache 一节算过，$S=100$ 个并发序列就要 50 GB+ 显存，而一张 A100 只有 80 GB。所以 <strong>Decode 在真实部署里几乎永远是访存受限的</strong>，批处理的上限往往由显存容量而不是算力决定。</span> 这也解释了为什么引擎层要拼了命地压 KV 显存（分页、量化、GQA）——把 $S$ 推上去，就是把吞吐推上去。

**辨析｜易错点：** 长上下文时，「权重是最大搬运项」的说法会失效。每步还要读已有的 KV Cache 参与注意力，量是 $2LH_{kv}db \cdot T$。LLaMA-2 7B 每 token KV 约 0.5 MB，$T$ 超过约 2.8 万 token 时，KV 的读取量反超权重（14 GB）；LLaMA-3 8B 每 token KV 约 128 KB，反超点约在 12.8 万 token。**超长上下文服务的 Decode 瓶颈不是权重，而是 KV Cache**——这正是 KV Cache 量化（第六篇）与 FlashDecoding（第七篇）要解决的事。

## 6 小结

- **运输清单**：Decode 每步必须完整读一遍权重（$Nb$ 字节），外加随上下文增长的 KV Cache 读取。
- **每 token 时间**：$t_{\text{token}} \approx Nb/\beta$——7B FP16 在 A100 上约 **7 ms**（≈143 token/s），H100 上约 **4.2 ms**（≈239 token/s）。
- **失衡倍数**：$t_{\text{memory}}/t_{\text{compute}} = b\pi/(2\beta) \approx 156$（A100 FP16），这就是 Memory-Bound 的量化含义。
- **批处理解药**：权重共享使吞吐近似随批大小线性增长，$B$ 越大越逼近算力屋顶。
- **长上下文的例外**：KV Cache 读取量随上下文线性增长，超长场景下 Decode 从「权重受限」翻转为「KV 受限」。
