## 为什么从批处理谈起

上一节我们把单条序列的 KV 管理做成了 O(1) 的块表。但服务端要面对的不是一条序列，而是一大群并发请求。**吞吐的关键在于批处理（batching）**：把多条请求合成一批，一次 GPU kernel 调用处理一批 token，把显存带宽和算力摊薄。

而「怎么批」，恰恰是静态批处理最反直觉的地方。先看一个残酷的数字：**若按「整批一起开始、一起结束」的静态批处理，一批请求的 GPU 利用率常常只有六成到八成**——剩下的时间 GPU 在等最长的那条序列。这一节要讲的 Continuous Batching，就是把这个浪费捡回来：**每一步都重新决定「谁在批里」。**

## 1 静态批处理的瀑布效应

假设 4 条请求在完成预填充后，还要分别再生成 4、6、8、10 个 token（为简化，每步一 token）。静态批处理的规则是：**整批一起跑，整批一起停**。于是批大小恒为 4，直到最长的 R4 在第 10 步结束。

问题一眼可见：第 5 步起，R1 已经生成完却还占着批里的槽位；第 7 步起 R2 也完了；第 9 步起只剩 R3、R4。<span class="marginnote">这个「长尾拖着整批走」的现象在工程里叫<strong>瀑布效应（waterfall effect）</strong>，在操作系统的调度里叫<strong>队头阻塞（head-of-line blocking）</strong>——本质是同一个东西：短任务被长任务堵在队列里。</span>GPU 不会因为槽位空着就把算力让给别人，它只会空转。

更糟的是「空转」的代价不对称。**Decode 阶段是访存瓶颈（Memory-Bound）**，见第一篇《访存瓶颈：为什么 Decode 是 Memory-Bound》：每生成一个 token，瓶颈在把整段 KV 读一遍，算力还有大量富余。所以批里多一条序列、少一条序列，**算力上几乎无感，但吞吐上实打实差出一条序列的量**。静态批处理把这种「每条序列独立的完成时间」强行焊成一体，等于主动放弃了一批内存带宽。

## 2 连续批处理：按迭代步重组批

Continuous Batching（论文里也叫 iteration-level scheduling）改了一条规则：**批的组成不是请求进来时决定的，而是每一步 Decode 结束之后重新决定的。** 每完成一个解码迭代：

1. **踢出完成的**：产生 `<eos>` 或达到 `max_tokens` 的请求，立刻离开批，其 KV 块归还（走上一节的 `free`）。
2. **补进新请求**：只要有等待中的请求、且显存（KV 块）与批大小有富余，就从等待队列补一条进来。
3. **剩下的继续**：批里剩余请求一起做下一个解码迭代。

于是批大小随时间自动伸缩：4、4、4、4、3、3、2、2、1、1，新请求可以随时顶上空位。**没有「批」这个概念本身**——只有「这一迭代步里活跃的请求集合」。<span class="marginnote">「连续」二字的意思是：批的边界在每一步之间是连续的、动态的，而不是在请求之间切成固定的一坨。vLLM 论文里把这一机制列为吞吐提升的第一来源，实验里比静态批处理高 2 倍以上。</span>

这里有一个前提值得点破：**连续批处理必须建立在上一节的块表之上**。因为请求随时进出，KV 必须按需增减、无碎片回收——连续分配做不到，这正是两节之间的因果链。

## 3 vLLM 的调度器：三队列模型

vLLM 用一个调度器（`Scheduler`）实现连续批处理，内部维护三个队列：

- **WAITING（等待）**：已到、尚未开始预填充的请求。
- **RUNNING（运行）**：正在预填充或解码的请求，每一步都参与迭代。
- **SWAPPED（换出）**：因显存不足被换到 CPU 的请求，等待被换回（第三节后续专门讲）。

每个迭代步，调度器做三件事：**从 WAITING 挑请求进入 RUNNING**（受 `max_num_seqs` 与 KV 余量约束）→ **让 RUNNING 跑一步** → **把完成的请求送走、处理抢占**。<span class="marginnote">两个核心配置：`max_num_seqs` 限制批里最多多少条序列；`max_num_batched_tokens` 限制一步里批内 token 总数上限（vLLM 默认 256）。后者是下一节 Chunked Prefill 的旋钮。</span>新请求能进批的条件是：RUNNING 未满、且有足够 KV 块容纳它的前缀——这一步要查块分配器的空闲块数。

伪代码把「每步重组」写得很直白：

```python
def step(scheduler):
    # 1. 换入/换出处理（显存不足时抢占，见后续章节）
    # 2. 把等待中的请求补进 RUNNING，只要显存与批大小允许
    while scheduler.waiting and can_admit(scheduler):
        seq = scheduler.waiting.pop()
        scheduler.running.append(seq)

    # 3. 让 RUNNING 里的所有请求各解码一步（合批成一个 GPU kernel）
    outputs = decode(scheduler.running)

    # 4. 处理完成/失败的请求，释放其 KV 块
    for seq, out in zip(scheduler.running, outputs):
        if out.is_finished():
            block_allocator.free(seq.kv_blocks)      # ref_count 递减
            scheduler.running.remove(seq)
```

注意第 3 步：**批里所有请求仍然共享一次 kernel 调用**。连续批处理改变的是「批的边界」，不是「批的粒度」——合批带来的显存带宽摊薄收益一点不少。

## 4 公式解析：气泡率与静态批的浪费

把静态批处理的浪费量化成一条公式。设批里有 $n$ 条请求，第 $i$ 条的解码步数为 $l_i$，最长的为 $l_{\max}$。静态批处理固定批大小 $n$ 跑满 $l_{\max}$ 步，则**利用率**：

$$
\eta_{\text{static}} = \frac{\sum_{i=1}^{n} l_i}{n \cdot l_{\max}}
$$

逐步拆解：

- **第一步，认分子**：$\sum l_i$ 是所有请求真正需要的解码工作量——单位是「序列·步」，这是刚需。
- **第二步，认分母**：$n \cdot l_{\max}$ 是静态批处理实际消耗的「批·步」。批大小 $n$ 恒定，一直跑到最长的 $l_{\max}$。
- **第三步，看浪费**：分子 ≤ 分母，差值就是**气泡**（bubble）——GPU 在等长尾的空白期。代入 4、6、8、10 的例子：$\eta = 28/(4 \times 10) = 70\%$，即 **30% 的 GPU 时间被瀑布效应浪费**。
- **第四步，看趋势**：请求越短、长短越不齐，$\eta$ 越低。若 8 条请求的解码步数从 2 到 16 均匀分布，$\eta = 72/128 = 56.25\%$——**请求越杂，静态批处理越浪费**。

连续批处理没有固定的 $n$ 和 $l_{\max}$，批大小每步随存活请求数变化，气泡只剩「请求进出批那一瞬间的调度延迟」，趋近于 0。<span class="marginnote">这正是「吞吐优先」哲学的第一课：在 Memory-Bound 的 Decode 阶段，把批尽量喂满比任何单请求的优化都划算——批满则带宽用尽，带宽用尽则吞吐封顶。</span>第一篇《推理吞吐、延迟与批大小的基本关系》里我们见过吞吐随批大小近乎线性上升，连续批处理就是「让批大小尽量时刻等于允许的上限」的机制。

## 5 为什么 Decode 阶段的合批几乎免费

连续批处理能捡回这么多吞吐，底层原因在 Decode 的资源画像：**Decode 是访存受限，不是算力受限**（第一篇《访存瓶颈：为什么 Decode 是 Memory-Bound》）。每一步只生成一个 token，SM 算力利用率很低，真正卡住吞吐的是显存带宽。于是给批里多塞一条请求，多出来的边际成本只是「把这条序列的 KV 也读一遍」的带宽需求；只要带宽还没用满，**合批的边际成本接近零，边际收益却是一条完整的吞吐**。

把这条直觉写成式子。设 GPU 显存带宽为 $BW$，单条序列每步要读取的 KV 字节数为 $m_{\text{kv}}$，则单步能合批的上限大约是：

$$
n_{\max} \approx \frac{BW}{m_{\text{kv}}}
$$

逐步拆解：

- **第一步，认分子 $BW$**：Decode 每步的吞吐上限由带宽决定，A100 的 HBM 带宽约 2 TB/s。
- **第二步，认分母 $m_{\text{kv}}$**：一条序列每步要把整段 KV 读一遍，$m_{\text{kv}} = \text{层数} \times 2 \times \text{KV head} \times \text{head\_dim} \times 2\text{ B} \times \text{序列长度}$——序列越长，单步读得越多，能合批的请求数越少。
- **第三步，看上限**：$n_{\max}$ 往往远大于算力允许的批大小。所以「批喂得越满越好」只对 Memory-Bound 阶段成立；若把同样逻辑套到 Compute-Bound 的 Prefill 上，批大小被算力锁死，堆再多请求也只是排队。

理解「带宽决定批上限」，就理解了连续批处理为何在 Decode 上立竿见影——它做的就是把批大小实时顶到这个带宽上限附近。<span class="marginnote">这也暗示了长序列服务的另一条出路：既然 $m_{\text{kv}}$ 随序列长度线性涨，长请求会压低能合批的请求数——这正是后面分布式章节里 PD 分离、KV Cache 分片要解决的动机。</span>

## 6 辨析｜易错点

**辨析｜易错点：**

- **误区一：把 Continuous Batching 当成「动态批处理」（dynamic batching）。** 推理服务框架（如 Triton Inference Server）里的 dynamic batching 是「攒够一定请求或等待一定超时再一起发」，批的边界仍是离散的；Continuous Batching 在**每一步迭代**之间重组批，粒度小了一个数量级。后者是 vLLM 的核心创新，前者是通用调度技巧。
- **误区二：以为它「把批拆成一条条跑」。** 恰恰相反，它仍是合批的——每一步的所有活跃请求合成一个 kernel。变的是**批的边界**，不是**批的粒度**。
- **误区三：以为增大 `max_num_seqs` 一定更好。** 不是。批越大，单步延迟越高（见第一篇吞吐-延迟权衡）；且 KV 显存有限，批上限最终由块分配器的空闲块数决定。`max_num_seqs` 是显存、延迟、吞吐三方折中的旋钮。
- **误区四：以为 EOS 之后立刻释放。** 释放发生在迭代步末尾统一处理，且受引用计数保护——共享块（上一节）要等所有引用者都结束时才真正归还。

## 7 小结

- **静态批处理的病灶**：批固定 → 长尾拖着短请求 → 气泡率 $\eta = \sum l_i / (n \cdot l_{\max})$，4 条请求的例子浪费 30%。
- **连续批处理的药方**：迭代级调度——每步踢出完成的、补进等待的，批的边界连续可动。
- **依赖块表**：请求随时进出要求 KV 按需增减、无碎片，块表是前提。
- **三队列模型**：WAITING / RUNNING / SWAPPED，调度器每步「准入 → 解码 → 清理」。
- **合批不变**：批的粒度不变，变的只是批的边界；Decode 是 Memory-Bound，批满收益巨大。
- **辨析**：不同于 dynamic batching；`max_num_seqs` 是折中不是越大越好。
