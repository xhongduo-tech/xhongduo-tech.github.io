## 为什么从自建 vs API 开始

最后一个决策问题：**模型服务是自建还是调用 API？** 这是每一家要落地 LLM 的公司都会问的问题。答案不是「自建省钱」或「API 省事」二选一，而是由「用量、规模、时延、数据、团队能力」共同决定的成本权衡。本篇给出决策框架：何时自建划算、何时 API 划算、以及混合形态。<span class="marginnote">本专题《单 token 成本》给了成本的分子分母；本篇把它变成<strong>决策框架</strong>——用量达到「盈亏平衡点」就自建，否则调用 API。这个点在哪，是全部问题。</span>

## 1 两边的成本结构

**调用 API**：按 token 计费，单价透明（如 GPT-4o 输入 $5/百万、输出 $15/百万）。无固定成本、无运维、无限扩容。**成本 = 单价 × 用量**。

**自建集群**：固定成本高（GPU 采购/租用 + 人力运维）、可变成本低（电费，见成本模型篇）。**成本 = 固定摊薄 + 可变**，且**随用量增长呈「阶梯」而非线性**——现有集群够用时不加成本，容量不足时要跳一级。

两个结构的交点就是决策分界：**用量低时 API 便宜，用量高时自建便宜**。<span class="marginnote">成本曲线交点的直觉：<strong>API 是「随用随付」的斜线，自建是「先付后摊」的阶梯</strong>。斜线与阶梯第一次相交的用量，就是盈亏平衡点。</span>

## 2 影响决策的五个维度

成本只是决策的一维。完整权衡要过五个维度：

**用量规模**：决定性因素。月 token 量低于平衡点 → API；远高于 → 自建。
**延迟与可用性**：API 有网络往返 + 第三方不可控；自建可优化到极致（本专题全部优化手段）。**延迟敏感型业务倾向自建**。<span class="marginnote">「延迟」是成本表里没有、却最影响体验的维度：<strong>一个 P99 要求 <200ms 的业务，API 的网络往返（50–200ms）就吃掉大半预算</strong>，此时自建是「能力必需」而非「成本选择」。</span>
**数据合规**：敏感数据出境的合规成本——医疗、金融、企业内部数据。**合规要求数据不出门时，自建几乎是唯一选择**。
**团队与运维**：自建需要 GPU 运维、模型调优、监控告警的人。**没有团队，自建的隐性成本（人力）可能超过省下的钱**。
**模型可替换性**：依赖特定模型（如未来换更强模型）时，API 更灵活；要长期用固定模型时，自建的定制化（微调、量化、私有化）是优势。

## 3 混合形态与渐进路径

现实往往不是二选一，而是「混合 + 渐进」：

**混合路由**：简单/低敏任务走自建小模型、复杂/高敏任务走 API 大模型（见端云协同篇的任务路由）。
**渐进路径**：从「全 API」起步验证业务 → 用量上升后「自建 + API 兜底」→ 稳定后「主力自建 + API 备灾」。**沿着用量曲线渐进迁移，避免一次性重投入**。
**云 GPU 中间态**：租用云 GPU（按小时）自建——**介于「买卡自建」与「调用 API」之间**：有自建的灵活性、无采购的沉没成本。<span class="marginnote">云 GPU 是「<strong>租赁的自建</strong>」：按小时计费、弹性扩缩容、不用管硬件寿命。<strong>它是自建与 API 之间的甜区</strong>——团队能自己调优引擎、又不想承担采购风险时的首选。</span>

**辨析｜易错点：别把「API 单价」与「自建单 token 成本」直接比。** 自建成本模型里的「单 token 成本」是**满利用率下的摊薄**（见成本模型篇）——利用率 20% 时自建的单 token 成本是满利用率的 5 倍。**拿「理论满负荷成本」对比「API 单价」会得出「自建很便宜」的错误结论**——要按「实际可达利用率」算。

## 4 公式解析：盈亏平衡点

自建与 API 的平衡点。设 API 单价 $p_{\text{api}}$（$/token）、自建固定成本 $C_{\text{fixed}}$（$/月，含折旧 + 人力）、自建可变成本 $c_{\text{var}}$（$/token，电费）、月用量 $N$：

- **第一步，写两边月成本**：API：$C_{\text{api}} = p_{\text{api}} \cdot N$；自建：$C_{\text{self}} = C_{\text{fixed}} + c_{\text{var}} \cdot N$。
- **第二步，解平衡点**：令 $C_{\text{api}} = C_{\text{self}}$，得

$$N^* = \frac{C_{\text{fixed}}}{p_{\text{api}} - c_{\text{var}}}$$

- **第三步，读含义**：$N^*$ 是「月 token 用量」的盈亏平衡点。$N > N^*$ 自建省钱，$N < N^*$ API 省钱。代入数字：$C_{\text{fixed}}$ = $5k/月（折旧+人力+运维），$p_{\text{api}} - c_{\text{var}}$ = $5/百万 token，则 $N^*$ = 10 亿 token/月——**月用量超过 10 亿 token，自建才省钱**。这个量级对大多数业务并不小，解释了为什么「多数公司用 API 更划算」。

## 5 数值算例：一个 50M 月 token 请求团队的决策

把前面的框架落到一个具体团队上。设某客服产品月请求 1000 万次、平均每次 5 千 token，月 token 量 $N = 500$ 亿。候选方案：调用 API（输入 $3/百万、输出 $15/百万，混合约 $6/百万）vs 自建 4×H100 集群。

先算自建的固定与可变成本：

| 成本项 | 月金额 | 说明 |
| --- | --- | --- |
| 4×H100 折旧 | $8,000 | 采购约 25 万、按 3 年直线折旧 |
| 机房/电费/网络 | $2,000 | 4 卡满载约 12 kW |
| 运维人力（0.5 人） | $5,000 | GPU 运维、模型调优、值班 |
| 合计固定 $C_{\text{fixed}}$ | $15,000/月 | 与用量无关 |

可变成本 $c_{\text{var}}$ 主要是电费与折旧外损耗，约 $0.2/百万 token，相对 API 单价可忽略。于是盈亏平衡点：

$$N^* = \frac{C_{\text{fixed}}}{p_{\text{api}} - c_{\text{var}}} = \frac{15{,}000}{6 \times 10^{-6} - 0.2 \times 10^{-6}} = 2.6 \text{ 亿 token/月}$$

**代入数字读结论**：这个团队月用量 500 亿 token 远超平衡点 2.6 亿，自建显然更省钱——但自建要同时满足「延迟/合规/团队」三个条件。对照五个维度：

- **用量**：500 亿 >> $N^*$，成本上自建占优（估月省 15–20 万）。
- **延迟**：客服对延迟不极端敏感（P99 < 2s 即可），API 尚可——**延迟维度不强制自建**。
- **合规**：客服对话含客户手机号，出境有合规风险——**合规强烈倾向自建**。
- **团队**：已有 2 名推理工程师——**团队可行**。
- **模型可替换性**：长期用固定模型做客服——**自建定制化优势成立**。

五个维度里成本、合规、团队、可替换都指向自建，只有延迟不痛不痒。

**结论：自建**——而且不是「为了省钱」，是「合规 + 成本 + 定制」三重合力的结果。

**辨析｜易错点：别把「月 token 量大」直接当成「该自建」。** 上面的数字只对「固定模型、稳定用量」成立。如果团队频繁换模型、流量波动大（平时 10 亿、活动日 100 亿），自建的阶梯成本（要按峰值买卡）会吃掉闲置期的摊销，**此时云 GPU 中间态或「自建保底 + API 弹性兜底」更稳**。

## 6 自建的隐性成本清单

盈亏平衡点只算了显性成本，自建还有三笔常被低估的隐性账：

**第一笔：GPU 利用率是假的。** 自建成本模型里的「单 token 成本」假设满利用率。客服产品有波峰波谷，平均利用率常只有 40–60%。**利用率 50% 意味着单 token 成本翻倍**——算平衡点时要把「实际可达利用率」乘进固定成本，而不是拿满负荷算。

**第二笔：模型升级的再训练与再验证。** 换模型不是「换一个 checkpoint」：要做评测、对齐基线、灰度、回滚演练，每次升级都要工程师投入。**API 时代升级是「改一个 model 名」，自建时代升级是「一次小型项目」**。

**第三笔：故障与容量规划的保险成本。** 自建集群要备冗余（备卡、备电、多 AZ），要为「QPS 突增」预留余量。**这些「为不确定性买单」的成本在 API 账单里是隐藏的**（API 自带弹性），在自建预算里必须显式列出来。

把三笔隐性账加起来，很多「理论平衡点达标」的团队实际并不省钱——**判断自建时，先把隐性成本列满，再算平衡点**。

把「该不该自建」各列一条，方便快速对照：

- **果断自建**：月用量远超平衡点 + 数据敏感 + 有团队 + 模型长期固定——四者缺一不可。
- **先别自建**：模型迭代快、流量波动大、团队不足 1 人、延迟不敏感——四条占两条以上就先用 API。
- **云 GPU 中间态**：想自建但怕采购风险、怕模型换代——按小时租卡把自建的灵活性先用起来。
- **API 兜底**：自建集群打满时把溢出流量切给 API，用「自建保底 + API 弹性」同时拿到成本与稳定。

这四条不是成本计算的替代，而是「算完之后」的常识检查——**数字算对是第一步，决策对还要靠维度对照**。

## 7 小结

- **成本结构对比**：API 是「按量斜线」，自建是「先付后摊的阶梯」，交点即盈亏平衡点 $N^* = C_{\text{fixed}}/(p_{\text{api}} - c_{\text{var}})$。
- **五个决策维度**：用量规模、延迟可用性、数据合规、团队运维、模型可替换性——成本只是其一。
- **延迟与合规常是「能力必需」**：即使 API 更便宜，延迟敏感与数据敏感业务也倾向自建。
- **混合与渐进**：任务路由、从全 API 渐进迁移、云 GPU 中间态，都是更稳妥的路径。
- **别拿理论摊薄对比 API 单价**：按实际可达利用率算，多数业务月用量低于平衡点，API 更划算。
- **隐性成本三笔账**：真实利用率、模型升级再验证、冗余与容量保险——列满再算平衡点，很多「达标」团队其实不省钱。
