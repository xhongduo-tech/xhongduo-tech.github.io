## 为什么从吞吐与 QPS 开始

服务能扛多大流量、该设多少并发上限、扩容能带来多少收益——这些问题的答案都藏在「吞吐-延迟-并发」的关系曲线里。LLM 推理的特殊之处是：**并发 = batch 大小**（每增加一个并发请求，批就多一个序列），而 batch 对吞吐与延迟的影响是非线性的。理解这条曲线，是压测与容量规划的核心。<span class="marginnote">本专题《Continuous Batching》讲过「批越大吞吐越高」，但那有前提：<strong>批大到一定程度，延迟爆炸、吞吐反而可能下降</strong>。本篇用排队论的语言把这条曲线讲清楚。</span>

本篇讲吞吐（QPS/TPS）与并发的关系、Little's Law 如何连接吞吐与延迟、以及「拐点」为什么存在。

## 1 吞吐的两个口径

先厘清「吞吐」的两个口径：

**QPS（每秒请求数）**：服务每秒完成多少个请求。反映「请求级」吞吐。
**TPS（每秒 token 数）**：服务每秒生成多少个 token。反映「计算级」吞吐。

两者的关系：**QPS = TPS / 平均生成长度**。一个服务 TPS=100k，平均每个回答 500 token，则 QPS = 200。**压测要同时看两个口径**——QPS 受生成长度分布影响，TPS 反映算力利用。<span class="marginnote">生成长度分布的差异会让「QPS 看起来一样但 TPS 差 10 倍」——<strong>报告吞吐时必须注明平均/分位生成长度</strong>，否则数字没有可比性。</span>

## 2 吞吐-并发曲线的形状

画「并发数 × 吞吐」的曲线，典型的 LLM 服务呈现三段式：

1. **线性区**：并发低时，每个请求都能立即进入 batch，吞吐随并发近似线性增长——GPU 利用率在爬升。
2. **饱和区**：并发继续增加，GPU 的批已经「满载」（算力或显存打满），吞吐增速放缓，趋近平台——**这是服务的「甜点区」**。
3. **过载区**：并发超过某阈值，排队急剧加长、KV Cache 吃紧甚至需要换出，**吞吐开始回落或持平，延迟爆炸**——这是「拐点」之后。

**拐点（knee point）**：吞吐曲线由「增长」转向「平台/回落」的那个并发点。它是服务容量规划的核心数字：**在拐点附近运营，吞吐与延迟的平衡最好**。<span class="marginnote">拐点不是一条线，是一个带：<strong>不同 prompt 长度、不同生成长度下，拐点位置不同</strong>。长输入 + 长输出的负载，拐点比短请求低得多——容量规划要按「最重负载」定拐点。</span>

延迟曲线的形状是另一面：**并发低时延迟低且稳，并发接近拐点时延迟开始上翘，过拐点后 P99 垂直起飞**。吞吐与延迟是同一枚硬币的两面——**「拐点」既是吞吐的峰值点，也是延迟的失稳点**。

## 3 Little's Law：连接吞吐与延迟

把「吞吐、并发、延迟」联系起来的核心定律是 **Little's Law**（排队论的基本定律）：

$$L = \lambda \cdot W$$

$L$ 是系统中请求数（并发），$\lambda$ 是到达/完成率（吞吐），$W$ 是每个请求在系统中的平均时间（延迟）。<span class="marginnote">Little's Law 的直观意义：<strong>系统里有多少请求，等于「每来多少」乘以「每个待多久」</strong>。它不依赖具体分布，是排队论里最通用的关系。</span>

对 LLM 服务，改写为：**并发 = QPS × 平均端到端延迟**。这意味着：给定目标延迟（如 P95 < 2 秒）与目标 QPS，并发是两者乘积——**你不能同时要求「极高吞吐」与「极低延迟」，因为并发（batch）是连接它们的硬约束**。

## 4 公式解析：从曲线读出容量

用 Little's Law 做容量规划。设目标 QPS 为 $\lambda$，目标端到端延迟上限 $W_{\max}$，则所需并发：

$$L_{\text{req}} = \lambda \cdot W_{\max}$$

- **第一步，读约束**：如果 $L_{\text{req}}$ 超过了服务的「拐点并发」$L_{\text{knee}}$，则该 QPS 在目标延迟下**不可达**——要么降 QPS，要么放宽延迟，要么扩容。
- **第二步，读扩容的意义**：扩容（加实例）不改变单实例的拐点，但把「请求分配到多实例」——每实例的并发降回拐点以下。**容量 = 单实例拐点 × 实例数**。
- **第三步，读 batch 的影响**：$W_{\max}$ 越严、$\lambda$ 越高，$L_{\text{req}}$ 越大，batch 越大——而 batch 大伤延迟。**这解释了为什么「既要高 QPS 又要低延迟」的唯一解是「更多实例」而非「更大 batch」**。

实测上的读数方法：压测出「并发-吞吐-延迟」三曲线，找到吞吐拐点 $L_{\text{knee}}$，对照目标延迟确认运营点，反推实例数。

## 5 数值算例：一条真实的吞吐曲线

把三段式曲线落到一组具体数字。设某 8×H100 服务、固定「512 输入 + 512 输出」token，并发从 1 扫到 256：

| 并发 L | 吞吐（QPS） | P99 延迟（s） | 阶段 |
| --- | --- | --- | --- |
| 1 | 0.9 | 0.8 | 线性区 |
| 8 | 6.8 | 1.0 | 线性区 |
| 32 | 22 | 1.6 | 饱和区前 |
| 64 | 30 | 2.5 | 拐点附近 |
| 128 | 31 | 6.0 | 过载区 |
| 256 | 29 | 15.0 | 过载区 |

**逐行读**：

- **线性区（1→32）**：吞吐从 0.9 涨到 22，几乎随并发线性——GPU 利用率在爬升。
- **拐点（≈64）**：64 并发时吞吐 30 接近峰值，P99 2.5s 尚可；128 并发吞吐只到 31（+3%），但 P99 跳到 6s——**过了拐点，吞吐不涨、延迟爆炸**。
- **过载区（128→256）**：256 并发吞吐反而回落到 29，P99 冲到 15s——**排队主导，体验断崖**。

**读这张表的决策**：若目标 P99 ≤ 3s，只有并发 ≤ 64 达标。代入 Little's Law：$L = \lambda \cdot W$，目标 QPS 30、延迟 2.5s，则 $L_{\text{req}} = 75$——超过单实例拐点 64，**需要扩容**。**「目标 QPS × 目标延迟」算出的并发，和「单实例拐点」一对比，该不该加实例立刻清楚**。<span class="marginnote">这张表同时说明：<strong>峰值吞吐（31 QPS）只出现在过载区，P99 已爆炸</strong>——报「峰值吞吐」要同时报当时的 P99，否则是误导。</span>

## 6 扩容与运营的决策

从曲线出发，把「运营」与「扩容」变成可执行动作：

**运营动作**：给服务设并发上限（限流），让它永远工作在拐点以下——超过就拒绝或排队。**限流阈值 = 拐点并发 × 安全系数**（如 0.8）。这一条就避免了「高峰把服务压进过载区」。

**扩容动作**：当「目标 QPS × 目标延迟」持续超过拐点时，加实例。**容量 = 单实例拐点 × 实例数**——加实例让每实例并发回到拐点以下，吞吐线性翻倍（前提是负载均衡到各实例）。

**三个常被误读的数字**：

| 数字 | 误区 | 正确读法 |
| --- | --- | --- |
| 峰值吞吐 | 当成运营容量 | 在过载区，P99 已炸，只能当硬件上界 |
| 拐点吞吐 | 当成目标运营点 | 拐点是上限，运营取拐点 × 0.8 |
| 单并发延迟 | 当成真实延迟 | 无排队、batch=1，与真实并发无关 |

**辨析｜易错点：别把「曲线测一次」当成「容量定了」。** 曲线的拐点随请求画像（输入/输出长度、并发模式）变化。**线上画像漂移后，原拐点数字会静默失效**——要按「最重负载」定运营点，并周期性重测曲线（见并发实验篇的回归）。

把吞吐-并发曲线相关的常见误读列成速查：

| 误读 | 真相 |
| --- | --- |
| 「并发越高吞吐越高」 | 过拐点后吞吐持平甚至回落 |
| 「平均延迟 1s 就是 1s」 | 要看 P99，长尾可能 5s+ |
| 「峰值 QPS 是运营容量」 | 峰值在过载区，P99 已炸 |
| 「加 batch 就能提吞吐」 | batch 大到一定程度伤延迟、伤吞吐 |
| 「曲线是固定的」 | 随请求画像漂移，要重测 |

**读这张表**：曲线相关的大部分「翻车」，都是把「瞬时/平均/峰值」当成了「可持续/分布/运营」数字。**报任何吞吐数字，都要带上「并发 + P99 + 请求画像」**——这才是可复现、可决策的完整信息。

**一个运营动作的落地**：把「拐点并发 × 0.8」设成限流阈值，写入网关（见服务化篇的 API 网关限流）——**曲线测出来的结论，要落到「限流阈值」这个可执行配置上**，才完成了从测量到运营的闭环。

## 7 小结

- **两个吞吐口径**：QPS（请求级）与 TPS（token 级），QPS = TPS/平均生成长度，报告必须注明长度分布。
- **吞吐-并发三段式**：线性区 → 饱和区 → 过载区；拐点是吞吐峰值点也是延迟失稳点。
- **Little's Law**：并发 = QPS × 平均延迟，连接吞吐与延迟的硬约束。
- **容量规划**：所需并发 = 目标 QPS × 目标延迟，超过拐点则需降 QPS 或扩容。
- **「高吞吐 + 低延迟」的唯一解是更多实例**：batch 越大延迟越伤，不能靠压单实例。
- **运营取拐点 × 0.8**：限流阈值 = 拐点 × 安全系数；容量 = 单实例拐点 × 实例数；曲线要随画像重测。
