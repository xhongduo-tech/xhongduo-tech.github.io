## 为什么从延迟排查开始

「服务变慢了」是运维最高频的报警。但「慢」有无数种可能：是请求排队了？是 prefill 变重了？是 GPU 降频了？是网络拥塞了？还是代码的某个 kernel 突然变慢？**延迟排查的能力决定了故障从「发现」到「定位」的时间**——而这正是线上事故 MTTR 的核心。本篇给出一条从粗到细的排查路径：**日志 → 引擎指标 → 系统层 → kernel Profile**，每一层回答一类问题。<span class="marginnote">本专题《服务监控》讲「怎么持续看住服务」，本篇讲<strong>「出问题了怎么往下挖」</strong>——监控是仪表盘，排查是探针。</span>

## 1 第一层：日志与请求元数据

延迟异常的定位从**日志**开始——它回答「哪个请求慢了、慢在哪一阶段」。

每一条请求日志要能回答：请求 ID、模型、prompt 长度、生成 token 数、TTFT、TPOT、E2E、finish_reason、路由目标。排查的读法：

**看是「普遍慢」还是「个别慢」**：如果 P99 慢但 P50 正常，是长尾问题——多半是某个大请求或缓存未命中；如果 P50 也慢，是全局限流——队列、GPU 过载或代码退化。
**看慢在哪个阶段**：TTFT 暴涨 = prefill/排队问题；TPOT 暴涨 = decode 问题；两者都涨 = 资源饱和。<span class="marginnote">日志是「第一现场」：<strong>先看日志把「慢」归到阶段，再决定往哪层挖</strong>。盲目往下挖 kernel 是最常见的错误——90% 的「慢」在日志层就能定位。</span>

**辨析｜易错点：没有请求级日志的排查是盲人摸象。** 如果只聚合了「平均延迟」，出问题时你连「是哪个请求、多长 prompt、走了哪条路由」都不知道。**请求级日志（含分阶段耗时）是延迟排查的前提**，应在服务上线时就埋好。

## 2 第二层：引擎指标与系统状态

日志说「prefill 慢了」，接下来看引擎与系统指标回答「为什么」：

**队列深度**：等待序列数暴涨？→ 请求堆积、调度器过载。看 max-num-seqs 是否打满、是否频繁抢占。
**GPU 利用率**：SM 利用率高 = 算力打满；显存带宽利用率高 = 带宽打满。**利用率低 + 延迟高 = 有阻塞**（kernel 等待、数据搬运卡住、同步开销）。
**GPU 降频**：温度/功耗异常 → GPU 降频，算力下降，**延迟悄悄变慢**——这是「硬件层」的原因，监控里必须盯温度与功耗。<span class="marginnote">GPU 降频是「隐蔽的慢」：<strong>SM 利用率看着正常，但频率掉了一半，算力实际折半</strong>。温度 >85°C 或功耗触墙时优先检查散热与机柜通风。</span>
**CPU 侧**：CPU 利用率、网络收发、磁盘（模型加载/日志刷盘）。CPU 打满会拖慢调度与 tokenizer。

## 3 第三层：系统层与资源竞争

引擎正常、GPU 正常，但延迟还是高——往系统层挖：

**多进程竞争**：同机跑多个推理进程/容器，共享 GPU 与 CPU——检查是否有其他进程抢占算力或带宽。
**网络瓶颈**：跨机推理的通信延迟（见多机通信篇）。用 `iperf` / `ib_write_bw` 测实际带宽，排查网络拥塞与链路问题。
**NUMA / PCIe 拓扑**：GPU 与 CPU 的亲和性、PCIe 通道争抢——用 `nvidia-smi topo -m` 看拓扑，错误的亲和性让数据搬运绕远路。

## 4 第四层：Kernel Profile

前三层都查完还定位不了，就用 **Profile 工具**看 GPU kernel 级别：

**nsys（Nsight Systems）**：时间线视图——每个 kernel、每次内存拷贝、每段等待在时间轴上的分布。**回答「时间去哪了」**：是某个 kernel 突然变长，还是 kernel 之间有空隙（等待同步）。<span class="marginnote">nsys 输出一张时间线：<strong>kernel 之间的空白 = 浪费</strong>。LLM 推理的常见 Profile 发现：GEMM 之间的小空隙（kernel launch 开销）、数据搬运等待、同步 barrier。</span>
- **ncu（Nsight Compute）**：单个 kernel 的深度分析——SM 占用率、内存吞吐、指令效率。**回答「这个 kernel 为什么慢」**：是访存没吃满、还是寄存器溢出、还是 occupancy 不足。

**Profile 的读法**：先 `nsys` 找到「最长的 kernel 或最大的空白」，再 `ncu` 深入那个 kernel。**Profile 是最后的手段，但也是最接近真相的手段**——它看到的是「GPU 上真实发生了什么」。

## 5 公式解析：延迟的分解定位

把一次慢请求的延迟拆成可定位的段（延续《TTFT/TPOT》篇的分解）：

$$T_{\text{E2E}} = T_{\text{net}} + T_{\text{queue}} + T_{\text{prefill}} + T_{\text{decode}} + T_{\text{overhead}}$$

- **第一步，逐段打点**：在请求经过的每一段埋时间戳（网关入、调度入、prefill 完、每 decode 步）。**打点是定位的前提**——没有分段时间，任何「慢」都只能靠猜。
- **第二步，找主导项**：哪段占比最大，哪里就是优化的主战场。$T_{\text{prefill}}$ 大 → 缓存/prefill 优化；$T_{\text{decode}}$ 大 → decode 优化；$T_{\text{queue}}$ 大 → 调度/扩容；$T_{\text{overhead}}$ 大 → 框架开销（序列化、tokenizer、网络协议）。
- **第三步，与基线比**：同样请求在正常时段的各段耗时作基线，**异常段 = 当前耗时 − 基线**。异常集中在哪段，问题就在哪段——日志、引擎指标、系统层、Profile 按段对应的方向查。

## 6 小结

- **排查四层递进**：日志（哪个请求慢、慢在哪段）→ 引擎指标（队列/利用率/降频）→ 系统层（竞争/网络/拓扑）→ Kernel Profile（时间去哪、kernel 为何慢）。
- **先日志后 Profile**：90% 的「慢」在日志层就定位，盲目挖 kernel 是常见错误。
- **请求级日志是前提**：含分阶段耗时（TTFT/TPOT），上线前就埋好。
- **GPU 降频是隐蔽的慢**：盯温度与功耗，利用率正常但算力折半。
- **延迟分解打点**：把 E2E 拆成 net/queue/prefill/decode/overhead，与基线比找异常段。
