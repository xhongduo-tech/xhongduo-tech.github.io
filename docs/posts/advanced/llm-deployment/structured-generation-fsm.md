## 为什么从结构化生成开始

一个 Agent 要调用工具，模型必须吐出一段**能被机器解析**的文本——通常是 JSON。但大模型是「按概率吐 token」的，它对「看起来像 JSON」有直觉，对「语法完全合法」没有承诺。真实生产里，LLM 输出的 JSON 缺个逗号、多个反斜杠、把数字写成字符串，是家常便饭。<span class="marginnote">代价不只是「重新生成一次」：一次非法 JSON 意味着一次失败的函数调用、一条错误的数据库写入、一次需要人工介入的重试。在每日百万次调用的 Agent 服务里，非法率哪怕只有 5%，也会把工程团队拖进无穷无尽的「解析 + 重试」泥潭。</span>

于是问题变成：**能不能让模型的输出「必然合法」？** 这就是结构化生成（structured generation）。第二章对比引擎时我们说过：SGLang 是「正确性之选」，它把「输出合法」从概率问题做成了**构造问题**——用一台有限状态机（Finite State Machine, FSM）看住每一步采样，非法 token 从一开始就不许出现。

**核心概念：约束解码（constrained decoding）**：在每一步生成时，根据当前状态计算「接下来哪些 token 仍然能通向合法输出」，把其余所有 token 的概率置零，再在合法子集上重新归一化采样。它给「输出格式」一个硬保证，而不是一个软请求。

## 1 三条路线：提示词、修复、硬约束

先看摆在我们面前的三条路，它们的成本与保证逐级递进。

**路线一：提示词约束（软约束）。** 在 prompt 里写「请以 JSON 输出，schema 如下」。零成本，但**零保证**——模型可能忽略、可能加注释、可能把 key 改成驼峰。对要求「必须能被机器解析」的场景，这条路只配当基线。

**路线二：后处理修复（retry / repair）。** 生成完毕后解析失败就重试或修补（拿正则把非法片段删掉、补括号）。它能救回一部分坏输出，但成本高：重试让延迟与 token 消耗翻倍，修补经常修出**另一处**非法。这像是「先泼墨再描边」，永远在追着错误跑。

**路线三：约束解码（硬约束）。** 在采样这一步就保证「每一步生成的 token，都能让整个输出最终落在合法语言里」。非法 token 被**从数学上排除**，而不是事后补救。这一条是 SGLang、以及被 vLLM 与 TensorRT-LLM 共同采纳的 xgrammar 走的路。<span class="marginnote">三条路线不是三选一：提示词约束依然值得写（它降低非法率的「自然基线」，减少约束解码要做的工作）；但「保证合法」只能来自硬约束。工程上常见做法是「好 prompt + 硬约束 + 极低的重试兜底」。</span>

## 2 有限状态机：把「合法结构」变成「状态迁移」

约束解码的关键，是把「合法的输出集合」翻译成一台**能逐步判定**的机器。最经典的做法是走两条翻译链：

**第一条链：schema → 正则 → FSM。** JSON Schema 或 Pydantic 模型被确定性地翻译成一条正则表达式（SGLang 早期用 Outlines 库做这件事），正则再经 Thompson 构造编译成 NFA，必要时确定化为 DFA。于是「输出合法」就等价于「输出的每个 token 都让自动机停在某个非接受路径上，最终到达接受态」。<span class="marginnote">正则表达式本身是「正则语言」的描述，而正则语言恰好能被有限状态机接受——这是计算理论里「三种等价表示」（正则、NFA、DFA）的直接应用，见第三级《计算理论》。把 JSON 翻译成正则，就是把「合法 JSON」这个集合交给一台机器去「认」。</span>

**第二条链：文法 → 压缩 FSM（xgrammar）。** JSON 其实不是正则语言（它要配对的括号、嵌套的结构），严格建模要用上下文无关文法。xgrammar 走的是文法路线：把 EBNF/JSON 文法编译成一棵**压缩的有限状态机**，状态更少、内存更低、每 token 掩码更快——官方数据是比标准约束解码快约 3 倍，且掩码计算与模型前向**重叠**进行，几乎不增加每步延迟。这也是它同时被 vLLM 与 TensorRT-LLM 收编的原因。

解码时，每一步的工作就是三拍：

1. **查当前状态**：从上一 token 的迁移结果拿到当前状态 $q$。
2. **算合法集**：对词表里每个 token，问 FSM「吃了它之后还活着吗？」——活着的进合法集 $V_{\text{valid}}(q)$。
3. **掩码 + 采样**：把不在 $V_{\text{valid}}(q)$ 里的 logits 压到 $-\infty$，在剩余子集上重新归一化采样；把采样到的 token 喂给 FSM 推进状态。

## 3 公式解析：被掩码的 softmax

约束解码的全部数学，就是把普通 softmax 换成一次「条件采样」。设原始 logits 为 $\ell$，当前 FSM 状态 $q$，合法 token 集合 $V_{\text{valid}}(q)$：

$$
\hat{\ell}_i =
\begin{cases}
\ell_i, & y_i \in V_{\text{valid}}(q) \\
-\infty, & y_i \notin V_{\text{valid}}(q)
\end{cases}
$$

采样概率则是在掩码后重新归一化的 softmax：

$$
p'(y_i) = \frac{e^{\hat{\ell}_i}}{\sum_{j} e^{\hat{\ell}_j}}
= \frac{\mathbb{1}[y_i \in V_{\text{valid}}(q)]\; e^{\ell_i}}
{\sum_{j \in V_{\text{valid}}(q)} e^{\ell_j}}
$$

逐步拆解：

- **第一步，认掩码操作**：$\hat{\ell}_i = -\infty$ 意味着 $e^{\hat{\ell}_i} = 0$，非法 token 在 softmax 分子上直接消失——它不是被「劝退」，而是被**物理抹除**。
- **第二步，认归一化分母**：分母只对合法子集求和。这保证**合法 token 之间的相对概率不变**——约束只重排「谁被允许」，不改写「允许者之间的偏好」。
- **第三步，认状态推进**：采样到的 $y_t$ 送进自动机，状态迁移 $\delta(q, y_t) \to q'$，下一轮用 $q'$ 再算合法集。整条链是「掩码 → 采样 → 迁移」的循环，直到 FSM 到达接受态（$q'$ 标志）。
- **第四步，认顺序细节**：掩码发生在**惩罚（penalty）之后、温度缩放与 top-k/top-p 之前**。也就是说 frequency/presence penalty 先把该扣的扣完，再抹非法 token，最后温度与 top-k 只在合法子集上生效。这个顺序保证了「约束」与「采样策略」互不干扰。

## 4 一条 JSON 的完整旅程：从 schema 到 token

空谈不如走一遍。假设约束是「输出一个 JSON 对象」的 JSON Schema，SGLang 里写成 `json_schema` 参数，或 `regex` 直接给正则。解码第一步，FSM 说「第一个字符必须是 `{`」。词表里有一堆 token——`{`、`{ "`、`"name"`、`[`、`hello`……**哪些合法？**

答案取决于自动机「能不能消费这个 token 的所有字符」。token `{` 合法（吃掉左花括号）；token `hello` 不合法（`h` 不在 `{` 之后的合法字符集里）；token `{ "` 也合法——它一次吃掉 `{` 与引号，自动机认作「已进入键名的途中」。**约束解码的对象是 token，不是字符**，所以每个 token 都要在自动机上「试吃」一遍，这正是不论哪家实现都必须处理的核心循环。

一个被反复踩的坑在这里暴露：**tokenizer 的边界与语法边界不对齐**。比如字符串值 `"world"` 的结束引号 `"` 可能与后续的逗号 `,` 拼进同一个 token；再如 JSON 数字 `3.14` 的最后一个字符后必须是 `,` 或 `}`，但 tokenizer 可能把数字 `3.14` 和分隔符 `,` 切成两个 token。处理办法是**字节级（byte-level）的 FSM**：把语法精细到字节，token 先解码成字节串，再看字节串能否被自动机逐步消费——xgrammar 就是这么做的。这让「合法」的判断精确到字节，tokenizer 怎么切都不怕。

把「每步试吃」写成伪代码，结构很清爽：

```python
def compute_valid_mask(state, vocab, fsm, tokenizer):
    """三拍之一：对整张词表算合法掩码"""
    mask = torch.full((len(vocab),), -torch.inf)
    for i, token in enumerate(vocab):
        byte_str = tokenizer.decode([token])        # token → 字节串
        if fsm.can_consume(state, byte_str):        # 自动机「试吃」
            mask[i] = 0.0                           # 合法，保留
    return mask

# 三拍之二：掩码 + 采样（只在合法子集上归一化）
logits = logits + compute_valid_mask(state, vocab, fsm, tokenizer)
probs = torch.softmax(logits, dim=-1)
next_token = torch.multinomial(probs, 1).item()

# 三拍之三：推进状态
state = fsm.transition(state, tokenizer.decode([next_token]))
```

这段代码把「公式解析」那一节的三拍落到实处：`fsm.can_consume()` 返回 `False` 就是「非法」，掩码一次性把整张词表的非法项抹平，`softmax` 只在合法子集上归一化——**没有任何一个非法 token 能从采样里漏出来**。

## 5 效率与质量：压缩、跳跃解码与代价

约束解码有保证，也有价格。三个工程要点：

**压缩 FSM**：朴素 FSM 状态数可能爆炸（JSON 文法展开后状态成百上千）。xgrammar 用「压缩状态」把等价状态合并，内存与查找都大幅下降，且掩码计算与注意力前向重叠——**每步掩码的额外延迟被藏进 GPU 计算里**，这是它敢说「3 倍提速」的底气。

**跳跃解码（jump-forward）**：FSM 常能确定「接下来的几个字符是唯一的」。比如 JSON 对象打开 `{` 之后，键名一旦确定，接下来 `"` 与 `:`（结束引号、冒号）几乎是唯一的；再如正则 `\d{4}` 要求四位数字，前三位定了，第四位也未必唯一，但**「必须是个数字」是确定的**。遇到这种「唯一继续路径」，可以直接跳过 token 生成、把确定字符一次性拼进输出——SGLang 的跳跃解码正是利用这一点，把「逐 token 问 FSM」变成「整段快进」。<span class="marginnote">跳跃解码与第二章的投机解码是两种「快进」，别混：投机解码靠一个<strong>草稿模型</strong>猜下一步 token，猜对了就接受；跳跃解码靠<strong>语法本身</strong>的确定性，不需要任何额外模型。前者是「概率性快进」，后者是「必然性快进」。</span>

**质量的代价**：约束会砍掉一部分「虽然合法但模型更想走」的路径。对 JSON、代码这类**语法即契约**的场景，损失可忽略；但对创意写作、开放问答，硬约束会明显压缩多样性。所以 SGLang 的 `SamplingParams` 把 `json_schema`、`regex`、`grammar`、`structured_output` 设为**互斥**——一次请求只用一个约束，逼你明确「这段输出到底要不要被管住」。

**辨析｜易错点：**

- **误区一：以为约束解码保证「答案正确」。** 只保证**语法合法**。模型该答错还是答错——掩码只能删除非法路径，制造不出模型不知道的知识。第二章那句「SGLang 是正确性之选」，说的是**格式**正确性，不是内容正确性。
- **误区二：以为掩码是「把概率改成 0」。** 是把 logits 设为 $-\infty$ 再重新归一化。若只把概率抹零而不重归一化，合法 token 的概率和就不为 1，采样分布会出错。
- **误区三：以字符为单位判断合法性。** 必须是 token（或字节）为单位。词表 token 可能横跨语法边界，字符级判断会漏放非法 token 或误杀合法 token。
- **误区四：以为约束解码免费。** 掩码本身有每 token 成本；压缩与重叠能把它藏起来，但复杂文法、超大词表下开销依然存在。跳跃解码与压缩 FSM 是配套的「还债」手段。
- **误区五：把 `json_schema`、`regex` 同时传。** 它们互斥；需要复合约束时用一个能表达二者的单一正则或文法。

## 6 小结

- **问题**：LLM 输出无法保证机器可解析，非法 JSON 拖垮 Agent 与函数调用。
- **三条路线**：提示词（软、零保证）、后处理修复（贵、追错误）、约束解码（硬保证）。
- **FSM 机制**：schema → 正则 → FSM，或文法 → 压缩 FSM（xgrammar）；每步「查状态 → 算合法集 → 掩码采样 → 推进状态」。
- **掩码公式**：$\hat{\ell}_i = -\infty \cdot \mathbb{1}[y_i \notin V_{\text{valid}}(q)]$，分母只在合法子集上归一化，合法 token 相对概率不变。
- **tokenizer 对齐**：合法性判断要到 token/字节级；字节级 FSM（xgrammar）解决边界错位。
- **效率**：压缩 FSM + 掩码与前向重叠 ≈ 3 倍提速；跳跃解码靠语法确定性整段快进。
- **辨析**：保证语法不保证语义；互斥的约束参数；掩码要重归一化。
