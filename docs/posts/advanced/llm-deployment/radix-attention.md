## 为什么从前缀树开始

上一章我们花了整整一节讲 vLLM 的 Prefix Caching：用**块哈希 + 引用计数 + LRU** 让共享前缀的 KV 被复用。但 vLLM 的这套方案有两个「先天短板」：共享的单位是**固定大小的块**（默认 16 token），前缀必须块对齐才能命中；而且哈希表只是「内容的索引」，查找是逐块比对，缓存本身没有结构。

SGLang 团队在 2024 年的论文 *Efficiently Programming Large Language Models using SGLang* 里给出了一个更激进的答案：**干脆把 KV Cache 本身组织成一棵前缀树（radix tree）**。在这棵树里，「两个请求共享前缀」不再是一个需要额外判断的巧合，而是树的**默认形态**——凡是前缀相同的路径，天然就合并成一条，KV 只算一次。<span class="marginnote">这就是「整体大于部分之和」的工程版：两份请求合起来，共用的那部分不按两份算。论文报告在共享前缀负载（多轮对话、RAG、few-shot）下能省去一半以上的 Prefill 计算量。</span>

**核心概念：RadixAttention（基数树注意力）**：用一棵前缀树（也叫 radix tree、压缩字典树）组织所有已计算的 KV Cache，新请求从根出发做最长前缀匹配，命中的路径直接复用 KV，只对未命中的后缀做计算。它是 SGLang 的 KV 缓存分配器的底层结构。

## 1 前缀树：把共享前缀变成一条路径

先看一颗前缀树长什么样。下面这棵树的根是空序列；根下第一个节点是「你好，请介绍」这 6 个 token——它同时是两个请求的公共前缀；再往下，两个请求各自长出「下微积分」与「下量子力学」两个不同的后缀节点。

![RadixAttention 前缀树：两个请求共享前缀路径](/images/llm-deployment/radix-attention-1.svg)

**重点：前缀树上，「共享」不是标注出来的，而是结构本身。** 两个请求共同走过的路径只有一份 KV。这与 vLLM 的「各自分配块、再靠哈希表发现可以共享」形成鲜明对比——SGLang 里 KV 缓存的存放方式天生就是共享友好的。

树的每个节点存三样东西：

- **键（key）**：一段 token ID 序列（即该节点代表的连续前缀）。
- **值（value）**：这段前缀对应的物理 KV 页的索引——指向真正存 K、V 张量的显存位置。
- **子节点与父节点**：子节点表示「在父节点前缀之后继续延伸」的更长前缀。一个节点可以有多个孩子，但只有一个父亲。

节点还有两个「管理字段」：`ref_count`（引用计数，被多少条活跃请求引用）与 `timestamp`（最近访问时间）。它们与 KV 页的引用计数、LRU 驱逐直接挂钩，后面会看到。

## 2 树上的三件事：匹配、插入、驱逐

一棵树要想当缓存用，只需要三个操作。

**匹配（match_prefix）**：新请求进来，从根出发，沿着「能对上 token 序列」的孩子一路往下走，找到**最长公共前缀**。命中的节点把它的 KV 页索引拼起来返回，调度器让新请求的前缀直接指向这些页，**一次前向都不多算**。匹配以页为粒度：若命中落在某个节点中间，就做一次**节点分裂（split）**，把节点从分叉处切成两段，让共享边界精确——分裂不复制数据，只是把节点拆细，方便下一次匹配命中更多。每走一步都会刷新路径上节点的 `timestamp`，供 LRU 使用。

**插入（insert）**：一个请求生成完毕后，把它的完整 token 序列与 KV 写回树。若它的前缀已经存在，只补上独有的后缀节点；若它与某节点部分共享，先分裂再插入。<span class="marginnote">多轮对话的树长得最快：第 $n$ 轮请求的前缀几乎就是第 $n-1$ 轮的全部，于是每一轮都在旧路径上「接着长」，上一轮算好的 KV 全部复用——这是树结构对「增量式多轮负载」最舒服的地方。</span>

**驱逐（eviction）**：显存不够时，按 LRU 淘汰节点。关键是两条规则：

- **只能驱逐 `ref_count = 0` 的节点**——正在被活跃请求引用的节点是「受保护」的，不能抢。
- **优先驱逐叶子节点**——叶子是最深、最独特的路径，淘汰它不影响别的请求的公共前缀。这保证了一棵树上那些被广泛共享的「主干」尽量留存。

这套「引用计数保护 + LRU + 叶子优先」与 vLLM 的驱逐哲学同源，但作用对象从「块」变成了「树节点」。树的优势在于：**驱逐是「剪枝」而不是「删页」**——剪掉一片叶子，主干还在；删掉一个块，它的邻居全得跟着失效。

## 3 公式解析：前缀树到底省下多少 Prefill 算力

把收益量化。设 $N$ 条请求共享一段长度为 $P$ 的前缀，第 $i$ 条请求的独有后缀长度为 $S_i$。回顾第一章《Prefill 与 Decode 两阶段的计算特征》：Prefill 的算力分**线性部分**（MLP/embedding，随 token 数线性）与**二次部分**（注意力，随 token 对数二次）。这里先看线性部分，设每 token 系数为 $a$：

$$
W^{\text{lin}}_{\text{naive}} = a \sum_{i=1}^{N} (P + S_i)
\qquad \longrightarrow \qquad
W^{\text{lin}}_{\text{radix}} = a \left( P + \sum_{i=1}^{N} S_i \right)
$$

逐步拆解：

- **第一步，认 $W^{\text{lin}}_{\text{naive}}$**：没有前缀复用，每条请求都把 $P + S_i$ 个 token 完整过一遍 MLP，共 $N$ 份前缀、$N$ 份后缀。
- **第二步，认 $W^{\text{lin}}_{\text{radix}}$**：前缀在树上只算一次，$N$ 条请求共享这 $P$ 的 KV；各自的后缀 $\sum S_i$ 仍要各算各的。
- **第三步，算节省比例**：线性部分省下的比例
$$
\eta_{\text{lin}} = \frac{W^{\text{lin}}_{\text{naive}} - W^{\text{lin}}_{\text{radix}}}{W^{\text{lin}}_{\text{naive}}}
= \frac{(N-1)P}{N P + \sum_i S_i}
$$
- **第四步，代入数字**：$P = 1000$，$N = 10$，每条后缀 $S_i = 20$。则 $\eta_{\text{lin}} = 9 \times 1000 / (10 \times 1000 + 200) = 9000 / 10200 \approx 88\%$。**前缀越长、共享次数越多，$\eta$ 越接近 100%。**

再看二次部分（注意力）。前缀自己的自注意力原本每条请求要算 $b P^2$（$b$ 为二次系数），$N$ 条共 $N b P^2$；复用后只算一次 $bP^2$，省下 $(N-1)bP^2$。**注意后缀的注意力省不掉**——第 $i$ 条请求的后缀 $S_i$ 个 query 仍要 attend 全部 $P + S_i$ 个 key，代价 $b S_i (P + S_i)$ 照付。<span class="marginnote">这和 vLLM 那节的结论一致：前缀缓存省的是「前缀自身的计算」，省不掉「后缀对前缀的读取」。长上下文场景里 $P$ 大，二次项 $(N-1)bP^2$ 省得最夸张——这正是 RAG 与长文档问答里 RadixAttention 收益最明显的原因。</span>

## 4 与 vLLM Prefix Caching 对比

两者目标相同（复用共享前缀的 KV），但骨架不同，值得摆在一起看：

| 维度 | vLLM Prefix Caching | SGLang RadixAttention |
| --- | --- | --- |
| 缓存结构 | 哈希表（块哈希 → 物理块） | **前缀树**（token 序列为键的节点） |
| 共享单位 | 固定大小块（默认 16 token），须块对齐 | 树节点，按页复用、节点可分裂 |
| 查找方式 | 逐块比对哈希值 | 从根出发最长前缀匹配 |
| 前缀管理 | 块表 + 写时复制（CoW） | 节点分裂（split）天然支持分支 |
| 驱逐 | LRU，`ref_count = 0` 可驱逐 | LRU，**叶子优先** + `ref_count = 0` |
| 与调度耦合 | 调度器单独做缓存感知准入 | 缓存结构与调度器深度融合（Cache-aware 路由） |

**辨析｜易错点：**

- **误区一：以为 RadixAttention 与 PagedAttention 是二选一。** 不是。SGLang 的 KV 也是按页管理的，RadixAttention 的节点**指向物理页**——它是在页式分配之上的共享层。第二章那句「SGLang 的块表结构本身也是页式的」在这里兑现。
- **误区二：以为前缀命中就是 100% 复用。** 匹配以页/块为粒度，节点分裂让边界尽量精确，但**不满一页的尾巴依旧不共享**——这是所有页式方案的共同限制，不是树能消除的。
- **误区三：以为 RadixAttention 省 Decode。** 不省。Decode 每步仍要读全部 KV；树省的是 Prefill 的重复计算与 TTFT。
- **误区四：以为树会自动带来收益，无需调度配合。** 树只是「缓存层」。请求走哪个分叉、往哪台机器路由，决定树能不能被命中。SGLang 为此专门做了 **Cache-aware 路由**——这是第四篇《Router 与 Runtime》的主角。
- **误区五：以为不同请求可以无条件共享前缀。** 可以给树节点加 `extra_key` 命名空间，把不同逻辑域（不同用户、不同 prompt 模板）隔开，防止「内容相似但不该共享」的序列串扰。

## 5 工程收益与适用负载

RadixAttention 的收益高度依赖负载的「前缀重复度」。三类负载是天然受益者：

- **多轮对话**：每轮请求的前缀 = 上一轮全部历史，树按轮次「接着长」，几乎全量命中。
- **RAG / 长文档问答**：所有查询共享同一份检索上下文，上下文占输入 95% 以上，命中率可到 90%+。
- **Agent 工具调用**：system prompt + 工具 schema 是固定前缀，函数调用链越长，复用越多。

反过来，**前缀几乎不重复的负载（每次输入都不同）**，树就退化成普通缓存，收益有限。选引擎时记住这条分界线：你的负载前缀重复度越高，RadixAttention（乃至整套 Cache-aware 调度）越值得。

还有一个容易忽视的实现细节：**请求在树上「走」过时，沿途节点要立刻 `lock`（引用计数 +1），生成完毕再释放。** 如果不加锁，驱逐器可能在请求正读取某段 KV 时把它剪掉，造成悬空引用。锁的粒度是节点而非页——这比逐页加锁更粗、更快，代价是「一段被引用的前缀里，哪怕只有一半正在用，整段都不能被驱逐」。这个「以节点为单位的锁」与 vLLM 块表上的引用计数殊途同归，都是「在用即保护」原则的具体化。

## 6 小结

- **RadixAttention**：用前缀树组织 KV Cache，共享前缀在树上只有一条路径，KV 只算一次。
- **三个操作**：最长前缀匹配（可节点分裂）、插入（后缀接着长）、LRU 叶子优先驱逐（`ref_count = 0` 才可驱逐）。
- **收益公式**：线性部分 $\eta = \frac{(N-1)P}{NP + \sum S_i}$，$P=1000, N=10$ 时约省 88%；二次部分省下 $(N-1)bP^2$，但后缀对前缀的读取照付。
- **与 vLLM 对比**：vLLM 是「块表 + 哈希 + CoW」，SGLang 是「树 + 分裂 + 叶子优先」，两者都基于页式 KV。
- **适用负载**：多轮对话、RAG、Agent 工具调用这些前缀重复度高的场景收益最大。
- **辨析**：树不替代页式分配、不省 Decode、命中要调度配合、可用命名空间防串扰。
