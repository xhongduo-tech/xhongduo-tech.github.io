## 为什么从端云协同开始

端侧能跑小模型、云端有大模型，但用户的真实需求往往两头都不完美：端侧模型能力有限、云端模型有延迟与隐私顾虑。**端云协同推理（edge-cloud collaboration）**把两端组合成一个系统——按任务、按阶段、按数据敏感度，动态决定「谁来做」——这是 LLM 应用落地的现实架构。<span class="marginnote">本专题端侧篇的收尾：前几篇讲「端侧能跑什么」，本篇讲<strong>「端侧与云端怎么分工」</strong>——它不是端侧的替代，而是「端侧 + 云端」的系统设计。</span>

本篇讲端云协同的三种模式（任务路由、阶段拆分、数据分流）、各自的适用场景、以及协同带来的新挑战。

## 1 模式一：任务路由（按难度分流）

最朴素的协同：**简单任务端侧做、复杂任务云端做**。系统对请求做「难度判断」，简单（分类、抽取、短问答）→ 端侧小模型；复杂（推理、创作、长文）→ 云端大模型。

- **判断依据**：任务类型（可事先分类）、prompt 长度、业务规则（敏感请求必上云）。
- **收益**：简单请求零网络延迟、数据不出设备；复杂请求获得云端能力。
- **代价**：需要一个「路由器」（端侧的分类器或规则），判断错了体验打折。<span class="marginnote">难度判断的经典启发式：<strong>「本地模型置信度低就升级云端」</strong>——端侧模型输出低置信度（如困惑度异常）时自动转云端，称为「级联（cascade）」策略，比硬编码规则更自适应。</span>

这是最易落地、应用最广的协同模式——「先本地试、不行再上云」。

## 2 模式二：阶段拆分（谁擅长哪段谁做）

把一次推理按**计算阶段**拆分到两端。最自然的切分是「端侧做首 token 前的感知/轻量处理 + 云端做生成」或「端侧做生成 + 云端做校验」。

更值得讲的是**投机解码式的协同**：端侧小模型当**草稿**，云端大模型当**验证者**（见本专题《投机解码》篇）。端侧每步生成几个候选 token，云端一次 forward 验证——**把「每 token 都走网络」变成「每批 token 走一次网络」**，网络往返次数除以候选数。<span class="marginnote">这是「<strong>把本专题两个概念拼起来</strong>」的漂亮应用：投机解码（草稿 + 验证）天然适配端云拓扑——端侧便宜草稿、云端权威验证。代价是网络延迟仍要付，但摊薄到 $\gamma$ 个 token 上。</span>

**阶段拆分的通用原则**：**把「便宜且高频」的步骤留在端侧（降延迟），把「昂贵且低频」的步骤交给云端（保质量）**。

## 3 模式三：数据分流（按隐私与敏感度）

隐私是端云协同的隐性驱动力。**数据分流**：敏感数据（个人对话、医疗信息、企业文档）只在端侧处理或脱敏后上云；非敏感数据直接上云。

- **端侧优先的隐私价值**：对话历史、键盘输入这类敏感数据不出设备，满足隐私合规（GDPR 等）与用户信任。
- **混合策略**：脱敏——把敏感字段（人名、地点、账号）先替换成占位符，上云处理后再还原。<span class="marginnote">数据分流的工程现实：<strong>「完全不上云」与「完全上云」之间有一个光谱</strong>——脱敏、摘要后上云、联邦式在端侧聚合再上云，都是中间形态。</span>

**隐私不是免费午餐**：端侧处理受能力限制（不能跑大模型做深度分析），脱敏有信息损失。**隐私与能力的平衡是产品决策**，不是纯技术决策。

## 4 公式解析：协同的端到端延迟

协同架构的延迟由「端侧部分 + 网络 + 云端部分」组成。设任务被端侧处理的概率 $\theta$、端侧耗时 $T_e$、网络往返 $T_{\text{net}}$、云端耗时 $T_c$：

$$T_{\text{E2E}} = \theta \cdot T_e + (1-\theta)(T_{\text{net}} + T_c)$$

- **第一步，读分流收益**：$\theta$ 越高（更多任务在端侧），网络与云端成本占比越低。**端侧覆盖率高 = 平均延迟低**，但端侧能力有限，$\theta$ 不可能无脑提高。
- **第二步，读网络项**：$T_{\text{net}}$ 是协同的固有代价——一个上云请求至少多付一次网络往返（通常 20–200 ms）。**网络延迟决定了「该不该上云」的阈值**：$T_e$ 与 $T_{\text{net}} + T_c$ 的差越大，路由的收益越大。
- **第三步，读分级策略的期望**：把任务分成「本地必行」（$\theta=1$）、「云端必行」（$\theta=0$）、「不确定」（端侧置信度判断）。期望延迟 $= \theta \cdot T_e + (1-\theta)(T_{\text{net}} + T_c)$ 在「分级准确」时最优——**路由判断的准确度直接决定协同的收益**。

## 5 小结

- **任务路由**：简单任务端侧、复杂任务云端，按「难度/敏感度」分流；级联策略（本地低置信度就升级）更自适应。
- **阶段拆分**：端侧做便宜高频、云端做昂贵低频；投机解码式协同让网络往返摊薄到多个 token 上。
- **数据分流**：敏感数据端侧处理或脱敏上云，隐私与能力的平衡是产品决策。
- **协同的延迟账**：$T_{\text{E2E}} = \theta T_e + (1-\theta)(T_{\text{net}} + T_c)$，端侧覆盖率与路由准确度共同决定收益。
- **协同不是替代**：端侧求快与隐私、云端求强与全知，组合成「快 + 强 + 私」的系统。
