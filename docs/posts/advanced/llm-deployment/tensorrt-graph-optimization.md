## 为什么从图优化开始

前面几篇讲的 vLLM、SGLang 是**运行时调度**路线：在通用算子库（PyTorch、cuBLAS）之上，靠聪明的内存管理与请求调度把 GPU 喂饱。TensorRT 走的是另一条路：**编译优化**。它把神经网络当成一个计算图，在部署前就做大量静态重写，把「标准算子」变成「针对这块 GPU 的极简内核」。这条路的代价是构建时间长、灵活性低，收益是更低的延迟与更小的显存占用——正适合对性能苛求的生产推理。<span class="marginnote">本专题《推理引擎要解决的核心问题》里说过：<strong>推理的敌人是访存与内核启动开销</strong>。TensorRT 的两板斧——图重写（本篇）与内核融合（下一篇）——都直接指向这两个敌人。</span>

本篇聚焦**图层面的优化**：TensorRT 拿到 ONNX 或模型定义后，先做一层层图变换，把计算图改写成更高效的等价形式。它是「引擎构建」的第一步，也是后续 Kernel 融合与低精度化（INT8/FP8）的舞台。

## 1 计算图的表示与降级

TensorRT 把模型表示为一张有向无环图（DAG），节点是**层（layer）**，边是**张量（tensor）**。输入模型先被「降级」到 TensorRT 内部的 **INetworkDefinition** 表示：把 PyTorch 模块、ONNX 算子映射为 TensorRT 层类型，同时记录张量的形状、数据类型与内存布局。<span class="marginnote">降级不是「无损翻译」：有些高级算子会被拆成基础算子，有些组合则保留为一个<strong>高层算子</strong>（如全连接、归一化）留给后续融合。降级的质量决定后续优化的天花板。</span>

这个阶段的关键信息是**张量的元数据**：每个张量的 shape（含动态 batch 维）、dtype、layout。TensorRT 与 PyTorch 的一个核心差异就在 dtype 上——PyTorch 默认全 FP32，TensorRT 允许每个张量独立声明精度，这是后续 INT8/FP8 混合精度量化的基础。

图优化器随后在 DAG 上跑**等价变换（equivalence-preserving rewrites）**：变换前后图的输入输出必须逐位一致（数学上等价），但计算路径更短、内存更少或更适合硬件。下面三种是最常见的。

## 2 常量折叠、死代码消除与代数简化

**常量折叠（constant folding）**：把「输入全是常量」的子图在构建期就计算掉。模型里到处都是这类结构——因果掩码的三角矩阵、位置编码的 cos/sin 预计算、归一化层的 eps 加法。构建期算掉它们，运行时每步就少几个内核调用。<span class="marginnote">在 LLM 里，<strong>旋转位置编码（RoPE）的 cos/sin 表</strong>是典型被折叠对象：它们只依赖位置索引，与权重无关，完全可以在构建期算成一张表。</span>

**死代码消除（dead code elimination, DCE）**：删掉输出永远不会被使用的子图。例如在 debug 模式下输出的中间张量、或某层算完后从未被引用。DCE 在每次重写后都会跑一遍，保证图里没有「白算」的节点。

**代数简化（algebraic simplification）**：把数学等价的模式换成更便宜的形式：

$x \times 1 \rightarrow x$，$x + 0 \rightarrow x$，去掉恒等变换层；
$\text{scale} \times \text{scale}'$ 合并成一次缩放（例如两个相邻归一化）；
Transpose 与 Reshape 的相邻组合合并成一次布局变换；
把「先除以分母再乘以权重」合并为「乘以合并后的系数」。

这些变换不改变数学结果，却能把图里的冗余层成批消掉。LLM 里动辄上百层的 Transformer，每层省几个恒等层，累计起来就是可观的启动开销节省。

## 3 布局优化与数据通路选择

图优化最「硬核」的一块是**内存布局（layout）优化**：同一个张量，在 GPU 上可以排成 NCHW、NHWC、NCDHW 等不同排列；对矩阵乘法，还有行主序（row-major）与列主序（column-major）的差别。<span class="marginnote">cuBLAS 的 GEMM 对 layout 极其挑剔：<strong>换一个布局，性能可能差出几倍</strong>。TensorRT 会为每个中间张量试探多种布局，在「布局转换的开销」与「后续算子因此获得的提速」之间做全局权衡。</span>

**数据通路（data path）选择**则指为每个层挑选实现路径：同样一个 GEMM，可以用 cuBLAS、cuDNN、TensorRT 自研内核，也可以走 Tensor Core 的 cutlass 实现；INT8 量化后还可以选 FP32 累加的「精确路径」或 FP16 累加的「快速路径」。TensorRT 用**成本模型 + 实际基准（tactic）**在构建期为每个层选出最快实现。

**辨析｜易错点：布局优化不是局部最优的叠加。** 初学者容易以为「每个层选最快布局，全局就最快」。实际上 layout 变换层（Transpose/Permute）本身是昂贵的内存拷贝，一个层的最快布局可能强迫下一个层多付出两次转换。TensorRT 在**整图层面**做联合搜索（结合动态规划式的最短路径思想），把「转换开销」与「执行提速」统一进成本函数——这正是图优化器最复杂也最有价值的部分。

## 4 公式解析：图变换的收益度量

图优化不是玄学，每一步都可以量化。设原图有 $N$ 个层，第 $i$ 层单次执行耗时 $t_i$，启动开销 $s$（内核发射成本，约 2–10 微秒）。一层层顺序执行时，一次前向的总耗时是：

$$T = \sum_{i=1}^{N} (t_i + s) = \sum_{i=1}^{N} t_i + N \cdot s$$

- **第一步，读出两层含义**：总耗时 = 计算时间总和 + 启动开销总和。当 $t_i$ 很小（几十微秒量级的 elementwise 算子）时，$N \cdot s$ 甚至超过 $\sum t_i$——**启动开销占比失控**。
- **第二步，代入融合与消除的效果**：若图重写把 $N$ 个层削减为 $M$ 个（$M < N$），且被削掉的层原本计算量很小，那么 $T' \approx \sum_{i=1}^{M} t_i + M \cdot s$。节省量约为 $(N-M) \cdot s$——**每消掉一个层，就省一次内核启动**。
- **第三步，看出图优化的杠杆在哪**：LLM 的一层 transformer 里有大量 elementwise 小算子（残差加、LayerNorm 缩放、SwiGLU 逐元素乘），单个 $t_i$ 小但数量庞大。**图优化 + 内核融合（下一篇）把几百个小算子折叠成十几个大内核**，让 $N \cdot s$ 项急剧下降，这正是 TensorRT 推理延迟低于动态图框架的秘密。

值得强调：$T$ 是「一次 decode 的耗时」。LLM 解码要逐 token 执行成百上千次，每省 10 微秒，一个 1000-token 回答就省 10 毫秒——图优化的收益是**乘上序列长度**的。

## 5 数值算例：一次图优化的成本收益

把「每消一层省一次启动」算成具体数字。设一个 7B 模型、每层 Transformer 有约 30 个算子（矩阵乘、归一化、残差、SwiGLU 分解、逐元素算子），约 32 层。未优化时一次前向：

- **算子总数**：$32 \times 30 \approx 960$ 个算子 → 约 960 次内核启动。
- **启动开销**：设每次内核启动约 5 微秒（$s$），则启动开销 $960 \times 5 = 4.8$ ms；计算时间 $t$ 假设 15 ms。**启动占了总耗时近 1/4**——这就是优化空间。

图优化 + 内核融合后，把 960 个算子折叠成约 60 个大内核（矩阵乘 + 融合的归一化/残差）：

- **启动开销**：$60 \times 5 = 0.3$ ms，**比 4.8 ms 降了一个数量级**。
- **总耗时**：$15 + 0.3 = 15.3$ ms vs 原 $15 + 4.8 = 19.8$ ms——**节省约 23%**，且这个节省对每个 decode 步都成立。

**读这个算例**：图优化的收益来自「把启动开销摊薄」。decode 要逐 token 执行，每步省 4.5 ms，一个 500-token 回答就省 2.25 秒——**收益乘上序列长度，这正是「编译路线适合生产推理」的量化理由**。<span class="marginnote">启动开销的直觉：<strong>内核启动就像「每次打电话都要先拨号」</strong>——调用几百次小函数，拨号时间加起来比通话还长；合并成大内核就像「一次电话谈完所有事」。</span>

## 6 图优化 vs 运行时优化的分工

TensorRT 的编译优化与 vLLM 的运行时优化不是竞争，而是「不同层的优化」：

| 优化类型 | 手段 | 粒度 | 适用 |
| --- | --- | --- | --- |
| 图优化（TensorRT） | 重写计算图 | 图/算子层 | 构建期一次做完 |
| 内核融合 | 合并 kernel | kernel 层 | 构建期一次做完 |
| 内存优化（vLLM） | 页式 KV、共享 | 请求/序列层 | 运行时动态 |
| 调度优化（vLLM） | 批、抢占 | 请求层 | 运行时动态 |

**两者的分工**：编译优化「把每个算子做快」，运行时优化「把每个请求安排得密」。**一个静态（构建期锁死），一个动态（运行时决策）**——生产上常「编译优化打底 + 运行时调度优化」，两者叠加。

**辨析｜易错点：别把「构建时间长」当成 TensorRT 的缺点而无视它。** 构建几分钟，换来的是每步 decode 省几毫秒、且生产运行无需再优化——**对「构建一次、长期运行」的生产服务，构建成本摊到千万次请求上趋近于零**。只有「模型天天换、部署临时用」的场景，构建时间才是真负担。

图优化阶段的常见问题速查：

| 现象 | 常见原因 | 对策 |
| --- | --- | --- |
| 构建报「unsupported op」 | 算子没有 TensorRT 实现 | 拆成基础算子或用插件 |
| 动态 shape 爆炸 | 未声明动态维度范围 | 给 batch/seq 设合理的动态范围 |
| 精度下降 | 等价变换引入舍入差异 | 用 FP32 校验关键层 |
| 性能没提升 | 图没触发融合/折叠 | 检查构建日志的优化项 |
| 构建太慢 | 布局搜索空间过大 | 缩小 tactic 搜索范围 |

**读这张表**：图优化阶段的问题大多集中在「算子支持」与「动态 shape」——**TensorRT 对「输入模型长什么样」很挑剔**，这是编译路线「灵活性低」的体现。好在这些都在构建期暴露，不会带到运行时。

**「算子支持」是选 TensorRT 前的第一项尽职调查**：先确认目标模型的算子 TensorRT 都能认——认不全，构建就要拆算子、写插件，成本远高于预期。

**TensorRT 图优化一句话总结**：它把「运行时每个算子都要做的事」提前到构建期做一遍，换来运行时「更少的启动、更稳的布局」——**这是「一次重、每次快」的典型交易**，与 vLLM 的「每次轻、运行时调度」形成互补。

**选编译还是选运行时，看负载形态**：模型长期固定、请求量大、延迟敏感 → 值得为 TensorRT 的构建时间付一次费；模型频繁换代、流量小、要快速迭代 → 运行时调度更灵活。**两种路线各有主场，理解各自「省什么、费什么」，就能选对**。

## 7 小结

- **TensorRT 先把模型降级成内部计算图**，保留张量的 shape、dtype、layout 元数据，这是所有后续优化的输入。
- **三类核心图重写**：常量折叠（构建期算掉常量子图）、死代码消除（删无用层）、代数简化（合并等价便宜形式）。
- **布局优化是全局问题**：layout 转换本身昂贵，TensorRT 在整图上联合搜索，而非逐层贪心。
- **图优化的量化收益**：每消掉一个小算子就省一次内核启动；LLM 里 elementwise 小算子极多，收益随序列长度放大。
- **编译 vs 运行时分工**：编译优化把算子做快（静态），运行时优化把请求安排密（动态），生产常两者叠加。

在下一节，我们看比「消层」更进一步的操作——**Kernel 融合与自定义 CUDA Kernel**：不满足于少启动几次，而是把多个算子的计算真正合并进同一个 CUDA 内核。
