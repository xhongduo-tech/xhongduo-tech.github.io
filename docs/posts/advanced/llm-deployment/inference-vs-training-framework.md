## 为什么训练框架的「惯性」会带偏推理优化

上一节对比完四家引擎，一个更基本的问题浮出水面：**为什么推理需要单独造一套引擎，而不能拿 PyTorch、DeepSpeed 这些训练框架直接服务？** 表面看都是「前向计算」，底层却天差地远。

原因可以浓缩成一句话：**训练是吞吐优先的批处理作业，推理是延迟敏感的交互式批处理。** 这句话的每一半都有一连串工程后果。这一节把训练框架的思维惯性逐条拆开，你会突然看懂推理引擎那些「多余」的设计——调度器、KV 管理器、流式接口——每一样都是在纠正训练框架的惯性。<span class="marginnote">为什么值得花一整节讲区别？因为几乎所有推理优化的误用，都源于把训练时的直觉带过来：以为批越大越好、以为显存大头是激活、以为框架层做做 kernel 加速就够了。先把「两者是两种动物」焊进脑子，后面读源码才不会懵。</span>

这一节的读法：不要把它当「训练框架的批评」，而是当**「训练思维 vs 推理思维」的对照表**。你在训练里积累的每一分经验——batch 调度、显存规划、并行策略——在推理里都有一份「翻译」，只是符号常常相反。

## 1 目标函数：吞吐优先 vs 延迟敏感

训练框架的 KPI 是**单位时间的有效算力**：GPU 空闲一毫秒都是浪费。于是训练像一条流水线，样本被切成均匀的 batch 喂进去，谁快谁慢无所谓，只要整条线不空转。

推理的 KPI 是**用户体验**：首 token 时间（TTFT）和每 token 时间（TPOT）都是要守的 SLO。用户等不了「批凑齐再开工」，也不能接受某个请求被排在长任务后面饿死。<span class="marginnote">这套「既要吞吐又要单请求延迟」的矛盾，正是推理调度器存在的意义：Continuous Batching 等技术的本质，是在吞吐与延迟之间做动态权衡——详见第五篇与第三篇的调度器。</span>

**训练可以等 32 个样本凑齐再算，推理不能。** 这一条单点差异，推导出后面所有的不同。

度量单位也完全不同。训练框架用 **MFU**（Model FLOPs Utilization，实际算力占峰值算力的比例）来考核自己——「GPU 空转就是犯罪」；推理引擎则用 **TTFT、TPOT、吞吐、P99 尾延迟**（第十篇）来考核自己——「单个用户等太久才是犯罪」。**两种货币，两套追求**，这是二者在工程上分道扬镳的起点。

还要看清推理的「交互」属性：用户在等 token，每个 token 都产生一次可见的等待，所以**「快」不是一个平均值，而是「最慢的那一个不能太慢」**。这正是 P99 尾延迟、而不是均值，成了推理最硬的指标。训练里没有「用户」这个概念，自然也没有尾延迟这回事。

## 2 显存画像：激活主导 vs KV 主导

训练要**反向传播**：求梯度需要从后往前回传，而每一步回传都要用到前向时算出的中间激活。所以训练显存被**激活值**主导，并且激活量与 `batch × 序列长度 × 层数` 成正比——这是「大 batch 反而装不下」的根源。

推理只做前向，不需要保留中间激活，**显存大头换成了 KV Cache**：它随序列长度逐 token 增长，且是动态的、每条序列独立。<span class="marginnote">训练里也建 KV Cache，但反向传播一结束就被释放，生命周期短；推理里 KV 要活到请求结束，还跨请求共享前缀。一个「临时工」一个「常住客」，管理策略自然完全不同。</span>

两张显存画像决定了两种优化方向：训练省显存靠**重计算**（把激活丢了，反传时再算一遍）；推理省显存靠**页式管理与量化**（第五、六篇）。工具完全不同。

为什么激活会这么多？因为**反向传播要把「前向每层的输出」一路带回起点**。一个 7B 左右的 Transformer，batch=8、seq=2048 时，激活动辄占几十 GB——这就是为什么训练一个大 batch 要先问「显存放不放得下激活」。推理没有反向，同样的输入激活只占几个 GB，省下的显存全被 KV 接管。<span class="marginnote">一个反直觉的结论：<strong>训练里 batch 越大越省算力、但越费显存（激活），推理里 batch 越大越省显存（KV 摊薄）、但越费算力（要喂更长的批）。</strong> 两者对 batch 的「口味」完全相反。</span>

再把 KV 的生命周期对比一下：训练里 KV 每步一建、反传一结束就释放，是**临时工**；推理里 KV 必须活到请求结束，甚至跨请求共享（第三篇的 Prefix Caching），是**常住客**。一个寿命以毫秒计、一个以秒计，管理它们的策略自然一个求快、一个求省。

## 3 批处理形态：固定形状大 batch vs 动态长短流

训练里样本可以 padding 到同一长度、拼成固定形状的张量，交给高度优化的 GEMM。形状越规整，kernel 越高效——训练框架因此喜欢**把世界整理成矩形**。

推理的请求是**随机到达、长短不一**的流：有的 prompt 3 token，有的 3000 token；有的输出 10 token 就 EOS，有的要吐 1000 token。把它们硬 padding 到同一长度，浪费巨大：

$$L_{\text{pad}} = L_{\max} - L_i$$

如果 10 条序列里最长 4096，其余都只有 512，padding 带来的算力浪费按比例算相当可观。**算一笔具体的账**：10 条序列、最长 4096、平均 1024，则填充 token 数 `$= 10 \times 4096 - 10 \times 1024 = 30720$`，而有效 token 只有 10240——**四分之三的算力花在 padding 上**。更糟的是，输出阶段每条序列的结束时间不同，先结束的还得陪跑到整批结束。推理引擎因此发展出 **Continuous Batching**：不再等一批集齐，而是每步把「当前活跃的序列」拼成一个临时 batch，做完的立即腾位、新来的立即补位——批的形状每步都在变。**训练框架无法承受这种每步变形的批量，这正是它不能直接服务推理的机械原因之一。**

不要误会成「训练完全没有 padding」。训练里也会用 **bucketing**（把相近长度的样本凑成一桶再 padding），但那是**静态的、离线优化的**——桶在训练前就分好，一个 epoch 内不再变化。推理的变长是**在线随机的**：请求像车流一样涌来，长短无法预测，只能靠每步的动态决策去接。静态的桶解决不了动态的车流。

## 4 公式解析：6N 规则——训练为什么注定是算力饥饿

为什么训练框架把一切压在「喂饱算力」上？因为训练的算力需求有一个**逃不掉的下界**。训练一个参数为 $N$ 的模型，处理每个 token 大约需要：

$$\text{FLOPs}_{\text{per-token}} \approx 6N$$

逐步拆解这个著名的「6N 规则」：

- **第一步，认前向的 2N**：每个参数参与一次乘法与一次加法，一次前向大约是 2N FLOPs——这是推理也算的那部分。
- **第二步，认反传的 4N**：反向传播要算两层梯度：激活梯度（误差往回传，约 2N）与权重梯度（约 2N）。于是每 token 总开销是 `$2N + 4N = 6N$`。**注意反传是前向的两倍**——训练比推理贵三倍，这正是「训练框架必须死磕算力峰值」的根源。
- **第三步，对照推理**：推理每 token 只有前向的 2N FLOPs，但它是**访存密集**的（第一篇的 Roofline 已经算过：单 token 要读全部权重）。于是同样 2N，训练里被算力淹没，推理里被带宽卡死。
- **第四步，得出分工**：训练框架要最大化「有效算力占比」，所以它痴迷于大 batch、算子融合、并行策略；推理引擎要最大化「带宽利用 × 并发调度」，所以它痴迷于 KV 优化、批的动态拼装、内存复用。**同一个 2N，两种完全不同的敌人。**

代入具体模型，这个差距触目惊心。7B 模型每 token 训练算 6N ≈ $4.2 \times 10^{10}$ FLOPs，一块 A100（FP16 约 312 TFLOP/s）的理论上限是每秒约 7400 token——但训练实际 MFU 往往只有 40%–60%，跑出几千 token/s 已算优秀。**推理每 token 只算 2N ≈ $1.4 \times 10^{10}$ FLOPs，理论上限反而更高，却因为访存瓶颈只能跑出每秒一百多 token（第一篇算过约 143）**。训练嫌算力不够，推理嫌带宽不够——同一个硬件，两种截然不同的稀缺资源。

## 5 连锁反应：框架层设计因此分道扬镳

前三节的目标差异，一路传导到框架的每一个层次：

- **自动微分 vs 纯前向**：训练框架的核心是 autograd 引擎，推理引擎连「不需要梯度」都写进内核里去省显存省时间。
- **静态图 vs 动态形状**：训练可以一次构图反复执行；推理的序列长度每步在变，引擎必须处理动态 shape，甚至用 CUDA Graph 捕获后按长度分桶（第十篇讲延迟调优时会碰到）。
- **并行策略**：训练靠数据并行（DP）做梯度同步，通信的是梯度；推理不做梯度，靠张量并行（TP）切权重、流水线并行（PP）切层、专家并行（EP）切 MoE 专家（第八篇）——通信的内容与模式完全不同。<span class="marginnote">训练也用 TP/PP，但目的是把超大模型放进显存；推理用 TP/PP 更多是为了「把延迟压下来」。同一套并行原语，两种动机，两种配置。</span>
- **数值精度**：训练常用 bf16/fp16 + fp32 优化器状态，精度要求高；推理可以降到 fp16/int8/fp8 甚至 4-bit（第六篇），因为生成对权重的量化扰动比梯度更新要宽容得多。<span class="marginnote">这个「宽容」不是偶然：训练时误差会被反向传播放大成千上万次；推理时权重只参与前向一次，量化误差是局部的。所以推理敢用更激进的低精度，训练不敢。</span>
- **权重的最终形态**：训练产出 checkpoint（包含优化器状态，体积翻几倍）；推理需要净化后的权重（去掉优化器状态、可能量化），并序列化成引擎格式（TensorRT-LLM 的 .plan、llama.cpp 的 GGUF，见第十一篇）。

**反过来说，训练框架的长处（自动微分、内存规划、大规模并行）恰好是推理引擎不擅长的**：没人用 vLLM 去训练一个 70B 模型。两种框架各守一个战场，只是引擎需要「借用」训练框架的模型定义与权重，而不是它的运行机制——这就是第 6 节要讲的边界。

**最后看执行循环本身。** 训练的主循环是**静态的**：`for epoch in range(...): for batch in dataloader: train_step(batch)`——步数预先知道、批次形状固定、节奏完全可控。推理的主循环是**事件驱动的**：请求在任意时刻到达、长度任意、EOS 随时可能触发，引擎每步都要重新决定「当前跑哪些序列、给谁分配显存、谁该被抢占」。这种「每步重新决策」的循环，训练框架没有对应的抽象——它根本不需要。

**这些差异不是细节，是分叉的树根**：训练框架的每一处设计都在为「高吞吐地算梯度」服务，推理引擎的每一处设计都在为「低延迟地发 token」服务。根不同，树当然不同。

## 6 辨析｜易错点：训练框架并非一无是处

把话说过头也是一种错误。训练框架在推理里并非完全没有位置：

**PyTorch 完全可以做推理，只是「裸跑」性能差、并发弱。** 所以现实里常见的路线是：PyTorch 负责模型定义与权重加载，推理引擎在其上接一层高性能内核与调度。vLLM 的模型代码就是 PyTorch 写的，SGLang 大量依赖 torch.compile，TGI 的模型层也基于 HF Transformers。**「引擎」不是取代训练框架，而是给训练框架套上推理的骨架。**

事实上，「训练框架与推理引擎」之间是一条连续谱，而不是一道墙：**纯 PyTorch 裸推理 → torch.compile 静态图优化 → 轻量推理层（如 TGI 的模型层）→ 完整推理引擎（vLLM/SGLang）→ 商业推理云服务**。越往右，调度、显存、服务化的能力越强，但也越「重」、越难定制。工程判断的核心是：你的负载需要停在谱系上的哪一格？大多数严肃的服务化需求会停在「完整推理引擎」这一格，而「为什么」正是前面五节的内容。

**辨析｜易错点：**

- **误区一：以为「推理引擎 = kernel 加速库」。** kernel 只解决「算得快」一项；调度、显存、服务化才是引擎的主体（第二章第一篇反复强调）。
- **误区二：以为训练框架做推理「只是慢一点」。** 慢只是表象，更深的问题是没有动态调度、没有 KV 管理、没有流式接口——纯 PyTorch 服务多用户会先爆显存和延迟，而不是先慢。即便你手写一个 Continuous Batching，没有配套的显存管理器，KV 碎片也会在几十个请求内把显存吃掉大半。
- **误区四：以为「训练快的框架推理一定快」。** 训练优化的是「把算力喂饱」，推理优化的是「把带宽用好」，两者几乎不共享优化手段。DeepSpeed 训练吞吐顶级，拿来服务推理并不比一个调度良好的引擎强——这是「目标函数不同」最直接的反例。
- **误区三：以为「推理框架也能顺手训练」。** 可以，但同样不是设计目标：vLLM 能微调 LoRA，SGLang 能算损失，但吞吐与显存优化都偏向推理形态。用引擎训练，等于用客车拉货。

## 7 小结

把这一节的六组对照放在一起，一张表就能装下：

| 维度 | 训练框架 | 推理引擎 |
| --- | --- | --- |
| 目标 | 吞吐优先（MFU） | 延迟敏感（TTFT/TPOT/P99） |
| 显存大头 | 激活（反传要留） | KV Cache（逐 token 增长） |
| 批形态 | 固定形状大 batch | 动态长短随机流 |
| 每 token 算力 | 6N（反传拖累） | 2N（纯前向） |
| 主要瓶颈 | 算力 | 带宽 |
| 精度 | bf16/fp32 保守 | int8/fp8/int4 激进 |
| 执行循环 | 静态 epoch | 事件驱动 |

- **一句话总纲**：训练是吞吐优先的批处理作业，推理是延迟敏感的交互式批处理。
- **显存画像**：训练被激活主导（反传要留中间值），推理被 KV 主导（随序列动态增长）；省显存的手段因此不同（重计算 vs 页式/量化）。
- **批形态**：训练爱固定形状大 batch，推理是长短不一的随机流；Continuous Batching 让批的形状每步在变。
- **6N 规则**：训练每 token 约 6N FLOPs（前向 2N + 反传 4N），注定算力饥饿；推理每 token 只算 2N 却访存密集，注定带宽饥饿。
- **框架分叉**：自动微分 vs 纯前向、静态图 vs 动态形状、DP 同步梯度 vs TP/PP/EP 切模型。
- **边界模糊**：引擎不取代训练框架，而是给它套推理骨架；用引擎训练、用框架裸推理都能跑，只是都不是设计主场。
- **执行循环**：训练是静态的 epoch 循环，推理是事件驱动的动态循环——每步都要重新决定跑谁。
- **数值精度**：训练保守（bf16/fp32），推理激进（int8/fp8/int4）——误差传播路径不同，容忍度天差地别。

在下一节，我们要把这套「框架差异」变成**动手能力**：面对一个推理引擎的源码，该按什么顺序读、用哪几把尺子评估——「如何阅读和评估一个推理引擎的源码」。
