## 为什么从监控指标开始

推理服务上线不是终点——它要 24 小时稳定运行，而稳定性靠**监控**维持：没有指标，你就不知道服务什么时候开始变慢、显存什么时候要爆、哪类请求在大量失败。监控体系回答三件事：**服务现在健康吗**（指标）、**问题出在哪**（日志与追踪）、**什么时候要报警**（告警）。<span class="marginnote">本专题《压测与调优》会讲怎么测出服务的能力上限；本篇讲<strong>上线后怎么持续看住它</strong>——测量的是「当前状态」，而非「压出来的极限」。</span>

本篇讲推理服务的黄金指标、监控的三支柱（指标/日志/追踪）、以及告警设计的原则。

## 1 LLM 服务的黄金指标

监控指标里，有几项是「一票否决」级别的——它们直接反映用户可感知的质量与服务的健康：

- **TTFT（首 token 延迟）**：请求发出到第一个 token 的时间。**用户等待的第一印象**，prefill 慢或队列深都会让它飙升。
- **TPOT（每 token 时间）/ ITL（token 间延迟）**：生成速度，反映 decode 是否健康。
- **端到端延迟**：完整请求的耗时，与 TTFT、TPOT 及生成长度相关。
- **吞吐**：每秒完成的请求数 / 每秒生成的 token 数（RPS / TPS）。
- **错误率**：5xx、超时、拒绝（429）的占比。
- **队列深度 / 排队请求数**：调度器积压程度，是延迟的前瞻指标。<span class="marginnote">延迟是「结果」，队列是「原因」。<strong>队列深度起来 10 秒后，延迟才会起来</strong>——盯队列能提前发现过载，是「预防式监控」的关键指标。</span>
- **GPU 指标**：显存占用、SM 利用率、显存带宽利用率、温度/功耗。**显存是硬上限，温度是降频的诱因**。

**核心指标三件套（RED）**：Rate（每秒请求数）、Errors（错误占比）、Duration（延迟分布）——这是任何 Web 服务的基础监控，LLM 服务在此基础上叠加 token 与 GPU 维度的指标。

## 2 监控三支柱：指标、日志、追踪

- **指标（Metrics）**：聚合的数值序列（延迟 P50/P99、吞吐、显存），用 Prometheus 采集、Grafana 展示。回答「现在整体怎么样」。
- **日志（Logs）**：每条请求的记录（模型、token 数、延迟、错误码）。回答「这个具体请求发生了什么」。LLM 日志特别要记：**prompt 的截断摘要、生成 token 数、finish_reason、路由去向**——这些是排查「模型回答异常」的第一手资料。<span class="marginnote">日志不是越多越好：<strong>完整 prompt 可能几千 token、占存储又涉隐私</strong>。工程上记「截断 prompt + 元数据 + 输出前 100 token」的摘要式日志。</span>
- **追踪（Traces）**：一次请求穿过「网关 → 路由 → 引擎 → GPU kernel」的每一跳耗时。回答「慢在哪一层」。LLM 的追踪要标记 prefill/decode 的分段耗时——**一段 2 秒的请求，是 prefill 占了 1.8 秒还是 decode 占了 1.8 秒，排查方向完全不同**。

**三支柱配合**：指标发现问题（P99 飙升）→ 追踪定位阶段（decode 慢）→ 日志定位请求（某个长 prompt）→ 复现修复。缺任何一个，排查都会像大海捞针。

## 3 告警设计：别让告警变成噪音

告警是把「异常」转成「人工介入」。设计差，告警会变成噪音（狼来了效应），真正出问题时没人看。告警设计四原则：

- **阈值要基于基线**：告警阈值来自「正常时段的统计基线」（如 P99 的 3 倍），而不是拍脑袋的数字。**基线动态化**（按天/时段滚动更新）比固定阈值准。
- **只告警「需要人动」的事件**：自动能恢复的（短暂排队）不告警，告警「持续性过载」「错误率持续上升」「显存将耗尽」这类要人决策的事件。<span class="marginnote">「显存将耗尽」是典型的「<strong>提前量告警</strong>」——等 OOM 了才告警就晚了，要在显存达到 85% 时告警，给扩容留时间。</span>
- **告警要有分级**：P0（服务不可用，立即响应）、P1（SLA 受损，当天处理）、P2（潜在风险，观察）。**分级决定响应时效，别让 P2 的事吵醒半夜值班的人**。
- **告警要可行动**：每条告警附「如何排查」的指引（看哪个面板、查哪个日志）——告警的目标是「让人知道下一步做什么」，不是「让人知道出事了」。

## 4 公式解析：用延迟分布而不是平均值

监控延迟最常见的错误是「看平均延迟」。平均延迟会被少数慢请求拉高、也会掩盖「大量请求其实很快」。正确做法是看**百分位分布（P50/P95/P99）**：

$$P_{99} = \inf\{t : F(t) \ge 0.99\}$$

- **第一步，读定义**：$F(t)$ 是延迟的累积分布函数，$P_{99}$ 是「99% 的请求快于它」的那个阈值。**P99 刻画「最差的那 1% 用户」的体验**。
- **第二步，读为什么不用平均**：平均延迟 $\bar{t} = \frac{1}{N}\sum t_i$ 被极端值主导。一个 100 秒的超长请求能把平均拉到 2 倍，但 P99 几乎不受影响——**平均掩盖长尾，P99 暴露长尾**。
- **第三步，读告警含义**：LLM 服务的告警应设「P99 超阈值」而非「平均超阈值」：平均超了可能是被一个坏请求带的，P99 超了才是「普遍变慢」。**用分位数做告警基线，是延迟监控的基本功**。

## 5 小结

- **黄金指标**：TTFT、TPOT/ITL、端到端延迟、吞吐、错误率、队列深度、GPU 指标；RED 三件套打底。
- **队列深度是前瞻指标**：队列起来 10 秒后延迟才起来，盯队列能提前发现过载。
- **三支柱配合**：指标发现异常、追踪定位阶段、日志定位请求，缺一不可。
- **告警设计四原则**：阈值基于基线、只告警需人动的事、分级响应、可行动指引。
- **用分位数不用平均**：P99 暴露长尾，平均掩盖长尾，告警基线应基于分位数。
