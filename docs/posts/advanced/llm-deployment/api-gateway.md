## 为什么从 API 网关开始

推理服务暴露成 API 之后，直接让用户打到推理引擎是很危险的：没有鉴权任何人都能调用、没有限流一个请求洪峰就能打满 GPU、没有计量就不知道谁用了多少、无法计费。**API 网关**站在请求入口统一处理这些问题——它是推理服务的「门卫、门禁与账房」。<span class="marginnote">本专题《OpenAI 兼容 API》讲了「API 长什么样」，本篇讲<strong>API 前面的那层基础设施</strong>：鉴权（你是谁）、限流（你最多用多少）、计费（你用了多少要付多少钱）。</span>

本篇讲网关的三大职责、LLM 场景的特殊限流（token 级而非请求级）、以及计费模型怎么基于 token 计量。

## 1 鉴权：请求的身份认证

网关的第一道门是**鉴权（authentication）**：确认「你是谁、能不能用」。常见机制：

**API Key**：客户端在请求头带 `Authorization: Bearer <API_KEY>`，网关查 key 是否有效、属于哪个租户。这是最普遍的 LLM 服务鉴权方式。<span class="marginnote">API Key 的本质是<strong>「长期凭证 + 服务端校验」</strong>。生产环境还要配套：Key 加密存储、轮换机制、泄露告警（检测到异常使用自动吊销）。</span>
**OAuth2 / JWT**：企业场景用标准身份协议，网关验证 token 签名与有效期，适合与既有身份系统打通。
**租户隔离**：鉴权完成后，网关把请求绑定到「租户 ID」，后续的限流与计费都按租户维度计量。

**鉴权失败的响应**：401（未认证）/ 403（无权限）。错误响应要遵循 OpenAI 兼容的 `error` 结构（见 OpenAI API 篇），客户端才能正确解析。

## 2 限流：LLM 的特殊之处

传统 Web 限流按「请求数/秒」计。LLM 场景这个指标严重失真——一个 100k token 的请求比 100 个 1k 请求更重。因此 LLM 网关的限流要**按 token 计量**：

**令牌桶（token bucket）**：每个租户一个「桶」，桶容量是「每分钟/每天可用 token 上限」。请求到达时按它的 prompt token 数扣减，桶空则拒绝（429）。
**并发限制**：除 token 外，还要限制「同时进行的请求数/流式连接数」——GPU 显存是硬上限，并发过载会 OOM。按「实例的 max-num-seqs」反推网关侧的并发阈值。<span class="marginnote">限流的三层防线：<strong>网关层（请求级 + token 级）→ 引擎层（调度器的队列上限）→ GPU 层（显存上限）</strong>。网关限流防「滥用」，引擎调度防「过载」，GPU 显存防「崩溃」。</span>
- **阶梯限流**：不同租户/套餐不同限额（免费用户日限额、付费用户高限额），网关按 key 对应的配置执行。

**辨析｜易错点：限流响应要「软」也要「准」。** 超限返回 429 + `Retry-After` 头（告诉客户端多久后再试），这是标准行为。别把超限当 500（服务故障）——**429 是「客户端的错」，500 是「服务端的错」**，语义搞错客户端会疯狂重试加剧雪崩。

## 3 计费：基于 token 的计量

计费依赖「用了多少」。前一篇讲过 usage 的 `prompt_tokens` 与 `completion_tokens`——网关要**在返回路径上可靠地捕获并记录**：

$$\text{bill} = p_{\text{in}} \cdot \text{prompt\_tokens} + p_{\text{out}} \cdot \text{completion\_tokens}$$

其中 $p_{\text{in}}$、$p_{\text{out}}$ 是输入/输出单价（通常输出比输入贵 2–4 倍，因为 decode 更贵）。<span class="marginnote">流式请求的计费最容易出错：<strong>流式的 usage 要在流结束（<code>[DONE]</code>）时从引擎取最终计数</strong>，而不是在响应头里——中途断流的请求也要记账（已生成的 token 照计）。</span>

计费链路还要处理：**重试与幂等**（客户端重试导致重复计费，用请求 ID 去重）、**失败请求**（500 不收费，429 不收？——通常 429 也计 prompt 部分）、**账单周期**（按日/月汇总，出账单）。

## 4 公式解析：令牌桶限流的参数设计

令牌桶的关键参数：桶容量 $C$（瞬时突发上限）与填充速率 $r$（持续速率上限）。请求 $j$ 的 token 消耗为 $u_j$，桶余额 $b$ 的演化：

$$b \leftarrow \min(C,\; b + r \cdot \Delta t - u_j)$$

- **第一步，读填充项**：$r \cdot \Delta t$ 是时间 $\Delta t$ 内「补进」的 token——$r$ 决定持续可用速率。
- **第二步，读消耗项**：$-u_j$ 是这次请求扣掉的 token。**$u_j$ 用 prompt token 而非请求数**——一个 100k 请求把桶打空，一个 10-token 请求几乎无感。
- **第三步，读桶的作用**：$C$ 决定「能否突然来一个大请求」。$C$ 大则允许突发（但事后要慢慢补），$C$ 小则突发直接被拒。**设计 $r$ 与 $C$ 的依据是 GPU 容量与租户 SLA**：$r$ 要 ≤ 实例群的实际 token 吞吐，$C$ 要与「单次最大请求」匹配。

## 5 数值算例：一次完整的请求流

把一个请求从进网关到出网关走一遍，看三大职责怎么协同。设某租户的套餐：令牌桶 $r = 10$ 万 token/分钟、$C = 50$ 万 token、并发上限 32。收到一个 `Authorization: Bearer sk-xxx` 的请求：

1. **鉴权**：网关查 `sk-xxx` 有效、属于租户 A，把请求绑定租户 ID。key 无效则返回 401；key 有效但套餐欠费/被封则 403。
2. **限流**：解析出该请求 prompt 3 万 token，从租户 A 的桶余额 $b$ 扣减。若 $b - 30000 < 0$ 则拒绝，返回 429 + `Retry-After: 6`（按 $r$ 补够 3 万 token 所需时间）。
3. **转发与生成**：通过后转发到推理引擎；同时检查并发计数，超过 32 则排队或 429。
4. **计费**：流式完成后从引擎取最终 usage（如 prompt 30000、completion 5000），按单价入账：$0.003 \times 30000 + 0.006 \times 5000 = 120$ 美元分（即 $1.20）。响应若 500，则不记 completion 部分。

把这四步对应到网关的「门卫、门禁、账房」三个角色，就明白网关的每一层职责在哪条路径上生效。

一个 429 的例子最直观：租户 A 的桶余额只有 1 万 token，却发来一个 3 万 token 的请求。**网关在第 2 关就拦下，引擎根本不会被打扰**——这就是网关「前置保护」的价值：把不该进的服务挡在门外，引擎只服务「通过了」的请求。<span class="marginnote"><strong>一次请求在网关里至少要「过四关」</strong>：鉴权 → 限流 → 转发 → 计费。每一关都独立失败、独立重试，任何一关没设计好，整个入口都不可靠。</span>

## 6 网关的高可用与运维

网关是单点吗？不是，但网关高可用有它自己的讲究：

**网关无状态**：鉴权、限流、计费的状态（key 表、令牌桶、账单）存在共享存储（Redis/DB），网关实例本身无状态、可水平扩缩容。**挂掉一台网关，流量自动切到另一台**——网关层的高可用靠「无状态 + 多副本」。

**限流状态的一致性**：令牌桶存 Redis，多实例并发扣减要原子（用 Lua 脚本或 Redis 的原子操作），避免「同时扣了两次」。**限流状态不一致会导致超卖**——实际 token 消耗超过桶容量。

**网关的容量**：网关转发是「透传 + 流式」，CPU 占用远低于推理引擎，**一台网关可扛几千 QPS**。但要注意：网关处理的是「字节流」，流式响应要边收边转发，不能等整个响应结束再返回（那会引入巨大延迟）。

**监控**：网关要单独监控——鉴权失败率（暴力破解信号）、429 比例（限流是否过严）、单请求计费金额、网关自身延迟与错误率。**网关的监控是「业务健康」的第一面镜子**：QPS、计费金额、429 比例都在这里，比引擎指标更接近业务。

**辨析｜易错点：别把网关当「万能中间层」加太多逻辑。** 每加一层逻辑（数据脱敏、A/B 路由、内容审核），网关延迟与故障面就多一分。**网关要薄，业务逻辑下沉到服务层**——网关守住「鉴权、限流、计费」三件事就够，别什么都往里塞。

把网关的常见故障列成速查表，报障时快速对照：

| 症状 | 根因 | 对策 |
| --- | --- | --- |
| 大量 429 | 限流过严 / 桶参数太小 | 调大 $r$ 或按租户分桶 |
| 401 激增 | API Key 泄露被爆破 | 吊销 + 限频 + 告警 |
| 计费对不上 | 流式断流没记 completion | 流结束统一取 usage |
| 网关延迟高 | 流式缓冲了完整响应 | 边收边转发、别缓存全文 |
| 令牌超卖 | Redis 扣减非原子 | 用原子操作扣 token |

网关要盯的业务指标清单：

- **QPS 与 token 吞吐**：反映用量曲线，是扩缩容的依据。
- **429 / 401 比例**：限流是否过严、是否有爆破。
- **单请求计费金额与账单周期**：账能不能对上。
- **网关自身 P99 延迟**：网关不能成为新瓶颈，应远低于引擎延迟。
- **租户维度用量**：谁用了多少、是否超套餐，支撑计费与销售。

这五行故障表加五个指标，就是网关运维的最小闭环——**日常看指标、出问题查表格、其余交给引擎层**。

**网关不要变成新的「故障点」**：它守护业务入口，自身却要尽量「薄、快、无状态」——无状态才能水平扩缩、薄才能不拖延迟、快才能扛住高 QPS。

## 7 小结

- **鉴权确认身份**：API Key / OAuth2 / JWT，请求绑定租户 ID，后续限流计费按租户执行。
- **限流按 token 计而非请求数**：令牌桶 + 并发限制 + 阶梯限额，三层防线（网关/引擎/GPU）。
- **429 是客户端问题**：带 `Retry-After` 头，与 500 的语义严格区分，避免雪崩。
- **计费基于 usage**：输入/输出不同单价，流式请求在流结束时取最终计数，注意幂等与去重。
- **令牌桶参数**：$r$ 匹配集群吞吐、$C$ 匹配单次最大请求，设计依据是 GPU 容量与 SLA。
- **请求过四关**：鉴权 → 限流 → 转发 → 计费；网关无状态多副本，状态放共享存储，监控看业务健康。
