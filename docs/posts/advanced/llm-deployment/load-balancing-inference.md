## 为什么从负载均衡开始

推理服务集群面前排着海量请求，谁来接？**负载均衡（load balancing）**把请求分发给后端实例。普通 Web 服务有成熟的轮询、最少连接等策略；但 LLM 推理服务有两个让传统策略失灵的特点：**请求的「重量」极不均衡**（一个 10-token 请求和一个 10 万-token 请求差 4 个数量级）与**缓存命中决定成本**（见 Cache-aware 路由篇）。<span class="marginnote">本专题《Cache-aware 路由》讲的是「面向缓存命中」的路由（SGLang 的 Router）；本篇讲<strong>通用负载均衡</strong>——面向「集群资源利用率」的分发策略，两者常常叠加使用。</span>

本篇讲传统负载均衡为什么不够、LLM 场景的「重量感知」负载均衡、以及如何把「缓存命中」与「负载均衡」两个目标协调。

## 1 传统策略为什么失灵

经典负载均衡策略在 LLM 推理前的失效方式：

- **轮询（round-robin）**：轮流分配。一个 100k token 的 prefill 请求落到某实例，该实例的 GPU 被占满、后续请求全排队，而其他实例闲着。**平均分配掩盖了重量不均**。
- **最少连接（least-connections）**：按「正在处理的请求数」分。但 LLM 里「1 个 100k 请求」比「100 个 1k 请求」重得多——**请求数不是重量的代理**。
- **IP 哈希（一致性哈希）**：同一来源固定到同一实例，能提升缓存命中，但负载会随来源分布而严重倾斜。<span class="marginnote">传统策略的共同假设是「请求成本可忽略且同质」，LLM 请求显然不满足。<strong>LLM 负载均衡的第一课：请求的重量差异巨大，必须按「重量」而不是「个数」度量。</strong></span>

## 2 重量感知的负载度量

要正确分负载，先要正确度量「实例现在有多忙」。候选指标（延续 Cache-aware 篇的思路，这里系统化）：

| 指标 | 优点 | 缺点 |
| --- | --- | --- |
| 请求数 | 便宜 | 完全忽略重量差异 |
| 批内 token 总量 | 贴近 GPU 工作量 | 无法反映 prefill/decode 差异 |
| KV Cache 占用比例 | 反映容量余量 | 不反映算力余量 |
| 预估剩余生成时长 | 最准 | 需要预测，成本高 |
| 混合权重（token 数 × 阶段系数） | 实用平衡 | 系数需要标定 |

**实用方案**：把「正在跑 + 正在排队的请求」换算成「等效 token 负载」——prefill 阶段每个 token 计算量大（系数高），decode 阶段每个 token 访存大（系数按带宽折算）。实例的繁忙度 = 其等效负载 / 容量上限。**负载均衡器按「繁忙度」而非「请求数」分配**，把新请求发给最闲的实例。<span class="marginnote">「最闲」的度量决定了均衡质量。<strong>工程上常把「显存中 KV 占用」与「队列 token 数」合成为评分</strong>，越接近实例的真实饱和程度越准。</span>

## 3 负载均衡 × 缓存命中的协调

普通负载均衡追求「均匀」，缓存路由追求「命中」，两个目标在同一个请求上打架：均匀分发会把相同前缀的请求打散到不同实例，缓存命中率大降；而「粘到同一实例」又会造成负载倾斜。

协调策略有三种：

- **命中优先 + 负载兜底**：请求先查「哪个实例缓存了最长前缀」，如果该实例的繁忙度低于阈值，就去；否则退而求其次。**这是 SGLang Router 的主策略**（见 Cache-aware 篇）。
- **缓存预热 + 均匀分发**：热点前缀预先复制到多台实例的缓存里，然后可以放心均匀分发——每个实例都有缓存，命中率不降。**用「多副本」换「均匀自由」**。
- **分桶路由**：把实例按「缓存域」分组，请求按前缀哈希进组，组内再负载均衡。**两级决策：组间缓存感知，组内均匀**。

**辨析｜易错点：缓存命中的收益有上限，别为它牺牲负载均衡。** 缓存命中的收益是「省 prefill 计算」，但负载倾斜的代价是「部分实例过载、整体吞吐下降」。**当命中收益（省下的算力）小于负载不均的代价时，应放弃命中、选择均衡**。判断公式见下节。

## 4 公式解析：命中优先 vs 均衡的权衡

设请求命中缓存时省下的 prefill 成本为 $C_{\text{save}}$，坚持命中导致该实例过载、拖慢同实例其他请求的代价为 $C_{\text{congest}}$。

- **第一步，写命中策略的净收益**：命中策略的期望收益 $= \Pr(\text{命中}) \cdot C_{\text{save}} - \Pr(\text{过载}) \cdot C_{\text{congest}}$。
- **第二步，写均衡策略的收益**：均衡策略 $= 0$（不追求命中，也不承担过载风险）。
- **第三步，看决策边界**：命中策略占优当且仅当

$$\Pr(\text{命中}) \cdot C_{\text{save}} > \Pr(\text{过载}) \cdot C_{\text{congest}}$$

当流量大（$\Pr(\text{过载})$ 上升）或命中率低时，不等式翻转——**此时必须切回均衡策略**。这也是「命中优先 + 负载兜底」策略的数学依据：先试命中，但「过载风险超过阈值就放弃」。

## 5 小结

- **传统策略（轮询/最少连接/哈希）在 LLM 场景失灵**：请求重量差异 4 个数量级，按「个数」度量失真。
- **重量感知度量**：把请求折算成等效 token 负载，prefill 与 decode 系数不同，实例繁忙度 = 负载/容量。
- **两个目标要协调**：命中优先 + 负载兜底、缓存预热多副本、分桶路由，是三种工程策略。
- **别为命中牺牲均衡**：命中收益 < 过载代价时切回均衡，边界由概率与成本决定。
- **与 Cache-aware 路由叠加**：负载均衡管「资源利用率」，缓存路由管「计算复用」，两者结合才完整。
