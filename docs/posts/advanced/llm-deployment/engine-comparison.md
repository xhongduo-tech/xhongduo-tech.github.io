## 为什么从「摆开对比」开始

上一节我们把推理引擎的核心问题归成五族：算得对、算得快、装得下、调度得动、服务得稳。但问题清单不是答案——同一个问题，vLLM、SGLang、TensorRT-LLM、TGI 给出了四套不同的解法，且都活得好好的。**这恰恰说明不存在「最好」的引擎，只存在「与你的负载、硬件、团队最匹配」的引擎。**

这一节不是产品测评，而是**技术路线的解剖**：把四家引擎各自站在哪个坐标点上讲清楚。读完之后，当你面对「我这个场景该上谁」时，能用五类核心问题当尺子自己量，而不是听别人拍脑袋。需要提醒的是，**本专题所写的引擎细节都有「保质期」**：vLLM 在 2025 年重写了 V1 调度器，SGLang 的 Router 架构也在快速迭代——但三条分水岭与技术取舍的框架是稳定的，变化的是实现细节。<span class="marginnote">记住戴明这句话：网上关于「谁更快」的争吵，大多没有数据。选引擎的唯一可靠办法，是把你的真实负载压上去测——第十篇会专门讲怎么测。</span>

## 1 四家引擎的名片

先认人。四家引擎出生地、血统与主打卖点各不相同，这决定了它们各自的基因：

- **vLLM**：加州大学伯克利分校 SkyLab 发起，2023 年 10 月开源。以 **PagedAttention**（页式 KV 内存管理）一炮而红，配套 Continuous Batching。Python 为主，社区最大、功能迭代最快，2025 年推出全新 V1 架构（第三篇专门拆解）。<span class="marginnote">vLLM 现在几乎是「开源推理引擎」的代名词：新模型发布后，最快拿到推理支持的通常是它。这与它巨大的社区与可插拔的后端设计直接相关。</span>
- **SGLang**：伯克利 LMSYS 团队（Chatbot Arena 的维护者）开发，2024 年开源。主打 **RadixAttention**（前缀树 KV 共享）、**结构化输出**（用有限状态机做约束解码，能逼真地输出 JSON/正则）、**Router/Runtime 前后端分离**。目标是把「复杂 Agent 推理链」服务得又快又稳。
- **TensorRT-LLM**：英伟达官方出品，2023 年底开源。C++/CUDA 血统，建立在 TensorRT 图优化之上，**编译期做算子融合与内核调优**，对自家 GPU（H100 的 FP8、FP4）做最深定制。要极致榨干英伟达硬件，它是参考答案。
- **TGI（Text Generation Inference）**：Hugging Face 官方发布，Rust 后端 + Python 封装，深度集成 HF Hub 生态——safetensors 秒级加载、模型自动下载、与 HF Inference Endpoints 开箱即用。**是「省心」路线的代表**。

再补一条容易被忽略的维度：**许可证与商业化风险**。四家都是开源，但许可证与治理模式不同——vLLM 与 SGLang 是宽松的 Apache 2.0，TGI 也是，TensorRT-LLM 同样是开源但深度绑定英伟达的 CUDA 生态。对个人与学术研究，差别不大；对要商业化部署、或要求「不被单一家硬件绑定」的企业，这是选型时该尽早确认的一栏。

一句话给这张名片收尾：**vLLM 是社区之选，SGLang 是正确性之选，TensorRT-LLM 是硬件之选，TGI 是生态之选。**

这四家的出生时间差不到一年，却代表了三种「解决推理问题」的哲学。**vLLM 先把「内存」这关打通（页式 KV），SGLang 再把「正确性」这关打通（约束解码），TensorRT-LLM 则从硬件往上做编译期优化**——每一个都是在前人没走通的地方另起炉灶。理解这个先后顺序，就理解了为什么它们的代码风格如此不同：vLLM 像实验室里的灵活原型，SGLang 像为复杂场景设计的精工仪器，TensorRT-LLM 像工厂里的高度自动化产线，TGI 像集成度最高的整机。

## 2 用「五类核心问题」做坐标系

把上一节的五类问题当表格的行，四家引擎当列，立刻看出各自把力气花在哪：

| 维度 | vLLM | SGLang | TensorRT-LLM | TGI |
| --- | --- | --- | --- | --- |
| 算得对 | 采样器完备、支持复现 | **约束解码最强**（正则→FSM） | 采样器随框架，约束弱 | 采样器完备 |
| 算得快 | 可插拔内核（FlashAttention/FlashInfer） | torch.compile + Triton 内核 | **编译期图优化 + 定制 CUDA** | 工程化稳定、非激进 |
| 装得下 | **PagedAttention 页式** | RadixAttention 前缀共享 | 内存池 + 编译期规划 | 简单内存管理 |
| 调度得动 | Continuous Batching + 抢占 | Cache-aware 路由 + 负载感知 | In-flight Batching | Continuous Batching |
| 服务得稳 | OpenAI 兼容 API 最成熟 | Router/Runtime 分离 | 需自建服务层 | **HF 生态原生集成** |

读这张表，重点不是背谁强谁弱，而是看**各自的取舍**：SGLang 把宝押在「正确性」与「调度」上，因为它的目标场景是复杂的多轮 Agent 调用；TensorRT-LLM 把宝押在「快」上，因为硬件是它自家造的；TGI 把宝押在「稳与省心」上，因为它的用户是 Hugging Face 的广大普通用户。

还应该留意一个事实：**vLLM 目前是「木桶最均衡」的那个**。它没有某一项做到极致，但每一项都在第一梯队，加上社区最大、新模型适配最快、OpenAI 兼容层最成熟，于是它成了行业默认。极致选手（SGLang 的正确性、TensorRT-LLM 的性能）是在「默认选项不够用」时拿出来替换某一环的——这个「默认 + 替换」的框架，比「谁最好」更有用。

同样值得观察的是**四家的生态圈**：vLLM 旁边围绕着一圈量化工具（AWQ、GPTQ 的集成）、模型库与第三方后端；SGLang 的生态集中在 Agent 与结构化输出方向；TGI 的生态就是 Hugging Face 全家桶；TensorRT-LLM 的生态则是英伟达的 TensorRT 与 Triton 推理服务器。**选引擎也等于选生态**：生态决定了你遇到问题时能否找到现成解法，决定了新特性能否快速用上，长期来看比一时的性能差更重要。

## 3 三条技术路线的分水岭

同样的五类问题，为什么解法会分裂成这么不同的样子？因为背后有**三条分水岭**：

**分水岭一：内存管理选「页」还是选「树」。** vLLM 把 KV 切成固定大小的页，按需分配（PagedAttention）；SGLang 更进一步，把「共享前缀」提升为一等公民，用**前缀树（radix tree）**组织 KV 块，让不同请求复用同一段前缀（RadixAttention）。TensorRT-LLM 走编译期路线：在构建引擎时把内存布局规划好，运行时用内存池管理。<span class="marginnote">RadixAttention 与 PagedAttention 并非对立：SGLang 的块表结构本身也是页式的。区别在于 SGLang 把「共享」做进了树里，而 vLLM 的共享要靠 Prefix Caching 层在块表上做写时复制——这层关系在第四篇讲 PagedAttention 时还会回来。</span>

**分水岭二：内核是「插上去」还是「编译出来」。** vLLM 的注意力后端是可插拔的（社区贡献 FlashAttention、FlashInfer、xformers 等实现，运行时挑选）；SGLang 大量使用 torch.compile 与 Triton，边跑边 JIT 生成内核；TensorRT-LLM 则在前端建图、后端编译，产出**预编译引擎文件**（.plan 后缀），运行时不再做任何优化决策。这条分水岭直接决定了「换模型快不快」：vLLM 装上新权重就能跑，TensorRT-LLM 要先重新构建引擎（从几分钟到几十分钟）。

**分水岭三：调度是「业务逻辑」还是「硬件配套」。** vLLM、SGLang、TGI 都把调度器做成 Python 里的显式业务逻辑，可读、可改、可调参；TensorRT-LLM 的 In-flight Batching 是引擎内置的 C++ 运行时，速度快但改起来门槛高。这解释了为什么学界与社区的新调度思路（Chunked Prefill、抢占策略、Prefix Caching）几乎总是先在 vLLM/SGLang 里落地，再回头被商业引擎吸收。

三条分水岭叠加，就是一份「读源码指南」：想理解 KV 内存管理，去 vLLM 的 `block_manager` 与 SGLang 的 RadixCache；想理解调度，去 vLLM 的 `scheduler.py`；想理解编译期优化，去 TensorRT-LLM 的引擎构建代码。**你关心哪一类问题，就有哪一家引擎的主干最适合你先读**——下一节《如何阅读和评估一个推理引擎的源码》正是把这条对应关系变成实操。

## 4 公式解析：内存利用率决定并发上界

对比引擎最硬的一杆秤，是**同一个 GPU 上能同时跑多少请求**。它比「单请求多快」更根本：并发上界决定了服务能扛住多少在线用户、决定了一条 A100 是服务 30 个人还是 120 个人，进而决定了每 token 的成本（第十二篇）。回顾第五篇的 KV 显存估算，并发的物理上界是：

$$N_{\max} = \left\lfloor \frac{M_{\text{avail}} - M_{\text{weights}} - M_{\text{act}}}{\bar{K}_{\text{seq}}} \right\rfloor$$

逐步拆解：

- **第一步，认分子**：`$M_{\text{avail}} - M_{\text{weights}} - M_{\text{act}}$` 是「扣掉常驻权重与激活预留后，还能给 KV 用的显存」。权重要一直住在显存里（模型加载篇讲过），激活要留一块应付前向计算。
- **第二步，认分母**：`$\bar{K}_{\text{seq}}$` 是每个序列的平均 KV 显存，随模型结构（层数、KV 头数、头维）与平均上下文长度变化，第五篇的估算公式在这里直接用。
- **第三步，找隐藏变量**：公式里藏着一个「浪费系数」。如果按连续分配，一条序列必须**按最大可能长度**预留 KV，那么 `$\bar{K}_{\text{seq}}$` 取的是最坏情况；页式管理只按实际长度分配，`$\bar{K}_{\text{seq}}$` 接近真实均值。**引擎的差异就藏在这个系数里。**
- **第四步，代入数字**：A100 80 GB、7B FP16（权重约 14 GB）、预留激活 4 GB，剩下约 62 GB 给 KV。7B 每 token 的 KV 约 512 KB，平均上下文 1024 token 的序列占约 0.5 GB——页式管理下 `$N_{\max} \approx 124$` 条并发；若连续分配按最大长度 4096 预留，每序列 2 GB，`$N_{\max}$` 跌到约 31。

注意这个估算里的两个「隐藏变量」，正是各家引擎真正竞争的战场：一是**平均上下文长度**——长上下文场景（如 Agent 的多轮累积）会让 $K_{\text{avg}}$ 暴涨，此时前缀共享的价值直线上升；二是**权重体积**——量化到 FP8 后权重减半，等于给 KV 腾出一大块，所以量化（第六篇）与 KV 优化（第三章）常常是配套动作。

**页式把并发上界放大了约四倍，这正是 vLLM 那篇论文里「利用率从 20%–38% 提到 90%+」的由来。** 至于「为什么按页切就能把浪费压到一页以内」，是下一章《PagedAttention》的主线，这里先立住结论。

把同样的账套到另两家，你就能看懂它们的设计取舍：SGLang 的 RadixAttention 在页式之上再加一层**前缀共享**，让「多请求共享同一段前缀」时 $K_{\text{avg}}$ 进一步缩小——同一个 1024 token 的 prompt 被 10 条请求共享，10 条只算一份 KV；TensorRT-LLM 则在编译期把内存布局定死，运行时零分配开销，代价是长度变化时要重建引擎。**同一杆秤，三家各用一个砝码压下去**：vLLM 压内部碎片，SGLang 压前缀重复，TensorRT-LLM 压运行时开销。

## 5 怎么选：一张决策清单

把前面的坐标系收拢成决策指南。判断你的场景属于哪一档：

（先记住一条总原则：**引擎不是信仰，是工具。** 生产系统里真正重要的不是「我用了哪个引擎」，而是「我的 SLO 达没达标、成本合不合理」。选型决定权永远应该交给压测数据，而不是社区口碑。）

- **要省心、要 Hugging Face 生态**（模型多、要自动下载、要跟 Inference Endpoints 无缝）→ **TGI**。
- **要最大并发、要社区功能、要最快的模型适配速度**（新模型发布当天就要跑）→ **vLLM**，它是事实上的默认选项。
- **要做复杂的结构化输出、多轮 Agent 推理链、想用程序式语言编排** → **SGLang**，它的约束解码与 Router 架构是为这类负载生的。
- **要榨干英伟达硬件**（H100/H200 的 FP8/FP4、极致的 kernel 性能、低延迟）→ **TensorRT-LLM**，代价是构建引擎慢、灵活性低。
- **犹豫不决** → 用 vLLM 起步；等摸清瓶颈在哪一项，再考虑 SGLang 或 TensorRT-LLM 替换那一段。

**把清单走一遍：一个 7B 通用助手的选型演练。** 假设你要给一个日活 5 万的对话助手做服务，需求是「新模型发布当天就能换、要兼容 OpenAI 接口、要稳定」。对照清单：兼容与适配速度指向 vLLM；省心程度 TGI 也不差，但 vLLM 的社区功能更全。于是首轮选 vLLM。上线三个月后压测发现瓶颈在「复杂工具调用要稳定输出 JSON」，于是把**工具调用这一类请求**单独路由给 SGLang（它靠约束解码能保证 JSON 合法），普通对话仍走 vLLM。这个例子说明：**先按清单定主引擎，再让负载数据告诉你哪里该换**。

这套「先默认、后替换」的节奏，也决定了团队该投入什么：**不要一开始就在四家引擎上各建一套部署，而是先把一条 vLLM 链路跑顺、把监控与压测搭起来**——有了数据，替换才有依据；没有数据，任何「换引擎更优」的说法都是信仰而非工程判断。

**辨析｜易错点：**

- **误区一：拿「星星数」当实力。** 星星多说明社区大、迭代快，不等于你的负载上更快。同一批 GPU、同一批 prompt，四家引擎的相对差距可能高达 2–3 倍，且随 batch 大小翻转。
- **误区二：以为「引擎之间只能二选一」。** 生产里常见多引擎并存：SGLang 服务复杂的 Agent 场景，vLLM 服务普通对话，前端统一走 OpenAI 兼容协议（第九篇）。
- **误区三：把「In-flight Batching」和「Continuous Batching」当两种技术。** 它们本质是同一个思想——请求做完就立刻腾出批位、新请求立刻补进来——只是命名流派不同。TensorRT-LLM 叫 In-flight，vLLM/SGLang/TGI 叫 Continuous。

## 6 小结

- **四张名片**：vLLM（社区最大、页式 KV）、SGLang（约束解码 + 前缀树）、TensorRT-LLM（编译期优化 + 硬件深度定制）、TGI（HF 生态、省心）。
- **五类问题坐标系**：正确性、性能、内存、调度、服务化——每家的取舍都落在某一两项上。
- **三条分水岭**：内存管理选页还是选树、内核是插拔还是编译、调度是业务逻辑还是硬件配套。
- **并发上界公式**：$N_{\max} = (M_{\text{avail}} - M_{\text{weights}} - M_{\text{act}})/\bar{K}_{\text{seq}}$，页式管理把浪费系数压到一页以内，并发上界放大约四倍。
- **选型靠负载不靠口碑**：先猜自己是哪一档用户，再上真实压测确认。
- **多引擎是常态**：生产系统常按负载类型分流（对话走 vLLM、工具调用走 SGLang），前端统一 OpenAI 兼容协议。
- **许可证与生态**：商用前确认许可与硬件绑定，避免被单一家供应商锁死。
- **选引擎 = 选生态**：量化工具、Agent 方向、HF 全家桶、Triton 服务器——生态决定长期可维护性。
- **记住「默认 + 替换」框架**：先用最均衡的 vLLM 起步，摸清瓶颈后再用极致选手替换对应环节。

在下一节，我们把「训练框架为什么不能直接拿来推理」这层窗户纸彻底捅破——**推理框架与训练框架的本质区别**，是理解引擎一切设计动机的总钥匙。
