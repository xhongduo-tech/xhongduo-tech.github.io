## 为什么「全量卸载」是最自然的失败尝试

上一节算清了挑战：671B 权重放不进 24GB 显存。那么最直觉的解法是什么？**把全部权重放进 CPU 内存（甚至磁盘），推理时按需读取**——这就是**全量卸载（full offload）**。llama.cpp 是这条路的代表，DeepSpeed Inference 的 CPU offload 也是。它们都能「跑起来」——但都跑不快。这一篇要做的，是把「为什么不快」拆到每一个字节的账面上。<span class="marginnote">ktransformers 论文在动机部分把全量卸载当成<strong>「上一代方案」</strong>来解剖：它不是错的，而是「均匀地低效」——对所有权重一视同仁，忽略了 MoE 的稀疏结构。理解它的瓶颈，才能理解 ktransformers 究竟改了什么。</span>

「自然的失败尝试」这个说法值得先立住：全量卸载在逻辑上完全自洽——权重放不下就放内存，放内存就配大内存，推理时读到哪算哪。它的失败不是「跑不起来」，而是「跑不快、还越跑越慢」。**一个方案的价值不只看「能不能」，更看「在它的场景里能到什么程度」**——全量卸载在「小模型 + 大显存」场景完全够用，只是它在「671B + 24GB」这个极限场景里露出了数学上的天花板。

## 1 卸载路线图：llama.cpp 与 DeepSpeed 分别怎么干

两条主流路线，卸载策略略有不同：

**llama.cpp（CPU 优先路线）**：把权重以 GGUF 量化格式常驻 CPU 内存，GPU 只负责「能放下的层」（如 Attention 的一部分）。推理时，GPU 每算一层都要从 CPU 内存取权重——**经 PCIe 或经 CPU 侧内存带宽**。它在纯 CPU 模式（不接 GPU）也能跑，只是更慢。

**DeepSpeed Inference（张量并行 + CPU offload）**：把权重在 CPU 与多张 GPU 之间切分；放不下的部分留在 CPU，推理时经 PCIe 搬入 GPU 临时计算。它的思路更接近「动态换入换出」——像一个「权重版的分页系统」。

两条路线的共同点：**每次前向，都需要把「这一层要用的权重」从慢速存储搬到计算设备**。这个「搬」字，就是全部瓶颈的来源。<span class="marginnote">把「搬」字划重点：llama.cpp 是「权重在 CPU、GPU 来取」，DeepSpeed 是「权重在 CPU、搬进 GPU 再算」——无论哪种，<strong>权重的每一次使用都伴随一次跨设备/跨带宽的移动</strong>。而移动，正是最贵的操作。</span>

还有一个共同点值得点出：**两条路线都「按层串行搬移」**——GPU 算完第 $l$ 层，才去取第 $l+1$ 层的权重。搬移与计算没有重叠，「算的时候在等搬、搬的时候算不了」。这比「带宽不够」更糟——它连「把搬移藏进计算」的余地都没留。全量卸载的「均匀地慢」，有一半来自这个「串行搬移」的实现方式。

## 2 瓶颈一：带宽被「全部激活权重」卡死

全量卸载的致命伤，是它**对权重的读取量与「全量」挂钩**——每生成一个 token，都要读「该 token 激活的所有权重」。

回到数字：DeepSeek-V3 每 token 激活约 37B 参数。INT4 量化后约 18.5GB。若这 18.5GB 全部从 CPU 内存读，decode 速度上界：

$$
\text{tps}_{\max} = \frac{BW}{B_{\text{act}}} = \frac{200\ \text{GB/s}}{18.5\ \text{GB}} \approx 10\ \text{token/s}
$$

而真实系统还达不到这个上界——llama.cpp 跑 671B 的实测通常只有 **3–5 token/s**。差距从哪来？因为上界公式假设「带宽被 100% 用于读激活权重」，而实际还有：权重布局的读取开销、CPU 侧计算的耗时、多线程的缓存缺失——每一项都在「上界」上再打折。

「上界只有 10、实测只有 3–5」这个差距，恰恰说明全量卸载的问题不只是「带宽不够」，更是「**带宽利用不充分**」——它既绕不开「读全部激活权重」的数学天花板，又没把「读回来的数据」高效用起来。**「上限低」与「离上限还差一大截」是两个叠加的问题**——前者是结构性的，后者是工程性的，全量卸载两者都没解决。<span class="marginnote">这也解释了为什么「多线程加速」对全量卸载几乎无效：<strong>瓶颈在内存带宽，不在 CPU 计算</strong>。线程再多，也改变不了「每秒只能从 DRAM 读 200GB」这个物理事实。带宽受限的问题，靠加计算资源是解决不了的。</span>

## 3 瓶颈二：PCIe 是更低的墙

若卸载方案选择「把权重搬到 GPU 再算」（DeepSpeed 路线），还会撞上第二堵墙：**PCIe 带宽**。

PCIe 4.0 ×16 的典型带宽约 32 GB/s——比 DDR5 还低一个数量级。若每层都要把权重从 CPU 内存经 PCIe 搬进 GPU 显存再算：

$$
\text{tps}_{\max} = \frac{32\ \text{GB/s}}{18.5\ \text{GB}} \approx 1.7\ \text{token/s}
$$

这已经不是「慢」，而是「不可用」。即便只搬「该层权重的 INT4 打包块」（比全权重少），层与层之间的搬移动辄几十 GB 累计，PCIe 很快饱和。

更深一层，PCIe 的带宽还是**双向共享**的：GPU 要把 token 输入、中间激活发往 CPU，CPU 要把专家结果发回 GPU——**来回都占同一条 PCIe**。全量卸载只盯着「搬权重」这一方向，忽略了「结果回传」也占带宽，实际可用带宽还要再打折。**PCIe 是「搬家」与「回传」共用的通道，全量卸载把两者都压在上面，通道必然堵死**。<span class="marginnote">把「PCIe 双向共享」记在心里：GPU 侧每多一次「搬权重进来」，就少一分「传结果出去」的带宽。<strong>全量卸载在搬移上的每一分努力，都在挤压它本来就要用的回传带宽</strong>——这是它「越忙越慢」的根源。</span>

「双向共享」还引出一个更深的推论：**跨设备方案的价值上限，取决于「搬运量」而不是「计算量」**。如果一次前向的搬运量（几十 GB）远大于计算量对应的数据量，那么不管 GPU 多快，都被「搬运」钉死。想救回这个方案，唯一的路是「让搬运量降到可忽略」——这恰恰是下一章的异构设计要做的：**尽量不搬**。

再补一个「PCIe 墙」的量化视角：32 GB/s 的 PCIe 即使只在 decode 时搬运「专家结果」（每层几 MB 的小张量），61 层累计也不过几百 MB——**小张量的回传不是问题，问题从来是大权重的前向搬运**。把「搬大权重」与「传小结果」分开看，就能理解为什么 ktransformers 的解法是「大权重就地算、只传小结果」：它把 PCIe 的负担从「GB 级搬运」降成「MB 级回传」——这不是「更省地搬」，而是「根本不搬大的」。

## 4 公式解析：全量卸载的「均匀浪费」

全量卸载的瓶颈可以用一个「权重读取分布」公式看清。设模型权重总集合为 $W$，某 token 激活的权重子集为 $W_{\text{act}} \subseteq W$，则全量卸载每 token 的读取量是 $|W_{\text{act}}|$——**与稀疏度无关，只与「激活量」有关**：

$$
\text{读取量}_{\text{full-offload}} = |W_{\text{act}}|, \qquad \text{与 } |W_{\text{act}}| / |W| \text{ 无关}
$$

逐项拆解：

- **第一步**：$|W_{\text{act}}|$（37B 参数，INT4 约 18.5GB）是每 token 必须读的「激活权重」——MoE 的稀疏性（671B 只激活 37B）在这里毫无帮助，因为**激活的 37B 仍要全部读**。
- **第二步**：全量卸载对这个量「一视同仁」——热专家、冷专家、稠密层，全都从同一个慢速存储读。**它没有任何「减少读取」的手段**，只能被动接受 $|W_{\text{act}}|$ 这个量。
- **第三步**：对比 ktransformers 的差异化读取——把高频、稠密的权重（Attention、共享专家、热专家）放显存（1 TB/s），只有低频的冷专家走 DRAM。读取量从「全部激活」降到「只有冷专家那一小部分」。

**一句话**：全量卸载的瓶颈公式是「每 token 付满 $|W_{\text{act}}|$ 的带宽」，而 ktransformers 的账本是「只付 $|W_{\text{cold}}|$」——**稀疏性给了「可以少读」的自由，全量卸载放弃了它，ktransformers 抓住了它**。<span class="marginnote">这个「$|W_{\text{act}}|$ vs $|W_{\text{cold}}|$」的对比，是理解本专题的钥匙之一：<strong>同样是 671B 模型，全量卸载每 token 读 18.5GB，ktransformers 只读几 GB 的冷专家</strong>——差距就是「稀疏性被用起来」与「没被用起来」的差距。</span>

## 5 瓶颈三：预填充的「一次性全量读」

decode 的瓶颈是「每 token 都读」，prefill 的瓶颈则是「一次性全量读」——但两者方向相反。

prefill 处理整个 prompt，要读的权重仍是「激活的 37B 参数」量级。但 prefill 的 batch 大、可以并行——**如果带宽能喂饱，prefill 本可以快**。问题是全量卸载在 prefill 时同样把权重放在慢速存储，**prefill 的大矩阵乘被「等权重」拖住**，GPU 算力空转、带宽成为铁墙。

于是全量卸载在 prefill 上的表现是「**高计算密度、低实际吞吐**」——它空有能并行算大矩阵的硬件（GPU），却让 GPU 一直在等慢速存储喂数据。**「硬件有能力，但数据到不了」是 prefill 优化的核心矛盾**——这正是下一章「异构推理的机会窗口」要解决的第一件事：让 prefill 的高频权重待在高速存储里，让 GPU 不必等。<span class="marginnote">把「decode 慢在每 token、prefill 慢在等数据」记成一句话：<strong>全量卸载在 decode 是「带宽钉死」，在 prefill 是「算力饿死」</strong>——两段的瓶颈不同，但根子相同：权重放错了层级。</span>

## 6 为什么「加大内存」救不了全量卸载

一个自然的补救想法是：既然带宽不够，那就「让权重别读了」——把权重换成更大的缓存、更快的 SSD、或者干脆加内存让部分权重驻留。这些补救有一个共同点：**都绕不开「每次前向仍要读激活权重」这个根**。

**加内存**：内存容量解决的是「放得下」，不是「读得快」。就算把 1.3TB 权重全塞进超大内存，decode 每 token 仍要读 18.5GB——带宽没有变，10 token/s 的上界纹丝不动。**「加容量」与「提带宽」是两件事，前者解不了后者的题**。

**加快 SSD / 加缓存**：这些确实能改善「首次加载」与「冷权重读取」，但 decode 的核心读取路径仍是「从 DRAM 读激活权重」——SSD 只能当「DRAM 的下级」，帮不上「decode 的主循环」。**缓存分层只对「低频访问」有效，decode 的激活权重是高频访问，缓存救不了高频**。

更深一层：**这些补救都在「全量卸载」的框架内打转**——它们默认「权重必须从慢速存储读」，只是想让慢速存储快一点。而真正的问题在于「**为什么激活的 37B 权重都得从慢速存储读**」——这个前提本身就是可质疑的。如果能把大部分高频权重放到高速存储（显存），让慢速存储只承担低频的冷专家，那么「带宽够不够」就从「结构性难题」降级为「可摊薄的小问题」。<span class="marginnote">这就是「框架内优化」与「框架外重设计」的区别：<strong>加内存、加快 SSD 是在全量卸载的框架里打补丁，而「让高频权重进显存」是跳出框架的重新设计</strong>。后者才是 ktransformers 走的路——下一节「异构推理的机会窗口」将正式展开。</span>

## 6.5 辨析｜易错点：量化 ≠ 解决卸载瓶颈

还有一个高频误区：**「只要把权重量化到 INT4，全量卸载就快了」**。量化确实把每 token 读取量从 37GB（BF16）砍到 18.5GB（INT4）——但这是「同一瓶颈的缩放」，不是「瓶颈的消除」：

**量化只缩小了 $|W_{\text{act}}|$，没改变「每 token 都要读全部激活权重」的结构**。18.5GB 仍然要从慢速存储读，10 token/s 的上界变成约 20 token/s——**快了一倍，但天花板仍在，且仍远低于「能用」**。而且实测还会被「解包、反量化」的计算开销往回拉，实际提升远小于理论。

**辨析｜易错点：** 把「量化省字节」与「异构省读取」混为一谈。量化是「把要读的字节变小」，异构是「让慢速存储少读、高速存储多读」——**两者正交，可以叠加**。ktransformers 正是「量化 + 异构」一起用：量化先省一遍字节，异构再让「省下来的字节」大部分走高速路径。**「省字节」与「选路径」是两个独立的杠杆，别用一个替代另一个**。<span class="marginnote">量化与异构的关系，可以类比「搬更小的箱子」与「走更快的路」：<strong>箱子再小，路还是慢的；路再快，也救不了「必须全搬」的结构</strong>。两件事一起做，才真正改变「每 token 的搬运总成本」。</span>

## 7 小结

把全量卸载的瓶颈收成「两堵墙、一个浪费、一个串行、一次框架内打转、一次误区辨析」：**DDR5 带宽墙**（每 token 读 18.5GB，上限约 10 token/s）、**PCIe 带宽墙**（若搬去 GPU，上限约 1.7 token/s）、**对稀疏性的均匀浪费**（激活的权重全部慢读，热冷不分）、**搬移与计算串行**（搬的时候算不了）、**补救无效**（加内存/加快 SSD 都解不了「读激活权重」的根）、**量化非解药**（省字节 ≠ 换路径）。

- **llama.cpp**：权重常驻 CPU 内存，GPU 取用——被 CPU 内存带宽卡在 3–5 token/s。
- **DeepSpeed**：权重经 PCIe 搬入 GPU——被 PCIe 的 32 GB/s 卡在约 1.7 token/s。
- **根因**：每 token 都付满 $|W_{\text{act}}|$ 的读取量，且无「减少读取」的手段。
- **稀疏性被浪费**：MoE 的「只激活 37B」没被利用，热冷专家同速读取。
- **两段都慢**：decode 每 token 付带宽，prefill 的 GPU 算力空等慢速存储。
- **框架内打转**：加内存解不了带宽、加快 SSD 救不了高频——要跳出「权重全走慢速存储」的框架。

在下一节，我们将走出「均匀地慢」，找到那条真正的机会窗口——**既然激活量远小于总量、且热冷不均，为什么不「热专家留 GPU、冷专家放 CPU」？这就是异构推理的设计目标。**
