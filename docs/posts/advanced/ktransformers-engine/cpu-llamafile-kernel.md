## 为什么 CPU 侧要「借」llamafile 的内核

GPU 侧有 Marlin，CPU 侧凭什么跟得上？答案是 **llamafile**——Mozilla 维护的、把 llama.cpp 装进单文件的推理运行时。ktransformers 的 CPU 专家内核直接借用了 llamafile/llama.cpp 的矩阵乘实现：它是纯 CPU 场景下久经考验、为**量化权重 + 多线程 + 各种 SIMD 指令集**深度优化过的内核。

「久经考验」不是套话：llamafile 内核被数百万次本地推理调用打磨过——从单核小模型到多核大模型，从 AVX2 老机器到 AMX 新平台，各种边角情况都被实际用户踩过、修过。**工程软件的可靠性来自「被使用的广度和时长」**——这是任何测试都替代不了的。ktransformers 选择复用，等于直接继承了这份「被踩过的可靠性」。<span class="marginnote">论文把 CPU 侧执行描述为「基于 llamafile 的 CPU 内核 + 多线程任务调度」。与其从零写 CPU GEMM，不如复用社区打磨多年的成熟内核——这是<strong>系统工程里的务实选择</strong>。</span>这一节拆解 llamafile 内核好在哪、以及 ktransformers 如何让多线程调度把它喂得满满当当。

## 1 llamafile 内核为什么快

llamafile 的量化 GEMM 针对 CPU 做了三层优化：

**SIMD 指令集分派**：现代 x86 CPU 有 SSE、AVX2、AVX-512，较新的服务器 CPU 还有 **AMX**。同一段矩阵乘，llamafile 按 CPU 能力编译/分派到最宽的指令集——一次指令同时算 8、16、32 个数据，吞吐随位宽翻倍。ktransformers 在支持 AMX 的 CPU（如第四代 Xeon）上开启 AMX-BF16 路径，CPU 端 prefill 比 llama.cpp 快约 **28×**。

「复用 llamafile」这个选择还省去了一个巨大的工作量：llamafile/llama.cpp 社区花了数年时间，在几十种 CPU 型号、多种量化格式、各种 batch 形状上打磨这些内核。**站在成熟开源内核的肩膀上**，ktransformers 不用从零踩一遍「哪个指令集在哪块 CPU 上有 bug」这类深坑——这是「工程上借力」的典型示范：核心创新留给「异构调度」，成熟部分直接复用。<span class="marginnote">第 3 篇下一篇《Intel AMX-BF16 与 AVX512-BF16/AVX-VNNI 指令集》会专门展开指令集这一层；这里记住结论：<strong>llamafile 内核是按 CPU 能力「选最宽 SIMD 通道」执行</strong>的。</span>

**量化权重友好**：与 Marlin 类似，llamafile 的 INT4/INT8 内核同样用「整数点积 + 末尾缩放」的线性技巧，主循环是高效的整数乘加，反量化推迟到累加后。

**cache 分块（tiling）**：矩阵乘按适合 L1/L2 缓存尺寸的分块进行，让数据尽可能在缓存里被反复使用，减少 DRAM 访存。这一点对「权重 377GB 在 DRAM、带宽有限」的场景尤其重要——**能命中缓存一次，就少一次 DRAM 慢速读取**。

cache tiling 与 GPU 侧的 tile 化布局是同一思想的两个实现：**把大矩阵切成「能装进缓存的小块」，让块内数据被反复使用**。区别在于：GPU 的「缓存」是共享内存 + L2，CPU 的「缓存」是 L1/L2——但「以块为单位组织计算」的逻辑完全一致。读到这里，你应该已经能总结出**贯穿全专题的主线之一：「块」**——权重打包成块、GEMM 切成块、专家按块放置——一切性能优化的尺度，都在「块」上。

## 2 多线程任务调度：让每颗核都别闲着

内核快，还得被喂饱。ktransformers 的 CPU 侧是一个**多线程任务调度器**：

**任务粒度**：每个被路由命中的冷专家 GEMM 是一个任务。一个 token 在某层命中 1 个冷专家，就是一个矩阵乘任务；多个 token × 多个专家 = 一大批独立任务。
**线程池**：预创建的线程池（默认可用核数），任务按依赖与 NUMA 亲和性派发。
- **并行策略**：专家 GEMM 本身再按行分块，多个线程并行算同一矩阵乘的不同行块；不同专家之间天然独立，可跨任务并行。

线程池的「预创建」很关键：它避免了「每次任务都现开线程」的巨大开销（线程创建是重量级操作）。池中的线程常驻、循环取任务，把「线程管理」的固定成本摊到了整个生命周期。**「池化」是高频异步场景的标准解法**——从线程池、连接池到内存池，都是「预分配资源、循环复用」的思路，目的都是避开「用一次建一次」的昂贵开销。

效果：CPU 上的所有核同时在算不同的专家分块，吞吐随核数近似线性扩展。

多线程调度的「任务粒度」选择是一个微妙权衡：任务切得太细（比如一个专家按行切成几十个小任务），调度开销占比上升、cache 局部性变差；切得太粗（一个专家就是一个任务），并行度不足、核数多时负载不均衡。**「粒度」是并行编程里最经典的调优旋钮**——理想粒度让「每个核都忙、且忙在足够长的任务上」。ktransformers 按「专家 GEMM 本身分块 + 多专家并行」的双层粒度组织，是经验上的好平衡。<span class="marginnote">关键点：<strong>任务的独立性</strong>是并行度之源——MoE 的「每个 token 走不同专家」恰好制造了大批互不依赖的 GEMM。对比稠密模型，它的 FFN 只有一个、无法拆成跨任务并行，CPU 侧并行度天然受限。</span>

## 3 异步协作：CPU 内核与 GPU 流水线的接口

CPU 内核不是在真空中跑——它要与 GPU 的 CUDA Graph 流水线咬合（第 2 篇《异步调度》）。接口约定：

- CPU 线程池**产出**：把算好的专家输出写入**预先分配的 pinned 缓冲**（第 2 篇《NUMA 与 Pinned Memory》），位置固定。
- GPU 侧**消费**：CUDA Graph 里的「等待专家结果」节点，从该固定地址经 DMA 取数——图结构因此稳定，无需重建。
- **同步粒度**：GPU 只在「需要专家输出做下一层 Attention」时才等；等待时 GPU 早已推进若干层稠密计算。

「等待时 GPU 早已推进若干层」正是第 2 篇异步流水线的体现——CPU 内核在这里扮演「异步生产者」：它不知道 GPU 何时会来取，只负责「尽快把结果写进缓冲」。**生产者只需「快」与「准时」，不需要「与消费者同步」**——这种「松耦合」让 CPU 侧可以专注于「算得快」，而不必操心「GPU 在干嘛」。把「生产者」与「消费者」的职责彻底分开，是异步设计里最干净的结构。

CPU 侧这一篇与 GPU 侧的 Marlin 篇构成一对完整的镜像：**GPU 用 Marlin 把「热路径」磨快，CPU 用 llamafile 把「稀疏路径」磨快**——两侧各有一套为「自己的负载画像」定制的高性能内核。异构系统的美，正在于「每台设备都有自己的看家内核」。

这一接口设计的精妙处：**CPU 侧不知道 CUDA Graph 的存在，GPU 侧也不知道 CPU 线程池的存在**——两边只通过「固定地址的 pinned 缓冲」耦合。解耦让两侧各自演进、互不阻塞。

「通过共享缓冲解耦」是系统设计里最古老的异步模式之一：生产者往缓冲写、消费者从缓冲读，双方只需约定「缓冲在哪、格式如何」，不必知道对方内部实现。**这个模式的可贵之处在于「接口极简、自由度极大」**——CPU 侧想换调度算法、GPU 侧想换内核，只要守住「缓冲地址 + 数据格式」的约定，就互不影响。ktransformers 的 CPU-GPU 协作，本质就是一条「用共享缓冲实现的异步管道」。

## 4 公式解析：CPU 侧吞吐的 Amdahl 式分解

CPU 侧专家计算的吞吐，可以拆成「算力 × 利用率」。设核数为 $C$，每核 BF16 峰值算力 $P_c$，则理想吞吐：

$$
T_{\text{cpu}} = C \times P_c \times \underbrace{\eta_{\text{sched}} \times \eta_{\text{simd}}}_{\text{利用率}}
$$

逐项拆解：

- **第一步**：$C \times P_c$ 是理论峰值——16 核 × 每核 64 GFLOPs/s ≈ 1 TFLOPS。
- **第二步**：$\eta_{\text{sched}}$ 是调度效率——线程池喂得饱、无负载失衡、无 NUMA 错位时的利用率（接近 1）。
