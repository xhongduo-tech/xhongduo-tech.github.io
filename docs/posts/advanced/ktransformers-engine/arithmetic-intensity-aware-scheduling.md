## 为什么放置要「感知算术强度」

「GPU 算稠密、CPU 算稀疏」是宏观分工，但到了**每个算子**的粒度，凭什么说这个 Linear 该在 GPU、那个专家 FFN 该在 CPU？光凭「稠密/稀疏」标签不够——还需要一把可计算的标尺。

「稠密/稀疏」是**定性**标签，只能区分「Attention 类」与「专家类」这样的大类；而「算术强度」是**定量**标尺，能区分「同一类里谁更适合 GPU」。比如同样是专家 FFN，prefill 的大 batch 版本算术强度高、decode 的单 token 版本算术强度低——定性标签看不出这种差异，定量标尺一眼分明。**从定性走向定量，是工程决策从「凭感觉」走向「可复现」的分水岭**。上一节我们建立了 Roofline，这一节把它变成**算子放置的决策规则**，并讲清楚 ktransformers 如何把这些规则编译成一次可执行的**推理内核调度**。<span class="marginnote">论文把这种决策称为 <strong>arithmetic-intensity-aware operator placement</strong>：先算每个算子的算术强度，再对照设备的 Roofline 转折点，决定它的归属。它是连接「理论」与「工程」的那层胶水。</span>

## 1 放置规则：三问定乾坤

ktransformers 对每个算子问三个问题，答案共同决定其设备归属：

**一问：算术强度 $I$ 有多高？** 用 Roofline 转折点 $I_0$ 作阈值。$I > I_0^{(gpu)}$ 的算子——例如大 batch 的稠密 GEMM——放 GPU，让算力吃满；$I$ 中等、靠近 CPU 转折点的算子——例如单 token 的专家 FFN——放 CPU，让带宽够用。

三个问题的顺序有讲究：**先问算术强度（理论约束），再问访问频率（实际收益），最后问存储体量（物理可行性）**。前两问决定「理想放哪」，第三问决定「现实放不放得下」——当显存不够时，物理约束优先于理论最优。这也是为什么实际部署里「GPU 专家数」往往由显存预算反推，而不是由算术强度正推：**理论选目标，物理设上限**。<span class="marginnote">注意<strong>同一个算子在不同运行条件下算术强度会变</strong>：batch 越大，GEMM 的 $I$ 越高。ktransformers 的放置是「运行感知」的——同样的专家 FFN，prefill 大 batch 时更倾向 GPU，decode 小 batch 时更倾向 CPU。这种动态性在第 2 篇的调度器里体现。</span>

**二问：访问频率高吗？** 高频率算子（Attention、共享专家、热专家）必须靠近高带宽存储，即使算术强度中等——因为「慢」会在每次调用时反复惩罚。

**三问：占多少存储？** 冷专家权重占几百 GB，必须留在 DRAM；KV Cache 与热专家权重小而高频，留在显存。

把三问合成一张决策表：

| 算子 | 算术强度 | 访问频率 | 存储体量 | 放置 |
| --- | --- | --- | --- | --- |
| MLA Attention | 中（decode）/ 高（prefill） | 每 token 必算 | 中 | GPU |
| 共享专家 | 中高 | 每 token 必算 | 小 | GPU |
| 热专家 | 中 | 高 | 小（精选 top-k） | GPU |
| 冷专家 | 中低 | 低 | 巨大 | CPU（DRAM） |

## 2 从放置到调度：推理内核的编排

有了「每个算子放哪」的静态决定，运行时还需要一套**调度**把这些算子串成一次前向传播。ktransformers 的推理内核调度承担四件事：

**路由驱动的专家激活**：每层先算路由，得到被选专家集合 $E_t$；对照放置表，热专家走 GPU 内核、冷专家提交给 CPU 任务队列。

把这四件事再压缩成一句：**调度 = 把「路由输出」翻译成「设备动作」**。路由每 token 给出一组专家 ID，调度器负责为每个 ID 回答「它现在归谁算、怎么算、结果送哪」——翻译得足够快，才不会成为前向的瓶颈。<span class="marginnote">调度器的输入是「路由结果 + 放置表」，输出是「每个被激活专家去哪个设备的哪条队列」。这是整个系统里唯一每 token 都在变的部分——因为路由结果每 token 不同。</span>

**GPU 内核序列化**：把 GPU 侧的 Attention、共享专家、热专家、投影等固定算子序列，用 **CUDA Graph** 一次性捕获、重复执行，把每层几百次的 launch 开销压成一次。

**CPU 任务队列**：被命中的冷专家作为任务投递到 CPU 线程池，按依赖关系并发执行；结果异步回传 GPU。

**跨设备同步**：GPU 与 CPU 之间只需在**层边界**同步一次（等冷专家结果就位），层内各自并行。

这四件事构成一次「前向的调度流水」：路由决定专家 → 对照放置表分流 → GPU 侧 Graph 固化 → CPU 侧队列执行。其中「路由决定专家」是唯一的动态输入，其余三件事都是「把动态输入喂进预置的执行框架」。**调度器的复杂度集中在「动态的分流」上，静态的部分全部被提前固化**——这又是「重决策、轻执行」在运行时的延续。

## 3 公式解析：放置判据的形式化

把「放哪」写成一个可计算的判据。对算子 $o$，设其算术强度 $I_o$、每 token 访问频次 $f_o$、占用存储 $s_o$。GPU 显存容量 $V$，放置策略是选一个「设备标签」$d(o) \in \{\text{GPU}, \text{CPU}\}$ 使：

$$
d(o) = \text{GPU} \iff I_o \ge I_{\text{thr}} \;\wedge\; f_o \ge f_{\text{thr}} \;\wedge\; s_o \le V_{\text{left}}
$$

逐项拆解：

- **第一步，算术强度门槛 $I_{\text{thr}}$**：取 GPU 转折点附近——低于它，GPU 算力吃不满，放 GPU 是浪费。
- **第二步，频率门槛 $f_{\text{thr}}$**：确保「放 GPU 的好处」被反复兑现；低频算子放 GPU 性价比低。
- **第三步，容量约束 $V_{\text{left}}$**：显存剩余空间——热专家放不下的部分只能去 CPU。**容量是硬约束**，最终决定「多少专家上 GPU」。

三个门槛里，前两个是「软」的（可以凭经验设阈值），第三个是「硬」的（物理上装不下就是装不下）。工程上常见的做法是**先算容量、再反推频率门槛**：设 $V_{\text{left}}$ 能装 $M$ 个专家，就让「激活频率排名前 $M$」的专家进 GPU——容量直接决定 $M$，频率只负责「选哪 $M$ 个」。这套「容量定名额、频率定人选」的流程，正是 `num_gpu_experts` 与 `placement-strategy` 两个参数各自扮演的角色。

**这正是论文与官方文档的映射**：`--kt-num-gpu-experts` / `--kt-gpu-experts-ratio` 就是给这个判据的「$V_{\text{left}}$ 预算」——你告诉系统「显存里最多塞多少专家」，调度器据此挑最热的那批。<span class="marginnote">官方 `--kt-expert-placement-strategy` 提供了四种挑法：`uniform`（每层均分）、`frequency`（按激活统计挑最热）、`front-loading`（从首层开始填）、`random`（固定随机种子做基线）。其中 `frequency` 正是「让 $f_{\text{thr}}$ 以上的进 GPU」的落地实现。</span>

注意判据里三个条件的「与」逻辑：**只要有一个不满足，就放 CPU**。算术强度再高，若频率极低，放 GPU 也是浪费；频率再高，若显存装不下，也只能放 CPU。这三个条件的「与」决定了放置是一个「筛选」而非「打分」——通过全部条件才上 GPU，任一不满足就留 CPU。理解这层「与」关系，就能解释「为什么这个算子明明很重却放 CPU」的疑惑：多半是显存装不下了。

## 4 辨析｜易错点：放置是静态配置，不是运行时魔法

**辨析｜易错点：** 初学者以为 ktransformers「运行时实时分析每个算子该放哪」——不是。放置是**启动时一次性的配置决策**（读 YAML 注入规则 + 放置策略 + 显存预算），运行时的调度只负责「按已定放置表把任务派到对应队列」。

把「启动时一次性的」再强调一次，因为它牵连出一个工程推论：**放置决策的代价是「一次性的」，所以可以做得「重」**——比如跑一遍统计、读一遍 YAML、做一次最优子集选择，都不心疼。而调度的代价是「每 token 的」，必须做得「轻」——查掩码、入队、派发，都是 O(1) 级别的操作。**「重决策，轻执行」是这套设计的效率密码**：把贵重的计算放在低频路径上，把高频路径保持极简。<span class="marginnote">把「放置（placement）」与「调度（scheduling）」分开理解：<strong>放置是计划，调度是执行</strong>。计划每层只做一次，执行每 token 都做。混为一谈是读论文时最常见的困惑来源。</span>

另一个易错点：把「算术强度」当作算子的固有属性。同一算子随 batch、随量化位宽而变——算术强度是**运行上下文相关的量**，这也是为什么 ktransformers 对 prefill 与 decode 采用不同偏好的原因。

「算术强度随上下文而变」还有一个反直觉的推论：**同一个算子，在 prefill 与 decode 里可能该放不同设备**。prefill 的专家 FFN 是「大 batch 的宽矩阵乘」，算术强度高，放 GPU 更优；decode 的专家 FFN 是「单 token 的瘦矩阵乘」，算术强度低，放 CPU 更划算。若用一套静态放置通吃两段，必然有一段落入次优。ktransformers 的解法是「**同一权重、两套执行路径**」——权重只有一份，但 prefill 与 decode 各走各的内核与调度偏好。这是「算术强度感知」落实到运行时的最精细形态。

## 5 放置 vs 调度：一张表分清

「放置」与「调度」这两个词在本篇反复出现，极易混淆，用一张表彻底钉死它们的区别：

| 维度 | 放置（Placement） | 调度（Scheduling） |
| --- | --- | --- |
| 回答的问题 | 每个算子放哪台设备 | 运行时每个任务去哪条队列 |
| 执行时机 | 启动时一次性（配置决定） | 每次前向/每 token（路由驱动） |
| 输入 | 注入 YAML、显存预算、放置策略 | 路由结果、放置表、任务队列状态 |
| 产物 | 静态的「设备归属表」 | 动态的「任务派发序列」 |
| 变化频率 | 几乎不变（除非动态更新） | 每 token 都变 |
| 类比 | 城市的区域规划 | 红绿灯与车流调度 |

两者是「计划」与「执行」的关系：**放置定下「谁该在哪」，调度负责「让谁按什么顺序在哪干活」**。没有放置，调度无从谈起；没有调度，放置只是一纸空文。ktransformers 的高明之处，是把「静态计划」与「动态执行」分离，让每一层都能独立演进——这也是分层架构（第 2 篇）带来的又一红利。

「计划与执行分离」还是软件工程里一个普适原则：编译器的「静态编译 + 动态执行」、数据库的「查询计划 + 执行器」、操作系统的「进程调度 + 资源管理」——都是同一模式。**ktransformers 的放置/调度分层，只是这个宏大模式在推理引擎里的一次具体演绎**。带着这个视角去读任何「计划 + 执行」架构，你都会发现似曾相识的骨架。

## 6 小结

把本篇的「三问 + 一判据」记成一句话：**算力问算术强度、收益问访问频率、可行性问显存容量，三者取「与」决定归属**。

再补一句「反着读」的提醒：判据的「与」逻辑意味着**任何一个条件不满足就放 CPU**——所以「为什么放 CPU」可以有三种不同理由（强度不够 / 频率太低 / 装不下）。遇到部署问题先分辨「是哪种理由」，比笼统地说「它太慢」更有诊断价值。

- 放置决策 = **三问**：算术强度、访问频率、存储体量，对照 Roofline 转折点与显存预算。
- 调度器四件事：**路由驱动专家激活、GPU 内核 CUDA Graph 化、CPU 任务队列、层边界同步**。
- 放置判据：$I_o \ge I_{\text{thr}} \wedge f_o \ge f_{\text{thr}} \wedge s_o \le V_{\text{left}}$
