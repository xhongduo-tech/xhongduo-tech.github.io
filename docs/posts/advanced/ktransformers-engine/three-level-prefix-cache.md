## 为什么 KV Cache 值得三层缓存

前 18 篇都在讲「权重怎么放」。但推理的另一个大户是 **KV Cache**——Attention 要存的键值缓存，随上下文线性增长，几十万 token 的对话要吃掉几十 GB。ktransformers 对 KV Cache 的管理沿用了与权重相同的哲学：**按访问频率分层放置**，于是有了 **GPU → CPU → Disk 三层前缀缓存**。<span class="marginnote">「前缀缓存（prefix cache）」的核心洞察：多轮对话、多请求常常共享同一段前缀（系统提示、历史对话）。与其每次重算，不如缓存起来复用。ktransformers 把这一思想扩展到<strong>跨 GPU/内存/磁盘三级存储</strong>——这在本专题里与「权重分层」遥相呼应。</span>

## 1 KV Cache 为什么是「重资产」

先算一笔账。设上下文长度 $L$、层数 $L_h$、每层 KV 维度 $d_{kv}$、每个 KV 元素 2 字节（BF16），则总 KV Cache 体积：

$$
\text{KV size} \approx 2 \times L_{\text{seq}} \times L_{\text{layers}} \times d_{kv} \times 2 \text{ B}
$$

对 DeepSeek-V3（61 层，MLA 显著压缩了 KV 维度），逐项看：

- **MLA 的贡献**：Multi-head Latent Attention 把每层的 KV 投影到低维潜空间（约 512 维量级），KV Cache 比传统 MHA 小一个数量级以上——**这是 139K 上下文能装进 24GB 显存的前提**。
- **长上下文的代价**：即便如此，139K token 的 KV Cache 仍达数十 GB，远超显存。

KV Cache 有两个「坏脾气」：**随序列线性增长**、**被 GPU 高频读取**。前者要求「能分层放」，后者要求「热的部分尽量在显存」。

这两个「坏脾气」也解释了为什么 KV Cache 的优化路径与权重不同：权重是「静态大文件」，优化靠「一次性量化 + 分层放置」；KV Cache 是「动态增长流」，优化靠「实时分层 + 淘汰管理」。**「静态资源」与「动态资源」的管理策略天然不同**——前者重「摆放」，后者重「调度」。ktransformers 对权重与 KV Cache 采用两套机制，正是「因材施教」：每种资源的性质，决定了优化它的手段。

## 2 三级缓存：速度、容量与成本的阶梯

ktransformers 把前缀 KV Cache 分成三层，构成完整的存储阶梯：

| 层级 | 速度 | 容量 | 命中成本 | 职责 |
| --- | --- | --- | --- | --- |
| **GPU 显存** | 最快 | 小（GB 级） | 零（就地） | 当前活跃对话的 KV，被 Attention 直接读 |
| **CPU 内存** | 中 | 大（几十–上百 GB） | 中（跨 PCIe） | 不活跃但仍可能复用的前缀 KV |
| **磁盘** | 慢 | 巨大（几百 GB–TB） | 高（文件 IO） | 冷门前缀、历史会话的 KV 落盘 |

**访问策略**：最新的、即将被 Attention 读取的 KV 放 GPU；被「挤出」的较旧前缀降级到 CPU 内存；更冷、且可能很久不用的落盘。

「被挤出」三个字揭示了缓存管理的内在机制——**淘汰（eviction）**。GPU 显存容量有限，新 KV 不断写入，旧 KV 必须被逐出；逐出到哪一层，取决于「它是否还有用」。ktransformers 用「时间局部性」做淘汰判据：最近被读过的 KV 更可能再被读（LRU 式）；很久没被碰的，降级到更慢层甚至落盘。**缓存的本质是「在有限容量下，决定谁留下、谁离开」**——留下的给快层，离开的去慢层，而不是删除。这个「逐层降级」而非「直接删除」的设计，正是「三层」而非「一层」的意义：宁可慢，不可丢。<span class="marginnote">这与操作系统的页面换入换出（paging）逻辑同构：<strong>热数据进高速层，冷数据被逐出到慢速层</strong>。ktransformers 把存储层次思想搬进了 KV Cache 管理。</span>

## 3 前缀复用：命中一次，省一次 prefill

**前缀缓存（prefix cache）**的价值建立在「前缀复用」上：多轮对话的每一轮，都要处理「系统提示 + 全部历史」——这部分前缀的 KV 是**逐轮重复计算**的。缓存命中后，新请求只需计算「新增长度」的 prefill，而非从头开始。

「前缀」这个词强调了复用的**结构前提**：只有「前缀相同」才能复用——若两个请求的公共部分不是前缀（比如中间某段相同、前后不同），就无法用「前缀缓存」复用。这是前缀缓存与「任意子串缓存」的区别，也是它的**适用边界**。多轮对话天然满足「前缀相同」（历史 + 新问题），所以前缀缓存在对话场景收益最大；而「改中间某段」的场景（如改 prompt 中间的一个示例）则无法命中。**理解「缓存能复用什么」，比理解「缓存怎么存」更根本**——它决定了缓存的上限收益。

设总前缀长 $L_{\text{prefix}}$、新增长 $L_{\text{new}}$，则：

$$
\text{prefill 计算量：无缓存 } \propto L_{\text{prefix}} + L_{\text{new}}, \qquad \text{有缓存 } \propto L_{\text{new}}
$$

对话轮次越多、前缀越长，缓存收益越大。

把「收益随轮次累积」再算一笔直觉账：第 1 轮没有可复用的前缀（缓存为空）；第 2 轮可复用第 1 轮的 KV；第 $n$ 轮可复用前 $n-1$ 轮的 KV——**轮次越靠后，命中率越高，单轮 prefill 越轻**。这解释了为什么「长对话的后半段」通常比前半段响应更快（prefill 更少）。但要注意：缓存收益的上限受「可复用的前缀占比」约束——若每轮新内容占比很高（比如每轮都换主题），命中率上不去，缓存价值就打折。**「缓存值不值」取决于你的「请求结构」**：多轮渐进式对话最值，独立短请求最不值。<span class="marginnote">实际中「系统提示 + few-shot 示例」常占单次请求的 90%+ token。缓存命中时，这 90% 的 prefill 直接省掉——TTFT 大幅下降。这解释了为什么「长上下文 + 多轮」场景下前缀缓存收益最大。</span>

## 4 公式解析：命中率与平均访问成本

三层缓存的整体性能由命中率加权。设 GPU/CPU/Disk 三层的命中率分别为 $h_g, h_c, h_d$（$h_g + h_c + h_d = 1$），各层访问成本 $c_g \ll c_c \ll c_d$，则平均每字节 KV 访问成本：

$$
\bar{c} = h_g c_g + h_c c_c + h_d c_d
$$

逐项拆解：

- **第一步**：$h_g$ 越高，$\bar{c}$ 越接近 $c_g$——**把最近命中的 KV 留在显存是关键**。
- **第二步**：当显存满，新 KV 把旧 KV 逐出到内存——$h_c$ 上升，$\bar{c}$ 略增。
- **第三步**：只有真正冷的前缀才落盘（$h_d$ 小），避免 $c_d$ 的高成本被高频触发。

**一句话**：三级缓存的目标是让**命中率分布向快速层倾斜**——$h_g$ 最大化、$h_d$ 最小化。这靠「时间局部性」实现：最近用的前缀最可能再用，LRU 式管理天然匹配。

从「平均成本」公式还能读出一个管理结论：**每一层的价值，由「它承接的命中率」与「它省下的成本」共同决定**。GPU 层虽然每字节最贵（高成本），但它省下了「去 CPU/磁盘取」的巨大代价，只要命中率足够高就值得；磁盘层每字节最便宜，但它承接的命中率极低、且命中时省得也不多，所以是「保底」而非「主力」。**缓存分层的经济学，是「命中率 × 节省量」的乘积**——不是「贵的层就一定值」，而是「贵的层要有高命中率才值」。<span class="marginnote">注意与权重的区别：权重分层靠「幂律频次」（第 1 篇），KV 分层靠「时间局部性」（最近使用的再使用概率高）。两类数据、两套局部性，但共享同一套「热进快层、冷出慢层」的存储哲学。</span>

## 5 辨析｜易错点：前缀缓存 ≠ KV Cache 全量入显存

**辨析｜易错点：** 有人以为「三层缓存 = 让 KV Cache 尽量装满显存」。恰恰相反，**显存永远优先放「最可能立刻被读」的活跃 KV**，而不是「塞满为止」——塞满会导致预留给热专家/Attention 的空间被挤占，引发抖动。三级缓存的意义是「该在哪层就在哪层」：GPU 装活跃、内存装温、磁盘装冷。<span class="marginnote">工程上「显存 KV 预留」与「GPU 专家数」是同一块预算的两面——第 2 篇《num_gpu_experts》里的拉锯战，在 KV Cache 篇再次上演：<strong>KV Cache 多留一点，专家就少放几个；反之亦然</strong>。`--max-total-tokens` 就是显存 KV 上限的旋钮。</span>

另一个易错点：把「磁盘 KV Cache」误解为「每次推理都读盘」。磁盘层只承载**冷门前缀**（跨会话复用场景），且命中率很低——它的存在是为了「不至于因显存/内存满而丢弃可复用前缀」，而非常态路径。

「磁盘层命中率很低」不是缺陷，而是设计使然：**磁盘层是「最后一层保险」，不是「常用路径」**。它的职责是「在极端情况下不至于彻底丢失可复用前缀」，而不是「提供常用加速」——常用加速由 GPU/内存层承担。理解这一点，就不会因为「磁盘层很少命中」而误判它「没用」：保险的价值，恰恰在于它「平时用不上，关键时刻兜底」。这与数据库的归档层、操作系统的 swap 是同一个定位逻辑。

## 6 缓存层级 vs 权重层级：两张「分层」的对照

本专题出现了两套「分层」：权重的 GPU/CPU 分层与 KV Cache 的 GPU/CPU/Disk 三层。对照着看，它们的异同格外有启发：

| 维度 | 权重分层 | KV Cache 分层 |
| --- | --- | --- |
| 分层依据 | 访问频率（幂律） | 时间局部性（最近性） |
| 设备 | GPU 显存 / CPU DRAM | GPU 显存 / CPU DRAM / Disk |
| 可否落盘 | 否（权重必须常驻 DRAM） | 是（冷前缀可落盘） |
| 更新频率 | 低（除非动态更新） | 高（每个请求都在写） |
| 一致性要求 | 权重只读、无一致性问题 | 需保证「复用的 KV 与重算一致」 |

**最大的不同是「可落盘性」**：权重是「必须随时可算」的静态数据，放磁盘会带来不可接受的加载延迟；KV Cache 的冷前缀是「可能再也不用的历史」，落盘的风险极低。**「什么能进更慢的层级」取决于「再访问的概率 × 再访问的代价」**——权重再访问概率高，代价高，不能落盘；冷前缀再访问概率低，可以落盘。这个判据，可以推广到任何存储分层设计。

这套「概率 × 代价」判据，其实是计算机存储体系里「置换策略」的通用语言：操作系统的页面置换、数据库的缓存淘汰、CPU 的 cache 替换——都在回答同一个问题「这个数据该留在快层还是逐出到慢层」。**ktransformers 的 KV 三层缓存，只是这套通用语言在「长上下文推理」场景的一次实例化**。掌握了语言本身，你就能设计自己的分层缓存。

## 7 小结

把三层缓存浓缩成「两个局部性」：**权重用「频率局部性」（幂律），KV 用「时间局部性」（最近性）**——两类数据、两套局部性，共享同一条「热进快层、冷出慢层」的存储语法。

- KV Cache 是随上下文线性增长的「重资产」，MLA 压缩是长上下文的前提。
- 三层阶梯：**GPU（活跃）→ CPU 内存（温）→ Disk（冷）**，按时间局部性管理。
- 前缀复用把 prefill 计算量从「全量」降到「新增量」——**多轮对话收益最大**。
- 平均成本 $\bar{c} = h_g c_g + h_c c_c + h_d c_d$——目标让命中率向快速层倾斜（$h_g$ 最大化、$h_d$ 最小化）。
- 三层缓存的价值 = 命中率 × 节省量：贵的 GPU 层要有高命中率才值，磁盘层是「保底」而非「主力」。
- 与权重分层的对照：权重靠「频率局部性」（幂律）、KV 靠「时间局部性」（最近性）——两类数据、两套局部性。

再补一句「从缓存到存储哲学」的收尾：三层前缀缓存是「存储层次」思想在 KV 上的又一次应用——**热进快层、冷出慢层、逐层降级而非删除**。这套语法你已经在「权重分层」（第 1 篇）、「存储层次」里见过多次，现在它在 KV Cache 上第三次现身。**「一种语法、多处应用」正是本专题最重要的学习收获**——当你在一套系统里反复看到同一个模式，就该意识到：这不是巧合，而是「解决同一类问题的通用方案」。带着「存储层次语法」这个认知工具，你能读懂任何缓存系统。
