## 为什么这个案例是「终点验收」

前 24 篇的所有理论——稀疏专家、幂律、Roofline、异构调度、Marlin、AMX、三层缓存、注入——最终都汇入这一个场景：**在 24GB 显存 + 大内存的消费级机器上，跑起满血 DeepSeek-V3/R1 671B**。这是 ktransformers 的招牌用例，也是「算力普惠」的直观证明。<span class="marginnote">官方 DeepSeek 教程给出的流程：下载权重 → 转换格式 → 写注入配置 → 启动推理。<strong>本节以「跑通」为目标</strong>，把每一步的要害讲清；数字以官方教程为据。</span>

## 1 权重准备：671B 的「进货」

DeepSeek-V3/R1 的官方权重是 BF16 的——约 1.3TB，消费级机器吃不消。所以第一步是**下载量化版权重**（社区发布的 GGUF/量化格式，或官方工具的 INT4 转换结果）：

**体积**：4.5-bit 混合量化约 **377GB**——这是 DDR5 要装下的主体。
**来源**：HuggingFace 上的量化仓库，或 ktransformers 教程链接的社区转换权重。
- **格式**：GGUF 或 ktransformers 原生格式，取决于教程版本。

**辨析｜易错点：** 别下载「满血 BF16 权重」然后抱怨装不下。**ktransformers 跑 671B 的默认形态就是 INT4/混合量化**——这是消费级部署的物理前提（第 3 篇算过：BF16 的 1.3TB 放不进 384GB 内存）。

下载权重时还要留意「**来源可信**」：671B 的量化权重有社区多种转换版本，质量与格式参差不齐。**优先用官方教程链接或社区高星仓库的版本**，并核对文件哈希——用错版本的量化权重，轻则精度异常，重则加载失败。**「下载即信任」在 377GB 级别的下载里尤其危险**：下载成本高，出错重下的代价更大，花一分钟核对来源，省几小时的返工。<span class="marginnote">「满血」二字在这里指「671B 全参数、未被剪枝或蒸馏」——<strong>参数一个不少，只是量化了</strong>。量化 ≠ 砍参数，这是「满血」的准确含义。</span>

「满血」还隐含一层「能力对等」：ktransformers 跑出的 671B，其**能力上限**与数据中心跑的是同一份模型——区别只在「推理速度」与「单次推理成本」。这对「本地私有部署」的用户意义重大：**能力不打折、数据不出机、成本降到个人可及**——这三者的组合，是云 API 无法提供的。

## 2 配置注入：一份 YAML 定乾坤

权重就位后，配置注入规则（第 4 篇讲过的机制）。对 DeepSeek-V3，官方教程的注入配置核心是：

**Attention** → 专用 MLA 内核，放 GPU。
**专家** → 异构专家内核，放 CPU（AMX-BF16 或 llamafile 内核）。
- **共享专家 + 热专家** → GPU。
- **量化** → 与权重格式匹配的 INT4 路径。

这四条配置与第 2 篇的「架构四件套」一一呼应：**Attention 去 GPU（稠密）、专家去 CPU（稀疏）、热专家留 GPU（频率）、量化匹配格式（数据）**——你看，部署配置不是「凭空写出来的」，而是「从架构原理推导出来的」。**能「推导配置」而不是「照抄配置」，是部署工程师与「复制粘贴者」的分水岭**：遇到新模型，前者能自己设计注入规则，后者只能等教程。

加上运行参数：

```bash
python -m ktransformers.local_chat \
    --model_path /path/to/DeepSeek-V3 \
    --gguf_path /path/to/quantized.gguf \
    --optimize_rule_path ktransformers_optimize_rule.yaml \
    --cpu_infer 32   # CPU 线程数
```

**关键参数**：`--cpu_infer` 决定 CPU 侧线程数（取物理核数），`--optimize_rule_path` 指向注入规则。

「`--cpu_infer` 取物理核数」这条经验背后是超线程的陷阱：现代 CPU 的「逻辑核」往往是「物理核 × 2」（超线程）。超线程让两个逻辑核共享一个物理核的运算单元——**线程数超过物理核数时，争抢运算单元反而变慢**。所以取「物理核数」而非「逻辑核数」是更稳妥的选择。**「核数」有两种数法，选错会让吞吐不升反降**——这是并行调优里最常见的隐性坑之一。<span class="marginnote">线程数不是越多越好：超过物理核数反而因超线程争抢而变慢。一般取「物理核数」即可；若还要留核给系统，取核数 − 1 更稳。</span>

## 3 启动与预期性能

启动后，加载权重要一段时间（377GB 权重从磁盘读入 + 转换布局，首次加载以分钟计）。加载完成后：

「首次加载以分钟计」这个「慢」是可以被优化的：**把转换后的权重缓存到本地**，下次加载直接读「已就绪」的权重，跳过转换——这正是第 4 篇「权重注入」里「一次性转换、反复使用」的落地。**「把一次性成本缓存起来」是系统设计的通用优化**：转换、编译、索引——凡是「算一次、用多次」的昂贵步骤，都值得缓存。ktransformers 的首次加载慢、之后快，就是这个原则的体现。

**Prefill**：官方数据可达 **~286 token/s**（处理长 prompt 快）。
**Decode**：官方数据约 **~14 token/s**；用户实测常见 **6–8 token/s**（受 DDR5 带宽、CPU 型号、量化格式影响）。

**辨析｜易错点：** 别拿「286 token/s 的 prefill」与「14 token/s 的 decode」直接相加幻想「50 token/s」。**两个数字服务于不同阶段**：prefill 是一次性处理整个 prompt，decode 是逐 token 生成。用户感知的速度主要由 decode 决定——6–8 token/s 大致相当于「每 0.1–0.15 秒出一个字」，可读但不算飞快。

「可读但不算飞快」这个评价，放在「本地跑满血 671B」的语境里其实是**惊人的**：一年前这是数据中心级硬件才能做到的事。**「衡量一个方案的好坏，要放在它的目标场景里」**——ktransformers 的目标不是「比数据中心快」，而是「让个人拥有接近数据中心的体验」。拿它跟 A100 集群比速度是错位比较；正确的比较是「没有 ktransformers 时，个人能不能跑 671B」——答案是「不能」。**「从 0 到 1」与「从 1 到 10」是两种成就**，ktransformers 属于前者。<span class="marginnote">这个速度对标免费云 API 的量级，但<strong>完全本地、数据不出机、无按量计费</strong>——对隐私敏感或高频实验场景，价值不在「最快」，而在「私有 + 可及」。</span>

## 4 公式解析：解码速度的带宽账

为什么 decode 卡在 6–14 token/s？用第 1 篇的带宽公式回头看。设每 token 需读取的激活权重字节 $B_{\text{act}}$，内存带宽 $BW$，则解码速度上界：

$$
\text{tps}_{\max} = \frac{BW}{B_{\text{act}}}
$$

逐项拆解：

- **第一步**：$B_{\text{act}}$ = 激活路径权重 × 每参数字节。671B 模型激活 37B 参数（含热/冷专家 + 稠密），INT4 下约 18.5GB。
- **第二步**：CPU 侧冷专家权重在 DRAM 读——若相当部分走 CPU 带宽（100–400 GB/s），这部分解码上界 = $BW_{cpu} / B_{\text{cold}}$。
- **第三步**：GPU 侧热专家走显存带宽（1 TB/s）——快得多。**整体速度 = 慢的那段（CPU 冷专家读取）主导**。

把数字代入验证「6–14 token/s 从哪来」：设冷专家激活约 20B 参数（INT4，约 10GB），走 200 GB/s 的 DDR5，则上界 ≈ 200/10 = 20 token/s；再叠加 GPU 稠密计算与 CPU 计算本身的时间，落到 6–14 token/s 量级——**数量级吻合，说明带宽账是自洽的**。这种「用理论公式反推实测数字」的练习，是验证「我真的懂了」的最好方法：**能复现数字，才算理解了机制**。

**一句话**：解码速度由「冷专家权重在 CPU 带宽下的读取时间」主导——DDR5 带宽越高、冷专家占比越低，速度越快。这也是为什么「GPU 专家占比」参数如此重要：**把更多热专家放 GPU，就减少走 CPU 带宽的权重字节**。

「把更多专家放 GPU」虽然能提速，但有个隐性代价：**GPU 专家多了，KV Cache 就少了，能撑的上下文与并发就降了**（第 2 篇的拉锯战）。所以「提速」与「长上下文/高并发」在调参上常常互相矛盾——**部署调优的本质，是在「速度」与「容量」之间找一个满足你需求的平衡点**。没有「默认最优」，只有「对你最优」：短问答场景多放专家求快，长文档场景少放专家求容量。<span class="marginnote">想提速的具体杠杆：① 用更高带宽的 DDR5（400GB/s+ 的服务器内存）；② 调高 `--kt-num-gpu-experts` 把更多专家放 GPU（前提显存够）；③ 用更低位宽量化（INT4 优于 INT8）。三者都是在「带宽账」上做文章。</span>

## 5 部署检查清单：从下载到跑通的完整核对

把部署流程压成一张「checklist」，每完成一项打勾：

- [ ] 权重下载完成，体积符合预期（约 377GB）
- [ ] 磁盘空间足够（权重 + 转换中间文件 + 缓存）
- [ ] 内存足够（382GB+），DDR5 带宽达标
- [ ] 注入规则与模型匹配（核对模型名与 YAML）
- [ ] 首次加载完成，无权重转换报错
- [ ] 简单 prompt 跑通，输出合理
- [ ] 性能与官方量级相符（decode 6–14 token/s 量级）

**Checklist 的价值**：它把「部署」从「玄学」变成「可验证的流程」——**每一格打勾都是一个「确认了」的证据**，最终「跑通」不再是「运气好」，而是「每步都验证过」的必然结果。这也呼应了本专题贯穿始终的「可度量、可验证」精神。

若部署失败，checklist 还承担「定位工具」的角色：**回看哪一格没打勾，问题范围就锁定在哪一步**——是权重没下对（第 1 格）、还是注入配置错（第 4 格）、还是性能不达标（第 7 格）。**「带检查点的流程」天然具备「二分定位」能力**：每个检查点都是一次「是否确认」的判断，出问题时「最后一个未确认的点」就是最可疑的起点。

## 6 小结

把 24GB 部署案例浓缩成「三个数字、一个平衡」：**377GB（权重体积）、24GB（显存）、6–14 token/s（解码速度）**，以及贯穿始终的「速度 × 容量」平衡。这三个数字本身，就是 ktransformers「算力普惠」的全部证明。

- 部署三步：**下载量化权重（约 377GB）→ 配置注入 YAML → 启动推理**。
- 成败关键：**先体检硬件（DDR5/AMX）、再核对权重来源、最后验证性能与理论量级吻合**。
- 「满血」= 全参数、只是量化；消费级跑 671B 的默认形态就是 INT4/混合量化。
- 预期性能：prefill 约 286 token/s、decode 约 6–14 token/s——**decode 决定用户感知速度**。
- 解码速度 = 带宽账：$BW / B_{\text{act}}$
