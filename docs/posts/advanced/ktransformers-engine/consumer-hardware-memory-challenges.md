## 为什么把「装不下」当成一门课

前三篇论证了 MoE 很稀疏、激活有幂律、Roofline 能定分工——但这都建立在「模型能放进系统」的前提上。回到现实：**DeepSeek-V3 有 671B 参数，而一张 RTX 4090 只有 24GB 显存**。两者之间隔着约 28 倍的鸿沟。这一篇要回答一个最朴素也最致命的问题：**671B 参数到底卡在哪里？显存、带宽、还是别的什么？**<span class="marginnote">这一节是 ktransformers 论文第 2 节的动机核心：<strong>先用数量级把「消费级 vs 671B」的差距钉死，才能理解后面所有架构选择为什么是「不得不」</strong>。装不下不是缺点，是必须被设计绕过的约束。</span>

把问题拆成两半：**显存容量**决定「权重放得下吗」，**内存带宽**决定「权重读得动吗」。前一半是物理天花板，后一半是数学天花板。下面四节分别算显存账、带宽账、算力账，最后再看看那些隐蔽的工程成本——它们共同构成「消费级运行超大 MoE」的全部挑战。

## 1 显存账：24GB 与 1.3TB 的鸿沟

DeepSeek-V3 的 BF16 权重总共有多少？先算体积：

$$
\text{size} = P \times \frac{b}{8} \ \text{Bytes}
$$

671B 参数、每参数 2 字节（BF16），体积约 $671 \times 2 \approx 1342$ GB——**约 1.3TB**。而一张 RTX 4090 只有 24GB 显存，两者相差约 56 倍。即使是 8 张 4090 的 192GB，也放不下 1.3TB。

于是量化成为第一步的必然：**INT4 量化把每参数压到 0.5 字节，671B 缩到约 336GB**；混合量化（4.5-bit，敏感层保留更高位宽）实测约 **377GB**。可即便是 377GB，也远超显存——**量化解决了「字节数」，没解决「显存容量」**。要装 377GB，只能靠几百 GB 的 DRAM 系统内存。

**核心结论**：**超大 MoE 的权重物理上装不进消费级显存，「装进大内存」是唯一出路**。这一步走完，「权重在 CPU 内存」就成了事实前提——后面的所有问题都从这个前提生长出来。<span class="marginnote">对比数据中心：8×H100 的 640GB HBM 也装不下 1.3TB，同样需要量化。但数据中心的「量化后放哪」答案是 GPU HBM；消费级的答案是 CPU DRAM。<strong>放哪不同，决定了后面整套架构不同</strong>。</span>

## 2 带宽账：权重每读一遍都要付钱

权重放进 DRAM 之后，**每次前向都要把它们读一遍**。读的速度由内存带宽决定——这是数学天花板。

**decode 的带宽账**：每生成一个 token，需要读取该 token 激活的权重（约 37B 参数，INT4 下约 18.5GB）。若全部从 CPU 内存读，速度上界是：

$$
\text{tps}_{\max} = \frac{BW_{\text{cpu}}}{B_{\text{act}}}
$$

消费级 DDR5 带宽约 100–200 GB/s，代进去：$200 / 18.5 \approx 10$ token/s——**这就是「全量卸载」方案的天然上限**（后面第 5 篇会专门拆）。更糟的是，若权重还要从 CPU 内存经 **PCIe** 搬到 GPU 再算，PCIe 4.0 ×16 的约 32 GB/s 会成为新的、更低的墙：$32 / 18.5 \approx 1.7$ token/s——慢到不可用。

**prefill 的带宽账**：prefill 一次性处理整个 prompt，要读的权重量与 decode 单 token 量级相近，但它可以并行、吞吐导向。即便走 CPU 带宽，377GB 全扫一遍也要数秒——**prefill 慢在「绝对量」，decode 慢在「每 token 都付带宽」**。<span class="marginnote">这两笔账给出两条不同的优化方向：<strong>prefill 要「减少读取的字节」（量化 + 把高频权重放显存），decode 要「减少每 token 的带宽付出」（权重就地计算、避免跨设备搬运）</strong>。Roofline 之所以是后面所有决策的尺子，正是因为这些账都能统一到「算术强度」上。</span>

把两笔账放一起，得到这一篇最重要的判断：**消费级跑 671B 的瓶颈不是「算力」，而是「权重读得动读不动」**——GPU 的算力（80 TFLOPS 量级）绰绰有余，但权重待在慢速 DRAM 里，每读一次都在向带宽「缴税」。谁能让「权重读取」变便宜，谁就赢。

## 3 公式解析：显存与带宽的两笔账并算

把两个约束合并成一张「可行性表」，这是整篇的浓缩：

$$
\text{可行} \iff V_{\text{权重}} \le V_{\text{内存}} \;\wedge\; \frac{B_{\text{act}}}{BW_{\text{瓶颈}}} \le t_{\text{可接受}}
$$

逐项拆解：

- **第一步，容量约束**：$V_{\text{权重}}$（377GB，INT4 量化后）必须 ≤ 系统内存容量（消费级可配到 384GB+）。这是「装不装得下」的硬约束，不满足一切免谈。
- **第二步，带宽约束**：解码每 token 的时间 $B_{\text{act}}/BW_{\text{瓶颈}}$ 必须可接受。$B_{\text{act}}$ ≈ 18.5GB（激活的 37B 参数），$BW_{\text{瓶颈}}$ 取决于「权重从哪读」——CPU DRAM（100–200 GB/s）还是 PCIe（32 GB/s）。
- **第三步，结论**：**容量约束把权重逼进 DRAM，带宽约束又规定「不能全部经 PCIe 搬去 GPU」**——于是「权重在 CPU 侧就地计算」成了唯一剩下的路。这正是 ktransformers 架构的第一个必然推论。

值得补充的是「瓶颈」的选择权：$BW_{\text{瓶颈}}$ 不是固定的——**谁被选中当读取路径，谁就成为瓶颈**。如果权重留在 CPU DRAM 且由 CPU 就地计算，瓶颈是 DDR5 带宽（100–200 GB/s）；如果每次都要经 PCIe 搬去 GPU，瓶颈骤降到 32 GB/s。**架构设计的核心自由，恰恰是「选择把瓶颈放在哪段」**——ktransformers 选择「DDR5 当瓶颈」，因为它比 PCIe 快 3–6 倍，而且还能被量化、冷热分层进一步摊薄。<span class="marginnote">「选择瓶颈」这个视角贯穿整篇：全量卸载把瓶颈放在 PCIe 或 DDR5 且每 token 都付满；ktransformers 的目标是<strong>把 DDR5 的读取量从「全部激活权重」降到「只有冷专家那一小部分」</strong>。同样是 DDR5，读 18.5GB 与读 2GB 的差别是天壤之别。</span>

## 4 算力账：为什么算力反而是「富余」的

装得下、读得动之外，第三个问题是「算得动吗」——而这一问的答案，恰恰是最不悲观的。

**decode 的算力账**：每 token 只激活 37B 参数，前向的浮点运算量约 $2 \times 37B = 74$ GFLOPs。GPU 有 80 TFLOPS 的 FP16 算力——**理论上每秒能算上万个 token**，远超带宽允许的 10 token/s。算力在这条链路里是「过剩」的。

**prefill 的算力账**：prefill 处理长 prompt、大 batch，浮点运算量随 batch 与序列长度增长——**这时算力才真正被用起来**。prefill 是「算力吃满」的阶段，decode 是「带宽受限」的阶段。

**结论**：消费级跑 671B 的资源瓶颈是「**显存装不下、带宽读不动**」，算力反而是最宽裕的。<span class="marginnote">「算力富余」听着反直觉，其实是大模型推理的常态：<strong>decode 阶段真正在意的不是「算得快」，而是「权重喂得够不够快」</strong>。理解这一点，就不会把优化的力气浪费在「提升算力」上——该花的力气在「让数据更快到位」。</span>

这条判断还带来一个「资源经济学」的推论：**既然算力富余、带宽稀缺，那么「用算力换带宽」就永远划算**。什么是「用算力换带宽」？——量化（用更多计算换更少字节）、缓存（用存储换重算）、就地计算（用 CPU 算力换掉 PCIe 搬运）。后面每一篇的优化，本质上都是这笔「以算换存、以算换带宽」的交易。**记住「算力富余」这个前提，你就能看懂 ktransformers 所有优化的「交易逻辑」**。

## 5 隐性成本：还有三笔账在背后

显存、带宽、算力是三大账，还有三笔隐形成本，同样决定「跑不跑得动」：

**第一笔：加载成本**。377GB 权重从磁盘读入 DRAM + 转换布局，首次加载以分钟计。这不影响单 token 延迟，但影响「能不能实用」——每次启动都等十分钟，体验就很差（所以「一次性转换、缓存复用」是部署必修课）。

**第二笔：跨设备同步**。GPU 与 CPU 协作时，专家结果要从 CPU 回传 GPU。这笔开销若处理不当（频繁小传输、每层都同步），会吃掉大量 PCIe 带宽——这正是后面「异步调度 + CUDA Graph」要解决的问题。

**第三笔：内存带宽的共享性**。并发请求增多时，所有请求共享同一条 DDR5 带宽——**带宽是「全局共享」的稀缺资源**，并发一高就会互相拖累（balance-serve 篇会展开）。<span class="marginnote">这三笔隐性成本有一个共同点：<strong>它们都不在「模型算法」里，而在「系统实现」里</strong>——这提醒我们，消费级推理的难点从来不是「模型多聪明」，而是「工程多细致」。这也是为什么本专题把大量篇幅留给系统设计。</span>

## 6 消费级部署的现实清单

把三笔账落到「一台机器该长什么样」上。能跑 671B 的消费级部署，硬件画像大致是：

| 部件 | 规格 | 这笔钱买了什么 |
| --- | --- | --- |
| GPU | RTX 4090（24GB 显存，1 TB/s 带宽） | 稠密算力 + 显存 KV |
| CPU | 多核 x86（支持 AVX512/AMX 更佳） | 冷专家计算的算力与就地执行 |
| 内存 | 382GB+ **DDR5**（不要 DDR4） | 装下 377GB 权重 + KV Cache 的空间 |
| 磁盘 | 400GB+ SSD | 存放权重文件，加速首次加载 |

**辨析｜易错点：** 内存选 DDR4 是最常见的翻车点——DDR4 带宽约 DDR5 的一半，等于把「带宽账」里本就不宽裕的数字再腰斩一次。**内存不只是「够大」，还得「够快」**——带宽账里算过的 10 token/s 上限，是 DDR5 给的；DDR4 直接掉到一半。这也是为什么 ktransformers 官方推荐 DDR5 而非「够大的 DDR4」：**容量满足「装得下」，带宽才能满足「读得动」**。

「为什么是 382GB+ 而不是 380GB」这类数字，也值得读两层：底层是「377GB 权重 + 若干 GB KV + 系统余量」的工程估算；上层是「理论预算 + 实际冗余」的部署哲学——**永远给自己留一点余量，别卡在账本的整数上**。现实中很多人配 384GB 是「4×96GB」的内存条组合，恰好也印证了「余量」思维。

把清单与前面三笔账一一对应，你会看到每条硬件都在「为账买单」：显存买「稠密算力与热专家」，大内存买「容量与冷专家空间」，DDR5 买「带宽」，多核 CPU 买「就地计算」。**「硬件是账的实体化」**——每一分钱花的都是前面算过的一笔账。这让你在选硬件时不必「听别人说」，而是自己「算账」：缺什么性能，就是哪笔账没付够。<span class="marginnote">这套「硬件=账的实体化」思维可以迁移到任何系统：<strong>买硬件之前，先把「容量账、带宽账、算力账」各算一遍</strong>，缺哪补哪，而不是「别人推荐什么买什么」。自己会算账，才不会被营销带偏。</span>

## 7 小结

把「消费级的挑战」收成一句话：**装得下（容量）是前提，读得动（带宽）是约束，算得快（算力）反而是最不稀缺的**。

- **显存账**：BF16 权重 1.3TB，INT4 量化后约 377GB——物理上装不进 24GB 显存，必须放进几百 GB DRAM。
- **带宽账**：decode 每 token 要读约 18.5GB 激活权重，CPU DRAM（100–200 GB/s）给出约 10 token/s 上限，PCIe（32 GB/s）只有约 1.7 token/s。
- **算力账**：每 token 只算 37B 参数，GPU 算力富余——真正的瓶颈是「数据到位」，不是「算得动」。
- **可行性判据**：容量约束 × 带宽约束双门槛——它把「权重在 CPU 侧就地计算」逼成唯一出路。
- **三笔隐性成本**：加载、跨设备同步、带宽共享——它们不在算法里，而在系统实现里。
- **硬件即账本**：显存买稠密、大内存买容量、DDR5 买带宽、多核 CPU 买就地计算——每分钱都在为某笔账买单。
- **核心转向**：瓶颈不是算力而是「权重读取」，**谁让读取变便宜，谁就赢得消费级 671B**。

在下一节，我们将把「全量卸载」这条最直觉的路线拿出来解剖——**llama.cpp 与 DeepSpeed 把权重全放 CPU/磁盘，为什么只能到 3–5 token/s？瓶颈到底卡在哪一环？**
