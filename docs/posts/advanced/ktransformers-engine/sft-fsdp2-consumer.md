## 为什么 SFT 需要「多卡 + FSDP2」

上一节讲的是 LoRA 微调的单机版。但要训得更快、batch 更大，就要把多张 4090 都用起来——这时单机的朴素训练（一张卡装全部）不再适用，需要**数据并行之上的分片策略**。ktransformers 的官方 SFT 路线用 **FSDP2 + accelerate** 把多卡 4090 组织起来，同时保住异构放置。<span class="marginnote">FSDP2 是 PyTorch 2.x 的「每参数分片」数据并行（Fully Sharded Data Parallel 第二代）。它与上一节的 KTrainer 的关系：<strong>KTrainer 管「每张卡放哪些算子」，FSDP2 管「多张卡之间如何分片与通信」</strong>——两层分工，不冲突。</span>

## 1 为什么是 FSDP2 而不是别的

SFT 超大 MoE 模型，可选的分布式方案有几种：

| 方案 | 思路 | 对消费级 MoE 的问题 |
| --- | --- | --- |
| Data Parallel（DP） | 每卡一份完整模型 | 模型装不下，根本复制不了 |
| Tensor Parallel（TP） | 把单层矩阵切到多卡 | 卡间通信频繁，消费级 PCIe 带宽不足 |
| ZeRO-Offload | 优化器/梯度卸载到 CPU | ktransformers 已把权重放 CPU，再卸载收益重叠 |
| **FSDP2（每参分片）** | 每参数分片到各卡 + 用时聚合 | 通信量小、与 LoRA/异构放置天然兼容 |

**FSDP2 的要点**：把每个参数**按卡分片**，前向需要时**聚合（all-gather）**、算完**释放**；反向梯度**归约（reduce-scatter）**。对 LoRA 微调，分片的是 LoRA 增量（很小）——通信量小，PCIe 也扛得住。

「分片 + 用时聚合 + 算完释放」这个模式，本质是**用「按需通信」换「显存容量」**：不把完整参数常驻每张卡（省显存），而是用到时才从各卡收集（花通信）。这是一个经典的「空间换时间」权衡的变体——**用「通信开销」换取「每卡装得下」**。对 LoRA 微调，分片的是「小增量」，通信量小，这笔交换非常划算；若是全量微调 671B，通信量巨大，PCIe 就成了灾难——**「FSDP 值不值」取决于分片对象的大小**，这正是 ktransformers 选「FSDP2 + LoRA」组合的原因。<span class="marginnote">FSDP2 之于 FSDP1 的改进是「按参数粒度」分片（per-parameter sharding），而非按层——内存更省、通信更细。ktransformers 选择它，正是因为<strong>它允许「冻结的专家权重留在 CPU、可训的 LoRA 分片在各 GPU」这种混合形态</strong>。</span>

## 2 启动形态：accelerate + 配置

官方 SFT 的启动命令：

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3 accelerate launch \
    --config_file examples/ktransformers/accelerate/fsdp2_kt_int8.yaml \
    src/train.py \
    examples/ktransformers/train_lora/qwen3_5moe_lora_sft_kt.yaml
```

要点拆解：

**`accelerate launch`**：HuggingFace 的分布式启动器，负责初始化进程组。
**`fsdp2_kt_int8.yaml`**：accelerate 的 FSDP2 配置——`int8` 指专家权重以 INT8 精度驻留（配合 CPU 端 INT8 内核）。
- **`train.py + 训练 YAML`**：复用 LLaMA-Factory 的训练入口与配置。

**多卡的角色**：4 张 4090 各自承担一部分 Attention 与热专家计算（模型并行 + 显式层放置，而非简单复制），LoRA 增量按 FSDP2 分片，梯度经归约同步。

「显式层放置，而非简单复制」点出了多卡的组织方式：不是「每卡算一份完整 batch」（数据并行），而是「每卡负责模型的不同部分」（模型并行）——**注意力与热专家按层分到各卡**，batch 的 token 流经各卡协作完成前向。这与推理里的「层内异构」一脉相承：**ktransformers 的放置哲学从推理延伸到训练，都是「按算子性质分到最适合的设备」**。多卡训练只是把「设备」从「GPU/CPU」扩展到「多张 GPU」，同一套哲学继续生效。<span class="marginnote">与「DataParallel（每卡复制全模型）」的对比：DP 在模型装不下时根本不可用；FSDP2 把「装得下」变成「每卡只装一小片」——这才是多卡消费级训练的正确姿势。</span>

## 3 异构 + 分片：冻结权重在 CPU，LoRA 分片在 GPU

这套方案的独特之处，是**异构放置与 FSDP2 分片的叠加**：

**冻结的 671B 权重**：大多数专家的权重常驻 CPU（各卡共享同一份 CPU 权重——不复制）。
**可训的 LoRA 增量**：分片到各 GPU（FSDP2），前向聚合、反向归约。
- **Attention 与热专家**：按层分配到各 GPU（KTrainer 的放置规则）。

**这带来的独特优势**：CPU 权重是**跨卡共享**的——不像多机训练那样每卡各存一份权重副本。显存只装「该卡负责的层」的激活与 LoRA 分片，因此 4×24GB 显存能承载的 batch 远大于「单卡 ×4」的直觉。

「CPU 权重跨卡共享」是多卡异构独有的红利：在多机训练里，每张卡通常各存一份权重（内存翻倍）；而在 ktransformers 里，671B 权重只有 CPU 里一份，所有卡共享——**内存成本不随卡数增长**。这意味着「加卡」的成本主要是 GPU 硬件本身，而不是「每加一张卡就要多配一份 377GB 内存」。**「共享一份大权重、各算各的增量」是异构多卡的核心经济性**——它让「多卡扩展」从「内存翻倍」变成「只加算力」。<span class="marginnote">官方数据：DeepSeek-V3 671B 在 2–4×RTX 4090 上 SFT 可达约 40 token/s，内存约 70GB；Kimi-K2 在 2×4090 上约 44 token/s。作为对照，<strong>这套组合是 4090 级别显卡上唯一能跑 671B 级 LoRA 微调的方案</strong>。</span>

## 4 公式解析：FSDP2 的显存账

FSDP2 能装下的「模型大小」由「每卡显存 × 卡数」决定。设单卡显存 $V_g$、卡数 $N$，可训参数总显存需求 $S$（LoRA + 激活 + 优化器状态），则可行条件：

$$
S \le N \times V_g
$$

逐项拆解：

- **第一步**：$N \times V_g$ 是聚合显存——4×24GB = 96GB。
- **第二步**：$S$ 包含 LoRA 参数、每卡激活、优化器状态。LoRA 微调时 $S$ 远小于全量微调——**所以 96GB 足以支撑较大 batch**。
- **第三步**：冻结权重不进 $S$（它们在 CPU）——这是「671B 也能训」的关键。

注意第二步里「每卡激活」——激活是 batch 大小与序列长度的函数，**batch 越大、序列越长，激活越占显存**。所以「多卡买更大 batch」的账要反过来算：batch 翻倍，激活翻倍，显存需求翻倍——**4 卡能撑的 batch 大约是单卡的 4 倍，而不是「想多大就多大」**。显存账 $S \le N \times V_g$ 里的 $S$ 是「batch 的函数」，这让「batch 该设多大」变成了「解一个显存不等式」的问题——**「先算显存账、再定 batch」是训练配置的第一原则**。

**一句话**：FSDP2 让「可训部分」跨卡均摊，冻结权重留在 CPU——消费级多卡的总显存，全部用于可训部分与激活。

把「全部用于可训部分与激活」再量化一下：4×24GB = 96GB 显存，其中 LoRA 增量（几百 MB）分片后每卡只有几十 MB，**显存几乎全部留给「激活」与「注意力计算」**——也就是说，多卡 SFT 的显存瓶颈不是「模型」，而是「batch 的激活」。这带来一个直观结论：**多卡主要买的是「更大 batch 的能力」，而不是「装更大模型的能力」**——模型早已在 CPU 里，卡只负责「算」。理解这一点，你就知道加卡的收益曲线：batch 需要多大，就配多少卡。<span class="marginnote">对比 ZeRO-Offload：它把优化器/梯度卸到 CPU，但训练吞吐受 CPU 往返拖累；ktransformers 把<strong>冻结权重</strong>放 CPU（只读、无梯度往返）、<strong>可训部分</strong>留 GPU——数据流更干净，这是「快 6–12 倍」的一个来源。</span>

## 5 辨析｜易错点：多卡 ≠ 模型切得更碎就更快

**辨析｜易错点：** 卡数翻倍，吞吐不翻倍。卡间要通信（聚合/归约），PCIe 带宽是共享瓶颈；且 CPU 侧专家计算不随卡数扩展（权重在 CPU、单份）。**多卡主要买「更大 batch + 更快的 GPU 侧训练」，CPU 侧仍是潜在的瓶颈**——卡太多时，CPU 专家计算会成为新的天花板。

「CPU 侧不随卡数扩展」这句值得再想一层：因为 671B 冻结权重只有 CPU 一份，无论 2 卡还是 8 卡，CPU 侧专家计算的**总量不变**（每步的前向都要过同样的冷专家）——加卡只是让「GPU 侧」变快，CPU 侧的「每步耗时」纹丝不动。**当 CPU 专家计算是每步耗时的大头时，加卡对「每步时间」几乎无帮助，只帮「更大的 batch」**。这就是为什么「2–4 卡是甜点」：超过后，CPU 每步耗时成为刚性瓶颈，加卡的边际收益趋近于零。**「瓶颈在哪一层，加资源就加在哪一层」**——这是扩展性的第一原则。<span class="marginnote">这也是为什么官方常见配置是「2–4 张 4090」而非「8 张」：<strong>超过一定卡数，边际收益递减，而 CPU 侧与 PCIe 的瓶颈凸显</strong>。调优的方向不是无脑加卡，而是「让 CPU 专家计算与多卡 GPU 计算平衡」。</span>

## 6 多卡 SFT 的调优速查

把多卡场景的常见问题与对策收成一张速查表：

| 症状 | 根因 | 对策 |
| --- | --- | --- |
| 卡数多了吞吐不涨 | CPU 专家计算成瓶颈 | 检查 CPU 侧利用率，或减少 GPU 卡数 |
| 卡间通信耗时高 | PCIe 带宽饱和 | 减小 FSDP2 分片粒度，或压缩梯度 |
| 显存不够 | 激活或 LoRA 分片过大 | 减小 batch、开梯度检查点 |
| 训练不稳 | 学习率/LoRA 秩不匹配 | 降 lr、调小 $r$ |

**调优心态**：多卡 SFT 不是「卡越多越好」，而是「让每条链路都不成为瓶颈」——**GPU 算力、CPU 专家、PCIe 通信、显存容量，四者必须匹配**。哪一环先到极限，哪一环就是新的瓶颈；调优就是「找到当前瓶颈、解除它、再找下一个」。

「瓶颈游走」是调优的常态：你以为在优化「GPU 算力」，瓶颈可能已经悄悄移到「CPU 专家」；解决了 CPU，PCIe 又冒头。**性能调优是一场「打地鼠」游戏**——但每次「打中」都让系统前进一截。这种「瓶颈迁移」思维（第 1 篇 Roofline 也提过）是性能工程师的核心心法：**永远先问「当前瓶颈在哪」，而不是「哪里还能优化」**——后者没有方向，前者才有。

## 7 小结

把多卡 SFT 浓缩成「一个分片、一个共享、一个瓶颈」：**FSDP2 分片**可训增量、**CPU 权重跨卡共享**、**CPU 专家计算是潜在瓶颈**——三者决定了多卡扩展的「收益曲线」。

- 消费级 SFT 路线 = **FSDP2 + accelerate + KTrainer 异构放置**三层叠加。
- FSDP2 按参数分片：**通信量小、与 LoRA/异构放置兼容**，优于 DP/TP/ZeRO 对消费级场景的适配。
- 独特形态：**冻结权重共享于 CPU，LoRA 增量分片于各 GPU**——显存全部用于可训部分。
- 显存账：$S \le N \times V_g$——聚合显存决定可训部分 + 激活能装多少，冻结权重不进账。
- CPU 专家计算是潜在瓶颈：权重只有 CPU 一份，加卡不改变每步的 CPU 耗时——「瓶颈在哪层，资源就加在哪层」。
- 甜点是 2–4 卡：超过后边际收益递减，PCIe 与 CPU 侧瓶颈凸显。

再补一句「从单机到多卡」的收尾：这一节把 SFT 从「单机 LoRA」推进到「多卡 FSDP2」——**但底层哲学没变：冻结的大权重留在 CPU、可训的小增量在 GPU**。多卡只是把「设备」从「GPU/CPU」扩展成「多张 GPU + CPU」，同一套「异构放置」继续生效。**「换规模不换哲学」是这套设计能平滑扩展的原因**——理解「哲学不变、规模变」，你就不会在多卡面前感到「又是一套新东西」：它只是单机异构的多卡版本。
