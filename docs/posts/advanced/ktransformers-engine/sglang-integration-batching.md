## 为什么一个本地引擎要「服务化」

ktransformers 不只做单机跑通——它还能作为 **SGLang 的推理后端**，把 671B 模型变成**可服务多用户**的 OpenAI 兼容服务。这一步的关键是 **Continuous Batching（连续批处理）**：让多个并发请求共享同一批推理，把 GPU/CPU 的每一轮计算都装满。<span class="marginnote">SGLang 是斯坦福与社区开源的 LLM 推理框架，ktransformers 自 2025 年 10 月起以 <strong>sglang-kt</strong> 包集成。SGLang 负责调度层（batching、路由、API），ktransformers 负责内核层（异构专家计算）——这是「调度框架 + 计算后端」的标准分工。</span>

## 1 朴素批处理 vs 连续批处理

**朴素批处理（static batching）**：把请求按 batch 分组，等整个 batch 全部解码完，再服务下一批。问题：不同请求长度不同，短请求很快结束，却要干等长请求——**GPU 出现大量空转**。

「短请求干等长请求」的空转有多严重？设想一个 batch 里有一个超长请求（生成 1000 token）和几个短请求（各 10 token）：短请求 10 步后就该结束，但在朴素批处理里，它们要陪着长请求跑完 1000 步——**短请求的实际完成时间被长请求放大了 100 倍**。这种「最慢决定整体」的效应，让朴素批处理在「长短混合」的负载下效率极低。这也是为什么「请求长度不均匀」是推理服务必须解决的核心问题——连续批处理正是它的解药。

**连续批处理（continuous batching）**：每一轮解码，调度器**动态决定**「这批里哪些请求继续解码、哪些已结束换新请求进来」。请求按自己的节奏进出，batch 始终被填满——每轮迭代都在算「有意义的 token」，而不是空等。

把「动态决定」再讲透一层：连续批处理的关键，是把「批的组成」从「启动时定死」变成「每轮迭代都在变」——某个请求解码完最后一步，立刻腾出 slot 给新请求；某个请求还在 prefill，另一个已在 decode，它们**在同一轮里混合推进**。这种「混合阶段」的批处理，是 SGLang 这类框架的核心调度能力。

「连续批处理」在业界也叫「动态批处理」（dynamic batching）或「水平批处理」（level batching）——名字虽多，核心都是「批的组成随每轮迭代动态变化」。**掌握一个概念的多重命名**，是读技术资料的通用技巧：不同文章用不同术语说同一件事，认得出「它们是同一件事」，就不会被术语吓住。对 ktransformers 而言，batch 里既有「需要 GPU 稠密计算」的 token，也有「需要 CPU 冷专家」的 token——**混合 batch 恰好让 CPU 与 GPU 的负载更均衡**，这是它从连续批处理中额外受益的原因。

对 ktransformers 的异构流水线，continuous batching 还有一个额外好处：**batch 越大，CPU 侧的并行任务越多**——多个请求可能命中同一个冷专家，一次 CPU GEMM 服务多个 token，CPU 吞吐被进一步填满。

「多个请求命中同一个冷专家」是 MoE 稀疏性 + 批处理叠加的「意外之喜」：单请求时，一个冷专家被命中可能只服务 1 个 token；并发时，多个请求如果都路由到同一个冷专家，就能**一次 GEMM 服务多个 token**——专家权重的读取成本被多个请求分摊，CPU 带宽的「每 token 成本」下降。这等于给「冷专家卸载」又添了一个理由：**低并发时冷专家在 CPU 上是「偶尔慢一次」，高并发时它是「批量高效服务」**——稀疏 + 批处理，让 CPU 侧也从「规模效应」中获益。<span class="marginnote">这解释了为什么「并发高」对异构引擎尤其重要：<strong>batch 稀释了每次解码的固定开销（内核启动、跨设备等待），CPU 侧也因「同专家多 token」而更高效</strong>。单请求解码慢，多请求并发反而吞吐更优。</span>

## 2 ktransformers 在 SGLang 里的角色

SGLang 作为「大脑」，ktransformers 作为「算力」：

「大脑 vs 算力」的分工，回答了一个常见疑问：「ktransformers 自己不是也能跑推理吗，为什么要套一层 SGLang？」答案在于**职责边界**：ktransformers 的 `local_chat` 适合「单机自己玩」；而「对外服务、多用户并发、OpenAI API、连续批处理」是 SGLang 这类调度框架的专职。**「本地用」与「服务化」是两套需求，一个引擎很难两头都做得极致**——所以 ktransformers 选择「在服务化场景让 SGLang 当大脑」，自己专注算力。这是「各司其职」的理性选择，而非「能力不足」。

| 层 | 组件 | 职责 |
| --- | --- | --- |
| 调度层 | SGLang 前端 | 请求排队、continuous batching、路由、OpenAI API |
| 翻译层 | `sglang-kt` 集成 | 把 SGLang 的 `num_gpu_experts` 翻译成 kt-kernel 的 `gpu_experts_mask` |
| 内核层 | ktransformers | 异构专家调度、Marlin/AMX 内核、三层 KV 缓存 |

这张三层表揭示了一个「组合式创新」的路径：**ktransformers 不需要自己重写 batching、API、路由**——这些 SGLang 已经做得很成熟；它只需要贡献「别人没有的内核能力」。**「站在巨人的肩膀上」不是套话，而是工程上最理性的选择**：重复造轮子（重写一个调度框架）是浪费，把精力投在自己最独特的价值（异构内核）上才是正解。这也解释了为什么「引擎 + 框架」的生态组合（如 vLLM + 各种后端）成为主流：**每个团队只做自己最擅长的一段，通过标准接口拼接成完整系统**。

**关键接口**：SGLang 传入「放多少专家上 GPU」的高层意图，`sglang-kt` 把它翻译成 ktransformers 的专家掩码（第 2 篇），ktransformers 据此完成异构放置。两端通过这一层「意图翻译」解耦——SGLang 不需要懂专家掩码，ktransformers 不需要懂 batching 策略。

「SGLang 不需要懂掩码、ktransformers 不需要懂 batching」这句解耦描述，正是「框架与后端」协作的标准形态：**框架管「请求的组织」，后端管「计算的高效」，二者通过一层「意图契约」交接**。这种分工让每一侧都能独立演进——SGLang 改进调度策略，ktransformers 改进内核性能，互不阻塞。**「解耦」不是「不相关」，而是「各管一段、接口清晰」**——这是所有大型软件系统能持续演进的工程基础。

## 3 多并发下的内存预算：并发与上下文的拉锯

并发数是双刃剑：并发越高，显存 KV 占用越大（每个请求都要占 KV 空间），留给 GPU 专家的空间越少。官方基准里对 Qwen3-Next-80B-A3B 的并发测试显示，`frequency` 与动态专家更新在较低 GPU 专家占比下收益明显——**高并发场景下「省出来的显存」特别值钱**。

「高并发下省显存特别值钱」这条洞察值得展开：并发高时，KV Cache 占了大头，GPU 专家只能挤占剩余空间——此时「把专家数降到很低」反而成为常态。而专家越少，CPU 侧负担越重、解码越慢——但**并发本身弥补了单请求的慢**（吞吐优先）。所以高并发场景的调优逻辑是「用并发换吞吐、把显存让给 KV」；低并发场景则是「用显存放专家、换单请求的速度」。**「并发高低」直接决定「优化重心」**——先看你的负载形态，再决定往哪边调。<span class="marginnote">并发、上下文、GPU 专家三者共享同一块显存预算：<strong>并发 × 上下文长度 = KV Cache 总需求，余下的空间才给专家</strong>。调 `--max-total-tokens`、`--chunked-prefill-size` 就是在解这道「三角不等式」。</span>

**辨析｜易错点：** 并发不是越高越好。当并发超过「显存 KV 容量 ÷ 每请求 KV」的临界点，请求会被排队（不算更优），或被迫截断上下文。**正确姿势**：按「并发 × 典型上下文」估出 KV 需求，再决定 GPU 专家与 KV 的分配。

「请求排队」不是坏事——它是连续批处理的正常状态：请求不是「被拒绝」，而是「在队列里等 slot」。**排队的体验取决于「排队时间」与「吞吐」的平衡**：队列太长 → 等待久；队列太短 → 算力闲置。理想状态是「队列长度刚好让设备吃饱」——这就是「背压（backpressure）」思想：用队列长度作为系统负载的信号，让请求速率自然匹配处理能力。**「用队列吸收波动」是服务系统设计的通用手法**，从消息队列到线程池到这里的请求队列，都是同一个模式。

## 4 公式解析：并发与 KV 容量的约束

设并发上限 $C$、每请求平均 token 数 $L$、每 token KV 体积 $b_{kv}$，则 KV Cache 总需求：

$$
V_{\text{need}} = C \times L \times b_{kv}
$$

而显存里 KV 的可分配上限 $V_{\text{gpu,kv}}$ 由「显存 − 专家权重 − 激活」决定。系统能稳定服务并发 $C$ 的条件：

$$
V_{\text{need}} \le V_{\text{gpu,kv}}
$$

逐项拆解：

- **第一步**：$C$ 或 $L$ 任一变大，$V_{\text{need}}$ 线性增长。
- **第二步**：$b_{kv}$ 由模型决定（MLA 已把每 token KV 压到很小）——这是「能服务较高并发」的结构前提。
- **第三步**：超过约束时，请求必须排队或截断——连续批处理让「排队」变成「动态让位」，而不是整批拒绝。

第三步的「动态让位」值得单独点出：朴素系统超载时常常「整批拒绝」（OOM 或超时），而连续批处理可以在「不让任何请求失败」的前提下，通过「让长请求暂停、给短请求让位」来软性降载。**「软性降载」比「硬性拒绝」的体验好得多**——前者是「稍等」，后者是「失败」。这种「宁可排队、不可拒绝」的设计取向，是面向服务的系统与「面向单次任务」的系统的关键区别。

**一句话**：并发上限 = 显存 KV 预算 ÷（平均上下文 × 每 token KV）。想提高并发，要么压上下文、要么压缩每 token KV、要么多给显存——三位一体。

把「三位一体」再落到 ktransformers 的实际：**压上下文** → 设小 `--max-total-tokens`；**压缩每 token KV** → 用 MLA 这类低维 KV 架构（模型决定，系统改不了）；**多给显存** → 少放 GPU 专家（`--kt-num-gpu-experts` 调低）。前两个是「减少需求」，第三个是「增加供给」——**调参的本质，就是在这「减需求/增供给」两个方向上的组合拳**。值得注意的是，「减少 GPU 专家」虽然腾出了 KV 空间，却可能拖慢解码——所以并发与速度常常此消彼长，需要按业务优先级取舍。<span class="marginnote">消费级机器上，几百 GB 内存还可以承接「溢出」的 KV（第 2 篇三层缓存）——但注意，从内存层读 KV 有跨设备成本，<strong>并发过高导致大量 KV 落到内存层时，吞吐会明显下降</strong>。并发不是「越高越快」，而是「在显存 KV 预算内最优」。</span>

## 5 实践：把 SGLang 后端跑起来

把「集成」落地成可操作的步骤，部署时按序执行：

1. **安装**：`pip install sglang-kt`（ktransformers 的 SGLang 集成包）。
2. **启动服务**：`python -m sglang.launch_server --model <路径> --kt-num-gpu-experts 8`。
3. **配放置**：加 `--kt-expert-placement-strategy frequency --init-expert-location <统计文件>` 启用频率感知。
4. **调并发**：按「并发 × 上下文」估出 KV 需求，设 `--max-total-tokens`。
5. **发请求**：用 OpenAI 兼容接口测试（`/v1/chat/completions`）。

启动前还有一步常被忽略：**确认 sglang-kt 与你装的 ktransformers 版本匹配**——两者通过 `gpu_experts_mask` 契约对接，版本错位会导致参数无法识别。这也是「框架 + 后端」生态的一个常见痛点：**组合系统要关注「接口契约的版本兼容」**。升级任何一侧前，先查另一侧的兼容性说明——这是「生态组合」时代的基本工程素养。

**排查口诀**：首 token 慢 → 查 prefill 与 KV 缓存命中；吞吐低 → 查 GPU 专家占比与 CPU 瓶颈；请求排队 → 查 `--max-total-tokens` 与并发上限。**「先分诊、再下药」**，比盲目改参数高效得多。

这一篇把 ktransformers 从「单机引擎」拉到了「服务后端」的位置：配合 SGLang，它不再是「自己玩」，而是「对外提供 OpenAI 兼容服务」。**「能被服务化」是引擎走向生产的关键一步**——本地脚本调用与多用户 API 服务，是完全不同的工程形态，而 ktransformers 通过「框架 + 后端」的组合，两者都支持。

「服务化」还带来一个额外红利：**它可以成为其他系统的基础设施**——RAG 应用、Agent 框架、对话产品，都可以通过 OpenAI 兼容接口把 ktransformers 当作「本地大模型后端」调用。**「引擎 → 服务 → 基础设施」的定位升级**，让 ktransformers 从「跑模型的工具」变成「可以被构建在之上的平台」——这是开源项目影响力的关键跃迁。

下一篇将深入 ktransformers 为多并发提供的专门机制——balance-serve 的「资源均衡」智慧。

## 6 小结

把 SGLang 集成的要点收成「一层契约、两种批处理、一个预算」：**一层契约**（`num_gpu_experts → gpu_experts_mask`）让框架与后端解耦；**两种批处理**（朴素 vs 连续）让并发从「堆请求」变成「填满每轮」；**一个预算**（并发 × 上下文 ≤ 显存 KV）把并发约束变成可计算的不等式。

- **Continuous Batching** 让请求动态进出 batch，消灭空等，最大化每轮计算利用率。
- 异构引擎在并发下收益更大：**同专家多 token 让 CPU GEMM 更高效**，batch 稀释固定开销。
- 分层集成：SGLang 管调度、`sglang-kt` 管意图翻译（`num_gpu_experts` → `gpu_experts_mask`）、ktransformers 管内核。
- 并发约束公式：$C \times L \times b_{kv} \le V_{\text{gpu,kv}}$
