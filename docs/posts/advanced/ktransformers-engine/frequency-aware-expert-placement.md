## 为什么放置需要「频率数据」

第 1 篇我们论证了专家激活服从幂律：少数热专家包揽大多数激活。这一篇要把这句话变成**可运行的策略**——系统怎么知道谁是热专家？怎么表达「谁在 GPU」？答案是两件事：**频率感知放置（frequency-aware placement）**与 **GPU Expert Mask**。<span class="marginnote">官方文档把这个机制称为「flexible GPU expert mask system」，随 ktransformers v0.5.1 引入。它把「显存预算」翻译成「哪批专家进 GPU」的一张掩码——<strong>掩码是放置决策的机器可读形式</strong>。</span>

## 1 频率感知放置：先统计，再决定

**频率感知放置（frequency-aware expert placement）**的流程分两步：

**离线统计**：在部署前，先用参考输入（代表性 prompt 集合）跑一次模型，记录每个路由专家被激活的次数，导出激活统计文件（官方参数 `--init-expert-location` 指向的 `.pt` 文件）。

离线统计的「参考输入」从哪来？实践中通常是三类：**真实流量日志**（从线上抽样的用户请求，最贴近实际）、**领域语料**（针对目标场景精选的样本，覆盖特定任务）、**通用语料**（通用基准集，稳健但中庸）。三类的取舍是「贴不贴近」与「好不好拿」的权衡——**真实流量最准但未必拿得到，通用语料最易得但可能错位**。工程上常见做法：先用通用语料「垫底」，有真实流量后再更新统计，配合动态专家更新逐步逼近最优。<span class="marginnote">这一步是「照一次 X 光」：花一次前向的代价，拿到真实的激活频率分布。分布来自<strong>代表性数据</strong>——数据越接近真实负载，统计越准，放置越优。</span>

**在线放置**：启动时读取统计，把激活频率最高的 $M$ 个专家放进 GPU 显存，其余放 CPU。被选中的集合在 ktransformers 里编码为 **GPU Expert Mask**——一张长度等于专家总数的位图，1 表示「此专家在 GPU」，0 表示「在 CPU」。

「先统计、再放置」这个两步流程，与机器学习里的「训练/推理」两阶段惊人地相似：统计阶段就像「训练」——用数据拟合出「哪些专家热」的模型；放置阶段就像「推理」——把学到的结论用于实际决策。也正因如此，它继承了「训练/推理」的全部教训：**统计质量决定放置质量，而统计的成本要花在离线、花在准备阶段**——绝不让「统计」拖慢在线推理。

$$
\text{mask}[e] = \begin{cases} 1, & e \in \text{top-}M \text{ 最热专家} \\ 0, & \text{否则} \end{cases}
$$

## 2 四种放置策略的取舍

官方 `--kt-expert-placement-strategy` 提供四种策略，对应「有没有统计、怎么用统计」的四种选择：

| 策略 | 需要统计？ | 做法 | 特点 |
| --- | --- | --- | --- |
| `uniform`（默认） | 否 | 把 GPU 专家名额按层均匀分配 | 零成本、稳健；但可能把名额分给冷专家 |
| `frequency` | 是 | 按激活统计挑全局最热的专家上 GPU | **性能最好**（官方基准）；依赖统计质量 |
| `front-loading` | 否 | 从第 1 层开始顺序填满 GPU 名额 | 简单；不利用幂律 |
| `random` | 否 | 固定随机种子（42）随机挑 | 仅作基线对比 |

`frequency` 之所以最优，正是因为它直接利用了幂律：把「名额」全部押在头部热专家上，让 GPU 覆盖的激活比例最大化。官方对 Qwen3-Next-80B-A3B 的基准显示，**`frequency` 与「动态专家更新」组合在较低 GPU 专家占比下收益最明显**（例如 10% 专家占比时吞吐约 56.6 token/s，比 0% 占比约 53 token/s 明显更高）。

读基准数字时要注意「对比的公平性」：`frequency` 与 `uniform` 的差距，本质是「用统计信息」与「不用统计信息」的差距——前者「开卷」，后者「盲选」。**任何「开卷优于盲选」的结果都不该令人惊讶，惊讶的应是差距的大小**。差距大，说明幂律强、统计信息值钱；差距小，说明专家分布接近均匀、统计没多少可榨的价值。所以这组基准的真实启示是：**在 DeepSeek-V3 这类强幂律模型上，统计信息非常值钱**——这正是「频率感知」能存在的土壤。<span class="marginnote">注意这里「GPU 专家占比 10%」指 10% 的路由专家放 GPU。因为幂律，这 10% 覆盖的激活远高于 10%——这正是第 1 篇覆盖率公式 $C(M)$ 的实战验证。</span>

## 3 GPU Expert Mask 为什么是「掩码」而非「列表」

用位图表达「谁在 GPU」，有三个工程上的理由：

**理由一：查得快**。路由每 token 得出一个专家 ID，判断它在哪侧只需一次位测试 `mask[e]`，O(1)，零分支预测压力。

再补一个直观例子：61 层 × 256 专家 = 15616 个专家，掩码就是一张 15616 bit ≈ 2KB 的位图。一次掩码查询（取第 $e$ bit）在现代 CPU/GPU 上只需几个时钟周期——**整个放置表才 2KB，却能描述全部一万五千多个专家的归属**。这个「小结构、大表达力」的特性，是掩码能同时服务「快查询」与「快更新」的根本原因。<span class="marginnote">在 61 层 × 256 专家 = 上万专家、每 token 都要查的规模下，「位图 + 一次与运算」比「哈希集合」更省、更可预测。这是低延迟路径上的典型工程选择。</span>

**理由二：与 SGLang 对接自然**。官方 SGLang 集成的 API 兼容层正是把 `num_gpu_experts` 翻译成 kt-kernel 的 `gpu_experts_mask`——掩码是两套系统交换「放置意图」的公共语言。

「公共语言」这个词值得展开：当上层框架（SGLang）只懂「放几个专家上 GPU」这种高层意图、下层内核（kt-kernel）只认「位图掩码」这种底层表达时，中间需要一个**翻译层**。`num_gpu_experts → gpu_experts_mask` 就是这个翻译的契约。**任何「框架 + 内核」的分层系统，都需要这样一层「意图契约」**——它让上下两层可以独立演进，只要契约不变，任何一层重构都不影响对方。这是软件架构「依赖倒置」在推理引擎里的具体体现。

**理由三：支持动态更新**。掩码是可以整体重写的位图：当运行时统计显示某专家该「升入」GPU，只需翻转对应 bit，再配合权重迁移，即完成一次动态放置调整（见下篇《num_gpu_experts 与动态专家更新》）。

把三个理由连起来看，掩码的本质就清晰了：**它把「放置决策」压成一个「可查询、可更新、可传输」的紧凑数据结构**——查询快（位测试）、更新快（翻位）、传输快（一张位图随配置分发）。这就像一个「放置状态寄存器」：整个系统的放置意图，全部浓缩在这一个数据结构里。任何想读放置、改放置、传放置的组件，都只需面对这一张位图——接口极简，耦合极低。

## 4 公式解析：掩码覆盖率的代价模型

放置策略的收益可以量化。设 GPU 专家掩码把 $M$ 个专家放上 GPU，其**覆盖率**（GPU 侧命中的激活比例）为：

$$
C = \sum_{e} p_e \cdot \text{mask}[e]
$$

其中 $p_e$ 是专家 $e$ 的激活概率（来自统计）。逐项拆解：

- **第一步**：$p_e$ 是幂律分布——少数专家贡献大头。
- **第二步**：`frequency` 策略选择「$p_e$ 最大」的 $M$ 个专家置 1，等于在给定 $\sum_e \text{mask}[e] = M$ 的约束下**最大化 $C$**——这是一个最优子集选择，贪心（按 $p_e$ 排序取 top-$M$）即是最优。
- **第三步**：`uniform` 不依赖 $p_e$，可能把名额分给低 $p_e$ 专家，覆盖率 $C$ 偏低——这是它的性能代价。

**一句话**：frequency 策略 = 「在显存预算约束下，用统计分布最大化 GPU 覆盖率」的贪心最优解。

这里的「贪心最优」值得稍微展开：覆盖率 $C$ 是各专家覆盖率的**线性加和**，而约束只是「最多选 $M$ 个」——线性目标 + 基数约束的最优解，恰好就是「按权重降序取前 $M$」。这就是贪心（排序取 top）等于全局最优的原因。**不是所有优化问题都能这么幸运**：一旦目标或约束变成非线性（比如要同时考虑专家间的相关性），贪心就不保证最优了。ktransformers 用频率排序恰好捡到了一个「可贪心且最优」的漂亮问题结构——这也是为什么它能用这么简单的策略拿到这么好的效果。<span class="marginnote">这也解释了为什么 `frequency` 需要统计文件而 `uniform` 不需要：<strong>优化目标（最大化覆盖率）需要输入（激活概率分布）</strong>。没有统计，就只能用「均匀」这种次优但稳健的启发式。</span>

## 5 辨析｜易错点：掩码 ≠ 路由结果

**辨析｜易错点：** 把 GPU Expert Mask 与「每 token 的路由选择」混为一谈。掩码是**静态的设备归属表**（启动时确定，谁在 GPU 侧）；路由是**动态的专家选择**（每 token 不同，选哪几个专家）。两者在运行时会合：路由先选专家，再查掩码判断「这个被选中的专家在哪台设备上算」。<span class="marginnote">打个比方：掩码是「每个科室在哪个院区」的固定排布；路由是「这个病人去哪个科室」的实时分诊。分诊结果 + 科室排布，才最终决定病人去哪栋楼。</span>

若再用「比喻的比喻」收束：**掩码是「地图」，路由是「导航」**——地图告诉你每个科室在哪，导航根据当前位置（token）决定去哪个科室，两者配合才完成一次「就诊」（前向）。地图过时了要重绘，导航每单都要算——这正是「静态掩码 + 动态路由」的全部含义。

另一个易错点：**掩码覆盖的激活比例不等于「GPU 承载的计算比例」**——GPU 还要算 Attention 与共享专家这些稠密算子。掩码只管「路由专家」的归属，不代表整层计算都在 GPU。

第三个易错点：把「掩码里的 1」误解为「这个专家永久在 GPU」。掩码表达的是「**当前放置**」，它可以在动态更新时被整体重写——一个此刻为 1 的专家，可能在下一次重排后变成 0（降级回 CPU）。**掩码是「快照」，不是「承诺」**。这一区分对理解「动态专家更新」至关重要：系统不是「焊死」一批专家在 GPU，而是「持续把当前最热的换上去」。

## 6 实践要点：怎么拿到一份好统计

频率感知放置的成败，很大程度取决于那份「激活统计」的质量。三个实践要点：

**要点一：数据要有代表性**。统计用的 prompt 集合要贴近真实负载——做代码补全就用代码语料、做客服就用对话语料。用「中文闲聊」统计出来的热专家，在「英文代码」负载下必然错位。

**要点二：统计样本要足够多**。专家激活是稀疏事件，样本太少时频率估计噪声大。官方教程的 `.pt` 统计文件通常来自上万条 prompt 的前向——**样本量不足时，宁可用 `uniform` 兜底**，也别让噪声统计误导放置。

**要点三：统计会过期**。负载漂移时，旧统计的放置会逐渐失配——此时开启「动态专家更新」（第 2 篇）让它运行时自纠，比重新离线统计更省事。

一句话总结：**统计质量 = 数据代表性 × 样本量 ÷ 时效衰减**。这份「经验式」的判断，正是「频率感知」从论文走向工程实践时最需要补的一课。

## 7 小结

把本篇压缩成一句带走：**先统计谁热，再用一张位图把「热专家在 GPU」固化下来——统计定人选，掩码管表达，贪心选 top 就是最优**。

最后补一个「反向验证」的方法：部署后对比「掩码覆盖的激活比例」与「理论覆盖率 $C(M)$」——若实测远低于理论，说明统计与真实负载失配，该更新统计或开启动态更新了。**理论曲线是体检表，实测值是体检结果，对不上就该就医**。

- 频率感知放置 = **离线统计激活频率 → 在线把最热 $M$
