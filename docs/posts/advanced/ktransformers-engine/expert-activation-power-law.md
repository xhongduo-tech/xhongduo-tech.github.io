## 为什么关心「谁被激活得多」

上一篇算出 DeepSeek-V3 的平均激活率约 5.5%，但「平均」掩盖了最大的机会。试想：如果 256 个路由专家被命中的次数**一样多**，那么「把一部分专家放 GPU、另一部分放 CPU」的异构方案就毫无优势——因为 CPU 那头的专家一样被频繁调用，慢速的 CPU 会成为铁定瓶颈。ktransformers 能成立，恰恰因为现实是另一番景象：**专家激活服从幂律分布，少数的热专家包揽了绝大多数请求。**

这一篇与上一篇的关系可以这样理解：上一篇给了「稀疏性」的**数量**（37B / 671B），这一篇要给稀疏性的**结构**（谁被频繁用到、谁被冷落）。数量决定「机会有多大」，结构决定「机会怎么抓」——只知总量而不知结构，就无法回答「哪些权重该放哪」这个核心问题。可以说，**幂律分布是「频率感知放置」成立的充分条件**：没有它，任何放置策略都会退化为「均匀随机」，异构也就失去了意义。<span class="marginnote">这一观察是 ktransformers 论文的核心动机之一，也是「频率感知放置」策略（见第2篇）的理论基础。<strong>没有幂律，就没有异构。</strong></span>本节我们把这条分布讲透，并量化它对内存布局的意义。

## 1 幂律分布：二八法则的数学形状

**幂律分布（power-law distribution）**描述的是「少数个体占据多数份额」的现象。它的概率密度长这样：

$$
p(x) \propto x^{-\alpha}, \qquad \alpha > 0
$$

意思是：某个量取值 $x$ 的概率，与 $x$ 的负幂次成正比。$x$ 越大，出现的概率越低，而且是**按幂次急剧走低**——不是线性下降，而是「头部极陡、尾巴极长」。<span class="marginnote">语言里的词频（Zipf 定律）、网页的访问量、城市人口、地震震级……都是幂律的经典例子。<strong>大模型专家激活，是这条定律在系统里的又一次现身。</strong></span>

把幂律套到专家上：少数「热专家」承担了绝大部分 token 的路由，而大量「冷专家」长时间无人问津。论文报告，DeepSeek-V3 路由专家的激活频率差异悬殊——**最热的少数专家贡献了不成比例的高占比激活**，而大量专家在很长窗口内几乎不被触发。

理解幂律，必须摆脱「平均思维」。平均激活率 5.5% 会让人以为「每个专家都被差不多地使用」——但幂律恰恰是「平均」的致命敌人：平均数被少数热专家拉高，掩盖了「大量专家几乎从不被激活」的真相。**在长尾分布里，平均数是没有代表性的统计量**，中位数与「头部占比」才是。这一课在推荐系统（少数热商品占据多数销量）、网络科学（少数枢纽节点连接多数边）里反复上演——幂律是自然界与人工系统共同的「不平等法则」。

为什么「热专家」会形成？这与训练数据的长尾分布互为因果：训练语料里，常见句式与高频词出现的次数远高于冷门知识，路由网络在梯度压力下逐渐学会「把高频任务指向少数专家」——这些专家被反复训练、被反复激活，形成正反馈。**热专家不是天生的，是数据分布「训练」出来的**——这也解释了为什么不同语料上训练的模型，热专家集合不同。

## 2 热专家与冷专家的二分

**热专家（hot experts）**：激活频率高，几乎每个 batch 都会命中。它们承载的是「通用高频能力」——比如语言建模里反复出现的基础语法、常见常识、通用推理模式。

为什么会形成「热专家」？这与训练数据的长尾分布互为因果：训练语料里，常见句式、常用词搭配出现的次数远高于冷门知识，于是路由网络在梯度压力下逐渐学会「把高频任务指向少数专家」——这些专家被反复训练、被反复激活，形成正反馈。**热专家不是天生的，是数据分布「训练」出来的**——这也解释了为什么不同语料上训练的模型，热专家集合不同。

**冷专家（cold experts）**：激活频率极低，只在碰到特定领域、特定格式、罕见知识点时被触发。它们权重巨大却利用率低，是整个模型里「性价比最低」的常住人口。<span class="marginnote">热专家是「大众书」，借阅率高，值得放在最贵的书架上（GPU 显存）以最快速度取用。</span>

**冷专家（cold experts）**：激活频率极低，只在碰到特定领域、特定格式、罕见知识点时被触发。它们权重巨大却利用率低，是整个模型里「性价比最低」的常住人口。<span class="marginnote">冷专家是「学术冷门书」，借阅率低，完全可以放到远一点的仓库（CPU 内存）——反正取用频率低，多等一会儿也没人察觉。</span>

这一「热/冷」二分不是人为约定，而是从激活统计里自然涌现的。ktransformers 的**频率感知专家放置**（frequency-aware expert placement）正是据此决策：把 top-k 最热的专家留在 GPU，其余全部推到 CPU。

「热/冷」的边界怎么定？实践中不是按绝对频次，而是按**排名**——先对所有专家按激活频次降序排列，取前 $k$ 名为「热」。这个 $k$ 由显存预算反推：显存能装下多少专家，就取前多少名。**边界是资源约束的自然结果**，而不是先验设定——预算越紧，边界越靠前，「热」的门槛越高。

热专家还有个容易忽略的性质：它们往往在**多数层**都热，而非只在一两层热。这意味着「热/冷」具有跨层一致性——某一层的前几名热专家，大概率也是其它层的前几名。这种跨层一致性，让「全局选 top-k」的简化放置策略行之有效：不需要逐层单独统计，全局频率排序就足够接近最优。

## 3 幂律如何决定「放几个专家上 GPU」

假设 GPU 显存只放得下 $M$ 个专家的权重，该选哪 $M$ 个？直觉答案：选被激活次数最多的那 $M$ 个。设全部专家按激活频率降序排列，前 $M$ 个热专家累计承担的激活比例为：

$$
C(M) = \frac{\sum_{i=1}^{M} f_i}{\sum_{i=1}^{N} f_i}
$$

其中 $f_i$ 是第 $i$ 热专家的激活次数，$N=256$ 是路由专家总数。**当幂律很强时，很小的 $M$ 就能让 $C(M)$ 逼近 1**——这正是「只放 10% 专家上 GPU 就能覆盖 90%+ 的请求」的数学来源。

注意 $C(M)$ 里用的是「激活次数占比」，而不是「计算时间占比」——两者还有一层差异：被命中的专家若是热专家（在 GPU 上），计算快；若是冷专家（在 CPU 上），计算慢。所以「GPU 覆盖率 90%」并不意味着「90% 的计算都在 GPU」，实际收益还要叠加上「冷专家多算一次更慢」的代价。**覆盖率是优化放置的近似目标，真实性能还要考虑设备速度差**——这正是下一篇《算术强度与 Roofline》要补上的维度。<span class="marginnote">ktransformers 的 `--kt-gpu-experts-ratio 0.1` 参数（把 10% 的专家放上 GPU）之所以性能损失可控，正是因为幂律让这 10% 覆盖了绝大多数激活。</span>

## 4 公式解析：Zipf 视角下的激活覆盖

用 Zipf 定律做一次具体计算，能直观看到「放多少专家上 GPU」与「覆盖多少激活」的关系。Zipf 认为第 $i$ 热的个体的频次 $f_i \propto 1/i$，即 $f_i = C / i$。代入覆盖率公式：

**第一步，归一化**：总频次 $\sum_{i=1}^{N} 1/i = H_N$（第 $N$ 个调和数），所以 $C = 1 / H_N$。
**第二步，求前 $M$ 的占比**：$C(M) = \frac{\sum_{i=1}^{M} 1/i}{H_N} \approx \frac{\ln M + \gamma}{\ln N + \gamma}$（$\gamma$ 是欧拉-马歇罗尼常数）。
- **第三步，代数字**：取 $N=256$，$M=32$，则 $C(32) \approx \frac{\ln 32}{\ln 256} = \frac{5}{8} = 62.5\%$；$M=64$ 时 $C(64) \approx \frac{6}{8} = 75\%$。

也就是说，**在理想 Zipf 分布下，把 1/8 的专家（32 个）放上 GPU，就能命中约 62% 的激活**。真实模型的分布比 Zipf 更极端（头部更集中），所以 ktransformers 实测中更低比例的 GPU 专家即可覆盖大部分激活。

这张「覆盖率曲线」的形状值得再体会一下：$C(M)$ 随 $M$ 的增长**先快后慢**——从 0 到 32 个专家，覆盖率冲到 62%；再加 32 个（到 64），只增加 13 个百分点。这意味着「GPU 专家预算」的边际收益递减得非常快。对部署者来说，这给出一个反直觉的结论：**把 GPU 专家数从 8% 提到 20%，性能提升远没有想象中大**；而省下来的显存若让给 KV Cache，收益可能更实在。调参的智慧，就在于看清这条「边际收益曲线」的拐点。<span class="marginnote">$\ln 256 = 8\ln 2$、$\ln 32 = 5\ln 2$，所以比值恰好是 5/8。真实 DeepSeek-V3 的分布曲线比这条更陡，这也是为什么「频率」策略在官方基准里通常优于「均匀」策略。</span>

## 5 辨析｜易错点：激活频率 ≠ 参数重要性

一个危险直觉是「冷专家没用，可以扔掉」。这不对。

**辨析｜易错点：** 冷专家只是**很少被激活**，不是**不重要**。那些处理罕见格式、专业术语、长尾知识的专家，恰恰是模型能力多样性的来源。删掉冷专家，模型在长尾任务上会明显退化。<span class="marginnote">正确姿势不是删，而是「降级存放」：留在系统里、放到慢速设备上。ktransformers 卸载的是位置，不是权重。这与量化里「重要权重高精度、次要权重低精度」的取舍哲学同源。</span>

另一个易错点：把「热专家」与「共享专家」混为一谈。共享专家是**每个 token 无条件计算**的稠密部分，它不属于路由分布；热专家是路由分布里被选中的高频个体。两者都值得放 GPU，但原因不同——一个因为「必算」，一个因为「常算」。

把「降级存放」进一步外推到整个课程体系：操作系统把不活跃的进程换出到磁盘、数据库把冷数据归档到慢速存储、缓存系统用 LRU 淘汰冷 key——**「热进快层、冷出慢层」是一切存储系统的共同语法**。ktransformers 只是把这条语法套用到了「MoE 专家」这个新对象上。看懂这一层，你就从「记住 ktransformers 的某个机制」升级为「掌握一种跨领域的系统设计模式」——这正是本专题放在第四级高阶位置的原因：它不只在讲一个引擎，更在示范「用存储层次思维解决计算问题」。

## 6 从理论到实测：Zipf 与真实分布的距离

前面用 Zipf 做了理想化计算，真实模型的激活分布与 Zipf 有哪些出入？用一张对照表说清：

| 维度 | 理想 Zipf | 真实 DeepSeek-V3 专家激活 |
| --- | --- | --- |
| 头部集中度 | 前 32 个覆盖约 62% | 往往更高（头部更陡） |
| 尾部形状 | 严格按 $1/i$ 衰减 | 尾部有「平台期」，极少专家近乎从不激活 |
| 随时间 | 静态不变 | 随语料/任务漂移 |
| 可预测性 | 完美 | 需统计估计，有噪声 |

三个「现实 vs 理想」的偏差，恰好解释了 ktransformers 的三个设计：

- **头部更陡** → 放更少专家上 GPU 就能覆盖大量激活，「低 GPU 专家占比可行」更有底气。
- **尾部有平台** → 有些专家几乎永不激活，把它们留在 CPU 几乎零代价。
- **分布漂移** → 静态放置会过时，所以需要「动态专家更新」（见第 2 篇）。

**Zipf 不是真相，而是「理解真相的梯子」**——先借它建立直觉，再用实测统计修正。这也正是「频率感知放置」为什么要求一份真实的激活统计文件：理论的分布再美，也不如实测数据可靠。

## 7 小结

- 专家激活服从**幂律分布**：少数热专家承担多数激活，大量冷专家只在长尾触发。
- **热专家**频次高、值得放 GPU；**冷专家**频次低、适合降级到 CPU/DRAM。
- 覆盖率公式 $C(M)$ 说明：幂律越强，**越少的 GPU 专家就能覆盖越高的激活比例**。
- Zipf 模型下 256 选 32 即可覆盖约 62% 激活；真实分布更陡，收益更大。
- **冷专家 ≠ 无用**：是「降级存放」而非「删除」，这是异构卸载与权重量化的共同哲学。

在下一节，我们将回答一个更基本的问题：凭什么「放到 CPU 上算」还能跟上趟？这需要引入**算术强度与 Roofline 模型**——计算/访存比的度量衡。

先记住本篇一句话：**幂律给了异构「为什么可行」，下一节将给出「凭什么能算得动」——前者管放置，后者管性能**。

**一个容易忽略的推论**：幂律不仅决定了「哪些专家放 GPU」，还决定了「放多少专家进 GPU」的收益递减曲线——专家放得越多，新增的每个专家覆盖的激活增量越小（因为越往后越冷）。这意味着 GPU 专家占比不是越多越好，而是存在一个「收益拐点」。这个拐点在哪，正由本篇的 $C(M)$
