## 为什么把「分工」讲成一篇架构课

第 1 篇我们用六篇篇幅论证了一个方向：MoE 推理该「GPU 算稠密、CPU 算稀疏」。但方向正确，不等于机器会自己动起来。真正难的是**工程**——一次 token 的前向传播要穿过 61 层 Transformer，每一层都同时涉及 GPU 侧的 Attention 与 CPU 侧的专家 FFN，两者如何编排、如何接力、如何不互相等死？

先给一个「一句话总览」，让后面每个细节都有坐标：**ktransformers = 一台「分层计算的系统」，把一次前向切成 GPU 与 CPU 两条流水线，用异步队列缝合，用四层子系统支撑**。下面三节分别展开「分工图景」「四件套」「设备足迹」，最后用辨析收束。读完这一篇，你应该能向别人画着图解释「为什么 24GB 显存能跑 671B」——而不是只记得几个名词。<span class="marginnote">这一节进入 ktransformers 论文第 3 节：<strong>总体架构</strong>。它是整个专题的分水岭——前面的「为什么」在这里变成「怎么做」，后面的内核、缓存、微调全是这座架构的零件。</span>先把「分工图景」立起来，再逐个拆解它的四个子系统。

## 1 分工图景：一次前向的「接力赛」

下图是 ktransformers 对一次 token 前向传播的分工抽象：

![ktransformers CPU-GPU 异构推理总体架构](/images/ktransformers-engine/hybrid-architecture-overview-1.svg)

每个 Transformer 块内部，计算被拆成两条流水线：

**GPU 流水线**：处理**稠密部分**——MLA Attention（每 token 必算）、共享专家、路由网络，以及被留在显存里的**热专家**。它们算术强度高或频次高，是 1 TB/s 显存带宽最值得服务的地方。

**CPU 流水线**：处理**稀疏部分**——被路由选中的**冷专家**。它们的权重以 INT4/INT8 量化形式常驻 DDR5，被命中时在 **CPU 侧就地完成矩阵乘**，结果经异步队列送回 GPU。

两条流水线的「负载比例」随阶段变化：prefill 时 token 多、batch 大，GPU 侧稠密计算占绝对主导，CPU 专家计算是「配角」；decode 时逐 token 生成、batch 小，GPU 稠密计算变轻，CPU 冷专家计算相对占比上升——**两阶段对 CPU/GPU 的依赖结构不同**。这也是为什么 ktransformers 在 prefill 与 decode 会采用不同的调度偏好（见第 2 篇《算术强度感知的算子放置》）——「分工」不是一张静态蓝图，而是随运行阶段动态调节的比例。

两条流水线通过**异步任务队列**咬合：GPU 算完 Attention 后，把路由结果发给 CPU 侧，CPU 并行算被选中的冷专家；GPU 不必等 CPU 就能继续算下一层的共享专家。

这幅「接力赛」图景中，最容易被忽略的是**每个 Transformer 块内部的顺序**：先算 Attention（GPU）→ 算路由（GPU）→ 派发冷专家任务（GPU→CPU）→ 算共享专家与热专家（GPU，与 CPU 专家计算重叠）→ 汇总专家输出（GPU）→ 输出投影（GPU）。一次前向里，CPU 计算被「塞进」GPU 的两次稠密计算之间——**CPU 不是在「旁边」跑，而是在 GPU 的时间间隙里跑**。理解这个「间隙填充」的时序，是理解整个架构如何「无感加速」的关键。<span class="marginnote">关键洞察：<strong>CPU 与 GPU 是「同时干活」而不是「接力等活」</strong>。路由结果一到，CPU 专家计算与 GPU 下一层稠密计算就重叠起来——这是吞吐能上去的工程核心。</span>

## 2 架构四件套：调度、内核、缓存、注入

ktransformers 的总体架构可拆成四个协作子系统，后面四篇将逐一展开：

| 子系统 | 职责 | 对应章节 |
| --- | --- | --- |
| **算子放置与调度** | 决定每个算子放哪个设备、CPU/GPU 任务如何编排 | §3–§4 |
| **GPU/CPU 内核** | 让「被选中设备」算得足够快（Marlin、llamafile、AMX） | §5 |
| **KV Cache 与缓存层次** | 管理显存/内存/磁盘三级缓存，支撑长上下文 | §6 |
| **注入框架** | 声明式替换模型算子，零改动接入新模型 | 官方文档 |

为什么是「这四件套」而不是别的？因为一次推理请求要依次回答四个问题：**模型能不能加载（注入）→ 每个算子该在哪算（调度）→ 选中的设备算得快不快（内核）→ 长对话装不装得下（缓存）**。四个问题恰好覆盖「加载、放置、计算、存储」四个环节——少任何一个，推理链条都会断。这种「按问题域切分子系统」的思路，是架构设计最可靠的方法：先枚举系统必须回答的问题，再让每个子系统对应一个问题。

这套分层是典型的**系统设计**思路：调度层回答「哪台设备」，内核层回答「怎么算快」，缓存层回答「长对话怎么装」，注入层回答「怎么让框架通用」。每层的优化都服务于同一目标——**让 24GB 显存 + 大内存跑满血 MoE**。

四层之间还有清晰的依赖次序：**注入层是地基**（没有它，模型加载不起来），**调度层是骨架**（决定算子在哪个设备），**内核层是肌肉**（决定算得多快），**缓存层是记忆**（决定能撑多长上下文）。读论文时按「地基→骨架→肌肉→记忆」的顺序理解，比逐节孤立记忆更能把握整体。这个「依赖次序」思维，也适用于任何分层系统的学习——先问「谁依赖谁」，再问「每层干什么」。

## 3 公式解析：一条前向的「设备足迹」

把一次前向的权重访问用式子写出来，能定量看见分工。设某 token 在某层的路由选中了专家集合 $E_t$（1 个路由专家），则该层被访问的权重为：

先说明记号：这里「$W_{\text{touch}}$」指「这一层被这次前向实际读到的权重」，不是整层全部权重——MoE 的稀疏性正在于此：整层有 256 个专家，但 $W_{\text{touch}}$ 只触及其中 2 个（1 共享 + 1 路由）。下面的每一项拆解，都在回答「这一部分权重为什么该在这台设备」。

$$
W_{\text{touch}} = \underbrace{W_{\text{attn}}}_{\text{GPU}} \;+\; \underbrace{W_{\text{shared}}}_{\text{GPU}} \;+\; \underbrace{W_{\text{hot}}}_{\text{GPU}} \;+\; \underbrace{W_{e^*}}_{\text{CPU}},\quad e^* \in E_t
$$

逐项拆解：

- **第一步**：$W_{\text{attn}}$ 与 $W_{\text{shared}}$ 是稠密权重，每 token 必读，且高算术强度 → 放 GPU。
- **第二步**：$W_{\text{hot}}$ 是留在 GPU 的热专家，频次高 → 放 GPU 以免 CPU 带宽拖累。
- **第三步**：$W_{e^*}$ 是被选中的那个路由专家。若它是冷专家，则权重在 CPU 内存、计算在 CPU 侧完成；GPU 只收结果。

对比「全量卸载」的足迹——那里**每一项**都要经 PCIe；而 ktransformers 里只有「$W_{e^*}$ 是冷专家时的一次 CPU 计算」发生在 GPU 外，且**不走 PCIe**（就地算完送结果）。这就是架构的收益来源：**把最重的、最高频的、最频繁访问的权重，全部压在 GPU 侧的高带宽存储里**。

值得把「$W_{e^*}$ 是冷专家时的一次 CPU 计算」再放大看：**它不只省了 PCIe 搬运，还省了「GPU 显存放不下」这个死结**。冷专家权重有几百 GB，GPU 装不下；把它留在 CPU 内存就地算，等于「用 CPU 的算力 + DRAM 的容量」承接了「GPU 装不下的负载」——**异构的收益不只是「快」，更是「装得下」**。全量卸载也能「装得下」（都放内存），但它是「所有权重都从内存读」；ktransformers 是「只有冷专家从内存读」——两者的差别，就是「均匀地慢」与「差异化地快」的差别。

## 3.5 公式解析再进一步：为什么「CPU 结果回传」很便宜

有人会追问：CPU 就地算冷专家，结果不还是要回传 GPU 吗？回传不也占 PCIe？**是的，但回传的「体积」与「搬权重」完全不同量级**：

$$
\text{回传体积} = |E_t| \times d_{\text{hidden}} \times 2 \text{ B}
$$

逐项拆解：

- **第一步**：$|E_t|$ 是每层被选中的冷专家数（通常 1 个），$d_{\text{hidden}}$ 是隐藏维度（数千）。
- **第二步**：单层回传约几千 × 几千 × 2 B ≈ **几 MB**——与「搬权重」的几十 GB 相差四个数量级。
- **第三步**：61 层累计不过几百 MB，分摊到每 token 解码里微乎其微——**「只传结果」把 PCIe 的负担从 GB 级降到 MB 级**。

这个「体积账」是架构「就地计算」成立的关键：**就地算的代价是「回传小结果」，不就地算的代价是「搬运大权重」——两者差四个数量级**。所以「CPU 就地算冷专家」不是「多此一举」，而是「把最大的搬运省掉、只留下最小的回传」。理解了这笔账，你就理解为什么架构图里 CPU 专家的输出要「异步回传」而不是「先搬权重去 GPU 算」——**架构的每一个选择，都在为「少搬大的」服务**。<span class="marginnote">「搬大的」与「传小的」是异构架构的全部经济学：<strong>权重是「大的」，必须少搬；结果是「小的」，可以随便传</strong>。谁把这两件事分清，谁就掌握了异构推理的命门。</span>

## 4 架构四件套如何协同：一次前向的完整流程

把四件套串成一次真实的「decode 循环」，你会看到它们如何接力：

1. **注入层**（地基）：加载时用 YAML 规则把 DeepSeek-V3 的算子替换成 ktransformers 内核，权重按规则放进 GPU/CPU。
2. **调度层**（骨架）：每 token 先算路由，对照放置表把冷专家任务投给 CPU 队列、热专家留给 GPU。
3. **内核层**（肌肉）：GPU 用 CUDA Graph 跑 Attention + 热专家，CPU 线程池并行算冷专家，结果写 pinned 缓冲。
4. **缓存层**（记忆）：KV Cache 按 GPU/CPU/Disk 三层放置，支撑长上下文与多轮对话。

四步依次发生、又部分重叠（CPU 专家计算与 GPU 下一层稠密计算并行），构成一次完整的异构前向。**「地基 → 骨架 → 肌肉 → 记忆」在运行时是一条流水线，而不是四个孤立的模块**——这也解释了为什么「架构四件套」必须协同设计：调度层假设内核层够快、内核层假设缓存层装得下、注入层假设所有层都有接口对接。**「分层」让每层可独立演进，「流水线」让它们必须协同运行**——理解这对「分层 vs 流水」的矛盾统一，是读系统架构的要领。<span class="marginnote">读任何分层系统，都别只看「每层干什么」，更要看「层与层怎么交接」——<strong>接口契约（权重格式、缓冲地址、任务格式）是分层系统的真正骨架</strong>。ktransformers 的四件套能协同，靠的正是这些契约稳定。</span>

## 5 设备足迹的扩展：prefill 与 decode 的不同编排

第 1 节提过「负载比例随阶段变化」，这里展开成一张对照表：

| 阶段 | GPU 侧主角 | CPU 侧角色 | 调度偏好 |
| --- | --- | --- | --- |
| Prefill | 大 batch 稠密 GEMM（算力吃满） | 冷专家批量计算（配合） | GPU 算力优先 |
| Decode | 小 batch 稠密 + 热专家 | 冷专家单 token 计算（占比上升） | 异步流水优先 |

「两阶段对 CPU/GPU 的依赖结构不同」这句话，在架构层面意味着：**ktransformers 的架构不是「一张静态蓝图」，而是「一套随阶段调节的编排」**——prefill 时 GPU 是绝对主力，decode 时 CPU 的参与度显著上升。这个「动态性」贯穿架构的每一层：调度偏好、内核路径、甚至 KV 放置都随阶段变化。**架构设计要能「兼容两阶段的不同需求」，而非「为某一阶段做最优」**——这是它比「为单阶段优化」的方案复杂、也更健壮的原因。

## 6 小结

把总体架构收成「一句话总览 + 四件套 + 两条流水线」：**ktransformers = 一台分层计算的系统，把一次前向切成 GPU 与 CPU 两条异步流水线，用四层子系统（注入、调度、内核、缓存）支撑**。

- **分工图景**：GPU 算稠密（Attention、共享专家、热专家），CPU 算稀疏（冷专家），异步队列缝合，层边界软同步。
- **架构四件套**：注入（地基）、调度（骨架）、内核（肌肉）、缓存（记忆）——按依赖次序理解。
- **设备足迹**：$W_{\text{touch}} = W_{\text{attn}} + W_{\text{shared}} + W_{\text{hot}} + W_{e^*}$，只有冷专家走 CPU，且就地算、不走 PCIe。
- **收益来源**：把最重、最高频、最频繁访问的权重全部压在 GPU 侧高带宽存储，稀疏冷专家留给 CPU/DRAM。
- **协同是流水线**：四件套在运行时是一条接力流水线，「分层让每层可演进、流水让它们必须协同」。
- **两阶段动态编排**：prefill 与 decode 对 CPU/GPU 的依赖结构不同，架构须兼容两阶段需求。
