## 为什么一个参数值得单独写一篇

上一节的掩码回答了「谁在 GPU」，这一节回答「**多少个**在 GPU」以及「**运行到一半能不能改**」。前者是显存预算的配置入口 `--kt-num-gpu-experts`，后者是 ktransformers 的一项硬核能力——**动态专家更新（dynamic expert update）**。<span class="marginnote">一个参数看起来琐碎，但它背后是「显存预算是静态的还是动态的」这一设计哲学。ktransformers 选择：<strong>预算可调，分配可动</strong>。</span>把参数语义、换算关系、动态更新的触发机制讲透，你就能自己给任何模型调出一份合适的放置配置。

## 1 `num_gpu_experts` 的精确语义

先破除一个常见误会。官方教程早期把 `--kt-num-gpu-experts` 描述为「每层放 GPU 的专家数」，但根据实现 `generate_gpu_experts_masks`，它的真实语义是：

把「三个容易混淆的量」摆在一起对照，语义就再也混不了：

| 量 | 含义 | 与总体的关系 |
| --- | --- | --- |
| 每层路由专家数 $N$ | 一层里有几个专家（DeepSeek-V3 为 256） | 与层数无关，模型结构决定 |
| MoE 层数 $L$ | 全模型有几层 MoE（DeepSeek-V3 为 61） | 与单层无关，模型结构决定 |
| `--kt-num-gpu-experts` $M$ | 全部分数层中放进 GPU 的专家总数 | $M \le L \times N$，你的配置决定 |

**易混淆点**：初学者常把「每层 256」当成「全模型 256」——实际上全模型有 $61 \times 256 = 15616$ 个路由专家。`--kt-num-gpu-experts` 管的是后者（总数），不是前者（每层）。这正是官方教程早期描述「有歧义」、后续用 PR 澄清的原因。

**`--kt-num-gpu-experts` = 全部分数层中，放进 GPU 的专家总数**（跨所有 MoE 层的总和）。

也就是说，设 MoE 层数为 $L$、每层路由专家数为 $N$（DeepSeek-V3 为 61 层、每层 256），若设置 $M$ 个专家上 GPU，则**平均每层**有 $M/L$ 个专家驻留 GPU，其余 $N - M/L$ 个在 CPU。

**换算关系**：官方还提供 `--kt-gpu-experts-ratio`（0.0–1.0）覆盖前者——`0.1` 表示把全部专家（$L \times N$ 个）的 10% 放上 GPU。二者是同一预算的两种表达：

为什么要有两个参数表达同一个意思？因为使用场景不同：`--kt-num-gpu-experts` 适合「我已经想好要放多少专家」的精确控制；`--kt-gpu-experts-ratio` 适合「我大概想放 10%」的比例思维，也便于在不同模型间平移（不同模型的专家总数不同，绝对数没有可比性，比例才是可迁移的）。**工程上的「双参数冗余」，往往是为了照顾两种不同的心智模型**——这本身就是一份关于「配置设计」的教材。

$$
\text{ratio} = \frac{\text{num-gpu-experts}}{L \times N}
$$

<span class="marginnote">对 DeepSeek-V3，$L \times N = 61 \times 256 = 15616$。设 `--kt-gpu-experts-ratio 0.1`，即约 1562 个专家（每层约 25–26 个）进 GPU。因为幂律，这 10% 通常覆盖 60%+ 的激活——这就是「预算不多，收益不少」的由来。</span>

## 2 预算怎么花：KV Cache 与专家的拉锯战

显存预算的分配是一场零和博弈：**放专家的空间与留 KV Cache 的空间互相挤占**。官方文档对 Kimi-K2 部署明确建议：`--kt-num-gpu-experts` 应「根据可用显存与预期的 KV Cache 空间调整」。

**辨析｜易错点：** 不是「显存越多，专家放越多越好」。专家放多了，KV Cache 变小，能支持的并发与上下文就短；反之 KV Cache 管够，但 CPU 侧专家变多、解码变慢。

这条拉锯可以用一个生活化的类比记住：显存就像一间「同时放书架和货架」的库房。书架（专家）摆得多，能快取的「知识」就多，但留给货架（KV Cache）的空间就少，能同时服务的「顾客」（并发请求）与「接待量」（上下文）就缩水。**没有绝对正确的摆放，只有与「你的生意形态」匹配的摆放**——书店（短问答、高并发）多摆货架，档案馆（长文档、低并发）多摆书架。<span class="marginnote">这是一条真正的<strong>系统权衡曲线</strong>：横轴是 GPU 专家数，纵轴是「吞吐 vs 上下文长度」。调参的本质，是在这条曲线上选一个与你的工作负载匹配的点——短上下文高并发选多专家，长上下文少并发选多 KV Cache。</span>配套参数：`--chunked-prefill-size` 控制 prefill 的额外显存、`--max-total-tokens` 控制 KV Cache 上限。

还有一对容易漏掉的参数：`--max-running-requests` 与 `--max-total-tokens` 一起，共同决定「同时有多少请求在跑、每个请求能占多少上下文」——它们与 GPU 专家数共享同一块显存，是「拉锯战」的另外两个玩家。

## 3 动态专家更新：运行时重排

静态放置的问题：**离线统计用的数据，不一定代表真实负载**。真实流量可能让某个「冷专家」突然变热——比如某个 batch 密集出现某种语言或格式。动态专家更新正是为此设计：

**触发机制**：启用 `--kt-enable-dynamic-expert-update` 后，系统在 **prefill 阶段**持续统计专家激活。当累计 token 数超过阈值 `--kt-gpu-prefill-token-threshold`（例如 512），调度器就基于「最新统计」重算掩码，把新晋热专家**升入** GPU、把失宠专家**降级**回 CPU。

把动态更新的一次完整流程拆成五步，它就不再是黑盒：

1. **统计**：prefill 阶段累积每个专家的激活计数。
2. **判断**：累计 token 数达到阈值（如 512）？未达则继续统计。
3. **重排**：按最新计数重算「top-M 热专家」，生成新掩码。
4. **迁移**：把新晋热专家的权重拷入显存、失宠专家的权重拷回 DRAM。
5. **生效**：更新后的掩码用于后续所有路由查询，直到下一次触发。

第五步之后回到第一步，循环往复。**整个循环只在 prefill 阶段进行**，decode 阶段掩码保持稳定——这是延迟敏感路径的底线。<span class="marginnote">这是「掩码可整体重写」能力的兑现：<strong>重排只翻位图 + 迁移少量权重，不需要重启服务</strong>。比起「启动时定死」，它在负载漂移时能自适应地保住吞吐。</span>

**为什么在 prefill 阶段做**：prefill 计算密集、CPU/GPU 都有富余算力，此时迁移权重几乎不增加延迟；而 decode 是延迟敏感路径，任何权重搬移都会卡顿。

动态更新的执行细节也值得留意：它不只是「翻掩码」，还要**迁移权重**——把新晋热专家的量化权重从 CPU DRAM 拷到显存、把失宠专家的权重从显存拷回 DRAM。权重大小以 GB 计，迁移本身有成本；所以调度器会**批量迁移**（一次把多个专家的位次调整合并执行），并把迁移安排在 prefill 的「计算间隙」里，避免与活跃计算抢带宽。把「决策」与「执行」分开看，动态更新才真正可理解：决策是翻位图（快），执行是搬权重（慢），后者决定了更新的频率上限。

## 4 公式解析：动态更新的收益条件

动态更新到底何时值得？设静态放置的 GPU 覆盖率为 $C_0$，负载漂移后降为 $C_{\text{static}}$（因为真实热点变了），动态更新把它重新拉回 $C_{\text{dyn}} \approx C_0$。定义覆盖率损失：

$$
\Delta C = C_{\text{static}} - C_{\text{dyn}} = \sum_e p_e^{\text{new}} \big( \text{mask}^{\text{new}}[e] - \text{mask}^{\text{old}}[e] \big)
$$

逐项拆解：

- **第一步**：$p_e^{\text{new}}$ 是真实负载下的激活概率；`mask` 是新旧掩码。
- **第二步**：若负载稳定，新旧掩码几乎相同，$\Delta C \approx 0$，动态更新**无收益**——此时关掉它以省迁移开销。
- **第三步**：若负载漂移大，静态掩码错配，$\Delta C > 0$
