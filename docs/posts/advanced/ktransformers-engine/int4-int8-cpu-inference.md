## 为什么 CPU 端要「专门」讲量化推理

第 3 篇的归宿在这里：CPU 侧承载着几百 GB 的冷专家权重，这些权重以 **INT4/INT8** 量化形式常驻 DRAM。CPU 端推理的核心问题是：**如何把打包好的低比特权重，用 CPU 最快的指令（整数 SIMD）算成正确结果**。这涉及打包布局、整数 GEMM、反量化流水三层设计。

先说清「CPU 端量化推理」与「GPU 端量化推理」的分工边界：**同一份量化权重，GPU 侧用 Marlin 算热专家、CPU 侧用 llamafile/VNNI 算冷专家**——两条路径共享同一套量化格式，但各有各的内核。这也是 ktransformers「一份权重、两套内核」的设计延续：量化是「数据面的统一」，内核是「执行面的分化」。理解这个边界，你就能明白为什么 CPU 端的内核问题值得单独写一篇。<span class="marginnote">官方文档的 `fp8_kernel` 等内核文件就是这一层的实现。理解 CPU 端量化推理，你就掌握了「为什么 CPU 能扛 377GB 的权重还能出活」的完整答案。</span>

## 1 从量化到可算：三件准备工作

CPU 要算量化 GEMM，权重必须先被「摆好」：

**打包（packing）**：INT4 权重两个挤一个字节、8 个挤一个 `uint32`；INT8 每个权重一字节、8 个挤一个 64-bit 向量。打包让内存连续、访存高效，也是 SIMD 能一次性处理多个权重的前提。

打包的「连续性」价值可以量化：假设不打包、每个权重占一个字节的地址空间，那么读 8 个 INT4 权重要访问 8 个「稀疏」的字节地址；打包后 8 个权重挤进 4 个字节，一次 4 字节的突发就能取回 8 个权重——**访存效率翻倍**。对带宽受限的 CPU 侧，这个「打包红利」是实打实的吞吐来源。打包的本质，就是「把逻辑上相邻的数据，在物理上也摆相邻」——与第 3 篇的 tile 化布局是同一原则的又一次应用。<span class="marginnote">打包不只是省空间——它让「一次 SIMD 加载 = 8/16/32 个权重」，喂给 VNNI 这类整数指令正好。</span>

**缩放因子预计算**：per-group 的缩放 $s_g$ 与零点 $z_g$ 在启动时预取、按布局存放，避免热循环里查表。

「避免热循环里查表」是个容易被低估的优化：缩放因子如果存得零散，热循环每算一块就要做一次「取缩放」的内存访问，把「纯整数点积」的清爽破坏掉。ktransformers 的做法是启动时把缩放因子**按计算顺序重排**，让「该用哪块缩放」与「正在算哪块」对齐——热循环里缩放触手可及，无需额外寻址。**「把常量准备好、摆放对」是内核优化的前置工作**，它不改变算法，却决定热循环有多干净。

**指令集选择**：INT8 走 **AVX-VNNI**（`vpdpbusd` 一次 8×u8×i8→i32）；INT4 走解包后的整数路径或专门打包指令。CPU 能力决定路径，ktransformers 启动时检测。

## 1.5 为什么要「CPU 端单独一套」而非「直接复用 GPU 内核」

一个合理的疑问：GPU 有 Marlin，CPU 为什么不能直接用同一套？答案在「硬件差异」里：

**指令集不同**：GPU 用 Tensor Core 的整数矩阵指令，CPU 用 VNNI 的整数点积指令——两套指令集的操作数格式、累加方式、寄存器组织都不同，内核代码无法直接移植。

**访存模型不同**：GPU 的共享内存、warp 级 coalescing 与 CPU 的 cache-line、多线程分块是两套体系——「为 GPU 优化的布局」在 CPU 上可能恰好是「最差布局」。

**计算语义不同**：GPU 是「数千线程协作一块大矩阵」，CPU 是「几十线程各算各的分块」——并行的粒度与同步方式完全不同。

**「同一份权重、两套内核」正是 ktransformers 的设计选择**：量化格式统一（一份权重），执行内核分化（GPU/CPU 各一套）——**数据面统一、执行面分化**。这个模式我们在第 3 篇《GPU 端 Marlin》已经见过一次，这里再确认一遍：**「一份数据、两套实现」是异构系统里最省力的结构**，它让「权重只有一份」成为可能，而把「怎么算」留给各设备自由发挥。

## 2 整数 GEMM 的热循环：让 VNNI 吃饱

INT8 的 CPU GEMM 热循环是一个**纯整数矩阵乘**。对激活 $x$（INT8）与权重 $w$（INT8）：

$$
y = \sum_{k} x_k \cdot w_k \quad (\text{INT32 累加})
$$

**AVX-VNNI 一条指令** `vpdpbusd` 同时算 8 对 `u8×i8` 的乘积并累加到 i32 向量。指令宽度 + 累加器，让 CPU 在单位周期内完成 8 次乘加——这是「整数比浮点快」的核心：整数 SIMD 吞吐是同级浮点 SIMD 的数倍，且没有 FP 舍入路径的功耗。

「整数比浮点快」还有个容易忽略的细节：整数运算的**能效比**也更高——同样的晶体管面积，整数单元能塞进更多的运算器，且整数乘法没有浮点乘法的归一化/舍入逻辑，功耗更低。对长期满载运行的推理服务，能效意味着「同样的功耗预算下能跑更高的吞吐」。**低精度不只是「更快」，还是「更省」**——这一点在消费级（功耗墙）与数据中心（电费）两个场景里都很关键。

**INT4 的特殊性**：4-bit 没有原生 SIMD 指令，所以策略是**解包成 INT8 再喂 VNNI**——从 `uint32` 里拆出 8 个 4-bit 值，扩展成 8 个 INT8，再做整数乘加。解包在寄存器里完成、被软件流水藏住（类似 Marlin 的思路），热循环仍是高效的整数乘加。

「解包在寄存器里完成」是一个关键的设计选择：为什么不在内存里先解包成 INT8 再读？因为那样就破坏了打包布局的带宽红利——解包后的 INT8 权重体积是 INT4 的两倍，内存里要多读一倍的字节。**解包必须发生在「数据已被读入计算单元之后」**，让「打包的带宽红利」与「解包的格式转换」各司其职：前者在内存侧省字节，后者在寄存器侧花计算。这个「把转换放在正确的位置」的思维，是高性能计算里反复出现的设计判断。<span class="marginnote">INT4 的收益在于<strong>字节减半</strong>：同一带宽下，INT4 权重能比 INT8 多读一倍数据——对带宽受限的 CPU 侧，这是实打实的吞吐翻倍。代价是解包的开销与稍大的量化误差。</span>

## 3 反量化流水：把 FP 转换推迟到末尾

与 GPU 的 Marlin 完全同构，CPU 端也利用量化的线性性：

$$
y = s \cdot \Big( \sum_k x_k \cdot w_k^{\text{int}} \Big) - s \cdot z \cdot \sum_k x_k
$$

主循环只做**整数点积**（i32 累加器），循环结束后一次性转换：把 i32 结果转成浮点、乘缩放 $s$、减零点修正——反量化只发生在矩阵乘的外层，而不是每个元素。<span class="marginnote">这套「整数热循环 + 末尾反量化」的结构，从 GPU Marlin 到 CPU llamafile 完全一致。它是量化推理最核心的工程套路：<strong>把「量化带来的额外工作」全部推到矩阵乘的末尾</strong>，让热循环保持最简、最快。</span>

「从 GPU 到 CPU 完全一致」这句话值得展开：GPU 用 Tensor Core 的 INT8/INT4 整数路径、CPU 用 VNNI 的整数路径——**硬件不同，但「整数点积 + 末尾缩放」的数学结构完全相同**。这再次印证了一个重要事实：**量化的数学本质是「线性」，而「线性」是跨硬件的**——只要抓住这个数学本质，同一套优化思路就能在不同硬件上重复兑现。这也是为什么「先学原理、再学实现」比「背 API」有价值得多：原理跨硬件，API 只在单平台。

## 4 公式解析：INT4 与 INT8 的带宽吞吐对比

CPU 侧带宽受限，比较两种位宽的「每字节算力贡献」。设权重体积 $V_b = P \times b/8$，内存带宽 $BW$，则「扫一遍所有权重」的时间：

$$
t_b = \frac{V_b}{BW}
$$

INT8 与 INT4 对照：

- **第一步，INT8**：$t_8 = \frac{P \times 1}{BW}$，单位时间读到的权重数 = $BW$ 个/秒。
- **第二步，INT4**：$t_4 = \frac{P \times 0.5}{BW} = \frac{t_8}{2}$——扫一遍 INT4 权重只需 INT8 的一半时间。
- **第三步，换算成吞吐**：单位时间能扫过的权重数，INT4 是 INT8 的 2 倍——**对带宽受限的 CPU 侧，INT4 的吞吐红利是实打实的翻倍**。

把「吞吐翻倍」再往深里想一层：它意味着**在相同的带宽下，INT4 能撑起「更大的 batch」或「更长的上下文」**——因为每秒能读的权重更多。这正是「量化不只是精度工具、更是容量工具」的含义：**INT4 让你在同一台机器上「多装」或「多算」**。对消费级用户来说，INT4 往往不是「精度够不够」的问题，而是「能不能跑 671B」的问题——**它的第一价值是「把装不下变成装得下、把跑不动变成跑得动」**。

## 4.5 打包的更多层次：int4 的「块打包」与缩放因子

前面讲了「两个 4-bit 挤一个字节」，但 ktransformers 的 CPU 端打包其实更细——**它按「块（group）」组织，每 $G$ 个权重共享一个缩放因子**：

**块打包**：8 个 INT4 权重挤进一个 `uint32`（两个一字节、四个一 16-bit、八个一 32-bit），同时按固定块大小（如 32–128 个权重）给每组配一个 32-bit 的缩放因子。

块打包的收益要算两笔账：**① 内存连续性**——权重在内存里紧密连续，一次突发读取整块，带宽利用率高；**② 缩放粒度**——每块一个缩放，能刻画「局部剧烈变化」的权重分布（离群值只影响所在块，不污染整列）。**「块」既是访存单位，也是精度单位**——一个结构同时服务「带宽」与「精度」两个目标，这是块打包设计的巧妙之处。

「缩放粒度」这一点值得与 per-channel 对照：per-channel 是「每列一个缩放」，块打包是「每 $G$ 个一组」——**粒度更细时精度更好、但缩放因子占的存储更多**。ktransformers 在 CPU 端用块打包，正是看中了「细粒度缩放 + 连续访存」的双重收益。**「打包」与「缩放」不是两件事，而是一体的**：打包决定了「权重怎么存」，缩放决定了「存的时候带多少标定信息」——两者共同决定了「读回来的数据能不能直接被高效计算」。

## 5 辨析｜易错点：INT4 精度「够不够」是任务相关的

**辨析｜易错点：** 用「绝对精度」评判 INT4，会得出「INT4 一定比 INT8 差」的错误结论。真相是：**INT4 的精度损失高度依赖任务**——对代码生成、常见问答这类「容错高」的任务，INT4 与 INT8 的差距几乎不可感知；对数学推理、长文档理解这类「精度敏感」的任务，差距才显现。**「精度够不够」不是 INT4 的固有属性，而是「任务敏感度」的函数**。

所以工程上的正确姿势不是「一律用 INT4」或「一律用 INT8」，而是**「按任务与负载选择」**：日常问答用 INT4（省带宽、快），精度敏感场景切 INT8/BF16（保质量）。ktransformers 的「精度谱系」支持（第 3 篇《原生 BF16 与 FP8》）正是为这种「按需选择」准备的——**「可切换的精度」比「固定的最高精度」更实用**，因为它给了用户「质量 × 速度」的选择权。<span class="marginnote">这也呼应了「精度-字节谱系」的连续性：<strong>从 INT4 到 BF16，每一步都是「字节减半、质量略降」——没有绝对的对错，只有「在你的约束下最合适」</strong>。学会「按约束取点」，比记住「某精度最好」更有用。</span>

还有一个工程细节值得点出：**INT4 的「解包开销」在 batch 大时会摊薄**。解包（从 uint32 拆 4-bit）有固定成本，单 token 时占比高；batch 大时多个 token 共享解包好的权重，摊薄后 INT4 的带宽优势进一步放大——**「INT4 适合大 batch」是它的另一重性格**。这与前面「CPU 侧多 token 共享冷专家」的收益（SGLang 篇）是同一机制：**batch 越大，固定成本越被摊薄，量化红利越显**。

## 6 小结

把 CPU 端 INT4/INT8 推理收成「三件准备、一个热循环、一次末尾缩放、一对精度权衡」：**打包 + 缩放预计算 + 指令集选择**是前置，**整数点积热循环**是核心，**末尾反量化**是技巧，**INT4 vs INT8**是精度与带宽的权衡。

- **三件准备**：打包（内存连续、SIMD 友好）、缩放预计算（热循环干净）、指令集选择（VNNI/AMX）。
- **整数热循环**：`vpdpbusd` 一次 8×u8×i8→i32，INT4 解包后喂 VNNI。
- **末尾反量化**：整数点积后一次性乘缩放、减零点——与 GPU Marlin 完全同构。
- **INT4 的带宽红利**：字节减半 → 扫权重的吞吐翻倍 → 同一带宽下能装更多/算更多。
- **精度权衡是任务相关**：容错高的任务用 INT4，精度敏感的场景切 INT8/BF16——按需取点。
- **batch 摊薄解包**：大 batch 共享解包好的权重，INT4 的带宽优势进一步放大。
