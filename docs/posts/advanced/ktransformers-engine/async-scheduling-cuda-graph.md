## 为什么「异步」是异构推理的命门

第 2 篇的架构图上，GPU 与 CPU 是两条流水线。但若实现得粗糙——「GPU 算完一层，等 CPU 专家算完，再继续」——那么**慢的一侧决定整体速度**：CPU 专家计算会像一根塞子一样，每隔几层就卡住 GPU 一次。ktransformers 解决这一问题的两手是：**异步任务调度**（让 CPU/GPU 各自独立推进）与 **CUDA Graph**（把 GPU 侧数千次内核启动压成一次）。

这两手一个管「空间上的重叠」（CPU 与 GPU 同时干活），一个管「时间上的压缩」（每次解码的启动开销最小化），恰好覆盖了「跨设备协作」的两个维度。把它们拆开看各有各的学问，合起来才构成一次「丝滑的解码」：GPU 图里每一步都有活干，CPU 队列里永远有任务在排队。<span class="marginnote">论文第 4 节专门处理「执行」层面的跨设备协同。理解这一节，你就掌握了 ktransformers 性能的「最后一个百分比」——<strong>前面所有放置策略，最终都靠这里的流水线兑现</strong>。</span>

## 1 异步调度：把「同步等」换成「队列推」

朴素实现是**同步屏障**：每个 Transformer 层的边界上，GPU 等 CPU、CPU 等 GPU。ktransformers 换成**生产者-消费者队列**：

**GPU 侧**：算完 Attention 与路由后，把「被选中的冷专家列表 + 对应 token 的输入」投递给 CPU 队列，立刻继续算下一层的稠密部分——**不等待**。

队列在这里扮演「缓冲垫」的角色：它吸收了 CPU/GPU 两边的速率波动。GPU 偶尔算得快、偶尔被内存带宽卡一下；CPU 线程池的吞吐也有起伏——队列让两边不必精确同步，而是「各自按自己的节奏推进，由队列吞吐差异」。**队列的长度本身就是健康信号**：队列总是空，说明 CPU 供过于求；队列总是满，说明 CPU 供不应求、GPU 在等数据。
**CPU 侧**：线程池从队列取任务，并行执行冷专家 GEMM，结果写入预先分配好的输出缓冲。
- **层边界同步点**：只在真正需要（下一层 Attention 要用专家输出）时才等一次，且此时 GPU 通常已把若干层稠密计算提前做完——等待被「藏在」已完成的计算里。

把同步与异步两种模式对照成一张表，差异立刻分明：

| 维度 | 同步屏障 | 异步队列 |
| --- | --- | --- |
| GPU 算完 Attention 后 | 等 CPU 专家结果 | 投递任务、继续算下一层 |
| CPU 算完专家后 | 等 GPU 下一层就绪 | 写缓冲、取新任务 |
| 等待的性质 | 每层强制屏障 | 层边界软同步 |
| 设备利用率 | 一方干活一方空等 | 双方持续忙碌 |
| 时间账 | $L(T_g + T_c)$ | $L \cdot \max(T_g, T_c)$ |

「同步」与「异步」不是谁对谁错——**同步简单正确，异步复杂高效**。ktransformers 选择异步，是因为 CPU 专家计算与 GPU 稠密计算在规模上旗鼓相当，串行等会让任何一方都有一半时间空转；只有当「同步的代价」足够大时，为异步付出的复杂性才值得。

这背后的理论是**流水线并行**的思想：把 61 层视为流水线的 61 级，CPU 专家计算与 GPU 稠密计算在**不同层上重叠执行**——GPU 在第 $l+1$ 层做稠密时，CPU 正在为第 $l$ 层算专家。<span class="marginnote">这种跨层重叠，让 CPU 的慢被「平均」进 GPU 的快里。前提是 CPU 任务足够多、足够独立——冷专家天然满足：它们之间无依赖，token 之间也无依赖（batch 内可并行）。</span>

## 2 CUDA Graph：把一次解码压成一次启动

GPU 内核有一个隐藏成本：**launch 开销**。每个内核启动约几微秒到几十微秒——单层几十个内核、61 层下来，每次前向光启动就吃掉可观时间；decode 阶段 batch 小、每内核计算时间短，**启动开销占比尤其刺眼**。

**CUDA Graph** 把这个账一次性解决：把 GPU 侧算子的**计算依赖图**捕获一次、固化成一个「图对象」，之后每次执行只提交一次 launch，由驱动按图重放。

要理解为什么「一次 launch」这么值钱，得知道 GPU 内核启动的完整链条：CPU 每次调用内核，都要做「参数打包 → 检查错误 → 写入命令队列 → 驱动调度」——一套几微秒到几十微秒的开销。decode 阶段每个内核的计算时间可能只有几十微秒，**启动开销占比可以达到一半甚至更高**。把 61 层 × 每层十几个内核的启动开销乘以每次解码，浪费的时钟周期十分可观。CUDA Graph 把「启动链条」提前固化，执行时一次性重放——**省掉的是重复的启动开销，而不是内核本身的计算**。<span class="marginnote">ktransformers 的官方表述是：<strong>把 CPU/GPU 通信开销压到「每次解码只调一次 CUDA Graph」</strong>。图里包含 Attention、热专家、投影以及「从 CPU 异步取专家结果」的等待点——整个 decode 的 GPU 侧，从几十上百次 launch 变成 1 次。</span>

CUDA Graph 之所以能这么干，前提是**图结构稳定**：算子的种类、依赖关系在多次解码间不变（只有数据变化）。ktransformers 通过「把专家 GEMM 的 CPU 结果在固定位置就位」维持图的稳定性——CPU 计算本身不进图，只是图中的一个「等待数据就位」节点。

「等待数据就位」这个节点的设计很巧妙：它不是让 GPU 傻等，而是把「CPU 结果何时到」封装成一个**事件（event）**——GPU 图走到该节点时，检查事件是否已触发；若 CPU 已写完，直接继续；若未写完，则阻塞直到事件触发。这样，**CPU 算得快时 GPU 不额外等，CPU 算得慢时 GPU 才停下来等**——等待是有条件的、最短的，而不是固定的一拍。这正是异步系统的精髓：把「同步」变成「按需同步」。

## 3 公式解析：流水线重叠的时间账

用流水线的经典时间公式看收益。设 GPU 每层稠密计算时间为 $T_g$，CPU 每层专家计算时间为 $T_c$（折算到 GPU 视角的等待），层数为 $L$。

**同步版**（每层串行等）：总时间 $T_{\text{sync}} = L (T_g + T_c)$——慢的一侧每层都罚一次。

**流水线版**（跨层重叠）：只要 $T_c \le T_g$（CPU 专家时间不超过 GPU 稠密时间），总时间可压到

$$
T_{\text{pipe}} \approx L \cdot \max(T_g, T_c) + T_{\text{warmup}}
$$

其中 $T_{\text{warmup}}$ 是首层/末层的填充与排空开销。

逐项拆解：

- **第一步**：同步版把两个时间**相加**；流水线版取**最大值**——重叠消灭了「相加」。
- **第二步**：条件 $T_c \le T_g$ 是流水线成立的前提。若 CPU 专家算得太慢（专家太多、CPU 太弱），$T_c > T_g$，瓶颈回到 CPU，$T_{\text{pipe}} \approx L \cdot T_c$——此时就该**减少 CPU 专家、提高 GPU 专家占比**（`num_gpu_experts`）。
- **第三步**：$T_{\text{warmup}}$ 与层数无关，是常数项——层数越大，摊销越好。61 层的 DeepSeek-V3 恰好让常数项微不足道。

**一句话**：异步调度把「每层相加」变成「整体取最大值」，而 CPU 慢不慢，取决于「专家在 CPU 的比例」与「CPU 算力」的匹配。

把流水线公式的边界条件再挖一层。若 CPU 侧完全跟不上（$T_c \gg T_g$），时间账退化为 $L \cdot T_c$——**此时异步流水线救不了你**，因为瓶颈已经移到 CPU 侧且无处可藏。反过来，若 CPU 侧快得过剩（$T_c \ll T_g$），流水线理论上限是 $L \cdot T_g$，CPU 变成「富余产能」，可以考虑把显存预算从专家手里让一部分给 KV Cache。**看懂公式的两个极限，才能读懂 ktransformers 调参的两种方向**：瓶颈在 CPU 时加专家上 GPU，瓶颈在 GPU 时把显存让给上下文。<span class="marginnote">这也给出了调参的判据：若解码吞吐被 CPU 侧拖死（CPU 跑满、GPU 空闲等数据），应<strong>提高 `num_gpu_experts`</strong>；若 GPU 满载而 CPU 闲置，则可<strong>减少 GPU 专家、把显存让给 KV Cache</strong>。</span>

## 4 辨析｜易错点：异步 ≠ 无同步

在进入辨析前，先厘清一个术语陷阱：ktransformers 里的「异步」到底异步在哪。它异步的是**任务投递**——GPU 投递专家任务后不等待、立刻干别的；但它**没有**异步的是**依赖关系**——下一层 Attention 真正需要专家结果时，仍要等。所以更准确的说法是：**投递异步、消费按需同步**。这两个词分开记，就再也不会把「异步」误解成「完全没有等待」。

**辨析｜易错点：** 异步调度不是「完全不等待」，而是「只在必要时等待」。真正的同步点仍然存在：层边界上，下一层 Attention 需要上一层专家输出，此时必须等。异步消灭的是**不必要的等待**——那些「CPU 还没算完、但 GPU 可以先干别的活」的等待。<span class="marginnote">把「同步（synchronization）」与「异步（asynchrony）」看作<strong>同步点稀疏化</strong>，而非消灭：61 层原本 61 个硬屏障，流水线把它压成每 k 层一个软屏障，屏障之间两设备自由推进。</span>

另一个易错点：把 CUDA Graph 当作「优化了内核本身」。它优化的是**启动开销**，不是内核的计算速度——GEMM 该多快还多快，省的是「启动」这层皮。两者收益叠加：内核快了（第 3 篇的 Marlin/AMX）是「单次算得快」，Graph 化是「启动次数少」。

第三个易错点：以为「CUDA Graph 捕获一次就永远有效」。Graph 的适用前提是**图结构稳定**——算子的种类与依赖关系在多次解码间不变。一旦放置策略变化（比如动态专家更新把某专家从 GPU 挪到 CPU），GPU 侧的算子集合就变了，Graph 需要**重新捕获**。ktransformers 把「可能变的部分」留在图外（CPU 专家计算）、「不变的部分」固化在图中，正是为了尽量减少重捕获的次数。

还有一个容易被忽视的点：异步流水线会放大「冷启动」的延迟。第一层 prefill 时 CPU 侧任务队列还没预热、pinned 缓冲首次分配未就绪——首 token 会比稳态稍慢。**这不是缺陷，而是异步系统的固有预热成本**；理解它，就不会把「首 token 稍慢」误判为 bug。

## 5 调度实践：把「流水线」调顺的判据

异步调度不是「配好就不管」，运行时需要持续判断「流水线是否健康」。三个可观察的信号：

**信号一：GPU 利用率**。若 GPU 满载（`nvidia-smi` 显示高利用率）而 CPU 侧偶发空闲，说明流水线健康——CPU 专家计算没有拖后腿。

**信号二：CPU 成为瓶颈**。若 CPU 线程长期跑满、GPU 间歇性等待数据，说明冷专家太多或 CPU 太弱——此时应**调高 `--kt-num-gpu-experts`**，把更多专家搬上 GPU。

**信号三：同步点拖沓**。若观察到的每层等待时间明显偏大，可能是 pinned 缓冲与 NUMA 配置不当（见下篇），数据没有「就近」到位。

**判据一句话**：异步流水线的最优状态，是 GPU 满载而 CPU 不成为瓶颈——**两者都不该空等，但 GPU 应当是最先被喂饱的那台机器**。

把这些观察手段养成习惯，你就拥有了「调试异构流水线」的现场感——这比记住任何一条参数都更重要：**参数是死的，现场是活的**。

## 6 小结

- 异步调度 = **生产者-消费者队列**：GPU 投递专家任务后继续算稠密，CPU 线程池并行消费，只在层边界软同步。
- 跨层重叠：GPU 算第 $l+1$ 层稠密时，CPU 正在算第 $l$ 层专家——慢被「藏」进快里。
- **CUDA Graph** 把 GPU 侧几十上百次内核 launch 压成一次，decode 只调一次图。
- 时间账：同步版 $L(T_g+T_c)$ → 流水线版 $L\cdot\max(T_g,T_c)$——瓶颈从「相加」变「取最大」。
- 边界条件：$T_c > T_g$ 时瓶颈回落到 CPU，应**提高 `num_gpu_experts`**；$T_c \ll T_g$ 时 CPU 富余，可把显存让给 KV Cache。
- 三个健康信号：GPU 满载（好）、CPU 跑满且 GPU 等数据（该加 GPU 专家）、每层等待偏大（查 pinned/NUMA）。
- 「投递异步、消费按需同步」：异步消灭的是「不必要的等待」，不是所有同步点。

再补一句「异步」的工程哲学：**异步的本质，是把「确定性同步」替换成「按需同步」**——能不等就不等，只在依赖真正需要时才等。这个原则不止适用于 CPU-GPU 协作，也适用于一切「两个速度不同的组件协同」的系统：生产者与消费者之间，永远是「队列 + 按需等待」优于「每一步都互相等」。**把「异步」从一项技术升华为一种设计原则，你就能在任何系统里找到应用它的位置**——从 HTTP 并发到数据库连接池，都是同一句话：别让快的一方等慢的一方。
