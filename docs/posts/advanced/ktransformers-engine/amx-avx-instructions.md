## 为什么指令集决定 CPU 的「天花板」

上一节的 `η_simd`——指令集利用率——决定了 CPU 实际算力能摸到峰值的几成。这一节把指令集这一层讲透：ktransformers 的 CPU 内核在支持 **Intel AMX** 的处理器上开启 AMX-BF16 路径，CPU 端 prefill 相对 llama.cpp 提升约 **28×**；在不支持 AMX 的机器上，退回到 **AVX512-BF16 / AVX-VNNI**。<span class="marginnote">28× 不是内存带宽带来的，是<strong>指令宽度与流水线结构</strong>带来的：AMX 的脉动阵列让 CPU 第一次有了「张量单元」。理解这几条指令，就理解了 CPU 侧性能的物理上限。</span>

## 1 从 SIMD 到矩阵指令：指令宽度的三次跃迁

CPU 靠 **SIMD（单指令多数据）**做并行浮点。一次指令同时处理的数据个数，就是「指令宽度」：

在进入表格前，先建立「宽度」的直觉：SSE 时代的 128-bit 意味着「一条指令同时处理 8 个 FP16」，而 AVX-512 的 512-bit 意味着「一条指令同时处理 32 个 FP16」——**宽度每翻一番，单指令的吞吐就翻一番**，这就是「为什么指令集决定 CPU 算力天花板」的朴素起点。下面的表格把这三次翻番与 AMX 的结构性跃迁并列起来看。

| 指令集 | 位宽 | 每周期 BF16 乘加 | 首次登场 |
| --- | --- | --- | --- |
| SSE | 128-bit | 8 | 1999 |
| AVX2 | 256-bit | 16 | 2013 |
| AVX-512 | 512-bit | 32 | 2016 |
| AVX512-BF16 | 512-bit + BF16 专用 | 64（两路 32） | 2020 |
| **AMX-BF16** | 二维张量（8×8 tile，1KB 寄存器） | 1024 | 2022（Sapphire Rapids） |

**跃迁的关键**：AVX-512 及其变体是**一维 SIMD**——一条指令算一排数；AMX 是**二维矩阵引擎**——一条指令算一个 8×8 的矩阵乘（256 次乘加），配合 tile 寄存器（1KB），把「从内存取数、喂给计算单元」的管线彻底改造。

「一维」与「二维」的区别值得停下来体会：一维 SIMD 是「一条指令对一排数做同样运算」，本质是「并行度的水平扩展」；AMX 是「一条指令对一整块矩阵做乘加」，本质是「把矩阵乘这个高频模式变成硬件原生操作」。**AMX 不是在 SIMD 上加宽，而是换了一种计算范式**——就像 GPU 用 Tensor Core 处理矩阵乘一样，CPU 的 AMX 是「CPU 版的 Tensor Core」。这条「专用计算单元」的路线，正在成为所有处理器追赶 AI 算力的共同答案。<span class="marginnote">AMX 的正式名称是 <strong>Advanced Matrix Extensions</strong>，在 Sapphire Rapids（第四代 Xeon）引入。它对 BF16 有原生支持：`_tile_dpbf16ps` 一条指令完成「两个 16×16 BF16 矩阵 → 16×16 FP32 累加」。一次就是 4096 次乘加。</span>

## 2 BF16 与 VNNI：两个「恰好够用」的数据类型

**BF16（bfloat16）**：Google 提出、在 AI 圈普及的 16 位格式——**与 FP32 相同的 8 位指数、较短的 7 位尾数**。它保留了 FP32 的动态范围（不会上溢/下溢），代价是精度稍低。对 LLM 推理「尾数精度比动态范围更不敏感」，BF16 是理想选择。

「尾数精度比动态范围更不敏感」这句话是理解 BF16 的关键，值得展开：LLM 的权重与激活分布通常是**重尾**的——有少数很大的离群值，多数集中在中小量级。若用尾数更长的 FP16（5 位指数），离群值会超出它的指数范围导致上溢/下溢；而 BF16 用 8 位指数覆盖了 FP32 的完整动态范围，虽然尾数短（精度略低），但**不会「爆范围」**。在「宁损失一点精度、不爆动态范围」的权衡里，BF16 是最稳的选择——这也是它成为大模型训练与推理主流的根本原因。

**AVX-VNNI（Vector Neural Network Instructions）**：另一套加速整数神经网络的指令，把「8-bit 整数乘加」压缩成一条指令——`vpdpbusd` 一次算「8 个 u8×i8 乘加并累加到 i32」。它是 **INT8 量化推理**的硬件加速器。

ktransformers 的 CPU 内核按权重类型分派：**BF16 权重走 AMX-BF16 / AVX512-BF16，INT8 权重走 AVX-VNNI，INT4 权重走打包后的整数路径**——每类数据都有对应的最宽指令。

「每类数据都有对应的最宽指令」这句值得再品一层：CPU 的指令集演进，本质是**「为 AI 计算里出现的高频模式逐个补硬件」**——BF16 出现 → 补 AMX-BF16；INT8 出现 → 补 VNNI；矩阵乘频繁 → 补 AMX tile。每一代 CPU 都在「追赶 AI 负载的轮廓」。**指令集的丰富程度，就是该 CPU 代次对 AI 负载友好度的直接指标**——这也是为什么「看 CPU 支持哪些 AI 指令」比「看 CPU 主频」更能预判推理性能。<span class="marginnote">这就是「指令集分派」（ISA dispatch）的工程含义：<strong>内核在启动时检测 CPU 支持哪些指令集，编译期/运行期选择最宽的一条路径</strong>。不是「用一个折中的路径通吃」，而是「逐指令集特化」。</span>

「逐指令集特化」的代价是**代码量膨胀**：每多支持一条指令路径，就要多维护一份内核变体，测试矩阵也成倍增长。这也是为什么「能用 AMX 的引擎」不是免费午餐——llamafile 社区花了大量精力维护这些变体。**「特化」是拿「实现成本」换「运行效率」**：对于要长期运行、反复调用的推理内核，这个交换非常划算——一次性的实现成本，摊到无数次推理上，微不足道。

## 3 AMX 为什么带来 28×：不只是位宽

把 prefill 的提升归因于「AMX 比 AVX 宽 32 倍」太天真。28× 来自三个层次叠加：

**位宽**：单指令乘加数从 32（AVX512）提到 1024（AMX tile），约 32×。
**流水线**：AMX 是**异步单元**——加载 tile 与计算可以并行推进，数据搬移被藏在矩阵乘时间里。
- **访存模式**：tile 寄存器的加载按二维块进行，天然匹配矩阵乘的 cache 分块，DRAM 访问次数更少。

三者相乘，28× 才成为现实。

「28×」这个数字还藏着一个「分母」问题：它是相对 **llama.cpp 在同类 CPU 上的 CPU prefill** 而言的——llama.cpp 的 CPU 内核主要走 AVX-512，甚至可能未启用 AMX。所以「28×」本质是「用上 AMX 的内核 vs 没用上 AMX 的内核」的差距，而不是「ktransformers vs llama.cpp 两个引擎」的差距——后者还有调度、量化等其它差异。**读性能数字时，先问「分母是什么」**：同样是「快 28×」，相对于「上一个实现」和相对于「理论最优」的含义完全不同。这是评估任何性能声明的基本功。<span class="marginnote">注意：28× 是 ktransformers 的 v0.3 预览版宣传的「CPU prefill 相对 llama.cpp」的提升，实际数字随批次、模型与内核版本波动。更稳妥的理解是：<strong>AMX 让 CPU 从「SIMD 向量机」升级成「真正的矩阵机」，量级上的差距是结构性的</strong>。</span>

## 4 公式解析：一条 AMX 指令的算力

把「一条 AMX-BF16 指令的算力」算清楚。设 CPU 主频 $f$，一个 core 有 1 个 AMX 单元，`_tile_dpbf16ps` 每周期完成 $16 \times 16 \times 16 = 4096$ 次乘加（BF16×BF16→FP32 累加），则单核峰值：

$$
\text{peak} = f \times 4096 \times 2 \ \text{FLOPs/s}
$$

代入主频 $f = 2$ GHz（约）：

- **第一步**：$4096 \times 2 = 8192$ FLOPs/cycle（乘加计 2 FLOPs）。
