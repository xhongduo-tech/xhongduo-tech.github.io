## 为什么 prefill 要单独优化

推理分两段：**prefill（预填充）**一次性处理整个输入 prompt，产出首个 token；**decode（解码）**逐 token 生成后续。两者的计算画像截然不同——prefill 是「大矩阵乘、计算密集、算术强度高」，decode 是「小 batch、带宽受限、算术强度低」。ktransformers 对 prefill 专门做了一套**块量化 + 内存布局**优化。

用一个生活类比记住两段的不同：prefill 像「一次性读完一本书并写下摘要」（大工作量的批处理），decode 像「逐字把摘要念出来」（小步骤的串行）。前者要的是「吞吐」（一口气处理多少），后者要的是「节奏」（每步多快）。**两段优化目标不同，也就必然需要两套手段**——这正是本篇「prefill 单独优化」的存在理由。<span class="marginnote">论文第 5 节把 prefill 优化单列：prefill 的算术强度高，适合 GPU 算力；但它同时要读取巨大权重，量化与布局直接决定「带宽能不能喂饱 GPU」。<strong>prefill 优化 = 让 GPU 在大矩阵乘时别被内存拖住</strong>。</span>

## 1 prefill vs decode：两段不同的画像

| 维度 | Prefill（预填充） | Decode（解码） |
| --- | --- | --- |
| 输入规模 | 整个 prompt（数百–数万 token） | 单个 token |
| 计算形状 | 大 GEMM，算术强度高 | 小 GEMM，算术强度低 |
| 瓶颈 | 算力（若数据喂得够） | 内存带宽 |
| 对延迟的影响 | 首 token 延迟（TTFT） | 每 token 延迟（TPOT） |
| 硬件偏好 | GPU 算力优先 | 带宽优先 |

「TTFT 与 TPOT」这两个指标是推理服务质量的**双引擎**：TTFT（首 token 时间）决定「用户要等多久才开始看到输出」，TPOT（每 token 时间）决定「输出流畅不流畅」。优化 prefill 就是在压 TTFT，优化 decode 就是在压 TPOT——**ktransformers 对两段分别优化，本质是同时对两个用户体验指标负责**。这也是它区别于「只优化 decode 吞吐」的普通方案的地方：长 prompt 场景下 TTFT 同样是体验瓶颈。

**结论**：prefill 是「喂饱算力」的问题——只要权重能以足够快的速度流入 GPU，GPU 就能跑满；decode 是「带宽主导」的问题——权重读多快，token 就出多快。ktransformers 对两者采取不同的优化：prefill 重点在**量化与布局**（让数据流更快），decode 重点在**异步流水**（第 2 篇已讲）。

「prefill 算力主导、decode 带宽主导」这个分野还带来一个实践推论：**prefill 阶段 GPU 是主角（算力吃满），decode 阶段 CPU 与 GPU 的配合成为主角（异步流水）**。因此调优的方向也随阶段而变：prefill 慢 → 优化量化与布局（本篇）、加大 batch；decode 慢 → 调整专家放置、优化流水线。**先定位「哪段慢」，再选对应的优化手段**——这是推理性能调优的第一原则，比盲目堆参数高效得多。

## 2 块量化：per-token 之外的第三种粒度

量化有三种粒度，区别在「缩放因子分多细」：

**per-tensor**：整张权重表一个缩放因子——最省事，但误差大，离群值拖累全局。

**per-channel（per-column）**：权重矩阵每一列（每个输出通道）一个缩放因子——误差小很多，是 GEMM 的常见选择。

**per-group / 块量化（block quantization）**：把每一列按长度 $G$（如 128）分成若干**块**，每块独立缩放——在精度与存储之间取最优平衡。<span class="marginnote">ktransformers 在 prefill 的 CPU/GPU 权重上都用块量化（group quantization）：以 32-bit 整数为容器打包 4-bit 权重，每 $G$ 个权重配一个缩放因子。相比 per-channel，它对权重分布中「局部剧烈变化」的刻画更细——离群值只影响所在块，不污染整列。</span>

块量化的反量化公式（对第 $g$ 块）：

$$
\tilde{w}_i = (w_i^{\text{int4}} - z_g) \times s_g,\quad i \in \text{块 } g
$$

其中 $s_g, z_g$ 是该块的缩放与零点。**块越小，误差越小，但缩放因子占的存储越多**——块大小是精度/存储的旋钮。

「块大小」这个旋钮的极端取值值得展开：块大小 = 整列（per-channel），则每列一个缩放，存储最省、误差最大；块大小 = 1（per-element），则每个权重一个缩放，精度最高、存储爆炸。实践中取 32–128 是「用可接受的存储开销换显著的误差下降」的甜点区间。**量化的艺术，就是在「误差曲线」与「存储曲线」之间找交点**——这个权衡思维，与第 1 篇「精度-字节谱系」完全一致，只是粒度更细了。

## 3 内存布局：为「连续读权重」重排

prefill 要读巨量权重，内存布局决定带宽利用率。两个关键决策：

先解释「为什么布局能影响带宽」：内存控制器以「突发」（burst）方式传输数据，一次突发读回一整段连续地址。若数据在内存里「排得紧凑连续」，一次突发就能取回大量有效数据；若数据「东一块西一块」，每次突发只取回一小片有用的，带宽被空转浪费。**布局优化的本质，是「让内存的突发传输尽量满载」**——下面两个决策都是在朝这个方向用力。

**布局一：打包的连续存储**。4-bit 权重以 32-bit 整数打包，8 个权重挤一个 `uint32`。这样权重在内存里是**紧密连续**的，一次突发读（burst）取回更多有效数据——DDR/显存的突发传输才更高效。若按「每字节一个权重」的稀疏摆放，带宽被浪费一大半。<span class="marginnote">这和 Marlin 的 tile 布局是同一哲学：<strong>让内存按「整块、连续」的方式被消费</strong>。prefill 的 GEMM 大、权重读取连续，打包布局的收益尤其明显。</span>

**布局二：按层/按块切分放置**。不同层的权重分属不同设备（GPU 层 vs CPU 层）、不同 NUMA 节点。prefill 时各层并行加载各自的权重块，互不干扰——内存控制器负载均匀，带宽被摊平使用。

「按层切分」还有一个隐藏收益：**它让 prefill 的「流水」成为可能**——第 $l$ 层在 GPU 上计算时，第 $l+1$ 层的权重已在并行加载（预取）。这种「计算与加载重叠」的流水，与第 2 篇的 CPU-GPU 异步流水是同一思想的「层内版本」：**只要「下一个要用的数据」能被提前放到「下一个要用的地方」，计算就永远不会等数据**。布局优化的最终目的，正是让这种「预取」可行。

## 4 公式解析：块量化带来的带宽节省

量化最直接的收益是**权重体积**。设总权重 $P$，位宽 $b$，则权重体积：

$$
\text{size} = P \times \frac{b}{8} \ \text{Bytes}
$$

对照三种位宽（DeepSeek-V3 671B）：

- **第一步，BF16**：$b = 16$，体积 $\approx 671 \times 2 = 1342$ GB——放不进消费级任何存储。
- **第二步，INT8**：$b = 8$，体积 $\approx 671$ GB——仍太大。
- **第三步，INT4（块量化）**：$b = 4$，体积 $\approx 336$ GB，再加缩放因子（每 128 个权重 1 个 32-bit 缩放 ≈ 3% 额外）→ **约 350GB**。ktransformers 的 4.5-bit 混合量化实测约 377GB。

带宽视角：若以 100 GB/s 的 DDR5 读 350GB 权重，全扫一遍约 3.5 秒——量化把「读权重」这个 prefill 的主要开销压缩到可接受范围。

3.5 秒这个数字再对照一下场景：一次长 prompt 的 prefill，如果权重全在 CPU 内存且要走 CPU 带宽，光「读权重」就要 3.5 秒——**首 token 要等 3.5 秒以上，体验几乎不可用**。而 ktransformers 把稠密权重放显存（1 TB/s 带宽）、冷专家权重放内存（低频读取），让 prefill 的「权重读取」大部分走显存侧——这是它能做到「prefill 286 token/s」的物理基础。**prefill 快不快，第一看权重在哪、第二看量化省了多少字节**——两者在本篇都有答案。<span class="marginnote">「4.5-bit」是混合量化：大部分层 4-bit、少量敏感层 5-bit 或更高——用「大多数层省字节、少数层保精度」的策略，在 336GB 基础上再加一点余量换更稳的生成质量。这就是为什么官方推荐 382GB+ 内存。</span>

## 5 辨析｜易错点：prefill 优化 ≠ decode 优化

**辨析｜易错点：** 别把「prefill 用块量化 + 大矩阵布局」套到 decode。decode 每步只算 1 个 token，矩阵是「瘦长」的——此时量化收益仍在（字节减半永远划算），但「大块连续布局」的收益大幅缩水，主导因素变成「小 GEMM 的内核启动与带宽延迟」。<span class="marginnote">ktransformers 的做法是「两段共用量化权重、各用各的执行路径」：<strong>权重只有一份（量化好的），prefill 走大矩阵内核，decode 走异步小矩阵流水</strong>。优化的是执行路径，不是权重本身。</span>

另一个易错点：把「块量化」等同于「per-tensor 量化」。per-tensor 是「全局一个缩放」，块量化是「每 G 个一组」——精度差异可高达数个百分点（在敏感层上）。ktransformers 对精度敏感的层（如 Attention 投影）保留更高位宽，正是为了在「省字节」与「保质量」之间取平衡。

「敏感层保留高位宽」这条值得再强调：它不是「一刀切 4-bit」，而是「大多数层 4-bit、敏感层 5/6/8-bit」的**混合精度**——这就是「4.5-bit」这个奇怪数字的由来：它是一个「混合平均位宽」，不是某个单一位宽。**混合精度的哲学是「把精度预算花在最需要的层」**：绝大多数层贡献的字节足够多、且对量化不敏感，压缩它们收益巨大；少数敏感层位宽稍高，保住生成质量。这个「预算分配」思维，与专家放置的「把显存花在最热的专家」是同构的——**资源永远花在回报最高的地方**。

## 6 prefill 优化的完整链路

把本篇的三个优化串成一条「prefill 加速链」：

1. **量化减字节**：块量化把权重从 BF16 的 2B 降到 4-bit 的 0.5B——prefill 要读的字节直接减 4 倍。
2. **布局提带宽**：32-bit 打包 + 按层切分放置，让「剩下的字节」以最高效率被读出来。
3. **内核吃算力**：大 GEMM + 高算术强度，让 GPU 的 Tensor Core 把「喂进来的字节」快速算完。

三环相扣，任何一环塌了整条链都慢：量化不到位 → 字节多；布局差 → 带宽浪费；内核弱 → 算力吃不饱。**「减字节、提带宽、吃算力」是 prefill 优化的三步曲**——它也是理解所有「大矩阵乘场景」优化（训练、prefill、推理引擎）的通用框架。

这套三步曲其实贯穿了本专题的多个篇章：减字节（量化篇）、提带宽（布局/打包篇）、吃算力（内核篇）。**prefill 篇不是孤立的一篇，而是把前面所有「数据面优化」串起来应用到「大矩阵乘阶段」的汇总**——读到这里，你应该能感觉到本专题的知识点正在收拢成一个整体：放置管「谁在哪」，量化管「多少字节」，布局管「字节怎么流」，内核管「流进来的字节怎么算」。

## 7 小结

本篇的「三步曲」值得再念一遍：**减字节（块量化）、提带宽（打包布局）、吃算力（大 GEMM 内核）**——prefill 的每一个优化动作，都能落进这三步中的一步。

- prefill 与 decode 画像不同：**prefill 算力主导、decode 带宽主导**，需分别优化。
