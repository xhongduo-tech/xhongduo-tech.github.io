## 为什么需要一把「尺子」

前面我们知道了 MoE 的稀疏性、专家激活的幂律——但这只是「哪些权重重要」。还缺一个更底层的问题：**一个算子放在 CPU 上算、还是放在 GPU 上算，凭什么决定？** 光说「GPU 快」是不够的：GPU 的算力确实强，但它的显存带宽同样惊人；CPU 算力弱，可它贴着的是容量巨大的 DRAM。真正决定「谁算更划算」的，是算子的**算术强度（arithmetic intensity）**——每搬一个字节，能换回多少次运算。<span class="marginnote">这把尺子正是计算机体系结构里的 <strong>Roofline 模型</strong>（Williams et al., 2009）。ktransformers 论文用 Roofline 统一解释了「什么算子该留 GPU、什么算子该放 CPU」，是整个异构决策的理论骨架。</span>

## 1 算术强度：FLOPs 与 Bytes 的比值

**算术强度（arithmetic intensity）**定义为一个计算内核在单位访存量下能完成的浮点运算数：

$$
I = \frac{\text{FLOPs}}{\text{Bytes 访存}}
$$

单位是 FLOPs/Byte。直觉：**$I$ 大 = 计算密集**——运算多、搬的数据少，属于「内存友好」的算子；**$I$ 小 = 访存密集 / 内存受限**——搬运数据花了大部分时间，算力反而闲着。

举大模型里最典型的两类算子：

- **GEMM（通用矩阵乘）**：一次 $M \times N$ 乘 $N \times K$ 的矩阵乘，FLOPs 约 $2MNK$，访存量约 $MN + NK$（输出 + 输入权重）。当 $M, N, K$ 都很大时，$I \approx \frac{2MNK}{MN+NK}$ 随维度增大而增长——**大矩阵乘是计算密集的**。
- **逐元素/小张量操作**：比如一次只处理一个向量、反复读写参数，FLOPs 少而访存多，$I$ 很小——**访存密集**。

**关键分野**：Attention 与小 batch 的算子往往受制于带宽（$I$ 低），大矩阵乘受制于算力（$I$ 高）。

注意 $I$ 的公式里，分子分母的「度量」不同：分子是**运算次数**（FLOPs），分母是**字节数**（Bytes）——两者没有天然的等价关系，所以 $I$ 的单位（FLOPs/Byte）看起来「混搭」。这正是算术强度的意义所在：**它强行把「运算」与「搬运」拉到同一把尺子上比较**，告诉你「搬一个字节的代价，能不能被足够多的运算摊薄」。一个 $I=100$ 的算子，搬 1 字节能做 100 次运算——带宽的付出「划算」；$I=1$ 的算子，搬 1 字节只做 1 次运算——带宽「亏本」。

把大模型里几类典型算子的算术强度排个序，立刻能看清「谁该去哪」：

| 算子 | 典型算术强度 | 设备偏好 |
| --- | --- | --- |
| 大 GEMM（prefill，大 batch） | 高（数百–数千） | GPU |
| 中 GEMM（decode，中等 batch） | 中（数十–数百） | GPU 或 CPU |
| 专家 FFN（单 token 激活） | 中低（十数） | CPU |
| 逐元素 / 归一化 / 注意力分数 | 低（个位数） | 靠近数据处 |

**一个反直觉点**：专家 FFN 单看是一个「大矩阵乘」，似乎算术强度很高；但把它放到「单 token、被稀疏激活」的上下文里，每次实际的矩阵形状很「瘦」（$1 \times d$ 乘 $d \times d_{\text{ff}}$），算术强度被拉低。**算术强度是「运行上下文」的函数，不是算子的固有属性**——同样的 GEMM，batch 大时适合 GPU，batch 小时更适合 CPU。

## 2 Roofline：一台机器的「天花板」

**Roofline 模型**把硬件抽象成两条限制线。设峰值算力为 $\Pi$（FLOPs/s）、峰值内存带宽为 $\beta$（Bytes/s），则任意内核的实际性能被夹在两条曲线之下：

$$
\text{performance} \le \min\left( \Pi,\ \beta \times I \right)
$$

以算术强度 $I$ 为横轴、性能（FLOPs/s）为纵轴画出来，得到一条「屋顶」：

- **左半段（内存受限区）**：$I$ 小，性能被 $\beta \times I$ 钉死——带宽是瓶颈，算力在「挨饿」。
- **右半段（算力受限区）**：$I$ 大，性能逼近 $\Pi$——算力吃满，带宽已不是问题。
- 两条线相交处 $I_0 = \Pi / \beta$，称为**转折点**，划分了「访存密集」与「计算密集」。

**这就是「放哪」的判据**：内存受限的算子，谁带宽够、谁便宜就放谁那；算力受限的算子，则必须交给算力峰值高的设备。

Roofline 还有一个容易被忽视的用途：**诊断「当前内核为什么不满速」**。如果一个 GPU 内核实测性能远低于 $\Pi$，查它的算术强度落在屋顶的哪一侧——若在左段（内存受限），堆算力没用，要优化访存（量化减字节、改善局部性）；若在右段（算力受限），才该优化计算（更好的指令、更宽的数据类型）。**Roofline 不只告诉「该放哪」，还告诉「瓶颈是什么」**——这是它成为系统设计通用工具的原因。

诊断思维还可以再进一步：**「瓶颈转移」是优化最常见的结果**。你用量化把算子的字节减半、算术强度翻倍，它可能从「内存受限」跳到「算力受限」——瓶颈从带宽换成了算力，天花板从 $\beta \times I$ 换成了 $\Pi$。**优化一个环节，常常只是把瓶颈推到下一个环节**；Roofline 让你能预判「推到了哪」，从而决定下一步该优化什么。这是「木桶理论」在性能工程里的精确版本。

## 3 公式解析：GPU 与 CPU 的转折点差距

把 RTX 4090 与一颗现代 CPU 的典型数字代进去，你会立刻看到「异构分工」为什么成立。

设 GPU 峰值算力 $\Pi_g = 80$ TFLOPS（FP16）、显存带宽 $\beta_g \approx 1$ TB/s；CPU 峰值算力 $\Pi_c \approx 1$ TFLOPS（BF16，多核）、内存带宽 $\beta_c \approx 100$ GB/s（DDR5 双通道量级）。<span class="marginnote">这些是量级估算，具体型号差异不影响结论。真正重要的是<strong>转折点的比值</strong>，它揭示两台设备的「舒适区」完全不同。</span>

用 RTX 4090 与一颗多核 Xeon 做对照，是「消费级旗舰 GPU」与「工作站 CPU」的典型组合——恰好也是 ktransformers 官方部署文档推荐的组合。数字本身不必精确到个位，**重要的是数量级**：GPU 的算力带宽比（转折点）比 CPU 高一个数量级，这个「一个数量级」足以撑起后面所有分工结论。换用 RTX 3090 或 AMD 卡，比值略有变化，但「GPU 转折点远高于 CPU」的定性结论不变——这也说明 Roofline 是「定性稳定」的分析工具。

逐项拆解转折点：

**第一步，GPU 转折点**：$I_0^{(g)} = \Pi_g / \beta_g = 80\times 10^{12} / 10^{12} = 80$ FLOPs/Byte。
**第二步，CPU 转折点**：$I_0^{(c)} = \Pi_c / \beta_c = 10^{12} / 10^{11} = 10$ FLOPs/Byte。
- **第三步，对照结论**：GPU 的转折点高达 80——只有算术强度超过 80 的算子才能让它「满负荷运转」；而 CPU 的转折点只有 10，算术强度 10 以上的算子就能喂饱它。

把「转折点之比」再算一笔：$I_0^{(g)} / I_0^{(c)} = 8$。这个「8 倍」的含义是：**一个算术强度落在 10 到 80 之间的算子，放 GPU 上是「带宽受限」（跑不满），放 CPU 上是「算力受限」（跑得满）**——而 CPU 的绝对性能虽低，但对这类算子来说「低而满」比「高而空」更划算。这就是「异构分工」最凝练的数学表达：**每台设备都有自己的「舒适区」，算术强度决定了算子落在哪台设备的舒适区里**。

于是分工法则浮出水面：**算术强度很高的算子（$I > 80$）适合 GPU；算术强度不高、但访存友好的算子（$10 \lt  I \lt  80$）反而适合 CPU——因为 CPU 的「天花板」更低、更容易摸到，而同样的算子放 GPU 上只是浪费算力、还被带宽卡脖子。**

这里的「适合」不是「只能」，而是「性价比最高」：高算术强度算子放 CPU 也能算，只是被 CPU 的低屋顶压住；低算术强度算子放 GPU 也能算，只是浪费 GPU 算力。**Roofline 给出的是「最优放置」，不是「可行放置」**——ktransformers 追求的是前者，这正是它与「能跑就行」的朴素方案的本质区别。<span class="marginnote">注意一个反直觉点：ktransformers 把<strong>稀疏专家</strong>放 CPU 不是因为 CPU 算得快，而是因为专家 FFN 在这种稀疏场景下算术强度并不高，CPU 的带宽恰好够用，而 GPU 的宝贵算力要留给真正的稠密大 GEMM。这个细节我们下一节展开。</span>

## 4 辨析｜易错点：「GPU 快」不等于「放 GPU 划算」

最普遍的误解是把「设备快慢」等同于「放置决策」。Roofline 说：**只有算力受限的算子才真正吃「快」**。

**辨析｜易错点：** 一个算术强度只有 20 的算子，放 RTX 4090 上性能被带宽卡在 $\beta_g \times 20 = 20$ TFLOPS——只有峰值算力的 1/4；放 CPU 上则能跑到 $\beta_c \times 20 = 2$ TFLOPS，**超出 CPU 峰值算力 1 TFLOPS 了吗？没有**，实际被钉在 1 TFLOPS。两边都不「完美」。真正的智慧在于：**别让低算术强度算子占用高算力设备**，把 GPU 算力腾给高算术强度的稠密算子，低算术强度的算子交给带宽型设备——哪怕它绝对性能不高，但「够用且便宜」。

这个例子里还藏着一个「资源经济学」的要点：GPU 的 80 TFLOPS 是**稀缺资源**，被低算术强度算子占用时，它「浪费」的不只是那 3/4 的算力，而是**挤掉了本来可以放上去的高算术强度算子**。系统优化常常不是「把每个算子都调到最快」，而是「**把稀缺资源分配给最值得它的算子**」——这是一种「分配优于优化」的思维，贯穿 ktransformers 的全部设计。

再补一个实用视角：Roofline 分析不需要昂贵的 profiler——手算几行就够。给定算子的 FLOPs 与访存字节数（框架日志或简单推导可得），除一下得 $I$，与设备转折点一比，归属与瓶颈立刻分明。**工具之简，恰是它普及之因**：它不需要黑科技，只需要「算一算」的习惯。

另一个易错点：**把峰值算力当性能**。GPU 标称 80 TFLOPS 只有喂足算术强度才可能逼近；现实中大量 LLM 解码算子是访存受限的，实际利用率常常只有几个百分点。ktransformers 的论文正是用 Roofline 解释了为什么「全量卸载到 CPU」会把性能浪费在低算术强度算子上——详见第 5 篇《全量卸载方案的瓶颈分析》。

还有一个更隐蔽的误区：**以为「算力受限」的算子放哪都一样**。不对——算力受限的算子放到 CPU 上，虽然「按屋顶模型不会被带宽卡」，但 CPU 的算力峰值 $\Pi_c$ 远低于 GPU，实际性能被「较低的屋顶」限死。**Roofline 的「放哪」要同时看「瓶颈类型」和「屋顶高度」**：放 GPU 是因为它的屋顶高（算力强），放 CPU 是因为低算术强度算子在 CPU 的屋顶下「够用且不浪费」。

## 5 小结

读这一篇时，请记住 Roofline 在 ktransformers 里的角色：它不是「某个内核的优化技巧」，而是**全局放置决策的判据**——每一个「放 GPU 还是放 CPU」的抉择，最终都能回溯到「这个算子的算术强度落在哪台设备的舒适区」。

把本篇的三个数字刻进记忆——**80（GPU 转折点）、10（CPU 转折点）、8（两者之比）**——它们比任何参数都更能概括 ktransformers 的「分工理性」。下次看到「这个算子放 GPU 吧」的直觉判断时，试着用算术强度重新验证一遍，你会发现直觉常常被数字纠正。

- **算术强度** $I = \text{FLOPs}/\text{Bytes}$ 衡量「每搬一个字节换回多少次运算」。
- **Roofline** 把性能天花板写成 $\min(\Pi, \beta \times I)$：左段访存受限、右段算力受限，转折点 $I_0 = \Pi/\beta$
