## 为什么检索是多模态的第一应用

对齐和融合讲了半天，第一个「落地成真问题」的就是**跨模态检索**：你脑子里有一个「画面」（夕阳下的沙滩），却只有文字能搜——于是你用文字搜图片；反过来，你手头有一张截图，想找它出自哪部电影、说的是什么——于是用图搜文字。这类任务不需要生成、不需要推理，只要求一件事：**在公共空间里比距离，把最像的排到最前**。也正因为「只比距离」，它成了检验对齐质量最干净、最可复现的探针。<span class="marginnote">检索是「表示对齐」最直接的应用：对齐学得好不好，检索指标就是试金石。这也是为什么多模态论文几乎都以检索分数作为对齐质量的例行报告项。</span>搜索引擎、商品找同款、视频素材库、以图搜图，全是跨模态检索的产业形态。它也是第三级《信息检索》倒排索引体系在「异构数据」上的自然延伸。

## 1 什么是跨模态检索

**跨模态检索（cross-modal retrieval）**：以一类模态的数据作为查询（query），从另一类模态的数据集（gallery）中找出语义最匹配的样本。

常见组合有：

**文本检索图像（text-to-image）**：输入「一只在雪地里打滚的熊猫」，返回匹配图片。
**图像检索文本（image-to-text）**：输入一张图，返回最贴切的描述/标题/网页文本。
**跨模态检索视频 / 音频**：一段语音查对应视频帧，或一句话查相关视频片段。

标准评测数据集有三座：**Flickr30K**（3 万张图，每张 5 句描述）、**MSCOCO**（12 万张图，每张 5 句描述）、**Flickr8K**（8000 张图）。三者都是「图文对」结构：训练时给「图 + 描述」对，测试时用双向检索报告 R@1/5/10。**数据规模小但结构经典**——直到 2021 年后才有以 CLIP 数据规模（4 亿对）为背景的检索基准，但论文报告格式至今沿用 Flickr30K/MSCOCO。

与单模态检索（文本搜文本、图搜图）相比，跨模态检索**没有天然的特征可比性**——必须先把 query 与 gallery 都映射到同一空间。这正是对齐空间存在的意义。所以跨模态检索的完整链路是：**对齐（学空间）→ 编码（进空间）→ 检索（比距离）**。前两步前两课已备好，本课重点在第三步，以及为第三步设计的评价指标。

检索结果的「形态」也随任务而变：**图搜文**返回一段段文本，排序依据是「这段文字描述的是不是这张图」；**文搜图**返回一张张图，排序依据是「这张图是不是这句话所描述的」。两者共享同一套向量空间与同一套指标，只是 query 与 gallery 的角色互换。这种对称性让「双向平均」成为默认评估方式——后文会展开。

## 2 双塔与单塔：两种检索架构

检索架构与表示范式一一对应，两种流派至今并行：

**双塔（two-tower）架构**：图像塔与文本塔各自编码，检索时只比对向量（余弦距离）。代表是 CLIP、VSE++。<span class="marginnote">双塔的杀手锏是<strong>索引可预计算</strong>：几亿张图的向量可以离线算好、建好索引，线上查询只需编码一条 query 再做最近邻搜索，毫秒级响应。这也是工业界大规模检索几乎只用双塔的原因。</span>
- **单塔（cross-attention）架构**：把 query 与每个候选拼接送进一个模型，模型「亲自」比对。代表是视觉语言 Transformer 系。准确率高，但**每个候选都要过一遍模型**，无法预计算索引，只适合候选量小（几百个）的场合。

| 维度 | 双塔 | 单塔（cross-attention） |
| --- | --- | --- |
| query 编码次数 | 1 次（只需编码 query） | 与候选数成正比 |
| gallery 索引 | 可预计算 + ANN | 无法预计算 |
| 交互粒度 | 全局向量级 | token/区域级细粒度 |
| 计算成本 | O(query) | O(query × 候选数) |
| 适用规模 | 亿级 | 百级 |
| 角色定位 | 召回 | 精排 |

两者是典型的「效率 vs 精度」权衡。工业界的标准解法是**两段式**：先用双塔从几亿候选里粗筛出 top-K（召回），再用单塔对这几百个候选精排（重排）。这套「**召回 + 精排**」的骨架与第三级《信息检索》里的「粗排 + 精排」如出一辙，只是召回通道从倒排索引换成了向量检索。

具体到一个电商「以图搜同款」场景：用户上传一件衣服的照片，系统先用图像塔在 5 亿商品图里 ANN 搜出 top-500，再用单塔模型把这张照片与 500 件商品逐一精算相似度，取 top-10 展示。**整个流程必须在几百毫秒内完成**——这就是「预计算索引 + 近似搜索」存在的全部理由。若在召回阶段就用单塔，5 亿次模型前向是任何 GPU 集群都扛不住的。

## 3 检索系统的完整流程

一个生产级跨模态检索系统，流程是固定的四步：

1. **编码（encoding）**：把 query 与全部 gallery 用双塔编码成向量，L2 归一化。
2. **建索引（indexing）**：把 gallery 向量组织成支持近似最近邻（ANN）的数据结构——HNSW 图、IVF 倒排向量桶——使「找最近邻」从线性扫描变成对数/亚线性搜索。细节见第三级《向量数据库》与第四级《大模型部署》的检索部分。索引的两大调参旋钮是**召回率**（索引能找全多少真近邻）与**查询延迟**（每次搜索耗时），二者此消彼长。
3. **检索（search）**：对 query 向量做 ANN 搜索，得到 top-K 候选。K 的大小直接影响下游：K 太小，真正的匹配可能不在候选里（召回不足）；K 太大，重排环节的延迟与成本上升。**K 是召回与精排之间的交通信号灯**，实践中取几百到几千。
4. **重排（rerank）**：对 top-K 用单塔模型精排，输出最终结果。

**关键洞察：检索质量的上限由「对齐质量」决定，ANN 只负责不丢召回**。对齐空间里「语义远」的，再好的索引也救不回来；反之，对齐好，即使 ANN 的近似召回损失一点，重排也能兜住。这套「上限由表示、下限由工程」的分层，和信息检索里「词项匹配决定上限、倒排索引决定速度」是同一结构。

向量检索的工程底座在本博客有多处延伸：索引结构（HNSW、IVF）在第四级《大模型部署》的「向量数据库」一节；把检索结果拼进 prompt 交给生成模型，就是第四级《大模型原理》的 **RAG（检索增强生成）**。多模态检索 + 生成模型 = 多模态 RAG，这是第四篇《多模态 Agent》的重要组成。**跨模态检索不只是「搜索引擎」，它还是「给生成模型供料的记忆系统」**——这个视角下一课讲共现与互补时会再次用到。

## 4 公式解析：Recall@K 指标

检索效果用**召回率**衡量。设一次「文搜图」查询，ground truth 是图 $I^*$，模型按相似度对全部图排序：

$$
\text{Recall@K} = \frac{1}{|\mathcal{Q}|}\sum_{q \in \mathcal{Q}} \mathbb{1}\left[\text{rank}(I^*_q) \le K\right]
$$

三步拆解：

- **第一步，读懂 $\mathbb{1}[\cdot]$**：这是指示函数，括号里的条件成立取 1，否则取 0。它把一个「对/错」的布尔判断变成可累加的数。
- **第二步，读懂 $\text{rank}(I^*_q) \le K$**：ground truth 图 $I^*_q$ 在排序结果里**排进了前 K 名**。K 通常取 1、5、10——K 越大越宽松。
- **第三步，整体求和平均**：对查询集 $\mathcal{Q}$ 里的每个 query 判一次「是否命中前 K」，求和再除以 $|\mathcal{Q}|$，得到一个 0–1 之间的平均分。**注意：这里的「召回」是「正确项是否被召回」的布尔命中率**，与信息检索里「recall = 命中的相关项 / 总相关项」在含义上略有不同，后者见第三级《信息检索》。

实践中还有两个伴随指标：**Median Rank（中位排名）**——所有 query 的正确项排名的中位数，越小越好；**Mean Recall（平均召回）**——把文搜图与图搜文两个方向的 Recall@K 取平均，防止模型「只擅长一个方向」。报告跨模态检索结果时，**双向平均是默认规矩**。<span class="marginnote">为什么必须双向平均？因为对齐损失若不对称（比如只在「图→文」方向加权），模型可能学成「文本塔万能、图像塔摆设」。双向平均能暴露这种不对称退化。</span>

用一个具体数字走一遍 Recall@1。假设有 5 个文搜图查询，模型分别把正确图片排在 1、2、1、5、3 名，那么 K=1 时只有两个查询命中（排名 ≤ 1），$\text{Recall@1} = 2/5 = 0.4$；K=5 时全部命中，$\text{Recall@5} = 1.0$。注意：**R@1 反映「第一名就找对」的硬实力，R@10 反映「召回不丢」的下限**——两者差距大，说明模型「对但不够准」，重排环节有提升空间。

还要分清两个「召回」：公式里算的是**在完整 gallery 上的排名**（学术报告口径，要求全量暴力排序）；而线上系统在 ANN 索引上只得到 top-K 候选，算出的命中率会**低估**真实效果——因为 ANN 可能把正确项漏出候选集。因此论文报告与线上监控的 Recall@K **不是同一个数**，跨系统对比时要留意口径是否一致。

顺带一提，除 Recall@K 之外，工业界还常报 **Precision@K**（返回的前 K 条里有多少真的相关）与 **nDCG**（考虑排序位置、对「排前面的正确项」加权）。检索任务的评价远不止「有没有找到」，还包括「找到的是不是排在前面」——但跨模态领域以 Recall@K 为主流报告口径，其他指标用于精排环节的线下评估。

**一条黄金经验**：当你动手实现第一个跨模态检索系统时，先别急着上难负样本或重排。先跑通「双塔 + 暴力检索 + R@1」，确认对齐空间的语义结构是对的；再逐步加入 ANN、重排、难负样本。每一步只动一个变量，性能瓶颈在哪、收益在哪，一目了然。

## 5 挑战与易错点

跨模态检索看似简单，实战里四个坑最常见：

**第一个坑：gallery 规模与指标失真。** 小数据集（如 Flickr30K 的 1000 张测试图）里 R@1 很容易做到 80%+，但放大到亿级 gallery，真实命中率断崖下跌。**报告的分数必须伴随 gallery 规模**，否则无法横向比较。

**第二个坑：近似搜索的召回损失。** ANN 是近似算法，可能把真正最近的向量漏掉。系统上线前要监控「ANN 召回率 vs 暴力检索」的差距，若差距过大，调 HNSW 的 `efSearch` 参数。

**第三个坑：把「匹配」当「语义」。** 双塔可能靠低层特征（颜色、布局）匹配而非语义，导致「一张红裙子的图」搜出「所有红色图」。**难负样本挖掘 + 细粒度对齐（局部对齐）**是缓解之道。<span class="marginnote">一个经典翻车案例：早期以图搜图系统里，搜「金毛犬」会返回所有「草地+暖色」的照片——模型学的不是「狗」而是「草地」。这种「语义泄漏」只有用反例难负样本才能压住。</span>

**第四个坑：冷启动与数据偏斜。** 检索效果严重依赖对齐空间的训练数据。垂直领域（医疗影像、法律文书）需要领域内图文对做二次对齐，否则通用模型在领域内检索效果堪忧。

选型小结一句话：**上线看规模，评测看口径，提分看负样本。** 规模决定用双塔还是单塔、评测要注意 R@K 的口径、而要突破精度瓶颈，几乎总要先从难负样本和局部对齐下手——这与第一课《表示对齐》的结论完全闭环。

## 6 小结

- **跨模态检索**以一类模态为 query、另一类为 gallery，在公共空间比距离；它是「表示对齐」最直接的应用。
- 两种架构：**双塔**（可预计算索引，效率高，工业主流）与**单塔**（逐候选精算，精度高，用于重排）；标准解法是「双塔召回 + 单塔精排」。
- 生产链路四步：**编码 → 建 ANN 索引 → 检索 → 重排**；质量上限由对齐决定，ANN 只负责不丢召回。
- 核心指标 **Recall@K** 衡量「正确项排进前 K」的平均命中率；报告时必须双向平均并注明 gallery 规模。
- 四个坑：**指标失真、ANN 召回损失、匹配≠语义、领域冷启动**。
- 双塔与单塔各司其职：**双塔召回、单塔精排**；跨模态检索还是多模态 RAG 与多模态 Agent 的底层记忆组件。
- 生产链路「编码 → 建索引 → 检索 → 重排」四步中，索引与重排只负责「不丢、排准」，真正的语义上限在对齐。
- 与第三级《信息检索》的承接：倒排索引负责符号级检索，向量检索负责语义级检索，二者互补而非替代。
- 与后续课程的连接：CLIP 正是「用对比学习把双塔对齐到极致」的模型——下一课我们就进入第二篇，从对比学习的数学核心 InfoNCE 开始。
