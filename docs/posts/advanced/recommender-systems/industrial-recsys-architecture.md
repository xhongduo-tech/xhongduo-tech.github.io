## 为什么从架构总览开始

前面所有章节都在讲「模型」：召回、排序、重排的算法。但一个真实上线的推荐系统，模型只是冰山一角——**模型之外，还有数据怎么流动、特征怎么提供、样本怎么构造、服务怎么扛住高并发**。这些「工程骨架」决定了模型能不能跑、跑得多快、学得对不对。<span class="marginnote">工业推荐系统是一个「数据闭环」：线上服务 → 行为日志 → 数据管道 → 特征/样本 → 模型训练 → 模型上线 → 回到线上服务。模型的迭代质量，取决于这个闭环转得多快、多准。理解架构，就是理解这个闭环。</span>

这一节画一张「全链路地图」：推荐服务在线链路长什么样、数据链路怎么闭环、以及各层之间的接口。

## 1 在线服务链路：一次请求的旅程

用户在 App 下拉刷新，一次推荐请求在服务端依次经过：

**多路召回 → 粗排 → 精排 → 重排 → 策略输出**：先并行跑多路召回（协同过滤、向量、热门、场景等），把候选从亿级全量快速筛到数千；粗排用轻量模型再砍到数百；精排用深度模型逐条精细打分、排序到数十；重排做列表级优化（去重、多样性、插广告、频控）；最后经策略层组装成用户看到的页面。

每一步的职责与预算：

| 阶段 | 职责 | 候选规模 | 延迟预算 |
| --- | --- | --- | --- |
| 多路召回 | 从海量物品快速筛出候选 | 全量 → 数千 | 几 ms |
| 粗排 | 轻量模型粗筛，压缩精排规模 | 数千 → 数百 | 几 ms |
| 精排 | 深度模型精细打分 | 数百 → 数十 | 几十 ms |
| 重排 | 列表级优化（多样性等） | 数十 | 几 ms |

**延迟预算层层分配**：整个链路通常要控制在 50~200ms 内，每一层都有自己的毫秒预算。越靠前的层越要「快而粗」，越靠后越能「慢而细」。

## 2 数据链路：行为怎么变成模型的燃料

在线服务产出的数据，经过离线管道变成模型训练与评估的输入：

**日志采集 → 特征计算 → 样本拼接 → 模型训练 → 上线回灌**：先把线上每次曝光与反馈沉淀成行为日志，再从日志与外部数据算出特征（用户近 7 天点击类目分布、物品热销度等），把「特征 + 标签」拼成训练样本，离线训练出模型后发布到在线服务；线上新产生的行为再回流进日志，完成闭环。

- **行为日志**：每次曝光、点击、消费都要记录（谁、何时、看到了什么、反馈如何）。
- **特征计算**：从日志与外部数据算出特征（用户近 7 天点击类目分布、物品热销度等）。
- **样本拼接**：把「特征 + 标签」拼成一条训练样本（见 [[sample-construction-label-delay]]）。
- **模型训练与上线**：离线训练好模型，推到在线服务加载（见 [[online-inference-low-latency]]）。

**关键接口是「特征一致性」**：离线训练时用的特征，和线上推理时用的特征必须一致——否则模型在离线评估好、线上表现差。这就是 [[feature-platform-offline-online-consistency]] 要解决的问题。

## 3 公式解析：链路的「延迟预算」分解

把一次请求的延迟预算写成约束：

$$
L_{\text{budget}} \ge L_{\text{召回}} + L_{\text{粗排}} + L_{\text{精排}} + L_{\text{重排}} + L_{\text{其他}}
$$

拆三步理解：

- **第一步，预算分配**：$L_{\text{budget}}$ 是产品定的总预算（如 100ms）。各层 $\sum L_i \le L_{\text{budget}}$，余量留给网络、特征读取等「其他」。**每层必须在自己的预算内完成，超时即降级**（返回上一层结果、用缓存）。
- **第二步，层层缩量**：召回从全量（亿级）缩到数千、粗排缩到数百、精排算几十、重排输出最终列表。**每一层都以「上一层的输出」为输入，把规模砍一个量级**——这是「漏斗」架构的本质。
- **第三步，预算换质量**：精排的模型最重、耗时最长，但只面对几百个候选；召回必须极快，因为面对亿级。**「用前面层的粗，换后面层的细」**——每一层的模型复杂度要与它面对的规模匹配。

## 4 离线与在线：两条腿的闭环

工业系统同时运行两条链路：

- **离线链路**：慢、全量、一次跑几小时到几天。负责模型训练、评估、特征/样本批量生成。
- **在线链路**：快、单次、毫秒级响应。负责召回、排序、重排、展示。

两链路的「握手」：

1. 离线训练出模型参数与特征表 → 定期发布到线上（小时级/天级）。
2. 线上行为 → 日志 → 回灌到离线（小时级/天级），更新训练数据。
3. 闭环节奏决定了「模型有多跟得上用户」——快节奏（实时推荐）见 [[realtime-recommendation-streaming]]。

## 5 架构里的「稳定」与「降级」

高并发系统必须为故障留后路：

- **缓存兜底**：特征、排序结果、热门榜都有缓存，缓存命中可绕过重链路。
- **降级策略**：召回挂了 → 直接返回热门榜；精排挂了 → 用粗排分数；重排挂了 → 原序返回。**每一层都要有「无它也能活」的退路**。
- **监控告警**：各层耗时、成功率、结果规模都要实时监控，异常立即告警。

## 辨析｜工业架构的「三层数据」与「两个时钟」

理解工业推荐架构，光看「链路」不够，还要看「数据」与「时钟」两个横切面：

**三层数据**：工业系统里数据按「时效与用途」分三层，各司其职：

| 数据层 | 时效 | 用途 | 存储 |
| --- | --- | --- | --- |
| 实时数据 | 秒级 | 在线特征、实时行为 | 消息流 + KV 缓存 |
| 准实时数据 | 分钟~小时 | 流式特征、样本回灌 | 流式计算 + 数仓 |
| 离线数据 | 天级 | 全量训练、批量特征 | Hive/数仓 |

**「同一份行为，三层各有一份」是常态**——实时层给「当下请求」，准实时层给「小时级更新」，离线层给「全量训练」。三层的一致性靠「统一日志口径」保证（见 [[feature-platform-offline-online-consistency]]）。

**两个时钟**：

- **模型时钟**：模型多久更新一次（天级重训、小时级增量）。模型时钟决定「模型有多了解用户」。
- **数据时钟**：行为多久能进到模型（秒级实时、天级离线）。数据时钟决定「模型用的是多新的数据」。

**「两个时钟不同步」是架构最常见的隐患**：模型更新快（时钟快）但数据滞后（时钟慢），模型在「旧数据」上更新，等于白忙。**工业架构优化的本质，就是「把两个时钟都调快、且让它们对齐」**——这正是 [[realtime-recommendation-streaming]] 的核心目标。

**一个架构哲学**：在线链路是「表演」，离线链路是「准备」，数据平台是「后台」——**三者缺一不可，但「表演」永远受「准备」与「后台」的制约**。看架构不要只盯着在线链路，要顺着数据流把三块都看到。

## 6 小结

- 工业推荐系统是一个**数据闭环**：在线服务 → 日志 → 特征/样本 → 训练 → 上线。
- **在线链路**是「召回→粗排→精排→重排→策略」的漏斗，每层有毫秒级预算、逐层缩量。
- **离线链路**负责训练与批量特征，与在线链路通过「模型发布」与「日志回灌」握手。
- **特征一致性**是离线/在线协同的关键接口，直接决定模型线上表现。
- 稳定第一：**每层都要有缓存与降级退路**。

**术语速查**：

| 术语 | 一句话 |
| --- | --- |
| 漏斗架构 | 召回→粗排→精排→重排逐层缩量 |
| 数据闭环 | 服务→日志→特征→训练→上线 |
| 双时钟 | 模型更新时钟与数据回灌时钟 |
