## 为什么从在线推理开始

训练好的模型最终要「上线服务」：每次用户刷新，推理服务要在几毫秒内用模型给候选打分。在线推理与离线训练是两套完全不同的工程：**训练看重吞吐与收敛，推理看重延迟与并发**。<span class="marginnote">在线推理的约束很硬：精排阶段要在一二十毫秒内给几百个候选各打一次分，整条链路总预算 100ms 左右；同时系统要扛住每秒几万次请求的并发。延迟超预算 = 用户流失，这是产品级硬指标，不是「尽力而为」。</span>

这一节讲在线推理的三大支柱：**低延迟、高并发、模型压缩**。

## 1 推理服务的分层

工业推理服务通常分两层部署：

- **参数层（Embedding 服务）**：embedding 表巨大，独立部署成 KV/向量服务，按需提供用户/物品 embedding。
- **计算层（模型服务）**：跑模型前向计算，从参数层取 embedding，算打分。

一次精排请求的流程：

$$
\text{取候选} \to \text{并行取用户/物品特征与 embedding} \to \text{模型前向} \to \text{输出分数} \to \text{排序}
$$

**瓶颈通常在「取参数」**：几百个候选 × 各自的 embedding + 特征，都是内存/网络访问。优化取参路径（本地缓存、批量拉取、SSD 分级）往往比优化模型计算更有效。

## 2 低延迟：三个层面的优化

- **计算层面**：模型尽量用低精度（FP16/INT8）、小 batch 切分、算子融合（把多层合并成更少的核调用）；推理框架（如 TensorRT、ONNX Runtime）做图优化。
- **存取层面**：embedding 与特征放本地内存或缓存，减少远端访问；常用「**批取**」（一次请求把几百个候选的 embedding 一起取）代替逐个取。
- **架构层面**：异步化、并发（把「取特征」与「算模型」流水线化）、以及「分级推理」——先用轻量模型筛，再对少数候选跑重模型（呼应 [[industrial-recsys-architecture]] 的粗排/精排分层）。

## 3 高并发：吞吐与稳定

高并发的本质是「单请求延迟 × 并发量」在算力/带宽约束内的平衡：

- **横向扩容**：多副本部署 + 负载均衡，用「加机器」换吞吐。
- **池化与复用**：线程池、连接池、模型实例复用，避免重复创建开销。
- **超时与熔断**：单请求超时直接降级返回（用缓存结果），防止「慢请求」拖垮整体。
- **批量推理**：把多个并发请求合并成一个 batch 前向（batching），GPU/CPU 吞吐更高——但要注意「等 batch 凑满」会引入额外延迟，需权衡。

## 4 模型压缩：让模型「变小变快」

模型压缩是推理优化的重头戏，常见手段：<span class="marginnote">推荐模型的主体是 embedding 表，所以推荐模型的压缩重点也在 embedding：从「每 ID 独立向量」到「共享子向量（哈希/量化）」、到「低精度存储」。相比 CV/NLP 的蒸馏/剪枝，推荐更常用「对 embedding 做文章」——因为 embedding 占了绝大多数参数。</span>

| 手段 | 原理 | 收益 |
| --- | --- | --- |
| 量化（quantization） | 参数从 FP32 降到 INT8/INT4 | 存储/带宽降 4~8 倍，推理加速 |
| embedding 哈希 | 多个 ID 共享一个 embedding 槽 | 表大小降数倍 |
| embedding 分级 | 热门 ID 全精度、冷门 ID 低精度 | 存储降、质量损失小 |
| 剪枝 | 去掉不重要的神经元/维度 | 计算降 |
| 蒸馏 | 大模型教小模型 | 模型变小 |

**量化的直觉**：把「连续的高精度权重」换成「离散的低精度权重」，推理时乘加运算更快、内存带宽需求更低——代价是精度损失，需评估量化前后指标。

## 5 公式解析：延迟、吞吐与并发的换算

把在线服务的关键关系写成「利特尔定律（Little's Law）」形态：

$$
\text{并发量} Q = \text{吞吐} \lambda \times \text{平均延迟} L
$$

拆三步理解：

- **第一步，吞吐**：$\lambda$ 是每秒处理的请求数。**吞吐要满足峰值流量**（如每秒 5 万请求）。
- **第二步，延迟**：$L$ 是平均单请求处理时间（含排队）。**延迟由产品预算定死**（如精排 ≤ 20ms）。
- **第三步，并发需求**：$Q = \lambda \times L$ 是「同一时刻在系统中的请求数」。如果 $\lambda = 5\text{万/s}$、$L = 20\text{ms}$，则需支撑 $Q = 1000$ 个并发——**这是扩容、线程池、队列设计的数量依据**。延迟降不下来，就要靠并发容量扛吞吐；并发扛不住，就是延迟劣化的开始。

## 6 部署与发布

- **模型热更新**：模型参数更新频繁（天级甚至小时级），要支持「无中断切换」（双副本灰度、流量平滑迁移）。
- **回滚**：新模型上线后指标恶化，要能秒级回滚到旧模型。
- **监控**：延迟分位数（P99）、错误率、吞吐、GPU/CPU 利用率都要实时监控。

## 辨析｜推理延迟的「分位数」思维与「降级」设计

在线推理的延迟管理，最常犯的错误是「只看平均延迟」。三个正确姿势：

**姿势一：看 P99 而不是平均值。** 平均延迟会被「大多数快请求」拉低，掩盖「少数慢请求」。用户感受到的「卡顿」是「最慢的那一小撮」——**P99 延迟（最慢的 1% 请求的平均）才是用户体验的真相**。优化的目标不是「平均降 5ms」，而是「P99 降下来」。P99 高通常来自「冷缓存」「网络抖动」「慢尾请求」——这三类问题与「平均延迟」几乎无关。

**姿势二：为「慢尾」设计降级。** 与其「保证每个请求都快」，不如「给慢请求一条退路」：设置「每层超时阈值」，某层超时就「用上一层结果」或「缓存兜底」返回。**「先返回一个结果」比「返回一个完美但慢的结果」重要**——用户等不起完美。

**姿势三：缓存要「分层」。** 推理服务的缓存不是「一层」：本地内存缓存（最快、容量小）→ 分布式缓存（快、容量中）→ 远端 KV（慢、容量大）。**热数据进内存、温数据进分布式缓存、冷数据走远端**——缓存分层是「P99 优化」最立竿见影的手段。缓存的关键不是「命中率」，而是「P99 场景下命中率」——冷启动、高峰期的缓存失效，才是 P99 的敌人。

**一个提醒**：推理服务「加机器」不能解决所有问题——如果瓶颈是「单请求的串行依赖」（先取特征、再算模型、再写日志），加机器只是「增加并发」，单请求延迟不变。**优化延迟先「砍串行、加并行」，再谈扩容**。

**补充｜推理服务的「三个监控指标」与「容量规划」**：

在线推理「不出事」靠监控，「能扛住」靠容量规划。三个关键监控：

- **P99/P999 延迟**：P99 看「常规最差」，P999 看「极端慢尾」——两者「同时监控」，P999 突然升高通常预告「容量告急」或「冷缓存风暴」。
- **超时率与降级率**：「超时降级」的比例——**降级率升高，说明系统「靠降级在撑」**，是容量不足或模型变慢的早期信号。
- **GPU/CPU 利用率与排队长度**：利用率接近 100% 且「请求在排队」，说明「算力饱和」——**利用率「高而稳」是「吃满但没垮」，利用率「抖动大」是「有尖峰」**。

**容量规划的三步**：先「压测」得出「单实例 QPS 上限」→ 按「峰值流量 ÷ 单实例能力」算「实例数」→ 再「× 1.5~2 冗余」扛「突发与故障」。**「平时吃不饱、峰值刚好够、故障能顶住」是容量设计的理想态**——吃太饱扛不住尖峰，太闲浪费成本。

**一个提醒**：监控「错误率」要「按错误类型拆」——「超时、5xx、降级、参数错误」的处置方式完全不同，混在一起看会「看不清病因」。

**收尾一句话**：推理优化的「第一性原理」是「把用户的等待时间花在刀刃上」——该快的层快、该省的省，P99 是裁判，回退是底线。

## 7 小结

- 在线推理的硬约束是**低延迟（毫秒级）与高并发（万级 QPS）**，与离线训练是完全不同的工程。
- 推理服务分**参数层（embedding 服务）**与**计算层（模型服务）**，瓶颈常在「取参数」。
- 低延迟靠**计算优化 + 存取优化 + 架构异步化**；高并发靠**扩容、池化、熔断、批量推理**。
- **模型压缩**重点是 embedding：量化、哈希、分级、剪枝、蒸馏，把模型「变小变快」。
- 延迟/吞吐/并发满足利特尔定律 $Q = \lambda L$，是容量设计的数量基础。
