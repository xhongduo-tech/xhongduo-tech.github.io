## 为什么从 Parameter Server 开始

推荐模型的训练与 CV/NLP 有本质不同：**推荐模型的参数量主要来自 embedding 表，而 embedding 表是「稀疏 + 海量」的**。用户 ID、物品 ID 各有几千万甚至上亿个，每个对应一个几十维的 embedding 向量——总参数量动辄数十亿、上百亿。<span class="marginnote">对比一下：BERT 大模型的参数是「稠密的」（全部参数在每一批样本上都更新）；推荐模型的参数是「极端稀疏的」——一个 batch 里的几百条样本，只碰到几百万参数里的一小撮 embedding 行。这种「稀疏性」让传统的「全参数同步」训练框架（如 AllReduce）完全失效。</span>

这一节讲推荐训练的两个核心：**稀疏参数存储**与 **Parameter Server（参数服务器）架构**。

## 1 推荐模型的参数画像

推荐深度模型（如 [[deepfm]]、[[din-deep-interest-network]]）的参数大致分两类：

| 参数类型 | 例子 | 规模 | 更新特性 |
| --- | --- | --- | --- |
| 稠密参数 | 全连接层权重 | 百万级 | 每批都更新 |
| 稀疏参数 | ID embedding 表 | 十亿级 | 每批只碰一小撮 |

**稀疏参数是主角**：用户 embedding 表几千万行、物品 embedding 表几千万行，加起来的参数量远超稠密部分。但它们有个致命特性——**一个 batch 的样本只会「激活」其中极小一部分**。如果训练框架还按「全量同步」的方式处理，通信量会是灾难。

## 2 稀疏性的困境：AllReduce 为什么会炸

深度学习的标准训练用 AllReduce：每轮把所有 worker 的梯度求和、同步到全部机器。这对稠密模型没问题（梯度是完整张量），但推荐模型：

- 每轮同步**全部 embedding 表的梯度**，哪怕其中 99.999% 是 0。
- 十亿参数 × 每轮全量通信 → 网络带宽成为瓶颈，训练慢得不可用。

**解法不是「同步全部」，而是「只同步被碰到的」**——这要求训练框架能感知「哪些参数这一轮被激活了」，只对这些参数做通信与更新。这就是 Parameter Server 架构的设计起点。

## 3 Parameter Server：把参数「放中间、分片存」

**Parameter Server（PS）** 把参数从 worker 里拿出来，放到一组独立的「参数服务器」上，worker 与 PS 分工：

- **Server 节点**：持有全部参数（embedding 表分片存储），负责「按需」提供参数、接收梯度、更新参数。
- **Worker 节点**：跑数据与计算，每轮只向 Server「拉取」本 batch 用到的 embedding 行，「推送」这些行对应的梯度。

交互流程：

$$
\text{Worker: 拉取 } \{W_{id}\}_{id \in \text{batch}} \to \text{前向/反向} \to \text{推送稀疏梯度} \to \text{Server 更新}
$$

**关键在「稀疏」**：Worker 只拉取 batch 命中的 ID 行，Server 只更新被推送梯度的行——**通信量与「batch 命中的参数」成正比，而不是与「总参数」成正比**。

## 4 公式解析：稀疏梯度更新的本质

把 PS 的参数更新写成「只在激活行上做」的形式。设 embedding 表为 $\mathbf{E} \in \mathbb{R}^{N \times d}$（$N$ 个 ID、每行 $d$ 维），batch 命中的 ID 集合为 $\mathcal{I}_b$：

$$
\mathbf{E}[i] \leftarrow \mathbf{E}[i] - \eta \cdot \text{agg}\left( \sum_{\text{samples}} \nabla_{\mathbf{E}[i]} L \right), \quad \forall i \in \mathcal{I}_b
$$

拆三步：

- **第一步，只更新命中的行**：$\forall i \in \mathcal{I}_b$ 表示「只对 batch 里出现过的 ID 更新」。未命中的 $N - |\mathcal{I}_b|$ 行不动——**这就是「稀疏更新」**。
- **第二步，梯度聚合**：同一个 ID 在 batch 里可能被多条样本命中（多个用户点了同一物品），梯度要累加（agg）。**累加在哪做？在 PS 上做**——Worker 推来「按 ID 汇总的梯度」，Server 一次性更新该行。
- **第三步，通信量**：通信量为 $O(|\mathcal{I}_b| \times d)$，与 batch 命中的 ID 数成正比。**当 batch 命中的 ID 远小于总 ID 数时，通信比 AllReduce 省几个量级**。

## 5 一致性模型与工程要点

- **同步 vs 异步**：同步 PS 每轮等所有 worker；异步 PS 各 worker 独立推进，吞吐高但有「梯度滞后」问题（参数已更新，旧梯度才到）。推荐训练常用「带限速的异步」平衡吞吐与稳定。
- **哈希分片**：embedding 表按 ID 哈希分到多台 PS 上，均衡负载。
- **embedding 压缩**：稀疏参数的存储与通信可用量化、分级存储（热门 ID 全量、冷门 ID 压缩）优化（见 [[online-inference-low-latency]] 的模型压缩）。
- **在线训练**：PS 也支持「流式更新」——线上每来一批反馈，立刻更新对应 embedding 行，实现实时学习（[[realtime-recommendation-streaming]]）。

## 6 现代演进

- 框架层面：TensorFlow PS、PyTorch 的 Sharded 方案、以及专为推荐打造的 GPU 稀疏训练框架（如 NVTabular、DeepRec），都围绕「稀疏参数的高效分布式存储与更新」。
- 趋势：随着硬件发展，部分场景用「全 GPU 稠密化」或「局部性友好的嵌入表放置」替代传统 CPU PS——但「按需拉取稀疏参数」的思想不变。

## 辨析｜稀疏参数训练的三个「隐形成本」

Parameter Server 解决了「通信量」，但推荐训练还有三个「隐性成本」经常被低估：

**成本一：embedding 表的内存与存储。** 用户 ID 几千万 × 每行 64 维 × 4 字节 ≈ 十几 GB——embedding 表本身就是「巨物」。加上「版本管理」（训练中要保留多个版本做回滚）、「特征平台」的在线副本，**embedding 表的存储成本常超模型本身一个量级**。缓解：embedding 维度压缩（8~32 维）、量化存储、按「热度」分级（热门 ID 全精度、冷门 ID 低精度）。

**成本二：稀疏参数更新的「随机性」。** 稀疏参数「每批只碰一小撮」带来了「更新频率极端不均」——热门 ID 每批都更新、冷门 ID 几周才碰一次。**这导致「热门 embedding 过拟合、冷门 embedding 欠训练」**。缓解：对冷门 ID 用「更慢的学习率」或「更强的正则」；对热门 ID 做「采样降频」——让「更新频率」与「样本频次」解耦。

**成本三：异步更新的「梯度陈旧」。** 异步 PS 里，worker 推送的梯度对应的参数版本可能「早已更新过」——陈旧梯度会让训练「震荡」。工业上常用「限速异步」：限制 worker 之间的进度差（staleness bound），在「吞吐」与「稳定」间取平衡。**异步不是「越异步越好」，而是「有限的异步」**。

**一个工程提醒**：推荐训练经常「看起来在收敛，但 embedding 表悄悄坏了」——要监控「embedding 的数值分布」「热门/冷门 ID 的更新量」，防止「稀疏参数」在没人注意的地方学偏。

**补充｜「稀疏训练」与「稠密训练」的取舍：什么时候不需要 PS**：

Parameter Server 是「稀疏 embedding 海量」场景的答案，但「不是所有推荐训练都要 PS」——两个判断：

- **场景一：embedding 表「不大」**（如小平台、千万级 ID 以内）——单机或「全参数同步」就能装下，PS 的「分布式」是过度设计。**先算「embedding 总参数 × 显存」是否单机可承载**，装得下就不必上 PS。
- **场景二：候选「稠密化」的趋势**——近年来「GPU 大显存 + 显存友好架构」让「整表放 GPU」成为可能（避免「拉取 embedding 的跨机通信」）。**「能放下就放 GPU、放不下才上 PS」**是当前的务实路线。

**另一个提醒**：PS 的「通信开销」不只是「带宽」，还有「序列化/反序列化」「网络往返延迟」——**「按行拉取 embedding」的延迟往往比「算模型」本身高**。优化方向：「本地缓存热门 embedding」（热门 ID 常驻本地）、「批量拉取」（一次请求把 batch 全部 ID 一起拉）——**「减少跨机访问」比「优化传输」更有效**。

**一句话**：PS 解决「稀疏海量」的训练问题，但「能不能不上 PS」是「显存预算」的问题——**「能本地不跨机、能单机不分布式」是工程第一原则**。

**收尾一句话**：稀疏训练的核心矛盾是「参数海量、每批只碰一点」——PS 的「按需拉取」是对这个矛盾的工程回应；「通信只跟命中行走」这一原则，至今仍是所有推荐训练框架的设计内核。

（收尾补一句「为什么值得学」：推荐训练的「稀疏性」是所有深度模型训练里最特别的一类——**理解 PS 的「按需拉取」，就理解了「为什么推荐模型的训练基建和 CV/NLP 长得不一样」**，这是读任何推荐训练框架代码的钥匙。）

**补一句**：推荐训练框架的演进（PS → 混合 → GPU 大显存）都在回答同一个问题——「怎么让『稀疏海量的 embedding』既放得下、又学得快」。

## 7 小结

- 推荐模型的参数以**稀疏 embedding 表**为主，每批只激活一小部分，导致 AllReduce 失效。
- **Parameter Server** 把参数放到独立服务器，Worker 只拉取/推送「batch 命中的行」。
- 稀疏更新 $\mathbf{E}[i] \leftarrow \mathbf{E}[i] - \eta \text{agg}(\nabla)$，$\forall i \in \mathcal{I}_b$——**通信与命中行数成正比**。
- 同步/异步一致性、哈希分片、压缩存储是工程关键；异步 PS 是推荐训练的主流。
