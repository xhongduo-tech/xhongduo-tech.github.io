## 为什么从 SIM 开始

SASRec、BERT4Rec 的自注意力是 $O(t^2)$——**序列一长就扛不住**。但真实用户的行为序列可以长达上千条：一个淘宝重度用户可能积累了两年的点击记录。截断到最近几十条，就把「三个月前买过奶粉」这种长期兴趣丢掉了。<span class="marginnote">长序列的挑战是双重的：计算量随长度暴涨，而且「全部历史平均池化」会把近期与长期兴趣搅在一起。业界思路是「不是把序列变短，而是先检索出相关子序列再建模」——先粗筛，再精读。</span>

**SIM（Search-based Interest Model）** 是阿里 2020 年提出的两阶段方案，解决「极端长序列」的建模：**先用粗粒度检索筛出与候选相关的子序列，再在子序列上做精细的序列建模**。这一节讲它的两阶段结构、兴趣检索的两个层次、以及它为何能支撑千级长度的线上 CTR 预估。

## 1 长序列问题为什么难

设用户行为序列长度为 $t$，自注意力的复杂度是 $O(t^2)$：

- $t = 50$：2500 次交互，轻松。
- $t = 1000$：100 万次交互，一个候选物品一次前向就上百万次注意力运算，精排要对几百个候选各算一遍——**不可行**。

更本质的问题是**信噪比**：用户上千次点击里，与「当前候选」相关的可能只有几十次。全量建模，绝大多数计算花在无关行为上，还可能把长期兴趣稀释在噪声里。SIM 的思路：**把「与候选相关」从 1000 里筛出来，再只对筛出的几十条建模**。

## 2 SIM 的第一阶段：泛化兴趣检索（General Search Unit, GSU）

第一阶段负责**快筛**：从长序列里把「可能相关的子序列」捞出来。检索方式有两种：

- **Hard Search**：用类目（category）等粗粒度属性匹配——候选是「运动鞋」，就从历史里取出「类目 = 运动鞋」的全部行为。检索快、可解释、零参数。
- **Soft Search**：用向量相似度检索——每个历史物品算一个 embedding，与候选 embedding 做内积，取 top-$K$ 个最相关的历史行为。检索更细腻，但需要训练。

$$\mathcal{S}_u(\text{cand}) = \text{Top}K_{i \in S_u} \left[ \text{Match}(i, \text{cand}) \right]$$

$\text{Match}$ 在 Hard Search 里是「类目是否相同」，在 Soft Search 里是「向量内积」。**GSU 把序列从 1000 缩到几十，为第二阶段扫清道路**。

## 3 SIM 的第二阶段：精准兴趣建模（Exact Search Unit, ESU）

第二阶段拿到筛出的子序列 $\mathcal{S}_u$，做**精细建模**。SIM 用一个「注意力增强的多头目标注意力」网络：<span class="marginnote">这里的注意力以「候选物品」为 query，以筛出的历史行为为 key/value——与 [[din-deep-interest-network]] 的局部激活单元同一思想，只是换成了多头、且作用在「已检索」的子序列上。</span>

$$
\mathbf{h} = \text{MultiHeadAttn}(q = \mathbf{e}_{\text{cand}}, \; K/V = \{\mathbf{e}_i\}_{i \in \mathcal{S}_u})
$$

子序列上再做候选驱动的注意力加权，得到针对候选的兴趣向量，拼入 CTR 模型。**因为子序列很短（几十条），注意力开销可控**，千级原始长度也能在线推理。

## 4 公式解析：两阶段如何分工

把 SIM 的「先粗后细」拆三步：

- **第一步，粗筛（GSU）**：$|\mathcal{S}_u| \approx 1000 \to K$（几十）。这一步**牺牲精度换速度**：只求「别漏掉相关行为」，允许捞进一些噪声，但不要求排序精确。Hard Search 用类目、Soft Search 用向量，都是 $O(t)$ 的一次扫描，快。
- **第二步，精读（ESU）**：对 $K$ 条子序列做候选驱动的多头注意力。这一步**在精而不在快**：把候选与每条历史行为的匹配程度精细量化，加权聚合出兴趣向量。
- **第三步，协同**：粗筛保证「相关行为不丢」，精读保证「留下的行为被充分利用」。**两阶段把「千级长度的注意力」变成「几十级长度的注意力」**，复杂度从 $O(t^2)$ 降到 $O(t + K^2)$。

## 5 SIM 的工程价值与要点

- **在线推理**：GSU 的类目检索可用倒排索引（见 [[ann-vector-search-hnsw-faiss]] 的思想），Soft Search 的向量检索可用 ANN；ESU 的子序列长度 $K$ 直接控制延迟预算。
- **训练一致性**：线上推理与离线训练用同一套 GSU 检索逻辑，避免「训练用全序列、线上用子序列」的分布偏移。
- **两阶段联合**：Soft Search 的检索 embedding 与 ESU 的参数一起训练，让「筛什么」与「怎么精读」对齐。
- 实测中 SIM 在淘宝主搜推荐上显著提升 CTR，是「长序列」问题的工业级标准解。

## 辨析｜SIM 与 DIN、DIEN 在序列建模谱系中的位置

SIM 不是孤立出现的，它站在一条「序列建模」的演进线上，理解这条线才能选对工具：

| 模型 | 输入序列长度 | 核心结构 | 处理长序列的手段 | 适用场景 |
| --- | --- | --- | --- | --- |
| DIN | 短（几十条） | 注意力加权 | 无（直接截断） | 常规 CTR 的候选驱动兴趣 |
| DIEN | 短（几十条） | GRU + 注意力 | 无 | 需要建模兴趣演化 |
| SASRec | 中（几十~上百） | 自注意力 | 位置编码 + 截断 | 序列推荐 |
| SIM | **极长（上千条）** | 两阶段检索 + 注意力 | **GSU 粗筛 + ESU 精读** | 长历史用户 |

选型要点：**序列长度决定结构**。当用户行为只有几十条时，SIM 的检索阶段收益不大，直接上 DIN/SASRec 更简单；当用户行为积累到数百上千条、且「很久以前的行为」仍有价值时（重度用户的长期偏好），SIM 的两阶段检索才真正发光。

**一个常被忽略的细节**：SIM 的 Hard Search 依赖「类目」等粗粒度属性，因此**类目体系的规范程度直接决定检索质量**。类目太粗（只有几个大类），Hard Search 筛出的子序列仍然很长；类目太细、有噪声，会把相关行为漏掉。工程上常对「类目」做清洗与合并，或直接改用 Soft Search 的向量检索来兜底。

**补充｜SIM 的「检索质量」评估与调优**：SIM 的 GSU 检索质量直接决定上限，两个评估手段：

- **检索召回率**：对「验证集里的真实正样本」，看「GSU 筛出的子序列里是否包含它」——**这是「召回里的召回」**。GSU 检索召回率低，说明 Hard/Soft Search 漏了相关历史，精读再强也救不回来。
- **子序列的相关性**：抽查「GSU 筛出的子序列」是否真的「与候选相关」——若筛出的内容与候选「八竿子打不着」，说明检索的「匹配函数」（类目 or 向量）没对齐「用户为什么点这个」。

**调优方向**：Hard Search 的「类目」粒度与 Soft Search 的「向量质量」是两个主要旋钮；也可以「Hard + Soft 混合检索」（先用类目粗筛，再用向量在粗筛结果里精排）——**「粗筛 + 精筛」的两级检索，与「召回 + 精排」的链路思想同构**。

**补充｜SIM 的「在线推理」与「训练一致性」**：SIM 上线有三个「必须对齐」的细节：

**1. 线上检索要与训练一致**：训练时 GSU 用「类目匹配/向量检索」筛子序列，线上推理必须「用同一套检索逻辑」——**若训练用「全序列」，线上用「检索后子序列」，分布偏移会让模型「在线失灵」**。正确做法：训练与线上「同一 GSU 逻辑」，「训练样本的子序列 = 线上会看到的子序列」。

**2. 检索的「缓存」与「实时」**：GSU 的类目倒排可以「离线建好、线上查表」（快）；但「用户实时行为」要「增量进检索库」——**「离线索引 + 实时增量」双轨**，保证「最新行为」也能被检索到（呼应 [[realtime-recommendation-streaming]]）。

**3. 长序列的「存储」**：上千条历史行为的存储与读取有成本——**「序列服务」要单独设计**：只存「必要字段」（物品 ID、时间、类目），压缩存储、按需读取。**「存得起、读得快」是长序列建模的工程前提**。

**一个提醒**：SIM 的「两阶段」本质是「把 O(t²) 的注意力拆成 O(t) 的检索 + O(K²) 的精读」——**K（子序列长度）是「精度/延迟」的总旋钮**：K 大精读更全但慢，K 小反之。**K 的取值要用「线上延迟预算」反推**。

## 6 小结

- 长序列的难点是**计算量（$O(t^2)$）与信噪比**：上千次点击里真正相关的只是少数。
- **SIM 两阶段**：GSU 粗筛相关子序列（Hard 类目检索 / Soft 向量检索），ESU 在子序列上做候选驱动的多头注意力精读。
- 复杂度从 $O(t^2)$ 降到 $O(t + K^2)$，**千级长度也能线上 CTR 推理**。
- 关键工程点是「训练与线上检索一致」「两阶段联合训练」。
- **度量**：用「有效历史长度」判断长序列是否值得——指标不再上涨的长度，就是该截断的长度。

**术语速查**：

| 术语 | 一句话 |
| --- | --- |
| GSU | 第一阶段快筛相关子序列 |
| ESU | 第二阶段候选驱动注意力精读 |
| Hard Search | 类目匹配的粗筛，零参数 |
| Soft Search | 向量相似度的粗筛，需训练 |
| 子序列长度 K | 精度/延迟的总旋钮 |

**一个复杂度对照**：原始序列 $t = 1000$，自注意力全量是 $10^6$ 次交互；SIM 用 GSU 先筛到 $K = 50$，ESU 的注意力变成 $50^2 = 2500$ 次——**计算量降了三个量级**，这就是「先检索、后精读」的全部意义。

**一个度量方法**：上线前用「有效历史长度」检验「长序列是否值得」——把序列长度从 20 逐步加到 2000，看 Recall@K 或 AUC 的增益曲线：若「超过 200 条后指标不再上涨」，说明有效历史只有 200，SIM 的两阶段是「杀鸡用牛刀」，截断到 200 更省。

**一个演进视角**：SIM 的「先检索、后精读」思想与推荐链路「召回 → 精排」同构，也与长上下文 LLM 的「检索增强（RAG）」同构——**「长输入太贵，先检索出相关片段再处理」是一个跨领域反复出现的通用工程范式**（见第四级《大模型原理》的 RAG 章节）。
