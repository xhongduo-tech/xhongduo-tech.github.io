## 为什么从统一排序框架开始

前三节分别看了搜索、推荐、广告。一个大型平台（如淘宝、抖音）同时运营这三个场景：用户搜索时要有搜索排序，逛首页要有推荐排序，每个位置还要插入广告。如果每个场景各建一套模型、一套特征、一套训练管线，成本爆炸且互相割裂。**统一排序框架（unified ranking framework）** 应运而生：**一套底座，服务多场景**。<span class="marginnote">统一不是「所有场景用同一个模型」，而是「共享技术底座 + 场景差异化适配」：同一套特征平台、样本体系、排序模型骨架、训练框架，各场景通过「场景标识 + 场景特定模块」差异化。这背后是「多场景多任务」建模——正是 [[mmoe-multi-gate-mixture-of-experts]]、[[ple-progressive-layered-extraction]] 的结构能力。</span>

这一节讲统一排序的动机、架构形态、以及「统一与差异」的边界。

## 1 为什么需要统一：分开建的代价

三个场景各自独立建模的问题：

- **数据割裂**：搜索数据、推荐数据、广告数据各存各的，样本无法共享，用户行为「跨场景」的信息（在搜索里买了、逛首页却没推荐到）被浪费。
- **重复建设**：特征平台、训练框架、推理服务各搭一套，工程成本三倍。
- **体验割裂**：用户在搜索、推荐、广告里看到「三个陌生人」，缺少跨场景的用户记忆。

**统一的收益**：一份数据、一套底座、共享用户理解，工程省成本、体验更连贯。

## 2 统一架构的形态

一个典型的「搜推广统一排序框架」：

```
统一特征平台（跨场景特征）
→ 统一样本体系（统一特征口径 + 场景标签）
→ 统一模型骨架（多场景多任务模型）
→ 场景化输出（搜索塔 / 推荐塔 / 广告塔）
→ 统一推理服务 + 场景差异化后处理
```

**核心是「模型骨架统一、场景模块差异」**：

- 底层 embedding 与共享网络：**全场景共享**——用户 embedding、物品 embedding 跨场景复用。
- 中间层：多专家 + 多门控（MMOE/PLE）——**各场景通过门控「按需取用」共享能力**。
- 输出层：每个「场景 × 目标」一个塔（搜索相关性塔、推荐点击塔、广告 eCPM 塔）。

## 3 公式解析：场景如何参与模型

统一模型里「场景」是一个显式信号。拆三步：

- **第一步，场景作为特征**：把「场景」（search/rec/ads）作为输入特征，进入门控与塔——$\text{gate}(x, \text{scene})$。**门控看到场景不同，给各专家的权重就不同**。
- **第二步，多任务多场景的联合目标**：损失是各「场景 × 目标」的加权和：

$$
L = \sum_{\text{scene}} \sum_{k \in \text{targets}(\text{scene})} w_{\text{scene}, k} \, L_{\text{scene}, k}
$$

搜索场景有「相关性 + CTR」，推荐场景有「CTR + 时长」，广告场景有「eCPM 相关」——**各场景的目标集合不同，但共享底层，一起训练**。
- **第三步，数据协同**：搜索里的「点击」和推荐里的「点击」是不同分布的行为，但共享的 embedding 让它们互相补充——**一个场景的稀疏数据，可以借助另一个场景的稠密数据学得更好**。这是统一的最大收益之一。

## 4 统一框架的差异化解法

| 环节 | 统一的部分 | 差异化的部分 |
| --- | --- | --- |
| 特征 | 用户/物品/上下文特征 | 场景特有特征（查询词、出价） |
| 模型 | embedding、共享专家 | 场景塔、门控权重 |
| 目标 | 共享损失权重 | 各场景目标集合与权重 |
| 服务 | 推理框架 | 后处理（广告插位、频控） |
| 评估 | 统一特征一致性 | 各场景指标（NDCG/CTR/eCPM） |

**统一的边界**：不是「一个模型包打天下」——搜索的「查询-文档相关性」、广告的「GSP 竞价」都太特殊，必须保留场景化模块。**统一的是「底座」，差异的是「上层」**。

## 5 统一框架的工程收益与挑战

**收益**：

- 训练与部署一套成本，而非三套。
- 跨场景数据协同，冷启动与稀疏场景受益（见 [[cold-start-classification]]）。
- 用户跨场景的「记忆」更连贯，体验一致。

**挑战**：

- **场景冲突**：搜索要「相关」，推荐要「个性」，广告要「收益」，三者在共享层可能冲突——**这是 MMOE/PLE 的用武之地**。
- **样本量失衡**：广告样本少、推荐样本多，联合训练要防「大场景淹没小场景」。
- **评测复杂**：统一模型上线，要同时盯搜索、推荐、广告三套指标，任何一个恶化都可能回滚。

## 辨析｜统一排序的「边界」：什么该统一、什么必须分开

「统一排序」常被误解为「一个模型包打天下」。实际上「统一」有明确的边界——**该统一的统一，该分开的死活不能统一**：

**必须统一的**：

- **用户与物品的表示（embedding）**：用户在主场景的偏好，应该被搜索场景知道——跨场景共享表示是统一的最大收益。
- **特征平台与样本体系**：一套特征口径、一套样本构造（[[feature-platform-offline-online-consistency]]），避免各场景「各说各话」。
- **训练框架与推理基础设施**：一套训练代码、一套推理服务，工程成本才降得下来。

**必须分开的**：

- **目标函数**：搜索优化「查询-文档相关性」（NDCG），推荐优化「个性化满意」（CTR/时长），广告优化「eCPM」——**目标不同，输出塔必须分**。
- **约束**：广告有「出价、预算、频控」，搜索有「相关性底线」（不能推无关结果），推荐有「多样性」——**约束不同，后处理必须分**。
- **场景特有特征**：查询词（搜索）、出价（广告）、用户实时序列（推荐）——**特征可以共享底层，但场景特有特征要保留**。

**一个判断准则**：「共享的部分」要满足「跨场景互不干扰」——如果两个场景「共享某模块」会互相伤害（如搜索的「相关性硬约束」污染推荐的「个性化」），这个模块就必须「分开」。**统一是「底座共享 + 上层分叉」，不是「一刀切」**。

**一个实践提醒**：统一排序「收益大、风险也大」——上线要「分场景灰度」：先让统一模型只服务推荐，验证「推荐指标不劣化」，再逐步扩展到搜索、广告。**统一不是「一步切换」，而是「渐进收敛」**。

**一个落地顺序**：统一排序的价值主张很清晰，但工程上「先统一表示、再统一训练、最后统一服务」是稳妥的三步走——每步都以「各场景指标不劣化」为验收，避免「为了统一而统一」造成的回退风险。

## 6 小结

- **统一排序框架** = 一套底座（特征、样本、模型骨架、训练服务）+ 各场景差异化模块。
- 底层 embedding 与共享专家**跨场景复用**，各「场景 × 目标」一个塔，**门控按场景调节**。
- 联合目标 $L = \sum w_{\text{scene},k} L_{\text{scene},k}$，**跨场景数据协同**是统一的最大收益。
- 统一的是底座、差异的是上层；**场景冲突用多任务结构（MMOE/PLE）缓解**，评测要三套指标一起看。
