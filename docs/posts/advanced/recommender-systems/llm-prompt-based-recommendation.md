## 为什么从 LLM 直接推荐开始

前面两节把 LLM 当「表示器」「特征工厂」，它仍在经典链路里打工。更激进的一派直接让 LLM「上岗」：**把推荐当成一个「自然语言任务」，让大模型直接给出推荐结果**——不再训练一个打分模型，而是写一段 Prompt，让 LLM 输出「该给这个用户推什么」。<span class="marginnote">LLM 直接推荐的价值在于「零样本/少样本」：不用为每个场景训练模型，写一段 Prompt 就能推荐；而且天然具备可解释性——LLM 不仅能说「推什么」，还能说「为什么」。代价是：LLM 不了解你平台的亿级物品、推理昂贵、且没有「行为数据」的直接经验。</span>

这一节讲直接推荐的两条路线：**Prompt 化推荐（让 LLM 排序/选品）** 与 **生成式推荐（让 LLM 生成推荐序列）**，以及它们的能力与局限。

## 1 Prompt 化推荐：把推荐写成「问答」

**Prompt 化推荐（prompt-based recommendation）** 把推荐问题包装成自然语言任务：构造一个 Prompt（提示词），输入用户信息与候选，让 LLM 输出推荐结果。

典型 Prompt 结构：

```
你是推荐系统。用户画像：{用户语义画像}。候选物品：{候选列表}。
请按用户兴趣从高到低排序，并给出排序理由。
```

- **用户侧**：用户画像、历史行为摘要（自然语言化）。
- **物品侧**：候选物品的标题/描述（语义化）。
- **任务侧**：「排序」「选 top-5」「解释为什么」。

**LLM 输出的是「决策 + 理由」**——推荐与解释一步到位，这正是经典推荐做不到的。

## 2 零样本 vs 微调：LLM 推荐的两种姿势

- **零样本（zero-shot）**：直接拿通用 LLM + 精心设计的 Prompt 做推荐。优点：上线快、无需训练；缺点：LLM 不了解「你平台」的特定偏好模式、候选规模受限、稳定性差。
- **少样本（few-shot）**：在 Prompt 里给几个「用户→推荐」的示例，让 LLM 模仿。比零样本准，但受「上下文窗口」限制。
- **微调（fine-tuning）**：用平台的行为数据微调 LLM（指令微调/偏好对齐，见 [[llm-finetuning]] 专题）。最准，但要训练成本与数据。

**工程现实**：纯零样本的 LLM 推荐常常「泛泛而谈」（推荐太热门、太通用）；微调后更懂平台，但成本逼近「再训练一个推荐模型」——所以工业上常「LLM 做主推、经典链路兜底」。

## 3 生成式推荐：推荐即「生成序列」

**生成式推荐（generative recommendation）** 更进一步：把推荐结果当成「序列生成任务」——LLM 自回归地「一个接一个」生成推荐的物品序列。

$$
\Pr(i_1, i_2, \dots, i_K \mid \text{prompt}_u) = \prod_{k=1}^{K} \Pr(i_k \mid i_{<k}, \text{prompt}_u)
$$

生成式推荐的优势与代价：

- **优势**：天然考虑「序列整体」——生成的列表是一个「连贯整体」，而非「逐个独立打分」；与 [[prm-generative-reranking]] 的生成式重排同源。
- **代价**：自回归解码慢（一次一个 token/物品）、候选要「先压缩成可生成的符号」（见 [[generative-retrieval-semantic-id-tiger]] 的语义 ID）、训练需要「序列式」数据。

## 4 公式解析：从「打分排序」到「生成决策」

把两代推荐的决策方式对比拆三步：

- **第一步，经典范式**：$a^* = \arg\max_a f_{\theta}(u, a)$——**对每个候选算一个分数，选分高的**。候选必须预先给定，模型不会「发明」候选。
- **第二步，生成范式**：$\pi^* = \arg\max_{\pi} \Pr(\pi \mid \text{prompt}_u)$——**LLM 直接「生成」整个推荐序列**。它可以从「词汇表」（语义 ID）里自主组合，不依赖预枚举的候选集。
- **第三步，本质差异**：经典范式是「**判别式 + 枚举**」（在给定候选里排序），生成范式是「**生成式 + 构造**」（从符号空间里构造结果）。**生成范式让「推荐」从「选择题」变成「填空题」**——更灵活，但也更难约束（要保证生成的 ID 真实存在、不越界）。

## 5 局限与工程现实

**局限**：

- **不了解你的行为数据**：通用 LLM 没有你平台的「点击/购买」先验，零样本推荐常「过于通用」。
- **推理贵、慢**：LLM 一次前向比「查表 + 浅模型」贵几个量级，难以在毫秒级线上链路里全量使用。
- **不可控**：LLM 可能「幻觉」出平台里不存在的物品，需要「生成结果校验 + 映射回真实候选」。
- **规模**：Prompt 只能塞下几百个候选，「全库生成」不现实。

**工程现实**：LLM 直接推荐目前更多用于「**新场景冷启、解释生成、用户画像总结**」这类「低延迟、高价值」的辅助位，而不是「亿级流量的主排序」——主排序仍由经典链路承担，LLM 与它结合（见 [[llm-traditional-recsys-integration]]）。

## 辨析｜Prompt 化推荐的「可控性」问题：三个必做的约束

让 LLM「自由发挥」做推荐，最危险的是「不可控」——LLM 可能说出平台里不存在的物品、违反业务规则、甚至「幻觉」出推荐理由。工程落地前三个约束必须做：

**约束一：候选「白名单」约束。** LLM 生成的推荐结果必须「映射回真实存在的候选」——不能让它「发明」物品。**做法**：Prompt 里明确「只能从给定候选里选」，且输出后用「候选校验」兜底（生成结果不在候选集内就丢弃/替换）。更稳的做法是「让 LLM 从候选列表里『挑』，而不是『想』」——把「开放生成」收敛成「封闭选择」。

**约束二：规则与商业约束。** 广告位、频控、运营置顶等业务规则，LLM 不懂。**做法**：LLM 生成「推荐意向」，最终展示前再过「规则层」——广告插位、频控、黑名单过滤（见 [[industrial-recsys-architecture]] 的策略层）。**LLM 是「建议者」，规则是「裁决者」**。

**约束三：一致性与稳定性。** 同一个用户、同一个场景，两次请求的 LLM 推荐结果应该「基本一致」——但 LLM 有「采样随机性」（温度高时输出不稳定）。**做法**：推荐场景用「低温度/确定性解码」（temperature 设为 0 或很小），或对「同一请求」做「多次生成 + 多数投票」，用确定性换取可复现。

**一个评估提醒**：LLM 直接推荐的效果要「跟经典基线比」——很多场景 LLM「说得头头是道」，但离线指标（Recall/NDCG）打不过「训练好的双塔 + 精排」。**「可解释的漂亮」不等于「效果更好」**——LLM 推荐上线前，先跑「同样的数据、同样的指标」与经典链路对比。

**补充｜Prompt 设计的「结构化」与「few-shot 示例」**：Prompt 化推荐的「效果」高度依赖「Prompt 怎么写」，三个设计要点：

**1. 用「结构化 Prompt」而非「自由散文」**：把「用户信息」「候选列表」「任务指令」分块写清，比「一段话描述」更稳——**「结构化输入」让 LLM 的解析更可靠**。候选列表要给「编号 + 标题 + 一句话描述」，让 LLM「对着编号选」。

**2. 用 few-shot 示例「校准输出格式」**：给 1~3 个「输入 → 期望输出」的示例，LLM 会「照着格式来」——**「示例不仅教内容，更教格式」**。示例里的「排序逻辑」要「展示业务偏好」（如「把与用户最近兴趣相关的排前面」），LLM 会「模仿这个逻辑」。

**3. 输出要「可解析」**：让 LLM「只输出候选编号、不要多余文字」——**「解析友好」是 Prompt 设计的硬要求**。输出格式（JSON/编号列表）要「提前约定」，解析失败要「有兜底」（回退到精排原序）。

**一个提醒**：Prompt 的「小改动」可能带来「大效果变化」——**Prompt 也要「版本管理」与「A/B 实验」**，像「模型参数」一样对待。**「Prompt 是新的超参数」**——这句话在 LLM 推荐里尤其成立。

## 6 小结

- **LLM 直接推荐**把推荐包装成「自然语言任务」：Prompt 化让 LLM 排序选品，生成式让 LLM 自回归生成推荐序列。
- 三种姿势：**零样本（快但泛）、少样本、微调（准但贵）**。
- 生成范式把推荐从「在候选里打分」变成「从符号空间生成」——更灵活、更整体，但难约束。
- 局限：不了解行为先验、推理贵、可能幻觉；**工业上常用在辅助位，主链路仍是经典推荐 + LLM 结合**。
