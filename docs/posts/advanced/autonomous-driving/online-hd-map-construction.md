## 为什么从在线矢量地图开始

上一节我们把「规则感知」讲完了——信号灯、交通标志，都是把环境里的**规则**翻译成机器能读的格式。但规则还藏在另一个地方：**路网本身**。车道线在哪、中心线怎么弯、停止线在哪、路口怎么连通，这套「道路拓扑」过去全靠高精地图离线制作、定期下发。可地图要覆盖新城市、要反映施工改道、要跟得上每一个路口的新画法，离线流程天生慢半拍。

于是有了**在线矢量地图构建**：让车自己、实时地、把相机（和可选的 LiDAR）看到的车道结构，直接画成一张矢量地图——不是像素栅格，而是「线、点、多边形」组成的地图元素。<span class="marginnote">「矢量 vs 栅格」是地图表达的两条路线：栅格（BEV 语义图）像位图，清楚但占内存、不结构化；矢量像向量绘图，省空间、直接对接规划器的坐标系。规划器要的不是「这块是车道」，而是「这条中心线的方程」。</span>这一节讲两条代表性路线：**HDMapNet**（先栅格、再矢量化）和 **MapTR**（端到端直接预测矢量），它们是 2021–2023 年在线建图的主线，也是后来无图智驾方案的技术底子。

## 1 为什么要把「地图」也变成实时感知

先分清两个层次，避免一上来就晕：

- **离线高精地图**：用专业采集车（LiDAR + 相机 + RTK）把城市扫一遍，人工标注，质检发布。精度厘米级、要素完整，但成本极高、覆盖有限、更新周期以月计。下一节《高精地图的要素、格式与制作流程》专门讲它。
- **在线矢量地图**：用自车传感器在行驶中「现场画图」，输出当前视野内的车道结构。它不需要提前采图，天然覆盖新路与施工区，还能逐帧刷新——代价是精度与视野受限于传感器。

两者不是替代关系，而是互补：离线地图提供「全局拓扑 + 语义先验」，在线建图提供「当前道路的实时矢量」。无图派（如更强调在线建图的一派）希望在线结果足够可靠，从而摆脱对离线高精地图的依赖——这个争论我们留到《高精地图派 vs 无图派之争》再展开，这里先把「在线画图」这件事的技术难度看清楚。

在线建图难在哪？三个问题：

1. **输入是高维的**：多路相机的图像（或点云），要统一到以自车为中心的 BEV 空间。
2. **输出必须是结构化的**：车道边界是「折线」，车道是「多边形」，不能输出一堆像素就交差——规划器要的是元素的拓扑与精确坐标。
3. **元素之间纠缠**：同一块区域里，左边界、右边界、中心线、停止线、路沿同时存在，模型要把它们分开，还不重不漏。

还有一个**拓扑**层面的隐性要求：画出的线不能只是「形状对」，还得能回答「相邻两条车道是否连通」「这条路能不能左转」这类问题。<span class="marginnote">规划器要的其实不是线，而是<strong>车道级拓扑图</strong>：节点是车道段，边是可达关系。在线建图输出的折线只是「画布」，拓扑推理（把线织成图）是紧随其后的另一半工作，本专题《行为规划》与《Frenet 路径规划》都会把这张图作为输入。</span>HDMapNet 与 MapTR 的第一版都只把「画线」做好，拓扑留给后处理与下游——记住这条分工，后面看无图方案就不会被「画了线 ≠ 能导航」绕晕。

HDMapNet 和 MapTR 分别用「两段式」和「端到端」两种哲学回答这三个问题。

## 2 HDMapNet：先出栅格、再矢量化

**HDMapNet**（清华大学，ICRA 2022）的思路很朴素：**先让网络把场景画成 BEV 语义栅格，再用几何后处理把栅格「矢量化」**。

- **第一步，BEV 特征**：多路相机图像经共享编码器提特征，用类似 LSS 的显式深度估计（或可学习的视角变换）投影到 BEV 网格；若车上装了 LiDAR，还可以把点云 BEV 特征与相机特征融合，显著提升远距离与夜间性能。<span class="marginnote">「相机 + LiDAR 双通道喂 BEV」正是本专题《多传感器融合》里「特征级融合」的实战版——HDMapNet 的相机分支与 LiDAR 分支在 BEV 空间对齐后拼接，属于同质特征融合。</span>
- **第二步，语义与实例分割**：BEV 特征接三个头——语义分割（每个像素是「车道边界 / 车道线 / 路沿 / 可行驶区域」哪一类）、实例分割（区分「这是第几条车道边界」）、以及方向预测。
- **第三步，矢量化后处理**：这是最「手工」的一步。对每个实例的 mask，用**中心线提取**（如距离变换 + 骨架化）抽出一条像素骨架，再把骨架转成折线——先抽稀（保留拐点）、再用最小二乘做直线/曲线拟合，必要时用三次样条平滑。<span class="marginnote">「像素骨架 → 折线 → 样条」是图像处理里的老手艺，本专题第六章《2D 目标检测》讲过的后处理（NMS、边框回归）是「框」，这里做的是「线」。从框到线，是从检测到地图的形态跃迁。</span>

HDMapNet 的价值在于把问题「立了起来」：BEV 语义分割 + 实例 + 矢量化后处理，这套范式清晰、可增量改进，2022 年前后大量工作沿它展开。它还有一个容易被忽略的贡献：把「在线建图」变成了一个**可训练、可评测的机器学习问题**，公开数据集（nuScenes、Argoverse 2）上有了统一的真值格式，后来者才能公平地比较「谁的线画得准」。但它的短板同样明显：**矢量化依赖一堆手工规则**（骨架化参数、拟合阈值、断点合并），每换一个场景就要调；而且整条链路不是端到端的，栅格阶段的小错会在后处理里被放大成线段的错位——语义分割在 BEV 边缘上的「毛边」，经骨架化后可能变成折线的「锯齿」，拟合参数就得为「锯齿」服务，进而损失直线精度。

这条「栅格打底」的路线还带一个数据成本问题：**像素级分割标签很难标**。要在 BEV 栅格上逐像素标「这是车道边界」，标注员得在俯视图上描一圈又一圈的边界；而 MapTR 式的矢量真值只需要「点出每条线的控制点」，标注成本低一个量级。<span class="marginnote">标注成本决定数据闭环的飞轮速度——这条规律在后面《数据闭环与 4D 标注》一节会反复出现：模型能用的「弱监督」越强，产线扩数据越便宜。</span>这是端到端矢量路线在工程上「弯道超车」的隐形原因之一。

## 3 MapTR：把地图元素当集合直接预测

**MapTR**（华为诺亚，ICLR 2023）换了一个更「优雅」的姿势：**不画栅格，直接回归矢量元素**。它的洞见是一句话：**地图元素本质上是「一组有序点」**——一条车道边界是折线，一个路面元素是多边形，都可以看成点的序列。

于是问题变成了：**从 BEV 特征出发，预测出若干个「点集实例」，每个实例带一个类别（车道边界/中心线/路沿/停止线……）**。这听起来和 DETR 式目标检测很像——确实，MapTR 就是**把「矢量地图元素」当成和「框」平级的检测目标**，用 Transformer 的集合预测范式来做。

但地图元素有一个框没有的麻烦：**点序等价（permutation equivalence）**。一个框有 4 个角的固定顺序；而一条折线，你从这头画和从那头画、起点选在哪个点，画出来是**同一条线**。<span class="marginnote">一张多边形还有一个「顶点是否共线」的冗余：多一个落在边上的顶点，画出的形状不变。所以 MapTR 允许预测点数量与真值不同，多余的点通过「填充 + 匹配」吸收。这个「等价类」思想在数学里很正——同一条折线的所有顺序表达构成一个等价类，模型学的是一类而不是一个实例。</span>如果网络把点顺序当成固定目标来训，同一个真值会对应无数个「正确」输出，训练直接震荡。

MapTR 的解法是**在匹配阶段显式枚举等价表达**：对每个真值点集，把所有「合法」的顺序（起点可取任意点、方向可正可反）都纳入匹配候选，匈牙利匹配在「预测实例 ↔ 真值实例 ↔ 点对齐」的三层结构上完成。为了让网络能「先定实例、再定点」，MapTR 用了**层级查询**：一组 instance-level query 先决定「有几个元素、各是什么类别」，每个实例再派生出一组 point-level query 去回归具体坐标。instance query 与 point query 在注意力里上下联动——前者像「要画几条线」的提纲，后者像「每条线的每个控制点在哪」的逐点落笔。

MapTR 的 BEV 特征本身也值得提一句：它采用「Transformer 编码器 + 多相机采样」的组合，与上一节 BEVFormer 的空间交叉注意力一脉相承——每个 BEV 位置主动去各路相机采特征，把 6 路环视图像压缩成一张统一画布。这也解释了为什么在线建图与 BEV 感知是「同源技术」：它们共用同一套「多相机 → BEV」的骨架，只是输出的头不同——检测头出框、分割头出栅格、建图头出点集。理解这一点，整个感知栈就被一根线串起来了。

## 4 公式解析：匈牙利匹配与点序等价

MapTR 的损失分两层：**实例层**（哪条预测线对应哪条真值线）用匈牙利匹配，**点层**（线内点怎么对齐）用点序等价的最小距离。先看点层，这是 MapTR 最精妙的地方。下图把这两层画在一起——上半部分是「点序等价」：同一条折线正画、反画是同一个真值；下半部分是「实例层匹配」：预测实例与真值实例之间求全局最小代价的双射。

![MapTR 的两层嵌套匹配](/images/autonomous-driving/online-hd-map-construction-1.svg)

假设一条真值车道边界有 $N$ 个点，预测出 $M$ 个点（$M \le N$，不足的补 padding 到 $N$）。由于**起点可以任选、方向可正可反**，这条真值折线共有 $2N$ 种「合法顺序」表达，记为集合 $\Pi$。点层距离定义为这 $2N$ 种表达里，与预测点集最接近的一种：

$$
\mathcal{L}_{\text{pos}}(\hat p, p) = \min_{\pi \in \Pi} \; \sum_{k=1}^{N} \left\lVert \hat p_k - p_{\pi(k)} \right\rVert
$$

- **第一步，先理解 $2N$ 从哪来**：一条 $N$ 点折线，起点有 $N$ 种选法；固定起点后，方向有正反 2 种——这就是 $2N$ 种合法表达。枚举它们，等于问：「预测的这条线，和真值这条线，长得最像的『画法』是哪一种？」这个 min 把「顺序」这个无关变量彻底消掉——网络只需把形状画对，不必担心从哪个点起笔。
- **第二步，理解 $\left\lVert \cdot \right\rVert$**：这是逐点的欧氏距离。把「线对得齐不齐」量化成「对应点离多远」。若预测线整体向右偏 20 cm，距离和就大约等于 $N \times 0.2$ m——损失会明确告诉网络「往左挪」。
- **第三步，放进实例层**：把点层距离 $\mathcal{L}_{\text{pos}}$ 与类别损失、方向损失相加，得到「预测实例 $i$ 配给真值实例 $j$」的匹配代价：

$$
\mathcal{L}_{\text{match}}(i, j) = \mathcal{L}_{\text{cls}}(i,j) + \alpha\, \mathcal{L}_{\text{dir}}(i,j) + \beta\, \mathcal{L}_{\text{pos}}(i,j)
$$

预测实例与真值实例各成「两列」，代价矩阵填满后，用**匈牙利算法**求全局最小代价的双射——这一步保证「每条预测线恰好归到一条真值线」，不会两条线抢同一个真值。训练损失再对匹配上的实例对求和，未匹配的预测线额外受分类惩罚（学会「别乱画」）。

**辨析｜易错点：** 很多人把 MapTR 的匹配理解成「点对点最近邻」，那是错的——**实例匹配与点匹配是嵌套的两层**：外层匈牙利决定「谁对应谁」，内层 min 处理「同一条线的不同画法」。把两层混成一层，模型会拿「预测线的第三个点」去对「真值线的第一个点」，形状对了也训不收敛。另外，点层 min 是对 $2N$ 种顺序**穷举**求的，$N$ 不能太大（MapTR 里典型 $N=20$ 左右），否则枚举成本失控——这是它不用更长折线的原因之一。

## 5 HDMapNet vs MapTR：两条路线的对比

把两条路线并排看，各自的取舍一目了然：

| 维度 | HDMapNet | MapTR |
| --- | --- | --- |
| 输出形式 | BEV 语义栅格 → 后处理矢量化 | 端到端直接回归矢量点集 |
| 矢量化方式 | 骨架化 + 折线拟合（手工规则） | 集合预测 + 点序等价匹配（可学习） |
| 监督 | 像素级分割标签 | 矢量级真值（点序列） |
| 端到端性 | 否，后处理不可微 | 是，全链路可微 |
| 元素边界 | 靠实例分割区分 | 靠实例查询（query）区分 |
| 优点 | 直观、易增量改进 | 结构化输出干净、少手工规则 |
| 短板 | 手工后处理脆弱、误差累积 | 训练复杂、点序枚举有成本 |

MapTRv2（CVPR 2023）在这条路上继续加了三分力：用一个轻量 BEV 编码器替代笨重的 Transformer 编码器、加入**辅助语义监督**让 BEV 特征更干净、并联合预测**元素的高度**把地图从 2D 抬到 3D。<span class="marginnote">「先 2D 拓扑、再补 3D 高度」是地图要素进化的通用路径：下一节《高精地图的要素》里，真实高精地图的车道也是有坡度、有曲率的 3D 曲线，在线建图只是把这条路径跑快。</span>到今天，「在线矢量化 + 车道拓扑推理」已经是城市 NOA 方案里离线地图缺席时的主力替补。

最后给一个「值得记住的工程判断」：**在线建图不是要取代离线地图，而是把「地图更新」从月级降到秒级**。高精地图提供长期稳定的全局骨架（哪条路通向哪），在线建图负责当前路口的即时形状（今天这条路画了几条线、施工改道怎么走）。两者结合时，系统先在地图坐标系里「定锚」，再用在线结果「修正与补盲」；只靠在线建图做全局导航会因视野有限而迷失，只靠离线地图又会因更新滞后而误判。这个「先验 + 实时修正」的分工，与上一节「地图预置标志 + 视觉验证」是同一个思想的一体两面。

从方法论上再看一眼：MapTR 把「画地图」重新定义成「预测有序点集」，本质上是在问**「什么样的输出表达，让学习问题变得最容易」**。栅格不是不能学，只是「从栅格到线」的手工步骤制造了梯度断层；点集把「线」当作一等公民，让误差直接以「几何距离」传播。这种「先选对输出表达、再谈网络结构」的思路，贯穿整个感知栈——从框到栅格、从栅格到点集，每一步选择都在回答同一个问题。

## 6 小结

- **在线矢量地图构建**让车用自身传感器实时画出车道结构，补充离线地图的覆盖盲区与时效短板。
- **HDMapNet** 走「BEV 语义分割 → 实例分割 → 骨架化 + 折线拟合」的两段式路线，直观但后处理手工且脆弱。
- **MapTR** 把地图元素视为**有序点集**，用 Transformer 集合预测直接回归矢量，端到端可微。
- **点序等价**是地图元素独有的挑战：起点任选、方向可反，靠 $2N$ 种合法表达的 min 距离消掉顺序无关变量。
- 匹配是**「实例层匈牙利 + 点层 min」的两层嵌套**，误当成一层会训不收敛。
- 在线建图与 **BEV 感知同源**：共用「多相机 → BEV 特征」骨架，只是输出头不同；它与离线高精地图是「先验 + 实时修正」的分工，而非替代。
- 方法论收获：**先选对输出表达（栅格 / 点集），再谈网络结构**——输出表达决定学习问题好不好解。

在下一节，我们跳出「在线实时画」的视角，回到那个更成熟的基线：**高精地图的要素、格式与制作流程**——真实产品里地图到底有哪些层、用什么格式存、又是怎么造出来的。这条基线，也是所有「在线建图」想要对标与超越的标尺。
