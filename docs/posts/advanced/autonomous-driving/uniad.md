## 为什么从 UniAD 讲起

上一节说第三代端到端把感知、预测、规划统一进一个 Transformer。**UniAD（Planning-oriented Autonomous Driving，2022）** 是这一范式的开创性代表作，也是过去几年自动驾驶论文中被引最多的架构之一。它的核心主张简洁而深刻：**过往的「多任务感知」把检测、跟踪、建图当成并列任务一起训练，但自动驾驶的终极目标是「规划」——所有任务都应该围绕规划来组织**。

UniAD 的价值不只是「又一个刷榜模型」，它回答了三个架构级问题：**多任务之间如何共享特征？任务之间如何传递信息？规划如何真正消费感知与预测？** 本节拆解 UniAD 的架构设计，讲清「规划导向」到底意味着什么。

## 1 从「多任务并列」到「规划导向」

在 UniAD 之前，「多任务学习」在自动驾驶里已很常见——一个 BEV 骨干上挂检测、分割、预测等多个头，任务之间只共享骨干、各算各的损失。UniAD 指出这种「并列多任务」的两个问题：

- **任务间不传递信息**：检测结果不用来帮助预测，预测结果不用来帮助规划——它们只是「恰好共享一个骨干」的独立任务。
- **规划被边缘化**：规划往往只是其中一个头，甚至不做；模型优化的是「感知准不准」，而不是「车开得好不好」。

UniAD 的回应是**「规划导向（planning-oriented）」**：让任务按「感知 → 预测 → 规划」的上下游关系组织，**每个任务都输出给下游任务消费**，且所有任务的最终目的是服务规划。这重新定义了多任务学习的组织方式——从「并列」到「流水线」，从「感知中心」到「规划中心」。

<span class="marginnote">规划导向的深层含义是<strong>「优化目标的对齐」</strong>：如果感知模块的错误不一定会导致规划变差（规划器很鲁棒），那感知就不该被过度惩罚；反过来，如果预测的微小偏差会让规划决策翻转，那预测就该被重点优化。UniAD 通过「下游消费上游、梯度全链路流动」让这种对齐成为可能——<strong>每个模块不再是「自己准就行」，而是「对下游有用才行」</strong>。</span>

## 2 架构总览：四个「tracking query」贯穿全局

UniAD 的架构可以用一条主线概括：**一组可学习的 query 像「档案袋」一样贯穿全程**。

**Track query**（跟踪查询）：代表「场景里每个被跟踪的目标」。在感知阶段被初始化、更新，携带目标的特征。
**Map query**（地图查询）：代表「道路结构」——车道、路缘、路口，从 BEV 特征里解码出在线地图。
**Motion query**（运动查询）：代表「每个目标的未来轨迹假设」，由 Track query 衍生，做轨迹预测。
**Occ query / Planning query**（占用/规划查询）：在运动预测之上做占用预测与自车规划。

关键设计是**query 的「接力」**：Track query 完成跟踪后，它的特征被传给 Motion query 做预测；预测结果又传给占用预测与规划。**信息以「查询特征」为载体在任务间流动，而不是靠重新计算**——这是「统一」二字的架构学含义。

## 3 四个任务模块：检测跟踪 → 建图 → 预测 → 规划

UniAD 由四个主干任务组成一条流水线：

1. **检测与跟踪（Track）**：从 BEV 特征解码目标，用 tracking query 维持时序一致性，输出每个目标的类别、位置、速度、朝向。这是整条链路的「眼睛」。
2. **在线建图（Map）**：用 map query 从同一 BEV 特征解码车道线、路缘、行人横道，替代对离线高精地图的依赖——「地图也是感知出来的」。
3. **轨迹预测（Motion）**：以 track query 为条件，用 motion query 预测每个目标的未来轨迹（多模态候选 + 概率）。
4. **占用预测与规划（Occ + Plan）**：把轨迹预测结果渲染成**未来占用网格**（每个目标未来会占据的空间），再让规划 query 在「避开占用」的约束下生成自车轨迹。

**规划是终点，前面的所有任务都在为它提供「避开什么、跟谁、等谁」的输入**。这条流水线在架构上与经典模块化栈同构，但区别在于——所有模块共享一个骨干、共享特征、联合训练。

<span class="marginnote">UniAD 的「占用预测 → 规划」设计值得单独强调：<strong>它把预测结果先「渲染」成未来占用（空间表达），再让规划在这个占用上求解</strong>。这一步把「离散轨迹」翻译成「连续空间约束」，让规划天然避开所有可能的未来占据——比直接消费轨迹候选更稳健，也更接近「时空联合规划」的端到端版本。这个「预测→占用→规划」的接口设计，被后续很多方案沿用。</span>

## 4 训练与评测：为什么它全面超过模块化基线

UniAD 在 nuScenes 数据集上的评测结果是标志性的：在跟踪、建图、预测、规划四项任务上，**同时超过所有独立最优的单任务模型**——这不是「一鱼多吃」的巧合，而是「信息共享」的系统性收益。

为什么统一架构能全面超过单任务最优？三个机制：

- **特征复用**：感知学到的 BEV 特征被所有任务共享，而不是每个任务重新提特征。
- **梯度互馈**：规划任务的梯度反传到感知与预测，让感知学到「对规划有用的特征」而非「对检测指标有用的特征」。
- **信息无损**：中间表示在模块间以特征传递，不经过离散化（检测框、轨迹点）造成的丢失。

UniAD 也确立了「端到端规划评测」的规范：报告 **碰撞率、L2 位移误差** 等规划级指标，而不是只看感知 mAP——**「车开得好不好」成为衡量感知与预测的最终标尺**。

## 5 公式解析：UniAD 的多任务联合损失

UniAD 的损失由各任务的损失加权求和，训练目标是「全链路最优」而非「单任务最优」：

$$
\mathcal{L} = \lambda_1 \mathcal{L}_{\text{track}} + \lambda_2 \mathcal{L}_{\text{map}} + \lambda_3 \mathcal{L}_{\text{motion}} + \lambda_4 \mathcal{L}_{\text{occ}} + \lambda_5 \mathcal{L}_{\text{plan}}
$$

- **第一步，看每一项**：$\mathcal{L}_{\text{track}}$（检测跟踪的框回归/分类损失）、$\mathcal{L}_{\text{map}}$（地图分割/点集损失）、$\mathcal{L}_{\text{motion}}$（预测的 minADE/NLL）、$\mathcal{L}_{\text{occ}}$（占用网格的损失）、$\mathcal{L}_{\text{plan}}$（规划轨迹与真值的 L2）。**每个任务都有独立的监督信号**——这是「可审计」的来源。
- **第二步，看权重 $\lambda$**：$\lambda_i$ 平衡各任务的收敛节奏。规划损失占比通常较大（它是终点目标），感知损失保证中间表示不塌缩。**权重设计是训练稳定性的关键**——感知先收敛、规划后收敛，可能需要分阶段或调整权重。
- **第三步，看梯度流**：$\mathcal{L}_{\text{plan}}$ 的梯度沿「规划 → 占用 → 预测 → 跟踪」反向传播到所有上游模块——**这就是「规划导向」的数学机制**：规划的错误会纠正感知与预测的特征。
- **第四步，看评测闭环**：训练后报告的不只是各任务损失，而是**规划碰撞率**——把「规划导向」从训练口号变成评测指标。训练目标与评测指标的一致，是 UniAD 范式最优雅的地方。

## 6 UniAD 架构的「工程启示」与局限

UniAD 的贡献不止于指标，更在于它示范的「架构工程」几条原则，值得独立拎出来：

- **「一个骨干、多任务头」的统一**：让感知、预测、规划共享同一个骨干，特征复用带来收益——**「共享表征」是统一的本质**，比「挂在同一个框架下」重要得多。
- **「query 接力」的信息流**：tracking query 传给 motion query、再传给规划——**信息以「带语义的载体」在任务间流动**，而不是「重新算一遍」。这是「统一」的架构学实现。
- **「规划导向」的损失权重**：所有任务服务规划，规划损失的梯度回传贯穿全链路——**「终点任务」的反馈塑造「上游任务」的特征**，这是「导向」的数学机制。

UniAD 的局限也同样清晰：**大模型 + 多任务的算力/数据需求极高**（训练成本远超单任务）、**端到端微调的「灾难性遗忘」**（新任务加入可能破坏旧任务）、**在真实车端推理的实时性**尚需验证。它证明了「统一」的可行性，但「统一」的工程化还有距离。

| 启示 | 工程含义 |
| --- | --- |
| 共享表征 | 多任务收益的核心来源 |
| query 接力 | 信息流动的语义载体 |
| 规划导向 | 终点反馈塑造上游特征 |

<span class="marginnote">UniAD 真正的历史地位，是它把「端到端」从「一个黑箱映射」变成了「<strong>一个有结构、可审计、可导向的统一系统</strong>」——<strong>「统一」不再是「没有中间步骤」，而是「中间步骤也是可学习的语义模块」</strong>。这个「端到端的再定义」，深刻影响了 VAD、以及后来所有「端到端大模型」的设计。</span>

UniAD 之后，端到端架构的演进方向已经清晰，三个趋势值得留意：

- **更统一的骨干**：从「BEV 特征」走向「query/稀疏表示」（VAD），算力更省、接口更语义化——**「统一的粒度」在变细**；
- **更深的规划导向**：从「规划作为任务之一」走向「规划作为唯一终点」，预测/占用都为规划服务——**「导向的强度」在加深**；
- **更强的数据依赖**：统一大模型需要海量「场景-真值」数据，数据飞轮成为端到端竞争的核心——**「模型的成败」越来越取决于「数据的规模」**。

这三个趋势共同指向：**端到端的「下半场」是「数据与工程」的竞争，而非「架构」的竞争**——架构的「统一」已经完成（UniAD 是里程碑），剩下的「谁能把数据、算力、工程整合得最好」，决定谁能把「统一的架构」变成「量产的能力」。**「论文拼架构，量产拼数据」**——这是端到端演进给产业的最大启示。

**辨析｜易错点：** 「多任务共享骨干 = 多任务都更好」不必然——共享骨干可能「任务间干扰」（感知与规划的梯度互相拉扯）。UniAD 通过「规划导向的损失权重」缓解，但「共享的副作用」并未消失。**「共享」是「收益与干扰的权衡」**，需要精心的损失设计才能「正收益」。

## 7 小结

- UniAD 提出**「规划导向」**：所有任务围绕规划组织，任务间以 query 特征传递信息。
- 架构是一条**跟踪 → 建图 → 预测 → 占用 → 规划**的统一流水线，共享骨干、联合训练。
- **tracking query 贯穿全局**是「统一」的架构学机制，任务之间不再重新计算特征。
- 「预测 → 占用 → 规划」的接口设计，让规划在空间约束上求解，比消费轨迹候选更稳健。
- 联合训练让统一架构**全面超过独立模块基线**，并确立了以碰撞率为中心的规划级评测。
