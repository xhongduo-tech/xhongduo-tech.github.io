## 为什么从时序融合开始

前几节的感知方案，几乎都在回答同一个问题：**给定这一帧图像/点云，世界是什么样**。但真实世界不是一帧一帧的静照，而是一条连续的河。车辆在动、目标在动、遮挡在变化——**单帧感知天生短视**：一个目标被卡车挡住的那一瞬，单帧检测器就「看不见」它了；一辆被误检的车，下一帧可能又突然消失又出现，输出的轨迹在时间上剧烈抖动。自动驾驶的规划与决策需要的是**稳定、连续、可预测**的世界理解，而不是一帧一帧「失忆」的瞬时快照。<span class="marginnote">「时序」两个字贯穿自动驾驶的各个模块：感知要做时序融合，预测要基于历史轨迹，控制要用到前一拍的状态。理解时序融合，是理解「感知如何为预测铺路」的第一块砖——你会在预测专题看到这条线索被继续拉长。</span>

单帧感知的「失忆症」有三个具体症状：**闪烁**（同一个目标这一帧被检到、下一帧漏掉，框在时间上忽隐忽现）、**抖动**（同一辆静止的车，每帧的框位置与尺寸都在小幅漂移）、**断头**（目标被遮挡时轨迹直接断裂，重见时被当成新目标）。这三个症状全部源于「每帧从零开始推断」——下一帧的世界观不继承上一帧。时序融合要治的，正是这组病。

这引出了感知的第二个维度：**时间**。怎样让感知「带着记忆看世界」？这一节讲清楚时序融合的三种范式，再深入最省算力的代表——**StreamPETR**，它把时序融合做进了稀疏的 object query 里，被称为「流式感知」。

## 1 时序融合的三种范式

「用历史帧帮助当前帧」在工程里有三种由浅入深的做法：

**结果级时序（tracking）**：每一帧先独立检测，再用卡尔曼滤波/匈牙利匹配把框关联成轨迹。这是最传统、最便宜的做法，但它**不回头修正检测**——如果这一帧漏检了，tracking 只能靠运动外推硬撑，改不了「这一帧没看到」的事实。它治标，不治本。

**BEV 特征级时序**：把上一帧的 BEV 特征（或特征图）用自车运动变换（warp）到当前帧坐标系，与当前 BEV 特征拼接或做注意力，再一起解码。你学过的 **BEVFormer** 的 temporal self-attention 就是这条路的代表：网络在稠密的 BEV 网格上「读历史」。效果好，但**稠密特征×多帧**的记忆开销极大。

**查询级时序（query-based）**：不在稠密特征空间做记忆，而在**稀疏的 object query** 空间做记忆——让每个 query 自带「前世今生」，跨帧传播。这就是 **StreamPETR** 的路线。<span class="marginnote">DETR 系列把目标检测重新表述为「一组可学习的 object query 与特征做交叉注意力」，每个 query 就是一个潜在的检测实例。StreamPETR 的天才之处在于：既然 query 本来就是「携带信息的向量」，那就让它携带时间信息——历史 query 就是现成的记忆。</span>

三者的核心差别一句话：**结果级在「答案」上融合，BEV 级在「地图」上融合，查询级在「记忆」上融合**。融合点越靠前，能修正的东西越多，代价也越大；而查询级巧妙地用「稀疏」把代价压了下来。

## 2 StreamPETR 的核心机制：object query 的时间记忆

StreamPETR（ICCV 2023）是 PETR 家族的时序扩展。PETR 本身的特点是**没有显式 BEV**：用 3D 位置编码把图像特征「垫」进 Transformer，object query 直接与 2D 特征做交叉注意力就得到 3D 检测。StreamPETR 在它的基础上加了一个轻巧但关键的部件——**历史查询记忆库（memory queue）**。

它的工作方式像一条流水线：

1. 当前帧的图像特征进来，当前帧的 object query 与其做交叉注意力，得到当前检测；
2. 把当前帧的 query 状态（携带了「哪里可能有目标」的信息）**推进一个固定长度的队列**；
3. 下一帧处理时，队列里的历史 query 会**经自车运动补偿（ego-motion compensation）**被变换到当前帧坐标系，与当前 query 一起送入一个**时序自注意力（relation-aware temporal self-attention）**模块——当前 query 向历史 query「提问」，读取跨帧的记忆；
4. 队列尾部出队，保持长度恒定，计算量不随帧数增长。

```python
# StreamPETR 流式感知：记忆队列 + 时序自注意力（伪代码）
class StreamPETR:
    def __init__(self, queue_len=16):
        self.memory_queue = deque(maxlen=queue_len)   # 历史 object query 状态

    def forward(self, img_features, ego_motion):
        # 1. 当前帧 query 与图像特征做交叉注意力，得到当前检测
        queries = self.cross_attention(self.object_queries, img_features)

        # 2. 当前 query 状态经自车运动补偿后入队
        history = [self.warp(q, ego_motion) for q in self.memory_queue]

        # 3. 时序自注意力：当前 query 向历史 query「提问」
        queries = self.temporal_self_attention(queries, history)

        # 4. 队列尾部出队，长度恒定
        self.memory_queue.append(queries.detach())
        return self.class_head(queries), self.reg_head(queries)
```

为什么 query 状态能当记忆载体，而不是把历史特征图存下来？关键在于 query 是**任务相关的潜状态（latent state）**：它已经被训练成「这里大概有什么目标、在哪」的压缩表达，天然剔除了光照、纹理等与检测无关的冗余。存 query 等于存「结论的草稿」，存特征图等于存「原始证据」——前者量小且语义纯净，后者量大且噪声多。这让 query 级记忆在「省」的同时还「干净」。

这套设计回答了一个尖锐的工程问题：**为什么不在 BEV 特征上做时序融合？** 因为 BEV 特征是稠密的（几百×几百的网格×通道数），把它存上十几帧再融合，显存与计算都难以承受。而 object query 是稀疏的（通常几百个），**存 16 帧历史 query 的成本约等于存一帧稠密特征**——这就是 StreamPETR「用稀疏换记忆」的算力账本。

StreamPETR 还把记忆分成了**两层**：**短时记忆**是当前帧的图像特征，负责「看清当下」；**长时记忆**是记忆队列里的历史 query 状态，负责「记得过去」。两层的分工让网络既不会被瞬时噪声带偏，又不会因时间跨度太大而遗忘关键目标。队列长度（如 16 帧）就是长时记忆的容量——它直接决定了车辆在目标被遮挡多久之后还能把它「想」起来。这与你在大模型语境里熟悉的「上下文窗口」是同一类资源：记忆有长度，长度即取舍。

「流式」还有一个工程含义：模型按帧在线推理，每一帧只读一次记忆、输出一次结果，**不存在把整段视频离线重看一遍的奢望**。这要求时序注意力必须在单帧时延内完成，记忆队列必须可丢弃、可恢复——这些约束把 StreamPETR 塑造成「为实时而设计」的架构，与后面端到端专题里「帧间一致性」的问题直接相连。<span class="marginnote">这个权衡与你在数据结构里学过的「稀疏表示 vs 稠密表示」完全同构：稠密表示访问任意位置 O(1)，但空间开销大；稀疏表示只存有信息的地方，代价是「没有位置就没有记忆」。BEV 特征与 query 正是这对矛盾在感知里的具体化。</span>

## 3 公式解析：时序注意力如何「读记忆」

StreamPETR 的记忆读取本质是一次**时序自注意力**。设当前帧第 $q$ 个 query 的特征为 $z_q$，记忆库里有 $T$ 个历史帧的 query 状态，则一次时序注意力更新写成：

$$
z_q \;=\; \sum_{t \in \{\text{cur}, \text{hist}\}} \; \sum_{k} \alpha_{q,k,t} \, v_{k,t},
\qquad
\alpha_{q,k,t} \;=\; \text{softmax}_{k,t}\!\Big( \frac{q_q \cdot k_{k,t}}{\sqrt{d}} + \Delta\big(\text{warp}(e_{k,t})\big) \Big)
$$

逐项拆解：

- **第一步，区分角色**：$q_q$ 是当前 query 派生的**查询向量**，代表「我现在想知道的事」；$k_{k,t}$、$v_{k,t}$ 是当前帧与历史各帧所有 query 派生的**键与值**，代表「记忆库能告诉我的事」。$\sqrt{d}$ 是特征维度的缩放因子，防止点积随维度爆炸，这是注意力公式的标准归一化。
- **第二步，运动补偿**：$\text{warp}(e_{k,t})$ 把历史第 $t$ 帧 query 的位置编码 $e_{k,t}$ 用自车运动变换到当前帧坐标系——因为**车在动，历史帧的「前方」不是当前的「前方」**。$\Delta(\cdot)$ 把相对位置信息加进注意力得分，让网络既按「语义像不像」、又按「空间在不在同一处」去匹配记忆。
- **第三步，软读取**：$\alpha_{q,k,t}$ 对「当前 query 与每一条记忆的相似度」做 softmax，得到一组和为 1 的权重；$z_q$ 就是所有记忆值的加权平均。**权重大的记忆被读到，权重小的被忽略**——网络学会了「该记什么、该忘什么」。
- **第四步，读出直觉**：如果一个目标上一帧被遮挡，它的历史 query 状态里仍存着「这里曾经有个目标」的信息；当前帧注意力把它捞回来，被遮挡的框得以延续。**这就是「带着记忆看世界」的数学形态**——不是把过去硬拼进现在，而是让现在按相似度去检索过去。

**辨析｜易错点：** 时序注意力 ≠ 简单的「多帧特征拼接」。拼接是等权重的堆叠，而注意力是**数据相关的软读取**——同一条记忆在「目标刚转弯」时权重很小，在「目标被遮挡」时权重很大。这也是为什么 query 级时序能比拼接式时序更好地处理遮挡与突变：**记忆的取舍是学出来的，不是写死的**。

顺带一提，这套「查询检索记忆」的机制，与你在大模型里见到的 **KV-Cache** 是同构的：过去的键值被缓存，新的查询只与缓存交互，而不是把整个历史重新计算一遍。理解 StreamPETR 的时序注意力，等于提前预习了大模型推理加速的核心思想——这也是本博客把自动驾驶与「从极限到大模型」主线连起来的又一针脚。

## 4 单帧 vs 流式，BEV 时序 vs 查询时序

把三条路线放到一张对账表里，差异一目了然：

| 维度 | 单帧感知 | BEVFormer（BEV 特征时序） | StreamPETR（查询时序） |
| --- | --- | --- | --- |
| 记忆载体 | 无 | 稠密 BEV 特征 | 稀疏 object query |
| 记忆长度 | 无 | 1 帧 | 可到 16 帧（队列） |
| 遮挡鲁棒性 | 差（瞬时失忆） | 中 | 好（query 记住目标） |
| 计算/显存 | 最低 | 高（稠密×多帧） | 低（稀疏） |
| 是否需要显式 BEV | 部分需要 | 需要 | 不需要 |
| 在线流式部署 | — | 偏难 | 天然适合 |

**辨析｜易错点：** 别把「时序融合」与「跟踪（tracking）」混为一谈。跟踪是结果级的关联，**它修正不了漏检**；StreamPETR 的时序注意力在特征/查询级，**能在源头把被遮挡的目标「想起」来**。两者在量产里常常一起用——感知级时序负责「记得住」，跟踪级关联负责「连成线」——但它们是两个不同层级的记忆。

回到选型：BEVFormer 的时序融合更像「拿一张地图不断覆盖更新」——信息密、覆盖全，但贵；StreamPETR 更像「只记住几个关键人物的事」——省、快，但没记住的角落就是空白。真实的量产系统往往两者兼用：稠密 BEV 负责「全景底图」，稀疏 query 负责「重点目标的连续跟踪」，把「全」与「省」配成组合拳。

还有一个被低估的收益——**流式感知天然服务预测**：稳定的 object query 状态本身就是一条「半成品的轨迹」，同一目标在不同帧的 query 状态构成了它的历史序列，下游预测模块可以直接在这些状态上接一层时序网络，而不必从头做数据关联。这也解释了为什么端到端与预测方向的研究者都偏爱查询级表示：**它把「感知的记忆」与「预测的历史」统一进了同一种数据结构**，为后面预测专题与端到端专题埋下了伏笔。

再往深一层看，流式感知揭示了一个方向性的判断：感知正在从「每帧重算的静态模块」变成「持续维护的在线状态」——这与控制里的状态估计（卡尔曼滤波）殊途同归，也与端到端系统里「一个模型维护整个驾驶状态」的野心遥相呼应。**感知的「时序化」，是模块化栈向端到端演进路上最自然的中间态**。

## 5 小结

- **时序融合三范式**：结果级（tracking，治标）、BEV 特征级（BEVFormer，稠密记忆）、查询级（StreamPETR，稀疏记忆）；融合点越靠前越能修正漏检，代价越大。
- **StreamPETR 的核心**：把历史 object query 存进记忆队列，经**自车运动补偿**后与当前 query 一起做**时序自注意力**——在稀疏 query 空间实现跨帧记忆，算力成本≈单帧。
- 时序注意力公式 $z_q = \sum_t \sum_k \alpha_{q,k,t} v_{k,t}$ 的直觉：**按相似度软读取记忆，权重是学出来的**。
- **稀疏 vs 稠密**的账本：存 16 帧历史 query ≈ 存一帧稠密 BEV 特征，这是「用稀疏换记忆」的根本原因。
- 时序融合 ≠ 跟踪：前者在特征/查询级修正漏检，后者在结果级关联；量产两者并用。
- 流式感知的「在线状态」思想，是模块化栈向端到端演进的自然中间态；query 记忆与 LLM 的 KV-Cache 同构。
- 单帧感知的闪烁、抖动、断头三症状，是时序融合要治的病；query 是「结论的草稿」，存它比存特征图更省更干净。

在下一节，我们把视角从「障碍物」转向「道路结构」：车辆要在车道内行驶，就需要知道**车道线在哪、哪里能走**——这就是**车道线与可行驶区域检测**，也是无图/轻图路线里「在线建图」的第一块拼图。
