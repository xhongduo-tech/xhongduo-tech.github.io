## 为什么从沙箱开始

上一节讲了三原则：最小权限、动作确认、可审计。但原则要靠「机制」落地——**沙箱（sandboxing）** 就是那个「技术上的笼子」。经典系统安全早就明白：**不能信任「运行中」的程序，于是把它关进受限环境**——浏览器把网页 JS 关进沙箱、操作系统把进程隔离在容器里。Agent 安全把这个思想应用到智能体：**让模型在一个「无论如何都不能逃出、不能触及真实关键资源」的受限环境里运行**。<span class="marginnote">沙箱的哲学与「对抗训练」不同：对抗训练赌「模型不会被骗」，沙箱不赌——<strong>它默认「模型可能会被劫持」，于是设计一个「即便被劫持也无法造成大损害」的环境</strong>。这是安全工程「以最坏情况为假设」的经典思维。</span>

这一节讲沙箱的两大支柱：**运行环境的隔离**（让工具执行碰不到真实系统）与**能力限制**（让模型本身不被赋予超过任务所需的能力），以及两者如何组合成 Agent 安全的现实防线。

## 1 运行环境隔离：把「执行」关进笼子

Agent 的「危险」大多来自「工具执行」——尤其是「执行代码」「读写文件」「访问网络」。运行环境隔离把这些执行动作放进「受限沙箱」：

**进程级沙箱**：Agent 的代码执行放在「独立容器/虚拟机」里，与主系统隔离。即使模型执行了恶意代码，代码也只能影响沙箱内部——读不到主系统的文件、碰不到真实的网络。Docker 容器、微虚拟机（microVM）、WebAssembly 是常见的实现载体。
**网络隔离**：沙箱内默认「无网络」或「白名单网络」——Agent 若要访问外网，必须通过「受控的代理」而非直连。这能阻止「注入的指令把数据外带」。
**文件系统隔离**：沙箱内的文件系统是「虚拟的」——Agent 只能读写「被授权的目录」，主系统的文件在它「视野之外」。**「看不见，就破坏不了」**——文件系统隔离把「破坏半径」物理化。<span class="marginnote">网络与文件系统隔离是沙箱的「两把锁」：网络隔离防「数据外带」，文件系统隔离防「数据破坏」。一个理想的 Agent 沙箱，是「<strong>模型能做的事 = 任务需要的事 = 沙箱允许的事</strong>」三者重叠的那一小块。</span>

**沙箱的边界**：隔离不是绝对的——「沙箱逃逸」（通过漏洞突破隔离）是经典攻击方向；而且「模型读取外部内容」这件事本身就发生在沙箱内，注入进来的指令**无法靠沙箱挡住**（沙箱挡的是「执行」，不挡「指令」）。所以沙箱必须与「指令/数据分离」（第 18 篇）配合：**沙箱管「能做什么」，指令分离管「听谁的」**。

## 2 能力限制：不给「不该有的能力」

**能力限制（capability restriction）** 是指「从能力层面约束模型本身」——不是「约束它执行的环境」，而是「约束它能做什么事」。两条路线：

**功能裁剪**：在「模型接入的系统」层面裁剪功能——不给它「执行代码」接口、不给它「写文件」接口、不给它「访问外部网络」接口。功能裁剪是「最小权限」在系统层的落地：**接口层面就不存在，模型再聪明也用不了**。<span class="marginnote">功能裁剪的优雅之处在于「<strong>能力不存在 ≠ 能力被禁止</strong>」：模型无法「绕过」一个不存在的接口。相比「提示词禁止」（模型可能不遵守），接口裁剪是「物理级」的约束——这是它比「指令式限制」可靠得多的原因。</span>
**行为约束**：在「模型自身」层面约束——训练/微调模型「不主动使用某些工具」「不越权操作」。行为约束依赖模型的「服从」，比接口裁剪弱，但能应对「接口都在、模型自己滥用」的情况（例如「自发地用搜索工具查不该查的信息」）。

两者要组合：**接口裁剪负责「硬边界」（物理上不能用），行为约束负责「软边界」（模型自觉不用）**。只靠软边界，模型被注入时可能「突破自觉」；只靠硬边界，任务需要的能力可能被误删。

## 3 沙箱的「信任边界」设计

设计沙箱的本质是画「信任边界」——哪些资源可信、哪些不可信、模型在哪个信任域内运行。一个清晰的信任模型分三层：

```text
┌───────────────────────────────────────────────┐
│ 可信层：模型本身、受控工具、被授权的数据         │ ← 模型运行在此
├───────────────────────────────────────────────┤
│ 半可信层：检索结果、解析后的结构化内容           │
├───────────────────────────────────────────────┤
│ 不可信层：外部网页、邮件、用户上传文档           │ ← 只能进数据通道
└───────────────────────────────────────────────┘
```

**核心设计原则**：

**模型运行时落在「可信层」**：模型本身被视为「可信但可能被误导」——所以要给它「执行的环境」隔离在可信域。
**来自不可信层的内容，永远不能直接进入「执行路径」**：网页内容只能进「数据通道」（被读取、被总结），不能进「指令通道」（触发工具调用）。这条原则（第 18 篇的「指令/数据分离」）在信任模型里有了精确的表达：**跨信任边界的内容，默认只当数据**。
**信任边界要「显式」**：沙箱设计必须能明确回答「哪个工具在哪个信任域」「什么内容能触发什么动作」——模糊的边界 = 没有边界。<span class="marginnote">「信任边界显式化」对审计（第 20 篇）也至关重要：当事故发生时，审计日志要能回答「这个危险动作是从哪个信任域、哪个通道触发的」——没有显式边界，就无法归因。</span>

## 4 沙箱的局限与「沙箱 + 护栏」组合

沙箱不是万能的，它的局限决定了必须与其他防线组合：

- **沙箱挡不住「指令劫持」**：注入的指令能让模型「输出危险内容」「把检索结果交给错误的人」——这些不涉及「执行」，沙箱管不了。
- **沙箱挡不住「合法工具滥用」**：Agent 在「任务范围内」的合法工具，被注入引导到「危险用法」——例如「搜索工具」被用来「搜索敏感信息」。工具本身合法，用法被劫持。
- **沙箱逃逸**：现实系统中存在「沙箱逃逸」漏洞（历史上无数次容器逃逸证明隔离可以被突破）——沙箱是「大幅提高攻击成本」，不是「绝对保险」。

因此，现实的 Agent 安全栈是**多层叠加**：

```text
第 1 层  沙箱隔离（执行环境）          ← 假设被突破
第 2 层  指令/数据分离（内容≠指令）     ← 假设被突破
第 3 层  权限与动作确认（最小权限）     ← 假设被突破
第 4 层  审计与监控（可追溯、可归因）   ← 兜底
```

**每一层都假设「上一层被突破」**，这是「纵深防御」的精髓——任何一个单点失效，系统整体仍然可控。

**辨析｜易错点：** 沙箱 ≠ Agent 安全本身。沙箱是「技术环境」，只解决「执行隔离」；Agent 安全的完整拼图还包括「指令信任」（第 18、19 篇）、「权限与确认」（第 20 篇）、「审计」（第 20 篇）、「护栏」（第 17 章）与「评估」（第 12、13 章）。**只装沙箱就宣称「Agent 安全」是最常见的错误**——沙箱是必要非充分。

## 5 拓展：沙箱的工程实现与逃逸的现实

沙箱不是「一个开关」，而是一套「层层隔离的工程系统」。理解它的实现细节，才能理解它的强度与弱点。

### 工程实现的层次

- **容器级隔离（如 Docker）**：轻量，共享内核——隔离「进程/文件系统/网络命名空间」，但「内核漏洞」可能逃逸。
- **微虚拟机（microVM，如 Firecracker）**：每个沙箱一个轻量虚拟机，有「独立内核」——隔离更强，但「启动开销」更高。
- **WebAssembly 沙箱**：在「字节码层面」隔离——最轻量，但「能力集」受限，适合「纯计算」任务。
- **网络与凭据隔离**：沙箱内「无网络」或「白名单网络」；API 凭据「不注入沙箱」或用「短期、最小权限凭据」。

### 沙箱逃逸的现实

历史上「容器逃逸」「虚拟机逃逸」都是真实存在的漏洞类别（CVE 案例众多）。沙箱的强度是「相对的」：

- **内核逃逸**：共享内核的容器，一个内核漏洞可能「逃出沙箱」。
- **侧信道**：时序、缓存等侧信道可能「泄露沙箱外信息」。
- **供应链攻击**：沙箱「镜像/依赖」被投毒，沙箱内运行的东西本身就是恶意的。

### 沙箱的定位：提高攻击成本，而非绝对保险

安全工程的成熟认知是：**没有「绝对隔离」的沙箱，只有「隔离强度与成本匹配威胁模型」的设计**。对「高危 Agent」（能执行代码、访问敏感数据），用「微虚拟机 + 网络隔离 + 最小凭据」；对「低危 Agent」（纯文本处理），容器级隔离即可。

**辨析｜易错点：** 不要以为「沙箱 = 隔离 = 安全」。**沙箱隔离的是「Agent 的执行」，不隔离「Agent 的输入」**——注入的指令（第 8 章）在沙箱内照样生效，只是「执行半径」被限制。**沙箱 + 指令分离 + 权限 + 护栏**才是完整防线。

## 6 拓展二：沙箱在「真实系统」中的落地案例

沙箱的「理论」到「落地」之间，有「真实系统的实践」——看两个「典型场景」的沙箱设计，能让「沙箱」更具体。

### 场景一：AI 编程助手

- **「执行隔离」**：AI 生成的代码「不能直接跑在主系统」——在「容器沙箱」里运行。
- **「网络限制」**：沙箱内「无网络」或「白名单」——防「代码外带数据」。
- **「文件隔离」**：代码只能「读写授权目录」——防「读取敏感文件」。
- **「超时与资源限制」**：代码「运行超时/内存超限」→ 自动终止——防「恶意代码耗尽资源」。

**这个沙箱的「核心设计」**：让「AI 生成的代码」在「即使被注入」时，「影响半径」被限制在「沙箱内」。

### 场景二：RAG 问答系统

- **「检索隔离」**：检索结果「只进数据通道」——「不触发工具调用」——「指令/数据分离」（第 18 篇）。
- **「来源限制」**：只检索「可信知识库」——「不可信网页」不进检索——「防『恶意文档注入』（第 19 篇）」。
- **「输出过滤」**：基于检索的生成「通过输出护栏」（第 53 篇）——「防『检索内容污染输出』」。

**这个沙箱的「核心设计」**：让「外部内容」在「即使带毒」时，「无法进入执行路径」——「隔离的是『指令通道』」。

### 沙箱设计的「共同原则」

两个场景「迥异」，但「沙箱设计」有「共同原则」：

- **「最小面」**：让「不可信的东西」能接触的「面」最小。
- **「最弱假设」**：假设「不可信的东西」是「恶意的」来设计。
- **「默认拒绝」**：没被「明确允许」的「访问/动作」→「默认拒绝」。

**辨析｜易错点：** 不要把「沙箱配置」当成「一次性设置」。**沙箱的「规则」要「随任务变化」**——「任务变了，权限要变，沙箱要调」。「配置一次就不动」的沙箱，「要么限制过死（任务跑不了）、要么放得过松（有漏洞）」。「动态调整」是「沙箱的常态」。

## 7 小结

- **沙箱（sandboxing）**：让 Agent 在受限环境运行——进程/网络/文件系统三层隔离；默认「模型可能被劫持」，设计「被劫持也无大害」。
- **能力限制**：功能裁剪（接口物理不存在）+ 行为约束（模型自觉不用）——硬边界与软边界互补。
- **信任边界设计**：把资源分层（可信/半可信/不可信），不可信内容只能进「数据通道」、不能进「执行路径」。
- 沙箱局限：挡不住**指令劫持**、**合法工具滥用**、且存在**逃逸**风险——必须与护栏、权限、审计组合。
- 安全观：沙箱是「必要非充分」——Agent 安全的完整拼图是多层防御的叠加。
