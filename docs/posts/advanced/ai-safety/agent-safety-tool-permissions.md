## 为什么从 Agent 安全开始

前面三节讲「注入」——让模型说错话、做错事。但「做错事」要成真，前提是模型**有能力做事**。**AI Agent（智能体）** 正是把「语言模型」升级成「能调用工具、能执行动作、能自主规划」的系统。第 16 章会讨论「工具 AI vs Agent AI」两条路线的安全性，本节先解决眼前最紧迫的工程问题：**当模型真的能调用工具时，怎么保证它不会（在注入、幻觉、或自主决策下）做出危险动作？** 答案不是「让模型更聪明」，而是「让系统更约束」——三个工程原则：**最小权限、动作确认、可审计**。<span class="marginnote">Agent 安全与提示注入是「同一枚硬币」：注入是「攻击者的入口」，Agent 安全是「受害者的边界」。<strong>即使注入成功，一个设计良好的 Agent 系统也应该把损害限制在可控范围</strong>——这就是「纵深防御」在 Agent 场景的体现。</span>

这一节从「Agent 为什么危险」出发，讲透三大安全原则及其工程落地。

## 1 Agent 为什么是一个新的安全层级

传统 LLM 应用（聊天、摘要）是「输入 → 输出」的闭环：模型再被注入，也只是「输出的内容被污染」。**Agent 打破了闭环**——模型现在可以「调用外部动作」：

```text
用户输入/提示 → 模型 → 工具调用（动作） → 外部环境
                    ↑                            ↓
                    ←──────── 结果反馈 ←─────────
```

这个「循环」引入了三个新的安全维度：

**动作**：模型的输出不再只是「文本」，而是「可执行的调用」——文本可以被「人」审查，调用直接作用于现实（或系统）。
**持久状态**：Agent 可以跨多轮保持状态（记忆、会话、甚至长期存储），攻击者可以「分多步」慢慢达成目标。
**自主性**：Agent 被设计为「在无人干预下完成目标」——自主性越强，「人审」的机会越少，出错/被注入的后果越难拦。<span class="marginnote">这三条维度共同指向一个判断：<strong>Agent 的「能力上限」与「危险上限」是同步增长的</strong>。给 Agent 的每个工具，都是一次「信任转移」——系统把「执行动作」的信任从「人」转移给了「模型」。Agent 安全研究的全部工作，就是管理这份「信任转移」。</span>

## 2 最小权限原则：只给「够用」的工具

**最小权限原则（principle of least privilege）** 源自操作系统安全：**每个进程/用户只拥有「完成任务所需的最小权限」，不多不少**。在 Agent 场景，它的含义是：

**工具集最小化**：Agent 只获得「当前任务需要」的工具，而不是「系统里所有」的工具。一个「总结文档」的 Agent 不需要「发送邮件」工具；一个「查天气」的 Agent 不需要「执行代码」工具。
**作用域最小化**：即使给了工具，也要限定作用域——「读文件」工具只能读「特定目录」，不能读整个磁盘；「执行代码」工具只能访问「白名单网络」，不能访问内网。
**凭据最小化**：工具背后挂的 API 密钥、数据库凭据，应该「最小权限 + 定期轮换」。Agent 用「只读密钥」还是「读写密钥」，后果完全不同。

**为什么最小权限是「第一原则」**：因为注入是**不可根除**的（前几节已论证）。既然「模型可能会被劫持」是常态，那么「即使被劫持，能造成的损害也有限」就是唯一可靠的兜底。**最小权限把「攻击的破坏力」从「全部」压缩到「最小必要」**——这是「纵深防御」的第一层。

**辨析｜易错点：** 最小权限 ≠ 「不给工具」。不给工具就没有 Agent 的功能价值；最小权限是「给够用的，不给多余的」——它是一个「权限边界」的精细设计，而不是「一刀切」。工程上通常用「任务描述 → 工具需求推导 → 权限授予 → 事后审计」的流程来落地。

## 3 动作确认机制：危险动作要「人拍板」

最小权限压缩了「破坏半径」，但有些动作即便「最小化」也危险（发一封外发邮件、删除一个文件、转一笔钱）。**动作确认机制（human-in-the-loop confirmation）** 是第二道防线：**让「高风险动作」在执行前需要人工确认**。

设计要点：

**风险分级**：把工具动作按「危险程度」分级——「读本地文件」低危、「外发网络请求」中危、「执行代码/删除/转账」高危。分级标准取决于「动作的可逆性」与「影响范围」。
**按级确认**：低危动作自动执行（保持 Agent 效率）；中危动作「弹确认」；高危动作「强制人工批准 + 双人复核」。**确认是「按风险分级」的，不是「所有动作都确认」**——否则 Agent 失去自主性价值。
**确认信息要「足够好」**：弹给用户的确认框不能只有「是否执行」，要展示「这个动作将做什么、影响什么、是哪个工具调用」——用户才能做出知情决策。**差的确认框是「假装安全」**。<span class="marginnote">动作确认的本质是「把最后一次判断权交还给人」。但它有一个上限：当 Agent 的动作「快到人审不过来」时（第 11 章「可扩展监督」的核心问题），确认机制就失效了——<strong>可扩展监督要解决的正是「人确认不过来」的规模化困境</strong>。这也是为什么 Agent 安全不只是工程问题，还是对齐研究的核心问题。</span>

## 4 可审计与可回溯：出事了要能查

第三道防线：**所有 Agent 动作都要留下「审计痕迹」，事故发生后可回溯、可归因、可学习**。工程实现：

**工具调用日志**：记录「谁（哪个会话）调用了什么工具、传入什么参数、返回什么结果」。
**决策轨迹**：记录模型的「思考过程」（第 13 章 CoT 监测会细讲）、「为什么调用这个工具」——为事故分析提供「模型视角」的上下文。
**权限变更审计**：记录「权限何时授予/撤销」——防止「权限漂移」（权限越滚越大）。
**异常检测**：用规则/模型检测「异常工具调用模式」（例如「连续多次高危调用」「工具调用频率异常」），实时告警。

**可审计的价值**不只是「事后追责」：它是「持续改进」的数据源——每个事故（被注入、被幻觉驱动、自主决策失误）都变成「改进策略/调整权限/补红队样本」的输入。**安全不是一次设计，而是一个「设计 → 运行 → 学习 → 再设计」的循环**。<span class="marginnote">可审计性还连接着「责任归属」：当 Agent 造成真实损害（发错邮件、删错文件），必须有「可解释的痕迹」来分清「模型误判」「注入攻击」「用户授权」的责任——这是第 14 章「AI 治理」的法律前提：<strong>没有审计，就没有责任；没有责任，就没有治理</strong>。</span>

## 5 三个原则如何协同

| 原则 | 回答的问题 | 防线层级 | 失效的后果 |
| --- | --- | --- | --- |
| 最小权限 | 被劫持后能破坏多大范围？ | 第一层（压缩半径） | 一次注入=全系统沦陷 |
| 动作确认 | 危险动作谁拍板？ | 第二层（人机边界） | 高危动作被模型自动执行 |
| 可审计 | 出事能不能查、能不能学？ | 第三层（回溯与改进） | 事故无法归因、无法改进 |

**三层的顺序就是纵深防御的次序**：最小权限把「能破坏的」变小 → 动作确认把「会被执行的高危动作」卡住 → 可审计把「漏网的动作」变成学习素材。**任何一层单独都不够，三层叠加才是 Agent 安全的现实底线**。

## 6 拓展：Agent 安全的评估与红队

Agent 安全不只是「设计原则」，还需要「评估」——否则无法知道「这套权限+确认+审计体系到底有没有用」。Agent 安全的评估与第 12-13 章的评估共享方法论，但有它自己的重点。

### 评估什么：三个维度

**权限有效性**：权限是否「最小必要」——评估「移除某个工具/权限后，Agent 还能不能完成任务」（权限过小伤功能、过大增风险）。
**确认机制有效性**：评估「危险动作是否真的被拦截」——用「攻击测试」：构造「让模型尝试高危动作」的场景，看「确认机制拦没拦住」。
**注入韧性**：评估「Agent 在注入攻击下能否守住底线」——用第 8 章的注入攻击测试「Agent 会不会被劫持执行危险动作」，以及「被劫持后，权限/确认/审计能不能兜住」。
  <span class="marginnote">Agent 安全评估的核心是「<strong>攻击模拟</strong>」：不是「看正常流程能不能跑通」，而是「假设模型被注入、被误导、决策失误，防线还站不站得住」。<strong>「防线」的价值只在「被攻击时」显现</strong>。</span>

### 红队 Agent：把攻击者请进来

Agent 红队（第 7 章方法的 Agent 版）专门攻击「Agent 系统」而非「单个模型」：

- **注入 Agent 红队**：测试「恶意网页/邮件/文档能否劫持 Agent 执行动作」（第 19 篇的现实载体 + 第 20 篇的防线）。
- **权限滥用红队**：测试「Agent 在『合法权限』内能做出多少危险事」——「最小权限」到底划得多小才够。
- **社会工程红队**：测试「人类用户能否被诱导让 Agent 执行危险动作」——「确认机制」是否被「用户被说服」绕过。

**辨析｜易错点：** 不要以为「Agent 有沙箱 + 权限」就「安全」。**沙箱管「执行环境」，权限管「动作范围」，但「模型自身的目标与判断」没有被直接约束**——一个「被注入的 Agent」仍可能「在权限范围内」做出「对人类有害的事」（如把敏感文件发给错误的人）。**Agent 安全是「多层防线」的叠加，任何单层都不能独立完成安全**。

## 7 拓展二：Agent 安全与「可解释性」的结合

Agent 安全不只是「权限 + 确认 + 审计」——它与「可解释性」（第 2-4 章）的结合，正在形成「新的安全维度」：**不仅知道「Agent 做了什么」，还要知道「它为什么这么做」**。

### 为什么 Agent 需要可解释性

- **「归因」**：Agent 的「多步动作」出事后，要「归因到哪一步、哪个决策」——「审计日志」记录「动作」，但「可解释性」解释「为什么做这个动作」。
- **「信任」**：用户「把动作权交给 Agent」的前提是「信任」——「可解释的动作」比「黑盒的动作」更可信。
- **「纠错」**：Agent「决策失误」时，「可解释性」帮助「定位错误环节」并「修正」——「不能解释的失误」只能「全部回滚」。

### 可解释性在 Agent 安全的具体应用

- **「决策轨迹的还原」**：用「CoT 监测」（第 39 篇）记录「Agent 决策时的『思考』」——「事后可回放『它为什么调用这个工具』」。
- **「工具调用的归因」**：用「归因方法」（第 2 篇）分析「哪个输入」驱动了「这个工具调用」——「判断是『正常任务』还是『被注入劫持』」。
- **「机制层面的验证」**：用「激活修补」（第 5 篇）验证「Agent 的『目标线路』是否被注入篡改」——「机制层面的注入检测」。

### 「可解释的 Agent 安全」的现实

「可解释 + 安全」的 Agent 还在「早期」：

- **「成本」**：记录「决策轨迹」增加「存储与延迟」成本。
- **「可解释性自身的局限」**：CoT 可能「不忠实」（第 39 篇），机制分析「难规模化」——「可解释的 Agent」要「承担可解释性的所有局限」。
- **「对抗性」**：攻击者可能「伪造决策轨迹」来「欺骗审计」——「可解释性」本身也要「防对抗」。

**辨析｜易错点：** 不要把「可解释的 Agent」当成「绝对安全的 Agent」。**「能解释」不等于「不会错」**——可解释性「提高了『发现问题』的能力」，不「消除『出错』的可能」。**「可解释 + 安全」是「增强」，不是「保证」**——「解释了为什么出错」不等于「不会出错」。

## 8 小结

- **Agent 安全**：管理「把执行动作的信任从人转移给模型」这份信任；注入、幻觉、自主决策失误都可能在 Agent 上「落地」为真实损害。
- **最小权限原则**：只给「够用」的工具、作用域、凭据——把攻击破坏力压缩到「最小必要」。
- **动作确认机制**：按「风险分级」让高危动作需人工确认；确认信息要「足够好」，否则是假安全。
- **可审计与可回溯**：工具调用日志、决策轨迹、权限审计、异常检测——事故可归因、安全可改进。
- 三者构成**纵深防御**：压缩半径 → 卡住高危 → 回溯学习；也铺平了「AI 治理」的责任归属基础。
