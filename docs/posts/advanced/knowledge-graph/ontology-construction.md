## 为什么从「本体」开始

前几篇把「图上有哪些实体、哪些事实」讲透了，但一个更根本的问题被搁置了：**「类」「属性」「约束」这些描述图的元结构，是谁规定的？** 为什么「爱因斯坦」被标成 `Person` 而不是 `Agent`？为什么 `bornIn` 的值必须是个地点？这层「描述概念及概念之间关系」的结构，就是**本体（ontology）**。<span class="marginnote">把 RDF 看成「名词的词汇表」，本体就是「语法的语法」：它规定哪些概念存在、概念如何分类、属性作用于什么类型。没有本体，图谱只是松散的三元组堆；有了本体，图谱才是一个「领域模型」。</span>

「本体」这个词来自哲学——研究「存在」本身的学问。计算机界借用了它，但含义非常具体：**本体**：对某个领域的概念、属性及其关系的**显式、形式化的规范说明**（Gruber, 1993）。显式（写下来了）、形式化（机器可读）、规范说明（是共识而非个人随想）——三个词各有用意。

顺带厘清一个常用词：**受控词表（controlled vocabulary）** 只是「概念的名单」，本体则在名单之上加入类层级、属性与公理——词表是静态分类，本体是推演引擎。别把「列了一堆术语」当成「建了一个本体」。

## 1 本体的两层：TBox 与 ABox

描述逻辑（Description Logic）把知识库拆成两层，这个划分贯穿整个本体工程：

**TBox（Terminological Box，术语层）**：关于类的公理——类与类之间的关系。「所有人都是行动者」「母亲一定有孩子」「猫与狗互斥」。
- **ABox（Assertional Box，断言层）**：关于个体的断言——某个个体属于哪个类、个体间的具体关系。「爱因斯坦是一个 Person」「乌尔姆是一个 City」<span class="marginnote">对照数据库：TBox 类似关系表的 schema（表结构、外键约束），ABox 类似表中的数据行。但有一个关键差别——数据库 schema 是「约束」，违例即报错；本体公理是「可推演的知识」，催生新断言而非拒绝数据。这个差别从第一篇的开放世界假设一路走来，到本体这里到达极致。</span>

**重点：TBox 描述「概念」，ABox 断言「个体」；推理器在两层之间架桥——从 ABox 的个体断言 + TBox 的类公理，推出新的个体断言。** 这就是「给数据立规矩」的精髓：规矩不只是管束，更是推演的引擎。

把 TBox/ABox 的分层再往深想一层：**为什么需要这两层？** 因为「概念」与「个体」的复用方式不同——概念要被多个图谱、多个应用共享与映射，个体则属于特定数据集。分层让「共享概念、各自断言」成为可能，这正是知识图谱跨源合并（第四篇）与互操作的本体前提：两边对齐的第一件事，就是对齐各自的 TBox。

## 2 描述逻辑：本体背后的形式语言

本体要「形式化」，就要有精确的语法与语义。最常用的描述逻辑是 **$\mathcal{ALC}$**（Attributive Concept Language with Complements），OWL DL 的语义内核就是它。

$\mathcal{ALC}$ 的概念（类）表达式归纳定义如下：

$$
C \;::=\; A \mid \top \mid \bot \mid \neg C \mid C \sqcap D \mid C \sqcup D \mid \exists R.C \mid \forall R.C
$$

读作：一个类可以是原子类 $A$、全集 $\top$、空集 $\bot$、否定 $\neg C$、合取 $C \sqcap D$、析取 $C \sqcup D$、存在限制 $\exists R.C$（「至少有一个 $R$ 关系指向某个 $C$」）、全称限制 $\forall R.C$（「所有 $R$ 关系都指向 $C$」）。<span class="marginnote">例如「有孩子的女性」可以写成 $\exists \texttt{hasChild}.\top \sqcap \texttt{Woman}$。注意这里没有一阶逻辑的谓词与函数符号——描述逻辑只在「概念」和「角色」（二元关系）上做文章，刻意牺牲表达力换取可判定性（推理必然停机）。</span>

在此基础上，公理的形式是**包含** $C \sqsubseteq D$（「$C$ 是 $D$ 的子类」）与**等价** $C \equiv D$。整个 TBox 就是一组这样的公理；推理器回答的问题如「$C$ 是否与 $D$ 矛盾」「个体 $x$ 是否一定属于 $C$」，都有算法保证可判定。

补一个名词澄清：很多人把 ontology、taxonomy、thesaurus 混着用——**taxonomy** 只讲「上下位」层级，**thesaurus** 还加「同义/相关」关系，**ontology** 则进一步包含属性与公理。越靠后表达力越强，代价也越高；工程上按需取用，别一上来就全副武装。

## 3 构建方法论：别从零造轮子

本体构建的工程智慧，可以用一句话概括：**能复用就不造，能轻量就轻量，能问答验证就问答验证。**

**复用优先**：先查是否有可复用的上层本体或领域本体，再接自己的扩展——从零建模的本体往往质量最差、兼容性最差。著名的**上层本体（upper ontology）**有 SUMO、DOLCE、BFO，定义「实体、过程、角色」等最抽象的顶层概念；**轻量模式**如 Schema.org、Wikidata 的类型体系、DBpedia 本体，够用且生态成熟。<span class="marginnote">现实中绝大多数应用根本不需要自建本体，直接用 Schema.org（网页标注事实标准）或 Wikidata 的类型树就够了。「本体工程师的首要技能是克制。」</span>
**先问能力问题（competency questions）**：动手前写下「这个本体必须能回答的问题清单」，如「列出所有 1900 年前出生的物理学家」。本体建完，用这些问题验收——它是需求文档，也是测试用例。

能力问题要具体可测，比如「列出所有出生在乌尔姆的物理学家」「找出所有与某药物共享靶点的药物」——前者要求本体支持「类约束 + 属性遍历」，后者要求「跨关系 join」。能力问题写不好的本体，多半是需求还没想清楚就动了手。能力问题的写法也有讲究：每个问题都要可判真伪（能用一个查询验证），避免「这个本体应该好用」这类不可测的口号。
- **自底向上与自顶向下结合**：从既有数据（表、文本）向上归纳概念（自底向上），再参考领域知识向下细化（自顶向下），反复碰撞。

举一个自底向上的例子：一份商品数据里有「iPhone 15」「MacBook Air」，向上可归纳出「手机」「笔记本电脑」，再向上「电子产品」；而参考领域分类学向下细化，「手机」又分出「智能手机 / 功能机」。两条方向在一个「概念格」上相遇，收敛出的类层级就是候选本体。<span class="marginnote">这里与第四篇《实体对齐》暗通款曲：对齐需要两个图谱的类能互相映射，而类映射的基础正是两侧本体的一致性——本体是跨图谱互操作的契约。</span>

## 4 本体学习：让文本替我们建模

手工建模费时费人，于是有**本体学习（ontology learning）**：从文本、表格等非结构化资源中半自动抽取本体元素——术语、类、类层级、属性、公理。

典型流程：先做**术语抽取**（领域高频词），再**归纳类层级**（用 Hearst 模式「X 是 Y 的一种」发现上下位，见第三篇），再发现**属性与关系**，最后人工审查保真。本体学习产出的通常是「候选本体」，交由专家修订——它是**辅助**而不是**替代**。

LLM 时代本体学习的形态升级：给模型一份领域语料与「能力问题」，让它提议候选类、判断「X 与 Y 是否等价概念」、补全缺失的属性与约束，甚至直接生成 $\mathcal{ALC}$ 公理。好处是速度与覆盖面，风险是幻象——机器起草的公理可能语法完美而语义荒谬，因此「人工审查」从流程的终点升格为每一环的必经关卡。

一个务实的建议：本体学习的启动集不必求全——几十个高频术语加一次专家校准，往往比「全量自动生成」更快产出可用的首版。本体是「精而可用」优先于「全而不准」的典型领域。<span class="marginnote">大模型时代这步被大幅增强：LLM 能直接提议类体系、判断两概念是否等价、补全公理——但幻象风险让「人工审查」这一环更加不可省略。本体工程永远是「机器起草、人拍板」。</span>

## 5 公式解析：ALC 的解释（语义）

形式的语法还不够，本体要精确，得给每个表达式定义**解释（interpretation）**。一个解释是一个二元组 $\mathcal{I} = (\Delta^{\mathcal{I}}, \cdot^{\mathcal{I}})$：$\Delta^{\mathcal{I}}$ 是论域（所有个体的集合），$\cdot^{\mathcal{I}}$ 把每个原子概念映成 $\Delta^{\mathcal{I}}$ 的子集、把每个角色映成 $\Delta^{\mathcal{I}}$ 上的二元关系。

关键两个构造的解释：

$$
(\exists R.C)^{\mathcal{I}} = \left\{ x \in \Delta^{\mathcal{I}} \mid \exists y : (x, y) \in R^{\mathcal{I}} \wedge y \in C^{\mathcal{I}} \right\}
$$

$$
(\forall R.C)^{\mathcal{I}} = \left\{ x \in \Delta^{\mathcal{I}} \mid \forall y : (x, y) \in R^{\mathcal{I}} \Rightarrow y \in C^{\mathcal{I}} \right\}
$$

三步拆解：

- **第一步，理解论域**：$\Delta^{\mathcal{I}}$ 是「世界里所有个体」的集合，是解释的舞台；一切概念都解释成它的子集。
- **第二步，读存在限制**：$(\exists R.C)^{\mathcal{I}}$ 收录所有「存在一个 $R$ 邻居落在 $C$ 里」的个体。直觉：某人有**至少一个**孩子是科学家，他就属于 $\exists \texttt{hasChild}.\texttt{Scientist}$。
- **第三步，读全称限制**：$(\forall R.C)^{\mathcal{I}}$ 收录所有「$R$ 邻居全都落在 $C$ 里」的个体。直觉：某人**所有**孩子都是科学家，才属于 $\forall \texttt{hasChild}.\texttt{Scientist}$。

**直觉**：$\exists$ 与 $\forall$ 的差别就是「至少一个」与「全部」的差别——描述逻辑把量词限制在角色的邻域内，从而保证了可判定性，这是它比一阶逻辑「弱但可靠」的根源。

再补一个承前启后的点：$\mathcal{ALC}$ 的推理问题（例如判定包含 $C \sqsubseteq D$ 是否成立）是可判定的，最坏情形复杂度为 EXPTIME 完备——这说明「表达力与可判定性」的交换有精确的代价，也是 OWL 选择它作语义内核的根本理由。描述逻辑的完整体系，第一级《数学逻辑》与第二级《离散数学》给你打了谓词逻辑的地基，这里只是把量词收回邻域。

OWL 还有三个实用子语言（profile），是「表达力—推理复杂度」的三档配置：**OWL DL**（完整表达、EXPTIME 推理）、**OWL EL**（面向大图谱、多项式时间推理，生物医学本体如 SNOMED CT 用它）、**OWL QL**（面向数据库查询重写，与 SQL 结合）。选哪个，取决于「图多大、推理要多快」——这就像第二级《数据结构》里按场景选数据结构，先看约束再选语言。

## 6 易错辨析：本体工程的三条红线

**易错点一：本体公理是推导不是校验。** 写了 `Person ⊑ Agent` 不会让推理器「拒绝」那些不是 Person 的 Agent 数据，只会推出「每个 Person 都是 Agent」。想实现数据库式约束（如「母亲必须有孩子」），需要专门的完整性约束机制，别指望 OWL 默认替你检查。

**易错点二：domain/range 别乱写。** 给 `bornIn` 写 `domain Person`，那么图上每条 `bornIn` 的主语都会被推导成 Person——这会把「被误标注的数据」悄悄「洗白」。domain/range 是「承接地」而非「守护者」，滥用会污染类型推断。

**易错点三：命名即承诺。** 本体的类名与 URI 是共享约定，改一次名字波及所有下游数据与推理。命名要稳定、语义要单一——「给猫起名是件艰难的事」，给类起名更是。把命名约定（前缀、大小写、语言）写进文档并坚持执行，是本体工程里最容易被忽略、却最值得投资的一步。

还有一条工程纪律值得单独拎出：**本体是活的**。业务演化、数据漂移都会让本体过时——定期重访能力问题、评估「哪些类再也没被用到」「哪些概念该拆该并」，与软件重构同理。本体的维护成本，常常被初次建模的光鲜掩盖。

最后补一条验收纪律：本体交付前，用最初的能力问题逐条跑一遍推理器——能答上来的才算数。这条「能力问题验收」与软件工程的验收测试同构，是本体项目最便宜的质量闸门。

## 7 小结

- **本体**是对领域概念与关系的显式、形式化规范；分 **TBox**（类公理）与 **ABox**（个体断言）两层。
- **描述逻辑 $\mathcal{ALC}$** 是 OWL DL 的语义内核：概念表达式 + 包含公理，牺牲表达力换取可判定性。
- 构建方法论：**复用优先、能力问题先行、双向建模**；上层本体（SUMO/DOLCE）与轻量模式（Schema.org/Wikidata）是最常见的起点。
- **本体学习**从文本半自动提取候选本体，大模型时代更要保留人工审查。
- 三条红线：公理是推导非校验、domain/range 别乱写、命名即承诺。
- 本体是推演引擎不是静态名单；本体是活的，需要像代码一样持续重构。

在下一节，也是本专题的收官：前面的一切技术，最终在哪些真实系统里兑现价值——知识图谱的应用，从搜索到药物研发，再到与大模型的双引擎合流。带着 TBox/ABox 的双眼去看应用，你会看到每一处图谱落地，其实都是一次隐性的本体工程。
