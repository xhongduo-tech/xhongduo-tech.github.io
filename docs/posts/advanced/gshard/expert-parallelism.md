## 为什么从「并行」开始

前四节把 MoE 层讲清楚了：结构、路由、负载均衡。但这套机制要落地到 2048 张卡上，还有最后一块硬骨头——**这些参数物理上放在哪**。
6000 亿参数远超单卡显存，而 GShard 的核心贡献恰恰不在 MoE 本身，而在**把 MoE 模型高效地切分到上千台设备上**的并行策略。
本文讲清楚这张「切分地图」：哪些参数复制、哪些参数切分、token 如何跨越设备找到自己的专家。

## 1 一张卡装不下：稀疏模型的「存储墙」

《条件计算动机》里强调过：**稀疏只省计算量，不省存储量**。
6000 亿参数的模型，哪怕一次推理只激活 1%，全部参数仍必须分布在设备上。
于是问题分两层：- **共享的稠密部分**（注意力、非 MoE 层）：每张卡各存一份，靠**数据并行**摊数据、靠 AllReduce 同步梯度；
- **专家的巨量参数**：必须**切分**到不同设备，每张卡只持有少数几个专家。

把「参数切到不同设备」这件事做对，就是**专家并行（Expert Parallelism, EP）**：**把 $E$ 个专家按设备切分，每个设备只保存并计算其中一部分专家**。
设备间靠通信让 token 找到自己所属的专家，而不是让每个设备都保有全部专家。

## 2 一张「切分地图」：四维并行怎么配

在分布式训练的标准术语里，GShard 的切分地图是几种并行方式的组合：| 并行方式 | 切分什么 | 通信模式 | 本模型中的角色 |
| --- | --- | --- | --- |
| 数据并行 | 数据（每卡一整套参数副本） | AllReduce（梯度同步） | 稠密层：注意力、普通 FFN |
| 专家并行 | 专家参数（按专家切分） | All-to-All（token 搬运） | 所有 MoE 层 |
| 张量/模型并行 | 单个算子的权重矩阵切块 | AllReduce（局部聚合） | 大模型切分辅助 |
| 流水线并行 | 按层切分、逐层接力 | 点对点（激活传递） | 本文不采用为主 |

关键区分：**注意力层是「数据并行 + 复制」，专家层是「专家并行 + 切分」**。
这背后是一条清晰的分工——注意力需要每个 token 看见全序列，无法轻易切分，干脆全卡复制；
专家本来就是独立函数，切分后只靠通信把 token 送上门，代价可控。

在最大的 GShard 模型里，每个 MoE 层有 2048 个专家，恰好与 2048 张设备一一对应：**每张卡每层持有约 1 个专家**。
这个「卡数 = 专家数」的整齐映射，让专家并行的负载天然均匀——前提是路由也均匀，这正是上一节辅助损失的用武之地。
<span class="marginnote">「每卡一个专家」并非必然。专家数可以比卡数多（多专家挤一卡）或少（一个专家跨多卡）。GShard 选「一一对应」是为了简单与均衡；后来 Switch 与 Mixtral 在更小的集群上通常一张卡放多个专家。</span>

## 3 All-to-All：token 如何「拜访」专家

专家被切走后，层内流动要重写一遍（对照《MoE 层结构》的六步）：1. 每张卡在本地对「自己手上的 token 组」打分、选出 Top-2 专家；
2. **All-to-All（全交换）**：把 token 连同它的目标专家编号，批量送到对应专家的宿主设备——这是跨设备的集体通信；
3. 各设备在本地专家的计算单元上处理收到的 token；4. **再一次 All-to-All**：把计算结果送回 token 的原属设备；
5. 原设备把「两个专家的结果」按 $g_i$ 加权合并，加上残差，继续往后传。

![专家并行中的 All-to-All 分发](/images/gshard/expert-parallelism-1.svg)**All-to-All**：一种集体通信原语，每个设备都向所有设备发送数据、并从所有设备接收数据，可以看作「同时发生的全网排列」。它正是 MoE 的天然通信模型：token 与专家之间是多对多的对应关系，没有任何固定拓扑能预先规定它们该在哪相遇。<span class="marginnote">对比数据并行的 AllReduce（全网求和）、流水线并行的点对点（邻站接力），All-to-All 的「全网互发」最贵也最灵活。MoE 训练的通信瓶颈几乎全压在它身上——这也是后来「专家分片（expert sharding）+ 局部路由」等优化要缓解的对象。</span>

**辨析｜易错点：** All-to-All 不是「广播」。广播（broadcast）是「一点到多点」，AllReduce 是「多点求和再回广播」，而 All-to-All 是「多点对多点的任意排列」——每个设备既是发送方又是接收方。三者的通信量随设备数的增长关系不同：广播与 AllReduce 近似线性，All-to-All 因为要做全网排列，成本更接近二次方。所以 MoE 的 All-to-All 才是集群通信里最贵的一档，也是工程上优先要优化的一环。

## 4 通信成本：稀疏省下的算力去哪了

All-to-All 的通信量需要精确计量。每个 token 前后各被搬运一次，设每批 token 数为 $T$、隐藏维为 $d$，一次 MoE 层的通信量为

$$V_{\text{comm}} = 2 \times T \times d \times (\text{每元素字节数})$$

- **第一步**：系数 2 来自「送去计算」和「取回结果」两次搬运；- **第二步**：$T \times d$ 是每个 token 的激活张量大小——搬的是 token 的向量表示，不是模型参数；- **第三步**：对比一下专家层的计算量约 $2 T d_{\text{ff}} d$，通信只与 $d$ 有关而与专家内部宽度 $d_{\text{ff}}$ 无关——**把专家做宽，计算涨、通信不涨**，所以 GShard 倾向于「专家少而大」的设计来摊薄通信比例。**辨析｜易错点：** All-to-All 搬运的是「中间激活」，不是「梯度」。梯度同步发生在各层内部的 AllReduce（稠密层）与专家内部的 AllReduce（专家权重的梯度在各副本之间求和），两者不要混为一谈。通信的时序是：前向搬运激活（All-to-All），反向搬运梯度（All-to-All 的逆过程 + AllReduce）。

把式子填进具体数字。设每批 $T = 8$ 个 token、隐藏维 $d = 1024$、每元素 2 字节（bfloat16），则一次 MoE 层前向的通信量

$$V_{\text{comm}} = 2 \times 8 \times 1024 \times 2 = 32\,768 \ \text{字节} \approx 32 \ \text{KB}$$

这个量级说明：单层通信与「批大小 × 隐藏维」成正比，与专家个数 $E$、专家宽度 $d_{\text{ff}}$ 都无关——**正是这一点让「把专家做宽而不涨通信」的设计可行**。把它与 §6 的公式对照着读，就能理解为什么 GShard 总想同时放大专家数与卡数。

## 5 反向传播：梯度怎么穿过两次 All-to-All

前面讲的前向是「token 去、结果回」，那反向传播怎么走？
原则只有一条：**All-to-All 是线性排列操作，它的反向就是逆排列**。
梯度沿通信图回流的路径是：- **回程 All-to-All 的逆**：把「对专家输出」的梯度按回程排列的逆序送还各专家宿主——即一次逆排列；
- **专家本体**：每个专家在本地做标准 FFN 反向，产出「对专家参数」的梯度与「对 token 激活」的梯度；
- **去程 All-to-All 的逆**：把「对 token 激活」的梯度按去程排列的逆序送回 token 的原属设备；
- **梯度聚合**：专家参数在每个数据并行副本组内做 AllReduce 求和——因为各副本对「同一批专家、不同数据切片」各自算出梯度，最终必须合并。

这条链的对称性是分布式训练的「公理」：**通信算子是线性的，反向传播一定会遇到它的伴随（adjoint）
运算**。理解了它，你就能从任何一张前向通信图直接推出反向通信图，而不必为每一层单独推导。
<span class="marginnote">「通信算子的反向 = 伴随算子」是自动微分的通用事实：AllReduce 的伴随是 AllReduce，All-to-All 的伴随是逆排列的 All-to-All，AllGather 的伴随是 ReduceScatter。推理分布式训练里的任意通信，都可以用这一条原则归约。</span>**辨析｜易错点：** 别把反向理解成「原路返回」这么简单——**去程搬的是 token 激活，回程搬的是梯度，两趟搬运的内容不同、设备流向相反**。另一个易错点是梯度聚合的位置：专家参数的梯度必须来自「该专家实际处理的 token」所贡献的梯度之和，跨设备的求和正是由 AllReduce 完成的；漏掉任何一环，梯度就会不完整。

## 6 公式解析：为什么「专家数 = 卡数」最省通信

设设备数为 $D$，专家总数为 $E$，每卡承载的专家数为 $E/D$。
若一个 token 去了某设备，它只与该设备上的专家交互，因此单次 All-to-All 的通信量与「每卡需要接待的 token 数」
成正比：$$
\text{每卡通信量} \propto \frac{T}{D} \times \frac{E}{D} \times d = \frac{T E d}{D^2}
$$

- **第一步**：$\frac{T}{D}$ 是每卡分到的 token 数；- **第二步**：$\frac{E}{D}$ 是每卡承载的专家数——它决定了「每卡要处理多少外来 token」的上界；- **第三步**：看 $1/D^2$：**设备越多，每卡通信量反而急剧下降**。这是专家并行「越并行越省」的反直觉之处——与数据并行（通信随 $D$ 缓慢增长）形成对照。
- **第四步**：当 $E = D$（每卡 1 个专家）时，式子退化为 $\frac{T d}{D}$，正是上一节给出的 $\frac{2 T d}{D}$ 量级（差个常数 2 与字节因子）。**辨析｜易错点：** 设备越多通信越省，前提是**专家数也同步增长**（保持 $E = D$）。如果 $E$ 固定而只加设备，那么 $E/D$ 变小、每卡通信量确实下降，但与此同时专家被迫跨卡切分（张量并行式切分），层内聚合通信会重新涨回来。所以专家并行优化的真正杠杆是「同时放大 $E$ 与 $D$」——这正是 GShard 把模型从 37.5B 一路放大到 600B 时反复使用的操作。

把 $1/D^2$ 的结论用数字验证。设 $T = 8192$、$d = 1024$，保持「每卡 1 个专家」（$E = D$）：

| 设备数 $D$ | 专家数 $E = D$ | 每卡通信量（相对值 $T E d / D^2$） |
| --- | --- | --- |
| 256 | 256 | 32 × 相对单位 |
| 1024 | 1024 | 8 × 相对单位 |
| 2048 | 2048 | 4 × 相对单位 |

设备从 256 涨到 2048（8 倍），每卡通信量反而降到原来的 1/8——「越并行越省」的直觉，就藏在这张表里。注意前提是专家数与设备数同步增长；否则专家被迫跨卡切分，聚合通信又会把省下的量吃回去。

## 9 小结

- **专家并行**：把 $E$ 个专家切分到各设备，每卡只持有 $E/D$ 个专家，其余设备复制稠密层。
- 切分地图：**稠密层 = 数据并行（复制 + AllReduce），MoE 层 = 专家并行（切分 + All-to-All）**。
- token 跨设备拜访专家的两趟 All-to-All 是 MoE 训练的通信核心。
- 通信量 $\propto T E d / D^2$：设备越多越省，前提是专家数同步增长。
- GShard 的「卡数 = 专家数」让专家并行负载天然均匀，配合负载均衡损失双保险。

在下一节，我们回答「谁来执行这些 AllReduce 和 All-to-All」：GShard 不是手写通信，而是靠编译器自动生成——这就是 **XLA SPMD 编译**。
