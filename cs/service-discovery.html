服务发现 ​

实例上下线比 DNS TTL 快；发现把名字映到健康地址集合，LB 再从中选。DNS、注册表、网格是三条路。

—— 据 RFC 1035 对照；微服务发现实践整理

DNS TTL 太慢跟不上容器。反向代理 需要后端列表。上一课 假定池已知。缺口是发现：注册、健康、订阅。本课结束实时与分发课序。

问题 ​

虚拟机/容器秒级生灭。权威 DNS + 60 s TTL 会指向死 IP。服务发现：实例启动向注册表报，心跳，代理 watch 变化。DNS 仍可用于粗入口。gRPC 客户端也可直连发现。与 BGP 对照：都是通告可达，一层应用实例，一层前缀。EVPN Type 2 是数据中心版 MAC 发现。

不要把 Kubernetes 当唯一标准。

接口因平台而异。本课钉问题：比 DNS 更短的生命周期。

数字实例：容器实例常以分钟甚至秒为单位生灭，而 60 s 的 DNS TTL 意味着实例死后最多还有一分钟的流量继续打进死 IP——各中间缓存还可能不听权威的生死通告。注册表 watch 是秒级甚至亚秒，这才是「更短生命周期」需要的节奏。

比 DNS TTL 更短的生命周期 ​

注册加心跳更新池。无健康检查只是更快的错误 DNS。注册表分区会脑裂。未认证注册像劫持。

方法 ​

对照：DNS / 注册表 / sidecar 网格。画：注册 → 健康 → 推送到 LB。与 Maglev 表更新衔接。

机制 ​

失败：注册表分区造成脑裂双池。与 iBGP RR 同类风险。GeoDNS 发现的是 POP，不是 pod。PTP 无。安全：未认证注册会把流量拐走，像 BGP 劫持的数据中心版。

客户端负载均衡 vs 代理：状态放哪。

上面那张图是正常的注册→心跳→更新；下面这张回答「实例死了怎么被发现、什么情况下会摘错」。

直觉类比：注册表分区脑裂像两地门卫各持一份访客名单，网络断了之后各自划掉各自以为离开的人——东门卫说 B 走了、西门卫名单上 B 还在；恢复连通前，问谁拿到的「可用实例集」都不一样。

常见误区：以为「注册成功」等于「服务健康」。注册只证明进程活着报了名；没有健康检查的注册表会把「启动到一半、端口还没监听」的实例放进池里，请求照样失败——注册必须配就绪探测才构成「健康实例集」。
