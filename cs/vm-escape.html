虚拟机逃逸 ​

虚拟机把客当做不可信，但设备模拟、共享内存与管理接口是 TCB。逃逸指客中代码到达宿主机。防御是缩小模拟面、设备 IOMMU、及时补丁，而不是假设「有虚拟化即隔离」。

—— 据 Barham et al., Xen, SOSP 2003 的隔离目标；对照 Anderson；CVE 史仅作动机点名

上一课Flush+Reload还是共驻下的机密性泄漏；缺口是完整性边界：客中代码能否到达宿主机。本课讲虚拟化的 TCB 面，不给逃逸 PoC。

后课默认已经读完本课钉下的合同，只补差，不从该领域第一性原理重开。

问题 ​

现代虚拟化把 CPU 与内存的拦截交给硬件，但设备仍靠宿侧的模拟代码：QEMU 的设备模型、virtio 后端、管理 API 都在特权侧解析客机发来的数据——模拟代码里的洞就是宿里的洞。缺口是三件收缩：最小设备模型（不给客机用不到的设备）、快照加及时补丁（逃逸漏洞的暴露窗口以天计）、生产上关闭嵌套虚拟化等非必要特性。

直觉类比：设备模型像替客人收发包裹的前台——客人递来什么单子它都得拆开看（解析不可信数据），前台自己的漏洞就是整栋楼（宿主）的漏洞；把客人用不到的前台撤掉（最小设备集），是最便宜也最有效的一笔安全支出。

机密计算 ​

机密计算（TEE 型虚机）防的是运营商窥视内存；它不自动防一个客机逃逸去打另一个客机——那要另配宿内网络与工作负载策略，别把两个威胁混为一谈。

Xen/KVM 文献。禁止逃逸教程。容器下一课是更薄的边界。

方法 ​

方法是把 IaaS 威胁模型写清楚：谁是对手（同宿租户、被攻陷的客机、云内部人员）、信任谁（hypervisor 加设备模拟）、每类洞由谁修。补丁窗口要量化：高危逃逸 CVE 从披露到全舰队打齐的天数就是风险敞口。下一课容器逃逸。

数字实例：高危逃逸漏洞从披露到全舰队打齐补丁若需 7 天，这 7 天就是明码标价的风险敞口——把「窗口以天计」写进威胁模型，意味着多租户平台这期间的调度与隔离决策都得自己顶住，不能指望别人先修好。

机制 ​

机制一句话：隔离强度等于 TCB 的正确性。hypervisor 的代码量比通用内核小一个量级、攻击面小，但设备模拟把它重新拉大——削减模拟面因此直接兑换安全。容器共用宿内核，syscall 界面巨大，边界比虚机再薄一层，下一课展开。

常见误区：「有虚拟化就等于隔离了」。虚拟化只是把拦截交给硬件，隔离成立与否取决于设备模拟与管理接口这些特权侧代码有没有洞；IOMMU 挡得住设备 DMA 越界，但直通网卡自己的固件有洞照样穿透——机制要逐层验，不能按标签信。

边界 ​

零 PoC；边界要点名：硬件辅助只收缩通道不证明正确性——IOMMU 挡住设备 DMA 越界，但直通网卡自身固件有洞照样穿透。容器逃逸下一课。

小结 ​

  • 侧信道漏 C；逃逸破隔离完整。
  • 设备模拟是高危 TCB。
  • 虚拟化不是自动证明。
  • 下一课容器逃逸。
  • 出处：Barham et al., Xen, 2003；Anderson。
