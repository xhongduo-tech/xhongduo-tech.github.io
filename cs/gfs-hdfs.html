GFS / HDFS ​

大文件切块，多副本放块服务器；主存元数据。主是 CP 小状态，数据面是尽力吞吐。客户端缓存块位置，租约管写。

—— 据 Ghemawat, Gobioff and Leung, The Google File System, SOSP 2003；HDFS 架构（Shvachko et al., MSST 2010）整理

上一课混沌把崩溃当实验。GFS 把崩溃当日常设计点。缺口是大数据文件如何在普通机器上活：不是 etcd 里放 blob。本课钉主 + 块副本。后课对象存储换 API 与一致性档。不重写 Raft 日志。

问题 ​

GFS：chunk 默认 64MB，三副本。Master 管命名空间与块位置，不承运数据。客户端问主拿位置，再打 chunkserver。写：主发租约给主副本，流水线推数据，主副本排序，再数据推。主故障：有 checkpoint+操作日志，早期单主切换慢——这是主备形态。

HDFS 公开实现同族：NameNode + DataNode，块报告、租约、流水线。HA NameNode 后来用共享编辑日志或独立 Journal。

SOSP 2003 强调弱一致性：追加、快照、主缓存过期。MapReduce 的输入是这种文件。本课不写 MapReduce。

方法 ​

读：从最近副本读，校验和。写：租约防双写同一 chunk。主内存元数据要匹配块服务器心跳；幽灵块靠校验与扫描。

不要把主当数据面：主过载会让整个命名空间停，尽管磁盘还在。

机制 ​

一致性：GFS 对并发写不保证 POSIX 全语义，保证追加的「至少一次」类记录追加（record append）可能有填充与重复——应用要容。这与线性一致文件对象不同。HDFS 对打开写的文件限制更严。选档为吞吐。

数字实例：chunk 取 64MB 是为了把元数据压到主能全放内存——1 PB 数据 ÷ 64MB ≈ 1600 万个块，主用不到几 GB 内存就能记住所有位置。若块只有 4KB，同样 1 PB 就是 2.7 亿个块，主内存与心跳报告都会爆炸。大块还让客户端长时间打同一台 chunkserver，减少元数据请求次数。

术语翻译：租约（lease）就是「有时限的写授权」——主把某一块的 primary 身份发给一个副本，说「在接下来 60 秒内由你决定写顺序」。租约到期作废，主就能安全地把角色另授他人；双主不会同时有效，因为旧租约一定先过期。

与 Chubby：GFS 主选主可外包锁服务。与链式复制：流水线像短链，提交规则是租约主排序。

常见误区：初学者容易以为 record append「至少一次」等于「正好一次」，于是并发追加不会重。实际上某副本超时未确认时，primary 会令整个追加重试，成功副本上就出现重复记录，中间还可能被填充凑齐对齐——所以读取端要靠记录内的校验和与唯一 ID 去重。

本课不写纠删码替代三副本的全部。也不写小文件海量的 NameNode 内存墙——下一课元数据会碰。

边界 ​

本课不把 Colossus 内部当公开规格。后课默认：块存储 = 小 CP 元数据 + 大数据面副本；POSIX 语义不默认。对象存储下一课把命名空间再摊平。分布式文件元数据课专门打 NameNode 墙。

数据面可丢一台；元数据面是控制面单点，必须有自己的恢复故事。

小结 ​

  • GFS/HDFS：主管元数据，块服务器管字节，租约管写。
  • 文件语义弱于 POSIX；为吞吐与追加。
  • 主必须快照+日志；客户端缓存位置会过期。
  • 出处：Ghemawat et al., SOSP 2003；Shvachko et al., MSST 2010。
