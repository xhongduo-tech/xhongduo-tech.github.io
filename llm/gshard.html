GShard ​

用稀疏门控专家把容量做大，用编译器切分把专家铺到 TPU 网格上；模型代码仍按单设备写，只在关键张量上留下切分策略。

—— Lepikhin 等，GShard: Scaling Giant Models with Conditional Computation and Automatic Sharding, 2020

Shazeer 等人 2017 年给出稀疏门控 MoE；要把专家库真的铺到上千块加速器上，还缺一套不改网络定义就能改切分的系统。Lepikhin、Lee、Xu、Chen、Huang、Krikun、Shazeer、Firat 等人的 GShard 由轻量标注 API 与 XLA 编译器扩展组成，在 TPU v3 上把多语言翻译 Transformer 做到超过 6000 亿参数：2048 块加速器、约 4 天，100 种语言译入英语，质量优于当时的公开对照。本篇写「条件计算 + 自动切分」如何接在一起；路由公式与负载均衡见 MoE 路由，All-to-All 语义见 专家并行，通用分区器见后继的 GSPMD。

问题 ​

放大稠密 Transformer，计算随参数线性涨。条件计算的承诺是：总参数可以很大，每个 token 只激活少数专家，FLOPs 涨得慢一些。论文报告相对基线，参数大约 16 倍时，计算大约只到 3.6 倍量级——这是稀疏的意义，不是免费午餐。代价转到系统：专家住在不同设备上，token 必须按路由结果做跨设备分发；容量要有上限，否则静态编译无法分配缓冲；负载要均衡，否则多数专家饿死。

若让算法工程师手写每条 All-to-All 与每张卡的专家布局，网络结构与 2048 核拓扑焊死，换一种切分就要改模型。GShard 的分离是：单设备视角写层；只在关键张量上标注切分策略；编译器做保持语义的变换，生成并行执行。

标注而不是重写算子 ​

开发者面对的是「一块巨大内存、巨大算力的逻辑设备」。API 把少数张量标成沿 mesh 某维切开或复制。专家权重沿专家维切开，token 激活在专家维上做分发与回收。稠密注意力、嵌入、残差仍可按数据并行或层内切分标注。换「每卡几个专家、mesh 哪一维是专家轴」时，改的是标注，不是 MoE 层里的矩阵乘。

GShard 不是「发明了 MoE」。它发明的是把 Shazeer 式稀疏专家接到 XLA SPMD 切分上，并在翻译任务上把规模推到 600B+。Switch Transformer 后来把 \(k\) 收到 1；DeepSeek 一类 GPU MoE 换了路由与通信实现。读 GShard 不要把 2020 年的 TPU permute 当成 2026 年的 NCCL 默认。

方法 ​

条件计算侧：Transformer 的 FFN 换成 Sparsely-Gated Mixture-of-Experts。每个 token 经路由器打分，取 top-\(k\)（GShard 用 \(k=2\) 这一档），只在选中的专家上做前馈，再按门控权重混合。容量因子给每个专家一个静态槽位数；超容量的 token 被丢掉或走备份路径，从而 All-to-All 缓冲可以在编译期定死。辅助损失拉负载，避免路由崩溃——细节不在本篇展开。

切分侧：XLA 扩展根据标注把计算图改写成每设备程序。专家维对齐 TPU mesh 的一条轴时，跨设备分发就是沿该轴的置换，而不是任意主机侧 scatter。稠密部分可以沿 batch 切。整个模型仍是一份 SPMD 二进制。训练用 2048 个 TPU v3，论文写约 4 天完成该巨型多语言翻译模型，并强调相对先前工作，100→En 的质量明显更好。这些是该任务、该数据、该硬件上的结果，不是「600B 一定 4 天」。

稀疏放大的是容量，不是步内 FLOPs ​

每个 token 只进 \(k\) 个专家，步内计算由「被激活的专家宽度 × token 数」决定，不由专家总数决定。专家总数决定内存与通信拓扑：2048 个专家可以一对一铺到 2048 核上，也可以每核多个专家。通信体积随 \(k\)、容量因子和是否跨轴切分变化。\(k=2\) 意味着一个 token 可能去两台设备，实现上要两套槽位与两次分发语义，这正是 Switch 后来要简化的对象。GShard 证明 \(k=2\) 在翻译上可行且质量好；它没有声称 \(k=2\) 是唯一合理开关。

自动切分的价值在换宽度：同一套层定义，把专家数从几十加到上千，编译器重分区，而不是手写第 2048 号通信组。失败模式是标注与 mesh 轴选错：专家维若落到慢连接上，置换会变成数据中心网络上的 All-to-All，稀疏带来的 FLOPs 优势被通信吞掉。

机制 ​

编译器能自动切，是因为 MoE 层可以写成对专家维的 einsum / 分组 GEMM：切分规则与稠密点积类似，只是多了「按路由下标 gather」这一层。路由本身是小的 \(d\times N\) 线性，通常复制在各设备上本地算，再按 top-\(k\) 生成分发计划。容量把计划变成定长缓冲：空槽仍占通信，容量过大等于给空气付带宽——与后来 GPU 上的 MoE 实现是同一屋顶线，只是 TPU 上走 mesh permute。

「自动」不等于「无启发式」。XLA 扩展要决定何时插入通信、如何把部分切分组合起来。用户标注是启发式的锚。论文把编程模型写成：关注网络结构，灵活改切分；底层做保持语义的变换。语义保持的是数值图，不是性能。同一模型两种标注都「正确」，步时可以差一截。

600B+ 是总参数。激活比例远小于 100%：Google 后续对照表里 GShard-M4 一类稀疏编解码大约 577B 参数、激活约 0.25%、2048 专家。读论文时把「参数量」和「每 token FLOPs」分开写，否则会以为 600B 稠密跑了 4 天。

与 GSPMD、Switch、GPU MoE 的位置 ​

GShard 是 2020 年的模块：标注 API + XLA 扩展 + 巨型翻译实验。GSPMD（2021）把分区器泛化到稠密、视觉、语音，并系统写传播算法。Switch（2021）在 MoE 算法上把 \(k\) 收到 1，并整理稳定性配方。GPU 生态后来用 NCCL All-to-All 实现同一「token 找专家」语义，但没有 XLA 标注那套默认分区器。三者互补：GShard 证明编译器切分能撑起稀疏巨模型；不要在 GPU 训练日志里写「我们用了 GShard」却只有一份 Megatron MoE 配置。

边界与工程取舍 ​

不要把 2048×TPU v3、4 天、100 语言 BLEU 当成通用训练定额。数据、词表、翻译方向、专家宽度都绑在那篇实验上。不要在没有容量因子的动态 MoE 上假设 XLA 能直接编过。不要把 GShard 的 mesh 轴抄到 NVLink 8 卡域上当专家并行度——域的大小不同，置换的代价不同。

\(k=2\) 的质量收益要用双倍专家计算与更复杂的缓冲来买。若目标是实现简单、通信体积小，Switch 的 \(k=1\) 更干净，但丢失第二专家的插值。负载均衡失败时，看起来参数很多，有效容量接近小稠密网——这是路由问题，切分再自动也救不了。

出处：Lepikhin 等，GShard，arXiv:2006.16668；Google Research 出版物页。ICLR 2021 条目与 arXiv 2020 预印本是同一工作。实现细节以论文与随后 XLA/GSPMD 文档为准，不引用未公开的内部 mesh 带宽表。

小结 ​

  • GShard = 稀疏 MoE Transformer + 面向 XLA 的自动切分标注，而不是新的注意力公式。
  • 超过 600B 参数的多语言翻译模型在 2048 个 TPU v3 上约 4 天训完，是该论文的主实验，不是硬件保修条款。
  • 参数大约 16× 时计算大约 3.6×，来自条件计算；通信与容量因子决定稀疏能不能落到墙钟。
  • 模型按单设备写，切分策略写在少数张量上；专家维应对准高带宽 mesh 轴。
  • 后继分区见 GSPMD，\(k=1\) 见 Switch；GPU 上要重写通信，不能照抄 TPU permute。
  • 出处：Lepikhin 等，GShard，2020。
