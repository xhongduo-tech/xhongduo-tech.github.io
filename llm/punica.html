Punica 背景批 ​

基座前向对所有租户形状相同，可以走普通批矩阵乘；差异只在低秩增量。核要能把不同 $A,B$ 收进同一次 launch，否则「共享基座」只省显存、不省 decode。

—— Chen et al., Punica: Multi-Tenant LoRA Serving, MLSys 2024

LoRA 把适应写成 \(\Delta W=BA\)。单租户可以把增量合并进 \(W_0\)，decode 与基座相同。多租户一旦为每个 \(BA\) 存一份合并后的满秩权重，显存按租户线性涨，切换还要重载数 GB。Chen 等人 2024 年的 Punica 把问题反过来：GPU 上常驻一份预训练基座（他们称为 backbone），KV 占大头，适配器按需从主机换入；基座的密集投影对整批做一次 GEMM——这就是背景批——再用特制 CUDA 核把各请求自己的 \(BAx\) 加回去。本篇只写这条批处理契约与 SGMV 核，集群分页与异构秩的展开见 多 LoRA 服务，动态合并见 dLoRA。

问题 ​

朴素多租户有三条死路。一是每适配器一份完整引擎，基座复制 \(N\) 份，HBM 先爆。二是请求到来时把 \(BA\) 合并进 \(W_0\) 再跑：合并本身是大 GEMM，租户一抖就合并风暴，且同一 batch 不能混租户。三是不合并、在 Python 里对每个样本做小矩阵乘：基座部分仍可成批，LoRA 路径却打散成许多 launch，decode 的 GEMV 小到吃不满 Tensor Core，吞吐掉回「几乎没批」。

Punica 的观察钉在 decode。前填算术强度高，批不批对延迟几乎线性；decode 每步一条查询，扫完整权重，批从 1 增到 32 时墙钟只涨一点，利用率却可以拉满——这是 连续批 早已用过的事实。问题是：连续批假定同一份权重。不同 LoRA 的请求若不能进同一迭代，基座的背景 GEMM 就被租户边界切断，GPU 仍按「每个适配器一个小批」空转。

背景与增量必须拆成两次乘 ​

记线性层 \(y=W_0x+BAx\)。左边 \(W_0x\) 对所有租户相同形状，是背景；右边 \(BAx\) 的 \(A,B\) 按请求 gather。若把 \(W_0+BA\) 先加再乘，背景就不再可批。Punica 坚持不合并：背景走现成 GEMM，增量走新核。于是「多 LoRA」的边际成本是低秩部分，而不是整网。

「背景批」不是把适配器放到后台线程去加载那么简单。加载可以毫秒级、与迭代重叠；真正挡住吞吐的，是 decode 步里基座权重每步扫一遍时，查询维能不能攒厚。核若不支持跨适配器批，加载再快也只是把空转从 PCIe 换到 SM。

方法 ​

一批里第 \(i\) 条请求使用适配器 \((A_i,B_i)\)，秩为 \(r\)。基座

\[y_0 = W_0 x \]

与租户无关，一次 GEMM 出整批。LoRA 分支为

\[y = y_0 + B_i A_i x \]

（实现里常再乘 \(\alpha/r\)）。Punica 把 \(x\mapsto Ax\) 与 \(v\mapsto Bv\) 收成同一种算子：Segmented Gather Matrix-Vector Multiplication（SGMV）。先按适配器 id 把同一 \(A,B\) 的请求排成连续分段，记分界 \(s_0=0<\cdots<s_n=B\)，第 \(k\) 段对应一个 LoRA：

\[Y[s_k:s_{k+1}] \mathrel{+}= X[s_k:s_{k+1}]\, W^{(k)}, \]

其中 \(W^{(k)}\) 是该段的 \(A\) 或 \(B\)。一次 kernel launch 覆盖整批所有分段，而不是每租户一次小核。

SGMV 再按形状分成 shrink 与 expand。\(v=xA\) 把 \(d_{\mathrm{in}}\) 收到 \(r\)，是 shrink；\(y=vB\) 把 \(r\) 扩到 \(d_{\mathrm{out}}\)，是 expand。CUDA 上把 LoRA 下标绑到 blockIdx.y，同一适配器的矩阵乘落在一组 threadblock 里，便于复用 \(A,B\) 的片上缓存。expand 沿输出维切块，shrink 沿输入维切块，两套日程不同，因为低秩维太窄，不能套同一套 GEMM tiling。

同适配器相邻，跨适配器仍同核 ​

分组不是为了退回「一租户一批」。微基准里，把不同 LoRA 混进同一 SGMV 与把同一 LoRA 重复 \(B\) 次，步延迟几乎不可分——这是 Punica 敢把调度写成「往已激活 GPU 上堆任意租户」的数值前提。分组只是提高同一 \(A,B\) 的运算强度，让 Tensor Core 有连续块可吃；核语义本身允许段与段之间 \(W^{(k)}\) 完全不同。

适配器按需加载。基座已在 HBM，冷 \(A,B\) 体积是 \(r(d_{\mathrm{in}}+d_{\mathrm{out}})\) 量级，相对 7B/70B 权重是百分之一到千分之一。论文报告加载是毫秒级，因此新租户不必等一份完整模型冷启动。集群调度把新请求尽量打到已经在跑的 GPU，只有这批卡打满才开新卡；已有请求再周期性迁移，把碎片工作收拢，空出的卡可以关机或还给训练。这与 KV 感知路由 正交：前者键是适配器与容量，后者键是前缀指纹。

机制 ​

背景批值钱的物理事实是 decode 屋顶线：每步几乎要把 \(W_0\) 从 HBM 读一遍。批大小 \(B\) 把这次读出摊到 \(B\) 条查询上，算术强度上升。若 \(B\) 被「每适配器一个小批」切开，摊销消失，每条请求仍付接近单请求的权重带宽。SGMV 把不规则 gather 留在一个核里，避免 \(N\) 次 launch 的 CPU 与流水线气泡；分组则让同一 \(A,B\) 的行在 L2 / 共享内存上被相邻 warp 复用。秩 \(r\) 增大，LoRA 部分相对背景的时间比例上升；当 \(r\) 大到接近「再训一小层」，背景批的优势缩小，应考虑把热租户合并，见 dLoRA。

调度与核是同一条假设的两面 ​

因为跨 LoRA 批与同 LoRA 批一样便宜，调度器不必为「这个 GPU 已经加载了哪些适配器」付出吞吐税，只需付加载时延。于是巩固（consolidation）成为一等策略：少开卡、把运行集堆厚。代价是单卡上的适配器工作集与 KV 抢同一块 HBM。Punica 把大头留给 KV，适配器当可换页的小对象；这与后来 S-LoRA 的统一页池是同一压力的不同答案。论文在固定集群上相对「每个 LoRA 当完整模型来服」报约 12 倍吞吐、每 token 大约 2 ms 额外延迟——这是他们 Llama-2 + A100 设定下的数字，不是跨硬件定律。

不要把 Punica 仓库的 API 当成 Hugging Face 的稳定接口。vLLM、TGI、LoRAX 后来都接了同类 gather 核，日程、是否支持同批多秩、是否要求 \(A,B\) 连续，以各项目当时文档为准。

边界与工程取舍 ​

SGMV 假定各适配器插在同一组线性层上，形状与缩放可在核内对齐。目标模块集合不同（只 \(W_q,W_v\) 对上 FFN 全插）、数值尺度 \(\alpha/r\) 不同、以及与 QLoRA 基座 4-bit 解量化路径耦合，都会让「一次背景 GEMM + 一次 SGMV」这条管道裂开。基座量化后 \(W_0x\) 与 \(BAx\) 的数值域要对齐，否则低秩分支在半精度下被淹没或溢出。

安全隔离：多租户共享 \(W_0\) 意味着侧信道模型与单租户相同，适配器文件本身是机密。页上的 \(A,B\) 下线应有明确回收，不要假设「换下就清零」。热更新进行中的请求应钉住旧版本，见 适配器热更新。HTTP 上的适配器 id 必须进入路由指纹，KV 是过了该 LoRA 之后的键值，不能跨适配器复用。

Punica（arXiv:2310.18547）与 S-LoRA（arXiv:2311.03285）是同期工作。S-LoRA 写明部分 decode 核改自 Punica 早期实现，并强调统一分页与多 GPU TP。引用吞吐数字时不要跨设定比大小；本篇的「背景批」专指基座 GEMM 可跨租户成批这一条。

小结 ​

  • Punica 的背景批：一份基座、\(W_0x\) 对整批做密集 GEMM，差异只在低秩增量。
  • SGMV 按适配器分段 gather，一次 launch 做完 shrink（\(xA\)）与 expand（\(vB\)）；同 LoRA 相邻以提高运算强度。
  • 跨适配器批与同适配器批延迟接近，调度才能把多租户堆到少数已激活 GPU 上。
  • 冷适配器按需加载是毫秒级；巩固与迁移用来少开卡，不是用来替代核。
  • 秩很大、模块集合不一致、量化基座未对齐时，背景批的假设失效。
  • 出处：Chen, Ye, Wu, Zhuo, Ceze, Krishnamurthy，Punica: Multi-Tenant LoRA Serving，MLSys 2024，arXiv:2310.18547。
