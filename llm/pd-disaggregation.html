PD 分离 ​

Prefill 偏计算、decode 偏带宽，绑在同一张 GPU 上会互相抢时间和并行策略；拆到不同池子，才能各自满足 TTFT 与 TPOT，并按阶段选硬件。

—— Zhong et al., DistServe, OSDI 2024；Patel et al., Splitwise, ISCA 2024

一次生成请求先经历 prefill：把整段提示并行算完，写出 KV，得到首 token（TTFT）；再经历 decode：逐步吐后续 token，每步时间构成 TPOT。Colocate 系统把两阶段编进同一连续批，长 prefill 插入时 decode 步被拉长，decode 占着 HBM 时 prefill 又凑不齐算力。并行策略也被耦合：为 TTFT 加的 张量并行 可能伤害 decode 的 All-Reduce 账，为吞吐加的 流水线 可能伤害单请求延迟。Zhong 等人的 DistServe 把两阶段拆到不同 GPU 实例，按 TTFT/TPOT 分别搜资源与并行，优化 goodput（满足双 SLO 的最大速率）。Patel 等人的 Splitwise 从表征出发做阶段拆分，并强调异构硬件与功耗：prompt 需要新卡的算力，generation 可以用更低功耗、更低成本的机器。本篇写为何拆、怎么分池，KV 怎么搬见 下一篇。

问题 ​

Prefill 在提示不算极短时接近 compute-bound：序列长，GEMM 能喂饱 Tensor Core。Decode 每步一个新 token，却要读全部权重与日益增长的 KV，接近 memory-bound。两者的最优 batch、最优并行、甚至最优 GPU 代数都不同。绑在一起时，调度只能优先其中一个 SLO，或靠超配同时满足两个。Chunked-prefill 加 piggyback 把长提示切开与 decode 拼批，能减轻 decode 被单次长 prefill 堵住，但 DistServe 指出干扰并未消除：块太小则 prefill 自己不饱和且与 decode 争用；块大到饱和则几乎拼不进 decode；prefill 还会重复扫 KV，多付内存访问。

并行耦合是第二层问题。Intra-op 降执行时间、要 NVLink；inter-op 扩速率、少降延迟。Colocate 实例只能选一套。拆开之后，prefill 实例可以按紧 TTFT 走更大 TP，decode 实例按 TPOT 与 KV 容量走复制或不同的 PP。

Goodput 不是吞吐 ​

吞吐可以靠牺牲延迟堆上去。DistServe 优化的是在 TTFT 与 TPOT 同时满足（评测里对 \(>90\%\) 请求达标）时，每 GPU 能吃的请求率。这个指标让「拆开之后多复制了一份权重」的代价可见：权重多占卡，但若干扰消失、并行更贴合，达标速率仍可升。论文报告在多种模型与聊天、编程助手、摘要负载上，相对当时 SOTA 可达约 7.4 倍请求率或约 12.6 倍更紧的 SLO。数字钉在他们的引擎与负载上，不是宇宙常数。

实例（instance）在 DistServe 里是「一份完整模型权重对应的资源」，内部可以有多卡模型并行。拆分后有 prefill 实例与 decoding 实例，权重至少两份。不要把「一张卡既做 P 又做 D」还叫做分离。

方法 ​

请求进入 prefill 实例，只算提示、产首 token 与 KV，再把中间状态交给 decode 实例继续生成。Decode 计算利用率低时，可以多个 prefill 实例对应一个 decode 实例，让 decode 侧堆起更大的连续批，把带宽墙推向计算墙。资源搜索分两层：先在单副本上为两阶段分别选 GPU 数与并行策略，使每卡 goodput 最大；再用复制把该配比扩到目标流量。放置还要看集群带宽：跨节点 InfiniBand 足够时 P/D 可任意节点对；节点内 NVLink 强、跨节点弱时，要把对应层段放进同一节点，让 KV 走 NVLink（细节见 KV 传输篇）。

Splitwise 的异构池 ​

Splitwise 的表征结论与 DistServe 一致：prompt 计算密集，generation 内存密集且往往吃不满最新 GPU 的算力。于是可以做同构拆分，也可以做异构：P 池用高算力卡，D 池用更便宜或更低功耗的卡。调度分集群级（请求进哪类机器）与机器级（批处理）。另设 mixed 池在突发时两阶段都能接，避免硬隔离导致一侧空、一侧炸。相对当时 colocate 设计，论文报告可达约 1.4 倍吞吐并降约 20% 成本，或在同样功耗与成本预算下约 2.35 倍吞吐。DistServe 正文把 Splitwise、TetriInfer、DéjàVu 列为同期分离工作，侧重点不同：DistServe 更强调双 SLO 下的 goodput 与带宽感知放置。

和 colocate 优化的边界 ​

连续批、PagedAttention、GQA 在分离之后仍然需要：分离解决的是阶段干扰与并行耦合，不解决 KV 碎片或头数。Chunked-prefill 在分离后不再承担「保护 decode」的任务，仍可用于限制 prefill 激活。投机解码打在 decode 池上，接受率 与 decode batch 互动；prefill 池一般不跑草稿树。MoE 上 P/D 可取不同 EP 度，这是分离送给稀疏模型的额外自由度。

机制 ​

机制是消除时间轴上的互抢，以及解开并行搜索的笛卡尔积。Colocate 的每一步 iteration 里，prefill token 与 decode token 争 SM、争 HBM 带宽、争调度槽。拆开后，P 实例的迭代全是高算术强度，D 实例的迭代全是逐步 decode，CUDA Graph、并行度、甚至功耗帽都可以按阶段固定。代价是 KV 必须在阶段边界移动，且权重复制。当传输时间小于从前干扰造成的等待，goodput 上升；当传输是墙，分离失败——所以放置算法是方法的一部分，不是运维附属。

Splitwise 再加一条：generation 不需要「最新 GPU 的峰值 FLOPs」，把新卡留给 prompt，能在集群功耗墙内提高总吞吐。这是硬件异构，不是算法异构。同构集群上 DistServe 的逻辑仍然成立。

TTFT 统计在分离后包含排队、prefill 执行与 KV 传输。若把传输算到 TPOT 里，SLO 归属会错，搜索机会往错误的池加卡。定义要在评测里写死。

突发与排队 ​

流量突发时，大量 KV 同时涌向 decode 会打满 D 侧显存。DistServe 用 pull：decode 按需来取，P 侧 GPU 内存当队列缓冲，两边各按自己的节奏跑。Splitwise 的 mixed 池是另一缓冲：暂时允许某台机器两阶段都做。没有这类阀门，分离系统会在峰值上比 colocate 更脆——colocate 至少「慢在同一张卡上」，分离会「D 侧 OOM、P 侧还在狂写」。

边界与工程取舍 ​

分离增加运维维度：两套扩缩、两套并行、一套传输、一套失败恢复。小流量、短提示、松 SLO 的服务，colocate 更简单，未必值得拆。KV 极大（超长上下文、未压缩 MHA）且互连弱时，传输税会吃掉干扰收益，应先压缩 KV 或同节点放置，再谈拆。权重复制让小模型的卡数翻倍更疼；大模型反正已经多卡，增量相对小。

不要把 PD 分离写成「P 用 CPU、D 用 GPU」或任意异构神话；Splitwise 的异构是 GPU 代数与功耗档，不是随便降级到不能跑模型的设备。不要伪造第三篇「PD 分离原论文」的 arXiv。可引用的就是 DistServe（arXiv:2401.09670）与 Splitwise（arXiv:2311.18677）。后续生产框架的实现以各自文档为准，性能数字随版本变。

评测必须同时报达标率、TTFT、TPOT、每 GPU 请求率。只报吞吐，分离看起来永远赢，因为可以把延迟藏在队列里。DistServe 用 goodput 就是为了堵住这条偷懒。

小结 ​

  • Prefill 与 decode 的 roofline、SLO、最优并行都不同；colocate 造成干扰并耦合资源配置。
  • DistServe 拆到不同实例，分阶段搜并行与复制，优化双 SLO 下的 goodput；报告约 7.4× 速率或约 12.6× 更紧 SLO。
  • Splitwise 强调阶段表征与异构/功耗，报告约 1.4× 吞吐降成本，或同预算约 2.35× 吞吐。
  • 权重复制与 KV 传输是代价；放置与 pull 队列是方法，不是可选项。
  • 小流量或弱互连上分离可能不划算；chunked-prefill 不能替代拆分。
  • 出处：Zhong et al., DistServe，OSDI 2024，arXiv:2401.09670；Patel et al., Splitwise，ISCA 2024，arXiv:2311.18677。
