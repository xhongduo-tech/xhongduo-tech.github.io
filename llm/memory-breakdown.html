显存占用分解 ​

一张加速卡上的字节不是一锅粥：权重相对固定，KV 随并发与长度涨，激活在前填时冒尖，碎片让「还剩好几 GB」的同时接不进下一条请求。

—— 对照自回归服务中权重、KV 缓存、激活与分配器碎片的账单拆分

显存打满是生成服务最常见的硬墙之一，但「打满」需要拆开看。模型参数、优化器状态（训练才有）、KV 缓存、前填激活、CUDA 上下文与工作区、以及分配器碎片，占用的原因和治理手段都不同。把 OOM 一律归因于「模型太大」，会错过分页 KV、减并发、切前填块、或换 GQA 这些便宜得多的杠杆。本篇给推理服务一张分解账单；带宽意义上的墙见 decode 显存墙，分页如何消灭预留空洞见 PagedAttention。

问题 ​

推理稳态下，一块 GPU 的 HBM 大致被五类对象切开。权重：\(P\) 个参数乘每参数字节（FP16 为 2，INT8 为 1，FP8 类似）。KV：每条请求、每层、每个 KV 头、每个已写入位置，键与值各一份。激活：前填时与序列长度、层宽、批内 token 数成正比，解码时激活很小。运行时：驱动、NCCL、cuBLAS workspace、torch CUDA 上下文，常是数 GB 级常数。碎片：逻辑占用低于水位，却没有形状合适的空闲块。

产品看到的症状混在一起：并发上不去、上下文长度加一点就炸、前填某条长提示时尖刺 OOM、或「nvidia-smi 显示还有空」但分配失败。不分解，就不知道该量化权重、该压缩 KV、该限制前填 token 预算，还是该换分页分配器。训练侧还要把 Adam 动量、梯度、检查点激活算进去；本篇范围是服务。

权重是地板，KV 是可变项 ​

权重在加载后几乎不变（LoRA 多适配器是例外，见多 LoRA 服务）。它决定最低卡型：70B 的 FP16 约 140 GB，必须切多卡或量化。KV 才是并发与长度的函数。粗算一条请求一层的字节：

\[\mathrm{KV}(n)\approx 2\cdot L\cdot n\cdot h_{\mathrm{kv}}\cdot d_k\cdot b, \]

因子 2 为 K 与 V，\(L\) 层数，\(n\) 当前上下文，\(b\) 元素宽度。\(h_{\mathrm{kv}}\) 在 MHA 等于查询头，GQA / MQA / MLA 把它打下来。系统总 KV 是运行集上 \(\sum_r \mathrm{KV}(n_r)\) 再加页内浪费。并发 16、每条 8k、大模型未压缩时，KV 可以超过权重，成为一等公民。还按「模型文件多大」去买卡，会在长上下文上突然破产。

查询头数不进 KV 公式。把 \(h_q\) 代入会把容量需求高估 \(h_q/h_{\mathrm{kv}}\) 倍。规划并发与窗口时，必须以 KV 头为准。

方法 ​

建议在引擎里暴露四条水位，而不是一个 memory_allocated。权重（及常驻量化表）、KV 池（已用页 / 已分配页）、激活峰值（按最近前填）、运行时保留。OOM 时打哪一条涨，决定动作：权重量化或切并行；KV 则减最大并发、减窗口、KV 量化、驱逐或拒绝；激活则切 chunked prefill 或减前填批；运行时则查是否重复初始化上下文、是否 workspace 过大。

分页把 KV 从「按 max_seq_len 预留」改成「按实际 token 买页」。逻辑占用接近 \(\sum n_r\)，内部碎片约半页 × 请求数 × 层 × 头结构。页太大，内部浪费明显；页太小，页表与核间接开销涨。未分页时外部碎片会让水位看起来还低就分配失败——这是账单上必须单列「不可用空闲」的原因。

前填激活与解码的不对称 ​

前填要对 \(n\) 个位置保留注意力与 FFN 的中间张量（即使 FlashAttention 不物化 \(n\times n\) 分数，FFN 激活仍随 \(n\) 线性、宽随 \(d\)）。一条 100k 提示的激活尖刺可以短暂超过 KV 池里所有短聊天之和，把本已安全的水位打穿。解码步的激活与批大小成正比、与 \(n\) 弱相关，通常不是容量主角，带宽才是。因此「能 decode 128k」的配置，仍可能在「prefill 128k」上 OOM——两条路径要分别压测。

机制 ​

容量墙与带宽墙同源不同证。容量：上述各项之和超过物理 HBM（再扣保留）。带宽：每步要搬的权重加 KV 超过总线，TPOT 变差，但 smi 显示还没满。压缩 KV 同时缓解两者；加并发在容量允许时改善权重摊销（吞吐升），同时增加 KV 字节（更接近容量墙）并增加每步要扫的 KV（带宽更紧）。这是同一旋钮的三面，不能只看占用百分比。

切并行不一定切 KV 池 ​

张量并行把权重按列/行切开，每卡权重下降，但 KV 是否切开取决于实现：有的每卡存全量 KV（浪费容量换通信形状），有的沿头或序列切。规划多卡时必须读清 KV 复制因子，否则「切 8 卡」并不给出 8 倍 KV 池。流水线并行每卡只持有部分层的 KV，容量按层分摊，但气泡与调度是另一笔账。

碎片不只来自 KV。PyTorch 缓存分配器持有已释放但未归还驱动的块，会出现「业务以为释放了、smi 仍高」。服务进程应在稳态看 reserved 与 allocated 之差；差值长期膨胀要查缓存与碎片，而不是再买卡。

边界与工程取舍 ​

量化权重减地板，可能伤质量；量化 KV 减可变项，可能伤长程检索（针测会先红）。驱逐与滑窗减 \(n\) 的有效部分，任务若要精确中间事实，会与 NIAH 冲突。这些是质量换容量，必须配对评测，不能只报「能上 32 并发」。

多 LoRA、多模态视觉塔、投机草稿模型，都是额外常驻权重。账单要加行，否则主模型看着能进，加上适配器就 OOM。CPU 卸载权重或 KV 把容量墙挪到 PCIe：占用问题变成延迟问题，TTFT / ITL 报表会说话。

不要用训练时的「激活检查点省显存」直接套解码服务。解码没有长反向图；前填的激活策略与训练时的重算不同。把训练的 memory profiler 截图拿来估 vLLM 实例，数量级会对不上。

nvidia-smi 是进程级粗表，含驱动上下文，不含逻辑 KV 页数。容量治理应以引擎内部计数为准，smi 只做对账。两者差很多时，先查泄漏与碎片，再查公式。

小结 ​

  • 服务显存应拆成权重、KV、前填激活、运行时、碎片；OOM 要对号入座再动手。
  • 权重是地板；KV 随 \(L,n,h_{\mathrm{kv}},b\) 与并发线性涨，长上下文下可超过权重。
  • 分页消灭外部预留空洞，仍留内部半页浪费；未分页时「有空闲」也能分配失败。
  • 前填激活尖刺与解码容量要分开压测；能 decode 的长度未必能一次 prefill。
  • 切并行时核对 KV 复制因子；量化与驱逐是质量换容量。
  • 用引擎水位对账，而不是只用 smi。
  • 出处：对照 PagedAttention / vLLM 的 KV 池模型与自回归服务的权重–缓存–激活分解；带宽侧见 decode 显存墙。
