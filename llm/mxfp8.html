MXFP8 ​

MXFP8 不是第三种 FP8 编码，而是给已有的 E4M3 / E5M2 加上块级 E8M0 尺度，让 8-bit 训练少依赖一张量一个 amax。

—— OCP MX Specification v1.0；Rouhani et al., arXiv:2310.10537；对照 NVIDIA 的 MXFP8 预训练配方

OCP 8-bit 浮点（OFP8）已经把 E4M3 与 E5M2 钉成可互换编码，见 FP8 推理 与 Micikevicius 等人 2022 年的联合白皮书。Hopper 上的 Transformer Engine 默认仍是每张量一个 FP32 尺度：统计 amax，量化，再 GEMM。张量里若同时有尖峰通道与大量近零值，一个 amax 会把格子浪费在尖峰上。MXFP8 把同一套元素格式嵌进微缩放块：32 个 FP8 元素共享一个 E8M0 尺度。它增强的是 8-bit 的稳健与可移植，峰值吞吐的跃迁通常留给 MXFP4。本篇写 MXFP8 相对逐张量 FP8 多了什么、训练配方改了哪一条、以及 Blackwell 上的 MX 路径与 Hopper TE 如何分家。

问题 ​

E4M3 尾数相对够用、范围窄；E5M2 范围宽、尾数糙。逐张量缩放能把整张量的 amax 映射到格式最大值附近，但对 LLM 激活的通道异常值不友好：少数维吃掉指数头空间，其余维量化阶梯变粗。这是 LLM.int8() 与 SmoothQuant 在 INT8 上遇到的同一结构，只是 FP8 自带指数，症状来得晚一些。把尺度从张量级改到通道级或 token 级，软件可行，MMA 若仍按整张量一个 scale 发射，硬件吃不到细粒度。

MX 联盟的目标之一是「增强现有 8-bit 格式的稳健，降低亚 8-bit 的用户摩擦」。MXFP8 因此不是新的 8-bit 编码——元素必须遵守 OCP FP8 规范——而是规定：块大小 32，尺度 E8M0。实现可以只支持 E4M3 或只支持 E5M2，二者算不同具体格式。问题变成：块尺度是否让预训练可以全程 E4M3、还是仍要 HYBRID；以及模拟出来的损失曲线，在没有 MX Tensor Core 的 GPU 上有没有吞吐意义。

存储：264 bit 一块 ​

每块 \(8 + 32\times 8 = 264\) bit，合 8.25 bit/元素。相对裸 FP8 的 8 bit，多出的 0.25 是共享指数。布局规范不强制尺度与元素连续存放，实现可以把尺度打成旁路向量。点积语义与 MXFP4 相同：元素乘积累加后乘回两个块尺度。转换算法同样把块内最大值映射到元素格式的最高 binade，再量化；溢出处理必须支持 OCP FP8 规定的饱和（SAT）与溢出（OVF）两种，由属性选择。

不要把 MXFP8 的 8.25 bit 四舍五入成「还是 FP8」。检查点体积、对齐、以及核是否按 32 对齐切块，都会被这 8 bit 尺度打乱。Hopper 的逐张量 FP8 检查点不能当 MXFP8 加载；反过来，把 MX 尺度丢掉再当 OFP8 用，等于随机重缩放。

方法 ​

推理：白皮书称 8-bit MX 格式可对多种已训练的 FP32 模型 direct-cast，不必校准或微调，精度接近基线。这是 MXFP8 / MXINT8 相对 MXFP6/MXFP4 的主要卖点。LLM 权重与激活是否同样「直接投射即无损」，要以具体模型与是否含异常通道为准，不能把视觉分类表抄到生成式服务 SLA 上。

训练：微缩放让块内动态范围分开，前向全程 E4M3 变得更可行——不必靠 E5M2 的宽指数去接梯度尖峰，因为尖峰往往落在少数块，只抬那些块的 \(X\)。NVIDIA 后续的 Recipes for Pre-training LLMs with MXFP8（Tseng 等，arXiv:2506.08027）在 Blackwell 原生 MX Tensor Core 上走这条路：用 FP8-E4M3 元素加特定转换算法，做到与 BF16 预训练对齐，模型做到 8B、数据到 15T token 量级。那篇强调两件事：转换算法（不是任意 round）与硬件原生 MX。把它的结论写回 Hopper 的 DelayedScaling，是代数错误。

与 DelayedScaling 的交接 ​

逐张量 DelayedScaling 用历史 amax 窗口避免每步双倍读，见 FP8 训练。MXFP8 的尺度在块上当场由块内 amax（或规范允许的其它转换）决定，统计粒度变细，陈旧窗口的必要性下降，但元数据流量上升：每 32 个元素多 8 bit，还要在分布式切分时保证块边界与分区对齐。张量并行若把一块 32 切开，块尺度归属破裂。GSPMD / Megatron 的切分必须落在块边界上，这是 MX 训练集成里最容易静默出错的地方。

Transformer Engine 在 Blackwell 上提供 MXFP8BlockScaling 一类配方，与 Hopper 的 DelayedScaling 并列，不要共用同一套 amax 历史去「验证」两条路径。推理校准得到的逐张量 FP8 尺度，也不能拿来当 MX 块尺度用。

机制 ​

块尺度把「一张量一个增益」拆成「每 32 元一个 2 的幂增益」。通道异常值若在空间上聚集，它们会独占若干块的尺度，其余块保留更细的相对网格——这是相对逐张量 FP8 的稳健来源。若异常值沿块均匀散开（旋转、Hadamard、QuaRot 一类预处理会改变这一点），块尺度的优势缩小，问题回到元素尾数本身。

E8M0 没有尾数，块增益是离散的。相邻两步若 amax 跨过 2 的幂边界，整块突然加倍或减半，等效于给该块乘一个阶跃。大 batch 预训练里 amax 平滑，阶跃少；微调与 RL 的尖峰更密，需要看溢出/饱和计数，而不是只看最终 loss。HYBRID 在 MX 下仍可能有用：反传梯度若块内动态范围仍比对 E4M3 更暴力，E5M2 元素更合适。Tseng 等人选择全程 E4M3，是因为他们的转换与数据配方让梯度进得去；换数据集不应默认拷贝。

Blackwell 产品材料里 MXFP8 与 MXFP4 的峰值常分栏。MXFP6 有时与 MXFP8 同吞吐，暗示走同一条数据通路、只是编码更窄。不要用 MXFP6 的「更窄」去推更高 TFLOPS。表头稀疏峰值另算。

边界与工程取舍 ​

布局未标准化 ​

MXFP8 不能替代 softmax、LayerNorm、损失里的宽格式。微缩放管的是 GEMM 操作数。Hopper 没有原生 MX MMA，在 H100 上模拟 MXFP8 只验证数值。服务栈若只实现逐张量 FP8 KV / 权重，加载 MX 检查点会错。OCP 允许实现只支持子集：一张只报 MXFP8 E4M3 的卡，不是「支持 MX」。

与 INT8 微缩放（MXINT8，同样块 32 + E8M0）相比，MXFP8 保留元素指数，对块内仍跨 binade 的分布更友好；MXINT8 块内是均匀整数格子。选型看硬件通路，不是看名字里的 8。

跨厂商互换是 MX 的政治目标。真正互换还要约定块沿哪一维切、行列主序、以及 GEMM 布局（例如某些实现要求特定 swizzle）。规范不规定内存 layout。导出权重时要把 vendor 的 layout 注记写进文档，否则「OCP 兼容」只保证解码单个块，不保证整网能直接 GEMM。

出处：OCP MX v1.0 表中的 MXFP8（元素 OFP8 E4M3/E5M2，块 32，尺度 E8M0）；Rouhani et al., arXiv:2310.10537；Micikevicius et al., FP8 Formats for Deep Learning, arXiv:2209.05433；Tseng et al., Recipes for Pre-training LLMs with MXFP8, arXiv:2506.08027。Hopper 逐张量路径对照 NVIDIA Transformer Engine 用户指南。

小结 ​

  • MXFP8 = OFP8 元素 + 每 32 个值一个 E8M0 尺度，约 8.25 bit/值，不是新的 E4M3 编码。
  • 块尺度缓解逐张量 amax 被异常通道绑死；direct-cast 推理是白皮书对 8-bit MX 的主主张。
  • Blackwell 上的 MX 训练配方（如全程 E4M3）不能原样搬到 Hopper DelayedScaling。
  • 切分必须对齐块边界；丢掉尺度等于随机重缩放。
  • 峰值跃迁看 MXFP4；MXFP8 买的是稳健与可互换。
  • 出处：OCP MX v1.0、Rouhani et al. 2310.10537、OFP8 白皮书与 MXFP8 预训练配方论文。
