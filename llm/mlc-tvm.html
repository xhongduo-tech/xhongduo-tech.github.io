MLC / TVM 编译 ​

把模型从框架图降到可生成代码的张量程序，再用调度与自动调优对准每一种后端；LLM 部署于是变成编译问题，而不是为每块芯片手写一份运行时。

—— Chen 等，TVM: An Automated End-to-End Optimizing Compiler for Deep Learning，OSDI 2018；MLC-LLM 项目说明

Apache TVM 要解决的是：深度学习算子在 GPU、手机、加速器上不能都靠厂商闭源库。Chen 等人把图级融合与算子级张量表达式、调度原语、基于学习的代价模型放进同一编译器，为 CPU、移动 GPU、服务器 GPU 以及当时的 FPGA 类后端生成代码。MLC-LLM（Machine Learning Compilation for LLM）把这条栈接到大模型：用 TVM Unity / Relax 一类 IR 导入开放权重，生成可在 CUDA、Vulkan、Metal、WebGPU 等目标上跑的运行时，并叠上分页 KV、连续批、前缀缓存等服务端已经证明过的机制。本篇写 编译 如何改变 LLM 的可移植性，对照 llama.cpp 的手写多后端与 TensorRT-LLM 的 NVIDIA 特化。

问题 ​

LLM 的计算图看起来重复：线性层、RMSNorm、RoPE、注意力、SwiGLU。每换一块硬件，却要重写：CUDA 核、Metal shader、WebGPU、NPU 厂商 SDK。手写三条后端已经很贵，还要跟新结构（GQA、滑动窗、MLA）。厂商库（cuDNN、TensorRT）在对应 GPU 上很快，一离开该生态就失效。浏览器里的 WebGPU 没有 cuBLAS。

TVM 的设定是：算子写成可变换的张量程序，调度（tiling、向量化、共享内存、张量化到 MMA）与硬件原语解耦，自动搜索或代价模型挑选调度。图级再做融合，减少中间写全局内存。对 LLM，还要处理 动态序列长度 与逐步 decode：这与 2018 年以静态 CNN 为主的评测不同，也是 Relax / TVM Unity 要把动态形状和一等函数放进 IR 的原因。不能编译动态轴，就只能为每个 \(n\) 特化一份引擎，或把 decode 打回低效的通用循环。

两个术语翻译：「tiling（分块）」是把一个大矩阵切成能塞进芯片小缓存的小块，免得每算一步都跑一趟慢内存；「向量化」是让一条指令同时算 8 个或 16 个数而不是 1 个。类比搬家：tiling 是把大件家具拆成能进电梯的箱子，向量化是每次搬 16 个盒子而不是一趟一个——都是「怎么搬」的问题，跟「算什么」无关。

可移植不等于一次生成万能二进制 ​

编译器为每个目标出一份库。可移植性是 同一前端、多份 codegen，不是一个 ELF 跑遍所有 ISA。WebGPU 与 CUDA 的共享内存模型不同，调度必须重搜。MLC 的主张是：优化知识（融合注意力、分页 KV 布局）可以在目标之间迁移，核由编译器重写，从而在工程带宽不够手写 Vulkan 时仍能把 CUDA 上验证过的算法搬过去。

2018 年 TVM 论文的实验对象是 ResNet、MobileNet、加速器上的通用卷积，不是 70B 自回归服务。把 OSDI 数字直接写成「TVM 让 LLM 加速 × 倍」是张冠李戴。LLM 数字应来自 MLC 项目当时的发布说明与可复现基准，并钉模型与设备。

方法 ​

前端导入：从 PyTorch / Hugging Face 权重进入 Relax 图，算子换成编译器认识的注意力与 GEMM。图级：算子融合、常量折叠、布局变换（如把权重排成后端喜欢的 tile）。算子级：对 GEMM 与注意力写出调度空间，用 AutoTVM / Ansor 一类搜索或手工模板生成 CUDA / Metal / Vulkan 源，再交给各自驱动编译。LLM 运行时部分（连续批、paged KV、前缀缓存、投机解码）以可组合的运行时模块存在：MLC 2024 年的 MLCEngine 说明里，把这些与 FlashInfer 等 CUDA 注意力库在 NVIDIA 上结合，同时用代码生成覆盖更广平台。

端侧与浏览器：同一套编译流程可以出 WebGPU 库，使模型在浏览器本地跑，权重仍量化。这与「服务器上的 vLLM」是不同交付物——没有多租户调度器，但有「无安装、GPU 在终端」的部署面。NPU 路径则取决于该 NPU 是否暴露 TVM 能张量化的指令；不友好的动态控制流仍会打回 CPU，见 NPU 友好算子。

与 ggml 手写核的差别 ​

llama.cpp 为每种 quant × 后端维护手写核，新增量化格式要人写 SIMD。TVM 把核当搜索产物：新后端先声明张量化指令与内存层次，再搜调度。代价是编译时间、调优时间和调试编译器的难度。手写核能精确压榨某一款 CPU 的指令；编译器在「还没有人写过的后端」上胜出。生产上常见混合：NVIDIA 上注意力调用已经极致的库（FlashInfer），其余算子与别的平台走生成代码——MLC 自己的说明也写了这种分工。

机制 ​

性能来自三层。融合减少 decode 每步的 kernel launch 与中间缓冲，对 ITL 很关键。调度把 GEMM 对齐到 Tensor Core / 矩阵单元 / SIMD 宽，算术强度上升。运行时的分页与连续批则与 vLLM 同类，解决的是并发与碎片，不是编译器独有数学。编译器不能把 \(O(n)\) 的 KV 读取变成 \(O(1)\)；它只能让每次读取的微内核更满。

这张图回答的问题是：「服务慢了，该归咎编译器还是运行时？」初学者容易把三层混成一团，怪「编译不行」就去换栈，其实分页 KV 的碎片与调度无关，融合不足与批处理无关。类比医院分诊：先分清是外科（算子层）、营养科（调度层）还是挂号排队问题（运行时层），再对症下药。

动态形状：若 IR 把序列长度当符号维，生成的核需要动态循环上界，优化空间变小。实践中 decode 常用固定「单查询 × 当前 KV 页」模板，prefill 用分块固定 tile。这与 TensorRT 引擎的 profile 类似，只是代码生成器面向的后端集合更大。量化可以是 IR 上的 dtype 变换：权重以 INT4 存储，计算时插入反量化节点并与 GEMM 融合；融合失败就会出现「先写成 FP16 缓冲」的败笔，端侧尤其疼。

自动调优给出的是在调优集上的局部最优调度。换 batch、换头数、换 GPU 代数，旧日志可能变差。要把调优日志当成该设备该形状的缓存，而不是模型的一部分随权重分发到所有芯片。

浏览器与云共用引擎的意义 ​

MLC 强调同一引擎抽象覆盖云与边：前缀缓存、投机、结构化生成可以在 WebGPU 上复用概念，而不等每条产品线单独实现。概念迁移不等于性能对齐——WebGPU 没有同等的 TMA / Hopper 原语，吞吐会差一截，但功能集合可以接近。这对「隐私本地推理」产品有用：功能清单跟服务器走，性能按设备降级。

边界 ​

TVM 不是 NVIDIA 上默认的吞吐冠军；TensorRT-LLM 吃得到的 Transformer Engine 细节，通用 codegen 要追赶。研究新注意力若含数据依赖稀疏、不规则 gather，调度空间可能搜不到好点，还不如手写。编译失败模式是：动态控制流、自定义归一化、MoE 的不规则专家索引——与 NPU 不友好算子清单高度重叠。

不要给 MLC-LLM 编造独立的经典会议论文编号。系统出处是 TVM OSDI 2018（arXiv:1802.04799）加 MLC 项目与博客（如 2024 年 MLCEngine 介绍）。Relax 另有后续论文，需要单独引用时再钉标题与年份，不要把「Unity」写成不存在的 arXiv。许可证走 Apache TVM 与 MLC 仓库当时的条款；模型权重仍是各家模型许可。

常见误区：以为「编译一次，处处最快」。实际上换一块 GPU 代数、换一个 batch 尺寸，最优调度都可能不同，要重新搜或至少重新验证——「可移植」迁移的是算法与融合知识，不是性能数字。类比导航软件：路线规划逻辑全国通用，但到每个城市都要按当地实时路况重算 ETA。

选编译栈的团队要能读 IR dump 和调度。否则一旦生成核比手写慢，没有人会改 tiling。若团队只会 pip install vLLM，MLC 的优势（WebGPU、奇怪后端）发挥不出来，维护成本却先到。

小结 ​

  • TVM 用图级优化加可搜索的算子调度，为多种硬件生成深度学习代码（OSDI 2018）。
  • MLC-LLM 把该编译栈接到 LLM：导入权重、生成多后端库，并叠上批处理与 KV 管理。
  • 可移植是「一前端多 codegen」，不是单一二进制；NVIDIA 上仍可调用特化注意力库。
  • 动态序列与 decode 模板是 LLM 相对早期 TVM 评测多出来的编译问题。
  • 与 ggml 手写核、TensorRT 特化栈是互补：新后端与浏览器偏编译，单厂峰值偏特化。
  • 出处：Chen et al., TVM: An Automated End-to-End Optimizing Compiler for Deep Learning, OSDI 2018（arXiv:1802.04799）；MLC-LLM / MLCEngine 项目说明（https://github.com/mlc-ai/mlc-llm）。
