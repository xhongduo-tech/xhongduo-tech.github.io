DeepSeek MoE ​

把专家切细，抽出共享支路，让每个 token 走到更多小专家——用激活量换组合，而不是用稠密宽度换组合。

—— DeepSeek-V2 / V3 技术报告，2024–2025

DeepSeek-V2 把 MLA 与 DeepSeekMoE 写进同一份技术报告：注意力侧压 KV，前馈侧用细粒度专家加共享专家。V3 把 MoE 进一步放大到总参数 671B、每 token 激活约 37B，并改用无辅助损失的负载均衡。相对 Mixtral 的 8 专家 top-2，DeepSeek MoE 的关键词是：更多、更小的路由专家，外加始终在线的共享专家，路由到更多小专家而不是一两个大专家。本篇把这套结构收成一篇，共享/细粒度的一般原理见上一篇，这里落在 DeepSeek 的规模、路由约束与和 Qwen2-MoE 的对照上。

问题 ​

稠密模型把容量和计算绑死。Switch 与 Mixtral 解开了一部分，但专家粒度和 Mixtral 的 8 选 2 仍粗：每个专家很肥，组合少，公共知识与专项知识挤在同一套对称专家里。DeepSeek 要的是：在激活参数可控（推理成本接近一个几十 B 的稠密模型）的前提下，把总参数加到数百 B，并让路由有足够的组合自由度去覆盖多语言、代码与长尾知识。

为何不直接复制 Mixtral ​

把 Mixtral 的专家数加到 64、仍保持每个专家像 7B FFN 那样肥，激活 \(k=2\) 时计算立刻不可接受，内存也放不下。必须在「专家变小」的同时「\(k\) 变大」，使激活的中间维总和仍与目标激活量对齐。同时，若 64 个小专家完全对称、没有共享支路，每个专家都会浪费容量去拟合公共变换。DeepSeekMoE 的问题设定就是这两点一起解。V2 与 V3 的专家个数、共享个数、\(k\) 并不相同，但家族特征稳定：细粒度路由专家 + 共享专家 + 设备限制路由。写「DeepSeek MoE」应指这套结构，而不是某一个具体 \(N\)。

方法 ​

DeepSeek-V2 报告中的典型配置：除第一层外的 FFN 换成 MoE；2 个共享专家 + 160 个路由专家，每个 token 激活 6 个路由专家。共享专家始终计算；路由用 token-choice top-\(k\)，输出与共享支路相加。V3 放大为约 1 个共享专家 + 256 个路由专家，激活 8 个路由专家，总参数 671B、激活约 37B。专家内部是标准的 SwiGLU，只是中间维被切细。

设备限制路由（device-limited routing）：每个 token 先看得分最高的专家所在设备，再在有限个设备上补齐 \(k\) 个专家。这样 All-to-All 不会把一个 token 打到所有 EP 节点，通信次数有上限。负载方面，V2 仍用辅助损失；V3 改为专家偏置的无辅助损失策略，减少均衡项对主损失的干扰。

和 Qwen2-MoE、Mixtral 的对照 ​

Mixtral：8 专家、top-2、无共享、专家肥、实现简单，激活比例 \(2/8\)。Qwen2-MoE（如 57B-A14B）：专家数明显多于 Mixtral，含共享专家，激活约 14B，方向与 DeepSeek 同类但规模和 \(k\) 不同。DeepSeek 把细粒度推得更远：\(N\) 到百级，\(k\) 到 6–8，共享支路明确承担公共知识。三者都是稀疏 FFN，不是稀疏注意力；DeepSeek-V2 的 MLA 是另一条轴，不要写进 MoE 公式里。

机制 ​

细粒度的效果是：同样激活中间维，路由选择从「两个大专家」变成「六个小专家的加和」。令每个小专家宽度为 \(w\)，激活通道约 \(k\cdot w\) 再加共享宽度 \(w_s\)。只要 \(k w+w_s\) 对齐目标，FLOPs 就对齐；表达力则来自 \(\binom{N}{k}\) 量级的专家组合。共享专家的梯度来自全部 token，学稳定的公共映射；小专家的梯度来自稀疏子集，学长尾。

训练与推理成本 ​

训练期 EP 必需：256 个专家无法复制到每张卡。设备限制路由把通信从「可能 \(k\) 个任意节点」收成「少数节点」，这是 V2/V3 能训起来的系统条件，不只是算法点缀。推理期激活 37B 左右，远小于 671B 稠密前向，但 All-to-All 与专家缓存决定 decode 延迟。服务时往往对热专家做复制或预取，这与训练的纯 EP 布局可以不同。

V3 的无辅助损失均衡：路由得分加专家偏置 \(b_i\)，\(b_i\) 根据近期负载升降，不进入对 \(W_r\) 的交叉熵梯度。机制上仍是负反馈，只是反馈走控制器而不是走 \(\partial\mathcal{L}_{\mathrm{aux}}\)。若部署时丢掉 \(b_i\)，负载会偏回训练末期的瞬时状态，可能过载。激活参数量才是和稠密模型比推理成本的尺子。671B 总参数描述的是容量和存储，不是每 token 的 GEMM 量。对照 Mixtral 时应比「激活 B 数」和「\(k\)、是否共享」，而不是只比专家个数。

边界 ​

DeepSeek MoE 依赖大规模 EP 与仔细的通信设计，小集群上复制不了 V3 的训练设定。把 \(N\) 降到 8 再自称 DeepSeekMoE 没有意义——细粒度被拿掉之后，只剩一个带共享专家的 Mixtral 变体。MLA 与 MoE 正交：可以只采用其中一项；V2 的质量来自两者叠加，写消融时要分开。

细粒度加高 \(k\) 使内核更碎，naive 实现会通信墙。没有融合的 grouped GEMM 和合理的 token 重排，理论 FLOPs 优势兑现不成墙钟。Qwen2-MoE 在更少专家上可能更好部署；Mixtral 在单机推理上仍更省事。DeepSeek MoE 的边界是：你愿意为组合数和总容量付系统复杂度。

文献应引用官方技术报告（2024 的 V2、2024–2025 的 V3），不要编造 arXiv 编号或把社区博客里的层数表当成论文定理。专家数以报告当时的配置为准，后续开源权重若有改动，以模型卡为准。

第一层 FFN 保持稠密、其余层 MoE，是 V2 写明的细节：底层更靠近嵌入，公共变换更重，稀疏收益更小。复现时若把第零层也改成 160 专家，早期表示会抖，需要单独验证。设备限制路由意味着「全局 top-\(k\)」并不总成立——得分第二的专家若在非法设备上，会被丢掉，换成本设备上稍差一点的专家。这是质量换通信的明确交易，评测路由准确率时要用实际被选中的集合，而不是未加设备约束的理想 top-\(k\)。V3 的偏置均衡与 V2 的 aux loss 不能同时当默认；混用会双倍惩罚热专家。开源推理框架若只实现了 Mixtral 式 8 专家，要把 DeepSeek 的共享支路、细粒度宽度和 EP 组补齐，否则测到的延迟和论文不可比。不要把 MLA 的 KV 压缩算进 MoE 的激活参数里。那是注意力侧的缓存体积，和 FFN 专家是否稀疏无关。对比推理成本时，应分列：激活 FFN 参数、注意力 FLOPs、KV 字节。DeepSeek MoE 能成立，靠的是算法与并行绑在一起；只抄专家数、不抄通信约束，很难在同样规模上训稳。

小结 ​

  • DeepSeek MoE = 细粒度路由专家 + 共享专家 + 较高的 \(k\)，使每个 token 走更多小专家。
  • V2 示例为 2 共享 + 160 路由、激活 6 个路由专家；V3 放大到 256 路由量级、激活约 37B / 总参 671B。
  • 设备限制路由约束 All-to-All 范围；V3 可用无辅助损失的偏置做负载均衡。
  • 对照 Mixtral 的对称 8 专家 top-2，以及 Qwen2-MoE 的共享专家路线。
  • 推理比的是激活量，不是总参数；系统复杂度是这套方法的主要边界。
  • 出处：DeepSeek-V2、DeepSeek-V3 技术报告，2024–2025；Lepikhin GShard 2020、Fedus Switch 2021、Mixtral 与 Qwen2-MoE 作对照。
