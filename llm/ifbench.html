大模型 · 2026-09-03

IFEval / IFBench ​

可验证约束把指令遵循收成程序谓词；一旦模型把那二十五个检查函数背熟，同一套谓词上的高分就不再说明遇到新约束仍会服从。需要一张约束类型被留出的卷子。

—— Zhou et al., IFEval；Pyatkin 等 IFBench 将新约束当作分布外服从测试

IFEval 的贡献是把「听不听指令」从有用性、文风和知识里拆出来：字数、段落、关键词、格式、语言、标点，凡能写成确定性检查函数的，就按通过/失败计分。Zhou 等人的协议——prompt-level 全约束满足、instruction-level 原子平均——已经成为回归门禁。问题随之而来：约束库存是公开的、有限的，强化学习若直接拿 verifier 当奖励，模型会过拟合那一张函数表。IFBench 要测的是对新约束类型的服从是否还在：检查器族与 IFEval 刻意错开，难度与组合方式也更接近「没背过的格式要求」。本篇把二者当成同一条尺子的校准端与留出端，而不是两套互不相干的排行榜。

问题 ​

助手失败里有一类极具体：内容对，格式错。用户要三段、禁某个词、输出 JSON，模型漏一条。主观偏好评测会原谅它，下游解析器不会。IFEval 证明这件事可以自动考。可一旦它成为公开门禁，训练就会看见同一批谓词：长度上下限怎么凑、标题 markdown 怎么写、禁用词怎么用同形字绕过。分数涨，可能是学会了服从，也可能是学会了这二十五个函数。

指令遵循的泛化问题与 MMLU 污染 同类，但更窄：泄漏的不是题面，是约束生成器。留出新的原子约束、新的组合模板、新的表层实现（例如另一种列表语法、另一种计数单位），才能区分「服从通道」和「背检查器」。IFBench 的存在理由就是这张留出卷，而不是把 IFEval 再出一遍更长的题。

可验证通过仍可能无用，留出失败则说明服从没泛化 ​

IFEval 高、IFBench 低：模型会做见过的格式体操，遇到新谓词就当建议。两张都高：更像真有一层「读取约束并监控输出表面」的能力。两张都低：服从通道本身弱，先别讨论泛化。只报 IFEval，会把过拟合写成对齐成功。只报 IFBench、不报 IFEval，则无法与已有文献对表——校准端仍然需要。

把 IFEval 的 verifier 直接当 RL 奖励时，应预先把 IFBench 锁进评测、不进奖励。否则留出集很快也会被「间接」优化，只是梯度来自相近约束。

方法 ​

IFEval 的实例是自然语言指令加若干原子约束 \(C_i\)。对输出 \(o\)：

\[\mathrm{PromptAcc}=\frac{1}{N}\sum_i\mathbf{1}\bigl[\forall c\in C_i:c(o)\bigr],\quad \mathrm{InstAcc}=\frac{\sum_{i,c}\mathbf{1}[c(o)]}{\sum_i|C_i|}. \]

复现必须调用官方检查器：词的定义、换行、代码块内是否计数，都是标准的一部分。约束族要分列，见 IFEval。

IFBench 沿用「谓词打分」骨架，替换约束库存与抽样：新的原子类型（IFEval 未覆盖的格式、条件更绕的计数、更易与助手默认文风冲突的禁令），以及更狠的组合。读分时同样应给 prompt-level 与 instruction-level，并按是否与 IFEval 约束族重叠切片。重叠切片用于校准（两套检查器是否同方向）；非重叠切片才是泛化命题。

解码协议两边必须一致：温度、max_new_tokens、系统提示、是否 约束解码。JSON mode 会把某一族变成语法保证，应分列「纯采样 / 带文法」两表，且 IFBench 里文法覆盖不到的软约束（语气词、段落修辞）仍归模型。

多轮修订是另一轴，不要混进单轮分 ​

用户说「再短一点、但保留第二条禁词」，是指令遵循的时间维：要在已生成内容上打补丁，而不是从空缓冲满足静态谓词。IFEval 主协议是单轮。IFBench 一类后续集若含多轮，必须单独成表——单轮高、多轮低，说明模型会「一次写对格式」，不会「按反馈改格式」。把多轮平均进单轮，会让失败不可归因。

机制 ​

可验证服从要求生成过程里有一个对表面形式的监控：段数、禁用词、括号是否闭合。这可以是隐式状态，也可以是把约束复述进思维。IFEval 的原子大多局部、可在短答案上满足；对齐若奖励「详尽」，会与长度上限系统性打架，长度族先掉。IFBench 的新约束若故意与默认助手文风冲突（更怪的格式、更窄的字符集），掉分反映的是默认策略与约束的 KL 距离，不只是「没看见指令」。

过拟合检查器的机制很具体：重复空行凑段、用 unicode 同形字绕过英文禁用词、把 JSON 包在符合「必须出现」的套话里。校准端 verifier 越固定，这些策略越稳。留出端若换了计数单位或换了「何谓一段」的定义，作弊策略会失效——这正是留出的诊断价值。反之，若留出谓词实现得与 IFEval 过于同构（只是换了关键词表），过拟合仍会转移。

必须出现易、禁止与计数难，在留出集上仍然成立 ​

关键词插入是服从；禁止是与语言模型先验作对；计数是对已写 token 的离散状态。IFBench 若在禁止与计数上掉得比「必须包含」更多，与 IFEval 的机制叙事一致，说明不是题出歪了。若反过来只有新「必须包含」在掉，更像是模型没把新词读进约束列表——提示解析问题，不是监控问题。分族报告才能读这一层。

中文产品不能只跑英文 IFEval / IFBench。字、词、标点、公文标题的谓词都要重写。英文高分不签发中文格式服从。

边界与工程取舍 ​

两套都不覆盖模糊风格（「幽默一点」）、冲突指令的优先级、工具是否调对、内容是否属实。高分无用、低分但内容极好，产品取舍仍要 Arena 或人工。可验证层适合 CI 与 RL 的可重复奖励，不适合当唯一质量分数。

检查器实现即标准。私自「收紧」或「放宽」谓词之后，与论文数字对比没有意义。IFBench 作为留出集，更要防训练泄漏：一旦检查器进入公开强化学习配方，它就变成新的 IFEval，需要再留出第三张卷。动态轮换的逻辑见 动态基准。

与文法解码的边界：能被 schema 保证的，应从「模型服从」里划走，算系统能力。剩余软约束才是这两张表要盯的对象。混报会让开 JSON mode 的栈看起来「指令遵循强很多」。

prompt-level 比 instruction-level 更接近用户：漏一条就算失败。刷榜只报后者，会掩盖「经常漏一条」的模型。两套基准都应把两个数字写全。

小结 ​

  • IFEval 用固定可验证谓词测表面约束服从；IFBench 用留出约束类型测这种服从有没有过拟合检查器。
  • 应同时报 prompt-level 与 instruction-level，并按约束族、按是否与 IFEval 重叠切片。
  • 用 IFEval 做 RL 奖励时，必须把 IFBench 隔离在评测侧。
  • 系统提示、截断、约束解码与中文谓词都会改分，须写入协议。
  • 可验证高分不保证有用或属实；多轮修订应分表。
  • 出处：Zhou et al., Instruction-Following Evaluation for Large Language Models；Pyatkin et al., IFBench / 可验证指令遵循的留出评测。
