NVSHMEM / NVLS ​

NVSHMEM 让 CUDA 核内发出单边 put/get，把通信从 CPU 启动的集合调用收进 GPU 上的 PGAS；NVLS 则让 NVLink 域里的归约走交换机上的组播内存，而不是每张卡各拷一份再加。

—— NVIDIA NVSHMEM 文档：面向 GPU 集群的 OpenSHMEM；NCCL 用户指南：NVLink SHARP（NVLS）在 Hopper 及以后、第三代 NVSwitch 上卸载 All-Reduce 等集合

多 GPU 上的张量要会合时，常见路径是：kernel 结束 → CPU 调 NCCL → 再启下一个 kernel。强缩放时，问题规模不变、卡数增加，同步与启动占的比例按 Amdahl 上涨。NVSHMEM 把 OpenSHMEM 的分区全局地址空间做到 NVIDIA GPU 上：对称地分配设备内存，允许在 CUDA 核、CUDA stream 或 CPU 上对远端 GPU 做单边通信，从而写出「边算边传」的长寿命 kernel。NVLS（NVLink SHARP）是另一条硬件路径：在支持的 NVSwitch 上，用 CUDA 组播与交换机内归约，让 ncclAllReduce 一类操作少搬重复字节。二者经常一起出现在 Hopper / Blackwell 超节点的调优指南里，但合同不同：一个是编程模型，一个是 NCCL 传输与交换机卸载。本篇分开写清。柜内链路背景见 NVLink；交换机内归约的 Rubin 代叙事见 SHARP。

问题 ​

NCCL 的主机发起集合对数据并行梯度很合适：一步一同步，语义简单。张量并行、专家并行、以及 decode 逐步的小消息 All-Reduce，启动延迟和 CPU 介入会变成墙。GPU 有足够的并行度去掩盖 HBM 延迟，却掩盖不了「等 CPU 再 launch」的气泡。NVSHMEM 要回答：能否在核内对对称堆做 put / get / quiet，让 warp 在等数据时切去算别的，而不把控制交还主机。文档把收益明确写在强缩放：CPU–GPU 同步所占分数随卡数变大时，核内通信才值得付 API 复杂度。

NVLS 要回答的是另一问：即便集合仍由 NCCL 发起，NVLink 域内的 All-Reduce 是否必须在 GPU 上把每张卡的向量都读一遍再写一遍。Hopper 起的数据中心 GPU 与第三代 NVSwitch（NVLink4）提供 NVLink SHARP：组播地址让一次访问落到多张卡，交换机参与归约。NCCL 环境变量 NCCL_NVLS_ENABLE 默认 2：能开则开，多 rank 共用一张 GPU 时则静默关掉。用户往往感觉「NCCL 自己变快了」，实际是传输层换了 NVLS，而不是模型代码改了算法。

单边 PGAS 与集合卸载不是同一 API ​

NVSHMEM 的编程对象是 PE（processing element）与对称堆：每个 PE 上同一偏移的指针指向「对应」的远端缓冲，nvshmem_float_put 把本地数据写到指定 PE。扩展 API 提供 _warp / _block 集体参与的 put/get，以及 stream 上的 CPU 发起但 GPU 上执行的通信。NVLS 的编程对象仍是 ncclAllReduce：用户不写组播指针，NCCL 在支持的硬件上选 NVLS 算法，并可对用户缓冲做 ncclCommRegister。把 NVSHMEM 的核内 put 写成「就是 NVLS」，排障会找错开关。

NCCL 文档：NVLS 需要 NVLink4 交换机与 Hopper 及更新架构；与「多 rank 共用一 GPU」不兼容，强制 NCCL_NVLS_ENABLE=1 时初始化失败，默认 2 则禁用 NVLS。调优指南允许为省显存或简化故障面而关掉 NVLS。

方法 ​

NVSHMEM：每个进程绑一张 GPU，初始化时库记住这张卡；nvshmem_malloc 返回的是该卡上的对称设备内存。核内通信必须从这张卡上的 kernel 发出。可与 MPI 共存：MPI 负责世界、NVSHMEM 负责 GPU 对称堆，文档给出典型初始化片段。传输可走 NVLink、GPUDirect RDMA 的网卡，以及文档中的 GPUDirect Async Kernel-Initiated（GDAKI）一类路径，使 InfiniBand 的控制面也尽量留在 GPU 上。正确性依赖 GPU 内存模型：区分 synchronizing 与 non-synchronizing 操作，quiet / fence 在 CPU 与 GPU 上只排序各自发出的通信；要从主机看见核内 put 完成，需要核内 quiet 再同步 kernel，或使用 stream 上的 quiet。

NVLS：保证运行在支持的 NVSwitch 域内，P2P 与 CUDA 组播可用，NCCL 版本足够新（用户缓冲注册自 2.19 一类版本起支持 NVLS）。集合仍按原 API 调用。要零拷贝走用户缓冲，按文档用 ncclMemAlloc 或合格分配器，并 ncclCommRegister，且各 rank 相对缓冲头的偏移一致。CUDA Graph 捕获时要用文档写明的 graph 注册路径，否则组播映射进不了图。Device API 进一步暴露 multimem：在核内用 ncclGetLsaMultimemDevicePointer 拿到组播指针，再用 PTX 如 multimem.ld_reduce 做硬件归约——这是给写自定义通信核的人，不是给只调 NCCL 的框架用户。

LLM 框架里，Megatron 类张量并行的层间 All-Reduce 默认仍是 NCCL；在 Hopper HGX 与 NVL72 上应确认日志选中了 NVLS，而不是默默走环。专家并行的 All-to-All 是置换，NVLS 帮不上忙，那要 NVLink 带宽与 NVSHMEM 或 NCCL send/recv。自定义融合核若把通信藏进 GEMM 尾部，才值得上 NVSHMEM，并接受对称堆与 PE 映射的约束。

显存、通道与多节点 ​

NVLS 要为组播区域留设备内存与交换机资源；NCCL 调优指南写明：关掉 NVLS 可能降低内存占用、减少故障点。SM90 与 SM100 上 NCCL 内部 NVLS 通道数不同（实现细节随版本），用户应靠 NCCL_DEBUG=INFO 看算法名，而不是硬编码通道数。多节点 NVLink（MNNVL）上，NCCL 会探测域：域内可 NVLS，域间仍走网卡。NVSHMEM 的对称堆跨节点时走 RDMA 传输，延迟从 NVLink 档掉到网卡档，强缩放收益要重新量。不要把单机 8 卡上的核内 put 延迟抄到跨柜。

机制 ​

PGAS 的对称性让编译器和程序员用「远端 PE 的同一偏移」思考，避免每次集合都做握手。GPU 发起把 doorbell 与数据路径放到 SM 能碰的地址，warp 调度掩盖延迟。这与 CPU 上的 OpenSHMEM 同构，但内存必须是 NVSHMEM 分配的设备页。GDAKI 再把网卡门铃也放到 GPU，避免核内通信还要 CPU 代理。

NVLS 的机制是组播虚拟地址 + 交换机归约：一次 ld_reduce 语义上对多张卡的对应行做加，结果可写回组播区域。流量从「每边两份完整向量」向「少一份重复搬运」靠，产品表述常见最多约一半的 All-Reduce 流量下降——与 SHARP 专文 同一类上界语言，依赖参与者、消息大小和是否真的走了 NVLS 算法。精度与数据类型必须是交换机支持的格式；假设 BF16 训练一定在 Switch 里用 BF16 加，可能与当代实现不符。

NVSHMEM 文档把对称堆钉成 pinned GPU 设备内存，并强调 PE 与 GPU 的绑定限制。多进程共用一 GPU 的模型与 NVLS 一样别扭。初始化之后换 cudaSetDevice 而不重新理解 PE，属于未定义用法。

和 InfiniBand SHARP 分层 ​

InfiniBand 交换机上的 SHARP 吃跨节点梯度；NVLS 吃 NVLink 域。层次化集体通信仍然对：域内 NVLS，域间 IB SHARP 或普通 RDMA。数字不可加总成「系统有多少 TFLOPS 的网内计算」。NVSHMEM 可以在两层之上提供统一的 put/get，但底层延迟仍是分层的。GPUDirect 保证网卡直达 HBM，见 InfiniBand 与 GPUDirect，与 NVLS 正交：一个去弹跳，一个去重复归约。

边界与工程取舍 ​

不要在 Ampere 八卡 PCIe 机器上指望 NVLS。不要为了 NVSHMEM 重写整个训练框架而不先量 NCCL+NVLS 是否已经够。不要在 CUDA Graph 里混用未注册的用户缓冲还抱怨 NVLS 没生效。不要把 Device API 的 PTX 示例复制进生产核而不处理 multimem 的对齐与 fence。MIG 与「一卡多 rank」会禁用 NVLS。消息极小时，卸载与组播的建立成本可能高于环；应用仍应让 NCCL 调优器选择，而不是全程强制 NCCL_NVLS_ENABLE=1。

NVSHMEM 的调试面更宽：死锁常来自 quiet 漏配、CPU/GPU 排序误解、或与 MPI 进度混用。生产服务（推理 decode）更常见的是 NCCL 逐步 All-Reduce；核内 PGAS 更常见于 HPC 与高度融合的研究核。选错模型，复杂度付给错误的瓶颈。

小结 ​

  • NVSHMEM 提供 GPU 上的 OpenSHMEM PGAS，核内单边通信服务强缩放与计算通信重叠。
  • NVLS 是 NCCL 在 NVSwitch 上的 SHARP 传输，卸载域内 All-Reduce 一类集合，对 All-to-All 无相同含义。
  • 默认让 NCCL 探测 NVLS；一卡多 rank 会关掉它。用户缓冲要按文档注册。
  • 域内 NVLS、域间 IB，与 GPUDirect 分层叠加，数字不可混加。
  • 融合核再考虑 NVSHMEM；多数 LLM 框架先确认 NCCL 算法名。
  • 出处：NVIDIA NVSHMEM 与 NCCL 公开文档。
