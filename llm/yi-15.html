Yi-1.5 ​

在 Yi 基座上再继续预训练 5000 亿高质量 token，并用 300 万条多样本做指令微调：代码、数学、推理和遵从变强，通识阅读不主动丢掉。

—— 01.AI，Yi-1.5 开源说明（GitHub / 模型卡，2024-05）；架构前史见 *Yi: Open Foundation Models by 01.AI*，arXiv:2403.04652

Yi-1.5 是零一万物在 2024 年 5 月 13 日开源的 Yi 升级版，稠密解码器 6B / 9B / 34B，Base 与 Chat，Apache 2.0。官方没有为 1.5 单独挂一篇与 2403.04652 同规格的长技术报告；原文贡献以仓库与模型卡为准：在 Yi 上 continue pretrain 500B 高质量语料，再 SFT 约 3M 多样样本。模型卡补充：系列预训练 token 累计约 3.6T（含 Yi 原 3T 量级再加继续训）。上下文提供 4K / 16K / 32K 等变体，部分卡标注更长窗口，以具体权重的 max_position_embeddings 为准。本篇写这一次数据加厚，不把 Yi 论文里的词表、GQA 与训练稳定性整章复制过来；那些属于 2024 年 3 月的基座报告。

问题 ​

Yi-6B/34B（2023 年 11 月开源）在中英通识与阅读上已经能打，但代码、数学、硬指令遵循相对同代专线与更大稠密模型仍弱。从零再训 34B 太贵；完全换架构会打断 Llama 生态的推理栈。可做的是：不改解码器骨架，改继续预训练的数据密度，再用大规模多样 SFT 把「会续写」变成「会按指令解题」。

风险是灾难性遗忘：500B 若过度倾斜代码与题库，MMLU、常识与长阅读会掉，Yi 原先的中英优势会先没。3M 条 SFT 若来源单一（只有某种进化指令），Chat 会变成基准刷子，真实对话变差。9B 这一档是 1.5 相对 Yi 原系列多出来的产品尺寸，用来填 6B 与 34B 之间的部署空档，而不是新的结构定理。

继续预训练不是新模型名营销 ​

「Yi-1.5」在官方句式里是 upgraded version of Yi，初始化来自 Yi 检查点，而不是随机初始化的第三套权重。评测若拿 Yi-34B-Chat 与 Yi-1.5-6B-Chat 比，比的是尺寸不是代际。应对齐同年同尺寸：6B 对 6B、34B 对 34B；9B 只能与其他实验室的 ~8–10B 比。

Yi 技术报告（2403.04652）描述的是第一代开源基座：解码器 Transformer、双语数据、较长上下文尝试等。1.5 的公开材料没有宣布换注意力、换 MoE 或换词表。实现上按 Yi 同系权重加载；若某第三方量化卡改了词表，那不是官方 1.5。

方法 ​

继续预训练：500B 高质量语料——官方未在 1.5 页面公开过滤规则与配比表，不能把 Yi 论文的网页清洗步骤直接写成 1.5 的新贡献，只能写「在 Yi 已有清洗管线经验上再灌 500B」。目标仍是因果语言建模。累计 3.6T 表示 1.5 基座见过的总 token 多于第一代发布时的 3T 叙事，多出来的主要是这 500B 与可能的补量，而不是另一次从零 3.6T。

3M SFT 的约束是「不要忘了阅读」 ​

指令微调：3M 多样本，覆盖代码、数学、推理、通用遵从。官方强调相对 Yi 更强的四项，同时 维持 语言理解、常识、阅读。这是明确的多任务约束：SFT 不能把阅读理解样本挤出配比。Chat 与 Base 成对发布，微调框架兼容 LLaMA-Factory、Swift、XTuner、Firefly 等——说明权重仍落在主流 Llama 形工具链里。3M 这个量级已经超过许多实验室公开的人标指令集，因此其中必有合成或爬取；官方未给比例，写 1.5 只能把它当成「大规模指令混合」而不是「三百万条专家手写」。

窗口变体是检查点，不是新位置公式 ​

上下文：同一参数量提供短窗与长窗检查点（4K / 16K / 32K）。长窗权重通常是基座或 Chat 再做长度扩展，而不是 3M SFT 里天然出现 32K 对话。缺 1.5 专文时，不要把 Yi 报告里的位置方案细节安到某一个 32K 文件名上；以该文件的配置与 01.AI 说明为准。用户下载时必须认准文件名里的 16K / 32K，把 4K Chat 的 max_position_embeddings 改成 32768 不会自动获得 32K 权重见过的相位。

Apache 2.0 使二次开发的合规成本低于早期部分 Yi 权重：衍生模型须保留官方要求的归因句，但可以商用。这解释了为何 1.5 在中文开源生态里被大量继续微调，而 Lightning 只能走 API。9B 填补了「6B 不够聪明、34B 单卡吃力」的部署空档；它需要独立的宽度与层数配置，不能当成 6B 加层。发布时官方称 9B-Chat 在同尺寸开源里靠前，随后 Qwen2.5-7B 等改变了这一对照，引用须钉 2024 年 5 月。

机制 ​

继续预训练把参数从「通识先验」往「代码符号与解题模板」挪，500B 的量级足以改变 6B/9B 的表层分布，对 34B 则是在已有能力上加密度。SFT 3M 把同一先验接到指令条件：\(p(y\mid x_{\text{inst}})\) 而不是网页续写。官方把「维持阅读与常识」写进发布说明，等于承认继续训与 SFT 都可能伤这些轴，需要用数据配比顶住——但他们没有公开遗忘曲线，机制上只能理解为多目标混合成功（以他们公布的对照表为准），而不是证明 500B 一定无遗忘。

9B 需要独立一组宽度与层数，不是 6B 加层那么简单；具体超参见配置文件。Apache 2.0 使 1.5 比早期 Yi 部分权重的许可证更适合二次开发——这是产品与法律层贡献，不是精度层。

Chatbot Arena 与静态榜可能分叉：1.5 的发布叙事偏静态基准（代码、数学、指令），与后来 Yi-Lightning 明确优化 Arena 不同。用 1.5 的 HumanEval 去外推 Arena Elo 没有根据。

3M SFT 的「多样」是官方形容词。没有数据卡就不能断言含多少合成、多少人标、是否含偏好对。写 1.5 不要编 RLHF 配方；那是 Lightning 报告才展开的后训练。

边界与工程取舍 ​

缺少 1.5 专有 arXiv 意味着层数、头数、RoPE 基数、是否 GQA，应以 Hugging Face config.json 与 Yi 基座报告对照，禁止为 1.5 伪造论文号或伪造一张「官方超参表」。长上下文变体的针测以模型卡为准，未写 1M。视觉、MoE、推理专线不属于 1.5。

6B 可在单消费卡量化部署，34B 需要更高显存；「9B 同尺寸开源最强」是发布时口径，随后 Qwen2.5-7B 等会改写排行。衍生工作须按 Apache 2.0 保留归因句。01.AI 后来把旗舰转到 API 的 Lightning，开源 1.5 停在这一代稠密线上。

Yi-Coder 等后续专线是另一仓库。不要把 52 语代码助手写进 1.5 通用模型。

小结 ​

  • Yi-1.5 是 Yi 的继续预训练（+500B）加 3M SFT，开源 6B/9B/34B，Apache 2.0。
  • 官方主张代码、数学、推理、遵从提升，并维持通识阅读；无单独长文展开过滤与 RL。
  • 架构以前史报告 2403.04652 与各权重 config 为准，不为 1.5 伪造 arXiv。
  • 上下文按变体区分 4K/16K/32K，与后来 Lightning 的 64K MoE 不是同一产品。
  • 出处：01.AI，Yi-1.5 GitHub 与 Hugging Face 模型卡（2024-05）；Yi: Open Foundation Models by 01.AI，arXiv:2403.04652，2024。
