切片化：每核本地 HBM 视图 + 集合网络 ​

把每个计算切片配上一块 HBM 切片，给出快速的本地视图；常见的跨核模式走专用集合网络，其余流量才走通用片上网络。

—— OpenAI，Hot Chips 2026 对 Jalapeño 空间架构的公开说明

Jalapeño 把推理加速器做成空间架构：物理核是可编程的线程块，张量、SIMD 与标量引擎围着一块本地内存视图转，而不是围着一块所有核争用的统一 HBM 转。Hot Chips 2026 上，Richard Ho、Ravi Narayanaswami 与 Chris Leary 把这一选择写成对带宽墙的直接回应——长延迟路径、争用的统一存储子系统、昂贵的全局内存栅栏，都会让计算单元空等在途数据。切片化要解决的，不是「再加几 TB/s 的标称带宽」，而是让常用操作数住在核旁边，并把 All-Reduce、All-to-All 一类固定图案从通用 NoC 里拆出去。本篇只写这一内存与片上互连形态，封装世代见 HBM4 与 2.5D，机柜以太见 Tomahawk。

问题 ​

自回归 decode 每步都要扫权重与 KV，算术强度低，屋顶线落在带宽上，见 decode 显存墙。若整颗芯片共享一份扁平 HBM 地址空间，核数一多，控制器、交叉开关和一致性协议都会变成串行点：同一拍里许多核对同一通道排队，有效带宽远低于封装上印的 15.4 TB/s。OpenAI 在同一场报告里算过：128 芯片聚合超过 1 PB/s 的 HBM 带宽，只按带宽天花板能推出每用户每秒上千 token 的量级，真实系统远低于此——说明瓶颈已经从「堆带宽」换成「数据到不了核」。

通用 GPU 用大容量共享缓存、TMA、warp 调度去掩盖延迟。Jalapeño 是推理专用空白设计，见 inference-only：它不需要为图形、通用 CUDA 内核保留同一套统一内存语义。代价是编程模型必须显式：张量布局要带物理放置，通信要说清楚走哪条网。切片化正是把这一约束写进硬件。

统一 HBM 视图把延迟藏进争用 ​

统一视图的好处是编译器简单：任意核对任意地址 load。坏处是每次跨切片访问都可能穿过片上互连、经过另一组控制器。LLM 里权重驻留、KV 按序列追加、激活在层间流转，访问图案高度结构化，并不需要任意核任意地址。把结构化流量硬塞进通用交叉开关，等于用最贵的互连去做最可预测的搬运。

切片不是把 216 GiB 拆成互不往来的孤岛。本地视图保证常见操作数近端；跨切片的规约、广播、专家分发走集合网络。没有后者，切片化只是把统一争用换成程序员手写 DMA。

方法 ​

公开架构把芯片切成若干核切片，每个切片配一块 HBM 切片，形成快速本地视图。核组内的张量引擎、SIMD 与标量引擎只把这一本地窗口当成一等存储：权重块、当前层激活、本切片负责的 KV 段优先落在这里。跨核的常见图案——张量并行的规约、MoE 的分发与合并——走专用、低延迟的集合网络，而不是与零散控制消息抢同一张通用 NoC。通用 NoC 仍在，负责不适合快路径的流量：不规则索引、调试、主机侧搬运、偶发的远程读。

编程上，Hot Chips 把 Jalapeño 写成空间架构：Gluon 框架把每个物理核当成一个线程块来编。张量布局显式记录物理放置，搜索器（人或 自家模型）做映射、放置、调度与流水。对软件，这意味着「这块权重住在核 7 的本地 HBM」是一等事实，而不是运行时才发现的 cache miss。

本地视图与集合网络的分工 ​

本地视图服务的是带宽：decode 扫本切片权重、追加本切片 KV，尽量不离开近端通道。集合网络服务的是延迟与同步：TP 的 All-Reduce 体积跟激活走，图案固定，值得一条专用快路径；EP 的 All-to-All 在细粒度专家下更碎，但图案仍是集合通信而不是随机 load。通用 NoC 故意不承诺与集合网同一延迟——它的价值是覆盖长尾，避免为每一种稀有流量再做一条专用网。

机柜外，本地域 128 颗 ASIC、全局域 2048 颗，是同一哲学的放大：先保证核旁内存，再保证核间集合，最后才是跨柜以太。片上切片与柜级域不要混成一个「大共享内存」故事。

机制 ​

切片化降低平均访存延迟的机制很具体。操作数已经按核切开，命中本地 HBM 时不经过跨切片交叉开关，也不需要全局栅栏把所有核对齐到同一次 fence。计算单元因此更少空等。脉动或权重驻留的矩阵核，见 systolic，进一步假定权重在本地窗口里停留多拍；若每次都从远端 HBM 拉，驻留没有意义。

集合网络把「谁和谁说话」从路由表里拿出来，做成硬件友好的几种原语。固定图案可以预留虚通道、避免与稀疏流量头阻塞。这与数据中心里把集合通信从尽全力以太网里拆到专用互连是同一类决定，只是发生在芯片内部。OpenAI 强调减少数据搬运、让实现利用率贴近峰值，见 data-movement；切片化是那句话在存储层次上的落点。

公开规格给出整封装 15.4 TB/s HBM4 与 216 GiB 容量、700 W 封装功耗。那是封装屋顶线，不是「每个核都能以该速率扫全部 216 GiB」。切片化的目的，正是让核看见的是自己那一份，而不是假装共享屋顶线可线性叠加。

与 GPU 统一内存的对比 ​

GPU 可以靠大量线程与缓存层次把统一地址空间用满。Jalapeño 的核是空间上铺开的，线程级延迟隐藏不是一等武器。它把放置问题交给编译与搜索：布局对了，本地视图就够快；布局错了，通用 NoC 会诚实地变慢，而不会用缓存碰巧救回来。这使性能更可预测，也使错误放置更致命——没有大 L2 当安全网。

边界与工程取舍 ​

切片化假设工作集可切。无法对齐到切片边界的权重、需要全芯片广播的词表投影、以及跨切片随机访问的稀疏核，都会把流量打回通用 NoC。此时不要指望「HBM4 很快」自动补偿。KV 若按错误的轴切——例如按 batch 切而 decode 实际按头或按序列分片——本地视图会变成远程视图。放置是模型并行与内核的契约，不是硬件的默契。

不要把切片化写成「片上 NVLink」。集合网络的拓扑、链路速率、是否支持任意核到任意核，Hot Chips 只给出职责划分，没有把未公开的片上 hop 延迟表印成产品手册。规划时用「本地命中 vs 集合 vs 通用 NoC」三档，而不是发明第四档一致性协议。跨芯片的 128 / 2048 域是以太与背板的事，不能从片上切片直接外推带宽数字。

出处：OpenAI 与 Broadcom 对 Jalapeño 的公开介绍，以及 Hot Chips 2026 关于每核 HBM 切片、集合网络与通用 NoC 的架构说明。不编造未公布的切片数、单切片容量或片上链路 Gb/s。

小结 ​

  • 切片化给每个核切片一块本地 HBM 视图，让常用操作数近端驻留，避免统一 HBM 交叉开关成为串行点。
  • 固定跨核图案走专用集合网络；长尾与控制走通用 NoC。两者职责不同，延迟承诺不同。
  • 空间编程把张量的物理放置写成一等布局，映射失败不会被大缓存悄悄掩盖。
  • 封装级 15.4 TB/s 是屋顶线；核看见的是本地切片，不是整颗芯片的共享带宽。
  • 切分轴必须与 TP / EP / KV 布局一致，否则本地视图名存实亡。
  • 出处：Hot Chips 2026 Jalapeño 演讲；OpenAI / Broadcom 公开平台说明。
