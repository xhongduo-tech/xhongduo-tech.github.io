REST 检索投机 ​

不必再训一个草稿模型：用当前后缀去语料库做精确匹配，把检索到的续写收成 Trie，一次树注意力交给目标模型验证。

—— He, Zhong, Cai, Lee, He，REST: Retrieval-Based Speculative Decoding，NAACL 2024

投机要快，通常先养一个与目标同词表的小模型。草稿选择 本身就是一套运维。Zhenyu He、Zexuan Zhong、Tianle Cai、Jason D. Lee 与 Di He 的 REST（Retrieval-Based Speculative Decoding）把 \(q\) 换成非参数检索：预构建 datastore，推理时用已生成后缀做精确匹配，命中片段的后续 token 当作草稿。验证仍走目标模型一次前向，树注意力与 SpecInfer 同族。本篇写后缀数组、Trie 剪枝与适用域，不把 RAG 的语义检索说成 REST。

问题 ​

参数化草稿有三笔账。训练要对齐目标分布；部署要占显存与调度槽；目标一升级，草稿往往要重蒸。很多生成轨迹其实高度重复：API 样板、Markdown 列表、单元测试骨架、客服话术。这些 n-gram 已经写在预训练或指令数据里，小模型只是在用参数记忆同一件事。REST 的问题是：若草稿的信息主要来自「语料里见过的续写」，能否跳过参数，直接查表？

查表必须极便宜。若每步做一次向量检索，延迟可能高过小 Transformer 的一步 decode，投机就亏了。因此 REST 不用语义近邻，而用当前上下文的最长后缀在 datastore 里的精确出现。匹配是字符串级的，实现可以是后缀数组或等价索引，开销相对一次 LLM 前向可忽略。换来的限制也很硬：没在库里出现过的新颖续写，检索给不出好草稿。

精确匹配不是语义检索 ​

「A 函数的文档字符串」与「B 函数的文档字符串」在嵌入空间里可能很近，后缀却对不上。REST 不会把 A 的续写接到 B 上，除非字符级后缀碰巧相同。这避免了把错误 API 名字写进草稿树——那种错误往往在验证的很早位置就被拒，等于白付检索。它也意味着库必须覆盖目标域：用网页对话库去加速 HumanEval，命中率会明显低于用代码库。

REST 的检索发生在 token 序列上，分词器必须与目标模型一致。换词表等于换了一套后缀，旧 datastore 全部失效。这和参数化草稿要对齐词表是同一条约束，只是失败模式从「接受率低」变成「查不到」。

方法 ​

离线：把预训练语料或指令数据（论文里两种都试过）按目标分词器切成 token 序列，建后缀索引。库的粒度是整段文档的 token 流，不是句子嵌入。在线：设当前序列为 \(s=(x_1,\ldots,x_t)\)。从 \(s\) 的末尾取越来越短的后缀，在索引里找精确命中；命中位置的后续若干 token 构成候选续写集合 \(S\)。

从多条续写收到一棵 Trie ​

\(S\) 里常有大量重叠。把它们插入 Trie（前缀树），边上挂 token，节点上累计频次。低频枝剪掉，避免把验证预算浪费在只出现一两次的怪异续写上。然后按频次从根往下选出一组草稿 token，形成一棵待验证的树（或一条高频链）。验证用树注意力：每个候选只看见自己的前缀与已提交上下文，目标模型一次前向给出所有节点的 logits，再按投机规则接受最长合法前缀。

\[\mathrm{query}(s)=\arg\max_{u\ \mathrm{suffix\ of}\ s}\{\lvert u\rvert: u\ \text{在 datastore 中出现}\} \]

最长后缀优先：更长的上下文匹配通常给出更靠谱的续写；匹配不到足够长的后缀时退化为短模板，接受长度变短。

库的选择决定加速比 ​

代码生成用代码语料建库，对话用 ShareGPT 一类指令数据。论文在 7B / 13B、单 batch、A6000 上报告约 1.62–2.36×，代码侧通常高于开放对话——与 Lookahead 挖掘可复用 n-gram 是同一方向，只是 REST 的 n-gram 来自静态库，Lookahead 来自本次 Jacobi 轨迹。库可以按租户分片：内部 API 文档进代码库，不要混进通用网页，以免高频但错误的网页短语污染 Trie。

机制 ​

REST 的 \(q\) 是经验 n-gram 模型：在「看见这段后缀」的条件下，续写的频率估计。它没有深层的长程推理，却在局部句法与惯用搭配上往往足够像 \(p\)。验证保证不像的部分被拒，输出仍来自目标模型。加速来自「许多步的局部续写确实在库里」，而不是来自检索质量评分。

与参数草稿比，REST 的边际成本几乎是 CPU 上的索引查询，不占 GPU 算力，也不和目标抢 KV 带宽。这在 batch=1 的交互场景特别合适。连续批处理变大后，目标一步已经偏算力墙，检索再快也只省掉草稿那一项——而 REST 本来就没有草稿 GPU 时间，收益上限变成「树验证多出来的节点是否仍能被一次稍胖前向消化」。

Trie 上的频次是语料统计，不是目标模型的概率。高频续写在 \(p\) 里也可能是错的（过时 API、错误类型注解）。必须验证。把 REST 理解成「检索到就输出」会破坏无损，也会在评测上显得异常好或异常差。

和 Lookahead、SpecInfer 的分工 ​

三条零或低训练的投机路：SpecInfer 用小模型采样多样性；Lookahead 用目标自己的并行猜测；REST 用静态语料的精确后缀。REST 对「库外」的新颖推理几乎没有帮助，但对样板极强。可以叠：检索树提供浅层高频枝，不够再让小模型补。工程上先单独测 REST，确认域内 n-gram 覆盖足够，再决定要不要养 SSM。

边界与工程取舍 ​

datastore 要占磁盘与内存。代码库可以很小仍有用；开放网页要覆盖有用后缀，体积会涨。索引构建是一次性成本，目标分词器或模板一变必须重建。版权与污染：库若含评测集原文，加速数字会掺进「背到了 HumanEval」。应用侧应用训练允许的数据建库，并按租户隔离。

采样温度升高时，目标更常离开高频 n-gram，REST 的接受长度下降，这与 Lookahead 同类。结构化输出若有 JSON schema，应用约束解码剪枝 Trie，否则大量检索枝会在 schema 上提前非法。不要把 REST 写成 RAG：它不把检索文档拼进提示，只把续写 token 当草稿，提示里的证据仍然要靠调用方提供。

最长后缀匹配在重复标点、空白和「```」一类代码围栏上会过度触发。需要对过短或过泛的后缀设最小长度，否则 Trie 被通用符号撑满，验证节点浪费在无信息枝上。

小结 ​

  • REST 用非参数 datastore 代替草稿模型：当前后缀精确匹配，续写进 Trie，目标模型一次树验证。
  • 索引必须与目标分词器一致；库的域决定加速，代码通常高于开放对话。
  • 论文在 7B/13B 单卡上约 1.62–2.36×；验证保持无损。
  • 检索是字符串级 n-gram，不是语义 RAG；命中物必须再过目标 logits。
  • 库外新颖生成帮助有限；温度升高或评测集泄漏都会扭曲数字。
  • 出处：He et al., REST: Retrieval-Based Speculative Decoding，NAACL 2024；arXiv:2311.08252。
