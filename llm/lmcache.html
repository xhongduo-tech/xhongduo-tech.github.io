LMCache ​

把 KV 从一次请求的临时状态做成可跨引擎、可分层存放的对象；前缀不够用时，再用选择性重算把多段非前缀块融回一条合法的注意力上下文。

—— Yao et al., CacheBlend, EuroSys 2025；Liu et al., CacheGen, SIGCOMM 2024

vLLM 的前缀缓存与 SGLang 的 radix 都假定：可复用的是从序列起点出发的最长前缀，并且默认活在当前引擎的 GPU 池里。RAG 与多文档问答把多段检索块拼进提示，只有第一块是前缀，其余块的 KV 在拼接后位置变了，跨块注意力也还没算。LMCache（LMCache/LMCache）做的是一层 KV 管理：持久化与分层卸载、跨引擎复用，以及 CacheBlend 对非前缀块的融合。压缩与流式加载的前身是 CacheGen。本篇写这层管理，不替代 分页 在一次前向里的块表。

问题 ​

长上下文的 TTFT 由前填主导。同一知识库被许多查询反复带上，按文本重算是在付二次注意力的全价。前缀缓存只能跳过「恰好排在最前面且字节级相同」的那段；RAG 里检索块的顺序随查询变，第二块、第三块明明算过，却因为不是前缀而不能用。Prompt Cache 一类「整段模块直接复用」若只改位置编码、不补跨块注意力，多跳问题的质量会掉——CacheBlend 把这称为 full KV reuse 的缺陷。

另一边是容量。HBM 放不下跨会话、跨实例的知识块。需要 CPU 内存、本地盘、远端存储上的 KV 对象，以及一条在查询到达时把对象拉回 GPU 的路径。对象若以稠密 FP16 张量在网上传，延迟可能高过重算。于是既要决定复用哪些块，也要决定以什么体积移动它们。

前缀复用与块复用不是同一接口 ​

前缀命中：跳过 \(m\) 个 token 的前填，后缀照常算，数值与全量前填一致。非前缀复用：块在预计算时看见的「前文」与当前拼接里的前文不同，直接粘贴会缺跨注意力。LMCache 把前者做成分层前缀/块存储，把后者做成 Blend 引擎：复用预计算 KV，再选一小部分 token 重算以补跨块信息。调用方必须知道自己走的是哪条语义，不能都叫「开了 LMCache」。

块键要包含模型、精度、RoPE 位置约定、层数与适配器。只对文本做哈希，会把 A 模型的 KV 喂给 B。跨引擎复用时这条更严：vLLM 与另一引擎的块布局若不同，对象不能当同一字节用。

方法 ​

官方文档把 LMCache 写成 vendor-neutral 的 KV 层：对接 vLLM 等引擎，把缓存从「进程内临时页」变成可持久、可观测、可变换的对象。分层卸载：GPU → CPU → 本地存储 → 远端 backend，淘汰常用 LRU。跨请求、跨会话、跨引擎实例命中同一键则跳过前填。观测栈用来看命中率与各层延迟，避免只看 GPU 利用率。

CacheBlend（Yao, Li, Liu, Ray, Cheng, Zhang, Du, Lu, Jiang，EuroSys 2025，arXiv:2405.16444，DOI 10.1145/3689031.3696098）针对「输入由多段已缓存文本拼接」：逐层做前填，但每层只更新一小部分 token 的 KV，其余复用预计算值。经验上更新比例低于约 15% 时，质量可与全量前填对齐，依据是注意力矩阵的稀疏——真正需要跨块信息的位置远少于全序列。重算与下一层 KV 从较慢设备取回可以流水线化，因而允许把对象放在盘上而不把 TTFT 加上整段加载。相对全量重算，论文报告 TTFT 降 2.2–3.3 倍、吞吐升 2.8–5 倍；相对只复用前缀，收益来自后几块不必重算；相对 full reuse，QA 的 F1 与摘要的 Rouge-L 更高。实现挂在 vLLM 上，文档用 engine-type blend 或遗留的 LMCACHE_ENABLE_BLENDING。

CacheGen（Liu 等，SIGCOMM 2024，arXiv:2310.07240）解决另一半：KV 在网上的体积。利用层内邻近 token 的 K/V 更相似、浅层对误差更敏感、按层与通道分组比按位置分组更值等分布性质，把张量编成比特流，再按带宽调节压缩档；带宽过低时回退为传文本、让 GPU 重算该块。相对当时的复用系统，报告体积约 3.5–4.3 倍、取回加处理延迟约 3.2–3.7 倍的下降。LMCache 文档把 CacheGen 与 CacheBlend 并列为自己的论文线。

与 Mooncake、引擎内缓存的分工 ​

SGLang 前缀树 索引本进程页；Mooncake Store 是近 GPU 的 RDMA 对象池，论文场景是聊天前缀与 PD 交接。LMCache 强调跨引擎的 KV 层与 RAG 式非前缀融合，并带压缩流式。三者都「用存储换前填」，键空间与一致性模型不同。生产上常见叠法：引擎内 radix/前缀缓存做热路径，LMCache 或 Mooncake 做跨实例与分层；Blend 只开在多块检索拼提示的应用上，不要对纯多轮聊天无故开选择性重算。

vLLM production stack 一类装配把 LMCache 接在多实例 vLLM 前，当作共享 KV 服务。这不改变 V1 的 {request_id: num_tokens} 调度，只改变「本步预算里有多少 token 其实不必算」。

机制 ​

前缀命中的正确性来自因果注意力：前缀 KV 不依赖后缀。Blend 的正确性是近似的：用少数 token 的重算去恢复跨块注意力中能量集中的那些项，其余沿用块内预计算。因此它有质量–延迟曲线，而不是二进制的「命中即精确」。流水线机制把「算 15%」藏进「从 SSD 取下一层」的墙钟里，所以存储层可以更慢，只要带宽与重算能重叠。这与 Mooncake 不等式「加载带宽必须高过重算」互补：Blend 降低的是必须在 GPU 上算的量，CacheGen 降低的是必须在网上走的字节。

CacheGen 的机制是把 KV 当可分级的媒体流。浅层少压、深层多压；带宽掉档时先升压缩再改传文本。回退路径保证 SLO：宁可变质量或局部重算，也不让 TTFT 无限等网。这要求块按 token 段独立可解码，与 Blend 按块融合的切分一致。

15% 不是定理。它是作者在若干模型与 RAG/QA 集上的工作点。注意力更密、块之间强耦合的任务要把重算比例当超参扫，并看 F1/Rouge，而不是只看 TTFT。

跨引擎复用的现实约束 ​

「存一次、vLLM 与另一引擎都能读」需要公共张量布局或转换器。头数、GQA 分组、MLA 压缩、RoPE 基数、量化方案任一不一致，对象只能当缓存未命中。LMCache 的 vendor-neutral 是产品目标，落地仍要按模型卡做兼容矩阵。观测上应分开报「键命中但布局放弃」与「键未命中」，否则命中率会被实现差异污染。

边界与工程取舍 ​

Blend 改变的是前填数值，属于有意的近似。对要求与全量前填逐 token 一致的评测（如某些回归测试、水印检测依赖的完整分布），不应默认打开。多租户下，检索块可能含用户私有文档，块键与存储 ACL 必须按租户切开；全局知识库才允许跨用户命中。

分层卸载的尾延迟不适合解码工作集。LMCache 的主场是前填上下文加载；把正在 decode 的 KV 卸到盘，TBT 会先坏。远端对象存储走 HTTP 时，CacheGen 的压缩往往仍不够，需要近 GPU 的 RDMA 池（Mooncake / NIXL）承接热层。CPU 内存池与分页分配器、CUDA 缓存分配器的生命周期要配对，泄漏会表现为「缓存越大越 OOM」。

不要把 EuroSys 与 SIGCOMM 两篇的倍数加在同一条因果链上当 10×。它们的基线分别是「全量重算 / 前缀缓存 / 未压缩传输」，乘起来没有实验意义。引用时分开写 TTFT 与体积，并钉数据集。

出处钉 Yao et al., CacheBlend: Fast Large Language Model Serving for RAG with Cached Knowledge Fusion, EuroSys 2025（arXiv:2405.16444）；Liu et al., CacheGen: KV Cache Compression and Streaming for Fast Large Language Model Serving, SIGCOMM 2024（arXiv:2310.07240）；文档 https://docs.lmcache.ai/ 与 https://github.com/LMCache/LMCache。

小结 ​

  • LMCache 是引擎外的 KV 管理：分层存放、跨实例复用、可选的非前缀融合与压缩流式。
  • CacheBlend 复用任意位置的块 KV，用约一成半 token 的重算补跨注意力，面向 RAG 拼接。
  • CacheGen 把 KV 编成可分级比特流，带宽不足时回退重算，降的是传输体积。
  • 与 radix / Mooncake 叠用时要分清「本进程前缀」「集群 RDMA 对象」「跨块近似融合」。
  • 倍数分别相对全量重算或未压缩传输，不能连乘。
  • 出处：CacheBlend EuroSys 2025、CacheGen SIGCOMM 2024、LMCache 仓库。
