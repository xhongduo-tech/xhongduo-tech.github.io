大模型 · 2026-09-03

长上下文是否取代 RAG ​

相关段落放在输入中间时，模型利用证据的能力往往低于放在开头或末尾；把整库塞进窗口，既贵，也不等于已经「检索到了」。

—— Liu et al., Lost in the Middle, TACL 2024；对照 Lewis 的 RAG：非参数记忆首先是可选择、可更新的索引，而不只是更长的自注意力

上下文窗口从 4k 涨到 128k、1M，很容易得出口号：不必切分、不必向量库，把手册和工单一次性喂进去。窗口确实消灭了 一类 问题——单文档较短、必须通读才能答的任务，检索切碎反而有害。它没有消灭索引、权限、新鲜度、费用和引用。Lewis 等人的 RAG 核心是参数记忆加 可替换的 非参数记忆；长上下文只扩大了一次前向能看见的 token 数。Liu 等人指出，即使证据已经在窗口里，位置在中间时利用率下降。本篇把「能不能塞进去」和「应不应该靠塞进去代替检索」分开，并说明两者如何叠用。

问题 ​

取代论假设三件事同时成立：语料总能装进窗口；装进去后模型总能找到相关跨度；装进去的费用与延迟可接受。第一件在私有全集、多租户、持续增长的语料上不成立。第二件被中间丢失、注意力稀释、以及「 distraction 文档」打脸——无关文本不是中性背景，会抢分数。第三件：预填充随长度涨（即使线性核也有大常数），把 80 万 token 的仓库每次问答都预填一遍，单位答案成本会高过「检索 5 块再生成」。

还有权限与审计。检索可以按文档 ACL 过滤后再生成；长上下文若把用户不可见的文件也塞进窗口，等于在模型侧泄漏。引用上，RAG 的块 ID 对应到页；百万 token 通读即使答对，也难指回条款号，除非再做一遍事后定位——那已经是检索。问题不是「长上下文有没有用」，而是它替代的是 通读已选中的材料，不是 从库中选择材料。

上下文窗扩大解决了哪一类问题 ​

窗口变长，最适合的是：用户或上游已经圈定的材料（一篇合同、一次会话历史、一组指定附件）、需要全局结构的任务（跨章节对照、代码仓库里已打开的子树）、以及检索容易切错的表格与长证明。这时应少切、甚至不切，让自注意力做交互。Needle-in-a-haystack 类评测证明「能从干草堆里读出插针」，不等于「干草堆可以是整个公司网盘」。评测若只用合成针，会高估通读策略在真实干扰文档上的表现。

把检索到的父块或多篇文档 拼进 长窗口，这是 RAG 加长上下文，不是取代。取代意味着取消索引、取消选块。口号混淆来自把「生成器能读更长提示」写成「系统不再需要选择」。

方法 ​

决策可以按语料基数来。十份以内、总长稳定低于窗口且每次问题都需要通读：直接塞，配引用提示。千份以上、增长中、或单次只需一小撮证据：索引 + 检索，生成器窗口只承担选中的块和对话。中间地带用混合：检索召回几十块，必要时把同一文档的相邻节展开，利用长窗口读 局部全集 而不是全球全集。这与父子切分一致：子块找门，长上下文进房间。

费用上应估算预填充 token：长上下文路径是 \(O(\)语料\()\) 每问，RAG 路径是 \(O(\)查询编码 + \(k\) 块\()\)。缓存整库 KV 只对「语料不变、用户共用同一前缀」成立，私有检索查询会使前缀分叉，前缀缓存 救不了每问不同的文档集合。新鲜度：索引可以增量更新一块；长上下文路径要换提示里的整份粘贴件，缓存全部失效。

中间丢失与费用 ​

Lost in the Middle：多文档问答里，把关键段落从开头挪到中间，准确率下降。因此即使窗口够大，块的 排列 仍要设计——这是重排序 和提示布局的事，不是「再买一档上下文套餐」能自动修好的。费用上，长预填充抬高 TTFT，占满批处理槽位，服务侧表现为并发下降。对多租户问答，RAG 让不同用户的热路径只共享系统提示前缀；通读各自的整库则几乎无法共享 KV。

产品上可以用长上下文做 会话内 材料（用户刚上传的 PDF），用 RAG 做 库内 材料（知识库）。两条路径的引用格式应统一，以免模型对上传件有页码、对库内件没有。不要用「模型宣称已读完全文」当证据；要用定位到的片段。

机制 ​

自注意力提供的是给定 token 集合上的全连接交互，不提供集合的选取。选取是检索（词法、向量、规则、用户指定）。窗口变长，选取的 容错 变大：可以多塞一些可能相关的块，让注意力再筛选。容错不是无限的：干扰项增加，中间位置利用率下降，生成器开始抄最近或最像「官方口吻」的段落。RAG 的非参数记忆还提供更新语义：改一页不必重训，也不必重传其余九千页。长上下文本身没有索引失效协议，除非你在应用层重建一套，那就是检索。

多跳推理常被用来支持通读：所有证据同时在场，不必多轮查询。若证据分布在未知文档里，通读要求先把它们放进窗口，又回到选取。多轮 ReAct 检索是在时间上做选取；长上下文是在空间上做交互。两者补，不互斥。

LOFT 一类基准问的是长上下文能否 承担 检索式任务，结论通常是「在受控语料上有时接近、费用更高、对干扰敏感」。不要把某一模型的营销上下文长度写成已经替代企业搜索。

检索仍然负责的三件事 ​

一是选取：从增长的、权限分片的集合里挑证据。二是更新：新文档可检索，而不必每次问答重传全集。三是归因：块 ID、版本、URL。长上下文可以在「已选取集合」上把三件事做弱：例如用户拖进三份 PDF，窗口当工作台。一旦集合变成「全公司」，三件事都回到索引。安全策略（不能把 A 租户文档放进 B 租户窗口）也是检索层过滤，不是注意力掩码能猜出来的。

边界与工程取舍 ​

不要用针测分数决定架构。针测几乎没有语义干扰，真实库里满是近主题错文档。也不要在窗口广告数字上假设有效长度等于标称长度；位置偏差和训练长度分布会让尾部不可用。代码仓库问答往往需要结构检索（符号、调用图）而不是纯通读或纯切块，长上下文是读文件内容的手段，找文件仍要索引。

叠用是默认：混合检索召回，重排，必要时展开父文档进长窗口，生成时要求引用。取消 RAG 只在材料封闭且每次必须通读时划算。引用 Liu et al. TACL 2024、Lewis et al. NeurIPS 2020；长上下文能否 subsume 检索的系统研究应点名具体基准，不要编造统一结论年分。

缓存「整本知识库的 KV」看起来像免费长上下文，实际是在假设所有用户共享同一只读前缀。一旦按用户检索分叉，这块 KV 立刻变得不可共享，费用模型回到按次预填充。

小结 ​

  • 长上下文扩大一次能读的 token，不负责从增长的库里选取、过滤权限和更新条目。
  • 中间丢失说明「在窗口里」不等于「被用上」；排列与干扰项仍然重要。
  • 通读适合已圈定、需全局结构的材料；开放知识库仍要索引。
  • 检索加长窗口是互补：召回找门，长上下文进房间。
  • 费用、TTFT、KV 共享和引用是取代论经常省略的约束。
  • 针测与营销窗口长度不能当企业搜索的替代证明。
  • 出处：Liu et al., Lost in the Middle, TACL 2024；Lewis et al., RAG, NeurIPS 2020。
