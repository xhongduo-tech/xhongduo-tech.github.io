verl 与 HybridFlow ​

HybridFlow 以混合方式结合单控制器与多控制器范式，使 RLHF 数据流既能灵活表达，又能高效执行。

—— Sheng et al., HybridFlow: A Flexible and Efficient RLHF Framework, EuroSys 2025

verl（Volcano Engine Reinforcement Learning for LLMs）是 HybridFlow 论文的开源实现，由字节跳动 Seed 团队发起，现由社区与 Hugging Face 等生态共同维护。RLHF / RLVR 把一次迭代拆成生成、奖励、参考对数概率、优势估计、策略更新等多段，每段都是分布式大模型程序，段与段之间是多对多的数据交换。传统 RL 框架用单控制器调度一切，控制消息会淹没大模型算子；纯多控制器又把算法图嵌进各 worker，换算法、换并行策略都很痛。Sheng、Zhang、Ye、Wu 等人提出混合编程模型，并设计 3D-HybridEngine，在训练与生成之间做零冗余的 actor 重分片。论文报告相对当时基线 1.53×–20.57× 的吞吐提升。

问题 ​

把 PPO 画成数据流：actor 生成、reward 模型打分、critic 或组内基线估优势、actor / critic 再训练。每个节点内部已是张量并行、数据并行、流水线并行之一；节点之间还要广播序列、logprob、mask。单控制器（driver 进程逐算子下发）在小模型 RL 里清晰，在 LLM 上调度粒度太细，dispatch 延迟压过计算。多控制器（每个 rank 跑同一份脚本，集合通信同步）适合单一训练图，但 RLHF 是多模型、多阶段、资源可重叠的图，把阶段嵌进 SPMD 脚本会导致：换 GRPO、换异步 rollout、换 Megatron 与 vLLM 的搭配都要改通信嵌套。

资源放置同样麻烦。生成希望推理引擎的 KV 布局；训练希望 FSDP 或 Megatron 的分片。若保存两份 actor 权重，显存翻倍；若每次用通用通信重分片，迭代时间被 reshard 吃掉。HybridFlow 要同时解决「算法图怎么写」和「训练-生成如何共权重」。

控制平面与数据平面必须拆开 ​

RL 算法的控制流是动态的：按 batch 决定是否再采样、是否跳过旧 reward、是否做 KL 惩罚。模型计算的数据流是静态 SPMD。把两者写在同一层，要么牺牲灵活性，要么牺牲吞吐。混合模型的主张很具体：宏观图用单控制器编排，微观计算用多控制器执行。

verl 名字里的 Volcano Engine 来自字节跳动的云与训练设施；仓库后来以 verl-project/verl 与 Hugging Face 文档的形式进入开源生态。论文评测的是 HybridFlow 系统，verl 是其代码名。读文档时两者常混用，指的是同一套混合控制器架构。

方法 ​

编程模型提供分层 API：Worker 封装一种角色（actor 训练、rollout 生成、reward、reference），内部走 FSDP / Megatron / vLLM / SGLang 等后端；WorkerGroup 与 ResourcePool 描述这组 worker 占哪些 GPU；训练器进程（单控制器）只编排阶段与数据依赖——先 rollout，再打分，再更新——而不插手 GEMM。数据在阶段间按协议搬运（广播、all-gather、或点对点），对算法作者暴露的是张量与批，而不是 NCCL 嵌套。

3D-HybridEngine 针对 actor 在「训练分片」与「推理分片」之间切换。三维来自数据并行、张量并行与流水线（或推理侧的复制）布局。引擎在切换时不保留完整冗余副本，而是按布局代数做重分片，通信体积相对朴素 dump-reload 显著下降。论文强调零显存冗余：同一组 GPU 上训练与生成交替时，不必为两套并行策略各留一份全量权重。

算法作为可替换数据流 ​

PPO、GRPO、以及后续社区加上的 DAPO 等，都被写成阶段图而不是硬编码循环。单控制器使「把奖励换成规则函数」「把 rollout 换成异步队列」变成改图，而不是改每个 rank 的通信顺序。这是 HybridFlow 相对 DeepSpeed-Chat、OpenRLHF、Nemo-Aligner 的接口主张：那些系统已能跑 RLHF，但算法与并行的耦合更紧。verl 文档把高层称为 MPMD 式编排，把引擎内部称为 SPMD。

Hugging Face 生态把 verl 当作可接 TRL 之外的大规模 RL 后端之一：模型来自 transformers，生成可接 vLLM，训练可接 FSDP。对用户，价值是同一套脚本从单机试验换到多机 Megatron，而不重写优势估计。

机制 ​

吞吐增益来自两处。一是调度：单控制器只发阶段级指令，重计算留在多控制器内部，dispatch 开销不再随层数线性膨胀。二是重分片：训练与生成的瓶颈常是权重布局不匹配；3D-HybridEngine 把这次匹配做成一等算子，迭代里的气泡缩短。论文在多种 RLHF 算法与模型规模上给出 1.53× 到 20.57× 的区间——上限出现在基线因冗余权重或拙劣编排而极慢的设置，下限是已经较优的对照。

放置与共享 ​

Ray placement group 上的 ResourcePool 允许 actor 与 rollout 分时复用同一组 GPU，或把 reward 模型放到另一组。灵活放置是混合模型的产品：单控制器看得见全局资源，多控制器看不见也不该看见。错误放置的典型症状是生成时训练分片未卸掉、或 critic 与 actor 抢同一张卡导致 OOM。这些是编排 bug，不是算法 bug。

HybridFlow 不发明 PPO。它发明的是 RLHF 作为分布式数据流的执行方式。算法正确性仍取决于优势估计、KL 控制、数据是否 on-policy。系统快不能补救奖励黑客；只能让你更便宜地迭代算法。

与 Pathways 一类「单控制器调度多计算图」的系统同族：宏观一张图，微观各节点自己并行。LLM RL 的特殊性在于节点本身已是 3D 并行的大模型，且训练/推理布局不同，所以需要专门的 HybridEngine，而不是通用 DAG 调度器。

边界与工程取舍 ​

混合模型增加概念负担：使用者要同时理解 Ray 编排与 FSDP/Megatron/vLLM。调试时错误可能出在控制器逻辑，也可能出在后端内核，栈比单一训练脚本更深。3D 重分片依赖后端暴露的权重布局；新并行策略要接进 HybridEngine 才能吃到零冗余。异步 rollout、投机解码、MoE 专家并行，都是后续工程，不是 2025 年论文里已经证完的部分。

吞吐数字不能跨论文横比。对照系统的版本、是否开启梯度检查点、生成长度、是否与训练同卡，都会改变倍数。合理用法是：在自己的模型与并行策略上复现基线，再看 verl 是否缩短 step time。算法研究还应报告样本效率，而不是只报告 tokens/s。

把 verl 理解成「Hugging Face 的官方 RLHF 实现」不准确。它是字节跳动与港大等工作开源、社区共建、Hugging Face 文档与教程积极接入的栈。选型时比较的是编排灵活性与引擎适配，而不是品牌归属。

小结 ​

  • HybridFlow 用单控制器编排 RL 阶段、用多控制器执行分布式模型计算，对应开源库 verl。
  • 分层 API 把算法图与并行后端解耦，便于在 PPO、GRPO 等数据流之间切换。
  • 3D-HybridEngine 在训练布局与生成布局之间重分片 actor，追求零权重冗余。
  • 论文报告相对当时 RLHF 系统 1.53×–20.57× 的吞吐；倍数依赖基线与放置，需自行对照。
  • 系统加速的是迭代成本，不替代奖励设计与 on-policy 正确性。
  • 出处：Sheng et al., HybridFlow: A Flexible and Efficient RLHF Framework, EuroSys 2025（arXiv:2409.19256）；实现见 https://github.com/verl-project/verl 。
