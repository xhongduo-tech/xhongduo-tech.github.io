视频 token 与时间采样 ​

视频不是「很多张图」；时间轴上采多少帧、每帧压成多少 token、位置编码如何对齐绝对时间，三者一起决定模型看见的运动。

—— 归纳自 Qwen2-VL / Qwen2.5-VL 的 MRoPE 与动态 FPS 叙述

图像 VLM 把一张图切成空间 patch。视频多一个时间维：同一空间网格在 \(T\) 个时刻重复。若每帧都按图像预算编码，一秒 30 帧的片段会把上下文打满，运动反而看不见——注意力全花在相邻近重复帧上。视频 token 设计因此是压缩问题：时间上如何采样，空间上如何合并 patch，位置上如何让模型知道「这是第几秒」而不是「这是第几张图」。Qwen2.5-VL 把动态分辨率延伸到时间维（动态 FPS），并把 MRoPE 的时间分量与绝对时间对齐。Qwen2.5-Omni 的 TM-RoPE 进一步让音画共用时间刻度。本篇讲这条时间轴，不把视频生成或多模态对话策略展开。

问题 ​

记视频为帧序列 \(I_{1:F}\)，原始帧率 \(r\) fps。朴素做法是每帧独立过 ViT，得到 \(F\times N\) 个视觉 token，\(N\) 为单帧 patch 数。\(F=r\Delta t\)，一分钟 30 fps、每帧数百 token，序列长度达到文本小说量级，二次注意力不可用。更糟的是相邻帧互信息极高，有效信息增速远低于 token 增速。

必须在三个地方减量。时间采样：用 \(r'\ll r\) 的帧率抽帧，或按场景切关键帧。空间压缩：2×2 patch merge、token 剪枝、 perceiver 式潜向量。时间合并：把相邻 \(k\) 帧合成一个 temporal patch。减量之后要回答：模型怎么知道两帧之间过了 40 ms 还是 400 ms？若位置 ID 只按「第几张输入帧」递增，同一段动作在 2 fps 与 10 fps 采样下会得到不同的时间几何，运动速度无法跨视频迁移。

帧索引不是时间 ​

Qwen2-VL 的 MRoPE 已把位置拆成时间、高、宽三个分量。图像上时间 ID 全图相同；视频上每帧递增。但该递增若绑定输入帧序号，则丢失绝对时长与采样率。Qwen2.5-VL 技术报告指出这一点，并把时间分量改为对齐绝对时间：时间 ID 的间隔反映真实时间间隔，使不同 FPS 下同一物理时段落到一致的时间几何上。

\[\Delta \mathrm{id}_t \propto \frac{\texttt{tokens\_per\_second}\times \texttt{temporal\_patch\_size}}{\mathrm{FPS}}. \]

实现里常用这类比例，使「一秒」在位置编码上占据稳定的跨度，而不是「一帧」占据 1。

压缩帧（把若干原始帧合成一个时间 patch）降低帧率的同时平均掉亚帧运动。闪白、镜头切换、口型可能落在被平均掉的那一侧。动态 FPS 的意义是：运动剧烈时提高采样，静止镜头降低采样，而不是全局锁死 1 fps。

方法 ​

时间采样先决定送入编码器的帧集合。均匀抽帧简单、可复现，但对广告快切不公平。动态 FPS 按内容或按长度预算调整 \(r'\)，使长视频仍能覆盖全程。抽帧后，每帧仍可能经 Naive Dynamic Resolution 切块，再 2×2 merge 控制空间 token。时间维上，相邻帧可打成 temporal patch，编码器一次看见短时立方体而不是单张图。

位置编码用 MRoPE：旋转角分配给 \((t,h,w)\)。文本三分量共用同一 1D 下标，退化为普通 RoPE。视频帧的 \(h,w\) 与静态图相同，\(t\) 随绝对时间步进。Qwen3-VL 后来改为用显式文本时间戳（如 <3.0 seconds>）标记时间块，认为把时间完全塞进位置频率会在长视频上失衡；那是下一阶段的选择，说明时间轴仍是未完成的接口。Qwen2.5-Omni 的 TM-RoPE 让音频每 80 ms 一个时间 ID，视频帧的时间 ID 按时间戳对齐到同一刻度，音画交错才有共同的「现在」。

Token 率与秒 ​

设时间 patch 覆盖 \(\tau\) 秒，每帧空间 merge 后剩 \(N\) 个 token，则视频 token 率约为 \(N/\tau\) 每秒，再乘采样后的帧组数。这与音频 12.5 Hz 形成对照：音频沿时间已经是一维的，视频是「时间 × 空间」。要做音画对齐，应先统一时间刻度，再谈每秒多少 token。只对齐 token 个数而不对齐秒，口型与字幕会系统性错位。

Qwen3-Omni 为尽量保留视频信息并与音频采样率对齐，使用动态帧率；音画表示用时间 ID 直接锚到绝对时间，而不再像 Qwen2.5-Omni 那样切成固定 2 秒块。这使任意时长流式输入在位置上可续接。代价是实现必须携带每段的时间戳元数据，而不是假设「token 下标除以常数即秒」。

机制 ​

MRoPE 的时间分量把相对时间差写成旋转，模型用内积感知「隔了多久」。对齐绝对时间后，相同物理间隔在不同 FPS 下对应相近的旋转差，运动速度成为可学习的不变量。若时间 ID 只按帧号，\(10\) fps 下间隔 10 与 \(2\) fps 下间隔 2 可能表示同一秒，几何不一致，速度头无法稳定。

空间 token 过多时，时间注意力被稀释：每一帧的「现在」要和所有空间位置交互。窗口注意力、周期性全局注意力（Qwen2.5-VL 视觉编码器）是在空间减负，让时间维有余量。DeepStack 一类多层注入不增加上下文长度，但也不是时间采样的替代品。时间信息丢了，再深的层也补不回没采到的帧。

显式时间戳把时间变成可读文本，便于接地和时间定位任务，但占用上下文，且格式（秒 vs 时分秒）要在训练里覆盖。位置编码路线零额外 token，但对超长视频的频率外推更敏感。两条路是工程取舍，不是对错。

与图像 OCR 管线的差异 ​

文档 OCR 的「时间」几乎不存在，页序是离散章，不是连续秒。把长 PDF 当视频——每页一帧——会误用时间插值：页与页之间没有光流。视频 token 方法不应直接套到多页文档。反过来，把视频当「稀疏的文档图」只做关键帧 OCR，会丢掉说话与动作。模态决定采样语义：文档按页，视频按秒。

边界与工程取舍 ​

极端慢动作与延时摄影在绝对时间对齐下会拉开时间 ID，可能超出训练时见过的时间跨度，外推失败。极短广告则几乎只有一两帧，动态 FPS 无空间可动。在线流还要因果抽帧：不能为了选关键帧而看未来 10 秒。离线理解可以双向选帧，在线助手不能。

压缩过狠时，评测上的「视频理解」退化成「封面图理解」。应用应报告实际平均 FPS 与每秒 token，而不是只报模型名。音画任务必须验证时间 ID 是否共用 80 ms 一类刻度；只把音频和视频拼进同一序列、位置却分别从零编号，等于拆掉 TM-RoPE。

Qwen2.5-VL 技术报告（arXiv:2502.13923）把动态 FPS 与绝对时间 MRoPE 列为相对 Qwen2-VL 的改动。引用时间轴时以该报告为准；Qwen3-VL 的交错 MRoPE 与文本时间戳是后续故事，不要回写到 2.5。

小结 ​

  • 视频 token 由时间采样、空间压缩与时间位置编码共同定义；只增加帧数会用重复像素填满上下文。
  • 帧索引不是时间；Qwen2.5-VL 将 MRoPE 时间分量与绝对时间对齐，使不同 FPS 共享时间几何。
  • 压缩帧与动态 FPS 用预算换运动分辨率；亚帧事件可能被平均掉。
  • 音画对齐依赖统一时间刻度（如 TM-RoPE 的 80 ms），而不是对齐 token 个数。
  • 长视频外推、流式因果抽帧、以及「视频当文档页」的误用，是主要失败模式。
  • 出处：Qwen2.5-VL 技术报告（arXiv:2502.13923）；音画时间对齐见 Qwen2.5-Omni（arXiv:2503.20215）与 Qwen3-Omni（arXiv:2509.17765）。
