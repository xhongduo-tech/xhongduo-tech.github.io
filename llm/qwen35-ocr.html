Qwen3.5-OCR：原生 PDF 与多轮抽取 ​

qwen3.5-ocr 支持通过 Response API 直接传入 PDF 文件进行文档解析，无需手动将 PDF 拆分为图片。

—— Qwen Cloud / 阿里云百炼文字提取文档

前代文档 OCR 的默认路径是：把 PDF 每一页光栅化成图，再按多图输入逐页识别。光栅化丢掉字体、矢量路径、嵌入文本层和页面树，只留下像素。调用方还要自己管分页、分辨率和跨页上下文。Qwen3.5-OCR 基于 Qwen3.5 架构，把文档解析、文字定位和关键信息抽取做了专用强化，并明确两件新产品能力：原生 PDF（不必先渲染成图）与多轮对话式抽取。前者改的是输入表示，后者改的是交互状态。本篇只谈这两件事如何改变文档 AI 的接口形状，不把全部卡证类型列表抄进正文。

问题 ​

PDF 不是图像容器。一页里可以同时有：可选择的文本对象、矢量线框、嵌入字体、扫描图像 XObject、以及标注和表单域。若一律 pdf2image，文本层被毁掉，模型必须从像素里把已经数字存在的字符再认一遍，既慢又引入识别误差。扫描件 PDF 则相反：没有文本层，光栅化不可避免。一刀切的「先转图」把两类文档绑上同一条最差路径。

单轮 OCR 的条件是 \(p(y_1\mid D)\)，\(D\) 为整份文件。多轮变成

\[p(y_{t}\mid D, y_{<t}, q_{\le t}), \]

查询 \(q_t\) 在对话中才会收窄抽取目标。用户先要全文，再问「金额是多少」，再改 schema 要「只要税前」。每次把同一份文件当新请求，视觉 token 重复计费，且模型看不到上一轮已经对齐过的字段。早期 Qwen-VL-OCR 快照按单条消息处理，不保留上下文。文档业务却天然是多轮的：核对、追问、纠正、补字段。

渲染损失与跨页状态 ​

光栅化还引入分辨率契约。DPI 太低，小号字不可读；太高，页数一多就打满 max_pixels 与上下文。原生 PDF 路径若能直接消费页面描述，理论上可按对象而不是按像素预算工作——至少对数字文档如此。跨页表格、脚注续页、目录与正文分离，则要求模型在记忆里保持「上一页最后一行」和「表头」，这不是单张图 VQA 的设定。多轮与长 PDF 是同一类状态问题的两个尺度：轮次之间的状态，和页与页之间的状态。

原生 PDF 不是万能输入。加密文件、损坏交叉引用表、极端巨大的单页矢量、以及以图片为主的扫描件，仍会退回光栅或直接失败。产品文档给出页数与体积上限（如最大 50 页、不超过 100MB），这是服务约束，不是模型隐层宽度定理。

方法 ​

Qwen3.5-OCR 允许在 Response API 中直接传 PDF 做文档解析；该路径不支持把同一文件随便塞进普通 Chat Completions。调用方可设置 ocr_options.task，例如 document_parsing，让输出走 LaTeX 或其他任务契约。数字页不必先变成 JPEG。扫描页在服务端仍可能被内部光栅化，但对调用方来说契约已经是「文件进、结构出」，而不是「自己管 dpi」。

多轮方面，从 qwen3.5-ocr 起支持对话：后续轮可以不带图，只发纯文本追问，依赖已上传文档的上下文。内置任务与用户自定义 Prompt 结合，不再强制覆盖；任务结构化结果通过 ocr_result 返回。这把「模板抽取」和「自然语言核对」叠在同一会话里。例如先按 schema 抽发票字段，再问某一行是否含税，不必重新传文件。

与「多图假长文档」的差别 ​

把 PDF 预渲染成 \(N\) 张图再当多图 VQA，页间关系完全靠提示词「这是第 i 页」。模型看到的是 \(N\) 组互不共享 PDF 对象树的视觉 token。原生路径至少保留文件级身份：同一文档、页序、可能的文本层。多轮则在时间维上复用这份身份。两者一起，才接近「打开一份文件然后对话」，而不是「每次邮寄一包截图」。

像素预算仍然存在。图像输入仍有 min_pixels / max_pixels；PDF 有页数和体积上限。原生并不等于无限页。超过上限要在应用层切分，切分时必须自己处理跨文件边界的表和段落——模型不会自动合并两次请求里的半张表。

机制 ​

多轮抽取改变的是条件前缀。第一轮条件是文件表示（页面编码或内部光栅加文本层），输出是转写或 JSON。后续轮把已经生成的结构放进对话历史，新的查询是短文本。视觉编码器不必每轮重跑——这是服务端缓存与计费细节，但对机制的意义是：追问是语言对结构的查询，不是重新感知。若历史被截断，追问就退回无记忆的单轮，可能与文件不一致。

原生 PDF 改变的是感知前端。文本对象可以按阅读顺序注入为离散 token，矢量与图像仍走视觉。混合页（上半扫描、下半数字字）需要两种前端对齐到同一阅读坐标。这比「整页都是图」难，也比「整页都是文本层」难。模型若过度信任文本层，会忽略盖章和手写；若忽略文本层，又浪费已有字符。工程上通常文本层当强先验、图像当校验，但公开文档并未把内部融合写成可调超参，调用方只能通过任务类型和追问来间接触发不同行为。

Response API 与 Chat API 的能力不对称：PDF 解析被绑在 Response 上。集成时不要假设「换一个 OpenAI 兼容 base URL 就能传 file」。协议选择和模型选择同样决定能否原生吃 PDF。

卡证与对话的交互 ​

文档称 Qwen3.5-OCR 在身份证、驾驶证等业务卡证上的信息抽取明显增强，并支持数十种证照票据类型。多轮在这里的典型用法不是闲聊，而是纠错：第一轮 JSON 某字段为 null 或 ?，用户补充拍摄角度或改 schema 再抽。因为任务通道与 Prompt 并存，纠错指令不会把 KIE 头整个关掉。幻觉风险仍在：文字过密或过糊时，模型可能编造笔画；与文字提取无关的开放问题，文档明确不保证准确。多轮会放大这种风险——一旦第一轮写进错误字段，后续追问可能把错误当成已验证事实。

边界与工程取舍 ​

页数、体积、超时和计费按页或按 token，都会比单图 OCR 更陡。50 页上限意味着长报告要切片；切片策略错误会造成目录页与正文页在不同会话里，多轮记忆对不上。扫描件占满体积预算时，原生 PDF 的好处只剩少一次客户端转码，服务端仍在认像素。

多轮会话默认不在服务端永久保存。调用方需自行传历史，或使用 Response 的上一轮标识一类机制。过长的 ocr_result 塞进历史会挤掉页面证据。应把结构化结果落库，对话里只留摘要和文档句柄，而不是把整本 LaTeX 当聊天记录。

不要把原生 PDF 理解成「模型执行了 JavaScript 或打开了附件」。OCR 路径消费的是页面外观与文本抽取，不是完整 PDF 运行时。表单提交、数字签名校验、嵌入文件解包属于另一类文档工作流。

小结 ​

  • Qwen3.5-OCR 的关键接口变化是原生 PDF 输入与多轮对话式抽取，不必先把每一页渲染成图再当互无关系的多图 VQA。
  • PDF 走 Response API，并受页数与体积上限约束；扫描件内部仍可能光栅化。
  • 多轮允许不带图追问，内置任务结果与用户 Prompt 并存，结构化输出在 ocr_result。
  • 追问是对已解析状态的语言查询；历史截断或第一轮幻觉会被后续轮当成事实。
  • 与文字无关的开放问答不在 OCR 契约内；过密过糊仍会幻觉。
