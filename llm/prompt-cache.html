Prompt Cache ​

把提示里反复出现的模块写成 schema，预先算好它们的注意力状态；只要位置编号按模块分配，这些键值可以在不同提示之间拼接复用。

—— Gim, Chen, Lee, Sarda, Khandelwal, Zhong，Prompt Cache，MLSys 2024

系统提示、少样本示例、待问答的文档，在流量里反复出现。服务引擎后来用自动前缀缓存识别从位置 0 起逐 token 相同的那一截。Gim 等人更早的 Prompt Cache 问的是另一件事：重叠片段不一定在前缀上，也不一定每次都出现在同一下标。他们用 Prompt Markup Language（PML）把可复用段标成模块，按 schema 预计算注意力状态（KV），再在请求到来时按用户勾选的模块拼接。本篇写模块、不连续位置编号与和自动前缀的差别，不把云厂商按字符计费的「prompt caching」当成同一篇论文。

问题 ​

Transformer 的 KV 依赖两件事：token 身份，以及写入时的位置编码。RoPE 一类方案把下标旋进键里，同一段话出现在位置 \(0\) 与位置 \(500\) 不是同一份 KV。因此朴素「把这段文本的 KV 存下来、下次在中间插入」会把相位用错。第二条困难是识别：没有标记时，引擎很难知道哪些跨请求的子串是「同一个模块」，而哪些只是碰巧相似。

自动前缀共享把问题缩小为「从左端起的最长公共前缀」，实现简单、语义正确，但浪费了一种常见结构：schema 里有一组互斥模块（选城市、选任务、选文档），用户每次只激活其中几个，未选中的不应占用前缀位置，选中的也不总是出现在固定偏移。Prompt Cache 要在不改模型权重的前提下，让这些模块的注意力状态可预计算、可按需拼接。

位置编号必须进入契约 ​

复用的不是「这段词的内容向量」，而是「这段词在 schema 指定的位置编号下算出来的 KV」。schema 预先给每个模块留好一段位置 ID，哪怕某次请求没选这个模块，其他模块仍使用自己那套编号。于是选中模块的 KV 可以直接拼接，不必因为邻居缺席而重算。作者的经验观察是：模型对不连续的位置 ID 有一定容忍——中间空出一段编号，softmax 仍能工作，输出质量在他们的评测里可接受。这不是理论保证，是该工作成立的经验前提。

不要把不连续位置 ID 推广成「任意打乱 RoPE 都没事」。Prompt Cache 的空隙来自 schema 里未选中的模块，编号仍是训练时见过的单调递增关系的变体。随机置换下标会失败。换模型、换 RoPE 基数，都要重测质量。

方法 ​

用户（或应用模板）用 PML 写两样东西。一份 schema 声明有哪些 prompt module、它们的互斥关系（union）、可选参数槽位和对话角色标签。一份 prompt 从该 schema 派生，用标签勾选本次要用的模块，例如选「迈阿密」文档而不是「纽约」。服务端第一次见到 schema 时，为每个模块在其预定位置上做预填充，把 KV 存进模块缓存。之后同一 schema 下的请求只计算未缓存的用户槽，把选中模块的 KV 按编号拼起来，再继续生成。

模块预计算与运行时拼接 ​

设模块 \(m\) 被赋予位置集合 \(\mathcal{P}_m\)。预计算得到 \(\{k_j,v_j\}_{j\in\mathcal{P}_m}\)。一次请求选中集合 \(M\)，可见键值是

\[\mathcal{C}(M)=\bigcup_{m\in M}\{k_j,v_j\}_{j\in\mathcal{P}_m} \]

再拼上本次独有的、未缓存的后缀（真正的用户问题）。注意力仍是 SDPA，只是 \(K,V\) 来自拼接而不是当场整段预填充。union 保证互斥模块共享同一段位置区间，避免两份文档抢同一下标。parameter 槽为短可变字段留空位，长度要在 schema 里写死，才能保持后续模块的位置稳定。

延迟数字该怎么读 ​

论文原型基于 HuggingFace Transformers，在 Llama 2、Falcon、MPT 上测。长提示（文档问答、推荐）的 TTFT 在 GPU 上可到约 8×，CPU 上可到约 60×——CPU 预填充更痛，省掉文档模块的收益更大。数字是相对「每次重算整段提示」，不是相对已经做了自动前缀缓存的现代引擎。质量上作者报告与未缓存基线接近，前提是 prompt 确实按 schema 填写。

机制 ​

机制是「用显式结构换位置可预测性，再用位置可预测性换 KV 复用」。PML 让复用边界成为语法问题，而不是运行时猜哈希。不连续位置 ID 让未选中模块不必在序列里占真实 token，却仍保留它们在编号轴上的「坑位」，使选中模块的 RoPE 相位与预计算时一致。这与自动前缀恰好相反：前缀缓存要求物理 token 从 0 连续相同；Prompt Cache 允许中间缺模块，但要求编号服从 schema。

和 RadixAttention 比，后者对任意共享前缀做内容寻址，调用方不用写 XML；前者能复用非前缀模块，调用方必须把提示结构化。两者可以同时存在：schema 的公共外壳走自动前缀，互斥文档模块走 Prompt Cache 的预留位置。混用时缓存键必须包含 schema 版本，否则改一个模块的正文会让旧 KV 继续被拼进去。

参数槽长度写死是为了后面模块的位置不变。用户输入一旦超过声明长度，后续模块的相位全部错位，缓存必须作废并回退到整段预填充。实现上应拒绝超长槽，而不是截断后假装命中。

为何后来工业界更多做前缀而不是 PML ​

PML 要改提示工程与客户端。多数应用其实是「系统提示 + 用户问题」的左对齐结构，自动前缀已经吃掉最大那块 TTFT。文档问答若文档每次不同且不在固定模块集合里，schema 也帮不上。Prompt Cache 更适合封闭模块集合的产品：技能列表、城市百科、工具说明书版本化。工业界的「prompt cache」计费接口，语义上更接近前缀 KV 的命中时长，与这篇 MLSys 论文的模块拼接不是同一个对象。

边界与工程取舍 ​

必须改提示写法；没有 schema 就没有这篇论文里的复用。不连续位置对部分模型、部分任务可能伤质量，上线前要用该模型的真实提示回归，不要只看论文的文档 QA。模块缓存占显存：模块多、文档长时，预计算本身就是一份很大的 KV 池，需要 LRU 与按 schema 分命名空间。LoRA、量化档、权重版本都要进缓存键。

不要把 Prompt Cache 理解成可以复用「提示中间任意一段相同子串」。没有 schema 给定的位置，那段子串的 RoPE 对不上。也不要在训练时没用过的超长空隙上假设模型仍然稳定。换到 YaRN、长上下文插值或与训练窗口差很多的编号，经验观察需要重做。

论文的 8× / 60× 是 TTFT，主要省预填充。解码阶段的逐步注意力仍随已拼接模块的总长度增长，模块选得越多，decode 越慢。产品指标应同时报首 token 与每个输出 token 的间隔。

小结 ​

  • Prompt Cache 用 PML schema 把可复用提示标成模块，预计算 KV，按勾选拼接，以降低 TTFT。
  • 关键经验是模型可在不连续位置 ID 下工作，从而使未选中模块不必出现在 token 序列里。
  • 与自动前缀缓存互补：前缀要求左对齐相同；模块缓存覆盖互斥、非前缀片段。
  • 论文报告 GPU 约 8×、CPU 约 60× 的首 token 加速，质量接近基线，不改权重。
  • 槽位超长、schema 变更、与计费向「prompt caching」同名不同义，都是工程陷阱。
  • 出处：Gim et al., Prompt Cache: Modular Attention Reuse for Low-Latency Inference，MLSys 2024；arXiv:2311.04934。
