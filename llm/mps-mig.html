MPS 与 MIG ​

一张 GPU 要给多个进程用，无非两条路：软件上挤着跑，或硬件上切成多份。隔离强度与利用率正好对调。

—— NVIDIA CUDA MPS 文档与 Multi-Instance GPU User Guide

数据中心很少让一张 A100 / H100 只跑一个 7B 推理进程。空闲的 SM 与空闲的 HBM 是真金。CUDA Multi-Process Service（MPS）让多个进程的 kernel 在同一块 GPU 上并发，共享上下文服务器，提高占用。Multi-Instance GPU（MIG）从 Ampere 起用硬件把一张卡切成多份实例，每份有自己的 SM、HBM 切片与隔离。两者可以叠：MIG 用户指南写明可在每个 GPU 实例上再开 MPS。本篇对齐这两种并发机制各自解决什么、不能解决什么。不把某一云厂商的切片售卖策略写成硬件规格。

与 连续批处理 的差别：连续批处理是同一进程内的请求复用；MPS / MIG 是多进程 / 多租户复用。

问题 ​

时间片共享（默认的多进程轮转）会让 A 的大 kernel 挡住 B 的延迟敏感 decode。MPS 把多个客户端接到一个 MPS 服务器，kernel 可以在 SM 上空间并发，利用率上升。代价是：它们仍共享同一份 HBM 与同一套内存保护叙事（Volta 之后 MPS 增强了错误隔离，但不是 MIG 那种硬件分区）。一个进程把显存吃光，邻居 OOM；一个恶意或有 bug 的 kernel，影响面仍是整卡或整份 MPS 域。

MIG 要解决的是另一端：云上要把一张 A100 卖成最多 7 份，彼此的显存带宽、SM、故障要隔离。启用 MIG 需要把 GPU 置于 MIG 模式（用户指南写 A100/A30 切模式要复位 GPU）。切完之后，每个 GPU Instance 在 CUDA 里像一张小卡。代价是：切片粒度固定，碎片可能浪费；跨实例不能当一张卡做 NVLink 全卡 TP；部分功能在 MIG 下受限。

官方能力边界 ​

NVIDIA MIG 用户指南给出驱动与 CUDA 下限：A100 / A30 走 CUDA 11 与对应数据中心驱动；H100 / H200 走 CUDA 12；B200 一类需更新的 R570 驱动。H100 SXM 产品页写最多 7 个约 10GB 的 MIG。A100 同样最多 7 实例，切片表（1g.10gb 等）以该代指南为准，不要跨代抄。指南还写：MIG 模式下不支持把整卡设成 EXCLUSIVE_PROCESS 来跑「一个 MPS 服务器管整卡」——因为每个 MIG 实例要自己的 MPS 服务器。

MPS 文档的模型是：控制守护进程、服务器、客户端；客户端的 CUDA 调用转到服务器。Volta 起改进了内存保护。MPS 不把 HBM 切成硬配额（配额若存在，也是软件配置，不是 MIG 的硬件隔离）。客户端上限在 MIG 上还要按 Compute Instance 大小比例下调，用户指南写最大客户端数 48 会按 CI 尺寸比例降低。

看见 nvidia-smi 里多个进程贴在同一张卡上，不要立刻说「已经 MIG 了」。MPS 是进程级共享；MIG 会列出 MIG- UUID 与 GI / CI。两者在 smi 上的样子不同。

方法 ​

选机制先问隔离还是利用率。

  • 同一信任域、要榨干 SM（同一作业的多进程、或内部多模型）：MPS。设好 CUDA_MPS_PIPE_DIRECTORY，客户端指向同一服务器。延迟敏感与吞吐型混部时，MPS 仍可能互相抢 SM，需要在应用层限并发。
  • 多租户、要硬隔离显存与 SM：MIG。按用户指南切 GI，再在 GI 上建 CI。把 CUDA_VISIBLE_DEVICES 设成 MIG UUID。调度器应把实例当独立设备，不要假设它们能 P2P 成一张大卡。
  • 隔离之后仍有多进程：每个 MIG 实例单独起 MPS：不同的 CUDA_MPS_PIPE_DIRECTORY，CUDA_VISIBLE_DEVICES 绑该实例 UUID。这是指南中的标准叠法。

LLM 服务上，小模型多副本适合 MIG：每份实例一份权重，QoS 硬的。大模型单副本需要整卡甚至整 NVLink 域，MIG 会把卡切碎，TP 跨实例走不通或退化到更慢路径。MPS 适合「同一张卡上多个小上下文的进程」或旧式多进程数据加载；现代服务更常在单进程里连续批处理，MPS 的收益下降。不要为了「看起来在用 MPS」而把已经合并的服务再拆成多进程。

与 NVLink、超节点 ​

MIG 切的是单卡内部。NVLink 域、NVL72 的 72 卡全互连，不因为 MIG 而变成 72×7 个对等加速器——每张卡切完，域的对称性按实例如何连到 NVLink 端口而定，细节以该代 MIG 与 NVLink 文档为准。不要规划「用 MIG 把超节点切成 504 路迷你 GPU 再做 TP」。超节点的切分单位是整卡或整域，见 NVL72。MPS 不改变拓扑，只改变一张卡上有几个上下文在发核。

机制 ​

MPS 的机制是集中式 CUDA 上下文：服务器拥有 GPU，客户端的启动被转发，SM 上可以同时有来自不同进程的 warp。没有硬件把 HBM 带宽按进程封顶（除非另做 QoS）。于是利用率高、吵闹邻居也高。MIG 的机制是把 SM、L2、HBM 控制器切片交给不同的 GPU Instance，IOMMU / 硬件防火墙级隔离，故障与性能干扰被限制在实例内。切模式需要复位，是因为内存系统与 SM 的分区是静态硬件配置，不是运行时随便改的软件开关。切完之后实例管理可以动态一些，指南把「模式」与「实例」分开写。

两者都不是魔术：总 SM 数与总 HBM 不变。MIG 的切片表若切不齐工作负载，边角料浪费。MPS 的并发若导致 cache 颠簸，占用上升、有效带宽下降，屋顶线的 \(\eta_b\) 变差。

vGPU 与 MIG 可以组合，用于虚拟机里的实例。那是虚拟化栈的故事。本篇只盯 CUDA 进程看到的 MPS 与 MIG。云上的「1/7 A100」通常是 MIG 或 vGPU，以云文档为准。

QoS 与故障 ​

MIG：邻居 OOM 不会吃掉你的切片；邻居的 kernel 超时不应拖垮你的 SM。这是租户 SLA 的基础。MPS：邻居可以占满 SM，你的 decode TPOT 抖动。要用 MPS 做多租户，必须在上层限流，不能把硬件隔离预期套上去。故障恢复：MIG 实例可以按 UUID 重启进程；MPS 服务器崩溃会影响所有客户端。监控上，MIG 应按实例采 nvidia-smi；MPS 要看服务器日志与整卡指标。

边界与工程取舍 ​

不要在 MIG 模式下按整卡 MPS 文档去设 EXCLUSIVE_PROCESS。不要把 A100 的 7 路切片表抄到 H100 上却仍写 10GB——H100 产品页对 SXM 写约 10GB，NVL 形态是约 12GB，形态不同。不要期望 MIG 实例之间走 NVLink 做层内 All-Reduce。不要用 MPS 修复连续批处理没写好的单进程占用。

CUDA Graph 在 MPS / MIG 上可用，但捕获绑上下文；多客户端不要共享一张可执行图。昇腾的虚拟化 / 切分是另一套产品名，不能把 MIG UUID 流程写过去。

出处：NVIDIA Multi-Instance GPU User Guide（含 MPS on MIG）、CUDA MPS 文档、H100 / A100 产品页上的 MIG 路数。不引用未公开的切片带宽保证值。

小结 ​

  • MPS：多进程空间共享一张 GPU，提高占用，隔离弱；适合同信任域。
  • MIG：硬件切 SM 与 HBM，最多路数以该代产品页为准（A100 / H100 SXM 均为最多 7 路量级），适合多租户。
  • 可在每个 MIG 实例上单独跑 MPS；不要用整卡 EXCLUSIVE_PROCESS 套到 MIG 上。
  • 大模型 TP 与超节点域需要整卡 / 整域，不要用 MIG 切碎后模拟全互连。
  • 连续批处理是进程内复用，优先于为了复用而拆多进程。
  • 出处：NVIDIA MIG User Guide 与 CUDA MPS 文档。
